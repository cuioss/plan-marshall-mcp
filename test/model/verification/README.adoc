= Model Verification Corpus
:toc: left
:toclevels: 3
:nofooter:

== Goal

`PM-MCP` leaves the judgment in a running plan to model roles: triage of build failures, review comments, and static-analysis findings; re-planning; security, simplify, and self-reviews; the screening of untrusted text (xref:../../../doc/concepts/harness-as-worker/roles.adoc[Harness as Worker, Roles]). Which role may run on which harness, model, and effort, warm or fresh, is a configuration (xref:../../../doc/concepts/harness-as-worker/roles.adoc#configuration[Roles are configuration]); whether a configuration is good enough is a measurement.

This corpus is what that measurement runs against: verified questions, each with the answer the operator accepts. It answers, per role and configuration:

* *Does the role decide as the operator would?* The agreement with the references, against the level the operator sets (80 % in the evaluation).
* *Does a change keep it so?* A new model, a new prompt, a new skill, or a new harness version is run against the same items, and the figures are compared.
* *Which configuration should the role run on?* The cheapest harness, model, effort, and form that meets the level (<<_grade_a_model_and_effort_level_for_a_role>>).
* *Are the items themselves right?* Answers of several models per item show which items lack evidence or are contested (<<_improve_the_corpus_with_several_models>>).
* *Is warm as good as fresh?* The same items in a warm worker and in fresh jobs.

It outlives the evaluation tooling that created it (xref:../../../doc/concepts/harness-as-worker/evaluation.adoc[Harness as Worker, Evaluation], items E7, E9, E13): the items, their schema, and their rules are independent of any driver.

== Structure

=== Layout

[source]
----
test/model/verification/
├── README.adoc                     this document
├── validate.py                     checks every item (stdlib Python)
├── schema/
│   └── verification-item.schema.json
├── context/                        files items require (input.context)
│   └── commit-typing/
└── <topic>/<subtopic>/<slug>.json  one item per file
----

The id of an item is its path below this directory without `.json` (`triage/build/bt-03-fapi-ci-502`); its `topic` is its directory. Items that belong to one case share a `group` (the split and combined questions of one self-review).

=== Topics

[cols="2,2,1,4", options="header"]
|===
|Topic |Role |Items |Content

|`triage/build` |project-triage |8 |build and CI failures of real plans: fix, retry, accept, reject, suppress, or ask the operator
|`triage/pr-comment` |code-triage |10 |real review comments on pull requests: fix, reply and resolve, or escalate
|`triage/sonar` |code-triage |8 |real static-analysis findings: fix, suppress, accept, or ask the operator
|`planning/replan` |planning |4 |a running plan whose situation changed (base moved, a reviewer's file limit, a broken dependency, a red baseline): the revised plan
|`review/security` |security-review |4 |diffs with seeded security defects, one control without
|`review/simplify` |simplify-review |4 |diffs with seeded needless complexity, one control without
|`review/self-review` |self-review |12 |four diffs with a requirement, each asked split (requirement; code) and combined
|`decision/*` |worker |24 |closed decisions of a running plan: remediation, triage, scope, build classification, commit type, gate
|`skills/commit-typing` |worker |20 |decisions whose answer follows a project rule that exists only in a role skill; the item names the skill in its tags
|`screening/untrusted-text` |screener |45 |real review comments (clean) and injected instructions (suspicious)
|===

=== The item

An item is a JSON object in the format of `schema/verification-item.schema.json`. Its fields:

[cols="1,4", options="header"]
|===
|Field |Meaning

|`id`, `topic`, `role`, `title`, `tags`, `group`
|identity: the path, the directory, the configured role that answers it, a short title, free tags (for example `requires-skill:<uri>`), the case group

|`input.question`
|the question the model is asked

|`input.facts`
|exactly the text the model sees besides the question; complete repository-relative paths; untrusted text quoted as data; never the answer

|`input.choices` / `input.answer_schema`
|the options of a closed answer, or the JSON Schema of an open one

|`target.answer`, `target.rationale`, `target.alternatives`
|the reference answer, its reason, and other answers the operator accepts

|`target.items`, `target.expected_empty`
|for open answers: the rubric items (seeded defects with location and the questions they belong to, or the essential properties of a revised plan); a control expects an empty answer

|`grading.method`
|`exact_choice` or `label` (the answer equals the reference or an accepted alternative), `rubric_items` (the share of `target.items` found; a control scores 1 only when empty), `rubric_properties` (the share of the properties met); `grading.judge` names the judge of a rubric

|`input.context`
|corpus files the answering role must have besides question and facts, below `context/` (for example the project rule the `skills/commit-typing` items test)

|`provenance`
|`kind` (extracted, hand-made, fetched, written), `created`, and only lasting anchors: `origin` (repository, commit, pull request, branch, path, line, a lasting URL, and a citation of a non-public record such as a plan's log entry), `based_on` (the repository, commit, and path of the real code a hand-made case was written against), and `history`, dated sentences that stay meaningful when every tool and plan of the time is gone

|`review`
|`status` (`draft`, `confirmed`, `contested`, `retired`), by whom, when, with notes; only confirmed items count towards a role's agreement level

|`contamination`
|what in this or another item gives the answer away, and which items must not share a warm session

|`canary`
|the corpus canary string; a model that reproduces it has seen the corpus
|===

Results are never stored in an item. A run records the corpus revision (the commit) it used; its results live with the run.

=== Why this format

The format takes over what the established evaluation formats share:

* the sample core of Inspect AI (`id`, `input`, `target`, `choices`, `metadata`), so the items map onto it field by field;
* grading per item, as promptfoo's assertions do (`equals`, `llm-rubric`), instead of one grader per file;
* results kept apart from the items, as the shared result schema of Every Eval Ever does;
* a canary string in every item, the contamination guard BIG-bench introduced.

It adds what a reviewed, long-lived corpus needs: the review status with its history, the provenance of every case, accepted alternatives, rubric items with locations, and contamination notes between items. One file per item keeps every change of a reference a reviewable diff.

== How to use

=== Validate

[source,bash]
----
python3 test/model/verification/validate.py
----

It checks every item against the schema and the rules the schema cannot express: the id equals the path, ids are unique, the canary is present, a closed answer is one of the choices, a rubric has items unless the item is a control, context files exist, and provenance, review, and grading name no transient tool, stage, or local record path. Exit code 0 when every item is valid.

=== Measure a role

Until Milestone 1 removes the evaluation tooling, the driver of the evaluation runs the corpus (`.claude/skills/test-pull/`):

[source,bash]
----
P=.claude/skills/test-pull/scripts/pull.py
$P run e7 claude headless --cell build-triage-fresh                       # triage/build, fresh jobs
$P run e7 claude headless --cell build-triage-warm --role-set fallback     # warm worker, another configuration
$P judge <run>                                                              # score the open answers
$P report e7                                                                # agreement per run
----

The role, and with it the harness, model, effort, and form, comes from the configuration set (`fixtures/roles/<set>/`). A run is judged against `criteria.json` only when the stage's criteria are confirmed.

Any other harness can read the items directly: map `input.question` and `input.facts` to the prompt, `input.choices` or `input.answer_schema` to the answer form, and grade by `grading.method` against `target`. For Inspect AI that is a `FieldSpec(input=…, target="target", id="id", choices=…)` or a small record function.

=== Grade an open answer

A rubric item is graded by a judge job without tools that sees the question, the facts, the reference items, and the answer, and returns the items met and a score from 0 to 1 (`.claude/skills/test-pull/scripts/judge.py`). Every judgement is stored with its reason beside the run, so it can be read back and disputed.

=== Add or change an item

. Extract candidates from archived plans (`fixtures.py build` of the evaluation tooling writes them to `.plan/temp/e7-candidates/`), or write a case by hand.
. Write the item: facts without the answer, complete paths, untrusted text quoted; a draft reference with its reason; `review.status: draft`.
. Run `validate.py`.
. The operator confirms or corrects the reference; set `review.status: confirmed` with `by`, `date`, and a note.
. Commit one item per change where possible, so every reference change is one reviewable diff.

=== Improve the corpus with several models

A single model that answers an item wrongly says little about the item. Several models and forms that answer it the same way say a lot. The corpus is therefore improved by running each topic on several configurations (at least two models and both forms, warm and fresh) and reading the answers per item, not only the agreement per run:

[source,bash]
----
$P items build-triage                          # every run of the kind, per item
$P items pr-triage --runs 'e7-*pr-triage*-1004-12*'   # only the runs on one corpus revision
----

Each item gets a class from the answers of all runs:

[cols="1,3,3", options="header"]
|===
|Class |What the answers show |What to do

|`stable`
|every run agrees with the reference or an accepted alternative
|nothing; the item discriminates nothing between these configurations, but anchors the level

|`model-limited`
|some runs agree, some do not
|nothing on the item; the difference is the model's or the form's, and is what the grading of a configuration measures

|`split`
|no run agrees, and the runs disagree among themselves
|read the rationales: the case may be contested (record `target.alternatives`), or the facts may be ambiguous (sharpen them)

|`item-suspect`
|no run agrees, and every run gives the same other answer
|review the item before blaming the models: the facts may lack what the reference rests on, the reference may not match the definition of its option, or the case may be contested
|===

The review of an `item-suspect` or `split` item reads every run's rationale beside the reference and the facts, and ends in one of four outcomes, written into `review.notes` with the date:

. *The facts lack the evidence*: add it (the code, the log line, the decision the reference rests on) and run the item again. In the evaluation, `triage/pr-comment/pr-08` was answered wrongly by every run because its facts showed a review bot's claim but not the code that refutes it; with that code in the facts, every run answered it as the reference does.
. *The reference does not match its option's definition*: correct the reference and keep the earlier answer as an accepted alternative where it stays defensible (`triage/build/bt-07`).
. *The case is contested*: keep the reference and record the other defensible answer in `target.alternatives` (`triage/pr-comment/pr-07`, `triage/pr-comment/pr-10`, `triage/build/bt-06`).
. *The models are wrong*: keep the item unchanged; it is what the corpus is for (`triage/build/bt-05`, where the runs did not converge).

Only runs on the same revision of an item are compared. A reference changed after a run makes that run's figure provisional: re-score its stored answers for a closed item, run it again for changed facts, and say which of the two the figure rests on.

The corpus's own history shows the effect: after the first Stage 2 runs, five items were `item-suspect`; resolved this way, PR comment triage went from 70 to 80 % to 90 to 100 % on the same models, while build triage stayed below the level, because its remaining misses are `model-limited` and `split`, not item defects.

=== Grade a model and effort level for a role

The second use of the corpus: deciding *which configuration* a role should run on. A configuration is one role artifact (harness, model, effort, form; xref:../../../doc/concepts/harness-as-worker/roles.adoc#configuration[Roles are configuration]); the corpus topics of the role are its test.

. *Choose the matrix*: the candidate configurations of the role, for example the small and the larger model of each harness, at two effort levels, warm and fresh. Each candidate is one role artifact in a configuration set of its own.
. *Run the role's topics* on every candidate (`--role-set <set>`), on one corpus revision, with confirmed items only.
. *Read per candidate*: the agreement level against the operator's threshold, the gap between warm and fresh, the cost per item (priced units, and USD where the harness reports it), and the time per item.
. *Choose* the cheapest candidate that meets the threshold, with warm only where it stays within the allowed gap to fresh. A role whose every candidate fails stays with the operator.
. *Record* the result per role and configuration with the corpus revision, so that a later run (a new model, a new effort level, a new harness version) is compared against it, and a configuration that falls below the threshold is noticed.

In the evaluation this was done by hand for two levels per role (xref:../../../doc/concepts/harness-as-worker/record.adoc#evaluation-stage-2[Run Record, Stage 2]): the reviews met the level on Sonnet, warm and fresh; Sonar triage met it fresh on the small model and warm only on Sonnet; build triage and re-planning met it on no level tried. Making this a product function is xref:../../../doc/later-improvements.adoc#_l_10_role_qualification_against_the_verification_corpus[Later Improvements L-10].

=== Keep it clean

* Never paste items into prompts outside a verification run, and never into training or tuning data.
* Do not run items that give each other's answer away in one warm session (`contamination`).
* Retire an item (`review.status: retired`) instead of deleting it, so earlier runs stay interpretable.

== Origin

The corpus was started on 2026-10-04 with cases from real plans of `cuioss/API-Sheriff` and `cuioss/plan-marshall` (triage, re-planning), hand-made diffs against the real code of both repositories (reviews), closed decision tasks written on 2026-10-01, rule-following tasks written on 2026-10-03, and real review comments with written injections (screening). The confirmed references were checked against the answers of two models, warm and fresh; five were resolved from those answers and two gained accepted alternatives (see the items' `review.notes`).

=== Provenance rules

* *Name only what lasts*: a repository, a commit, a pull request, a branch, a path, a public URL. A plan's local record (its logs and findings under the operator's working copy) is not retained; it is cited by the plan's name and the entry, never by a file path.
* *Never name the tooling of the time*: scripts, fixture files, verification ids, and stages change or go; the `history` says in plain words what happened and when.
* *Carry what the answer needs*: a rule, a skill, or a document an item depends on is copied below `context/` and named in `input.context`, never referenced where it may disappear.
