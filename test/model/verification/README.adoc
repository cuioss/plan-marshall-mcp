= Model Verification Corpus
:toc: left
:toclevels: 2
:nofooter:

Verified questions for the model roles of `PM-MCP`: one verification task per file, each with what the model sees, the reference answer, how an answer is graded, where the case comes from, and who reviewed the reference. The corpus measures whether a role, on a given harness, model, and effort, decides the way the operator would (xref:../../../doc/concepts/harness-as-worker/evaluation.adoc[Harness as Worker, Evaluation], item E7). It outlives the evaluation tooling.

== Layout

* `schema/verification-item.schema.json`: the format of an item (JSON Schema, draft 2020-12).
* `<topic>/<subtopic>/<slug>.json`: one item. The id of an item is its path below this directory without `.json`; its `topic` is the directory.
* `validate.py`: checks every item against the schema and the corpus rules (`python3 test/model/verification/validate.py`, exit code 0 when every item is valid).

|===
|Topic |Items |Content

|`triage/build` |8 |build and CI failures of real plans: fix, retry, accept, reject, suppress, or ask the operator
|`triage/pr-comment` |10 |real review comments on pull requests: fix, reply and resolve, or escalate

== The item format

The format takes over what the established evaluation formats share, and adds what a reviewed, long-lived corpus needs:

* *Sample core* as in Inspect AI (`id`, `input`, `target`, `choices`, `metadata`): `input.question`, `input.facts` (exactly the text the model sees besides the question, with complete repository-relative paths), `input.choices` for a closed answer, `input.answer_schema` for an open one.
* *Grading per item*, as promptfoo's assertions do: `grading.method` is `exact_choice` or `label` (the answer equals `target.answer`), `rubric_items` (the share of `target.items` found, such as seeded defects; a control with `expected_empty` scores only an empty answer), or `rubric_properties` (the share of the essential properties met). Rubric methods name their judge.
* *Reference with its reason*: `target.answer`, `target.rationale`, accepted `target.alternatives`, and rubric `target.items` with location and, for split reviews, the questions they belong to.
* *Provenance*: `provenance.kind` (extracted, hand-made, fetched, written), the source (archived plan, file, log entry, URL), the date, and the earlier fixture id.
* *Review*: `review.status` (`draft`, `confirmed`, `contested`, `retired`), by whom and when, with notes. Only confirmed items count towards a role's agreement level.
* *Contamination*: every item carries the corpus canary (`canary`), so that a model reproducing it shows it was trained on the corpus, as BIG-bench introduced; `contamination` names items that give each other's answer away and must not share a warm session.
* *Results are never stored in an item*: a run records the corpus revision it used, and its results live with the run, so that the corpus stays a stable reference.

== Rules

. One item per file; a change of an item's reference is a reviewed change with a new `review` entry.
. Facts never contain the answer; untrusted text (review comments, analysis messages) is quoted as data.
. Paths in facts are complete and relative to the repository root; text is cut only at word boundaries.
. A new item starts as `draft`; it enters the agreement level of a role when the operator sets `confirmed`.
. An item whose reference every run decides against is reviewed: its facts may lack what the reference rests on (the notes of the five such items name the answers the runs gave).
. Keep the corpus out of training data where possible: it is public in this repository, so the canary is the only protection; never paste items into prompts outside verification runs.

== Origin

Imported on 2026-10-04 from the evaluation of the harness as worker: the E7 fixtures with the operator's references (confirmed), the decision tasks of Part A, the E13 skill-rule tasks, and the E9 screener corpus (draft). New candidates are extracted from archived plans with the evaluation tooling and enter the corpus after review.

Format research: Inspect AI datasets (sample fields `input`, `target`, `choices`, `id`, `metadata`; JSON, JSONL, CSV), promptfoo test cases (variables, assertions per case such as `equals` and `llm-rubric`, metadata tags, one file or directory per test set), OpenAI Evals (JSONL samples with an eval class), Every Eval Ever (a shared schema for results, kept apart from the items), and the contamination practice of canary strings (BIG-bench).
