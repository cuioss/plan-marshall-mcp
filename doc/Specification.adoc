== Overview
_See Requirement link:Requirements.adoc#PM-ARCH-1[PM-ARCH-1: Process Ownership & Always-On Runtime]_

This document serves as the master technical specification index for *plan-marshall-mcp* (`PM-MCP`). While the link:Requirements.adoc[Requirements Document] specifies *what* the system must accomplish and the normative constraints it must satisfy, this specification tree defines *how* the system is designed, its internal architecture, data structures, wire protocols, and execution contracts.

For development sequencing and milestone delivery gates, see the link:roadmap.adoc[Roadmap]. Defect archetypes, real-corpus fixtures and verification hints that guard each specification document during implementation are collected in the link:ImplementationWatch.adoc[Implementation Watch].

== Specification Lifecycle Governance

Every component specification in `doc/specification/` declares its lifecycle status immediately following the traceability block using the following standard indicators:

[cols="1,2,3"]
|===
|Status |Meaning |Criteria for Transition

|`Status: PLANNED`
|Pre-implementation technical blueprint.
|Complete architecture, exact schemas, wire protocols, edge cases, and backtracking links to `Requirements.adoc` are defined. No code yet written.

|`Status: IN PROGRESS`
|Active implementation and testing underway.
|Implementation tasks in progress; partial code committed; contract being actively exercised by unit or integration tests. Entry requires that the specification's watch items (its watch document in `doc/implementation-watch/` and every `cross-cutting.adoc` item anchored to it) have been read and planned into the implementation tasks.

|`Status: REFERENCE`
|Non-normative reference that substantiates values of other specifications.
|Updated with every new measurement; never implemented. Its traceability names the requirements whose values it substantiates; the normative values stay in their owning specifications.

|`Status: DEPRECATED`
|Superseded or retired component.
|Replaced by a newer specification or made obsolete by an architectural shift; migration notes provided.
|===

There is no `IMPLEMENTED` status: a specification is scaffolding for code that does not exist yet, and implemented content is removed rather than marked. The implementation PR verifies every normative statement of the implemented sections, the requirements they trace to, and the anchored watch items against code and tests, and writes the concept, developer and user documentation of the implemented slice from the specification and watch corpus (`doc/Concepts.adoc`, `doc/DeveloperGuide.adoc`, `doc/UserGuide.adoc` and their folders), describing the implemented system as verified against the code; once that coverage is verified, the same PR deletes the implemented sections (a part or specification document left without normative sections is deleted together with its index row) and links each requirement to the implementing classes, tests and documentation sections. A specification with sections remaining keeps `IN PROGRESS`. The procedure is the project skill `traced-implementation` (`.claude/skills/traced-implementation/SKILL.md`).

== Traceability Requirements
_Implementation watch: link:implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-35[PM-WATCH-GEN-35]_

To ensure complete, verifiable traceability across the project lifecycle:

1. *Backtracking from Specifications*: Every specification document must include an explicit `== Traceability` section listing the `Requirements.adoc` IDs it fulfills, with relative links to `../Requirements.adoc#PM-<DOMAIN>-<NUM>`.
2. *Forward Linking from Requirements*: Every requirement in `doc/requirements/` must cross-reference its governing technical specification(s).
3. *Implementation Traceability*: When a specification section is implemented, each requirement it traces to receives an `Implementation:` line linking the production classes in the owning module's `src/main/java/` (the modules of the link:specification/module-structure.adoc[Module Structure Specification]), a `Verified by:` line linking the automated tests in its `src/test/java/`, and a `Documentation:` line linking the concept, developer and user documentation sections that describe it; the implemented section itself is then deleted (§ Specification Lifecycle Governance), so the link runs from requirement to code and documentation, never through the specification.
4. *Module Linking*: The link:specification/module-structure.adoc[Module Structure Specification] is the only listing of the modules; other documents name modules without repeating the listing. Its *Specified in* column names the specification documents (or parts) each module implements, and every specification document names its implementing modules in a `== Modules` section directly after its status, linking each module's row. Both directions change together: a module, a part, or an assignment that is added, moved or removed is updated on both sides in the same change.
