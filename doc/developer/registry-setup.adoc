== Why a Token Is Needed
_Requirements: link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]_

The artifacts of the product are deployed to the GitHub Packages Maven registry of the organisation `plan-marshall` and resolved from there. That registry answers no anonymous request, not even for the package of a public repository: without a token Maven gets `401`. A build that resolves a module or the parent POM from the registry therefore needs a token on every machine.

== One-Time Setup of a Developer Machine
_Requirements: link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]_

. Create a personal access token on GitHub: *classic*, with the scope `read:packages` only. A fine-grained token does not work with the Maven registry.
. Add a server with the id `plan-marshall` to `~/.m2/settings.xml`. The element must lie inside `<servers>`; Maven ignores a `<server>` directly below `<settings>` with a warning.
+
[source,xml]
----
<settings>
  <servers>
    <server>
      <id>plan-marshall</id>
      <username>YOUR_GITHUB_LOGIN</username>
      <password>YOUR_TOKEN</password>
    </server>
  </servers>
</settings>
----
. Check it from the repository root. The output must show your login as the user name of the server `plan-marshall` and no warning about the settings:
+
[source,shell]
----
./mvnw -N help:effective-settings
----

An agent worktree on the same machine uses the same `~/.m2/settings.xml` and needs nothing of its own. The token is never set as the environment variable `GITHUB_TOKEN` on a developer machine, because `gh` would then use it instead of its own login.

== How the Repository Finds the Registry
_Requirements: link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]_

The registry cannot be named in a POM, because the parent POM itself comes from it. It is named in link:../../.mvn/settings.xml[`.mvn/settings.xml`], which holds no token and which link:../../.mvn/maven.config[`.mvn/maven.config`] passes to every `./mvnw` call as the *global* settings (`-gs`):

* As global settings it is merged with the personal `~/.m2/settings.xml`, and the personal file wins. Passed as user settings (`-s`) it would replace the personal file with its mirrors and servers.
* It activates a profile with two repositories: Maven Central first, so that no third-party artifact is looked up in the organisation registry, then `https://maven.pkg.github.com/plan-marshall/*`, which covers every repository of the organisation, for releases and `SNAPSHOT` versions.
* It declares the server `plan-marshall` with the user `${env.GITHUB_ACTOR}` and the password `${env.GITHUB_TOKEN}`. This is the server of a CI job, where no personal settings exist. On a developer machine the server of the same id in `~/.m2/settings.xml` replaces it.
* The path in `maven.config` is `${session.rootDirectory}/.mvn/settings.xml`, so a call from a module directory finds it as well.

== Continuous Integration
_Requirements: link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]_

A CI job resolves with the `GITHUB_TOKEN` of its workflow, which must be in the environment of the step that runs Maven. That token reads the packages of a public repository of the organisation without a further permission; it cannot read a package of another, private repository.

While every module is built in this one repository, nothing is resolved from the registry. A build without a token then passes with one warning: the metadata lookup of the `SNAPSHOT` of `pm-mcp-server`, which `pm-e2e` orders itself after, is answered with `401`, and Maven takes the module from the reactor.
