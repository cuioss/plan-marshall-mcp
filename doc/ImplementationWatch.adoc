== Overview

The link:Requirements.adoc[Requirements] state *what* PM-MCP must do and the
link:Specification.adoc[Specification] states *how*. This watch list holds what neither states normatively
but what the implementation must not get wrong: defect archetypes that plan-marshall reproduced in
production, real-corpus fixtures, and verification hints. Every item is anchored to the specification
section or requirement it guards, so whoever implements that section reads its watch items first.

The items were carried over from the known-defect corpora of the plan-marshall epics
(`truthful-signals`, `code-intelligence-substrate`, `review-apparatus`, `process-compliance`,
`post-run-quality`, `instrumentation-substrate`, `lessons-routing`, `orchestrator-refactor`; source
ledgers under `.plan/orchestrator/<epic>/` in the plan-marshall repository). Only
implementation-independent content carries: Python- and prose-bound findings of those corpora do not
apply to PM-MCP. A few items guard hazards of PM-MCP's own design decisions that have no plan-marshall defect record
(for example the native git and provider integrations); their *Source* names the decision.

== Item Format

Each watch document in `doc/implementation-watch/` mirrors one specification document of the same name
(`cross-cutting.adoc` holds archetypes that span all of them). Each item has an anchor
`[#PM-WATCH-<AREA>-<N>]`, a title and these fields:

[cols="1,4"]
|===
|Field |Content

|*Anchor*
|The specification section or requirement the item guards (link).

|*Hazard*
|What went wrong in plan-marshall: the observed defect, stated implementation-free.

|*Guard*
|What the implementation must do, and the test that proves it.

|*Fixture*
|Optional: real-corpus data the test uses verbatim.

|*Source*
|Epic, plan and deliverable in plan-marshall the item came from, or the PM-MCP design decision it guards.
|===

Area codes: `RUN` runtime-model, `CLI` cli-and-security, `TOOL` mcp-tools, `HYP` hypermedia-format,
`DSL` workflow-dsl, `PHASE` phase-workflows, `DISP` dispatch-and-effort, `EXT` domain-extensions,
`FS` filesystem-layout, `STORE` store-schemas, `JOB` job-runtime,
`CLIENT` client-profiles, `GEN` cross-cutting.

Item numbers are never reused or renumbered: an item deleted because its hazard no longer applies (for example the
items that guarded the removed legacy import, withdrawn by the operator decision of 2026-09-27 that `PM-MCP` imports
nothing from plan-marshall) leaves a gap in its area's numbering.

== Lifecycle

Every specification section and requirement named in an item's *Anchor* carries an _Implementation watch_ line
that links back to the item, so whoever plans or implements that section finds its items. The roadmap milestone that
implements a specification section also covers its watch items, and the specification lifecycle
(link:Specification.adoc#_specification_lifecycle_governance[Specification Lifecycle Governance]) gates on them.
The procedure is the project skill `traced-implementation` (`.claude/skills/traced-implementation/SKILL.md`):

* *Before `IN PROGRESS`*: the specification's watch document and every `cross-cutting.adoc` item anchored to the
specification have been read and planned into the implementation tasks, each item with the test that will guard it.
* *Guarding an item*: the guarding test implements the *Guard*, uses the *Fixture* verbatim, and states the hazard
in its Javadoc with the requirement ID, so it explains itself without this document.
* *Removing an item*: once the implementation PR has verified that the guarding test exists, the item is deleted in
that same PR together with the _Implementation watch_ backlinks to it; items are not kept as records. A
`cross-cutting.adoc` item anchored to several specifications loses only its implemented anchors and is deleted when
none remains. A watch document left without items is deleted together with its row below.
