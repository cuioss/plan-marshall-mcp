== Overview

This document defines the normative functional and non-functional requirements for *plan-marshall-mcp* (`PM-MCP`): an always-on local Model Context Protocol (MCP) runtime (`pm-mcpd`) with two native command-line binaries (the host-facing relay binary `pm-mcp` and the operator CLI `pm-operator`), reached by coding agent hosts through a native `stdio` relay (`pm-mcp serve`), that replaces prose-enforced workflow instructions and shell-invoked Python scripts with a server-owned hypermedia state machine (HATEOAS) that drives plans and epics through supervised headless workers, warm platform services, and verified native execution.

PM-MCP is built out in parallel to plan-marshall and never shares state with it: it keeps its own repository tree (`.marshall/`) and machine root (`~/.plan-marshall-mcp/`), and never reads plan-marshall's `.plan/` and `~/.plan-marshall/` trees: it imports nothing from plan-marshall, and every project starts from a clean slate. Both systems may be installed on one machine and used in the same repository, where PM-MCP's `mcp-` prefixed entry commands stand beside the plan-marshall plugin's commands (`PM-CLIENT-1`); an enrolled project is offered the PM-MCP plan lifecycle once the lifecycle gate has opened (`PM-MIG-1`, `PM-MIG-2`, `PM-MIG-4`).

For technical implementation blueprints, wire protocols, data schemas, and formal grammars, see the link:Specification.adoc[Technical Specification]. For delivery staging, see the link:roadmap.adoc[Roadmap]. Research notes and open proposals are held in link:discussions/README.adoc[Discussions]. Defect archetypes and verification hints that guard individual requirements during implementation are held in the link:ImplementationWatch.adoc[Implementation Watch]; each guarded requirement names its watch items in an _Implementation watch_ line.

=== Requirement Authoring Conventions (SMART)

All requirements in this document set follow the SMART criteria:

* *Specific*: Each requirement uses unambiguous normative statements ("The system must...") defining exact behavior, inputs, outputs, and constraints.
* *Measurable*: Acceptance criteria specify observable, testable outcomes (latency bounds, closed outcome enumerations, digest checks, and `McpAssured` integration assertions).
* *Achievable*: Grounded in the selected technology stack (Java 25+, Quarkus MCP server `quarkus-mcp-server-http` behind the native `pm-mcp serve` STDIO relay, GraalVM native image, OS credential stores, MCP `2026-07-28` specification).
* *Relevant*: Directly addresses identified cost, reliability, or security limitations of the script-and-prose architecture.
* *Traceable*: Identified by a stable hierarchical anchor `[#PM-<DOMAIN>-<NUM>]` with bidirectional links to technical specifications in `doc/specification/`; the milestones of `doc/roadmap.adoc` link to the requirements they deliver.

== Motivation & System Context

=== Limitations of the Script-and-Prose Architecture

Today, plan-marshall ships as a marketplace of Markdown skills and Python scripts executed via a generated proxy (`python3 .plan/execute-script.py {bundle}:{skill}:{script} ...`) through the host's Bash tool. While functional, this architecture incurs structural costs that motivate `plan-marshall-mcp`:

* *Process rules enforced by prose*: Workflow ordering, finalize gates, and operator-only boundaries live in Markdown instructions. Rules such as "never invent arguments" or "never `--force` the freshness gate" can be misread, ignored, or lost during context compaction.
* *Model-assembled CLI calls*: The model composes every script invocation from prose (plan ID, worktree path, step name, CLI flags), making malformed or stale arguments a recurring defect class.
* *Resident context overhead*: Whole-phase workflow documents remain in model context across turns even when only a single state transition is relevant.
* *Bash as transport*: Routing every operation through Bash requires shell-hygiene rules, PreToolUse hooks, and host permission allowlists solely to police the transport channel.
* *Scratch-file staging for multi-line text*: Passing multi-line text (commit messages, PR bodies, outlines, task descriptions, lesson bodies) over Bash CLI arguments or heredocs triggers shell-quoting hazards, OS `ARG_MAX` limits, and host safety prompts (such as `#` headings in heredocs), forcing multi-step temp-file dances (`prepare-body` / `resolve-path` -> host `Write` to `.plan/temp/` or `work/ci-bodies/` -> script commit call).
* *Skill and script drift*: Skills (loaded from plugin cache) and scripts (resolved via generated executors) travel through separate mechanisms and can diverge across updates.
* *Multi-stage distribution chain*: Source bundles -> target runtime generator -> `target/{runtime}/` -> dist branch -> marketplace install -> plugin cache -> executor regeneration -> host restart.
* *Cold language servers*: LSP queries spawn and tear down a language server per invocation across sub-agents.
* *Static runtime translation*: Supporting frontier coding agents (Claude Code, OpenCode, Antigravity) requires static build-time corpus translation per runtime.

=== Architectural Shift

[cols="2,3"]
|===
|Problem |PM-MCP Requirement & Design Response

|Rules enforced by prose
|The workflow state machine executes inside the server (`PM-WF`); invalid transitions are omitted from representations and rejected on execution.

|Model assembles CLI calls
|The server drives every plan and epic and hands each piece of model work to a supervised worker of a role as a task (`PM-ARCH-1`, `PM-WORK-2`); the worker follows the task's hypermedia links and supplies only a `link` identifier and judgment parameters (`args`) via `pm_do` (`PM-WF-2`).

|Scratch-file staging for multi-line text
|The model passes multi-line UTF-8 text (commit messages, PR/issue bodies, outlines, clarified requests, task descriptions, lessons, ADRs) directly in `pm_do` `args` over JSON-RPC (`PM-WF-2`, `PM-WF-6`); `pm-mcpd` validates and persists stores atomically or pipes payloads in memory via `stdin` to child tools (`PM-EXEC-5`), eliminating `.plan/temp/` and `work/` staging files.

|Duplicated compound operations (commit, push)
|Reusable, config-aware compound sub-workflows (`PM-WF-16`, such as `git.commit_and_push`) execute over a persisted call stack (`call_stack`) and return closed outcomes to any calling phase or tool workflow.

|Resident context overhead
|Only the active state's representation and targeted vocabulary skill enter model context (`PM-SKILL-1`).

|Bash as transport
|All plan-marshall operations execute as typed MCP tool calls over native `stdio`, relayed to the always-on runtime (`PM-ARCH-3`, `PM-TOOL-1`); only the initial entry bootstrap (`pm-mcp enter`) runs in the host shell.

|Skill/script drift
|Skills, state transitions, and tool schemas are served from a single versioned binary (`PM-DIST-1`).

|Cold LSP startups
|The always-on runtime maintains a warm language server pool shared by all host connections (`PM-SVC-2`).

|Static runtime translation
|The server translates tool names, the headless launch conventions of model jobs, and skill references on the fly using data-driven client profiles (`PM-CLIENT-2`) across `claude`, `opencode`, `antigravity`, and `codex`.

|Plans that outlive their premises
|The server detects changed premises of a running plan at fixed checkpoints and re-plans it through one bounded mechanism, a task of the re-planning role with closed actions, guarded like a first plan, never asking the operator (`PM-WF-17`).

|A plan lives only as long as the session that drives it
|The server continues every plan and epic on its own; workers are supervised, recycled, and replaced, every task is delivered exactly once, and the interactive session is entry and viewer (`PM-ARCH-8`, `PM-WORK-3`, `PM-WORK-5`).

|Migration off a running system
|PM-MCP keeps separate state trees (`.marshall/`, `~/.plan-marshall-mcp/`) and never converts, shares, or writes plan-marshall stores (`PM-MIG-2`); its services are usable alongside plan-marshall from their stage on, and an enrolled project is offered the PM-MCP plan lifecycle from the release that meets the Stage 4 exit criteria and therefore ships with the lifecycle gate open (before that only a project enrolled as a pilot), switched off per project by operator release (`PM-MIG-1`, `PM-MIG-4`, `PM-MIG-5`).
|===

Judgment remains strictly with the model: refining requests, authoring solution outlines, implementing code, triaging findings, reviewing, and composing commit/PR descriptions. PM-MCP narrows the model's workflow obligations to doing one task at a time for a role and supplying its judgment artifacts directly as free parameters of the task's hypermedia links.

[cols="1,3"]
|===
|Term |Definition

|Machine
|The developer's workstation running the `PM-MCP` native processes and any number of coding agent hosts.

|Host
|A frontier coding agent runtime connecting to MCP servers over `stdio` and hosting the model (`claude` for Claude Code, `opencode` for OpenCode, `antigravity` for Antigravity, `codex` for Codex).

|Host session (entry session)
|A single interactive conversation instance within a host. It spawns a `pm-mcp serve` relay over `stdin`/`stdout`, carries no workflow state, turns the user's words into a plan or an epic through an entry command, drives the bootstraps and the project setup, shows the scope and its questions, and may take a task as an optional worker (`PM-WORK-5`).

|Plan and epic continuation
|A plan or epic is identified solely by its ID, carried solely by the scope's persisted files, and continued by the server; any host connection views it with `pm_state` (`PM-ARCH-8`).

|Workspace scope
|The one plan-less scope of an enrolled project, addressed as `plan_id: "NO_PLAN"` and resolved from the relay's `PM-MCP-Workspace` header (`PM-ARCH-4`). It hosts the `project-setup` workflow, the pending plan and epic bootstraps, the lesson maintenance, and the ledger rows, findings, and logs of plan-less service calls, in its home `<PM_MCP_BASE>/projects/<project_id>/workspace/` of the per-project machine store.

|Per-project machine store
|The machine-local home of all server-owned state of one enrolled project, `<PM_MCP_BASE>/projects/<project_id>/`, keyed by the project's enrolment identifier: plan directories (never moved), archived plans, the lesson store, the workspace home, the epics' non-tracked state, pending entry records, and the scope locks (`PM-ARCH-5`). The repository keeps only worktrees and temporary files in its git-ignored `.marshall/local/`.

|Bootstrap
|The sub-workflow (`bootstrap-plan`, `bootstrap-epic`) that gathers everything a new plan or epic needs before it exists (what to work on, its source and the source's verification), run as an entity of the workspace scope addressed by its `entry_id`; the scope is created atomically when the bootstrap completes, so an abandoned start leaves no scope behind (`PM-TOOL-1`).

|Role
|A configuration artifact that defines one kind of model work: class and exact tool set, harness, model, effort, form (`warm` or `fresh`), count, skills, and recycling. The roles that exist are the artifacts present; workflows name them freely, and one model caller acts on the artifact (`PM-WORK-1`).

|Task
|One piece of model work for a role, persisted in the task queue, leased to one worker generation, and ended in a closed outcome (`PM-WORK-2`).

|Worker (model job)
|A headless harness process of a role that the runtime launches as a job of kind `llm`, with a server-composed launch prompt and a job-bound connection back to PM-MCP; it receives tasks through `pm_wait` (a fresh worker its one task in its launch prompt), works along each task's links, and submits results. A _fresh_ worker serves one task, a _warm_ worker serves tasks while its role has work. The runtime supervises, recycles, and replaces it and observes its end and usage itself; the host never dispatches a sub-agent (`PM-WF-5`, `PM-WORK-3`).

|Generation
|The identity of one worker or session start, issued with its job token (or at session entry) and carried by its relay; tasks are leased to a generation, and a fenced generation's calls are refused (`PM-WORK-2`).

|Screener
|The fresh zero-tool worker that judges external text the deterministic validator has already cleaned, the second level of the guard for external text; it can only withhold text, never admit it (`PM-SEC-1`).

|PM
|A model participant: the model of the entry session or of a worker.

|Operator
|The human developer responsible for the machine and its repositories. Enrols and releases projects, sets waivers, aborts plans and epics, resolves integrity breaches, and performs privileged actions exclusively via the operator CLI (`pm-operator`) or a paired web device (answering the operator-configuration choices of the project setup also through MCP elicitation), always on the operator's own initiative: no plan waits for an operator decision (`PM-WF-1`, `PM-SEC-3`). Content questions are answered by the user through the question mechanism, never as operator overrides.

|`pm-mcp`
|The relay binary, one of the four native executables of a release (`PM-DIST-1`, `PM-TECH-3`, `PM-IMPL-1`) and the only one hosts and models invoke; it holds no store logic and starts `pm-mcpd` on demand by path. Its verbs are the harness- and model-facing ones only: `pm-mcp serve` (the per-connection STDIO relay; `serve --job` for a worker) and `pm-mcp enter` (link:specification/cli-and-security/01-cli-and-installer.adoc#command-tree[CLI, Coordination & Security Specification, Command Tree]).

|`pm-operator`
|The operator CLI, the binary a human runs at a terminal; it holds no store logic, sends every state change as a request to the runtime's local API, and starts `pm-mcpd` on demand by path. Its verbs stand at its top level without an `operator` sub-level: the operator verbs (`enrol`, `unenrol`, `enrol-harness`, `roles`, `credentials`, `waive` / `unwaive` / `waivers`, `accept-edit`, `abort`, `config`, `sweep`, `upstream`, `release-project`, and the others of the command tree) and `status`, `drain`, `runtime` (on-demand start and service registration of `pm-mcpd`), `client`, and `web`. The client bundles deny the whole binary to the model (`PM-SEC-3`).

|`pm-mcpd`
|The runtime binary (daemon), started on demand by `pm-mcp` or `pm-operator`; it also serves the optional web access (`PM-SEC-7`), and beside it the release ships the job launcher `pm-exec` (`PM-DIST-1`).

|Runtime / Daemon
|The always-on `pm-mcpd` process (one per machine and `PM_MCP_BASE`) executing the workflow engine, state stores, jobs, build slot scheduler, warm LSP pool, MCP proxy, audit log, and, when the operator enabled it, the web access, independent of any host conversation (`PM-ARCH-1`, link:specification/runtime-model.adoc[Runtime & Interaction Model Specification]).

|Relay
|The `pm-mcp serve` process a host spawns over `stdio`; it forwards MCP messages to and from the runtime without interpreting them beyond the closed relay rules (`PM-SEC-4`, `PM-ARCH-3`).

|Entry point & Entry call
|A user-invoked command in the client bundle (`/mcp-plan-marshall`, `/mcp-plan-orchestrator`, `/mcp-marshall-steward`; `$mcp-…` skills on Codex, `PM-CLIENT-1`) that executes `pm-mcp enter --client <client>` to append the session's entry row (client, host build, model, project, entry origin) to the plan, epic, or workspace session log, or to open a bootstrap entry for a plan or epic that does not exist yet.

|Representation
|The TOON-formatted state payload returned by the server describing the current state of a plan or epic, relevant domain facts, and valid hypermedia links.

|Link & Link ID
|A valid state transition offered in a representation (`rel`, `link` identifier such as `submit:TASK-003`, and free parameter names), invoked via `pm_do`; links are offered on task entities to workers and on bootstrap and setup states to the entry session.

|Job
|A build, git, CI, project script, or worker (`llm`) subprocess run by the runtime on the host, independent of any host connection, verified against project enrolment, and awaited by the engine.

|Enrolment
|The operator-authorized registration of a project root, its pinned build wrappers/tools, SHA-256 digests, command templates, and project scripts, held in one file per project, `<PM_MCP_BASE>/enrolments/<project_id>.json`, under its own operator HMAC.

|Plan outcome
|How a plan ends: `merged` (terminal `completed`), `handed_back`, `returned`, or `no_change` (terminal `completed`, an empty recipe harvest), each reached only through `finalize.archive-plan` after the post-run band, or `aborted` by the operator. Every blocking condition ends in a bounded self-remedy and then the defined fallback of its phase (`PM-WF-1`).

|Hand-back
|The fallback from Phase 5 until the merge (`finalize.hand-back`): the work is delivered as an open pull request (a new one opened as a draft, an existing one left as it is, a ready one under `merge.auto_merge: false`), or as a branch where no pull request can exist, with the gaps documented in a pull-request comment and the label `pm-mcp:handed-back`. The fallback of Phases 1–4 is the return (`plan.return`, outcome `returned`): the planning result only, nothing implemented; a plan whose branch already has commits beyond the base is forwarded from the return to the hand-back.

|Remediation policy
|A project-owned DSL sub-workflow unit per failure class (`remediation.qgate-findings`, `.build-failure`, `.ci-failure`, `.analysis`, `.review-findings`, `.merge-conflict`, `.spend`): the server gathers the evidence, and every policy with an action set has a decision step: a task of the policy's role chooses `retry`, `fix`, `loop_back` (the form of `fix` that runs as Phase 5 remediation tasks, bounded by the fix budget), or `request_waiver` within budgets capped by compiled limits (the server itself where only one action is bound); `.spend` is the gather plus the bound waiver wait; the unit returns `resolved`, `waived`, `exhausted`, or `fix_requested`, or `stepped_out` (`PM-WF-7`).

|Waiver
|An operator override of a closed list of process gates and budgets (`pm-operator waive`, `--raise`), plan-scoped, with a mandatory reason, recorded append-only in the plan's waiver record and listed in the pull request and the landing record; the only operator influence on a running plan. A *waiver request* is filed by a worker's `request_waiver` (rel `escalate`) and is answered only by a waiver (`PM-WF-12`).

|Question record
|A server-owned content question (options with `branch_key`, a recommended option with its confidence, rationale, and decision kind, an optional default assumption) created by a worker's `ask` link, an envelope task's `ask:TASK-NNN` link, the `questions` list of a refine or outline authoring task's `submit`, or a server classifier (among them the team-configuration choices of the workspace setup), adjudicated by the decision declarations of its kinds in mode `quorum`, delivered to the user through the web app and the entry session per `questions.mode`, validated and recorded with its channel, and ended by its class fallback when an `auto` question expires. It replaces every in-run operator decision about content (`PM-WF-12`).

|Decision quorum
|The declaration `decide <kind> -> quorum(<role>, ..., <score>)` of the project-owned adjudication unit, the alternative to `ask` (the user decides, the default of every kind): in the question mode `quorum` the listed roles, on pairwise different models, answer a question of that kind blind, without the asker's recommendation (the asking role votes with its recommendation only when it is listed); a question set is answered with the channel `quorum` only when every question's listed roles all choose the same option at or above the score and the declaration is calibrated on the corpus, otherwise it is delivered to the user with every vote (`PM-WF-18`).

|Decision record
|The append-only record of one decision taken at a closed decision point, whoever takes it (a server rule, a role's task, a decision quorum, or the user): its decider, the evidence and facts the decider saw, the options, the confidence or the measured values against their thresholds with their sources, the choice, and the rationale; a later departure appends a correction and never rewrites it. Judgment decisions are exported by the operator as draft items of the model verification corpus (`PM-WF-19`).

|Plan instance
|The composed, immutable, versioned DSL unit each plan executes, built from the workflow templates and the plan's facts with the provenance of every prune, bound budget, and waiver; it carries the step lists and the configuration snapshot, and its diagram shows the process in force (`PM-IMPL-5`).

|Integrity breach
|A tampered plan, epic, or workspace store, a tampered lesson, or a tampered enrolment: the only condition that pauses a scope, ended only by the operator's `accept-edit` or, for a plan or epic, `abort` (`PM-WF-3`). No decision registry exists; every other engine-raised condition ends through its bounded self-remedy or the fallback.

|Lifecycle Gate
|The compiled constant of a release that decides whether an enrolled project is offered the PM-MCP plan lifecycle: closed in every release before the Stage 4 exit criteria are met and open from the release that meets them. While it is closed, plans and epics are created only in a project enrolled as a pilot (`pm-operator enrol --pilot`); once it is open, the lifecycle is offered in every enrolled project until the operator releases the project (`pm-operator release-project`). A project becomes usable by enrolment followed by the project setup workflow, which creates `.marshall/` and a fresh configuration; nothing is imported from plan-marshall, and plans and epics open in plan-marshall stay there (`PM-MIG-1`, `PM-MIG-4`, `PM-MIG-5`).
|===

== Appendix: Verification Gates & Risk Register (Non-Normative)

=== Technical Verifications Required During Implementation
Each item names a technique the implementation rests on and how it is settled. A technique the verifications confirmed is stated as the rule, with the conditions the confirmation rests on; its evidence is the gate's row in the link:specification/evaluation.adoc[Evaluation Reference]. A fallback is stated only where it still applies: for a platform, host, or version that is not yet run. An item that verifies product behaviour names the tests that verify it, since its failure is a defect to fix, not an assumption to replace.

1. *Native Image Dependency Set*: Confirmed on macOS and Linux: `io.quarkiverse.mcp:quarkus-mcp-server-http` and the local API run in the native `pm-mcpd` on a Unix domain socket with the runtime-token authentication mechanism and Server-Sent Events, together with `cui-http` and `org.commonmark:commonmark`; the picocli binaries `pm-mcp` and `pm-operator` run as plain native images with the shared HTTP/1.1 and SSE client of `pm-api` over the JDK Unix domain socket channel (`PM-TECH-1`, `PM-TECH-3`, `PM-SEC-4`). The Quarkus domain-socket listener is the listener of the local adapter, and no fallback is in use. The confirmation rests on three conditions, each a requirement: `quarkus-security` is a runtime dependency (without it no request is authenticated), the runtime offers the Netty `kqueue` and `epoll` transports itself with the transport library beside `pm-mcpd` (`PM-DIST-1`), and the runtime restricts the socket to `0600` before it announces it. _Fallback for the socket binding_, for a platform not yet run or a later Quarkus, Vert.x, or platform version that breaks it, in this order: a loopback `127.0.0.1` listener with the runtime token and `Host`/`Origin` validation, then a runtime-side listener on JDK `UnixDomainSocketAddress` channels bridging to the Quarkus router. _Rule for a new dependency_: supply explicit native-image reachability metadata or replace the component; native compilation of all four binaries is non-negotiable.
2. *LSP4J under GraalVM Native Image*: Confirmed on macOS and Linux: the LSP4J JSON-RPC proxies work in the native `pm-mcpd` with reachability metadata that registers the `[interface, Endpoint]` proxies (`PM-SVC-2`, `PM-TECH-3`). No replacement client is needed.
3. *Linux Landlock Confinement against Real Builds*: Confirmed on Linux (`x86_64`, Landlock ABI 8): the ruleset of the `pm-exec` launcher (via FFM under native image) confines jobs while real builds with wrapper caches, the Gradle daemon, `mvnd`, Testcontainers, and Docker Compose succeed with the declared write set and no further path (`PM-SEC-5`, `PM-TECH-4`). What Landlock does not cover is answered by rules of their own: a per-project build daemon store, the container engine as an enrolment opt-in, every job kept off the session bus, and pathname sockets refused by the ruleset from ABI 9 (`PM-EXEC-4`, `PM-SEC-5`). Landlock availability on WSL2 is not yet run. _Fallback for a kernel or build not yet run_: enrol additional explicit write paths in the project enrolment; never disable confinement where Landlock is available.
4. *macOS Keychain Access from Native Binary*: Confirmed on macOS: the native `pm-mcpd` stores, reads, and deletes items in the login keychain through `Security.framework` via Java FFM, and the default access control trusts exactly the creating binary (`PM-CRED-2`). Trust that survives an upgrade requires the Developer ID signature of the release; the file credential store serves only where no keychain is available (`PM-CRED-3`).
5. *Linux Secret Service via D-Bus Unix Socket*: Confirmed on Linux: the native `pm-mcpd` uses `org.freedesktop.secrets` over the JDK `UnixDomainSocketAddress` channel (`PM-CRED-2`). Where the session bus is not reachable or the default collection is locked at runtime start, the file credential store `<PM_MCP_BASE>/credentials/` with `0600` files serves, without a prompt (`PM-CRED-3`); that is the standing store selection, not a replacement of the technique.
6. *McpAssured STDIO Integration Harness (`McpStdioTestClient`)*: Confirmed on macOS and Linux, in the JVM and the native layout: `io.quarkiverse.mcp:quarkus-mcp-server-test` under `maven-failsafe-plugin` drives the three MCP integration test layers of `PM-TEST-3` (the fourth layer, the operator verbs in `pm-operator`, serves no MCP): the packaged daemon over MCP/HTTP on its Unix socket (`pm-mcp-server`), the `pm-mcp serve` relay over real `stdio` (`McpAssured.newStdioClient()`) against a reactor-built `pm-mcpd` staged into a temporary `PM_MCP_HOME/bin` (`pm-relay`), and all four binaries staged in the release layout (`pm-e2e`) (`PM-TECH-2`, `PM-TEST-3`, `PM-TEST-4`). The client waits at most 10 s for a response, so a test starts the daemon before the relay. _Verified by_ the `*IT` tests of these layers; a failure after a dependency upgrade is a defect of the test setup to fix, with no fallback.
7. *Embedded Classpath Client Bundle Installation*: Verify `pm-operator client install <client>` extraction and atomic configuration merge across Claude Code (`claude`), OpenCode (`opencode`), Antigravity (`antigravity`), and Codex (`codex`), with element-level ownership of permission rules (install appends missing elements, update replaces recorded ones, remove deletes recorded ones only, a user-authored identical element survives) and the drift checks `bundle_outdated` and `bundle_modified` (`PM-DIST-2`, `PM-DIST-4`). _Verified by_ the installer `*IT` tests of `pm-operator`: Milestone 7 for `claude`, Milestone 14 for the remaining hosts; no fallback, a failure is an installer defect.
8. *Detached Runtime Start*: Confirmed on macOS (`arm64`) and Linux (`x86_64`): `pm-mcp` and `pm-operator` start `pm-mcpd` on demand via FFM `posix_spawn` with `POSIX_SPAWN_SETSID`, and a termination of the relay never reaches the runtime (`PM-ARCH-7`). _Fallback for a platform not yet run_ (macOS `x86_64`, Linux `aarch64`, WSL2): where the detached start fails, the starting binary reports it with the `pm-operator runtime install` command and the per-user OS service start (`launchd` / `systemd --user`) serves that platform; on-demand start stays the default everywhere it works.
9. *MCP Call Idle Timeouts & Progress Reset*: Measured for Claude Code, OpenCode, and Antigravity, with relay start and termination confirmed on the three (link:specification/evaluation.adoc[Evaluation Reference]); Codex and every host version change are measured before the profile values ship (`PM-IMPL-4`, `PM-CLIENT-2`). A host whose values are not measured keeps provisional profile values and is no worker host.
10. *Sessionless Streamable HTTP*: Confirmed on the pinned MCP version with `quarkus-mcp-server` 2.0.2: Streamable HTTP is served without MCP sessions, the host's protocol data and the per-request `PM-MCP-*` headers reach the tool handler through the request's security identity, progress arrives on the call's own response stream, and elicitation is an `input_required` result answered by a retry of the call with `inputResponses` (`PM-ARCH-3`, `PM-ARCH-4`). The confirmation rests on the runtime's own protocol filters, because the library has no setting for them: the `Mcp-Session-Id` of an `initialize` response is removed, `listChanged` is declared `false`, and `subscriptions/listen` is refused with `-32601` (link:specification/runtime-model/03-relay.adoc#_host_protocol_forms[Runtime & Interaction Model Specification, Host Protocol Forms]). _Verified by_ the test that pins these filters, re-run before every upgrade of `quarkus-mcp-server`; no session-holding runtime stands in.
11. *Host-Portable Flat Tool Schemas*: Confirmed on Claude Code, OpenCode, and Antigravity: the final flat schemas of the ten core tools are registered and called without a rejected schema (`PM-TOOL-5`). Codex is not yet run. _Fallback for a host not yet run or a later host version that rejects a schema_: a per-host reduced schema rendered by the client profile, with the server's argument validation unchanged.
12. *TOON Specification Pin*: The encoder is pinned to the official TOON specification version 4.1, release v4.1.3, and passes every encode conformance fixture of it with the canonical options; before a newer official version is pinned, every encode conformance fixture of it must pass the same way (`PM-IMPL-3`). _Fallback_: keep the previously pinned version until the conformance fixtures pass.
13. *Headless Harness Command Lines*: Confirmed for Claude Code on macOS and Linux: the headless launch template, the per-call MCP connection back through `pm-mcp serve --job` under Landlock (socket connect and environment passing), structured output, the usage and cost fields, the exit on `SIGTERM`, and session residue (`PM-WF-5`, `PM-CLIENT-2`). Confirmed for OpenCode up to its tool-result limit, under two conditions its profile declares: no tool result above that limit reaches a worker, and every worker has its own data home. Codex is not yet run, and the resource tools of a worker are verified with the worker surface. _Rule_: a harness that fails a capability runs no worker of the roles needing it, and the operator assigns those roles to another eligible harness (`PM-WORK-1`).
14. *Provisional Host Integration Values*: Confirmed against live hosts for Claude Code, OpenCode, and the configuration locations and version probe of Antigravity; every Codex value, the Antigravity values that only a live session shows, and the process-id marker of Claude Code stay marked provisional in the link:specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table] until verified against a live host (`PM-CLIENT-2`, `PM-DIST-3`). _Fallback for a value found wrong_: the corrected value ships in the compiled profile of the next release; the operator override of `PM-CLIENT-5` covers only the connection values.
15. *Web Listener inside the Runtime*: Confirmed on macOS and Linux: a second Vert.x HTTP server beside the Unix-socket listener in the native `pm-mcpd` is opened and closed while the runtime runs (`pm-operator web enable|disable`) without touching plans, jobs, or open streams of the socket listener, routes only the web app and `/api/v1/`, and accepts only its own token kind (`PM-SEC-4`, `PM-SEC-7`). The setting takes effect immediately; no start-time activation stands in. The second server reaches the shared router and security chain through an internal Quarkus API, so the listener tests are re-run before every Quarkus upgrade.
16. *Worker Supervision*: Confirmed for Claude Code against the real relay `pm-mcp serve` with confined writer workers: every task is submitted exactly once under the faults of `PM-TEST-4`, detection holds within the profile's deadlines, and every call of a fenced generation is refused (`PM-WORK-2`, `PM-WORK-3`). OpenCode did not pass the stall longer than its silence limit and is re-run with its per-worker data home; Codex and Antigravity are not yet run. _Rule_: a harness is a worker host only after it passed.

=== Tracked Architectural Risks & Mitigations

[cols="1,2,2"]
|===
|Risk |Impact |Normative Mitigation

|MCP Framework Evolution
|Quarkus MCP Server extension tracks fast-moving MCP specifications.
|Target exclusively the frontier MCP `2026-07-28` specification over `quarkus-mcp-server-http` behind a `stdio` relay (`PM-ARCH-3`, `PM-TECH-1`), own job scheduling (`PM-SVC-1`) and standard tool/resource skill delivery (`PM-SKILL-3`), and verify protocol behavior continuously with `McpAssured` (`PM-TEST-3`).

|Host Capability Variance
|Progress notifications, elicitation support, and the capabilities of the headless command lines (per-call MCP, tool allowlists, zero-tool runs, structured output) vary across Claude Code, OpenCode, Antigravity, and Codex.
|Baseline interaction uses standard MCP tools (`PM-TOOL-1`) over `stdio`, bounded waits (`pm_wait`, `pm_build`, `PM-IMPL-4`), and operator CLI fallback (`PM-SEC-3`); a role runs only on an eligible harness that declares every capability its class needs, otherwise its artifact is invalid and the operator assigns it to another harness (`PM-WORK-1`, `PM-CLIENT-2`).

|Model Out-of-Sequence Calls or Invalid Arguments
|Because `pm_do` accepts free parameters in an `args` map, the host cannot pre-validate link-specific arguments via static JSON Schema.
|Server re-validates every transition and parameter against persisted state (`PM-WF-6`) and returns a structured parameter validation error plus fresh representation on mismatch.

|Judgment Quality Regression
|Replacing full-phase Markdown documents with concise state representations could omit implicit guidance.
|Pair every judgment state with a focused static vocabulary skill (`PM-SKILL-1`), measure outline/triage quality in parallel runs against plan-marshall before the lifecycle gate opens (`PM-MIG-4`), verify the model-facing content per client profile against live models in an out-of-band pre-release gate (`PM-TEST-6`), and run every role only on a configuration qualified against the model verification corpus, with a conservative server fallback until one qualifies (`PM-WORK-6`).

|Host Disconnect or Runtime Crash
|A host closing its relay interrupts only that connection; a runtime crash interrupts running jobs and in-flight transitions.
|Decouple jobs from host connections and persist every transition before responding (`PM-ARCH-8`), persist all workflow and job state in the filesystem (`PM-ARCH-6`), and recover interrupted transaction journals and orphaned jobs on runtime start (`PM-ARCH-7`).

|Operator Channel Reachable from a Model Shell
|The operator proof is the own checks of `pm-operator` (interactive terminal, no agent environment markers): a model-driven shell that deliberately defeats them can run operator verbs, and any same-user process holding the runtime token can call the operator endpoints of the local API directly.
|Accepted residual risk (`PM-SEC-3`); the checks and the host rule that denies the whole binary `pm-operator` to the model guard against accidental and naive invocation, every privileged action is recorded in the audit log with its channel (`PM-SEC-6`), and a user proof the model cannot produce is deferred (link:later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).

|Parallel Operation of plan-marshall and PM-MCP on One Repository
|During the overlap both systems may run plans in the same repository; they use separate trees (`.plan/`, `.marshall/`) and share no locks, so the cross-plan merge mutex and review-bot rate windows do not coordinate across the two systems.
|Accepted residual risk (`PM-MIG-2`); the entry commands of the two systems are kept apart by the `mcp-` prefix (`PM-CLIENT-1`), the plan lifecycle is offered per enrolled project only after the lifecycle gate opens (before that only in projects enrolled as pilots), plans open in plan-marshall finish there, and the operator avoids concurrent merges from both systems in the same repository.

|Browser-Facing Listener inside the Runtime
|With web access enabled, browser-facing HTTP, TLS, and static serving run in the process that holds the credential store and the workflow engine; no separate web server process stands between a browser and the runtime.
|Accepted consequence (`PM-SEC-7`); web access is off by default and enabled only by an operator verb, the listener is loopback-only by default and on the LAN only over TLS, every request passes the `Host` validation and needs a device secret that the runtime checks without a cache, and the listener routes only the web app and `/api/v1/`, never `/mcp`, and never accepts the runtime token (`PM-SEC-4`).

|Enrolment Store Tampering
|A process running as the operator's user could rewrite an enrolment file to widen enrolled tools or arguments.
|Operator-HMAC over the canonical content, verified at runtime start and before every verify-not-resolve check (`enrolment_tampered`, audit record), job reads and writes of `<PM_MCP_BASE>` excluded by the Linux Landlock ruleset (a model job reads only its own job-private directory), and host deny rules for `<PM_MCP_BASE>/**` (`PM-EXEC-2`, `PM-SEC-5`). Accepted residual risk: a model-driven shell that defeats the operator checks, or a same-user process calling the operator endpoint with the runtime token, can re-baseline a tampered file (`PM-SEC-3`), and on hosts without a keyring the key lives in a `0600` file under `<PM_MCP_BASE>/state/`.

|Upstream Proxy Trust Laundering
|Untrusted content from proxied external MCP servers could be mistaken for authoritative PM-MCP state.
|Keep the upstream allowlist operator-owned (the object `upstream_mcp` of `<PM_MCP_BASE>/projects/<project_id>/local-config.json`, never repository content), attach provenance metadata (`_meta`), mark proxied output untrusted, admit it to plan stores only through the two-level guard for external text, and forbid re-serving upstream skills (`PM-SVC-3`, `PM-SEC-1`).

|Prompt Injection through External Text
|Issue, pull-request, review, and analysis texts authored by third parties can carry instructions addressed to the model.
|Deterministic level-1 validator as the containment boundary, a fail-closed zero-tool screener job as defence in depth, flagged text withheld inside a plan, and every external text delivered marked untrusted (`PM-SEC-1`); a local classifier model is deferred (link:later-improvements.adoc#_l_7_local_prompt_injection_classifier[Later Improvements, L-7]).

|Job Reach beyond the Filesystem Rules
|Landlock confines a job's file access, not what the job talks to: a warm build daemon, the container daemon, and, below Landlock ABI 9, every pathname Unix socket (the session bus with the Secret Service among them) are outside its rules, and a loopback connection is never restricted.
|A per-project build daemon store keyed by the write set, the container engine only as an audited enrolment opt-in recorded as `confinement: partial(container_engine)`, no session bus variable in any job environment, and the ruleset's socket right from Landlock ABI 9 (`PM-EXEC-4`, `PM-SEC-5`). Accepted residual risks: a job that names a socket path itself on a kernel below ABI 9, and an unconfined same-user process reaching the Secret Service (`PM-SEC-5`); a loopback connect restriction is deferred (link:later-improvements.adoc#_l_11_loopback_connect_restriction_for_jobs[Later Improvements, L-11]).

|Harness Usage Terms
|Model jobs run the user's own harness binary with the user's own login; a heavy fan-out can exceed what an individual subscription assumes.
|A machine-wide model-slot cap that counts warm workers, at most one writer worker per plan, and idle recycling (`PM-WF-14`, `PM-WORK-3`); the operator may assign roles to another harness (`PM-WORK-1`).

|Dependence on Headless Harnesses
|The interior of every plan runs on headless harness command lines whose behaviour (flags, output, limits, terms) changes between versions and differs between hosts.
|Each harness is eligible as a worker host only after its worker behaviour is measured (`PM-CLIENT-2`); a harness version change invalidates the qualification of its roles (`PM-WORK-6`); the supported version range lives in the client profile, and a role can be moved to another harness by configuration (`PM-WORK-1`).

|Worker Loss
|A worker can be killed, stall in a provider, give up in an empty wait, exhaust its context, or lose its account quota, and neither the transport nor the model reports it.
|The supervisor detects loss by process exit, a missed acknowledgement, and silence, recycles on idle and token budget, fences the lost generation, and redelivers its task exactly once; repeated start failures stop the role and are reported to the operator, and its tasks take their conservative fallback (`PM-WORK-2`, `PM-WORK-3`).
|===
