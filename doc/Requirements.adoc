== Overview

This document defines the normative functional and non-functional requirements for *plan-marshall-mcp* (`PM-MCP`): an always-on local Model Context Protocol (MCP) runtime (`pm-mcpd`) with a native command line (`pm-mcp`), reached by coding agent hosts through a native `stdio` relay (`pm-mcp serve`), that replaces prose-enforced workflow instructions and shell-invoked Python scripts with a server-owned hypermedia state machine (HATEOAS), warm platform services, and verified native execution.

PM-MCP is built out in parallel to legacy plan-marshall and never shares state with it: it keeps its own repository tree (`.marshall/`) and machine root (`~/.plan-marshall-mcp/`), and never reads the legacy `.plan/` and `~/.plan-marshall/` trees: it imports nothing from legacy plan-marshall, and every project starts from a clean slate. Both systems may be installed on one machine and used in the same repository; an enrolled project is offered the PM-MCP plan lifecycle once the lifecycle gate has opened (`PM-MIG-1`, `PM-MIG-2`, `PM-MIG-4`).

For technical implementation blueprints, wire protocols, data schemas, and formal grammars, see the link:Specification.adoc[Technical Specification]. For delivery staging, see the link:roadmap.adoc[Roadmap]. For historical background and evaluated alternatives, see link:discussions/README.adoc[Discussions]. Defect archetypes and verification hints that guard individual requirements during implementation are held in the link:ImplementationWatch.adoc[Implementation Watch]; each guarded requirement names its watch items in an _Implementation watch_ line.

=== Requirement Authoring Conventions (SMART)

All requirements in this document set follow the SMART criteria:

* *Specific*: Each requirement uses unambiguous normative statements ("The system must...") defining exact behavior, inputs, outputs, and constraints.
* *Measurable*: Acceptance criteria specify observable, testable outcomes (latency bounds, closed outcome enumerations, digest checks, and `McpAssured` integration assertions).
* *Achievable*: Grounded in the selected technology stack (Java 25+, Quarkus MCP server `quarkus-mcp-server-http` behind the native `pm-mcp serve` STDIO relay, GraalVM native image, OS credential stores, MCP `2026-07-28` specification).
* *Relevant*: Directly addresses identified cost, reliability, or security limitations of the script-and-prose architecture.
* *Traceable*: Identified by a stable hierarchical anchor `[#PM-<DOMAIN>-<NUM>]` with bidirectional links to technical specifications in `doc/specification/`; the milestones of `doc/roadmap.adoc` link to the requirements they deliver.

== Motivation & System Context

=== Limitations of the Script-and-Prose Architecture

Today, plan-marshall ships as a marketplace of Markdown skills and Python scripts executed via a generated proxy (`python3 .plan/execute-script.py {bundle}:{skill}:{script} ...`) through the host's Bash tool. While functional, this architecture incurs structural costs that motivate `plan-marshall-mcp`:

* *Process rules enforced by prose*: Workflow ordering, finalize gates, and operator-only boundaries live in Markdown instructions. Rules such as "never invent arguments" or "never `--force` the freshness gate" can be misread, ignored, or lost during context compaction.
* *Model-assembled CLI calls*: The model composes every script invocation from prose (plan ID, worktree path, step name, CLI flags), making malformed or stale arguments a recurring defect class.
* *Resident context overhead*: Whole-phase workflow documents remain in model context across turns even when only a single state transition is relevant.
* *Bash as transport*: Routing every operation through Bash requires shell-hygiene rules, PreToolUse hooks, and host permission allowlists solely to police the transport channel.
* *Scratch-file staging for multi-line text*: Passing multi-line text (commit messages, PR bodies, outlines, task descriptions, lesson bodies) over Bash CLI arguments or heredocs triggers shell-quoting hazards, OS `ARG_MAX` limits, and host safety prompts (such as `#` headings in heredocs), forcing multi-step temp-file dances (`prepare-body` / `resolve-path` -> host `Write` to `.plan/temp/` or `work/ci-bodies/` -> script commit call).
* *Skill and script drift*: Skills (loaded from plugin cache) and scripts (resolved via generated executors) travel through separate mechanisms and can diverge across updates.
* *Multi-stage distribution chain*: Source bundles -> target runtime generator -> `target/{runtime}/` -> dist branch -> marketplace install -> plugin cache -> executor regeneration -> host restart.
* *Cold language servers*: LSP queries spawn and tear down a language server per invocation across sub-agents.
* *Static runtime translation*: Supporting frontier coding agents (Claude Code, OpenCode, Antigravity) requires static build-time corpus translation per runtime.

=== Architectural Shift

[cols="2,3"]
|===
|Problem |PM-MCP Requirement & Design Response

|Rules enforced by prose
|The workflow state machine executes inside the server (`PM-WF`); invalid transitions are omitted from representations and rejected on execution.

|Model assembles CLI calls
|The server returns valid transitions as hypermedia links (`PM-WF-2`); the model supplies only a `link` identifier and judgment parameters (`args`) via `pm_do`.

|Scratch-file staging for multi-line text
|The model passes multi-line UTF-8 text (commit messages, PR/issue bodies, outlines, clarified requests, task descriptions, lessons, ADRs) directly in `pm_do` `args` over JSON-RPC (`PM-WF-2`, `PM-WF-6`); `pm-mcpd` validates and persists stores atomically or pipes payloads in memory via `stdin` to child tools (`PM-EXEC-5`), eliminating `.plan/temp/` and `work/` staging files.

|Duplicated compound operations (commit, push)
|Reusable, config-aware compound sub-workflows (`PM-WF-16`, such as `git.commit_and_push`) execute over a persisted call stack (`call_stack`) and return closed outcomes to any calling phase or tool workflow.

|Resident context overhead
|Only the active state's representation and targeted vocabulary skill enter model context (`PM-SKILL-1`).

|Bash as transport
|All plan-marshall operations execute as typed MCP tool calls over native `stdio`, relayed to the always-on runtime (`PM-ARCH-3`, `PM-TOOL-1`); only the initial entry bootstrap (`pm-mcp enter`) runs in the host shell.

|Skill/script drift
|Skills, state transitions, and tool schemas are served from a single versioned binary (`PM-DIST-1`).

|Cold LSP startups
|The always-on runtime maintains a warm language server pool shared by all host connections (`PM-SVC-2`).

|Static runtime translation
|The server translates tool names, the headless launch conventions of model jobs, and skill references on the fly using data-driven client profiles (`PM-CLIENT-2`) across `claude`, `opencode`, `antigravity`, and `codex`.

|Migration off a running system
|PM-MCP keeps separate state trees (`.marshall/`, `~/.plan-marshall-mcp/`) and never converts, shares, or writes legacy stores (`PM-MIG-2`); its services are usable alongside legacy plan-marshall from their stage on, and an enrolled project is offered the PM-MCP plan lifecycle once the Stage 4 exit criteria open the lifecycle gate, switched off per project by operator release (`PM-MIG-1`, `PM-MIG-4`, `PM-MIG-5`).
|===

Judgment remains strictly with the model: refining requests, authoring solution outlines, implementing code, triaging findings, and composing commit/PR descriptions. PM-MCP narrows the model's workflow obligations to supplying those judgment artifacts directly as free parameters of hypermedia links.

|===
|Term |Definition

|Machine
|The developer's workstation running `pm-mcp` native processes and any number of coding agent hosts.

|Host
|A frontier coding agent runtime connecting to MCP servers over `stdio` and hosting the model (`claude` for Claude Code, `opencode` for OpenCode, `antigravity` for Antigravity, `codex` for Codex).

|Host session
|A single conversation instance within a host. It spawns a `pm-mcp serve` relay over `stdin`/`stdout`; it carries no workflow state.

|Logical plan session
|The sequence of calls addressing one `plan_id` or `epic_id`, identified solely by that ID and carried solely by the scope's persisted files. Continued by following a link or by `pm_state` from any host connection (`PM-ARCH-8`).

|Workspace scope
|The one plan-less scope of an enrolled project, addressed as `plan_id: "NO_PLAN"` and resolved from the relay's `PM-MCP-Workspace` header (`PM-ARCH-4`). It hosts the `project-setup` workflow, the pending plan and epic bootstraps, the lesson maintenance, and the ledger rows, findings, and logs of plan-less service calls, in its home `<PM_MCP_BASE>/projects/<project_id>/workspace/` of the per-project machine store.

|Per-project machine store
|The machine-local home of all server-owned state of one enrolled project, `<PM_MCP_BASE>/projects/<project_id>/`, keyed by the project's enrolment identifier: plan directories (never moved), archived plans, the lesson store, the workspace home, the epics' non-tracked state, pending entry records, and the scope locks (`PM-ARCH-5`). The repository keeps only worktrees and temporary files in its git-ignored `.marshall/local/`.

|Bootstrap
|The sub-workflow (`bootstrap-plan`, `bootstrap-epic`) that gathers everything a new plan or epic needs before it exists (what to work on, its source and the source's verification), run as an entity of the workspace scope addressed by its `entry_id`; the scope is created atomically when the bootstrap completes, so an abandoned start leaves no scope behind (`PM-TOOL-1`).

|Sub-agent (model job)
|A job of kind `llm` that the runtime launches through the headless command line of an enrolled harness for one entity of a plan, epic, or workspace scope, with a server-composed prompt and a job-bound connection back to PM-MCP; the runtime observes its end and usage itself, and the host never dispatches a sub-agent (`PM-WF-5`).

|Screener
|The zero-tool model job that judges external text the deterministic validator has already cleaned, the second level of the guard for external text; it can only withhold text, never admit it (`PM-SEC-1`).

|PM
|The model participant operating within a host session.

|Operator
|The human developer responsible for the machine and its repositories. Enrols and releases projects, sets waivers, aborts plans and epics, resolves integrity breaches, and performs privileged actions exclusively via the operator CLI or a paired web device (answering only the operator-configuration choices the server raises itself also through MCP elicitation), always on the operator's own initiative: no plan waits for an operator decision (`PM-WF-1`, `PM-SEC-3`). Content questions are answered by the user through the question mechanism, never as operator overrides.

|`pm-mcp`
|The command-line binary, one of the four native executables of a release (`PM-DIST-1`, `PM-TECH-3`, `PM-IMPL-1`) and the only one hosts and users invoke; it holds no store logic and starts the others by path. Its verbs: `pm-mcp serve` (the per-connection STDIO relay), `pm-mcp enter`, `pm-mcp hook`, `pm-mcp status`, `pm-mcp drain`, `pm-mcp runtime` (on-demand start and service registration of `pm-mcpd`), `pm-mcp client`, `pm-mcp web`, and `pm-mcp operator` (link:specification/cli-and-security/01-cli-and-installer.adoc#command-tree[CLI, Coordination & Security Specification, Command Tree]).

|`pm-mcpd`
|The runtime binary (daemon), started on demand by `pm-mcp`; beside it the release ships the job launcher `pm-mcp-exec` and the optional web server `pm-mcp-web` (`PM-DIST-1`).

|Runtime / Daemon
|The always-on `pm-mcpd` process (one per machine and `PM_MCP_BASE`) executing the workflow engine, state stores, jobs, build slot scheduler, warm LSP pool, MCP proxy, and audit log, independent of any host conversation (`PM-ARCH-1`, link:specification/runtime-model.adoc[Runtime & Interaction Model Specification]).

|Relay
|The `pm-mcp serve` process a host spawns over `stdio`; it forwards MCP messages to and from the runtime without interpreting them (`PM-ARCH-3`).

|Entry point & Entry call
|A user-invoked command in the client bundle that executes `pm-mcp enter --client <client>` to append the session's identity (client, host build, model, project, entry origin) to the plan, epic, or workspace session log, or to open a bootstrap entry for a plan or epic that does not exist yet.

|Representation
|The TOON-formatted state payload returned by the server describing the current state of a plan or epic, relevant domain facts, and valid hypermedia links.

|Link & Link ID
|A valid state transition offered in a representation (`rel`, `link` identifier such as `push` or `submit:TASK-003`, and free parameter names), invoked via `pm_do`.

|Job
|A build, git, CI, project script, or model (`llm`) subprocess run by the runtime on the host, independent of any host connection, verified against project enrolment and tracked via `wait` links.

|Enrolment
|The operator-authorized registration of a project root, its pinned build wrappers/tools, SHA-256 digests, command templates, and project scripts, held in one file per project, `<PM_MCP_BASE>/enrolments/<project_id>.json`, under its own operator HMAC.

|Plan outcome
|How a plan ends: `merged` (terminal `completed`), `handed_back`, `returned`, or `no_change` (terminal `completed`, an empty recipe harvest), each reached only through `finalize.archive-plan` after the post-run band, or `aborted` by the operator. Every blocking condition ends in a bounded self-remedy and then the defined fallback of its phase (`PM-WF-1`).

|Hand-back
|The fallback from Phase 5 until the merge (`finalize.hand-back`) and the model's own exit link `hand_back`: the work is delivered as an open pull request (a new one opened as a draft, an existing one left as it is, a ready one under `merge.auto_merge: false`), or as a branch where no pull request can exist, with the gaps documented in a pull-request comment and the label `pm-mcp:handed-back`. The fallback of Phases 1–4 is the return (`plan.return`, outcome `returned`): the planning result only, nothing implemented; a plan whose branch already has commits beyond the base is forwarded from the return to the hand-back.

|Remediation policy
|A project-owned DSL sub-workflow unit per failure class (`remediation.qgate-findings`, `.build-failure`, `.ci-failure`, `.analysis`, `.review-findings`, `.merge-conflict`, `.spend`): the server gathers the evidence, the model chooses `retry`, `fix`, or `request_waiver` within budgets capped by compiled limits, and the unit returns `resolved`, `waived`, `exhausted`, or `fix_requested`, or `stepped_out` (`PM-WF-7`).

|Waiver
|An operator override of a closed list of process gates and budgets (`pm-mcp operator waive`, `--raise`), plan-scoped, with a mandatory reason, recorded append-only in the plan's waiver record and listed in the pull request and the landing record; the only operator influence on a running plan. A *waiver request* is filed by the model's `request_waiver` (rel `escalate`) and is answered only by a waiver (`PM-WF-12`).

|Question record
|A server-owned content question (options with `branch_key`, a recommended option or default assumption) created by the model's `ask` link, a task-envelope job's `ask:TASK-NNN` link, the `questions` list of a refine or outline authoring job's `submit`, or a server classifier (among them the team-configuration choices of the workspace setup), delivered to the user per `questions.delivery` and `questions.mode`, validated and recorded with its channel, and ended by its class fallback when an `auto` question expires. It replaces every in-run operator decision about content (`PM-WF-12`).

|Plan instance
|The composed, immutable, versioned DSL unit each plan executes, built from the workflow templates and the plan's facts with the provenance of every prune, bound budget, and waiver; it absorbs the execution manifest and the configuration snapshot, and its diagram shows the process in force (`PM-IMPL-5`).

|Integrity breach
|A tampered plan, epic, or workspace store, a tampered lesson, or a tampered enrolment: the only condition that pauses a scope, ended only by the operator's `accept-edit` or, for a plan or epic, `abort` (`PM-WF-3`). No decision registry exists; every other engine-raised condition ends through its bounded self-remedy or the fallback.

|Lifecycle Gate
|The condition under which an enrolled project is offered the PM-MCP plan lifecycle: it opens once the Stage 4 exit criteria are met and stays open for a project until the operator releases it (`pm-mcp operator release-project`). A project becomes usable by enrolment followed by the project setup workflow, which creates `.marshall/` and a fresh configuration; nothing is imported from legacy plan-marshall, and open legacy plans and epics stay in plan-marshall (`PM-MIG-1`, `PM-MIG-4`, `PM-MIG-5`).
|===

== Appendix: Verification Gates & Risk Register (Non-Normative)

=== Technical Verifications Required During Implementation

Each verification item below specifies the deterministic fallback if the primary technical assumption fails during spike testing:

1. *Native Image Dependency Set*: Verify `io.quarkiverse.mcp:quarkus-mcp-server-http` and the local API bound to a Unix domain socket with the runtime-token authentication mechanism and Server-Sent Events, `cui-http`, and `org.commonmark:commonmark`, under GraalVM native image in `pm-mcpd`; and the picocli CLI with its own HTTP/1.1 and SSE client over the JDK Unix domain socket channel as a plain native image in `pm-mcp` (`PM-TECH-1`, `PM-TECH-3`, `PM-SEC-4`). _Fallback for the socket binding_, in this order: a loopback `127.0.0.1` listener with the runtime token and `Host`/`Origin` validation, then a runtime-side listener on JDK `UnixDomainSocketAddress` channels bridging to the Quarkus router. _Fallback_: Supply explicit native-image reachability metadata or replace incompatible library components; native compilation of all four binaries is non-negotiable.
2. *LSP4J under GraalVM Native Image*: Verify LSP4J JSON-RPC protocol reflection and dynamic proxy registration (`PM-SVC-2`, `PM-TECH-3`). _Fallback_: Replace LSP4J with a minimal Jackson-based JSON-RPC client for the closed set of LSP operations used by PM-MCP.
3. *Linux Landlock Confinement against Real Builds*: Verify the Landlock ruleset of the `pm-mcp-exec` launcher (via FFM under native image) with real project builds using wrapper caches, Gradle daemon, `mvnd`, Testcontainers, and Docker Compose, and verify Landlock availability on WSL2 (`PM-SEC-5`, `PM-TECH-4`). _Fallback_: Enrol additional explicit write paths in project enrolment; never disable confinement where Landlock is available.
4. *macOS Keychain Access from Native Binary*: Verify `Security.framework` access via Java FFM from the `pm-mcpd` native executable (`PM-CRED-2`). _Fallback_: Use the encrypted/permission-guarded file credential store (`~/.plan-marshall-mcp/credentials/`) and require interactive operator confirmation via CLI.
5. *Linux Secret Service via D-Bus Unix Socket*: Verify `org.freedesktop.secrets` over JDK `UnixDomainSocketAddress` under native image (`PM-CRED-2`). _Fallback_: Fall back to `~/.plan-marshall-mcp/credentials/` with `0600` permissions.
6. *McpAssured STDIO Integration Harness (`McpStdioTestClient`)*: Verify `io.quarkiverse.mcp:quarkus-mcp-server-test` under `maven-failsafe-plugin` in the three integration test layers of `PM-IMPL-1`: the packaged daemon over MCP/HTTP on its Unix socket (`pm-mcp-server`), the `pm-mcp serve` relay over real `stdio` (`McpAssured.newStdioClient()`) against a reactor-built `pm-mcpd` staged into a temporary `PM_MCP_HOME/bin` (`pm-mcp-cli`), and all four binaries staged in the release layout (`pm-mcp-e2e`) (`PM-TECH-2`, `PM-TEST-3`, `PM-TEST-4`).
7. *Embedded Classpath Client Bundle Installation*: Verify `pm-mcp client install <client>` extraction and atomic configuration merge across Claude Code (`claude`), OpenCode (`opencode`), Antigravity (`antigravity`), and Codex (`codex`), with element-level ownership of permission rules and hook entries (install appends missing elements, update replaces recorded ones, remove deletes recorded ones only, a user-authored identical element survives) and the drift checks `bundle_outdated` and `bundle_modified` (`PM-DIST-2`, `PM-DIST-4`).
8. *Detached Runtime Start*: Verify on-demand start of `pm-mcpd` by the CLI via FFM `posix_spawn` with `POSIX_SPAWN_SETSID` on macOS and Linux, and that host termination of the relay never reaches the runtime (`PM-ARCH-7`). _Fallback_: on a platform where the detached start fails, the CLI reports it with the `pm-mcp runtime install` command and the per-user OS service start (`launchd` / `systemd --user`) serves that platform; on-demand start stays the default everywhere it works.
9. *MCP Call Idle Timeouts & Progress Reset*: Verify per-host tool call timeout thresholds and whether MCP `notifications/progress` messages reset the timer (`PM-IMPL-4`).
10. *Sessionless Streamable HTTP*: Verify that the pinned MCP version and the Quarkus MCP server support Streamable HTTP without MCP sessions, with the host's `initialize` data carried in per-request `PM-MCP-*` headers and elicitation and progress on the call's own response stream (`PM-ARCH-4`). _Fallback_: a session-holding runtime whose relay replays the recorded `initialize` after a runtime restart (link:specification/runtime-model.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]).
11. *Host-Portable Flat Tool Schemas*: Register and call the final flat tool schemas on every supported host and its provider API (`PM-TOOL-5`). _Fallback_: a per-host reduced schema rendered by the client profile, with the server's argument validation unchanged.
12. *TOON Specification Pin*: Verify the current official TOON specification version and its conformance fixtures and pin the encoder to it (`PM-IMPL-3`). _Fallback_: keep the previously pinned version until the conformance fixtures pass.
13. *Headless Harness Command Lines*: Verify per harness the headless launch template (inline named agent or per-call flags), the per-call MCP connection back through `pm-mcp serve --job` under Landlock (socket connect and environment passing), a zero-tool screener run, structured output, the usage and cost fields, the exit behaviour on `SIGTERM`, and session residue (`PM-WF-5`, `PM-CLIENT-2`). _Fallback_: a harness that fails a capability runs no job of the roles needing it, and the operator names another installed harness (`model_jobs.harness`).
14. *Provisional Host Integration Values*: Verify every value marked provisional in the link:specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table] (configuration paths, session variables, `clientInfo` names) against current host documentation (`PM-CLIENT-2`, `PM-DIST-3`). _Fallback_: a per-host operator override in the client profile override hierarchy (`PM-CLIENT-5`).

=== Tracked Architectural Risks & Mitigations

[cols="1,2,2"]
|===
|Risk |Impact |Normative Mitigation

|MCP Framework Evolution
|Quarkus MCP Server extension tracks fast-moving MCP specifications.
|Target exclusively the frontier MCP `2026-07-28` specification over `quarkus-mcp-server-http` behind a `stdio` relay (`PM-ARCH-3`, `PM-TECH-1`), own job scheduling (`PM-SVC-1`) and standard tool/resource skill delivery (`PM-SKILL-3`), and verify protocol behavior continuously with `McpAssured` (`PM-TEST-3`).

|Host Capability Variance
|Progress notifications, elicitation support, and the capabilities of the headless command lines (per-call MCP, tool allowlists, zero-tool runs, structured output) vary across Claude Code, OpenCode, Antigravity, and Codex.
|Baseline interaction uses standard MCP tools (`PM-TOOL-1`) over `stdio`, bounded wait links (`PM-IMPL-4`), and operator CLI fallback (`PM-SEC-3`); a model job runs only on a harness that declares every capability its role needs, otherwise the operator names another installed harness (`PM-WF-5`, `PM-CLIENT-2`).

|Model Out-of-Sequence Calls or Invalid Arguments
|Because `pm_do` accepts free parameters in an `args` map, the host cannot pre-validate link-specific arguments via static JSON Schema.
|Server re-validates every transition and parameter against persisted state (`PM-WF-6`) and returns a structured parameter validation error plus fresh representation on mismatch.

|Judgment Quality Regression
|Replacing full-phase Markdown documents with concise state representations could omit implicit guidance.
|Pair every judgment state with a focused static vocabulary skill (`PM-SKILL-1`), measure outline/triage quality in parallel runs against legacy plan-marshall before the lifecycle gate opens (`PM-MIG-4`), and verify the model-facing content per client profile against live models in an out-of-band pre-release gate (`PM-TEST-6`).

|Host Disconnect or Runtime Crash
|A host closing its relay interrupts only that connection; a runtime crash interrupts running jobs and in-flight transitions.
|Decouple jobs from host connections and persist every transition before responding (`PM-ARCH-8`), persist all workflow and job state in the filesystem (`PM-ARCH-6`), and recover stale locks, interrupted transaction journals, and orphaned jobs on runtime start (`PM-ARCH-7`).

|Operator Channel Reachable from a Model Shell
|The operator proof is the CLI's own checks (interactive terminal, no agent environment markers): a model-driven shell that deliberately defeats them can run operator verbs, and any same-user process holding the runtime token can call the operator endpoints of the local API directly.
|Accepted residual risk (`PM-SEC-3`); the checks and the host deny rules guard against accidental and naive invocation, every privileged action is recorded in the audit log with its channel (`PM-SEC-6`), and a user proof the model cannot produce is deferred (link:later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).

|Parallel Operation of Legacy plan-marshall and PM-MCP on One Repository
|During the overlap both systems may run plans in the same repository; they use separate trees (`.plan/`, `.marshall/`) and share no locks, so the cross-plan merge mutex and review-bot rate windows do not coordinate across the two systems.
|Accepted residual risk (`PM-MIG-2`); the plan lifecycle is offered per enrolled project only after the lifecycle gate opens, open legacy plans finish in plan-marshall, and the operator avoids concurrent merges from both systems in the same repository.

|Enrolment Store Tampering
|A process running as the operator's user could rewrite an enrolment file to widen enrolled tools or arguments.
|Operator-HMAC over the canonical content, verified at runtime start and before every verify-not-resolve check (`enrolment_tampered`, audit record), job reads and writes of `<PM_MCP_BASE>` excluded by the Linux Landlock ruleset, and host deny rules for `<PM_MCP_BASE>/**` (`PM-EXEC-2`, `PM-SEC-5`). Accepted residual risk: a model-driven shell that defeats the operator checks, or a same-user process calling the operator endpoint with the runtime token, can re-baseline a tampered file (`PM-SEC-3`), and on hosts without a keyring the key lives in a `0600` file under `<PM_MCP_BASE>/state/`.

|Upstream Proxy Trust Laundering
|Untrusted content from proxied external MCP servers could be mistaken for authoritative PM-MCP state.
|Keep the upstream allowlist operator-owned (`<PM_MCP_BASE>/conf/upstream-mcp.json`, never repository content), attach provenance metadata (`_meta`), mark proxied output untrusted, admit it to plan stores only through the two-level guard for external text, and forbid re-serving upstream skills (`PM-SVC-3`, `PM-SEC-1`).

|Prompt Injection through External Text
|Issue, pull-request, review, and analysis texts authored by third parties can carry instructions addressed to the model.
|Deterministic level-1 validator as the containment boundary, a fail-closed zero-tool screener job as defence in depth, flagged text withheld inside a plan, and every external text delivered marked untrusted (`PM-SEC-1`); a local classifier model is deferred (link:later-improvements.adoc#_l_7_local_prompt_injection_classifier[Later Improvements, L-7]).

|Harness Usage Terms
|Model jobs run the user's own harness binary with the user's own login; a heavy fan-out can exceed what an individual subscription assumes.
|A machine-wide model-slot cap and at most one writing job per plan (`PM-WF-14`); the operator may name another installed harness (`PM-CLIENT-5`).
|===
