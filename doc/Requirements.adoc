== Overview

This document defines the normative functional and non-functional requirements for *plan-marshall-mcp* (`PM-MCP`): a local Model Context Protocol (MCP) server and native executable (`pm-mcp`) built on `io.quarkiverse.mcp:quarkus-mcp-server-stdio` that replaces prose-enforced workflow instructions and shell-invoked Python scripts with a server-owned hypermedia state machine (HATEOAS), warm platform services, and verified native execution.

For technical implementation blueprints, wire protocols, data schemas, and formal grammars, see the link:Specification.adoc[Technical Specification]. For delivery staging, see the link:roadmap.adoc[Roadmap]. For historical background and evaluated alternatives, see link:discussions/README.adoc[Discussions].

=== Requirement Authoring Conventions (SMART)

All requirements in this document set follow the SMART criteria:

* *Specific*: Each requirement uses unambiguous normative statements ("The system must...") defining exact behavior, inputs, outputs, and constraints.
* *Measurable*: Acceptance criteria specify observable, testable outcomes (latency bounds, closed outcome enumerations, digest checks, and `McpAssured` integration assertions).
* *Achievable*: Grounded in the selected technology stack (Java 25+, Quarkus MCP STDIO native image, OS credential stores, MCP `2026-07-28` specification).
* *Relevant*: Directly addresses identified cost, reliability, or security limitations of the script-and-prose architecture.
* *Traceable*: Identified by a stable hierarchical anchor `[#PM-<DOMAIN>-<NUM>]` with bidirectional links to technical specifications in `doc/specification/` and verification gates in `doc/roadmap.adoc`.

== Motivation & System Context

=== Limitations of the Script-and-Prose Architecture

Today, plan-marshall ships as a marketplace of Markdown skills and Python scripts executed via a generated proxy (`python3 .plan/execute-script.py {bundle}:{skill}:{script} ...`) through the host's Bash tool. While functional, this architecture incurs structural costs that motivate `plan-marshall-mcp`:

* *Process rules enforced by prose*: Workflow ordering, finalize gates, and operator-only boundaries live in Markdown instructions. Rules such as "never invent arguments" or "never `--force` the freshness gate" can be misread, ignored, or lost during context compaction.
* *Model-assembled CLI calls*: The model composes every script invocation from prose (plan ID, worktree path, step name, CLI flags), making malformed or stale arguments a recurring defect class.
* *Resident context overhead*: Whole-phase workflow documents remain in model context across turns even when only a single state transition is relevant.
* *Bash as transport*: Routing every operation through Bash requires shell-hygiene rules, PreToolUse hooks, and host permission allowlists solely to police the transport channel.
* *Scratch-file staging for multi-line text*: Passing multi-line text (commit messages, PR bodies, outlines, task descriptions, lesson bodies) over Bash CLI arguments or heredocs triggers shell-quoting hazards, OS `ARG_MAX` limits, and host safety prompts (such as `#` headings in heredocs), forcing multi-step temp-file dances (`prepare-body` / `resolve-path` -> host `Write` to `.plan/temp/` or `work/ci-bodies/` -> script commit call).
* *Skill and script drift*: Skills (loaded from plugin cache) and scripts (resolved via generated executors) travel through separate mechanisms and can diverge across updates.
* *Multi-stage distribution chain*: Source bundles -> target runtime generator -> `target/{runtime}/` -> dist branch -> marketplace install -> plugin cache -> executor regeneration -> host restart.
* *Cold language servers*: LSP queries spawn and tear down a language server per invocation across sub-agents.
* *Static runtime translation*: Supporting frontier coding agents (Claude Code, OpenCode, Antigravity, Codex) requires static build-time corpus translation per runtime.

=== Architectural Shift

[cols="2,3"]
|===
|Problem |PM-MCP Requirement & Design Response

|Rules enforced by prose
|The workflow state machine executes inside the server (`PM-WF`); invalid transitions are omitted from representations and rejected on execution.

|Model assembles CLI calls
|The server returns valid transitions as hypermedia links (`PM-WF-2`); the model supplies only a `link` identifier and judgment parameters (`args`) via `pm_do`.

|Scratch-file staging for multi-line text
|The model passes multi-line UTF-8 text (commit messages, PR/issue bodies, outlines, clarified requests, task descriptions, lessons, ADRs) directly in `pm_do` `args` over JSON-RPC (`PM-WF-2`, `PM-WF-6`); `pm-mcp` validates and persists stores atomically or pipes payloads in memory via `stdin` to child tools (`PM-EXEC-5`), eliminating `.plan/temp/` and `work/` staging files.

|Duplicated compound operations (commit, push, triage)
|Reusable, config-aware compound sub-workflows (`PM-WF-16`, such as `git.commit_and_push` and `verify.feedback_triage`) execute over a persisted call stack (`call_stack`) and return closed outcomes to any calling phase or tool workflow.

|Resident context overhead
|Only the active state's representation and targeted vocabulary skill enter model context (`PM-SKILL-1`).

|Bash as transport
|All plan-marshall operations execute as typed MCP tool calls over native `stdio` (`PM-ARCH-3`, `PM-TOOL-1`); only the initial entry bootstrap (`pm-mcp enter`) runs in the host shell.

|Skill/script drift
|Skills, state transitions, and tool schemas are served from a single versioned binary (`PM-DIST-1`).

|Cold LSP startups
|Each `pm-mcp` server process maintains a warm language server pool for the active session (`PM-SVC-2`).

|Static runtime translation
|The server translates tool names, dispatch conventions, and skill references on the fly using data-driven client profiles (`PM-CLIENT-2`) across `claude`, `opencode`, `antigravity`, and `codex`.
|===

Judgment remains strictly with the model: refining requests, authoring solution outlines, implementing code, triaging findings, and composing commit/PR descriptions. PM-MCP narrows the model's workflow obligations to supplying those judgment artifacts directly as free parameters of hypermedia links.

|===
|Term |Definition

|Machine
|The developer's workstation running `pm-mcp` native processes and any number of coding agent hosts.

|Host
|A frontier coding agent runtime connecting to MCP servers over `stdio` and hosting the model (`claude` for Claude Code, `opencode` for OpenCode, `antigravity` for Antigravity, `codex` for Codex).

|Session
|A single conversation instance within a host. Each host session spawns `pm-mcp serve` over `stdin`/`stdout` and coordinates with other sessions via atomic filesystem stores and OS file locks.

|Sub-agent
|A child session spawned through a `dispatch` link; operates within the parent plan or epic scope and inherits its recorded client identity.

|PM
|The model participant operating within a host session.

|Operator
|The human developer responsible for the machine and its repositories. Enrols projects, resolves escalations, and performs privileged actions exclusively via MCP elicitation or the operator CLI.

|`pm-mcp`
|The single GraalVM native executable deployed on the host, providing `pm-mcp serve` (the native STDIO MCP server), `pm-mcp enter`, `pm-mcp client`, `pm-mcp status`, `pm-mcp drain`, and `pm-mcp operator` CLI commands.

|Server / Daemon
|The `pm-mcp` native server runtime executing the workflow engine, state stores, build slot scheduler, warm LSP pool, MCP proxy, and audit log.

|Entry point & Entry call
|A user-invoked command in the client bundle that executes `pm-mcp enter --client <client>` to record the client identity and workspace root in the plan or epic entry record.

|Representation
|The TOON-formatted state payload returned by the server describing the current state of a plan or epic, relevant domain facts, and valid hypermedia links.

|Link & Link ID
|A valid state transition offered in a representation (`rel`, `link` identifier such as `push` or `triage:F-12`, and free parameter names), invoked via `pm_do`.

|Job
|A build, git, CI, or script subprocess managed by `pm-mcp` on the host, verified against project enrolment and tracked via `wait` links.

|Enrolment
|The operator-authorized registration of a project root, its pinned build wrappers/tools, SHA-256 digests, and allowed execution arguments.
|===

== Appendix: Verification Gates & Risk Register (Non-Normative)

=== Technical Verifications Required During Implementation

Each verification item below specifies the deterministic fallback if the primary technical assumption fails during spike testing:

1. *Quarkus Native Image Dependency Set*: Verify `io.quarkiverse.mcp:quarkus-mcp-server-stdio` and `cui-http` under GraalVM native image (`PM-TECH-1`, `PM-TECH-3`). _Fallback_: Supply explicit native-image reachability metadata or replace incompatible library components; native compilation of `pm-mcp` is non-negotiable.
2. *LSP4J under GraalVM Native Image*: Verify LSP4J JSON-RPC protocol reflection and dynamic proxy registration (`PM-SVC-2`, `PM-TECH-3`). _Fallback_: Replace LSP4J with a minimal Jackson-based JSON-RPC client for the closed set of LSP operations used by PM-MCP.
3. *Linux systemd Confinement against Real Builds*: Verify `systemd-run --user` read-only filesystem confinement with real project builds using wrapper caches, Testcontainers, and Docker Compose (`PM-SEC-5`, `PM-TECH-4`). _Fallback_: Enrol additional explicit write paths in project enrolment (`~/.plan-marshall/mcp/`); never disable confinement.
4. *macOS Keychain Access from Native Binary*: Verify `Security.framework` access via Java FFM from the `pm-mcp` native executable (`PM-CRED-2`). _Fallback_: Use the encrypted/permission-guarded file credential store (`~/.plan-marshall/credentials/`) and require interactive operator confirmation via CLI.
5. *Linux Secret Service via D-Bus Unix Socket*: Verify `org.freedesktop.secrets` over JDK `UnixDomainSocketAddress` under native image (`PM-CRED-2`). _Fallback_: Fall back to `~/.plan-marshall/credentials/` with `0600` permissions.
6. *McpAssured STDIO Integration Harness (`McpStdioTestClient`)*: Verify `io.quarkiverse.mcp:quarkus-mcp-server-test` (`McpAssured.newStdioClient()`) spawning the compiled `pm-mcp` native image and JVM Uber-JAR under `maven-failsafe-plugin` (`PM-TECH-2`, `PM-TEST-3`, `PM-TEST-4`).
7. *Embedded Classpath Client Bundle Installation*: Verify `pm-mcp client install <client>` extraction and atomic configuration merge across Claude Code (`claude`), OpenCode (`opencode`), Antigravity (`antigravity`), and Codex (`codex`) (`PM-DIST-2`).
8. *MCP Call Idle Timeouts & Progress Reset*: Verify per-host tool call timeout thresholds and whether MCP `notifications/progress` messages reset the timer (`PM-IMPL-4`).

=== Tracked Architectural Risks & Mitigations

[cols="1,2,2"]
|===
|Risk |Impact |Normative Mitigation

|MCP Framework Evolution
|Quarkus MCP Server extension tracks fast-moving MCP specifications.
|Target exclusively the frontier MCP `2026-07-28` specification over `quarkus-mcp-server-stdio` (`PM-ARCH-3`, `PM-TECH-1`), own job scheduling (`PM-SVC-1`) and standard tool/resource skill delivery (`PM-SKILL-3`), and verify protocol behavior continuously with `McpAssured` (`PM-TEST-3`).

|Host Capability Variance
|Progress notifications, sub-agent MCP inheritance, and elicitation support vary across Claude Code, OpenCode, Antigravity, and Codex.
|Baseline interaction uses standard MCP tools (`PM-TOOL-1`) over `stdio`, bounded wait links (`PM-IMPL-4`), and operator CLI fallback (`PM-SEC-3`).

|Model Out-of-Sequence Calls or Invalid Arguments
|Because `pm_do` accepts free parameters in an `args` map, the host cannot pre-validate link-specific arguments via static JSON Schema.
|Server re-validates every transition and parameter against persisted state (`PM-WF-6`) and returns a structured parameter validation error plus fresh representation on mismatch.

|Judgment Quality Regression
|Replacing full-phase Markdown documents with concise state representations could omit implicit guidance.
|Pair every judgment state with a focused static vocabulary skill (`PM-SKILL-1`) and measure outline/triage quality before retiring legacy phases (`PM-MIG-4`).

|Server Process Crash or Disconnect
|An unexpected host or `pm-mcp` process termination interrupts the active STDIO session.
|Persist all workflow and job state in the filesystem (`PM-ARCH-6`), coordinate across processes via `FileChannel.lock()`, and recover interrupted jobs and move journals on startup (`PM-ARCH-8`).

|Upstream Proxy Trust Laundering
|Untrusted content from proxied external MCP servers could be mistaken for authoritative PM-MCP state.
|Attach provenance metadata (`_meta`), mark proxied output untrusted, and forbid re-serving upstream skills (`PM-SVC-3`, `PM-SEC-1`).
|===
