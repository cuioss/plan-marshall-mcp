= Roadmap
:toc: left
:toclevels: 1
:nofooter:

link:../README.md[plan-marshall-mcp] » Roadmap

The high-level order in which PM-MCP is built. Each entry ships on its own and is measured against plan-marshall's baselines before the next one starts. The details are in the xref:concept/README.adoc[concept documents]. The order follows the xref:concept/16-implementation.adoc#_transition_order[transition order]: first the foundation (entries 1–4), then ported stores, then redesigned workflows phase by phase; entries 4 and 6–10 correspond to the stages of the xref:concept/12-migration.adoc[Migration Path].

== 1. Verifications and development skills

Resolve the pending verifications first: the daemon's dependencies and LSP4J under native image, Keychain and Secret Service access, systemd confinement, dynamic request headers per client (xref:concept/13-open-questions.adoc[Open Questions and Risks]).
Add the project-local `pm-mcp-` skills that build, run and drive a development daemon in isolation (xref:concept/16-implementation.adoc#_development_skills[Development skills]).

== 2. Native binary, daemon and operator channel

One native executable `pm-mcp` with its modes: daemon, `token`, `serve --stdio`, `enter` and `operator`; loopback Streamable HTTP with short-lived tokens, and the daemon's lifecycle.
The operator CLI and PM-MCP's own secrets in the credential store come with it (xref:concept/02-architecture.adoc[Architecture], xref:concept/08-credentials.adoc[Credential Handling]).

== 3. State store, formats and entry

JSON and JSONL stores with format versions, serialized writes per plan, and the TOON renderer for results; the workflow engine's own state-machine core (xref:concept/16-implementation.adoc#_storage_and_output_formats[Storage and output formats]).
`pm-mcp enter` writes the entry record with client identity and workspace root (xref:concept/15-client-profiles.adoc[Client Profiles]).

== 4. Jobs, waits and executor adapter

The daemon replaces `marshalld` with `build`, `git` and `script` jobs on the host, followed by bounded and progress `wait` links; both waits are tested beyond the host's idle timeout (xref:concept/16-implementation.adoc#_waiting_primitives[Waiting primitives]).
The existing plan-marshall executor is exposed as tools and still runs every script in Python (xref:concept/07-build-execution.adoc[Build Execution]).

== 5. Ported core stores

References, tasks, findings and status switch to Java one by one after their differential tests pass; plan-marshall converts its remaining TOON stores to JSON beforehand.
This is the prerequisite for any redesigned workflow (xref:concept/14-test-strategy.adoc[Test Strategy]).

== 6. Build server, CI jobs and token-lane credentials

`pm_build` replaces the resolve-then-run pattern and returns structured results; CI providers are integrated as `ci` jobs through `gh` and `glab`.
Token-lane credentials for services such as Sonar, configured by the operator (xref:concept/06-services.adoc[Services], xref:concept/08-credentials.adoc[Credential Handling]).

== 7. Hypermedia pilot: finalize

The finalize phase runs through `pm_state` and `pm_do` links only; its skills shrink to vocabulary skills.
Exit criteria: no model-composed calls, and resume after `/clear` works from `pm_state` alone (xref:concept/03-hypermedia-workflow.adoc[Hypermedia Workflow]).

== 8. Remaining phases and epics

Init, refine, outline, plan and execute follow phase by phase, then orchestrator epics with sub-agent dispatch; each phase after the stores it writes are ported.
Retired scripts are removed together with the phase that replaces them (xref:concept/12-migration.adoc[Migration Path]).

== 9. LSP pool and MCP proxy

A warm LSP pool replaces per-call language servers.
Selected upstream MCP servers are proxied, each reached with its own credential (xref:concept/06-services.adoc[Services]).

== 10. Skill serving and distribution switch

Vocabulary skills are served by PM-MCP and translated per client profile; `pm-mcp` ships as a package with one MCP entry per host.
The filesystem skill corpus and the plugin-cache distribution are retired for plan-marshall's process skills (xref:concept/11-distribution.adoc[Distribution]).
