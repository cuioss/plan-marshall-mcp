= Roadmap
:toc: left
:toclevels: 1
:nofooter:

link:../README.md[plan-marshall-mcp] » Roadmap

The high-level order in which PM-MCP is built. Each entry ships on its own and is measured against plan-marshall's baselines before the next one starts. The details are in the xref:concept/README.adoc[concept documents]. The order follows the xref:concept/16-implementation.adoc#_transition_order[transition order]: first the foundation (entries 1–4), then ported stores, then redesigned workflows phase by phase in phase order; entries 4 and 6–13 correspond to the stages of the xref:concept/12-migration.adoc[Migration Path].

== 1. Verifications and development skills

Resolve the pending verifications first: the daemon's dependencies and LSP4J under native image, Keychain and Secret Service access, systemd confinement, dynamic request headers per client (xref:concept/13-open-questions.adoc[Open Questions and Risks]).
Add the project-local `pm-mcp-` skills that build, run and drive a development daemon in isolation (xref:concept/16-implementation.adoc#_development_skills[Development skills]).

== 2. Native binary, daemon and operator channel

One native executable `pm-mcp` with its modes: daemon, `token`, `serve --stdio`, `enter` and `operator`; loopback Streamable HTTP authenticated with a per-start cookie file, and the daemon's lifecycle.
It ships in an installation layout with start, stop and run scripts; the operator CLI and PM-MCP's own secrets in the credential store come with it (xref:concept/11-distribution.adoc#_server_installation[Server installation], xref:concept/08-credentials.adoc[Credential Handling]).

== 3. Core module, workflow DSL, state store and entry

A plain Java core module next to the Quarkus server holds primitives, the workflow DSL with its engine and generated diagrams, JSON and JSONL stores with format versions, and the TOON renderer; the DSL grammar is fixed with the init pilot, its first real workflow (xref:concept/16-implementation.adoc#_workflow_definition[Workflow definition], xref:concept/16-implementation.adoc#_modules[Modules]).
`pm-mcp enter` writes the entry record with client identity and workspace root (xref:concept/15-client-profiles.adoc[Client Profiles]).

== 4. Jobs, waits and executor adapter

The job runtime: the daemon replaces `marshalld` and runs the builds plan-marshall's scripts request, git operations and scripts as `build`, `git` and `script` jobs, with bounded and progress `wait` links tested beyond the host's idle timeout (xref:concept/16-implementation.adoc#_waiting_primitives[Waiting primitives]).
The existing executor is exposed as tools and still runs every script in Python; plan-marshall first adds the entry-record guard (xref:concept/12-migration.adoc#_plan_marshall_prerequisites[plan-marshall prerequisites]).

== 5. Ported core stores

References, tasks, findings, the `status.json` store and the working-tree hash switch to Java one by one after their differential tests pass; `manage-status`'s lifecycle and routing are not ported but replaced by the engine later.
plan-marshall converts its remaining TOON stores to JSON beforehand; this is the prerequisite for any redesigned workflow (xref:concept/14-test-strategy.adoc[Test Strategy]).

== 6. Build server, CI jobs and token-lane credentials

On top of the job runtime of entry 4: `pm_build` resolves the canonical command itself, replacing the resolve-then-run pattern, and returns parsed, structured results; CI providers are integrated as `ci` jobs through `gh` and `glab`.
Token-lane credentials for services such as Sonar, configured by the operator (xref:concept/06-services.adoc[Services], xref:concept/08-credentials.adoc[Credential Handling]).

== 7. Hypermedia pilot: init

Init runs through `pm_state` and `pm_do` links only, starting with typed questions to the user and the plan sources; its skills shrink to vocabulary skills, served by PM-MCP through its skill tools from here on.
Exit criteria: no model-composed calls, resume after `/clear` from `pm_state` alone, and the plan continues in legacy refine without loss (xref:concept/12-migration.adoc#_stage_3_hypermedia_pilot_init[Stage 3]).

== 8. Refine and outline

Refine and the outline with its light and deep lanes switch, including the escalation from the light to the deep lane as an engine transition.
Outline and triage quality are measured against plan-marshall before the next entry starts (xref:concept/13-open-questions.adoc#_risks[Risks]).

== 9. Plan and execute

The plan phase packs tasks into envelopes; execute dispatches them to sub-agents with tracked `dispatch_id`s and runs builds as jobs.
The plan directory moves into the worktree and back under the daemon's control (xref:concept/03-hypermedia-workflow.adoc#dispatch[Sub-agent dispatch], xref:concept/02-architecture.adoc#_plan_location[Plan location]).

== 10. Finalize

The finalize step sequence with its gates, CI and review waits, merge and landing, including the loop back to execute.
Its skills shrink to vocabulary skills; the retired finalize scripts are removed with it (xref:concept/12-migration.adoc#_stage_4_remaining_phases_and_epics[Stage 4]).

== 11. Epics

Orchestrator epics emit plans through their entry commands and follow them through their entry records; epic state changes only in a worktree.
The last plan-marshall process scripts retire with this entry (xref:concept/03-hypermedia-workflow.adoc#_epic_orchestration[Epic orchestration]).

== 12. LSP pool and MCP proxy

A warm LSP pool replaces per-call language servers.
Selected upstream MCP servers are proxied, each reached with its own credential (xref:concept/06-services.adoc[Services]).

== 13. Skill serving and distribution switch

All vocabulary skills are served and translated per client profile, also through the MCP Skills extension; client bundles are served by the daemon's install endpoint and applied with `pm-mcp client`.
The filesystem skill corpus and the plugin-cache distribution are retired for plan-marshall's process skills (xref:concept/11-distribution.adoc[Distribution]).
