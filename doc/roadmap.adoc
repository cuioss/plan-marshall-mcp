= Roadmap
:toc: left
:toclevels: 1
:nofooter:

link:../README.md[plan-marshall-mcp] » Roadmap

The high-level order in which PM-MCP is built. Each entry ships on its own and is measured against plan-marshall's baselines before the next one starts. The details are in the xref:concept/README.adoc[concept documents]; entries 4 and 6–10 follow the stages of the xref:concept/12-migration.adoc[Migration Path].

== 1. Verifications

Resolve the pending verifications before building on them: the daemon's dependencies and LSP4J under native image, Keychain and Secret Service access, systemd confinement against real builds, and dynamic request headers per client.
Every negative result is turned into a concept decision first (xref:concept/13-open-questions.adoc[Open Questions and Risks]).

== 2. Native binary and daemon

One native executable `pm-mcp` with its modes: daemon, `token`, `serve --stdio`, `enter` and `operator`.
The daemon serves Streamable HTTP on loopback with short-lived tokens and manages its own lifecycle: on-demand start, optional OS service, drain and restart on update (xref:concept/02-architecture.adoc[Architecture], xref:concept/09-security.adoc[Security]).

== 3. State store and entry

Plans and epics are persisted in the filesystem, with serialized writes per plan and no session context.
`pm-mcp enter` writes the entry record with client identity and workspace root; every call is validated against the persisted state (xref:concept/15-client-profiles.adoc[Client Profiles]).

== 4. Jobs and executor adapter

The daemon replaces `marshalld` with `build`, `git` and `script` jobs as subprocesses on the host, verified against the enrolment.
The existing plan-marshall executor is exposed as tools, so skills call tools instead of Bash (xref:concept/07-build-execution.adoc[Build Execution]).

== 5. Credentials and operator channel

The OS credential store with the file store as fallback, and `pm-mcp operator credentials` for set, check, verify and migrate.
Operator-only actions run through elicitation or the operator CLI, never through MCP tools (xref:concept/08-credentials.adoc[Credential Handling]).

== 6. Build server and CI jobs

`pm_build` replaces the resolve-then-run pattern and returns structured results; log parsers come with the domain support.
CI providers are integrated as `ci` jobs through `gh` and `glab` (xref:concept/06-services.adoc[Services], xref:concept/07-build-execution.adoc[Build Execution]).

== 7. Hypermedia pilot: finalize

The finalize phase runs through `pm_state` and `pm_do` links only; its skills shrink to vocabulary skills.
Exit criteria: no model-composed calls, and resume after `/clear` works from `pm_state` alone (xref:concept/03-hypermedia-workflow.adoc[Hypermedia Workflow]).

== 8. Remaining phases and epics

Init, refine, outline, plan and execute follow, then orchestrator epics with sub-agent dispatch.
Ported scripts switch to Java one by one once their differential tests pass (xref:concept/14-test-strategy.adoc[Test Strategy]).

== 9. LSP pool and MCP proxy

A warm LSP pool replaces per-call language servers.
Selected upstream MCP servers are proxied, each reached with its own credential (xref:concept/06-services.adoc[Services]).

== 10. Skill serving and distribution switch

Vocabulary skills are served by PM-MCP and translated per client profile; `pm-mcp` ships as a package with one MCP entry per host.
The filesystem skill corpus and the plugin-cache distribution are retired for plan-marshall's process skills (xref:concept/11-distribution.adoc[Distribution]).
