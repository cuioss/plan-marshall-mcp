A proposal to model every way a plan (and an epic) comes into existence as one server-side process. Today the corpus has a creation verb (`pm_start`) with six sources, but no process around it: nothing selects what to work on, nothing gathers a source's inputs before the plan exists, epic-emitted plans have no source at all, and an epic cannot be created. Legacy `plan-marshall` has about twenty ways in, spread over two commands, several menus and inline init prose. This document collects them (<<inventory-legacy>>), lists what PM-MCP specifies today and where it contradicts itself (<<inventory-pmmcp>>), describes the target process (<<target-model>>), and asks one question per open design point (<<decisions>>).

[#direction]
== Scope and operator direction

*In scope*: every path from "the user wants something done" to a plan (or epic) in its first workflow state: the host entry commands and their arguments, the pending entry record, selecting what to work on, gathering and verifying a source before the plan exists, the atomic creation, resuming, epic-emitted plans, creating and filling an epic, and the lesson maintenance that feeds lesson-sourced plans. *Out of scope*: everything after `init.classify` (WC decided it), the epic's running coordination after `epic.active` (DAE04), and the setup workflow's own states (SC06), except where a bootstrap route enters them.

The approved draft (operator 2026-09-29):

. *Entry*: `/plan-marshall [args]`, `/plan-orchestrator [args]`, `/marshall-steward` run `pm-mcp enter`; the arguments (plan id, text, issue, lesson, recipe, pr, local, base branch, from-epic) go into the pending entry record.
. *Bootstrap unit*: a unit of the workspace scope gathers everything before a plan exists, so an abandoned start leaves no plan directory: `start.resolve` (automatic: ambiguity guard; existing id -> resume; named source -> its source step; nothing named -> `start.choose`; missing setup -> the setup workflow), `start.choose` (server-listed candidates as facts, links `resume:<id>`, `new:request`, `new:issue`, `new:lesson:<id>`, `new:recipe:<key>`, `new:local_changes`, `new:pr`, `maintain:lessons`), source sub-steps (issue fetch through the ingestion validator, lesson premise, recipe parameters from `parameters_schema` replacing the built-in selection screens, local-changes preview, PR observation, epic row spec section), and `start.commit` = `pm_start` (atomic creation, then `init.classify`).
. *Epic-emitted plans*: a new source `epic_row` (epic id + plan id): `request.md` is the staged spec section, the `plan_id` binds the queue row, and the emitted command is the host entry command.
. *Epic bootstrap*: epic intake `epic.define` (title, vision into `spec.md`, `parallelization_scope`; source text or issue), `epic.decompose` (dispatch of the decompose role; workstreams and staged specs submitted; surface disjointness checked by the server), then `epic.active`.
. *Lesson maintenance* (analyze, aggregate): a separate workspace workflow that ends pointing at `new:lesson:<id>`.

Principles applied to every item: clean cut from legacy (legacy is reference behaviour, nothing is imported); server-side first; model-facing minimality; native provider modules; the process enforces itself (no operator questions during a plan, bounded self-remedy then a defined fallback, operator influence only through the operator channel, content questions are question records per Z5-E); minimal resolution first; no new dependency.

*Bootstrap is not mid-plan*: before a plan exists there is no plan to protect. Choosing what to work on is the user's intent, relayed by the model from the host conversation; it is a legitimate interaction and not an operator question in the sense of Z5-A. Once `pm_start` has created the plan, every rule of WC applies unchanged.

One process, three units: the *bootstrap unit* (per entry, hosted by the workspace scope), the plan workflow from `init.classify` on (unchanged), and the *epic intake* states at the front of `epic.pmwf`. Lesson maintenance is a separate workspace unit that feeds the bootstrap (<<z6-19>>).

[#decisions]
== Decision items

Items are ordered so that each depends only on earlier ones. Every item names the principle that decides it and what the server checks.

[#z6-a]
=== Z6-A Principle: bootstrap sub-workflows instead of source parameters

* *Question*: Operator 2026-09-29 while discussing Z6-10: "Why not bootstrapping using a subprocess? For all bootstraps like plan, epic and marshall-steward. So you do not need to pass a fixed number."
* *Evidence*: Z6-2 and Z6-10 as proposed enumerate the sources twice (the `pm-mcp enter` flags and the `pm_start` arguments); every new way to start would change the CLI, the tool schema, PM-TOOL-1 and the host bundles.
* *Decision*: Operator 2026-09-29: adopted, and `pm_start` is removed. Every scope is created by a bootstrap sub-workflow of its kind (`bootstrap-plan`, `bootstrap-epic`; the workspace keeps `project-setup`, driven by `/marshall-steward`). `pm-mcp enter` passes only the kind, an optional id, and an optional free-text hint (the user's words). The ways to start are links of the bootstrap; the model maps the user's words onto a link, and the server validates every argument. * *Adjusted by round-4 D17 (2026-10-01)*: the adoption enters `epic.decompose` only for a ledger without any queue row (the specified form), otherwise `epic.active`; "no staged row" would leave an epic with only launched or running rows in a state that cannot ingest landings.
