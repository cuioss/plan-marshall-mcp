= Client Architecture
:toc: left
:toclevels: 2
:nofooter:

xref:../Requirements.adoc[Requirements] » xref:README.adoc[Discussions] » Client Architecture

NOTE: *Status: decided 2026-09-28*: see decision list (<<decisions>>). Where a *Decision* or *Adjusted by* line differs from the recommendation or the proposal body, that line holds. Deferred improvements are recorded in link:../later-improvements.adoc[Later Improvements] (L-1, L-2, L-4).

A proposal for how clients reach `PM-MCP`: a local adapter that trusts local processes of the same OS user without any credential distribution, a separate native CLI binary, a web adapter with one-time-password pairing, and a Svelte web application. It also folds in the client/CLI points collected during the design review (Z1 agenda) and the contradictions found in the current client and transport design.

Research date for all external sources: 2026-09-28. Recheck versions and issue states before relying on them.

[#direction]
== Operator direction

. An *adapter of the core service* receives requests from separate local CLIs without special configuration or credential distribution. It trusts locally running clients, built on researched secure patterns.
. A *CLI binary*, started locally, connects to that adapter. It is a separate Java module built into a GraalVM native binary, uses existing libraries for the low-level work where they are native-compatible, is part of the delivery and installation, and starts *very fast*.
. A new *top-level Maven aggregator for clients*; the CLI is one module in it.
. A *web adapter* provides REST endpoints and an authentication scheme. First iteration: one-time-password pairing (code entered manually and/or QR code); the CLI onboards a user/browser. Later iterations: OAuth with Token-Sheriff and API-Sheriff.
. A *web application* module in Svelte (current version) stores the paired secret in the browser and sends it as `Authorization: Bearer`, so an OAuth access token can replace it later.

[#current]
== Current design (inventory)

* *One native binary* (`pm-mcp`, Quarkus, module `pm-mcp-server`) with subcommands `runtime`, `serve`, `enter`, `client`, `operator`, `status`, `drain`, `hook` and the internal `job-exec` (`PM-IMPL-1`, link:../specification/runtime-model.adoc[Runtime Model]).
* *Always-on runtime* per machine and `PM_MCP_BASE`, started on demand by the relay; hosts reach it only through the `pm-mcp serve` STDIO relay; sessionless Streamable HTTP over a Unix domain socket `<PM_MCP_BASE>/run/runtime.sock` (0600 in a 0700 directory, `$TMPDIR/pm-mcp-<hash16>/` fallback for `sun_path` length); peer-UID check "where the platform exposes peer credentials"; *zero TCP/UDP listeners* (`PM-SEC-4`, `PM-ARCH-1`).
* *Trust*: only the OS (directory and socket permissions, peer UID). No token. Any process of the same user can reach the socket; this grants nothing beyond the model's own MCP tool surface.
* *Operator channel*: MCP elicitation, or `pm-mcp operator <verb>`, which writes stores directly under file locks and never calls the runtime; TTY required, agent environment markers refused, operator credential in the OS keyring, passphrase (PBKDF2) on Linux Secret Service and file store; macOS pty residual risk accepted.
* *`enter`* and *`hook`* run in the host shell (model-executed), write stores directly and never contact the runtime.
* *No* web UI, REST API, browser access, pairing or OAuth in the requirements or specifications. `token-sheriff-bom` is imported in Milestone 0 without any user. link:local-endpoint-authentication.adoc[Local Endpoint Authentication] describes a superseded loopback/cookie design.

* *Four binaries.* `pm-mcp` is the interactive and host-facing CLI (fast start, small); `pm-mcpd` is the daemon, started on demand by the CLI; `pm-mcp-exec` is the job launcher; `pm-mcp-web` is the optional web server, started by `pm-mcp web enable` and stopped by `web disable` (<<z1-1>>, <<z1-2>>, <<z1-21>>).
* *One REST API, two clients.* `/api/v1` exists only on the daemon's Unix socket; the CLI and the web server are its clients. Relays use `/mcp` on the same socket (<<z1-8>>).
* *Single writer.* All state changes go through the daemon, including the web device store and pairing codes; neither client holds store logic (<<z1-5>>).
* *Daemon posture unchanged.* The daemon keeps zero TCP listeners (`PM-SEC-4`); every browser-facing concern (listener, TLS, CSP, framing headers, Host validation, static files) lives in `pm-mcp-web`.

[#local-trust]
== Local adapter: trusting local clients

Research summary (sources in <<sources>>):

* *Unix domain socket as the only local entry* is the established pattern (Docker moved from loopback TCP to a socket because of CSRF; ssh-agent, gpg-agent, D-Bus, rootless Podman). Loopback TCP without authentication is repeatedly exploitable from a browser (DNS rebinding: Ollama CVE-2024-28224, Tailscale CVE-2022-41924; MCP Inspector CVE-2025-49596). Browsers cannot reach a Unix socket.
* *Mandatory layers*: a 0700 directory owned by the user (checked with `lstat`: owner, mode, no symlink; refused otherwise), socket 0600 created under `umask 077`; the *peer UID* checked right after `accept` (Linux `SO_PEERCRED`, macOS `getpeereid`), a mismatch refused and logged; a `flock` singleton that alone may unlink a stale socket; clients run the same directory check before connecting, so a squatter cannot impersonate the daemon. The directory mode and the UID check protect, not the socket file mode (some systems ignore socket permissions, unix(7)).
* *Same-user processes cannot be kept out* (ssh-agent and 1Password document the same boundary); PID checks are unreliable (PID reuse). A token file readable by the user adds nothing against them; it matters only for a TCP or Windows fallback. Code-signature checks work only when both ends are signed by the same vendor. The existing statement stays: reaching the socket grants nothing beyond the MCP tool surface; operator actions need the operator session (<<z1-9>>).
* *Sandboxed agent shells* (Claude Code Seatbelt/bubblewrap) cannot reach Unix sockets unless allowed; the relay runs outside the sandbox. This is the desired boundary.
* *Runtime token file (operator input)*: a fresh random secret written at start into the 0700 run directory and read by clients (Jupyter token, Tailscale `sameuserproof` file) gives the same boundary as the peer-UID check without reading peer credentials, and works through the standard HTTP authentication seam (<<z1-6>>).
* *Java*: `jdk.net.ExtendedSocketOptions.SO_PEERCRED` (JDK 16+) returns the peer UID/GID on Linux and macOS through a JDK `SocketChannel` (no PID). *Quarkus/Vert.x over a Unix socket* needs the Netty native transport, has a history of failing in native executables, and exposes no peer credentials. Hence the proposal of an own JDK listener in front of the Quarkus router (<<z1-7>>). Native-image support of `SO_PEERCRED` is unverified: Milestone 1 spike, fallback `junixsocket` (Apache-2.0, native metadata since 2.6).

|No reflection metadata; reuses the existing Jackson dependency

|QR code
|Nayuki `qrcodegen` (MIT, no dependencies, no reflection), rendered with Unicode half blocks, 4-module quiet zone, forced black on white
|Smallest correct encoder; ZXing is larger and decodes too

|Terminal
|picocli ANSI and `System.console()`; no JLine
|Line editing is not needed

[#web]
== Web adapter and pairing

Research summary:

* *Pairing* follows the device-grant pattern (RFC 8628, Jellyfin Quick Connect, Home Assistant, WhatsApp linked devices): a short one-time code only *authorizes*; the browser receives a *separate per-device secret*. Code: 8 characters of the RFC 8628 alphabet `BCDFGHJKLMNPQRSTVWXZ` shown as `WDJB-MJHT` (~34.5 bits), single use, TTL 5 minutes, at most 5 failed attempts, one open pairing at a time, stored as hash. Device secret: 256 bits from `SecureRandom`, base64url, prefix `pmw_`, opaque (the daemon is issuer and validator, a JWT adds nothing and cannot be revoked instantly), stored as SHA-256 only with `{id, label, role, created_at, last_used_at}`; idle expiry.
* *QR content*: `http(s)://<host>:<port>/pair#code=WDJBMJHT` — code in the fragment (never sent to the server, not in logs or Referer), cleared by the SPA with `history.replaceState`; `Referrer-Policy: no-referrer`. On the same machine `pm-mcp web open` opens the URL directly (Jupyter pattern), no typing.
* *Exposure*: loopback `127.0.0.1` is a secure context and not subject to Chrome's Local Network Access prompt for same-origin requests. Mandatory: Host header validation (Quarkus `quarkus.http.host-validation.*`), `Origin` check on the MCP endpoint, no CORS, strict CSP as HTTP header (`default-src 'self'; script-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; require-trusted-types-for 'script'`), `X-Content-Type-Options: nosniff`. A LAN listener (phone scanning the QR) needs TLS: a daemon-generated self-signed certificate whose SHA-256 fingerprint the CLI and the pairing page show (Syncthing model); a local CA is a later option.
* *CSRF* does not apply: the credential is an explicit `Authorization` header, never an ambient cookie.
* *Browser storage*: `localStorage` keeps the pairing across restarts; its XSS exposure is accepted and mitigated (no third-party scripts, strict CSP with Trusted Types, no `{@html}`, per-device revocation, idle expiry). An HttpOnly cookie hides the secret but brings back CSRF and does not fit the Bearer/OAuth path. RFC 10017 (BCP 212, browser-based OAuth apps) ranks BFF > token-mediating backend > browser-only client for the later OAuth iteration.
* *Live updates*: SSE from Quarkus REST (`Multi<T>`); the SPA reads it with `fetch()` and a `ReadableStream`, because `EventSource` cannot send an `Authorization` header (never a token in the URL).
* *Quarkus*: a custom `HttpAuthenticationMechanism` (Bearer `pmw_…`) plus an `IdentityProvider` (hash lookup) building a `SecurityIdentity` with device id and roles; resources use only `@Authenticated`/`@RolesAllowed`. Token-Sheriff's Quarkus integration is a CDI interceptor (`@BearerAuth`) with injected `JsonWebToken`, not an authentication mechanism, so the OAuth iteration wraps its validation in a mechanism of its own and routes by token shape (`pmw_` opaque vs three-part JWT), keeping paired devices working during the switch. API-Sheriff: no public documentation found — its role is for the operator to define.

[#webapp]
== Web application

* Svelte 5.57 (runes) is current; SvelteKit 2 is stable, SvelteKit 3 is a release candidate (2026-08-13). For a small SPA (pairing, devices, status, live plan view, decisions) plain *Svelte 5 + Vite* with a small router avoids the Kit 2→3 transition; SvelteKit with `adapter-static` is the alternative.
* The build produces static files served by the daemon from `META-INF/resources` (works in JVM and native). Options: Quarkus Quinoa (Quarkiverse extension, runs the npm build inside the Quarkus module, proxies the Vite dev server) or `frontend-maven-plugin` in the web-app module producing a resource JAR that `pm-mcp-server` depends on.

[#decisions]
== Decisions

[#z1-1]
=== Z1-1 Binary split

* *Question*: Which binary does what?
* *Options*: (a) two binaries: `pm-mcp` (CLI: relay, enter, hook, status, drain, runtime, client, web, operator, job-exec) and `pm-mcpd` (daemon); (b) keep the single Quarkus binary for everything and add the CLI for operator and web pairing only; (c) as (a) but the relay stays in the daemon binary.
* *Recommendation*: (a). Everything hosts and users invoke gets ~3 ms start and a small binary (the relay's 50 ms budget becomes trivial); the daemon binary carries Quarkus only where it is needed. Host configurations keep calling `pm-mcp serve`.
* *Affected*: `PM-IMPL-1`, `PM-TECH-1`/`-3`, `PM-DIST-*`, Runtime Model (start modes: the CLI spawns `pm-mcpd`), release layout.
* *Decision*: Operator 2026-09-28: (a) two binaries, `pm-mcp` (CLI) and `pm-mcpd` (daemon, started on demand by the CLI).
* *Adjusted by Z1-2 and Z1-21*: four binaries — `pm-mcp`, `pm-mcpd`, `pm-mcp-exec`, `pm-mcp-web`.

[#z1-2]
=== Z1-2 Location of `job-exec`

* *Question*: Where does the confinement launcher live?
* *Options*: (a) hidden subcommand of the CLI binary; (b) its own tiny binary `pm-mcp-exec`; (c) stays in the daemon binary.
* *Recommendation*: (a). Fast start matters for every job, the launcher needs no Quarkus, and one fewer artifact to digest and install. The FFM code for Landlock/`setpgid` moves into the CLI module.
* *Affected*: Job Runtime § Launcher, `PM-SEC-5`, release layout.
* *Decision*: Operator 2026-09-28: (b) own tiny binary `pm-mcp-exec`. Rationale: the CLI is only for interaction — a clear direction per binary. The Z1-1 split reads accordingly: `pm-mcp` interactive/host-facing commands, `pm-mcpd` daemon, `pm-mcp-exec` job launcher.

[#z1-3]
=== Z1-3 Module structure

* *Question*: How are client and shared modules arranged?
* *Options*: (a) as in <<modules>>: new `pm-mcp-api` under `pm-mcp-modules`, new top-level `pm-mcp-clients` with `pm-mcp-cli` and `pm-mcp-web-app`, adapters as packages of `pm-mcp-server`; (b) as (a) plus a module `pm-mcp-adapters` for the local and web adapter; (c) CLI depends on `pm-mcp-core` (no `pm-mcp-api`).
* *Recommendation*: (a). The adapters are Quarkus wiring (listeners, security mechanisms, REST resources) and belong to the assembly; `pm-mcp-api` keeps the CLI and web contract free of engine and store code, so native-image cannot reach it.
* *Affected*: `PM-IMPL-1`, roadmap Milestone 0, CLAUDE.md § Modules.
* *Decision*: Operator 2026-09-28: (a) `pm-mcp-modules/pm-mcp-api` (contract), `pm-mcp-modules/pm-mcp-exec` (launcher binary, Z1-2), top-level `pm-mcp-clients` with `pm-mcp-cli` and `pm-mcp-web-app`, adapters as packages of `pm-mcp-server`, release profile packages all three binaries.
* *Adjusted by Z1-21*: `pm-mcp-clients` also contains `pm-mcp-web-server`.

[#z1-4]
=== Z1-4 CLI technology stack and dependencies

* *Question*: Which stack builds the CLI?
* *Options*: (a) plain native-image + picocli/picocli-codegen + JDK Unix socket with own HTTP/SSE client + jackson-core + Nayuki qrcodegen, built with `native-maven-plugin`; (b) Quarkus command mode (`quarkus-picocli`) native.
* *Recommendation*: (a). New dependencies to approve: `info.picocli:picocli` and `picocli-codegen` (Apache-2.0), `io.nayuki:qrcodegen` (MIT), build plugin `org.graalvm.buildtools:native-maven-plugin`.
* *Affected*: `PM-TECH-*`, `PM-IMPL-1`, Milestone 0.
* *Decision*: Operator 2026-09-28: (a); dependencies APPROVED: `info.picocli:picocli`, `info.picocli:picocli-codegen`, `io.nayuki:qrcodegen`, build plugin `org.graalvm.buildtools:native-maven-plugin` (also used by `pm-mcp-exec`, without picocli).

[#z1-5]
=== Z1-5 Single writer: the CLI through the daemon only

* *Question*: May the CLI write stores directly (today: `operator`, `enter`, `hook`)?
* *Options*: (a) no: every command is a request to the daemon's REST API; the CLI starts the daemon on demand; only `status` (when the daemon is down: reads `runtime.json`) and `drain` (signal) work without it; (b) keep direct store access for operator verbs and `enter` (CLI depends on `pm-mcp-core`).
* *Recommendation*: (a). One writer means one lock owner, one validation path and one audit path (server-side first); it removes the duplicated store code from the CLI and lets the web app offer the same actions. The cost — the daemon must run for operator actions — is already paid by on-demand start.
* *Affected*: CLI & Security § Operator CLI ("never calls the runtime"), `PM-DIST-3` ("requires no runtime pre-start"), `enter`, `hook`.
* *Decision*: Operator 2026-09-28: (a) daemon is the only writer; every CLI command is an API request (daemon started on demand); without the daemon only `status` (reads `runtime.json`, reports not running), `drain` (signal) and `hook session-start` (reads files, never starts the daemon, exits 0) work, none of them writes; a damaged store blocks only its scope/project, so repair verbs run through the daemon.

[#z1-6]
=== Z1-6 Local trust model

* *Question*: Which layers establish trust on the local adapter?
* *Operator input 2026-09-28*: "On start it writes a random secret into the filesystem, and the client reads it" (runtime token file, Jupyter/Tailscale `sameuserproof` pattern).
* *Options*: (a) runtime token file: at every start, before binding, the daemon writes a fresh 256-bit secret atomically to `<PM_MCP_BASE>/run/runtime.token` (0600, directory 0700); every local request carries `Authorization: Bearer <runtime token>`, checked by a Quarkus `HttpAuthenticationMechanism`; clients verify owner, mode and no symlink of directory and file before reading; on `401` a client re-reads the file once (daemon restarted); the secret is in the redaction registry, never in logs, arguments or job environments, and `run/` is outside every job's Landlock read set; the Unix socket stays the listener (0600 under `umask 077`, `flock` singleton), the peer UID is checked additionally where cheaply available and never required; (b) peer UID mandatory, no token (requires an own JDK listener); (c) (a) plus peer UID mandatory.
* *Recommendation*: (a). Same boundary as the peer-UID check (only the same OS user reads the file; same-user processes are out of reach for either), but an ordinary HTTP authentication through the standard Quarkus seam, identical to the web adapter's bearer tokens, portable to a loopback-TCP fallback (with Host/Origin validation) and to Windows.
* *Affected*: `PM-SEC-4`, Runtime Model § Transport Endpoint, Filesystem Layout (run directory), CLI & Security § Runtime Secret Redaction, Job Runtime (Landlock read set).
* *Decision*: Operator 2026-09-28: (a) runtime token file (operator's proposal); peer UID optional, never required.

[#z1-7]
=== Z1-7 Local adapter implementation

* *Question*: How does the daemon listen locally?
* *Options*: (a) Quarkus/Vert.x domain socket (`quarkus.http.domain-socket-enabled`, `host-enabled=false`) with the runtime-token mechanism of <<z1-6>>; (b) an own JDK `ServerSocketChannel` (UNIX, virtual threads) bridging requests in-process to the Quarkus router; (c) loopback TCP `127.0.0.1` with the runtime token, Host and Origin validation.
* *Recommendation*: (a), verified by a Milestone 1 spike (native image on macOS and Linux, SSE streaming, stale-socket handling); fallback (c), then (b). With the token, the listener no longer has to expose peer credentials, which was the reason for (b).
* *Affected*: `PM-TECH-1`, Runtime Model § Transport Endpoint, roadmap Milestone 1.
* *Decision*: Operator 2026-09-28: (a) Quarkus/Vert.x domain socket with the runtime-token mechanism, verified by a Milestone 1 spike (native macOS/Linux, SSE, stale socket, path-length fallback); fallback order (c) loopback TCP with token + Host/Origin validation, then (b) own JDK listener.

[#z1-8]
=== Z1-8 One REST API on both listeners

* *Question*: What do the CLI and the web app talk to?
* *Options*: (a) one versioned REST API `/api/v1` (JSON, resource model from `pm-mcp-api`) served on the local and the web listener, authorization per listener (local: runtime token, operator verbs need the operator session; web: device bearer and role); `/mcp` only on the local listener; (b) separate local and web APIs.
* *Recommendation*: (a). One contract, tested once; the web app and the CLI stay feature-equal where roles allow. The MCP endpoint is never exposed on TCP (browser threat model).
* *Affected*: new specification section (API), `PM-TOOL-*` boundary statement, `PM-SEC-4`.
* *Decision*: Operator 2026-09-28: (a) one REST API `/api/v1` on both listeners, authorization per listener; `/mcp` only on the local listener.
* *Adjusted by Z1-21*: `/api/v1` is served only on the daemon's Unix socket; the web server is a proxying client, not a second listener of the daemon.

[#z1-9]
=== Z1-9 Operator authentication (replaces D2b)

* *Question*: How is an operator action told apart from a model shell of the same user?
* *Options*: (a) `pm-mcp operator login` requires a TTY and no agent environment markers, reads the passphrase without echo and sends it over the Unix socket; the daemon verifies it against a PBKDF2-HMAC-SHA256 hash (≥ 600,000 iterations, salt, parameters in `<PM_MCP_BASE>/state/operator.json`, 0600) with the persisted back-off, and issues an *operator session* (random, in memory only, idle timeout 15 minutes, absolute 8 hours, compiled) that the CLI keeps in a 0600 file bound to the terminal session and presents as `Authorization: Bearer`; (b) keep the OS keyring as the operator credential without a passphrase on macOS (today); (c) OS authentication (Touch ID / polkit) — later.
* *Recommendation*: (a). One mechanism on every platform, an actual user proof on macOS too, and the same session model the web adapter uses (roles). The macOS pty residual risk narrows to "the model watches the operator type": documented, accepted.
* *Affected*: `PM-SEC-*` operator channel, `PM-CRED-*` (operator entry leaves the credential store), CLI & Security § Operator Channel Isolation, Store Schemas (new `operator.json`), C5.
* *Decision*: Operator 2026-09-28: new option (e) CLI-only proof for now — operator verbs are accepted when the CLI passes its checks (terminal attached, no agent environment markers, host deny rules as defence in depth); no passphrase. Risk accepted: a model shell that deliberately defeats the checks can run operator verbs. The improvement (passphrase session, later Touch ID/polkit) is recorded as L-1 in link:../later-improvements.adoc[Later Improvements]; OAuth for the web adapter as L-2. C5 is resolved by removing the operator passphrase/keyring entry from the first iteration.

=== Z1-10 Web adapter exposure

* *Question*: Where does the web adapter listen?
* *Options*: (a) off by default; `pm-mcp web enable` (or the first `web pair`) opens a loopback listener `127.0.0.1:<port>` over HTTP; `--lan` opens it on the LAN with TLS (daemon-generated self-signed certificate, fingerprint shown by the CLI and the pairing page); Host validation, no CORS, strict CSP; (b) loopback only, no LAN in the first iteration (the QR code then only serves the same machine); (c) LAN with TLS always.
* *Recommendation*: (a). The QR code is only useful with a second device, which needs LAN; TLS is mandatory there. Off by default keeps "no listener" as the default posture; `PM-SEC-4`/`PM-ARCH-1` change from "zero TCP listeners" to "no TCP listener unless the operator enables the web adapter".
* *Affected*: `PM-SEC-4`, `PM-ARCH-1`, `PM-ARCH-2` (local only still holds), Runtime Model, `machine-config.json` (listener settings).
* *Decision*: Operator 2026-09-28: (a) off by default; loopback HTTP on `web enable`/first `web pair`; `--lan` with daemon-generated self-signed TLS and fingerprint; Host validation, no CORS, strict CSP, `/mcp` never on TCP. Local CA for LAN recorded as later improvement (L-2).
* *Adjusted by Z1-21*: the listener, TLS and headers belong to `pm-mcp-web`, started by `web enable`; the daemon keeps zero TCP listeners, so `PM-SEC-4`/`PM-ARCH-1` are unchanged for the daemon and gain a statement for the optional web server.

=== Z1-11 Pairing protocol

* *Question*: What is the one-time password and what does the browser keep?
* *Options*: (a) one-time *code* (8 chars, base-20, TTL 5 min, single use, 5 attempts, one open pairing, hashed) exchanged at `POST /api/v1/pair` for a per-device secret (`pmw_` + 256 bits, opaque, SHA-256 stored); the browser keeps and sends the device secret; (b) the one-time password itself becomes the bearer (then it must be long and random, cannot be typed from the screen, and is not one-time).
* *Recommendation*: (a). It keeps "one time" true, makes typing feasible, and gives each browser a revocable identity.
* *Affected*: new API section, Store Schemas (new `web-devices.json`), identifiers.
* *Decision*: Operator 2026-09-28: (a) one-time code (8 chars base-20, 5 min, single use, 5 attempts, one open pairing, hashed; QR with code in the URL fragment; `web open` for the same machine) exchanged at `POST /api/v1/pair` for a per-device secret `pmw_` + 256 bits (SHA-256 stored); the browser keeps and sends the device secret as Bearer.

=== Z1-15 Browser storage of the secret

* *Question*: Where does the SPA keep the device secret?

* *Recommendation*: (a). Persistence is the purpose of pairing; the XSS exposure is contained by the CSP and revocation; (c) breaks the Bearer path. For OAuth the access token moves to memory (RFC 10017).
* *Affected*: web app, security headers.
* *Decision*: Operator 2026-09-28: (a) `localStorage` with strict CSP header plus Trusted Types, no third-party scripts, no `{@html}`, lockfile-pinned dependencies, revocation and idle expiry as recovery; plus explicit anti-framing: CSP `frame-ancestors 'none'` and `X-Frame-Options: DENY` on every web-adapter response. Sender-constrained tokens (non-extractable WebCrypto key, DPoP) recorded in L-2.
* *Adjusted by Z1-21*: the security headers are set by `pm-mcp-web`.

=== Z1-21 Web server as a separate client process

* *Question* (operator 2026-09-28): Would a custom web server that talks to the daemon through the same endpoints as the CLI simplify matters and keep the daemon leaner?
* *Proposal*: `pm-mcp-web` (module `pm-mcp-clients/pm-mcp-web-server`, Quarkus native) is a client of the daemon like the CLI. It serves the SvelteKit app, owns the TCP listener (loopback, `--lan` with TLS), the security headers, Host validation and the pairing-redemption endpoint, and proxies `/api/v1` including SSE to the daemon's Unix socket with the runtime token, forwarding the browser's device secret in a header. The daemon keeps the device store and pairing codes (single writer) and checks the forwarded device secret on every request. `pm-mcp web enable|disable` starts and stops the web server; without it no listener exists. The pattern is a backend-for-frontend, the recommended placement for the later OAuth iteration (L-2).
* *Note*: with the daemon as single writer (Z1-5) and the CLI-only operator proof (Z1-9), any same-user process holding the runtime token can call operator endpoints directly (for example `curl --unix-socket`), not only a model that defeats the CLI checks; this is within the risk accepted for Z1-9 and stated in L-1.
* *Affected*: Z1-1, Z1-3, Z1-8, Z1-10, Z1-14, Z1-15, Z1-17 (adjusted), `PM-SEC-4`, `PM-IMPL-1`, `PM-DIST-*`.
* *Decision*: Operator 2026-09-28: adopted.
