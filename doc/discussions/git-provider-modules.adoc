= Git and Provider Modules
:toc: left
:toclevels: 2
:nofooter:

xref:../Requirements.adoc[Requirements] » xref:README.adoc[Discussions] » Git and Provider Modules

NOTE: *Status: decided 2026-09-28*: see decision list (<<decisions>>); decisions applied to the specifications. Where a *Decision* line differs from the recommendation or the proposal body, the Decision line holds.

A proposal for how `PM-MCP` performs git, GitHub, GitLab and CI operations. It reverses the current design: instead of driving the host's `git`, `gh` and `glab` with the operator's credentials, `PM-MCP` ships its own in-process implementations as the default, authenticated through its own credential stores, and keeps the command-line tools as a configurable variant. It proposes the Maven module structure for this (and for all other Java modules of the concept), evaluates the candidate libraries, and resolves the provider and merge mechanics that the specifications mark _open design topic: git/GitHub/GitLab approach_. Nothing here is part of the target design until the decisions in <<decisions>> are taken and carried into the specifications.

Research date for all external sources: 2026-09-28. Recheck versions and issue states before relying on them.

== Overview and direction

[#direction]
=== Operator direction

Current design (`PM-EXEC-5`, `PM-CRED-1`, link:../specification/cli-and-security.adoc[CLI & Security] § Two-Lane Provider Architecture): every git and provider operation is a verified subprocess job of the enrolled `git`, `gh` or `glab`, inheriting the developer's authentication (credential helpers, SSH agent, `gh auth`). `PM-MCP` holds no credentials for this *System Lane*. Two problems follow:

. *One identity for operator and agents.* Every push, pull request, comment, thread resolution and merge made by an agent is indistinguishable from the operator's own work, and runs with the operator's full token scope (typically `repo`, often `admin:org` after a merge-queue setup). A compromised or confused agent session acts with everything the operator may do.
. *Sandboxing of subprocesses.* The provider CLIs need the operator's credential stores (`~/.config/gh/hosts.yml`, the keyring, the SSH agent socket, the GPG agent), their own write paths (token refresh, `known_hosts`), and environment variables the job environment otherwise refuses (link:../specification/job-runtime.adoc[Job Runtime] § Job Environment ends with "Environment and write paths specific to `git` and `ci` jobs … are an open design topic"). Opening these to a Landlock-confined job opens them to everything the job runs, including repository hooks.

New direction, binding for this document:

* `PM-MCP` ships its *own* implementations of the git and provider operations as the *default* (the _native variant_), authenticated with credentials from `PM-MCP`'s token lane (`PM-CRED-1..5`) that belong to an agent identity, not to the operator.
* The existing CLIs remain as a *variant* (_CLI variant_) that the operator can configure.
* Native implementations prefer an existing, maintained Java library, provided it works in the Quarkus native image. Otherwise they use HTTP directly with `de.cuioss:cui-http`, as the Sonar client already does.
* A new Maven aggregator gathers the new modules. The Java modules are `pm-mcp-git`, `pm-mcp-ci`, `pm-mcp-github` and `pm-mcp-gitlab`.
* Creating and integrating *all* Java modules (aggregator, `pm-mcp-core`, `pm-mcp-server`, `pm-mcp-dist`, `pm-mcp-conformance`, and the four modules above) becomes the first roadmap item.

[#principles]
=== Principles

[cols="1,4"]
|===
|Principle |Meaning for git and provider operations

|G1 Native by default
|Every operation family has a native implementation. The CLI variant is an operator opt-in, never a silent fallback.

|G2 Agent identity, not operator identity
|The native variant authenticates as an agent identity (GitHub App installation, GitLab project or bot token) whose secret the operator enters once through `pm-mcp operator credentials`. The operator's own credentials are never read.

|G3 One contract, two implementations
|The workflow engine sees one contract per operation (typed input, closed outcome enumeration, TOON shape). Native and CLI implementations are interchangeable behind it and are verified against the same fixtures.

|G4 Observed, not assumed
|Every mutation is confirmed from the provider's or the repository's observed state before it counts (merge, enqueue, push, close). Exit codes and HTTP 2xx alone are never evidence (link:../specification/timeouts/01-job-budgets-and-waits.adoc#ci-mutation-budget[Timeouts] `ci` mutation class already requires this).

|G5 Derive capability, do not configure it
|Whether the native variant can serve a repository (object format, partial clone, filter protocol, signing requirement) is a derived fact (`C1` of link:store-and-config-model.adoc[Store and Configuration Model]). A repository the native variant cannot serve is reported with the reason and the operator command, never half-served.

|G6 Subprocesses only for foreign code
|In-process operations need no confinement of their own. A subprocess exists only where foreign code runs: repository hooks, `.gitattributes` filter drivers, and the CLI variant. Each runs as a confined job.
|===

[#current-state]
== Current state

What the specifications fix today, and where they stop:

* *Execution*: `PM-EXEC-5` requires all git operations as `git` jobs "preserving the developer's git configuration, credential helpers, SSH agent, commit signing, and repository hooks", and all provider operations as `ci` jobs of `gh`/`glab` "under the developer's existing CLI authentication", with argument vectors composed server-side from a closed operation set and free text on `stdin`.
* *Credentials*: `PM-CRED-1` classifies `git`, `gh` and `glab` as System Lane with "zero credentials" held by `PM-MCP`; the Token Lane serves Sonar and upstream MCP servers only. The credential store schema (link:../specification/store-schemas/12-machine-stores.adoc#credential-store[Store Schemas § Credential Store]) has `auth_type` `token|basic` and states that the System Lane "uses the CLI's own authentication".
* *Job environment*: built from scratch; `GH_TOKEN`, `GITHUB_TOKEN`, `GITLAB_TOKEN` and every `*_TOKEN` are never passed; `SSH_AUTH_SOCK`, `GH_CONFIG_DIR` and `XDG_CONFIG_HOME` are not listed, so under the current table a `git push` over SSH and every `gh` call would fail. The Landlock write set has no provider-CLI configuration or `known_hosts` path.
* *Budgets*: operation classes with floors exist (link:../specification/timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts § Job Budgets]): `git` local `120`, hook-running `300`, network `300`; `ci` query `60`, mutation `120`.
* *Open design topic*: the specifications mark provider and merge mechanics _open design topic: git/GitHub/GitLab approach_ (convention in link:../specification/state-catalogue.adoc[State Catalogue], opening paragraph). The occurrences are collected in <<parked-items>>.
* *Inconsistencies found while collecting*: the rate-window floor is `3600` in link:../specification/phase-workflows.adoc[Phase Workflows] § Refusals & Rate Windows but `5400` in link:../specification/timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts]; the finding `source` enum has no `ci` value although Predicate 1 counts `ci-verify` findings; `git.commit_and_push` still reads the retired `.marshall/marshal.json -> /plan/phase-5-execute/commit_and_push`; `PM-EXEC-5` and the Two-Lane section contradict the job environment table.

In `plan-marshall` (the reference implementation, inventory in <<inventory>>) all authentication is ambient: no subprocess gets an `env=`, bodies are passed on the argument vector from a scratch file (`--body-file` was deliberately removed), GitLab reads are never paginated, and no provider rate limit is handled.

[#inventory-ci]
=== CI evaluation and review-bot bookkeeping (server logic, not provider calls)

These stay in `pm-mcp-core` (phase workflows); the provider modules only deliver observations.

* *Check partitions* (`_github_checks.py`): non-failing `SUCCESS`, `SKIPPED`, `NEUTRAL`; failing `FAILURE`, `TIMED_OUT`, `CANCELLED`, `ACTION_REQUIRED`, `STALE`, `STARTUP_FAILURE`; waiting `IN_PROGRESS`, `QUEUED`, `PENDING`, empty.
* *Failure taxonomy* (`phase-6-finalize/scripts/ci_verify.py`): `ci_build_failure` (workflow name contains `verify|quality-gate|module-tests|coverage`), `ci_policy_failure` (every other failure and every unknown conclusion, fail-closed), `ci_cancelled`, `ci_action_required`, `ci_stale`, `ci_timeout`, `ci_no_checks`.
* *Wait mechanics*: seeded first sleep from learned `ci:wait` durations, then `gh run watch` per run or a 30 s poll; plan-marshall default timeout 600 s.
* *Review-bot rate windows* (`manage-locks`): claim per `(bot_kind, pr_number)` with `--window-seconds` default 3600 and `--attempt-cap` default 6; outcomes `claimed|renewed|reclaimed`, `window_held_by_other_plan`, `recovery_cap_exhausted`.
* *Participation states* (`review_completeness.py`): `absent, in_progress, refused_awaitable, refused_hard, refused_unknown, refused_structural, participated_but_empty, participated_stale, declined, not_triggered, unregistered_kind, participated`.

[#inventory-spec]
=== Operations the `PM-MCP` specifications add

* Push-barrier decision on the persisted `branch_pushed_at` fact, then the parity probe (`synced`, `ahead`, `remote_absent_landed`, `remote_absent_unverified`) with a fetch before classifying (link:../specification/workflow-dsl.adoc[Workflow DSL] § Six-Stage Execution Contract).
* Enqueue evidence only from observed membership; merged only from the observed pull-request state (link:../specification/phase-workflows.adoc[Phase Workflows] § Cross-Plan Merge Mutex, item 5).
* CI runs looked up by head SHA, never by `pull_requests[]` (fork pull requests, `PM-WATCH-JOB-9`).
* Scratch worktree at the merge base for baseline-red separation (link:../specification/job-runtime.adoc[Job Runtime] § Gate Honesty Verification, item 4).
* Timed-out `worktree remove` re-check with `worktree list --porcelain` and `worktree prune` (link:../specification/timeouts.adoc[Timeouts] D74).
* Capture of the user's local changes for the `local_changes` source and the land lane (link:../specification/phase-workflows.adoc[Phase Workflows] § Plan Source Contracts).
* Closing a pull request on `close-pr-and-archive`.
* Derived facts `base_branch_default`, `push_remote`, `ci_provider`, `merge_methods_allowed`, `merge_queue_enforced` (link:../specification/store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas § Derived Facts]).

[#scope-cuts]
=== Operations not carried over

* *Merge-queue enable* (ruleset create/update, bypass actors from app installations, GitLab `merge_trains_enabled=true`): administrative repository changes need admin scope, which an agent identity should not hold. `setup.merge-queue` reports the derived state and names the provider setting; the operator changes it.
* *Admin merge on stuck state* (`gh pr merge --admin`): removed by Z3-4 (weakens a guarantee).
* *Organisation reads* (`org list-repos`, `org search-code`, `repo file read` on foreign repositories): no `PM-MCP` consumer in the specifications. They return as operations of the orchestrator if a specification asks for them.
* *Pre-rendered scratch body files* (`ci pr prepare-body`): bodies are request payloads (native) or `stdin` (CLI variant).

== Module architecture

[#module-layout]
=== Modules and aggregator

[source]
----
plan-marshall-mcp-parent (root pom, aggregator of everything)
├── pm-mcp-core                 plain Java: primitives SPI, DSL, engine, stores, TOON, SPIs
├── pm-mcp-providers            NEW aggregator (packaging pom) for the provider modules
│   ├── pm-mcp-git              git contracts + native (JGit) + CLI adapter (git)
│   ├── pm-mcp-ci               provider-neutral CI contracts, provider SPI, registry, HTTP base
│   ├── pm-mcp-github           GitHub: native (REST + GraphQL over cui-http) + CLI adapter (gh)
│   └── pm-mcp-gitlab           GitLab: native (REST over cui-http) + CLI adapter (glab)
├── pm-mcp-server               Quarkus assembly (replaces plan-marshall-mcp)
├── pm-mcp-dist                 release layout (native binaries, digests, SBOM, notes)
└── pm-mcp-conformance          out-of-band, own profile, never in verify
----

The aggregator `pm-mcp-providers` is a `pom`-packaging module that only lists its four children and carries their shared `dependencyManagement` (JGit, and any GraphQL or JWT helper admitted by <<decisions>>). The root pom lists `pm-mcp-core`, `pm-mcp-providers`, `pm-mcp-server`, `pm-mcp-dist`, and `pm-mcp-conformance` only inside its profile (`PM-IMPL-1`).

Java packages follow `de.cuioss.pm.mcp.<module>` with the sub-packages `api` (contracts, exported), `nativeimpl` (native variant), `cli` (CLI variant), and `internal`. Each module sets `maven.jar.plugin.automatic.module.name` (project `CLAUDE.md`: no `module-info.java` in Quarkus modules; the provider modules follow the same rule so that one convention covers all modules).

[#dependency-direction]
=== Dependency direction

[source]
----
pm-mcp-core  <──  pm-mcp-git  <─────────────────────┐
     ^                                              │
     └──────  pm-mcp-ci  <──  pm-mcp-github  <──  pm-mcp-server  ──>  pm-mcp-dist
                         <──  pm-mcp-gitlab  <──────┘
----

* `pm-mcp-core` knows none of the provider modules and keeps its dependency rule (Jackson and `cui-java-tools` only, `PM-IMPL-1`). It defines the SPIs the provider modules implement or consume:
** `Primitive<P, R>` and the sealed-outcome convention (already specified);
** `JobRunner` (subprocess jobs through the `job-exec` shim, confinement, `stdin` payload, budgets; used by the CLI variants, hooks and filters);
** `SecretSource` (resolve a token-lane secret for one request, register it with the redactor; implemented in `pm-mcp-server` over the keyring primitive);
** `DerivedFacts` (read and refresh derived facts), `LeaseStore` (merge lease, review-bot windows).
* `pm-mcp-git` depends on `pm-mcp-core` and JGit. It contributes the `git.*` primitives, whose names the `.pmwf` units in `pm-mcp-core` reference.
* `pm-mcp-ci` depends on `pm-mcp-core` and `cui-http`. It holds the provider-neutral contracts, the provider SPI, the registry, and the shared HTTP base (authentication header injection, pagination, conditional requests, rate-limit handling, redaction) that both provider modules reuse.
* `pm-mcp-github` and `pm-mcp-gitlab` depend on `pm-mcp-ci` only. They receive repository coordinates as values (parsed remote), never through `pm-mcp-git`.
* `pm-mcp-server` depends on all of them, wires them through CDI producers, and registers native-image metadata (reflection, substitutions, resources) for JGit and the provider DTOs. It hosts the build-time test that every `.pmwf` unit validates against the assembled primitive catalogue: `pm-mcp-core` alone cannot see the `git.*` and `ci.*` primitives (<<z2-3>>).

[#contracts]
=== Contracts

Every operation is a contract with four parts, independent of the variant:

. *Operation name*: `git.<op>` or `ci.<op>`; it is the primitive name the DSL references and the budget key suffix (`git:<op>`, `ci:<op>`, link:../specification/timeouts.adoc[Timeouts]).
. *Input record*: typed, validated server-side, never carrying a free-form flag, argument or URL (`PM-EXEC-5`, `PM-WF-6`).
. *Closed outcome enumeration*: a sealed interface of result records. Every operation shares the *transport outcomes* `auth_failed`, `permission_denied`, `rate_limited{reset_at}`, `provider_unavailable`, `malformed_response`, `timed_out`, `unsupported_by_variant{reason}`, `capability_missing{reason}`, and adds its domain outcomes.
. *TOON shape*: the rendering of the result record at the wire boundary by the `pm-mcp-core` encoder (`PM-IMPL-3`). Every result carries `operation`, `outcome` and, for population reads, `completeness` (`complete|incomplete`) with `incomplete_reason` (`page_bound_reached`, `count_mismatch`, `provider_incomplete_results`, `result_cap_reached`, as `plan-marshall` defines them). The variant that served the operation (`native|cli`), the credential origin, and the timing are written to the operation's audit record (and the server log), never into the result: they change nothing the model does next (link:../specification/hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format, Model-Facing Minimality]). A variant that matters for a decision surfaces as an outcome (`unsupported_by_variant{reason}`, `capability_missing{reason}`), not as a field.

[#provider-resolution]
=== Provider resolution: registry and factory

`pm-mcp-ci` defines:

* `CiProviderModule` (SPI): `providerId()` (`github`, `gitlab`), `claims(RemoteCoordinates)` (host match or probed API), `create(ProviderBinding)` returning a `CiProvider`.
* `CiProvider`: one accessor per family (`pullRequests()`, `review()`, `checks()`, `merging()`, `facts()`, `issues()`, `branches()`), each an interface of the operations above.
* `ProviderBinding`: the resolved inputs for one project: remote coordinates, effective variant per family (<<variant-config>>), credential key, enrolled host tool (CLI variant), `JobRunner`, `SecretSource`.
* `CiProviderRegistry`: an explicit list of modules passed to its constructor. `resolve(project)` selects the module from the derived fact `ci_provider` (or the team override `ci_provider`), builds the binding, and returns a `CiProvider` whose family accessors dispatch to the native or the CLI implementation per family.

Registration is explicit, not `ServiceLoader` or classpath scanning: `pm-mcp-server` produces the registry from the two modules through a CDI producer, and plain-Java tests construct it directly. This keeps the closed-world property of the native image obvious (`PM-TECH-3`) and avoids provider discovery at run time (<<z2-4>>). `pm-mcp-git` has no registry: there is one git, with a `GitBackend` chosen per family by the same binding.

[#variant-config]
=== Configuration of the variants

The choice of variant decides whose credentials act and which binaries run. Under the configuration model (link:store-and-config-model.adoc[Store and Configuration Model], C4 and C5) that is operator posture and execution binding, never team policy: a team file must not be able to make an operator's machine act with the operator's personal credentials.

* *Team file* `.marshall/config/project.json`: unchanged. `ci_provider` stays the override for ambiguous remotes; `merge_method` stays a team key. No variant key.
* *Operator file* `<PM_MCP_BASE>/projects/<project_id>/local-config.json`, sparse, default native everywhere:
+
[source,json]
----
{
  "format_version": 1,
  "integrations": {
    "git":    { "variant": "cli" },
    "github": { "variant": "native", "families": { "checks": "cli" } }
  }
}
----
+
`integrations.<module>.variant` (`native|cli`) sets the module; `integrations.<module>.families.<family>` overrides one family. Validation: a `cli` value requires the host tool (`git`, `gh`, `glab`) in the project's enrolment (`cli_tool_not_enrolled`); a family unknown to the module is refused (`unknown_config_key`). `machine-config.json` `project_defaults` may carry the same keys machine-wide, per the operator resolution chain.
* *Derived capability*: the derived fact `git_native_capability` (local, <<derived-git-facts>>) lists repository features the native git cannot serve. When a family needs a missing capability and the operator has not configured `cli`, the step raises `blocked` with `facts.reason: git_capability_missing`, the feature, and the `pm-mcp operator config` command that selects the CLI variant for that family. There is no automatic fallback (G1): a silent switch to the CLI would silently switch to the operator's credentials.
* *Credential binding*: implicit. The native GitHub and GitLab variants use the token-lane entry with credential key `github` or `gitlab` (project entry before global entry, `PM-CRED-2`); the native git transport uses the provider's entry for provider hosts and `git-https` for other hosts (<<credential-model>>). The origin of the entry's `url` must match the remote (<<remote-integrity>>).
* *Effective configuration*: `pm://project/config` reports per family the effective variant and its source (`operator`, `machine_default`, `compiled`), so neither the model nor the operator reads raw files.

[#credential-model]
== Credential model

[#credential-lanes]
=== Lanes after the change

`PM-CRED-1` keeps its two lanes but moves the providers: in the native variant `git` transport, GitHub and GitLab are *Token Lane* providers; the *System Lane* shrinks to the CLI variant. Token-lane rules apply unchanged: the operator enters every secret through `pm-mcp operator credentials` (`PM-CRED-4`), the secret goes only to the origin of the entry's `url` (`PM-CRED-5`), and it never reaches a subprocess.

[cols="2,3,3,2"]
|===
|Credential key |Agent identity |Stored secret |Used for

|`github`
|GitHub App installed on the organisation or repository (recommended); alternatively a fine-grained PAT of a dedicated machine user
|App: `client_id`, `private_key` (PKCS#8 PEM), optional `installation_id` (else discovered per repository owner through `GET /repos/{o}/{r}/installation`); PAT: `token`
|REST and GraphQL; git HTTPS transport to the same host (`x-access-token:<installation token>`)

|`gitlab`
|Project access token (bot user `project_<id>_bot_…`) or group access token; on gitlab.com Free a PAT of a dedicated service user
|`token`, `expires_at`
|REST; git HTTPS transport (`oauth2:<token>`)

|`git-https`
|Any other HTTPS remote (Gitea, Bitbucket, self-hosted without provider module)
|`token` or `basic`
|git HTTPS transport only
|===

The credential file schema (link:../specification/store-schemas/12-machine-stores.adoc#credential-store[Store Schemas § Credential Store], closed properties per Z3-18) gains `auth_type: github_app` with `client_id`, `private_key`, optional `installation_id`, and an optional `expires_at` for tokens; `pm-mcp operator credentials status` reports `expiring` within 14 days of `expires_at` (a new status value next to `complete`, `incomplete`, `not_found`, `verified`, `unverified`). `verify` calls `ci.whoami` and reports the identity and its permissions on the enrolled repository without revealing the secret.

Why a GitHub App over a fine-grained PAT: installation tokens live one hour and are minted per repository and per permission set; the App has its own `[bot]` identity that is visibly not the operator; fine-grained PATs cannot read the Checks API, which `ci.checks` needs.

Minimal permissions of the App (repository scope): `contents: write` (push), `pull_requests: write`, `checks: read`, `actions: read` (runs and logs), `statuses: read`, `issues: write` (issue verbs, labels), `metadata: read`; `administration: read` only if the ruleset read for `merge_queue_enforced` needs it (spike). The server mints each installation token with the narrowest permission set of the operation class (read-only for query classes).

[#short-lived-tokens]
=== Short-lived derived tokens

`PM-CRED-5` forbids caching a secret beyond one request. An installation token is not the stored secret but a derivative that expires within the hour; minting one per request costs a JWT signature and a round trip and burns the App's token-creation rate. Proposal (<<z2-13>>): the stored secret (the App key) keeps the per-request rule; installation tokens are held in memory only, per `(repository, permission set)`, until 5 minutes before their expiry, registered with the redactor, never persisted, never exported, and dropped on runtime stop and on credential change.

[#identity]
=== Commit identity and trailer

The native variant does not read `user.name` and `user.email` from the operator's git configuration by default. Options are in <<z2-14>>; the recommendation is:

* *Author*: the operator, from `local-config.json` `commit_identity{name, email}` (operator key, default: the global git `user.name`/`user.email` read once at `pm-mcp operator enrol` and written into `local-config.json`, never re-read silently). The operator is responsible for the change (CLA, DCO, blame).
* *Committer*: the agent identity (`<app-slug>[bot] <<id>+<app-slug>[bot]@users.noreply.github.com>` for a GitHub App, the token's bot user for GitLab), taken from `ci.whoami` and recorded per project in the derived facts.
* *Trailer*: `commit_trailer` unchanged (`local-config.json`), injected server-side (Stage 3 of `git.commit_and_push`).

[#cli-credentials]
=== Credentials of the CLI variant

The CLI variant runs the operator's `git`, `gh` or `glab` with the operator's ambient authentication, *by design*. Injecting the agent token into the job (`GH_TOKEN`, `GITLAB_TOKEN`, a `GIT_ASKPASS` helper) was considered and rejected: the value would be readable by every descendant of the job, including repository hooks, and by same-user processes through `/proc/<pid>/environ`, which breaks `PM-CRED-5`. Consequences:

* Selecting `cli` for a family is an operator decision that names the operator's identity for that family; `pm-mcp operator config` shows this on the terminal before it writes the key, and every CLI job's audit record carries `identity: operator_ambient`.
* The job environment table gains a `ci` and a `git` (CLI variant) row set (<<z2-16>>): `HOME` (configuration discovery), `SSH_AUTH_SOCK` (git network, only when the remote is SSH), `GH_CONFIG_DIR` and `XDG_CONFIG_HOME` (enrolment provenance), and the non-interactive guards `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, `GH_PROMPT_DISABLED=1`, `GH_NO_UPDATE_NOTIFIER=1`, `NO_COLOR=1`, `GIT_OPTIONAL_LOCKS=0` for read-only calls. Token variables stay forbidden.
* Landlock write set additions for CLI jobs: the `gh`/`glab` configuration directory (token refresh writes `hosts.yml`); `known_hosts` stays read-only (an unknown host fails with `host_key_unknown`, no `accept-new`).
* Free text goes on `stdin`: `git commit -F -`, `gh pr create|edit|comment --body-file -`, `gh issue create|comment --body-file -`, `gh api graphql --input -`. For `glab`, `stdin` forms are not confirmed for `mr create`, `mr note` and `issue note`; the CLI variant sends those through `glab api … --input -` if the spike confirms it, otherwise the operation is `unsupported_by_variant` and the family needs the native variant.

[#sandboxing]
== Sandboxing

[#sandbox-native]
=== Native operations

A native operation runs inside the runtime process: no argument vector, no environment, no Landlock ruleset, no process group. What it can do is bounded by the code, not by a sandbox:

* It writes only inside the enrolled project roots and their linked worktrees (`PM-SEC-2` path checks on every path the operation derives, including `worktrees/<id>/gitdir` targets).
* It talks only to the origin of the credential entry (`cui-http` origin pinning; JGit transport through a connection factory that refuses any other host, <<remote-integrity>>).
* It never runs a program on its own. JGit's process hooks (`FS.runInShell`, `FS.runHookIfPresent`, filter-driver execution) are routed through a `pm-mcp-git` subclass of JGit's `FS` whose process methods delegate to the `JobRunner` (<<hard-hooks>>). A repository configuration value can therefore not start an unconfined process in the runtime.
* It reads configuration through an allowlist: from the repository configuration and the user's global configuration only content-shaping keys (`core.autocrlf`, `core.eol`, `core.safecrlf`, `core.excludesFile`, `core.hooksPath`, `core.ignoreCase`, `core.precomposeUnicode`, `filter.<driver>.*`, `lfs.*`, `submodule.*`, `remote.<name>.url|pushurl|fetch`, `url.<base>.insteadOf|pushInsteadOf`, `branch.<name>.*`, `extensions.*`, `init.defaultBranch`); everything else (`credential.*`, `core.sshCommand`, `core.fsmonitor`, `http.*` proxies, `include.*` outside the repository) is ignored. A `http.proxy` need is an operator setting of `machine-config.json`, not a repository value.
* *Adjusted by round-4 D14 (2026-10-01)*: `machine-config.json` gets the closed object `proxy` (`https_proxy` without credentials, `no_proxy`); authenticated proxies are deferred (link:../later-improvements.adoc#_l_8_authenticated_proxies[Later Improvements L-8]).

[#hard-points]
== Hard points of the native path

[#hard-worktrees]
=== Linked worktrees

JGit opens and operates linked worktrees since 7.0 but cannot create, list, remove or prune them. The on-disk format is stable and documented (`gitrepository-layout(5)`, `git-worktree(1)`):

* `add`: create `$GIT_COMMON_DIR/worktrees/<id>/` with `gitdir` (absolute path of `<wt>/.git`), `commondir` (`../..`), `HEAD` (symbolic ref to the new branch, or detached SHA), then write `<wt>/.git` (`gitdir: <common>/worktrees/<id>`), create the branch ref under the ref lock, and check out into the new tree with JGit (building its `index`); `locked` while the add is in progress, removed on success.
* `list`: enumerate `worktrees/*`, read `gitdir`, `HEAD`, `locked`, flag `prunable` when the `gitdir` target is missing.
* `remove`: refuse when dirty unless the caller is the D74 re-check after a timeout; delete the tree, then the admin directory; report `partially_removed` when either remains.
* `prune`: delete admin directories whose `gitdir` target is missing and which are not `locked`.

Recommendation (<<z2-7>>): implement the lifecycle natively in `pm-mcp-git` and prove it with differential fixtures against the CLI (`git worktree list --porcelain`, `git status`, `git fsck` must accept every tree the native code produces, and native code must operate every tree the CLI produces). `extensions.worktreeConfig` in a repository marks the `worktree` family as `capability_missing` until the fixture set covers per-worktree configuration.

[#hard-hooks]
=== Repository hooks

Running hooks keeps the project's own guarantees (secret scanners, formatters, commit-message linters); not running them silently diverges from what the developer's own commits go through. JGit's own hook support covers four hooks and runs them unconfined, so `pm-mcp-git` invokes hooks itself at the points git does: `pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit` around `stage-and-commit`; `pre-push` before `push` (ref lines on `stdin`); `post-checkout` after `worktree-add` and `switch`; `post-merge` after `fast-forward`; `pre-rebase` and `post-rewrite` around `rebase`.

Policy (<<z2-17>>):

* Hooks run as confined `hook` jobs (<<sandbox-subprocesses>>) with the budget of the hook-running class.
* Hook files are pinned at enrolment like wrapper files (`pinned_files` with digests, link:../specification/job-runtime.adoc[Job Runtime] § Verify-Not-Resolve); `core.hooksPath` is resolved and pinned too. A changed or new hook refuses with `hooks_changed` naming the paths and the re-baselining `pm-mcp operator enrol` command. Model-writable hook files thus never execute unreviewed (C5).
* A hook that only exists in the operator's global template or `core.hooksPath` outside the repository is pinned the same way (enrolment captures the resolved path).
* A failing `pre-commit` or `commit-msg` hook yields `hook_failed{hook, exit, output_tail}` → `git.commit-fix`; a failing `pre-push` hook yields the push outcome `rejected_by_hook`. There is no bypass (`--no-verify` has no contract input).

[#hard-signing]
=== Commit signing

* A GitHub App cannot register a GPG or SSH signing key; commits it pushes from local objects are never "Verified". Commits created through `createCommitOnBranch` are signed by GitHub, but that API builds commits from file contents against an expected head, which does not fit locally built commits, rebases, hooks and the footprint check.
* GitLab does not verify commits by a project-token bot user either (unverified in this research).
* Therefore: *unsigned by default* in the native variant. The derived fact `signed_commits_required` (GitHub rule `required_signatures`, GitLab push rule `reject_unsigned_commits`) turns a push into `capability_missing{reason: signing_required}` unless the operator selects the CLI variant for the `commit` and `network` families, which signs with the operator's own configuration. Native SSH signing with an agent-owned key (JGit 7.1+ `SshSigner`, MINA sshd in native) is a later option once spike 12 passes and a provider can attribute the key to the agent identity (<<z2-15>>).

[#hard-filters]
=== `.gitattributes` filters, LFS, submodules and unsupported repository features

* *Filter drivers* (`filter.<x>.clean|smudge`): executed as confined `filter` jobs. `filter.<x>.process` (long-running protocol) is not supported by JGit; a repository whose effective attributes name a driver with only `process` is `capability_missing{reason: filter_process}`.
* *LFS*: JGit's built-in LFS in-process, authenticated with the provider token (GitHub and GitLab LFS endpoints accept it); `lfs.url` pointing to another origin is `capability_missing{reason: lfs_foreign_origin}`.
* *Submodules*: supported when every submodule URL resolves to the same provider origin (one credential); otherwise `capability_missing{reason: submodule_foreign_origin}`. `submodule deinit` is never used (JGit issue #293).
* *SHA-256 object format*, *partial clone* (promisor remote), *sparse checkout*, *split index*: `capability_missing` with the feature name.

All of these are local derivations of `git_native_capability` (<<derived-git-facts>>), recomputed when `.gitattributes`, `.gitmodules` or the repository configuration changes (`input_digest`).

[#hard-ssh]
=== SSH remotes and `known_hosts`

The native variant speaks HTTPS only. A remote `git@github.com:o/r.git` or `ssh://git@gitlab.example.com/o/r.git` of a known provider host is mapped to its HTTPS form (`https://github.com/o/r.git`) for transport; the configured remote is not changed. The mapping is exact for github.com, gitlab.com and hosts whose `ci_provider` is established; any other SSH remote is `capability_missing{reason: ssh_only_remote}` (CLI variant). Reasons: JGit's SSH is in transition (JSch removed 2026-09-11, MINA sshd without complete native metadata, agent support through JNA), and HTTPS keeps one credential per provider. `known_hosts` handling therefore only concerns the CLI variant (<<cli-credentials>>).

[#hard-performance]
=== Large repositories and memory

JGit status on very large working trees is slower than C git (no fsmonitor, index timestamp caveats). Budgets remain those of the operation classes; an in-process operation observes its budget through JGit's cooperative cancellation and reports `timed_out` like a job (<<z2-28>>). JGit's `WindowCache` is configured small (packed-git limit and delta-base cache in the low megabytes) so that the idle RSS bound of `PM-TECH-3` holds after an operation; spike 6 measures both. A project where the native variant is too slow is served by the operator selecting the CLI variant for the `read` family; there is no size threshold key.

[#remote-integrity]
=== Remote URL integrity

A repository controls its `remote.<name>.url`, `pushurl`, and the `url.<base>.insteadOf` rewrites. Without a check, a model-edited `.git/config` could redirect a push, together with the agent token, to another host. The native transport resolves the effective push and fetch URL (with rewrites), requires `https` (after the SSH mapping), and requires the origin to equal the credential entry's `url` origin; otherwise it refuses with `remote_origin_mismatch` and an audit record. This is the git-transport form of `PM-CRED-5` (<<z2-19>>).

[#hard-bot-identity]
=== Review bots and the agent identity

Moving pull-request authorship and trigger comments to a `[bot]` identity changes who the review bots see. Some bots ignore comments from other bots or only obey triggers from users with write access. Spike 9 verifies CodeRabbit, Sourcery and `cuioss-review-bot`. If a bot ignores App-authored triggers, its registry record gains `trigger_identity: operator`, and the trigger for that bot is either sent through the CLI variant of the `review` family (operator identity, opt-in) or the bot is configured to review automatically on push (`trigger_semantics: auto_on_push`). Required workflows triggered by pushes and pull requests of an installation token do run (unlike `GITHUB_TOKEN` pushes); spike 10 confirms it for the fixture repository.

[#z2-1]
=== Z2-1 Native implementations by default, CLI as operator variant
