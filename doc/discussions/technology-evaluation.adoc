== Quarkus MCP Server

=== Overview

The https://github.com/quarkiverse/quarkus-mcp-server[Quarkus MCP Server] extension (Quarkiverse, Apache 2.0) implements the MCP server side itself; it does not build on the official Java SDK. Server features are CDI beans with annotated business methods (`@Tool`, `@Resource`, `@ResourceTemplate`, `@Prompt`), with programmatic managers for registering them at runtime.

=== Protocol support

* The 2.0 line implements the stateless `2026-07-28` revision and serves stateful `2025-11-25` clients at the same time: "The server supports both stateful and stateless clients simultaneously (protocol version `2026-07-28`)." (https://docs.quarkiverse.io/quarkus-mcp-server/dev/release-notes.html[release notes]).
* Features include `server/discover`, per-response `serverInfo` and `resultType`, multi round-trip requests, cache control, subscriptions, sampling, elicitation, progress, cancellation, roots and structured content.
* The Quarkus team published https://quarkus.io/blog/mcp-stateless/["MCP goes stateless, and Quarkus already implements it"] for the `2026-07-28` release.

=== Transports

stdio (`quarkus-mcp-server-stdio`), Streamable HTTP and legacy SSE (`quarkus-mcp-server-http`), and WebSocket.

=== Extensions

* A generic extension API — `@McpExtension`, `@McpExtensionSetting`, `@McpExtensionMethod` — lets an application declare an extension in the capabilities and handle its own JSON-RPC methods (https://docs.quarkiverse.io/quarkus-mcp-server/dev/guides-mcp-extensions.html[MCP Extensions guide]). The guide names Skills and Tasks as typical uses.
* It was added in response to https://github.com/quarkiverse/quarkus-mcp-server/issues/1000[quarkus-mcp-server#1000], which requested exactly what SEP-2640 needs. The issue is closed with milestone 2.1.0; 2.1.0 is not yet released.
* *Skills*: no built-in support; implementable on top of the extension API.
* *Tasks*: built-in support is proposed in draft https://github.com/quarkiverse/quarkus-mcp-server/pull/1013[PR #1013] (`@Task`, `TaskContext`, `TaskManager`), under rework after review.

=== Security, developer experience, native image

* Integrates with Quarkus Security and OIDC; DNS-rebinding protection for HTTP transports; OIDC security failure handler.
* Dev mode with live reload, a Dev UI for exercising tools and resources, and the `McpAssured` test library covering all transports, including a stdio test client.
* Quarkus native executables start in milliseconds with a small memory footprint.

=== Risks

* Quarkiverse extension, not an official MCP SDK; outside the MCP SDK tiering and conformance listing. Maintenance is concentrated in a small group of maintainers.
* SEP-2640 support rests on the 2.1 extension API, which is not yet released.
* Tasks support is a draft.

== Official MCP SDKs

[cols="1,1,3"]

|1

|Python
|1

|1

|3

Python::
The fastest route to a working server, since the logic exists already. It keeps the codebase in the language that produced the current architecture's problems (prose-driven scripts), lacks a single-binary front end, and has no first-party security stack.

TypeScript::
Strong for LSP work and closest to the reference SDK, but adds an ecosystem the operator does not want to maintain.

Go and Rust::
Best delivery characteristics (small static binaries, small images). Rust's SDK is the most complete. Both mean a new language and a rebuilt security layer.

C#::
Technically among the most complete SDKs; no alignment with the existing codebase or expertise.

Java / Quarkus::
Supports the current protocol, provides the extension API SEP-2640 needs, gives a native front end and a JVM daemon from one codebase, and reuses the first-party cuioss security libraries. Its gaps — Skills, Tasks — are either implementable by PM-MCP (Skills) or not required by the design (Tasks).

== Python runtime options

A Python runtime is needed to run plan-marshall's existing scripts during migration. The options below were evaluated when PM-MCP was planned as a distroless container image. The target design has since settled on script jobs with the host's Python, run by the native daemon on the host (xref:../requirements/09-technology.adoc[Native binary]).

[cols="1,3,1"]
|===
|Option |Assessment |Verdict

|CPython in the image, called as a subprocess
|Full compatibility with the existing scripts; process isolation; simple. Requires an interim image with CPython, `git` and `gh`; the distroless target is reached only when the last script is ported.
|Open

|Scripts through the host build server
|Scripts run on the host as today, verified like `marshalld` does now; the PM-MCP image is distroless from the start. Requires the host build server on every machine during migration, a script job type in the job contract, and a low-latency channel for frequent short calls.
|Open

|GraalPy embedded in the JVM
|Python 3.12-compatible, embeddable via the GraalVM polyglot API, can be built into native executables. No Quarkus extension found; C-extension packages and native image builds add friction.
|Rejected for now

|Rewrite in Java
|The end state for PM-MCP's own logic; removes the Python runtime from the image.
|Incremental, per migration stage
|===
