Where a *Decision* line differs from the recommendation or the proposal body, the Decision line holds. All import parts (the one-way import, `adopt-project`, `import-legacy`, import receipts, the import mapping, and Z3-17) are withdrawn by the operator decision of 2026-09-27 that `PM-MCP` imports nothing from `plan-marshall` (clean cut) and are kept only as a record of the discussion.

A clean-slate proposal for the persisted files of `PM-MCP`: which configuration exists at all, where it lives, who writes it, how every file is versioned and validated, and how `plan-marshall` data enters through the one-way import (withdrawn). It collects the open items D63 (configuration versioning), D64 (enrolment schema), D79 (stores without schema), D80 (lesson record) and D84 (entry record), together with the configuration shapes the specifications defer to "the later clean-slate configuration redesign". Nothing here is part of the target design until the decisions in <<decisions>> are taken and carried into the specifications.

== Overview and principles

Operator direction: `PM-MCP` stores and configuration are designed from a clean slate. `plan-marshall` shapes matter only as input of `pm-mcp operator adopt-project` and `pm-mcp operator import-legacy` (withdrawn: `PM-MCP` imports nothing, clean cut 2026-09-27). Logic, validation and derivation belong in the server. Before 1.0 there are no deprecation cycles and no compatibility shims (project `CLAUDE.md`).

[cols="1,4"]
|===
|Principle |Meaning for stores and configuration

|C1 Server-side first
|A value the server can observe, derive or bound is never configured. Files hold decisions only a human can make.

|C2 Fewer knobs
|Every key must name a legitimate reason why one project chooses differently from another (<<removal>>). An option whose only sensible value is fixed becomes a constant. An option that only weakens a guarantee is removed.

|C3 Sparse configuration
|Configuration files hold only deviations from the compiled and derived defaults. The server computes the effective configuration and reports the source of every value.

|C4 One owner per file
|Every file has exactly one owner class: *team* (git-tracked, shared through the repository), *operator* (machine-local, written through the operator channel), or *server* (machine-local state). No file mixes owner classes, and no key exists in two owner classes.

|C5 Nothing the model can write decides execution
|Kept from `PM-EXT-6`: binaries, argument vectors, scripts and the origins tokens are sent to come only from operator-owned files.

|C6 One file, one schema, one version
|Every persisted JSON file and JSONL record carries `format_version`; a reader accepts exactly the versions the binary declares and refuses any other with a named reason.

|C7 Identities, not paths
|Machine-level records are keyed by `project_id` (link:../specification/identifiers.adoc[Identifier Registry]), never by a project root path.

|C8 No bookkeeping in team files
|Binary versions, fingerprints, migration ledgers and "offered" lists never land in git-tracked files, where they produce commit churn and merge conflicts between developers on different binaries.
|===

== Current state

The current specifications (link:../specification/store-schemas.adoc[Store Schemas], link:../specification/filesystem-layout.adoc[Filesystem Layout], link:../specification/domain-extensions.adoc[Domain Extensions] § Three-Way Configuration Split and § Systematized `marshal.json` Upgrades) define a three-way split: git-tracked `.marshall/marshal.json` (top-level shape of `plan-marshall`'s `marshal.json`), operator-owned `enrolments.json` and `machine-config.json`, and server state under `<PM_MCP_BASE>`. Problems found:

. *One file, four concerns*: `marshal.json` mixes team policy (base branch, providers), operator posture (`interaction_mode`, `*_without_asking`), derived data (`build.map` seed, domain activation) and server bookkeeping (`provisioned_version`, `config_seed_fingerprint`, `schema_version`, `applied_migrations`, `offered_steps`). `provisioned_version` changes whenever a developer with a different binary reconciles, so the tracked file churns between machines.
. *Open schema*: `plan`, `skill_domains`, `providers`, `build` and `orchestrator` are declared only by description, while § Five-Phase Reconciliation promises "undeclared keys are refused". The schema cannot enforce what it does not declare.
. *Materialised defaults*: because defaults are copied into the file, the design needs write-once seeding, `syncDefaults`, `offered_steps`, a seed fingerprint, `stepsSort` and `normalizeKeys`. All of this exists only to keep a copy of compiled defaults consistent.
. *Three versioning schemes*: server stores use `format_version` with forward migration on startup (`PM-IMPL-2`); `marshal.json` uses `system.schema_version` with the `ConfigMigrationCommand` chain whose first command `M001` exists only to read legacy files (`PM-EXT-7`); credential files are unversioned. The migration chain carries `plan-marshall` history (`M002_rename_retired_step_keys`, `M004_split_enabled_bots…`) into a system that never had those shapes.
. *Legacy knobs carried over unexamined*: most `plan.*` keys are copied from `plan-marshall`, including options whose only purpose was plan-marshall behaviour (`use_worktree`, `branch_strategy: direct`, `commit_and_push: false`, `q_gate_validation: off`, `admin_merge_on_stuck_state`) or that duplicate server logic (wait timeouts, iteration caps, prune thresholds).
. *Deferred shapes*: `always_on`/`file_globs` overrides, `project_skills`, `active_profiles`, `outline_skill`, `workflow_skill_extensions`, the lane selection mode, forced escalation, the recipe threshold, per-deliverable verification verbs and the cost table are all deferred to this redesign.
. *Enrolment gaps (D64)*: `enrolments.json` lacks fields other specifications rely on: canonical and discovery argument templates, CLI provider `verify_command` overrides, `project_script` worker binding and argument schema (`PM-EXT-5` requires the schema). `allowed_goals` duplicates the templates. One file for all projects means one tampered or unparsable entry blocks every project.
. *Stores without schema (D79)*: the epic ledger `status.json`, queue rows, `landings.jsonl`, `metrics.json`, `build-timings.json`, `install-records.json`, `effort-ladder.json`, `state/runtime.json` and `state/operator-auth.json` have prose only. The job journal and `discovery-cache.json` have no location. `.marshall/recipes/` is used by Domain Extensions but missing from the layout and the `.gitignore` partition.
. *Path keys*: `build-timings.json` and `machine-config.json` → `derivation_resolvers` are keyed by project root; a moved checkout loses its learned budgets and resolver settings.
. *Name clash*: the git-tracked epic header `.marshall/orchestrator/<epic_id>/status.json` and the epic FSM store `epics/<epic_id>/status.json` share a name but not a schema.
. *Retention in the wrong owner*: `system.retention` is git-tracked, but it governs machine-local stores (archived plans, job logs, lessons) that no other clone sees.
. *Lesson format (D80)*: the `key=value` header with single-line JSON values is a private grammar; there is no body revision history and no source list, and applying a lesson moves its file into a plan directory, which in turn needs the carry-back veto on plan deletion.
. *Entry record (D84)*: `entry` duplicates `scope_type`; `client_version`, `client_session_id`, `from_epic` and `environment_match_tier` are optional, so "not recorded" and "host provides none" are indistinguishable; `workspace_root` duplicates the enrolled project root.

== Target model

[#config-model]
=== Configuration model

==== Files and ownership

[cols="2,1,2,3"]
|===
|File |Owner |Writer |Content

|`.marshall/config/project.json`
|team
|project-setup workflow (validated links), committed edits
|Repository and collaboration policy: base branch, branch prefix, merge method, CI provider override, integrations (Sonar coordinates), review bots and review currency.

|`.marshall/config/workflow.json`
|team
|project-setup workflow, committed edits
|Plan workflow policy: minimum planning lane, refine policy, verification verbs, optional finalize steps and their parameters, effort levels (target-neutral).

|`.marshall/config/domains.json`
|team
|project-setup workflow, committed edits
|Overrides of derived domain detection: forced enable/disable, `always_on`, `file_globs`, disabled profiles.

|`.marshall/config/build-map.json`
|team
|`setup.seed-build-map` (write-once), `customize_routes`, `setup.reseed-build-map`, committed edits
|The file-to-build route table (today `build.map`). Separate because it is seeded, reseeded and drift-checked on its own cycle and is by far the largest block.

|`<PM_MCP_BASE>/projects/<project_id>/local-config.json`
|operator
|`pm-mcp operator config --project`, operator-channel links (elicitation) of the setup workflow
|Operator posture and machine-local bindings of one project: continuation default, merge consent, recipe auto-route, interaction mode, language, commit trailer, effort ladder, envelope budget override, resolver enablement, retention. Replaces `effort-ladder.json` and `run-configuration.json`.

|`<PM_MCP_BASE>/machine-config.json`
|operator
|`pm-mcp operator config`
|Machine resources and bounds (build slots, LSP pool, drain, escalation cap, progress wait, audit rotation) and `project_defaults`, the machine-wide defaults for `local-config.json` keys.

|`<PM_MCP_BASE>/enrolments/<project_id>.json` (+ `.hmac`)
|operator
|`pm-mcp operator enrol`
|Execution bindings of one project (<<enrolment>>).
|===

Resolution of an effective value: team keys resolve *team file → derived value → compiled default*; operator keys resolve *`local-config.json` → `machine-config.json` `project_defaults` → compiled default*. No key is resolvable from both chains. The server publishes the effective configuration as `pm://project/config` with the source of every value (`team`, `derived`, `operator`, `machine_default`, `compiled`) and every validation finding, so neither the model nor the operator reads raw files.

A project-local finalize step or recipe is split along C5: the team file names the step (id, order, lane), the enrolment binds the script (path, digest, interpreter, worker binding, argument schema), and the step is offered only when both agree.

[#enrolment]
==== Enrolment (D64)

One file per project, `<PM_MCP_BASE>/enrolments/<project_id>.json`, with its own HMAC sidecar `<project_id>.json.hmac` and lock `locks/enrolment-<project_id>.lock`. A tampered or unreadable enrolment blocks only its project. The project index is the directory listing; `project_root` uniqueness across files is checked at every enrolment write and at runtime start (`enrolment_root_conflict`).

[#versioning]
=== Versioning and validation rules

Proposal (D63): *no migration chain before 1.0.* Every persisted file carries `format_version`; a mismatch is refused with a named reason; legacy configuration enters only through `adopt-project`.

. *Envelope*: every JSON root object and every JSONL record carries `format_version` (positive integer, one sequence per file kind). This now includes the four team configuration files, `local-config.json`, enrolments and credential files. Exempt: Markdown documents (their structure is checked by their parsers), plain-text logs, OS primitives, the raw HMAC key.
. *Accept exactly one*: before 1.0 a binary accepts exactly the current `format_version` of each kind. A reader returns `absent`, `unreadable` (including a missing `format_version`), `format_outdated{file, found, current}` or `format_newer{file, found, current}`. No reader tolerates an older shape (`PM-WATCH-GEN-56`).
. *Refuse, never rewrite*: an outdated or newer file is never modified. For a scope store the scope raises the `blocked` condition with the operator command; for team configuration every plan start and phase handshake refuses with `config_format_outdated` naming the file; for operator files the CLI names the file and the changed keys.
. *Release discipline*: a `format_version` bump is listed in the release notes with the changed keys. Scope stores of in-flight plans follow the drain rule: `pm-mcp drain` reports live scopes, and the operator finishes them before upgrading or accepts that they stay readable only through the old binary. Sparse configuration keeps a manual update to a few lines.
. *Validation on every read*: team files are validated against closed schemas (`additionalProperties: false` at every level) and the server-side rules of the key catalogue on every effective-configuration computation; findings are published in `pm://project/config`. An undeclared key is a finding (`unknown_config_key`), never silently kept.
. *Snapshot of in-flight plans*: kept from `PM-EXT-7`: the execution manifest records `config_hash`, computed over the effective configuration (values plus sources plus the digest of the compiled defaults), not over file bytes; a difference raises `config_drift` (`adopt`/`keep`).
. *Removed*: `system.schema_version`, `baseline_version`, `applied_migrations`, `provisioned_version`, `config_seed_fingerprint`, `offered_steps`, `ConfigMigrationCommand` (`M001`–`M004`), `syncDefaults`, `stepsSort`, `normalizeKeys`, `MINIMUM_SUPPORTED_SCHEMA_VERSION`, `unsupported_legacy_config_epoch`, the `ConfigMigrationChainTest`, and the startup forward migration of `PM-IMPL-2`.
. *At 1.0*: one forward-migration mechanism for every file kind (ordered steps per kind, floor = oldest supported version, removal trigger recorded, `PM-WATCH-GEN-57`), decided then with the knowledge of the actual format churn.

Evaluation of the proposal:

[cols="1,3"]
|===
|Aspect |Assessment

|For
|No code whose only input is `plan-marshall` history. One rule for every file instead of three. No git-tracked bookkeeping. The reconcile pipeline shrinks to validation plus explicit reseed, which removes the source of `PM-WATCH-EXT-21`/`-22` hazards (restored steps, expanded curated maps). Import becomes a plain mapper with a removal trigger.

|Against
|A format bump strands in-flight plans of the previous binary. Mitigated by the drain rule and by keeping scope-store bumps rare before 1.0; the alternative (a migration step per bump) is exactly the shim the pre-1.0 policy forbids.

|Against
|Developers on different binaries share team files. A newer binary's `format_version` is refused by an older one (`format_newer`), which is the correct signal; sparse files make simultaneous format changes rare.

|Risk
|Operator-edited files (credentials) now need `format_version`; the operator CLI writes it, and a hand-written file without it is refused with a message naming the field.
|===

== Decisions

Each decision lists the question, the options, the recommendation and the documents that change if it is taken.

=== Z3-1 Split of `.marshall/marshal.json`

* *Question*: One configuration file or several?
* *Options*: (a) keep one file with closed sections; (b) four purpose files `.marshall/config/{project,workflow,domains,build-map}.json`; (c) two files (`marshal.json` + `build-map.json`).
* *Recommendation*: (b). Each file has a different edit cadence and writer path (build map on its seed/reseed cycle, domains on detection, workflow on team decisions), a smaller merge-conflict surface, and its own `format_version` and validation outcome.
* *Affected*: Filesystem Layout (tree, `.gitignore` partition), Store Schemas § Project Configuration Store, Domain Extensions § Three-Way Split, `PM-EXT-6`, every `marshal.json` reference (94 occurrences), setup staging set.
* *Decision*: Operator 2026-09-28: (b) four purpose files `.marshall/config/{project,workflow,domains,build-map}.json`.

=== Z3-2 Sparse configuration and server-computed effective configuration

* *Question*: Do files hold materialised defaults or only deviations?
* *Options*: (a) materialised defaults with write-once seeding and `syncDefaults` (current); (b) sparse overrides, effective configuration computed by the server and published with per-key source.
* *Recommendation*: (b). Removes `syncDefaults`, seed fingerprint, `stepsSort`, `normalizeKeys` and the restored-step hazards (`PM-WATCH-EXT-22`); default changes of a new binary reach every project, while in-flight plans stay protected by the manifest snapshot (Z3-11). `pm://project/config` makes the effective values visible.
* *Affected*: Domain Extensions § Systematized Upgrades (largely removed), `PM-EXT-7`, MCP Tools (new resource), `PM-WATCH-EXT-21`/`-22`, `PM-WATCH-STORE-13` (the pinned defaults move to the compiled table).
* *Decision*: Operator 2026-09-28: (b), as applied: sparse files and a server-computed effective configuration published with per-key source; two exceptions keep materialised content: the build map seed (write-once, explicit reseed) and the copies of the default `.pmwf` units, for which setup offers a three-way diff against the new default.

=== Z3-3 Team policy versus operator posture

* *Question*: Where do posture keys live (autonomy, interaction, language, trailer, ladder, retention)?
* *Options*: (a) all in the git-tracked file (current, as `plan-marshall`); (b) a per-project operator file `PS/local-config.json` with machine-wide defaults in `machine-config.json`; (c) machine-wide only.
* *Recommendation*: (b). Posture is a property of the person and machine, not of the repository; per-project override is needed because one operator treats repositories differently. Merges `effort-ladder.json` and `run-configuration.json` into one file.
* *Affected*: Filesystem Layout § Per-Project Machine Store, Store Schemas (new schema), Dispatch & Effort § Effort Ladders, Workflow DSL (commit trailer), Domain Extensions (setup states `effort-ladder`, `project-settings`), Timeouts § Configuration Keys.
* *Decision*: Operator 2026-09-28: (b) per-project `local-config.json` with machine-wide defaults in `machine-config.json` `project_defaults`; adjusted by Z2: the integration variants and the commit identity are per project only and have no machine-wide default.

=== Z3-4 Remove options that weaken guarantees

* *Question*: Are options kept whose only effect is to disable a guarantee?
* *Options*: (a) keep with safe defaults; (b) remove them.
* *Recommendation*: (b): `use_worktree`, `branch_strategy: direct`, `commit_and_push`, `escalation`, `revalidation`, `q_gate_validation: off`, forcing the light lane, lowering `confidence_threshold`, `admin_merge_on_stuck_state`, `re_review_on_timeout: proceed`, `drop_review_on_scope_gate`, `auto_rebase_threshold`, and disabling mandatory finalize steps. Each has a server-derived or operator-decision path for the rare legitimate case (local-only outcome from provider absence, extensions, merge authorizations).
* *Affected*: Phase Workflows (lanes, Q-Gate, finalize roster, merge barrier), State Catalogue (`realized_state` cause `disabled`, `outline.review` bypass rows), Store Schemas § References (`disabled` cause), Job Runtime (non-worktree path), Workflow DSL (`git.commit_and_push` push modes), `02-workflow`.
* *Decision*: Operator 2026-09-28: (b) remove them.

=== Z3-5 One continuation policy instead of five auto-continue gates

* *Question*: How is session autonomy configured?
* *Options*: (a) the five `*_without_asking` flags plus `lane_selection`; (b) the existing per-plan `continuation_policy`, defaulted from `local-config.json`.
* *Recommendation*: (b). One mechanism already exists in the status store and the operator channel; two would conflict.
* *Affected*: Phase Workflows § Workflow Settings Resolution, State Catalogue (auto-continue branches), Domain Extensions (`setup.project-settings`), Store Schemas § status `continuation_policy`.
* *Decision*: Operator 2026-09-28: (b) the per-plan `continuation_policy`, defaulted from `local-config.json`.

=== Z3-6 Tuning knobs become compiled constants

* *Question*: Stay configurable: recipe threshold, prune thresholds, refine confidence, iteration caps, step wait timeouts, preference recurrence, raw-input byte cap, rate-window floor, lock-wait report threshold, pending-entry age?
* *Options*: (a) configurable with defaults; (b) compiled constants in the Timeouts table or the owning specification.
* *Recommendation*: (b). They calibrate server algorithms; per-project tuning makes metrics incomparable across projects (`PM-MIG-5` triggers) and adds untestable combinations.
* *Affected*: Timeouts (rows move to `fixed`), Phase Workflows, Domain Extensions § Tier-1 Routing, Store Schemas § Machine Configuration.
* *Decision*: Operator 2026-09-28: (b) compiled constants.
