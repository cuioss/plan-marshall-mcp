== Operator direction

*Z5-0* (operator 2026-09-29): complete the workflow model on paper. Resolve every contradiction, routing gap, unregistered decision and "_(to be specified)_" marker in `workflow-dsl.adoc`, `phase-workflows.adoc`, `state-catalogue.adoc` (and `hypermedia-format.adoc` where it defines workflow semantics) before implementation.

*Z5-A* (operator 2026-09-29), *the process enforces itself*: no operator questions during a plan; gates are process conformance, not security. Every blocking condition gets a bounded self-remedy and then a *defined fallback* continuation to an end. Plan outcomes:

* `merged`: the work landed.
* `handed_back`: the work is delivered as an open pull request or branch; the gaps are documented in a PR comment and label; the post-run band and the archive still run.
* `returned`: the planning result only; nothing was implemented.

Operator influence is deliberate: `pm-mcp operator waive <plan> <gate> --reason "…"` (and `unwaive`), operator channel only, audited, recorded in the landing record and the pull request, settable at any time before the gate is evaluated (at plan start or during the run). Once the fallback has been taken it is too late: a human merges the open pull request, or a new plan continues. A waiver either declares a gate met or *raises* a budget (`--raise <budget>=N`). Closed waivable list: review evidence (a bot did not review, re-review timeout), a named failing CI check, the Sonar quality gate, open findings of a class after triage, Q-Gate findings, and the loop/fix, retry and spend budgets (raise). Not waivable: integrity breaches, the footprint and main-checkout guard, job confinement, credentials, security findings, the operator boundary. The *only* pause of a plan is a critical integrity breach (`store_tampered`, tampered enrolment). This replaces `authorize-merge`, `force-gate` and the limit-extension decisions, and adjusts the round-2 operator-verb decision (commit `c323023`, which kept `authorize-merge` and `force-gate` as verbs).

*Z5-B* (operator 2026-09-29), *remediation policies*: the server gathers the evidence (CI logs through the provider module, parsed by the domain `log_parser` extension; build failures; review findings; Sonar issues; merge conflicts; Q-Gate findings) and hands the model structured failures plus log-excerpt URIs. The model chooses from a closed action set that the server validates: `retry` (reason `enum[flaky|infra|timeout]`, bounded by `retry_budget`), `fix` (change code and re-verify, bounded by `fix_budget`, which is the loop limit), `request_waiver` (rationale), which is a waiver request to the operator. Waiting for the operator is a *bounded* process step (`waiver_wait`); then the fallback runs.

*Z5-C* (operator 2026-09-29), *policies in the DSL*: remediation policies are ordinary DSL sub-workflow units, one per failure class (`remediation.ci-failure`, `.review-findings`, `.build-failure`, `.merge-conflict`, `.qgate-findings`, `.sonar`, and spend where applicable), `scope subworkflow` with `param retry_budget`, `fix_budget`, `waiver_wait_seconds`. States: gather (server evidence job) -> decide (model links `retry` / `fix` / `request_waiver`, guarded by budgets) -> await-ci / await-verify -> …; at exhaustion, if `waiver_wait_seconds > 0`, a bounded wait for the operator: `raised` -> back to decide with the new budget, `waived` -> terminal `waived`, `expired` -> terminal `exhausted`. Terminals `resolved | waived | exhausted` return to the caller, and the caller routes `exhausted` to the defined fallback. The units are project-owned (budgets and allowed actions adaptable by the team) within compiled invariants: hard budget caps, waivers written only by the operator channel, `exhausted` always leads to a defined fallback, no dead ends. Diagrams are generated like for every unit; the units are scenario-testable. They replace the special states `finalize.ci-failed`, `finalize.review-escalate`, `finalize.loop-limit-reached`, `finalize.spend-escalate`, the `finalize.merge-gap` / `finalize.wind-down` decision routing, the Q-Gate remediation loops and the `<phase>.qgate-exhausted` operator paths.

Principles applied to every item:

. *Clean cut*: legacy `plan-marshall` is evidence of behaviour, not a compatibility target.
. *Server-side first*: prefer server-computed and server-enforced behaviour over model prose or host behaviour.
. *Model-facing minimality*: the model sees only fields with operational value.
. *Minimal resolution*: state the concrete damage first; prefer ordering, reuse of existing mechanisms, or removal over new states, fields or grammar; mirror legacy where its behaviour is sound and evidenced.
. *Self-enforcing process* (Z5-A–C): no in-run operator decision; a former operator decision becomes either a server rule, a model work judgment under server checks, a remediation policy, or a waiver the operator sets on the operator's own initiative. Every item names which, and what the server checks.

Reading of "no operator questions" used throughout, settled by Z5-E: content questions (init questions, the refine and outline clarification rounds, sub-agent task questions, PW:170-173) are not operator questions; each is a server question record created through an `ask` link, delivered per the operator's `questions.delivery` and bounded by a question wait (<<z5-e>>, <<z5-60>>, <<z5-61>>). What goes are the operator-channel decisions (`decide`, elicitation of operator-authorizing outcomes, the `blocked` condition). Overrides (waivers, `abort`, integrity resolutions) are never content questions and use only the operator channel.

== Research summary

Legacy behaviour relevant to the items (paths relative to LEG):

* *Execution is sequential; the envelope owns the chain-tail commit*: tasks run one after another and commit at the chain tail inside that sequence (`phase-5-execute/SKILL.md:14`, `:134-136`, `:747-759`); a failed module build returns `triage_required`, the fix is dispatched and the sequence resumes (`:831`); an empty `per_deliverable_verbs` list is allowed (`:811`, a recorded PM-MCP difference: `SS:2047` `minItems: 1`). A dirty worktree at a boundary is settled by commits and halts on unmappable paths (`plan-marshall/workflow/execution.md:429-460`).
* *Leaf questions and deviations go through the main session*: a leaf returns `escalate_ask` with `prompt_options[]`; the main orchestrator fires one batched `AskUserQuestion` over all deviations (hold / accept with rationale / split), applies each side effect and re-dispatches (`plan-marshall/workflow/execution.md:332-345`); a leaf cannot fire `AskUserQuestion` (`ref-workflow-architecture/standards/agents.md`).
* *Infeasible and task status*: `infeasible` is terminal and resolved by a gate-level planning step, with no concurrent operator decision (`manage-tasks/standards/task-contract.md:193`; `execute-task/SKILL.md:46-50`). Task statuses are `pending`, `in_progress`, `done`, `blocked`, `infeasible`, with no task skip (`task-contract.md:120`, `:224-228`); `skipped` is a step status only (`:202`). No operator step skip exists (`phase-6-finalize/standards/verdict-currency.md`).
* *Q-Gate*: an LLM validation workflow (`plan-marshall/workflow/q-gate-validation.md`, 951 lines, §2.1-2.17) dispatched as a sibling task after each phase (`phase-3-outline/SKILL.md:354`; `phase-4-plan/SKILL.md:61`, mechanical checks as scripts beside it). Refine validates regardless of confidence (`phase-2-refine/SKILL.md:269`).
* *Init*: "Rename" deletes the plan and restarts init (`phase-1-init/SKILL.md:909-922`); the lane is asked by default (`lane_selection: ask`, `:924-981`) and fixed at init; the issue is fetched inline (`:296`); lesson-premise "Refine" and "Residual" (`:380-395`). Outline approval uses `AskUserQuestion` (`plan-marshall/workflow/planning-outline.md`).
* *Finalize*: a red CI check is a triage finding with a fix path, never a plan abort by refusal (`phase-6-finalize/standards/ci-verify.md:183-187`). One grant roster; "a grant authorizes exactly one gap class" (`phase-6-finalize/standards/branch-cleanup.md:123-134`); force-done marks the FIND step `done` "byte-identical to one earned by a genuine pass", and the barrier, not force-done, authorizes the merge (`automatic-review/SKILL.md:989-1034`; `branch-cleanup.md:129`, `:726-728`). `sync-baseline` classifies `no_overlap` (auto rebase), overlap (`needs_user` prompt "Yes, rebase / No, skip", with the late `branch-cleanup` rebase as backstop) and conflict (`failed`, halt) (`finalize-step-sync-baseline.md:60-130`, `:143-186`, `:196`). `simplify` reverts a deletion that conflicts with a review commitment itself, recording `reverted_count` (`finalize-step-simplify.md:211-216`, `:254-258`). workflow remediation.ci-failure version 1 format 1
scope subworkflow
param retry_budget: int[0..5]
param fix_budget: int[0..5]
param waiver_wait_seconds: int[0..86400]
start remediation-ci.gather

state remediation-ci.gather
  phase inherit
  composite_job remediation.gather-ci-evidence   # provider module + domain log_parser

    none            -> remediation-ci.resolved
    all_waived      -> remediation-ci.waived     # every failing check has a waiver record

  phase inherit
  auto remediation.check-budgets
    budget_left     -> remediation-ci.decide
    exhausted_wait  -> remediation-ci.waiver-wait  # waiver_wait_seconds > 0: server files the request
    exhausted       -> remediation-ci.exhausted

state remediation-ci.decide
  phase inherit
  facts remediation.failure-evidence             # structured failures + log-excerpt URIs
  link retry retry [submit] (reason: enum[flaky|infra|timeout])
    guard predicate:remediation.retry-budget-left
    do remediation.rerun-checks
      rerun_started -> remediation-ci.await-ci
  link fix fix [submit] (summary: text[1..500])
    guard predicate:remediation.fix-budget-left
    do remediation.record-fix-attempt
      recorded      -> remediation-ci.commit-fix
  link escalate request_waiver [submit] (rationale: text[1..2000])
    guard predicate:remediation.waiver-wait-enabled
    do remediation.request-waiver
      requested     -> remediation-ci.waiver-wait

state remediation-ci.commit-fix
  phase inherit
  call git.commit_and_push (message_mode=interactive, push_mode=always)
    committed_and_pushed -> remediation-ci.await-ci
    pushed_clean         -> remediation-ci.await-ci
    # … the other terminal outcomes (Rule 6 bijection)
    aborted              -> remediation-ci.decide

state remediation-ci.await-ci
  phase inherit
  composite_job ci.watch-checks                  # only the CI checks of the new HEAD
    passed          -> remediation-ci.resolved
    failed          -> remediation-ci.gather
    interrupted     -> remediation-ci.gather

state remediation-ci.waiver-wait
  phase inherit
  composite_job remediation.await-waiver         # bounded by waiver_wait_seconds
    raised          -> remediation-ci.budget-check
    waived          -> remediation-ci.waived
    expired         -> remediation-ci.exhausted

state remediation-ci.resolved terminal resolved success
state remediation-ci.waived terminal waived success
state remediation-ci.exhausted terminal exhausted failure
----

=== Z5-D The plan instance: a composed, versioned DSL unit per plan

* *Question*: Does a plan execute the project's template units directly, or a concrete process composed for this plan; and where do configuration and waivers live relative to it?
* *Decision*: Operator 2026-09-29: every plan executes its own *plan instance* `plan.pmwf`, a real DSL unit composed by the server from the templates (compiled defaults and the project-owned `.marshall/config/*.pmwf`, remediation policy units) and the plan's *facts*. A new version takes effect at the next transition, never mid-state; state ids stay stable so the current position maps across versions; completed history is never rewritten; the compiled invariants are checked on every version; a template change reaches a running plan only through an adopted re-composition (the existing adopt/keep drift rule). The instance absorbs `execution-manifest.json` (the step list is the instance) and the `config_hash` snapshot (its header). Diagrams are generated from the instance, so the process in force is visible per plan.

=== Z5-64 `step_out` with remediation units, nested calls, `hand_back` and step firings (new)

* *Question*: How does a caller route `stepped_out` of a remediation unit (like `exhausted`, or differently), how does a unit route a nested `stepped_out` of its own `git.commit_and_push` call, does a step-out consume budgets, where is `step_out` offered (link states only, or also waiting job states), is `hand_back` still offered inside a sub-process, and what is recorded?

* *Options*: (a) `step_out` is offered on every resting `link` state of a sub-process, never on `auto`, `job` or `composite_job` states (a waiver wait or CI wait is bounded and ends by itself) and never at plan scope, where `hand_back` is the equivalent; `hand_back` is not offered inside a sub-process, so every caller sees and routes the unwinding. A remediation unit routes a nested `stepped_out` of its commit call back to `decide` (the model keeps its remedies; the uncommitted fix is not charged, Z5-7). Phase-level callers route a unit's `stepped_out` to the same fallback state as `exhausted`; the gap record distinguishes them (`cause: stepped_out` with the reason vs `cause: exhausted` with the budget). A step-out consumes no budget and writes no waiver; the begun step's firing is recorded `failed` on the fallback entry (Z5-25). (b) `stepped_out` of a unit is folded into `exhausted`: one route less, but the reason and the "model gave up with budget left" signal are lost. (c) `hand_back` at any depth, unwinding every frame at once: skips callers that can recover (`epic.commit-ledger`, a remediation unit's `decide`).
* *Recommendation*: (a). It keeps the one-frame rule of Z5-21, gives every caller its routing chance, and keeps the landing record honest about why a plan was handed back.
* *Affected*: DSL § Implicit Links (`step_out`), Rule 6 wording, Abort model; the remediation unit template (commit-call routing); SC rows of every sub-process link state (implicit link); SS gap record (`cause`); PW § Post-Run Band hand-back comment content.
* *Decision*: Operator 2026-09-29: (a): `step_out` on every resting link state of a sub-process only (never on `auto` / job states, never at plan scope where `hand_back` is the equivalent); `hand_back` not offered inside a sub-process; a remediation unit routes a nested commit-call `stepped_out` back to `decide` (uncommitted fix not charged); phase callers route a unit's `stepped_out` to the same fallback as `exhausted`, the gap record distinguishes `cause: stepped_out` (reason) vs `cause: exhausted` (budget); a step-out consumes no budget and writes no waiver; the begun step is recorded `failed` on fallback entry.

=== Z5-65 Question wait vs waiver wait: mechanism, concurrency, pauses and stops (new)

* *Question*: Z5-E adds a bounded question wait beside the bounded waiver wait of Z5-B. Which mechanism runs the question wait (state kind, timer), can a question and a waiver request be pending at once, what happens to both under the integrity pause, an operator `abort` or `delete-plan`, and a gone host session, and how do they interact with the continuation policy?
* *Evidence*: waiver wait as server-side `composite_job` (Z5-7 decision), shipped `waiver_wait_seconds = 0` (Z5-5 decision), `waiver_requests[]` and its notifications (Z5-9 decision); the integrity pause rejects every `pm_do` and is unbounded (Z5-3 decision); a state body is one clause, so a job state offers no answer link (DSL:167-171); `pm_do` chains until a link, job or terminal state (DSL:1169); `stop_on_issue_only` stops at `awaiting_user` states and escalations (HF:138); awaited events (Z5-18 decision and its *Adjusted by Z5-E* line).
* *Options*: (a) Two records, one timer mechanism: the question wait is a link state (answer link for `session` delivery, <<z5-61>>) with an engine-owned deadline processed by the job runtime's timer, which takes the fallback transition without a model call; the waiver wait stays a `composite_job`. Serial phases guarantee at most one question state per plan scope; a waiver request can only arise inside a remediation unit, which is never entered while a question state is current, so the two never overlap. The integrity pause holds both deadlines' fallback transitions until the pause ends (a paused plan cannot act on an expiry); `abort` and `delete-plan` close pending question records `cancelled` and pending waiver requests `expired`. With `session` delivery a question state is a stop point under both continuation policies; with `elicitation` or `web` the model need not stop and may long-poll the question (`wait:question:<question_id>`, bounded). Notifications reuse the Z5-9 channels for `web` delivery while the records stay apart. (b) One "human wait" mechanism and record for both: contradicts Z5-E (overrides are never content questions) and the Z5-9 decision. (c) The question wait as a `composite_job` like the waiver wait: a `session` answer would need a link on a job state, which the DSL forbids.
* *Recommendation*: (a). It needs no new state body, keeps overrides and content apart, and bounds every human wait server-side.
* *Affected*: DSL § Engine (deadline processing), `AwaitedEvent`; job runtime timer; SC question states; HF:138 (continuation policy stop points), `wait:question:` link; SS `questions.jsonl` closure `cancelled`, `waiver_requests[].outcome`; `timeouts.adoc`.
* *Decision*: Operator 2026-09-29: (a), adjusted to the Z5-61 question modes: the question wait is a link state with an engine-owned deadline processed by the job-runtime timer (no deadline in `questions.mode: operator`; usually no wait in `none` / `model`); the waiver wait stays a server-side `composite_job`; the two never overlap; the integrity pause holds both deadlines' fallbacks; `abort` / `delete-plan` close pending questions `cancelled` and waiver requests `expired`; timers survive a gone host session; with `session` delivery a question state is a continuation stop point, with `elicitation` / `web` the model may long-poll `wait:question:<question_id>` (bounded); `web` notifications reuse the Z5-9 channels, records stay apart.
* *Flag*: design.
