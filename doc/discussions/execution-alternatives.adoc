= Execution Alternatives
:toc: left
:toclevels: 2

xref:../Requirements.adoc[Requirements] » xref:README.adoc[Discussions] » Execution Alternatives

Alternatives to the decided build execution (xref:../requirements/06-execution.adoc[Build Execution]: native execution on the host as subprocesses of the daemon) kept for later verification. None is part of the target design; host-native PM-MCP (pattern A) has since been adopted. Each entry states when it should be reconsidered. The pattern letters refer to xref:execution-patterns.adoc[Execution Patterns].

== Candidate: container backend

Each build in a short-lived container through Docker or Podman, with sibling containers for builds that start containers themselves. The full design is in xref:container-backend.adoc[Container Backend].

== Candidate: microVM backend (Docker Sandboxes)

A third build backend in which each build — or each plan — gets its own microVM with a private container runtime, using https://docs.docker.com/ai/sandboxes/[Docker Sandboxes].

Strengths::
* Builds that start containers work unchanged, without access to the developer's runtime and without Docker-in-Docker on a shared daemon.
* Strongest isolation of all options: own kernel, no path back to the host.
* Built for coding agents and supported for Claude Code, Codex and OpenCode.

Weaknesses::
* No shared image store or caches with the host runtime: images and dependencies are pulled per sandbox unless caching is provided.
* Workspace synchronisation instead of same-path mounts: PM-MCP must translate paths between sandbox and host.
* Additional product to install and operate.

To verify::
* Platform support (macOS, Linux, Windows) and licensing of the `sbx` tooling.
* Start-up time per sandbox; lifetime per build versus per plan.
* Caching of images and dependencies across sandboxes.
* Workspace sync semantics, latency and conflict handling with the worktree.
* API for creating, observing and removing sandboxes programmatically.

Reconsider when::
Container-using builds must run where no rootless runtime is available, or projects' builds are not trusted to control the developer's runtime.

== Alternative: host execution through ssh and a verifying guard (pattern D)

The PM-MCP container calls a `host-exec` shim; sshd on the host accepts a key restricted by a forced command and starts a guard that verifies and runs the wrapper. Detailed in xref:host-execution-ssh.adoc[Host Execution through ssh].

Strengths::
Native build performance; host toolchains and credentials; no container runtime API needed; fine-grained verification of each call.

Weaknesses::
No precedent in agent tooling; requires a listening sshd on the host; custom guard; does not cover warm language servers. The host backend with an outbound channel provides the same result without a listening port.

Reconsider when::
The host backend's outbound channel proves impractical and PM-MCP must run in a container.

== Alternative: host-native PM-MCP (pattern A)

PM-MCP itself runs as a native binary on the host (Quarkus native, distributed via Homebrew, GitHub releases or JBang), started by the host as a stdio server.

Strengths::
Mainstream for local coding tools; no path mapping, credential passing or mount penalty; language servers use host toolchains directly.

Weaknesses::
No isolation of PM-MCP itself; separate distribution artifacts per platform.

Reconsider when::
A container runtime is unavailable or undesirable on target machines. Compatible with both build backends: a host-native PM-MCP can start build containers and talk to the host build server over a Unix socket.

== Alternative: host execution with OS sandbox (pattern A+)

Builds run natively but inside an OS sandbox (Seatbelt on macOS, bubblewrap on Linux), with writes limited to the plan's worktree and caches and network access through a proxy — the mechanism of https://github.com/anthropic-experimental/sandbox-runtime[Anthropic's sandbox-runtime]. Would be a sandboxed variant of the host backend.

Strengths::
Isolation without containers; native performance; host toolchains.

Weaknesses::
Platform-specific sandbox profiles; no Windows support without WSL2; builds that start containers need the runtime socket inside the sandbox; sandbox-runtime is a research preview.

Reconsider when::
Host-backend projects need isolation, or isolation is required on hosts without a container runtime.

== Alternative: everything in one container (pattern B)

PM-MCP and all toolchains in one image, with the worktrees mounted.

Strengths::
Single artifact; reproducible toolchains.

Weaknesses::
Large images with per-domain toolchain layers; builds share PM-MCP's container and privileges; no per-build isolation.

Reconsider when::
Not expected; the container backend provides the same reproducibility with per-build isolation.

== Alternative: unprivileged nested runtime (Sysbox)

Build containers run on https://github.com/nestybox/sysbox[Sysbox], which allows a container runtime inside unprivileged containers, so container-using builds get a private runtime without a VM.

Strengths::
Private runtime per build without privileged mode; lighter than a microVM.

Weaknesses::
Linux only; installation of a separate runtime on the host; no shared caches with the host runtime.

Reconsider when::
Container-using builds need a private runtime on Linux hosts and the microVM candidate is not viable.

== Language servers

Where warm language servers run is not yet decided (xref:../Requirements.adoc#_appendix_verification_gates_risk_register_non_normative[Open Questions]). Options:

* in PM-MCP's environment — requires toolchains in the PM-MCP image;
* in per-project language-server containers, analogous to warm builder containers;
* on the host, hosted by the host build server alongside builds (pattern E), which keeps host toolchains and works when PM-MCP runs elsewhere.
