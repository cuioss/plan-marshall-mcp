== Setup

* *Stub*: the package `de.cuioss.pm.mcp.spike` of the module `plan-marshall-mcp` (throwaway, removed with Milestone 1). It registers its tools only when `pm.spike.scenario` names a scenario file: `pull_wait` blocks and answers `wait_again`, a task, or `done`; `pull_submit` takes the decision of a task; `pull_info` is a distractor that a correct loop never calls; `pull_escalate` is registered in the middle of a run for the widening test of V9. Every answer names the next call, as the fresh links of a real wait answer do.
* *Measurement source*: the stub writes every request, call start and end, progress frame, delivery, submit, and refusal to `events.jsonl`. Timings and counts come from this file and from the arrival time of every output line of the harness, never from what a model reports about itself.
* *Driver*: the project-local skills `test-pull` (shared) and `test-v1` to `test-v10` (`.claude/skills/`). One stub process and one detached supervisor per run; run data under `.plan/temp/pull-spike/runs/`.
* *Harnesses*: Claude Code (`claude`), OpenCode (`opencode`), Antigravity (`agy`). Headless runs use `claude-haiku-4-5`, `opencode/space-bunny-free` (OpenCode Zen), and `gemini-3.8-flash-medium`; a verification that the small model fails is run once more with the next larger model, and both rows are recorded. Interactive runs use the model selected in the session. Harness version and model are recorded with every result, because harness versions move during a measurement series.
* *Transport*: a host reaches the stub as it will reach the product, over `stdio`. The host starts `relay.py`, the stand-in for `pm-mcp serve`, which forwards every message to the stub over Streamable HTTP and writes the host side (requests, cancellations, the end of `stdin`, signals) to a log of its own. A run with `--transport http` connects the host to the stub directly and is marked as such.
* *Worker identity*: the relay sets the argument `worker` of every call to its worker id, as the real relay carries the job token; the model never passes it. The MCP connection cannot identify a caller on every host (see <<observations>>).
* *Decisions*: the closed-answer tasks of `.claude/skills/test-pull/fixtures/tasks.json`, modelled on the decision states of a running plan (remediation, review triage, scope, build classification, commit type, quality gate). The expected answer is never sent to the model.

=== Limits of the setup

* *Relay*: the relay is a Python stand-in, not `pm-mcp serve`. What a host does towards a `stdio` server is measured faithfully; the relay's own start time and its behaviour at termination are Part B items.
* *Antigravity*: `agy` offers no per-call MCP configuration. A run registers the stub in the operator's user configuration (`agy mcp add`) and removes the entry when it ends, so Antigravity runs are sequential, and V9 (two workers on one queue) cannot separate its workers by configuration.
* *Model level*: the headless figures describe the small model. Reliability at a higher level is spot-checked with `--model`, not measured throughout.

== Pass criteria

Set before the measured runs (`.claude/skills/test-pull/criteria.json`, confirmed by the operator on 2026-10-02; the confirming commit precedes the first measured run). A run that fails for a tooling reason is repeated and the repeat is noted; a run that fails its criterion is recorded as failed with its failure mode and is never repeated until it passes.

Read against the criteria:

* *Bounded wait of 240 s*: holds on Claude Code by default. On OpenCode it holds only when the server sends progress or the profile raises the timeout; a silent call ends after 60 s. On Antigravity it does not hold: the limit is 180 s, so the fallback applies, `bounded_wait_seconds` = 150 for that profile.
* *`progress_resets_timeout`*: true for Claude Code (1800 s without, at least 3600 s with) and for OpenCode (60 s without, at least 3600 s with). False for Antigravity: 36 frames did not move its 180 s deadline.
* *Withdrawn*: the first headless runs showed Antigravity ending the MCP server after a timed-out call ("`server name pullstub failed to load`"). That was a defect of the stand-in relay, which wrote the stub's reply to a notification back to the host; Antigravity ends a server that answers a notification. With the relay corrected, the interactive session called again after the timeout and was answered. The two headless cells are repeated with the corrected relay.
* *Cancellation*: OpenCode and Antigravity send `notifications/cancelled` when they give a call up; Claude Code does not.
* All three harnesses send a `progressToken` with every call.

Interactive session, Antigravity 1.2.14, 2026-10-02: the silent call and the call with a progress frame every 5 s were both cancelled after 180 s (`timed out after 3m0s: context deadline exceeded`); in both the model called again and was answered. The interactive limit equals the headless one.

[#observations]
== Observations from building the tooling

These come from short trial runs (seconds to two minutes; Claude Code 2.1.287, OpenCode 1.18.32 to 1.18.34, Antigravity 1.2.14; 2026-10-01 and 2026-10-02). They are not results of V1 to V10; they changed the tooling and name what the measured runs have to confirm.

* *Hosts differ in session use, and one host differs by transport.* Over Streamable HTTP, Claude Code calls without a session: `server/discover` and `subscriptions/listen`, never `initialize`, every request on a transient connection of its own. Over `stdio` it probes `server/discover` and, when that fails, opens a session with `initialize`. Antigravity calls without a session over `stdio` (protocol `2026-07-28`, client info `antigravity-client`, not the provisional `antigravity` of the Host Integration Table) and ends its relay with a cancellation, the end of `stdin`, and `SIGTERM`. OpenCode opens a session (`initialize`, protocol `2025-11-25`, `clientInfo.name` `opencode`). A connection can therefore not bind a task to its worker on every host; the stub binds by an explicit `worker` argument, which the relay sets.
* *A relay has to add what a sessionless host does not send.* Such a host puts protocol version, client info, and capabilities into `params._meta` of every request. The HTTP transport of the server additionally demands the headers `Mcp-Method` and, for a call by name, `Mcp-Name`, and refuses the request without them. The stand-in relay derives them from the message; `pm-mcp serve` will have to do the same.
* *The server does not learn that a client dropped a held call.* A call abandoned by its client is held until its own end, its progress frames are written without an error, and the step it took from the queue is consumed. The abort time of V1 is therefore taken from the harness side (a `notifications/cancelled`, the harness reporting the call as ended, the model's next call). For the design this means that the bounded wait and leases, not the transport, bound how long a dead puller keeps its place.
* *Over Streamable HTTP, a silent call ended after about 60 s on both harnesses in a 90 s trial.* OpenCode sent `notifications/cancelled` with `MCP error -32001: Request timed out` after 60.0 s; Claude Code reported `The operation timed out` after about 61 s and sent no cancellation. With a progress frame every 5 s the Claude Code call outlived the 90 s of the trial. The stub held a silent call for 75 s against its own client, so the limit is the harness's. V1 measures this up to the cap and with the raised configuration.
* *A harness that receives `SIGTERM` during a held call may send the call once more.* Claude Code sent a second `pull_wait` within 50 ms of the signal; the stub answered it and so consumed a step. V4 counts these calls.
* *A tool allowlist with a wildcard admits a tool added in mid-run.* An OpenCode agent whose tool set named `pullstub_*` called the tool the stub registered later. The runs use explicit tool names; V9 tests whether that holds.
* *A relay must never answer a notification.* The server's HTTP transport returns a body for some notifications of a sessionless host (for example `notifications/roots/list_changed`); written to `stdout`, it makes Antigravity end the server ("`failed to load: invalid request`"). The stand-in relay discards such bodies; `pm-mcp serve` must do the same.
* *In Antigravity an MCP tool is called through the built-in `call_mcp_tool`.* The headless model found that by itself; the model of the interactive session called the tool by its bare name and failed until the prompt named the convention.
* *Per-turn output tokens of Claude Code need partial messages.* The `assistant` events of `stream-json` carry the output tokens of the stream start; the final figure of a turn is in the `message_delta` events that `--include-partial-messages` adds. The headless runs set that flag.
* *Antigravity has a headless mode, and it needs a leash.* `agy` 1.2 offers `-p` with `--output-format stream-json`, `--json-schema`, and `--conversation`, which the specification does not yet know (`headless: null` for `antigravity`). MCP calls in that mode need `--dangerously-skip-permissions`; when its MCP server failed to connect, the model started to investigate with shell commands. The runs add `--sandbox`. Whether the mode is usable for model jobs is a Part B question; the runs here test it as a puller.
* *The free OpenCode model is slow.* `space-bunny-free` took about 33 s per turn in the trial, against 1 to 3 s for the other two harnesses; 240 cycles of V2 take about four hours instead of two.
