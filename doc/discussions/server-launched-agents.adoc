NOTE: *Status: decided 2026-09-30*: Z7-0 and Z7-1 to Z7-14 are decided (see the *Decision* lines); where a *Decision* line differs from the recommendation or the proposal body, that line holds. Every sub-agent is a server-launched harness-CLI job (job kind `llm`, job-bound token, model slots); the host never dispatches a sub-agent; Antigravity and the neutral profile run no model jobs in v1.

A proposal to replace the host sub-agent dispatch of PM-MCP by jobs the server launches itself. Today the server renders a `dispatch` link, the host model starts its own sub-agent tool (`Agent`, `task`, `invoke_subagent`, `spawn_agent`), and the parent session reports the return through `returned:<dispatch_id>`. The server cannot see the sub-agent, cannot bound it in time, and learns its token usage only from the model's self-report. Every harness PM-MCP targets has a headless CLI (`claude -p`, `opencode run`, `codex exec`, `agy -p`), so the server can start the sub-agent as a job, like a build, and observe its process, exit, output and usage directly. This document collects the legacy execution context (<<inventory-legacy>>), the PM-MCP dispatch design with its contradictions (<<inventory-pmmcp>>) and the capabilities of the harness CLIs (<<inventory-harness>>), describes the target model (<<target-model>>), and asks one question per open design point (<<decisions>>).

[#direction]
== Scope and operator direction

*In scope*: how a sub-agent is started, bounded, connected, observed and accounted for; what it receives (skills, contract, working directory, model, effort); how untrusted text is batched for the screener and for model judgment; how the dispatch vocabulary (states, links, records, conditions, roles, variants) maps onto jobs. *Out of scope*: what each workflow state does with a sub-agent's result (WC and PB decided that), the level-1 validator (Z6-25), and the web server.

[#z7-0]
=== Z7-0 Principle: complete switch to server-launched jobs

* *Decision*: Operator 2026-09-29: complete switch. Every sub-agent becomes a server-launched harness-CLI job: the headless run connects back to PM-MCP for its entity scope with a restricted tool set. There is no host `dispatch:` of sub-agents; the host model only drives the main workflow and waits on job links.

*Operator constraints* (2026-09-29), referenced as C1–C6:

[cols="1,8"]
|===
|C1 |Revisit the legacy execution context: each job is passed its skills and its interface contract (links offered, result schema) explicitly, for fine-grained control.
|C2 |Untrusted ingestion uses an enforced batch format: the workflow gathers all inputs of a phase or step and screens them in one batch where sensible (for example several PR comments or Sonar findings).
|C3 |Every call runs in the directory of the concrete project (the plan worktree when present, else the project checkout), like builds, so project-level skills and instructions load.
|C4 |The screener is the special case: server-fixed prompt only, no project-level files or skills (isolated working directory or project settings disabled).
|C5 |The design may target named agents where the harness supports them; research shows per harness whether inline named agents or per-call flags compose the agent.
|C6 |Operator configuration may name a specialized model per model-job role, passed through the CLI where the harness offers it (from Z6-24).
|===

*Related decisions*: Z6-A (bootstrap sub-workflows, `pm_start` removed), Z6-B and Z6-22 to Z6-25 (two-level guard; screener = exec job kind `llm` through the detected harness's headless CLI; batching and SHA-256 verdict cache; level-1 stack JDK + commonmark), Z6-21 (M1 headless spike, M4 `llm` job kind).

*Principles applied to every item*: server-side first; model-facing minimality; the process enforces itself (bounded self-remedy, fallback ends, no operator questions mid-plan); prefer simple resolutions (minimal option first); clean cut from legacy; no new dependency without approval; the native-provider pattern (native default, CLI variant) as precedent for "one default path, declared variants".

[#inventory-legacy]
== Inventory A: legacy execution context

*Contract* (LEG `agents/execution-context.md`): tools `Read, Write, Edit, Glob, Grep, Bash, Skill` (no `AskUserQuestion`, no `Task`); prompt fields (`:20-28`) `name`, `plan_id`, ordered `skills[]` (persona excluded), exactly one of `workflow` / `instructions`, `WORKTREE` (repo-relative), workflow placeholders, optional `caller_phase`. Steps: validate (`contract_violation`) -> load the persona `persona-plan-marshall-agent` -> load `skills[]` in order (`skill_load_failure`) -> resolve the workflow notation from the installed plugin cache (not the worktree) -> execute as a leaf -> log. Return: the workflow's TOON verbatim, minimum `status` (`success | error | loop_back | blocked`) and `display_detail` (<= 80 ASCII), plus workflow-specific fields (`refine_prompt`, `outline_prompt`, `escalate_to_deep`, …); the orchestrator parses the harness `<usage>` block (`total_tokens`, `tool_uses`, `duration_ms`).

*Levels*: seven levels plus `inherit`; Claude ladder L1 haiku/none, L2 sonnet/medium, L3 sonnet/high, L4 opus/medium, L5 opus/high, L6 opus/xhigh, L7 fable/max (LEG `skills/plan-marshall/standards/effort-levels.md:54-63`); up to seven variants per agent generated at build time and installed through the plugin cache; local override `.plan/local/effort-ladder.json`. Roles resolve `plan.<phase>.effort.<sub>` > `.default` > phase string > `plan.effort` > `inherit`.

*Tool surfaces*: writer (`Read, Write, Edit, Glob, Grep, Bash, Skill`); reader (`WebSearch, WebFetch, Read, Grep`, no skills, contract in the agent body); a PreToolUse hook enforces rules on the execution-context identity. Needed but missing: read-only-with-Bash (corroboration is "read-only by instruction") and text-only extraction.

*Dispatch sites*: refine (one re-dispatch; baseline-drift loop cap 3), Q-Gate siblings after phases 2/3/4, outline (deep and light lanes), change-type fallback, plan, execute envelopes (seven termination causes, `budget_yield`, batched `escalate_ask`), verification-feedback triage (findings by reference), finalize dispatched steps (timeouts 900 s for sonar / automatic review, 300 s for lessons / ADR; a timeout fails the step and the loop continues), one unified finalize triage over PR-comment and Sonar findings, self-review author and verifier, `enrich-module` per module all in parallel (the only fan-out), slash commands (pr-doctor, plugin-doctor, retrospective), research reader, issue-body reader, seven orchestrator sub-steps.

*Untrusted ingestion*: reader -> `validate_struct` -> writer; the script is the boundary (ADR-003). PR review comments and Sonar findings get no reader: producers quarantine raw text under `raw_input.{field}`, one batched deterministic ingest pass validates every finding, and triage runs in one envelope grouped by `(domain, rule_id)` with one model decision per group (LEG `skills/plan-marshall/workflow/verification-feedback.md:196`: "containment is now one batched pass"). Length-clamped but semantically raw comment text still reaches a write-capable triage context, the gap Z6-B closes.

[#inventory-pmmcp]
== Inventory B: current PM-MCP dispatch design

*Premise*: DAE02:14: "MCP servers do not directly spawn host sub-agents"; the host executes its native agent tool and the server "cannot observe sub-agent termination, harness cancellation, or token consumption" unless the parent reports it. PB Z6-B repeats it ("the PM-MCP server has no model access of its own"). Z7-0 reverses both.

*Mechanism*: the link form `dispatch` (WD01:104, :107, :143-146, :187; HF01:175-178) renders `host_tool`, `params` and a `prompt` (REQ02 PM-WF-5, :70: `name`, `dispatch_id`, `plan_id` / `epic_id`, `entity`, `skills[]`, `WORKTREE`, continuation policy, `start: pm_state(...)`). The return link `returned:<dispatch_id>` carries `dispatch-return-args-v1` (DAE02:64-146: `status` `success | error | harness_cancellation`, `display_detail`, `token_usage` and four components, `tool_uses`; `duration_ms` measured by the server). Lifecycle `ALLOCATED | CLAIMED | RETURNED | INCOMPLETE_SUBMISSION | UNCONFIRMED | SUPERSEDED`, "there is no dispatch timeout" (DAE02:23); recovery links `redispatch:<entity>` and `resume:<entity>` (DAE02:57-62); `stale_dispatch_id` (DAE02:51); the `dispatch_incomplete` condition with a self-remedy budget of 3 (DAE02:156); the return-evaluation primitive reads only persisted records (DAE02:170).

*Profiles and variants*: the profile `dispatch` block requires `supported`, `host_tool`, `agent_variants`, `params_template`, `token_usage_components`, `reports_tool_uses` (CP01:113-153); `connection.durable_cwd` (CP01:216, :291). The installer renders per-level worker and reader variants into the host's agent directory, rendered from the ladder; a ladder change takes effect after `pm-mcp client update` and a host restart (DAE03:252-269). Roles resolve to a level and then to an installed variant (DAE03:173-250).

*Sites* (the full inventory is the input of <<z7-10>>): refine (`refine.analyze`), Q-Gate (`dispatch:qgate` after phases 2, 3, 4), outline (deep and light), task envelopes (`execute.dispatch-ready`, serial, DAE01:232), finalize `simplify` ("returns proposals and edits nothing", no submit), finalize `security-audit` (no role row), finalize `lessons-author` (role `post-run-review`), `setup.enrich-architecture` (concurrent `dispatch:enrich-<module_id>`, uncapped, SC06:188-193), epic `dispatch:decompose` (Z6-15), epic spec re-grounding (DAE04:199-201, no dispatching state), lessons review (Z6-19, role unspecified), the screener (Z6-24, already a job). Named as roles but run inline: triage (`triage:<finding_id>` links), self-review, create-pr, ADR author. The reader family (DAE03:271-320) is obsolete after Z6-B.

[#target-model]
== Target model

A sub-agent is a job of kind `llm` (SS10 job kinds extended). The workflow state that needs model work is a job state; the server composes the launch, starts the harness CLI through `pm-mcp-exec` in the project's directory, and the headless run connects back to the daemon for exactly its entity with a job-bound capability. The host model follows a `wait:` link like for a build; the job's completion is the awaited event.

[source,text]
----
host model (main session)                      pm-mcpd (daemon)                          harness CLI job
 pm_do(link) ----------------------------> job state entered (role, entity)
                                            compose launch contract:
                                              template   <- client profile `headless` block
                                              harness    <- detected client | operator override
                                              model/effort <- role -> level -> ladder | operator model per role
                                              cwd        <- plan worktree | project checkout | isolated (screener)
                                              prompt     <- core conduct + skills + contract envelope
                                              mcp        <- `pm-mcp serve --job` + job token (not for screener)
                                              schema     <- result schema (named)
                                            model slot lease (machine cap, per-plan writer cap)
                                            pm-mcp-exec (process group, confinement, env) --> claude -p … / codex exec … / opencode run …
 <-- facts + wait:<job_id> ---------------                                                     |
 pm_do(wait:<job_id>) (composite wait)                                                          | pm_state / pm_do(entity) / pm_build / pm_skill
                                            job-bound connection <------------------------------+ (job token; tool and link allowlist)
                                            output parsed: result, usage, cost                  |
                                            fate: succeeded | failed | timed_out | killed <-----+ exit
                                            return-evaluation primitive on persisted records
 <-- outcome transition ------------------ next state
----

*Launch contract* (server-composed per job, recorded in the job record; the composed argument vector is digested like every job's, SS10 `argv_digest`):

. *Harness*: the detected client of the scope's last session row (Z6-24), or an operator-configured `model_jobs.harness` naming an installed profile with a headless template (<<z7-1>>).
. *Command template*: the profile's `headless` block: an argument-vector template with typed slots and declared capabilities (<<z7-1>>). Claude and OpenCode compose an inline named agent; Codex composes by per-call flags.
. *Working directory*: the plan worktree when it exists, else the enrolled project checkout; for the screener an empty job-private directory (<<z7-13>>).
. *Model and effort*: role -> level -> ladder entry of that harness -> CLI flags; an operator model per role overrides the ladder's model (<<z7-8>>).
. *Prompt*: the core conduct skill, the role's and state's skills, and the contract envelope, delivered as a system-prompt file where the harness takes one (<<z7-6>>).
. *MCP connection back*: an MCP configuration starting the relay `pm-mcp serve --job`, with the job token in the relay's environment; no connection for the screener (<<z7-2>>).
. *Output*: structured result against the named result schema where the harness supports it; usage and cost parsed from the harness output (<<z7-9>>).

*Lifecycle*: the job record replaces the dispatch record. Fates `succeeded | failed | timed_out | killed | refused` replace `RETURNED | UNCONFIRMED | SUPERSEDED`; budgets replace "no dispatch timeout"; the server, not the parent session, observes the end. Completion runs the entity kind's return-evaluation primitive on persisted records, as today; a job that ended without its required submit raises the existing incomplete condition with a bounded relaunch (<<z7-5>>).

*Batching*: every step that ingests external text gathers its new items first and screens them in one screener job per gather firing; model judgment of findings (triage) runs as one job per gather firing over finding groups, not per finding (<<z7-7>>).

*Screener special case*: zero tools, no MCP, server-fixed prompt, isolated working directory, project and user settings disabled where the harness allows, closed `screen-verdict` schema, fail-closed; supported only on harnesses that can remove all tools per call (<<z7-1>>, <<z7-13>>).

*Per-harness mapping* (proposal; verified in M1):

[cols="2,3,3,3,3"]
|===
|Harness |Worker job |Read-only job (Q-Gate, triage, enrich) |Screener |Support in v1

|`claude` |inline agent `--agents` + `--agent pm-job`, `--mcp-config` + `--strict-mcp-config`, `--json-schema`, `--no-session-persistence`, `--output-format stream-json` |same, tools `Read, Grep, Glob` + PM tools |`--tools ""`, `--strict-mcp-config`, `--setting-sources ""`, `--max-turns 1`, `--system-prompt-file`, `--json-schema` |full (M7)
|`codex` |`-c developer_instructions`, `-c mcp_servers.pm.*` with `required=true`, `--output-schema`, `--ephemeral`, `--cd` |sandbox `read-only` |no hard zero-tool: `features.shell_tool=false`, web search off, no MCP, isolated cwd |worker and read-only; screener only if M1 shows no tool remains (M13)

== Decision items

Items are ordered so that each depends only on earlier ones. Every item names the principle that decides it and what the server checks.

[#z7-1]
=== Z7-1 Launch contract per harness

* *Question*: How does the server compose a model job's command line per harness (inline named agent or per-call flags), where does the template live, and what happens on a harness that lacks a capability (Antigravity, Gemini CLI) or on a neutral or unknown host (Z6-24 blocks vs an inline fallback)?

=== Z7-2 Job-bound capability and connection classification

* *Question*: How does a headless run connect back to the daemon, how is its connection bound to its job (scope, entity, allowed tools and links), and how are job connections kept out of session rows and client identity checks without the runtime token entering the job?
* *Evidence*: G8, G9. The daemon listens on a Unix socket and requires the runtime token on every request (RTM:156-164); jobs cannot read `<PM_MCP_BASE>`, where the token lives, and never receive it in argv or environment (JR02:24); the runtime is stateless per request (REQ01:59, RTM:269); a new `PM-MCP-Client-Session` appends a session row and may hand over the client (SS01:84; REQ13:11-15); the entity is asserted only by arguments (MT01:139). Claude, Codex and OpenCode accept a per-call MCP server started as a local command with its own environment.
* *Options*:
** (a) *Job token through a job relay*: at spawn the server mints a random 256-bit job token (stored as SHA-256 in the job record, valid only while the job runs, revoked with its fate). The job's MCP configuration starts `pm-mcp serve --job` with the token in `PM_MCP_JOB_TOKEN`; the relay sends it as `PM-MCP-Job-Token` instead of the runtime token, and the daemon accepts it on `/mcp` only. Per request the server resolves the job and enforces: the scope and entity arguments must equal the job's (else `job_scope_mismatch`); `tools/list` and calls are limited to the role's tool set (`pm_state`, `pm_do`, `pm_build`, `pm_lsp`, `pm_skill`, `pm_skill_file`; never scope-creating or operator actions); `pm_do` admits only links of the job's entity and never a link that starts a model job (leaf rule, PM-WF-5). A job connection appends no session row, triggers no client handover and takes its client profile from the job record; audit rows carry the `job_id`. The harness-side allowlist (`--allowedTools`, `enabled_tools`) is added as defence in depth.
** (b) *Runtime token plus harness allowlist only*: no daemon change, but a job could address any scope and would be classified as a new host session (G8); the runtime token would enter the job.
** (c) *A loopback HTTP listener for jobs*: contradicts the Unix-socket-only transport (PM-SEC-4).
* *Recommendation*: (a). The binding is server-enforced per request (stateless: the token is looked up, no connection state) and dies with the job. M1 verifies that a Landlock-confined job can connect to the socket path (Landlock filesystem rules do not govern `connect(2)` on pathname sockets up to the verified ABI; to be confirmed) and that each harness passes the environment to its local MCP command.
* *Affected*: RTM § Connection Metadata (header `PM-MCP-Job-Token`), § Local Trust; CS01 (`pm-mcp serve --job`); MT01 (entity binding, `job_scope_mismatch`); SS01:84 (no session row for job connections); SS10 (job token digest, `connected_at`); `identifiers/*` (reason); REQ13 PM-CLIENT-1; REQ08 PM-SEC-3, PM-SEC-4; PM-ARCH-8.
* *Decision*: Operator 2026-09-30: (a): per-job 256-bit token (SHA-256 in the job record, valid while the job runs) passed to pm-mcp serve --job, header PM-MCP-Job-Token; per request scope/entity binding (job_scope_mismatch), role tool set, entity links only, never a model-job-starting link; no session row, no client handover, audit rows carry job_id; harness allowlist as defence in depth; M1 verifies socket connect under Landlock and environment passing per harness.
* *Adjusted by round-4 RD1 (2026-10-01)*: decided by the reviewer under the operator's delegation (at least 95% confidence): the tool set depends on the job class: `read_only` jobs get `pm_state`, `pm_do`, `pm_skill`, `pm_skill_file` and the read operations of `pm_lsp`; `pm_build` and `pm_lsp` `rename` are writer-only.
