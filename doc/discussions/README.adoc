This directory holds the analyses, research and variants behind the concept. The decisions themselves live in the concept documents one level up; nothing here is part of the target design unless a concept document adopts it.

Research documents reflect a point-in-time view of external projects and specifications. Recheck their sources before relying on them.

== Analyses and research

* xref:mcp-skills-extension.adoc[MCP Skills Extension] — analysis of SEP-2640 and what it does and does not provide.
* xref:skills-host-support.adoc[Skills Host Support] — support status of the Skills extension in Claude Code, OpenCode and Antigravity.
* xref:technology-evaluation.adoc[Technology Evaluation] — Quarkus MCP Server assessment, official SDK comparison, Python runtime options.
* xref:execution-patterns.adoc[Execution Patterns] — how comparable tools place coordination and execution, and how they handle builds that start containers.
* xref:container-build-measurements.adoc[Container Build Measurements] — cost of a fresh container per build.
* xref:local-endpoint-authentication.adoc[Local Endpoint Authentication] — _superseded 2026-09-28 by xref:client-architecture.adoc[Client Architecture]_ (Unix socket with runtime token file, web access through the separate `pm-mcp-web`); what a credential on the loopback endpoint protects; cookie file instead of signed tokens; TokenSheriff for later.
* xref:store-and-config-model.adoc[Store and Configuration Model] — clean-slate proposal for configuration files, store inventory, versioning without a migration chain before 1.0, import mapping, lesson and entry records; decisions Z3-1 to Z3-19 decided 2026-09-28; import withdrawn.
* xref:git-provider-modules.adoc[Git and Provider Modules] — native in-process git, GitHub and GitLab implementations with an agent identity as default and the CLIs as operator variant; module structure (`pm-mcp-providers` with `pm-mcp-git`, `pm-mcp-ci`, `pm-mcp-github`, `pm-mcp-gitlab`), library evaluation, credential model, resolution of the open git/GitHub/GitLab design topic; decisions Z2-1 to Z2-34 decided 2026-09-28 and applied to the specifications.
* xref:client-architecture.adoc[Client Architecture] — local adapter trusting same-user clients over a Unix socket with a runtime token file, separate native CLI binary (`pm-mcp-clients/pm-mcp-cli`), web adapter with one-time-code pairing and device bearer tokens, SvelteKit web app, web server as separate client process, OAuth seam; decisions Z1-1 to Z1-21 decided 2026-09-28.
* xref:workflow-consistency.adoc[Workflow Consistency] — completing the workflow model on paper before implementation under a self-enforcing process (no in-run operator decisions; bounded self-remedy through remediation policies as DSL sub-workflows; operator waivers; defined fallbacks `handed_back` / `returned`; integrity breaches as the only pause): waiver record and gate identifiers, fallback routes, policy calls and evidence, DSL rule semantics, routing of every open Phase 1–5, setup, epic and entity marker, and the finalize, land, merge-path and post-run gaps; plan instance per plan (Z5-D) and question records (Z5-E); decided Z5-0, Z5-A to Z5-E, Z5-1 to Z5-66 and post-apply follow-ups F1–F7 (2026-09-29); team overrides deferred to L-5. _Decided 2026-09-29._
* xref:plan-bootstrap.adoc[Plan Bootstrap] — every way a plan or epic comes into existence modelled as one server-side process: entry command arguments in the pending entry record, bootstrap sub-workflows per scope kind with source sub-workflow units (`pm_start` removed, Z6-A), two-level guard for external text (deterministic validator plus a zero-tool LLM screener run as a harness-CLI job, Z6-B), epic-emitted plans as source `epic_row`, epic creation and intake (`epic.define`, `epic.decompose`), lesson maintenance; legacy inventory, absorbs review points D8, D9, D10, D24, D51; decided Z6-A, Z6-B, Z6-1 to Z6-25 (2026-09-29).
* xref:server-launched-agents.adoc[Server-Launched Sub-Agents] — every sub-agent as a server-launched harness-CLI job instead of a host dispatch (Z7-0 decided): launch contract per harness from the client profile (inline named agent or per-call flags), job-bound capability for the MCP connection back, job kind `llm` confinement and enrolment, model slots, dispatch lifecycle mapped onto job records, skills and contract envelope, batched screening and triage, effort resolution without agent variants, parsed usage, role table cleanup, epic job states, working directory and screener isolation; legacy execution-context, PM-MCP dispatch and harness CLI inventories. _Decided (2026-09-30)._
* xref:control-direction.adoc[Control Direction] — _analysis, undecided_: whether the server should drive the interior of plans and epics by calling the harness instead of depending on a live session (four options, the operator leans to the server-driven interior), warm sessions that pull their next task against a fresh job per decision, the verifications V1 to V10 that must come first (stability of the wait and pull mechanism, cold-start and idle cost, carry-over between tasks), and the decision gate after Roadmap Milestone 0.
