== Purpose

This runbook covers the Linux half of link:../roadmap.adoc[Roadmap] Milestone 0, Part B (technical verifications): every item that runs only on Linux (Landlock, Secret Service), and every item that must hold on both platforms (native image, on-demand start, web listener, the `PM-TECH-3` bounds). The macOS half is link:technical_macos.adoc[Technical Verifications on macOS]. Each item checks a technique against a gate of the link:../Requirements.adoc#_appendix_verification_gates_risk_register_non_normative[Requirements, Appendix: Verification Gates & Risk Register]. The technique is built in its target module, so a result applies to the product code.

The document is self-contained. A Claude Code session on the Linux machine can run it from top to bottom without any other context.

=== Rules

* *Pass criteria are fixed.* Every item states its pass criterion below, set before the first run. Never edit a pass criterion after a run. If a criterion turns out to be wrong, record that as a finding in the item's result.
* *Branch.* Work on `feature/m0-part-b-linux`, created from `main`. Write results only into this document, in the item's *Result* block, its *Status* line, and <<setup-record>>. A procedure step that proves unusable is corrected in place after the run and named as a finding in the item's result.
* *Code changes.* Code may change only in the Linux-specific classes, and every change comes with a test:
** `pm-modules/pm-exec` (Landlock), `pm-mcp-server/.../credentials/dbus` and `SecretServiceStore` (Secret Service);
** the Linux branches of `pm-modules/pm-api/.../posix` (spawn);
** the epoll native-image metadata under `pm-mcp-server/src/main/native-linux/` (<<native-transport-linux>>).
+
A failure elsewhere is recorded as a finding and is not fixed here; the macOS side owns that code.
* *Builds and tests.* Use Maven and JUnit only. `.plan/execute-script.py` is not tracked, so use `./mvnw` with the arguments given here. Never run `javac` directly, and never write ad-hoc verifier programs; a shell sequence written out in an item is allowed. Analyse a failing build and never work around it.
* *Figures.* Every verification IT writes its measured figures to `<module>/target/verification-results/<item>.json`. Copy the figures into the result table and name the file.
* *Fallbacks.* A failed item records the fallback its gate names (quoted in the item) and does not apply it in code. The consolidation on the macOS side decides and applies it.
* *Handback.* At the end: commit, push `feature/m0-part-b-linux`, and open one PR against `main`, titled `docs: Part B technical verifications on Linux`. Do not merge it.

=== Keyring Session (gate 5)

On a desktop session the keyring already runs; record which one it is. On a headless machine, start a session bus and an unlocked keyring for the run. Isolate it first: set a private, short `XDG_DATA_HOME` and `XDG_RUNTIME_DIR` *before* `dbus-run-session`, so that the bus and the D-Bus-activated keyring never open the user's own keyrings with the test password. Keep the directory short: the keyring's control socket `<XDG_RUNTIME_DIR>/keyring/control` must fit the 108-byte `sun_path`.

[source,bash]
----
mkdir -p ~/.pmkr/data ~/.pmkr/run && chmod 700 ~/.pmkr/run
export XDG_DATA_HOME=~/.pmkr/data XDG_RUNTIME_DIR=~/.pmkr/run
dbus-run-session -- bash        # every gate-5 step runs inside this shell
echo -n "pm-test-keyring" | gnome-keyring-daemon --daemonize --unlock --components=secrets
echo "$DBUS_SESSION_BUS_ADDRESS"   # must be unix:path=..., an abstract address is not usable (L8)
secret-tool store --label=probe service probe key probe <<< "x" && secret-tool lookup service probe key probe
----

If `DBUS_SESSION_BUS_ADDRESS` names an abstract socket (`unix:abstract=...`), that is itself a finding for L8: the JDK cannot connect to an abstract socket. Record it, and start `dbus-daemon --session --address=unix:path=$XDG_RUNTIME_DIR/bus --fork` to continue.

[#native-transport-linux]
=== Native Transport Metadata for Linux (prerequisite of the native daemon)

Vert.x binds the Unix socket only through the Netty native transport (`epoll` on Linux, `kqueue` on macOS). In a native image, Quarkus replaces the transport lookup with the JDK transport. `pm-mcp-server` therefore offers the transport itself (`de.cuioss.pm.mcp.server.runtime.NativeTransport`, a Vert.x `Transport` service). The transport also needs the JNI and resource metadata of its native library. For macOS this metadata is `pm-mcp-server/src/main/native-macos/META-INF/native-image/de.cuioss/pm-mcp-server-macos/reachability-metadata.json`. The Linux equivalent does not exist yet and is the first task of this run:

. Build the JVM runner: `./mvnw package -pl pm-mcp-server -am -DskipTests`.
. Run it once under the tracing agent with a short base. Exercise the socket: `GET /api/v1/status`, a few SSE events, then `POST /api/v1/runtime/stop`, all with `curl --unix-socket "$PM_MCP_BASE/run/runtime.sock" -H "Authorization: Bearer $(cat $PM_MCP_BASE/run/runtime.token)" http://localhost/...`:
+
[source,bash]
----
export PM_MCP_BASE=$HOME/.pmt && mkdir -p /tmp/agent-out
java -agentlib:native-image-agent=config-output-dir=/tmp/agent-out -jar pm-mcp-server/target/quarkus-app/quarkus-run.jar
----
+
. From the agent output, keep only the entries for `io.netty.channel.epoll.*`, `io.netty.channel.unix.*`, `io.netty.channel.ChannelException`, `io.netty.channel.DefaultFileRegion`, `io.vertx.core.impl.transports.EpollTransport`, and the `META-INF/native/libnetty_transport_native_epoll_*.so` resources. The macOS file shows the shape and the kind of entries to keep. Write the result to `pm-mcp-server/src/main/native-linux/META-INF/native-image/de.cuioss/pm-mcp-server-linux/reachability-metadata.json`.
. Build natively and run `DaemonStartupIT` (L1). Iterate until the native daemon binds its socket.

The ITs stage `libnetty_transport_native_epoll_<arch>.so` beside the native runner, as the release layout will. Without it beside the binary, Netty extracts the library into the temporary directory on every start, which costs about 250 ms on macOS and puts executed native code in `/tmp`. Record in L2 whether the same holds on Linux.

A single module and its ITs run as `./mvnw verify -Pnative,integration-tests -pl <module> -am`. Record the binary sizes and the native build durations in L2.

A *staged installation* for manual steps: copy the four binaries into one `bin/` directory under their release names `pm-mcp`, `pm-operator`, `pm-exec` and `pm-mcpd`, and export `PM_MCP_HOME` as its parent. Use a short `PM_MCP_BASE`, for example `export PM_MCP_BASE=$HOME/.pmv`, so that the socket path fits `sun_path`.

== Items

Every item has the same blocks: what it verifies, the fixed pass criterion, the procedure, the fallback if it fails, and the result.

=== L1: Local Adapter under Native Image (gate 1)

*Verifies*: roadmap Part B, item "local adapter under native image". `pm-mcpd` serves MCP and `/api/v1` on its Unix socket with runtime-token authentication and unbuffered SSE. It handles a stale socket under the singleton lock and refuses to start when the socket path exceeds the Linux `sun_path` limit of 108 bytes. `cui-http` and `commonmark` are part of the same native build. See link:../specification/runtime-model.adoc[Runtime & Interaction Model Specification].

*Pass criterion*: all of the following hold for the native binary:

. The socket has mode `0600` in a `0700` `run/`.
. A request without the token, or with a wrong one, gets `401`.
. The first SSE event arrives before the stream ends.
. A second runtime exits `0` and leaves `<PM_MCP_BASE>` byte-identical.
. After a `kill -9` the next start removes the stale socket and serves.
. A base whose socket path exceeds 108 bytes exits `77` and writes no token and no socket.
. The ingestion validator (which uses `commonmark` and `cui-http`) works in the native binary.

*Procedure*: `./mvnw verify -Pnative,integration-tests -pl pm-mcp-server -am`, which runs the daemon ITs listed in <<daemon-its>> against the native runner.

*Fallback (gate 1)*: listener fallback (1) is loopback `127.0.0.1` with the runtime token and `Host`/`Origin` validation. Fallback (2) is an own JDK `UnixDomainSocketAddress` channel bridging to the Quarkus router. Otherwise: explicit reachability metadata, or replace the incompatible library.

*Result*:

|Check |Figure / evidence |Pass

|401 without / with wrong token |`DaemonStartupIT` native, passed |yes
|Unbuffered SSE |first event after 314 ms, before the stream ends (`gate1-sse-unbuffered.json`) |yes

=== L4: Detached On-Demand Start (gate 8)

*Verifies*: `pm-mcp` and `pm-operator` start `pm-mcpd` through FFM `posix_spawn` with `POSIX_SPAWN_SETSID` (glibc value `0x80`, glibc ≥ 2.26). The descriptors of the child are closed with `posix_spawn_file_actions_addclosefrom_np` (glibc ≥ 2.34). A termination of the relay by the host never reaches the runtime.

*Pass criterion*: all of the following, for the native binaries:

* The started daemon's process-group id and session id equal its pid.
* Its `stdin` is `/dev/null`, and `stdout`/`stderr` are appended to `logs/daemon.log`.
* After `kill -9` of the relay, and after `kill -HUP` of the relay's process group, the daemon still answers `GET /api/v1/status`.
* No zombie of the relay's children remains.

*Procedure*:

. Run the gate 8 tests of `PmMcpProcessIT` and `PmOperatorProcessIT` (L3 run).
. Manually, with a staged installation:
+
[source,bash]
----
INIT='{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"l4","version":"1"}}}'
relay() {   # a relay in its own session; the initialize request starts the runtime, the open stdin keeps the relay alive
  setsid bash -c "(echo '$INIT'; sleep 60) | \$PM_MCP_HOME/bin/pm-mcp serve --client neutral" > /dev/null 2>&1 &
  sleep 2; pgrep -n -f "pm-mcp serve --client neutral"
}
r=$(relay); pid=$(jq .pid $PM_MCP_BASE/state/runtime.json)
ps -o pid,ppid,pgid,sid,stat,cmd -p $pid,$r
ls -l /proc/$pid/fd/0 /proc/$pid/fd/1 /proc/$pid/fd/2; grep flags /proc/$pid/fdinfo/1
kill -9 $r; sleep 1; $PM_MCP_HOME/bin/pm-operator status
r=$(relay); kill -HUP -- -$(ps -o pgid= -p $r | tr -d ' '); sleep 1
$PM_MCP_HOME/bin/pm-operator status
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'   # no zombie
----

*Fallback (gate 8)*: on a failing platform the starting binary reports the failure and names `pm-operator runtime install`, and the per-user `systemd --user` service serves that platform. On-demand start stays the default wherever it works.

*Result*:

|===
|Check |Evidence |Pass
|pid = pgid = sid of the daemon |manual: daemon pid = pgid = sid `4017689`, relay in its own session `4017681`; after the relay's end the daemon's parent is pid 1. ITs: `gate8-detached-start-pm-mcp-native.json`, `gate8-detached-start-pm-operator-native.json` (pid = pgid, survived) |yes

Finding on the procedure (corrected above after the run): the sequence first given, `setsid bash -c 'echo "" | $PM_MCP_HOME/bin/pm-mcp serve --client neutral & …'`, starts no runtime. The run used the sequence now in the procedure: an `initialize` request with `stdin` held open, which starts the runtime and keeps the relay alive for the `kill -9` and the group `SIGHUP`.

=== L6: LSP4J and JGit under Native Image (gate 2, `PM-TECH-2`)

Findings (the pass criterion above is met; it does not cover delegation of work to a process outside the job's Landlock domain):

* *F1, unconfined build daemon escapes the write set.* A Landlock domain confines a process and its descendants, not the processes it talks to. An mvnd or Gradle daemon started outside confinement (`NoNewPrivs: 0`) serves a later confined client over its loopback TCP connection and writes wherever the client asks. * *F2, confined build daemon carries the first job's ruleset.* The reverse direction: a daemon started under confinement inherits the starting job's domain for its lifetime. A daemon shared across jobs therefore needs the same per-job daemon store as F1.
* *F3, the Docker socket bypasses the read set.* Under `--deny-read $PM_MCP_BASE`, `cat $PM_MCP_BASE/run/runtime.token` is denied, but `docker run -v $PM_MCP_BASE/run:/b:ro alpine:3 wc -c /b/runtime.token` through the same `pm-exec` printed `43` (the token length; the token itself was not printed). Testcontainers and Compose (gate 3) need that socket; whether such jobs are admitted, and under which enrolment, is a decision for the macOS side.

=== L15: Session Bus under Confinement (gate 5, `PM-SEC-5`)

*Verifies*: whether a confined job can reach the user's D-Bus session bus, and with it the Secret Service of gate 5. A job is to be cut off from the session bus: its environment carries no `DBUS_SESSION_BUS_ADDRESS`, and its read set does not cover `$XDG_RUNTIME_DIR/bus`. Dropping the variable alone is not enough, because libdbus and GDBus fall back to `$XDG_RUNTIME_DIR/bus` when it is unset. By the kernel documentation (`Documentation/userspace-api/landlock.rst`, § Pathname UNIX sockets), Landlock governs `connect(2)` to a pathname Unix socket only from ABI 9 (`LANDLOCK_ACCESS_FS_RESOLVE_UNIX`); ABI 6 scopes abstract sockets only, so up to ABI 8 a confined job reaches every pathname socket whose path it knows, `/var/run/docker.sock` included (L9, finding F3). From ABI 9 `pm-exec` handles that right: the read and write sets grant it, so a socket outside both is refused with `EACCES`. The relay's runtime socket lies below `<PM_MCP_BASE>`, outside the read set, so the launchers (`WorkerLauncher`, `JobChainIT`) grant it with `--read <PM_MCP_BASE>/run/runtime.sock`. `pm-exec` records the applied ABI in its launch report (`landlock_abi`).

*Pass criterion*:

. `PmExecIT` passes natively, the session-bus check of its `Landlock` group included (`gate3-pm-exec-linux-native.json`):
** `session_bus_env_dropped` is true: the job environment built from an operator environment with `DBUS_SESSION_BUS_ADDRESS` reaches the job without it;
** `runtime_socket_read_rule_connect` is true: a socket under a `--read` rule below the denied base, and a socket in the write set, accept the job's connect;
** `session_bus_connect_denied` is true (refused with `Permission denied`) when `session_bus_landlock_abi` is 9 or higher, and false (the connect succeeds) below 9.
. On the user's real session bus `/run/user/<uid>/bus`, steps b and c below are refused when `pm-exec --probe` reports ABI 9 or higher. Below ABI 9 the outcomes of a to c are recorded.

*Procedure*:

+

----

Options for all three:

* `-Dspike.model=<model>` (for example `claude-haiku-4-5`; for OpenCode the model of Part A's setup record or a current free model);
* `-Dspike.layout=auto|native|jvm`;
* `-Dspike.wait-s=20`, `-Dspike.grace-s=30`, `-Dspike.stop-short-s=16`, `-Dspike.stop-long-s=70`, `-Dspike.exit-detect-max-ms=1500`;
* `-Dspike.write-extra=<paths>` (extra writable paths for the harness under Landlock);
* `-Dspike.opencode.shared-data=true` (OpenCode only: the shared `~/.local/share/opencode` and the write set of L10 instead of a data directory per worker, L14).

The logs of every run (`events.jsonl`, `supervisor.jsonl`, `harness-*.jsonl`, `daemon.log`, `trials.json`, `result.json`) go to `pm-modules/pm-e2e/target/spike-runs/<name>-<stamp>/`. Keep them for the result.

Known points to watch on the first Linux run:

* Claude Code rewrites `~/.claude.json` atomically, which may need write access to `$HOME` itself. Record what is needed and widen it with `-Dspike.write-extra` (this is the writable-paths finding of L10).
* The Codex flags (`codex exec --json`, `-c mcp_servers.…`, `--output-schema`) are taken from documentation and have not been run. Expect adjustments, which are allowed in `de.cuioss.pm.e2e.spike`.
* That OpenCode passes its environment on to the `stdio` MCP server (job token) is unverified.
* The turn-end prompt is new; Part A's was not archived.
