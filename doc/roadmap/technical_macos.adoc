=== M1: Local Adapter under Native Image (gate 1)

*Pass criterion*: as link:technical_linux.adoc#_l1_local_adapter_under_native_image_gate_1[L1], with the macOS `sun_path` limit of 104 bytes and the `kqueue` transport.

*Result* _(measured during implementation)_:

* `DaemonStartupIT`, `McpSurfaceIT` and `HelloToolIT` pass against the native `pm-mcpd` and the JVM runner.
* Findings:
** Vert.x creates the socket under the process `umask` (mode `0755`). The runtime restricts it to `0600` right after the bind and verifies it, before `runtime.json` is written.
** `StartupEvent` observers run before the HTTP server binds.
** Quarkus 3.39 replaces the native transport by the JDK transport in a native image. `pm-mcpd` offers kqueue/epoll itself as a Vert.x `Transport` service, with JNI metadata from the tracing agent.
** Authentication needs the `quarkus-security` extension: without it, the mechanism and the identity providers are inert.

*Status*: `[~]` (repeat after the merge)

=== M6: Keychain via FFM from the Native Binary (gate 4)

*Pass criterion*:

* The native `pm-mcpd` puts, gets, replaces and deletes a generic-password item of the login keychain through FFM `SecItem*` (`KeyringIT`).
* The item's ACL trusts only `pm-mcpd`: another reader triggers an OS prompt.

*Result* _(measured during implementation)_:

* `KeyringIT` passes on the runner JAR and the native `pm-mcpd`. Native put / get / delete take 40.5 / 2.8 / 16.0 ms.
* The default ACL of the login keychain already trusts exactly the creating binary, so the legacy `SecAccess`/`SecTrustedApplication` APIs are not needed.
* For an ad-hoc-signed build the ACL is pinned to the binary's code-directory hash (`cdhash`, `partition_id cdhash:…`). A rebuild or upgrade therefore loses unprompted access to its items. Stable trust needs `pm-mcpd` signed with a stable Developer ID (team ID).
* The data-protection keychain has no per-application ACL and refuses an unentitled binary (`errSecMissingEntitlement`, -34018).

*Finding*: the trust part of `PM-CRED-2` holds only for a release signed with a stable identity. It goes to consolidation as a correction candidate (signing requirement for macOS releases).

*Status*: `[~]` (the prompt for a second reader is still to be observed)

=== M8: Sessionless Streamable HTTP (gate 10)

*Pass criterion*:

* On `quarkus-mcp-server` 2.0.2, the runtime issues no `Mcp-Session-Id` and serves requests that arrive without a prior `initialize`.
* It answers `server/discover` (MCP `2026-07-28`) and `initialize` (`2025-11-25`).
* The `PM-MCP-*` headers reach a tool handler through the security identity.
* Progress and elicitation arrive on the call's own response stream.

*Result* _(measured during implementation, `McpSurfaceIT`)_:

* MCP `2026-07-28` is served sessionless: `server/discover`, with the protocol data in `_meta` of every request. `server/discover` without `_meta` is refused with `400`.
* `initialize` (`2025-11-25`) always issues `Mcp-Session-Id` in 2.0.2. A filter strips it, and later requests without a session are served through `quarkus.mcp.server.http.streamable.auto-init`.
* The `PM-MCP-*` headers reach a tool handler through the security identity, read through the current request (`CurrentVertxRequest`). The `params._meta` fallback is not needed.
* Progress notifications arrive on the call's SSE stream.
* Elicitation in `2026-07-28` is no server-initiated request: it is an `input_required` result answered by a retry with `inputResponses`. This contradicts `runtime-model/03-relay.adoc` (messages from runtime to host) and is a correction candidate.

*Host run* (2026-10-06): `McpSurfaceIT` passes against the native runner (4 of 4).

*How the daemon answers `subscriptions/listen`*, recorded from real host traffic:

* `server/discover` advertises `capabilities.tools.listChanged: true`.
* `subscriptions/listen` (from Claude Code and Antigravity) is acknowledged at once with `notifications/subscriptions/acknowledged`. The stream then stays open for the whole session without a final response.
* This contradicts `runtime-model/03-relay.adoc` (no `list_changed`, no messages unrelated to a pending call) and `PM-SKILL-2`.
* `quarkus-mcp-server` 2.0.2 has no setting to turn either off.

*What Claude Code does with the alternatives* (spike filter `pm.spike.listen`):

* Unanswered: Claude Code blocks its startup for 27 s, then cancels the listen request and continues.
* Refused with `-32601`, or ended at once with an empty result: `tools/list` follows immediately. Claude Code retries the listen three times (+1, +3, +7 s), then stops. All tools work.

*Correction candidate*: the runtime refuses `subscriptions/listen` with `-32601` and does not advertise `tools.listChanged`. Whether hosts then skip the listen entirely is untested. The refuse and ignore runs used the JVM layout.

*Status*: `[~]` (pass; the `listChanged` correction is open)

*Result* _(measured during implementation)_:

* *Claude Code*:

* *Antigravity*:

** Plugin skills under `~/.gemini/config/plugins/<name>/skills`.
** `ANTIGRAVITY_AGENT` and `ANTIGRAVITY_CONVERSATION_ID`, from the binary's strings only.
* *Model source*: `declared` for all four hosts; no host puts the model into the environment.

*Corrected*:

. Antigravity has a project-scope MCP configuration, `.agents/mcp_config.json`.
. Antigravity has a version probe: `agy --version` prints the version and exits `0`.
. Codex `clientInfo.name` is `codex-mcp-client`, not `codex`.
. Codex passes only a fixed list of variables to MCP servers (`HOME`, `PATH`, `SHELL`, `USER`, `LANG`, `TERM`, and a few more). Its markers (`CODEX_THREAD_ID`, `CODEX_CI=1`, and `CODEX_SANDBOX=seatbelt` when sandboxed) never reach `pm-mcp serve`; only `pm-mcp enter`, run through the shell tool, sees them. . `version_pattern` values, which the table lacked:
** claude `^(\d+\.\d+\.\d+) \(Claude Code\)$`
** opencode and agy `^(\d+\.\d+\.\d+)\s*$`
** codex `^codex-cli (\S+)\s*$`

* Neither host clears the other's markers.
* OpenCode inside Claude Code is attributed correctly by the fixed precedence.
* Claude Code inside OpenCode is wrongly attributed to `opencode`. Proposal: match `CLAUDE_PID` or `OPENCODE_PID` against the nearest parent process.

*`AI_AGENT`*: only Claude Code sets it (`claude-code_2-1-291_agent`, overwriting an inherited value). Proposal: map the prefix before the first `_` or `@`, as a secondary signal only, because an inherited value survives into a host started inside Claude Code.

*Further findings*:

* `.agents/skills` is read by Codex, Antigravity and OpenCode, and OpenCode also reads `.claude/skills`. One shim skill is therefore visible to several hosts.
* The model `space-bunny-free` is gone from `opencode models`, but `worker.restricted_models` still lists it.

* A live Antigravity run with the logging server, to record its child variables and `clientInfo.name` on the wire. The binary suggests `antigravity-client`. The headless run (`agy -p` with skipped permissions) was refused by the permission classifier of this session and not retried.

*Status*: `[~]` (corrections go to consolidation; the Antigravity live check is open)

*Pass criteria*:

*Fixtures* (set up 2026-10-06):

* GitHub: the repository `cuioss/pm-mcp-fixture` (public). It has a trivial `ci` workflow on `push`, `pull_request` and `merge_group`. The org-wide review bots CodeRabbit, Sourcery and `cuioss-review-bot` cover it.
* GitHub App: `pm-mcp-fixture-agent` (App ID 5208102), installed on that repository only with the seven repository permissions of the specification: `contents: write`, `pull_requests: write`, `issues: write`, `checks: read`, `actions: read`, `statuses: read`, `metadata: read`. Its key and identifiers are in the operator's `~/.config/pm-mcp-fixture/`, outside the repository.
* GitLab: the project `cuioss/pm-mcp-fixture` (public), with a trivial pipeline. The token is taken from the operator's `glab` login.

*Result* (2026-10-06, `FixtureGitHubIT` and `FixtureGitLabIT`, opt-in with `-Dspike.fixture`, each run twice with identical results; evidence in `target/verification-results/m16`–`m21*.json`):

*M17: fail.* The App opened the pull requests (`pm-mcp-fixture-agent[bot]`) and posted `@coderabbitai review` under its own identity; the wait was bounded at 15 min.

* CodeRabbit answered only with a skip notice ("Review skipped … Bot user detected"), within 9 s of the pull request opening, and never answered the App's trigger.
* Sourcery reviewed on its own about 40 s after opening, which is review on push.
* `cuioss-review-bot` stayed silent.
