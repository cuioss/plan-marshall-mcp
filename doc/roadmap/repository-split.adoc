== Purpose

This is the working plan for the first part of link:../roadmap.adoc[Roadmap] Milestone 1: the renaming to
`de.planmarshall`, the module `pm-runtime`, and the split of the one repository `plan-marshall/plan-marshall-mcp` into
the repositories of link:../specification/module-structure.adoc#repositories[Module Structure § Repositories]. It is
written so that a Claude Code session can execute it with no other context than this repository. The specification
states the target; this document states the order, the commands, the checks, and what the operator must do by hand. It
is deleted when its last step is done, and the roadmap items it covers are ticked as their steps land.

== Read First

* `CLAUDE.md` of this repository: build commands, code standards, the git workflow, and the publishing rule.
* link:../specification/module-structure.adoc[Module Structure Specification]: sections _Repositories_,
  _Model-Facing Content_, _Artifact Flow_, _Modules_ (row `pm-runtime`), and _Dependency Rules_.
* link:../implementation-watch/module-structure.adoc[Module Structure Implementation Watch]: all six items;
  `PM-WATCH-MOD-5` and `PM-WATCH-MOD-6` are guards this plan builds.
* link:publishing.adoc[Publishing and Licensing State].
* The setup scripts and documents of `cuioss/cuioss-organization` (`repo-settings/`, `branch-protection/`,
  `.github/project.yml`, `docs/`): every new repository is set up with them.

== Rules

. *One registry.* Artifacts are deployed to `https://maven.pkg.github.com/plan-marshall/<repository>` and nowhere else.
  Never Maven Central, never another registry, never a credential of one in any workflow.
. *Visibility.* All five repositories are public during this plan. `plan-marshall-mcp` stays public for the first
  iterations; it is switched to private in Milestone 7, before the first model-facing content is committed.
  `plan-marshall-documentation` is switched to private when the documentation has settled. No step of this plan
  changes the visibility of a repository other than the throwaway repository of <<step-registry>>.
. *No model-facing content in a public artifact.* The library repositories never receive a workflow unit, a role
  artifact, a skill, or a bundle, not as a test fixture copied from real content either.
. *`SNAPSHOT` only.* `pm-mcp-clients` and `pm-mcp-core` deploy `SNAPSHOT` versions and are never released. Only
  `pm-mcp-parent` is released.
. *History is kept.* Modules and documents move with their git history (`git filter-repo` on a fresh clone); nothing is
  copied as a new initial commit.
. *Green before the next cut.* A step is done when every code repository it touched is green on `main` (the
  documentation repository has no build; its check is the review of <<repository-setup>>): `verify`,
  `verify -Ppre-commit` (review and commit its rewrites), `verify -Pcoverage`, `verify -Pintegration-tests`, and
  locally `verify -Pnative,integration-tests`. The code is removed from `plan-marshall-mcp` only after its new
  repository has deployed a `SNAPSHOT` and `plan-marshall-mcp` builds against that `SNAPSHOT`.
. *Workflow.* Every change is a pull request through the merge queue with all review comments answered and resolved, as
  `CLAUDE.md` states. No auto-merge and no merge without the operator's word. Commits end with
  `Co-Authored-By: plan-marshall <noreply@cuioss.de>`.
. *No new dependency* without asking the operator. `git filter-repo` is a tool on the machine, not a dependency.
. *Operator tasks.* Whatever needs organisation-admin rights, a secret, an App installation, or a setting of an
  external service is listed in <<operator-tasks>>. Ask for it when its step starts and continue with what does not
  depend on it; never work around a missing permission.

== Starting State

* One repository, public, `main` protected by the ruleset `main-branch-protection` with the merge queue.
* Root POM `de.cuioss:plan-marshall-mcp-parent:0.1.1-SNAPSHOT`, parent `de.cuioss:cui-quarkus-parent`.
* Modules: `pm-modules/{pm-api, pm-exec, pm-core, pm-providers/{pm-provider-git, pm-provider-ci, pm-provider-github,
  pm-provider-gitlab}, pm-e2e}`, `pm-clients/{pm-relay, pm-operator}`, `pm-mcp-server`.
* Java packages below `de.cuioss.pm`; the old names also occur in the automatic module names of the POMs, in the
  native-image metadata (`src/main/resources/META-INF/native-image/de.cuioss/<artifact>/`), in
  `pm-mcp-server/src/main/resources/META-INF/services/`, in `application.properties`, and in about twenty documents.
* Deployment is switched off (link:publishing.adoc[Publishing and Licensing State]).
* CI: reusable workflows of `cuioss/cuioss-organization`; SonarCloud project `plan-marshall_plan-marshall-mcp`; review
  by CodeRabbit, Sourcery, and `cuioss-review-bot`; release propagation into this repository through the App
  `plan-marshall-release-bot`.

== Steps

[#step-rename]
=== Step 1: Rename to `de.planmarshall`

One pull request in `plan-marshall-mcp`, before anything moves, so that no artifact is ever deployed under the old
coordinates.

. Group id `de.cuioss` -> `de.planmarshall` for the root POM, every module POM, and every reference to a PM-MCP module
  (`dependencyManagement`, dependencies, the `pom`-type dependencies of `pm-e2e`). The parent stays
  `de.cuioss:cui-quarkus-parent`, and the dependencies on `de.cuioss` libraries (`cui-java-tools`, `cui-http`, the test
  libraries) keep their group id.
. Root artifact `plan-marshall-mcp-parent` stays until <<step-parent>>.
. Java packages `de.cuioss.pm` -> `de.planmarshall` with `git mv` of the directories, so that history follows:
  `de.cuioss.pm.api` -> `de.planmarshall.api`, `de.cuioss.pm.mcp.server` -> `de.planmarshall.mcp.server`, and so on for
  every module. Update `package` and `import` statements, `package-info.java`, and every string that names a class
  or package.
. `maven.jar.plugin.automatic.module.name` of every module.
. Native-image metadata: move `META-INF/native-image/de.cuioss/<artifact>/` to
  `META-INF/native-image/de.planmarshall/<artifact>/` and rename the classes inside `reflect-config.json`,
  `reachability-metadata.json`, `native-image.properties`, and the like. Also `META-INF/services/*` (file names and
  contents), `application.properties`, and the `native` profiles of the POMs (main classes).
. Documents: every `de.cuioss.pm` and every path `de/cuioss/pm` in `doc/`, `CLAUDE.md`, `README.md`, and
  `.claude/skills/`.
  `doc/specification/module-structure.adoc` and `PM-IMPL-1` already name the new packages.
. `sonar` settings and workflow files, if they name a package or the group id.
. The product identifier `de.cuioss.pm-mcp` -> `de.planmarshall.mcp`: the keyring service name, the `_meta` key
  prefix (`de.planmarshall.mcp/source`, `de.planmarshall.mcp/sha256`), and the label of the per-user service
  (`de.planmarshall.mcpd`), in the code, the test fixtures, and the documents.

Check: `git grep -nE "de\.cuioss\.pm|de/cuioss/pm" -- ':!doc/roadmap/repository-split.adoc' ':!doc/roadmap.adoc'`
returns nothing (the two excluded documents describe the renaming); `git grep -n "<groupId>de.cuioss</groupId>"`
returns only the parent and the `de.cuioss` libraries; all builds of rule 6 are green, the native one included, because
a missed class name in the native-image metadata fails only there.

Roadmap: tick the renaming item of Milestone 1.

[#step-runtime]
=== Step 2: Module `pm-runtime`, in the one repository

One or more pull requests in `plan-marshall-mcp`. Doing this before the cut keeps the refactoring inside one reactor.

. Create `pm-modules/pm-runtime` (package `de.planmarshall.runtime`), depending on `pm-core`, on `pm-api` (the machine paths of the client contract), and on the libraries its
  code needs (`cui-http`, LSP4J, `commonmark`, Jackson, `cui-java-tools`), which are already managed in the root POM.
. Move every class of `pm-mcp-server` that references no Quarkus, CDI (`jakarta.*`), Vert.x, Netty, or MCP type, with
  its tests, by `git mv`. By package, as measured on the code of Milestone 0: `credentials` (18 of 20 files),
  `ingest` (1 of 1), `lsp` (3 of 3; the language client loses its Quarkus reflection annotation to an entry in the
  native-image metadata), `runtime` (6 of 10), `security` (4 of 11), `web` (4 of 6), and the root class. A class that mixes
  logic with a framework type is split: the logic moves, a thin CDI bean stays.
. `pm-mcp-server` produces the moved services through CDI `@Produces` (constructor injection, `@ApplicationScoped`).
. Move the native-image metadata that belongs to the moved classes (`pm-mcp-server-credentials`, the LSP4J part of
  `pm-mcp-server-lsp4j-jgit`) into `pm-runtime`.
. `LogRecord` constants of the moved classes follow the registry rule of `CLAUDE.md`; `doc/LogMessages.adoc` is updated.
. Add the architecture test of `PM-WATCH-MOD-6` to `pm-mcp-server`: it fails for a class that references no
  Quarkus, CDI, Vert.x, or MCP type and is not a record exchanged by such classes. Add its control (a fixture class
  that trips it).
. Follow the project skill `traced-implementation` for the documents this step touches.

Check: the architecture test passes; `pm-runtime` meets the coverage minimum on its own; `pm-mcpd` builds natively and
the integration tests pass against it.

Roadmap: tick the `pm-runtime` item of Milestone 1.

[#step-registry]
=== Step 3: Prove the Registry

On a throwaway repository `plan-marshall/pm-mcp-registry-probe` with a POM-only artifact `de.planmarshall:probe`. No
product code is involved. This is spike work: it stays on a branch and needs no pull request.

. Deploy a `SNAPSHOT` from a workflow with `GITHUB_TOKEN` and `packages: write`; deploy it again and confirm that a
  consumer resolves the newer one.
. Deploy a release version.
. Resolve both on this machine with the personal token of <<step-settings>>.
. Resolve both in a workflow of a _second_ repository of the organisation. Find out which token that needs
  (`GITHUB_TOKEN` with `packages: read` after the package grants the repository access, or a token of the App) and
  record the answer: it decides how every consumer's CI resolves.
. Switch the probe repository to private. Confirm that the package is private, that the personal token of an
  organisation member still resolves it, and that a GitHub account outside the organisation gets `401` or `404`.
. Record the results in link:../specification/evaluation.adoc[Evaluation Reference] as a new row, and correct
  link:../specification/module-structure.adoc#artifact-flow[Module Structure § Artifact Flow] where the registry behaves
  differently from what it states. Delete the probe repository and its packages.

Stop and ask the operator if the package does not turn private with its repository: the later switch of
`plan-marshall-mcp` rests on it.

Roadmap: tick the registry item of Milestone 1.

[#step-settings]
=== Step 4: Maven Settings

The parent POM is itself resolved from the registry, so the registry cannot be named in a POM. Every build resolves
through a `settings.xml` of the repository:

[source,xml]
----
<settings>
  <servers>
    <server>
      <id>plan-marshall</id>
      <username>${env.GITHUB_ACTOR}</username>
      <password>${env.GITHUB_TOKEN}</password>
    </server>
  </servers>
  <profiles>
    <profile>
      <id>plan-marshall</id>
      <repositories>
        <repository>
          <id>central</id>
          <url>https://repo.maven.apache.org/maven2</url>
          <snapshots><enabled>false</enabled></snapshots>
        </repository>
        <repository>
          <id>plan-marshall</id>
          <url>https://maven.pkg.github.com/plan-marshall/*</url>
          <releases><enabled>true</enabled></releases>
          <snapshots><enabled>true</enabled><updatePolicy>always</updatePolicy></snapshots>
        </repository>
      </repositories>
    </profile>
  </profiles>
  <activeProfiles><activeProfile>plan-marshall</activeProfile></activeProfiles>
</settings>
----

. Commit this file, without any token, as `.mvn/settings.xml` in every code repository and activate it as the
  *global* settings through `.mvn/maven.config` (`-gs ${session.rootDirectory}/.mvn/settings.xml`), so that `./mvnw`
  and the executor use it without an argument. As global settings it leaves the operator's `~/.m2/settings.xml` in
  force, which takes precedence; as user settings (`-s`) it would replace it. Maven Central is listed first, so that
  an artifact Central has is not looked up in the organisation registry.
. On a developer machine and in an agent worktree the token comes from the server `plan-marshall` of
  `~/.m2/settings.xml`, which replaces the server of the committed file. In CI no such entry exists, and the
  committed server reads the `GITHUB_TOKEN` of the workflow from the environment of the Maven step; <<step-registry>>
  found that token to resolve the packages of a public repository of the organisation without a grant (a private
  publishing repository needs another token, see
  link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-5[PM-WATCH-MOD-5]). The reusable workflows of
  `cuioss-organization` put the token into that environment only in the release that follows v0.37.0, switched on in
  `.github/project.yml` (<<open-items>>).
. Document the one-time setup in the developer documentation.

Roadmap: tick the settings item of Milestone 1.

[#step-parent]
=== Step 5: Repository `pm-mcp-parent`

. Create the repository (public) and set it up as <<repository-setup>> describes.
. The POM `de.planmarshall:pm-mcp-parent`, parent `de.cuioss:cui-quarkus-parent`, takes over from today's root POM
  what every repository shares: the Java release, the licence header and licence configuration, the `pre-commit`
  profile with its recipe list, the SonarCloud organisation, the managed versions of every third-party dependency with
  the import order of the Quarkus BOMs (`quarkus-bom` first), the plugin management of `native-maven-plugin` and of the
  coverage check, the `central-publishing-maven-plugin` skipped, and `distributionManagement` with repository and
  snapshot repository `plan-marshall` at `https://maven.pkg.github.com/plan-marshall/${pm.repository}`. `pm.repository`
  is a property the parent declares without a default; the root POM of each repository sets it to its repository name.
. Add the build check of `PM-WATCH-MOD-5` as an enforcer rule in the parent, so that every consumer inherits it: the
  build fails when `pm.repository` is unset or the effective deployment target is not
  `https://maven.pkg.github.com/plan-marshall/<repository>` with a resolved repository name.
. Release `1.0.0` to the registry through the release workflow of `cuioss-organization`, configured in
  `.github/project.yml` to deploy to the organisation registry only. Read that workflow first: if it can only release to
  Maven Central, do not use it; deploy with `./mvnw deploy` from a workflow of the repository and tell the operator
  what a change to `cuioss-organization` would have to add.
. In `plan-marshall-mcp`, switch the root POM to the new parent and delete from it what the parent now holds.

. Dependabot resolves the Maven dependencies outside the workflows and receives neither the `GITHUB_TOKEN` nor the
  Actions secrets. Find out on the real registry whether its update run of a repository that inherits the parent
  resolves it while the package is public, and which `registries` entry of `.github/dependabot.yml` and which
  Dependabot secret it needs. GitHub documents two ways: a `registries` entry of type `maven-repository` with a user
  name and a token from a Dependabot secret (without `replaces-base`, which would replace Maven Central), and
  Dependabot's own token after the package grants the repository read access, which may not exist for a Maven
  package. Record the answer in
  link:../specification/evaluation.adoc[Evaluation Reference] and in <<repository-setup>>.

Check: `plan-marshall-mcp` is green against the released parent; `./mvnw help:effective-pom` shows no deployment target
other than the organisation registry.

Roadmap: tick the parent item of Milestone 1.

[#repository-setup]
=== Repository Setup (used by Steps 5 to 8)

Every new repository gets the structure of `cuioss/cuioss-organization`, the same as `plan-marshall-mcp` has today:

. `gh repo create plan-marshall/<name> --public`, then the settings and the ruleset `main-branch-protection` with the
  merge queue through `repo-settings/setup-repo-settings.py` and `branch-protection/setup-branch-protection.py` of
  `cuioss-organization`; compare the result with `gh api repos/plan-marshall/plan-marshall-mcp/rulesets`.
. `.github/project.yml` (name, SonarCloud key, `cuioss-review-bot` enabled, `consumers` where the repository has
  them), the workflows of `plan-marshall-mcp` pinned to the same SHAs, `dependabot.yml`, `.coderabbit.yaml`,
  `LICENSE.md`, `CONTRIBUTING.md`, the Maven wrapper, `.gitignore`.
. Its own `CLAUDE.md`: the sections of this repository's file that apply, the repository's modules by reference to the
  module listing, the place of the documents (`plan-marshall-documentation`), and the publishing rule.
. `cuioss-review-bot.yml` with `settings-repository: pr-agent-settings`.
. The operator tasks of <<operator-tasks>> for this repository.
. A first pull request proves the setup: required checks run, SonarCloud analyses, the review bots answer.

The documentation repository gets the same setup without Maven, SonarCloud, CodeRabbit, and Sourcery: its only reviewer
is `cuioss-review-bot`, and its required check is that review.

[#step-clients]
=== Step 6: Repository `pm-mcp-clients`

. On a fresh clone of `plan-marshall-mcp`:
  `git filter-repo --path pm-modules/pm-api --path pm-modules/pm-exec --path pm-clients/pm-relay --path pm-clients/pm-operator --path-rename pm-modules/: --path-rename pm-clients/:`,

  the `native` profile on Linux, attach each binary as an archive under the classifier
  `linux-x86_64` or `linux-aarch64` and deploy it with the `SNAPSHOT`.
. The integration tests of `pm-relay`, `pm-operator`, and `pm-exec` keep the stub daemon they run against today.
. Add the dependency check for this repository (no module depends on a PM-MCP module other than `pm-api`; `pm-api`
  on `jackson-core` only) and the content check of `PM-WATCH-MOD-6`.
. In `plan-marshall-mcp`: remove the four modules and the aggregator `pm-clients`, name the `SNAPSHOT` by one version
  property, and let `pm-e2e` resolve the three binaries by classifier (on macOS, where no archive is deployed, from
  a local native build of the checked-out `pm-mcp-clients`, or the launcher scripts over the JARs).

Check: both repositories are green; `pm-e2e` runs against binaries from the registry on Linux.

Roadmap: tick the `pm-mcp-clients` item of Milestone 1.

[#step-core]
=== Step 7: Repository `pm-mcp-core`

As <<step-clients>>, with `--path pm-modules/pm-core --path pm-modules/pm-runtime --path pm-modules/pm-providers
--path-rename pm-modules/:`. `pm-core` resolves `pm-api` from the registry. The differential and fixture tests of the

Check: a change merged in `pm-mcp-core` is visible in a build of `plan-marshall-mcp` without a manual step.

Roadmap: tick the `pm-mcp-core` and the "reduce `plan-marshall-mcp`" items of Milestone 1.

. Move the project skills `traced-implementation` and `doc-review` with it, and keep in each code repository a short

[#step-propagation]
=== Step 9: Propagation

. Enter every new repository as a consumer of `cuioss-organization` (`.github/project.yml` there, entry
  `plan-marshall/<repository>`). Enter `pm-mcp-parent` as the consumer of `cui-quarkus-parent` (entry
  `plan-marshall/pm-mcp-parent:cui-quarkus-parent` in `cuioss/cuioss-parent-pom`) and remove the entry of
  `plan-marshall-mcp` there, which no longer inherits it directly. Open the pull requests in `cuioss`; the operator
  merges them.
. `pm-mcp-parent` lists `pm-mcp-clients`, `pm-mcp-core`, and `plan-marshall-mcp` as its consumers, so that its release
  opens their update pull request through `plan-marshall-release-bot`.
. A merge to `main` of `pm-mcp-clients` starts the build of `pm-mcp-core` and `plan-marshall-mcp`, and one of
  `pm-mcp-core` the build of `plan-marshall-mcp` (`repository_dispatch` sent with a token of
  `plan-marshall-release-bot`, received by a `workflow_dispatch`-able build). A failed downstream build is reported on
  the upstream commit.

Check: a no-op release of `pm-mcp-parent` opens three pull requests; a merge in `pm-mcp-clients` starts two builds.

Roadmap: tick the setup and propagation items of Milestone 1.

[#open-items]
== Open Items

* *Reusable workflows.* The reusable workflows of `cuioss-organization` v0.37.0 give no token to the Maven steps of
  the build and the integration tests, and their snapshot deploy and release publish to Maven Central only. A pull
  request in `cuioss/cuioss-organization` adds both as opt-in modes. Until its release is pinned in a repository,
  that repository deploys with a plain workflow of its own (`deploy.yml`), which receives no credential but the
  `GITHUB_TOKEN`; afterwards the plain workflow is replaced by the reusable one and deleted, and
  `.github/project.yml` switches the token for the Maven steps on. Repositories to revisit: every one this plan
  creates, and `plan-marshall-mcp`.
