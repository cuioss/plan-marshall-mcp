== Overview

Improvements deliberately deferred by operator decisions: the first iteration accepts a known limitation, and the improvement is planned but not scheduled in a milestone of the link:roadmap.adoc[Roadmap]. Each entry names the decision that deferred it, the accepted limitation, and the improvement. An entry moves into a milestone when it is scheduled; it is removed here in the same change.

Status legend as in the link:roadmap.adoc#_status_legend[Roadmap].

== Operator Channel

=== L-1: Operator Proof Beyond the CLI Checks

_Deferred by:_ Client Architecture decision Z1-9 (link:discussions/client-architecture.adoc#z1-9[Client Architecture § Z1-9]), 2026-09-28.

_Accepted limitation:_ An operator verb is accepted when the operator CLI `pm-operator` passes its local checks (terminal attached, no agent environment markers, host deny rules as defence in depth). A model shell that deliberately defeats these checks (pseudo-terminal, cleared environment, indirect invocation) can run operator verbs, including waivers, aborts and credential changes. Because the daemon cannot verify the checks of `pm-operator` (Client Architecture decisions Z1-5, Z1-21), any same-user process that holds the runtime token can call the operator endpoints of the API directly (for example `curl --unix-socket`).

* [ ] Require a user proof the model cannot produce: an operator passphrase (PBKDF2-HMAC-SHA256 hash in `<PM_MCP_BASE>/state/operator.json`) exchanged for an operator session with idle and absolute limits, presented as `Authorization: Bearer` on operator verbs
* [ ] Offer OS user presence as an alternative way to obtain the operator session (macOS LocalAuthentication/Touch ID, Linux polkit)
* [ ] Device roles for the web adapter (`viewer` default, `operator` only by explicit pairing) and step-up with the operator session before operator actions from a browser; until then every paired device has operator rights (Client Architecture decision Z1-13)

== Web Adapter

=== L-2: OAuth for the Web Adapter

_Deferred by:_ operator direction for the client architecture (link:discussions/client-architecture.adoc#direction[Client Architecture § Operator Direction]), 2026-09-28.

_Accepted limitation:_ Browsers authenticate with per-device bearer secrets obtained through one-time-code pairing by the operator CLI (`pm-operator web pair`); no identity provider, no token rotation.

* [ ] Validate OAuth access tokens with Token-Sheriff behind the web adapter's authentication seam, coexisting with device tokens during migration (routing by token shape)
* [ ] Define and integrate the role of API-Sheriff
* [ ] Authorization Code + PKCE in the web app with the access token kept in memory; evaluate BFF or token-mediating backend per RFC 10017 (BCP 212)
* [ ] Token rotation and absolute expiry for device tokens until OAuth replaces them
* [ ] Sender-constrained tokens: non-extractable WebCrypto key in IndexedDB and signed requests (DPoP), so script injection can use but not steal the credential (Client Architecture decision Z1-15)
* [ ] A local certificate authority (mkcert-style, installed on paired devices) for the LAN listener, removing the self-signed certificate warning (Client Architecture decision Z1-10)

== Git and Providers

=== L-3: Native Support for Repository Features Now Served by the CLI Variant

_Deferred by:_ Git and Provider Modules decisions Z2-15, Z2-17, Z2-18 (link:discussions/git-provider-modules.adoc#z2-15[Git and Provider Modules § Z2-15]), 2026-09-28.

_Accepted limitation:_ Repositories that need hooks, commit signing, filters including LFS, submodules, or SHA-256, partial or sparse repositories are refused by the native variant with `capability_missing` and must use the CLI variant.

* [ ] Native commit signing with an agent-owned key once a provider attributes the key to the agent identity
* [ ] Native execution of repository hooks and filter drivers through confined jobs
* [ ] Native LFS, submodules, and SHA-256 / partial / sparse repositories where the library supports them

== Skills

=== L-4: Project-Local Vocabulary Skills

_Deferred by:_ Client Architecture decision Z1-19.7 (link:discussions/client-architecture.adoc#z1-19[Client Architecture § Z1-19]), 2026-09-28; narrowed by Server-Launched Sub-Agents decision Z7-6 (link:discussions/server-launched-agents.adoc#z7-6[Server-Launched Sub-Agents § Z7-6]), 2026-09-30.

_Accepted limitation:_ `pm_skills` / `pm_skill` and the prompt files of model jobs serve only skills compiled into the binary. Project-local knowledge (conventions, vocabulary) reaches the main session and every model job only through the harness's own project instructions and skills, which a job loads natively from its working directory (`CLAUDE.md` / `AGENTS.md`, the harness's project skills); project automation enters as project-local recipes or enrolled `project_script` steps.

* [ ] Project skills in `.marshall/skills/<name>/SKILL.md` (team-owned, git-tracked), bound to domains in `domains.json`, served by `pm_skill` in a `project:` namespace
* [ ] Treat their content as untrusted repository input: size cap, recorded digest, never able to change gates or the workflow
* [ ] Include them in the server-composed prompt of model jobs once domain-bound selection is measured

== Workflow Composition

=== L-5: Team Overrides of Templates and Composition Rules

_Deferred by:_ Workflow Consistency decision Z5-47 (link:discussions/workflow-consistency.adoc#z5-47[Workflow Consistency § Z5-47]), 2026-09-29; narrowed by the round-3 document review, 2026-09-30 (the phase and sub-workflow units, remediation policy units included, are already project-owned copies).

_Accepted limitation:_ Plan instances (Z5-D) are composed from the project-owned units (`.marshall/config/*.pmwf`, copied from the defaults) and the shipped default composition rule file only. Teams cannot override or add composition rules, and cannot override the units that stay compiled only (the entity units, among them the task envelope and the plan and epic bootstraps, the workspace units, and the epic workflow).

* [ ] Team-authored composition rules (for example lane or posture prunes) in the project-owned configuration
* [ ] Team overrides of the compiled-only units where a team need is shown
* [ ] Composition rules validated against the compiled invariants on load, so no team rule can remove a mandatory step, a non-waivable guard or the operator boundary
* [ ] Provenance of every team override in the plan instance header and diagram

== Plan Bootstrap

=== L-6: Issue and Pull-Request Candidates in the Plan Bootstrap

_Deferred by:_ Plan Bootstrap decision Z6-5 (link:discussions/plan-bootstrap.adoc#z6-5[Plan Bootstrap § Z6-5]), 2026-09-29.

_Accepted limitation:_ The bootstrap's choice state lists only local candidates (live plans or epics, active unclaimed lessons, recipes, local changes, launched epic rows). Issues and pull requests are not listed; the user names a number, which the bootstrap's `issue` or `pr` source then fetches.

* [ ] List open issues and pull requests through the provider module as bootstrap candidates, within the provider's rate limits and with the same model-facing bound as the local listings
* [ ] Screen the listed titles through the guard for external text before they reach the model

== Security

=== L-7: Local Prompt-Injection Classifier

_Deferred by:_ Plan Bootstrap decision Z6-25 (link:discussions/plan-bootstrap.adoc#z6-25[Plan Bootstrap § Z6-25]), 2026-09-29.

_Accepted limitation:_ The deterministic level-1 validator recognizes injection only by its own rule table; semantic injection is judged by the level-2 screener, a model job that costs a harness run and is available only on a harness that can run without tools. Local classifier runtimes (ONNX Runtime, DJL) lack GraalVM native-image support and need models of 100–700 MB.

* [ ] Evaluate a local prompt-injection classifier as an additional risk signal of level 1 once a runtime works under native image at an acceptable size
* [ ] Measure it against the same attack corpora as the validator and the screener before it influences any delivery

== Network

=== L-8: Authenticated Proxies

_Deferred by:_ round-4 document review decision D14 (link:discussions/git-provider-modules.adoc#sandbox-native[Git and Provider Modules § Native operations]), 2026-10-01.

_Accepted limitation:_ Outbound connections (`cui-http` and the git transport of the native variant) use only an unauthenticated HTTPS proxy, set by the operator in the `proxy` object of `machine-config.json` (`https_proxy` as a URL without embedded credentials, `no_proxy`). A proxy that requires authentication is not supported.

* [ ] Proxy credentials through the credential store, never in `machine-config.json`

== Host Bundles

=== L-9: Plain Entry Command Names

_Deferred by:_ naming review decision N5 (link:discussions/plan-bootstrap.adoc#z6-12[Plan Bootstrap § Z6-12]), 2026-10-01.

_Accepted limitation:_ The entry commands are `/mcp-plan-marshall`, `/mcp-plan-orchestrator` and `/mcp-marshall-steward` (`$mcp-…` skills on Codex) while the legacy `plan-marshall` plugin, which owns the plain names, may be installed side by side. The prefix keeps the two command sets apart and lets the three commands complete together in the harness.

* [ ] Rename the entry commands to `/plan-marshall`, `/plan-orchestrator` and `/marshall-steward` once legacy `plan-marshall` is retired
* [ ] Have the bundle update remove the prefixed artifacts in the same install that places the plain ones

== Model Roles

=== L-10: Role Qualification Against the Verification Corpus

_Deferred by:_ the operator, 2026-10-04, after Stage 2 of the evaluation of the harness as worker (link:concepts/harness-as-worker/evaluation.adoc#e7[Evaluation § E7]).

_Accepted limitation:_ A role's configuration (harness, model, effort, warm or fresh; link:concepts/harness-as-worker/roles.adoc#configuration[Roles are configuration]) is chosen by the operator. The model verification corpus (`test/model/verification/` (its `README.adoc`)) can grade candidate configurations per role, but only through the evaluation tooling and by hand.

* [ ] Run a role's corpus topics on a matrix of candidate configurations and report, per candidate, the agreement level, the warm-fresh gap, the cost and the time per item
* [ ] Propose the cheapest configuration that meets the operator's level, and refuse a configuration below it unless the operator waives it
* [ ] Store the result per role, configuration and corpus revision, and re-grade on a change of model, effort, prompt, skill or harness version, reporting a configuration that falls below the level
* [ ] Report per item the class across configurations (stable, model-limited, split, item-suspect), so that the corpus is improved with the same runs
