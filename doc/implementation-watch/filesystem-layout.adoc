== Repository Workspace Layout (`.marshall/`)

[#PM-WATCH-FS-1]
=== PM-WATCH-FS-1: The layout documentation and the resolver agree

Anchor:: link:../specification/filesystem-layout/01-repository-workspace.adoc#repository-layout[Filesystem Layout § Repository Workspace Layout],
link:../specification/filesystem-layout/03-project-store.adoc#archives[Filesystem Layout § Plan & Epic Archives],
link:../Requirements.adoc#PM-IMPL-5[PM-IMPL-5]
Hazard:: The documentation stated one archive path while the resolver produced another.
Guard:: Location resolution lives in one resolver; a build-time test renders its path templates and compares them with
the layout tree in this specification (generated block or checked table), extending the documentation drift gate
beyond DSL diagrams.
Fixture:: `plan-marshall` documentation `.plan/archived-plans/{date}-{plan_id}` vs resolver
`.plan/local/archived-plans/{date}-{plan_id}`.
Source:: plan-marshall defect process-compliance PLAN-13 D2.

[#PM-WATCH-FS-2]
=== PM-WATCH-FS-2: Missing is not empty

Anchor:: link:../specification/filesystem-layout/03-project-store.adoc#plan-worktree-resolution[Filesystem Layout § Plan & Worktree Resolution]
Hazard:: A nonexistent archived path returned success, byte-identical to an empty plan directory.
Guard:: Resolvers return `absent` for a missing path, distinct from an existing empty one (the inbox `no_file` vs
`empty_file` distinction is the model); test both. A metadata reader that finds nothing it can parse reports
`unreadable`, never an empty record: a production-format `request.md` never parses to an empty metadata map.
Fixture:: a key=value-only metadata reader stopped at the `# Request:` heading and returned `{}` for every production
colon-format `request.md`, read as "no metadata" (`implement-opencode-enforcement-parity-002`,
`module-budget-campaign-completion-004`).
Source:: plan-marshall defect post-run-quality PLAN-PRQ-10 D0; process-compliance PLAN-10 § Claim Labels (mailbox probe mis-parses colon-format request.md).

[#PM-WATCH-FS-4]

== Worktree Lifecycle

[#PM-WATCH-FS-5]
=== PM-WATCH-FS-5: No claim survives on a removed worktree

Anchor:: link:../specification/filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout § Worktree Lifecycle],
link:../Requirements.adoc#PM-ARCH-5[PM-ARCH-5],
link:../specification/phase-workflows/02-planning-lanes-phases-3-4.adoc#_planning_transition_guards_real_world_invariants[Phase Workflows § Planning Transition Guards]
Hazard:: Three post-merge steps refused because plan metadata still claimed a worktree that branch-cleanup had
deleted (five independent sightings). The downstream fail-closed refusal was correct; the stale claim was the
defect.
Guard:: After worktree removal no store keeps pointing at it: `worktree_path` is cleared in the same transaction that
records the removal. A scenario test runs every post-merge step (order > 70) after branch-cleanup and after a runtime
restart at that point; each runs fail-closed-clean. A baseline scratch worktree (`baseline-<plan_id>-<sha12>`) is removed
when its plan leaves finalize, is archived, or is aborted, and by the recovery sweep when its plan is gone or
terminal; a test asserts that the sweep never removes the baseline worktree of a live plan.
Fixture:: five sightings, including archived PLAN-TRUTH-126 and PLAN-TRUTH-093, and PLAN-TRUTH-148; API-Sheriff PR
#305: the removal deleted the branch, the prune errored, and a stale `origin/{branch}` was left (ref pruning is
idempotent per ref: an absent local branch reports `skipped / already_absent`, the remote-tracking ref is still
pruned).
Source:: plan-marshall defect truthful-signals PLAN-TRUTH-164 D0 and D2.

[#PM-WATCH-FS-6]
=== PM-WATCH-FS-6: Open: adopting a branch of a re-used plan id

Anchor:: link:../specification/filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout § Worktree Lifecycle] (Crash Consistency)
Hazard:: Undecided: the creating step adopts an existing unrecorded branch or worktree of the plan's name, but a `plan_id` of a
deleted or purged plan may be allocated again, so a new plan can adopt the deleted plan's commits; Phase Workflows
states that a candidate identifier never ends "in a silent reuse". Options: (1) adopt only a branch provably the
plan's own (a creation marker), otherwise refuse into the step's failure route; (2) accept the adoption and correct
the Phase Workflows statement. Recommendation: 1, foreign commits never enter a plan unseen.
Guard:: The plan implementing this anchor decides the point (with the operator where it changes scope), records
the result in the specification and the requirement it touches, and deletes this item.
Source:: `filesystem-layout/01-repository-workspace.adoc:69`, `store-schemas/13-leases-integrity-testing.adoc:108`
(accepted risk), `phase-workflows/01-planning-phases-1-2.adoc:268`.
