== Dependency Rules

[#PM-WATCH-MOD-1]
=== PM-WATCH-MOD-1: Clients never reach the engine

Anchor:: link:../specification/module-structure.adoc#dependency-rules[Module Structure § Dependency Rules],
link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]
Hazard:: One convenience dependency from a client module to `pm-core`, `pm-workflow` or a provider module
lets `pm-mcp` or `pm-operator` run engine or store code in its own process, bypassing the runtime as the only writer;
a dependency of one client module on the other puts operator verbs into the binary the model may run;
`jackson-databind` in `pm-api` pulls reflection-heavy binding into the plain native client binaries.
Guard:: A build-time dependency guard (Maven enforcer or an architecture test over the resolved dependency trees)
fails when any module of `pm-mcp-clients` depends, directly or transitively, on `pm-core`, `pm-workflow`,
`pm-runtime` or a module under `pm-providers`, when `pm-relay` or `pm-operator` depends on a PM-MCP module other than `pm-api`
(the other client module and `pm-mcp-server` included), when a provider module depends on `pm-workflow`, when `pm-core` depends on a PM-MCP module other than
`pm-api` (which it uses for the host-detection table alone), and when `pm-api` depends on anything but
`jackson-core`; control: a deliberately added dependency in a test fixture module trips the
guard.
Source:: design review.

[#PM-WATCH-MOD-4]
=== PM-WATCH-MOD-4: Open: the TOON encoder in two modules

Anchor:: link:../specification/module-structure.adoc#modules[Module Structure § Modules],
link:../Requirements.adoc#PM-IMPL-3[PM-IMPL-3]
Hazard:: Undecided: `pm-api` holds the JSON/TOON codecs and `pm-core` holds `ToonEncoder`, and `pm-api` does not depend on
`pm-core`; two encoders drift apart, and the conformance fixtures of the pinned TOON version guard only one.
Options: (1) the API is JSON-only; (2) `ToonEncoder` moves to `pm-api`, `pm-core` reuses it, and `PM-IMPL-3` is
amended. Recommendation: 2, a single encoder.
Guard:: The plan implementing this anchor decides the point (with the operator where it changes scope), records
the result in the specification and the requirement it touches, and deletes this item.
Source:: `specification/module-structure.adoc:70`, `:80`, `:238`, `requirements/14-implementation.adoc:46`.

== Repositories & Artifact Flow

[#PM-WATCH-MOD-5]
=== PM-WATCH-MOD-5: Artifacts leave only through the organisation's registry

Anchor:: link:../specification/module-structure.adoc#artifact-flow[Module Structure § Artifact Flow],
link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1], link:../Requirements.adoc#PM-DIST-1[PM-DIST-1]
Hazard:: The parent of `pm-mcp-parent` binds a Maven Central publishing plugin to `deploy`; one repository that
overrides the parent's distribution configuration, or one workflow that receives publishing credentials, puts
proprietary artifacts on a public registry, where they cannot be withdrawn. A package of a public repository is
readable by every GitHub account. Undecided: the `GITHUB_TOKEN` of a consumer's workflow cannot read the package of a
private repository, and which token the CI of the consumers uses from then on is open: a personal token of a member
as a secret, or the token of a GitHub App installed on the publishing repository with package read permission, which
is unverified.
Guard:: No workflow of any repository receives a credential of another registry, and no repository overrides the
deployment configuration or the build check it inherits from `pm-mcp-parent`. Before the first publishing repository is switched to
private, the plan that switches it decides the token of the consumers' CI, proves it on the real registry, and
records it in the specification.
Source:: design review.

[#PM-WATCH-MOD-6]
=== PM-WATCH-MOD-6: No model-facing content in a public artifact

Anchor:: link:../specification/module-structure.adoc#model-facing-content[Module Structure § Model-Facing Content],
link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]
Hazard:: A default workflow unit, a shipped role artifact, a skill or a client bundle that is added to a module of
`pm-mcp-core` or `pm-mcp-clients` (as a main resource, or as a test fixture copied from the real content) is published
with that module's JAR or lies in a public repository.
Guard:: A build check in `pm-mcp-core` and `pm-mcp-clients` fails when a module JAR contains an entry under
`workflows/`, `roles/`, `bundles/` or the skill corpus, and their test fixtures are written for the test, never copied
from the content.
Source:: design review.

== Binaries & Build Types

[#PM-WATCH-MOD-2]
=== PM-WATCH-MOD-2: The release is exactly four binaries with a complete SBOM

Anchor:: link:../specification/module-structure.adoc#binaries[Module Structure § Binaries & Build Types],
link:../specification/cli-and-security/01-cli-and-installer.adoc#installation-layout[CLI & Security § Installation Layout],
link:../Requirements.adoc#PM-DIST-1[PM-DIST-1]
Hazard:: A release profile that packs a stray artifact, misses a binary or its digest, or ships operator verbs
inside the relay binary breaks the layout the host deny rule rests on; an SBOM built from the Maven graph only leaves
the npm packages of the web application, which `pm-mcpd` serves, unaccounted for.
Guard:: The release build's output is checked: `bin/` holds exactly `pm-mcp`, `pm-operator`, `pm-mcpd`, and
`pm-exec`, each with its SHA-256 digest, and nothing else; `pm-mcp` offers exactly the verbs `serve` (`--client`,
`--job`) and `enter`, and no operator verb; the CycloneDX SBOM lists every package of
`pm-web-app/package-lock.json` with its pinned version next to the Java dependencies.
Source:: design review.

[#PM-WATCH-MOD-3]
=== PM-WATCH-MOD-3: Open: the build order of `pm-e2e`

Anchor:: link:../specification/module-structure.adoc#module-tree[Module Structure § Module Tree],
link:../specification/module-structure.adoc#dependency-rules[Module Structure § Dependency Rules]
Hazard:: Undecided: `pm-e2e` may not depend on `pm-mcp-server` through Maven, so the reactor can build it before
`pm-mcpd` exists and its tests run against a stale or missing binary; the three binaries of `pm-mcp-clients` come
from the registry and can be older than the contract `pm-mcpd` was built against. Options: (1) move it to the end of the root reactor; (2) an ordering-only `pom`/`provided`
dependency exempt from the guard; (3) run it in a separate invocation like `pm-conformance`. Recommendation: 3,
the pattern already exists.
Guard:: The plan implementing this anchor decides the point (with the operator where it changes scope), records
the result in the specification and the requirement it touches, and deletes this item.
Source:: `specification/module-structure.adoc:40-52`, `:155`.
