== Core Workflow Tool Schemas (`pm_state`, `pm_do`, `pm_wait`)

[#PM-WATCH-TOOL-1]
=== PM-WATCH-TOOL-1: A plan's outbox reaches only its own epic inbox

Anchor:: link:../specification/mcp-tools/01-core-workflow-tools.adoc#_pm_do_follow_a_hypermedia_link[MCP Tools § `pm_do`],
link:../specification/model-work/08-epic-coordination.adoc#plan-scope-outbox-link[Model Work § Plan-Scope Outbox Link],
link:../Requirements.adoc#PM-TOOL-1[PM-TOOL-1]
Hazard:: Plans could file into their epic only by writing ledger paths directly, and nothing proved that they could
not reach other ledger files.
Guard:: Negative tests: from a plan scope no `pm_do` argument combination writes outside that epic's inbox; a plan
whose `origin.epic_id` is `E1` cannot file into `E2`; a task entity of a plan without `origin.epic_id` is not offered
`outbox:send`; `queue/`, `epic.json`, `landings.jsonl` and the epic's machine-store `status.json` are never written
from a plan scope.
Source:: plan-marshall process-compliance PLAN-09 D2 (also test-fidelity-rules-follow-up-005).

[#PM-WATCH-TOOL-2]
=== PM-WATCH-TOOL-2: Rejected calls are counted, and repeats are visible

Anchor:: link:../specification/mcp-tools/04-errors-and-testing.adoc#_rejected_transition_representation_iserror_false[MCP Tools § Rejected Transition Representation],
link:../specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[§ Closed Rejection Reasons & Failure Classes],
link:../specification/phase-workflows/05-finalize-review-metrics-descriptor.adoc#post-run-metrics-and-landing[Phase Workflows § Post-Run Metrics & Landing Envelope] (Caller-Drift Rate),
link:../Requirements.adoc#PM-TOOL-4[PM-TOOL-4], link:../Requirements.adoc#PM-MIG-5[PM-MIG-5]
Hazard:: Repeated resubmission of rejected call shapes dominated `plan-marshall` script failures; an identical rejected call
was repeated one second apart; most invocation failures were caller drift, not product defects, and nobody could
measure the rate.
Guard:: The audit record of a rejection carries the link and an argument digest; the `rejected` block carries no
repeat count; the Caller-Drift Rate counts rejected link calls per plan and `rejected.reason` and the repeated
identical ones (same link and argument digest), with the three failure classes `caller_drift`, `precondition`, and
`server_fault` kept apart and only `caller_drift` counted in the rate, so the workflow-discipline rate is measurable (test: three identical rejected calls yield one reason count of 3 and a repeat
count of 2, and three identical `rejected` blocks).
Fixture:: one plan logged 20 script failures, 12 unique, dominated by argument-shape rejections (lesson
`2026-09-21-10-001`); `manage-solution-outline get-deliverable` repeated identically 1 s apart (Token-Sheriff PR
#744); PRQ-06 baseline: 26 failures across 15 failing notations, 22 of 26 caller-side (clusters 8 + 4 + 10);
partition by failure class: 20 of 26 caller drift (invented subcommand, missing required flag, invented flag, other
argument rejection), 6 bug (4 of them notation errors). Invocation-rejection population ~33 (PLAN-TRUTH-148: 17,
10 unique across 8 components; PLAN-TRUTH-157: 6; PLAN-PR-065: 10). `plan-marshall` workflow-discipline baseline:
router-scoped `--plan-id` recurred on a live `ci` invocation despite a documented signature (lesson `2026-09-20-08-013`); an
external-repository cluster had five argument-shape recurrences across five scripts (unregistered verb,
sibling-verb flag, router flag position ×2, abbreviated typed id, invented flag) plus one exemplary compound-flag
refusal (positive control), a `review_completeness` bare-bot recurrence, and `qgate list` missing the required
`--phase` (`lessons-routing-002`/`-003`).
Source:: plan-marshall defects process-compliance PLAN-14 D1, PLAN-12 D4; truthful-signals PLAN-TRUTH-162 D0 and item
(c); post-run-quality PLAN-PRQ-11 D0 and D1.

[#PM-WATCH-TOOL-13]
=== PM-WATCH-TOOL-13: Every scoped tool demands an explicit scope

Anchor:: link:../specification/mcp-tools/01-core-workflow-tools.adoc#_architectural_constraints[MCP Tools § Architectural Constraints] (Explicit Scope on Every Scoped Tool),
link:../Requirements.adoc#PM-TOOL-1[PM-TOOL-1]
Hazard:: A tool that falls back to the workspace scope when `plan_id` is omitted acts on the main checkout while the
model believes it addressed its plan; a `NO_PLAN` accepted as a plan id creates a phantom plan.
Guard:: Each of `pm_state`, `pm_do`, `pm_build`, `pm_lsp`, `pm_skill`, `pm_skills`, and `pm_skill_file` called
without a scope is refused with `invalid_arguments`; `NO_PLAN` as a derived or supplied `plan_id` of a plan to create
is refused by the phantom-id guard; `pm_lsp` `rename` with `NO_PLAN` is refused; control: a read with `NO_PLAN`
addresses the workspace scope.
Source:: design review.

[#PM-WATCH-TOOL-15]
=== PM-WATCH-TOOL-15: The bootstrap commit re-checks what could change and creates nothing on refusal

Anchor:: link:../specification/mcp-tools/01-core-workflow-tools.adoc#bootstrap-commit-recheck[MCP Tools § Bootstrap Commit Re-Check],
link:../Requirements.adoc#PM-TOOL-1[PM-TOOL-1]
Hazard:: A check made while gathering (identifier free, lifecycle gate open or project enrolled as a pilot, lesson
unclaimed, identifier not staged by an epic, roles defined, local changes present) is stale at the commit, so a plan
is created over a taken identifier, a closed gate in a project that is no pilot, or a lesson another plan claimed.
Guard:: Race tests per closed reason: change the checked condition between `start.ready` and `create` (a concurrent
plan takes the identifier, the operator re-enrols the project without `--pilot` while the release's gate is closed
(`lifecycle_closed`), another entry claims the lesson, an epic stages a row with the derived identifier
(`epic_pointer_mismatch`), the operator removes a role the composed workflow names (`role_undefined`), the working
tree is cleaned): the `create` transaction creates no directory, keeps the pending entry
record, and returns to `start.ready` with `facts.commit_refused` naming the reason; the refusal is audit-logged
(`bootstrap_refused`) and counted against no plan; matched control: an unchanged record commits once.
Source:: design review.

[#PM-WATCH-TOOL-16]
=== PM-WATCH-TOOL-16: A worker connection is bound by the daemon, not by the harness allowlist

Anchor:: link:../specification/mcp-tools/01-core-workflow-tools.adoc#job-bound-connections[MCP Tools § Worker Connections] (Tool set, Resources, Task binding, Fencing and end)
Hazard:: A tool or resource boundary that only the harness's allowlist enforces falls with one harness bug or one
bypassed flag: a `read_only` worker builds or renames, a worker reads the stores of another enrolled project or acts
on a task it does not hold, and a token that outlived its job keeps reading.
Guard:: Tests that call the daemon with a job token and generation directly, without a harness: a worker connection
lists and reads the resources of its own project and `skill://pm/…` and is refused a resource of another enrolled
project (`-32002`, `scope_not_found`); `pm_state` and `pm_do` on an entity not leased to the worker's generation, and
`pm_build` or `pm_lsp` on a scope of no leased task, are refused `job_scope_mismatch`; a `zero_tool` worker has no
connection and reads none; every call of a fenced generation is refused `generation_fenced`, and every call after the
job's fate `job_ended`; a `read_only` worker's `pm_build` call is refused (the tool is
not in its set) and its `pm_lsp` `rename` is refused `invalid_arguments`, while its `pm_lsp` read operations succeed;
positive control: a `writer` worker's `pm_build` and `pm_lsp` `rename` on its leased task's scope are served.
Source:: design review.

== Orthogonal Service Capability Tool Schemas (`pm_build`, `pm_lsp`)

[#PM-WATCH-TOOL-3]
=== PM-WATCH-TOOL-3: LSP uptake is measured by the fallback-to-read rate

Anchor:: link:../specification/mcp-tools/02-service-and-skill-tools.adoc#_pm_lsp_warm_language_server_operations[MCP Tools § `pm_lsp`],
link:../Requirements.adoc#PM-SVC-2[PM-SVC-2]
Hazard:: A code-intelligence surface can be used and still be ignored: the agent reads the file anyway.
Guard:: Count `pm_lsp` calls followed by a host read of the same path within one task of a worker; that rate is the
uptake metric.
Source:: plan-marshall code-intelligence-substrate inbox other-approaches-001.

[#PM-WATCH-TOOL-4]
=== PM-WATCH-TOOL-4: LSP latency is not a constant

Anchor:: link:../specification/mcp-tools/02-service-and-skill-tools.adoc#_warm_lsp_pool_lifecycle_pm_svc_2[MCP Tools § Warm LSP Pool Lifecycle]
Hazard:: A cold `documentSymbol` call took about a second but milliseconds after a workspace-symbol call and
diagnostics had warmed the server; magnitudes depended on call order.
Guard:: Tests of `pm_lsp` and of the warm pool never assert absolute per-call timings; they assert results only
(for `diagnostics`, the pulled diagnostics or the cached published ones marked `source: published`).
Source:: plan-marshall code-intelligence-substrate PLAN-CIS-054 D5 item 1, bullet 010/G7.

[#PM-WATCH-TOOL-5]
=== PM-WATCH-TOOL-5: Corpus language-server diagnostics are not served

Anchor:: link:../specification/mcp-tools/02-service-and-skill-tools.adoc#_pm_lsp_warm_language_server_operations[MCP Tools § `pm_lsp` — Warm Language Server Operations] (Corpus Language Server),
link:../Requirements.adoc#PM-SVC-2[PM-SVC-2]
Hazard:: A corpus validator overcounted unresolved references, with a false-positive share of about 97%; decisions
taken on its output had to be re-taken.
Guard:: The corpus language server's diagnostics are not served: it is reachable through `pm_lsp` `definition`,
`references`, and `hover` only (test: `pm_lsp diagnostics` on a corpus file returns no diagnostic of the corpus
server).
Fixture:: 120 of 2467 overcount; 380 → 61 unresolved flipped the false-positive share from ~97% to ~41%.
Source:: plan-marshall code-intelligence-substrate WS-03 charter.

[#PM-WATCH-TOOL-18]
=== PM-WATCH-TOOL-18: Continuing a finished build returns its result, a foreign build stays refused

Anchor:: link:../specification/mcp-tools/02-service-and-skill-tools.adoc#_pm_build_enrolled_build_execution[MCP Tools § `pm_build` — Enrolled Build Execution],
link:../Requirements.adoc#PM-SVC-1[PM-SVC-1]
Hazard:: A worker whose bounded wait ended just before its build finished continues with the `job_id` it holds; a
server that refuses a finished build makes the worker start the same build again, and one that accepts any
`job_id` hands a build of another scope to a caller that never ran it.
Guard:: Test: a `pm_build` continuation naming a build of the same scope that finished between the two calls
returns that build's terminal result and starts no job; a continuation naming an unknown `job_id`, and one naming
a build of another scope, is refused `invalid_arguments` (parameter `job_id`). Matched control: a continuation of a
running build of the same scope waits one bounded window and returns `running` with the same `job_id`.
Source:: design review.

[#PM-WATCH-TOOL-19]
=== PM-WATCH-TOOL-19: An upstream tool error is passed through, an unreachable upstream is `upstream_unavailable`

Anchor:: link:../specification/mcp-tools/02-service-and-skill-tools.adoc#_selective_upstream_mcp_proxy_meta_provenance_pm_svc_3[MCP Tools § Selective Upstream MCP Proxy & `_meta` Provenance],
link:../specification/mcp-tools/04-errors-and-testing.adoc#_sanitized_tool_execution_error_envelope_iserror_true[§ Sanitized Tool Execution Error Envelope],
link:../Requirements.adoc#PM-SVC-3[PM-SVC-3]
Hazard:: A proxy that folds the upstream server's own tool error into its transport error hides the upstream's
answer from the caller, and one that passes a transport failure through as an upstream result makes a missing
credential look like an upstream verdict.
Guard:: Test against a stub upstream server: an upstream result with `isError: true` reaches the caller unchanged,
wrapped with the provenance `_meta`; a refused connection, a failed TLS handshake, a missing `mcp-<server_id>`
credential, a credential the upstream rejects, and an upstream JSON-RPC error each answer `upstream_unavailable`
(class `server_fault`) with no upstream content; an upstream that does not answer in time answers
`upstream_timeout`. Matched control: a successful upstream result is passed through with the same `_meta`.
Source:: design review.

[#PM-WATCH-TOOL-20]
=== PM-WATCH-TOOL-20: The entry session reads code through `pm_lsp` and never edits it

Anchor:: link:../specification/mcp-tools/01-core-workflow-tools.adoc#session-and-worker-surfaces[MCP Tools § Session and Worker Surfaces]
Hazard:: An entry session that may `rename` edits a plan's worktree beside the plan's writer worker, so the change
lands outside every task, footprint, and review.
Guard:: Test with an entry session connection: `pm_lsp` `rename` is refused `invalid_arguments` for a real `plan_id`
and for `NO_PLAN`, and the worktree is unchanged; its read operations on both scopes succeed; matched control: a
`writer` worker's `rename` on its leased task's scope is applied.
Source:: design review.

[#PM-WATCH-TOOL-6]
=== PM-WATCH-TOOL-6: Skills name only link ids that exist

Anchor:: link:../specification/mcp-tools/02-service-and-skill-tools.adoc#_pure_vocabulary_skills_dynamic_context_injection_pm_skill_1_pm_skill_2_pm_skill_4[MCP Tools § Pure Vocabulary Skills & Dynamic Context Injection],
link:../Requirements.adoc#PM-SKILL-1[PM-SKILL-1], link:../Requirements.adoc#PM-IMPL-5[PM-IMPL-5]
Hazard:: Descriptive guidance ("deliverable extraction") induced a paraphrased verb (`extract-deliverables` instead of

link or verb that no workflow offers. Store→render and render→store are walked

[#PM-WATCH-TOOL-21]
=== PM-WATCH-TOOL-21: One rule checker decides for shipped and extension skills

Anchor:: link:../specification/mcp-tools/02-service-and-skill-tools.adoc#skill-rule-checker[MCP Tools § Skill Rule Checker],
link:../Requirements.adoc#PM-SKILL-1[PM-SKILL-1], link:../Requirements.adoc#PM-SKILL-5[PM-SKILL-5]
Hazard:: Two checkers drift: the build test of the shipped corpus and the read-time validation of extension skills
accept different skills, so a team skill that a shipped skill could never be (a shell block, a dangling link, an

`rule_violation` naming that rule, and the same content placed in the shipped corpus fails the build; matched control:
a skill with a prose mention of a command name inside a sentence and a `text` code block passes.

[#PM-WATCH-TOOL-10]

[#PM-WATCH-TOOL-17]
=== PM-WATCH-TOOL-17: Every tool execution error code has exactly one failure class

Anchor:: link:../specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools § Closed Rejection Reasons & Failure Classes],
link:../specification/mcp-tools/04-errors-and-testing.adoc#_sanitized_tool_execution_error_envelope_iserror_true[§ Sanitized Tool Execution Error Envelope],
link:../Requirements.adoc#PM-TOOL-4[PM-TOOL-4]
Hazard:: A tool execution error classified by its tool instead of its `error_code` counts an infrastructure fault as
caller drift, or a caller mistake as a server fault, so the caller-drift rate is wrong and a worker's attempt ends on
a call it could have corrected.
Guard:: Table test over the closed handler `error_code` enumeration: every code maps to exactly one class
(`invalid_arguments`, `section_not_found`, `job_scope_mismatch` -> `caller_drift`; `scope_not_found`,
`project_not_enrolled`, `runtime_recovering`, `generation_fenced`, `job_ended` -> `precondition`; `internal_fault`,
`file_unreadable`, `lsp_unavailable`, `upstream_timeout`, `upstream_unavailable` -> `server_fault`), and a code added
to the enumeration without a class fails the build; the relay and transport codes (`runtime_unavailable`,
`generation_superseded`) are no `CallToolResult` and stay outside the table. Matched control: a `pm_skill` call
failing with a `server_fault` code ends the worker's attempt, the same call refused `section_not_found` does not.
Source:: design review.
