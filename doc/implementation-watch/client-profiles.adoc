== Normative Client Profile JSON Schema

[#PM-WATCH-CLIENT-8]
=== PM-WATCH-CLIENT-8: A writable harness path never covers a managed settings, command, or skill file

Anchor:: link:../specification/client-profiles/01-profile-schema.adoc#_normative_client_profile_json_schema[Client Profiles § Normative Client Profile JSON Schema] (Writable paths)
Hazard:: A `headless.writable_paths` entry that names a harness home as a whole, or a directory holding the settings,
command, or skill file the bundle installed, puts that file into the Landlock write set of every worker: a worker
rewrites the host's deny rules, entry commands, or shim skill, and the operator's next session runs without them.
Guard:: Profile validation refuses a `headless.writable_paths` entry that equals, contains, or lies under a settings,
command, or skill file the client's bundle manifest manages, or a shared configuration file in which the bundle owns
an `enforcement` element; a build-time test runs the rule over every shipped profile against its own bundle
manifest; negative fixture: a profile with the entry `~/.claude` and one with the path of the managed settings file
are each refused naming the entry and the managed file; runtime control: a worker's write to the managed settings
file fails.
Hazard:: The `claude` harness cannot run headless without rewriting `~/.claude.json`, which also holds the
user-scope MCP registration the bundle owns; with the file in the write set a worker can change or remove
`mcpServers.plan-marshall`, and the operator's next session starts another command or none.
Guard:: The bundle owns no `enforcement` element in a writable shared configuration file (build-time test over
every shipped profile and manifest); a fixture worker that rewrites the owned key is reported `bundle_modified`
with that key by the next `pm-mcp enter` and by `pm-operator client status`; a confined `claude` writer worker
runs with exactly the declared entries (not `~/.claude` as a whole) before the _(provisional)_ marker of its
sub-paths is removed.
Fixture:: Claude Code 2.1.291 under Landlock ABI 8: writes to `~/.claude.json` (a file rule; `$HOME` not needed),
5 files under `~/.claude` (session transcript, synced plugin and skill manifests), 1 MCP log under
`~/.cache/claude-cli-nodejs`; unconfined also `~/.claude/backups/` and `~/.claude/sessions/<pid>.json`.
Source:: design review; link:../specification/evaluation.adoc#results[Evaluation Reference], Gate 13.

[#PM-WATCH-CLIENT-11]
=== PM-WATCH-CLIENT-11: A harness that cannot restrict its workers

Anchor:: link:../specification/client-profiles/01-profile-schema.adoc#role-classes[Client Profiles § Role Classes of a Harness],
link:../specification/client-profiles/01-profile-schema.adoc#worker-block[Client Profiles § Worker Block] (`worker.eligible`),
link:../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2]
Hazard:: Antigravity runs every worker with all its host tools and beside the MCP servers of the operator's own
configuration (`tool_set: advisory`, `mcp_config.exclusive: false`). That is accepted for `writer` and `read_only`
roles and fatal for the screener: a profile that declared `zero_tool` for it would hand untrusted text to a model
with a shell. Beside that, three things were seen in its measurement and not yet tested under target conditions:
the operator's global configuration holds the bundle's own `plan-marshall` entry, so a worker would start the
session relay beside its job relay under the same server name; all `agy` processes share a tool schema cache per
server name, while the tool list differs per role; and task inputs of 8,000 characters and more were read back with
the host's `view_file` from its own step output, outside the server's resource tools. Its fault matrix passed only as
a three-trial smoke run with unconfined workers on macOS.
Guard:: Profile validation refuses a non-null `zero_tool` on a profile whose `mcp_config.exclusive` is `false`, and
a fixture profile proves it. `worker.eligible` of `antigravity` becomes `true` only after: the ten-trial fault matrix
with confined workers on Linux, with the bundle's global entry installed (the session relay exits inside a worker and
no tool of it is listed); two workers of roles with different tool sets running at once, each listing exactly its own
tools; and its writable paths under Landlock, the step output it reads back included, recorded in
`headless.writable_paths`.
Source:: link:../specification/evaluation.adoc[Evaluation Reference] (Gates 13 and 16), design review.

[#PM-WATCH-CLIENT-12]
=== PM-WATCH-CLIENT-12: A harness that cuts a tool result loses the task

Anchor:: link:../specification/client-profiles/01-profile-schema.adoc#headless-tool-result-limit[Client Profiles § Normative Client Profile JSON Schema] (Tool-result limit),
link:../specification/model-work/02-task-protocol.adoc#offer[Model Work § Offer]
Hazard:: A harness truncates an MCP tool result above its own limit and keeps the full text in a file that a
worker restricted to the server's tools cannot read. An offer whose task identifiers lie in the cut part leaves
the worker without its task: it acknowledges and submits with guessed ids, every call is refused, and the task
ends unsubmitted.
Guard:: Table test per harness with a declared `tool_result_limit_chars` over task inputs below, at, and above the
limit (8 000, 32 000, 128 000 characters): no tool result the server returns exceeds the limit, the task id and the
`ack` link are in the first part of every offer, and the worker completes the task by reading the parts as
resources; negative control: with the limit unset the largest input reproduces the loss; the exact threshold of
`opencode` is measured and replaces the provisional `32000`; a profile with a limit and no `resource_tools` is
refused.
Fixture:: OpenCode 1.18.34: 8 000 and 32 000 characters completed, 128 000 failed ("…128402 bytes truncated…",
full output saved under `~/.local/share/opencode/tool-output/`); the worker's `pull_ack` calls with the guessed ids
`h128000`, `128000`, `gate13` and a `pull_submit` with `task_id` `test` were all refused, and it ended with
`{"task_id":"unknown"}`. Claude Code 2.1.291 completed all three sizes.
Source:: link:../specification/evaluation.adoc#results[Evaluation Reference], Gate 13.

[#PM-WATCH-CLIENT-13]
=== PM-WATCH-CLIENT-13: A host started inside another host is attributed to the outer one

Anchor:: link:../specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Client Profiles § Host Integration Table] (Detection precedence, Nested hosts),
link:../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3]
Hazard:: Host markers are inherited, and no host clears another's: with a fixed precedence alone, Claude Code
started inside OpenCode is detected as `opencode`, the entry is recorded with `identity_mismatch` although the
declared client is right, and `AI_AGENT`, inherited from an outer Claude Code, names the wrong host in a host
started inside it. Codex passes only a fixed variable list to its MCP servers, so a detection attempted in the
relay never sees its markers.
Guard:: Table test of the host-detection table, read from the profile documents, over environments with the markers of one host, of both
nestings of every pair of hosts (process tree fixtures with the process-id markers), and with an inherited
`AI_AGENT`: the detected client is the host of the nearest ancestor, the fixed order decides only where no
process-id marker resolves, and `AI_AGENT` never overrides a primary signal; detection runs in `pm-mcp enter`
only, and `pm-mcp serve` computes no environment signature; the process-id marker of `claude` is verified against
a live host before its _(provisional)_ marker is removed.
Fixture:: OpenCode inside Claude Code is attributed correctly by the fixed order; Claude Code inside OpenCode is
attributed to `opencode`; Claude Code sets `AI_AGENT=claude-code_2-1-291_agent`, overwriting an inherited value.
Source:: link:../specification/evaluation.adoc#results[Evaluation Reference], Gate 14.

[#PM-WATCH-CLIENT-1]
=== PM-WATCH-CLIENT-1: Format-accuracy evidence is secondhand

Anchor:: link:../specification/client-profiles/02-placeholders-and-detection.adoc#_rendering_invariants[Client Profiles § Rendering Invariants],
link:../specification/client-profiles/02-placeholders-and-detection.adoc#calibration-decision[Client Profiles § Calibration Decision],
link:../Requirements.adoc#PM-TOOL-5[PM-TOOL-5], link:../Requirements.adoc#PM-IMPL-2[PM-IMPL-2],
link:../Requirements.adoc#PM-TEST-6[PM-TEST-6]
Hazard:: The TOON wire form is a settled design decision, but its parse fidelity per client runtime is unmeasured;
the only format-accuracy figures in circulation are secondhand (an up-to-40% drop from generic Markdown, a
model-specific optimal format, parsing accuracy YAML 51.9% / JSON 43.1% / XML 33.8%). A runtime that parses TOON
poorly degrades silently.
Guard:: Keep the decision. Before revisiting TOON or the Calibration Decision, read the primary source (Ouyang et al.
2026, _SkCC_, arXiv 2605.03353) and record what it measured; never cite the figures in a specification before
that. The `PM-TEST-6` baseline of every client includes a TOON representation-parsing scenario (the model extracts
`links` and `facts` from a `pm_state` result), link:../specification/workflow-dsl/07-loop-back-diagrams-verification.adoc#behavioural-conformance-harness[Workflow DSL § Behavioural Conformance Harness].

Source:: plan-marshall defect instrumentation-substrate PLAN-03 deliverable 5 and § Folded finding — `next-level-006`.

== Embedded Client Bundle `bundle-manifest.json` Schema

[#PM-WATCH-CLIENT-5]
=== PM-WATCH-CLIENT-5: Host-side enforcers are scope-bound; only server gates travel with every session

Anchor:: link:../specification/client-profiles/03-bundle-manifest.adoc#_embedded_client_bundle_bundle_manifest_json_schema[Client Profiles § Embedded Client Bundle `bundle-manifest.json` Schema],
link:../Requirements.adoc#PM-DIST-2[PM-DIST-2], link:../Requirements.adoc#PM-ARCH-1[PM-ARCH-1]
Hazard:: plan-marshall's hooks lived only in git-ignored machine-local configuration, so fresh clones and cloud
sessions ran with zero mechanical enforcement while documents claimed the rules were enforced.
Guard:: Server gates are the only enforcement claimed as universal. Every host-side enforcer (`permission_rule`
elements) is declared in a scope section of the bundle manifest and recorded with its scope in
`install-records.json`; `pm-operator client status` reports which enforcers are installed and in which scope; documents
never call a host-side enforcer universal.
Fixture:: plan-marshall's checked-in `.claude/settings.json` has no `hooks` key; all 6 hook events live in the
git-ignored `settings.local.json`.
Source:: plan-marshall defect instrumentation-substrate PLAN-08 deliverable 4 and § Claim Labels (hook surface machine-local only).

[#PM-WATCH-CLIENT-9]
=== PM-WATCH-CLIENT-9: Bundle artifacts carry the `mcp-` command names and never a `plan-marshall` name

Anchor:: link:../specification/client-profiles/03-bundle-manifest.adoc#_ownership_digest_verification_on_installupdateremove[Client Profiles § Ownership & Digest Verification on Install/Update/Remove] (Side-by-Side with Legacy `plan-marshall`),

Hazard:: A command or skill file whose name differs from the entry command the profile renders leaves
`{{command:*}}` pointing at a command the host does not have; a bundle file named `plan-marshall`,
`plan-orchestrator`, or `marshall-steward` shadows or is shadowed by the `plan-marshall` plugin's command in a mixed

command file and the skill directory name (the first segment of `target_name`, for example
`mcp-plan-marshall-skills` of `mcp-plan-marshall-skills/SKILL.md`) for an entry or shim skill; no compared name of
any scope equals a `plan-marshall` command name (`plan-marshall`, `plan-orchestrator`, `marshall-steward`); control:
a fixture manifest with an unprefixed command file or skill directory fails the build.
Source:: design review.

[#PM-WATCH-CLIENT-13]
=== PM-WATCH-CLIENT-13: A profile starts a process, and its verification runs an unknown harness

Anchor:: link:../specification/client-profiles/01-profile-schema.adoc#profile-sets[Client Profiles § Profile Sets],
link:../specification/client-profiles/01-profile-schema.adoc#profile-verification[Client Profiles § Profile Verification],
link:../Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5], link:../Requirements.adoc#PM-SEC-3[PM-SEC-3]
Hazard:: A machine profile holds the argument vector and the environment of every worker of its harness and decides
whether a harness may run the screener; whoever can write one runs a command of their choice with the operator's
login and can declare a harness with a shell to be tool-free. The verification itself starts a harness nobody has
measured yet, with every tool it has, and a model's own report of what it did is no measurement: a `zero_tool` check
that asks the worker whether it has tools, or an `exclusive` check that trusts the draft, certifies exactly the
harness it should refuse. A record made on macOS, where no job is confined, says nothing about confined workers.
Guard:: The machine profile directory is written only by `pm-operator profile install` under the operator checks; a
profile whose digest differs from its record, a record without its profile, and a profile dropped into the directory
by hand are each refused as `profile_unverified` (fixtures for all three), with the shipped profile staying in force.
Every probe worker runs in a throwaway workspace in the user's temporary directory, outside `<PM_MCP_BASE>`,
confined where the platform confines jobs, and never in a project. The `classes` and `isolation` stages decide from what the runtime observes
(tool-call events in the harness output, connections at the probe and decoy servers, the canary in the answer), never
from the worker's statement; control fixtures are a stub harness that calls a tool although started as `zero_tool` and
one that connects to the decoy server, each of which must fail its stage. A candidate never carries
`worker.eligible: true` or a non-null `zero_tool` from the draft alone, and the runtime honours both only for a
record of its own platform. The probes record variable names, never values.
Source:: design review.
