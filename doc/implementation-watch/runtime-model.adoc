== Overview

Watch items for the link:../specification/runtime-model.adoc[Runtime & Interaction Model Specification]: start-up
liveness, the runtime token and the offline verbs, drain, the relay rules, stall and idle-gap detection on active
plans, and test isolation from machine-wide state. The sections mirror the specification. Item format and
lifecycle: link:../ImplementationWatch.adoc[Implementation Watch].

== Runtime

[#PM-WATCH-RUN-1]
=== PM-WATCH-RUN-1: Started means reachable

Anchor:: link:../specification/runtime-model/01-processes-and-transport.adoc#_start_modes[Runtime Model § Start Modes],
link:../Requirements.adoc#PM-ARCH-7[PM-ARCH-7]
Hazard:: A daemon start reported `running` before liveness was verified.
Guard:: Every on-demand start by `pm-mcp` or `pm-operator` (the relay's included) and `pm-operator status` report `running` only after a
successful authenticated round trip on the runtime's socket (runtime token); `status` is an API request, so its
`running` is that round trip, and `state/runtime.json` serves only the "not running" answer (no live record) without
starting the runtime; a test kills the runtime during start, and another leaves a `runtime.json` of a dead process
and a stale `runtime.token`.
Source:: plan-marshall defect truthful-signals PLAN-TRUTH-150 D8.

[#PM-WATCH-RUN-4]
=== PM-WATCH-RUN-4: The runtime token is fresh, private, and never leaks

Anchor:: link:../specification/runtime-model/01-processes-and-transport.adoc#runtime-token[Runtime Model § Local Trust: Runtime Token],
link:../Requirements.adoc#PM-SEC-4[PM-SEC-4]
Hazard:: A bearer secret shared by file becomes the weak point of the local boundary when it survives a restart, when
a client reads it from a directory or file another user or a symlink controls, or when it reaches a log, the audit
log, an argument vector, or a job's environment.
Guard:: The runtime writes a fresh token before it binds the socket on every start (a test compares the token across
two starts and asserts the file exists before the socket); a client refuses `run/` or `runtime.token` with a foreign
owner, a broader mode, or a symlink, sending nothing (one fixture per case); a canary token appears in no
`daemon.log`, `audit.jsonl`, process argument vector, or job environment; restart fixture: a client holding the old
token gets `401`, re-reads the file exactly once, and succeeds, and a second `401` is not retried.
Source:: design review.

[#PM-WATCH-RUN-5]
=== PM-WATCH-RUN-5: Without a runtime, the three runtime-free verbs start nothing and write nothing

Anchor:: link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime Model § Local API] (Availability),
link:../specification/cli-and-security/01-cli-and-installer.adoc#cli-daemon-access[CLI & Security § Runtime Access & On-Demand Start],
link:../Requirements.adoc#PM-ARCH-7[PM-ARCH-7]
Hazard:: A status query, a client status check, or a drain that silently brings up the runtime or writes a file
breaks the single-writer rule and turns a read-only check into a state change.
Guard:: With no runtime running, `pm-operator status`, `pm-operator client status`, and `pm-operator drain` each run
against a `PM_MCP_BASE` whose tree is hashed before and after: no runtime process is started,
no socket exists afterwards, and the tree is byte-identical (contents, names, and modes), and each verb opens only
files of the closed read-only list of `pm-api`; matched control: each command of the on-demand list (the session
relay `pm-mcp serve --client`, `pm-mcp enter`, a `pm-operator` command that sends an API request, and
`pm-operator runtime start`) starts the runtime on demand; negative control: the worker relay `pm-mcp serve --job`
started without a runtime starts no runtime process.
Source:: design review.

[#PM-WATCH-RUN-6]
=== PM-WATCH-RUN-6: Drain releases slots and task leases, never provider leases

Anchor:: link:../specification/runtime-model/02-startup-recovery-drain.adoc#_drain_stop_upgrade[Runtime Model § Drain, Stop & Upgrade]
Hazard:: A drain that releases merge-queue or review-bot leases lets another plan take a merge slot or a rate window
while the drained plan's merge or review round is still in flight on the provider; a drain that leaves a worker's
generation unfenced lets its late submit land after the restart, and one that counts its tasks as lost spends their
re-offer budget on an operator action.
Guard:: Drain with a running build, a busy writer worker, an idle warm worker, a held merge-queue lease, and a held
review-bot lease: the waits of idle workers are answered `end`; after the drain timeout the build and the remaining
worker are settled `killed`, the worker's generation is fenced and its job token revoked, its task lease released,
and the build and model slots released; both provider leases are still recorded after exit, and the next start
adopts or releases them by the recovery evidence rules exactly as after a crash; after the next start the released
task is offered again exactly once without counting a re-offer, and a late call of the fenced generation is refused
`generation_fenced`.
Source:: design review.

[#PM-WATCH-RUN-7]
=== PM-WATCH-RUN-7: A second runtime exits at once, and one on-demand start wins

Anchor:: link:../specification/runtime-model/01-processes-and-transport.adoc#_singleton_discovery[Runtime Model § Singleton & Discovery],
link:../specification/runtime-model/01-processes-and-transport.adoc#_start_modes[Runtime Model § Start Modes]
Hazard:: A losing runtime that waits for, probes, or cleans up after the holder races the winner's startup; a client
binary that drops `runtime-start.lock` before the round trip lets concurrent commands start further runtimes.
Guard:: A second `pm-mcpd` for the same `PM_MCP_BASE` exits `0` immediately and writes nothing; concurrent `pm-mcp`
and `pm-operator` commands against a stopped runtime start exactly one `pm-mcpd`, and `runtime-start.lock` stays held until the
authenticated round trip succeeds or the runtime start timeout expires.
Source:: design review.

[#PM-WATCH-RUN-8]
=== PM-WATCH-RUN-8: An operator-mode question is listed as waiting, never as stalled or timed out

Anchor:: link:../specification/runtime-model/04-sessions-and-workers.adoc#stalled-plans[Runtime Model § Stalled Plans],
link:../Requirements.adoc#PM-WF-12[PM-WF-12]
Hazard:: A plan waiting on a question in mode `operator` (an unbounded wait, like the integrity pause) is invisible, or is treated as a
bounded wait and expires.
Guard:: Aged fixture: a plan resting on a mode-`operator` question beyond the stalled threshold is listed by
`pm-operator status`, the web app, and the event stream as waiting for an answer with the question named, never as
`stalled`, produces no `plan_stalled` record, and the question never expires; matched control: the same plan without
an open question and without progress beyond the threshold is reported `stalled` with cause `no_progress`.
Source:: design review.

[#PM-WATCH-RUN-9]
=== PM-WATCH-RUN-9: The web listener never outlives, blocks, or relocates with the runtime

Anchor:: link:../specification/runtime-model/02-startup-recovery-drain.adoc#_startup_sequence[Runtime Model § Startup Sequence] (Web listener),
link:../specification/runtime-model/02-startup-recovery-drain.adoc#_drain_stop_upgrade[Runtime Model § Drain, Stop & Upgrade],
link:../Requirements.adoc#PM-SEC-7[PM-SEC-7]
Hazard:: A second HTTP server bound in the same start path as the socket makes an occupied `web.port` a start
failure, so relays and operator verbs lose the runtime over a browser setting; a start that falls back to a free
port serves paired devices at an address nobody enabled; a drain that clears `web.enabled` silently switches web
access off, and one that leaves the TCP socket bound keeps a listener without a runtime behind it.
Guard:: Start test with `web.enabled` true and `web.port` held by a fixture process: the Unix-socket listener
accepts an authenticated round trip, no TCP socket is listening on any other port, `pm-operator status` reports the
web listener closed with the port, and `machine-config.json` is unchanged; drain and stop tests with web access
enabled: after the exit no process listens on `web.port`, `web` in `machine-config.json` is byte-identical, and the
next start opens the listener again; matched control: with the port free the same start opens it.
Source:: design review.

[#PM-WATCH-RUN-12]
=== PM-WATCH-RUN-12: Every `pm-api` refusal carries a code of the closed list

Anchor:: link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime Model § Local API (`/api/v1`)] (Error codes)
Hazard:: Refusals of the local API answered with ad-hoc codes or a bare `500`, so `pm-operator` and the web app cannot
tell a wrong listener from an unknown scope, and a CLI-only endpoint reached over the web listener leaks which scope
exists before it is refused.
Guard:: Integration test over every `pm-api` endpoint and refusal path: each refusal returns the HTTP status and code
of the closed list; a CLI-only endpoint called on the web listener answers `403 cli_only` before argument validation
and scope lookup. Matched control: an unauthenticated request answers `401` without a code.
Source:: design review.

[#PM-WATCH-RUN-13]
=== PM-WATCH-RUN-13: A job created during drain is recorded, never admitted, and settled with the queue

Anchor:: link:../specification/runtime-model/02-startup-recovery-drain.adoc#_drain_stop_upgrade[Runtime Model § Drain, Stop & Upgrade]
Hazard:: A transition that runs while the runtime drains creates a job that is spawned after admission stopped, so it
outlives the drain timeout unsupervised, or is dropped without a record, so the state waits on a job that never
settles; a `pm_build` during drain blocks until the exit instead of answering.
Guard:: Scenario test on a test clock: a transition during drain creates a build job and a `git` job; both are recorded
`queued`, never spawned, and settled `status: ended`, `fate: killed` at exit without a signal, and the next start's
recovery routes their states like any `killed` job; a `pm_build` during drain returns the queued job with its `job_id`
continuation at once. Matched control: a job admitted before the drain began runs to its end within the drain timeout.
Source:: design review.

[#PM-WATCH-RUN-14]
=== PM-WATCH-RUN-14: The first start on a fresh machine creates its base before it locks

Anchor:: link:../specification/runtime-model/01-processes-and-transport.adoc#_start_modes[Runtime Model § Start Modes],
link:../specification/runtime-model/02-startup-recovery-drain.adoc#_startup_sequence[Runtime Model § Startup Sequence]
Hazard:: On a machine without `<PM_MCP_BASE>` the start procedure cannot take `locks/runtime-start.lock`, or creates the
directories with the process umask, so the runtime's permission check (step 3) refuses the start with exit code `77`
on a directory the client binary created itself, or accepts a world-readable one.
Guard:: Test per client binary (`pm-mcp`, `pm-operator`) against an empty `PM_MCP_BASE` under a permissive umask:
the client creates `<PM_MCP_BASE>`, `locks/`, and `logs/` with mode `0700` before it takes the start lock and spawns
the runtime (whose output redirect to `logs/daemon.log` needs the directory), the runtime creates `run/`,
`enrolments/`, and `state/` with mode `0700` before its permission check, and the start succeeds; matched
control: a pre-existing `<PM_MCP_BASE>` with mode `0755` is checked, never repaired, and refuses the start with `77`.
Source:: design review.

[#PM-WATCH-RUN-15]
=== PM-WATCH-RUN-15: Open: an upgrade must not be undone by the old relays and the service unit

Anchor:: link:../specification/runtime-model/02-startup-recovery-drain.adoc#_drain_stop_upgrade[Runtime Model § Drain, Stop & Upgrade]
Hazard:: Undecided: after the `PATH` symlink switch and the drain, the relays of open host sessions are still the old
binaries and resolve `PM_MCP_HOME` from their running executable, so their next request starts the old `pm-mcpd`
again; the per-user service unit (Start Modes) still names the old path. The upgrade is reverted without notice and
the old installation directory is in use again. Options: (1) host sessions must be restarted, a relay refuses to
start a runtime that is not the current `PATH` target, and the upgrade re-runs `pm-operator runtime install`; (2) a
stable `<PM_MCP_HOME>` `current` link that every binary and the unit resolve; (3) accept and document.
Recommendation: 2, one mechanism covers relays and the service unit.
Guard:: The plan implementing this anchor decides the point (with the operator where it changes scope), records
the result in the specification and the requirement it touches, and deletes this item.
Source:: `runtime-model/02-startup-recovery-drain.adoc:59` (Upgrade), `runtime-model/01-processes-and-transport.adoc:165`
(Start Modes), `cli-and-security/01-cli-and-installer.adoc:51` (Resolution of `PM_MCP_HOME`).

[#PM-WATCH-RUN-17]
=== PM-WATCH-RUN-17: The socket is private before it is announced, and no native code runs from the temporary directory

Anchor:: link:../specification/runtime-model/01-processes-and-transport.adoc#_transport_endpoint[Runtime Model § Transport Endpoint],
link:../specification/runtime-model/02-startup-recovery-drain.adoc#_startup_sequence[Runtime Model § Startup Sequence],
link:../Requirements.adoc#PM-TECH-3[PM-TECH-3]
Hazard:: Vert.x creates the Unix socket under the process `umask`, so a runtime started from a shell with `umask 022`
announces a `0755` socket in `runtime.json`; a native `pm-mcpd` that cannot find the Netty transport library beside
itself lets Netty extract it into the temporary directory on every start (about 250 ms, so the cold-start bound fails)
and loads native code from a directory every job can write.
Guard:: Start test under `umask 022`: when `state/runtime.json` first exists, the socket is already `0600` and owned
by the user; a socket whose mode cannot be restricted refuses the start with `77`. Native start test of the release
layout: no file of the Netty library appears in the temporary directory, and with the library removed from
`<PM_MCP_HOME>/bin/` the start is refused with a diagnostic naming the path; matched control: the cold-start figure of
`PM-TECH-3` holds with the library in place.
Fixture:: socket mode `0755` after bind; cold start 292 ms median with the extracted library, 40.5 ms with it beside
the binary (macOS arm64).
Source:: roadmap/technical_macos.adoc M1, M2.

== Relay

[#PM-WATCH-RUN-16]
=== PM-WATCH-RUN-16: The runtime refuses `subscriptions/listen` and announces no list changes

Anchor:: link:../specification/runtime-model/03-relay.adoc#_host_protocol_forms[Runtime Model § Host Protocol Forms],
link:../Requirements.adoc#PM-ARCH-3[PM-ARCH-3], link:../Requirements.adoc#PM-SKILL-2[PM-SKILL-2]
Hazard:: The Quarkus MCP server declares `tools.listChanged: true` and acknowledges `subscriptions/listen` with a stream
that stays open for the whole session without a final response; a host then waits for change notifications the
sessionless runtime never sends, and left unanswered the listen blocks Claude Code's start for 27 s. Equally, the
`Mcp-Session-Id` the server attaches to every `initialize` response turns a session-opening host into a
session-holding one.
Guard:: Test pinning both: `server/discover` and `initialize` results declare `listChanged: false` for every list and no
resource subscription, and `subscriptions/listen` is answered at once with `-32601` without opening a stream; the
`initialize` response carries no `Mcp-Session-Id`, and a following request without a session is served; a
`server/discover` without the protocol keys in `_meta` is refused `400`. A dependency upgrade of
`quarkus-mcp-server` re-runs the test before it lands.
Fixture:: Claude Code: 27 s start delay with an unanswered listen; after `-32601` three retries at +1, +3, +7 s, then
none; all tools usable.
Source:: roadmap/technical_macos.adoc M8.

[#PM-WATCH-RUN-10]
=== PM-WATCH-RUN-10: A host cancel of an answered request cancels nothing

Anchor:: link:../specification/runtime-model/03-relay.adoc#relay-rules[Runtime Model § Relay Rules] (rule 4),
link:../Requirements.adoc#PM-ARCH-3[PM-ARCH-3]
Hazard:: OpenCode sends `notifications/cancelled` for every request it has already received an answer for;
treated as the cancel of pending work, each such notification cancels the wait or the job that the answer started.
Guard:: Relay and runtime fixtures: a cancellation whose `requestId` the relay has already answered is dropped and
never forwarded; the runtime ignores a cancellation of a request it has answered; a cancellation of a pending
`pm_wait` ends only that call without consuming or leasing a task; no cancellation ends a job; matched control: a
cancellation of a pending `pm_build` wait ends that wait and leaves the build running.
Source:: harness-as-worker evaluation (doc/specification/evaluation.adoc).

[#PM-WATCH-RUN-11]
=== PM-WATCH-RUN-11: Identity arguments never appear in a tool schema

Anchor:: link:../specification/runtime-model/03-relay.adoc#relay-rules[Runtime Model § Relay Rules] (rule 5),
link:../Requirements.adoc#PM-ARCH-3[PM-ARCH-3]
Hazard:: With the worker identity, generation, and role visible as tool arguments, the OpenCode model filled them
with invented values and kept them in its compaction summary; after a compaction an interactive model passed an
invented worker id remembered from another session.
Guard:: A `tools/list` through the relay, for a session and a worker relay of every client, contains no property of
the identity set (`generation_id`, `role`, `worker`, `job_token`) in any `inputSchema`; a `tools/call` carrying such an
argument reaches the runtime without it; the runtime's own tool schemas declare none, and identity, role, and
generation are taken only from the relay's headers; matched control: a call whose header identity differs from an
invented argument is bound to the header identity.
Source:: harness-as-worker evaluation (doc/specification/evaluation.adoc).

== Server-Driven Scopes

[#PM-WATCH-RUN-2]
=== PM-WATCH-RUN-2: Stalls and idle gaps on an active plan are derived

Anchor:: link:../specification/runtime-model/04-sessions-and-workers.adoc#stalled-plans[Runtime Model § Stalled Plans],
link:../Requirements.adoc#PM-ARCH-7[PM-ARCH-7], link:../Requirements.adoc#PM-SEC-6[PM-SEC-6]
Hazard:: A stalled plan left no record; an agent that announced continuation and then ended its turn halted the plan
unnoticed.
Guard:: `pm-operator status`, the web app, and the epic view derive `stalled` (cause `no_progress`) for non-terminal
scopes without pending condition or awaited event (no running job, no task queued or leased within its budget, no
open external wait, waiver wait, or question record) whose last transition or task progress is older than the
compiled stalled threshold, and the runtime records one `plan_stalled` audit record per episode with the idle span;
a role the supervisor cannot serve stalls nothing, because its tasks close `role_unavailable`; metrics derive idle
gaps from the audit log; nothing of it reaches a model-facing representation; test with an aged fixture, a blocked
control, and a control with a leased task, neither of which is reported.
Fixture:: a 17-min gap 13:45:20 → 14:02:28; 12h54m idle vs 2h8m worked; a deferred stall nothing recorded
(D-087-g).
Source:: plan-marshall defect post-run-quality PLAN-PRQ-04 D0; truthful-signals (quality-aspect) PLAN-217 D3.

== Verification

[#PM-WATCH-RUN-3]
=== PM-WATCH-RUN-3: Tests never observe machine-wide state

Anchor:: link:../specification/runtime-model/04-sessions-and-workers.adoc#_verification[Runtime Model § Verification],
link:../Requirements.adoc#PM-DIST-5[PM-DIST-5], link:../Requirements.adoc#PM-TEST-4[PM-TEST-4]
Hazard:: A test-isolation guard blamed a 52.33 s test for a concurrent plan's write of a machine-global lock file.
Guard:: Every test that starts a runtime uses its own `PM_MCP_BASE`; isolation guards ignore writes outside the test's
base.
Fixture:: a concurrent plan's `merge.lock` write during a run of 23951 passing tests.
Source:: plan-marshall defect truthful-signals (quality-aspect) PLAN-205 D4.
