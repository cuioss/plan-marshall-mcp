== Overview

This document specifies the end-to-end phase state machines (Phases 1–6), transition guards, Q-Gate validation loop, change-type and scope-deviation contracts, Phase 5 envelope execution and verification sweep, Phase 6 finalize step ordering bands, `FinalizeStepDescriptor` schema, verdict currency rules, pre-merge review barrier, and cross-plan merge mutex for *plan-marshall-mcp* (`PM-MCP`).

In `PM-MCP`, the prose-driven orchestrator loops, phase handshake files (`handshakes.toon`), and intra-phase step-recording rituals (`mark-step-done`, `assert-step-recorded`) of the legacy script architecture are replaced by deterministic server-owned state machines defined in `classpath:/workflows/*.pmwf` and executed by `pm-mcp-core`.

=== Lifecycle Topology (Phases 1–4)

The planning lifecycle is a server-enforced state machine spanning `phase-1-init`, `phase-2-refine`, `phase-3-outline`, and `phase-4-plan`. Sub-states that previously lived only in the orchestrating model's conversation context (`refine.awaiting_answers`, `outline.review`, Q-Gate iteration counters, and re-dispatch counters) are persisted in `mcp/status.json` so that any session restart or `/clear` resumes at the exact sub-state via `pm_state(plan_id)`.

Every state of Phases 1–4 is catalogued in the State Catalogue (link:state-catalogue.adoc#state-catalogue-init[`init`], link:state-catalogue.adoc#state-catalogue-refine[`refine`], link:state-catalogue.adoc#state-catalogue-outline[`outline`], link:state-catalogue.adoc#state-catalogue-plan[`plan`]; generic per-phase states in link:state-catalogue.adoc#state-catalogue-generic[Generic Per-Phase States]; condition overlays in link:state-catalogue.adoc#state-catalogue-conditions[Conditions]).

│ Phase 1: init (pm_start)                                                         │
│  init.classify -> [init.<question> states] -> init.ready                         │
│  (Plan source resolution, phantom-ID guard, recipe match, initial lane routing)  │
│  -> [init.light-gate (light only, server): |A| + |neighbours| > 25 | |A| > 8 |   │

A plan started from the `local_changes` source does not traverse Phases 2–4: it runs in the `land` lane (<<land-lane>>) from `init.ready` through `land.*` verification states directly into Phase 6.

A plan in the `light` planning lane does not traverse the Phase 2 states (`refine.baseline-reconcile`, `refine.analyze`, the confidence loop, `refine.qgate`): after the server-side light gate (`init.light-gate`) it enters Phase 3 and runs one collapsed light envelope (`outline.light`) that folds refine without the loop, the Simple outline, and deliverable derivation together, mirroring `plan-marshall`'s light lane. The deep lane keeps the full refine loop -> outline -> plan pipeline. The phase enum is unchanged; how the light envelope satisfies the Phase 2 and Phase 3 artifact gates is specified in <<planning-lanes>>.

=== Phase 1 (`init`): Plan Sources, Phantom-ID Refusal & Classifiers

==== Plan Source Contracts

`pm_start` initializes the plan directory (`<PM_MCP_BASE>/projects/<project_id>/plans/<plan_id>/`, link:filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), `request.md`, `references.json`, and `mcp/status.json` from exactly one of five closed plan sources (`PlanSource`):

[cols="1,2,4"]
|===
|Source (`plan_source`) |Input Parameters |Server Initialization & Verification Behavior

|`request`
|`description` (or `request`), optional `plan_slug`, `base_branch`
|Writes `original_input` to `request.md`, runs the deterministic recipe scorer ahead of the planning-lane router (as for `issue` and `lesson`; the operator's `recipes.auto_route` decides auto-route vs ask), detects initial domains from narrative path tokens, and checks for sibling plan collisions.

|`issue`
|`issue_number`, optional `plan_slug`, `base_branch`
|Spawns an enrolled CI provider job to fetch the issue title and body into `request.md` (passing untrusted external content through the deterministic ingestion validator), records `issue_number` in `references.json`, and schedules asynchronous CI mirror jobs to post clarified requirements and the approved outline back to the issue after Phase 2 and Phase 3 transitions.

|`lesson`
|`lesson_id`, optional `plan_slug`, `base_branch`
|Resolves the lesson in the main-anchored lesson store (`manage-lessons`), executes a deterministic *source premise check* verifying that cited files and symbols in the lesson still exist in the current tree (transitioning to `init.lesson-premise` with obsolescence options if the premise is already resolved or invalid), and claims the lesson for the new plan in the plan initialization transaction (`claim{plan_id, claimed_at}` in its front matter; the lesson file stays in the lesson store and is never moved into the plan). A lesson that is already claimed, retired, or not resolvable is refused (`lesson_unavailable`). The claim ends with the plan: completion with a merge retires the lesson (verdict `applied`), closing it as obsolete in `init.lesson-premise` retires it (verdict `obsolete`), and an abort or `delete-plan` releases the claim, leaving the lesson `active` (link:store-schemas.adoc#lesson-record[Store Schemas Specification, Lesson Record, Claim]). There is no carry-back and no deletion veto.

|`recipe`
|`recipe_id`, optional `recipe_params`, `base_branch`
|Binds the plan to a registered recipe definition (`skill://pm/recipe/<name>/SKILL.md`), derives `plan_id` as `recipe-{recipe_key}-{yyyy-mm-dd-hh-mm-ss}` (UTC; see link:domain-extensions.adoc#recipe-plan-id[Domain Extensions Specification]) to prevent git branch and worktree collisions across repeated runs of the same recipe, sets `confidence = 100` and `planning_lane = deep` (`track = complex`), renders `status.metadata.pr_title` at `init.recipe-selected` from the recipe's required `pr_title_template` with the bound `recipe_params` substituted (link:domain-extensions.adoc[Domain Extensions Specification], Declarative Recipe Descriptor Schema), so the recipe shortcut reaches Phase 3 with a title and no model work, and skips Phase 2 quality analysis and Phase 3 change-type/Q-Gate steps: its Phase 3 entry is `outline.recipe-entry` (an `auto` state deriving the deliverables from the harvest, or from the request for a `request_scoped` recipe), followed by `outline.recipe-confirm` (link `confirm_recipe_targets`) and `outline.review`. `recipe_params` are validated against the recipe's own input schema (`parameters_schema`). An empty harvest is a no-op: the plan ends `completed` with `merge_outcome: no_pr` and the fact `empty_harvest`, never with an empty pull request (link:domain-extensions.adoc#_tier_1_init_routing_deterministic_deliverable_generation[Domain Extensions Specification, Tier-1 Init Routing item 7]).

|`local_changes`
|`local_changes: true`, optional `summary`, `plan_slug`, `base_branch`
|Captures the user's own current changes of the main checkout: every dirty and staged path with its porcelain code and content digest, plus the commits of the checked-out branch ahead of `origin/<base_branch>`. The capture is recorded as `references.json` `captured_changes`, its paths (including those changed by the commits ahead) become `declared_files`, the plan's declared footprint, and `request.md` records the change set together with the `summary`. An empty change set creates no plan and is refused with `no_local_changes` (a scope-less `pm_start` refusal, link:mcp-tools.adoc#pm-start-refusal[MCP Tools Specification]). Sets `planning_lane = land` and routes the plan into the land lane (<<land-lane>>). How the captured changes move from the main checkout onto the plan's branch and worktree is a git mechanic left open (open design topic: git/GitHub/GitLab approach).
|===

==== Plan ID Derivation & Phantom-ID Refusal Guard

The server derives or validates `plan_id` against a strict lexical grammar before creating any directory on disk:

1. *Canonical Grammar*: A `plan_id` matches the link:identifiers.adoc#id-plan-id[`plan_id` grammar] of the Identifier Registry, the single definition of the plan ID grammar; every schema that restates it (`plan_id` tool properties, `scope_id`, queue rows) matches it exactly. A `plan_slug` (link:identifiers.adoc#id-plan-slug[registry]) becomes the `plan_id` verbatim; without a slug the server derives one from the plan source. Recipe plans are `recipe-{recipe_key}-{yyyy-mm-dd-hh-mm-ss}` (link:domain-extensions.adoc#recipe-plan-id[Recipe Plan ID]), which the length bound admits because a `recipe_key` has at most 37 characters (link:identifiers.adoc#id-recipe-plan-id[registry]). Epic IDs use the same grammar (mirroring `plan-marshall`, which validates the epic slug with its plan-id validator).
2. *Phantom-ID Refusal*: The validator explicitly rejects any candidate `plan_id` or `plan_slug` matching either the link:identifiers.adoc#id-lesson-id[`lesson_id` grammar] or a UUID / hex-digest pattern (`^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$`, a bare hex string of 12 or more characters `^[0-9a-fA-F]{12,}$`, or a token beginning case-insensitively with `execution-context` or `agent-`). Rejecting these shapes prevents callers from accidentally passing a lesson ID or dispatch/session UUID into `plan_id` and creating a phantom plan directory.
3. *Never-Reused IDs*: A candidate `plan_id` that already names a live plan (`plans/<plan_id>/` of the project's machine store) or an archived plan (`archive/<plan_id>/`, link:filesystem-layout.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]) is refused with `plan_id_taken`, naming where it exists. The refusal is the collision dialogue: it is a scope-less `pm_start` refusal (link:mcp-tools.adoc#pm-start-refusal[MCP Tools Specification, `pm_start` Refusals]) that keeps the pending entry record and names the existing `plan_id` and a free alternative slug; resuming is `pm_state` on the existing plan, renaming is a new `pm_start` with another `plan_slug`, and replacing an existing plan is operator deletion (`delete-plan`) followed by a new `pm_start`. Because the archive path carries no date, this refusal is what keeps every archived plan addressable by its `plan_id` alone.

==== Deterministic Init Classifiers & Workflow Settings
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-1[PM-WATCH-PHASE-1]_

During `init.classify`, the engine executes pure, model-free classifiers in a fixed order:

1. *Recipe Match before Lane Routing*: For every source other than `recipe` (`request`, `issue`, `lesson`; `local_changes` is not scored), the registry-wide recipe scorer evaluates the request narrative first; scoring always runs, and the operator's `recipes.auto_route` (`local-config.json`) only chooses between auto-routing (when `true` and the top confidence reaches the compiled auto-route threshold `0.6`, `plan-marshall`'s default, not configurable) and asking in `init.recipe-candidate` (link:domain-extensions.adoc#_tier_1_init_routing_deterministic_deliverable_generation[Domain Extensions Specification, Tier-1 Init Routing]). In the same step the server computes the Tier-1 request-aspect classification (`status.metadata.request_aspect`) and, for source `lesson`, the doc-shaped predicate that routes a doc-shaped lesson to the `lesson-cleanup` recipe (items 9 and 10 there). An explicit `recipe` source selection is never overridden by the scorer.
2. *Initial Planning-Lane Router*: Computes the initial `planning_lane` (`light` or `deep`) from the request with zero discovery (`deep` for every plan when the team's `workflow.json` `plan.phase-1-init.minimum_lane` is `deep`, <<planning-lanes>>), and the pre-route `scope_estimate` (`none`, `surgical`, `single_module`, `multi_module`, `broad`). `scope_estimate` is derived from expected-modification paths only; read-only references never raise it. The pre-route value is persisted immutably as `scope_estimate_pre_route`; every later update of `scope_estimate` (Phase 2 or Phase 3) records its own provenance under `scope_estimate_provenance[]` instead of overwriting the pre-route evidence.
3. *Sibling Collision Detector*: Scans live plans for overlapping target modules or affected file paths; if an overlap is found, transitions to `init.sibling-collision` to resolve the collision (`proceed`, `rename`, or the request `abort`, which raises the operator decision `abort-plan`).
4. *Workflow Settings Resolution*: Reads the project's effective configuration (link:store-schemas.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]): the team's `minimum_lane` (<<planning-lanes>>), `compatibility`, and `simplicity`, and the operator's `recipes.auto_route`; computes the execution posture (`minimal | standard | full`) for the preview; and copies the operator's `continuation.default_policy` into the plan's `continuation_policy` (`mcp/status.json`). The per-plan `continuation_policy` (`stop_at_phase_boundary` or `stop_on_issue_only`, changed only through the operator channel) is the only autonomy setting: it decides whether the session continues across a phase boundary or stops there. *Deliberate change vs. `plan-marshall`*: the five auto-continue flags (`init_`, `plan_`, `execute_`, `finalize_`, `loop_back_without_asking`) and the `lane_selection` prompt switch do not exist; no setting turns an operator-authorizing decision (outline approval, the merge gates) into an automatic transition. The refine confidence threshold (`95`), the recipe auto-route threshold (`0.6`), the lane prune thresholds, and the iteration caps are compiled constants.
5. *Base Stamp*: Stamps `main_sha` in `mcp/status.json` from `git rev-parse origin/<base_branch>`. It is written once here and re-stamped only by the `sync-baseline` and `branch-cleanup` rebases; the Outside-World Invariants guard reads it as the producer of the baseline-drift check.

At `phase-4-plan` entry the lane predicate is re-evaluated with the settled inputs (declared deliverables and their expected modifications) and the result is logged as `lane_reevaluation` in `audit.jsonl`; the re-evaluation never re-routes the plan (see <<_lane_ratchet_rules>>).

=== Routine User Interaction vs Operator-Authorizing Decisions
_See Requirement link:../Requirements.adoc#PM-WF-12[PM-WF-12: Routine User Dialogue vs Operator-Authorizing Elicitation]_

_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-69[PM-WATCH-PHASE-69]_

`PM-MCP` separates interactive questions into two security classes with distinct transport rules:

[cols="2,2,2,3"]
|===
|Interaction Class |Target States & Decisions |Permitted Channels |Fallback & Audit Semantics

|*Routine User Dialogue* (Non-Authorizing)
|Obsolete lesson premise (`init.lesson-premise`: `continue`, or `close`), recipe selection (in its own state `init.recipe-candidate`), ambiguous domain selection (`init.domain-choice`), sibling plan collision (`init.sibling-collision`), execution posture choice (`init.posture-choice`: `minimal`, `standard`, `full`), Phase 2 request clarifications (`refine.awaiting_answers`), Phase 3 design clarifications (`outline.awaiting_answers`), Q-Gate iteration exhaustion (`*.qgate-exhausted`: `edit` or `abort` only). A routine answer that would end the plan (`close`, `abort`) is only a request: the link `abort` (rel `escalate`) raises the operator-authorizing decision `abort-plan` (next row).
|Host MCP Elicitation (preferred), or model-relayed `submit` link (`answer_questions`) when host elicitation is unsupported or unavailable.
|The plan persists a state of kind `awaiting_user`, named by its question (link:state-catalogue.adoc#_state_kinds[State Catalogue, State Kinds]), carrying a typed `questions` schema in `facts`. When answered via the model-relayed `submit` link, the transition succeeds and records `channel: "model_relayed"` in `audit.jsonl`.

|*Operator-Authorizing Decisions* (Gate-Forcing / Privileged)
|Solution outline approval (`outline.review` -> `phase-4-plan`), scope-deviation `accept` (`execute.deviation-review`), handshake or baseline drift override, bare-transition artifact-gate exemption (`--allow-bare-transition`), pre-rebase overlap override, merge-authorization grants for every gap class of the roster (`review_barrier_gap`, `merge_action`, `red_ci_gate`, `rereview_timeout`, `find_step_completion`, the last one being the `automatic-review` force-done), Q-Gate override on exhaustion (`force-gate` with its `exemption_class`), the decision on a hypothesis refuted twice (`refine.hypothesis-refuted`: continue narrowed, or abort for re-staging through `abort-plan`), the resolution of `execute.awaiting-infeasible-decision` after an `infeasible` task (`remove-deliverable` or `loop-back-outline`, <<_task_envelope_execution_independent_server_verification>>), an operator task skip (`skip-task` with its mandatory reason), ending the plan from any phase (`abort-plan`: `aborted` enters `plan.aborted`, `resumed` returns to the requesting state), ending an epic (`abort-epic`: `aborted` enters `epic.aborted`, `resumed` returns to `epic.active`), a failed land-lane verification (`land-verification-failed`: `recapture` or `abort-plan`), archiving over an open, unmerged pull request (`archive-with-open-pr`: `close-pr-and-archive` or `keep`), and plan deletion (`delete-plan`). The decision kinds and their outcome classes are registered in the link:workflow-dsl.adoc#decision-registry[Workflow DSL Specification, Decision Registry].
|Host MCP Elicitation, or Authenticated Operator CLI (`pm-mcp operator ...`).
|*Strict Link Omission (`PM-WF-3`)*: No model-invocable `submit` or `noop` link is ever emitted to approve or force these gates. If the host does not support MCP elicitation, the engine raises the `blocked` condition on the current state (link:state-catalogue.adoc#condition-blocked[State Catalogue, Conditions]; the state and `call_stack` stay unchanged), emits the exact `pm-mcp operator` command in `facts.operator_command`, and offers only the link `wait:decision:<decision_id>` (rel `wait`), a bounded wait on the pending operator decision record, until the operator acts; the resolution is routed as an outcome of that state.
|===

*Intent Amendments*: Phase 2 answers are written into `request.md` (`## Clarifications`). Every later answer that changes the plan's intent (an answer in a state of kind `awaiting_user` in Phases 3–6, an answered task question of Phase 5, deviation guidance, or a refuted premise) is persisted as an entry of `mcp/status.json -> amendments[]` (`at`, `phase`, `source: operator | refutation`, `text`, `supersedes`). Every later representation that renders the request (outline, `create-pr`, landing envelope) includes the amendments, so a superseded statement of the request never reaches a later phase unmarked.

==== Typed Question Envelope Schema (`awaiting_user`)

Sub-agents operating in leaf `execution-context` scopes are forbidden from prompting the user in-leaf or blocking on `escalate`. Instead, a sub-agent completes its analysis pass using its best judgment and includes a batched question list in its `submit` payload (`refine_prompt` or `outline_prompt`) as the free parameter `questions:list<schema[question-envelope]>?`, validated by the server against the named schema `question-envelope` (link:hypermedia-format.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]; link:dispatch-and-effort.adoc#question-envelope-schema[Dispatch & Effort Specification, Prompt Envelopes & Entity Escalation Protocol]). Each persisted question is rendered to the operator in the following Java record and TOON tabular structure:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.dialogue;

import java.util.List;

public record UserQuestion(
    String id,
    String header,
    String question,
    List<String> options,
    String recommended,
    boolean allowFreeText
) {}
----

Every option string in `options` is authored as a two-sided contract whose label explicitly names the workflow branch selected when chosen, with the `recommended` option listed first.

=== Phase 2 (`refine`): Quality Aggregation, Domain Widening & Bounded Re-Dispatch

The Phase 2 states run for `deep`-lane plans only (including a plan ratcheted from `light` to `deep`). A `light`-lane plan never enters `refine.analyze` or its confidence loop; its refine work is folded into the collapsed light envelope (<<planning-lanes>>).

==== Phase Entry & Baseline Reconciliation
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-2[PM-WATCH-PHASE-2]_

At `phase-2-refine` entry, the engine caches loop-invariant inputs (`request.md`, `references.json`, `module_mapping.json`, and the architecture overview) so they are read once per phase rather than re-read inside the confidence loop. When a base branch is configured, `refine.baseline-reconcile` runs a non-mutating `git merge-tree` probe against upstream and classifies drift into three outcomes:

* `no_overlap`: Upstream commits touch disjoint files; advances directly to `refine.analyze`.
* `overlap_no_content_conflict`: Overlapping files merge cleanly; records `auto_reconcilable: true` without mutating the tree (deferring the actual rebase to Phase 5/6) and advances to `refine.analyze`.
* `overlap_with_content_conflict`: Content conflicts exist; emits blocking Q-Gate findings so the conflict is absorbed during request refinement.

* *Probe Parsing*: The probe runs `git merge-tree --write-tree --name-only -z` with `LC_ALL=C` and reads only the conflicted-file section; informational and message lines are never paths. The conflict count is the number of distinct conflicted paths. The locale pin applies to this parse job only, not to the `worktree_sha` git invocations (link:job-runtime.adoc[Job Runtime Specification]).
* *Overlap Population*: Overlap is computed between the upstream changed paths and the plan's declared ∪ derived footprint known at that point, never only the in-flight diff (which is empty before execution), so a first Phase 5 entry never reports `conflict_count: 0` merely because nothing was written yet.
* *Drift Routing*: Content overlap (`overlap_with_content_conflict`) is the only drift routed to refinement. A `main_sha` ancestry drift is cleared only by a sync or rebase transition (`sync_rebase`) or by operator escalation; a refine re-dispatch is never offered as its remedy.

==== Five Quality Dimensions & Fixed-Weight Confidence Aggregation
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-6[PM-WATCH-PHASE-6], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-68[PM-WATCH-PHASE-68]_

During `refine.analyze`, the dispatched refine sub-agent executes source-premise verification (checking cited files, flags, and APIs against the codebase) and proposed-fix verification (constructing a semantic probe to verify whether a proposed fix resolves the stated symptom), maps affected modules, estimates scope (`none`, `surgical`, `single_module`, `multi_module`, `broad`), authors a conventional-commit `pr_title` ($\le 72$ characters, distinct from the human plan `title`), and submits raw scores (`0..100`) for the five quality dimensions plus architectural module mapping.

* *Premise Verdicts*: Source-premise verification records each premise with the verdict record of epic Spec Re-Grounding (link:dispatch-and-effort.adoc#_server_derived_landing_facts_spec_re_grounding_cross_plan_locks[Dispatch & Effort Specification, Verdict Record]): label `observed` or `hypothesis`, verdict `corroborated | contradicted | partially_exercised | unverifiable`, and `scope_change` (`none | rescoped`); no second vocabulary exists. A command flag mandated by the request is a premise and must name a module of the command's actual reactor that the flag affects.
* *Open Hypotheses of Emitted Plans*: For a plan emitted from an epic (`from_epic`), every `hypothesis`-labelled claim of its spec section is surfaced in `facts.open_hypotheses`. `submit:refine` must carry a verdict per claim (`confirmed` or `refuted`, citing the named artifact), and any `refuted` claim routes to `refine.awaiting_answers` for re-scoping instead of `refine.ready`; that pass counts as the one refine re-dispatch. A claim refuted again in the second pass routes to `refine.hypothesis-refuted`: the server appends a `hypothesis_refuted` event (claim, evidence, plan) to the epic inbox, and the plan waits on an operator-authorizing decision, either continuing with a narrowed scope (recorded as an intent amendment) or aborting through the decision `abort-plan` (`plan.aborted`) so the epic re-stages the plan with a corrected premise. There is never a third refine pass.

The server-side `ConfidenceAggregator` computes the overall confidence deterministically using fixed weights (zero LLM arithmetic):

[cols="2,1,4"]
|===
|Dimension |Fixed Weight |Verification Criteria

|`correctness`
|20%
|Technical validity of referenced modules, APIs, flags, source premises, and proposed fixes against the live architecture.

|`completeness`
|20%
|Presence of clear scope boundaries, acceptance criteria, test expectations, and cross-module dependencies.

|`consistency`
|20%
|Absence of internal contradictions or conflicting constraints across request sections and architecture rules.

|`non_duplication`
|10%
|Absence of redundant or overlapping requirement statements.

|`ambiguity`
|20%
|Single unambiguous interpretation of terminology, target scope, and measurable outcomes (`100` = unambiguous).

|`module_mapping`
|10%
|Confidence in mapping the request to concrete project modules and dependency directions.
|===

$$\text{confidence} = \lfloor 0.20 \cdot S_{\text{corr}} + 0.20 \cdot S_{\text{comp}} + 0.20 \cdot S_{\text{cons}} + 0.10 \cdot S_{\text{nondup}} + 0.20 \cdot S_{\text{ambig}} + 0.10 \cdot S_{\text{mod}} \rfloor$$

* All six dimensions are required parameters of `submit:refine`; a submission omitting one is rejected with `invalid_link_args`, so no absent score is ever folded into the aggregate as `0`.
* *Evidence Class*: `submit:refine` carries `evidence_class` (`self_assessment`, `operator_answered`, or `downstream_reproduced`), persisted beside the score and shown in `facts`. The server checks it against its records: `operator_answered` is refused (`invalid_link_args`) unless an answered `refine.awaiting_answers` round exists in this plan, and `downstream_reproduced` requires an `evidence_ref` naming the reproducing artifact (a build job, test run, or re-grounding verdict). No heuristic fires on an all-100 score by itself: only `self_assessment` with every dimension at `100` on a plan without `from_epic` adds the advisory fact `self_assessed_full_confidence` (never blocking, never a link change), while an all-100 score on an emitted plan's pre-verified specification is expected and adds nothing.
* The aggregated score is persisted to `status.metadata.confidence` and compared against `confidence_threshold`, the compiled constant `95` (not configurable: lowering it would only admit less-clarified requests).
* The server also validates that `compatibility` (`breaking | deprecation | smart_and_ask`, compiled default `breaking`) and `simplicity` (`lean | pragmatic | defensive`, compiled default `lean`) are resolved from the effective configuration and persisted in the plan.

==== Widen-Only Domain Re-Merge
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-67[PM-WATCH-PHASE-67]_

Once concrete `affected_files` are identified in `refine.analyze` (for a `light`-lane plan: on acceptance of the light envelope's submission, before the single narrowing pass of Phase 3), the server runs `domain-detect` over those file paths (`file_globs` and `always_on` inclusion legs) and computes the set union with the existing `references.domains`:

$$\text{domains}_{\text{new}} = \text{domains}_{\text{cached}} \cup \text{detect}(\text{affected\_files})$$

* *Monotonic Widening Invariant*: Phase 2 may **only widen** `references.domains`, never narrow it, ensuring convergence across refine iterations. If `affected_files` produce zero narrative or glob matches, `domain-detect` returns all offerable domains under `reason = "over_provisioned_resolve"`; that temporary over-provisioning is narrowed exactly once in Phase 3 after deliverables are declared.
* *Match Provenance*: `domain-detect` returns, per domain, its `source` (`always_on`, `glob`, or `narrative`) and `matches: N`, rendered in `facts`. A result resting only on `always_on` legs with zero matches is reported `floor_only`, never as a confident single-domain answer.

==== Single-Batch Clarification & Re-Dispatch Ceiling

If $\text{confidence} < \text{confidence\_threshold}$:

1. The sub-agent submits its best-judgment `clarified_request` alongside a single batched `refine_prompt` (`questions:list<schema[question-envelope]>?`, <<_typed_question_envelope_schema_awaiting_user>>) containing at most 4 clarification questions prioritized by `Correctness > Consistency > Completeness > Ambiguity > Non-Duplication`.
2. The engine persists the questions in `mcp/status.json`, transitions to `refine.awaiting_answers`, and collects the user's answers in one batch.
3. Upon receiving the answers, the engine writes the `## Clarifications` and `## Clarified Request` sections, increments `refine_redispatch_count` in `mcp/status.json`, and re-dispatches `refine.analyze` **at most once** (`refine_redispatch_count <= 1`).
4. If the second pass still yields $\text{confidence} < \text{confidence\_threshold}$, the engine does **not** loop again (a hypothesis refuted again goes to `refine.hypothesis-refuted` instead, see Open Hypotheses of Emitted Plans); it flags `low_confidence_manual_review: true` in `facts` and advances to `outline` (where `outline.review` gates progression before task creation).

[#planning-lanes]
=== Planning Lanes & One-Way Ratchet (`light` -> `deep`)

`PM-MCP` routes the planning pipeline (Phases 2–4) along one of two structural lanes stored in `status.metadata.planning_lane`, which deterministically drives the legacy `track` field (`light => simple`, `deep => complex`). The lane is the structural selector for the whole Phase 2–4 pipeline, mirroring `plan-marshall` (`plan-marshall/workflow/planning.md` § Planning-lane dispatch and `phase-3-outline/workflow/light-lane.md`; re-verify before implementing): a `light` plan runs one collapsed light envelope, a `deep` plan runs the full refine loop -> outline -> plan pipeline.

[cols="1,2,4"]
|===
|Lane |Target Scope |Discovery & Execution Contract

|`light`
|Bounded, localized changes (`scope_estimate` in `{surgical, single_module}` with known target files)
|Skips the Phase 2 states. After the server-side light gate (<<light-gate>>) passes, runs *one* collapsed light envelope (`outline.light`) that folds refine without the confidence loop (clarified request, `pr_title`, minimal premise check over the bounded read set, no clarification iteration, no confidence scores), the Simple outline, and deliverable derivation. The envelope reads only the bounded read set the server computed: the declared affected files plus their one-hop neighbours (*Total Read Set Cap* `cap = 25`, *Declared-File Band* `band = 8`). No Q-Gate runs.

|`deep`
|Codebase-wide, multi-module, architectural, or uncertain changes
|Runs the full Phase 2 refine loop (`refine.analyze`, the confidence loop, lesson Q-Gate), then full domain discovery, ADR progressive-disclosure scan (`manage-adr scan`), consumer sweeps for symbol renames/deletions, and full Q-Gate verification (`outline.deep`).
|===

[#light-gate]
==== Light Gate: Deterministic Budget Trigger

The budget trigger is the primitive `lane.budget-check`, computed by the server before the light envelope is dispatched. Two `auto` states run it: `init.light-gate` (in `phase-1-init`, entered from `init.ready` for a `light` plan only) and `outline.light-regate` (in `phase-3-outline`, entered from `outline.review` on a change request for a `light` plan, before every re-dispatch of `outline.light`); a revision never re-enters a Phase 1 state (link:state-catalogue.adoc#state-outline.light-regate[State Catalogue]). It never reads a sub-agent file-read counter: the server cannot observe host reads, so the bound is decided over the declared and resolved file set before any model work.

1. *Declared Affected Files `A`*: On the first dispatch, the explicit repository-relative paths named in the request (the same path extraction the initial lane router uses; the gate never discovers files the request did not name). On a re-dispatch after revision, the `Affected files` of the current `outline.md`.
2. *One-Hop Neighbours*: For each file of `A`, the server reads the file-level neighbours resource `pm://architecture/files/{path}/neighbours` (link:domain-extensions.adoc#_architecture_query_resources_pmarchitecture[Domain Extensions Specification, Architecture Query Resources]: the file's own resolved imports, its paired test or production file, and its owning module), and adds the owning module's descriptor; exactly one hop, never transitive, never a content search. `neighbours` is the resolved set minus `A`.
3. *Budget*: The plan escalates to `deep` when `|A| + |neighbours| > 25` (cap) or `|A| > 8` (band); `escalation_trigger` records `budget_cap` or `budget_band` with both counts.
4. *Fail Toward the Safe Lane*: When the neighbours of any file of `A` cannot be resolved (architecture inventory absent, file not attributed to a module, or a resource answering `indeterminate` or an error), the plan goes `deep` with `escalation_trigger: neighbours_indeterminate` and `facts` naming the unresolved files and the reason. An unresolved neighbour set is never counted as empty, and an empty `A` is unresolved, not bounded.
5. *Baseline Probe*: Because a light plan never enters `refine.baseline-reconcile`, the gate runs the same non-mutating probe (<<_phase_entry_baseline_reconciliation>>, parsing and overlap population unchanged). `overlap_with_content_conflict` sends the plan `deep` (`escalation_trigger: baseline_conflict`), since content conflicts are absorbed during refinement, which only the deep lane runs; the other outcomes are recorded as on the deep lane.
6. *Record*: The gate records `A`, `neighbours`, both counts, and its outcome in `audit.jsonl` (`lane_budget`). On pass, `A ∪ neighbours` is handed to the envelope in `facts.light_read_set` as its read bound.

[#light-envelope]
==== Collapsed Light Envelope (`outline.light`) & Artifact Gates

When the light gate passes, the plan moves to `phase-3-outline` with `phase-2-refine` recorded as collapsed (`status.metadata.phase_2_mode = collapsed_light`, not yet `done`), so the envelope's spend is attributed to `phase-3-outline`. `outline.detect-change-type` runs as on the deep lane (the heuristic scores `original_input`, since no clarified request exists yet), then the server dispatches `outline.light`. The phase artifact gates apply to light plans unchanged; the collapsed envelope satisfies them as follows:

* *Clarified Request and `pr_title` (Phase 2 exit gate)*: The envelope's `submit:outline` carries `clarified_request: text[1..32768]`, `pr_title` (conventional commit, `<= 72` characters), and `outline: text[1..65536]`. A light submission missing `clarified_request` or `pr_title` is refused with `invalid_link_args`. On acceptance the server writes `request.md` `## Clarified Request`, `status.metadata.pr_title`, and `outline.md` in one transaction and records `phase-2-refine` `done`. The light envelope is thereby the `pr_title` producer on its own path (link:workflow-dsl.adoc#static-verification-rules[Workflow DSL Specification, rule 8]); the Phase 3 arrival requirement for `pr_title` is evaluated on this submission.
* *Validated `outline.md` (Phase 3 exit gate)*: The submission passes `OutlineValidator` exactly as on the deep lane (<<_phase_3_outline_validation_rules_outline_review_gate>>), after the widen-only domain merge over the declared files and followed by the single narrowing pass.
* *Operator Outline Approval*: `outline.review` follows unchanged and remains an operator-authorizing decision; the light lane never approves its own outline. A revision requested there enters `outline.light-regate`, which re-runs the budget check over the outline's `Affected files` and re-dispatches `outline.light` on pass (a failing check ratchets the plan to `deep`).
* *Judgment Escalation*: Instead of an outline, the envelope may submit `outcome = escalate_to_deep` with `escalation_trigger` (`premise`, `cross_module_ripple`, or `public_symbol_deletion`) and a rationale; nothing of the envelope is persisted besides the escalation record.

==== Lane Ratchet Rules

1. *Unknown Scope Bias*: At initial routing, an unknown or unresolved `scope_estimate` biases fail-safe to `deep`. Conversely, an unset `change_type` does **not** force `deep` when `scope_estimate` and target files are bounded.
2. *One-Way Escalation (`light -> deep`)*: The engine ratchets a `light` plan to `deep` (locking `planning_lane = "deep"`, `track = "complex"`, `lane_escalated = true`, and `escalation_trigger` permanently for the plan) whenever either the *Deterministic Budget Trigger* fires in the light gate (<<light-gate>>, including `neighbours_indeterminate` and `baseline_conflict`) or the *Judgment Escalation Trigger* fires (the envelope submits `outcome = escalate_to_deep` because it found a false request premise, cross-module ripple effects, or public symbol deletions requiring a full consumer sweep). The escalation is a first-class engine transition into `refine.baseline-reconcile`: from `init.light-gate` the plan enters Phase 2 normally; from `outline.light` or `outline.light-regate` the collapsed Phase 2 record is superseded (`phase_2_mode = full`), the phase is set back to `phase-2-refine`, and the deep pipeline runs fresh.
3. *No Down-Ratchet*: No transition exists from `deep` to `light`. Even if Phase 3 discovery later narrows `scope_estimate` from `multi_module` to `surgical` (which may enable the Q-Gate surgical bypass), `planning_lane` remains `deep`.
4. *Minimum Lane (team configuration)*: The only lane setting is the team key `plan.phase-1-init.minimum_lane` in `.marshall/config/workflow.json` (`light` default: the initial router decides; `deep`: every plan runs the deep lane, `plan-marshall`'s `deep_lane: always`). *Deliberate change vs. `plan-marshall`*: a forced `light` lane (`deep_lane: never`) and switching off the escalation ratchet (`plan.phase-1-init.escalation`) do not exist, because they can only skip a check the router or the ratchet would run; the ratchet always applies. A `deep` minimum is recorded in `audit.jsonl` as the lane decision's reason. The recipe auto-route threshold `0.6` is a compiled constant.

[#land-lane]
=== Land Lane (`local_changes`)

A plan started with `local_changes` lands changes the user already made; it has no model implementation work. Its lane `land` stands next to `light` and `deep` but is not part of the planning lane ratchet: it is fixed by `pm_start` and never converts to `light` or `deep`, and no plan converts into it. Its states are catalogued in the link:state-catalogue.adoc#state-catalogue-land[State Catalogue, Land Lane: `land`].

1. *Init*: `init.classify` runs the sibling collision detector over the captured paths and resolves the workflow settings; the recipe scorer and the planning-lane router do not run. `status.metadata.pr_title` is set from `summary`; without a `summary` it is derived from the `plan_id` and marked `pr_title_stale`, so `create-pr` requires the retitle submission. The execution manifest is composed by the shared manifest resolver (<<_shared_execution_manifest_posture_preview_resolver>>) over the captured footprint, with no tasks.
2. *Skipped Work*: The plan skips `phase-2-refine`, `phase-3-outline`, `phase-4-plan`, and the task work of `phase-5-execute` (no deliverables, tasks, envelopes, or chain-tail commits).
3. *Verification*: `land.worktree-init` creates the plan's branch and worktree as `execute.worktree-init` does and carries the captured changes onto them (the open git mechanic of the `local_changes` source). `land.verify-sweep` then runs the verification of execute's exit over the captured footprint: the `manifest.phase_5.verification_steps` with the footprint-driven scope and relocation override (<<_whole_tree_verification_gates_triage_required_routing>>), baseline-red separation, and the footprint check that the realized footprint of the worktree equals the captured `declared_files`. The `land.*` states run in phase `phase-5-execute` (`mcp/status.json` `phase`). `land.exit-barrier` evaluates the Phase 5 exit barrier (<<_phase_5_exit_barrier_dual_freshness_pending_tasks_gates>>) with zero tasks; the clean-tree and freshness gates apply unchanged. The plan then enters `phase-6-finalize` with every guarantee: step verdicts and verdict currency, the pre-merge barrier, the merge record, and the landing.
4. *Failures Without Task Allocation*: A failed verification enters `land.verification-feedback`, which files the failures in `findings.jsonl` and offers only `escalate` (decision kind `land-verification-failed`: `recapture`, executed by the `auto` state `land.recapture`, or `abort-plan`, which enters `plan.aborted`) and `abort` (the request `abort-plan`), plus `recapture` once the user has fixed the changes. In `phase-6-finalize` a `land` plan is never offered `loop_back` and never settles a `FIX` in-branch: where another plan would loop back, it offers `escalate` and `abort` only, and the `recapture` link.
5. *Recapture*: `recapture` (rel `fix`, no free parameters, primitive `land.recapture-changes`, also run by `land.recapture` on the operator's approval) re-derives the footprint server-side from the main checkout (a new `captured_changes` with `recapture_count` incremented, the updated `declared_files` and `request.md` change set), carries the changes onto the plan's branch, and re-enters `land.verify-sweep`; finalize steps re-run as verdict currency decides (<<_re_entry_head_at_completion_verdict_currency_rules>>). A recapture that finds no change set is refused with `no_local_changes`.

=== Phase 3 (`outline`): Validation Rules & `outline.review` Gate
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-4[PM-WATCH-PHASE-4], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-5[PM-WATCH-PHASE-5]_

When the model submits the solution outline (`outline.md`) in `outline.light` or `outline.deep`, the submit primitive validates it before accepting the transition; validation is not a state of its own, and a rejected submission leaves the plan in the submitting state with `rejected.reason = "invalid_link_args"`. The server-side `OutlineValidator` enforces four structural invariants and validates each deliverable's optional `Added dependencies` section (§ 5):

==== 1. Per-File Intent Marker Validation
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-3[PM-WATCH-PHASE-3], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-65[PM-WATCH-PHASE-65]_

Every entry under a deliverable's `**Affected files:**` list must carry an explicit trailing parenthesized intent marker from a closed 5-value enum:

[cols="1,2,3"]
|===
|Intent Marker |Syntax Example |Pre-Execution `files_exist` Gate Semantics

|`read`
|``- `src/main/java/Foo.java` (read)``
|Consulted as read-only reference. The `files_exist` gate is satisfied when the path (after glob expansion) exists on disk, or when a deliverable in the transitive `depends:` closure declares it `write-new`; a glob is judged on its expansion, never on the literal. Recorded in `references.json` under read-only references, disjoint from expected modifications.

|`write-new`
|``- `src/main/java/Bar.java` (write-new)``
|Created fresh by the deliverable; file **must not exist** on disk prior to execution (flags a Q-Gate finding if already present).

|`write-replace`
|``- `src/main/java/Baz.java` (write-replace)``
|Modified in place; file exists on disk and is recorded in the declared modification footprint.

|`write-conditional`
|``- `src/test/resources/baseline.json` (write-conditional)``
|Modified only if a gate named in the deliverable fires (for example a snapshot baseline refreshed only when the snapshot test turns red). The file must exist on disk (same rule as `read`). Stored in `references.json -> derived_files.conditional_modifications`: excluded from the footprint coverage denominator and never reported as `modify_shortfall` when untouched, but inside the scope-creep allow set, so a touch is never a deviation.

|`delete`
|``- `src/main/java/Old.java` (delete)``
|Removed by the deliverable; file **must exist** on disk prior to execution (with the same glob-expansion and `depends:`-closure rule as `read`) and triggers the whole-tree verification gate in Phase 5.
|===

An `Affected files` entry is recognised only as a list bullet anchored at line start (after indentation) whose first token is a back-quoted path; a line that does not match is rejected as `unparsed` with its line number and is never re-scanned from an interior hyphen. The same rule applies to every other path-bearing list of the outline (for example survey lists). The validator publishes `bullets_seen` and `bullets_parsed` per list and fails the submission when they differ. Any `Affected files` line lacking a valid `(read|write-new|write-replace|write-conditional|delete)` suffix is rejected immediately with `rejected.reason = "invalid_link_args"`. Furthermore, if a deliverable changes a default value, constant, or enum member, the *value-change test-sweep rule* requires all existing test files asserting the old value (discovered identifier-first) to be listed in `Affected files` with `(write-replace)`.

==== 2. Six-Bucket File-Type Classifier & `module_testing` Profile Requirement

For each deliverable, the server classifies its write-intent `Affected files` via the domain build extensions into one of six closed file-type buckets and validates the deliverable's declared `profiles[]`:

[cols="1,2,3"]
|===
|File-Type Bucket |Path Composition |Mandatory `profiles[]` Assignment

|`production_only`
|Production source files only
|`[implementation, module_testing]` — `module_testing` is **mandatory**.

|`test_only`
|Test source files only
|`[module_testing]` only.

|`mixed_code`
|Production and test source files (no docs)
|`[implementation, module_testing]` — `module_testing` is **mandatory**.

|`mixed_with_docs`
|Production/test source files plus documentation files
|`[implementation, module_testing]`, with `module_testing` scoped strictly to the code/test paths.

|`documentation_only`
|Documentation or markdown files only
|`[implementation]` only — `module_testing` is **prohibited**.

|`unknown`
|Unclaimed file extension or path
|*Blocks Deliverable*: Emits a blocking finding requiring path correction or build-extension mapping; never silently falls back to `documentation_only`. A path the build map routes as build-neutral (for example `.github/**`) is not `unknown`: it is `no_module` (<<_whole_tree_verification_gates_triage_required_routing>>, Footprint-Driven Scope) and neither blocks the deliverable nor widens a gate.
|===

==== 3. Single Domain Narrowing Pass

Immediately after `outline.md` passes structural validation, the server re-derives the plan's active domain set from the union of all deliverables' declared footprints (`Affected files`) and narrows `references.domains` **exactly once**. This removes any temporary over-provisioned domains introduced during Phase 2's widen-only union before Phase 4 resolves task skills. A narrowing that removes a domain sets `status.metadata.pr_title_stale` (the title was authored for the wider scope).

==== 4. Persisted `outline.review` State (Surviving `/clear`)
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-58[PM-WATCH-PHASE-58]_

Once the outline and its Q-Gate pass complete, the engine transitions to `outline.review` *while remaining in `phase-3-outline`* (never marking Phase 3 `done` prior to approval). Because `outline.review` is persisted in `mcp/status.json`:

* A session compaction or `/clear` resumes directly at `outline.review` via `pm_state(plan_id)`.
* Advancing from `outline.review` to `phase-4-plan` is always an *operator-authorizing decision* requiring MCP elicitation or `pm-mcp operator approve-outline`; no configuration key and no continuation policy approves an outline (a compiled invariant of the `outline` unit, link:workflow-dsl.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]). *Deliberate change vs. `plan-marshall`*: its `plan_without_asking` flag, which advanced without approval, does not exist.
* *Dependency Approval*: `outline.review` renders the union of all deliverables' `Added dependencies` sections in `facts` as `added_dependencies[]` (each coordinate with its deliverable; an explicit empty list when the outline adds none). Approving the outline approves exactly these coordinates as the plan's approved dependency set (§ 5), which the pre-merge Dependency Delta Check (<<dependency-delta>>) verifies.
* If the operator requests changes during `outline.review`, the operator's feedback is persisted as pending Q-Gate findings (`phase = 3-outline`) and the state transitions back to `outline.deep` / `outline.light` to revise the outline (a light plan passes `outline.light-regate`, which re-runs the budget check over the outline's `Affected files` before the envelope is re-dispatched, <<light-gate>>).
* *No Silently Carried Q-Gate Findings*: `outline.review` renders every `phase-3-outline` Q-Gate finding still `pending` in `facts` and, while non-blocking ones remain, offers `accept_nonblocking` (rel `alt`, form `submit`, free `rationale:text[1..2000]`), which records `ACCEPT` with that rationale on every pending non-blocking `3-outline` finding in one transition (the server derives each `resolution`). Blocking findings still need their own triage or revision. The approved advance to `phase-4-plan` is taken only when no `3-outline` finding is pending (Blocking Findings Guard).

==== 5. `Added dependencies` Section
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-60[PM-WATCH-PHASE-60]_

A deliverable that introduces a new third-party dependency names it in an `**Added dependencies:**` list. Each entry is one ecosystem-qualified coordinate from a closed ecosystem set, without a version:

* `maven:<groupId>:<artifactId>` for Maven and Gradle build files (for example ``- `maven:org.jspecify:jspecify` ``);
* `npm:<name>` for `package.json`, including scoped names (``- `npm:@scope/name` ``);
* `pypi:<name>` for `pyproject.toml`, compared in its PEP 503 normalized form.

`OutlineValidator` parses the section with the same line-anchored bullet rule as `Affected files` (`bullets_seen` equals `bullets_parsed`, a non-matching line is `unparsed`). An entry with an unknown ecosystem prefix or a coordinate that does not match its ecosystem's grammar, and a coordinate named twice in the outline (within one deliverable or across deliverables), is rejected with `rejected.reason = "invalid_link_args"` naming the line. A deliverable without the section adds no third-party dependency; the section never lists the project's own modules. A version change of an existing dependency is not an addition and is not listed.

The union of the sections of the approved `outline.md` is the plan's *approved dependency set*. Like `declared_files` it is immutable after `outline.review` approval; adding a coordinate later requires an outline revision through the operator-authorizing `loop-back-outline`.

=== Phase 4 (`plan`): Task Derivation, DAG Validation & Manifest Resolver

Phase 4 transforms the approved structured deliverables in `outline.md` into executable `TASK-NNN.json` files, dispatch envelopes, and the per-plan execution manifest (`execution-manifest.json`).

==== Deterministic Task Derivation & DAG Cycle Detection
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-7[PM-WATCH-PHASE-7], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-8[PM-WATCH-PHASE-8], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-16[PM-WATCH-PHASE-16]_

1. *Profile-to-Task Mapping*: For each deliverable $D_i$ in `outline.md`, the engine generates one task per declared profile in fixed intra-deliverable order (`implementation` $\rightarrow$ `module_testing` $\rightarrow$ `verification`), copying the deliverable's `Intent gloss` verbatim into each derived task's description. A verification command the deliverable declares is copied verbatim into `verification.commands` of its tasks (placeholders are substituted at execute); a deliverable that declares a command whose tasks would receive none is a derivation failure, never a silent fallback to a module-level command.
2. *Dependency DAG Construction & Cycle Rejection*: Inter-deliverable `depends:` declarations map the head task of $D_i$ to the tail task of each prerequisite deliverable $D_j$, and each task of a deliverable depends on its predecessor in the fixed intra-deliverable order; the edges are persisted in each task's `depends_on` (link:store-schemas.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]). `TaskGraphValidator` runs Kahn's topological sort and depth-first cycle detection over the complete task graph; any self-dependency, unresolved task or deliverable reference, or cycle (`TASK-A -> ... -> TASK-A`) fails validation before any task file is written. The same check runs server-side on every later task creation or amendment and refuses the write (`invalid_link_args` with `task_dependency_unresolved` or `task_dependency_cycle`).
3. *Two-Tier Skill Resolution*: Each task is assigned `skills[]` (`skill://pm/...` URIs) by combining system persona skills (`skill://pm/core`, profile vocabulary skill) with domain-resolved skills for the deliverable's `(domain, module, profile)` tuple.
4. *Atomic Non-Idempotent Task Creation*: All derived tasks are persisted in a single atomic batch (`batch-add`). Task creation is strictly non-idempotent: once `tasks/TASK-*.json` files exist for the plan, the engine omits the task-creation link on any re-entry into Phase 4, preventing duplicate task generation. Q-Gate findings on the task bundle are remediated only through *Targeted Task Revision*: in `plan.qgate` the server offers `revise:TASK-NNN` for each task that carries a blocking finding, with the free parameters of `plan.describe-tasks` for that task (`description`, `steps`, `target_files`, `depends_on`) and the same validations (declared-path discipline, dependency graph check). A revision changes only the named task, never the task set: no task is added or deleted. A finding that needs a structural change (a different task split, a missing or superfluous deliverable) is resolved only by the operator-authorizing `loop-back-outline` to Phase 3. The next Q-Gate iteration hashes the revised bundle.
5. *Server-Side Cost Sizing, Envelope Bin-Packing & Manifest Composition*: Upon `plan.describe-tasks` submission, the server automatically executes three deterministic passes in-process (without exposing separate LLM-driven `pack-envelopes` or `compose-manifest` states):
** `TaskCostEstimator` computes `cost_size` (`XS | S | M | L | XL | XXL`) for each task from its step count, profile, skill count, and target file count, and stamps `predicted_cost_tokens`, the size-to-token table value of that size (link:dispatch-and-effort.adoc#cost-sizing[Dispatch & Effort Specification, Cost Sizing]).
** `EnvelopePacker` groups the tasks, topologically ordered over `depends_on` (ties broken by `task_id`), Next-Fit into dispatch envelopes (`envelope-1..M`) bounded by the configured per-envelope budget, merges an envelope below the minimum dispatch work of `10K` into an adjacent compatible one, and stamps `envelope_id` on each `TASK-NNN.json`. Tasks share an envelope when they have the same module and effort role, so a deliverable's `implementation` and `module_testing` pair shares one leaf sub-agent context window.
** `ExecutionManifestResolver` writes `execution-manifest.json` (including structured `phase_6.dropped_steps: [{step_id, gate, reason}]` for every pruned step).
6. *Declared-Path Discipline in Task Descriptions*: A task description or step submitted via `plan.describe-tasks` that names a path outside its deliverable's `Affected files` is rejected with `invalid_link_args` naming the path; the outline must be revised or the path declared, and the step is never silently dropped.
7. *Budget Projection & Advisory Split*: In the same pass the server sums `predicted_cost_tokens` over all tasks (`BudgetProjector`) and persists the projection in `mcp/status.json` (`metadata.budget_projection`: the sum, the deliverable count, the plan's `(scope_estimate, change_type)` pair, and the compared anchor column, link:dispatch-and-effort.adoc#spend-accounting-budget-anchors[Dispatch & Effort Specification, Spend Accounting & Budget Anchors]). When the deliverable count exceeds the guidance ceiling of 12 or the projection exceeds the warning column of the pair (for a fallback pair: its normalized ceilings), the plan representation carries the fact `split_advice` naming the figures and the exceeded bound. `split_advice` is advisory only: it never blocks, never enters a state of kind `awaiting_user`, and never changes the tasks. The projection carries the basis of the size-to-token table it summed (link:dispatch-and-effort.adoc#cost-sizing[Dispatch & Effort Specification, Cost Sizing]): `basis: uncalibrated` until the server has recalibrated the table from measured metrics.

==== Shared Execution Manifest & Posture Preview Resolver

Both the Phase 1/Phase 4 *posture preview* and the Phase 4 *execution manifest composition* (`execution-manifest.json`) invoke the same deterministic `ExecutionManifestResolver`:

* *Posture Lattice*: `minimal` $\sqsubset$ `standard` $\sqsubset$ `full`.
* *Floor Immunity*: Steps whose lane class is `core` or `derived-state` carry floor immunity (currently `sync-baseline`, `pre-push-quality-gate`, `push`, `create-pr`, `ci-verify`, `branch-cleanup`, `preference-emitter`, `record-metrics`, `print-phase-breakdown`, `emit-landing`, `archive-plan`, and `architecture-refresh`): these are the mandatory steps, whose presence in the project's `finalize.pmwf` unit is a compiled invariant (link:workflow-dsl.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]) and which `workflow.json` cannot configure (a `steps` entry for one is refused with `mandatory_step_not_configurable`). Steps without a `lane` block are not lane-participating and are always kept.
* *Local-Only Runs*: When the project has no push remote (derived fact `push_remote` empty, link:store-schemas.adoc#derived-facts[Store Schemas Specification, Derived Facts Store]), the resolver drops `push`, `pre-push-quality-gate`, and `pre-submission-self-review` from the Phase 6 manifest at composition time and records them in `dropped_steps` with `gate: local_only`; the plan completes with `merge_outcome: local_only`. *Deliberate change vs. `plan-marshall`*: the local-only outcome is derived from the repository, never chosen (`plan-marshall`'s `commit_and_push: false` does not exist), and with a push remote every plan pushes, opens a pull request, and passes CI and the merge barrier. A `stale` or `failed` `push_remote` fact makes the composition `indeterminate`, never local-only.
* *Prune Predicates & Structured `dropped_steps`*: Conditional steps (such as `sonar-roundtrip`, `automatic-review`, or `adr-propose`) evaluate their provider availability and footprint prune predicates; an unresolved `ask` seed is dropped only when its backing provider is unconfigured, and every pruned step is recorded in `execution-manifest.json -> phase_6.dropped_steps` with its `gate` (`posture`, `provider_unconfigured`, `footprint_disjoint`, `change_type_exempt`, or `recipe_override`) and human-readable `reason`. A `footprint_disjoint` prune evaluates the structured-derived footprint (`references.json -> derived_files.expected_modifications`); an absent, unreadable, or empty footprint is `indeterminate` and keeps the step (never pruned, never reported clean), mirroring `VerdictCurrencyEvaluator`: absence of a footprint never means "disjoint from everything".

|*Artifact Gate*

|`pm_start` and all planning transitions

A `local_changes` plan is exempt from `config_dirty`: a dirty file under `.marshall/config/` is part of its captured change set, shown in `request.md` and the pull request, and its verification runs with the changed configuration (which must still verify).

|Phase entries (Phases 2–6)
|Verifies `main_sha` baseline drift, the `config_hash` of the effective configuration (compiled defaults, derived facts, team files, operator file, and process DSL units, link:store-schemas.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]; `PM-EXT-7`), and worktree consistency keyed on the plan's worktree presence in `mcp/status.json`: a non-null `worktree_path` must resolve to a live git worktree of `branch_name`; `worktree_path` must be `null` in Phases 1–4 and in Phase 6 steps after `branch-cleanup` at order `> 70`, which therefore never refuse on the removed worktree (link:filesystem-layout.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). Baseline drift is never auto-rationalized; loop-back re-entry drift is auto-accepted exactly once, and worktree refusal errors are never bypassed.

|*Store Integrity & Digest Guard*
|Every `pm_state` / `pm_do` read
|Every server write to the plan's stores in the per-project machine store (`status.json`, `references.json`, `findings.jsonl`, `TASK-*.json`) records a SHA-256 content digest. If a host shell edits these files directly (host file tools are denied `<PM_MCP_BASE>/**`), the digest mismatch is detected on the next MCP call that takes the scope lock, which, after transaction-journal recovery, raises the `store_tampered` condition on the current state requiring operator resolution (link:store-schemas.adoc#store-digest-verification[Store Digest Verification]); it is a condition, not a state change and not a `rejected.reason`. A lock-free read (`pm_state`, `pm://` resources) never decides it and reports `digest_unverified` instead.

|*Blocking Findings Guard* (`pending_findings_blocking_count == 0`)
|Exits from Phases 2, 3, 4, 5
|Refuses phase exit while any Q-Gate or verification finding with `blocking == true` remains in `resolution == "pending"` (the server-written resolution, link:store-schemas.adoc[Store Schemas Specification], Findings Ledger Record). The exit from Phase 3 is stricter: it requires every Q-Gate finding of phase `phase-3-outline`, blocking or not, to carry a terminal disposition; the non-blocking ones may be accepted together in `outline.review` (Phase 3, § 4). A finding addressed to a phase the plan has already left is refused at the findings write seam with `phase_closed` (link:mcp-tools.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]); only Phase 6 findings filed after the merge are carried out instead (below). In Phase 6 the pre-merge review barrier (Predicate 1) is the last findings guard; after the merge no step refuses on findings, and a blocking finding filed later is carried out and recorded in the landing (catalogue rows `1000` and `1100`). A refusal lists each blocking finding (`finding_id`, `source`, `severity`, age since `created_at`, failing predicate) in `facts`, never only a count. == Q-Gate Validation, Change-Type & Scope-Deviation Contracts
_See Requirement link:../Requirements.adoc#PM-WF-11[PM-WF-11: Q-Gate Validation Loop, Change-Type & Scope-Deviation Contracts]_

=== Q-Gate Validation Loop
_Implementation watch: link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-52[PM-WATCH-GEN-52], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-6[PM-WATCH-PHASE-6], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-10[PM-WATCH-PHASE-10], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-12[PM-WATCH-PHASE-12]_

Quality Gate (`Q-Gate`) validation runs at the tail of Phase 3 (deep lane only; the light lane never runs it), at the tail of Phase 4, and in Phase 2 only for lesson-derived plans on the deep lane (narrative-vs-code validation; a light lesson-derived plan never enters Phase 2, and its premise contradictions surface through the light envelope's premise check as a judgment escalation to `deep`), mirroring `plan-marshall` (verified at commit `1d4a1da37`; re-verify before implementing). It catches structural defects (narrative-vs-code drift, missing consumer sweeps, invalid CLI flags, tier deltas, architecture mismatches, and unresolved lesson citations) before advancing to the next phase.

==== Modes, Iteration Ceiling & Content-Hash Rerun Gate
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-13[PM-WATCH-PHASE-13]_

[cols="1,3"]
|===
|Parameter / Rule |Normative Specification

|*Mode* (fixed `until_clean`)
|The Q-Gate mode is not configurable in any phase: validation and remediation iterate until `pending_findings_blocking_count == 0` or the iteration ceiling is reached, bounded by the ceiling and the surgical bypass. *Deliberate change vs. `plan-marshall`*: its `q_gate_validation` knob (`off` skips validation, `once` leaves known findings open) does not exist, because both only weaken the gate; the presence of the Q-Gate states in the deep-lane `outline` and in the `plan` unit is a compiled invariant (link:workflow-dsl.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]).

|*Iteration Ceiling* (`max_qgate_iterations = 3`)
|The Q-Gate auto-loop runs **at most 3 iterations** per phase (`qgate_iteration` persisted in `mcp/status.json`, range `0..3`).

|*Content-Hash Rerun Gate*
|Before running Q-Gate validators on iteration $k$, the engine computes `sha256(target_artifact)` (`request.md` in Phase 2, `outline.md` in Phase 3, `TASK-*.json` bundle in Phase 4) and compares it to `status.qgate_last_evaluated_hash`. If the hash is identical, the validators are not re-run: with `pending_findings_blocking_count == 0` the loop exits clean; with open blocking findings the plan transitions directly to `<phase>.qgate-exhausted` with `facts.reason: artifact_unchanged` (routine answers `edit` or the request `abort`, which raises `abort-plan`; closing the gate is only the operator-authorizing `force-gate`), since unchanged content cannot produce a different verdict.

|*Surgical Bypass Predicate*
|In Phase 3 (`outline`), Q-Gate validation is automatically bypassed (logging `(phase-3-outline:qgate-bypass)` to the audit log) if and only if all three conditions hold: `scope_estimate == "surgical"`, `change_type` $\in \{\text{"bug\_fix"}, \text{"tech\_debt"}, \text{"verification"}\}$, and `deliverable_count == 1`.

|*Exit & Exhaustion Semantics*
|The loop exits to the next state (`refine.ready`, `outline.review`, or `execute.worktree-init`) as soon as `pending_findings_blocking_count == 0`. (In Phase 2 lesson-derived plans, `stale` narrative-vs-code findings are non-blocking signals preserved for Phase 3 confirmation, whereas `invalid` findings are blocking.) If `pending_findings_blocking_count > 0` after iteration 3, the plan transitions to `<phase>.qgate-exhausted` (kind `awaiting_user`), where the routine answers are `edit` and the request `abort` (the operator decision `abort-plan`, never ended by the model); closing the gate over open blocking findings is only the operator-authorizing `force-gate` (elicitation or operator CLI, recorded with its `exemption_class`), never a model-relayed answer. A Q-Gate pass over zero recorded component assessments is `not_evaluated` and never exits the loop as clean.

|*Convergence Record*
|Each iteration records `findings_raised`, `findings_self_seeded` (findings located in lines changed by the previous iteration's fix) and, on exhaustion, `findings_at_ceiling` (raised in the last iteration, whose fixes no round reviews). The exit renders `converged` vs `oscillating` from these figures, never from the last count alone.

|*Deterministic Ordering Check*
|Ordering phrases (`before`, `after`, `gate`, `first`, `then`, `depends on`) in a deliverable's narrative that name another deliverable without a corresponding `depends:` edge are filed as non-blocking Q-Gate findings; `depends:` edges between deliverables that name each other symmetrically are audited for cycles and omissions.
|===

=== Single-Writer `change_type` Contract
_Implementation watch: link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-21[PM-WATCH-GEN-21]_

`change_type` classifies the intent of a plan and its deliverables using a closed 6-value enumeration orthogonal to `domain` and `profile`:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.classification;

public enum ChangeType {
    FEATURE("feature", 1),
    BUG_FIX("bug_fix", 2),
    TECH_DEBT("tech_debt", 3),
    ENHANCEMENT("enhancement", 4),
    VERIFICATION("verification", 5),
    ANALYSIS("analysis", 6);

    private final String wireName;
    private final int priorityOrder;

    ChangeType(String wireName, int priorityOrder) {
        this.wireName = wireName;
        this.priorityOrder = priorityOrder;
    }

    public String wireName() { return wireName; }
    public int priorityOrder() { return priorityOrder; }
}

==== Single-Writer Heuristic vs Judgment Fallback

To prevent conflicting writes between deterministic heuristics and model judgment, `status.metadata.change_type` enforces a strict *single-writer* protocol at the start of Phase 3 (`outline.detect-change-type`):

1. *Deterministic Heuristic First (`ChangeTypeHeuristic`)*: Scores `clarified_request` (falling back to `original_input`) against fixed keyword tables, applying compound-intent guards and `bug_fix`-vs-`tech_debt` object disambiguation. If a single `ChangeType` wins with $\text{confidence} \ge 0.70$ and no top-two score tie, `ChangeTypeHeuristic` persists `status.metadata.change_type` and advances directly to the plan's lane state, `outline.deep` or `outline.light` (`ambiguous = false`). If no keyword fires, the top two scores tie, or $\text{confidence} < 0.70$, `ChangeTypeHeuristic` returns `ambiguous = true` and **writes nothing** to `status.json`.
2. *Judgment Fallback (`submit`)*: Only when `ambiguous == true` does the engine enter `outline.classify-change-type`, offering a `submit` link (`change_type:enum[feature|bug_fix|tech_debt|enhancement|verification|analysis],rationale:text[1..500]`) guided by `skill://pm/outline/detect-change-type/SKILL.md`. The submitted value becomes the single authoritative write to `status.metadata.change_type`.

==== Plan-vs-Deliverable Scope Reconciliation & Classification Validation
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-9[PM-WATCH-PHASE-9]_

* *Scope Disagreement Refusal*: Every deliverable in `outline.md` declares its own deliverable-scoped `change_type`, while `status.metadata.change_type` holds the plan-scoped classification. `OutlineValidator` and `ExecutionManifestResolver` reconcile the two scopes and **refuse** incompatible combinations: a deliverable with `change_type: verification` or `analysis` is read-only by definition; if any of its `Affected files` carries a mutating intent (`write-new`, `write-replace`, `delete`), or if a plan classified as `verification`/`analysis` contains mutating deliverables, validation fails closed with `change_type_scope_disagreement`.
* *Flag-Not-Block Classification Validation*: When `scope_estimate` is updated in Phase 2 or Phase 3, `classification-validate` checks for narrow-over-large mismatches (for example, `change_type == bug_fix` paired with `scope_estimate == broad`). Mismatches emit an advisory warning fact in `facts.classification_warning` but never block a transition.

* *Loop-Back Footprint Review*: At every `loop_back`, before remediation tasks are allocated, the server re-captures `realized_files` and presents `realized − (declared ∪ approved_widening)` as one batched item of `execute.deviation-review` (link:workflow-dsl.adoc#loop-back-bounds[Workflow DSL Specification, Loop-Back Bounds]). `accept` absorbs the paths into `approved_widening[]` with provenance `observed`, never into `declared_files`; `hold` keeps them outside the declaration, so they stay reported as drift. Drift the operator already reviewed is not presented again in later rounds.
* *Task Blocking & Envelope Batching*: Submitting a deviation marks `TASK-NNN` as `blocked` before any out-of-scope file write or decision-log entry occurs. If an envelope encounters multiple deviations across independent tasks in its pass, all pending `ScopeDeviationRequest` records are batched into a single operator escalation state (`execute.deviation-review`).
* *Three Closed Operator Dispositions*: The operator resolves each deviation through MCP elicitation or `pm-mcp operator resolve-deviation` using one of three deterministic branches:

|===
|Disposition |Required Operator Input |Deterministic Server Side Effects

|`hold`
|Optional guidance note (`text[0..1000]`)

|`accept`
|**Mandatory** `rationale: text[1..2000]`

==== Task Envelope Execution & Independent Server Verification
_Implementation watch: link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-47[PM-WATCH-GEN-47], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-1[PM-WATCH-DISP-1], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-6[PM-WATCH-PHASE-6], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-11[PM-WATCH-STORE-11]_

1. *Envelope Dispatch*: `execute.dispatch-ready` offers `dispatch:envelope-M` (`form: dispatch`) paired with `returned:<dispatch_id>` (`form: submit`). The dispatched sub-agent calls `pm_state(plan_id, entity="envelope-M", dispatch_id)` and receives only the current active task (`TASK-NNN`) and its resolved `skill://pm/...` URIs.
2. *Independent Verification on `submit:TASK-NNN`*: The server never trusts a sub-agent's self-reported completion. When `submit:TASK-NNN` is invoked, the daemon independently verifies: (a) *Non-Empty Diff & Footprint Check* — for write-intent tasks, verifies that `git status --porcelain` in the worktree contains changes, that no files outside the worktree were touched, and that every modified path is a write-intent entry (`write-new`, `write-replace`, `write-conditional`, `delete`) of the deliverable's `Affected files` or of `approved_widening[]` (`verify_failure_scope` / scope-creep check) — a modified `(read)` entry is its own outcome `read_only_modified` (blocking finding), never absorbed as in scope — forbidding batched destructive `git checkout` commands; (b) *Obfuscation & Marker Check* — scans modified lines for prohibited suppression comments, `TODO`/`FIXME` markers, or rewrite markers; and (c) *Independent Command Re-Run* — executes the task's declared verification command via the daemon's build runner and verifies a passing verdict artifact. When the verification passes, the server appends (d) a *Task Diff Record* to `change-ledger.jsonl`: `kind: "task_diff"` with `task_id`, `deliverable_id`, the `worktree_sha` of the worktree at submit, `changed_paths` (the paths changed since the previous task's recorded snapshot, present and possibly empty), and `commit_sha: null`, because tasks never commit. This is the only producer of per-task change attribution.
3. *Context Budget Yield & Infeasibility*: If a sub-agent approaches its context window limit before finishing all tasks in `envelope-M`, it invokes `yield:envelope-M` (`budget_yield`, free parameter `yield_reason:enum[budget|blocked_dependency]`, persisted as data beside the dispatch classification in the metrics store) and the server splits the remaining unstarted tasks of `envelope-M` into a new envelope `envelope-(M+1)` with a fresh `dispatch_id`. If a task is genuinely impossible as specified, the sub-agent submits `infeasible:TASK-NNN` with evidence; the server sets the task to `infeasible` with the evidence as its disposition, `infeasible` is terminal for that task, and substituting a weaker deliverable under the same name is strictly prohibited. The server opens the operator decision for the affected deliverable at once (elicitation, or a pending decision record reachable through `wait:decision:<decision_id>`) without halting the plan: dispatch continues for every task that does not depend, transitively through `depends_on`, on the infeasible deliverable, and running tasks are never cancelled. The plan enters `execute.awaiting-infeasible-decision` only when no runnable task remains and the decision is still open (`PM-WATCH-GEN-47`); this is a real state entered by its own condition, not the `blocked` condition overlay.
4. *Dependency-Ordered Dispatch*: A task is yielded to its envelope's sub-agent only when every task in its `depends_on` is `completed` or `skipped`; an envelope is offered for dispatch only when its first task is yieldable. A task whose dependency is `infeasible` or `removed` is never yielded.
5. *Deciding an `infeasible` deliverable*: The decision may arrive while independent tasks still run or after the plan entered `execute.awaiting-infeasible-decision`. Neither the running plan nor `execute.awaiting-infeasible-decision` offers the model a link that changes a task or a deliverable; the deliverable is settled, and `execute.awaiting-infeasible-decision` left, only through one of two operator-authorizing decisions (<<_routine_user_interaction_vs_operator_authorizing_decisions>>), and the model never chooses removal:
** `remove-deliverable`: the `infeasible` task keeps its status and evidence, and every other task of the deliverable becomes `removed` (`disposition.by: operator`, with the decision id); the operator's decision also names every deliverable that depends on it, whose tasks are removed with it, since a removal that would leave a remaining task depending on a `removed` task is refused. The server sets `status.metadata.pr_title_stale` and records a scope amendment in `mcp/status.json -> amendments[]` (`source: operator`) naming the removed deliverables and the infeasibility evidence.
** `loop-back-outline`: the plan loops back to `phase-3-outline` with the evidence as an amendment; a deliverable the revised outline drops has its tasks set `removed` by the outline gate (`disposition.by: outline_gate`), and Phase 4 derives the tasks of the revised deliverables additively; `completed` tasks are never reopened (`PM-WF-7`).

=== Per-Deliverable Chain-Tail Commit & Module Build (`git.commit_and_push`)
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-17[PM-WATCH-PHASE-17]_

Individual tasks never run `git commit`. When the last task belonging to deliverable $D_i$ (the *chain tail*) passes independent verification:

1. *Chain-Tail Commit via `call git.commit_and_push`*: The server transitions to `execute.chain-tail-commit`, which invokes the reusable compound sub-workflow `call git.commit_and_push (message_mode=auto_deliverable, push_mode=never)` (`PM-WF-16`, see link:workflow-dsl.adoc[Workflow DSL Specification]). The sub-workflow cleans untracked build/temp artifacts against `artifact-patterns.json` (respecting `.gitignore` and excluding `.marshall/**`), formats the conventional commit message (`feat(<module>): complete deliverable <N> - <title>`) with the configured `Co-Authored-By` trailer, streams the message over `stdin` to `git -C <worktree> commit -F -`, and appends a `kind = "change"` entry to `change-ledger.jsonl` stamped with the new `commit_sha` and git-sourced `changed_paths`.
2. *Per-Deliverable Module Build*: Immediately after `git.commit_and_push` returns `committed_local` (or `clean` for read-only deliverables), the server spawns a module-scoped build job running the per-deliverable verification verbs of the effective configuration (`workflow.json` `plan.phase-5-execute.per_deliverable_verbs`, default `compile` and `module-tests`, as `plan-marshall`'s `per_deliverable_build`, operator decision D40(c); link:store-schemas.adoc#config-workflow-json[Store Schemas Specification, `workflow.json`]), scoped to $D_i$'s module, and records a `kind = "build"` entry in `change-ledger.jsonl`. If the module build passes, the envelope advances to the next deliverable's tasks (or completes the envelope); if the module build fails, the envelope transitions immediately to `execute.verification-feedback` (`triage_required`). A module build ending `timed_out`, `killed`, `indeterminate`, `refused`, or `failed_unparsed` never advances the envelope either: it transitions to `execute.verification-feedback` with a no-verdict reason and offers `retry`, because an absent verdict is never admitted as a pass.

=== Whole-Tree Verification Gates & `triage_required` Routing
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-15[PM-WATCH-PHASE-15], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-66[PM-WATCH-PHASE-66]_

Once all task envelopes reach completion, `execute.verify-sweep` runs the end-of-phase verification pipeline declared in `manifest.phase_5.verification_steps` (ordered by the `ext-point-build-verify-step` descriptors: `module-tests`, `quality-gate`, `coverage`, and domain `arch-gate`):

* *Footprint-Driven Scope & Relocation Override*: The server compares the realized git footprint (`references.json:realized_footprint`) against project modules to scope build executions. However, if any deliverable in the plan performed a **file relocation or deletion** (any `Affected files` entry with `delete` intent or a git rename `R`), the server unconditionally forces a **whole-tree build and verification sweep** across all modules to catch broken cross-module imports or references. A realized path claimed by no module but routed by the build map as build-neutral (for example `.github/**`) is classified `no_module`: it neither blocks nor widens a module-scoped gate to whole-tree, and the scope decision lists it.
* *`triage_required` -> Verification-Feedback Transition*: Whenever any per-deliverable module build or end-of-phase verification step fails, the engine ingests the parsed build/test/arch-gate failures into `findings.jsonl`, sets the phase sub-state to `execute.verification-feedback` (`triage_required`), and offers a `dispatch:verify-feedback` link (or inline `fix` links) that diagnoses the root cause against `verify_failure_scope`, applies the fix, commits via `call git.commit_and_push (message_mode=interactive, push_mode=never)`, and re-enters `execute.verify-sweep`.
* *Baseline-Red Gates*: Before a failing whole-tree gate routes to `triage_required`, the server re-runs it on the plan's merge base (link:job-runtime.adoc#_gate_honesty_verification[Job Runtime Specification, Gate Honesty Verification], Baseline Separation). Diagnostics present on the base are never plan findings (coverage debt in untouched modules is a non-blocking `baseline_debt` finding); a gate red only through baseline diagnostics enters `execute.baseline-red` (in Phase 6 `finalize.baseline-red`), which offers only `escalate`: the operator may accept the known-red base for the current `HEAD` and merge base, which the step records as `done` with `assurance_verdict: degraded` and the baseline diagnostics named, or stop the plan. The plan is never looped back to remediate a baseline failure.

=== Phase 5 Exit Barrier: Dual Freshness & Pending-Tasks Gates
_Implementation watch: link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-25[PM-WATCH-GEN-25], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-17[PM-WATCH-PHASE-17]_

Transitioning from `phase-5-execute` to `phase-6-finalize` is governed by an atomic dual-gate barrier in `execute.exit-barrier`. **Both gates are always evaluated together before acting on either** so a single diagnostics payload surfaces all reasons if both fail:

1. *Pending-Tasks & Clean-Tree Gate*: Every `tasks/TASK-*.json` record in the plan must be in a terminal status (`completed`, `skipped`, `infeasible`, or `removed`), every `skipped`, `infeasible`, or `removed` task must carry its recorded `disposition` (link:store-schemas.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]), and no task may be open (`pending_count == 0`, `in_progress_count == 0`, `blocked_count == 0`); the gate reports the counts of every status and lists each non-`completed` task with its disposition. The worktree must have zero uncommitted modifications (`git status --porcelain` is empty). A barrier failing on open tasks routes to `execute.dispatch-ready` while runnable tasks remain, and otherwise to `execute.awaiting-infeasible-decision` (link:state-catalogue.adoc#state-execute.exit-barrier[State Catalogue]).
2. *Worktree Freshness Gate (`worktree_sha`)*: Freshness is keyed strictly on `worktree_sha` — the composite SHA-256 digest of `HEAD` commit SHA plus staged index, unstaged working-tree diff, and untracked file paths/contents — never on `HEAD` commit SHA alone (which would misclassify an unbuilt dirty tree as fresh). The gate queries the change ledger (`change-ledger.jsonl`) and reads the explicit closed-enum `status` member (`fresh`, `exempt`, `stale`, `undecidable`), never inferring freshness from a process exit code or from `"not stale"`: `fresh` requires that every required build notation for the realized footprint has a passing `kind = "build"` ledger entry whose recorded `worktree_sha` equals the current live `worktree_sha` and every ledger row matches a registered build notation of the project; `exempt` applies when the `build-decision` verdict over the build map and the realized footprint is `not_necessary` (every realized path is build-neutral); the `documentation_only` file-type bucket is a file role for `profiles[]` assignment and is never read as a build verdict (as in `plan-marshall` ADR-004); `stale` / `undecidable` fails the barrier with an explicit `stale_reason` (`tree_modified_since_build`, `last_build_failed`, `no_successful_build`, `missing_module_build`, `unrecognized_build_notation`, `reconciliation_record_absent`, `ledger_unreadable`, or `worktree_sha_unavailable`), routing back to `execute.verify-sweep`. A live or recorded `worktree_sha` that is `unavailable` (a failed git invocation) makes the gate `undecidable` with `worktree_sha_unavailable`, never `fresh`, and ledger rows of another `worktree_sha_version` never match the live digest (link:job-runtime.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash], rules 4 and 5).
+
`last_build_failed` (the latest build row for a required notation is not `succeeded`) is a different operator action than `tree_modified_since_build` (source edited after a passing build) and is never reported as it; when no successful build exists at all the reason is `no_successful_build` and no `freshness_reconcile` is recorded (it requires a `prior_build_worktree_sha`). `reconciliation_record_absent` lists in `facts.admitted_causes` the causes that absence admits (`source_drift_unbuilt`, `no_successful_build`, `record_owed_not_emitted`, `commit_outside_reconcile_membership`), so the refusal reports what it observed rather than guessing one cause. Where the step records show that `HEAD` is a finalize-internal commit, the refusal names the committing step.

The catalogue mirrors the finalize step roster of `plan-marshall` (step identifiers, `order`, descriptor facts, `lane` data, and defaults), verified against `plan-marshall` commit `1d4a1da37` (`extension-api/standards/ext-point-finalize-step.md` and each step's frontmatter). Differences are marked as *deliberate changes*. Before implementing the finalize pipeline, re-verify the roster against the latest `plan-marshall` version. Rows marked "project" are project-local steps of `plan-marshall`'s own repository, listed only to show how project steps occupy the bands; they are not shipped.

The catalogue is the roster of the binary's *default* `finalize.pmwf` unit. A project runs its own copy (`.marshall/config/finalize.pmwf`, link:workflow-dsl.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]): it may omit an optional step (lane class `prunable` or `adversarial`, or a step whose default is off) and add project steps (descriptor in `workflow.json` `plan.phase-6-finalize.project_steps`, script bound in the enrolment), but every step of lane class `core` or `derived-state` (the mandatory steps, <<_shared_execution_manifest_posture_preview_resolver>>) must be present at its catalogue `order`, and the verified unit decides the roster; `workflow.json` only sets the lane and parameters of an optional step.

Every `head_dependent` step declares its `input_scope` (<<verdict-input-scope,Verdict Input Scope>>): `remote_state` for `ci-verify`, `automatic-review`, and `sonar-roundtrip`; `open_ended` for `pre-push-quality-gate`; `plan_footprint` for `simplify`, `security-audit`, and `pre-submission-self-review`. Project-local steps declare their own (`plan-marshall`'s `plugin-doctor` has no sound subset, `open_ended`; its `era-stamp-fill` names its files, `declared`). *Deliberate change vs. `plan-marshall`*: `plan-marshall` has no `input_scope` field; its steps either declare `verdict_inputs` or leave it absent.

Problems are filed as findings and handled by loop-back; the step itself never commits. Records `acceptance`, `may_close`, `work_performed`.

A delta round never closes the step: a clean delta round is followed by exactly one full-surface round over the whole plan diff, and only a full-surface clean round records `may_close = true`; a delta round that surfaces findings loops back without a confirmation round. *Review chain terminus*: after the last remediation commit that follows the final review-bot round, the engine runs exactly one self-review pass over the residual delta since the last bot-reviewed head; its findings are filed and shown to the operator at the pre-merge gate, never auto-fixed, and no further chaining occurs.

|Triggered whenever `ci-verify`, `automatic-review`, or `sonar-roundtrip` files open findings. For producers declaring a `verification_profile`, runs an adversarial refutation sub-state (`ext-point-verify`) first. Model submits `triage:F-n` (`disposition: enum[FIX\|SUPPRESS\|ACCEPT]`, `reply_text: text[1..4000]`, optional `requirement_refs: list<text[1..120]>`). The `finalize.triage` representation carries every open finding's essentials in `facts.findings` (`finding_id`, `source`, `bot_kind`, `severity`, `blocking`, `summary`, `file_path`, `line`, and the `provider_ref.comment_kind`), so triaging N findings costs exactly N `pm_do` calls and no reads; the untrusted `body` stays behind the `pm://plan/{plan_id}/findings` resource, and a table beyond the render bound names the omitted count and that resource. `requirement_refs` names the requirement ids (`PM-<AREA>-<N>`) or specification anchors the finding bears on; the server validates each against the requirement and specification registry of the binary and refuses an unknown reference with `invalid_link_args`. `FIX` transitions via `loop_back` to Phase 5 (if cross-task) or settles in-branch via `finalize.settle-commit` and re-runs from the Settle band; server transmits replies/dismissals via `stdin` or REST to GitHub/GitLab/Sonar. `finalize.triage` exits automatically once the last open finding is triaged: with at least one `FIX` to the in-branch fix path (`finalize.settle-commit`), otherwise to `finalize.next-step`, completing the wait-region steps as `done` (link:state-catalogue.adoc#state-finalize.triage[State Catalogue]).

The triage `submit` is refused when the chosen disposition contradicts the finding's own detail classification (checked at the write seam, never coerced from prose). `FIX` carries `population: text[1..2000]` naming the sites the fix covers (the whole co-reference population of the defect, never only the named site), recorded on the finding. A disposition that lowers a finding's severity must cite an executed check (build or test job id); raising it needs only a rationale. A disposition whose remedy is documentary (`reply_text` promising a change) is recorded as a commitment `{finding_id, promised_change, anchor_paths}` and re-checked against the merge-candidate diff before the barrier; an unmet commitment fails Predicate 1, and reconciliation over zero commitments records `not_reached` with `population: 0`. When the `ext-point-verify` refutation sub-state is unavailable, the triage records the substitute evidence the resolution rested on (`evidence.class: substitute`). The disposition grammar stays `FIX\|SUPPRESS\|ACCEPT`; the server derives the finding's `resolution` (`fixed`, `rejected`, `suppressed`, `accepted`, `taken_into_account`) from the recorded evidence, the refutation verdict, and the finding's `scope_class` against the plan footprint (link:store-schemas.adoc[Store Schemas Specification], Server-Written Resolution). A re-disposition of a finding whose reply was already transmitted requires a new `reply_text`; a bare re-disposition is refused. The triage facts carry round-scoped counters (replies sent, threads resolved) and the explicit `unanswered[]` list (`finding_id`, `transmit_outcome`, `transmit_reason`; link:store-schemas.adoc[Store Schemas Specification], Transmit Reasons), empty when every finding was answered.

Otherwise the step never refuses on its inputs: a blocking finding still `pending` at this point is carried out like in `emit-landing` and listed in `facts.late_findings`, and an undelivered landing envelope (`landing_delivery: pending`) moves with the plan directory, never discarded. *Deliberate change vs. `plan-marshall`*: `plan-marshall` records `done` and archives with the pull request still open on non-merging branches.

[[automatic-review]]
=== Automatic Review: Registry, Participation, Refusals & Ingestion
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-24[PM-WATCH-PHASE-24], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-25[PM-WATCH-PHASE-25], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-26[PM-WATCH-PHASE-26], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-27[PM-WATCH-PHASE-27], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-28[PM-WATCH-PHASE-28], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-29[PM-WATCH-PHASE-29], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-30[PM-WATCH-PHASE-30]_

`plan-marshall:automatic-review` (order `30`) and the composite wait `finalize.concurrent-wait` work from one server-owned review-bot registry and write one participation record per `(pr_number, round, bot_kind)` into the plan's `review-participation.jsonl` at review time, each stamped with the `HEAD` it observed (link:store-schemas.adoc#review-participation[Store Schemas Specification, Review Participation Record]). The rules mirror `plan-marshall` `automatic-review` (`SKILL.md`, `standards/*.md`), verified at `plan-marshall` commit `f3de0e14f`; re-verify against the latest `plan-marshall` version before implementing.

==== Review-Bot Registry

The registry holds one compiled-in record per `bot_kind`; a project may add records.

[cols="1,4"]
|===
|Field group |Content

|Identity & trigger
|`bot_kind` and `author_login` (the identity used for author binding). One `trigger_token`: the server posts only this token, never one chosen per call; `trigger_verbs{incremental, full}` (CodeRabbit `@coderabbitai review` / `@coderabbitai full review`). `trigger_events`: the PR events the bot subscribes to (pr-agent does not subscribe to `synchronize`).

|Publish shapes
|`publish_shapes` ⊆ `{conversation, inline_thread, pr_review}` and `participation_evidence` (which shapes prove a review). Participation markers are anchored patterns (start of block or structural element, never a bare substring), and each marker records the sample (PR count) it was validated on. Observed shapes the registry does not declare raise a `registry_drift` finding; a missing optional shape is not non-participation.

|Currency
|`participation_requires_update` (mirrored from `plan-marshall`, where it opts a bot into the currency test; `sourcery` declares `false`, `coderabbit` and `cuioss-review-bot` declare `true`). In `PM-MCP` it exempts no bot: the currency test is unconditional (<<_two_fail_closed_barrier_predicates>>). `reviewed_sha_carrier` (`structured`, `body_pattern`, or `none`) with `reviewed_sha_pattern` (cuioss-review-bot: body "Review updated until commit `<sha>`"); `completion_check_name` (nullable).

|Refusal recognition
|`refusal_patterns`, `refusal_size_patterns`, `refusal_wrapper_markers` (CodeRabbit `<details><summary>⚠️ Action not completed</summary>`), and `rate_limit_eta_patterns` (including "reset in 57 minutes"; the CodeRabbit reset notice may omit its trailing phrases). `no_new_commits_patterns` (CodeRabbit "Review skipped" / "No new commits to review") and, for a bot without `trigger_verbs.full`, `no_new_commits_class` (`refused` or `declined`). Sourcery phrasings: "your pull request is larger than the review limit of", "reached your weekly rate limit of", "you've used your own review budget of N diff characters".

|Rate class & caps
|`rate_limit_class` (`awaitable_window`, `hard_quota`, or `unknown`), `rate_interval_seconds`, `attempt_ceiling` (default `10`), and `structural_caps{max_files, max_diff_chars}`.

|Content classification
|`actionable_content_markers`, `contentless_review_markers`, `ignore_patterns`, `severity_map`, and dated per-bot `config_verdicts[]` (for example CodeRabbit `enable_prompt_for_ai_agents`).
|===

Compiled-in data (re-verify before implementing): `coderabbit` (one review per hour, `awaitable_window`, `max_files: 100`); `sourcery` (`hard_quota`, 250,000 diff characters per 7 days, per PR 150,000 characters or 300 files); `cuioss-review-bot` (`unknown`, reviewed SHA in the body only). The provider cap for a GitHub comment body is 65,536 characters.

* *One Shared Reader*: Required, optional, and enabled populations are resolved only from `required_bots` / `optional_bots` against the registry through one shared reader. An unregistered token fails loud (`unregistered_kind`) with the same disposition everywhere and is never counted in a ratio denominator.
* *Review Bots Are Not CI*: `ci_status` evaluation excludes check-runs owned by registered review bots. On a bot timeout the engine first checks that the bot's trigger workflow or app is installed for the repository (`not_wired`) before reporting `unproven`.
* *Size Cap at Fetch Time*: A bot whose structural cap is below the PR's measured diff is classified `refusal_candidate` when comments are fetched; an unmatched comment from it is checked against its refusal phrasings before any participation verdict.

==== Per-Bot Participation States

Per round, every bot of the roster resolves to exactly one per-bot `state` of the closed enumeration defined in link:hypermedia-format.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations] (with a `refusal_mode` for `refused`); the composite `bot_status` of `finalize.concurrent-wait` is the aggregate of these states over the required bots, and its outcomes route the finalize excerpt (link:workflow-dsl.adoc[Workflow DSL Specification]). The rules below decide which state applies.

* *Review Evidence*: Completion requires a review verdict object (a review, an inline comment of that review, or a completed check-run) authored by the bot's registered `author_login`; per-bot completion waits match `author_login`, because a SHA match proves which commit was reviewed, not who reviewed it. Rate-limit meta-comments, re-served prior-round comments, "Review completed" placeholders without a review, inline comment or check-run, and thread acknowledgements never count. A declared clean verdict ("No major issues detected", "No code suggestions found") counts as `participated_but_empty`.
* *Refusal Precedence*: A refusal outranks a later edit timestamp, and a refusal observed in the same pass as a clean review of the same bot resolves `refused`. A refusal never sets the covered commit and never advances the `head_at_completion` of `automatic-review`.
* *Declined vs Unproven*: `declined` requires a named commit that is not the merge candidate; evidence that names no commit resolves `unproven` for a bot with `reviewed_sha_carrier: none`.
* *Nobody-Reviewed Shapes*: `not_triggered`, `rereview_silent_failure`, and `run_stuck` stay distinct; workflow runs are queried unfiltered by branch. An exhausted poll yields `unproven`, never `absent`.
* *Opposite Claims*: `unreadable` (the read failed) and `silent` (the read succeeded and nothing was published) are opposite claims; a prediction is recorded as `unrecorded`, never as an observation. A fetch returning zero comments resolves to exactly one of: no review covering `HEAD` (`absent` or `unproven`), reviewed clean (`participated_but_empty`), or fetch unreachable (`unreadable`).
* *Per-State Remedies*: Each non-participating state carries its own remedy link, never a shared generic `retry`, and a `reopens` axis (`awaitable` or `hard`) derived from the refusal mode. A roster question that was never put renders "question never put"; an awaitable refusal's representation names the governing config key and value.
* *Partitioned Reporting*: Unproven and blocking sets are reported partitioned by `roster_class` (`required`, `optional`, `unclassified`); only the required partition gates. The roster aggregate is `reviewed`, `incomplete`, `vacuous` (empty required set, answered: `review.required_bots` present in `project.json` as `[]`), or `unestablished` (never answered: the key is absent; there is no separate provenance bookkeeping, the presence of the key is the answer); an empty roster never renders `reviewed` or `clean`.
* *Per-Bot Facts*: `facts.bots` renders per bot `state`, `completion_check`, and `at_head` as separate columns (hypermedia-format.adoc), because "participated", "completion check finished", and "CI check green" prove different things. The participation summary renders per class `required k/|required|`, `optional j/|optional|` (with each silence's state), and `roster r/|roster|`; a bare N-of-M is never emitted.

==== Refusals & Rate Windows

1. *Derived Recognition*: Refusals are recognised by a derived rule (wrapper marker plus registry patterns), tested with controls in both directions. An unrecognised refusal-shaped notice resolves `refused` with mode `unknown`; an unmatched bot comment is never counted as participation.
2. *Capture on Sight*: The body and `observed_at` of a refusal are captured when first seen; a later absence of the notice is not a refutation, and a body divergence on re-read is reported. Every refusing bot is reported, never only the first.
3. *Wake on Edits*: Waiters order comments by `max(created_at, updated_at)`.
4. *Currency of a Notice*: A notice is current only if it answers a trigger this run posted (by trigger id) or its stated window is still open; otherwise it is `stale`. A rate-limit refusal is bound to the request it answered and to its reset time; a window already waited out is never restarted by re-reading the same refusal.
5. *Window Derivation*: The window is `rate_interval_seconds × attempt_ceiling`. The window's `reset_at` is taken from the bot-stated reset ETA, which is a floor to re-check and beats the compiled rate-window floor (`5400 s`, applied only when no ETA is published; not configurable, link:timeouts.adoc#review-bot-windows[Timeouts & Budgets Specification]); `3600 s` applies only when no ETA is parseable. Waiting past the ETA records a reason. A detected but unparsed ETA records `eta_unparsed` (a drift signal), never "no ETA". Wait budgets derive from the registered interval, never from a flat timeout, and the waits per plan are bounded (`plan-marshall` policy: at most 10 waits of 90 minutes; re-verify).
6. *Closed Windows*: A trigger is never posted inside a closed window (a trigger extends the window, close and reopen do not reset it, and windows are organisation-scoped); `retry` is offered only while the window is open.
7. *Mode Routing*: `size` routes to `finalize.review-structural` (triage of the structural finding: split, accept, or disable the bot for this PR), never to a wait; `weekly_quota` and `hard_quota` route to `escalate`, never to a wait; `rate` waits for the window and then triggers; `no_unreviewed_commit` routes to `finalize.review-full-trigger`, which posts the registry's `full` trigger verb once for the current `HEAD` (a repeated notice after that trigger escalates). A stale bot with a declared comment trigger gets the trigger posted once and a bounded wait, then escalation (never for a quota refusal).
8. *Satisfying Event*: Every wait names its satisfying event and its producer; if the bot's `trigger_events` cannot fire on this retry path, the wait fails fast with `no_satisfying_event`.
9. *Re-Trigger Target*: The re-trigger target is the unproven set (including bots that never published), selected after the round's own fetch, never by comment recency. The wait and trigger target set is the unproven part of `required ∪ optional`; the gating set is the required bots only.
10. *Per-PR Counters*: Rate-window claims (the cross-plan leases in `review-bot-windows.json`) and attempt counters are kept per PR and per bot.
11. *No-New-Commits Notice*: A bot notice matching the registry's `no_new_commits_patterns` ("Review skipped: No new commits") is never participation and never a neutral acknowledgement. For a bot whose registry declares a `full` trigger verb it resolves `refused` with mode `no_unreviewed_commit`, whose remedy is that verb (observed to succeed within seconds on the same `HEAD`). For a bot without a `full` verb the registry's `no_new_commits_class` decides: `refused` (mode `no_unreviewed_commit`, escalated because no remedy verb exists) or `declined` (the `plan-marshall` classification). *Deliberate change vs. `plan-marshall`*: `plan-marshall` classifies the notice as `declined`, accepts the decline, and never re-triggers; `PM-MCP` re-triggers with the `full` verb wherever one exists, so no stale credit stands for an unreviewed `HEAD`.
12. *Pre-Wait Cap Gate*: Before entering `finalize.concurrent-wait`, the engine measures the diff (files and diff characters) against each required bot's `structural_caps`. An exceeded cap records `refused` with mode `size` pre-emptively, names the cap and the measurement, and routes to `finalize.review-structural` instead of waiting, which shows each structural refusal as a finding and offers `triage:<finding_id>` per finding (`FIX` splits, `ACCEPT` accepts, `SUPPRESS` disables the bot for this PR); when a path partition (for example test sources vs the rest) brings each part under the cap, the finding proposes that concrete split. Under every cap the flow is unchanged.

==== Comment Ingestion

1. *Every Firing*: Comments are re-ingested on every firing of `automatic-review` and on every re-entry of `finalize.concurrent-wait`. All three surfaces (conversation, inline threads, PR review bodies) are fetched and classified.
2. *Own Comments by Provenance*: Own comments are recognised by provenance (server-recorded posted comment ids and trigger ids); headings are secondary. Repository-owner comments are genuine reviews unless provenance matches. Posted triggers are excluded and counted with a reason; a bot comment quoting a trigger is still ingested.
3. *Noise Filter*: Fenced code, blockquotes, and `<details>` blocks are stripped first; a comment is noise only if an acknowledgement pattern covers the whole remainder; length is an outer bound only. Drops are recorded distinguishably from genuine acknowledgements.
4. *Actionable Content*: A bot comment becomes a finding only if it matches the registry's `actionable_content_markers` (when declared) after noise stripping; enumerated refusal patterns are the secondary guard.
5. *Status Line then Remainder*: A `review_body` yields finding candidates only from the text after the bot's status line ("Actionable comments posted: N"). A body consisting only of a status line, an approval notice, or a "Review finished" header is a status record, never a finding, and never enters Predicate 1.
6. *Complete Fetches*: Every connection is paginated (`pageInfo`) or reports `observed` vs `cap`; a clipped fetch is never success.
7. *Comment Identity*: A comment's identity is `(bot_kind, comment_id)` plus its edit marker (`updated_at != created_at`); an edited comment is new information.
8. *Fetch Freshness*: The merge barrier re-fetches immediately before merge; a review newer than the last fetch blocks.
9. *Summary-Card Overflow*: Overflow folded into a summary card ("Outside diff range comments (N)") is ingested as findings.
10. *Participation-Only Artifacts*: A persistent summary card or a trigger acknowledgement is participation-only: no finding, no reply. Refusals, rate-limit notices, own comments, and other participation-only artifacts are never filed as findings; they update the participation record only.
11. *Agent Prompt Blocks*: The bot's "Prompt for AI Agents" block is stripped once, at the triage-representation boundary, and never by length clamping; the stored body keeps it, quarantined as untrusted content.

[[post-run-metrics-and-landing]]
=== Post-Run Metrics & Landing Envelope
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-19[PM-WATCH-DISP-19], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-14[PM-WATCH-GEN-14], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-55[PM-WATCH-GEN-55], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-35[PM-WATCH-PHASE-35], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-36[PM-WATCH-PHASE-36], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-37[PM-WATCH-PHASE-37], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-38[PM-WATCH-PHASE-38], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-41[PM-WATCH-PHASE-41], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-56[PM-WATCH-PHASE-56], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-35[PM-WATCH-STORE-35]_

`record-metrics` (`998`) composes the plan's figures once. `print-phase-breakdown` (`999`), the landing envelope of `emit-landing` (`1000`), and the terminal `completed` representation render that composition and never re-derive a figure. The per-dispatch and per-phase rows are persisted in the plan's metrics store (link:store-schemas.adoc[Store Schemas Specification]).

==== Metric Aggregates (`record-metrics`)

* *Population-Stamped Aggregates*: Every published sum is `{value?, rows, rows_unmeasured, population_count}`. A total over an empty population omits `value`, and a structurally unmeasured plan is excluded from composition roll-ups. When `rows_unmeasured > 0` the total is labelled a floor (`total_is_floor: true`, listing the channels lacking evidence) and never wins a max-reconciliation against another source; a channel with no records renders `no_evidence`. This applies to `total_tokens` and `total_wall_seconds` alike.
* *Priced Units*: A cost figure, where one is shown, is exactly one derived figure, `priced_units = input + 5 × output + 0.1 × cache_read + 1.25 × cache_creation`, computed in views from the persisted raw token components (link:store-schemas.adoc#metrics-store[Store Schemas Specification, Metrics Store]) with the weights taken from one named constant table (`PricingWeights`; output at 5× input follows list prices). `priced_units` is never persisted per dispatch or per phase; a row lacking a component contributes to `rows_unmeasured` of the priced figure, which is then a floor, and a row that reports only a total makes the priced figure `not_derivable` for that row. Every percentage names its unit (`priced_units` or `tokens`), and the unweighted `total_tokens` is never labelled cost. *Deliberate change vs. `plan-marshall`*: `plan-marshall` computes `billing_weighted_total` with output at 1×, which understates generation (about 1.1% of the column against about 5.3% of spend); legacy baselines are re-derived from their raw components under `PricingWeights` before any comparison.
* *One Population per Figure*: Every token figure carries its population stamp (`dispatched` or `main_context`); totals are formed only within one population, and figures of different populations are never summed or compared in reports.
* *Dispatch Accounting*: Per phase, `dispatches_rendered`, `dispatches_returned`, and `dispatches_unreturned` are recorded; a non-zero difference is a recorded gate signal in `facts`.
* *Phase Time Monotonicity*: Every phase block with both timestamps is validated (`end >= start`; start, end, and duration agree when all three exist), and `phase_blocks_checked` and `phase_time_violations[]` are recorded beside `any_phase_missing_end_time`.
* *Stall Rate & Ledger Divergence*: A dispatch that terminates with `tasks_remaining > 0` and no blocked cause counts as `stall`; the stall rate and the `yield_reason` counts are published per plan. When two ledgers can diverge (dispatch rows vs audit rows), `record-metrics` publishes `union_rows` and a non-blocking `reconciliation{findings_count}` warning instead of picking one ledger.
* *Spend Classes*: Token spend is published per spend class (`submitted`, `findings_only`, `no_product`, `unmeasured`) cross-tabulated with the termination `status`, with the residual asserted `0` (link:dispatch-and-effort.adoc#spend-accounting-budget-anchors[Dispatch & Effort Specification, Spend Classes]); spend is never classified by `status`.
* *Caller-Drift Rate*: Per plan, the count of link calls rejected per `rejected.reason` and the count of repeated identical rejected calls (same link and same argument digest), with the failure classes `caller_drift` and `server_fault` kept apart (link:mcp-tools.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]). `PM-MIG-5` compares this rate with the legacy baseline of argument-shape failures per plan.
* *Per-Document Consumption*: From the served-content ledger (link:store-schemas.adoc#metrics-store[Store Schemas Specification, Metrics Store]), per served URI and section the read count, the bytes served, and the repeat reads within one dispatch, together with the per-phase document residency. Host `Read`/`Grep` bytes are outside the server and are never estimated into these figures.
* *Terminal Phase Boundary*: Phase 6 is recorded with `boundary: provisional`, `measured_until`, and `excluded_steps` (catalogue row `998`); every consumer (the landing, `print-phase-breakdown`, the quality report) renders the label with the figure, never a provisional total as a final one. Every earlier phase carries `boundary: closed` once its close row exists (labelled `re_entered` when rows follow its close).
* *Build Figures*: `build_count` and build time come from the plan's change ledger (`kind = "build"` rows). An unreadable ledger renders `unavailable`; when the runtime job journal shows build jobs for the plan while the ledger is unavailable or empty, a finding is filed.
* *No-Verdict Jobs*: A `timed_out` job counts as `no_verdict` in every roll-up (link:timeouts.adoc#no-verdict-rule[Timeouts & Budgets Specification, Timed-Out Outcomes Are No-Verdict]).
* *Wait Lapses*: `wait_lapses` are recorded per lapsed bot wait, keyed by the `finalize.concurrent-wait` outcome that ended it (`bot_unproven`, `bot_refused_awaitable`, `bot_refused_hard`; link:hypermedia-format.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations]), together with whether the awaited operation later settled green. CI waits never lapse (they are re-polled), so they have no lapse kind. The counts enter the landing envelope as policy evidence.
* *Rendering*: `print-phase-breakdown` renders absent or unmeasured figures as `unmeasured`, never `0`, and renders the coverage verdict whenever coverage is decidable (rows and total persisted together), including when rows exist but the sum is zero.

==== Landing Envelope (`emit-landing`)

The landing envelope carries:

* *Identity & Merge Facts*: `plan_id`, `plan_source` (the plan's `pm_start` source, `origin.source`: `request`, `issue`, `lesson`, `recipe`, or `local_changes`), `prs[]` (all PRs of the plan, re-recorded when a PR is replaced or split), `merged_pr_numbers`, `merge_commit_sha` (required when merged), `merge_state` (`landed`, `open`, `closed`, `enqueued_not_landed`, `unknown`, or `not_applicable_after_merge`, with fallback `unclassified`, which asserts no landing), and `owed[]`, the plan's owed items (link:store-schemas.adoc#owed-item-record[Store Schemas Specification, Owed Item Record]), as an explicit empty list when nothing is owed.
* *Figures*: `total_tokens` with its population count (omitted when that count is `0`), `total_wall_seconds`, the `wait_lapses`, the realized footprint, and `finalize_spend_ratio`; the Phase 6 figures carry their `boundary: provisional` label, `measured_until`, and `excluded_steps`.
* *Step Record*: `steps[]` with, per finalize step, `step_id`, its firings, the final outcome, `head_at_completion`, `work_performed`, and the dropping or pruning gate, taken from the step records.
* *Review Facts*: `review_state` of the merge (`reviewed`, `vacuous`, or `unreviewed_by_grant` with the grant's `kind` and gap class), `self_review` (`reviewed`, `not_covered`, or `not_run`, never collapsed into a clean result), and `review_yield` per review bot and for self-review (`findings` and the count per `resolution`, every member stated, zeros included).
* *Late Findings & Quality Report*: `late_findings[]` (`finding_id`, `source`, `severity`, `carried_to`) for every blocking finding carried out after the merge, as an explicit empty list when there is none; and `quality_report`, the persisted `quality-report.json` when `plan-retrospective` ran, else `not_run`.
* *Findings*: `findings[]`, every `FindingRecord` of the plan (all statuses and dispositions), not a curated subset, so the epic never depends on the archived plan directory to read them.
* *Narrative & Amendments*: `narrative`, a Markdown string field written in the same atomic record as the server-derived facts (`PM-IMPL-2`), with its producer named (the PR body submitted in `create-pr` plus the rendering of `accepted_deviations[]`; without a PR it is `n/a` with a reason) and the plan's `amendments[]`.
* *Completeness*: `complete` and `missing_facts[]`, computed at emission. Each fact is a typed value, `"n/a"`, or `"unknown"`; `complete: false` is emitted only with a non-empty `missing_facts` (the facts that are `unknown`) and is surfaced as a fact on the epic representation; `unknown` and `n/a` are counted separately. Every fact carries `provenance` (`derived`, or `recovered_by_hand` with a required `verified_by`); a correction is appended as an `annotation` event referencing the original record (link:store-schemas.adoc#epic-inbox-record[Store Schemas Specification, Epic Inbox & Plan Mailbox Records]), never a rewrite. The epic representation reports `facts_outstanding` (landings with `unknown` facts) separately from `messages_outstanding` (inbox messages not yet processed).

Rules:

* *One Landing per Plan*: Every landing is plan-typed, and exactly one landing exists per `plan_id`; `n/a` is never legal at the pull-request and merge keys, and at the deliverable and task keys only for `local_changes` landings, whose land lane has no deliverables or tasks (fact states: link:dispatch-and-effort.adoc#_server_derived_landing_facts_spec_re_grounding_cross_plan_locks[Dispatch & Effort Specification, Fact States]). When nothing merged, the step emits a non-landing record naming the outcome (`enqueued_not_landed`, `declined`, `no_pr`, `dequeued`, or `local_only`), never a landing with `n/a` values.
* *Delivery Verification*: After appending, `emit-landing` reads the record back from the epic inbox, validates it against the landing schema (the closed JSON Schema of the fields above, `$id` `https://cuioss.de/plan-marshall-mcp/schemas/landing-envelope.json`, referenced by the `landings.jsonl` record of link:store-schemas.adoc#landing-record[Store Schemas Specification, Landing Record]), and records `landing_delivery` (`verified`, `incomplete`, or `failed`) in its step record and in `facts`.

[[post-run-quality-report]]
=== Post-Run Quality Report (`plan-retrospective`)
_Implementation watch: link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-1[PM-WATCH-GEN-1], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-38[PM-WATCH-PHASE-38], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-47[PM-WATCH-PHASE-47], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-48[PM-WATCH-PHASE-48], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-49[PM-WATCH-PHASE-49], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-50[PM-WATCH-PHASE-50], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-51[PM-WATCH-PHASE-51], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-52[PM-WATCH-PHASE-52], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-53[PM-WATCH-PHASE-53]_

`plan-marshall:plan-retrospective` (`995`) runs the server's report engine over the plan's persisted stores (findings, review participation, step records, execution manifest, assessments, references, change ledger) and the metrics snapshot labelled `measured_until` (<<_spend_measurement_window>>), and writes `quality-report.json` (link:store-schemas.adoc#quality-report[Store Schemas Specification, Quality Report Record]). The engine is deterministic and in-process: it dispatches no sub-agent, reads no model-authored text as evidence, and every figure it publishes is derived from records. It is observability only: every instrument declares `gates_merge: false`, the step never refuses, and no step reads the report as a precondition. The report is computed before the landing, and `emit-landing` carries it (<<post-run-metrics-and-landing>>).

==== Instrument Contract

* *Populations*: Every published count is `{value, population}`; a rate is published with its numerator and denominator populations, so `2/2` and `40/40` stay distinguishable. A population of `0` renders `unmeasurable`, never a rate; `withheld` (with `withheld_reason`), `unmeasured`, and `0` are distinct values. Populations are rendered as explicit lists, empty lists included.
* *Declared Preconditions*: Every instrument declares what it proves (`proves`), whether any precondition it evaluates can be falsified by the condition it audits (`falsifiable_preconditions`), and whether its own output is inside the population it measures (`self_included`). `self_included: false` requires a reason. The instrument census iterates over all instruments and the report's own meta blocks, so it counts itself.
* *Why Zero*: Every zero carries `zero_reason` (`structural`, `starved`, `gated`, `no_count`, `disciplinary`, `no_block`, or `fired`). A plan or store the engine cannot read contributes `floor` (a lower bound, never healthy). A figure scanned across several stores (for example contradiction incidence across the findings stores of a corpus) carries `records_scanned` and `stores_reached` of `stores_expected`; a zero over fewer stores than expected renders `none reachable`, never `0`, so an honest zero exists only when every expected store was reached.
* *Clean Is Rendered*: A section with zero findings renders its populations and its zeros; no section is dropped because it is empty. An instrument whose status is `unmeasured` still renders every finding it holds.
* *Domain Aspects*: Domain bundles extend the report with retrospective aspects (link:domain-extensions.adoc#retrospective-aspects[Domain Extensions Specification § Retrospective Aspect Extension Point]); each is an instrument under this contract with `gates_merge: false`, run only for plans of its domain.

==== Quality Chain

* *Derived Step Set*: The finding-filing steps are derived from the registered `FinalizeStepDescriptor` roster (`filesFindings`, validator rule 8), never from a list. Per step the report records `presence`: `not_admitted`, `admitted_not_fired`, `fired`, or `fired_but_refused`, with admission taken from `execution-manifest.json` (`phase_6.steps` and `dropped_steps`). A firing is counted per step from its step record, never per audit line. Steps ordered after `plan-retrospective` are `after_window`, never `not_admitted`. A plan whose records lack an execution manifest is `indeterminate` on presence and forms its own, separately sized population.
* *Examination*: A fired step reports its `assurance_verdict` (`checked`, `degraded`, `not_reached`, `never_performed`, `attempted_over_empty_scope`); `degraded` (curable by a re-run) and the step's declared `cannotReach` class (a structural limit) are reported separately.
* *Coverage and Yield*: `coverage` is fired over admitted steps, with every not-admitted step named. `yield` is computed over the fired set only and split by `resolution`, `source`, and `severity` with every enum member tallied. Yield scores `fixed` and `rejected`; `accepted`, `taken_into_account`, and `suppressed` count as recorded decisions, never as points; `pending` never scores. Committed findings are `{fixed, accepted, taken_into_account}`, released findings `{rejected, suppressed}`. Coverage and yield are rendered side by side, never as one product.
* *Escape Distance*: The stage that caught each finding is a separate figure, ordered by cost: build < self-review < automatic review < human. It is never folded into yield.

==== Review Retrospective

The checks of `plan-marshall`'s project step `finalize-step-review-retrospective` are one section of the report, read from `review-participation.jsonl` and the findings store. All its verdicts are observability only (`gates_merge: false`, `proves: reviewer_quality_only`) and are recorded as INFO decisions; none enters the pre-merge barrier.

* *Rows*: The rows are the enabled roster (`required_bots ∪ optional_bots`); the required set is a column, never a filter, and a silent reviewer still gets a row. Metrics and participation follow every PR of the plan in `prs[]`, including superseded and split PRs.
* *Review Deficit*: `review_deficit` is one of `clean`, `required_absent`, `unassessable`, `vacuous`, or `unestablished`, with precedence `unassessable` > `vacuous`/`unestablished` > `required_absent` > `clean`. No roster baseline yields `unassessable`; a configured empty roster yields `vacuous` and an omitted roster `unestablished`; `required_absent` needs a non-empty baseline, a non-empty roster, and no required reviewer that reviewed. `clean` requires at least one required reviewer that reviewed and is graded on the actionable count. Participation per reviewer is `measured`, `reviewed_silent`, or `unmeasurable`, persisted with its populations.
* *Coverage Denominator*: Reviewer coverage is anchored to the configured roster baseline. An omitted, empty, or non-superset baseline withholds the figure with its cause; a roster that is a proper subset of the baseline is reported as `roster_narrowed`.
* *Gate Escapes*: A gate escape is a finding raised by a later stage for a defect an earlier gate could see. `rejected` and `suppressed` findings are not escapes (their count is published), and the escape numerator counts only roster reviewers. When the gates ran on different commits the verdict is `gate_tree_unsubstantiated`; when every gate commit precedes the last loop-back it is `gates_did_not_cover_reviewed_tree`.
* *False Positives per Reviewer*: The per-reviewer false-positive figure is the reviewer's `rejected` count over its findings; contradicting records are disclosed, never resolved into a confident zero.
* *Reviewed Tree*: The report asserts that the newest `reviewed_commit_sha` equals the merged head; otherwise it records `reviewed_tree_stale` with both commits.
* *Bypass Audit*: For a merged PR, every required bot must have a participation record covering the merge candidate; otherwise the merge is classified `bypass` as `barrier_skipped`, `refusal_misread`, or `merged_outside_finalize`.

==== Footprint & Assessments

The report publishes the three-way footprint reconciliation of the persisted capture (link:store-schemas.adoc#three-way-footprint[Store Schemas Specification, Three-Way File Footprint Reconciliation]) and compares it with the component assessments. The comparison is `measured` only with a resolved footprint and more than zero assessments read, `no_assessments` when the assessment store is empty, and `inconclusive` otherwise; include and exclude verdicts are withheld unless it is `measured`, and `touched_but_unassessed` paths are always reported.

==== Spend & Measurement Window

The report reads spend only from the metrics snapshot the metrics reader composes at the report's own call (validator rule 5). The snapshot is the composition of `record-metrics` (<<post-run-metrics-and-landing>>) over the records present at that instant, labelled `measured_until` with that instant; the report never reads `metrics.json`, which `record-metrics` (`998`) writes later.

* *Window Named*: The spend section renders `measured_until` and names the steps outside the window (the report's own step and every manifest step ordered after it), so the report's own spend and the terminal steps are visibly absent, never silently zero. Phase 6 figures carry `boundary: provisional`.
* *Figures*: Priced units and tokens per phase with their population stamps and floor labels, spend per spend class cross-tabulated with the termination `status`, spend per finding-filing step and per firing cause (from the step records' `firings[]`), and the finalize spend ratio against the plan's budget anchor (link:dispatch-and-effort.adoc#spend-accounting-budget-anchors[Dispatch & Effort Specification, Spend Accounting & Budget Anchors]). Every figure is a `count` with its population; an unmeasured channel renders `unmeasured`, and a derived ratio over an empty population renders `not_derivable`.
* *Yield per Spend*: Where the quality chain and the spend share a step, the report places the step's yield beside its spend; it never divides yield by spend into one score.

==== Corpus Mode

`pm-mcp operator quality-report --corpus` computes the report over the archived and active plans of the project. It returns `quality-report.json` of the same schema (`mode: corpus`), folded from the per-plan results of the same engine; a corpus of one plan equals that plan's report. Plans are grouped into populations (with and without an execution manifest), and every population is sized. *Deliberate change vs. `plan-marshall`*: the archived-plan auditor (`audit-archived-plan-retrospectives`) is a second implementation; `PM-MCP` has one engine for both modes.

=== Finalize Commit Instrumentation, Freshness Reconcile & Post-PR Re-Push (`PM-WF-16`)

Whenever any Phase 6 step declaring `mutatesSource == true` (`order < 70`) completes, the finalize engine routes through `finalize.settle-commit`, which invokes `call git.commit_and_push (message_mode=step_or_fallback, push_mode=post_pr_conditional)` (see link:workflow-dsl.adoc[Workflow DSL Specification]):

1. *Conditional Auto-Commit & Ledger Recording*: If `git status --porcelain` in the worktree is clean, `git.commit_and_push` returns `clean` immediately and the finalize pipeline advances to the next step. If uncommitted modifications exist, `git.commit_and_push` runs `.gitignore`-aware artifact cleanup, resolves the step's commit message (or deterministic fallback `chore(finalize): apply <step_id> changes`) with the `Co-Authored-By` trailer, pipes the message via `stdin` to `git -C <worktree> commit -F -`, and appends a `kind = "change"` entry (`commit_sha`, `changed_paths`, `worktree_sha`) to `change-ledger.jsonl`.
2. *`head_at_completion` Re-Stamping*: If the completed `mutatesSource == true` step also declares `headDependent == true` (such as `simplify`, `security-audit`, `pre-push-quality-gate`, `automatic-review`, `sonar-roundtrip`), `git.commit_and_push` atomically updates that step's persisted `head_at_completion` in `mcp/status.json` to the newly created `commit_sha` without emitting a duplicate step completion event. This prevents the step's own commit from self-invalidating its verdict on a subsequent re-entry check.
3. *`freshness_reconcile` for Commits after the Latest Successful Build*: If any `mutatesSource == true` step produces a commit after the latest successful build (not only steps at `order >= 10`, `PRE_PUSH_QUALITY_GATE_ORDER`; for example `architecture-refresh` at `9` committing on re-entry), `git.commit_and_push` records a `freshness_reconcile` entry in `mcp/status.json` containing `(commit_sha, step_id, prior_build_worktree_sha)` where `prior_build_worktree_sha` is read from the latest `status == "succeeded"` build entry in `change-ledger.jsonl`. When the `git.pre-commit-verify-freshness` gate runs before pushing, it consults `freshness_reconcile` so a known non-build-affecting finalize commit (such as an ADR addition in `adr-propose`) is recognized as reconciled, whereas any modification to buildable source paths invalidates `pre-push-quality-gate` and re-runs the Settle quality gate first. A commit whose changed paths are all build-neutral per the build map (for example generated architecture metadata) is reconciled without a rebuild.
4. *Post-PR Conditional Re-Push (`order > 20`)*: When `finalize.settle-commit` is triggered by a step with `order > 20` (after `default:create-pr`, such as `default:adr-propose` at `62` or an in-branch `finalize.triage` fix) and the project has a push remote (derived fact `push_remote`), `push_mode=post_pr_conditional` evaluates `push_required`, verifies freshness and `branch-sync-state` parity, pushes the new commit to `origin/<branch>`, and returns `committed_and_pushed -> finalize.review-cap-check`, whose `within_caps` outcome enters `finalize.concurrent-wait` so CI and review bots re-evaluate the updated PR `HEAD` (link:workflow-dsl.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Workflow DSL Specification, `finalize.pmwf` Excerpt]).

[[realized-footprint-capture]]
=== Realized Footprint Capture & Footprint-Scoped Steps
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-64[PM-WATCH-PHASE-64], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-36[PM-WATCH-STORE-36]_

Finalize steps obtain the realized footprint (link:store-schemas.adoc[Store Schemas Specification], Three-Way File Footprint Reconciliation) through one resolver:

* *Reconcile Before Footprint-Scoped Steps*: At Phase 6 entry and after every `finalize.settle-commit`, the engine re-captures `realized_files` and runs the three-way reconciliation before any step whose scope is the footprint (`simplify`, `security-audit`, `pre-submission-self-review`, `pre-push-quality-gate`) runs.
* *One Resolver for Diff-Fed Steps*: Every diff-fed step reads the footprint through this resolver, which resolves only from the plan's own worktree. Without a resolvable footprint the step records `indeterminate` with the cause named (`pending` when the worktree is not yet materialised, `disabled` when the plan runs without a worktree), never a clean `done` and never another tree's footprint.
* *Capture Before Destruction*: `branch-cleanup` persists the realized footprint in `references.json` before it removes the worktree; every post-merge consumer reads the persisted capture.
* *Only `measured` Is Evidence*: The three-way reconciliation, the scope-creep and coverage checks, the pre-merge footprint checks inside `branch-cleanup`, and every post-merge footprint consumer compare against `realized_files` only when `realized_state.state == measured`. `unresolved` and `not_captured` (link:store-schemas.adoc#three-way-footprint[Store Schemas Specification]) make each of them record `indeterminate` with the state and cause named, never a clean or empty result.

=== Dependency Delta Check (Pre-Merge)
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-60[PM-WATCH-PHASE-60]_

The server verifies that every third-party dependency the plan adds was approved in `outline.review` (Phase 3, § 5). The check is part of the footprint reconciliation: it runs with the three-way reconciliation at Phase 6 entry and after every `finalize.settle-commit` (<<realized-footprint-capture>>), and again inside `default:branch-cleanup` after its rebase, against the re-derived `base_ref`, immediately before the Pre-Merge Review Barrier is evaluated.

1. *Changed Build Files*: From the realized footprint (only when `realized_state.state == measured`), the server selects every path claimed as a build file by the build-file dependency parser of a build domain (link:domain-extensions.adoc#_server_owned_module_discovery_enrolled_discovery_jobs[Domain Extensions Specification, Build-File Dependency Parser]): Maven `pom.xml`, Gradle build files, `package.json`, `pyproject.toml`.
2. *Added Coordinates*: Each changed build file is parsed at `base_ref` and at `HEAD` (a file absent at `base_ref` contributes an empty base set). The added coordinates are the ecosystem-qualified coordinates declared at `HEAD` and not at `base_ref`, over every dependency scope the parser reports (including test, development, and optional dependencies). Coordinates of the project's own modules (module discovery snapshot) are not third-party and are excluded; a version change is not an addition.
3. *Blocking Finding per Undeclared Coordinate*: For every added coordinate the approved dependency set does not name, the server files one blocking finding (`source: dependency_delta`, finding type `undeclared_dependency`, `severity: major`, `file_path` the build file, `summary` naming the coordinate and the build file; link:store-schemas.adoc[Store Schemas Specification], Findings Ledger Record). A coordinate the approved outline names is not reported (matched negative control). A repeated run files no duplicate for a coordinate that already has a finding. The model may triage the finding only with `FIX` (remove the dependency); accepting or suppressing it is an operator decision, because it would approve a dependency outside `outline.review`.
4. *Never Clean without Evidence*: The check records `indeterminate`, never clean, when the realized footprint is not `measured`, when a changed build file has no build-file dependency parser, or when a parser fails on either side (the parse diagnostic and file are named). An `indeterminate` check blocks like a finding: the server files one blocking finding (`source: dependency_delta`, finding type `dependency_delta_indeterminate`, `file_path` the unparsed build file or null, `summary` naming the cause), so the Pre-Merge Review Barrier (Predicate 1) refuses the merge; the same triage restriction as for `undeclared_dependency` applies.
5. *Result*: The check publishes `dependency_delta: {state: clean | findings | indeterminate, build_files_checked, added[], undeclared[], cause}` in the finalize facts and in the merge record; `clean` requires at least one parsed changed build file or an empty set of changed build files, stated as `build_files_checked: 0`.

=== Java `FinalizeStepDescriptor` Record Schema & Static Checks

Every built-in, bundle, or project-local finalize step is represented in `pm-mcp-core` by an immutable `FinalizeStepDescriptor` record capturing all step descriptor facts:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.finalize;

import java.util.List;
import java.util.Optional;
import java.util.Set;

public record FinalizeStepDescriptor(
    String name,
    int order,
    boolean defaultOn,
    Set<String> presets,
    String description,
    boolean mutatesSource,
    boolean headDependent,
    Optional<InputScope> inputScope,   // required iff headDependent; never defaulted (validator rule 6)
    List<String> verdictInputs,        // non-empty iff inputScope == DECLARED
    boolean advancesMainViaRebase,
    boolean postRunReview,
    List<String> reads,
    List<String> destroys,
    List<String> recordsFacts,
    Optional<Lane> lane,
    List<String> requires,
    List<ConfigurableKey> configurable,
    Optional<String> persona,
    List<String> requiresPromptFields,
    Optional<String> cannotReach,
    List<String> filesFindings  // finding sources the step may file; empty = files none
) {
    /** Lane data as declared by plan-marshall ({@code lane:} frontmatter block). Absent lane = not lane-participating, always kept. */
    public record Lane(LaneClass laneClass, Optional<String> tier, Optional<String> prunableWhen, String costSize) {}
    public enum LaneClass { CORE, DERIVED_STATE, PRUNABLE, ADVERSARIAL }
    /** Closed verdict input scope ({@code input_scope:} frontmatter), see Verdict Input Scope. */
    public enum InputScope { REMOTE_STATE, OPEN_ENDED, PLAN_FOOTPRINT, DECLARED }
    /** Operator-configurable step setting ({@code configurable:} frontmatter). */
    public record ConfigurableKey(String key, String defaultValue, String description) {}

    public static final int PUSH_ORDER = 11;
    public static final int PRE_PUSH_QUALITY_GATE_ORDER = 10;
    public static final int MERGE_GATE_ORDER = 70;
    public static final int POST_RUN_MIN_ORDER = 900;
    public static final int TERMINUS_ARCHIVE_ORDER = 1100;
}
----

*Assurance Verdict*: Every finalize step record carries `assurance_verdict` (`checked`, `degraded`, `not_reached`, `never_performed`, or `attempted_over_empty_scope`); a record without it reads `unadjudicated`, never a pass. A gate step declares in `cannotReach` the defect class it cannot detect (for example `ci-verify`: unreviewed semantics and untested paths), which is rendered with its verdict. An empty examined scope renders "NONE — this pass analysed no dimension; it certifies nothing".

==== Build-Time & Startup Static Invariant Verification (`FinalizePipelineValidator`)
_Implementation watch: link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-3[PM-WATCH-DSL-3], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-20[PM-WATCH-GEN-20], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-39[PM-WATCH-PHASE-39], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-55[PM-WATCH-PHASE-55]_

`FinalizePipelineValidator` validates the complete registered `List<FinalizeStepDescriptor>` at build time (via JUnit tests, over the default roster) and on every load of a project's finalize unit (over the project's roster: the default descriptors of the steps its `finalize.pmwf` contains plus its project step descriptors), failing closed on any violation; a violation in a project roster refuses the project's plan lifecycle with the file and line (link:workflow-dsl.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]):

1. *Order Uniqueness (No Collisions)*: For all distinct descriptors $A \neq B$, $A.\text{order}() \neq B.\text{order}()$. Tie-breaking by list insertion order is strictly forbidden.
2. *Pre-Push Quality Gate Placement*: `default:pre-push-quality-gate` must have $\text{order} == 10$, `default:push` must have $\text{order} == 11$, and no step may occupy an order between them.
3. *Source-Mutation Before Merge Gate (`mutatesSource`)*: Every descriptor with `mutatesSource == true` must satisfy $\text{order} < \text{branchCleanup.order}()$ (`70`). Every step with $\text{order} \ge 70$ must have `mutatesSource == false` (supported at runtime by the post-run source guard, which checks `git status --porcelain` after every post-merge step to detect stray tracked writes).
4. *Post-Run Review & Source-Mutation Mutual Exclusion (`P1 \land P2`)*: No descriptor may declare both `postRunReview == true` and `mutatesSource == true`. Every descriptor with `postRunReview == true` must satisfy $900 \le \text{order} \le 1000$ (`emit-landing` at `1000` is a post-run review step).
5. *`reads` / `destroys` Data-Dependency Ordering*: For every artifact token $X \in A.\text{reads}()$ and any step $D$ with $X \in D.\text{destroys}()$, $A.\text{order}() < D.\text{order}()$ (no read-after-destroy: e.g., all `reads: [worktree]` steps precede `branch-cleanup` at `70`; all steps precede `archive-plan` at `1100` which `destroys: [plan-directory]`). For `X == "metrics"`, every consumer declaring `reads: [metrics]` either orders after the producer ($\text{order} > \text{recordMetrics.order}()$, `998`: `print-phase-breakdown` at `999`, `emit-landing` at `1000`) or reads a labelled snapshot (`plan-retrospective` at `995`). The engine has one metrics reader, the composition function of `record-metrics`: for a consumer ordered after `998` it returns the recorded `metrics.json`, and for a consumer ordered before it a snapshot composed at the consumer's call and labelled `measured_until`, never the unwritten store. A consumer before `998` that renders a snapshot figure without its `measured_until` label violates the rule at runtime.
6. *Anchor & Fact Contract Completeness*: Every descriptor with `headDependent == true` declares `inputScope` from the closed set `remote_state`, `open_ended`, `plan_footprint`, `declared` (<<verdict-input-scope,Verdict Input Scope>>); a missing `inputScope` on a `headDependent` step is a validation error and is never defaulted, and a descriptor with `headDependent == false` declares neither `inputScope` nor `verdictInputs`. `inputScope == declared` requires non-empty `verdictInputs`; every other value requires `verdictInputs.isEmpty() == true`. And every step whose `done` outcome is reachable through a no-op/skipped branch as well as a work-performing branch must include `"work_performed"` in `recordsFacts` and emit `work_performed=true|false`.
7. *No Guard After the Irreversible Move*: No step with $\text{order} > \text{MERGE\_GATE\_ORDER}$ (`70`) may declare an outcome that refuses on its inputs; post-merge steps record degraded outcomes (`indeterminate`, `landing_delivery: pending`, carried late findings) instead. An I/O failure of a post-merge step routes to a `retry`/`escalate` state, never to a refusal that strands the merged plan. The single exception is the open-pull-request refusal of `archive-plan` (`1100`), which applies only when the plan's pull request is open and unmerged, so no irreversible move has happened; with `merge_outcome: merged` it never refuses.
8. *Declared Finding Sources*: The finding-filing step set is $\{d : \neg d.\text{filesFindings}().\text{isEmpty}()\}$ over the registered roster; it is derived, never listed. At runtime the findings store refuses a write from a step whose `filesFindings` does not contain the finding's `source`.

=== Re-Entry & `head_at_completion` Verdict Currency Rules

When Phase 6 re-enters after a loop-back from Phase 5, an in-branch settle commit, a `sync-baseline` rebase, or a session resume, the engine decides for each step whether to `SKIP` (preserving its prior `done` verdict) or `RE_FIRE`.

==== Fail-Closed `head_at_completion` Anchor Obligation
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-22[PM-WATCH-PHASE-22]_

* Every step with `headDependent == true` must record `head_at_completion: "<40-hex-sha>"` in `mcp/status.json` when transitioning to `done`.
* Any attempt to record `done` for a `headDependent == true` step without a valid `head_at_completion` SHA is **refused** (`error: "missing_head_at_completion"`).
* The server derives `head_at_completion` from `git rev-parse HEAD` of the plan's worktree in the same transition that records `done`; no link accepts it as a parameter. The same rule holds for every recorded commit identity (`reviewed_commit_sha`, `commit_sha`, `branch_pushed_at.head_sha`) and for `pr_number`, so an invented or padded SHA can never enter a step record.
* On re-entry, if a step's persisted record lacks `head_at_completion`, the engine reports the prior record as `unverified` and unconditionally re-fires the step.

==== Deterministic Verdict Currency Algorithm (`VerdictCurrencyEvaluator`)
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-23[PM-WATCH-PHASE-23], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-62[PM-WATCH-PHASE-62]_

[[verdict-input-scope]]*Verdict Input Scope (`input_scope`)*: Every `headDependent == true` step descriptor declares `input_scope` from a closed enum, validated by `FinalizePipelineValidator` rule 6 (a missing value is a validation error, never a default):

* `remote_state`: the verdict is a property of remote state (`ci-verify`, `automatic-review`, `sonar-roundtrip`); currency is decided by remote evidence, and the recorded verdict is stale on every change of `HEAD`. `verdict_inputs` is empty.
* `open_ended`: the step's body runs something open-ended over the repository, so no sound input subset exists; the verdict is stale on every change of `HEAD`. A step has no sound subset when any of three shapes applies: (1) a test suite that asserts against the real tree, (2) a scan whose inputs are discovered at run time rather than fixed, (3) a whole-repository walk. Example: `pre-push-quality-gate`. `verdict_inputs` is empty.
* `plan_footprint`: the step's subject is the plan's changes; the scope resolves at evaluation time to the realized footprint (Footprint-Scoped Inputs below). `verdict_inputs` is empty.
* `declared`: the step's verdict is a property of named files; `verdict_inputs` lists them as explicit, non-empty globs naming what determines the truth of the recorded claim.

For a `headDependent == true` step $S$ with recorded `head_at_completion` $= H_{\text{rec}}$ and current worktree `HEAD` $= H_{\text{cur}}$:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.finalize;

import java.util.List;
import java.util.Optional;
import java.util.Set;

public enum CurrencyVerdict {
    CURRENT_SAME_HEAD,
    PRESERVED_INPUTS_UNAFFECTED,
    STALE_MISSING_ANCHOR,
    STALE_REBASE_ADVANCED,
    STALE_UNSCOPED_HEAD_CHANGE,
    STALE_INPUTS_MODIFIED
}

public final class VerdictCurrencyEvaluator {

    public CurrencyVerdict evaluate(
            FinalizeStepDescriptor step,
            String recordedHeadSha,
            String currentHeadSha,
            boolean rebaseReplayedCommits,
            Set<String> changedRepoRelativePaths) {

        if (recordedHeadSha == null || recordedHeadSha.isBlank()) {
            return CurrencyVerdict.STALE_MISSING_ANCHOR;
        }
        if (recordedHeadSha.equals(currentHeadSha) && !rebaseReplayedCommits) {
            return CurrencyVerdict.CURRENT_SAME_HEAD;
        }
        // changedRepoRelativePaths is the tree diff H_rec..H_cur (git diff --name-only H_rec H_cur);
        // after a replaying rebase it includes the upstream changes the rebase pulled in.
        // inputScope is present on every headDependent step (FinalizePipelineValidator rule 6).
        List<String> globs;
        switch (step.inputScope().orElseThrow()) {
            case REMOTE_STATE, OPEN_ENDED -> {
                // remote_state: currency is decided by remote evidence; open_ended: no sound
                // input subset exists. Both are stale on every change of HEAD.
                return rebaseReplayedCommits
                    ? CurrencyVerdict.STALE_REBASE_ADVANCED
                    : CurrencyVerdict.STALE_UNSCOPED_HEAD_CHANGE;
            }
            case PLAN_FOOTPRINT -> {
                // realized footprint plus the paths the step's own commits touched
                Optional<List<String>> footprint = resolvePlanFootprint(step);
                if (footprint.isEmpty()) {
                    return CurrencyVerdict.STALE_UNSCOPED_HEAD_CHANGE;   // unresolvable: fail-closed
                }
                globs = footprint.get();
            }
            case DECLARED -> globs = step.verdictInputs();   // non-empty by validation
        }
        boolean anyInputTouched = changedRepoRelativePaths.stream()
            .anyMatch(path -> matchesAnyFnmatchGlob(path, globs));
        return anyInputTouched
            ? CurrencyVerdict.STALE_INPUTS_MODIFIED
            : CurrencyVerdict.PRESERVED_INPUTS_UNAFFECTED;
    }
}
----

* *No Re-Stamp on Preserve Invariant*: When `VerdictCurrencyEvaluator` returns `PRESERVED_INPUTS_UNAFFECTED` (because `git diff --name-only <H_rec>..<H_cur>` touched zero paths matching the step's resolved inputs), the step is skipped and its persisted `head_at_completion` **remains $H_{\text{rec}}$** — it is **never** overwritten with $H_{\text{cur}}$. Keeping $H_{\text{rec}}$ ensures that subsequent commits are always diffed against the cumulative range since the step actually executed.
* *Rebase vs No-Op Rebase*: A step declaring `advancesMainViaRebase == true` (`sync-baseline`, `branch-cleanup`) can invalidate downstream verdicts **only** when it actually replayed commits (`action == "rebased"` and `upstream_commit_count > 0`). When the branch was already up-to-date (`work_performed == false`), `HEAD` does not change and existing verdicts remain current.
* *Path-Derived Re-Fire After a Replaying Rebase*: A replaying rebase does not by itself stale a verdict. The changed paths are the tree diff between $H_{\text{rec}}$ and $H_{\text{cur}}$, which includes the upstream changes the rebase pulled in, and a `declared` or `plan_footprint` step re-fires iff that diff touches its resolved inputs (`STALE_INPUTS_MODIFIED`), in both directions: an upstream change to an input re-fires the step even when the plan's own commits did not touch it, and an unrelated upstream change never re-fires it. Only `remote_state` and `open_ended` steps return `STALE_REBASE_ADVANCED`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` classifies by the same tree diff over declared `verdict_inputs`, but an absent declaration is legal there and silently means "invalidated on every `HEAD` change" (in practice no bundled step declares `verdict_inputs`); `PM-MCP` requires an explicit `input_scope` on every head-dependent step and validates it at build time and startup, and adds the resolved `plan_footprint` scope that `plan-marshall`'s static glob vocabulary cannot express.
* *Footprint-Scoped Inputs (`plan_footprint`)*: A step whose subject is the plan's changes (`simplify`, `security-audit`, `pre-submission-self-review`) declares `input_scope: plan_footprint` with empty `verdictInputs`; the evaluator resolves the scope at evaluation time to the realized footprint (link:store-schemas.adoc#three-way-footprint[Store Schemas Specification, Three-Way File Footprint Reconciliation]) together with the paths the step's own commits touched. An unresolvable footprint makes the verdict `STALE_UNSCOPED_HEAD_CHANGE` (fail-closed).
* *Skip Basis*: Every currency decision, skip or re-fire, is persisted on the step record as `skip_basis` (`verdict`, `h_rec`, `h_cur`, `changed_paths_count`, `inputs_touched`), so a skip is auditable and never leaves no record.

==== Step Records, Re-Fire & Loop-Back Rules
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-11[PM-WATCH-PHASE-11], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-21[PM-WATCH-PHASE-21], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-71[PM-WATCH-PHASE-71]_

* *Settled Completions Only*: A step completion record (`done`) is emitted only for settled outcomes. `loop_back` and defer emit none, so a re-fired step never produces two completions.
* *Firings & Re-Fire Replaces*: The persisted step record keeps one entry per firing (`firings[]` with `dispatch_id`, `started_at`, `outcome`, and `cause`: `first`, `loop_back`, `failure`, `error`, or `input_changed`); the current outcome is the last firing's. When `VerdictCurrencyEvaluator` decides `RE_FIRE`, the step's outcome is set to `unverified` before the step runs and is replaced by the new terminal outcome; a prior `done` never survives a re-fire, a refused outcome change is appended as a firing and never leaves the prior outcome silently current, and no force flag exists. Re-fire counts are derived from the firings per cause, never from the step-outcome log. Each firing also records `productive` (it produced a commit or filed a finding, derived from the change ledger and the findings store), so re-fires are published split into productive and unproductive ones and an unproductive re-fire pattern is visible beside the loop-back counts (link:workflow-dsl.adoc#loop-back-bounds[Workflow DSL Specification]).
* *Phase-Exit Completeness*: The check is positional. Entering a step of order N requires, for every manifest step of order < N, a satisfied outcome: `done` or `skipped` whose currency verdict against the current `HEAD` is `CURRENT_SAME_HEAD` or `PRESERVED_INPUTS_UNAFFECTED` (for steps that are not `headDependent`, the presence of `done` in the firing of the current `loop_back_iteration`), or `skipped_by_operator` (an operator decision with its own audit record; its stale `head_at_completion` stays as the record); a stale `done`, or a firing from an earlier iteration, counts as missing. At `branch-cleanup` (70) entry the check runs before any rebase that `branch-cleanup` performs. Currency evidence produced inside `branch-cleanup` after its own rebase (fresh CI and review results on the rebased `HEAD`) is recorded on the affected remote-state steps as their new evidence; how that evidence is obtained is part of the open git/GitHub/GitLab design topic. Phase 6 exit (after the merge, when no worktree `HEAD` exists) requires every step of order > 70 to have a settled outcome (`done`, `skipped`, or `skipped_by_operator`) and checks no currency, since nothing is merged anymore.
* *Operator Skip*: A step the operator skips (operator CLI or elicitation) while its currency verdict is stale is recorded as `skipped_by_operator` with its stale `head_at_completion` kept, never as `done` at the current `HEAD`; it satisfies Phase-Exit Completeness.
* *Stale-Finding Re-Anchor*: Before `loop_back` is offered, every open finding is re-anchored against `HEAD` (from the commit it was raised against); a finding whose cited location no longer exists is resolved as stale (status `resolved`, `resolution: taken_into_account`, recorded and never counted as fixed). If only stale findings remain, `loop_back` is omitted and the loop closes.

=== Pre-Merge Review Barrier & Operator Merge Authorization Grants

Inside `default:branch-cleanup` (`order = 70`), immediately before executing the merge command (`pr safe-merge` or `merge-queue` enqueue), the engine enforces the fail-closed **Pre-Merge Review Barrier**.

==== Two Fail-Closed Barrier Predicates
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-24[PM-WATCH-PHASE-24], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-25[PM-WATCH-PHASE-25], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-33[PM-WATCH-PHASE-33]_

Both predicates must evaluate to `true` against the current worktree `HEAD` SHA ($H_{\text{cur}}$):

1. *Predicate 1 — Zero Unhandled Findings*: Every finding in the findings store originating from `automatic-review`, `ci-verify`, or `sonar-roundtrip`, and every other finding with `blocking == true` of any `source` of the findings store's source enumeration (`self_review`, `qgate`, `security_audit`, `code_review`, `arch_gate`, `compiler`, `self_report`, `dependency_delta`), must have a persisted, terminal triage disposition (`FIX`, `SUPPRESS`, or `ACCEPT`; status `triaged_*` or `resolved`) whose server-written `resolution` is not `pending`; a `FIX` whose fix has not landed is still `pending` and fails the predicate. A finding with a provider address (`provider_ref`) must also have its outbound response or dismissal transmitted to the provider (`transmit_outcome == "sent"`), which requires a per-finding reply on the finding's own thread or comment; a bot's own resolution marker or a PR-level note is not a response. An unmet triage commitment (Unified Triage Hook) fails the predicate. *Deliberate change vs. `plan-marshall`*: `plan-marshall` counts only pending PR-comment findings and does not require transmission; `PM-MCP` covers every blocking finding and requires the response to be transmitted.
2. *Predicate 2 — Required-Bot Participation on Current `HEAD`*: Every bot in the required set (resolved from `required_bots` against the review-bot registry, <<automatic-review>>) must have a participation record (link:store-schemas.adoc#review-participation[Store Schemas Specification]) whose `state` is `participated` or `participated_but_empty`, whose `reviewer_login` equals the bot's registered `author_login`, and which passes the review currency test for $H_{\text{cur}}$. A SHA match without an author match never satisfies the predicate. A `bot_status` other than `completed` (link:hypermedia-format.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations]), and every other per-bot state (<<automatic-review>>: in particular `not_triggered`, `refused` of any mode, including a spend-capped or quota-exhausted reviewer, `declined`, `unproven`, `unreadable`, and `silent`), **never** satisfies Predicate 2 and **never** automatically mints a merge grant.
+
*Review Currency*: The currency test applies to every required bot; no registry field exempts a bot from it. Its strictness is the team setting `review.currency` (`.marshall/config/project.json`, link:store-schemas.adoc#config-project-json[Store Schemas Specification]): `exact_sha` requires `covered_commit_sha` to equal $H_{\text{cur}}$; `after_last_push` (the default) accepts a `covered_commit_sha` equal to $H_{\text{cur}}$, or, for a bot whose registry declares `reviewed_sha_carrier: none`, review evidence whose `created_at` is later than the last push of the branch (`branch_pushed_at`). A review evidence object that names a commit other than $H_{\text{cur}}$ never passes, and a latest evidence object that predates the last push resolves `unproven`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` applies currency only to bots whose registry declares `participation_requires_update`, so one exempt bot disables the test for the ANDed gate; `PM-MCP` evaluates currency per bot record for every required bot.
+
*Empty Required Set*: An empty required set satisfies Predicate 2 only as the roster aggregate `vacuous` (the team answered with an empty list: `review.required_bots: []` in `project.json`): the merge proceeds and records `review_state: vacuous` on the merge record and the landing. The roster aggregate `unestablished` (the key is absent: the question was never answered) fails Predicate 2; only a `review_barrier_gap` grant proceeds, and the merge records `review_state: unreviewed_by_grant`. A merge whose required bots all satisfy Predicate 2 records `review_state: reviewed`.

If the findings store cannot be evaluated, the barrier routes to an explicit `unknown` disposition: a `review_barrier_gap` in `ask` mode with cause `findings_unevaluable`, neither a hard halt nor a pass. A refusal of the barrier lists each blocking finding (`finding_id`, `source`, `severity`, age, failing predicate) in `facts`, never only a count.

A grant authorizes exactly one *gap class*; HEAD binding alone is never authorization.

==== Operator Merge Authorization Record (`MergeAuthorizationRecord`)
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-32[PM-WATCH-PHASE-32], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-57[PM-WATCH-PHASE-57], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-70[PM-WATCH-PHASE-70]_

When the barrier fails, a gate requires consent, or an override is requested, the plan cannot merge unless an admissible `MergeAuthorizationRecord` exists in `mcp/status.json` for the active gap class (or, for `merge_action`, the operator's `merge.auto_merge` is `true`).

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.finalize;

import java.time.Instant;
import java.util.Set;

public enum MergeGapClass {
    REVIEW_BARRIER_GAP("review_barrier_gap"),
    MERGE_ACTION("merge_action"),
    RED_CI_GATE("red_ci_gate"),
    REREVIEW_TIMEOUT("rereview_timeout"),
    FIND_STEP_COMPLETION("find_step_completion");

    private final String wireName;
    MergeGapClass(String wireName) { this.wireName = wireName; }
    public String wireName() { return wireName; }
}

public record MergeAuthorizationRecord(
    String kind,
    String planId,
    String headSha,
    MergeGapClass gapClass,
    String operatorChannel,       // "elicitation" or "operator_cli"
    String operatorRationale,
    Set<String> coveredFindings,  // finding_ids open (not terminally dispositioned) when the grant was minted
    Instant grantedAt
) {
    public boolean isAdmissibleFor(String currentHeadSha, MergeGapClass activeGapClass,
                                   Set<String> unhandledFindingIds) {
        return this.headSha != null
            && this.headSha.equals(currentHeadSha)
            && this.gapClass == activeGapClass
            && this.coveredFindings.containsAll(unhandledFindingIds);
    }
}
----

* *Grants Cover Named Findings*: A grant records in `coveredFindings` the findings that were unhandled (failing Predicate 1) when it was minted. It stays admissible only while every unhandled finding at evaluation time is in that set: a finding filed later on the same `HEAD` (a late bot comment) reopens the barrier and needs its own triage or a new grant. The same rule binds an `accept` scope deviation: its `accepted_deviations[]` entry records `covered_findings[]`, and a finding filed after the acceptance is never treated as dispositioned by it.
* *Operator-Only Minting*: Grants are minted through the authenticated operator channel (MCP elicitation or `pm-mcp operator authorize-merge --plan <plan_id> --head <sha> --gap-class <class> --rationale <text>`) only; the server never mints a grant. *Deliberate change vs. `plan-marshall`*: `plan-marshall`'s `re_review_on_timeout: proceed` policy branch (`branch-cleanup-rereview.md`), which merges unreviewed code without an operator, does not exist. The operator's `merge.auto_merge` is the only standing consent; it satisfies `merge_action` and no other gap class and records no grant. Free-text lines in `decision.log` are never accepted as authorization evidence. A re-grant of the same `kind` supersedes the previous record: the prior record is kept with `superseded_at` and is never admissible again.
* *Route on `admissible`, Never on Boolean `authorized`*: The barrier checks `grant.isAdmissibleFor(currentHeadSha, activeGapClass, unhandledFindingIds)`. A grant minted for an earlier commit $H_1$ or for `RED_CI_GATE` is inadmissible if `HEAD` advances to $H_2$ (e.g., after rebase) or if the active gap is `REVIEW_BARRIER_GAP`.
* *Merges Under a Grant Are Marked Unreviewed*: A merge that proceeds under a `rereview_timeout` or `review_barrier_gap` grant records `review_state: unreviewed_by_grant` (with the grant's `kind`, gap class, and the commit no review covered) on the merge record, in a pull-request comment the server posts, and in the landing; it is never reported as a reviewed merge.

=== Cross-Plan Merge Mutex, FIFO Admission Queue & Epic Plan Emission
_See Requirement link:../Requirements.adoc#PM-WF-15[PM-WF-15: Epic Plan Emission & Cross-Plan Merge Mutex]_

==== Cross-Plan Merge Mutex & FIFO Admission Queue
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-44[PM-WATCH-PHASE-44], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-45[PM-WATCH-PHASE-45]_

When multiple plans execute concurrently across worktrees of the same repository, `default:branch-cleanup` (`order = 70`) serializes their rebase-and-merge critical sections through the **Cross-Plan Merge Mutex** (`MergeMutexManager`), a lease persisted in `<PM_MCP_BASE>/state/merge-queue.json` whose updates run as short transactions under `<PM_MCP_BASE>/locks/merge.lock` (`PM-IMPL-7`; cross-plan review-bot rate-window claims are separate leases in `<PM_MCP_BASE>/state/review-bot-windows.json`):

[source,text]
----
Plan A (branch-cleanup) ──► [Enqueue FIFO] ──► [Acquire Holder Slot]
                                                      │
                        ┌─────────────────────────────┴─────────────────────────────┐
                        │ Widened Critical Section:                                 │
                        │  1. git fetch + rebase onto base (worktree-rebase-to)     │
                        │  2. Post-rebase CI / re-review check                      │
                        │     └─► If async wait required: RELEASE slot & keep FIFO  │
                        │  3. Pre-merge barrier check (last gate before merge)      │
                        │  4. Closed merge dispatch (safe-merge | merge-queue)      │
                        └─────────────────────────────┬─────────────────────────────┘
                                                      ▼
                                            [Release Mutex & Pop]
----

1. *FIFO Admission Queue*: Plans requesting the merge mutex enter an ordered per-repository FIFO `waiting[]` keyed by `plan_id`, `owner_pid`, and `enqueued_at`. A plan may acquire the active `holder` slot only when it is at the head of the FIFO queue and `holder == null`. Enqueueing is idempotent per `plan_id` (a waiter already in `waiting[]` keeps its position), and a holder re-requesting the mutex is granted reentrantly without re-queueing.
2. *Widened Hold across Rebase-to-Merge*: Unlike a narrow lock around `gh pr merge`, the merge mutex is acquired **before** `branch-cleanup` rebases the feature branch onto `main` and held through the merge execution so a sibling plan cannot land a conflicting commit on `main` between rebase and merge.
3. *Mandatory Release on Every Wait & Abort*: A plan must **never** hold the merge mutex while blocked in an asynchronous wait (`wait:finalize.concurrent-wait` for post-rebase CI, review-bot rate-window wait, merge-queue landing wait, or operator elicitation/escalation) or on abort. Entering any `wait` or `escalate` state inside `branch-cleanup` atomically releases `holder = null` while preserving the plan's FIFO queue position, allowing ready sibling plans to merge without head-of-line blocking.
4. *Atomic Stale-Holder & Budget Reclaim*: Reaping runs inside the same short transaction as admission. An active `holder` is forcibly reclaimed if and only if it is provably stale — either the runtime instance recorded as owner is no longer alive (PID plus start instant) and no active git/CI job for that plan is running, the holding `plan_id` is in a terminal state (`completed`, `aborted`), or the holder's lease budget (`lease_expires_at`, refreshed by every heartbeat transition; link:timeouts.adoc#merge-lease[Timeouts & Budgets Specification, Merge Holder Lease]) has expired.
5. *Closed Merge Dispatch Set*: `branch-cleanup` executes merges exclusively through one of two closed mechanisms: direct `safe-merge` (squash/merge via enrolled CI provider when branch is up-to-date and green) or `merge-queue` enqueue (selected only when the provider reports a merge queue configured for the base branch, checked immediately before enqueueing; transitions to `finalize.merge-queue-wait` after releasing the mutex).
+
The enqueue counts only after a post-condition read of this PR's own queue membership (GitHub: repository `mergeQueue.entries` containing the PR); neither the CLI exit code, nor the existence of a queue rule, nor `mergeStateStatus` (which reads `CLEAN` while queued) is membership evidence, and an unobservable membership records `enqueued: indeterminate`. After either mechanism, the merge is confirmed only by the provider's observed pull-request state (`merged`, with the merge commit on the base branch), never by the merge command's return value or exit code. `finalize.merge-queue-wait` waits for a terminal outcome — `merged`, `ejected`, `closed`, or `timed_out` — because an entry can be ejected on rebase after its checks turned green; a PR that leaves the queue unmerged routes to `escalate`.

==== Epic Plan Emission (`emit:<plan_id>`)
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-41[PM-WATCH-PHASE-41]_

Orchestrator epics (`scope: epic`) manage multi-plan workstreams stored in `.marshall/orchestrator/<epic_id>/` (`epic.json` header and per-plan `.marshall/orchestrator/<epic_id>/queue/<plan_id>.json` files, keyed by the child plan's `plan_id`; the epic-local ordinal is display-only, link:dispatch-and-effort.adoc[Dispatch & Effort Specification]).

* *Never Dispatch a Plan as a Sub-Agent*: Because sub-agents are single-level leaf workers (`PM-WF-5`) and every plan dispatches its own leaf sub-agents during Phases 2–6, an epic **never** offers a `dispatch` link to launch a plan and **never** executes a plan inline.
* *Staging-Time Surface Disjointness*: Disjointness is a modelling invariant of one epic, not a runtime gate. When the epic stages a plan, the queue row declares its expected surface (`declared_surface`), and the server refuses the staging with `surface_overlap` when it overlaps the declared surface of another non-terminal row of the same epic that is not ordered with it through prerequisites, and with `surface_undeclared` when the surface cannot be declared (link:dispatch-and-effort.adoc#epic-surface-disjointness[Dispatch & Effort Specification, Staging-Time Surface Disjointness]). There is no cross-epic check and no check against plans started without an epic; such conflicts surface at rebase or merge (open git/GitHub/GitLab design topic).
* *`emit:<plan_id>` Transition (`rel: emit`)*: For each staged plan whose prerequisite rows are in the partition `terminal.shipped` (`merged` or `completed`), the epic state offers `emit:<plan_id>` (emission compares no surfaces); the representation shows the row's re-grounding staleness (`regrounded_at_sha`, `main_commits_since`, link:dispatch-and-effort.adoc[Dispatch & Effort Specification]). Following `emit:<plan_id>`:
** Updates `.marshall/orchestrator/<epic_id>/queue/<plan_id>.json` atomically (`status = "launched"`) under the epic lock.
** Returns the exact operator bootstrap command (`pm-mcp enter --client <client> plan <plan_id> --from-epic <epic_id>`) in `facts.emitted_command`. Emission is always operator-mediated: there is no `auto_emit` setting, and the server never spawns a background plan session.
** Transitions the epic's view of `<plan_id>` from `launched` to `running` on the next call on the epic scope after `pm_start` has consumed the pending entry record written by `pm-mcp enter` (its session becomes the first row of `plans/<plan_id>/sessions.jsonl`, its `from_epic` the plan's `origin.epic_id`; link:store-schemas.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]).
