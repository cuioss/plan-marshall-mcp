== Overview

This document specifies the end-to-end phase state machines (Phases 1–6), transition guards, Q-Gate validation loop, change-type and scope-deviation contracts, Phase 5 envelope execution and verification sweep, Phase 6 finalize step ordering bands, `FinalizeStepDescriptor` schema, verdict currency rules, pre-merge review barrier, and cross-plan merge mutex for *plan-marshall-mcp* (`PM-MCP`).

In `PM-MCP`, the prose-driven orchestrator loops, phase handshake files (`handshakes.toon`), and intra-phase step-recording rituals (`mark-step-done`, `assert-step-recorded`) of the legacy script architecture are replaced by deterministic server-owned state machines defined in `classpath:/workflows/*.pmwf` and executed by `pm-mcp-core`.

=== Lifecycle Topology (Phases 1–4)

The planning lifecycle is a server-enforced state machine spanning `phase-1-init`, `phase-2-refine`, `phase-3-outline`, and `phase-4-plan`. Sub-states that previously lived only in the orchestrating model's conversation context (`refine.awaiting_answers`, `outline.review`, Q-Gate iteration counters, and re-dispatch counters) are persisted in `mcp/status.json` so that any session restart or `/clear` resumes at the exact sub-state via `pm_state(plan_id)`.

[source,text]
----
┌──────────────────────────────────────────────────────────────────────────────────┐
│ Phase 1: init (pm_start)                                                         │
│  init.classify -> [init.awaiting_user] -> init.ready                             │
│  (Plan source resolution, phantom-ID guard, recipe match, initial lane routing)  │
└────────────────────────────────────────┬─────────────────────────────────────────┘
                                         │ (clean-tree guard; recipe shortcut -> Phase 3)
                                         ▼
┌──────────────────────────────────────────────────────────────────────────────────┐
│ Phase 2: refine                                                                  │
│  refine.baseline-reconcile -> refine.analyze -> [refine.awaiting_answers (<=1x)] │
│  -> [refine.qgate (<=3x)] -> refine.ready                                        │
│  (5 quality dimensions + module mapping, widen-only domains, pr_title authored)  │
└────────────────────────────────────────┬─────────────────────────────────────────┘
                                         │ (artifact gate: clarified_request + pr_title)
                                         ▼
┌──────────────────────────────────────────────────────────────────────────────────┐
│ Phase 3: outline                                                                 │
│  outline.detect-change-type -> { outline.light | outline.deep }                  │
│  outline.light --(cap > 25 | band > 8 | premise/cross-cutting)--> outline.deep   │
│  -> outline.validate (intent markers, file-type buckets, narrow domains once)    │
│  -> [outline.qgate (<=3x)] -> outline.review (Operator Approval Gate)            │
└────────────────────────────────────────┬─────────────────────────────────────────┘
                                         │ (artifact gate: validated outline.md
                                         │  + operator approval via elicitation/CLI)
                                         ▼
┌──────────────────────────────────────────────────────────────────────────────────┐
│ Phase 4: plan                                                                    │
│  plan.derive-tasks (DAG cycle check, profile mapping, skill resolution)          │
│  -> plan.describe-tasks (+ server-side cost sizing, envelope packing & manifest) │
│  -> [plan.qgate (<=3x)] -> execute.worktree-init                                 │
└──────────────────────────────────────────────────────────────────────────────────┘
----

=== Phase 1 (`init`): Plan Sources, Phantom-ID Refusal & Classifiers

==== Plan Source Contracts

`pm_start` initializes the plan directory (`.plan/local/plans/<plan_id>/`), `request.md`, `references.json`, and `mcp/status.json` from one of four closed plan sources (`PlanSource`):

[cols="1,2,4"]
|===
|Source (`plan_source`) |Input Parameters |Server Initialization & Verification Behavior

|`request`
|`description` (or `request`), optional `slug`, `base_branch`
|Writes `original_input` to `request.md`, runs the deterministic recipe scorer (`auto_route_recipe`) ahead of the planning-lane router, detects initial domains from narrative path tokens, and checks for sibling plan collisions.

|`issue`
|`issue_number`, optional `slug`, `base_branch`
|Spawns an enrolled CI provider job to fetch the issue title and body into `request.md` (passing untrusted external content through the deterministic ingestion validator), records `issue_number` in `references.json`, and schedules asynchronous CI mirror jobs to post clarified requirements and the approved outline back to the issue after Phase 2 and Phase 3 transitions.

|`lesson`
|`lesson_id`, optional `slug`, `base_branch`
|Resolves the lesson in the main-anchored lesson store (`manage-lessons`), executes a deterministic *source premise check* verifying that cited files and symbols in the lesson still exist in the current tree (transitioning to `init.awaiting_user` with obsolescence options if the premise is already resolved or invalid), and atomically moves/retires the lesson file into the plan's lifecycle scope. If the plan is later deleted via `delete-plan`, the server enforces a fail-closed *lesson carry-back veto* that restores the lesson to the main-anchored corpus and refuses plan deletion if restoration fails.

|`recipe`
|`recipe_id`, optional `recipe_params`, `base_branch`
|Binds the plan to a registered recipe definition (`skill://pm/recipe/<name>/SKILL.md`), appends a mandatory UTC timestamp suffix to `plan_id` (`<recipe-slug>-YYYYMMDD-HHMMSS`) to prevent git branch and worktree collisions across repeated runs of the same recipe, sets `confidence = 100` and `planning_lane = deep` (`track = complex`), and skips Phase 2 quality analysis and Phase 3 change-type/Q-Gate steps.
|===

==== Plan ID Derivation & Phantom-ID Refusal Guard

The server derives or validates `plan_id` against a strict lexical grammar before creating any directory on disk:

1. *Canonical Slug Pattern*: `^[a-z0-9][a-z0-9-]{1,48}[a-z0-9]$` (with recipe plans suffixed by `-\d{8}-\d{6}`).
2. *Phantom-ID Refusal*: The validator explicitly rejects any candidate `plan_id` or `slug` matching either a lesson identifier pattern (`^\d{4}-\d{2}-\d{2}-\d{2}-\d{3}$`) or a UUID / hex-digest pattern (`^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$` or bare 32/40/64-char hex strings). Rejecting these shapes prevents callers from accidentally passing a lesson ID or dispatch/session UUID into `plan_id` and creating a phantom plan directory.

==== Deterministic Init Classifiers & Workflow Settings

During `init.classify`, the engine executes pure, model-free classifiers in a fixed order:

1. *Recipe Match before Lane Routing*: When `plan_source == request` and `auto_route_recipe == true`, the registry-wide recipe scorer evaluates the request narrative first. An explicit `recipe` source selection is never overridden by the scorer.
2. *Initial Planning-Lane Router*: Computes the initial `planning_lane` (`light` or `deep`) and pre-route `scope_estimate` (`none`, `surgical`, `single_module`, `multi_module`, `broad`).
3. *Sibling Collision Detector*: Scans live plans for overlapping target modules or affected file paths; if an overlap is found, transitions to `init.awaiting_user` to resolve the collision (`proceed`, `rename`, or `abort`).
4. *Workflow Settings Resolution*: Reads project workflow configuration from `.plan/marshal.json` (`init_without_asking`, `plan_without_asking`, `execute_without_asking`, `auto_route_recipe`, `confidence_threshold`, `compatibility`, `simplicity`, and execution posture `minimal | standard | full`) to determine which interactive states are entered vs auto-advanced.

=== Routine User Interaction vs Operator-Authorizing Decisions
_See Requirement link:../Requirements.adoc#PM-WF-12[PM-WF-12: Routine User Dialogue vs Operator-Authorizing Elicitation]_

`PM-MCP` separates interactive questions into two security classes with distinct transport rules:

[cols="2,2,2,3"]
|===
|Interaction Class |Target States & Decisions |Permitted Channels |Fallback & Audit Semantics

|*Routine User Dialogue* (Non-Authorizing)
|Existing plan collision (`replace`, `resume`, `abort`), obsolete lesson premise (`close`, `continue`), recipe selection, ambiguous domain selection, sibling plan collision, execution posture choice (`minimal`, `standard`, `full`), Phase 2 request clarifications (`refine.awaiting_answers`), Phase 3 design clarifications (`outline.awaiting_answers`), Q-Gate iteration exhaustion (`*.qgate-exhausted`).
|Host MCP Elicitation (preferred), or model-relayed `submit` link (`answer_questions`) when host elicitation is unsupported or unavailable.
|The plan persists a `<phase>.awaiting_user` (or `<phase>.awaiting_answers`) state carrying a typed `questions` schema in `facts`. When answered via the model-relayed `submit` link, the transition succeeds and records `channel: "model_relayed"` in `audit.jsonl`.

|*Operator-Authorizing Decisions* (Gate-Forcing / Privileged)
|Solution outline approval (`outline.review` -> `phase-4-plan`), scope-deviation `accept` (`execute.deviation-review`), handshake or baseline drift override, bare-transition artifact-gate exemption (`--allow-bare-transition`), pre-rebase overlap override & pre-merge consent, pre-merge barrier / coverage-gap / red-CI / bot-demotion grants, and plan deletion (`delete-plan`).
|Host MCP Elicitation, or Authenticated Operator CLI (`pm-mcp operator ...`).
|*Strict Link Omission (`PM-WF-3`)*: No model-invocable `submit` or `noop` link is ever emitted to approve or force these gates. If the host does not support MCP elicitation, the state transitions to `<phase>.blocked`, emits the exact `pm-mcp operator` command in `facts.operator_command`, and offers only a `wait` link until the operator acts.
|===

==== Typed Question Envelope Schema (`*.awaiting_user`)

Sub-agents operating in leaf `execution-context` scopes are forbidden from prompting the user in-leaf or blocking on `escalate`. Instead, a sub-agent completes its analysis pass using its best judgment and includes a batched question list in its `submit` payload (`refine_prompt` or `outline_prompt`). Each question conforms to the following Java record and TOON tabular structure:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.dialogue;

import java.util.List;

public record UserQuestion(
    String id,
    String header,
    String question,
    List<String> options,
    String recommended,
    boolean allowFreeText
) {}
----

Every option string in `options` is authored as a two-sided contract whose label explicitly names the workflow branch selected when chosen, with the `recommended` option listed first.

=== Phase 2 (`refine`): Quality Aggregation, Domain Widening & Bounded Re-Dispatch

==== Phase Entry & Baseline Reconciliation

At `phase-2-refine` entry, the engine caches loop-invariant inputs (`request.md`, `references.json`, `module_mapping.json`, and the architecture overview) so they are read once per phase rather than re-read inside the confidence loop. When a base branch is configured, `refine.baseline-reconcile` runs a non-mutating `git merge-tree` probe against upstream and classifies drift into three outcomes:

* `no_overlap`: Upstream commits touch disjoint files; advances directly to `refine.analyze`.
* `overlap_no_content_conflict`: Overlapping files merge cleanly; records `auto_reconcilable: true` without mutating the tree (deferring the actual rebase to Phase 5/6) and advances to `refine.analyze`.
* `overlap_with_content_conflict`: Content conflicts exist; emits blocking Q-Gate findings so the conflict is absorbed during request refinement.

==== Five Quality Dimensions & Fixed-Weight Confidence Aggregation

During `refine.analyze`, the dispatched refine sub-agent executes source-premise verification (checking cited files, flags, and APIs against the codebase) and proposed-fix verification (constructing a semantic probe to verify whether a proposed fix resolves the stated symptom), maps affected modules, estimates scope (`none`, `surgical`, `single_module`, `multi_module`, `broad`), authors a conventional-commit `pr_title` ($\le 72$ characters, distinct from the human plan `title`), and submits raw scores (`0..100`) for the five quality dimensions plus architectural module mapping.

The server-side `ConfidenceAggregator` computes the overall confidence deterministically using fixed weights (zero LLM arithmetic):

[cols="2,1,4"]
|===
|Dimension |Fixed Weight |Verification Criteria

|`correctness`
|20%
|Technical validity of referenced modules, APIs, flags, source premises, and proposed fixes against the live architecture.

|`completeness`
|20%
|Presence of clear scope boundaries, acceptance criteria, test expectations, and cross-module dependencies.

|`consistency`
|20%
|Absence of internal contradictions or conflicting constraints across request sections and architecture rules.

|`non_duplication`
|10%
|Absence of redundant or overlapping requirement statements.

|`ambiguity`
|20%
|Single unambiguous interpretation of terminology, target scope, and measurable outcomes (`100` = unambiguous).

|`module_mapping`
|10%
|Confidence in mapping the request to concrete project modules and dependency directions.
|===

$$\text{confidence} = \lfloor 0.20 \cdot S_{\text{corr}} + 0.20 \cdot S_{\text{comp}} + 0.20 \cdot S_{\text{cons}} + 0.10 \cdot S_{\text{nondup}} + 0.20 \cdot S_{\text{ambig}} + 0.10 \cdot S_{\text{mod}} \rfloor$$

* Any omitted dimension defaults to `0` and is recorded in `missing_dimensions` (never silently ignored).
* The aggregated score is persisted to `status.metadata.confidence` and compared against `confidence_threshold` (configured in `.plan/marshal.json -> /plan/phase-2-refine/confidence_threshold`, default: `95`).
* The server also validates that `compatibility` (`breaking | deprecation | smart_and_ask`, mandatory with no fallback) and `simplicity` (`lean | pragmatic | defensive`, defaulting to `lean`) are resolved and persisted.

==== Widen-Only Domain Re-Merge

Once concrete `affected_files` are identified in `refine.analyze`, the server runs `domain-detect` over those file paths (`file_globs` and `always_on` inclusion legs) and computes the set union with the existing `references.domains`:

$$\text{domains}_{\text{new}} = \text{domains}_{\text{cached}} \cup \text{detect}(\text{affected\_files})$$

* *Monotonic Widening Invariant*: Phase 2 may **only widen** `references.domains`, never narrow it, ensuring convergence across refine iterations. If `affected_files` produce zero narrative or glob matches, `domain-detect` returns all offerable domains under `reason = "over_provisioned_resolve"`; that temporary over-provisioning is narrowed exactly once in Phase 3 after deliverables are declared.

==== Single-Batch Clarification & Re-Dispatch Ceiling

If $\text{confidence} < \text{confidence\_threshold}$:

1. The sub-agent submits its best-judgment `clarified_request` alongside a single batched `refine_prompt` containing at most 4 clarification questions prioritized by `Correctness > Consistency > Completeness > Ambiguity > Non-Duplication`.
2. The engine persists the questions in `mcp/status.json`, transitions to `refine.awaiting_answers`, and collects the user's answers in one batch.
3. Upon receiving the answers, the engine writes the `## Clarifications` and `## Clarified Request` sections, increments `refine_redispatch_count` in `mcp/status.json`, and re-dispatches `refine.analyze` **at most once** (`refine_redispatch_count <= 1`).
4. If the second pass still yields $\text{confidence} < \text{confidence\_threshold}$, the engine does **not** loop again; it flags `low_confidence_manual_review: true` in `facts` and advances to `outline` (where `outline.review` gates progression before task creation).

=== One-Way Planning Lane Ratchet (`light` -> `deep`)

`PM-MCP` routes Phase 3 (`outline`) along one of two structural lanes stored in `status.metadata.planning_lane`, which deterministically drives the legacy `track` field (`light => simple`, `deep => complex`):

[cols="1,2,4"]
|===
|Lane |Target Scope |Discovery & Execution Contract

|`light`
|Bounded, localized changes (`scope_estimate` in `{surgical, single_module}` with known target files)
|Executes in a single collapsed scoping envelope (`outline.light`) with a strictly bounded file read set: *Total Read Set Cap* of **25 files** (`cap = 25`, restricted to declared `affected_files` plus their 1-hop dependency neighbors), and *Per-Step Discovery Band* of **8 files** (`band = 8` maximum read expansion within a single discovery step).

|`deep`
|Codebase-wide, multi-module, architectural, or uncertain changes
|Executes full domain discovery, ADR progressive-disclosure scan (`manage-adr scan`), consumer sweeps for symbol renames/deletions, and full Q-Gate verification (`outline.deep`).
|===

==== Lane Ratchet Rules

1. *Unknown Scope Bias*: At initial routing, an unknown or unresolved `scope_estimate` biases fail-safe to `deep`. Conversely, an unset `change_type` does **not** force `deep` when `scope_estimate` and target files are bounded.
2. *One-Way Escalation (`light -> deep`)*: While in `outline.light`, the engine transitions via an explicit ratchet edge to `outline.deep` (locking `planning_lane = "deep"` and `track = "complex"` permanently for the plan) whenever either the *Deterministic Budget Trigger* fires (the sub-agent's file-read counter exceeds `cap = 25` total files or `band = 8` files in a discovery band) or the *Judgment Escalation Trigger* fires (the sub-agent submits `outcome = escalate_to_deep` because discovery revealed a false request premise, cross-module ripple effects, or public symbol deletions requiring a full consumer sweep).
3. *No Down-Ratchet*: No transition exists from `deep` to `light`. Even if Phase 3 discovery later narrows `scope_estimate` from `multi_module` to `surgical` (which may enable the Q-Gate surgical bypass), `planning_lane` remains `deep`.

=== Phase 3 (`outline`): Validation Rules & `outline.review` Gate

When the model submits the solution outline (`outline.md`, accepting `solution_outline.md` as a legacy read alias under `PM-MIG-3`) in `outline.light` or `outline.deep`, the server-side `OutlineValidator` enforces four structural invariants before accepting the transition:

==== 1. Per-File Intent Marker Validation

Every entry under a deliverable's `**Affected files:**` list must carry an explicit trailing parenthesized intent marker from a closed 4-value enum:

[cols="1,2,3"]
|===
|Intent Marker |Syntax Example |Pre-Execution `files_exist` Gate Semantics

|`read`
|``- `src/main/java/Foo.java` (read)``
|Consulted as read-only reference; file **must exist** on disk prior to execution. Recorded in `references.json` under read-only references, disjoint from expected modifications.

|`write-new`
|``- `src/main/java/Bar.java` (write-new)``
|Created fresh by the deliverable; file **must not exist** on disk prior to execution (flags a Q-Gate finding if already present).

|`write-replace`
|``- `src/main/java/Baz.java` (write-replace)``
|Modified in place; file exists on disk and is recorded in the declared modification footprint.

|`delete`
|``- `src/main/java/Old.java` (delete)``
|Removed by the deliverable; file **must exist** on disk prior to execution and triggers the whole-tree verification gate in Phase 5.
|===

Any `Affected files` line lacking a valid `(read|write-new|write-replace|delete)` suffix is rejected immediately with `rejected.reason = "invalid_link_args"`. Furthermore, if a deliverable changes a default value, constant, or enum member, the *value-change test-sweep rule* requires all existing test files asserting the old value (discovered identifier-first) to be listed in `Affected files` with `(write-replace)`.

==== 2. Six-Bucket File-Type Classifier & `module_testing` Profile Requirement

For each deliverable, the server classifies its write-intent `Affected files` via the domain build extensions into one of six closed file-type buckets and validates the deliverable's declared `profiles[]`:

[cols="1,2,3"]
|===
|File-Type Bucket |Path Composition |Mandatory `profiles[]` Assignment

|`production_only`
|Production source files only
|`[implementation, module_testing]` — `module_testing` is **mandatory**.

|`test_only`
|Test source files only
|`[module_testing]` only.

|`mixed_code`
|Production and test source files (no docs)
|`[implementation, module_testing]` — `module_testing` is **mandatory**.

|`mixed_with_docs`
|Production/test source files plus documentation files
|`[implementation, module_testing]`, with `module_testing` scoped strictly to the code/test paths.

|`documentation_only`
|Documentation or markdown files only
|`[implementation]` only — `module_testing` is **prohibited**.

|`unknown`
|Unclaimed file extension or path
|*Blocks Deliverable*: Emits a blocking finding requiring path correction or build-extension mapping; never silently falls back to `documentation_only`.
|===

==== 3. Single Domain Narrowing Pass

Immediately after `outline.md` passes structural validation, the server re-derives the plan's active domain set from the union of all deliverables' declared footprints (`Affected files`) and narrows `references.domains` **exactly once**. This removes any temporary over-provisioned domains introduced during Phase 2's widen-only union before Phase 4 resolves task skills.

==== 4. Persisted `outline.review` State (Surviving `/clear`)

Once the outline and its Q-Gate pass complete, the engine transitions to `outline.review` *while remaining in `phase-3-outline`* (never marking Phase 3 `done` prior to approval). Because `outline.review` is persisted in `mcp/status.json`:

* A session compaction or `/clear` resumes directly at `outline.review` via `pm_state(plan_id)`.
* Unless `plan_without_asking == true` is configured in `.plan/marshal.json`, advancing from `outline.review` to `phase-4-plan` is an *operator-authorizing decision* requiring MCP elicitation or `pm-mcp operator approve-outline`.
* If the operator requests changes during `outline.review`, the operator's feedback is persisted as pending Q-Gate findings (`phase = 3-outline`) and the state transitions back to `outline.deep` / `outline.light` to revise the outline.

=== Phase 4 (`plan`): Task Derivation, DAG Validation & Manifest Resolver

Phase 4 transforms the approved structured deliverables in `outline.md` into executable `TASK-NNN.json` files, dispatch envelopes, and the per-plan execution manifest (`execution-manifest.json`).

==== Deterministic Task Derivation & DAG Cycle Detection

1. *Profile-to-Task Mapping*: For each deliverable $D_i$ in `outline.md`, the engine generates one task per declared profile in fixed intra-deliverable order (`implementation` $\rightarrow$ `module_testing` $\rightarrow$ `verification`), copying the deliverable's `Intent gloss` verbatim into each derived task's description.
2. *Dependency DAG Construction & Cycle Rejection*: Inter-deliverable `depends:` declarations map the head task of $D_i$ to the tail task of each prerequisite deliverable $D_j$. `TaskGraphValidator` runs Kahn's topological sort and depth-first cycle detection over the complete task graph; any self-dependency, unresolved deliverable reference, or cycle (`TASK-A -> ... -> TASK-A`) fails validation before any task file is written.
3. *Two-Tier Skill Resolution*: Each task is assigned `skills[]` (`skill://pm/...` URIs) by combining system persona skills (`skill://pm/core`, profile vocabulary skill) with domain-resolved skills for the deliverable's `(domain, module, profile)` tuple.
4. *Atomic Non-Idempotent Task Creation*: All derived tasks are persisted in a single atomic batch (`batch-add`). Task creation is strictly non-idempotent: once `tasks/TASK-*.json` files exist for the plan, the engine omits the task-creation link on any re-entry into Phase 4, preventing duplicate task generation.
5. *Server-Side Cost Sizing, Envelope Bin-Packing & Manifest Composition*: Upon `plan.describe-tasks` submission, the server automatically executes three deterministic passes in-process (without exposing separate LLM-driven `pack-envelopes` or `compose-manifest` states):
** `TaskCostEstimator` computes `cost_size` (`small | medium | large`) and `predicted_cost_tokens` for each task from its step count, target file count, and profile.
** `EnvelopePacker` groups topologically ordered tasks into context-budget-bounded dispatch envelopes (`envelope-1..M`) and stamps `envelope_id` on each `TASK-NNN.json` so related tasks (such as a deliverable's `implementation` and `module_testing` pair) share one leaf sub-agent context window without exceeding host token limits.
** `ExecutionManifestResolver` writes `execution-manifest.json` (including structured `phase_6.dropped_steps: [{step_id, gate, reason}]` for every pruned step).

==== Shared Execution Manifest & Posture Preview Resolver

Both the Phase 1/Phase 4 *posture preview* and the Phase 4 *execution manifest composition* (`execution-manifest.json`) invoke the same deterministic `ExecutionManifestResolver`:

* *Posture Lattice*: `minimal` $\sqsubset$ `standard` $\sqsubset$ `full`.
* *Floor Immunity*: Core and derived-state workflow steps (`push`, `branch-cleanup`, `record-metrics`, `emit-landing`, `archive-plan`, and mandatory freshness/quality gates) carry floor immunity: an operator or config override setting a floor-immune step to `off` is ignored and recorded as a diagnostic note in `facts`.
* *Prune Predicates & Structured `dropped_steps`*: Conditional steps (such as `sonar-roundtrip`, `automatic-review`, `adr-propose`, or `architecture-refresh`) evaluate their provider availability and footprint prune predicates; an unresolved `ask` seed is dropped only when its backing provider is unconfigured, and every pruned step is recorded in `execution-manifest.json -> phase_6.dropped_steps` with its `gate` (`posture`, `provider_unconfigured`, `footprint_disjoint`, `change_type_exempt`, or `recipe_override`) and human-readable `reason`.

=== Planning Transition Guards & Real-World Invariants

Every phase transition out of Phases 1, 2, 3, and 4 executes a deterministic server-side guard pipeline replacing the legacy `phase_handshake.py` script:

[cols="2,1,4"]
|===
|Guard / Invariant |Scope |Enforcement Rule

|*Artifact Gate*
|Exits from Phases 2, 3, 4
|Refuses transition unless the phase's mandatory artifacts exist and pass schema validation: Exit Phase 2 requires `request.md` containing `## Clarified Request` and non-empty `status.metadata.pr_title`; Exit Phase 3 requires `outline.md` passing `OutlineValidator` and `outline.review` approved; Exit Phase 4 requires $\ge 1$ `tasks/TASK-*.json`, an acyclic DAG, and a composed `execution-manifest.json`. Bypassing the artifact gate (`--allow-bare-transition`) is restricted exclusively to the operator channel with a mandatory audit reason.

|All planning transitions
|If `.plan/marshal.json` is dirty in the working tree during a planning phase, the server **never** silently discards or commits it. The plan transitions to `<phase>.blocked` and prompts the operator via elicitation/CLI to either commit the config change or restore the file.

|*Store Integrity & Digest Guard*
|Every `pm_state` / `pm_do` read
|Every server write to `.plan/` stores (`status.json`, `references.json`, `findings.jsonl`, `TASK-*.json`) records a SHA-256 content digest. If the model edits files under `.plan/` directly via host file tools, the digest mismatch is detected on the next MCP call and rejected with `store_tampered`.

|*Blocking Findings Guard* (`pending_findings_blocking_count == 0`)
|Exits from Phases 2, 3, 4, 5
|Refuses phase exit while any Q-Gate or verification finding with `blocking == true` remains in `resolution == "pending"`.

=== Direct In-Band Text Submissions & Retired Scratch-File Patterns (`PM-WF-2`, `PM-WF-6`)

=== Q-Gate Validation Loop

Quality Gate (`Q-Gate`) validation runs at the tail of Phases 2, 3, and 4 to catch structural defects (narrative-vs-code drift, missing consumer sweeps, invalid CLI flags, tier deltas, architecture mismatches, and unresolved lesson citations) before advancing to the next phase.

==== Modes, Iteration Ceiling & Content-Hash Rerun Gate

[cols="1,3"]
|===
|Parameter / Rule |Normative Specification

|*Configuration Modes* (`q_gate_validation`)
|Configured per phase in `.plan/marshal.json`: `off` skips Q-Gate validation completely; `once` (default) runs one validation pass and one remediation pass if blocking findings are emitted; `until_clean` iterates validation and remediation until `pending_findings_blocking_count == 0` or the iteration ceiling is reached.

|*Iteration Ceiling* (`max_qgate_iterations = 3`)
|The Q-Gate auto-loop runs **at most 3 iterations** per phase (`qgate_iteration` persisted in `mcp/status.json`, range `0..3`).

|*Content-Hash Rerun Gate*
|Before running Q-Gate validators on iteration $k$, the engine computes `sha256(target_artifact)` (`request.md` in Phase 2, `outline.md` in Phase 3, `TASK-*.json` bundle in Phase 4) and compares it to `status.qgate_last_evaluated_hash`. If the hash is identical and `pending_findings_blocking_count == 0`, the engine short-circuits and exits the Q-Gate loop immediately without re-running validators.

|*Surgical Bypass Predicate*
|In Phase 3 (`outline`), when `q_gate_validation != off`, Q-Gate validation is automatically bypassed (logging `(phase-3-outline:qgate-bypass)` to the audit log) if and only if all three conditions hold: `scope_estimate == "surgical"`, `change_type` $\in \{\text{"bug\_fix"}, \text{"tech\_debt"}, \text{"verification"}\}$, and `deliverable_count == 1`.

|*Exit & Exhaustion Semantics*
|The loop exits to the next state (`refine.ready`, `outline.review`, or `execute.worktree-init`) as soon as `pending_findings_blocking_count == 0`. (In Phase 2 lesson-derived plans, `stale` narrative-vs-code findings are non-blocking signals preserved for Phase 3 confirmation, whereas `invalid` findings are blocking.) If `pending_findings_blocking_count > 0` after iteration 3, the plan transitions to `<phase>.qgate-exhausted` (`*.awaiting_user`), requiring the user/operator to override, edit, or abort.
|===

=== Single-Writer `change_type` Contract

`change_type` classifies the intent of a plan and its deliverables using a closed 6-value enumeration orthogonal to `domain` and `profile`:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.classification;

public enum ChangeType {
    FEATURE("feature", 1),
    BUG_FIX("bug_fix", 2),
    TECH_DEBT("tech_debt", 3),
    ENHANCEMENT("enhancement", 4),
    VERIFICATION("verification", 5),
    ANALYSIS("analysis", 6);

    private final String wireName;
    private final int priorityOrder;

    ChangeType(String wireName, int priorityOrder) {
        this.wireName = wireName;
        this.priorityOrder = priorityOrder;
    }

    public String wireName() { return wireName; }
    public int priorityOrder() { return priorityOrder; }
}
----

==== Single-Writer Heuristic vs Judgment Fallback

To prevent conflicting writes between deterministic heuristics and model judgment, `status.metadata.change_type` enforces a strict *single-writer* protocol at the start of Phase 3 (`outline.detect-change-type`):

1. *Deterministic Heuristic First (`ChangeTypeHeuristic`)*: Scores `clarified_request` (falling back to `original_input`) against fixed keyword tables, applying compound-intent guards and `bug_fix`-vs-`tech_debt` object disambiguation. If a single `ChangeType` wins with $\text{confidence} \ge 0.70$ and no top-two score tie, `ChangeTypeHeuristic` persists `status.metadata.change_type` and advances directly to lane routing (`ambiguous = false`). If no keyword fires, the top two scores tie, or $\text{confidence} < 0.70$, `ChangeTypeHeuristic` returns `ambiguous = true` and **writes nothing** to `status.json`.
2. *Judgment Fallback (`submit`)*: Only when `ambiguous == true` does the engine enter `outline.classify-change-type`, offering a `submit` link (`change_type:enum[feature|bug_fix|tech_debt|enhancement|verification|analysis],rationale:text[1..500]`) guided by `skill://pm/outline/detect-change-type/SKILL.md`. The submitted value becomes the single authoritative write to `status.metadata.change_type`.

==== Plan-vs-Deliverable Scope Reconciliation & Classification Validation

* *Scope Disagreement Refusal*: Every deliverable in `outline.md` declares its own deliverable-scoped `change_type`, while `status.metadata.change_type` holds the plan-scoped classification. `OutlineValidator` and `ExecutionManifestResolver` reconcile the two scopes and **refuse** incompatible combinations: a deliverable with `change_type: verification` or `analysis` is read-only by definition; if any of its `Affected files` carries a mutating intent (`write-new`, `write-replace`, `delete`), or if a plan classified as `verification`/`analysis` contains mutating deliverables, validation fails closed with `change_type_scope_disagreement`.
* *Flag-Not-Block Classification Validation*: When `scope_estimate` is updated in Phase 2 or Phase 3, `classification-validate` checks for narrow-over-large mismatches (for example, `change_type == bug_fix` paired with `scope_estimate == broad`). Mismatches emit an advisory warning fact in `facts.classification_warning` but never block a transition.

=== Scope-Deviation Contract

When an executing leaf sub-agent in Phase 5 (`execute`) discovers that completing a task requires modifying files outside the deliverable's declared `Affected files` or violating a declared architectural constraint, it must never silently widen its footprint or soften the deliverable requirements.

==== Deviation Submission & Batching Mechanics

|Disposition |Required Operator Input |Deterministic Server Side Effects

|`hold`

==== Task Envelope Execution & Independent Server Verification

1. *Envelope Dispatch*: `execute.dispatch-ready` offers `dispatch:envelope-M` (`form: dispatch`) paired with `returned:<dispatch_id>` (`form: submit`). The dispatched sub-agent calls `pm_state(plan_id, entity="envelope-M", dispatch_id)` and receives only the current active task (`TASK-NNN`) and its resolved `skill://pm/...` URIs.
2. *Independent Verification on `submit:TASK-NNN`*: The server never trusts a sub-agent's self-reported completion. When `submit:TASK-NNN` is invoked, the daemon independently verifies: (a) *Non-Empty Diff & Footprint Check* — for write-intent tasks, verifies that `git status --porcelain` in the worktree contains changes, that no files outside the worktree were touched, and that modified paths match the deliverable's declared `Affected files` (`verify_failure_scope` / scope-creep check), forbidding batched destructive `git checkout` commands; (b) *Obfuscation & Marker Check* — scans modified lines for prohibited suppression comments, `TODO`/`FIXME` markers, or rewrite markers; and (c) *Independent Command Re-Run* — executes the task's declared verification command via the daemon's build runner and verifies a passing verdict artifact.
3. *Context Budget Yield & Infeasibility*: If a sub-agent approaches its context window limit before finishing all tasks in `envelope-M`, it invokes `yield:envelope-M` (`budget_yield`) and the server splits the remaining unstarted tasks of `envelope-M` into a new envelope `envelope-(M+1)` with a fresh `dispatch_id`. If a task is genuinely impossible as specified, the sub-agent submits `infeasible:TASK-NNN` with evidence; `infeasible` is terminal for that deliverable and transitions the plan to `execute.blocked` (operator escalation), and substituting a weaker deliverable under the same name is strictly prohibited.

=== Per-Deliverable Chain-Tail Commit & Module Build (`git.commit_and_push`)

Individual tasks never run `git commit`. When the last task belonging to deliverable $D_i$ (the *chain tail*) passes independent verification:

1. *Chain-Tail Commit via `call git.commit_and_push`*: The server transitions to `execute.chain-tail-commit`, which invokes the reusable compound sub-workflow `call git.commit_and_push (message_mode=auto_deliverable, push_mode=never)` (`PM-WF-16`, see link:workflow-dsl.adoc[Workflow DSL Specification]). The sub-workflow cleans untracked build/temp artifacts against `artifact-patterns.json` (respecting `.gitignore` and excluding `.plan/**`), formats the conventional commit message (`feat(<module>): complete deliverable <N> - <title>`) with the configured `Co-Authored-By` trailer, streams the message over `stdin` to `git -C <worktree> commit -F -`, and appends a `kind = "change"` entry to `change-ledger.jsonl` stamped with the new `commit_sha` and git-sourced `changed_paths`.
2. *Per-Deliverable Module Build*: Immediately after `git.commit_and_push` returns `committed_local` (or `clean` for read-only deliverables), the server spawns a module-scoped build job (`canonical = "module-tests"`, scoped to $D_i$'s module) and records a `kind = "build"` entry in `change-ledger.jsonl`. If the module build passes, the envelope advances to the next deliverable's tasks (or completes the envelope); if the module build fails, the envelope transitions immediately to `execute.verification-feedback` (`triage_required`).

=== Whole-Tree Verification Gates & `triage_required` Routing

Once all task envelopes reach completion, `execute.verify-sweep` runs the end-of-phase verification pipeline declared in `manifest.phase_5.verification_steps` (ordered by the `ext-point-build-verify-step` descriptors: `module-tests`, `quality-gate`, `coverage`, and domain `arch-gate`):

* *Footprint-Driven Scope & Relocation Override*: The server compares the realized git footprint (`references.json:realized_footprint`) against project modules to scope build executions. However, if any deliverable in the plan performed a **file relocation or deletion** (any `Affected files` entry with `delete` intent or a git rename `R`), the server unconditionally forces a **whole-tree build and verification sweep** across all modules to catch broken cross-module imports or references.
* *`triage_required` -> Verification-Feedback Transition*: Whenever any per-deliverable module build or end-of-phase verification step fails, the engine ingests the parsed build/test/arch-gate failures into `findings.jsonl`, sets the phase sub-state to `execute.verification-feedback` (`triage_required`), and offers a `dispatch:verify-feedback` link (or inline `fix` links) that diagnoses the root cause against `verify_failure_scope`, applies the fix, commits via `call git.commit_and_push (message_mode=interactive, push_mode=never)`, and re-enters `execute.verify-sweep`.

=== Phase 5 Exit Barrier: Dual Freshness & Pending-Tasks Gates

Transitioning from `phase-5-execute` to `phase-6-finalize` is governed by an atomic dual-gate barrier in `execute.exit-barrier`. **Both gates are always evaluated together before acting on either** so a single diagnostics payload surfaces all reasons if both fail:

1. *Pending-Tasks & Clean-Tree Gate*: Every `tasks/TASK-*.json` record in the plan must have `status == "completed"` (`pending_count == 0`, `in_progress_count == 0`, `blocked_count == 0`), and the worktree must have zero uncommitted modifications (`git status --porcelain` is empty).
2. *Worktree Freshness Gate (`worktree_sha`)*: Freshness is keyed strictly on `worktree_sha` — the composite SHA-256 digest of `HEAD` commit SHA plus staged index, unstaged working-tree diff, and untracked file paths/contents — never on `HEAD` commit SHA alone (which would misclassify an unbuilt dirty tree as fresh). The gate queries the change ledger (`change-ledger.jsonl`) and reads the explicit closed-enum `status` member (`fresh`, `exempt`, `stale`, `undecidable`), never inferring freshness from a process exit code or from `"not stale"`: `fresh` requires that every required build notation for the realized footprint has a passing `kind = "build"` ledger entry whose recorded `worktree_sha` equals the current live `worktree_sha` and every ledger row matches a registered build notation of the project; `exempt` applies when the realized footprint touches exclusively non-buildable documentation/markdown paths (`documentation_only` across the entire plan), verified against the build extension path classifiers; `stale` / `undecidable` fails the barrier with an explicit `stale_reason` (`tree_modified_since_build`, `missing_module_build`, `unrecognized_build_notation`, or `ledger_unreadable`), routing back to `execute.verify-sweep`.

=== Finalize Commit Instrumentation, Freshness Reconcile & Post-PR Re-Push (`PM-WF-16`)

Whenever any Phase 6 step declaring `mutatesSource == true` (`order < 70`) completes, the finalize engine routes through `finalize.settle-commit`, which invokes `call git.commit_and_push (message_mode=step_or_fallback, push_mode=post_pr_conditional)` (see link:workflow-dsl.adoc[Workflow DSL Specification]):

1. *Conditional Auto-Commit & Ledger Recording*: If `git status --porcelain` in the worktree is clean, `git.commit_and_push` returns `clean` immediately and the finalize pipeline advances to the next step. If uncommitted modifications exist, `git.commit_and_push` runs `.gitignore`-aware artifact cleanup, resolves the step's commit message (or deterministic fallback `chore(finalize): apply <step_id> changes`) with the `Co-Authored-By` trailer, pipes the message via `stdin` to `git -C <worktree> commit -F -`, and appends a `kind = "change"` entry (`commit_sha`, `changed_paths`, `worktree_sha`) to `change-ledger.jsonl`.
2. *`head_at_completion` Re-Stamping*: If the completed `mutatesSource == true` step also declares `headDependent == true` (such as `simplify`, `security-audit`, `self-review`, `architecture-refresh`, `adr-propose`), `git.commit_and_push` atomically updates that step's persisted `head_at_completion` in `mcp/status.json` to the newly created `commit_sha` without emitting a duplicate step completion event. This prevents the step's own commit from self-invalidating its verdict on a subsequent re-entry check.
3. *`freshness_reconcile` for Steps at `order >= 10`*: If a `mutatesSource == true` step at `order >= 10` (`PRE_PUSH_QUALITY_GATE_ORDER`) produces a commit, `git.commit_and_push` records a `freshness_reconcile` entry in `mcp/status.json` containing `(commit_sha, step_id, prior_build_worktree_sha)` where `prior_build_worktree_sha` is read from the latest `status == "succeeded"` build entry in `change-ledger.jsonl`. When the `git.pre-commit-verify-freshness` gate runs before pushing, it consults `freshness_reconcile` so a known non-build-affecting finalize commit (such as an ADR addition in `adr-propose`) is recognized as reconciled, whereas any modification to buildable source paths invalidates `pre-push-quality-gate` and re-runs the Settle quality gate first.
4. *Post-PR Conditional Re-Push (`order > 20`)*: When `finalize.settle-commit` is triggered by a step with `order > 20` (after `default:create-pr`, such as `default:adr-propose` at `62` or an in-branch `finalize.triage` fix) and `.plan/marshal.json -> /phase-5-execute/commit_and_push == true`, `push_mode=post_pr_conditional` evaluates `push_required`, verifies freshness and `branch-sync-state` parity, pushes the new commit to `origin/<branch>`, and returns `committed_and_pushed -> finalize.concurrent-wait` so CI and review bots re-evaluate the updated PR `HEAD`.

=== Java `FinalizeStepDescriptor` Record Schema & Static Checks

Every built-in, bundle, or project-local finalize step is represented in `pm-mcp-core` by an immutable `FinalizeStepDescriptor` record capturing all step descriptor facts:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.finalize;

import java.util.List;
import java.util.Set;

public record FinalizeStepDescriptor(
    String name,
    int order,
    boolean defaultOn,
    Set<String> presets,
    String description,
    boolean mutatesSource,
    boolean headDependent,
    List<String> verdictInputs,
    boolean advancesMainViaRebase,
    boolean postRunReview,
    List<String> reads,
    List<String> destroys,
    List<String> recordsFacts
) {
    public static final int PUSH_ORDER = 11;
    public static final int PRE_PUSH_QUALITY_GATE_ORDER = 10;
    public static final int MERGE_GATE_ORDER = 70;
    public static final int POST_RUN_MIN_ORDER = 900;
    public static final int TERMINUS_ARCHIVE_ORDER = 1100;
}
----

==== Build-Time & Startup Static Invariant Verification (`FinalizePipelineValidator`)

`FinalizePipelineValidator` validates the complete registered `List<FinalizeStepDescriptor>` at build time (via JUnit tests) and at daemon startup, failing closed on any violation:

1. *Order Uniqueness (No Collisions)*: For all distinct descriptors $A \neq B$, $A.\text{order}() \neq B.\text{order}()$. Tie-breaking by list insertion order is strictly forbidden.
2. *Pre-Push Quality Gate Placement*: `default:pre-push-quality-gate` must have $\text{order} == 10$, `default:push` must have $\text{order} == 11$, and no step may occupy an order between them.
3. *Source-Mutation Before Merge Gate (`mutatesSource`)*: Every descriptor with `mutatesSource == true` must satisfy $\text{order} < \text{branchCleanup.order}()$ (`70`). Every step with $\text{order} \ge 70$ must explicitly declare `mutatesSource == false` (supported at runtime by the post-run source guard, which checks `git status --porcelain` after every post-merge step to detect stray tracked writes).
4. *Post-Run Review & Source-Mutation Mutual Exclusion (`P1 \land P2`)*: No descriptor may declare both `postRunReview == true` and `mutatesSource == true`. Every descriptor with `postRunReview == true` must satisfy $900 \le \text{order} < 1000$.
5. *`reads` / `destroys` Data-Dependency Ordering*: For every artifact token $X \in A.\text{reads}()$ and any step $D$ with $X \in D.\text{destroys}()$, $A.\text{order}() < D.\text{order}()$ (no read-after-destroy: e.g., all `reads: [worktree]` steps precede `branch-cleanup` at `70`; all steps precede `archive-plan` at `1100` which `destroys: [plan-directory]`). For `X == "metrics"`, every consumer declaring `reads: [metrics]` (`emit-landing` at `1000`) must satisfy $\text{order} > \text{recordMetrics.order}()$ (`998`).
6. *Anchor & Fact Contract Completeness*: `verdictInputs` may be non-empty only when `headDependent == true` (remote-state steps `ci-verify`, `automatic-review`, `sonar-roundtrip` and open-ended repository steps must have `verdictInputs.isEmpty() == true`); and every step whose `done` outcome is reachable through a no-op/skipped branch as well as a work-performing branch must include `"work_performed"` in `recordsFacts` and emit `work_performed=true|false`.

=== Re-Entry & `head_at_completion` Verdict Currency Rules

When Phase 6 re-enters after a loop-back from Phase 5, an in-branch settle commit, a `sync-baseline` rebase, or a session resume, the engine decides for each step whether to `SKIP` (preserving its prior `done` verdict) or `RE_FIRE`.

==== Fail-Closed `head_at_completion` Anchor Obligation

* Every step with `headDependent == true` must record `head_at_completion: "<40-hex-sha>"` in `mcp/status.json` when transitioning to `done`.
* Any attempt to record `done` for a `headDependent == true` step without a valid `head_at_completion` SHA is **refused** (`error: "missing_head_at_completion"`).
* On re-entry, if a step's persisted record lacks `head_at_completion`, the engine reports the prior record as `unverified` and unconditionally re-fires the step.

==== Deterministic Verdict Currency Algorithm (`VerdictCurrencyEvaluator`)

For a `headDependent == true` step $S$ with recorded `head_at_completion` $= H_{\text{rec}}$ and current worktree `HEAD` $= H_{\text{cur}}$:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.finalize;

import java.util.List;
import java.util.Set;

public enum CurrencyVerdict {
    CURRENT_SAME_HEAD,
    PRESERVED_INPUTS_UNAFFECTED,
    STALE_MISSING_ANCHOR,
    STALE_REBASE_ADVANCED,
    STALE_UNSCOPED_HEAD_CHANGE,
    STALE_INPUTS_MODIFIED
}

public final class VerdictCurrencyEvaluator {

    public CurrencyVerdict evaluate(
            FinalizeStepDescriptor step,
            String recordedHeadSha,
            String currentHeadSha,
            boolean rebaseReplayedCommits,
            Set<String> changedRepoRelativePaths) {

        if (recordedHeadSha == null || recordedHeadSha.isBlank()) {
            return CurrencyVerdict.STALE_MISSING_ANCHOR;
        }
        if (recordedHeadSha.equals(currentHeadSha) && !rebaseReplayedCommits) {
            return CurrencyVerdict.CURRENT_SAME_HEAD;
        }
        if (rebaseReplayedCommits) {
            // A non-noop rebase (action == "rebased", upstream_commit_count > 0)
            // replays history onto a new base tip and re-stales all head-dependent verdicts.
            return CurrencyVerdict.STALE_REBASE_ADVANCED;
        }
        List<String> globs = step.verdictInputs();
        if (globs == null || globs.isEmpty()) {
            // Fail-closed default: absence of verdict_inputs never means "matches nothing".
            return CurrencyVerdict.STALE_UNSCOPED_HEAD_CHANGE;
        }
        boolean anyInputTouched = changedRepoRelativePaths.stream()
            .anyMatch(path -> matchesAnyFnmatchGlob(path, globs));
        return anyInputTouched
            ? CurrencyVerdict.STALE_INPUTS_MODIFIED
            : CurrencyVerdict.PRESERVED_INPUTS_UNAFFECTED;
    }
}
----

* *No Re-Stamp on Preserve Invariant*: When `VerdictCurrencyEvaluator` returns `PRESERVED_INPUTS_UNAFFECTED` (because `git diff --name-only <H_rec>..<H_cur>` touched zero paths matching `step.verdictInputs()`), the step is skipped and its persisted `head_at_completion` **remains $H_{\text{rec}}$** — it is **never** overwritten with $H_{\text{cur}}$. Keeping $H_{\text{rec}}$ ensures that subsequent commits are always diffed against the cumulative range since the step actually executed.
* *Rebase vs No-Op Rebase*: A step declaring `advancesMainViaRebase == true` (`sync-baseline`, `branch-cleanup`) invalidates downstream verdicts (`STALE_REBASE_ADVANCED`) **only** when it actually replayed commits (`action == "rebased"` and `upstream_commit_count > 0`). When the branch was already up-to-date (`work_performed == false`), `HEAD` does not change and existing verdicts remain current.

=== Pre-Merge Review Barrier & Operator Merge Authorization Grants

Inside `default:branch-cleanup` (`order = 70`), immediately before executing the merge command (`pr safe-merge` or `merge-queue` enqueue), the engine enforces the fail-closed **Pre-Merge Review Barrier**.

==== Two Fail-Closed Barrier Predicates

Both predicates must evaluate to `true` against the current worktree `HEAD` SHA ($H_{\text{cur}}$):

1. *Predicate 1 — Zero Unhandled Review Comments*: Every finding in `findings.jsonl` originating from `automatic-review`, `ci-verify`, or `sonar-roundtrip` must have a persisted, terminal triage disposition (`FIX`, `SUPPRESS`, or `ACCEPT`) whose outbound response or dismissal has been transmitted to the provider (`response_transmitted == true`).
2. *Predicate 2 — Required-Bot Participation on Current `HEAD`*: Every review bot configured as required in the project's review-bot registry must have a verified participation record for $H_{\text{cur}}$ with `completion_state == "completed"`. An `unknown`, `pending`, `rate_limited`, `timed_out`, or `not_triggered` bot state **never** satisfies Predicate 2 and **never** automatically mints a merge grant.

==== Operator Merge Authorization Record (`MergeAuthorizationRecord`)

When either barrier predicate fails (or when coverage-gap or red-CI overrides are requested), the plan cannot merge unless an admissible `MergeAuthorizationRecord` exists in `mcp/status.json`.

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.finalize;

import java.time.Instant;

public enum MergeGapClass {
    UNHANDLED_COMMENTS("unhandled_comments"),
    BOT_TIMED_OUT("bot_timed_out"),
    BOT_RATE_LIMITED("bot_rate_limited"),
    BOT_NOT_TRIGGERED("bot_not_triggered"),
    RED_CI_OVERRIDE("red_ci_override"),
    COVERAGE_GAP("coverage_gap");

    private final String wireName;
    MergeGapClass(String wireName) { this.wireName = wireName; }
    public String wireName() { return wireName; }
}

public record MergeAuthorizationRecord(
    String grantId,
    String planId,
    String headSha,
    MergeGapClass gapClass,
    String operatorChannel,
    String operatorRationale,
    Instant grantedAt
) {
    public boolean isAdmissibleFor(String currentHeadSha, MergeGapClass activeGapClass) {
        return this.headSha != null
            && this.headSha.equals(currentHeadSha)
            && this.gapClass == activeGapClass;
    }
}
----

* *Operator-Only Minting*: Grants are minted exclusively through the authenticated operator channel (MCP elicitation or `pm-mcp operator authorize-merge --plan <plan_id> --head <sha> --gap-class <class> --rationale <text>`). Free-text lines in `decision.log` are never accepted as authorization evidence.
* *Route on `admissible`, Never on Boolean `authorized`*: The barrier checks `grant.isAdmissibleFor(currentHeadSha, activeGapClass)`. A grant minted for an earlier commit $H_1$ or for `BOT_RATE_LIMITED` is inadmissible if `HEAD` advances to $H_2$ (e.g., after rebase) or if the active failure is `UNHANDLED_COMMENTS`.

=== Cross-Plan Merge Mutex, FIFO Admission Queue & Epic Plan Emission
_See Requirement link:../Requirements.adoc#PM-WF-15[PM-WF-15: Epic Plan Emission & Cross-Plan Merge Mutex]_

==== Cross-Plan Merge Mutex & FIFO Admission Queue

When multiple plans execute concurrently across worktrees of the same repository, `default:branch-cleanup` (`order = 70`) serializes their rebase-and-merge critical sections through the **Cross-Plan Merge Mutex** (`MergeMutexManager`), coordinated across `pm-mcp serve` processes via an OS kernel `FileChannel.lock()` on `~/.plan-marshall/mcp/locks/merge.lock` and backed on disk by `~/.plan-marshall/mcp/state/merge-queue.json` (while cross-plan review-bot rate-window claims are coordinated separately via `~/.plan-marshall/mcp/locks/review-bot.lock` and `~/.plan-marshall/mcp/state/review-bot-windows.json`):

[source,text]
----
Plan A (branch-cleanup) ──► [Enqueue FIFO] ──► [Acquire Holder Slot]
                                                      │
                        ┌─────────────────────────────┴─────────────────────────────┐
                        │ Widened Critical Section:                                 │
                        │  1. git fetch + rebase onto base (worktree-rebase-to)     │
                        │  2. Post-rebase CI / re-review check                      │
                        │     └─► If async wait required: RELEASE slot & keep FIFO  │
                        │  3. Pre-merge barrier check (last gate before merge)      │
                        │  4. Closed merge dispatch (safe-merge | merge-queue)      │
                        └─────────────────────────────┬─────────────────────────────┘
                                                      ▼
                                            [Release Mutex & Pop]
----

1. *FIFO Admission Queue*: Plans requesting the merge mutex enter an ordered per-repository FIFO `waiting[]` (aliased as `admission_queue[]`) keyed by `plan_id`, `owner_pid`, and `enqueued_at`. A plan may acquire the active `holder` slot only when it is at the head of the FIFO queue and `holder == null`.
2. *Widened Hold across Rebase-to-Merge*: Unlike a narrow lock around `gh pr merge`, the merge mutex is acquired **before** `branch-cleanup` rebases the feature branch onto `main` and held through the merge execution so a sibling plan cannot land a conflicting commit on `main` between rebase and merge.
3. *Mandatory Release on Every Wait & Abort*: A plan must **never** hold the merge mutex while blocked in an asynchronous wait (`wait:finalize.concurrent-wait` for post-rebase CI, review-bot rate-window wait, merge-queue landing wait, or operator elicitation/escalation) or on abort. Entering any `wait` or `escalate` state inside `branch-cleanup` atomically releases `holder = null` while preserving the plan's FIFO queue position, allowing ready sibling plans to merge without head-of-line blocking.
4. *Atomic Stale-Holder & Budget Reclaim*: Reaping runs inside the same atomic `FileChannel.lock()` transaction as admission. An active `holder` is forcibly reclaimed if and only if it is provably stale — either its owning `pm-mcp serve` process is no longer alive (`ProcessHandle.of(owner_pid).isPresent() == false` and no active git/CI job for that plan is running), the holding `plan_id` is in a terminal state (`completed`, `aborted`), or the holder's lease budget (`lease_expires_at`, default 15 minutes without a heartbeat transition) has expired.
5. *Closed Merge Dispatch Set*: `branch-cleanup` executes merges exclusively through one of two closed mechanisms: direct `safe-merge` (squash/merge via enrolled CI provider when branch is up-to-date and green) or `merge-queue` enqueue (when repository merge queue is enabled, transitioning to `finalize.merge-queue-wait` after releasing the mutex).

==== Epic Plan Emission (`emit:<plan_id>`)

Orchestrator epics (`scope: epic`) manage multi-plan workstreams stored in `.plan/orchestrator/<epic_id>/` (`status.json` header and per-plan `.plan/orchestrator/<epic_id>/queue/<plan_id>.json` files).

* *Never Dispatch a Plan as a Sub-Agent*: Because sub-agents are single-level leaf workers (`PM-WF-5`) and every plan dispatches its own leaf sub-agents during Phases 2–6, an epic **never** offers a `dispatch` link to launch a plan and **never** executes a plan inline.
* *Surface Disjointness Gate*: When building the epic representation, the server evaluates expected file-surface disjointness across all currently `launched` and `running` sibling plans. An `indeterminate` surface is treated fail-closed as **not disjoint** (never eligible for parallel emission).
* *`emit:<plan_id>` Transition (`rel: emit`)*: For each staged plan whose dependencies are `completed` and whose surface is disjoint from active plans, the epic state offers `emit:<plan_id>`. Following `emit:<plan_id>`:
** Updates `.plan/orchestrator/<epic_id>/queue/<plan_id>.json` atomically (`status = "launched"`) under the epic lock.
** Returns the exact operator bootstrap command (`pm-mcp enter --client <client> --plan <plan_id>`) in `facts.launch_command`. Note that `auto_emit` only pre-selects the emission candidate; it never spawns a background plan session automatically.
** Transitions the epic's view of `<plan_id>` from `launched` to `running` automatically as soon as the operator runs `pm-mcp enter` and the daemon writes `.plan/local/plans/<plan_id>/mcp/entry.json`.
