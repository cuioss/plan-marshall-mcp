== Overview

This document specifies the native STDIO MCP transport (`quarkus-mcp-server-stdio`), `stdout` stream hygiene, cross-process `FileChannel.lock()` coordination, embedded client bundle installer (`pm-mcp client`), entry identity recorder (`pm-mcp enter`), token-lane credential resolution, operator channel isolation (`pm-mcp operator`), and tamper-evident audit logging for the *plan-marshall-mcp* (`PM-MCP`) native binary (`pm-mcp`). Because every supported frontier coding agent (`Claude Code`, `OpenCode`, `Antigravity`, `Codex`) spawns MCP servers directly as child processes over `stdio` and compiling Quarkus to a GraalVM native executable yields `<= 50 ms` cold startup and `<= 64 MB` RSS, `pm-mcp` exposes zero listening network ports and requires no HTTP cookies, `headersHelper` scripts, or background network daemons.

=== Native STDIO Transport Configuration (`quarkus-mcp-server-stdio`)

The `pm-mcp` executable is built exclusively on `io.quarkiverse.mcp:quarkus-mcp-server-stdio` with zero HTTP/SSE/WebSocket server dependencies on the runtime classpath. When launched as `pm-mcp serve` (or with no subcommand when `stdin` is a pipe), the process communicates with its parent coding agent strictly via newline-delimited UTF-8 JSON-RPC 2.0 frames over `stdin` and `stdout`.

[cols="2,2,3"]
|===
|Configuration Property |Normative Value |Enforcement Rule

|`quarkus.mcp.server.stdio.enabled`
|`true`
|Enables the Quarkus STDIO MCP transport in `serve` mode. Disabled automatically when Picocli dispatches a CLI subcommand (`enter`, `client`, `operator`, `status`, `drain`).

|`quarkus.mcp.server.stdio.null-system-out`
|`true`
|Redirects `System.out` to a null output stream immediately after `quarkus-mcp-server-stdio` captures the real `FileDescriptor.out` stream, guaranteeing that stray library writes cannot corrupt the JSON-RPC wire stream on `stdout` (`PM-SEC-4`).

|`quarkus.log.console.stderr`
|`true`
|Routes all `java.util.logging` / `CuiLogger` console output exclusively to `stderr` (`FileDescriptor.err`) in addition to structured file logs under `~/.plan-marshall/mcp/logs/daemon.log`.

|`quarkus.banner.enabled`
|`false`
|Suppresses the Quarkus ASCII startup banner so zero non-JSON-RPC bytes are emitted on startup.

|`pm.mcp.protocol.version`
|`2026-07-28`
|Targets only the current frontier MCP protocol specification (`2026-07-28`); legacy protocol revisions (`2025-11-25`, `2024-11-05`) and draft custom extensions are rejected during `initialize` negotiation (`PM-ARCH-3`, `PM-TECH-1`).
|===

=== Multi-Session File-Lock Coordination & Active Process Registry

Multiple coding agent sessions (across `Claude Code`, `OpenCode`, `Antigravity`, and `Codex`) may spawn concurrent `pm-mcp serve` processes on the same workstation and repository. All state is persisted on disk and coordinated via OS kernel `FileChannel.lock()` locks (`PM-ARCH-1`):

[source,text]
----
~/.plan-marshall/mcp/                        (mode 0700, owned by current UID)
├── locks/
│   ├── merge.lock                           (mode 0600, per-repo FIFO merge barrier lock)
│   ├── review-bot.lock                      (mode 0600, cross-plan review-bot rate-window lock)
│   └── build-slots.lock                     (mode 0600, global build-slot semaphore lock)
├── state/
│   ├── build-slots.json                     (mode 0600, active PID-keyed build leases)
│   ├── merge-queue.json                     (mode 0600, per-repo FIFO merge queues & active holders)
│   ├── review-bot-windows.json              (mode 0600, per-bot cross-plan rate-window claims)
│   ├── install-records.json                 (mode 0600, installed client bundle digests)
│   └── processes/
│       └── <pid>.json                       (mode 0600, active STDIO server process descriptor)
└── logs/
    ├── daemon.log                           (mode 0600, runtime diagnostic log)
    └── audit.jsonl                          (mode 0600, tamper-evident security audit log)
----

==== Startup & Shutdown Sequence (`pm-mcp serve`)

1. *Directory & Permission Verification (`PM-SEC-4`)*: Verify that `~/.plan-marshall/mcp/` exists, is owned by the current OS effective user ID (`geteuid()`), and has POSIX permissions `0700` (`drwx------`). Verify that `~/.plan-marshall/mcp/enrolments.json` and any fallback credential files have mode `0600` (`rw-------`). If group or world permissions are set (`(mode & 0077) != 0`), or ownership differs, log a security fault to `audit.jsonl`, write a diagnostic message to `stderr`, and exit immediately with code `77` (`EX_NOPERM`).
2. *Crash Recovery & Stale Lease Sweep (`PM-ARCH-7`, `PM-ARCH-8`)*: Before processing the first tool call on a workspace, check for any incomplete `.plan/local/move-journal.json` (replaying or rolling back idempotently under the plan lock) and sweep `~/.plan-marshall/mcp/state/processes/*.json`, `build-slots.json`, `merge-queue.json`, and `review-bot-windows.json` using `ProcessHandle.of(pid).isPresent()`, releasing any slots/mutexes or marking any `running` jobs whose owning `pm-mcp` PID is no longer alive as `interrupted_by_restart`.
3. *Process Registration*: Write `~/.plan-marshall/mcp/state/processes/<pid>.json` (mode `0600`) recording `pid`, `started_at`, `version`, `client_info`, and active child job PIDs so `pm-mcp status` and `pm-mcp drain` can inspect and coordinate all live `pm-mcp serve` instances on the machine.
4. *Graceful EOF / Signal Drain (`PM-ARCH-8`)*: When `stdin` reaches `EOF` (host session closed) or `SIGTERM`/`SIGINT` arrives, the `pm-mcp serve` process stops accepting new requests, terminates any active child process groups (`kill(-pgid, SIGTERM)` followed by `SIGKILL` after grace period, or awaits completion when triggered via `pm-mcp drain`), releases held `build-slots.json`, `merge-queue.json`, and `review-bot-windows.json` leases, unlinks `state/processes/<pid>.json`, and exits with code `0`.

== STDIO Transport Isolation, Zero Network Exposure & Stream Hygiene
_See Requirement link:../Requirements.adoc#PM-SEC-4[PM-SEC-4: STDIO Transport Isolation, Zero Network Exposure & Stream Hygiene]_

=== Zero Listening Sockets Invariant

`pm-mcp` never opens a listening TCP, UDP, HTTP, SSE, or WebSocket server socket in any mode. Transport access is inherently confined by the operating system kernel to the parent coding agent process holding the `stdin`/`stdout` anonymous pipe descriptors created via `fork`/`exec`. Network-based attack classes against the MCP server—including DNS rebinding, cross-origin browser `fetch()` requests, port scanning, and cross-UID localhost socket probing—are structurally impossible.

=== `stdout` Wire Hygiene & Subprocess Stream Redirection

Because any non-JSON-RPC byte written to `stdout` breaks the host's MCP framing parser:

1. `quarkus.mcp.server.stdio.null-system-out=true` and `quarkus.log.console.stderr=true` are compiled into the application image and cannot be disabled at runtime.
2. Every child subprocess spawned by `pm-mcp` (`git`, `gh`, `glab`, Maven, Gradle, npm, pytest, Python scripts, and warm LSP servers) is configured with `ProcessBuilder.redirectInput(Redirect.PIPE)` (or `/dev/null` for non-interactive jobs) and dedicated output capture pipes (`Redirect.PIPE` or log file redirect). No child process ever inherits the MCP server's `stdin` (`fd 0`) or `stdout` (`fd 1`).
3. Every outbound JSON-RPC message written to `stdout` is serialized as a single UTF-8 line without embedded `LF` (`\n`) or `CR` (`\r`) characters, terminated by `\n`, and flushed immediately.

[source,text]
----
Coding Agent Host (claude | opencode | antigravity | codex)
  │
  │  fork + exec: pm-mcp serve
  │  fd 0 (stdin)  ───► JSON-RPC 2.0 Requests / Notifications
  │  fd 1 (stdout) ◄─── JSON-RPC 2.0 Responses / Notifications (ONLY)
  │  fd 2 (stderr) ◄─── CuiLogger Diagnostics (never JSON-RPC)
  ▼
pm-mcp Native Process (Java 25 / GraalVM / quarkus-mcp-server-stdio)
  ├── System.out ──────► NullOutputStream (guarded at startup)
  ├── Child Jobs ──────► Isolated ProcessGroup + Dedicated Pipe/File Captures
  └── State Stores ────► Atomic Write-and-Rename under FileChannel.lock()
----

== Direct Binary Bundle Extraction & Client Installer (`pm-mcp client`)
_See Requirement link:../Requirements.adoc#PM-DIST-1[PM-DIST-1: Single Version Authority & Embedded Client Bundles]_

_See Requirement link:../Requirements.adoc#PM-DIST-2[PM-DIST-2: Direct Binary Bundle Extraction & Client Installer]_

_See Requirement link:../Requirements.adoc#PM-DIST-4[PM-DIST-4: Bundle Upgrade Detection & Atomic Reconciliation]_

The `pm-mcp` binary is the single version authority for all client integration bundles. All bundle manifests and templates are compiled directly into the native image under `classpath:/bundles/<client>/` (`claude`, `opencode`, `antigravity`, `codex`).

=== Embedded Classpath Bundle Layout

[cols="2,2,3"]
|===
|Classpath Resource Path |Client IDs |Normative Contract

|`classpath:/bundles/{client}/bundle-manifest.json`
|`claude`, `opencode`, `antigravity`, `codex`
|Contains the normative `ClientBundleManifest` (see link:client-profiles.adoc[Client Profiles Specification]) declaring `bundle_version`, `daemon_version`, `manifest_sha256`, `files[]`, and `shared_configs[]` for `scope=user` and `scope=project`.

|`classpath:/bundles/{client}/files/{bundle_path}`
|`claude`, `opencode`, `antigravity`, `codex`
|Immutable UTF-8 template bytes for every command (`/plan-marshall`, `/plan-orchestrator`, `/marshall-steward` or `$plan-marshall` skills), sub-agent definition (`execution-context-l1..l7`, `inherit`, `reader`), and optional hook referenced in `bundle-manifest.json`.
|===

=== Path Traversal & Integrity Guards During Bundle Extraction

1. Every `bundle_path` and `target_path` in `bundle-manifest.json` is validated against `^(?!/)(?!.*\.\.)[A-Za-z0-9_./-]+$` before touching the filesystem.
2. Target installation paths are resolved against the canonical scope root (`user` home directory or `project` repository root) via `Path.resolve(targetPath).normalize()` and verified with `startsWith(canonicalScopeRoot)` (`PM-SEC-2`).
3. Before writing any extracted file, `pm-mcp client` computes the SHA-256 digest of the classpath resource bytes and verifies that it matches the `sha256` declared in `bundle-manifest.json`.

=== `pm-mcp client` CLI Subcommands (`install`, `update`, `remove`, `status`)

* `pm-mcp client install <claude|opencode|antigravity|codex> [--scope user|project]`:
** Reads `classpath:/bundles/<client>/bundle-manifest.json` directly in-process.
** Computes the diff between the target filesystem and the manifest (`files[]` additions/modifications and surgical `shared_configs[]` key merges for `.mcp.json`, `opencode.json`, `mcp_config.json`, or `.codex/config.toml`).
** Displays the complete planned file and configuration changes on the terminal and requires interactive operator confirmation (unless `--yes` is passed in an interactive CLI session).
** Writes each file atomically (`*.tmp` + `fsync` + `Files.move(..., ATOMIC_MOVE)`) and records the installed `bundle_version`, `daemon_version`, `scope`, and per-file SHA-256 digests in `~/.plan-marshall/mcp/state/install-records.json` under `FileChannel.lock()`.
* `pm-mcp client update [<client>] [--scope user|project]`:
** Compares the running binary's embedded `bundle-manifest.json` against `install-records.json`, detects any user-modified files via SHA-256 comparison (refusing to overwrite modified files without interactive confirmation), removes retired files from prior bundle versions, and atomically applies updates.
* `pm-mcp client remove <client> [--scope user|project]`:
** Removes only the unmodified files and `owned_keys` recorded in `install-records.json`, leaving all user-owned configuration keys and sibling host installations intact.
* `pm-mcp client status`:
** Reports installed bundle versions, binary version parity, and any local file modifications across all scopes.

== Entry Identity Recording (`pm-mcp enter`)
_See Requirement link:../Requirements.adoc#PM-CLIENT-1[PM-CLIENT-1: Advisory Entry Identity Declaration & Persistence]_

_See Requirement link:../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Three-Tier Environment Mismatch Detection & Audit]_

When a user invokes `/plan-marshall`, `/plan-orchestrator`, or `/marshall-steward` (or the corresponding Codex skill), the host's entry command executes:

[source,bash]
----
pm-mcp enter --client <claude|opencode|antigravity|codex|neutral> <plan|epic|steward> [<plan_id>|<epic_id>]
----

1. *Workspace & Enrolment Resolution*: Resolves the canonical git repository root (`workspace_root`) from the current working directory and verifies that the project is enrolled in `~/.plan-marshall/mcp/enrolments.json`.
2. *Three-Tier Environment Detection*: Evaluates the inherited process environment (`CLAUDECODE`, `OPENCODE`, `ANTIGRAVITY_AGENT`, `CODEX_SANDBOX` / `CODEX_CI`) against `--client` (`PM-CLIENT-3`), logging the comparison to `~/.plan-marshall/mcp/logs/audit.jsonl`.
3. *Atomic `entry.json` Persistence*: Acquires the scope's `FileChannel.lock()` and writes `<scope_dir>/mcp/entry.json` (or `.plan/local/mcp/entry.json` prior to `pm_start`) with `format_version: 1`, `client_id`, `workspace_root`, `detected_client`, `environment_match_tier`, `os_principal`, and `entered_at`.
4. *Bundle Drift Notice (`PM-DIST-4`)*: Compares the `bundle_version` recorded in `~/.plan-marshall/mcp/state/install-records.json` against the binary's `daemon_version`; if skewed, emits a `bundle_outdated` warning so the initial `pm_start` / `pm_state` representation prompts `pm-mcp client update <client_id>`.

=== Two-Lane Provider Architecture

External provider integrations are strictly partitioned into two authentication lanes:

1. *CLI Lane (`git`, `gh`, `glab`)*: Executed as verified subprocess jobs (`PM-EXEC-5`) that inherit the developer's existing CLI authentication (`~/.gitconfig`, SSH agent, `gh auth`). `pm-mcp` never reads, extracts, or stores CLI-lane tokens.
2. *Token Lane (SonarQube/SonarCloud, Jira, and authenticated upstream MCP servers)*: Executed directly by `pm-mcp`'s in-process HTTP client (`de.cuioss:cui-http`). Tokens are resolved per request from the credential store hierarchy: `<project>/<provider>` (project-scoped override) -> `<provider>` (global fallback).

=== OS Keyring Backends & Fallback File Store

The `CredentialStore` service resolves secrets using a three-tier backend chain:

* *macOS Keychain (Primary on macOS)*: Invokes macOS Security framework APIs (`SecItemAdd`, `SecItemCopyMatching`, `SecItemUpdate`, `SecItemDelete`) directly via Java 25's Foreign Function & Memory (FFM) API (`java.lang.foreign.Linker`). Items are stored under service name `de.cuioss.plan-marshall-mcp` with account `<provider>` or `<project>/<provider>` and a trusted-application ACL restricting unprompted read access to the signed `pm-mcp` binary.
* *Linux Secret Service (Primary on Linux)*: Communicates with `org.freedesktop.secrets` over the user session D-Bus (`gnome-keyring` / `KWallet`) storing attributes `application=pm-mcp`, `provider=<provider>`, and optional `project=<project>`.
* *Permission-Guarded Fallback File Store*: When no OS keyring is available (headless Linux or WSL2), secrets are stored in `~/.plan-marshall/credentials/<provider>.json` and `~/.plan-marshall/credentials/<project>/<provider>.json` (directory mode `0700`, file mode `0600`, see link:filesystem-layout.adoc[Filesystem Layout Specification] and link:store-schemas.adoc[Store Schemas Specification]). If ownership or permission checks fail, `pm-mcp` refuses to read the file and transitions the calling step to a `credentials_file_insecure` state.

=== Operator-Only Credential CLI & Runtime Secret Redaction

* *Operator CLI Verbs*: Credential mutations and verifications are restricted exclusively to interactive TTY invocations of `pm-mcp operator credentials set|get|list|delete|verify <provider> [--project <slug>]`. `set` reads the secret from the terminal with echo disabled (`System.console().readPassword()`) or `stdin`, never from command-line flags.
* *Zero Model Exposure & Redaction*: No MCP tool, resource, or state representation exposes credential values (`list` and `get` report only metadata: provider name, scope, backend type, and configured status). All resolved secret values are registered in an in-memory `SecretRedactor` filter that scrubs matching byte/character sequences to `[REDACTED]` across all log records, `audit.jsonl` entries, and error messages, and never exports them into subprocess environments (`PM-CRED-5`).

== Operator Channel Isolation & Privileged CLI (`pm-mcp operator`)
_See Requirement link:../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Elicitation & Operator CLI)]_

_See Requirement link:../Requirements.adoc#PM-WF-12[PM-WF-12: Routine User Dialogue vs Operator-Authorizing Elicitation]_

Privileged actions—project enrolment (`enrol`, `unenrol`), credential management (`credentials`), gate overrides (`force-gate`), merge-barrier overrides (`authorize-merge`), cross-project access grants (`grant-access`), and plan deletion (`delete-plan`)—are unreachable from the MCP tool surface (`pm_start`, `pm_state`, `pm_do`, `pm_build`, `pm_lsp`).

1. *Dual Operator Channels*: Authorizing decisions require either (a) native MCP Elicitation (`elicitation/create`) on hosts where `client_profile.connection.elicitation_supported == true`, or (b) the interactive `pm-mcp operator <action>` CLI executing directly against the local state stores under `FileChannel.lock()`.
2. *Interactive TTY & Keyring / Passphrase Verification*: `pm-mcp operator` verifies that it is attached to an interactive terminal (`System.console() != null`), detects and rejects known coding-agent subshell environment markers (`CLAUDECODE=1`, `OPENCODE=1`, `ANTIGRAVITY_AGENT=1`, `CODEX_SANDBOX`, `CODEX_CI`) unless interactive operator authentication succeeds, and verifies the operator credential stored in the OS keyring (`service=de.cuioss.plan-marshall-mcp.operator`). On platforms without binary-bound Keychain ACLs (Linux Secret Service or fallback file store), `pm-mcp operator` additionally prompts interactively (no echo) for the operator passphrase, verified against a salted PBKDF2-HMAC-SHA256 hash (`>= 600,000` iterations) with exponential backoff rate-limiting (`2^failures` seconds, max 300s) and audit logging on every attempt.
3. *Blocked Workflow State*: When a workflow requires operator authorization and MCP Elicitation is unavailable, the engine transitions the scope to `*.blocked`, populates `facts.operator_command` with the exact `pm-mcp operator ...` invocation, and offers only a `wait` link until the operator completes the action on the terminal.

== Security Audit Trail & Three-Tier Identity Verification
_See Requirement link:../Requirements.adoc#PM-SEC-6[PM-SEC-6: Security Audit Trail & Tamper-Evident Logging]_

_See Requirement link:../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Three-Tier Environment Mismatch Detection & Audit]_

_See Requirement link:../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

Every MCP tool call, state transition, job execution, credential lookup, and operator command appends a structured JSONL record to `~/.plan-marshall/mcp/logs/audit.jsonl` (mode `0600`, coordinated under `FileChannel.lock()`, schema defined in link:store-schemas.adoc[Store Schemas Specification]):

* *Three-Tier Identity Tuple*: Every audit record captures (1) `declared_client` (from `mcp/entry.json`), (2) `detected_env` (from environment signatures at `enter` or MCP `clientInfo`), and (3) `os_principal` (`System.getProperty("user.name")` / `geteuid()`). Any disagreement between Tier 1 and Tier 2 sets `identity_mismatch: true` in both `audit.jsonl` and the returned TOON representation's `facts`.
* *Error Sanitization*: Unhandled exceptions or protocol errors return only a closed-enum error code and `audit_id` (UUIDv7) to the MCP caller; stack traces and host filesystem paths are written exclusively to `~/.plan-marshall/mcp/logs/daemon.log`.

== Outbound HTTPS Security (`cui-http`) & Native Runtime Stack
_See Requirement link:../Requirements.adoc#PM-TECH-1[PM-TECH-1: Java 25+ & Quarkus Native STDIO MCP Server Foundation]_

_See Requirement link:../Requirements.adoc#PM-TECH-2[PM-TECH-2: Outbound HTTPS, LSP & MCP Testing Libraries (cui-http, LSP4J, McpAssured)]_

_See Requirement link:../Requirements.adoc#PM-TECH-3[PM-TECH-3: GraalVM Native Executable & Startup/Memory Bounds]_

_See Requirement link:../Requirements.adoc#PM-TECH-4[PM-TECH-4: Operating System Platform Integration (macOS & Linux)]_

_See Requirement link:../Requirements.adoc#PM-SVC-3[PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging]_

_See Requirement link:../Requirements.adoc#PM-TEST-5[PM-TEST-5: Security Boundary & Confinement Adversarial Testing]_

* *Outbound HTTPS Hardening (`de.cuioss:cui-http`)*: All outbound REST calls (SonarQube/SonarCloud, Jira) and remote upstream MCP calls use `de.cuioss:cui-http`'s `HttpHandler` and `ResilientHttpAdapter` with TLS 1.3+, mandatory certificate/hostname verification, HTTPS-only redirect following, and origin-pinned bearer token transmission (stripping `Authorization` headers on any cross-origin redirect). All URL/path/header parameters composed into outbound requests are validated through `de.cuioss.http.security` pipelines.
* *GraalVM Native Image & Resource Bounds*: Compiled as a standalone native executable (`Java 25+`, Quarkus `quarkus-mcp-server-stdio`, Virtual Threads) with cold startup `<= 50 ms` to initial MCP `initialize` response and idle RSS `<= 64 MB`.
* *STDIO & Confinement Adversarial Verification (`PM-TEST-5`)*: Integration tests (`*IT`) using `McpAssured` (`McpStdioTestClient`) verify that zero listening TCP/UDP sockets are opened by `pm-mcp serve`, that `stdout` emits strictly valid JSON-RPC 2.0 frames even under concurrent subprocess output and uncaught exceptions, that insecure permissions (`0644`) on `enrolments.json` or fallback credential files trigger immediate fail-closed termination, and that path-traversal or command-injection payloads are deterministically rejected and logged to `audit.jsonl`.
