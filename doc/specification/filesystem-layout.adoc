== Overview

This document specifies the authoritative filesystem layout for *plan-marshall-mcp* (`PM-MCP`), covering the repository-scoped workspace tree (`.marshall/`), the machine-wide instance directory `<PM_MCP_BASE>` (default `~/.plan-marshall-mcp/`, including the fallback credential store `credentials/`), and the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/` that holds all server-owned state of one project. It defines path resolution rules, worktree isolation boundaries, the worktree lifecycle, and the separation from the state trees of legacy `plan-marshall` (`.plan/`, `~/.plan-marshall/`), which `PM-MCP` never reads or writes.

Plan state never lives in the repository: every plan directory stays in the per-project machine store for its whole life and is never moved. The repository keeps git-tracked documents in `.marshall/` and only technical local data (worktrees and temporary files) in the git-ignored `.marshall/local/`.

[#repository-layout]
== Repository Workspace Layout (`.marshall/`)
_Implementation watch: link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-1[PM-WATCH-FS-1]_

Every repository checkout of an enrolled project contains a `.marshall/` directory structured into two distinct regions: git-tracked shared documents and the git-ignored technical directory `.marshall/local/`. It is created by the first run of the project setup workflow in the project's workspace scope (link:domain-extensions/04-setup-state-machine.adoc#_architecture_enrichment_judgment_links_project_setup_state_machine[Domain Extensions Specification, Project Setup State Machine]) and is disjoint from the `.plan/` tree of legacy `plan-marshall`, which may exist beside it and is never read or written by `PM-MCP`.

[source,text]
----
<workspace-root>/
├── .gitignore
├── .marshall/
│   ├── config/                          # Team configuration (git-tracked, sparse, Store Schemas § Project Configuration)
│   │   ├── project.json                 # Repository and collaboration policy
│   │   ├── workflow.json                # Plan workflow policy, optional finalize step lanes, effort levels
│   │   ├── domains.json                 # Overrides of the derived domain detection
│   │   ├── build-map.json               # Seeded file-to-build route table
│   │   └── *.pmwf                       # Project-owned phase and sub-workflow units (Workflow DSL)
│   ├── project-architecture/            # Architecture module enrichment (git-tracked)
│   │
│   ├── orchestrator/                    # Orchestrator epics (git-tracked, edited only in the shared epic worktree)
│   │   └── <epic_id>/                   # Fully tracked; the epic's FSM state lives in the machine store
│   │       ├── epic.json                # Epic header: identity, workstreams, lifecycle (no FSM state)
│   │       ├── spec.md                  # Epic specification (workstream and plan sections)
│   │       ├── queue/                   # Staged per-plan spec definitions
│   │       │   └── <plan_id>.json       # Individual queued plan record and spec reference
│   │       ├── inbox.jsonl              # Append-only event log: messages from plans and epics
│   │       ├── landings.jsonl           # Verified plan landings and post-merge analysis
│   │       └── resume_anchor.md         # Human- and model-readable epic checkpoint summary
│   │
│   ├── archived-orchestrators/          # Terminal epics (git-tracked, moved in the shared epic worktree)
│   │   └── <epic_id>-<YY-MM-DD>/        # Same per-concern layout; epic.json keeps epic_id
│   │
│   └── local/                           # Git-ignored technical data only, never state
│       ├── worktrees/                   # Worktree root (git checkouts, recreated from branches)
│       │   ├── _epics/                  # Shared epic worktree (one for all epics, fixed branch)
│       │   ├── baseline-<plan>-<sha12>/ # Baseline scratch worktree of plan <plan>, detached at the merge base
│       │   └── <plan_id>/               # Plan worktree: created for execute/finalize, removed afterwards
│       │       ├── .git                 # Git worktree pointer file
│       │       └── <repo-source-files>  # The branch's checkout, including its git-tracked .marshall/
│       │
│       └── temp/                        # Disposable temporary files of the runtime and its jobs
----

Nothing in `.marshall/local/` is state: deleting it loses no plan data. A plan worktree is recreated from the plan's branch by the next step that needs it (<<worktree-lifecycle>>), the shared epic worktree from its branch `pm-mcp/epics`, and `temp/` is never read across calls. All server-owned state of the project lives in the per-project machine store (<<machine-store>>).

The repository `.gitignore` partitions `.marshall/`: `.marshall/*` is ignored as a blanket, `!.marshall/config/`, `!.marshall/project-architecture/`, `!.marshall/orchestrator/`, and `!.marshall/archived-orchestrators/` are un-ignored, and `.marshall/local/` stays fully ignored. The orchestrator trees are fully tracked; no re-ignore rule below them exists. The first run of the project setup workflow writes this partition and every later run verifies it; the entries for the legacy `.plan/` tree are left untouched.

[#worktree-lifecycle]
=== Worktree Lifecycle
_Implementation watch: link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-5[PM-WATCH-FS-5], link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-4[PM-WATCH-JOB-4]_

A plan never moves (`PM-ARCH-5`). Its worktree is only a git checkout, created for execute and finalize and removed afterwards; the plan's `mcp/status.json` records the worktree's presence as `worktree_path` (link:store-schemas.adoc[Store Schemas Specification], Workflow State Store):

* *Creation*: `execute.worktree-init` (or `land.worktree-init` of the `land` lane) creates the plan's feature branch and the git worktree (`finalize.adopt-pr` of the `adopt` lane creates the worktree on the adopted pull request's existing head branch) at `.marshall/local/worktrees/<plan_id>/`, then records the canonical absolute path of the worktree root (`Path.toRealPath()`) as `worktree_path` in one journaled transaction under the plan lock. The plan directory stays in the machine store; nothing is moved or copied into the worktree.
* *Use*: While `worktree_path` is set, the plan's jobs run with the worktree root as working directory (link:job-runtime.adoc[Job Runtime Specification], Working Directory Selection), dispatch prompts carry it as `WORKTREE`, and every server-owned repository write of the plan happens in the worktree, never in the main checkout.
* *Removal*: `default:branch-cleanup` removes the worktree (`git worktree remove`, run by a job whose working directory is the main checkout, never inside the worktree) and sets `worktree_path` to `null` in the same transaction that records the removal. A removal that timed out is recorded only after the partial-removal re-check (link:timeouts/01-job-budgets-and-waits.adoc#worktree-remove-recheck[Timeouts & Budgets Specification]) found positive evidence that it completed; it is never retried with `--force`. No store keeps pointing at a removed worktree: every post-merge step, and a resume after branch-cleanup, reads `worktree_path: null` and either runs against the main checkout or refuses fail-closed-clean, never on a stale path.
* *Crash Consistency*: Creation and removal are idempotent and reconciled under the plan lock on retry and on the first call after a runtime start: a recorded `worktree_path` whose worktree no longer exists is cleared with an audit record, never silently followed, and a worktree of the plan's branch that exists but is not recorded is adopted by the creating step. A plan whose worktree was deleted with `.marshall/local/` gets it recreated from its branch by the next step that needs one.
* *Baseline Scratch Worktrees*: Baseline re-runs of a failing whole-tree gate (link:job-runtime/03-parsers-and-gates.adoc#_gate_honesty_verification[Job Runtime Specification, Gate Honesty Verification]) use one scratch worktree per plan and merge base, `.marshall/local/worktrees/baseline-<plan_id>-<sha12>/`, where `<sha12>` is the first 12 hex digits of the merge-base SHA. It never carries plan state and is never recorded in `worktree_path`:
** *Creation*: created on the plan's first base run by the native `git.worktree-add`, detached (no branch) at `merge-base(HEAD, origin/<base_branch>)`.
** *Reuse*: every later base run of the plan reuses it while the merge base is unchanged, after checking that it is clean (`git.status` empty and `HEAD` at the merge base); a dirty or moved one is removed and created again, never used.
** *Replacement*: when the merge base moves, the old baseline worktree is removed and one for the new merge base is created.
** *Removal*: removed (`git.worktree-remove`, from the main checkout) when the plan leaves `finalize`, is archived, or is aborted; a removal that times out follows the partial-removal re-check (link:timeouts/01-job-budgets-and-waits.adoc#worktree-remove-recheck[Timeouts & Budgets Specification]).
** *Recovery Sweep*: the project's recovery after a runtime start, and every plan-worktree enumeration, removes a baseline worktree whose plan no longer resolves or is terminal (archived or aborted), with an audit record; it never removes one whose plan is live. A `baseline-*` directory is never mistaken for a plan worktree or adopted as one.

[#shared-epic-worktree]
=== Shared Epic Worktree
_Implementation watch: link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-4[PM-WATCH-FS-4]_

Git-tracked orchestrator state (`.marshall/orchestrator/**`) is edited only in one shared epic worktree and reaches the default branch only through the epic landing (`PM-ARCH-5`):

* *Location*: `.marshall/local/worktrees/_epics/`, beside the plan worktrees under the same git-ignored root. The key `_epics` lies outside the link:identifiers/01-general-rules-and-registry.adoc#id-plan-id[plan ID grammar], so no plan can collide with it.
* *Branch*: One fixed, long-lived branch (`pm-mcp/epics`) created once off `origin/<default branch>`; the ledger changes of every epic are committed there.
* *Lifecycle*: Created on the first epic-ledger write and reused as-is afterwards (idempotent). No normal operation removes it, including the epic landing; only `pm-mcp operator epic-worktree teardown` does. Plan-worktree enumeration, startup recovery, and any orphan sweep recognise it and never treat it as an orphaned plan worktree.
* *Concurrency*: The per-concern ledger layout lets concurrent epic sessions write disjoint files in the one working tree. Ledger writes serialize per epic under the epic lock; git operations on the worktree serialize under the project-wide lock `<PM_MCP_BASE>/projects/<project_id>/locks/epics-worktree.lock`.
* *No Plan Mechanics*: The ledger is git-tracked, so the worktree is a second checkout of it: no per-scope executor and no plan-keyed merge lease apply. The epics' non-tracked FSM state lives in the machine store (`epics/<epic_id>/`, <<machine-store>>) and the epic locks live there too, outside the tree (link:store-schemas.adoc[Store Schemas Specification], § Lock-Free Snapshot Reads, Transaction Locks & Leases).
* *Epic Ledger Resolution Seam*: Every read and write of `.marshall/orchestrator/**` (epic header `epic.json`, queue rows, inbox, landings, spec documents, `pm://epic/**` resources, and `pm_epics`) and every plan-side access (the `default:emit-landing` inbox append, a child plan's read of its specification, the `running` observation) resolves through one resolver to the shared epic worktree copy; nothing reads the primary checkout's copy. A specification staged in the worktree but not yet landed is served to the child plan through this seam.
* *Stranded-Change Guard*: Before the first ledger write is routed into the shared epic worktree, the runtime checks the primary checkout for uncommitted or unpushed changes under `.marshall/orchestrator/**`. If any exist it refuses with `ledger_changes_stranded`, naming the paths, until the operator lands them or carries them into the worktree with `pm-mcp operator epic-worktree adopt`; two diverging copies are never left behind silently.

[#machine-layout]
== Machine-Wide Runtime Layout (`<PM_MCP_BASE>`)

The runtime (`pm-mcpd`) persists machine-wide configuration, cross-process `FileChannel.lock()` files, audit logs, project enrolments, the fallback credential store, and the per-project machine stores in its instance directory `<PM_MCP_BASE>`, default `~/.plan-marshall-mcp/`; the only override is the environment variable `PM_MCP_BASE` (`PM-ARCH-2`, `PM-ARCH-6`, `PM-DIST-5`). `PM-MCP` never reads `PLAN_MARSHALL_HOME` or `PLAN_MARSHALL_CREDENTIALS_DIR`, and never reads or writes `~/.plan-marshall/`. The binaries live apart from it in the read-only installation directory `<PM_MCP_HOME>/bin/` (link:cli-and-security/01-cli-and-installer.adoc#installation-layout[CLI, Coordination & Security Specification, Installation Layout]), which holds no configuration file: machine settings are `machine-config.json`.

[source,text]
----
~/.plan-marshall-mcp/                    # <PM_MCP_BASE>: PM-MCP instance directory (mode 0700)
├── machine-config.json                  # Build slot caps, warm LSP pool defaults, project_defaults (mode 0600)
├── enrolments/                          # Operator enrolments, one file per project (mode 0700)
│   ├── <project_id>.json                # Root, wrappers, tools, templates, scripts, budgets (mode 0600)
│   └── <project_id>.json.hmac           # HMAC-SHA-256 sidecar of that file, written with every enrolment write (mode 0600)
│
├── credentials/                         # Token-lane file credential fallback (PM-CRED-3, mode 0700)
│   ├── <credential_key>.json            # Global entry (e.g. workflow-integration-sonar.json, mode 0600)
│   └── <project>/
│       └── <credential_key>.json        # Project-scoped override (mode 0600)
│
├── conf/                                # Operator-owned configuration overrides
│   ├── upstream-mcp.json                # Selective upstream MCP proxy configuration
│   └── profiles/                        # Optional machine-wide client profile overrides
│       └── <client_id>.json
│
├── projects/                            # Per-project machine stores (mode 0700, see below)
│   └── <project_id>/                    # One store per enrolled project: plans, archive, lessons, ...
│
├── state/                               # Persistent cross-session operational state
│   ├── install-records.json             # Client bundle ownership & SHA-256 manifest records
│   ├── build-slots.json                 # Active PID-keyed build concurrency leases
│   ├── merge-queue.json                 # Per-repo FIFO merge admission queues & active holders
│   ├── review-bot-windows.json          # Per-bot cross-plan rate-window claims
│   ├── web-devices.json                 # Paired web devices: device_id, label, secret hash, timestamps (mode 0600)
│   ├── enrolment-hmac.key               # Enrolment HMAC key, only on hosts without an OS keyring (mode 0600)
│   └── runtime.json                     # Runtime record: pid, start instant, version, effective socket path
│                                        # (default or $TMPDIR fallback), written at socket bind
│
├── run/                                 # Runtime directory (mode 0700); like all of <PM_MCP_BASE> outside every job's Landlock read set
│   ├── runtime.token                    # Runtime token, rewritten at every runtime start before bind (mode 0600)
│   ├── runtime.sock                     # Unix domain socket of the runtime (mode 0600); if this path
│   │                                    # exceeds sun_path, $TMPDIR/pm-mcp-<hash>/runtime.sock instead
│   └── web.json                         # Process record of the running web server pm-mcp-web (mode 0600)
│
├── web/                                 # Web server files (mode 0700)
│   └── tls/                             # Self-signed LAN certificate and key of pm-mcp-web (key mode 0600)
│
├── locks/                               # Cross-process OS FileChannel.lock() primitives
│   ├── runtime.lock                     # Runtime singleton lock (held for the runtime lifetime)
│   ├── runtime-start.lock               # Serializes on-demand runtime start by CLI commands (the CLI's only lock)
│   │                                    # Machine store locks, one sibling lock per renamed store,
│   │                                    # acquired alphabetically after all scope locks:
│   ├── build-slots.lock                 # state/build-slots.json
│   ├── enrolments/
│   │   └── <project_id>.lock            # enrolments/<project_id>.json and its .hmac (lexicographic by project_id)
│   ├── install-records.lock             # state/install-records.json
│   ├── machine-config.lock              # machine-config.json
│   ├── merge.lock                       # state/merge-queue.json (merge leases)
│   ├── review-bot.lock                  # state/review-bot-windows.json
│   ├── web-devices.lock                 # state/web-devices.json
│   └── web.lock                         # Web server singleton (held for the pm-mcp-web lifetime)
│
└── logs/                                # Diagnostic logs and structured security audit
    ├── daemon.log                       # Rolling runtime diagnostic log (mode 0600)
    ├── audit.jsonl                      # Append-only audit (mode 0600); locked directly, leaf lock
    ├── audit-<first_event_id>.jsonl     # Rotated audit files, closed by a checkpoint record
    ├── audit-index.jsonl                # Hash-chained index of rotated audit files
    └── audit.head                       # HMAC-anchored head: file, record count, last event_id, head hash
----

The Linux Landlock write set of a job contains only its own project root (with its worktrees and `.marshall/local/temp/`), the declared toolchain caches, `/tmp`, and `/dev`; it never contains `<PM_MCP_BASE>`, including `projects/`, or another enrolled project's root (`PM-SEC-5`): jobs never write the machine stores. The client bundles install host file-tool deny rules for `<PM_MCP_BASE>/**` as defense in depth (a model-driven shell bypasses them), and the HMAC sidecar `enrolments/<project_id>.json.hmac` detects edits of a project's enrolment file outside the operator verbs. The runtime is the only writer of every store under `<PM_MCP_BASE>`; the CLI and `pm-mcp-web` write none (link:runtime-model.adoc#local-api[Runtime & Interaction Model Specification, Local API]). The Landlock read set of jobs is the whole filesystem except all of `<PM_MCP_BASE>`, so no job reads the runtime token, a credential file, an enrolment, or another project's machine store; the installation directory `<PM_MCP_HOME>` stays readable (link:job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification]).

=== File Permissions & Security Attributes

The runtime creates every file under `<PM_MCP_BASE>` with mode `0600` and every directory with mode `0700`. At start it checks only `<PM_MCP_BASE>`, `enrolments/`, and `run/` (owned by the effective UID, mode `0700`) and the files in `state/` (mode `0600`); enrolment and credential files are checked on every use (`PM-SEC-4`). The `0700` base directory is what protects the rest.

[cols="2,1,3"]
|===
|Path |POSIX Permissions |Security Requirement

|`<PM_MCP_BASE>/credentials/`
|`0700` (`drwx------`)
|Strict user-only read/write directory (`PM-CRED-3`). Checked when a credential is resolved, not at runtime start: if group/others have read, write, or execute permissions, the runtime reads no credential from it and the step needing the credential raises the `blocked` condition on its current state with the repairing `pm-mcp operator credentials` command (`PM-CRED-4`).

|`<PM_MCP_BASE>/credentials/<credential_key>.json` and `<project>/<credential_key>.json`
|`0600` (`-rw-------`)
|Strict user-only access (`PM-CRED-3`). The runtime refuses to read any credential file whose permissions are broader than `0600`; only the step needing that credential is blocked (`credentials_file_insecure`, `PM-CRED-4`).

|`<PM_MCP_BASE>/enrolments/`
|`0700` (`drwx------`)
|Operator-owned enrolment directory; one file per project. Owned by the effective UID; checked at runtime start with `<PM_MCP_BASE>`.

|`<PM_MCP_BASE>/enrolments/<project_id>.json` and `<project_id>.json.hmac`
|`0600` (`-rw-------`)
|Operator-verified project root, pinned tool and wrapper digests, command templates, and project scripts (`PM-EXEC-2`). A file with permissions broader than `0600` blocks only its project (`enrolment_insecure`), like a tampered one. Every write of it (by the runtime, on an operator verb) also writes the file's HMAC-SHA-256 sidecar, verified before the project is first served after a runtime start and before every verify-not-resolve check (`enrolment_tampered` on mismatch, link:cli-and-security/02-credentials-and-operator.adoc#enrolment-integrity[CLI, Coordination & Security Specification]).

|`<PM_MCP_BASE>/state/enrolment-hmac.key`
|`0600` (`-rw-------`)
|Enrolment HMAC key on hosts without an OS keyring only; its residual risk is documented with the enrolment integrity (`PM-SEC-5`).

|`<PM_MCP_BASE>/projects/` and every `<project_id>/` below it
|`0700` (`drwx------`)
|Covered by the `<PM_MCP_BASE>` rules: owned by the effective UID, never in a job's Landlock read or write set, and behind the host deny rules for `<PM_MCP_BASE>/**`. The store digest sidecars still detect out-of-band edits by a host shell (link:store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification]).

|`<PM_MCP_BASE>/locks/*.lock` and `<PM_MCP_BASE>/projects/<project_id>/locks/*.lock`
|`0600` (`-rw-------`)
|Held via OS kernel `FileChannel.lock()`. The store and scope locks are taken only by the runtime, the only store writer; `runtime-start.lock` is also taken by a CLI command during the on-demand start, and `web.lock` by `pm-mcp-web`.

|`<PM_MCP_BASE>/run/`
|`0700` (`drwx------`), no symlink
|Checked by the runtime at start and by every client before it reads the token or connects; a foreign owner, a broader mode, or a symlink makes the runtime exit with code `77` and a client refuse (`PM-SEC-4`).

|`<PM_MCP_BASE>/run/runtime.token`
|`0600` (`-rw-------`), no symlink
|The runtime token of the running instance (link:runtime-model.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]), written atomically at every start before the socket is bound; format in link:store-schemas/12-machine-stores.adoc#web-access-records[Store Schemas Specification]. Stays in `run/` also when the socket uses the fallback path. Never in a job's Landlock read set, never in a log or job environment.

|`<PM_MCP_BASE>/run/runtime.sock`, or the fallback `$TMPDIR/pm-mcp-<hash>/runtime.sock`
|`0600` (`srw-------`) in a `0700` directory owned by the effective UID
|Only listener of the runtime (`PM-SEC-4`). The fallback is bound when the default path would exceed the platform's `sun_path` limit (104 bytes including NUL on macOS, 108 on Linux); `<hash>` is the first 16 hex characters of SHA-256 of `PM_MCP_BASE`, the directory is refused unless owned by the effective UID with mode `0700`, and the effective path is recorded in `state/runtime.json` (link:runtime-model.adoc#_singleton_discovery[Runtime & Interaction Model Specification, Singleton & Discovery]).

|`<PM_MCP_BASE>/logs/audit.jsonl`
|`0600` (`-rw-------`)
|Append-only security and transition audit log, hash-chained through each record's `prev_hash`, with its head anchored in the HMAC-protected `audit.head` and rotated files listed in `audit-index.jsonl` (same mode); the chain is verified incrementally at runtime start, and a broken chain (including a deleted, reset, or truncated log) is reported and recorded, never repaired (`PM-SEC-6`).
|===

[#machine-store]
== Per-Project Machine Store (`<PM_MCP_BASE>/projects/<project_id>/`)

All server-owned state of one project lives in its per-project machine store `<PM_MCP_BASE>/projects/<project_id>/`, where `<project_id>` is the project's enrolment identifier, the name of its enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (the same key that names project-scoped credentials, `PM-CRED-3`): assigned by the operator, unique per machine, and identical for the main checkout and all its worktrees. `pm-mcp operator enrol` creates the store and records its `project_root` in `store.json` (link:store-schemas/11-enrolment-store.adoc#project-store-identity[Store Schemas Specification, Project Store Identity]); `pm-mcp operator release-project` leaves it readable (<<coexistence-lifecycle>>), and `pm-mcp operator unenrol` leaves it untouched: its removal is a retention purge of `pm-mcp operator sweep` (link:store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification, Evidence-Based Removal Sweeps]).

[source,text]
----
~/.plan-marshall-mcp/projects/<project_id>/
├── plans/                               # Every live plan directory, for its whole life (never moved)
│   └── <plan_id>/
│       ├── request.md
│       ├── outline.md
│       ├── execution-manifest.json
│       ├── tasks/
│       │   ├── TASK-001.json
│       │   └── TASK-002.json
│       ├── findings.jsonl
│       ├── assessments.jsonl            # Append-only component assessments (never findings)
│       ├── review-participation.jsonl   # Per-round review-bot participation records
│       ├── metrics.json                 # Dispatch and phase measurements (record-metrics)
│       ├── quality-report.json          # Post-run quality report (plan-retrospective)

* *Never Moved*: A plan directory is created by `pm_start` in `plans/<plan_id>/` and stays there until `archive-plan` moves it to `archive/<plan_id>/` (a rename within the same store directory) or `delete-plan` removes it. No worktree creation, worktree removal, or finalize step moves it.
* *Scope Directories*: The FSM state of a scope lives in its scope metadata directory: `plans/<plan_id>/mcp/`, `epics/<epic_id>/`, and `workspace/mcp/`. For an epic the metadata directory is `epics/<epic_id>/` itself, which holds nothing else; where the specifications name a scope's `mcp/` files (`mcp/status.json`, `mcp/digests.json`, `mcp/transaction-journal.json`), an epic's are these files in `epics/<epic_id>/`. Every scope's session log `sessions.jsonl` lies directly in the scope directory (`plans/<plan_id>/`, `epics/<epic_id>/`, `workspace/`; link:store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]). The epic ledger (`epic.json`, queue, inbox, landings, spec) stays git-tracked in `.marshall/orchestrator/<epic_id>/` of the shared epic worktree; `epics/<epic_id>/` holds only what is not tracked.
* *Locks*: The scope locks live in `locks/`, outside the directories they protect (link:store-schemas/13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Store Schemas Specification, Transaction Locks]); the machine-wide store locks stay in `<PM_MCP_BASE>/locks/`.
* *Writers*: Only the runtime writes the store (operator verbs included, which reach it through the runtime's local API), always through the stores' transactions; jobs never write it, and the model reaches it only through server links and resources (`pm://plan/…`, `pm://epic/…`, `pm://workspace/…`), never through file paths.

[#workspace-home]
=== Workspace Home (`<PM_MCP_BASE>/projects/<project_id>/workspace/`)

Every enrolled project has exactly one workspace scope (`PM-ARCH-4`), addressed in a tool call as `plan_id: NO_PLAN` (link:identifiers/01-general-rules-and-registry.adoc#id-no-plan[Identifier Registry, `NO_PLAN`]) and resolved from the `PM-MCP-Workspace` header of the request (link:runtime-model.adoc[Runtime & Interaction Model Specification], Connection Metadata). Its home is `workspace/` in the project's machine store:

* *No Worktree, No Archive*: The workspace scope has no worktree and no archive; its home stays in the machine store for the life of the enrolment.
* *Contents*: `mcp/status.json` (the FSM state of the workflows the workspace hosts, `project-setup`, link:domain-extensions.adoc[Domain Extensions Specification]), `sessions.jsonl` (the session log, appended by `pm-mcp enter … workspace` and by the server), `mcp/digests.json` (the store digest sidecar), `change-ledger.jsonl` (the ledger rows of plan-less service calls, `pm_build` with `plan_id: NO_PLAN`), and `findings.jsonl` (the findings of plan-less builds). Build and job logs of the workspace scope lie in `jobs/` of the project's machine store, next to their records, and are addressed as `pm://workspace/builds/{job_id}/log`; `pm://workspace/status` and `pm://workspace/findings` project the two stores (link:mcp-tools.adoc[MCP Tools Specification]).
* *Lock*: Every write to the workspace home takes `locks/workspace.lock` of the project's machine store, the first lock of the one total order (workspace -> plan locks -> epic locks -> `epics-worktree` -> `lessons` -> `local-config` -> `build-timings` -> machine store locks -> leaf locks, link:store-schemas/13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Store Schemas Specification]), and runs as a journaled transaction (`mcp/transaction-journal.json`, link:store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal]).

[#archives]
=== Plan & Epic Archives
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-20[PM-WATCH-DISP-20], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-21[PM-WATCH-DISP-21], link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-1[PM-WATCH-FS-1]_

Archived records keep their identity and stay readable by it (`PM-WF-13`):

* *Plan Archive*: `archive-plan` (step `1100`) moves the plan directory from `plans/<plan_id>/` to `archive/<plan_id>/` of the project's machine store. The path carries no date, so a `plan_id` present in the archive is never allocated again (link:phase-workflows/01-planning-phases-1-2.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]). Archived plans are purged only by the operator's retention setting (`retention.archived_plans_days` of the machine-local `local-config.json`, link:timeouts/03-retention-host-config.adoc#retention-days[Timeouts & Budgets Specification]) through an evidence-based removal sweep (link:store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification]). Archiving already lands machine-side, so there is no separate export: the archive never leaves the workstation (`PM-ARCH-2`).
* *Epic Archive*: When an epic reaches a terminal state, the epic workflow moves its directory inside the shared epic worktree from `.marshall/orchestrator/<epic_id>/` to `.marshall/archived-orchestrators/<epic_id>-<YY-MM-DD>/` (UTC archival date), and the move reaches the default branch through the epic landing. The archived `epic.json` keeps `epic_id`; the dated suffix is never parsed for identity, and a title is never an identity. The epic archive is git-tracked and has no retention purge; the epic's non-tracked `epics/<epic_id>/` stays in the machine store, read-only.
* *Enumeration*: Every enumeration of epics (`pm_epics`, sibling-epic enumeration, re-grounding reads) covers the active root `.marshall/orchestrator/` and, where it reads history, the archived root, and reports per root `root`, `exists`, `listed`, `entries_scanned`, and `unreadable`, so "zero epics" is distinguishable from "root not scanned". Sibling-epic enumeration excludes every archived snapshot whose `epic_id` equals the enumerating epic's own.
* *Read-Only Access by ID*: An archived record answers read requests by its id; mutating calls are rejected with its terminal representation. A project reads only its own machine store; reading another project's archived plans requires the operator-approved cross-project escalation (`PM-SEC-2`).

[#plan-worktree-resolution]
=== Plan & Worktree Resolution
_Implementation watch: link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-2[PM-WATCH-FS-2], link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-3[PM-WATCH-FS-3], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-1[PM-WATCH-STORE-1]_

[[project-resolution]]
*Project Resolution Rule*: One rule maps a working directory to a project. `pm-mcp enter` applies it to its current directory, and the runtime applies it to the directory named by the `PM-MCP-Workspace` header (link:runtime-model.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]); no other resolver exists:

. Run `git rev-parse --show-toplevel` and `git rev-parse --git-common-dir` in the directory and canonicalise both (`Path.toRealPath()`); outside a git work tree the directory is refused as `project_not_enrolled`.
. The main checkout is the directory that contains the common git directory (the parent of `--git-common-dir`). It must equal the `project_root` of exactly one enrolment file (link:store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]); that file names the `project_id`. No match is refused as `project_not_enrolled`; a match of a tampered or unreadable enrolment file is refused with that file's reason.
. If the toplevel equals the main checkout, the directory was entered from `main_checkout`. If the toplevel is `<project_root>/.marshall/local/worktrees/<x>/`, it was entered from a `worktree` with `worktree_of: <x>` (a `plan_id`, or `_epics` for the shared epic worktree); a baseline scratch worktree (`baseline-<plan_id>-<sha12>`, <<worktree-lifecycle>>) is not an entry point and is refused as unenrolled. Any other toplevel (a git worktree outside `.marshall/local/worktrees/`, or a nested repository) is refused as unenrolled.

The resolved `project_id` and origin are recorded in the session row (`entered_from`, `worktree_of`, link:store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]); no session row records a path.

* *Deterministic Location*: A plan has exactly one directory, so its resolution has no candidates to arbitrate:
** The project is the one the verified `PM-MCP-Workspace` header resolves to by the project resolution rule above; the plan is looked up only in that project's machine store, and the last row of its session log supplies the client profile (link:store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]). The main checkout is the enrolled `project_root`; no scope record stores a path to it.
** If `plans/<plan_id>/` exists, the plan is live. Its worktree is the recorded `worktree_path`, re-canonicalised and confinement-checked on every read; a recorded path that is not a live git worktree of `branch_name` is reconciled as described in <<worktree-lifecycle>>, never followed.
** Otherwise, if `archive/<plan_id>/` exists, the plan is archived: `pm_state` returns its terminal representation (empty `links`, read-only), `pm://plan/{plan_id}/*` resources and the report and corpus readers serve the archived stores, and every mutating call is rejected.
** Otherwise the plan does not exist (`scope_not_found`).
* *Missing Is Not Empty*: Every path and record resolver distinguishes `absent` (the path does not exist) from an existing empty directory or file, and a metadata reader that finds nothing it can parse reports `unreadable`, never an empty record; neither is ever answered as a successful empty result.
* *Enumeration*: Every enumeration of live plans (`pm_plans`, dedup gates, sibling reads) lists `plans/*` of the project's machine store, one directory, and reports `could_not_look` for an unreadable store, distinct from an empty one.
* *Stateless Client Scope*: Neither the model nor the MCP client ever passes filesystem paths (`PM-ARCH-4`, `PM-SEC-2`). The client passes only `plan_id` (a plan id, or `NO_PLAN` for the workspace scope) or `epic_id`. The daemon dynamically resolves the canonical real path (`Path.toRealPath()`) and verifies confinement to the project's machine store or workspace before any file I/O.

[#coexistence-lifecycle]
== Coexistence with plan-marshall, Enrolment & Release (`PM-MIG-1`, `PM-MIG-2`, `PM-MIG-5`)
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-2[PM-WATCH-DISP-2]_

`PM-MCP` is built out in parallel to legacy `plan-marshall` and shares no state tree with it:

1. *Separate State Trees (`PM-MIG-2`)*: `PM-MCP` owns `.marshall/` per repository and `<PM_MCP_BASE>` (with the per-project machine stores) per machine; legacy `plan-marshall` keeps `.plan/` and `~/.plan-marshall/`. Both may be installed on one machine and used in the same repository. `PM-MCP` runs no legacy script, holds no lock of the legacy tree, and never reads or writes it, without exception; legacy `plan-marshall` never reads or writes the `PM-MCP` trees.
2. *Clean Slate & Enrolment (`PM-MIG-1`, `PM-MIG-2`)*: `PM-MCP` imports nothing from legacy `plan-marshall`: no configuration, lessons, `project-architecture/`, credentials, or learned build timeouts. `pm-mcp operator enrol` creates the project's machine store and its workspace scope; the first run of the project setup workflow creates `.marshall/` and `.marshall/config/` with the copies of the default workflow units. Legacy plans and epics are never taken over; they finish in `plan-marshall`. The plan lifecycle is offered in an enrolled project once the lifecycle gate has opened (`PM-MIG-4`).
3. *Release (`PM-MIG-5`)*: `pm-mcp operator release-project` is the operator's switch-off for the `PM-MIG-5` triggers and stops offering the plan lifecycle for a project; plans in flight stay readable in the project's machine store and nothing is converted. The project can continue on legacy `plan-marshall`, whose `.plan/` `PM-MCP` never touched.
