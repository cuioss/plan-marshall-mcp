== Overview

This document specifies the authoritative filesystem layout for *plan-marshall-mcp* (`PM-MCP`), covering both repository-scoped workspace structures (`.plan/`) and machine-wide user-level daemon directories (`~/.plan-marshall/mcp/` and `~/.plan-marshall/credentials/`). It defines path resolution rules, worktree isolation boundaries, same-filesystem guarantees, and mutual coexistence markers.

== Repository Workspace Layout (`.plan/`)
_Implementation watch: link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-1[PM-WATCH-FS-1], link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-2[PM-WATCH-FS-2]_

The repository `.gitignore` partitions `.plan/`: `.plan/*` is ignored as a blanket, `!.plan/marshal.json`, `!.plan/orchestrator/`, and `!.plan/archived-orchestrators/` are un-ignored, `.plan/orchestrator/*/mcp/` and `.plan/archived-orchestrators/*/mcp/` (and any per-epic log directory) are ignored again after the negations, and `.plan/local/` stays fully ignored. The project setup workflow verifies this partition.

[#archives]
=== Plan & Epic Archives
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-20[PM-WATCH-DISP-20], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-21[PM-WATCH-DISP-21], link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-1[PM-WATCH-FS-1]_

Archived records keep their identity and stay readable by it (`PM-WF-13`):

* *Plan Archive*: `archive-plan` (step `1100`) moves the plan directory to `.plan/local/archive/<plan_id>/` (git-ignored, same filesystem, never relocated). The path carries no date, so a `plan_id` present in the archive is never allocated again (link:phase-workflows.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]). Archived plans are purged only by the project's retention setting (`system.retention.archived_plans_days`, kept from `plan-marshall`) through an evidence-based removal sweep (link:store-schemas.adoc#evidence-based-removal-sweeps[Store Schemas Specification]).
* *Epic Archive*: When an epic reaches a terminal state, the epic workflow moves its directory inside the shared epic worktree from `.plan/orchestrator/<epic_id>/` to `.plan/archived-orchestrators/<epic_id>-<YY-MM-DD>/` (UTC archival date), and the move reaches the default branch through the epic landing. The archived `status.json` keeps `epic_id`; the dated suffix is never parsed for identity, and a title is never an identity. The epic archive is git-tracked and has no retention purge.
* *Enumeration*: Every enumeration of epics (`pm_epics`, sibling-epic enumeration, disjointness and re-grounding reads) covers the active root `.plan/orchestrator/` and, where it reads history, the archived root, and reports per root `root`, `exists`, `listed`, `entries_scanned`, and `unreadable`, so "zero epics" is distinguishable from "root not scanned". Sibling-epic enumeration excludes every archived snapshot whose `epic_id` equals the enumerating epic's own.
* *Operator Export*: `pm-mcp operator archive export --plan <plan_id>` or `--epic <epic_id>` moves an archived record into the machine-local export `~/.plan-marshall/mcp/archive/<project_key>/plans/<plan_id>/` or `.../epics/<epic_id>-<YY-MM-DD>/`, where `<project_key>` is the project's enrolment key in `enrolments.json`. The export is a move, never a copy, so each record has exactly one authoritative location: a plan is renamed out of `.plan/local/archive/` (a copy-then-delete across filesystems runs under a move journal), and an epic is removed from the archived root in the shared epic worktree, the removal reaching the default branch through the next epic landing. The export is only ever operator-initiated, never automatic, and never leaves the workstation (`PM-ARCH-2`); exported records are outside every retention purge.
* *Read-Only Access by ID*: An archived or exported record answers read requests by its id; mutating calls are rejected with its terminal representation. A project reads only its own export partition; reading another project's partition requires the operator-approved cross-project escalation (`PM-SEC-2`).

=== Worktree Path Resolution & Same-Filesystem Invariant
_Implementation watch: link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-3[PM-WATCH-FS-3]_

* *Deterministic Location*: For any plan identified by `<plan_id>`, the server resolves its active working tree deterministically:
** If `.plan/local/worktrees/<plan_id>/` exists and is a valid git worktree, the plan directory is located at `.plan/local/worktrees/<plan_id>/.plan/local/plans/<plan_id>/`.
** Otherwise, if `.plan/local/plans/<plan_id>/` exists, the plan directory is located there within the primary checkout.
** Otherwise, if `.plan/local/archive/<plan_id>/` exists, the plan is archived: `pm_state` returns its terminal representation (empty `links`, read-only), `pm://plan/{plan_id}/*` resources and the report and corpus readers serve the archived stores, and every mutating call is rejected.
** Otherwise, if the project's export partition `~/.plan-marshall/mcp/archive/<project_key>/plans/<plan_id>/` exists, the plan is exported and answered read-only in the same way.
* *Same-Filesystem Invariant*: All worktrees are created within `.plan/local/worktrees/<plan_id>`. This guarantees that moving the `<plan_id>` directory between the primary checkout and the worktree operates on the *same physical filesystem partition*, enabling POSIX atomic renames (`rename(2)` / `Files.move(..., ATOMIC_MOVE)`).
* *Stateless Client Scope*: Neither the model nor the MCP client ever passes filesystem paths (`PM-ARCH-4`, `PM-SEC-2`). The client passes only `plan_id` or `epic_id`. The daemon dynamically resolves the canonical real path (`Path.toRealPath()`) and verifies workspace confinement before any file I/O.

=== Shared Epic Worktree
_Implementation watch: link:../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-4[PM-WATCH-FS-4]_

Git-tracked orchestrator state (`.plan/orchestrator/**`) is edited only in one shared epic worktree and reaches the default branch only through the epic landing (`PM-ARCH-5`):

* *Location*: `.plan/local/worktrees/_epics/`, beside the plan worktrees under the same git-ignored root and filesystem. The key `_epics` lies outside the plan ID grammar, so no plan can collide with it.
* *Branch*: One fixed, long-lived branch (`pm-mcp/epics`) created once off `origin/<default branch>`; the ledger changes of every epic are committed there.
* *Lifecycle*: Created on the first epic-ledger write and reused as-is afterwards (idempotent). No normal operation removes it, including the epic landing; only `pm-mcp operator epic-worktree teardown` does. Plan-worktree enumeration, startup recovery, and any orphan sweep recognise it and never treat it as an orphaned plan worktree.
* *Concurrency*: The per-concern ledger layout lets concurrent epic sessions write disjoint files in the one working tree. Ledger writes serialize per epic under the epic lock; git operations on the worktree serialize under the repository-wide lock `<main>/.plan/local/locks/epics-worktree.lock`.
* *No Relocation*: The ledger is git-tracked, so the worktree is a second checkout of it: no move journal, no per-scope executor, and no plan-keyed merge lease apply. Epic locks already live outside the tree (link:store-schemas.adoc[Store Schemas Specification], § Lock-Free Snapshot Reads, Transaction Locks & Leases).
* *Epic Ledger Resolution Seam*: Every read and write of `.plan/orchestrator/**` (epic `status.json`, queue rows, inbox, landings, spec documents, `pm://epic/**` resources, and `pm_epics`) and every plan-side access (the `default:emit-landing` inbox append, a child plan's read of its specification, the `running` observation) resolves through one resolver to the shared epic worktree copy; nothing reads the primary checkout's copy. A specification staged in the worktree but not yet landed is served to the child plan through this seam.
* *Cutover Guard*: Before the first ledger write is routed into the shared epic worktree (and at the Stage 4 epic-ledger conversion), the runtime checks the primary checkout for uncommitted or unpushed changes under `.plan/orchestrator/**`. If any exist it refuses with `ledger_changes_stranded`, naming the paths, until the operator lands them or carries them into the worktree with `pm-mcp operator epic-worktree adopt`; two diverging copies are never left behind silently.

== Machine-Wide Runtime Layout (`~/.plan-marshall/mcp/`)

`pm-mcp` persists machine-wide configuration, cross-process `FileChannel.lock()` files, audit logs, and project enrolments in the user's home directory (`PM-ARCH-2`, `PM-ARCH-6`).

[source,text]

│   └── <project>/

|===
|Path |POSIX Permissions |Security Requirement

|`~/.plan-marshall/credentials/`
|`0700` (`drwx------`)

|`0600` (`-rw-------`)

== Plan Directory Relocation Sequence
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-4[PM-WATCH-JOB-4]_

When a plan transitions to or from an isolated worktree, the daemon executes atomic relocation under an exclusive lock backed by `link:move-journal.adoc[move-journal.json]` (`PM-ARCH-7`):

* *Outward Relocation (Main Checkout -> Worktree)*:
** Git worktree is created at `.plan/local/worktrees/<plan_id>/`.
** `.plan/local/worktrees/<plan_id>/.plan/local/plans/` directory is prepared.
** Write-ahead journal entry is flushed (`operation: RELOCATE_TO_WORKTREE`, `phase_state: TARGET_PREPARED`).
** Atomic directory rename moves `.plan/local/plans/<plan_id>/` to `.plan/local/worktrees/<plan_id>/.plan/local/plans/<plan_id>/`.
** `status.json` location is updated and fsynced, then the journal is deleted.
* *Inward Relocation (Worktree -> Main Checkout)*:
** Prior to worktree removal, write-ahead journal entry is flushed (`operation: RELOCATE_TO_MAIN`, `phase_state: TARGET_PREPARED`).
** Atomic directory rename moves `.plan/local/worktrees/<plan_id>/.plan/local/plans/<plan_id>/` back to `.plan/local/plans/<plan_id>/`.
** `status.json` location is updated and fsynced, then the journal is deleted.
** Git worktree at `.plan/local/worktrees/<plan_id>/` is safely dismantled (`git worktree remove`).

If a power failure or crash occurs during either step, the daemon's startup recovery procedure inspects `move-journal.json` to complete or roll back the move idempotently.

== Staged Porting, Cutover & Rollback (`PM-MIG-2`, `PM-MIG-3`, `PM-MIG-5`)
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-2[PM-WATCH-DISP-2]_

During the staged porting from `plan-marshall` Python scripts to `PM-MCP`:

1. *Machine Cutover (`PM-MIG-2`)*: Installing Stage 1 switches the whole machine to `PM-MCP`. The client bundles remove the host allowlist entries for `execute-script.py`, and the legacy executor refuses to run unless launched by the runtime as a `script` job. Legacy and `PM-MCP` never run in parallel on one machine.
2. *Single Writer Set (`PM-MIG-3`)*: Ported Java primitives and routed legacy `script` jobs both run inside the runtime. A `script` job holds the addressed scope's lock for its whole duration, so shared `.plan/` stores (`status.json`, `findings.jsonl`, `references.json`, `TASK-*.json`) never see concurrent writers from the two implementations and no cross-runtime lock protocol exists.
3. *Rollback (`PM-MIG-5`)*: `pm-mcp operator rollback` drains the runtime, converts the stores switched by the rolled-back stages back to their legacy formats with the reverse converters (link:store-schemas.adoc#legacy-store-formats[Store Schemas Specification]), and restores direct legacy execution on the machine. Plan directories and domain artifacts stay in place.
