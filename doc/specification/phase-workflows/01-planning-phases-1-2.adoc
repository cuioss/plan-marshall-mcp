=== Lifecycle Topology (Phases 1–4)

The planning lifecycle is a server-enforced state machine spanning `phase-1-init`, `phase-2-refine`, `phase-3-outline`, and `phase-4-plan`. Sub-states (open questions, the Q-Gate remediation budgets, and the refine relaunch counter) are persisted in the plan store (question records in `questions.jsonl`, the per-plan policy counters and the current state in `mcp/status.json`) so that a runtime restart resumes at the exact sub-state; no session holds plan state. The process a plan runs is its own composed plan instance (xref:02-planning-lanes-phases-3-4.adoc#plan-instance-composition[Plan Instance Composition]); every blocking condition of a planning phase ends in a bounded self-remedy and, when that is spent, in the `returned` fallback (<<plan-outcomes>>).

Every state of Phases 1–4 is catalogued in the State Catalogue (link:../state-catalogue/02-plan-phases-1-3.adoc#state-catalogue-init[`init`], link:../state-catalogue/02-plan-phases-1-3.adoc#state-catalogue-refine[`refine`], link:../state-catalogue/02-plan-phases-1-3.adoc#state-catalogue-outline[`outline`], link:../state-catalogue/03-plan-phases-4-5-land.adoc#state-catalogue-plan[`plan`]; generic per-phase states in link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-generic[Generic Per-Phase States]; condition overlays in link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-conditions[Conditions]).

A plan started from the `local_changes` source does not traverse Phases 2–4: it runs in the `land` lane (xref:02-planning-lanes-phases-3-4.adoc#land-lane[Land Lane (`local_changes`)]) from `init.ready` through `land.*` verification states directly into Phase 6. A plan started from the `pr` source does not traverse Phases 2–5: it runs in the `adopt` lane (xref:02-planning-lanes-phases-3-4.adoc#adopt-lane[Adopt Lane (`pr`)]), `init.ready` enters `finalize.adopt-pr`, which adopts the pull request's head branch, and the plan runs Phase 6 (<<_plan_source_contracts>>).

A plan in the `light` planning lane does not traverse the Phase 2 states (`refine.baseline-reconcile`, `refine.analyze`, the confidence loop, `refine.qgate`): after the server-side light gate (`init.light-gate`) it enters Phase 3 and runs one collapsed light envelope (`outline.light`) that folds refine without the loop, the Simple outline, and deliverable derivation together, mirroring `plan-marshall`'s light lane. The deep lane keeps the full refine loop -> outline -> plan pipeline. The phase enum is unchanged; how the light envelope satisfies the Phase 2 and Phase 3 artifact gates is specified in xref:02-planning-lanes-phases-3-4.adoc#planning-lanes[Planning Lanes & One-Way Ratchet (`light` -> `deep`)].

=== Model Work per State (Role Tasks)

The server drives every phase. A state that needs no model is server logic (`auto`, `do`, `job`); a state that needs one is a `job llm <entity_kind> role <role> [each <primitive>]` state, which creates one task per entity for the named role, done by a worker of that role through the task protocol (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). The plan representation is a view: it offers no link, and no session drives a plan state. The default units name only roles of the shipped default role set (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]); `implement` is the only writer role among them, so a plan has at most one writer worker, and every other role they name is `read_only` or `zero_tool`.

* *Composition*: A unit that names a role the effective role set does not define is refused when the plan instance is composed (`role_undefined`), never when the state is reached.
* *Closed Outcomes*: A task ends only `submitted`, `asked` (a question record, xref:07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Questions, Waivers & Operator Influence]), `infeasible` (with its evidence), or `lost`. A task that ends without its required submission is offered again within the state's compiled self-remedy budget; then the task closes `lost` and the state takes the fallback its row names (last column), else the fallback of its position. No task ends a plan, and no plan state offers a `hand_back` or `step_out` link: a plan ends early only through a server rule or a closed decision a task submits where its state offers one (the `return` of a refuted hypothesis, the `hand_back` of the infeasible review).
* *Unqualified Roles*: While a role has no valid qualification record, its tasks are not served; the state takes the fallback of the last column, the task is recorded with the reason `role_unqualified`, and no question reaches the operator (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]). In the shipped set `replan`, `triage-build`, and `triage-ci` are unqualified, so an infeasible deliverable hands the plan back and a build or CI failure gets its one `retry` before the fallback.
* *Evidence in Facts*: The facts of every decision task of a phase (`refine.hypothesis-refuted`, `execute.infeasible-review`, the triage, and every `decide`) carry the evidence the decision rests on, by the rule of link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Envelopes, Questions & Deadlines]: the claims and their artifacts, the infeasible deliverables with their evidence and server-computed dependents, the findings, and the structured failures with their budgets.

=== Plan Outcomes, Fallback Routes & Remediation Policies
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-90[PM-WATCH-PHASE-90], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-75[PM-WATCH-PHASE-75], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-91[PM-WATCH-PHASE-91]_

The process enforces itself: a plan asks the operator nothing while it runs, and its gates are process conformance, not security. Every blocking condition has a bounded self-remedy and, when that is spent, a defined fallback to one of the fallback outcomes `handed_back` and `returned`. The operator influences a running plan only through waivers and the operator verbs (xref:07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Questions, Waivers & Operator Influence]); the only pause is a critical integrity breach.

[cols="1,1,4"]
|===
|Outcome |Terminal state |Meaning

|`merged`
|`completed`
|The plan's pull request merged (`merge_outcome: merged`).

|`handed_back`
|`handed_back`
|The work is delivered as an open pull request (a draft after a fallback, ready for review when the operator's merge policy `merge.auto_merge` is `false` and the pre-merge barrier passed, `merge_outcome: awaiting_human_merge`) or, without a push remote or pull request, as a branch; the gaps are documented in an idempotent pull-request comment and the label `pm-mcp:handed-back`.

|`returned`
|`returned`
|Only the planning result exists; nothing was implemented, no branch and no pull request are left behind, and the planning artifacts are archived.

|`no_change`
|`completed`
|A recipe run whose harvest yielded no targets: nothing to change, no commit and no pull request (`merge_outcome: no_pr`, fact `empty_harvest`); not a fallback.
|===

An empty harvest reports `no_change`, never `merged`; `no_change` keeps "nothing merged" distinct from a merge in the landing and the metrics. Both outcomes end in the terminal `completed`, declared `terminal merged success`; that declared outcome id is nominal, and the plan's `outcome` field is authoritative.

The landing record carries `outcome: merged | handed_back | returned | no_change | aborted` beside the `merge_outcome`; `aborted` is reached only by the operator (below). Every outcome other than `aborted` is reached only through `finalize.archive-plan` after the post-run band, so metrics, the landing, and the archive run for every ending.

*Fallback Route per Position*:

* *Begun Steps*: The transaction that enters `plan.return`, `finalize.hand-back`, or `plan.aborted` records every begun, unsettled step `failed`.
* *Gap Record*: A fallback records its gap (gate, policy, evidence summary, and `cause`: `exhausted` with the spent budget, `stepped_out` with the server's step-out cause, `decided` with the decision task's reason and evidence, `infeasible` with the task's evidence, or the condition that ran out of self-remedy; a gap of a task's fallback names the task and, for a `lost` task, its `task_reason`, for example `role_unqualified`; link:../store-schemas/14-plan-instance-waivers-questions.adoc[Store Schemas Specification, Gap Record]); the landing record and the hand-back comment render it, and the hand-back comment names every waiver request that expired unanswered.
* *Server Step-Out*: Inside a sub-process of a plan (a remediation unit, `git.commit_and_push`) only the server leaves a frame early: when the frame's attempts or bounded retries are spent it returns `stepped_out` with its cause, its caller routes it once, and a phase-level caller routes it to the same fallback as `exhausted`. A step-out consumes no budget and writes no waiver.
* *Operator Abort*: `pm-operator abort plan <plan_id> --reason` moves the plan to `plan.aborted` in its next transaction. `plan.aborted` is entered only by operator `abort`, by `delete-plan`, and by the `abort` resolution of an integrity breach; pending question records close `cancelled`, pending waiver requests `expired`, and the plan's open tasks are withdrawn and their workers ended.
* *Integrity Pause*: A tampered plan or epic store, or a tampered enrolment (every running plan of the project), raises the condition overlay `integrity_breach` (`kind: store_tampered | enrolment_tampered`, the store, recorded and current digest; link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-conditions[State Catalogue, Conditions]). No task of the scope is offered, every `pm_do` is rejected with `integrity_paused`, and `facts.operator_command` names `pm-operator accept-edit` and `pm-operator abort`. The pause is unbounded and has no fallback; it holds the expiry of a pending question or waiver request until it ends. `accept-edit` re-baselines, and the engine re-verifies before clearing the condition.
* *Other Conditions*: Every other engine-raised condition runs its self-remedy, bounded by a compiled per-condition-instance budget (default `3`): the server retries where a retry can clear it, and where clearing it needs judgment or work, it creates a task of the role whose work raised it (for example a `fix` of a footprint violation by the `implement` role); the operator may remove the cause at any time (a missing credential keeps its bounded server `retry`, and `pm-operator status` and the web app name the operator command). A spent budget takes the fallback of the current position with the condition as the gap; where the fallback itself lacks what is missing (no push credential), `handed_back` degrades to the local branch with the gap stated in the landing record.

==== Remediation Policy Calls

The self-remedy of a failure class is an ordinary sub-workflow unit per class (link:../workflow-dsl/08-remediation-units.adoc#remediation-units[Workflow DSL Specification, Remediation Policy Units]): the server gathers the evidence as structured failures (`{failure_id, class, kind, source, file?, line?, message, fingerprint, excerpt_uri?}`; logs and excerpts stay behind untrusted resources `pm://plan/{plan_id}/evidence/{evidence_id}`), and the unit's `decide` chooses from the closed actions `retry` (reason `enum[flaky|infra|timeout]`), `fix` (in-branch only after the pull request exists; before it, at the security-audit and self-review call sites, only in the `loop_back` form), and `request_waiver` (rationale), each validated by the server and bounded by its budget. The decision is a task of the policy's role whose facts carry the evidence and the remaining budgets, and whose submit names one action of the set its representation offers; where the bound budgets and actions leave exactly one action, the server takes it without a task, and where they leave none, the unit ends `exhausted`. Which of these applies is decided at runtime from the bound remedies alone, never by the unit (link:../workflow-dsl/08-remediation-units.adoc#remediation-invariants[Workflow DSL Specification, `INV-REM-7`]). A unit ends with a reachable subset of the domain outcomes `resolved`, `waived`, `exhausted`, `fix_requested`, plus the control outcome `stepped_out`. Every caller routes `resolved` to its continuation, `waived` to the continuation completing the begun step `waived`, `exhausted` and `stepped_out` to the fallback of its position, and `fix_requested` (only where the fix runs in the caller) to its authoring or allocation state, which calls the unit again after the next verification.

|`execute.deliverable-build`, `execute.verify-sweep`, `land.verify-sweep`, `finalize.pre-push-quality-gate` |`remediation.build-failure` |1 / 3 / 0 (land: 1 / 0 / 0) |`triage-build` (land: server) |`handed_back` (`returned` without commits)
|`finalize.concurrent-wait` `ci_failed`, and every other CI red at the merge path |`remediation.ci-failure` |2 / 3 / 0 |`triage-ci` |`handed_back`

* *Budgets*: The defaults are call arguments of the project-owned phase units (team-adaptable), bounded by the compiled hard caps (link:../timeouts/01-job-budgets-and-waits.adoc#remediation-budgets[Timeouts & Budgets Specification, Remediation Budgets]). The plan instance carries the effective ceiling per policy with its source (the unit file's call argument, or the `raise` waiver of `fix_budget` or `retry_budget` that lifted it). The consumed budget is a per-plan, per-class counter of the plan status, persisted and never reset: re-entering a unit, a new `HEAD`, or a re-composed instance continues the same count.
* *Server Checks in `decide`*: `retry` is refused with `retry_not_applicable` when the same failure fingerprints already failed after a retry with the same reason; `fix` is charged in the transaction that submits it, a `no_change` result included (link:../workflow-dsl/08-remediation-units.adoc#remediation-units[Workflow DSL Specification, Remediation Policy Units, Budget accounting]), and a `fix` choice on an unchanged worktree or artifact is refused with `fix_unchanged`; `request_waiver` is offered only when the unit's waiver wait is positive and the failing gate is waivable (non-waivable failures carry `waivable: false` in the evidence). With the shipped waiver wait `0`, a waiver the `decide` task would request goes into the hand-back report instead.
* *The Fix Is a Task*: The work a `fix` needs is a task of the plan's writer role `implement` (remediation tasks of Phase 5, an in-branch fix of the unit, `git.resolve-conflicts`) or of the phase's authoring role (a Q-Gate revision); the `decide` task never edits.
* *Unqualified `decide` Role*: The server takes the unit's `retry` once where its bound budgets offer one, and then, or at once, ends the unit `exhausted`; the task is recorded with the reason `role_unqualified` (<<phase-roles>>).
* *Land Lane*: For a `land` plan the composition binds every policy call with `actions: [retry]`, so `decide` is server logic (`auto`): it retries within the retry budget and then ends the unit `exhausted` (xref:02-planning-lanes-phases-3-4.adoc#land-lane[Land Lane (`local_changes`)]).

=== Phase 1 (`init`): Plan Sources, Phantom-ID Refusal & Classifiers

==== Plan Source Contracts
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-76[PM-WATCH-PHASE-76], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-88[PM-WATCH-PHASE-88], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-92[PM-WATCH-PHASE-92]_

A plan is created by its bootstrap, never by a tool call (link:../state-catalogue.adoc[State Catalogue], Bootstrap). The entry session drives the bootstrap and its source units, the one sub-workflow of a plan's life a session drives; the server itself runs the bootstrap of a plan an epic starts (source `epic_row`). `pm-mcp enter` opens a pending entry (kind, optional id, optional free-text hint of the user's words); the compiled entity unit `bootstrap-plan`, hosted by the workspace scope and addressed with `pm_state` / `pm_do(plan_id: "NO_PLAN", entity: <entry_id>)`, resumes a live plan named by the id and otherwise leads to `start.choose`, whose links are the ways to start. Each source except `request` is gathered by its own sub-workflow unit with the exit contract `done {source record}` or `stepped_out`; the record is kept in the pending entry, so an abandoned entry leaves no plan directory. A new way to start is one more source unit and one more link, never a tool parameter or CLI flag. `start.ready` shows the source summary, the derived `plan_id` (<<_plan_id_derivation_phantom_id_refusal_guard>>), and the commit options (slug, base branch, posture, outline review). The `create` link of `start.ready` runs `start.create-scope`, and the engine creates the plan in that transaction (outcome `created`, bootstrap terminal `start.committed`): the plan directory (`<PM_MCP_BASE>/projects/<project_id>/plans/<plan_id>/`, link:../filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), `request.md`, `references.json`, `mcp/status.json` with `origin.source` (`PlanSource`), `entry_baseline`, and the plan instance version 1; the plan enters `init.classify`. The same transaction re-checks what creation requires (the identifier is free, the lifecycle gate is open or the project is enrolled as a pilot, the configuration is committed and valid, the lesson is unclaimed, the epic row is launchable and not `running`); a failing check creates nothing and returns the entry to `start.ready` with the reason in `facts`. External text a source reads (issue and pull-request title and body) passes the two-level guard in the bootstrap: the deterministic level-1 validator, then the level-2 screening by `screener` tasks over the source's batch; a `suspicious` verdict enters the source unit's link state showing the flagged spans, with `accept` (the text is used, still marked untrusted, and the acceptance is audited) or `back` (link:../model-work/07-untrusted-text-screening.adoc#two-level-guard[Model Work Specification, Two-Level Guard for External Text]).

==== Plan ID Derivation & Phantom-ID Refusal Guard

The server derives or validates `plan_id` against a strict lexical grammar before creating any directory on disk:

1. *Canonical Grammar*: A `plan_id` matches the link:../identifiers/01-general-rules-and-registry.adoc#id-plan-id[`plan_id` grammar] of the Identifier Registry, the single definition of the plan ID grammar; every schema that restates it (`plan_id` tool properties, `scope_id`, queue rows) matches it exactly. A `plan_slug` (link:../identifiers/01-general-rules-and-registry.adoc#id-plan-slug[registry]) becomes the `plan_id` verbatim; without a slug the server derives one from the plan source. Recipe plans are `recipe-{recipe_key}-{yyyy-mm-dd-hh-mm-ss}` (link:../domain-extensions/05-recipes-and-extension-points.adoc#recipe-plan-id[Recipe Plan ID]), which the length bound admits because a `recipe_key` has at most 37 characters (link:../identifiers/01-general-rules-and-registry.adoc#id-recipe-plan-id[registry]). Epic IDs use the same grammar (mirroring `plan-marshall`, which validates the epic slug with its plan-id validator).
2. *Phantom-ID Refusal*: The validator explicitly rejects any candidate `plan_id` or `plan_slug` matching either the link:../identifiers/02-registry-stores-to-web.adoc#id-lesson-id[`lesson_id` grammar] or a UUID / hex-digest pattern (`^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$`, a bare hex string of 12 or more characters `^[0-9a-fA-F]{12,}$`, or a token beginning case-insensitively with `execution-context` or `agent-`). Rejecting these shapes prevents a lesson ID or a session or job UUID from becoming a `plan_id` and a phantom plan directory; a `set_slug` naming such a slug is refused with `invalid_link_args`. A supplied or derived `plan_id` beginning with the reserved prefix `baseline-` is refused as well (link:../identifiers/01-general-rules-and-registry.adoc#id-plan-id[Identifier Registry, `plan_id`]), so no plan worktree can collide with a baseline scratch worktree `baseline-<plan_id>-<sha12>`.
3. *No Reuse While Live or Archived*: A candidate `plan_id` that already names a live plan (`plans/<plan_id>/` of the project's machine store) or an archived plan (`archive/<plan_id>/`, link:../filesystem-layout.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]) is never used for a new plan. The collision is resolved in the bootstrap's `start.ready`, before anything is created: its `facts` show the derived `plan_id` and whether it is free; `set_slug (plan_slug)` re-derives it; a live plan with that id offers `resume:<plan_id>`, an archived one only the rename. The creation transaction re-checks the identifier, and a taken one returns the entry to `start.ready`. Replacing an existing plan is operator deletion (`delete-plan`) followed by a new choice in the bootstrap. Because the archive path carries no date, this rule is what keeps every archived plan addressable by its `plan_id` alone. After `delete-plan` or an archive purge the identifier is free again, while the plan's branch, pull request, and capture ref `refs/pm-mcp/captures/<plan_id>` may still exist on the remote or in the repository; a new plan with the same identifier then collides with them at its first push, pull-request creation, or capture, which ends in that step's own failure route, never in a silent reuse.

==== Deterministic Init Classifiers & Workflow Settings
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-1[PM-WATCH-PHASE-1]_

During `init.classify`, the engine executes pure, model-free classifiers in a fixed order. A classifier that needs an answer raises a *server-raised question record* (xref:07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Questions, Waivers & Operator Influence]) with server-owned options and a declared expiry fallback; `init.classify` is re-entrant: every init answer (including the recipe candidate options `recipe_1` to `recipe_N`, each labelled with its recipe key, and `skip_recipe`) records the answer and returns to `init.classify`, which raises the next unanswered question in the fixed order recipe candidate, sibling collision, domain choice, never re-asks an answered question, never rewrites a write-once output, and exits to `init.ready` only when no init question is open. The stop answer of `init.sibling-collision` is an ordinary option whose effect is the `returned` route (`plan.return`, <<plan-outcomes>>). The lesson premise is no init question: it is checked in the bootstrap before the plan exists (source `lesson`, <<_plan_source_contracts>>), so an obsolete lesson creates no plan. *Deliberate change vs. `plan-marshall`*: its `rename` answer (delete the plan and restart init) does not exist; the stop answer of `init.sibling-collision` followed by a new bootstrap covers it.

1. *Recipe Match before Lane Routing*: For the sources `request`, `issue`, and `lesson` (`recipe` binds its recipe; `local_changes`, `pr`, and `epic_row` are not scored), the registry-wide recipe scorer evaluates the request narrative first; scoring always runs, and the operator's `recipes.auto_route` (`local-config.json`) only chooses between auto-routing (when `true` and the top confidence reaches the compiled auto-route threshold `0.6`, `plan-marshall`'s default, not configurable) and asking in `init.recipe-candidate` (link:../domain-extensions/05-recipes-and-extension-points.adoc#_tier_1_init_routing_deterministic_deliverable_generation[Domain Extensions Specification, Tier-1 Init Routing]). In the same step the server computes the Tier-1 request-aspect classification (`status.metadata.request_aspect`) and, for source `lesson`, the doc-shaped predicate that routes a doc-shaped lesson to the `lesson-cleanup` recipe (items 9 and 10 there). An explicit `recipe` source selection is never overridden by the scorer.
2. *Initial Planning-Lane Router*: Computes the initial `planning_lane` (`light` or `deep`) from the request with zero discovery (`deep` for every plan when the team's `workflow.json` `plan.phase-1-init.minimum_lane` is `deep`, xref:02-planning-lanes-phases-3-4.adoc#planning-lanes[Planning Lanes & One-Way Ratchet (`light` -> `deep`)]), and the pre-route `scope_estimate` (`none`, `surgical`, `single_module`, `multi_module`, `broad`). `scope_estimate` is derived from expected-modification paths only; read-only references never raise it. The pre-route value is persisted immutably as `scope_estimate_pre_route`; every later update of `scope_estimate` (Phase 2 or Phase 3) records its own provenance under `scope_estimate_provenance[]` instead of overwriting the pre-route evidence.
3. *Sibling Collision Detector*: Scans live plans for overlapping target modules or affected file paths; if an overlap is found, it raises the `init.sibling-collision` question (`proceed`, or stop, which ends the plan `returned`); its expiry fallback is `proceed`.
4. *Workflow Settings Resolution*: Reads the project's effective configuration (link:../store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]): the team's `minimum_lane` (xref:02-planning-lanes-phases-3-4.adoc#planning-lanes[Planning Lanes & One-Way Ratchet (`light` -> `deep`)]), `compatibility`, and `simplicity`, and the operator's `recipes.auto_route`, `merge.auto_merge` (whose `false` the plan instance carries as the merge execution pruned with reason `auto_merge_off`), and `questions.*` keys; takes the execution posture (`minimal | standard | full`) from the plan's posture fact, recorded at creation from the commit option of `start.ready` or, without one, from the server projection. The posture is a plan fact, never a question: its effect, the steps pruned with reason `posture`, is composed into instance version 1 at creation (composition event `start`) with its provenance, so the posture preview is the diagram of version 1 (xref:02-planning-lanes-phases-3-4.adoc#plan-instance-composition[Plan Instance Composition]); floor immunity keeps every mandatory step whatever the value. No setting stops a plan between phases: the server runs every plan to its outcome. *Deliberate change vs. `plan-marshall`*: the five auto-continue flags (`init_`, `plan_`, `execute_`, `finalize_`, `loop_back_without_asking`), the `lane_selection` prompt switch, and the posture question do not exist. The refine confidence threshold (`95`), the recipe auto-route threshold (`0.6`), the lane prune thresholds, and the hard caps of the remediation budgets are compiled constants.
5. *Base Stamp*: Stamps `main_sha` in `mcp/status.json` from `git rev-parse origin/<base_branch>`. It is written once here and re-stamped only by the `sync-baseline` and `branch-cleanup` rebases. Before Phase 5 a drift of `main_sha` is informational only (rendered in `facts`, never refusing); from Phase 5 on the exit-barrier freshness gate and the merge-path rebase act on the base.

At `phase-4-plan` entry the lane predicate is re-evaluated with the settled inputs (declared deliverables and their expected modifications) and the result is logged as `lane_reevaluation` in `audit.jsonl`; the re-evaluation never re-routes the plan (see xref:02-planning-lanes-phases-3-4.adoc#_lane_ratchet_rules[Lane Ratchet Rules]).

=== Phase 2 (`refine`): Quality Aggregation, Domain Widening & Bounded Relaunch

The Phase 2 states run for `deep`-lane plans only (including a plan ratcheted from `light` to `deep`). A `light`-lane plan never enters `refine.analyze` or its confidence loop; its refine work is folded into the collapsed light envelope (xref:02-planning-lanes-phases-3-4.adoc#planning-lanes[Planning Lanes & One-Way Ratchet (`light` -> `deep`)]).

==== Phase Entry & Baseline Reconciliation
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-2[PM-WATCH-PHASE-2], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-86[PM-WATCH-PHASE-86]_

At `phase-2-refine` entry, the engine caches loop-invariant inputs (`request.md`, `references.json`, and the architecture module inventory with its overview, link:../domain-extensions/03-module-discovery.adoc#_server_owned_module_discovery_enrolled_discovery_jobs[Domain Extensions Specification, Server-Owned Module Discovery]) so they are read once per phase rather than re-read inside the confidence loop. When a base branch is configured, `refine.baseline-reconcile` runs a non-mutating merge-conflict probe against upstream and classifies drift into three outcomes:

* `no_overlap`: Upstream commits touch disjoint files; advances directly to `refine.analyze`.
* `overlap_no_content_conflict`: Overlapping files merge cleanly; records `auto_reconcilable: true` without mutating the tree (deferring the actual rebase to Phase 5/6) and advances to `refine.analyze`.
* `overlap_with_content_conflict`: Content conflicts exist; emits blocking Q-Gate findings so the conflict is absorbed during request refinement.

* *Probe Variants*: The probe is one operation of the git contract with both variants. The native variant merges in memory with JGit's `ResolveMerger` and takes the conflicted paths from its merge result; nothing is written to the object database or the worktree. The CLI variant runs `git merge-tree --write-tree --name-only -z` with `LC_ALL=C` and reads only the conflicted-file section; informational and message lines are never paths, and the locale pin applies to this probe only. In both variants the conflict count is the number of distinct conflicted paths.
* *Overlap Population*: Overlap is computed between the upstream changed paths and the plan's declared ∪ derived footprint known at that point, never only the in-flight diff (which is empty before execution), so a first Phase 5 entry never reports `conflict_count: 0` merely because nothing was written yet.
* *Drift Routing*: Content overlap (`overlap_with_content_conflict`) is the only drift routed to refinement. A `main_sha` ancestry drift is informational before Phase 5 and is cleared only by a sync or rebase transition; a refine relaunch is never offered as its remedy, and no operator override exists.

==== Five Quality Dimensions & Fixed-Weight Confidence Aggregation
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-6[PM-WATCH-PHASE-6], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-68[PM-WATCH-PHASE-68]_

During `refine.analyze`, a `job llm` state of role `refine` (<<phase-roles>>), the refine task executes source-premise verification (checking cited files, flags, and APIs against the codebase) and proposed-fix verification (constructing a semantic probe to verify whether a proposed fix resolves the stated symptom), maps affected modules, estimates scope (`none`, `surgical`, `single_module`, `multi_module`, `broad`), authors a conventional-commit `pr_title` ($\le 72$ characters, distinct from the human plan `title`), and submits raw scores (`0..100`) for the five quality dimensions plus architectural module mapping.

* *Premise Verdicts*: Source-premise verification records each premise with the verdict record of epic Spec Re-Grounding (link:../model-work/08-epic-coordination.adoc#_server_derived_landing_facts_spec_re_grounding_cross_plan_locks[Model Work Specification, Verdict Record]): label `observed` or `hypothesis`, verdict `corroborated | contradicted | partially_exercised | unverifiable`, and `scope_change` (`none | rescoped`); no second vocabulary exists. A command flag mandated by the request is a premise and must name a module of the command's actual reactor that the flag affects.
* *Open Hypotheses of Epic Plans*: For a plan its epic started (source `epic_row`), every `hypothesis`-labelled claim of its spec section is surfaced in `facts.open_hypotheses`. `submit:refine` must carry a verdict per claim (`confirmed` or `refuted`, citing the named artifact), and any `refuted` claim routes to `refine.awaiting_answers` for re-scoping instead of `refine.ready`; that pass counts as the one refine relaunch. A claim refuted again in the second pass routes to `refine.hypothesis-refuted`: the server appends a `hypothesis_refuted` event (claim, evidence, plan) to the epic inbox and creates a task of role `refine`, whose facts carry the claim, both refutations with their cited artifacts, and the spec section; its submit names one decision of the closed set its representation offers: `continue_narrowed` (`narrowed_scope: text[1..2000]`) enters the `auto` state `refine.apply-narrowing`, whose primitive writes the intent amendment (`source: model`, listed in the pull-request body and the landing record) and continues to `refine.ready`; `return` (`reason: text[1..2000]`) ends the plan `returned` (gap `cause: decided`), so the epic re-stages it with a corrected premise; while `refine` is unqualified the state takes `return`. There is never a third refine pass.

The server-side `ConfidenceAggregator` computes the overall confidence deterministically using fixed weights (zero LLM arithmetic):

[cols="2,1,4"]
|===
|Dimension |Fixed Weight |Verification Criteria

|`correctness`
|20%
|Technical validity of referenced modules, APIs, flags, source premises, and proposed fixes against the live architecture.

|`completeness`
|20%
|Presence of clear scope boundaries, acceptance criteria, test expectations, and cross-module dependencies.

|`consistency`
|20%
|Absence of internal contradictions or conflicting constraints across request sections and architecture rules.

|`non_duplication`
|10%
|Absence of redundant or overlapping requirement statements.

|`ambiguity`
|20%
|Single unambiguous interpretation of terminology, target scope, and measurable outcomes (`100` = unambiguous).

|`module_mapping`
|10%
|Confidence in mapping the request to concrete project modules and dependency directions.
|===

$$\text{confidence} = \lfloor 0.20 \cdot S_{\text{corr}} + 0.20 \cdot S_{\text{comp}} + 0.20 \cdot S_{\text{cons}} + 0.10 \cdot S_{\text{nondup}} + 0.20 \cdot S_{\text{ambig}} + 0.10 \cdot S_{\text{mod}} \rfloor$$

* All six dimensions are required parameters of `submit:refine`; a submission omitting one is rejected with `invalid_link_args`, so no absent score is ever folded into the aggregate as `0`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` scores the dimensions discretely (`100` on pass and `0` on an issue; completeness `100`/`50`/`0`; non-duplication `100`/`80`); `PM-MCP` accepts each dimension as `int[0..100]`.
* *Evidence Class*: `submit:refine` carries `evidence_class` (`self_assessment`, `operator_answered`, or `downstream_reproduced`), persisted beside the score and shown in `facts`. The server checks it against its records: `operator_answered` is refused (`invalid_link_args`) unless a `refine.awaiting_answers` round of this plan has at least one answer given through a human channel (`web` or `session`; an `assumption` or `model` answer does not count), and `downstream_reproduced` requires an `evidence_ref` naming the reproducing artifact (a build job, test run, or re-grounding verdict). No heuristic fires on an all-100 score by itself: only `self_assessment` with every dimension at `100` on a plan no epic started adds the advisory fact `self_assessed_full_confidence` (never blocking, never a link change), while an all-100 score on an emitted plan's pre-verified specification is expected and adds nothing.
* *Server Checks on Every Submission*: For every deep plan, `submit:refine` is refused with `invalid_link_args` when its module mapping names a module that the architecture module inventory does not know, or maps no module for an expected modification (module-mapping existence, blocking). The consistency of `scope_estimate` with the lane is checked where a `light` plan records an estimate (a ratchet trigger, xref:02-planning-lanes-phases-3-4.adoc#_lane_ratchet_rules[Lane Ratchet Rules]); a deep plan is never ratcheted down. *Deliberate change vs. `plan-marshall`*: its refine Q-Gate also judges scope realism and confidence justification on every plan; both are dropped, because the fixed-weight `ConfidenceAggregator` and the evidence class cover them.
* The aggregated score is persisted to `status.metadata.confidence` and compared against `confidence_threshold`, the compiled constant `95` (not configurable: lowering it would only admit less-clarified requests). *Deliberate change vs. `plan-marshall`*: its `confidence_threshold` is a project setting (default `95`).
* The server also validates that `compatibility` (`breaking | deprecation | smart_and_ask`, compiled default `breaking`) and `simplicity` (`lean | pragmatic | defensive`, compiled default `lean`) are resolved from the effective configuration and persisted in the plan.

==== Widen-Only Domain Re-Merge
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-67[PM-WATCH-PHASE-67]_

Once concrete `affected_files` are identified in `refine.analyze` (for a `light`-lane plan: on acceptance of the light envelope's submission, before the single narrowing pass of Phase 3), the server runs `domain-detect` over those file paths (`file_globs` and `always_on` inclusion legs) and computes the set union with the existing `references.domains`:

$$\text{domains}_{\text{new}} = \text{domains}_{\text{cached}} \cup \text{detect}(\text{affected\_files})$$

* *Monotonic Widening Invariant*: Phase 2 may **only widen** `references.domains`, never narrow it, ensuring convergence across refine iterations. If `affected_files` produce zero narrative or glob matches, `domain-detect` returns all offerable domains under `reason = "over_provisioned_resolve"`; that temporary over-provisioning is narrowed exactly once in Phase 3 after deliverables are declared.
* *Match Provenance*: `domain-detect` returns, per domain, its `source` (`always_on`, `glob`, or `narrative`) and `matches: N`, rendered in `facts`. A result resting only on `always_on` legs with zero matches is reported `floor_only`, never as a confident single-domain answer.

==== Single-Batch Clarification & Relaunch Ceiling

If $\text{confidence} < \text{confidence\_threshold}$:

1. The refine task submits its best-judgment `clarified_request` alongside a single batched `refine_prompt` (`questions:list<schema[question-envelope]>?`, xref:07-questions-waivers-operator-influence.adoc#phase-question-envelope[Question Envelope Schema]) containing at most 4 clarification questions prioritized by `Correctness > Consistency > Completeness > Ambiguity > Non-Duplication`.
2. The engine records each question as a question record (class `clarification`, xref:07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Questions, Waivers & Operator Influence]), transitions to `refine.awaiting_answers`, and waits for the batch on the server-owned deadline of the plan's question mode (xref:07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Questions, Waivers & Operator Influence]); a question still open at expiry is recorded with its `default_assumption`.
3. When every question of the batch is answered or assumed, the engine writes the `## Clarifications` and `## Clarified Request` sections, increments `refine_relaunch_count` in `mcp/status.json`, and creates a new `refine.analyze` task **at most once** (`refine_relaunch_count <= 1`).
4. If the second pass still yields $\text{confidence} < \text{confidence\_threshold}$, the engine does **not** loop again (a hypothesis refuted again goes to `refine.hypothesis-refuted` instead, see Open Hypotheses of Emitted Plans); it flags `low_confidence_manual_review: true` in `facts` and advances to `refine.qgate` for a lesson-derived plan, otherwise to `refine.ready`.
5. A remediation pass of `refine.analyze` requested by the Q-Gate policy (`fix_requested` of `remediation.qgate-findings`, xref:03-q-gate-and-execute.adoc#_q_gate_validation_loop[Q-Gate Validation Loop]) is never counted by `refine_relaunch_count` and never opens a new `refine.awaiting_answers` round; its questions and a below-threshold score are recorded as `low_confidence_manual_review`.
