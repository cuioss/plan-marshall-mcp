[#planning-lanes]
== Planning Lanes & One-Way Ratchet (`light` -> `deep`)

`PM-MCP` routes the planning pipeline (Phases 2–4) along one of two structural lanes stored in `status.metadata.planning_lane`, which deterministically drives the legacy `track` field (`light => simple`, `deep => complex`). The lane is the structural selector for the whole Phase 2–4 pipeline, mirroring `plan-marshall` (`plan-marshall/workflow/planning.md` § Planning-lane dispatch and `phase-3-outline/workflow/light-lane.md`; re-verify before implementing): a `light` plan runs one collapsed light envelope, a `deep` plan runs the full refine loop -> outline -> plan pipeline.

[cols="1,2,4"]
|===
|Lane |Target Scope |Discovery & Execution Contract

|`light`
|Bounded, localized changes (`scope_estimate` in `{surgical, single_module}` with known target files)
|Skips the Phase 2 states. After the server-side light gate (<<light-gate>>) passes, runs *one* collapsed light envelope (`outline.light`) that folds refine without the confidence loop (clarified request, `pr_title`, minimal premise check over the bounded read set, no clarification iteration, no confidence scores), the Simple outline, and deliverable derivation. The envelope reads only the bounded read set the server computed: the declared affected files plus their one-hop neighbours (*Total Read Set Cap* `cap = 25`, *Declared-File Band* `band = 8`). No Q-Gate runs.

|`deep`
|Codebase-wide, multi-module, architectural, or uncertain changes
|Runs the full Phase 2 refine loop (`refine.analyze`, the confidence loop, lesson Q-Gate), then full domain discovery, ADR progressive-disclosure scan (`manage-adr scan`), consumer sweeps for symbol renames/deletions, and full Q-Gate verification (`outline.deep`).
|===

The closed `planning_lane` enumeration also holds the lanes `land` (source `local_changes`, <<land-lane>>) and `adopt` (source `pr`, <<adopt-lane>>). Both are fixed by `pm_start`, skip the planning pipeline, and stand outside the ratchet below.

[#light-gate]
=== Light Gate: Deterministic Budget Trigger

The budget trigger is the primitive `lane.budget-check`, computed by the server before the light envelope is dispatched. Two `auto` states run it: `init.light-gate` (in `phase-1-init`, entered from `init.ready` for a `light` plan only) and `outline.light-regate` (in `phase-3-outline`, entered from `outline.review` on a change request for a `light` plan, before every re-dispatch of `outline.light`); a revision never re-enters a Phase 1 state (link:../state-catalogue/02-plan-phases-1-3.adoc#state-outline.light-regate[State Catalogue]). It never reads a sub-agent file-read counter: the server cannot observe host reads, so the bound is decided over the declared and resolved file set before any model work.

1. *Declared Affected Files `A`*: On the first dispatch, the explicit repository-relative paths named in the request (the same path extraction the initial lane router uses; the gate never discovers files the request did not name). On a re-dispatch after revision, the `Affected files` of the current `outline.md`.
2. *One-Hop Neighbours*: For each file of `A`, the server reads the file-level neighbours resource `pm://architecture/files/{path}/neighbours` (link:../domain-extensions/03-module-discovery.adoc#_architecture_query_resources_pmarchitecture[Domain Extensions Specification, Architecture Query Resources]: the file's own resolved imports, its paired test or production file, and its owning module), and adds the owning module's descriptor; exactly one hop, never transitive, never a content search. `neighbours` is the resolved set minus `A`.
3. *Budget*: The plan escalates to `deep` when `|A| + |neighbours| > 25` (cap) or `|A| > 8` (band); `escalation_trigger` records `budget_cap` or `budget_band` with both counts.
4. *Fail Toward the Safe Lane*: When the neighbours of any file of `A` cannot be resolved (architecture inventory absent, file not attributed to a module, or a resource answering `indeterminate` or an error), the plan goes `deep` with `escalation_trigger: neighbours_indeterminate` and `facts` naming the unresolved files and the reason. An unresolved neighbour set is never counted as empty, and an empty `A` is unresolved, not bounded.
5. *Baseline Probe*: Because a light plan never enters `refine.baseline-reconcile`, the gate runs the same non-mutating probe (xref:01-planning-phases-1-2.adoc#_phase_entry_baseline_reconciliation[Phase Entry & Baseline Reconciliation], probe variants and overlap population unchanged). `overlap_with_content_conflict` sends the plan `deep` (`escalation_trigger: baseline_conflict`), since content conflicts are absorbed during refinement, which only the deep lane runs; the other outcomes are recorded as on the deep lane.
6. *Record*: The gate records `A`, `neighbours`, both counts, and its outcome in `audit.jsonl` (`lane_budget`). On pass, `A ∪ neighbours` is handed to the envelope in `facts.light_read_set` as its read bound.

[#light-envelope]
=== Collapsed Light Envelope (`outline.light`) & Artifact Gates

When the light gate passes, the plan moves to `phase-3-outline` with `phase-2-refine` recorded as collapsed (`status.metadata.phase_2_mode = collapsed_light`, not yet `done`), so the envelope's spend is attributed to `phase-3-outline`. `outline.detect-change-type` runs as on the deep lane (the heuristic scores `original_input`, since no clarified request exists yet), then the server dispatches `outline.light`. The phase artifact gates apply to light plans unchanged; the collapsed envelope satisfies them as follows:

* *Clarified Request and `pr_title` (Phase 2 exit gate)*: The envelope's `submit:outline` carries `clarified_request: text[1..32768]`, `pr_title` (conventional commit, `<= 72` characters), and `outline: text[1..65536]`. A light submission missing `clarified_request` or `pr_title` is refused with `invalid_link_args`. On acceptance the server writes `request.md` `## Clarified Request`, `status.metadata.pr_title`, and `outline.md` in one transaction and records `phase-2-refine` `done`. The light envelope is thereby the `pr_title` producer on its own path (link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, rule 8]); the Phase 3 arrival requirement for `pr_title` is evaluated on this submission.
* *Validated `outline.md` (Phase 3 exit gate)*: The submission passes `OutlineValidator` exactly as on the deep lane (<<_phase_3_outline_validation_rules_outline_review_gate>>), after the widen-only domain merge over the declared files and followed by the single narrowing pass.
* *Operator Outline Approval*: `outline.review` follows unchanged and remains an operator-authorizing decision; the light lane never approves its own outline. A revision requested there enters `outline.light-regate`, which re-runs the budget check over the outline's `Affected files` and re-dispatches `outline.light` on pass (a failing check ratchets the plan to `deep`).
* *Judgment Escalation*: Instead of an outline, the envelope may submit `outcome = escalate_to_deep` with `escalation_trigger` (`premise`, `cross_module_ripple`, or `public_symbol_deletion`) and a rationale; nothing of the envelope is persisted besides the escalation record.

=== Lane Ratchet Rules

1. *Unknown Scope Bias*: At initial routing, an unknown or unresolved `scope_estimate` biases fail-safe to `deep`. Conversely, an unset `change_type` does **not** force `deep` when `scope_estimate` and target files are bounded.
2. *One-Way Escalation (`light -> deep`)*: The engine ratchets a `light` plan to `deep` (locking `planning_lane = "deep"`, `track = "complex"`, `lane_escalated = true`, and `escalation_trigger` permanently for the plan) whenever either the *Deterministic Budget Trigger* fires in the light gate (<<light-gate>>, including `neighbours_indeterminate` and `baseline_conflict`) or the *Judgment Escalation Trigger* fires (the envelope submits `outcome = escalate_to_deep` because it found a false request premise, cross-module ripple effects, or public symbol deletions requiring a full consumer sweep). The escalation is a first-class engine transition into `refine.baseline-reconcile`: from `init.light-gate` the plan enters Phase 2 normally; from `outline.light` or `outline.light-regate` the collapsed Phase 2 record is superseded (`phase_2_mode = full`), the phase is set back to `phase-2-refine`, and the deep pipeline runs fresh.
3. *No Down-Ratchet*: No transition exists from `deep` to `light`. Even if Phase 3 discovery later narrows `scope_estimate` from `multi_module` to `surgical` (which may enable the Q-Gate surgical bypass), `planning_lane` remains `deep`.
4. *Minimum Lane (team configuration)*: The only lane setting is the team key `plan.phase-1-init.minimum_lane` in `.marshall/config/workflow.json` (`light` default: the initial router decides; `deep`: every plan runs the deep lane, `plan-marshall`'s `deep_lane: always`). *Deliberate change vs. `plan-marshall`*: a forced `light` lane (`deep_lane: never`) and switching off the escalation ratchet (`plan.phase-1-init.escalation`) do not exist, because they can only skip a check the router or the ratchet would run; the ratchet always applies. A `deep` minimum is recorded in `audit.jsonl` as the lane decision's reason. The recipe auto-route threshold `0.6` is a compiled constant.

[#land-lane]
== Land Lane (`local_changes`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-77[PM-WATCH-PHASE-77]_

A plan started with `local_changes` lands changes the user already made; it has no model implementation work. Its lane `land` stands next to `light` and `deep` but is not part of the planning lane ratchet: it is fixed by `pm_start` and never converts to `light` or `deep`, and no plan converts into it. Its states are catalogued in the link:../state-catalogue/03-plan-phases-4-5-land.adoc#state-catalogue-land[State Catalogue, Land Lane: `land`].

1. *Init*: `init.classify` runs the sibling collision detector over the captured paths and resolves the workflow settings; the recipe scorer and the planning-lane router do not run. `status.metadata.pr_title` is set from `summary`; without a `summary` it is derived from the `plan_id` and marked `pr_title_stale`, so `create-pr` requires the retitle submission. The execution manifest is composed by the shared manifest resolver (<<_shared_execution_manifest_posture_preview_resolver>>) over the captured footprint, with no tasks.
2. *Skipped Work*: The plan skips `phase-2-refine`, `phase-3-outline`, `phase-4-plan`, and the task work of `phase-5-execute` (no deliverables, tasks, envelopes, or chain-tail commits).
3. *Verification*: `land.worktree-init` creates the plan's branch at the capture's snapshot commit and its worktree as `execute.worktree-init` does, restores the main checkout's captured paths where their digest still matches, and re-records `entry_baseline` (the capture mechanic of the `local_changes` source, xref:01-planning-phases-1-2.adoc#_plan_source_contracts[Plan Source Contracts]). `land.verify-sweep` then runs the verification of execute's exit over the captured footprint: the `manifest.phase_5.verification_steps` with the footprint-driven scope and relocation override (xref:03-q-gate-and-execute.adoc#_whole_tree_verification_gates_triage_required_routing[Whole-Tree Verification Gates & `triage_required` Routing]), baseline-red separation, and the footprint check that the realized footprint of the worktree equals the captured `declared_files`. The `land.*` states run in phase `phase-5-execute` (`mcp/status.json` `phase`). `land.exit-barrier` evaluates the Phase 5 exit barrier (xref:03-q-gate-and-execute.adoc#_phase_5_exit_barrier_dual_freshness_pending_tasks_gates[Phase 5 Exit Barrier: Dual Freshness & Pending-Tasks Gates]) with zero tasks; the clean-tree and freshness gates apply unchanged. The plan then enters `phase-6-finalize` with every guarantee: step verdicts and verdict currency, the pre-merge barrier, the merge record, and the landing.
4. *Failures Without Task Allocation*: A failed verification enters `land.verification-feedback`, which files the failures in `findings.jsonl` and offers only `escalate` (decision kind `land-verification-failed`: `recapture`, executed by the `auto` state `land.recapture`, or `abort-plan`, which enters `plan.aborted`) and `abort` (the request `abort-plan`), plus `recapture` once the user has fixed the changes. In `phase-6-finalize` a `land` plan is never offered `loop_back` and never settles a `FIX` in-branch: where another plan would loop back, it offers `escalate` and `abort` only, and the `recapture` link.
5. *Recapture*: `recapture` (rel `fix`, no free parameters, primitive `land.recapture-changes`, also run by `land.recapture` on the operator's approval) re-derives the footprint server-side from the main checkout (a new `captured_changes` with `recapture_count` incremented, the updated `declared_files` and `request.md` change set), carries the changes onto the plan's branch with the capture mechanic (a new snapshot commit on the plan branch, the capture ref moved to it, the main checkout's captured paths restored where their digest matches), and re-enters `land.verify-sweep`; finalize steps re-run as verdict currency decides (xref:06-finalize-re-entry-and-merge.adoc#_re_entry_head_at_completion_verdict_currency_rules[Re-Entry & `head_at_completion` Verdict Currency Rules]). A recapture that finds no change set is refused with `no_local_changes`.
6. *Capture Ref Retention*: `refs/pm-mcp/captures/<plan_id>` is removed only when the plan's `merge_outcome` is `merged`, in the post-merge band after `switch-and-pull` has confirmed the tree equality of the carried commits with the landed base. Every other ending (`aborted`, `declined`, `dequeued`, `enqueued_not_landed`, and `delete-plan`) keeps the ref and writes the owed item `capture_ref_retained` (link:../store-schemas/03-findings-and-review-records.adoc#owed-item-record[Store Schemas Specification, Owed Item Record]), so the user's captured changes stay recoverable. The operator removes a retained ref with `pm-mcp operator drop-capture <plan_id>` (link:../cli-and-security/02-credentials-and-operator.adoc#operator-drop-capture[CLI & Security Specification]); the recovery sweep never touches it.

[#adopt-lane]
== Adopt Lane (`pr`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-76[PM-WATCH-PHASE-76], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-84[PM-WATCH-PHASE-84]_

A plan started with `pr` repairs an existing pull request; it has no planning work. Its lane `adopt` is, like `land`, fixed by `pm_start`, outside the planning lane ratchet: it never converts to `light` or `deep`, and no plan converts into it.

1. *Init*: `init.classify` runs the sibling collision detector over the pull request's changed paths (`declared_files`) and resolves the workflow settings; the recipe scorer and the planning-lane router do not run. `init.ready` routes by the lane alone into `finalize.adopt-pr`. The execution manifest is composed at init by the shared manifest resolver (<<_shared_execution_manifest_posture_preview_resolver>>) over `declared_files`, with no tasks.
2. *Verification*: the plan's verification is the finalize pipeline itself: `pre-push-quality-gate` (`10`) over the whole tree and the push freshness gate of `default:push` (`11`, applied when a push is required).
3. *Baseline Sync Checks Only*: `sync-baseline` (`3`) never rebases an adopted branch: it fetches, records `upstream_commit_count`, and completes with `action` `noop` or `check`. A rebase happens only in `finalize.merge-sync` under the rule of xref:06-finalize-re-entry-and-merge.adoc#merge-path[Merge Path (`branch-cleanup`)], item 3, with the explicit lease and the handling of item 3 there.
4. *Ending*: an open pull request is never closed by the plan (`hand-back` at `archive-plan`, Step Catalogue row `1100`).

== Phase 3 (`outline`): Validation Rules & `outline.review` Gate
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-4[PM-WATCH-PHASE-4], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-5[PM-WATCH-PHASE-5]_

When the model submits the solution outline (`outline.md`) in `outline.light` or `outline.deep`, the submit primitive validates it before accepting the transition; validation is not a state of its own, and a rejected submission leaves the plan in the submitting state with `rejected.reason = "invalid_link_args"`. The server-side `OutlineValidator` enforces four structural invariants and validates each deliverable's optional `Added dependencies` section (§ 5):

=== 1. Per-File Intent Marker Validation
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-3[PM-WATCH-PHASE-3], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-65[PM-WATCH-PHASE-65]_

Every entry under a deliverable's `**Affected files:**` list must carry an explicit trailing parenthesized intent marker from a closed 5-value enum:

[cols="1,2,3"]
|===
|Intent Marker |Syntax Example |Pre-Execution `files_exist` Gate Semantics

|`read`
|``- `src/main/java/Foo.java` (read)``
|Consulted as read-only reference. The `files_exist` gate is satisfied when the path (after glob expansion) exists on disk, or when a deliverable in the transitive `depends:` closure declares it `write-new`; a glob is judged on its expansion, never on the literal. Recorded in `references.json` under read-only references, disjoint from expected modifications.

|`write-new`
|``- `src/main/java/Bar.java` (write-new)``
|Created fresh by the deliverable; file **must not exist** on disk prior to execution (flags a Q-Gate finding if already present).

|`write-replace`
|``- `src/main/java/Baz.java` (write-replace)``
|Modified in place; file exists on disk and is recorded in the declared modification footprint.

|`write-conditional`
|``- `src/test/resources/baseline.json` (write-conditional)``
|Modified only if a gate named in the deliverable fires (for example a snapshot baseline refreshed only when the snapshot test turns red). The file must exist on disk (same rule as `read`). Stored in `references.json -> derived_files.conditional_modifications`: excluded from the footprint coverage denominator and never reported as `modify_shortfall` when untouched, but inside the scope-creep allow set, so a touch is never a deviation.

|`delete`
|``- `src/main/java/Old.java` (delete)``
|Removed by the deliverable; file **must exist** on disk prior to execution (with the same glob-expansion and `depends:`-closure rule as `read`) and triggers the whole-tree verification gate in Phase 5.
|===

An `Affected files` entry is recognised only as a list bullet anchored at line start (after indentation) whose first token is a back-quoted path; a line that does not match is rejected as `unparsed` with its line number and is never re-scanned from an interior hyphen. The same rule applies to every other path-bearing list of the outline (for example survey lists). The validator publishes `bullets_seen` and `bullets_parsed` per list and fails the submission when they differ. Any `Affected files` line lacking a valid `(read|write-new|write-replace|write-conditional|delete)` suffix is rejected immediately with `rejected.reason = "invalid_link_args"`. Furthermore, if a deliverable changes a default value, constant, or enum member, the *value-change test-sweep rule* requires all existing test files asserting the old value (discovered identifier-first) to be listed in `Affected files` with `(write-replace)`.

=== 2. Six-Bucket File-Type Classifier & `module_testing` Profile Requirement

For each deliverable, the server classifies its write-intent `Affected files` via the domain build extensions into one of six closed file-type buckets and validates the deliverable's declared `profiles[]`:

[cols="1,2,3"]
|===
|File-Type Bucket |Path Composition |Mandatory `profiles[]` Assignment

|`production_only`
|Production source files only
|`[implementation, module_testing]` — `module_testing` is **mandatory**.

|`test_only`
|Test source files only
|`[module_testing]` only.

|`mixed_code`
|Production and test source files (no docs)
|`[implementation, module_testing]` — `module_testing` is **mandatory**.

|`mixed_with_docs`
|Production/test source files plus documentation files
|`[implementation, module_testing]`, with `module_testing` scoped strictly to the code/test paths.

|`documentation_only`
|Documentation or markdown files only
|`[implementation]` only — `module_testing` is **prohibited**.

|`unknown`
|Unclaimed file extension or path
|*Blocks Deliverable*: Emits a blocking finding requiring path correction or build-extension mapping; never silently falls back to `documentation_only`. A path the build map routes as build-neutral (for example `.github/**`) is not `unknown`: it is `no_module` (xref:03-q-gate-and-execute.adoc#_whole_tree_verification_gates_triage_required_routing[Whole-Tree Verification Gates & `triage_required` Routing], Footprint-Driven Scope) and neither blocks the deliverable nor widens a gate.
|===

=== 3. Single Domain Narrowing Pass

Immediately after `outline.md` passes structural validation, the server re-derives the plan's active domain set from the union of all deliverables' declared footprints (`Affected files`) and narrows `references.domains` **exactly once**. This removes any temporary over-provisioned domains introduced during Phase 2's widen-only union before Phase 4 resolves task skills. A narrowing that removes a domain sets `status.metadata.pr_title_stale` (the title was authored for the wider scope).

=== 4. Persisted `outline.review` State (Surviving `/clear`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-58[PM-WATCH-PHASE-58]_

Once the outline and its Q-Gate pass complete, the engine transitions to `outline.review` *while remaining in `phase-3-outline`* (never marking Phase 3 `done` prior to approval). Because `outline.review` is persisted in `mcp/status.json`:

* A session compaction or `/clear` resumes directly at `outline.review` via `pm_state(plan_id)`.
* Advancing from `outline.review` to `phase-4-plan` is always an *operator-authorizing decision* requiring MCP elicitation or `pm-mcp operator decide` on the pending outline-approval decision; no configuration key and no continuation policy approves an outline (a compiled invariant of the `outline` unit, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]). *Deliberate change vs. `plan-marshall`*: its `plan_without_asking` flag, which advanced without approval, does not exist.
* *Dependency Approval*: `outline.review` renders the union of all deliverables' `Added dependencies` sections in `facts` as `added_dependencies[]` (each coordinate with its deliverable; an explicit empty list when the outline adds none). Approving the outline approves exactly these coordinates as the plan's approved dependency set (§ 5), which the pre-merge Dependency Delta Check (xref:05-finalize-review-metrics-descriptor.adoc#dependency-delta[Dependency Delta Check (Pre-Merge)]) verifies.
* If the operator requests changes during `outline.review`, the operator's feedback is persisted as pending Q-Gate findings (`phase = 3-outline`) and the state transitions back to `outline.deep` / `outline.light` to revise the outline (a light plan passes `outline.light-regate`, which re-runs the budget check over the outline's `Affected files` before the envelope is re-dispatched, <<light-gate>>).
* *No Silently Carried Q-Gate Findings*: `outline.review` renders every `phase-3-outline` Q-Gate finding still `pending` in `facts` and, while non-blocking ones remain, offers `accept_nonblocking` (rel `alt`, form `submit`, free `rationale:text[1..2000]`), which records `ACCEPT` with that rationale on every pending non-blocking `3-outline` finding in one transition (the server derives each `resolution`). Blocking findings still need their own triage or revision. The approved advance to `phase-4-plan` is taken only when no `3-outline` finding is pending (Blocking Findings Guard).

=== 5. `Added dependencies` Section
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-60[PM-WATCH-PHASE-60]_

A deliverable that introduces a new third-party dependency names it in an `**Added dependencies:**` list. Each entry is one ecosystem-qualified coordinate from a closed ecosystem set, without a version:

* `maven:<groupId>:<artifactId>` for Maven and Gradle build files (for example ``- `maven:org.jspecify:jspecify` ``);
* `npm:<name>` for `package.json`, including scoped names (``- `npm:@scope/name` ``);
* `pypi:<name>` for `pyproject.toml`, compared in its PEP 503 normalized form.

`OutlineValidator` parses the section with the same line-anchored bullet rule as `Affected files` (`bullets_seen` equals `bullets_parsed`, a non-matching line is `unparsed`). An entry with an unknown ecosystem prefix or a coordinate that does not match its ecosystem's grammar, and a coordinate named twice in the outline (within one deliverable or across deliverables), is rejected with `rejected.reason = "invalid_link_args"` naming the line. A deliverable without the section adds no third-party dependency; the section never lists the project's own modules. A version change of an existing dependency is not an addition and is not listed.

The union of the sections of the approved `outline.md` is the plan's *approved dependency set*. Like `declared_files` it is immutable after `outline.review` approval; adding a coordinate later requires an outline revision through the operator-authorizing `loop-back-outline`.

== Phase 4 (`plan`): Task Derivation, DAG Validation & Manifest Resolver

Phase 4 transforms the approved structured deliverables in `outline.md` into executable `TASK-NNN.json` files, dispatch envelopes, and the per-plan execution manifest (`execution-manifest.json`).

=== Deterministic Task Derivation & DAG Cycle Detection
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-7[PM-WATCH-PHASE-7], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-8[PM-WATCH-PHASE-8], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-16[PM-WATCH-PHASE-16]_

1. *Profile-to-Task Mapping*: For each deliverable $D_i$ in `outline.md`, the engine generates one task per declared profile in fixed intra-deliverable order (`implementation` $\rightarrow$ `module_testing` $\rightarrow$ `verification`), copying the deliverable's `Intent gloss` verbatim into each derived task's description. A verification command the deliverable declares is copied verbatim into `verification.commands` of its tasks (placeholders are substituted at execute); a deliverable that declares a command whose tasks would receive none is a derivation failure, never a silent fallback to a module-level command.
2. *Dependency DAG Construction & Cycle Rejection*: Inter-deliverable `depends:` declarations map the head task of $D_i$ to the tail task of each prerequisite deliverable $D_j$, and each task of a deliverable depends on its predecessor in the fixed intra-deliverable order; the edges are persisted in each task's `depends_on` (link:../store-schemas/06-task-references-manifest.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]). `TaskGraphValidator` runs Kahn's topological sort and depth-first cycle detection over the complete task graph; any self-dependency, unresolved task or deliverable reference, or cycle (`TASK-A -> ... -> TASK-A`) fails validation before any task file is written. The same check runs server-side on every later task creation or amendment and refuses the write (`invalid_link_args` with `task_dependency_unresolved` or `task_dependency_cycle`).
3. *Two-Tier Skill Resolution*: Each task is assigned `skills[]` (`skill://pm/...` URIs) by combining system persona skills (`skill://pm/core/SKILL.md`, profile vocabulary skill) with domain-resolved skills for the deliverable's `(domain, module, profile)` tuple. A `verification` task resolves only the core skills and no domain skills; its steps are the verification commands (as `plan-marshall` `phase-4-plan/SKILL.md`, profile `verification`).
4. *Atomic Non-Idempotent Task Creation*: All derived tasks are persisted in a single atomic batch (`batch-add`). Task creation is strictly non-idempotent: once `tasks/TASK-*.json` files exist for the plan, the engine omits the task-creation link on any re-entry into Phase 4, preventing duplicate task generation. Q-Gate findings on the task bundle are remediated only through *Targeted Task Revision*: in `plan.qgate` the server offers `revise:TASK-NNN` for each task that carries a blocking finding, with the free parameters of `plan.describe-tasks` for that task (`description`, `steps`, `target_files`, `depends_on`) and the same validations (declared-path discipline, dependency graph check). A revision changes only the named task, never the task set: no task is added or deleted. A finding that needs a structural change (a different task split, a missing or superfluous deliverable) is resolved only by the operator-authorizing `loop-back-outline` to Phase 3. The next Q-Gate iteration hashes the revised bundle. *Deliberate change vs. `plan-marshall`*: its Phase 4 Q-Gate auto-loop clears the existing task set and re-runs task creation from scratch (clear-and-replan); `PM-MCP` keeps the task set and revises only the tasks named by blocking findings.
5. *Server-Side Cost Sizing, Envelope Bin-Packing & Manifest Composition*: Upon `plan.describe-tasks` submission, the server automatically executes three deterministic passes in-process (without exposing separate LLM-driven `pack-envelopes` or `compose-manifest` states):
** `TaskCostEstimator` computes `cost_size` (`XS | S | M | L | XL | XXL`) for each task from its step count, profile, skill count, and target file count, and stamps `predicted_cost_tokens`, the size-to-token table value of that size (link:../dispatch-and-effort/01-task-envelopes.adoc#cost-sizing[Dispatch & Effort Specification, Cost Sizing]).
** `EnvelopePacker` groups the tasks, topologically ordered over `depends_on` (ties broken by `task_id`), Next-Fit into dispatch envelopes (`envelope-1..M`) bounded by the configured per-envelope budget, merges an envelope below the minimum dispatch work of `10K` into an adjacent compatible one, and stamps `envelope_id` on each `TASK-NNN.json`. Tasks share an envelope when they have the same module and effort role, so a deliverable's `implementation` and `module_testing` pair shares one leaf sub-agent context window.
** `ExecutionManifestResolver` writes `execution-manifest.json` (including structured `phase_6.dropped_steps: [{step_id, gate, reason}]` for every pruned step).
6. *Declared-Path Discipline in Task Descriptions*: A task description or step submitted via `plan.describe-tasks` that names a path outside its deliverable's `Affected files` is rejected with `invalid_link_args` naming the path; the outline must be revised or the path declared, and the step is never silently dropped.
7. *Budget Projection & Advisory Split*: In the same pass the server sums `predicted_cost_tokens` over all tasks (`BudgetProjector`) and persists the projection in `mcp/status.json` (`metadata.budget_projection`: the sum, the deliverable count, the plan's `(scope_estimate, change_type)` pair, and the compared anchor column, link:../dispatch-and-effort/02-dispatch-observability-and-spend.adoc#spend-accounting-budget-anchors[Dispatch & Effort Specification, Spend Accounting & Budget Anchors]). When the deliverable count exceeds the guidance ceiling of 12 or the projection exceeds the warning column of the pair (for a fallback pair: its normalized ceilings), the plan representation carries the fact `split_advice` naming the figures and the exceeded bound. `split_advice` is advisory only: it never blocks, never enters a state of kind `awaiting_user`, and never changes the tasks. The projection carries the basis of the size-to-token table it summed (link:../dispatch-and-effort/01-task-envelopes.adoc#cost-sizing[Dispatch & Effort Specification, Cost Sizing]): `basis: uncalibrated` until the server has recalibrated the table from measured metrics.

=== Shared Execution Manifest & Posture Preview Resolver

Both the Phase 1/Phase 4 *posture preview* and the Phase 4 *execution manifest composition* (`execution-manifest.json`) invoke the same deterministic `ExecutionManifestResolver`:

* *Posture Lattice*: `minimal` $\sqsubset$ `standard` $\sqsubset$ `full`.
* *Floor Immunity*: Steps whose lane class is `core` or `derived-state` carry floor immunity (currently `sync-baseline`, `pre-push-quality-gate`, `push`, `create-pr`, `ci-verify`, `branch-cleanup`, `preference-emitter`, `record-metrics`, `print-phase-breakdown`, `emit-landing`, `archive-plan`, and `architecture-refresh`): these are the mandatory steps, whose presence in the project's `finalize.pmwf` unit is a compiled invariant (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]) and which `workflow.json` cannot configure (a `steps` entry for one is refused with `mandatory_step_not_configurable`). Steps without a `lane` block are not lane-participating and are always kept.
* *Local-Only Runs*: When the project has no push remote (derived fact `push_remote` empty, link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts Store]), the resolver drops `push`, `pre-push-quality-gate`, and `pre-submission-self-review` from the Phase 6 manifest at composition time and records them in `dropped_steps` with `gate: local_only`; the plan completes with `merge_outcome: local_only`. *Deliberate change vs. `plan-marshall`*: the local-only outcome is derived from the repository, never chosen (`plan-marshall`'s `commit_and_push: false` does not exist), and with a push remote every plan pushes, opens a pull request, and passes CI and the merge barrier. A `stale` or `failed` `push_remote` fact makes the composition `indeterminate`, never local-only.
* *Prune Predicates & Structured `dropped_steps`*: Conditional steps (such as `sonar-roundtrip`, `automatic-review`, or `adr-propose`) evaluate their provider availability and footprint prune predicates; an unresolved `ask` seed is dropped only when its backing provider is unconfigured, and every pruned step is recorded in `execution-manifest.json -> phase_6.dropped_steps` with its `gate` (`posture`, `provider_unconfigured`, `footprint_disjoint`, `change_type_exempt`, or `recipe_override`) and human-readable `reason`. A `footprint_disjoint` prune evaluates the structured-derived footprint (`references.json -> derived_files.expected_modifications`); an absent, unreadable, or empty footprint is `indeterminate` and keeps the step (never pruned, never reported clean), mirroring `VerdictCurrencyEvaluator`: absence of a footprint never means "disjoint from everything".

== Planning Transition Guards & Real-World Invariants
_Implementation watch: link:../../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-5[PM-WATCH-FS-5], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-58[PM-WATCH-PHASE-58], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-59[PM-WATCH-PHASE-59], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-6[PM-WATCH-STORE-6]_

Every phase transition out of Phases 1, 2, 3, and 4 executes a deterministic server-side guard pipeline replacing the legacy `phase_handshake.py` script:

[cols="2,1,4"]
|===
|Guard / Invariant |Scope |Enforcement Rule

|*Artifact Gate*
|Exits from Phases 2, 3, 4
|Refuses transition unless the phase's mandatory artifacts exist and pass schema validation: Exit Phase 2 requires `request.md` containing `## Clarified Request`; every arrival at Phase 3, whether by the refine exit or by the recipe shortcut, requires a non-empty `status.metadata.pr_title` (the recipe shortcut renders it from the recipe's `pr_title_template`); on the light lane both Phase 2 requirements are evaluated on the collapsed envelope's submission, which must carry the clarified request and `pr_title` before `phase-2-refine` is recorded `done` and `outline.md` is accepted (<<light-envelope>>); Exit Phase 3 requires `outline.md` passing `OutlineValidator` and `outline.review` approved; Exit Phase 4 requires $\ge 1$ `tasks/TASK-*.json`, an acyclic DAG, and a composed `execution-manifest.json`. Bypassing the artifact gate (`--allow-bare-transition`) is restricted exclusively to the operator channel with a mandatory audit reason. Each exemption (this bypass and every other operator exemption from a gate, such as `force-gate` or an operator skip of a stale step) records its `exemption_class` in `audit.jsonl`: the gate identifier plus a reason class from the closed set `gate_false_positive`, `gate_not_applicable`, `tooling_unavailable`, `deliberate_deferral`, `unknown`. The server counts classes across plans: an exemption class granted in three or more plans within the retained plans (live and archived, `archived_plans_days`) triggers the `lessons-capture` signal gate (catalogue row `991`) and is listed by `pm-mcp status` as a recurring exemption, so a gap that is repeatedly absorbed by operator overrides becomes a recorded defect.

|*Clean Main Checkout Guard* (`git status --porcelain`)
|All planning transitions (Phases 1–4), and every later transition
|A plan writes its state only through server links into its directory in the per-project machine store (`<PM_MCP_BASE>/projects/<project_id>/plans/<plan_id>/`), and server-owned repository writes happen only in worktrees (the plan worktree and the shared epic worktree), so the plan has no legitimate write in the main checkout in any phase. `pm_start` records `entry_baseline` (the main checkout's porcelain paths with their content digests, link:../store-schemas.adoc[Store Schemas Specification], Workflow State Store) in `mcp/status.json`. Before completing any planning transition, the daemon runs `git status --porcelain` on the main checkout; a path outside the git-ignored `.marshall/local/` that is absent from `entry_baseline` or whose digest changed violates the plan's rules: it is a hard error that refuses the transition and raises the `footprint_violation` condition on the current state (link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-footprint_violation[State Catalogue, Conditions]), attributed to the plan. Baseline dirt present at entry is listed in `facts.baseline_dirty`, never blocks, and is never offered for revert. Server-owned writes never land in the main checkout (the epic ledger is written in the shared epic worktree), so a sibling plan's landing or outbox write cannot trip this guard. *Deliberate change vs. `plan-marshall`*: `plan-marshall`'s handshake refuses on any main-checkout dirt, including operator dirt the phase could not have authored.

|*`.marshall/config/` Recovery Guard*
|`pm_start` and all planning transitions
|If a file under `.marshall/config/` (a team file or a workflow unit) changed in the main checkout since `entry_baseline` during a planning phase, the server **never** silently discards or commits it. The transition is refused, the `blocked` condition is raised on the current state (state unchanged), and the operator is prompted via elicitation/CLI to either commit the config change or restore the file; the resolution clears the condition. A dirty `.marshall/config/` when `pm_start` is called refuses `pm_start` with `config_dirty` (link:../mcp-tools/01-core-workflow-tools.adoc#pm-start-refusal[MCP Tools Specification, `pm_start` Refusals]), so no plan starts on an uncommitted configuration; a team file or workflow unit that fails validation refuses it with `config_invalid`, and one at another format with `format_outdated` or `format_newer`, each naming the file. A `local_changes` plan is exempt from `config_dirty`: a dirty file under `.marshall/config/` is part of its captured change set, shown in `request.md` and the pull request, and its verification runs with the changed configuration (which must still verify).

|*Outside-World Invariants* (`main_sha`, `worktree_path`, `config_hash`)
|Phase entries (Phases 2–6)
|Verifies `main_sha` baseline drift, the `config_hash` of the effective configuration (compiled defaults, derived facts, team files, operator file, and process DSL units, link:../store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]; `PM-EXT-7`), and worktree consistency keyed on the plan's worktree presence in `mcp/status.json`: a non-null `worktree_path` must resolve to a live git worktree of `branch_name`; `worktree_path` must be `null` in Phases 1–4 and in Phase 6 steps after `branch-cleanup` at order `> 70`, which therefore never refuse on the removed worktree (link:../filesystem-layout.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). A plan in Phases 4–6 executes against the configuration snapshot bound when its manifest was composed (`execution-manifest.json` `composed_inputs.config_hash`). When the current `config_hash` differs (after a binary upgrade that changed a compiled default or a default unit adopted into the project, a changed derived fact, or a committed edit of a team file, the operator file, or a workflow unit, including an edit the plan's own deliverable made), the engine composes a candidate manifest: an identical candidate is adopted and the new hash recorded; a differing candidate raises the `config_drift` condition on the phase entry state (routine user dialogue, link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-config_drift[State Catalogue, Conditions]) offering `adopt` and `keep`, with the manifest diff in `facts` and the choice recorded in `audit.jsonl` and in the manifest's `adoptions[]`; `keep` continues on the bound snapshot. *Deliberate change vs. `plan-marshall`*: an upgrade no longer re-composes an in-flight plan silently. Baseline drift is never auto-rationalized; loop-back re-entry drift is auto-accepted exactly once, and worktree refusal errors are never bypassed.

|*Store Integrity & Digest Guard*
|Every `pm_state` / `pm_do` read
|Every server write to the plan's stores in the per-project machine store (`status.json`, `references.json`, `findings.jsonl`, `TASK-*.json`) records a SHA-256 content digest. If a host shell edits these files directly (host file tools are denied `<PM_MCP_BASE>/**`), the digest mismatch is detected on the next MCP call that takes the scope lock, which, after transaction-journal recovery, raises the `store_tampered` condition on the current state requiring operator resolution (link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification]); it is a condition, not a state change and not a `rejected.reason`. A lock-free read (`pm_state`, `pm://` resources) never decides it and reports `digest_unverified` instead.

|*Blocking Findings Guard* (`pending_findings_blocking_count == 0`)
|Exits from Phases 2, 3, 4, 5
|Refuses phase exit while any Q-Gate or verification finding with `blocking == true` remains in `resolution == "pending"` (the server-written resolution, link:../store-schemas.adoc[Store Schemas Specification], Findings Ledger Record). The exit from Phase 3 is stricter: it requires every Q-Gate finding of phase `phase-3-outline`, blocking or not, to carry a terminal disposition; the non-blocking ones may be accepted together in `outline.review` (Phase 3, § 4). A finding addressed to a phase the plan has already left is refused at the findings write seam with `phase_closed` (link:../mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]); only Phase 6 findings filed after the merge are carried out instead (below). In Phase 6 the pre-merge review barrier (Predicate 1) is the last findings guard; after the merge no step refuses on findings, and a blocking finding filed later is carried out and recorded in the landing (catalogue rows `1000` and `1100`). A refusal lists each blocking finding (`finding_id`, `source`, `severity`, age since `created_at`, failing predicate) in `facts`, never only a count. Independently of refusals, every phase-transition representation (including Phase 6 entry) carries `pending_findings: {blocking: N, non_blocking: M}` in `facts`.
|===

== Direct In-Band Text Submissions & Retired Scratch-File Patterns (`PM-WF-2`, `PM-WF-6`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-16[PM-WATCH-STORE-16]_

In legacy `plan-marshall`, passing multi-line markdown or prose over Bash CLI arguments triggered shell-quoting hazards, OS `ARG_MAX` limits, and host permission prompts (such as heredocs containing `#` markdown headings or `$(cat <<'EOF'...)`), forcing multi-step temp-file rituals (`resolve-path` or `prepare-*` -> host `Write` tool -> script commit/validate call). Because `pm-mcp` receives tool arguments over structured JSON-RPC 2.0 (`stdio`) and streams payloads to child tools in memory via `stdin` (`PM-EXEC-5`), all scratch-file staging patterns are permanently retired:

[cols="2,2,3"]
|===
|Workflow Operation |Retired Legacy Pattern (Prohibited) |PM-MCP Direct In-Band Contract

|*Git Commit Message* (`git.commit_and_push`)
|Write `{worktree_path}/.plan/temp/{plan_id}-commit-msg.txt` via host `Write` tool -> `git -C {worktree_path} commit -F ...` -> `rm -f`
|Model submits `message: text[1..2000]` in `pm_do` `args` (or engine uses deterministic fallback). Server validates Conventional Commits, appends `Co-Authored-By` trailer, and pipes UTF-8 bytes via `stdin` to `git -C <tree> commit -F -`.

|*PR / MR & Issue Bodies and Replies* (`create-pr`, `triage:F-n`, issue mirror)
|`ci pr prepare-body` / `prepare-comment` / `ci issue prepare-body` -> host `Write` to `<plan>/work/ci-bodies/*.md` -> `ci pr create --body-file ...`
|Model submits `body: text[1..32768]` or `reply_text: text[1..4000]` directly in `pm_do` `args`. Server injects deterministic sections (`## Scope Deviations` from `accepted_deviations[]`) in memory and streams to `gh pr create --body-file -` / `glab` via `stdin`. Server-owned sections are delimited by `<!-- pm-mcp:section:<name> -->` … `<!-- /pm-mcp:section:<name> -->` markers; every render (`create-pr`, `edit_pr_body`, a later accepted deviation) reads the current body first, replaces only the delimited blocks (never appending a second copy), and preserves model-authored text outside the markers. A budgeted server section is truncated only at a paragraph or list-item boundary with an explicit `… (truncated, N chars)` marker, or dropped whole with a marker, never mid-token.

|*Clarified Request Document* (`phase-2-refine`)
|`manage-plan-documents resolve-path` -> host `Write`/`Edit` on `request.md` -> `manage-plan-documents validate`
|Sub-agent submits `clarified_request: text[1..32768]`, `pr_title`, and the six confidence dimension scores as separate `int[0..100]` parameters (`correctness`, `completeness`, `consistency`, `non_duplication`, `ambiguity`, `module_mapping`) in `submit:refine`. Server validates structure and writes `request.md` + SHA-256 digest atomically. On the light lane the collapsed envelope submits `clarified_request` and `pr_title` (no confidence scores) together with the outline in `submit:outline` (<<light-envelope>>).

|*Solution Outline Document* (`phase-3-outline`)
|`manage-solution-outline resolve-path` -> host `Write` on `outline.md` -> `manage-solution-outline validate` -> `extract-deliverables`
|Sub-agent submits `outline: text[1..65536]` directly in `submit:outline`. Server runs `OutlineValidator` (intent markers, 6-bucket profile classifier, deliverable schema, `Added dependencies` grammar) in-process before persisting `outline.md` and narrowing `references.domains`.

|*Task Creation & Descriptions* (`phase-4-plan`)
|`manage-tasks prepare-add` -> host `Write` to `<plan>/work/pending-tasks/*.json` -> `commit-add` (or `work/tasks-batch.json`)
|Engine derives task skeletons in-process (`plan.derive-tasks`), model submits enriched descriptions via `plan.describe-tasks` `args`, and server writes `tasks/TASK-NNN.json` atomically.

|*Lesson Creation & Body* (`lessons-capture`, `split` deviation)
|`manage-lessons add` -> host `Write` to `work/lesson-body-{id}.md` -> `manage-lessons set-body --file`
|Single `submit` transition passing `title`, `component`, `category: enum[bug\|improvement\|anti-pattern\|arch-constraint]` (mirroring `plan-marshall` `manage-lessons`; re-verify before implementing), `rule` (required for `arch-constraint`, absent otherwise), `provenance: enum[run_artifact\|tool_return\|operator_decision]` (set by the server where the creating transition determines it), and full markdown `body: text[1..16384]` in `args`; the server writes the lesson file (YAML front matter plus Markdown body, link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record]) atomically as revision 1, whose `sources[]` the server records from the creating transition (the plan, and the findings, jobs, or landing it names; every `ref` resolved by the server, never a caller path). A later body change replaces the body wholesale as a new revision with its own sources. The server stamps the lesson's `tool_version` from its own release version (`PM-DIST-1`) and derives its `audience` (link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Audience Classification]); neither is a submit parameter. No submit parameter chooses a store or a route, so a lesson is never stored anywhere by fallback.

|*ADR Authoring* (`adr-propose`)
|`manage-adr resolve-path` -> host `Write` on `.plan/doc/adr/ADR-NNN-*.adoc` -> `manage-adr validate`
|Model submits `title`, `tags`, `affects`, and `adr_body: text[1..32768]` in `submit:adr-propose`; server runs `AsciiDocValidator` in-process and writes the numbered ADR file atomically.
|===
