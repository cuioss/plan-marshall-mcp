== Re-Entry & `head_at_completion` Verdict Currency Rules

When Phase 6 re-enters after a loop-back from Phase 5, an in-branch settle commit, a `sync-baseline` rebase, or a session resume, the engine decides for each step whether to `SKIP` (preserving its prior `done` verdict) or `RE_FIRE`.

=== Fail-Closed `head_at_completion` Anchor Obligation
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-22[PM-WATCH-PHASE-22]_

* Every step with `headDependent == true` must record `head_at_completion: "<40-hex-sha>"` in `mcp/status.json` when transitioning to `done`.
* Any attempt to record `done` for a `headDependent == true` step without a valid `head_at_completion` SHA is **refused** (`error: "missing_head_at_completion"`).
* The server derives `head_at_completion` from `git rev-parse HEAD` of the plan's worktree in the same transition that records `done`; no link accepts it as a parameter. The same rule holds for every recorded commit identity (`reviewed_commit_sha`, `commit_sha`, `branch_pushed_at.head_sha`) and for `pr_number`, so an invented or padded SHA can never enter a step record.
* On re-entry, if a step's persisted record lacks `head_at_completion`, the engine reports the prior record as `unverified` and unconditionally re-fires the step.

=== Deterministic Verdict Currency Algorithm (`VerdictCurrencyEvaluator`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-23[PM-WATCH-PHASE-23], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-62[PM-WATCH-PHASE-62]_

[[verdict-input-scope]]*Verdict Input Scope (`input_scope`)*: Every `headDependent == true` step descriptor declares `input_scope` from a closed enum, validated by `FinalizePipelineValidator` rule 6 (a missing value is a validation error, never a default):

* `remote_state`: the verdict is a property of remote state (`ci-verify`, `automatic-review`, `sonar-roundtrip`); currency is decided by remote evidence, and the recorded verdict is stale on every change of `HEAD`. `verdict_inputs` is empty.
* `open_ended`: the step's body runs something open-ended over the repository, so no sound input subset exists; the verdict is stale on every change of `HEAD`. A step has no sound subset when any of three shapes applies: (1) a test suite that asserts against the real tree, (2) a scan whose inputs are discovered at run time rather than fixed, (3) a whole-repository walk. Example: `pre-push-quality-gate`. `verdict_inputs` is empty.
* `plan_footprint`: the step's subject is the plan's changes; the scope resolves at evaluation time to the realized footprint (Footprint-Scoped Inputs below). `verdict_inputs` is empty.
* `declared`: the step's verdict is a property of named files; `verdict_inputs` lists them as explicit, non-empty globs naming what determines the truth of the recorded claim.

For a `headDependent == true` step $S$ with recorded `head_at_completion` $= H_{\text{rec}}$ and current worktree `HEAD` $= H_{\text{cur}}$:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.finalize;

import java.util.List;
import java.util.Optional;
import java.util.Set;

public enum CurrencyVerdict {
    CURRENT_SAME_HEAD,
    PRESERVED_INPUTS_UNAFFECTED,
    STALE_MISSING_ANCHOR,
    STALE_REBASE_ADVANCED,
    STALE_UNSCOPED_HEAD_CHANGE,
    STALE_INPUTS_MODIFIED
}

public final class VerdictCurrencyEvaluator {

    public CurrencyVerdict evaluate(
            FinalizeStepDescriptor step,
            String recordedHeadSha,
            String currentHeadSha,
            boolean rebaseReplayedCommits,
            Set<String> changedRepoRelativePaths) {

        if (recordedHeadSha == null || recordedHeadSha.isBlank()) {
            return CurrencyVerdict.STALE_MISSING_ANCHOR;
        }
        if (recordedHeadSha.equals(currentHeadSha) && !rebaseReplayedCommits) {
            return CurrencyVerdict.CURRENT_SAME_HEAD;
        }
        // changedRepoRelativePaths is the tree diff H_rec..H_cur (git diff --name-only H_rec H_cur);
        // after a replaying rebase it includes the upstream changes the rebase pulled in.
        // inputScope is present on every headDependent step (FinalizePipelineValidator rule 6).
        List<String> globs;
        switch (step.inputScope().orElseThrow()) {
            case REMOTE_STATE, OPEN_ENDED -> {
                // remote_state: currency is decided by remote evidence; open_ended: no sound
                // input subset exists. Both are stale on every change of HEAD.
                return rebaseReplayedCommits
                    ? CurrencyVerdict.STALE_REBASE_ADVANCED
                    : CurrencyVerdict.STALE_UNSCOPED_HEAD_CHANGE;
            }
            case PLAN_FOOTPRINT -> {
                // realized footprint plus the paths the step's own commits touched
                Optional<List<String>> footprint = resolvePlanFootprint(step);
                if (footprint.isEmpty()) {
                    return CurrencyVerdict.STALE_UNSCOPED_HEAD_CHANGE;   // unresolvable: fail-closed
                }
                globs = footprint.get();
            }
            case DECLARED -> globs = step.verdictInputs();   // non-empty by validation
        }
        boolean anyInputTouched = changedRepoRelativePaths.stream()
            .anyMatch(path -> matchesAnyFnmatchGlob(path, globs));
        return anyInputTouched
            ? CurrencyVerdict.STALE_INPUTS_MODIFIED
            : CurrencyVerdict.PRESERVED_INPUTS_UNAFFECTED;
    }
}
----

* *No Re-Stamp on Preserve Invariant*: When `VerdictCurrencyEvaluator` returns `PRESERVED_INPUTS_UNAFFECTED` (because `git diff --name-only <H_rec>..<H_cur>` touched zero paths matching the step's resolved inputs), the step is skipped and its persisted `head_at_completion` **remains $H_{\text{rec}}$** — it is **never** overwritten with $H_{\text{cur}}$. Keeping $H_{\text{rec}}$ ensures that subsequent commits are always diffed against the cumulative range since the step actually executed.
* *Rebase vs No-Op Rebase*: A step declaring `advancesMainViaRebase == true` (`sync-baseline`, `branch-cleanup`) can invalidate downstream verdicts **only** when it actually replayed commits (`action == "rebased"` and `upstream_commit_count > 0`). When the branch was already up-to-date (`work_performed == false`), `HEAD` does not change and existing verdicts remain current.
* *Path-Derived Re-Fire After a Replaying Rebase*: A replaying rebase does not by itself stale a verdict. The changed paths are the tree diff between $H_{\text{rec}}$ and $H_{\text{cur}}$, which includes the upstream changes the rebase pulled in, and a `declared` or `plan_footprint` step re-fires iff that diff touches its resolved inputs (`STALE_INPUTS_MODIFIED`), in both directions: an upstream change to an input re-fires the step even when the plan's own commits did not touch it, and an unrelated upstream change never re-fires it. Only `remote_state` and `open_ended` steps return `STALE_REBASE_ADVANCED`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` classifies by the same tree diff over declared `verdict_inputs`, but an absent declaration is legal there and silently means "invalidated on every `HEAD` change" (in practice no bundled step declares `verdict_inputs`); `PM-MCP` requires an explicit `input_scope` on every head-dependent step and validates it at build time and startup, and adds the resolved `plan_footprint` scope that `plan-marshall`'s static glob vocabulary cannot express.
* *Footprint-Scoped Inputs (`plan_footprint`)*: A step whose subject is the plan's changes (`simplify`, `security-audit`, `pre-submission-self-review`) declares `input_scope: plan_footprint` with empty `verdictInputs`; the evaluator resolves the scope at evaluation time to the realized footprint (link:../store-schemas/13-leases-integrity-testing.adoc#three-way-footprint[Store Schemas Specification, Three-Way File Footprint Reconciliation]) together with the paths the step's own commits touched. An unresolvable footprint makes the verdict `STALE_UNSCOPED_HEAD_CHANGE` (fail-closed).
* *Skip Basis*: Every currency decision, skip or re-fire, is persisted on the step record as `skip_basis` (`verdict`, `h_rec`, `h_cur`, `changed_paths_count`, `inputs_touched`), so a skip is auditable and never leaves no record.

=== Step Records, Re-Fire & Loop-Back Rules
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-11[PM-WATCH-PHASE-11], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-21[PM-WATCH-PHASE-21], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-71[PM-WATCH-PHASE-71], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-79[PM-WATCH-PHASE-79], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-11[PM-WATCH-DSL-11]_

* *Settled Completions Only*: A step completion record (`done`) is emitted only for settled outcomes. `loop_back` and defer emit none, so a re-fired step never produces two completions.
* *Firings & Re-Fire Replaces*: The persisted step record keeps one entry per firing (`firings[]` with `dispatch_id`, `started_at`, `outcome`, and `cause`: `first`, `loop_back`, `failure`, `error`, or `input_changed`); the current outcome is the last firing's. When `VerdictCurrencyEvaluator` decides `RE_FIRE`, the step's outcome is set to `unverified` before the step runs and is replaced by the new terminal outcome; a prior `done` never survives a re-fire, a refused outcome change is appended as a firing and never leaves the prior outcome silently current, and no force flag exists. Re-fire counts are derived from the firings per cause, never from the step-outcome log. Each firing also records `productive` (it produced a commit or filed a finding, derived from the change ledger and the findings store), so re-fires are published split into productive and unproductive ones and an unproductive re-fire pattern is visible beside the loop-back counts (link:../workflow-dsl/07-loop-back-diagrams-verification.adoc#loop-back-bounds[Workflow DSL Specification]).
* *Phase-Exit Completeness*: The check is positional. Entering a step of order N requires, for every manifest step of order < N, a satisfied outcome: `done` or `skipped` whose currency verdict against the current `HEAD` is `CURRENT_SAME_HEAD` or `PRESERVED_INPUTS_UNAFFECTED` (for steps that are not `headDependent`, the presence of `done` in the firing of the current `loop_back_iteration`), or `skipped_by_operator` (an operator decision with its own audit record, either an operator skip or a step completed by an approved grant decision, link:../workflow-dsl/02-units-jobs-decisions.adoc#decision-registry[Workflow DSL Specification, `completes <step> as skipped_by_operator`]; its stale `head_at_completion` stays as the record and the grant reference is kept on the step record); a stale `done`, or a firing from an earlier iteration, counts as missing. A `skipped_by_operator` completion never satisfies a barrier predicate: the Pre-Merge Review Barrier and the `red_ci_gate` gap class still evaluate `HEAD`. A plan wound down unmerged (`finalize.wind-down`, <<merge-path>>, item 8) has `default:branch-cleanup` completed as `failed`; the check accepts that record for the steps of order > 70, none of which reads merge evidence. At `branch-cleanup` (70) entry the check runs before any rebase that `branch-cleanup` performs. `merge.gate-entry` and `finalize.next-step` evaluate it through one shared `PhaseExitCompleteness` evaluator, and `finalize.next-step` never selects order `70` while a step of lower order is unmet (<<merge-path>>, item 1). Currency evidence produced inside `branch-cleanup` after its own rebase (fresh CI and review results on the rebased `HEAD`) is recorded on the affected remote-state steps as their new evidence; it is obtained by `finalize.merge-evidence-wait`, which runs the composite CI and review-bot watch over the rebased `HEAD` with the merge lease released (<<merge-path>>, item 4). Phase 6 exit (after the merge, when no worktree `HEAD` exists) requires every step of order > 70 to have a settled outcome (`done`, `skipped`, or `skipped_by_operator`) and checks no currency, since nothing is merged anymore.
* *Operator Skip*: A step the operator skips (operator CLI or elicitation) while its currency verdict is stale is recorded as `skipped_by_operator` with its stale `head_at_completion` kept, never as `done` at the current `HEAD`; it satisfies Phase-Exit Completeness. The approved outcomes of `review_barrier_gap`, `ci_failure_override`, and `wait_cancelled_override` complete the wait-region steps `default:ci-verify`, `plan-marshall:automatic-review`, and `default:sonar-roundtrip` the same way, with the grant or acknowledgement as reference; the clause is admitted only on `APPROVED` decision outcomes.
* *Stale-Finding Re-Anchor*: Before `loop_back` is offered, every open finding is re-anchored against `HEAD` (from the commit it was raised against); a finding whose cited location no longer exists is resolved as stale (status `resolved`, `resolution: taken_into_account`, recorded and never counted as fixed). If only stale findings remain, `loop_back` is omitted and the loop closes.

== Merge Path (`branch-cleanup`)
_See Requirement link:../../Requirements.adoc#PM-WF-13[PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier]_

_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-18[PM-WATCH-PHASE-18], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-44[PM-WATCH-PHASE-44], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-74[PM-WATCH-PHASE-74], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-79[PM-WATCH-PHASE-79], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-80[PM-WATCH-PHASE-80], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-81[PM-WATCH-PHASE-81], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-82[PM-WATCH-PHASE-82], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-83[PM-WATCH-PHASE-83], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-85[PM-WATCH-PHASE-85]_

`default:branch-cleanup` (`order = 70`) runs as a chain of states, so that every approved finalize escalation re-enters an `auto` state (link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Static Verification Rule 10]) and the merge lease is held only while no wait is open (link:../state-catalogue/04-plan-finalize-terminal.adoc#state-catalogue-finalize[State Catalogue, Phase 6: `finalize`]):

1. *Gate Entry* (`finalize.merge-gate`, `auto merge.gate-entry`): records the grant or acknowledgement of the approved escalation that entered it (<<_operator_merge_authorization_record_mergeauthorizationrecord>>), runs the finalize spend check (an overrun enters `finalize.spend-escalate`) and Phase-Exit Completeness, and reads the recorded grants. It is the target of every approved finalize escalation (`review_barrier_gap`, `ci_failure_override`, `wait_cancelled_override`, `finalize_spend_overrun`, `merge_action`, `red_ci_gate`, `rereview_timeout`) and of a moved head at dispatch. What an approval records is fixed: `ci_failure_override` records a HEAD-bound grant of gap class `red_ci_gate`; `finalize_spend_overrun` records a spend acknowledgement only, never a grant; `wait_cancelled_override` records an acknowledgement only, never a grant (evidence still missing later raises its own gap through `finalize.merge-gap`); `review_barrier_gap`, `merge_action`, `red_ci_gate`, and `rereview_timeout`, raised from `finalize.merge-gap`, record a HEAD-bound grant of that gap class. A Phase-Exit Completeness check that finds a step unmet ends with the outcome `incomplete` (`missing_steps`) and enters `finalize.next-step`, which re-fires the lowest-order unmet step. `merge.gate-entry` and `finalize.next-step` use one shared `PhaseExitCompleteness` evaluator, and `finalize.next-step` never selects order `70` while a lower-order step is unmet.
2. *Lease* (`finalize.merge-lease`, job): FIFO admission to the Cross-Plan Merge Mutex (<<_cross_plan_merge_mutex_fifo_admission_queue>>); the plan rests until it holds the lease. A lease job that ends `failed`, `timed_out`, `cancelled`, `killed`, `refused`, or `indeterminate` enters the link state `finalize.merge-lease-interrupted`, which holds no lease and shows the job outcome (`timed_out` as `no_verdict`) and the FIFO position in `facts`. It offers `retry` (re-enters the lease job; the enqueue is idempotent, so the position is kept, except after `cancelled`, which rejoins at the tail) and `abort` (the request `abort-plan`); it offers no `escalate` and no override.
3. *Sync Only When Required* (`finalize.merge-sync`, `auto`): the plan branch is rebased onto `origin/<base_branch>` and pushed with an explicit lease (the expected remote SHA is the last recorded push, link:../workflow-dsl/06-reusable-sub-workflows.adoc#_six_stage_execution_contract_of_git_commit_and_push[Workflow DSL Specification, Stage 6]) only when the derived fact `branch_up_to_date_required` holds (the provider requires an up-to-date branch; a `stale` or `failed` fact is `indeterminate` and counts as holding) or when the base changed, since the merge base, a path of the plan's realized footprint. Otherwise no rebase runs (`not_required`) and the evidence already gathered for `HEAD` stands. A base that is already an ancestor of `HEAD` is never rebased. Independently of the rebase, `merge.sync-base` pushes with the explicit lease whenever the local `HEAD` differs from the last recorded push, even when the base is already an ancestor, and every such push (outcome `pushed`) leads through the evidence wait (item 4), so the barrier never evaluates a `HEAD` the remote does not hold. *Deliberate change vs. `plan-marshall`*: `plan-marshall` always rebases before merging; an unnecessary rebase costs a CI and review round and a forced push.
+
Every sync outcome other than success releases the lease first. A rebase `conflict` enters the link state `finalize.merge-conflict` (`facts` list the conflicted paths): `continue_rebase` (after the model resolved the conflict) re-enters `finalize.merge-gate` when the rebase completes and `finalize.merge-conflict` on the next conflict; `abort_rebase` restores the pre-rebase `HEAD` and enters the link state `finalize.merge-sync-escalate`, which offers only `retry` (re-enters `finalize.merge-gate`) and `abort` (the request `abort-plan`). A push rejected by the lease (`rejected_lease`: the remote branch moved) resets the branch to the pre-rebase `HEAD` and enters the link state `finalize.merge-remote-moved` (`facts`: the observed `remote_sha` and the count of foreign commits); `integrate` runs the server primitive `merge.integrate-remote`, which rebases onto the observed remote head (`integrated` re-enters `finalize.merge-gate`, `conflict` enters `finalize.merge-conflict`), and `abort` raises `abort-plan`. No link offers a forced push over the foreign commits. A plan of the `land` lane is offered no model resolution: in both states its links are `recapture` and `abort` (xref:02-planning-lanes-phases-3-4.adoc#land-lane[Land Lane (`local_changes`)]).
4. *Evidence Wait* (`finalize.merge-evidence-wait`, `composite_job`): after a rebase or push, CI and the review bots evaluate the pushed `HEAD`; the lease is released for the wait and the FIFO position kept; `all_green` re-enters the gate, every other outcome routes as in `finalize.concurrent-wait`.
5. *Barrier and Gap* (`finalize.merge-barrier`, `auto`): under the held lease, the Dependency Delta Check (xref:05-finalize-review-metrics-descriptor.adoc#dependency-delta[Dependency Delta Check (Pre-Merge)]) and the Pre-Merge Review Barrier (<<_two_fail_closed_barrier_predicates>>) evaluate `HEAD` with the admissible grants. A gap of one gap class enters the link state `finalize.merge-gap`, which releases the lease and offers `retry` (re-enters the gate), exactly one `escalate` link raising the decision kind of that gap class (`APPROVED` records the grant and re-enters the gate; `DENIED` returns to `finalize.merge-gap`), the link `wind_down` (rel `escalate`, decision kind `wind-down-unmerged`, item 8), and `abort` (the request `abort-plan`). A denied authorization never aborts the plan.
6. *Dispatch Bound to the Head* (`finalize.merge-dispatch`, `auto`): `ci.merge` or, when the derived fact `merge_queue_enforced` reports `enforced`, `ci.enqueue`, both with the expected head SHA, the `HEAD` the barrier and the grants evaluated (item 5 of <<_cross_plan_merge_mutex_fifo_admission_queue>>). A head that moved since (`head_moved`) re-enters the gate. A merge counts only from `ci.pr-observe`; an enqueue enters `finalize.merge-queue-wait`, and so does an `enqueued_indeterminate` enqueue, with the lease released: the wait's observation settles it (queue membership is progress, `merged` is `merged`, an open pull request that is not queued is `ejected`, an unobservable membership runs into the stall bound and ends `timed_out`, a no-verdict outcome). A provider refusal `not_mergeable` releases the lease and enters the link state `finalize.merge-refused`; `facts.reason` is one of the closed class `conflict`, `behind`, `checks_pending`, `checks_failed`, `review_required`, `blocked`, `draft`, `method_not_allowed`, `unknown`. For `behind` and `conflict` the fact `branch_up_to_date_required` is marked stale, so the next sync rebases. The state offers `retry` (re-enters `finalize.merge-gate`), the link `wind_down` (rel `escalate`, decision kind `wind-down-unmerged`, item 8), and `abort` (the request `abort-plan`). *Deliberate change vs. `plan-marshall`*: no link and no grant merges over a provider refusal; `plan-marshall`'s administrator merge (`gh pr merge --admin`) has no counterpart.
7. *Queue Exit* (`finalize.merge-queue-exit`, link state): every wait outcome of `finalize.merge-queue-wait` other than `merged` (`ejected`, `closed`, `timed_out`, `cancelled`, and the job outcomes `failed`, `refused`, `killed`, `indeterminate`) enters it; `facts` carry the exit outcome, the observed pull-request and queue state, and the ejection reason. Its links are guarded by that observation: `retry` (pull request open and not queued) re-enters `finalize.merge-gate`; `resume_wait` (still queued, after `timed_out` or `cancelled`) re-enters the wait; the link `wind_down` (rel `escalate`, decision kind `wind-down-unmerged`, item 8); and `abort` (the request `abort-plan`).
8. *Wind-Down Unmerged*: the decision kind `wind-down-unmerged`, raised from `finalize.merge-gap`, `finalize.merge-refused`, or `finalize.merge-queue-exit`, ends the plan without a merge. `APPROVED` enters the `auto` state `finalize.wind-down`, whose outcome `wound_down` completes `default:branch-cleanup` as `failed` and enters the post-run band (metrics, landing, archive); `archive-plan` derives the `merge_outcome` through the merge outcome mapping: `declined` when the pull request is closed, `dequeued` when it was ejected, `enqueued_not_landed` when it is still queued (with the owed item `post_merge_cleanup`). `DENIED` returns to the raising link state.
9. *Post-Merge*: on `merged`, the realized footprint is captured, the worktree removed, the branch refs removed, the lease released, and the merge record written (`merge_state`, `merge_commit_sha`, `review_state`); the plan continues in the post-merge band. For a `land` plan, the capture ref is removed there after `switch-and-pull` has confirmed tree equality (xref:02-planning-lanes-phases-3-4.adoc#land-lane[Land Lane (`local_changes`)], item 6).

== Pre-Merge Review Barrier & Operator Merge Authorization Grants

Inside `default:branch-cleanup` (`order = 70`), immediately before executing the merge command (`pr safe-merge` or `merge-queue` enqueue), the engine enforces the fail-closed **Pre-Merge Review Barrier** in the state `finalize.merge-barrier` (<<merge-path>>, item 5).

=== Two Fail-Closed Barrier Predicates
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-24[PM-WATCH-PHASE-24], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-25[PM-WATCH-PHASE-25], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-33[PM-WATCH-PHASE-33]_

Both predicates must evaluate to `true` against the current worktree `HEAD` SHA ($H_{\text{cur}}$):

1. *Predicate 1 — Zero Unhandled Findings*: Every finding in the findings store originating from `automatic-review` (sources `github_pr`, `gitlab_mr`), `ci-verify` (source `ci`), or `sonar-roundtrip` (source `sonar`), and every other finding with `blocking == true` of any `source` of the findings store's source enumeration (`self_review`, `qgate`, `security_audit`, `code_review`, `arch_gate`, `compiler`, `self_report`, `dependency_delta`), must have a persisted, terminal triage disposition (`FIX`, `SUPPRESS`, or `ACCEPT`; status `triaged_*` or `resolved`) whose server-written `resolution` is not `pending`; a `FIX` whose fix has not landed is still `pending` and fails the predicate. A finding with a provider address (`provider_ref`) must also have its outbound response or dismissal transmitted to the provider (`transmit_outcome == "sent"`), which requires a per-finding reply on the finding's own thread or comment; a bot's own resolution marker or a PR-level note is not a response. An unmet triage commitment (Unified Triage Hook) fails the predicate. *Deliberate change vs. `plan-marshall`*: `plan-marshall` counts only pending PR-comment findings and does not require transmission; `PM-MCP` covers every blocking finding and requires the response to be transmitted.
2. *Predicate 2 — Required-Bot Participation on Current `HEAD`*: Every bot in the required set (resolved from `required_bots` against the review-bot registry, xref:05-finalize-review-metrics-descriptor.adoc#automatic-review[Automatic Review: Registry, Participation, Refusals & Ingestion]) must have a participation record (link:../store-schemas/03-findings-and-review-records.adoc#review-participation[Store Schemas Specification]) whose `state` is `participated` or `participated_but_empty`, whose `reviewer_login` equals the bot's registered `author_login`, and which passes the review currency test for $H_{\text{cur}}$. A SHA match without an author match never satisfies the predicate. A `bot_status` other than `completed` (link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations]), and every other per-bot state (xref:05-finalize-review-metrics-descriptor.adoc#automatic-review[Automatic Review: Registry, Participation, Refusals & Ingestion]: in particular `not_triggered`, `refused` of any mode, including a spend-capped or quota-exhausted reviewer, `declined`, `unproven`, `unreadable`, and `silent`), **never** satisfies Predicate 2 and **never** automatically mints a merge grant.
+
*Review Currency*: The currency test applies to every required bot; no registry field exempts a bot from it. Its strictness is the team setting `review.currency` (`.marshall/config/project.json`, link:../store-schemas/07-project-configuration.adoc#config-project-json[Store Schemas Specification]): `exact_sha` requires `covered_commit_sha` to equal $H_{\text{cur}}$; `after_last_push` (the default) accepts a `covered_commit_sha` equal to $H_{\text{cur}}$, or, for a bot whose registry declares `reviewed_sha_carrier: none`, review evidence whose `created_at` is later than the last push of the branch (`branch_pushed_at`). A review evidence object that names a commit other than $H_{\text{cur}}$ never passes, and a latest evidence object that predates the last push resolves `unproven`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` applies currency only to bots whose registry declares `participation_requires_update`, so one exempt bot disables the test for the ANDed gate; `PM-MCP` evaluates currency per bot record for every required bot.
+
*Empty Required Set*: An empty required set satisfies Predicate 2 only as the roster aggregate `vacuous` (the team answered with an empty list: `review.required_bots: []` in `project.json`): the merge proceeds and records `review_state: vacuous` on the merge record and the landing. The roster aggregate `unestablished` (the key is absent: the question was never answered) fails Predicate 2; only a `review_barrier_gap` grant proceeds, and the merge records `review_state: unreviewed_by_grant`. A merge whose required bots all satisfy Predicate 2 records `review_state: reviewed`.

If the findings store cannot be evaluated, the barrier routes to an explicit `unknown` disposition: a `review_barrier_gap` in `ask` mode with cause `findings_unevaluable`, neither a hard halt nor a pass. A refusal of the barrier lists each blocking finding (`finding_id`, `source`, `severity`, age, failing predicate) in `facts`, never only a count.

=== Merge-Authorization Roster & Gap Classes
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-57[PM-WATCH-PHASE-57]_

Every mechanism that authorizes advancing past the merge gate mirrors the merge-authorization roster of `plan-marshall` (`phase-6-finalize/standards/branch-cleanup.md`, verified at commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing). A grant authorizes exactly one *gap class*; HEAD binding alone is never authorization.

[cols="2,2,1,4"]
|===
|Mechanism (`kind`) |Gap class |Bound via |Trigger

|`barrier-ask-override`
|`review_barrier_gap`
|HEAD-bound grant
|Barrier in `ask` mode ("merge anyway, record reason"), including accepting a structural coverage gap; covers every failing state of Predicate 1 or 2.

|`pre-merge-consent`
|`merge_action`
|HEAD-bound grant
|Operator answers the pre-merge confirmation gate with "Yes, merge". A re-rebase between consent and merge lapses the consent.

|`red-ci-override`
|`red_ci_gate`
|HEAD-bound grant
|Immediate-merge arm with red CI: "merge anyway, override red CI". The merge-queue arm needs no grant.

|`rereview-timeout-override`
|`rereview_timeout`
|HEAD-bound grant
|Re-review timeout after a rebase, only by the operator choosing "merge anyway, proceed unreviewed" (the timeout always asks; a standing `proceed` policy does not exist, because it would merge unreviewed code without an operator). The timeout derives from the required bots' open rate windows or registered intervals (the window derivation of xref:05-finalize-review-metrics-descriptor.adoc#automatic-review[Automatic Review: Registry, Participation, Refusals & Ingestion], Refusals & Rate Windows; values in link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows]), never from a flat value, so a bot with an hourly window is not timed out inside it.

|`automatic-review-force-done`
|`find_step_completion`
|Step `head_at_completion`
|`automatic-review` force-completed with a recorded reason, only through the operator-authorizing channel (elicitation or operator CLI, never a model-relayed link); bound by the step's own `head_dependent` anchor, no separate grant. Force-done over refused required bots records the refused set in the rationale. Force-done over an `absent` or `unproven` bot state is refused unless `evidence_ref` names a review object, inline comment, or check-run proving the review; without such evidence only a `barrier-ask-override` (`review_barrier_gap`) can proceed.

|`merge.auto_merge`
|`merge_action`
|Standing operator consent (not HEAD-bound)
|Operator posture key of the machine-local `local-config.json` (default `false`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]); when set, it satisfies `merge_action` without a per-merge consent. It never satisfies any other gap class and never bypasses a barrier predicate. It is not a team setting.
|===

*Grants vs Acknowledgements*: `merge.gate-entry` records what an approved escalation authorizes (<<merge-path>>, item 1). The decision kinds `review_barrier_gap`, `merge_action`, `red_ci_gate`, and `rereview_timeout`, raised from `finalize.merge-gap`, and `ci_failure_override` (gap class `red_ci_gate`) record a HEAD-bound `MergeAuthorizationRecord` of their gap class. `finalize_spend_overrun` and `wait_cancelled_override` record an acknowledgement: it lets the plan proceed to the gate but is no `MergeAuthorizationRecord`, satisfies no gap class, and is never admissible at the barrier. A denied grant decision returns to `finalize.merge-gap`, which keeps offering `retry`, the grant escalation, `wind-down-unmerged`, and `abort`; a denial never aborts the plan and never merges.

=== Operator Merge Authorization Record (`MergeAuthorizationRecord`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-32[PM-WATCH-PHASE-32], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-57[PM-WATCH-PHASE-57], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-70[PM-WATCH-PHASE-70]_

When the barrier fails, a gate requires consent, or an override is requested, the plan cannot merge unless an admissible `MergeAuthorizationRecord` exists in `mcp/status.json` for the active gap class (or, for `merge_action`, the operator's `merge.auto_merge` is `true`).

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.finalize;

import java.time.Instant;
import java.util.Set;

public enum MergeGapClass {
    REVIEW_BARRIER_GAP("review_barrier_gap"),
    MERGE_ACTION("merge_action"),
    RED_CI_GATE("red_ci_gate"),
    REREVIEW_TIMEOUT("rereview_timeout"),
    FIND_STEP_COMPLETION("find_step_completion");

    private final String wireName;
    MergeGapClass(String wireName) { this.wireName = wireName; }
    public String wireName() { return wireName; }
}

public record MergeAuthorizationRecord(
    String kind,
    String planId,
    String headSha,
    MergeGapClass gapClass,
    String operatorChannel,       // "elicitation" or "operator_cli"
    String operatorRationale,
    Set<String> coveredFindings,  // finding_ids open (not terminally dispositioned) when the grant was minted
    Instant grantedAt
) {
    public boolean isAdmissibleFor(String currentHeadSha, MergeGapClass activeGapClass,
                                   Set<String> unhandledFindingIds) {
        return this.headSha != null
            && this.headSha.equals(currentHeadSha)
            && this.gapClass == activeGapClass
            && this.coveredFindings.containsAll(unhandledFindingIds);
    }
}
----

* *Grants Cover Named Findings*: A grant records in `coveredFindings` the findings that were unhandled (failing Predicate 1) when it was minted. It stays admissible only while every unhandled finding at evaluation time is in that set: a finding filed later on the same `HEAD` (a late bot comment) reopens the barrier and needs its own triage or a new grant. The same rule binds an `accept` scope deviation: its `accepted_deviations[]` entry records `covered_findings[]`, and a finding filed after the acceptance is never treated as dispositioned by it.
* *Operator-Only Minting*: Grants are minted through the authenticated operator channel (MCP elicitation or `pm-mcp operator authorize-merge --plan <plan_id> --head <sha> --gap-class <class> --rationale <text>`) only; the server never mints a grant. *Deliberate change vs. `plan-marshall`*: `plan-marshall`'s `re_review_on_timeout: proceed` policy branch (`branch-cleanup-rereview.md`), which merges unreviewed code without an operator, does not exist. The operator's `merge.auto_merge` is the only standing consent; it satisfies `merge_action` and no other gap class and records no grant. Free-text lines in `decision.log` are never accepted as authorization evidence. A re-grant of the same `kind` supersedes the previous record: the prior record is kept with `superseded_at` and is never admissible again.
* *Route on `admissible`, Never on Boolean `authorized`*: The barrier checks `grant.isAdmissibleFor(currentHeadSha, activeGapClass, unhandledFindingIds)`. A grant minted for an earlier commit $H_1$ or for `RED_CI_GATE` is inadmissible if `HEAD` advances to $H_2$ (e.g., after rebase) or if the active gap is `REVIEW_BARRIER_GAP`.
* *Merges Under a Grant Are Marked Unreviewed*: A merge that proceeds under a `rereview_timeout` or `review_barrier_gap` grant records `review_state: unreviewed_by_grant` (with the grant's `kind`, gap class, and the commit no review covered) on the merge record, in a pull-request comment the server posts, and in the landing; it is never reported as a reviewed merge.

=== Cross-Plan Merge Mutex & FIFO Admission Queue
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-44[PM-WATCH-PHASE-44], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-45[PM-WATCH-PHASE-45], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-78[PM-WATCH-PHASE-78], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-83[PM-WATCH-PHASE-83]_

When multiple plans execute concurrently across worktrees of the same repository, `default:branch-cleanup` (`order = 70`) serializes their rebase-and-merge critical sections through the **Cross-Plan Merge Mutex** (`MergeMutexManager`), a lease persisted in `<PM_MCP_BASE>/state/merge-queue.json` whose updates run as short transactions under `<PM_MCP_BASE>/locks/merge.lock` (`PM-IMPL-7`; cross-plan review-bot rate-window claims are separate leases in `<PM_MCP_BASE>/state/review-bot-windows.json`):

[source,text]
----
Plan A (branch-cleanup) ──► [Enqueue FIFO] ──► [Acquire Holder Slot]
                                                      │
                        ┌─────────────────────────────┴─────────────────────────────┐
                        │ Widened Critical Section:                                 │
                        │  1. git fetch + rebase onto base, only when required      │
                        │  2. Post-rebase CI / re-review check                      │
                        │     └─► If async wait required: RELEASE slot & keep FIFO  │
                        │  3. Pre-merge barrier check (last gate before merge)      │
                        │  4. Closed merge dispatch bound to the expected head SHA  │
                        └─────────────────────────────┬─────────────────────────────┘
                                                      ▼
                                            [Release Mutex & Pop]
----

1. *FIFO Admission Queue*: Plans requesting the merge mutex enter an ordered per-repository FIFO `waiting[]` whose entries carry `owner` (the `LeaseOwner`: the owning scope `scope_type`/`scope_id`, here the plan and its `plan_id`, plus the serving `holder_instance`) and `enqueued_at` (link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]). A plan may acquire the active `holder` slot only when it is at the head of the FIFO queue and `holder == null`. Enqueueing is idempotent per owning plan (a waiter already in `waiting[]` keeps its position), and a holder re-requesting the mutex is granted reentrantly without re-queueing.
2. *Widened Hold across Rebase-to-Merge*: Unlike a narrow lock around `gh pr merge`, the merge mutex is acquired **before** `branch-cleanup` decides whether to rebase the feature branch onto `main` (<<merge-path>>, item 3) and held through the merge execution so a sibling plan cannot land a conflicting commit on `main` between that decision and the merge.
3. *Mandatory Release on Every Wait & Abort*: A plan must **never** hold the merge mutex while blocked in an asynchronous wait (`wait:finalize.concurrent-wait` for post-rebase CI, review-bot rate-window wait, merge-queue landing wait, or operator elicitation/escalation) or on abort. Entering any `wait`, `escalate`, or link state inside `branch-cleanup` (`finalize.merge-gap`, `finalize.merge-conflict`, `finalize.merge-sync-escalate`, `finalize.merge-remote-moved`, `finalize.merge-refused`, `finalize.merge-queue-exit`; `finalize.merge-lease-interrupted` holds none) atomically releases `holder = null` while preserving the plan's FIFO queue position, allowing ready sibling plans to merge without head-of-line blocking.
4. *Atomic Stale-Holder & Budget Reclaim*: Reaping runs inside the same short transaction as admission. The lease is owned by the plan, never by the runtime instance: a `holder` whose `holder_instance` is no longer alive (PID plus start instant) is not reclaimed but marked `orphaned_at` at runtime start, and the next call addressing the owning plan adopts it (new `holder_instance`, `orphaned_at` cleared). An active `holder` is released only on positive evidence of abandonment: the owning plan is terminal (`completed`, `aborted`), archived, or no longer resolvable; the holder's lease budget (`lease_expires_at`, refreshed by every heartbeat transition; link:../timeouts/02-runtime-leases-operator-web.adoc#merge-lease[Timeouts & Budgets Specification, Merge Holder Lease]) has expired without adoption; or the provider observation of the holder's pull request (`ci.pr-observe`) reports it merged or closed, recorded in an audit record naming the observation. An unobservable or failed observation releases nothing (ownership and liveness rules: link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]).
5. *Closed Merge Dispatch Set*: `branch-cleanup` executes merges exclusively through one of two closed mechanisms, both bound to the expected head SHA (the `HEAD` the barrier and the grants evaluated; GitHub merge `sha` and enqueue `expectedHeadOid`, GitLab merge and merge-train `sha`): direct `safe-merge` (`ci.merge` with the plan's merge method) or `merge-queue` enqueue (`ci.enqueue`, selected only when the derived fact `merge_queue_enforced` reports a merge queue for the base branch; transitions to `finalize.merge-queue-wait` after releasing the mutex). A head that moved since the evaluation is refused by the provider (`head_moved`) and re-enters `finalize.merge-gate`, so a grant and a barrier verdict hold for exactly the merged commit. Any other provider refusal (`not_mergeable`) releases the mutex and enters `finalize.merge-refused` (<<merge-path>>, item 6); no administrator merge bypasses it.
+
The enqueue counts only after a post-condition read of this PR's own queue membership (`ci.queue-membership`; GitHub: repository `mergeQueue.entries` containing the PR); neither the command's return value or exit code, nor the existence of a queue rule, nor `mergeStateStatus` (which reads `CLEAN` while queued) is membership evidence, and an unobservable membership records `enqueued: indeterminate`. After either mechanism, the merge is confirmed only by the provider's observed pull-request state (`ci.pr-observe` or `ci.queue-membership`: `merged`, with the merge commit on the base branch), never by the merge command's return value or exit code. `finalize.merge-queue-wait` waits for a terminal outcome — `merged`, `ejected`, `closed`, or `timed_out` — because an entry can be ejected on rebase after its checks turned green; every outcome other than `merged` (the terminal queue outcomes, `cancelled`, and the job outcomes `failed`, `refused`, `killed`, `indeterminate`) enters the link state `finalize.merge-queue-exit` (<<merge-path>>, item 7), whose links `retry`, `resume_wait`, `wind_down`, and `abort` are guarded by the observed pull-request and queue state. An `enqueued: indeterminate` enqueue enters the wait as well and is settled by its observation. The wait is bounded by stall, not by a fixed budget: every observed progress of the entry (a change of queue position or entry state) restarts the clock, and `timed_out` is reached only after no progress for twice the queue's check-response timeout (the `check_response_timeout` of the derived fact `merge_queue_enforced`), else the compiled fallback `3600` s. `timed_out` is a no-verdict outcome, never evidence that the entry failed; a landing that ends `timed_out` records no merge verdict. *Deliberate change vs. `plan-marshall`*: `plan-marshall` bounds the wait with a fixed budget.

=== Epic Plan Emission (`emit:<plan_id>`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-41[PM-WATCH-PHASE-41]_

Orchestrator epics (`scope: epic`) manage multi-plan workstreams stored in `.marshall/orchestrator/<epic_id>/` (`epic.json` header and per-plan `.marshall/orchestrator/<epic_id>/queue/<plan_id>.json` files, keyed by the child plan's `plan_id`; the epic-local ordinal is display-only, link:../dispatch-and-effort.adoc[Dispatch & Effort Specification]).

* *Never Dispatch a Plan as a Sub-Agent*: Because sub-agents are single-level leaf workers (`PM-WF-5`) and every plan dispatches its own leaf sub-agents during Phases 2–6, an epic **never** offers a `dispatch` link to launch a plan and **never** executes a plan inline.
* *Staging-Time Surface Disjointness*: Disjointness is a modelling invariant of one epic, not a runtime gate. When the epic stages a plan, the queue row declares its expected surface (`declared_surface`), and the server refuses the staging with `surface_overlap` when it overlaps the declared surface of another non-terminal row of the same epic that is not ordered with it through prerequisites, and with `surface_undeclared` when the surface cannot be declared (link:../dispatch-and-effort/04-epic-coordination.adoc#epic-surface-disjointness[Dispatch & Effort Specification, Staging-Time Surface Disjointness]). There is no cross-epic check and no check against plans started without an epic; such conflicts surface as a rebase conflict (`sync-baseline`, `finalize.merge-sync`) or as a pull request the provider refuses to merge, and are the operator's responsibility.
* *`emit:<plan_id>` Transition (`rel: emit`)*: For each staged plan whose prerequisite rows are in the partition `terminal.shipped` (`merged` or `completed`), the epic state offers `emit:<plan_id>` (emission compares no surfaces); the representation shows the row's re-grounding staleness (`regrounded_at_sha`, `main_commits_since`, link:../dispatch-and-effort.adoc[Dispatch & Effort Specification]). Following `emit:<plan_id>`:
** Updates `.marshall/orchestrator/<epic_id>/queue/<plan_id>.json` atomically (`status = "launched"`) under the epic lock.
** Returns the exact operator bootstrap command (`pm-mcp enter --client <client> plan <plan_id> --from-epic <epic_id>`) in `facts.emitted_command`. Emission is always operator-mediated: there is no `auto_emit` setting, and the server never spawns a background plan session.
** Transitions the epic's view of `<plan_id>` from `launched` to `running` on the next call on the epic scope after `pm_start` has consumed the pending entry record written by `pm-mcp enter` (its session becomes the first row of `plans/<plan_id>/sessions.jsonl`, its `from_epic` the plan's `origin.epic_id`; link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]).
