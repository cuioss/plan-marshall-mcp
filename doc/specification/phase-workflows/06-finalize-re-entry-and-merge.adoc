== Re-Entry & `head_at_completion` Verdict Currency Rules

When Phase 6 re-enters after a loop-back from Phase 5, an in-branch settle commit, a `sync-baseline` rebase, a remediation unit that resolved on a new `HEAD`, or a session resume, the engine decides for each step whether to `SKIP` (preserving its prior `done` verdict) or `RE_FIRE`.

*Remediation inside the Wait Region*: The composite wait `finalize.concurrent-wait` stays the single joint observation of CI, the review bots, and the analysis providers. When several classes fail, one remediation unit runs at a time in the fixed order CI (`remediation.ci-failure`), analysis (`remediation.analysis`), review findings (`remediation.review-findings`), because a code fix for one class invalidates the others' evidence. A unit's await state watches only its own class at the new `HEAD`. After `resolved` or `waived` the caller re-enters `finalize.next-step`, and verdict currency re-fires the wait region for every class that is stale at the new `HEAD`, so a CI fix is followed by a fresh review and analysis observation. The merge path follows the same pattern (<<merge-path>>).

=== Fail-Closed `head_at_completion` Anchor Obligation
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-22[PM-WATCH-PHASE-22]_

* Every step with `headDependent == true` must record `head_at_completion: "<40-hex-sha>"` in `mcp/status.json` when transitioning to `done`.
* Any attempt to record `done` for a `headDependent == true` step without a valid `head_at_completion` SHA is **refused** (`error: "missing_head_at_completion"`).
* The server derives `head_at_completion` from `git rev-parse HEAD` of the plan's worktree in the same transition that records `done`; no link accepts it as a parameter. The same rule holds for every recorded commit identity (`reviewed_commit_sha`, `commit_sha`, `branch_pushed_at.head_sha`) and for `pr_number`, so an invented or padded SHA can never enter a step record.
* On re-entry, if a step's persisted record lacks `head_at_completion`, the engine reports the prior record as `unverified` and unconditionally re-fires the step.

=== Deterministic Verdict Currency Algorithm (`VerdictCurrencyEvaluator`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-23[PM-WATCH-PHASE-23], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-62[PM-WATCH-PHASE-62]_

[[verdict-input-scope]]*Verdict Input Scope (`input_scope`)*: Every `headDependent == true` step descriptor declares `input_scope` from a closed enum, validated by `FinalizePipelineValidator` rule 6 (a missing value is a validation error, never a default):

* `remote_state`: the verdict is a property of remote state (`ci-verify`, `automatic-review`, `analysis-roundtrip`); currency is decided by remote evidence, and the recorded verdict is stale on every change of `HEAD`. `verdict_inputs` is empty.
* `open_ended`: the step's body runs something open-ended over the repository, so no sound input subset exists; the verdict is stale on every change of `HEAD`. A step has no sound subset when any of three shapes applies: (1) a test suite that asserts against the real tree, (2) a scan whose inputs are discovered at run time rather than fixed, (3) a whole-repository walk. Example: `pre-push-quality-gate`. `verdict_inputs` is empty.
* `plan_footprint`: the step's subject is the plan's changes; the scope resolves at evaluation time to the realized footprint (Footprint-Scoped Inputs below). `verdict_inputs` is empty.
* `declared`: the step's verdict is a property of named files; `verdict_inputs` lists them as explicit, non-empty globs naming what determines the truth of the recorded claim.

For a `headDependent == true` step $S$ with recorded `head_at_completion` $= H_{\text{rec}}$ and current worktree `HEAD` $= H_{\text{cur}}$:

[source,java]
----
package de.cuioss.pm.core.workflow.finalize;

import java.util.List;
import java.util.Optional;
import java.util.Set;

public enum CurrencyVerdict {
    CURRENT_SAME_HEAD,
    PRESERVED_INPUTS_UNAFFECTED,
    STALE_MISSING_ANCHOR,
    STALE_REBASE_ADVANCED,
    STALE_UNSCOPED_HEAD_CHANGE,
    STALE_INPUTS_MODIFIED
}

public final class VerdictCurrencyEvaluator {

    public CurrencyVerdict evaluate(
            FinalizeStepDescriptor step,
            String recordedHeadSha,
            String currentHeadSha,
            boolean rebaseReplayedCommits,
            Set<String> changedRepoRelativePaths) {

        if (recordedHeadSha == null || recordedHeadSha.isBlank()) {
            return CurrencyVerdict.STALE_MISSING_ANCHOR;
        }
        if (recordedHeadSha.equals(currentHeadSha) && !rebaseReplayedCommits) {
            return CurrencyVerdict.CURRENT_SAME_HEAD;
        }
        // changedRepoRelativePaths is the tree diff H_rec..H_cur (git diff --name-only H_rec H_cur);
        // after a replaying rebase it includes the upstream changes the rebase pulled in.
        // inputScope is present on every headDependent step (FinalizePipelineValidator rule 6).
        List<String> globs;
        switch (step.inputScope().orElseThrow()) {
            case REMOTE_STATE, OPEN_ENDED -> {
                // remote_state: currency is decided by remote evidence; open_ended: no sound
                // input subset exists. Both are stale on every change of HEAD.
                return rebaseReplayedCommits
                    ? CurrencyVerdict.STALE_REBASE_ADVANCED
                    : CurrencyVerdict.STALE_UNSCOPED_HEAD_CHANGE;
            }
            case PLAN_FOOTPRINT -> {
                // realized footprint plus the paths the step's own commits touched
                Optional<List<String>> footprint = resolvePlanFootprint(step);
                if (footprint.isEmpty()) {
                    return CurrencyVerdict.STALE_UNSCOPED_HEAD_CHANGE;   // unresolvable: fail-closed
                }
                globs = footprint.get();
            }
            case DECLARED -> globs = step.verdictInputs();   // non-empty by validation
        }
        boolean anyInputTouched = changedRepoRelativePaths.stream()
            .anyMatch(path -> matchesAnyFnmatchGlob(path, globs));
        return anyInputTouched
            ? CurrencyVerdict.STALE_INPUTS_MODIFIED
            : CurrencyVerdict.PRESERVED_INPUTS_UNAFFECTED;
    }
}
----

* *No Re-Stamp on Preserve Invariant*: When `VerdictCurrencyEvaluator` returns `PRESERVED_INPUTS_UNAFFECTED` (because `git diff --name-only <H_rec>..<H_cur>` touched zero paths matching the step's resolved inputs), the step is skipped and its persisted `head_at_completion` **remains $H_{\text{rec}}$** — it is **never** overwritten with $H_{\text{cur}}$. Keeping $H_{\text{rec}}$ ensures that subsequent commits are always diffed against the cumulative range since the step actually executed.
* *Rebase vs No-Op Rebase*: A step declaring `advancesMainViaRebase == true` (`sync-baseline`, `branch-cleanup`) can invalidate downstream verdicts **only** when it actually replayed commits (`action == "rebased"` and `upstream_commit_count > 0`). When the branch was already up-to-date (`work_performed == false`), `HEAD` does not change and existing verdicts remain current.
* *Path-Derived Re-Fire After a Replaying Rebase*: A replaying rebase does not by itself stale a verdict. The changed paths are the tree diff between $H_{\text{rec}}$ and $H_{\text{cur}}$, which includes the upstream changes the rebase pulled in, and a `declared` or `plan_footprint` step re-fires iff that diff touches its resolved inputs (`STALE_INPUTS_MODIFIED`), in both directions: an upstream change to an input re-fires the step even when the plan's own commits did not touch it, and an unrelated upstream change never re-fires it. Only `remote_state` and `open_ended` steps return `STALE_REBASE_ADVANCED`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` classifies by the same tree diff over declared `verdict_inputs`, but an absent declaration is legal there and silently means "invalidated on every `HEAD` change" (in practice no bundled step declares `verdict_inputs`); `PM-MCP` requires an explicit `input_scope` on every head-dependent step and validates it at build time and startup, and adds the resolved `plan_footprint` scope that `plan-marshall`'s static glob vocabulary cannot express.
* *Footprint-Scoped Inputs (`plan_footprint`)*: A step whose subject is the plan's changes (`simplify`, `security-audit`, `pre-submission-self-review`) declares `input_scope: plan_footprint` with empty `verdictInputs`; the evaluator resolves the scope at evaluation time to the realized footprint (link:../store-schemas/13-leases-integrity-testing.adoc#three-way-footprint[Store Schemas Specification, Three-Way File Footprint Reconciliation]) together with the paths the step's own commits touched. An unresolvable footprint makes the verdict `STALE_UNSCOPED_HEAD_CHANGE` (fail-closed).
* *Skip Basis*: Every currency decision, skip or re-fire, is persisted on the step record as `skip_basis` (`verdict`, `h_rec`, `h_cur`, `changed_paths_count`, `inputs_touched`), so a skip is auditable and never leaves no record.

=== Step Records, Re-Fire & Loop-Back Rules
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-11[PM-WATCH-PHASE-11], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-21[PM-WATCH-PHASE-21], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-71[PM-WATCH-PHASE-71], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-79[PM-WATCH-PHASE-79], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-11[PM-WATCH-DSL-11]_

* *Settled Completions Only*: A step completion record is emitted only for settled outcomes. A `fix_requested` of a remediation unit (the `loop_back` form of `fix`) and a defer emit none, so a re-fired step never produces two completions.
* *Completion per Firing*: A step's firing opens on entry to a beginning state of the step when no firing of it is open; re-entry continues the open firing; each firing completes exactly once, at the next opening of the same step, at order `70`, or at a terminal, and a remediation call belongs to the firing that made it. The persisted step record keeps one entry per firing (`firings[]` with `job_id` (the model job of the firing, if any), `fired_at`, `outcome` (`running` while open), and `cause`: `first`, `loop_back`, `failure`, `error`, or `input_changed`); the current outcome is the last firing's. When `VerdictCurrencyEvaluator` decides `RE_FIRE`, the step's outcome is set to `unverified` before the step runs and is replaced by the new terminal outcome; a prior `done` never survives a re-fire, a refused outcome change is appended as a firing and never leaves the prior outcome silently current, and no force flag exists. Re-fire counts are derived from the firings per cause, never from the step-outcome log. Each firing also records `productive` (it produced a commit or filed a finding, derived from the change ledger and the findings store), so re-fires are published split into productive and unproductive ones and an unproductive re-fire pattern is visible beside the remediation counters (link:../workflow-dsl/07-loop-back-diagrams-verification.adoc#loop-back-bounds[Workflow DSL Specification]).
* *Phase-Exit Completeness*: The check is positional. Entering a step of order N requires, for every step of the plan instance of order < N, a satisfied outcome: `done` or `skipped` whose currency verdict against the current `HEAD` is `CURRENT_SAME_HEAD` or `PRESERVED_INPUTS_UNAFFECTED` (for steps that are not `headDependent`, the presence of `done` in the current firing), or `waived` (the step completed by a remediation unit's `waived` outcome, with the waiver id kept on the step record and its stale `head_at_completion` kept as the record); a stale `done`, or a firing from an earlier remediation round, counts as missing. A `waived` completion never satisfies a barrier predicate by itself: the Pre-Merge Review Barrier still evaluates `HEAD` and admits a failure only through a waiver lookup that logs a consumption. At `branch-cleanup` (70) entry the check runs before any rebase that `branch-cleanup` performs. `merge.gate-entry` and `finalize.next-step` evaluate it through one shared `PhaseExitCompleteness` evaluator, and `finalize.next-step` never selects order `70` while a step of lower order is unmet (<<merge-path>>, item 1). Currency evidence produced inside `branch-cleanup` after its own rebase (fresh CI and review results on the rebased `HEAD`) is recorded on the affected remote-state steps as their new evidence; it is obtained by `finalize.merge-evidence-wait`, a beginning state of those steps (firing cause `input_changed`) that runs the composite CI, analysis, and review-bot watch over the rebased `HEAD` with the merge lease released (<<merge-path>>, item 4). Both transitions into the post-merge band on `merged` complete `default:branch-cleanup` as `done`. A plan that took a fallback runs a post-run-only instance version, whose steps below order `900` are pruned, so the check covers only the post-run band; its begun `branch-cleanup` firing was recorded `failed` on entry to `finalize.hand-back`. Phase 6 exit (after the merge, when no worktree `HEAD` exists) requires every step of order > 70 to have a settled outcome (`done`, `skipped`, or `waived`) and checks no currency, since nothing is merged anymore.
* *No Operator Skip*: No verb skips or force-completes a step; the only operator influence on a step is a waiver of a gate the step evaluates.
* *Stale-Finding Re-Anchor*: Before a remediation unit offers its `fix`, every open finding of its class is re-anchored against `HEAD` (from the commit it was raised against); a finding whose cited location no longer exists is resolved as stale (status `resolved`, `resolution: taken_into_account`, recorded and never counted as fixed). If only stale findings remain, the unit ends `resolved`.

[#merge-path]
== Merge Path (`branch-cleanup`)
_See Requirement link:../../Requirements.adoc#PM-WF-13[PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier]_

_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-18[PM-WATCH-PHASE-18], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-44[PM-WATCH-PHASE-44], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-74[PM-WATCH-PHASE-74], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-79[PM-WATCH-PHASE-79], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-80[PM-WATCH-PHASE-80], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-81[PM-WATCH-PHASE-81], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-82[PM-WATCH-PHASE-82], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-83[PM-WATCH-PHASE-83], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-85[PM-WATCH-PHASE-85], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-93[PM-WATCH-PHASE-93]_

`default:branch-cleanup` (`order = 70`) runs as a chain of states, so that every remediation unit it calls returns to an `auto` state and the merge lease is held only while no wait is open (link:../state-catalogue/04-plan-finalize-terminal.adoc#state-catalogue-finalize[State Catalogue, Phase 6: `finalize`]). No state of the chain asks the operator; every failure has a remediation policy or a bounded retry and ends, when spent, in `finalize.hand-back` (item 8).

1. *Gate Entry* (`finalize.merge-gate`, `auto merge.gate-entry`): runs the finalize spend check, the only evaluation point of the gate `spend` (an overrun calls `remediation.spend`: its only remedies are an operator `met` waiver of gate `spend`, within the waiver wait or set earlier, and the fallback), re-attempts the transmission of every finding whose `transmit_outcome` is `not_sent`, `partial`, or `sent_unresolved` (idempotent per finding and disposition) so that the barrier never fails on a transmission a retry would repair, and runs Phase-Exit Completeness. It is the re-entry target of every remediation unit of the merge path that ended `resolved` or `waived`, and of a moved head at dispatch. Its outcomes: `incomplete` (`missing_steps`) enters `finalize.next-step`, which re-fires the lowest-order unmet step; `terminus_review_owed` (a consumed `review_evidence` waiver covers a `HEAD` no bot reviewed) runs the review chain terminus (Step Catalogue row `8`) and returns here; `local_only` (no push remote) enters `finalize.hand-back` in its local form (item 8); otherwise the lease is requested. `merge.gate-entry` and `finalize.next-step` use one shared `PhaseExitCompleteness` evaluator, and `finalize.next-step` never selects order `70` while a lower-order step is unmet.
2. *Lease* (`finalize.merge-lease`, job): FIFO admission to the Cross-Plan Merge Mutex (<<_cross_plan_merge_mutex_fifo_admission_queue>>); the plan rests until it holds the lease. A lease job that ends `failed`, `timed_out`, `cancelled`, `killed`, `refused`, or `indeterminate` enters the link state `finalize.merge-lease-interrupted`, which holds no lease and shows the job outcome (`timed_out` as `no_verdict`) and the FIFO position in `facts`. It offers `retry` (re-enters the lease job; the enqueue is idempotent, so the position is kept, except after `cancelled`, which rejoins at the tail), bounded by the compiled condition budget, and `hand_back`; a spent budget enters `finalize.hand-back`.
3. *Sync Only When Required* (`finalize.merge-sync`, `auto`): the plan branch is rebased onto `origin/<base_branch>` and pushed with an explicit lease (the expected remote SHA is the last recorded push, link:../workflow-dsl/06-reusable-sub-workflows.adoc#_six_stage_execution_contract_of_git_commit_and_push[Workflow DSL Specification, Stage 6]) only when the derived fact `branch_up_to_date_required` holds (the provider requires an up-to-date branch; a `stale` or `failed` fact is `indeterminate` and counts as holding) or when the base changed, since the merge base, a path of the plan's realized footprint. Otherwise no rebase runs (`not_required`) and the evidence already gathered for `HEAD` stands. A base that is already an ancestor of `HEAD` is never rebased. Independently of the rebase, `merge.sync-base` pushes with the explicit lease whenever the local `HEAD` differs from the last recorded push, even when the base is already an ancestor, and every such push (outcome `pushed`) leads through the evidence wait (item 4), so the barrier never evaluates a `HEAD` the remote does not hold. A lease-protected push to the plan's own branch after this server rebase is routine; any other force push is refused. *Deliberate change vs. `plan-marshall`*: `plan-marshall` always rebases before merging; an unnecessary rebase costs a CI and review round and a forced push.
+
Every sync outcome other than success releases the lease first. A rebase `conflict` (the conflicted paths and the base commits that touched them are the evidence) and a push rejected by the lease (`rejected_lease`: the remote branch moved; the branch is reset to the pre-rebase `HEAD`, and the observed `remote_sha` and the foreign commits are the evidence) call `remediation.merge-conflict` (retry `0`, fix `2`): its `fix` resolves the conflict or integrates the observed remote head in-branch (server primitive `merge.integrate-remote`; the foreign commits are kept, never overwritten), `resolved` re-enters `finalize.merge-gate`, and `exhausted` and `stepped_out` enter `finalize.hand-back`. An interrupted rebase is aborted by the server before the unit's frame unwinds. No link offers a forced push over foreign commits. A fetch failure and a push failure other than the lease rejection end the sync `sync_failed` (the failing operation and its output are the evidence): it releases the lease and re-enters `finalize.merge-gate` within the compiled server-rule retry budget (link:../timeouts/01-job-budgets-and-waits.adoc#server-rule-retry[Timeouts & Budgets Specification, Server-Rule Retry Budget]), and a spent budget enters `finalize.hand-back`. For a `land` plan the unit is bound with `actions: [retry]` (xref:02-planning-lanes-phases-3-4.adoc#land-lane[Land Lane (`local_changes`)]), so a conflict hands the plan back.
4. *Evidence Wait* (`finalize.merge-evidence-wait`, `composite_job`, a beginning state with firing cause `input_changed`): after a rebase or push, CI, the analysis providers, and the review bots evaluate the pushed `HEAD`; the lease is released for the wait and the FIFO position kept; `all_green` re-enters the gate, and every other outcome routes as in `finalize.concurrent-wait`: to the remediation units in the order CI, analysis, review findings, whose `resolved` or `waived` re-enters `finalize.merge-gate`. A constituent job ending other than in success (`killed`, `timed_out`, `indeterminate`, `refused`, `failed`) ends the wait `watch_interrupted{constituent, fate}`, a deliberate cancel of the wait ends it `cancelled`, and both enter the `auto` state `finalize.restart-watch`, which restarts the watch explicitly within a compiled restart budget (default `2` per wait-region firing); a spent budget enters `finalize.hand-back`. The same rule applies to `finalize.concurrent-wait`.
5. *Barrier* (`finalize.merge-barrier`, `auto`): under the held lease, the Dependency Delta Check (xref:05-finalize-review-metrics-descriptor.adoc#dependency-delta[Dependency Delta Check (Pre-Merge)]) and the Pre-Merge Review Barrier (<<_two_fail_closed_barrier_predicates>>) evaluate `HEAD` with the waiver lookups of <<waiver-lookup>>. `pass` continues to the dispatch; when the operator's merge policy `merge.auto_merge` is `false`, the plan instance has no merge execution (the states `finalize.merge-dispatch`, `finalize.merge-queue-wait`, and `finalize.merge-queue-exit` pruned with reason `auto_merge_off`, link:../workflow-dsl/09-plan-instance.adoc#composition-rules[Workflow DSL Specification, Composition Rules]), and the barrier's passing outcome is `pass_hand_back`, which completes `default:branch-cleanup` as `done` and enters the ready form of `finalize.hand-back` (item 8). Every failing outcome releases the lease and calls the unit of its class: `findings_untriaged` (Predicate 1 fails only through findings without a terminal disposition) and `evidence_missing` (a required bot without review evidence on `HEAD`) call `remediation.review-findings`, whose triage state settles each finding before its `decide` offers `retry` (bot re-trigger), `fix` (in-branch), and `request_waiver`; a red required CI check calls `remediation.ci-failure`. `resolved` and `waived` re-enter `finalize.merge-gate`; `exhausted` and `stepped_out` enter `finalize.hand-back`. A barrier that cannot evaluate the findings store ends `indeterminate`: the gate re-evaluates within the retry budget, then the plan is handed back with the cause; an unevaluable barrier is never waivable and never a pass.
6. *Dispatch Bound to the Head* (`finalize.merge-dispatch`, `auto`): `ci.merge` or, when the derived fact `merge_queue_enforced` reports `enforced`, `ci.enqueue`, both with the expected head SHA, the `HEAD` the barrier and the waiver lookups evaluated (item 5 of <<_cross_plan_merge_mutex_fifo_admission_queue>>). A head that moved since (`head_moved`) re-enters the gate. A merge counts only from `ci.pr-observe`; an enqueue enters `finalize.merge-queue-wait`, and so does an `enqueued_indeterminate` enqueue, with the lease released: the wait's observation settles it (queue membership is progress, `merged` is `merged`, an open pull request that is not queued is `ejected`, an unobservable membership runs into the stall bound and ends `timed_out`, a no-verdict outcome). A provider refusal `not_mergeable` releases the lease; `facts.reason` is one of the closed class `conflict`, `behind`, `checks_pending`, `checks_failed`, `review_required`, `blocked`, `draft`, `method_not_allowed`, `unknown`. `behind` and `conflict` mark `branch_up_to_date_required` stale and re-enter `finalize.merge-gate`, so the next sync rebases; `checks_pending` and `checks_failed` re-enter the gate, whose evidence wait and barrier observe the checks; these re-entries are bounded by a compiled retry budget. `review_required`, `blocked`, `draft`, `method_not_allowed`, and `unknown` are a refusal of the merge action by the provider's protection rules, which is not waivable: the plan enters `finalize.hand-back`, as it does when the retry budget is spent. *Deliberate change vs. `plan-marshall`*: no link, no waiver, and no operator consent merges over a provider refusal; `plan-marshall`'s administrator merge (`gh pr merge --admin`) has no counterpart.
7. *Queue Exit* (`finalize.merge-queue-exit`, `auto`): every wait outcome of `finalize.merge-queue-wait` other than `merged` enters it with the exit outcome, the observed pull-request and queue state, and the ejection reason. It routes by that observation: an open pull request that is not queued (`ejected`) re-enters `finalize.merge-gate` within the compiled retry budget; a pull request that is still queued after `timed_out` or `cancelled`, or after a job outcome `failed`, `refused`, `killed`, or `indeterminate`, resumes the wait within the restart budget of item 4; a `closed` pull request and every spent budget enter `finalize.hand-back`.
8. *Hand-Back* (`finalize.hand-back`, `auto`): the one fallback state of Phase 5, the `land` lane, and finalize before the merge (xref:01-planning-phases-1-2.adoc#plan-outcomes[Plan Outcomes & Fallback Routes]). Its entering transaction records every begun, unsettled step `failed` (so `default:branch-cleanup` completes `failed`) and composes the post-run-only instance version (event `fallback`, prune reason `handed_back`). It settles uncommitted work (commit only, footprint-checked), captures the realized footprint, removes the worktree, and delivers the work in one of four forms: *before `create-pr`* it pushes the branch and opens the pull request as a draft; *after `create-pr`* it leaves the existing pull request open; in the *ready form* (the barrier passed under `merge.auto_merge: false`, gap `cause: auto_merge_off`) it marks the existing pull request ready for review (never a draft) and leaves it open for a human merge, recording `merge_outcome: awaiting_human_merge`; in each of these it posts the idempotent gap comment (gap record, waiver consumptions, expired waiver requests) and sets the label `pm-mcp:handed-back`. The *local form* (no push remote, or a fallback that lacks what it needs, such as a push credential) keeps the plan branch as the product, records `merge_outcome: local_only` for a local-only project, and completes `default:branch-cleanup` as `done`. Late findings are carried out as after a merge. A plan branch without any commit beyond the base ends `returned` instead. The post-run band follows, and `archive-plan` derives the `merge_outcome` through the merge outcome mapping (`handed_back` for an open pull request, `awaiting_human_merge` for the ready form's open pull request, `declined` when it was observed closed, `dequeued` when it was ejected, `enqueued_not_landed` when it is still queued, with the owed item `post_merge_cleanup`). A `land` plan keeps its capture ref and owes `capture_ref_retained`.
9. *Post-Merge*: on `merged`, the realized footprint is captured, the worktree removed, the branch refs removed, the lease released, and the merge record written (`merge_state`, `merge_commit_sha`, `review_state`, the waiver consumptions); the plan continues in the post-merge band. For a `land` plan the post-merge actions of `finalize.merge-dispatch` and `finalize.merge-queue-wait` then decide the capture ref (xref:02-planning-lanes-phases-3-4.adoc#land-lane[Land Lane (`local_changes`)], item 5); the main checkout is never moved.

[#pre-merge-barrier]
== Pre-Merge Review Barrier & Waivers

Inside `default:branch-cleanup` (`order = 70`), immediately before executing the merge command (`pr safe-merge` or `merge-queue` enqueue), the engine enforces the fail-closed **Pre-Merge Review Barrier** in the state `finalize.merge-barrier` (<<merge-path>>, item 5).

=== Two Fail-Closed Barrier Predicates
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-24[PM-WATCH-PHASE-24], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-25[PM-WATCH-PHASE-25], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-33[PM-WATCH-PHASE-33]_

Both predicates must evaluate to `true` against the current worktree `HEAD` SHA ($H_{\text{cur}}$), or their failure must be covered by a consumed waiver:

1. *Predicate 1 — Zero Unhandled Findings*: Every finding in the findings store originating from `automatic-review` (sources `github_pr`, `gitlab_mr`), `ci-verify` (source `ci`), or the analysis providers (source `sonar` and every further provider source), and every other finding with `blocking == true` of any `source` of the findings store's source enumeration (`self_review`, `qgate`, `security_audit`, `code_review`, `arch_gate`, `compiler`, `self_report`, `dependency_delta`), must have a persisted, terminal triage disposition (`FIX`, `SUPPRESS`, or `ACCEPT`; status `triaged_*` or `resolved`) whose server-written `resolution` is not `pending`, or be covered by a `findings:<class>` waiver (never for security findings); a `FIX` whose fix has not landed is still `pending` and fails the predicate. A finding with a provider address (`provider_ref`) must also have its outbound response or dismissal transmitted to the provider (`transmit_outcome == "sent"`), which requires a per-finding reply on the finding's own thread or comment; a bot's own resolution marker or a PR-level note is not a response. An unmet triage commitment (Unified Triage) fails the predicate. *Deliberate change vs. `plan-marshall`*: `plan-marshall` counts only pending PR-comment findings and does not require transmission; `PM-MCP` covers every blocking finding and requires the response to be transmitted.
2. *Predicate 2 — Required-Bot Participation on Current `HEAD`*: Every bot in the required set (resolved from `required_bots` against the review-bot registry, xref:05-finalize-review-metrics-descriptor.adoc#automatic-review[Automatic Review: Registry, Participation, Refusals & Ingestion]) must have a participation record (link:../store-schemas/03-findings-and-review-records.adoc#review-participation[Store Schemas Specification]) whose `state` is `participated` or `participated_but_empty`, whose `reviewer_login` equals the bot's registered `author_login`, and which passes the review currency test for $H_{\text{cur}}$. A SHA match without an author match never satisfies the predicate. A `bot_status` other than `completed` (link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations]), and every other per-bot state (xref:05-finalize-review-metrics-descriptor.adoc#automatic-review[Automatic Review: Registry, Participation, Refusals & Ingestion]: in particular `not_triggered`, `refused` of any mode, including a spend-capped or quota-exhausted reviewer, `declined`, `unproven`, `unreadable`, and `silent`), **never** satisfies Predicate 2; only a consumed `review_evidence` (or `review_evidence:<bot_kind>`) waiver lets the merge proceed without it.
+
*Review Currency*: The currency test applies to every required bot; no registry field exempts a bot from it. Its strictness is the team setting `review.currency` (`.marshall/config/project.json`, link:../store-schemas/07-project-configuration.adoc#config-project-json[Store Schemas Specification]): `exact_sha` requires `covered_commit_sha` to equal $H_{\text{cur}}$; `after_last_push` (the default) accepts a `covered_commit_sha` equal to $H_{\text{cur}}$, or, for a bot whose registry declares `reviewed_sha_carrier: none`, review evidence whose `created_at` is later than the last push of the branch (`branch_pushed_at`). A review evidence object that names a commit other than $H_{\text{cur}}$ never passes, and a latest evidence object that predates the last push resolves `unproven`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` applies currency only to bots whose registry declares `participation_requires_update`, so one exempt bot disables the test for the ANDed gate; `PM-MCP` evaluates currency per bot record for every required bot.
+
*Empty Required Set*: An empty required set satisfies Predicate 2 only as the roster aggregate `vacuous` (the team answered with an empty list: `review.required_bots: []` in `project.json`): the merge proceeds and records `review_state: vacuous` on the merge record and the landing. The roster aggregate `unestablished` (the key is absent: the question was never answered) fails Predicate 2; only a consumed `review_evidence` waiver proceeds, and the merge records `review_state: unreviewed_by_waiver`. A merge whose required bots all satisfy Predicate 2 records `review_state: reviewed`.

If the findings store cannot be evaluated, the barrier ends `indeterminate` (<<merge-path>>, item 5), neither a pass nor a waivable failure. A refusal of the barrier lists each blocking finding (`finding_id`, `source`, `severity`, age, failing predicate) in `facts`, never only a count.

=== Waivable Merge Gates
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-57[PM-WATCH-PHASE-57], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-80[PM-WATCH-PHASE-80]_

Every gate of the merge path that a plan may pass over a failure is a waivable gate of the closed list (xref:07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Waivers & Operator Verbs]); every other failure has only its remediation policy and the fallback. HEAD binding alone is never authorization, and nothing the model submits authorizes a merge.

[cols="2,2,4"]
|===
|Merge-path failure |Waivable as |Otherwise

|Missing review evidence of a required bot (Predicate 2), including a re-review that timed out after a rebase
|`review_evidence`, `review_evidence:<bot_kind>`
|`remediation.review-findings` (`evidence_missing`), then `finalize.hand-back`. The re-review wait derives from the required bots' open rate windows or registered intervals (xref:05-finalize-review-metrics-descriptor.adoc#_refusals_rate_windows[Refusals & Rate Windows]; values in link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows]), never from a flat value.

|Open findings after triage (Predicate 1)
|`findings:<class>`, `findings:<provider>` (never security findings)
|`remediation.review-findings`, then `finalize.hand-back`.

|A named failing CI check
|`ci_check:<check_name>`
|`remediation.ci-failure`, then `finalize.hand-back`.

|The quality gate of an analysis provider
|`analysis_gate:<provider>`
|`remediation.analysis`, then `finalize.hand-back`.

|Finalize spend over the budget anchor
|`spend` (a `met` waiver; `spend` is no `raise` target)
|`remediation.spend`, then `finalize.hand-back`.

|A provider refusal of the merge action (branch protection, required review, draft, merge method)
|not waivable
|`finalize.hand-back` (<<merge-path>>, item 6).
|===

*Deliberate change vs. `plan-marshall`*: the merge-authorization roster (`barrier-ask-override`, `pre-merge-consent`, `red-ci-override`, `rereview-timeout-override`, `automatic-review-force-done`), its gap classes, and the operator's per-merge consent do not exist; a plan whose barrier passes merges without asking. The operator's standing merge policy `merge.auto_merge` (`local-config.json`, default `true`) applies: `false` stops every plan of the project before the merge (item 5) and hands back a ready pull request; it never passes a barrier predicate or a gate and is not a waiver. `plan-marshall`'s `re_review_on_timeout: proceed` policy branch (`branch-cleanup-rereview.md`), which merges unreviewed code without an operator, has no counterpart: a timed-out re-review proceeds only under an operator-written `review_evidence` waiver.

[#waiver-lookup]
=== Waiver Lookup & Consumption
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-32[PM-WATCH-PHASE-32], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-57[PM-WATCH-PHASE-57], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-70[PM-WATCH-PHASE-70], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-81[PM-WATCH-PHASE-81]_

* *Operator-Only Records*: Waivers are written only by the operator API (`pm-operator waive`); no primitive has a waiver-write capability, and the server never creates one. Free-text lines in logs or pull-request comments are never accepted as a waiver.
* *Lookup at Evaluation*: A waivable gate admits a failure only through `waiver.lookup` at the moment it evaluates, naming a gate of the closed list; a non-waivable gate has no lookup. A `met` waiver is plan-scoped: it applies to every later evaluation of that gate (a known-flaky check stays waived after a later push), not only to the `HEAD` it was set for.
* *Consumption Names What It Covered*: Every evaluation that relies on a waiver appends a consumption (`at`, state, `head_sha`, the covered items: check names, finding ids, bot kinds). A finding filed after an evaluation is covered only by a later evaluation's consumption, so the record always names exactly what each merge-path evaluation let through. The consumptions are posted as an idempotent pull-request comment and listed in the landing record.
* *Merges under a Review Waiver Are Marked Unreviewed*: A merge that proceeds under a consumed `review_evidence` waiver records `review_state: unreviewed_by_waiver` (with the waiver id and the commit no review covered) on the merge record, in a pull-request comment the server posts, and in the landing; it is never reported as a reviewed merge.
* *Timing*: A waiver is too late once the fallback was taken (`plan_ended`); `unwaive` is refused after a consumption (`already_consumed`).

=== Cross-Plan Merge Mutex & FIFO Admission Queue
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-44[PM-WATCH-PHASE-44], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-45[PM-WATCH-PHASE-45], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-78[PM-WATCH-PHASE-78], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-83[PM-WATCH-PHASE-83]_

When multiple plans execute concurrently across worktrees of the same repository, `default:branch-cleanup` (`order = 70`) serializes their rebase-and-merge critical sections through the **Cross-Plan Merge Mutex** (`MergeMutexManager`), a lease persisted in `<PM_MCP_BASE>/state/merge-queue.json` whose updates run as short transactions under `<PM_MCP_BASE>/locks/merge.lock` (`PM-IMPL-7`; cross-plan review-bot rate-window claims are separate leases in `<PM_MCP_BASE>/state/review-bot-windows.json`):

[source,text]
----
Plan A (branch-cleanup) ──► [Enqueue FIFO] ──► [Acquire Holder Slot]
                                                      │
                        ┌─────────────────────────────┴─────────────────────────────┐
                        │ Widened Critical Section:                                 │
                        │  1. git fetch + rebase onto base, only when required      │
                        │  2. Post-rebase CI / re-review check                      │
                        │     └─► If async wait required: RELEASE slot & keep FIFO  │
                        │  3. Pre-merge barrier check (last gate before merge)      │
                        │  4. Closed merge dispatch bound to the expected head SHA  │
                        └─────────────────────────────┬─────────────────────────────┘
                                                      ▼
                                            [Release Mutex & Pop]
----

1. *FIFO Admission Queue*: Plans requesting the merge mutex enter an ordered per-repository FIFO `waiting[]` whose entries carry `owner` (the `LeaseOwner`: the owning scope `scope_type`/`scope_id`, here the plan and its `plan_id`, plus the serving `holder_instance`) and `enqueued_at` (link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]). A plan may acquire the active `holder` slot only when it is at the head of the FIFO queue and `holder == null`. Enqueueing is idempotent per owning plan (a waiter already in `waiting[]` keeps its position), and a holder re-requesting the mutex is granted reentrantly without re-queueing.
2. *Widened Hold across Rebase-to-Merge*: Unlike a narrow lock around `gh pr merge`, the merge mutex is acquired **before** `branch-cleanup` decides whether to rebase the feature branch onto `main` (<<merge-path>>, item 3) and held through the merge execution so a sibling plan cannot land a conflicting commit on `main` between that decision and the merge.
3. *Mandatory Release on Every Wait, Remediation & Ending*: A plan must **never** hold the merge mutex while blocked in an asynchronous wait (post-rebase CI and review evidence, review-bot rate-window wait, merge-queue landing wait, a waiver wait), while a remediation unit runs, or when it ends. Entering any wait, any remediation call, or any link state inside `branch-cleanup` (`finalize.merge-lease-interrupted` holds none), and entering `finalize.hand-back` or `plan.aborted`, atomically releases `holder = null` while preserving the plan's FIFO queue position where the plan continues, allowing ready sibling plans to merge without head-of-line blocking.
4. *Atomic Stale-Holder & Budget Reclaim*: Reaping runs inside the same short transaction as admission. The lease is owned by the plan, never by the runtime instance: a `holder` whose `holder_instance` is no longer alive (PID plus start instant) is not reclaimed but marked `orphaned_at` at runtime start, and the next call addressing the owning plan adopts it (new `holder_instance`, `orphaned_at` cleared). An active `holder` is released only on positive evidence of abandonment: the owning plan is terminal (`completed`, `handed_back`, `returned`, `aborted`), archived, or no longer resolvable; the holder's lease budget (`lease_expires_at`, refreshed by every heartbeat transition; link:../timeouts/02-runtime-leases-operator-web.adoc#merge-lease[Timeouts & Budgets Specification, Merge Holder Lease]) has expired without adoption; or the provider observation of the holder's pull request (`ci.pr-observe`) reports it merged or closed, recorded in an audit record naming the observation. An unobservable or failed observation releases nothing (ownership and liveness rules: link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]).
5. *Closed Merge Dispatch Set*: `branch-cleanup` executes merges exclusively through one of two closed mechanisms, both bound to the expected head SHA (the `HEAD` the barrier and the waiver lookups evaluated; GitHub merge `sha` and enqueue `expectedHeadOid`, GitLab merge and merge-train `sha`): direct `safe-merge` (`ci.merge` with the plan's merge method) or `merge-queue` enqueue (`ci.enqueue`, selected only when the derived fact `merge_queue_enforced` reports a merge queue for the base branch; transitions to `finalize.merge-queue-wait` after releasing the mutex). A head that moved since the evaluation is refused by the provider (`head_moved`) and re-enters `finalize.merge-gate`, so a barrier verdict and its waiver consumptions hold for exactly the merged commit. Any other provider refusal (`not_mergeable`) releases the mutex and is routed by its reason (<<merge-path>>, item 6); no administrator merge bypasses it.
+
The enqueue counts only after a post-condition read of this PR's own queue membership (`ci.queue-membership`; GitHub: repository `mergeQueue.entries` containing the PR); neither the command's return value or exit code, nor the existence of a queue rule, nor `mergeStateStatus` (which reads `CLEAN` while queued) is membership evidence, and an unobservable membership records `enqueued: indeterminate`. After either mechanism, the merge is confirmed only by the provider's observed pull-request state (`ci.pr-observe` or `ci.queue-membership`: `merged`, with the merge commit on the base branch), never by the merge command's return value or exit code. `finalize.merge-queue-wait` waits for a terminal outcome — `merged`, `ejected`, `closed`, or `timed_out` — because an entry can be ejected on rebase after its checks turned green; every outcome other than `merged` (the terminal queue outcomes, `cancelled`, and the job outcomes `failed`, `refused`, `killed`, `indeterminate`) enters the `auto` state `finalize.merge-queue-exit` (<<merge-path>>, item 7), which routes by the observed pull-request and queue state. An `enqueued: indeterminate` enqueue enters the wait as well and is settled by its observation. The wait is bounded by stall, not by a fixed budget: every observed progress of the entry (a change of queue position or entry state) restarts the clock, and `timed_out` is reached only after no progress for twice the queue's check-response timeout (the `check_response_timeout` of the derived fact `merge_queue_enforced`), else the compiled fallback `3600` s. `timed_out` is a no-verdict outcome, never evidence that the entry failed; a landing that ends `timed_out` records no merge verdict. *Deliberate change vs. `plan-marshall`*: `plan-marshall` bounds the wait with a fixed budget.

=== Epic Plan Emission (`emit:<plan_id>`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-41[PM-WATCH-PHASE-41]_

Orchestrator epics (`scope: epic`) manage multi-plan workstreams stored in `.marshall/orchestrator/<epic_id>/` (`epic.json` header and per-plan `.marshall/orchestrator/<epic_id>/queue/<plan_id>.json` files, keyed by the child plan's `plan_id`; the epic-local ordinal is display-only, link:../dispatch-and-effort.adoc[Model Jobs & Effort Specification]).

* *Never Run a Plan as a Job*: Because model jobs are single-level leaf workers (`PM-WF-5`) and every plan launches its own model jobs during Phases 2–6, an epic **never** starts a plan as a model job and **never** executes a plan inline.
* *Staging-Time Surface Disjointness*: Disjointness is a modelling invariant of one epic, not a runtime gate. When the epic stages a plan, the queue row declares its expected surface (`declared_surface`), and the server refuses the staging with `surface_overlap` when it overlaps the declared surface of another non-terminal row of the same epic that is not ordered with it through prerequisites, and with `surface_undeclared` when the surface cannot be declared (link:../dispatch-and-effort/04-epic-coordination.adoc#epic-surface-disjointness[Model Jobs & Effort Specification, Staging-Time Surface Disjointness]). There is no cross-epic check and no check against plans started without an epic; such conflicts surface as a rebase conflict (`sync-baseline`, `finalize.merge-sync`) or as a pull request the provider refuses to merge, and are the operator's responsibility.
* *`emit:<plan_id>` Transition (`rel: emit`)*: For each staged plan whose prerequisite rows are in the partition `terminal.shipped` (`merged` or `completed`), the epic state offers `emit:<plan_id>` (emission compares no surfaces; a row whose re-grounding verdict is `stale` is not offered until its spec section is re-submitted); the representation shows the row's re-grounding staleness (`regrounded_at_sha`, `main_commits_since`, link:../dispatch-and-effort.adoc[Model Jobs & Effort Specification]). Following `emit:<plan_id>`:
** Updates `.marshall/orchestrator/<epic_id>/queue/<plan_id>.json` atomically (`status = "launched"`) under the epic lock.
** Returns the host entry command of the emitting session's client, rendered from its client profile as `{{command:plan}} <plan_id> --from-epic <epic_id>` (for `claude`: `/mcp-plan-marshall <plan_id> --from-epic <epic_id>`; link:../client-profiles/02-placeholders-and-detection.adoc[Client Profiles Specification, Placeholders & Detection]), in `facts.emitted_command`; typed in the host, it opens the plan's bootstrap with the source `epic_row` (xref:01-planning-phases-1-2.adoc#_plan_source_contracts[Plan Source Contracts]). Emission is always operator-mediated: there is no `auto_emit` setting, and the server never spawns a background plan session.
** Moves the row from `launched` to `running` in the transaction that creates the plan from its bootstrap (source `epic_row`, lock order workspace, plan, epic): the plan's first session row is the entering session and `from_epic` becomes the plan's `origin.epic_id` (link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]).
