=== Finalize Step Ordering Bands

The Phase 6 (`finalize`) pipeline is a banded integer `order` space partitioned around the single `push` barrier (`order = 11`) and the `branch-cleanup` merge gate (`order = 70`).

==== Band Allocation Summary

[cols="2,1,2,4"]
|===
|Band Name |`order` Range |Owner |Semantic Role & Insertion Guarantee

|*Settle — Pre-Push*
|`1..10`
|Shared bundle + project-local (densely packed at `3..10`)
|Prepares, reviews, mutates source, refreshes architecture, and runs the final local quality gate before pushing. `pre-push-quality-gate` (`10`) is strictly the last step before `push` (`11`). Adding a new step inside `3..10` requires a deliberate re-spacing of the sub-cluster.

|*Push Barrier*
|`11`
|Shared bundle (fixed)
|Single branch push (`default:push`), implemented via `call git.commit_and_push (message_mode=none_assert_clean, push_mode=if_push_remote)`. Verifies the `worktree_sha` freshness gate, clean working tree, and remote branch parity before pushing.

|*Settle — Post-Push & Concurrent Wait Region*
|`12..69`
|Shared majors (`20`, `22`, `30`, `40`, `62`) + interior gaps (`12..19`, `21`, `23..29`, `31..39`, `41..61`, `63..69`)
|Opens the PR (`20`), enters the composite concurrent wait region (`22..40`: CI verification, automatic review bots, code analysis providers), whose failing classes call their remediation policies in the fixed order CI, analysis, review findings, and proposes ADRs (`62`). Any source fix of a policy (in-branch, or in the `loop_back` form through Phase 5) re-enters the Settle band as verdict currency decides.

|*Merge Gate*
|`70`
|Shared bundle (fixed)
|`default:branch-cleanup` — runs the merge path (xref:06-finalize-re-entry-and-merge.adoc#merge-path[Merge Path (`branch-cleanup`)]): acquires the cross-plan merge mutex, rebases onto base only when required, evaluates the pre-merge review barrier, merges via safe-merge or merge-queue bound to the expected head SHA, destroys the worktree (`destroys: [worktree]`), and clears `worktree_path` in the same transaction that records the removal.

|*Post-Merge Operational*
|`71..899`
|Project-local / third-party
|Post-merge operational actions that do not mutate tracked source and are not backward-looking reports. (Legacy `deploy-target` at `81` and `sync-plugin-cache` at `85` are obsolete for `PM-MCP`'s own distribution.)

|*Post-Run Review*
|`900..999`
|Shared bundle (`991..999`) + reserved gap (`900..989`)
|Backward-looking analysis and reporting steps (`post_run_review: true`, `mutates_source: false`) that depend on post-merge evidence: `lessons-capture` (`991`), `preference-emitter` (`992`), optional `plan-retrospective` (`995`), `record-metrics` (`998`), `print-phase-breakdown` (`999`).

|*Terminal Emission*
|`1000..1099`
|Shared bundle (reserved)
|`default:emit-landing` (`1000`, `post_run_review: true`) — emits the machine-readable landing envelope to the orchestrator epic inbox after all metrics and post-run reports complete.

|*Terminus*
|`1100`
|Shared bundle (fixed)
|`default:archive-plan` (`1100`) — archives/moves the plan directory (`destroys: [plan-directory]`) and enters the plan's terminal state (`completed`, `handed_back`, or `returned`). Strictly the highest `order` in the pipeline.
|===

==== Step States & Failure Routing

Every default step runs in a declared state of the `finalize` template unit (`finalize.<step-name>`; link:../state-catalogue/04-plan-finalize-terminal.adoc#state-catalogue-finalize[State Catalogue, Phase 6: `finalize`]), which the plan-instance composition includes or prunes; `finalize.next-step` selects the next unsettled step of the instance in force, so a post-run-only instance version (a fallback or an empty harvest) needs no special selection mode. Every link state asks for exactly one judgment through one link that names its skill section (guided step-in).

[cols="2,2,4"]
|===
|Step (order) |State (kind) |Outcomes

|`sync-baseline` (3)
|`finalize.sync-baseline` (`composite_job`)
|`up_to_date` (`noop`, `check`) -> `finalize.next-step` (`skipped`); `rebased` -> `finalize.next-step` (`done`); `conflict` -> `finalize.remediate-sync-conflict` (`remediation.merge-conflict`, `resolved` -> `finalize.settle-commit`); `fetch_failed`, `cancelled` -> `finalize.step-failed`.

|`simplify` (5)
|`finalize.simplify` (`job llm`, role `plan.phase-6-finalize.effort.simplify`, read-only), then `finalize.simplify-apply` (`link`)
|The job's `submit:simplify` records its proposals; none -> `finalize.next-step`; otherwise the main-session model applies the subset it accepts and follows `apply` -> `finalize.settle-commit` (an empty accepted set -> `finalize.next-step`); a job that ended without its submission raises `job_incomplete`.

|`security-audit` (7)
|`finalize.security-audit` (`job llm`, role `plan.phase-6-finalize.effort.security-audit`, read-only)
|The job files its findings through `submit:findings`; findings -> `remediation.review-findings` (security findings are not waivable), none -> `finalize.next-step`; a job that ended without its submission raises `job_incomplete`.

|`pre-submission-self-review` (8)
|`finalize.self-review` (`link`, `submit` verdict)
|Clean full round -> `finalize.next-step`; clean delta round -> itself (one full round owed); `not_covered`, `not_run` -> `finalize.next-step` (non-blocking); findings -> `remediation.review-findings` (its `fix` in the `loop_back` form). Also run in `terminus` mode (catalogue row `8`, Review chain terminus).

|`architecture-refresh` (9)
|`finalize.architecture-refresh` (`composite_job`)
|`unchanged` -> `finalize.next-step` (`done`, `work_performed=false`); `changed` -> `finalize.architecture-judgment` (`link`, `submit`) -> `finalize.settle-commit`; `failed` (every constituent failure fate), `cancelled` -> `finalize.step-failed`.

|`pre-push-quality-gate` (10)
|`finalize.pre-push-quality-gate` (`composite_job`, `build.quality-gate`)
|`passed`, `baseline_red` (baseline-only red) -> `finalize.settle-commit`; `red` (plan-caused), `no_verdict`, `cancelled` -> `finalize.remediate-build` (`remediation.build-failure`).

|`adr-propose` (62)
|`finalize.adr-propose` (`auto` signal gate), `finalize.adr-author` (`link`)
|No signal -> `finalize.next-step` (`skipped`); `submit` ADR -> `finalize.settle-commit`; `decline` -> `finalize.next-step` (`done`, `work_performed=false`).

|Project steps (`71..899`, `900..989`)
|`project.run-step` states
|Job outcomes; failures -> `finalize.step-failed`.

|`lessons-capture` (991)
|`finalize.lessons-capture` (`auto` signal gate, then `job llm`, role `plan.phase-6-finalize.effort.post-run-review`, read-only)
|No signal -> `skipped`; the job's `submit:lesson` recorded -> `done`.

|`preference-emitter` (992), `plan-retrospective` (995), `record-metrics` (998), `print-phase-breakdown` (999)
|one `auto` state each
|`recorded` -> `finalize.next-step` (`done`); degraded inputs are recorded as `indeterminate`, floor, or `unmeasured`, never refused.

|`emit-landing` (1000)
|`finalize.emit-landing` (`auto`)
|`delivered`, `not_orchestrated`, `pending` (indeterminate epic linkage: the envelope kept with `landing_delivery: pending`) -> `finalize.next-step` (`done`); `append_failed` -> `finalize.emit-landing-failed` (bounded `retry`, then `pending`).
|===

* *Settle Commits*: Every `-> finalize.settle-commit` continues on `done` as listed and routes `stepped_out` to `finalize.hand-back` (before order `70`).
* *Shared Failure State*: `finalize.step-failed` (`auto`) re-fires the failed step once; a second failure before order `70` enters `finalize.hand-back`, after order `70` it writes an owed item and continues at `finalize.next-step` (the plan stays `merged`; no step is skipped by the operator). Store I/O failures of post-run `auto` steps are transaction failures, not workflow outcomes.

The catalogue mirrors the finalize step roster of `plan-marshall` (step identifiers, `order`, descriptor facts, `lane` data, and defaults), verified against `plan-marshall` commit `1d4a1da37` (`extension-api/standards/ext-point-finalize-step.md` and each step's frontmatter). Differences are marked as *deliberate changes*. Before implementing the finalize pipeline, re-verify the roster against the latest `plan-marshall` version. Rows marked "project" are project-local steps of `plan-marshall`'s own repository, listed only to show how project steps occupy the bands; they are not shipped.

The catalogue is the roster of the binary's *default* `finalize.pmwf` unit. A project runs its own copy (`.marshall/config/finalize.pmwf`, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]): it may omit an optional step (lane class `prunable` or `adversarial`, or a step whose default is off) and add project steps (descriptor in `workflow.json` `plan.phase-6-finalize.project_steps`, script bound in the enrolment), but every step of lane class `core` or `derived-state` (the mandatory steps, xref:02-planning-lanes-phases-3-4.adoc#plan-instance-composition[Plan Instance Composition]) must be present at its catalogue `order`, and the verified unit decides the roster; `workflow.json` only sets the lane and parameters of an optional step.

Every `head_dependent` step declares its `input_scope` (xref:06-finalize-re-entry-and-merge.adoc#verdict-input-scope[Verdict Input Scope]): `remote_state` for `ci-verify`, `automatic-review`, and `analysis-roundtrip`; `open_ended` for `pre-push-quality-gate`; `plan_footprint` for `simplify`, `security-audit`, and `pre-submission-self-review`. Project-local steps declare their own (`plan-marshall`'s `plugin-doctor` has no sound subset, `open_ended`; its `era-stamp-fill` names its files, `declared`). *Deliberate change vs. `plan-marshall`*: `plan-marshall` has no `input_scope` field; its steps either declare `verdict_inputs` or leave it absent.

|Post-Push (`12..69`)

|—
|`core`, on; `requires: [ci-complete]`
|Monitors CI workflow runs against pushed `HEAD` (`input_scope: remote_state`), looked up by head SHA and re-polled at the provider re-poll cadence (link:../timeouts/01-job-budgets-and-waits.adoc#ci-repoll-cadence[Timeouts & Budgets Specification]); check runs owned by registered review bots are excluded. Applies a deterministic two-level CI failure taxonomy to every failed check: `failure_class` from the provider's conclusion (`failure`, `cancelled`, `timed_out`, `action_required`, `stale`, `startup_failure`, `not_triggered`, `no_checks`) and `failure_kind` from the check's log, parsed by the build output parsers of `PM-IMPL-6` (`compile`, `test`, `lint`, `policy`, or `unknown` when no parser recognises the log or the log is unreadable). `unknown` stays its own value and is handled fail-closed: its finding is blocking like any other. A provider `timed_out` is a failed check, not a no-verdict outcome of `PM-MCP` (that rule covers only `PM-MCP`'s own operations). There is no `infra_flake` class: flakiness is not deterministically decidable. Each failed check is filed as one finding with source `ci`, its `failure_class` and `failure_kind`; a check outside the derived `required_checks` is filed with `blocking: false`. `ci_status` (link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification]) is `not_triggered` for the classes `not_triggered` and `no_checks`, `cancelled` when every failed required check has class `cancelled`, and `failed` for any other failed required check. Hard CI failure immediately short-circuits `finalize.concurrent-wait` (`PM-WF-9`) and calls `remediation.ci-failure`, whose evidence job also fetches the base's CI result of the same checks, so a baseline-only red passes by the server rule and never reaches `decide`; a failing check is waivable as `ci_check:<name>`. A failed check whose re-observation at a later `HEAD` passes is resolved by the server (`resolution: fixed`), a waived one `accepted` by waiver. Pruned for local-only runs. *Deliberate change vs. `plan-marshall`*: `plan-marshall` classifies by workflow name (`ci_build_failure` vs `ci_policy_failure`); `PM-MCP` classifies by provider conclusion and parsed log content.
