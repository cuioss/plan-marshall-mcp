== Q-Gate Validation, Change-Type & Unplanned-Change Contracts
_See Requirement link:../../Requirements.adoc#PM-WF-11[PM-WF-11: Q-Gate Validation Loop, Change-Type & Unplanned-Change Recording]_

=== Q-Gate Validation Loop
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-52[PM-WATCH-GEN-52], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-6[PM-WATCH-PHASE-6], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-10[PM-WATCH-PHASE-10], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-12[PM-WATCH-PHASE-12]_

Quality Gate (`Q-Gate`) validation runs at the tail of Phase 3 (deep lane only; the light lane never runs it), at the tail of Phase 4, and in Phase 2 only for lesson-derived plans on the deep lane (narrative-vs-code validation; a light lesson-derived plan never enters Phase 2, and its premise contradictions surface through the light envelope's premise check as a judgment escalation to `deep`); the Phase 3 and Phase 4 populations follow `plan-marshall` (verified at commit `1d4a1da37`; re-verify before implementing). *Deliberate change vs. `plan-marshall`*: its Phase 2 Q-Gate runs on every plan and adds module-mapping completeness, track-scope consistency, scope realism, and confidence justification; here module-mapping existence is a server check of every refine submission and scope-lane consistency a ratchet trigger (xref:01-planning-phases-1-2.adoc#_five_quality_dimensions_fixed_weight_confidence_aggregation[Five Quality Dimensions], Server Checks on Every Submission), while scope realism and confidence justification are dropped as covered by the `ConfidenceAggregator`. It catches structural defects (narrative-vs-code drift, missing consumer sweeps, invalid command flags, tier and architecture mismatches, and unresolved lesson citations) before advancing to the next phase.

*Worker and Server Verdict*: `refine.qgate`, `outline.qgate`, and `plan.qgate` are job states of kind `llm` running a read-only validation job (role `plan.<phase>.effort.qgate`, link:../dispatch-and-effort.adoc[Model Jobs & Effort Specification]; link:../hypermedia-format/01-representation-and-link-forms.adoc#model-job-states[Hypermedia Format Specification, Model Job States]) that submits component assessments and findings from its entity scope. The job's completion runs the return-evaluation primitive, which executes the compiled mechanical checks of the table below and decides the verdict from the persisted findings alone: `clean` (no blocking finding pending) exits to the next state (`refine.ready`, `outline.gate`, or `execute.worktree-init`), `blocking` calls `remediation.qgate-findings`. The model files findings; the server decides. A pass over zero recorded component assessments is `not_evaluated` and is never `clean`.

==== Remediation Budget, `fix_unchanged` & Surgical Bypass
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-13[PM-WATCH-PHASE-13]_

[cols="1,3"]
|===
|Parameter / Rule |Normative Specification

|*No Mode*
|The Q-Gate has no configurable mode in any phase: validation and remediation continue until the verdict is `clean` or the remediation budget is spent. *Deliberate change vs. `plan-marshall`*: its `q_gate_validation` knob (`off` skips validation, `once` leaves known findings open) does not exist, because both only weaken the gate; the presence of the Q-Gate states in the deep-lane `outline` and in the `plan` unit is a compiled invariant (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]).

|*Remediation Policy* (`remediation.qgate-findings`, retry `0`, fix `3`, waiver wait `0`)
|A `blocking` verdict calls the unit, whose evidence is the phase's blocking findings. Its `fix` returns `fix_requested`, which the caller routes to the authoring state with the findings in `facts.qgate_findings`: `refine.analyze` (Phase 2), `outline.route-rework` (Phase 3, which routes by lane), or the link state `plan.revise-tasks` (Phase 4, targeted task revision). The next accepted submission re-enters `<phase>.qgate`, whose `blocking` verdict calls the unit again on the same per-plan counter. The counter replaces the former `qgate_iteration`; the hard cap is `5`, and the operator raises the ceiling only with `--raise fix_budget:qgate-findings=N`.

|*`fix_unchanged` instead of a Content-Hash Gate*
|A remediation submission whose target artifact (`request.md` in Phase 2, `outline.md` in Phase 3, the `TASK-*.json` bundle in Phase 4) is byte-identical to the one the last verdict evaluated is refused with `fix_unchanged` and charges nothing: unchanged content cannot produce a different verdict.

|*Surgical Bypass Predicate*
|In Phase 3 (`outline`), Q-Gate validation is automatically bypassed (logging `(phase-3-outline:qgate-bypass)` to the audit log) if and only if all three conditions hold: `scope_estimate == "surgical"`, `change_type` $\in \{\text{"bug\_fix"}, \text{"tech\_debt"}, \text{"verification"}\}$, and `deliverable_count == 1`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` applies the same surgical-scope bypass to its Phase 4 Q-Gate (its "B2"); in `PM-MCP` the bypass is limited to Phase 3 and `plan.qgate` runs on every path into Phase 5 (`INV-PLAN-1`, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]).

|*Exit Semantics*
|`resolved` continues to the phase exit; `waived` (operator waiver `qgate_findings:<phase>`) continues to the phase exit with the open blocking findings dispositioned accepted-by-waiver; `exhausted` and `stepped_out` enter `plan.return` (`returned`, xref:01-planning-phases-1-2.adoc#plan-outcomes[Plan Outcomes & Fallback Routes]). *Deliberate change vs. the earlier design*: the `<phase>.qgate-exhausted` state, its `edit` answer, and the operator's `force-gate` do not exist.

|*Convergence Record*
|Each remediation round records `findings_raised`, `findings_self_seeded` (findings located in lines changed by the previous round's fix) and, on exhaustion, `findings_at_ceiling` (raised in the last round, whose fixes no round reviews). The exit renders `converged` vs `oscillating` from these figures, never from the last count alone.
|===

=== Single-Writer `change_type` Contract
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-21[PM-WATCH-GEN-21]_

`change_type` classifies the intent of a plan and its deliverables using a closed 6-value enumeration orthogonal to `domain` and `profile`:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.classification;

public enum ChangeType {
    ANALYSIS("analysis", 1),
    FEATURE("feature", 2),
    ENHANCEMENT("enhancement", 3),
    BUG_FIX("bug_fix", 4),
    TECH_DEBT("tech_debt", 5),
    VERIFICATION("verification", 6);

    private final String wireName;
    private final int priorityOrder;

    ChangeType(String wireName, int priorityOrder) {
        this.wireName = wireName;
        this.priorityOrder = priorityOrder;
    }

    public String wireName() { return wireName; }
    public int priorityOrder() { return priorityOrder; }
}
----

The priority order is `plan-marshall`'s documented order (`ref-workflow-architecture/standards/change-types.md`, Priority Ordering Rationale). *Deliberate change vs. `plan-marshall`*: its planning-lane routing also knows the value `feature_breaking`, which does not exist here; whether a change breaks compatibility is the separate `compatibility` field (`breaking`, `deprecation`, `smart_and_ask`; Phase 2), never a change type.

==== Single-Writer Heuristic vs Judgment Fallback

To prevent conflicting writes between deterministic heuristics and model judgment, `status.metadata.change_type` enforces a strict *single-writer* protocol at the start of Phase 3 (`outline.detect-change-type`):

1. *Deterministic Heuristic First (`ChangeTypeHeuristic`)*: Scores `clarified_request` (falling back to `original_input`) against fixed keyword tables, applying compound-intent guards and `bug_fix`-vs-`tech_debt` object disambiguation. If a single `ChangeType` wins with $\text{confidence} \ge 0.70$ and no top-two score tie, `ChangeTypeHeuristic` persists `status.metadata.change_type` and advances directly to the plan's lane state, `outline.deep` or `outline.light` (`ambiguous = false`). If no keyword fires, the top two scores tie, or $\text{confidence} < 0.70$, `ChangeTypeHeuristic` returns `ambiguous = true` and **writes nothing** to `status.json`.
2. *Judgment Fallback (`submit`)*: Only when `ambiguous == true` does the engine enter `outline.classify-change-type`, offering a `submit` link (`change_type:enum[feature|bug_fix|tech_debt|enhancement|verification|analysis],rationale:text[1..500]`) guided by `skill://pm/outline/detect-change-type/SKILL.md`. The submitted value becomes the single authoritative write to `status.metadata.change_type`.

==== Plan-vs-Deliverable Scope Reconciliation & Classification Validation
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-9[PM-WATCH-PHASE-9]_

* *Scope Disagreement Refusal*: Every deliverable in `outline.md` declares its own deliverable-scoped `change_type`, while `status.metadata.change_type` holds the plan-scoped classification. `OutlineValidator` and the plan instance composition reconcile the two scopes and **refuse** incompatible combinations: a deliverable with `change_type: verification` or `analysis` is read-only by definition; if any of its `Affected files` carries a mutating intent (`write-new`, `write-replace`, `delete`), or if a plan classified as `verification`/`analysis` contains mutating deliverables, validation fails closed with `change_type_scope_disagreement`.
* *Flag-Not-Block Classification Validation*: When `scope_estimate` is updated in Phase 2 or Phase 3, `classification-validate` checks for narrow-over-large mismatches (for example, `change_type == bug_fix` paired with `scope_estimate == broad`). Mismatches emit an advisory warning fact in `facts.classification_warning` but never block a transition.

=== Unplanned Changes (Recorded, Not Reviewed)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-14[PM-WATCH-PHASE-14]_

The declared footprint (`declared_files`, fixed when `outline.gate` passes) is the plan's statement of intent, not a fence inside the worktree. An envelope job that needs to change a file beyond its deliverable's `Affected files` changes it in the plan worktree without asking: there is no deviation request, no task blocking, and no review state.

* *Recording*: The server records every path of `realized − declared` (the realized footprint minus the declared write intents; a modified `(read)` entry included) as an *unplanned change* with its provenance (`task_id` and deliverable, or the loop-back round that produced it) from the Task Diff Records and the change ledger. The unplanned changes are listed in the pull-request body (`## Unplanned Changes`), in the landing record, and in the retrospective's footprint reconciliation; they never extend `declared_files`.
* *Boundaries Stay Hard*: Only a boundary breach is refused, by the non-waivable guards: a write outside the plan worktree, a change of the main checkout (Clean Main Checkout Guard), or a change of a protected path (`.marshall/**`, a pinned wrapper file). A breach raises `footprint_violation` (xref:02-planning-lanes-phases-3-4.adoc#_planning_transition_guards_real_world_invariants[Planning Transition Guards & Real-World Invariants]), whose bounded self-remedy ends in the fallback.
* *Epic Plans*: When an unplanned path overlaps the declared surface of a sibling plan of the same epic, the overlap is noted in the landing record for the epic's landing reconciliation; it never blocks.
* *Title Staleness*: A task that ends `infeasible`, a removed deliverable, and a domain narrowing set `status.metadata.pr_title_stale` (the shipped scope shrank).
* *Deliberate change vs. `plan-marshall`* and the earlier design: the batched deviation question (`hold` / `accept` / `split`), the `ScopeDeviationRequest` record, the deviation review state, the `approved_widening` approval path, and the loop-back footprint review do not exist; the recorded provenance replaces them.

=== Worktree Materialization & Envelope Execution Loop

At Phase 5 entry (`execute.worktree-init`), the daemon creates the plan's feature branch and isolated git worktree at `.marshall/local/worktrees/<plan_id>/` and records its canonical path as `worktree_path` in `mcp/status.json` in the same transaction; after a loop-back to Phase 3 it adopts the kept worktree instead. The plan directory stays in the machine store and is never moved (link:../filesystem-layout.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]).

==== Task Envelope Execution & Independent Server Verification
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-47[PM-WATCH-GEN-47], link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-1[PM-WATCH-DISP-1], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-6[PM-WATCH-PHASE-6], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-11[PM-WATCH-STORE-11]_

1. *Serial Envelope Jobs*: `execute.envelope-ready` is a job state of kind `llm` (`job llm envelope role plan.phase-5-execute.effort.default`, a writer job, link:../hypermedia-format/01-representation-and-link-forms.adoc#model-job-states[Hypermedia Format Specification, Model Job States]): entering it allocates the next envelope `envelope-M` in dependency order and launches its job in the plan worktree; at most one job with write tools runs per plan (link:../dispatch-and-effort/05-model-job-launch.adoc#model-slots[Model Jobs & Effort Specification, Model Slots & One Writer per Plan]), so the worktree has one writer, and the main session follows `wait:<job_id>`. The job calls `pm_state` on its entity `envelope-M` and receives only the current active task (`TASK-NNN`); the skills of its tasks are in its prompt (link:../dispatch-and-effort/05-model-job-launch.adoc#job-prompt[Model Jobs & Effort Specification, Prompt File & Contract Envelope]). The entity's submits move only the entity; the plan state reacts only to the job's end, observed by the server, whose return-evaluation primitive `execute.evaluate-envelope-return` decides one closed outcome from the persisted task and question records, in this precedence when several apply: `question_pending` -> `execute.task-question`; `infeasible_pending` -> `execute.infeasible-review` (only when no runnable task remains, item 5); `chain_tail` -> `execute.chain-tail-commit` (`execute.remediation-commit` when the finished tasks are remediation tasks); `continue` -> `execute.envelope-ready`; `all_complete` -> `execute.verify-sweep`. A job that ended without the submits its entity requires raises `job_incomplete`, whose `resume` launches a new job for the remaining tasks within the condition budget. The `submit` of a chain-tail task ends the entity and yields the envelope's remaining tasks to `envelope-(M+1)`.
2. *Independent Verification on `submit:TASK-NNN`*: The server never trusts a job's self-reported completion. When `submit:TASK-NNN` is invoked, the daemon independently verifies: (a) *Non-Empty Diff & Boundary Check* — for write-intent tasks, verifies that `git status --porcelain` in the worktree contains changes and that no path outside the worktree, of the main checkout, or of a protected path was touched (a boundary breach raises `footprint_violation`), forbidding batched destructive `git checkout` commands; paths beyond the deliverable's declared write intents, a modified `(read)` entry included, are recorded as unplanned changes (<<unplanned-changes>>); (b) *Obfuscation & Marker Check* — scans modified lines for prohibited suppression comments, `TODO`/`FIXME` markers, or rewrite markers; and (c) *Independent Command Re-Run* — executes the task's declared verification command via the daemon's build runner and verifies a passing verdict artifact. When the verification passes, the server appends (d) a *Task Diff Record* to `change-ledger.jsonl`: `kind: "task_diff"` with `task_id`, `deliverable_id`, the `worktree_sha` of the worktree at submit, `changed_paths` (the paths changed since the previous task's recorded snapshot, present and possibly empty), and `commit_sha: null`, because tasks never commit. This is the only producer of per-task change attribution.
3. *Context Yield, Task Questions & Infeasibility*: If an envelope job approaches its context window limit before finishing all tasks in `envelope-M`, it follows `yield:envelope-M` (no free parameters). Every early end of an envelope completes the entity (`envelope.completed`), and the server hands the remaining unstarted tasks to `envelope-(M+1)`, a new job; the server records `yield_reason` from the exit taken, a closed enum `chain_tail | question | context` persisted beside the job's classification in the metrics store. An envelope job that needs an answer calls `ask:TASK-NNN` (`question:schema[question-envelope]`), which records a question record of class `task` and ends the entity (`yield_reason: question`), so no job waits for a human; the remaining tasks, the asking task included, go to `envelope-(M+1)`, whose job receives the answer in `facts`. `execute.task-question` waits for the answer per the plan's question mode; at expiry the record moves to "parent answer expected" and the state offers `answer_questions` to the main-session model (`channel: model`, validated against the record's options like every answer; `question_expired` applies only to answers on user channels). The answer is recorded as an `amendments[]` entry and listed in the pull-request body and the landing record. If a task is genuinely impossible as specified, the job submits `infeasible:TASK-NNN` with evidence; the server sets the task to `infeasible` with the evidence as its disposition, `infeasible` is terminal for that task, and substituting a weaker deliverable under the same name is strictly prohibited. Envelope jobs continue for every task that does not depend, transitively through `depends_on`, on the infeasible deliverable (`PM-WATCH-GEN-47`).
4. *Dependency-Ordered Launch*: A task is yielded to its envelope's job only when every task in its `depends_on` is `completed`; an envelope's job is launched only when its first task is yieldable. A task whose dependency is `infeasible` or `removed` is never yielded.
5. *Infeasible Review (Model Judgment)*: When no runnable task remains and a deliverable is infeasible, the plan enters the link state `execute.infeasible-review`; `facts` carry the infeasible deliverables with their evidence and the server-computed transitive dependents. The model chooses one of:
** `remove_deliverable:<deliverable_id>` (`reason`): the `auto` state `execute.apply-removal` keeps the `infeasible` task with its evidence, sets every other task of the deliverable and of its server-computed dependents `removed` (`disposition.by: model`), records an `amendments[]` entry (`source: model`) naming the removed deliverables and the evidence, sets `status.metadata.pr_title_stale`, composes a plan instance version (event `deliverable_removed`), and routes `runnable_remaining` -> `execute.envelope-ready`, `all_settled` -> `execute.verify-sweep`. Removing the last remaining deliverable is refused; removed deliverables are listed as gaps in the pull-request body and the landing record.
** `loop_back_outline` (`reason`): *Loop-Back to the Outline*, also offered by `plan.revise-tasks`. The target is chosen by lane (`deep` -> `outline.deep`, `light` -> `outline.light-regate`, never `outline.light` directly), with the evidence as an amendment. The loop-back budget is a compiled `1` per plan, raised only as `fix_budget:qgate-findings`; a spent budget takes the fallback (`handed_back` when Phase 5 committed work, else `returned`). A loop-back from Phase 5 keeps the worktree: the outline job runs in it (a model job's working directory is the plan worktree when it exists), and `execute.worktree-init` adopts it; a fallback taken in Phases 3–4 after such a loop-back reaches `plan.return`, which forwards the committed work to `finalize.hand-back`. The re-authored outline and the re-derived tasks compose new instance versions at the `outline` and `plan` events; a deliverable the revised outline drops has its tasks set `removed` (`disposition.by: outline_gate`), Phase 4 derives the tasks of the revised deliverables additively, and `completed` tasks are never reopened (`PM-WF-7`). The loop-back counter is never reset.
** `hand_back`: the `handed_back` fallback.
+
The model may `ask` the user first which of the choices to take: the question record (class `ask`) is waited for in the question state `execute.infeasible-review.asked`, which returns to `execute.infeasible-review` with the answer in `facts` when it is answered or assumed; at expiry the choice stays with the model.

=== Per-Deliverable Chain-Tail Commit & Module Build (`git.commit_and_push`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-17[PM-WATCH-PHASE-17]_

Individual tasks never run `git commit`. When the last task belonging to deliverable $D_i$ (the *chain tail*) passes independent verification:

1. *Chain-Tail Commit via `call git.commit_and_push`*: `execute.chain-tail-commit` invokes the reusable compound sub-workflow `call git.commit_and_push (message_mode=auto_deliverable, push_mode=never)` (`PM-WF-16`, see link:../workflow-dsl.adoc[Workflow DSL Specification]). The sub-workflow cleans untracked build/temp artifacts against `artifact-patterns.json` (respecting `.gitignore` and excluding `.marshall/**`), formats the conventional commit message (`feat(<module>): complete deliverable <N> - <title>`) with the configured `Co-Authored-By` trailer, streams the message over `stdin` to `git -C <worktree> commit -F -`, and appends a `kind = "change"` entry to `change-ledger.jsonl` stamped with the new `commit_sha` and git-sourced `changed_paths`. It returns `done` with the result `{commit?, pushed, clean, landed}` (a read-only deliverable returns `clean` without a commit), or `stepped_out`, which the caller routes to `finalize.hand-back`.
2. *Per-Deliverable Module Build*: `done` enters the `job` state `execute.deliverable-build`, which runs the per-deliverable verification verbs of the effective configuration (`workflow.json` `plan.phase-5-execute.per_deliverable_verbs`, default `compile` and `module-tests`, as `plan-marshall`'s `per_deliverable_build`; link:../store-schemas/07-project-configuration.adoc#config-workflow-json[Store Schemas Specification, `workflow.json`]) scoped to $D_i$'s module and records a `kind = "build"` entry in `change-ledger.jsonl`. `succeeded` continues at `execute.envelope-ready`. Every other fate (`failed`, `timed_out`, `killed`, `indeterminate`, `refused`, `failed_unparsed`) calls `remediation.build-failure` with the recorded fact `failed_build: deliverable`, because an absent verdict is never admitted as a pass: its `retry` re-runs the build, its `fix` returns `fix_requested`, which allocates remediation tasks whose commit (`execute.remediation-commit`, routing `done` and `stepped_out`) continues by the `failed_build` fact (`deliverable` -> `execute.deliverable-build`, `sweep` -> `execute.verify-sweep`). `resolved` (the unit's own re-run passed) continues by the same fact: `deliverable` -> `execute.envelope-ready` (the deliverable's build is green, so the next envelope follows), `sweep` -> `execute.verify-sweep`. A build failure is not waivable, so the unit has no `waived` outcome; `exhausted` and `stepped_out` enter `finalize.hand-back`.

=== Whole-Tree Verification Gates & `triage_required` Routing
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-15[PM-WATCH-PHASE-15], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-66[PM-WATCH-PHASE-66]_

Once all task envelopes reach completion, `execute.verify-sweep` (a `composite_job`) runs the end-of-phase verification steps of the plan instance (ordered by the `ext-point-build-verify-step` descriptors: `module-tests`, `quality-gate`, `coverage`, and domain `arch-gate`):

* *Footprint-Driven Scope & Relocation Override*: The server compares the realized git footprint (`references.json:realized_footprint`) against project modules to scope build executions. However, if any deliverable in the plan performed a **file relocation or deletion** (any `Affected files` entry with `delete` intent or a git rename `R`), the server unconditionally forces a **whole-tree build and verification sweep** across all modules to catch broken cross-module imports or references. A realized path claimed by no module but routed by the build map as build-neutral (for example `.github/**`) is classified `no_module`: it neither blocks nor widens a module-scoped gate to whole-tree, and the scope decision lists it.
* *`triage_required` -> Build Remediation*: Whenever an end-of-phase verification step fails, or a constituent ends without a verdict, the engine ingests the parsed build/test/arch-gate failures into `findings.jsonl` (the evidence of the unit) and calls `remediation.build-failure` with `failed_build: sweep` (routing as in the per-deliverable build above); its `fix` allocates remediation tasks that commit via `call git.commit_and_push (message_mode=interactive, push_mode=never)` and re-enter `execute.verify-sweep`.
* *Baseline-Red Server Rule*: Before a failing gate reaches the remediation policy, the server proves whether it is red only through failures already present on the base (link:../job-runtime/03-parsers-and-gates.adoc#_gate_honesty_verification[Job Runtime Specification, Gate Honesty Verification], Baseline Separation). The proof compares the failure fingerprints primarily with the provider's CI result of the same check on the base (the merge base, or the latest base-branch commit containing it); a local build of the merge base is the fallback for local gates such as the pre-push quality gate, or when the provider has no result for the base. When every failure is baseline-only, the server writes a `baseline_red` build row into `change-ledger.jsonl` bound to the `worktree_sha`, the merge base, and the digest of the accepted diagnostics, and the gate passes: the freshness gate counts that row as passing for the same `worktree_sha` only, a finalize gate step completes `done` with `assurance_verdict: degraded`, and the pull-request body and the landing record list the baseline failures. Coverage debt in untouched modules is a non-blocking `baseline_debt` finding. A red that is not provably baseline-only is plan-caused and calls the build (or, in finalize, the CI) remediation policy. There is no baseline-red state and no operator acceptance; the plan is never looped back to remediate a baseline failure.

=== Phase 5 Exit Barrier: Dual Freshness & Pending-Tasks Gates
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-25[PM-WATCH-GEN-25], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-17[PM-WATCH-PHASE-17]_

Transitioning from `phase-5-execute` to `phase-6-finalize` is governed by an atomic dual-gate barrier in `execute.exit-barrier`. **Both gates are always evaluated together before acting on either** so a single diagnostics payload surfaces all reasons if both fail:

1. *Pending-Tasks & Clean-Tree Gate*: Every `tasks/TASK-*.json` record in the plan must be in a terminal status (`completed`, `infeasible`, or `removed`), every `infeasible` or `removed` task must carry its recorded `disposition` (link:../store-schemas/06-task-references-manifest.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]), and no task may be open (`pending_count == 0`, `in_progress_count == 0`); the gate reports the counts of every status and lists each non-`completed` task with its disposition. The worktree must have zero uncommitted modifications (`git status --porcelain` is empty). A dirty tree is handled first: it enters `execute.remediation-commit`, whose artifact review separates build leftovers from real changes; real changes are committed and recorded as unplanned changes, and the route continues to `execute.verify-sweep` because `HEAD` changed; only a boundary breach raises `footprint_violation`. A barrier failing on open tasks routes to `execute.envelope-ready` while runnable tasks remain, and otherwise to `execute.infeasible-review` (link:../state-catalogue/03-plan-phases-4-5-land.adoc#state-catalogue-execute[State Catalogue]).
2. *Worktree Freshness Gate (`worktree_sha`)*: Freshness is keyed strictly on `worktree_sha` — the SHA-256 digest over the `HEAD` commit id plus, for every path the status reports as changed, deleted, or untracked (sorted by path), the path and either the file's bytes read from disk or a deletion marker, computed by the single git contract operation `git.worktree-sha` for both variants (link:../job-runtime/03-parsers-and-gates.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash]) — never on `HEAD` commit SHA alone (which would misclassify an unbuilt dirty tree as fresh). The gate queries the change ledger (`change-ledger.jsonl`) and reads the explicit closed-enum `status` member (`fresh`, `exempt`, `stale`, `undecidable`), never inferring freshness from a process exit code or from `"not stale"`: `fresh` requires that every required build notation for the realized footprint has a passing `kind = "build"` ledger entry whose recorded `worktree_sha` equals the current live `worktree_sha` and every ledger row matches a registered build notation of the project; `exempt` applies when the `build-decision` verdict over the build map and the realized footprint is `not_necessary` (every realized path is build-neutral); the `documentation_only` file-type bucket is a file role for `profiles[]` assignment and is never read as a build verdict (as in `plan-marshall` ADR-004); `stale` / `undecidable` fails the barrier with an explicit `stale_reason` (`tree_modified_since_build`, `last_build_failed`, `no_successful_build`, `missing_module_build`, `unrecognized_build_notation`, `reconciliation_record_absent`, `ledger_unreadable`, or `worktree_sha_unavailable`), routing back to `execute.verify-sweep`. A live or recorded `worktree_sha` that is `unavailable` (a failed git invocation) makes the gate `undecidable` with `worktree_sha_unavailable`, never `fresh`, and ledger rows of another `worktree_sha_version` never match the live digest (link:../job-runtime/03-parsers-and-gates.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash], rules 4 and 5).
+
`last_build_failed` (the latest build row for a required notation is not `succeeded`) is a different operator action than `tree_modified_since_build` (source edited after a passing build) and is never reported as it; when no successful build exists at all the reason is `no_successful_build` and no `freshness_reconcile` is recorded (it requires a `prior_build_worktree_sha`). `reconciliation_record_absent` lists in `facts.admitted_causes` the causes that absence admits (`source_drift_unbuilt`, `no_successful_build`, `record_owed_not_emitted`, `commit_outside_reconcile_membership`), so the refusal reports what it observed rather than guessing one cause. Where the step records show that `HEAD` is a finalize-internal commit, the refusal names the committing step.
