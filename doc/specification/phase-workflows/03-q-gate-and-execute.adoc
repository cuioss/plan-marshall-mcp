== Q-Gate Validation, Change-Type & Unplanned-Change Contracts
_See Requirement link:../../Requirements.adoc#PM-WF-11[PM-WF-11: Q-Gate Validation Loop, Change-Type & Unplanned-Change Recording]_

=== Q-Gate Validation Loop
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-52[PM-WATCH-GEN-52], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-6[PM-WATCH-PHASE-6], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-10[PM-WATCH-PHASE-10], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-12[PM-WATCH-PHASE-12], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-5[PM-WATCH-PHASE-5]_

Quality Gate (`Q-Gate`) validation runs at the tail of Phase 3 (deep lane only; the light lane never runs it), at the tail of Phase 4, and in Phase 2 only for lesson-derived plans on the deep lane (narrative-vs-code validation; a light lesson-derived plan never enters Phase 2, and its premise contradictions surface through the light envelope's premise check as a judgment escalation to `deep`); the Phase 3 and Phase 4 populations follow `plan-marshall` (verified at commit `1d4a1da37`; re-verify before implementing). *Deliberate change vs. `plan-marshall`*: its Phase 2 Q-Gate runs on every plan and adds module-mapping completeness, track-scope consistency, scope realism, and confidence justification; here module-mapping existence is a server check of every refine submission and scope-lane consistency a ratchet trigger (xref:01-planning-phases-1-2.adoc#_five_quality_dimensions_fixed_weight_confidence_aggregation[Five Quality Dimensions], Server Checks on Every Submission), while scope realism and confidence justification are dropped as covered by the `ConfidenceAggregator`. It catches structural defects (narrative-vs-code drift, missing consumer sweeps, invalid command flags, tier and architecture mismatches, and unresolved lesson citations) before advancing to the next phase.

*Task and Server Verdict*: `refine.qgate`, `outline.qgate`, and `plan.qgate` are `job llm` states of role `qgate` (xref:01-planning-phases-1-2.adoc#phase-roles[Model Work per State]) whose task submits component assessments and findings from its entity. The task's completion runs the return-evaluation primitive, which executes the compiled mechanical checks of the table below and decides the verdict from the persisted findings alone: `clean` (no blocking finding pending) exits to the next state (`refine.ready`, `outline.gate`, or `execute.worktree-init`), `blocking` calls `remediation.qgate-findings`. The task files findings; the server decides. The task's submit carries `confidence:int[0..100]`, and the verdict appends a `qgate.verdict` decision record with the task as decider and the blocking findings against `0` (link:../model-work/11-decision-records.adoc#decision-points[Model Work Specification, Decision Points]). A pass over zero recorded component assessments is `not_evaluated` and is never `clean`; while `qgate` is unqualified no verdict exists, and the phase takes its fallback (`returned`).

==== Remediation Budget, `fix_unchanged` & Surgical Bypass

[cols="1,3"]
|===
|Parameter / Rule |Normative Specification

|*No Mode*
|The Q-Gate has no configurable mode in any phase: validation and remediation continue until the verdict is `clean` or the remediation budget is spent. *Deliberate change vs. `plan-marshall`*: its `q_gate_validation` knob (`off` skips validation, `once` leaves known findings open) does not exist, because both only weaken the gate; the presence of the Q-Gate states in the deep-lane `outline` and in the `plan` unit is a compiled invariant (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]).

|*Remediation Policy* (`remediation.qgate-findings`, retry `0`, fix `3`, waiver wait `0`)
|A `blocking` verdict calls the unit, whose evidence is the phase's blocking findings. Whether a task of the role `qgate` decides the remedy follows from the bound remedies: with the shipped bindings (`fix` only, no waiver wait) the server takes `fix` without a task; a positive waiver wait adds `request_waiver`, and the choice then goes to the decision task (xref:01-planning-phases-1-2.adoc#_remediation_policy_calls[Remediation Policy Calls]). Its `fix` returns `fix_requested`, which the caller routes to the authoring state with the findings in `facts.qgate_findings`: `refine.analyze` (Phase 2), `outline.route-rework` (Phase 3, which routes by lane), or the task state `plan.revise-tasks` (Phase 4, targeted task revision). The next accepted submission re-enters `<phase>.qgate`, whose `blocking` verdict calls the unit again on the same per-plan counter. The hard cap is `5`, and the operator raises the ceiling only with `--raise fix_budget:qgate-findings=N`.

|*`fix_unchanged` instead of a Content-Hash Gate*
|A remediation submission whose target artifact (`request.md` in Phase 2, `outline.md` in Phase 3, the `TASK-*.json` bundle in Phase 4) is byte-identical to the one the last verdict evaluated is refused with `fix_unchanged` and charges nothing: unchanged content cannot produce a different verdict.

|*Surgical Bypass Predicate*
|In Phase 3 (`outline`), Q-Gate validation is automatically bypassed (logging `(phase-3-outline:qgate-bypass)` to the audit log) if and only if all three conditions hold: `scope_estimate == "surgical"`, `change_type` $\in \{\text{"bug\_fix"}, \text{"tech\_debt"}, \text{"verification"}\}$, and `deliverable_count == 1`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` applies a surgical-scope bypass of its own to its Phase 4 Q-Gate (its "B2": `scope_estimate == surgical` and at most 2 paths in the deliverables' declared file surface); in `PM-MCP` the bypass is limited to Phase 3 and `plan.qgate` runs on every path into Phase 5 (`INV-PLAN-1`, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]).

|*Exit Semantics*
|`resolved` continues to the phase exit; `waived` (operator waiver `qgate_findings:<phase>`) continues to the phase exit with the open blocking findings dispositioned accepted-by-waiver; `exhausted` and `stepped_out` enter `plan.return` (`returned`, xref:01-planning-phases-1-2.adoc#plan-outcomes[Plan Outcomes & Fallback Routes]).

|*Convergence Record*
|Each remediation round records `findings_raised`, `findings_self_seeded` (findings located in lines changed by the previous round's fix) and, on exhaustion, `findings_at_ceiling` (raised in the last round, whose fixes no round reviews). The exit renders `converged` vs `oscillating` from these figures, never from the last count alone.
|===

=== Single-Writer `change_type` Contract
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-21[PM-WATCH-GEN-21]_

`change_type` classifies the intent of a plan and its deliverables using a closed 6-value enumeration orthogonal to `domain` and `profile`:

[source,java]
----
package de.planmarshall.core.workflow.classification;

public enum ChangeType {
    ANALYSIS("analysis", 1),
    FEATURE("feature", 2),
    ENHANCEMENT("enhancement", 3),
    BUG_FIX("bug_fix", 4),
    TECH_DEBT("tech_debt", 5),
    VERIFICATION("verification", 6);

    private final String wireName;
    private final int priorityOrder;

    ChangeType(String wireName, int priorityOrder) {
        this.wireName = wireName;
        this.priorityOrder = priorityOrder;
    }

    public String wireName() { return wireName; }
    public int priorityOrder() { return priorityOrder; }
}
----

The priority order is `plan-marshall`'s documented order (`ref-workflow-architecture/standards/change-types.md`, Priority Ordering Rationale). *Deliberate change vs. `plan-marshall`*: its planning-lane routing also knows the value `feature_breaking`, which does not exist here; whether a change breaks compatibility is the separate `compatibility` field (`breaking`, `deprecation`, `smart_and_ask`; Phase 2), never a change type.

==== Single-Writer Heuristic vs Judgment Fallback

To prevent conflicting writes between deterministic heuristics and model judgment, `status.metadata.change_type` enforces a strict *single-writer* protocol at the start of Phase 3 (`outline.detect-change-type`):

1. *Deterministic Heuristic First (`ChangeTypeHeuristic`)*: Scores `clarified_request` (falling back to `original_input`) against fixed keyword tables, applying compound-intent guards and `bug_fix`-vs-`tech_debt` object disambiguation. If a single `ChangeType` wins with $\text{confidence} \ge 0.70$ and no top-two score tie, `ChangeTypeHeuristic` persists `status.metadata.change_type` and advances directly to the plan's lane state, `outline.deep` or `outline.light` (`ambiguous = false`). If no keyword fires, the top two scores tie, or $\text{confidence} < 0.70$, `ChangeTypeHeuristic` returns `ambiguous = true` and **writes nothing** to `status.json`. Either way it appends an `outline.change-type` decision record with the top score against `0.70` (link:../model-work/11-decision-records.adoc#decision-points[Model Work Specification, Decision Points]).
2. *Judgment Fallback (`submit`)*: Only when `ambiguous == true` does the engine enter `outline.classify-change-type`, a `job llm` state of role `classify` whose task submits `change_type:enum[feature|bug_fix|tech_debt|enhancement|verification|analysis],rationale:text[1..500]`, guided by `skill://pm/outline/detect-change-type/SKILL.md`, with the heuristic's scores as facts. The submitted value becomes the single authoritative write to `status.metadata.change_type`; the submit carries `confidence:int[0..100]` and appends an `outline.classify-change-type` decision record. While `classify` is unqualified the server writes `feature`, recorded as an assumption (it keeps every gate of the plan, including the Q-Gate, since the surgical bypass needs `bug_fix`, `tech_debt`, or `verification`).

==== Plan-vs-Deliverable Scope Reconciliation & Classification Validation
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-9[PM-WATCH-PHASE-9]_

* *Scope Disagreement Refusal*: Every deliverable in `outline.md` declares its own deliverable-scoped `change_type`, while `status.metadata.change_type` holds the plan-scoped classification. `OutlineValidator` and the plan instance composition reconcile the two scopes and **refuse** incompatible combinations: a deliverable with `change_type: verification` or `analysis` is read-only by definition; if any of its `Affected files` carries a mutating intent (`write-new`, `write-replace`, `delete`), or if a plan classified as `verification`/`analysis` contains mutating deliverables, validation fails closed with `change_type_scope_disagreement`.
* *Flag-Not-Block Classification Validation*: When `scope_estimate` is updated in Phase 2 or Phase 3, `classification-validate` checks for narrow-over-large mismatches (for example, `change_type == bug_fix` paired with `scope_estimate == broad`). Mismatches emit an advisory warning fact in `facts.classification_warning` but never block a transition.

=== Unplanned Changes (Recorded, Not Reviewed)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-14[PM-WATCH-PHASE-14]_

The declared footprint (`declared_files`, fixed when `outline.gate` passes) is the plan's statement of intent, not a fence inside the worktree. An envelope task that needs to change a file beyond its deliverable's `Affected files` changes it in the plan worktree without asking: there is no deviation request, no task blocking, and no review state.

* *Recording*: The server records every path of `realized − declared` (the realized footprint minus the declared write intents; a modified `(read)` entry included) as an *unplanned change* with its provenance (`task_id` and deliverable, or the loop-back round that produced it) from the Task Diff Records and the change ledger. The unplanned changes are listed in the pull-request body (`## Unplanned Changes`), in the landing record, and in the retrospective's footprint reconciliation; they never extend `declared_files`.
* *Boundaries Stay Hard*: Only a boundary breach is refused, by the non-waivable guards: a write outside the plan worktree, a change of the main checkout (Clean Main Checkout Guard), or a change of a protected path (`.marshall/**`, a pinned wrapper file). A breach raises `footprint_violation` (xref:02-planning-lanes-phases-3-4.adoc#_planning_transition_guards_real_world_invariants[Planning Transition Guards & Real-World Invariants]), whose bounded self-remedy ends in the fallback.
* *Epic Plans*: When an unplanned path overlaps the declared surface of a sibling plan of the same epic, the overlap is noted in the landing record for the epic's landing reconciliation; it never blocks.
* *Title Staleness*: A plan task that ends `infeasible`, a removed deliverable, and a domain narrowing set `status.metadata.pr_title_stale` (the shipped scope shrank).
* *Deliberate change vs. `plan-marshall`*: the batched deviation question (`hold` / `accept` / `split`), the `ScopeDeviationRequest` record, the deviation review state, the `approved_widening` approval path, and the loop-back footprint review do not exist; the recorded provenance replaces them.

=== Worktree Materialization & Envelope Execution Loop

==== Task Envelope Execution & Independent Server Verification
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-47[PM-WATCH-GEN-47], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-1[PM-WATCH-DISP-1], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-6[PM-WATCH-PHASE-6], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-11[PM-WATCH-STORE-11]_

1. *Serial Envelope Tasks*: `execute.envelope-ready` is a `job llm` state of the writer role `implement` (`job llm envelope role implement`, xref:01-planning-phases-1-2.adoc#phase-roles[Model Work per State]): entering it allocates the next envelope `envelope-M` in dependency order and creates its task; the task's worker runs in the plan worktree, and at most one writer worker runs per plan (link:../model-work/04-worker-launch.adoc#model-slots[Model Work Specification, Model Slots & One Writer per Plan]), so the worktree has one writer. The worker receives the entity `envelope-M` with only the current active plan task (`TASK-NNN`); the skills its plan tasks require come with the offer (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). The entity's submits move only the entity; the plan state reacts only to the end of the task, whose return-evaluation primitive `execute.evaluate-envelope-return` decides one closed outcome from the persisted plan-task and question records, in this precedence when several apply: `question_pending` -> `execute.task-question`; `infeasible_pending` -> `execute.replan` (only when no runnable plan task remains, item 5); `chain_tail` -> `execute.chain-tail-commit`; `remediation_chain_tail` (the finished plan tasks are remediation tasks) -> `execute.remediation-commit`; `continue` -> `execute.envelope-ready`; `all_complete` -> `execute.verify-sweep`. A task that ended without the submits its entity requires (outcome `lost`) is offered again for the remaining plan tasks within the state's self-remedy budget, then the Phase 5 fallback (`finalize.hand-back`). The `submit` of a chain-tail plan task ends the entity and yields the envelope's remaining plan tasks to `envelope-(M+1)`.
2. *Independent Verification on `submit:TASK-NNN`*: The server never trusts a task's self-reported completion. When `submit:TASK-NNN` is invoked, the daemon independently verifies: (a) *Non-Empty Diff & Boundary Check* — for write-intent tasks, verifies that `git status --porcelain` in the worktree contains changes and that no path outside the worktree, of the main checkout, or of a protected path was touched (a boundary breach raises `footprint_violation`), forbidding batched destructive `git checkout` commands; paths beyond the deliverable's declared write intents, a modified `(read)` entry included, are recorded as unplanned changes (<<unplanned-changes>>); (b) *Obfuscation & Marker Check* — scans modified lines for prohibited suppression comments, `TODO`/`FIXME` markers, or rewrite markers; and (c) *Independent Command Re-Run* — executes the task's declared verification command via the daemon's build runner and verifies a passing verdict artifact. When the verification passes, the server appends (d) a *Task Diff Record* to `change-ledger.jsonl`: `kind: "task_diff"` with `task_id`, `deliverable_id`, the `worktree_sha` of the worktree at submit, `changed_paths` (the paths changed since the previous task's recorded snapshot, present and possibly empty), and `commit_sha: null`, because tasks never commit. This is the only producer of per-task change attribution.
3. *Context Yield, Task Questions & Infeasibility*: If the worker approaches its context limit before finishing all plan tasks in `envelope-M`, it follows `yield:envelope-M` (no free parameters). Every early end of an envelope completes the entity (`envelope.completed`), and the server hands the remaining unstarted plan tasks to `envelope-(M+1)`, a new task; the server records `yield_reason` from the exit taken, a closed enum `chain_tail | question | context` persisted beside the task's classification in the metrics store. An envelope task that needs an answer calls `ask:TASK-NNN` (`question:schema[question-envelope]`), which records a question record of class `task` and ends the task with outcome `asked` (`yield_reason: question`), so no worker waits for a human; the remaining plan tasks, the asking one included, go to `envelope-(M+1)`, whose task receives the answer in `facts`. `execute.task-question` waits on the server-owned deadline of the plan's question mode; at expiry the server applies the question's stated default, validated against its options and recorded as an assumption (xref:07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Questions, Waivers & Operator Influence]). The answer is recorded as an `amendments[]` entry and listed in the pull-request body and the landing record. If a plan task is genuinely impossible as specified, the envelope task submits `infeasible:TASK-NNN` with evidence (task outcome `infeasible`); the server sets the task to `infeasible` with the evidence as its disposition, `infeasible` is terminal for that task, and substituting a weaker deliverable under the same name is strictly prohibited. Envelope tasks continue for every plan task that does not depend, transitively through `depends_on`, on the infeasible deliverable.
4. *Dependency-Ordered Creation*: A plan task is yielded to its envelope's task only when every plan task in its `depends_on` is `completed`; an envelope's task is created only when its first plan task is yieldable. A task whose dependency is `infeasible` or `removed` is never yielded.
5. *Infeasible Deliverables (Re-Planning)*: When no runnable plan task remains and a deliverable is infeasible, the plan is re-planned with the trigger `infeasible` (`execute.replan`, xref:08-dynamic-re-planning.adoc#dynamic-re-planning[Dynamic Re-Planning]): the `replan` task's facts carry the infeasible deliverables with their evidence and their server-computed transitive dependents, and it re-integrates (new or amended deliverables and plan tasks, or the loop-back to the outline below), defers or removes the infeasible part (an `infeasible` task keeps its evidence; the other tasks of the moved deliverables and their dependents become `removed`, `disposition.by: model`; removing the last deliverable is refused), waits for a prerequisite, or hands the plan back. While `replan` is unqualified the plan is handed back with the reason `role_unqualified`.
+
[[loop-back-outline]]*Loop-Back to the Outline*: a decision of a re-planning (`reintegrate_in_plan` with `reentry: outline`) and of the `plan.revise-tasks` task. The target is chosen by lane (`deep` -> `outline.deep`, `light` -> `outline.light-regate`, never `outline.light` directly), with the evidence as an amendment. The loop-back budget is a compiled `1` per plan, raised only as `fix_budget:outline-loop-back` (link:../timeouts/01-job-budgets-and-waits.adoc#loop-back-outline-budget[Timeouts & Budgets Specification, Outline Loop-Back Budget]); a spent budget takes the fallback (`handed_back` when Phase 5 committed work, else `returned`). A loop-back from Phase 5 or finalize keeps the worktree: the `outline` task's worker runs in it (a worker's working directory is the plan worktree when it exists, link:../model-work/04-worker-launch.adoc#job-working-directory[Model Work Specification, Working Directory]), and `execute.worktree-init` adopts it; a fallback taken in Phases 3–4 after such a loop-back reaches `plan.return`, which forwards the committed work to `finalize.hand-back`. The re-authored outline and the re-derived tasks compose new instance versions at the `outline` and `plan` events; a deliverable the revised outline drops has its tasks set `removed` (`disposition.by: outline_gate`), Phase 4 derives the tasks of the revised deliverables additively, and `completed` tasks are never reopened (`PM-WF-7`). The loop-back counter is never reset.

=== Per-Deliverable Chain-Tail Commit & Module Build (`git.commit_and_push`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-17[PM-WATCH-PHASE-17]_

Individual tasks never run `git commit`. When the last task belonging to deliverable $D_i$ (the *chain tail*) passes independent verification:

1. *Chain-Tail Commit via `call git.commit_and_push`*: `execute.chain-tail-commit` invokes the reusable compound sub-workflow `call git.commit_and_push (message_mode=auto_deliverable, push_mode=never)` (`PM-WF-16`, see link:../workflow-dsl.adoc[Workflow DSL Specification]). The sub-workflow cleans untracked build/temp artifacts against the compiled artifact pattern table of `pm-core` (respecting `.gitignore` and excluding `.marshall/**`), formats the conventional commit message (`feat(<module>): complete deliverable <N> - <title>`) with the configured `Co-Authored-By` trailer, streams the message over `stdin` to `git -C <worktree> commit -F -`, and appends a `kind = "change"` entry to `change-ledger.jsonl` stamped with the new `commit_sha` and git-sourced `changed_paths`. It returns `done` with the result `{commit?, pushed, clean, landed}` (a read-only deliverable returns `clean` without a commit), or `stepped_out`, which the caller routes to `finalize.hand-back`.
2. *Per-Deliverable Module Build*: `done` enters the `job` state `execute.deliverable-build`, which runs the per-deliverable verification verbs of the effective configuration (`workflow.json` `plan.phase-5-execute.per_deliverable_verbs`, default `compile` and `module-tests`, as `plan-marshall`'s `per_deliverable_build`; link:../store-schemas/07-project-configuration.adoc#config-workflow-json[Store Schemas Specification, `workflow.json`]) scoped to $D_i$'s module and records a `kind = "build"` entry in `change-ledger.jsonl`. `succeeded` continues at the re-planning checkpoint `execute.replan-check` and then at `execute.envelope-ready` (xref:08-dynamic-re-planning.adoc#replan-triggers[Dynamic Re-Planning, Triggers]). Every other fate (`failed`, `timed_out`, `killed`, `indeterminate`, `refused`, `failed_unparsed`) enters `execute.remediate-build`, writing the status field `remediation_cause: deliverable` (link:../store-schemas/02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Store Schemas Specification, Workflow State Store]), which calls `remediation.build-failure`, because an absent verdict is never admitted as a pass: its `retry` re-runs the build, its `fix` returns `fix_requested`, which allocates remediation tasks whose commit (`execute.remediation-commit`, routing `done` and `stepped_out`) continues through the router `execute.route-commit-cause` by `remediation_cause` (`deliverable` -> `execute.deliverable-build`, `sweep` -> `execute.verify-sweep`). `resolved` (the unit's own re-run passed) continues through the router `execute.route-build-cause` by the same field: `deliverable` -> `execute.envelope-ready` (the deliverable's build is green, so the next envelope follows), `sweep` -> `execute.verify-sweep`. A build failure is not waivable, so the unit has no `waived` outcome; `exhausted` enters `execute.replan` (trigger `ceiling`) and `stepped_out` enters `finalize.hand-back`.

=== Whole-Tree Verification Gates & `triage_required` Routing
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-15[PM-WATCH-PHASE-15], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-66[PM-WATCH-PHASE-66]_

Once all task envelopes reach completion, `execute.verify-sweep` (a `composite_job`) runs the end-of-phase verification steps of the plan instance (ordered by the `ext-point-build-verify-step` descriptors: `module-tests`, `quality-gate`, `coverage`, and domain `arch-gate`):

* *Footprint-Driven Scope & Relocation Override*: The server compares the realized git footprint (`references.json:realized_footprint`) against project modules to scope build executions. However, if any deliverable in the plan performed a **file relocation or deletion** (any `Affected files` entry with `delete` intent or a git rename `R`), the server unconditionally forces a **whole-tree build and verification sweep** across all modules to catch broken cross-module imports or references. A realized path claimed by no module but routed by the build map as build-neutral (for example `.github/**`) is classified `no_module`: it neither blocks nor widens a module-scoped gate to whole-tree, and the scope decision lists it.
* *`triage_required` -> Build Remediation*: Whenever an end-of-phase verification step fails, or a constituent ends without a verdict, the engine ingests the parsed build/test/arch-gate failures into `findings.jsonl` (the evidence of the unit) and enters `execute.remediate-build` with `remediation_cause: sweep` (routing as in the per-deliverable build above); its `fix` allocates remediation tasks that commit via `call git.commit_and_push (message_mode=interactive, push_mode=never)` and re-enter `execute.verify-sweep`.
* *Baseline-Red Server Rule*: Before a failing gate reaches the remediation policy, the server proves whether it is red only through failures already present on the base (link:../job-runtime/03-parsers-and-gates.adoc#_gate_honesty_verification[Job Runtime Specification, Gate Honesty Verification], Baseline Separation). The proof compares the failure fingerprints primarily with the provider's CI result of the same check on the base (the merge base, or the latest base-branch commit containing it); a local build of the merge base is the fallback for local gates such as the pre-push quality gate, or when the provider has no result for the base. When every failure is baseline-only, the server writes a `baseline_red` build row into `change-ledger.jsonl` bound to the `worktree_sha`, the merge base, and the digest of the accepted diagnostics, and the gate passes: the freshness gate counts that row as passing for the same `worktree_sha` only, a finalize gate step completes `done` with `assurance_verdict: degraded`, and the pull-request body and the landing record list the baseline failures. Coverage debt in untouched modules is a non-blocking `baseline_debt` finding. A red that is not provably baseline-only is plan-caused and calls the build (or, in finalize, the CI) remediation policy. There is no baseline-red state and no operator acceptance; the plan is never looped back to remediate a baseline failure.

=== Phase 5 Exit Barrier: Dual Freshness & Pending-Tasks Gates
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-25[PM-WATCH-GEN-25], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-17[PM-WATCH-PHASE-17], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-96[PM-WATCH-PHASE-96]_

Transitioning from `phase-5-execute` to `phase-6-finalize` is governed by an atomic dual-gate barrier in `execute.exit-barrier`. **Both gates are always evaluated together before acting on either** so a single diagnostics payload surfaces all reasons if both fail:

1. *Pending-Tasks & Clean-Tree Gate*: Every `tasks/TASK-*.json` record in the plan must be in a terminal status (`completed`, `infeasible`, or `removed`), every `infeasible` or `removed` task must carry its recorded `disposition` (link:../store-schemas/06-task-and-references.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]), and no task may be open (`pending_count == 0`, `in_progress_count == 0`); the gate reports the counts of every status and lists each non-`completed` task with its disposition. The worktree must have zero uncommitted modifications (`git status --porcelain` is empty). A dirty tree is handled first: it enters `execute.remediation-commit`, whose artifact review separates build leftovers from real changes; real changes are committed and recorded as unplanned changes, and the route continues to `execute.verify-sweep` because `HEAD` changed; only a boundary breach raises `footprint_violation`. A barrier failing on open tasks routes to `execute.envelope-ready` while runnable tasks remain, and otherwise to `execute.replan` (trigger `infeasible`) (link:../state-catalogue/03-plan-phases-4-5-land.adoc#state-catalogue-execute[State Catalogue]).
2. *Worktree Freshness Gate (`worktree_sha`)*: Freshness is keyed strictly on `worktree_sha` — the SHA-256 digest over the `HEAD` commit id plus, for every path the status reports as changed, deleted, or untracked (sorted by path), the path and either the file's bytes read from disk or a deletion marker, computed by the single git contract operation `git.worktree-sha` for both variants (link:../job-runtime/03-parsers-and-gates.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash]) — never on `HEAD` commit SHA alone (which would misclassify an unbuilt dirty tree as fresh). The gate queries the change ledger (`change-ledger.jsonl`) and reads the explicit closed-enum `status` member (`fresh`, `exempt`, `stale`, `undecidable`), never inferring freshness from a process exit code or from `"not stale"`: `fresh` requires that every required build notation for the realized footprint has a passing `kind = "build"` ledger entry whose recorded `worktree_sha` equals the current live `worktree_sha` and every ledger row matches a registered build notation of the project; `exempt` applies when the `build-decision` verdict over the build map and the realized footprint is `not_necessary` (every realized path is build-neutral); the `documentation_only` file-type bucket is a file role for `profiles[]` assignment and is never read as a build verdict (as in `plan-marshall` ADR-004); `stale` / `undecidable` fails the barrier with an explicit `stale_reason` (`tree_modified_since_build`, `last_build_failed`, `no_successful_build`, `missing_module_build`, `unrecognized_build_notation`, `reconciliation_record_absent`, `ledger_unreadable`, or `worktree_sha_unavailable`). A reason a build clears routes back to `execute.verify-sweep`; `unrecognized_build_notation`, `ledger_unreadable`, and `worktree_sha_unavailable`, which no sweep clears, raise the `guard_indeterminate` condition on the barrier (link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-guard_indeterminate[State Catalogue Specification, Conditions]), whose bounded re-evaluation and spent-budget fallback replace an unbounded sweep loop. A live or recorded `worktree_sha` that is `unavailable` (a failed git invocation) makes the gate `undecidable` with `worktree_sha_unavailable`, never `fresh`, and ledger rows of another `worktree_sha_version` never match the live digest (link:../job-runtime/03-parsers-and-gates.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash], rules 4 and 5).
+
`last_build_failed` (the latest build row for a required notation is not `succeeded`) is a different operator action than `tree_modified_since_build` (source edited after a passing build) and is never reported as it; when no successful build exists at all the reason is `no_successful_build` and no `freshness_reconcile` is recorded (it requires a `prior_build_worktree_sha`). `reconciliation_record_absent` lists in `facts.admitted_causes` the causes that absence admits (`source_drift_unbuilt`, `no_successful_build`, `record_owed_not_emitted`, `commit_outside_reconcile_membership`), so the refusal reports what it observed rather than guessing one cause. Where the step records show that `HEAD` is a finalize-internal commit, the refusal names the committing step.
