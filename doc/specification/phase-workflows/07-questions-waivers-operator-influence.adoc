== Questions, Waivers & Operator Influence
_See Requirement link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_

_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-69[PM-WATCH-PHASE-69], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-87[PM-WATCH-PHASE-87]_

`PM-MCP` keeps two kinds of human input apart. A *content question* (a request clarification, an init classifier question, the optional outline review, a task question, a question a worker raises before its judgment, a team-configuration choice of the workspace setup) is a server-owned question record with a server-owned deadline and default. An *override* (a waiver or its revocation, an operator abort, `delete-plan`, an integrity resolution) is never a content question: it is taken only through the authenticated operator channel, the operator CLI (`pm-operator …`) or a paired web device, and a value relayed by a model or a session is never accepted for it. MCP elicitation carries only the choices of the project setup and of the plan and epic bootstraps, which the entry session drives, among them the operator-configuration choices the server raises in the setup. An override is never taken as a content answer, and a content answer given through elicitation or a paired device is never an override.

=== Question Records

* *One Mechanism*: Every content question is a record in the scope's append-only `questions.jsonl` (plan, epic, or workspace store; schema: link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]). Records survive the end of every session and worker; answered records are listed in the pull-request body, the landing record, and the retrospective. The delivery and the deadline mechanics are specified in link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Envelopes, Questions & Deadlines].
* *Creation*: A worker creates a question through the `ask` link (form `submit`, `question:schema[question-envelope]`) of its task entity where its state declares `ask` in its `job llm` clause (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Task States (`job llm`), item 8]); the task ends with the outcome `asked`, the state waits in its question state `<state>.asked`, and on the answer or the assumption the asking state is entered again and a new task of the same role follows with the answer in `facts`. An envelope task asks through `ask:TASK-NNN`, which records the question and ends the task (xref:03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Task Envelope Execution], item 3); the refine and outline tasks ask through the `questions` list of their `submit` (each item becomes a record). Server-raised questions (the init classifiers, the outline review, the team-configuration choices of the setup) are created by their primitive with server-owned options.
* *Recommendation & Adjudication*: Every question carries its recommended option, the asker's confidence, a rationale, and a decision kind, and every new question set passes the adjudication `question.adjudicate` before delivery, which in the mode `quorum` answers a set where the quorum declarations of its kinds decide it (link:../model-work/10-decision-quorum.adoc[Model Work Specification, Recommendation Score & Decisions: Ask or Quorum]).
* *Delivery*: Every content question is delivered through the web app, the dependable channel, and through the answer links of the scope's representation, through which the entry session relays the user's answer; the first valid answer wins, and a question is never a stop point of a session or a worker (link:../model-work/06-envelopes-questions-deadlines.adoc#question-delivery[Model Work Specification, Delivery, Mode & Server-Owned Deadlines]).
* *Answer Validation*: Every channel passes the same check: an unknown `branch_key` is refused with `invalid_link_args`, a second answer with `already_answered`, and an answer after expiry with `question_expired`.
* *Waiting State*: The state that waits for a question is a question state with a server-owned deadline (catalogue kind `awaiting_user`); its awaited event is `QUESTION_ANSWER` from any channel, and the server's timer applies the expiry fallback without a model call or a session. A question state and a waiver wait never overlap in one plan, the integrity pause holds a pending expiry, and operator `abort` or `delete-plan` closes the record `cancelled`. No content-answer command exists in `pm-mcp` or `pm-operator`.
* *Bootstrap Choices Are Links*: Before a plan exists nothing is a question record: choosing what to work on (`start.choose`), a source's own choices (a lesson premise, recipe parameters, accepting a text the screener flagged), and the commit options of `start.ready` are the user's intent, relayed by the entry session through the bootstrap's links or answered through MCP elicitation (link:../state-catalogue.adoc[State Catalogue], Bootstrap). They have no question wait, no expiry, and no fallback; an entry nobody continues is removed by the pending-record sweep. A plan its epic starts has no bootstrap choices: the server runs its bootstrap with the source `epic_row` (xref:06-finalize-re-entry-and-merge.adoc#epic-plan-start[Epic Plan Start]).

=== Question Mode & Deadline

The operator decides per project in `local-config.json` how questions are handled (`questions.mode`, optionally per class, and `questions.wait_seconds`; link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]): who answers and how long. Who decides a question of which kind is not operator configuration: it is the decision declarations of the project-owned adjudication unit (`ask` or a quorum per decision kind) and the artifacts of the roles they list (link:../model-work/10-decision-quorum.adoc#decision-declarations[Model Work Specification, Decision Declarations]). The modes and the compiled expiry fallback per class are owned by link:../model-work/06-envelopes-questions-deadlines.adoc#question-delivery[Model Work Specification, Delivery, Mode & Server-Owned Deadlines]; the fallback values of the setup's question states are in link:../domain-extensions/04-setup-state-machine.adoc#setup-questions[Domain Extensions Specification, Setup Choices by Owner]. A scope in an `operator`-mode question state is listed as waiting for an answer in `pm-operator status` and the web app. `questions.outline_review` (`none` default, or `ask`) switches the optional outline review question on (xref:02-planning-lanes-phases-3-4.adoc#outline-gate[Server Outline Gate]).

=== Waivers & Operator Verbs

A *waiver* declares a waivable gate met or raises a budget. It is written only by the operator verb `pm-operator waive <plan_id> <gate> --reason "…"` (or `--raise <budget>=N`), stored in the plan's append-only `waivers.jsonl` (`waiver_id`, `gate`, `mode: met | raise`, `value`, mandatory `reason`, operator identity and channel, `event: waived | revoked`, `at` (the creation time of a `waived` line, the revocation time of a `revoked` line); mirrored to `audit.jsonl`), and composed into a new plan instance version (composition event `waiver`). A waiver is plan-scoped, not bound to `HEAD`: it may be set at any time until the gate's fallback is taken (after that it is refused `plan_ended`), and it applies to every later evaluation of its gate. A gate admits a failure only through a waiver lookup at evaluation time, which logs a consumption (`HEAD`, covered items such as check names or finding ids); the consumptions are listed in a pull-request comment and in the landing record. `--raise` targets only a policy budget (`fix_budget:<policy>`, `retry_budget:<policy>`) and sets an absolute ceiling above the effective ceiling in force and at most the compiled hard cap. `waive` refuses a gate outside the list (`not_waivable`), `unwaive` refuses a consumed waiver (`already_consumed`).

[cols="2,4"]
|===
|Gate identifier |Waives

|`review_evidence` or `review_evidence:<bot_kind>`
|Missing review evidence of the required bots (Predicate 2 of the pre-merge barrier); the merge records `review_state: unreviewed_by_waiver`.

|`ci_check:<check_name>`
|A named failing CI check.

|`analysis_gate:<provider>`
|The quality gate of a code analysis provider (for example `analysis_gate:sonar`).

|`findings:<class>`, `findings:<provider>`
|Open findings of a class, or of an analysis provider, after triage.

|`qgate_findings:<phase>` (`refine`, `outline`, `plan`)
|Blocking Q-Gate findings of the phase; they are dispositioned accepted-by-waiver.

|`spend`
|The finalize spend check at `merge.gate-entry`, the gate's only evaluation point; a `met` waiver passes it.

|`--raise fix_budget:<policy>=N`, `--raise retry_budget:<policy>=N`
|Raises a policy budget.
|===

Never waivable: every gate on the non-waivable list of the waiver record (link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record, Refusals]), among them integrity breaches, security findings, a build failure, a merge conflict, and a provider refusal of the merge action.

*Waiver Requests*: The `request_waiver` action a remediation unit's `decide` task chooses files a record in `waiver_requests[]` of the plan status (`request_id`, `gate`, `rationale`, `evidence_uri`, `requested_at`, `expires_at`, `outcome?`), announced to the operator independently of the question delivery: shown in the plan's view as `facts.waiver_request` (link:../mcp-tools/01-core-workflow-tools.adoc#question-waiver-facts[MCP Tools Specification, Question Records & Waiver Requests in Representations]), listed by `pm-operator waivers <plan_id> --pending`, `pm-operator status`, and the web app, and posted as an idempotent pull-request comment with the label `pm-mcp:waiver-requested` when a pull request exists. A waiver request is never a question record: a session may show the announcement, but only the operator's `waive` answers it, and its bounded wait then ends in the fallback.

*Operator Verbs*: `waive`, `unwaive`, `waivers`, `abort`, and `grant-access` act on a running plan (`grant-access <plan> <project> read|read-write --reason` appends an audited grant record to the plan store; an access to another project without a grant raises `precondition_unmet` naming the command, whose bounded server `retry` re-checks and whose spent budget takes the fallback); `delete-plan`, `accept-edit`, `credentials`, `config`, and `roles` are operator commands (link:../cli-and-security/02-credentials-and-operator.adoc[CLI & Security Specification]). No operator verb stops, continues, or steers a plan between phases: the server runs every plan to its outcome. *Deliberate change vs. `plan-marshall`*: no in-run operator decision exists. Outline approval is a server gate, scope deviations are recorded (xref:03-q-gate-and-execute.adoc#unplanned-changes[Unplanned Changes]), infeasible deliverables and refuted hypotheses are decisions of role tasks, baseline-only red is a server rule, and merge authorization is the waiver lookup; the verbs `decide`, `authorize-merge`, and `force-gate`, the artifact-gate bypass `--allow-bare-transition`, the handshake and baseline drift override, the pre-rebase overlap override, and the escalation beside a timed-out `retry` do not exist.

*Intent Amendments*: Phase 2 answers are written into `request.md` (`## Clarifications`). Every later answer or decision that changes the plan's intent (an answered or assumed question in Phases 3–6, an answered task question, a narrowed scope after a refuted hypothesis, a removed deliverable, or a refuted premise) is persisted as an entry of `mcp/status.json -> amendments[]` (`at`, `phase`, `source: user | model | assumption | refutation`, `question_id?`, `text`, `supersedes`). Every later representation and task that renders the request (outline, `create-pr`, landing envelope) includes the amendments, so a superseded statement of the request never reaches a later phase unmarked.

=== Question Envelope Schema

Workers never prompt a user (a headless worker has none) and never wait on a question. A refine or outline task completes its pass on best judgment and includes a batched question list in its `submit` payload (`refine_prompt` or `outline_prompt`) as the free parameter `questions:list<schema[question-envelope]>?`; an envelope task asks through `ask:TASK-NNN`, and any other task through the `ask` link its state declares. Every question is validated against the named schema `question-envelope` (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]; link:../model-work/06-envelopes-questions-deadlines.adoc#question-envelope-schema[Model Work Specification, Question Envelope Schema]). Each accepted question is persisted as a question record (link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]).

Every option is authored as a two-sided contract whose label names the workflow branch selected when chosen, with the `recommended` option listed first.
