== Automatic Review: Registry, Participation, Refusals & Ingestion
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-24[PM-WATCH-PHASE-24], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-25[PM-WATCH-PHASE-25], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-26[PM-WATCH-PHASE-26], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-27[PM-WATCH-PHASE-27], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-28[PM-WATCH-PHASE-28], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-29[PM-WATCH-PHASE-29], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-30[PM-WATCH-PHASE-30]_

`plan-marshall:automatic-review` (order `30`) and the composite wait `finalize.concurrent-wait` work from one server-owned review-bot registry and write one participation record per `(pr_number, round, bot_kind)` into the plan's `review-participation.jsonl` at review time, each stamped with the `HEAD` it observed (link:../store-schemas/03-findings-and-review-records.adoc#review-participation[Store Schemas Specification, Review Participation Record]). The rules mirror `plan-marshall` `automatic-review` (`SKILL.md`, `standards/*.md`), verified at `plan-marshall` commit `f3de0e14f`; re-verify against the latest `plan-marshall` version before implementing. The comment fetch and the reply transmission are the findings contract of `pm-mcp-core` (`FindingSource`, `FindingResponder`), the pull-request and check reads contracts of `pm-mcp-ci`, both implemented by `pm-mcp-github` and `pm-mcp-gitlab` (link:../../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]).

=== Review-Bot Registry

The registry holds one compiled-in record per `bot_kind`; a project may add records.

[cols="1,4"]
|===
|Field group |Content

|Identity & trigger
|`bot_kind` and `author_login` (the identity used for author binding). One `trigger_token`: the server posts only this token, never one chosen per call; `trigger_verbs{incremental, full}` (CodeRabbit `@coderabbitai review` / `@coderabbitai full review`). `trigger_events`: the PR events the bot subscribes to (pr-agent does not subscribe to `synchronize`). The server posts every trigger under the agent identity of the provider credential, never under the operator's. `trigger_semantics` (`comment_trigger`, the default, or `auto_on_push`): a bot that does not act on trigger comments from the agent identity is configured to review every push on its own and registered as `auto_on_push`; the server then never posts a trigger for it, its waits are satisfied only by a review of the pushed `HEAD`, and a remedy that needs a trigger (re-trigger after a window, the `full` verb) is unavailable for it, so the bot resolves `unproven` instead.

|Publish shapes
|`publish_shapes` ⊆ `{conversation, inline_thread, pr_review}` and `participation_evidence` (which shapes prove a review). Participation markers are anchored patterns (start of block or structural element, never a bare substring), and each marker records the sample (PR count) it was validated on. Observed shapes the registry does not declare raise a `registry_drift` finding; a missing optional shape is not non-participation.

|Currency
|`participation_requires_update` (mirrored from `plan-marshall`, where it opts a bot into the currency test; `sourcery` declares `false`, `coderabbit` and `cuioss-review-bot` declare `true`). In `PM-MCP` it exempts no bot: the currency test is unconditional (xref:06-finalize-re-entry-and-merge.adoc#_two_fail_closed_barrier_predicates[Two Fail-Closed Barrier Predicates]). `reviewed_sha_carrier` (`structured`, `body_pattern`, or `none`) with `reviewed_sha_pattern` (cuioss-review-bot: body "Review updated until commit `<sha>`"); `completion_check_name` (nullable).

|Refusal recognition
|`refusal_patterns`, `refusal_size_patterns`, `refusal_wrapper_markers` (CodeRabbit `<details><summary>⚠️ Action not completed</summary>`), and `rate_limit_eta_patterns` (including "reset in 57 minutes"; the CodeRabbit reset notice may omit its trailing phrases). `no_new_commits_patterns` (CodeRabbit "Review skipped" / "No new commits to review") and, for a bot without `trigger_verbs.full`, `no_new_commits_class` (`refused` or `declined`). Sourcery phrasings: "your pull request is larger than the review limit of", "reached your weekly rate limit of", "you've used your own review budget of N diff characters".

|Rate class & caps
|`rate_limit_class` (`awaitable_window`, `hard_quota`, or `unknown`), `rate_interval_seconds`, `attempt_ceiling` (compiled default `6`, link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows]), and `structural_caps{max_files, max_diff_chars}`.

|Content classification
|`actionable_content_markers`, `contentless_review_markers`, `ignore_patterns`, `severity_map`, and dated per-bot `config_verdicts[]` (for example CodeRabbit `enable_prompt_for_ai_agents`).
|===

Compiled-in data (re-verify before implementing): `coderabbit` (one review per hour, `awaitable_window`, `max_files: 100`); `sourcery` (`hard_quota`, 250,000 diff characters per 7 days, per PR 150,000 characters or 300 files); `cuioss-review-bot` (`unknown`, reviewed SHA in the body only). The provider cap for a GitHub comment body is 65,536 characters.

* *One Shared Reader*: Required, optional, and enabled populations are resolved only from `required_bots` / `optional_bots` against the registry through one shared reader. An unregistered token fails loud (`unregistered_kind`) with the same disposition everywhere and is never counted in a ratio denominator.
* *Review Bots Are Not CI*: `ci_status` evaluation excludes check-runs owned by registered review bots. On a bot timeout the engine first checks that the bot's trigger workflow or app is installed for the repository (`not_wired`) before reporting `unproven`.
* *Size Cap at Fetch Time*: A bot whose structural cap is below the PR's measured diff is classified `refusal_candidate` when comments are fetched; an unmatched comment from it is checked against its refusal phrasings before any participation verdict.

=== Per-Bot Participation States

Per round, every bot of the roster resolves to exactly one per-bot `state` of the closed enumeration defined in link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations] (with a `refusal_mode` for `refused`); the composite `bot_status` of `finalize.concurrent-wait` is the aggregate of these states over the required bots through the closed per-bot mapping table defined there (satisfied, `running` when a run is observed, `pending` when none is observed and then `unproven` when the poll budget is spent, fail-fast `unproven`, and `refused` by mode), and its outcomes route the finalize excerpt (link:../workflow-dsl.adoc[Workflow DSL Specification]). `unproven` for a required bot calls `remediation.review-findings` with the failure kind `evidence_missing`, whose `retry` is a window-gated re-trigger that is never offered for `unregistered_kind` and `not_wired`; their only ends are a `review_evidence` waiver or the fallback. The rules below decide which state applies.

* *Review Evidence*: Completion requires a review verdict object (a review, an inline comment of that review, or a completed check-run) authored by the bot's registered `author_login`; per-bot completion waits match `author_login`, because a SHA match proves which commit was reviewed, not who reviewed it. Rate-limit meta-comments, re-served prior-round comments, "Review completed" placeholders without a review, inline comment or check-run, and thread acknowledgements never count. A declared clean verdict ("No major issues detected", "No code suggestions found") counts as `participated_but_empty`.
* *Refusal Precedence*: A refusal outranks a later edit timestamp, and a refusal observed in the same pass as a clean review of the same bot resolves `refused`. A refusal never sets the covered commit and never advances the `head_at_completion` of `automatic-review`.
* *Declined vs Unproven*: `declined` requires a named commit that is not the merge candidate; evidence that names no commit resolves `unproven` for a bot with `reviewed_sha_carrier: none`.
* *Nobody-Reviewed Shapes*: `not_triggered`, `rereview_silent_failure`, and `run_stuck` stay distinct; workflow runs are queried unfiltered by branch. An exhausted poll yields `unproven`, never `absent`.
* *Opposite Claims*: `unreadable` (the read failed) and `silent` (the read succeeded and nothing was published) are opposite claims; a prediction is recorded as `unrecorded`, never as an observation. A fetch returning zero comments resolves to exactly one of: no review covering `HEAD` (`absent` or `unproven`), reviewed clean (`participated_but_empty`), or fetch unreachable (`unreadable`).
* *Per-State Remedies*: Each non-participating state carries its own remedy in the evidence of `remediation.review-findings` (the kind of re-trigger its `retry` performs, or none), never a shared generic `retry`, and a `reopens` axis (`awaitable` or `hard`) derived from the refusal mode. A roster question that was never put renders "question never put"; an awaitable refusal's representation names the governing config key and value.
* *Partitioned Reporting*: Unproven and blocking sets are reported partitioned by `roster_class` (`required`, `optional`, `unclassified`); only the required partition gates. The roster aggregate is `reviewed`, `incomplete`, `vacuous` (empty required set, answered: `review.required_bots` present in `project.json` as `[]`), or `unestablished` (never answered: the key is absent; there is no separate provenance bookkeeping, the presence of the key is the answer); an empty roster never renders `reviewed` or `clean`.
* *Per-Bot Facts*: `facts.bots` renders per bot `state`, `completion_check`, and `at_head` as separate columns (hypermedia-format.adoc), because "participated", "completion check finished", and "CI check green" prove different things. The participation summary renders per class `required k/|required|`, `optional j/|optional|` (with each silence's state), and `roster r/|roster|`; a bare N-of-M is never emitted.

=== Refusals & Rate Windows

1. *Derived Recognition*: Refusals are recognised by a derived rule (wrapper marker plus registry patterns), tested with controls in both directions. An unrecognised refusal-shaped notice resolves `refused` with mode `unknown`; an unmatched bot comment is never counted as participation.
2. *Capture on Sight*: The body and `observed_at` of a refusal are captured when first seen; a later absence of the notice is not a refutation, and a body divergence on re-read is reported. Every refusing bot is reported, never only the first.
3. *Wake on Edits*: Waiters order comments by `max(created_at, updated_at)`.
4. *Currency of a Notice*: A notice is current only if it answers a trigger this run posted (by trigger id) or its stated window is still open; otherwise it is `stale`. A rate-limit refusal is bound to the request it answered and to its reset time; a window already waited out is never restarted by re-reading the same refusal.
5. *Window Derivation*: A window's `reset_at` is the bot-stated reset ETA when one is published and parsed (a floor to re-check, which beats every derived value); otherwise `claimed_at + rate_interval_seconds` of the bot's registry record; otherwise the compiled rate-window floor. The re-review timeout is the `reset_at` of the bot's open window, or, without an open window, the registered interval plus a compiled completion allowance. Values, floor, and allowance are defined only in link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows] (compiled, not configurable). Waiting past the ETA records a reason. A detected but unparsed ETA records `eta_unparsed` (a drift signal), never "no ETA", and falls back to the interval. Wait budgets derive from the registered interval, never from a flat timeout. The triggers per `(repository, pr_number, bot_kind)` are bounded by the registry's `attempt_ceiling`; at the ceiling no further trigger is posted and the bot resolves `unproven`.
6. *Closed Windows*: A trigger is never posted inside a closed window (a trigger extends the window, close and reopen do not reset it, and windows are organisation-scoped); `retry` is offered only while the window is open.
7. *Mode Routing*: `size` files a structural finding that `remediation.review-findings` triages (`FIX` splits the pull request, `ACCEPT` accepts, `SUPPRESS` disables the bot for this PR), never a wait; `weekly_quota` and `hard_quota` resolve `unproven` at once with no `retry`, never a wait; `rate` waits for the window and then triggers; `no_unreviewed_commit` routes to `finalize.review-full-trigger`, which posts the registry's `full` trigger verb once for the current `HEAD` (a repeated notice after that trigger resolves `unproven`). A stale bot with a declared comment trigger gets the trigger posted once and a bounded wait, then resolves `unproven` (never re-triggered for a quota refusal).
8. *Satisfying Event*: Every wait names its satisfying event and its producer; if the bot's `trigger_events` cannot fire on this retry path, the wait fails fast with `no_satisfying_event`.
9. *Re-Trigger Target*: The re-trigger target is the unproven set (including bots that never published), selected after the round's own fetch, never by comment recency. The wait and trigger target set is the unproven part of `required ∪ optional`; the gating set is the required bots only.
10. *Per-PR Counters*: Rate-window claims (the cross-plan leases in `review-bot-windows.json`) and attempt counters are kept per repository, PR, and bot.
11. *No-New-Commits Notice*: A bot notice matching the registry's `no_new_commits_patterns` ("Review skipped: No new commits") is never participation and never a neutral acknowledgement. For a bot whose registry declares a `full` trigger verb it resolves `refused` with mode `no_unreviewed_commit`, whose remedy is that verb (observed to succeed within seconds on the same `HEAD`). For a bot without a `full` verb the registry's `no_new_commits_class` decides: `refused` (mode `no_unreviewed_commit`, resolving `unproven` because no remedy verb exists) or `declined` (the `plan-marshall` classification). *Deliberate change vs. `plan-marshall`*: `plan-marshall` classifies the notice as `declined`, accepts the decline, and never re-triggers; `PM-MCP` re-triggers with the `full` verb wherever one exists, so no stale credit stands for an unreviewed `HEAD`.
12. *Pre-Wait Cap Gate*: Before entering `finalize.concurrent-wait`, the engine measures the diff (files and diff characters) against each required bot's `structural_caps`. An exceeded cap records `refused` with mode `size` pre-emptively, names the cap and the measurement, and calls `remediation.review-findings` instead of waiting, whose triage state shows each structural refusal as a finding and offers `triage:<finding_id>` per finding (`FIX` splits, `ACCEPT` accepts, `SUPPRESS` disables the bot for this PR); when a path partition (for example test sources vs the rest) brings each part under the cap, the finding proposes that concrete split. Under every cap the flow is unchanged.

=== Comment Ingestion

1. *Every Firing*: Comments are re-ingested on every firing of `automatic-review` and on every re-entry of `finalize.concurrent-wait`. All three surfaces (conversation, inline threads, PR review bodies) are fetched and classified.
2. *Own Comments by Provenance*: Own comments are recognised by provenance (server-recorded posted comment ids and trigger ids); headings are secondary. Repository-owner comments are genuine reviews unless provenance matches. Posted triggers are excluded and counted with a reason; a bot comment quoting a trigger is still ingested.
3. *Noise Filter*: Fenced code, blockquotes, and `<details>` blocks are stripped first; a comment is noise only if an acknowledgement pattern covers the whole remainder; length is an outer bound only. Drops are recorded distinguishably from genuine acknowledgements.
4. *Actionable Content*: A bot comment becomes a finding only if it matches the registry's `actionable_content_markers` (when declared) after noise stripping; enumerated refusal patterns are the secondary guard.
5. *Status Line then Remainder*: A `review_body` yields finding candidates only from the text after the bot's status line ("Actionable comments posted: N"). A body consisting only of a status line, an approval notice, or a "Review finished" header is a status record, never a finding, and never enters Predicate 1.
6. *Complete Fetches*: Every connection is paginated (`pageInfo`) or reports `observed` vs `cap`; a clipped fetch is never success.
7. *Comment Identity*: A comment's identity is `(bot_kind, comment_id)` plus its edit marker (`updated_at != created_at`); an edited comment is new information.
8. *Fetch Freshness*: The merge barrier re-fetches immediately before merge; a review newer than the last fetch blocks.
9. *Summary-Card Overflow*: Overflow folded into a summary card ("Outside diff range comments (N)") is ingested as findings.
10. *Participation-Only Artifacts*: A persistent summary card or a trigger acknowledgement is participation-only: no finding, no reply. Refusals, rate-limit notices, own comments, and other participation-only artifacts are never filed as findings; they update the participation record only.
11. *Agent Prompt Blocks*: The bot's "Prompt for AI Agents" block is stripped once, at the triage-representation boundary, and never by length clamping; the stored body keeps it, quarantined as untrusted content.

== Post-Run Metrics & Landing Envelope

`record-metrics` (`998`) composes the plan's figures once. `print-phase-breakdown` (`999`, an operator view) and the landing envelope of `emit-landing` (`1000`) render that composition and never re-derive a figure; the terminal `completed` representation carries only its outcome facts (`merge_outcome`, `landing_delivery`, `owed[]`), not the figures. The per-dispatch and per-phase rows are persisted in the plan's metrics store (link:../store-schemas.adoc[Store Schemas Specification]).

=== Metric Aggregates (`record-metrics`)

* *Population-Stamped Aggregates*: Every published sum is `{value?, rows, rows_unmeasured, population_count}`. A total over an empty population omits `value`, and a structurally unmeasured plan is excluded from composition roll-ups. When `rows_unmeasured > 0` the total is labelled a floor (`total_is_floor: true`, listing the channels lacking evidence) and never wins a max-reconciliation against another source; a channel with no records renders `no_evidence`. This applies to `total_tokens` and `total_wall_seconds` alike.
* *Priced Units*: A cost figure, where one is shown, is exactly one derived figure, `priced_units = input + 5 × output + 0.1 × cache_read + 1.25 × cache_creation`, computed in views from the persisted raw token components (link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]) with the weights taken from one named constant table (`PricingWeights`; output at 5× input follows list prices). `priced_units` is never persisted per dispatch or per phase; a row lacking a component contributes to `rows_unmeasured` of the priced figure, which is then a floor, and a row that reports only a total makes the priced figure `not_derivable` for that row. Every percentage names its unit (`priced_units` or `tokens`), and the unweighted `total_tokens` is never labelled cost. *Deliberate change vs. `plan-marshall`*: `plan-marshall` computes `billing_weighted_total` with output at 1×, which understates generation (about 1.1% of the column against about 5.3% of spend); legacy baselines are re-derived from their raw components under `PricingWeights` before any comparison.
* *One Population per Figure*: Every token figure carries its population stamp (`dispatched` or `main_context`); totals are formed only within one population, and figures of different populations are never summed or compared in reports.
* *Dispatch Accounting*: Per phase, `dispatches_rendered`, `dispatches_returned`, and `dispatches_unreturned` are recorded; a non-zero difference is a recorded gate signal in `facts`.
* *Phase Time Monotonicity*: Every phase block with both timestamps is validated (`end >= start`; start, end, and duration agree when all three exist), and `phase_blocks_checked` and `phase_time_violations[]` are recorded beside `any_phase_missing_end_time`.
* *Stall Rate & Ledger Divergence*: A dispatch that terminates with `tasks_remaining > 0` and no blocked cause counts as `stall`; the stall rate and the `yield_reason` counts are published per plan. When two ledgers can diverge (dispatch rows vs audit rows), `record-metrics` publishes `union_rows` and a non-blocking `reconciliation{findings_count}` warning instead of picking one ledger.
* *Spend Classes*: Token spend is published per spend class (`submitted`, `findings_only`, `no_product`, `unmeasured`) cross-tabulated with the termination `status`, with the residual asserted `0` (link:../dispatch-and-effort/02-dispatch-observability-and-spend.adoc#spend-accounting-budget-anchors[Dispatch & Effort Specification, Spend Classes]); spend is never classified by `status`.
* *Caller-Drift Rate*: Per plan, the count of link calls rejected per `rejected.reason` and the count of repeated identical rejected calls (same link and same argument digest), with the failure classes `caller_drift` and `server_fault` kept apart (link:../mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]). `PM-MIG-5` compares this rate with the legacy baseline of argument-shape failures per plan.
* *Per-Document Consumption*: From the served-content ledger (link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]), per served URI and section the read count, the bytes served, and the repeat reads within one dispatch, together with the per-phase document residency. Host `Read`/`Grep` bytes are outside the server and are never estimated into these figures.
* *Terminal Phase Boundary*: Phase 6 is recorded with `boundary: provisional`, `measured_until`, and `excluded_steps` (catalogue row `998`); every consumer (the landing, `print-phase-breakdown`, the quality report) renders the label with the figure, never a provisional total as a final one. Every earlier phase carries `boundary: closed` once its close row exists (labelled `re_entered` when rows follow its close).
* *Build Figures*: `build_count` and build time come from the plan's change ledger (`kind = "build"` rows). An unreadable ledger renders `unavailable`; when the runtime job journal shows build jobs for the plan while the ledger is unavailable or empty, a finding is filed.
* *No-Verdict Jobs*: A `timed_out` job counts as `no_verdict` in every roll-up (link:../timeouts/01-job-budgets-and-waits.adoc#no-verdict-rule[Timeouts & Budgets Specification, Timed-Out Outcomes Are No-Verdict]).
* *Wait Lapses*: `wait_lapses` are recorded per lapsed bot wait, keyed by the bot status that ended it (`unproven`, `refused_awaitable`, `refused_hard`; the `finalize.concurrent-wait` outcomes `review_evidence_missing` and `bot_refused_awaitable`, link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations]), together with whether the awaited operation later settled green. CI waits never lapse (they are re-polled), so they have no lapse kind. The counts enter the landing envelope as policy evidence.
* *Rendering*: `print-phase-breakdown` renders absent or unmeasured figures as `unmeasured`, never `0`, and renders the coverage verdict whenever coverage is decidable (rows and total persisted together), including when rows exist but the sum is zero.

=== Landing Envelope (`emit-landing`)

The landing envelope carries:

* *Identity & Merge Facts*: `plan_id`, `outcome` (`merged`, `handed_back`, `returned`, `no_change`, or `aborted`), `plan_source` (the plan's `pm_start` source, `origin.source`: `request`, `issue`, `lesson`, `recipe`, `local_changes`, or `pr`), `prs[]` (all PRs of the plan, re-recorded when a PR is replaced or split), `merged_pr_numbers`, `merge_commit_sha` (required when merged), `merge_state` (`landed`, `open`, `closed`, `enqueued_not_landed`, `not_applicable`, or `unknown`), derived from the same observation as the plan's `merge_outcome` through the one merge outcome mapping (link:../store-schemas/02-workflow-state-store.adoc#merge-outcome-mapping[Store Schemas Specification, Merge Outcome Mapping]); `unknown` is recorded only when the observation failed and is counted in `missing_facts`, and `owed[]`, the plan's owed items (link:../store-schemas/03-findings-and-review-records.adoc#owed-item-record[Store Schemas Specification, Owed Item Record]), as an explicit empty list when nothing is owed.
* *Figures*: `total_tokens` with its population count (omitted when that count is `0`), `total_wall_seconds`, the `wait_lapses`, the realized footprint, and `finalize_spend_ratio`; the Phase 6 figures carry their `boundary: provisional` label, `measured_until`, and `excluded_steps`.
* *Step Record*: `steps[]` with, per finalize step, `step_id`, its firings, the final outcome, `head_at_completion`, `work_performed`, and the dropping or pruning gate, taken from the step records.
* *Waivers & Gaps*: every waiver of the plan with its consumptions (`HEAD`, covered items), every waiver request with its outcome, the gap record of a fallback (gate, policy, `cause`, reason or spent budget), the unplanned changes with their provenance, the deliverables removed as infeasible, and the baseline failures a `baseline_red` row accepted.
* *Review Facts*: `review_state` of the merge (`reviewed`, `vacuous`, or `unreviewed_by_waiver` with the waiver id), `self_review` (`reviewed`, `not_covered`, or `not_run`, never collapsed into a clean result), and `review_yield` per review bot and for self-review (`findings` and the count per `resolution`, every member stated, zeros included).
* *Late Findings & Quality Report*: `late_findings[]` (`finding_id`, `source`, `severity`, `carried_to`) for every blocking finding carried out after the merge, as an explicit empty list when there is none; and `quality_report`, the persisted `quality-report.json` when `plan-retrospective` ran, else `not_run`.
* *Findings*: `findings[]`, every `FindingRecord` of the plan (all statuses and dispositions), not a curated subset, so the epic never depends on the archived plan directory to read them.
* *Narrative & Amendments*: `narrative`, a Markdown string field written in the same atomic record as the server-derived facts (`PM-IMPL-2`), with its producer named (the PR body submitted in `create-pr` plus the server-rendered sections; without a PR it is `n/a` with a reason), the plan's `amendments[]`, and the answered question records.
* *Completeness*: `complete` and `missing_facts[]`, computed at emission. Each fact is a typed value, `"n/a"`, or `"unknown"`; `complete: false` is emitted only with a non-empty `missing_facts` (the facts that are `unknown`) and is surfaced as a fact on the epic representation; `unknown` and `n/a` are counted separately. Every fact carries `provenance` (`derived`, or `recovered_by_hand` with a required `verified_by`); a correction is appended as an `annotation` event referencing the original record (link:../store-schemas/04-epic-and-change-ledger.adoc#epic-inbox-record[Store Schemas Specification, Epic Inbox & Plan Mailbox Records]), never a rewrite. The epic representation reports `facts_outstanding` (landings with `unknown` facts) separately from `messages_outstanding` (inbox messages not yet processed).

Rules:

* *One Landing per Plan*: Every landing is plan-typed, and exactly one landing exists per `plan_id`; `n/a` is never legal at the pull-request and merge keys, and at the deliverable and task keys only for `local_changes` landings, whose land lane has no deliverables or tasks, and `pr` landings, which have no deliverables and tasks only from a loop-back (fact states: link:../dispatch-and-effort/04-epic-coordination.adoc#_server_derived_landing_facts_spec_re_grounding_cross_plan_locks[Dispatch & Effort Specification, Fact States]). When nothing merged, the step emits a non-landing record naming the outcome (`enqueued_not_landed`, `declined`, `no_pr`, `dequeued`, `local_only`, `handed_back`, or `awaiting_human_merge`), never a landing with `n/a` values.
* *Delivery Verification*: After appending, `emit-landing` reads the record back from the epic inbox, validates it against the landing schema (the closed JSON Schema of the fields above, `$id` `https://cuioss.de/plan-marshall-mcp/schemas/landing-envelope.json`, referenced by the `landings.jsonl` record of link:../store-schemas/04-epic-and-change-ledger.adoc#landing-record[Store Schemas Specification, Landing Record]), and records `landing_delivery` (`verified`, `incomplete`, or `failed`) in its step record and in `facts`.

[[post-run-quality-report]]
== Post-Run Quality Report (`plan-retrospective`)
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-1[PM-WATCH-GEN-1], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-38[PM-WATCH-PHASE-38], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-47[PM-WATCH-PHASE-47], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-48[PM-WATCH-PHASE-48], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-49[PM-WATCH-PHASE-49], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-50[PM-WATCH-PHASE-50], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-51[PM-WATCH-PHASE-51], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-52[PM-WATCH-PHASE-52], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-53[PM-WATCH-PHASE-53]_

`plan-marshall:plan-retrospective` (`995`) runs the server's report engine over the plan's persisted stores (findings, review participation, step records, plan instance versions and composition events, assessments, references, change ledger, waivers, question records) and the metrics snapshot labelled `measured_until` (<<_spend_measurement_window>>), and writes `quality-report.json` (link:../store-schemas/05-metrics-and-quality-report.adoc#quality-report[Store Schemas Specification, Quality Report Record]). The engine is deterministic and in-process: it dispatches no sub-agent, reads no model-authored text as evidence, and every figure it publishes is derived from records. It is observability only: every instrument declares `gates_merge: false`, the step never refuses, and no step reads the report as a precondition. The report is computed before the landing, and `emit-landing` carries it (<<post-run-metrics-and-landing>>).

=== Instrument Contract

* *Populations*: Every published count is `{value, population}`; a rate is published with its numerator and denominator populations, so `2/2` and `40/40` stay distinguishable. A population of `0` renders `unmeasurable`, never a rate; `withheld` (with `withheld_reason`), `unmeasured`, and `0` are distinct values. Populations are rendered as explicit lists, empty lists included.
* *Declared Preconditions*: Every instrument declares what it proves (`proves`), whether any precondition it evaluates can be falsified by the condition it audits (`falsifiable_preconditions`), and whether its own output is inside the population it measures (`self_included`). `self_included: false` requires a reason. The instrument census iterates over all instruments and the report's own meta blocks, so it counts itself.
* *Why Zero*: Every zero carries `zero_reason` (`structural`, `starved`, `gated`, `no_count`, `disciplinary`, `no_block`, or `fired`). A plan or store the engine cannot read contributes `floor` (a lower bound, never healthy). A figure scanned across several stores (for example contradiction incidence across the findings stores of a corpus) carries `records_scanned` and `stores_reached` of `stores_expected`; a zero over fewer stores than expected renders `none reachable`, never `0`, so an honest zero exists only when every expected store was reached.
* *Clean Is Rendered*: A section with zero findings renders its populations and its zeros; no section is dropped because it is empty. An instrument whose status is `unmeasured` still renders every finding it holds.
* *Domain Aspects*: Domain bundles extend the report with retrospective aspects (link:../domain-extensions/05-recipes-and-extension-points.adoc#retrospective-aspects[Domain Extensions Specification § Retrospective Aspect Extension Point]); each is an instrument under this contract with `gates_merge: false`, run only for plans of its domain.

=== Quality Chain

* *Derived Step Set*: The finding-filing steps are derived from the registered `FinalizeStepDescriptor` roster (`filesFindings`, validator rule 8), never from a list. Per step the report records `presence`: `not_admitted`, `admitted_not_fired`, `fired`, or `fired_but_refused`, with admission taken from the plan instance version in force when the step would have fired (`not_admitted` = pruned, with its prune reason). A firing is counted per step from its step record, never per audit line. Steps ordered after `plan-retrospective` are `after_window`, never `not_admitted`. A plan whose records lack a plan instance is `indeterminate` on presence and forms its own, separately sized population.
* *Examination*: A fired step reports its `assurance_verdict` (`checked`, `degraded`, `not_reached`, `never_performed`, `attempted_over_empty_scope`); `degraded` (curable by a re-run) and the step's declared `cannotReach` class (a structural limit) are reported separately.
* *Coverage and Yield*: `coverage` is fired over admitted steps, with every not-admitted step named. `yield` is computed over the fired set only and split by `resolution`, `source`, and `severity` with every enum member tallied. Yield scores `fixed` and `rejected`; `accepted`, `taken_into_account`, and `suppressed` count as recorded decisions, never as points; `pending` never scores. Committed findings are `{fixed, accepted, taken_into_account}`, released findings `{rejected, suppressed}`. Coverage and yield are rendered side by side, never as one product.
* *Escape Distance*: The stage that caught each finding is a separate figure, ordered by cost: build < self-review < automatic review < human. It is never folded into yield.

=== Review Retrospective

The checks of `plan-marshall`'s project step `finalize-step-review-retrospective` are one section of the report, read from `review-participation.jsonl` and the findings store. All its verdicts are observability only (`gates_merge: false`, `proves: reviewer_quality_only`) and are recorded as INFO decisions; none enters the pre-merge barrier.

* *Rows*: The rows are the enabled roster (`required_bots ∪ optional_bots`); the required set is a column, never a filter, and a silent reviewer still gets a row. Metrics and participation follow every PR of the plan in `prs[]`, including superseded and split PRs.
* *Review Deficit*: `review_deficit` is one of `clean`, `required_absent`, `unassessable`, `vacuous`, or `unestablished`, with precedence `unassessable` > `vacuous`/`unestablished` > `required_absent` > `clean`. No roster baseline yields `unassessable`; a configured empty roster yields `vacuous` and an omitted roster `unestablished`; `required_absent` needs a non-empty baseline, a non-empty roster, and no required reviewer that reviewed. `clean` requires at least one required reviewer that reviewed and is graded on the actionable count. Participation per reviewer is `measured`, `reviewed_silent`, or `unmeasurable`, persisted with its populations.
* *Coverage Denominator*: Reviewer coverage is anchored to the configured roster baseline. An omitted, empty, or non-superset baseline withholds the figure with its cause; a roster that is a proper subset of the baseline is reported as `roster_narrowed`.
* *Gate Escapes*: A gate escape is a finding raised by a later stage for a defect an earlier gate could see. `rejected` and `suppressed` findings are not escapes (their count is published), and the escape numerator counts only roster reviewers. When the gates ran on different commits the verdict is `gate_tree_unsubstantiated`; when every gate commit precedes the last loop-back it is `gates_did_not_cover_reviewed_tree`.
* *False Positives per Reviewer*: The per-reviewer false-positive figure is the reviewer's `rejected` count over its findings; contradicting records are disclosed, never resolved into a confident zero.
* *Reviewed Tree*: The report asserts that the newest `reviewed_commit_sha` equals the merged head; otherwise it records `reviewed_tree_stale` with both commits.
* *Bypass Audit*: For a merged PR, every required bot must have a participation record covering the merge candidate; otherwise the merge is classified `bypass` as `barrier_skipped`, `refusal_misread`, or `merged_outside_finalize`, unless a consumed `review_evidence` waiver covers the bot, which is reported as `unreviewed_by_waiver` with the waiver id.

=== Footprint & Assessments

The report publishes the three-way footprint reconciliation of the persisted capture (link:../store-schemas/13-leases-integrity-testing.adoc#three-way-footprint[Store Schemas Specification, Three-Way File Footprint Reconciliation]) and compares it with the component assessments. The comparison is `measured` only with a resolved footprint and more than zero assessments read, `no_assessments` when the assessment store is empty, and `inconclusive` otherwise; include and exclude verdicts are withheld unless it is `measured`, and `touched_but_unassessed` paths are always reported.

=== Spend & Measurement Window

The report reads spend only from the metrics snapshot the metrics reader composes at the report's own call (validator rule 5). The snapshot is the composition of `record-metrics` (<<post-run-metrics-and-landing>>) over the records present at that instant, labelled `measured_until` with that instant; the report never reads `metrics.json`, which `record-metrics` (`998`) writes later.

* *Window Named*: The spend section renders `measured_until` and names the steps outside the window (the report's own step and every step of the plan instance ordered after it), so the report's own spend and the terminal steps are visibly absent, never silently zero. Phase 6 figures carry `boundary: provisional`.
* *Figures*: Priced units and tokens per phase with their population stamps and floor labels, spend per spend class cross-tabulated with the termination `status`, spend per finding-filing step and per firing cause (from the step records' `firings[]`), and the finalize spend ratio against the plan's budget anchor (link:../dispatch-and-effort/02-dispatch-observability-and-spend.adoc#spend-accounting-budget-anchors[Dispatch & Effort Specification, Spend Accounting & Budget Anchors]). Every figure is a `count` with its population; an unmeasured channel renders `unmeasured`, and a derived ratio over an empty population renders `not_derivable`.
* *Yield per Spend*: Where the quality chain and the spend share a step, the report places the step's yield beside its spend; it never divides yield by spend into one score.

=== Corpus Mode

`pm-mcp operator quality-report --corpus` computes the report over the archived and active plans of the project. It returns `quality-report.json` of the same schema (`mode: corpus`), folded from the per-plan results of the same engine; a corpus of one plan equals that plan's report. Plans are grouped into populations (with and without a plan instance), and every population is sized. *Deliberate change vs. `plan-marshall`*: the archived-plan auditor (`audit-archived-plan-retrospectives`) is a second implementation; `PM-MCP` has one engine for both modes.

== Finalize Commit Instrumentation, Freshness Reconcile & Post-PR Re-Push (`PM-WF-16`)

Whenever any Phase 6 step declaring `mutatesSource == true` (`order < 70`) completes, the finalize engine routes through `finalize.settle-commit`, which invokes `call git.commit_and_push (message_mode=step_or_fallback, push_mode=post_pr_conditional)` (see link:../workflow-dsl.adoc[Workflow DSL Specification]):

1. *Conditional Auto-Commit & Ledger Recording*: If `git status --porcelain` in the worktree is clean, `git.commit_and_push` returns `done` with `clean: true` immediately and the finalize pipeline advances to the next step; a `stepped_out` return enters `finalize.hand-back`. If uncommitted modifications exist, `git.commit_and_push` runs `.gitignore`-aware artifact cleanup, resolves the step's commit message (or deterministic fallback `chore(finalize): apply <step_id> changes`) with the `Co-Authored-By` trailer, pipes the message via `stdin` to `git -C <worktree> commit -F -`, and appends a `kind = "change"` entry (`commit_sha`, `changed_paths`, `worktree_sha`) to `change-ledger.jsonl`.
2. *`head_at_completion` Re-Stamping*: If the completed `mutatesSource == true` step also declares `headDependent == true` (such as `simplify`, `security-audit`, `pre-push-quality-gate`, `automatic-review`, `analysis-roundtrip`; the in-branch fixes of the remediation units re-stamp the step whose class they fixed), `git.commit_and_push` atomically updates that step's persisted `head_at_completion` in `mcp/status.json` to the newly created `commit_sha` without emitting a duplicate step completion event. This prevents the step's own commit from self-invalidating its verdict on a subsequent re-entry check.
3. *`freshness_reconcile` for Commits after the Latest Successful Build*: If any `mutatesSource == true` step produces a commit after the latest successful build (not only steps at `order >= 10`, `PRE_PUSH_QUALITY_GATE_ORDER`; for example `architecture-refresh` at `9` committing on re-entry), `git.commit_and_push` records a `freshness_reconcile` entry in `mcp/status.json` containing `(commit_sha, step_id, prior_build_worktree_sha)` where `prior_build_worktree_sha` is read from the latest `status == "succeeded"` build entry in `change-ledger.jsonl`. When the `git.pre-commit-verify-freshness` gate runs before pushing, it consults `freshness_reconcile` so a known non-build-affecting finalize commit (such as an ADR addition in `adr-propose`) is recognized as reconciled, whereas any modification to buildable source paths invalidates `pre-push-quality-gate` and re-runs the Settle quality gate first. A commit whose changed paths are all build-neutral per the build map (for example generated architecture metadata) is reconciled without a rebuild.
4. *Post-PR Conditional Re-Push (`order > 20`)*: The transition entering `finalize.settle-commit` persists `settle_trigger {step_id, order}`; a caller that is not a step (`execute.exit-barrier`, `land.exit-barrier`, `finalize.adopt-pr`) writes order `0`, so a commit after a loop-back is never pushed before the Settle band re-runs. When the trigger's `order > 20` (after `default:create-pr`, such as `default:adr-propose` at `62`) and the project has a push remote (derived fact `push_remote`), `push_mode=post_pr_conditional` evaluates `push_required`, verifies freshness and `branch-sync-state` parity, pushes the new commit to `origin/<branch>`, and returns `done` with `pushed: true`, routed by the guard `result.pushed` to `finalize.review-cap-check`, whose `within_caps` outcome enters `finalize.concurrent-wait` so CI and review bots re-evaluate the updated PR `HEAD`. The in-branch fixes of the remediation units commit inside the unit with `push_mode=always` and await their own class at the new `HEAD` (link:../workflow-dsl/03-reference-excerpt.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Workflow DSL Specification, `finalize.pmwf` Excerpt]).

[[realized-footprint-capture]]
== Realized Footprint Capture & Footprint-Scoped Steps
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-64[PM-WATCH-PHASE-64], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-36[PM-WATCH-STORE-36]_

Finalize steps obtain the realized footprint (link:../store-schemas.adoc[Store Schemas Specification], Three-Way File Footprint Reconciliation) through one resolver:

* *Reconcile Before Footprint-Scoped Steps*: At Phase 6 entry and after every `finalize.settle-commit`, the engine re-captures `realized_files` and runs the three-way reconciliation before any step whose scope is the footprint (`simplify`, `security-audit`, `pre-submission-self-review`, `pre-push-quality-gate`) runs.
* *One Resolver for Diff-Fed Steps*: Every diff-fed step reads the footprint through this resolver, which resolves only from the plan's own worktree. Without a resolvable footprint the step records `indeterminate` with the cause named (`pending` when the worktree is not yet materialised, `disabled` when the plan runs without a worktree), never a clean `done` and never another tree's footprint.
* *Capture Before Destruction*: `branch-cleanup` persists the realized footprint in `references.json` before it removes the worktree; every post-merge consumer reads the persisted capture.
* *Only `measured` Is Evidence*: The three-way reconciliation, the scope-creep and coverage checks, the pre-merge footprint checks inside `branch-cleanup`, and every post-merge footprint consumer compare against `realized_files` only when `realized_state.state == measured`. `unresolved` and `not_captured` (link:../store-schemas/13-leases-integrity-testing.adoc#three-way-footprint[Store Schemas Specification]) make each of them record `indeterminate` with the state and cause named, never a clean or empty result.

[#dependency-delta]
== Dependency Delta Check (Pre-Merge)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-60[PM-WATCH-PHASE-60]_

The server verifies that every third-party dependency the plan adds was approved when `outline.gate` passed (Phase 3, § 5). The check is part of the footprint reconciliation: it runs with the three-way reconciliation at Phase 6 entry and after every `finalize.settle-commit` (<<realized-footprint-capture>>), and again inside `default:branch-cleanup` after its rebase, against the re-derived `base_ref`, immediately before the Pre-Merge Review Barrier is evaluated.

1. *Changed Build Files*: From the realized footprint (only when `realized_state.state == measured`), the server selects every path claimed as a build file by the build-file dependency parser of a build domain (link:../domain-extensions/03-module-discovery.adoc#_server_owned_module_discovery_enrolled_discovery_jobs[Domain Extensions Specification, Build-File Dependency Parser]): Maven `pom.xml`, Gradle build files, `package.json`, `pyproject.toml`.
2. *Added Coordinates*: Each changed build file is parsed at `base_ref` and at `HEAD` (a file absent at `base_ref` contributes an empty base set). The added coordinates are the ecosystem-qualified coordinates declared at `HEAD` and not at `base_ref`, over every dependency scope the parser reports (including test, development, and optional dependencies). Coordinates of the project's own modules (module discovery snapshot) are not third-party and are excluded; a version change is not an addition.
3. *Blocking Finding per Undeclared Coordinate*: For every added coordinate the approved dependency set does not name, the server files one blocking finding (`source: dependency_delta`, finding type `undeclared_dependency`, `severity: major`, `file_path` the build file, `summary` naming the coordinate and the build file; link:../store-schemas.adoc[Store Schemas Specification], Findings Ledger Record). A coordinate the approved outline names is not reported (matched negative control). A repeated run files no duplicate for a coordinate that already has a finding. The model may triage the finding only with `FIX` (remove the dependency); it is accepted otherwise only by an operator waiver (`findings:dependency_delta`), because accepting it approves a dependency the outline gate never saw, and without one the plan is handed back.
4. *Never Clean without Evidence*: The check records `indeterminate`, never clean, when the realized footprint is not `measured`, when a changed build file has no build-file dependency parser, or when a parser fails on either side (the parse diagnostic and file are named). An `indeterminate` check blocks like a finding: the server files one blocking finding (`source: dependency_delta`, finding type `dependency_delta_indeterminate`, `file_path` the unparsed build file or null, `summary` naming the cause), so the Pre-Merge Review Barrier (Predicate 1) refuses the merge; the same triage restriction as for `undeclared_dependency` applies.
5. *Result*: The check publishes `dependency_delta: {state: clean | findings | indeterminate, build_files_checked, added[], undeclared[], cause}` in the finalize facts and in the merge record; `clean` requires at least one parsed changed build file or an empty set of changed build files, stated as `build_files_checked: 0`.

== Java `FinalizeStepDescriptor` Record Schema & Static Checks

Every built-in, bundle, or project-local finalize step is represented in `pm-mcp-workflow` by an immutable `FinalizeStepDescriptor` record capturing all step descriptor facts:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.finalize;

import java.util.List;
import java.util.Optional;
import java.util.Set;

public record FinalizeStepDescriptor(
    String name,
    int order,
    boolean defaultOn,
    Set<String> presets,
    String description,
    boolean mutatesSource,
    boolean headDependent,
    Optional<InputScope> inputScope,   // required iff headDependent; never defaulted (validator rule 6)
    List<String> verdictInputs,        // non-empty iff inputScope == DECLARED
    boolean advancesMainViaRebase,
    boolean postRunReview,
    List<String> reads,
    List<String> destroys,
    List<String> recordsFacts,
    Optional<Lane> lane,
    List<String> requires,
    List<ConfigurableKey> configurable,
    Optional<String> persona,
    List<String> requiresPromptFields,
    Optional<String> cannotReach,
    List<String> filesFindings  // finding sources the step may file; empty = files none
) {
    /** Lane data as declared by plan-marshall ({@code lane:} frontmatter block). Absent lane = not lane-participating, always kept. */
    public record Lane(LaneClass laneClass, Optional<String> tier, Optional<String> prunableWhen, String costSize) {}
    public enum LaneClass { CORE, DERIVED_STATE, PRUNABLE, ADVERSARIAL }
    /** Closed verdict input scope ({@code input_scope:} frontmatter), see Verdict Input Scope. */
    public enum InputScope { REMOTE_STATE, OPEN_ENDED, PLAN_FOOTPRINT, DECLARED }
    /** Operator-configurable step setting ({@code configurable:} frontmatter). */
    public record ConfigurableKey(String key, String defaultValue, String description) {}

    public static final int PUSH_ORDER = 11;
    public static final int PRE_PUSH_QUALITY_GATE_ORDER = 10;
    public static final int MERGE_GATE_ORDER = 70;
    public static final int POST_RUN_MIN_ORDER = 900;
    public static final int TERMINUS_ARCHIVE_ORDER = 1100;
}
----

*Assurance Verdict*: Every finalize step record carries `assurance_verdict` (`checked`, `degraded`, `not_reached`, `never_performed`, or `attempted_over_empty_scope`); a record without it reads `unadjudicated`, never a pass. A gate step declares in `cannotReach` the defect class it cannot detect (for example `ci-verify`: unreviewed semantics and untested paths), which is rendered with its verdict. An empty examined scope renders "NONE — this pass analysed no dimension; it certifies nothing".

=== Build-Time & Startup Static Invariant Verification (`FinalizePipelineValidator`)
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-3[PM-WATCH-DSL-3], link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-20[PM-WATCH-GEN-20], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-39[PM-WATCH-PHASE-39], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-55[PM-WATCH-PHASE-55]_

`FinalizePipelineValidator` validates the complete registered `List<FinalizeStepDescriptor>` at build time (via JUnit tests, over the default roster) and on every load of a project's finalize unit (over the project's roster: the default descriptors of the steps its `finalize.pmwf` contains plus its project step descriptors), failing closed on any violation; a violation in a project roster refuses the project's plan lifecycle with the file and line (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]):

1. *Order Uniqueness (No Collisions)*: For all distinct descriptors $A \neq B$, $A.\text{order}() \neq B.\text{order}()$. Tie-breaking by list insertion order is strictly forbidden.
2. *Pre-Push Quality Gate Placement*: `default:pre-push-quality-gate` must have $\text{order} == 10$, `default:push` must have $\text{order} == 11$, and no step may occupy an order between them.
3. *Source-Mutation Before Merge Gate (`mutatesSource`)*: Every descriptor with `mutatesSource == true` must satisfy $\text{order} < \text{branchCleanup.order}()$ (`70`). Every step with $\text{order} \ge 70$ must have `mutatesSource == false` (supported at runtime by the post-run source guard, which checks `git status --porcelain` after every post-merge step to detect stray tracked writes).
4. *Post-Run Review & Source-Mutation Mutual Exclusion (`P1 \land P2`)*: No descriptor may declare both `postRunReview == true` and `mutatesSource == true`. Every descriptor with `postRunReview == true` must satisfy $900 \le \text{order} \le 1000$ (`emit-landing` at `1000` is a post-run review step).
5. *`reads` / `destroys` Data-Dependency Ordering*: For every artifact token $X \in A.\text{reads}()$ and any step $D$ with $X \in D.\text{destroys}()$, $A.\text{order}() < D.\text{order}()$ (no read-after-destroy: e.g., all `reads: [worktree]` steps precede `branch-cleanup` at `70`; all steps precede `archive-plan` at `1100` which `destroys: [plan-directory]`). For `X == "metrics"`, every consumer declaring `reads: [metrics]` either orders after the producer ($\text{order} > \text{recordMetrics.order}()$, `998`: `print-phase-breakdown` at `999`, `emit-landing` at `1000`) or reads a labelled snapshot (`plan-retrospective` at `995`). The engine has one metrics reader, the composition function of `record-metrics`: for a consumer ordered after `998` it returns the recorded `metrics.json`, and for a consumer ordered before it a snapshot composed at the consumer's call and labelled `measured_until`, never the unwritten store. A consumer before `998` that renders a snapshot figure without its `measured_until` label violates the rule at runtime.
6. *Anchor & Fact Contract Completeness*: Every descriptor with `headDependent == true` declares `inputScope` from the closed set `remote_state`, `open_ended`, `plan_footprint`, `declared` (xref:06-finalize-re-entry-and-merge.adoc#verdict-input-scope[Verdict Input Scope]); a missing `inputScope` on a `headDependent` step is a validation error and is never defaulted, and a descriptor with `headDependent == false` declares neither `inputScope` nor `verdictInputs`. `inputScope == declared` requires non-empty `verdictInputs`; every other value requires `verdictInputs.isEmpty() == true`. And every step whose `done` outcome is reachable through a no-op/skipped branch as well as a work-performing branch must include `"work_performed"` in `recordsFacts` and emit `work_performed=true|false`.
7. *No Guard After the Irreversible Move*: No step with $\text{order} > \text{MERGE\_GATE\_ORDER}$ (`70`) may declare an outcome that refuses on its inputs; post-merge steps record degraded outcomes (`indeterminate`, `landing_delivery: pending`, carried late findings, owed items) instead. An I/O failure of a post-merge step routes to a bounded `retry` state or `finalize.step-failed`, never to a refusal that strands the merged plan. There is no exception: `archive-plan` holds no open pull request.
8. *Declared Finding Sources*: The finding-filing step set is $\{d : \neg d.\text{filesFindings}().\text{isEmpty}()\}$ over the registered roster; it is derived, never listed. At runtime the findings store refuses a write from a step whose `filesFindings` does not contain the finding's `source`.
