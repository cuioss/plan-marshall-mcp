== Overview

This document specifies the four-axis domain extension architecture (Axes A–D), provenance-preserving dependency edge and path-attribution merge algorithms, server-owned module discovery and `derive-verification` build map, architecture query resources and enrichment workflow, declarative recipe engine with Tier-1 init scoring, out-of-process `project_script` execution contract, and the normative three-way configuration split for *plan-marshall-mcp* (`PM-MCP`).

In the legacy script-and-prose architecture, domain extensions were implemented as in-process Python classes (`extension.py`) discovered via `importlib` even though roughly 80% of their surface returned constant metadata, while `marshal.json` mixed git-tracked project preferences, frozen hook snapshots, and executable command overrides. `PM-MCP` replaces dynamic code loading with a closed-world native design: declarative domain descriptors paired with sealed Java axis interfaces in `pm-mcp-core`, permanent out-of-process `project_script` jobs for project-local and custom domain code, and a strict security boundary separating the sparse git-tracked team configuration (`.marshall/config/`) from operator files, enrolment, and server-managed runtime state.

== Four-Axis Domain Architecture (Axes A–D, ADR-004 / ADR-013)
_See Requirement link:../Requirements.adoc#PM-EXT-1[PM-EXT-1: Four-Axis Domain Descriptors (Axes A–D)]_

_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-1[PM-WATCH-EXT-1]_

To comply with the GraalVM native-image closed-world constraint (`PM-TECH-3`), `PM-MCP` eliminates runtime `importlib` plugin loading. Built-in domains (`java`, `java-cui`, `javascript`, `javascript-cui`, `python`, `oci-containers`, `documentation`, `requirements`, `plan-marshall-plugin-dev`, `general-dev`) and organization data packs are represented by declarative JSON descriptors (`classpath:/domains/<domain_id>.json`) bound to four orthogonal, sealed Java interfaces corresponding to Axes A through D (ADR-004, ADR-013). Axis B is the exception: the file-to-build contract is owned by build-system extensions, not by language or content domains (ADR-004), so it is declared by build-system descriptors (`classpath:/build-systems/<build_system_id>.json` for `maven`, `gradle`, `npm`, and `pyproject`), each naming the domain key its routes are filed under in `build.map`.

The axis split mirrors `plan-marshall` (`script-shared/scripts/extension/extension_base.py`: `ExtensionBase` owns Axis A — `get_skill_domains`, `applies_to_module`, `config_defaults`, and the `provides_*` hooks; `BuildExtensionBase` owns Axis B — `classify_globs`, `classify_paths`, `classify_path_specificity`, `classify_build_class`; `DerivationResolverBase` and `PathAttributionBase` own Axes C and D; ADR-004, ADR-013), verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing.

=== Core Architectural Invariants
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-23[PM-WATCH-EXT-23]_

1. *Fail-Closed Descriptor Loading (ADR-017)*: A validator derives its contract from the target's own declaration and fails closed when it cannot. Unlike the legacy catch-all that silently ignored broken `extension.py` modules, `PM-MCP` validates every compiled and project-local descriptor against its closed JSON Schema at startup. Any schema violation or unresolvable skill/resolver reference causes an immediate, explicit diagnostic failure rather than silent degradation.
2. *Null-on-Absent Never Fabricates a Positive (ADR-010)*: When a domain is inactive or does not declare an optional capability (such as an architecture fitness gate or a domain verb like `marker-detect` or `rewrite-log-parse`), that capability is omitted from representations (`null` / absent). Conversely, if an active domain promises a mandatory gate that cannot execute, the engine halts with a diagnosable refusal (`refused`) and **never** records a synthetic pass.
3. *Security Profile Resolution Constraint*: The `security` profile in `skills_by_profile` resolves focused security vocabulary skills (`skill://pm/domain/<domain>/security`) for implementation, review, and audit states; it **never** generates standalone implementation tasks of its own.
4. *Technique Preconditions*: A prescriptive section of a domain vocabulary skill may declare a precondition in the descriptor's `technique_preconditions`, using the Axis A `applies_to_module` predicate grammar (build system, packaging, dependency coordinates, module path glob, file existence). The server evaluates it against the project's discovered modules at render time; when no module satisfies it, the renderer emits that section marked "available technique, not adopted in this project" instead of as binding guidance (link:client-profiles.adoc#_rendering_invariants[Client Profiles Specification, Rendering Invariants]), and the rendered digest (`PM-SKILL-2`) reflects the result. Every section that prescribes the same `technique` declares the same precondition, so the technique's status is identical in every skill that carries it; the descriptor loader refuses a technique with diverging preconditions.

=== Sealed Java Interfaces for Axes A–D
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-3[PM-WATCH-EXT-3], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-4[PM-WATCH-EXT-4]_

[source,java]
----
package de.cuioss.pm.mcp.core.domain;

import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.Set;

/**
 * Axis A: Skill loading, domain detection globs, profile-to-skill mapping,
 * module applicability, write-once config defaults, triage vocabulary,
 * and architecture gate declarations (ADR-004).
 */
public sealed interface SkillLoadingAxis permits DeclarativeDomainAxisA {

    String domainId();

    /** Detection globs (domain-detection glob dialect, distinct from build-map fnmatch). */
    List<String> providesFileGlobs();

    /** Maps execution profile (core, implementation, module_testing, integration_testing, quality, documentation, security; `core` is merged into every other profile) to its {defaults, optionals} skill:// URIs. */
    Map<String, ProfileSkills> skillsByProfile();

    /** Parent domain of an additive domain (java-cui -> java, javascript-cui -> javascript); empty for a standalone domain. */
    Optional<String> additiveTo();

    /** Descriptor default of the always_on inclusion leg. */
    boolean alwaysOn();

    /**
     * Evaluates the domain's declarative applicability rules (applies_to_module) against a
     * discovered module's facts: decides whether the domain applies to the module, which
     * profiles activate, and which optional skills are promoted. Also gates whether the
     * routes filed under this domain are seeded into build.map (ADR-004).
     */
    ApplicabilityMatch evaluateApplicability(DiscoveredModuleFacts moduleFacts);

    /** Optional domain-specific triage vocabulary skill (e.g. skill://pm/triage/java); falls back to skill://pm/triage/generic. */
    Optional<String> triageSkillUri();

    /** Optional supporting outline analysis facts and vocabulary URI. */
    Optional<OutlineExtensionSpec> outlineExtension();

    /** Optional architectural fitness function gate (ArchUnit, import-linter, dependency-cruiser). */
    Optional<ArchGateDeclaration> archGateDeclaration();

    /** Optional compiled-in domain verbs (marker-detect, invoked as search-markers; rewrite-log-parse, invoked as parse-rewrite-log). */
    Set<String> domainVerbs();
}

/**
 * Axis B: File-to-build classification, owned by build-system extensions
 * (maven, gradle, npm, pyproject), never by language/content domains (ADR-004).
 * Classifies changed paths into (role, build_class) build-map routes that
 * resolve to canonical build commands; it decides no module applicability.
 */
public sealed interface BuildRoutingAxis permits DeclarativeBuildSystemAxisB {

    String buildSystemId();

    /** Domain key under which this build system's routes are filed in build.map. */
    String servedDomainKey();

    /**
     * Explicit (glob, role) build-map routes (classify_globs); role is production, test,
     * or config. Globs are single-* fnmatch patterns or bare basenames, never recursive **.
     */
    List<BuildMapRoute> classifyGlobs();

    /**
     * Build class of a claimed (path, role) pair (classify_build_class): production -> compile,
     * test -> module-tests, config -> verify, any other role -> none, unless the build system
     * overrides the default for a specific path.
     */
    BuildClass classifyBuildClass(String path, BuildMapRole role);

    /**
     * Classifies changed paths into (role, build_class) routes of this build system, with the
     * non-wildcard segment count of the matching glob as longest-glob-wins specificity
     * (classify_paths, classify_path_specificity). Paths matching no route are omitted.
     */
    List<ClassifiedPathRoute> classifyPaths(List<String> changedPaths);

    /** Maps canonical verbs (clean..package, module-tests, quality-gate, verify) to argument templates. */
    Map<CanonicalBuildVerb, ArgumentTemplate> canonicalCommandTemplates();

    /** Maps discovery operations to enrolled argument templates. */
    Map<String, ArgumentTemplate> discoveryCommandTemplates();
}

/**
 * Axis C: Directed module dependency edge derivation with explicit resolver identity (ADR-013, ADR-014).
 */
public sealed interface EdgeDerivationAxis
        permits MavenEdgeResolver, GradleEdgeResolver, NpmEdgeResolver,
                PyprojectEdgeResolver, PythonImportEdgeResolver,
                MarkdownCrossRefResolver, DocumentationCrossRefResolver,
                LspSymbolEdgeResolver, ProjectScriptEdgeResolver {

    /** Stable, unique resolver ID ("maven", "gradle", "npm", "pyproject", "python", "markdown", "documentation", "lsp"). */
    String resolverId();

    /**
     * Derives directed inter-module dependency edges; never activated by file pattern, only by explicit resolverId.
     *
     * @throws ResolverException when the derivation fails; DerivationMerge.invoke reports it as
     *         status ERROR and continues with the sibling resolvers
     */
    ResolverExecutionResult deriveEdges(WorkspaceDiscoveryContext context) throws ResolverException;
}

/**
 * Axis D: Repository subtree path-prefix ownership claims (ADR-013, ADR-014).
 */
public sealed interface PathOwnershipAxis permits DeclarativeDomainAxisD {

    /** Stable attributor ID stamped onto every claim's producers and onto its AttributorReport. */
    String attributorId();

    /**
     * Returns constant (pathPrefix, targetModuleId) ownership claims plus the attributor's own
     * notes on claims it suppressed; stateless, no filesystem access.
     *
     * @throws AttributorException when the attributor cannot produce its claims; the merge
     *         reports it and continues with the sibling attributors
     */
    PathClaimSet claimPaths() throws AttributorException;
}
----

The Axis C resolver IDs mirror `plan-marshall` (`derivation_resolver_id()` of `build-maven`, `build-npm`, `build-pyproject`, `pm-dev-python`, `pm-plugin-development`, `pm-documents`, and `plan-marshall-plugin`), verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing. `pyproject` (declared-dependency join) and `python` (import join) stay distinct IDs so an edge's provenance tells the two derivations apart; `markdown` and `documentation` read overlapping file types over different module corpora, and an edge both find carries both IDs. *Deliberate addition vs. `plan-marshall`*: the `gradle` resolver (`GradleEdgeResolver`) has no `plan-marshall` counterpart (`build-gradle` ships no derivation resolver).

*Machine-local resolver enablement*: Which discovered resolvers run is a machine-local binding, because a resolver's availability and cost depend on locally installed tooling (the `lsp` resolver needs an enrolled language server). The binding `derivation_resolvers.<resolver_id>.enabled` lives in the project's operator file `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (Tier 2, written via `pm-mcp operator config --project <project_id>`, machine-wide default in `machine-config.json` `project_defaults`; link:store-schemas.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), keyed by `project_id`, never by a project root path, and mirroring `plan-marshall`'s `derivation_resolvers` section of its `.plan/local/run-configuration.json`. An absent section or absent entry means *enabled*; only an explicit `false` disables a resolver (a malformed entry fails the closed schema of `local-config.json` and is reported, never read as a setting). A disabled resolver is still discovered and reported (status `NOT_DISPATCHED`, reason `DISABLED`, zero edges), never pruned from the report, and is not counted as having run.

*Profile and applicability semantics*:

* *`core` merge*: `core` is not an activatable profile. When the server resolves a profile's skills, it prepends the domain's `core.defaults` to that profile's `defaults` and its `core.optionals` to that profile's `optionals` (duplicates removed, first occurrence kept), mirroring `plan-marshall`'s `core` profile (for example `pm-dev-java-cui` declares `cui-logging` under `core`). A profile that the domain neither lists nor declares minimal still receives `core`.
* *`when` predicates*: all predicates present in one rule must hold (AND within a rule); a module matches the domain when any rule matches (OR across rules); an empty `when` (`{}`) matches every module. `packaging_equals` and `packaging_not_equals` compare the module's discovered packaging exactly (a module without a packaging fact satisfies only `packaging_not_equals`), `dependency_contains` is a substring test over the module's declared dependency coordinates, and `file_exists` tests a module-relative path. Disjunction inside one predicate is expressed by a second rule, never by a list value.
* *`activate_profiles`*: a closed enum of the activatable profiles; a matching rule activates exactly the listed profiles for that module, and `promote_optional_skills_to_default` moves the named skills of those profiles from `optionals` to `defaults` for that module.
* *`additive_to`*: an additive domain (`java-cui` extends `java`, `javascript-cui` extends `javascript`) applies to a module only where its parent domain applies, and its resolved skills are appended after the parent's for the same profile; a descriptor whose `additive_to` names an unknown domain or forms a cycle fails descriptor loading.
* *`always_on`*: the descriptor declares the default of the `always_on` inclusion leg (`domain-detect`, phase-workflows.adoc § Widen-Only Domain Re-Merge). The project's override of `always_on` and of `file_globs` (plan-marshall's `skill_domains.<domain>.always_on` / `file_globs` in `marshal.json`) belongs to the team file `.marshall/config/domains.json`, not to the descriptor (link:store-schemas.adoc#config-domains-json[Store Schemas Specification, `domains.json`]). *Deliberate change vs. `plan-marshall`*: a descriptor carries no `config_defaults` map; nothing is seeded into a configuration file when a domain is activated, and a domain's defaults are compiled defaults of the effective configuration.

== Provenance-Preserving Merge Algorithms (ADR-014)
_See Requirement link:../Requirements.adoc#PM-EXT-2[PM-EXT-2: Provenance-Preserving Edge Derivation & Path Attribution Merges]_

When multiple domains and resolvers are active in a repository, `PM-MCP` merges their module dependency edges (Axis C) and path-prefix ownership claims (Axis D) using deterministic, order-independent algorithms ported from `_derivation_merge.py` and `_path_attribution_merge.py` (ADR-014; `extension-api/scripts/`, verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing). Neither merge ever throws or aborts on a producer's output: a producer that fails is reported and its siblings still contribute, and every candidate the merge drops is recorded as a note prefixed `merge: ` on the producer's own report, so a dropped candidate is never silent and is always distinguishable from the producer's own notes.

=== Edge Derivation Merge (`DerivationMerge`)
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-5[PM-WATCH-EXT-5]_

The edge derivation merge combines directed inter-module edges $(u \to v)$ from all explicitly activated Axis-C resolvers while preserving full producer provenance and distinguishing "zero edges found" from "resolver did not run":

1. *Activation by Explicit Resolver ID*: Resolvers are invoked strictly by their `resolverId` (never implicitly by file extension). A resolver disabled by the machine-local `derivation_resolvers` binding is not invoked; the caller folds in a `ResolverExecutionResult` with status `NOT_DISPATCHED` and reason `DISABLED`, which is reported with zero edges and excluded from the count of resolvers that ran.
2. *Idempotent Union with Provenance*: Multiple resolvers discovering the same directed edge $(u, v)$ are merged into a single `MergedDependencyEdge` record whose `resolverIds` set is the sorted union of all contributing resolver IDs. A resolver's `contributedEdgeCount` counts its distinct accepted pairs.
3. *Reported Drops*: Malformed candidates (a missing edge or endpoint), self-edges $(u, u)$, and edges naming a module outside the discovered module set are dropped, each with a `merge: ` note on the producing resolver's report.
4. *Explicit Non-Run Reporting for LSP & External Resolvers*: An `LspSymbolEdgeResolver` (or `ProjectScriptEdgeResolver`) that could not execute **never returns an empty edge list masquerading as a clean scan**. Instead, it returns a `ResolverExecutionResult` with status `NOT_RUN` and an explicit `NonRunReason` (`ABSENT`, `FAILED_TO_START`, `TIMEOUT`, `UNSUPPORTED`).
5. *Failing Resolver Isolation*: A resolver whose `deriveEdges` throws `ResolverException` is folded in by `DerivationMerge.invoke` as status `ERROR` with zero edges and a `merge: ` note carrying the sanitized exception (simple class name and message, line breaks collapsed to spaces, truncated to 200 characters; never a stack trace). It contributes no edges, counts as dispatched, and never aborts the merge; its siblings still contribute.
6. *Duplicate Resolver IDs*: When two results carry the same `resolverId`, the first registration wins; the second is dropped entirely (no edges, no report of its own) and the surviving report receives a `merge: ` note naming the dropped duplicate.
7. *Ordered Output*: Every map in the result is an ordered, unmodifiable view (`TreeMap` by key), never `Map.copyOf`, whose iteration order is unspecified; merged edges are sorted by `(from, to)` and reports by `resolverId`, so two runs over the same input serialize byte-identically.

package de.cuioss.pm.mcp.core.architecture;

import de.cuioss.pm.mcp.core.domain.EdgeDerivationAxis;
import de.cuioss.pm.mcp.core.domain.ResolverException;
import de.cuioss.pm.mcp.core.domain.WorkspaceDiscoveryContext;

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.TreeMap;
import java.util.TreeSet;

public final class DerivationMerge {

    private static final String MERGE_NOTE = "merge: ";

    private static final int MAX_ERROR_TEXT = 200;

    public enum ResolverStatus { RAN, NOT_RUN, NOT_DISPATCHED, ERROR }

    public enum NonRunReason { NONE, ABSENT, FAILED_TO_START, TIMEOUT, UNSUPPORTED, DISABLED }

    public record RawEdge(String fromModule, String toModule, String detail) {}

    public record ResolverExecutionResult(
            String resolverId,
            ResolverStatus status,
            NonRunReason nonRunReason,
            String diagnosticMessage,
            List<RawEdge> edges,
            List<String> notes          // the resolver's own suppression notes
    ) {}

    public record MergedDependencyEdge(
            String fromModule,
            String toModule,
            List<String> resolverIds,
            Map<String, List<String>> detailsByResolver
    ) {}

    public record ResolverStatusReport(
            String resolverId,
            ResolverStatus status,
            NonRunReason nonRunReason,
            String diagnosticMessage,
            int contributedEdgeCount,   // distinct accepted (from, to) pairs
            List<String> notes          // resolver notes followed by "merge: " drop notes
    ) {}

    public record DerivationMergeResult(
            List<MergedDependencyEdge> edges,
            List<ResolverStatusReport> resolverReports,
            int dispatchedResolverCount // excludes NOT_DISPATCHED reports
    ) {}

    /** Invokes one resolver; a thrown ResolverException becomes an ERROR result, never an abort. */
    public static ResolverExecutionResult invoke(EdgeDerivationAxis resolver, WorkspaceDiscoveryContext context) {
        try {
            return resolver.deriveEdges(context);
        } catch (ResolverException e) {
            return new ResolverExecutionResult(resolver.resolverId(), ResolverStatus.ERROR, NonRunReason.NONE,
                    null, List.of(), List.of(MERGE_NOTE + "deriveEdges() failed: " + sanitize(e)));
        }
    }

    /** Simple class name and message, single line, bounded; never a stack trace. */
    static String sanitize(ResolverException e) {
        String message = e.getMessage() == null ? "" : e.getMessage().replaceAll("[\\r\\n\\t]+", " ").strip();
        String text = e.getClass().getSimpleName() + (message.isEmpty() ? "" : ": " + message);
        return text.length() <= MAX_ERROR_TEXT ? text : text.substring(0, MAX_ERROR_TEXT) + "...";
    }

    public DerivationMergeResult merge(
            Set<String> knownModules,
            List<ResolverExecutionResult> results) {

        record EdgeKey(String from, String to) implements Comparable<EdgeKey> {
            @Override
            public int compareTo(EdgeKey o) {
                int c = this.from.compareTo(o.from);
                return c != 0 ? c : this.to.compareTo(o.to);
            }
        }

        Map<EdgeKey, TreeSet<String>> provenance = new TreeMap<>();
        Map<EdgeKey, Map<String, TreeSet<String>>> details = new TreeMap<>();
        Map<String, ResolverStatusReport> reports = new TreeMap<>();

        Map<String, List<String>> duplicateNotes = new TreeMap<>();

        for (ResolverExecutionResult res : results) {
            if (reports.containsKey(res.resolverId())) {
                // First registration wins; the duplicate is dropped and named on the surviving report
                duplicateNotes.computeIfAbsent(res.resolverId(), k -> new ArrayList<>())
                        .add(MERGE_NOTE + "dropped duplicate registration of resolver id '" + res.resolverId()
                                + "' (status " + res.status() + ") - the first registration wins");
                continue;
            }
            List<String> notes = new ArrayList<>(res.notes());
            if (res.status() != ResolverStatus.RAN) {
                // NOT_RUN, NOT_DISPATCHED and ERROR contribute no edges
                reports.put(res.resolverId(), new ResolverStatusReport(
                        res.resolverId(), res.status(), res.nonRunReason(),
                        res.diagnosticMessage(), 0, List.copyOf(notes)));
                continue;
            }
            Set<EdgeKey> contributed = new TreeSet<>();
            for (RawEdge edge : res.edges()) {
                if (edge == null || edge.fromModule() == null || edge.toModule() == null) {
                    notes.add(MERGE_NOTE + "dropped malformed candidate " + edge
                            + " - not a (from, to) pair of module names");
                    continue;
                }
                if (edge.fromModule().equals(edge.toModule())) {
                    notes.add(MERGE_NOTE + "dropped self-edge (" + edge.fromModule() + " -> "
                            + edge.toModule() + ") - a module does not depend on itself");
                    continue;
                }
                List<String> unknown = new ArrayList<>();
                if (!knownModules.contains(edge.fromModule())) {
                    unknown.add(edge.fromModule());
                }
                if (!knownModules.contains(edge.toModule())) {
                    unknown.add(edge.toModule());
                }
                if (!unknown.isEmpty()) {
                    notes.add(MERGE_NOTE + "dropped edge (" + edge.fromModule() + " -> " + edge.toModule()
                            + ") - unknown module endpoint(s): " + String.join(", ", unknown));
                    continue;
                }
                EdgeKey key = new EdgeKey(edge.fromModule(), edge.toModule());
                contributed.add(key);
                provenance.computeIfAbsent(key, k -> new TreeSet<>()).add(res.resolverId());
                if (edge.detail() != null && !edge.detail().isBlank()) {
                    details.computeIfAbsent(key, k -> new TreeMap<>())
                            .computeIfAbsent(res.resolverId(), r -> new TreeSet<>())
                            .add(edge.detail());
                }
            }
            reports.put(res.resolverId(), new ResolverStatusReport(
                    res.resolverId(), ResolverStatus.RAN, NonRunReason.NONE,
                    res.diagnosticMessage(), contributed.size(), List.copyOf(notes)));
        }

        duplicateNotes.forEach((id, extra) -> reports.computeIfPresent(id, (k, r) -> {
            List<String> notes = new ArrayList<>(r.notes());
            notes.addAll(extra);
            return new ResolverStatusReport(r.resolverId(), r.status(), r.nonRunReason(),
                    r.diagnosticMessage(), r.contributedEdgeCount(), List.copyOf(notes));
        }));

        List<MergedDependencyEdge> mergedEdges = provenance.entrySet().stream()
                .map(entry -> {
                    EdgeKey k = entry.getKey();
                    TreeMap<String, List<String>> detMap = new TreeMap<>();
                    details.getOrDefault(k, Map.of())
                            .forEach((r, s) -> detMap.put(r, List.copyOf(s)));
                    // ordered view, never Map.copyOf (unspecified iteration order)
                    return new MergedDependencyEdge(k.from(), k.to(), List.copyOf(entry.getValue()),
                            Collections.unmodifiableSortedMap(detMap));
                })
                .toList();

        int dispatched = (int) reports.values().stream()
                .filter(r -> r.status() != ResolverStatus.NOT_DISPATCHED)
                .count();

        return new DerivationMergeResult(mergedEdges, List.copyOf(reports.values()), dispatched);
    }
}

=== Path Attribution Merge & Collision Rejection (`PathAttributionMerge`)

The path attribution merge combines Axis-D `claim_paths` claims across active attributors and resolves repository-relative file paths to their owning module via longest-prefix matching:

1. *Single Shared Spelling Normalizer (`normalizeSpelling`)*: Claim registration and file lookup pass through the exact same normalizer. Normalization is spelling-only: it trims surrounding whitespace, folds backslashes to `/`, strips leading `./` runs, and strips trailing slashes. It resolves no symlink, touches no filesystem, does not collapse `..` segments, does not strip a leading `/`, and does not collapse `//`; whether a path is admissible is a policy decision of each side, not a spelling decision.
2. *Claim Validity Filters (Drop and Report, Never Throw)*: A claim survives only if it is well-formed (non-null prefix and module), its normalized prefix bounds a subtree inside the repository, and its `target_module` is a known module (a discovered module or a registered synthetic domain module such as the one owning `.marshall`). A blank or root-level prefix (`""`, `.`, `..`, or a bare `/`), an absolute prefix (a leading `/` or a drive letter such as `C:/`), and a repository-escaping prefix (any normalized segment equal to `..`, not only the first) are dropped; a merely dot-relative prefix (`./doc`) is normalized to `doc`, not dropped. Every dropped claim appends a `merge: ` note naming the claim and the reason to the claiming attributor's report. *Deliberate hardening vs. `plan-marshall`*: `plan-marshall`'s `_normalize_prefix` drops only a leading `..` segment and admits `/etc` or `doc/../../x`; `PM-MCP` drops both, because such a prefix can never bound a subtree inside the repository.
3. *Failing Attributor Isolation*: An attributor whose `claimPaths()` throws `AttributorException` is reported with status `ERROR`, `claimCount` `0`, and a `merge: ` note carrying the sanitized failure (simple class name and message, as in `DerivationMerge.sanitize`); it contributes no claims, and its siblings still contribute. A failing attributor never aborts the merge. *Duplicate attributor IDs*: when two attributors share an `attributorId`, the first registration wins; the second is not invoked, and the surviving report receives a `merge: ` note naming the dropped duplicate. All internal maps are ordered (`TreeMap` / `LinkedHashMap` in registration order), never `HashMap` or `Map.copyOf`.
4. *Collision Without Winner Invariant*: If two attributors claim the same normalized `path_prefix` for **different** `target_module` IDs, the merge **never selects an iteration-order winner**. Instead, the collided `path_prefix` yields no claim, is recorded as a `PathClaimCollision` diagnostic, and every contending attributor receives a `merge: ` note naming all contending modules. Identical claims `(same prefix, same target_module)` merge idempotently into one claim carrying the sorted union of producer IDs. Differently-scoped prefixes (`.marshall` and `.marshall/local`) are not a collision.
5. *Per-Attributor Report*: Every attributor yields exactly one `AttributorReport(attributorId, status, claimCount, notes)`, where `claimCount` counts the surviving (non-collided) claims it produced. Zero attributors is a first-class outcome (empty claims, empty reports, never an exception); the report count distinguishes "no attributor ran" from "attributors ran and none claimed the path".
6. *Segment-Boundary Longest-Prefix Lookup*: A spelling-normalized file path `p` matches a claimed prefix `c` if and only if `p.equals(c)` or `p.startsWith(c + "/")`, so `.marshalls/x` never resolves through a `.marshall` claim. Among all matching claims, the longest prefix wins; this is resolution order, not a collision tie-break.

package de.cuioss.pm.mcp.core.architecture;

import de.cuioss.pm.mcp.core.domain.AttributorException;
import de.cuioss.pm.mcp.core.domain.PathClaimSet;
import de.cuioss.pm.mcp.core.domain.PathOwnershipAxis;
import de.cuioss.pm.mcp.core.domain.PathOwnershipClaim;

import java.util.ArrayList;
import java.util.Collections;
import java.util.Comparator;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.Set;
import java.util.TreeMap;
import java.util.TreeSet;

public final class PathAttributionMerge {

    private static final String MERGE_NOTE = "merge: ";

    private static final Set<String> ROOT_LEVEL_PREFIXES = Set.of("", ".", "..");

    public enum AttributorStatus { OK, ERROR }

    public record ActivePathClaim(String normalizedPrefix, String targetModule, List<String> producers) {}

    public record PathClaimCollision(String normalizedPrefix, Map<String, List<String>> producersByTargetModule) {}

    public record AttributorReport(String attributorId, AttributorStatus status, int claimCount, List<String> notes) {}

    public record AttributionTable(
            List<ActivePathClaim> claimsByDescendingLength,
            List<PathClaimCollision> collisions,
            List<AttributorReport> attributorReports
    ) {
        public Optional<ActivePathClaim> attributePath(String rawFilePath) {
            String norm = normalizeSpelling(rawFilePath);
            for (ActivePathClaim claim : claimsByDescendingLength) {
                String prefix = claim.normalizedPrefix();
                if (norm.equals(prefix) || norm.startsWith(prefix + "/")) {
                    return Optional.of(claim);
                }
            }
            return Optional.empty();
        }
    }

    /** Spelling-only normalizer shared by the claim side and the lookup side. */
    public static String normalizeSpelling(String raw) {
        String p = raw.strip().replace('\\', '/');
        while (p.startsWith("./")) {
            p = p.substring(2);
        }
        int end = p.length();
        while (end > 0 && p.charAt(end - 1) == '/') {
            end--;
        }
        return p.substring(0, end);
    }

    /** Simple class name and single-line message, bounded to 200 characters; never a stack trace. */
    static String sanitize(AttributorException e) {
        String message = e.getMessage() == null ? "" : e.getMessage().replaceAll("[\\r\\n\\t]+", " ").strip();
        String text = e.getClass().getSimpleName() + (message.isEmpty() ? "" : ": " + message);
        return text.length() <= 200 ? text : text.substring(0, 200) + "...";
    }

    /**
     * Identity key of a claimed prefix; empty when the prefix bounds no subtree inside the repository:
     * root-level, absolute (leading '/' or drive letter), or repository-escaping (any '..' segment).
     * Deliberate hardening vs. plan-marshall, which rejects only a leading '..' segment.
     */
    static Optional<String> normalizePrefix(String raw) {
        String p = normalizeSpelling(raw);
        boolean absolute = p.startsWith("/") || p.matches("^[A-Za-z]:(/.*)?$");
        boolean escaping = List.of(p.split("/")).contains("..");
        if (ROOT_LEVEL_PREFIXES.contains(p) || absolute || escaping) {
            return Optional.empty();
        }
        return Optional.of(p);
    }

    public AttributionTable buildTable(Set<String> knownModules, List<PathOwnershipAxis> attributors) {
        record ClaimKey(String prefix, String module) implements Comparable<ClaimKey> {
            @Override
            public int compareTo(ClaimKey o) {
                int c = this.prefix.compareTo(o.prefix);
                return c != 0 ? c : this.module.compareTo(o.module);
            }
        }

        Map<ClaimKey, TreeSet<String>> producers = new TreeMap<>();
        Map<String, AttributorStatus> statusById = new LinkedHashMap<>();   // registration order
        Map<String, List<String>> notesById = new TreeMap<>();

        for (PathOwnershipAxis attributor : attributors) {
            String id = attributor.attributorId();
            if (statusById.containsKey(id)) {
                // First registration wins; the duplicate is not invoked and is named on the surviving report
                notesById.computeIfAbsent(id, k -> new ArrayList<>()).add(MERGE_NOTE
                        + "dropped duplicate registration of attributor id '" + id + "' - the first registration wins");
                continue;
            }
            PathClaimSet declared;
            try {
                declared = attributor.claimPaths();
            } catch (AttributorException e) {
                statusById.put(id, AttributorStatus.ERROR);
                notesById.put(id, new ArrayList<>(List.of(MERGE_NOTE + "claimPaths() failed: " + sanitize(e))));
                continue;
            }
            statusById.put(id, AttributorStatus.OK);
            List<String> notes = new ArrayList<>(declared.notes());
            for (PathOwnershipClaim claim : declared.claims()) {
                if (claim == null || claim.pathPrefix() == null || claim.targetModule() == null) {
                    notes.add(MERGE_NOTE + "dropped malformed claim " + claim
                            + " - not a (path_prefix, module_name) pair");
                    continue;
                }
                Optional<String> prefix = normalizePrefix(claim.pathPrefix());
                if (prefix.isEmpty()) {
                    notes.add(MERGE_NOTE + "dropped claim ('" + claim.pathPrefix() + "' -> " + claim.targetModule()
                            + ") - blank, root-level, absolute, or repo-escaping prefix does not bound a subtree"
                            + " inside the repository");
                    continue;
                }
                if (!knownModules.contains(claim.targetModule())) {
                    notes.add(MERGE_NOTE + "dropped claim (" + prefix.get() + " -> " + claim.targetModule()
                            + ") - unknown module name");
                    continue;
                }
                producers.computeIfAbsent(new ClaimKey(prefix.get(), claim.targetModule()), k -> new TreeSet<>())
                        .add(id);
            }
            notesById.put(id, notes);   // a later duplicate appends its note after these
        }

        Map<String, TreeMap<String, TreeSet<String>>> byPrefix = new TreeMap<>();
        producers.forEach((key, ids) ->
                byPrefix.computeIfAbsent(key.prefix(), p -> new TreeMap<>()).put(key.module(), ids));

        List<ActivePathClaim> active = new ArrayList<>();
        List<PathClaimCollision> collisions = new ArrayList<>();
        Map<String, Integer> claimCountById = new TreeMap<>();

        byPrefix.forEach((prefix, targets) -> {
            if (targets.size() == 1) {
                var single = targets.firstEntry();
                active.add(new ActivePathClaim(prefix, single.getKey(), List.copyOf(single.getValue())));
                single.getValue().forEach(id -> claimCountById.merge(id, 1, Integer::sum));
            } else {
                // Collision: never pick a winner; no claim, a diagnostic, and a note to every contender
                TreeMap<String, List<String>> reportMap = new TreeMap<>();
                targets.forEach((mod, ids) -> reportMap.put(mod, List.copyOf(ids)));
                collisions.add(new PathClaimCollision(prefix, Collections.unmodifiableSortedMap(reportMap)));
                String note = MERGE_NOTE + "suppressed claim on prefix '" + prefix
                        + "' - contested by more than one module (" + String.join(", ", targets.keySet()) + ")";
                targets.values().stream()
                        .flatMap(Set::stream)
                        .distinct()
                        .sorted()
                        .forEach(id -> notesById.computeIfAbsent(id, k -> new ArrayList<>()).add(note));
            }
        });

        active.sort(Comparator.comparingInt((ActivePathClaim c) -> c.normalizedPrefix().length())
                .reversed()
                .thenComparing(ActivePathClaim::normalizedPrefix));

        List<AttributorReport> reports = statusById.entrySet().stream()
                .map(e -> new AttributorReport(
                        e.getKey(),
                        e.getValue(),
                        claimCountById.getOrDefault(e.getKey(), 0),
                        List.copyOf(notesById.getOrDefault(e.getKey(), List.of()))))
                .toList();

        return new AttributionTable(List.copyOf(active), List.copyOf(collisions), reports);
    }
}

== Module Discovery, Build Map & Architecture State Machine
_See Requirement link:../Requirements.adoc#PM-EXT-3[PM-EXT-3: Module Discovery, Build Map & Architecture Enrichment]_

`PM-MCP` moves deterministic module discovery, dependency graph construction, verification routing (`derive-verification`), and architecture queries into the daemon while keeping semantic module enrichment (`responsibility`, `purpose`, `key_packages`) as model judgment.

=== Server-Owned Module Discovery & Enrolled Discovery Jobs

* **Python Import Scan (Deliberate Simplification)**: The Python import scan is a line-oriented scanner in Java: it reads only `import x[.y]` and `from x[.y] import ...` lines (leading whitespace allowed, continuation lines and parenthesized import lists joined), and builds no full Python AST. *Deliberate simplification vs. `plan-marshall`*, which parses with Python's `ast` module: imports produced dynamically (`importlib`, `__import__`) or hidden in string literals are not seen, and an `import` line inside a multi-line string may be read as an import; both errors are accepted because the scan only derives module edges, never a gate verdict.

* **Live Crawl, Snapshot as Cache**: Discovery always crawls the live worktree, including uncommitted descriptors. The descriptor tree hash covers the live descriptor content, not `HEAD`. The persisted snapshot is a denormalized cache, never the gatekeeper: a module directory present on disk but absent from the snapshot is still discovered.
* **In-Process Crawl vs. Lazy Discovery Jobs**: The in-process crawl (compiled-in descriptor parsers and file-tree scans) issues no child process except `git rev-parse --git-common-dir`. Enrolled discovery jobs (the job templates above) run lazily, only when a fact that only they provide is requested, and always as enrolled jobs of the job runtime, never as ad-hoc subprocesses of the crawl.
* **Per-Descriptor Failure Isolation**: A malformed descriptor (the root descriptor or one workspace member) is reported for its module with the parse diagnostic and does not abort discovery of the remaining modules.
* **Build-File Dependency Parser**: Each build domain (Maven, Gradle, npm, `pyproject`) provides, next to its descriptor parser, a build-file dependency parser: it claims its build files (`pom.xml`, `build.gradle(.kts)` and `settings.gradle(.kts)`, `package.json`, `pyproject.toml`) and returns the ecosystem-qualified third-party coordinates a file declares at a given revision (`maven:<groupId>:<artifactId>`, `npm:<name>`, `pypi:<name>`) with their scope, or a parse diagnostic. The pre-merge Dependency Delta Check consumes it (link:phase-workflows.adoc#dependency-delta[Phase Workflows Specification, Dependency Delta Check]); a changed build file that no parser claims, or that fails to parse, makes that check `indeterminate`.

=== Build Map & Deterministic `derive-verification` (ADR-004)
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-9[PM-WATCH-EXT-9]_

The file-to-build contract lives in the team file `.marshall/config/build-map.json` (`routes`, link:store-schemas.adoc#config-build-map-json[Store Schemas Specification, `build-map.json`]; called the build map, `build.map` in `plan-marshall`): a domain-keyed inventory `{"<domain>": [{"glob", "role", "build_class"}]}` with roles `production`, `test`, and `config` and the closed build classes `compile`, `module-tests`, `verify`, and `none`. Phase 4 (`plan`) calls `derive-verification` with each task's changed-artifact list and stamps the returned canonical command set into the task's `verification.commands`; Phase 5 (`execute`) runs the stamped commands. The seeding, editing, and reseeding rules mirror `plan-marshall` (`manage-config/scripts/_cmd_build_map.py`, `manage-config/standards/data-model.md` § build.map, `marshall-steward/references/build-map-setup.md`, `phase-4-plan/SKILL.md`), verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing.

* **Seeding from Axis B**: The seed collects every build-system descriptor's `classifyGlobs()` routes under its served domain key, keeps a domain's routes only when that domain's Axis-A applicability matches at least one discovered module, prunes routes that match no git-tracked file, and stamps each route with `classifyBuildClass()`. Because applicability needs discovered modules, seeding happens only in `setup.seed-build-map` after `setup.discover-modules`; nothing else creates `build-map.json`.
* **Write-Once Seed, Direct Edits**: A seed never overwrites an existing `build-map.json`. Corrections are made directly to the seeded entries — through the `customize_routes` link of `setup.seed-build-map`, or by a committed edit of `.marshall/config/build-map.json` — and there is no separate override layer. `customize_routes` therefore edits the seeded block itself and is not an exception to write-once: write-once constrains the seeder, not the user.
* **Explicit Reseed Only**: The seeded block is re-derived only through `setup.reseed-build-map`, which the setup workflow enters on every reconcile run when `build-map.json` exists. The state compares the persisted block with the live derivation (per domain, added and removed globs). When they agree it passes silently; on drift it offers `reseed_build_map` (replace the whole block with the live derivation, discarding hand edits) and `keep_build_map` (preserve the persisted block). The state always waits for this answer, even when other setup decisions are pre-answered, so a hand edit is never discarded without consent (`plan-marshall`: `build-map drift`, `build-map seed --force`, upgrade nested gate `build-map-reseed`).
* **Separate Glob Dialect**: Build-map routes use the **`fnmatch` glob dialect**, which is kept strictly separate from the Axis-A `provides_file_globs` domain-detection dialect. A path-bearing route matches the whole repository-relative path (a single `*` spans `/`; routes never use `**`), and a bare-basename route (no `/`, e.g. `pom.xml`) matches that file name at any depth.
* **Fail-Closed Read Invariant**: `derive-verification` reads `build-map.json` fail-closed. If it is absent, malformed, at another `format_version`, or holds an entry with an unknown `role` or `build_class`, the engine refuses verification derivation with an explicit diagnostic (`build_map_invalid` or `build_map_unseeded`) rather than returning an empty verification set. *Deliberate hardening vs. `plan-marshall`*: `plan-marshall`'s `build-map read` also fails closed, but its deriver and build-decision readers degrade an absent `build.map` to an empty map instead of refusing.
* **Canonical Command Resolution Rules**:
  - Production paths (`role == "production"`, `build_class == "compile"`) resolve `compile` on the owning module.
  - Test paths (`build_class == "module-tests"`) resolve `test-compile` + `module-tests` on the owning module (Maven Failsafe `*IT`/`IT*`/`*ITCase` test paths route to `verify`).
  - Build/lint/packaging config paths (`role == "config"`, `build_class == "verify"`) resolve `verify` for the affected module.
  - Documentation or non-compiled path claims (`build_class == "none"`) require zero build jobs and route only to applicable doc/plugin validators.

=== Architecture Query Resources (`pm://architecture/...`)
_See Requirement link:../Requirements.adoc#PM-TOOL-3[PM-TOOL-3: Read-Only MCP Resource URI Surface]_

_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-5[PM-WATCH-EXT-5], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-8[PM-WATCH-EXT-8], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-10[PM-WATCH-EXT-10], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-25[PM-WATCH-EXT-25]_

Instead of invoking Python CLI scripts via Bash to inspect repository structure, the model reads server-computed MCP resources under `pm://architecture/`:

[cols="2,3"]
|===
|Resource URI |Returned TOON Payload

|`pm://architecture/overview`
|Project-wide module inventory, active domains, resolver status reports, and enrichment completion status.

|`pm://architecture/modules/{module_id}`
|Complete discovered facts, active profiles, resolved `skill://` URIs, key packages, and persisted semantic enrichment for `<module_id>`.

|`pm://architecture/files`
|Tier-0 file inventory of the working tree (the zero-configuration floor every higher discovery tier degrades to): file categories (content classes and file types) with their counts, plus a coverage block `{files_scanned, excluded{reason: n}, complete}` (git-ignored, binary, size-capped, and unreadable paths counted per reason). A zero count is honest only when `files_scanned > 0` and `complete: true`; otherwise the category renders `indeterminate`, never `0`. Content search (which files contain a string) stays with the host's search tool for leaf workers (link:dispatch-and-effort.adoc[Dispatch & Effort Specification], Mandatory MCP Tool Inclusion); the server adds no search verb (`PM-TOOL-5`).

|`pm://architecture/files?path={rel_path}`
|Owning module (`which-module`) resolved via module roots and Axis-D `PathAttributionMerge`, plus matching `build.map` route.

|`pm://architecture/files/{path}/neighbours`
|File-level neighbours of one repository-relative file: the files it imports (resolved by the same scanners as the Axis-C resolvers, unresolvable imports listed as `unresolved[]`), its paired test or production file (by the owning build system's source-set convention, `none` when there is none), and its owning module. |`pm://architecture/graph`
|Merged Axis-C dependency graph (`MergedDependencyEdge[]` with `resolverIds` provenance) and topological layers.

|`pm://architecture/neighbours/{module_id}`
|Direct upstream dependencies and direct downstream consumers of `<module_id>`, annotated with resolver provenance.

|`pm://architecture/impact?modules={csv}`
|Transitive downstream blast radius and derived verification set (`derive-verification`) for the specified modules or active plan footprint. |Descriptor regression and module-diff report comparing the current working tree against the project architecture snapshot `.marshall/project-architecture/_project.json` (same file name as `plan-marshall`'s `.plan/project-architecture/_project.json`, with the per-module `{module}/derived.json`): `changed[]` for modules whose comparison is certified as different, and `indeterminate[]{module, reason}` for modules the hash surface cannot certify. An uncertifiable comparison is `indeterminate`, never `changed`.

* **Resource Contracts**: Every `pm://architecture/*` resource documents its arguments, its payload, and its zero-result and error semantics. An empty result is returned only for a population that was actually examined; a resource that could not examine its population returns an explicit error or `indeterminate` entry, never an empty list.
* **Empty Graph Is Not Clean**: When the project has at least 2 modules and the merged graph holds 0 edges, `pm://architecture/graph`, `pm://architecture/neighbours/{module_id}`, and `pm://architecture/impact` answer `indeterminate` (with the resolver status reports), never an empty edge set, and every gate reading the graph treats that answer as `indeterminate`.
* **Two Capability Vocabularies**: Capability status uses two distinct vocabularies that are never mixed: `derivable` / `not_derivable` for derivation capabilities (a discovery tier or resolver can produce the fact) and `available` / `unavailable` for content capabilities (the content can be read or searched).

=== Architecture Enrichment Judgment Links & Project Setup State Machine

Only semantic module enrichment (`responsibility`, `purpose`, and `key_packages` with their reasoning) requires model judgment. `PM-MCP` replaces the legacy `marshall-steward` first-run wizard (Steps 1–16) and its `upgrade` verb with one dedicated **`project-setup`** state machine (`classpath:/workflows/project-setup.pmwf`), hosted by the project's workspace scope (`scope workspace`; entered with `pm-mcp enter --client <client> workspace` and driven through `pm_state` / `pm_do` with `scope=workspace`, `PM-ARCH-4`; its state lives in `workspace/mcp/status.json` of the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/`, link:filesystem-layout.adoc#workspace-home[Filesystem Layout Specification, Workspace Home]). The workspace scope exists once the project is enrolled: `pm-mcp operator enrol` creates the project's machine store for every project, and the first run of the setup workflow creates `.marshall/`. Enrolment (`pm-mcp operator enrol`, host tools) therefore precedes the workspace scope and is never a state of the setup workflow; the credentials of the git and provider integrations are verified in `setup.verify-credentials`, and every other missing secret is handled by the credential check (`pm-mcp operator credentials`, `PM-CRED-3`) where the credential is used. The workflow has one start state, `setup.entry`, an `auto` state that routes by server facts: without `.marshall/config/` (first run) to `setup.prepare-workspace`, which creates `.marshall/config/` with the copies of the binary's default workflow units (the JSON team files stay absent until a deviation is configured, since they are sparse), otherwise to the reconcile path starting at `setup.reconcile-config`. The workflow unit `project-setup.pmwf` itself is compiled into the binary and is never project-owned: the setup workflow must be able to repair a project whose units fail verification. The workflow has no terminal state: the workspace scope lives as long as the project's enrolment, and every run ends in the resting `link` state `setup.completed`, whose `reconcile` link returns to `setup.entry` for the next run. A project that also runs on legacy `plan-marshall` starts from a clean slate like any other: `PM-MCP` imports nothing from its `.plan/` (`PM-MIG-2`), so its first setup run takes the first-run path; setup never reads or writes `.plan/`. Its states are catalogued in the link:state-catalogue.adoc#state-catalogue-setup[State Catalogue, Project Setup: `setup`].

[#setup-integration-variants]
*Integration variants* (`setup.select-integration-variants`): Every git and provider operation is a contract of a provider module (link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]) with two interchangeable implementations: the *native variant* (in-process JGit, respectively the GitHub or GitLab client over `cui-http`, authenticated with the agent credential of the token lane) and the *CLI variant* (the enrolled `git`, `gh`, or `glab` host tool, acting with the operator's ambient authentication). The project's variant is decided explicitly, per integration, by the operator in this state; there is no implicit default, the compiled default table holds no variant, and `machine-config.json` `project_defaults` cannot carry one.

* *Integrations*: `git` (the `git.*` contracts: repository, worktree, and transport operations) and the CI provider integration `github` or `gitlab` (the `ci.*` contracts together with the provider's review-thread and code-scanning finding sources, `pm-mcp-findings`). The provider integration asked for is the one the local derivation of `ci_provider` names (a known provider host of the push remote) or the team override `project.json` `ci_provider`; when neither names it, only `git` is asked here, and `setup.select-providers` asks the provider integration once its `configure_providers` link sets the override. The Sonar integration (`pm-mcp-sonar`) has only a native variant and is not asked. One variant holds for all operations of an integration; integrations may differ (for example `git` `cli` with `github` `native`), operations within one integration never do.
* *Decision*: The choice is taken only through the operator channel: following the state's link `select_variants` (rel `next`) opens an elicitation; on a connection without elicitation support it raises the `blocked` condition (link:state-catalogue.adoc#condition-blocked[State Catalogue, `blocked`]) whose `facts.operator_command` names `pm-mcp operator config --project <project_id>`. Per integration the elicitation shows `native` as the recommended value, the result of the derived fact `git_native_capability` (for `git`: each repository feature the native variant cannot serve, with its reason), and, for a `cli` choice, that the operator's own ambient identity (credential helper, SSH agent, `gh`/`glab` login, signing key) will act for every operation of that integration. A `cli` choice requires the host tool in the project's enrolment (`cli_tool_not_enrolled` names `pm-mcp operator enrol`). The answer is written to `local-config.json` `integrations.<integration>.variant` (link:store-schemas.adoc#local-config[Store Schemas Specification, Operator Local Configuration]); the same elicitation captures the commit author `commit_identity {name, email}` while it is unset, prefilled with the operator's global git `user.name` and `user.email` read once as a proposal and confirmed or edited by the operator (never re-read silently afterwards).
* *Validity*: The state passes without a link when every integration it asks for has a stored choice that is still valid. A stored `native` choice is invalid while `git_native_capability` reports a missing capability for it (a repository feature that appeared after the decision: hooks, signing requirement, filter drivers, LFS, submodules, SHA-256 or partial or sparse repositories, an SSH-only remote); the state then asks again and shows the finding. There is no automatic fallback to the CLI variant: switching silently would switch to the operator's credentials.
* *Before the decision*: No git or provider operation runs for the project, in either variant, before the integration it belongs to has a valid choice: every such primitive refuses with `integration_variant_unset` naming the integration and this state, and `pm_start` of the project refuses with the same reason. The derivation of `git_native_capability` itself is no git operation: the server reads the repository configuration and files directly (`extensions.*`, `core.hooksPath`, non-sample files under `.git/hooks/`, `.husky/`, `lefthook.yml`, `.pre-commit-config.yaml`, `.gitattributes` drivers, `.gitmodules`, `lfs.url`, the remote URLs).
* *Model-facing minimality*: The chosen variants, the capability details, and the identity notice are rendered to the operator (elicitation) and served on demand by the operator surfaces (`pm-mcp operator config`, `pm-mcp status`, `pm://project/config`), never pushed into the state's model-facing `facts`, which name only the integrations still undecided (link:hypermedia-format.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

[#setup-verify-credentials]
*Credential verification* (`setup.verify-credentials`): An `auto` state that checks, per decided integration, that the chosen variant can act, then refreshes the network derived facts (link:store-schemas.adoc#derived-facts[Store Schemas Specification, Derived Facts]) with the chosen variants:

* *Native `github`*: resolves the token-lane entry `github` (`PM-CRED-2`, project entry before global entry). For a GitHub App it mints the App JWT (RS256, JDK `Signature`), resolves the App's installation for the repository, and mints an installation token restricted to the repository and a read-only permission set (held in memory per `PM-CRED-5`, never persisted); for a fine-grained or classic personal access token it calls `ci.whoami`. The check derives the network facts `agent_identity` (login, kind, permissions on the repository; operator-only) and `checks_visible`. A credential that cannot read check runs is accepted: the operator is told that `ci.checks` will report `completeness: incomplete`. A token without expiry is accepted and shown on `pm-mcp operator credentials status`.
* *Native `gitlab`*: resolves the entry `gitlab` (project access token, group access token, service-user or personal access token, all accepted alike) and calls `ci.whoami`; an `expires_at` within 14 days is reported as `expiring`.
* *Native `git`*: the transport credential is the provider's entry for a provider host and `git-https` for any other HTTPS host; the check resolves the effective push and fetch URLs (with `insteadOf` rewrites), requires `https` after the SSH mapping of known provider hosts and the origin of the credential entry's `url` (`remote_origin_mismatch`, audited), and reads the push remote's refs with `git.ls-remote`.
* *CLI integrations*: no credential is read; the state verifies the enrolled host tool and records that the integration acts as `identity: operator_ambient` (audit record).
* *Committer identity*: the committer of server commits is resolved from the verified agent credential (a GitHub App's `<slug>[bot]` noreply address, the token's user), else the fixed `plan-marshall-mcp` noreply identity; the author is the operator's `commit_identity`. Both variants produce the same author and committer metadata.
* *Failure*: a missing credential or a failing check raises the `blocked` condition with the `pm-mcp operator credentials` command (`PM-CRED-3`); its resolution re-runs the check. A failing check is never a fallback to another variant or credential.

Exit: `setup.project-settings` on the first run, `setup.detect-domains` on the reconcile run; back to `setup.select-integration-variants` when the refreshed facts invalidate a stored `native` choice (for example the network fact `signed_commits_required`, an input of `git_native_capability`).

[#setup-merge-queue]
*Merge-queue probe* (`setup.merge-queue`): The state reports the derived network fact `merge_queue_enforced` (`{enforced, available, check_response_timeout}`, link:store-schemas.adoc#derived-facts[Store Schemas Specification, Derived Facts Store]) for the base branch. The project is eligible when a CI provider integration is selected, the derived fact `push_remote` is non-empty, and `available` is not `no`. `available` is `no` only where the provider's answer is readable: GitHub, a repository owned by a user, or a private or internal repository whose organization plan is readable and is not Enterprise Cloud; GitLab, a tier below Premium when the tier is readable. An `indeterminate` or stale value counts as eligible. It passes without a link when the queue is enforced or the project is not eligible. Otherwise it names the provider setting that enables the queue (GitHub: the "Require merge queue" rule of a ruleset on the base branch; GitLab: merge trains with merged-results pipelines) and offers `recheck_merge_queue` (re-derives the fact after the operator changed the setting) and `skip_merge_queue`. The server never changes the setting and persists no key: administrative repository changes need admin scope, which the agent identity does not hold. *Deliberate change vs. `plan-marshall`*: `plan-marshall` provisions the queue (ruleset create or update, `merge_trains_enabled=true`) and persists a `use_merge_queue` opt-in.
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-30[PM-WATCH-EXT-30], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-31[PM-WATCH-EXT-31]_

In `setup.enrich-architecture`, the engine offers concurrent entity-scoped `dispatch:enrich-<module_id>` links (or direct `enrich:<module_id>` submission links for single-module repositories). The submission parameters mirror `plan-marshall`'s `architecture enrich module` and `architecture enrich package` commands (`manage-architecture/scripts/architecture.py`, purpose values from `manage-architecture/standards/architecture-persistence.md`), verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing:

|===
|Parameter |Required |Content

|`responsibility`
|Yes
|Module description, 1–3 sentences.

|`responsibility_reasoning`
|No
|Sources the responsibility was derived from (for example the README overview or a central type).

|`purpose`
|No
|Module classification, closed enum `library` \| `extension` \| `deployment` \| `runtime` \| `parent` \| `bom` \| `integration-tests` \| `benchmark`.

|`purpose_reasoning`

The reasoning fields carry the enrichment rationale required by `PM-EXT-3` and are persisted next to the values they justify. *Deliberate hardening vs. `plan-marshall`*: `purpose` is validated against the closed enum; `plan-marshall` documents the same eight values but its CLI accepts any string. The state cannot transition to `setup.commit-changes` until the **`every_module_enriched`** guard evaluates to `true` (every discovered module has a `responsibility`). On the reconcile path the state is scoped to the modules listed in `changed[]` of `pm://architecture/drift`: only those are offered for enrichment, and the state passes without a dispatch when the list is empty; a module listed in `indeterminate[]` is never treated as changed.

*Landing*: `setup.commit-changes` is a `link` state offering the routine decision `land` or `leave`; `land` enters the `call` state `setup.land-changes`, which runs `call git.commit_and_push (message_mode=step_or_fallback, push_mode=if_push_remote)` on the primary checkout with the setup staging set `.marshall/config/**` (team files and workflow units), `.gitignore`, and `.marshall/project-architecture/**` (link:workflow-dsl.adoc#_call_site_reuse_matrix_across_workflows[Workflow DSL Specification, Call-Site Reuse Matrix]). Every outcome except `aborted` enters `setup.completed`; `aborted` returns to the decision. `leave` enters `setup.completed` with the changes uncommitted.

=== Tier-1 Init Routing & Deterministic Deliverable Generation
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-9[PM-WATCH-PHASE-9]_

The scoring and routing rules mirror `plan-marshall` (`script-shared/scripts/recipe_scoring.py`, `phase-1-init/SKILL.md`, verified at commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing).

1. *Explicit Choice Beats Heuristic Match*: A plan started from a recipe (`pm_start` with `recipe_id`, i.e. source `recipe`) bypasses scoring and routes directly to `init.recipe-selected`.
2. *Registry-Wide Deterministic Scoring*: For every source other than `recipe` (`request`, `issue`, `lesson`; a `local_changes` plan goes to the land lane and is not scored), during `phase-1-init` (ahead of light/deep planning-lane routing), the server scores **every** registered recipe (no domain pre-filter): $\text{confidence} = 0.6 \cdot \text{keyword} + 0.25 \cdot \text{domain} + 0.15 \cdot \text{scope}$, rounded to three decimals, where `keyword` is the share of the recipe's `display_name` + `description` tokens (stop-words removed) found in the request, `domain` is `1` when the recipe's `domain` equals the plan's domain, and `scope` is `1` when the plan's scope estimate matches the recipe's `scope` (`module` for surgical/narrow plans, `codebase_wide` for broad ones). For the surgical-fix recipe only, a pre-diagnosed-change shape score of the request may raise the confidence (`max`). Recipes below `0.35` are dropped.
3. *Auto-Route or Ask*: Scoring always runs (item 2); `recipes.auto_route` never switches it off, it only chooses between auto-routing and asking. When the operator's `recipes.auto_route` (`local-config.json`, default `true`) holds and the top confidence is at least the compiled auto-route threshold `0.6` (a calibration of the scorer, not configurable), the engine selects that recipe without asking. Otherwise (auto-routing disabled, or the top confidence below the threshold), if candidates remain, it enters `init.recipe-candidate` (the single state of the recipe selection dialogue, kind `awaiting_user`; recipe selection never uses another `init` question state) offering `use_recipe:<recipe_key>` (`rel = "next"` for the highest-scoring recipe, `rel = "alt"` for the others) and `skip_recipe` (`rel = "alt"`) to proceed with standard light/deep planning.
4. [[recipe-plan-id]]*Recipe Plan ID*: A recipe plan's `plan_id` is `recipe-{recipe_key}-{yyyy-mm-dd-hh-mm-ss}` (UTC), so every run gets a fresh branch name; its grammar and the 37-character bound of `recipe_key` that keeps it within the `plan_id` grammar are in the link:identifiers.adoc#id-recipe-plan-id[Identifier Registry]. *Deliberate change vs. `plan-marshall`*: `plan-marshall` uses hour precision (`{yyyy-mm-dd-hh}`), which collides when the same recipe runs twice within an hour.
5. *Server-Side Target Harvesting & Deliverable Generation*: When a recipe is selected, the server executes the recipe's deterministic `target_harvester` (e.g., enumerating packages per module, scanning `.md`/`.adoc` files for misaligned ASCII box diagrams, or invoking an enrolled `project_script` harvester) and populates the solution outline deliverables automatically. A recipe whose harvester kind is `request_scoped` (`surgical-fix`) runs no harvest: its deliverables come from the pre-diagnosed request (the named files, root cause, and exact change; one deliverable per affected file or one for the whole cohesive edit), and a request that names no file or crosses a module boundary is refused by the recipe's fit gate rather than widened. The deliverables are derived in the Phase 3 entry state of the recipe shortcut, `outline.recipe-entry` (link:state-catalogue.adoc#state-outline.recipe-entry[State Catalogue]). The workflow exposes judgment links only where model evaluation is required: confirming or pruning harvested targets (`confirm_recipe_targets`, offered by `outline.recipe-confirm` before `outline.review`) and verifying coverage at completion.
6. *Auditable, Idempotent Harvest Runs*: A recipe run records one disposition per harvested target; for `recipe-lesson-cleanup` over `stalled_lessons` the dispositions are `routed`, `reclassified`, and `retired` (through the lesson's in-file retirement with its mandatory `reason` and `verdict`, link:store-schemas.adoc#lesson-record[Store Schemas Specification, Lesson Record, Retirement]); the `stalled_lessons` population is the lessons with a stale claim (link:store-schemas.adoc#lesson-record[Store Schemas Specification, Lesson Record, Claim]). Re-running on unchanged input is a no-op keyed on the target's duplicate key (for lessons: link:store-schemas.adoc#lesson-record[Store Schemas Specification, Lesson Record, Upstream Release, Duplicates]). If the population differs between harvesting and action, the run reports the delta (added and removed target ids) and never adopts it silently.
7. *Empty Harvest Is a No-Op, Never an Empty PR*: When the harvester (after `confirm_recipe_targets` pruning) yields zero targets, the plan creates no deliverables, no commit, and no pull request: it ends as `completed` with `merge_outcome: no_pr` (link:store-schemas.adoc[Store Schemas Specification, `merge_outcome`]) and the fact `empty_harvest` (harvester kind and the population it scanned) in its landing envelope. An empty pull request is never created for a recipe plan.
8. *Recipe Parameters*: `recipe_params` (link:mcp-tools.adoc[MCP Tools Specification, `pm_start`]) is validated by the server against the recipe's own `parameters_schema`; there is no global parameter vocabulary such as a fixed scope × thoroughness matrix. A violation refuses `pm_start` before any plan directory is created, and a recipe without `parameters_schema` refuses non-empty `recipe_params`.
9. *Doc-Shaped Lesson Route*: For source `lesson`, the server additionally evaluates `plan-marshall`'s doc-shaped predicate over the lesson body (`phase-1-init` Step 5c-lesson): the body has at least one `## Directive` or `## Actions` section, contains no fenced code block tagged `python`, `py`, `java`, `js`, `javascript`, `ts`, or `typescript`, and the first non-empty line of no directive section begins (case-insensitively) with `test`, `refactor`, `implement`, `add code`, `write code`, or `migrate`. When all three hold, the plan is routed to the `lesson-cleanup` recipe (`init.recipe-selected`, recorded with `route_reason: doc_shaped_lesson`) ahead of the registry scoring; otherwise the lesson is scored like any other source.
10. *Request-Aspect Classification*: For every source other than `recipe`, the server classifies the request aspect (`analysis`, `planning`, `implementation`) by keyword-table token overlap (`plan-marshall`'s `aspect-classify`): the higher of `analysis` and `planning` is accepted only when its overlap confidence is at least `0.7` (independent of the recipe thresholds) and beats the `implementation` overlap; otherwise the aspect is `implementation`. The result is persisted as `status.metadata.request_aspect` with its confidence, silently (no question), and records intent only; it never decides whether a build is needed.

Items 9 and 10 are Tier-1 routing computed by the server in `init.classify` with zero model calls. *Deliberate change vs. `plan-marshall`*: `plan-marshall` lets the orchestrating model apply the doc-shaped predicate and offers a bounded model fallback for an ambiguous aspect; `PM-MCP` computes both deterministically and has no model fallback.

== Pre-Submission Self-Review Surfacer Extension Point (`ext-self-review-*`)
_See Requirement link:../Requirements.adoc#PM-EXT-5[PM-EXT-5: Out-of-Process Project Script Jobs & Domain Workers]_

_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-13[PM-WATCH-EXT-13], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-14[PM-WATCH-EXT-14], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-15[PM-WATCH-EXT-15], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-16[PM-WATCH-EXT-16], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-17[PM-WATCH-EXT-17], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-18[PM-WATCH-EXT-18], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-19[PM-WATCH-EXT-19], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-20[PM-WATCH-EXT-20], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-24[PM-WATCH-EXT-24], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-26[PM-WATCH-EXT-26], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-45[PM-WATCH-GEN-45]_

The self-review surfacer is a domain extension point, not a recipe: a domain bundle registers at most one compiled surfacer `ext-self-review-<domain_id>` (in `plan-marshall`: `pm-plugin-development:ext-self-review-plan-marshall`), declaring the content classes it covers and its detectors. During `phase-6-finalize`, the pre-submission structural self-review step (link:phase-workflows.adoc#_normative_step_catalogue_across_ordering_bands[Phase Workflows Specification, catalogue row `8`, `pre-submission-self-review`]) runs the surfacers registered for the plan's domains as deterministic candidate detectors over the plan's realized diff to surface high-risk patterns (unvalidated boundary inputs, asymmetric function pairs, description-vs-body mismatches, stale ordinal prose, unguarded flags) as structured facts for model review.

*Outcomes*: every round records exactly one of three outcomes, carried into the landing facts as `self_review` (link:phase-workflows.adoc#_landing_envelope_emit_landing[Phase Workflows Specification § Landing Envelope]):

* `reviewed`: at least one applicable surfacer ran and the model submitted its verdict over the surfaced candidates.
* `not_covered`: a surfacer is registered for the plan's domains but does not apply to the footprint; the surfacer names the reason (`no_covered_content_class` with the uncovered content classes, or `zero_detectors`).
* `not_run`: no surfacer is registered for any of the plan's domains; the reason is `no_domain_surfacer`.

Neither `not_covered` nor `not_run` is ever recorded or rendered as `clean` or `passed`. The contract rules:

* **AsciiDoc Content Class**: `*.adoc` paths form their own content class `asciidoc` (never `other`), covered at least by the stale-count and ordinal-prose detector: a count or ordinal stated in prose ("the five bands", "the third item", "13-state vocabulary") that no longer matches the enumeration, table, or list it describes, including one in a file the plan did not edit, is a candidate. PM-MCP's own documentation is AsciiDoc, so its changes are reviewed rather than reported `not_covered`.
* **Applicability by Content Class**: A surfacer is applicable when its declared content classes cover at least one content class of the realized footprint; a footprint whose paths all fall in content class `other` has no applicable surfacer. An inapplicable surfacer is never run: the step records `not_covered` with the surfacer's reason and the uncovered content classes and completes non-blocking, never as `clean`. The reasons `no_domain_surfacer`, `no_covered_content_class`, and `zero_detectors` are round-invariant at an unchanged `HEAD`.
* **Not Run Is Not Clean Invariant**: When no self-review surfacer is registered for the plan's domains, the server records `"status": "not_run"` with `"reason": "no_domain_surfacer"` in the finalize ledger—never `"clean"` or `"passed"`. Every active surfacer records its `scope_statement`, `structural_limit`, and `delta_coverage`; a detector class with zero matching files in the diff is recorded as `unapplicable`, never counted toward measured clean coverage.
* **Which Zero Coverage**: Per content class the surfacer records `files`, `files_with_candidates`, and `detectors`; a class with `files > 0` and `detectors == 0` is recorded as `gap`, never as clean. The reach map is derived from the registered detectors. Every realized path with no applicable detector is listed as `not_scanned` in the step facts and the landing facts, and a round over only `not_scanned` paths is `not_covered`. Per-file candidate counts distinguish `examined_zero` (an applicable detector ran on the file and found nothing) from `not_scanned`.
* **Run-Emitted Diagnostics**: Diagnostics emitted by the plan's own run (build, validator, or gate output) whose subject overlaps the plan footprint are surfaced as candidates alongside the detector findings.
* **Target-Class Seeding**: When the plan's approved outline names the defect class the plan exists to remove (its target defect class), the surfacer also seeds candidates of that class over the plan footprint in every round, because a fix for a class is the likeliest place to re-commit it; the seeded candidates are counted in the round's `cohort_size` like any other.
* **Out-of-Surface Findings**: Findings identified outside the surface go into a non-blocking `observed_out_of_surface` list whose count reaches the step summary, so `clean`, `nothing_found`, and `suppressed` stay distinct outcomes.
* **Round Accounting**: `cohort_size` is published per round and cumulatively. A finding at a file and line of a prior round's finding is marked `repeat_site` with its repeat count. A finding classified `self_seeded` (introduced by the previous round's fix) records that classification at WARNING level; its remedy is the deletion of the added clause, gated on that recorded classification. Each round records `findings_total` and `findings_self_seeded`; from round 2 the step's facts state the self-seeded share, the vocabulary skill prescribes deleting the added text or replacing it with a pointer as the default remediation, and the share of every round is rendered in `finalize.loop-limit-reached` (link:workflow-dsl.adoc#loop-back-bounds[Workflow DSL Specification]). The share is a signal only: `max_iterations` remains the loop's only automatic bound.
* **Delta Round Narrowing Invariant**: On subsequent finalize iterations after a fix, delta self-review rounds narrow only the candidate file set to files modified since the previous reviewed `worktree_sha`, never narrowing the hunk basis against the plan's base commit. Every fix hunk is reviewed together with its full enclosing passage (the enclosing section, list, table, or code block), never as the bare hunk. The plan's base commit is the footprint `base_ref` defined in link:store-schemas.adoc[Store Schemas Specification] (§ Three-Way File Footprint Reconciliation). Before computing candidates the step fetches `origin/<base_branch>` itself; the fail-closed refusal applies only when the base commit or the previous `worktree_sha` is still unresolvable after that fetch, and then the step fails with an explicit error rather than silently widening or skipping. The delta candidate set also includes the reference closure: every file of the plan footprint that references a path or a declared symbol changed since the previous reviewed `worktree_sha` (a document line made stale by an edit in another file is therefore a candidate in the next delta round, not only in the closing full round). When the previous round's `worktree_sha` is not an ancestor of `HEAD` (the branch was rebased), delta resolution is skipped, open findings stay pending, and a full round is required: an endpoint diff across an upstream advance never marks a finding fixed. A delta round can never close the step: a clean delta round is followed by exactly one full-surface round over the whole plan diff, and only a clean full-surface round records `done` (`may_close = true`). A delta round that surfaces findings loops back without a confirmation round.

== Out-of-Process Project Script Jobs (`project_script`) & Domain Workers
_See Requirement link:../Requirements.adoc#PM-EXT-5[PM-EXT-5: Out-of-Process Project Script Jobs & Domain Workers]_

To support repository-specific automation (`finalize-step-*` skills that ship executable checks, custom `recipe-*` target harvesters) and third-party/organization domain workers (custom build-log parsers, marker scanners, or module discovery for languages not compiled into `pm-mcp`) without compromising the GraalVM native-image closed world, `PM-MCP` provides a permanent **`project_script`** job type in the Job Runtime (see link:job-runtime.adoc[Job Runtime Specification]).

=== Division of Authority: Server vs. `project_script`

[source,text]
----
┌─────────────────────────────────────────────────────────────────────────┐
│ PM-MCP Daemon (Authoritative State & Security Boundary)                 │
│  • Owns workflow state machine, step ordering, gating, and locks        │
│  • Verifies script path, interpreter hash, and SHA-256 against enrolment│
│  • Serializes closed JSON input payload; spawns isolated process group  │
│  • Validates stdout against strict output JSON Schema                   │
│  • Persists findings/facts into .marshall/ stores atomically            │
└───────────────────┬─────────────────────────────────▲───────────────────┘
                    │ stdin: ProjectScriptInput JSON  │ stdout: ProjectScriptOutput JSON
                    ▼                                 │
┌─────────────────────────────────────────────────────────────────────────┐
│ Out-of-Process `project_script` Subprocess (Stateless Fact Producer)    │
│  • Runs in sanitized environment (no provider credentials)              │
│  • Reads worktree files read-only; NEVER writes to .marshall/ stores    │
│  • Returns structured facts, candidate findings, or parsed log records  │
└─────────────────────────────────────────────────────────────────────────┘
----

1. *No Direct Store Mutation*: A `project_script` subprocess is a stateless fact producer. It **must never** write directly to the per-project machine store (`<PM_MCP_BASE>/projects/<project_id>/`, outside its Landlock write set anyway), `.marshall/orchestrator/`, or `.marshall/config/`. All persistence is performed by the daemon after validating the script's JSON output.
2. *Operator Enrolment Precondition*: Every `project_script` (and its runtime interpreter, such as a pinned `python3` binary) must be enrolled by the operator in the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (`project_scripts.<project_script_id>`, link:store-schemas.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]) with its repository-relative script path, expected SHA-256 content hash, interpreter, maximum timeout (`max_timeout_seconds`, the budget of every run, link:timeouts.adoc#project-script-budget[Timeouts & Budgets Specification]), its binding (`worker_kind` ∈ `finalize_step`, `recipe_harvester`, `log_parser`, `module_discovery`, `edge_resolver`, and `target`, the step id, recipe key, or build system it serves), and its `argument_schema` (an inline JSON Schema, validated as a schema at enrolment, against which the runtime validates the arguments of every run, `PM-EXT-5`). A job that uses a script for another worker kind or target than its binding is refused. If a script file is modified in the working tree without re-enrolment, the verify-not-resolve digest check rejects execution with job outcome `refused`.

== Configuration Split (Team Files, Operator Files & Enrolment, Server State)
_See Requirement link:../Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

In the legacy architecture, `.plan/marshal.json` and `.plan/local/run-configuration.json` mixed declarative project settings, operator posture, frozen extension hook snapshots (`skill_domains`), overridable shell commands (`verify_command`), language-server argument vectors, server bookkeeping, and learned runtime timeouts inside workspace files that the model's file/shell tools could modify.

`PM-MCP` keeps none of these files and imports nothing from them: it never reads or writes `.plan/` (`PM-MIG-2`) and enforces a fundamental security invariant: **Nothing that decides what binary or argument vector executes on the host may be read from a file the model can write.** Configuration and operational state are partitioned by owner class across strictly separated stores, and every file has exactly one owner class: *team* (git-tracked, shared through the repository), *operator* (machine-local, written only through the operator channel), or *server* (machine-local state and caches). A value the server can observe or derive is never configured (link:store-schemas.adoc#derived-facts[Store Schemas Specification, Derived Facts Store]); a tuning value that calibrates a server algorithm is a compiled constant (link:timeouts.adoc#configuration-keys[Timeouts & Budgets Specification, Configuration Keys]); an option whose only effect is to weaken a guarantee does not exist.

=== Tier 1: Git-Tracked Team Configuration (`.marshall/config/`)
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-29[PM-WATCH-EXT-29]_

1. *No Frozen Hook Snapshots*: Unlike `plan-marshall`'s `.plan/marshal.json`, no team file stores frozen hook outputs (skill lists, globs, recipes, `bundle`, `outline_skill`, `workflow_skill_extensions`). The compiled-in domain descriptors in `pm-mcp` are authoritative; domain activation and active profiles are derived (`setup.detect-domains`, per-module Axis-A applicability), and `domains.json` holds only overrides where the derivation is wrong for the repository (`enabled`, `always_on`, `file_globs`, `disabled_profiles`).
2. *No Default Seeding*: Team files are sparse: no compiled default and no domain default is ever written into them. A domain descriptor contributes no `config_defaults` map; its defaults are compiled defaults of the effective configuration (link:store-schemas.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]). `plan-marshall`'s per-domain `project_skills` key does not exist: `PM-MCP` serves only compiled skills, and project automation enters as project-local recipes or enrolled `project_script` steps (whether project-local vocabulary skills become a feature is an open question of the client and CLI topic).
3. *Derived Providers & Origin Pinning*: The version-control provider is always `git`; the CI provider is derived from the remote host (derived fact `ci_provider`), overridable only by `project.json` `ci_provider` for self-hosted remotes; whether an integration runs natively or through its CLI is operator posture (`local-config.json` `integrations.<integration>.variant`, <<setup-integration-variants>>), never a team key, because it decides whose credentials act; code-quality integrations (Sonar) are configured under `project.json` `integrations`, because their coordinates are project facts the server cannot observe. For token-lane REST providers (`PM-CRED-2`), a team file only references the credential key; it never decides where a token is sent. The single issuing origin to which the daemon's REST client restricts authentication headers is the origin of the operator-owned credential entry's `url` (`https://`, `PM-CRED-5`), never a value from a model-writable team file (forbidding cross-origin or HTTP downgrade redirects). A provider `verify_command` is never read from a team file; an override is an enrolment `verify_argv` (Tier 2).
4. *One Owner per Key*: Operator posture (integration variants, commit identity, continuation default, merge consent, interaction mode, language, commit trailer, effort ladder, retention) never appears in a team file; a team file that carries it fails validation with `unknown_config_key`.

[#enrolled-argument-templates]
=== Tier 2: Enrolled Argument Templates & Slot Cap (`<PM_MCP_BASE>`)

To prevent argument injection without requiring the operator to re-enrol the project every time a new module is added, build enrolment binds wrappers and host tools to **typed argument templates** defined by domain support. The templates live in the project's enrolment file (`build.canonical_templates.<build_system>.<verb>` and `build.discovery_templates.<build_system>.<name>`, link:store-schemas.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]); they decide what a build job runs, and no separate goal allowlist exists:

[source,json]
----
{
  "build": {
    "canonical_templates": {
      "maven": {
        "module-tests": ["test", "-pl", "{module}"],
        "quality-gate": ["verify", "-DskipTests", "-pl", "{module}"],
        "verify": ["verify", "-P{profile}", "-pl", "{module}"]
      }
    },
    "discovery_templates": {}
  }
}
----

* **Typed Placeholder Validation at Job Time**: When the daemon constructs a build job, it substitutes `{module}` and `{profile}` and validates them against its own cached module discovery snapshot (`{module}` must be a discovered module path/coordinate in the repository; `{profile}` must be a profile declared in that module's build descriptor).
* **Enrolled Template Precedence**: An enrolled template for a canonical verb replaces the compiled default template for that project; every build job record names the template source (`enrolled` or `compiled_default`), which `pm-mcp status` shows; build representations and `pm_build` results never carry it (link:hypermedia-format.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). Templates are never read from a team configuration file (`PM-EXT-6`).
* **Forbidden Free Flags**: Arbitrary user- or model-supplied flags—specifically `-D`, `-f`, `--file`, `-s`, `--settings`, `--init-script`, or shell metacharacters—are never accepted in canonical build jobs. Flags that repository files inject (`.mvn/maven.config`, `.mvn/jvm.config`, `gradle.properties`) are not filtered here; those files are pinned by the wrapper enrolment and refuse the build when changed (link:job-runtime.adoc[Job Runtime Specification], Verify-Not-Resolve).
* **Machine-Wide Slot Cap & Source Discrimination**: `machine-config.json` holds `max_build_slots`. On every build submission, the scheduler resolves the cap and records both the value and its resolution `source` (`machine_config`, `default`, `invalid`, or `unreadable`) in the job record and `pm-mcp status`, never in a tool result; `invalid` and `unreadable` configuration files are surfaced explicitly in diagnostics and never silently folded into `"default"`.

=== Tier 3: Adaptive Build Timeouts & Crash-Replay State

The daemon maintains learned operational metrics and job journals in Tier 3 server state:

1. *Adaptive Timeout Learning (`build-timings.json`)*: One store per project, `<PM_MCP_BASE>/projects/<project_id>/build-timings.json` (link:store-schemas.adoc#build-timings-store[Store Schemas Specification, Build Timings Store]), keyed by canonical budget key (for build jobs the normalized canonical command `(build_system, canonical_verb, module_id, sorted_profiles)`); no repository-local and no machine-level timeout store exists, so a moved checkout keeps its budgets. The server maintains a max-biased learned baseline from observed run durations and allocates each job budget from it; the per-engine floors are never violated, also not by an operator budget, which may exceed the escalation cap but is clamped up to the floor. Which runs feed the baseline is defined in link:job-runtime.adoc#_adaptive_timeout_learning[Job Runtime Specification, Adaptive Timeout Learning]; the blend, the floors, the allocation, the escalation budget and its cap, operator budgets, and `budget_derivation` are defined only in link:timeouts.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets].
2. *No Inherited Timeouts*: Every learned value starts from the project's own finished runs under `PM-MCP`; learned timeouts of legacy `plan-marshall` (`.plan/local/run-configuration.json`) are never read or imported (`PM-MIG-2`). Until a key has a learned value, its budget is the floor default (link:timeouts.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]).
3. *Gate Honesty & Examined Population Tracking*: Before a green build or quality gate clears open findings in `findings.jsonl`, the server's compiled log and report parsers verify that for Maven and Gradle the build log explicitly contains the engine's terminal success marker (e.g., `BUILD SUCCESS` / `BUILD SUCCESSFUL`) in addition to exit code `0`, and that the tool examined a non-empty file/test population capable of reaching the finding's file and category (e.g., `mypy` gates run with `--no-incremental` / cache disabled so untouched files with broken cross-module types are not skipped).
4. *Crash Replay & Atomic Fate Recording*: Every spawned job is recorded in the daemon's write-ahead job journal, one job record `<PM_MCP_BASE>/projects/<project_id>/jobs/<job_id>.json` per job (link:store-schemas.adoc#job-record[Store Schemas Specification, Job Record]), prior to `ProcessBuilder.start()`. Request status (`running`) is never treated as terminal fate; terminal fate (`succeeded`, `failed`, `failed_unparsed`, `timed_out`, `cancelled`, `killed`, `indeterminate`), derived by link:job-runtime.adoc#outcome-derivation[Job Runtime Specification, Outcome Derivation], is written atomically at process termination; `refused` is written atomically when the job is refused before spawn, so no journal entry of a refused job ever reaches `ProcessBuilder.start()`. If the daemon restarts while a job record is still `running`, journal replay marks the orphaned job `killed` ("do not retry blindly") and attaches no synthetic error findings.

[#config-upgrades]
== Configuration Validation & Upgrades Before 1.0 (`PM-EXT-7`)
_See Requirement link:../Requirements.adoc#PM-EXT-7[PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades]_

In legacy `plan-marshall`, schema and default updates to `.plan/marshal.json` were split across ad-hoc hooks inside `manage-config.py -> sync-defaults` (`RETIRED_STEP_KEY_RENAMES`, `run_at_all -> lane`, lane materialization), separate CLI canonicalizers (`steps-sort`, `normalize-keys`), and one-shot subcommands in `marshall-steward/scripts/upgrade.py` (`migrate-bot-lists`, `validate-bot-lists`). Every new migration required adding prose instructions to `upgrade-flow.md` that the LLM had to read into its context window and execute via separate `Bash` calls—polluting the model's Chain of Thought (CoT) with historical schema trivia even on already-current repositories. The seeding, sorting, and offered-step bookkeeping existed only to keep a materialised copy of compiled defaults consistent.

`PM-MCP` has none of this machinery. Team files are sparse and hold no defaults, so there is nothing to seed, sync, sort, normalize, or offer through a ledger; there is no `system` block, no seed fingerprint, no migration chain (`ConfigMigrationCommand`, `ConfigReconciler`), and no startup migration. It never reads, converts, or upgrades a legacy `.plan/marshal.json` (`PM-MIG-2`).

=== 1. One Version Rule for Every File Kind
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-21[PM-WATCH-EXT-21]_

Every team configuration file, the operator's `local-config.json`, every enrolment and credential file, every server store, and every workflow unit declares its format version (`format_version`, or the `format` of a unit header). Before 1.0 a binary accepts exactly the current version of each kind and refuses any other with `format_outdated` or `format_newer` naming the file (link:store-schemas.adoc#format-versioning[Store Schemas Specification, Format Versioning]); a reader never rewrites a file. The migration mechanism for 1.0 and later (one mechanism for every file kind) is decided at 1.0 with the knowledge of the actual format churn.

=== 2. Validation on Every Read & the Effective Configuration

Every computation of the effective configuration (at `pm_start`, phase handshakes, `pm-mcp enter`, and `setup.reconcile-config`) parses the team files and the operator file against their closed schemas, applies the server-side rules of each key, loads and verifies the project's workflow units (link:workflow-dsl.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]), resolves every value along its chain (team or operator file, derived fact, compiled default), and publishes the result with per-key sources as `pm://project/config` (link:store-schemas.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]). A non-object root fails before any field access. Unknown keys are `unknown_config_key` findings naming the key path, never silently kept as unread settings; a setup or config link that would write an undeclared key is refused (`invalid_link_args`). Review-bot tokens are checked against the registered bot kinds (`unregistered_kind`) and effort keys against the role registry (`PM_MCP-100`).

=== 3. Upgrade Path: Drain, Release Notes, Offered Default Changes
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-22[PM-WATCH-EXT-22]_

A new binary reaches a project in three ways, none of which rewrites a file silently:

. *New compiled defaults* take effect at once for every key a team or operator file does not set, because the files are sparse. In-flight plans stay on their bound snapshot (§ 5).
. *A `format_version` bump* of a file kind is listed in the release notes with the changed keys. Scope stores of in-flight plans follow the drain rule: `pm-mcp drain` reports the live scopes, and the operator finishes them before upgrading. For a team JSON file the binary refuses (`format_outdated`), `setup.reconcile-config` offers a server-rendered rewrite at the current format: every key still valid is carried over, every key the new schema no longer admits is listed by name as dropped, and the rewrite is shown as a diff and lands only through `setup.commit-changes`. An operator file is refused by the CLI naming the file and the changed keys, and the operator sets the keys again through `pm-mcp operator config`.
. *Changed default workflow units* are offered in `setup.offer-new-steps` as a three-way diff: from the default revision the project unit was derived from (`derived_from` in the unit header) to the binary's current default revision, applied to the project's unit. `adopt` applies the hunks and advances `derived_from`; `decline` advances `derived_from` without applying them, so a declined change is never offered again, and a step the team removed from its unit is never restored (only hunks between two default revisions are ever offered). The resulting unit is verified like every project unit before it can land.

=== 4. Anti-CoT-Clutter Guarantees

To ensure configuration upgrades never degrade model reasoning or bloat context windows:

1. *Zero Migration Prose in Skills (`PM-SKILL-1`, `PM-EXT-7`)*: No vocabulary skill (`skill://pm/...`) or workflow state prompt ever instructs the model to run `sync-defaults`, `steps-sort`, `normalize-keys`, or `migrate-*` commands, nor mentions retired configuration keys (`enabled_bots`, `run_at_all`, `default:automated-review`, `skill_domains`).
2. *Silent Fast-Path When Current*: At `pm_start`, phase handshakes, and `pm-mcp enter`, the server compares the digests of the team files, the operator file, the project's workflow units, the derived facts, and the compiled defaults with those of the last validated effective configuration; when they match, verification completes in memory and emits **zero** facts, links, or warnings into the state representation.
3. *Upgrades Only in the Setup Workflow*: Offered default changes and format rewrites happen only in `project-setup` (`setup.reconcile-config`, `setup.offer-new-steps`), whose receipt lists only non-empty deltas (`format_refusals[]`, `rewrites[]`, `unit_changes_offered[]`, `findings[]`).

[#config-snapshot]
=== 5. Three-Surface Synchronization (In-Flight `execution-manifest.json` Snapshot & Adoption)

An in-flight plan (Phases 4–6) executes against the configuration snapshot bound at composition. `config_hash` is computed over the effective configuration: every effective value with its source, the compiled defaults, the derived facts the values rest on, the team files, the operator file, and the process DSL units the plan's lifecycle loads (link:store-schemas.adoc#project-configuration-store[Store Schemas Specification, Project Configuration] item 6), never over raw file bytes alone, so a binary upgrade that changes a default would otherwise silently change in-flight plans. Whenever an edit, a changed derived fact, a changed workflow unit, or a new binary changes it, the next phase handshake (`phase-workflows.adoc`, Outside-World Invariants) detects that the plan's recorded `config_hash` differs and runs `ExecutionManifestResolver` in-process to compose a candidate: an identical candidate is adopted silently; a differing one raises the `config_drift` condition on the phase entry state (`adopt` / `keep`, audited; link:state-catalogue.adoc#condition-config_drift[State Catalogue, Conditions]). A candidate whose workflow units no longer contain the plan's current state or an entry of its `call_stack` offers only `keep`. The manifest records its `composed_inputs` (`config_hash`, `realized_footprint_digest`, `change_type`, `providers_digest`); at Phase 6 entry the resolver re-computes every recorded input: a difference in the plan's own inputs (`realized_footprint_digest`, `change_type`, `providers_digest`) re-composes the manifest and records the changed inputs in the audit record of the re-composition, a difference in `config_hash` follows the adoption rule above, and an input the resolver cannot re-derive is listed as `unchecked` in that record, never omitted; neither the hashes nor the changed inputs are rendered, because the re-composition needs no model decision (the `config_drift` condition renders its manifest diff). `config_hash` reads the configuration of the plan's current location (the worktree copy of `.marshall/config/` from Phase 5 on), so a deliverable that edits a configuration file or workflow unit re-composes the manifest at the next handshake.

=== 6. Build-Time Verification

JUnit 5 build tests in `pm-mcp-core` enforce:

** Every configuration schema is closed at every level and valid JSON Schema (draft 2020-12); the compiled default table satisfies it.
** Every default workflow unit passes Rules 1–12 and the compiled invariants (link:workflow-dsl.adoc#project-owned-units[Workflow DSL Specification]), and the invariant checker refuses a fixture set of weakened units (a mandatory step removed, the push barrier bypassed, the Q-Gate removed from a phase that requires it).
** A three-way default-unit offer never re-adds a hunk the fixture project removed, and a declined offer is not repeated.
