== Overview

This document specifies the four-axis domain extension architecture (Axes A–D), provenance-preserving dependency edge and path-attribution merge algorithms, server-owned module discovery and `derive-verification` build map, architecture query resources and enrichment workflow, declarative recipe engine with Tier-1 init scoring, out-of-process `project_script` execution contract, and the normative three-way configuration split for *plan-marshall-mcp* (`PM-MCP`).

In the legacy script-and-prose architecture, domain extensions were implemented as in-process Python classes (`extension.py`) discovered via `importlib` even though roughly 80% of their surface returned constant metadata, while `marshal.json` mixed git-tracked project preferences, frozen hook snapshots, and executable command overrides. `PM-MCP` replaces dynamic code loading with a closed-world native design: declarative domain descriptors paired with sealed Java axis interfaces in `pm-mcp-core`, permanent out-of-process `project_script` jobs for project-local and custom domain code, and a strict security boundary separating git-tracked project settings from operator enrolment and server-managed runtime state.

== Four-Axis Domain Architecture (Axes A–D, ADR-004 / ADR-013)
_See Requirement link:../Requirements.adoc#PM-EXT-1[PM-EXT-1: Four-Axis Domain Descriptors (Axes A–D)]_

_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-1[PM-WATCH-EXT-1]_

To comply with the GraalVM native-image closed-world constraint (`PM-TECH-3`), `PM-MCP` eliminates runtime `importlib` plugin loading. Built-in domains (`java`, `java-cui`, `javascript`, `javascript-cui`, `python`, `oci-containers`, `documentation`, `requirements`, `plan-marshall-plugin-dev`, `general-dev`) and organization data packs are represented by declarative JSON descriptors (`classpath:/domains/<domain_id>.json`) bound to four orthogonal, sealed Java interfaces corresponding to Axes A through D (ADR-004, ADR-013). Axis B is the exception: the file-to-build contract is owned by build-system extensions, not by language or content domains (ADR-004), so it is declared by build-system descriptors (`classpath:/build-systems/<build_system_id>.json` for `maven`, `gradle`, `npm`, and `pyproject`), each naming the domain key its routes are filed under in `build.map`.

The axis split mirrors `plan-marshall` (`script-shared/scripts/extension/extension_base.py`: `ExtensionBase` owns Axis A — `get_skill_domains`, `applies_to_module`, `config_defaults`, and the `provides_*` hooks; `BuildExtensionBase` owns Axis B — `classify_globs`, `classify_paths`, `classify_path_specificity`, `classify_build_class`; `DerivationResolverBase` and `PathAttributionBase` own Axes C and D; ADR-004, ADR-013), verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing.

=== Core Architectural Invariants
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-23[PM-WATCH-EXT-23]_

1. *Fail-Closed Descriptor Loading (ADR-017)*: A validator derives its contract from the target's own declaration and fails closed when it cannot. Unlike the legacy catch-all that silently ignored broken `extension.py` modules, `PM-MCP` validates every compiled and project-local descriptor against its closed JSON Schema at startup. Any schema violation or unresolvable skill/resolver reference causes an immediate, explicit diagnostic failure rather than silent degradation.
2. *Null-on-Absent Never Fabricates a Positive (ADR-010)*: When a domain is inactive or does not declare an optional capability (such as an architecture fitness gate or a domain verb like `marker-detect` or `rewrite-log-parse`), that capability is omitted from representations (`null` / absent). Conversely, if an active domain promises a mandatory gate that cannot execute, the engine halts with a diagnosable refusal (`refused`) and **never** records a synthetic pass.
3. *Security Profile Resolution Constraint*: The `security` profile in `skills_by_profile` resolves focused security vocabulary skills (`skill://pm/domain/<domain>/security`) for implementation, review, and audit states; it **never** generates standalone implementation tasks of its own.
4. *Technique Preconditions*: A prescriptive section of a domain vocabulary skill may declare a precondition in the descriptor's `technique_preconditions`, using the Axis A `applies_to_module` predicate grammar (build system, dependency coordinates, path and file globs). The server evaluates it against the project's discovered modules at render time; when no module satisfies it, the renderer emits that section marked "available technique, not adopted in this project" instead of as binding guidance (link:client-profiles.adoc#_rendering_invariants[Client Profiles Specification, Rendering Invariants]), and the rendered digest (`PM-SKILL-2`) reflects the result. Every section that prescribes the same `technique` declares the same precondition, so the technique's status is identical in every skill that carries it; the descriptor loader refuses a technique with diverging preconditions.

    Map<String, List<String>> skillsByProfile();

     * Evaluates the domain's declarative applicability rules (applies_to_module) against a
     * discovered module's facts: decides whether the domain applies to the module, which
     * profiles activate, and which optional skills are promoted. Also gates whether the
     * routes filed under this domain are seeded into build.map (ADR-004).

    Optional<OutlineExtensionSpec> outlineExtension();

    Optional<ArchGateDeclaration> archGateDeclaration();

    Set<String> domainVerbs();

/**
 * Axis B: File-to-build classification, owned by build-system extensions
 * (maven, gradle, npm, pyproject), never by language/content domains (ADR-004).
 * Classifies changed paths into (role, build_class) build-map routes that
 * resolve to canonical build commands; it decides no module applicability.
 */
public sealed interface BuildRoutingAxis permits DeclarativeBuildSystemAxisB {

    String buildSystemId();

    /** Domain key under which this build system's routes are filed in build.map. */
    String servedDomainKey();

    /**
     * Explicit (glob, role) build-map routes (classify_globs); role is production, test,
     * or config. Globs are single-* fnmatch patterns or bare basenames, never recursive **.
     */
    List<BuildMapRoute> classifyGlobs();

    /**
     * Build class of a claimed (path, role) pair (classify_build_class): production -> compile,
     * test -> module-tests, config -> verify, any other role -> none, unless the build system
     * overrides the default for a specific path.
     */
    BuildClass classifyBuildClass(String path, BuildMapRole role);

    /**
     * Classifies changed paths into (role, build_class) routes of this build system, with the
     * non-wildcard segment count of the matching glob as longest-glob-wins specificity
     * (classify_paths, classify_path_specificity). Paths matching no route are omitted.
     */
    List<ClassifiedPathRoute> classifyPaths(List<String> changedPaths);

    /** Maps canonical verbs (clean..package, module-tests, quality-gate, verify) to argument templates. */
    Map<CanonicalBuildVerb, ArgumentTemplate> canonicalCommandTemplates();

    /** Maps discovery operations to enrolled argument templates. */
    Map<String, ArgumentTemplate> discoveryCommandTemplates();
}

/**
 * Axis C: Directed module dependency edge derivation with explicit resolver identity (ADR-013, ADR-014).
 */
public sealed interface EdgeDerivationAxis
        permits MavenEdgeResolver, GradleEdgeResolver, NpmEdgeResolver,

                MarkdownCrossRefResolver, DocumentationCrossRefResolver,

    /** Stable, unique resolver ID ("maven", "gradle", "npm", "pyproject", "python", "markdown", "documentation", "lsp"). */
    String resolverId();

    /** Derives directed inter-module dependency edges; never activated by file pattern, only by explicit resolverId. */
    ResolverExecutionResult deriveEdges(WorkspaceDiscoveryContext context);
}

 * Axis D: Repository subtree path-prefix ownership claims (ADR-013, ADR-014).
 */
public sealed interface PathOwnershipAxis permits DeclarativeDomainAxisD {

    /** Stable attributor ID stamped onto every claim's producers and onto its AttributorReport. */
    String attributorId();

     *
     * @throws AttributorException when the attributor cannot produce its claims; the merge
     *         reports it and continues with the sibling attributors

    PathClaimSet claimPaths() throws AttributorException;

The Axis C resolver IDs mirror `plan-marshall` (`derivation_resolver_id()` of `build-maven`, `build-npm`, `build-pyproject`, `pm-dev-python`, `pm-plugin-development`, `pm-documents`, and `plan-marshall-plugin`), verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing. `pyproject` (declared-dependency join) and `python` (import join) stay distinct IDs so an edge's provenance tells the two derivations apart; `markdown` and `documentation` read overlapping file types over different module corpora, and an edge both find carries both IDs. *Deliberate addition vs. `plan-marshall`*: the `gradle` resolver (`GradleEdgeResolver`) has no `plan-marshall` counterpart (`build-gradle` ships no derivation resolver).

*Machine-local resolver enablement*: Which discovered resolvers run is a machine-local binding, because a resolver's availability and cost depend on locally installed tooling (the `lsp` resolver needs an enrolled language server). The binding `derivation_resolvers.<resolver_id>.enabled` lives per project in `~/.plan-marshall/mcp/machine-config.json` (Tier 2, written via `pm-mcp operator config`), mirroring `plan-marshall`'s `derivation_resolvers` section of `.plan/local/run-configuration.json`. An absent section, absent entry, or malformed entry means *enabled*; only an explicit `false` disables a resolver. A disabled resolver is still discovered and reported (status `NOT_DISPATCHED`, reason `DISABLED`, zero edges), never pruned from the report, and is not counted as having run.

== Provenance-Preserving Merge Algorithms (ADR-014)
_See Requirement link:../Requirements.adoc#PM-EXT-2[PM-EXT-2: Provenance-Preserving Edge Derivation & Path Attribution Merges]_

When multiple domains and resolvers are active in a repository, `PM-MCP` merges their module dependency edges (Axis C) and path-prefix ownership claims (Axis D) using deterministic, order-independent algorithms ported from `_derivation_merge.py` and `_path_attribution_merge.py` (ADR-014; `extension-api/scripts/`, verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing). Neither merge ever throws or aborts on a producer's output: a producer that fails is reported and its siblings still contribute, and every candidate the merge drops is recorded as a note prefixed `merge: ` on the producer's own report, so a dropped candidate is never silent and is always distinguishable from the producer's own notes.

=== Edge Derivation Merge (`DerivationMerge`)
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-5[PM-WATCH-EXT-5]_

The edge derivation merge combines directed inter-module edges $(u \to v)$ from all explicitly activated Axis-C resolvers while preserving full producer provenance and distinguishing "zero edges found" from "resolver did not run":

1. *Activation by Explicit Resolver ID*: Resolvers are invoked strictly by their `resolverId` (never implicitly by file extension). A resolver disabled by the machine-local `derivation_resolvers` binding is not invoked; the caller folds in a `ResolverExecutionResult` with status `NOT_DISPATCHED` and reason `DISABLED`, which is reported with zero edges and excluded from the count of resolvers that ran.
2. *Idempotent Union with Provenance*: Multiple resolvers discovering the same directed edge $(u, v)$ are merged into a single `MergedDependencyEdge` record whose `resolverIds` set is the sorted union of all contributing resolver IDs. A resolver's `contributedEdgeCount` counts its distinct accepted pairs.
3. *Reported Drops*: Self-edges $(u, u)$ and edges naming a module outside the discovered module set are dropped, each with a `merge: ` note on the producing resolver's report.
4. *Explicit Non-Run Reporting for LSP & External Resolvers*: An `LspSymbolEdgeResolver` (or `ProjectScriptEdgeResolver`) that could not execute **never returns an empty edge list masquerading as a clean scan**. Instead, it returns a `ResolverExecutionResult` with status `NOT_RUN` and an explicit `NonRunReason` (`ABSENT`, `FAILED_TO_START`, `TIMEOUT`, `UNSUPPORTED`).

[source,java]
----
package de.cuioss.pm.mcp.core.architecture;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.TreeMap;
import java.util.TreeSet;

public final class DerivationMerge {

    private static final String MERGE_NOTE = "merge: ";

    public enum ResolverStatus { RAN, NOT_RUN, NOT_DISPATCHED }

    public enum NonRunReason { NONE, ABSENT, FAILED_TO_START, TIMEOUT, UNSUPPORTED, DISABLED }

    public record RawEdge(String fromModule, String toModule, String detail) {}

    public record ResolverExecutionResult(
            String resolverId,
            ResolverStatus status,
            NonRunReason nonRunReason,
            String diagnosticMessage,
            List<RawEdge> edges,
            List<String> notes          // the resolver's own suppression notes
    ) {}

    public record MergedDependencyEdge(
            String fromModule,
            String toModule,
            List<String> resolverIds,
            Map<String, List<String>> detailsByResolver
    ) {}

    public record ResolverStatusReport(
            String resolverId,
            ResolverStatus status,
            NonRunReason nonRunReason,
            String diagnosticMessage,
            int contributedEdgeCount,   // distinct accepted (from, to) pairs
            List<String> notes          // resolver notes followed by "merge: " drop notes
    ) {}

    public record DerivationMergeResult(
            List<MergedDependencyEdge> edges,
            List<ResolverStatusReport> resolverReports,
            int dispatchedResolverCount // excludes NOT_DISPATCHED reports
    ) {}

    public DerivationMergeResult merge(
            Set<String> knownModules,
            List<ResolverExecutionResult> results) {

        record EdgeKey(String from, String to) implements Comparable<EdgeKey> {
            @Override
            public int compareTo(EdgeKey o) {
                int c = this.from.compareTo(o.from);
                return c != 0 ? c : this.to.compareTo(o.to);
            }
        }

        Map<EdgeKey, TreeSet<String>> provenance = new TreeMap<>();
        Map<EdgeKey, Map<String, TreeSet<String>>> details = new TreeMap<>();
        Map<String, ResolverStatusReport> reports = new TreeMap<>();

        for (ResolverExecutionResult res : results) {
            List<String> notes = new ArrayList<>(res.notes());
            if (res.status() != ResolverStatus.RAN) {
                reports.put(res.resolverId(), new ResolverStatusReport(
                        res.resolverId(), res.status(), res.nonRunReason(),
                        res.diagnosticMessage(), 0, List.copyOf(notes)));
                continue;
            }
            Set<EdgeKey> contributed = new TreeSet<>();
            for (RawEdge edge : res.edges()) {
                if (edge.fromModule().equals(edge.toModule())) {
                    notes.add(MERGE_NOTE + "dropped self-edge (" + edge.fromModule() + " -> "
                            + edge.toModule() + ") - a module does not depend on itself");
                    continue;
                }
                List<String> unknown = new ArrayList<>();
                if (!knownModules.contains(edge.fromModule())) {
                    unknown.add(edge.fromModule());
                }
                if (!knownModules.contains(edge.toModule())) {
                    unknown.add(edge.toModule());
                }
                if (!unknown.isEmpty()) {
                    notes.add(MERGE_NOTE + "dropped edge (" + edge.fromModule() + " -> " + edge.toModule()
                            + ") - unknown module endpoint(s): " + String.join(", ", unknown));
                    continue;
                }
                EdgeKey key = new EdgeKey(edge.fromModule(), edge.toModule());
                contributed.add(key);
                provenance.computeIfAbsent(key, k -> new TreeSet<>()).add(res.resolverId());
                if (edge.detail() != null && !edge.detail().isBlank()) {
                    details.computeIfAbsent(key, k -> new TreeMap<>())
                            .computeIfAbsent(res.resolverId(), r -> new TreeSet<>())
                            .add(edge.detail());
                }
            }
            reports.put(res.resolverId(), new ResolverStatusReport(
                    res.resolverId(), ResolverStatus.RAN, NonRunReason.NONE,
                    res.diagnosticMessage(), contributed.size(), List.copyOf(notes)));
        }

        List<MergedDependencyEdge> mergedEdges = provenance.entrySet().stream()
                .map(entry -> {
                    EdgeKey k = entry.getKey();
                    Map<String, List<String>> detMap = new LinkedHashMap<>();
                    details.getOrDefault(k, Map.of())
                            .forEach((r, s) -> detMap.put(r, List.copyOf(s)));
                    return new MergedDependencyEdge(
                            k.from(), k.to(), List.copyOf(entry.getValue()), Map.copyOf(detMap));
                })
                .toList();

        int dispatched = (int) reports.values().stream()
                .filter(r -> r.status() != ResolverStatus.NOT_DISPATCHED)
                .count();

        return new DerivationMergeResult(mergedEdges, List.copyOf(reports.values()), dispatched);
    }
}

=== Path Attribution Merge & Collision Rejection (`PathAttributionMerge`)

The path attribution merge combines Axis-D `claim_paths` claims across active attributors and resolves repository-relative file paths to their owning module via longest-prefix matching:

1. *Single Shared Spelling Normalizer (`normalizeSpelling`)*: Claim registration and file lookup pass through the exact same normalizer. Normalization is spelling-only: it trims surrounding whitespace, folds backslashes to `/`, strips leading `./` runs, and strips trailing slashes. It resolves no symlink, touches no filesystem, does not collapse `..` segments, does not strip a leading `/`, and does not collapse `//`; whether a path is admissible is a policy decision of each side, not a spelling decision.
2. *Claim Validity Filters (Drop and Report, Never Throw)*: A claim survives only if it is well-formed (non-null prefix and module), its normalized prefix bounds a subtree inside the repository, and its `target_module` is a known module (a discovered module or a registered synthetic domain module such as the one owning `.plan`). A blank or root-level prefix (`""`, `.`, `..`, or a bare `/`) and a prefix whose first normalized segment is `..` are dropped; a merely dot-relative prefix (`./doc`) is normalized to `doc`, not dropped. Every dropped claim appends a `merge: ` note naming the claim and the reason to the claiming attributor's report.
3. *Failing Attributor Isolation*: An attributor whose `claimPaths()` throws `AttributorException` is reported with status `ERROR`, `claimCount` `0`, and a note carrying the failure; it contributes no claims, and its siblings still contribute. A failing attributor never aborts the merge.
4. *Collision Without Winner Invariant*: If two attributors claim the same normalized `path_prefix` for **different** `target_module` IDs, the merge **never selects an iteration-order winner**. Instead, the collided `path_prefix` yields no claim, is recorded as a `PathClaimCollision` diagnostic, and every contending attributor receives a `merge: ` note naming all contending modules. Identical claims `(same prefix, same target_module)` merge idempotently into one claim carrying the sorted union of producer IDs. Differently-scoped prefixes (`.plan` and `.plan/local`) are not a collision.
5. *Per-Attributor Report*: Every attributor yields exactly one `AttributorReport(attributorId, status, claimCount, notes)`, where `claimCount` counts the surviving (non-collided) claims it produced. Zero attributors is a first-class outcome (empty claims, empty reports, never an exception); the report count distinguishes "no attributor ran" from "attributors ran and none claimed the path".
6. *Segment-Boundary Longest-Prefix Lookup*: A spelling-normalized file path `p` matches a claimed prefix `c` if and only if `p.equals(c)` or `p.startsWith(c + "/")`, so `.plans/x` never resolves through a `.plan` claim. Among all matching claims, the longest prefix wins; this is resolution order, not a collision tie-break.

[source,java]
----
package de.cuioss.pm.mcp.core.architecture;

import de.cuioss.pm.mcp.core.domain.AttributorException;
import de.cuioss.pm.mcp.core.domain.PathClaimSet;
import de.cuioss.pm.mcp.core.domain.PathOwnershipAxis;
import de.cuioss.pm.mcp.core.domain.PathOwnershipClaim;

import java.util.ArrayList;
import java.util.Collections;
import java.util.Comparator;
import java.util.HashMap;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.Set;
import java.util.TreeMap;
import java.util.TreeSet;

public final class PathAttributionMerge {

    private static final String MERGE_NOTE = "merge: ";

    private static final Set<String> ROOT_LEVEL_PREFIXES = Set.of("", ".", "..");

    public enum AttributorStatus { OK, ERROR }

    public record ActivePathClaim(String normalizedPrefix, String targetModule, List<String> producers) {}

    public record PathClaimCollision(String normalizedPrefix, Map<String, List<String>> producersByTargetModule) {}

    public record AttributorReport(String attributorId, AttributorStatus status, int claimCount, List<String> notes) {}

    public record AttributionTable(
            List<ActivePathClaim> claimsByDescendingLength,
            List<PathClaimCollision> collisions,
            List<AttributorReport> attributorReports
    ) {
        public Optional<ActivePathClaim> attributePath(String rawFilePath) {
            String norm = normalizeSpelling(rawFilePath);
            for (ActivePathClaim claim : claimsByDescendingLength) {
                String prefix = claim.normalizedPrefix();
                if (norm.equals(prefix) || norm.startsWith(prefix + "/")) {
                    return Optional.of(claim);
                }
            }
            return Optional.empty();
        }
    }

    /** Spelling-only normalizer shared by the claim side and the lookup side. */
    public static String normalizeSpelling(String raw) {
        String p = raw.strip().replace('\\', '/');
        while (p.startsWith("./")) {
            p = p.substring(2);
        }
        int end = p.length();
        while (end > 0 && p.charAt(end - 1) == '/') {
            end--;
        }
        return p.substring(0, end);
    }

    /** Identity key of a claimed prefix; empty when the prefix bounds no subtree inside the repository. */
    static Optional<String> normalizePrefix(String raw) {
        String p = normalizeSpelling(raw);
        if (ROOT_LEVEL_PREFIXES.contains(p) || "..".equals(p.split("/", 2)[0])) {
            return Optional.empty();
        }
        return Optional.of(p);
    }

    public AttributionTable buildTable(Set<String> knownModules, List<PathOwnershipAxis> attributors) {
        record ClaimKey(String prefix, String module) implements Comparable<ClaimKey> {
            @Override
            public int compareTo(ClaimKey o) {
                int c = this.prefix.compareTo(o.prefix);
                return c != 0 ? c : this.module.compareTo(o.module);
            }
        }

        Map<ClaimKey, TreeSet<String>> producers = new TreeMap<>();
        Map<String, AttributorStatus> statusById = new LinkedHashMap<>();
        Map<String, List<String>> notesById = new HashMap<>();

        for (PathOwnershipAxis attributor : attributors) {
            String id = attributor.attributorId();
            PathClaimSet declared;
            try {
                declared = attributor.claimPaths();
            } catch (AttributorException e) {
                statusById.put(id, AttributorStatus.ERROR);
                notesById.put(id, new ArrayList<>(List.of("claimPaths() failed: " + e.getMessage())));
                continue;
            }
            statusById.put(id, AttributorStatus.OK);
            List<String> notes = new ArrayList<>(declared.notes());
            for (PathOwnershipClaim claim : declared.claims()) {
                if (claim == null || claim.pathPrefix() == null || claim.targetModule() == null) {
                    notes.add(MERGE_NOTE + "dropped malformed claim " + claim
                            + " - not a (path_prefix, module_name) pair");
                    continue;
                }
                Optional<String> prefix = normalizePrefix(claim.pathPrefix());
                if (prefix.isEmpty()) {
                    notes.add(MERGE_NOTE + "dropped claim ('" + claim.pathPrefix() + "' -> " + claim.targetModule()
                            + ") - blank, root-level, or repo-escaping prefix does not bound a subtree"
                            + " inside the repository");
                    continue;
                }
                if (!knownModules.contains(claim.targetModule())) {
                    notes.add(MERGE_NOTE + "dropped claim (" + prefix.get() + " -> " + claim.targetModule()
                            + ") - unknown module name");
                    continue;
                }
                producers.computeIfAbsent(new ClaimKey(prefix.get(), claim.targetModule()), k -> new TreeSet<>())
                        .add(id);
            }
            notesById.put(id, notes);
        }

        Map<String, TreeMap<String, TreeSet<String>>> byPrefix = new TreeMap<>();
        producers.forEach((key, ids) ->
                byPrefix.computeIfAbsent(key.prefix(), p -> new TreeMap<>()).put(key.module(), ids));

        List<ActivePathClaim> active = new ArrayList<>();
        List<PathClaimCollision> collisions = new ArrayList<>();
        Map<String, Integer> claimCountById = new HashMap<>();

        byPrefix.forEach((prefix, targets) -> {
            if (targets.size() == 1) {
                var single = targets.firstEntry();
                active.add(new ActivePathClaim(prefix, single.getKey(), List.copyOf(single.getValue())));
                single.getValue().forEach(id -> claimCountById.merge(id, 1, Integer::sum));
            } else {
                // Collision: never pick a winner; no claim, a diagnostic, and a note to every contender
                TreeMap<String, List<String>> reportMap = new TreeMap<>();
                targets.forEach((mod, ids) -> reportMap.put(mod, List.copyOf(ids)));
                collisions.add(new PathClaimCollision(prefix, Collections.unmodifiableSortedMap(reportMap)));
                String note = MERGE_NOTE + "suppressed claim on prefix '" + prefix
                        + "' - contested by more than one module (" + String.join(", ", targets.keySet()) + ")";
                targets.values().stream()
                        .flatMap(Set::stream)
                        .distinct()
                        .sorted()
                        .forEach(id -> notesById.computeIfAbsent(id, k -> new ArrayList<>()).add(note));
            }
        });

        active.sort(Comparator.comparingInt((ActivePathClaim c) -> c.normalizedPrefix().length())
                .reversed()
                .thenComparing(ActivePathClaim::normalizedPrefix));

        List<AttributorReport> reports = statusById.entrySet().stream()
                .map(e -> new AttributorReport(
                        e.getKey(),
                        e.getValue(),
                        claimCountById.getOrDefault(e.getKey(), 0),
                        List.copyOf(notesById.getOrDefault(e.getKey(), List.of()))))
                .toList();

        return new AttributionTable(List.copyOf(active), List.copyOf(collisions), reports);
    }
}

== Module Discovery, Build Map & Architecture State Machine
_See Requirement link:../Requirements.adoc#PM-EXT-3[PM-EXT-3: Module Discovery, Build Map & Architecture Enrichment]_

`PM-MCP` moves deterministic module discovery, dependency graph construction, verification routing (`derive-verification`), and architecture queries into the daemon while keeping semantic module enrichment (`responsibility`, `purpose`, `key_packages`) as model judgment.

=== Server-Owned Module Discovery & Enrolled Discovery Jobs
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-6[PM-WATCH-EXT-6], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-7[PM-WATCH-EXT-7], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-8[PM-WATCH-EXT-8]_

Module discovery combines compiled-in descriptor parsers with optional enrolled build-tool discovery jobs, caching the resulting structural snapshot in server state keyed by the repository's descriptor tree hash:

|===
|Build System |Compiled-In Descriptor Parser |Enrolled Discovery Job Template |Extracted Module Facts

|Maven

* **Live Crawl, Snapshot as Cache**: Discovery always crawls the live worktree, including uncommitted descriptors. The descriptor tree hash covers the live descriptor content, not `HEAD`. The persisted snapshot is a denormalized cache, never the gatekeeper: a module directory present on disk but absent from the snapshot is still discovered.
* **Per-Descriptor Failure Isolation**: A malformed descriptor (the root descriptor or one workspace member) is reported for its module with the parse diagnostic and does not abort discovery of the remaining modules.

=== Build Map & Deterministic `derive-verification` (ADR-004)
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-9[PM-WATCH-EXT-9]_

The file-to-build contract lives at `build.map` in `.plan/marshal.json` (peer of `build.queue`): a domain-keyed inventory `{"<domain>": [{"glob", "role", "build_class"}]}` with roles `production`, `test`, and `config` and the closed build classes `compile`, `module-tests`, `verify`, and `none`. Phase 4 (`plan`) calls `derive-verification` with each task's changed-artifact list and stamps the returned canonical command set into the task's `verification.commands`; Phase 5 (`execute`) runs the stamped commands. The seeding, editing, and reseeding rules mirror `plan-marshall` (`manage-config/scripts/_cmd_build_map.py`, `manage-config/standards/data-model.md` § build.map, `marshall-steward/references/build-map-setup.md`, `phase-4-plan/SKILL.md`), verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing.

* **Seeding from Axis B**: The seed collects every build-system descriptor's `classifyGlobs()` routes under its served domain key, keeps a domain's routes only when that domain's Axis-A applicability matches at least one discovered module, prunes routes that match no git-tracked file, and stamps each route with `classifyBuildClass()`. Because applicability needs discovered modules, seeding happens only in `setup.seed-build-map` after `setup.discover-modules`; `config.reconcile` default seeding never creates `build.map`.
* **Write-Once Seed, Direct Edits**: A seed never overwrites an existing `build.map` block. Corrections are made directly to the seeded entries — through the `customize_routes` link of `setup.seed-build-map`, or by a committed edit of `.plan/marshal.json` — and there is no separate override layer. `customize_routes` therefore edits the seeded block itself and is not an exception to write-once: write-once constrains the seeder, not the user.
* **Explicit Reseed Only**: The seeded block is re-derived only through `setup.reseed-build-map`, which the setup workflow enters on every reconcile run when a `build.map` block exists. The state compares the persisted block with the live derivation (per domain, added and removed globs). When they agree it passes silently; on drift it offers `reseed_build_map` (replace the whole block with the live derivation, discarding hand edits) and `keep_build_map` (preserve the persisted block). The state always waits for this answer, even when other setup decisions are pre-answered, so a hand edit is never discarded without consent (`plan-marshall`: `build-map drift`, `build-map seed --force`, upgrade nested gate `build-map-reseed`).
* **Separate Glob Dialect**: Build-map routes use the **`fnmatch` glob dialect**, which is kept strictly separate from the Axis-A `provides_file_globs` domain-detection dialect. A path-bearing route matches the whole repository-relative path (a single `*` spans `/`; routes never use `**`), and a bare-basename route (no `/`, e.g. `pom.xml`) matches that file name at any depth.
* **Fail-Closed Read Invariant**: `derive-verification` reads `build.map` fail-closed. If `build.map` is absent, malformed, or holds an entry with an unknown `role` or `build_class`, the engine refuses verification derivation with an explicit diagnostic (`build_map_invalid` or `build_map_unseeded`) rather than returning an empty verification set. *Deliberate hardening vs. `plan-marshall`*: `plan-marshall`'s `build-map read` also fails closed, but its deriver and build-decision readers degrade an absent `build.map` to an empty map instead of refusing.
* **Canonical Command Resolution Rules**:
  - Production paths (`role == "production"`, `build_class == "compile"`) resolve `compile` on the owning module.
  - Test paths (`build_class == "module-tests"`) resolve `test-compile` + `module-tests` on the owning module (Maven Failsafe `*IT`/`IT*`/`*ITCase` test paths route to `verify`).
  - Build/lint/packaging config paths (`role == "config"`, `build_class == "verify"`) resolve `verify` for the affected module.
  - Documentation or non-compiled path claims (`build_class == "none"`) require zero build jobs and route only to applicable doc/plugin validators.

=== Tier-1 Init Routing & Deterministic Deliverable Generation
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-9[PM-WATCH-PHASE-9]_

The scoring and routing rules mirror `plan-marshall` (`script-shared/scripts/recipe_scoring.py`, `phase-1-init/SKILL.md`, verified at commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing).

1. *Explicit Choice Beats Heuristic Match*: A plan started from a recipe (`pm_start` with `recipe_id`, i.e. source `recipe`) bypasses scoring and routes directly to `init.recipe-selected`.
2. *Registry-Wide Deterministic Scoring*: For every other source, during `phase-1-init` (ahead of light/deep planning-lane routing), the server scores **every** registered recipe (no domain pre-filter): $\text{confidence} = 0.6 \cdot \text{keyword} + 0.25 \cdot \text{domain} + 0.15 \cdot \text{scope}$, rounded to three decimals, where `keyword` is the share of the recipe's `display_name` + `description` tokens (stop-words removed) found in the request, `domain` is `1` when the recipe's `domain` equals the plan's domain, and `scope` is `1` when the plan's scope estimate matches the recipe's `scope` (`module` for surgical/narrow plans, `codebase_wide` for broad ones). For the surgical-fix recipe only, a pre-diagnosed-change shape score of the request may raise the confidence (`max`). Recipes below `0.35` are dropped.
3. *Auto-Route or Ask*: When `plan.phase-1-init.auto_route_recipe` is `true` (default) and the top confidence is at least `plan.phase-1-init.auto_route_recipe_threshold` (default `0.6`), the engine selects that recipe without asking. Otherwise, if candidates remain, it enters `init.recipe-candidate` (an `*.awaiting_user` state) offering `use_recipe:<recipe_key>` (`rel = "next"` for the highest-scoring recipe, `rel = "alt"` for the others) and `skip_recipe` (`rel = "alt"`) to proceed with standard light/deep planning.
4. [[recipe-plan-id]]*Recipe Plan ID*: A recipe plan's `plan_id` is `recipe-{recipe_key}-{yyyy-mm-dd-hh-mm-ss}` (UTC), so every run gets a fresh branch name. *Deliberate change vs. `plan-marshall`*: `plan-marshall` uses hour precision (`{yyyy-mm-dd-hh}`), which collides when the same recipe runs twice within an hour.
5. *Server-Side Target Harvesting & Deliverable Generation*: When a recipe is selected, the server executes the recipe's deterministic `target_harvester` (e.g., enumerating packages per module, scanning `.md`/`.adoc` files for misaligned ASCII box diagrams, or invoking an enrolled `project_script` harvester) and populates the solution outline deliverables automatically. The workflow exposes judgment links only where model evaluation is required: confirming or pruning harvested targets (`confirm_recipe_targets`) and verifying coverage at completion.
6. *Auditable, Idempotent Harvest Runs*: A recipe run records one disposition per harvested target; for `recipe-lesson-cleanup` over `stalled_lessons` the dispositions are `routed`, `reclassified`, and `retired` (through a lesson tombstone with its mandatory `reason` and `coverage_verdict`, link:store-schemas.adoc#lesson-record[Store Schemas Specification, Lesson Record, Retirement]). Re-running on unchanged input is a no-op keyed on the target's duplicate key (for lessons: link:store-schemas.adoc#lesson-record[Store Schemas Specification, Lesson Record, Upstream Release, Duplicates]). If the population differs between harvesting and action, the run reports the delta (added and removed target ids) and never adopts it silently.

=== Pre-Submission Self-Review Surfacer Contract (`ext-self-review-*`)
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-13[PM-WATCH-EXT-13], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-14[PM-WATCH-EXT-14], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-15[PM-WATCH-EXT-15], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-16[PM-WATCH-EXT-16], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-17[PM-WATCH-EXT-17], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-18[PM-WATCH-EXT-18], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-19[PM-WATCH-EXT-19], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-20[PM-WATCH-EXT-20], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-24[PM-WATCH-EXT-24], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-26[PM-WATCH-EXT-26], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-40[PM-WATCH-GEN-40], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-45[PM-WATCH-GEN-45]_

During `phase-6-finalize`, the pre-submission structural self-review step runs deterministic candidate detectors over the plan's realized diff to surface high-risk patterns (unvalidated boundary inputs, asymmetric function pairs, description-vs-body mismatches, stale ordinal prose, unguarded flags) as structured facts for model review:

* **AsciiDoc Content Class**: `*.adoc` paths form their own content class `asciidoc` (never `other`), covered at least by the stale-count and ordinal-prose detector: a count or ordinal stated in prose ("the five bands", "the third item", "13-state vocabulary") that no longer matches the enumeration, table, or list it describes, including one in a file the plan did not edit, is a candidate. PM-MCP's own documentation is AsciiDoc, so its changes are reviewed rather than reported `not_covered`.
* **Applicability by Content Class**: A surfacer is applicable when its declared content classes cover at least one content class of the realized footprint; a footprint whose paths all fall in content class `other` has no applicable surfacer. An inapplicable surfacer is never run: the step records `not_covered` with the uncovered content classes and completes non-blocking, never as `clean`. The refusal reasons `no_domain_surfacer`, `no_covered_content_class`, and `zero_detectors` are round-invariant at an unchanged `HEAD`.
* **Not Run Is Not Clean Invariant**: When no self-review surfacer is applicable, the server records `"status": "not_run: no_surfacer_resolved"` in the finalize ledger—never `"clean"` or `"passed"`. Every active surfacer records its `scope_statement`, `structural_limit`, and `delta_coverage`; a detector class with zero matching files in the diff is recorded as `unapplicable`, never counted toward measured clean coverage.
* **Which Zero Coverage**: Per content class the surfacer records `files`, `files_with_candidates`, and `detectors`; a class with `files > 0` and `detectors == 0` is recorded as `gap`, never as clean. The reach map is derived from the registered detectors. Every realized path with no applicable detector is listed as `not_scanned` in the step facts and the landing facts, and a round over only `not_scanned` paths is `not_covered`. Per-file candidate counts distinguish `examined_zero` (an applicable detector ran on the file and found nothing) from `not_scanned`.
* **Run-Emitted Diagnostics**: Diagnostics emitted by the plan's own run (build, validator, or gate output) whose subject overlaps the plan footprint are surfaced as candidates alongside the detector findings.
* **Target-Class Seeding**: When the plan's approved outline names the defect class the plan exists to remove (its target defect class), the surfacer also seeds candidates of that class over the plan footprint in every round, because a fix for a class is the likeliest place to re-commit it; the seeded candidates are counted in the round's `cohort_size` like any other.
* **Out-of-Surface Findings**: Findings identified outside the surface go into a non-blocking `observed_out_of_surface` list whose count reaches the step summary, so `clean`, `nothing_found`, and `suppressed` stay distinct outcomes.
* **Round Accounting**: `cohort_size` is published per round and cumulatively. A finding at a file and line of a prior round's finding is marked `repeat_site` with its repeat count. A finding classified `self_seeded` (introduced by the previous round's fix) records that classification at WARNING level; its remedy is the deletion of the added clause, gated on that recorded classification. Each round records `findings_total` and `findings_self_seeded`; from round 2 the step's facts state the self-seeded share, the vocabulary skill prescribes deleting the added text or replacing it with a pointer as the default remediation, and the share of every round is rendered in `finalize.loop-limit-reached` (link:workflow-dsl.adoc#loop-back-bounds[Workflow DSL Specification]). The share is a signal only: `max_iterations` remains the loop's only automatic bound.
* **Delta Round Narrowing Invariant**: On subsequent finalize iterations after a fix, delta self-review rounds narrow only the candidate file set to files modified since the previous reviewed `worktree_sha`, never narrowing the hunk basis against the plan's base commit. The plan's base commit is the footprint `base_ref` defined in link:store-schemas.adoc[Store Schemas Specification] (§ Three-Way File Footprint Reconciliation). Before computing candidates the step fetches `origin/<base_branch>` itself; the fail-closed refusal applies only when the base commit or the previous `worktree_sha` is still unresolvable after that fetch, and then the step fails with an explicit error rather than silently widening or skipping. The delta candidate set also includes the reference closure: every file of the plan footprint that references a path or a declared symbol changed since the previous reviewed `worktree_sha` (a document line made stale by an edit in another file is therefore a candidate in the next delta round, not only in the closing full round). When the previous round's `worktree_sha` is not an ancestor of `HEAD` (the branch was rebased), delta resolution is skipped, open findings stay pending, and a full round is required: an endpoint diff across an upstream advance never marks a finding fixed. A delta round can never close the step: a clean delta round is followed by exactly one full-surface round over the whole plan diff, and only a clean full-surface round records `done` (`may_close = true`). A delta round that surfaces findings loops back without a confirmation round.

== Out-of-Process Project Script Jobs (`project_script`) & Domain Workers
_See Requirement link:../Requirements.adoc#PM-EXT-5[PM-EXT-5: Out-of-Process Project Script Jobs & Domain Workers]_

To support repository-specific automation (`finalize-step-*` skills that ship executable checks, custom `recipe-*` target harvesters) and third-party/organization domain workers (custom build-log parsers, marker scanners, or module discovery for languages not compiled into `pm-mcp`) without compromising the GraalVM native-image closed world, `PM-MCP` provides a permanent **`project_script`** job type in the Job Runtime (see link:job-runtime.adoc[Job Runtime Specification]).

=== Division of Authority: Server vs. `project_script`

[source,text]
----
┌─────────────────────────────────────────────────────────────────────────┐
│ PM-MCP Daemon (Authoritative State & Security Boundary)                 │
│  • Owns workflow state machine, step ordering, gating, and locks        │
│  • Verifies script path, interpreter hash, and SHA-256 against enrolment│

                    ▼                                 │
┌─────────────────────────────────────────────────────────────────────────┐
│ Out-of-Process `project_script` Subprocess (Stateless Fact Producer)    │
│  • Runs in sanitized environment (no provider credentials)              │

└─────────────────────────────────────────────────────────────────────────┘

1. *No Direct Store Mutation*: A `project_script` subprocess is a stateless fact producer. It **must never** write directly to `.plan/local/plans/`, `.plan/orchestrator/`, or `marshal.json`. All persistence is performed by the daemon after validating the script's JSON output.
2. *Operator Enrolment Precondition*: Every `project_script` (and its runtime interpreter, such as a pinned `python3` binary) must be enrolled by the operator in `~/.plan-marshall/mcp/enrolments.json` with its repository-relative script path, expected SHA-256 content hash, maximum timeout, and allowed step/worker binding (`finalize_step`, `recipe_harvester`, `log_parser`, `module_discovery`, `edge_resolver`). If a script file is modified in the working tree without re-enrolment, the verify-not-resolve digest check rejects execution with job outcome `refused`.

== Three-Way Configuration Split (`marshal.json`, Enrolment, Server State)
_See Requirement link:../Requirements.adoc#PM-EXT-6[PM-EXT-6: Three-Way Configuration Split (Project, Enrolment, Server State)]_

In the legacy architecture, `.plan/marshal.json` and `.plan/local/run-configuration.json` mixed declarative project settings, frozen extension hook snapshots (`skill_domains`), overridable shell commands (`verify_command`), language-server argument vectors, and learned runtime timeouts inside workspace files that the model's file/shell tools could modify.

`PM-MCP` enforces a fundamental security invariant: **Nothing that decides what binary or argument vector executes on the host may be read from a file the model can write.** Configuration and operational state are partitioned across three strictly separated stores.

=== Tier 1: Git-Tracked Project Configuration (`.plan/marshal.json`)

1. *Elimination of Frozen `skill_domains` Snapshots*: During migration from legacy `marshal.json`, frozen hook outputs stored under `skill_domains.{key}` (skill lists, globs, recipes) are treated as derived legacy artifacts and stripped. The compiled-in domain descriptors in `pm-mcp` are authoritative; `.plan/marshal.json` retains under `skill_domains` only the active domain IDs and explicit operator parameter overrides.
2. *Write-Once Domain Defaults*: When a domain is enabled, its `config_defaults` map is merged into `.plan/marshal.json` using write-once semantics: existing project keys are never overwritten.
3. *Provider Cardinality & Origin Pinning*: Provider declarations in `.plan/marshal.json` enforce category cardinality: exactly `1` version-control provider (`git`), at most `1` CI provider (`github` or `gitlab`), and `0..N` code-quality/issue providers (such as `sonar`). For token-lane REST providers (`PM-CRED-2`), `.plan/marshal.json` stores the non-secret provider `url` (which must use `https://`; the credential entry's own `url` is the origin tokens are sent to, `PM-CRED-5`), establishing the single issuing origin to which the daemon's REST client restricts authentication headers (forbidding cross-origin or HTTP downgrade redirects).

=== Tier 2: Enrolled Argument Templates & Slot Cap (`~/.plan-marshall/mcp/`)

To prevent argument injection without requiring the operator to re-enrol the project every time a new module is added, build enrolment binds wrappers and host tools to **typed argument templates** defined by domain support:

[source,json]
----
{
  "canonical_templates": {
    "maven": {
      "module-tests": ["test", "-pl", "{module}"],
      "quality-gate": ["verify", "-DskipTests", "-pl", "{module}"],
      "verify": ["verify", "-P{profile}", "-pl", "{module}"]
    }
  }
}
----

* **Typed Placeholder Validation at Job Time**: When the daemon constructs a build job, it substitutes `{module}` and `{profile}` and validates them against its own cached module discovery snapshot (`{module}` must be a discovered module path/coordinate in the repository; `{profile}` must be a profile declared in that module's build descriptor).
* **Enrolled Template Precedence**: An enrolled template for a canonical verb replaces the compiled default template for that project; every build representation names the template source (`enrolled` or `compiled_default`). Templates are never read from `.plan/marshal.json` (`PM-EXT-6`).
* **Forbidden Free Flags**: Arbitrary user- or model-supplied flags—specifically `-D`, `-f`, `--file`, `-s`, `--settings`, `--init-script`, or shell metacharacters—are never accepted in canonical build jobs.
* **Machine-Wide Slot Cap & Source Discrimination**: `machine-config.json` holds `max_concurrent_builds`. On every build submission, the scheduler resolves the cap and reports both the value and its resolution `source` (`machine_config`, `default`, `invalid`, or `unreadable`); `invalid` and `unreadable` configuration files are surfaced explicitly in diagnostics and never silently folded into `"default"`.

=== Tier 3: Adaptive Build Timeouts & Crash-Replay State

The daemon maintains learned operational metrics and job journals in Tier 3 server state:

1. *Adaptive Timeout Learning (`build-timings.json`)*: One machine-level store, `~/.plan-marshall/mcp/state/build-timings.json`, keyed by project (the enrolled project root) and canonical command (the normalized canonical argument vector `(build_system, canonical_verb, module_id, sorted_profiles)`); no project-local timeout store exists. Given observed run durations, the server maintains a max-biased baseline $T_{\text{learned}} = \lfloor 0.8 \times \max(T_{\text{learned}}, d) + 0.2 \times \min(T_{\text{learned}}, d) \rfloor$ and sets the execution timeout to $T_{\text{limit}} = \max\left(T_{\text{engine\_floor}},\; \lfloor 1.25 \times T_{\text{learned}} \rfloor\right)$. Per-engine minimum floors (Maven/Gradle/npm: `300s`, pyproject: `330s`) are never violated, even if an explicit bound is configured, every finished run (any exit code) feeds $T_{\text{learned}}$, a `timed_out` run never feeds it but sets a one-shot escalation budget $\min(2 \times \text{timeout}, 1800\,s)$ for the next run, residue-poisoned runs are not blended while clean observations exist, every allocation records its `budget_derivation`, and durations from `killed` or `cancelled` runs are **never** incorporated (link:job-runtime.adoc#_adaptive_timeout_learning[Job Runtime Specification, Adaptive Timeout Learning]).
2. *One-Time Import of Learned Timeouts*: At machine cutover (`PM-MIG-2`), and when a project is first enrolled after cutover, the runtime imports that project's learned values once from `.plan/local/run-configuration.json` (`commands["<tool>:<key>"].timeout_seconds`, in seconds, e.g. `commands["maven:verify"]`) as the initial $T_{\text{learned}}$ of the canonical command the key maps to. Existing `build-timings.json` entries are never overwritten, keys that map to no canonical command are skipped and listed in the cutover receipt, and the legacy file is left unchanged. As a store conversion under `PM-MIG-3`, the import has a reverse converter that writes the learned values back to their originating keys on rollback (`PM-MIG-5`). The legacy source mirrors `plan-marshall` (`manage-run-config/scripts/run_config.py`, `script-shared/scripts/build/_build_execute.py`), verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing.
3. *Gate Honesty & Examined Population Tracking*: Before a green build or quality gate clears open findings in `findings.jsonl`, the server's compiled log and report parsers verify that for Maven and Gradle the build log explicitly contains the engine's terminal success marker (e.g., `BUILD SUCCESS` / `BUILD SUCCESSFUL`) in addition to exit code `0`, and that the tool examined a non-empty file/test population capable of reaching the finding's file and category (e.g., `mypy` gates run with `--no-incremental` / cache disabled so untouched files with broken cross-module types are not skipped).
4. *Crash Replay & Atomic Fate Recording*: Every spawned job is recorded in the daemon's write-ahead job journal prior to `ProcessBuilder.start()`. Request status (`running`) is never treated as terminal fate; terminal fate (`succeeded`, `failed`, `timed_out`, `cancelled`, `killed`, `indeterminate`) is written atomically at process termination. If the daemon restarts while a job record is still `running`, journal replay marks the orphaned job `killed` ("do not retry blindly") and attaches no synthetic error findings.

== Systematized `marshal.json` Upgrades: Command-Pattern Migration Chain & Zero-CoT Reconciliation (`PM-EXT-7`)
_See Requirement link:../Requirements.adoc#PM-EXT-7[PM-EXT-7: Versioned Command-Pattern Configuration Upgrades & Zero-CoT Reconciliation]_

In legacy `plan-marshall`, schema and default updates to `.plan/marshal.json` were split across ad-hoc hooks inside `manage_config.py -> sync-defaults` (`RETIRED_STEP_KEY_RENAMES`, `run_at_all -> lane`, lane materialization), separate CLI canonicalizers (`steps-sort`, `normalize-keys`), and one-shot subcommands in `marshall-steward/scripts/upgrade.py` (`migrate-bot-lists`, `validate-bot-lists`). Every new migration required adding prose instructions to `upgrade-flow.md` that the LLM had to read into its context window and execute via separate `Bash` calls—polluting the model's Chain of Thought (CoT) with historical schema trivia even on already-current repositories.

`PM-MCP` replaces ad-hoc config updates with a self-contained, version-tracked **Command-Pattern** subsystem (`de.cuioss.pm.mcp.core.config.migration`) executed atomically inside the server.

=== 1. Version Tracking & Migration Ledger in `.plan/marshal.json`

Every `.plan/marshal.json` root document carries a `system` tracking block managed exclusively by `ConfigReconciler` (see link:store-schemas.adoc[Store Schemas Specification]):

The `system` block extends the one `plan-marshall` already writes (`retention`, `provisioned_version`, `config_seed_fingerprint`); the first migration command (`M001`) adds the versioning fields. `marshal.json` has no `format_version` of its own.

[source,json]
----
{
  "system": {
    "retention": { "logs_days": 1, "archived_plans_days": 5 },
    "provisioned_version": "1.0.0",
    "config_seed_fingerprint": "a94f6e2c81b3d04e7f1298a0b5c6d7e8f90123456789abcdef0123456789abcd",
    "schema_version": 4,
    "baseline_version": 1,
    "applied_migrations": [
      "M002_rename_retired_step_keys",
      "M003_migrate_run_at_all_to_lane",
      "M004_split_enabled_bots_to_participation_lists"
    ]
  }
}
----

* `retention`, `provisioned_version`: Kept from `plan-marshall` unchanged. `provisioned_version` is the version of the binary that last reconciled the file and only advances when a valid version is present (never blanked).
* `schema_version`: Monotonically increasing integer (`1..CURRENT_SCHEMA_VERSION`) identifying the highest `ConfigMigrationCommand.targetVersion()` applied to this file; its absence identifies an unmigrated `plan-marshall` file, which `M001` handles.
* `baseline_version`: Integer epoch floor (`MINIMUM_SUPPORTED_SCHEMA_VERSION`). Migration IDs with `targetVersion <= baseline_version` are compacted out of `applied_migrations` at major epoch bumps so `.plan/marshal.json` never accumulates unbounded historical entries.
* `applied_migrations`: Ordered array of `migrationId` strings for all commands applied above `baseline_version`.
* `offered_steps`: Step ids ever seeded into or offered for the operator-prunable step maps (§ 3); written only by `ConfigReconciler` and by the answer to a new-step offer.
* `config_seed_fingerprint`: *Deliberate change vs. `plan-marshall`* (8-hex MD5 over the default config only): a deterministic SHA-256 digest of the compiled-in default configuration tree, the active domains' `config_defaults`, and the `FinalizeStepDescriptor` ordering table.

=== 2. Command-Pattern Architecture (`ConfigMigrationCommand`)

Each version-specific structural or value migration ($v-1 \to v$) is implemented as a standalone, immutable Java class implementing the sealed `ConfigMigrationCommand` interface:

[source,java]
----
package de.cuioss.pm.mcp.core.config.migration;

import com.fasterxml.jackson.databind.node.ObjectNode;
import java.util.List;
import java.util.Set;

public record MigrationContext(
    Set<String> enabledDomains,
    Set<String> registeredBotKinds,
    List<String> orderedFinalizeStepIds
) {}

public record MigrationMutation(
    String kind,        // "renamed" | "migrated" | "stripped" | "seeded"
    String jsonPointer,
    String detail
) {}

public record MigrationWarning(
    String code,        // e.g., "unknown_bot_tokens", "unrecognized_top_level_key"
    String jsonPointer,
    String message,
    List<String> offendingValues,
    List<String> allowedValues
) {}

public record MigrationStepResult(
    int targetVersion,
    String migrationId,
    boolean mutated,
    List<MigrationMutation> mutations,
    List<MigrationWarning> warnings
) {}

public sealed interface ConfigMigrationCommand
    permits M001_StripLegacySkillDomainsAndExecBindings,
            M002_RenameRetiredStepKeys,
            M003_MigrateRunAtAllToLane,
            M004_SplitEnabledBotsToParticipationLists {

    /** Strictly monotonic target schema version (e.g., 1, 2, 3, 4). */
    int targetVersion();

    /** Stable unique identifier (e.g., "M004_split_enabled_bots_to_participation_lists"). */
    String migrationId();

    /** Concise human-readable summary for audit.jsonl and operator receipts. */
    String description();

    /**
     * Applies an idempotent structural/value transformation to the raw Jackson ObjectNode AST.
     * Must preserve operator overrides (Rule 3) and never throw on already-migrated trees.
     */
    MigrationStepResult execute(ObjectNode root, MigrationContext context);
}
----

* *AST-Before-Binding Isolation*: `ConfigMigrationCommand.execute(...)` transforms the raw Jackson `ObjectNode` tree **before** the tree is deserialized into the strongly typed `MarshalConfigRecord`. Consequently, `MarshalConfigRecord` and runtime readers (`ConfigService`) represent **only** the current canonical schema and never carry `@JsonAlias` annotations, deprecated record components, or fallback branches for retired keys.
* *Lossless Override Preservation*: Every command must move or transform existing operator values in place rather than resetting to defaults (e.g., renaming `default:automated-review` $\to$ `plan-marshall:automatic-review` carries the step's nested parameter block verbatim, or drops the retired key if the canonical key already exists; migrating `enabled_bots` $\to$ `required_bots` / `optional_bots` never overwrites an existing operator-answered `bot_lists_provenance`).

=== 3. Five-Phase Atomic Reconciliation Pipeline (`ConfigReconciler`)
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-21[PM-WATCH-EXT-21], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-22[PM-WATCH-EXT-22]_

All updates to `.plan/marshal.json` (whether triggered during `steward` setup/upgrade, `pm-mcp operator upgrade-config`, or automatic forward migration) pass through a single deterministic in-process method `ConfigReconciler.reconcile(Path marshalJsonPath)`:

[source,text]
----
Raw .plan/marshal.json (ObjectNode)
  │
  ├─► Phase 1: Pending Command Chain (v_cur + 1 .. CURRENT_SCHEMA_VERSION)
  │     Executes each unapplied ConfigMigrationCommand in ascending targetVersion order
  │
  ├─► Phase 2: Non-Destructive Default Seeding (syncDefaults)
  │     Deep-merges missing keys from DefaultMarshalConfig + enabled domain config_defaults
  │     (key-exists preservation: existing operator values and lists are never overwritten;
  │     operator-prunable step maps are excluded, new steps are offered once via offered_steps)
  │
  ├─► Phase 3: Deterministic Canonicalization (stepsSort + normalizeKeys)
  │     Re-orders plan.phase-6-finalize.steps by FinalizeStepDescriptor.order() ascending
  │     and orders all top-level/nested object keys into canonical schema order
  │
  ├─► Phase 4: Registry & Post-Condition Validation
  │     Validates every key at every level against the MarshalConfigRecord schema and checks
  │     required_bots/optional_bots against registered bot kinds; unknown keys are reported
  │
  └─► Phase 5: Epoch Compaction, Stamp & Conditional Atomic Write
        Compacts applied_migrations <= baseline_version, updates system.schema_version,
        provisioned_version, and config_seed_fingerprint, and atomically writes
        .plan/marshal.json ONLY if canonical JSON bytes changed
----

*Operator-Prunable Step Maps*: `plan.phase-5-execute.verification_steps` and `plan.phase-6-finalize.steps` are keyed maps the operator prunes by deleting keys, so a missing key there means "removed", never "not yet seeded". Phase 2 therefore never deep-merges into them. `system.offered_steps[]` records every step id ever seeded into or offered for these maps; a shipped step id absent from it is offered once through a setup `*.awaiting_user` question (`add` / `decline`), and either answer is recorded in `offered_steps`, so a declined or removed step is never offered or added again. The initial seeding of a new project (no `system.schema_version`) writes the default maps and records their ids. *Deliberate change vs. `plan-marshall`*: `plan-marshall`'s `syncDefaults` deep-merges these maps and restores removed steps (TokenSheriff#745).

*Undeclared Keys Are Refused, Never Kept Unread*: A setup or config link that would write a key not declared in `MarshalConfigRecord` is refused (`invalid_link_args`). Unknown keys found in a hand-edited `.plan/marshal.json` are reported as `unknown_config_key` findings naming the key path; they are never silently kept as unread settings.

=== 4. Anti-CoT-Clutter & Lifecycle Compaction Guarantees

To ensure configuration upgrades never degrade model reasoning or bloat context windows:

1. *Zero Migration Prose in Skills (`PM-SKILL-1`, `PM-EXT-7`)*: No vocabulary skill (`skill://pm/...`) or workflow state prompt ever instructs the model to run `sync-defaults`, `steps-sort`, `normalize-keys`, or `migrate-*` commands, nor mentions retired configuration keys (`enabled_bots`, `run_at_all`, `default:automated-review`, `skill_domains`).
2. *Silent $O(1)$ Fast-Path When Current*: At `pm_start`, phase handshakes, and `pm-mcp enter`, the server compares `(system.schema_version, system.config_seed_fingerprint)` against `(CURRENT_SCHEMA_VERSION, CURRENT_SEED_FINGERPRINT)`. When they match, verification completes in memory in $<1\text{ ms}$ and emits **zero** facts, links, or warnings into the state representation.
3. *Single Server-Side Reconcile Transition*: When `schema_version < CURRENT_SCHEMA_VERSION` or `config_seed_fingerprint` differs, `steward` (or `pm-mcp operator upgrade-config`) runs the entire 5-phase `ConfigReconciler` pipeline in one atomic step (`config.reconcile`) and emits a compact receipt containing only non-empty deltas (`from_schema_version`, `to_schema_version`, `applied_migrations[]`, `added_defaults_count`, `new_step_offers[]`, `warnings[]`); `added_defaults_count` never counts a key of an operator-prunable step map, and `new_step_offers[]` lists the newly shipped steps offered, so a new default is never confused with re-adding a removed one.
4. *Epoch Compaction (`MINIMUM_SUPPORTED_SCHEMA_VERSION`)*: At major releases, `MINIMUM_SUPPORTED_SCHEMA_VERSION` advances. `ConfigMigrationCommand` classes with `targetVersion <= MINIMUM_SUPPORTED_SCHEMA_VERSION` are deleted from the active command chain, and `ConfigReconciler` compacts their IDs out of `system.applied_migrations` into `system.baseline_version`. If a repository presents a `schema_version < MINIMUM_SUPPORTED_SCHEMA_VERSION`, `ConfigReconciler` fails closed with an explicit `unsupported_legacy_config_epoch` error naming the required bridge version.
5. *Three-Surface Synchronization (In-Flight `execution-manifest.json` Snapshot & Adoption)*: An in-flight plan (Phases 4–6) executes against the configuration snapshot bound at composition. Whenever `ConfigReconciler` or an edit changes `.plan/marshal.json`, the next phase handshake (`phase-workflows.adoc`, Outside-World Invariants) detects that the plan's recorded `config_hash` / `schema_version` differs and runs `ExecutionManifestResolver` in-process to compose a candidate: an identical candidate is adopted silently; a differing one enters `<phase>.config-drift` (`adopt` / `keep`, audited). The manifest records its `composed_inputs` (`config_hash`, `realized_footprint_digest`, `change_type`, `providers_digest`); at Phase 6 entry the resolver re-computes every recorded input: a difference in the plan's own inputs (`realized_footprint_digest`, `change_type`, `providers_digest`) re-composes the manifest and records the changed inputs in `facts`, a difference in `config_hash` follows the adoption rule above, and an input the resolver cannot re-derive is listed as `unchecked` in those facts, never omitted. `config_hash` is computed over the `.plan/marshal.json` of the plan's current location (the worktree copy from Phase 5 on), so a deliverable that edits a configuration knob re-composes the manifest at the next handshake.
6. *Build-Time Chain Integrity Verification (`ConfigMigrationChainTest`)*: JUnit 5 build tests in `pm-mcp-core` enforce:
** Contiguous gap-free `targetVersion()` numbering from `MINIMUM_SUPPORTED_SCHEMA_VERSION + 1` to `CURRENT_SCHEMA_VERSION`.
** Globally unique `migrationId()` strings matching `^M\d{3}_[a-z0-9_]+$`.
** Strict idempotency: running `ConfigReconciler.reconcile(...)` a second time on any migrated fixture yields `mutated == false` and zero byte diff.
** Lossless override preservation across per-version fixture pairs (`v1 -> v2 -> ... -> vN`).
