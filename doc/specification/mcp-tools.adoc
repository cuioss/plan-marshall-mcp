== Overview

This document defines the normative Model Context Protocol (MCP) tool schemas, resource URI templates, skill delivery surface, and error/result envelope contracts for *plan-marshall-mcp* (`PM-MCP`). It specifies the JSON Schema (Draft 2020-12) definitions for the core workflow verbs (`pm_start`, `pm_state`, `pm_do`), discovery tools (`pm_plans`, `pm_epics`), orthogonal service tools (`pm_build`, `pm_lsp`), tool-based skill retrieval (`pm_skill`, `pm_skills`, `pm_skill_file`), and the transitional legacy script tool (`pm_legacy_script`, Migration Stages 1–5), alongside the strict separation between JSON-RPC protocol errors, tool execution errors (`isError: true`), and domain workflow failure states (`isError: false`).

=== Architectural Constraints

1. *Small, Stable Verb Set*: PM-MCP exposes a fixed set of top-level MCP tools (`pm_start`, `pm_state`, `pm_do`, `pm_plans`, `pm_epics`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`) rather than one tool per workflow step or script. Across all phases and domains, the resident tool surface remains constant, and privileged operator actions are strictly excluded from the MCP tool surface (`PM-SEC-3`). The one documented exception is the transitional `pm_legacy_script` tool, present only during Migration Stages 1–5 and removed at Stage 6 (<<transitional-legacy-script-tool>>).
2. *Portable Naming Convention*: Every tool name conforms to `^pm_[a-z0-9_]+$`, ensuring identical identifiers across Claude Code, OpenCode, Antigravity, Codex, and raw model tool-calling APIs without escaping or translation.
3. *Closed Top-Level Schemas*: Every tool `inputSchema` conforms to JSON Schema Draft 2020-12 (`https://json-schema.org/draft/2020-12/schema`) and declares `"additionalProperties": false` at the top-level object boundary.
4. *TOON Text Output Only (No `outputSchema`)*: Tools intentionally omit `outputSchema` and `structuredContent`. Every tool result is returned in a single MCP `TextContent` block (`type: "text"`) encoded in deterministic TOON (link:hypermedia-format.adoc[Hypermedia Format Specification]). This avoids resident output-schema token overhead while optimizing token density on every turn.
5. *Zero Client-Supplied Filesystem Paths*: No workflow or service tool accepts absolute filesystem paths or worktree locations from the model. Worktrees, branches, and configuration files are resolved server-side from `plan_id` or `epic_id`.
6. *On-Demand Preloading*: For hosts configured with `schema_residency: "on_demand"` in their client profile, the user entry command preloads `pm_start`, `pm_state`, and `pm_do` so workflow execution incurs zero schema-lookup round trips.
7. *Canonical Plan and Epic Identifiers*: Every `plan_id` and `epic_id` input property uses the canonical plan ID grammar `^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$`, defined once in link:phase-workflows.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation] (epic IDs share it), and every example in this specification conforms to it.

=== `pm_start` — Initialize a Plan Scope

Creates a new plan directory from one of the four supported initialization sources (`request`, `issue_number`, `lesson_id`, or `recipe_id`) following a plan-mode `pm-mcp enter` invocation, consumes the pending entry record `.plan/local/mcp/pending/<entry_id>.json` whose `entry_id` that invocation printed by relocating it atomically into `.plan/local/plans/<plan_id>/mcp/entry.json`, initializes `mcp/status.json`, and returns the initial TOON hypermedia representation. Concurrent entries for different new plans therefore never share a slot. Epic membership has one carrier: the consumed entry record's `from_epic` (written by the emitted `pm-mcp enter … --from-epic <epic_id>` command), which `pm_start` copies into `origin.epic_id`; the tool has no epic parameter. When the new `plan_id` equals a `launched` queue row of an epic and `from_epic` is absent or names another epic, `pm_start` is refused with `epic_pointer_mismatch` (link:dispatch-and-effort.adoc[Dispatch & Effort Specification], Single Epic Pointer). Parameter names follow the entity-noun-first convention of `plan-marshall` ADR-023 within the `<entity>_id` symmetry: `plan_slug`, `epic_id`, `plan_id`.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_start",
  "description": "Create a new plan from a request, issue, lesson, or recipe and return its initial hypermedia representation.",
  "type": "object",
  "properties": {
    "entry_id": {
      "type": "string",
      "pattern": "^ent-[0-9a-f]{8,32}$",
      "description": "Identifier printed by 'pm-mcp enter' for the pending entry record this plan consumes."
    },
    "request": {
      "type": "string",
      "minLength": 1,
      "maxLength": 65536,
      "description": "Free-form user request or problem statement for the new plan."
    },
    "issue_number": {
      "type": "integer",
      "minimum": 1,
      "description": "GitHub/GitLab issue number to fetch via the enrolled CI CLI as the plan source."
    },
    "lesson_id": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{1,63}$",
      "description": "Lesson-learned identifier to convert into a remediation plan (runs premise check and relocates the lesson file into the plan)."
    },
    "recipe_id": {
      "type": "string",
      "pattern": "^[a-z][a-z0-9_-]{1,63}$",
      "description": "Registered recipe identifier (e.g., 'simplify-codebase', 'security-audit'); appends a deterministic UTC timestamp suffix to plan_id."
    },
    "recipe_params": {
      "type": "object",
      "default": {},
      "description": "Optional recipe scope/thoroughness parameters validated against the recipe's input schema."
    },
    "plan_slug": {
      "type": "string",
      "pattern": "^[a-z0-9]+(-[a-z0-9]+){0,7}$",
      "maxLength": 64,
      "description": "Optional short kebab-case slug used to derive the plan_id (rejected if shaped like a UUID or lesson_id, or if the derived plan_id is taken by a live, archived, or exported plan)."
    },
    "base_branch": {
      "type": "string",
      "pattern": "^[A-Za-z0-9_./-]+$",
      "maxLength": 128,
      "description": "Optional target base branch override (defaults to repository default branch)."
    }
  },
  "oneOf": [
    { "required": ["request"] },
    { "required": ["issue_number"] },
    { "required": ["lesson_id"] },
    { "required": ["recipe_id"] }
  ],
  "required": ["entry_id"],
  "additionalProperties": false
}
----

=== `pm_state` — Query Authoritative Hypermedia State

Returns the current hypermedia representation (`state`, `summary`, `skill` URI, domain `facts`, and valid `links`) for a `plan_id`, `epic_id`, or `steward` scope. When `entity` (and optional `scope: "entity"`) is supplied by a dispatched sub-agent, returns the leaf-scoped representation for that entity (e.g., task envelope `envelope-2` or finding `F-12`) and claims `dispatch_id` if provided.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_state",
  "description": "Return the current TOON hypermedia representation and valid links for a plan, epic, steward, or sub-agent entity.",
  "type": "object",
  "properties": {
    "scope": {
      "type": "string",
      "enum": ["plan", "epic", "entity", "steward"],
      "description": "Optional explicit scope discriminator (inferred from plan_id/epic_id/entity when omitted)."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target plan scope. Mutually exclusive with epic_id."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target orchestrator epic scope. Mutually exclusive with plan_id."
    },
    "entity": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_.:-]{0,63}$",
      "description": "Optional entity identifier within the plan or epic (e.g., 'envelope-1', 'F-12') for sub-agent scope."
    },
    "dispatch_id": {
      "type": "string",
      "pattern": "^(dsp-[A-Za-z0-9_.-]+-[0-9]{4}-[0-9a-f]{6}|d-[0-9a-f]{4,16})$",
      "description": "Optional dispatch tracking identifier supplied by a dispatched sub-agent on its initial call."
    }
  },
  "oneOf": [
    { "required": ["plan_id"] },
    { "required": ["epic_id"] },
    { "properties": { "scope": { "const": "steward" } }, "required": ["scope"] }
  ],
  "additionalProperties": false
}
----

NOTE: Companion discovery tools `pm_plans` (zero-argument, `{"type": "object", "properties": {}, "additionalProperties": false}`) and `pm_epics` (one optional boolean `include_archived`, default `false`, `additionalProperties: false`) return a tabular TOON listing of active plans or epics in the enrolled workspace; `pm_epics` with `include_archived` also lists archived epics (`.plan/archived-orchestrators/`, link:filesystem-layout.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]) with their archival date. Both always return a `coverage` table with one row per scanned root (`root`, `exists`, `listed`, `entries_scanned`, `unreadable`), so zero rows are distinguishable from a root that was absent or not scanned. Each listing carries a `last_entered` column that marks the scope whose `mcp/entry.json` was last written by the calling connection's `client_session_id` (`PM-CLIENT-6`); with no session identifier or no match, no row is marked. This is the post-compaction scope pointer on hosts without session lifecycle hooks (link:client-profiles.adoc#session-lifecycle-hook[Client Profiles Specification, Session Lifecycle Hook & Scope Pointer]).

=== `pm_do` — Follow a Hypermedia Link

The sole state transition verb in PM-MCP. Executes the transition identified by `link` from the current representation of `plan_id`, `epic_id`, or `steward`, passing any judgment parameters in `args`.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_do",
  "description": "Follow a hypermedia link from the current representation with its required free parameters.",
  "type": "object",
  "properties": {
    "scope": {
      "type": "string",
      "enum": ["plan", "epic", "entity", "steward"],
      "description": "Optional explicit scope discriminator."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target plan scope. Mutually exclusive with epic_id."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target orchestrator epic scope. Mutually exclusive with plan_id."
    },
    "entity": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_.:-]{0,63}$",
      "description": "Optional entity identifier when invoked by a dispatched leaf sub-agent."
    },
    "link": {
      "type": "string",
      "pattern": "^[a-z][a-z0-9_-]*(:(decision:)?[A-Za-z0-9][A-Za-z0-9_.-]*)?$",
      "maxLength": 128,
      "description": "Link identifier from the current representation (e.g., 'push', 'triage:F-12', 'wait:b-2291', 'wait:decision:dec-7f3a', 'returned:dsp-plan-042-0001-a9f3c2')."
    },
    "args": {
      "type": "object",
      "default": {},
      "description": "Free parameters required by the target link, validated server-side against the link's closed parameter schema."
    },
    "dispatch_id": {
      "type": "string",
      "pattern": "^(dsp-[A-Za-z0-9_.-]+-[0-9]{4}-[0-9a-f]{6}|d-[0-9a-f]{4,16})$",
      "description": "Optional dispatch identifier when invoked by a dispatched leaf sub-agent."
    }
  },
  "required": ["link"],
  "oneOf": [
    { "required": ["plan_id", "link"] },
    { "required": ["epic_id", "link"] },
    { "properties": { "scope": { "const": "steward" } }, "required": ["scope", "link"] }
  ],
  "additionalProperties": false
}
----

==== Two-Stage Schema Validation for `pm_do`

1. *Stage 1 (MCP Protocol Boundary)*: Validates that the incoming payload conforms to the `pm_do` JSON Schema above (`additionalProperties: false`, valid `plan_id`/`epic_id`, syntactic `link` pattern, `args` is a JSON object); a violation is answered with a JSON-RPC `-32602` invalid-params error.
2. *Stage 2 (Workflow Engine Link Schema)*: Under the scope's exclusive lock, the engine resolves the active `LinkSpec` for `link` in the current state and validates `args` against the link's dynamically derived closed JSON Schema (`additionalProperties: false`, exact required free parameter keys, closed enum values, string length bounds, and integer ranges). If `args` fails Stage 2 validation or `link` is not offered in the current state, the engine returns `isError: false` with a structured `rejected` block and the fresh representation (see <<protocol-errors-vs-domain-workflow-failure-states>>).

=== `pm_build` — Enrolled Build Execution

Submits or awaits a build job in the plan's worktree (or the primary repository checkout when `plan_id` is omitted) using one of the project's canonical build verbs (`compile`, `test`, `module-tests`, `quality-gate`, `verify`, `coverage`, `format-check`). The model never supplies shell commands or flags.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_build",
  "description": "Execute a canonical project build verb in the plan's worktree (or primary checkout when plan_id is omitted) via the integrated build runner.",
  "type": "object",
  "properties": {
    "plan_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Optional plan scope whose worktree the build runs in. When omitted, runs in the primary repository checkout (orchestrator/workspace scope)."
    },
    "command": {
      "type": "string",
      "enum": ["compile", "test", "module-tests", "quality-gate", "verify", "coverage", "format-check"],
      "description": "Closed build verb resolved against the project's domain configuration and enrolled wrapper."
    },
    "module": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_./:-]{0,127}$",
      "description": "Optional logical module identifier discovered in the project (never an arbitrary filesystem path)."
    },
    "test_filter": {
      "type": "string",
      "pattern": "^[A-Za-z0-9_.$#*-]{1,256}$",
      "description": "Optional test class or method filter when command is 'test' or 'module-tests'."
    },
    "expect": {
      "type": "string",
      "enum": ["green", "red"],
      "default": "green",
      "description": "Declared intent of the run; 'red' marks a deliberately failing run (for example a test written before its fix)."
    },
    "job_id": {
      "type": "string",
      "pattern": "^b-[0-9a-f]{4,16}$",
      "description": "Optional job_id of a running build returned earlier by pm_build; the call then continues waiting on that build for one bounded window (PM-TOOL-2, PM-IMPL-4) instead of starting a new one."
    }
  },
  "required": ["command"],
  "additionalProperties": false
}
----

==== `pm_build` TOON Output Contract

`pm_build` never returns raw console output. It returns a structured TOON result containing:

* `job_id`: unique build job identifier (e.g., `b-2291`)
* `status`: the closed job outcome enum (`succeeded`, `failed`, `failed_unparsed`, `refused`, `cancelled`, `timed_out`, `killed`, `indeterminate`; `PM-EXEC-4`) plus the non-terminal `running`
* `worktree_sha`: 64-character SHA-256 freshness digest of `HEAD` + staged + unstaged + untracked files, simultaneously appended to `change-ledger.jsonl` (`kind: "build"`)
* `summary`: counts of total/passed/failed/skipped tests and compiler/linter errors
* `failures`: tabular TOON array of located compiler errors or test failures (`file`, `line`, `column`, `rule_or_test`, `message`)
* `log_uri`: `pm://plan/{plan_id}/builds/{job_id}/log` (or `pm://workspace/builds/{job_id}/log` when `plan_id` is omitted; accompanied by the last 50 lines / 4 KB tail when `status == "failed_unparsed"`, `PM-IMPL-6`)

*Expected-red runs*: A failing run with `expect: red` is recorded as `expected_red` in the change ledger and files no finding; a passing run with `expect: red` is surfaced as `expected_red_went_green`. An `expect: red` run never satisfies a freshness gate.

==== Warm LSP Pool Lifecycle (`PM-SVC-2`)

* *Pool Keying & Lazy Spawn over `stdio`*: The runtime maintains a warm in-memory pool of LSP server child processes, shared by all host connections, keyed by `(canonical_worktree_path, language_id)` using language servers enrolled in `~/.plan-marshall/mcp/enrolments.json` and managed via `org.eclipse.lsp4j:org.eclipse.lsp4j` over `stdio`. Processes start lazily on the first `pm_lsp` or Axis C symbol-edge query and shut down automatically after `idle_timeout_seconds` (default 900s), when the plan worktree is removed, or when the runtime drains or stops.
* *Diagnostics (`diagnostics`)*: When the language server advertises the LSP 3.17 pull-diagnostics capability (`diagnosticProvider`), `pm-mcp` requests the file's current diagnostics with `textDocument/diagnostic`. Otherwise it returns the diagnostics the server last published for that file through the `textDocument/publishDiagnostics` notification, which the pool caches per document, and marks the result `source: published`.
* *Server-Applied `WorkspaceEdit` (`rename`)*: When `op == "rename"`, `pm-mcp` validates that every target URI in the LSP `WorkspaceEdit` resolves inside the plan's worktree (`PM-SEC-2`), applies the text edits atomically on disk, notifies the warm LSP server (`textDocument/didChange`), and appends all modified file paths to the plan's `references.json` realized footprint. A server answer without a `WorkspaceEdit` is a third outcome, returned as `status: success, applied: false, reason: no_workspace_edit` with nothing changed. A malformed `documentChanges` entry refuses the whole edit instead of being dropped silently, and a rollback is reported as `rolled_back: true` only after the restored bytes, line endings included, are verified identical to the originals.

=== Selective Upstream MCP Proxy & `_meta` Provenance (`PM-SVC-3`)
_See Requirement link:../Requirements.adoc#PM-SVC-3[PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging]_

When a project configures upstream MCP integrations (such as external issue trackers or documentation indexes), `pm-mcp` acts as a selective filter and provenance boundary:

1. *Allowlisted Tool Re-Exposure & Schema Narrowing*: Only upstream tools explicitly listed in the project configuration are re-exposed on the `pm-mcp` tool surface, with unused optional parameters stripped from their `inputSchema` to conserve resident context budget. Upstream skills are never re-exposed as PM-MCP vocabulary skills.
2. *Provenance Tagging (`_meta` key `de.cuioss.pm-mcp/source`)*: Every tool result or resource proxied from an upstream MCP server is wrapped with `_meta: {"de.cuioss.pm-mcp/source": "upstream_mcp:<server_id>", "de.cuioss.pm-mcp/trusted": false}`, using PM-MCP's own `_meta` key prefix (MCP `_meta` key prefix convention) so that provenance never collides with or is overwritten by keys the upstream server sets, and routed through the untrusted-ingestion validator (`PM-SEC-1`) before any candidate data can enter plan stores.
3. *Credential Isolation*: Upstream MCP connections authenticate using server-specific credentials resolved from `CredentialStore` (`<project>/mcp-<server_id>`) over `de.cuioss:cui-http` (or isolated `stdio` subprocess pipes); tokens from other providers are never forwarded.

== Skill Architecture & Retrieval Tool Schemas (`pm_skill`, `pm_skills`, `pm_skill_file`)

_See Requirement link:../Requirements.adoc#PM-SKILL-2[PM-SKILL-2: Per-Project Skill Generation & Digest Integrity]_

_See Requirement link:../Requirements.adoc#PM-SKILL-3[PM-SKILL-3: Standard MCP Tool & Resource Skill Delivery]_

=== Pure Vocabulary Skills & Dynamic Context Injection (`PM-SKILL-1`, `PM-SKILL-2`, `PM-SKILL-4`)

* *Pure Vocabulary Contract (`PM-SKILL-1`)*: All procedural sequencing, CLI invocations, file path templates, and phase transition rules live exclusively in the compiled workflow engine. Vocabulary skills (`skill://pm/<domain>/<topic>/SKILL.md`) contain strictly domain standards, quality rubrics, architectural principles, and judgment criteria.
* *Server-Generated & Client-Cached Catalogue (`PM-SKILL-2`)*: Vocabulary skills are compiled into the `pm-mcp` binary, filtered by the project's enabled domains in `.plan/marshal.json`, and translated on the fly for the active client profile (`PM-CLIENT-2`). Every rendered skill includes a deterministic `_meta.sha256` content digest (`SHA-256(canonical_skill_bytes + client_profile_digest + domain_config_digest)`) enabling client-side caching and invalidation: when the rendered content of a skill resource a client has subscribed to (`resources/subscribe`) changes, `pm-mcp` sends `notifications/resources/updated` for that URI; `notifications/resources/list_changed` is sent only when the set of available skill resources changes (for example, when a domain is enabled or disabled).
* *Dynamic State Context Injection (`PM-SKILL-4`)*: Live plan facts (`plan_id`, `worktree_sha`, active task summary, findings count, and valid `links`) are injected into the turn's TOON hypermedia representation (`skill` + `facts` + `links`), never baked into static `SKILL.md` files.
* *Core Conduct Vocabulary (`skill://pm/core`)*: The always-loaded core skill states at minimum: (1) a fix covers the whole co-reference population of the defect (derived with `pm_lsp references` or a search before editing), never only the named site; (2) every "only", "all", "none", or "the set is N" claim carries its enumeration and the scope it was derived over; (3) a case outside a closed vocabulary is reported with the vocabulary's out-of-set member, never mapped onto a stand-in member; (4) a re-derived count or coverage figure is checked against its population before it is reported; (5) plan state is read only through `pm_state` and `pm://` resources, never from `.plan/` files; (6) the correction a rejection names is applied before the call is retried, and a rejected call shape is never resubmitted unchanged; (7) an action taken outside the offered links (a bypass of a sanctioned path, a direct `.plan/` read or write) is reported with the `report_bypass` link (link:hypermedia-format.adoc#self-report-link[Hypermedia Format Specification, Self-Report Link]).

[#vocabulary-skill-rule-classification]
=== Vocabulary Skill Rule Classification

Every prescriptive rule that remains in a vocabulary skill after process ownership moved to the engine (`PM-ARCH-1`) carries exactly one class:

* *`engine`*: Enforced by link omission or server-side validation. The skill only names the rule; it is a candidate for deletion from resident content.
* *`check`*: Structural and violated in practice. Enforced by a deterministic check that needs no model call.
* *`guidance`*: Semantic and not decidable by a deterministic check. It stays guidance and becomes a measurement subject of the link:workflow-dsl.adoc#behavioural-conformance-harness[Behavioural Conformance Harness] (`PM-TEST-6`); any automated gate on it runs only under a stated cost ceiling.

Whether a `guidance` rule stays in resident content is decided by its recorded violation history (`PM-TEST-6` verdicts, audit rejections, and findings attributed to the rule); a rule with no recorded violation is a deletion candidate. The class is recorded per rule and carried into every behavioural scenario as its `enforcement_class`, so conformance reports group results by class: mechanically enforced rules and prose-only rules are different propositions and are never pooled into one rate.

=== `pm_skill` — Retrieve Vocabulary Skill Content

Fetches a rendered `SKILL.md` document by its canonical `skill://pm/.../SKILL.md` URI, along with its SHA-256 digest, supporting file list, and section index.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_skill",
  "description": "Retrieve a vocabulary skill document (SKILL.md) rendered for the active project and client profile.",
  "type": "object",
  "properties": {
    "uri": {
      "type": "string",
      "pattern": "^skill://pm/[a-z0-9/_-]+/SKILL\\.md$",
      "description": "Canonical skill URI referenced in a state representation's 'skill' field."
    },
    "section": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9_-]{0,127}$",
      "description": "Optional heading anchor from the document's section index; returns only that section."
    },
    "dispatch_id": {
      "type": "string",
      "pattern": "^dsp-[a-z0-9-]+-[0-9]{4}-[0-9a-f]{6}$",
      "description": "Optional; rendered by the server into the load directives of a dispatch prompt so the served-content ledger attributes the read. Never composed by the model."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Optional plan_id scope used to resolve the persisted client profile and project domain configuration."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Optional epic_id scope used to resolve the persisted client profile."
    }
  },
  "required": ["uri"],
  "additionalProperties": false
}
----

* *Section Index & Progressive Loading*: Every `pm_skill` and `pm_skill_file` result carries a section index computed by the server from the rendered document (`sections[]{anchor, title, level, bytes}`). Without `section`, the result carries the whole document beside the index; when the rendered document exceeds the server's inline threshold (one named constant, derived from the measured served-content distribution, link:store-schemas.adoc#metrics-store[Store Schemas Specification, Served-Content Ledger]), it carries the index instead of the body, with the total size, so the caller reads index first, then sections, then the whole document only when needed. With `section`, the result carries that section only, its `bytes`, and the index.
* *Three Distinct Section Outcomes*: A `section` that the index does not contain returns a tool execution error with `error_code: section_not_found` (naming the available anchors); a document the server cannot read or render returns `error_code: file_unreadable`; a section that exists but has no content returns `bytes: 0` with an empty body. None of the three is ever rendered as a silent empty result.
* *Served-Content Recording*: Every served read in a plan or epic scope appends a row to the served-content ledger (`uri`, `section`, `bytes`, `plan_id`, `phase`, `dispatch_id`), from which `record-metrics` publishes the per-document consumption. Host file reads are not observable and are never estimated.

=== Companion Catalogue, Supporting File Tools & MCP Resource Parity (`pm_skills`, `pm_skill_file`, `resources/read`)

* `pm_skills`: Accepts optional `plan_id` or `epic_id` (`additionalProperties: false`) and returns the tabular TOON catalogue of all vocabulary skills active for the project's enabled domains (`uri`, `name`, `description`, `sha256`). Catalogue descriptions (skills, execution-context variants, and tool descriptions) are single-line and bounded by a length limit derived from the measured distribution of the resident surface (link:client-profiles.adoc[Client Profiles Specification]); a build-time test enforces the bound. A change of description shape (for example from summary-shaped to trigger-shaped) is a separately justified change.
* `pm_skill_file`: Accepts required `uri` (`^skill://pm/[a-z0-9/_-]+/[a-zA-Z0-9_.-]+\.(md|adoc|json|toon)$`) and optional `plan_id`/`epic_id`, `section`, and `dispatch_id` with the same semantics as for `pm_skill` (`additionalProperties: false`) to retrieve progressive-disclosure reference files linked from a `SKILL.md`. Skill `resources/read` returns the whole document and publishes the section index in `_meta`; section reads are served by the two tools.
* *Standard MCP Resource Template Parity (`PM-SKILL-3`)*: `pm-mcp` simultaneously exposes the RFC 6570 templates `skill://pm/{+path}/SKILL.md` and `skill://pm/{+path}/{file}` (`{+path}` = one or more `/`-separated lowercase segments) via standard MCP `resources/templates/list` and `resources/read`. Unadopted draft custom RPC methods (`skills/list`, `skills/get`) are not exposed.

[#transitional-legacy-script-tool]
== Transitional Legacy Script Tool (`pm_legacy_script`)
_See Requirement link:../Requirements.adoc#PM-MIG-1[PM-MIG-1: Six-Stage Incremental Seam Migration]_

_See Requirement link:../Requirements.adoc#PM-MIG-2[PM-MIG-2: Exclusive Runtime per Machine & Routed Legacy Script Execution]_

_See Requirement link:../Requirements.adoc#PM-TOOL-5[PM-TOOL-5: Tool Schema Stability & Context Budget Discipline]_

After the machine cutover (Stage 1) the host can no longer run `execute-script.py`, while the workflows that are not yet served by the hypermedia engine still call unported `plan-marshall` scripts. `pm_legacy_script` is their only route. It is the one documented exception to the fixed tool set (`PM-TOOL-5`): it is registered only while unported scripts remain (Migration Stages 1–5) and is removed from the tool surface, the client bundles, and the host permissions at Stage 6.

=== `pm_legacy_script` — Run an Unported Script

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_legacy_script",
  "description": "Transitional (Migration Stages 1-5): run an unported plan-marshall script as a verified script job and return its result as TOON.",
  "type": "object",
  "properties": {
    "notation": {
      "type": "string",
      "pattern": "^[a-z][a-z0-9-]*:[a-z][a-z0-9-]*:[a-z][a-z0-9_-]*$",
      "maxLength": 192,
      "description": "Script notation {bundle}:{skill}:{script} (e.g., 'plan-marshall:manage-status:manage_status')."
    },
    "args": {
      "type": "array",
      "items": { "type": "string", "maxLength": 65536 },
      "maxItems": 128,
      "default": [],
      "description": "Argument vector passed to the script, validated against the script's registered argument schema."
    }
  },
  "required": ["notation"],
  "additionalProperties": false
}
----

1. *Registered Scripts Only*: `notation` must resolve to a script in the executor adapter's registry (verified script digest and pinned Python interpreter, `PM-EXEC-3`). A script that is not registered, including every ported or retired script, is refused with status `refused`.
2. *Argument Validation*: `args` is validated against the script's registered argument schema (closed subcommands and flags, typed values) before any process starts. Values are passed as discrete `argv` entries and never through a shell (`PM-EXEC-1`, `PM-SEC-5`).
3. *Verified `script` Job Under the Scope Lock*: The executor adapter runs the script as a `script` job in the working directory matching the plan's location (never setting `PLAN_BASE_DIR`, `PM-ARCH-5`). The addressed scope is taken from the plan identifier argument declared in the registered schema (the project scope for plan-less scripts); its lock is held for the whole job (`PM-MIG-2`), and the store digests are re-recorded afterwards (link:store-schemas.adoc[Store Schemas Specification]).
4. *TOON Result*: The result is a TOON document with the job `status` (closed job outcome enum, `PM-EXEC-4`), the script `exit_code`, and the script's own TOON output with secrets redacted (`PM-CRED-5`). A failing script is a normal tool result, not an MCP error.
5. *No Workflow Transition*: `pm_legacy_script` never advances the PM-MCP workflow state machine; hypermedia-served phases never emit instructions to call it.

[#protocol-errors-vs-domain-workflow-failure-states]
== Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)
_See Requirement link:../Requirements.adoc#PM-TOOL-4[PM-TOOL-4: Domain Failures as Valid Workflow States]_

_See Requirement link:../Requirements.adoc#PM-TEST-4[PM-TEST-4: End-to-End Scenario & Compaction Resume Testing]_

A foundational invariant of PM-MCP is that *domain failures and transition rejections are workflow states, not MCP protocol errors*. Three response classes are distinguished:

* *JSON-RPC protocol errors*: a JSON-RPC `error` response (no `CallToolResult`) for malformed JSON-RPC (`-32700` parse error, `-32600` invalid request), unknown tool names (`-32602`), and tool arguments that violate the tool's MCP `inputSchema` (`-32602` invalid params).
* *Tool execution errors*: a normal `CallToolResult` with `isError: true` when a schema-valid call cannot be executed (unknown scope, unenrolled project, missing entry record, unhandled server exception).
* *Domain results*: a normal `CallToolResult` with `isError: false` for every workflow outcome, including failures and rejected transitions (`PM-TOOL-4`).

=== Normative Classification Matrix

[cols="2,1,2,3"]
|===
|Condition |MCP Response Class |Response Structure |Model Recovery Path

|Valid transition succeeds (`pm_do`)
|`isError: false`
|Next state's TOON representation (`state`, `facts`, `links`).
|Follow one of the new `links`.

|Build fails, tests fail, or quality gate turns red
|`isError: false`
|TOON representation in a remediation state (e.g., `execute.verify.failed`, `finalize.ci-failed`) with structured failure facts and `fix`, `retry`, `loop_back`, or `escalate` links.
|Inspect failure facts (or `log_uri`), apply code fixes, and follow `fix` / `retry` / `loop_back`.

|Git push rejected (non-fast-forward) or merge conflict
|`isError: false`
|TOON representation in `git.sync-required` or `git.sync-escalate` (inside the `git.commit_and_push` sub-workflow) with `sync_rebase` (rel `fix`) / `escalate` links.
|Follow the offered `sync_rebase` or `escalate` link.

|Host tool modifies files outside the plan's worktree
|`isError: false`
|TOON representation in `<phase>.footprint-violation` naming the offending files and offering `fix` and `escalate` links.
|Inspect the named files; revert only changes this plan made, never baseline dirt (`facts.baseline_dirty`) or foreign changes, and follow `fix`, or `escalate` to the operator.

|Stale link followed, entity no longer in accepting state, or `args` fails link parameter validation
|`isError: false`
|Authoritative *current* TOON representation plus a top-level `rejected` block (`reason` from the closed set in <<rejection-reasons>>, `link`, `detail`).
|Read the current representation and follow one of its valid `links` with corrected `args`.

|Operator approval required or loop-back limit reached
|`isError: false`
|TOON representation in `*.blocked` offering `wait:decision:<decision_id>` (a bounded wait on the pending operator decision record), or `finalize.loop-limit-reached` offering `escalate`.
|Follow `escalate`, or `wait:decision:<decision_id>` until the operator resolves the decision.

|Malformed JSON-RPC, unknown tool name, or top-level tool `inputSchema` violation
|JSON-RPC error
|JSON-RPC `error` object (`-32700`, `-32600`, or `-32602`) whose `data` carries `audit_id`; no `CallToolResult`.
|Fix top-level tool invocation syntax.

|Unknown `plan_id` / `epic_id`, unenrolled workspace, missing pending entry record, or internal server exception
|`isError: true`
|MCP `CallToolResult` with `isError: true`, closed `error_code` (`scope_not_found`, `project_not_enrolled`, `entry_record_missing`, `internal_fault`), and `audit_id`.
|Halt or invoke discovery (`pm_plans` / `pm_epics`) or notify operator with `audit_id`.

|`pm_skill` / `pm_skill_file` names a section the document does not contain, or a document that cannot be read or rendered
|`isError: true`
|MCP `CallToolResult` with `isError: true`, closed `error_code` (`section_not_found` with the available anchors, or `file_unreadable`), and `audit_id`.
|Read the section index and request an existing anchor, or notify the operator with `audit_id`.
|===

=== Rejected Transition Representation (`isError: false`)

When `pm_do` is called with a stale link or invalid free parameter `args`, the server returns `isError: false` with a `rejected` block inserted into the current authoritative representation at its canonical position (after `skill`, before `facts`; see link:hypermedia-format.adoc#canonical-top-level-fields[Hypermedia Format Specification]). The example shows the `git.compose-message` state of the `git.commit_and_push` sub-workflow, active while the `finalize.push-barrier` call runs:

[source,toon]
----

plan_id: plan-x
state: git.compose-message
phase: finalize
summary: "push barrier found 2 uncommitted files, commit message required"
skill: "skill://pm/git/commit-message/SKILL.md"
rejected:
  link: commit
  reason: invalid_link_args
  detail: "parameter 'message' length 0 is below minimum 1"
facts:
  branch: feature/plan-x
  changed_files: 2
  module_scope: http
  suggested_type: fix
links[2]{rel,link,form,free}:
  next,commit,submit,"message:text[1..2000]"
  abort,abort,noop,""
----

[cols="1,3"]
|===
|`reason` |Condition

|`link_not_available`
|The link identifier is not offered in the current state, including invented or paraphrased identifiers.

|`stale_entity`

|`operator_only`

|The supplied `dispatch_id` is superseded or expired (link:dispatch-and-effort.adoc[Dispatch & Effort Specification]).

|`phase_closed`
|A finding submission is addressed to a phase the plan has already left (for example a `3-outline` Q-Gate finding after the plan entered `phase-4-plan`, link:phase-workflows.adoc[Phase Workflows Specification], Blocking Findings Guard); the finding is not written.

|`epic_pointer_mismatch`
|`pm_start` would create a plan whose `plan_id` equals a `launched` queue row of an epic while the consumed entry record's `from_epic` is absent or names another epic (link:dispatch-and-effort.adoc[Dispatch & Effort Specification], Single Epic Pointer).

|`plan_id_taken`
|The `plan_id` derived by `pm_start` already names a live, archived, or exported plan (link:phase-workflows.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]); an archived `plan_id` is never reused.

|`target_undeliverable`
|`mailbox_send:<plan_id>` names a plan that does not exist or is archived (link:dispatch-and-effort.adoc#plan-mailbox[Dispatch & Effort Specification, Plan Mailbox]); the message is not written.

|`path_traversal_rejected`
|A repository path in `args` escapes the workspace: a `..` segment, an absolute path, or a symlink resolving outside the plan's worktree (`PM-SEC-2`). Job requests carry the same reason with the job outcome `refused` (link:job-runtime.adoc[Job Runtime Specification]).
|===

A content validator that refuses a payload answers `invalid_link_args` and names its specific cause in `detail` (for example `non_resolving_package_key`, link:domain-extensions.adoc[Domain Extensions Specification]); such causes are `detail` codes, not reasons. Outcome, state, and finding tokens (a job's `refused`, the `store_tampered` block, surface states such as `untracked_surface`, finding types such as `unknown_config_key`) are never `rejected.reason` values.

A job that exceeds its budget is a job outcome (`timed_out`), never a rejection. Every rejection belongs to the failure class `caller_drift` (the call did not match the offered contract); a tool execution error (`isError: true`, carrying an `audit_id`) belongs to the class `server_fault`. The two classes are counted separately per plan (link:phase-workflows.adoc[Phase Workflows Specification], `record-metrics`), each with its population.

=== Sanitized Tool Execution Error Envelope (`isError: true`)

When a tool call cannot be executed (`isError: true`), the `TextContent` payload is strictly sanitized — stack traces, Java class names, filesystem paths, and credentials are never emitted:

[source,toon]
----
error: true
error_code: scope_not_found
audit_id: aud-20260925-004192
message: "Plan scope 'plan-unknown' does not exist in the enrolled workspace."
----

Closed `error_code` enumeration for `isError: true`:

* `scope_not_found` — Referenced `plan_id`, `epic_id`, or `entity` does not exist: the plan is in neither the primary checkout, a worktree, the plan archive, nor the project's export partition, or the epic or entity is unknown. An archived or exported plan is found and answered read-only with its terminal representation.
* `project_not_enrolled` — The target repository is not enrolled in `~/.plan-marshall/mcp/enrolments.json`.
* `entry_record_missing` — `pm_start` was called with an `entry_id` for which no pending entry record `.plan/local/mcp/pending/<entry_id>.json` exists (never written by `pm-mcp enter`, or already consumed).
* `section_not_found` — `pm_skill` or `pm_skill_file` named a `section` that the document's section index does not contain; the message lists the available anchors.
* `file_unreadable` — The requested skill document or supporting file exists in the catalogue but cannot be read or rendered.
* `internal_fault` — Unexpected server exception; full diagnostics are written exclusively to `audit.jsonl` under `audit_id`.

JSON-RPC protocol errors are sanitized the same way: the `error.message` is a fixed text per code and `error.data` carries only the `audit_id`.

=== End-to-End STDIO Integration Testing (`McpStdioTestClient` in `*IT.java`)

Failsafe integration tests (`*IT.java`) spawn the packaged `pm-mcp` runner JAR or GraalVM native executable as a real child process over `stdin`/`stdout` via `McpAssured.newStdioClient()`:

[source,java]
----
// The pending entry record is written first, as the user entry command does: `pm-mcp enter` prints its entry_id.
String entryId = runPmMcpEnter(pmMcpBinaryPath, tempWorkspaceRoot);

McpStdioTestClient client = McpAssured.newStdioClient()
    .setCommand(List.of(pmMcpBinaryPath.toString(), "serve"))
    .setWorkingDirectory(tempWorkspaceRoot)
    .setEnvironment(Map.of("PLAN_MARSHALL_HOME", tempMarshallHome.toString()))
    .setStderrHandler(stderrAuditBuffer::add)
    .build()
    .connect();

client.when()
    .toolsList(page -> {
        assertThat(page.tools())
            .extracting(ToolInfo::name)
            .containsExactlyInAnyOrder(
                "pm_start", "pm_state", "pm_do", "pm_plans", "pm_epics",
                "pm_build", "pm_lsp", "pm_skills", "pm_skill", "pm_skill_file");
    })
    .toolsCall("pm_start", Map.of("entry_id", entryId, "request", "Add JSpecify null-safety to service layer", "plan_slug", "null-safety"), response -> {
        assertThat(response.isError()).isFalse();
        assertThat(response.content().getFirst().asText().text())
            .contains("scope: plan")
            .contains("phase: init");
    })
    .thenAssertResults();
----

=== Normative `McpAssured` Verification Requirements

1. *Tool & Resource Schema Conformance*: Every `@Tool` and `@ResourceTemplate` is asserted via `client.when().toolsList(...)` and `client.when().resourcesTemplatesList(...)` to verify closed JSON Schema Draft 2020-12 `inputSchema` definitions (`additionalProperties: false`) and exact URI template registrations. The example asserts the Stage 6 tool set; during Migration Stages 1–5 the expected list additionally contains the transitional `pm_legacy_script`.
2. *Domain Failure vs Protocol Error Assertions*: Every `pm_do` rejection and domain failure state is asserted with `assertThat(response.isError()).isFalse()`, unknown scope queries are asserted with `assertThat(response.isError()).isTrue()` and sanitized `error_code` + `audit_id` payloads, and unknown tools and top-level schema violations are asserted as JSON-RPC error responses (`-32602`) without a `CallToolResult`.
3. *`stdout` Stream Hygiene & `stderr` Separation*: `setStderrHandler(...)` captures all diagnostic output on `stderr` while `McpStdioTestClient` parses every `stdout` line as a strict JSON-RPC 2.0 frame, proving zero `stdout` pollution across concurrent `pm_build` and `pm_lsp` executions (`PM-SEC-4`, `PM-TEST-5`).
