== Overview

This document defines the normative Model Context Protocol (MCP) tool schemas, resource URI templates, skill delivery surface, and error/result envelope contracts for *plan-marshall-mcp* (`PM-MCP`). It specifies the JSON Schema (Draft 2020-12) definitions for the core workflow verbs (`pm_start`, `pm_state`, `pm_do`), discovery tools (`pm_plans`, `pm_epics`), orthogonal service tools (`pm_build`, `pm_lsp`), and tool-based skill retrieval (`pm_skill`, `pm_skills`, `pm_skill_file`), alongside the strict separation between JSON-RPC protocol errors, tool execution errors (`isError: true`), and domain workflow failure states (`isError: false`).

=== Architectural Constraints

1. *Small, Stable Verb Set*: PM-MCP exposes a fixed set of top-level MCP tools (`pm_start`, `pm_state`, `pm_do`, `pm_plans`, `pm_epics`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`) rather than one tool per workflow step or script. Across all phases and domains, the resident core tool surface remains constant, and privileged operator actions are strictly excluded from the MCP tool surface (`PM-SEC-3`). The only additional tools are the operator-allowlisted upstream pass-through tools (<<_selective_upstream_mcp_proxy_meta_provenance_pm_svc_3>>), which change only with the operator's allowlist and are never part of the core set. The set has no exception: no tool runs legacy `plan-marshall` scripts (<<transitional-legacy-script-tool>>).
2. *Portable Naming Convention*: Every core tool name conforms to the link:identifiers.adoc#id-core-tool-name[core tool name grammar] and every upstream pass-through tool name to the link:identifiers.adoc#id-upstream-tool-name[upstream tool name grammar] (Identifier Registry), ensuring identical identifiers across Claude Code, OpenCode, Antigravity, Codex, and raw model tool-calling APIs without escaping or translation.
3. *Closed, Host-Portable Flat Schemas*: Every tool `inputSchema` conforms to JSON Schema Draft 2020-12 and declares `"additionalProperties": false` at the top-level object boundary. It uses only the subset every supported host and provider API accepts: a top-level `type: object` with `properties`, `required` (only parameters that are always required), and `additionalProperties`; per property `type`, `enum`, `pattern` without lookaround, `minimum`/`maximum`, `minLength`/`maxLength`, `default`, and `description`. Top-level `oneOf`/`anyOf`/`allOf`, `if`/`then`/`else`, `not`, and `const` are never used; the `$schema` and `title` members shown in this specification are documentation only and are not sent in `tools/list`. Rules the subset cannot express (mutually exclusive scope parameters, alternative plan sources, per-operation required parameters, path shape) are enforced by the server's argument validation and answered with the closed error of <<protocol-errors-vs-domain-workflow-failure-states>>; each such rule is stated in one line of the affected property's `description`. Milestone 1 verifies the final schemas by registering and calling them on every supported host.
4. *TOON Text Output Only (No `outputSchema`)*: Tools intentionally omit `outputSchema` and `structuredContent`. Every tool result is returned in a single MCP `TextContent` block (`type: "text"`) encoded in deterministic TOON (link:hypermedia-format.adoc[Hypermedia Format Specification]). This avoids resident output-schema token overhead while optimizing token density on every turn.
5. *Zero Client-Supplied Filesystem Paths*: No workflow or service tool accepts absolute filesystem paths or worktree locations from the model. Worktrees, branches, and configuration files are resolved server-side from `plan_id` or `epic_id`.
6. *On-Demand Preloading*: For hosts configured with `schema_residency: "on_demand"` in their client profile, the user entry command preloads `pm_start`, `pm_state`, and `pm_do` so workflow execution incurs zero schema-lookup round trips.
7. *Canonical Identifiers*: Every identifier property (`plan_id`, `epic_id`, `entry_id`, `entity`, `link`, `dispatch_id`, `job_id`, `lesson_id`, `recipe_id`, `plan_slug`, `module`, skill `uri` and `section`) uses the grammar of the link:identifiers.adoc[Identifier Registry] (`plan_id` and `epic_id`: link:identifiers.adoc#id-plan-id[`plan_id`]; the derivation rules stay in link:phase-workflows.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]); every `pattern` below equals the registry grammar, and every example in this specification conforms to it.
8. *Model-Facing Minimality*: Every tool result and error payload, like every representation, carries only fields with an operational purpose for the model (link:hypermedia-format.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). Implementation variants, derivation sources, internal versions and digests, confinement, timing, and audit identifiers (outside `internal_fault` and `file_unreadable`) are recorded in `audit.jsonl`, the job record, or the metrics store and served by `pm-mcp status` or the operator CLI; `ModelFacingFieldAuditTest` checks every result record against the registry of model-facing fields.

=== `pm_start` — Initialize a Plan Scope
_Implementation watch: link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-2[PM-WATCH-STORE-2]_

Creates a new plan directory from exactly one of the six supported initialization sources (`request`, `issue_number`, `lesson_id`, `recipe_id`, `local_changes`, or `pr_number`) following a plan-mode `pm-mcp enter` invocation, consumes the pending entry record `<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>.json` whose `entry_id` that invocation printed, in the plan initialization transaction: its session row becomes the first row of the new plan's session log `plans/<plan_id>/sessions.jsonl` of the same per-project machine store and the pending file is deleted (link:store-schemas.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]), initializes `mcp/status.json`, and returns the initial TOON hypermedia representation. Concurrent entries for different new plans therefore never share a slot. Epic membership has one carrier, `origin.epic_id` of the plan's `mcp/status.json`, which `pm_start` fills from the consumed pending entry record's `from_epic` (written by the emitted `pm-mcp enter … --from-epic <epic_id>` command); the tool has no epic parameter. With source `lesson`, `pm_start` claims the lesson in the same transaction (link:store-schemas.adoc#lesson-record[Store Schemas Specification, Lesson Record, Claim]); an unavailable lesson refuses the start. When the new `plan_id` equals a `launched` queue row of an epic and `from_epic` is absent or names another epic, `pm_start` is refused with `epic_pointer_mismatch` (link:dispatch-and-effort.adoc[Dispatch & Effort Specification], Single Epic Pointer). Parameter names follow the `<entity>_id` naming rule of the link:identifiers.adoc[Identifier Registry] (`plan_slug`, `epic_id`, `plan_id`); this is a PM-MCP rule and deliberately differs from `plan-marshall`'s proposed ADR-023, which names the epic with the bare entity noun (`--epic`).

[#pm-start-refusal]
==== `pm_start` Refusals

A refused `pm_start` (`plan_id_taken`, `epic_pointer_mismatch`, `no_local_changes`, `capability_missing`, `integration_variant_unset`, `config_dirty`, `config_invalid`, `format_outdated`, `format_newer`, `lesson_unavailable`, or a `recipe_params` violation) creates no plan and returns `isError: false` with a scope-less representation: `scope: none`, no `state`, a `rejected` block (`link: pm_start`, closed `reason`, `detail`), `facts` with the server-computed alternatives, and `links[0]` (without a scope there is no `pm_do`). For `plan_id_taken`, `facts` names the existing `plan_id` and where it exists (live or archived) and a free alternative `plan_slug` derived by the server; for `epic_pointer_mismatch`, it names the epic whose `launched` row matched; for `no_local_changes`, it names the base branch the capture compared against; for `capability_missing`, it names the `reason` (`head_not_writable`: the agent identity cannot push to the head branch of the pull request named by `pr_number`, for example a fork) and the pull request; for `integration_variant_unset`, it names the undecided integrations and the operator command that decides them; for `config_dirty`, it names the porcelain state of the dirty files under `.marshall/config/` and the operator's two resolutions (commit or restore); for `config_invalid`, `format_outdated`, and `format_newer`, it names the file and the finding. The pending entry record `<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>.json` is consumed only by a successful `pm_start`; after a refusal it stays in place, so a retry with a corrected `plan_slug` uses the same `entry_id`, and an abandoned record is removed by the runtime's pending-record sweep.

----

  "properties": {
    "entry_id": {
      "type": "string",
      "pattern": "^ent-[0-9a-f]{8,32}$",
      "description": "Identifier printed by 'pm-mcp enter' for the pending entry record this plan consumes."
    },
    "request": {
      "type": "string",
      "minLength": 1,
      "maxLength": 65536,
      "description": "Free-form user request or problem statement for the new plan. Exactly one of request, issue_number, lesson_id, recipe_id, local_changes, pr_number is required (server-enforced)."
    },
    "issue_number": {
      "type": "integer",
      "minimum": 1,
      "description": "GitHub/GitLab issue number to fetch via the enrolled CI CLI as the plan source."
    },
    "lesson_id": {
      "type": "string",
      "pattern": "^[0-9]{4}-[0-9]{2}-[0-9]{2}-[0-9]{2}-[0-9]{3,}$",
      "maxLength": 64,
      "description": "Lesson-learned identifier to convert into a remediation plan (runs premise check and claims the lesson for the plan; the lesson file stays in the lesson store)."
    },
    "recipe_id": {
      "type": "string",
      "pattern": "^[a-z][a-z0-9]*(-[a-z0-9]+)*$",

    },
    "local_changes": {

=== `pm_state` — Query Authoritative Hypermedia State

Returns the current hypermedia representation (`state`, `summary`, `skill` URI, domain `facts`, and valid `links`) for a `plan_id`, an `epic_id`, or the project's workspace scope (`scope: "workspace"`, resolved from the `PM-MCP-Workspace` header, `PM-ARCH-4`; it hosts `project-setup`). When `entity` (and optional `scope: "entity"`) is supplied by a dispatched sub-agent, returns the leaf-scoped representation for that entity (e.g., task envelope `envelope-2` or finding `F-12`) and claims `dispatch_id` if provided.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_state",
  "description": "Return the current TOON hypermedia representation and valid links for a plan, epic, the project workspace, or a sub-agent entity.",
  "type": "object",
  "properties": {
    "scope": {
      "type": "string",
      "enum": ["plan", "epic", "entity", "workspace"],
      "description": "Optional explicit scope discriminator (inferred from plan_id/epic_id/entity when omitted)."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target plan scope. Exactly one of plan_id, epic_id, or scope=workspace is required (server-enforced)."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target orchestrator epic scope. Mutually exclusive with plan_id."
    },
    "entity": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$",
      "description": "Optional entity identifier within the plan or epic (e.g., 'envelope-1', 'F-12') for sub-agent scope."
    },
    "dispatch_id": {
      "type": "string",
      "pattern": "^dsp-[0-9]{4}-[0-9a-f]{6}$",
      "description": "Optional dispatch tracking identifier supplied by a dispatched sub-agent on its initial call."
    }
  },
  "additionalProperties": false
}
----

NOTE: Companion discovery tools `pm_plans` (zero-argument, `{"type": "object", "properties": {}, "additionalProperties": false}`) and `pm_epics` (one optional boolean `include_archived`, default `false`, `additionalProperties: false`) return a tabular TOON listing of active plans or epics in the enrolled workspace; `pm_epics` with `include_archived` also lists archived epics (`.marshall/archived-orchestrators/`, link:filesystem-layout.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]) with their archival date. Both always return a `coverage` table with one row per scanned root (`root`, `exists`, `listed`, `entries_scanned`, `unreadable`), so zero rows are distinguishable from a root that was absent or not scanned. Each listing carries a `last_entered` column that marks one scope (`PM-CLIENT-6`): the scope whose session log (link:store-schemas.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]) holds the most recent row with the `client_session_id` that the request's `PM-MCP-Client-Session` header carries (link:runtime-model.adoc[Runtime & Interaction Model Specification], Connection Metadata); when the request carries no session identifier or no row matches it, the scope with the most recent session row (`last_seen_at`) in the project's workspace. This is the post-compaction scope pointer on hosts without session lifecycle hooks (link:client-profiles.adoc#session-lifecycle-hook[Client Profiles Specification, Session Lifecycle Hook & Scope Pointer]).

=== `pm_do` — Follow a Hypermedia Link
_Implementation watch: link:../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-1[PM-WATCH-TOOL-1]_

The sole state transition verb in PM-MCP. Executes the transition identified by `link` from the current representation of `plan_id`, `epic_id`, or the workspace scope (`scope: "workspace"`), passing any judgment parameters in `args`.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_do",
  "description": "Follow a hypermedia link from the current representation with its required free parameters.",
  "type": "object",
  "properties": {
    "scope": {
      "type": "string",
      "enum": ["plan", "epic", "entity", "workspace"],
      "description": "Optional explicit scope discriminator."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target plan scope. Exactly one of plan_id, epic_id, or scope=workspace is required (server-enforced)."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target orchestrator epic scope. Mutually exclusive with plan_id."
    },
    "entity": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$",
      "description": "Optional entity identifier when invoked by a dispatched leaf sub-agent."
    },
    "link": {
      "type": "string",
      "pattern": "^[a-z][a-z0-9_-]{0,31}(:(decision:)?[A-Za-z0-9][A-Za-z0-9_.-]{0,63})?$",
      "maxLength": 106,
      "description": "Link identifier from the current representation (e.g., 'push', 'triage:F-12', 'wait:b-2291', 'wait:decision:dec-7f3a', 'returned:dsp-0001-a9f3c2')."
    },
    "args": {
      "type": "object",
      "default": {},
      "description": "Free parameters required by the target link, validated server-side against the link's closed parameter schema."
    },
    "dispatch_id": {
      "type": "string",
      "pattern": "^dsp-[0-9]{4}-[0-9a-f]{6}$",
      "description": "Optional dispatch identifier when invoked by a dispatched leaf sub-agent."
    }
  },
  "required": ["link"],
  "additionalProperties": false
}
----

==== Two-Stage Schema Validation for `pm_do`

1. *Stage 1 (Tool Argument Validation)*: The server's own argument validator (plain Java over the flat schema and the rules stated in the property descriptions; no JSON Schema library) checks the payload: `additionalProperties: false`, valid `plan_id`/`epic_id`, exactly one scope, syntactic `link` pattern, `args` is a JSON object. A violation is a tool execution error: `isError: true`, `error_code: invalid_arguments`, the offending `parameter`, and the violated `rule` (<<protocol-errors-vs-domain-workflow-failure-states>>). The Quarkus MCP server runs with `quarkus.mcp.server.tools.input-validation-error=TOOL`, so its own parameter binding reports the same way.
2. *Stage 2 (Workflow Engine Link Schema)*: Under the scope's exclusive lock, the engine resolves the active `LinkSpec` for `link` in the current state and validates `args` against the link's dynamically derived closed JSON Schema (`additionalProperties: false`, exact required free parameter keys, closed enum values, string length bounds, and integer ranges). If `args` fails Stage 2 validation or `link` is not offered in the current state, the engine returns `isError: false` with a structured `rejected` block and the fresh representation (see <<protocol-errors-vs-domain-workflow-failure-states>>).

=== `pm_build` — Enrolled Build Execution
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-11[PM-WATCH-JOB-11]_

Submits or awaits a build job in the plan's worktree (or the primary repository checkout when `plan_id` is omitted; such a plan-less build is workspace-addressed, `PM-ARCH-4`, and writes its `change-ledger.jsonl` row, findings, and log into the workspace home `<PM_MCP_BASE>/projects/<project_id>/workspace/`) using one of the canonical build verbs (link:job-runtime.adoc#canonical-build-verbs[Job Runtime Specification, Canonical Build Verb Set]; the `command` enum below equals it). The gate scope of the run follows from `module` alone: without `module` the build runs whole-tree, with it only that module. The call blocks for one bounded or progress wait window (link:timeouts.adoc#bounded-wait[Timeouts & Budgets Specification]). The model never supplies shell commands or flags.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_build",
  "description": "Execute a canonical project build verb in the plan's worktree (or primary checkout when plan_id is omitted) via the integrated build runner.",
  "type": "object",
  "properties": {
    "plan_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Optional plan scope whose worktree the build runs in. When omitted, runs in the primary repository checkout as a workspace-addressed request; its ledger row, findings, and log belong to the workspace scope."
    },
    "command": {
      "type": "string",
      "enum": ["clean", "compile", "test-compile", "module-tests", "integration-tests", "e2e", "coverage", "benchmark", "quality-gate", "arch-gate", "verify", "install", "clean-install", "package"],
      "description": "Canonical build verb (job-runtime.adoc, Canonical Build Verb Set) resolved against the project's enrolled or compiled default template and enrolled wrapper."
    },
    "module": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,56}$",

==== `pm_build` TOON Output Contract

`pm_build` never returns raw console output. It returns a structured TOON result containing:

* `job_id`: unique build job identifier in the `b-` form of the link:identifiers.adoc#id-job-id[`job_id` grammar] (e.g., `b-2291`)
* `status`: the closed job outcome enum (`succeeded`, `failed`, `failed_unparsed`, `refused`, `cancelled`, `timed_out`, `killed`, `indeterminate`; `PM-EXEC-4`, derived by link:job-runtime.adoc#outcome-derivation[Job Runtime Specification, Outcome Derivation]) plus the non-terminal `running`
* `summary`: counts of total/passed/failed/skipped tests and compiler/linter errors
* `failures`: tabular TOON array of located compiler errors or test failures (`file`, `line`, `column`, `rule_or_test`, `message`)
* `log_uri`: `pm://plan/{plan_id}/builds/{job_id}/log` (or `pm://workspace/builds/{job_id}/log` when `plan_id` is omitted; accompanied by the last 50 lines / 4 KB tail when `status == "failed_unparsed"`, `PM-IMPL-6`)

*Recorded, never returned*: The working-tree digest the build ran against (`worktree_sha` with its `worktree_sha_version`, or `unavailable` with its `worktree_sha_failure`; link:job-runtime.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash]) is stamped on the job's `change-ledger.jsonl` row (`kind: "build"`) and in its job record, where the freshness gates read it; the model makes no decision on it. The allocated budget with its `budget_derivation`, the build template source, the job's `confinement`, the build-slot cap and its source, and the job timing are likewise job-record data, shown by `pm-mcp status` (link:hypermedia-format.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

*Expected-red runs*: A failing run with `expect: red` is recorded as `expected_red` in the change ledger and files no finding; a passing run with `expect: red` is surfaced as `expected_red_went_green`. An `expect: red` run never satisfies a freshness gate.

*Position Semantics*: Every `pm_lsp` input and output position is 1-based in lines and in columns, and a column counts Unicode code points of the line as stored on disk. The server negotiates the LSP `positionEncoding` with the language server (preferring `utf-32`, then `utf-8`, falling back to `utf-16`) and converts positions in both directions from the file content; a position beyond the end of its line, or beyond the last line, is refused with `invalid_arguments` and never clamped.

==== Warm LSP Pool Lifecycle (`PM-SVC-2`)
_Implementation watch: link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-11[PM-WATCH-EXT-11], link:../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-4[PM-WATCH-TOOL-4]_

* *Pool Keying & Lazy Spawn over `stdio`*: The runtime maintains a warm in-memory pool of LSP server child processes, shared by all host connections, keyed by `(canonical_worktree_path, language_id)` using language servers enrolled in the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json`and managed via `org.eclipse.lsp4j:org.eclipse.lsp4j` over `stdio`. Processes start lazily on the first `pm_lsp` or Axis C symbol-edge query and shut down automatically after the language server idle timeout (`lsp_idle_timeout_seconds` in `machine-config.json`), when the plan worktree is removed, or when the runtime drains or stops; the idle, start, and request timeouts are defined in link:timeouts.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle].
* *Diagnostics (`diagnostics`)*: When the language server advertises the LSP 3.17 pull-diagnostics capability (`diagnosticProvider`), `pm-mcp` requests the file's current diagnostics with `textDocument/diagnostic`. Otherwise it returns the diagnostics the server last published for that file through the `textDocument/publishDiagnostics` notification, which the pool caches per document, and marks the result `source: published`.
* *Server-Applied `WorkspaceEdit` (`rename`)*: When `op == "rename"`, `pm-mcp` validates that every target URI in the LSP `WorkspaceEdit` resolves inside the plan's worktree (`PM-SEC-2`), applies the text edits atomically on disk, notifies the warm LSP server (`textDocument/didChange`), and appends all modified file paths to the plan's `references.json` realized footprint. A server answer without a `WorkspaceEdit` is a third outcome, returned as `status: success, applied: false, reason: no_workspace_edit` with nothing changed. A malformed `documentChanges` entry refuses the whole edit instead of being dropped silently, and a rollback is reported as `rolled_back: true` only after the restored bytes, line endings included, are verified identical to the originals.
* *Corpus Cross-Reference Integrity*: The marketplace corpus language server in the pool exposes cross-reference integrity (links between skills, standards, and documents) through the LSP `documentLink` request, so a broken reference is an LSP-visible fact rather than a separate scan; its per-language cost stays at the warm-pool tier.

=== Selective Upstream MCP Proxy & `_meta` Provenance (`PM-SVC-3`)
_See Requirement link:../Requirements.adoc#PM-SVC-3[PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging]_

`pm-mcp` is the host's single MCP entry point: upstream MCP servers (such as external issue trackers or documentation indexes) are connected once by the runtime and reached through it, and `pm-mcp` acts as their selective filter and provenance boundary:

1. *Operator-Owned Allowlist*: Upstream servers, the tools re-exposed per server, and their credential keys are configured only in `<PM_MCP_BASE>/conf/upstream-mcp.json`, per enrolled project (the operator CLI writes it; `PM-SEC-3`). Repository content, including the team configuration under `.marshall/config/`, never adds a server or a tool.
2. *Pass-Through Surface & Schema Narrowing*: Allowlisted tools are listed to the host as `up_<server_id>_<tool>` next to the core `pm_*` tools, with unused optional parameters stripped from their `inputSchema` to conserve resident context budget. The pass-through set is computed per request from the request's `PM-MCP-Workspace` header and the allowlist; it changes only when the operator changes the allowlist, and hosts see the change at their next `tools/list`. Upstream resources and prompts are not passed through, and upstream skills are never re-exposed as PM-MCP vocabulary skills.
3. *Server-Side Use by Workflow Steps*: A workflow step may call an allowlisted upstream tool server-side; its result enters plan stores only through the untrusted-ingestion validator (`PM-SEC-1`), never verbatim.
4. *Provenance Tagging (`_meta` key `de.cuioss.pm-mcp/source`)*: Every tool result or resource proxied from an upstream MCP server is wrapped with `_meta: {"de.cuioss.pm-mcp/source": "upstream_mcp:<server_id>", "de.cuioss.pm-mcp/trusted": false}`, using PM-MCP's own `_meta` key prefix (MCP `_meta` key prefix convention) so that provenance never collides with or is overwritten by keys the upstream server sets, and routed through the untrusted-ingestion validator (`PM-SEC-1`) before any candidate data can enter plan stores.
5. *Credential Isolation*: Upstream MCP connections authenticate using server-specific credentials resolved from `CredentialStore` (`<project>/mcp-<server_id>`) over `de.cuioss:cui-http` (or isolated `stdio` subprocess pipes); tokens from other providers are never forwarded.

=== Pure Vocabulary Skills & Dynamic Context Injection (`PM-SKILL-1`, `PM-SKILL-2`, `PM-SKILL-4`)
_Implementation watch: link:../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-6[PM-WATCH-TOOL-6]_

* *Pure Vocabulary Contract (`PM-SKILL-1`)*: All procedural sequencing, CLI invocations, file path templates, and phase transition rules live exclusively in the compiled workflow engine. Vocabulary skills (`skill://pm/<path>/SKILL.md`) contain strictly domain standards, quality rubrics, architectural principles, and judgment criteria.
* *Server-Generated & Client-Cached Catalogue (`PM-SKILL-2`)*: Vocabulary skills are compiled into the `pm-mcp` binary, filtered by the project's enabled domains (derived, with the overrides of `.marshall/config/domains.json`), and translated on the fly for the active client profile (`PM-CLIENT-2`). Every rendered skill includes a deterministic `_meta.sha256` content digest (`_meta["de.cuioss.pm-mcp/sha256"]`: the SHA-256 of exactly the rendered bytes the client receives, after profile translation and domain filtering, so it changes exactly when those bytes change) enabling client-side caching and invalidation: the runtime is sessionless (link:runtime-model.adoc[Runtime & Interaction Model Specification], Connection Metadata), so it offers no resource subscriptions and sends no `notifications/resources/updated` or `list_changed`; a client detects a changed skill by its digest, which every catalogue listing and every representation that names the skill carries.
* *Dynamic State Context Injection (`PM-SKILL-4`)*: Live plan facts (`plan_id`, active task summary, open findings count, and valid `links`) are injected into the turn's TOON hypermedia representation (`skill` + `facts` + `links`), never baked into static `SKILL.md` files.
* *Core Conduct Vocabulary (`skill://pm/core`)*: The always-loaded core skill states at minimum: (1) a fix covers the whole co-reference population of the defect (derived with `pm_lsp references` or a search before editing), never only the named site; (2) every "only", "all", "none", or "the set is N" claim carries its enumeration and the scope it was derived over; (3) a case outside a closed vocabulary is reported with the vocabulary's out-of-set member, never mapped onto a stand-in member; (4) a re-derived count or coverage figure is checked against its population before it is reported; (5) plan state is read only through `pm_state` and `pm://` resources, never from `.marshall/` files; (6) the correction a rejection names is applied before the call is retried, and a rejected call shape is never resubmitted unchanged; (7) an action taken outside the offered links (a bypass of a sanctioned path, a direct `.marshall/` read or write) is reported with the `report_bypass` link (link:hypermedia-format.adoc#self-report-link[Hypermedia Format Specification, Self-Report Link]).

[#vocabulary-skill-rule-classification]
=== Vocabulary Skill Rule Classification

Every prescriptive rule that remains in a vocabulary skill after process ownership moved to the engine (`PM-ARCH-1`) carries exactly one class:

* *`engine`*: Enforced by link omission or server-side validation. The skill only names the rule; it is a candidate for deletion from resident content.
* *`check`*: Structural and violated in practice. Enforced by a deterministic check that needs no model call.
* *`guidance`*: Semantic and not decidable by a deterministic check. It stays guidance and becomes a measurement subject of the link:workflow-dsl.adoc#behavioural-conformance-harness[Behavioural Conformance Harness] (`PM-TEST-6`); any automated gate on it runs only under a stated cost ceiling.

Whether a `guidance` rule stays in resident content is decided by its recorded violation history (`PM-TEST-6` verdicts, audit rejections, and findings attributed to the rule); a rule with no recorded violation is a deletion candidate. The class is recorded per rule and carried into every behavioural scenario as its `enforcement_class`, so conformance reports group results by class: mechanically enforced rules and prose-only rules are different propositions and are never pooled into one rate.

=== `pm_skill` — Retrieve Vocabulary Skill Content

Fetches a rendered `SKILL.md` document by its canonical `skill://pm/.../SKILL.md` URI, along with its SHA-256 digest, supporting file list, and section index.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_skill",
  "description": "Retrieve a vocabulary skill document (SKILL.md) rendered for the active project and client profile.",
  "type": "object",
  "properties": {
    "uri": {
      "type": "string",
      "pattern": "^skill://pm/[a-z0-9][a-z0-9_-]*(/[a-z0-9][a-z0-9_-]*)*/SKILL\\.md$",
      "maxLength": 256,
      "description": "Canonical skill URI referenced in a state representation's 'skill' field."
    },
    "section": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9_-]{0,127}$",
      "description": "Optional heading anchor from the document's section index; returns only that section."
    },
    "dispatch_id": {
      "type": "string",
      "pattern": "^dsp-[0-9]{4}-[0-9a-f]{6}$",
      "description": "Optional; rendered by the server into the load directives of a dispatch prompt so the served-content ledger attributes the read. Never composed by the model."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Optional plan_id scope used to resolve the persisted client profile and project domain configuration."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Optional epic_id scope used to resolve the persisted client profile."
    }
  },
  "required": ["uri"],
  "additionalProperties": false
}
----

* *Section Index & Progressive Loading*: Every `pm_skill` and `pm_skill_file` result carries a section index computed by the server from the rendered document (`sections[]{anchor, title, level, bytes}`). Without `section`, the result carries the whole document beside the index; when the rendered document exceeds the server's inline threshold (one named constant, derived from the measured served-content distribution, link:store-schemas.adoc#metrics-store[Store Schemas Specification, Served-Content Ledger]), it carries the index instead of the body, with the total size, so the caller reads index first, then sections, then the whole document only when needed. With `section`, the result carries that section only, its `bytes`, and the index.
* *Three Distinct Section Outcomes*: A `section` that the index does not contain returns a tool execution error with `error_code: section_not_found` (naming the available anchors); a document the server cannot read or render returns `error_code: file_unreadable`; a section that exists but has no content returns `bytes: 0` with an empty body. None of the three is ever rendered as a silent empty result.
* *Served-Content Recording*: Every served read in a plan or epic scope appends a row to the served-content ledger (`uri`, `section`, `bytes`, `plan_id`, `phase`, `dispatch_id`), from which `record-metrics` publishes the per-document consumption. Host file reads are not observable and are never estimated.

=== Companion Catalogue, Supporting File Tools & MCP Resource Parity (`pm_skills`, `pm_skill_file`, `resources/read`)

* `pm_skills`: Accepts optional `plan_id` or `epic_id` (`additionalProperties: false`) and returns the tabular TOON catalogue of all vocabulary skills active for the project's enabled domains (`uri`, `name`, `description`, `sha256`). Catalogue descriptions (skills, execution-context variants, and tool descriptions) are single-line and bounded by a length limit derived from the measured distribution of the resident surface (link:client-profiles.adoc[Client Profiles Specification]); a build-time test enforces the bound. A change of description shape (for example from summary-shaped to trigger-shaped) is a separately justified change.
* `pm_skill_file`: Accepts required `uri` (supporting file form of the link:identifiers.adoc#id-skill-uri[skill URI grammar]) and optional `plan_id`/`epic_id`, `section`, and `dispatch_id` with the same semantics as for `pm_skill` (`additionalProperties: false`) to retrieve progressive-disclosure reference files linked from a `SKILL.md`. Skill `resources/read` returns the whole document and publishes the section index in `_meta`; section reads are served by the two tools.
* *Standard MCP Resource Template Parity (`PM-SKILL-3`)*: `pm-mcp` simultaneously exposes the RFC 6570 templates `skill://pm/{+path}/SKILL.md` and `skill://pm/{+path}/{file}` (`{+path}` = one or more `/`-separated lowercase segments) via standard MCP `resources/templates/list` and `resources/read`. Unadopted draft custom RPC methods (`skills/list`, `skills/get`) are not exposed.

|`pm://architecture/neighbours/{module_id}`
|`text/toon`
|Project
|Direct upstream dependencies and downstream dependents of `{module_id}`.

|`pm://architecture/impact?modules={csv}`
|`text/toon`
|Project
|Transitive impact closure and required verification commands for a comma-separated module list.

|`pm://architecture/drift`
|`text/toon`
|Project
|Structural drift report comparing current build descriptors against the project architecture snapshot `.marshall/project-architecture/_project.json` (with its per-module `{module}/derived.json`; file names as in `plan-marshall`'s `manage-architecture`): `changed[]` and `indeterminate[]{module, reason}`; a comparison the hash surface cannot certify is `indeterminate`, never `changed`.

|`skill://pm/{+path}/SKILL.md`
|`text/markdown`
|Project / Client
|Client-profile-rendered vocabulary skill Markdown with the `_meta["de.cuioss.pm-mcp/sha256"]` digest of the rendered bytes.
|===

*Resource Contract*: Every resource template documents its arguments, its payload, and its zero-result and error semantics (the `pm://architecture/*` details are in link:domain-extensions.adoc[Domain Extensions Specification]). A resource that returns no rows states what it examined, so an empty result is distinguishable from a result that could not be computed; an unknown scope or entity is answered with the JSON-RPC resource error `-32002` (resource not found) whose `data` carries `error_code: scope_not_found` (sanitized as in <<protocol-errors-vs-domain-workflow-failure-states>>; the refusal is audited, its `audit_id` is not returned), never with an empty payload; a resource path resolving outside its permitted root is answered the same way with `error_code: path_traversal_rejected`. `ReadResourceResult` has no `isError`, so resource errors are always JSON-RPC errors.

*Epic Read Access*: An epic scope may read `pm://plan/{plan_id}/findings` and `pm://plan/{plan_id}/status` of the plans in its queue that are `launched`, `running`, or `blocked`, read-only.

[#protocol-errors-vs-domain-workflow-failure-states]
== Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)
_See Requirement link:../Requirements.adoc#PM-TOOL-4[PM-TOOL-4: Domain Failures as Valid Workflow States]_

_See Requirement link:../Requirements.adoc#PM-TEST-4[PM-TEST-4: End-to-End Scenario & Compaction Resume Testing]_

_Implementation watch: link:../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-11[PM-WATCH-TOOL-11]_

A foundational invariant of PM-MCP is that *domain failures and transition rejections are workflow states, not MCP protocol errors*. Three response classes are distinguished:

* *JSON-RPC protocol errors*: a JSON-RPC `error` response (no `CallToolResult`) for malformed JSON-RPC (`-32700` parse error, `-32600` invalid request), unknown tool names (`-32602`), and resource read errors (`-32002`, see Resource Contract).
* *Tool execution errors*: a normal `CallToolResult` with `isError: true` when the arguments violate the tool's input schema or a server-enforced argument rule (`invalid_arguments`, following MCP `2025-11-25`, so the model sees the error and corrects the call) or a valid call cannot be executed (unknown scope, unenrolled project, missing entry record, unhandled server exception).
* *Domain results*: a normal `CallToolResult` with `isError: false` for every workflow outcome, including failures and rejected transitions (`PM-TOOL-4`).

=== Normative Classification Matrix

[cols="2,1,2,3"]
|===
|Condition |MCP Response Class |Response Structure |Model Recovery Path

|Valid transition succeeds (`pm_do`)
|`isError: false`
|Next state's TOON representation (`state`, `facts`, `links`).
|Follow one of the new `links`.

|Build fails, tests fail, or quality gate turns red
|`isError: false`
|TOON representation in a remediation state (e.g., `execute.verification-feedback`, `finalize.ci-failed`; link:state-catalogue.adoc[State Catalogue]) with structured failure facts and `fix`, `retry`, `loop_back`, or `escalate` links.
|Inspect failure facts (or `log_uri`), apply code fixes, and follow `fix` / `retry` / `loop_back`.

|Git push rejected (non-fast-forward) or merge conflict
|`isError: false`
|TOON representation in `git.sync-required` or `git.sync-escalate` (inside the `git.commit_and_push` sub-workflow) with `sync_rebase` (rel `fix`) / `escalate` links.
|Follow the offered `sync_rebase` or `escalate` link.

|Host tool modifies files outside the plan's worktree
|`isError: false`
|TOON representation of the unchanged current state with `condition: footprint_violation` (link:state-catalogue.adoc#condition-footprint_violation[State Catalogue, Conditions]), naming the offending files and offering only `fix` and `escalate` links.
|Inspect the named files; revert only changes this plan made, never baseline dirt (`facts.baseline_dirty`) or foreign changes, and follow `fix`, or `escalate` to the operator.

|Stale link followed, entity no longer in accepting state, or `args` fails link parameter validation
|`isError: false`
|Authoritative *current* TOON representation plus a top-level `rejected` block (`reason` from the closed set in <<rejection-reasons>>, `link`, `detail`).
|Read the current representation and follow one of its valid `links` with corrected `args`.

|Operator approval required or loop-back limit reached
|`isError: false`
|TOON representation of the unchanged current state with `condition: blocked` (link:state-catalogue.adoc#condition-blocked[State Catalogue, Conditions]) offering only `wait:decision:<decision_id>` (a bounded wait on the pending operator decision record), or `finalize.loop-limit-reached` offering `escalate`.
|Follow `escalate`, or `wait:decision:<decision_id>` until the operator resolves the decision.

|Malformed JSON-RPC or unknown tool name
|JSON-RPC error
|JSON-RPC `error` object (`-32700`, `-32600`, or `-32602`) with its fixed message; no `CallToolResult`.
|Fix the tool invocation.

|Tool arguments violate the input schema or a server-enforced argument rule (type, pattern, unknown property, mutually exclusive scope parameters, alternative plan sources, per-operation required parameters)
|`isError: true`
|MCP `CallToolResult` with `isError: true`, `error_code: invalid_arguments`, `parameter`, and `rule`.
|Correct the named parameter and call again.

|Unknown `plan_id` / `epic_id`, unenrolled workspace, missing pending entry record, or internal server exception
|`isError: true`
|MCP `CallToolResult` with `isError: true` and closed `error_code` (`scope_not_found`, `project_not_enrolled`, `entry_record_missing`, `internal_fault`); only `internal_fault` adds `audit_id`.
|Halt or invoke discovery (`pm_plans` / `pm_epics`), or notify the operator (with `audit_id` for `internal_fault`).

|The addressed project's recovery after a runtime start has not finished within the project recovery wait
|`isError: true`
|MCP `CallToolResult` with `isError: true` and `error_code: runtime_recovering`; nothing of the call was executed.
|Retryable: repeat the same call.

|`pm_skill` / `pm_skill_file` names a section the document does not contain, or a document that cannot be read or rendered
|`isError: true`
|MCP `CallToolResult` with `isError: true` and closed `error_code` (`section_not_found` with the available anchors, or `file_unreadable` with `audit_id`).
|Read the section index and request an existing anchor, or notify the operator with `audit_id`.
|===

[#rejection-reasons]
==== Closed Rejection Reasons & Failure Classes
_Implementation watch: link:../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-2[PM-WATCH-TOOL-2], link:../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-11[PM-WATCH-TOOL-11]_

`rejected.reason` is a closed enumeration. This table is its single definition; a specification that introduces a new rejection reason extends it here:

[cols="1,3"]
|===
|`reason` |Condition

|`link_not_available`
|The link identifier is not offered in the current state, including invented or paraphrased identifiers.

|`stale_entity`
|The entity-addressed link names an entity that is no longer in an accepting state (for example an already triaged finding).

|`operator_only`
|The link names an operator transition, which is never offered to the model (`PM-SEC-3`).

|`undeclared_param`
|`args` contains a key the link does not declare.

|`missing_param`
|A required free parameter is absent.

|`invalid_link_args`
|A free parameter violates its type, enum, length, or range constraint, or an attached content validator refuses the payload.

|`stale_dispatch_id`
|The supplied `dispatch_id` is superseded (link:dispatch-and-effort.adoc[Dispatch & Effort Specification]; a `dispatch_id` has no time-based expiry, link:timeouts.adoc#operator-decisions[Timeouts & Budgets Specification]).

|`phase_closed`
|A finding submission is addressed to a phase the plan has already left (for example a `phase-3-outline` Q-Gate finding after the plan entered `phase-4-plan`, link:phase-workflows.adoc[Phase Workflows Specification], Blocking Findings Guard); the finding is not written.

|`epic_pointer_mismatch`
|`pm_start` would create a plan whose `plan_id` equals a `launched` queue row of an epic while the consumed pending entry record's `from_epic` is absent or names another epic (link:dispatch-and-effort.adoc[Dispatch & Effort Specification], Single Epic Pointer).

|`no_local_changes`
|`pm_start` with `local_changes`, or the `recapture` link of a `land` plan, found an empty change set in the main checkout: no dirty or staged path and no commit ahead of the base branch (link:phase-workflows.adoc#land-lane[Phase Workflows Specification, Land Lane]).

|`capability_missing`
|`pm_start` with `pr_number` names a pull request whose head branch the agent identity cannot push to (`detail` names `reason: head_not_writable`, for example the head of a fork without push access; link:phase-workflows.adoc#_plan_source_contracts[Phase Workflows Specification, Plan Source Contracts]). The same reason refuses a native git operation that needs a repository capability the native variant lacks (derived fact `git_native_capability`; `detail` names the feature and the `pm-mcp operator` command that selects the CLI variant; link:cli-and-security.adoc#native-confinement[CLI & Security Specification, Native Operation Confinement]); there it is the transport outcome of the operation's job record, never a fallback.

|`integration_variant_unset`
|`pm_start`, or a git or provider primitive, found no valid operator choice of the integration variant (`native` or `cli`) for an integration it needs; `detail` names the integration and the project setup state `setup.select-integration-variants` that decides it (link:domain-extensions.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]). No git or provider operation runs before the decision.

|`config_dirty`
|`pm_start` found a file under `.marshall/config/` (a team configuration file or a workflow unit) already modified, staged, or untracked in the main checkout; no plan starts on an uncommitted configuration, and the operator commits or restores the file first. A `local_changes` start is exempt: the file is then part of the captured change set, verified and landed like every other captured path (link:phase-workflows.adoc#_planning_transition_guards_real_world_invariants[Phase Workflows Specification, Planning Transition Guards]).

|`config_invalid`
|`pm_start` or a phase handshake found a team configuration file or a project workflow unit that fails validation: a schema violation or undeclared key of a team file, or a unit violating a static verification rule or a compiled invariant (link:workflow-dsl.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]); `detail` names the file and the JSON pointer or line and the violated rule. The same finding is recorded in the workspace scope and published in `pm://project/config`; nothing falls back to a default.

|`format_outdated`, `format_newer`
|`pm_start` or a phase handshake found a team configuration file or a project workflow unit whose `format_version` (or DSL `format`) is older or newer than the binary accepts (link:store-schemas.adoc#format-versioning[Store Schemas Specification, Format Versioning]); `detail` names the file, the found and the current version. The file is never rewritten; the project setup workflow offers the rewrite.

|`lesson_unavailable`
|`pm_start` with `lesson_id` names a lesson that is already claimed by another plan, retired, or not resolved `found` (link:store-schemas.adoc#lesson-record[Store Schemas Specification, Lesson Record, Claim]); `detail` names the lesson state and, for a claim, the claiming `plan_id`.

|`plan_id_taken`
|The `plan_id` derived by `pm_start` already names a live or archived plan (link:phase-workflows.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]); an archived `plan_id` is never reused.

|`target_undeliverable`
|`mailbox_send:<plan_id>` names a plan that does not exist or is archived (link:dispatch-and-effort.adoc#plan-mailbox[Dispatch & Effort Specification, Plan Mailbox]); the message is not written.

|`surface_overlap`
|An epic queue-row write (staging a plan, or amending a `staged` row's `declared_surface` or `prerequisites[]`) would give the row a declared surface overlapping that of another non-terminal row of the same epic that is not ordered with it through prerequisites; `detail` names the overlapping plans and paths, and the row is not written (link:dispatch-and-effort.adoc#epic-surface-disjointness[Dispatch & Effort Specification, Staging-Time Surface Disjointness]).

|`surface_undeclared`
|An epic queue-row write stages a plan whose expected surface cannot be declared (empty, an entry that is not a git-tracked path or glob inside the workspace, or an entry that cannot be evaluated); `detail` names the offending entries, and the row is not written (link:dispatch-and-effort.adoc#epic-surface-disjointness[Dispatch & Effort Specification, Staging-Time Surface Disjointness]).

|`path_traversal_rejected`
|A repository path in `args` escapes the workspace: a `..` segment, an absolute path, or a symlink resolving outside the plan's worktree (`PM-SEC-2`). Job requests carry the same reason with the job outcome `refused` (link:job-runtime.adoc[Job Runtime Specification]).
|===

A content validator that refuses a payload answers `invalid_link_args` and names its specific cause in `detail` (for example `non_resolving_package_key`, link:domain-extensions.adoc[Domain Extensions Specification]); such causes are `detail` codes, not reasons. Outcome, state, condition, and finding tokens (a job's `refused`, the `store_tampered` condition, finding types such as `unknown_config_key`) are never `rejected.reason` values.

A job that exceeds its budget is a job outcome (`timed_out`), never a rejection. Every rejection belongs to the failure class `caller_drift` (the call did not match the offered contract); a tool execution error (`isError: true`) belongs to the class `server_fault`. The two classes are counted separately per plan (link:phase-workflows.adoc[Phase Workflows Specification], `record-metrics`), each with its population.

=== Sanitized Tool Execution Error Envelope (`isError: true`)

When a tool call cannot be executed (`isError: true`), the `TextContent` payload is strictly sanitized — stack traces, Java class names, filesystem paths, and credentials are never emitted:

[source,toon]
----
error: true
error_code: scope_not_found
message: "Plan scope 'plan-unknown' does not exist in the enrolled workspace."
----

Every tool execution error is written to `audit.jsonl`, but the payload carries `audit_id` only for the codes whose recovery path is an operator look-up, `internal_fault` and `file_unreadable`; for every other code the model corrects the call, retries, or uses discovery, and the identifier would have no operational value for it (link:hypermedia-format.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

Closed `error_code` enumeration for `isError: true`:

* `invalid_arguments` — The tool arguments violate the tool's input schema or a server-enforced argument rule; the payload adds `parameter` (the offending property, or the set of mutually exclusive properties) and `rule` (one line, as stated in the property's `description`).
* `scope_not_found` — Referenced `plan_id`, `epic_id`, or `entity` does not exist: the plan is in neither `plans/` nor `archive/` of the project's machine store (link:filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), or the epic or entity is unknown. An archived plan is found and answered read-only with its terminal representation.
* `project_not_enrolled` — The target repository has no enrolment file in `<PM_MCP_BASE>/enrolments/`, or, for a workspace-addressed request (`PM-ARCH-4`), the `PM-MCP-Workspace` header does not resolve to an enrolled project by the project resolution rule (link:filesystem-layout.adoc#project-resolution[Filesystem Layout Specification, Project Resolution Rule]) (`pm-mcp operator enrol`, link:cli-and-security.adoc#enrolment-lifecycle-release[CLI, Coordination & Security Specification]).
* `entry_record_missing` — `pm_start` was called with an `entry_id` for which no pending entry record `<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>.json` exists (never written by `pm-mcp enter`, or already consumed).
* `section_not_found` — `pm_skill` or `pm_skill_file` named a `section` that the document's section index does not contain; the message lists the available anchors.
* `file_unreadable` — The requested skill document or supporting file exists in the catalogue but cannot be read or rendered.
* `runtime_recovering` — Retryable. The call addresses a project whose per-project recovery after a runtime start has not finished within the project recovery wait (link:runtime-model.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery], link:timeouts.adoc#project-recovery-wait[Timeouts & Budgets Specification]); nothing of the call was executed, recovery continues, and the same call repeated later is served.
* `upstream_timeout` — An upstream pass-through tool call (`up_*`) exceeded its connect or read timeout (link:timeouts.adoc[Timeouts & Budgets Specification]); the call can be retried.
* `internal_fault` — Unexpected server exception, including a lock acquisition the lock manager refuses as out of order (`lock_order_violation`, link:store-schemas.adoc#lock-free-snapshot-reads[Store Schemas Specification]); full diagnostics are written exclusively to `audit.jsonl` under `audit_id`.

JSON-RPC protocol errors are sanitized the same way: the `error.message` is a fixed text per code, and `error.data` is present only for resource read errors, carrying the closed `error_code` (`-32002`: `scope_not_found`, `path_traversal_rejected`); the audit record is written, its `audit_id` is not returned.

=== End-to-End STDIO Integration Testing (`McpStdioTestClient` in `*IT.java`)

Failsafe integration tests (`*IT.java`) spawn the packaged `pm-mcp` runner JAR or GraalVM native executable as a real child process over `stdin`/`stdout` via `McpAssured.newStdioClient()`:

[source,java]
----
// The pending entry record is written first, as the user entry command does: `pm-mcp enter` prints its entry_id.
String entryId = runPmMcpEnter(pmMcpBinaryPath, tempWorkspaceRoot);

McpStdioTestClient client = McpAssured.newStdioClient()
    .setCommand(List.of(pmMcpBinaryPath.toString(), "serve"))
    .setWorkingDirectory(tempWorkspaceRoot)
    .setEnvironment(Map.of("PM_MCP_BASE", tempPmMcpBase.toString()))
    .setStderrHandler(stderrAuditBuffer::add)
    .build()
    .connect();

client.when()
    .toolsList(page -> {
        assertThat(page.tools())
            .extracting(ToolInfo::name)
            .containsExactlyInAnyOrder(
                "pm_start", "pm_state", "pm_do", "pm_plans", "pm_epics",
                "pm_build", "pm_lsp", "pm_skills", "pm_skill", "pm_skill_file");
    })
    .toolsCall("pm_start", Map.of("entry_id", entryId, "request", "Add JSpecify null-safety to service layer", "plan_slug", "null-safety"), response -> {
        assertThat(response.isError()).isFalse();
        assertThat(response.content().getFirst().asText().text())
            .contains("scope: plan")
            .contains("phase: init");
    })
    .thenAssertResults();
----

=== Normative `McpAssured` Verification Requirements

1. *Tool & Resource Schema Conformance*: Every `@Tool` and `@ResourceTemplate` is asserted via `client.when().toolsList(...)` and `client.when().resourcesTemplatesList(...)` to verify closed JSON Schema Draft 2020-12 `inputSchema` definitions (`additionalProperties: false`) and exact URI template registrations. The example asserts the complete, fixed core tool set at every migration stage with an empty upstream allowlist; no legacy script tool is ever registered. A second test with a configured allowlist asserts exactly the core set plus the allowlisted `up_*` tools, and that an upstream tool not on the allowlist, or one added only in a team configuration file under `.marshall/config/`, never appears.
2. *Domain Failure vs Protocol Error Assertions*: Every `pm_do` rejection and domain failure state is asserted with `assertThat(response.isError()).isFalse()`, unknown scope queries are asserted with `assertThat(response.isError()).isTrue()` and a sanitized `error_code` payload without `audit_id` (present only for `internal_fault` and `file_unreadable`), argument violations (schema and server-enforced rules) are asserted with `assertThat(response.isError()).isTrue()` and `error_code: invalid_arguments`, unknown tools are asserted as JSON-RPC error responses (`-32602`) without a `CallToolResult`, and unknown-scope resource reads as JSON-RPC `-32002` with `scope_not_found` in `data`.
3. *`stdout` Stream Hygiene & `stderr` Separation*: `setStderrHandler(...)` captures all diagnostic output on `stderr` while `McpStdioTestClient` parses every `stdout` line as a strict JSON-RPC 2.0 frame, proving zero `stdout` pollution across concurrent `pm_build` and `pm_lsp` executions (`PM-SEC-4`, `PM-TEST-5`).
