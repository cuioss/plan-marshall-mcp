[#web-server]
== Web Access & Pairing (`pm-operator web`)
_See Requirement link:../../Requirements.adoc#PM-SEC-7[PM-SEC-7: Optional Web Access, Device Pairing & Browser Channel Hardening]_

_See Requirement link:../../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_

_See Requirement link:../../Requirements.adoc#PM-SEC-4[PM-SEC-4: Local Transport Isolation, Operator-Gated Network Exposure & Stream Hygiene]_

_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-3[PM-WATCH-CLI-3]_

The optional web access gives a paired browser access to the runtime. It is part of the runtime (`pm-mcpd`), not a binary and not a process of its own: the web adapter is a package of `pm-mcp-server` (`de.cuioss.pm.mcp.server.web`, link:../../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]) beside the local adapter, and `pm-mcp-server` serves the web app `pm-web-app`, one of its dependencies. The web adapter owns every browser-facing concern (the TCP listener, TLS, `Host` validation, security headers, the route restriction, the static web app, pairing redemption) and adds no store: the web device store and the pairing code are stores of the runtime. The runtime opens no TCP listener unless the operator enabled web access (`PM-SEC-4`), apart from the loopback listener fallback of the local API (link:../runtime-model/01-processes-and-transport.adoc#_transport_endpoint[Runtime & Interaction Model Specification, Transport Endpoint]). The consequence is stated in `PM-SEC-7` and in <<web-threats>>: browser-facing HTTP, TLS, and static serving run in the process that holds the credential store and the engine. The web adapter is the place the later OAuth iteration builds on (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).

[#web-server-lifecycle]
=== Lifecycle (`pm-operator web enable|disable`)
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-21[PM-WATCH-CLI-21]_

* *Off by default*: Without an explicit `pm-operator web enable` (or a first `pm-operator web pair` / `pm-operator web open`, which enables the loopback listener) the runtime opens no web listener.
* *Setting*: Web access is the closed object `web` of `<PM_MCP_BASE>/machine-config.json` (link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]): `web.enabled` (boolean, default `false`), `web.lan` (boolean, default `false`), and `web.port` (integer, default the compiled port `7420`). The runtime writes it: `web.enabled` and `web.lan` on the request of the verbs below, `web.port` on `pm-operator config` (a changed port is used the next time the listener opens: at the next `web enable` or runtime start; an open listener is never re-bound); no process record and no process lock exist for web access.
* `pm-operator web enable [--lan]` is an operator verb (the operator checks, xref:02-credentials-and-operator.adoc#operator-channel-isolation[Operator Channel Isolation & Privileged CLI (`pm-operator`)]). It starts the runtime on demand and sends one request; the runtime opens the listener, writes `web.enabled: true` and `web.lan` (`true` with `--lan`, `false` without), and the verb reports success only after a round trip on the new listener. The verb has no port option: the listener uses `web.port`, which is changed with `pm-operator config`; an occupied port fails the command and leaves `web` unchanged, and another port is never chosen. While web access is enabled with the other exposure (loopback versus LAN), the verb is refused with a notice to run `pm-operator web disable` first.
* `pm-operator web disable` (operator verb): the runtime ends every open browser stream, closes the listener, and writes `web.enabled: false`. Paired devices stay paired; `web enable` later serves them again.
* *Audit*: `web enable` and `web disable` have no audit rule of their own. Like every operator verb that changes `machine-config.json` (`pm-operator config`), each appends one machine-level `operator` record with `details.channel: cli` (xref:02-credentials-and-operator.adoc#_security_audit_trail_three_tier_identity_verification[Security Audit Trail]; link:../store-schemas/12-machine-stores.adoc#audit-log[Store Schemas Specification, Audit Log]).
* *Activation*: `web enable` and `web disable` take effect immediately: the runtime opens or closes the second HTTP server while it runs, without touching plans or jobs. The Milestone 0 spike verifies this (a second Vert.x HTTP server beside the Unix-socket listener in the native image, with the route restriction of <<web-proxy>>; link:../runtime-model/04-sessions-and-workers.adoc#_verification[Runtime & Interaction Model Specification, Verification]). Fallback if the spike fails: the setting takes effect at the next runtime start, and the verb says so.
* *At every start*: While `web.enabled` is `true` the runtime opens the listener at every start with the recorded `web.lan` and `web.port` (link:../runtime-model/02-startup-recovery-drain.adoc#_startup_sequence[Runtime & Interaction Model Specification, Startup Sequence]); a drain or stop closes the listener and leaves `web.enabled` unchanged. An occupied `web.port` at a runtime start leaves the web listener closed: `pm-operator status` reports it, another port is never chosen, and the runtime still starts and serves its Unix socket. The listener's live state (exposure, port, in LAN mode the certificate fingerprint) is part of the runtime status that `pm-operator status` shows.
* *Runtime not running*: The web listener exists only while `pm-mcpd` runs. With the runtime stopped a browser gets a refused connection; no process answers in the runtime's place, and a browser request never starts the runtime. Under the on-demand start mode the listener therefore returns with the next command that starts the runtime; the service-managed start mode keeps it available from login (link:../runtime-model/01-processes-and-transport.adoc#_start_modes[Runtime & Interaction Model Specification, Start Modes]).

[#web-listener]
=== Listener Exposure

When web access is enabled the runtime opens exactly one additional HTTP server, separate from the Unix-socket listener of its local clients:

* *Loopback (default)*: plain HTTP on `127.0.0.1:<web.port>` only. Loopback is a secure context for the browser; nothing leaves the machine.
* *LAN (`--lan`)*: HTTPS only, on all interfaces, with a certificate the runtime generates itself on the first `--lan` enable: a self-signed ECDSA P-256 certificate whose subject alternative names are the host name, `<hostname>.local`, the interface addresses at generation, and the loopback addresses. Key and certificate are kept in `<PM_MCP_BASE>/web/tls/` (directory `0700`, key `0600`) and reused on every later `--lan` enable, so paired devices keep a stable fingerprint. Its SHA-256 fingerprint (of the DER certificate) is printed by `pm-operator web enable --lan`, `pm-operator web pair`, and `pm-operator status`, and shown on the pairing page, so the operator compares it with the browser's certificate details before accepting the warning. Plain HTTP is never served on a non-loopback address. A local certificate authority that removes the warning is deferred (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).

[#web-security-headers]
=== Request Validation & Security Headers
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-18[PM-WATCH-CLI-18], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-19[PM-WATCH-CLI-19]_

* *`Host` validation*: Before routing, the web listener accepts a request only when its `Host` header names the listener's own origin: `127.0.0.1:<port>` or `localhost:<port>` in loopback mode, and additionally one of the certificate's names or addresses with `<port>` in LAN mode. Every other `Host` is refused with `403` and reaches no route. This defeats DNS rebinding.
* *No CORS*: The web listener sends no `Access-Control-*` header on any response; a preflight `OPTIONS` request is refused. A state-changing request (`POST`, `PUT`, `PATCH`, `DELETE`) whose `Origin` header is present and differs from the listener's own origin is refused with `403`.
* *Security headers on every response* of the web listener (static files, API responses, event streams, errors, and `404`s alike):
** `Content-Security-Policy: default-src 'self'; script-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; require-trusted-types-for 'script'` (as an HTTP header, never a `<meta>` element);
** `X-Frame-Options: DENY` (anti-framing together with `frame-ancestors 'none'`);
** `X-Content-Type-Options: nosniff`;
** `Referrer-Policy: no-referrer`.
* *Static web app*: The web listener serves the `pm-web-app` resource JAR (`META-INF/resources`) for every `GET` outside `/api/`; a path without a matching file returns the app's fallback page (client-side routing). No server-side rendering exists.

[#web-proxy]
=== API Access & Device Secret
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-16[PM-WATCH-CLI-16], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-20[PM-WATCH-CLI-20], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-21[PM-WATCH-CLI-21], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-26[PM-WATCH-CLI-26], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-27[PM-WATCH-CLI-27]_

The runtime serves its own API to the browser on the web listener, without an intermediary and without a forwarding header, restricted as follows.

* [[web-routes]]*Route restriction*: The web listener routes exactly two things, the static web app (<<web-security-headers>>) and the path prefix `/api/v1/`. `/mcp`, every other `/api/` path, and a path that changes under normalization (encoded `/`, `..`, duplicate `/`) are refused (`404`, `400`) before routing; `/mcp` is never reachable on the TCP listener. The restriction belongs to the listener: a route of the Unix-socket listener is not reachable on the web listener unless it lies under one of the two.
* *Device secret*: A browser authenticates with its device secret as `Authorization: Bearer pmw_…` (link:../identifiers/02-registry-stores-to-web.adoc#id-device-secret[Identifier Registry, device secret]). The runtime checks it against the web device store on every request, without a cache, and ties the request to the device id (link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]); a request without a secret, or with a malformed, unknown, revoked, or expired one, is answered `401`. The only unauthenticated API endpoint is pairing redemption (<<web-pairing>>).
* *No runtime token*: The runtime token is never accepted on the web listener, and neither is a job token: a request carrying one is answered `401` like any other value that is no paired device's secret. Conversely a device secret is accepted on the web listener only. The listener a request arrived on decides which credential counts; no request header changes that.
* *Web-originated requests*: A request that arrives on the web listener is web-originated for the runtime: CLI-only endpoints (issuing a pairing code, enabling or disabling web access, entering a credential secret) refuse it with `403` (`cli_only`).
* *Event streams*: `GET /api/v1/events` and `GET /api/v1/plans/{plan_id}/events` are served unbuffered and uncompressed, honouring `Last-Event-ID`; the device is checked when the stream connects, and the runtime ends a device's open streams when the device is revoked.
* *Logging*: The runtime logs no request header. The runtime token and every `pmw_` value are redacted by the `SecretRedactor` (xref:02-credentials-and-operator.adoc#operator-credential-cli[Operator-Only Credential CLI & Runtime Secret Redaction]): the runtime token by value, device secrets by their shape, because the runtime keeps only their hashes.

[#web-pairing]
=== Pairing Protocol
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-15[PM-WATCH-CLI-15]_

Pairing follows the device-grant pattern: a short one-time code only authorizes; the browser receives a separate per-device secret.

. *Issue*: `pm-operator web pair [--label <label>]` (operator verb; enables the loopback listener when web access is not enabled) asks the runtime for a pairing code (`POST /api/v1/web/pairings`, CLI-only). The code has 8 characters of the alphabet `BCDFGHJKLMNPQRSTVWXZ` (about 34.5 bits, link:../identifiers/02-registry-stores-to-web.adoc#id-pairing-code[Identifier Registry, pairing code]), is valid for the pairing code lifetime (link:../timeouts/02-runtime-leases-operator-web.adoc#pairing-code-ttl[Timeouts & Budgets Specification, Pairing Code Lifetime]), single use, and allows a bounded number of failed redemptions (link:../timeouts/02-runtime-leases-operator-web.adoc#pairing-attempt-limit[Timeouts & Budgets Specification, Pairing Failed-Attempt Limit]). At most one pairing is open: a new one invalidates the previous. The runtime keeps only the code's SHA-256, the label, the expiry, and the failure count, in memory (link:../store-schemas/12-machine-stores.adoc#web-access-records[Store Schemas Specification, Web Access Records]).
. *Show*: `pm-operator` prints the code as `XXXX-XXXX`, the URL `http(s)://<host>:<port>/pair#code=<code>`, a QR code of that URL (Unicode half blocks, 4-module quiet zone, black on white), the expiry, and in LAN mode the certificate fingerprint. The code travels in the URL fragment, which the browser never sends to a server, so it appears in no request line, log, or `Referer`.
. *Open on the same machine*: `pm-operator web open` (operator verb) issues a pairing code and opens the loopback pairing URL in the default browser (`open` on macOS, `xdg-open` on Linux, started with an argument vector, never through a shell).
. *Redeem*: The web app's pairing page reads the code from the fragment (or from manual input, normalized to upper case without `-` and spaces), removes the fragment with `history.replaceState`, and sends `POST /api/v1/pair` with `{code}`, the only API request the web listener serves without a device secret. The runtime compares the SHA-256 in constant time; on success it consumes the code, generates the device secret (`pmw_` plus 256 bits from `SecureRandom`, base64url; link:../identifiers/02-registry-stores-to-web.adoc#id-device-secret[Identifier Registry, device secret]), stores only its SHA-256 with a new `device_id` and the pairing's label (default: the `device_id`), appends the audit record `web_device_paired`, and returns `{device_id, label, device_secret}` once. The secret is opaque: the runtime is issuer and validator, so a self-contained token would add nothing and could not be revoked instantly.
. *Failure*: A wrong, expired, consumed, or superseded code yields the same `400` (`pairing_invalid`) without saying which, and appends `web_pairing_failed`. The failure that reaches the attempt limit invalidates the open pairing, so a later redemption fails even with the right code. A runtime restart discards the open pairing; the operator runs `pm-operator web pair` again.
. *Keep*: The web app stores the device secret in `localStorage` and sends it as `Authorization: Bearer <device secret>` on every API request (<<web-app>>).

[#web-devices]
=== Paired Devices (`pm-operator web devices`)
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-17[PM-WATCH-CLI-17]_

* `pm-operator web devices list` shows `device_id`, label, `created_at`, and `last_used_at` of every paired device; `pm-operator web devices revoke <device_id>` and `pm-operator web devices revoke --all` remove devices (`GET /api/v1/web/devices`, `DELETE /api/v1/web/devices/{device_id}`, `DELETE /api/v1/web/devices`, link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]). All three are operator verbs; the web app offers the same list and revocation to a paired device.
* *Immediate revocation*: A revoked device's record is removed from `state/web-devices.json`; the runtime ends the device's open event streams at once and answers its next request `401`, whereupon the web app deletes its stored secret and shows the pairing page. Every revocation appends `web_device_revoked`.
* *Idle expiry*: A device whose `last_used_at` is older than the device idle expiry (compiled, link:../timeouts/02-runtime-leases-operator-web.adoc#device-idle-expiry[Timeouts & Budgets Specification, Device Idle Expiry]) is expired: its next request is answered `401`, and its record is removed with `web_device_revoked` (`reason: idle_expired`). `last_used_at` is written at most once per write-granularity interval per device (link:../timeouts/02-runtime-leases-operator-web.adoc#device-last-used-granularity[Timeouts & Budgets Specification, `last_used_at` Write Granularity]). Rotation and absolute expiry are deferred (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).
* *Store damage*: An unreadable or invalid `state/web-devices.json` authenticates no device (every web-originated request `401`, reported by `pm-operator status`) and leaves the CLI binaries unaffected; `pm-operator web devices revoke --all` rewrites an empty store.

[#web-operator-channel]
=== Every Paired Device Is an Operator Channel

In the first iteration there are no device roles: every paired device may do what the privileged verbs of `pm-operator` do (waivers, answers to waiver requests, `abort`, `delete-plan`, the integrity resolutions, operator configuration), except the CLI-only endpoints of <<web-proxy>>. A paired device also answers the content question records of every plan and epic (<<web-app>>); the app keeps question records and waiver requests apart, and a question answer is never an override. The web app is therefore the second operator channel next to the operator CLI; MCP elicitation carries no override, only the operator-configuration choices the server raises (`PM-SEC-3`); every action through it is audited with channel `web` and the `device_id`. Pairing a device is an operator act for this reason, and every device secret is as powerful as the operator. Roles (`viewer`, `operator`) and step-up before operator actions from a browser are deferred (link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).

[#web-auth-seam]
=== Authentication Seam

The runtime uses Quarkus Security on both listeners: one `HttpAuthenticationMechanism` (Bearer) and one `IdentityProvider` per token kind, and resources annotated only `@Authenticated` (`@RolesAllowed` once roles exist). Which token kind a request may present is fixed by the listener it arrived on: the Unix-socket listener has the provider for the runtime token, the web listener only the provider for `pmw_` device secrets, which validates the secret against the web device store (<<web-proxy>>). The OAuth iteration adds a provider wrapping Token-Sheriff validation for three-part JWTs next to the `pmw_` provider, so paired devices keep working during the switch; `token-sheriff-bom` stays imported for it (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).

[#web-app]
=== Web App (`pm-web-app`)

* *Build*: SvelteKit 3 (release candidate, pinned; moved to 3.0 final when released) with Svelte 5 and TypeScript, built as a static single-page app (`@sveltejs/adapter-static`, `ssr = false`, fallback page) by `frontend-maven-plugin` with pinned Node and npm (`npm ci` from `package-lock.json`), tested with Vitest, and packaged as a resource JAR (`META-INF/resources`) that `pm-mcp-server` depends on and `pm-mcpd` serves. The npm packages are covered by the CycloneDX SBOM. During development the Vite dev server proxies `/api` to the web listener of a running runtime.
* *Views*: pairing (code from the fragment or typed, the certificate fingerprint in LAN mode), paired devices (list, revoke), runtime status (projects, plans and epics including `stalled` ones with their cause, workers with role, form, generation, and state, queue tasks with role, state, lease, and attempts, roles stopped by the start-failure guard with the harness's own error text, the identity mismatches recorded at entry, build and model slots, jobs), the effective role set with each role's qualification state, the decision records of a plan, an epic, or the workspace scope with their corrections (link:../model-work/11-decision-records.adoc#decision-visibility[Model Work Specification, Reading Decisions]), the live view of one plan or epic (state, phase, plan tasks, queue tasks and the workers serving them, jobs, findings counts, plan instance version and diagram, waivers and consumptions), pending waiver requests with the waive actions, open question records and the questions the decision panel decided, with the agreed option and the systems that agreed (a separate view), and the other operator actions.
* *Dependable view and question channel*: The web app is the dependable view of every plan, epic, worker, and task, beside the terminal view `pm-operator status`, and the dependable channel of content questions (`PM-SEC-7`, `PM-WF-12`). It shows every delivered open question record of a plan or epic with its question, its decision kind, its options with the recommended option, the recommendation's confidence and rationale, the default assumption, and its deadline, and for a set the decision panel delivered every panel role's answer with its confidence and rationale (link:../model-work/10-decision-panel.adoc#panel-record[Model Work Specification, Decision Panel, Record]), and answers it through the scope-qualified answer endpoint of the link:../runtime-model/01-processes-and-transport.adoc#local-api[Local API] (`POST /api/v1/{plans|epics}/{id}/questions/{question_id}/answer`, `POST /api/v1/workspace/questions/{question_id}/answer`; channel `web`; the first valid answer wins, link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]). On the event of a newly opened question record it raises a browser notification where the device granted the permission; the entry session shows the same records through their answer links while one is open. The app never shows a choice of the project setup or a bootstrap, which the entry session drives.
* *Live updates*: The app reads the event streams with `fetch()` and a `ReadableStream`, because `EventSource` cannot send an `Authorization` header; a credential never appears in a URL. It reconnects with `Last-Event-ID`.
* *Browser storage*: The device secret is kept in `localStorage`, so the pairing survives browser restarts; the app never uses cookies. Its exposure to injected script is contained by the security headers (<<web-security-headers>>), Trusted Types, no third-party scripts or origins, no `{@html}` or other raw-HTML sink (all server text is rendered as text), and lockfile-pinned dependencies; revocation and idle expiry are the recovery. Sender-constrained credentials (a non-extractable WebCrypto key, DPoP) are deferred (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).

[#web-threats]
=== Threat Notes

* *Browser-facing surface inside the runtime*: HTTP parsing, TLS, and static serving for browsers run in the process that holds the credential store, the stores, and the engine; no process boundary stands between a flaw in that surface and the runtime. This is the accepted consequence of serving web access from the runtime (`PM-SEC-7`). The mitigations are: web access is off by default; the listener is loopback-only by default and on the LAN only over TLS; every request passes the `Host` validation before routing and needs a device secret that the runtime checks on every request; the listener routes nothing but the web app and `/api/v1/`, never `/mcp`, and never accepts the runtime token; `pm-operator web disable` closes the listener.
* *Cross-site scripting*: `script-src 'self'` with Trusted Types blocks injected and inline script and raw-HTML sinks; `connect-src 'self'` keeps script from sending the secret to another origin by `fetch`. Accepted residual: script that does run in the app's origin can read `localStorage` and act as the device until it is revoked (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).
* *DNS rebinding*: A rebound page carries a foreign `Host` and is refused before routing; it also has no access to the app origin's `localStorage`, and the credential is never ambient.
* *Cross-site request forgery*: Not applicable: the credential is an explicit `Authorization` header, never a cookie; no CORS is granted.
* *Framing*: `frame-ancestors 'none'` and `X-Frame-Options: DENY` on every response prevent clickjacking of operator actions.
* *Code interception*: The pairing code is short-lived, single use, limited in failed redemptions (link:../timeouts/02-runtime-leases-operator-web.adoc#pairing-attempt-limit[Timeouts & Budgets Specification, Pairing Failed-Attempt Limit]), carried in the URL fragment, and on the LAN only over TLS.
* *Same-user processes*: Web access adds no boundary against processes of the same OS user: any of them can read the runtime token and call the Local API on the Unix socket directly, including operator endpoints (link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).
* *Model surface*: Nothing of the web access, the pairing, or the device store is reachable through an MCP tool or appears in a model-facing representation (link:../mcp-tools.adoc[MCP Tools Specification], Architectural Constraints; link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
