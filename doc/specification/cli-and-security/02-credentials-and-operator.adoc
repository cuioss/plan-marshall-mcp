*Proven Write Credential for Upstream Filing*: A credential that an operator-confirmed filing job would use to write to a vendor tracker (the lesson Upstream Release, link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record]) is proven by a write-permission probe on the target tracker before the filing job is offered; without a passed probe the release action only renders the issue body for the operator to file.

=== Two-Lane Provider Architecture

External provider integrations are strictly partitioned into two authentication lanes. The provider operations of both lanes are contracts of the provider modules `pm-mcp-git` and `pm-mcp-ci` and the findings and code-analysis contracts of `pm-mcp-core`, implemented by `pm-mcp-github`, `pm-mcp-gitlab`, and `pm-mcp-sonar` (link:../../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]). For the integrations `git`, `github`, and `gitlab` each contract has two implementations, the *native variant* (in process) and the *CLI variant* (jobs of the enrolled `git`, `gh`, `glab`); the lane of such an integration follows its variant:

1. *System Lane (CLI variant of `git`, `github`, `gitlab`)*: Executed as verified subprocess jobs (`PM-EXEC-5`) that inherit the developer's existing CLI authentication (`~/.gitconfig`, credential helpers, SSH agent, `gh auth`, `glab auth`), by design (<<cli-variant-credentials>>). `pm-mcp` never reads, extracts, or stores CLI-lane tokens and never injects a Token Lane secret into such a job.
2. *Token Lane (SonarQube/SonarCloud, authenticated upstream MCP servers, and the native variant of the git HTTPS transport, GitHub, and GitLab)*: Executed directly by the runtime (`pm-mcpd`) in process: REST and GraphQL through `de.cuioss:cui-http`, git transport through JGit over HTTPS. Tokens are resolved per request by credential key (`PM-CRED-1`) from the credential store hierarchy: `<project>/<credential_key>` (project-scoped override) -> `<credential_key>` (global fallback), and sent only to the origin of the entry's `url` and, for `github` and `gitlab`, the API origin derived from it (<<agent-credentials>>, `PM-CRED-5`). That `url` belongs to the operator-owned credential entry; the team configuration (`.marshall/config/project.json`) may only reference a credential key and never decides where a token is sent. The native variant authenticates as an agent identity, never as the operator.

*Variant selection*: The project setup state `setup.select-integration-variants` (link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]) applies `native` to every integration unless the derived fact `git_native_capability` finds a feature the project uses that the native variant cannot serve; only then the operator chooses, through the operator channel only (elicitation where the connection supports it, otherwise `pm-mcp operator config --project <project_id>`, named in the state's `facts`, after which the model follows `retry`). The choice is never a question record and never taken from a model-relayed answer, and no git or provider operation runs before the variant is set. The choice is stored in the operator's `local-config.json` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Local Configuration]), never in a team file, because it decides whose credentials act. One integration of a project uses exactly one variant for all its operations; different integrations may differ (for example the CLI variant of `git` with the native variant of `github`). `sonar` has only the native variant. There is no automatic fallback between variants: a silent switch to the CLI variant would silently switch to the operator's identity. The variant that served an operation, the credential key and origin, and for the CLI variant `identity: operator_ambient` are written to the operation's audit record, never into a model-facing result (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

* *No refusal by credential kind*: Every listed credential kind is accepted on equal footing; neither the kind nor a missing expiry is refused or warned about in a workflow. `set` and `verify` determine the token kind from the provider and record it with the entry (<<operator-credential-cli>>).
* *Check visibility*: A credential that cannot read check runs (a GitHub fine-grained personal access token cannot call the Checks API) is detected up front by the derived network fact `checks_visible` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts]); `ci.checks` then reads what the credential can see (commit statuses, check suites) and reports `completeness: incomplete`, which never counts as a green check.
* *Installation tokens*: For a `github_app` entry the runtime signs an RS256 JWT with the JDK (`iat` back-dated and `exp` bounded by the GitHub App JWT validity window, link:../timeouts/03-retention-host-config.adoc#github-app-jwt-window[Timeouts & Budgets Specification]; `iss` the `client_id`) and mints an installation token narrowed to the one repository and to the narrowest permission set of the operation class (read-only for query classes) through `POST /app/installations/{id}/access_tokens`. The App needs at most the repository permissions `contents: write`, `pull_requests: write`, `checks: read`, `actions: read`, `statuses: read`, `issues: write`, and `metadata: read`; administrative permissions are never required, because repository administration (such as enabling a merge queue) stays with the operator.
* *Committer identity*: The committer of agent commits is the identity resolved from the agent credential through `ci.whoami` (a GitHub App: `<app-slug>[bot]` with the address `<id>+<app-slug>[bot]@users.noreply.github.com`; a token: the token's user), recorded as the operator-only derived fact `agent_identity`; without a Token Lane provider credential the committer is the fixed `plan-marshall-mcp` noreply identity. The author stays the operator (`commit_identity`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Local Configuration]). The identity appears in the operator's `status` output and the audit log, never in a model-facing representation.

[#derived-tokens]
=== Short-Lived Derived Tokens
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-5[PM-WATCH-CLI-5]_

A stored secret is read per request and never cached (`PM-CRED-5`). A token derived from it that expires by construction, a GitHub App installation token (valid one hour), is the second named exception of `PM-CRED-5`:

* It is held in memory only, keyed by installation and permission set, and reused until the derived token reuse margin before its expiry (link:../timeouts/03-retention-host-config.adoc#derived-token-reuse-margin[Timeouts & Budgets Specification]); then a new one is minted.
* It is registered with the redaction registry when minted (<<operator-credential-cli>>).
* It is never persisted, never exported to a subprocess environment or log, and never passed to the CLI variant.
* It is dropped when its credential entry is rotated, removed, or re-set, when a request with it fails with `auth_failed` (revocation), and when the runtime stops.

[#native-confinement]
=== Native Operation Confinement
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-6[PM-WATCH-CLI-6], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-9[PM-WATCH-CLI-9], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-28[PM-WATCH-EXT-28]_

A native operation runs inside the runtime process: it has no argument vector, no environment, and no Landlock ruleset. What it can do is bounded by the following rules, each enforced in the provider modules:

* *Paths*: It writes only inside the enrolled project root and its linked worktrees; every path it derives, including the `gitdir` targets of worktree administration files, passes the `PM-SEC-2` checks.
* *Origin check*: HTTP requests go through `cui-http` with origin pinning. The git transport resolves the effective fetch and push URL of the remote with every `url.<base>.insteadOf`/`pushInsteadOf` rewrite and `remote.<name>.pushurl`, maps an SSH remote of a known provider host (`github.com`, `gitlab.com`, and hosts whose `ci_provider` is established) to its HTTPS form without changing the configured remote, and requires `https` and an origin equal to the credential entry's origin. A mismatch refuses the operation with `remote_origin_mismatch`, appends a `security` record to `audit.jsonl`, and sends nothing; every other SSH remote is `capability_missing{reason: ssh_only_remote}`. Its connection factory refuses every other host, so a redirect cannot carry the credential elsewhere.
* *Configuration allowlist*: From the repository configuration and the user's global configuration it reads only content-shaping keys: `core.autocrlf`, `core.eol`, `core.safecrlf`, `core.excludesFile`, `core.ignoreCase`, `core.precomposeUnicode`, `remote.<name>.url|pushurl|fetch`, `url.<base>.insteadOf|pushInsteadOf`, `branch.<name>.*`, `init.defaultBranch`, and, for capability detection only, `core.hooksPath`, `filter.<driver>.*`, `lfs.*`, `submodule.*`, and `extensions.*`. Every other key is ignored, among them `credential.*`, `core.sshCommand`, `core.fsmonitor`, `http.*` proxy settings, and `include.*`/`includeIf.*` targets outside the repository. A proxy is an operator setting, never a repository value or an environment variable: the closed object `proxy` of `machine-config.json` (`https_proxy`, a URL without embedded credentials, and `no_proxy`, a list of hosts; link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]), set with `pm-mcp operator config` and applied to every `cui-http` call and to the JGit transport of the native variant. Authenticated proxies are deferred (link:../../later-improvements.adoc#_l_8_authenticated_proxies[Later Improvements, L-8]).
* *No process execution*: A native operation never starts a process. JGit's process entry points (`FS.runInShell`, `FS.runHookIfPresent`, filter-driver execution) are served by a `pm-mcp-git` subclass of JGit's `FS` that refuses with `capability_missing` instead of running anything, so no repository value can start a process in the runtime.
* *Selection criterion instead of fallback*: Repository hooks (non-sample files in `.git/hooks/`, `core.hooksPath`, `.husky/`, `lefthook.yml`, `.pre-commit-config.yaml`), required commit signing (`signed_commits_required`), filter drivers including LFS, submodules, SHA-256 object format, partial clone, sparse checkout, split index, and SSH-only remotes are detected by the derived fact `git_native_capability` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts]). An operation that needs a missing capability is refused with `capability_missing{reason}` naming the feature and the `pm-mcp operator` command that selects the CLI variant for the integration; there is no automatic fallback. A new capability finding invalidates a recorded native selection, and project setup requires the operator-channel choice for that integration.

[#cli-variant-credentials]
=== Credentials of the CLI Variant
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-8[PM-WATCH-CLI-8]_

The CLI variant runs the operator's enrolled `git`, `gh`, or `glab` with the operator's ambient authentication, by design: its purpose is the operator's own setup (signing, SSH remotes, hooks, special hosts).

* *Operator choice, audited*: `setup.select-integration-variants` (link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]) shows on selection that the CLI variant of that integration acts with the operator's identity; every CLI job's audit record carries `identity: operator_ambient`.
* *No token injection*: An agent token is never passed to a CLI job, neither as `GH_TOKEN`, `GITHUB_TOKEN`, `GITLAB_TOKEN`, or another token variable, nor through a `GIT_ASKPASS` or `SSH_ASKPASS` helper, nor through a credential helper served by `pm-mcp`: every descendant of the job, including repository hooks, and every same-user process reading `/proc/<pid>/environ` could read it, which breaks `PM-CRED-5`.
* *Environment, write paths, `stdin`*: The job environment rows of CLI-variant `git` and `ci` jobs (configuration discovery, SSH agent socket, provider CLI configuration directories, non-interactive guards, committer variables), their additional write paths, and their `stdin` forms are specified in link:../job-runtime.adoc[Job Runtime Specification] (Job Environment; In-Memory `stdin` Streaming). `known_hosts` stays read-only: an unknown host key fails the job, it is never accepted.
* *Hooks and signing*: Repository hooks and signing programs run only here, started by `git` itself inside the CLI `git` job and therefore under that job's environment and Landlock confinement (`PM-SEC-5`).

=== OS Keyring Backends & Fallback File Store

The `CredentialStore` service uses exactly one active backend per machine, chosen at runtime start: the OS keyring when one is available, otherwise the fallback file store. A secret never exists in two backends, and within the active backend the project entry `<project>/<credential_key>` is resolved before the global entry `<credential_key>` (`PM-CRED-2`). `<project>` is the project's enrolment identifier (`PM-CRED-3`), never derived from a remote URL or a checkout path. The backends are:

* *macOS Keychain (Primary on macOS)*: Invokes macOS Security framework APIs (`SecItemAdd`, `SecItemCopyMatching`, `SecItemUpdate`, `SecItemDelete`) directly via Java 25's Foreign Function & Memory (FFM) API (`java.lang.foreign.Linker`). Items are stored under PM-MCP's own service name `de.cuioss.pm-mcp` (qualified by the instance directory when a non-default `PM_MCP_BASE` is set, `PM-DIST-5`) with account `<credential_key>` or `<project>/<credential_key>` and a trusted-application ACL restricting unprompted read access to the signed runtime binary `pm-mcpd`, the only process that reads or writes credentials (the CLI never touches the credential store).
* *Linux Secret Service (Primary on Linux)*: Communicates with `org.freedesktop.secrets` over the user session D-Bus (`gnome-keyring` / `KWallet`) storing attributes `service=de.cuioss.pm-mcp`, `credential_key=<credential_key>`, and optional `project=<project>`.
* *Permission-Guarded Fallback File Store*: When no OS keyring is available (headless Linux or WSL2), secrets are stored in the `PM-MCP` credential file format (`format_version`, closed schema, written only by the runtime on a `pm-mcp operator credentials` verb, `PM-CRED-3`) at `<PM_MCP_BASE>/credentials/<credential_key>.json` and `<PM_MCP_BASE>/credentials/<project>/<credential_key>.json` (directory mode `0700`, file mode `0600`, see link:../filesystem-layout.adoc[Filesystem Layout Specification] and link:../store-schemas.adoc[Store Schemas Specification]). If ownership or permission checks on a credential file fail, the runtime refuses to read it and holds only the step that needs that credential: the engine raises the `precondition_unmet` condition on the step's current state with `facts.reason: credentials_file_insecure` and `facts.operator_command` naming the exact `pm-mcp operator credentials` command that repairs it (`PM-CRED-4`); its `retry` re-checks the file within the condition budget (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]), after which the phase's fallback is taken with the credential as the gap. A missing credential is handled the same way (`facts.reason: credential_missing`). The runtime itself keeps running; it exits with code `77` only when `<PM_MCP_BASE>` or its state files fail the startup ownership and permission checks (link:../runtime-model.adoc#_startup_sequence[Runtime & Interaction Model Specification]).

* *No Legacy Credential Access*: The `CredentialStore` never reads legacy `plan-marshall` credentials (its keyring entries, `~/.plan-marshall/credentials/`, `PLAN_MARSHALL_CREDENTIALS_DIR`, `PLAN_MARSHALL_HOME`), and no verb imports them (`PM-MIG-2`). Credentials enter the `PM-MCP` stores only through `pm-mcp operator credentials`, each entry operator-owned, including its allowed `url`.

[#operator-credential-cli]
=== Operator-Only Credential CLI & Runtime Secret Redaction

* *Operator CLI Verbs*: Credential mutations and verifications are restricted exclusively to interactive TTY invocations of `pm-mcp operator credentials set|status|check|verify|remove|migrate|rotate <credential_key> [--project]` (operator verbs, <<operator-channel-isolation>>). `set` and `rotate` always read the secret from the terminal with echo disabled (`System.console().readPassword()`), together with the non-secret fields (`url`, `auth_type`, header settings; for `github_app` the `client_id` and optional `installation_id`, the PKCS#8 `private_key` being read as a secret), and send them in the body of one request to the runtime's API over its Unix domain socket (link:../runtime-model.adoc#local-api[Runtime & Interaction Model Specification, Local API]); the CLI keeps the secret only in a `char[]` that it clears after the request and never writes it anywhere. Entering a secret is CLI-only: the endpoint refuses a web-originated request (xref:03-web-server.adoc#web-proxy[API Proxy & Device Secret Forwarding]). The runtime writes the entry into the active backend; when targeting the file store it writes the complete credential file in the `PM-MCP` format (`format_version`, closed schema, link:../store-schemas/12-machine-stores.adoc#credential-store[Store Schemas Specification, Credential Store]) atomically with mode `0600`. The runtime, on an operator verb, is the only writer of credential files: no placeholder file and no hand-edited file exists, and a file it did not write in the current format is refused (`credentials_file_invalid`). Secrets are never accepted from command-line arguments or environment variables.
* *Identity, Kind & Expiry*: For `github` and `gitlab` entries, `set` and `verify` call `ci.whoami` and record the token kind (`token_kind`) and, where the provider reports one, the expiry (`expires_at`; an operator-entered expiry at `set` otherwise); `verify` shows the resolved identity, its permissions on the enrolled repository, and whether it can read check runs (`checks_visible`), without revealing the secret. `status` reports per entry one of `complete`, `incomplete`, `not_found`, `verified`, `unverified`, plus `expiring` when `expires_at` lies within the credential expiry warning window (link:../timeouts/02-runtime-leases-operator-web.adoc#credential-expiring-window[Timeouts & Budgets Specification]), and names an entry without a known expiry; neither is a refusal, and neither reaches a model-facing representation, since an expiring credential still works. `rotate <credential_key>` replaces the secret of an existing entry, keeps its non-secret fields, and drops every token derived from the old secret (<<derived-tokens>>); rotation is always an operator verb, never automatic.
* *Zero Model Exposure & Redaction*: No MCP tool, resource, or state representation exposes credential values (`status` and `check` report only metadata: provider name, scope, backend type, and configured status). Every secret value resolved for a request, and every value derived from one (a GitHub App JWT and installation token, <<derived-tokens>>; the `user:token` form of a git transport credential), is added to the in-memory redaction registry of the `SecretRedactor` filter, which keeps it for the runtime's lifetime solely to scrub matching byte/character sequences to `[REDACTED]` across tool results, representations, log records, `audit.jsonl` entries, and error messages. The registry is never persisted and never exported to subprocess environments or logs; it is discarded when the runtime stops (`PM-CRED-5`).
* *Runtime Secrets*: The local-trust and web secrets are redacted the same way (`PM-SEC-6`): the runtime token (link:../runtime-model.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]) is registered by value when the runtime writes it and by every client process when it reads it; device secrets (`pmw_` values) and pairing codes are scrubbed by their shape (link:../identifiers/02-registry-stores-to-web.adoc#id-device-secret[Identifier Registry, device secret]; link:../identifiers/02-registry-stores-to-web.adoc#id-pairing-code[Identifier Registry, pairing code]), because the runtime keeps only their SHA-256 hashes. None of them is written to a log, an audit record, a command-line argument, a process environment, or a representation; request headers are never logged (xref:03-web-server.adoc#web-proxy[API Proxy & Device Secret Forwarding]). The pairing code is printed once to the operator's terminal and never logged. No runtime secret is ever passed to a job: the runtime token file lies outside every job's Landlock read set (link:../job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification]).

|The upstream MCP allowlist of a project: the closed object `upstream_mcp` of its `local-config.json` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), written by the runtime under `local-config.lock` (`PM-SVC-3`)

|`pm-mcp operator epic-worktree teardown\|adopt`
|Maintenance of the shared epic worktree (link:../filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification])

|The optional web server, device pairing, and paired devices (xref:03-web-server.adoc#web-server[Web Server & Pairing (`pm-mcp-web`, `pm-mcp web`)])
|===

1. *Operator Channels*: Overrides (`waive`, `unwaive`, `abort`, `delete-plan`, `grant-access`, and the integrity resolutions) are the operator's own acts and take one of two channels: (a) an operator verb of the CLI (`pm-mcp operator <verb>`, `pm-mcp web ...`), or (b) a paired web device (xref:03-web-server.adoc#web-operator-channel[Every Paired Device Is an Operator Channel]), which has operator rights because only an operator verb can pair it. MCP elicitation (`elicitation/create`) carries no override: it is used only for the operator-configuration choices the server raises itself (for example the integration variants of project setup), and only on a connection that declared elicitation support in its `initialize` capabilities, which are authoritative (link:../runtime-model.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]); without it the state names the `pm-mcp operator config` command. None of these routes through the model; every privileged action is audited with its channel (`cli`, `web` with the `device_id`, or `elicitation` for a configuration choice). An override is never taken as a content answer, and a content answer through elicitation or a paired device is never an override: a question record is answered through its configured delivery (session relay, elicitation, or a paired web device, link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]), there is no CLI command that answers one, and an override relayed by the model (for example a "waive" typed into the host chat) is never accepted. No in-run operator decision exists: the operator acts on a running plan only by waivers, access grants, `abort`, `delete-plan`, and the integrity resolutions, each on the operator's own initiative.
2. *CLI Operator Checks*: Before it sends an operator verb, `pm-mcp` verifies that it is attached to an interactive terminal (`System.console() != null && System.console().isTerminal()`) and that none of the coding-agent environment signals of the link:../client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table] (primary and secondary) is present; either failure refuses the verb with a diagnostic before any request is sent. Every verb then asks for interactive confirmation of the displayed change. The host deny rules installed with the bundles (`Bash(pm-mcp operator:*)`, `Bash(pm-mcp web:*)`, link:../client-profiles.adoc[Client Profiles Specification]) are defence in depth against a model shell. There is no passphrase, no operator session, and no operator entry in the OS keyring: the operator proof of the first iteration is these checks alone.
3. *Accepted Risk*: The checks guard against accidental and naive invocation, not against a model shell that deliberately defeats them (a pseudo-terminal, a cleared environment, indirect invocation). The runtime cannot verify the CLI's checks, so any process of the same OS user that holds the runtime token can call the operator endpoints directly (for example with `curl --unix-socket`). This is accepted for the first iteration and documented as a residual risk (`PM-SEC-3`); a user proof the model cannot produce (an operator passphrase session, OS user presence) and device roles with step-up are deferred (link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]). Every privileged action stays recorded in the audit log (`PM-SEC-6`).
4. [[operator-integrity-pause]]*Integrity Pause*: The only pause of a plan is the `integrity_breach` condition (a tampered plan, epic, or workspace store, or a tampered enrolment file, which pauses every running plan of the project; link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification, Store Digest Verification]). The state and `call_stack` stay unchanged, the representation offers no link, every `pm_do` is rejected with `integrity_paused`, and `facts.operator_command` names `pm-mcp operator accept-edit …` and `pm-mcp operator abort …`. A tampered harness enrolment (`harnesses.json`) is no pause: it refuses the model job and raises the bounded `precondition_unmet` condition (<<operator-enrol-harness>>). The pause has no time bound and no fallback, because a tampered store cannot be trusted to write a hand-back; it ends only by `accept-edit` (the engine re-verifies before it clears the condition) or, for a plan or epic scope, `abort`; the workspace scope has no abort, so `accept-edit workspace <store>` is its only resolution. Every other condition is bounded by its self-remedy budget and ends in the phase's fallback (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]).
5. [[operator-drop-capture]]*Capture Ref Removal (`pm-mcp operator drop-capture <plan_id>`)*: A `land` plan that ended without `merged` keeps its capture ref `refs/pm-mcp/captures/<plan_id>` in the enrolled repository as the user's recovery point and owes `capture_ref_retained` (link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane, item 6]). The verb shows the ref's snapshot commit and its paths, deletes the ref after confirmation, discharges the owed item (also for an archived plan), and appends an `audit.jsonl` record. It is operator-only like every verb of this section; no workflow state, recovery sweep, or MCP tool removes a retained capture ref.
6. [[operator-waive]]*Waivers (`pm-mcp operator waive`, `unwaive`, `waivers`)*: `waive <plan_id> <gate> --reason <text> [--reason-class <class>]` declares a waivable gate met (`review_evidence[:<bot_kind>]`, `ci_check:<name>`, `analysis_gate:<provider>`, `findings:<class>`, `qgate_findings:<phase>`, `spend`, link:../identifiers/02-registry-stores-to-web.adoc#id-waivable-gate[Identifier Registry, Waivable Gate Identifier]; a `met` waiver of `spend` passes the spend check, evaluated once at `merge.gate-entry`); `waive <plan_id> --raise <budget>=<N> --reason <text>` sets the absolute ceiling of `fix_budget:<policy>` or `retry_budget:<policy>` for the plan, above the effective ceiling in force and at most the compiled hard cap. The verb may be given at any time from plan start until the gate's fallback is taken, and the waiver applies to every later evaluation of the gate; it shows the plan, the gate, and the effect before the confirmation. `--reason-class` classifies the reason (`gate_false_positive`, `gate_not_applicable`, `tooling_unavailable`, `deliberate_deferral`, default `unknown`; link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record]); it is mirrored into the audit log with the gate, where the Artifact Gate recurrence count and the lessons-capture signal read it. The runtime appends the record to `waivers.jsonl` (the only writer, link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record]), mirrors it to `audit.jsonl`, and composes a new plan instance version. `unwaive <plan_id> <waiver_id>` revokes an unconsumed waiver; revoking a raise lowers the ceiling at the next budget check, where a counter already above it exhausts the budget and the fallback follows, without a refusal. Refusals: `not_waivable` (a gate outside the closed list, or on the non-waivable list of link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record, Refusals]), `plan_ended` (the gate's fallback was taken or the plan ended), `already_consumed`, `raise_out_of_range`, `position_not_contained`. `waivers <plan_id> [--pending]` lists the waivers with their consumptions and the waiver requests; a pending request filed by a remediation unit's `request_waiver` is answered by `waive` (naming the gate, optionally `--request <request_id>`) within the request's waiver wait (link:../timeouts/01-job-budgets-and-waits.adoc#waiver-wait[Timeouts & Budgets Specification, Waiver Wait]). Requests are also announced as an MCP log notification, shown by `pm-mcp status` and the web app, and posted as an idempotent pull request comment with the label `pm-mcp:waiver-requested`; these announcements are independent of `questions.delivery` and are information only. Every waiver and consumption is listed in the pull request comment and the landing record.
7. [[operator-accept-edit]]*Accept-Edit (`pm-mcp operator accept-edit`)*: `pm-mcp operator accept-edit plan <plan_id> <store> | epic <epic_id> <store> | workspace <store> | lesson <lesson_id> | enrolment <project_id>` shows the file's path and its recorded and current size and SHA-256 before the confirmation; there is no diff, because the prior content is not kept. On confirmation the runtime re-baselines the store's digest (link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification, Store Digest Verification]), the lesson's entry, or the enrolment file's HMAC sidecar (<<enrolment-integrity>>), and appends an `audit.jsonl` record. The resolutions of an `integrity_breach` condition are closed: `accept-edit`, or, for a plan or epic scope, `pm-mcp operator abort` (<<operator-abort>>); a workspace breach ends only by `accept-edit workspace <store>` (for a paused bootstrap entry the store is its pending entry record `pending/<entry_id>.json`, link:../store-schemas/01-format-and-session-log.adoc#pending-entry-record[Store Schemas Specification, Pending Entry Record]).
8. [[operator-abort]]*Abort (`pm-mcp operator abort plan <plan_id>|epic <epic_id> --reason <text>`)*: An unsolicited operator verb: the runtime moves the scope into `plan.aborted` / `epic.aborted` in the next transaction, an engine-owned scope-wide transition under the on-entry rule (every begun, unsettled step is recorded `failed`); pending questions are closed `cancelled`, pending waiver requests `expired`, and the plan's lesson claims released. `plan.aborted` is entered only by this verb (also when it resolves an integrity pause) or by `delete-plan`, whose first transaction is this one and whose second, ordered after it, removes the plan directory; the model ends a plan it cannot continue with `hand_back`, which takes the phase's fallback (`returned` or `handed_back`), never `plan.aborted`. The reason is recorded in the landing record and the audit log.

9. [[operator-grant-access]]*Cross-Project Access (`pm-mcp operator grant-access <plan_id> <project_id> read|read-write --reason <text>`)*: A plan works inside its own enrolled project (`PM-SEC-2`); access to another enrolled project is granted only by the operator, on the operator's own initiative. The verb shows the plan, the target project (identified by its remote owner and name, never by a checkout path), and the access level before the confirmation; the runtime appends a grant record to the plan's append-only grant log in the plan store (link:../store-schemas/15-screening-and-grants.adoc#grant-record[Store Schemas Specification, Grant Record]) and mirrors it to `audit.jsonl`. The grant applies from the plan's next transaction and holds until the plan ends; there is no revocation, and `pm-mcp operator abort plan <plan_id>` (<<operator-abort>>) is the only way to stop it. An access to a project without a grant of the needed level raises `precondition_unmet` on the current state with `facts.operator_command` naming this verb; its `retry` re-checks the grants within the condition budget (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]), after which the phase's fallback is taken with the access as the gap. No link requests a grant, and no plan waits for one.
10. [[operator-enrol-harness]]*Harness Enrolment (`pm-mcp operator enrol-harness <client>`)*: Model jobs run only through an enrolled harness (`PM-EXEC-1`). The verb resolves the absolute path of the profile's `headless.executable`, runs the profile's version probe, and records the path, version, and digest, and nothing else, in the machine's harness enrolment (link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]); it shows the path, version, and digest for confirmation; it refuses a client whose profile has `headless: null` and a version outside `headless.supported_versions`. It captures no environment value: `PM-MCP` never stores or exports a harness's authentication. The harness CLI must already be authenticated by its own login, cached under its home; a harness that is not logged in fails its job like any other failing job. The verb is also the re-baseline of a tampered harness enrolment: when the HMAC check of `harnesses.json` fails, the model job is refused (a `security` audit record `enrolment_tampered`), the model-job state raises `precondition_unmet` with reason `harness_tampered` naming `pm-mcp operator enrol-harness <client>`, and the verb rewrites the file and its sidecar with the named client only after showing path, version, and digest; entries of other clients in the tampered file are not carried over, and each of those clients must be enrolled again. There is no pause and no `accept-edit` form for this file. A later change of the digest or version (the harness updates itself) is accepted while the version stays inside the range: in the accepting transaction the runtime rewrites `harnesses.json` and its HMAC sidecar under `locks/harnesses.lock` and appends the audit record `harness_updated`; outside it every model job on that harness is refused `harness_version_unsupported` until the operator enrols it again (link:../client-profiles/01-profile-schema.adoc#headless-block[Client Profiles Specification, `headless`]).

[#enrolment-integrity]
=== Enrolment Integrity
_See Requirement link:../../Requirements.adoc#PM-SEC-5[PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement]_

* *One File, One HMAC, One Lock per Project*: Every project has its own enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]). Every write of it (the operator verbs `enrol`, `unenrol`, and re-baselining, executed by the runtime on the verb's request) runs under `<PM_MCP_BASE>/locks/enrolments/<project_id>.lock` and also writes the sidecar `<PM_MCP_BASE>/enrolments/<project_id>.json.hmac`, an HMAC-SHA-256 over the canonical file content. `unenrol` removes the file and its sidecar. The key lives in the OS keyring under the `PM-MCP` namespace (service `de.cuioss.pm-mcp`, operator lane); on hosts without a keyring it lives in `<PM_MCP_BASE>/state/enrolment-hmac.key` (mode `0600`).
* *Harness Enrolment*: The machine-wide `<PM_MCP_BASE>/harnesses.json` has its own sidecar `harnesses.json.hmac` under the same key and its own lock `locks/harnesses.lock`; it is verified before every model-job spawn, and a mismatch is resolved by `pm-mcp operator enrol-harness`, never by `accept-edit` (<<operator-enrol-harness>>).
* *Verification*: The runtime verifies a project's HMAC in the project's recovery after a runtime start, before the project is first served (link:../runtime-model.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery]), and before every verify-not-resolve check of the project's jobs (`PM-EXEC-2`, link:../job-runtime/01-pipeline-and-subprocesses.adoc#enrolment-integrity[Job Runtime Specification]); the runtime also verifies it before it serves an `enter` request or an operator verb that uses the file. On mismatch it refuses with `enrolment_tampered`, appends an `audit.jsonl` record, and names the operator command; nothing in that file is trusted until the operator re-baselines it interactively (`pm-mcp operator accept-edit enrolment <project_id>`, after reviewing the displayed recorded and current size and SHA-256, <<operator-accept-edit>>). A tampered file blocks only its own project; every other enrolled project keeps being served.
* *Residual Risk*: Landlock keeps jobs from writing `<PM_MCP_BASE>` on Linux (`PM-SEC-5`), but a host shell driven by the model is not a job and is not confined; the HMAC is the control against it. The key never leaves the runtime (`pm-mcpd`), but a model-driven shell that defeats the CLI's operator checks, or any same-user process that calls the operator endpoint directly with the runtime token, can re-baseline a tampered file (Accepted Risk of <<operator-channel-isolation>>). On hosts without a keyring the key file is readable by every process of the same user, so the HMAC detects edits made without the key but not a deliberate forgery. Both are documented as accepted residual risks (`PM-SEC-5`).

[#enrolment-lifecycle-release]
=== Enrolment, Lifecycle Gate & Release
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-23[PM-WATCH-CLI-23], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-25[PM-WATCH-CLI-25]_
_See Requirement link:../../Requirements.adoc#PM-MIG-1[PM-MIG-1: Six-Stage Build-Out & Per-Project Plan Lifecycle]_

_See Requirement link:../../Requirements.adoc#PM-MIG-5[PM-MIG-5: Quantitative Triggers & Project Release]_

`PM-MCP` and legacy `plan-marshall` keep separate state trees (`PM-MIG-2`, link:../filesystem-layout.adoc#coexistence-lifecycle[Filesystem Layout Specification]). There is no crossing: `PM-MCP` imports nothing from legacy `plan-marshall` (no configuration, lessons, `project-architecture/`, credentials, or learned build timeouts) and never reads or writes `.plan/` or `~/.plan-marshall/`. A project is taken into use as follows; each operator verb is interactive and writes an `audit.jsonl` record:

* `pm-mcp operator enrol [--pilot]`: writes the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` with its HMAC sidecar (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]): the project root (refused with `enrolment_root_conflict` when another enrolment file already names it, and with `project_store_root_mismatch` when the machine store of this `project_id` records a different `project_root`), wrappers with their `pinned_files` and interpreter, host tools, the canonical and discovery command templates it overrides, provider `verify_argv` overrides, project scripts with binding, argument schema (validated as a schema), and maximum timeout, command budgets, write paths, the captured build environment, language servers, and `pilot` (`true` with `--pilot`, audited like every enrolment write); each field is shown to the operator for confirmation. On first enrolment it creates the project's machine store `<PM_MCP_BASE>/projects/<project_id>/` (link:../filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]) with its workspace scope.
* The project setup workflow in the workspace scope (link:../domain-extensions/04-setup-state-machine.adoc#_architecture_enrichment_judgment_links_project_setup_state_machine[Domain Extensions Specification, Project Setup State Machine]) creates, on its first run, `.marshall/` with its `.gitignore` partition (link:../filesystem-layout.adoc#repository-layout[Filesystem Layout Specification]) and `.marshall/config/` with copies of the binary's default workflow units (the JSON team files are sparse and start absent); no legacy input exists.
* *Lifecycle gate*: The gate is a compiled constant of the release: closed in every release before the Stage 4 exit criteria are met (`PM-MIG-4`), open from the release that meets them. While it is closed, plans and epics are created only in a project enrolled as a pilot (`pm-mcp operator enrol --pilot`, the field `pilot: true` of the enrolment file); in every other project `start.create-scope` refuses with `lifecycle_closed` (link:../mcp-tools/01-core-workflow-tools.adoc[MCP Tools Specification]), and the orthogonal services and the workspace scope stay available. The clones of a parallel run are enrolled as pilots. `pilot` is set and cleared only by running `pm-mcp operator enrol` again, with or without `--pilot`; clearing it affects only later `start.create-scope` calls, and the project's live plans and epics continue. With the gate open, `pilot` has no effect: the plan lifecycle (the `plan` and `epic` scopes) is offered in every enrolled project until the project is released.
* `pm-mcp operator unenrol`: refuses while the project has non-terminal plans or epics or running jobs, naming them. It removes only the enrolment file and its HMAC sidecar and leaves the project's machine store `<PM_MCP_BASE>/projects/<project_id>/` untouched; retention (`pm-mcp operator sweep`, with the machine-wide retention defaults) purges only aged items and never the store as a whole (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification, Evidence-Based Removal Sweeps]). The store records its `project_root` (link:../store-schemas/11-enrolment-store.adoc#project-store-identity[Store Schemas Specification, Project Store Identity]); enrolling the same `project_id` again reuses the store only for the same root and is refused otherwise (`project_store_root_mismatch`, an operator-verb refusal naming both roots, not an MCP tool error).
* `pm-mcp operator release-project`: the operator's switch-off for the `PM-MIG-5` triggers; stops offering the plan lifecycle for the project. Plans in flight stay readable in the project's machine store and nothing is converted. The project can continue on legacy `plan-marshall`, whose `.plan/` `PM-MCP` never touched.

== Security Audit Trail & Three-Tier Identity Verification
_See Requirement link:../../Requirements.adoc#PM-SEC-6[PM-SEC-6: Security Audit Trail & Tamper-Evident Logging]_

_See Requirement link:../../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Three-Tier Environment Mismatch Detection & Audit]_

_See Requirement link:../../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

Every MCP tool call, state transition, job execution, credential lookup, and operator command appends a structured JSONL record to `<PM_MCP_BASE>/logs/audit.jsonl` (mode `0600`, appended under the audit lock on the log file itself, the leaf of the lock order, schema defined in link:../store-schemas.adoc[Store Schemas Specification]):

* *Three-Tier Identity Tuple*: Every session-bound audit record (state transitions and `enter`) captures in its `details` (1) `declared_client` (the declared `client` of the scope's last session row, link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]), (2) `detected_env` (from environment signatures at `enter` or MCP `clientInfo`), and (3) `os_principal` (`System.getProperty("user.name")` / `geteuid()`). A machine-level record (runtime start, an operator verb, a sweep) carries only `os_principal` (link:../store-schemas/12-machine-stores.adoc#audit-log[Store Schemas Specification, Audit Log]). Any disagreement between Tier 1 and Tier 2 sets the top-level `identity_mismatch: true` of the record; the returned TOON representation carries only the top-level `profile_warning: client_identity_mismatch` (link:../client-profiles.adoc[Client Profiles Specification], Mismatch Resolution & Audit Behavior), never the identity tuple.
* *Hash Chain*: Every record carries `prev_hash`, the lowercase hex SHA-256 of the previous record's canonical line (its exact UTF-8 bytes in the file, without the trailing newline). The first record of a new log carries the genesis value (64 `0` characters). Records are appended only by writers that hold the log's lock and read the current last line first.
* *Anchored Head (`logs/audit.head`)*: After every append the writer updates, under the same lock, the sidecar `logs/audit.head` with the current file name, record count, last `event_id`, and head hash (the hash of the last canonical line), protected by an HMAC-SHA-256 under the integrity key of the enrolment store (<<enrolment-integrity>>). The chain alone proves only that the records present are consistent; the anchored head makes a deleted log, a reset to the genesis value, a truncated tail, and a consistently rewritten chain detectable.
* *Rotation & Checkpoints*: When `audit.jsonl` exceeds `audit_rotation.max_bytes` or `audit_rotation.max_days` (`machine-config.json`, link:../timeouts/03-retention-host-config.adoc#audit-rotation-age[Timeouts & Budgets Specification]), the writer appends a `checkpoint` record (record count, head hash, HMAC under the same key), renames the file to `audit-<first_event_id>.jsonl`, and starts the new `audit.jsonl` with a record whose `prev_hash` is the hash of that checkpoint line. Every rotated file is listed in the append-only index `logs/audit-index.jsonl` (file name, first and last `event_id`, record count, checkpoint hash), itself hash-chained and anchored in `audit.head`. The machine sweep `pm-mcp operator sweep --machine` (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas, Evidence-Based Removal Sweeps]) removes rotated files older than `audit_rotation.retain_days` (`machine-config.json`, link:../timeouts/03-retention-host-config.adoc#rotated-audit-files[Timeouts & Budgets Specification, Rotated Audit Files]) as whole files and never their index entries, one audit record each, so a purged file stays accounted for.
* *Chain Verification at Runtime Start*: The runtime verifies incrementally: the HMAC of `audit.head`, the index, and the records of the current file after its last checkpoint. A missing log, a reset to genesis, a record count below the anchored count, or a head mismatch is reported as `audit_chain_broken` with `reason` `missing`, `reset`, `truncated`, or `head_mismatch`; a broken link inside the verified range uses `reason: link_broken` and names the first broken line. The full chain across all rotated files is verified on demand by `pm-mcp operator audit verify`. The same reporting rules apply to every result: on `stderr`, in `pm-mcp status`, and as an `audit_chain_broken` security record; the log is never rewritten or silently repaired, and the next record chains to the last line as found.
* *Residual Risk*: The anchoring is tamper-evident, not tamper-proof: a process that holds the integrity key (on macOS, anything that runs the `pm-mcpd` binary, <<enrolment-integrity>>; on hosts without a keyring, any process of the user) can forge a consistent head. This is accepted and documented with the enrolment integrity risk (`PM-SEC-6`).
* *Error Sanitization*: Unhandled exceptions or protocol errors return only a closed-enum error code to the MCP caller, plus the `audit_id` (a UUIDv7, link:../identifiers/02-registry-stores-to-web.adoc#id-audit-id[Identifier Registry]) only where the operator must look the error up (`internal_fault`, `file_unreadable`; link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]); stack traces and host filesystem paths are written exclusively to `<PM_MCP_BASE>/logs/daemon.log`.

== Outbound HTTPS Security (`cui-http`) & Native Runtime Stack
_See Requirement link:../../Requirements.adoc#PM-TECH-1[PM-TECH-1: Java 25+ & Quarkus MCP Runtime Foundation]_

_See Requirement link:../../Requirements.adoc#PM-TECH-2[PM-TECH-2: Outbound HTTPS Client, LSP Client & McpAssured Testing Libraries]_

_See Requirement link:../../Requirements.adoc#PM-TECH-3[PM-TECH-3: GraalVM Native Executable & Startup/Memory Bounds]_

_See Requirement link:../../Requirements.adoc#PM-TECH-4[PM-TECH-4: Operating System Platform Integration (macOS & Linux)]_

_See Requirement link:../../Requirements.adoc#PM-SVC-3[PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging]_

_See Requirement link:../../Requirements.adoc#PM-TEST-5[PM-TEST-5: Security Boundary & Confinement Adversarial Testing]_

* *Outbound HTTPS Hardening (`de.cuioss:cui-http`)*: All outbound REST and GraphQL calls (SonarQube/SonarCloud, the native GitHub and GitLab clients) and remote upstream MCP calls use `de.cuioss:cui-http`'s `HttpHandler` and `ResilientHttpAdapter` with TLS 1.2+, mandatory certificate/hostname verification, HTTPS-only redirect following, and origin-pinned bearer token transmission (stripping `Authorization` headers on any cross-origin redirect). All URL/path/header parameters composed into outbound requests are validated through `de.cuioss.http.security` pipelines. The native git transport (JGit) uses a connection factory with the same TLS rules that connects only to the credential entry's origin (<<native-confinement>>). Both honour the operator's `proxy` setting of `machine-config.json` and no other proxy source (<<native-confinement>>, Configuration allowlist). An upstream MCP server is always a remote HTTPS server reached this way; no upstream server runs as a `stdio` subprocess (`PM-TECH-2`).
* *GraalVM Native Image & Resource Bounds*: The runtime `pm-mcpd` is compiled as a standalone Quarkus native executable (`Java 25+`, `quarkus-mcp-server-http`, Virtual Threads); the CLI `pm-mcp` (with the relay) and the launcher `pm-mcp-exec` are plain native images without Quarkus (xref:01-cli-and-installer.adoc#cli-implementation[CLI Implementation]). Startup and memory bounds for the runtime, the relay, and the CLI are defined in `PM-TECH-3` and verified as described in the link:../runtime-model.adoc[Runtime & Interaction Model Specification].
* *STDIO & Confinement Adversarial Verification (`PM-TEST-5`)*: Integration tests (`*IT`) using `McpAssured` (`McpStdioTestClient`) verify the transport isolation properties listed in the link:../runtime-model.adoc#_verification[Runtime & Interaction Model Specification], that insecure permissions (`0755`) on `<PM_MCP_BASE>/enrolments/` trigger fail-closed termination at runtime start (exit code `77`), that insecure permissions (`0644`) on one project's enrolment file block only that project (`enrolment_insecure`), that a project's enrolment file edited outside the operator verbs is refused with `enrolment_tampered` for that project while a second enrolled project is still served, that a job writing `<PM_MCP_BASE>/enrolments/<project_id>.json` or into another enrolled project's root fails under the Linux Landlock write set while a write into its own project root succeeds, that a job cannot read `<PM_MCP_BASE>/run/runtime.token` or a credential file under `<PM_MCP_BASE>/credentials/` under the Linux Landlock read set while a read outside `<PM_MCP_BASE>` succeeds (positive control), that a request without the runtime token is refused on `/mcp` and `/api/v1`, that an operator verb run without a terminal or with an agent environment marker is refused before any request is sent, while an insecure fallback credential file blocks only the step that needs it (`credentials_file_insecure`), that path-traversal or command-injection payloads are deterministically rejected and logged to `audit.jsonl`, and that hostile repository configuration against the native git variant is contained: a `url.<base>.insteadOf` or `pushInsteadOf` rewrite and a `remote.<name>.pushurl` to a foreign host yield `remote_origin_mismatch` with a `security` audit record and no credential-bearing request to that host, while `core.sshCommand`, `core.fsmonitor`, a `.gitattributes` filter driver, and a hook in a native-selected repository start no process and yield `capability_missing`; CLI-variant `git` and `ci` jobs are shown to carry no token variable or askpass helper in their environment.
