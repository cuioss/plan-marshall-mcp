*Proven Write Credential for Upstream Filing*: A credential that an operator-confirmed filing job would use to write to a vendor tracker (the lesson Upstream Release, link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record]) is proven by a write-permission probe on the target tracker before the filing job is offered; without a passed probe the release action only renders the issue body for the operator to file.

=== Two-Lane Provider Architecture

External provider integrations are strictly partitioned into two authentication lanes. The provider operations of both lanes are contracts of the provider modules `pm-provider-git` and `pm-provider-ci` and the findings and code-analysis contracts of `pm-core`, implemented by `pm-provider-github`, `pm-provider-gitlab`, and `pm-provider-sonar` (link:../../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]). For the integrations `git`, `github`, and `gitlab` each contract has two implementations, the *native variant* (in process) and the *CLI variant* (jobs of the enrolled `git`, `gh`, `glab`); the lane of such an integration follows its variant:

1. *System Lane (CLI variant of `git`, `github`, `gitlab`)*: Executed as verified subprocess jobs (`PM-EXEC-5`) that inherit the developer's existing CLI authentication (`~/.gitconfig`, credential helpers, SSH agent, `gh auth`, `glab auth`), by design (<<cli-variant-credentials>>). `PM-MCP` never reads, extracts, or stores CLI-lane tokens and never injects a Token Lane secret into such a job.
2. *Token Lane (SonarQube/SonarCloud, authenticated upstream MCP servers, and the native variant of the git HTTPS transport, GitHub, and GitLab)*: Executed directly by the runtime (`pm-mcpd`) in process: REST and GraphQL through `de.cuioss:cui-http`, git transport through JGit over HTTPS. Tokens are resolved per request by credential key (`PM-CRED-1`) from the credential store hierarchy: `<project>/<credential_key>` (project-scoped override) -> `<credential_key>` (global fallback), and sent only to the origin of the entry's `url` and, for `github` and `gitlab`, the API origin derived from it (<<agent-credentials>>, `PM-CRED-5`). That `url` belongs to the operator-owned credential entry; the team configuration (`.marshall/config/project.json`) may only reference a credential key and never decides where a token is sent. The native variant authenticates with the agent credential, never with the operator's ambient CLI login: for a GitHub App every write acts as the operator via the App (its user access token, <<user-access-token>>) and every read-only query as the App installation (<<agent-credentials>>).

*Variant selection*: The project setup state `setup.select-integration-variants` (link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]) applies `native` to every integration unless the derived fact `git_native_capability` finds a feature the project uses that the native variant cannot serve; only then the operator chooses, by elicitation where the connection supports it or otherwise through the operator channel (`pm-operator config --project <project_id>`, named in the state's `facts`, after which the entry session, which drives the project setup, follows `retry`), never by a model or a content answer: the choice is never a question record, and no git or provider operation runs before the variant is set. The choice is stored in the operator's `local-config.json` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Local Configuration]), never in a team file, because it decides whose credentials act. One integration of a project uses exactly one variant for all its operations; different integrations may differ (for example the CLI variant of `git` with the native variant of `github`). `sonar` has only the native variant. There is no automatic fallback between variants: a silent switch to the CLI variant would silently switch to the operator's ambient identity with all of the operator's rights. The variant that served an operation, the credential key and origin, and for the CLI variant `identity: operator_ambient` are written to the operation's audit record, never into a model-facing result (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

=== Agent Credentials of the Native Variant
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-7[PM-WATCH-CLI-7]_

* *No refusal by credential kind*: Every listed credential kind is accepted on equal footing; neither the kind nor a missing expiry is refused or warned about in a workflow. `set` and `verify` determine the token kind from the provider and record it with the entry (<<operator-credential-cli>>).
* *Check visibility*: A credential that cannot read check runs (a GitHub fine-grained personal access token cannot call the Checks API) is detected up front by the derived network fact `checks_visible` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts]); `ci.checks` then reads what the credential can see (commit statuses, check suites) and reports `completeness: incomplete`, which never counts as a green check.
* *Installation tokens*: For a `github_app` entry the runtime signs an RS256 JWT with the JDK (`iat` back-dated and `exp` bounded by the GitHub App JWT validity window, link:../timeouts/03-retention-host-config.adoc#github-app-jwt-window[Timeouts & Budgets Specification]; `iss` the `client_id`) and mints an installation token for the read-only query classes, narrowed to the one repository (or, for a granted cross-repository read, to the granted repositories, <<cross-repository-reads>>) and to the read-only permission set of the operation class, through `POST /app/installations/{id}/access_tokens`; every write operation uses the user access token instead (<<user-access-token>>). The App needs at most the repository permissions `contents: write`, `pull_requests: write`, `checks: read`, `actions: read`, `statuses: read`, `issues: write`, and `metadata: read`; a comment on a pull request needs `pull_requests: write` (`issues: write` alone is refused for it), and `issues: write` serves issue comments only. Administrative permissions are never required, because repository administration (such as enabling a merge queue) stays with the operator.
* [[user-access-token]]*User access token (writes)*: A `github_app` entry also holds a user refresh token of the App, obtained once by the device flow of `pm-operator credentials set github` (<<operator-credential-cli>>; the App must have the device flow enabled). Every write operation (push, pull-request creation and edit, comments and review replies, review triggers, thread resolution, merge and merge-queue enqueue, branch delete) runs with the user access token, which acts as the operator via the App (shown by the provider as the operator's login "via" the App) with the intersection of the App's and the operator's permissions; so the pull requests and review triggers the server writes are user-authored, which review bots that skip bot-authored pull requests and bot triggers require (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#automatic-review[Phase Workflows Specification, Automatic Review]). The access token (valid 8 hours) is held in memory only, like an installation token (<<derived-tokens>>). Before it expires (link:../timeouts/03-retention-host-config.adoc#user-token-refresh-margin[Timeouts & Budgets Specification, User token refresh margin]) the runtime refreshes it with the refresh token and the `client_id`, without a client secret; the provider rotates both tokens on every refresh, revokes the old access token at once, and accepts each refresh token (valid about six months) once. The refresh is therefore atomic under `<PM_MCP_BASE>/locks/credentials.lock`: one refresh at a time per entry; the new refresh token is written to the active backend and read back before the new access token is used, and every in-memory holder switches to the new access token in the same step. A refresh whose answer is lost, or a refused or expired refresh token, makes the entry `credential_check_failed`, whose operator command is `pm-operator credentials set github` (a new device flow); there is no fallback to the installation token for a write. A personal access token credential (GitHub or GitLab) authors as its own user and needs none of this. _Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-30[PM-WATCH-CLI-30], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-105[PM-WATCH-PHASE-105]_
* *Committer identity*: The committer of agent commits is the identity resolved from the agent credential through `ci.whoami` (a GitHub App: `<app-slug>[bot]` with the address `<id>+<app-slug>[bot]@users.noreply.github.com`; a token: the token's user), recorded as the operator-only derived fact `agent_identity`; without a Token Lane provider credential the committer is the fixed `plan-marshall-mcp` noreply identity. The author stays the operator (`commit_identity`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Local Configuration]). The identity appears in the operator's `status` output and the audit log, never in a model-facing representation.

[#derived-tokens]
=== Short-Lived Derived Tokens
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-2[PM-WATCH-CLI-2], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-5[PM-WATCH-CLI-5]_

A stored secret is read per request and never cached (`PM-CRED-5`). A token derived from it that expires by construction, a GitHub App installation token (valid one hour) or a GitHub App user access token (valid 8 hours, <<user-access-token>>), is the second named exception of `PM-CRED-5`:

* It is held in memory only, an installation token keyed by installation and permission set and reused until the derived token reuse margin before its expiry (link:../timeouts/03-retention-host-config.adoc#derived-token-reuse-margin[Timeouts & Budgets Specification]), then a new one is minted; a user access token keyed by its credential entry and refreshed at the user token refresh margin (link:../timeouts/03-retention-host-config.adoc#user-token-refresh-margin[Timeouts & Budgets Specification]). The user refresh token is the stored secret of that derivation: it is read only for a refresh and replaced in the store by its successor in the same refresh.
* It is registered with the redaction registry when minted (<<operator-credential-cli>>).
* It is never persisted, never exported to a subprocess environment or log, and never passed to the CLI variant.
* It is dropped when its credential entry is rotated, removed, or re-set, when a request with it fails with `auth_failed` (revocation), and when the runtime stops; a user access token is also replaced at once by its successor when it is refreshed.

[#cross-repository-reads]
=== Cross-Repository Reads
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-31[PM-WATCH-CLI-31]_

The CI provider contract (`pm-provider-ci`) has four read operations beyond the project's own repository, served by both variants and in the `ci` query operation class (link:../timeouts/01-job-budgets-and-waits.adoc#ci-query-budget[Timeouts & Budgets Specification]):

* `ci.org-repos`: the repositories of an organisation (GitHub) or group (GitLab);
* `ci.code-search`: a code search restricted to an organisation or group;
* `ci.repo-file`: one file of a repository outside the project, at a named ref;
* `ci.labels`: the label list of a repository.

Each runs only under an operator grant that names its target (`pm-operator grant-access <plan_id> --org <owner> read` or `--repo <owner>/<name> read`, <<operator-grant-access>>); `ci.labels` of the project's own repository needs none. Without the grant the operation raises `precondition_unmet` with `grant_missing`, like every cross-project access (`PM-SEC-2`). In the native variant a GitHub App reads with an installation token narrowed to `metadata: read` and `contents: read` on the granted repositories; a repository outside the App's installation is not visible to it. Every result carries `completeness`: `complete`, or `incomplete` with the bounds that cut it (`page_cap`, the server's compiled page bound; `provider_result_cap`, for example the provider's cap on search results or its `incomplete_results` flag; `not_visible`, repositories the credential cannot see, where the provider reports them). An `incomplete` result is never read as "absent": a consumer that needs the whole population treats it as unknown. File contents and search excerpts are external text and pass the level-1 validator before they reach a model (`PM-SEC-1`).

[#native-confinement]
=== Native Operation Confinement
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-6[PM-WATCH-CLI-6], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-9[PM-WATCH-CLI-9], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-28[PM-WATCH-EXT-28]_

A native operation runs inside the runtime process: it has no argument vector, no environment, and no Landlock ruleset. What it can do is bounded by the following rules, each enforced in the provider modules:

* *Paths*: It writes only inside the enrolled project root and its linked worktrees; every path it derives, including the `gitdir` targets of worktree administration files, passes the `PM-SEC-2` checks.
* *Origin check*: HTTP requests go through `cui-http` with origin pinning. The git transport resolves the effective fetch and push URL of the remote with every `url.<base>.insteadOf`/`pushInsteadOf` rewrite and `remote.<name>.pushurl`, maps an SSH remote of a known provider host (`github.com`, `gitlab.com`, and hosts whose `ci_provider` is established) to its HTTPS form without changing the configured remote, and requires `https` and an origin equal to the credential entry's origin. A mismatch refuses the operation with `remote_origin_mismatch`, appends a `security` record to `audit.jsonl`, and sends nothing; every other SSH remote is `capability_missing{reason: ssh_only_remote}`. Its connection factory refuses every other host, so a redirect cannot carry the credential elsewhere.
* *Configuration allowlist*: From the repository configuration and the user's global configuration it reads only content-shaping keys: `core.autocrlf`, `core.eol`, `core.safecrlf`, `core.excludesFile`, `core.ignoreCase`, `core.precomposeUnicode`, `remote.<name>.url|pushurl|fetch`, `url.<base>.insteadOf|pushInsteadOf`, `branch.<name>.*`, `init.defaultBranch`, and, for capability detection only, `core.hooksPath`, `filter.<driver>.*`, `lfs.*`, `submodule.*`, and `extensions.*`. Every other key is ignored, among them `credential.*`, `core.sshCommand`, `core.fsmonitor`, `http.*` proxy settings, and `include.*`/`includeIf.*` targets outside the repository. A proxy is an operator setting, never a repository value or an environment variable: the closed object `proxy` of `machine-config.json` (`https_proxy`, a URL without embedded credentials, and `no_proxy`, a list of hosts; link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]), set with `pm-operator config` and applied to every `cui-http` call and to the JGit transport of the native variant. Authenticated proxies are deferred (link:../../later-improvements.adoc#_l_8_authenticated_proxies[Later Improvements, L-8]).
* *No process execution*: A native operation never starts a process. JGit's process entry points (`FS.runInShell`, `FS.runHookIfPresent`, filter-driver execution) are served by a `pm-provider-git` subclass of JGit's `FS` that refuses with `capability_missing` instead of running anything, so no repository value can start a process in the runtime.
* *Selection criterion instead of fallback*: Repository hooks (non-sample files in `.git/hooks/`, `core.hooksPath`, `.husky/`, `lefthook.yml`, `.pre-commit-config.yaml`), required commit signing (`signed_commits_required`), filter drivers including LFS, submodules, SHA-256 object format, partial clone, sparse checkout, split index, and SSH-only remotes are detected by the derived fact `git_native_capability` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts]). An operation that needs a missing capability is refused with `capability_missing{reason}` naming the feature and the `pm-operator` command that selects the CLI variant for the integration; there is no automatic fallback. A new capability finding invalidates a recorded native selection, and project setup requires the operator-channel choice for that integration.

[#cli-variant-credentials]
=== Credentials of the CLI Variant
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-8[PM-WATCH-CLI-8]_

The CLI variant runs the operator's enrolled `git`, `gh`, or `glab` with the operator's ambient authentication, by design: its purpose is the operator's own setup (signing, SSH remotes, hooks, special hosts).

* *Operator choice, audited*: `setup.select-integration-variants` (link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]) shows on selection that the CLI variant of that integration acts with the operator's identity; every CLI job's audit record carries `identity: operator_ambient`.
* *No token injection*: An agent token is never passed to a CLI job, neither as `GH_TOKEN`, `GITHUB_TOKEN`, `GITLAB_TOKEN`, or another token variable, nor through a `GIT_ASKPASS` or `SSH_ASKPASS` helper, nor through a credential helper served by `PM-MCP`: every descendant of the job, including repository hooks, and every same-user process reading `/proc/<pid>/environ` could read it, which breaks `PM-CRED-5`.
* *Environment, write paths, `stdin`*: The job environment rows of CLI-variant `git` and `ci` jobs (configuration discovery, SSH agent socket, provider CLI configuration directories, non-interactive guards, committer variables), their additional write paths, and their `stdin` forms are specified in link:../job-runtime.adoc[Job Runtime Specification] (Job Environment; In-Memory `stdin` Streaming). `known_hosts` stays read-only: an unknown host key fails the job, it is never accepted.
* *Hooks and signing*: Repository hooks and signing programs run only here, started by `git` itself inside the CLI `git` job and therefore under that job's environment and Landlock confinement (`PM-SEC-5`).
* *No session bus*: A job never reaches the user's session bus (link:../job-runtime/02-confinement-and-environment.adoc#session-bus[Job Runtime Specification, Session Bus]), so on Linux a CLI job cannot use a login kept only in the Secret Service (the `libsecret` git credential helper, the keyring storage of `gh` or `glab`). The verification command of the integration (`gh auth status`, `glab auth status`, `git ls-remote`) then fails as a job, and the setup names the cause; the operator keeps that login in the tool's own file storage or an SSH agent, or selects the native variant.

=== OS Keyring Backends & Fallback File Store

The `CredentialStore` service uses exactly one active backend per machine, chosen at runtime start: the OS keyring when one is available, otherwise the fallback file store. A secret never exists in two backends, and within the active backend the project entry `<project>/<credential_key>` is resolved before the global entry `<credential_key>` (`PM-CRED-2`). `<project>` is the project's enrolment identifier (`PM-CRED-3`), never derived from a remote URL or a checkout path. [[keyring-service-name]]Every keyring entry of `PM-MCP`, Token Lane credentials and the enrolment integrity key alike, is stored under one *service name* (`PM-CRED-2`): `de.planmarshall.mcp` for the default `PM_MCP_BASE`, and `de.planmarshall.mcp/<instance_hash>` for any other, where `<instance_hash>` is the first 16 hex characters of the SHA-256 of the canonical absolute path of `<PM_MCP_BASE>` (`PM-DIST-5`), so two instances never share an entry. The backends are:

* *macOS Keychain (Primary on macOS)*: Invokes macOS Security framework APIs (`SecItemAdd`, `SecItemCopyMatching`, `SecItemUpdate`, `SecItemDelete`) directly via Java 25's Foreign Function & Memory (FFM) API (`java.lang.foreign.Linker`). Items are stored under the <<keyring-service-name,service name>> with account `<credential_key>` or `<project>/<credential_key>` and a trusted-application ACL restricting unprompted read access to the runtime binary `pm-mcpd`, the only process that reads or writes credentials (neither CLI binary touches the credential store); another reader raises the OS access dialog. The ACL identifies the binary by its code signature: `pm-mcpd` of a macOS release is signed with a Developer ID and notarised in the macOS release job, so the ACL holds the designated requirement of that signature (the team identifier) and an upgraded `pm-mcpd` reads the items of its predecessor without a prompt. A locally built `pm-mcpd` is ad-hoc signed and trusted by its code-directory hash, so every rebuild loses unprompted access to the items the previous build stored (the OS asks once per item). The items live in the login keychain; the data-protection keychain refuses a binary without an entitlement and is not used.
* *Linux Secret Service (Primary on Linux)*: Communicates with `org.freedesktop.secrets` over the user session D-Bus (`gnome-keyring` / `KWallet`) storing attributes `service=<service name>` (<<keyring-service-name>>), `credential_key=<credential_key>`, and optional `project=<project>`. It is available only when the session bus is reachable and the default collection is unlocked at runtime start; a locked collection is never prompted for, and the file store then serves until the next runtime start. The Secret Service has no per-application access control: every process of the user that reaches the session bus can read an unlocked collection. Jobs therefore never reach the session bus (link:../job-runtime/02-confinement-and-environment.adoc#session-bus[Job Runtime Specification, Session Bus]); an unconfined process of the user, such as a model-driven host shell, can, which is an accepted residual risk (`PM-SEC-5`).
* *Permission-Guarded Fallback File Store*: When no OS keyring is available (headless Linux or WSL2), secrets are stored in the `PM-MCP` credential file format (`format_version`, closed schema, written only by the runtime on a `pm-operator credentials` verb, `PM-CRED-3`) at `<PM_MCP_BASE>/credentials/<credential_key>.json` and `<PM_MCP_BASE>/credentials/<project>/<credential_key>.json` (directory mode `0700`, file mode `0600`, see link:../filesystem-layout.adoc[Filesystem Layout Specification] and link:../store-schemas.adoc[Store Schemas Specification]). If ownership or permission checks on a credential file fail, the runtime refuses to read it and holds only the step that needs that credential: the engine raises the `precondition_unmet` condition on the step's current state with `facts.reason: credentials_file_insecure` and `facts.operator_command` naming the exact `pm-operator credentials` command that repairs it (`PM-CRED-4`); its `retry` re-checks the file within the condition budget (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]), after which the phase's fallback is taken with the credential as the gap. A missing credential, a credential file the runtime did not write in the current format, and a resolved credential whose check against its provider fails (the step's provider call, or `ci.whoami` where the step verifies the identity, answers that the credential is rejected, revoked, or lacks a required permission) are handled the same way (`facts.reason: credential_missing`, `credentials_file_invalid`, `credential_check_failed`). The runtime itself keeps running; it exits with code `77` only for the causes of step 3 of the startup sequence (link:../runtime-model/02-startup-recovery-drain.adoc#_startup_sequence[Runtime & Interaction Model Specification, Startup Sequence]).

* *No Legacy Credential Access*: The `CredentialStore` never reads `plan-marshall` credentials (its keyring entries, `~/.plan-marshall/credentials/`, `PLAN_MARSHALL_CREDENTIALS_DIR`, `PLAN_MARSHALL_HOME`), and no verb imports them (`PM-MIG-2`). Credentials enter the `PM-MCP` stores only through `pm-operator credentials`, each entry operator-owned, including its allowed `url`.

[#operator-credential-cli]
=== Operator-Only Credential CLI & Runtime Secret Redaction
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-28[PM-WATCH-CLI-28]_

* *Operator CLI Verbs*: Credential mutations and verifications are restricted exclusively to interactive TTY invocations of `pm-operator credentials set|status|verify|remove|migrate|rotate <credential_key> [--project]` (operator verbs, <<operator-channel-isolation>>). `set` and `rotate` always read the secret from the terminal with echo disabled (`System.console().readPassword()`), together with the non-secret fields (`url`, `auth_type`, header settings; for `github_app` the `client_id` and optional `installation_id`, the PKCS#1 or PKCS#8 `private_key` being read as a secret), and send them in the body of one request to the runtime's API over its Unix domain socket (link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]); `pm-operator` keeps the secret only in a `char[]` that it clears after the request and never writes it anywhere. Entering a secret is CLI-only: the endpoint refuses a web-originated request (xref:03-web-server.adoc#web-proxy[API Access & Device Secret]). The runtime writes the entry into the active backend; when targeting the file store it writes the complete credential file in the `PM-MCP` format (`format_version`, closed schema, link:../store-schemas/12-machine-stores.adoc#credential-store[Store Schemas Specification, Credential Store]) atomically with mode `0600`, under `<PM_MCP_BASE>/locks/credentials.lock`. For a `github_app` entry, `set` (and `rotate`) then runs the GitHub device flow: the runtime requests a device code for the `client_id` on the entry's `url` origin, `pm-operator` shows the verification URL and the user code, the operator authorizes the App in the browser, and the runtime polls at the interval the provider names until it receives the user tokens or the code expires (the verb then fails and writes nothing); it stores the refresh token with its expiry (`expires_at`) in the entry and never shows either token. The runtime is the only writer of credential files, on an operator verb and, for the rotated refresh token of a `github_app` entry, in its token refresh (<<user-access-token>>): no placeholder file and no hand-edited file exists, and a file it did not write in the current format is refused (`credentials_file_invalid`). Secrets are never accepted from command-line arguments or environment variables.
* *Identity, Kind & Expiry*: For `github` and `gitlab` entries, `set` and `verify` call `ci.whoami` and record the token kind (`token_kind`) and, where the provider reports one, the expiry (`expires_at`; an operator-entered expiry at `set` otherwise); `verify` shows the resolved identity, its permissions on the enrolled repository, and whether it can read check runs (`checks_visible`), without revealing the secret. `status` reports per entry one of `present` (stored, not yet verified), `not_found`, `verified`, `unverified`, the serving backend, plus `expiring` when `expires_at` lies within the credential expiry warning window (link:../timeouts/02-runtime-leases-operator-web.adoc#credential-expiring-window[Timeouts & Budgets Specification]), and names an entry without a known expiry; neither is a refusal, and neither reaches a model-facing representation, since an expiring credential still works. No verb shows a stored secret, and the runtime's API has no endpoint that returns one: `status` and `verify` read the entry inside the runtime and receive only its status and backend (link:../runtime-model/01-processes-and-transport.adoc#api-no-secret-read[Runtime & Interaction Model Specification, Local API, Credential entries]). `rotate <credential_key>` replaces the secret of an existing entry, keeps its non-secret fields, and drops every token derived from the old secret (<<derived-tokens>>); replacing a stored secret is always an operator verb, and the only automatic replacement is the refresh-token rotation of the user access token (<<user-access-token>>). For `gitlab`, `ci.whoami` reads `GET /personal_access_tokens/self`; for a token that endpoint refuses because it is no personal access token (an OAuth token, `400`), it falls back to `GET /user` for the identity and records `token_kind: gitlab_oauth_token`; GitLab reports neither scopes nor an expiry for such a token there, so its scopes stay unknown and its expiry is the operator-entered one or unknown. `migrate <credential_key> [--project]` moves an entry of the fallback file store into the OS keyring once one is the active backend: the runtime writes the entry to the keyring, verifies it by reading it back, and only then deletes the credential file; a failed write or read-back leaves the file in place and reports the failure (`credential_store_failed`, link:../runtime-model/01-processes-and-transport.adoc#api-error-codes[Runtime & Interaction Model Specification, Local API Error Codes]). While the keyring is the active backend, the file store is never read for resolution, and `status` lists every remaining file entry with the `migrate` command that moves it.
* *Zero Model Exposure & Redaction*: No MCP tool, resource, or state representation exposes credential values (`status` reports only metadata: provider name, scope, backend type, and configured status). Every secret value resolved for a request, and every value derived from one (a GitHub App JWT and installation token, <<derived-tokens>>; the `user:token` form of a git transport credential), is added to the in-memory redaction registry of the `SecretRedactor` filter, which keeps it for the runtime's lifetime solely to scrub matching byte/character sequences to `[REDACTED]` across tool results, representations, log records, `audit.jsonl` entries, and error messages. The registry is never persisted and never exported to subprocess environments or logs; it is discarded when the runtime stops (`PM-CRED-5`).
* *Runtime Secrets*: The local-trust and web secrets are redacted the same way (`PM-SEC-6`): the runtime token (link:../runtime-model/01-processes-and-transport.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]) is registered by value when the runtime writes it and by every client process when it reads it; a worker's job token (link:../identifiers/02-registry-stores-to-web.adoc#id-job-token[Identifier Registry, Job Token]) is registered by value when the runtime mints it and is also scrubbed by its `pmj_` shape, because only its SHA-256 survives a runtime restart; device secrets (`pmw_` values) and pairing codes are scrubbed by their shape (link:../identifiers/02-registry-stores-to-web.adoc#id-device-secret[Identifier Registry, device secret]; link:../identifiers/02-registry-stores-to-web.adoc#id-pairing-code[Identifier Registry, pairing code]), because the runtime keeps only their SHA-256 hashes. None of them is written to a log, an audit record, a command-line argument, a process environment (the job token's relay environment excepted), or a representation; request headers are never logged (xref:03-web-server.adoc#web-proxy[API Access & Device Secret]). The pairing code is printed once to the operator's terminal and never logged. No runtime secret other than a worker's own job token (in its relay's environment `PM_MCP_JOB_TOKEN`) is ever passed to a job: the runtime token file lies outside every job's Landlock read set (link:../job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification]).

[#operator-channel-isolation]
== Operator Channel Isolation & Privileged CLI (`pm-operator`)
_See Requirement link:../../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_

_See Requirement link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_

_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-3[PM-WATCH-CLI-3], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-14[PM-WATCH-CLI-14], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-22[PM-WATCH-CLI-22], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-24[PM-WATCH-CLI-24]_

Privileged actions are unreachable from every MCP tool and every link. They are verbs of the operator CLI, the binary `pm-operator`, given directly as `pm-operator <verb>` without an `operator` level; the relay binary `pm-mcp` (`serve`, `enter`) has none of them. 1. *Operator Channels*: Overrides (`waive`, `unwaive`, `abort`, `delete-plan`, `grant-access`, and the integrity resolutions) are the operator's own acts and take one of two channels: (a) a privileged verb of the operator CLI (`pm-operator <verb>`, the `pm-operator web ...` verbs included), or (b) a paired web device (xref:03-web-server.adoc#web-operator-channel[Every Paired Device Is an Operator Channel]), which has operator rights because only an operator verb can pair it. MCP elicitation (an `input_required` result of the call, answered by the host's retry of the call with `inputResponses`; link:../runtime-model/03-relay.adoc#_messages_from_runtime_to_host[Runtime & Interaction Model Specification, Messages from Runtime to Host]) carries no override: it is used only for the operator-configuration choices the server raises itself (for example the integration variants of project setup), and only on a connection that declared elicitation support in its client capabilities (from its `initialize` request or, for a sessionless host, from the request's `params._meta`), which are authoritative (link:../runtime-model/03-relay.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]); without it the state names the `pm-operator config` command. None of these routes through the model; every privileged action is audited with its channel (`cli`, `web` with the `device_id`, or `elicitation` for a configuration choice). An override is never taken as a content answer, and a content answer through elicitation or a paired device is never an override: a content question record is answered in the web app (channel `web`, xref:03-web-server.adoc#web-app[Web App]) or through the entry session's answer link (channel `session`), and a choice of the project setup or a bootstrap also through elicitation (link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]); there is no CLI command that answers one, and an override relayed by the model (for example a "waive" typed into the host chat) is never accepted. No in-run operator decision exists: the operator acts on a running plan only by waivers, access grants, `abort`, `delete-plan`, and the integrity resolutions, each on the operator's own initiative.
2. *CLI Operator Checks*: Before it sends a privileged verb, `pm-operator` verifies that it is attached to an interactive terminal (`System.console() != null && System.console().isTerminal()`) and that none of the coding-agent environment signals of the link:../client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table] (primary and secondary) is present; either failure refuses the verb with a diagnostic before any request is sent. Every verb that changes state then asks for interactive confirmation of the displayed change; a read-only verb (for example `waivers`, `roles list|show`, `audit verify`, or `sweep` without `--apply`) needs only these terminal and environment checks. The host deny rule installed with the bundles denies the whole binary `pm-operator` to the model (`Bash(pm-operator:*)`, no sub-command rule; `pm-mcp` stays allowed; link:../client-profiles.adoc[Client Profiles Specification]) and is defence in depth against a model shell. There is no passphrase, no operator session, and no operator credential or passphrase in the OS keyring (its only operator-lane entry is the enrolment integrity key, <<enrolment-integrity>>): the operator proof of the first iteration is these checks alone.
3. *Accepted Risk*: The checks guard against accidental and naive invocation, not against a model shell that deliberately defeats them (a pseudo-terminal, a cleared environment, indirect invocation). The runtime cannot verify the checks of `pm-operator`, so any process of the same OS user that holds the runtime token can call the operator endpoints directly (for example with `curl --unix-socket`). This is accepted for the first iteration and documented as a residual risk (`PM-SEC-3`); a user proof the model cannot produce (an operator passphrase session, OS user presence) and device roles with step-up are deferred (link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]). Every privileged action stays recorded in the audit log (`PM-SEC-6`).
4. [[operator-integrity-pause]]*Integrity Pause*: The only pause of a plan is the `integrity_breach` condition (a tampered plan, epic, or workspace store, or a tampered enrolment file, which pauses every running plan of the project; link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification, Store Digest Verification]). The state and `call_stack` stay unchanged, the representation offers no link, no task of the scope is offered, every `pm_do` is rejected with `integrity_paused`, and `facts.operator_command` names `pm-operator accept-edit …` and `pm-operator abort …`. A tampered harness enrolment (`harnesses.json`) is no pause: it refuses the worker launch (`harness_tampered`), which counts as a start failure of the role on that harness and ends, once the start-failure guard holds, in the conservative fallback of the role's tasks (<<operator-enrol-harness>>). The pause has no time bound and no fallback, because a tampered store cannot be trusted to write a hand-back; it ends only by `accept-edit` (the engine re-verifies before it clears the condition) or, for a plan or epic scope, `abort`; the workspace scope has no abort, so `accept-edit workspace <store>` is its only resolution. A tampered pending entry record pauses only its bootstrap entity, never the workspace scope's own state or its other entities, and ends by `accept-edit workspace pending/<entry_id>.json` or by the pending-record sweep, which removes the record. Every other condition is bounded by its self-remedy budget and ends in the phase's fallback (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]).
5. [[operator-drop-capture]]*Capture Ref Removal (`pm-operator drop-capture <plan_id>`)*: A `land` plan that ended without `merged` keeps its capture ref `refs/pm-mcp/captures/<plan_id>` in the enrolled repository as the user's recovery point and owes `capture_ref_retained` (link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane, item 5]). The verb shows the ref's snapshot commit and its paths, deletes the ref after confirmation, discharges the owed item `capture_ref_retained` (also for an archived plan), and appends an `audit.jsonl` record. `drop-capture` and `discharge-owed` (which records `discharge_proof` and `discharged_at` of an owed item whose discharger is `operator`, link:../store-schemas/03-findings-and-review-records.adoc#owed-item-record[Store Schemas Specification, Owed Item Record]) are the only writes an archived plan accepts. It is operator-only like every verb of this section; no workflow state, recovery sweep, or MCP tool removes a retained capture ref.
6. [[operator-waive]]*Waivers (`pm-operator waive`, `unwaive`, `waivers`)*: `waive <plan_id> <gate> --reason <text> [--reason-class <class>]` declares a waivable gate met (`review_evidence[:<bot_kind>]`, `ci_check:<name>`, `analysis_gate:<provider>`, `findings:<class>`, `qgate_findings:<phase>`, `spend`, link:../identifiers/02-registry-stores-to-web.adoc#id-waivable-gate[Identifier Registry, Waivable Gate Identifier]; a `met` waiver of `spend` passes the spend check, evaluated once at `merge.gate-entry`); `waive <plan_id> --raise <budget>=<N> --reason <text>` sets the absolute ceiling of `fix_budget:<policy>` or `retry_budget:<policy>` for the plan, above the effective ceiling in force and at most the compiled hard cap. The verb may be given at any time from plan start until the gate's fallback is taken, and the waiver applies to every later evaluation of the gate; it shows the plan, the gate, and the effect before the confirmation. `--reason-class` classifies the reason (`gate_false_positive`, `gate_not_applicable`, `tooling_unavailable`, `deliberate_deferral`, default `unknown`; link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record]); it is mirrored into the audit log with the gate, where the Artifact Gate recurrence count and the lessons-capture signal read it. The runtime appends the record to `waivers.jsonl` (the only writer, link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record]), mirrors it to `audit.jsonl`, and composes a new plan instance version. `unwaive <plan_id> <waiver_id>` revokes an unconsumed waiver; revoking a raise lowers the ceiling at the next budget check, where a counter already above it exhausts the budget and the fallback follows, without a refusal. Refusals: `not_waivable` (a gate outside the closed list, or on the non-waivable list of link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record, Refusals]), `plan_ended` (the gate's fallback was taken or the plan ended), `already_consumed`, `raise_out_of_range`, `position_not_contained`. `waivers <plan_id> [--pending]` lists the waivers with their consumptions and the waiver requests; a pending request filed by a worker's `request_waiver` in a remediation unit is answered by `waive` (naming the gate, optionally `--request <request_id>`) within the request's waiver wait (link:../timeouts/01-job-budgets-and-waits.adoc#waiver-wait[Timeouts & Budgets Specification, Waiver Wait]). Requests are also shown in the plan's view as `facts.waiver_request` (link:../mcp-tools/01-core-workflow-tools.adoc#question-waiver-facts[MCP Tools Specification, Waiver Requests in Representations]), by `pm-operator status` and the web app, and posted as an idempotent pull request comment with the label `pm-mcp:waiver-requested`; these announcements are independent of the question channels and are information only. Every waiver and consumption is listed in the pull request comment and the landing record.
7. [[operator-accept-edit]]*Accept-Edit (`pm-operator accept-edit`)*: `pm-operator accept-edit plan <plan_id> <store> | epic <epic_id> <store> | workspace <store> | lesson <lesson_id> | enrolment <project_id>` shows the file's path and its recorded and current size and SHA-256 before the confirmation; there is no diff, because the prior content is not kept. On confirmation the runtime re-baselines the store's digest (link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification, Store Digest Verification]), the lesson's entry, or the enrolment file's HMAC sidecar (<<enrolment-integrity>>), and appends an `audit.jsonl` record. The resolutions of an `integrity_breach` condition are closed: `accept-edit`, or, for a plan or epic scope, `pm-operator abort` (<<operator-abort>>); a workspace breach ends only by `accept-edit workspace <store>`, and the breach of a pending entry record `pending/<entry_id>.json` also by the pending-record sweep (link:../store-schemas/01-format-and-session-log.adoc#pending-entry-record[Store Schemas Specification, Pending Entry Record]). A workspace `<store>` is named relative to the project store root (`workspace/sessions.jsonl`, `pending/<entry_id>.json`), a plan's or epic's relative to its scope directory (link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal]).
8. [[operator-abort]]*Abort (`pm-operator abort plan <plan_id>|epic <epic_id> --reason <text>`)*: An unsolicited operator verb: the runtime moves a plan into `plan.aborted` in the next transaction, an engine-owned scope-wide transition under the on-entry rule (every begun, unsettled step is recorded `failed`); an epic takes the archive path in the next transaction (its open tasks withdrawn, then `epic.archive`, the ledger commit, and the epic landing) and ends in `epic.aborted` (link:../state-catalogue/06-setup-epic-other.adoc#state-epic.archive[State Catalogue Specification, `epic.archive`]); aborting an epic leaves its running child plans untouched: each runs to its own outcome, and once the epic is terminal its epic linkage resolves to `detached`, which every consumer treats like `not_orchestrated` (no landing emission to an inbox, late findings seeded as lessons, no outbox link; link:../store-schemas/02-workflow-state-store.adoc#epic-linkage[Store Schemas Specification, Origin and Epic Linkage]); pending questions are closed `cancelled`, pending waiver requests `expired`, and the plan's lesson claims released. `plan.aborted` is entered only by this verb (also when it resolves an integrity pause), by `release-project` (the same engine-owned abort, reason `project_released`, <<enrolment-lifecycle-release>>), or by `delete-plan` (the same engine-owned abort, fixed reason `plan_deleted`), whose first transaction is this one and whose second, ordered after it, removes the plan directory; no model ends a plan: a worker's task ends only in its closed task outcomes, and a plan that cannot continue takes its phase's fallback (`returned` or `handed_back`), never `plan.aborted`. The reason is recorded in the landing record and the audit log.

9. [[operator-grant-access]]*Cross-Project Access (`pm-operator grant-access <plan_id> <project_id> read|read-write --reason <text>`)*: A plan works inside its own enrolled project (`PM-SEC-2`); access to another enrolled project, and the read-only provider reads of an organisation, group, or repository outside the project (`--org <owner>` or `--repo <owner>/<name>`, only with `read`; <<cross-repository-reads>>), is granted only by the operator, on the operator's own initiative. The verb shows the plan, the target (a project identified by its remote owner and name, never by a checkout path; an organisation, group, or repository by its name at the plan's provider), and the access level before the confirmation; the runtime appends a grant record to the plan's append-only grant log in the plan store (link:../store-schemas/15-screening-and-grants.adoc#grant-record[Store Schemas Specification, Grant Record]) and mirrors it to `audit.jsonl`. The grant applies from the plan's next transaction and holds until the plan ends; there is no revocation, and `pm-operator abort plan <plan_id>` (<<operator-abort>>) is the only way to stop it. An access to a project without a grant of the needed level raises `precondition_unmet` on the current state with `facts.operator_command` naming this verb; its `retry` re-checks the grants within the condition budget (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]), after which the phase's fallback is taken with the access as the gap. No link requests a grant, and no plan waits for one.
10. [[operator-enrol-harness]]*Harness Enrolment (`pm-operator enrol-harness <client>`)*: Workers run only through an enrolled harness (`PM-EXEC-1`). The verb resolves the absolute path of the profile's `headless.executable`, runs the profile's version probe, and records the path, version, and digest, and nothing else, in the machine's harness enrolment (link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]); it shows the path, version, and digest for confirmation; it refuses a client whose profile has `headless: null` (`invalid_arguments`) and a version outside `headless.supported_versions` (`harness_version_unsupported`). It captures no environment value: `PM-MCP` never stores or exports a harness's authentication. The harness CLI must already be authenticated by its own login, cached under its home; a worker of a harness that is not logged in fails to start, and the start-failure guard reports the harness's own error text to the operator (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]). The verb is also the re-baseline of a tampered harness enrolment: when the HMAC check of `harnesses.json` fails, every worker launch on that harness is refused before spawn (fate `refused`, reason `harness_tampered`, a `security` audit record `enrolment_tampered`) and counts as a start failure of the role on that harness; once the start-failure guard holds, the role's tasks close `lost` with `role_unavailable` and take their conservative fallback, and the operator is told `pm-operator enrol-harness <client>` in `pm-operator status`, the web app, and the audit log (link:../model-work/04-worker-launch.adoc#harness-selection[Model Work Specification, Launch Refusals]). The verb rewrites the file and its sidecar with the named client only after showing path, version, and digest; entries of other clients in the tampered file are not carried over, and each of those clients must be enrolled again. There is no pause and no `accept-edit` form for this file. A later change of the digest or version (the harness updates itself) is accepted while the version stays inside the range: in the accepting transaction the runtime rewrites `harnesses.json` and its HMAC sidecar under `locks/harnesses.lock` and appends the audit record `harness_updated`; outside it every worker launch on that harness is refused `harness_version_unsupported` until the operator enrols it again; a version change also invalidates the qualification records of the roles on that harness (`PM-WORK-6`) (link:../client-profiles/01-profile-schema.adoc#headless-block[Client Profiles Specification, `headless`]).
11. [[operator-roles]]*Roles (`pm-operator roles`)*: Roles are configuration artifacts in the shipped, machine, and project role sets (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]); the verbs read and grade them and never write an artifact; the operator edits the artifacts of the machine or project set. The qualification semantics (validity, corpus topics, grading, conservative fallback) are in link:../model-work/01-roles-and-configuration.adoc#qualification[Model Work Specification, Role Qualification].
* `roles list [--project <project_id>]`: every role of the effective set (of the project, or the machine and shipped sets without `--project`) with its source set, class, form, harness, model, and effort, its qualification state (`qualified`, `qualified_fresh_only`, `unqualified` naming the changed input when a record no longer matches or the measurement below the project's current level, or `invalid` with the validation reason; an invalid artifact counts as undefined), and whether the start-failure guard of the role holds (link:../model-work/03-supervision-and-recycling.adoc#start-failure-guard[Model Work Specification, Start-Failure Guard]). Read-only.
* `roles show <role> [--project <project_id>]`: the effective artifact, the artifacts of lower sets it replaces, its configuration digest and its qualification digest, its validation result, an effort narrowing the harness applies to it, and the summary of its qualification record. Read-only.
* `roles show --decisions [--project <project_id>]`: the decision declarations of the project's adjudication unit and of the binary's default unit (per decision kind `ask` or the quorum with each listed role's harness, model, availability, and qualification, and the validation result) and the calibration record of every quorum declaration: the items graded, the automatic share, the false automatic share against the declared level, and whether the declaration decides (link:../model-work/10-decision-quorum.adoc#quorum-calibration[Model Work Specification, Quorum Calibration]). Read-only.
* `roles qualify --decisions [--project <project_id>] [--kind <decision_kind>] [--yes]`: calibrates every quorum declaration that the project's adjudication unit or the binary's default unit uses and that has no valid record, or the declarations of the named kind, on the corpus items of closed decisions of its kind, with the confirmation and progress of `roles qualify`, and has the runtime write one decision calibration record per declaration digest to the project set (identical declarations share one), bound to the corpus revision; it prints the measurements and the paths.
* `roles qualify <role> [--project <project_id>] [--yes]`: shows the configuration, the corpus topics, the item count per form, and the expected cost and time from earlier records, and runs only after confirmation (`--yes` skips the confirmation, never the terminal check of item 2); it then grades the configuration warm and fresh (link:../model-work/01-roles-and-configuration.adoc#grading[Model Work Specification, Grading]) and has the runtime write the qualification record to the project set, bound to the qualification digest (over the graded members `PM-WORK-6` names, link:../model-work/01-roles-and-configuration.adoc#qualification[Model Work Specification, Role Qualification]) and the corpus revision; its progress is shown like any other jobs (`pm-operator status`, the web app), and it prints the record's measurements, whether they qualify each form at the project's current levels, and the path. While a role is unqualified its tasks take their conservative fallback with the reason `role_unqualified`; no task waits for a qualification. The project setup runs the same grading for every role without a valid record (link:../domain-extensions/04-setup-state-machine.adoc#setup-qualification[Domain Extensions Specification, Role Qualification at Install]).
12. [[operator-decisions-export]]*Decision Export (`pm-operator decisions export`)*: Reads the decision records of the project (`--project`, else every enrolled project; live and archived plans, epics, and the workspace scope) and writes the selected judgment decisions as `draft` corpus items, and with `--calibration` the server-rule decisions as calibration rows, into `--out`, a directory the operator names; the selection, the target, the mapping, and the skip reasons are owned by link:../model-work/11-decision-records.adoc#corpus-export[Model Work Specification, Corpus Export]. It is read-only on every store, needs no confirmation, never overwrites a file, and sends nothing over the network (`PM-ARCH-2`); the runtime appends one audit record with the counts written and skipped. The items carry real code and facts of the project: the operator reviews them before anything enters the corpus.

[#enrolment-integrity]
=== Enrolment Integrity
_See Requirement link:../../Requirements.adoc#PM-SEC-5[PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement]_

* *One File, One HMAC, One Lock per Project*: Every project has its own enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]). Every write of it (the operator verbs `enrol`, `unenrol`, and re-baselining, executed by the runtime on the verb's request) runs under `<PM_MCP_BASE>/locks/enrolments/<project_id>.lock` and also writes the sidecar `<PM_MCP_BASE>/enrolments/<project_id>.json.hmac`, an HMAC-SHA-256 over the canonical file content. `unenrol` removes the file and its sidecar. The key lives in the OS keyring under the <<keyring-service-name,service name>> with the fixed account `enrolment-integrity-key` (operator lane; on Linux the attribute `credential_key=enrolment-integrity-key` without `project`); on hosts without a keyring it lives in `<PM_MCP_BASE>/state/enrolment-hmac.key` (mode `0600`).
* *Harness Enrolment*: The machine-wide `<PM_MCP_BASE>/harnesses.json` has its own sidecar `harnesses.json.hmac` under the same key and its own lock `locks/harnesses.lock`; it is verified before every worker launch, and a mismatch is resolved by `pm-operator enrol-harness`, never by `accept-edit` (<<operator-enrol-harness>>).
* *Verification*: The runtime verifies a project's HMAC in the project's recovery after a runtime start, before the project is first served (link:../runtime-model/02-startup-recovery-drain.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery]), and before every verify-not-resolve check of the project's jobs (`PM-EXEC-2`, link:../job-runtime/01-pipeline-and-subprocesses.adoc#enrolment-integrity[Job Runtime Specification]); the runtime also verifies it before it serves an `enter` request or an operator verb that uses the file. On mismatch it refuses with `enrolment_tampered`, appends an `audit.jsonl` record, and names the operator command; nothing in that file is trusted until the operator re-baselines it interactively (`pm-operator accept-edit enrolment <project_id>`, after reviewing the displayed recorded and current size and SHA-256, <<operator-accept-edit>>). A tampered file blocks only its own project; every other enrolled project keeps being served.
* *Residual Risk*: Landlock keeps jobs from writing `<PM_MCP_BASE>` on Linux (`PM-SEC-5`), but a host shell driven by the model is not a job and is not confined; the HMAC is the control against it. The key never leaves the runtime (`pm-mcpd`), but a model-driven shell that defeats the operator checks of `pm-operator`, or any same-user process that calls the operator endpoint directly with the runtime token, can re-baseline a tampered file (Accepted Risk of <<operator-channel-isolation>>). On hosts without a keyring the key file is readable by every process of the same user, so the HMAC detects edits made without the key but not a deliberate forgery. Both are documented as accepted residual risks (`PM-SEC-5`).

[#enrolment-lifecycle-release]
=== Enrolment, Lifecycle Gate & Release
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-23[PM-WATCH-CLI-23], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-25[PM-WATCH-CLI-25], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-29[PM-WATCH-CLI-29]_
_See Requirement link:../../Requirements.adoc#PM-MIG-1[PM-MIG-1: Six-Stage Build-Out & Per-Project Plan Lifecycle]_

_See Requirement link:../../Requirements.adoc#PM-MIG-5[PM-MIG-5: Quantitative Triggers & Project Release]_

`PM-MCP` and `plan-marshall` keep separate state trees (`PM-MIG-2`, link:../filesystem-layout/03-project-store.adoc#coexistence-lifecycle[Filesystem Layout Specification]). There is no crossing: `PM-MCP` imports nothing from `plan-marshall` (no configuration, lessons, `project-architecture/`, credentials, or learned build timeouts) and never reads or writes `.plan/` or `~/.plan-marshall/`. A project is taken into use as follows; each operator verb is interactive and writes an `audit.jsonl` record:

* `pm-operator enrol [--pilot] [--container-engine docker]`: writes the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` with its HMAC sidecar (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]): the project root (refused with `enrolment_root_conflict` when another enrolment file already names it, and with `project_store_root_mismatch` when the machine store of this `project_id` records a different `project_root`), wrappers with their `pinned_files` and interpreter, host tools, the canonical and discovery command templates it overrides, provider `verify_argv` overrides, project scripts with binding, argument schema (validated as a schema), and maximum timeout, command budgets, write paths, the captured build environment, language servers, `container_engine` (`docker` only with `--container-engine docker`, after the verb has told the operator that the project's jobs then hold the authority of the Docker group, which reaches every host path including `<PM_MCP_BASE>`, and the operator has confirmed it; audited as `container_engine_enabled`; link:../job-runtime/02-confinement-and-environment.adoc#container-engine[Job Runtime Specification, Container Engine]), and `pilot` (`true` with `--pilot`, audited like every enrolment write); each field is shown to the operator for confirmation. On first enrolment it creates the project's machine store `<PM_MCP_BASE>/projects/<project_id>/` (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]) with its workspace scope.
* The project setup workflow in the workspace scope (link:../domain-extensions/04-setup-state-machine.adoc#_architecture_enrichment_judgment_links_project_setup_state_machine[Domain Extensions Specification, Project Setup State Machine]) creates, on its first run, `.marshall/` with its `.gitignore` partition (link:../filesystem-layout/01-repository-workspace.adoc#repository-layout[Filesystem Layout Specification]) and `.marshall/config/` with copies of the binary's default workflow units (the JSON team files are sparse and start absent); no `plan-marshall` input exists.
* *Lifecycle gate*: The gate is a compiled constant of the release: closed in every release before the Stage 4 exit criteria are met (`PM-MIG-4`), open from the release that meets them. While it is closed, plans and epics are created only in a project enrolled as a pilot (`pm-operator enrol --pilot`, the field `pilot: true` of the enrolment file); in every other project `start.create-scope` refuses with `lifecycle_closed` (link:../mcp-tools/01-core-workflow-tools.adoc[MCP Tools Specification]), and the orthogonal services and the workspace scope stay available. The clones of a parallel run are enrolled as pilots. `pilot` is set and cleared only by running `pm-operator enrol` again, with or without `--pilot`; clearing it affects only later `start.create-scope` calls, and the project's live plans and epics continue. With the gate open, `pilot` has no effect: the plan lifecycle (the `plan` and `epic` scopes) is offered in every enrolled project until the project is released.
* `pm-operator unenrol`: refuses with `scope_active` while the project has non-terminal plans or epics or running jobs, naming them. It removes only the enrolment file and its HMAC sidecar and leaves the project's machine store `<PM_MCP_BASE>/projects/<project_id>/` untouched; retention (`pm-operator sweep`, with the machine-wide retention defaults) purges only aged items and never the store as a whole (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification, Evidence-Based Removal Sweeps]). The store records its `project_root` (link:../store-schemas/11-enrolment-store.adoc#project-store-identity[Store Schemas Specification, Project Store Identity]); enrolling the same `project_id` again reuses the store only for the same root and is refused otherwise (`project_store_root_mismatch`, an operator-verb refusal naming both roots, not an MCP tool error).
* `pm-operator release-project`: the operator's switch-off for the `PM-MIG-5` triggers. The runtime writes `released_at` (the release instant) into the project's enrolment file (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]) and aborts every non-terminal plan and epic of the project through the engine-owned abort (<<operator-abort>>) with the reason `project_released`; branches and stores stay as the abort leaves them, readable in the project's machine store, and nothing is converted. While `released_at` is set, the plan lifecycle is not offered: `start.create-scope` refuses with `lifecycle_closed` and `pm-mcp enter` refuses the `plan` and `epic` kinds (xref:01-cli-and-installer.adoc#_entry_identity_recording_pm_mcp_enter[Entry Identity Recording], step 1); the workspace scope and the orthogonal services stay available. `pm-operator enrol` on a released project clears `released_at`, and the lifecycle is offered again under the lifecycle gate. Both writes append an `operator` audit record. The project can continue on `plan-marshall`, whose `.plan/` `PM-MCP` never touched.

== Security Audit Trail & Three-Tier Identity Verification
_See Requirement link:../../Requirements.adoc#PM-SEC-6[PM-SEC-6: Security Audit Trail & Tamper-Evident Logging]_

_See Requirement link:../../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Entry Identity Audit]_

_See Requirement link:../../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

Every MCP tool call, state transition, job execution, credential lookup, and operator command appends a structured JSONL record to `<PM_MCP_BASE>/logs/audit.jsonl` (mode `0600`, appended under the audit lock on the log file itself, the leaf of the lock order, schema defined in link:../store-schemas.adoc[Store Schemas Specification]):

* *Identity at Entry, Binding Afterwards*: The audit record of every `pm-mcp enter` captures in its `details` the three identity tiers: (1) `declared_client` (`--client`), (2) `detected_env` (the environment signature `pm-mcp enter` computed, `unknown` when unrecognized), and (3) `os_principal` (`System.getProperty("user.name")` / `geteuid()`); the record is the enter record (`category: identity`, `event: entered`), which also carries `details.environment_match_tier`; a disagreement between Tier 1 and Tier 2 sets `details.identity_mismatch: true` and is reported to the operator in `pm-operator status` and the web app, never in a model-facing representation (xref:01-cli-and-installer.adoc#_entry_identity_recording_pm_mcp_enter[Entry Identity Recording], `PM-CLIENT-3`). No later call is checked against the environment: a record of a session's call carries the client its relay declares and the session's generation, a record of a worker's operation carries its `job_id`, role, and generation, and a machine-level record (runtime start, an operator verb, a sweep) carries only `os_principal` (link:../store-schemas/12-machine-stores.adoc#audit-log[Store Schemas Specification, Audit Log]).
* *Hash Chain*: Every record carries `prev_hash`, the lowercase hex SHA-256 of the previous record's canonical line (its exact UTF-8 bytes in the file, without the trailing newline). The first record of a new log carries the genesis value (64 `0` characters). Records are appended only by writers that hold the log's lock and read the current last line first.
* *Anchored Head (`logs/audit.head`)*: After every append the writer updates, under the same lock, the sidecar `logs/audit.head` with the current file name, record count, last `event_id`, and head hash (the hash of the last canonical line), protected by an HMAC-SHA-256 under the integrity key of the enrolment store (<<enrolment-integrity>>). The chain alone proves only that the records present are consistent; the anchored head makes a deleted log, a reset to the genesis value, a truncated tail, and a consistently rewritten chain detectable.
* *Rotation & Checkpoints*: When `audit.jsonl` exceeds `audit_rotation.max_bytes` or `audit_rotation.max_days` (`machine-config.json`, link:../timeouts/03-retention-host-config.adoc#audit-rotation-age[Timeouts & Budgets Specification]), the writer appends a `checkpoint` record (record count, head hash, HMAC under the same key), renames the file to `audit-<first_event_id>.jsonl`, and starts the new `audit.jsonl` with a record whose `prev_hash` is the hash of that checkpoint line. Every rotated file is listed in the append-only index `logs/audit-index.jsonl` (file name, first and last `event_id`, record count, checkpoint hash), itself hash-chained and anchored in `audit.head`. The machine sweep `pm-operator sweep --machine` (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas, Evidence-Based Removal Sweeps]) removes rotated files older than `audit_rotation.retain_days` (`machine-config.json`, link:../timeouts/03-retention-host-config.adoc#rotated-audit-files[Timeouts & Budgets Specification, Rotated Audit Files]) as whole files and never their index entries, one audit record each, so a purged file stays accounted for.
* *Chain Verification at Runtime Start*: The runtime verifies incrementally: the HMAC of `audit.head`, the index, and the records of the current file after its last checkpoint. A missing log, a reset to genesis, a record count below the anchored count, or a head mismatch is reported as `audit_chain_broken` with `reason` `missing`, `reset`, `truncated`, or `head_mismatch`; a broken link inside the verified range uses `reason: link_broken` and names the first broken line. The full chain across all rotated files is verified on demand by `pm-operator audit verify`. The same reporting rules apply to every result: on `stderr`, in `pm-operator status`, and as an `audit_chain_broken` security record; the log is never rewritten or silently repaired, and the next record chains to the last line as found.
* *Residual Risk*: The anchoring is tamper-evident, not tamper-proof: a process that holds the integrity key (on macOS, anything that runs the `pm-mcpd` binary, <<enrolment-integrity>>; on hosts without a keyring, any process of the user) can forge a consistent head. This is accepted and documented with the enrolment integrity risk (`PM-SEC-6`).
* *Error Sanitization*: Unhandled exceptions or protocol errors return only a closed-enum error code to the MCP caller, plus the `audit_id` (a UUIDv7, link:../identifiers/02-registry-stores-to-web.adoc#id-audit-id[Identifier Registry]) only where the operator must look the error up (`internal_fault`, `file_unreadable`; link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]); stack traces and host filesystem paths are written exclusively to `<PM_MCP_BASE>/logs/daemon.log`.

== Outbound HTTPS Security (`cui-http`) & Native Runtime Stack
_See Requirement link:../../Requirements.adoc#PM-TECH-1[PM-TECH-1: Java 25+ & Quarkus MCP Runtime Foundation]_

_See Requirement link:../../Requirements.adoc#PM-TECH-2[PM-TECH-2: Outbound HTTPS Client, LSP Client & McpAssured Testing Libraries]_

_See Requirement link:../../Requirements.adoc#PM-TECH-3[PM-TECH-3: GraalVM Native Executable & Startup/Memory Bounds]_

_See Requirement link:../../Requirements.adoc#PM-TECH-4[PM-TECH-4: Operating System Platform Integration (macOS & Linux)]_

_See Requirement link:../../Requirements.adoc#PM-SVC-3[PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging]_

_See Requirement link:../../Requirements.adoc#PM-TEST-5[PM-TEST-5: Security Boundary & Confinement Adversarial Testing]_

* *Outbound HTTPS Hardening (`de.cuioss:cui-http`)*: All outbound REST and GraphQL calls (SonarQube/SonarCloud, the native GitHub and GitLab clients) and remote upstream MCP calls use `de.cuioss:cui-http`'s `HttpHandler` and `ResilientHttpAdapter` with TLS 1.2+, mandatory certificate/hostname verification, HTTPS-only redirect following, and origin-pinned bearer token transmission (stripping `Authorization` headers on any cross-origin redirect). All URL/path/header parameters composed into outbound requests are validated through `de.cuioss.http.security` pipelines. The native git transport (JGit) uses a connection factory with the same TLS rules that connects only to the credential entry's origin (<<native-confinement>>). Both honour the operator's `proxy` setting of `machine-config.json` and no other proxy source (<<native-confinement>>, Configuration allowlist). An upstream MCP server is always a remote HTTPS server reached this way; no upstream server runs as a `stdio` subprocess (`PM-TECH-2`).
* *GraalVM Native Image & Resource Bounds*: The runtime `pm-mcpd` is compiled as a standalone Quarkus native executable (`Java 25+`, `quarkus-mcp-server-http`, Virtual Threads); the two CLI binaries `pm-mcp` (the relay) and `pm-operator` and the launcher `pm-exec` are plain native images without Quarkus (xref:01-cli-and-installer.adoc#cli-implementation[CLI Implementation]). Startup and memory bounds for the runtime, the relay, and the operator CLI are defined in `PM-TECH-3` and verified as described in the link:../runtime-model/04-sessions-and-workers.adoc#_verification[Runtime & Interaction Model Specification, Verification].
* *STDIO & Confinement Adversarial Verification (`PM-TEST-5`)*: Integration tests (`*IT`) using `McpAssured` (`McpStdioTestClient`) verify the transport isolation properties listed in the link:../runtime-model/04-sessions-and-workers.adoc#_verification[Runtime & Interaction Model Specification, Verification], that insecure permissions (`0755`) on `<PM_MCP_BASE>/enrolments/` trigger fail-closed termination at runtime start (exit code `77`), that insecure permissions (`0644`) on one project's enrolment file block only that project (`enrolment_insecure`), that a project's enrolment file edited outside the operator verbs is refused with `enrolment_tampered` for that project while a second enrolled project is still served, that a job writing `<PM_MCP_BASE>/enrolments/<project_id>.json` or into another enrolled project's root fails under the Linux Landlock write set while a write into its own project root succeeds, that a job cannot read `<PM_MCP_BASE>/run/runtime.token` or a credential file under `<PM_MCP_BASE>/credentials/` under the Linux Landlock read set while a read outside `<PM_MCP_BASE>` succeeds (positive control), that a request without the runtime token is refused on `/mcp` and `/api/v1`, that an operator verb run without a terminal or with an agent environment marker is refused before any request is sent, while an insecure fallback credential file blocks only the step that needs it (`credentials_file_insecure`), that path-traversal or command-injection payloads are deterministically rejected and logged to `audit.jsonl`, and that hostile repository configuration against the native git variant is contained: a `url.<base>.insteadOf` or `pushInsteadOf` rewrite and a `remote.<name>.pushurl` to a foreign hook in a native-selected repository start no process and yield `capability_missing`; CLI-variant `git` and `ci` jobs are shown to carry no token variable or askpass helper in their environment.
