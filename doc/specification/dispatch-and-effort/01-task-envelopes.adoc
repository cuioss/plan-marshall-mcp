== Task Envelope Bin-Packing & Sequential Task Yield
_See Requirements link:../../Requirements.adoc#PM-WF-5[PM-WF-5: Server-Launched Model Jobs & Single-Level Leaf Constraint], link:../../Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Job Accounting & Effort Role Resolution]_

During Phase 4 (`plan`), the workflow engine does not launch a model job per individual task. Instead, it sizes each planned task, packs compatible tasks into budget-bounded execution envelopes (`envelope-1`, `envelope-2`, ...), and Phase 5 launches one leaf model job per envelope (xref:05-model-job-launch.adoc#model-job-launch[Model Job Launch]).

[#cost-sizing]
=== Cost Sizing (`derive-cost-size`), Envelope Budget & Minimum Job Work

The cost model (size rubric, size-to-token table, and Next-Fit packing under the budget) is `plan-marshall`'s (`manage-tasks/scripts/_tasks_cost.py`, `manage-tasks/scripts/_tasks_envelope.py`, the defaults in `manage-config/scripts/_config_defaults.py`, and `extension-api/standards/dispatch-granularity.md` § 1.2), verified at commit `88fcfc9ef`; re-verify against the latest `plan-marshall` version before implementing. `plan-marshall`'s packer packs on the budget alone; envelope sharing by module and effort role (item 5) and the below-minimum merge (item 6) are deliberate changes. It predicts the token consumption of a task's work (generation, reasoning, and in-context skill loads), not wall-clock time; the build count is deliberately not a signal, because a build is token-cheap whatever its duration. The dominant cost of a model job is the per-task work, not the envelope's re-establishment overhead, so bundling tasks amortises only that minor share.

1. *Size Rubric*: For every planned task $t$, `TaskCostEstimator` (the `derive-cost-size` function) computes a deterministic weighted score from four signals of the task record (link:../store-schemas/06-task-references-manifest.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]):
+
$$\text{score}(t) = 10 \cdot N_{\text{steps}}(t) + W_{\text{profile}}(t) + 3 \cdot N_{\text{skills}}(t) + 4 \cdot N_{\text{files}}(t)$$
+
where $N_{\text{steps}}(t)$ is the number of the task's `steps` (the dominant term), $N_{\text{skills}}(t)$ the number of its `skills[]`, $N_{\text{files}}(t)$ the number of its distinct `target_files`, and $W_{\text{profile}}(t)$ the weight of its `profile`: `implementation` `12`, `module_testing` `12`, `verification` `4`, and the default weight `8` for every other member of the task profile enum (`integration_testing`, `documentation`), as `plan-marshall` weights a profile it does not list. There is no per-profile base cost.
2. *Six Sizes*: The score maps to `cost_size` through monotone bands, so raising any signal never lowers the size:
+
[cols="1,2,2"]
|===
|`cost_size` |Score band |Default `predicted_cost_tokens`

|`XS` |$\text{score} < 30$ |`5K`
|`S` |$30 \le \text{score} < 60$ |`25K`
|`M` |$60 \le \text{score} < 150$ |`60K`
|`L` |$150 \le \text{score} < 300$ |`130K`
|`XL` |$300 \le \text{score} < 700$ |`260K`
|`XXL` |$\text{score} \ge 700$ |`520K`
|===
3. *Size-to-Token Table*: `predicted_cost_tokens(t)` is defined as the value of the task's `cost_size` in the size-to-token table; it is a table lookup, never a per-task computation. The table is derived, never configured: its compiled defaults are the column above, and a hand-set table could only be less accurate than the calibration (*deliberate change vs. `plan-marshall`*: its `plan.phase-5-execute.cost_size_token_table` does not exist). The table's values are labelled `uncalibrated` until the server recalibrates them from a measured `metrics.json` population (link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]: per envelope the summed `predicted_cost_tokens` beside the measured token components); a recalibrated table carries `basis: calibrated` with its population count and is kept as the derived fact `cost_calibration` of the project's `derived-facts.json` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-fact-kinds-discovery-calibration[Store Schemas Specification, Derived fact kinds]), and every figure derived from a table (`predicted_cost_tokens`, the Phase 4 budget projection) carries the basis of the table it used.
4. *Envelope Budget*: Envelopes are packed Next-Fit under a per-envelope budget derived from the context budget of the plan's client profile (`headless.context_budget_tokens`, link:../client-profiles.adoc[Client Profiles Specification]; compiled fallback `400K`, `plan-marshall`'s `per_envelope_budget_tokens` default), because it depends on the model's context window, a property of the operator's host and ladder; the operator may override it per project (`envelope_budget_tokens` in `local-config.json`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]); a team file never sets it. The budget is a plan-time packing bound over summed `predicted_cost_tokens`, never a runtime comparand: a model job cannot measure its own context use mid-turn, and a job that runs short of context leaves through `yield:envelope-M` (link:../phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution]). A task whose predicted cost alone exceeds the budget (an `XXL` task under the defaults) is placed alone in its envelope.
5. *Envelope Sharing*: Tasks share an envelope only when they target the same module and resolve under the same effort role; the execution profile is not a sharing criterion, so a deliverable's `implementation` and `module_testing` tasks share one envelope. *Deliberate change vs. `plan-marshall`*: its packer (`_tasks_envelope.py`) closes an envelope only on the budget and has no module or role compatibility, so one envelope could mix modules and effort roles under a single level.
6. *Minimum Job Work (10K)*: `10K` tokens is the minimum judgement work that justifies a model job of its own (`plan-marshall`'s `dispatch-granularity.md` § 1.2), not an envelope ceiling. An envelope whose summed `predicted_cost_tokens` stays below `10K` (for example a lone `XS` task) is merged by the server into its adjacent envelope of the same module and effort role, the preceding one first; without such a neighbour it stays alone, and the plan representation lists it in the fact `below_minimum_job`. Every such merge produces an envelope over the budget: Next-Fit closes an envelope only on an incompatible task or on the budget, so two adjacent compatible envelopes were split by the budget alone, and a merge only enlarges envelopes. The minimum job work therefore takes precedence over the budget by design. *Deliberate change vs. `plan-marshall`*: its packer has no below-minimum merge; an envelope below `10K` is dispatched alone.

The rubric prices a byte when it enters a context and ignores how long it stays resident. Isolating work in a separate envelope is justified only when re-creating the envelope's starting context (created bytes bill 1.25) costs less than the residency it removes (read bytes bill 0.1 per remaining turn); this condition is evaluated per split, never assumed. The server supplies both inputs: `record-metrics` publishes per envelope the `predicted_cost_tokens` beside the measured token components, and per envelope split (`yield:envelope-M`) the re-creation and residency terms, or `not_derivable` when a component is unmeasured.

=== Deterministic Envelope Packing Algorithm (`EnvelopePacker`)
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-1[PM-WATCH-DISP-1]_

Given the ordered sequence of tasks $T = [t_1, t_2, \dots, t_n]$ produced during Phase 4 (`plan`), each stamped with its `predicted_cost_tokens` (<<cost-sizing>>), `EnvelopePacker` runs automatically in-process upon `plan.describe-tasks` submission to partition $T$ into an ordered list of envelopes, each a contiguous slice of $T$, so topological dependency order is preserved. The packer never re-derives a task's cost; it only sums the stamped values:

[source,java]
----
package de.cuioss.pm.mcp.workflow.envelope;

import java.util.ArrayList;
import java.util.List;
import java.util.Set;

public final class EnvelopePacker {

    /** Minimum predicted work that justifies a model job of its own (dispatch-granularity § 1.2). */
    public static final long MIN_JOB_TOKENS = 10_000;

    public enum CostSize { XS, S, M, L, XL, XXL }

    public record PlannedTaskSummary(
            String taskId,
            String moduleId,
            String role,
            Set<String> skillUris,
            CostSize costSize,
            long predictedCostTokens,
            List<String> dependsOnTaskIds
    ) {}

    public record PackedEnvelope(
            String envelopeId,
            String moduleId,
            String role,
            List<String> taskIds,
            List<String> unionSkillUris,
            long totalPredictedCostTokens
    ) {}

    /**
     * @param orderedTasks         topological order over depends_on, ties broken by task_id
     * @param envelopeBudgetTokens the configured per-envelope budget (default 400K)
     */
    public List<PackedEnvelope> packEnvelopes(List<PlannedTaskSummary> orderedTasks, long envelopeBudgetTokens) {
        List<List<PlannedTaskSummary>> groups = new ArrayList<>();
        List<PlannedTaskSummary> current = new ArrayList<>();
        long currentTotal = 0;

        // Next-Fit in task order: close the open envelope when the next task is
        // incompatible or would push it past the budget; a task over budget sits alone.
        for (PlannedTaskSummary task : orderedTasks) {
            boolean fits = !current.isEmpty()
                    && canShareEnvelope(current.getFirst(), task)
                    && currentTotal + task.predictedCostTokens() <= envelopeBudgetTokens;
            if (!fits && !current.isEmpty()) {
                groups.add(current);
                current = new ArrayList<>();
                currentTotal = 0;
            }
            current.add(task);
            currentTotal += task.predictedCostTokens();
        }
        if (!current.isEmpty()) {
            groups.add(current);
        }

        mergeBelowMinimum(groups);

        List<PackedEnvelope> envelopes = new ArrayList<>();
        for (List<PlannedTaskSummary> group : groups) {
            envelopes.add(sealEnvelope(envelopes.size() + 1, group));
        }
        return List.copyOf(envelopes);
    }

    private boolean canShareEnvelope(PlannedTaskSummary first, PlannedTaskSummary candidate) {
        // Same module and same effort role; the execution profile is not a criterion
        return first.moduleId().equals(candidate.moduleId())
                && first.role().equals(candidate.role());
    }

    private void mergeBelowMinimum(List<List<PlannedTaskSummary>> groups) {
        // An envelope below the minimum job work joins its adjacent compatible
        // envelope (preceding first); adjacent compatible envelopes were split only by
        // the budget, so every merge yields an over-budget envelope. Contiguity is kept.
        for (int i = 0; i < groups.size(); i++) {
            List<PlannedTaskSummary> small = groups.get(i);
            if (total(small) >= MIN_JOB_TOKENS) {
                continue;
            }
            int target = -1;
            if (i > 0 && canShareEnvelope(groups.get(i - 1).getFirst(), small.getFirst())) {
                target = i - 1;
            } else if (i + 1 < groups.size() && canShareEnvelope(groups.get(i + 1).getFirst(), small.getFirst())) {
                target = i + 1;
            }
            if (target < 0) {
                continue; // stays alone; reported in the fact below_minimum_job
            }
            if (target < i) {
                groups.get(target).addAll(small);
            } else {
                groups.get(target).addAll(0, small);
            }
            groups.remove(i);
            i--;
        }
    }

    private static long total(List<PlannedTaskSummary> group) {
        return group.stream().mapToLong(PlannedTaskSummary::predictedCostTokens).sum();
    }

    private PackedEnvelope sealEnvelope(int index, List<PlannedTaskSummary> group) {
        PlannedTaskSummary head = group.getFirst();
        List<String> taskIds = group.stream().map(PlannedTaskSummary::taskId).toList();
        List<String> skills = group.stream()
                .flatMap(t -> t.skillUris().stream())
                .distinct()
                .sorted()
                .toList();
        return new PackedEnvelope("envelope-" + index, head.moduleId(), head.role(), taskIds, skills, total(group));
    }
}
----

*Dependency Order*: The ordered input $T$ is the topological order of the task graph persisted in each task's `depends_on` (link:../store-schemas/06-task-references-manifest.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]; Kahn's algorithm, ties broken by `task_id`), and `PlannedTaskSummary.dependsOnTaskIds` is that field, so no envelope places a task before one of its dependencies. The same field governs execution: a task is yielded only when every task in its `depends_on` is `completed`, and an envelope is offered only when its first task is yieldable (link:../phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution]); a task whose dependency ended `infeasible` or `removed` is never yielded.

=== Sequential Task Yield Within an Envelope
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-1[PM-WATCH-DISP-1]_

When Phase 5 launches the model job of an envelope (`entity = "envelope-N"`, xref:05-model-job-launch.adoc#model-job-launch[Model Job Launch]), the job interacts with the daemon only on its entity, bound by its job token (xref:05-model-job-launch.adoc#job-token[Job-Bound Capability & Connection Binding]). Its prompt file carries the envelope's skills and contract but never the task bodies; the server yields the tasks one at a time as hypermedia state representations:

----

The diagram abbreviates identifiers: `l-01` stands for a full `job_id` such as `l-3f9a2c417e0d8b65` and `TASK-1` for `TASK-001` (link:../identifiers/01-general-rules-and-registry.adoc#id-job-id[`job_id`], link:../identifiers/01-general-rules-and-registry.adoc#id-task-id[`task_id`]).

1. *Initial Yield (`start`)*: The job's first call is `pm_state(plan_id="<plan_id>", entity="envelope-N")`, named in its contract envelope. The server records `connected_at` on the first accepted request and returns the state representation for the first uncompleted task $t_1$ (`state: "envelope.task.active"`, `facts.task_id: "TASK-001"`). The representation offers the job's four exits from a task: `submit:TASK-001` (complete the task), `ask:TASK-001` (a task question, xref:03-escalation-roles-readers.adoc#task-questions[Task Questions]), `yield:envelope-N` (give back the envelope's remaining tasks, for example when the context runs short), and `infeasible:TASK-001` (the task is impossible as specified, with evidence); link:../phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution] defines what the server does on each. A change to files beyond the task's declared footprint inside the plan's worktree needs no link and no question: the server records it as an unplanned change with its provenance and lists it in the pull-request body and the landing record; only a boundary breach (outside the worktree, the main checkout, a protected path) is refused by the non-waivable guards.
2. *Sequential Advancement on `submit`*: When the job completes task $t_i$ and invokes `pm_do(plan_id="<plan_id>", entity="envelope-N", link="submit:TASK-i", args={...})`, the engine atomically persists task $t_i$'s result in the plan store and advances the envelope cursor to $t_{i+1}$. If $i < k$ and $t_i$ is not a chain tail, the `pm_do` call immediately returns the representation for task $t_{i+1}$.
3. *Terminal Envelope Completion*: When the final task $t_k$ in `envelope-N` is submitted, `pm_do` transitions the entity to the terminal state `envelope.completed` with an empty `links` table (`links[0]{rel,link,form,free}:`). The job then ends with its `job-result` (xref:02-dispatch-observability-and-spend.adoc#job-result-schema[Job Result & Usage Parsing]), and the plan's return evaluation runs on the persisted records (xref:02-dispatch-observability-and-spend.adoc#return-evaluation[Return Evaluation]).
4. [[envelope-early-end]]*Early End of the Entity*: Three exits end the entity before $t_k$, each moving it to `envelope.completed` with its required submission recorded and handing the remaining tasks to the next envelope `envelope-(N+1)`. The server records the `yield_reason` from the exit taken, from the closed enumeration `chain_tail | question | context`; the `yield` link has no free parameter. The exits are the `submit` of a chain-tail task (the last task of a deliverable, `yield_reason: chain_tail`), after which the plan commits the deliverable and runs its module build before the next envelope job; `ask:TASK-i` (`yield_reason: question`), after which the remaining tasks, the asking task included, form `envelope-(N+1)`, launched once the question record is closed and carrying the answer in its `facts`; and `yield:envelope-N` (`yield_reason: context`). No entity state waits on a question, so a waiting job never holds a model slot.
5. *Serial Envelopes*: At most one envelope job of a plan is `queued` or `running` at a time, by the one-writer rule of the model slots (xref:05-model-job-launch.adoc#model-slots[Model Slots & One Writer per Plan]), because the envelopes share one worktree, one chain-tail commit, and one module build. The plan state moves only when the envelope job settles, evaluated by `execute.evaluate-envelope-return` (xref:02-dispatch-observability-and-spend.adoc#return-evaluation[Return Evaluation]).
