[#model-job-launch]
== Model Job Launch
_See Requirements link:../../Requirements.adoc#PM-WF-5[PM-WF-5: Server-Launched Model Jobs & Single-Level Leaf Constraint], link:../../Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Job Accounting & Effort Role Resolution], link:../../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

Every sub-agent of `PM-MCP` is a *model job*: a job of kind `llm` that the server launches itself through the headless command-line interface of a harness (`claude -p`, `codex exec`, `opencode run`), like a build. The workflow state that needs model work is a job state `job llm <entity_kind> role <role_key>` (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Model Job States]); entering it composes the launch, starts the harness through `pm-mcp-exec` in the project's directory, and the headless run connects back to the daemon for exactly its entity. The host model never starts a sub-agent and never reports one: it follows the implicit `wait:<job_id>` of the job state, and the job's end is the awaited event. There is no dispatch link, no return link, and no installed agent file.

[source,text]
----
host model (main session)             pm-mcpd (daemon)                          harness CLI job
 pm_do(link) -------------------> job state entered (role, entity)
                                   compose the launch contract:
                                     harness      <- detected client | model_jobs.harness
                                     template     <- client profile `headless` block
                                     model/effort <- role -> level -> ladder | model_jobs.roles
                                     cwd          <- plan worktree | project checkout | private (screener)
                                     prompt file  <- core conduct + skills + contract envelope
                                     mcp config   <- `pm-mcp serve --job` + job token (not for the screener)
                                     schema       <- named result schema
                                   model slot lease (machine cap, one writer per plan)
                                   pm-mcp-exec (process group, confinement, environment) --> claude -p … / codex exec …
 <-- facts + wait:<job_id> -------                                                            |
 pm_do(wait:<job_id>)                                                                         | pm_state / pm_do(entity) /
                                   job-bound connection <-------------------------------------+ pm_build / pm_lsp / pm_skill
                                   output parsed: result, usage, cost                         |
                                   fate: succeeded | failed | timed_out | killed <------------+ exit
                                   return-evaluation primitive on persisted records
 <-- outcome transition ---------- next state
----

A model job is a leaf (`PM-WF-5`): its connection never follows a link into a `job llm` state, so a model job never starts another model job, and the harness tool that starts sub-agents is never in its tool set (<<job-tool-sets>>).

[#launch-contract]
=== Launch Contract

The server composes the launch of every model job from server-owned inputs only; no element is read from a file the model can write. The composed contract is recorded in the job record (`harness`, `role`, `model`, `effort`, `entity`, `prompt_digest`, and the `argv_digest` of the composed argument vector, link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]):

[cols="1,4"]
|===
|Element |Source

|Harness
|The detected client of the scope (<<harness-selection>>), or the operator's `model_jobs.harness`.

|Command template
|The `headless` block of that harness's client profile: an argument-vector template with typed slots and declared capabilities (link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification, Profile Schema]); composed as an inline named agent or by per-call flags (<<agent-composition>>).

|Working directory
|The plan worktree when it exists, else the enrolled project checkout; for the screener an empty job-private directory (<<job-working-directory>>).

|Model and effort
|Role -> level -> the harness's ladder entry -> CLI flags; an operator model per role replaces the ladder's model (xref:03-escalation-roles-readers.adoc#effort-resolution[Effort Resolution to Harness Flags]).

|Prompt
|The server-composed prompt file: core conduct skill, persona, role and state skills, and the contract envelope (<<job-prompt>>).

|MCP connection back
|A per-call MCP configuration that starts only the job relay `pm-mcp serve --job --socket <path>` with the job token in the relay's environment (<<job-token>>); none for the screener.

|Output
|The structured result against the named result schema where the harness supports schema output, otherwise parsed from the final message against the same schema, fail-closed; usage and cost parsed from the harness output (xref:02-dispatch-observability-and-spend.adoc#job-result-schema[Job Result & Usage Parsing]).
|===

The composed argument vector passes the argument schema validation of every job (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Verify-Not-Resolve Execution Pipeline]); free text (the prompt, the agent definition, the result schema) never enters the argument vector beyond the file paths and the inline-agent JSON the template declares.

[#harness-selection]
=== Harness Selection & Support Rule
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-33[PM-WATCH-DISP-33]_

*Harness*: The harness of a model job is the detected client (`client`, `client_detected`) of the scope's last session row (link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]); for an entity of the bootstrap units hosted by the workspace scope it is the entering session of the pending entry record. The operator may name another installed profile with a headless template in `local-config.json` `model_jobs.harness` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]); that setting holds for every model job of the project. A job connection never changes the scope's client (<<job-token>>).

*Job classes*: Every role belongs to one job class (xref:03-escalation-roles-readers.adoc#_role_registry_lookup_hierarchy[Role Registry & Lookup Hierarchy]), and a class needs a fixed set of the capabilities a `headless` block declares:

[cols="1,3,3"]
|===
|Class |Tools |Required capabilities

|`writer`
|The harness's file-reading, file-writing and shell tools, plus the `PM-MCP` tools of <<job-tool-sets>>.
|`per_call_mcp`, `tool_allowlist`

|`read_only`
|The harness's file-reading and search tools, plus the `PM-MCP` tools.
|`per_call_mcp`, `tool_allowlist` (with a read-only tool set)

|`zero_tool`
|None, and no MCP connection (the screener, xref:06-untrusted-text-screening.adoc#screener[Screener Job]).
|`zero_tools`
|===

*Support rule*: A role runs on a harness only when the harness declares every capability the role's class needs. Otherwise the job state raises `precondition_unmet` (link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-precondition_unmet[State Catalogue, Conditions]) with `facts.missing: [<capability>]` and the operator command that sets `model_jobs.harness`; the condition's budget and fallback apply. There is no inline fallback in the main session: it would bypass the contract, the tool restriction, and the accounting of a model job.

*Harnesses in v1* (capabilities verified per harness in the Milestone 1 host spikes):

[cols="1,3,3,3"]
|===
|Harness |`writer` and `read_only` |`zero_tool` (screener) |Notes

|`claude`
|Inline agent (`--agents '<json>'`, `--agent pm-job`), `--mcp-config` with `--strict-mcp-config`, `--json-schema`, `--no-session-persistence`, `--output-format stream-json`; `read_only` with the tools `Read`, `Grep`, `Glob` plus the `PM-MCP` tools
|`--tools ""`, `--strict-mcp-config`, `--setting-sources ""`, `--max-turns 1`, `--system-prompt-file`, `--json-schema`
|Full support.

|`codex`
|Per-call flags: `-c developer_instructions`, `-c mcp_servers.pm.*` with `required=true`, `--output-schema`, `--ephemeral`, `--cd`; `read_only` with sandbox `read-only`
|Only when the Milestone 1 spike shows that no tool remains (`features.shell_tool=false`, web search off, no MCP, isolated working directory)
|No hard zero-tool switch.

|`opencode`
|Inline agent in `OPENCODE_CONFIG_CONTENT` with a local MCP command; `read_only` with every permission denied except the read tools
|Result parsed from the final message against the schema, fail-closed
|No schema output in the CLI; unreliable exit codes (`exit_reliable: false`): the server applies its own budget and parses the JSONL output.

|`antigravity`
|—
|—
|No model jobs in v1: no per-call MCP, no per-call system prompt, and no per-call tool allowlist. An operator whose host is Antigravity names another installed harness in `model_jobs.harness`.

|`neutral`
|—
|—
|No headless template; the support rule applies (`model_jobs.harness`).
|===

*Harness enrolment*: A harness executable is an enrolled host tool of the machine: `pm-mcp operator enrol-harness <client>` records its absolute path, the version its version probe reports, and its SHA-256 digest (link:../cli-and-security/02-credentials-and-operator.adoc#operator-enrol-harness[CLI, Coordination & Security Specification, Harness Enrolment]; store: link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]). Before every launch the runtime verifies it without resolving (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Verify-Not-Resolve Execution Pipeline]). Because harnesses update themselves, a changed digest whose version probe reports a version within the profile's supported version range is accepted and audited (the new digest is recorded); a version outside the range refuses the job with `harness_version_unsupported`.

[#agent-composition]
=== Agent Composition per Harness (`agent_mode`)

The `headless` block declares `agent_mode: inline | flags`, the typed slots `{{prompt_file}}`, `{{model}}`, `{{effort}}`, `{{mcp_config}}`, `{{result_schema}}`, `{{tools}}`, `{{cwd}}`, and `{{agent}}` (the rendered inline agent definition), the per-class argument templates `class_args` (`writer`, `read_only`, `zero_tool`; a class without an entry is not runnable on that harness), together with the capabilities `per_call_mcp`, `tool_allowlist`, `zero_tools`, `result_schema`, `ephemeral`, `usage_fields`, `cost_field`, `exit_reliable`, and `project_settings_control`. The server fills only the slots the template declares.

* *`inline`* (Claude, OpenCode): the server renders a per-job named agent from the same slots (Claude: the `--agents` JSON with `tools`, `model`, `effort`, `mcpServers`, `maxTurns`, and `prompt`; OpenCode: the agent in `OPENCODE_CONFIG_CONTENT`) into the `{{agent}}` slot and starts the harness as that agent. Nothing is installed in the host's agent directory, so a newly composed agent is never "not found" and no environment variable of the host overrides its model.
* *`flags`* (Codex): the same slots become per-call flags (`-m`, `-c model_reasoning_effort`, `-c model_instructions_file` or `-c developer_instructions`, `-c mcp_servers.pm.*`, `--output-schema`, `--cd`).
* *Session residue*: The ephemeral flag (`--no-session-persistence`, `--ephemeral`) is always passed where the block declares `ephemeral`; a harness without it declares `session_residue: persisted`, which `pm-mcp status` reports.

[#job-tool-sets]
=== Tool Sets

The tool set of a job is the class's host tools (<<harness-selection>>) and, for `writer` and `read_only`, the `PM-MCP` tools `pm_state`, `pm_do`, `pm_build`, `pm_lsp`, `pm_skill`, and `pm_skill_file`, rendered into `{{tools}}` and enforced a second time by the daemon on the job connection (<<job-token>>). Never in a tool set: the harness's sub-agent tool (`Agent`, `task`, `spawn_agent`), a tool that asks the user, the web tools, and every operator action or scope-creating link. The harness allowlist is defence in depth; the containment is the daemon's per-request binding.

[#job-token]
=== Job-Bound Capability & Connection Binding
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-10[PM-WATCH-DISP-10], link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-30[PM-WATCH-DISP-30], link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-34[PM-WATCH-DISP-34]_

A job never receives the runtime token (link:../runtime-model.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]). It connects back through a capability of its own:

1. *Job token*: At spawn the server mints a random 256-bit job token, stores only its SHA-256 in the job record, and revokes it with the job's fate. The job's MCP configuration starts the relay `pm-mcp serve --job` with the token in the relay's environment variable `PM_MCP_JOB_TOKEN` and the daemon's socket path as a relay argument (a job cannot read `state/runtime.json` under `<PM_MCP_BASE>`, link:../runtime-model.adoc#local-api[Runtime & Interaction Model Specification, Local API]); the relay sends it as the header `PM-MCP-Job-Token` instead of the runtime token (link:../runtime-model.adoc[Runtime & Interaction Model Specification]), and the daemon accepts the header on `/mcp` only.
2. *Per-request binding*: The daemon resolves the job from the token's digest on every request (stateless; no connection state) and enforces: the scope arguments (`plan_id`, `epic_id`, or `NO_PLAN`) and `entity` equal the job's, else `job_scope_mismatch`; `tools/list` and every call are limited to the tool set of <<job-tool-sets>>; `pm_do` admits only links of the job's entity and never a link that enters a `job llm` state. A request carrying the token of an ended job is refused `job_ended`.
3. *No session*: A job connection appends no session row, triggers no client handover, and takes its client profile from the job record; every audit row it causes carries the `job_id`. The first accepted request records `connected_at` in the job record.
4. *Strict MCP configuration*: The per-call MCP configuration is exclusive, so only the job relay connects (`--strict-mcp-config`; Codex `-c mcp_servers.<host entry>.enabled=false`; OpenCode an inline configuration that replaces `mcp`). The hooks and entry commands of the `PM-MCP` client bundle exit at once when `PM_MCP_JOB_ID` is set (link:../cli-and-security/01-cli-and-installer.adoc#session-start-hook[CLI, Coordination & Security Specification, Session-Start Hook]), so the host's own integration never starts inside a job.

The Milestone 1 host spikes verify per harness that its local MCP command receives the relay's environment and that a Landlock-confined job can connect to the daemon's socket.

[#job-working-directory]
=== Working Directory, Project Files & Screener Isolation

* *`writer` and `read_only` jobs*: The process working directory is the plan worktree when the plan has one, else the enrolled project checkout (for the workspace, an epic, and a plan without worktree), by the working-directory rule of every job (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Working Directory Selection]). The harness loads the project's own instructions and skills natively from there (for example `CLAUDE.md`, `AGENTS.md`, project skill directories). No prompt field names a worktree, and the client profile declares no working-directory property.
* *The screener*: runs in an empty directory inside its job-private directory (<<job-prompt>>), with project and user settings off where the harness offers it (`--setting-sources ""`; Codex `--ignore-user-config --ignore-rules`; OpenCode an inline configuration that replaces everything), so no project file and no project skill reaches it; its prompt is the server-fixed screener prompt only.

[#model-slots]
=== Model Slots & One Writer per Plan
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-31[PM-WATCH-DISP-31]_

* *Machine cap*: Model jobs run under a machine lease store `model-slots.json` beside `build-slots.json` (link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]), with the cap `model_slots` in `machine-config.json` (link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration]; default and bounds: link:../timeouts/02-runtime-leases-operator-web.adoc#model-slot-lease[Timeouts & Budgets Specification, Model slot lease]). Admission is FIFO in submission order; stale slots are reaped in the admission transaction as build slots are.
* *Queued*: A job waiting for a slot has the job record status `queued`; its budget starts at spawn, so the time in the queue never counts against it (link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]).
* *One writer per plan*: At most one `writer` job of a plan runs or is queued at a time (serial envelopes: they share one worktree, one chain-tail commit, and one module build, xref:01-task-envelopes.adoc#envelope-early-end[Early End of the Entity]); `read_only` and `zero_tool` jobs of the plan run beside it within the machine cap.
* *Fan-out*: A state that needs one job per item (architecture enrichment: one job per module) submits all of them at once; the slots bound how many run.

[#job-prompt]
=== Prompt File & Contract Envelope
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-9[PM-WATCH-DISP-9], link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-10[PM-WATCH-DISP-10], link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-24[PM-WATCH-DISP-24]_

The server hands a job everything it needs in one prompt file and decides exactly what the job knows; the job starts working without loading anything.

* *Job-private directory*: The runtime creates `pm-mcp-job-<job_id>/` in the system temporary directory inside the job's write set (mode `0700`) before spawn and removes it when the job settles. It holds the prompt file (`0600`), the rendered result schema, and, for the screener, the empty working directory. The prompt file's SHA-256 is the job record's `prompt_digest`.
* *Content, in this order*: (1) the core conduct skill `skill://pm/core/SKILL.md`; (2) the persona, flattened by the server from its `composes:` and `profiles:` graph (cycles rejected); (3) the role's skills; (4) the state's `skill` clauses and, for a task envelope, the union of its tasks' `skills[]` (xref:01-task-envelopes.adoc#_deterministic_envelope_packing_algorithm_envelopepacker[Deterministic Envelope Packing Algorithm]); (5) the contract envelope. Skills are rendered in-band up to the compiled prompt in-band bound (link:../timeouts/03-retention-host-config.adoc#prompt-in-band-bound[Timeouts & Budgets Specification, Prompt in-band skill bound], provisional until the Milestone 1 spikes); above it, the remaining skills are rendered as their section index with the URIs that `pm_skill` serves (link:../mcp-tools/02-service-and-skill-tools.adoc[MCP Tools Specification, Service & Skill Tools]).
* *Contract envelope*: `job_id`; the scope (`plan_id`, `epic_id`, or `NO_PLAN`) and `entity`; the first call (`pm_state` with that scope and entity); the links the entity offers with their named parameter schemas (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]); the job's result schema; and the rule that deliverables are recorded only through the entity's `submit` links.
* *Result*: The job's final structured output is only `job-result` `{status, display_detail}` (xref:02-dispatch-observability-and-spend.adoc#job-result-schema[Job Result & Usage Parsing]); a deliverable is never taken from it.
* *Fail closed*: A prompt that cannot be composed (a skill that does not resolve or renders empty, a schema that does not render) refuses the job before spawn with `prompt_composition_failed`, which raises `precondition_unmet` on the job state; no job ever runs with a skill missing.
* *Project files*: Project-level instructions and skills load natively from the working directory (<<job-working-directory>>); `pm_skill` serves only compiled skills (project-local vocabulary skills: link:../../later-improvements.adoc#_l_4_project_local_vocabulary_skills[Later Improvements, L-4]).

[#job-environment-and-budget]
=== Environment, Confinement & Budget

A model job is confined like every job of its project (link:../job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification, Linux Filesystem Confinement]): no access to `<PM_MCP_BASE>`, writes only to the project root, the job-private directory in the system temporary directory, and the harness homes its profile declares (`headless.writable_paths`), with network access for the harness's model provider. Its environment holds the rows of every job, the harness authentication variables the profile declares in `headless.env_passthrough` (only when captured at the harness enrolment; their values are read from the credential store entry `harness-<client_id>`), and `PM_MCP_JOB_TOKEN` and `PM_MCP_JOB_ID` as the only `PM-MCP` values (link:../job-runtime/02-confinement-and-environment.adoc#_job_environment_pm_sec_5[Job Runtime Specification, Job Environment]). The job reads the harness's own authentication and never a `PM-MCP` credential.

Every model job runs under the job budget of its role, learned per role with a floor default (link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]); budget expiry, `cancel:<job_id>`, and drain end it through the termination protocol of every job (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_process_termination_cancellation_protocol[Job Runtime Specification, Process Termination & Cancellation Protocol]).
