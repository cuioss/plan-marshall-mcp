[#two-level-guard]
== Two-Level Guard for External Text
_See Requirement link:../../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

Fetching, extracting, and guarding external content is server work; a model only judges content the server has already fetched, validated, and marked untrusted. External text passes two guards before it reaches a model as content:

1. *Level 1, the deterministic ingestion validator* of the server, which is the containment boundary (link:../job-runtime/03-parsers-and-gates.adoc#ingestion-validator[Job Runtime Specification, Ingestion Validator]).
2. *Level 2, the screener*: a zero-tool model job that receives the cleaned text in-band and returns a closed verdict per item (<<screener>>). It can only restrict, never grant: it is defence in depth, never the boundary, and screened text is still delivered marked untrusted.

*Surfaces*: Level 2 screens all externally authored free text: issue and pull-request titles and bodies, every review comment and bot finding text, analysis-provider messages, and upstream MCP results entering a store. CI logs and build excerpts are the server's own job output and pass level 1 only.

There is no model that extracts from external text: no reader agent exists, and a model never fetches external content itself.

[#batch-v1]
=== Batch Format (`batch-v1`)
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-36[PM-WATCH-DISP-36]_

Every source step and every gather firing that ingests external text gathers its new items first and writes them, after level 1, as one server-built batch. The batch is the unit of screening and of batched judgment:

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/batch-v1.json",
  "title": "Batch",
  "type": "object",
  "required": ["batch_id", "items"],
  "additionalProperties": false,
  "properties": {
    "batch_id": { "type": "string", "pattern": "^BT-[0-9]+$", "description": "Scope-unique identifier of the batch, assigned by the server (identifiers.adoc, record counters)." },
    "items": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["item_id", "kind", "source", "fields", "text", "sha256"],
        "additionalProperties": false,
        "properties": {
          "item_id": { "type": "string", "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$", "description": "Batch-unique item identifier; for a finding its finding_id." },
          "kind": { "type": "string", "enum": ["issue", "pull_request", "review_comment", "bot_finding", "analysis_message", "upstream_result"] },
          "source": { "type": "string", "description": "Provider, bot kind, analysis provider, or upstream server that authored the text." },
          "fields": { "type": "object", "description": "The item's structured fields (author, file, line, rule_id, domain); never free text." },
          "text": { "type": "string", "description": "The level-1-cleaned text, enclosed in the spotlighting delimiters of the validator." },
          "sha256": { "type": "string", "pattern": "^[0-9a-f]{64}$", "description": "SHA-256 of the cleaned text; the key of the verdict cache." }
        }
      }
    }
  }
}
----

The batch is persisted with the records it came from (the pending entry record for a bootstrap source, the findings records of a gather firing with their `batch_id`, link:../store-schemas/03-findings-and-review-records.adoc[Store Schemas Specification, Findings & Review Records]); it is never rendered into `facts` as a whole.

[#screener]
=== Screener Job (role `screen.effort`)
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-25[PM-WATCH-DISP-25], link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-35[PM-WATCH-DISP-35]_

* *One job per batch part*: The screen state after a source or gather step screens the batch's items that have no cached verdict. It is declared with the fan-out of a model job state, `job llm screen role screen.effort each screen.batch-parts` (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Model Job States]), over the server-computed list of the batch's parts: a batch within the compiled screening split bound (link:../timeouts/03-retention-host-config.adoc#screening-split-bound[Timeouts & Budgets Specification, Screening split bound], provisional until the Milestone 1 spikes) is one part, a batch above it is split into consecutive parts. The state starts one screener job per part through the model slots and completes when every part has its verdict.
* *Verdict cache*: Verdicts are cached per scope by the `sha256` of the cleaned text, so a re-gather screens only new texts. A cached verdict is reused, never re-decided; a fail-closed verdict (no valid screener output) is never cached (link:../store-schemas/15-screening-and-grants.adoc#screen-verdict-cache[Store Schemas Specification, Screening Verdict Cache]).
* *Isolation*: The screener is a `zero_tool` job (xref:05-model-job-launch.adoc#harness-selection[Harness Selection & Support Rule]): no tools, no MCP connection, one turn where the harness offers the limit, the server-fixed screener prompt (compiled, never a skill and never project-overridable) with the items in-band inside their spotlighting delimiters, the empty `cwd/` subdirectory of its job-private directory as working directory, and project and user settings off (xref:05-model-job-launch.adoc#job-working-directory[Working Directory, Project Files & Screener Isolation]). It has no entity unit.
* *Result*: The structured output `screen-verdict`, validated by the server:
+
[source,json]
----
{
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/screen-verdict-v1.json",
  "type": "object",
  "required": ["items"],
  "additionalProperties": false,
  "properties": {
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["item_id", "verdict", "spans"],
        "additionalProperties": false,
        "properties": {
          "item_id": { "type": "string", "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$" },
          "verdict": { "type": "string", "enum": ["clean", "suspicious"] },
          "spans": {
            "type": "array",
            "items": {
              "type": "object",
              "required": ["start", "end", "reason"],
              "additionalProperties": false,
              "properties": {
                "start": { "type": "integer", "minimum": 0 },
                "end": { "type": "integer", "minimum": 0 },
                "reason": { "type": "string", "maxLength": 200 }
              }
            }
          }
        }
      }
    }
  }
}
----
* *Fail closed*: A missing, extra, duplicate, or unparseable item counts as `suspicious`; a screener job that ends with any fate other than `succeeded`, or whose output does not validate, makes every item of its part `suspicious`. On a harness without schema output the final message is parsed against the same schema, with the same rule.
* *Effect of `suspicious`*: In a bootstrap source step, the step enters a link state that shows the flagged spans and offers `accept` (the text is used, still marked untrusted, the acceptance audited) or `back`. Inside a plan the text is withheld: only the item's structured fields and `withheld: flagged by screener` are delivered; a withheld finding stays pending, its unit ends through its budget and fallback, the hand-back report lists the withheld items, and a `met` waiver of that finding lets the plan proceed (link:../state-catalogue.adoc[State Catalogue]).

[#batched-triage]
=== Batched Triage (`triage-groups`)
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-36[PM-WATCH-DISP-36]_

Model judgment of findings is batched like screening: one triage job per gather firing, never one per finding.

* *Grouping*: The server groups the batch's findings that are not withheld by `(domain, rule_id)` and renders the groups, each with its findings' structured fields and cleaned texts, as the entity of one triage job (role `plan.phase-6-finalize.effort.triage`, the job state `remediation-review.triage`).
* *Submission*: The job submits `submit:triage-groups` once: per group one disposition (`FIX`, `SUPPRESS`, or `ACCEPT`, with `reply_text` and, for `FIX`, `population`; optional `requirement_refs`), and per finding an optional exception that overrides the group's disposition for that finding.
* *Server writes per finding*: The server expands the groups and writes one disposition per finding, validating each like a single disposition (a disposition that contradicts the finding's class is refused, `invalid_link_args` naming the finding); a finding the submission does not cover stays untriaged. Withheld findings are never part of a triage batch.
