[#question-records]
== Question Records
_See Requirements link:../../Requirements.adoc#PM-WF-5[PM-WF-5: Server-Launched Model Jobs & Single-Level Leaf Constraint], link:../../Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Job Accounting & Effort Role Resolution]_
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-14[PM-WATCH-TOOL-14]_

Every content question of a plan (an init classifier's question, a refine or outline clarification, the optional outline review, a Phase 5 task question, a question the model asks before a judgment) is a server-owned *question record*. A question is never an operator decision: overrides (waivers, `abort`, the integrity resolutions) use only the operator channel, and a waiver request is its own record, never a question record. A model job never prompts a human and never waits for an answer.

=== Architectural Rationale

1. *Slot Conservation*: A model job waiting for human input would hold a model slot and the plan's one writer slot; a question therefore ends the asking entity at once.
2. *No User Inside a Job*: A headless model job has no user at all: its tool set holds no tool that asks one, and nothing it could raise reaches a human; the server, not the job, delivers the question.
3. *Bounded, Resumable Questions*: A record lives in the plan store, so a question survives `/clear`, compaction, and a gone host session; every question is bounded by a server-side question wait and ends in a defined fallback, except where the operator chose `questions.mode: operator`.

[#question-record-creation]
=== Record, Store & Creation

Question records are appended to `questions.jsonl` of the scope's store (plan, epic, or workspace; link:../store-schemas.adoc[Store Schemas Specification]): the envelope below, `asked_at`, the resolved `delivery`, the engine-owned deadline, answer events `{branch_key, text?, channel, answered_at}` with `channel: user_relayed | elicitation | web | assumption | model`, and the closure `answered | assumed | cancelled`. They are created in three ways:

1. *The `ask` link*: a state that declares it offers `ask` (`question:schema[question-envelope]`, link:../hypermedia-format/01-representation-and-link-forms.adoc#question-waiver-and-exit-links[Hypermedia Format Specification, Question, Waiver-Request & Exit Links]); the model asks before it takes a judgment (for example which of `remove_deliverable` and `loop_back_outline` to follow), and the engine enters the state's question state `<state>.asked`, which serves the record and returns to the asking state once the record closes (`answered` or `assumed`), with the answer in its `facts`.
2. *A model job's submission*: a refine or outline authoring entity completes its draft on best judgment and carries its open questions in the `questions` list of its one `submit` (`questions:list<schema[question-envelope]>?`), each item becoming a record (class `clarification`); a task envelope's `ask:TASK-NNN` creates one record (class `task`) and ends the entity (<<task-questions>>).
3. *A server primitive*: init classifiers, the optional outline review, and the workspace setup choices that write team configuration raise records with server-owned options (`origin: server`, classes `init`, `review`, and `setup`). Setup choices that write operator configuration are never question records: they use the operator channel.

[#question-envelope-schema]
*Server-Owned Fields*: `question_id`, `class`, `origin`, and `source_entity` are assigned by the server when it persists a question, never by the model. `question_id` is the next value of a scope-wide counter of the plan, epic, or workspace (link:../identifiers/01-general-rules-and-registry.adoc#id-question-id[Identifier Registry, `question_id`]), never reused; `source_entity` is the `entity` of the entity-scoped call that carried the question, the call's `job_id` when it names no entity, or the creating state of a server-raised question. The model supplies a question without these four fields: the free schema of `ask` and `ask:TASK-NNN` and the item schema of the `questions` list are the `BatchedQuestionEnvelope` minus `question_id`, `class`, `origin`, and `source_entity` (that is `question_text`, `default_assumption`, and `options`, each option an object `{branch_key, label, description, recommended?}`), and a payload that carries a server-owned field is rejected with `invalid_link_args`. This model-supplied subset is registered as the named parameter schema `question-envelope` (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]). It is the schema below with the four server-owned members removed from `properties` and `required`, closed with `additionalProperties: false`.

=== Mode, Delivery & the Question Wait
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-29[PM-WATCH-DISP-29]_

How a record is answered is operator configuration in `local-config.json` (operator channel only, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), per project with optional overrides per class (`init`, `clarification`, `review`, `task`; `setup` and `ask` follow the project value):

[cols="1,5"]
|===
|`questions.mode` |Effect

|`auto` (default)
|Delivered per `questions.delivery`, bounded by `questions.wait_seconds` (shipped `1800`); on expiry the class fallback below applies.

|`operator`
|Delivered to a human per `questions.delivery` without a deadline: an operator-chosen exception to the bounded waits. The state is derived `awaiting_user` and a long wait is listed by the stalled-plan detection.

|`model`
|The model answers itself through `answer_questions` with a `confidence` (`0..100`); the server accepts it at or above the compiled refine confidence threshold (`95`) with `channel: model`, otherwise the record falls through to `auto`.

|`none`
|No wait: the `recommended` option, else the `default_assumption`, is applied at once and recorded with `channel: assumption`.
|===

`questions.delivery` defaults to `elicitation` where the connection declared elicitation support, else `session`; `web` (a paired web device, with notification) is opt-in. The delivery is resolved per record at creation and recorded as the answer's `channel`. With `session` delivery the model relays the question in the host chat and submits the answer through `answer_questions` (`channel: user_relayed`), and the question state is a continuation stop point; with `elicitation` or `web` the server asks the human itself and the model may long-poll `wait:question:<question_id>`. Neither `pm-mcp` nor `pm-operator` has an answer command. The question wait is a link state with an engine-owned deadline processed by the job runtime's timer, which takes the fallback transition without a model call and survives a gone host session; its awaited events are `QUESTION_ANSWER` (any channel) and `TIME` (expiry).

*Expiry Fallback per Class* (compiled):

[cols="1,4"]
|===
|Class |On expiry

|`init`
|The classifier's server-computed `recommended` option as a recorded assumption.

|`clarification`
|The envelope's `default_assumption`, recorded as an assumption amendment.

|`review`
|The `returned` route (a review that was asked for and not given does not start execution).

|`task`
|Parent answer expected: the main-session model answers (<<task-questions>>).

|`setup`
|The question state's declared fallback, recorded as an assumption (link:../domain-extensions/04-setup-state-machine.adoc#setup-questions[Domain Extensions Specification, Setup choices by owner]).

|`ask`
|The record closes `assumed` with its `default_assumption`; the state's links stay offered for the model's own judgment.
|===

*Answers & Amendments*: `answer_questions` takes `answers:list<schema[question-answer]>` (`question_id`, `branch_key`, optional `text`, `confidence` only in `model` mode); elicitation and web answers pass the same validation. An unknown `branch_key` is refused `invalid_link_args`, a second answer `already_answered`, an answer on a user channel after the expiry fallback `question_expired` (never the main-session model's answer to an expired `task` record, <<task-questions>>). A model-relayed answer is accepted only for content questions, never for an override (`PM-WF-12`). An answer creates an `amendments[]` entry (with its `question_id`) only when it changes the plan's intent; refine answers still go into `request.md`. The amendment `source` is `user` (a human answer on any channel), `model` (the main-session model's or a self-answer), `assumption` (a fallback or `none`), or `refutation` (a refuted lesson premise, carried from the lesson source of the plan's bootstrap); answered questions and amendments are listed in the pull-request body, the landing record, and the retrospective.

*Lifecycle Rules*: A plan scope has at most one question state at a time (phases are serial), and a waiver request arises only inside a remediation unit, which is never entered while a question state is current, so a question wait and a waiver wait never overlap. The `integrity_breach` pause holds a record's expiry until the pause ends. Operator `abort` and `delete-plan` close every open record `cancelled`.

[#phase-question-states]
=== Phase Question States (`refine.awaiting_answers`, `outline.awaiting_answers`)

When the return evaluation of a refine or outline authoring job finds that the entity's submission created open records, it enters the phase's question state (`refine.awaiting_answers` or `outline.awaiting_answers`), which serves the records per their mode and delivery and advances once every record is closed. A Q-Gate remediation pass of `refine.analyze` never opens a new question round: its questions and a below-threshold confidence are recorded as `low_confidence_manual_review`.

[#task-questions]
=== Task Questions (Phase 5)
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-28[PM-WATCH-DISP-28]_

A task question is an ordinary question record of class `task`. The envelope's model job follows `ask:TASK-NNN` (`question:schema[question-envelope]`) on `envelope.task.active` when a task cannot proceed without an answer (for example a contradictory interface contract); the server persists the record with `source_entity` the envelope and the task id and ends the entity (xref:01-task-envelopes.adoc#envelope-early-end[Early End of the Entity]), and the job ends. The plan's return evaluation yields `question_pending` and enters `execute.task-question` on the plan scope, which serves the record per the `task` class's mode and delivery. When the question wait expires on a user channel, the record moves to *parent answer expected*: `execute.task-question` offers `answer_questions` to the main-session model, whose answer (`channel: model`) is validated against the stored options like any answer; `question_expired` applies only to the user channels, never to this answer. With a wait of `0` the main-session model answers at once. In every case the server records the answer as an `amendments[]` entry (`source: user` or `model`) and lists it in the pull-request body and the landing record. The remaining tasks, the asking task included, form the next envelope `envelope-(N+1)`, launched as a new model job with the answer in its `facts`. No further envelope job is launched while the record is open.

== Role Registry, Effort Level Ladder (Levels 1–7) & Resolution to Harness Flags
_See Requirements link:../../Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Job Accounting & Effort Role Resolution], link:../../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

`PM-MCP` decouples the workflow's job states from concrete model identifiers through a two-stage resolution, evaluated at the launch of every model job:

1. **Role Resolution**: Maps the job state's role key to an abstract **effort level** (`level-1`..`level-7` or `inherit`).
2. **Ladder Resolution**: Maps that level and the job's harness (xref:05-model-job-launch.adoc#harness-selection[Harness Selection & Support Rule]) to a `model` and an `effort`, which the launch passes as CLI flags (<<effort-resolution>>).

The role registry, the level vocabulary, the resolve chain, and the ladders mirror `plan-marshall` (`plan-marshall/standards/effort-roles.md`, `effort-levels.md`, ADR-021), verified at commit `1d4a1da37`, with three deliberate changes: an unknown effort key is a validation error (<<_role_registry_lookup_hierarchy>>), a role exists only where a job state uses it, and nothing is installed per level (`plan-marshall`'s build-time agent variants do not exist). Re-verify against the latest `plan-marshall` version before implementing.

=== Role Registry & Lookup Hierarchy
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-11[PM-WATCH-DISP-11]_

Configured values are the strings `level-1` .. `level-7` or `inherit`; any other value is a hard error on read. Effort keys are validated against the role registry below on the same read: a group the registry does not know (for example `plan.phase-1-init.effort`, or an unknown key under `orchestrator.effort`) or a sub-key its group does not list is a validation error exactly like an invalid value, never skipped with a fallback to the `default` slot. The validation on read of the effective configuration reports it (in `pm://project/config` and in `setup.reconcile-config`, link:../domain-extensions/06-configuration.adoc#config-upgrades[Domain Extensions Specification, Validation on Every Read]) as an `unknown_config_key` finding naming the key path in `workflow.json`, and the server logs `PM_MCP-100` (link:../../LogMessages.adoc[Log Messages]). *Deliberate change vs. `plan-marshall`*: it only warns on an unknown role key and resolves it through the fallback chain (`default` -> `effort` -> `plan.effort` -> `inherit`) so that registry renames do not break saved configurations (`effort-variants.md` § Validation, `manage-config/scripts/_cmd_effort.py`); `PM-MCP` rejects it, because a silently ignored key hides a misconfigured role. There are no mandatory keys and one built-in per-role default: `screen.effort` ships the compiled default `level-1` (the screener's work is a small, fixed classification); every other unconfigured role resolves to `inherit`.

A role key is the configuration path the job state names (`job llm <entity_kind> role <role_key>`), and a role exists if and only if a job state uses it; work that runs inline in the main session (Phase 1, Phase 4 task planning, `create-pr`, the pre-submission self-review, applying accepted simplify proposals, the ADR author, and the epic landing analysis `submit_landing`) has no role. The class decides the job's tool set (xref:05-model-job-launch.adoc#job-tool-sets[Tool Sets]):

A group (`plan.<phase>.effort`, `setup.effort`, `lessons.effort`, `orchestrator.effort`) may be a plain string (one level for every sub-key) or an object with per-sub-key values and a `default` slot; `screen.effort` is a plain string.

==== Deterministic Role Lookup Algorithm

1. **Plan, setup and lesson roles**: `<group>.<subkey>` -> `<group>.default` -> `<group>` (string) -> `plan.effort` -> `inherit`, where `<group>` is `plan.<phase>.effort`, `setup.effort`, or `lessons.effort`; `screen.effort` -> the compiled default `level-1` (never `plan.effort`).
2. **Orchestrator roles**: `orchestrator.effort.<surface>` -> `orchestrator.effort.default` (or the plain string) -> `plan.effort` -> `inherit`, then clamped to `orchestrator.effort.max` on the ordinal ladder (`min(resolved, max)`; an unset `max` is a no-op). Before the clamp, a result of `inherit` is resolved to a concrete level: with `max` set it becomes `max` itself, because the harness default has no rung the server can order against the ceiling; with `max` unset it stays `inherit`. *Deliberate change vs. `plan-marshall`*: its clamp passes `inherit` through unclamped, so an inheriting surface escaped the ceiling. Orchestrator job states always name their surface so the clamp cannot be bypassed.
3. **Unknown group or sub-key**: A validation error of the effort configuration (see above), reported by the validation on read of the effective configuration and logged as `PM_MCP-100`; the lookup never falls back from an unknown key to the `default` slot.

=== Effort Ladders (`effort_ladder` in `<PM_MCP_BASE>/projects/<project_id>/local-config.json`)
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-12[PM-WATCH-DISP-12]_

The ladder maps each level to a concrete `model` and `effort` per harness. The team file `.marshall/config/workflow.json` carries only the target-neutral levels; model pins are never stored in git-tracked configuration (ADR-021).

* **Machine-local ladder**: The operator file `<PM_MCP_BASE>/projects/<project_id>/local-config.json` holds `effort_ladder: {"<client_id>": {"level-N": {"model": <string|null>, "effort": <string|null>}}}` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), keyed by the harness's client id, with machine-wide defaults in `machine-config.json` `project_defaults.effort_ladder`; `plan-marshall`'s own ladder file is never read. `model: null` means unpinned.
* **Compiled defaults**: When an entry is absent (the file is sparse), the ladder compiled into the client profile (link:../client-profiles.adoc[Client Profiles Specification]) applies and `pm://project/config` reports the source `compiled_default`; nothing is seeded into the file.
* **Narrow but never escalate (ADR-021)**: A ladder entry serves only its own level and never provisions a model beyond the capability of the resolved rung. ADR-021 (status *Proposed* in `plan-marshall`) also prescribes an entry-kind discriminator (`local` / `provider`) that `plan-marshall`'s current file format does not yet carry; verify its status before implementing the ladder reader.

[#effort-resolution]
=== Effort Resolution to Harness Flags

* *Flags, not files*: The resolved `model` and `effort` fill the `{{model}}` and `{{effort}}` slots of the harness's `headless` template (xref:05-model-job-launch.adoc#agent-composition[Agent Composition per Harness]); `inherit` and an unpinned entry fill neither slot, so the harness's own default applies. No agent file is installed per level or per client, and a ladder or role change reaches the next model job without a client update and without a host restart.
* *Operator model per role*: An entry `model_jobs.roles.<role_key>.model` in `local-config.json` replaces the ladder's model for that role (for example a small model for `screen.effort`); the effort still comes from the ladder.
* *Narrowing*: An effort that the harness or the model does not support (as the harness's `headless.model_efforts` declares per model, link:../client-profiles/01-profile-schema.adoc#headless-block[Client Profiles Specification, `headless`]) narrows to the nearest supported lower value, never to a higher one; the job record keeps the resolved value as `effort_narrowed_from`. A level whose model the harness cannot run is a launch refusal (`precondition_unmet`), never a silent substitution. *Deliberate change vs. `plan-marshall`*: its resolver does not know which variants the emitter skipped, so a dispatch resolved to a skipped `level-6` / `level-7` variant fails at runtime with `Agent type not found` (`effort-variants.md` § Build-Time Alias-Capability Guard).
