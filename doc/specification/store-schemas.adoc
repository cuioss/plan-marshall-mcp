== Overview

This document defines the normative JSON and JSONL storage schemas for *plan-marshall-mcp* (`PM-MCP`). Every persisted file includes an explicit `format_version` integer; before 1.0 a binary accepts exactly the current version of each file kind and refuses any other with a named reason, and nothing is migrated on startup (`PM-IMPL-2`, <<format-versioning>>). `PM-MCP` shares no store with legacy `plan-marshall`: its stores live under `.marshall/` and `<PM_MCP_BASE>` (`PM-MIG-2`), and it imports nothing from legacy `plan-marshall`. Legacy formats are not part of this specification: the legacy -> target mapping of the differential tests lives in test code only (`PM-TEST-2`).

[#format-versioning]
== Format Versioning & Atomic Write Discipline
_Implementation watch: link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-17[PM-WATCH-GEN-17], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-25[PM-WATCH-STORE-25], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-37[PM-WATCH-STORE-37]_

[[_format_versioning_atomic_write_discipline]]
1. *Version Envelope*: Every persisted JSON root object and every JSONL header/record must declare `"format_version": 1` (positive integer, one sequence per file kind): the server-owned stores, the git-tracked team configuration files `.marshall/config/*.json` (<<project-configuration-store>>), and the operator files (`local-config.json`, `machine-config.json`, enrolments, credential files). A workflow unit (`*.pmwf`) declares its DSL format in its header (`workflow <id> version <n> format <f>`, link:workflow-dsl.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification]). Exempt are Markdown documents (checked by their parsers), plain-text logs, OS primitives, and the raw HMAC key.
+
*Accept exactly one, refuse, never rewrite*: Before 1.0 a binary accepts exactly the current `format_version` of each file kind; there is no migration chain and no startup migration. A reader returns `absent`, `unreadable` (including a missing `format_version`), `format_outdated{file, found, current}`, `format_newer{file, found, current}`, or `parsed`; no reader tolerates an older shape. An outdated or newer file is never modified by a reader: a scope store raises the `blocked` condition on its scope with the operator command; a team configuration file or workflow unit refuses every `pm_start` and phase handshake of the project with `format_outdated` or `format_newer` naming the file (link:mcp-tools.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]); an operator file is refused by the CLI naming the file and the changed keys. *Upgrade path*: a `format_version` bump is listed with the changed keys in the release notes; in-flight scopes follow the drain rule (`pm-mcp drain` reports live scopes; the operator finishes them before upgrading), and the project setup workflow offers the new binary's default changes (a diff for workflow units, a server-rendered rewrite for JSON configuration files, link:domain-extensions.adoc#config-upgrades[Domain Extensions Specification, Configuration Upgrades]). The migration mechanism for 1.0 and later is decided at 1.0.
2. *Atomic Write-and-Rename*: All JSON file updates are written to a sibling temporary file (`<filename>.tmp.<uuid>`), flushed to disk (`FileChannel.force(true)`), and atomically renamed over the target file (`StandardCopyOption.ATOMIC_MOVE`, `StandardCopyOption.REPLACE_EXISTING`). A store replaced this way is guarded by a sibling lock file, never by a lock on the store file itself (<<lock-free-snapshot-reads>>). Every write to a plan, epic, or workspace store runs as a journaled transaction (<<transaction-journal>>).
3. *Single Writer Set*: Every writer of a `PM-MCP` store runs inside the one `PM-MCP` runtime and serializes through its own locks. Legacy `plan-marshall` never touches `.marshall/` or `<PM_MCP_BASE>`, and `PM-MCP` never writes `.plan/` or `~/.plan-marshall/` (`PM-MIG-2`), so no store is shared and no cross-runtime lock protocol exists.
4. *Absent vs Unparseable*: Every store and document reader returns one of `absent`, `empty`, `parsed`, or `unreadable` (with the failing line or offset). An input that yields no parsable content is `unreadable`, never an empty record and never `absent`. Consumers handle `unreadable` explicitly: they fail closed or report `indeterminate`.
5. *One Wire Shape per Instant*: Every persisted or exchanged instant is an RFC 3339 UTC string (`"format": "date-time"`, `Z` suffix); epoch numbers are never persisted. A process start instant is taken from the OS (`ProcessHandle.Info.startInstant()`) and stored in the same shape. Durations are integers whose field name carries the unit (`duration_ms`, `*_seconds`).
6. *JSONL Append Discipline*: A JSONL store is appended to only under the lock of its store (the scope lock for plan, epic, and workspace stores; the audit lock for `audit.jsonl`), by one `write` on a descriptor opened with `O_APPEND` (`StandardOpenOption.APPEND`), followed by `fsync` (`FileChannel.force(true)`); every appended record ends with a newline. A last line without a trailing newline is a torn tail left by an interrupted append: the next writer, still under the store's lock and before appending, truncates the file to the end of the last complete line and appends an audit record `jsonl_tail_repaired` (`category: store`, `details{store, truncated_bytes, truncated_sha256}`). Lines before the last complete newline are never touched; a malformed complete line stays in place and is reported `unreadable` with its line number (item 4). In `audit.jsonl` a torn tail lies after the anchored head (`audit.head` is updated only after a complete append), so the repair never touches a chained record.

[#transaction-journal]
=== Transaction Journal (`mcp/transaction-journal.json`)

Every write to the server-owned stores of a plan, epic, or workspace scope runs as one transaction under the scope lock, recorded in the per-scope transaction journal `mcp/transaction-journal.json` in the scope's metadata directory of the per-project machine store (`plans/<plan_id>/mcp/`, `epics/<epic_id>/`, `workspace/mcp/`, link:filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]). A single-store write is a transaction with one target; there is no second write path.

. *Stage*: Write the new content of every replaced store to its sibling temporary file (`<file>.tmp.<transaction_id>`), and the bytes of every JSONL append to `<file>.append.<transaction_id>`; `fsync` each.
. *Journal*: Write `mcp/transaction-journal.json` (atomic write-and-rename, `fsync` of the file and of `mcp/`) listing every target store with its staged file and its new size and SHA-256.
. *Apply*: Rename every staged file over its store (`ATOMIC_MOVE`) and append every staged JSONL block (item 6 above), then `fsync` the parent directories.
. *Digests*: Where the scope keeps a digest sidecar (<<store-digest-verification>>), write it with the new digests taken from the journal (atomic write-and-rename).
. *Close*: Delete the journal and `fsync` `mcp/`; only then is the scope lock released.

*Recovery*: At runtime start, and lazily on the first call that addresses a scope, the runtime takes the scope lock and rolls an existing journal forward: a target whose current size and SHA-256 equal the journal's is already applied; otherwise its staged file is renamed over it (replace), or the file is truncated to `size_before` and the staged block appended (append). It then writes the sidecar (where the scope keeps one) from the journal, deletes the journal, and records a `transaction_rolled_forward` audit record. Digests are recorded only on this path (a transaction or its roll-forward); there is no other rule that re-records a digest. A journal whose target has neither the new digest nor its staged file is an invariant violation: the scope enters `store_tampered` for that store. Orphaned staged files without a journal belong to a transaction that never journaled and are deleted by recovery. The project's lesson store follows the same protocol with its journal `lessons/.transaction-journal.json` of the machine store under the lesson store lock.

  "additionalProperties": false,

[#scope-session-log]
== Scope Session Log (`sessions.jsonl`)
_Implementation watch: link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-1[PM-WATCH-STORE-1]_

[[_scope_session_log_sessions_jsonl]]
Every scope keeps an append-only session log in the per-project machine store (link:filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]): `plans/<plan_id>/sessions.jsonl`, `epics/<epic_id>/sessions.jsonl`, or `workspace/sessions.jsonl` (the project's workspace scope, link:filesystem-layout.adoc#workspace-home[Filesystem Layout Specification, Workspace Home]). Each row records one host session that entered or addressed the scope. The *current identity* of the scope is its last row: every scope-addressed MCP call resolves the client profile from it (`PM-ARCH-4`); the project is the store the log lives in, never a path recorded in a row.

* *Appended by `pm-mcp enter`*: Every `pm-mcp enter` on an existing scope appends one row (link:cli-and-security.adoc#_entry_identity_recording_pm_mcp_enter[CLI, Coordination & Security Specification, Entry Identity Recording]).
* *Appended by the server*: When a scope-addressed call carries a `PM-MCP-Client-Session` header (link:runtime-model.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]) whose value differs from the `client_session_id` of the scope's last row, the server appends a row for that session in a short transaction under the scope lock, outside any snapshot read. Such a row keeps the declared `client` of the previous row (a declaration is only ever made by `pm-mcp enter`), takes `client_detected` from the connection's MCP `clientInfo.name`, and records `client_build: null` (the version probe runs only in `pm-mcp enter`).
* *`last_seen_at`*: The server refreshes `last_seen_at` of the last row at most once per minute per scope, by a journaled replace of the file in which every earlier row stays byte-identical; no other field of any row is ever changed, and no earlier row is ever touched.
* *Pending Entry Record*: When the entered plan does not exist yet, `pm-mcp enter` writes a pending entry record `pending/<entry_id>.json` of the per-project machine store and prints the `entry_id`. `pm_start(entry_id, ...)` consumes it inside the plan initialization transaction: its `session` becomes the first row of the new plan's `sessions.jsonl`, its `from_epic` is copied into the plan's `mcp/status.json` `origin.epic_id` (the single carrier of epic membership, <<_workflow_state_store_mcpstatus_json>>), and the pending file is deleted. A consumed `entry_id` no longer exists, so each pending record starts at most one plan.
* *History in the Log*: The session history of a scope is the log itself. A row whose declared `client` differs from the previous row's additionally appends an `identity` audit record (`event: entry_handover`, `details` with the previous and the new `client` and `client_session_id`, <<audit-log>>).
* *Integrity*: `sessions.jsonl` follows the JSONL append discipline (<<format-versioning>> item 6) and is covered by the scope's digest sidecar (<<store-digest-verification>>).

== Workflow State Store (`mcp/status.json`)
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-1[PM-WATCH-PHASE-1], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-40[PM-WATCH-PHASE-40], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-69[PM-WATCH-PHASE-69], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-3[PM-WATCH-STORE-3]_

Tracks the authoritative state machine position, phase, persisted sub-workflow `call_stack`, active jobs and the job bound to the current job state (`active_job`), the pending condition overlay and operator decision, loop-back iteration counters, per-step outcome records, merge authorizations, and composite wait facts for a plan, an epic, or the project's workspace scope (`PM-ARCH-6`, `PM-WF-7`, `PM-WF-13`, `PM-WF-16`, `PM-IMPL-7`). Store digests live in the sidecar `mcp/digests.json` (<<store-digest-verification>>). The values of the `state` field (and the `phase` value each state carries) are catalogued in the link:state-catalogue.adoc[State Catalogue].

* *Step Records Count Firings*: Every firing of a step appends to its `firings[]`; a re-fire never replaces the history. When `VerdictCurrencyEvaluator` decides to re-fire, the step's `outcome` is set to `unverified` before the step runs and is then replaced by the new firing's terminal outcome, so a prior `done` never survives a re-fire. The current `outcome` and `head_at_completion` are always those of the last firing; no force flag exists. A requested outcome change that the engine refuses appends a firing with `refused` set and leaves no stale outcome silently current. Re-fire counts per cause are `firings` minus one, grouped by `cause`, never counted from log lines. A record without `assurance_verdict` reads `unadjudicated`, never as a pass.
* *Origin and Epic Linkage*: Epic membership has one carrier, `origin.epic_id`: `pm-mcp enter --from-epic` writes `from_epic` into the pending entry record (<<scope-session-log>>), and `pm_start` copies it into `origin.epic_id`; `pm_start` accepts no epic parameter, and no session row carries epic membership. Every consumer (landing emission, outbox link offering, epic observation) reads epic membership from `origin.epic_id` through one resolver, which derives `epic_linkage`: `not_orchestrated` iff `origin.epic_id` is null, `indeterminate` iff it is set but the epic's header `epic.json` (<<epic-header>>) is absent or unreadable, otherwise `orchestrated`. `indeterminate` is never read as `not_orchestrated`.
* *Amendments*: Every intent-changing answer after refinement appends an `amendments[]` entry; every later representation that renders the request (outline review, `create-pr`, landing) includes the amendments in order.

An owed item is an obligation a plan incurred but did not discharge. It is written by the step that incurs it, never
derived from prose, and it stays in the plan's `mcp/status.json` through archival (`PM-WF-13`).

* *Kinds*: `cleanup` (worktree or branch removal owed after a non-merging run; the former landing field `cleanup_owed`), `deferred_reconcile` (a reconcile deferred instead of performed), `pr_body_note` (a note that could not be written before the pull request existed), `owed_source_edit` (a follow-up source change, for example a triage `ACCEPT` with follow-up), `owed_hint` (a hint routed for later action by `lessons-capture`, `preference-emitter`, or disposition-to-hint routing), and `unrecorded_stall` (a stall the epic view or `pm-mcp status` derived from the last-transition age of a non-terminal plan).
* *Explicit Empty Set*: `emit-landing` and `archive-plan` write `owed` explicitly; `[]` means the plan owes nothing, an absent or null field means the question was never asked and is rendered `unknown`, never as nothing owed.
* *Survives Archival*: Owed items stay readable from the archived plan (link:filesystem-layout.adoc[Filesystem Layout Specification]) and are never folded into `completed`.
* *Listable Without Prose*: For an epic plan the landing envelope carries `owed[]` to the epic inbox. For every plan, the project owed index `pm://project/owed` (link:mcp-tools.adoc[MCP Tools Specification]) lists the undischarged items of active and archived plans, derived from their `owed[]` (no separate store), with per-root coverage; a root that could not be read is reported, never read as zero.
* *Discharge*: An item is discharged only by recording `discharge_proof` and `discharged_at` through the discharging party's transition (a transition of the owning epic, the step that incurred it on a later firing, or the operator CLI `pm-mcp operator discharge-owed --plan <plan_id> --owed <owed_id> --proof <ref>`, which also serves archived plans and is the only write an archived plan accepts); a discharged item is kept, never deleted.

* *Immutable Severity, Mutable Blocking*: `severity` is set at creation and never changed. `blocking` is written from the producer's declared class for the finding type (each producer declares it per finding type in its descriptor, validated at write) and may later change only through triage or an operator decision.
* *What Is Not a Finding*: Refusals, rate-limit or budget notices, the server's own posted comments and triggers, and participation-only artifacts (summary cards, trigger acknowledgements) are never filed as findings; they update the review participation record only (<<review-participation>>).
* *Self-Reports*: A `self_report` finding is filed by the server, never by a step, when the model follows `report_bypass` (link:hypermedia-format.adoc#self-report-link[Hypermedia Format Specification, Self-Report Link]); it carries the reported action as `summary`, the reason as `body`, `severity: major`, and `blocking: false`, and its paired audit record shares its timestamp. It names a sanctioned path that was missing or bypassed so the gap is fixed, and it is triaged like any other finding.
* *Structured Reviewer Identity*: `author` and `bot_kind` come from the provider's structured author field, never from comment text. A comment whose structured author and self-declared bot identity disagree is itself filed as a finding with the provider's `source`. A comment's identity is `(bot_kind, provider_ref.comment_id)` plus `edit_marker`; an edited comment is new information.
* *Server-Written Resolution*: The model submits only `disposition` (`FIX`, `SUPPRESS`, `ACCEPT`); the triage link grammar has no resolution parameter. The server writes `resolution` from recorded evidence, so a refuted claim, a valid finding that was dismissed, and a finding that is not this plan's concern stay distinguishable:
+
[cols="1,3,1"]
|===
|Disposition |Recorded condition |`resolution`

|— |Finding created, or triaged but its effect not yet recorded |`pending`
|`FIX` |The fix landed: its fix task passed server verification, or the in-branch settle commit covering the fix's `population` is recorded |`fixed`
|`SUPPRESS` |`evidence.claim_refuted == true`: the `ext-point-verify` refutation sub-state refuted the claim (`evidence.class: verifier`), or, when that sub-state is unavailable, substitute evidence with a concrete `evidence.ref` (file:line, job id, or URL) |`rejected`
|`SUPPRESS` |Otherwise (the finding is valid but dismissed) |`suppressed`
|`ACCEPT` |`scope_class == out_of_footprint` (pre-existing or another owner's code), or the triage cites a standing decision of the plan (an `amendments[]` entry or an ADR id that the server resolves) |`taken_into_account`
|`ACCEPT` |Otherwise (a known, accepted gap) |`accepted`
|— |Stale re-anchor: the finding's cited location no longer exists at `HEAD` (link:phase-workflows.adoc[Phase Workflows Specification], Step Records, Re-Fire & Loop-Back Rules) |`taken_into_account`
|===
+
`scope_class` is computed by the server at triage from `file_path` against the plan's effective footprint (`declared_files ∪ approved_widening[].path ∪ realized_files`, <<three-way-footprint>>). An operator triage decision (operator CLI or elicitation) may record any terminal resolution directly, with `evidence.class: operator`. `pending` is the only non-terminal resolution: the Blocking Findings Guard and the pre-merge barrier count it, and a `FIX` whose fix has not landed is still `pending`. Every report and landing figure over findings is keyed by `resolution` with every member tallied (stated zeros); the false-positive count of a source is its `rejected` count and never includes `suppressed`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` lets the model choose one of the six resolutions directly; `PM-MCP` keeps the three model dispositions and derives the six-value resolution from evidence the server holds.
* *Evidence Symmetry*: A resolution rests on evidence of the same kind whichever way it goes: `rejected` requires a concrete `evidence.ref` as a `FIX` requires a landed change, and a disposition that lowers severity cites an executed check.
* *Re-Disposition of a Transmitted Finding*: A finding whose `transmit_outcome` is `sent` may be re-dispositioned only together with a new `reply_text`; the server then resets `transmit_outcome` to `pending`, re-derives `resolution`, and transmits again. A bare re-disposition (same or no reply) is refused with `invalid_link_args`.
* *Late Findings Are Carried Out*: After the merge gate (order `> 70`) no step refuses on findings. A blocking finding still `pending` after the merge (filed after the barrier evaluated) is carried out by the server: appended to the parent epic inbox as a `process_finding` message, or, for a plan without an epic, seeded as a lesson (category `bug`, title from `summary`, body from `body`); while the epic linkage is `indeterminate` the message is kept with the undelivered landing envelope and delivered with it. The finding is set to status `carried` with `carried_to`; its `resolution` stays `pending`, so the carried debt remains visible (link:phase-workflows.adoc[Phase Workflows Specification], rows `1000` and `1100`).
* *Transmit Reasons*: `transmit_reason` is one closed vocabulary shared by every provider: `no_provider_address` (no thread, comment id, or Sonar issue key to answer on), `pr_number_unrecorded` and `belongs_to_other_pr` (the finding cannot be shown to belong to this pull request; deferred, never dropped), `nothing_to_transmit` (the disposition carries no reply), `reply_failed` and `resolve_failed` (the provider call for the reply or for the thread resolution failed), `provider_unreachable`, and `provider_rejected`. Provider error text is never packed into the reason. *Deliberate change vs. `plan-marshall`*: the GitHub, GitLab, and Sonar integrations each report their own free-text skip reasons (`no_resolution_detail`, `no thread_id or resolution_detail`, `no issue key in detail`, `thread-reply failed: <error>`; verified at `plan-marshall` `b1a9a89fa`), so one condition has three spellings.
* *Transmission and Resolution Are Separate*: Before the provider call the server persists `transmit_outcome: pending` with the `transmit_disposition` it sends. `responded_at` is stamped after the provider accepted the reply and before the thread is resolved; `resolve_state` is persisted separately, so a resolve-only retry never re-sends the reply. After a crash, a `pending` transmission is reconciled by looking up the reply on the provider before any re-send.

* *Assessments Are Inputs, Never Back-Filled*: The server stamps `recorded_at` when it appends the record. A gate or coverage check that consumes assessments reads only records whose `recorded_at` is earlier than its own evaluation start and refuses those written after it; an empty assessment population is reported as a gap, and no link writes placeholder assessments.
* *Append-Only Supersession*: A line is never rewritten. A superseding record names the record it replaces in `supersedes`; the superseded record's validity window is `[effective_from, effective_from of the superseding record)`. Superseded assessments stay readable, never live.
* *Widening Supersedes*: An accepted scope deviation (`approved_widening`, <<three-way-footprint>>) or an outline revision that changes a deliverable's footprint appends superseding assessments for the affected components.
* *Grading Against the Judgement in Force*: A consumer that grades a recorded action against an assessment uses the assessment whose window contains the action's timestamp. A write to a path whose live assessment is `exclude` is `violated_live_exclusion`; a write admitted by a later approved widening is `superseded_by_approved_widening`, not a violation.

* *Store-Assigned Identity*: The store allocates `message_id` as the next number above the highest ever written in that file, including ids of lines it cannot parse; an id is never reused, and a caller never supplies one. A `claimed`, `processed`, `consumed`, or `annotation` event for an unknown or already-folded-terminal message is refused.
* *Fold*: Inbox messages fold to `pending` (only `message`), `claimed`, or `processed`; mailbox messages fold to `unconsumed` or `consumed`, or `unknown` when a referencing line is unreadable. The empty states (`no_file`, `empty_file`, `all_processed`) and `unreadable` (with the failing line) are distinct and never read as each other.
* *Writers*: Inbox events are appended under the epic lock in the shared epic worktree copy (link:filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification]); mailbox events under the plan lock in the plan directory, which never moves except on archival, when it carries the mailbox with it. The mailbox is covered by the plan's store digests (`mcp/digests.json`, <<store-digest-verification>>), so an out-of-band edit is detected; the git-tracked inbox is protected by its git history.
* *Read Scope*: The epic scope reads all inbox messages; a plan scope reads only the inbox messages whose `sender` is itself, and only its own mailbox.

[#metrics-store]
== Metrics Store (`metrics.json`)
_Implementation watch: link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-26[PM-WATCH-STORE-26], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-35[PM-WATCH-STORE-35]_

The plan's `metrics.json` holds the dispatch and phase measurements that `default:record-metrics` aggregates (`PM-WF-14`, link:dispatch-and-effort.adoc[Dispatch & Effort Specification], Post-Return Integrity Invariants). It extends the rule "unmeasured is never `0`" from token usage to every figure it publishes.

* *Rows*: One row per dispatch (`dispatch_id`, `phase`, `step_id` or null, `envelope_id` or null with its summed `predicted_cost_tokens` and their basis (`uncalibrated` or `calibrated`), `lifecycle_state` (link:dispatch-and-effort.adoc#_dispatch_id_generation_lifecycle_states[Dispatch & Effort Specification, Lifecycle States]), `status`, `cause_class`, `spend_class`, `population`, the usage columns of the `returned:<dispatch_id>` link (`token_usage`, `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `tool_uses`), each a measured integer, `"unmeasured"` (with `not_reported_by_client` where the client profile cannot report it), or, for a step that runs inline by design, `"inline"`, and the server-measured `duration_ms` with its `duration_basis`), one row per wait slice (`phase`, `wait_reason`, `deliberate`, duration; link:job-runtime.adoc[Job Runtime Specification], Wait Attribution), one row per phase close (`start_time`, `end_time`, `duration_ms`, `duration_clamped`, `boundary` (`closed`, `re_entered`, or `provisional` with `measured_until` and `excluded_steps`), `step_firings` as a map from step id to firing count), and one row per served document read (Served-Content Ledger below).
* *Served-Content Ledger*: Every `pm_skill`, `pm_skill_file`, and skill `resources/read` served in a plan or epic scope appends `{uri, section?, bytes, plan_id, phase, dispatch_id?, served_at}`; `bytes` is the rendered size served, `0` for an empty section. `dispatch_id` is set when the read carries it (the server renders it into the load directives of a dispatch prompt) and is otherwise null. A read without a scope is attributed to no plan. `record-metrics` publishes from these rows the per-document consumption (reads per URI and section, bytes, repeat reads within one dispatch). It measures only what the server serves; host `Read`/`Grep` of files is not observable.
* *Aggregates*: Every sum (per phase, per cause class, per plan) is published as `{value?, rows, rows_unmeasured, population_count, excluded{<class>: count}}` with `rows = measured + Σ excluded`. `value` is omitted when `population_count == 0`. A phase that is still open is reported as a floor, never as a total; Phase 6, which `record-metrics` measures from inside, is recorded `boundary: provisional` with `measured_until` and its `excluded_steps`.
* *Populations*: Every token figure carries a `population` stamp (`dispatched` or `main_context`); an absent stamp reads `dispatched`. Relations (`=`, `<`, `>`) and sums are formed only between figures of one population. A derived ratio whose denominator population is empty is `not_derivable`, never `0`.
* *Re-Entry*: Re-entry is derived from observables (rows timestamped after the phase's recorded `end_time`), never from a close counter. A re-entered phase is labelled `re_entered` and accumulates across closes.
* *Cause Classes*: `cause_class` (`terminal_error`, `retryable`, `returned_with_findings`, `benign`, `stall`, `unconfirmed`) is a total function over the dispatch `status` enum plus `INCOMPLETE_SUBMISSION` and `UNCONFIRMED` (class `unconfirmed`: no observable host reaction, link:dispatch-and-effort.adoc#cause-class[Dispatch & Effort Specification, Cause Classes]), and the per-class populations sum to the total dispatch population with an asserted residual of `0`; the build-time exhaustiveness check (`PM-IMPL-5`) fails on an unclassified member. A spend decomposition sums to the phase total, with an explicit `unbucketed` class.
* *Spend Classes*: `spend_class` (`submitted`, `findings_only`, `no_product`, `unmeasured`) is derived by the server from what the dispatch produced (link:dispatch-and-effort.adoc#spend-accounting-budget-anchors[Dispatch & Effort Specification, Spend Classes]); it is a separate dimension from `status` and `cause_class`, and waste is read only from `no_product`.
* *Stall Rate*: A termination with `tasks_remaining > 0` and no blocked cause is `stall`. The stall rate and the `yield_reason` counts are published per plan.
* *Ledger Divergence*: Where two ledgers can diverge (dispatch rows vs audit rows), `record-metrics` publishes `union_rows` and a non-blocking `reconciliation{findings_count}` warning. Each ledger states its counting unit.
* *One Writer per Name*: Every metric name has exactly one writer. A second producer over another population uses a different name.
* *Raw Components Only*: Rows persist measured token components, never a weighted or priced figure. `priced_units` is derived in views from the rows and one named constant table (link:phase-workflows.adoc#post-run-metrics-and-landing[Phase Workflows Specification, Metric Aggregates]); a change of the weights re-derives every figure, including legacy baselines, from the persisted components.
* *Session Attribution*: A dispatch row references the host session that rendered the dispatch by its `client_session_id` (the row of the scope's session log, <<scope-session-log>>; `null` when the host provides none), never by a copy of the client or model identity.

Aggregates are never persisted; they are derived in views from `rows[]`.

*Task Status*: `pending` (not yet dispatched), `in_progress` (yielded to a dispatched sub-agent), and `blocked` (a submitted scope deviation awaits the operator's decision) are open; a task whose dependencies are not yet satisfied stays `pending`. `completed`, `skipped`, `infeasible`, and `removed` are terminal:

* `completed`: the server's independent verification of `submit:TASK-NNN` passed (link:phase-workflows.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification]).
* `skipped`: set by the operator only, with a recorded reason (`disposition.by: operator`); never offered to the model.
* `infeasible`: set by the sub-agent's `infeasible:TASK-NNN` with its evidence (`disposition.by: sub_agent`, `disposition.evidence`).
* `removed`: the task's deliverable was removed by the outline gate, by a `split`, or by the operator after an `infeasible` (`disposition.by` names which).

A task in `skipped`, `infeasible`, or `removed` carries a non-null `disposition`; a task in any other status carries none. Step status is `pending`, `completed`, `skipped`, or `failed`.

*Dependencies (`depends_on`)*: Phase 4 writes the task graph into `depends_on` (link:phase-workflows.adoc#_deterministic_task_derivation_dag_cycle_detection[Phase Workflows Specification]). At every task creation or amendment the server checks that every referenced task exists in the plan and that the graph stays acyclic; otherwise the write is refused (`invalid_link_args`, `detail` `task_dependency_unresolved` or `task_dependency_cycle`, naming the tasks) and no task file is written. A dependency is satisfied only by a task in status `completed` or `skipped`.

A deliverable may declare several verification command and criterion pairs; the task carries them all in `verification`. A task with profile `implementation`, `module_testing`, or `integration_testing` requires at least one command and at least one criterion. An empty or truncated criterion rejects task creation; it is never downgraded to a warning.

Configuration is split by owner class (link:domain-extensions.adoc#config-split[Domain Extensions Specification, Configuration Split]): four git-tracked *team* files and the project-owned workflow units under `.marshall/config/`, one machine-local *operator* file per project (<<local-config>>), and the machine-wide operator defaults `project_defaults` of `machine-config.json` (<<machine-config>>). No file mixes owner classes and no key exists in two owner classes. Binary versions, fingerprints, migration ledgers, and "offered" lists never land in a team file. `PM-MCP` never reads a legacy `.plan/marshal.json` and imports nothing from it (`PM-MIG-2`); the project setup workflow creates `.marshall/config/` on its first run.

[cols="2,1,2,3"]
|===
|File |Owner |Writer |Content

|`.marshall/config/project.json`
|team
|project-setup links (validated), committed edits
|Repository and collaboration policy: base branch, branch prefix, the `merge_method` and `ci_provider` overrides, integrations (Sonar coordinates), review bots, the project's review-bot registry records, review currency.

|`.marshall/config/workflow.json`
|team
|project-setup links, committed edits
|Plan workflow policy: minimum planning lane, refine compatibility and simplicity, per-deliverable verification verbs and final verification, lane and parameters of optional finalize steps, project finalize step descriptors, target-neutral effort levels.

|`.marshall/config/domains.json`
|team
|project-setup links, committed edits
|Overrides of the derived domain detection: forced enable or disable, `always_on`, `file_globs`, disabled profiles.

|`.marshall/config/build-map.json`
|team
|`setup.seed-build-map` (write-once), `customize_routes`, `setup.reseed-build-map`, committed edits
|The file-to-build route table (link:domain-extensions.adoc#_build_map_deterministic_derive_verification_adr_004[Domain Extensions Specification, Build Map]); seeded, not sparse.

|`.marshall/config/*.pmwf`
|team
|`setup.prepare-workspace` (copy of the binary's default units), `setup.offer-new-steps` (adopted default changes), committed edits
|The project-owned phase workflow and sub-workflow units, verified on every load against the compiled invariants (link:workflow-dsl.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]).

|`<PM_MCP_BASE>/projects/<project_id>/local-config.json`
|operator
|`pm-mcp operator config --project <project_id>`, operator-channel links (elicitation) of the setup workflow
|Operator posture and machine-local bindings of one project (<<local-config>>); replaces the former `effort-ladder.json` and `run-configuration.json`.
|===

. *Sparse Files*: A team file and `local-config.json` hold only deviations from the effective default; an absent file means "no deviation" (except `build-map.json`, whose absence is `build_map_unseeded`). There is no default seeding into files, no default sync, no key sorting, and no key normalization: a new compiled default reaches every project with the binary, while in-flight plans stay protected by the manifest snapshot (item 6). A key whose value equals the effective default without it is reported as the advisory finding `redundant_config_key`.
. *Version*: Every JSON configuration file carries `format_version` and is accepted only at the binary's current version (<<format-versioning>>); an outdated or newer team file refuses the project's `pm_start` and phase handshakes with `format_outdated` or `format_newer` naming the file, and is never rewritten by a reader.
. *Closed Schemas, Validated on Every Read*: The schemas below are closed at every level (`additionalProperties: false`). Every computation of the effective configuration validates the files against them and against the server-side rules named in their descriptions. An undeclared key is the finding `unknown_config_key` naming the file and JSON pointer, never a silently kept setting; a setup or configuration link that would write an undeclared key is refused (`invalid_link_args`). A team file or workflow unit that fails validation is a verification finding in the workspace scope and refuses the project's `pm_start` and phase handshakes with `config_invalid` naming the file and pointer (for a workflow unit: file and line); an operator file that fails validation is reported with source `invalid` and never folded into the defaults. A non-object root fails before any field access.
. *Effective Configuration and Sources*: The server computes the effective configuration; neither the model nor the operator reads raw files. A team key resolves *team file → derived value (<<derived-facts>>) → compiled default*; an operator key resolves *`local-config.json` → `machine-config.json` `project_defaults` → compiled default*; no key is resolvable from both chains. Every effective value carries its `source`: `compiled_default`, `derived`, `team`, or `operator` (with the file for `team` and `operator`, and the fact `state` for `derived`). The effective key of a value is `<file_stem>.<dotted path>` (for example `project.review.currency`, `workflow.plan.phase-2-refine.compatibility`, `local-config.continuation.default_policy`, `derived.push_remote`); workflow guards name configuration keys in this form (`depends_on_config`, link:workflow-dsl.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification]).
. *Published View*: The effective configuration is served as the read-only resource `pm://project/config` (link:mcp-tools.adoc#_normative_resource_uri_templates[MCP Tools Specification]): `config_hash`; `entries[]` of `{key, value, source, file?, fact_state?}`; `units[]` of `{unit, file, digest, origin: default|project, default_revision, verification: verified|refused, findings[]}`; and `findings[]` (every validation finding with file, pointer or line, and reason).
. *Snapshot of In-Flight Plans (`config_hash`)*: `config_hash` is the SHA-256 over the canonical serialization of the effective configuration: every effective value with its source, the digests of the process DSL units the project loads (<<project-configuration-store>> row `*.pmwf`), the derived facts the values rest on (value and `input_digest`), the team files, the operator file, and the digest of the compiled defaults. It is never computed over raw file bytes alone, so a binary upgrade that changes a default, a changed derived fact, or an edited workflow unit changes it. The execution manifest records it in `composed_inputs.config_hash`; a difference at a phase handshake raises `config_drift` (`adopt` / `keep`, link:phase-workflows.adoc#_planning_transition_guards_real_world_invariants[Phase Workflows Specification, Outside-World Invariants]).

The pinned compiled defaults (for example the review rate-window values) live in the compiled default table that every effective-configuration computation starts from; a test pins that table (`PM-WATCH-STORE-13`).

[#derived-facts]
== Derived Facts Store (`<PM_MCP_BASE>/projects/<project_id>/derived-facts.json`)

A value the server can observe is derived, never configured; an override exists only where a derivation input can be ambiguous (`project.json` `ci_provider` and `merge_method`, `domains.json`, `local-config.json` `envelope_budget_tokens`). The derived values are cached in one per-project store of owner class *cache*: deleting it only forces re-derivation. The store is written under the workspace lock.

* *Local derivations* (inputs read from the repository or the machine) are recomputed whenever their `input_digest` (SHA-256 over the canonical derivation inputs) changes.
* *Network derivations* (inputs read from a provider) hold for the validity period of link:timeouts.adoc#network-derivation-validity[Timeouts & Budgets Specification, Network Derivation Validity] and are additionally refreshed by the project-setup reconcile and by `pm-mcp enter`.
* *Failure*: A failed derivation keeps the last value with `state: stale` (or `failed` when no value was ever derived) and records `failure`; every gate or guard that depends on a `stale` or `failed` fact evaluates `indeterminate` (`COULD_NOT_EVALUATE`, the `guard_indeterminate` condition), never pass.
* *Fact kinds* are a closed enumeration open for registration: a new kind is added to `kind` below and to the kind table together with its value schema, its class, and its inputs. The git/GitHub/GitLab-specific derivation mechanics (`merge_methods_allowed`, `merge_queue_enforced`, the CI provider detection) are part of the open git/GitHub/GitLab design topic.

[#lesson-record]
== Lesson Record (project lesson store)
_Implementation watch: link:../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-4[PM-WATCH-CLI-4], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-14[PM-WATCH-STORE-14], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-15[PM-WATCH-STORE-15], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-16[PM-WATCH-STORE-16], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-17[PM-WATCH-STORE-17], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-18[PM-WATCH-STORE-18], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-19[PM-WATCH-STORE-19], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-20[PM-WATCH-STORE-20], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-34[PM-WATCH-STORE-34]_

Lessons live in the project's lesson store in the per-project machine store and outlive the plans that create them. Each lesson is one Markdown file: YAML front matter carrying the fields below, followed by its Markdown body. The narrative stays Markdown text (`PM-IMPL-2`); only the front matter is structured. The lesson `submit` transition (link:phase-workflows.adoc[Phase Workflows Specification], Lesson Creation & Body) writes both atomically. The store is a Ported store (`PM-TEST-1`; its legacy mapping lives in test code only, `PM-TEST-2`).

* *Placement*: The store is `<PM_MCP_BASE>/projects/<project_id>/lessons/` (link:filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]): machine-local, outside the repository, resolved identically from the main checkout and every worktree, one file `<lesson_id>.md` per lesson and the lesson-store digest sidecar `.digests.json`. A lesson file is never moved and never deleted by a lifecycle transition: applying a lesson claims it, and retiring it records the retirement in its front matter. Legacy lessons never enter it: `PM-MCP` never reads the project's legacy `.plan/local/lessons-learned/` (`PM-MIG-2`), and every project starts with an empty lesson store. A lesson therefore stays on the machine that recorded it; a second machine or clone does not see it. This trade-off is accepted: lessons reach other machines only through their promotion destinations (`promotions[]`).
* *Lock*: Lesson id allocation and every write, claim, release, or retirement in the lesson store run under the lesson store lock `locks/lessons.lock` of the per-project machine store (<<lock-free-snapshot-reads>>), each as one journaled transaction (<<transaction-journal>>), so two concurrent sessions never allocate the same `lesson_id` and never claim the same lesson.
* *File Format*: A lesson file starts with a line `---`, followed by the front matter, a line `---`, and the Markdown body. The front matter is YAML restricted to the JSON data model (YAML 1.2 core schema; anchors, aliases, tags, and multiple documents are refused) and is validated against the `LessonFrontMatter` schema below, including `format_version`, on every read and write; a write with missing or invalid front matter is rejected, and a file without parseable front matter lists as `present_unreadable`. The body is free Markdown; the `title` lives only in the front matter.
* *Revisions*: A change of the body replaces it wholesale and increments `revision`; the new body carries its own `sources[]` (the evidence it was regenerated from), and `revisions[]` appends `{n, at, sources, body_sha256}` for the new revision. Old bodies are not kept; `revisions[]` keeps their digests and sources, so the derivation of every revision stays stated. A body is never edited in part (`PM-WATCH-STORE-17`).
* *Lesson-Store Digest*: Every server write, claim, release, or retirement in the lesson store records the size and SHA-256 of the lesson file in `.digests.json` (the sidecar format of <<store-digest-verification>>) in the same transaction as the lesson write. On read, a lesson whose file differs from its entry is `store_tampered` for that lesson only; a lesson file that disappeared while its entry remains is reported as `deleted_out_of_band`, and a file without an entry is reported as `untracked`. None of these states is ever read as `absent`, and an out-of-band edit is accepted only with `pm-mcp operator accept-edit`, which re-baselines that lesson's entry and records the action in `audit.jsonl`.

* *One Resolver, Four States*: Listing and lookup use one resolver over the lesson store. Every listed lesson resolves by the exact id it is listed under to one of `found`, `absent`, `present_unreadable` (front matter missing or invalid; listed with its path, never omitted), or `empty_shell` (valid front matter, empty body). `present_unreadable` is never reported as `absent`, and `empty_shell` is never a content verdict. A lesson write without valid front matter is rejected.
* *Lifecycle*: `status` is `active`, `upstream_pending`, or `retired`; the lifecycle is binary (live or retired) and carries no moving confidence value, mirroring `plan-marshall`. Whether a lesson is being applied is its `claim`, never the location of its file.
* *Claim*: `pm_start` with source `lesson` claims the lesson in the plan initialization transaction (plan lock, then lesson store lock): it sets `claim{plan_id, claimed_at}`; a lesson that is already claimed, retired, or not resolved `found` is refused (`lesson_unavailable`, naming the state and, for a claim, the claiming plan). The claim ends with the plan: when the plan reaches `completed` with a merge, the lesson is retired with verdict `applied` (`by`: the `plan_id`); when the plan closes the lesson as obsolete (`init.lesson-premise` `close`), with verdict `obsolete`; when the plan is aborted or deleted (`delete-plan`), the claim is released (`claim: null`) and the lesson stays `active`. A claim whose plan is terminal, archived, or no longer resolvable while the claim is still set is a *stale claim*: listed as such (the `stalled_lessons` harvester population), never released without one of the above events or an operator action.
* *arch-constraint Recurrence*: An add whose `rule` matches an active `arch-constraint` lesson reinforces it (increments `recurrence_count`, refreshes `last_seen`) instead of allocating a new lesson. A quiet-window retirement retires every active `arch-constraint` lesson whose `last_seen` is older than the window (`retention.arch_constraint_quiet_days` of the operator's `local-config.json`, link:timeouts.adoc#retention-days[Timeouts & Budgets Specification]).
* *Retirement*: A retirement (supersede, remove, quiet-window retirement, or the end of a claim) sets `retired{at, by, verdict, reason, …}` and `status: retired` in the front matter in one transaction; the file stays in place, so no separate tombstone exists. Every retirement other than the claim outcomes requires a `verdict` from the closed set, with no default. `completely_covered` also requires `covering_clause` and a concrete `covering_input` that the clause's worked example resolves; a whitespace-only value counts as missing. A retirement acts only on a lesson resolved `found`, or on a `present_unreadable` lesson through an explicit operator action, which replaces the unparseable front matter by a minimal valid one (`lesson_id` from the file name, `title` and `component` `unknown`, `retired.lesson_state: present_unreadable`) and keeps the original file bytes as the body; in every other state it changes nothing and reports the state. Retention purges only the body of a retired lesson after `superseded_lessons_days` and keeps its front matter.
* *No Bulk Mutation*: The lesson store is never wiped or bulk-mutated; no bulk-mutation verb exists. A removal answering `absent` is not proof that the lesson never existed and is never retried automatically; it is reported together with the store-resolution discriminator.
* *Version Provenance*: The runtime stamps `tool_version` from its own release version (`PM-DIST-1`) at creation; it is never a `submit` parameter. An operator override is stored in `tool_version_override` beside the stamped value.
* *Provenance*: Every new lesson records `provenance` (`run_artifact`, `tool_return`, or `operator_decision`); the server sets it where the creating transition determines it (a `split` deviation lesson is `operator_decision`, a recurring-exemption lesson of `lessons-capture` is `run_artifact`) and otherwise requires it as a `submit` parameter.
* *Audience Classification*: A lesson's `audience` is `upstream` iff its `component` names a component shipped by the `pm-mcp` distribution (a built-in skill, recipe, or finalize-step identifier from the compiled-in catalogue); every other component, including a project-prefixed one (`api-sheriff:maven-build`) and one without a bundle prefix (`integration-tests`), is `local`. The classification never inspects the repository layout. An operator override of the classification is persisted on the lesson in `audience_override` in addition to its audit record, so a lesson admitted by an override is never indistinguishable from a classified one. *Deliberate change vs. `plan-marshall`*: `manage-lessons add` decides ownership by the existence of `marketplace/bundles/{prefix}`, which misfiles a consumer's own prefixed component as foreign.
* *Upstream Release (`PM-ARCH-2`)*: An `upstream` lesson is created `upstream_pending` and stays in the local store; nothing transmits it automatically. It leaves the workstation only through the operator action `pm-mcp operator lesson release --lesson <lesson_id>`, which renders the issue body for review and either hands it to the operator to file or, on the operator's explicit confirmation, runs a filing job through the enrolled CI provider. A `local` lesson is never offered this action; naming one is refused with `audience_mismatch`, which states the lesson's audience and leaves it unchanged. A successful filing records the issue in `promotions[]` (`kind: issue`) and returns the lesson to `active`.
** *Rendering*: The issue body is rendered from the stored record only: body, `component`, producing `plan_id`, and the recorded `tool_version`, never values sampled at filing time.
** *Duplicates*: Duplicate detection keys on (`component`, normalized `rule`) for `arch-constraint` lessons and on (`component`, normalized `title`) for every other category, never on `component` alone (two lessons on the same component are usually different defects); a `no_duplicate` verdict carries the compared population (count and ids).
** *Loud, Lossless Failure*: A failed filing leaves the lesson `upstream_pending` with `last_filing_failure` (`offline`, `forbidden`, `rate_limited`, or `refused`) and the unchanged content; it never falls back to `local`.
** *Corpus Routing Campaign*: A routing run over an existing lesson corpus (the `lesson-cleanup` recipe) records one disposition per lesson (`routed`, `reclassified`, or `retired` through the in-file retirement with its mandatory `reason` and `verdict`, *Retirement*); re-running on unchanged input is a no-op keyed on the duplicate key (*Duplicates*); when the population differs between derivation and action, the run reports the delta (added and removed ids) and never adopts it silently.
* *Promotion Provenance*: `promotions[]` records every destination that absorbed the lesson. A routing sweep or the `lesson-cleanup` harvester reports a lesson with a matching destination as `already_promoted` and never routes it again as new.

[#enrolment-store]
== Project Enrolment Store (`<PM_MCP_BASE>/enrolments/<project_id>.json`)

One file per enrolled project, `<PM_MCP_BASE>/enrolments/<project_id>.json`, holding the operator-authorized project root, build wrappers with their pinned files, pinned host tools, the canonical and discovery command templates, provider verification overrides, language servers, approved out-of-process project scripts, operator budgets, the Landlock write paths, and the captured build environment (`PM-EXEC-2`, `PM-EXEC-3`, `PM-EXT-5`, `PM-EXT-6`). Written exclusively via the operator channel (`pm-mcp operator enrol`, link:cli-and-security.adoc#enrolment-lifecycle-release[CLI, Coordination & Security Specification]). The set of enrolled projects is the directory listing; the operator-owned `enrolments/` directory is separate from the server-owned `projects/`.

* *Integrity*: Every operator CLI write of an enrolment file runs under its own lock `<PM_MCP_BASE>/locks/enrolments/<project_id>.lock` and also writes its sidecar `<PM_MCP_BASE>/enrolments/<project_id>.json.hmac`, the lowercase-hex HMAC-SHA-256 over the exact bytes of the canonical file the CLI wrote, keyed with the operator-lane secret from the OS keyring (service `de.cuioss.pm-mcp`; on hosts without a keyring `<PM_MCP_BASE>/state/enrolment-hmac.key`, mode `0600`). The runtime verifies a project's file before serving the project for the first time after start and before every verify-not-resolve check, and refuses with `enrolment_tampered` on mismatch (link:cli-and-security.adoc#enrolment-integrity[CLI, Coordination & Security Specification, Enrolment Integrity]).
* *Isolation*: A tampered, unreadable, or schema-invalid enrolment file blocks only its own project; every other project is served. `project_root` is unique across all enrolment files; the operator CLI checks it at every enrolment write and the runtime at start, and a duplicate root blocks both projects with `enrolment_root_conflict` until the operator resolves it.
* *Closed and Exact*: The schema is closed at every level (`additionalProperties: false`), and a file whose `format_version` is not the binary's is refused (`format_outdated` or `format_newer`, naming the file, <<format-versioning>>).
* *Templates Decide What Runs*: A build job runs the canonical template of its build system and verb (`build.canonical_templates`), or the compiled default when none is enrolled; there is no goal allowlist per wrapper. Typed placeholders (`{module}`, `{profile}`) are validated at job time (link:domain-extensions.adoc#enrolled-argument-templates[Domain Extensions Specification, Tier 2]).

[#credential-store]
=== Permission-Guarded Credential Store (`<PM_MCP_BASE>/credentials/<credential_key>.json`, `PM-CRED-3`)

When OS keychain access (service `de.cuioss.pm-mcp`) is unavailable (e.g., headless Linux SSH session), Token-Lane credentials fall back to user-only `0600` JSON files inside `<PM_MCP_BASE>/credentials/` (`0700` directory; only `PM_MCP_BASE` relocates it). The file format is `PM-MCP`'s own, with `format_version` and a closed schema (<<format-versioning>>); the naming keeps the project-scoped tier `<PM_MCP_BASE>/credentials/<project>/<credential_key>.json`, which is resolved before the global file, and files are named by credential key (the provider skill name without bundle prefix, `PM-CRED-1`). A credential file is written only by `pm-mcp operator credentials` (the secret read from the terminal with echo disabled, the file written atomically with mode `0600`); it is never a template for hand editing. A file with a missing or different `format_version`, an undeclared field, or a field its `auth_type` does not allow is refused with a reason naming the file and the field, and blocks only the step that needs the credential (`credentials_file_invalid`, with the `pm-mcp operator credentials set` command that rewrites it). `PM-MCP` never reads `~/.plan-marshall/credentials/`, `PLAN_MARSHALL_CREDENTIALS_DIR`, or legacy keyring entries (`PM-MIG-2`); credentials enter this store only through `pm-mcp operator credentials`.

The allowed origin for a credential is the origin of the `url` of its operator-owned entry (`PM-CRED-5`); the team configuration (`.marshall/config/project.json` `integrations`) may only reference a credential key and never decides where a token is sent.

[#machine-lease-stores]
== Machine Lease Stores (`merge-queue.json`, `review-bot-windows.json`, `build-slots.json`)
_Implementation watch: link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-37[PM-WATCH-STORE-37]_

The three lease stores in `<PM_MCP_BASE>/state/` are updated only in short transactions under their machine store locks (<<lock-free-snapshot-reads>>; `PM-IMPL-7`, `PM-WF-15`). Every lease owner has the same shape, and every instant follows the one wire shape (<<format-versioning>> item 5), so a lease written by one component and reclaimed by another round-trips byte-identical instants.

*Ownership vs Liveness*: A lease is owned by its scope (`scope_type`, `scope_id`), never by the runtime instance; `holder_instance` records only which runtime currently serves it. At runtime start, a lease whose `holder_instance` is no longer alive (PID plus start instant) is not released but marked `orphaned_at`; the next call addressing the owning scope adopts it (sets `holder_instance` to the new runtime, clears `orphaned_at`) under the machine store lock. An orphaned lease is released only on positive evidence of abandonment: the owning scope is terminal, archived, or no longer resolvable; its `lease_expires_at` passed without adoption; or, for a build slot, its job was recorded as `killed` at the restart (a build slot is therefore released at once). Provider-side evidence for the merge holder (the observed state of the provider's merge queue) is part of the open git/GitHub/GitLab design topic.

== Data Layer Integrity & Concurrency Invariants (`PM-IMPL-7`)

[#store-digest-verification]
=== Store Digest Verification Against Out-of-Band Edits

[[_store_digest_verification_against_out_of_band_edits]]
The stores reside in the per-project machine store (link:filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), outside the repository working tree and behind the host deny rules for `<PM_MCP_BASE>/**`, so an out-of-band edit is no longer a working-tree accident; a host shell with filesystem write access can still modify them directly outside the MCP server:

* Digests live in the sidecar `mcp/digests.json` (`{"format_version": 1, "stores": {"<relative path>": {"size": <int>, "sha256": "<hex>"}}}`), never inside a store they protect.
* On every server write to a plan store (`mcp/status.json`, `references.json`, `TASK-*.json`, `execution-manifest.json`, `metrics.json`, `quality-report.json`, the findings, assessment, review-participation, and change-ledger JSONL files, the plan mailbox `mcp/mailbox.jsonl`, the session log `sessions.jsonl`, `outline.md`, `request.md`), the server records the file's size and SHA-256 in the sidecar under the plan lock; the workspace scope's stores (`mcp/status.json`, `sessions.jsonl`, the findings and change-ledger JSONL files) are recorded the same way in `workspace/mcp/digests.json` under the workspace lock, and an epic scope's stores in `epics/<epic_id>/digests.json` under the epic lock.
* The digest of a store is updated in the same transaction as the store write, and only through the transaction journal (<<transaction-journal>>): a transaction that fails part-way leaves its journal, which recovery rolls forward (runtime start, and lazily on the first call to the scope) before any digest is compared. A store whose content differs from its sidecar entry while a journal of its scope lists it is never reported as tampered; recovery completes the transaction first.
* On every subsequent read inside a transition, the engine verifies size and SHA-256 against the sidecar. `store_tampered` is decided only by a reader that holds the store's scope lock, after journal recovery: any remaining mismatch immediately raises the `store_tampered` condition on the scope's current state (link:state-catalogue.adoc#condition-store_tampered[State Catalogue, Conditions]), which replaces any other condition, leaves `state` and `call_stack` unchanged, and requires operator resolution.
* A lock-free snapshot reader (<<lock-free-snapshot-reads>>) that sees a digest mismatch, or a transaction journal, may observe a transaction in flight. It never reports `store_tampered`; it serves the snapshot with `facts.store_integrity: digest_unverified` naming the store, and the next locked access of the scope decides.
* An intentional manual edit is accepted with `pm-mcp operator accept-edit <plan_id> <store>`, which re-baselines that store's digest and records the action in `audit.jsonl`.
* The project's lesson store keeps its own sidecar with the same format and rules, at lesson granularity (<<lesson-record>>): an out-of-band edit or deletion of one lesson blocks only that lesson.

[#three-way-footprint]
=== Three-Way File Footprint Reconciliation (`references.json`)
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-19[PM-WATCH-PHASE-19], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-21[PM-WATCH-STORE-21], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-22[PM-WATCH-STORE-22], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-23[PM-WATCH-STORE-23], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-24[PM-WATCH-STORE-24], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-33[PM-WATCH-STORE-33], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-36[PM-WATCH-STORE-36]_

[[_three_way_file_footprint_reconciliation_references_json]]
The `references.json` store tracks three distinct file-footprint sets for a plan:

* *Declared Footprint (`declared_files`)*: Files explicitly listed during refinement/outline. `declared_files` is immutable after `outline.review` approval. A path admitted later by an accepted scope deviation is recorded in `approved_widening[]` with its provenance (deviation task, `approved_via`, phase, time), never appended to `declared_files`. The effective declaration is `declared_files ∪ approved_widening[].path`, and every reconciliation result names which of the two admitted a path.
* *Structured-Derived Footprint (`derived_files`)*: Re-derived by set union over the solution outline's structured deliverables and partitioned into two disjoint keys:
** `expected_modifications`: Files the plan intends to create, modify, or delete.
** `conditional_modifications`: Files declared `(write-conditional)`, edited only if a named gate fires.
** `read_only_references`: Files inspected for context that must remain unmodified.
* *Realized Footprint (`realized_files`)*: Captured from the plan's own worktree via `git` jobs as the union of `git diff --name-status -M <base_ref>...HEAD` and `git status --porcelain=v1 -z`. A rename or copy contributes both its old and its new path to `realized_files` and is also recorded as a pair in `realized_renames[]`. *Deliberate change vs. `plan-marshall`*: `compute-footprint` uses `--name-only`, which drops the old path of a rename.

Resolution and capture rules:

* *Base Reference*: `<base_ref>` is `git merge-base HEAD origin/<base_branch>`, computed after the most recent fetch (after `sync-baseline`, the rebased-onto tip). It is never the SHA the plan was created against and never a local `<base_branch>` ref. Every footprint, scope, and self-review diff of the plan reads this one `base_ref`, recorded in `realized_state.base_ref`; after a `sync-baseline` or `branch-cleanup` rebase the realized footprint is re-derived against the new merge-base. When the local `<base_branch>` trails `origin/<base_branch>`, `realized_state.base_commits_behind` records by how many commits, so a stale local ref is visible although it is never used.
* *Own Tree Only*: The realized footprint resolves only from the plan's own worktree, through one resolver whose tiers (the live diff, then the persisted capture) apply identically to every consumer. A pending or absent worktree yields `realized_state.state: unresolved` with cause `pending` (not yet materialised; plans always execute in a worktree, so no other cause exists), never another tree's measured-empty set; `unresolved` and "measured, both sides empty" stay distinct. A diff-fed step without a resolvable footprint records `indeterminate` with the cause, never a clean `done`.
* *Only `measured` Reconciles*: `realized_state` is always present; `pm_start` writes it as `not_captured`. The three-way reconciliation, the footprint coverage, the scope-creep check, and every pre-merge or post-merge footprint check compare against `realized_files` only when `realized_state.state == measured`; for `unresolved` and `not_captured` each of them reports `indeterminate` with the state and cause named, never a clean or empty result.
* *Capture Before Destruction*: `realized_files` is captured and persisted (`realized_state.captured_at`) at the latest before `branch-cleanup` (order 70) removes the worktree. Post-merge consumers read the persisted set; a post-merge git-derived empty set is never evidence of no change, and a missing persisted set (`realized_state.state: not_captured`) makes the consumer report `indeterminate`. Steps that compute the footprint publish its size (`files_total`, `insertions_total`, and a source-vs-data split) as facts.
* *Consumer Scope and Provenance*: Every consumer that derives a scope from `references.json` names the set it reads. Footprint-scoped consumers (the self-review surfacer, `simplify`, `security-audit`) scope on `declared_files ∪ approved_widening[].path ∪ derived_files.expected_modifications ∪ realized_files`, re-read at each firing, and carry each path's provenance (`declared`, `widened`, `derived`, `realized`); a union is never passed on without it. `derive-verification` keeps reading the realized set only.

Pairwise reconciliation computes the **symmetric difference in both directions** ($A \setminus B$ and $B \setminus A$) across all three sets so that two equal-sized but disjoint file sets are reported as 100% disagreeing rather than matching by count. In addition:

* `derived_files \ realized_files` is reported split by intent: untouched `read_only_references` and untouched `conditional_modifications` are expected, while untouched `expected_modifications` are reported as `modify_shortfall`.
* *Coverage Populations*: Footprint coverage is $|\text{expected\_modifications} \cap \text{realized\_files}| / |\text{expected\_modifications}|$, published with both populations. Read-only references are a separate population (reported as touched or untouched, never in the coverage ratio), and conditional modifications are reported beside it (touched or not), never in the denominator. An empty `expected_modifications` makes coverage `not_derivable`, never `100%`.
* *Scope-Creep Allow Set*: A realized path is inside the plan's scope when it is in `declared_files ∪ approved_widening[].path ∪ derived_files.expected_modifications ∪ derived_files.conditional_modifications`; a realized path declared only as a read-only reference is outside it.
* Paths from change-ledger entries with `change_origin: quality_gate_autofix` are reported separately from deliverable changes.
* Results are published per deliverable (from the deliverable's `Affected files` and its task and chain-tail change entries) beside the plan-level figures; a plan-level average never replaces them.
* *Dependency Delta*: The reconciliation also runs the pre-merge Dependency Delta Check over the changed build files of the realized footprint against the outline's approved dependency set (link:phase-workflows.adoc#dependency-delta[Phase Workflows Specification, Dependency Delta Check]).

[#plan-deletion-lessons]
=== Plan Deletion and Lesson Claims

When the operator invokes plan deletion (`delete-plan` via elicitation or CLI), no lesson file lives in the plan directory, so nothing is carried back and no veto exists: in one transaction (plan lock, then lesson store lock) the server releases the claim of every lesson whose `claim.plan_id` names the plan (<<lesson-record>>, Claim) and deletes the plan directory. Lessons resolved `present_unreadable` during the scan are listed in the deletion result by id, because their claims cannot be read; a claim among them surfaces later as a stale claim, and the deletion proceeds.

[#lock-free-snapshot-reads]
=== Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)

[[_lock_free_snapshot_reads_transaction_locks_leases_pm_impl_7]]
* *Lock-Free Snapshot Reads*: Because every store update uses atomic write-and-rename (`<file>.tmp.<uuid>` -> `<file>`), all read-only operations (`pm_state`, `pm_plans`, `pm_epics`, `pm://` resources) read the current inode snapshot directly without acquiring file locks. A snapshot reader never decides `store_tampered`; it reports `digest_unverified` (<<store-digest-verification>>).
* *Sibling Lock Files*: Every store that is replaced by atomic rename is guarded by a sibling lock file, never by a lock on the store file itself (a rename replaces the inode, so a lock on the old file excludes nobody). The machine stores and their lock files are:
** `<PM_MCP_BASE>/locks/build-slots.lock`: `state/build-slots.json`
** `<PM_MCP_BASE>/locks/enrolments/<project_id>.lock`: `enrolments/<project_id>.json` and its sidecar `enrolments/<project_id>.json.hmac` (one lock per enrolment file)
** `<PM_MCP_BASE>/locks/install-records.lock`: `state/install-records.json`
** `<PM_MCP_BASE>/locks/machine-config.lock`: `machine-config.json`
** `<PM_MCP_BASE>/locks/merge.lock`: `state/merge-queue.json`
** `<PM_MCP_BASE>/locks/operator-auth.lock`: `state/operator-auth.json`
** `<PM_MCP_BASE>/locks/review-bot.lock`: `state/review-bot-windows.json`
+
The per-project server and operator stores that are not guarded by a scope lock have their own lock files in the per-project machine store: `projects/<project_id>/locks/local-config.lock` guards `local-config.json`, and `projects/<project_id>/locks/build-timings.lock` guards `build-timings.json` (<<build-timings-store>>).
+
The append-only `logs/audit.jsonl` is never replaced by rename (rotation renames it only under its own lock) and may be locked directly; `logs/audit.head` and `logs/audit-index.jsonl` are written under that audit lock.
* *Transaction Locks*: Short locks held only for one transaction. All locks of the runtime and the CLI are acquired in one total order, and a transaction that needs several locks acquires them strictly in this order to prevent deadlocks:
. workspace lock: `<PM_MCP_BASE>/projects/<project_id>/locks/workspace.lock` (the project's one workspace scope)
. plan locks: `<PM_MCP_BASE>/projects/<project_id>/locks/plan-<plan_id>.lock`, lexicographic by `plan_id`
. epic locks: `<PM_MCP_BASE>/projects/<project_id>/locks/epic-<epic_id>.lock`, lexicographic by `epic_id`
. epic worktree lock: `<PM_MCP_BASE>/projects/<project_id>/locks/epics-worktree.lock` (git operations on the shared epic worktree)
. lesson store lock: `<PM_MCP_BASE>/projects/<project_id>/locks/lessons.lock` (lesson id allocation and every write, claim, release, or retirement in the lesson store)
. local configuration lock: `<PM_MCP_BASE>/projects/<project_id>/locks/local-config.lock` (`local-config.json`)
. build timings lock: `<PM_MCP_BASE>/projects/<project_id>/locks/build-timings.lock` (`build-timings.json`)
. machine store locks: `<PM_MCP_BASE>/locks/{build-slots,enrolments/<project_id>,install-records,machine-config,merge,operator-auth,review-bot}.lock`, alphabetical by lock path (several enrolment locks lexicographic by `project_id`)
. leaf locks: the audit log lock (`<PM_MCP_BASE>/logs/audit.jsonl`) and the digest sidecar writes; nothing is acquired after a leaf lock
+
The runtime singleton lock (`locks/runtime.lock`, held for the process lifetime) and the relay start lock (`locks/runtime-start.lock`) are process locks, not transaction locks, and stay outside this order. Workspace, plan, epic, epic worktree, lesson store, local configuration, and build timings locks live in the per-project machine store outside the directories they protect (link:filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), so archiving a plan directory or editing an epic in a worktree never splits a lock.
* *Order Assertion*: The lock manager asserts the order on every acquisition against the locks the current transaction already holds (re-entry of a held lock is allowed). An out-of-order acquisition is refused: the call fails with `internal_fault` (link:mcp-tools.adoc[MCP Tools Specification]), nothing is written, and an audit record `lock_order_violation` (`category: store`, `outcome: refused`, `details{held, requested}`) is appended. A unit test of the lock manager covers an out-of-order acquisition at every level boundary.
* *Leases*: Long-lived claims (merge holder in `merge-queue.json`, review-bot windows in `review-bot-windows.json`, build slots in `build-slots.json`) are lease records owned by a scope (`scope_type`, `scope_id`), served by a runtime instance (`holder_instance`: PID and start instant), and bounded by an expiry (<<machine-lease-stores>>); a restart orphans a lease instead of releasing it, and the owning scope adopts it on its next call. A lease is claimed or released inside a short transaction on the machine store lock and is never held as an OS lock, so holding a lease while taking a plan lock does not invert the lock order.
* *Lock Manager*: All acquisitions in the runtime go through one lock manager (link:runtime-model.adoc#_in_process_lock_manager[Runtime & Interaction Model Specification]).

[#evidence-based-removal-sweeps]
=== Evidence-Based Removal Sweeps
_Implementation watch: link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-39[PM-WATCH-GEN-39]_

Every removal sweep (retention purges of job logs, archived plans and superseded lessons under the four retention keys of the operator's `local-config.json`, link:timeouts.adoc#retention-days[Timeouts & Budgets Specification]; worktree orphan sweeps):

* runs as a dry run unless the operator explicitly applies it;
* reports for every kept item the first keep-rule that fired, and for every removed item the trigger that fired;
* reports the source (`compiled_default`, `derived`, `team`, or `operator`, <<project-configuration-store,Project Configuration>>) of every configuration value it used;
* reports an empty population as one of `root_absent`, `root_unreadable`, `nothing_listed`, or `all_kept`, never as a bare zero;
* never removes an item on absence of evidence: a missing marker, record, or audit tombstone keeps the item and reports it as `skipped_no_evidence`.

[#differential-harness]
=== Differential Equivalence Harness (`PM-TEST-2`)
_Implementation watch: link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-32[PM-WATCH-GEN-32], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-57[PM-WATCH-GEN-57], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-58[PM-WATCH-GEN-58]_

* *Fixture Corpus Differential Runner (`PM-TEST-2`)*: In JUnit 5 (`pm-mcp-core`), parameterized differential tests execute each `Ported` Java store primitive and its reference Python counterpart against identical initial fixture trees in a test sandbox (the legacy `.plan/` layout for Python, the `.marshall/` layout for Java). The harness maps the Python result through the legacy -> target mapping, which lives in test code only (`PM-TEST-2`): it is re-verified against the latest `plan-marshall` version before it is implemented or changed, a target field or stored identifier it cannot populate fails the test instead of being defaulted or guessed, and no reverse mapping exists. The harness then canonicalizes JSON/JSONL outputs (normalizing generated UUIDs and ISO-8601 timestamps), and asserts zero structural diff across both returned payloads and resulting stores for all canonical store read/write invariants.
* *Known-Defect Baseline*: A known defect of the Python reference is either fixed in `plan-marshall` before the differential run or recorded as a named *deliberate change* with its own fixture, for which the harness asserts the corrected behaviour. A differential run never adopts a known defect as the equivalence baseline, and an equivalence proof for a structural refactor is taken only after every behaviour fix touching the same code has landed.
* *No Shadow Execution*: Differential tests never run on live stores, and the runtime has no routing seam, executor adapter, or automatic fallback to Python (`PM-MIG-2`). Behaviour on real work is measured by parallel runs: the same requests executed by legacy `plan-marshall` and by `PM-MCP` on separate clones or checkouts, compared by the server-computed metrics (`priced_units`, discipline events, outline and triage quality; `PM-MIG-4`).
