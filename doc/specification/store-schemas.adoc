== Overview

This document defines the normative JSON and JSONL storage schemas for *plan-marshall-mcp* (`PM-MCP`). Every persisted file includes an explicit `format_version` integer enabling deterministic forward migration on daemon startup (`PM-IMPL-2`) and safe coexistence with legacy Python scripts during staged migration (`PM-MIG-3`).

[#format-versioning]
== Format Versioning & Atomic Write Discipline

[[_format_versioning_atomic_write_discipline]]
1. *Version Envelope*: Every server-owned JSON store root object and every JSONL header/record must declare `"format_version": 1` (positive integer). The git-tracked `.plan/marshal.json` (versioned by `system.schema_version`) and the operator-edited credential files (`PM-CRED-3`) are the only exceptions. When the runtime opens a store with a lower `format_version`, it upgrades the structure in memory and writes the migrated store atomically. If a store has a `format_version` higher than the binary supports, the daemon refuses to mutate the store and requests a binary upgrade.
2. *Atomic Write-and-Rename*: All JSON file updates are written to a sibling temporary file (`<filename>.tmp.<uuid>`), flushed to disk (`FileChannel.force(true)`), and atomically renamed over the target file (`StandardCopyOption.ATOMIC_MOVE`, `StandardCopyOption.REPLACE_EXISTING`).
3. *Single Writer Set*: Legacy scripts never run in parallel with `PM-MCP`; during staged porting they run only as `script` jobs of the runtime under the addressed scope's lock (`PM-MIG-2`, `PM-MIG-3`), so all read-modify-write operations on shared stores are serialized by the runtime's own locks and no cross-runtime lock protocol exists.
4. *Absent vs Unparseable*: Every store and document reader returns one of `absent`, `empty`, `parsed`, or `unreadable` (with the failing line or offset). An input that yields no parsable content is `unreadable`, never an empty record and never `absent`. Consumers handle `unreadable` explicitly: they fail closed or report `indeterminate`.
5. *One Wire Shape per Instant*: Every persisted or exchanged instant is an RFC 3339 UTC string (`"format": "date-time"`, `Z` suffix); epoch numbers are never persisted. A process start instant is taken from the OS (`ProcessHandle.Info.startInstant()`) and stored in the same shape. Durations are integers whose field name carries the unit (`duration_ms`, `*_seconds`).

== Scope Entry Record (`mcp/entry.json`)

Written by `pm-mcp enter --client <client>` when a session enters a plan, epic, or project steward scope. Read on every subsequent MCP call within that scope (`PM-ARCH-4`).

When the entered plan does not exist yet, `pm-mcp enter` writes the same record as a pending entry record `.plan/local/mcp/pending/<entry_id>.json` (with `scope_id: null`) and prints the `entry_id`. `pm_start(entry_id, ...)` sets `scope_id` to the new `plan_id` and relocates the record atomically to `.plan/local/plans/<plan_id>/mcp/entry.json`; a consumed `entry_id` no longer exists, so each pending record starts at most one plan.

* *Scalar Identity, History in the Audit Log*: `entry.json` holds only the current entry; it has no session-history list. A re-entry that overwrites it appends an `identity` audit record (`event: entry_handover`, `details` with the previous and the new `client_id` and `client_session_id`, link:cli-and-security.adoc[CLI, Coordination & Security Specification], Entry Identity Recording), so the session history of a scope is reconstructed from `audit.jsonl` (<<_security_transition_audit_log_plan_marshallmcplogsaudit_jsonl_pm_sec_6>>).

* *Step Records Count Firings*: Every firing of a step appends to its `firings[]`; a re-fire never replaces the history. When `VerdictCurrencyEvaluator` decides to re-fire, the step's `outcome` is set to `unverified` before the step runs and is then replaced by the new firing's terminal outcome, so a prior `done` never survives a re-fire. The current `outcome` and `head_at_completion` are always those of the last firing; no force flag exists. A requested outcome change that the engine refuses appends a firing with `refused` set and leaves no stale outcome silently current. Re-fire counts per cause are `firings` minus one, grouped by `cause`, never counted from log lines. A record without `assurance_verdict` reads `unadjudicated`, never as a pass.
* *Origin and Epic Linkage*: Epic membership has one carrier: `pm-mcp enter --from-epic` writes `from_epic` into the entry record, and `pm_start` copies it into `origin.epic_id`; `pm_start` accepts no epic parameter. Every consumer (landing emission, outbox link offering, epic observation) reads epic membership from `origin.epic_id` through one resolver, which derives `epic_linkage`: `not_orchestrated` iff `origin.epic_id` is null, `indeterminate` iff it is set but the epic's `status.json` is absent or unreadable, otherwise `orchestrated`. `indeterminate` is never read as `not_orchestrated`.
* *Amendments*: Every intent-changing answer after refinement appends an `amendments[]` entry; every later representation that renders the request (outline review, `create-pr`, landing) includes the amendments in order.

* *Kinds*: `cleanup` (worktree or branch removal owed after a non-merging run; the former landing field `cleanup_owed`), `deferred_reconcile` (a reconcile deferred instead of performed), `pr_body_note` (a note that could not be written before the pull request existed), `owed_source_edit` (a follow-up source change, for example a triage `ACCEPT` with follow-up), `owed_hint` (a hint routed for later action by `lessons-capture`, `preference-emitter`, or disposition-to-hint routing), and `unrecorded_stall` (a stall the epic view or `pm-mcp status` derived from the last-transition age of a non-terminal plan).

* *Immutable Severity, Mutable Blocking*: `severity` is set at creation and never changed. `blocking` is written from the producer's declared class for the finding type (each producer declares it per finding type in its descriptor, validated at write) and may later change only through triage or an operator decision.
* *What Is Not a Finding*: Refusals, rate-limit or budget notices, the server's own posted comments and triggers, and participation-only artifacts (summary cards, trigger acknowledgements) are never filed as findings; they update the review participation record only (<<review-participation>>).
* *Self-Reports*: A `self_report` finding is filed by the server, never by a step, when the model follows `report_bypass` (link:hypermedia-format.adoc#self-report-link[Hypermedia Format Specification, Self-Report Link]); it carries the reported action as `summary`, the reason as `body`, `severity: major`, and `blocking: false`, and its paired audit record shares its timestamp. It names a sanctioned path that was missing or bypassed so the gap is fixed, and it is triaged like any other finding.
* *Structured Reviewer Identity*: `author` and `bot_kind` come from the provider's structured author field, never from comment text. A comment whose structured author and self-declared bot identity disagree is itself filed as a finding with the provider's `source`. A comment's identity is `(bot_kind, provider_ref.comment_id)` plus `edit_marker`; an edited comment is new information.
* *Server-Written Resolution*: The model submits only `disposition` (`FIX`, `SUPPRESS`, `ACCEPT`); the triage link grammar has no resolution parameter. The server writes `resolution` from recorded evidence, so a refuted claim, a valid finding that was dismissed, and a finding that is not this plan's concern stay distinguishable:
+
[cols="1,3,1"]
|===
|Disposition |Recorded condition |`resolution`

|— |Finding created, or triaged but its effect not yet recorded |`pending`
|`FIX` |The fix landed: its fix task passed server verification, or the in-branch settle commit covering the fix's `population` is recorded |`fixed`
|`SUPPRESS` |`evidence.claim_refuted == true`: the `ext-point-verify` refutation sub-state refuted the claim (`evidence.class: verifier`), or, when that sub-state is unavailable, substitute evidence with a concrete `evidence.ref` (file:line, job id, or URL) |`rejected`
|`SUPPRESS` |Otherwise (the finding is valid but dismissed) |`suppressed`
|`ACCEPT` |`scope_class == out_of_footprint` (pre-existing or another owner's code), or the triage cites a standing decision of the plan (an `amendments[]` entry or an ADR id that the server resolves) |`taken_into_account`
|`ACCEPT` |Otherwise (a known, accepted gap) |`accepted`
|— |Stale re-anchor: the finding's cited location no longer exists at `HEAD` (link:phase-workflows.adoc[Phase Workflows Specification], Step Records, Re-Fire & Loop-Back Rules) |`taken_into_account`
|===
+
`scope_class` is computed by the server at triage from `file_path` against the plan's effective footprint (`declared_files ∪ approved_widening[].path ∪ realized_files`, <<three-way-footprint>>). An operator triage decision (operator CLI or elicitation) may record any terminal resolution directly, with `evidence.class: operator`. `pending` is the only non-terminal resolution: the Blocking Findings Guard and the pre-merge barrier count it, and a `FIX` whose fix has not landed is still `pending`. Every report and landing figure over findings is keyed by `resolution` with every member tallied (stated zeros); the false-positive count of a source is its `rejected` count and never includes `suppressed`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` lets the model choose one of the six resolutions directly; `PM-MCP` keeps the three model dispositions and derives the six-value resolution from evidence the server holds.
* *Evidence Symmetry*: A resolution rests on evidence of the same kind whichever way it goes: `rejected` requires a concrete `evidence.ref` as a `FIX` requires a landed change, and a disposition that lowers severity cites an executed check.
* *Re-Disposition of a Transmitted Finding*: A finding whose `transmit_outcome` is `sent` may be re-dispositioned only together with a new `reply_text`; the server then resets `transmit_outcome` to `pending`, re-derives `resolution`, and transmits again. A bare re-disposition (same or no reply) is refused with `invalid_link_args`.
* *Late Findings Are Carried Out*: After the merge gate (order `> 70`) no step refuses on findings. A blocking finding still `pending` after the merge (filed after the barrier evaluated) is carried out by the server: appended to the parent epic inbox as a `process_finding` message, or, for a plan without an epic, seeded as a lesson (category `bug`, title from `summary`, body from `body`); while the epic linkage is `indeterminate` the message is kept with the undelivered landing envelope and delivered with it. The finding is set to status `carried` with `carried_to`; its `resolution` stays `pending`, so the carried debt remains visible (link:phase-workflows.adoc[Phase Workflows Specification], rows `1000` and `1100`).
* *Transmission and Resolution Are Separate*: Before the provider call the server persists `transmit_outcome: pending` with the `transmit_disposition` it sends. `responded_at` is stamped after the provider accepted the reply and before the thread is resolved; `resolve_state` is persisted separately, so a resolve-only retry never re-sends the reply. After a crash, a `pending` transmission is reconciled by looking up the reply on the provider before any re-send.

== Epic Inbox & Plan Mailbox Records (`inbox.jsonl`, `mcp/mailbox.jsonl`)

The epic inbox (`.plan/orchestrator/<epic_id>/inbox.jsonl`, plan → epic and epic → epic) and the plan mailbox (`mcp/mailbox.jsonl` in the plan directory, epic → plan) share one record model: a strictly append-only event log. * *Store-Assigned Identity*: The store allocates `message_id` as the next number above the highest ever written in that file, including ids of lines it cannot parse; an id is never reused, and a caller never supplies one. [#metrics-store]
== Metrics Store (`metrics.json`)

The plan's `metrics.json` holds the dispatch and phase measurements that `default:record-metrics` aggregates (`PM-WF-14`, link:dispatch-and-effort.adoc[Dispatch & Effort Specification], Post-Return Integrity Invariants). It extends the rule "unmeasured is never `0`" from token usage to every figure it publishes.

* *Rows*: One row per dispatch (`dispatch_id`, `phase`, `step_id` or null, `envelope_id` or null with its `predicted_cost_tokens`, `status`, `cause_class`, `spend_class`, `population`, the usage columns of the `returned:<dispatch_id>` link (`token_usage`, `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `tool_uses`), each a measured integer, `"unmeasured"` (with `not_reported_by_client` where the client profile cannot report it), or, for a step that runs inline by design, `"inline"`, and the server-measured `duration_ms` with its `duration_basis`), one row per wait slice (`phase`, `wait_reason`, `deliberate`, duration; link:job-runtime.adoc[Job Runtime Specification], Wait Attribution), one row per phase close (`start_time`, `end_time`, `duration_ms`, `duration_clamped`, `boundary` (`closed`, `re_entered`, or `provisional` with `measured_until` and `excluded_steps`), `step_firings` as a map from step id to firing count), and one row per served document read (Served-Content Ledger below).
* *Served-Content Ledger*: Every `pm_skill`, `pm_skill_file`, and skill `resources/read` served in a plan or epic scope appends `{uri, section?, bytes, plan_id, phase, dispatch_id?, served_at}`; `bytes` is the rendered size served, `0` for an empty section. `dispatch_id` is set when the read carries it (the server renders it into the load directives of a dispatch prompt) and is otherwise null. A read without a scope is attributed to no plan. `record-metrics` publishes from these rows the per-document consumption (reads per URI and section, bytes, repeat reads within one dispatch). It measures only what the server serves; host `Read`/`Grep` of files is not observable.
* *Aggregates*: Every sum (per phase, per cause class, per plan) is published as `{value?, rows, rows_unmeasured, population_count, excluded{<class>: count}}` with `rows = measured + Σ excluded`. `value` is omitted when `population_count == 0`. A phase that is still open is reported as a floor, never as a total; Phase 6, which `record-metrics` measures from inside, is recorded `boundary: provisional` with `measured_until` and its `excluded_steps`.
* *Populations*: Every token figure carries a `population` stamp (`dispatched` or `main_context`); an absent stamp reads `dispatched`. Relations (`=`, `<`, `>`) and sums are formed only between figures of one population. A derived ratio whose denominator population is empty is `not_derivable`, never `0`.
* *Re-Entry*: Re-entry is derived from observables (rows timestamped after the phase's recorded `end_time`), never from a close counter. A re-entered phase is labelled `re_entered` and accumulates across closes.
* *Cause Classes*: `cause_class` (`terminal_error`, `retryable`, `returned_with_findings`, `benign`, `stall`) is a total function over the dispatch `status` enum plus `INCOMPLETE_SUBMISSION`; the build-time exhaustiveness check (`PM-IMPL-5`) fails on an unclassified member. A spend decomposition sums to the phase total, with an explicit `unbucketed` class.
* *Spend Classes*: `spend_class` (`submitted`, `findings_only`, `no_product`, `unmeasured`) is derived by the server from what the dispatch produced (link:dispatch-and-effort.adoc#spend-accounting-budget-anchors[Dispatch & Effort Specification, Spend Classes]); it is a separate dimension from `status` and `cause_class`, and waste is read only from `no_product`.
* *Stall Rate*: A termination with `tasks_remaining > 0` and no blocked cause is `stall`. The stall rate and the `yield_reason` counts are published per plan.
* *Ledger Divergence*: Where two ledgers can diverge (dispatch rows vs audit rows), `record-metrics` publishes `union_rows` and a non-blocking `reconciliation{findings_count}` warning. Each ledger states its counting unit.
* *One Writer per Name*: Every metric name has exactly one writer. A second producer over another population uses a different name.
* *Raw Components Only*: Rows persist measured token components, never a weighted or priced figure. `priced_units` is derived in views from the rows and one named constant table (link:phase-workflows.adoc#post-run-metrics-and-landing[Phase Workflows Specification, Metric Aggregates]); a change of the weights re-derives every figure, including legacy baselines, from the persisted components.

== Lesson Record (main-anchored lesson store)

Lessons live in the main-anchored lesson store of the repository and outlive the plans that create them. Each lesson is one Markdown file whose structured header carries the fields below, followed by its Markdown body (`PM-IMPL-2`); the lesson `submit` transition (link:phase-workflows.adoc[Phase Workflows Specification], Lesson Creation & Body) writes both atomically. The store is a Ported store (`PM-TEST-1`, <<legacy-store-formats>>).

* *Placement*: The store is `.plan/local/lessons-learned/` of the main checkout (link:filesystem-layout.adoc[Filesystem Layout Specification]): git-ignored and machine-local, resolved main-anchored from every worktree, one file `<lesson_id>.md` per lesson, tombstones in `.tombstones/<lesson_id>.json`, and the lesson-store digest sidecar `.digests.json`. The directory name is kept from `plan-marshall` (`manage-lessons` `DIR_LESSONS`, verified at `plan-marshall` `f3de0e14f`), so conversion moves no file. A lesson therefore stays on the machine that recorded it; a second machine or clone does not see it. This trade-off is accepted: lessons reach other machines only through their promotion destinations (`promotions[]`).
* *File Format*: A lesson file starts with a header block of `key=value` lines (the `manage-lessons` header style), one line per scalar field of the schema below; `promotions` and `tool_version_override` are single-line JSON values. The header ends at the first blank line, followed by the H1 heading, which is the `title` field, and the Markdown body. The server validates the header against the schema, including `format_version`, on every write; a write with a missing or invalid header is rejected, and a file without a parseable header lists as `present_unreadable`.
* *Lesson-Store Digest*: Every server write, move, or retirement in the lesson store records the size and SHA-256 of each lesson file and tombstone in `.digests.json` (the sidecar format of <<store-digest-verification>>) in the same transaction as the lesson write. On read, a lesson whose file differs from its entry is `store_tampered` for that lesson only; a lesson file that disappeared without a tombstone is reported as `deleted_without_tombstone`, and a file without an entry is reported as `untracked`. None of these states is ever read as `absent`, and an out-of-band edit is accepted only with `pm-mcp operator accept-edit`, which re-baselines that lesson's entry and records the action in `audit.jsonl`.

* *One Resolver, Four States*: Listing and lookup use one resolver over the lesson store. Every listed lesson resolves by the exact id it is listed under to one of `found`, `absent`, `present_unreadable` (metadata missing or invalid; listed with its path, never omitted), or `empty_shell` (valid metadata, empty body). `present_unreadable` is never reported as `absent`, and `empty_shell` is never a content verdict. A lesson write without valid metadata is rejected.
* *Lifecycle*: `status` is `active`, `upstream_pending`, `superseded`, or `removed` (the last exists only as a tombstone); the lifecycle is binary (live or retired) and carries no moving confidence value, mirroring `plan-marshall`. `applied` (moved into a plan directory; inverse: carry-back, <<lesson-carry-back-veto>>) and `stalled` (stranded in a non-terminal plan directory) are derived from the file location and never stored.
* *arch-constraint Recurrence*: An add whose `rule` matches an active `arch-constraint` lesson reinforces it (increments `recurrence_count`, refreshes `last_seen`) instead of allocating a new lesson. A quiet-window retirement retires every active `arch-constraint` lesson whose `last_seen` is older than the window.
* *Retirement*: A retirement (supersede, remove, quiet-window retirement) requires a `coverage_verdict` from the closed set, with no default. `completely_covered` also requires `covering_clause` and a concrete `covering_input` that the clause's worked example resolves; a whitespace-only value counts as missing. The tombstone is written before the lesson is removed. A retirement acts only on a lesson resolved `found`, or on a `present_unreadable` lesson through an explicit operator action; in every other state it changes nothing and reports the state.
* *No Bulk Mutation*: The lesson store is never wiped or bulk-mutated; no bulk-mutation verb exists. A removal answering `absent` is not proof that the lesson never existed and is never retried automatically; it is reported together with the store-resolution discriminator.
* *Version Provenance*: The runtime stamps `tool_version` from its own release version (`PM-DIST-1`) at creation; it is never a `submit` parameter. An operator override is stored in `tool_version_override` beside the stamped value. Converted legacy lessons keep three states apart: no version field in the legacy lesson → `absent`; a field that cannot be resolved → `undetermined`; otherwise the recorded version. Conversion never backfills a version.
* *Provenance*: Every new lesson records `provenance` (`run_artifact`, `tool_return`, or `operator_decision`); the server sets it where the creating transition determines it (a `split` deviation lesson is `operator_decision`, a recurring-exemption lesson of `lessons-capture` is `run_artifact`) and otherwise requires it as a `submit` parameter. `unknown` is written only by the one-time converter for legacy lessons, and the reverse converter drops the field.
* *Audience Classification*: A lesson's `audience` is `upstream` iff its `component` names a component shipped by the `pm-mcp` distribution (a built-in skill, recipe, or finalize-step identifier from the compiled-in catalogue); every other component, including a project-prefixed one (`api-sheriff:maven-build`) and one without a bundle prefix (`integration-tests`), is `local`. The classification never inspects the repository layout. An operator override of the classification is persisted on the lesson in `audience_override` in addition to its audit record, so a lesson admitted by an override is never indistinguishable from a classified one. *Deliberate change vs. `plan-marshall`*: `manage-lessons add` decides ownership by the existence of `marketplace/bundles/{prefix}`, which misfiles a consumer's own prefixed component as foreign.
* *Upstream Release (`PM-ARCH-2`)*: An `upstream` lesson is created `upstream_pending` and stays in the local store; nothing transmits it automatically. It leaves the workstation only through the operator action `pm-mcp operator lesson release --lesson <lesson_id>`, which renders the issue body for review and either hands it to the operator to file or, on the operator's explicit confirmation, runs a filing job through the enrolled CI provider. A `local` lesson is never offered this action; naming one is refused with `audience_mismatch`, which states the lesson's audience and leaves it unchanged. A successful filing records the issue in `promotions[]` (`kind: issue`) and returns the lesson to `active`.
** *Rendering*: The issue body is rendered from the stored record only: body, `component`, producing `plan_id`, and the recorded `tool_version`, never values sampled at filing time.
** *Duplicates*: Duplicate detection keys on (`component`, normalized `rule`); a `no_duplicate` verdict carries the compared population (count and ids).
** *Loud, Lossless Failure*: A failed filing leaves the lesson `upstream_pending` with `last_filing_failure` (`offline`, `forbidden`, `rate_limited`, or `refused`) and the unchanged content; it never falls back to `local`.
** *Corpus Routing Campaign*: A routing run over an existing lesson corpus (the `lesson-cleanup` recipe) records one disposition per lesson (`routed`, `reclassified`, or `retired` with a mandatory `retired_reason`); re-running on unchanged input is a no-op keyed on the dedup key; when the population differs between derivation and action, the run reports the delta (added and removed ids) and never adopts it silently.
* *Promotion Provenance*: `promotions[]` records every destination that absorbed the lesson. A routing sweep or the `lesson-cleanup` harvester reports a lesson with a matching destination as `already_promoted` and never routes it again as new.

=== Permission-Guarded Credential Store (`~/.plan-marshall/credentials/<credential_key>.json`, `PM-CRED-3`)

When OS keychain access is unavailable (e.g., headless Linux SSH session), Token-Lane credentials fall back to user-only `0600` JSON files inside `~/.plan-marshall/credentials/` (`0700` directory; `PLAN_MARSHALL_CREDENTIALS_DIR` overrides the directory). `PM-MCP` uses `plan-marshall`'s file format and naming unchanged: files are named by credential key (the provider skill name without bundle prefix, `PM-CRED-1`), are edited by the operator, are never converted, and are exempt from the `format_version` envelope. === Security & Transition Audit Log (`~/.plan-marshall/mcp/logs/audit.jsonl`, `PM-SEC-6`)

Every state transition, job execution, operator elicitation/CLI action, credential lookup, and environment mismatch appends a structured JSONL record to `audit.jsonl` (with all Token-Lane secrets redacted):

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/audit-record.json",
  "title": "AuditRecord",
  "type": "object",
  "required": ["format_version", "event_id", "prev_hash", "timestamp", "category", "event", "actor", "outcome"],
  "additionalProperties": false,
  "properties": {
    "format_version": { "type": "integer", "const": 1 },
    "event_id": { "type": "string", "format": "uuid" },
    "prev_hash": {
      "type": "string",
      "pattern": "^[0-9a-f]{64}$",
      "description": "SHA-256 (lowercase hex) of the previous record's canonical line; 64 '0' characters for the first record of the log."
    },
    "timestamp": { "type": "string", "format": "date-time" },
    "category": { "type": "string", "enum": ["transition", "job", "operator", "security", "identity", "credential"] },
    "event": { "type": "string" },
    "scope_type": { "type": ["string", "null"], "enum": ["plan", "epic", "project", "machine", null] },
    "scope_id": { "type": ["string", "null"] },
    "actor": { "type": "string", "description": "Client profile ID or OS principal username." },
    "outcome": { "type": "string", "enum": ["allowed", "refused", "succeeded", "failed", "warning"] },
    "details": { "type": "object" }
  }
}
----

*Exemption and self-report records*: An operator exemption from a gate is an `operator` record whose `details.exemption_class` holds `{gate_id, reason_class}` (`gate_false_positive`, `gate_not_applicable`, `tooling_unavailable`, `deliberate_deferral`, or `unknown`); the recurrence count across plans (link:phase-workflows.adoc[Phase Workflows Specification], Artifact Gate) is derived from these records. A model self-report (`report_bypass`) is a `transition` record with `event: self_report` and `details{action, reason, finding_id}`.

*Hash chain (`PM-SEC-6`)*: The canonical line of a record is its exact UTF-8 byte sequence in `audit.jsonl`, excluding the terminating newline. A writer appends only under the log's `FileChannel.lock()`, after reading the current last line to compute `prev_hash`. The runtime verifies the chain at startup; a mismatch or unparsable line is reported to the operator and recorded as an `audit_chain_broken` record (`category: security`, `details.first_broken_line`), and the log is never rewritten or repaired.

[#machine-lease-stores]
== Machine Lease Stores (`merge-queue.json`, `review-bot-windows.json`, `build-slots.json`)

The three lease stores in `~/.plan-marshall/mcp/state/` are updated only in short transactions under their machine store locks (<<lock-free-snapshot-reads>>; `PM-IMPL-7`, `PM-WF-15`). Every lease owner has the same shape, and every instant follows the one wire shape (<<format-versioning>> item 5), so a lease written by one component and reclaimed by another round-trips byte-identical instants.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/lease-owner.json",
  "title": "LeaseOwner",
  "type": "object",
  "required": ["plan_id", "runtime_pid", "runtime_started_at"],
  "additionalProperties": false,
  "properties": {
    "plan_id": { "type": "string" },
    "runtime_pid": { "type": "integer", "minimum": 1 },
    "runtime_started_at": { "type": "string", "format": "date-time" }
  }
}
----

* *`merge-queue.json`*: `{"format_version": 1, "repositories": {"<repository key>": {"holder": <lease> | null, "waiting": [<entry>]}}}`. A `holder` lease carries `owner`, `acquired_at`, `heartbeat_at`, and `lease_expires_at`; a `waiting` entry carries `owner` and `enqueued_at`, in FIFO order.
* *`build-slots.json`*: `{"format_version": 1, "slots": [<lease>]}`, each lease with `owner`, `job_id`, `acquired_at`, and `lease_expires_at`; the slot count never exceeds `max_build_slots` (<<machine-config>>).
* *`review-bot-windows.json`*: `{"format_version": 1, "windows": {"<org>/<bot_kind>": <window>}}`. Rate windows are org-scoped, so a window claim is keyed by organisation and `bot_kind`; attempt counters inside a window are keyed by `(repository, pr_number, bot_kind)`, so one pull request never reports another's attempts. A window stores `owner`, `claimed_at`, the absolute `reset_at`, `attempts`, and `answers_trigger_id` (the review request the refusal answered). A wait on a window computes its remainder from `reset_at`, so a killed waiter or a runtime restart resumes the remainder; re-reading the same refusal never restarts a window that has already been waited out. A contended claim returns `reason`, `holder`, and `seconds_remaining`.

== Data Layer Integrity & Concurrency Invariants (`PM-IMPL-7`)

[#store-digest-verification]
=== Store Digest Verification Against Out-of-Band Edits

[[_store_digest_verification_against_out_of_band_edits]]
Because `.plan/` files reside in the repository working tree where an agent with filesystem write access could modify them directly outside the MCP server:

* Digests live in the sidecar `mcp/digests.json` (`{"format_version": 1, "stores": {"<relative path>": {"size": <int>, "sha256": "<hex>"}}}`), never inside a store they protect.
* On every server write to a plan store (`mcp/status.json`, `references.json`, `TASK-*.json`, `execution-manifest.json`, `metrics.json`, `quality-report.json`, the findings, assessment, review-participation, and change-ledger JSONL files, `outline.md`, `request.md`), the server records the file's size and SHA-256 in the sidecar under the plan lock.
* The digest of a store is updated in the same transaction as the store write. A multi-store transaction that fails part-way re-records the digests of every store it already replaced before it releases the lock. Startup recovery re-verifies a store whose sidecar entry is older than the file against the pending-write marker of the interrupted transaction instead of reporting it as tampered.
* On every subsequent read inside a transition, the engine verifies size and SHA-256 against the sidecar. Any mismatch triggers an immediate `store_tampered` transition block requiring operator resolution.
* After a legacy `script` job finishes (it runs under the plan lock, `PM-MIG-2`), the runtime re-records the digests of the stores that job may write, so legitimate legacy writes never raise `store_tampered`.
* An intentional manual edit is accepted with `pm-mcp operator accept-edit <plan_id> <store>`, which re-baselines that store's digest and records the action in `audit.jsonl`.
* The main-anchored lesson store keeps its own sidecar with the same format and rules, at lesson granularity (<<lesson-record>>): an out-of-band edit or deletion of one lesson blocks only that lesson.

[#three-way-footprint]
=== Three-Way File Footprint Reconciliation (`references.json`)

[[_three_way_file_footprint_reconciliation_references_json]]
The `references.json` store tracks three distinct file-footprint sets for a plan:

* *Declared Footprint (`declared_files`)*: Files explicitly listed during refinement/outline. `declared_files` is immutable after `outline.review` approval. A path admitted later by an accepted scope deviation is recorded in `approved_widening[]` with its provenance (deviation task, `approved_via`, phase, time), never appended to `declared_files`. The effective declaration is `declared_files ∪ approved_widening[].path`, and every reconciliation result names which of the two admitted a path.
* *Structured-Derived Footprint (`derived_files`)*: Re-derived by set union over the solution outline's structured deliverables and partitioned into two disjoint keys:
** `expected_modifications`: Files the plan intends to create, modify, or delete.
** `conditional_modifications`: Files declared `(write-conditional)`, edited only if a named gate fires.
** `read_only_references`: Files inspected for context that must remain unmodified.
* *Realized Footprint (`realized_files`)*: Captured from the plan's own worktree via `git` jobs as the union of `git diff --name-status -M <base_ref>...HEAD` and `git status --porcelain=v1 -z`. A rename or copy contributes both its old and its new path to `realized_files` and is also recorded as a pair in `realized_renames[]`. *Deliberate change vs. `plan-marshall`*: `compute-footprint` uses `--name-only`, which drops the old path of a rename.

Resolution and capture rules:

* *Base Reference*: `<base_ref>` is `git merge-base HEAD origin/<base_branch>`, computed after the most recent fetch (after `sync-baseline`, the rebased-onto tip). It is never the SHA the plan was created against and never a local `<base_branch>` ref. Every footprint, scope, and self-review diff of the plan reads this one `base_ref`, recorded in `realized_state.base_ref`; after a `sync-baseline` or `branch-cleanup` rebase the realized footprint is re-derived against the new merge-base. When the local `<base_branch>` trails `origin/<base_branch>`, `realized_state.base_commits_behind` records by how many commits, so a stale local ref is visible although it is never used.
* *Own Tree Only*: The realized footprint resolves only from the plan's own worktree, through one resolver whose tiers (the live diff, then the persisted capture) apply identically to every consumer. A pending or absent worktree yields `realized_state.state: unresolved` with cause `pending` (not yet materialised) or `disabled` (`use_worktree == false`), never another tree's measured-empty set; `unresolved` and "measured, both sides empty" stay distinct. A diff-fed step without a resolvable footprint records `indeterminate` with the cause, never a clean `done`.
* *Capture Before Destruction*: `realized_files` is captured and persisted (`realized_state.captured_at`) at the latest before `branch-cleanup` (order 70) removes the worktree. Post-merge consumers read the persisted set; a post-merge git-derived empty set is never evidence of no change, and a missing persisted set makes the consumer report `indeterminate`. Steps that compute the footprint publish its size (`files_total`, `insertions_total`, and a source-vs-data split) as facts.
* *Consumer Scope and Provenance*: Every consumer that derives a scope from `references.json` names the set it reads. Footprint-scoped consumers (the self-review surfacer, `simplify`, `security-audit`) scope on `declared_files ∪ approved_widening[].path ∪ derived_files.expected_modifications ∪ realized_files`, re-read at each firing, and carry each path's provenance (`declared`, `widened`, `derived`, `realized`); a union is never passed on without it. `derive-verification` keeps reading the realized set only.

Pairwise reconciliation computes the **symmetric difference in both directions** ($A \setminus B$ and $B \setminus A$) across all three sets so that two equal-sized but disjoint file sets are reported as 100% disagreeing rather than matching by count. In addition:

* `derived_files \ realized_files` is reported split by intent: untouched `read_only_references` and untouched `conditional_modifications` are expected, while untouched `expected_modifications` are reported as `modify_shortfall`.
* *Coverage Populations*: Footprint coverage is $|\text{expected\_modifications} \cap \text{realized\_files}| / |\text{expected\_modifications}|$, published with both populations. Read-only references are a separate population (reported as touched or untouched, never in the coverage ratio), and conditional modifications are reported beside it (touched or not), never in the denominator. An empty `expected_modifications` makes coverage `not_derivable`, never `100%`.
* *Scope-Creep Allow Set*: A realized path is inside the plan's scope when it is in `declared_files ∪ approved_widening[].path ∪ derived_files.expected_modifications ∪ derived_files.conditional_modifications`; a realized path declared only as a read-only reference is outside it.
* Paths from change-ledger entries with `change_origin: quality_gate_autofix` are reported separately from deliverable changes.
* Results are published per deliverable (from the deliverable's `Affected files` and its task and chain-tail change entries) beside the plan-level figures; a plan-level average never replaces them.

[#lesson-carry-back-veto]
=== Fail-Closed Lesson Carry-Back Veto on Plan Deletion

[[_fail_closed_lesson_carry_back_veto_on_plan_deletion]]
When the operator invokes plan deletion (`delete-plan` via elicitation or CLI):

1. The server scans the plan directory for any lessons created or carried during the plan's execution.
2. It executes `restore-from-plan` against the main-anchored global lesson store, producing a 4-state outcome (`restored`, `restore_incomplete`, `no_lesson_file`, `plan_dir_unresolved`; `not_attempted` when carry-back is explicitly opted out) plus a store-resolution discriminator confirming the main store was resolved and scanned. Only `restored` and `no_lesson_file` permit deletion; `restore_incomplete` and `plan_dir_unresolved` veto it.
3. If any carried lesson fails to land in the main-anchored store, the deletion is **vetoed fail-closed** and the plan directory is preserved intact.

[#lock-free-snapshot-reads]
=== Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)

[[_lock_free_snapshot_reads_transaction_locks_leases_pm_impl_7]]
* *Lock-Free Snapshot Reads*: Because every store update uses atomic write-and-rename (`<file>.tmp.<uuid>` -> `<file>`), all read-only operations (`pm_state`, `pm_plans`, `pm_epics`, `pm://` resources) read the current inode snapshot directly without acquiring file locks.
* *Transaction Locks*: Short locks held only for one transaction. When a transaction spans several scopes, they are acquired strictly in this order to prevent deadlocks:
** plan lock: `<main>/.plan/local/locks/plan-<plan_id>.lock`
** epic lock: `<main>/.plan/local/locks/epic-<epic_id>.lock`
** machine store locks: `~/.plan-marshall/mcp/locks/{merge,review-bot,build-slots}.lock`
+
Plan and epic locks live outside the directories they protect, so relocating a plan directory (link:move-journal.adoc[Move Journal Specification]) or editing an epic in a worktree never splits a lock.
* *Leases*: Long-lived claims (merge holder in `merge-queue.json`, review-bot windows in `review-bot-windows.json`, build slots in `build-slots.json`) are lease records with an owner (`plan_id` plus runtime instance PID and start instant) and an expiry (<<machine-lease-stores>>). A lease is claimed or released inside a short transaction on the machine store lock and is never held as an OS lock, so holding a lease while taking a plan lock does not invert the lock order.
* *Lock Manager*: All acquisitions in the runtime go through one lock manager (link:runtime-model.adoc#_in_process_lock_manager[Runtime & Interaction Model Specification]).

[#evidence-based-removal-sweeps]
=== Evidence-Based Removal Sweeps

Every removal sweep (legacy-surface retirement, retention purges of logs, archived plans and superseded lessons, worktree orphan sweeps, converter and migration-command retirement):

* runs as a dry run unless the operator explicitly applies it;
* reports for every kept item the first keep-rule that fired, and for every removed item the trigger that fired;
* reports the source (compiled default, `.plan/marshal.json`, machine configuration) of every configuration value it used;
* reports an empty population as one of `root_absent`, `root_unreadable`, `nothing_listed`, or `all_kept`, never as a bare zero;
* never removes an item on absence of evidence: a missing marker, record, or audit tombstone keeps the item and reports it as `skipped_no_evidence`.

[#legacy-store-formats]
=== Legacy Store Formats & One-Time Conversion (`PM-MIG-3`, `PM-MIG-5`)

The schemas in this document are the target formats. Legacy `plan-marshall` stores differ; each store switches exactly once, in the stage that ports it, through a legacy -> target converter, and every legacy script touching that store is ported or retired in the same stage. Each converter has a reverse converter used by `pm-mcp operator rollback`.

* *No Defaulted Fields*: A converter that cannot populate a target field from legacy data never defaults it. The cutover receipt records `{source_format, missing_fields[]}` for every partially converted record, keyed by its identifier, together with the count per store, and consumers treat those fields as absent.
* *Mapped Identifiers*: Each store conversion writes a cutover receipt that lists every in-flight plan and epic whose stored identifiers (`from_epic`, spec references, queue row identifiers) the converter mapped, and refuses the switch for that store when any identifier cannot be mapped.

IMPORTANT: The legacy formats below were verified against `plan-marshall` commit `1d4a1da37`. `plan-marshall` keeps evolving: before implementing a converter, re-verify the legacy format of that store against the latest `plan-marshall` version and update this table.

=== Differential Equivalence Harness & Executor Shadow Routing (`PM-TEST-2`, `PM-MIG-1`)

* *Shared Corpus Differential Runner (`PM-TEST-2`)*: In JUnit 5 (`pm-mcp-core`), parameterized differential tests execute each `Ported` Java store primitive and its reference Python counterpart against identical initial `.plan/` directory trees. The harness maps the Python result through the store's legacy -> target converter, canonicalizes JSON/JSONL outputs (normalizing generated UUIDs and ISO-8601 timestamps), and asserts zero structural diff across both returned payloads and resulting stores for all canonical store read/write invariants.
* *Known-Defect Baseline*: A known defect of the Python reference is either fixed in `plan-marshall` before the differential run or recorded as a named *deliberate change* with its own fixture, for which the harness asserts the corrected behaviour. A differential run never adopts a known defect as the equivalence baseline, and an equivalence proof for a structural refactor is taken only after every behaviour fix touching the same code has landed.
* *Executor Shadow Routing (`PM-MIG-1`)*: During Migration Stages 1 and 2, the runtime's executor adapter supports shadow-routing `Ported` read/write operations to the Java primitive while comparing results against the Python baseline (mapped through the converter), logging any divergence to `audit.jsonl` and triggering automatic fallback (`PM-MIG-5`) if a discrepancy occurs.
