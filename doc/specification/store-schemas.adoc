== Overview

This document defines the normative JSON and JSONL storage schemas for *plan-marshall-mcp* (`PM-MCP`). Every persisted file includes an explicit `format_version` integer enabling deterministic forward migration on daemon startup (`PM-IMPL-2`) and safe coexistence with legacy Python scripts during staged migration (`PM-MIG-3`).

== Format Versioning & Atomic Write Discipline

[[_format_versioning_atomic_write_discipline]]
1. *Version Envelope*: Every server-owned JSON store root object and every JSONL header/record must declare `"format_version": 1` (positive integer). The git-tracked `.plan/marshal.json` (versioned by `system.schema_version`) and the operator-edited credential files (`PM-CRED-3`) are the only exceptions. When the runtime opens a store with a lower `format_version`, it upgrades the structure in memory and writes the migrated store atomically. If a store has a `format_version` higher than the binary supports, the daemon refuses to mutate the store and requests a binary upgrade.
2. *Atomic Write-and-Rename*: All JSON file updates are written to a sibling temporary file (`<filename>.tmp.<uuid>`), flushed to disk (`FileChannel.force(true)`), and atomically renamed over the target file (`StandardCopyOption.ATOMIC_MOVE`, `StandardCopyOption.REPLACE_EXISTING`).
3. *Single Writer Set*: Legacy scripts never run in parallel with `PM-MCP`; during staged porting they run only as `script` jobs of the runtime under the addressed scope's lock (`PM-MIG-2`, `PM-MIG-3`), so all read-modify-write operations on shared stores are serialized by the runtime's own locks and no cross-runtime lock protocol exists.
4. *Absent vs Unparseable*: Every store and document reader returns one of `absent`, `empty`, `parsed`, or `unreadable` (with the failing line or offset). An input that yields no parsable content is `unreadable`, never an empty record and never `absent`. Consumers handle `unreadable` explicitly: they fail closed or report `indeterminate`.
5. *One Wire Shape per Instant*: Every persisted or exchanged instant is an RFC 3339 UTC string (`"format": "date-time"`, `Z` suffix); epoch numbers are never persisted. A process start instant is taken from the OS (`ProcessHandle.Info.startInstant()`) and stored in the same shape. Durations are integers whose field name carries the unit (`duration_ms`, `*_seconds`).

== Scope Entry Record (`mcp/entry.json`)

Written by `pm-mcp enter --client <client>` when a session enters a plan, epic, or project steward scope. Read on every subsequent MCP call within that scope (`PM-ARCH-4`).

When the entered plan does not exist yet, `pm-mcp enter` writes the same record as a pending entry record `.plan/local/mcp/pending/<entry_id>.json` (with `scope_id: null`) and prints the `entry_id`. `pm_start(entry_id, ...)` sets `scope_id` to the new `plan_id` and relocates the record atomically to `.plan/local/plans/<plan_id>/mcp/entry.json`; a consumed `entry_id` no longer exists, so each pending record starts at most one plan.

* *Step Records Count Firings*: Every firing of a step appends to its `firings[]`; a re-fire never replaces the history. When `VerdictCurrencyEvaluator` decides to re-fire, the step's `outcome` is set to `unverified` before the step runs and is then replaced by the new firing's terminal outcome, so a prior `done` never survives a re-fire. The current `outcome` and `head_at_completion` are always those of the last firing; no force flag exists. A requested outcome change that the engine refuses appends a firing with `refused` set and leaves no stale outcome silently current. Re-fire counts per cause are `firings` minus one, grouped by `cause`, never counted from log lines. A record without `assurance_verdict` reads `unadjudicated`, never as a pass.
* *Origin and Epic Linkage*: Every consumer (landing emission, outbox link offering, epic observation) reads epic membership from `origin.epic_id` through one resolver, which derives `epic_linkage`: `not_orchestrated` iff `origin.epic_id` is null, `indeterminate` iff it is set but the epic's `status.json` is absent or unreadable, otherwise `orchestrated`. `indeterminate` is never read as `not_orchestrated`.
* *Amendments*: Every intent-changing answer after refinement appends an `amendments[]` entry; every later representation that renders the request (outline review, `create-pr`, landing) includes the amendments in order.

* *Immutable Severity, Mutable Blocking*: `severity` is set at creation and never changed. `blocking` is written from the producer's declared class for the finding type (each producer declares it per finding type in its descriptor, validated at write) and may later change only through triage or an operator decision.
* *What Is Not a Finding*: Refusals, rate-limit or budget notices, the server's own posted comments and triggers, and participation-only artifacts (summary cards, trigger acknowledgements) are never filed as findings; they update the review participation record only (<<review-participation>>).
* *Structured Reviewer Identity*: `author` and `bot_kind` come from the provider's structured author field, never from comment text. A comment whose structured author and self-declared bot identity disagree is itself filed as a finding with the provider's `source`. * *Transmission and Resolution Are Separate*: Before the provider call the server persists `transmit_outcome: pending` with the `transmit_disposition` it sends. `responded_at` is stamped after the provider accepted the reply and before the thread is resolved; `resolve_state` is persisted separately, so a resolve-only retry never re-sends the reply. After a crash, a `pending` transmission is reconciled by looking up the reply on the provider before any re-send.

[#metrics-store]
== Metrics Store (`metrics.json`)

The plan's `metrics.json` holds the dispatch and phase measurements that `default:record-metrics` aggregates (`PM-WF-14`, link:dispatch-and-effort.adoc[Dispatch & Effort Specification], Post-Return Integrity Invariants). It extends the rule "unmeasured is never `0`" from token usage to every figure it publishes.

* *Rows*: One row per dispatch (`dispatch_id`, `phase`, `step_id` or null, `status`, `cause_class`, `population`, and the usage columns of the `returned:<dispatch_id>` link, each a measured integer, `"unmeasured"`, or, for a step that runs inline by design, `"inline"`), one row per wait slice (`phase`, `wait_reason`, `deliberate`, duration; link:job-runtime.adoc[Job Runtime Specification], Wait Attribution), and one row per phase close (`start_time`, `end_time`, `duration_ms`, `duration_clamped`, `step_firings` as a map from step id to firing count).
* *Aggregates*: Every sum (per phase, per cause class, per plan) is published as `{value?, rows, rows_unmeasured, population_count, excluded{<class>: count}}` with `rows = measured + Σ excluded`. `value` is omitted when `population_count == 0`. A phase that is still open is reported as a floor, never as a total.
* *Populations*: Every token figure carries a `population` stamp (`dispatched` or `main_context`); an absent stamp reads `dispatched`. Relations (`=`, `<`, `>`) and sums are formed only between figures of one population. A derived ratio whose denominator population is empty is `not_derivable`, never `0`.
* *Re-Entry*: Re-entry is derived from observables (rows timestamped after the phase's recorded `end_time`), never from a close counter. A re-entered phase is labelled `re_entered` and accumulates across closes.
* *Cause Classes*: `cause_class` (`terminal_error`, `retryable`, `returned_with_findings`, `benign`, `stall`) is a total function over the dispatch `status` enum plus `INCOMPLETE_SUBMISSION`; the build-time exhaustiveness check (`PM-IMPL-5`) fails on an unclassified member. A spend decomposition sums to the phase total, with an explicit `unbucketed` class.
* *Stall Rate*: A termination with `tasks_remaining > 0` and no blocked cause is `stall`. The stall rate and the `yield_reason` counts are published per plan.
* *Ledger Divergence*: Where two ledgers can diverge (dispatch rows vs audit rows), `record-metrics` publishes `union_rows` and a non-blocking `reconciliation{findings_count}` warning. Each ledger states its counting unit.
* *One Writer per Name*: Every metric name has exactly one writer. A second producer over another population uses a different name.

* *One Resolver, Four States*: Listing and lookup use one resolver over the lesson store. Every listed lesson resolves by the exact id it is listed under to one of `found`, `absent`, `present_unreadable` (metadata missing or invalid; listed with its path, never omitted), or `empty_shell` (valid metadata, empty body). `present_unreadable` is never reported as `absent`, and `empty_shell` is never a content verdict. A lesson write without valid metadata is rejected.
* *Lifecycle*: `status` is `active`, `superseded`, or `removed` (the last exists only as a tombstone). `applied` (moved into a plan directory; inverse: carry-back, <<lesson-carry-back-veto>>) and `stalled` (stranded in a non-terminal plan directory) are derived from the file location and never stored.
* *arch-constraint Recurrence*: An add whose `rule` matches an active `arch-constraint` lesson reinforces it (increments `recurrence_count`, refreshes `last_seen`) instead of allocating a new lesson. A quiet-window retirement retires every active `arch-constraint` lesson whose `last_seen` is older than the window.
* *Retirement*: A retirement (supersede, remove, quiet-window retirement) requires a `coverage_verdict` from the closed set, with no default. `completely_covered` also requires `covering_clause` and a concrete `covering_input` that the clause's worked example resolves; a whitespace-only value counts as missing. The tombstone is written before the lesson is removed. A retirement acts only on a lesson resolved `found`, or on a `present_unreadable` lesson through an explicit operator action; in every other state it changes nothing and reports the state.
* *No Bulk Mutation*: The lesson store is never wiped or bulk-mutated; no bulk-mutation verb exists. A removal answering `absent` is not proof that the lesson never existed and is never retried automatically; it is reported together with the store-resolution discriminator.
* *Version Provenance*: The runtime stamps `tool_version` from its own release version (`PM-DIST-1`) at creation; it is never a `submit` parameter. An operator override is stored in `tool_version_override` beside the stamped value. Converted legacy lessons keep three states apart: no version field in the legacy lesson → `absent`; a field that cannot be resolved → `undetermined`; otherwise the recorded version. Conversion never backfills a version.
* *Promotion Provenance*: `promotions[]` records every destination that absorbed the lesson. A routing sweep or the `lesson-cleanup` harvester reports a lesson with a matching destination as `already_promoted` and never routes it again as new.

== Data Layer Integrity & Concurrency Invariants (`PM-IMPL-7`)

[#store-digest-verification]
=== Store Digest Verification Against Out-of-Band Edits

[[_store_digest_verification_against_out_of_band_edits]]
Because `.plan/` files reside in the repository working tree where an agent with filesystem write access could modify them directly outside the MCP server:

* Digests live in the sidecar `mcp/digests.json` (`{"format_version": 1, "stores": {"<relative path>": {"size": <int>, "sha256": "<hex>"}}}`), never inside a store they protect.
* On every server write to a plan store (`mcp/status.json`, `references.json`, `TASK-*.json`, `execution-manifest.json`, `metrics.json`, the findings, assessment, review-participation, and change-ledger JSONL files, `outline.md`, `request.md`), the server records the file's size and SHA-256 in the sidecar under the plan lock.
* The digest of a store is updated in the same transaction as the store write. A multi-store transaction that fails part-way re-records the digests of every store it already replaced before it releases the lock. Startup recovery re-verifies a store whose sidecar entry is older than the file against the pending-write marker of the interrupted transaction instead of reporting it as tampered.
* On every subsequent read inside a transition, the engine verifies size and SHA-256 against the sidecar. Any mismatch triggers an immediate `store_tampered` transition block requiring operator resolution.
* After a legacy `script` job finishes (it runs under the plan lock, `PM-MIG-2`), the runtime re-records the digests of the stores that job may write, so legitimate legacy writes never raise `store_tampered`.
* An intentional manual edit is accepted with `pm-mcp operator accept-edit <plan_id> <store>`, which re-baselines that store's digest and records the action in `audit.jsonl`.

[#three-way-footprint]
=== Three-Way File Footprint Reconciliation (`references.json`)

[[_three_way_file_footprint_reconciliation_references_json]]
The `references.json` store tracks three distinct file-footprint sets for a plan:

* *Declared Footprint (`declared_files`)*: Files explicitly listed during refinement/outline. `declared_files` is immutable after `outline.review` approval. A path admitted later by an accepted scope deviation is recorded in `approved_widening[]` with its provenance (deviation task, `approved_via`, phase, time), never appended to `declared_files`. The effective declaration is `declared_files ∪ approved_widening[].path`, and every reconciliation result names which of the two admitted a path.
* *Structured-Derived Footprint (`derived_files`)*: Re-derived by set union over the solution outline's structured deliverables and partitioned into two disjoint keys:
** `expected_modifications`: Files the plan intends to create, modify, or delete.
** `read_only_references`: Files inspected for context that must remain unmodified.
* *Realized Footprint (`realized_files`)*: Captured from the plan's own worktree via `git` jobs as the union of `git diff --name-status -M <base_ref>...HEAD` and `git status --porcelain=v1 -z`. A rename or copy contributes both its old and its new path to `realized_files` and is also recorded as a pair in `realized_renames[]`. *Deliberate change vs. `plan-marshall`*: `compute-footprint` uses `--name-only`, which drops the old path of a rename.

Resolution and capture rules:

* *Base Reference*: `<base_ref>` is `git merge-base HEAD origin/<base_branch>`, computed after the most recent fetch (after `sync-baseline`, the rebased-onto tip). It is never the SHA the plan was created against and never a local `<base_branch>` ref. Every footprint, scope, and self-review diff of the plan reads this one `base_ref`, recorded in `realized_state.base_ref`; after a `sync-baseline` or `branch-cleanup` rebase the realized footprint is re-derived against the new merge-base. When the local `<base_branch>` trails `origin/<base_branch>`, `realized_state.base_commits_behind` records by how many commits, so a stale local ref is visible although it is never used.
* *Own Tree Only*: The realized footprint resolves only from the plan's own worktree, through one resolver whose tiers (the live diff, then the persisted capture) apply identically to every consumer. A pending or absent worktree yields `realized_state.state: unresolved` with cause `pending` (not yet materialised) or `disabled` (`use_worktree == false`), never another tree's measured-empty set; `unresolved` and "measured, both sides empty" stay distinct. A diff-fed step without a resolvable footprint records `indeterminate` with the cause, never a clean `done`.
* *Capture Before Destruction*: `realized_files` is captured and persisted (`realized_state.captured_at`) at the latest before `branch-cleanup` (order 70) removes the worktree. Post-merge consumers read the persisted set; a post-merge git-derived empty set is never evidence of no change, and a missing persisted set makes the consumer report `indeterminate`. Steps that compute the footprint publish its size (`files_total`, `insertions_total`, and a source-vs-data split) as facts.
* *Consumer Scope and Provenance*: Every consumer that derives a scope from `references.json` names the set it reads. Footprint-scoped consumers (the self-review surfacer, `simplify`, `security-audit`) scope on `declared_files ∪ approved_widening[].path ∪ derived_files.expected_modifications ∪ realized_files`, re-read at each firing, and carry each path's provenance (`declared`, `widened`, `derived`, `realized`); a union is never passed on without it. `derive-verification` keeps reading the realized set only.

Pairwise reconciliation computes the **symmetric difference in both directions** ($A \setminus B$ and $B \setminus A$) across all three sets so that two equal-sized but disjoint file sets are reported as 100% disagreeing rather than matching by count. In addition:

* `derived_files \ realized_files` is reported split by intent: untouched `read_only_references` are expected, while untouched `expected_modifications` are reported as `modify_shortfall`.
* Paths from change-ledger entries with `change_origin: quality_gate_autofix` are reported separately from deliverable changes.
* Results are published per deliverable (from the deliverable's `Affected files` and its task and chain-tail change entries) beside the plan-level figures; a plan-level average never replaces them.

[#lesson-carry-back-veto]
=== Fail-Closed Lesson Carry-Back Veto on Plan Deletion

[[_fail_closed_lesson_carry_back_veto_on_plan_deletion]]
When the operator invokes plan deletion (`delete-plan` via elicitation or CLI):

1. The server scans the plan directory for any lessons created or carried during the plan's execution.
2. It executes `restore-from-plan` against the main-anchored global lesson store, producing a 4-state outcome (`restored`, `restore_incomplete`, `no_lesson_file`, `plan_dir_unresolved`; `not_attempted` when carry-back is explicitly opted out) plus a store-resolution discriminator confirming the main store was resolved and scanned. Only `restored` and `no_lesson_file` permit deletion; `restore_incomplete` and `plan_dir_unresolved` veto it.
3. If any carried lesson fails to land in the main-anchored store, the deletion is **vetoed fail-closed** and the plan directory is preserved intact.

[#lock-free-snapshot-reads]
=== Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)

[[_lock_free_snapshot_reads_transaction_locks_leases_pm_impl_7]]
* *Lock-Free Snapshot Reads*: Because every store update uses atomic write-and-rename (`<file>.tmp.<uuid>` -> `<file>`), all read-only operations (`pm_state`, `pm_plans`, `pm_epics`, `pm://` resources) read the current inode snapshot directly without acquiring file locks.
* *Transaction Locks*: Short locks held only for one transaction. When a transaction spans several scopes, they are acquired strictly in this order to prevent deadlocks:
** plan lock: `<main>/.plan/local/locks/plan-<plan_id>.lock`
** epic lock: `<main>/.plan/local/locks/epic-<epic_id>.lock`
** machine store locks: `~/.plan-marshall/mcp/locks/{merge,review-bot,build-slots}.lock`
+
Plan and epic locks live outside the directories they protect, so relocating a plan directory (link:move-journal.adoc[Move Journal Specification]) or editing an epic in a worktree never splits a lock.
* *Leases*: Long-lived claims (merge holder in `merge-queue.json`, review-bot windows in `review-bot-windows.json`, build slots in `build-slots.json`) are lease records with an owner (`plan_id` plus runtime instance PID and start instant) and an expiry (<<machine-lease-stores>>). A lease is claimed or released inside a short transaction on the machine store lock and is never held as an OS lock, so holding a lease while taking a plan lock does not invert the lock order.
* *Lock Manager*: All acquisitions in the runtime go through one lock manager (link:runtime-model.adoc#_in_process_lock_manager[Runtime & Interaction Model Specification]).

[#evidence-based-removal-sweeps]
=== Evidence-Based Removal Sweeps

Every removal sweep (legacy-surface retirement, retention purges of logs, archived plans and superseded lessons, worktree orphan sweeps, converter and migration-command retirement):

* runs as a dry run unless the operator explicitly applies it;
* reports for every kept item the first keep-rule that fired, and for every removed item the trigger that fired;
* reports the source (compiled default, `.plan/marshal.json`, machine configuration) of every configuration value it used;
* reports an empty population as one of `root_absent`, `root_unreadable`, `nothing_listed`, or `all_kept`, never as a bare zero;
* never removes an item on absence of evidence: a missing marker, record, or audit tombstone keeps the item and reports it as `skipped_no_evidence`.

[#legacy-store-formats]
=== Legacy Store Formats & One-Time Conversion (`PM-MIG-3`, `PM-MIG-5`)

The schemas in this document are the target formats. Legacy `plan-marshall` stores differ; each store switches exactly once, in the stage that ports it, through a legacy -> target converter, and every legacy script touching that store is ported or retired in the same stage. Each converter has a reverse converter used by `pm-mcp operator rollback`.

* *No Defaulted Fields*: A converter that cannot populate a target field from legacy data never defaults it. The cutover receipt records `{source_format, missing_fields[]}` for every partially converted record, keyed by its identifier, together with the count per store, and consumers treat those fields as absent.
* *Mapped Identifiers*: Each store conversion writes a cutover receipt that lists every in-flight plan and epic whose stored identifiers (`from_epic`, spec references, queue row identifiers) the converter mapped, and refuses the switch for that store when any identifier cannot be mapped.

IMPORTANT: The legacy formats below were verified against `plan-marshall` commit `1d4a1da37`. `plan-marshall` keeps evolving: before implementing a converter, re-verify the legacy format of that store against the latest `plan-marshall` version and update this table.

[cols="1,3,2"]
|===
|Store |Legacy format (verified snapshot) |Conversion notes

|Plan status
|`.plan/local/plans/<id>/status.json` with `title`, `short_description`, `current_phase`, `phases[{name,status}]`, `created`, `updated`, `metadata` (`manage-status/scripts/_cmd_lifecycle.py`); merge authorizations in `metadata.merge_authorizations`, keyed by kind, `{head, gap_class, granted_over, reason, granted_at}`, re-grant overwrites (`_cmd_merge_authorization.py`)
|Split into the target plan record and `mcp/status.json`; map phase names and statuses; map keyed merge authorizations to the target array.

|Tasks

|Map field names and status enums; keep task numbers; `verification{commands,criteria,manual}` maps unchanged to the target `verification` object.

|Findings
|`artifacts/findings/{type}.jsonl` (one file per type), `artifacts/findings/qgate-{phase}.jsonl`, `artifacts/findings/assessments.jsonl`; 6-character `hash_id`; 14 types `bug\|improvement\|anti-pattern\|triage\|tip\|insight\|best-practice\|build-error\|test-failure\|lint-issue\|sonar-issue\|arch-constraint\|pr-comment\|pr-comment-overflow` (`tools-file-ops/scripts/constants.py`, verified at `plan-marshall` `f3de0e14f`); severity `error\|warning\|info`; resolution `pending\|fixed\|suppressed\|accepted\|taken_into_account\|rejected` (`manage-findings/scripts/_findings_core.py`)

|`references.json` with `affected_files`, `read_intent_files`, `realized_footprint`; the structured-derived set is recomputed, never stored (`manage-references/scripts/_references_crud.py`)
|Map key names; do not persist the derived set unless the target schema requires it.

A lesson whose header cannot be parsed is listed in the cutover receipt as `unreadable` with a named diagnostic and kept verbatim, never dropped; every converted lesson that lists is addressable by its id. Tombstones are kept. The reverse converter restores the legacy layout.

|Change ledger
|Repository-level `.plan/work/change-ledger.jsonl` (not plan-scoped, `NO_PLAN` rows) with `timestamp_iso`, `duration_seconds`, status `success\|error\|timeout\|killed\|unknown` (`manage-change-ledger/scripts/_ledger_core.py`)

|Learned build timeouts

|`^[a-z][a-z0-9-]*$` (`tools-input-validation/scripts/input_validation.py`); epic slugs are validated with the same function (`plan-orchestrator/scripts/orchestrator.py`, verified at `plan-marshall` `f3de0e14f`)
|Legacy plan IDs and epic slugs of 3–64 characters that do not end in `-` are valid target IDs (phase-workflows.adoc, Plan ID Derivation) and are kept unchanged; any other legacy ID is an unmappable identifier and refuses the switch for its store (*Mapped Identifiers* above). The reverse converter refuses plans whose IDs fall outside the legacy grammar.

=== Differential Equivalence Harness & Executor Shadow Routing (`PM-TEST-2`, `PM-MIG-1`)

* *Shared Corpus Differential Runner (`PM-TEST-2`)*: In JUnit 5 (`pm-mcp-core`), parameterized differential tests execute each `Ported` Java store primitive and its reference Python counterpart against identical initial `.plan/` directory trees. The harness maps the Python result through the store's legacy -> target converter, canonicalizes JSON/JSONL outputs (normalizing generated UUIDs and ISO-8601 timestamps), and asserts zero structural diff across both returned payloads and resulting stores for all canonical store read/write invariants.
* *Known-Defect Baseline*: A known defect of the Python reference is either fixed in `plan-marshall` before the differential run or recorded as a named *deliberate change* with its own fixture, for which the harness asserts the corrected behaviour. A differential run never adopts a known defect as the equivalence baseline, and an equivalence proof for a structural refactor is taken only after every behaviour fix touching the same code has landed.
* *Executor Shadow Routing (`PM-MIG-1`)*: During Migration Stages 1 and 2, the runtime's executor adapter supports shadow-routing `Ported` read/write operations to the Java primitive while comparing results against the Python baseline (mapped through the converter), logging any divergence to `audit.jsonl` and triggering automatic fallback (`PM-MIG-5`) if a discrepancy occurs.
