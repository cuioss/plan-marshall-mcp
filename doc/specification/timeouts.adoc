== Overview

This document is the single normative source of every timeout, time window, wait window, budget, deadline, expiry, idle limit, heartbeat, back-off, interval, and age-based retention of *plan-marshall-mcp* (`PM-MCP`) (operator decisions D70 and D74). Every other requirement and specification names *what* is timed and links the anchor here for the value, its derivation, its configuration key, its floor or cap, and the behaviour on expiry; none of them restates a number or a derivation rule.

JSON Schemas of configuration stores (`machine-config.json` and the per-project enrolment files `enrolments/<project_id>.json` in link:store-schemas.adoc[Store Schemas Specification], the client profile schema in link:client-profiles.adoc[Client Profiles Specification]) keep their `default`, `minimum`, and `maximum` values because a schema must be self-contained; each of those values equals the value registered here, and a divergence is a defect of the schema.

Every duration is stated in seconds unless the table says otherwise. Deadlines are measured on the monotonic clock of the process that enforces them; persisted instants (`lease_expires_at`, `reset_at`, next-allowed timestamps) follow the one wire shape of link:store-schemas.adoc[Store Schemas Specification] (RFC 3339 UTC).

Not in scope: the startup and memory bounds of `PM-TECH-3` (performance bounds, not timeouts, defined there), the token and wall-minute spend anchors of link:dispatch-and-effort.adoc#spend-accounting-budget-anchors[Dispatch & Effort Specification, Spend Accounting] (spend warnings, never a deadline).

== Table Conventions

Every group below is one normative table with the columns:

* *Name*: what is timed.
* *Value / derivation*: the compiled default or the rule that computes the value.
* *Configurable?*: the configuration key and its store, or `fixed` (compiled into the binary; changed only by a release).
* *Floor / cap*: the bounds a configured or derived value is clamped to; `—` when none applies.
* *Applies to*: the jobs, calls, or records the value governs.
* *Behaviour on expiry*: what happens when the time runs out.
* *Defined for*: the sections that use the value (they link here and restate nothing).

A value marked _open_ is not yet defined; it belongs to the named open design topic, and nothing may assume a value for it until that topic defines it here.

== Job Budgets & Escalation
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-3[PM-WATCH-JOB-3], link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-15[PM-WATCH-JOB-15], link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-16[PM-WATCH-JOB-16]_

Every job, and every in-process `git` or `ci` operation of the native variant (<<in-process-operations>>), runs under a wall-clock budget $t$ allocated at its start and recorded, with its `budget_derivation`, in the job record (`PM-EXEC-4`, `PM-EXEC-6`); the representation carries neither, since the derivation only selects the retry link the server offers (link:hypermedia-format.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). The budget is keyed per project by the *budget key*:

* build jobs: the canonical command `<build_system>:<verb>[@<module_id>][+<profile>…]` (canonical verb from the link:job-runtime.adoc#canonical-build-verbs[Canonical Build Verb Set], module omitted for a whole-tree run, profiles sorted), for example `maven:verify+pre-commit` or `maven:module-tests@plan-marshall-mcp`;
* `git` and `ci` operations: `<kind>:<operation>`, where `<operation>` is the closed contract operation name of the composing primitive, for example `git:worktree-remove` or `ci:checks`. The key is the same for the native and the CLI variant: a project uses one variant per integration, so the key needs no variant component;
* `project_script` jobs: `project_script:<project_script_id>`.

Learned values live in the project's `<PM_MCP_BASE>/projects/<project_id>/build-timings.json` (link:store-schemas.adoc#build-timings-store[Store Schemas, Build Timings Store]) under this key (link:job-runtime.adoc#_adaptive_timeout_learning[Job Runtime Specification, Adaptive Timeout Learning], which defines which runs feed the learned baseline).

[#in-process-operations]
=== In-Process Operations of the Native Variant

A native `git` or `ci` operation runs inside the runtime, not as a process (link:job-runtime.adoc#in-process-operations[Job Runtime Specification, In-Process Operations]); the operation classes, floors, allocation, learning, escalation, and the no-verdict rule above apply to it unchanged:

* *Cooperative Cancellation*: At budget expiry, on `cancel:<job_id>`, and at drain, the runtime cancels the operation cooperatively: JGit operations through their `ProgressMonitor` (`isCancelled`) and revision-walk cancellation, provider requests by interrupting the HTTP exchange. Every HTTP request additionally carries the <<http-request-timeout>>, so no single request can outlast the class budget.
* *Abandonment*: An operation that has not returned within the termination grace period (<<grace-period>>) after cancellation is abandoned: it is recorded at the deadline, and the result that arrives later is discarded.
* *Partial Results Discarded*: A cancelled or abandoned operation yields no result record; nothing it observed before the cancellation is used. A mutation it may have applied is established only from the observed repository or provider state before any retry, as for a job (a push by `ls-remote`, a merge or enqueue by the provider observation, a worktree removal by the <<worktree-remove-recheck>>).
* *Outcome*: Budget expiry records `timed_out`, which is `no_verdict` (<<no-verdict-rule>>); cancellation records `cancelled`, drain records `killed`.

[#no-verdict-rule]
=== Timed-Out Outcomes Are No-Verdict (D70)

* *Every `timed_out` is `no_verdict`*: A job settled `timed_out` counts as `no_verdict` in every roll-up (landing facts, metrics, gate facts, CI taxonomy, finding counts), never as `failed` and never as `succeeded`, whatever its `budget_derivation`. It never fails a gate, and it emits zero located code errors or findings (`PM-EXEC-4`).
* *The derivation selects only the retry offer*: A `timed_out` job auto-offers `retry` with the escalation budget $E$ when $E > t$ (derivations `floor_default`, `learned`, `operator`, and `escalated` below the cap). When $E = t$ (the budget already reached $\max(t, C)$) or for a `project_script`, `retry` is offered at $t$ together with `escalate`, so the operator can enrol an operator budget above the cap.
* *Budget statistic*: A budget always names the statistic it came from (the blend $L$ with its observation count, never a median or percentile); a p50 or p95 duration quoted in a record or report is labelled as such and is never used as a budget.

[#worktree-remove-recheck]
=== Partial-Removal Re-Check after a Timed-Out `git worktree remove` (D74)

A `timed_out` `git worktree remove` can leave a partially deleted tree. Before any retry and before the removal is recorded:

1. The runtime runs `git.worktree-list` in the main checkout (budget class <<git-local-budget>>) and checks whether the worktree directory still exists.
2. *Unregistered and absent*: the removal is complete; it is recorded (`worktree_path: null`) with `removal_evidence: recheck`.
3. *Registered but the directory is absent*: the runtime runs `git.worktree-prune` and repeats step 1 once; it records the removal only on the re-checked positive evidence.
4. *Directory present (registered or not)*: `worktree_path` stays set, the step reports `worktree_removal: partial` with the remaining path, and `retry` is offered with the escalation budget; the retry never adds `--force`.
5. *Re-check itself fails or times out*: the removal is `indeterminate`; nothing is recorded as removed (link:store-schemas.adoc#evidence-based-removal-sweeps[Store Schemas, Evidence-Based Removal Sweeps]).

[#configuration-keys]
== Configuration Keys

The configurable values above, by store:

* `machine-config.json` (operator CLI, link:store-schemas.adoc#machine-config[Store Schemas, Machine Configuration Store]): `drain_timeout_seconds`, `escalation_cap_seconds`, `progress_wait_max_seconds`, `lsp_idle_timeout_seconds`, `lsp_start_timeout_seconds`, `lsp_request_timeout_seconds`, `audit_rotation.max_days`, and `project_defaults.retention.*` (machine-wide defaults of the per-project retention keys).
* `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (operator CLI, link:store-schemas.adoc#local-config[Store Schemas, Operator Local Configuration]): `retention.*`.
* `enrolments/<project_id>.json` (operator CLI, link:store-schemas.adoc#enrolment-store[Store Schemas, Project Enrolment Store]): `command_budgets` (operator budgets per budget key), `project_scripts.<project_script_id>.max_timeout_seconds`.
* Client profile (compiled, operator override in `<PM_MCP_BASE>/conf/profiles/`): `connection.bounded_wait_seconds`, `connection.idle_timeout_seconds`, `connection.progress_resets_timeout`.

No team configuration file (`.marshall/config/*.json`) holds a timeout, wait, threshold, or retention value. Tuning values that calibrate server algorithms are compiled constants (`fixed` above, and in the owning specification: the recipe auto-route threshold `0.6`, the lane prune thresholds, the refine confidence threshold `95`, the iteration caps, the step wait timeouts, the preference recurrence threshold, the untrusted raw-input byte cap, the review rate-window floor `3600`, the re-review completion allowance `600`, the default review attempt ceiling `6`, the provider re-poll cadence `30`, the merge-queue stall fallback `3600`, the native request timeouts, the `git.commit-fix` cap of `3` failed commit attempts per identical staged change set: staged tree id plus message, reset when either changes, CLI variant only, exhaustion ends `attempts_exhausted` in `git.done-aborted` and the caller's `<phase>.commit-aborted`); per-project tuning would make metrics incomparable across projects (`PM-MIG-5` triggers).

A value outside its floor or cap is never used: the runtime clamps it to the bound and reports the configured value, the used value, and the source (`machine_config`, `local_config`, `enrolment`, `profile_override`, `compiled_default`, `invalid`, or `unreadable`) in `pm-mcp status` and in the record of the affected job or wait, never in its facts: the model cannot change an operator value.

[#resolved-divergences]
== Resolved Divergences

The definitions that existed before this document, and how they were resolved:

[cols="2,4"]
|===
|Item |Divergence and resolution

|No-verdict rule
|`PM-EXEC-6` and Adaptive Timeout Learning made only a `timed_out` job with a `floor_default` or `escalated` budget no-verdict, while Process Termination counted every `timed_out` as `no_verdict`. Every `timed_out` is now `no_verdict`; the derivation selects only the retry offer (<<no-verdict-rule>>).

|Escalation
|$E = \min(2 \times t, 1800)$ lowered the budget when $t > 1800$ (for example after an operator budget above the cap). Now $E = \max(t, \min(2 \times t, C))$ with the configurable cap $C$.

|Operator budget vs floors
|Job Runtime let an operator per-command budget "win over every derivation", while Domain Extensions said floors are "never violated, even if an explicit bound is configured". An operator budget may exceed the cap but is clamped up to the engine floor ($\max(F, O)$), as `plan-marshall`'s explicit bound is.

|Python floor
|Job Runtime and `PM-EXEC-6` put the `330` floor on "pytest", Domain Extensions on "pyproject". `plan-marshall` applies `PYTEST_OUTER_FLOOR_SECONDS` to every pyproject command; the floor is keyed by build system (`pyproject`).

|Progress notification interval
|Job Runtime emitted frames every 5 s, `PM-IMPL-4` required "at least every 60 seconds", and the Hypermedia Format described "60s MCP progress notifications". The interval is `5`; `60` is the ceiling between two frames.

|LSP idle key
|MCP Tools named the eviction key `idle_timeout_seconds`, which is the client profile's host idle timeout; the key is `lsp_idle_timeout_seconds` in `machine-config.json`.

|Drain timeout key
|Runtime Model referenced `drain_timeout_seconds` in `machine-config.json`, which the schema did not define; the key is now in the schema.

|Git, CI and script budgets
|Undefined (D74); a watch fixture recorded a 60 s git budget firing twice. Defined per operation class with floors (<<job-budgets>>); `project_script` uses the enrolled maximum, which the enrolment schema did not carry. The classes apply unchanged to the in-process operations of the native variant (<<in-process-operations>>).

|Review-bot window floor and attempt ceiling
|This document and Phase Workflows registered different rate-window floors, and the registry's default `attempt_ceiling` had no source. The floor is `3600` and the default ceiling `6`, `plan-marshall`'s window default and attempt cap (<<review-bot-windows>>).

|Bounded wait vs host idle timeout
|"Safely below the host's idle timeout" had no rule; profile validation now rejects `bounded_wait_seconds` above `idle_timeout_seconds − 30`.

|`dispatch_id` expiry
|MCP Tools and the Workflow DSL rejected a `dispatch_id` that is "superseded or expired", but the dispatch lifecycle defines no expiry; a `dispatch_id` is stale only when superseded.
|===
