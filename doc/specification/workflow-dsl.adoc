== Overview

This document specifies the declarative Workflow Domain-Specific Language (DSL), Abstract Syntax Tree (AST) model, typed Java `Primitive<P, R>` execution contract, loop-back guard semantics, automated diagram generation, and the verification harnesses (including the out-of-band behavioural conformance harness for model-facing content) for *plan-marshall-mcp* (`PM-MCP`). The workflow engine and DSL reside in the plain-Java `pm-mcp-core` module with zero runtime framework dependencies and are assembled into the native daemon by `pm-mcp-server`.

== Module Boundary & Decoupled Core Architecture
_See Requirement link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1: Decoupled Plain-Java Core Engine & Quarkus Assembly]_

The workflow engine is strictly decoupled from Quarkus, CDI, Vert.x, and MCP transport libraries. During the initial M1 scaffold, packages reside within the root `plan-marshall-mcp` Maven module and are extracted into dedicated Maven sub-modules (`pm-mcp-core`, `pm-mcp-server`, `pm-mcp-dist`) with ArchUnit boundary enforcement before M2 distribution packaging:

[cols="1,2,3"]
|===
|Module |Package Namespace |Responsibilities & Allowed Dependencies

|`pm-mcp-core`
|`de.cuioss.pm.mcp.core.workflow.*`
|Contains the line-oriented DSL lexer/parser, immutable AST records, compile-time/startup static verifier, `Primitive<P, R>` SPI, deterministic state machine interpreter, and Mermaid/AsciiDoc-table/ASCII diagram generators. Depends *only* on the JDK (`java.base`) and `cui-java-tools` / Jackson annotations. Unit tests execute directly in JUnit 5 without Quarkus augmentation.

|`pm-mcp-server`
|`de.cuioss.pm.mcp.server.*`
|Instantiates core engine services via CDI `@Produces`, binds concrete `Primitive` implementations to the daemon's job runner and state stores, registers persisted records via `@RegisterForReflection`, and maps `pm_start`, `pm_state`, and `pm_do` calls to the engine.

|`pm-mcp-dist`
|`de.cuioss.pm.mcp.dist.*`
|Packages the GraalVM native executable (`pm-mcp`), static `skill://pm/**` corpus resources, and platform archive artifacts (`tar.gz`, Homebrew formula, JBang catalog).
|===

== Formal EBNF Grammar for the Workflow DSL
_See Requirement link:../Requirements.adoc#PM-WF-2[PM-WF-2: Closed Link Relation Grammar & Link Forms]_

_See Requirement link:../Requirements.adoc#PM-WF-3[PM-WF-3: Capability Enforcement by Link Omission]_

_See Requirement link:../Requirements.adoc#PM-WF-4[PM-WF-4: Entity-Scoped Links & Fine-Grained Concurrency]_

_See Requirement link:../Requirements.adoc#PM-WF-9[PM-WF-9: Composite Wait States & Short-Circuit Failure Handling]_

_See Requirement link:../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

Workflow definitions (`*.pmwf` resources compiled into the binary under `classpath:/workflows/`) conform to the following ISO/IEC 14977 Extended Backus-Naur Form (EBNF) grammar. The DSL is line-oriented; comments start with `#` and run to the end of the line.

[source,ebnf]
----
workflow_file        = workflow_header ,
                       ( subworkflow_decl | [ scope_decl ] ) ,
                       start_decl ,
                       { migrate_decl } ,
                       state_decl , { state_decl } ;

workflow_header      = "workflow" , state_id , "version" , positive_int , EOL ;
scope_decl           = "scope" , ( "plan" | "epic" | "entity" ) , EOL ;
subworkflow_decl     = "scope" , "subworkflow" , EOL ,
                       { subworkflow_param } ;
subworkflow_param    = "param" , identifier , ":" , subworkflow_type , EOL ;
subworkflow_type     = enum_type
                     | "int" , [ int_range ] ;
start_decl           = "start" , state_id , EOL ;
migrate_decl         = "migrate" , state_id , "->" , state_id , EOL ;

state_decl           = "state" , state_id , [ "terminal" , [ outcome_id ] ] , EOL ,
                       [ phase_clause ] ,
                       [ skill_clause ] ,
                       [ facts_clause ] ,
                       state_body ;

phase_clause         = "phase" , identifier , EOL ;
skill_clause         = "skill" , skill_path , EOL ;
facts_clause         = "facts" , primitive_id , EOL ;

state_body           = (* empty for terminal states *)
                     | auto_clause
                     | job_clause
                     | call_clause
                     | link_clause , { link_clause } ;

auto_clause          = "auto" , primitive_id , EOL ,
                       outcome_transition , { outcome_transition } ;

job_clause           = ( "job" | "composite_job" ) , primitive_id , EOL ,
                       outcome_transition , { outcome_transition } ;

call_clause          = "call" , state_id , [ "(" , [ call_arg_list ] , ")" ] , EOL ,
                       outcome_transition , { outcome_transition } ;
call_arg_list        = call_arg , { "," , call_arg } ;
call_arg             = identifier , "=" , ( enum_value | positive_int_or_zero ) ;

link_clause          = "link" , relation , link_id_pattern ,
                       [ "[" , link_form , "]" ] ,
                       "(" , [ param_list ] , ")" , EOL ,
                       [ guard_clause ] ,
                       link_action ,
                       outcome_transition , { outcome_transition } ;

relation             = "next" | "alt" | "retry" | "fix" | "loop_back"
                     | "submit" | "dispatch" | "wait" | "escalate"
                     | "abort" | "emit" ;

link_form            = "submit" | "wait" | "dispatch" | "escalate" | "noop" ;

link_id_pattern      = action_id , [ ":" , ( entity_placeholder | identifier ) ] ;
entity_placeholder   = "<" , identifier , ">" ;

param_list           = param_decl , { "," , param_decl } ;
param_decl           = identifier , ":" , type_spec , [ "?" ] ;

type_spec            = scalar_type
                     | "list" , "<" , scalar_type , ">" ;
scalar_type          = "text" , [ int_range ]
                     | "int" , [ int_range ]
                     | enum_type ;
enum_type            = "enum" , "[" , enum_value , { "|" , enum_value } , "]" ;

int_range            = positive_int_or_zero , ".." , positive_int ;

guard_clause         = "guard" , guard_expr , EOL ;
guard_expr           = guard_term , { "or" , guard_term } ;
guard_term           = guard_factor , { "and" , guard_factor } ;
guard_factor         = [ "not" ] , ( guard_atom | "(" , guard_expr , ")" ) ;
guard_atom           = "in_worktree"
                     | "has_open_findings"
                     | "all_tasks_completed"
                     | "predicate:" , primitive_id ;

link_action          = ( "do" , primitive_id , EOL )
                     | ( "dispatch" , identifier , ( "role" , identifier | "level" , ( "1" | "2" | "3" | "4" | "5" | "6" | "7" | "inherit" ) ) , EOL )
                     | ( "escalate" , identifier , EOL ) ;

outcome_transition   = outcome_id , "->" , state_id , EOL ;

state_id             = identifier , { "." , identifier } ;
primitive_id         = identifier , "." , identifier ;
skill_path           = "pm/" , identifier , { "/" , identifier } ;  (* maps to the URI "skill://" , skill_path , "/SKILL.md" *)
outcome_id           = identifier ;
action_id            = identifier ;
identifier           = lowercase_alpha , { lowercase_alpha | digit | "_" | "-" } ;
enum_value           = letter , { letter | digit | "_" | "-" } ;
positive_int         = nonzero_digit , { digit } ;
positive_int_or_zero = "0" | positive_int ;
letter               = lowercase_alpha | uppercase_alpha ;
lowercase_alpha      = ? ASCII "a".."z" ? ;
uppercase_alpha      = ? ASCII "A".."Z" ? ;
digit                = "0" | nonzero_digit ;
nonzero_digit        = ? ASCII "1".."9" ? ;
any_char_except_nl   = ? any Unicode scalar value except "\n" ? ;
EOL                  = [ "#" , { any_char_except_nl } ] , "\n" ;
----

Identifiers (state, primitive, action, parameter, and outcome names) are lowercase. Enum values are a separate token (`enum_value`) that also admits upper case, so closed domain vocabularies such as `enum[FIX|SUPPRESS|ACCEPT]` are expressible verbatim. Lists use the single syntax `list<…>` in both the DSL and the hypermedia `free` column (link:hypermedia-format.adoc[Hypermedia Format Specification]); there is no object type and no boolean type.

`param` declarations are permitted only in the header of a `scope subworkflow` file. They declare the complete closed parameter schema that every `call` site must bind (Rule 6 in <<static-verification-rules>>); sub-workflow parameters are restricted to `enum[…]` and `int` because they are bound from literal values at the call site, never from model input.

[#workflow-definition-units]
=== Workflow Definition Units (Multi-File Workflows)

A workflow definition may be split across several `.pmwf` files:

* *Plan workflow*: All phase workflow files of a plan (`init.pmwf`, `refine.pmwf`, `outline.pmwf`, `plan.pmwf`, `execute.pmwf`, `finalize.pmwf`) together form *one* workflow definition. The loader merges them into a single `WorkflowDefinition` before validation: `states` and `migrations` are the union of all files, the definition's `startState` is the `start` of `init.pmwf`, and the `start` of every other phase file names that phase's entry state. A transition in one phase file may therefore target a state declared in another (for example `allocated -> execute.dispatch-ready` in `finalize.pmwf`).
* *Other top-level workflows*: Every other file with `scope plan`, `epic`, or `entity` (for example `orchestrator.pmwf`, `steward.pmwf`, `pr-doctor.pmwf`) forms a single-file definition.
* *Sub-workflows*: Every `scope subworkflow` file (for example `git-commit-and-push.pmwf`) is a separately scoped definition. Its states are never merged into a caller's definition and are reachable only through `call`; transitions inside a sub-workflow may target only states of the same sub-workflow, and transitions outside it may never target a sub-workflow state.

All static verification rules (<<static-verification-rules>>) run over the merged definition unit: state identifiers must be unique across all files of the unit, transition targets must exist in the unit, every state must be reachable from the unit's `startState`, outcome coverage is exhaustive per state, and link identifier patterns are unique within their state.

[#implicit-job-links]
=== Implicit Links of Job States

Every `job` and `composite_job` state implicitly offers two links that are never declared in DSL source:

[cols="1,1,1,3"]
|===
|Link |`rel` |`form` |Semantics

|`wait:<job_id>`
|`wait`
|`wait`
|Bounded blocking wait on the running job (`PM-WF-8`); returns the next state's representation once the job settles, or the updated running representation.

|`cancel:<job_id>`
|`abort`
|`noop`
|Cancels the running job (for a composite job, all constituent jobs); the job settles with the outcome `cancelled`.
|===

`<job_id>` is the job identifier of a `job` state (for example `wait:b-2291`) and the composite identifier, which equals the state identifier, of a `composite_job` state (for example `wait:finalize.concurrent-wait`). The outcome enumeration of every `job` and `composite_job` primitive contains `cancelled`, so every such state must declare an explicit `cancelled -> <state>` outcome transition; Rule 2 (exhaustive outcome coverage) enforces it. A `job` state's outcome enumeration is the closed job outcome set of `PM-EXEC-4` (`succeeded`, `failed`, `failed_unparsed` for build jobs only, `refused`, `cancelled`, `timed_out`, `killed`, `indeterminate`); a `composite_job` primitive declares its own closed workflow outcomes (`PM-WF-8`). A DSL link whose identifier pattern collides with an implicit link fails validation.

[#escalation-decision-wait]
=== Escalation Without Elicitation & the Implicit Decision Wait

An `escalate <decision>` link action requests an operator decision (`PM-SEC-3`). On a connection that declared elicitation support, the engine prompts through `elicitation/create` and takes the link's outcome transition for the answer. Otherwise it records the pending decision in the scope's `mcp/status.json` (`pending_decision` with a fresh `decision_id`, link:store-schemas.adoc[Store Schemas Specification]) and moves the scope to its `<phase>.blocked` state, whose representation carries `facts.operator_command` and offers exactly one implicit link:

[cols="1,1,1,3"]
|===
|Link |`rel` |`form` |Semantics

|`wait:decision:<decision_id>`
|`wait`
|`wait`
|Bounded wait (`PM-IMPL-4`) on the pending decision record. Once the operator resolves the decision through `pm-mcp operator`, the escalate link's outcome transition for that resolution is taken and the next state's representation is returned; when the wait bound expires, the unchanged `*.blocked` representation is returned.
|===

The `wait:decision:` identifier prefix is reserved for this implicit link; a DSL link whose identifier pattern collides with it fails validation.

=== Reference Workflow DSL Excerpt (`finalize.pmwf`)

[source,text]
----
workflow finalize version 1
scope plan
start finalize.settle-commit
migrate finalize.push_wait -> finalize.push-barrier

state finalize.settle-commit
  phase finalize
  call git.commit_and_push (message_mode=step_or_fallback, push_mode=post_pr_conditional)
    committed_local      -> finalize.next-step
    committed_and_pushed -> finalize.review-cap-check
    pushed_clean         -> finalize.review-cap-check
    clean                -> finalize.next-step
    aborted              -> finalize.aborted

state finalize.push-barrier
  phase finalize
  call git.commit_and_push (message_mode=none_assert_clean, push_mode=if_configured)
    committed_local      -> finalize.create-pr
    committed_and_pushed -> finalize.create-pr
    pushed_clean         -> finalize.create-pr
    clean                -> finalize.create-pr
    aborted              -> finalize.aborted

state finalize.review-cap-check
  phase finalize
  auto review.check-structural-caps
    within_caps         -> finalize.concurrent-wait
    cap_exceeded        -> finalize.review-structural

state finalize.concurrent-wait
  phase finalize
  composite_job finalize.watch-ci-and-bots
    all_green                -> finalize.merge-gate
    findings_open            -> finalize.triage
    ci_failed                -> finalize.ci-failed
    bot_refused_awaitable    -> finalize.review-window-wait
    bot_refused_hard         -> finalize.review-escalate
    bot_refused_structural   -> finalize.review-structural
    bot_no_unreviewed_commit -> finalize.review-full-trigger
    bot_unproven             -> finalize.review-escalate
    cancelled                -> finalize.wait-cancelled

state finalize.review-window-wait
  phase finalize
  facts review.window-status
  job review.await-rate-window
    succeeded           -> finalize.review-retrigger
    failed              -> finalize.review-escalate
    refused             -> finalize.review-escalate
    cancelled           -> finalize.wait-cancelled
    timed_out           -> finalize.review-escalate
    killed              -> finalize.review-escalate
    indeterminate       -> finalize.review-escalate

state finalize.review-retrigger
  phase finalize
  auto review.retrigger-unproven
    triggered           -> finalize.review-cap-check
    window_closed       -> finalize.review-window-wait

state finalize.review-escalate
  phase finalize
  facts review.window-status
  link retry retry:<bot_kind> [noop] ()
    guard predicate:review.window-open
    do review.retrigger-bot
      triggered         -> finalize.review-cap-check
      window_closed     -> finalize.review-window-wait
  link escalate escalate [escalate] (reason: text 1..500)
    escalate review_barrier_gap
      approved          -> finalize.merge-gate
      denied            -> finalize.aborted

state finalize.ci-failed
  phase finalize
  skill pm/finalize/ci-triage
  facts ci.failure-summary
  link fix fix_in_branch [submit] (fix_summary: text 1..2000)
    do finalize.record-in-branch-fix
      recorded          -> finalize.settle-commit
      no_changes        -> finalize.ci-failed
  link loop_back loop_back [submit] (remediation_summary: text 1..2000)
    guard in_worktree
    do plan.allocate-remediation-tasks
      allocated         -> execute.dispatch-ready
      limit_reached     -> finalize.loop-limit-reached
  link escalate escalate [escalate] (reason: text 1..500)
    escalate ci_failure_override
      approved          -> finalize.merge-gate
      denied            -> finalize.aborted

state finalize.wait-cancelled
  phase finalize
  facts finalize.wait-status
  link retry retry [noop] ()
    do finalize.restart-watch
      started           -> finalize.concurrent-wait
  link escalate escalate [escalate] (reason: text 1..500)
    escalate wait_cancelled_override
      approved          -> finalize.merge-gate
      denied            -> finalize.aborted

state finalize.loop-limit-reached
  phase finalize
  facts plan.loop-status
  link escalate escalate [escalate] (reason: text 1..500)
    escalate loop_limit_extension
      extended          -> execute.dispatch-ready
      aborted           -> finalize.aborted

state finalize.aborted terminal
  phase aborted
----

* *Hard CI failure (`PM-WF-9`)*: `finalize.ci-failed` offers both remediation paths. `fix_in_branch` (rel `fix`) is followed after the model has applied the fix in the worktree; `finalize.record-in-branch-fix` records `fix_summary` and routes through `finalize.settle-commit` (`call git.commit_and_push` with `push_mode=post_pr_conditional`), whose `committed_and_pushed` outcome re-enters `finalize.concurrent-wait` (through `finalize.review-cap-check`) so CI and review bots re-evaluate the new `HEAD`. A clean worktree yields `no_changes` and leaves the plan in `finalize.ci-failed`. `loop_back` returns to `execute` for cross-task remediation (<<loop-back-bounds>>).
* *Pre-wait cap gate*: Before `finalize.concurrent-wait` is entered, `finalize.review-cap-check` measures the diff (changed files, diff characters) against the structural caps each required review bot declares in the review-bot registry (link:phase-workflows.adoc[Phase Workflows Specification]). An exceeded cap records the bot as `refused` with mode `size` pre-emptively, names the cap and the measurement in `facts`, and routes to `finalize.review-structural` instead of waiting; under every cap the flow is unchanged.
* *Review-bot refusal modes*: The composite outcomes of `finalize.watch-ci-and-bots` separate the refusal modes, because a single rate-limit outcome cannot express them. `bot_refused_awaitable` (a rate window that reopens) enters `finalize.review-window-wait`, a job that waits for the registered window (the registered interval times the attempt ceiling; a published ETA is a floor that is re-checked, never skipped) and then re-triggers the unproven bots automatically. `bot_refused_hard` (weekly or hard quota) and `bot_unproven` (no review evidence for the current `HEAD` after the wait) enter `finalize.review-escalate`. `bot_refused_structural` (size) enters `finalize.review-structural`, which offers split, accept, and disable-for-this-PR but never a wait; when a path partition (for example test sources versus the rest) brings each part under the cap, it proposes that concrete split. `bot_no_unreviewed_commit` enters `finalize.review-full-trigger`, which posts the registry's full-review trigger verb.
* *Window-gated re-trigger*: `finalize.review-escalate` offers `retry:<bot_kind>` only while the predicate `review.window-open` holds, so a trigger is never posted inside a closed rate window (a trigger in a closed window extends it; closing and reopening the PR does not reset it). The `<bot_kind>` placeholder expands over the bots of the required set that have no review evidence for the current `HEAD`, selected after the round's own comment fetch and never by comment recency; a required bot that never published is selectable. A closed window at execution time routes to `finalize.review-window-wait`.
* *Implicit job links*: `finalize.concurrent-wait` is a `composite_job` state and therefore offers `wait:finalize.concurrent-wait` and `cancel:finalize.concurrent-wait` without declaring them (<<implicit-job-links>>). Following `cancel` yields the composite outcome `cancelled`, handled by `finalize.wait-cancelled`.
* *Cross-file targets*: `execute.dispatch-ready` is declared in `execute.pmwf`; the target is valid because all phase files form one definition unit (<<workflow-definition-units>>).

== AST Node Model

_See Requirement link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1: Decoupled Plain-Java Core Engine & Quarkus Assembly]_

The parser produces an immutable tree of Java 25 `record` and `sealed interface` nodes in `de.cuioss.pm.mcp.core.workflow.ast`:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.ast;

import java.util.List;
import java.util.Map;
import java.util.Optional;

public record SourceLocation(String resourceName, int line, int column) {}

public enum WorkflowScope { PLAN, EPIC, ENTITY, SUBWORKFLOW }

public record StateMigration(String oldStateId, String newStateId, SourceLocation location) {}

public sealed interface ParamType
    permits ParamType.Text, ParamType.Int, ParamType.EnumOf, ParamType.ListOf {

    record Text(Optional<Integer> minLength, Optional<Integer> maxLength) implements ParamType {}
    record Int(Optional<Integer> min, Optional<Integer> max) implements ParamType {}
    record EnumOf(List<String> values) implements ParamType {}
    record ListOf(ParamType elementType) implements ParamType {}
}

/** Free parameter of a link (`param_decl`). */
public record ParamSpec(String name, ParamType type, boolean optional, SourceLocation location) {}

/** Sub-workflow parameter declared in the header (`param <name>: <type>`); always required. */
public record ParamDecl(String name, ParamType type, SourceLocation location) {}

public record WorkflowDefinition(
    String id,
    int version,
    WorkflowScope scope,
    List<ParamDecl> params,          // non-empty only when scope == SUBWORKFLOW
    String startState,
    List<StateMigration> migrations,
    Map<String, StateNode> states,
    SourceLocation location
) {}

public record StateNode(
    String id,
    String phase,
    boolean terminal,
    Optional<String> terminalOutcome,
    Optional<String> skillPath,
    Optional<String> factsPrimitiveId,
    StateBehavior behavior,
    SourceLocation location
) {}

public sealed interface StateBehavior
    permits StateBehavior.InteractiveLinks,
            StateBehavior.AutoStep,
            StateBehavior.JobStep,
            StateBehavior.SubWorkflowCall,
            StateBehavior.TerminalState {

    record InteractiveLinks(List<LinkSpec> links) implements StateBehavior {}
    record AutoStep(String primitiveId, List<OutcomeTransition> transitions) implements StateBehavior {}
    record JobStep(String primitiveId, boolean composite, List<OutcomeTransition> transitions) implements StateBehavior {}
    record SubWorkflowCall(
        String subWorkflowId,
        Map<String, String> paramBindings,
        List<OutcomeTransition> transitions
    ) implements StateBehavior {}
    record TerminalState() implements StateBehavior {}
}

public record CallFrame(
    String callerWorkflowId,
    String callerStateId,
    String callerPhase,
    String subWorkflowId,
    Map<String, String> boundArgs,
    String pushedAt
) {}

public record LinkSpec(
    LinkRelation rel,
    String idPattern,
    LinkForm form,
    List<ParamSpec> freeParams,
    Optional<GuardExpr> guard,
    LinkAction action,
    List<OutcomeTransition> transitions,
    SourceLocation location
) {}

public sealed interface LinkAction
    permits LinkAction.ExecutePrimitive,
            LinkAction.DispatchSubAgent,
            LinkAction.EscalateDecision {

    record ExecutePrimitive(String primitiveId) implements LinkAction {}
    record DispatchSubAgent(String targetEntityKind, Optional<String> roleId, Optional<String> effortLevel) implements LinkAction {}
    record EscalateDecision(String decisionId) implements LinkAction {}
}

public sealed interface GuardExpr
    permits GuardExpr.InWorktree,
            GuardExpr.HasOpenFindings,
            GuardExpr.AllTasksCompleted,
            GuardExpr.CustomPredicate,
            GuardExpr.And,
            GuardExpr.Or,
            GuardExpr.Not {

[#static-verification-rules]
=== Static AST Verification Rules (Build-Time & Daemon Startup)
_See Requirement link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint]_

_See Requirement link:../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../Requirements.adoc#PM-MIG-4[PM-MIG-4: Stage Exit Criteria & Legacy Surface Retirement]_

`WorkflowValidator` verifies every `WorkflowDefinition` both in JUnit build tests and at daemon startup (failing closed if any rule is violated). A `WorkflowDefinition` is always a complete definition unit (<<workflow-definition-units>>): the merged union of all phase files of the plan workflow, a single-file top-level workflow, or one sub-workflow. Rules 2, 3, 5, and 8 run over that union, never over an individual phase file:

1. *Primitive Binding & Parameter Equivalence*: Every `primitiveId` in `do`, `auto`, `job`, `facts`, and `predicate:` must resolve to a registered `Primitive<P, R>`. For every `LinkSpec`, the declared `freeParams` list must exactly match the name, type, and constraints of the `Record` components annotated as `@FreeParam` on `P`.
2. *Exhaustive Outcome Coverage*: For every `auto`, `job`, `composite_job`, and `link` action backed by `Primitive<P, R>`, the set of `OutcomeTransition.outcomeName` entries must form an exact 1-to-1 bijection with the enum constants of `R` (`R.getEnumConstants()`). For `job` and `composite_job` states this includes `cancelled`, the outcome of the implicit `cancel:<job_id>` link (<<implicit-job-links>>). Missing or unknown outcome names fail validation with the source file and line number.
3. *Graph Integrity*: State identifiers must be unique across all files of the definition unit. `startState` and every `OutcomeTransition.targetStateId` must exist in the unit's `states` (a cross-file target within the plan workflow is valid; a target inside another unit or inside a sub-workflow is not). Every `StateNode` must be reachable from the unit's `startState`. Every non-terminal `StateNode` must have at least one outgoing transition path to a `terminal` state. Every `skill` clause must resolve to a vocabulary skill in the compiled corpus, and every link identifier pattern must be unique within its state, including the implicit `wait:<job_id>` and `cancel:<job_id>` links of job states.
4. *Single-Level Leaf Sub-Agent Constraint (`PM-WF-5`)*: Any `WorkflowDefinition` with `scope == WorkflowScope.ENTITY` (or any state reachable within an entity sub-agent scope) is strictly forbidden from containing a `LinkSpec` with `form == LinkForm.DISPATCH` or `LinkAction.DispatchSubAgent`. Sub-agents are leaves and can never dispatch nested sub-agents.
5. *Backwards-Compatible State Migration (`PM-MIG-4`)*: Every state name present in the committed `released-states.txt` baseline must either exist in `states` or appear as `oldStateId` in a `migrate <old> -> <new>` declaration whose target exists in `states`.
6. *Sub-Workflow Outcome Bijection & Parameter Binding (`PM-WF-16`)*: Every `StateBehavior.SubWorkflowCall` (`call <subWorkflowId>`) must reference a registered `WorkflowDefinition` whose `scope == WorkflowScope.SUBWORKFLOW`. Every terminal `StateNode` in a `SUBWORKFLOW` must declare a non-empty `terminalOutcome` (`state <id> terminal <outcome_id>`), and the set of `OutcomeTransition.outcomeName` entries on each `call` site must form an exact 1-to-1 bijection with the target sub-workflow's declared `terminalOutcome` values. The `paramBindings` of every `call` site are checked against the target's `params` (`param` declarations): every declared parameter must be bound exactly once, no binding may name an undeclared parameter, and every bound value must match the declared type (membership in the `enum[…]` value set, or an integer within the declared `int` range).
7. *Acyclic Call-Graph DAG & Bounded Depth (`PM-WF-16`)*: Across all registered `WorkflowDefinition` instances, the static `call` graph must form a strict directed acyclic graph (DAG) with zero cycles and a maximum static call-stack depth $\le 4$.
8. *Gate Artifact Producer Coverage*: For every guard or gating primitive that declares a required artifact (`requiredArtifacts()`, for example `pr_title`, `outline.md`, or `execution-manifest.json`), every path from the unit's `startState` to that guard or state, including recipe and lane shortcuts, must pass a state whose primitive declares the artifact in `producedArtifacts()`. A path without a producer fails validation, so a gate can never refuse for an artifact its lane could not produce.
9. *Failure Outcomes Never Map to Success*: Every outcome constant of every primitive, `composite_job` outcome set, and sub-workflow terminal outcome declares an `OutcomeClass` (<<primitive-outcome-classes>>). Only an outcome of class `SUCCESS` may lead to a step completion record `done`; a `FAILURE` or `INDETERMINATE` outcome must never be mapped to a transition that records the step `done`. A composite primitive whose sub-operations report any `FAILURE` outcome yields a `FAILURE` outcome itself.

[#primitive-outcome-classes]
==== Outcome Classes & Step Records

Every outcome constant declares one `OutcomeClass`, and the engine derives the step record from it, never from the outcome name:

* *`SUCCESS`*: The step completed with its work; the engine records `done`.
* *`SKIP`*: The step had nothing to do. A primitive with an optional input declares a `skipped_<reason>` outcome of this class for the absent-input case; the step record stores `skipped`, `work_performed: false`, and the reason, and downstream steps treat it as neither a failure nor produced content.
* *`FAILURE`* and *`INDETERMINATE`*: The step record stores `failed` or `indeterminate`; neither is ever recorded as `done`, and `INDETERMINATE` is never folded into success or failure (`PM-EXEC-4`).
* *`UNSETTLED`*: Outcomes that hand the step back without settling it (`loop_back`, defer). The engine writes no completion record, so a re-fired step never produces two completions.

[#independent-transition-validation]
=== Independent Server-Side Transition & Parameter Validation (`PM-WF-6`)

[[_independent_server_side_transition_parameter_validation_pm_wf_6]]
When `pm_do(scope_id, link, args, dispatch_id)` arrives, the workflow engine executes a single atomic transaction under the scope's exclusive `FileChannel` lock:

1. *Load Authoritative State*: Read `mcp/status.json` for `scope_id` (applying any `migrate` mapping if `status.json` references a legacy state) and resolve the active `StateNode` (within the top `CallFrame.subWorkflowId()` if `call_stack` is non-empty, or the root workflow otherwise).
2. *Verify Dispatch Claim (if `dispatch_id` present)*: If `dispatch_id` is superseded or expired, reject immediately with `reason: "stale_dispatch_id"`.
3. *Re-Compute Active Links & Guards*: Evaluate all `LinkSpec` entries on `StateNode`, expanding entity placeholders (`triage:<finding_id>`) against current persisted stores (`findings.jsonl`, `tasks/TASK-*.json`) and evaluating each link's `GuardExpr`.
4. *Verify Link Offering*: Confirm that `link` exactly matches one of the currently active, guard-satisfied `LinkSpec` instances. If `link` is not in the active set, return `isError: false` with the current representation and a `rejected.reason` from the closed enumeration (link:mcp-tools.adoc#rejection-reasons[MCP Tool & Resource Surface Specification]): `operator_only` for an operator transition, which is never offered to the model; `stale_entity` for an entity-addressed link whose entity is no longer in an accepting state; `link_not_available` for any other identifier, including invented or paraphrased ones.
5. *Validate & Bind Free Parameters (`P`)*: Validate the raw `args` map against the `LinkSpec.freeParams` constraints (`additionalProperties: false`, required keys, enum membership, string length bounds, integer ranges) and execute any attached content validator (`OutlineValidator`, `AsciiDocValidator`, `ConventionalCommitValidator`) in-process on submitted text payloads. If validation fails, return `isError: false` with the current representation and `rejected.reason` `undeclared_param` (a key the link does not declare), `missing_param` (a required key is absent), or `invalid_link_args` (type, range, or content-validator violation); `detail` names the offending parameter.
6. *Verify Workspace Footprint*: For task `submit` and git `commit` links, verify that no files outside the plan's worktree were dirtied by host tools; on violation, transition immediately to `<phase>.footprint-violation`.
7. *Execute Primitive & Advance State*: Instantiate `P`, invoke `primitive.execute(context, params)`, look up the returned `R.wireName()` in `LinkSpec.transitions`, persist the new `state` (and updated `call_stack` if entering or exiting a `SubWorkflowCall`) in `mcp/status.json`, append the transition event to `audit.jsonl`, and render the next state's TOON representation (executing chained `auto` and `call` steps until an interactive link state, async job state, or root terminal state is reached).

== Reusable Compound Sub-Workflows & Call-Stack Execution (`PM-WF-16`)
_See Requirement link:../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

Workflows are composed not only of atomic `do` / `auto` / `job` primitives, but also of reusable, config-aware *compound sub-workflows* (`scope subworkflow`). A compound sub-workflow encapsulates a multi-state sub-process—combining deterministic `auto` checks, configuration lookups, conditional interactive pauses, and recovery branches—so that Phase 5 (`execute`), Phase 6 (`finalize`), `pr-doctor`, `marshall-steward`, and `plan-orchestrator` invoke the exact same state machine rather than duplicating states or collapsing interactive recovery into opaque Java code.

=== Call-Stack Execution & Persistence Semantics

1. *Sub-Workflow Invocation (`call`)*: When the engine transitions into a `StateNode` whose behavior is `StateBehavior.SubWorkflowCall(subWorkflowId, paramBindings, transitions)`, it pushes a `CallFrame(callerWorkflowId, callerStateId, callerPhase, subWorkflowId, paramBindings, Instant.now().toString())` onto the `call_stack` array in `mcp/status.json` and sets `status.state` to the target sub-workflow's `startState` while preserving `status.phase = callerPhase` whenever a sub-workflow state declares `phase inherit`. Preserving `callerPhase` guarantees that phase-scoped guards (such as `in_worktree`), phase metric accounting (`metrics.json`), and terminal-title updates remain invariant regardless of which caller invoked the sub-workflow.
2. *Interactive Pauses & Job Waits Inside a Sub-Workflow*: If execution inside the sub-workflow reaches an `AutoStep`, the engine executes it immediately in the same turn. If execution reaches an `InteractiveLinks` state (such as `git.artifact-review`, `git.compose-message`, `git.commit-fix`, or `git.sync-required`) or a `JobStep`, the engine persists `mcp/status.json` (with the active `call_stack` and sub-workflow `state`) and returns that state's TOON representation to the caller. Subsequent `pm_do` or `pm_state` calls resolve against the active sub-workflow state at the top of `call_stack`, surviving context compactions and daemon restarts identically to top-level states.
3. *Sub-Workflow Return (`terminal <outcome_id>`)*: When a transition inside the sub-workflow lands on a `StateNode` with `terminal == true` and `terminalOutcome == Optional.of(outcomeId)`, the engine pops the top `CallFrame` from `call_stack`, looks up `outcomeId` in the caller state's `OutcomeTransition` table, transitions `status.state` to `targetStateId` in `callerWorkflowId`, and continues auto-chaining in the same atomic transaction.

=== Canonical Reusable Sub-Workflow: `git.commit_and_push` (`git-commit-and-push.pmwf`)

The `git.commit_and_push` sub-workflow models the complete git commit-and-push sub-process grounded in `workflow-integration-git`, `phase-5-execute` (Step 10a), and `phase-6-finalize` (Step 3 item 5f, `standards/push.md`, and post-PR re-push).

==== Six-Stage Execution Contract of `git.commit_and_push`

* *Stage 1 — Working-Tree Inspection (`git.inspect-worktree`)*:
** Resolves the target checkout path from the locked scope context: `worktree_path` when `location == WORKTREE`, `workspace_root` when `MAIN_CHECKOUT` or `steward`, and the shared epic worktree (link:filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification]) when `epic`. Git-tracked orchestrator state is never committed on the primary checkout (`PM-ARCH-5`).
** Executes `git -C <tree> status --porcelain` (ignoring `.plan/local/**`).
** If uncommitted changes exist (`staged`, `unstaged`, or `untracked`), returns `dirty -> git.detect-artifacts`.
** If the working tree is clean: returns `clean_skip_push -> git.done-clean` when `push_mode == never`; otherwise returns `clean_needs_push_check -> git.evaluate-push-policy` so clean-tree push barriers (`finalize.push-barrier` or post-rebase pushes) proceed directly to the freshness and parity checks without creating an empty commit.
* *Stage 2 — `.gitignore`-Aware Artifact Detection & Cleanup (`git.detect-artifacts`)*:
** Scans the working tree against `artifact-patterns.json` (`*.tmp`, `*.bak`, `*.orig`, `*.swp`, `.DS_Store`, `Thumbs.db`, coverage/build scratch files) while querying `git -C <tree> check-ignore`.
** Fails closed (`oracle_failed -> git.artifact-escalate`) if the `.gitignore` oracle cannot be evaluated.
** Unconditionally excludes `.plan/**` and any nested git worktrees or submodules (`git submodule status` / `.git` file markers) from deletion.
** Automatically deletes `safe` untracked artifact files and records `artifacts_deleted` in the audit log.
** Transitions to `git.artifact-review` only for paths in the change set of this commit (porcelain entries: staged, unstaged, untracked) that match artifact patterns and are `uncertain`, or for prohibited secret files (`.env*`, `*.pem`, `*.key`, `credentials.json`) in that change set. Unchanged tracked files are never candidates; unchanged tracked files that match artifact patterns are reported only as a count (`facts.tracked_pattern_matches`).
* *Stage 3 — In-Memory Commit Message Resolution, Validation & Trailer Injection (`git.resolve-message` / `git.compose-message`)*:
** When `message_mode` is `auto_deliverable` or `step_or_fallback`, resolves the deterministic commit message in memory (e.g., `feat(<module>): complete deliverable <N> - <title>` or `chore(finalize): apply <step_id> changes`).
** When `message_mode == interactive` (or `none_assert_clean` when unexpected dirty files were found), transitions to `git.compose-message`, populates `facts` via `git.diff-summary` (changed file count, module scope, priority-ordered suggested type `fix > feat > perf > refactor > docs > style > test > chore > ci`), and accepts `message: text 1..2000` directly in `pm_do` `args`.
** Validates Conventional Commits format (`<type>[optional (<scope>)][!]: <subject>`) via `ConventionalCommitValidator` and deterministically appends the configured trailer `Co-Authored-By: {name} <{email}>`, resolved as in `plan-marshall` (`manage-run-config` `commit-trailer get`) from `commit_trailer{name,email}` in the git-ignored `.plan/local/run-configuration.json`: each half defaults independently (`plan-marshall`, `noreply@cuioss.de`), and a stored value that is empty, not a string, or contains an angle bracket or line break is treated as absent. `.plan/marshal.json` is never consulted for the trailer.
** The resolved trailer is the only authority: a `Co-Authored-By:` line in a model-supplied `message` is rejected (`invalid_link_args`, `detail` names the line), and the only trailer in the commit is the one the server appends. The commit facts record `trailer_source: {name, email}`, each half `configured`, `default`, or `invalid_ignored` (a stored value that was treated as absent).
* *Stage 4 — Staging, `stdin`-Piped Commit & Change-Ledger Stamping (`git.stage-and-commit`)*:
** Derives the staging set from the plan, never from whatever the working tree holds: the dirty paths intersected with the declared footprint, the accepted deviations, the task `target_files`, and the step-declared outputs (for epic scopes, `.plan/orchestrator/**`; for the steward, `.plan/marshal.json`). A dirty path outside that set is never staged; the engine's workspace footprint check (<<independent-transition-validation>>, item 6) moves the scope to `<phase>.footprint-violation` naming it.
** Stages the scoped files (`git -C <tree> add -- <paths>`) and invokes `git -C <tree> commit -F -`, streaming the validated UTF-8 commit message + trailer directly to child `stdin` in memory (`PM-EXEC-5`) with zero `.plan/temp/` files.
** Captures `commit_sha` (`git -C <tree> rev-parse HEAD`) and git-sourced `changed_paths` (`git -C <tree> diff-tree --no-commit-id --name-only -r <commit_sha>`), appending a `kind = "change"` entry to `change-ledger.jsonl`.
** When invoked from a Phase 6 `mutates_source: true` step: re-stamps `head_at_completion = commit_sha` on `head_dependent: true` steps in `mcp/status.json`, and for steps with `order >= 10` (`pre-push-quality-gate.order`), writes a `freshness_reconcile` record (`commit_sha`, `step_id`, `prior_build_worktree_sha` from the latest passing build row in `change-ledger.jsonl`) so the downstream push gate recognizes the finalize-internal commit without requiring a redundant full build when no source-affecting inputs changed.
** If `git commit` exits non-zero due to a repository pre-commit hook, returns `hook_failed -> git.commit-fix`.
* *Stage 5 — Config-Driven Push Policy & Freshness Precondition (`git.evaluate-push-policy` -> `git.verify-freshness`)*:
** Evaluates `push_mode` together with `.plan/marshal.json -> /plan/phase-5-execute/commit_and_push` (default `true`): `push_mode == never` skips push (`skip_push_committed -> git.done-committed-local`); `push_mode == if_configured` requires push if and only if `commit_and_push == true`; `push_mode == post_pr_conditional` requires push if and only if `commit_and_push == true` and the calling finalize step has `order > 20` (after `create-pr`), automating post-PR re-push for late source-mutating steps (`adr-propose` or triage fixes); `push_mode == always` requires push unconditionally.
** Before any push, `git.pre-commit-verify-freshness` verifies `change-ledger.jsonl` freshness (`fresh` corroborated on both notation and scope dimensions against the current `worktree_sha`, `exempt` when `build-decision == not_necessary`, or reconciled via `freshness_reconcile`). If `stale` or `undecidable`, transitions to `git.freshness-blocked` (offering `run_verification_build` or operator `escalate`).
** When no reconciliation record names the live `HEAD`, `git.freshness-status` reports `stale_reason: reconciliation_record_absent` together with the causes that absence admits (`admitted_causes` ⊆ `source_drift_unbuilt`, `no_successful_build`, `record_owed_not_emitted`, `commit_outside_reconcile_membership`). The refusal reports what it observed and never asserts a single inferred cause; the fail-closed halt is unchanged.
** `git.freshness-blocked` renders, beside `stale_reason`, the evidence it would accept: the required build notation(s), the scope (`whole_tree` or a module list), and the current `worktree_sha`.
* *Stage 6 — Branch Sync Parity Probe & Push Execution (`git.check-branch-parity` -> `git.execute-push`)*:
** `git.push-barrier-decision` first reads the persisted fact `branch_pushed_at` in `mcp/status.json`. When it is unset, the branch has never been pushed by this plan and the decision is `first_push` (`git -C <tree> push --set-upstream origin <branch>`) without consulting the probe. When it is set (re-entry), the decision follows `plan-marshall`'s push-barrier mapping (`workflow-integration-git/scripts/git-workflow.py`, `push_barrier_action`, verified at commit `1d4a1da37`; re-verify before implementing): it runs `git.branch-sync-state` and returns `refire` only for `ahead`; `synced`, `remote_absent_landed`, `remote_absent_unverified`, and any unrecognised state return `skip`. `remote_absent_unverified` never pushes, because a never-pushed branch and a squash-merged-and-deleted branch are indistinguishable locally and re-pushing would resurrect a landed branch.
** `git.branch-sync-state` classifies the plan's recorded `branch_name` (`mcp/status.json`), never the ambient `HEAD` of the checkout, and fetches the remote ref before classifying. A classification made without a fetch in the same transaction is labelled unverified (as `remote_absent_unverified` already is) and is never used to claim that the branch is unpushed.
** `git.execute-push` sets `branch_pushed_at` (timestamp and pushed `HEAD`) in `mcp/status.json` on the first successful push.
** If `git push` is rejected as non-fast-forward (`rejected_non_ff`), transitions to `git.sync-required` (offering `sync_rebase` or operator `force_push_with_lease` escalation).

[#loop-back-bounds]
== Worktree-Constrained Loop-Back & Iteration Bounds
_See Requirement link:../Requirements.adoc#PM-WF-7[PM-WF-7: Worktree-Constrained Loop-Back & Iteration Bounds]_

When a finalize step (CI failure, quality gate failure, or review finding triage) requires code changes, the workflow transitions from `finalize` back to `execute` via a `loop_back` link governed by two strict server-side invariants:

=== 1. Worktree Confinement Guard (`in_worktree`)

* Every `loop_back` link in `finalize.pmwf` declares `guard in_worktree` and no other guard; the iteration bound is enforced by the backing primitive, not by link omission (see Section 2).
* `GuardExpr.InWorktree` evaluates to `true` if and only if `.plan/local/worktrees/<plan_id>/` exists, is a valid git worktree for the plan's branch, and the plan directory currently resides at `.plan/local/worktrees/<plan_id>/.plan/local/plans/<plan_id>/`.
* Once the plan passes `finalize.merge-gate`, merges its branch, and relocates back to the primary checkout (`.plan/local/plans/<plan_id>/`), `InWorktree` evaluates to `false`. All `loop_back` links are automatically omitted from representations and rejected by `pm_do`.

=== 2. Configuration Resolution & Iteration Counter Validation

* The maximum number of automated finalize-to-execute loop-backs is configured in `.plan/marshal.json` under JSON pointer `/plan/phase-6-finalize/max_iterations`:
+
[source,json]
----
{
  "plan": {
    "phase-6-finalize": {
      "max_iterations": 3
    }
  }
}
----

* If `/plan/phase-6-finalize/max_iterations` is omitted in `.plan/marshal.json`, the engine applies the normative default of `3` (valid configured range: `1..10`).
* The plan's `mcp/status.json` persists `"loop_back_iteration": <int>` (initialized to `0` when entering `finalize` for the first time). The name mirrors plan-marshall's `status.metadata.loop_back_iteration`.
* When `loop_back` is followed, `plan.allocate-remediation-tasks` compares `loop_back_iteration` against the resolved `max_iterations` inside the same locked transaction:
** If `loop_back_iteration < max_iterations`, `loop_back_iteration` is atomically incremented by `1` in `mcp/status.json`, fresh task files (`TASK-NNN.json`) and a fresh dispatch envelope (`envelope-M` with a new `dispatch_id`) are allocated in the worktree — completed tasks are never mutated or reopened — and the primitive returns `allocated -> execute.dispatch-ready`.
** If `loop_back_iteration >= max_iterations`, the primitive allocates nothing, leaves the counter unchanged, and returns `limit_reached -> finalize.loop-limit-reached`.
* At the limit, `loop_back` therefore stays offered (subject only to `in_worktree`), and its execution transitions to `finalize.loop-limit-reached`, which offers only `escalate` (requiring operator approval via elicitation or `pm-mcp operator` to grant additional iterations or abort). This is the transition required by `PM-WF-7`; the counter is never evaluated by a guard, so the limit state is always reachable.
* `finalize.loop-limit-reached`, like every other limit state, renders the resolved limit and its source in `facts` (for example `max_iterations: 14`, `max_iterations_source: marshal.json` or `default`), so an escalation never quotes the documented default instead of the configured value.
* Only `loop_back` allocations count against `max_iterations`. Waiting for a review bot's rate window (`finalize.review-window-wait`) and re-triggering a bot never consume a loop-back iteration; their budgets derive from the bot's registered interval.
* A refusal whose reason cannot change between rounds at an unchanged `HEAD` (for example a verifier that cannot apply to the plan's content) is recorded once and closes the step or escalates once; it never offers `loop_back` and never increments `loop_back_iteration`.

== State-Machine Property Verification, Scenario Replay & State Migration
_See Requirement link:../Requirements.adoc#PM-TEST-3[PM-TEST-3: State-Machine Invariant, Property & McpAssured Protocol Verification]_

_See Requirement link:../Requirements.adoc#PM-TEST-4[PM-TEST-4: End-to-End Scenario & Compaction Resume Testing]_

_See Requirement link:../Requirements.adoc#PM-TEST-6[PM-TEST-6: Behavioural Conformance of Model-Facing Content]_

_See Requirement link:../Requirements.adoc#PM-MIG-4[PM-MIG-4: Stage Exit Criteria & Legacy Surface Retirement]_

=== Property-Based State-Machine Verification (`PM-TEST-3`)

The `pm-mcp-core` test suite executes property-based tests (using `jqwik` / `cui-test-generator`) over every compiled `WorkflowDefinition` AST:

* *No Dead-End Non-Terminal States*: Every non-terminal `StateNode` has at least one guard assignment under which at least one outgoing link or auto/job transition is offered, and every reachable state has a finite path to a `terminal` state (`completed` or `aborted`).
* *Strict Guard Enforcement & Link Omission*: Random sequences of `pm_do` calls with invalid link names, unsatisfied guards (such as `loop_back` when `in_worktree == false`), or out-of-range parameters never mutate `mcp/status.json` and always return `rejected.reason` with `isError: false`.
* *Reachable Loop Limit*: Following `loop_back` while `loop_back_iteration >= max_iterations` always transitions to `finalize.loop-limit-reached` with outcome `limit_reached`, allocates no tasks, and leaves `loop_back_iteration` unchanged.
* *Single-Level Leaf Sub-Agent Invariant*: Property generators traverse all reachable states in `WorkflowScope.ENTITY` definitions and verify that zero `form == LinkForm.DISPATCH` links are ever emitted.
* *Monotonic Bounded Loops*: Random failure injection in Q-Gate and finalize-to-execute loop-backs verifies that no path can complete `loop_back` with outcome `allocated` more than `max_iterations` times (`loop_back_iteration` never exceeds `max_iterations` without an operator grant) and that every further `loop_back` enters `*.loop-limit-reached` / `*.qgate-exhausted`.

=== Deterministic Scenario Replay Harness (`pm-mcp-scenario`, `PM-TEST-4`)

End-to-end lifecycle scenarios are authored as deterministic `.pmscenario` scripts executed in-process by `ScenarioReplayRunner` against a hermetic temporary git repository without invoking any live LLM:

[source,text]
----
scenario happy-path-single-module
start request "Add null-safe header parser" slug "header-parser"
assert_state refine.analyze
assert_skill skill://pm/refine/analyze/SKILL.md
assert_links submit:refine
do submit:refine {"clarified_request":"Add a null-safe header parser ...","correctness":98,"completeness":96,"consistency":100,"non_duplication":100,"ambiguity":95,"module_mapping":100,"pr_title":"feat(http): add null-safe header parser"}
assert_state outline.detect-change-type
...
resolve_elicitation approve_outline {"decision":"approve"}
complete_job b-0001 {"outcome":"succeeded","worktree_sha":"e3b0c442..."}
assert_state completed
----

* Simulated `do` arguments use only the DSL parameter types (`text`, `int`, `enum[…]`, `list<…>`); there is no object type, so the six refine confidence dimensions (`correctness`, `completeness`, `consistency`, `non_duplication`, `ambiguity`, `module_mapping`) are submitted as separate `int[0..100]` parameters.
* Each scenario step supports deterministic assertions (`assert_state`, `assert_links`, `assert_skill`, `assert_rejected`) and simulated actor actions (`do`, `complete_job`, `resolve_elicitation`, `operator_cli`).
* The mandatory CI regression suite replays scenarios covering: (1) happy-path single-module plan, (2) multi-task envelope dispatch and context-budget yield, (3) CI failure and worktree-constrained `loop_back` to `execute`, (4) review-bot finding triage (`FIX`, `SUPPRESS`, `ACCEPT`), (5) operator escalation via elicitation and CLI fallback, and (6) mid-job daemon restart recovery.

[#behavioural-conformance-harness]
=== Behavioural Conformance Harness (`PM-TEST-6`)

The deterministic harnesses above verify the engine without a live model. The behavioural conformance harness (`pm-mcp-conformance`) verifies the model-facing content instead: whether a live model, served the rendered vocabulary skills and representations of one client profile, follows the rules they state. It is PM-MCP tooling, not prose: scenario execution, trajectory capture, observation, scoring, and verdict computation are performed by the harness against the runtime's own records, and no step relies on the model's account of what it did.

==== Execution Boundary: Out-of-Band Pre-Release Gate

* The harness is never bound to a Maven lifecycle phase or profile. `verify`, `-Pintegration-tests`, `-Pcoverage`, and the required CI checks (`build / conclusion`, `integration-tests / conclusion`) never invoke a live model.
* It is run explicitly against a release candidate binary (`pm-mcp` native executable with its embedded client bundles) before a release whose model-facing content changed: vocabulary skill templates, guidance strings, representation wording, client profiles, or tool descriptions. The resulting report is published with the release candidate; a `violated` or `indeterminate` verdict is resolved by a recorded operator decision (see *Evidence, Not Authorization* below), never by the harness.
* Each run starts an isolated runtime under a temporary `PM_MCP_BASE`, connects the host under test through a real `pm-mcp serve` relay with the client's installed bundle (`pm-mcp client install <client>`), and uses a hermetic fixture repository per scenario.

==== Scenario Records

Behavioural scenarios are declarative records executed against a live model through a real client connection (`pm-mcp serve`) on a fixture repository. Each scenario declares:

* `rule_ref`: the skill URI and section that states the rule, with the canonical (pre-render) SHA-256 of that section.
* `situation`: the fixture state and the entry command.
* `pressure`: the prompt or state condition that tempts a violation.
* `observation`: a predicate over the recorded tool-call trajectory, the returned `rejected.reason` values, and the resulting artifact tree.
* `binding_context`: where the rule binds, including its scoped exceptions. A scenario never places a rule in a context where its `binding_context` excludes it.
* `enforcement_class`: the class of the rule under link:mcp-tools.adoc#vocabulary-skill-rule-classification[Vocabulary Skill Rule Classification] (`engine`, `check`, or `guidance`). For an `engine` rule the scenario measures attempts that the engine rejected; the engine's acceptance of a violation is a `PM-TEST-3`/`PM-TEST-4` defect, not a behavioural verdict.
* `tolerance_band` and `population`: the held-rate band the verdict is mapped against and the number of samples per run.
* `negative_control`: `true` for a control scenario whose pressure is built to be violated; the harness expects `violated` from it.

Only rules whose violation is mechanically observable in the recorded tool calls or the resulting artifact tree are scored.

==== Trajectory Capture & Observation

* The trajectory is read from the isolated runtime's `audit.jsonl` (every MCP tool call, transition, rejection, and `channel` value, link:cli-and-security.adoc[CLI, Coordination & Security Specification]), from the plan and orchestrator stores, and from the fixture repository's final tree and commits. Host transcripts and model self-reports are never inputs of an observation.
* *Order-Tolerant Trajectory Predicates*: An observation predicate asserts the reached state, the set of required calls, and the absence of forbidden calls; it asserts call order only when order is itself the rule under test.
* *Reference Artifact Trees*: A benchmark scenario is a real workflow task on a fixture repository whose expected result is a concrete reference artifact tree (files, commits, recorded lessons), never a prose rubric; recipe-sourced plans skip Phase 2 and therefore run in batch without an operator stand-in.
* *Representation Parsing*: The baseline of every client includes a representation-parsing scenario in which the model extracts `links` and `facts` from a `pm_state` result in the TOON wire form (`PM-TOOL-5`, `PM-IMPL-2`).

==== Batch Roles

A question-driven scenario runs with three separate roles: the executor (model under test), an operator stand-in that answers `refine.awaiting_answers` through model-relayed `submit` (at most one batched round, matching the re-dispatch ceiling of link:phase-workflows.adoc#_single_batch_clarification_re_dispatch_ceiling[Phase Workflows § Single-Batch Clarification & Re-Dispatch Ceiling]), and the scorer. Authorizing decisions (`PM-WF-12`) are resolved by the harness through the operator channel, never by the stand-in.

==== Scoring & Verdicts

* *Axis Statement*: The harness design lists the five eval axes (task success, tool-use quality, trajectory compliance, hallucination, response quality) and states for each whether it is scored and, if not, why; each scored axis has a rubric that the observation predicate implements.
* *Deterministic Scorer First*: The scorer is the harness's predicate evaluator, which needs no model call. A judging model is admitted only for a scored axis whose rubric no predicate can decide; it is then fixed across all models under test, and before each run the harness compares its model identifier and family against the model under test and refuses the run with `scorer_not_independent` when the judge is the scored model or its sibling at default configuration.
* *Verdict Over a Margin*: Each scenario is run over a stated population of samples; the harness computes the held rate and its margin and maps it to `held`, `violated`, or `indeterminate` against the scenario's tolerance band. The per-sample observation is boolean; the three-valued verdict exists only at the aggregated level. A sample that cannot be scored (host error, timeout, unreadable trajectory) is counted as unscorable, and a run whose scored samples fall below the population resolves to `indeterminate`, never to `held`. A single run is reported with `sample: true`, never as a verdict.
* *Attribution Mode*: Every verdict records `attribution: isolated | realistic_context`; a rule that is also stated in resident content (the `pm/core` skill, entry commands, catalogue descriptions, link:client-profiles.adoc#host-resident-surface-inventory[Host-Resident Surface Inventory]) can only be measured as `realistic_context`.

==== Rule Population & Selection

* *Derived Rule Population*: The baseline's rule population is derived from every resident and served source in the Host-Resident Surface Inventory (entry commands, agent variants, catalogue descriptions, `pm/core`, tool descriptions); the harness reports the derived population size and never asserts completeness.
* *Selection by Defect Cost*: Rules are selected for scenarios by recorded defect cost (audit rejections such as `invalid_link_args`, `store_tampered`, and historical defect records), never by intuition; the selection records its source.
* *Negative Controls*: Every baseline contains at least one negative-control scenario; a baseline whose negative control does not score `violated` is itself reported `indeterminate`, because the harness has shown it cannot detect a violation.

==== Digest Binding & Baseline Lifecycle

* *Digest Binding*: Every scenario records the canonical (pre-render) SHA-256 of the skill section that states its rule and every verdict records the rendered per-client `_meta.sha256` (`PM-SKILL-2`); a scenario whose recorded canonical digest differs from the current skill is refused as `stale_scenario` until re-authored.
* *Baseline Lifecycle*: A baseline is re-recorded when a bound skill digest, the client profile digest, the model identifier, or the binary's major/minor version changes; verdicts whose bound digest no longer matches are marked `invalidated`, never silently kept.

==== Report Fields

Every run report carries `client_id`, model identifier, binary version, client profile digest, bound skill digests, population, per-verdict counts, margin, tolerance band, `attribution`, `sample: true` for single runs, and token consumption per client and model (`unmeasured` when the host reports none, never `0`). Results are grouped by `enforcement_class`. Every report states an absolute reference as well as the delta to the previous baseline, never the delta alone. A client profile without a report of its own is reported as behaviourally untested; structural results (rendering, digests, registration, resolution) never stand in for it.

The store that holds verdict records and baselines (versioned repository artifacts or a runtime store) is not fixed yet; the record content above is independent of that choice.

==== Cost Ceilings & Sizing

Every scoring layer, including a judging model, declares its cost ceiling (runtime, tokens, and money per run) in the harness configuration at design time; the harness stops a run that reaches a ceiling and reports it `indeterminate` with the ceiling that was hit. The sizing of a full baseline (runtime, tokens, and money per client and model) is published before the harness is used as a routine pre-release gate.

==== Evidence, Not Authorization

A verdict is evidence for a separately authorized decision. It never directly authorizes an edit of model-facing content, and a `violated` verdict is scoped to the rule, pressure, model, and client it was measured on. Any per-client or per-model change of wording, emphasis, or scaffolding beyond the vocabulary dimensions of `PM-CLIENT-2` requires a behavioural signal for that client and a recorded decision.

=== State-Name Migration Registry & `released-states.txt` Gate (`PM-MIG-4`)

To guarantee that active plans survive `pm-mcp` binary upgrades across state renames or workflow splits:

* Every state identifier shipped in a public release is appended to the committed `classpath:/workflows/released-states.txt` baseline.
* When a state is renamed or split in a `.pmwf` file, the workflow header declares `migrate <old_state_id> -> <new_state_id>`.
* When `WorkflowEngine` loads `mcp/status.json` whose `state` matches `<old_state_id>`, it transparently rewrites `state` to `<new_state_id>` and appends a `state_migrated` event to `audit.jsonl`.
* A build-time JUnit gate (`ReleasedStatesMigrationTest`) verifies that every entry in `released-states.txt` either exists in the current `WorkflowDefinition.states()` map or is covered by a transitive `migrate` chain terminating in a live state.
