== Overview

This document specifies the declarative Workflow Domain-Specific Language (DSL), Abstract Syntax Tree (AST) model, typed Java `Primitive<P, R>` execution contract, loop-back guard semantics, and automated diagram generation for *plan-marshall-mcp* (`PM-MCP`). The workflow engine and DSL reside in the plain-Java `pm-mcp-core` module with zero runtime framework dependencies and are assembled into the native daemon by `pm-mcp-server`.

== Module Boundary & Decoupled Core Architecture
_See Requirement link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1: Decoupled Plain-Java Core Engine & Quarkus Assembly]_

The workflow engine is strictly decoupled from Quarkus, CDI, Vert.x, and MCP transport libraries. During the initial M1 scaffold, packages reside within the root `plan-marshall-mcp` Maven module and are extracted into dedicated Maven sub-modules (`pm-mcp-core`, `pm-mcp-server`, `pm-mcp-dist`) with ArchUnit boundary enforcement before M2 distribution packaging:

[cols="1,2,3"]
|===
|Module |Package Namespace |Responsibilities & Allowed Dependencies

|`pm-mcp-core`
|`de.cuioss.pm.mcp.core.workflow.*`
|Contains the line-oriented DSL lexer/parser, immutable AST records, compile-time/startup static verifier, `Primitive<P, R>` SPI, deterministic state machine interpreter, and PlantUML/Mermaid/ASCII diagram generators. Depends *only* on the JDK (`java.base`) and `cui-java-tools` / Jackson annotations. Unit tests execute directly in JUnit 5 without Quarkus augmentation.

|`pm-mcp-server`
|`de.cuioss.pm.mcp.server.*`
|Instantiates core engine services via CDI `@Produces`, binds concrete `Primitive` implementations to the daemon's job runner and state stores, registers persisted records via `@RegisterForReflection`, and maps `pm_start`, `pm_state`, and `pm_do` calls to the engine.

|`pm-mcp-dist`
|`de.cuioss.pm.mcp.dist.*`
|Packages the GraalVM native executable (`pm-mcp`), static `skill://pm/**` corpus resources, and platform archive artifacts (`tar.gz`, Homebrew formula, JBang catalog).
|===

== Formal EBNF Grammar for the Workflow DSL
_See Requirement link:../Requirements.adoc#PM-WF-2[PM-WF-2: Closed Link Relation & Form Vocabulary]_

_See Requirement link:../Requirements.adoc#PM-WF-3[PM-WF-3: Server-Side Guard Evaluation & Link Omission]_

_See Requirement link:../Requirements.adoc#PM-WF-4[PM-WF-4: Closed-Outcome Primitives & Deterministic Auto-Chaining]_

_See Requirement link:../Requirements.adoc#PM-WF-9[PM-WF-9: Composite Wait States & Short-Circuit Failure Handling]_

_See Requirement link:../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

Workflow definitions (`*.pmwf` resources compiled into the binary under `classpath:/workflows/`) conform to the following ISO/IEC 14977 Extended Backus-Naur Form (EBNF) grammar. The DSL is line-oriented; comments start with `#` and run to the end of the line.

[source,ebnf]
----
workflow_file        = workflow_header ,
                       [ scope_decl ] ,
                       start_decl ,
                       { migrate_decl } ,
                       state_decl , { state_decl } ;

workflow_header      = "workflow" , state_id , "version" , positive_int , EOL ;
scope_decl           = "scope" , ( "plan" | "epic" | "entity" | "subworkflow" ) , EOL ;
start_decl           = "start" , state_id , EOL ;
migrate_decl         = "migrate" , state_id , "->" , state_id , EOL ;

state_decl           = "state" , state_id , [ "terminal" , [ outcome_id ] ] , EOL ,
                       [ phase_clause ] ,
                       [ skill_clause ] ,
                       [ facts_clause ] ,
                       state_body ;

phase_clause         = "phase" , identifier , EOL ;
skill_clause         = "skill" , skill_path , EOL ;
facts_clause         = "facts" , primitive_id , EOL ;

state_body           = /* empty for terminal states */
                     | auto_clause
                     | job_clause
                     | call_clause
                     | link_clause , { link_clause } ;

auto_clause          = "auto" , primitive_id , EOL ,
                       outcome_transition , { outcome_transition } ;

job_clause           = ( "job" | "composite_job" ) , primitive_id , EOL ,
                       outcome_transition , { outcome_transition } ;

call_clause          = "call" , state_id , [ "(" , [ call_arg_list ] , ")" ] , EOL ,
                       outcome_transition , { outcome_transition } ;
call_arg_list        = call_arg , { "," , call_arg } ;
call_arg             = identifier , "=" , identifier ;

link_clause          = "link" , relation , link_id_pattern ,
                       [ "[" , link_form , "]" ] ,
                       "(" , [ param_list ] , ")" , EOL ,
                       [ guard_clause ] ,
                       link_action ,
                       outcome_transition , { outcome_transition } ;

relation             = "next" | "alt" | "retry" | "fix" | "loop_back"
                     | "submit" | "dispatch" | "wait" | "escalate"
                     | "abort" | "emit" ;

link_form            = "submit" | "wait" | "dispatch" | "escalate" | "noop" ;

link_id_pattern      = action_id , [ ":" , ( entity_placeholder | identifier ) ] ;
entity_placeholder   = "<" , identifier , ">" ;

param_list           = param_decl , { "," , param_decl } ;
param_decl           = identifier , ":" , type_spec , [ "?" ] ;

type_spec            = "text" , [ int_range ]
                     | "int" , [ int_range ]
                     | "enum" , "[" , identifier , { "|" , identifier } , "]"
                     | "list" , "<" , ( "text" | "int" | "enum" , "[" , identifier , { "|" , identifier } , "]" ) , ">" ;

int_range            = positive_int_or_zero , ".." , positive_int ;

guard_clause         = "guard" , guard_expr , EOL ;
guard_expr           = guard_term , { "or" , guard_term } ;
guard_term           = guard_factor , { "and" , guard_factor } ;
guard_factor         = [ "not" ] , ( guard_atom | "(" , guard_expr , ")" ) ;
guard_atom           = "in_worktree"
                     | "loop_count_below_max"
                     | "has_open_findings"
                     | "all_tasks_completed"
                     | "predicate:" , primitive_id ;

link_action          = ( "do" , primitive_id , EOL )
                     | ( "dispatch" , identifier , ( "role" , identifier | "level" , ( "1" | "2" | "3" | "4" | "5" | "6" | "7" | "inherit" ) ) , EOL )
                     | ( "escalate" , identifier , EOL ) ;

outcome_transition   = outcome_id , "->" , state_id , EOL ;

state_id             = identifier , { "." , identifier } ;
primitive_id         = identifier , "." , identifier ;
skill_path           = "pm/" , identifier , { "/" , identifier } ;
outcome_id           = identifier ;
action_id            = identifier ;
identifier           = lowercase_alpha , { lowercase_alpha | digit | "_" | "-" } ;
positive_int         = nonzero_digit , { digit } ;
positive_int_or_zero = "0" | positive_int ;
EOL                  = [ "#" , { any_char_except_nl } ] , "\n" ;
----

=== Reference Workflow DSL Excerpt (`finalize.pmwf`)

[source,text]
----
workflow finalize version 1
scope plan
start finalize.settle-commit
migrate finalize.push_wait -> finalize.push-barrier

state finalize.settle-commit
  phase finalize
  call git.commit_and_push (message_mode=step_or_fallback, push_mode=post_pr_conditional)
    committed_local      -> finalize.next-step
    committed_and_pushed -> finalize.concurrent-wait
    pushed_clean         -> finalize.concurrent-wait
    clean                -> finalize.next-step
    aborted              -> finalize.aborted

state finalize.push-barrier
  phase finalize
  call git.commit_and_push (message_mode=none_assert_clean, push_mode=if_configured)
    committed_local      -> finalize.create-pr
    committed_and_pushed -> finalize.create-pr
    pushed_clean         -> finalize.create-pr
    clean                -> finalize.create-pr
    aborted              -> finalize.aborted

state finalize.concurrent-wait
  phase finalize
  composite_job finalize.watch-ci-and-bots
    all_green           -> finalize.merge-gate
    findings_open       -> finalize.triage
    ci_failed           -> finalize.ci-failed
    bot_rate_limited    -> finalize.review-escalate

state finalize.ci-failed
  phase finalize
  skill pm/finalize/ci-triage
  facts ci.failure-summary
  link loop_back loop_back [submit] (remediation_summary: text 1..2000)
    guard in_worktree and loop_count_below_max
    do plan.allocate-remediation-tasks
      allocated         -> execute.dispatch-ready
      limit_reached     -> finalize.loop-limit-reached
  link escalate escalate [escalate] (reason: text 1..500)
    escalate ci_failure_override
      approved          -> finalize.merge-gate
      denied            -> finalize.aborted

state finalize.loop-limit-reached
  phase finalize
  facts plan.loop-status
  link escalate escalate [escalate] (reason: text 1..500)
    escalate loop_limit_extension
      extended          -> execute.dispatch-ready
      aborted           -> finalize.aborted

state finalize.aborted terminal
  phase aborted
----

== AST Node Model
_See Requirement link:../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

The parser produces an immutable tree of Java 25 `record` and `sealed interface` nodes in `de.cuioss.pm.mcp.core.workflow.ast`:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.ast;

import java.util.List;
import java.util.Map;
import java.util.Optional;

public record SourceLocation(String resourceName, int line, int column) {}

public enum WorkflowScope { PLAN, EPIC, ENTITY, SUBWORKFLOW }

public record StateMigration(String oldStateId, String newStateId, SourceLocation location) {}

public record WorkflowDefinition(
    String id,
    int version,
    WorkflowScope scope,
    String startState,
    List<StateMigration> migrations,
    Map<String, StateNode> states,
    SourceLocation location
) {}

public record StateNode(
    String id,
    String phase,
    boolean terminal,
    Optional<String> terminalOutcome,
    Optional<String> skillPath,
    Optional<String> factsPrimitiveId,
    StateBehavior behavior,
    SourceLocation location
) {}

public sealed interface StateBehavior
    permits StateBehavior.InteractiveLinks,
            StateBehavior.AutoStep,
            StateBehavior.JobStep,
            StateBehavior.SubWorkflowCall,
            StateBehavior.TerminalState {

    record InteractiveLinks(List<LinkSpec> links) implements StateBehavior {}
    record AutoStep(String primitiveId, List<OutcomeTransition> transitions) implements StateBehavior {}
    record JobStep(String primitiveId, boolean composite, List<OutcomeTransition> transitions) implements StateBehavior {}
    record SubWorkflowCall(
        String subWorkflowId,
        Map<String, String> paramBindings,
        List<OutcomeTransition> transitions
    ) implements StateBehavior {}
    record TerminalState() implements StateBehavior {}
}

public record CallFrame(
    String callerWorkflowId,
    String callerStateId,
    String callerPhase,
    String subWorkflowId,
    Map<String, String> boundArgs,
    String pushedAt
) {}

public record LinkSpec(
    LinkRelation rel,
    String idPattern,
    LinkForm form,
    List<ParamSpec> freeParams,
    Optional<GuardExpr> guard,
    LinkAction action,
    List<OutcomeTransition> transitions,
    SourceLocation location
) {}

public sealed interface LinkAction
    permits LinkAction.ExecutePrimitive,
            LinkAction.DispatchSubAgent,
            LinkAction.EscalateDecision {

    record ExecutePrimitive(String primitiveId) implements LinkAction {}
    record DispatchSubAgent(String targetEntityKind, Optional<String> roleId, Optional<String> effortLevel) implements LinkAction {}
    record EscalateDecision(String decisionId) implements LinkAction {}
}

public sealed interface GuardExpr
    permits GuardExpr.InWorktree,
            GuardExpr.LoopCountBelowMax,
            GuardExpr.HasOpenFindings,
            GuardExpr.AllTasksCompleted,
            GuardExpr.CustomPredicate,
            GuardExpr.And,
            GuardExpr.Or,
            GuardExpr.Not {

    record InWorktree() implements GuardExpr {}
    record LoopCountBelowMax() implements GuardExpr {}
    record HasOpenFindings() implements GuardExpr {}
    record AllTasksCompleted() implements GuardExpr {}
    record CustomPredicate(String primitiveId) implements GuardExpr {}
    record And(GuardExpr left, GuardExpr right) implements GuardExpr {}
    record Or(GuardExpr left, GuardExpr right) implements GuardExpr {}
    record Not(GuardExpr operand) implements GuardExpr {}
}

public record OutcomeTransition(
    String outcomeName,
    String targetStateId,
    SourceLocation location
) {}
----

=== Static AST Verification Rules (Build-Time & Daemon Startup)
_See Requirement link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint]_

_See Requirement link:../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../Requirements.adoc#PM-MIG-4[PM-MIG-4: State-Name Migration Registry]_

`WorkflowValidator` verifies every `WorkflowDefinition` both in JUnit build tests and at daemon startup (failing closed if any rule is violated):

1. *Primitive Binding & Parameter Equivalence*: Every `primitiveId` in `do`, `auto`, `job`, `facts`, and `predicate:` must resolve to a registered `Primitive<P, R>`. For every `LinkSpec`, the declared `freeParams` list must exactly match the name, type, and constraints of the `Record` components annotated as `@FreeParam` on `P`.
2. *Exhaustive Outcome Coverage*: For every `auto`, `job`, and `link` action backed by `Primitive<P, R>`, the set of `OutcomeTransition.outcomeName` entries must form an exact 1-to-1 bijection with the enum constants of `R` (`R.getEnumConstants()`). Missing or unknown outcome names fail validation with the source file and line number.
3. *Graph Integrity*: `startState` and every `OutcomeTransition.targetStateId` must exist in `states`. Every `StateNode` must be reachable from `startState`. Every non-terminal `StateNode` must have at least one outgoing transition path to a `terminal` state.
4. *Single-Level Leaf Sub-Agent Constraint (`PM-WF-5`)*: Any `WorkflowDefinition` with `scope == WorkflowScope.ENTITY` (or any state reachable within an entity sub-agent scope) is strictly forbidden from containing a `LinkSpec` with `form == LinkForm.DISPATCH` or `LinkAction.DispatchSubAgent`. Sub-agents are leaves and can never dispatch nested sub-agents.
5. *Backwards-Compatible State Migration (`PM-MIG-4`)*: Every state name present in the committed `released-states.txt` baseline must either exist in `states` or appear as `oldStateId` in a `migrate <old> -> <new>` declaration whose target exists in `states`.
6. *Sub-Workflow Outcome Bijection & Parameter Binding (`PM-WF-16`)*: Every `StateBehavior.SubWorkflowCall` (`call <subWorkflowId>`) must reference a registered `WorkflowDefinition` whose `scope == WorkflowScope.SUBWORKFLOW`. Every terminal `StateNode` in a `SUBWORKFLOW` must declare a non-empty `terminalOutcome` (`state <id> terminal <outcome_id>`), and the set of `OutcomeTransition.outcomeName` entries on each `call` site must form an exact 1-to-1 bijection with the target sub-workflow's declared `terminalOutcome` values. Every key/value in `paramBindings` must conform to the sub-workflow's declared parameter schema.
7. *Acyclic Call-Graph DAG & Bounded Depth (`PM-WF-16`)*: Across all registered `WorkflowDefinition` instances, the static `call` graph must form a strict directed acyclic graph (DAG) with zero cycles and a maximum static call-stack depth $\le 4$.

== Typed Java `Primitive<P, R>` Interface & Transition Validation

=== `Primitive<P, R>` SPI Contract

Every deterministic server operation is encapsulated as a stateless Java `Primitive<P, R>` in `pm-mcp-core`:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.spi;

import java.util.Map;
import java.util.Optional;

public interface PrimitiveOutcome {
    String wireName();
}

public record PrimitiveResult<R extends Enum<R> & PrimitiveOutcome>(
    R outcome,
    Map<String, Object> updatedFacts,
    Optional<String> spawnedJobId
) {}

public interface Primitive<P extends Record, R extends Enum<R> & PrimitiveOutcome> {

    /**
     * Canonical dotted primitive identifier (e.g., "git.commit", "git.push", "findings.triage").
     */
    String id();

    /**
     * Record class defining the free and state-resolved parameters.
     */
    Class<P> parameterType();

    /**
     * Closed enum class of all possible deterministic outcomes.
     */
    Class<R> outcomeType();

    /**
     * Execute the operation within the locked scope context and return one of the closed outcomes.
     */
    PrimitiveResult<R> execute(WorkflowExecutionContext context, P parameters);
}
----

=== Independent Server-Side Transition & Parameter Validation (`PM-WF-6`)

When `pm_do(scope_id, link, args, dispatch_id)` arrives, the workflow engine executes a single atomic transaction under the scope's exclusive `FileChannel` lock:

1. *Load Authoritative State*: Read `mcp/status.json` for `scope_id` (applying any `migrate` mapping if `status.json` references a legacy state) and resolve the active `StateNode` (within the top `CallFrame.subWorkflowId()` if `call_stack` is non-empty, or the root workflow otherwise).
2. *Verify Dispatch Claim (if `dispatch_id` present)*: If `dispatch_id` is superseded or expired, reject immediately with `reason: "superseded_dispatch_id"`.
3. *Re-Compute Active Links & Guards*: Evaluate all `LinkSpec` entries on `StateNode`, expanding entity placeholders (`triage:<finding_id>`) against current persisted stores (`findings.jsonl`, `tasks/TASK-*.json`) and evaluating each link's `GuardExpr`.
4. *Verify Link Offering*: Confirm that `link` exactly matches one of the currently active, guard-satisfied `LinkSpec` instances. If `link` is not in the active set (including any attempt to invoke an omitted operator transition or an already-closed entity), return `isError: false` with `rejected.reason = "link_not_available"` and the current representation.
5. *Validate & Bind Free Parameters (`P`)*: Validate the raw `args` map against the `LinkSpec.freeParams` constraints (`additionalProperties: false`, required keys, enum membership, string length bounds, integer ranges) and execute any attached content validator (`OutlineValidator`, `AsciiDocValidator`, `ConventionalCommitValidator`) in-process on submitted text payloads. If validation fails, return `isError: false` with `rejected.reason = "invalid_link_args"` and the current representation.
6. *Verify Workspace Footprint*: For task `submit` and git `commit` links, verify that no files outside the plan's worktree were dirtied by host tools; on violation, transition immediately to `<phase>.footprint-violation`.
7. *Execute Primitive & Advance State*: Instantiate `P`, invoke `primitive.execute(context, params)`, look up the returned `R.wireName()` in `LinkSpec.transitions`, persist the new `state` (and updated `call_stack` if entering or exiting a `SubWorkflowCall`) in `mcp/status.json`, append the transition event to `audit.jsonl`, and render the next state's TOON representation (executing chained `auto` and `call` steps until an interactive link state, async job state, or root terminal state is reached).

== Reusable Compound Sub-Workflows & Call-Stack Execution (`PM-WF-16`)
_See Requirement link:../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

Workflows are composed not only of atomic `do` / `auto` / `job` primitives, but also of reusable, config-aware *compound sub-workflows* (`scope subworkflow`). A compound sub-workflow encapsulates a multi-state sub-process—combining deterministic `auto` checks, configuration lookups, conditional interactive pauses, and recovery branches—so that Phase 5 (`execute`), Phase 6 (`finalize`), `pr-doctor`, `marshall-steward`, and `plan-orchestrator` invoke the exact same state machine rather than duplicating states or collapsing interactive recovery into opaque Java code.

=== Call-Stack Execution & Persistence Semantics

1. *Sub-Workflow Invocation (`call`)*: When the engine transitions into a `StateNode` whose behavior is `StateBehavior.SubWorkflowCall(subWorkflowId, paramBindings, transitions)`, it pushes a `CallFrame(callerWorkflowId, callerStateId, callerPhase, subWorkflowId, paramBindings, Instant.now().toString())` onto the `call_stack` array in `mcp/status.json` and sets `status.state` to the target sub-workflow's `startState` while preserving `status.phase = callerPhase` whenever a sub-workflow state declares `phase inherit`. Preserving `callerPhase` guarantees that phase-scoped guards (`in_worktree`, `loop_count_below_max`), phase metric accounting (`metrics.json`), and terminal-title updates remain invariant regardless of which caller invoked the sub-workflow.
2. *Interactive Pauses & Job Waits Inside a Sub-Workflow*: If execution inside the sub-workflow reaches an `AutoStep`, the engine executes it immediately in the same turn. If execution reaches an `InteractiveLinks` state (such as `git.artifact-review`, `git.compose-message`, `git.commit-fix`, or `git.sync-required`) or a `JobStep`, the engine persists `mcp/status.json` (with the active `call_stack` and sub-workflow `state`) and returns that state's TOON representation to the caller. Subsequent `pm_do` or `pm_state` calls resolve against the active sub-workflow state at the top of `call_stack`, surviving context compactions and daemon restarts identically to top-level states.
3. *Sub-Workflow Return (`terminal <outcome_id>`)*: When a transition inside the sub-workflow lands on a `StateNode` with `terminal == true` and `terminalOutcome == Optional.of(outcomeId)`, the engine pops the top `CallFrame` from `call_stack`, looks up `outcomeId` in the caller state's `OutcomeTransition` table, transitions `status.state` to `targetStateId` in `callerWorkflowId`, and continues auto-chaining in the same atomic transaction.

=== Canonical Reusable Sub-Workflow: `git.commit_and_push` (`git-commit-and-push.pmwf`)

The `git.commit_and_push` sub-workflow models the complete git commit-and-push sub-process grounded in `workflow-integration-git`, `phase-5-execute` (Step 10a), and `phase-6-finalize` (Step 3 item 5f, `standards/push.md`, and post-PR re-push).

==== Bound Parameter Contract

[cols="1,2,3"]
|===
|Parameter |Allowed Values |Semantics

|`message_mode`
|`auto_deliverable` \| `step_or_fallback` \| `interactive` \| `none_assert_clean`
|Controls commit message sourcing: `auto_deliverable` formats `feat(<module>): complete deliverable <N> - <title>` from the active deliverable; `step_or_fallback` uses a step-supplied commit message or `chore(finalize): apply <step_id> changes`; `interactive` pauses in `git.compose-message` with diff analysis facts for model submission; `none_assert_clean` expects a clean working tree (used by `finalize.push-barrier`) and routes any unexpected dirty files through `git.compose-message` before pushing.

|`push_mode`
|`never` \| `if_configured` \| `always` \| `post_pr_conditional`
|Controls push execution after commit (or on a clean tree): `never` stops after local commit; `if_configured` reads `.plan/marshal.json -> /phase-5-execute/commit_and_push` (default `true`); `always` pushes unconditionally; `post_pr_conditional` pushes if and only if the caller step has `order > 20` (post-`create-pr`) and `commit_and_push == true`.
|===

==== Declarative DSL Definition (`classpath:/workflows/git-commit-and-push.pmwf`)

[source,text]
----
workflow git.commit_and_push version 1
scope subworkflow
start git.inspect-worktree

      ok                    -> git.evaluate-push-policy
      hook_failed           -> git.commit-fix

      valid                 -> git.stage-and-commit

      denied                -> git.done-aborted

      denied                -> git.done-aborted

  phase inherit

==== Six-Stage Execution Contract of `git.commit_and_push`

* *Stage 1 — Working-Tree Inspection (`git.inspect-worktree`)*:
** Resolves the target checkout path from the locked scope context (`worktree_path` when `location == WORKTREE`, or `workspace_root` when `MAIN_CHECKOUT` / `epic` / `steward`).
** Executes `git -C <tree> status --porcelain` (ignoring `.plan/local/**`).
** If uncommitted changes exist (`staged`, `unstaged`, or `untracked`), returns `dirty -> git.detect-artifacts`.
** If the working tree is clean: returns `clean_skip_push -> git.done-clean` when `push_mode == never`; otherwise returns `clean_needs_push_check -> git.evaluate-push-policy` so clean-tree push barriers (`finalize.push-barrier` or post-rebase pushes) proceed directly to the freshness and parity checks without creating an empty commit.
* *Stage 2 — `.gitignore`-Aware Artifact Detection & Cleanup (`git.detect-artifacts`)*:
** Scans the working tree against `artifact-patterns.json` (`*.tmp`, `*.bak`, `*.orig`, `*.swp`, `.DS_Store`, `Thumbs.db`, coverage/build scratch files) while querying `git -C <tree> check-ignore`.
** Fails closed (`oracle_failed -> git.artifact-escalate`) if the `.gitignore` oracle cannot be evaluated.
** Unconditionally excludes `.plan/**` and any nested git worktrees or submodules (`git submodule status` / `.git` file markers) from deletion.
** Automatically deletes `safe` untracked artifact files and records `artifacts_deleted` in the audit log.
** Transitions to `git.artifact-review` only if `uncertain` tracked files match artifact patterns (`tracked_resolved == false`) or prohibited secret files (`.env*`, `*.pem`, `*.key`, `credentials.json`) are staged/untracked.
* *Stage 3 — In-Memory Commit Message Resolution, Validation & Trailer Injection (`git.resolve-message` / `git.compose-message`)*:
** When `message_mode` is `auto_deliverable` or `step_or_fallback`, resolves the deterministic commit message in memory (e.g., `feat(<module>): complete deliverable <N> - <title>` or `chore(finalize): apply <step_id> changes`).
** When `message_mode == interactive` (or `none_assert_clean` when unexpected dirty files were found), transitions to `git.compose-message`, populates `facts` via `git.diff-summary` (changed file count, module scope, priority-ordered suggested type `fix > feat > perf > refactor > docs > style > test > chore > ci`), and accepts `message: text 1..2000` directly in `pm_do` `args`.
** Validates Conventional Commits format (`<type>[optional (<scope>)][!]: <subject>`) via `ConventionalCommitValidator` and deterministically appends the configured trailer (`commit-trailer` from `.plan/marshal.json`, defaulting to `Co-Authored-By: plan-marshall <noreply@cuioss.de>`).
* *Stage 4 — Staging, `stdin`-Piped Commit & Change-Ledger Stamping (`git.stage-and-commit`)*:
** Stages scoped files (`git -C <tree> add -- <paths>`) and invokes `git -C <tree> commit -F -`, streaming the validated UTF-8 commit message + trailer directly to child `stdin` in memory (`PM-EXEC-5`) with zero `.plan/temp/` files.
** Captures `commit_sha` (`git -C <tree> rev-parse HEAD`) and git-sourced `changed_paths` (`git -C <tree> diff-tree --no-commit-id --name-only -r <commit_sha>`), appending a `kind = "change"` entry to `change-ledger.jsonl`.
** When invoked from a Phase 6 `mutates_source: true` step: re-stamps `head_at_completion = commit_sha` on `head_dependent: true` steps in `mcp/status.json`, and for steps with `order >= 10` (`pre-push-quality-gate.order`), writes a `freshness_reconcile` record (`commit_sha`, `step_id`, `prior_build_worktree_sha` from the latest passing build row in `change-ledger.jsonl`) so the downstream push gate recognizes the finalize-internal commit without requiring a redundant full build when no source-affecting inputs changed.
** If `git commit` exits non-zero due to a repository pre-commit hook, returns `hook_failed -> git.commit-fix`.
* *Stage 5 — Config-Driven Push Policy & Freshness Precondition (`git.evaluate-push-policy` -> `git.verify-freshness`)*:
** Evaluates `push_mode` together with `.plan/marshal.json -> /phase-5-execute/commit_and_push` (default `true`): `push_mode == never` skips push (`skip_push_committed -> git.done-committed-local`); `push_mode == if_configured` requires push if and only if `commit_and_push == true`; `push_mode == post_pr_conditional` requires push if and only if `commit_and_push == true` and the calling finalize step has `order > 20` (after `create-pr`), automating post-PR re-push for late source-mutating steps (`adr-propose` or triage fixes); `push_mode == always` requires push unconditionally.
** Before any push, `git.pre-commit-verify-freshness` verifies `change-ledger.jsonl` freshness (`fresh` corroborated on both notation and scope dimensions against the current `worktree_sha`, `exempt` when `build-decision == not_necessary`, or reconciled via `freshness_reconcile`). If `stale` or `undecidable`, transitions to `git.freshness-blocked` (offering `run_verification_build` or operator `escalate`).
* *Stage 6 — Branch Sync Parity Probe & Push Execution (`git.check-branch-parity` -> `git.execute-push`)*:
** Runs `git.branch-sync-state` comparing local `HEAD` against `origin/<branch>`: `ahead` or `remote_absent_unverified` (initial unpushed branch) proceeds to `git.execute-push` (`git -C <tree> push` or `git -C <tree> push --set-upstream origin <branch>`); `synced` or `remote_absent_landed` (branch already merged and remote deleted) returns `synced_or_landed_skip -> git.done-pushed-clean` so a landed-and-deleted remote branch is never resurrected.
** If `git push` is rejected as non-fast-forward (`rejected_non_ff`), transitions to `git.sync-required` (offering `sync_rebase` or operator `force_push_with_lease` escalation).

== Worktree-Constrained Loop-Back & Iteration Bounds
_See Requirement link:../Requirements.adoc#PM-WF-7[PM-WF-7: Worktree-Constrained Loop-Back & Iteration Bounds]_

When a finalize step (CI failure, quality gate failure, or review finding triage) requires code changes, the workflow transitions from `finalize` back to `execute` via a `loop_back` link governed by three strict server-side invariants:

=== 1. Worktree Confinement Guard (`in_worktree`)

* Every `loop_back` link in `finalize.pmwf` declares `guard in_worktree and loop_count_below_max`.
* `GuardExpr.InWorktree` evaluates to `true` if and only if `.plan/local/worktrees/<plan_id>/` exists, is a valid git worktree for the plan's branch, and the plan directory currently resides at `.plan/local/worktrees/<plan_id>/.plan/plans/<plan_id>/`.
* Once the plan passes `finalize.merge-gate`, merges its branch, and relocates back to the primary checkout (`.plan/local/plans/<plan_id>/`), `InWorktree` evaluates to `false`. All `loop_back` links are automatically omitted from representations and rejected by `pm_do`.

=== 2. Configuration Resolution & Iteration Counter Validation

* The maximum number of automated finalize-to-execute loop-backs is configured in `.plan/marshal.json` under JSON pointer `/phase-6-finalize/max_iterations`:
+
[source,json]
----
{
  "phase-6-finalize": {
    "max_iterations": 3
  }
}
----

* If `/phase-6-finalize/max_iterations` is omitted in `.plan/marshal.json`, the engine applies the normative default of `3` (valid configured range: `1..10`).
* The plan's `mcp/status.json` persists `"finalize_iteration": <int>` (initialized to `0` when entering `finalize` for the first time).
* `GuardExpr.LoopCountBelowMax` evaluates `status.finalizeIteration() < config.phase6Finalize().maxIterations()`.
* When `plan.allocate-remediation-tasks` executes on a valid `loop_back`:
** `finalize_iteration` is atomically incremented by `1` in `mcp/status.json`.
** Fresh task files (`TASK-NNN.json`) and a fresh dispatch envelope (`envelope-M` with a new `dispatch_id`) are allocated in the worktree — completed tasks are never mutated or reopened.
* If a finalize failure occurs when `finalize_iteration >= max_iterations`, `LoopCountBelowMax` evaluates to `false`, `loop_back` is omitted, and the state transitions to `finalize.loop-limit-reached`, which offers only `escalate` (requiring operator approval via elicitation or `pm-mcp operator` to grant additional iterations or abort).

== State-Machine Property Verification, Scenario Replay & State Migration
_See Requirement link:../Requirements.adoc#PM-TEST-3[PM-TEST-3: State-Machine Property Verification]_

_See Requirement link:../Requirements.adoc#PM-TEST-4[PM-TEST-4: End-to-End Scenario Replay Harness]_

_See Requirement link:../Requirements.adoc#PM-MIG-4[PM-MIG-4: State-Name Migration Registry]_

=== Property-Based State-Machine Verification (`PM-TEST-3`)

The `pm-mcp-core` test suite executes property-based tests (using `jqwik` / `cui-test-generator`) over every compiled `WorkflowDefinition` AST:

* *No Dead-End Non-Terminal States*: Every non-terminal `StateNode` has at least one guard assignment under which at least one outgoing link or auto/job transition is offered, and every reachable state has a finite path to a `terminal` state (`completed` or `aborted`).
* *Strict Guard Enforcement & Link Omission*: Random sequences of `pm_do` calls with invalid link names, unsatisfied guards (such as `loop_back` when `in_worktree == false` or `finalize_iteration >= max_iterations`), or out-of-range parameters never mutate `mcp/status.json` and always return `rejected.reason` with `isError: false`.
* *Single-Level Leaf Sub-Agent Invariant*: Property generators traverse all reachable states in `WorkflowScope.ENTITY` definitions and verify that zero `form == LinkForm.DISPATCH` links are ever emitted.
* *Monotonic Bounded Loops*: Random failure injection in Q-Gate and finalize-to-execute loop-backs verifies that no path can traverse `loop_back` more than `max_iterations` times without entering `*.loop-limit-reached` / `*.qgate-exhausted`.

=== Deterministic Scenario Replay Harness (`pm-mcp-scenario`, `PM-TEST-4`)

End-to-end lifecycle scenarios are authored as deterministic `.pmscenario` scripts executed in-process by `ScenarioReplayRunner` against a hermetic temporary git repository without invoking any live LLM:

resolve_elicitation approve_outline {"decision":"approve"}
complete_job job-build-0001 {"outcome":"passed","worktree_sha":"e3b0c442..."}

----

* Each scenario step supports deterministic assertions (`assert_state`, `assert_links`, `assert_skill`, `assert_rejected`) and simulated actor actions (`do`, `complete_job`, `resolve_elicitation`, `operator_cli`).
* The mandatory CI regression suite replays scenarios covering: (1) happy-path single-module plan, (2) multi-task envelope dispatch and context-budget yield, (3) CI failure and worktree-constrained `loop_back` to `execute`, (4) review-bot finding triage (`FIX`, `SUPPRESS`, `ACCEPT`), (5) operator escalation via elicitation and CLI fallback, and (6) mid-job daemon restart recovery.

=== State-Name Migration Registry & `released-states.txt` Gate (`PM-MIG-4`)

To guarantee that active plans survive `pm-mcp` binary upgrades across state renames or workflow splits:

* Every state identifier shipped in a public release is appended to the committed `classpath:/workflows/released-states.txt` baseline.
* When a state is renamed or split in a `.pmwf` file, the workflow header declares `migrate <old_state_id> -> <new_state_id>`.
* When `WorkflowEngine` loads `mcp/status.json` whose `state` matches `<old_state_id>`, it transparently rewrites `state` to `<new_state_id>` and appends a `state_migrated` event to `audit.jsonl`.
* A build-time JUnit gate (`ReleasedStatesMigrationTest`) verifies that every entry in `released-states.txt` either exists in the current `WorkflowDefinition.states()` map or is covered by a transitive `migrate` chain terminating in a live state.
