== Overview

This document specifies the declarative Workflow Domain-Specific Language (DSL), Abstract Syntax Tree (AST) model, typed Java `Primitive<P, R>` execution contract, loop-back guard semantics, automated diagram generation, and the verification harnesses (including the out-of-band behavioural conformance harness for model-facing content) for *plan-marshall-mcp* (`PM-MCP`). The workflow engine and DSL reside in the plain-Java `pm-mcp-core` module with zero runtime framework dependencies and are assembled into the native daemon by `pm-mcp-server`.

== Module Boundary & Decoupled Core Architecture
_See Requirement link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1: Decoupled Plain-Java Core Engine & Quarkus Assembly]_

_Implementation watch: link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-12[PM-WATCH-DSL-12], link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-13[PM-WATCH-DSL-13]_

The workflow engine is strictly decoupled from Quarkus, CDI, Vert.x, and MCP transport libraries. All modules are created and integrated in Milestone 0 (link:../roadmap.adoc[Roadmap]), each with minimal real code and tests: the root `plan-marshall-mcp` module is renamed to `pm-mcp-server`, the library modules are gathered under the aggregator `pm-mcp-modules` (the external integrations under the nested aggregator `pm-mcp-providers`), the client modules under the top-level aggregator `pm-mcp-clients`, and an automated build check enforces the dependency direction (`PM-IMPL-1`). Dependencies flow toward `pm-mcp-core`: provider contract and implementation modules depend on `pm-mcp-core`, implementation modules on their contract modules, and `pm-mcp-server` on all of them and on `pm-mcp-api`. The client modules never depend on `pm-mcp-core` or a provider module: `pm-mcp-cli` depends on `pm-mcp-api` only, `pm-mcp-web-server` on `pm-mcp-api`, `pm-mcp-web-app`, and Quarkus. One release produces four native binaries: `pm-mcp` (CLI), `pm-mcpd` (daemon), `pm-mcp-exec` (job launcher), and `pm-mcp-web` (optional web server).

== Formal EBNF Grammar for the Workflow DSL
_See Requirement link:../Requirements.adoc#PM-WF-2[PM-WF-2: Closed Link Relation Grammar & Link Forms]_

_See Requirement link:../Requirements.adoc#PM-WF-3[PM-WF-3: Capability Enforcement by Link Omission]_

_See Requirement link:../Requirements.adoc#PM-WF-4[PM-WF-4: Entity-Scoped Links & Fine-Grained Concurrency]_

_See Requirement link:../Requirements.adoc#PM-WF-9[PM-WF-9: Composite Wait States & Short-Circuit Failure Handling]_

_See Requirement link:../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

Workflow definitions (the default `*.pmwf` units compiled into the binary under `classpath:/workflows/`, and the project-owned copies of the phase and sub-workflow units in `.marshall/config/*.pmwf`, <<project-owned-units>>) conform to the following ISO/IEC 14977 Extended Backus-Naur Form (EBNF) grammar. The DSL is line-oriented; comments start with `#` and run to the end of the line.

[source,ebnf]
----
workflow_file        = workflow_header ,
                       ( subworkflow_decl | [ scope_decl ] ) ,
                       start_decl ,
                       { migrate_decl } ,
                       state_decl , { state_decl } ;

workflow_header      = "workflow" , state_id , "version" , positive_int ,
                       "format" , positive_int ,
                       [ "derived_from" , positive_int ] , EOL ;
                       (* version: the unit's revision; format: the DSL format version, accepted only
                          at the binary's current value (store-schemas.adoc, Format Versioning);
                          derived_from: only in a project-owned copy, the default revision it derives from *)
scope_decl           = "scope" , ( "plan" | "epic" | "workspace" | "entity" ) , EOL ;
subworkflow_decl     = "scope" , "subworkflow" , EOL ,
                       { subworkflow_param } ;
subworkflow_param    = "param" , param_name , ":" , subworkflow_type , EOL ;
subworkflow_type     = enum_type
                     | "int" , [ int_range ] ;
start_decl           = "start" , state_id , EOL ;
migrate_decl         = "migrate" , state_id , "->" , state_id , EOL ;

state_decl           = "state" , state_id , [ terminal_decl ] , EOL ,
                       [ phase_clause ] ,
                       [ skill_clause ] ,
                       [ facts_clause ] ,
                       state_body ;
terminal_decl        = "terminal" , outcome_id , outcome_class ;
outcome_class        = "success" | "skip" | "failure" | "indeterminate" | "unsettled" | "aborted" ;
                       (* the closed OutcomeClass set, lower case *)

phase_clause         = "phase" , ( identifier | "inherit" ) , EOL ;
skill_clause         = "skill" , skill_path , EOL ;
facts_clause         = "facts" , primitive_id , EOL ;

state_body           = (* empty for terminal states *)
                     | auto_clause
                     | job_clause
                     | call_clause
                     | link_clause , { link_clause } ;

auto_clause          = "auto" , primitive_id , EOL ,
                       outcome_transition , { outcome_transition } ;

job_clause           = ( "job" | "composite_job" ) , primitive_id , EOL ,
                       outcome_transition , { outcome_transition } ;

call_clause          = "call" , state_id , [ "(" , [ call_arg_list ] , ")" ] , EOL ,
                       outcome_transition , { outcome_transition } ;
call_arg_list        = call_arg , { "," , call_arg } ;
call_arg             = param_name , "=" , ( enum_value | positive_int_or_zero ) ;

link_clause          = "link" , relation , link_id_pattern ,
                       [ "[" , link_form , "]" ] ,
                       "(" , [ param_list ] , ")" , EOL ,
                       [ guard_clause ] ,
                       link_action ,
                       outcome_transition , { outcome_transition } ;

relation             = "next" | "alt" | "retry" | "fix" | "loop_back"
                     | "submit" | "dispatch" | "wait" | "escalate"
                     | "abort" | "emit" ;

link_form            = "submit" | "wait" | "dispatch" | "escalate" | "noop" ;

link_id_pattern      = action_id , [ ":" , ( entity_placeholder | identifier ) ] ;
entity_placeholder   = "<" , identifier , ">" ;

param_list           = param_decl , { "," , param_decl } ;
param_decl           = param_name , ":" , type_spec , [ "?" ] ;

type_spec            = scalar_type
                     | "list" , "<" , scalar_type , ">" ;
scalar_type          = "text" , [ int_range ]
                     | "int" , [ int_range ]
                     | enum_type
                     | schema_ref ;
enum_type            = "enum" , "[" , enum_value , { "|" , enum_value } , "]" ;
schema_ref           = "schema" , "[" , schema_name , "]" ;
                       (* named parameter schema, hypermedia-format.adoc, Named Parameter Schemas *)
schema_name          = lowercase_alpha , { lowercase_alpha | digit | "-" } ;   (* identifiers.adoc, named parameter schema *)

int_range            = "[" , positive_int_or_zero , ".." , positive_int , "]" ;
                       (* the same bracket form as the hypermedia `free` column, e.g. text[1..500] *)

guard_clause         = "guard" , guard_expr , EOL ,
                       [ "depends_on_config" , "[" , config_key , { "," , config_key } , "]" , EOL ] ;
guard_expr           = guard_term , { "or" , guard_term } ;
guard_term           = guard_factor , { "and" , guard_factor } ;
guard_factor         = [ "not" ] , ( guard_atom | "(" , guard_expr , ")" ) ;
guard_atom           = "in_worktree"
                     | "has_open_findings"
                     | "all_tasks_completed"
                     | "predicate:" , primitive_id ;

link_action          = ( "do" , primitive_id , EOL )
                     | ( "dispatch" , identifier , "role" , role_key , EOL )
                     | ( "escalate" , identifier , EOL ) ;
role_key             = identifier , { "." , identifier } ;
                       (* effort role key, e.g. plan.phase-5-execute.effort.default; the effort level is
                          always resolved from the role (dispatch-and-effort.adoc, Role Resolution) *)

outcome_transition   = outcome_id , "->" , state_id , EOL ,
                       { completes_clause } ;
completes_clause     = "completes" , step_id , "as" , step_completion , EOL ;
step_completion      = "done" | "skipped" | "failed" | "skipped_by_operator" ;
                       (* skipped_by_operator: only on an outcome of class APPROVED of a decision (Rule 9) *)
step_id              = step_segment , ":" , step_segment ;   (* identifiers.adoc, step_id *)
step_segment         = lowercase_alpha , { lowercase_alpha | digit | "-" } ;
config_key           = identifier , { "." , identifier } ;   (* an enum or boolean configuration key *)

state_id             = identifier , { "." , identifier } ;
primitive_id         = identifier , "." , identifier ;
skill_path           = "pm/" , identifier , { "/" , identifier } ;  (* maps to the URI "skill://" , skill_path , "/SKILL.md" *)
outcome_id           = identifier ;
action_id            = identifier ;
identifier           = lowercase_alpha , { lowercase_alpha | digit | "_" | "-" } ;
param_name           = lowercase_alpha , { lowercase_alpha | digit | "_" } ;   (* identifiers.adoc, free parameter name *)
enum_value           = letter , { letter | digit | "_" | "-" } ;
positive_int         = nonzero_digit , { digit } ;
positive_int_or_zero = "0" | positive_int ;
letter               = lowercase_alpha | uppercase_alpha ;
lowercase_alpha      = ? ASCII "a".."z" ? ;
uppercase_alpha      = ? ASCII "A".."Z" ? ;
digit                = "0" | nonzero_digit ;
nonzero_digit        = ? ASCII "1".."9" ? ;
any_char_except_nl   = ? any Unicode scalar value except "\n" ? ;
EOL                  = [ "#" , { any_char_except_nl } ] , "\n" ;
----

Identifiers (state, primitive, action, parameter, and outcome names) are lowercase; their regex forms and length bounds (32 characters per identifier, 64 per dotted `state_id`) are registered in the link:identifiers.adoc#id-state-id[Identifier Registry], which the static verification rules enforce. Parameter names (`param_name`: link parameters, sub-workflow `param` declarations, and `call` arguments) follow the registry's link:identifiers.adoc#id-param-name[free parameter name] grammar and never contain `-`, because they appear verbatim as keys of `pm_do` `args` and in the hypermedia `free` column. Ranges use the bracket form of the wire (`text[1..500]`, `int[0..100]`), so a declared parameter reads the same in DSL source and in the rendered `free` column. Enum values are a separate token (`enum_value`) that also admits upper case, so closed domain vocabularies such as `enum[FIX|SUPPRESS|ACCEPT]` are expressible verbatim. Lists use the single syntax `list<…>` in both the DSL and the hypermedia `free` column (link:hypermedia-format.adoc[Hypermedia Format Specification]); there is no free-form object type and no boolean type. The only object-valued type is the named schema reference `schema[<schema_name>]` (also as `list<schema[<schema_name>]>`), whose value the server validates against the closed JSON Schema registered under that name (link:hypermedia-format.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]); a name that is not registered fails validation (Rule 1 in <<static-verification-rules>>). Sub-workflow `param` declarations never use it.

`param` declarations are permitted only in the header of a `scope subworkflow` file. They declare the complete closed parameter schema that every `call` site must bind (Rule 6 in <<static-verification-rules>>); sub-workflow parameters are restricted to `enum[…]` and `int` because they are bound from literal values at the call site, never from model input.

[#dsl-reserved-keywords]
* *Reserved keywords*: `workflow`, `version`, `format`, `derived_from`, `scope`, `param`, `start`, `migrate`, `state`, `terminal`, `phase`, `inherit`, `skill`, `facts`, `auto`, `job`, `composite_job`, `call`, `link`, `guard`, `depends_on_config`, `do`, `dispatch`, `role`, `escalate`, `completes`, `as`, `and`, `or`, `not`, `in_worktree`, `has_open_findings`, `all_tasks_completed`, `predicate`, `text`, `int`, `enum`, `schema`, and `list` are reserved. None of them may be used as an outcome name, a parameter name, a decision kind, a dispatch entity kind, or a segment of a state, primitive, role, or configuration key identifier; the parser rejects such a use with the source file and line. Two positional vocabularies are not reserved, because they occur only where the grammar expects them: the relation and form values (`next` .. `emit`, `noop`), which deliberately double as action names (`link escalate escalate [escalate]`, `link retry retry [noop]`; `dispatch` and `escalate` are reserved as link-action keywords but stay admitted in the relation, form, and action-name positions), and the scope, outcome class, and step completion values (`plan`, `epic`, `workspace`, `entity`, `subworkflow`, `success` .. `aborted`, `done`, `skipped`, `failed`, `skipped_by_operator`), which are also ordinary identifier segments (`plan.allocate-remediation-tasks`).
* *Link relations and forms*: `relation` and `link_form` are the closed enumerations `LinkRelation` and `LinkForm` (<<_ast_node_model>>), taken from the link:hypermedia-format.adoc#_closed_link_relations_rel[Hypermedia Format Specification, Closed Link Relations] table. Every relation admits a fixed set of forms and has a default form, which applies when a `link` clause omits `[form]`. Their compatibility, and the fit of the form to the parameter list and the link action, is Rule 12 (<<static-verification-rules>>).
* *Dispatch*: A dispatch link action is written only as `dispatch <entity_kind> role <role_key>`. The DSL never names an effort level: the level is always resolved from the role at dispatch time (link:dispatch-and-effort.adoc#_role_registry_lookup_hierarchy[Dispatch & Effort Specification, Role Registry & Lookup Hierarchy]), so a configuration change of the role reaches every dispatch without a workflow version.
* *`phase inherit`*: A state that declares `phase inherit` takes the phase value of the calling state: the `callerPhase` of the top `CallFrame` (<<_call_stack_execution_persistence_semantics>>), which is itself the resolved phase value of the caller state, so a nested call inherits transitively down to the first state with a concrete phase. `inherit` is admitted only in a `scope subworkflow` unit (Rule 6); a sub-workflow state never changes `status.phase`.
* *Terminal declarations*: Every terminal state declares `terminal <outcome_id> <outcome_class>`: the outcome it reports (for a sub-workflow, the outcome returned to the caller) and its `OutcomeClass` (<<primitive-outcome-classes>>), for example `state git.done-clean terminal clean skip`, `state git.done-aborted terminal aborted aborted`, or `state plan.aborted terminal aborted failure`.
* *Abort model*: A plan-scope or epic-scope unit has exactly one abort terminal state, `plan.aborted` or `epic.aborted` (phase value `aborted`, class `failure`), reachable from every phase; there are no phase-specific abort terminals. A model-followable `abort` link inside a sub-workflow or a phase flow only leaves that flow: it ends in a terminal state of outcome `aborted` and class `aborted`, which returns the outcome to the caller, and the caller routes it back to a decision state or to an escalation. Ending the whole plan or epic is operator-authorizing: a routine `abort` answer is the link `abort` (rel `escalate`, form `escalate`, action `escalate abort-plan`, or `escalate abort-epic` in the epic unit), which raises the `blocked` condition (<<condition-overlays>>) with that decision kind when no elicitation is available (<<decision-registry>>). Only an operator decision outcome of class `ABORTED` or `DENIED` enters `plan.aborted` or `epic.aborted`.
* *Step completion (`completes`)*: A transition that settles a finalize step names it with one `completes <step_id> as done|skipped|failed|skipped_by_operator` clause per settled step, on the lines following the transition. The engine writes the step record (`mcp/status.json` `steps`, link:store-schemas.adoc[Store Schemas Specification]) in the transaction of that transition; Rule 9 (<<static-verification-rules>>) checks that every step is completed exactly once on every path and never as `done` on a failing, denied, or aborted path. `skipped_by_operator` is admitted only on an `APPROVED` decision outcome: the step is settled by the operator's decision, whose record the step record references (the grant or acknowledgement, `decision_id`), and it satisfies Phase-Exit Completeness (link:phase-workflows.adoc#_re_entry_head_at_completion_verdict_currency_rules[Phase Workflows Specification, Verdict Currency Rules]).
* *Configuration-dependent guards*: A `guard` clause may declare `depends_on_config [key, …]`, the enum or boolean keys of the effective configuration (in the effective-key form `<file_stem>.<dotted path>`, for example `project.review.currency` or `derived.push_remote`, link:store-schemas.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]) whose values the guard reads. Rule 3 checks reachability for every combination of the declared keys' values (<<static-verification-rules>>).

[#workflow-definition-units]
=== Workflow Definition Units (Multi-File Workflows)

A workflow definition may be split across several `.pmwf` files:

* *Plan workflow*: All phase workflow files of a plan (`init.pmwf`, `refine.pmwf`, `outline.pmwf`, `plan.pmwf`, `execute.pmwf`, `land.pmwf` for the `land` lane states, `finalize.pmwf`) together form *one* workflow definition. The loader merges them into a single `WorkflowDefinition` before validation: `states` and `migrations` are the union of all files, the definition's `startState` is the `start` of `init.pmwf`, and the `start` of every other phase file names that phase's entry state. A transition in one phase file may therefore target a state declared in another (for example `allocated -> execute.dispatch-ready` in `finalize.pmwf`). Every phase file declares `scope plan` and its own `workflow <part> version <n>` header; the part headers identify files only. The merged unit carries a header of its own, which no file declares: `id` is `plan`, `scope` is `plan`, and `version` is derived from the part versions as their sum, recorded with the part versions themselves (`WorkflowDefinition.partVersions`, <<_ast_node_model>>). Because a part version only ever increases, the derived version increases with every change of any part. The unit id `plan` is the value of `CallFrame.callerWorkflowId` for every `call` made from a plan-workflow state (`status.json` `call_stack[].caller_workflow_id`), whichever phase file declares the calling state; the part header `workflow plan` of `plan.pmwf` (Phase 4) is a file identifier and never names the unit.
* *Other top-level workflows*: Every other file with `scope plan`, `epic`, `workspace`, or `entity` (for example `epic.pmwf` with `scope epic`, `project-setup.pmwf` with `scope workspace`) forms a single-file definition.
* *Sub-workflows*: Every `scope subworkflow` file (for example `git-commit-and-push.pmwf`) is a separately scoped definition. Its states are never merged into a caller's definition and are reachable only through `call`; transitions inside a sub-workflow may target only states of the same sub-workflow, and transitions outside it may never target a sub-workflow state.

The same unit rules apply to the default units of the binary and to a project's own copies in `.marshall/config/` (<<project-owned-units>>); a project never mixes a default file with its own copies inside one definition unit.

All static verification rules (<<static-verification-rules>>) run over the merged definition unit: state identifiers must be unique across all files of the unit, transition targets must exist in the unit, every state must be reachable from the unit's `startState` under every combination of the configuration keys its guards declare, outcome coverage is exhaustive per state, and link identifier patterns are unique within their state.

[#implicit-job-links]
=== Implicit Links of Job States

Every `job` and `composite_job` state implicitly offers two links that are never declared in DSL source:

[cols="1,1,1,3"]
|===
|Link |`rel` |`form` |Semantics

|`wait:<job_id>`
|`wait`
|`wait`
|Bounded blocking wait on the running job (`PM-WF-8`); returns the next state's representation once the job settles, or the updated running representation.

|`cancel:<job_id>`
|`abort`
|`noop`
|Cancels the running job (for a composite job, all constituent jobs); the job settles with the outcome `cancelled`.
|===

Independently of the state kind, the engine accepts the self-report link `report_bypass` in every state of a live plan, epic, or entity scope and never renders it (link:hypermedia-format.adoc#self-report-link[Hypermedia Format Specification, Self-Report Link]); it returns the unchanged representation and never changes state, so it needs no outcome transition. Implicit links count as offered for every check that compares link identifiers against the workflow definitions (for example the vocabulary-skill link check, `PM-WATCH-TOOL-6`).

`<job_id>` is the job identifier of a `job` state (for example `wait:b-2291`) and the composite identifier, which equals the state identifier, of a `composite_job` state (for example `wait:finalize.concurrent-wait`). The outcome enumeration of every `job` and `composite_job` primitive contains `cancelled`, so every such state must declare an explicit `cancelled -> <state>` outcome transition; Rule 2 (exhaustive outcome coverage) enforces it. A `job` state's outcome enumeration is the closed job outcome set of `PM-EXEC-4` (`succeeded`, `failed`, `failed_unparsed` for build jobs only, `refused`, `cancelled`, `timed_out`, `killed`, `indeterminate`); a `composite_job` primitive declares its own closed workflow outcomes (`PM-WF-8`). A DSL link whose identifier pattern collides with an implicit link fails validation. `<job_id>` is always the job bound in `active_job` (<<job-state-binding>>); `wait` on a bound job only waits and never starts one.

[#job-state-binding]
=== Job State Entry & Binding (`JobStep`)
_See Requirement link:../Requirements.adoc#PM-ARCH-8[PM-ARCH-8: Runtime & Relay Lifecycle, Crash Recovery & Job Drain]_

A `job` state is a resting state over exactly one job. The engine binds it as follows (normative for `StateBehavior.JobStep`):

1. *One job per entry*: Entering a `job` state starts exactly one job through the state's primitive, unless a job id is already bound for the state. A job id is bound when the entering transition carries one (item 3) or when `active_job` already names this state.
2. *`active_job` in the state transaction*: `mcp/status.json` records `active_job {state_id, job_id}` (link:store-schemas.adoc#_workflow_state_store_mcpstatus_json[Store Schemas Specification, Workflow State Store]) in the same journaled transaction (link:store-schemas.adoc#transaction-journal[Transaction Journal]) as the state change that enters the state and the enqueue of the job. A crash therefore leaves either the old state without a job or the new state with its bound job, never a job without a binding or a job state without its job.
3. *Enqueued by a preceding primitive*: A primitive that enqueues a job for the following state (an `auto` state or a `do` link action, for example `build.enqueue-verification` before `git.freshness-build-running`) declares `enqueuesJob()` and returns the job's id as its primitive result (`PrimitiveResult.spawnedJobId`) with the outcome `started`. The `started` transition enters the `job` (or `composite_job`) state, which binds that id and starts nothing itself. Rule 1 (<<static-verification-rules>>) verifies the binding: every `started` outcome of an `enqueuesJob()` primitive targets a `job` or `composite_job` state, and no other outcome of such a primitive does.
4. *Re-entry only waits*: A `pm_state` or `pm_do` on a job state whose bound job is `queued` or `running`, including the first call after a runtime restart, only waits on it (`wait:<job_id>`); it never starts a second job.
5. *Killed jobs are routed, never restarted*: A bound job that the runtime recorded `killed` (for example an orphaned `running` job marked on restart, `PM-ARCH-8`) settles the state with the outcome `killed`, which every `job` state routes explicitly (Rule 2). The engine never re-enqueues a job on its own (no blind re-execution); a new job starts only when a declared transition enters a job state again, for example through a `retry` link.
6. *Leaving clears the binding*: The transition that leaves the state (on the job's outcome, or on `cancel:<job_id>`) clears `active_job` in the same transaction.

A `composite_job` state follows the same rules with its composite identifier (the state identifier) as the bound id; its constituent jobs are recorded in `active_jobs`.

[#escalation-decision-wait]
=== Escalation Without Elicitation & the Implicit Decision Wait

An `escalate <decision>` link action requests an operator decision (`PM-SEC-3`). On a connection that declared elicitation support, the engine prompts through `elicitation/create` and takes the link's outcome transition for the answer. Otherwise it records the pending decision in the scope's `mcp/status.json` (`pending_decision` with a fresh `decision_id`, link:store-schemas.adoc[Store Schemas Specification]) and raises the `blocked` condition on the current state (<<condition-overlays>>): `state` and `call_stack` stay unchanged, and the representation carries `condition: blocked` and `facts.operator_command` and offers exactly one implicit link:

[cols="1,1,1,3"]
|===
|Link |`rel` |`form` |Semantics

|`wait:decision:<decision_id>`
|`wait`
|`wait`
|Bounded wait (`PM-IMPL-4`) on the pending decision record. Once the operator resolves the decision through `pm-mcp operator`, the condition is cleared, the escalate link's outcome transition for that resolution is taken from the current state, and the next state's representation is returned; when the wait bound expires, the unchanged representation with its `blocked` condition is returned.
|===

The `wait:decision:` identifier prefix is reserved for this implicit link; a DSL link whose identifier pattern collides with it fails validation.

[#decision-registry]
=== Decision Registry & Typed Escalation Outcomes
_See Requirement link:../Requirements.adoc#PM-WF-12[PM-WF-12: Routine User Dialogue vs Operator-Authorizing Elicitation]_

Escalation decisions are typed like primitives. Every decision kind named by an `escalate <decision>` link action is registered server-side in the `DecisionRegistry` (`pm-mcp-core`, beside the primitive registry) as a `DecisionSpec`: the closed outcome enumeration of the decision kind, one `DecisionOutcomeClass` per outcome (as every `Primitive<P, R>` outcome declares an `OutcomeClass`, <<primitive-outcome-classes>>), and, for every approving outcome, the primitive that performs the approved action. A decision kind that is not registered fails validation (Rule 2 in <<static-verification-rules>>). The operator's resolution, by elicitation or `pm-mcp operator`, is accepted only when it names a declared outcome of the pending decision's kind; `pending_decision.resolution` (link:store-schemas.adoc[Store Schemas Specification]) never holds any other value.

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.spi;

import java.util.Map;
import java.util.Set;

public enum DecisionOutcomeClass { APPROVED, DENIED, ABORTED }

public record DecisionSpec(
    String decisionKind,                          // e.g. "loop_limit_extension"
    Set<String> outcomes,                         // closed outcome enumeration, e.g. {"extended", "aborted"}
    Map<String, DecisionOutcomeClass> classes,    // exactly one class per outcome
    Map<String, String> approvedActions,          // APPROVED outcome -> primitive id performing the approved action
    List<ParamSpec> escalateParams                // free parameters of every escalate link of this kind (possibly empty)
) {}
----

* *`APPROVED`*: The operator authorizes an action. The outcome names the primitive that performs it (`approvedActions`), and its transition must enter an `auto` state running that primitive (Rule 10).
* *`DENIED`*: The operator declines the action. The transition leads to a state that does not perform it (a retry or alternative state of the same unit, or the unit's `aborted` terminal state) and never records the step `done` (Rule 9).
* *`ABORTED`*: The operator stops the scope. The transition leads to the unit's `aborted` terminal state: `plan.aborted` in the plan workflow, `epic.aborted` in the epic workflow, and in a sub-workflow the terminal state with outcome `aborted`, which returns to the caller (<<_formal_ebnf_grammar_for_the_workflow_dsl>>, Abort model).

* *Hard CI failure (`PM-WF-9`)*: `finalize.ci-failed` offers both remediation paths. `fix_in_branch` (rel `fix`) is followed after the model has applied the fix in the worktree; `finalize.record-in-branch-fix` records `fix_summary` and routes through `finalize.settle-commit` (`call git.commit_and_push` with `push_mode=post_pr_conditional`), whose `committed_and_pushed` outcome re-enters `finalize.concurrent-wait` (through `finalize.review-cap-check`) so CI and review bots re-evaluate the new `HEAD`. A clean worktree yields `no_changes` and leaves the plan in `finalize.ci-failed`. `loop_back` returns to `execute` for cross-task remediation (<<loop-back-bounds>>).
* *Pre-wait cap gate*: Before `finalize.concurrent-wait` is entered, `finalize.review-cap-check` measures the diff (changed files, diff characters) against the structural caps each required review bot declares in the review-bot registry (link:phase-workflows.adoc[Phase Workflows Specification]). An exceeded cap records the bot as `refused` with mode `size` pre-emptively, names the cap and the measurement in `facts`, and routes to `finalize.review-structural` instead of waiting; under every cap the flow is unchanged.
* *Review-bot refusal modes*: The composite outcomes of `finalize.watch-ci-and-bots` separate the refusal modes, because a single rate-limit outcome cannot express them. `bot_refused_awaitable` (a rate window that reopens) enters `finalize.review-window-wait`, a job that waits for the registered window (the registered interval times the attempt ceiling; a published ETA is a floor that is re-checked, never skipped) and then re-triggers the unproven bots automatically. `bot_refused_hard` (weekly or hard quota) and `bot_unproven` (no review evidence for the current `HEAD` after the wait) enter `finalize.review-escalate`. `bot_refused_structural` (size) enters `finalize.review-structural`, which never waits: it shows each structural refusal as a finding and offers `triage:<finding_id>` per finding, the link and primitive of `finalize.triage`, where `FIX` splits (when a path partition, for example test sources versus the rest, brings each part under the cap, the finding proposes that concrete split), `ACCEPT` accepts the refusal, and `SUPPRESS` disables the bot for this pull request. Once every structural finding is triaged, a `FIX` takes the fix path through `finalize.settle-commit`; otherwise the flow returns through `finalize.review-cap-check`, which no longer counts the accepted or disabled bots, into the wait region, where any other open finding is triaged in `finalize.triage` (`findings_open`). `bot_no_unreviewed_commit` enters `finalize.review-full-trigger`, which posts the registry's full-review trigger verb.
* *Full-review trigger*: `finalize.review-full-trigger` posts the registry's `full` trigger verb for the bots that reported no unreviewed commit, once per bot and `HEAD`; a repeated notice after that trigger yields `already_triggered` and escalates, and a closed rate window routes to `finalize.review-window-wait` (link:phase-workflows.adoc#automatic-review[Phase Workflows Specification], Refusals & Rate Windows).
* *Unestablished roster*: `roster_unestablished` (the required set is empty because the roster question was never put) enters `finalize.review-escalate`; with no bot to re-trigger, its only way on is the `review_barrier_gap` escalation.
* *Finalize spend overrun*: Before the pre-merge barrier, `finalize.merge-gate` compares the cumulative finalize spend with the error column of the plan's budget anchor (link:dispatch-and-effort.adoc#spend-accounting-budget-anchors[Dispatch & Effort Specification]); an overrun enters `finalize.spend-escalate`, whose approved escalation records the acknowledgement and returns to `finalize.merge-gate`.
* *Merge path*: The merge-path states after `finalize.merge-gate` are not part of the excerpt; they are catalogued in the link:state-catalogue.adoc#state-catalogue-finalize[State Catalogue]. Their link states hold no merge lease (it is released before they are entered), offer a way back into the merge path (`retry`, `resume_wait`, `integrate`, `continue_rebase`), the request `abort` (`abort-plan`, except in `finalize.merge-conflict`, which returns through `abort_rebase`), and, where the plan cannot merge (`finalize.merge-refused`, `finalize.merge-queue-exit`, `finalize.merge-gap`), the link `wind_down` (rel `escalate`, `wind-down-unmerged`), whose approval enters the `auto` state `finalize.wind-down` (Rule 10) and whose denial returns to the raising state. A denied gap escalation of `finalize.merge-gap` returns to `finalize.merge-gap` and never aborts the plan.
* *Unified triage exit*: `finalize.triage` offers `triage:<finding_id>` for every open finding and `loop_back`. The triage primitive `findings.triage` decides the exit automatically once the last open finding is triaged: `open_remaining` stays in the state; `triaged_with_fix` (at least one `FIX`) takes the in-branch fix path through `finalize.settle-commit` (a `FIX` that needs cross-task remediation is taken through `loop_back` instead); `triaged_without_fix` enters `finalize.next-step` and completes the three wait-region steps as `done`.
* *Landing delivery failure*: An I/O failure of the `emit-landing` append enters `finalize.emit-landing-failed`. `retry` re-appends and re-verifies the envelope; the approved escalation enters the `auto` state `finalize.retry-landing-delivery`, which repeats the landing delivery once more and continues the pipeline, with `landing_delivery: pending` when that delivery fails again, keeping the envelope in the plan directory for the epic's shipped-without-landing reconciliation. Neither link refuses or strands the merged plan (link:phase-workflows.adoc[Phase Workflows Specification], validator rule 7); a denied escalation leaves the plan in the state, never aborts it.
* *Window-gated re-trigger*: `finalize.review-escalate` offers `retry:<bot_kind>` only while the predicate `review.window-open` holds, so a trigger is never posted inside a closed rate window (a trigger in a closed window extends it; closing and reopening the PR does not reset it). The `<bot_kind>` placeholder expands over the unproven bots of `required_bots ∪ optional_bots` (only the required ones gate; link:phase-workflows.adoc#automatic-review[Phase Workflows Specification, Refusals & Rate Windows] item 9) that have no review evidence for the current `HEAD`, selected after the round's own comment fetch and never by comment recency; a required bot that never published is selectable. A closed window at execution time routes to `finalize.review-window-wait`.
* *Implicit job links*: `finalize.concurrent-wait` is a `composite_job` state and therefore offers `wait:finalize.concurrent-wait` and `cancel:finalize.concurrent-wait` without declaring them (<<implicit-job-links>>). Following `cancel` yields the composite outcome `cancelled`, handled by `finalize.wait-cancelled`.
* *Loop-limit extension*: The approving outcome `extended` of `loop_limit_extension` enters `finalize.allocate-after-extension`, an `auto` state that runs `plan.allocate-remediation-tasks` for the `loop_back` refused at the limit, and never `execute.dispatch-ready` directly, which would dispatch without the fix tasks and envelope the extension granted (Rule 10, <<loop-back-bounds>>). Its outcomes take the same post-allocation path as every `loop_back` link.
* *Escalation outcomes*: Every `escalate` decision kind of the excerpt is registered with its closed outcome set and outcome classes (<<decision-registry>>).
* *Aborted commits*: An `aborted` outcome of `git.commit_and_push` in `finalize.settle-commit` or `finalize.push-barrier` enters `finalize.commit-aborted`, never the plan's abort terminal: `retry` re-enters the calling state (`plan.resume-aborted-call` returns the outcome naming it), and the link `abort` requests `abort-plan`, whose `aborted` outcome enters `plan.aborted` and whose `resumed` outcome returns to the state.
* *Step completion*: The `completes` clauses name the finalize steps each transition settles: `default:push` in `finalize.push-barrier` (`skipped` when the tree was clean, the push was not required, or the remote branch already held `HEAD`, `in_sync`), `default:ci-verify`, `plan-marshall:automatic-review`, and `default:sonar-roundtrip` (the `22..40` wait region entered through `finalize.review-cap-check`) as `done` on `all_green` and on `triaged_without_fix`, as `failed` on every denied or aborted path to `plan.aborted`, and as `skipped_by_operator` on the `approved` outcome of `review_barrier_gap`, `ci_failure_override`, and `wait_cancelled_override` (each step record references the decision; Phase-Exit Completeness accepts it, and the barrier predicates and the `red_ci_gate` check still guard the merge), `default:branch-cleanup` on the denied spend escalation and in `finalize.wind-down` (`failed`), and `default:emit-landing` in `finalize.emit-landing-failed` and `finalize.retry-landing-delivery`. A step begun but not completed when `plan.aborted` is entered through `abort-plan` (for example `default:push` after an aborted commit) is recorded `failed` on entry (Rule 9). A `loop_back` outcome is `UNSETTLED` and completes nothing (<<primitive-outcome-classes>>). What each approval records at `finalize.merge-gate` (a grant of which gap class, or an acknowledgement only) is the grant mapping of the Decision Registry (<<decision-grant-mapping>>).
* *Cross-file targets*: `execute.dispatch-ready` is declared in `execute.pmwf`; the target is valid because all phase files form one definition unit (<<workflow-definition-units>>).

[#guard-results]
==== Three-Valued Guard Results
_Implementation watch: link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-2[PM-WATCH-DSL-2]_

Every guard evaluates to the sealed `GuardResult`: `HELD`, `NOT_HELD`, or `COULD_NOT_EVALUATE(reason)` (a built-in guard whose input cannot be read, a `predicate:` primitive that fails or times out, an unreadable configuration key). A link is offered, and its transition fires, only on `HELD`; `NOT_HELD` omits the link (`PM-WF-3`). `COULD_NOT_EVALUATE` is never folded into either: the engine raises the `guard_indeterminate` condition on the current state (<<condition-overlays>>), naming the guard, the link, and the reason in `facts`, and the undecided link is neither offered nor refused silently. `And`, `Or`, and `Not` propagate `COULD_NOT_EVALUATE` unless the other operand decides the result (`NOT_HELD` and anything is `NOT_HELD`, `HELD` or anything is `HELD`).


[#condition-overlays]
=== Condition Overlays (Engine-Owned)

A condition is an engine-owned overlay on the scope's current state, not a state: `blocked` (an operator decision is pending), `footprint_violation`, `dispatch_incomplete`, `config_drift`, `store_tampered`, and `guard_indeterminate` (link:state-catalogue.adoc#state-catalogue-conditions[State Catalogue, Conditions]). The engine raises it where the condition arises (an `escalate` link without elicitation, the footprint check of `git.stage-and-commit` (<<_six_stage_execution_contract_of_git_commit_and_push>>, Stage 4) or of a task `submit` (<<independent-transition-validation>> item 6), a planning transition guard, a dispatch return, a phase handshake, a locked digest check, a guard that could not be evaluated (<<guard-results>>)) and records it in `mcp/status.json` as `pending_condition` (`kind` from the closed `ConditionKind` enumeration, `decision_id` when an operator decision is pending, `facts`, `raised_at`, link:store-schemas.adoc[Store Schemas Specification]). `state`, `phase`, and `call_stack` are not changed, so a condition raised inside a sub-workflow leaves the scope inside that sub-workflow.

* *Rendering*: While a condition is set, the representation keeps `state` as the current state id, carries the field `condition` naming the kind (link:hypermedia-format.adoc#canonical-top-level-fields[Hypermedia Format Specification]) and the condition's `facts`, and offers only the condition's links (`wait:decision:<decision_id>` for a pending decision; `fix` and `escalate` for a footprint violation; `retry` and `escalate` for an indeterminate guard; the links the condition names otherwise), plus the implicit unrendered `report_bypass`. Every other declared or implicit link of the state is answered with `link_not_available`.
* *Resolution Routing*: A decision resolution is routed like a primitive outcome of the state that raised the condition: for an `escalate` link, the resolution is the `DecisionSpec` outcome of that link and takes its declared outcome transition in the current state's unit (Rule 2 guarantees the bijection), in the same transaction that clears the condition; `call_stack` is untouched, so a resolution inside a sub-workflow stays inside it and only a sub-workflow terminal returns to the caller. A condition raised by the engine rather than a link (a guard, a credential check, a footprint check, a dispatch return, a phase handshake) is cleared by its own resolution (the operator's decision, a `fix` whose next footprint check passes, `resume:<entity>`, `adopt` / `keep`, a `retry` whose re-evaluation of every guard of the state yields `HELD` or `NOT_HELD`) and re-renders the current state with its declared links.
* *Not Declared in DSL Units*: Conditions are never declared in a `*.pmwf` unit and are never a transition target. A DSL transition whose target names a condition or a former engine-implicit state id (`<phase>.blocked`, `<phase>.footprint-violation`, `<phase>.dispatch-incomplete`, `<phase>.config-drift`) fails validation (Rule 3).

[#static-verification-rules]
=== Static AST Verification Rules (Build Time & Every Unit Load)
_See Requirement link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint]_

_See Requirement link:../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../Requirements.adoc#PM-MIG-4[PM-MIG-4: Stage Exit Criteria & Lifecycle Gate]_

_Implementation watch: link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-1[PM-WATCH-DSL-1], link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-3[PM-WATCH-DSL-3], link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-4[PM-WATCH-DSL-4], link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-5[PM-WATCH-DSL-5], link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-8[PM-WATCH-DSL-8], link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-9[PM-WATCH-DSL-9], link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-11[PM-WATCH-DSL-11]_

`WorkflowValidator` verifies every `WorkflowDefinition` in JUnit build tests (the default units) and on every load of a project's units (<<project-owned-units>>), failing closed if any rule is violated; a project unit is additionally checked against the compiled invariants. A `WorkflowDefinition` is always a complete definition unit (<<workflow-definition-units>>): the merged union of all phase files of the plan workflow, a single-file top-level workflow, or one sub-workflow. Rules 2, 3, 5, 8, 9, 10, and 11 run over that union, never over an individual phase file:

1. *Primitive Binding & Parameter Equivalence*: Every `primitiveId` in `do`, `auto`, `job`, `facts`, and `predicate:` must resolve to a registered `Primitive<P, R>`. For every `LinkSpec`, the declared `freeParams` list must exactly match the name, type, and constraints of the `Record` components annotated as `@FreeParam` on `P`. Every `ParamType.SchemaRef` (`schema[<schema_name>]`, in a link's free parameters or a `DecisionSpec.escalateParams`) must name a schema registered in the Named Parameter Schemas (link:hypermedia-format.adoc#named-parameter-schemas[Hypermedia Format Specification]); an unknown schema name fails validation with the source file and line. Every primitive that declares `enqueuesJob()` must declare the outcome `started`, and every `started` transition of such a primitive must target a `job` or `composite_job` state, which binds the returned job id instead of starting a job (<<job-state-binding>>); no other outcome of such a primitive may target a job state.
2. *Exhaustive Outcome Coverage*: For every `auto`, `job`, `composite_job`, and `link` action backed by `Primitive<P, R>`, the set of `OutcomeTransition.outcomeName` entries must form an exact 1-to-1 bijection with the enum constants of `R` (`R.getEnumConstants()`). For `job` and `composite_job` states this includes `cancelled`, the outcome of the implicit `cancel:<job_id>` link (<<implicit-job-links>>). For every `link` whose action is `escalate <decision>`, the decision kind must be registered in the Decision Registry (<<decision-registry>>), and the `OutcomeTransition.outcomeName` entries must form the same exact bijection with the `DecisionSpec.outcomes` of that kind: every declared outcome routed exactly once, no undeclared outcome. An unregistered decision kind, a missing outcome, and an unknown outcome name fail validation with the source file and line number.
3. *Graph Integrity*: State identifiers must be unique across all files of the definition unit. `startState` and every `OutcomeTransition.targetStateId` must exist in the unit's `states` (a cross-file target within the plan workflow is valid; a target inside another unit or inside a sub-workflow is not). Every `StateNode` must be reachable from the unit's `startState`, and reachability is checked for every combination of the values of the configuration keys that the unit's guards declare in `depends_on_config` (every enum value, `true` and `false` for a boolean): a state or outcome transition that no combination reaches fails validation, and one that some combinations do not reach is reported with those combinations. Every non-terminal `StateNode` must have at least one outgoing transition path to a `terminal` state; in a `scope workspace` unit, which declares no terminal state because the workspace scope lives as long as the project's adoption, every state must instead have a path back to the unit's `startState`. Every `skill` clause must resolve to a vocabulary skill in the compiled corpus, and every link identifier pattern must be unique within its state, including the implicit `wait:<job_id>` and `cancel:<job_id>` links of job states. Condition overlays (<<condition-overlays>>) are engine-owned and need no target in `states`: a transition whose target names a condition kind or a former engine-implicit state id (`<phase>.blocked`, `<phase>.footprint-violation`, `<phase>.dispatch-incomplete`, `<phase>.config-drift`) fails validation.
4. *Single-Level Leaf Sub-Agent Constraint (`PM-WF-5`)*: Any `WorkflowDefinition` with `scope == WorkflowScope.ENTITY` (or any state reachable within an entity sub-agent scope) is strictly forbidden from containing a `LinkSpec` with `form == LinkForm.DISPATCH` or `LinkAction.DispatchSubAgent`. Sub-agents are leaves and can never dispatch nested sub-agents.
5. *Backwards-Compatible State Migration (`PM-MIG-4`)*: Every state name present in the committed `released-states.txt` baseline must either exist in `states` or appear as `oldStateId` in a `migrate <old> -> <new>` declaration whose target exists in `states`. The rule applies to the default units; an in-flight plan of a project whose unit dropped or renamed a state stays on its bound unit copy (<<project-owned-units>>, item 4).
6. *Sub-Workflow Outcome Bijection & Parameter Binding (`PM-WF-16`)*: Every `StateBehavior.SubWorkflowCall` (`call <subWorkflowId>`) must reference a registered `WorkflowDefinition` whose `scope == WorkflowScope.SUBWORKFLOW`. Every terminal `StateNode` in a `SUBWORKFLOW` declares its `terminalOutcome` (`state <id> terminal <outcome_id> <outcome_class>`, which the grammar requires of every terminal state), and the set of `OutcomeTransition.outcomeName` entries on each `call` site must form an exact 1-to-1 bijection with the target sub-workflow's declared `terminalOutcome` values. The `paramBindings` of every `call` site are checked against the target's `params` (`param` declarations): every declared parameter must be bound exactly once, no binding may name an undeclared parameter, and every bound value must match the declared type (membership in the `enum[…]` value set, or an integer within the declared `int` range). `phase inherit` is admitted only in a `SUBWORKFLOW` unit. A `call` site's transition for a terminal outcome of class `aborted` must target a `link` state of the caller's unit (a decision state, or a state offering the escalation that ends the scope), never a terminal state and never a state that continues the flow.
7. *Acyclic Call-Graph DAG & Bounded Depth (`PM-WF-16`)*: Across all registered `WorkflowDefinition` instances, the static `call` graph must form a strict directed acyclic graph (DAG) with zero cycles and a maximum static call-stack depth $\le 4$.
8. *Gate Artifact Producer Coverage*: For every guard or gating primitive that declares a required artifact (`requiredArtifacts()`, for example `pr_title`, `outline.md`, or `execution-manifest.json`), every path from the unit's `startState` to that guard or state, including recipe and lane shortcuts, must pass a state whose primitive declares the artifact in `producedArtifacts()`. A path without a producer fails validation, so a gate can never refuse for an artifact its lane could not produce.
9. *Step Completion Exactly Once & Failure Outcomes Never Map to Success*: Every outcome constant of every primitive and `composite_job` outcome set declares an `OutcomeClass` (<<primitive-outcome-classes>>), and every terminal state declares its class in `terminal <outcome_id> <outcome_class>`; a sub-workflow's terminal class is the class of the matching outcome at its `call` sites. A step is completed only by a `completes <step_id> as done|skipped|failed|skipped_by_operator` clause (<<_formal_ebnf_grammar_for_the_workflow_dsl>>). The rule checks:
** *Exactly once*: Every finalize step named by a `completes` clause is completed exactly once on every path from the state that begins it (the state `finalize.next-step` selects for it, or the region entry state for steps that share one, such as `finalize.review-cap-check` for the `22..40` wait region) to the state of order `70` (`finalize.merge-gate`) or to a terminal state. A path ends early at an `UNSETTLED` outcome (`loop_back`, defer) or an `ABORTED` outcome (a sub-workflow returning `aborted`), which hands the step back without a completion. Entering `plan.aborted` or `epic.aborted` records every begun step that no transition on the path completed as `failed`, in the transaction of the entering transition; a path into the abort terminal therefore needs no `completes` clause for such a step, and a clause it does carry is that step's single completion. No completion on a path, or two, fails validation.
** *Class admits the completion*: `as done` is admitted only on an outcome of class `SUCCESS` or a decision outcome of class `APPROVED` (an operator-authorized completion, for example the `automatic-review` force-done); `as skipped` only on `SUCCESS` or `SKIP`; `as skipped_by_operator` only on a decision outcome of class `APPROVED` (the operator settles a step whose evidence is missing or failed, for example the wait-region steps under an approved `review_barrier_gap`, `ci_failure_override`, or `wait_cancelled_override`), never on a primitive outcome. A `FAILURE`, `INDETERMINATE`, or `ABORTED` outcome never completes a step `done`, and a composite primitive whose sub-operations report any `FAILURE` outcome yields a `FAILURE` outcome itself.
** *Denied and aborted paths*: Every outcome of every registered `DecisionSpec` declares exactly one `DecisionOutcomeClass` (<<decision-registry>>). No transition on a path that follows a `DENIED` or `ABORTED` outcome completes a step `done` or `skipped_by_operator`, and such an outcome never enters a state running the decision's approved-action primitive; an `ABORTED` outcome must target the unit's `aborted` terminal state.
10. *Approving Decision Outcomes Execute the Approved Action*: Every `escalate` outcome of class `APPROVED` must target an `auto` state whose primitive is the one the `DecisionSpec` names for that outcome in `approvedActions`, so the approved action is performed in the transaction that applies the resolution. It must never target a terminal state, a sub-workflow terminal (`done`/`completed`) state, or a state that merely continues the flow without executing the action (a step selector, a dispatch or wait state, or a `link` state). An `APPROVED` outcome without an `approvedActions` entry fails validation. Example: `loop_limit_extension` `extended -> finalize.allocate-after-extension` (`auto plan.allocate-remediation-tasks`), never `extended -> execute.dispatch-ready`.
11. *No Self-Loop or Cycle Without an Awaited Event*: Every primitive declares the external event it waits for (`Primitive.awaitedEvent()`, <<_primitive_spi_contract>>). A self-loop (an outcome transition that targets its own state) or a cycle of transitions fails validation when every primitive executed on it (`do`, `auto`, `job`, and `composite_job` primitives, including those of a sub-workflow called on the cycle) declares `NONE`: such a loop re-runs without any event that could change its outcome. A cycle passes when at least one of its primitives awaits `JOB_SETTLED`, `OPERATOR_DECISION`, `MODEL_SUBMIT`, `HEAD_CHANGE`, or `TIME`.
12. *Link Relation & Form Compatibility*: For every `LinkSpec`, the form (the declared `[form]`, or `LinkRelation.defaultForm()` when it is omitted) must be one of `rel.allowedForms()` (<<_ast_node_model>>, link:hypermedia-format.adoc#_closed_link_relations_rel[Hypermedia Format Specification, Closed Link Relations]). The form must also fit the link: `submit` declares a non-empty parameter list; `noop`, `wait`, and `dispatch` declare none; `escalate` declares the action `escalate <decision>`, and that action is admitted only with the form `escalate`; its free parameters must equal the parameter schema its decision kind declares in the Decision Registry (possibly empty); the action `dispatch <entity_kind> role <role_key>` is admitted only with the form `dispatch`. A violation fails validation with the source file and line.

[#project-owned-units]
=== Project-Owned Workflow Units & Compiled Invariants
_See Requirement link:../Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

_See Requirement link:../Requirements.adoc#PM-EXT-7[PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades]_

The process a project runs is visible to and owned by its team: the units that define it are files in the repository, reviewed like code. The guarantees of the process stay server-enforced, because every unit is verified on every load against rules and invariants compiled into the binary, and a unit can only compose compiled primitives and enrolled scripts.

1. *Which Units Are Project-Owned*: Every phase file of the plan workflow (`init.pmwf`, `refine.pmwf`, `outline.pmwf`, `plan.pmwf`, `execute.pmwf`, `land.pmwf`, `finalize.pmwf`) and every sub-workflow unit (`scope subworkflow`, for example `git-commit-and-push.pmwf`) lives in the project as `.marshall/config/<file>.pmwf` (git-tracked, owner class *team*, link:store-schemas.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]). The binary ships the *default* units (`classpath:/workflows/`); `setup.prepare-workspace` copies them on the project's first run, each copy carrying `derived_from <n>` (the default revision it was copied from) in its header. The workspace unit `project-setup.pmwf` and the epic unit `epic.pmwf` are compiled only and never project-owned; they call the binary's default sub-workflows, never the project's copies, so a failing project unit never blocks the setup workflow that repairs it or the epic ledger.
2. *Load & Verification*: Every computation of the effective configuration (`pm_start`, every phase handshake, `pm-mcp enter`, `setup.reconcile-config`; cached by the units' digests) parses the project's units, merges the plan workflow unit (<<workflow-definition-units>>), and verifies it with Rules 1–12 (<<static-verification-rules>>; Rule 5 only for default units), with `FinalizePipelineValidator` over the project's finalize roster (link:phase-workflows.adoc#_build_time_startup_static_invariant_verification_finalizepipelinevalidator[Phase Workflows Specification]), and with the compiled invariants (item 5). A unit at another DSL `format` is refused with `format_outdated` or `format_newer` naming the file. A missing, unparsable, or violating unit is never replaced by the default unit (no silent fallback): it is a verification finding in the workspace scope naming the file, the line, and the violated rule or invariant, and it refuses the project's plan lifecycle (`pm_start` and every phase handshake refuse with `config_invalid` naming the file and line) until the unit verifies. The verification outcome of every unit is published in `pm://project/config` (`units[]`).
3. *Project Steps Bind to Enrolled Scripts*: A unit never introduces executable code: every primitive it names must be registered in the binary (Rule 1). A project finalize step is a state running the compiled primitive `project.run-step` for its step id; it exists only when three owners agree: the unit contains the step, `workflow.json` `plan.phase-6-finalize.project_steps` declares its descriptor (`order`, `lane`, `project_script_id`), and the operator's enrolment binds the `project_script` with `worker_kind: finalize_step` and `target` equal to the step id (link:domain-extensions.adoc#_out_of_process_project_script_jobs_project_script_domain_workers[Domain Extensions Specification, `project_script`]). A disagreement is the verification finding `project_step_unbound`.
4. *Bound Unit Copy per Plan*: At `pm_start` the engine binds the verified unit sources to the plan (a copy in the plan's metadata directory, digest-recorded, part of `config_hash`); a plan always executes its bound copy. A changed project unit raises `config_drift` at the next phase handshake (link:domain-extensions.adoc#config-snapshot[Domain Extensions Specification, Three-Surface Synchronization]); `adopt` replaces the bound copy only when the new unit verifies and still contains the plan's current state and every state of its `call_stack`, otherwise only `keep` is offered.
5. *Compiled Invariants*: The following invariants are compiled into the binary; no configuration key and no unit edit can switch one off, and every one of them is checked over the merged project unit on every load (`INV-*` identifiers name the invariant in findings):

== Typed Java `Primitive<P, R>` Interface & Transition Validation
_See Requirement link:../Requirements.adoc#PM-WF-6[PM-WF-6: Independent Server-Side Transition & Parameter Validation]_

=== `Primitive<P, R>` SPI Contract

Every deterministic server operation is encapsulated as a stateless Java `Primitive<P, R>` in `pm-mcp-core`:

[source,java]
----
package de.cuioss.pm.mcp.core.workflow.spi;

import java.util.Map;
import java.util.Optional;
import java.util.Set;

public enum OutcomeClass { SUCCESS, SKIP, FAILURE, INDETERMINATE, UNSETTLED, ABORTED }

/** The external event a primitive waits for before its outcome can change (Rule 11). */
public enum AwaitedEvent { NONE, JOB_SETTLED, OPERATOR_DECISION, MODEL_SUBMIT, HEAD_CHANGE, TIME }

public interface PrimitiveOutcome {
    String wireName();

    /**
     * Class of the outcome; decides which step record the engine writes (see Outcome Classes).
     */
    OutcomeClass outcomeClass();
}

public record PrimitiveResult<R extends Enum<R> & PrimitiveOutcome>(
    R outcome,
    Map<String, Object> updatedFacts,
    Optional<String> spawnedJobId
) {}

public interface Primitive<P extends Record, R extends Enum<R> & PrimitiveOutcome> {

    /**
     * Canonical dotted primitive identifier (e.g., "git.stage-and-commit", "git.push", "findings.triage").
     */
    String id();

    /**
     * Record class defining the free and state-resolved parameters.
     */
    Class<P> parameterType();

    /**
     * Closed enum class of all possible deterministic outcomes.
     */
    Class<R> outcomeType();

    /**
     * Execute the operation within the locked scope context and return one of the closed outcomes.
     */
    PrimitiveResult<R> execute(WorkflowExecutionContext context, P parameters);

    /**
     * Artifacts this primitive produces as side effects (Rule 8), e.g. "pr_title".
     */
    default Set<String> producedArtifacts() { return Set.of(); }

    /**
     * Artifacts this primitive requires before it can pass (Rule 8), e.g. a gate requiring "pr_title".
     */
    default Set<String> requiredArtifacts() { return Set.of(); }

    /**
     * External event this primitive waits for (Rule 11); NONE for a primitive whose outcome
     * depends only on state it reads in the same transaction.
     */
    AwaitedEvent awaitedEvent();

    /**
     * True for a primitive that enqueues a job for the following job state and returns its id
     * in PrimitiveResult.spawnedJobId with the outcome "started" (Rule 1, Job State Entry & Binding).
     */
    default boolean enqueuesJob() { return false; }
}

[#primitive-outcome-classes]
==== Outcome Classes & Step Records
_Implementation watch: link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-9[PM-WATCH-DSL-9]_

Every outcome constant declares one `OutcomeClass`, and the engine derives the step record from it, never from the outcome name:

* *`SUCCESS`*: The step completed with its work; the engine records `done`.
* *`SKIP`*: The step had nothing to do. A primitive with an optional input declares a `skipped_<reason>` outcome of this class for the absent-input case; the step record stores `skipped`, `work_performed: false`, and the reason, and downstream steps treat it as neither a failure nor produced content.
* *`FAILURE`* and *`INDETERMINATE`*: The step record stores `failed` or `indeterminate`; neither is ever recorded as `done`, and `INDETERMINATE` is never folded into success or failure (`PM-EXEC-4`).
* *`UNSETTLED`*: Outcomes that hand the step back without settling it (`loop_back`, defer). The engine writes no completion record, so a re-fired step never produces two completions.
* *`ABORTED`*: A flow was left by a model-followed `abort` link or a denied escalation inside it (the sub-workflow terminal `git.done-aborted`, outcome `aborted`). Like `UNSETTLED` it writes no completion record: the caller routes the outcome back to a decision state or to an escalation (<<_formal_ebnf_grammar_for_the_workflow_dsl>>, Abort model), never to a state that continues the flow as if the operation had succeeded, and never completes a step `done` or `skipped` on it.

[#independent-transition-validation]
=== Independent Server-Side Transition & Parameter Validation (`PM-WF-6`)

[[_independent_server_side_transition_parameter_validation_pm_wf_6]]
When `pm_do(scope_id, link, args, dispatch_id)` arrives, the workflow engine executes a single atomic transaction under the scope's exclusive lock (acquired through the lock manager in the total lock order, link:store-schemas.adoc#lock-free-snapshot-reads[Store Schemas Specification]); all of its store writes form one journaled transaction (link:store-schemas.adoc#transaction-journal[Store Schemas Specification, Transaction Journal]):

1. *Load Authoritative State*: Read `mcp/status.json` for `scope_id` (applying any `migrate` mapping if `status.json` references a legacy state) and resolve the active `StateNode` (within the top `CallFrame.subWorkflowId()` if `call_stack` is non-empty, or the root workflow otherwise).
2. *Verify Dispatch Claim (if `dispatch_id` present)*: If `dispatch_id` is superseded (a `dispatch_id` has no time-based expiry), reject immediately with `reason: "stale_dispatch_id"`.
3. *Re-Compute Active Links & Guards*: Evaluate all `LinkSpec` entries on `StateNode`, expanding entity placeholders (`triage:<finding_id>`) against current persisted stores (`findings.jsonl`, `tasks/TASK-*.json`) and evaluating each link's `GuardExpr` to a `GuardResult` (<<guard-results>>): only `HELD` links are active, and a `COULD_NOT_EVALUATE` result raises the `guard_indeterminate` condition instead of dropping the link. While `pending_condition` is set, the active set is only the condition's links (<<condition-overlays>>).
4. *Verify Link Offering*: Confirm that `link` exactly matches one of the currently active, guard-satisfied `LinkSpec` instances. If `link` is not in the active set, return `isError: false` with the current representation and a `rejected.reason` from the closed enumeration (link:mcp-tools.adoc#rejection-reasons[MCP Tool & Resource Surface Specification]): `operator_only` for an operator transition, which is never offered to the model; `stale_entity` for an entity-addressed link whose entity is no longer in an accepting state; `link_not_available` for any other identifier, including invented or paraphrased ones.
5. *Validate & Bind Free Parameters (`P`)*: Validate the raw `args` map against the `LinkSpec.freeParams` constraints (`additionalProperties: false`, required keys, enum membership, string length bounds, integer ranges) and execute any attached content validator (`OutlineValidator`, `AsciiDocValidator`, `ConventionalCommitValidator`) in-process on submitted text payloads. If validation fails, return `isError: false` with the current representation and `rejected.reason` `undeclared_param` (a key the link does not declare), `missing_param` (a required key is absent), or `invalid_link_args` (type, range, or content-validator violation); `detail` names the offending parameter.
6. *Verify Task Footprint (`submit:TASK-*` only)*: For a task `submit:<task_id>` link, verify the task's contribution: that no files outside the plan's worktree were dirtied by host tools and that no enrolled wrapper's `pinned_files` (link:job-runtime.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Verify-Not-Resolve]) changed inside it; on violation, the link's primitive is not executed and the `footprint_violation` condition is raised on the current state (<<condition-overlays>>), naming the offending files; `state` and `call_stack` are unchanged. Commits are not checked here: every commit, whatever its caller and whichever link or state leads to it, is guarded by the footprint check that `git.stage-and-commit` runs as its first step (<<_six_stage_execution_contract_of_git_commit_and_push>>, Stage 4).
7. *Execute Primitive & Advance State*: Instantiate `P`, invoke `primitive.execute(context, params)`, look up the returned `R.wireName()` in `LinkSpec.transitions`, persist the new `state` (and updated `call_stack` if entering or exiting a `SubWorkflowCall`) in `mcp/status.json`, append the transition event to `audit.jsonl`, and render the next state's TOON representation (executing chained `auto` and `call` steps until an interactive link state, async job state, or root terminal state is reached).

== Reusable Compound Sub-Workflows & Call-Stack Execution (`PM-WF-16`)
_See Requirement link:../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

Workflows are composed not only of atomic `do` / `auto` / `job` primitives, but also of reusable, config-aware *compound sub-workflows* (`scope subworkflow`). A compound sub-workflow encapsulates a multi-state sub-process—combining deterministic `auto` checks, configuration lookups, conditional interactive pauses, and recovery branches—so that Phase 5 (`execute`), Phase 6 (`finalize`), `marshall-steward`, and `plan-orchestrator` invoke the exact same state machine rather than duplicating states or collapsing interactive recovery into opaque Java code.

=== Call-Stack Execution & Persistence Semantics

1. *Sub-Workflow Invocation (`call`)*: When the engine transitions into a `StateNode` whose behavior is `StateBehavior.SubWorkflowCall(subWorkflowId, paramBindings, transitions)`, it pushes a `CallFrame(callerWorkflowId, callerStateId, callerPhase, subWorkflowId, paramBindings, Instant.now().toString())` onto the `call_stack` array in `mcp/status.json` and sets `status.state` to the target sub-workflow's `startState` while preserving `status.phase = callerPhase` whenever a sub-workflow state declares `phase inherit` (the caller state's resolved phase value; <<_formal_ebnf_grammar_for_the_workflow_dsl>>). `callerWorkflowId` is the id of the caller's definition unit, `plan` for every state of the merged plan workflow (<<workflow-definition-units>>). Preserving `callerPhase` guarantees that phase-scoped guards (such as `in_worktree`), phase metric accounting (`metrics.json`), and terminal-title updates remain invariant regardless of which caller invoked the sub-workflow.
2. *Interactive Pauses & Job Waits Inside a Sub-Workflow*: If execution inside the sub-workflow reaches an `AutoStep`, the engine executes it immediately in the same turn. If execution reaches an `InteractiveLinks` state (such as `git.artifact-review`, `git.compose-message`, `git.commit-fix`, or `git.sync-required`) or a `JobStep`, the engine persists `mcp/status.json` (with the active `call_stack` and sub-workflow `state`) and returns that state's TOON representation to the caller. Subsequent `pm_do` or `pm_state` calls resolve against the active sub-workflow state at the top of `call_stack`, surviving context compactions and daemon restarts identically to top-level states.
3. *Sub-Workflow Return (`terminal <outcome_id> <outcome_class>`)*: When a transition inside the sub-workflow lands on a `StateNode` whose `terminalOutcome` is present with the id `outcomeId`, the engine pops the top `CallFrame` from `call_stack`, looks up `outcomeId` in the caller state's `OutcomeTransition` table, transitions `status.state` to `targetStateId` in `callerWorkflowId`, and continues auto-chaining in the same atomic transaction.

=== Canonical Reusable Sub-Workflow: `git.commit_and_push` (`git-commit-and-push.pmwf`)

The `git.commit_and_push` sub-workflow models the complete git commit-and-push sub-process grounded in `workflow-integration-git`, `phase-5-execute` (Step 10a), and `phase-6-finalize` (Step 3 item 5f, `standards/push.md`, and post-PR re-push). The unit and its states stay in `pm-mcp-core`; the git operations its primitives invoke are contracts of the provider module `pm-mcp-git` (<<_module_boundary_decoupled_core_architecture>>).

==== Bound Parameter Contract

The sub-workflow header declares both parameters with `param` (see the DSL definition below); every `call git.commit_and_push (…)` site must bind both exactly once with a declared value (Rule 6 in <<static-verification-rules>>).

[cols="1,2,3"]
|===
|Parameter |Allowed Values |Semantics

|`message_mode`
|`auto_deliverable` \| `step_or_fallback` \| `interactive` \| `none_assert_clean`
|Controls commit message sourcing: `auto_deliverable` formats `feat(<module>): complete deliverable <N> - <title>` from the active deliverable (*a `PM-MCP` choice*: `plan-marshall`'s `phase-5-execute` Step 10a derives the commit message from the task title instead); `step_or_fallback` uses a step-supplied commit message or `chore(finalize): apply <step_id> changes`; `interactive` pauses in `git.compose-message` with diff analysis facts for model submission; `none_assert_clean` expects a clean working tree (used by `finalize.push-barrier`) and routes any unexpected dirty files through `git.compose-message` before pushing.

|`push_mode`
|`never` \| `if_push_remote` \| `always` \| `post_pr_conditional`
|Controls push execution after commit (or on a clean tree): `never` stops after local commit; `if_push_remote` pushes when the project has a push remote (derived fact `push_remote`, link:store-schemas.adoc#derived-facts[Store Schemas Specification, Derived Facts Store]; a `stale` or `failed` fact is `indeterminate`, never "no remote"); `always` pushes unconditionally; `post_pr_conditional` pushes if and only if the caller step has `order > 20` (post-`create-pr`) and a push remote exists. No configuration key suppresses a push (`plan-marshall`'s `commit_and_push` does not exist).
|===

NOTE: The sub-workflow has three operator escalations, each of whose `approved` outcome enters an `auto` state performing the approved action (Rule 10, <<static-verification-rules>>; <<decision-registry>>): `gitignore_oracle_failure` enters `git.stage-under-oracle-override`, `force_stale_push` enters `git.push-under-freshness-override`, and `force_push_with_lease` enters `git.push-with-lease`, which executes the forced push. A repository hook failure is never bypassed: `git.commit-fix` offers `retry`, `recompose`, and `abort`, and `git.retry-commit` returns `attempts_exhausted` after `3` failed commit attempts on an identical staged change set (the staged tree id and the message; compiled constant, link:timeouts.adoc[Timeouts & Budgets Specification]); the counter resets when the staged tree or the message changes (a fix, a hook that rewrote files, a `recompose`). Hooks run only in the CLI variant, so only that variant reaches `git.commit-fix`. `attempts_exhausted` enters `git.done-aborted`, whose `aborted` the caller routes to its `<phase>.commit-aborted`. The three push states `git.execute-push`, `git.push-under-freshness-override`, and `git.push-with-lease` route the outcome set of `git.push` uniformly: `pushed_with_commit` -> `git.done-committed-and-pushed`, `pushed_clean_tree` -> `git.done-pushed-clean`, `up_to_date` -> `git.done-in-sync`, `rejected_non_ff` and `rejected_lease` -> `git.sync-required`. A rebase conflict is model work: `git.resolve-conflicts` offers `continue_rebase` (the model has resolved the conflicted files in the checkout) and `abort_rebase`, which restores the pre-rebase branch and enters `git.sync-escalate` (`retry` the sync, or `abort`, whose `aborted` outcome lets the caller offer `abort-plan`).

`git.done-in-sync` (outcome `in_sync`, class `skip`) is returned when nothing was pushed because the remote branch already holds the local `HEAD` (the parity decision `skip`, or a push answered `up_to_date`); `pushed_clean` is returned only after an executed push of a clean tree. Every caller routes `in_sync` like `pushed_clean`.

`git.done-aborted` (outcome `aborted`, class `aborted`) only leaves the sub-workflow: it is entered by the model-followed `abort` links of `git.artifact-review`, `git.compose-message`, `git.commit-fix`, and `git.sync-escalate`, by exhausted commit attempts, and by the denied escalations, and never ends the plan, the epic, or the workspace run. The caller routes the returned `aborted` to one of its own `link` states (Rule 6): `execute.commit-aborted` and `finalize.commit-aborted` (retry the commit, or request `abort-plan`), `setup.commit-changes`, and `epic.active` (link:state-catalogue.adoc#state-git.done-aborted[State Catalogue]).

==== Six-Stage Execution Contract of `git.commit_and_push`
_Implementation watch: link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-6[PM-WATCH-DSL-6], link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-7[PM-WATCH-DSL-7], link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-10[PM-WATCH-DSL-10], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-9[PM-WATCH-STORE-9], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-73[PM-WATCH-PHASE-73], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-74[PM-WATCH-PHASE-74]_

* *Stage 1 — Working-Tree Inspection (`git.inspect-worktree`)*:
** Resolves the target checkout path from the locked scope context: `worktree_path` of a plan while it is set, the main checkout (the enrolled `project_root`) for a plan whose `worktree_path` is `null` and for `workspace`, and the shared epic worktree (link:filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification]) when `epic`. Git-tracked orchestrator state is never committed on the primary checkout (`PM-ARCH-5`).
** Executes `git -C <tree> status --porcelain` (ignoring `.marshall/local/**`).
** If uncommitted changes exist (`staged`, `unstaged`, or `untracked`), returns `dirty -> git.detect-artifacts`.
** If the working tree is clean: returns `clean_skip_push -> git.done-clean` when `push_mode == never`; otherwise returns `clean_needs_push_check -> git.evaluate-push-policy` so clean-tree push barriers (`finalize.push-barrier` or post-rebase pushes) proceed directly to the freshness and parity checks without creating an empty commit.
* *Stage 2 — `.gitignore`-Aware Artifact Detection & Cleanup (`git.detect-artifacts`)*:
** Scans the working tree against `artifact-patterns.json` (`*.temp`, `*.backup*`, `*.orig`, `*.swp`, `.DS_Store`, `Thumbs.db`, coverage/build scratch files) while querying `git -C <tree> check-ignore`.
** Fails closed (`oracle_failed -> git.artifact-escalate`) if the `.gitignore` oracle cannot be evaluated. The operator's approval of `gitignore_oracle_failure` enters `git.stage-under-oracle-override`, whose primitive `git.apply-oracle-override` records an override bound to the current `HEAD` that names the paths the oracle could not classify; the next `git.stage-and-commit` of the same call stages those paths under the override and records it in the commit's audit record, and the override lapses with that commit or when `HEAD` moves.
** Unconditionally excludes `.marshall/**` and any nested git worktrees or submodules (`git submodule status` / `.git` file markers) from deletion.
** Automatically deletes `safe` untracked artifact files and records `artifacts_deleted` in the audit log.
** Transitions to `git.artifact-review` only for paths in the change set of this commit (porcelain entries: staged, unstaged, untracked) that match artifact patterns and are `uncertain`, or for prohibited secret files (`.env*`, `*.pem`, `*.key`, `credentials.json`) in that change set. Unchanged tracked files are never candidates; unchanged tracked files that match artifact patterns are recorded only as a count (`tracked_pattern_matches`) in the audit record, never rendered, since no link acts on them.
* *Stage 3 — In-Memory Commit Message Resolution, Validation & Trailer Injection (`git.resolve-message` / `git.compose-message`)*:
** When `message_mode` is `auto_deliverable` or `step_or_fallback`, resolves the deterministic commit message in memory (e.g., `feat(<module>): complete deliverable <N> - <title>` or `chore(finalize): apply <step_id> changes`).
** When `message_mode == interactive` (or `none_assert_clean` when unexpected dirty files were found), transitions to `git.compose-message`, populates `facts` via `git.diff-summary` (changed file count, module scope, priority-ordered suggested type `fix > feat > perf > refactor > docs > style > test > chore > ci`), and accepts `message: text[1..2000]` directly in `pm_do` `args`.
** Validates Conventional Commits format (`<type>[optional (<scope>)][!]: <subject>`) via `ConventionalCommitValidator` and deterministically appends the configured trailer `Co-Authored-By: {name} <{email}>`, resolved as in `plan-marshall` (`manage-run-config` `commit-trailer get`) from the operator's `commit_trailer{name,email}` in the machine-local `<PM_MCP_BASE>/projects/<project_id>/local-config.json`, falling back to `machine-config.json` `project_defaults.commit_trailer` and then to the compiled default `plan-marshall <noreply@cuioss.de>` (link:store-schemas.adoc#local-config[Store Schemas Specification, Operator Local Configuration]); the schema refuses an empty value or one containing an angle bracket or line break. No team file is ever consulted for the trailer.
** The trailer names the system that produced the commit; it is independent of the commit's author and committer (Stage 4), which are never taken from the message.
** The resolved trailer is the only authority: a `Co-Authored-By:` line in a model-supplied `message` is rejected (`invalid_link_args`, `detail` names the line), and the only trailer in the commit is the one the server appends. The commit's audit record carries `trailer_source: {name, email}`, each half `configured`, `default`, or `invalid_ignored` (a stored value that was treated as absent); it is provenance for the operator and is never rendered in `facts`.
* *Stage 4 — Staging, `stdin`-Piped Commit & Change-Ledger Stamping (`git.stage-and-commit`)*:
** *Footprint check first*: Before anything is staged, the primitive runs the footprint check for every caller (plan, epic, and workspace scope; <<_call_site_reuse_matrix_across_workflows>>): (1) the worktree boundary: no dirty path of the target checkout lies outside the staging set derived below, and for a plan no file outside its worktree was dirtied; (2) the pinned build files: no enrolled wrapper's `pinned_files` (link:job-runtime.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Verify-Not-Resolve]) changed in the target checkout; (3) the main checkout: for a plan scope, no main-checkout path outside `.marshall/local/` is absent from `entry_baseline` or changed since it (`mcp/status.json`, link:store-schemas.adoc[Store Schemas Specification]); for a `local_changes` plan this is the `entry_baseline` re-recorded by `land.worktree-init` after the capture restored the main checkout's captured paths, so the captured changes and their restoration never count as a violation (link:phase-workflows.adoc#_plan_source_contracts[Phase Workflows Specification, Plan Source Contracts]). A violation raises the `footprint_violation` condition on the current state (the sub-workflow state `git.stage-and-commit`, <<condition-overlays>>) naming the offending files, and no commit is made; the condition's `fix` re-runs the check. The check is part of the primitive, not of a link, so no caller can reach a commit around it.
** Derives the staging set from the plan, never from whatever the working tree holds: the dirty paths intersected with the declared footprint, the accepted deviations, the task `target_files`, and the step-declared outputs (for epic scopes, `.marshall/orchestrator/**`; for the workspace scope, the setup call's set `.marshall/config/**`, `.gitignore`, and `.marshall/project-architecture/**`). A dirty path outside that set is never staged.
** Stages the scoped files (`git -C <tree> add -- <paths>`) and invokes `git -C <tree> commit -F -`, streaming the validated UTF-8 commit message + trailer directly to child `stdin` in memory (`PM-EXEC-5`) with zero `.plan/temp/` files.
** *Author and committer*: The commit's author is the operator: `commit_identity{name, email}` of the operator's `local-config.json` (link:store-schemas.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), captured in project setup. The committer is the agent identity resolved from the provider credential (the derived fact `agent_identity`: for a GitHub App its `<app-slug>[bot]` noreply address, for a token the token's user); without a resolvable agent identity it is the compiled identity `plan-marshall-mcp <noreply@cuioss.de>`. Both variants produce identical metadata: the native variant sets author and committer on the commit object, the CLI variant passes the author as `-c user.name=… -c user.email=…` and the committer through `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL`. The operator's own git `user.*` configuration is never read at commit time. Author and committer are recorded in the commit's audit record and never rendered in `facts` (link:hypermedia-format.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
** Captures `commit_sha` (`git -C <tree> rev-parse HEAD`) and git-sourced `changed_paths` (`git -C <tree> diff-tree --no-commit-id --name-only -r <commit_sha>`), appending a `kind = "change"` entry to `change-ledger.jsonl`.
** When invoked from a Phase 6 `mutates_source: true` step: re-stamps `head_at_completion = commit_sha` on `head_dependent: true` steps in `mcp/status.json`, and when the commit follows the latest successful build (any such step, not only steps at `order >= 10`, `pre-push-quality-gate.order`; for example `architecture-refresh` at `9` on re-entry; link:phase-workflows.adoc#_finalize_commit_instrumentation_freshness_reconcile_post_pr_re_push_pm_wf_16[Phase Workflows Specification, Finalize Commit Instrumentation] item 3), writes a `freshness_reconcile` record (`commit_sha`, `step_id`, `prior_build_worktree_sha` from the latest passing build row in `change-ledger.jsonl`) so the downstream push gate recognizes the finalize-internal commit without requiring a redundant full build when no source-affecting inputs changed.
** If `git commit` exits non-zero due to a repository pre-commit hook, returns `hook_failed -> git.commit-fix`.
* *Stage 5 — Config-Driven Push Policy & Freshness Precondition (`git.evaluate-push-policy` -> `git.verify-freshness`)*:
** Evaluates `push_mode` together with the derived fact `push_remote`: `push_mode == never` skips push (`skip_push_committed -> git.done-committed-local`); `push_mode == if_push_remote` requires push if and only if a push remote exists; `push_mode == post_pr_conditional` requires push if and only if a push remote exists and the calling finalize step has `order > 20` (after `create-pr`), automating post-PR re-push for late source-mutating steps (`adr-propose` or triage fixes); `push_mode == always` requires push unconditionally.
** Before any push, `git.pre-commit-verify-freshness` verifies `change-ledger.jsonl` freshness (`fresh` corroborated on both notation and scope dimensions against the current `worktree_sha`, `exempt` when `build-decision == not_necessary`, or reconciled via `freshness_reconcile`). If `stale` or `undecidable`, transitions to `git.freshness-blocked` (offering `run_verification_build` or operator `escalate`). The approval of `force_stale_push` enters `git.push-under-freshness-override`, which runs `git.push` under an override record bound to the current `HEAD` and to the rendered `stale_reason`; the override is recorded in the audit record and lapses when `HEAD` moves.
** When no reconciliation record names the live `HEAD`, `git.freshness-status` reports `stale_reason: reconciliation_record_absent` together with the causes that absence admits (`admitted_causes` ⊆ `source_drift_unbuilt`, `no_successful_build`, `record_owed_not_emitted`, `commit_outside_reconcile_membership`). The refusal reports what it observed and never asserts a single inferred cause; the fail-closed halt is unchanged.
** `git.freshness-blocked` renders, beside `stale_reason`, the evidence it would accept: the required build notation(s) and the scope (`whole_tree` or a module list); the current `worktree_sha` is recorded in the audit record, not rendered.
* *Stage 6 — Branch Sync Parity Probe & Push Execution (`git.check-branch-parity` -> `git.execute-push`)*:
** `git.push-barrier-decision` first reads the persisted fact `branch_pushed_at` in `mcp/status.json`. When it is unset, the branch has never been pushed by this plan and the decision is `first_push` (`git -C <tree> push --set-upstream origin <branch>`) without consulting the probe. When it is set (re-entry), the decision follows `plan-marshall`'s push-barrier mapping (`workflow-integration-git/scripts/git-workflow.py`, `push_barrier_action`, verified at commit `1d4a1da37`; re-verify before implementing): it runs `git.branch-sync-state` and returns `refire` only for `ahead`; `synced`, `remote_absent_landed`, `remote_absent_unverified`, and any unrecognised state return `skip`, which ends the call with `in_sync` (`git.done-in-sync`). A never-pushed branch and a squash-merged-and-deleted branch are indistinguishable locally, so `remote_absent_unverified` is resolved with provider evidence before it is classified: `ci.pr-find` by the head branch finding a merged pull request turns it into `remote_absent_landed` (`skip`, re-pushing would resurrect a landed branch); finding no pull request at all turns it into `never_pushed`, which pushes (`refire`); any other observation (an open or closed-unmerged pull request, or a provider that cannot be observed) keeps `remote_absent_unverified`, which never pushes. *Deliberate change vs. `plan-marshall`*: `plan-marshall` never pushes on `remote_absent_unverified` and consults no provider evidence.
** `git.branch-sync-state` classifies the plan's recorded `branch_name` (`mcp/status.json`), never the ambient `HEAD` of the checkout, and fetches the remote ref before classifying. A classification made without a fetch in the same transaction is labelled unverified (as `remote_absent_unverified` already is) and is never used to claim that the branch is unpushed.
** `git.execute-push` sets `branch_pushed_at` (timestamp and pushed `HEAD`) in `mcp/status.json` on the first successful push and refreshes it on every later successful push, so it always names the last pushed commit. A push answered `up_to_date` pushed nothing and returns `in_sync`.
** If `git push` is rejected as non-fast-forward (`rejected_non_ff{remote_sha}`), transitions to `git.sync-required` (offering `sync_rebase` or operator `force_push_with_lease` escalation). `sync_rebase` rebases onto the fetched upstream; a conflict enters `git.resolve-conflicts` (model work, never an operator decision).
** *Explicit push lease*: A forced push always names its lease explicitly as the expected remote SHA, in both variants: the `remote_sha` observed at the rejection that raised the escalation, else the SHA of the last recorded push (`branch_pushed_at`). The local remote-tracking ref is never the lease, because a fetch between observation and push moves it and turns the lease into a plain force. `git.push-with-lease` runs the approved forced push; a `rejected_lease{remote_sha}` (the remote moved again) returns to `git.sync-required`. Before every retry of a rejected push, the remote branch is re-read (`ls-remote`) and the retry uses the re-read SHA. *Deliberate change vs. `plan-marshall`*: `plan-marshall` pushes `--force-with-lease` without an expected value, taking the lease from the tracking ref.

[#loop-back-bounds]
== Worktree-Constrained Loop-Back & Iteration Bounds
_See Requirement link:../Requirements.adoc#PM-WF-7[PM-WF-7: Worktree-Constrained Loop-Back & Iteration Bounds]_

_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-63[PM-WATCH-PHASE-63]_

When a finalize step (CI failure, quality gate failure, or review finding triage) requires code changes, the workflow transitions from `finalize` back to `execute` via a `loop_back` link governed by two strict server-side invariants:

=== 1. Worktree Confinement Guard (`in_worktree`)

* Every `loop_back` link in `finalize.pmwf` declares `guard in_worktree` and no other guard; the iteration bound is enforced by the backing primitive, not by link omission (see Section 2).
* `GuardExpr.InWorktree` evaluates to `true` if and only if the plan's `mcp/status.json` records a non-null `worktree_path` and that path is `.marshall/local/worktrees/<plan_id>/`, exists, and is a valid git worktree for the plan's branch. The plan directory itself never moves (link:filesystem-layout.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]).
* Once the plan passes `finalize.merge-gate`, merges its branch, and its worktree is removed (`worktree_path: null`), `InWorktree` evaluates to `false`. All `loop_back` links are automatically omitted from representations and rejected by `pm_do`.

=== 2. Iteration Cap & Iteration Counter Validation

* The maximum number of automated finalize-to-execute loop-backs, `max_iterations`, is the compiled constant `3`; it is not configurable (a per-project cap would make loop metrics incomparable across projects). The only way past it is the operator's per-plan extension (`granted_extensions`, below).
* The plan's `mcp/status.json` persists `"loop_back_iteration": <int>` (initialized to `0` when entering `finalize` for the first time). The name mirrors plan-marshall's `status.metadata.loop_back_iteration`.
* When `loop_back` is followed, `plan.allocate-remediation-tasks` compares `loop_back_iteration` against the compiled `max_iterations` inside the same locked transaction:
** If `loop_back_iteration < max_iterations + granted_extensions`, `loop_back_iteration` is atomically incremented by `1` in `mcp/status.json`, fresh task files (`TASK-NNN.json`) and a fresh dispatch envelope (`envelope-M` with a new `dispatch_id`) are allocated in the worktree — completed tasks are never mutated or reopened — and the primitive returns `allocated -> execute.dispatch-ready`. Before allocating, the primitive re-captures `realized_files` and, when `realized − (declared ∪ approved_widening)` is non-empty, returns `footprint_review -> execute.deviation-review` first: the new paths are presented as one batched deviation item, and `accept` records them in `approved_widening[]` with provenance `observed` (link:phase-workflows.adoc#_scope_deviation_contract[Phase Workflows Specification, Scope-Deviation Contract]); allocation continues after the review.
** If `loop_back_iteration >= max_iterations + granted_extensions`, the primitive allocates nothing, leaves the counter unchanged, records the refused request's `remediation_summary` in `mcp/status.json -> pending_remediation`, and returns `limit_reached -> finalize.loop-limit-reached`.
* *Productive vs Unproductive Loop-Backs*: When a loop-back iteration returns to `finalize`, the server records it in `mcp/status.json -> loop_backs[]` with `iteration`, `productive` (the iteration made at least one fix commit or filed at least one new finding, derived from `change-ledger.jsonl` and the findings store, never from a model claim), `fix_commits`, `findings_raised`, and `findings_self_seeded` (findings located in lines changed by an earlier iteration's fix). All loop-backs count against the ceiling; `productive` never lifts it.
* *Informed Escalation & Re-Arming*: `finalize.loop-limit-reached` renders the productive and unproductive counts, the per-iteration `findings_raised` and `findings_self_seeded` with the self-seeded share of the last iteration (and of the self-review step's rounds, link:domain-extensions.adoc[Domain Extensions Specification], Self-Review Surfacer Contract), and `findings_at_ceiling` (findings raised in the last iteration, whose fixes no round will review), so converging and oscillating loops are distinguishable. The operator's extension (elicitation or `pm-mcp operator`) grants N further iterations, recorded in `granted_extensions` with its reason, which re-arms the allocation. The approving outcome `extended` executes the allocation it approves (Rule 10 in <<static-verification-rules>>): it enters the `auto` state `finalize.allocate-after-extension`, which runs `plan.allocate-remediation-tasks` for `pending_remediation` in the same locked transaction as the resolution — allocating the fresh fix tasks and envelope, incrementing `loop_back_iteration` within `max_iterations + granted_extensions`, and running the footprint review — clears `pending_remediation`, and routes like every `loop_back` link (`allocated -> execute.dispatch-ready`, `footprint_review -> execute.deviation-review`, `limit_reached -> finalize.loop-limit-reached`). An extension therefore never reaches `execute.dispatch-ready` without the tasks it granted; the self-seeded share is a displayed fact only and never stops the loop automatically.
* At the limit, `loop_back` therefore stays offered (subject only to `in_worktree`), and its execution transitions to `finalize.loop-limit-reached`, which offers only `escalate` (requiring operator approval via elicitation or `pm-mcp operator` to grant additional iterations or abort). This is the transition required by `PM-WF-7`; the counter is never evaluated by a guard, so the limit state is always reachable.
* `finalize.loop-limit-reached`, like every other limit state, renders the effective limit in `facts` (`max_iterations: 3`, `granted_extensions`, and the resulting bound), so an escalation always quotes the bound actually applied.
* Only `loop_back` allocations count against `max_iterations`. Waiting for a review bot's rate window (`finalize.review-window-wait`) and re-triggering a bot never consume a loop-back iteration; their budgets derive from the bot's registered interval.
* A refusal whose reason cannot change between rounds at an unchanged `HEAD` (for example a verifier that cannot apply to the plan's content) is recorded once and closes the step or escalates once; it never offers `loop_back` and never increments `loop_back_iteration`.

=== Build-Time Drift Gate

A mandatory JUnit test (`WorkflowDiagramDriftTest`) in `pm-mcp-core` parses all `classpath:/workflows/*.pmwf` files, invokes `WorkflowDiagramGenerator`, and compares the output byte-for-byte against the committed diagram files in `doc/`. == State-Machine Property Verification, Scenario Replay & State Migration
_See Requirement link:../Requirements.adoc#PM-TEST-3[PM-TEST-3: State-Machine Invariant, Property & McpAssured Protocol Verification]_

_See Requirement link:../Requirements.adoc#PM-TEST-4[PM-TEST-4: End-to-End Scenario & Compaction Resume Testing]_

_See Requirement link:../Requirements.adoc#PM-TEST-6[PM-TEST-6: Behavioural Conformance of Model-Facing Content]_

_See Requirement link:../Requirements.adoc#PM-MIG-4[PM-MIG-4: Stage Exit Criteria & Lifecycle Gate]_

=== Property-Based State-Machine Verification (`PM-TEST-3`)

The `pm-mcp-core` test suite executes property-based tests (using `jqwik` / `cui-test-generator`) over every compiled `WorkflowDefinition` AST:

* *No Dead-End Non-Terminal States*: See <<no-dead-end-states>>.
* *Strict Guard Enforcement & Link Omission*: Random sequences of `pm_do` calls with invalid link names, unsatisfied guards (such as `loop_back` when `in_worktree == false`), or out-of-range parameters never mutate `mcp/status.json` and always return `rejected.reason` with `isError: false`.
* *Reachable Loop Limit*: Following `loop_back` while `loop_back_iteration >= max_iterations + granted_extensions` always transitions to `finalize.loop-limit-reached` with outcome `limit_reached`, allocates no tasks, and leaves `loop_back_iteration` unchanged.
* *Approved Extensions Allocate*: Resolving `loop_limit_extension` with `extended` always passes `finalize.allocate-after-extension`, and every subsequent entry of `execute.dispatch-ready` from it has fresh remediation tasks and an envelope allocated and `loop_back_iteration` incremented by exactly `1`; no path reaches `execute.dispatch-ready` from `finalize.loop-limit-reached` without an allocation.
* *Single-Level Leaf Sub-Agent Invariant*: Property generators traverse all reachable states in `WorkflowScope.ENTITY` definitions and verify that zero `form == LinkForm.DISPATCH` links are ever emitted.
* *Monotonic Bounded Loops*: Random failure injection in Q-Gate and finalize-to-execute loop-backs verifies that no path can complete `loop_back` with outcome `allocated` more than `max_iterations` times (`loop_back_iteration` never exceeds `max_iterations` without an operator grant) and that every further `loop_back` enters `*.loop-limit-reached` / `*.qgate-exhausted`.

[#no-dead-end-states]
==== No Dead-End Non-Terminal States
_Implementation watch: link:../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-1[PM-WATCH-DSL-1]_

Every persisted sub-state of every non-terminal `StateNode` has at least one exit whose guard can hold: an offered link, the implicit wait of a bound job (`active_job`) or pending decision, or an `auto`/`job` transition, whose guard evaluates to `HELD` in a store and configuration state the generators reach (<<guard-results>>). Persisted sub-states include entity sub-states, every condition overlay (`pending_condition`), and a bound running or settled job. That some abstract guard assignment would offer a link is not sufficient. Every reachable state has a finite path to a `terminal` state (`completed` or `aborted`), or, in a `scope workspace` unit, back to its start state (Rule 3).

=== Deterministic Scenario Replay Harness (`pm-mcp-scenario`, `PM-TEST-4`)

The harness is a test-scope part of `pm-mcp-core` (JUnit, in-process), not a module of its own (<<_module_boundary_decoupled_core_architecture>>). End-to-end lifecycle scenarios are authored as deterministic `.pmscenario` scripts executed in-process by `ScenarioReplayRunner` against a hermetic temporary git repository without invoking any live LLM:

[source,text]
----

assert_state refine.analyze
assert_skill skill://pm/refine/analyze/SKILL.md
assert_links submit:refine
do submit:refine {"clarified_request":"Add a null-safe header parser ...","correctness":98,"completeness":96,"consistency":100,"non_duplication":100,"ambiguity":95,"module_mapping":100,"pr_title":"feat(http): add null-safe header parser"}

...
resolve_elicitation approve_outline {"decision":"approve"}

* Simulated `do` arguments use only the DSL parameter types (`text`, `int`, `enum[…]`, `list<…>`); there is no object type, so the six refine confidence dimensions (`correctness`, `completeness`, `consistency`, `non_duplication`, `ambiguity`, `module_mapping`) are submitted as separate `int[0..100]` parameters.
* Each scenario step supports deterministic assertions (`assert_state`, `assert_links`, `assert_skill`, `assert_rejected`) and simulated actor actions (`do`, `complete_job`, `resolve_elicitation`, `operator_cli`).
* The mandatory CI regression suite replays scenarios covering: (1) happy-path single-module plan, (2) multi-task envelope dispatch and context-budget yield, (3) CI failure and worktree-constrained `loop_back` to `execute`, (4) review-bot finding triage (`FIX`, `SUPPRESS`, `ACCEPT`), (5) operator escalation via elicitation and CLI fallback, (6) mid-job daemon restart recovery, (7) a light-lane plan through `init.light-gate` and the collapsed light envelope to `outline.review`, and (8) light-to-deep escalation by the server budget trigger and by the judgment trigger.

[#behavioural-conformance-harness]
=== Behavioural Conformance Harness (`PM-TEST-6`)

The deterministic harnesses above verify the engine without a live model. The behavioural conformance harness (`pm-mcp-conformance`) verifies the model-facing content instead: whether a live model, served the rendered vocabulary skills and representations of one client profile, follows the rules they state. It is PM-MCP tooling, not prose: scenario execution, trajectory capture, observation, scoring, and verdict computation are performed by the harness against the runtime's own records, and no step relies on the model's account of what it did.

==== Execution Boundary: Out-of-Band Pre-Release Gate

* The harness lives in its own module `pm-mcp-conformance` outside the regular build (<<_module_boundary_decoupled_core_architecture>>): it is built and run only through its own Maven profile and is never bound to `verify`. `verify`, `-Pintegration-tests`, `-Pcoverage`, and the required CI checks (`build / conclusion`, `integration-tests / conclusion`) never invoke a live model.
* It is run explicitly against a release candidate binary (`pm-mcp` native executable with its embedded client bundles) before a release whose model-facing content changed: vocabulary skill templates, guidance strings, representation wording, client profiles, or tool descriptions. The resulting report is published with the release candidate; a `violated` or `indeterminate` verdict is resolved by a recorded operator decision (see *Evidence, Not Authorization* below), never by the harness.
* Each run starts an isolated runtime under a temporary `PM_MCP_BASE`, connects the host under test through a real `pm-mcp serve` relay with the client's installed bundle (`pm-mcp client install <client>`), and uses a hermetic fixture repository per scenario.

==== Scenario Records

Behavioural scenarios are declarative records executed against a live model through a real client connection (`pm-mcp serve`) on a fixture repository. Each scenario declares:

* `rule_ref`: the skill URI and section that states the rule, with the canonical (pre-render) SHA-256 of that section.
* `situation`: the fixture state and the entry command.
* `pressure`: the prompt or state condition that tempts a violation.
* `observation`: a predicate over the recorded tool-call trajectory, the returned `rejected.reason` values, and the resulting artifact tree.
* `binding_context`: where the rule binds, including its scoped exceptions. A scenario never places a rule in a context where its `binding_context` excludes it.
* `enforcement_class`: the class of the rule under link:mcp-tools.adoc#vocabulary-skill-rule-classification[Vocabulary Skill Rule Classification] (`engine`, `check`, or `guidance`). For an `engine` rule the scenario measures attempts that the engine rejected; the engine's acceptance of a violation is a `PM-TEST-3`/`PM-TEST-4` defect, not a behavioural verdict.
* `tolerance_band` and `population`: the held-rate band the verdict is mapped against and the number of samples per run.
* `negative_control`: `true` for a control scenario whose pressure is built to be violated; the harness expects `violated` from it.

Only rules whose violation is mechanically observable in the recorded tool calls or the resulting artifact tree are scored.

==== Trajectory Capture & Observation

* The trajectory is read from the isolated runtime's `audit.jsonl` (every MCP tool call, transition, rejection, and `channel` value, link:cli-and-security.adoc[CLI, Coordination & Security Specification]), from the plan and orchestrator stores, and from the fixture repository's final tree and commits. Host transcripts and model self-reports are never inputs of an observation.
* *Order-Tolerant Trajectory Predicates*: An observation predicate asserts the reached state, the set of required calls, and the absence of forbidden calls; it asserts call order only when order is itself the rule under test.
* *Reference Artifact Trees*: A benchmark scenario is a real workflow task on a fixture repository whose expected result is a concrete reference artifact tree (files, commits, recorded lessons), never a prose rubric; recipe-sourced plans skip Phase 2 and therefore run in batch without an operator stand-in.
* *Representation Parsing*: The baseline of every client includes a representation-parsing scenario in which the model extracts `links` and `facts` from a `pm_state` result in the TOON wire form (`PM-TOOL-5`, `PM-IMPL-2`).

==== Batch Roles

A question-driven scenario runs with three separate roles: the executor (model under test), an operator stand-in that answers `refine.awaiting_answers` through model-relayed `submit` (at most one batched round, matching the re-dispatch ceiling of link:phase-workflows.adoc#_single_batch_clarification_re_dispatch_ceiling[Phase Workflows § Single-Batch Clarification & Re-Dispatch Ceiling]), and the scorer. Authorizing decisions (`PM-WF-12`) are resolved by the harness through the operator channel, never by the stand-in.

==== Scoring & Verdicts

* *Axis Statement*: The harness design lists the five eval axes (task success, tool-use quality, trajectory compliance, hallucination, response quality) and states for each whether it is scored and, if not, why; each scored axis has a rubric that the observation predicate implements.
* *Deterministic Scorer First*: The scorer is the harness's predicate evaluator, which needs no model call. A judging model is admitted only for a scored axis whose rubric no predicate can decide; it is then fixed across all models under test, and before each run the harness compares its model identifier and family against the model under test and refuses the run with `scorer_not_independent` when the judge is the scored model or its sibling at default configuration.
* *Verdict Over a Margin*: Each scenario is run over a stated population of samples; the harness computes the held rate and its margin and maps it to `held`, `violated`, or `indeterminate` against the scenario's tolerance band. The per-sample observation is boolean; the three-valued verdict exists only at the aggregated level. A sample that cannot be scored (host error, timeout, unreadable trajectory) is counted as unscorable, and a run whose scored samples fall below the population resolves to `indeterminate`, never to `held`. A single run is reported with `sample: true`, never as a verdict.
* *Attribution Mode*: Every verdict records `attribution: isolated | realistic_context`; a rule that is also stated in resident content (the `pm/core` skill, entry commands, catalogue descriptions, link:client-profiles.adoc#host-resident-surface-inventory[Host-Resident Surface Inventory]) can only be measured as `realistic_context`.

==== Rule Population & Selection

* *Derived Rule Population*: The baseline's rule population is derived from every resident and served source in the Host-Resident Surface Inventory (entry commands, agent variants, catalogue descriptions, `pm/core`, tool descriptions); the harness reports the derived population size and never asserts completeness.
* *Selection by Defect Cost*: Rules are selected for scenarios by recorded defect cost (audit rejections such as `invalid_link_args`, `store_tampered`, and historical defect records), never by intuition; the selection records its source.
* *Negative Controls*: Every baseline contains at least one negative-control scenario; a baseline whose negative control does not score `violated` is itself reported `indeterminate`, because the harness has shown it cannot detect a violation.

==== Digest Binding & Baseline Lifecycle

* *Digest Binding*: Every scenario records the canonical (pre-render) SHA-256 of the skill section that states its rule and every verdict records the rendered per-client `_meta.sha256` (`PM-SKILL-2`); a scenario whose recorded canonical digest differs from the current skill is refused as `stale_scenario` until re-authored.
* *Baseline Lifecycle*: A baseline is re-recorded when a bound skill digest, the client profile digest, the model identifier, or the binary's major/minor version changes; verdicts whose bound digest no longer matches are marked `invalidated`, never silently kept.

==== Report Fields

Every run report carries `client_id`, model identifier, binary version, client profile digest, bound skill digests, population, per-verdict counts, margin, tolerance band, `attribution`, `sample: true` for single runs, and token consumption per client and model (`unmeasured` when the host reports none, never `0`). Results are grouped by `enforcement_class`. Every report states an absolute reference as well as the delta to the previous baseline, never the delta alone. A client profile without a report of its own is reported as behaviourally untested; structural results (rendering, digests, registration, resolution) never stand in for it.

*Verdict and Baseline Store*: Verdict records and baselines are versioned test artifacts in the PM-MCP repository, one file per client and model (`src/test/behaviour/baselines/<client_id>/<model>.json` in the module that hosts the harness), never a runtime store: the runtime neither writes nor reads them. Each file carries `format_version`, the scenario population, per-verdict counts, margin, tolerance band, the bound skill and client profile digests, and its pin (binary version and model identifier). The harness writes a new baseline only into the working tree; it enters the repository through a reviewed pull request and is thereby bound to a release. The delta of a report is computed against the baseline committed for the same client and model; a missing baseline makes the report absolute-only and names the client and model as behaviourally untested. A conformance verdict is never written to `findings.jsonl`, which is plan-scoped and has no verdict or population fields.

==== Cost Ceilings & Sizing

Every scoring layer, including a judging model, declares its cost ceiling (runtime, tokens, and money per run) in the harness configuration at design time; the harness stops a run that reaches a ceiling and reports it `indeterminate` with the ceiling that was hit. The sizing of a full baseline (runtime, tokens, and money per client and model) is published before the harness is used as a routine pre-release gate.

==== Evidence, Not Authorization

A verdict is evidence for a separately authorized decision. It never directly authorizes an edit of model-facing content, and a `violated` verdict is scoped to the rule, pressure, model, and client it was measured on. Any per-client or per-model change of wording, emphasis, or scaffolding beyond the vocabulary dimensions of `PM-CLIENT-2` requires a behavioural signal for that client and a recorded decision.

=== State-Name Migration Registry & `released-states.txt` Gate (`PM-MIG-4`)
_Implementation watch: link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-19[PM-WATCH-GEN-19]_

To guarantee that active plans survive `pm-mcp` binary upgrades across state renames or workflow splits:

* Every state identifier shipped in a public release is appended to the committed `classpath:/workflows/released-states.txt` baseline.
* When a state is renamed or split in a `.pmwf` file, the workflow header declares `migrate <old_state_id> -> <new_state_id>`.
* When `WorkflowEngine` loads `mcp/status.json` whose `state` matches `<old_state_id>`, it transparently rewrites `state` to `<new_state_id>` and appends a `state_migrated` event to `audit.jsonl`.
* A build-time JUnit gate (`ReleasedStatesMigrationTest`) verifies that every entry in `released-states.txt` either exists in the current `WorkflowDefinition.states()` map or is covered by a transitive `migrate` chain terminating in a live state.
