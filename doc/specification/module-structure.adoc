== Overview

This document is the authoritative listing of the Maven modules of *plan-marshall-mcp* (`PM-MCP`): the aggregators, every module with its package namespace, responsibilities and allowed dependencies, the binary it builds, and the specification documents it implements. Every other document names modules only by reference to this listing and never repeats it; a module that is added, renamed or removed changes here first.

The listing is linked in both directions: the *Specified in* column of <<modules>> names the specification documents (or parts) each module implements, and every specification document names its implementing modules in its `Modules` section, linking back to the module's row here. A change to either side updates the other in the same change (link:../Specification.adoc#_traceability_requirements[Specification § Traceability Requirements]). When Milestone 1 implements the module structure, this listing moves into the module map of the developer documentation, which then takes over as the only listing (project skill `traced-implementation`).

[#module-tree]
== Module Tree
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-3[PM-WATCH-MOD-3]_

All modules are created and integrated in Milestone 1 (link:../roadmap.adoc[Roadmap]), each with minimal real code and tests, never an empty shell: the initial single module `plan-marshall-mcp` is renamed to `pm-mcp-server`, the library modules are gathered under the aggregator `pm-modules` (the external integrations under its nested aggregator `pm-providers`), and the client modules under the top-level aggregator `pm-clients`. Aggregators hold no code of their own.

[source,text]
----
plan-marshall-mcp (root POM)
├── pm-modules                  aggregator: library modules
│   ├── pm-api                  client contract of /api/v1
│   ├── pm-exec                 job launcher        -> binary pm-exec
│   ├── pm-core                 foundation: SPIs, contracts, stores, TOON
│   ├── pm-workflow             DSL, engine, workflow units, hypermedia
│   ├── pm-providers            aggregator: external integrations
│   │   ├── pm-provider-git              git contract, JGit + git CLI variants
│   │   ├── pm-provider-ci               CI contract and registry
│   │   ├── pm-provider-github           GitHub: ci + findings (core)
│   │   ├── pm-provider-gitlab           GitLab: ci + findings (core)
│   │   └── pm-provider-sonar            Sonar: analysis + findings (core)
│   ├── pm-e2e                  release-shape end-to-end tests
│   └── pm-conformance          out-of-band behavioural conformance
├── pm-clients                  aggregator: client modules
│   ├── pm-relay                relay, enter        -> binary pm-mcp
│   ├── pm-operator             operator CLI        -> binary pm-operator
│   └── pm-web-app              SvelteKit SPA (resource JAR)
└── pm-mcp-server               daemon assembly     -> binary pm-mcpd
----

[#dependency-rules]
== Dependency Rules
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-1[PM-WATCH-MOD-1], link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-3[PM-WATCH-MOD-3]_

Dependencies flow toward `pm-core`; an automated build check (Maven enforcer or an architecture test over the resolved dependency trees) enforces every rule below (`PM-IMPL-1`):

* `pm-core` depends on no other PM-MCP module except `pm-api`, whose host-detection table its client profiles read; `pm-workflow` on `pm-core` only. Neither depends on Quarkus, CDI, MCP libraries, JGit, or `cui-http`.
* `pm-provider-git` and `pm-provider-ci` depend on `pm-core`; `pm-provider-github`, `pm-provider-gitlab`, and `pm-provider-sonar` on `pm-provider-ci` (its shared HTTP base) and `pm-core`. No provider module depends on `pm-workflow`: providers contribute primitives through the SPI in `pm-core` and never see engine internals.
* `pm-mcp-server` depends on `pm-core`, `pm-workflow`, every provider module, `pm-api`, and the resource JAR `pm-web-app`, and assembles them. It is the only module that depends on `org.commonmark:commonmark`, which its ingestion validator uses.
* The client modules never depend on `pm-core`, `pm-workflow`, a provider module, `pm-mcp-server`, or Quarkus: `pm-relay` and `pm-operator` depend on `pm-api` only and never on each other, and `pm-web-app` depends on no PM-MCP module. `pm-api` depends on `jackson-core` only.
* `pm-exec` depends on no other PM-MCP module.
* `pm-conformance` and `pm-e2e` have no Maven dependency on `pm-mcp-server`; they reach the product only through its built binaries.

Provider resolution uses explicit registries (the CI registry of `pm-provider-ci` by CI provider, the findings registry of `pm-core` by source kind, the analysis registry of `pm-core` by analysis provider) whose modules are passed to the registry's constructor: `pm-mcp-server` produces each registry through a CDI producer, and plain-Java tests construct it directly; no `ServiceLoader` or classpath discovery.

[#integration-variants]
== Integration Variants

Which implementation of `pm-provider-git`, `pm-provider-github`, or `pm-provider-gitlab` serves a project is settled per integration in project setup (link:domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]): the native variant applies unless the derived fact `git_native_capability` finds a used repository feature the native variant cannot serve; only then is a choice required, and it is taken through the operator channel (`setup.select-integration-variants`). One variant serves all operations of an integration, and there is no automatic fallback from one variant to the other (`PM-EXEC-5`).

[#findings-analysis-contracts]
== Findings & Code-Analysis Contracts

The findings and code-analysis contracts are provider-neutral and live in `pm-core` (packages `de.cuioss.pm.core.findings` and `de.cuioss.pm.core.analysis`), not in provider modules of their own, because their data is part of the foundation: the findings store persists the normalized findings (link:store-schemas/03-findings-and-review-records.adoc[Store Schemas § Findings & Review Records]), and the composite wait in `pm-workflow` evaluates the `analysis_status` dimension, so neither `pm-core` nor `pm-workflow` could reach them in a provider module.

* *Findings*: `FindingSource.fetch(scope)` returning normalized findings and `FindingResponder.respond(finding, disposition)` with `FIX`, `ACCEPT`, or `SUPPRESS` and a reason, the TOON contracts, and a registry by source kind (review bots, static analysis, code scanning). Implemented by `pm-provider-github`, `pm-provider-gitlab`, and `pm-provider-sonar`.
* *Code analysis*: the analysis status of a commit or pull request, the quality gate result (passed or failed, with its conditions), and new issues tagged by provider, with a registry by analysis provider; every provider adapter (Sonar, CodeQL, and others) maps its results to the closed wait dimension `analysis_status`, so a new provider needs only an adapter. Implemented by `pm-provider-sonar`.

The CI contracts stay in the provider module `pm-provider-ci`, because they carry the shared HTTP base over `cui-http`, which `pm-core` must not depend on.

One release produces exactly four native binaries; their roles and the installation layout are specified in link:cli-and-security/01-cli-and-installer.adoc#cli-binary[CLI & Security § Command-Line Binaries].

[cols="1,2,3"]
|===
|Binary |Module |Build

|`pm-mcp`
|<<module-pm-relay,`pm-relay`>>
|Plain GraalVM native image, `native-maven-plugin` in the module's `native` profile

|`pm-operator`
|<<module-pm-operator,`pm-operator`>>
|Plain GraalVM native image, `native-maven-plugin` in the module's `native` profile

|`pm-mcpd`
|<<module-pm-mcp-server,`pm-mcp-server`>>
|Quarkus native build

|`pm-exec`
|<<module-pm-exec,`pm-exec`>>
|Plain GraalVM native image, `native-maven-plugin` in the module's `native` profile
|===

All other modules are plain JARs, except `pm-web-app` (resource JAR, served by `pm-mcpd`); no binary of its own serves the web access. The native builds of all four binaries run in CI from Milestone 1.

*Platform matrix* (`PM-TECH-4`): one release version produces the four binaries for each first-tier platform, each set built natively on its platform and installed in the same release layout:

[cols="1,2"]
|===
|Operating system |Architectures

|macOS
|`arm64`, `x86_64`

|Linux (`glibc`)
|`x86_64`, `aarch64`
|===

Windows is served only through WSL2, with the Linux binaries; no Windows-native binary is built.

[#test-placement]
== Test Placement

* *Unit tests*: every module carries its own JUnit 5 suite and meets the coverage minimum on its own. The plain-Java library modules (`pm-api`, `pm-exec`, `pm-core`, `pm-workflow`, the provider modules) run them on the JVM without Quarkus augmentation.
* *Integration tests* (`*IT`, `-Pintegration-tests`), four layers: `pm-mcp-server` (packaged daemon over MCP/HTTP on its Unix socket, including the web listener and pairing), `pm-relay` (the `pm-mcp serve` relay over real `stdio` against a staged `pm-mcpd`), `pm-operator` (operator verbs against a staged `pm-mcpd`), and `pm-e2e` (all four binaries in the release layout). The MCP protocol layers (McpAssured) are the server, the relay, and the end-to-end layer; the `pm-operator` layer serves no MCP (link:mcp-tools/04-errors-and-testing.adoc[MCP Tools § Errors & Protocol Testing]).
* *Native reflection*: a build test in `pm-mcp-server` verifies that every persisted record of `pm-core`, `pm-workflow`, and the provider modules is registered for GraalVM native reflection.
* *Scenario replay* (`pm-scenario`, `PM-TEST-4`): test scope of `pm-workflow`, not a module.
* *Behavioural conformance* (`PM-TEST-6`): `pm-conformance`, out of band.

[#module-cuts]
== Module Cuts

A module exists where it separates a dependency boundary, a build type, or a binary; a subject area alone does not justify one.

* `pm-workflow` is separated from `pm-core` because the workflow language and the process it runs form the largest body of logic with its own verification (grammar, static verifier, property tests, drift tests, scenario replay), and the separation keeps the provider modules away from engine internals: they build against the foundation in `pm-core` only.
* The findings and code-analysis contracts are part of `pm-core` rather than provider modules of their own (<<findings-analysis-contracts>>): they are interfaces and registries without an external dependency, and their data belongs to the store and the workflow. A provider module is cut only where it holds an implementation or a dependency the foundation must not have (`pm-provider-git` with JGit, `pm-provider-ci` with its `cui-http` base, the provider adapters).
* The stores, configuration, domain extensions, client profiles, and parsers stay together in `pm-core`: each is consumed by the engine and by the assembly alike, none has a dependency the others lack, and splitting them would only add modules without a boundary to enforce.
* The CLI is cut in two modules by caller, not by subject: `pm-relay` builds `pm-mcp` with the verbs a harness or the model runs (`serve`, `enter`), `pm-operator` builds `pm-operator` with every verb a human runs at a terminal. The cut makes the host deny rule a whole binary: a bundle denies `pm-operator` to the model as one executable and keeps `pm-mcp` allowed, instead of sub-command rules inside one binary that every new verb would have to be sorted into. What the two share (the socket client, the on-demand start, the codecs, the direct file reads with the drift checks, the host-detection table) lives in `pm-api`, their only dependency.
* The web adapter is a package of `pm-mcp-server`, not a module and not a binary: it has no dependency the daemon lacks (the second HTTP server is the daemon's own Quarkus/Vert.x stack) and no build type of its own, and the device store, the pairing codes, and the device-secret check it needs already live in the daemon. Only the web app is a module (`pm-web-app`), because its build type differs (npm, resource JAR).
* Model work is cut by what each part depends on: the role sets and the task queue store live in `pm-core` with the other stores and configuration, because the client profiles that validate a role and the lock order of the queue are there; the model caller and the task protocol unit live in `pm-workflow`, because they are workflow logic over persisted records; the supervisor lives in `pm-mcp-server` beside the job runner, because it starts, signals, and observes processes, which neither library module may do.
* The hypermedia state engine stays in `pm-workflow`: it renders the links of the current workflow state and cannot be separated from the interpreter; only the generic TOON encoder, which the providers also use, lives in `pm-core`.
