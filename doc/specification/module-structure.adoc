== Overview

This document is the authoritative listing of the Maven modules of *plan-marshall-mcp* (`PM-MCP`): the aggregators, every module with its package namespace, responsibilities and allowed dependencies, the binary it builds, and the specification documents it implements. Every other document names modules only by reference to this listing and never repeats it; a module that is added, renamed or removed changes here first.

The listing is linked in both directions: the *Specified in* column of <<modules>> names the specification documents (or parts) each module implements, and every specification document names its implementing modules in its `Modules` section, linking back to the module's row here. A change to either side updates the other in the same change (link:../Specification.adoc#_traceability_requirements[Specification § Traceability Requirements]). When Milestone 0 implements the module structure, this listing moves into the module map of the developer documentation, which then takes over as the only listing (project skill `traced-implementation`).

[#module-tree]
== Module Tree

All modules are created and integrated in Milestone 0 (link:../roadmap.adoc[Roadmap]), each with minimal real code and tests, never an empty shell: the initial single module `plan-marshall-mcp` is renamed to `pm-mcp-server`, the library modules are gathered under the aggregator `pm-mcp-modules` (the external integrations under its nested aggregator `pm-mcp-providers`), and the client modules under the top-level aggregator `pm-mcp-clients`. Aggregators hold no code of their own.

[source,text]
----
plan-marshall-mcp (root POM)
├── pm-mcp-modules                  aggregator: library modules
│   ├── pm-mcp-api                  client contract of /api/v1
│   ├── pm-mcp-exec                 job launcher        -> binary pm-mcp-exec
│   ├── pm-mcp-core                 foundation: SPIs, contracts, stores, TOON
│   ├── pm-mcp-workflow             DSL, engine, workflow units, hypermedia
│   ├── pm-mcp-providers            aggregator: external integrations
│   │   ├── pm-mcp-git              git contract, JGit + git CLI variants
│   │   ├── pm-mcp-ci               CI contract and registry
│   │   ├── pm-mcp-github           GitHub: ci + findings (core)
│   │   ├── pm-mcp-gitlab           GitLab: ci + findings (core)
│   │   └── pm-mcp-sonar            Sonar: analysis + findings (core)
│   ├── pm-mcp-e2e                  release-shape end-to-end tests
│   └── pm-mcp-conformance          out-of-band behavioural conformance
├── pm-mcp-clients                  aggregator: client modules
│   ├── pm-mcp-cli                  CLI and STDIO relay -> binary pm-mcp
│   ├── pm-mcp-web-server           web server          -> binary pm-mcp-web
│   └── pm-mcp-web-app              SvelteKit SPA (resource JAR)
└── pm-mcp-server                   daemon assembly     -> binary pm-mcpd
----

[#dependency-rules]
== Dependency Rules
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-1[PM-WATCH-MOD-1]_

Dependencies flow toward `pm-mcp-core`; an automated build check (Maven enforcer or an architecture test over the resolved dependency trees) enforces every rule below (`PM-IMPL-1`):

* `pm-mcp-core` depends on no other PM-MCP module except `pm-mcp-api`, whose host-detection table its client profiles read; `pm-mcp-workflow` on `pm-mcp-core` only. Neither depends on Quarkus, CDI, MCP libraries, JGit, or `cui-http`.
* `pm-mcp-git`, `pm-mcp-ci`, and `pm-mcp-sonar` depend on `pm-mcp-core`; `pm-mcp-github` and `pm-mcp-gitlab` on `pm-mcp-ci` and `pm-mcp-core`. No provider module depends on `pm-mcp-workflow`: providers contribute primitives through the SPI in `pm-mcp-core` and never see engine internals.
* `pm-mcp-server` depends on `pm-mcp-core`, `pm-mcp-workflow`, every provider module, and `pm-mcp-api`, and assembles them. It is the only module that depends on `org.commonmark:commonmark`, which its ingestion validator uses.
* The client modules never depend on `pm-mcp-core`, `pm-mcp-workflow`, or a provider module: `pm-mcp-cli` depends on `pm-mcp-api` only, `pm-mcp-web-server` on `pm-mcp-api`, `pm-mcp-web-app`, and Quarkus. `pm-mcp-api` depends on `jackson-core` only.
* `pm-mcp-exec` depends on no other PM-MCP module.
* `pm-mcp-conformance` and `pm-mcp-e2e` have no Maven dependency on `pm-mcp-server`; they reach the product only through its built binaries.

Provider resolution uses explicit registries (the CI registry of `pm-mcp-ci` by CI provider, the findings registry of `pm-mcp-core` by source kind, the analysis registry of `pm-mcp-core` by analysis provider) whose modules are passed to the registry's constructor: `pm-mcp-server` produces each registry through a CDI producer, and plain-Java tests construct it directly; no `ServiceLoader` or classpath discovery.

[#integration-variants]
== Integration Variants

Which implementation of `pm-mcp-git`, `pm-mcp-github`, or `pm-mcp-gitlab` serves a project is settled per integration in project setup (link:domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]): the native variant applies unless the derived fact `git_native_capability` finds a used repository feature the native variant cannot serve; only then is a choice required, and it is taken through the operator channel (`setup.select-integration-variants`). One variant serves all operations of an integration, and there is no automatic fallback from one variant to the other (`PM-EXEC-5`).

[#findings-analysis-contracts]
== Findings & Code-Analysis Contracts

The findings and code-analysis contracts are provider-neutral and live in `pm-mcp-core` (packages `de.cuioss.pm.mcp.core.findings` and `de.cuioss.pm.mcp.core.analysis`), not in provider modules of their own, because their data is part of the foundation: the findings store persists the normalized findings (link:store-schemas/03-findings-and-review-records.adoc[Store Schemas § Findings & Review Records]), and the composite wait in `pm-mcp-workflow` evaluates the `analysis_status` dimension, so neither `pm-mcp-core` nor `pm-mcp-workflow` could reach them in a provider module.

* *Findings*: `FindingSource.fetch(scope)` returning normalized findings and `FindingResponder.respond(finding, disposition)` with `FIX`, `ACCEPT`, or `SUPPRESS` and a reason, the TOON contracts, and a registry by source kind (review bots, static analysis, code scanning). Implemented by `pm-mcp-github`, `pm-mcp-gitlab`, and `pm-mcp-sonar`.
* *Code analysis*: the analysis status of a commit or pull request, the quality gate result (passed or failed, with its conditions), and new issues tagged by provider, with a registry by analysis provider; every provider adapter (Sonar, CodeQL, and others) maps its results to the closed wait dimension `analysis_status`, so a new provider needs only an adapter. Implemented by `pm-mcp-sonar`.

The CI contracts stay in the provider module `pm-mcp-ci`, because they carry the shared HTTP base over `cui-http`, which `pm-mcp-core` must not depend on.

[#test-placement]
== Test Placement

* *Unit tests*: every module carries its own JUnit 5 suite and meets the coverage minimum on its own. The plain-Java library modules (`pm-mcp-api`, `pm-mcp-exec`, `pm-mcp-core`, `pm-mcp-workflow`, the provider modules) run them on the JVM without Quarkus augmentation.
* *Integration tests* (`*IT`, `-Pintegration-tests`), one layer per binary: `pm-mcp-server` (packaged daemon over MCP/HTTP on its Unix socket), `pm-mcp-cli` (the `pm-mcp serve` relay over real `stdio` against a staged `pm-mcpd`), `pm-mcp-web-server` (packaged web server), and `pm-mcp-e2e` (all four binaries in the release layout) (link:mcp-tools/04-errors-and-testing.adoc[MCP Tools § Errors & Protocol Testing]).
* *Native reflection*: a build test in `pm-mcp-server` verifies that every persisted record of `pm-mcp-core`, `pm-mcp-workflow`, and the provider modules is registered for GraalVM native reflection.
* *Scenario replay* (`pm-mcp-scenario`, `PM-TEST-4`): test scope of `pm-mcp-workflow`, not a module.
* *Behavioural conformance* (`PM-TEST-6`): `pm-mcp-conformance`, out of band.

[#module-cuts]
== Module Cuts

A module exists where it separates a dependency boundary, a build type, or a binary; a subject area alone does not justify one.

* `pm-mcp-workflow` is separated from `pm-mcp-core` because the workflow language and the process it runs form the largest body of logic with its own verification (grammar, static verifier, property tests, drift tests, scenario replay), and the separation keeps the provider modules away from engine internals: they build against the foundation in `pm-mcp-core` only.
* The findings and code-analysis contracts are part of `pm-mcp-core` rather than provider modules of their own (<<findings-analysis-contracts>>): they are interfaces and registries without an external dependency, and their data belongs to the store and the workflow. A provider module is cut only where it holds an implementation or a dependency the foundation must not have (`pm-mcp-git` with JGit, `pm-mcp-ci` with its `cui-http` base, the provider adapters).
* The stores, configuration, domain extensions, client profiles, and parsers stay together in `pm-mcp-core`: each is consumed by the engine and by the assembly alike, none has a dependency the others lack, and splitting them would only add modules without a boundary to enforce.
* The hypermedia state engine stays in `pm-mcp-workflow`: it renders the links of the current workflow state and cannot be separated from the interpreter; only the generic TOON encoder, which the providers also use, lives in `pm-mcp-core`.
