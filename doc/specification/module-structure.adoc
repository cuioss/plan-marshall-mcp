== Overview

This document is the authoritative listing of the repositories and Maven modules of *plan-marshall-mcp* (`PM-MCP`): the repositories with their visibility and the artifacts each publishes, the aggregators, every module with its package namespace, responsibilities and allowed dependencies, the binary it builds, and the specification documents it implements. Every other document names modules only by reference to this listing and never repeats it; a module that is added, renamed or removed changes here first.

The listing is linked in both directions: the *Specified in* column of <<modules>> names the specification documents (or parts) each module implements, and every specification document names its implementing modules in its `Modules` section, linking back to the module's row here. A change to either side updates the other in the same change (link:../Specification.adoc#_traceability_requirements[Specification § Traceability Requirements]). When Milestone 1 implements the module structure, this listing moves into the module map of the developer documentation, which then takes over as the only listing (project skill `traced-implementation`).

[#repositories]
== Repositories
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-5[PM-WATCH-MOD-5], link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-6[PM-WATCH-MOD-6]_

The product is built from five repositories of the GitHub organisation `plan-marshall`. The cut follows what a repository costs and what it must keep closed: the plain-Java modules live in repositories that stay public while the product is developed, where CI minutes, static analysis and review bots are free, and the private repository holds only the Quarkus assembly, the model-facing content and the tests that need all four binaries.

A repository listed as public is switched to private when the product is distributed (the documentation repository when the documentation has settled); nothing in this structure depends on a repository being public, and the switch changes no build (<<artifact-flow>>).

Every code repository has the same shape: the parent `pm-mcp-parent`, its own `CLAUDE.md`, the ruleset `main-branch-protection` with the merge queue, and the reusable CI workflows. A module is named with its repository only in this document.

[#model-facing-content]
=== Model-Facing Content

The mechanism is public and the content is not. The workflow language, the engine, the role and profile schemas and the skill rule checker are code of `pm-mcp-core`. What they run and serve is content of the private repository, packaged as classpath resources of `pm-mcp-server` and compiled into `pm-mcpd`: the default workflow units (`classpath:/workflows/`), the shipped role set (`classpath:/roles/`), the `skill://pm/**` corpus, and the client bundles (`classpath:/bundles/<client>/`). The modules of `pm-mcp-core` read these resources by their classpath location and carry none of them; their own tests run against fixture units and fixture roles in test scope. The client profiles (`classpath:/profiles/`) hold host facts and stay in `pm-core`.

[#artifact-flow]
== Artifact Flow
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-5[PM-WATCH-MOD-5]_

* *One registry*: every artifact of every repository is deployed to the GitHub Packages Maven registry of the organisation `plan-marshall` (`https://maven.pkg.github.com/plan-marshall/<repository>`) and to no other place. No build deploys to Maven Central or to any other registry: the parent sets `distributionManagement` to the organisation registry and switches the Maven Central publishing of its own parent off. Third-party dependencies and `cui-quarkus-parent` are resolved from Maven Central as before.
* *Visibility*: a Maven package takes the visibility of the repository it is published from. A package of a public repository can be downloaded by every authenticated GitHub account, in or outside the organisation; a package of a private repository only by an account or token with access to that repository.
* *Resolution*: the registry answers no anonymous request, for a public package either. Every developer machine and every CI job resolves through a Maven `settings.xml` that names the organisation registry (`https://maven.pkg.github.com/plan-marshall/*`) with a token carrying package read permission. The registry is named in the settings and not in a POM, because the parent POM itself is resolved from it.
* *Order*: `pm-mcp-parent` -> `pm-mcp-clients` -> `pm-mcp-core` -> `plan-marshall-mcp`. `pm-mcp-core` consumes `pm-api` of `pm-mcp-clients` (<<dependency-rules>>); the product consumes both BOMs.
* *Versions*: every repository has its own version. A merge to `main` deploys the `SNAPSHOT` of that repository; a release is a tag that deploys the release version. A consuming repository names each upstream by one version property and imports its BOM; between releases it builds against the upstream `SNAPSHOT`, and it pins release versions for a release of its own. The release version of the product (`PM-DIST-1`) is the version of `plan-marshall-mcp`; the release notes name the versions of the three upstream repositories it was built from.
* *Propagation*: a merge to `main` of an upstream repository starts the build of each consumer against the new `SNAPSHOT`, so a break shows in the consumer before the next change there; a release opens the update pull request in each consumer.
* *Native binaries*: `pm-mcp-clients` builds `pm-mcp`, `pm-operator`, and `pm-exec` per platform and deploys each as an archive attached to its module under the platform classifier (`linux-x86_64`, `linux-aarch64`). `plan-marshall-mcp` builds only `pm-mcpd`, resolves the three other binaries by version and classifier, and assembles the release layout from them.

[#module-tree]
== Module Tree
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-3[PM-WATCH-MOD-3]_

Every module is created when its first code arrives, each with minimal real code and tests, never an empty shell. Aggregators hold no code of their own.

[source,text]
----
pm-mcp-parent                   parent POM of all modules

pm-mcp-clients (root POM)
├── bom                         pm-mcp-clients-bom
├── pm-api                      client contract of /api/v1
├── pm-exec                     job launcher        -> binary pm-exec
├── pm-relay                    relay, enter        -> binary pm-mcp
├── pm-operator                 operator CLI        -> binary pm-operator
└── pm-web-app                  SvelteKit SPA (resource JAR)

pm-mcp-core (root POM)
├── bom                         pm-mcp-core-bom
├── pm-core                     foundation: SPIs, contracts, stores, TOON
├── pm-workflow                 DSL, engine, hypermedia
├── pm-providers                aggregator: external integrations
│   ├── pm-provider-git              git contract, JGit + git CLI variants
│   ├── pm-provider-ci               CI contract and registry
│   ├── pm-provider-github           GitHub: ci + findings (core)
│   ├── pm-provider-gitlab           GitLab: ci + findings (core)
│   └── pm-provider-sonar            Sonar: analysis + findings (core)
└── pm-runtime                  daemon logic without a framework

plan-marshall-mcp (root POM)
├── pm-mcp-server               Quarkus assembly, content -> binary pm-mcpd
├── pm-e2e                      release-shape end-to-end tests
└── pm-conformance              out-of-band behavioural conformance
----

[#dependency-rules]
== Dependency Rules
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-1[PM-WATCH-MOD-1], link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-3[PM-WATCH-MOD-3]_

Dependencies flow toward `pm-core`, and between repositories only in the order of <<artifact-flow>>: no module depends on a module of a repository later in that order. An automated build check in every repository (Maven enforcer or an architecture test over the resolved dependency trees) enforces the rules below that concern its modules (`PM-IMPL-1`):

* `pm-core` depends on no other PM-MCP module except `pm-api`, whose host-detection table its client profiles read; `pm-workflow` on `pm-core` only. Neither depends on Quarkus, CDI, MCP libraries, JGit, or `cui-http`.
* `pm-provider-git` and `pm-provider-ci` depend on `pm-core`; `pm-provider-github`, `pm-provider-gitlab`, and `pm-provider-sonar` on `pm-provider-ci` (its shared HTTP base) and `pm-core`. No provider module depends on `pm-workflow`: providers contribute primitives through the SPI in `pm-core` and never see engine internals.
* `pm-runtime` depends on `pm-core` only among the PM-MCP modules, never on `pm-workflow` or a provider module, and never on Quarkus, CDI, Vert.x, or an MCP library. It is the only module that depends on `org.commonmark:commonmark`, which its ingestion validator uses, and on LSP4J.
* `pm-mcp-server` depends on `pm-core`, `pm-workflow`, `pm-runtime`, every provider module, `pm-api`, and the resource JAR `pm-web-app`, and assembles them. It is the only module that depends on Quarkus, on `quarkus-security`, and on the Netty native transports, and no class of it exists without a Quarkus, CDI, Vert.x, or MCP type in its signature or its annotations, apart from the records those classes exchange.
* The client modules never depend on `pm-core`, `pm-workflow`, a provider module, `pm-mcp-server`, or Quarkus: `pm-relay` and `pm-operator` depend on `pm-api` only and never on each other, and `pm-web-app` depends on no PM-MCP module. `pm-api` depends on `jackson-core` only.
* `pm-exec` depends on no other PM-MCP module.
* `pm-conformance` and `pm-e2e` have no compile or runtime dependency on `pm-mcp-server`; they reach the product only through its built binaries. `pm-e2e` declares a test-scoped dependency of type `pom` on `pm-mcp-server`, which brings no class onto its classpath and only orders the reactor so that `pm-mcpd` is built before it is staged; the three other binaries are resolved as archives from the registry.

Provider resolution uses explicit registries (the CI registry of `pm-provider-ci` by CI provider, the findings registry of `pm-core` by source kind, the analysis registry of `pm-core` by analysis provider) whose modules are passed to the registry's constructor: `pm-mcp-server` produces each registry through a CDI producer, and plain-Java tests construct it directly; no `ServiceLoader` or classpath discovery.

[#integration-variants]
== Integration Variants

Which implementation of `pm-provider-git`, `pm-provider-github`, or `pm-provider-gitlab` serves a project is settled per integration in project setup (link:domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]): the native variant applies unless the derived fact `git_native_capability` finds a used repository feature the native variant cannot serve; only then is a choice required, and it is taken through the operator channel (`setup.select-integration-variants`). One variant serves all operations of an integration, and there is no automatic fallback from one variant to the other (`PM-EXEC-5`).

[#findings-analysis-contracts]
== Findings & Code-Analysis Contracts

The findings and code-analysis contracts are provider-neutral and live in `pm-core` (packages `de.cuioss.pm.core.findings` and `de.cuioss.pm.core.analysis`), not in provider modules of their own, because their data is part of the foundation: the findings store persists the normalized findings (link:store-schemas/03-findings-and-review-records.adoc[Store Schemas § Findings & Review Records]), and the composite wait in `pm-workflow` evaluates the `analysis_status` dimension, so neither `pm-core` nor `pm-workflow` could reach them in a provider module.

* *Findings*: `FindingSource.fetch(scope)` returning normalized findings and `FindingResponder.respond(finding, disposition)` with `FIX`, `ACCEPT`, or `SUPPRESS` and a reason, the TOON contracts, and a registry by source kind (review bots, static analysis, code scanning). Implemented by `pm-provider-github`, `pm-provider-gitlab`, and `pm-provider-sonar`.
* *Code analysis*: the analysis status of a commit or pull request, the quality gate result (passed or failed, with its conditions), and new issues tagged by provider, with a registry by analysis provider; every provider adapter (Sonar, CodeQL, and others) maps its results to the closed wait dimension `analysis_status`, so a new provider needs only an adapter. Implemented by `pm-provider-sonar`.

The CI contracts stay in the provider module `pm-provider-ci`, because they carry the shared HTTP base over `cui-http`, which `pm-core` must not depend on.

[#test-placement]
== Test Placement

* *Unit tests*: every module carries its own JUnit 5 suite and meets the coverage minimum on its own. The plain-Java library modules (`pm-api`, `pm-exec`, `pm-core`, `pm-workflow`, `pm-runtime`, the provider modules) run them on the JVM without Quarkus augmentation.
* *Integration tests* (`*IT`, `-Pintegration-tests`), four layers: `pm-mcp-server` (packaged daemon over MCP/HTTP on its Unix socket, including the web listener and pairing), `pm-relay` (the `pm-mcp serve` relay over real `stdio` against the stub daemon of its test scope), `pm-operator` (operator verbs against the stub daemon of its test scope), and `pm-e2e` (all four binaries in the release layout, the only layer in which the client binaries meet the real `pm-mcpd`). The MCP protocol layers (McpAssured) are the server and the end-to-end layer, which runs the relay against the real daemon; the relay layer of `pm-mcp-clients` verifies the forwarding against recorded exchanges, and the `pm-operator` layer serves no MCP (link:mcp-tools/04-errors-and-testing.adoc[MCP Tools § Errors & Protocol Testing]).
* *Native reflection*: a build test in `pm-mcp-server` verifies that every persisted record of `pm-core`, `pm-workflow`, and the provider modules is registered for GraalVM native reflection.
* *Scenario replay* (`pm-scenario`, `PM-TEST-4`): test scope of `pm-workflow`, not a module.
* *Behavioural conformance* (`PM-TEST-6`): `pm-conformance`, out of band.

[#module-cuts]
== Module Cuts

A module exists where it separates a dependency boundary, a build type, or a binary; a subject area alone does not justify one.

* `pm-workflow` is separated from `pm-core` because the workflow language and the process it runs form the largest body of logic with its own verification (grammar, static verifier, property tests, drift tests, scenario replay), and the separation keeps the provider modules away from engine internals: they build against the foundation in `pm-core` only.
* The findings and code-analysis contracts are part of `pm-core` rather than provider modules of their own (<<findings-analysis-contracts>>): they are interfaces and registries without an external dependency, and their data belongs to the store and the workflow. A provider module is cut only where it holds an implementation or a dependency the foundation must not have (`pm-provider-git` with JGit, `pm-provider-ci` with its `cui-http` base, the provider adapters).
* The stores, configuration, domain extensions, client profiles, and parsers stay together in `pm-core`: each is consumed by the engine and by the assembly alike, none has a dependency the others lack, and splitting them would only add modules without a boundary to enforce.
* The CLI is cut in two modules by caller, not by subject: `pm-relay` builds `pm-mcp` with the verbs a harness or the model runs (`serve`, `enter`), `pm-operator` builds `pm-operator` with every verb a human runs at a terminal. The cut makes the host deny rule a whole binary: a bundle denies `pm-operator` to the model as one executable and keeps `pm-mcp` allowed, instead of sub-command rules inside one binary that every new verb would have to be sorted into. What the two share (the socket client, the on-demand start, the codecs, the direct file reads with the drift checks, the host-detection table) lives in `pm-api`, their only dependency.
* The web adapter is a package of `pm-mcp-server`, not a module and not a binary: it has no dependency the daemon lacks (the second HTTP server is the daemon's own Quarkus/Vert.x stack) and no build type of its own, and the device store, the pairing codes, and the device-secret check it needs already live in the daemon. Only the web app is a module (`pm-web-app`), because its build type differs (npm, resource JAR).
* Model work is cut by what each part depends on: the role sets and the task queue store live in `pm-core` with the other stores and configuration, because the client profiles that validate a role and the lock order of the queue are there; the model caller and the task protocol unit live in `pm-workflow`, because they are workflow logic over persisted records; the supervisor lives in `pm-runtime` beside the job runner, because it starts, signals, and observes processes, which neither of the two may do.
* `pm-runtime` is separated from `pm-mcp-server` by the framework boundary: whatever the daemon does without a Quarkus, CDI, or Vert.x type is library code with plain JUnit tests in a public repository, and the assembly is the wiring that remains. It is separated from `pm-core` because it starts processes and carries dependencies the foundation must not have (LSP4J, `commonmark`, `cui-http`), and from `pm-workflow` because the engine decides and the runtime executes: the engine reaches it only through the service interfaces of `pm-core`.
* The repositories are cut along the two seams the dependency rules already draw. `pm-mcp-clients` holds what depends on `pm-api` at most; its wire contract changes rarely, so the step from one repository to the next costs little there. `pm-mcp-core` keeps `pm-core`, `pm-workflow`, the providers, and `pm-runtime` together, because most changes of the engine cross these modules and a repository boundary between them would turn each into two releases. The parent is a repository of its own so that a change of the shared build configuration is one release every repository takes, and the documentation is one, because a document describes modules of all of them.
* The hypermedia state engine stays in `pm-workflow`: it renders the links of the current workflow state and cannot be separated from the interpreter; only the generic TOON encoder, which the providers also use, lives in `pm-core`.
