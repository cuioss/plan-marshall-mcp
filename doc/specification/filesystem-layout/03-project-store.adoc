[#machine-store]
== Per-Project Machine Store (`<PM_MCP_BASE>/projects/<project_id>/`)

All server-owned state of one project lives in its per-project machine store `<PM_MCP_BASE>/projects/<project_id>/`, where `<project_id>` is the project's enrolment identifier, the name of its enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (the same key that names project-scoped credentials, `PM-CRED-3`): assigned by the operator, unique per machine, and identical for the main checkout and all its worktrees. `pm-operator enrol` creates the store and records its `project_root` in `store.json` (link:../store-schemas/11-enrolment-store.adoc#project-store-identity[Store Schemas Specification, Project Store Identity]); `pm-operator release-project` leaves it readable (<<coexistence-lifecycle>>), and `pm-operator unenrol` leaves it untouched. Retention (`pm-operator sweep`) purges only aged items inside it, never the store as such (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification, Evidence-Based Removal Sweeps]); removing the store of an unenrolled project is an operator act outside `PM-MCP` (deleting its directory).

* *Never Moved*: A plan directory is created by the `start.create-scope` transaction of the plan bootstrap, built complete in the sibling temporary directory `plans/.init-<entry_id>/` and published by one atomic rename to `plans/<plan_id>/` (link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal], Writes outside the scope), and stays there until `archive-plan` moves it to `archive/<plan_id>/` (a rename within the same store directory) or `delete-plan` removes it. No worktree creation, worktree removal, or finalize step moves it.
* *Scope Directories*: The FSM state of a scope lives in its scope metadata directory: `plans/<plan_id>/mcp/`, `epics/<epic_id>/`, and `workspace/mcp/`. For an epic the metadata directory is `epics/<epic_id>/` itself, which holds nothing else; where the specifications name a scope's `mcp/` files (`mcp/status.json`, `mcp/digests.json`, `mcp/transaction-journal.json`), an epic's are these files in `epics/<epic_id>/`. Every scope's session log `sessions.jsonl` (entry rows only) lies directly in the scope directory (`plans/<plan_id>/`, `epics/<epic_id>/`, `workspace/`; link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]). The epic ledger (`epic.json`, queue, inbox, landings, spec) stays git-tracked in `.marshall/orchestrator/<epic_id>/` of the shared epic worktree; `epics/<epic_id>/` holds only what is not tracked. Store paths in a scope's transaction journal, its digest sidecar, and `pm-operator accept-edit` are relative to the scope directory of a plan or epic, and to the project store root `projects/<project_id>/` for the workspace scope, whose stores include `pending/<entry_id>.json`.
* *Locks*: The scope locks live in `locks/`, outside the directories they protect (link:../store-schemas/13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Store Schemas Specification, Transaction Locks]); the machine-wide store locks stay in `<PM_MCP_BASE>/locks/`.
* *Writers*: Only the runtime writes the store (operator verbs included, which reach it through the runtime's local API), always through the stores' transactions; jobs never write it, and the model reaches it only through server links and resources (`pm://plan/…`, `pm://epic/…`, `pm://workspace/…`), never through file paths.

[#workspace-home]
=== Workspace Home (`<PM_MCP_BASE>/projects/<project_id>/workspace/`)

Every enrolled project has exactly one workspace scope (`PM-ARCH-4`), addressed in a tool call as `plan_id: NO_PLAN` (link:../identifiers/01-general-rules-and-registry.adoc#id-no-plan[Identifier Registry, `NO_PLAN`]) and resolved from the `PM-MCP-Workspace` header of the request (link:../runtime-model.adoc[Runtime & Interaction Model Specification], Connection Metadata). Its home is `workspace/` in the project's machine store:

* *No Worktree, No Archive*: The workspace scope has no worktree and no archive; its home stays in the machine store for the life of the enrolment, and its rows older than `retention.workspace_rows_days` are purge candidates of `pm-operator sweep` (link:../timeouts/03-retention-host-config.adoc#retention-days[Timeouts & Budgets Specification]).
* *Contents*: `mcp/status.json` (the FSM state of the workflow the workspace hosts, `project-setup`, with the lesson maintenance sub-workflow `lessons` it calls, link:../domain-extensions.adoc[Domain Extensions Specification]; the bootstrap entities it hosts keep their state in their pending entry records in `pending/`), `screen-verdicts.jsonl` (the screen verdict cache of the workspace scope and its bootstrap entities), `sessions.jsonl` (the session log, appended only by `pm-mcp enter … workspace`), `mcp/digests.json` (the store digest sidecar), `change-ledger.jsonl` (the ledger rows of plan-less service calls, `pm_build` with `plan_id: NO_PLAN`), `findings.jsonl` (the findings of plan-less builds), `metrics.json` (the task and served-content rows of the workspace scope and the `worker_idle` rows of the project's warm workers, link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]), `questions.jsonl` (the question records of team-configuration setup choices), and `decisions.jsonl` with its facts snapshots `decision-facts/<facts_digest>.toon` (the decision records of the workspace scope, link:../store-schemas/18-decision-records.adoc#decision-record[Store Schemas Specification, Decision Record]). Build and job logs of the workspace scope lie in `jobs/` of the project's machine store, next to their records, and are addressed as `pm://workspace/builds/{job_id}/log`; `pm://workspace/status`, `pm://workspace/findings`, and `pm://workspace/questions` project the three stores (link:../mcp-tools.adoc[MCP Tools Specification]).
* *Lock*: Every write to the workspace home takes `locks/workspace.lock` of the project's machine store, the first lock of the one total order (workspace -> plan locks -> epic locks -> `epics-worktree` -> `lessons` -> `local-config` -> `derived-facts` -> `build-timings` -> `queue` -> machine store locks -> leaf locks, link:../store-schemas/13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Store Schemas Specification]), and runs as a journaled transaction (`mcp/transaction-journal.json`, link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal]).

[#role-sets]
=== Role Sets & Task Queue

* *Role Sets*: The effective role set of a project is built from three sets, each artifact replacing the artifact of the same name in a lower set as a whole (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]): the shipped set compiled into `pm-mcpd` (classpath `roles/<role>.json` with its qualification records `roles/qualification/<role>.json`), the machine set `<PM_MCP_BASE>/roles/`, and the project set `<PM_MCP_BASE>/projects/<project_id>/roles/`. Every qualification record the operator makes (setup grading, `pm-operator roles qualify`) lies in the project set, whichever set holds the artifact it qualifies; a record is looked up in the project set first, then in the set of the artifact, and the machine set holds no qualification records (link:../model-work/01-roles-and-configuration.adoc#qualification-records[Model Work Specification, Qualification Records]). The decision calibration record of a quorum declaration that the project's adjudication unit or the binary's default unit uses is `<PM_MCP_BASE>/projects/<project_id>/roles/qualification/decisions/<declaration-digest>.json`, one per declaration digest, so identical declarations share one record; the subdirectory keeps it apart from the role records `qualification/<role>.json`. The release ships the calibration of the default unit's quorum declarations as `roles/qualification/decisions/<declaration-digest>.json` on the classpath, and the machine set holds none (link:../model-work/10-decision-quorum.adoc#quorum-calibration[Model Work Specification, Quorum Calibration]). All three sets are operator-owned or compiled; no role, harness, or model pin is ever read from the repository (`PM-EXT-6`).
* *Skill Directories*: Extension skills (link:../mcp-tools/02-service-and-skill-tools.adoc#skill-extensions[MCP Tools Specification, Skill Extensions]) come from the machine skill directory `<PM_MCP_BASE>/skills/<name>/` (operator files) and the project skill directory `.marshall/skills/<name>/` of the enrolled project root (team-owned, git-tracked; never read from a plan worktree or the shared epic worktree), each skill one directory with its `SKILL.md` and supporting files; a project skill replaces a machine skill of the same name. The runtime reads both and writes neither.
* *Task Queue*: `queue/` of the per-project machine store holds one queue task record per task of every scope of the project and the session generation record; the job records of the project's workers lie in `jobs/` beside every other job record. Both are written only under `locks/queue.lock` (link:../store-schemas/16-task-queue.adoc#task-queue[Store Schemas Specification, Task Queue]).

[#archives]
=== Plan & Epic Archives
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-20[PM-WATCH-DISP-20], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-21[PM-WATCH-DISP-21], link:../../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-1[PM-WATCH-FS-1]_

Archived records keep their identity and stay readable by it (`PM-WF-13`) until a retention purge removes them:

* *Plan Archive*: `archive-plan` (step `1100`) moves the plan directory from `plans/<plan_id>/` to `archive/<plan_id>/` of the project's machine store. The path carries no date, so a `plan_id` present in the archive is never allocated again (link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]). Archived plans are purged only by the operator's retention setting (`retention.archived_plans_days` of the machine-local `local-config.json`, link:../timeouts/03-retention-host-config.adoc#retention-days[Timeouts & Budgets Specification]) through an evidence-based removal sweep (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification]). Archiving already lands machine-side, so there is no separate export: the archive never leaves the workstation (`PM-ARCH-2`).
* *Epic Archive*: When an epic ends, archived or aborted, the epic workflow (`epic.archive`) moves its directory inside the shared epic worktree from `.marshall/orchestrator/<epic_id>/` to `.marshall/archived-orchestrators/<epic_id>-<YY-MM-DD>/` (UTC archival date), commits the move (`epic.commit-ledger`, staging both roots), and lands it on the default branch through the epic landing before the epic reaches its terminal state (link:../state-catalogue/06-setup-epic-other.adoc#state-epic.archive[State Catalogue Specification, `epic.archive`]). The archived `epic.json` keeps `epic_id`; the dated suffix is never parsed for identity, and a title is never an identity. The epic archive is git-tracked and has no retention purge; the epic's non-tracked `epics/<epic_id>/` stays in the machine store, read-only, and is purged with the archived plans (`retention.archived_plans_days`) through the same evidence-based removal sweep.
* *Enumeration*: Every enumeration of epics (`pm_epics`, sibling-epic enumeration, re-grounding reads) covers the active root `.marshall/orchestrator/` and, where it reads history, the archived root, and reports per root `root`, `exists`, `listed`, `entries_scanned`, and `unreadable`, so "zero epics" is distinguishable from "root not scanned". Sibling-epic enumeration excludes every archived snapshot whose `epic_id` equals the enumerating epic's own.
* *Read-Only Access by ID*: An archived record answers read requests by its id; mutating calls are rejected with its terminal representation. A project reads only its own machine store; a plan reads another project's archived plans only under an operator access grant (`pm-operator grant-access`, link:../store-schemas/15-screening-and-grants.adoc#grant-record[Store Schemas Specification, Access Grant Record]; `PM-SEC-2`).

[#plan-worktree-resolution]
=== Plan & Worktree Resolution
_Implementation watch: link:../../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-2[PM-WATCH-FS-2], link:../../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-3[PM-WATCH-FS-3], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-1[PM-WATCH-STORE-1]_

[[project-resolution]]
*Project Resolution Rule*: One rule maps a working directory to a project. `pm-mcp enter` applies it to its current directory, and the runtime applies it to the directory named by the `PM-MCP-Workspace` header (link:../runtime-model/03-relay.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]); no other resolver exists:

. Run `git rev-parse --show-toplevel` and `git rev-parse --git-common-dir` in the directory and canonicalise both (`Path.toRealPath()`); outside a git work tree the directory is refused as `project_not_enrolled`.
. The main checkout is the directory that contains the common git directory (the parent of `--git-common-dir`). It must equal the `project_root` of exactly one enrolment file (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]); that file names the `project_id`. No match is refused as `project_not_enrolled`; a match of a tampered or unreadable enrolment file is refused with that file's reason.
. If the toplevel equals the main checkout, the directory was entered from `main_checkout`. If the toplevel is `<project_root>/.marshall/local/worktrees/<x>/`, it was entered from a `worktree` with `worktree_of: <x>` (a `plan_id`, or `_epics` for the shared epic worktree); a baseline scratch worktree (`baseline-<plan_id>-<sha12>`, xref:01-repository-workspace.adoc#worktree-lifecycle[Worktree Lifecycle]) is not an entry point and is refused as unenrolled. Any other toplevel (a git worktree outside `.marshall/local/worktrees/`, or a nested repository) is refused as unenrolled.

The resolved `project_id` and origin are recorded in the session row (`entered_from`, `worktree_of`, link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]); no session row records a path.

* *Deterministic Location*: A plan has exactly one directory, so its resolution has no candidates to arbitrate:
** The project is the one the verified `PM-MCP-Workspace` header resolves to by the project resolution rule above (for a worker, the project of its job record); the plan is looked up only in that project's machine store. The client profile of a call comes from the client the session's relay declares or from the worker's job record, never from the session log. The main checkout is the enrolled `project_root`; no scope record stores a path to it.
** If `plans/<plan_id>/mcp/status.json` exists, the plan is live. Its worktree is the recorded `worktree_path`, re-canonicalised and confinement-checked on every read; a recorded path that is not a live git worktree of `branch_name` is reconciled as described in xref:01-repository-workspace.adoc#worktree-lifecycle[Worktree Lifecycle], never followed.
** Otherwise, if `archive/<plan_id>/` exists, the plan is archived: `pm_state` returns its terminal representation (empty `links`, read-only), `pm://plan/{plan_id}/*` resources and the report and corpus readers serve the archived stores, and every mutating call is rejected.
** Otherwise the plan does not exist (`scope_not_found`).
* *Missing Is Not Empty*: Every path and record resolver distinguishes `absent` (the path does not exist) from an existing empty directory or file, and a metadata reader that finds nothing it can parse reports `unreadable`, never an empty record; neither is ever answered as a successful empty result.
* *Enumeration*: Every enumeration of live plans (`pm_plans`, dedup gates, sibling reads) lists the directories `plans/*` of the project's machine store that hold `mcp/status.json`, one directory (a temporary init directory `plans/.init-*` is never listed), and reports `could_not_look` for an unreadable store, distinct from an empty one.
* *Stateless Client Scope*: Neither the model nor the MCP client ever passes filesystem paths (`PM-ARCH-4`, `PM-SEC-2`). The client passes only `plan_id` (a plan id, or `NO_PLAN` for the workspace scope) or `epic_id`. The daemon dynamically resolves the canonical real path (`Path.toRealPath()`) and verifies confinement to the project's machine store or workspace before any file I/O.

[#coexistence-lifecycle]
== Coexistence with plan-marshall, Enrolment & Release (`PM-MIG-1`, `PM-MIG-2`, `PM-MIG-5`)
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-2[PM-WATCH-DISP-2]_

`PM-MCP` is built out in parallel to `plan-marshall` and shares no state tree with it:

1. *Separate State Trees (`PM-MIG-2`)*: `PM-MCP` owns `.marshall/` per repository and `<PM_MCP_BASE>` (with the per-project machine stores) per machine; `plan-marshall` keeps `.plan/` and `~/.plan-marshall/`. Both may be installed on one machine and used in the same repository. `PM-MCP` runs no `plan-marshall` script, holds no lock of its trees, and never reads or writes them, without exception; `plan-marshall` never reads or writes the `PM-MCP` trees.
2. *Clean Slate & Enrolment (`PM-MIG-1`, `PM-MIG-2`)*: `PM-MCP` imports nothing from `plan-marshall`: no configuration, lessons, `project-architecture/`, credentials, or learned build timeouts. `pm-operator enrol` creates the project's machine store and its workspace scope; the first run of the project setup workflow creates `.marshall/` and `.marshall/config/` with the copies of the default workflow units. Plans and epics of `plan-marshall` are never taken over; they finish in `plan-marshall`. The plan lifecycle is offered in an enrolled project once the lifecycle gate is open, a compiled constant of the release (`PM-MIG-4`); while it is closed, only in a project enrolled as a pilot (`pm-operator enrol --pilot`, link:../cli-and-security/02-credentials-and-operator.adoc#enrolment-lifecycle-release[CLI, Coordination & Security Specification, Lifecycle gate]).
3. *Release (`PM-MIG-5`)*: `pm-operator release-project` is the operator's switch-off for the `PM-MIG-5` triggers and stops offering the plan lifecycle for a project: it records `released_at` on the enrolment (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]) and aborts every non-terminal plan and epic of the project through the engine-owned abort (reason `project_released`); their branches and stores stay as the abort leaves them, readable in the project's machine store, and nothing is converted. A later `pm-operator enrol` of the project clears `released_at` (link:../cli-and-security/02-credentials-and-operator.adoc#enrolment-lifecycle-release[CLI, Coordination & Security Specification, Lifecycle gate]). The project can continue on `plan-marshall`, whose `.plan/` `PM-MCP` never touched.
