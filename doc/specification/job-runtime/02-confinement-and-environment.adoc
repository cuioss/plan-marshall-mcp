== Linux Filesystem Confinement (Landlock)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-20[PM-WATCH-JOB-20], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-21[PM-WATCH-JOB-21], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-28[PM-WATCH-JOB-28]_

On Linux (`PM-SEC-5`, `PM-TECH-4`), the `pm-exec` launcher (xref:01-pipeline-and-subprocesses.adoc#_process_group_creation_via_the_pm_exec_launcher[Process-Group Creation via the `pm-exec` Launcher]) confines every job before `execve`:

. `prctl(PR_SET_NO_NEW_PRIVS, 1)`: the job and all its descendants can never gain privileges (setuid/setgid binaries, file capabilities).
. A Landlock ruleset (Landlock ABI >= 2, Linux >= 5.19, applied via FFM) that grants read and execute access to the whole filesystem except `<PM_MCP_BASE>` (see *Read set* below) and write access only to:
** the job's own project root (which contains all of that project's worktrees under `.marshall/local/worktrees/` and its `.marshall/local/temp/`); never the root of another enrolled project and never the per-project machine store under `<PM_MCP_BASE>`,
** the build toolchain caches declared per project in the enrolment field `write_paths` (for example `~/.m2/repository`, `~/.gradle`, `~/.npm`, `~/.cache/pip`),
** the system temporary directory (`/tmp`; the JVM ignores `TMPDIR` for `java.io.tmpdir`) and device nodes under `/dev`; nothing the runtime reads back or trusts lies there,
** for a `ci` job of the CLI variant only, the configuration directory of its CLI (`gh` or `glab`: `GH_CONFIG_DIR` or `GLAB_CONFIG_DIR` as captured at enrolment, else the CLI's default location below `XDG_CONFIG_HOME`), which the CLI writes while it runs (token refresh, state files; <<_job_environment_pm_sec_5,Job Environment>>),
** for a `build` or `project_script` job, and a CLI-variant `git` job that runs repository hooks, the project's daemon store (<<build-daemons>>),
** for a worker (kind `llm`) only, the paths the client profile of its role's harness declares in `headless.writable_paths`: only the sub-paths below the harness home that the headless harness must write to run (its login or credential file, its caches, and its session directory), never the harness home as a whole and never a settings, command, or skill file that the bundle manifest manages; a profile rule forbids such an entry (link:../client-profiles/01-profile-schema.adoc#headless-writable-paths[Client Profiles Specification, Writable Paths]), and, for a harness whose profile declares a per-worker data home (`headless.data_home`), the worker's data directory `<PM_MCP_BASE>/run/jobs/<job_id>/data/` (<<worker-data-home>>). The concrete paths per harness are listed in the client profile; a path stays _(provisional)_ there until a writer worker has run in confinement with exactly the declared set.

The write set never contains `<PM_MCP_BASE>` (enrolments, machine configuration, credentials, logs, the machine stores, and the job-private directories under `run/jobs/` stay out of every job's write reach) apart from two places that hold nothing the runtime reads or trusts: the project's daemon store and a worker's own data directory. It never contains `~/.plan-marshall/`.

*Consequence for the harness configuration*: A worker cannot change the host configuration its harness loads: the settings, command, and skill files of the installed client bundle (permission rules, MCP server entries, entry commands, the shim skill) lie outside its write set, so a worker cannot weaken the deny rules or rewrite what the operator's next session loads. The restriction applies to the Landlock write set of workers only; the operator's own host session and the bundle installer, which runs inside `pm-mcpd`, are unaffected (`PM-SEC-5`).

*Read set*: The whole of `<PM_MCP_BASE>` is outside every job's read set: the runtime token in `run/` (link:../runtime-model/01-processes-and-transport.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]), the credential files, the enrolments and their HMAC sidecars, the machine stores, and the logs. The one exception is a worker's own job-private directory `<PM_MCP_BASE>/run/jobs/<job_id>/` (link:../filesystem-layout/02-machine-runtime.adoc#job-private-directories[Filesystem Layout Specification, Job-Private Directories]): the ruleset of that job, and of no other, grants read access to it and never write access, so nothing the daemon composes for a launch lies in a job-writable place; only its `data/` subdirectory, where one exists (<<worker-data-home>>), is also writable, and the project's daemon store (<<build-daemons>>) is readable and writable for the jobs that use it. Besides `<PM_MCP_BASE>`, the read set leaves out the user's session bus socket (<<session-bus>>) and, for a project without the container-engine opt-in, the container engine's socket paths (<<container-engine>>); whether leaving a socket out of the read set also refuses a `connect(2)` to it is subject to verification (<<pathname-sockets>>). The installation directory `<PM_MCP_HOME>` (the four binaries) lies apart from it and stays readable. Because Landlock rules only grant access, the runtime builds the read set as read and execute rules on `/` minus the path to `<PM_MCP_BASE>`: for each directory from `/` down to the parent of `<PM_MCP_BASE>`, a rule for every entry except the next directory on that path. The entries are enumerated at job start; an entry created later on that path (for example a new file directly in the home directory) is not readable by the job, which is accepted. A consequence of the same construction: a job can traverse the directories on that path and `stat` `<PM_MCP_BASE>` itself, but cannot list them (`ls /`, `ls $HOME`, and a listing of `<PM_MCP_BASE>` fail with `EACCES`), while every subtree below them stays readable; no build of the verification needed such a listing. On macOS and on Linux without Landlock a job can read `<PM_MCP_BASE>`, the token included, like any process of the user; this lies within the same-user boundary accepted for the operator channel (link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]). The runtime token and every other runtime secret are never passed in a job's argument vector or environment (<<Job Environment (`PM-SEC-5`)>>).

The ruleset is inherited across `fork`/`execve` and cannot be removed by the job. The runtime passes the read and write sets to the launcher as an argument vector computed from the project's enrolment file at job start, so enrolment changes take effect for the next job without restarting anything.

Properties and limits:

* *Warm build daemons*: A Gradle daemon or `mvnd` keeps the ruleset of the job that started it, and a job reaches only the daemons of its own project's daemon store (<<build-daemons>>). Enrolling a project needs no daemon restart.
* *Container engine*: Docker, Docker Compose, and Testcontainers hand their work to the container daemon, which runs outside every job's confinement; a project's jobs reach it only under the enrolment opt-in (<<container-engine>>).
* *Not covered*: Landlock does not restrict network address families and does not provide a private `/tmp`. `RestrictAddressFamilies` and `PrivateTmp` are therefore not enforced, and no loopback connection is restricted (a build tool reaches its daemon over loopback TCP). A worker needs the network for its harness's model provider; this is a declared exception of the job confinement (`PM-SEC-5`), not a gap.
* [[pathname-sockets]]*Unix sockets*: A confined worker's job relay connects to the runtime socket `<PM_MCP_BASE>/run/runtime.sock`, which lies outside its read set (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]): the filesystem rules of the measured ABI (8) do not govern a `connect(2)` to a pathname socket, and the worker's connection relies on that. For the same reason, leaving a socket path out of the read set (the session bus, the container engine) is not proven to refuse a connection and is not expected to on that ABI: it is verified on Linux per applied ABI, and until then the guard that holds is the withheld environment (<<session-bus>>, <<container-engine>>); the job record never claims more.
* *ABI Floor*: ABI 1 denies every cross-directory rename and link (`LANDLOCK_ACCESS_FS_REFER` arrives with ABI 2), which breaks Gradle, npm, and Java `Files.move` with `EXDEV`. On a kernel offering only ABI 1 the runtime applies no ruleset and records `confinement: partial(abi=1)`; it never reports a job as confined unless ABI >= 2 was applied. Rights that later ABIs add (for example `LANDLOCK_ACCESS_FS_TRUNCATE`, ABI 3) are handled as best effort, and the applied ABI is recorded in every job record (`landlock_abi`).
* *Unavailable Landlock*: On kernels without Landlock (older kernels, some WSL2 kernels), jobs run with `PR_SET_NO_NEW_PRIVS` only; the runtime records `confinement: unavailable` in each job record and in `pm-operator status`, and this is an accepted residual platform risk (`PM-SEC-5`).

[#build-daemons]
=== Build Daemons
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-34[PM-WATCH-JOB-34]_

A Landlock domain confines a process and its descendants, never the processes it talks to. A warm build daemon serves every client that finds it in its registry, with the ruleset of whichever process started it: a daemon started outside confinement writes wherever a confined client asks, and a daemon started under one write set fails the writes of a client with another. Whether a build uses a daemon is decided by the project's build configuration (for example `org.gradle.daemon` in `gradle.properties`) and the enrolled command templates (`mvnd` or `mvn`, `--no-daemon`), never by `PM-MCP`; where it does, the runtime keeps the daemons of one project and one write set apart from every other daemon (`PM-EXEC-4`):

* *Daemon store*: `<PM_MCP_BASE>/projects/<project_id>/daemons/<write_set_digest>/` (mode `0700`; link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), where `<write_set_digest>` is the first 16 hex characters of the SHA-256 over the job's sorted write set. The runtime creates the directory at job start. It holds only the registries and logs of the build daemons; the runtime reads nothing from it and trusts nothing in it. It is readable and writable for the `build` and `project_script` jobs of the project and for a CLI-variant `git` job that runs repository hooks, and for no other job.
* *How the build tools find it*: `mvnd` through `MVND_DAEMON_STORAGE=<store>/mvnd` in the job environment (<<_job_environment_pm_sec_5,Job Environment>>); Gradle through its daemon registry directory, which the server appends to the composed argument vector of a Gradle wrapper (`-Dorg.gradle.daemon.registry.base=<store>/gradle`; the flag-injecting `GRADLE_OPTS` is never exported) _(provisional until a confined Gradle build is verified with it)_. `GRADLE_USER_HOME` and the other declared toolchain caches (`write_paths`) stay shared between the projects and with the operator.
* *Effect*: A job finds only daemons that jobs of the same project started under the same write set, so every daemon carries exactly the ruleset of its clients, and a job never drives a daemon of the operator or of another project. A changed write set (an enrolment change) gives the next job a new store directory; the daemons of the old one end by their own idle timeout, and `pm-operator sweep` lists the store directories of other digests as removal candidates once no daemon process recorded in them lives (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification, Evidence-Based Removal Sweeps]).
* *Limit*: The store separates daemons by registry; it is no network confinement (Properties and limits, _Not covered_). The rule applies on every platform, so that a job never drives the operator's daemons where no confinement exists either.

[#container-engine]
=== Container Engine
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-35[PM-WATCH-JOB-35], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-36[PM-WATCH-JOB-36]_

Docker, Docker Compose, and Testcontainers hand their work to the container daemon over its socket. That daemon runs with root authority outside every job's Landlock domain, so a job that reaches the socket holds the authority of the Docker group: it can mount any host path into a container, `<PM_MCP_BASE>` with the runtime token and the credential store included. Access to the container engine is therefore an opt-in of the project's enrolment, the field `container_engine` (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]; `PM-EXEC-4`, `PM-SEC-5`):

* *Without the opt-in* (`container_engine: null`, the default): no job of the project receives `DOCKER_HOST`, `DOCKER_CONFIG`, or a `TESTCONTAINERS_*` variable, and the read set leaves out the engine's socket paths: `/var/run/docker.sock`, `/run/docker.sock`, `$XDG_RUNTIME_DIR/docker.sock`, and the path of a `unix:` `DOCKER_HOST` found at enrolment. A build that needs the engine fails with the tool's own error; the failure envelope names `pm-operator enrol --container-engine docker`.
* *With the opt-in* (`container_engine: "docker"`): the `build` jobs of the project receive the container variables as captured at enrolment, and the socket paths stay in the read set. Every process job of the project then records `confinement: partial(container_engine)` in place of `confined` (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]), and `pm-operator status` shows it for the project: the job's own writes stay confined, the engine's do not.
* *Operator confirmation*: The opt-in is set only by `pm-operator enrol --container-engine docker`, which tells the operator that the project's jobs then hold the authority of the Docker group, reaching every host path including `<PM_MCP_BASE>`, and requires the confirmation; the write is audited (`container_engine_enabled`; link:../cli-and-security/02-credentials-and-operator.adoc#enrolment-lifecycle-release[CLI, Coordination & Security Specification, Enrolment Lifecycle]). `docker` is the only engine value.

[#session-bus]
=== Session Bus
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-36[PM-WATCH-JOB-36]_

The Linux Secret Service has no per-application access control: every process of the user that reaches the session bus can read an unlocked collection, and with it the Token Lane secrets (link:../cli-and-security/02-credentials-and-operator.adoc#_os_keyring_backends_fallback_file_store[CLI, Coordination & Security Specification, OS Keyring Backends]). Every job is therefore cut off from the user's session bus:

* No job receives `DBUS_SESSION_BUS_ADDRESS` or `XDG_RUNTIME_DIR` (<<_job_environment_pm_sec_5,Job Environment>>), so no D-Bus client library of a job finds the bus.
* The read set leaves out the bus socket `$XDG_RUNTIME_DIR/bus` of the runtime's user (`/run/user/<uid>/bus`); whether that refuses a deliberate `connect(2)` is subject to verification (<<pathname-sockets>>).
* *Consequence for the CLI variant*: A CLI-variant `git` or `ci` job cannot use a login that lives only in the Secret Service (the `libsecret` git credential helper, the keyring storage of `gh` or `glab`). The tool then reports its own authentication error, and the readiness check of the integration names it (link:../cli-and-security/02-credentials-and-operator.adoc#cli-variant-credentials[CLI, Coordination & Security Specification, Credentials of the CLI Variant]): the operator keeps that login in the tool's file storage or an SSH agent, or selects the native variant.
* *Residual risk*: An unconfined process of the same user (the operator's shell, a model-driven shell of an interactive host session) reaches the bus like any desktop application; this is an accepted residual risk (`PM-SEC-5`). On macOS the Keychain's per-application access control guards the same secrets, and no session bus exists.

[#worker-data-home]
=== Per-Worker Data Home
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-60[PM-WATCH-DISP-60]_

A harness that keeps its local state in one per-user store shares it between all its processes: a stalled worker that holds the write lock of that store blocks every other worker of the harness and the operator's own interactive sessions of it. A client profile therefore declares a per-worker data home for such a harness (`headless.data_home`, link:../client-profiles/01-profile-schema.adoc#headless-data-home[Client Profiles Specification, Per-Worker Data Home]; `opencode`: `XDG_DATA_HOME`):

* The runtime creates `<PM_MCP_BASE>/run/jobs/<job_id>/data/` (mode `0700`) with the job-private directory and sets the declared variable to it in the worker's environment.
* It copies the harness's own login file (the profile's `data_home.login_file`, relative to the operator's data home) into the same relative place below it with mode `0600`. The file is copied as bytes: the runtime never parses it, logs it, or keeps it anywhere else, and `PM-MCP` still stores and exports no harness authentication (`PM-EXEC-1`). A harness without a login file fails its worker's start like every harness that is not logged in.
* The directory is readable and writable for that worker alone, the only job-writable place below `run/jobs/`; the runtime reads nothing back from it.
* It is removed with the job-private directory after the job's fate is recorded, the login copy included; a login the harness refreshed inside it is not copied back. A worker of such a harness therefore leaves no session residue.

The rule applies on every platform. With it, the write set of such a worker needs no path of the harness's shared data directory (`headless.writable_paths`).

== Job Environment (`PM-SEC-5`)

The runtime builds every job environment from scratch; nothing is inherited from the runtime's own environment, which belongs to whichever `pm-mcp` or `pm-operator` command or service manager started it (link:../runtime-model.adoc[Runtime & Interaction Model Specification]). Each variable has one provenance: `enrolment` values are captured by the operator CLI at enrolment into the project's `build_environment` (enrolment file `enrolments/<project_id>.json`) and refreshed only by re-enrolment; `runtime` values are computed at job start. The harness enrolment (`pm-operator enrol-harness`) captures no environment value.

|`PATH`
|all
|runtime
|Directories of the enrolled host tools and interpreters only; the runtime itself never searches it (`PM-EXEC-1`).

|`HOME`, `USER`, `LOGNAME`
|all
|runtime
|The runtime user's values.

|`LANG`, `LC_ALL`, `LC_*`
|all
|enrolment
|As captured; `LC_ALL=C.UTF-8` when none was captured.

|`TMPDIR`
|all
|runtime

|`JAVA_HOME`, `GRADLE_USER_HOME`

|enrolment
|`JAVA_HOME` and `GRADLE_USER_HOME` as captured; `MAVEN_OPTS`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, and `GRADLE_OPTS` are never passed, since they inject flags outside the pinned build configuration (`PM-EXEC-1`).

|`MVND_DAEMON_STORAGE`

|===

*`llm` jobs (workers)*: A worker receives the rows above that name all job types plus:

The runtime token is never among them, and no variable of the operator's environment reaches a worker; in particular the host session markers of the host-detection table (link:../client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Client Profiles Specification, Host Integration Table]) are never passed, so a harness the runtime starts never inherits the identity of the operator's host. `PM-MCP` never stores or exports a harness's authentication: the harness CLI authenticates with its own login, cached under its home (`HOME`; its login or credential file is one of the profile's `headless.writable_paths`, <<_linux_filesystem_confinement_landlock,write set>>, or is copied into the worker's data home, <<worker-data-home>>). A harness that is not logged in exits before its first call, which the supervisor treats as a start failure (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]) and whose job outcome is derived like any other (xref:01-pipeline-and-subprocesses.adoc#outcome-derivation[Outcome Derivation]); no credential of an integration and no `PM-MCP` credential entry ever stands in for the login.

A variable not listed is not passed.

*`git` and `ci` jobs*: These jobs exist only for the CLI variant of an integration (`PM-EXEC-5`); a native-variant operation runs in process and has no job environment. The CLI variant authenticates with the operator's ambient credentials by design (link:../cli-and-security/02-credentials-and-operator.adoc#cli-variant-credentials[CLI, Coordination & Security Specification, Credentials of the CLI Variant]); its jobs receive the rows above that name all job types plus:

The credential row and the session-bus row apply unchanged (a login kept only in the Secret Service is out of reach, <<session-bus>>), and additionally `GH_ENTERPRISE_TOKEN`, `GITLAB_PRIVATE_TOKEN`, `GIT_ASKPASS`, `SSH_ASKPASS`, and `GIT_CONFIG_PARAMETERS`/`GIT_CONFIG_COUNT` are never passed: no agent token reaches a CLI job, neither as a variable nor through an askpass or credential helper served by a binary of the release.

*Write paths of CLI-variant jobs*: The Landlock write set of a `ci` job additionally contains the `gh` or `glab` configuration directory (token refresh rewrites `hosts.yml`). `~/.ssh/known_hosts` stays read-only for every job: an unknown host key fails the job and is never accepted (no `accept-new`). Repository hooks and signing programs are started by `git` inside the CLI `git` job and inherit its environment, write set, and budget (the hook-running `git` class, link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]); there is no separate hook or filter job type.

[#canonical-build-verbs]
== Canonical Build Verb Set

This is the one closed set of canonical build verbs of PM-MCP. `pm_build.command` (link:../mcp-tools/02-service-and-skill-tools.adoc#_pm_build_enrolled_build_execution[MCP Tools Specification]), `PM-TOOL-2`, the canonical argument templates of link:../domain-extensions.adoc[Domain Extensions Specification] (Tier 2), the budget keys of link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification], and the link:../identifiers/02-registry-stores-to-web.adoc#id-build-verb[Identifier Registry] use exactly this set. It equals `plan-marshall`'s `ALL_CANONICAL_COMMANDS` (`script-shared/scripts/extension/_extension_constants.py`, verified at plan-marshall commit `88fcfc9ef`; re-verify before implementing), in the same order:

[cols="1,2,3"]
|===
|Verb |`plan-marshall` constant |Meaning

|`clean` |`CMD_CLEAN` |Remove build output.
|`compile` |`CMD_COMPILE` |Compile production sources (build class `compile`).
|`test-compile` |`CMD_TEST_COMPILE` |Compile test sources.
|`module-tests` |`CMD_MODULE_TESTS` |Run the unit tests (build class `module-tests`).
|`integration-tests` |`CMD_INTEGRATION_TESTS` |Run the integration tests.
|`e2e` |`CMD_E2E` |Run the end-to-end tests.
|`coverage` |`CMD_COVERAGE` |Run the tests with coverage measurement and thresholds (xref:03-parsers-and-gates.adoc#_native_coverage_report_parsers[Native Coverage Report Parsers]).
|`benchmark` |`CMD_BENCHMARK` |Run the benchmarks; never a gate.
|`quality-gate` |`CMD_QUALITY_GATE` |Static checks, formatting, and lint.
|`arch-gate` |`CMD_ARCH_GATE` |Architecture rules through a domain-owned engine.
|`verify` |`CMD_VERIFY` |Full verification including tests (build class `verify`).
|`install` |`CMD_INSTALL` |Install the artifacts into the local repository (a toolchain cache of the enrolment's `write_paths`).
|`clean-install` |`CMD_CLEAN_INSTALL` |`clean` followed by `install`.
|`package` |`CMD_PACKAGE` |Package the artifacts.
|===

* *Scope is not a verb*: Every verb runs whole-tree without `module` and module-scoped with it, through the optional module-argument group of its template (link:../domain-extensions/06-configuration.adoc#module-argument-group[Domain Extensions Specification, Optional Module-Argument Group]); gate scope follows from `module` alone (xref:03-parsers-and-gates.adoc#_gate_honesty_verification[Gate Honesty Verification], Gate Coverage).
* *Resolution*: A verb resolves through the project's enrolled template or the domain's compiled default template; a verb without either is refused (`refused`, reason `verb_not_supported`), never approximated by another verb.
* *Deliberate deviations*: None against `plan-marshall`'s set. PM-MCP adds no verb of its own: module tests run as `module-tests`, and format checking is part of `quality-gate`.
