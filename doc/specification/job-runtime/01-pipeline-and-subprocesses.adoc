== Verify-Not-Resolve Execution Pipeline

Before spawning any subprocess, the runtime reads the enrolment file of the job's project, `<PM_MCP_BASE>/enrolments/<project_id>.json` (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]), verifies its integrity (<<enrolment-integrity>>), and then validates the job request through a deterministic three-stage verification pipeline (`PM-EXEC-1`..`PM-EXEC-3`, `PM-SEC-2`):

[source,text]
----
  Job Request (Scope, Executable, Argv, WorkingDir)
                       │
                       ▼
       ┌───────────────────────────────┐
       │ 0. Enrolment HMAC Check       │ ──► Mismatch: REFUSED (enrolment_tampered)
       └───────────────┬───────────────┘
                       │ Valid (HMAC matches file content)
                       ▼
       ┌───────────────────────────────┐
       │ 1. Working Directory Check    │ ──► Mismatch: REFUSED (outside enrolled tree)
       └───────────────┬───────────────┘
                       │ Valid (Root or linked worktree)
                       ▼
       ┌───────────────────────────────┐
       │ 2. Executable & Digest Check  │ ──► Mismatch: REFUSED (unpinned tool / digest drift)
       └───────────────┬───────────────┘
                       │ Valid (Exact path & SHA-256 match)
                       ▼
       ┌───────────────────────────────┐
       │ 3. Argument Schema Validation │ ──► Mismatch: REFUSED (illegal flag / unquoted space)
       └───────────────┬───────────────┘
                       │ Valid
                       ▼
             Spawn Subprocess (Direct)
----

* *Working Directory Confinement (`PM-SEC-2`)*: The working directory must resolve canonically via `Path.toRealPath()` to the project's enrolled root or a live linked git worktree verified through the git contract's `worktree-list` operation, served by the project's configured variant. Arbitrary paths or symlink escapes are rejected with outcome `refused` and reason `path_traversal_rejected`.
* *Working Directory Selection (`PM-ARCH-5`)*: The working directory is derived from the plan's persisted worktree presence at job start, never from the phase: jobs for plans whose `worktree_path` is set run in the plan's worktree root; jobs for plans whose `worktree_path` is `null` and plan-less jobs run in the main checkout (link:../filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). A job that removes a worktree never runs with a working directory inside that worktree. A worker's working directory is fixed at its launch (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]). The exceptions are the `zero_tool` workers (the screener and the grading judge `judge`) and the graded workers of a qualification item whose corpus context travels in-band: each runs in the empty subdirectory `cwd/` of its job-private directory `<PM_MCP_BASE>/run/jobs/<job_id>/`, which it can read and never write (link:../model-work/01-roles-and-configuration.adoc#grading[Model Work Specification, Grading]); no other job's working directory lies outside the enrolled tree.
* *Verify-Not-Resolve Executable Resolution (`PM-EXEC-1`, `PM-EXEC-2`, `PM-EXEC-3`, `PM-EXT-5`)*: The runtime *never* searches the system `PATH`:
** *Wrapper Jobs (`mvnw`, `gradlew`, `pw`)*: The wrapper must be committed at the root of the tree, must match an enrolled wrapper name in the project's enrolment file, and its SHA-256 content hash must match the enrolled digest. The digest check also covers every file that decides which tool runs and with which flags, recorded at enrolment as the wrapper's `pinned_files`: the wrapper jar and wrapper properties (`gradle/wrapper/gradle-wrapper.jar`, `gradle/wrapper/gradle-wrapper.properties`, `.mvn/wrapper/maven-wrapper.properties`) and the repository build configuration (`.mvn/maven.config`, `.mvn/jvm.config`, `gradle.properties`) where present; a pinned file that appears after enrolment counts as changed. Enrolment of `mvnw` or `gradlew` requires `distributionSha256Sum` in the wrapper properties, so the downloaded distribution is pinned as well. A mismatch refuses the job with `refused`, reason `build_config_changed`, the changed paths, and the `pm-operator enrol` command that re-baselines them (`PM-EXEC-2`). The interpreter-based wrapper `pw` is never started through its `#!/usr/bin/env` shebang: the runtime invokes the enrolled interpreter host tool (the wrapper's `interpreter`) with the wrapper as its first argument. What a wrapper runs is decided by the enrolled canonical template of the build verb (`build.canonical_templates`) or its compiled default; there is no per-wrapper goal allowlist.
** *Host Tools (`git`, `gh`, `glab`, `python3`, `npm`, `npx`)*: The runtime invokes the exact absolute `executable_path` recorded in the project's enrolment file after verifying that the file's current SHA-256 matches the enrolment record.
** *Worker Jobs (`llm`)*: The harness executable of a worker (`claude`, `codex`, `opencode`) is enrolled per machine by `pm-operator enrol-harness <client>`, which records its absolute path, the version its version probe reports, and its SHA-256, and nothing else: no environment value and no credential (link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]). The runtime invokes exactly that path, never a `PATH` lookup. Before every worker spawn it verifies the HMAC sidecar of `harnesses.json`; a mismatch refuses the job (`refused`, reason `harness_tampered`, a `security` audit record `enrolment_tampered`). Harnesses update themselves, so a digest that differs from the record is accepted only when the version probe of the file reports a version within the supported version range of the harness's client profile: the new digest and version are recorded and audited. A version outside the range, or a probe that fails, refuses the job with `harness_version_unsupported`. A refused spawn is no model call and no question: it counts as a start failure of the role on that harness (link:../model-work/04-worker-launch.adoc#harness-selection[Model Work Specification, Launch Refusals]); once the start-failure guard holds, the supervisor starts no further worker of the role on that harness, reports the reason and the re-baselining command `pm-operator enrol-harness <client>` to the operator (`pm-operator status`, the web app, the audit log), and the role's tasks close `lost` with `role_unavailable` and take their conservative fallback (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]). There is no pause and no `accept-edit` form for it. The argument vector is the one the server composed from the role artifact and the profile's `headless` template (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]), validated like every other.
** *Project Script Jobs (`project_script`, `PM-EXT-5`)*: Both the script file (`script_path`) and its interpreter (`interpreter`, an enrolled host tool) must match their enrolled SHA-256 digests (`project_scripts.<project_script_id>` of the project's enrolment file), the job's use must match the script's `binding` (`worker_kind` and `target`), and the job arguments must validate against the script's enrolled `argument_schema`; the budget is the script's `max_timeout_seconds`. There is no job kind for `plan-marshall` scripts.
* *Argument Schema Validation (`PM-EXEC-1`, `PM-EXEC-5`)*: The argument vector (`argv`) is checked against a closed allowlist schema per tool type. Shell meta-characters (`|`, `;`, `&`, `$`, `` ` ``, `>`, `<`) are never evaluated: the runtime spawns every job without a shell, and the `#!/bin/sh` wrappers `mvnw` and `gradlew` receive the validated vector as positional arguments. This validation guards only against injection through link parameters; flags that come from repository content (the build configuration files above) are governed by their enrolled digests, not by the argument schema.

[#enrolment-integrity]
=== Enrolment Integrity Check (`PM-EXEC-2`)

Step 0 of the pipeline verifies the HMAC-SHA-256 sidecar `<PM_MCP_BASE>/enrolments/<project_id>.json.hmac` against the current enrolment file of the job's project (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]) before every verify-not-resolve check, in addition to the check in the project's recovery after a runtime start. A failed check blocks only this project's jobs. The runtime (`pm-mcpd`) computes and writes every HMAC with a key that only it reads. Key handling, operator re-baselining, and the accepted residual risks (hosts without a keyring; a same-user process that re-baselines through the operator endpoint with the runtime token) are specified in link:../cli-and-security/02-credentials-and-operator.adoc#enrolment-integrity[CLI, Coordination & Security Specification, Enrolment Integrity].

* *Mismatch*: The job is refused with reason `enrolment_tampered` (outcome `refused`) and a `security` record is appended to `audit.jsonl`; the runtime never repairs or re-signs the file and trusts no enrolment until the operator re-baselines it through the operator CLI.
* *Write Protection*: Jobs can neither read nor write `<PM_MCP_BASE>` on Linux (xref:02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Linux Filesystem Confinement (Landlock)]); the HMAC is the control against writers that are not jobs, such as a model-driven host shell.

== Subprocess Lifecycle & Process-Group Isolation

Every job runs as a direct child of the always-on runtime (`pm-mcpd`), started through the launcher `pm-exec`, independent of any host connection (link:../runtime-model.adoc[Runtime & Interaction Model Specification]), inside its own isolated operating system process group (`PM-EXEC-4`, `PM-EXEC-5`, `PM-IMPL-1`).

*Job identity and files*: A job's `job_id` (link:../identifiers/01-general-rules-and-registry.adoc#id-job-id[Identifier Registry]) is its kind prefix (`b` build, `c` ci, `g` git, `p` project script, `l` worker of kind `llm`) and 16 random hex digits (64 bits); a review-bot poll is a `ci` job with the budget key `ci:<operation>`, never a kind of its own; at creation it is checked against the project's existing job records and drawn again on a collision. The job record (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]) and the job log lie side by side at `<PM_MCP_BASE>/projects/<project_id>/jobs/<job_id>.json` and `<job_id>.log`. Language servers are no jobs (<<_warm_language_server_pool_orthogonal_service_access_pm_svc_2_pm_svc_4_pm_tool_2,Warm Language Server Pool>>).

[#job-status]
*Job status*: A job record's status is `queued`, `running`, `refused`, or `ended` (with its fate, <<outcome-derivation>>). `queued` is a real wait before spawn: the job waits for a slot of its machine lease store, a build slot for a `build` job or a model slot for a worker (link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]); it has no process, no `pid`, and no running budget, and a queued job is cancelled or refused without any signal. Admission moves it to `running` in the transaction that takes the slot; a job that needs no slot is `running` from its creation. While the runtime drains, no job is admitted: a job a transition creates then is recorded `queued`, whatever its kind, and settled `killed` at exit (row 4 of <<outcome-derivation>>; link:../runtime-model/02-startup-recovery-drain.adoc#_drain_stop_upgrade[Runtime & Interaction Model Specification, Drain, Stop & Upgrade]).

[#job-wall-times]
*Wall times*: The settling transaction records two wall times on the job record: the job's own, from `spawned_at` to `ended_at` (queued time lies outside it), and the child's, `child_wall_ms`, from the child process's start instant (`process_started_at`, reported by the launcher) to the exit the runtime observes. Their difference is the runtime's overhead on the job (launcher, confinement, pipeline, and settling), the source of the build-overhead trigger of `PM-MIG-5` (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#migration-trigger-evaluation[Phase Workflows Specification, Migration Trigger Evaluation]). A job settled without an observed exit (`killed` by recovery, `refused`) and an in-process operation record `child_wall_ms: null`.

=== Process-Group Creation via the `pm-exec` Launcher
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-2[PM-WATCH-JOB-2]_

Java's `ProcessBuilder` cannot place a child into a new process group or session (`setpgid`/`setsid`); a child started directly would inherit the runtime's own process group, and signalling that group would hit the runtime and every other job. The runtime therefore starts every job through the launcher `pm-exec`, a separate tiny native binary of the release (plain GraalVM native image with FFM, no Quarkus, module `pm-modules/pm-exec`), started by its path in the runtime's own installation directory `<PM_MCP_HOME>/bin/`, never through `PATH`:

. The runtime verifies the job (verify-not-resolve, `PM-EXEC-2`) and starts `<PM_MCP_HOME>/bin/pm-exec -- <verified absolute executable> <args…>` with `ProcessBuilder`, keeping all of its I/O handling (pipes, in-memory `stdin` payloads, log redirection, exit codes).
. The launcher calls `setpgid(0, 0)` via FFM, so its PID becomes the process-group ID, and then replaces itself with the target via `execve` (never `execvp`: no `PATH` search, `PM-EXEC-1`). The job's PID recorded by the runtime is therefore both the job PID and its process-group ID.
. [[launch-report]]*Launch report*: Right before `execve` the launcher writes exactly one launch report to `stderr`: a single line holding one JSON object (its PID after `setpgid`, the process start instant `process_started_at`, the applied `confinement`, and `landlock_abi`). `stderr` is the only channel the launcher has (it receives the job's output redirection and nothing else), so the report is the first line of the job log: the runtime parses it, records its fields in the job record (step 6 of <<Process Termination & Cancellation Protocol>>), and strips it from the job log, so no output parser, no log resource, and no excerpt ever contains it. A missing or unparseable report means the launcher failed before `execve` (its exit codes: `64` usage, `126` confinement could not be applied, `127` `execve` failed) and the job's outcome is derived from that exit (<<outcome-derivation>>).
. Cancellation and timeouts signal exactly that group (`kill(-pid, …)`). Warm build daemons that detach themselves into their own session (Gradle daemon, `mvnd`) are intentionally not affected (`PM-EXEC-4`).
. `pm-exec` is not a user command and not a verb of `pm-mcp` or `pm-operator`; only the runtime starts it: it accepts only an absolute executable path, an argument vector, and (on Linux) the confinement sets, performs no verification of its own, reads no file of `<PM_MCP_BASE>`, and holds no secret.

*Alternative for later implementations (macOS only)*: Start jobs directly via FFM `posix_spawn` with `POSIX_SPAWN_SETPGROUP` (the mechanism already used for the detached runtime start, link:../runtime-model.adoc[Runtime & Interaction Model Specification]). This removes the extra `execve` hop but replaces `ProcessBuilder` completely: pipes, `stdin` streaming, output capture, and exit-status reaping (`waitpid`) must then be implemented on FFM as well. The job contract (process group = job PID, outcome classification) is identical, so the runtime can switch implementations without changing any other specification. On Linux the `pm-exec` launcher (or an equivalent restricted spawner thread) stays mandatory: `PR_SET_NO_NEW_PRIVS` and the Landlock ruleset must be applied between `fork` and `execve`, and `posix_spawn` offers no hook for that.

[source,java]
----
List<String> argv = new ArrayList<>(List.of(pmExecBinary, "--")); // <PM_MCP_HOME>/bin/pm-exec
argv.addAll(verifiedArgv); // verifiedArgv.get(0) is the verified absolute executable path
ProcessBuilder pb = new ProcessBuilder(argv);
pb.directory(verifiedWorkingDir.toFile());
// Environment sanitization
pb.environment().clear();
pb.environment().putAll(sanitizedEnvAllowlist);
// Standard input handling: /dev/null by default, or in-memory pipe for multi-line payloads
if (stdinPayload.isPresent()) {
    pb.redirectInput(ProcessBuilder.Redirect.PIPE);
} else {
    pb.redirectInput(ProcessBuilder.Redirect.from(new File("/dev/null")));
}
// Direct output redirection to job log file (never inherits the runtime's stdin/stdout)
pb.redirectOutput(jobLogPath.toFile());
pb.redirectErrorStream(true);
Process process = pb.start();
if (stdinPayload.isPresent()) {
    byte[] bytes = stdinPayload.get();
    Thread.startVirtualThread(() -> {
        try (OutputStream out = process.getOutputStream()) {
            out.write(bytes);
            out.flush();
        } catch (IOException ignored) {
            // Child process exited early; handled by exit-code & outcome classifier
        }
    });
}
----

=== In-Memory `stdin` Streaming (`PM-EXEC-5`)

When a workflow primitive served by the CLI variant (link:../cli-and-security/02-credentials-and-operator.adoc#cli-variant-credentials[CLI, Coordination & Security Specification, Credentials of the CLI Variant]) passes multi-line text to an enrolled `git` or `ci` tool, `JobRuntime` supplies the validated UTF-8 bytes in `stdinPayload`. The native variant runs in process and passes the same text as an in-memory request payload; it has no job and no `stdin`.

The `stdin` forms of the CLI variant are closed:

* `git`: `git -C <tree> commit -F -`.
* `gh`: `gh pr create|edit|comment --body-file -`, `gh issue create|comment --body-file -`, and `gh api graphql --input -` for the fixed GraphQL documents.
* `glab`: the operations whose `glab` subcommand has no confirmed `stdin` form (`mr create`, `mr note`, `issue note`) are sent as `glab api <endpoint> --input -` with a server-composed JSON body. Until the Milestone 0 verification of these forms passes, these operations return `unsupported_by_variant{reason: no_stdin_form}` in the CLI variant, and the `gitlab` integration needs the native variant for them; free text is never moved to the argument vector or a file to work around it.

For every form:

* *Zero Temp or Scratch Files*: The server never writes commit messages or PR/issue bodies to a scratch file, in the worktree or in `/tmp/`.
* *Zero Shell / Argv Exposure*: Multi-line text is never placed in `verifiedArgv`, avoiding OS `ARG_MAX` limits and `ps` command-line inspection.
* *Deterministic EOF*: The virtual writer thread closes `process.getOutputStream()` immediately after flushing `bytes`, guaranteeing that `git` and `gh` see EOF and never hang waiting for interactive input.

=== Process Termination & Cancellation Protocol
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-3[PM-WATCH-JOB-3], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-22[PM-WATCH-JOB-22]_

When a job exceeds its allocated budget (`PM-EXEC-4`, link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]), when the engine cancels it (a cancel is an engine event, never a model link), when the supervisor ends a worker (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]), or when the runtime drains:

1. *SIGTERM Escalation*: The runtime sends `SIGTERM` to the job's process group (`kill(-pgid, SIGTERM)` via Java FFM, `PM-TECH-4`), whose ID equals the job PID (see <<Process-Group Creation via the `pm-exec` Launcher>>).
2. *Grace Period*: The runtime (`pm-mcpd`) waits the termination grace period (link:../timeouts/01-job-budgets-and-waits.adoc#grace-period[Timeouts & Budgets Specification]) for all processes in the group to exit cleanly.
3. *SIGKILL Cleanup*: If any process of the group remains alive after the grace period, the runtime issues `kill(-pgid, SIGKILL)`. Steps 1–3 address the group, never only its leader: they run to completion even when the leader has already exited and only descendants remain.
4. *Cancel Before the Group Exists*: The launcher calls `setpgid` after it starts, so a cancel (or budget expiry, or drain) that reaches a job in that window gets `ESRCH` from `kill(-pgid, …)`. The runtime then signals the PID directly (`kill(pid, SIGTERM)`) and retries against the group after the short bounded delay of link:../timeouts/01-job-budgets-and-waits.adoc#cancel-group-retry[Timeouts & Budgets Specification, Cancel-Before-Group Retry], and records `cancel_before_group: true` in the job record.
5. *Outcome*: The outcome of a terminated job is derived by <<outcome-derivation>>; relay termination never affects a job. For a worker, the fence follows step 3: its job token is revoked, its generation fenced, and its lease released at once. A `timed_out` job is `no_verdict` in every roll-up (link:../timeouts/01-job-budgets-and-waits.adoc#no-verdict-rule[Timeouts & Budgets Specification, Timed-Out Outcomes Are No-Verdict]).
6. *Live Orphans after a Runtime Crash*: The job record is written before spawn and, mandatorily, replaced right after spawn with the job PID (which is its process-group ID) and the process start instant (`pid`, `process_started_at`); the launcher reports its PID after `setpgid` and before `execve` in its launch report on `stderr` (<<launch-report>>), and the job counts as running only once that replace is persisted. In the project's recovery after the next runtime start, every record left `queued` is settled `status: ended`, `fate: killed` without signalling anything (it never started), and every record left `running` is settled `killed` by the first matching rule, and it is never adopted or re-executed (link:../runtime-model/02-startup-recovery-drain.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery]): (a) its `execution` is `in_process` (<<in-process-operations>>): the operation died with the previous runtime, nothing is signalled, and no orphan note is written; (b) its `spawned_at` lies before the system boot time: the process cannot have survived the reboot, and nothing is signalled; (c) its `pid` is `null` (the runtime ended between spawn and the post-spawn replace): nothing is signalled, and the audit record notes `orphan unidentifiable`; (d) otherwise the runtime probes the process group with `kill(-pgid, 0)`: a group exists while any of its members lives, and a PGID cannot be reused while its group is alive within one boot, so a live group whose ID equals the recorded PGID is that job's group, even when the leader (whose start instant was recorded) has exited. Such a group is terminated with steps 1–3; a group that no longer exists needs no termination.

[#in-process-operations]
=== In-Process Operations (Native Variant)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-3[PM-WATCH-JOB-3], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-32[PM-WATCH-JOB-32]_

A `git` or `ci` operation of the native variant (JGit, provider HTTP clients) runs inside the runtime: no argument vector, no environment, no process group, no Landlock ruleset, and no `pm-exec` launcher exist for it. It is still a job of the runtime, so waits, cancellation, metrics, and recovery treat it like any other job:

* *Job Record*: Every in-process operation gets a job record of its kind (`git` or `ci`, job id prefix `g` or `c`) with `execution: in_process`, its budget key `<kind>:<operation>`, `budget_seconds`, and `budget_derivation`; the process fields (`argv_digest`, `pid`, `process_started_at`, `spawned_at`, `exit_code`, `signal`) are `null` and `confinement` is `not_applicable` (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]). It writes no job log file.
* *Budget & Cancellation*: The operation runs under the budget of its operation class; at budget expiry, on a cancel by the engine, and at the expiry of the drain timeout it is cancelled cooperatively (JGit `ProgressMonitor`, interruption of the HTTP exchange), every HTTP request carries the compiled per-request connect and read timeout, and an operation that does not return within the grace period is abandoned with its late result discarded (link:../timeouts/01-job-budgets-and-waits.adoc#in-process-operations[Timeouts & Budgets Specification, In-Process Operations]). A partial result is never used.
* *Outcome*: Rows 1 to 4 of <<outcome-derivation>> apply unchanged (`refused` before the operation starts, `cancelled`, `timed_out` as `no_verdict`, `killed` at drain or for a record left `running` by a previous runtime instance; nothing is probed or adopted). Otherwise rows 11 to 13 decide: `succeeded` for a domain outcome of its closed contract enumeration, `failed` for a transport outcome, `indeterminate` for an end outside its contract. A provider rate limit (`rate_limited{reset_at}`, or a `Retry-After`) is neither a failure nor a timeout: the operation is re-issued after the stated instant, the time until then does not count against its budget, and the wait records `provider_rate_limit` (<<_bounded_long_poll_progress_reset_waiting_primitives_pm_wf_8_pm_impl_4>>).

=== Bounded Long-Poll & Progress-Reset Waiting Primitives (`PM-WF-8`, `PM-IMPL-4`)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-5[PM-WATCH-JOB-5], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-6[PM-WATCH-JOB-6], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-19[PM-WATCH-JOB-19], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-30[PM-WATCH-JOB-30]_

Every job is awaited by the engine, never by a model: a job state advances on the job's completion as an engine event, a composite wait settles or short-circuits on the events of its members, and a cancel terminates the job's process group (<<Process Termination & Cancellation Protocol>>). No representation offers a link to wait for or cancel a job; the plan representation shows the job's progress as a view (`PM-WF-8`).

Two waiting primitives serve the only calls a model holds open: a worker's `pm_wait` (a consultation's wait included; semantics in link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]) and a running `pm_build` (`PM-SVC-1`, `PM-SVC-4`). The server selects between them without model involvement:

* *Bounded Wait*: The server holds the call open for at most the bounded wait window of the calling connection's client profile (`connection.bounded_wait_seconds`; for a worker the profile of its role's harness; value and bounds in link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Timeouts & Budgets Specification, Bounded Wait Window]). A `pm_wait` returns an offered task, `wait_again`, or `end` within the window; a `pm_build` returns its result once the build completes, otherwise the running build with its `job_id` to continue the call with. Neither ever fails with an MCP transport timeout.
* *Progress Wait*: When the profile declares `progress_resets_timeout: true` and the request supplies a `_meta.progressToken`, the runtime emits periodic `notifications/progress` frames over the calling connection (relayed to the host by `pm-mcp serve`) at the interval of link:../timeouts/01-job-budgets-and-waits.adoc#progress-interval[Timeouts & Budgets Specification], never with a gap the host could read as idle. A `pm_wait` keeps its bounded window and is held through it by the frames (the per-host rule in link:../client-profiles/01-profile-schema.adoc#worker-block[Client Profiles Specification, Worker Block]); a `pm_build` waits up to the progress wait upper bound (link:../timeouts/01-job-budgets-and-waits.adoc#progress-wait[Timeouts & Budgets Specification]).
* *Wait Attribution*: The engine records for every interval a plan spends waiting its `wait_reason` and `deliberate` (`true` for a waiver wait, a question wait, a prerequisite wait, or a rate window). The closed enum maps every wait of a plan to exactly one reason:
** `build`: a build or `project_script` job, its wait for a build slot included;
** `git`: a `git` job or in-process `git` operation;
** `ci`: a `ci` job or operation and a CI wait (link:../timeouts/01-job-budgets-and-waits.adoc#ci-wait[Timeouts & Budgets Specification, CI Wait]);
** `model_job`: the tasks of a `job llm` state, the wait of its workers for a model slot (link:../timeouts/01-job-budgets-and-waits.adoc#model-slot-wait[Timeouts & Budgets Specification, Model Slot Wait]) and the re-offers of its tasks included;
** `review_bot_window`: a review-bot rate window or re-review wait (link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows]);
** `operator_waiver`: the waiver wait of a remediation unit;
** `question`: an open question record, the vote wait of an adjudication included;
** `merge_queue`: the merge-queue landing wait;
** `merge_mutex`: the admission wait of the cross-plan merge mutex (link:../timeouts/02-runtime-leases-operator-web.adoc#merge-mutex-admission-wait[Timeouts & Budgets Specification, Merge-Mutex Admission Wait]);
** `server_retry`: the backoff before a server retry, of a bounded server rule or of a condition's self-remedy retry (link:../timeouts/01-job-budgets-and-waits.adoc#server-retry-backoff[Timeouts & Budgets Specification, Server Retry Backoff]);
** `provider_rate_limit`: the time a provider's API rate limit (`Retry-After` or a rate-limit reset instant) deferred the next observation of a `ci`, review-bot, or merge-queue wait (link:../timeouts/01-job-budgets-and-waits.adoc#ci-repoll-cadence[Timeouts & Budgets Specification, Provider Re-Poll Cadence]); it is never a timeout and never a failure;
** `prerequisite`: the time a plan holds in `replan.await-prerequisite` for a named prerequisite to land;
** `integrity_pause`: the time the plan's scope holds under an integrity pause (link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification, Store Digest Verification]), `deliberate: false`.
+
`record-metrics` sums wait time per reason and reports deliberate waits separately from poll misses, never as one "waste" figure.

[#engine-deadlines]
=== Engine Deadlines: Waiver Wait, Question Deadline & Prerequisite Wait

Three waits of a plan end by time without any model call: the waiver wait of a remediation unit, the deadline of an open question record (values in link:../timeouts/01-job-budgets-and-waits.adoc#remediation-budgets[Timeouts & Budgets Specification, Remediation Budgets, Question & Waiver Waits]), and the prerequisite wait of a re-planning (value in link:../timeouts/01-job-budgets-and-waits.adoc#replan-budget[Timeouts & Budgets Specification, Re-planning budget & prerequisite wait]). All three deadlines are persisted instants (`expires_at` of the waiver request and of the question record, link:../store-schemas/14-plan-instance-waivers-questions.adoc[Store Schemas Specification]; `prerequisite.deadline_at` of the re-planning record, link:../store-schemas/17-re-planning.adoc[Store Schemas Specification, Re-Planning]), never in-memory timers alone:

* *Waiver Wait*: A server-side `composite_job` of the unit (`remediation.await-waiver`), bound as `active_job` like every job state; its constituents are the deadline and a watch of the plan's `waivers.jsonl`. A `waive` naming the requested gate or budget settles it `waived` or `raised`; the deadline settles it `expired`. It needs no model turn and no host session.
* *Question Deadline*: A question state is a waiting state of the derived kind `awaiting_user`; the question is answered through the web app or through the answer link shown to the entry session (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]). Its deadline is engine-owned and processed by the runtime's deadline timer, which takes the class fallback transition in its own journaled transaction under the scope lock. Mode `operator` sets no deadline; mode `none`, and `auto` with `questions.wait_seconds: 0`, resolve at creation; mode `quorum` sets the deadline on the `adjudicated` line.
* *Prerequisite Wait*: A server-side `composite_job` of the re-planning (`replan.await-prerequisite`), bound as `active_job`; its constituents are the deadline and a watch of the prerequisite (the provider's pull-request state or the prerequisite plan's outcome). The prerequisite landing settles it `landed`, its closing unlanded `closed`, the deadline `expired` (link:../phase-workflows/08-dynamic-re-planning.adoc#replan-actions[Phase Workflows Specification, Actions & Guards]). It needs no model turn and no host session.
* *Timer*: The runtime keeps one deadline timer over the persisted instants of every enrolled project; it fires at the earliest instant and after every runtime start, where the per-project recovery (link:../runtime-model/02-startup-recovery-drain.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery]) processes every deadline that passed while the runtime was down, before the project is served. A deadline fires at most once; its transaction re-checks that the record is still open (an answer or a waiver that won the race wins).
* *Holds*: While the scope is under an integrity pause, a passed deadline is held and processed after the pause ends. `abort` and `delete-plan` close the pending records (questions `cancelled`, waiver requests `expired`) in their own transaction, so no timer fires on them. The question wait and the waiver wait never overlap in one plan.

=== Warm Language Server Pool & Orthogonal Service Access (`PM-SVC-2`, `PM-SVC-4`, `PM-TOOL-2`)

The Job Runtime manages the runtime's bounded pool of warm Language Server Protocol (LSP) processes (`max_lsp_instances` in `machine-config.json`, link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration]) spoken via Eclipse `LSP4J` over `stdio` (`PM-TECH-2`, `PM-TECH-3`):

* *Verify-Not-Resolve Launch*: Each language server binary (for example `jdtls`, `pyright-langserver`, `typescript-language-server`, `rust-analyzer`, or any other language server a domain declares) is verified against `language_servers` of the project's enrolment file `enrolments/<project_id>.json` before launch.
* *Pool Processes, Not Jobs*: A language server is started through `pm-exec` like a job, in its own process group and, on Linux, with the same confinement as a job of its project (xref:02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Linux Filesystem Confinement (Landlock)]), but it gets no job record, no `job_id`, and no outcome (there is no job kind for it). After a runtime crash it ends when its `stdin` closes.
* *Lifecycle & Eviction*: Instances are keyed by `(canonical_worktree_path, language_id)` (the plan worktree, or the main checkout at the enrolled `project_root`), initialized lazily on the first `pm_lsp` call (`PM-TOOL-2`, `PM-SVC-4`), evicted cleanly (`shutdown` -> `exit` -> `SIGTERM`) after the language server idle timeout (`lsp_idle_timeout_seconds`; start, request, and idle timeouts in link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle]) or when the runtime drains or stops, and restarted automatically on unexpected exit, within the language server restart cap (link:../timeouts/02-runtime-leases-operator-web.adoc#lsp-restart-cap[Timeouts & Budgets Specification]). After the retries are exhausted, `pm_lsp` returns `lsp_unavailable` for that instance until its idle eviction or a runtime restart (link:../mcp-tools.adoc[MCP Tools Specification], closed error codes).

[#outcome-derivation]
== Outcome Derivation
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-1[PM-WATCH-JOB-1], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-23[PM-WATCH-JOB-23]_

The runtime derives every job outcome itself, at the boundary, from evidence it observed: whether it refused the job before spawn, which signal it sent and why, the wait status of the process (exit code or terminating signal), and the parse of the job log (`PM-EXEC-4`, `PM-SVC-1`). A status that a job reports about itself (the `status` field of a `project_script` output payload, the final message of a worker) is evidence to check, never the outcome. The table is closed and evaluated top to bottom; the first matching row decides. The derived outcome (`fate`), the matching row (`outcome_row`), the exit code or signal, and `cancel_before_group` (<<Process Termination & Cancellation Protocol>>) are recorded in the job record (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]).

[cols="1,3,2,3"]
|===
|# |Evidence |Outcome |Notes

|1
|The job was refused before spawn: verify-not-resolve pipeline (<<Verify-Not-Resolve Execution Pipeline>>, including `enrolment_tampered`, `build_config_changed`, `path_traversal_rejected`), argument schema, or admission.
|`refused`
|Carries the refusal reason (`refusal_reason` of the job record); no process ever existed.

|2

|4

|Exit code `0` without the positive success marker, or with contradicting evidence (parsed errors, failing test counts).
|`indeterminate`

|9
|Non-zero exit code and the parser extracted at least one diagnostic.

|10

|`succeeded`

Rows 5 to 10 apply to process jobs only, rows 11 to 13 to the in-process operations of the native variant only (<<in-process-operations>>); rows 1 to 4 apply to both. The success markers of row 7 for `git` and `ci` apply to the jobs of the CLI variant.

*Write order at job end*: When a job settles, the runtime writes in this fixed order: the job record's fate (which revokes a worker's token and fences its generation; the job record carries no usage), then for a worker the queue task record (attempt end, lease release; link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal], Worker end), then the metrics row of the attempt that ended with the job, if any, with its usage parsed (every other attempt's row is written when that attempt ends; `metrics.json` of the task's scope, link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]), then the change-ledger row (`change-ledger.jsonl`, for jobs that stamp one), then the timing observation (link:../store-schemas/09-derived-facts-and-build-timings.adoc#build-timings-store[Store Schemas Specification, Build Timings Store]), then the build-slot or model-slot release; a worker's job-private directory is removed last. A crash in between loses at most a task's metrics row (reported by `record-metrics` as the divergence `row_absent_from_metrics`, never read as `0`), a freshness mark (the build re-runs), or a timing sample; a task lease left on an ended generation is released by the recovery, and the recovery removes a job-private directory whose job has settled.

Language server instances of the warm LSP pool are not classified by this table; their failures are reported as the non-run reasons of link:../domain-extensions.adoc[Domain Extensions Specification] (Explicit Non-Run Reporting) and the timeouts of link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle].
