== Native Build Output Parsers
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-10[PM-WATCH-JOB-10], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-12[PM-WATCH-JOB-12], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-18[PM-WATCH-JOB-18]_

When a build completes with a non-zero exit code or compiler warnings, the runtime extracts structured diagnostics without calling external Python scripts (`PM-IMPL-6`). Each compiled parser ports one `plan-marshall` parser module (`marketplace/bundles/plan-marshall/skills/build-*/scripts/`, plus the domain-owned OpenRewrite parser) and is verified against it by differential tests (`PM-TEST-2`):

[cols="2,2,3,3"]
|===
|Parser |`plan-marshall` Module |Parser Strategy |Diagnostic Extractions

|*Maven*
|`build-maven/_maven_cmd_parse.py`
|Line scanner over `[ERROR]` / `[WARNING]` lines with the shared JVM category patterns (compiler, test, dependency, OpenRewrite info), stack-trace collection, deduplication across reactor summary and per-module output, and Surefire/Failsafe test summary.
|File path, line, column, message, category, severity; test counts; build status.

|*Gradle*
|`build-gradle/_gradle_cmd_parse.py`
|Scanner over Java/Kotlin compiler errors (`e: <path>:(line, col): <message>`), failing tasks, and `N tests completed, M failed` summaries with the shared JVM category patterns.
|File path, line, column, message, category, failing task; test counts; build status.

|*npm errors*
|`build-npm/_npm_parse_errors.py`
|Scanner over `npm ERR!` lines, classifying error codes (`ERESOLVE`, `E404`, and others).
|Error code, conflicting package / peer dependency, message.

|*TypeScript*
|`build-npm/_npm_parse_typescript.py`
|Scanner over `tsc` diagnostics in both `path(line,col): error TSnnnn: message` and `path:line:col - error TSnnnn: message` forms.
|File path, line, column, `TS` code, message.

|*ESLint*
|`build-npm/_npm_parse_eslint.py`
|Scanner over the stylish formatter output (file header lines followed by `line:col severity message rule` rows) and the problem summary.
|File path, line, column, severity, rule ID, message; error and warning counts.

|*Jest*
|`build-npm/_npm_parse_jest.py`
|Scanner over `FAIL <suite>` blocks and the `Tests:` summary line.
|Failing test file and test name, failure message; test counts.

|*TAP*
|`build-npm/_npm_parse_tap.py`
|Scanner over `not ok N - <name>` lines and the `# tests` / `# pass` / `# fail` / `# skipped` summary.
|Failing test name; test counts.

|*Python (pyproject)*
|`build-pyproject/_pyproject_cmd_parse.py`
|Tool-detecting scanner for pytest (`FAILED` and collection/setup `ERROR` short-summary lines, with the deepest traceback frame for the location), ruff (`path:line:col: CODE message`), and mypy (`path:line: error: message`).
|File path, line, rule code or test node ID, message; test counts.

|*OpenRewrite*
|`pm-dev-java-cui:parse-rewrite-log` (domain verb `rewrite-log-parse`, consumed by `build-maven/_maven_cmd_rewrite_log.py`)
|Scanner over the structured OpenRewrite `WARN` finding lines in the Maven log, run only when the build reached the `rewrite:run` goal and the java-cui domain is active; fail-closed verdicts `observed`, `not_observed`, `domain_inactive`, `parse_error`.
|Recipe finding per line (newly detected vs pre-existing), verdict.
|===

Test counts are aggregated over every summary block of a multi-module run. When a successful build's summaries cannot be aggregated, the result reports `tests_population: unmeasured`, never `tests_run: 0`; a `no_tests_ran` verdict requires a positive marker, not a zero count. In the Maven parser, failure-trailer advice lines (`Re-run Maven using the -X switch…`, `[Help 1] http…`, `After correcting the problems, you can resume the build…`, `mvn <args> -rf :<module>`) are dropped, and an unrecognised `[ERROR]` line is categorised `unrecognized`, never assigned a real category. The trailer drop, the `unrecognized` category and the positive-marker rule for `no_tests_ran` do not exist in the `plan-marshall` parsers; they are *deliberate changes* verified by their own fixtures, never adopted from the differential baseline (link:../store-schemas/13-leases-integrity-testing.adoc#differential-harness[Store Schemas Specification, Known-Defect Baseline]).

Coverage reports are parsed separately (<<Native Coverage Report Parsers>>).

=== Unparseable Output Fallback (`failed_unparsed`)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-7[PM-WATCH-JOB-7], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-14[PM-WATCH-JOB-14]_

If a build exits with a non-zero exit code but the output parser cannot extract any structured diagnostic (row 10 of xref:01-pipeline-and-subprocesses.adoc#outcome-derivation[Outcome Derivation]; a build ended by a signal, including a crash, is `killed`):

* The job outcome is classified as `failed_unparsed` (never folded into normal `failed`).
* The full raw log is preserved at `<PM_MCP_BASE>/projects/<project_id>/jobs/<job_id>.log`, next to the job record.
* The failure is gathered as one failure envelope of class `build` and kind `unparsed` (<<evidence-gathering>>) whose excerpt is the bounded raw-log tail (last 50 lines, capped at 4 KB, secrets redacted), with the resource URI `pm://plan/{plan_id}/builds/{job_id}/log` for the full log; the representation carries no invented diagnostic, preventing the model from hallucinating non-existent compiler errors, and the gate's caller routes the failure to its build remediation policy (no `escalate` link exists).

== Adaptive Build Timeouts, Coverage Parsers & Gate Honesty (`PM-EXEC-6`)

=== Adaptive Timeout Learning
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-15[PM-WATCH-JOB-15], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-16[PM-WATCH-JOB-16]_

The runtime (`pm-mcpd`) persists observed execution durations per project in `<PM_MCP_BASE>/projects/<project_id>/build-timings.json` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#build-timings-store[Store Schemas Specification, Build Timings Store]), keyed by budget key (for build jobs the canonical command: build system, canonical verb of the xref:02-confinement-and-environment.adoc#canonical-build-verbs[Canonical Build Verb Set], and module; a build profile is named literally in the verb's template, so it needs no key component; for `git` and `ci` operations the operation key `<kind>:<operation>`, the same for an in-process operation of the native variant and a job of the CLI variant, xref:01-pipeline-and-subprocesses.adoc#in-process-operations[In-Process Operations (Native Variant)]; for model jobs the key `llm:<role_key>`, one key per role whatever the harness); there is no repository-local and no machine-level timeout store, so a moved checkout keeps its budgets. The blend formula, the engine floors, the allocation rule, the escalation budget and its cap, operator budgets, and the no-verdict rule for `timed_out` are defined only in link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]; this section defines which runs feed the learned baseline $L$:

* *Finished Runs Feed $L$*: Every finished run (any exit code) feeds $L$ with its duration; `killed` and `cancelled` runs never do. A model job (key `llm:<role_key>`) feeds $L$ only when it ended `succeeded`: a run that ended with any other fate says nothing about the time the role's work takes. An in-process operation has finished when it returned a result of its contract; the time it spent deferred by a provider rate limit is excluded from the duration.
* *Timed-Out Runs Never Feed $L$*: A `timed_out` run is a non-finish, so its duration is unknown. It never feeds $L$; it sets the one-shot escalation budget of link:../timeouts/01-job-budgets-and-waits.adoc#escalation-budget[Timeouts & Budgets Specification] for the next run of the same key, which the next finished run clears. *Deliberate change vs. `plan-marshall`*: `plan-marshall` blends its doubled timeout into $L$, so one residue-slowed timeout inflates every later budget.
* *Residue-Poisoned Runs*: A finished run whose worktree held build residue above the hygiene threshold at its start (the count of git-ignored build output files measured at job start, beside the <<worktree-sha>> scan; the threshold is a named engine constant recorded with the observation) is stored as `poisoned` and not blended while clean observations exist. The learned value's hygiene (`observations`, `poisoned`, `cold`, `escalation_seconds`) is recorded in the build timings store (link:../store-schemas/09-derived-facts-and-build-timings.adoc#build-timings-store[Store Schemas Specification, Build Timings Store]), the job record carries only its `budget_derivation` (kind and, for `learned`, the observation count), and `pm-mcp status` shows both; it is never rendered in the job facts (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
* *Budget Derivation*: Every allocated budget records `budget_derivation` (`learned` with its observation count, `escalated`, `operator`, or `floor_default`; link:../timeouts/01-job-budgets-and-waits.adoc#budget-allocation[Timeouts & Budgets Specification, Allocated Budget]) in the job record, never in the representation: the model acts on the offered links, not on the derivation. Every `timed_out` outcome is `no_verdict`, whatever the derivation; the derivation selects only the retry offer, server-side (link:../timeouts/01-job-budgets-and-waits.adoc#no-verdict-rule[Timeouts & Budgets Specification]).
* *Budget Scope & Measurement*: Every budget states the statistic it came from and the scope it applies to (link:../timeouts/01-job-budgets-and-waits.adoc#no-verdict-rule[Timeouts & Budgets Specification], Budget statistic). Its scope is the budget key, so a figure measured under one key is never applied to another.
* *Runner-Dependent Verdicts*: When the same test population is red under one canonical command and green under another (for example a real-tree test that times out under a module-scoped test run but passes under `verify`), the job facts report both keys with their verdicts (the budgets stay in the job records); the difference is never left implicit.
* *Cold Rebuilds*: A finished run that starts after a dependency sync or a build-cache invalidation since the key's previous observation (a changed resolved-dependency set or a cleared build cache) is stored as `cold`. Like a `poisoned` run it is not blended into $L$ while warm observations exist, and it is never read as a regression of $L$.
* *Seeded Wait Budgets*: The expected duration of a CI wait (link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_deterministic_evaluation_immediate_short_circuit_matrix[Hypermedia Format Specification, Short-Circuit Matrix]) is seeded from the project's known-slow ceilings (the operator budgets in the enrolment) when no learned figure exists. CI waits are re-polled and never lapse, so a seeded figure sets only the expected duration recorded with the wait (shown by `pm-mcp status`, never rendered), never a failure deadline (link:../timeouts/01-job-budgets-and-waits.adoc#ci-wait[Timeouts & Budgets Specification, CI Wait]). Review-bot waits are bounded by the bot's rate window, re-review timeout, and attempt ceiling, never by a learned or seeded figure (link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows]).
* *No Inherited Baselines*: Every learned value starts from the project's own finished runs under `PM-MCP`; learned timeouts of legacy `plan-marshall` are never read or imported (`PM-MIG-2`).

=== Native Coverage Report Parsers

The build runtime parses coverage artifacts natively after test execution to evaluate threshold compliance, porting `plan-marshall`'s format-agnostic coverage parser (`script-shared/scripts/build/_coverage_parse.py`, formats JaCoCo, Cobertura, LCOV, and Istanbul JSON). As in that parser, the threshold verdict (`passed`) compares the overall *line* percentage with the threshold, and the low-coverage list compares each item's line percentage with it; every other metric is parsed, rendered in the job facts, and never feeds a threshold:

* *JaCoCo (`jacoco.xml`)*: StAX XML reader extracting the `INSTRUCTION`, `BRANCH`, `LINE`, and `METHOD` counters (overall `instruction`, `branch`, `line`, `method` percentages from `covered / (missed + covered)`), plus per class the `LINE` counter and the methods with missed `METHOD` counters (`<init>` and `<clinit>` excluded) as `missed_methods` detail. Threshold metrics: overall `line`, per-class `line`.
* *Cobertura (`coverage.xml`, as written by `coverage.py` for pytest)*: StAX XML reader extracting the root `line-rate` and `branch-rate` and per class `line-rate` (methods with `line-rate` 0 as `missed_methods` detail). Threshold metrics: overall `line`, per-class `line`.
* *LCOV (`lcov.info`)*: Line-oriented parser over the per-file records `SF:`, `LF:`, `LH:`, `BRF:`, `BRH:`, `FNF:`, `FNH:` (up to `end_of_record`), summed over all files into overall `line` (`LH/LF`), `branch` (`BRH/BRF`), and `function` (`FNH/FNF`) percentages (`statement` equals `line`, since LCOV has no statement counter). `DA:` records may be kept as per-line detail but never enter a percentage or a threshold. Threshold metrics: overall `line`, per-file `line`.
* *Istanbul (`coverage-summary.json`)*: Jackson streaming reader extracting the `pct` of `lines`, `statements`, `functions`, and `branches` from `total` and per file. Threshold metrics: overall `line` (`lines.pct`), per-file `line`.

=== Gate Honesty Verification
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-2[PM-WATCH-GEN-2], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-8[PM-WATCH-JOB-8], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-17[PM-WATCH-JOB-17], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-25[PM-WATCH-JOB-25]_

Before marking a module or pre-push quality gate as `fresh` in `change-ledger.jsonl` (`PM-SVC-1`), the runtime applies four honesty checks:

1. *Examined Population*: The set of modules and source files actually compiled and tested in the build log must be non-empty and must cover every module mapped from the plan's realized file footprint.
2. *Gate Coverage*: The gate scope of a build is computed from its `module` argument, never from its verb: an absent `module` is the whole tree, a present `module` is that module only. A module-scoped run of any verb never satisfies a whole-tree gate, and a whole-tree gate (`quality-gate`, `verify`, `coverage`, `arch-gate` of the xref:02-confinement-and-environment.adoc#canonical-build-verbs[Canonical Build Verb Set]) is satisfied only by a whole-tree run of that verb. Every gate result carries server-derived coverage facts in `plan-marshall`'s terms (`script-shared/scripts/build/_gate_coverage.py`, verified at plan-marshall commit `88fcfc9ef`), which the server derives from the parsed build and the gate definition and the model never supplies:
** `gate_coverage`: `COMPLETE` (at least one dimension checked over its full scope and none degraded), `PARTIAL` (the degraded dimensions are named with their reason; a clean exit is then not a full pass), or `UNKNOWN` (nothing checked and nothing degraded recorded; the run certifies nothing). A dimension attempted over an empty scope is recorded as `empty_scope`, neither a pass nor a gap.
** `structural_limits`: per checked analysis kind, what the analysis cannot evaluate however wide its scope (for example type checking cannot decide whether a well-typed value is correct, tests are silent on inputs no test supplies); an analysis kind without a registered limit is recorded `UNKNOWN`, never omitted.
** `uncovered`: the dimensions the run did not cover, split into `not_at_this_scope` (the gate performs them, but not at this scope) and `not_by_this_gate` (no invocation of this gate performs them); without a declared scope the split is `undeclared`, never an empty list.
** `parity_population`: the recorded dimensions along which the local gate is compared with CI, each `equal`, `subset`, or `closed`; the population is asserted non-empty, because a parity table over nothing reads as perfect parity.
+
All four are persisted in the gate's job record (`gate_facts`, link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]) and step record. The representation of a gate result renders only what the model acts on: `gate_coverage` with, for `PARTIAL`, the degraded dimensions and their reasons, and `uncovered`, so a clean exit is never reported as a full pass. `structural_limits` (a static, registered property of each analysis kind) and `parity_population` (local-versus-CI parity evidence for metrics and the quality report) are never rendered (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
3. *Test-Scope Divergence Detection*: Detects and rejects runs where test filtering flags or skipped-test properties excluded tests belonging to modified modules.
4. *Baseline Separation*: A red gate is checked for failures already present on the base before any routing, as a server rule (no model judgment, no operator decision, no `<phase>.baseline-red` state). The failures are compared by their fingerprints (<<evidence-gathering>>):
** *Primary proof, the provider's CI result on the base*: For a CI check, and for a local gate that CI also runs, the proof is the provider's result of the same check on the base: on the merge base (`merge-base(HEAD, origin/<base_branch>)`), or on the latest base-branch commit that contains it and has a result. `remediation.ci-failure`'s gathering job fetches this base result in the same job, so a baseline-only red never reaches the unit's `decide`.
** *Fallback, a local build of the merge base*: For a local gate CI does not run (for example the pre-push quality gate) or when the provider has no result for the base, the gate is re-run on the merge base in the plan's baseline scratch worktree. The baseline worktree is a detached worktree at the merge base, created natively with `git.worktree-add` at `.marshall/local/worktrees/baseline-<plan_id>-<sha12>` (`<sha12>` the first 12 hex digits of the merge-base SHA), never the primary checkout and never the plan's worktree; it is reused by every base run of the plan while the merge base is unchanged, replaced (the old one removed, a new one created) when the merge base moves, and removed when the plan leaves `finalize`, is archived, or is aborted; the recovery sweep removes one whose plan is gone or terminal (link:../filesystem-layout.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). Before each reuse it must be clean (`git.status` empty); a dirty baseline worktree is replaced, never used. A quality-gate or format job run there (or in any fresh worktree of the base) must leave `git.status` empty; a job that rewrites committed files there is reported as dirtying the base, never silently accepted, and the worktree is replaced before the next base run.
** *Verdict*: Located diagnostics present on both sides are `baseline` and never become plan findings; for coverage, a threshold failure in a module whose main sources the plan did not change is `baseline_debt` (one non-blocking finding of severity `info` per module, never fanned out into build-error or Q-Gate findings). When every failure of the gate is baseline-only, the server writes a `baseline_red` row into `change-ledger.jsonl`, bound to the gate's `worktree_sha`, the merge base, the base commit and proof source, and the digest of the accepted diagnostics (link:../store-schemas/04-epic-and-change-ledger.adoc#_change_ledger_record_change_ledger_jsonl[Store Schemas Specification, Change Ledger Record]); the freshness gate accepts that row as passing for the same `worktree_sha` only, the gate step completes `done` with `assurance_verdict: degraded`, and the PR body and the landing record list the baseline failures. Both build jobs keep their own outcomes. A red that is not provably baseline-only is plan-caused: its failures (the remaining diagnostics) go to the build or CI remediation policy. A base run or base result that cannot be obtained or parsed leaves every diagnostic attributed to the plan (fail-closed) and says so in `facts`.

=== Evidence Gathering per Failure Class
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-26[PM-WATCH-JOB-26]_

Every remediation unit starts with a gather state: one server-side gathering per failure class, which hands the model structured failures and never raw logs (`PM-SEC-1`). A class whose gathering reads only server stores (`build`, `review`, `qgate`, `spend`) gathers inside the gather state's own transaction, without a job, and its failure records carry `gather_job_id: null`; a class that calls a provider or git (`ci`, `analysis`, `merge_conflict`) gathers through its gathering job, whose `job_id` its records carry. The model receives the failures as failure envelopes (`{failure_id, class, kind, source, file?, line?, message, fingerprint, excerpt_uri?}`, link:../store-schemas/14-plan-instance-waivers-questions.adoc#evidence-directory[Store Schemas Specification, Evidence Directory & Failure Envelope]); logs and excerpts are stored in the plan's evidence directory as untrusted, redacted resources (`pm://plan/{plan_id}/evidence/{evidence_id}`) and never inlined beyond `message`.

[cols="1,3,2"]
|===
|Class |Gathering |Kinds

|`ci`
|Fetches the failed checks' logs through the provider module (a `ci` job), parses each with the domain's `log_parser` worker (a `project_script` of worker kind `log_parser`, link:../domain-extensions/05-recipes-and-extension-points.adoc#_out_of_process_project_script_jobs_project_script_domain_workers[Domain Extensions Specification, Project Script Jobs & Domain Workers]) or the native build output parsers, else a generic tail parser yielding `unknown`; fetches the base result of the same checks for the baseline proof in the same job.
|`compile`, `test`, `lint`, `infra`, `timeout`, `unknown`

|`build`
|Reads the failed build's ledger row and parsed diagnostics (`errors[N]{file,line,message,category}`); a `failed_unparsed` build yields one `unparsed` envelope with the log tail as excerpt.
|`compile`, `test`, `quality_gate`, `arch_gate`, `unparsed`

|`review`
|Reads the open findings of the ledger, including the barrier re-fetch, and the review evidence state of the required bots.
|`finding`, `evidence_missing`

|`analysis`
|Reads each configured analysis provider's gate conditions and new-code issues through the code-analysis contract, tagged by provider.
|`gate_condition`, `issue`, `undecidable`

|`merge_conflict`
|Lists the conflicting paths and hunks with the base commits that touched them; a push refused under a rejected lease (the plan branch's remote moved) yields one `remote_moved` envelope whose source is the observed `remote_sha`.
|`conflict`, `remote_moved`

|`qgate`
|Reads the phase's blocking Q-Gate findings.

|`spend`
|Renders the spend report of the plan.

The `fingerprint` (class, kind, file, normalized message) lets the server recognise a repeated failure (`retry_not_applicable`) and the baseline proof. Every envelope states whether its gate is waivable and names the gate; a non-waivable failure (a security finding, a footprint breach) is marked `waivable: false`. Untrusted content (CI logs, bot comments, analysis messages) passes the ingestion validator (<<ingestion-validator>>) before it is stored; externally authored text (bot comments, analysis messages) is in addition gathered into one batch per firing and screened (link:../dispatch-and-effort/06-untrusted-text-screening.adoc#batch-v1[Model Jobs & Effort Specification, Batch Format]), while CI logs and build excerpts, the server's own job output, pass the validator only.

[#ingestion-validator]
=== Ingestion Validator (Level 1, `PM-SEC-1`)
_See Requirement link:../../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-27[PM-WATCH-JOB-27]_

Every surface that admits external text into a server store or a representation runs it through one deterministic validator first: issue and pull-request titles and bodies, review comments and bot findings, analysis-provider messages, upstream MCP results, and CI log and build excerpts. The validator is the containment boundary of the two-level guard (link:../dispatch-and-effort/06-untrusted-text-screening.adoc#two-level-guard[Model Jobs & Effort Specification, Two-Level Guard]); it runs in-process on the JDK and `org.commonmark:commonmark` (0.30.0), the one library added for it, and uses the URL validation pipelines of `cui-http` (`de.cuioss.http.security`). Its stages run in this order:

1. *Unicode, to a fixpoint*: removes the Unicode tag block (`U+E0000`–`U+E007F`), variation selectors, every code point of the general categories `Cf`, `Co`, and `Cn`, the `Cc` controls except line feed and tab, lone surrogates, and ANSI escape sequences; normalizes the content to NFC and keeps an NFKC copy for detection only (never delivered). The stage repeats until a pass changes nothing, bounded by a compiled pass limit; a text that does not settle within it is refused.
2. *Markdown AST*: parses the text with `commonmark` and renders it back from the tree: images are removed; a link whose target lies outside the allowlist (the origins of the project's push remote provider and of its configured analysis providers, all server-derived) is neutralized to inert text; raw HTML blocks, inline HTML, and HTML comments are removed; URLs shaped for exfiltration (long encoded query or path segments, `data:` and non-`https` schemes, credentials in the authority) are flagged; every URL extracted from the tree passes the `cui-http` URL validation pipelines (encoding and traversal attacks), and a failing URL is neutralized.
3. *Bounds*: the per-field length, line, and item bounds of the record's closed schema; an over-long value is clamped, never truncated silently.
4. *Rule table*: a compiled table of injection-shaped patterns evaluated on the NFKC detection copy (instructions addressed to a model, role and tool-call markers, prompt delimiters). A hit is a risk signal recorded as a finding of the item and handed to the screener as context; it never blocks the text on its own.
5. *Spotlighting at delivery*: wherever the cleaned text reaches a model (a representation, a screener or triage prompt), it is enclosed in delimiters with a per-delivery random nonce that the text is checked not to contain, and marked untrusted.

*Every change is reported*: each stage appends to the item's change report what it removed, neutralized, clamped, or flagged, with counts and positions; nothing is dropped silently, and an item whose report is not empty says so wherever it is delivered. The structured fields of every ingested record are validated against their closed schema (`additionalProperties: false`, `maxLength`, `maxItems`, `pattern`); a structural violation refuses the record. The validator detects no semantic injection: that is the screener's task (level 2), and a local classifier is deferred.

[#worktree-sha]
== Working-Tree Hash (`worktree_sha`, `PM-SVC-1`)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-24[PM-WATCH-JOB-24]_

`worktree_sha` stamps every build and change entry in `change-ledger.jsonl` and keys every freshness gate. It is a PM-MCP-native, variant-neutral digest computed by one operation of the git contract, `git.worktree-sha` (budget class link:../timeouts/01-job-budgets-and-waits.adoc#git-local-budget[Timeouts & Budgets Specification, `git` local operation class]), which both variants serve from the same status information and which returns the digest together with its hash version; a workflow uses it as a single node (link:../workflow-dsl.adoc[Workflow DSL Specification]). *Deliberate change vs. `plan-marshall`*: `plan-marshall`'s `script-shared/scripts/worktree_sha.py` hashes the textual output of `git diff` and `git ls-files`, which depends on git configuration; PM-MCP hashes file bytes read from disk, so its bytes differ from that script's. Byte parity is not required, because the digest is never exchanged between the two systems (`PM-MIG-2`); the differential tests (`PM-TEST-2`) compare equality behaviour instead (rule 6):

1. *Inputs*: The `HEAD` commit id, and every path the working-tree status of the worktree root reports as changed (in the index or the working tree), deleted, or untracked; ignored paths are not included. The native variant reads the status with JGit `StatusCommand` (untracked files listed individually, no rename detection); the CLI variant runs `git status --porcelain -z --untracked-files=all --no-renames` and `git rev-parse HEAD` with the worktree root as working directory, so that both variants report the same path set.
2. *Framing*: `sha256(HEAD ‖ NUL ‖ Σ entry)`, where `HEAD` is the lower-case hex commit id and the entries are sorted by the bytes of their UTF-8 path. An entry is the path, `NUL`, and then either the tag byte `F`, the content length as 8-byte big-endian integer, and the file's bytes read from disk, or, for a path that no longer exists on disk, the tag byte `D` (the deletion marker). A symbolic link contributes the tag byte `L`, the length, and its target path (never the target's content).
3. *Configuration independence*: The digest reads no textual diff output, so settings that shape it (`diff.noprefix`, `color.diff`, external diff and textconv drivers, `diff.renames`, `core.quotePath`) have no effect, and the configuration-neutralising options of earlier drafts are dropped. The status itself honours the repository's ignore rules in both variants.
4. *Hash version*: Every record that carries a `worktree_sha` also carries `worktree_sha_version` (currently `1`, the inputs of rule 1 with the framing of rule 2): the `change-ledger.jsonl` rows and the `freshness_reconcile` record, whose version is that of its `prior_build_worktree_sha` (link:../store-schemas.adoc[Store Schemas Specification]). Any change of the inputs or the framing is a new version. Freshness gates compare digests only of equal versions: a row of another version never matches the live digest and never makes a gate `fresh`; the gate reports it like an absent row for that notation.
5. *Fail-closed on failure*: If the status, the `HEAD` resolution, or a file read fails (in the CLI variant a non-zero exit, termination by a signal, or its timeout; in the native variant an exception or the timeout), no digest is produced. The value is `unavailable`, recorded with the failing step and its failure (`exit_code`, `signal`, `timed_out`, or the exception class) as `worktree_sha_failure`; an unresolvable `HEAD` is such a failure. Every freshness gate keyed on it evaluates indeterminate, never `fresh`: the gate status is `undecidable` with `stale_reason: worktree_sha_unavailable` (link:../phase-workflows.adoc[Phase Workflows Specification], Worktree Freshness Gate), and an `unavailable` value never equals another `unavailable`. *Deliberate change vs. `plan-marshall`*: its `worktree_sha.py` ignores the exit codes of `git diff` and `git ls-files` and hashes the empty output of a failed call into an ordinary digest.
6. *Differential tests (`PM-TEST-2`)*: Over the same fixture trees, both implementations are run and their *equality behaviour* is compared, never their bytes: the same tree yields the same digest (on each side), and any change of a tracked file's content, an untracked path or its content, a deletion, or `HEAD` yields a different digest (on each side). Fixtures include non-ASCII paths, staged-only changes, deletions, and a repository configuration that changes git's diff output (for example `diff.noprefix` or a textconv driver); for the last, PM-MCP's digest must stay unchanged while plan-marshall's may change. The native and the CLI variant must produce byte-identical digests on every fixture. A failure fixture (unreadable file, unresolvable `HEAD`) asserts `unavailable` (rule 5) and is excluded from the comparison.

== Security Boundary & Confinement Adversarial Testing (`PM-TEST-5`, `PM-SEC-1`, `PM-SEC-2`, `PM-SEC-5`)

The `pm-mcp-core` and `pm-mcp-server` verification suite enforces automated adversarial tests (`PM-TEST-5`) across every job and ingestion boundary:

1. *Workspace & Symlink Escape Rejection (`PM-SEC-2`)*: Adversarial fixtures containing `..` segments, URL-encoded path traversal, and intra-worktree symlinks pointing outside `<workspace-root>` must be rejected (`path_traversal_rejected`: job outcome `refused` for a job, `rejected.reason` for a `pm_do` argument) before any file descriptor or subprocess is opened.
2. *Tampered Binary & Wrapper Rejection (`PM-EXEC-2`, `PM-EXEC-3`, `PM-EXT-5`)*: Modifying 1 byte of an enrolled `mvnw`, `gradlew`, `pw`, one of a wrapper's `pinned_files` (wrapper jar, wrapper properties, `.mvn/maven.config`, `.mvn/jvm.config`, `gradle.properties`), host binary, or `project_script` without operator re-enrolment, or adding a pinned build configuration file after enrolment, must fail the SHA-256 preflight check with `refused` and emit a `security` event in `audit.jsonl`.
3. *Argument Vector Injection & Environment Sanitization (`PM-EXEC-1`, `PM-SEC-5`)*: Passing shell metacharacters (`; rm -rf`, `$(...)`, backticks) or non-allowlisted flags (`-Dexec.executable=...`, `--init-script`) in job parameters must be rejected at schema validation, and spawned child environments must never contain `GITHUB_TOKEN` or `SONAR_TOKEN`.
4. *Ingestion Validator & Model Job Containment (`PM-SEC-1`, `PM-SEC-5`)*: The ingestion validator (<<ingestion-validator>>) is run as JUnit fixtures over the attack generators of `cui-http` and over prompt-injection corpora (garak, promptfoo): every tag-block, variation-selector, bidirectional, and ANSI payload is removed within the pass limit, every image, raw HTML fragment, and non-allowlisted link is removed or neutralized, and each change appears in the change report. A screener job is launched with zero tools and no MCP configuration, and an unparseable or incomplete verdict makes its items `suspicious`. A request with a job token that names another scope or entity is refused `job_scope_mismatch`, a link into a `job llm` state is refused on a job connection, and a request with the token of an ended job is refused `job_ended`. On a Landlock-capable kernel a model job cannot read `<PM_MCP_BASE>` (the runtime token included) apart from its own job-private directory `run/jobs/<job_id>/`, which it cannot write and which no other job can read, and writes only its project root, the system temporary directory, and its declared harness paths, never a settings or hook file of the installed client bundle; its environment holds no runtime token and no credential variable, a harness authentication variable set in the runtime's environment included (matched positive controls as in item 5).
5. *Landlock Read and Write Sets (`PM-SEC-5`)*: On a Landlock-capable kernel, a job that reads a credential file under `<PM_MCP_BASE>/credentials/` (or any other path under `<PM_MCP_BASE>`, `run/runtime.token` included) fails with a permission error, while a matched positive control reads a file of its own project root and a binary of `<PM_MCP_HOME>/bin/`. A job that writes its project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (and any other path under `<PM_MCP_BASE>` or `~/.plan-marshall/`) fails with a permission error and leaves the file unchanged, and so does a job that writes into the root of a second enrolled project; a matched positive control writes inside the job's own project root.
6. *Enrolment Tampering (`PM-EXEC-2`)*: Editing a project's enrolment file out of band without the operator CLI makes the next job of that project refuse with `enrolment_tampered` and an `audit.jsonl` `security` record, while a job of a second enrolled project on the same runtime still runs (matched control); the same edit re-baselined through the operator CLI is accepted.
