== Overview

This document is the single normative description of how *plan-marshall-mcp* (`PM-MCP`) runs and how coding agent hosts and workers interact with it. It separates two models that must never be conflated:

* *Runtime model*: One always-on *runtime* process (the daemon, binary `pm-mcpd`) per machine and `PM_MCP_BASE` owns all workflow execution, jobs, workers, warm services, coordination, and every store write. Its lifetime is independent of every host conversation.
* *Interaction model*: The runtime drives every plan and epic itself. A state that needs no model is server logic; a state that needs a model becomes a task of a role, which a *worker* (a headless harness process the runtime starts as a job of kind `llm`) receives through `pm_wait` and does along the task's links. The *entry session*, an interactive host conversation, turns the user's words into a plan or an epic, drives the bootstraps and the project setup, views plans and epics, and relays answers to open questions; it may take tasks of `read_only` roles as an optional worker, and no plan or epic waits on it. Hosts and workers reach the runtime through a thin STDIO *relay* (`pm-mcp serve --client <client>` for a session, `pm-mcp serve --job` for a worker) that carries their identity and generation. A plan or epic is carried entirely by its persisted files, never by a connection.

One release delivers four native binaries, each with one direction (`PM-TECH-3`, link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]):

[cols="1,1,3"]
|===
|Binary |Build |Role

|`pm-mcp`
|plain GraalVM native image, picocli
|The relay binary: only the harness- and model-facing commands `serve` (the STDIO relay of a session, `serve --job` for a worker) and `enter`. A client of the runtime (`/mcp` for `serve`, the link:runtime-model/01-processes-and-transport.adoc#local-api[Local API] for `enter` and for the relay's generation binding); holds no store logic and writes no store.

|`pm-operator`
|plain GraalVM native image, picocli
|The operator CLI: every command a human runs at a terminal (the operator verbs such as `enrol`, `credentials`, `waive`, `config`, `roles`, plus `web`, `client`, `runtime`, `drain`, `status`), without an `operator` sub-level. A client of the runtime's Local API; holds no store logic and writes no store. The host bundle denies the whole binary to the model (link:cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]).

|`pm-mcpd`
|Quarkus native
|The runtime (daemon). Started on demand by `pm-mcp` or `pm-operator` or by the per-user service manager (link:runtime-model/01-processes-and-transport.adoc#_start_modes[Start Modes]); opens no TCP or UDP listener unless the operator enabled web access, apart from the loopback listener fallback (link:runtime-model/01-processes-and-transport.adoc#_transport_endpoint[Transport Endpoint]).

|`pm-exec`
|plain GraalVM native image
|The job launcher: process group and, on Linux, confinement before `execve` (link:job-runtime/01-pipeline-and-subprocesses.adoc#_process_group_creation_via_the_pm_exec_launcher[Job Runtime Specification]). Started only by the runtime.
|===

Web access is no binary and no process of its own: while the operator enabled it, the runtime serves the web app and the Local API to paired browsers on a second HTTP server (link:cli-and-security.adoc[CLI, Coordination & Security Specification]). The web app and `pm-operator status` are the dependable views of every plan, epic, worker, and task. The binaries are installed side by side in `<PM_MCP_HOME>/bin/`; a binary starts a sibling by its path in that directory, never through `PATH`.

All other specifications reference this document for process topology, transport, the relay, connection lifecycle, and the roles of sessions and workers at the transport instead of restating them. The task protocol, roles, supervision, and consultation are specified in the link:model-work.adoc[Model Work Specification].
