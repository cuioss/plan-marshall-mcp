[#task-queue]
== Task Queue (`<PM_MCP_BASE>/projects/<project_id>/queue/`)

Every piece of model work of a project is a queue task, persisted in the project's task queue until a worker of its role has served it (`PM-WORK-2`). The protocol that moves a task (offer, acknowledgement, execution, consultation, submit, fencing) is specified in link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]; this part holds its records. The queue directory holds one queue task record per task (<<queue-task-record>>) and the session generation record of the project (<<session-generation-record>>).

* *One Queue per Project*: Tasks of every scope of the project (plans, epics, the workspace scope and its bootstrap entities) share the queue, ordered per role: consultation tasks first, then work tasks in creation order (link:../model-work/02-task-protocol.adoc#queue-task[Model Work Specification, Queue Task]). The queue is per project because a worker serves one project (its job record's scope is `project`, xref:10-job-and-lesson-records.adoc#job-record[Job Record]).
* *Lock and Write*: Every write runs under the queue lock `locks/queue.lock` (xref:13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)]) as an atomic write-and-rename of the one record it changes (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline]). A transition that creates or settles a task holds its scope lock and takes the queue lock after it; the offer, the acknowledgement, the consultation, and the fence take the queue lock alone. Queue records are not part of a scope's transaction journal and not covered by a digest sidecar, like the job records.
* *Two Authorities*: The scope store is authoritative for which tasks a model state owns and for how they ended (`active_tasks` of xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store (`mcp/status.json`)]); the queue task record is authoritative for the delivery (lease, attempts, consultations). A creating transition writes `active_tasks` first and the queue record after it; a settling transition records the outcome in the scope and then closes the queue record.
* *Recovery*: The project's recovery after a runtime start records every running worker `killed` and fences its generation (xref:10-job-and-lesson-records.adoc#job-record[Job Record]), then reconciles the queue: a held task's current attempt ends with `end_cause: restart`, its lease is released, and the task is queued again without counting a re-offer; a task its scope lists closed is closed with the scope's outcome; a task its scope no longer lists is closed `lost` (reason `withdrawn`) without a re-offer; a task the scope lists without a queue record is created again `queued`. Each reconciliation appends one audit record.
* *Retention*: A closed queue task record is a retention purge candidate with the job logs (`retention.job_logs_days`, link:../timeouts/03-retention-host-config.adoc#retention-days[Timeouts & Budgets Specification]) once its scope no longer lists it. Usage is never kept here: every task's usage is a metrics row of its scope keyed by its `queue_task_id` (xref:05-metrics-and-quality-report.adoc#metrics-store[Metrics Store (`metrics.json`)]).

[#queue-task-record]
=== Queue Task Record (`queue/<queue_task_id>.json`)

One record per task. A `job llm <entity_kind> role <role> [each <primitive>]` state creates one per entity in the transaction that enters it (kind `work`); a `consult:<role>` link creates one for the consulted role (kind `consultation`, whose `queue_task_id` is the `consultation_id`, link:../model-work/05-consultation.adoc[Model Work Specification, Consultation]). The semantics of every field are those of link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]; this section fixes the record.

* *Status*: `queued` (waiting for a generation of its role), `offered` (leased, not acknowledged), `acknowledged`, `executing`, `consulting` (an own consultation is open), `closed`. An attempt that ends without a result returns the task to `queued`, released at once, and the task is offered again within its re-offer budget (link:../timeouts/01-job-budgets-and-waits.adoc#task-reoffer-budget[Timeouts & Budgets Specification, Task Re-Offer Budget]).
* *Outcome and Reason*: A closed task has exactly one of the outcomes `submitted`, `asked` (with its `question_id`), `infeasible`, or `lost`; a `lost` task names its `reason`: `attempts_spent` (its re-offers are spent), `role_undefined`, `role_unqualified`, or `role_unavailable` (the model caller closed it before any attempt), or `withdrawn` (its state or scope ended while the task was open). `form_downgraded` records that the caller ran a `warm` role `fresh` because only the fresh form qualifies.
* *Lease*: `lease` names the generation the task is leased to, set in the transaction of the offer (for a fresh worker: at its spawn) and cleared at the submit that closes the attempt, at the fence of the generation, and at the withdrawal of an unacknowledged session offer. Every call on the task entity is checked against it.
* *Attempts*: One entry per offer, with its generation, its worker (`null` for a session), its instants, and how it ended. `counts` is `false` for an attempt ended by a restart, a drain, a start failure of a fresh worker, or the withdrawal of a session offer, which spend no re-offer.
* *Consultations*: The asking task lists its consultations in `consultations[]` (their limits: link:../model-work/05-consultation.adoc[Model Work Specification, Consultation]); the consultation task names its asker in `consultation_of`. The answer is recorded on the asker's entry when the consultation closes and delivered once, to the asking generation's next wait, or to the successor in the task's facts after a fence (`delivered_to`).

[#session-generation-record]
=== Session Generation Record (`queue/session-generations.json`)

The generations of the project's interactive sessions (`PM-WORK-5`). `pm-mcp enter`, the first binding of a session relay that finds no current generation, and every new host session the relay reports issue a new generation (`sg-` form, link:../identifiers/01-general-rules-and-registry.adoc#id-generation-id[Identifier Registry, `generation_id`]) for the session identity, which fences every earlier generation of that identity in the same transaction; a call of a fenced generation is refused `generation_fenced`. The identity, the relay's report of a new host session, and the host markers are specified in link:../runtime-model.adoc[Runtime & Interaction Model Specification] (relay) and link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]. Written under the queue lock; fenced entries are removed by the periodic runtime sweep once they are older than the pending entry record maximum age (link:../timeouts/02-runtime-leases-operator-web.adoc#pending-entry-max-age[Timeouts & Budgets Specification]).

[#qualification-record]
== Role Qualification Record (`<set>/qualification/<role>.json`)

The record of one grading of a role's configuration by `pm-operator roles qualify` (`PM-WORK-6`; grading, validity, and invalidation: link:../model-work/01-roles-and-configuration.adoc#qualification[Model Work Specification, Role Qualification]). It lies in the role set that holds the role's effective artifact (for a shipped artifact the operator's record is written to the machine set, for an artifact that names a project extension skill to the project set; paths: link:../filesystem-layout.adoc#role-sets[Filesystem Layout Specification, Role Sets & Task Queue]); the shipped set carries its own records. Written only by the runtime, by atomic write-and-rename; a new grading replaces the record. The operator's level (`qualification.agreement_level`, `qualification.allowed_gap`) is operator configuration (xref:08-project-configuration-local.adoc#local-config[Operator Local Configuration]).
