[#metrics-store]
== Metrics Store (`metrics.json`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-26[PM-WATCH-STORE-26], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-35[PM-WATCH-STORE-35]_

The plan's `metrics.json` holds the model-job and phase measurements that `default:record-metrics` aggregates (`PM-WF-14`, link:../dispatch-and-effort.adoc[Model Jobs & Effort Specification], Post-Return Integrity Invariants). It extends the rule "unmeasured is never `0`" from token usage to every figure it publishes.

* *Rows*: One row per model job (kind `llm`: `job_id`, `role`, `harness`, `model`, `effort`, `phase`, `step_id` or null, `envelope_id` or null with its summed `predicted_cost_tokens` and their basis (`uncalibrated` or `calibrated`), `fate` (the job record's fate) or `job_incomplete`, `cause_class`, `spend_class`, `population`, the usage columns parsed from the harness output through the client profile's `headless.usage` declaration (`token_usage`, `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `tool_uses`, `cost_usd`), each a measured value or `"unmeasured"` (with `not_reported_by_harness` where the harness does not report the field, `output_unparsed` where its output could not be parsed), and the server-measured `duration_ms` with its `duration_basis` and the slot-queue time `queued_ms`), one row per wait slice (`phase`, `wait_reason`, `deliberate`, duration; link:../job-runtime.adoc[Job Runtime Specification], Wait Attribution), one row per phase close (`start_time`, `end_time`, `duration_ms`, `duration_clamped`, `boundary` (`closed`, `re_entered`, or `provisional` with `measured_until` and `excluded_steps`), `step_firings` as a map from step id to firing count), and one row per served document read (Served-Content Ledger below). Work the main session does inline (for example Phase 4 authoring or `create-pr`) has no model-job row; its measurements, where the host reports them, carry the population `main_context`.
* *Served-Content Ledger*: Every `pm_skill`, `pm_skill_file`, and skill `resources/read` served in a plan or epic scope appends `{uri, section?, bytes, plan_id, phase, job_id?, served_at}`; `bytes` is the rendered size served, `0` for an empty section. Every skill document or section the server renders in-band into a model job's prompt file is recorded the same way when the job is spawned. `job_id` is set for a read over a job connection and for an in-band rendering, and is otherwise null. A read without a scope is attributed to no plan. `record-metrics` publishes from these rows the per-document consumption (reads per URI and section, bytes, repeat reads within one job). It measures only what the server serves; a harness's own reads of project files are not observable.
* *Aggregates*: Every sum (per phase, per cause class, per plan) is published as `{value?, rows, rows_unmeasured, population_count, excluded{<class>: count}}` with `rows = measured + Σ excluded`. `value` is omitted when `population_count == 0`. A phase that is still open is reported as a floor, never as a total; Phase 6, which `record-metrics` measures from inside, is recorded `boundary: provisional` with `measured_until` and its `excluded_steps`.
* *Populations*: Every token figure carries a `population` stamp (`model_job` or `main_context`); an absent stamp reads `model_job`. Relations (`=`, `<`, `>`) and sums are formed only between figures of one population. A derived ratio whose denominator population is empty is `not_derivable`, never `0`.
* *Re-Entry*: Re-entry is derived from observables (rows timestamped after the phase's recorded `end_time`), never from a close counter. A re-entered phase is labelled `re_entered` and accumulates across closes.
* *Cause Classes*: `cause_class` (`terminal_error`, `retryable`, `returned_with_findings`, `benign`, `stall`) is a total function over the job fate enum plus `job_incomplete` (link:../dispatch-and-effort/02-dispatch-observability-and-spend.adoc#cause-class[Model Jobs & Effort Specification, Cause Classes]); the server observes every end of a model job, so no unconfirmed class exists. The per-class populations sum to the total model-job population with an asserted residual of `0`; the build-time exhaustiveness check (`PM-IMPL-5`) fails on an unclassified member. A spend decomposition sums to the phase total, with an explicit `unbucketed` class.
* *Spend Classes*: `spend_class` (`submitted`, `findings_only`, `no_product`, `unmeasured`) is derived by the server from what the model job produced (link:../dispatch-and-effort/02-dispatch-observability-and-spend.adoc#spend-accounting-budget-anchors[Model Jobs & Effort Specification, Spend Classes]); it is a separate dimension from `fate` and `cause_class`, and waste is read only from `no_product`.
* *Stall Rate*: A termination with `tasks_remaining > 0` and no blocked cause is `stall`. The stall rate and the `yield_reason` counts are published per plan.
* *Ledger Divergence*: Where two ledgers can diverge (model-job rows vs job records and audit rows), `record-metrics` publishes `union_rows` and a non-blocking `reconciliation{findings_count}` warning. Each ledger states its counting unit.
* *One Writer per Name*: Every metric name has exactly one writer. A second producer over another population uses a different name.
* *Raw Components Only*: Rows persist measured token components and the harness-reported `cost_usd`, never a weighted or priced figure of the server's own. `priced_units` is derived in views from the rows and one named constant table (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#post-run-metrics-and-landing[Phase Workflows Specification, Metric Aggregates]); a change of the weights re-derives every figure, including legacy baselines, from the persisted components.
* *Session Attribution*: A model-job row references the host session whose call entered the job state by its `client_session_id` (the row of the scope's session log, xref:01-format-and-session-log.adoc#scope-session-log[Scope Session Log (`sessions.jsonl`)]; `null` when the host provides none), never by a copy of the client or model identity; the job's own harness, model, and effort are its launch contract, recorded in the job record.

Aggregates are never persisted; they are derived in views from `rows[]`.

[#quality-report]
== Quality Report Record (`quality-report.json`)

The plan's `quality-report.json` is written once per firing of `plan-marshall:plan-retrospective` (`995`) by the server's report engine (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#post-run-quality-report[Phase Workflows Specification, Post-Run Quality Report]). It is derived only from persisted plan stores and from the metrics snapshot composed from them at the report's call (labelled `measured_until`); no model-authored text enters it. A re-fire replaces it atomically, and the store is covered by the digest sidecar (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]).

* *Counts with Populations*: Every published count is a `count` object; a rate is published as numerator and denominator counts, never as a bare ratio. An empty population renders `unmeasurable`; `withheld`, `unmeasured`, and `0` are distinct values. A plan or store the engine cannot read contributes `floor` (a lower bound, never healthy).
* *Report Instruments Never Gate*: `gates_merge` is `false` for every instrument (schema constant); the report is written after the merge and no step reads it as a precondition.
* *One Schema for Both Modes*: A corpus report has exactly this schema; it is a fold over the per-plan results of the same engine.
