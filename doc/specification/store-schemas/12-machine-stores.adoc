== Machine Configuration, Credentials & Security Audit Stores

[#machine-config]
=== Machine Configuration Store (`<PM_MCP_BASE>/machine-config.json`)

Configures machine-wide build and worker concurrency limits, warm LSP pool sizing, the machine-level timeouts and budgets (drain timeout, escalation cap, progress wait bound, language server timeouts, audit rotation age, rotated audit file retention), the machine-wide connection overrides of the client profiles (`client_profiles.<client_id>.connection`, link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification], Machine-Wide Operator Overrides), the outbound proxy (`proxy`), web access (`web`), and `project_defaults`, the machine-wide defaults of the per-project operator keys of `local-config.json` (xref:08-project-configuration-local.adoc#local-config[Operator Local Configuration (`<PM_MCP_BASE>/projects/<project_id>/local-config.json`)], `PM-EXT-6`). The pending entry record age and the lock-wait report threshold are compiled constants (link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle]). Written only by the runtime (on `pm-operator config`, `web.port` included, and `web.enabled` and `web.lan` on `pm-operator web enable|disable`, which take no port option) under `locks/machine-config.lock`; `pm-operator` reads it directly only for the drain timeout that bounds `pm-operator drain` (link:../cli-and-security/01-cli-and-installer.adoc#cli-file-reads[CLI, Coordination & Security Specification, Direct File Reads]). The timeout values, their bounds, and their expiry behaviour are defined in link:../timeouts/03-retention-host-config.adoc#configuration-keys[Timeouts & Budgets Specification]; the `default`, `minimum`, and `maximum` values below equal them.

[#credential-store]
=== Permission-Guarded Credential Store (`<PM_MCP_BASE>/credentials/<credential_key>.json`, `PM-CRED-3`)

When OS keychain access (service `de.cuioss.pm-mcp`) is unavailable (e.g., headless Linux SSH session), Token-Lane credentials fall back to user-only `0600` JSON files inside `<PM_MCP_BASE>/credentials/` (`0700` directory; only `PM_MCP_BASE` relocates it). The file format is `PM-MCP`'s own, with `format_version` and a closed schema (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline]); the naming keeps the project-scoped tier `<PM_MCP_BASE>/credentials/<project>/<credential_key>.json`, which is resolved before the global file, and files are named by credential key (`github`, `gitlab`, `git-https` for the native git and provider integrations, `mcp-<server_id>` for an upstream MCP server, otherwise the key the project configuration names for the integration in its `credential_key`, for example `sonar`; `PM-CRED-1`, link:../identifiers/02-registry-stores-to-web.adoc#id-credential-key[Identifier Registry, `credential_key`]). No entry holds a harness's authentication: a harness CLI uses its own login, which `PM-MCP` neither stores nor exports. A credential file is written only by the runtime, on a `pm-operator credentials` verb (the secret read from the terminal with echo disabled, the file written atomically with mode `0600`) and, for the rotated user refresh token of a `github_app` entry, in the token refresh under `locks/credentials.lock` (link:../cli-and-security/02-credentials-and-operator.adoc#user-access-token[CLI, Coordination & Security Specification, User Access Token]); it is never a template for hand editing. A file with a missing or different `format_version`, an undeclared field, or a field its `auth_type` does not allow is refused with a reason naming the file and the field, and blocks only the step that needs the credential (`credentials_file_invalid`, with the `pm-operator credentials set` command that rewrites it). `PM-MCP` never reads `~/.plan-marshall/credentials/`, `PLAN_MARSHALL_CREDENTIALS_DIR`, or legacy keyring entries (`PM-MIG-2`); credentials enter this store only through `pm-operator credentials`.

The allowed origin for a credential is the origin of the `url` of its operator-owned entry (`PM-CRED-5`), plus, for `github` and `gitlab`, the API origin the provider module derives from it by its compiled rule (`https://github.com` -> `https://api.github.com`; every other host: the `url` origin; link:../cli-and-security/02-credentials-and-operator.adoc#agent-credentials[CLI, Coordination & Security Specification, Agent Credentials of the Native Variant]); the native git transport sends the credential only when the effective remote URL has that origin (`remote_origin_mismatch` otherwise). The team configuration (`.marshall/config/project.json` `integrations`) may only reference a credential key and never decides where a token is sent.

A file exists only for a complete credential: `pm-operator credentials set` refuses to write an empty secret, so no placeholder state exists. The `auth_type` values `none` and `system` of `plan-marshall` have no file: a provider without authentication needs no credential, and the System Lane (the CLI variant of `git`, `github`, `gitlab`) uses the operator's ambient CLI authentication by design (link:../cli-and-security/02-credentials-and-operator.adoc#cli-variant-credentials[CLI, Coordination & Security Specification, Credentials of the CLI Variant]). A GitHub App installation token is derived from the `private_key`, and a user access token from the `refresh_token`, at run time; neither is stored in any backend (link:../cli-and-security/02-credentials-and-operator.adoc#derived-tokens[CLI, Coordination & Security Specification, Short-Lived Derived Tokens]).

[#machine-state-records]
=== Machine State Records (`install-records.json`, `runtime.json`)

Two single-writer records in `<PM_MCP_BASE>/state/` (mode `0600`), each with `format_version` and a closed schema.

*`state/install-records.json`*: written by the runtime on the requests of `pm-operator client install|update|remove` under `locks/install-records.lock` (link:../cli-and-security/01-cli-and-installer.adoc#client-installer[CLI, Coordination & Security Specification, Client Bundle Installer]); read by the runtime (ownership and digest verification, link:../client-profiles/03-bundle-manifest.adoc#_ownership_digest_verification_on_installupdateremove[Client Profiles Specification]; the session row's `bundle_version`) and, read-only, by `pm-mcp enter` and `pm-operator client status` for the drift checks `bundle_outdated` and `bundle_modified` (link:../cli-and-security/01-cli-and-installer.adoc#bundle-drift-notice[CLI, Coordination & Security Specification, Bundle Drift Notice]). One install exists per `(client_id, scope, target_root)`; every owned file, key, and element carries the digest the drift checks compare.

[#web-access-records]
=== Runtime Token & Web Access Records (`run/runtime.token`, `state/web-devices.json`)
_See Requirement link:../../Requirements.adoc#PM-SEC-7[PM-SEC-7: Optional Web Access, Device Pairing & Browser Channel Hardening]_

_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-16[PM-WATCH-CLI-16]_

The records of local trust and browser access (link:../runtime-model/01-processes-and-transport.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]; link:../cli-and-security/03-web-server.adoc#web-server[CLI, Coordination & Security Specification, Web Access & Pairing]). None of their content reaches a model-facing representation (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

*`run/runtime.token`*: not JSON and without `format_version`: the file content is exactly the runtime token, 43 base64url characters without padding and without a trailing newline (256 bits, link:../identifiers/02-registry-stores-to-web.adoc#id-runtime-token[Identifier Registry, runtime token]). Mode `0600` in the `0700` directory `<PM_MCP_BASE>/run/`; written atomically by the runtime at every start before the socket is bound, replacing the previous token; read by every local client after its owner, mode, and no-symlink check; outside every job's read set on Linux with Landlock ABI >= 2; on macOS and on Linux without Landlock a job can read it like any process of the user (link:../job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification, Linux Filesystem Confinement]). A token file that is absent, of another length, or outside the alphabet makes a client refuse with a diagnostic naming the path, never guess.

*`state/web-devices.json`*: the web device store, mode `0600`, written only by the runtime under `locks/web-devices.lock` (pairing, revocation, idle expiry, and the `last_used_at` update at most once per write interval per device, link:../timeouts/02-runtime-leases-operator-web.adoc#device-last-used-granularity[Timeouts & Budgets Specification]). A device secret is never stored, only its SHA-256. An unreadable or invalid store authenticates no device and leaves every other function of the runtime unaffected; `pm-operator web devices revoke --all` rewrites it empty.

          "secret_sha256": { "type": "string", "pattern": "^[0-9a-f]{64}$", "description": "SHA-256 of the UTF-8 device secret (pmw_...); the secret itself is returned once at pairing and never stored." },
          "created_at": { "type": "string", "format": "date-time" },
          "last_used_at": { "type": "string", "format": "date-time", "description": "Last authenticated request, written at most once per write interval (timeouts.adoc#device-last-used-granularity); older than the device idle expiry (timeouts.adoc#device-idle-expiry) expires the device." }
        }
      }
    }
  }
}
----

*Pairing code (in memory only)*: The open pairing is held in the runtime's memory, never persisted: the SHA-256 of the normalized code, the label, `expires_at` (issue plus the pairing code lifetime, link:../timeouts/02-runtime-leases-operator-web.adoc#pairing-code-ttl[Timeouts & Budgets Specification]), and the failure count (at most the pairing failed-attempt limit, link:../timeouts/02-runtime-leases-operator-web.adoc#pairing-attempt-limit[Timeouts & Budgets Specification]). At most one pairing is open; a new one replaces it, a redemption or the failure that reaches the limit removes it. A runtime restart discards it, so a pairing code never survives a restart and nothing about it is recoverable from disk.

*No process record*: The web listener is part of the runtime and has no record and no lock of its own. Its setting is the `web` object of `machine-config.json` (<<machine-config>>); its live state (open or closed, mode, port, and in LAN mode the SHA-256 fingerprint of the DER certificate) is part of the runtime status (`GET /api/v1/status`, link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]), from which `pm-operator status` and `pm-operator web pair|open` take it.

The generated certificate and its private key live in `<PM_MCP_BASE>/web/tls/` (`cert.pem`, `key.pem`; directory `0700`, files `0600`), written only by the runtime on the first LAN enable and reused afterwards.

*Enrolment records*: An enrolment HMAC mismatch appends a `security` record (`event: enrolment_tampered`), an operator re-baselining an `operator` record. An enrolment write that sets or clears `container_engine` appends an `operator` record (`event: container_engine_enabled` or `container_engine_disabled`, `details{project_id, engine}`), naming the Docker-group authority the operator confirmed.

*Credential refresh records*: Every refresh of a GitHub App user access token appends a `credential` record (`event: user_token_refreshed`, `details{credential_key, refresh_expires_at}`, never a token); a refresh that fails appends `event: user_token_refresh_failed` with the provider's reason, and the entry is `credential_check_failed` until the operator runs the device flow again.

*Waiver records*: Every line of a plan's `waivers.jsonl` is mirrored as an `operator` record (`event: waiver_waived` or `waiver_revoked`, `details{plan_id, waiver_id, gate, mode, reason_class}`, xref:14-plan-instance-waivers-questions.adoc#waiver-record[Waiver Record]); the recurrence count of a gate across plans (link:../phase-workflows.adoc[Phase Workflows Specification], Artifact Gate) and the lessons-capture signal are derived from these records by `gate` and `reason_class`. No separate exemption record exists.

*Integration records*: Every git or provider operation, in-process (native variant) or as a job (CLI variant), appends a `job` record whose `details` carry `integration` (`git`, `github`, `gitlab`, `sonar`), `variant` (`native` or `cli`), and `identity`: for the native variant the credential key that authenticated it (`github`, `gitlab`, `git-https`, link:../identifiers/02-registry-stores-to-web.adoc#id-credential-key[Identifier Registry, `credential_key`]; never the secret or a derived token) and the resolved agent identity, for the CLI variant the value `operator_ambient` (link:../cli-and-security/02-credentials-and-operator.adoc#cli-variant-credentials[CLI & Security Specification, Credentials of the CLI Variant]). A native operation refused by the origin check appends a `security` record with `event: remote_origin_mismatch`, `outcome: refused`, and `details{integration, remote, effective_url_host, credential_origin}` (link:../cli-and-security/02-credentials-and-operator.adoc#native-confinement[CLI & Security Specification, Native Operation Confinement]). The operator's selection of a variant in `setup.select-integration-variants` is an `operator` record with `event: integration_variant_selected` and `details{integration, variant}`. These fields are operator and audit data only: they never appear in a model-facing representation, resource, or tool result (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

*Worker, grant, and bootstrap records*: A request over a worker's connection carries `details.job_id`, `details.role`, and `details.generation_id` in every record it causes. The supervisor appends a `job` record `worker_started` and `worker_ended` (`details{job_id, role, form, end_reason}`) per worker; a refused call of a fenced generation a `security` record `generation_fenced` (`details{generation_id, tool}`); a stop of a role's starts after repeated start failures a `job` record `worker_starts_stopped` (`outcome: warning`, `details{role, harness, start_failures, harness_error}`, the harness's own error text, redacted); a task that ended `lost` and sent its state to the conservative fallback a `transition` record `task_fallback` (`details{queue_task_id, role, reason}`, reason `attempts_spent`, `role_undefined`, `class_mismatch`, `role_unqualified`, or `role_unavailable`); and the load of an invalid role artifact an `operator` record `role_invalid` (`details{role, set, reason}`). `pm-operator enrol-harness` appends an `operator` record `harness_enrolled` (also when it re-baselines a tampered file), an accepted self-update an `operator` record `harness_updated`, and a failed HMAC check of `harnesses.json` a `security` record `enrolment_tampered` naming the file (xref:11-enrolment-store.adoc#harness-enrolment-store[Harness Enrolment Store]). Every access grant is mirrored as an `operator` record `access_granted` with `details{plan_id, project_id, access, reason}` (xref:15-screening-and-grants.adoc#grant-record[Access Grant Record]). The `accept` of a screened-suspicious text in a bootstrap appends a `security` record `screen_accepted` with `details{entry_id, item_id, sha256}`. A refused re-check of a bootstrap's `start.create-scope` transaction is scope-less (no plan or epic exists yet): it appends a `transition` record `bootstrap_refused` (`scope_type: workspace`, `details{entry_id, reason}`) and is never counted per plan.

*Web access records*: A successful pairing appends an `operator` record with `event: web_device_paired`, `outcome: succeeded`, and `details{device_id, label, mode}`; a failed redemption a `security` record with `event: web_pairing_failed`, `outcome: refused`, and `details{failures, pairing_invalidated}` (never the submitted code); a revocation an `operator` record with `event: web_device_revoked`, `outcome: succeeded`, and `details{device_id, reason}` (`reason`: `operator` for `pm-operator web devices revoke` or a revocation from the web app, `idle_expired` for the device idle expiry, link:../timeouts/02-runtime-leases-operator-web.adoc#device-idle-expiry[Timeouts & Budgets Specification]), including one record per device for `revoke --all`. An action taken through a paired device carries `details.channel: web` and `details.device_id`; one through `pm-operator` `details.channel: cli`. `pm-operator web enable|disable` have no record form of their own: like every operator verb that changes `machine-config.json` they append one machine-level `operator` record. No record carries a device secret, its hash, or the runtime token (link:../cli-and-security/03-web-server.adoc#web-server[CLI, Coordination & Security Specification, Web Access & Pairing]).

*Stall records*: A plan (or epic) that becomes stalled (link:../runtime-model/04-sessions-and-workers.adoc#stalled-plans[Runtime & Interaction Model Specification]) appends one `transition` record per stall episode with `event: plan_stalled`, `outcome: warning`, `scope_type: plan` (or `epic` for a stalled epic), and `details{state, cause, idle_since, idle_seconds}` (`cause` from the closed set of link:../runtime-model/04-sessions-and-workers.adoc#stalled-plans[Runtime & Interaction Model Specification, Stalled Plans]: `no_progress`); the next transition of the scope ends the episode, and a later stall starts a new one. The record is operator and metrics data only and never appears in a model-facing representation.

*Hash chain (`PM-SEC-6`)*: The canonical line of a record is its exact UTF-8 byte sequence in `audit.jsonl`, excluding the terminating newline. A writer appends only under the log's `FileChannel.lock()`, after reading the current last line to compute `prev_hash`. The writer also maintains the HMAC-anchored head `logs/audit.head` (<<audit-head>>) and, on rotation, a `checkpoint` record plus an entry in the hash-chained index `logs/audit-index.jsonl` (<<audit-index>>; link:../cli-and-security/02-credentials-and-operator.adoc#_security_audit_trail_three_tier_identity_verification[CLI, Coordination & Security Specification, Security Audit Trail]). The runtime verifies incrementally from the last checkpoint at startup; a mismatch, unparsable line, missing log, reset, truncation, or head mismatch is reported to the operator and recorded as an `audit_chain_broken` record (`category: security`, `details.reason` `link_broken | missing | reset | truncated | head_mismatch`, and `details.first_broken_line` for `link_broken`), and no complete record of the log is ever rewritten or repaired; only a torn tail after the anchored head is truncated by the next writer (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline] item 6).
