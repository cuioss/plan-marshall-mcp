[#screen-verdict-cache]
== Screen Verdict Cache (`screen-verdicts.jsonl`)
_See Requirement link:../../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-35[PM-WATCH-DISP-35]_

External text (issue and pull request titles and bodies, review comments and bot findings, analysis-provider messages, upstream MCP results entering a store) passes two guards before it reaches a model as content: the server's deterministic level-1 validator, which cleans it and reports every change, and the level-2 screener, a zero-tool model job of role `screen.effort` that returns a closed verdict per item (link:../dispatch-and-effort/06-untrusted-text-screening.adoc#screener[Model Jobs & Effort Specification, Screener Job]). The screener can only restrict: an item whose verdict is missing, extra, or unparseable counts as `suspicious`. Screened text is still delivered marked untrusted.

* *One Batch per Firing*: Every source unit and every gather firing that ingests external text builds one screening batch (named schema `batch-v1`, link:../dispatch-and-effort/06-untrusted-text-screening.adoc#batch-v1[Model Jobs & Effort Specification, Batch Format]) over its new items. The batch is persisted with the records it came from (the finding records with their `batch_id`, the bootstrap's source record in the pending entry record) and is not stored separately; `batch_id` is a per-scope counter (`BT-<n>`) recorded on each item and in this cache.
* *Cache*: One append-only file per scope, `screen-verdicts.jsonl` in the plan directory, in `epics/<epic_id>/`, and in `workspace/` (which also serves the bootstrap entities it hosts), written in the transaction that settles the screener job. Before a batch is sent, every item whose SHA-256 has a verdict in the scope's cache takes it and is left out; only uncached items are screened, split into several screener jobs above the screening split bound (link:../timeouts/03-retention-host-config.adoc#screening-split-bound[Timeouts & Budgets Specification, Screening split bound]). Only verdicts the screener returned are cached; an item counted `suspicious` fail-closed (job failed, timed out, or answered without the item) is not cached and is screened again by the next firing. The done transaction of a plan bootstrap copies the verdicts of its source items into the new plan's cache.
* *Effect*: In a bootstrap, a `suspicious` item enters a link state that shows the flagged spans: `accept` (the text is used, still marked untrusted; audited) or `back`. Inside a scope, a `suspicious` item is withheld: only its structured fields and `withheld: flagged by screener` are delivered, a withheld finding stays `pending`, and the unit ends through its budget and fallback unless a `met` waiver of its gate lets the plan proceed (xref:03-findings-and-review-records.adoc#_findings_ledger_record_findings_jsonl[Findings Ledger Record]).
* *Integrity*: The cache is covered by its scope's digest sidecar (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]); flagged spans are operator and audit data, never rendered to a model beyond the bootstrap's accept state.

[#grant-record]
== Access Grant Record (`grants.jsonl`)
_See Requirement link:../../Requirements.adoc#PM-SEC-2[PM-SEC-2: Workspace Confinement & Path Traversal Prevention]_

A plan reads or writes only its own project. Access to another enrolled project (its checkout, or its archived plans) exists only through an operator grant: `pm-mcp operator grant-access <plan_id> <project_id> read|read-write --reason <text>` (link:../cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]) appends one line to the plan's append-only `plans/<plan_id>/grants.jsonl`; the runtime executing that verb is its only writer, no link or primitive writes it, and every line is mirrored into the audit log (`access_granted`, xref:12-machine-stores.adoc#audit-log[Audit Log]). The model never requests a grant: an access to another project without a grant for the needed access raises the `precondition_unmet` condition (reason `grant_missing`, `facts.operator_command` naming the verb), whose bounded `retry` re-checks the grants before the phase's fallback. A grant holds until the plan ends: there is no revocation verb and no revoking record, and `abort` of the plan is the only way to stop an issued grant. It is refused for the plan's own project, an unenrolled project, and an ended plan (`plan_ended`). The store is covered by the plan's digest sidecar.

    "reason": { "type": "string", "minLength": 1, "maxLength": 2000 },

      "type": "object",

      }
    },

  }
