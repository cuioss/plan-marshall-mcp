[#plan-instance]
== Plan Instance (`instance/plan.v<N>.pmwf`, `instance/composition.jsonl`)
_See Requirement link:../../Requirements.adoc#PM-WF-13[PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier]_
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-41[PM-WATCH-STORE-41]_

_See Requirement link:../../Requirements.adoc#PM-EXT-7[PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades]_

Every plan executes its own *plan instance*: a DSL unit, stored per version as `instance/plan.v<N>.pmwf`, that the server composes from the templates (the compiled defaults and the project-owned `.marshall/config/*.pmwf`, the `remediation.*` policy units, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]), the composition rules (<<composition-rules>>), and the plan's facts. Facts stay where they are owned and are never copied into the instance: configuration in its stores (xref:07-project-configuration.adoc#project-configuration-store[Project Configuration]), waivers in `waivers.jsonl` (<<waiver-record>>), plan facts (lane, deliverables, footprint, tasks) in the plan stores. The instance carries their *effect* with provenance. It replaces the former `execution-manifest.json` (the step list is the instance) and the former `config_hash` snapshot (the instance header).

* *Storage*: Each version is an immutable file `plans/<plan_id>/instance/plan.v<N>.pmwf` (`N` from `1`, never rewritten, never deleted while the plan exists); the instance is always referred to by this file, and its header `version` is the plan's `instance_version` (link:../identifiers/02-registry-stores-to-web.adoc#id-instance-version[Identifier Registry, Plan Instance Version]). The version in force is `instance_version` of the plan's `mcp/status.json` (xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store]). A version composed by an operator or configuration event (`config_adopted`, `waiver`) is in force from the transition after the one that composed it, never mid-state; a version composed by a server event (`outline`, `plan`, `fallback`, `empty_harvest`, `deliverable_removed`) is in force for the rest of its composing chain, from the transition that enters its target state, so every `auto` state of that chain (for example `finalize.next-step` after `plan.return`) selects from the new version. Completed firings, step records, and history always refer to the version in force when they happened; history is never rewritten.
* *Header*: The first element of every version is its instance header (schema below), which names every input by digest; the DSL body follows. In the `.pmwf` file the header is the single `instance` line after the `workflow` line, serialized as one line of canonical JSON (keys sorted, no insignificant whitespace, UTF-8), so its digest is reproducible (link:../workflow-dsl/09-plan-instance.adoc#instance-header-grammar[Workflow DSL Specification, Instance Header Grammar]). `pm://plan/{plan_id}/instance[/{version}]` returns the DSL text with its header, `pm://plan/{plan_id}/diagram` renders the version in force (active state, pruned elements with reason, waived gates with waiver id), and `pm-operator status` names the version and its last composition event (link:../mcp-tools/03-resource-uris.adoc#_normative_resource_uri_templates[MCP Tools Specification, Resource URI Templates]).
* *Invariants per Version*: The compiled invariants are checked on every composed version before it is written; a version that fails them is never written (the composing transition is refused, and for a server event the plan takes the phase's fallback route with the failed invariant as the gap).
* *Position Rule*: A version is valid only if it contains the current state and every state of the `call_stack` (the adopt rule of the bound unit copy, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification]). State ids are stable across versions, so the current position maps onto the new version unchanged. An operator-triggered event whose version fails the rule is refused (a configuration candidate is then kept, a waiver verb is refused with `position_not_contained`); a server event (`fallback`, `empty_harvest`, `deliverable_removed`, `outline`, `plan`) is composed in the transaction that enters its target state, so the version always contains it.
* *Sub-Units*: The header lists every sub-unit the instance calls (`git.commit_and_push`, the `remediation.*` units) by id and digest; each call site carries its bound arguments with provenance, so one sub-unit serves every call site and is never expanded inline. The verified text of each bound sub-unit is kept as `plans/<plan_id>/mcp/units/<digest>.pmwf` (`<digest>` the SHA-256 of the unit text): content-addressed, written once in the transaction that composes the first version naming the digest, never rewritten, covered by the plan's digest sidecar, and read by the engine instead of the project copy while a version naming it is in force, so an edit of `.marshall/config/*.pmwf` never changes a running call.
* *Readers*: Every former reader of the execution manifest reads the instance: Phase 5 and Phase 6 step selection, verdict currency, and the retrospective's step admission, which reads the version in force when the step would have fired (`not_admitted` = pruned, with the prune reason).

*Composition Events*: The closed `composition_event` enum (link:../identifiers/02-registry-stores-to-web.adoc#id-composition-event[Identifier Registry]): `start` (version 1 in the plan's creation transaction: init and refine routes, both lanes open, posture prunes), `outline` (lane known, the other lane pruned), `plan` (tasks and steps known; provider and footprint prunes; budgets bound), `config_adopted` (an adopted configuration or template change), `waiver` (a `met` waiver, a `raise`, or an `unwaive`), `fallback` (the post-run-only form of the `returned` and `handed_back` routes, pruned steps with reason `returned` / `handed_back`), `empty_harvest` (post-run-only, steps below `900` pruned with reason `empty_harvest`), and `deliverable_removed`. A loop-back re-runs `outline` and `plan`. Every version has exactly one event.

[#composition-rules]
=== Composition Rules
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-89[PM-WATCH-PHASE-89]_

The land restriction (link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane]), the local-only prunes, and every former manifest prune predicate are *data*: one declarative rule file, versioned like the templates, whose rules map a plan fact or an effective configuration value to prunes and policy bindings. Its revision and digest are an input of every instance header.

* *Location*: The shipped default rule file is compiled into the binary (`composition-rules.json`, with its `revision`); it has no project copy in `.marshall/config/` and no operator file overrides it. The phase and sub-workflow templates are already team-owned copies in `.marshall/config/*.pmwf`; only team overrides of the composition rules (and of units that are not project-owned) are deferred (link:../../later-improvements.adoc#_l_5_team_overrides_of_templates_and_composition_rules[Later Improvements, L-5]); until then the shipped rule file applies to every project.
* *Rule Shape*: Each rule has a `when` predicate over one fact (`lane`, `posture`, `derived.push_remote`, `change_type`, a provider configuration key, the operator key `merge.auto_merge`, `recipe_id`), and a `then` of `prune` entries (`element`, `id`, `reason` from the prune-reason enum) and `bind` entries (a policy call site and the argument it fixes, for example `actions: [retry]`). A rule never adds an element that no template declares, never raises a budget, and never names a gate; the compiled invariants are checked on the result.
* *Shipped Rules*: `lane = land` binds every policy call with `actions: [retry]` (no `fix`; `decide` offers `retry` and `step_out`) and prunes task allocation, `loop_back`, and in-branch fix links with reason `land_lane`; an empty `derived.push_remote` prunes `push`, `create-pr`, `ci-verify`, `automatic-review`, and `analysis-roundtrip` with reason `local_only` and keeps `pre-push-quality-gate` and `pre-submission-self-review` (*deliberate change vs. `plan-marshall`*, which drops them); `merge.auto_merge = false` prunes the merge execution, the states `finalize.merge-dispatch`, `finalize.merge-queue-wait`, and `finalize.merge-queue-exit`, with reason `auto_merge_off` (source fact `merge.auto_merge`), so `finalize.merge-barrier` routes `pass` to the ready form of `finalize.hand-back` and the plan ends `handed_back` with `merge_outcome: awaiting_human_merge`; the posture, provider, footprint, change-type, and recipe prunes carry the reasons of the same names.

[#waiver-record]
== Waiver Record (`waivers.jsonl`, `waiver-consumptions.jsonl`)
_See Requirement link:../../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-38[PM-WATCH-STORE-38]_

A waiver is the operator's only influence on the gates and budgets of a running plan: it declares a waivable gate met (`mode: met`) or raises a remediation budget ceiling (`mode: raise`). `plans/<plan_id>/waivers.jsonl` is append-only and has exactly one writer, the runtime executing an operator verb (`pm-operator waive` / `unwaive`, link:../cli-and-security/02-credentials-and-operator.adoc#operator-waive[CLI, Coordination & Security Specification, Waivers]); no primitive has a write capability for it (compiled invariant `INV-GEN-2`). Every line is mirrored to `audit.jsonl`, and every `waived` or `revoked` line composes a new plan instance version (event `waiver`).

* *Plan-Scoped, not HEAD-Bound*: A `met` waiver applies to every evaluation of its gate after it is set, for the rest of the plan (a known-flaky check stays waived after a later push). It can be set at any time until the gate's fallback is taken, including before the plan's first transition and after a failing evaluation; once the fallback of the gate was taken or the plan has ended it is refused (`plan_ended`). The spend check has one evaluation point (`merge.gate-entry`); the operator passes it only with a `met` waiver of gate `spend`.
* *Raise*: `raise` sets the new absolute ceiling of `fix_budget:<policy>` or `retry_budget:<policy>`; `spend` is not raisable. The consumed budget stays the per-plan counter of the status store, so a re-composition never resets it (xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store], `policy_counters`). A value at or below the effective ceiling, or above the compiled hard cap, is refused (`raise_out_of_range`). Revoking a `raise` (`unwaive`) lowers the ceiling from the next budget check on: a counter already above the restored ceiling reads exhausted there, and the unit takes its fallback; no refusal applies to the revocation.
* *Consumption*: A waivable gate admits a failure only through the primitive `waiver.lookup`, which appends one line per evaluation that relies on a `met` waiver to `plans/<plan_id>/waiver-consumptions.jsonl` (`{format_version, waiver_id, gate, at, state_id, head_sha, covered[]}`, `covered` naming the check names, finding ids, or provider conditions it admitted). `waiver-consumptions.jsonl` has exactly one writer, `waiver.lookup`; the waiver store itself is never written by a primitive. Every consumption is listed in the pull request comment and the landing record.
* *Refusals*: `not_waivable` (an unknown gate or one on the non-waivable list: integrity breaches, the footprint and main-checkout guards, job confinement, credentials, security findings, the operator boundary, a build failure, a merge conflict, a provider refusal of the merge), `plan_ended`, `already_consumed` (`unwaive` of a waiver with at least one consumption), `raise_out_of_range`, `position_not_contained` (<<plan-instance>>, Position Rule).

[#waiver-request-record]
=== Waiver Request Record (`mcp/status.json` → `waiver_requests[]`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-40[PM-WATCH-STORE-40]_

A model's `request_waiver` in a remediation unit's `decide` state (offered only when the call's `waiver_wait_seconds > 0` and the failing gate is waivable) files a request and enters the waiver wait. A waiver request is never a question record: it is answered only through the operator channel (`waive` / `unwaive`), never by a model-relayed answer (link:../phase-workflows/01-planning-phases-1-2.adoc[Phase Workflows Specification, Questions]).

The hand-back comment names an expired request.

[#policy-counter]
=== Remediation Budget Accounting (`mcp/status.json` → `policy_counters`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-39[PM-WATCH-STORE-39]_

Budgets are counted per plan and policy class, persisted, and never reset: re-entering a unit, a new `HEAD`, a loop-back, and a re-composition of the instance continue the same counter; a `raise` waiver lifts only the effective ceiling carried in the instance. A step-out consumes no budget.

[source,json]
----
{

[#question-record]
== Question Record (`questions.jsonl`)
_See Requirement link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-40[PM-WATCH-STORE-40]_

Every content question is a server-owned question record, created by a model job through an `ask` link (`ask:TASK-NNN` on a task envelope entity, and each item of the `questions` list of a refine or outline `submit`) or by a server primitive (init classifiers, the optional outline review, workspace setup choices that write team configuration). The store is append-only, one file per scope: `plans/<plan_id>/questions.jsonl`, `epics/<epic_id>/questions.jsonl`, and `workspace/questions.jsonl`. Overrides (waivers, access grants, `abort`, integrity resolutions), choices that write operator configuration, and the choices of a bootstrap (links of `start.choose`, which run before any scope exists) are never question records.

* *Answer Validation*: Every channel passes the same validation: an unknown `branch_key` is refused `invalid_link_args`, a second answer `already_answered`, an answer after expiry `question_expired`. A model-relayed answer (`channel: user_relayed`) is accepted for content questions only.
* *Modes*: `operator` delivers to a human and waits without deadline (the plan shows `awaiting_user` and is listed by stalled-plan detection, link:../runtime-model.adoc#stalled-plans[Runtime & Interaction Model Specification, Stalled Plans]); `model` accepts the model's self-answer at or above the compiled refine confidence threshold (`95`), otherwise continues as `auto`; `none` applies the `recommended` option or `default_assumption` at once (`channel: assumption`); `auto` delivers per `questions.delivery`, waits `questions.wait_seconds` (link:../timeouts/01-job-budgets-and-waits.adoc#question-wait[Timeouts & Budgets Specification, Question Wait]), then takes the compiled fallback of the class.
* *Closure*: A question is closed by exactly one `answered` or `cancelled` line; `abort` and `delete-plan` cancel every open question of the plan. An expiry held by an integrity pause is processed only after the pause ends.
* *Amendments*: An answer creates an `amendments[]` entry only when it changes intent (refine answers still go to `request.md`); the entry names the `question_id` (xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store]).

[#evidence-directory]
== Evidence Directory & Failure Envelope (`evidence/`)

Each remediation unit's gather state gathers per failure class, either by one server-side gathering job (CI logs, provider observations) or, for a class read from the plan's own stores (build, review, qgate, spend, merge conflict), inside the gather state's own transaction (link:../job-runtime/03-parsers-and-gates.adoc#evidence-gathering[Job Runtime Specification, Evidence Gathering]) and records its failures in the plan's evidence directory: the append-only `plans/<plan_id>/evidence/failures.jsonl` (one failure envelope per line) and one excerpt file `plans/<plan_id>/evidence/<evidence_id>.log` per stored log excerpt. Excerpts are untrusted content, redacted before they are written, exposed only as the resource `pm://plan/{plan_id}/evidence/{evidence_id}`, and never inlined into a representation beyond the envelope's `message`.
