[#format-versioning]
== Format Versioning & Atomic Write Discipline
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-17[PM-WATCH-GEN-17], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-25[PM-WATCH-STORE-25], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-37[PM-WATCH-STORE-37]_

[[_format_versioning_atomic_write_discipline]]
1. *Version Envelope*: Every persisted JSON root object and every JSONL header/record must declare `"format_version": 1` (positive integer, one sequence per file kind): the server-owned stores, the git-tracked team configuration files `.marshall/config/*.json` (xref:07-project-configuration.adoc#project-configuration-store[Project Configuration (`.marshall/config/`, `local-config.json`, Effective Configuration; `PM-EXT-6`, `PM-EXT-7`)]), and the operator files (`local-config.json`, `machine-config.json`, the project enrolments, the harness enrolment `harnesses.json`, credential files). A workflow unit (`*.pmwf`) declares its DSL format in its header (`workflow <id> version <n> format <f>`, link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification]). Exempt are Markdown documents (checked by their parsers), plain-text logs, OS primitives, and the raw HMAC key.
+
*Accept exactly one, refuse, never rewrite*: Before 1.0 a binary accepts exactly the current `format_version` of each file kind; there is no migration chain and no startup migration. A reader returns `absent`, `unreadable` (including a missing `format_version`), `format_outdated{file, found, current}`, `format_newer{file, found, current}`, or `parsed`; no reader tolerates an older shape. An outdated or newer file is never modified by a reader: a scope store raises the `precondition_unmet` condition on its scope (reason `format_outdated` or `format_newer`) with the operator command; a team configuration file or workflow unit refuses every scope creation of a bootstrap (re-checked in the bootstrap's `start.create-scope` transaction) and every phase handshake of the project with `format_outdated` or `format_newer` naming the file (link:../mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]); an operator file is refused by the CLI naming the file and the changed keys. *Upgrade path*: a `format_version` bump is listed with the changed keys in the release notes; in-flight scopes follow the drain rule (`pm-mcp drain` reports live scopes; the operator finishes them before upgrading), and the project setup workflow offers the new binary's default changes (a diff for workflow units, a server-rendered rewrite for JSON configuration files, link:../domain-extensions/06-configuration.adoc#config-upgrades[Domain Extensions Specification, Configuration Upgrades]). The migration mechanism for 1.0 and later is decided at 1.0.
2. *Atomic Write-and-Rename*: All JSON file updates are written to a sibling temporary file (`<filename>.tmp.<uuid>`), flushed to disk (`FileChannel.force(true)`), and atomically renamed over the target file (`StandardCopyOption.ATOMIC_MOVE`, `StandardCopyOption.REPLACE_EXISTING`). A store replaced this way is guarded by a sibling lock file, never by a lock on the store file itself (xref:13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)]). Every write to a plan, epic, or workspace store runs as a journaled transaction (<<transaction-journal>>).
3. *Single Writer Set*: Every writer of a `PM-MCP` store runs inside the one `PM-MCP` runtime and serializes through its own locks. Legacy `plan-marshall` never touches `.marshall/` or `<PM_MCP_BASE>`, and `PM-MCP` never writes `.plan/` or `~/.plan-marshall/` (`PM-MIG-2`), so no store is shared and no cross-runtime lock protocol exists.
4. *Absent vs Unparseable*: Every store and document reader returns one of `absent`, `empty`, `parsed`, or `unreadable` (with the failing line or offset). An input that yields no parsable content is `unreadable`, never an empty record and never `absent`. Consumers handle `unreadable` explicitly: they fail closed or report `indeterminate`.
5. *One Wire Shape per Instant*: Every persisted or exchanged instant is an RFC 3339 UTC string (`"format": "date-time"`, `Z` suffix); epoch numbers are never persisted. A process start instant is taken from the OS (`ProcessHandle.Info.startInstant()`) and stored in the same shape. Durations are integers whose field name carries the unit (`duration_ms`, `*_seconds`).
6. *JSONL Append Discipline*: A JSONL store is appended to only under the lock of its store (the scope lock for plan, epic, and workspace stores; the audit lock for `audit.jsonl`; the mailbox leaf lock for a plan's `mcp/mailbox.jsonl`, xref:04-epic-and-change-ledger.adoc#epic-inbox-record[Epic Inbox & Plan Mailbox Records (`inbox.jsonl`, `mcp/mailbox.jsonl`)]), by one `write` on a descriptor opened with `O_APPEND` (`StandardOpenOption.APPEND`), followed by `fsync` (`FileChannel.force(true)`); every appended record ends with a newline. A last line without a trailing newline is a torn tail left by an interrupted append: the next writer, still under the store's lock and before appending, truncates the file to the end of the last complete line and appends an audit record `jsonl_tail_repaired` (`category: store`, `details{store, truncated_bytes, truncated_sha256}`). Lines before the last complete newline are never touched; a malformed complete line stays in place and is reported `unreadable` with its line number (item 4). In `audit.jsonl` a torn tail lies after the anchored head (`audit.head` is updated only after a complete append), so the repair never touches a chained record.
+
*Single exception*: The refresh of `last_seen_at` in the last row of a scope's `sessions.jsonl` (<<_scope_session_log_sessions_jsonl>>) is not an append: it replaces the file by a journaled replace (<<transaction-journal>>) under the scope lock, in which every earlier row stays byte-identical and only that one field of the last row changes. No other JSONL store is ever rewritten.

[#transaction-journal]
=== Transaction Journal (`mcp/transaction-journal.json`)

Every write to the server-owned stores of a plan, epic, or workspace scope runs as one transaction under the scope lock, recorded in the per-scope transaction journal `mcp/transaction-journal.json` in the scope's metadata directory of the per-project machine store (`plans/<plan_id>/mcp/`, `epics/<epic_id>/`, `workspace/mcp/`, link:../filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]). A single-store write is a transaction with one target; there is no second write path.

. *Stage*: Write the new content of every replaced store to its sibling temporary file (`<file>.tmp.<transaction_id>`), and the bytes of every JSONL append to `<file>.append.<transaction_id>`; `fsync` each.
. *Journal*: Write `mcp/transaction-journal.json` (atomic write-and-rename, `fsync` of the file and of `mcp/`) listing every target store with its staged file and its new size and SHA-256.
. *Apply*: Rename every staged file over its store (`ATOMIC_MOVE`) and append every staged JSONL block (item 6 above), then `fsync` the parent directories.
. *Digests*: Where the scope keeps a digest sidecar (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]), write it with the new digests taken from the journal (atomic write-and-rename).
. *Close*: Delete the journal and `fsync` `mcp/`; only then is the scope lock released.

*Recovery*: At runtime start, and lazily on the first call that addresses a scope, the runtime takes the scope lock and rolls an existing journal forward: a target whose current size and SHA-256 equal the journal's is already applied; otherwise its staged file is renamed over it (replace), or the file is truncated to `size_before` and the staged block appended (append). It then writes the sidecar (where the scope keeps one) from the journal, deletes the journal, and records a `transaction_rolled_forward` audit record. Digests are recorded only on this path (a transaction or its roll-forward); there is no other rule that re-records a digest. A journal whose target has neither the new digest nor its staged file is an invariant violation: the engine raises the `integrity_breach` condition (kind `store_tampered`) for that store. Orphaned staged files without a journal belong to a transaction that never journaled and are deleted by recovery. The project's lesson store follows the same protocol with its journal `lessons/.transaction-journal.json` of the machine store under the lesson store lock.

[#scope-session-log]
== Scope Session Log (`sessions.jsonl`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-1[PM-WATCH-STORE-1]_

[[_scope_session_log_sessions_jsonl]]
Every scope keeps a session log in the per-project machine store (link:../filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), append-only apart from the `last_seen_at` refresh of its last row (the single exception to the JSONL append discipline, <<format-versioning>> item 6): `plans/<plan_id>/sessions.jsonl`, `epics/<epic_id>/sessions.jsonl`, or `workspace/sessions.jsonl` (the project's workspace scope, link:../filesystem-layout.adoc#workspace-home[Filesystem Layout Specification, Workspace Home]). Each row records one host session that entered or addressed the scope. The *current identity* of the scope is its last row: every scope-addressed MCP call resolves the client profile from it (`PM-ARCH-4`); the project is the store the log lives in, never a path recorded in a row.

* *Appended by `pm-mcp enter`*: Every `pm-mcp enter` on an existing scope appends one row (link:../cli-and-security/01-cli-and-installer.adoc#_entry_identity_recording_pm_mcp_enter[CLI, Coordination & Security Specification, Entry Identity Recording]).
* *Appended by the server*: When a scope-addressed call carries a `PM-MCP-Client-Session` header (link:../runtime-model.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]) whose value differs from the `client_session_id` of the scope's last row, the server appends a row for that session in a short transaction under the scope lock, outside any snapshot read. Such a row keeps the declared `client` of the previous row (a declaration is only ever made by `pm-mcp enter`), takes `client_detected` from the connection's MCP `clientInfo.name`, and records `client_build: null` (the version probe runs only in `pm-mcp enter`).
* *Job Connections Append Nothing*: A request authenticated by a job token (`PM-MCP-Job-Token`, sent by the job relay `pm-mcp serve --job` of a model job, link:../runtime-model.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]) never appends a row, never refreshes `last_seen_at`, and never triggers a client handover: it takes its client profile from its job record (xref:10-job-and-lesson-records.adoc#job-record[Job Record]), and its audit records carry the `job_id`.
* *`last_seen_at`*: The server refreshes `last_seen_at` of the last row at most once per refresh interval per scope (link:../timeouts/02-runtime-leases-operator-web.adoc#session-last-seen-refresh[Timeouts & Budgets Specification, Session Row `last_seen_at` Refresh Interval]), by a journaled replace of the file in which every earlier row stays byte-identical; no other field of any row is ever changed, and no earlier row is ever touched.
* *Pending Entry Record*: When `pm-mcp enter … plan|epic` names no live scope, it writes a pending entry record `pending/<entry_id>.json` of the per-project machine store and prints the `entry_id` (<<pending-entry-record>>). The record is the state store of that entry's bootstrap (`bootstrap-plan` or `bootstrap-epic`, the entity `<entry_id>` hosted by the workspace scope). In the bootstrap's `start.create-scope` transaction the engine creates the scope from it: its `session` becomes the first row of the new scope's `sessions.jsonl`, and for a plan its `from_epic` is copied into `mcp/status.json` `origin.epic_id` (the single carrier of epic membership, xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store (`mcp/status.json`)]). The record is deleted in the transaction that enters a terminal of the bootstrap. A deleted `entry_id` no longer exists, so each pending record creates at most one scope.
* *History in the Log*: The session history of a scope is the log itself. A row whose declared `client` differs from the previous row's additionally appends an `identity` audit record (`event: entry_handover`, `details` with the previous and the new `client` and `client_session_id`, xref:12-machine-stores.adoc#audit-log[Security & Transition Audit Log (`<PM_MCP_BASE>/logs/audit.jsonl`, `PM-SEC-6`)]).
* *Integrity*: `sessions.jsonl` follows the JSONL append discipline (<<format-versioning>> item 6, including its single stated exception for the `last_seen_at` refresh) and is covered by the scope's digest sidecar (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]).

[#pending-entry-record]
=== Pending Entry Record (`pending/<entry_id>.json`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-42[PM-WATCH-STORE-42]_

The pending entry record carries what the user named at `pm-mcp enter` and the state of the entry's bootstrap until a terminal of the bootstrap deletes it:

* *Written under the workspace lock*: `pm-mcp enter` (through the runtime) creates the record, and every bootstrap transition replaces it, each as a journaled transaction of the workspace scope under `locks/workspace.lock` (<<transaction-journal>>); the record is covered by the workspace scope's digest sidecar (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]). A digest mismatch pauses only that bootstrap entity (`integrity_breach`, kind `store_tampered`), ended by `pm-mcp operator accept-edit workspace pending/<entry_id>.json` or by the pending-record sweep; no other entry and no workspace workflow is affected.
* *What the user named, unvalidated*: `kind`, `requested_id`, and `hint` are recorded as given; `start.resolve` and the source units validate them. `hint` is the user's own words, relayed by the host entry command; it is shown to the model as facts of the bootstrap and never parsed by the server into a source.
* *Bootstrap state*: `bootstrap` holds the entity's state position, its call frames (the called source unit), its condition overlay, the source record a source unit returned with `done`, the commit options chosen in `start.ready`, and the reason of the last refused re-check of the `start.create-scope` transaction. A source record keeps the fetched external text only in its level-1-cleaned form with its screen verdict (xref:15-screening-and-grants.adoc#screen-verdict-cache[Screen Verdict Cache]); a `suspicious` item is used only after the audited `accept` of its link state.
* *Addressing*: The model addresses the entry as `pm_state` / `pm_do` with `plan_id: NO_PLAN` and `entity: <entry_id>`; a call naming a deleted or swept `entry_id` is `scope_not_found`. The pending-record sweep removes records older than the maximum age (link:../timeouts/02-runtime-leases-operator-web.adoc#pending-entry-max-age[Timeouts & Budgets Specification, Pending Entry Record Maximum Age]).
