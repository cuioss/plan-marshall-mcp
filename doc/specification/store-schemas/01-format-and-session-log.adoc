[#format-versioning]
== Format Versioning & Atomic Write Discipline
_Implementation watch: link:../../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-17[PM-WATCH-GEN-17], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-25[PM-WATCH-STORE-25], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-37[PM-WATCH-STORE-37]_

[[_format_versioning_atomic_write_discipline]]
1. *Version Envelope*: Every persisted JSON root object and every JSONL header/record must declare `"format_version": 1` (positive integer, one sequence per file kind): the server-owned stores, the git-tracked team configuration files `.marshall/config/*.json` (xref:07-project-configuration.adoc#project-configuration-store[Project Configuration (`.marshall/config/`, `local-config.json`, Effective Configuration; `PM-EXT-6`, `PM-EXT-7`)]), and the operator files (`local-config.json`, `machine-config.json`, the project enrolments, the harness enrolment `harnesses.json`, credential files). A workflow unit (`*.pmwf`) declares its DSL format in its header (`workflow <id> version <n> format <f>`, link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification]). Exempt are Markdown documents (checked by their parsers), plain-text logs, OS primitives, and the raw HMAC key.
+
*Accept exactly one, refuse, never rewrite*: Before 1.0 a binary accepts exactly the current `format_version` of each file kind; there is no migration chain and no startup migration. A reader returns `absent`, `unreadable` (including a missing `format_version`), `format_outdated{file, found, current}`, `format_newer{file, found, current}`, or `parsed`; no reader tolerates an older shape. An outdated or newer file is never modified by a reader: a scope store raises the `precondition_unmet` condition on its scope (reason `format_outdated` or `format_newer`) with the operator command; a team configuration file or workflow unit refuses every scope creation of a bootstrap (re-checked in the bootstrap's `start.create-scope` transaction) and every phase handshake of the project with `format_outdated` or `format_newer` naming the file (link:../mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]); an operator file is refused by the operator CLI (`pm-operator`) naming the file and the changed keys. *Upgrade path*: a `format_version` bump is listed with the changed keys in the release notes; in-flight scopes follow the drain rule (`pm-operator drain` reports live scopes; the operator finishes them before upgrading), and the project setup workflow offers the new binary's default changes (a diff for workflow units, a server-rendered rewrite for JSON configuration files, link:../domain-extensions/06-configuration.adoc#config-upgrades[Domain Extensions Specification, Configuration Upgrades]). The migration mechanism for 1.0 and later is decided at 1.0.
2. *Atomic Write-and-Rename*: All JSON file updates are written to a sibling temporary file (`<filename>.tmp.<uuid>`), flushed to disk (`FileChannel.force(true)`), and atomically renamed over the target file (`StandardCopyOption.ATOMIC_MOVE`, `StandardCopyOption.REPLACE_EXISTING`). A store replaced this way is guarded by a sibling lock file, never by a lock on the store file itself (xref:13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)]). Every write to a plan, epic, or workspace store runs as a journaled transaction (<<transaction-journal>>).
3. *Single Writer Set*: Every writer of a `PM-MCP` store runs inside the one `PM-MCP` runtime and serializes through its own locks. Legacy `plan-marshall` never touches `.marshall/` or `<PM_MCP_BASE>`, and `PM-MCP` never writes `.plan/` or `~/.plan-marshall/` (`PM-MIG-2`), so no store is shared and no cross-runtime lock protocol exists.
4. *Absent vs Unparseable*: Every store and document reader returns one of `absent`, `empty`, `parsed`, or `unreadable` (with the failing line or offset). An input that yields no parsable content is `unreadable`, never an empty record and never `absent`. Consumers handle `unreadable` explicitly: they fail closed or report `indeterminate`.
5. *One Wire Shape per Instant*: Every persisted or exchanged instant is an RFC 3339 UTC string (`"format": "date-time"`, `Z` suffix); epoch numbers are never persisted. A process start instant is taken from the OS (`ProcessHandle.Info.startInstant()`) and stored in the same shape. Durations are integers whose field name carries the unit (`duration_ms`, `*_seconds`).
6. *JSONL Append Discipline*: A JSONL store is appended to only under the lock of its store (the scope lock for plan, epic, and workspace stores; the audit lock for `audit.jsonl`; the mailbox leaf lock for a plan's `mcp/mailbox.jsonl`, xref:04-epic-and-change-ledger.adoc#epic-inbox-record[Epic Inbox & Plan Mailbox Records (`inbox.jsonl`, `mcp/mailbox.jsonl`)]), by one `write` on a descriptor opened with `O_APPEND` (`StandardOpenOption.APPEND`), followed by `fsync` (`FileChannel.force(true)`); every appended record ends with a newline. A last line without a trailing newline is a torn tail left by an interrupted append: the next writer, still under the store's lock and before appending, truncates the file to the end of the last complete line and appends an audit record `jsonl_tail_repaired` (`category: store`, `details{store, truncated_bytes, truncated_sha256}`). Lines before the last complete newline are never touched, and no JSONL store is ever rewritten, except by the workspace-row retention purge of `pm-operator sweep --apply` (xref:13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Evidence-Based Removal Sweeps]); a malformed complete line stays in place and is reported `unreadable` with its line number (item 4). A *versioned* JSONL store, whose records change (`findings.jsonl` keyed by `finding_id`, `review-participation.jsonl` keyed by `(pr_number, round, bot_kind)`, xref:03-findings-and-review-records.adoc#_findings_ledger_record_findings_jsonl[Findings Ledger Record]), appends the full record again at every change: the current record of a key is the last readable line with that key, and the earlier lines are its history. In `audit.jsonl` a torn tail lies after the anchored head (`audit.head` is updated only after a complete append), so the repair never touches a chained record.

[#transaction-journal]
=== Transaction Journal (`mcp/transaction-journal.json`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-44[PM-WATCH-STORE-44], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-47[PM-WATCH-STORE-47], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-49[PM-WATCH-STORE-49]_

Every write to the server-owned stores of a plan, epic, or workspace scope runs as one transaction under the scope lock, recorded in the per-scope transaction journal `mcp/transaction-journal.json` in the scope's metadata directory of the per-project machine store (`plans/<plan_id>/mcp/`, `epics/<epic_id>/`, `workspace/mcp/`, link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]). A single-store write is a transaction with one target. A journal lists only targets of its own scope. Store paths of a plan or epic scope are relative to its scope directory (`plans/<plan_id>/`, `epics/<epic_id>/`); those of the workspace scope are relative to the project store root `projects/<project_id>/`, because its stores include the pending entry records `pending/<entry_id>.json` beside `workspace/`. The same path base keys the scope's digest sidecar and names a store in `pm-operator accept-edit`.

. *Stage*: Write the new content of every replaced store to its sibling temporary file (`<file>.tmp.<transaction_id>`), and the bytes of every JSONL append to `<file>.append.<transaction_id>`; `fsync` each.
. *Journal*: Write `mcp/transaction-journal.json` (atomic write-and-rename, `fsync` of the file and of `mcp/`) listing every target store with its staged file, its new size and SHA-256, and for an append its size before the append.
. *Apply*: Rename every staged file over its store (`ATOMIC_MOVE`) and append every staged JSONL block (item 6 above), then `fsync` the parent directories.
. *Digests*: Where the scope keeps a digest sidecar (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]), write it with the new digests taken from the journal (atomic write-and-rename).
. *Close*: Delete the journal and `fsync` `mcp/`; only then is the scope lock released.

*Recovery*: At runtime start, and lazily on the first call that addresses a scope, the runtime takes the scope lock and rolls an existing journal forward: a target whose current size and SHA-256 equal the journal's is already applied; otherwise its staged file is renamed over it (replace), or the file is truncated to `size_before` and the staged block appended (append). It then writes the sidecar (where the scope keeps one) from the journal, deletes the journal, and records a `transaction_rolled_forward` audit record. Digests are recorded only on this path (a transaction or its roll-forward); there is no other rule that re-records a digest. A journal whose target has neither the new digest nor its staged file is an invariant violation: the engine raises the `integrity_breach` condition (kind `store_tampered`) for that store. Orphaned staged files without a journal belong to a transaction that never journaled and are deleted by recovery. The project's lesson store follows the same protocol with its journal `lessons/.transaction-journal.json` of the machine store under the lesson store lock.

*Writes outside the scope*: A transition that also writes outside its scope (another scope, the lesson store, the job records, the task queue) never extends its journal. It writes in a fixed order, the authoritative store first, each further write as a transaction of its own store under that store's lock, and the runtime's startup recovery derives every later write from the authoritative store (link:../runtime-model/02-startup-recovery-drain.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery], cross-scope reconciliation). Each reconciliation appends one audit record.

* *`start.create-scope`*: the new scope (authoritative; a plan's directory is built complete in the sibling temporary directory `plans/.init-<entry_id>/` and published by one atomic directory rename to `plans/<plan_id>/`; for a new epic, its git-tracked ledger before its machine scope, so a crash between them leaves a ledger the epic bootstrap adopts), then for a `local_changes` plan the capture ref `refs/pm-mcp/captures/<plan_id>` at the recorded `captured_changes.snapshot_sha` (xref:06-task-and-references.adoc#_references_footprint_store_schema_references_json[References & Footprint Store Schema (`references.json`)]), then the epic queue row (`running`, `started_at`, xref:04-epic-and-change-ledger.adoc#epic-queue-row[Epic Queue Row]), then the lesson claim (xref:10-job-and-lesson-records.adoc#lesson-record[Lesson Record]), then the deletion of the pending entry record (<<pending-entry-record>>). A plan is live when `plans/<plan_id>/mcp/status.json` exists; every enumeration of live plans lists only such directories. Recovery: a temporary init directory `plans/.init-*` is deleted (no transaction survives a restart); a non-terminal plan whose capture ref is missing gets it re-created at its `snapshot_sha`; a plan with `origin.epic_id` whose epic queue row is still unstarted (`started_at: null`) sets the row `running` with the plan's creation instant as `started_at`; a non-terminal plan created from a lesson whose lesson is unclaimed claims it; a pending entry record whose plan or epic exists is deleted.
* *Job states*: the scope's `active_job` (authoritative for which job a state owns, xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store (`mcp/status.json`)]), then the job record in `jobs/` (authoritative for the job's fate, xref:10-job-and-lesson-records.adoc#job-record[Job Record]). Recovery: an `active_job` that names a job without a record is settled `killed` (the job never started).
* *Worker end*: the job record (fate, fenced generation, revoked token; authoritative for the generation), then the queue task record (the held task's attempt ended, its lease released). Recovery: a task leased to a generation whose job record has ended is released and queued again like a task held at a restart (xref:16-task-queue.adoc#task-queue[Task Queue], Recovery).
* *Queue tasks*: `active_tasks` first, then the queue task record (xref:16-task-queue.adoc#task-queue[Task Queue], Two Authorities and Recovery).
* *Plan end*: the plan's terminal transaction (authoritative for its `outcome`), then the lesson store transaction: a plan ending `merged` retires its claimed lesson, every other outcome releases the claim (xref:10-job-and-lesson-records.adoc#lesson-record[Lesson Record], Claim). Recovery: a lesson whose `claim.plan_id` names a terminal or archived plan is retired or released per that plan's recorded outcome, and released when the plan no longer resolves.
* *Late findings*: the carry-out of a blocking finding after the merge (xref:03-findings-and-review-records.adoc#_findings_ledger_record_findings_jsonl[Findings Ledger Record], Late Findings Are Carried Out) writes the destination first (the `process_finding` message under the epic lock, or the seeded lesson under the lesson store lock), because the destination assigns the `ref`; then the plan's transaction sets the finding `carried` with `carried_to`. A message appended to the kept landing envelope is part of the plan's own transaction. Recovery derives nothing: a crash between the two leaves the finding `pending` without `carried_to`, and the resumed carry-out carries it again; the accepted cost is a duplicate notice of a debt that stays visible, never a lost one.
* *`pm-mcp enter`*: the session generation record (authoritative for the generation; issuing it fences the earlier generations, xref:16-task-queue.adoc#session-generation-record[Session Generation Record]) under the queue lock, then the entry row (<<scope-session-log>>) or the pending entry record under the scope lock, each its own transaction. Recovery derives nothing: a crash between them leaves an issued generation without its history row (accepted loss, since no call resolves anything from the row), and the failed `pm-mcp enter` is repeated.

[#scope-session-log]
== Scope Session Log (`sessions.jsonl`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-1[PM-WATCH-STORE-1]_

[[_scope_session_log_sessions_jsonl]]
Every scope keeps an append-only session log in the per-project machine store (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]): `plans/<plan_id>/sessions.jsonl`, `epics/<epic_id>/sessions.jsonl`, or `workspace/sessions.jsonl` (the project's workspace scope, link:../filesystem-layout/03-project-store.adoc#workspace-home[Filesystem Layout Specification, Workspace Home]). Each row is the entry row of one `pm-mcp enter` on the scope. The log is history and audit data: no call resolves anything from it, a session's call is rendered from the client its relay declares, and a worker's call from its job record (`PM-ARCH-4`, `PM-CLIENT-3`).

* *Appended only by `pm-mcp enter`*: Every `pm-mcp enter` on an existing scope appends one row (link:../cli-and-security/01-cli-and-installer.adoc#_entry_identity_recording_pm_mcp_enter[CLI, Coordination & Security Specification, Entry Identity Recording]). No other call, connection, or transition appends a row, and no row is ever changed.
* *Session Generation*: The row records the session generation that the entry issued (`generation_id`, `sg-` form, link:../identifiers/01-general-rules-and-registry.adoc#id-generation-id[Identifier Registry, `generation_id`]). The generation itself is held in the session generation record of the task queue (xref:16-task-queue.adoc#session-generation-record[Session Generation Record]), which fences earlier generations; the row is its history.
* *Worker Connections Append Nothing*: A request authenticated by a job token (`PM-MCP-Job-Token`, sent by the job relay `pm-mcp serve --job` of a worker) never appends a row: its identity is its job record (xref:10-job-and-lesson-records.adoc#job-record[Job Record]), and its audit records carry its `job_id`, `role`, and `generation_id`.
* *Pending Entry Record*: When `pm-mcp enter … plan|epic` names no live scope, it writes a pending entry record `pending/<entry_id>.json` of the per-project machine store and prints the `entry_id` (<<pending-entry-record>>). The record is the state store of that entry's bootstrap (`bootstrap-plan` or `bootstrap-epic`, the entity `<entry_id>` hosted by the workspace scope). In the bootstrap's `start.create-scope` transaction the engine creates the scope from it: its `session` becomes the first row of the new scope's `sessions.jsonl`, and for a plan its `from_epic` is copied into `mcp/status.json` `origin.epic_id` (the single carrier of epic membership, xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store (`mcp/status.json`)]). The record is deleted in the workspace transaction that enters a terminal of the bootstrap, after the new scope is written (<<transaction-journal>>, Writes outside the scope). A deleted `entry_id` no longer exists, so each pending record creates at most one scope.
* *Server-Started Plans*: A plan that the server starts for a launchable row of an epic (link:../model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]) runs the same plan bootstrap from a pending entry record that the server writes itself, with `session: null` and `from_epic` set; its `sessions.jsonl` starts empty and gains a row only when a session enters the plan.
* *Identity Changes*: A row whose declared `client` differs from the previous row's additionally appends an `identity` audit record (`event: entry_client_changed`, `details` with the previous and the new `client` and `client_session_id`, xref:12-machine-stores.adoc#audit-log[Security & Transition Audit Log (`<PM_MCP_BASE>/logs/audit.jsonl`, `PM-SEC-6`)]); it changes nothing else.
* *Integrity*: `sessions.jsonl` follows the JSONL append discipline (<<format-versioning>> item 6) and is covered by the scope's digest sidecar (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]).

[#pending-entry-record]
=== Pending Entry Record (`pending/<entry_id>.json`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-42[PM-WATCH-STORE-42]_

The pending entry record carries what the user named at `pm-mcp enter` and the state of the entry's bootstrap until a terminal of the bootstrap deletes it:

* *Written under the workspace lock*: `pm-mcp enter` (through the runtime) creates the record, and every bootstrap transition replaces it, each as a journaled transaction of the workspace scope under `locks/workspace.lock` (<<transaction-journal>>); the record is covered by the workspace scope's digest sidecar (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]). A digest mismatch pauses only that bootstrap entity (`integrity_breach`, kind `store_tampered`), ended by `pm-operator accept-edit workspace pending/<entry_id>.json` or by the pending-record sweep; no other entry and no workspace workflow is affected.
* *What the user named, unvalidated*: `kind`, `requested_id`, and `hint` are recorded as given (for a server-started plan: `kind: plan`, the row's `plan_id` as `requested_id`, `hint: null`); `start.resolve` and the source units validate them. `hint` is the user's own words, relayed by the host entry command; it is shown to the entry session as facts of the bootstrap and never parsed by the server into a source.
* *Bootstrap state*: `bootstrap` holds the entity's state position, its call frames (the called source unit), its condition overlay, the source record a source unit returned with `done`, the commit options chosen in `start.ready`, and the reason of the last refused re-check of the `start.create-scope` transaction. A source record keeps the fetched external text only in its level-1-cleaned form with its screen verdict (xref:15-screening-and-grants.adoc#screen-verdict-cache[Screen Verdict Cache]); a `suspicious` item is used only after the audited `accept` of its link state.
* *Addressing*: The entry session addresses the entry as `pm_state` / `pm_do` with `plan_id: NO_PLAN` and `entity: <entry_id>`; a call naming a deleted or swept `entry_id` is `scope_not_found`. The pending-record sweep removes records older than the maximum age (link:../timeouts/02-runtime-leases-operator-web.adoc#pending-entry-max-age[Timeouts & Budgets Specification, Pending Entry Record Maximum Age]).

  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/pending-entry.json",
