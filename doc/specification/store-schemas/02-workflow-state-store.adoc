== Workflow State Store (`mcp/status.json`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-1[PM-WATCH-PHASE-1], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-40[PM-WATCH-PHASE-40], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-69[PM-WATCH-PHASE-69], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-3[PM-WATCH-STORE-3], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-48[PM-WATCH-STORE-48], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-51[PM-WATCH-STORE-51], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-57[PM-WATCH-STORE-57]_

Tracks the authoritative state machine position, phase, persisted sub-workflow `call_stack`, active jobs and the job bound to the current job state (`active_job`), the queue tasks of the current model state (`active_tasks`), the pending condition overlay, the plan instance version in force, the remediation policy counters, the identifier counters of the scope (`counters`), pending waiver requests, recorded gaps, per-step outcome records, the plan outcome, and composite wait facts for a plan, an epic, or the project's workspace scope (`PM-ARCH-6`, `PM-WF-7`, `PM-WF-13`, `PM-WF-16`, `PM-IMPL-7`). The plan's instance files, waivers, questions, and evidence are separate stores (xref:14-plan-instance-waivers-questions.adoc#plan-instance[Plan Instance, Waivers, Questions & Evidence]). Store digests live in the sidecar `mcp/digests.json` (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]). The values of the `state` field (and the `phase` value each state carries) are catalogued in the link:../state-catalogue.adoc[State Catalogue].

* *Step Records Count Firings*: Every firing of a step appends to its `firings[]`; a re-fire never replaces the history. When `VerdictCurrencyEvaluator` decides to re-fire, the step's `outcome` is set to `unverified` before the step runs and is then replaced by the new firing's terminal outcome, so a prior `done` never survives a re-fire. The current `outcome` and `head_at_completion` are always those of the last firing; no force flag exists. A requested outcome change that the engine refuses appends a firing with `refused` set and leaves no stale outcome silently current. Re-fire counts per cause are `firings` minus one, grouped by `cause`, never counted from log lines. A record without `assurance_verdict` reads `unadjudicated`, never as a pass.
* [[epic-linkage]]*Origin and Epic Linkage*: Epic membership has one carrier, `origin.epic_id`: the server writes `from_epic` into the pending entry record of a plan it starts for a launchable epic row (xref:01-format-and-session-log.adoc#pending-entry-record[Pending Entry Record]), `source-epic-row` verifies the queue row, and the `start.create-scope` transaction of the plan bootstrap copies it into `origin.epic_id`; no tool parameter and no session row carries epic membership. Every consumer (landing emission, outbox link offering, epic observation) reads epic membership from `origin.epic_id` through one resolver, which reads the active orchestrator root and the archived orchestrator root (link:../filesystem-layout/03-project-store.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]) and derives `epic_linkage`: `not_orchestrated` iff `origin.epic_id` is null; `detached` iff it names a terminal epic (archived or aborted, its directory in the archived root); `indeterminate` iff it is set but the epic's header `epic.json` (xref:04-epic-and-change-ledger.adoc#epic-header[Epic Header (`epic.json`)]) is found readable in neither root; otherwise `orchestrated`. Every consumer treats `detached` like `not_orchestrated`: no landing emission to an inbox, late findings seeded as lessons, no outbox link; the plan runs to its own outcome. `indeterminate` is never read as `not_orchestrated`.
* *Amendments*: Every intent-changing answer after refinement appends an `amendments[]` entry with its `question_id`; every later representation that renders the request (outline review, `create-pr`, landing) includes the amendments in order.
* *No Operator Decision State*: The store holds no pending operator decision and no merge authorization: the operator acts only through waivers (xref:14-plan-instance-waivers-questions.adoc#waiver-record[Waiver Record]), cross-project access grants (xref:15-screening-and-grants.adoc#grant-record[Access Grant Record]), `abort`, `delete-plan`, and the integrity resolutions, none of which waits in this store.
