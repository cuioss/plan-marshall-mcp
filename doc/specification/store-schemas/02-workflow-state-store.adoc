== Workflow State Store (`mcp/status.json`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-1[PM-WATCH-PHASE-1], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-40[PM-WATCH-PHASE-40], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-69[PM-WATCH-PHASE-69], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-3[PM-WATCH-STORE-3]_

Tracks the authoritative state machine position, phase, persisted sub-workflow `call_stack`, active jobs and the job bound to the current job state (`active_job`), the pending condition overlay and operator decision, loop-back iteration counters, per-step outcome records, merge authorizations, and composite wait facts for a plan, an epic, or the project's workspace scope (`PM-ARCH-6`, `PM-WF-7`, `PM-WF-13`, `PM-WF-16`, `PM-IMPL-7`). Store digests live in the sidecar `mcp/digests.json` (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]). The values of the `state` field (and the `phase` value each state carries) are catalogued in the link:../state-catalogue.adoc[State Catalogue].

* *Step Records Count Firings*: Every firing of a step appends to its `firings[]`; a re-fire never replaces the history. When `VerdictCurrencyEvaluator` decides to re-fire, the step's `outcome` is set to `unverified` before the step runs and is then replaced by the new firing's terminal outcome, so a prior `done` never survives a re-fire. The current `outcome` and `head_at_completion` are always those of the last firing; no force flag exists. A requested outcome change that the engine refuses appends a firing with `refused` set and leaves no stale outcome silently current. Re-fire counts per cause are `firings` minus one, grouped by `cause`, never counted from log lines. A record without `assurance_verdict` reads `unadjudicated`, never as a pass.
* *Origin and Epic Linkage*: Epic membership has one carrier, `origin.epic_id`: `pm-mcp enter --from-epic` writes `from_epic` into the pending entry record (xref:01-format-and-session-log.adoc#scope-session-log[Scope Session Log (`sessions.jsonl`)]), and `pm_start` copies it into `origin.epic_id`; `pm_start` accepts no epic parameter, and no session row carries epic membership. Every consumer (landing emission, outbox link offering, epic observation) reads epic membership from `origin.epic_id` through one resolver, which derives `epic_linkage`: `not_orchestrated` iff `origin.epic_id` is null, `indeterminate` iff it is set but the epic's header `epic.json` (xref:04-epic-and-change-ledger.adoc#epic-header[Epic Header (`epic.json`)]) is absent or unreadable, otherwise `orchestrated`. `indeterminate` is never read as `not_orchestrated`.
* *Amendments*: Every intent-changing answer after refinement appends an `amendments[]` entry; every later representation that renders the request (outline review, `create-pr`, landing) includes the amendments in order.

[#merge-outcome-mapping]
=== Merge Outcome Mapping
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-19[PM-WATCH-DISP-19], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-82[PM-WATCH-PHASE-82]_

The plan's `merge_outcome` (this store) and the landing's `merge_state` (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#_landing_envelope_emit_landing[Phase Workflows Specification, Landing Envelope]) are two enumerations with different consumers, derived from *one* observation through *one* table. The observation is the result of `ci.pr-observe` (`pr_state`: `open`, `merged`, `closed`; `queue_state`: `not_queued`, `queued`, `ejected`, `unobservable`; `merge_commit_sha`, `head_sha`, `observed_at`), together with the plan's own facts where no pull request exists. No other rule derives either value, and a test (`MergeOutcomeMappingTest`) asserts the table row by row for both enumerations.

|`merged`, the merge commit on the base branch
