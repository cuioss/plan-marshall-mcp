[#epic-inbox-record]
== Epic Inbox & Plan Mailbox Records (`inbox.jsonl`, `mcp/mailbox.jsonl`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-32[PM-WATCH-STORE-32]_

The epic inbox (`.marshall/orchestrator/<epic_id>/inbox.jsonl`, plan → epic and epic → epic) and the plan mailbox (`mcp/mailbox.jsonl` in the plan directory, epic → plan) share one record model: a strictly append-only event log. No line is ever rewritten or deleted; a message's current state is the fold of its events (link:../dispatch-and-effort.adoc[Model Jobs & Effort Specification], Git-Distributed Epic Ledger and Plan Mailbox).

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/message-event.json",
  "title": "MessageEvent",
  "type": "object",
  "required": ["format_version", "event", "message_id", "at"],
  "additionalProperties": false,
  "properties": {
    "format_version": { "type": "integer", "const": 1 },
    "event": { "type": "string", "enum": ["message", "claimed", "processed", "consumed", "annotation"] },
    "message_id": { "type": "string", "pattern": "^msg-[0-9]{4,}$", "description": "Store-assigned on the message event, monotonic per store file, never reused; later events reference it." },
    "at": { "type": "string", "format": "date-time" },
    "sender": {
      "type": "object",
      "description": "message events only; derived by the store from the calling scope, never supplied by the caller.",
      "required": ["scope", "id"],
      "additionalProperties": false,
      "properties": {
        "scope": { "type": "string", "enum": ["plan", "epic"] },
        "id": { "type": "string", "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$" }
      }
    },
    "kind": {
      "type": "string",
      "enum": ["blocker_report", "process_finding", "landing_notification", "transfer_offer", "intake_confirmed", "hypothesis_refuted", "advisory", "spec_amendment", "coordination"],
      "description": "message events only. Inbox kinds: the first three from plans, transfer_offer and intake_confirmed from epics (an overlap of a plan's unplanned changes with a sibling's declared surface is noted in the plan's landing record, never an inbox message). Mailbox kinds: advisory, spec_amendment, coordination."
    },
    "summary": { "type": "string", "minLength": 1, "maxLength": 200 },
    "body": { "type": "string", "maxLength": 16384 },
    "payload": { "type": "object", "description": "Kind-specific structured payload (the landing envelope for landing_notification; source_epic, source_plan_id, source_location for transfer_offer)." },
    "by": { "type": "string", "description": "claimed, processed, consumed, annotation: the scope id that appended the event." },
    "outcome": { "type": "string", "description": "processed only: what the consumer did (for example the landing record id or the queue row changed)." },
    "note": { "type": "string", "maxLength": 2000, "description": "annotation only: a correction referencing the original message, which is never rewritten." }
  }
}
----

* *Store-Assigned Identity*: The store allocates `message_id` as the next number above the highest ever written in that file, including ids of lines it cannot parse; an id is never reused, and a caller never supplies one. A `claimed`, `processed`, `consumed`, or `annotation` event for an unknown or already-folded-terminal message is refused.
* *Fold*: Inbox messages fold to `pending` (only `message`), `claimed`, or `processed`; mailbox messages fold to `unconsumed` or `consumed`, or `unknown` when a referencing line is unreadable. The empty states (`no_file`, `empty_file`, `all_processed`) and `unreadable` (with the failing line) are distinct and never read as each other.
* *Writers*: Inbox events are appended under the epic lock in the shared epic worktree copy (link:../filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification]). The plan mailbox has its own leaf lock, taken on `mcp/mailbox.jsonl` itself like the audit log (xref:13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)]): the epic's transaction holds the epic lock, then takes the mailbox leaf lock, reads the last `message_id`, and appends one line; the plan's `consumed` events are appended under the same leaf lock. The plan directory never moves except on archival, when it carries the mailbox with it. The mailbox is advisory content and is not covered by the plan's store digests; a reader ignores a torn last line (the next writer repairs it, xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline], item 6). The git-tracked inbox is protected by its git history.
* *Read Scope*: Inbox and mailbox resources are readable by every scope of their project (`PM-SEC-2` is the boundary); a representation points each scope at its own messages (the epic at its inbox, a plan at its own inbox messages and its mailbox).

[#epic-ledger-records]
== Epic Ledger Records (`epic.json`, `queue/<plan_id>.json`, `landings.jsonl`)

The git-tracked epic ledger `.marshall/orchestrator/<epic_id>/` (link:../dispatch-and-effort/04-epic-coordination.adoc#_git_distributed_epic_ledger_per_file_store_layout_adr_024[Model Jobs & Effort Specification, Git-Distributed Epic Ledger]) holds, beside the inbox (<<epic-inbox-record>>) and the Markdown documents `spec.md` and `resume_anchor.md`, three JSON stores. All are written only by the server, under the epic lock, in the shared epic worktree (link:../filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification]); their integrity is their git history. The epic's FSM state is not part of the ledger: it lives in `epics/<epic_id>/status.json` of the per-project machine store (xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store (`mcp/status.json`)]).

[#epic-header]
=== Epic Header (`epic.json`)

The epic's identity and descriptive header. It carries no FSM state and no queue content. It is created by the `start.create-scope` transaction of the epic bootstrap (`bootstrap-epic`) from the gathered title and `parallelization_scope`, together with the vision section of `spec.md`; adopting an existing ledger without machine scope (`start-epic.adopt`) only reads and validates it and never rewrites the header or a row; `workstreams` starts empty and grows through the `submit workstream` link of `epic.decompose` and `epic.active`.

[#landing-record]
=== Landing Record (`landings.jsonl`)

Every line of `landings.jsonl` is one landing record: `format_version` plus the landing envelope of link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#_landing_envelope_emit_landing[Phase Workflows Specification, Landing Envelope], which defines its fields, fact states, and the non-landing record; that envelope is the only definition and is not restated here. The line is the envelope that `emit-landing` delivered, stored unchanged; a correction is an `annotation` event in the inbox (<<epic-inbox-record>>), never a rewrite.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/landing-record.json",
  "title": "LandingRecord",
  "type": "object",
  "required": ["format_version", "plan_id", "envelope"],
  "additionalProperties": false,
  "properties": {
    "format_version": { "type": "integer", "const": 1 },
    "plan_id": { "type": "string", "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$", "description": "One landing record per plan_id." },
    "envelope": { "$ref": "https://cuioss.de/plan-marshall-mcp/schemas/landing-envelope.json", "description": "The landing envelope (phase-workflows.adoc, Landing Envelope)." }
  }
}
----

[#kept-landing-envelope]
=== Kept Landing Envelope (`landing-envelope.json`)

When `emit-landing` cannot deliver the landing envelope because the plan's epic linkage is `indeterminate` (`landing_delivery: pending`, xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store]), the server keeps the undelivered envelope in the plan directory as `plans/<plan_id>/landing-envelope.json`: `{format_version, envelope}` with `envelope` of the landing schema (`landing-envelope.json#`, link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#_landing_envelope_emit_landing[Phase Workflows Specification, Landing Envelope]). A late finding carried out while the envelope is kept (xref:03-findings-and-review-records.adoc#_findings_ledger_record_findings_jsonl[Findings Ledger Record], Late Findings Are Carried Out) is appended to the envelope's carried messages by a replace of this file. The file is written only by the server under the plan lock, is covered by the plan's digest sidecar, travels with the plan directory into the archive, and is delivered unchanged by the epic's landing reconciliation; it is never re-rendered from the plan's records.

* *Per-Task Attribution*: `kind: "task_diff"` rows are appended by the server when `submit:TASK-NNN` passes independent verification (link:../phase-workflows.adoc[Phase Workflows Specification], Task Envelope Execution): `task_id`, `changed_paths` since the previous task's snapshot (present, possibly empty), and `commit_sha: null`. They are the only producer of `task_id` in this ledger.
* *Baseline-Red Rows*: A `baseline_red` row is written by the server only, in the transaction that proves a red gate baseline-only (every failing fingerprint present on the base); it is bound to its `worktree_sha`, merge base, and diagnostics digest. A freshness gate accepts it as passing for the same `worktree_sha` (and hash version) only, never for another tree, so the exit barrier does not reject the same tree as `last_build_failed`. The gate step completes `done` with `assurance_verdict: degraded`, and the PR body and the landing record list the baseline failures. A red gate that is not provably baseline-only never produces the row; it calls the build or CI remediation policy.
* *Attribution State*: Every per-task consumer first reads `change_attribution`, which the server derives: `measured` when every completed task has a `task_diff` row, otherwise `unavailable` (for example when a task snapshot could not be taken). Under `unavailable` the dependent per-task keys are absent, never empty or zero.
