[#workflow-definition-units]
== Workflow Definition Units (Multi-File Workflows)
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-27[PM-WATCH-DSL-27]_

A workflow definition may be split across several `.pmwf` files:

* *Plan workflow*: All phase workflow files of a plan (`init.pmwf`, `refine.pmwf`, `outline.pmwf`, `plan.pmwf`, `execute.pmwf`, `land.pmwf` for the `land` lane states, `finalize.pmwf`) together form *one* workflow definition, the plan *template*. The loader merges them into a single `WorkflowDefinition` before validation: `states` and `migrations` are the union of all files, the definition's `startState` is the `start` of `init.pmwf`, and the `start` of every other phase file names that phase's entry state. A transition in one phase file may therefore target a state declared in another (for example `allocated -> execute.envelope-ready` in `finalize.pmwf`). Every phase file declares `scope plan` and its own `workflow <part> version <n>` header; the part headers identify files only. The merged unit carries a header of its own, which no file declares: `id` is `plan`, `scope` is `plan`, and `version` is derived from the part versions as their sum, recorded with the part versions themselves (`WorkflowDefinition.partVersions`, xref:04-ast-node-model.adoc#_ast_node_model[AST Node Model]). Because a part version only ever increases, the derived version increases with every change of any part. The unit id `plan` is the value of `CallFrame.callerWorkflowId` for every `call` made from a plan-workflow state (`status.json` `call_stack[].caller_workflow_id`), whichever phase file declares the calling state; the part header `workflow plan` of `plan.pmwf` (Phase 4) is a file identifier and never names the unit.
* *Plan instance*: A plan never executes the template directly. It executes its *plan instance*, a single-file unit composed by the server from the template, the sub-units it calls, the composition rules, and the plan's facts, and versioned per composition event (xref:09-plan-instance.adoc#plan-instance[Plan Instance]). Every rule of this document applies to each instance version as to the template.
* *Other top-level workflows*: Every other file with `scope plan`, `epic`, `workspace`, or `entity` forms a single-file definition: `epic.pmwf` (`scope epic`), `project-setup.pmwf` (`scope workspace`), the envelope units, the two generic entity units, and the bootstrap units. `entity.pmwf` (`scope entity`: `entity.active`, which offers the `submit` link of the entity kind its model job works on, and the terminal `entity.completed` declared `terminal submitted success`) serves every entity kind that submits once (for example refine and outline authoring, Q-Gate validation, triage groups, enrichment, re-grounding). `entity-multi.pmwf` (`scope entity`: `entity-multi.active`, which offers the kind's repeatable submit links, each validated and persisted on its own while the entity stays active, and the kind's one closing submit, and the terminal `entity-multi.completed` declared `terminal submitted success`) serves the kinds that submit several times: the epic decomposition draft (`workstream`, `spec_section`, `stage`; closing `submit:decompose`) and the lesson review (`merge`, `retire`, `supersede`; closing `submit:review`). Every entity unit declares `phase inherit`; no entity state waits on a question (a task envelope's `ask:TASK-NNN` records the question and ends the entity).
* *Bootstrap units*: Every scope is created by a bootstrap unit of its kind: `bootstrap-plan.pmwf` and `bootstrap-epic.pmwf` (`scope entity`, compiled only) are entity units hosted by the workspace scope. One instance runs per pending entry record; its instance id is the `entry_id`, its state lives in the pending entry record (link:../store-schemas/01-format-and-session-log.adoc[Store Schemas Specification, Pending Entry Record]), and the model addresses it with `pm_state(plan_id: "NO_PLAN", entity: "<entry_id>")` and `pm_do(…, entity: "<entry_id>", link)`; `phase inherit` resolves to `workspace`. The ways to start are its links, and each source is a sub-workflow unit it calls (`source-issue`, `source-lesson` with the lesson's premise check, `source-recipe`, `source-pr`, `source-local-changes`, `source-epic-row`), whose exit contract is `done` with its source record or `stepped_out`; a new way to start is one more unit and one more link, never a tool parameter. The unit's `create` link (`start.ready`, `start-epic.ready`) runs the primitive `start.create-scope`, whose transaction creates the plan or epic scope atomically from the gathered record and re-checks the creation preconditions (identifier free, lifecycle gate open or the project enrolled as a pilot, configuration state): `created` enters the terminal `start.committed` or `start-epic.committed`; a failing re-check (`refused`) re-enters `start.ready` or `start-epic.ready` instead, with the reason in `facts`, and creates nothing. The unit's other terminals end the entry without a scope; the terminal transaction deletes the pending record (link:../state-catalogue/09-bootstrap-and-lessons.adoc[State Catalogue, Bootstrap]).
* *Sub-workflows*: Every `scope subworkflow` file (`git-commit-and-push.pmwf`, the remediation policy units `remediation-*.pmwf`, xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units], the bootstrap source units `source-*.pmwf`, and the lesson maintenance unit `lessons.pmwf`, which the workspace's `setup.maintain-lessons` calls and whose exit contract is `done` or `stepped_out`, link:../state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-lessons[State Catalogue, Lesson Maintenance]) is a separately scoped definition. Its states are never merged into a caller's definition and are reachable only through `call`; transitions inside a sub-workflow may target only states of the same sub-workflow, and transitions outside it may never target a sub-workflow state.

The same unit rules apply to the default units of the binary and to a project's own copies in `.marshall/config/` (xref:04-ast-node-model.adoc#project-owned-units[Project-Owned Workflow Units & Compiled Invariants]); a project never mixes a default file with its own copies inside one definition unit.

All static verification rules (xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules (Build Time & Every Unit Load)]) run over the merged definition unit: state identifiers must be unique across all files of the unit, transition targets must exist in the unit, every state must be reachable from the unit's `startState` under every combination of the configuration keys its guards declare, outcome coverage is exhaustive per state, and link identifier patterns are unique within their state.

[#implicit-job-links]
== Implicit Links

The engine offers the following links without a declaration in DSL source. Each counts as offered for every check that compares link identifiers against the workflow definitions (for example the vocabulary-skill link check, `PM-WATCH-TOOL-6`), and a DSL link whose identifier pattern collides with one fails validation (Rule 3).

[cols="2,1,1,2,4"]
|===
|Link |`rel` |`form` |Offered on |Semantics

|`wait:<job_id>`
|`wait`
|`wait`
|every `job` and `composite_job` state
|Bounded blocking wait on the running job (`PM-WF-8`); returns the next state's representation once the job settles, or the updated running representation.

|`cancel:<job_id>`
|`abort`
|`noop`
|every `job` and `composite_job` state
|Cancels the running job (for a composite job, all constituent jobs); the job settles with the outcome `cancelled` (in a `job llm` state its return evaluation follows, <<model-job-states>>).

|`step_out`
|`abort`
|`submit`
|every resting `link` state (including a question state) of a `scope subworkflow` unit
|`reason: text[1..2000]`. Unwinds exactly one call frame and returns the control outcome `stepped_out {by: model, cause: step_out, reason}` to the caller (xref:01-grammar.adoc#sub-workflow-exits[Sub-Workflow Exit Contract]). Never guarded, never charged to a budget, never writes a waiver; before the frame unwinds the engine undoes an interrupted in-flight operation of the frame (an unfinished rebase is aborted). Never offered on `auto`, `job`, or `composite_job` states, and never at plan scope, where the declared `hand_back` link is the equivalent.

|`answer_questions`
|`submit`
|`submit`
|every question state whose open record has `session` delivery, and a `task` question state after its deadline
|`answers: list<schema[question-answer]>` (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]); the relayed human answer (`channel: user_relayed`), or for a `task` question after its deadline the main session's own answer (`channel: model`) (<<question-states>>).

|`wait:question:<question_id>`
|`wait`
|`wait`
|every question state whose open record has `elicitation` or `web` delivery
|Bounded long-poll on the question record; returns the next state's representation once the question is resolved, or the unchanged representation.
|===

Independently of the state kind, the engine accepts the self-report link `report_bypass` in every state of a live plan, epic, or entity scope and never renders it (link:../hypermedia-format/01-representation-and-link-forms.adoc#self-report-link[Hypermedia Format Specification, Self-Report Link]); it returns the unchanged representation and never changes state, so it needs no outcome transition.

`<job_id>` is the job identifier of a `job` state (for example `wait:b-3f9a2c417e0d8b65`) and the composite identifier, which equals the state identifier, of a `composite_job` state (for example `wait:finalize.concurrent-wait`) and of a fan-out model job state (`job llm … each …`, <<model-job-states>> item 6; for example `wait:setup.enrich-architecture`), where `wait:` waits on the set of the state's jobs and `cancel:` cancels all of them. The outcome enumeration of every `job` and `composite_job` primitive contains `cancelled`, so every such state must declare an explicit `cancelled -> <state>` outcome transition; Rule 2 (exhaustive outcome coverage) enforces it. A `job llm` state is the exception: every end of its job, a cancel included, runs the entity kind's return evaluation, whose outcomes it routes (<<model-job-states>>). A `job` state's outcome enumeration is exactly the closed job outcome set of `PM-EXEC-4` (`succeeded`, `failed`, `failed_unparsed` for build jobs only, `refused`, `cancelled`, `timed_out`, `killed`, `indeterminate`); a state that runs several jobs or routes domain outcomes is a `composite_job`, whose primitive declares its own closed workflow outcomes (`PM-WF-8`). `<job_id>` is always the job bound in `active_job` (<<job-state-binding>>); `wait` on a bound job only waits and never starts one.

[#job-state-binding]
== Job State Entry & Binding (`JobStep`)
_See Requirement link:../../Requirements.adoc#PM-ARCH-7[PM-ARCH-7: Runtime & Relay Lifecycle, Crash Recovery & Job Drain]_

A `job` state is a resting state over exactly one job. The engine binds it as follows (normative for `StateBehavior.JobStep`):

1. *One job per entry*: Entering a `job` state starts exactly one job through the state's primitive, unless a job id is already bound for the state. A job id is bound when the entering transition carries one (item 3) or when `active_job` already names this state.
2. *`active_job` in the state transaction*: `mcp/status.json` records `active_job {state_id, job_id}` (link:../store-schemas/02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Store Schemas Specification, Workflow State Store]) in the same journaled transaction (link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Transaction Journal]) as the state change that enters the state and the enqueue of the job. A crash therefore leaves either the old state without a job or the new state with its bound job, never a job without a binding or a job state without its job.
3. *Enqueued by a preceding primitive*: A primitive that enqueues a job for the following state (an `auto` state or a `do` link action, for example `build.enqueue-verification` before `git.freshness-build-running`, or `finalize.restart-watch` before `finalize.concurrent-wait` or `finalize.merge-evidence-wait`) declares `enqueuesJob()` and returns the job's id as its primitive result (`PrimitiveResult.spawnedJobId`) with its job-starting outcome: `started`, or for `finalize.restart-watch` `concurrent_restarted` and `evidence_restarted`, which name the restarted wait (its third outcome `exhausted` enqueues nothing and takes the fallback). The job-starting transition enters the `job` (or `composite_job`) state, which binds that id and starts nothing itself. Rule 1 (xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules (Build Time & Every Unit Load)]) verifies the binding: every job-starting outcome of an `enqueuesJob()` primitive targets a `job` or `composite_job` state, and no other outcome of such a primitive does.
4. *Re-entry only waits*: A `pm_state` or `pm_do` on a job state whose bound job is `queued` or `running`, including the first call after a runtime restart, only waits on it (`wait:<job_id>`); it never starts a second job.
5. *Killed jobs are routed, never restarted*: A bound job that the runtime recorded `killed` (for example an orphaned `running` job marked on restart, `PM-ARCH-7`) settles the state with the outcome `killed`, which every `job` state routes explicitly (Rule 2). The engine never re-enqueues a job on its own (no blind re-execution); a new job starts only when a declared transition enters a job state again, for example through a `retry` link or the bounded `auto` restart `finalize.restart-watch`.
6. *Leaving clears the binding*: The transition that leaves the state (on the job's outcome, or on `cancel:<job_id>`) clears `active_job` in the same transaction.
7. *Composite constituents*: A `composite_job` state follows the same rules with its composite identifier (the state identifier) as the bound id; its constituent jobs are recorded in `active_jobs`. Its primitive declares how every constituent fate other than success maps onto its closed outcomes (`killed`, `timed_out`, `indeterminate`, and `refused` or `failed` where they are no domain result); the watches of the finalize wait region map them to `watch_interrupted {constituent, fate}`, while a deliberate `cancel` of the composite settles it `cancelled` (xref:03-reference-excerpt.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Reference Workflow Excerpt]). A timer constituent (the waiver wait, xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units]) keeps its persisted deadline, so a restart never extends the wait.

[#model-job-states]
== Model Job States (`job llm`)
_See Requirement link:../../Requirements.adoc#PM-WF-5[PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint]_

_See Requirement link:../../Requirements.adoc#PM-WF-8[PM-WF-8: Asynchronous Job Links & Wait Transitions]_
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-20[PM-WATCH-DSL-20], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-26[PM-WATCH-DSL-26], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-27[PM-WATCH-DSL-27]_

A state declared `job llm <entity_kind> role <role_key> [each <primitive_id>]` (`StateBehavior.ModelJob`, xref:04-ast-node-model.adoc#_ast_node_model[AST Node Model]) is a job state whose job is a model run: the server launches the harness CLI as a job of kind `llm` for one entity of the kind (the launch contract, the job-bound connection, and the model slots are specified in link:../dispatch-and-effort/05-model-job-launch.adoc#model-job-launch[Model Jobs & Effort Specification, Model Job Launch], the job fates in link:../job-runtime.adoc[Job Runtime Specification]). The rules of <<job-state-binding>> apply, with these additions:

1. *Entry*: Entering the state allocates the entity (for a task envelope `envelope-M`) and starts exactly one model job bound in `active_job`; a job that waits for a model slot is `queued`, and re-entry only waits on it (`wait:<job_id>`). The host model never launches a sub-agent; its only duty is following `wait:`.
2. *Completion is the awaited event*: When the job ends, with any fate, the engine runs the return-evaluation primitive the entity kind registers on the persisted entity, task, question, and findings records (never on the job's own report) in the transaction that settles the state, and takes the transition of its outcome (Rule 11b: `JOB_SETTLED`). The zero-tool screener kind `screen` has no connection and no entity unit; its return evaluation validates the job's structured `screen-verdict` output, fail-closed.
3. *Incomplete work*: A job that ended without the submits its entity requires raises the `job_incomplete` condition on the state (xref:04-ast-node-model.adoc#condition-overlays[Condition Overlays]); its `resume` launches a new job for the remaining work, bound to the same state, within the condition's self-remedy budget, then the phase's fallback. The engine never relaunches on its own. For an entity of the multi-submit unit `entity-multi.pmwf` (<<workflow-definition-units>>) the required submission is the closing submit; what its repeatable submits persisted stays, and the relaunched job continues from it.
4. *Refused launch*: A job the runtime cannot launch (the harness lacks a capability the role's job class needs, an unsupported harness version, a harness enrolment store `harnesses.json` that fails its HMAC check: reason `harness_tampered`) raises `precondition_unmet` naming the missing item and the operator setting or command that resolves it (for `harness_tampered`: `pm-operator enrol-harness <client>`).
5. *Leaf*: A job's connection is bound to its scope and entity and never follows a link into a `job llm` state (Rule 4).
6. *Fan-out (`each <primitive_id>`)*: A state that declares `each` runs one model job per element of a server-computed list. Entering it runs the named list primitive (registered and read-only, Rule 1), allocates one entity per element (for the zero-tool kind `screen`, which has no entity, one batch part per element), and starts one model job per element, each with its own `job_id`, job token, and entity; the jobs run through the model slots, so those beyond the free slots are `queued`. The state binds like a composite (<<job-state-binding>> item 7): the bound identifier is the state identifier, the jobs are recorded in `active_jobs`, `wait:<state_id>` waits on the set, and `cancel:<state_id>` cancels every queued or running job of the state. Items 2, 4, and 5 and Rules 2, 4, and 11b apply per job: every job's end runs the kind's return evaluation on that job's entity, and the state completes, taking the transition of the evaluation's outcome over the whole list, once every entity has its required submission (for `screen`: once every part has its verdict, a missing or unparseable one counting as `suspicious`). When the last job has ended while an entity still lacks its required submission, `job_incomplete` is raised on the state; its one `resume` link relaunches jobs only for the unfinished entities. An empty list completes the state in the entering transaction. The fan-out states of the default units are `setup.enrich-architecture` (one job per module to enrich) and the screener states (one job per part of a batch; a batch above the screening split bound has several parts, link:../dispatch-and-effort/06-untrusted-text-screening.adoc#screener[Model Jobs & Effort Specification, Screener Job]).

[#question-states]
== Question States & the Question Deadline
_See Requirement link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-23[PM-WATCH-DSL-23]_

Every content question is a server-owned question record (link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]). The model creates one through a declared `ask` link (rel `submit`, form `submit`, `question: schema[question-envelope]`, primitive `question.create`, outcome `created` into the state's question state), through `ask:TASK-NNN` on a task envelope (which ends the entity), or through the `questions` list of a refine or outline `submit`; a server primitive creates the questions whose options it owns (init classifiers, the optional outline review, workspace setup choices that write team configuration). Choices that write operator configuration, waivers, `abort`, and integrity resolutions are never question records; they use the operator channel only.

A *question state* is a state whose body starts with `question <class>` (xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Formal EBNF Grammar]; `StateBehavior.QuestionWait`, xref:04-ast-node-model.adoc#_ast_node_model[AST Node Model]). It rests until the scope's open record of that class is resolved and then takes the outcome transition of the resolution; it may declare further links (for example `hand_back`). Every resolution outcome enters a re-entrant `auto` state that reads the answer from the record and decides, as `init.classify` does; the choice between the options of an answer is routed there, never by the question clause (for example the budget check of a `revise` answer to the outline review). An `ask` question state (`<state>.asked`) returns to the asking state, which renders the answer in `facts`. The catalogue kind `awaiting_user` is derived from this clause, so the kind stays derivable from the AST.

* *Mode and delivery*: The effective `questions.mode` of the class (operator `local-config.json`, per project with per-class overrides) decides how the record resolves. `auto` (default) delivers per `questions.delivery` (`elicitation` where the connection declared support, otherwise `session`; resolved per question at creation and recorded as the answer's `channel`) and sets the deadline `questions.wait_seconds` (default `1800`); `operator` delivers to a human and sets no deadline (the only unbounded wait a plan can have, chosen by the operator); `model` accepts the model's self-answer at or above the compiled refine confidence threshold (`95`, `channel: model`), otherwise continues as `auto`; `none` applies the `recommended` option or `default_assumption` at once, so the question state resolves in the transaction that entered it.
* *Deadline*: The deadline is engine-owned and processed by the job runtime's timer (link:../job-runtime.adoc[Job Runtime Specification]): on expiry the engine resolves the record through the class's compiled fallback and takes the matching outcome transition without a model call. The timer survives a gone host session. An integrity pause holds the fallback transition until the pause ends; `pm-operator abort` and `delete-plan` close every open record `cancelled`.
* *Resolution outcomes*: Each class has a closed outcome set, which a question clause must route exactly (Rule 2):
+
[cols="1,2,3"]
|===
|Class |Outcomes |Expiry fallback (compiled)

|`init`
|`answered`, `assumed`, `returned`
|The classifier's `recommended` option as a recorded assumption (`assumed`); `returned` where the classifier declares no safe default.

|`clarification`
|`answered`, `assumed`
|The envelope's `default_assumption`, recorded as an assumption amendment.

|`review`
|`approve`, `revise`, `returned`
|`returned` (a review that was asked for and not given never starts execution).

|`task`
|`answered`
|The main-session model answers through `answer_questions` (`channel: model`); no assumption is taken.

|`setup`
|`answered`, `assumed`
|The `recommended` option.

|`ask`
|`answered`, `assumed`
|The question's `default_assumption`; the model then decides on its own judgment.
|===
* *Answer validation*: Every channel passes the same validation: an unknown `branch_key` is rejected with `invalid_link_args`, a second answer with `already_answered`, an answer on a user channel after the deadline with `question_expired` (a `task` record after its deadline expects the main session's answer instead). A model-relayed answer is accepted for content questions only, never for an override (`PM-WF-12`).
* *Awaited events*: A question state awaits `QUESTION_ANSWER` (an answer on any channel) and `TIME` (the deadline) (Rule 11b, xref:05-primitives.adoc#primitive-spi-contract[`Primitive<P, R>` SPI Contract]).
* *Continuation*: With `session` delivery a question state is a stop point under every continuation policy; with `elicitation` or `web` delivery the model may long-poll `wait:question:<question_id>`.

[#waivers-and-integrity]
== Waivers, Waiver Requests & the Integrity Pause
_See Requirement link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-18[PM-WATCH-DSL-18]_

_See Requirement link:../../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_

The process enforces itself: no state of any unit waits for an operator decision, and the DSL has no decision construct (no decision registry, no escalation action or form, no pending decision). Every blocking condition gets a bounded self-remedy, mostly a remediation policy unit (xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units]), and then a defined fallback end. The operator influences a running plan only through records written on the operator channel, which primitives read:

* *Waiver record*: `pm-operator waive <plan> <gate> --reason …` declares a waivable gate met (`mode: met`), `waive <plan> --raise <budget>=N --reason …` raises a budget ceiling (`mode: raise`), and `unwaive` revokes an unconsumed waiver (link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record]; link:../cli-and-security.adoc[CLI, Coordination & Security Specification]). The gate identifiers form a closed list: `review_evidence[:<bot_kind>]`, `ci_check:<check_name>`, `analysis_gate:<provider>`, `findings:<class>` and `findings:<provider>`, `qgate_findings:<phase>`; the raisable budgets are `fix_budget:<policy>`, `retry_budget:<policy>`, and `spend`. A waiver is plan-scoped, settable at any time until the gate's fallback is taken, and applies to every later evaluation of its gate; after the fallback it is refused (`plan_ended`). Every waiver line composes a new plan instance version (event `waiver`), which marks the gate waived with the waiver id or carries the raised ceiling with its source.
* *Reading a waiver*: A waivable gate admits a failure only through `waiver.lookup(gate)` (read-only in `WorkflowExecutionContext`), which appends a consumption naming `HEAD` and the covered items; the PR comment and the landing record list every consumption. A primitive may look up only the gate identifiers it declares in `waivableGates()` (xref:05-primitives.adoc#primitive-spi-contract[`Primitive<P, R>` SPI Contract]), and no primitive can write a waiver (`INV-GEN-2`, xref:04-ast-node-model.adoc#project-owned-units[Compiled Invariants]). In the DSL a waived path is visible only as the `waived` terminal of a remediation unit.
* *Waiver requests*: The model's `request_waiver (rationale: text[1..2000])` link (rel `escalate`, form `submit`) in a remediation unit's `decide` state, and an exhausted budget with `waiver_wait_seconds > 0`, file a request record (`waiver_requests[]`, announced through the operator channels and an idempotent PR comment). It is an ordinary `submit` link: nothing waits for an answer except the bounded waiver wait of the unit, a `composite_job` (`remediation.await-waiver`) that awaits `OPERATOR_WAIVER` or `TIME` and ends `raised`, `waived`, or `expired`. The shipped `waiver_wait_seconds` is `0`, so by default a request goes into the hand-back report.
* *Operator-initiated ends*: `pm-operator abort <plan|epic> <id> --reason` and `delete-plan` are engine-owned, scope-wide transitions into `plan.aborted` or `epic.aborted` in the next transaction, under the on-entry rule (every begun, unsettled step recorded `failed`); they close open question records `cancelled` and pending waiver requests `expired`. They need no DSL construct: no unit declares a transition into an abort terminal (xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Formal EBNF Grammar], Ends of a scope).
* *Integrity pause*: The only pause of a plan is the condition overlay `integrity_breach {kind: store_tampered | enrolment_tampered, store, recorded_digest, current_digest}` (xref:04-ast-node-model.adoc#condition-overlays[Condition Overlays (Engine-Owned)]). It offers no link, every `pm_do` of the paused scope is rejected with `integrity_paused`, and `facts.operator_command` names the two resolutions: `pm-operator accept-edit …`, after which the engine re-verifies the digests before it clears the condition, and `pm-operator abort …`. It has no bound and no fallback, because a tampered store cannot be trusted to write a hand-back; the deadlines of a pending question or waiver request of the paused scope are held until it ends.
