[#workflow-definition-units]
== Workflow Definition Units (Multi-File Workflows)
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-27[PM-WATCH-DSL-27]_

A workflow definition may be split across several `.pmwf` files:

* *Plan workflow*: All phase workflow files of a plan (`init.pmwf`, `refine.pmwf`, `outline.pmwf`, `plan.pmwf`, `execute.pmwf`, `land.pmwf` for the `land` lane states, `finalize.pmwf`) together form *one* workflow definition, the plan *template*. The loader merges them into a single `WorkflowDefinition` before validation: `states` and `migrations` are the union of all files, the definition's `startState` is the `start` of `init.pmwf`, and the `start` of every other phase file names that phase's entry state. A transition in one phase file may therefore target a state declared in another (for example `allocated -> execute.envelope-ready` in `finalize.pmwf`). Every phase file declares `scope plan` and its own `workflow <part> version <n>` header; the part headers identify files only. The merged unit carries a header of its own, which no file declares: `id` is `plan`, `scope` is `plan`, and `version` is derived from the part versions as their sum, recorded with the part versions themselves (`WorkflowDefinition.partVersions`, xref:04-ast-node-model.adoc#_ast_node_model[AST Node Model]). Because a part version only ever increases, the derived version increases with every change of any part. The unit id `plan` is the value of `CallFrame.callerWorkflowId` for every `call` made from a plan-workflow state (`status.json` `call_stack[].caller_workflow_id`), whichever phase file declares the calling state; the part header `workflow plan` of `plan.pmwf` (Phase 4) is a file identifier and never names the unit.
* *Plan instance*: A plan never executes the template directly. It executes its *plan instance*, a single-file unit composed by the server from the template, the sub-units it calls, the composition rules, and the plan's facts, and versioned per composition event (xref:09-plan-instance.adoc#plan-instance[Plan Instance]). Every rule of this document applies to each instance version as to the template.
* *Other top-level workflows*: Every other file with `scope plan`, `epic`, `workspace`, or `entity` forms a single-file definition: `epic.pmwf` (`scope epic`), `project-setup.pmwf` (`scope workspace`), the envelope units, the two generic entity units, and the bootstrap units.
* *Entity units*: The states a worker sees after it acknowledged a task are those of the entity unit of the task's kind (`scope entity`, compiled only). `entity.pmwf` (`entity.active`, which offers the closing link of the entity kind its task works on, or the kind's alternative closing links where it declares several, and the terminal `entity.completed` declared `terminal submitted success`) serves every entity kind that submits once (for example refine and outline authoring, Q-Gate validation, triage groups, enrichment, re-grounding, commit messages, and the remediation decision kind `remediation-decision`, whose alternative closing links are the remedies, xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units]). `entity-multi.pmwf` (`entity-multi.active`, which offers the kind's repeatable submit links, each validated and persisted on its own while the entity stays active, and the kind's one closing submit, and the terminal `entity-multi.completed` declared `terminal submitted success`) serves the kinds that submit several times: the epic decomposition draft (`workstream`, `spec_section`, `stage`; closing `submit:decompose`), the lesson review (`merge`, `retire`, `supersede`; closing `submit:review`), the task revision, the pull-request body, the epic inbox message (closing `submit:message`), and the epic completion (closing `submit:completion`). Every entity unit declares `phase inherit`; no entity state waits on a question (an `ask` ends the task with the outcome `asked`, and a task envelope's `ask:TASK-NNN` ends the envelope task). A kind's links, their schemas, and its return-evaluation primitive are registered with the kind (link:../model-work/09-completion-usage-and-spend.adoc#return-evaluation[Model Work Specification, Return Evaluation]); the guards of a kind's links are evaluated in the call frame of the task state that created the task.
* *Task protocol unit*: `worker-task.pmwf` (`scope subworkflow`, compiled only) is the protocol of one task (<<worker-task-unit>>). Every `job llm` state runs it once per task; no unit redefines or calls it.
* *Bootstrap units*: Every scope is created by a bootstrap unit of its kind: `bootstrap-plan.pmwf` and `bootstrap-epic.pmwf` (`scope entity`, compiled only) are entity units hosted by the workspace scope, except for the plans the server starts for an epic, whose bootstrap runs without a session (source `epic_row`, link:../model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]). One instance runs per pending entry record; its instance id is the `entry_id`, its state lives in the pending entry record (link:../store-schemas/01-format-and-session-log.adoc[Store Schemas Specification, Pending Entry Record]), and the entry session addresses it with `pm_state(plan_id: "NO_PLAN", entity: "<entry_id>")` and `pm_do(…, entity: "<entry_id>", link)`; `phase inherit` resolves to `workspace`. The ways to start are its links, and each source is a sub-workflow unit it calls (`source-issue`, `source-lesson` with the lesson's premise check, `source-recipe`, `source-pr`, `source-local-changes`, `source-epic-row`), whose exit contract is `done` with its source record or `stepped_out`; a new way to start is one more unit and one more link, never a tool parameter. The unit's `create` link (`start.ready`, `start-epic.ready`) runs the primitive `start.create-scope`, whose transaction creates the plan or epic scope atomically from the gathered record and re-checks the creation preconditions (identifier free, lifecycle gate open or the project enrolled as a pilot, configuration state, every role the composed workflow names defined): `created` enters the terminal `start.committed` or `start-epic.committed`; a failing re-check (`refused`) re-enters `start.ready` or `start-epic.ready` instead, with the reason in `facts`, and creates nothing. The unit's other terminals end the entry without a scope; the terminal transaction deletes the pending record (link:../state-catalogue/09-bootstrap-and-lessons.adoc[State Catalogue, Bootstrap]).
* *Sub-workflows*: Every `scope subworkflow` file (`git-commit-and-push.pmwf`, the remediation policy units `remediation-*.pmwf`, xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units], the task protocol unit `worker-task.pmwf`, the bootstrap source units `source-*.pmwf`, the re-planning unit `replan.pmwf` (compiled only; exit contract `done`, `reentered`, `reauthor`, `hand_back`, `stepped_out`; link:../phase-workflows/08-dynamic-re-planning.adoc#dynamic-re-planning[Phase Workflows Specification, Dynamic Re-Planning]), the adjudication unit `question-adjudicate.pmwf` (compiled only, run by every question state, <<question-adjudicate-unit>>), and the lesson maintenance unit `lessons.pmwf`, which the workspace's `setup.maintain-lessons` calls and whose exit contract is `done` or `stepped_out`, link:../state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-lessons[State Catalogue, Lesson Maintenance]) is a separately scoped definition. Its states are never merged into a caller's definition and are reachable only through `call` (or, for `worker-task`, through a `job llm` state); transitions inside a sub-workflow may target only states of the same sub-workflow, and transitions outside it may never target a sub-workflow state.

[#session-driven-units]
*Session-driven units*: The entry session drives exactly the workspace unit `project-setup.pmwf`, the bootstrap units, and the sub-workflows only they call (the source units and `lessons.pmwf`). Only these units contain resting `link` states and question states with declared links (Rule 10, xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules]). A plan, an epic, and every sub-workflow a plan or epic unit calls (`git.commit_and_push`, the remediation units, `worker-task`) consist of `auto`, `job`, `composite_job`, `job llm`, `call`, question, and terminal states: the server moves them, and a model acts in them only through a task.

The same unit rules apply to the default units of the binary and to a project's own copies in `.marshall/config/` (xref:04-ast-node-model.adoc#project-owned-units[Project-Owned Workflow Units & Compiled Invariants]); a project never mixes a default file with its own copies inside one definition unit.

All static verification rules (xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules (Build Time & Every Unit Load)]) run over the merged definition unit: state identifiers must be unique across all files of the unit, transition targets must exist in the unit, every state must be reachable from the unit's `startState` under every combination of the configuration keys its guards declare, outcome coverage is exhaustive per state, and link identifier patterns are unique within their state.

[#implicit-job-links]
== Implicit Links

The engine offers the following links without a declaration in DSL source. Each counts as offered for every check that compares link identifiers against the workflow definitions (for example the vocabulary-skill link check, `PM-WATCH-TOOL-6`), and a DSL link whose identifier pattern collides with one fails validation (Rule 3).

[cols="2,1,1,2,4"]
|===
|Link |`rel` |`form` |Offered on |Semantics

|`ack`
|`next`
|`noop`
|a task entity in `task.offered`, to the generation that holds its lease
|The worker's acknowledgement of the offer (<<worker-task-unit>>); returns the task entity in the first state of its entity unit.

|`consult:<role>`
|`consult`
|`submit`
|a task entity in `task.executing`, once per `consult role <role>` clause of the task state
|`question: text[1..4000]`. Moves the task to `task.consulting` and creates a task of the named role (link:../model-work/05-consultation.adoc[Model Work Specification, Consultation]); never offered on a consultation task.

|`answer:<question_id>`
|`submit`
|`submit`
|the view of a plan or epic and a question state of a session-driven unit, to the entry session, for every open question record of the scope once it is delivered (after its adjudication, <<question-adjudicate-unit>>)
|`branch_key: enum[…]` (the record's option keys), `text: text[1..2000]?`; the session's relayed answer (`channel: session`, <<question-states>>).

|`step_out`
|`abort`
|`submit`
|every resting `link` state (including a question state) of a sub-workflow the entry session drives
|`reason: text[1..2000]`. Unwinds exactly one call frame and returns the control outcome `stepped_out {by: model, cause: step_out, reason}` to the caller (xref:01-grammar.adoc#sub-workflow-exits[Sub-Workflow Exit Contract]). Never guarded, never charged to a budget, never writes a waiver; before the frame unwinds the engine undoes an interrupted in-flight operation of the frame. Never offered on `auto`, `job`, `composite_job`, or `job llm` states, and never in a plan or epic, whose sub-workflows the server leaves.
|===

No link waits on or cancels a job: a job's completion is an engine event, and a plan or epic view shows its progress. Every `job` and `composite_job` primitive's outcome enumeration contains `cancelled`, the outcome of a cancellation by the engine (the scope's operator `abort`, a runtime drain, the short-circuit of a composite), so every such state declares an explicit `cancelled -> <state>` outcome transition; Rule 2 (exhaustive outcome coverage) enforces it. A `job` state's outcome enumeration is exactly the closed job outcome set of `PM-EXEC-4` (`succeeded`, `failed`, `failed_unparsed` for build jobs only, `refused`, `cancelled`, `timed_out`, `killed`, `indeterminate`); a state that runs several jobs or routes domain outcomes is a `composite_job`, whose primitive declares its own closed workflow outcomes (`PM-WF-8`). A `job llm` state routes the outcomes of its entity kind's return evaluation and the reserved `lost` instead (<<model-job-states>>).

[#job-state-binding]
== Job State Entry & Binding (`JobStep`)
_See Requirement link:../../Requirements.adoc#PM-ARCH-7[PM-ARCH-7: Runtime & Relay Lifecycle, Crash Recovery & Job Drain]_

A `job` state is a resting state over exactly one job. The engine binds it as follows (normative for `StateBehavior.JobStep`):

1. *One job per entry*: Entering a `job` state starts exactly one job through the state's primitive, unless a job id is already bound for the state. A job id is bound when the entering transition carries one (item 3) or when `active_job` already names this state.
2. *`active_job` in the state transaction*: `mcp/status.json` records `active_job {state_id, job_id}` (link:../store-schemas/02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Store Schemas Specification, Workflow State Store]) in the same journaled transaction (link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Transaction Journal]) as the state change that enters the state and the enqueue of the job. A crash therefore leaves either the old state without a job or the new state with its bound job, never a job without a binding or a job state without its job.
3. *Enqueued by a preceding primitive*: A primitive that enqueues a job for the following state (an `auto` state or a `do` link action, for example `build.enqueue-verification` before `git.freshness-build-running`, or `finalize.restart-watch` before `finalize.concurrent-wait` or `finalize.merge-evidence-wait`) declares `enqueuesJob()` and returns the job's id as its primitive result (`PrimitiveResult.spawnedJobId`) with its job-starting outcome: `started`, or for `finalize.restart-watch` `concurrent_restarted` and `evidence_restarted`, which name the restarted wait (its third outcome `exhausted` enqueues nothing and takes the fallback). The job-starting transition enters the `job` (or `composite_job`) state, which binds that id and starts nothing itself. Rule 1 (xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules (Build Time & Every Unit Load)]) verifies the binding: every job-starting outcome of an `enqueuesJob()` primitive targets a `job` or `composite_job` state, and no other outcome of such a primitive does.
4. *Re-entry never restarts*: A read of a job state whose bound job is `queued` or `running`, and the engine's recovery after a runtime restart, observe the bound job; neither starts a second job.
5. *Killed jobs are routed, never restarted*: A bound job that the runtime recorded `killed` (for example an orphaned `running` job marked on restart, `PM-ARCH-7`) settles the state with the outcome `killed`, which every `job` state routes explicitly (Rule 2). The engine never re-enqueues a job on its own (no blind re-execution); a new job starts only when a declared transition enters a job state again, for example through a `retry` link or the bounded `auto` restart `finalize.restart-watch`.
6. *Leaving clears the binding*: The transition that leaves the state (on the job's outcome, or on its cancellation by the engine) clears `active_job` in the same transaction.
7. *Composite constituents*: A `composite_job` state follows the same rules with its composite identifier (the state identifier) as the bound id; its constituent jobs are recorded in `active_jobs`. Its primitive declares how every constituent fate other than success maps onto its closed outcomes (`killed`, `timed_out`, `indeterminate`, and `refused` or `failed` where they are no domain result); the watches of the finalize wait region map them to `watch_interrupted {constituent, fate}`, while a cancellation of the composite by the engine settles it `cancelled` (xref:03-reference-excerpt.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Reference Workflow Excerpt]). A timer constituent (the waiver wait, xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units]) keeps its persisted deadline, so a restart never extends the wait.

[#model-job-states]
== Task States (`job llm`)
_See Requirement link:../../Requirements.adoc#PM-WF-5[PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint]_

_See Requirement link:../../Requirements.adoc#PM-WF-8[PM-WF-8: Asynchronous Job Links & Wait Transitions]_

_See Requirement link:../../Requirements.adoc#PM-WORK-2[PM-WORK-2: Task Protocol]_

_See Requirement link:../../Requirements.adoc#PM-WORK-6[PM-WORK-6: Role Qualification]_
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-20[PM-WATCH-DSL-20], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-26[PM-WATCH-DSL-26], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-27[PM-WATCH-DSL-27]_

A state declared `job llm <entity_kind> role <role> [each <primitive_id>]` with its `consult role <role>` clauses (`StateBehavior.ModelJob`, xref:04-ast-node-model.adoc#_ast_node_model[AST Node Model]) is a task state: the model work it needs is a task of the named role, done by a worker of that role (a supervised headless harness process, a job of kind `llm`, link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]). The rules of <<job-state-binding>> apply with the queue task in place of the job, with these additions:

1. *Entry*: Entering the state allocates the entity (for a task envelope `envelope-M`) and creates one queue task of the role for it in the same transaction (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]); the state binds its own state id in `active_job` and records the task, keyed by its entity, in `active_tasks` (link:../store-schemas/02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Store Schemas Specification, Workflow State Store]); the engine runs the task through `worker-task` (<<worker-task-unit>>). A worker of the role receives the task as the answer to its `pm_wait`; the plan's view shows the task's progress and offers no link. No host launches a sub-agent, and no session is needed for the state to complete.
2. *Completion is the awaited event*: When the task ends, the engine runs the return-evaluation primitive the entity kind registers on the persisted entity, plan task, question, and findings records (never on the worker's own report) in the transaction that records the task's outcome, and takes the transition of its outcome (Rule 11b: `TASK_SETTLED`; link:../model-work/09-completion-usage-and-spend.adoc#job-completion[Model Work Specification, Task Completion]). The zero-tool screener kind `screen` has no connection and no entity unit; its return evaluation validates the worker's structured `screen-verdict` output, fail-closed.
3. *Re-offer*: An attempt that ends without the required submission (its worker lost or ended while holding the task) is offered again by the server, as a new attempt of the same task, within the compiled task re-offer budget (link:../timeouts/01-job-budgets-and-waits.adoc#task-reoffer-budget[Timeouts & Budgets Specification, Task Re-Offer Budget]); the re-offers are recorded as the `job_incomplete` condition of the state, which the view shows and which offers no link (xref:04-ast-node-model.adoc#condition-overlays[Condition Overlays]). For an entity of the multi-submit unit `entity-multi.pmwf` (<<workflow-definition-units>>) the required submission is the closing submit; what its repeatable submits persisted stays, and the next attempt continues from it.
4. *Conservative fallback (`lost`)*: A task that closes `lost` (its re-offers spent, or closed without an attempt because its role is undefined, unqualified, or has no startable worker, link:../model-work/01-roles-and-configuration.adoc#conservative-fallback[Model Work Specification, Conservative Fallback]) settles the state with the reserved outcome `lost` (class `INDETERMINATE`), with the task's reason recorded as the gap. A state routes `lost` to the fallback it declares: a conservative `auto` state of its unit (a remediation unit's `conservative`, which takes the unit's single `retry` once and otherwise `exhausted`), a server step-out of its sub-workflow, or, for an optional step, the continuation that completes the step `failed`. A state of a plan-scope unit that declares no `lost` transition takes the phase's fallback: the engine unwinds every call frame in one transaction with the server step-out `stepped_out {by: server, cause: lost, reason}` and enters `plan.return` or `finalize.hand-back`, like a spent condition budget. A state of an epic, workspace, or bootstrap unit, and of a sub-workflow such a unit calls, declares its `lost` transition (Rule 2). A state whose item the epic marked `held` (link:../model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]) creates no task when it is entered again for that item and awaits the event of a change of the effective role set. No `lost` route reaches the operator.
5. *Leaf*: A worker's connection reaches only the task entities leased to its generation; no entity unit and no consultation task contains a task state, offers a link into one, or offers a `consult` link (Rule 4). A consultation is a task of the consulted role created by the server, never a model a worker starts (`PM-WORK-4`).
6. *Fan-out (`each <primitive_id>`)*: A state that declares `each` runs one task per element of a server-computed list. Entering it runs the named list primitive (registered and read-only, Rule 1), allocates one entity per element (for the zero-tool kind `screen`, which has no entity, one batch part per element), and creates one task per element, each with its own entity; workers of the role take them within the role's `count` and the machine's model slots. The state binds like a composite (<<job-state-binding>> item 7): the bound identifier is the state identifier in `active_job`, and the tasks are recorded in `active_tasks`, one per entity. Items 2 to 5 and Rules 2, 4, and 11b apply per task: every task's end runs the kind's return evaluation on that task's entity, and the state completes, taking the transition of the evaluation's outcome over the whole list, once every task has ended. An entity whose task closed `lost` after its re-offers is passed to the evaluation as missing (for `screen` a missing or unparseable verdict counts as `suspicious`); the state settles `lost` only when its role is undefined, unqualified, or has no startable worker. The re-offers cover only the unfinished entities. An empty list completes the state in the entering transaction. The fan-out states of the default units are `setup.enrich-architecture` (one task per module to enrich) and the screener states (one task per part of a batch; a batch above the screening split bound has several parts, link:../model-work/07-untrusted-text-screening.adoc#screener[Model Work Specification, Screener]).
7. *Session as optional worker*: A task of a `read_only` role whose artifact sets `session_first` (no other class may set it) may be offered to the entry session first; the session follows the same `worker-task` protocol, and the state never waits on it (link:../model-work/02-task-protocol.adoc#session-worker[Model Work Specification, The Session as Optional Worker]).

[#worker-task-unit]
=== Task Protocol Unit (`worker-task.pmwf`)
_See Requirement link:../../Requirements.adoc#PM-WORK-2[PM-WORK-2: Task Protocol]_

The protocol of one task is the compiled sub-workflow unit `worker-task`; its semantics, leases, generations, and fencing are specified in link:../model-work/02-task-protocol.adoc#worker-task-unit[Model Work Specification, The `worker-task` Sub-Workflow]. A `job llm` state runs one instance per task in the task's own frame, recorded in the queue task record and never on the scope's `call_stack`, so the tasks of a fan-out state run side by side. The engine binds the role, the entity, and the consultation roles of the calling state; no unit calls `worker-task` with `call`, and no project unit can replace it.

[source,text]
----
workflow worker-task version 1 format 1
scope subworkflow
start task.queued

state task.queued
  phase inherit
  auto task.call-model                      # the model caller: role, artifact, qualification, re-offer budget
    queued          -> task.waiting
    closed          -> task.lost            # role_undefined, role_unqualified, role_unavailable, attempts_spent

state task.waiting
  phase inherit
  composite_job task.await-offer            # a pm_wait of a worker of the role; the offer leases the task
    offered         -> task.offered
    released        -> task.queued          # the role's workers were stopped (start-failure guard)
    cancelled       -> task.lost

state task.offered
  phase inherit
  composite_job task.await-ack              # the link ack within the host's acknowledgement deadline
    acknowledged    -> task.executing
    released        -> task.queued          # worker lost, deadline missed, or offer withdrawn
    cancelled       -> task.lost

state task.executing
  phase inherit
  composite_job task.await-entity           # the entity unit of the kind runs; its links are the task's links
    submitted       -> task.submitted
    asked           -> task.asked
    infeasible      -> task.infeasible
    consulting      -> task.consulting
    released        -> task.queued          # worker lost or ended without the required submission
    cancelled       -> task.lost

state task.consulting
  phase inherit
  composite_job task.await-consultation     # a task of the consulted role; the answer through the next pm_wait
    answered        -> task.executing
    released        -> task.queued          # the answer reaches the successor in the task's facts
    cancelled       -> task.lost

state task.submitted terminal submitted success
  phase inherit

state task.asked terminal asked unsettled
  phase inherit

state task.infeasible terminal infeasible failure
  phase inherit

state task.lost terminal lost indeterminate
  phase inherit
----

Every transition of the unit is an engine event or an `auto` primitive. The only links a worker follows are `ack`, the links of the task's entity unit, and the `consult:<role>` links of the calling state; the unit offers no `step_out` and no link that ends a scope. Every cycle passes a `composite_job` state that awaits a worker's call or the time of a deadline (Rule 11b), and `task.call-model` closes the task `lost` once the re-offer budget is spent, so the unit always ends. `cancelled` is the engine's cancellation when the scope ends (`pm-operator abort`, `delete-plan`) or the state is left otherwise; the task's record names the cause.

[#question-states]
== Question States & the Question Deadline
_See Requirement link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_

Every content question is a server-owned question record (link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]). A worker creates one through the `ask` link of a task whose state declares it (`question: schema[question-envelope]`; the task ends `asked`), through `ask:TASK-NNN` on a task envelope (which ends the envelope task), or through the `questions` list of a refine or outline `submit`; a server primitive creates the questions whose options it owns (init classifiers, the optional outline review, workspace setup choices that write team configuration). Choices that write operator configuration, waivers, `abort`, and integrity resolutions are never question records; they use the operator channel only.

A *question state* is a state whose body starts with `question <class>` (xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Formal EBNF Grammar]; `StateBehavior.QuestionWait`, xref:04-ast-node-model.adoc#_ast_node_model[AST Node Model]). Entering it runs the adjudication of the scope's new question set (<<question-adjudicate-unit>>) before any delivery; an `auto_decided` set resolves the state like an answer. It rests until the scope's open record of that class is resolved and then takes the outcome transition of the resolution. Every resolution outcome enters a re-entrant `auto` state that reads the answer from the record and decides, as `init.classify` does, or returns to the asking task state; the choice between the options of an answer is routed there, never by the question clause (for example the budget check of a `revise` answer to the outline review). An `ask` question state (`<state>.asked`) returns to the asking task state, which creates a new task with the answer in its `facts`. The catalogue kind `awaiting_user` is derived from this clause, so the kind stays derivable from the AST.

* *Delivery*: A content question of a plan or epic is delivered through the web app, which notifies the paired devices and is the dependable channel, and is shown to the entry session while one is open, through the answer link `answer:<question_id>` of the scope's view (<<implicit-job-links>>); the first valid answer wins, and the answer records its channel (`web` or `session`). MCP elicitation carries only the choices of the project setup and of the plan and epic bootstraps (`elicitation`), which the entry session drives (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]).
* *Mode*: The effective `questions.mode` of the class (operator `local-config.json`, per project with per-class overrides) decides how the record resolves. `auto` (default) delivers it and sets the deadline `questions.wait_seconds` (default `1800`) from the delivery; `operator` delivers it and sets no deadline (the only unbounded wait a plan can have, chosen by the operator); `panel` lets the adjudication answer the set where the decision panel agrees (`channel: panel`) and otherwise continues as `auto`; `none` applies the `recommended` option or `default_assumption` at once (`channel: assumption`), so the question state resolves in the transaction that entered it.
* *Deadline*: The deadline is server-owned and processed by the job runtime's timer (link:../job-runtime.adoc[Job Runtime Specification]): on expiry the engine resolves the record through the class's compiled fallback (`channel: assumption`) and takes the matching outcome transition without a model call. The timer needs no session. An integrity pause holds the fallback transition until the pause ends; `pm-operator abort` and `delete-plan` close every open record `cancelled`.
* *Resolution outcomes*: Each class has a closed outcome set, which a question clause must route exactly (Rule 2):
+
[cols="1,2,3"]
|===
|Class |Outcomes |Expiry fallback (compiled)

|`init`
|`answered`, `assumed`, `returned`
|The classifier's `recommended` option as a recorded assumption (`assumed`); `returned` where the classifier declares no safe default.

|`clarification`
|`answered`, `assumed`
|The envelope's `default_assumption`, recorded as an assumption amendment.

|`review`
|`approve`, `revise`, `returned`
|`returned` (a review that was asked for and not given never starts execution).

|`task`
|`answered`, `assumed`
|The question's stated default, validated against its options, recorded as an assumption.

|`setup`
|`answered`, `assumed`
|The fallback the question state declares, recorded as an assumption.

|`ask`
|`answered`, `assumed`
|The question's stated default, validated against its options; the asking task then decides on its own judgment.
|===
* *Answer validation*: Every channel passes the same validation: an unknown `branch_key` is rejected with `invalid_link_args`, a second answer with `already_answered`, an answer after the deadline with `question_expired`. A relayed answer is accepted for content questions only, never for an override (`PM-WF-12`).
* *Awaited events*: A question state awaits `QUESTION_ANSWER` (an answer on any channel) and `TIME` (the deadline) (Rule 11b, xref:05-primitives.adoc#primitive-spi-contract[`Primitive<P, R>` SPI Contract]).

[#question-adjudicate-unit]
=== Adjudication Unit (`question-adjudicate.pmwf`)
_See Requirement link:../../Requirements.adoc#PM-WF-18[PM-WF-18: Question Recommendation Score & Decision Panel]_

The adjudication of a question set is the compiled sub-workflow unit `question.adjudicate`; its rules, the blind input, the decision rule, and the record are specified in link:../model-work/10-decision-panel.adoc#adjudication[Model Work Specification, Decision Panel]. Every question state runs one instance for the scope's new question set when it is entered, in its own frame, recorded on the set's question records and never on the scope's `call_stack`, like `worker-task` in a `job llm` state; no unit calls it with `call`, no unit can omit it, and no project unit can replace it. The engine binds the set; the unit reads the effective mode, the panel configuration, and the records. Its exit contract is `auto_decided` and `delivered`; the engine routes the control outcome `stepped_out` like `delivered`, so a set the unit cannot finish reaches the user.

[source,text]
----
workflow question.adjudicate version 1 format 1
scope subworkflow
start adjudicate.check

state adjudicate.check
  phase inherit
  auto question.check-adjudication          # mode panel, valid panel, every kind in auto_kinds, score >= min_score
    eligible        -> adjudicate.panel
    ineligible      -> adjudicate.delivered # reason mode, panel_invalid, panel_not_diverse, kind_ineligible, below_score

state adjudicate.panel
  phase inherit
  job llm panel role each question.panel-roles   # one blind task per panel role; empty list: completes at once
    collected       -> adjudicate.decide
    lost            -> adjudicate.delivered # no panel task could be served: the set goes to the user

state adjudicate.decide
  phase inherit
  auto question.decide-agreement            # the decision rule over the asker and the answering panel roles
    agreed          -> adjudicate.auto-decided
    not_agreed      -> adjudicate.delivered

state adjudicate.auto-decided terminal auto_decided success
  phase inherit

state adjudicate.delivered terminal delivered success
  phase inherit
----

The state `adjudicate.panel` is the one task state whose roles come from configuration (`role each <primitive_id>`, xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Formal EBNF Grammar]): the read-only primitive `question.panel-roles` returns the configured panel roles, and the state creates one task per role, each with its own entity of the kind `panel`, which a fresh worker of that role does through `worker-task`. The return evaluation of the kind records each answer and settles `collected` once every task has ended or the compiled panel wait expired (link:../timeouts/01-job-budgets-and-waits.adoc#panel-wait[Timeouts & Budgets Specification, Panel Wait]); a task without a valid answer is passed to `adjudicate.decide` as missing, and the state settles `lost` only when no task of the list was served. The transaction of each terminal writes the set's `adjudicated` lines with the outcome and its reason (in mode `panel` only) and, for `auto_decided`, the answers. The unit never asks anyone: every path ends in a terminal without a link, a question, or a waiver.

[#waivers-and-integrity]
== Waivers, Waiver Requests & the Integrity Pause
_See Requirement link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-18[PM-WATCH-DSL-18]_

_See Requirement link:../../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_

The process enforces itself: no state of any unit waits for an operator decision, and the DSL has no decision construct (no decision registry, no escalation action or form, no pending decision). Every blocking condition gets a bounded self-remedy, mostly a remediation policy unit (xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units]), and then a defined fallback end. The operator influences a running plan only through records written on the operator channel, which primitives read:

* *Waiver record*: `pm-operator waive <plan> <gate> --reason …` declares a waivable gate met (`mode: met`), `waive <plan> --raise <budget>=N --reason …` raises a budget ceiling (`mode: raise`), and `unwaive` revokes an unconsumed waiver (link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record]; link:../cli-and-security.adoc[CLI, Coordination & Security Specification]). The gate identifiers form a closed list: `review_evidence[:<bot_kind>]`, `ci_check:<check_name>`, `analysis_gate:<provider>`, `findings:<class>` and `findings:<provider>`, `qgate_findings:<phase>`; the raisable budgets are `fix_budget:<policy>`, `retry_budget:<policy>`, and `spend`. A waiver is plan-scoped, settable at any time until the gate's fallback is taken, and applies to every later evaluation of its gate; after the fallback it is refused (`plan_ended`). Every waiver line composes a new plan instance version (event `waiver`), which marks the gate waived with the waiver id or carries the raised ceiling with its source.
* *Reading a waiver*: A waivable gate admits a failure only through `waiver.lookup(gate)` (read-only in `WorkflowExecutionContext`), which appends a consumption naming `HEAD` and the covered items; the PR comment and the landing record list every consumption. A primitive may look up only the gate identifiers it declares in `waivableGates()` (xref:05-primitives.adoc#primitive-spi-contract[`Primitive<P, R>` SPI Contract]), and no primitive can write a waiver (`INV-GEN-2`, xref:04-ast-node-model.adoc#project-owned-units[Compiled Invariants]). In the DSL a waived path is visible only as the `waived` terminal of a remediation unit.
* *Waiver requests*: The `request_waiver (rationale: text[1..2000])` link (rel `escalate`, form `submit`) of a remediation unit's decision task, and an exhausted budget with `waiver_wait_seconds > 0`, file a request record (`waiver_requests[]`, announced through the operator channels and an idempotent PR comment). It is an ordinary `submit` link: nothing waits for an answer except the bounded waiver wait of the unit, a `composite_job` (`remediation.await-waiver`) that awaits `OPERATOR_WAIVER` or `TIME` and ends `raised`, `waived`, or `expired`. The shipped `waiver_wait_seconds` is `0`, so by default a request goes into the hand-back report.
* *Operator-initiated ends*: `pm-operator abort <plan|epic> <id> --reason` and `delete-plan` are engine-owned, scope-wide transitions into `plan.aborted` or `epic.aborted` in the next transaction, under the on-entry rule (every begun, unsettled step recorded `failed`); they close open question records `cancelled` and pending waiver requests `expired`. They need no DSL construct: no unit declares a transition into an abort terminal (xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Formal EBNF Grammar], Ends of a scope).
* *Integrity pause*: The only pause of a plan is the condition overlay `integrity_breach {kind: store_tampered | enrolment_tampered, store, recorded_digest, current_digest}` (xref:04-ast-node-model.adoc#condition-overlays[Condition Overlays (Engine-Owned)]). It offers no link, every `pm_do` of the paused scope is rejected with `integrity_paused`, and `facts.operator_command` names the two resolutions: `pm-operator accept-edit …`, after which the engine re-verifies the digests before it clears the condition, and `pm-operator abort …`. It has no bound and no fallback, because a tampered store cannot be trusted to write a hand-back; the deadlines of a pending question or waiver request of the paused scope are held until it ends.
