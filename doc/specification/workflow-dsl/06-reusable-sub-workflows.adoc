== Reusable Compound Sub-Workflows & Call-Stack Execution (`PM-WF-16`)
_See Requirement link:../../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

Workflows are composed not only of atomic `do` / `auto` / `job` primitives, but also of reusable, config-aware *compound sub-workflows* (`scope subworkflow`). A compound sub-workflow encapsulates a multi-state sub-process (deterministic `auto` checks, configuration lookups, conditional interactive pauses, and recovery branches) and handles its internal cases locally with its own states and links, so that Phase 5 (`execute`), Phase 6 (`finalize`), the workspace setup, and the epic invoke the exact same state machine rather than duplicating states or collapsing interactive recovery into opaque Java code. Its exit contract towards the caller is small and control-only (xref:01-grammar.adoc#sub-workflow-exits[Sub-Workflow Exit Contract]). The shipped sub-workflows are `git.commit_and_push` (below) and the remediation policy units (xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units]).

=== Call-Stack Execution & Persistence Semantics

1. *Sub-Workflow Invocation (`call`)*: When the engine transitions into a `StateNode` whose behavior is `StateBehavior.SubWorkflowCall(subWorkflowId, paramBindings, transitions)`, it pushes a `CallFrame(callerWorkflowId, callerStateId, callerPhase, subWorkflowId, paramBindings, Instant.now().toString())` onto the `call_stack` array in `mcp/status.json` and sets `status.state` to the target sub-workflow's `startState` while preserving `status.phase = callerPhase` whenever a sub-workflow state declares `phase inherit` (the caller state's resolved phase value; xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Formal EBNF Grammar for the Workflow DSL]). `callerWorkflowId` is the id of the caller's definition unit, `plan` for every state of the plan instance (xref:02-units-jobs-decisions.adoc#workflow-definition-units[Workflow Definition Units (Multi-File Workflows)]). `paramBindings` are the effective values the plan instance binds at the call site, whose provenance (template file, composition rule, or waiver) the instance header records (xref:09-plan-instance.adoc#plan-instance[Plan Instance]). Preserving `callerPhase` guarantees that phase-scoped guards (such as `in_worktree`), phase metric accounting (`metrics.json`), and terminal-title updates remain invariant regardless of which caller invoked the sub-workflow.
2. *Interactive Pauses & Job Waits Inside a Sub-Workflow*: If execution inside the sub-workflow reaches an `AutoStep`, the engine executes it immediately in the same turn. If execution reaches an `InteractiveLinks` state (such as `git.artifact-review`, `git.compose-message`, `git.commit-fix`, or a remediation unit's `decide`) or a `JobStep`, the engine persists `mcp/status.json` (with the active `call_stack` and sub-workflow `state`) and returns that state's TOON representation to the caller. Subsequent `pm_do` or `pm_state` calls resolve against the active sub-workflow state at the top of `call_stack`, surviving context compactions and daemon restarts identically to top-level states.
3. *Sub-Workflow Return (`terminal <outcome_id> <outcome_class>`)*: When a transition inside the sub-workflow lands on a `StateNode` whose `terminalOutcome` is present with the id `outcomeId`, the engine assembles the frame's result record (for `done`: the fields the unit's primitives contributed through `PrimitiveResult.updatedFacts`, validated against the unit's `result` schema), pops the top `CallFrame` from `call_stack`, selects the caller's transition for `outcomeId` (for an outcome routed twice, the one whose result guard holds), transitions `status.state` to its target in `callerWorkflowId`, and continues auto-chaining in the same atomic transaction.
4. *Step-Out (`stepped_out`)*: The implicit `step_out (reason)` of a resting link state (xref:02-units-jobs-decisions.adoc#implicit-job-links[Implicit Links]) returns like a terminal with the outcome `stepped_out {by: model, cause: step_out, reason}`; a terminal of class `stepped_out` returns `{by: server, cause: <the outcome that entered it>}`. Exactly one frame unwinds; the caller routes the outcome once (Rule 6), and a caller that is itself a sub-workflow routes it to one of its own link states, where the model may step out further. A step-out consumes no budget and writes no waiver; the gap record of a fallback it leads to names `cause: stepped_out` with the reason.
5. *Guided Step-In*: A `call` makes the sub-workflow's first resting state current, and the representation shows the call-path breadcrumb (the caller states of every frame). Each interactive state of a sub-workflow asks for exactly one piece of model judgment through one link naming its skill section (`skill` clause, Rule 6); it asks only for inputs the server cannot derive and never bundles unrelated inputs. This is a design rule for every sub-workflow, including the remediation units, whose `decide` state asks only for the remedy and leaves the triage of individual findings to a separate state.

=== Canonical Reusable Sub-Workflow: `git.commit_and_push` (`git-commit-and-push.pmwf`)

The `git.commit_and_push` sub-workflow models the complete git commit-and-push sub-process grounded in `workflow-integration-git`, `phase-5-execute` (Step 10a), and `phase-6-finalize` (Step 3 item 5f, `standards/push.md`, and post-PR re-push). The unit and its states stay in `pm-mcp-workflow`; the git operations its primitives invoke are contracts of the provider module `pm-mcp-git` (link:../module-structure.adoc#module-pm-mcp-git[Module Structure, `pm-mcp-git`]).

==== Bound Parameter Contract

The sub-workflow header declares both parameters with `param` and its result record with `result` (see the DSL definition below); every `call git.commit_and_push (…)` site must bind both parameters exactly once with a declared value (Rule 6 in xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules (Build Time & Every Unit Load)]).

[cols="1,2,3"]
|===
|Parameter |Allowed Values |Semantics

|`message_mode`
|`auto_deliverable` \| `step_or_fallback` \| `interactive` \| `none_assert_clean`
|Controls commit message sourcing: `auto_deliverable` formats `feat(<module>): complete deliverable <N> - <title>` from the active deliverable (*a `PM-MCP` choice*: `plan-marshall`'s `phase-5-execute` Step 10a derives the commit message from the task title instead); `step_or_fallback` uses a step-supplied commit message or `chore(finalize): apply <step_id> changes`; `interactive` pauses in `git.compose-message` with diff analysis facts for model submission; `none_assert_clean` expects a clean working tree (used by `finalize.push-barrier`) and routes any unexpected dirty files through `git.compose-message` before pushing.

|`push_mode`
|`never` \| `if_push_remote` \| `always` \| `post_pr_conditional`
|Controls push execution after commit (or on a clean tree): `never` stops after local commit; `if_push_remote` pushes when the project has a push remote (derived fact `push_remote`, link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts Store]; a `stale` or `failed` fact is `indeterminate`, never "no remote"); `always` pushes unconditionally; `post_pr_conditional` pushes if and only if the order of the persisted `settle_trigger` is greater than `20` (after `create-pr`) and a push remote exists. `settle_trigger {step_id, order}` is written by the transition entering `finalize.settle-commit`: the step whose firing is open, or order `0` when the caller is not a step (`execute.exit-barrier`, `land.exit-barrier`, `finalize.adopt-pr`), so such a caller never pushes. No configuration key suppresses a push (`plan-marshall`'s `commit_and_push` does not exist).
|===

*Exit contract*: `done` with the result record `commit-result {commit?, pushed, clean}`, where `commit` is the SHA of the commit this call made (absent when none), `pushed` means that the remote branch holds `HEAD` after the call (so a clean tree whose `HEAD` the remote already holds returns `{pushed: true, clean: true}` without a push), and `clean` that the working tree was clean on entry; plus `stepped_out {by, cause, reason}`, returned by the model's `step_out` or by the server after exhausted commit attempts (`cause: attempts_exhausted`) or an exhausted `.gitignore` oracle retry (`cause: oracle_failed`). Callers branch on the result with result guards (`guard result.pushed`); no caller routes a push-mode-specific outcome.

==== Declarative DSL Definition (`classpath:/workflows/git-commit-and-push.pmwf`)

[source,text]
----
workflow git.commit_and_push version 1 format 1
scope subworkflow
param message_mode: enum[auto_deliverable|step_or_fallback|interactive|none_assert_clean]
param push_mode: enum[never|if_push_remote|always|post_pr_conditional]
result schema[commit-result]
start git.inspect-worktree

state git.inspect-worktree
  phase inherit
  auto git.inspect-worktree
    dirty                   -> git.detect-artifacts
    clean_skip_push         -> git.done
    clean_needs_push_check  -> git.evaluate-push-policy

state git.detect-artifacts
  phase inherit
  auto git.detect-artifacts
    clean_or_safe_deleted   -> git.resolve-message
    uncertain_or_prohibited -> git.artifact-review
    oracle_failed           -> git.artifact-escalate

state git.artifact-escalate
  phase inherit
  auto git.retry-oracle                         # bounded re-run of the detection
    clean_or_safe_deleted   -> git.resolve-message
    uncertain_or_prohibited -> git.artifact-review
    exhausted               -> git.stepped-out

state git.artifact-review
  phase inherit
  skill pm/git/artifact-cleanup
  facts git.artifact-candidates
  link next confirm_cleanup [submit] (action: enum[delete_uncertain|keep_tracked], paths: list<text>?)
    do git.apply-artifact-decision
      resolved              -> git.resolve-message
      prohibited_remaining  -> git.artifact-review

state git.resolve-message
  phase inherit
  auto git.resolve-message
    ready                   -> git.stage-and-commit
    needs_interactive       -> git.compose-message

state git.compose-message
  phase inherit
  skill pm/git/commit-message
  facts git.diff-summary
  link next commit [submit] (message: text[1..2000])
    do git.validate-message
      valid                 -> git.stage-and-commit

state git.stage-and-commit
  phase inherit
  auto git.stage-and-commit
    committed               -> git.evaluate-push-policy
    nothing_to_commit       -> git.evaluate-push-policy
    hook_failed             -> git.commit-fix

state git.commit-fix
  phase inherit
  skill pm/git/commit-recovery
  facts git.hook-failure
  link retry retry [noop] ()
    do git.retry-commit
      ok                    -> git.evaluate-push-policy
      hook_failed           -> git.commit-fix
      attempts_exhausted    -> git.stepped-out
  link fix recompose [submit] (message: text[1..2000])
    do git.validate-message
      valid                 -> git.stage-and-commit

state git.evaluate-push-policy
  phase inherit
  auto git.evaluate-push-policy
    skip_push               -> git.done
    push_required           -> git.verify-freshness

state git.verify-freshness
  phase inherit
  auto git.pre-commit-verify-freshness
    fresh_or_exempt         -> git.check-branch-parity
    stale_or_undecidable    -> git.freshness-blocked

state git.freshness-blocked
  phase inherit
  skill pm/finalize/push-barrier
  facts git.freshness-status
  link fix run_verification_build [noop] ()
    do build.enqueue-verification
      started               -> git.freshness-build-running

state git.freshness-build-running
  phase inherit
  job build.verify-worktree
    succeeded               -> git.verify-freshness
    failed                  -> git.freshness-blocked
    failed_unparsed         -> git.freshness-blocked
    refused                 -> git.freshness-blocked
    cancelled               -> git.freshness-blocked
    timed_out               -> git.freshness-blocked
    killed                  -> git.freshness-blocked
    indeterminate           -> git.freshness-blocked

state git.check-branch-parity
  phase inherit
  auto git.push-barrier-decision
    first_push              -> git.execute-push
    refire                  -> git.execute-push
    rewritten_by_rebase     -> git.push-with-lease
    skip                    -> git.done

state git.execute-push
  phase inherit
  auto git.push
    pushed                  -> git.done
    up_to_date              -> git.done
    rejected_non_ff         -> git.sync-required
    rejected_lease          -> git.sync-required

state git.push-with-lease
  phase inherit
  auto git.push-with-lease
    pushed                  -> git.done
    up_to_date              -> git.done
    rejected_non_ff         -> git.sync-required
    rejected_lease          -> git.sync-required

state git.sync-required
  phase inherit
  skill pm/git/sync-recovery
  facts git.branch-divergence
  link fix sync_rebase [noop] ()
    do git.rebase-onto-upstream
      rebased               -> git.verify-freshness
      conflict              -> git.resolve-conflicts
      rebase_failed         -> git.stepped-out

state git.resolve-conflicts
  phase inherit
  skill pm/git/sync-recovery
  facts git.rebase-conflict
  link fix continue_rebase [noop] ()
    do git.rebase-continue
      rebased               -> git.verify-freshness
      conflict              -> git.resolve-conflicts

state git.done terminal done success
  phase inherit

state git.stepped-out terminal stepped_out stepped_out
  phase inherit
----

NOTE: The sub-workflow has no operator escalation and no override state. The `.gitignore` oracle is retried by the server: `git.artifact-escalate` re-runs the detection a compiled number of times and then steps out (`cause: oracle_failed`); nothing is ever staged past an unclassified path. A stale or undecidable freshness verdict is never pushed: `git.freshness-blocked` offers only `run_verification_build` (and the implicit `step_out`). A repository hook failure is never bypassed: `git.commit-fix` offers `retry` and `recompose`, and `git.retry-commit` returns `attempts_exhausted` after `3` failed commit attempts on an identical staged change set (the staged tree id and the message; compiled constant, link:../timeouts.adoc[Timeouts & Budgets Specification]); the counter resets when the staged tree or the message changes (a fix, a hook that rewrote files, a `recompose`). Hooks run only in the CLI variant, so only that variant reaches `git.commit-fix`. `attempts_exhausted` enters `git.stepped-out`, and so does a rebase that could not start (the fetch or the rebase start failed: `rebase_failed`, server step-out with `cause: rebase_failed`); there is no escalation state for it. A rebase conflict is model work: `git.resolve-conflicts` offers `continue_rebase` once the model has resolved the conflicted files in the checkout; a `step_out` from it or from `git.sync-required` lets the server abort the unfinished rebase and restore the pre-rebase branch before the frame unwinds. The only forced push is `git.push-with-lease`, entered automatically when the parity decision finds that a server rebase rewrote the plan's own, already pushed branch (Stage 6); every other force push is refused.

Every resting link state (`git.artifact-review`, `git.compose-message`, `git.commit-fix`, `git.freshness-blocked`, `git.sync-required`, `git.resolve-conflicts`) asks for one judgment through one link naming its skill section (`confirm_cleanup` with `pm/git/artifact-cleanup`, `commit` with `pm/git/commit-message`, `retry` or `recompose` with `pm/git/commit-recovery`, `run_verification_build` with `pm/finalize/push-barrier`, `sync_rebase` and `continue_rebase` with `pm/git/sync-recovery`), and offers the implicit `step_out`. `stepped_out` never ends the plan, the epic, or the workspace run by itself: the caller routes it (Rule 6, <<_call_site_reuse_matrix_across_workflows>>).

==== Six-Stage Execution Contract of `git.commit_and_push`
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-6[PM-WATCH-DSL-6], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-7[PM-WATCH-DSL-7], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-10[PM-WATCH-DSL-10], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-9[PM-WATCH-STORE-9], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-73[PM-WATCH-PHASE-73], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-74[PM-WATCH-PHASE-74]_

* *Stage 1 — Working-Tree Inspection (`git.inspect-worktree`)*:
** Resolves the target checkout path from the locked scope context: `worktree_path` of a plan while it is set, the main checkout (the enrolled `project_root`) for a plan whose `worktree_path` is `null` and for `workspace`, and the shared epic worktree (link:../filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification]) when `epic`. Git-tracked orchestrator state is never committed on the primary checkout (`PM-ARCH-5`).
** Executes `git -C <tree> status --porcelain` (ignoring `.marshall/local/**`).
** If uncommitted changes exist (`staged`, `unstaged`, or `untracked`), returns `dirty -> git.detect-artifacts`.
** If the working tree is clean: returns `clean_skip_push -> git.done` (result `{pushed: false, clean: true}`) when `push_mode == never`; otherwise returns `clean_needs_push_check -> git.evaluate-push-policy` so clean-tree push barriers (`finalize.push-barrier` or post-rebase pushes) proceed directly to the freshness and parity checks without creating an empty commit.
* *Stage 2 — `.gitignore`-Aware Artifact Detection & Cleanup (`git.detect-artifacts`)*:
** Scans the working tree against `artifact-patterns.json` (`*.temp`, `*.backup*`, `*.orig`, `*.swp`, `.DS_Store`, `Thumbs.db`, coverage/build scratch files) while querying `git -C <tree> check-ignore`.
** Fails closed (`oracle_failed -> git.artifact-escalate`) if the `.gitignore` oracle cannot be evaluated: `git.retry-oracle` re-runs the detection a compiled number of times with backoff (link:../timeouts.adoc[Timeouts & Budgets Specification]) and, when the oracle still fails, ends the call with the server step-out `stepped_out {by: server, cause: oracle_failed}`. There is no override: a path the oracle could not classify is never staged.
** Unconditionally excludes `.marshall/**` and any nested git worktrees or submodules (`git submodule status` / `.git` file markers) from deletion.
** Automatically deletes `safe` untracked artifact files and records `artifacts_deleted` in the audit log.
** Transitions to `git.artifact-review` only for paths in the change set of this commit (porcelain entries: staged, unstaged, untracked) that match artifact patterns and are `uncertain`, or for prohibited secret files (`.env*`, `*.pem`, `*.key`, `credentials.json`) in that change set. Unchanged tracked files are never candidates; unchanged tracked files that match artifact patterns are recorded only as a count (`tracked_pattern_matches`) in the audit record, never rendered, since no link acts on them.
* *Stage 3 — In-Memory Commit Message Resolution, Validation & Trailer Injection (`git.resolve-message` / `git.compose-message`)*:
** When `message_mode` is `auto_deliverable` or `step_or_fallback`, resolves the deterministic commit message in memory (e.g., `feat(<module>): complete deliverable <N> - <title>` or `chore(finalize): apply <step_id> changes`).
** When `message_mode == interactive` (or `none_assert_clean` when unexpected dirty files were found), transitions to `git.compose-message`, populates `facts` via `git.diff-summary` (changed file count, module scope, priority-ordered suggested type `fix > feat > perf > refactor > docs > style > test > chore > ci`), and accepts `message: text[1..2000]` directly in `pm_do` `args`.
** Validates Conventional Commits format (`<type>[optional (<scope>)][!]: <subject>`) via `ConventionalCommitValidator` and deterministically appends the configured trailer `Co-Authored-By: {name} <{email}>`, resolved as in `plan-marshall` (`manage-run-config` `commit-trailer get`) from the operator's `commit_trailer{name,email}` in the machine-local `<PM_MCP_BASE>/projects/<project_id>/local-config.json`, falling back to `machine-config.json` `project_defaults.commit_trailer` and then to the compiled default `plan-marshall <noreply@cuioss.de>` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]); the schema refuses an empty value or one containing an angle bracket or line break. No team file is ever consulted for the trailer.
** The trailer names the system that produced the commit; it is independent of the commit's author and committer (Stage 4), which are never taken from the message.
** The resolved trailer is the only authority: a `Co-Authored-By:` line in a model-supplied `message` is rejected (`invalid_link_args`, `detail` names the line), and the only trailer in the commit is the one the server appends. The commit's audit record carries `trailer_source: {name, email}`, each half `configured`, `default`, or `invalid_ignored` (a stored value that was treated as absent); it is provenance for the operator and is never rendered in `facts`.
* *Stage 4 — Staging, `stdin`-Piped Commit & Change-Ledger Stamping (`git.stage-and-commit`)*:
** *Footprint check first*: Before anything is staged, the primitive runs the footprint check for every caller (plan, epic, and workspace scope; <<_call_site_reuse_matrix_across_workflows>>): (1) the worktree boundary: no dirty path of the target checkout lies outside the staging set derived below, and for a plan no file outside its worktree was dirtied; (2) the pinned build files: no enrolled wrapper's `pinned_files` (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Verify-Not-Resolve]) changed in the target checkout; (3) the main checkout: for a plan scope, no main-checkout path outside `.marshall/local/` is absent from `entry_baseline` or changed since it (`mcp/status.json`, link:../store-schemas.adoc[Store Schemas Specification]); for a `local_changes` plan this is the `entry_baseline` re-recorded by `land.worktree-init` after the capture restored the main checkout's captured paths, so the captured changes and their restoration never count as a violation (link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_source_contracts[Phase Workflows Specification, Plan Source Contracts]). A violation raises the `footprint_violation` condition on the current state (the sub-workflow state `git.stage-and-commit`, xref:04-ast-node-model.adoc#condition-overlays[Condition Overlays (Engine-Owned)]) naming the offending files, and no commit is made; the condition's `fix` re-runs the check. The check is part of the primitive, not of a link, so no caller can reach a commit around it.
** Derives the staging set from the scope, never from whatever the checkout holds: for a plan, the dirty paths inside its worktree after the footprint check (paths beyond the declared footprint are unplanned changes, staged and recorded with their provenance, the task or the loop-back, for the PR body and the landing record); for epic scopes, `.marshall/orchestrator/**`; for the workspace scope, the setup call's set `.marshall/config/**`, `.gitignore`, and `.marshall/project-architecture/**`. A dirty path outside that set is never staged.
** Stages the scoped files (`git -C <tree> add -- <paths>`) and invokes `git -C <tree> commit -F -`, streaming the validated UTF-8 commit message + trailer directly to child `stdin` in memory (`PM-EXEC-5`) with zero `.plan/temp/` files.
** *Author and committer*: The commit's author is the operator: `commit_identity{name, email}` of the operator's `local-config.json` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), captured in project setup. The committer is the agent identity resolved from the provider credential (the derived fact `agent_identity`: for a GitHub App its `<app-slug>[bot]` noreply address, for a token the token's user); without a resolvable agent identity it is the compiled identity `plan-marshall-mcp <noreply@cuioss.de>`. Both variants produce identical metadata: the native variant sets author and committer on the commit object, the CLI variant passes the author as `-c user.name=… -c user.email=…` and the committer through `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL`. The operator's own git `user.*` configuration is never read at commit time. Author and committer are recorded in the commit's audit record and never rendered in `facts` (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
** Captures `commit_sha` (`git -C <tree> rev-parse HEAD`) and git-sourced `changed_paths` (`git -C <tree> diff-tree --no-commit-id --name-only -r <commit_sha>`), appending a `kind = "change"` entry to `change-ledger.jsonl`.
** When invoked from a Phase 6 `mutates_source: true` step: re-stamps `head_at_completion = commit_sha` on `head_dependent: true` steps in `mcp/status.json`, and when the commit follows the latest successful build (any such step, not only steps at `order >= 10`, `pre-push-quality-gate.order`; for example `architecture-refresh` at `9` on re-entry; link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#_finalize_commit_instrumentation_freshness_reconcile_post_pr_re_push_pm_wf_16[Phase Workflows Specification, Finalize Commit Instrumentation] item 3), writes a `freshness_reconcile` record (`commit_sha`, `step_id`, `prior_build_worktree_sha` from the latest passing build row in `change-ledger.jsonl`) so the downstream push gate recognizes the finalize-internal commit without requiring a redundant full build when no source-affecting inputs changed.
** If `git commit` exits non-zero due to a repository pre-commit hook, returns `hook_failed -> git.commit-fix`.
* *Stage 5 — Config-Driven Push Policy & Freshness Precondition (`git.evaluate-push-policy` -> `git.verify-freshness`)*:
** Evaluates `push_mode` together with the derived fact `push_remote`: `push_mode == never` skips push (`skip_push -> git.done`); `push_mode == if_push_remote` requires push if and only if a push remote exists; `push_mode == post_pr_conditional` requires push if and only if a push remote exists and the persisted `settle_trigger` has `order > 20` (after `create-pr`), automating post-PR re-push for late source-mutating steps (`adr-propose`, in-branch fixes); `push_mode == always` requires push unconditionally.
** Before any push, `git.pre-commit-verify-freshness` verifies `change-ledger.jsonl` freshness (`fresh` corroborated on both notation and scope dimensions against the current `worktree_sha`, computed by the git contract operation `git.worktree-sha`, one node for both variants that returns the digest and its `worktree_sha_version`, `exempt` when `build-decision == not_necessary`, or reconciled via `freshness_reconcile`). If `stale` or `undecidable`, transitions to `git.freshness-blocked`, which offers only `run_verification_build`; a stale tree is never pushed, and there is no override.
** When no reconciliation record names the live `HEAD`, `git.freshness-status` reports `stale_reason: reconciliation_record_absent` together with the causes that absence admits (`admitted_causes` ⊆ `source_drift_unbuilt`, `no_successful_build`, `record_owed_not_emitted`, `commit_outside_reconcile_membership`). The refusal reports what it observed and never asserts a single inferred cause; the fail-closed halt is unchanged.
** `git.freshness-blocked` renders, beside `stale_reason`, the evidence it would accept: the required build notation(s) and the scope (`whole_tree` or a module list); the current `worktree_sha` is recorded in the audit record, not rendered.
* *Stage 6 — Branch Sync Parity Probe & Push Execution (`git.check-branch-parity` -> `git.execute-push`)*:
** `git.push-barrier-decision` first reads the persisted fact `branch_pushed_at` in `mcp/status.json`. When it is unset, the branch has never been pushed by this plan and the decision is `first_push` (`git -C <tree> push --set-upstream origin <branch>`) without consulting the probe. When it is set (re-entry), the decision follows `plan-marshall`'s push-barrier mapping (`workflow-integration-git/scripts/git-workflow.py`, `push_barrier_action`, verified at commit `1d4a1da37`; re-verify before implementing): it runs `git.branch-sync-state` and returns `refire` only for `ahead`, and `rewritten_by_rebase` (a *PM-MCP* addition) when the plan's recorded last push (`branch_pushed_at`) is no ancestor of `HEAD` because a server rebase (`sync-baseline` or the merge-path sync) rewrote the branch; `synced`, `remote_absent_landed`, `remote_absent_unverified`, and any unrecognised state return `skip`, which ends the call with `done` (`pushed: true`). A never-pushed branch and a squash-merged-and-deleted branch are indistinguishable locally, so `remote_absent_unverified` is resolved with provider evidence before it is classified: `ci.pr-find` by the head branch finding a merged pull request turns it into `remote_absent_landed` (`skip`, re-pushing would resurrect a landed branch); finding no pull request at all turns it into `never_pushed`, which pushes (`refire`); any other observation (an open or closed-unmerged pull request, or a provider that cannot be observed) keeps `remote_absent_unverified`, which never pushes. *Deliberate change vs. `plan-marshall`*: `plan-marshall` never pushes on `remote_absent_unverified` and consults no provider evidence.
** `git.branch-sync-state` classifies the plan's recorded `branch_name` (`mcp/status.json`), never the ambient `HEAD` of the checkout, and fetches the remote ref before classifying. A classification made without a fetch in the same transaction is labelled unverified (as `remote_absent_unverified` already is) and is never used to claim that the branch is unpushed. *Deliberate change vs. `plan-marshall`*: its `branch-sync-state` is a read-only comparison against the local remote-tracking ref and never fetches.
** `git.execute-push` (and `git.push-with-lease`) sets `branch_pushed_at` (timestamp and pushed `HEAD`) in `mcp/status.json` on the first successful push and refreshes it on every later successful push, so it always names the last pushed commit. A push answered `up_to_date` pushed nothing and ends the call with `done` (`pushed: true`).
** If `git push` is rejected as non-fast-forward (`rejected_non_ff{remote_sha}`), transitions to `git.sync-required`, which offers `sync_rebase`. `sync_rebase` rebases onto the fetched upstream; a conflict enters `git.resolve-conflicts` (model work, never an operator decision).
** *Explicit push lease*: The only forced push is `git.push-with-lease`, a server rule rather than a decision: it is entered automatically when the parity decision returns `rewritten_by_rebase`, pushes only the plan's own branch, and always names its lease explicitly as the expected remote SHA, in both variants: the `remote_sha` observed at the last rejection, else the SHA of the last recorded push (`branch_pushed_at`). The local remote-tracking ref is never the lease, because a fetch between observation and push moves it and turns the lease into a plain force. A `rejected_lease{remote_sha}` (the remote moved meanwhile) returns to `git.sync-required`; any other force push is refused. Before every retry of a rejected push, the remote branch is re-read (`ls-remote`) and the retry uses the re-read SHA. *Deliberate change vs. `plan-marshall`*: `plan-marshall` pushes `--force-with-lease` without an expected value, taking the lease from the tracking ref.
