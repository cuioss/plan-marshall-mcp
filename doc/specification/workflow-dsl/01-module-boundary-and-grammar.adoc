== Module Boundary & Decoupled Core Architecture
_See Requirement link:../../Requirements.adoc#PM-IMPL-1[PM-IMPL-1: Decoupled Plain-Java Core Engine & Quarkus Assembly]_

_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-12[PM-WATCH-DSL-12], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-13[PM-WATCH-DSL-13]_

The workflow engine is strictly decoupled from Quarkus, CDI, Vert.x, and MCP transport libraries. All modules are created and integrated in Milestone 0 (link:../../roadmap.adoc[Roadmap]), each with minimal real code and tests: the root `plan-marshall-mcp` module is renamed to `pm-mcp-server`, the library modules are gathered under the aggregator `pm-mcp-modules` (the external integrations under the nested aggregator `pm-mcp-providers`), the client modules under the top-level aggregator `pm-mcp-clients`, and an automated build check enforces the dependency direction (`PM-IMPL-1`). Dependencies flow toward `pm-mcp-core`: provider contract and implementation modules depend on `pm-mcp-core`, implementation modules on their contract modules, and `pm-mcp-server` on all of them and on `pm-mcp-api`. The client modules never depend on `pm-mcp-core` or a provider module: `pm-mcp-cli` depends on `pm-mcp-api` only, `pm-mcp-web-server` on `pm-mcp-api`, `pm-mcp-web-app`, and Quarkus. One release produces four native binaries: `pm-mcp` (CLI), `pm-mcpd` (daemon), `pm-mcp-exec` (job launcher), and `pm-mcp-web` (optional web server).

Which implementation of `pm-mcp-git`, `pm-mcp-github`, or `pm-mcp-gitlab` serves a project is decided explicitly per integration by the operator in project setup (`setup.select-integration-variants`, link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]): the native variant is recommended, neither variant is an implicit default, and there is no automatic fallback from one variant to the other.

The deterministic scenario replay harness `pm-mcp-scenario` (xref:07-loop-back-diagrams-verification.adoc#_deterministic_scenario_replay_harness_pm_mcp_scenario_pm_test_4[Deterministic Scenario Replay Harness (`pm-mcp-scenario`, `PM-TEST-4`)]) is not a module: it is a test-scope part of `pm-mcp-core` (JUnit, in-process).

== Formal EBNF Grammar for the Workflow DSL
_See Requirement link:../../Requirements.adoc#PM-WF-2[PM-WF-2: Closed Link Relation Grammar & Link Forms]_

_See Requirement link:../../Requirements.adoc#PM-WF-3[PM-WF-3: Capability Enforcement by Link Omission]_

_See Requirement link:../../Requirements.adoc#PM-WF-4[PM-WF-4: Entity-Scoped Links & Fine-Grained Concurrency]_

_See Requirement link:../../Requirements.adoc#PM-WF-9[PM-WF-9: Composite Wait States & Short-Circuit Failure Handling]_

_See Requirement link:../../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../../Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

Workflow definitions (the default `*.pmwf` units compiled into the binary under `classpath:/workflows/`, and the project-owned copies of the phase and sub-workflow units in `.marshall/config/*.pmwf`, xref:04-ast-node-model.adoc#project-owned-units[Project-Owned Workflow Units & Compiled Invariants]) conform to the following ISO/IEC 14977 Extended Backus-Naur Form (EBNF) grammar. The DSL is line-oriented; comments start with `#` and run to the end of the line.

[source,ebnf]
----
workflow_file        = workflow_header ,
                       ( subworkflow_decl | [ scope_decl ] ) ,
                       start_decl ,
                       { migrate_decl } ,
                       state_decl , { state_decl } ;

workflow_header      = "workflow" , state_id , "version" , positive_int ,
                       "format" , positive_int ,
                       [ "derived_from" , positive_int ] , EOL ;
                       (* version: the unit's revision; format: the DSL format version, accepted only
                          at the binary's current value (store-schemas.adoc, Format Versioning);
                          derived_from: only in a project-owned copy, the default revision it derives from *)
scope_decl           = "scope" , ( "plan" | "epic" | "workspace" | "entity" ) , EOL ;
subworkflow_decl     = "scope" , "subworkflow" , EOL ,
                       { subworkflow_param } ;
subworkflow_param    = "param" , param_name , ":" , subworkflow_type , EOL ;
subworkflow_type     = enum_type
                     | "int" , [ int_range ] ;
start_decl           = "start" , state_id , EOL ;
migrate_decl         = "migrate" , state_id , "->" , state_id , EOL ;

state_decl           = "state" , state_id , [ terminal_decl ] , EOL ,
                       [ phase_clause ] ,
                       [ skill_clause ] ,
                       [ facts_clause ] ,
                       state_body ;
terminal_decl        = "terminal" , outcome_id , outcome_class ;
outcome_class        = "success" | "skip" | "failure" | "indeterminate" | "unsettled" | "aborted" ;
                       (* the closed OutcomeClass set, lower case *)

phase_clause         = "phase" , ( identifier | "inherit" ) , EOL ;
skill_clause         = "skill" , skill_path , EOL ;
facts_clause         = "facts" , primitive_id , EOL ;

state_body           = (* empty for terminal states *)
                     | auto_clause
                     | job_clause
                     | call_clause
                     | link_clause , { link_clause } ;

auto_clause          = "auto" , primitive_id , EOL ,
                       outcome_transition , { outcome_transition } ;

job_clause           = ( "job" | "composite_job" ) , primitive_id , EOL ,
                       outcome_transition , { outcome_transition } ;

call_clause          = "call" , state_id , [ "(" , [ call_arg_list ] , ")" ] , EOL ,
                       outcome_transition , { outcome_transition } ;
call_arg_list        = call_arg , { "," , call_arg } ;
call_arg             = param_name , "=" , ( enum_value | positive_int_or_zero ) ;

link_clause          = "link" , relation , link_id_pattern ,
                       [ "[" , link_form , "]" ] ,
                       "(" , [ param_list ] , ")" , EOL ,
                       [ guard_clause ] ,
                       link_action ,
                       outcome_transition , { outcome_transition } ;

relation             = "next" | "alt" | "retry" | "fix" | "loop_back"
                     | "submit" | "dispatch" | "wait" | "escalate"
                     | "abort" | "emit" ;

link_form            = "submit" | "wait" | "dispatch" | "escalate" | "noop" ;

link_id_pattern      = action_id , [ ":" , ( entity_placeholder | identifier ) ] ;
entity_placeholder   = "<" , identifier , ">" ;

param_list           = param_decl , { "," , param_decl } ;
param_decl           = param_name , ":" , type_spec , [ "?" ] ;

type_spec            = scalar_type
                     | "list" , "<" , scalar_type , ">" ;
scalar_type          = "text" , [ int_range ]
                     | "int" , [ int_range ]
                     | enum_type
                     | schema_ref ;
enum_type            = "enum" , "[" , enum_value , { "|" , enum_value } , "]" ;
schema_ref           = "schema" , "[" , schema_name , "]" ;
                       (* named parameter schema, hypermedia-format.adoc, Named Parameter Schemas *)
schema_name          = lowercase_alpha , { lowercase_alpha | digit | "-" } ;   (* identifiers.adoc, named parameter schema *)

int_range            = "[" , positive_int_or_zero , ".." , positive_int , "]" ;
                       (* the same bracket form as the hypermedia `free` column, e.g. text[1..500] *)

guard_clause         = "guard" , guard_expr , EOL ,
                       [ "depends_on_config" , "[" , config_key , { "," , config_key } , "]" , EOL ] ;
guard_expr           = guard_term , { "or" , guard_term } ;
guard_term           = guard_factor , { "and" , guard_factor } ;
guard_factor         = [ "not" ] , ( guard_atom | "(" , guard_expr , ")" ) ;
guard_atom           = "in_worktree"
                     | "has_open_findings"
                     | "all_tasks_completed"
                     | "predicate:" , primitive_id ;

link_action          = ( "do" , primitive_id , EOL )
                     | ( "dispatch" , identifier , "role" , role_key , EOL )
                     | ( "escalate" , identifier , EOL ) ;
role_key             = identifier , { "." , identifier } ;
                       (* effort role key, e.g. plan.phase-5-execute.effort.default; the effort level is
                          always resolved from the role (dispatch-and-effort.adoc, Role Resolution) *)

outcome_transition   = outcome_id , "->" , state_id , EOL ,
                       { completes_clause } ;
completes_clause     = "completes" , step_id , "as" , step_completion , EOL ;
step_completion      = "done" | "skipped" | "failed" | "skipped_by_operator" ;
                       (* skipped_by_operator: only on an outcome of class APPROVED of a decision (Rule 9) *)
step_id              = step_segment , ":" , step_segment ;   (* identifiers.adoc, step_id *)
step_segment         = lowercase_alpha , { lowercase_alpha | digit | "-" } ;
config_key           = identifier , { "." , identifier } ;   (* an enum or boolean configuration key *)

state_id             = identifier , { "." , identifier } ;
primitive_id         = identifier , "." , identifier ;
skill_path           = "pm/" , identifier , { "/" , identifier } ;  (* maps to the URI "skill://" , skill_path , "/SKILL.md" *)
outcome_id           = identifier ;
action_id            = identifier ;
identifier           = lowercase_alpha , { lowercase_alpha | digit | "_" | "-" } ;
param_name           = lowercase_alpha , { lowercase_alpha | digit | "_" } ;   (* identifiers.adoc, free parameter name *)
enum_value           = letter , { letter | digit | "_" | "-" } ;
positive_int         = nonzero_digit , { digit } ;
positive_int_or_zero = "0" | positive_int ;
letter               = lowercase_alpha | uppercase_alpha ;
lowercase_alpha      = ? ASCII "a".."z" ? ;
uppercase_alpha      = ? ASCII "A".."Z" ? ;
digit                = "0" | nonzero_digit ;
nonzero_digit        = ? ASCII "1".."9" ? ;
any_char_except_nl   = ? any Unicode scalar value except "\n" ? ;
EOL                  = [ "#" , { any_char_except_nl } ] , "\n" ;
----

Identifiers (state, primitive, action, parameter, and outcome names) are lowercase; their regex forms and length bounds (32 characters per identifier, 64 per dotted `state_id`) are registered in the link:../identifiers/01-general-rules-and-registry.adoc#id-state-id[Identifier Registry], which the static verification rules enforce. Parameter names (`param_name`: link parameters, sub-workflow `param` declarations, and `call` arguments) follow the registry's link:../identifiers/01-general-rules-and-registry.adoc#id-param-name[free parameter name] grammar and never contain `-`, because they appear verbatim as keys of `pm_do` `args` and in the hypermedia `free` column. Ranges use the bracket form of the wire (`text[1..500]`, `int[0..100]`), so a declared parameter reads the same in DSL source and in the rendered `free` column. Enum values are a separate token (`enum_value`) that also admits upper case, so closed domain vocabularies such as `enum[FIX|SUPPRESS|ACCEPT]` are expressible verbatim. Lists use the single syntax `list<…>` in both the DSL and the hypermedia `free` column (link:../hypermedia-format.adoc[Hypermedia Format Specification]); there is no free-form object type and no boolean type. The only object-valued type is the named schema reference `schema[<schema_name>]` (also as `list<schema[<schema_name>]>`), whose value the server validates against the closed JSON Schema registered under that name (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]); a name that is not registered fails validation (Rule 1 in xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules (Build Time & Every Unit Load)]). Sub-workflow `param` declarations never use it.

`param` declarations are permitted only in the header of a `scope subworkflow` file. They declare the complete closed parameter schema that every `call` site must bind (Rule 6 in xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules (Build Time & Every Unit Load)]); sub-workflow parameters are restricted to `enum[…]` and `int` because they are bound from literal values at the call site, never from model input.

[#dsl-reserved-keywords]
* *Reserved keywords*: `workflow`, `version`, `format`, `derived_from`, `scope`, `param`, `start`, `migrate`, `state`, `terminal`, `phase`, `inherit`, `skill`, `facts`, `auto`, `job`, `composite_job`, `call`, `link`, `guard`, `depends_on_config`, `do`, `dispatch`, `role`, `escalate`, `completes`, `as`, `and`, `or`, `not`, `in_worktree`, `has_open_findings`, `all_tasks_completed`, `predicate`, `text`, `int`, `enum`, `schema`, and `list` are reserved. None of them may be used as an outcome name, a parameter name, a decision kind, a dispatch entity kind, or a segment of a state, primitive, role, or configuration key identifier; the parser rejects such a use with the source file and line. Two positional vocabularies are not reserved, because they occur only where the grammar expects them: the relation and form values (`next` .. `emit`, `noop`), which deliberately double as action names (`link escalate escalate [escalate]`, `link retry retry [noop]`; `dispatch` and `escalate` are reserved as link-action keywords but stay admitted in the relation, form, and action-name positions), and the scope, outcome class, and step completion values (`plan`, `epic`, `workspace`, `entity`, `subworkflow`, `success` .. `aborted`, `done`, `skipped`, `failed`, `skipped_by_operator`), which are also ordinary identifier segments (`plan.allocate-remediation-tasks`).
* *Link relations and forms*: `relation` and `link_form` are the closed enumerations `LinkRelation` and `LinkForm` (xref:04-ast-node-model.adoc#_ast_node_model[AST Node Model]), taken from the link:../hypermedia-format/02-link-grammar.adoc#_closed_link_relations_rel[Hypermedia Format Specification, Closed Link Relations] table. Every relation admits a fixed set of forms and has a default form, which applies when a `link` clause omits `[form]`. Their compatibility, and the fit of the form to the parameter list and the link action, is Rule 12 (xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules (Build Time & Every Unit Load)]).
* *Dispatch*: A dispatch link action is written only as `dispatch <entity_kind> role <role_key>`. The DSL never names an effort level: the level is always resolved from the role at dispatch time (link:../dispatch-and-effort/03-escalation-roles-readers.adoc#_role_registry_lookup_hierarchy[Dispatch & Effort Specification, Role Registry & Lookup Hierarchy]), so a configuration change of the role reaches every dispatch without a workflow version.
* *`phase inherit`*: A state that declares `phase inherit` takes the phase value of the calling state: the `callerPhase` of the top `CallFrame` (xref:06-reusable-sub-workflows.adoc#_call_stack_execution_persistence_semantics[Call-Stack Execution & Persistence Semantics]), which is itself the resolved phase value of the caller state, so a nested call inherits transitively down to the first state with a concrete phase. `inherit` is admitted only in a `scope subworkflow` unit (Rule 6); a sub-workflow state never changes `status.phase`.
* *Terminal declarations*: Every terminal state declares `terminal <outcome_id> <outcome_class>`: the outcome it reports (for a sub-workflow, the outcome returned to the caller) and its `OutcomeClass` (xref:05-primitives.adoc#primitive-outcome-classes[Outcome Classes & Step Records]), for example `state git.done-clean terminal clean skip`, `state git.done-aborted terminal aborted aborted`, or `state plan.aborted terminal aborted failure`.
* *Abort model*: A plan-scope or epic-scope unit has exactly one abort terminal state, `plan.aborted` or `epic.aborted` (phase value `aborted`, class `failure`), reachable from every phase; there are no phase-specific abort terminals. A model-followable `abort` link inside a sub-workflow or a phase flow only leaves that flow: it ends in a terminal state of outcome `aborted` and class `aborted`, which returns the outcome to the caller, and the caller routes it back to a decision state or to an escalation. Ending the whole plan or epic is operator-authorizing: a routine `abort` answer is the link `abort` (rel `escalate`, form `escalate`, action `escalate abort-plan`, or `escalate abort-epic` in the epic unit), which raises the `blocked` condition (xref:04-ast-node-model.adoc#condition-overlays[Condition Overlays (Engine-Owned)]) with that decision kind when no elicitation is available (xref:02-units-jobs-decisions.adoc#decision-registry[Decision Registry & Typed Escalation Outcomes]). Only an operator decision outcome of class `ABORTED` or `DENIED` enters `plan.aborted` or `epic.aborted`.
* *Step completion (`completes`)*: A transition that settles a finalize step names it with one `completes <step_id> as done|skipped|failed|skipped_by_operator` clause per settled step, on the lines following the transition. The engine writes the step record (`mcp/status.json` `steps`, link:../store-schemas.adoc[Store Schemas Specification]) in the transaction of that transition; Rule 9 (xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules (Build Time & Every Unit Load)]) checks that every step is completed exactly once on every path and never as `done` on a failing, denied, or aborted path. `skipped_by_operator` is admitted only on an `APPROVED` decision outcome: the step is settled by the operator's decision, whose record the step record references (the grant or acknowledgement, `decision_id`), and it satisfies Phase-Exit Completeness (link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#_re_entry_head_at_completion_verdict_currency_rules[Phase Workflows Specification, Verdict Currency Rules]).
* *Configuration-dependent guards*: A `guard` clause may declare `depends_on_config [key, …]`, the enum or boolean keys of the effective configuration (in the effective-key form `<file_stem>.<dotted path>`, for example `project.review.currency` or `derived.push_remote`, link:../store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]) whose values the guard reads. Rule 3 checks reachability for every combination of the declared keys' values (xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules (Build Time & Every Unit Load)]).
