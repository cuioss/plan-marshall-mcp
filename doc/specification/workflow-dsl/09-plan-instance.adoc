[#plan-instance]
== Plan Instance (`instance/plan.v<N>.pmwf` per Plan)
_See Requirement link:../../Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-41[PM-WATCH-STORE-41]_

_See Requirement link:../../Requirements.adoc#PM-EXT-7[PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades]_

Every plan executes its own *plan instance*: a real DSL unit (`scope plan`, one file per version, `instance/plan.v<N>.pmwf`, `id` `plan`) that the server composes from the templates (the merged plan workflow of the compiled defaults or of the project-owned `.marshall/config/*.pmwf`, xref:04-ast-node-model.adoc#project-owned-units[Project-Owned Workflow Units & Compiled Invariants]), the sub-units it calls (`git.commit_and_push` and the `remediation.*` units, xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units]), the composition rules (<<composition-rules>>), and the plan's facts. Facts stay where they are owned and are never copied into the instance: configuration in its stores, waivers in the plan's waiver record, plan facts (lane, posture, deliverables, footprint, tasks) in the plan stores. The instance carries their *effect* with provenance, which makes the process in force visible per plan:

* the lane's route: the states of the lanes and sources the plan cannot take are absent;
* the pruned template elements (steps, states, links, and policy actions), each with its prune reason and source fact in the header;
* the policy calls with their effective bound arguments; the header names each argument's source (the template's call argument, a composition rule, or the `raise` waiver id);
* the gates marked waived, with the waiver id;
* the header with the digests of every input (template files, sub-units, composition rule file, effective configuration, plan facts).

The instance replaces the former execution manifest (the step list is the instance: `finalize.next-step` selects the next unsettled step of the version in force) and the former configuration snapshot (its header). Its storage, header schema, and composition log are specified in link:../store-schemas/14-plan-instance-waivers-questions.adoc#plan-instance[Store Schemas Specification, Plan Instance].

=== Versions & Composition Events
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-21[PM-WATCH-DSL-21]_

The instance is immutable and versioned; each version has exactly one composition event from the closed enum: `start` (version 1, composed in the transaction that creates the plan, `start.create-scope` of the `create` link of `bootstrap-plan`: init and refine routes, both lanes open, the posture prunes), `outline` (lane known, the other lane pruned), `plan` (steps and tasks known; provider and footprint prunes; budgets bound), `config_adopted` (an adopted configuration or template change, `adopt` of the `config_drift` condition), `waiver` (a `met` waiver, a `raise`, or an `unwaive`), `fallback` (the post-run-only form of the `returned` and `handed_back` routes), `empty_harvest` (post-run-only), and `deliverable_removed`. A loop-back to the outline re-runs `outline` and `plan`.

1. *When a version is in force*: A version composed by a server event (`outline`, `plan`, `fallback`, `empty_harvest`, `deliverable_removed`) is in force for the rest of its composing chain, from the transition that enters its target state on, so the states that chain on (for example `finalize.next-step` after `plan.return` or `finalize.hand-back`) already select from it. A version composed by an operator or configuration event (`config_adopted`, `waiver`) is in force from the next transition. `instance_version` of `mcp/status.json` names the version in force; a version never takes effect mid-state.
2. *Position rule*: A version is valid only if it contains the scope's current state and every state of its `call_stack`. State ids are stable across versions, so the current position maps onto the new version unchanged. A server event (`outline`, `plan`, `fallback`, `empty_harvest`, `deliverable_removed`) is composed in the transaction that enters its target state and always contains it; an operator-triggered event whose version fails the rule is refused (a configuration change is then kept, a waiver verb refused with `position_not_contained`).
3. *Verified per version*: Every version passes Rules 1–12 (xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules]) and every compiled invariant before it is written; a version that fails is never written.
4. *History*: Completed firings, step records, and the audit trail always refer to the version in force when they happened; history is never rewritten, and a counter (policy budgets, the loop-back budget) is never reset by a re-composition.
5. *Templates reach a running plan only through adoption*: A changed template or composition rule file raises `config_drift` at the next phase handshake; only `adopt` composes it into the plan (event `config_adopted`).

[#instance-header-grammar]
=== Instance Header Grammar

An instance version is a `.pmwf` file of the workflow grammar (xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Formal EBNF Grammar]) with one additional line after the `workflow` header, which only the server writes:

[source,ebnf]
----
instance_decl        = "instance" , instance_header , EOL ;
instance_header      = ? one line of canonical JSON, valid against the plan instance
                         header schema (store-schemas/14-plan-instance-waivers-questions.adoc,
                         Plan Instance) ? ;
----

The `workflow` header of an instance is `workflow plan version <N> format <f>`, where `<N>` is the plan's `instance_version` (the instance header's `version`), which the file name `instance/plan.v<N>.pmwf` repeats; the unit id `plan` never refers to the Phase 4 part file `plan.pmwf`. The body is the composed state list; it never contains an element that no template declares, and every call site carries the effective values it binds. Pruned elements are absent from the body and listed in the header (`pruned[]`), so the verification rules and invariants run over exactly what the plan executes. A project unit that contains an `instance` line fails validation.

[source,text]
----
workflow plan version 3 format 1
instance {"format_version":1,"plan_id":"header-parser","version":3,"event":"plan", …}
scope plan
start init.classify
…
state finalize.remediate-ci
  phase finalize
  call remediation.ci-failure (retry_budget=2, fix_budget=4, waiver_wait_seconds=0, actions=[retry,fix,loop_back])
    …
----

In the example the header records `fix_budget=4` with the source of a `raise` waiver (`fix_budget:ci-failure`), while the template binds `3`.

[#composition-rules]
=== Composition Rules

The land restriction, the local-only prunes, the merge-policy prune, and every former manifest prune predicate are *data*: one declarative composition rule file, shipped with the binary and versioned like the templates, whose rules map a plan fact or an effective configuration value to prunes (element, id, prune reason) and policy bindings (a call site and the argument it fixes). The rule shape and the shipped rules are specified in link:../store-schemas/14-plan-instance-waivers-questions.adoc#composition-rules[Store Schemas Specification, Composition Rules]; the DSL-relevant effects are:

* *`land` lane*: every policy call is bound with `actions=[retry]`, so `decide` offers `retry` and `step_out` only (xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[bound-parameter guards]); task allocation, `loop_back`, and the in-branch fix links are pruned with reason `land_lane`; exhaustion ends in `finalize.hand-back`.
* *No push remote*: `push`, `create-pr`, `ci-verify`, `automatic-review`, and `analysis-roundtrip` are pruned with reason `local_only`; `pre-push-quality-gate` and `pre-submission-self-review` stay; `finalize.merge-gate` routes `local_only` to the local form of `finalize.hand-back`, and the plan ends `handed_back`.
* *Merge policy off* (the operator's `merge.auto_merge: false`, `local-config.json`): the merge execution (`finalize.merge-dispatch`, `finalize.merge-queue-wait`, `finalize.merge-queue-exit`) is pruned with reason `auto_merge_off`; the gate, lease, sync, evidence wait, and barrier stay, and `finalize.merge-barrier`, reading that the instance prunes the merge execution, settles `pass_hand_back` instead of `pass`, completes `default:branch-cleanup` as `done`, and enters the ready form of `finalize.hand-back` (the pull request marked ready for review, never a draft), so the plan ends `handed_back` with `merge_outcome: awaiting_human_merge`. The policy never prunes a gate or a barrier predicate.
* *Posture, providers, footprint, change type, recipe*: steps pruned with the reasons `posture` (at event `start`), `provider_unconfigured`, `footprint_disjoint`, `change_type_exempt`, `recipe_override`; floor immunity protects the mandatory steps (`INV-FIN-1`).
* *Post-run-only forms*: `plan.return`, `finalize.hand-back`, and `outline.empty-harvest` compose a version in which every step below order `900` is pruned with the reason `returned`, `handed_back`, or `empty_harvest`, so `finalize.next-step` runs the post-run band and `finalize.archive-plan` without a special mode.

A rule never adds an element, never raises a budget, and never names a gate; the compiled invariants are checked on its result. The templates are the project-owned units; team overrides of the composition rules are deferred (link:../../later-improvements.adoc[Later Improvements, L-5]); until then the shipped rule file applies.

=== Display

The diagram generator renders the instance, not the template: `pm://plan/{plan_id}/diagram` shows the version in force with the active state, the pruned elements with their reason, and the waived gates with their waiver id; `pm://plan/{plan_id}/instance[/{version}]` returns the DSL text with its header; `pm-operator status` names the version and its last composition event (xref:07-loop-back-diagrams-verification.adoc#_automated_mermaid_asciidoc_table_and_ascii_diagram_generation[Diagram Generation]). Version 1, composed when the plan is created, is also the preview of the plan's process (for example of its posture).
