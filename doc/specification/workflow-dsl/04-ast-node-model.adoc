The parser produces an immutable tree of Java 25 `record` and `sealed interface` nodes in `de.cuioss.pm.core.workflow.ast`:

[source,java]
----
package de.cuioss.pm.core.workflow.ast;

import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.Set;

import de.cuioss.pm.core.workflow.spi.OutcomeClass;

public record SourceLocation(String resourceName, int line, int column) {}

public enum WorkflowScope { PLAN, EPIC, WORKSPACE, ENTITY, SUBWORKFLOW }

/** Closed link relations (hypermedia-format.adoc, Closed Link Relations): allowed forms and the default form. */
public enum LinkRelation {
    NEXT(Set.of(LinkForm.NOOP, LinkForm.SUBMIT), LinkForm.NOOP),
    ALT(Set.of(LinkForm.NOOP, LinkForm.SUBMIT), LinkForm.NOOP),
    RETRY(Set.of(LinkForm.NOOP, LinkForm.SUBMIT), LinkForm.NOOP),
    FIX(Set.of(LinkForm.NOOP, LinkForm.SUBMIT), LinkForm.NOOP),
    LOOP_BACK(Set.of(LinkForm.NOOP, LinkForm.SUBMIT), LinkForm.SUBMIT),
    SUBMIT(Set.of(LinkForm.SUBMIT), LinkForm.SUBMIT),
    ESCALATE(Set.of(LinkForm.SUBMIT), LinkForm.SUBMIT),     // request_waiver only: files a request, never awaits an answer
    CONSULT(Set.of(LinkForm.SUBMIT), LinkForm.SUBMIT),      // consult:<role>, rendered from a consult clause, never declared
    ABORT(Set.of(LinkForm.SUBMIT), LinkForm.SUBMIT);        // the implicit step_out of a session-driven sub-workflow only

    private final Set<LinkForm> allowedForms;
    private final LinkForm defaultForm;
    LinkRelation(Set<LinkForm> allowedForms, LinkForm defaultForm) {
        this.allowedForms = allowedForms;
        this.defaultForm = defaultForm;
    }
    public Set<LinkForm> allowedForms() { return allowedForms; }
    /** Form of a `link` clause that omits `[form]`. */
    public LinkForm defaultForm() { return defaultForm; }
}

/** Closed link forms (hypermedia-format.adoc, Normative Link Forms); there is no wait and no escalation form. */
public enum LinkForm { SUBMIT, NOOP }

public record StateMigration(String oldStateId, String newStateId, SourceLocation location) {}

public sealed interface ParamType
    permits ParamType.Text, ParamType.Int, ParamType.EnumOf, ParamType.SchemaRef, ParamType.ListOf {

    record Text(Optional<Integer> minLength, Optional<Integer> maxLength) implements ParamType {}
    record Int(Optional<Integer> min, Optional<Integer> max) implements ParamType {}
    record EnumOf(List<String> values) implements ParamType {}
    /** `schema[<schemaName>]`: a JSON object validated against the named closed schema (hypermedia-format.adoc, Named Parameter Schemas). */
    record SchemaRef(String schemaName) implements ParamType {}
    record ListOf(ParamType elementType) implements ParamType {}   // elementType is never a ListOf
}

/** Free parameter of a link (`param_decl`). */
public record ParamSpec(String name, ParamType type, boolean optional, SourceLocation location) {}

/** Sub-workflow parameter declared in the header (`param <name>: <type>`); always required.
 *  Its type is EnumOf, Int, or ListOf(EnumOf). */
public record ParamDecl(String name, ParamType type, SourceLocation location) {}

public record WorkflowDefinition(
    String id,
    int version,
    WorkflowScope scope,
    List<ParamDecl> params,          // non-empty only when scope == SUBWORKFLOW
    Optional<String> resultSchema,   // SUBWORKFLOW only: named schema of the result record returned with `done`
    Optional<InstanceHeader> instance, // plan instance only: the parsed instance header line (09-plan-instance.adoc)
    Map<String, Integer> partVersions, // merged plan unit only (id "plan", version = sum of the part versions); empty otherwise
    int formatVersion,                 // DSL format of every file of the unit (all files declare the same)
    UnitOrigin origin,                 // DEFAULT (compiled) or PROJECT (.marshall/config/)
    Map<String, Integer> derivedFrom,  // PROJECT only: default revision per file the copy derives from
    String startState,
    List<StateMigration> migrations,
    Map<String, StateNode> states,
    SourceLocation location
) {}

/** Parsed `instance` header line of a plan instance version; the JSON is validated against the
 *  instance header schema (store-schemas.adoc, Plan Instance). */
public record InstanceHeader(String planId, int version, String event, Map<String, String> inputDigests, String json) {}

/** `terminal <outcome_id> <outcome_class>`: the outcome a terminal state reports and its class. */
public record TerminalOutcome(String id, OutcomeClass outcomeClass) {}

public record StateNode(
    String id,
    String phase,                    // concrete phase short name, or "inherit" (sub-workflow units only)
    Optional<TerminalOutcome> terminalOutcome, // present iff the state is terminal
    Optional<String> skillPath,
    Optional<String> factsPrimitiveId,
    StateBehavior behavior,
    SourceLocation location
) {}

public sealed interface StateBehavior
    permits StateBehavior.InteractiveLinks,
            StateBehavior.AutoStep,
            StateBehavior.JobStep,
            StateBehavior.ModelJob,
            StateBehavior.SubWorkflowCall,
            StateBehavior.QuestionWait,
            StateBehavior.TerminalState {

    record InteractiveLinks(List<LinkSpec> links) implements StateBehavior {}
    record AutoStep(String primitiveId, List<OutcomeTransition> transitions) implements StateBehavior {}
    record JobStep(String primitiveId, boolean composite, List<OutcomeTransition> transitions) implements StateBehavior {}
    /** `job llm <entity_kind> role <role_name> [each <primitive_id>]` with its `consult role` clauses: a task of the
     *  named role for one entity of the kind, or with `each` (fanOutPrimitiveId) one task per element of the list that
     *  primitive returns, each run through worker-task; harness, model, effort, and form come only from the role's
     *  artifact; the transitions route the outcomes of the kind's return-evaluation primitive and the reserved `lost`. */
    record ModelJob(String entityKind, String roleName, Optional<String> fanOutPrimitiveId,
                    List<String> consultRoles, List<OutcomeTransition> transitions) implements StateBehavior {}
    record SubWorkflowCall(
        String subWorkflowId,
        Map<String, String> paramBindings,
        List<OutcomeTransition> transitions
    ) implements StateBehavior {}
    /** `question <class>`: rests on the scope's open question record; catalogue kind awaiting_user. */
    record QuestionWait(
        String questionClass,
        List<OutcomeTransition> transitions,   // the class's closed resolution outcomes
        List<LinkSpec> links                   // further declared links, session-driven units only (Rule 10)
    ) implements StateBehavior {}
    record TerminalState() implements StateBehavior {}
}

public record CallFrame(
    String callerWorkflowId,
    String callerStateId,
    String callerPhase,
    String subWorkflowId,
    Map<String, String> boundArgs,
    String pushedAt
) {}

public record LinkSpec(
    LinkRelation rel,
    String idPattern,
    LinkForm form,
    List<ParamSpec> freeParams,
    Optional<GuardSpec> guard,
    LinkAction action,
    List<OutcomeTransition> transitions,
    SourceLocation location
) {}

/** `do <primitive_id>`: the only link action; model work is a `job llm` task state, never a link action. */
public sealed interface LinkAction permits LinkAction.ExecutePrimitive {

    record ExecutePrimitive(String primitiveId) implements LinkAction {}
}

public sealed interface GuardExpr
    permits GuardExpr.InWorktree,
            GuardExpr.HasOpenFindings,
            GuardExpr.AllTasksCompleted,
            GuardExpr.CustomPredicate,
            GuardExpr.BoundParamHas,
            GuardExpr.And,
            GuardExpr.Or,
            GuardExpr.Not {

    record InWorktree() implements GuardExpr {}
    record HasOpenFindings() implements GuardExpr {}
    record AllTasksCompleted() implements GuardExpr {}
    record CustomPredicate(String primitiveId) implements GuardExpr {}
    /** `param:<name> has <value>`: the current call frame's bound enum equals, or bound list contains, the value. */
    record BoundParamHas(String paramName, String value) implements GuardExpr {}
    record And(GuardExpr left, GuardExpr right) implements GuardExpr {}
    record Or(GuardExpr left, GuardExpr right) implements GuardExpr {}
    record Not(GuardExpr operand) implements GuardExpr {}
}

/** Result of evaluating a guard; a transition fires only on HELD. */
public sealed interface GuardResult
    permits GuardResult.Held, GuardResult.NotHeld, GuardResult.CouldNotEvaluate {

    record Held() implements GuardResult {}
    record NotHeld() implements GuardResult {}
    record CouldNotEvaluate(String reason) implements GuardResult {}
}

/** `guard <expr>` with the enum or boolean configuration keys it reads (`depends_on_config`). */
public record GuardSpec(GuardExpr expr, List<String> dependsOnConfig) {}

public enum StepCompletionStatus { DONE, SKIPPED, FAILED, WAIVED }

/** `completes <step_id> as <status>` clause of a transition. */
public record StepCompletion(String stepId, StepCompletionStatus status, SourceLocation location) {}

/** `guard [not] result.<field>` on a call-site transition: a field of the callee's result record
 *  (holds when a boolean field is true or an optional field is present). */
public record ResultGuard(String field, boolean negated) {}

public record OutcomeTransition(
    String outcomeName,
    String targetStateId,
    Optional<ResultGuard> resultGuard,
    List<StepCompletion> completions,
    SourceLocation location
) {}

[#guard-results]
==== Three-Valued Guard Results
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-2[PM-WATCH-DSL-2]_

Every guard evaluates to the sealed `GuardResult`: `HELD`, `NOT_HELD`, or `COULD_NOT_EVALUATE(reason)` (a built-in guard whose input cannot be read, a `predicate:` primitive that fails or times out, an unreadable configuration key). A link is offered, and its transition fires, only on `HELD`; `NOT_HELD` omits the link (`PM-WF-3`). `COULD_NOT_EVALUATE` is never folded into either: the engine raises the `guard_indeterminate` condition on the current state (<<condition-overlays>>), naming the guard, the link, and the reason in `facts`, and the undecided link is neither offered nor refused silently. `And`, `Or`, and `Not` propagate `COULD_NOT_EVALUATE` unless the other operand decides the result (`NOT_HELD` and anything is `NOT_HELD`, `HELD` or anything is `HELD`). A `BoundParamHas` guard and a result guard read values bound in the same transaction and always decide.

[#condition-overlays]
=== Condition Overlays (Engine-Owned)
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-14[PM-WATCH-DSL-14]_

A condition is an engine-owned overlay on the scope's current state, not a state: `integrity_breach`, `footprint_violation`, `job_incomplete`, `config_drift`, `guard_indeterminate`, and `precondition_unmet` (link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-conditions[State Catalogue, Conditions]). The engine raises it where the condition arises (a digest check of a plan or epic store or of an enrolment file, the footprint check of `git.stage-and-commit` (xref:06-reusable-sub-workflows.adoc#_six_stage_execution_contract_of_git_commit_and_push[Six-Stage Execution Contract of `git.commit_and_push`], Stage 4) or of a task `submit` (xref:05-primitives.adoc#independent-transition-validation[Independent Server-Side Transition & Parameter Validation (`PM-WF-6`)] item 6), a planning transition guard, a task attempt that ended without its required submission (xref:02-units-jobs-decisions.adoc#model-job-states[Task States]), an indeterminate derived fact, a phase handshake, a missing credential, a guard that could not be evaluated (<<guard-results>>)) and records it in `mcp/status.json` as `pending_condition` (`kind` from the closed `ConditionKind` enumeration, `facts`, `raised_at`, `remedy_attempts`, link:../store-schemas.adoc[Store Schemas Specification]). `state`, `phase`, and `call_stack` are not changed, so a condition raised inside a sub-workflow leaves the scope inside that sub-workflow. No condition waits for an operator decision.

* *Rendering*: While a condition is set, the representation keeps `state` as the current state id, carries the field `condition` naming the kind (link:../hypermedia-format/01-representation-and-link-forms.adoc#canonical-top-level-fields[Hypermedia Format Specification]) and the condition's `facts`. In a plan or an epic the self-remedy is server logic, so the view offers no link for it, and every task entity of the scope keeps its own links. In a session-driven unit (xref:02-units-jobs-decisions.adoc#session-driven-units[Session-Driven Units]) the condition offers only its self-remedy link (`retry`, which re-runs the check or re-evaluates the guard), and every other declared or implicit link of the state is answered with `link_not_available`.
* *Integrity pause*: `integrity_breach {kind: store_tampered | enrolment_tampered, store, recorded_digest, current_digest}` offers no link at all, and every `pm_do` of the paused scope is rejected with `integrity_paused`; a tampered plan or epic store pauses that scope, a tampered enrolment file every running plan of the project. `facts.operator_command` names the two operator resolutions, `accept-edit` (the engine re-verifies the digests before it clears the condition) and `abort` (the engine-owned transition into `plan.aborted` or `epic.aborted`). The pause has no bound and no fallback (xref:02-units-jobs-decisions.adoc#waivers-and-integrity[Waivers, Waiver Requests & the Integrity Pause]).
* *Bounded self-remedy*: Every other condition is bounded by the compiled self-remedy budget of `3` attempts per condition instance (`remedy_attempts`); the operator may fix the cause at any time. In a plan or an epic the server runs the self-remedy itself: it retries where a retry can clear the condition (`guard_indeterminate` re-evaluates every guard of the state, `precondition_unmet` re-checks its precondition after the compiled backoff, `job_incomplete` re-offers the task, xref:02-units-jobs-decisions.adoc#model-job-states[Task States]), and where clearing it needs work, it creates a task of the role whose work raised it (`footprint_violation`: a task of the plan's writer role that reverts the offending changes, after which the check runs again); `config_drift` is resolved by the server: it adopts when the re-composed instance version verifies and contains the scope's position, and keeps the version in force otherwise (item 4 of <<project-owned-units>>), recording the choice in the audit log and the composition log (link:../store-schemas/14-plan-instance-waivers-questions.adoc#plan-instance[Store Schemas Specification, Composition Log]). A self-remedy that succeeds clears the condition and re-renders the current state. When the budget is spent, the engine takes the phase's fallback route with the condition recorded as the gap (`cause: condition`, with the condition kind): at plan scope it unwinds every call frame in one transaction with the server step-out `stepped_out {by: server, cause: condition}` and enters the phase's fallback state (`plan.return` or `finalize.hand-back`) directly; no caller's `stepped_out` transition is taken, so a unit's own recovery state never catches it; `handed_back` degrades to a local branch when the fallback itself needs what is missing (a push credential). After the merge there is no fallback: the condition's step is re-fired or owed (xref:03-reference-excerpt.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Reference Workflow Excerpt], shared failure state). The epic and workspace scopes have no fallback end: an epic condition is retried by the server at the compiled backoff until its cause clears, shown with its `facts.operator_command` in the epic's view, `pm-operator status`, and the web app, and ends by the operator removing the cause or by `pm-operator abort epic`; a bootstrap entry keeps its `retry` link and ends through its own exits or the pending-record sweep; workspace setup failures are routed by `setup.needs-repair` (link:../domain-extensions/04-setup-state-machine.adoc[Domain Extensions Specification, Project Setup State Machine]).
* *Not Declared in DSL Units*: Conditions are never declared in a `*.pmwf` unit and are never a transition target. A DSL transition whose target names a condition or one of the reserved state ids `<phase>.blocked`, `<phase>.footprint-violation`, and `<phase>.config-drift` fails validation (Rule 3).

[#static-verification-rules]
=== Static AST Verification Rules (Build Time & Every Unit Load)
_See Requirement link:../../Requirements.adoc#PM-WF-5[PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint]_

_See Requirement link:../../Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../../Requirements.adoc#PM-MIG-4[PM-MIG-4: Stage Exit Criteria & Lifecycle Gate]_

_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-1[PM-WATCH-DSL-1], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-3[PM-WATCH-DSL-3], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-4[PM-WATCH-DSL-4], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-5[PM-WATCH-DSL-5], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-8[PM-WATCH-DSL-8], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-9[PM-WATCH-DSL-9], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-11[PM-WATCH-DSL-11], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-15[PM-WATCH-DSL-15], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-16[PM-WATCH-DSL-16]_

`WorkflowValidator` verifies every `WorkflowDefinition` in JUnit build tests (the default units), on every load of a project's units (<<project-owned-units>>), and on every composed plan instance version (xref:09-plan-instance.adoc#plan-instance[Plan Instance]), failing closed if any rule is violated; a project unit and an instance version are additionally checked against the compiled invariants. A `WorkflowDefinition` is always a complete definition unit (xref:02-units-jobs-decisions.adoc#workflow-definition-units[Workflow Definition Units (Multi-File Workflows)]): the merged union of all phase files of the plan workflow, a plan instance, a single-file top-level workflow, or one sub-workflow. Rules 2, 3, 5, 8, 9, and 11 run over that union, never over an individual phase file:

1. *Primitive Binding & Parameter Equivalence*: Every `primitiveId` in `do`, `auto`, `job`, `facts`, and `predicate:` must resolve to a registered `Primitive<P, R>`, every `job llm` entity kind to a registered entity kind with its entity unit and return-evaluation primitive, and every `each` primitive of a `job llm` state to a registered read-only list primitive. Every role name of a `job llm` state and of a `consult role` clause must match the role-name grammar of the link:../identifiers/01-general-rules-and-registry.adoc[Identifier Registry]; whether the role exists is checked at composition (Rule 13), never at unit load, because the role set is operator configuration. For every `LinkSpec`, the declared `freeParams` list must exactly match the name, type, and constraints of the `Record` components annotated as `@FreeParam` on `P`. Every `ParamType.SchemaRef` (`schema[<schema_name>]`, in a link's free parameters or a sub-workflow's `result` declaration) must name a schema registered in the Named Parameter Schemas (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Hypermedia Format Specification]); an unknown schema name fails validation with the source file and line. Every question clause names a registered question class. Every primitive that declares `enqueuesJob()` must declare the outcome `started`, and every `started` transition of such a primitive must target a `job` or `composite_job` state, which binds the returned job id instead of starting a job (xref:02-units-jobs-decisions.adoc#job-state-binding[Job State Entry & Binding (`JobStep`)]); no other outcome of such a primitive may target a job state.
2. *Exhaustive Outcome Coverage*: For every `auto`, `job`, `composite_job`, and `link` action backed by `Primitive<P, R>`, the set of `OutcomeTransition.outcomeName` entries must form an exact 1-to-1 bijection with the enum constants of `R` (`R.getEnumConstants()`). For `job` and `composite_job` states this includes `cancelled`, the outcome of a cancellation by the engine (xref:02-units-jobs-decisions.adoc#implicit-job-links[Implicit Links]); a `job` state's constants are exactly the `PM-EXEC-4` set. The transitions of a `job llm` state form the bijection with the outcomes of the entity kind's return-evaluation primitive, which the task's completion runs, plus the reserved outcome `lost` (no `cancelled` transition; in a fan-out state the evaluation runs at every task's end, and the state takes its outcome over the whole list once every task has ended); `lost` may be left undeclared only in a unit of `scope plan` and in a sub-workflow only plan units call, where the engine routes it to the phase's fallback (xref:02-units-jobs-decisions.adoc#model-job-states[Task States] item 4); the transitions of a question clause form the bijection with the closed resolution outcomes of its class (xref:02-units-jobs-decisions.adoc#question-states[Question States & the Question Deadline]). A missing outcome and an unknown outcome name fail validation with the source file and line number.
3. *Graph Integrity*: State identifiers must be unique across all files of the definition unit. `startState` and every `OutcomeTransition.targetStateId` must exist in the unit's `states` (a cross-file target within the plan workflow is valid; a target inside another unit or inside a sub-workflow is not). Every `StateNode` must be reachable from the unit's `startState`, and reachability is checked for every combination of the values of the configuration keys that the unit's guards declare in `depends_on_config` (every enum value, `true` and `false` for a boolean): a state or outcome transition that no combination reaches fails validation, and one that some combinations do not reach is reported with those combinations. Reachability is graph reachability under those combinations only; it never evaluates the feasibility of a primitive outcome or of a bound call parameter. The abort terminals `plan.aborted` and `epic.aborted` count as reachable from every state (they are entered only by the engine-owned operator transition, and no transition may target them). Every non-terminal `StateNode` must have at least one outgoing transition path to a `terminal` state, where the implicit `step_out` of a link state of a session-driven sub-workflow and the default `lost` route of a task state count as such a path; in a `scope workspace` unit, which declares no terminal state because the workspace scope lives as long as the project's adoption, every state must instead have a path back to the unit's `startState`. Every `skill` clause must resolve to a vocabulary skill in the compiled corpus, and every link identifier pattern must be unique within its state, including the implicit links (`ack`, `consult:<role>`, `answer:<question_id>`, `step_out`). Condition overlays (<<condition-overlays>>) are engine-owned and need no target in `states`: a transition whose target names a condition kind or one of the reserved state ids `<phase>.blocked`, `<phase>.footprint-violation`, and `<phase>.config-drift` fails validation.
4. *Single-Level Leaf Task Constraint (`PM-WF-5`, `PM-WORK-4`)*: No unit a worker acts in (the entity unit of every entity kind a `job llm` state names, `worker-task`, and every sub-workflow such a unit calls) contains a `StateBehavior.ModelJob` state or a link whose transitions enter one. A consultation task offers no `consult` link (consultation depth one), and a `consult role` clause never names a role whose class is `zero_tool` (checked with the role's existence, Rule 13). At runtime a worker's connection is refused every link outside the task entities leased to its generation. Workers are leaves and never start a model, each task of a fan-out state included; a consultation is a task the server creates.
5. *Backwards-Compatible State Migration (`PM-MIG-4`)*: Every state name present in the committed `released-states.txt` baseline must either exist in `states` or appear as `oldStateId` in a `migrate <old> -> <new>` declaration whose target exists in `states`. The rule applies to the default units; an in-flight plan of a project whose unit dropped or renamed a state keeps executing its instance version in force (xref:09-plan-instance.adoc#plan-instance[Plan Instance], position rule).
6. *Sub-Workflow Exit Contract & Parameter Binding (`PM-WF-16`)*: Every `StateBehavior.SubWorkflowCall` (`call <subWorkflowId>`) must reference a registered `WorkflowDefinition` whose `scope == WorkflowScope.SUBWORKFLOW`. The callee's *exit contract* is the set of its declared `terminalOutcome` values plus the control outcome `stepped_out`, which every sub-workflow returns implicitly (xref:01-grammar.adoc#sub-workflow-exits[Sub-Workflow Exit Contract]). Every call site routes each outcome of the contract: exactly once, or twice with the complementary result guards `guard result.<f>` and `guard not result.<f>` over a boolean or optional field `<f>` of the callee's result schema; a result guard on any other transition, or on an outcome other than `done`, fails validation. `stepped_out` targets the phase's fallback state (`plan.return` or `finalize.hand-back`), inside a `scope epic` or `scope workspace` unit or a bootstrap unit (which have no fallback end) a resting state of the calling unit (for example `epic.active`, `setup.commit-changes`, `setup.completed`, `start.choose`, `start-epic.define`), or, inside a sub-workflow, a state of the same unit that continues the unwinding (a server step-out terminal, or in a session-driven sub-workflow a `link` state whose own `step_out` continues it); never a terminal state of class `success` and never a state that continues the flow as if the call had succeeded. The outcome id `stepped_out` is declared only by a terminal of class `stepped_out`, and every other outcome id of a sub-workflow terminal is a domain outcome its callers continue on differently. The `paramBindings` of every `call` site are checked against the target's `params` (`param` declarations): every declared parameter must be bound exactly once, no binding may name an undeclared parameter, and every bound value must match the declared type (membership in the `enum[…]` value set, an integer within the declared `int` range, or a non-empty list of distinct members of a `list<enum[…]>`). `phase inherit` is admitted only in `SUBWORKFLOW` and `ENTITY` units. *Guided step-in*: every resting `link` state of a session-driven `SUBWORKFLOW` unit declares a `skill` clause (the skill section of the one judgment it asks for); a task state takes its skill from its `skill` clause or, where it declares none, from its entity kind.
7. *Acyclic Call-Graph DAG & Bounded Depth (`PM-WF-16`)*: Across all registered `WorkflowDefinition` instances, the static `call` graph must form a strict directed acyclic graph (DAG) with zero cycles and a maximum static call-stack depth $\le 4$.
8. *Gate Artifact Producer Coverage*: For every guard or gating primitive that declares a required artifact (`requiredArtifacts()`, for example `pr_title` or `outline.md`), every path from the unit's `startState` to that guard or state, including recipe and lane shortcuts, must pass a state whose primitive declares the artifact in `producedArtifacts()`. A path without a producer fails validation, so a gate can never refuse for an artifact its lane could not produce.
9. *Step Completion Once per Firing & Failure Outcomes Never Map to Success*: Every outcome constant of every primitive and `composite_job` outcome set declares an `OutcomeClass` (xref:05-primitives.adoc#primitive-outcome-classes[Outcome Classes & Step Records]), and every terminal state declares its class in `terminal <outcome_id> <outcome_class>`; a sub-workflow's terminal class is the class of the matching outcome at its `call` sites, and `stepped_out` has the class `STEPPED_OUT`. A step is completed only by a `completes <step_id> as done|skipped|failed|waived` clause (xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Formal EBNF Grammar for the Workflow DSL]). The rule checks:
** *Once per firing*: A firing of a finalize step opens on entry into the step's beginning state (the state `finalize.next-step` selects for it, the region entry state for steps that share one, such as `finalize.review-cap-check` for the `22..40` wait region, and `finalize.merge-evidence-wait` for the wait-region steps with the cause `input_changed`) while the step has no open firing; a re-entry while it is open continues it. Every path from an opening to the next opening of the same step, to the state of order `70` (`finalize.merge-gate`), or to a terminal state carries exactly one completion of that step; a remediation call on the path belongs to the firing. A path ends early at an `UNSETTLED` outcome (`loop_back`, `fix_requested`, defer) or a `STEPPED_OUT` outcome, which hands the step back without a completion. Entering `plan.aborted`, `plan.return`, or `finalize.hand-back` records every begun step whose firing is still open as `failed`, in the transaction of the entering transition; a path into one of them therefore carries no `completes` clause for such a step. No completion on a path, or two, fails validation.
** *Class admits the completion*: `as done` is admitted only on an outcome of class `SUCCESS`; `as skipped` only on `SUCCESS` or `SKIP`; `as failed` on any class except `UNSETTLED` and `STEPPED_OUT`; `as waived` only on the transition of the outcome `waived` of a `call` to a remediation unit (the step is settled by a consumed waiver, whose id the step record references). A `FAILURE`, `INDETERMINATE`, or `STEPPED_OUT` outcome never completes a step `done`, `skipped`, or `waived`, and a composite primitive whose sub-operations report any `FAILURE` outcome yields a `FAILURE` outcome itself.
10. *Links Only Where a Model Acts (`PM-WF-1`)*: A resting `link` state, and a declared link of a question state, exist only in the session-driven units (xref:02-units-jobs-decisions.adoc#session-driven-units[Session-Driven Units]). A unit of `scope plan` or `scope epic`, and every sub-workflow such a unit calls, consists of `auto`, `job`, `composite_job`, `job llm`, `call`, question, and terminal states, so the server moves the scope and a model acts in it only through the links of its task entities and the answer links of its question records. A violation fails validation with the source file and line.
11. *No Cycle Without an Awaited Event*: Every primitive declares the external event it waits for (`Primitive.awaitedEvent()`, xref:05-primitives.adoc#primitive-spi-contract[`Primitive<P, R>` SPI Contract]).
** *11a (engine-chained cycles)*: A cycle that consists only of engine-chained transitions (the outcomes of `auto` states, the entry of `call` states, and sub-workflow terminal returns, including those of a sub-workflow called on the cycle) fails validation, whatever its primitives declare: `pm_do` chains such transitions inside one transaction, so the cycle would never yield.
** *11b (cycles through a resting state)*: A self-loop or cycle that passes a resting state (a `link`, question, `job`, `composite_job`, or `job llm` state) must contain an awaited event. Link actions count by kind: a `submit`-form link awaits `MODEL_SUBMIT`, and a `noop`-form link counts through its primitive's `awaitedEvent()`; a `job` or `composite_job` state awaits `JOB_SETTLED` (a waiver wait `OPERATOR_WAIVER` or `TIME`); a `job llm` state awaits `TASK_SETTLED` of its task (in a fan-out state of each of its tasks), whose completion runs the return evaluation; a question state awaits `QUESTION_ANSWER` or `TIME`. A cycle all of whose events are `NONE` fails validation: it would re-run without any event that could change its outcome.
12. *Link Relation & Form Compatibility*: For every `LinkSpec`, the form (the declared `[form]`, or `LinkRelation.defaultForm()` when it is omitted) must be one of `rel.allowedForms()` (<<_ast_node_model>>, link:../hypermedia-format/02-link-grammar.adoc#_closed_link_relations_rel[Hypermedia Format Specification, Closed Link Relations]). The form must also fit the link: `submit` declares a non-empty parameter list; `noop` declares none; a link of rel `escalate` is a `submit` link whose primitive files a waiver request and never waits for or applies an operator answer; the rels `consult` and `abort` are never declared in a `link` clause (the engine renders `consult:<role>` from a `consult role` clause and the implicit `step_out`). A violation fails validation with the source file and line.
13. *Every Named Role Exists (composition, `PM-WORK-1`)*: When the runtime composes a plan instance version, an epic workflow, or the project setup workflow of a project, every role named by a `job llm` state or a `consult role` clause of the composed unit and of every unit it calls must be defined by the project's effective role set (link:../model-work/01-roles-and-configuration.adoc#role-composition[Model Work Specification, Composition Check]); a missing or invalid role refuses the composition with `role_undefined`, naming the role and the state, so no state that names it is ever reached; a `consult role` clause that names a `zero_tool` role refuses it the same way. The shipped default role set defines every role the default units name, which `DefaultUnitInvariantTest` verifies at build time.
14. *Every Named Skill Resolves (composition, `PM-SKILL-5`)*: At the same compositions, every skill named by a `skill` clause of the composed unit and of every unit it calls must resolve in the project's skill catalogue: a compiled skill, or an extension skill under `skill://pm/ext/` that is present and accepted at that read (link:../mcp-tools/02-service-and-skill-tools.adoc#skill-extensions[MCP Tools Specification, Skill Extensions]). A skill that does not resolve (absent, or an extension skill that is missing or refused) refuses the composition with `skill_unresolved`, naming the skill and the state, so no state renders a skill the server cannot deliver; the launch-time `prompt_composition_failed` remains only as a defence against a skill that changed after the composition (link:../model-work/04-worker-launch.adoc#job-prompt[Model Work Specification, Launch Prompt]). The default units name only compiled skills, which `DefaultUnitInvariantTest` verifies at build time.

[#project-owned-units]
=== Project-Owned Workflow Units & Compiled Invariants
_See Requirement link:../../Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

_See Requirement link:../../Requirements.adoc#PM-EXT-7[PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades]_

The process a project runs is visible to and owned by its team: the units that define it are files in the repository, reviewed like code. The guarantees of the process stay server-enforced, because every unit and every plan instance composed from it is verified against rules and invariants compiled into the binary, and a unit can only compose compiled primitives and enrolled scripts.

1. *Which Units Are Project-Owned*: Every phase file of the plan workflow (`init.pmwf`, `refine.pmwf`, `outline.pmwf`, `plan.pmwf`, `execute.pmwf`, `land.pmwf`, `finalize.pmwf`) and the sub-workflow units `git-commit-and-push.pmwf` and `remediation-*.pmwf` (the remediation policy units, xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units]; the source units `source-*.pmwf`, the re-planning unit `replan.pmwf`, and the lesson maintenance unit `lessons.pmwf` are `scope subworkflow` too but compiled only) live in the project as `.marshall/config/<file>.pmwf` (git-tracked, owner class *team*, link:../store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]). The binary ships the *default* units (`classpath:/workflows/`); `setup.prepare-workspace` copies them on the project's first run, each copy carrying `derived_from <n>` (the default revision it was copied from) in its header. The workspace unit `project-setup.pmwf` with the lesson maintenance sub-workflow `lessons.pmwf` it calls, the epic unit `epic.pmwf`, the entity units, the task protocol unit `worker-task.pmwf`, and the bootstrap units with their source units `source-*.pmwf` are compiled only and never project-owned; they call the binary's default sub-workflows, never the project's copies, so a failing project unit never blocks the setup workflow that repairs it, the epic ledger, or the start of a plan. The composition rule file is shipped data, not a project unit; team overrides of the composition rules, and of the units that are not project-owned, are deferred (link:../../later-improvements.adoc[Later Improvements, L-5]).
2. *Load & Verification*: Every computation of the effective configuration (the bootstrap's scope creation, every phase handshake, `pm-mcp enter`, `setup.reconcile-config`; cached by the units' digests) parses the project's units, merges the plan workflow unit (xref:02-units-jobs-decisions.adoc#workflow-definition-units[Workflow Definition Units (Multi-File Workflows)]), and verifies it with Rules 1–12 (<<static-verification-rules>>; Rule 5 only for default units; Rules 13 and 14 when an instance or workflow is composed from it), with `FinalizePipelineValidator` over the project's finalize roster (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#_build_time_startup_static_invariant_verification_finalizepipelinevalidator[Phase Workflows Specification]), and with the compiled invariants (item 5). A unit at another DSL `format` is refused with `format_outdated` or `format_newer` naming the file. A missing, unparsable, or violating unit is never replaced by the default unit (no silent fallback): it is a verification finding in the workspace scope naming the file, the line, and the violated rule or invariant, and it refuses the project's plan lifecycle (the bootstrap's scope creation returns to `start.ready` and every phase handshake refuses with `config_invalid`, naming the file and line) until the unit verifies. The verification outcome of every unit is published in `pm://project/config` (`units[]`).
3. *Project Steps Bind to Enrolled Scripts*: A unit never introduces executable code: every primitive it names must be registered in the binary (Rule 1). A project finalize step is a state running the compiled primitive `project.run-step` for its step id; it exists only when three owners agree: the unit contains the step, `workflow.json` `plan.phase-6-finalize.project_steps` declares its descriptor (`order`, `lane`, `project_script_id`), and the operator's enrolment binds the `project_script` with `worker_kind: finalize_step` and `target` equal to the step id (link:../domain-extensions/05-recipes-and-extension-points.adoc#_out_of_process_project_script_jobs_project_script_domain_workers[Domain Extensions Specification, `project_script`]). A disagreement is the verification finding `project_step_unbound`.
4. *Plan Instance*: A plan never executes the project units directly: in the transaction that creates the plan (`start.create-scope`, run by the `create` link of `bootstrap-plan`) the server composes the plan's first instance version from the verified units, the sub-units they call, the composition rules, and the plan's facts, and every later composition event composes a new version (xref:09-plan-instance.adoc#plan-instance[Plan Instance]). A changed project unit raises `config_drift` at the next phase handshake (link:../domain-extensions/06-configuration.adoc#config-snapshot[Domain Extensions Specification, Three-Surface Synchronization]); the server adopts it, composing a new version (event `config_adopted`), only when it verifies and still contains the plan's current state and every state of its `call_stack`, and keeps the version in force otherwise (<<condition-overlays>>).
5. *Compiled Invariants*: The following invariants are compiled into the binary; no configuration key, composition rule, and unit edit can switch one off, and every one of them is checked over the merged project unit on every load and over every composed instance version (`INV-*` identifiers name the invariant in findings). The invariants of the remediation units, `INV-REM-*`, are listed with the units (xref:08-remediation-units.adoc#remediation-invariants[Compiled Invariants of Remediation Units]).

6. *Offered Default Changes*: A new binary never changes a project unit. Its default-unit changes are offered in `setup.offer-new-steps` as a three-way diff from the unit's `derived_from` revision to the current default revision (link:../domain-extensions/06-configuration.adoc#config-upgrades[Domain Extensions Specification, Upgrade Path]); a unit whose `derived_from` is older than the default revision is valid and runs unchanged as long as it verifies.
