=== `pm_build` — Enrolled Build Execution
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-5[PM-WATCH-JOB-5], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-19[PM-WATCH-JOB-19], link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-18[PM-WATCH-TOOL-18]_

Submits or awaits a build job in the plan's worktree (or the primary repository checkout when `plan_id` is `NO_PLAN`; such a plan-less build is workspace-addressed, `PM-ARCH-4`, and writes its `change-ledger.jsonl` row, findings, and log into the workspace home `<PM_MCP_BASE>/projects/<project_id>/workspace/`) using one of the canonical build verbs (link:../job-runtime/02-confinement-and-environment.adoc#canonical-build-verbs[Job Runtime Specification, Canonical Build Verb Set]; the `command` enum below equals it). The gate scope of the run follows from `module` alone: without `module` the build runs whole-tree, with it only that module. The call blocks for one bounded or progress wait window (link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Timeouts & Budgets Specification]). The model never supplies shell commands or flags. On a worker connection `pm_build` belongs to the tool set of `writer` workers only and must name the scope of a task leased to the worker's generation: for a `read_only` worker it is not listed, and a call of it is the JSON-RPC error `-32602` like every unlisted tool (xref:01-core-workflow-tools.adoc#session-and-worker-surfaces[Session and Worker Surfaces]).

[source,json]
----

  "type": "object",
  "properties": {
    "plan_id": {
      "type": "string",
      "pattern": "^([a-z0-9][a-z0-9-]{1,62}[a-z0-9]|NO_PLAN)$",
      "description": "Plan scope whose worktree the build runs in. The literal NO_PLAN runs in the primary repository checkout as a workspace-addressed request; its ledger row, findings, and log belong to the workspace scope."
    },
    "command": {
      "type": "string",
      "enum": ["clean", "compile", "test-compile", "module-tests", "integration-tests", "e2e", "coverage", "benchmark", "quality-gate", "arch-gate", "verify", "install", "clean-install", "package"],

    },
    "module": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,56}$",

    },

  "additionalProperties": false

----

==== `pm_build` TOON Output Contract

`pm_build` never returns raw console output. It returns a structured TOON result containing:

* `job_id`: unique build job identifier in the `b-` form of the link:../identifiers/01-general-rules-and-registry.adoc#id-job-id[`job_id` grammar] (e.g., `b-7f3a09c4e1d2b865`)
* `status`: the closed job outcome enum (`succeeded`, `failed`, `failed_unparsed`, `refused`, `cancelled`, `timed_out`, `killed`, `indeterminate`; `PM-EXEC-4`, derived by link:../job-runtime/01-pipeline-and-subprocesses.adoc#outcome-derivation[Job Runtime Specification, Outcome Derivation]) plus the non-terminal `running`, which also reports a queued build still waiting for a build slot
* `expectation`: present only on a terminal result of a call that supplied `expect`: `met` when the outcome matches the declared intent (`succeeded` for `green`; `failed` or `failed_unparsed` for `red`), otherwise `violated`; it never changes `status`
* `summary`: counts of total/passed/failed/skipped tests and compiler/linter errors
* `failures`: tabular TOON array of located compiler errors or test failures (`file`, `line`, `column`, `rule_or_test`, `message`)
* `log_uri`: `pm://plan/{plan_id}/builds/{job_id}/log` (or `pm://workspace/builds/{job_id}/log` when `plan_id` is `NO_PLAN`; accompanied by the last 50 lines / 4 KB tail when `status == "failed_unparsed"`, `PM-IMPL-6`)

*Recorded, never returned*: The working-tree digest the build ran against (`worktree_sha` with its `worktree_sha_version`, or `unavailable` with its `worktree_sha_failure`; link:../job-runtime/03-parsers-and-gates.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash]) is stamped on the job's `change-ledger.jsonl` row (`kind: "build"`) and in its job record, where the freshness gates read it; the model makes no decision on it. The allocated budget with its `budget_derivation`, the build template source, the job's `confinement`, the build-slot cap and its source, and the job timing are likewise job-record data, shown by `pm-operator status` (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

*Expected-red runs*: A failing run with `expect: red` returns `status: failed` with `expectation: met`, is recorded as `expected_red` in the change ledger, and files no finding; a passing run with `expect: red` returns `status: succeeded` with `expectation: violated`, and the change ledger records `expected_red_went_green`. An `expect: red` run never satisfies a freshness gate.

=== `pm_lsp` — Warm Language Server Operations
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-3[PM-WATCH-TOOL-3], link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-5[PM-WATCH-TOOL-5]_

Queries or applies verified workspace edits against the runtime's warm LSP pool keyed by `(worktree, language)`. `plan_id: "NO_PLAN"` addresses the main checkout of the project's workspace scope for the read operations; `rename` with `NO_PLAN` is refused with `invalid_arguments`, because an edit is applied only inside a plan's worktree. On the entry-session connection and on the connection of a `read_only` worker `pm_lsp` serves its read operations only: `rename` is refused with `invalid_arguments` (parameter `op`; xref:01-core-workflow-tools.adoc#session-and-worker-surfaces[Session and Worker Surfaces]). The other argument rules the flat schema cannot express are answered the same way, naming the `parameter` and the `rule` (xref:04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[Errors, Failure States & Protocol Testing]): a `path` with a `..` segment or resolving outside the worktree (rule `path_outside_worktree`), and a `path` whose language has no language server enrolled for the project (rule `no_language_server`, naming the language).

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_lsp",
  "description": "Execute a language-server operation against the warm LSP pool for a plan's worktree or the main checkout.",
  "type": "object",
  "properties": {
    "plan_id": {
      "type": "string",
      "pattern": "^([a-z0-9][a-z0-9-]{1,62}[a-z0-9]|NO_PLAN)$",
      "description": "Plan scope identifying the target worktree, or the literal NO_PLAN for the main checkout of the workspace scope (refused for rename, server-enforced)."
    },
    "op": {
      "type": "string",
      "enum": [
        "workspace_symbol",
        "document_symbol",
        "definition",
        "references",
        "hover",
        "diagnostics",
        "rename"
      ],
      "description": "Closed LSP operation to execute."
    },
    "path": {
      "type": "string",
      "minLength": 1,
      "maxLength": 512,
      "pattern": "^[A-Za-z0-9_][A-Za-z0-9_./-]*$",
      "description": "Repository-relative file path within the plan's worktree (required for document_symbol, definition, references, hover, diagnostics, rename; a '..' segment or a path resolving outside the worktree is refused with invalid_arguments)."
    },
    "line": {
      "type": "integer",
      "minimum": 1,
      "description": "1-based line number (required for definition, references, hover, rename)."
    },
    "character": {
      "type": "integer",
      "minimum": 1,
      "description": "1-based column counted in Unicode code points of the line (required for definition, references, hover, rename); the server converts to the language server's negotiated position encoding."
    },
    "query": {
      "type": "string",
      "minLength": 1,
      "maxLength": 256,
      "description": "Symbol search query (required for workspace_symbol)."
    },
    "new_name": {
      "type": "string",
      "pattern": "^[A-Za-z_$][A-Za-z0-9_$]*$",
      "maxLength": 128,
      "description": "Replacement identifier for 'rename' operation."
    }
  },
  "required": ["plan_id", "op"],
  "additionalProperties": false
}
----

*Position Semantics*: Every `pm_lsp` input and output position is 1-based in lines and in columns, and a column counts Unicode code points of the line as stored on disk. The server negotiates the LSP `positionEncoding` with the language server (preferring `utf-32`, then `utf-8`, falling back to `utf-16`) and converts positions in both directions from the file content; a position beyond the end of its line, or beyond the last line, is refused with `invalid_arguments` and never clamped.

==== Warm LSP Pool Lifecycle (`PM-SVC-2`)
_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-11[PM-WATCH-EXT-11], link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-4[PM-WATCH-TOOL-4]_

* *Pool Keying & Lazy Spawn over `stdio`*: The runtime maintains a warm in-memory pool of LSP server child processes, shared by all host connections, keyed by `(canonical_worktree_path, language_id)` using language servers enrolled in the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json`and managed via `org.eclipse.lsp4j:org.eclipse.lsp4j` over `stdio`. They are pool processes, not jobs: started through `pm-exec` with the job confinement but without a job record, and ended by their closed `stdin` when the runtime crashes. Processes start lazily on the first `pm_lsp` or Axis C symbol-edge query and shut down automatically after the language server idle timeout (`lsp_idle_timeout_seconds` in `machine-config.json`), when the plan worktree is removed, or when the runtime drains or stops; the idle, start, and request timeouts are defined in link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle].
* *Diagnostics (`diagnostics`)*: When the language server advertises the LSP 3.17 pull-diagnostics capability (`diagnosticProvider`), the runtime requests the file's current diagnostics with `textDocument/diagnostic`. Otherwise it returns the diagnostics the server last published for that file through the `textDocument/publishDiagnostics` notification, which the pool caches per document, and marks the result `source: published`.
* *Server-Applied `WorkspaceEdit` (`rename`)*: When `op == "rename"`, the runtime validates that every target URI in the LSP `WorkspaceEdit` resolves inside the plan's worktree (`PM-SEC-2`), applies the text edits atomically on disk, and notifies the warm LSP server (`textDocument/didChange`); the modified files reach the realized footprint through its resolver (link:../store-schemas/13-leases-integrity-testing.adoc[Store Schemas Specification, Three-Way File Footprint Reconciliation]) and the unplanned list through the next submit or commit (link:../phase-workflows/03-q-gate-and-execute.adoc#unplanned-changes[Phase Workflows Specification, Unplanned Changes]), like every edit of the worktree. A server answer without a `WorkspaceEdit` is a third outcome, returned as `status: success, applied: false, reason: no_workspace_edit` with nothing changed. A malformed `documentChanges` entry refuses the whole edit instead of being dropped silently, and a rollback is reported as `rolled_back: true` only after the restored bytes, line endings included, are verified identical to the originals.
* *Corpus Language Server*: The corpus language server is an enrollable language server of the meta-project domain (`marshall-plugin`, `pm-plugin-development` in `plan-marshall`), served through the existing `definition`, `references`, and `hover` operations with `plan-marshall`'s completeness bound: an empty answer means the index found none. It adds no operation and no pool tier.
* *Restart Limit*: A language server that crashes is restarted at most the compiled retry limit (link:../job-runtime.adoc[Job Runtime Specification]); after the retries are exhausted, `pm_lsp` answers `lsp_unavailable` for that pool instance until its idle eviction or a runtime restart.

=== Selective Upstream MCP Proxy & `_meta` Provenance (`PM-SVC-3`)
_See Requirement link:../../Requirements.adoc#PM-SVC-3[PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging]_
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-19[PM-WATCH-TOOL-19]_

The relay `pm-mcp serve` is the host's single MCP entry point: upstream MCP servers (such as external issue trackers or documentation indexes) are connected once by the runtime and reached through it, and the runtime acts as their selective filter and provenance boundary:

1. *Operator-Owned Allowlist*: Upstream servers are configured only in the closed object `upstream_mcp` of the per-project operator file `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]): per server its id, its URL, its credential key `mcp-<server_id>`, and the tools re-exposed. The only writer is the runtime on the operator verb `pm-operator upstream allow|deny`, under `local-config.lock` (`PM-SEC-3`). Repository content, including the team configuration under `.marshall/config/`, never adds a server or a tool.
2. *Pass-Through Surface & Schema Narrowing*: Allowlisted tools are listed to the entry session as `up_<server_id>_<tool>` next to the core `pm_*` tools of the session surface, never to a worker, with unused optional parameters stripped from their `inputSchema` to conserve resident context budget. The pass-through set is computed per request from the request's `PM-MCP-Workspace` header and the allowlist; it changes only when the operator changes the allowlist, and hosts see the change at their next `tools/list`. Upstream resources and prompts are not passed through, and upstream skills are never re-exposed as PM-MCP vocabulary skills.
3. *Server-Side Use by Workflow Steps*: A workflow step may call an allowlisted upstream tool server-side; its result enters plan stores only through the two-level guard for external text (the deterministic untrusted-ingestion validator, then the screener, `PM-SEC-1`; link:../model-work/07-untrusted-text-screening.adoc#two-level-guard[Model Work Specification, Two-Level Guard for External Text]), never verbatim.
4. *Provenance Tagging (`_meta` key `de.cuioss.pm-mcp/source`)*: Every tool result or resource proxied from an upstream MCP server is wrapped with `_meta: {"de.cuioss.pm-mcp/source": "upstream_mcp:<server_id>", "de.cuioss.pm-mcp/trusted": false}`, using PM-MCP's own `_meta` key prefix (MCP `_meta` key prefix convention) so that provenance never collides with or is overwritten by keys the upstream server sets, and routed through the two-level guard (`PM-SEC-1`) before any candidate data can enter plan stores.
5. *Credential Isolation & Transport*: An upstream MCP server is reached only as a remote server over HTTPS through `de.cuioss:cui-http` (`PM-TECH-2`); the runtime starts no upstream server as a subprocess. The connection authenticates with the server-specific credential resolved from `CredentialStore` under the key `mcp-<server_id>` of the project; tokens from other providers are never forwarded. A call that cannot reach the upstream server or is refused by it answers `upstream_timeout` or `upstream_unavailable`; an upstream result with `isError: true` is passed through with the provenance `_meta` (xref:04-errors-and-testing.adoc#_sanitized_tool_execution_error_envelope_iserror_true[Errors, Sanitized Tool Execution Error Envelope]).

=== Pure Vocabulary Skills & Dynamic Context Injection (`PM-SKILL-1`, `PM-SKILL-2`, `PM-SKILL-4`)
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-6[PM-WATCH-TOOL-6]_

* *Pure Vocabulary Contract (`PM-SKILL-1`)*: All procedural sequencing, CLI invocations, file path templates, and phase transition rules live exclusively in the compiled workflow engine. Vocabulary skills (`skill://pm/<path>/SKILL.md`) contain strictly domain standards, quality rubrics, architectural principles, and judgment criteria.
* *Server-Generated & Client-Cached Catalogue (`PM-SKILL-2`)*: Vocabulary skills are compiled into the runtime binary `pm-mcpd` or read from the skill directories of the machine and the project (<<skill-extensions>>), filtered by the project's enabled domains (derived, with the overrides of `.marshall/config/domains.json`), and translated on the fly for the client profile of the calling connection (`PM-CLIENT-2`): for a session the client its relay declares, for a worker the harness of its role. Every rendered skill includes a deterministic `_meta.sha256` content digest (`_meta["de.cuioss.pm-mcp/sha256"]`: the SHA-256 of exactly the rendered bytes the client receives, after profile translation and domain filtering, so it changes exactly when those bytes change) enabling client-side caching and invalidation: the runtime's surface is fixed per connection, so it offers no resource subscriptions and never sends `notifications/resources/updated` or a `list_changed` notification, also not on a host's open `subscriptions/listen` stream (link:../runtime-model/03-relay.adoc[Runtime & Interaction Model Specification, Relay]); a client detects a changed skill by its digest, which travels only in `_meta` of the skill result, never as a TOON field of a listing or representation.
* *Dynamic State Context Injection (`PM-SKILL-4`)*: Live plan facts (`plan_id`, active task summary, open findings count, and valid `links`) are injected into the turn's TOON hypermedia representation (`skill` + `facts` + `links`), never baked into static `SKILL.md` files.
* *Worker Protocol Skills (`PM-SKILL-2`)*: The runtime generates three skills that every task's required skill set contains (link:../model-work/04-worker-launch.adoc[Model Work Specification, Skill Delivery]): the core conduct skill `skill://pm/core/SKILL.md`, the task-protocol skill `skill://pm/task-protocol/SKILL.md` (what a wait, an offer, `wait_again`, and `end` mean; acknowledging, executing along the task's links, submitting, and consulting, link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]), and one role skill per role of the shipped role set, `skill://pm/role/<role>/SKILL.md`, the role's contract (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]); a role of the machine or project set may name an extension skill as its contract instead (<<skill-extensions>>).
* *Core Conduct Vocabulary (`skill://pm/core/SKILL.md`)*: The core skill states at minimum: (1) work only along the offered links, act on the scope only through them, and deliver a result only through a `submit` link of the task's entity; (2) a fix covers the whole co-reference population of the defect (derived with `pm_lsp references` or a search before editing), never only the named site; (3) every "only", "all", "none", or "the set is N" claim carries its enumeration and the scope it was derived over; (4) a case outside a closed vocabulary is reported with the vocabulary's out-of-set member, never mapped onto a stand-in member; (5) a re-derived count or coverage figure is checked against its population before it is reported; (6) plan state is read only through `pm_state` and `pm://` resources, never from `.marshall/` files; (7) the correction a rejection names is applied before the call is retried, and a rejected call shape is never resubmitted unchanged.

[#vocabulary-skill-rule-classification]
=== Vocabulary Skill Rule Classification

Every prescriptive rule in a vocabulary skill (the engine owns the process, `PM-ARCH-1`) carries exactly one class:

* *`engine`*: Enforced by link omission or server-side validation. The skill only names the rule; it is a candidate for deletion from resident content.
* *`check`*: Structural and violated in practice. Enforced by a deterministic check that needs no model call.
* *`guidance`*: Semantic and not decidable by a deterministic check. It stays guidance and becomes a measurement subject of the link:../workflow-dsl/07-loop-back-diagrams-verification.adoc#behavioural-conformance-harness[Behavioural Conformance Harness] (`PM-TEST-6`); any automated gate on it runs only under a stated cost ceiling.

Whether a `guidance` rule stays in resident content is decided by its recorded violation history (`PM-TEST-6` verdicts, audit rejections, and findings attributed to the rule); a rule with no recorded violation is a deletion candidate. The class is recorded per rule and carried into every behavioural scenario as its `enforcement_class`, so conformance reports group results by class: mechanically enforced rules and prose-only rules are different propositions and are never pooled into one rate.

=== `pm_skill` — Retrieve Vocabulary Skill Content

Fetches a rendered `SKILL.md` document by its canonical `skill://pm/.../SKILL.md` URI, with its supporting file list and section index, and its SHA-256 digest in `_meta`.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_skill",
  "description": "Retrieve a vocabulary skill document (SKILL.md) rendered for the active project and the calling client.",
  "type": "object",
  "properties": {
    "uri": {
      "type": "string",
      "pattern": "^skill://pm/[a-z0-9][a-z0-9_-]*(/[a-z0-9][a-z0-9_-]*)*/SKILL\\.md$",
      "maxLength": 256,
      "description": "Canonical skill URI referenced in a state representation's 'skill' field."
    },
    "section": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9_-]{0,127}$",
      "description": "Optional heading anchor from the document's section index; returns only that section."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^([a-z0-9][a-z0-9-]{1,62}[a-z0-9]|NO_PLAN)$",
      "description": "Plan scope used to resolve the project and its domain configuration, or the literal NO_PLAN for the workspace scope. Exactly one of plan_id or epic_id is required (server-enforced)."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Epic scope used to resolve the project and its domain configuration. Mutually exclusive with plan_id."
    }
  },
  "required": ["uri"],
  "additionalProperties": false
}
----

* *Rendering Scope*: The client profile is that of the calling connection: the client a session's relay declares, or the harness of a worker's role from its job record (xref:01-core-workflow-tools.adoc#job-bound-connections[Worker Connections]). The addressed scope selects the project and its enabled domains; with `NO_PLAN` the domains come from the project configuration.
* *Section Index & Progressive Loading*: Every `pm_skill` and `pm_skill_file` result carries a section index computed by the server from the rendered document (`sections[]{anchor, title, level, bytes}`). Without `section`, the result carries the whole document beside the index; when the rendered document exceeds the server's inline threshold (one named constant, derived from the measured served-content distribution, link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Served-Content Ledger]), it carries the index instead of the body, with the total size, so the caller reads index first, then sections, then the whole document only when needed. With `section`, the result carries that section only, its `bytes`, and the index.
* *Three Distinct Section Outcomes*: A `section` that the index does not contain returns a tool execution error with `error_code: section_not_found` (naming the available anchors); a document the server cannot read or render returns `error_code: file_unreadable`; a section that exists but has no content returns `bytes: 0` with an empty body. None of the three is ever rendered as a silent empty result.
* *Delivery Record*: On a worker connection, and on a session connection while its session generation holds a task, every served read of a skill (`pm_skill`, with or without `section`, or `resources/read` of the skill under host activation) is written to the generation's skill delivery record with the digest it was served; a submit for a task whose required skills are not all in that record is refused `skills_not_loaded` with the missing URIs (link:../model-work/04-worker-launch.adoc#skills-loaded-at-submit[Model Work Specification, Loaded before Submit]). A `pm_skill` call that fails with a tool execution error of class `server_fault` ends the worker's attempt like any server fault.
* *Served-Content Recording*: Every served read in a plan, epic, or workspace scope appends a row to the served-content ledger in the `metrics.json` of that scope (`uri`, `section`, `bytes`, `plan_id`, `phase`, and the `job_id` of a worker connection, otherwise `null`; `phase` is null outside a plan), from which `record-metrics` publishes the per-document consumption. Host file reads are not observable and are never estimated.

=== Companion Catalogue, Supporting File Tools & MCP Resource Parity (`pm_skills`, `pm_skill_file`, `resources/read`)

* `pm_skills` (session surface): Accepts exactly one of `plan_id` (a plan id or `NO_PLAN`) or `epic_id` (`additionalProperties: false`) and returns the tabular TOON catalogue of all vocabulary skills active for the project's enabled domains (`uri`, `name`, `description`; the digests travel in `_meta`). Catalogue descriptions (skills and tool descriptions) are single-line and bounded by a length limit derived from the measured distribution of the resident surface (link:../client-profiles.adoc[Client Profiles Specification]); a build-time test enforces the bound. A change of description shape (for example from summary-shaped to trigger-shaped) is a separately justified change.
* `pm_skill_file`: Accepts required `uri` (supporting file form of the link:../identifiers/02-registry-stores-to-web.adoc#id-skill-uri[skill URI grammar]), exactly one of `plan_id` (a plan id or `NO_PLAN`) or `epic_id`, and optional `section` with the same semantics as for `pm_skill` (`additionalProperties: false`) to retrieve progressive-disclosure reference files linked from a `SKILL.md`. Skill `resources/read` carries no scope argument; it renders with the client profile of the calling connection (the client a session's relay declares; on a worker connection the harness of its role from the job record) and the enabled domains of the project named by the `PM-MCP-Workspace` header, or of the worker's project; it returns the whole document and publishes the section index in `_meta`; section reads are served by the two tools.
* *Standard MCP Resource Template Parity (`PM-SKILL-3`)*: The runtime exposes the RFC 6570 templates `skill://pm/{+path}/SKILL.md` and `skill://pm/{+path}/{file}` (`{+path}` = one or more `/`-separated lowercase segments) via standard MCP `resources/templates/list` and `resources/read`.

[#skills-extension]
=== MCP Skills Extension & Tool Mirror (`PM-SKILL-3`, `PM-SKILL-4`)
_See Requirement link:../../Requirements.adoc#PM-SKILL-3[PM-SKILL-3: Standard MCP Tool & Resource Skill Delivery]_

* *Published structure*: Every skill is a `SKILL.md` with its supporting files, each an MCP resource under `skill://pm/...`. The runtime declares the MCP Skills Extension (`io.modelcontextprotocol/skills`) in its server capabilities and answers its methods `skills/list` (every skill active for the project's enabled domains, as its manifest) and `skills/get` (the manifest of one skill), and `resources/read` for every file. A manifest carries the skill's `SKILL.md` URI, its frontmatter (`name`, `description`), and every file with its URI, SHA-256 digest of the rendered bytes, and size; it is rendered for the calling connection like every skill. Until the runtime serves the extension, the tool mirror and the `skill://` resources serve the skills alone: the runtime declares no Skills Extension capability, answers no `skills/list` or `skills/get`, switches no connection to host activation, and every bundle installs the shim skill. `quarkus-mcp-server` 2.0.2 has no Skills Extension; the runtime serves it from the first `quarkus-mcp-server` release that does (2.1, not yet released), and the mirror serves alone until then.
* *Tool mirror*: `pm_skills`, `pm_skill`, and `pm_skill_file` serve the same manifests, URIs, and digests as the extension for hosts without it, never a second format: `pm_skills` lists what `skills/list` lists, `pm_skill` and `pm_skill_file` return the bytes `resources/read` returns (with the section index and `section` reads as above), and the digests travel in `_meta` in both.
* *Closed content*: No skill is `dynamic`, no skill comes from a second origin (extension skills are read and served by the runtime itself, <<skill-extensions>>), and no skill instructs code execution on the host (`PM-SKILL-1`); upstream skills are never re-exposed (<<_selective_upstream_mcp_proxy_meta_provenance_pm_svc_3,Selective Upstream MCP Proxy>>).
* *Host activation*: A connection whose host declared the client capability of the Skills Extension is switched to host activation: an offer names the required skills by URI only, their digests in `_meta`, and the host loads them (link:../runtime-model/04-sessions-and-workers.adoc#_connection_scoped_rendering[Runtime & Interaction Model Specification, Connection-Scoped Rendering]). Every other connection receives them in-band (link:../model-work/04-worker-launch.adoc[Model Work Specification, Skill Delivery]). The client profile records a host's verified support, and the next bundle of that host no longer installs the shim (link:../client-profiles.adoc[Client Profiles Specification]).
* *Shim skill*: Until its host supports the extension, every client bundle installs one shim skill in the host's own skill format and directory (link:../client-profiles/03-bundle-manifest.adoc[Client Profiles Specification, Bundle Manifest]), and every server-composed launch prompt carries the same paragraph: skills of `plan-marshall` arrive in-band or are named by a `skill://pm/` URI; a named skill is binding and is read through `pm_skill`; a skill is never reconstructed from memory; and a skill of the same name from elsewhere does not replace it. The shim never chooses skills. It covers a clear or compaction its host does not report, after which the session reads a skill named by URI itself.

[#skill-rule-checker]
=== Skill Rule Checker (`PM-SKILL-1`, `PM-SKILL-5`)
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-21[PM-WATCH-TOOL-21]_

One compiled checker in `pm-core` decides whether a skill may be served. It applies to every skill the runtime distributes, compiled or extension, and runs at two points: in the build for the shipped skills (a build test over the `skill://pm/**` corpus fails the build on any finding), and on every read of an extension skill, as part of its validation (<<skill-extensions>>). It holds only rules about skills as the runtime serves them; rules that concern a host's own plugin or marketplace format are not part of it. Each rule yields a finding with the skill, the file, the line where one exists, and a closed rule id:

* *`frontmatter`*: The frontmatter is the closed set of the skill's kind: `name` and `description` for a compiled skill, plus optional `domains` for an extension skill (<<skill-extensions>>); `name` equals the skill's last path segment (the directory name of an extension skill); any other member, or a missing one, is a finding.
* *`description`*: The description is one line, within the catalogue description bound of `pm_skills` (above), and not empty.
* *`disclosure`*: The three tiers of `PM-SKILL-1` hold: the `SKILL.md` body is within the inline threshold of `pm_skill` or carries headings that give the section index anchors to read; a supporting file is reached only through a link of the `SKILL.md`, never only from another supporting file; and no supporting file is unreferenced.
* *`reference`*: Every relative link and every `skill://pm/` URI in a file resolves: to a supporting file of the same skill, to a section anchor of the linked document, or to a skill of the catalogue (for an extension skill only to its own supporting files, the link allowlist of its validation).
* *`size`*: The bounds of the skill's kind hold (for an extension skill the compiled bounds of its validation; for a compiled skill the same per-file and per-skill bounds).
* *`executable`*: No content instructs execution on the host (`PM-SKILL-1`): no fenced block in a shell or scripting language (`sh`, `bash`, `zsh`, `console`, `shell`, `python`, `ruby`, `powershell`), no line that starts with a shell prompt, no file whose name or first line marks it as a script (a shebang, or a suffix such as `.sh`, `.py`, `.rb`, `.ps1`), and no reference to a `plan-marshall` script or executor (`execute-script.py`, `scripts/`).

A finding fails the build for a shipped skill. For an extension skill it refuses the skill as a whole with the reason `rule_violation` and the findings, reported like every refusal of its validation.

[#skill-extensions]
=== Skill Extensions (`skill://pm/ext/`, `PM-SKILL-5`)
_See Requirement link:../../Requirements.adoc#PM-SKILL-5[PM-SKILL-5: Skill Extensions]_

Extension skills are skills that the runtime reads from directories instead of its binary, so that a role's contract or a project's conventions are configuration. They join the catalogue of a project beside the compiled skills and are served, rendered, and delivered by the same paths; nothing below differs for them except their source and their validation.

* *Sources*: Two skill directories contribute, each skill one subdirectory `<name>/` (the link:../identifiers/02-registry-stores-to-web.adoc#id-extension-skill-name[extension skill name]) with its `SKILL.md` and its supporting files directly beside it: the *machine skill directory* `<PM_MCP_BASE>/skills/` (operator files, for every project of the machine) and the *project skill directory* `.marshall/skills/` of the enrolled project checkout (team-owned and git-tracked; paths in the link:../filesystem-layout.adoc[Filesystem Layout Specification], owner classes in link:../domain-extensions/06-configuration.adoc#config-split[Domain Extensions Specification, Configuration Split]). The project directory is read only from the enrolled project root, never from a plan worktree or the shared epic worktree, so a plan's deliverables never change the skills of the plan's own workers. A project skill replaces a machine skill of the same name as a whole; files are never merged.
* *Namespace*: Every extension skill is served as `skill://pm/ext/<name>/SKILL.md`, its supporting files as `skill://pm/ext/<name>/<file>` (link:../identifiers/02-registry-stores-to-web.adoc#id-skill-uri[skill URI grammar]). The first path segment `ext` is reserved: no compiled skill lies under it (a build test enforces it), so an extension skill never shadows a compiled skill, and the DSL clause `skill pm/ext/<name>` names an extension skill like any other.
* *Validation on every read*: The runtime validates a skill each time it reads it (<<skill-extension-reads>>) and serves it only when every check holds; a skill that fails one is refused as a whole, never served altered or in part, and it is absent from the catalogue:
** _Bounds_ (compiled constants): at most 64 skills per directory, at most 16 files per skill (`SKILL.md` included), at most 64 KiB per file and 256 KiB per skill; UTF-8 only; no subdirectory, no symbolic link, and no file name outside the supporting-file form of the skill URI grammar.
** _Frontmatter_ (closed): `name` (equal to the directory name), `description` (single-line, within the catalogue description bound of `pm_skills` above), and optional `domains` (a list of domain keys of the compiled domain registry). Any other member (`allowed-tools`, `resources`, a dynamic marker) refuses the skill. `domains` is binding data of the runtime and is not rendered; the rendered frontmatter holds `name` and `description` like a compiled skill's.
** _Rules_: the skill passes the <<skill-rule-checker,Skill Rule Checker>> without a finding.
** _Content_: every file passes stages 1 to 3 of the deterministic ingestion validator (link:../job-runtime/03-parsers-and-gates.adoc#ingestion-validator[Job Runtime Specification, Ingestion Validator]) in refusing mode: a file that any stage would change (a removed code point, image, raw HTML, comment, or collapsed section, a neutralized link, a clamped value) is refused with that stage's change report. The link allowlist of an extension skill holds only relative links to its own supporting files. Stage 4 (the injection rule table) and spotlighting do not apply: a skill addresses a model by design and is delivered as binding vocabulary.
* *Refusal reporting*: A refused skill is reported with its directory, file, and reason (`bounds_exceeded`, `frontmatter_invalid`, `name_mismatch`, `rule_violation` with the findings of the rule checker, `content_refused` with the change report, `file_unreadable`) in `pm-operator status`, in the `findings[]` of `pm://project/config` for a project skill, and in the audit log, once per digest of the refused content. A read through `pm_skill` or `pm_skill_file` of a skill refused after it was listed answers `file_unreadable` (xref:04-errors-and-testing.adoc[Errors]).
* [[skill-extension-reads]]*Reads and change*: The runtime reads the extension skills of a project whenever it composes a catalogue listing (`skills/list`, `pm_skills`), a launch prompt, or an offer, and whenever it computes the configuration and qualification digests of a role (link:../model-work/01-roles-and-configuration.adoc#role-artifact[Model Work Specification, Role Artifact]); it caches each accepted skill by the digests of its files. The digest a delivery carries is that of the read, so an edited skill reaches a worker generation through the re-delivery on a changed digest (link:../model-work/04-worker-launch.adoc#skill-delivery[Model Work Specification, Skill Delivery Record & Re-Delivery]) and needs no re-composition: an extension skill is no input of a plan instance, because no gate, link, schema, budget, or workflow unit is ever read from a skill (`PM-SKILL-1`).
* *Use*: A role artifact names extension skills in its `skills`, its role skill (the contract) included (link:../model-work/01-roles-and-configuration.adoc#role-validation[Model Work Specification, Validation]). An extension skill with `domains` joins the domain skills of every task of a project in which one of its domains is active (link:../model-work/04-worker-launch.adoc#skill-delivery[Model Work Specification, Skill Delivery]) and is listed by `skills/list` and `pm_skills` only for such a project; one without `domains` is listed for every project and is delivered only to the roles that name it or the states whose `skill` clause names it.
* *Trust*: A project skill is untrusted repository input with the trust of the project instructions a worker loads natively from its working directory: it can shape a model's judgment but never a gate, a link, or a result schema, which the server checks against the contract whatever the model made of a skill. A changed skill of a role changes the role's qualification digest, so the role is unqualified until the operator grades it again (link:../model-work/01-roles-and-configuration.adoc#qualification-records[Model Work Specification, Qualification Records]); a team edit can therefore never change a qualified contract silently.
