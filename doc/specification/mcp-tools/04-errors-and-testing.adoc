[#protocol-errors-vs-domain-workflow-failure-states]
== Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)
_See Requirement link:../../Requirements.adoc#PM-TOOL-4[PM-TOOL-4: Domain Failures as Valid Workflow States]_

_See Requirement link:../../Requirements.adoc#PM-TEST-4[PM-TEST-4: End-to-End Scenario & Worker Supervision Testing]_

_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-11[PM-WATCH-TOOL-11]_

A foundational invariant of PM-MCP is that *domain failures and transition rejections are workflow states, not MCP protocol errors*. Three response classes are distinguished:

* *JSON-RPC protocol errors*: a JSON-RPC `error` response (no `CallToolResult`) for malformed JSON-RPC (`-32700` parse error, `-32600` invalid request), unknown tool names (`-32602`), and resource read errors (`-32002`, see Resource Contract).
* *Tool execution errors*: a normal `CallToolResult` with `isError: true` when the arguments violate the tool's input schema or a server-enforced argument rule (`invalid_arguments`, as MCP specifies since `2025-11-25`, so the model sees the error and corrects the call) or a valid call cannot be executed (unknown scope, unenrolled project, a worker connection outside its binding, a fenced generation, an ended job, unhandled server exception).
* *Domain results*: a normal `CallToolResult` with `isError: false` for every workflow outcome, including failures and rejected transitions (`PM-TOOL-4`).

=== Normative Classification Matrix

[cols="2,1,2,3"]
|===
|Condition |MCP Response Class |Response Structure |Model Recovery Path

|Valid transition succeeds (`pm_do`)
|`isError: false`
|Next state's TOON representation (`state`, `facts`, `links`).
|Follow one of the new `links`.

|Build fails, tests fail, CI or an analysis gate turns red, or review evidence is missing
|`isError: false`
|The decision task of the class's remediation policy unit (`remediation.build-failure`, `remediation.ci-failure`, `remediation.analysis`, `remediation.review-findings`; link:../state-catalogue.adoc[State Catalogue]) is offered to a worker of the policy's role; its entity renders the failure envelopes in `facts` (excerpts as `pm://plan/{plan_id}/evidence/{evidence_id}` resources) and the budget-guarded links `retry`, `fix`, and, where the gate is waivable and a waiver wait is configured, `request_waiver`. Where the bound budgets leave one action, the server takes it without a task.
|The worker inspects the failure envelopes (and their excerpts), then follows one remedy; an exhausted remediation in Phase 5 or in finalize before the merge enters the phase's re-planning call state (`execute.replan`, `finalize.replan`, trigger `ceiling`), whose conservative fallback is the hand-back, and elsewhere takes the phase's fallback route (`handed_back` or `returned`) (link:../workflow-dsl/08-remediation-units.adoc#remediation-units[Workflow DSL Specification, Remediation Policy Units]).

|Git push rejected (non-fast-forward) or merge conflict
|`isError: false`
|`git.sync-required` (inside the `git.commit_and_push` sub-workflow) is server logic that rebases; a rebase conflict becomes a task of the plan's writer role in `git.resolve-conflicts`, whose entity renders the conflicting hunks and its submit links; a rebase that cannot start ends the call with the server step-out (`cause: rebase_failed`); a merge conflict on the merge path calls `remediation.merge-conflict`.
|The writer worker resolves the conflict in the worktree and submits; the server continues the sub-workflow.

|A change outside the plan's worktree, or a main-checkout change since the plan's entry baseline
|`isError: false`
|The scope's current state stays unchanged under `condition: footprint_violation` (link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-footprint_violation[State Catalogue, Conditions]); its self-remedy is a `fix` task of the role whose work raised it, whose entity names the offending files.
|The worker inspects the named files, reverts only changes this plan made, never baseline dirt (`facts.baseline_dirty`) or foreign changes, and submits `fix`; when the condition's budget is spent, the engine takes the phase's fallback route with the violation recorded as the gap.

|Stale link followed, entity no longer in accepting state, `args` fails link parameter validation, or `pm_do` of a fenced generation
|`isError: false`
|Authoritative *current* TOON representation plus a top-level `rejected` block (`reason` from the closed set in <<rejection-reasons>>, `link`, `detail`); for `generation_fenced` the entity's representation without links.
|Read the current representation and follow one of its valid `links` with corrected `args`; after `generation_fenced` the caller stops working on the task.

|A task's submission exhausts a remediation budget
|`isError: false`
|The task entity's terminal representation; in Phase 5 and in finalize before the merge the engine enters the phase's re-planning call state (trigger `ceiling`), whose conservative fallback is the hand-back; elsewhere it continues the plan on the phase's fallback route (`plan.return` or `finalize.hand-back`, then the post-run band), which ends the plan `returned` or `handed_back`; with a positive `waiver_wait_seconds`, the unit's waiver wait comes first, and the plan's view renders the waiver hint in `facts.operator_command`.
|The worker calls `pm_wait` again; an entry session viewing the plan relays a waiver hint to the operator as information, never answers it.

|A digest-protected store or an enrolment file was changed outside the runtime
|`isError: false`
|TOON representation of the unchanged current state with `condition: integrity_breach` (link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-conditions[State Catalogue, Conditions]), `links: []`, and `facts.operator_command` naming `pm-operator accept-edit …` and `pm-operator abort …`; no task of the scope is offered, and every `pm_do` on the scope is rejected with `integrity_paused` until the operator resolves the pause.
|The entry session relays the operator command; the pause has no time bound and no model link.

|Malformed JSON-RPC or unknown tool name
|JSON-RPC error
|JSON-RPC `error` object (`-32700`, `-32600`, or `-32602`) with its fixed message; no `CallToolResult`.
|Fix the tool invocation.

|Tool arguments violate the input schema or a server-enforced argument rule (type, pattern, unknown property, missing or mutually exclusive scope parameters, per-operation required parameters, path shape, unknown module or job)
|`isError: true`
|MCP `CallToolResult` with `isError: true`, `error_code: invalid_arguments`, `parameter`, and `rule`.
|Correct the named parameter and call again.

|Unknown `plan_id` / `epic_id` / `entity` (a consumed or swept bootstrap entry included), unenrolled workspace, or internal server exception
|`isError: true`
|MCP `CallToolResult` with `isError: true` and closed `error_code` (`scope_not_found`, `project_not_enrolled`, `internal_fault`); only `internal_fault` adds `audit_id`.
|Halt or invoke discovery (`pm_plans` / `pm_epics`), or notify the operator (with `audit_id` for `internal_fault`).

|A worker connection names a scope or entity not leased to its generation, its generation was fenced, or its job has ended
|`isError: true`
|MCP `CallToolResult` with `isError: true` and `error_code: job_scope_mismatch`, `generation_fenced` (every tool but `pm_do`, which rejects instead), or `job_ended` (xref:01-core-workflow-tools.adoc#job-bound-connections[Worker Connections]).
|Address the offered task's scope and entity; after `generation_fenced` or `job_ended` the caller stops.

|The addressed project's recovery after a runtime start has not finished within the project recovery wait
|`isError: true`
|MCP `CallToolResult` with `isError: true` and `error_code: runtime_recovering`; nothing of the call was executed.
|Retryable: repeat the same call.

|`pm_lsp` addresses a language server whose restart retries are exhausted
|`isError: true`
|MCP `CallToolResult` with `isError: true` and `error_code: lsp_unavailable`.
|Continue without semantic navigation (search instead); the instance returns after its idle eviction or a runtime restart.

|`pm_skill` / `pm_skill_file` names a section the document does not contain, or a document that cannot be read or rendered
|`isError: true`
|MCP `CallToolResult` with `isError: true` and closed `error_code` (`section_not_found` with the available anchors, or `file_unreadable` with `audit_id`).
|Read the section index and request an existing anchor, or notify the operator with `audit_id`.
|===

=== Rejected Transition Representation (`isError: false`)
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-2[PM-WATCH-TOOL-2]_

When `pm_do` is called with a stale link or invalid free parameter `args`, the server returns `isError: false` with a `rejected` block inserted into the current authoritative representation at its canonical position (after `skill`, before `facts`; see link:../hypermedia-format/01-representation-and-link-forms.adoc#canonical-top-level-fields[Hypermedia Format Specification]). The example shows the task entity of `git.compose-message` that a worker of the commit-message role holds while the `finalize.push-barrier` call runs the `git.commit_and_push` sub-workflow:

[source,toon]
----
scope: entity
plan_id: plan-x
entity: qt-3c1e9a7b52d04f16
state: entity.active
phase: finalize
summary: "push barrier found 2 uncommitted files, commit message required"
skill: "skill://pm/git/commit-message/SKILL.md"
rejected:
  link: commit
  reason: invalid_link_args
  detail: "parameter 'message' length 0 is below minimum 1"
facts:
  changed_files: 2
  module_scope: http
  suggested_type: fix
links[2]{rel,link,form,free}:
  submit,commit,submit,"message:text[1..2000]"
  submit,infeasible,submit,"evidence:text[1..2000]"
----

[#rejection-reasons]
==== Closed Rejection Reasons & Failure Classes
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-2[PM-WATCH-TOOL-2], link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-11[PM-WATCH-TOOL-11], link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-14[PM-WATCH-TOOL-14], link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-17[PM-WATCH-TOOL-17]_

`rejected.reason` is a closed enumeration. This table is its single definition; a specification that introduces a new rejection reason extends it here:

[cols="1,3"]
|===
|`reason` |Condition

|`link_not_available`
|The link identifier is not offered in the current state, including invented or paraphrased identifiers.

|`stale_entity`
|The entity-addressed link names an entity that is no longer in an accepting state (for example an already triaged finding, or a task whose lease was released).

|`generation_fenced`
|The call's generation was fenced (a replaced worker, a new start of the same session identity, a drain or recovery); the rejection carries the entity's representation without links, and nothing is executed (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). The other tools answer the same case with the error code `generation_fenced` (<<_sanitized_tool_execution_error_envelope_iserror_true>>).

|`role_undefined`
|The transition would compose a plan instance or an epic workflow (an adopted configuration drift, the adoption of a changed workflow unit, a re-composition after a waiver) that names a role the effective role set does not define or whose artifact is invalid; `detail` names the role and the state, and nothing is composed (`PM-WORK-1`, link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]). At a bootstrap's commit the same check is a re-check reason (xref:01-core-workflow-tools.adoc#bootstrap-commit-recheck[Bootstrap Commit Re-Check]).

|`class_mismatch`
|The same compositions as `role_undefined`, for a role's class: a model state names a role whose class differs from the class its entity kind requires, or a `consult role` clause names a `zero_tool` role; `detail` names the role, its class, the state, and the required class, and nothing is composed (`PM-WORK-1`, link:../model-work/01-roles-and-configuration.adoc#role-composition[Model Work Specification, Composition Check]). At a bootstrap's commit the same check is a re-check reason.

|`skill_unresolved`
|The same compositions as `role_undefined`, for a skill: a `skill` clause of the composed units names a skill that does not resolve in the project's skill catalogue (absent, or an extension skill under `skill://pm/ext/` that is missing or refused); `detail` names the skill and the state, and nothing is composed (`PM-SKILL-5`, link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Rule 14]). At a bootstrap's commit the same check is a re-check reason.

|`quorum_invalid`, `quorum_not_diverse`
|The same compositions as `role_undefined`, in a project where a class's effective mode is `quorum`: a quorum declaration fails its check against the effective role set (a listed role undefined, not `read_only`, or `session_first`; or two listed roles naming the same model); `detail` names the declaration, the rule, and the role, and nothing is composed (`PM-WF-18`, link:../model-work/10-decision-quorum.adoc#decision-declarations[Model Work Specification, Decision Declarations]; link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Rule 13]). At a bootstrap's commit the same check is a re-check reason.

|`skills_not_loaded`
|A submit of a task entity whose required skills are not all in the delivery record of the caller's generation; `detail` lists the missing `skill://` URIs, the task stays executing, and the worker loads them and submits again (`PM-SKILL-4`, link:../model-work/04-worker-launch.adoc#skills-loaded-at-submit[Model Work Specification, Loaded before Submit]).

|`operator_only`
|The link names an operator transition, which is never offered to the model (`PM-SEC-3`).

|`integrity_paused`
|The addressed scope is paused by the `integrity_breach` condition (a tampered plan or epic store, or a tampered enrolment file of the project; a tampered harness enrolment store `harnesses.json` pauses nothing: it refuses the worker launch before spawn with fate `refused` and reason `harness_tampered`, a start failure of the role on that harness, never a tool error, link:../model-work/04-worker-launch.adoc#harness-selection[Model Work Specification, Launch Refusals]); every `pm_do` on it is refused, and no task of it is offered, until the operator resolves the pause with `accept-edit` or `abort` (link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-conditions[State Catalogue, Conditions]). The rejection carries the unchanged paused representation.

|`undeclared_param`
|`args` contains a key the link does not declare.

|`missing_param`
|A required free parameter is absent.

|`invalid_link_args`
|A free parameter violates its type, enum, length, or range constraint, or an attached content validator refuses the payload (including an answer whose `branch_key` is not an option of its question record).

|`already_answered`
|An answer (`answer:<question_id>`, or the web app's answer request) names a question record that is already answered or cancelled; nothing is written for that record (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]).

|`question_expired`
|An answer on a user channel (`session`, `elicitation`, `web`) arrives after its record's deadline passed and the runtime applied its default; the recorded default stands.

|`retry_not_applicable`
|The `retry` link of a remediation policy's `choose` task names the same failure fingerprints that already failed after a retry with the same `reason`; a retry cannot change them (link:../workflow-dsl/08-remediation-units.adoc#remediation-units[Workflow DSL Specification, Remediation Policy Units]).

|`fix_unchanged`
|The `fix` of a remediation policy (or a re-submitted artifact of a Q-Gate remediation pass) produced no change: an empty commit or an artifact identical to the one the failing verification saw. The attempt is not charged against the fix budget.

|`phase_closed`
|A finding submission is addressed to a phase the plan has already left (for example a `phase-3-outline` Q-Gate finding after the plan entered `phase-4-plan`, link:../phase-workflows.adoc[Phase Workflows Specification], Blocking Findings Guard); the finding is not written.

|`capability_missing`
|A native git operation needs a repository capability the native variant lacks (derived fact `git_native_capability`; `detail` names the feature and the `pm-operator` command that selects the CLI variant; link:../cli-and-security/02-credentials-and-operator.adoc#native-confinement[CLI & Security Specification, Native Operation Confinement]); it is the transport outcome of the operation's job record, never a fallback.

|`integration_variant_unset`
|A git or provider primitive found no valid operator choice of the integration variant for an integration whose used features the `native` variant cannot serve (derived fact `git_native_capability`; otherwise `native` applies without a choice); `detail` names the integration and the project setup state `setup.select-integration-variants`, where the operator chooses through the operator channel (link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]). No git or provider operation runs before the decision.

|`config_invalid`
|A phase handshake found a team configuration file or a project workflow unit that fails validation: a schema violation or undeclared key of a team file, or a unit violating a static verification rule or a compiled invariant (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]); `detail` names the file and the JSON pointer or line and the violated rule. The same finding is recorded in the workspace scope and published in `pm://project/config`; nothing falls back to a default.

|`format_outdated`, `format_newer`
|A phase handshake found a team configuration file or a project workflow unit whose `format_version` (or DSL `format`) is older or newer than the binary accepts (link:../store-schemas/01-format-and-session-log.adoc#format-versioning[Store Schemas Specification, Format Versioning]); `detail` names the file, the found and the current version. The file is never rewritten; the project setup workflow offers the rewrite.

|`target_undeliverable`
|A `mailbox_send` submit whose `plan_id` names a plan that does not exist or is archived (link:../model-work/08-epic-coordination.adoc#plan-mailbox[Model Work Specification, Plan Mailbox]); the message is not written.

|`surface_overlap`
|An epic queue-row write (staging a plan, or amending a `staged` row's `declared_surface` or `prerequisites[]`) would give the row a declared surface overlapping that of another non-terminal row of the same epic that is not ordered with it through prerequisites; `detail` names the overlapping plans and paths, and the row is not written (link:../model-work/08-epic-coordination.adoc#epic-surface-disjointness[Model Work Specification, Staging-Time Surface Disjointness]).

|`surface_undeclared`
|An epic queue-row write stages a plan whose expected surface cannot be declared (empty, an entry that is not a git-tracked path or glob inside the workspace, or an entry that cannot be evaluated); `detail` names the offending entries, and the row is not written (link:../model-work/08-epic-coordination.adoc#epic-surface-disjointness[Model Work Specification, Staging-Time Surface Disjointness]).

|`path_traversal_rejected`
|A repository path in `args` escapes the workspace: a `..` segment, an absolute path, or a symlink resolving outside the plan's worktree (`PM-SEC-2`). Job requests carry the same reason with the job outcome `refused` (link:../job-runtime.adoc[Job Runtime Specification]).
|===

A content validator that refuses a payload answers `invalid_link_args` and names its specific cause in `detail` (for example `non_resolving_package_key`, link:../domain-extensions.adoc[Domain Extensions Specification]); such causes are `detail` codes, not reasons (for example `pr_title_missing`, a pull request title that the recipe or the model did not supply). A store write the server itself cannot complete, such as a landing record without its required facts (`landing_facts_missing`), is no rejection: it is an internal write refusal of class `server_fault`, answered `internal_fault`. Outcome, state, condition, and finding tokens (a job's `refused`, the `integrity_breach` condition, finding types such as `unknown_config_key`) are never `rejected.reason` values; `integrity_paused` names the refusal, not the condition.

A job that exceeds its budget is a job outcome (`timed_out`), never a rejection. A rejection belongs to the failure class `caller_drift` (the call did not match the offered contract), except the environment refusals `integrity_paused`, `capability_missing`, `integration_variant_unset`, `config_invalid`, `format_outdated`, `format_newer`, `role_undefined`, `class_mismatch`, `skill_unresolved`, `quorum_invalid`, `quorum_not_diverse`, and `generation_fenced`, which belong to the class `precondition` (the call matched the contract, the environment refused it). A tool execution error (`isError: true`) is classified by its `error_code` (<<_sanitized_tool_execution_error_envelope_iserror_true>>): `invalid_arguments`, `section_not_found`, and `job_scope_mismatch` belong to `caller_drift`; `scope_not_found`, `project_not_enrolled`, `runtime_recovering`, `generation_fenced`, and `job_ended` to `precondition`; `internal_fault`, `file_unreadable`, `lsp_unavailable`, `upstream_timeout`, and `upstream_unavailable` to `server_fault`. The three classes are counted separately per plan (link:../phase-workflows.adoc[Phase Workflows Specification], `record-metrics`), each with its population. A scope-less refusal, the bootstrap commit re-check (xref:01-core-workflow-tools.adoc#bootstrap-commit-recheck[Bootstrap Commit Re-Check]), has class `precondition` and no plan to count against: it is recorded in the audit log only.

=== Sanitized Tool Execution Error Envelope (`isError: true`)
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-17[PM-WATCH-TOOL-17], link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-19[PM-WATCH-TOOL-19]_

When a tool call cannot be executed (`isError: true`), the `TextContent` payload is strictly sanitized — stack traces, Java class names, filesystem paths, and credentials are never emitted:

[source,toon]
----
error: true
error_code: scope_not_found
message: "Plan scope 'plan-unknown' does not exist in the enrolled workspace."
----

Every tool execution error is written to `audit.jsonl`, but the payload carries `audit_id` only for the codes whose recovery path is an operator look-up, `internal_fault` and `file_unreadable`; for every other code the model corrects the call, retries, or uses discovery, and the identifier would have no operational value for it (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

Closed `error_code` enumeration for `isError: true`:

* `invalid_arguments` — The tool arguments violate the tool's input schema or a server-enforced argument rule; the payload adds `parameter` (the offending property, or the set of mutually exclusive properties) and `rule` (one line, as stated in the property's `description`). This includes a `pm_lsp` `path` outside the worktree and a `path` whose language has no enrolled language server, an unknown or foreign `pm_build` `job_id` (a finished build of the same scope returns its terminal result), and a `module` the project's discovery does not know (xref:02-service-and-skill-tools.adoc#_orthogonal_service_capability_tool_schemas_pm_build_pm_lsp[Service Tools]).
* `scope_not_found` — Referenced `plan_id`, `epic_id`, or `entity` does not exist: the plan is in neither `plans/` nor `archive/` of the project's machine store (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), or the epic or entity is unknown (a bootstrap `entry_id` whose pending entry record was consumed by its commit or removed by the sweep included). An archived plan is found and answered read-only with its terminal representation.
* `project_not_enrolled` — The target repository has no enrolment file in `<PM_MCP_BASE>/enrolments/`, or, for a workspace-addressed request (`PM-ARCH-4`), the `PM-MCP-Workspace` header does not resolve to an enrolled project by the project resolution rule (link:../filesystem-layout/03-project-store.adoc#project-resolution[Filesystem Layout Specification, Project Resolution Rule]) (`pm-operator enrol`, link:../cli-and-security/02-credentials-and-operator.adoc#enrolment-lifecycle-release[CLI, Coordination & Security Specification]).
* `job_scope_mismatch` — A worker connection addressed a scope or entity that is not a task entity leased to its generation (xref:01-core-workflow-tools.adoc#job-bound-connections[Worker Connections]); nothing was executed.
* `generation_fenced` — The call's generation was fenced: a worker the supervisor replaced, or an earlier start of the same session identity (link:../runtime-model/03-relay.adoc#_generations_at_the_relay[Runtime & Interaction Model Specification, Generations at the Relay]); nothing was executed, and the caller stops. `pm_do` answers the same case with the rejection `generation_fenced` (<<rejection-reasons>>).
* `job_ended` — The job token of the connection belongs to a job that has ended (a fresh worker after its task, a recycled warm worker); its token is revoked.
* `section_not_found` — `pm_skill` or `pm_skill_file` named a `section` that the document's section index does not contain; the message lists the available anchors.
* `file_unreadable` — The requested skill document or supporting file exists in the catalogue but cannot be read or rendered.
* `runtime_recovering` — Retryable. The call addresses a project whose per-project recovery after a runtime start has not finished within the project recovery wait (link:../runtime-model/02-startup-recovery-drain.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery], link:../timeouts/02-runtime-leases-operator-web.adoc#project-recovery-wait[Timeouts & Budgets Specification]); nothing of the call was executed, recovery continues, and the same call repeated later is served.
* `lsp_unavailable` — `pm_lsp` addressed a language server pool instance whose restart retries are exhausted (link:../job-runtime.adoc[Job Runtime Specification]); the instance stays unavailable until its idle eviction or a runtime restart, so repeating the call at once returns the same code.
* `upstream_timeout` — An upstream pass-through tool call (`up_*`) exceeded its connect or read timeout (link:../timeouts.adoc[Timeouts & Budgets Specification]); the call can be retried.
* `upstream_unavailable` — An upstream pass-through tool call (`up_*`) could not be completed: the connection or the TLS handshake failed, the `mcp-<server_id>` credential is missing or the upstream server rejected it, or the upstream server answered with a JSON-RPC error (xref:02-service-and-skill-tools.adoc#_selective_upstream_mcp_proxy_meta_provenance_pm_svc_3[Selective Upstream MCP Proxy]). An upstream result with `isError: true` is no error of this set: it is passed through as the upstream server returned it, wrapped with the provenance `_meta`.
* `internal_fault` — Unexpected server exception, including a lock acquisition the lock manager refuses as out of order (`lock_order_violation`, link:../store-schemas/13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Store Schemas Specification]); full diagnostics are written exclusively to `audit.jsonl` under `audit_id`.

[#relay-transport-codes]
*Relay and transport codes*: Two closed codes never come from a tool handler and are never a `CallToolResult`:

* `runtime_unavailable` — The relay answers a pending request with the JSON-RPC error code `-32000` (the implementation-defined server error range of JSON-RPC 2.0) and this code in `error.data.error_code` when its stream to the runtime is lost or the runtime does not accept connections within the start timeout; the host may repeat the call, and the relay keeps retrying on subsequent requests (link:../runtime-model/03-relay.adoc#relay-rules[Runtime & Interaction Model Specification, Relay Rules], rule 3).
* `generation_superseded` — The runtime's transport answers a request whose generation `pm-mcp enter` of the same session identity replaced with HTTP `409` and this code, before any handler; the relay binds again with `relay_start` and repeats the request once, so the code never reaches the host (link:../runtime-model/03-relay.adoc#_generations_at_the_relay[Runtime & Interaction Model Specification, Generations at the Relay]).

JSON-RPC protocol errors are sanitized the same way: the `error.message` is a fixed text per code, and `error.data` is present only for resource read errors, carrying the closed `error_code` (`-32002`: `scope_not_found`, `path_traversal_rejected`), and for `runtime_unavailable` (`-32000`); the audit record is written, its `audit_id` is not returned.

=== End-to-End STDIO Integration Testing (`McpStdioTestClient` in `*IT.java`)

Integration tests run in four layers, each in Failsafe `*IT.java` classes under the integration-tests profile (`PM-TEST-3`, `PM-TEST-4`, `PM-TECH-2`; link:../module-structure.adoc#test-placement[Module Structure Specification, Test Placement]). Two of them are MCP protocol layers verified with `McpAssured`: the daemon and the release shape; the relay layer verifies the forwarding against its stub daemon, and the operator layer serves no MCP.

* *Daemon (`pm-mcp-server`)*: the integration tests exercise the packaged daemon `pm-mcpd` over MCP Streamable HTTP on its Unix socket. The same layer covers the runtime's web listener and pairing (link:../cli-and-security/03-web-server.adoc#web-listener[CLI, Coordination & Security Specification, Listener Exposure]): the TCP listener serves no MCP, so these tests run without `McpAssured` and assert, among the listener rules, that `/mcp` is not routed there.
* *Relay (`pm-relay`)*: the integration tests exercise the `pm-mcp serve` STDIO relay over real `stdin`/`stdout` against the stub daemon of the module's test scope; `pm-mcpd` is built later than `pm-relay` (link:../module-structure.adoc#artifact-flow[Module Structure Specification, Artifact Flow]), so the relay meets it in the release-shape layer, with `McpAssured.newStdioClient()`. The STDIO client waits at most 10 s per response (its Awaitility default, without a setter), so a test that does not verify the on-demand start itself starts the daemon before the relay.
* *Operator (`pm-operator`)*: the integration tests run operator verbs of the binary `pm-operator` against the same kind of stub daemon; the binary serves no MCP, so this layer runs without `McpAssured`. The verbs against the real `pm-mcpd` run in the release-shape layer.
* *Release shape (`pm-e2e`)*: the module `pm-e2e` stages all four binaries (`pm-mcp`, `pm-operator`, `pm-mcpd`, `pm-exec`) in the release layout and runs end-to-end scenarios through the whole chain: relay, daemon, and jobs launched by `pm-exec`.

The release-shape tests spawn `pm-mcp serve` as a real child process:

[source,java]
----
// The pending entry record is written first, as the user entry command does: `pm-mcp enter plan` prints `entry: <entry_id>`.
String entryId = runPmMcpEnter(pmMcpBinaryPath, tempWorkspaceRoot, "Add JSpecify null-safety to service layer");

McpStdioTestClient client = McpAssured.newStdioClient()
    .setCommand(List.of(pmMcpBinaryPath.toString(), "serve", "--client", "claude"))
    .setWorkingDirectory(tempWorkspaceRoot)
    .setEnvironment(Map.of(
        "PM_MCP_BASE", tempPmMcpBase.toString(),
        "PM_MCP_HOME", tempPmMcpHome.toString())) // bin/ holds the staged pm-mcpd
    .setStderrHandler(stderrAuditBuffer::add)
    .build()
    .connect();

client.when()
    .toolsList(page -> {
        assertThat(page.tools())
            .extracting(ToolInfo::name)
            .containsExactlyInAnyOrder(
                "pm_state", "pm_do", "pm_wait", "pm_plans", "pm_epics",
                "pm_build", "pm_lsp", "pm_skills", "pm_skill", "pm_skill_file"); // claude: session_tasks; every stage delivered
    })
    .toolsCall("pm_state", Map.of("plan_id", "NO_PLAN", "entity", entryId), response -> {
        assertThat(response.isError()).isFalse();
        assertThat(response.content().getFirst().asText().text())
            .contains("state: start.choose"); // a hint names no source: the bootstrap lists the candidates
    })
    .thenAssertResults();
----

=== Normative `McpAssured` Verification Requirements

1. *Tool & Resource Schema Conformance*: Every `@Tool` and `@ResourceTemplate` is asserted via `client.when().toolsList(...)` and `client.when().resourcesTemplatesList(...)` to verify closed JSON Schema Draft 2020-12 `inputSchema` definitions (`additionalProperties: false`) and exact URI template registrations. The example asserts the complete session surface of a client whose profile allows session tasks, with an empty upstream allowlist, as served once every tool is delivered; the test of a release asserts exactly the tools its migration stage has delivered (`PM-MIG-1`; for example no `pm_lsp` before Stage 5), never the full set ahead of its stage; further tests assert the session surface without `pm_wait` for a client without session tasks, the tool set of a `writer` and a `read_only` worker connection, and that no listed schema carries an identity argument; no `plan-marshall` script tool is ever registered. A second test with a configured allowlist asserts exactly the core set plus the allowlisted `up_*` tools, and that an upstream tool not on the allowlist, or one added only in a team configuration file under `.marshall/config/`, never appears.
2. *Domain Failure vs Protocol Error Assertions*: Every `pm_do` rejection and domain failure state is asserted with `assertThat(response.isError()).isFalse()`, unknown scope queries are asserted with `assertThat(response.isError()).isTrue()` and a sanitized `error_code` payload without `audit_id` (present only for `internal_fault` and `file_unreadable`), argument violations (schema and server-enforced rules) are asserted with `assertThat(response.isError()).isTrue()` and `error_code: invalid_arguments`, unknown tools are asserted as JSON-RPC error responses (`-32602`) without a `CallToolResult`, and unknown-scope resource reads as JSON-RPC `-32002` with `scope_not_found` in `data`.
3. *`stdout` Stream Hygiene & `stderr` Separation*: `setStderrHandler(...)` captures all diagnostic output on `stderr` while `McpStdioTestClient` parses every `stdout` line as a strict JSON-RPC 2.0 frame, proving zero `stdout` pollution across concurrent `pm_build` and `pm_lsp` executions (`PM-SEC-4`, `PM-TEST-5`).
