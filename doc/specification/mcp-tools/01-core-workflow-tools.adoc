=== Architectural Constraints
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-13[PM-WATCH-TOOL-13]_

1. *Small, Stable Verb Set*: PM-MCP exposes a fixed set of top-level MCP tools (`pm_start`, `pm_state`, `pm_do`, `pm_plans`, `pm_epics`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`) rather than one tool per workflow step or script. Across all phases and domains, the resident core tool surface remains constant, and privileged operator actions are strictly excluded from the MCP tool surface (`PM-SEC-3`). The only additional tools are the operator-allowlisted upstream pass-through tools (xref:02-service-and-skill-tools.adoc#_selective_upstream_mcp_proxy_meta_provenance_pm_svc_3[Selective Upstream MCP Proxy & `_meta` Provenance (`PM-SVC-3`)]), which change only with the operator's allowlist and are never part of the core set. The set has no exception: no tool runs legacy `plan-marshall` scripts (xref:02-service-and-skill-tools.adoc#transitional-legacy-script-tool[Legacy Script Execution (Removed)]).
2. *Portable Naming Convention*: Every core tool name conforms to the link:../identifiers/02-registry-stores-to-web.adoc#id-core-tool-name[core tool name grammar] and every upstream pass-through tool name to the link:../identifiers/02-registry-stores-to-web.adoc#id-upstream-tool-name[upstream tool name grammar] (Identifier Registry), ensuring identical identifiers across Claude Code, OpenCode, Antigravity, Codex, and raw model tool-calling APIs without escaping or translation.
3. *Closed, Host-Portable Flat Schemas*: Every tool `inputSchema` conforms to JSON Schema Draft 2020-12 and declares `"additionalProperties": false` at the top-level object boundary. It uses only the subset every supported host and provider API accepts: a top-level `type: object` with `properties`, `required` (only parameters that are always required), and `additionalProperties`; per property `type`, `enum`, `pattern` without lookaround, `minimum`/`maximum`, `minLength`/`maxLength`, `default`, and `description`. Top-level `oneOf`/`anyOf`/`allOf`, `if`/`then`/`else`, `not`, and `const` are never used; the `$schema` and `title` members shown in this specification are documentation only and are not sent in `tools/list`. Rules the subset cannot express (mutually exclusive scope parameters, alternative plan sources, per-operation required parameters, path shape) are enforced by the server's argument validation and answered with the closed error of xref:04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)]; each such rule is stated in one line of the affected property's `description`. Milestone 1 verifies the final schemas by registering and calling them on every supported host.
4. *TOON Text Output Only (No `outputSchema`)*: Tools intentionally omit `outputSchema` and `structuredContent`. Every tool result is returned in a single MCP `TextContent` block (`type: "text"`) encoded in deterministic TOON (link:../hypermedia-format.adoc[Hypermedia Format Specification]). This avoids resident output-schema token overhead while optimizing token density on every turn.
5. *Zero Client-Supplied Filesystem Paths*: No workflow or service tool accepts absolute filesystem paths or worktree locations from the model. Worktrees, branches, and configuration files are resolved server-side from `plan_id` or `epic_id`.
6. *On-Demand Preloading*: For hosts configured with `schema_residency: "on_demand"` in their client profile, the user entry command preloads `pm_start`, `pm_state`, and `pm_do` so workflow execution incurs zero schema-lookup round trips.
7. *Canonical Identifiers*: Every identifier property (`plan_id`, `epic_id`, `entry_id`, `entity`, `link`, `dispatch_id`, `job_id`, `lesson_id`, `recipe_id`, `plan_slug`, `module`, skill `uri` and `section`) uses the grammar of the link:../identifiers.adoc[Identifier Registry] (`plan_id` and `epic_id`: link:../identifiers/01-general-rules-and-registry.adoc#id-plan-id[`plan_id`]; the derivation rules stay in link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]); every `pattern` below equals the registry grammar, and every example in this specification conforms to it.
8. *Model-Facing Minimality*: Every tool result and error payload, like every representation, carries only fields with an operational purpose for the model (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). Implementation variants, derivation sources, internal versions and digests, confinement, timing, and audit identifiers (outside `internal_fault` and `file_unreadable`) are recorded in `audit.jsonl`, the job record, or the metrics store and served by `pm-mcp status` or the operator CLI; `ModelFacingFieldAuditTest` checks every result record against the registry of model-facing fields.
9. *MCP Is Not the Operator or Web Surface*: The MCP endpoint `/mcp` and the Local API `/api/v1` are separate surfaces on the runtime's Unix socket (link:../runtime-model.adoc#local-api[Runtime & Interaction Model Specification, Local API]). No MCP tool, resource, or link reaches an `/api/v1` operator endpoint, the web device store, pairing, or the web server's lifecycle, and no `pm_do` argument selects one; `/mcp` is never served over TCP and never proxied by the web server (link:../cli-and-security/03-web-server.adoc#web-proxy[CLI, Coordination & Security Specification, API Proxy]).
10. *Explicit Scope on Every Scoped Tool (`NO_PLAN` Sentinel)*: `pm_state`, `pm_do`, `pm_build`, `pm_lsp`, `pm_skill`, `pm_skills`, and `pm_skill_file` require exactly one of `plan_id` or, where the tool accepts epics, `epic_id`. `plan_id` is a real plan id or the literal `NO_PLAN`, a reserved value that cannot match the `plan_id` grammar (link:../identifiers/01-general-rules-and-registry.adoc#id-plan-id[Identifier Registry, `plan_id`]) and addresses the project's workspace scope and its main checkout (workspace-addressed, `PM-ARCH-4`, resolved from the `PM-MCP-Workspace` header). A call without a scope is refused with `invalid_arguments`; no tool infers a scope from an omitted parameter, and no tool takes a `scope: "workspace"` input (the `scope` enum stays in returned representations). The sentinel mirrors `plan-marshall`'s `NO_PLAN` convention, applied to every scoped tool.

== Core Workflow Tool Schemas (`pm_start`, `pm_state`, `pm_do`)
_See Requirement link:../../Requirements.adoc#PM-TOOL-1[PM-TOOL-1: Core Workflow Verb Set (pm_start, pm_state, pm_do)]_

=== `pm_start` — Initialize a Plan Scope
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-2[PM-WATCH-STORE-2]_

Creates a new plan directory from exactly one of the six supported initialization sources (`request`, `issue_number`, `lesson_id`, `recipe_id`, `local_changes`, or `pr_number`) following a plan-mode `pm-mcp enter` invocation, consumes the pending entry record `<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>.json` whose `entry_id` that invocation printed, in the plan initialization transaction: its session row becomes the first row of the new plan's session log `plans/<plan_id>/sessions.jsonl` of the same per-project machine store and the pending file is deleted (link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]), initializes `mcp/status.json`, and returns the initial TOON hypermedia representation. Concurrent entries for different new plans therefore never share a slot. Epic membership has one carrier, `origin.epic_id` of the plan's `mcp/status.json`, which `pm_start` fills from the consumed pending entry record's `from_epic` (written by the emitted `pm-mcp enter … --from-epic <epic_id>` command); the tool has no epic parameter. With source `issue`, `pm_start` fetches the issue itself before it creates anything: a bounded provider read (`ci.issue-view` through the enrolled provider module) whose title and body pass the untrusted-ingestion validator (link:../dispatch-and-effort/03-escalation-roles-readers.adoc#_reader_agent_family_execution_context_reader[Dispatch & Effort Specification, Reader Agent Family]); no state waits for the fetch, and an issue that cannot be read refuses the start with `issue_unavailable`, because a plan that cannot read its own request is never created. With source `lesson`, `pm_start` claims the lesson in the same transaction (link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record, Claim]); an unavailable lesson refuses the start. When the new `plan_id` equals a `launched` queue row of an epic and `from_epic` is absent or names another epic, `pm_start` is refused with `epic_pointer_mismatch` (link:../dispatch-and-effort.adoc[Dispatch & Effort Specification], Single Epic Pointer). Parameter names follow the `<entity>_id` naming rule of the link:../identifiers.adoc[Identifier Registry] (`plan_slug`, `epic_id`, `plan_id`); this is a PM-MCP rule and deliberately differs from `plan-marshall`'s proposed ADR-023, which names the epic with the bare entity noun (`--epic`).

[#pm-start-refusal]
==== `pm_start` Refusals

A refused `pm_start` (`plan_id_taken`, `epic_pointer_mismatch`, `no_local_changes`, `capability_missing`, `integration_variant_unset`, `config_dirty`, `config_invalid`, `format_outdated`, `format_newer`, `lesson_unavailable`, `issue_unavailable`, or `recipe_params_invalid`) creates no plan and returns `isError: false` with a scope-less representation: `scope: none`, no `state`, a `rejected` block (`link: pm_start`, closed `reason`, `detail`), `facts` with the server-computed alternatives, and `links[0]` (without a scope there is no `pm_do`). For `plan_id_taken`, `facts` names the existing `plan_id` and where it exists (live or archived) and a free alternative `plan_slug` derived by the server; for `epic_pointer_mismatch`, it names the epic whose `launched` row matched; for `no_local_changes`, it names the base branch the capture compared against; for `capability_missing`, it names the `reason` (`head_not_writable`: the agent identity cannot push to the head branch of the pull request named by `pr_number`, for example a fork) and the pull request; for `integration_variant_unset`, it names the undecided integrations and the operator command that decides them; for `config_dirty`, it names the porcelain state of the dirty files under `.marshall/config/` and the operator's two resolutions (commit or restore); for `config_invalid`, `format_outdated`, and `format_newer`, it names the file and the finding; for `issue_unavailable`, `detail` names the reason (`not_found`: the provider reports no such issue; `not_readable`: the issue exists but its content cannot be read or fails the ingestion validator; `provider_unavailable`: the provider did not answer within the bounded read); for `recipe_params_invalid`, `detail` names the offending parameter. The pending entry record `<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>.json` is consumed only by a successful `pm_start`; after a refusal it stays in place, so a retry with a corrected `plan_slug` uses the same `entry_id`, and an abandoned record is removed by the runtime's pending-record sweep.

=== `pm_state` — Query Authoritative Hypermedia State

Returns the current hypermedia representation (`state`, `summary`, `skill` URI, domain `facts`, and valid `links`) for a `plan_id`, an `epic_id`, or the project's workspace scope (`plan_id: "NO_PLAN"`, resolved from the `PM-MCP-Workspace` header, `PM-ARCH-4`; it hosts `project-setup`). When `entity` (and optional `scope: "entity"`) is supplied by a dispatched sub-agent, returns the leaf-scoped representation for that entity (e.g., task envelope `envelope-2` or finding `F-12`) and claims `dispatch_id` if provided.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_state",
  "description": "Return the current TOON hypermedia representation and valid links for a plan, epic, the project workspace, or a sub-agent entity.",
  "type": "object",
  "properties": {
    "scope": {
      "type": "string",
      "enum": ["plan", "epic", "entity"],
      "description": "Optional explicit scope discriminator (inferred from plan_id/epic_id/entity when omitted)."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^([a-z0-9][a-z0-9-]{1,62}[a-z0-9]|NO_PLAN)$",
      "description": "Identifier of the target plan scope, or the literal NO_PLAN for the project's workspace scope. Exactly one of plan_id or epic_id is required (server-enforced)."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target orchestrator epic scope. Mutually exclusive with plan_id."
    },
    "entity": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$",
      "description": "Optional entity identifier within the plan or epic (e.g., 'envelope-1', 'F-12') for sub-agent scope."
    },
    "dispatch_id": {
      "type": "string",
      "pattern": "^dsp-[0-9]{4}-[0-9a-f]{6}$",
      "description": "Optional dispatch tracking identifier supplied by a dispatched sub-agent on its initial call."
    }
  },
  "additionalProperties": false
}
----

NOTE: Companion discovery tools `pm_plans` (zero-argument, `{"type": "object", "properties": {}, "additionalProperties": false}`) and `pm_epics` (one optional boolean `include_archived`, default `false`, `additionalProperties: false`) return a tabular TOON listing of active plans or epics in the enrolled workspace; `pm_epics` with `include_archived` also lists archived epics (`.marshall/archived-orchestrators/`, link:../filesystem-layout.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]) with their archival date. Both always return a `coverage` table with one row per scanned root (`root`, `exists`, `listed`, `entries_scanned`, `unreadable`), so zero rows are distinguishable from a root that was absent or not scanned. Each listing carries a `last_entered` column that marks one scope (`PM-CLIENT-6`): the scope whose session log (link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]) holds the most recent row with the `client_session_id` that the request's `PM-MCP-Client-Session` header carries (link:../runtime-model.adoc[Runtime & Interaction Model Specification], Connection Metadata); when the request carries no session identifier or no row matches it, the scope with the most recent session row (`last_seen_at`) in the project's workspace. This is the post-compaction scope pointer on hosts without session lifecycle hooks (link:../client-profiles/02-placeholders-and-detection.adoc#session-lifecycle-hook[Client Profiles Specification, Session Lifecycle Hook & Scope Pointer]).

[#question-waiver-facts]
==== Question Records & Waiver Requests in Representations

`pm_state` and every `pm_do` result render open question records and waiver requests only as far as the model acts on them (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]); the records themselves are served by the resources `pm://plan/{plan_id}/questions` and `pm://plan/{plan_id}/waivers` (xref:03-resource-uris.adoc#_normative_resource_uri_templates[Resource URI Surface]) and by `pm-mcp status`:

* *Question state, `session` delivery*: `facts.questions` lists each open record the model must relay, with `question_id`, `question_text`, `default_assumption`, and its options `{branch_key, label, description, recommended}`; the state offers `answer_questions` (link:../hypermedia-format/01-representation-and-link-forms.adoc#question-waiver-and-exit-links[Hypermedia Format Specification, Question, Waiver-Request & Exit Links]) and is a continuation stop point.
* *Question state, `elicitation` or `web` delivery*: `facts.questions` lists only `question_id` and `delivery`; the server asks the human itself, and the state offers `wait:question:<question_id>`.
* *Question state, `questions.mode: model`*: `facts.questions` renders the full record as for `session`, and the state offers `answer_questions`, whose answers carry the model's `confidence`; below the compiled threshold the record falls through to `auto` delivery.
* *Waiver wait*: the remediation unit's server-side waiver-wait state renders `facts.waiver_request` (`gate`, the closed gate identifier) and the waiver hint in `facts.operator_command` (link:../hypermedia-format/01-representation-and-link-forms.adoc#operator-command-relay[Hypermedia Format Specification, Operator Commands]), which the model relays as information and never answers; the state offers only its implicit `wait:` and `cancel:` links.

Deadlines, delivery resolution, channels of past answers, waiver consumptions, and the operator identity are recorded, never rendered. Answered questions reach the model only through their effect (an amendment, the next state) and, for a re-dispatched task envelope, as the answer in the envelope's `facts`.

==== Two-Stage Schema Validation for `pm_do`

1. *Stage 1 (Tool Argument Validation)*: The server's own argument validator (plain Java over the flat schema and the rules stated in the property descriptions; no JSON Schema library) checks the payload: `additionalProperties: false`, valid `plan_id`/`epic_id`, exactly one scope, syntactic `link` pattern, `args` is a JSON object. A violation is a tool execution error: `isError: true`, `error_code: invalid_arguments`, the offending `parameter`, and the violated `rule` (xref:04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)]). The Quarkus MCP server runs with `quarkus.mcp.server.tools.input-validation-error=TOOL`, so its own parameter binding reports the same way.
2. *Stage 2 (Workflow Engine Link Schema)*: Under the scope's exclusive lock, the engine resolves the active `LinkSpec` for `link` in the current state and validates `args` against the link's dynamically derived closed JSON Schema (`additionalProperties: false`, exact required free parameter keys, closed enum values, string length bounds, and integer ranges). If `args` fails Stage 2 validation or `link` is not offered in the current state, the engine returns `isError: false` with a structured `rejected` block and the fresh representation (see xref:04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)]).
