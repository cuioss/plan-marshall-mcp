=== Architectural Constraints
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-13[PM-WATCH-TOOL-13]_

1. *Small, Stable Verb Set*: PM-MCP exposes a fixed set of top-level MCP tools (`pm_state`, `pm_do`, `pm_wait`, `pm_plans`, `pm_epics`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`) rather than one tool per workflow step or script; no tool creates a scope (<<bootstrap-entries>>). Each connection sees a fixed subset: the entry session the session surface, a worker the `PM-MCP` tools its role artifact names, within the set its role's class allows (<<session-and-worker-surfaces>>). Across all phases and domains these subsets stay constant, and privileged operator actions are strictly excluded from the MCP tool surface (`PM-SEC-3`). The only additional tools are the operator-allowlisted upstream pass-through tools of the session surface (xref:02-service-and-skill-tools.adoc#_selective_upstream_mcp_proxy_meta_provenance_pm_svc_3[Selective Upstream MCP Proxy & `_meta` Provenance (`PM-SVC-3`)]), which change only with the operator's allowlist and are never part of the core set. The set has no exception: no tool runs `plan-marshall` scripts (xref:02-service-and-skill-tools.adoc#no-script-execution[No Script Execution Surface]).
2. *Portable Naming Convention*: Every core tool name conforms to the link:../identifiers/02-registry-stores-to-web.adoc#id-core-tool-name[core tool name grammar] and every upstream pass-through tool name to the link:../identifiers/02-registry-stores-to-web.adoc#id-upstream-tool-name[upstream tool name grammar] (Identifier Registry), ensuring identical identifiers across Claude Code, OpenCode, Antigravity, Codex, and raw model tool-calling APIs without escaping or translation.
3. *Closed, Host-Portable Flat Schemas*: Every tool `inputSchema` conforms to JSON Schema Draft 2020-12 and declares `"additionalProperties": false` at the top-level object boundary. It uses only the subset every supported host and provider API accepts: a top-level `type: object` with `properties`, `required` (only parameters that are always required), and `additionalProperties`; per property `type`, `enum`, `pattern` without lookaround, `minimum`/`maximum`, `minLength`/`maxLength`, `default`, and `description`. Top-level `oneOf`/`anyOf`/`allOf`, `if`/`then`/`else`, `not`, and `const` are never used; the `$schema` and `title` members shown in this specification are documentation only and are not sent in `tools/list`. Rules the subset cannot express (mutually exclusive scope parameters, per-operation required parameters, path shape) are enforced by the server's argument validation and answered with the closed error of xref:04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)]; each such rule is stated in one line of the affected property's `description`. Milestone 0 verifies the final schemas by registering and calling them on every supported host.
4. *TOON Text Output Only (No `outputSchema`)*: Tools intentionally omit `outputSchema` and `structuredContent`. Every tool result is returned in a single MCP `TextContent` block (`type: "text"`) encoded in deterministic TOON (link:../hypermedia-format.adoc[Hypermedia Format Specification]). This avoids resident output-schema token overhead while optimizing token density on every turn.
5. *Zero Client-Supplied Filesystem Paths*: No workflow or service tool accepts absolute filesystem paths or worktree locations from the model. Worktrees, branches, and configuration files are resolved server-side from `plan_id` or `epic_id`.
6. *Tool Loading*: A worker's launch loads the tools of its role artifact directly, with no deferred tool loading (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]). On hosts configured with `schema_residency: "on_demand"` in their client profile, the entry commands preload `pm_state` and `pm_do`. No other preload rule exists.
7. *No Identity Arguments*: No tool schema declares an identity, role, or generation argument. The identity, role, and generation of the caller come from its connection (the job token and the relay's headers, link:../runtime-model/03-relay.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]); the relay hides any such argument from the schemas the host sees and never forwards one a model invents (link:../runtime-model/03-relay.adoc#relay-rules[Runtime & Interaction Model Specification, Relay Rules]).
8. *Canonical Identifiers*: Every identifier property (`plan_id`, `epic_id`, `entity` including an `entry_id`, `link`, `job_id`, `module`, skill `uri` and `section`) and every identifier in link `args` (`lesson_id`, recipe key, `plan_slug`) uses the grammar of the link:../identifiers.adoc[Identifier Registry] (`plan_id` and `epic_id`: link:../identifiers/01-general-rules-and-registry.adoc#id-plan-id[`plan_id`]; the derivation rules stay in link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]); every `pattern` below equals the registry grammar, and every example in this specification conforms to it.
9. *Model-Facing Minimality*: Every tool result and error payload, like every representation, carries only fields with an operational purpose for the model (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). Implementation variants, derivation sources, internal versions and digests, confinement, timing, leases, generations, and audit identifiers (outside `internal_fault` and `file_unreadable`) are recorded in `audit.jsonl`, the job record, the queue task record, or the metrics store and served by the operator surfaces (`pm-operator status`, the web app); `ModelFacingFieldAuditTest` checks every result record against the registry of model-facing fields.
10. *MCP Is Not the Operator or Web Surface*: The MCP endpoint `/mcp` and the Local API `/api/v1` are separate surfaces on the runtime's Unix socket (link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]). No MCP tool, resource, or link reaches an `/api/v1` operator endpoint, the web device store, pairing, or the web access settings (`pm-operator web enable|disable`), and no `pm_do` argument selects one; `/mcp` is never served over TCP: the TCP listener the runtime opens while web access is enabled routes only the web app and `/api/v1/`, and never accepts the runtime token (link:../cli-and-security/03-web-server.adoc#web-listener[CLI, Coordination & Security Specification, Listener Exposure]).
11. *Explicit Scope on Every Scoped Tool (`NO_PLAN` Sentinel)*: `pm_state`, `pm_do`, `pm_build`, `pm_lsp`, `pm_skill`, `pm_skills`, and `pm_skill_file` require exactly one of `plan_id` or, where the tool accepts epics, `epic_id`. `plan_id` is a real plan id or the literal `NO_PLAN`, a reserved value that cannot match the `plan_id` grammar (link:../identifiers/01-general-rules-and-registry.adoc#id-plan-id[Identifier Registry, `plan_id`]) and addresses the project's workspace scope and its main checkout (workspace-addressed, `PM-ARCH-4`, resolved from the `PM-MCP-Workspace` header). A call without a scope is refused with `invalid_arguments`; no tool infers a scope from an omitted parameter, and no tool takes a `scope: "workspace"` input (the `scope` enum stays in returned representations). Under `NO_PLAN`, `pm_state` and `pm_do` with `entity` address a bootstrap entry by its `entry_id` (<<bootstrap-entries>>). `pm_wait` takes no scope: its offers name the scope and entity of the task. The sentinel mirrors `plan-marshall`'s `NO_PLAN` convention, applied to every scoped tool.

[#bootstrap-entries]
=== Bootstrap Entries: Scope Creation Without a Creation Tool
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-2[PM-WATCH-STORE-2]_

No tool creates a scope. A plan or an epic is created by the bootstrap sub-workflow of its kind (`bootstrap-plan`, `bootstrap-epic`; link:../state-catalogue.adoc[State Catalogue], Bootstrap), a compiled-only entity unit hosted by the project's workspace scope. `pm-mcp enter` opens one for every `plan` or `epic` entry that names no live scope: the runtime writes the pending entry record `<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>.json` (link:../store-schemas/01-format-and-session-log.adoc#pending-entry-record[Store Schemas Specification, Pending Entry Record]), which holds the bootstrap's state, and `pm-mcp enter` prints `entry: <entry_id>` (link:../cli-and-security/01-cli-and-installer.adoc#_entry_identity_recording_pm_mcp_enter[CLI, Coordination & Security Specification, Entry Identity Recording]). The entry session addresses the entry with the ordinary verbs and the `entry_id` as entity of the workspace scope: `pm_state(plan_id: "NO_PLAN", entity: "<entry_id>")` and `pm_do(plan_id: "NO_PLAN", entity: "<entry_id>", link, args)`. Concurrent entries never share a state position, and nothing is created under `plans/` or `epics/` before the commit, so an abandoned entry leaves no scope; the pending-record sweep removes it (link:../runtime-model/02-startup-recovery-drain.adoc#periodic-sweep[Runtime & Interaction Model Specification, Periodic Sweep]).

* *Ways to start are links*: What to work on is chosen through the links of the bootstrap (`start.choose`, the server-listed candidates in `facts`, the full lists in `pm://workspace/lessons` and `pm://workspace/recipes`, xref:03-resource-uris.adoc#_normative_resource_uri_templates[Resource URI Surface]); each source is a sub-workflow unit (`source-issue`, `source-lesson`, `source-recipe`, `source-pr`, `source-local-changes`) that ends `done` with its source record or steps out. The user's words reach the server as the entry's free-text hint and as link `args` (request text, issue or pull request number, `lesson_id`, recipe key and `recipe_params`, `plan_slug`, posture, `review_outline`, base branch), each validated against the link's closed parameter schema (<<_two_stage_schema_validation_for_pm_do>>, Stage 2). No tool parameter and no CLI flag enumerates sources: a new way to start is one more unit and one more link.
* *Plans of an epic*: The runtime creates a plan of an epic itself, without a session, by running the plan bootstrap with the source unit `source-epic-row` for a launchable queue row of the epic (link:../model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]); no session offers this source.
* *Commit in the `start.create-scope` transaction*: When the bootstrap commits (the `create` link of `start.ready` or `start-epic.ready`, whose primitive `start.create-scope` returns `created`, entering the terminal `start.committed` or `start-epic.committed`, or `refused{reason}`, returning to the ready state), the engine creates the scope from the gathered record in that transaction: it consumes the pending entry record (its entry row becomes the first row of the new scope's session log `plans/<plan_id>/sessions.jsonl` or `epics/<epic_id>/sessions.jsonl` and the pending file is deleted, link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]), composes and checks the scope's plan instance or epic workflow (every role it names must be defined, `role_undefined`, and every skill its `skill` clauses name must resolve, `skill_unresolved`), initializes `mcp/status.json`, claims a lesson source (link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record, Claim]), takes the local-changes snapshot, and re-observes a pull request's head. For an epic row, the same transaction binds the plan to its row (`origin.epic_id`) and sets the row `running`. The `pm_do` call that commits returns the terminal bootstrap representation naming the new scope; from there the runtime drives the scope, and the entry session views it with `pm_state`. A later call naming the consumed or swept `entry_id` is answered `scope_not_found`.
* *Epic adoption*: An `epic` entry whose id names an existing git-tracked ledger (`.marshall/orchestrator/<epic_id>/` with `epic.json`) without machine scope is adopted (`adopt_epic:<epic_id>`, or directly for a requested id): the adoption's `start.create-scope` transaction (outcome `adopted`) consumes the pending entry record as above and creates only the machine scope from the ledger, which it never rewrites (link:../state-catalogue/09-bootstrap-and-lessons.adoc#state-start-epic.adopt[State Catalogue, `start-epic.adopt`]).
* *Epic membership*: A plan whose `plan_id` equals a non-terminal queue row of an epic is created only by the runtime's launch of that row; a session entry deriving that `plan_id` is not committed (`epic_pointer_mismatch`, <<bootstrap-commit-recheck>>).

[#bootstrap-commit-recheck]
==== Bootstrap Commit Re-Check
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-15[PM-WATCH-TOOL-15]_
The checks the bootstrap made while gathering can be invalidated before the commit (a concurrent plan takes the identifier, the operator releases the project, a team file or a role set is edited). The `start.create-scope` transaction therefore re-checks them under the workspace lock; a failing check creates nothing, keeps the pending entry record, and returns the entry to `start.ready` with `facts.commit_refused` (`reason`, `detail`) and the server-computed alternatives, so the entry session corrects the input (a new `plan_slug`) or relays the named operator command and commits again. For a plan of an epic, the runtime records the refusal on the epic's queue row and launches nothing (link:../model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]). The closed reasons:

[cols="1,3"]
|===
|`reason` |Check and `facts`

|`plan_id_taken`
|The derived `plan_id` (or `epic_id`) names a live or archived scope, or (`epic_id`) an existing ledger, which is adopted instead of re-created (link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]); `facts` name where it exists and a free alternative slug. An archived identifier is never reused.

|`lifecycle_closed`
|The plan lifecycle is not offered in the project: the lifecycle gate, a compiled constant of the release, is closed and the project is not enrolled as a pilot (`pm-operator enrol --pilot`), or the project was released (link:../cli-and-security/02-credentials-and-operator.adoc#enrolment-lifecycle-release[CLI, Coordination & Security Specification, Enrolment, Lifecycle Gate & Release]).

|`config_dirty`
|A file under `.marshall/config/` (a team file or a workflow unit) is modified, staged, or untracked in the main checkout; `facts` name the porcelain state and the resolutions (commit or restore; after a stepped-out setup commit, `retry` of `setup.commit-changes`). A local-changes source is exempt: the file is then part of the captured change set.

|`config_invalid`, `format_outdated`, `format_newer`
|A team configuration file or a project workflow unit fails validation or has an unsupported `format_version` (xref:04-errors-and-testing.adoc#rejection-reasons[Closed Rejection Reasons]); `facts` name the file and the finding.

|`role_undefined`
|The plan instance or epic workflow composed for the commit names a role that the effective role set does not define, or whose artifact is invalid (`PM-WORK-1`, link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]); `facts` name the role, the state that names it, and the operator command that shows the role set (`pm-operator roles list`).

|`skill_unresolved`
|The plan instance or epic workflow composed for the commit has a `skill` clause naming a skill that does not resolve in the project's skill catalogue (absent, or an extension skill that is missing or refused; `PM-SKILL-5`, link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Rule 14]); `facts` name the skill and the state that names it.

|`integration_variant_unset`
|An integration whose used features the `native` variant cannot serve has no operator choice of its variant; `facts` name the integrations and the operator command.

|`lesson_unavailable`
|The source lesson was claimed by another plan, retired, or no longer resolves `found` since `source-lesson` checked it; `facts` name its state.

|`no_local_changes`
|The local-changes snapshot taken at commit is empty (no dirty or staged path, no commit ahead of the base branch); `facts` name the base branch.

|`pr_not_open`, `head_not_writable`
|The re-observed pull request is no longer open, or its head branch can no longer be pushed to by the agent identity; `facts` name the pull request.

|`epic_pointer_mismatch`
|A session entry derives a `plan_id` that equals a non-terminal queue row of an epic; `facts` name the epic and the row. A refused server start of a row is no tool error: it marks the row `held` (link:../model-work/08-epic-coordination.adoc#server-started-plans[Model Work Specification, Server-Started Plans]).
|===

The re-check is a transition of the bootstrap, not a rejection: the `pm_do` result is `isError: false` without a `rejected` block. Its reasons belong to the failure class `precondition` and, since no plan exists, are recorded in the audit log only and never counted per plan (xref:04-errors-and-testing.adoc#rejection-reasons[Closed Rejection Reasons & Failure Classes]). Parameter names follow the `<entity>_id` naming rule of the link:../identifiers.adoc[Identifier Registry] (`plan_slug`, `epic_id`, `plan_id`); this is a PM-MCP rule and deliberately differs from `plan-marshall`'s proposed ADR-023, which names the epic with the bare entity noun (`--epic`).

=== `pm_state` — Query Authoritative Hypermedia State

Returns the current hypermedia representation (`state`, `summary`, `skill` URI, domain `facts`, and valid `links`) for a `plan_id`, an `epic_id`, or the project's workspace scope (`plan_id: "NO_PLAN"`, resolved from the `PM-MCP-Workspace` header, `PM-ARCH-4`; it hosts `project-setup`). A plan or epic representation is a view whose only links are the answer links of its open question records (link:../hypermedia-format/01-representation-and-link-forms.adoc[Hypermedia Format Specification]). When `entity` (and optional `scope: "entity"`) is supplied, returns the entity-scoped representation: within a plan or epic a task entity (e.g., task envelope `envelope-2` or finding `F-12`; on a worker connection only an entity leased to its generation, <<job-bound-connections>>), under `NO_PLAN` a bootstrap entry by its `entry_id` (<<bootstrap-entries>>).

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_state",
  "description": "Return the current TOON hypermedia representation and valid links for a plan, epic, the project workspace, a task entity, or a bootstrap entry.",
  "type": "object",
  "properties": {
    "scope": {
      "type": "string",
      "enum": ["plan", "epic", "entity"],
      "description": "Optional explicit scope discriminator (inferred from plan_id/epic_id/entity when omitted)."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^([a-z0-9][a-z0-9-]{1,62}[a-z0-9]|NO_PLAN)$",
      "description": "Identifier of the target plan scope, or the literal NO_PLAN for the project's workspace scope. Exactly one of plan_id or epic_id is required (server-enforced)."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target orchestrator epic scope. Mutually exclusive with plan_id."
    },
    "entity": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$",
      "description": "Optional entity identifier: a task entity as its offer names it, such as 'envelope-1', 'F-12', 'enrich-core', or a consultation_id (a worker may name only an entity offered to it, server-enforced); with plan_id NO_PLAN also the entry_id printed by 'pm-mcp enter'."
    }
  },
  "additionalProperties": false
}
----

NOTE: Companion discovery tools of the session surface `pm_plans` (zero-argument, `{"type": "object", "properties": {}, "additionalProperties": false}`) and `pm_epics` (one optional boolean `include_archived`, default `false`, `additionalProperties: false`) return a tabular TOON listing of active plans or epics in the enrolled workspace, one line each with its state and summary; `pm_epics` with `include_archived` also lists archived epics (`.marshall/archived-orchestrators/`, link:../filesystem-layout/03-project-store.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]) with their archival date. Both always return a `coverage` table with one row per scanned root (`root`, `exists`, `listed`, `entries_scanned`, `unreadable`), so zero rows are distinguishable from a root that was absent or not scanned.

[#question-waiver-facts]
==== Question Records & Waiver Requests in Representations

`pm_state` and every `pm_do` result render open question records and waiver requests only as far as the caller acts on them (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]); the records themselves are served by the resources `pm://plan/{plan_id}/questions` (`pm://workspace/questions` for the workspace scope) and `pm://plan/{plan_id}/waivers` (xref:03-resource-uris.adoc#_normative_resource_uri_templates[Resource URI Surface]), by the web app, and by `pm-operator status`:

* *Open question, entry session*: A view of a plan or epic and a question state of a session-driven unit render `facts.questions` for each open record once it is delivered (`question_id`, `question_text`, `decision_kind`, `default_assumption`, `recommendation_confidence`, `rationale`, the set's `score`, its options `{branch_key, label, description, recommended}`, and for a set the adjudication escalated `votes[]` with each listed role's `role`, `branch_key`, `confidence`, and `rationale`) with one answer link `answer:<question_id>` per record (link:../hypermedia-format/01-representation-and-link-forms.adoc#question-waiver-and-exit-links[Hypermedia Format Specification, Task, Answer, Waiver-Request & Exit Links]); the session relays the user's choice. The same records are shown in the web app, the dependable channel; the first valid answer wins. No representation is a stop point: the runtime owns the record's deadline and default (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]).
* *Open question, `questions.mode: quorum`*: While the adjudication runs, the set's records are not rendered; a listed role votes through the links of its own task entity, blind to the recommendation (link:../model-work/10-decision-quorum.adoc#adjudication[Model Work Specification, Ask or Quorum]), and a set it does not decide is rendered as above.
* *Setup and bootstrap choices*: The states of the project setup and the bootstraps offer their choices as links, which the entry session follows after relaying the user's choice, or asks through elicitation where the connection supports it (link:../runtime-model/04-sessions-and-workers.adoc#_connection_scoped_rendering[Runtime & Interaction Model Specification, Connection-Scoped Rendering]).
* *Waiver wait*: A view of a plan in the server-side waiver wait of a remediation unit renders `facts.waiver_request` (`gate`, the closed gate identifier) and the waiver hint in `facts.operator_command` (link:../hypermedia-format/01-representation-and-link-forms.adoc#operator-command-relay[Hypermedia Format Specification, Operator Commands]), which the entry session relays as information and never answers; the wait itself is an engine event and offers no link.

Deadlines, the channels of past answers, waiver consumptions, and the operator identity are recorded, never rendered. Answered questions reach a worker only through their effect (an amendment, the next state) and, for the task envelope served after an asking envelope, as the answer in the envelope's `facts`.

=== `pm_do` — Follow a Hypermedia Link
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-1[PM-WATCH-TOOL-1]_

The sole state transition verb in PM-MCP. Executes the transition identified by `link` from the current representation of `plan_id`, `epic_id`, or the workspace scope (`plan_id: "NO_PLAN"`), passing any judgment parameters in `args`. Its links are those of the bootstraps, the project setup, the answer links, and, while it takes tasks, the links of task entities leased to its generation for the entry session, and those of the leased task entities for a worker (the acknowledgement `ack` and the `consult:<role>` links included). No link waits on or cancels a job: waiting on a job and cancelling it are engine events (`PM-WF-8`).

[source,json]
----

==== Two-Stage Schema Validation for `pm_do`

1. *Stage 1 (Tool Argument Validation)*: The server's own argument validator (plain Java over the flat schema and the rules stated in the property descriptions; no JSON Schema library) checks the payload: `additionalProperties: false`, valid `plan_id`/`epic_id`, exactly one scope, syntactic `link` pattern, `args` is a JSON object. A violation is a tool execution error: `isError: true`, `error_code: invalid_arguments`, the offending `parameter`, and the violated `rule` (xref:04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)]). The Quarkus MCP server runs with `quarkus.mcp.server.tools.input-validation-error=TOOL`, so its own parameter binding reports the same way.
2. *Stage 2 (Workflow Engine Link Schema)*: Under the scope's exclusive lock, the engine resolves the active `LinkSpec` for `link` in the current state and validates `args` against the link's dynamically derived closed JSON Schema (`additionalProperties: false`, exact required free parameter keys, closed enum values, string length bounds, and integer ranges); on a task entity it also checks the lease and the generation (`PM-WORK-2`). If `args` fails Stage 2 validation or `link` is not offered in the current state, the engine returns `isError: false` with a structured `rejected` block and the fresh representation (see xref:04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)]). A submit that misses a required reference (for example to a consultation it made) is refused this way with a reason the worker can act on.

[#pm-wait]
=== `pm_wait` — Receive a Task
_See Requirement link:../../Requirements.adoc#PM-WORK-2[PM-WORK-2: Task Protocol]_

_See Requirement link:../../Requirements.adoc#PM-IMPL-4[PM-IMPL-4: Bounded Long-Poll & Progress-Reset Waiting Primitives]_

The only way a worker, or the entry session as an optional worker, receives work. The semantics (offer, lease, acknowledgement, the task's states and outcomes, fencing, consultation answers) are those of the task protocol (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]); this section defines the tool.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_wait",
  "description": "Wait for the next task. Answers with an offered task, with wait_again, or with end. Call it again after wait_again and after each submitted task.",
  "type": "object",
  "properties": {},
  "additionalProperties": false
}
----

* *No arguments*: `pm_wait` takes no scope and no identity argument. The caller's identity, role, and generation come from its connection (link:../runtime-model/03-relay.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]); a call with any argument is refused with `invalid_arguments`.
* *Bounded*: The call blocks at most the bounded wait of the caller's host (`connection.bounded_wait_seconds` of its client profile), with progress frames where the connection supplied a `progressToken` and the profile states that progress resets the host's timeout (link:../runtime-model/04-sessions-and-workers.adoc#_connection_scoped_rendering[Runtime & Interaction Model Specification, Connection-Scoped Rendering]; link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Timeouts & Budgets Specification]). It returns before the host's limit in every case.
* *Answer `offer`*: `answer: offer`, followed by the representation of the offered task entity (scope, `plan_id` or `epic_id`, `entity`, `state`, `summary`, `skill`, `facts`, and its links: while offered only `ack`), and the required skills: `skills_in_band[]{uri, section, content}` for the skills this generation has not received yet, and `skills_named[]{uri, sha256}` for the others (link:../model-work/04-worker-launch.adoc[Model Work Specification, Skill Delivery]). The task is leased to the caller's generation when the offer is written, never before; a cancelled wait consumes no task. The answer to a consultation the caller asked arrives the same way, as the asking task with the answer in its `facts`, exactly once and only to the asking generation (link:../model-work/05-consultation.adoc[Model Work Specification, Consultation]).
* *Answer `wait_again`*: `answer: wait_again` and nothing else: the bounded wait passed without a task; the caller calls `pm_wait` again.
* *Answer `end`*: `answer: end` and nothing else: the caller ends (a fresh worker after its task, a recycled warm worker, a draining runtime, a session that is no longer offered tasks).
* *Refusals*: A call of a fenced generation is refused `generation_fenced`, a call carrying the token of an ended job `job_ended` (xref:04-errors-and-testing.adoc[Errors]). A task leased to a generation is never offered to a second concurrent `pm_wait` of the same generation.

[#job-bound-connections]
=== Worker Connections
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-16[PM-WATCH-TOOL-16]_

_See Requirement link:../../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_

Every worker is a job of kind `llm` that the runtime launches through the headless CLI of an enrolled harness (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]); the host never starts one. The worker connects back through the relay `pm-mcp serve --job`, which presents the job token and the generation instead of the runtime token (link:../runtime-model/01-processes-and-transport.adoc#job-token[Runtime & Interaction Model Specification, Local Trust: Job Token]). The runtime resolves the job from the token on every request and binds the call to its job and generation, without connection state:

* *Tool set*: The `PM-MCP` tools its role artifact names, within its class's column (<<session-and-worker-surfaces>>). `pm_plans`, `pm_epics`, `pm_skills`, and the upstream pass-through tools are never listed.
* *Resources*: `resources/list` and `resources/read` work read-only for every resource of the worker's own project and `skill://pm/…` (xref:03-resource-uris.adoc#_normative_resource_uri_templates[Resource URI Surface]). The project boundary is the only read boundary; the task binding below applies to tools, not to resources. A URI carries no project: the runtime resolves it in the worker's project, taken from the job record, so a URI that names a plan or epic of another project is the resource read error `-32002` with `error_code: scope_not_found`, as in a session (xref:04-errors-and-testing.adoc[Errors & Testing]).
* *Task binding*: The scope argument (`plan_id`, `epic_id`, or `NO_PLAN` for a workspace task) and, for `pm_state` and `pm_do`, the `entity` argument must name a task entity leased to the worker's generation, by the scope and `entity` of its offer (the scope entity such as `envelope-3`, for a consultation task its `consultation_id`; a `queue_task_id` is never passed otherwise); `pm_build` and `pm_lsp` must name the scope of such a task. Any other value is refused with `job_scope_mismatch` (`isError: true`), audited.
* *Links*: The worker's representation renders only the links of its leased task entity, and never a link whose target starts a model (the leaf rule, `PM-WF-5`); a consultation goes through the server as a `consult:<role>` link (`PM-WORK-4`). A `pm_do` naming any other link is rejected `link_not_available`. Deliverables reach the server only through the entity's `submit` links.
* *Fencing and end*: A call of a fenced generation is refused `generation_fenced`; the token is revoked with the fence or the job's fate, and a call carrying the token of an ended job is refused `job_ended` (`isError: true`).
* *No session identity*: A worker connection appends no session row, triggers no identity check, and takes its client profile from its role's harness, recorded in the job record; its audit records carry its `job_id`, role, and generation.

The entry session takes a task through the same tools, links, validation, and fencing; its connection is bound to its session generation instead of a job (link:../runtime-model/04-sessions-and-workers.adoc#_entry_session[Runtime & Interaction Model Specification, Entry Session]).
