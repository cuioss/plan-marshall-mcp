== Overview

This document specifies the technical design, process management, security controls, and output parsers for the PM-MCP **Job Runtime**. The runtime manages native host subprocesses for builds, git operations, CI command-line integrations (`gh`, `glab`), and migration script wrappers under strict operator enrolment (`PM-EXEC-1`..`PM-EXEC-5`).

== Verify-Not-Resolve Execution Pipeline

Before spawning any subprocess, the runtime validates the job request through a deterministic three-stage verification pipeline (`PM-EXEC-1`..`PM-EXEC-3`, `PM-SEC-2`):

[source,text]
----
  Job Request (Scope, Executable, Argv, WorkingDir)
                       │
                       ▼
       ┌───────────────────────────────┐
       │ 1. Working Directory Check    │ ──► Mismatch: REFUSED (outside enrolled tree)
       └───────────────┬───────────────┘
                       │ Valid (Root or linked worktree)
                       ▼
       ┌───────────────────────────────┐
       │ 2. Executable & Digest Check  │ ──► Mismatch: REFUSED (unpinned tool / digest drift)
       └───────────────┬───────────────┘
                       │ Valid (Exact path & SHA-256 match)
                       ▼
       ┌───────────────────────────────┐
       │ 3. Argument Schema Validation │ ──► Mismatch: REFUSED (illegal flag / unquoted space)
       └───────────────┬───────────────┘
                       │ Valid
                       ▼
             Spawn Subprocess (Direct)
----

* *Working Directory Confinement (`PM-SEC-2`)*: The working directory must resolve canonically via `Path.toRealPath()` to the project's enrolled root or a live linked git worktree verified via `git worktree list --porcelain`. Arbitrary paths or symlink escapes are rejected with outcome `refused`.
* *Working Directory Selection (`PM-ARCH-5`)*: Jobs for plans in Phases 1–4 and plan-less jobs run in the main checkout; jobs for plans in Phase 5 or later run in the plan's worktree root. Legacy `script` jobs thereby resolve their runtime-state root (`.plan/local`) by plan-marshall's working-directory rule (ADR-002). The legacy override `PLAN_BASE_DIR` is never set for production jobs, because plan-marshall treats it as a replacement for the main checkout's `.plan/local` and would redirect main-anchored stores (lessons, merge lock).
* *Verify-Not-Resolve Executable Resolution (`PM-EXEC-1`, `PM-EXEC-2`, `PM-EXEC-3`, `PM-EXT-5`)*: The runtime *never* searches the system `PATH`:
** *Wrapper Jobs (`mvnw`, `gradlew`, `pw`)*: The wrapper must be committed at the root of the tree, must match an enrolled wrapper name in `~/.plan-marshall/mcp/enrolments.json`, and its SHA-256 content hash must match the enrolled digest.
** *Host Tools (`git`, `gh`, `glab`, `python3`, `npm`, `npx`)*: The runtime invokes the exact absolute `executable_path` recorded in `enrolments.json` after verifying that the file's current SHA-256 matches the enrolment record.
** *Project Script Jobs (`project_script`, `PM-EXT-5`)*: Both the script file (`script_path`) and its interpreter (`interpreter_ref`) must match their enrolled SHA-256 digests in `enrolments.json -> projects.<id>.project_scripts`.
* *Argument Schema Validation (`PM-EXEC-1`, `PM-EXEC-5`)*: The argument vector (`argv`) is checked against a closed allowlist schema per tool type. Shell meta-characters (`|`, `;`, `&`, `$`, `` ` ``, `>`, `<`) are never evaluated because execution bypasses `/bin/sh` entirely.

== Subprocess Lifecycle & Process-Group Isolation

Every job runs as a direct child of the always-on `pm-mcp` runtime, independent of any host connection (link:runtime-model.adoc[Runtime & Interaction Model Specification]), inside its own isolated operating system process group (`PM-EXEC-4`, `PM-EXEC-5`, `PM-IMPL-1`).

=== Process-Group Creation via the `job-exec` Shim

Java's `ProcessBuilder` cannot place a child into a new process group or session (`setpgid`/`setsid`); a child started directly would inherit the runtime's own process group, and signalling that group would hit the runtime and every other job. The runtime therefore starts every job through a shim built into the same native binary:

. The runtime verifies the job (verify-not-resolve, `PM-EXEC-2`) and starts `pm-mcp job-exec -- <verified absolute executable> <args…>` with `ProcessBuilder`, keeping all of its I/O handling (pipes, in-memory `stdin` payloads, log redirection, exit codes).
. The shim calls `setpgid(0, 0)` via FFM, so its PID becomes the process-group ID, and then replaces itself with the target via `execve` (never `execvp`: no `PATH` search, `PM-EXEC-1`). The job's PID recorded by the runtime is therefore both the job PID and its process-group ID.
. Cancellation and timeouts signal exactly that group (`kill(-pid, …)`). Warm build daemons that detach themselves into their own session (Gradle daemon, `mvnd`) are intentionally not affected (`PM-EXEC-4`).
. `job-exec` is an internal verb: it accepts only an absolute executable path and an argument vector, performs no verification of its own, and is not part of the operator CLI.

*Alternative for later implementations*: Start jobs directly via FFM `posix_spawn` with `POSIX_SPAWN_SETPGROUP` (the mechanism already used for the detached runtime start, link:runtime-model.adoc[Runtime & Interaction Model Specification]). This removes the extra `execve` hop but replaces `ProcessBuilder` completely: pipes, `stdin` streaming, output capture, and exit-status reaping (`waitpid`) must then be implemented on FFM as well. The job contract (process group = job PID, outcome classification) is identical, so the runtime can switch implementations without changing any other specification.

[source,java]
----
List<String> argv = new ArrayList<>(List.of(pmMcpBinary, "job-exec", "--"));
argv.addAll(verifiedArgv); // verifiedArgv.get(0) is the verified absolute executable path
ProcessBuilder pb = new ProcessBuilder(argv);
pb.directory(verifiedWorkingDir.toFile());
// Environment sanitization
pb.environment().clear();
pb.environment().putAll(sanitizedEnvAllowlist);
// Standard input handling: /dev/null by default, or in-memory pipe for multi-line payloads
if (stdinPayload.isPresent()) {
    pb.redirectInput(ProcessBuilder.Redirect.PIPE);
} else {
    pb.redirectInput(ProcessBuilder.Redirect.from(new File("/dev/null")));
}
// Direct output redirection to job log file (never inherits the runtime's stdin/stdout)
pb.redirectOutput(jobLogPath.toFile());
pb.redirectErrorStream(true);
Process process = pb.start();
if (stdinPayload.isPresent()) {
    byte[] bytes = stdinPayload.get();
    Thread.startVirtualThread(() -> {
        try (OutputStream out = process.getOutputStream()) {
            out.write(bytes);
            out.flush();
        } catch (IOException ignored) {
            // Child process exited early; handled by exit-code & outcome classifier
        }
    });
}
----

=== In-Memory `stdin` Streaming vs Retired Temp-File Patterns (`PM-EXEC-5`)

When a workflow primitive passes multi-line text to an enrolled `git` or `ci` tool (`git -C <tree> commit -F -`, `gh pr create --body-file -`, `gh pr edit --body-file -`, `gh pr comment --body-file -`, `gh issue comment --body-file -`, `glab mr create`), `JobRuntime` supplies the validated UTF-8 bytes in `stdinPayload`:

* *Zero Temp or Scratch Files*: The server never writes commit messages or PR/issue bodies to `.plan/temp/{plan_id}-commit-msg.txt`, `<plan>/work/ci-bodies/`, or `/tmp/`.
* *Zero Shell / Argv Exposure*: Multi-line text is never placed in `verifiedArgv`, avoiding OS `ARG_MAX` limits and `ps` command-line inspection.
* *Deterministic EOF*: The virtual writer thread closes `process.getOutputStream()` immediately after flushing `bytes`, guaranteeing that `git` and `gh` see EOF and never hang waiting for interactive input.

=== Process Termination & Cancellation Protocol

When a job exceeds its configured timeout (`PM-EXEC-4`) or when the user/client calls `cancel`:

1. *SIGTERM Escalation*: `pm-mcp` sends `SIGTERM` to the job's process group (`kill(-pid, SIGTERM)` via Java FFM, `PM-TECH-4`), whose ID equals the job PID (see <<Process-Group Creation via the `job-exec` Shim>>).
2. *Grace Period*: `pm-mcp` waits up to 5,000 milliseconds for all processes in the group to exit cleanly.
3. *SIGKILL Cleanup*: If any process remains alive after the grace period, `pm-mcp` issues `kill(-pid, SIGKILL)` to immediately terminate the remaining process group.
4. *Closed-Enum Outcome Assignment*: Cancelled requests return `cancelled`; wall-clock timeout expirations return `timed_out`; jobs interrupted by a runtime crash or drain are recorded as `killed` (on drain, or by crash recovery at the next runtime start); relay termination never affects a job.
5. *Live Orphans after a Runtime Crash*: Each job record stores the job PID and the process start instant. At the next runtime start, a record left `running` whose process group still exists (PID and start instant match, ruling out PID reuse) is terminated with steps 1–3 and recorded as `killed`; it is never adopted or re-executed (link:runtime-model.adoc[Runtime & Interaction Model Specification], Startup Sequence).

=== Bounded Long-Poll & Progress-Reset Waiting Primitives (`PM-WF-8`, `PM-IMPL-4`)

When a workflow transition spawns a long-running `build`, `ci`, or `project_script` job, or when the model invokes `pm_build` (`PM-SVC-1`, `PM-SVC-4`):

* *Bounded Wait Slice*: The server holds the request open for at most `bounded_wait_seconds` (configured per client profile in `15s`–`3600s`, default `240s` / 4 minutes). If the job completes within the window, the server immediately evaluates the completion guard and returns the next workflow state.
* *Progress Notifications*: When the client profile supports `progress_resets_timeout == true` and supplies a `_meta.progressToken`, the job runner emits periodic `notifications/progress` frames (every 5 seconds with current build stage and elapsed time) over the calling host connection (relayed to the host by `pm-mcp serve`).
* *Non-Blocking Wait Links*: If the job is still running when `bounded_wait_seconds` elapses, the call returns a valid hypermedia state with `form: wait` (`rel: wait`) and `form: submit` (`rel: abort`) links (`PM-WF-8`), never failing with an MCP transport timeout.

=== Warm Language Server Pool & Orthogonal Service Access (`PM-SVC-2`, `PM-SVC-4`, `PM-TOOL-2`)

The Job Runtime manages a bounded pool of warm Language Server Protocol (LSP) subprocesses (`max_lsp_instances` in `machine-config.json`, default `3`) spoken via Eclipse `LSP4J` over `stdio` (`PM-TECH-2`, `PM-TECH-3`):

* *Verify-Not-Resolve Launch*: Each language server binary (`jdtls`, `pyright-langserver`, `typescript-language-server`, `rust-analyzer`, or the marketplace corpus language server) is verified against `enrolments.json -> projects.<id>.language_servers` before launch.
* *Lifecycle & Eviction*: Instances are keyed by `(workspace_root, language_id)`, initialized lazily on the first `pm_lsp` call (`PM-TOOL-2`, `PM-SVC-4`), evicted cleanly (`shutdown` -> `exit` -> `SIGTERM`) after 15 minutes of inactivity or when the runtime drains or stops, and restarted automatically (up to 2 retries) on unexpected exit.

== Linux Filesystem Confinement (Landlock)

On Linux (`PM-SEC-5`, `PM-TECH-4`), the `job-exec` shim (<<Process-Group Creation via the `job-exec` Shim>>) confines every job before `execve`:

. `prctl(PR_SET_NO_NEW_PRIVS, 1)`: the job and all its descendants can never gain privileges (setuid/setgid binaries, file capabilities).
. A Landlock ruleset (Linux >= 5.13, applied via FFM) that grants read and execute access to the whole filesystem and write access only to:
** every enrolled project root (which contains all of that project's worktrees under `.plan/local/worktrees/`),
** the build toolchain caches declared in the enrolment (for example `~/.m2/repository`, `~/.gradle`),
** `~/.plan-marshall/`,
** the system temporary directory (`/tmp`; the JVM ignores `TMPDIR` for `java.io.tmpdir`) and device nodes under `/dev`.

The ruleset is inherited across `fork`/`execve` and cannot be removed by the job. The runtime passes the writable set to the shim as an argument vector computed from `enrolments.json` at job start, so enrolment changes take effect for the next job without restarting anything.

Properties and limits:

* *Warm build daemons*: A Gradle daemon or `mvnd` started from a confined job keeps that job's ruleset. Because the ruleset covers all enrolled project roots, later builds of any enrolled project can reuse it; after enrolling a new project, the operator stops running warm daemons once so the next build starts one with the extended ruleset.
* *Container runtimes*: Docker, Docker Compose, and Testcontainers talk to the container daemon over its socket; writes performed by the daemon itself are outside the job's confinement (`PM-EXEC-4`).
* *Not covered*: Landlock does not restrict network address families and does not provide a private `/tmp`. `RestrictAddressFamilies` and `PrivateTmp` are therefore not enforced.
* *Unavailable Landlock*: On kernels without Landlock (older kernels, some WSL2 kernels), jobs run with `PR_SET_NO_NEW_PRIVS` only; the runtime records `confinement: unavailable` in each job record and in `pm-mcp status`, and this is an accepted residual platform risk (`PM-SEC-5`).

== Native Build Output Parsers

When a build completes with a non-zero exit code or compiler warnings, the runtime extracts structured diagnostics without calling external Python scripts (`PM-IMPL-6`):

[cols="1,2,2"]
|===
|Build System |Parser Strategy |Diagnostic Extractions

|*Maven*
|Regex stream scanner for `\[ERROR\]` lines and compiler plugin reports (`javac`, `maven-compiler-plugin`).
|File path, line number, column number, error message, compiler diagnostic code.

|*Gradle*
|Scanner for `e: <path>:(line, col): <message>` Kotlin/Java errors and Gradle task execution failures.
|Task name, source file, line/col, stack summary.

|*npm / ESLint*
|Direct structured JSON parser when invoked with `--format json` or regex parser over standard TAP/Unix lint stream.
|Rule ID, severity (`error`/`warning`), file path, line/col, repair message.

|*Python / Pytest*
|JUnit XML / Cobertura report parser or regex scanner over standard traceback blocks.
|Test class, test method, failure type, file path, line number, failure diff.
|===

=== Unparseable Output Fallback (`failed_unparsed`)

If a build fails (exit code != 0) but the output parser cannot extract any structured diagnostic errors:

* The job outcome is classified as `failed_unparsed` (never folded into normal `failed`).
* The full raw log is preserved at `~/.plan-marshall/mcp/logs/jobs/<job_id>.log`.
* The representation embeds the bounded raw-log tail (last 50 lines, capped at 4 KB, secrets redacted) and the resource URI `pm://plan/{plan_id}/builds/{job_id}/log`, plus an `escalate` link, preventing the model from hallucinating non-existent compiler errors.

== Adaptive Build Timeouts, Coverage Parsers & Gate Honesty (`PM-EXEC-6`)

=== Adaptive Timeout Learning

`pm-mcp` persists observed execution durations in one machine-level store, `~/.plan-marshall/mcp/state/build-timings.json`, keyed by project (the enrolled project root) and canonical command (build system, canonical verb, module, and sorted profiles); there is no project-local timeout store:

* *Baseline Update Rule*: Upon each completed run (any exit code; never `killed`/`cancelled`) with duration $d$, the learned baseline $L$ updates via $L_{\text{new}} = \lfloor 0.8 \times \max(L_{\text{old}}, d) + 0.2 \times \min(L_{\text{old}}, d) \rfloor$ (first observation stored raw); a `timed_out` run feeds $d = \min(2 \times \text{timeout}, 1800)$.
* *Timeout Allocation*: The job timeout is set to $\max(\text{engine\_floor}, \lfloor 1.25 \times L \rfloor)$ (default `300s` when unlearned), where $\text{engine\_floor}$ is `300s` for Maven/Gradle/npm and `330s` for pytest.
* *One-Time Import*: At machine cutover, and when a project is first enrolled after cutover, the learned values in that project's legacy `.plan/local/run-configuration.json` (`commands["<tool>:<key>"].timeout_seconds`) are imported once as initial baselines, never overwriting an existing entry; the import is a `PM-MIG-3` store conversion with a reverse converter for rollback (see link:domain-extensions.adoc[Domain Extensions Specification]).

=== Native Coverage Report Parsers

The build runtime parses coverage artifacts natively after test execution to evaluate threshold compliance:

* *JaCoCo (`jacoco.xml`)*: StAX XML reader extracting `INSTRUCTION`, `BRANCH`, and `LINE` counters per package, class, and source file.
* *Cobertura (`coverage.xml`)*: StAX XML reader extracting `line-rate` and `branch-rate` per module and file.
* *LCOV (`lcov.info`)*: Line-oriented parser over `SF:`, `DA:`, `LF:`, `LH:`, `BRF:`, `BRH:` records.
* *Istanbul (`coverage-summary.json`)*: Jackson streaming reader extracting `lines`, `statements`, `functions`, and `branches` percentages.

=== Gate Honesty Verification

Before marking a module or pre-push quality gate as `fresh` in `change-ledger.jsonl` (`PM-SVC-1`), the runtime verifies three honesty predicates:

1. *Examined Population*: The set of modules and source files actually compiled and tested in the build log must be non-empty and must cover every module mapped from the plan's realized file footprint.
2. *Gate Coverage*: A module-scoped build (`module-tests`) never satisfies a whole-tree quality gate (`quality-gate` / `verify`).
3. *Test-Scope Divergence Detection*: Detects and rejects runs where test filtering flags or skipped-test properties excluded tests belonging to modified modules.

== Security Boundary & Confinement Adversarial Testing (`PM-TEST-5`, `PM-SEC-1`, `PM-SEC-2`, `PM-SEC-5`)

The `pm-mcp-core` and `pm-mcp-server` verification suite enforces automated adversarial tests (`PM-TEST-5`) across every job and ingestion boundary:

1. *Workspace & Symlink Escape Rejection (`PM-SEC-2`)*: Adversarial fixtures containing `..` segments, URL-encoded path traversal, and intra-worktree symlinks pointing outside `<workspace-root>` must be rejected with `refused` before any file descriptor or subprocess is opened.
2. *Tampered Binary & Wrapper Rejection (`PM-EXEC-2`, `PM-EXEC-3`, `PM-EXT-5`)*: Modifying 1 byte of an enrolled `mvnw`, `gradlew`, `pw`, host binary, or `project_script` without operator re-enrolment must fail the SHA-256 preflight check with `refused` and emit a `security` event in `audit.jsonl`.
3. *Argument Vector Injection & Environment Sanitization (`PM-EXEC-1`, `PM-SEC-5`)*: Passing shell metacharacters (`; rm -rf`, `$(...)`, backticks) or non-allowlisted flags (`-Dexec.executable=...`, `--init-script`) in job parameters must be rejected at schema validation, and spawned child environments must never contain `GITHUB_TOKEN`, `SONAR_TOKEN`, or `JIRA_API_TOKEN`.
4. *Untrusted Reader Containment (`PM-SEC-1`)*: Sub-agent dispatches targeting `execution-context-reader` are verified to emit zero MCP tool permissions and pass all ingested candidate structs through the deterministic Java validator before writing to `.plan/` stores.
