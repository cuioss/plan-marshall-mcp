== Overview

This document specifies the technical design, process management, security controls, and output parsers for the PM-MCP **Job Runtime**. The runtime manages native host subprocesses for builds, the git and CI operations of the CLI variant (`git`, `gh`, `glab`), and out-of-process project scripts (`PM-EXT-5`) under strict operator enrolment (`PM-EXEC-1`..`PM-EXEC-5`). The git and CI operations of the native variant run in-process; they get a job record without process fields and the same budgets, cancellation, and outcome rules (<<in-process-operations>>). The runtime never executes legacy `plan-marshall` scripts (`PM-MIG-2`). The git, CI, findings, and static-analysis operation contracts that these jobs serve live in the provider modules `pm-mcp-git`, `pm-mcp-ci`, `pm-mcp-findings`, and `pm-mcp-analysis`; their CLI adapter variants run as jobs of this runtime (link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]).

== Verify-Not-Resolve Execution Pipeline

Before spawning any subprocess, the runtime reads the enrolment file of the job's project, `<PM_MCP_BASE>/enrolments/<project_id>.json` (link:store-schemas.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]), verifies its integrity (<<enrolment-integrity>>), and then validates the job request through a deterministic three-stage verification pipeline (`PM-EXEC-1`..`PM-EXEC-3`, `PM-SEC-2`):

[source,text]
----
  Job Request (Scope, Executable, Argv, WorkingDir)
                       │
                       ▼
       ┌───────────────────────────────┐
       │ 0. Enrolment HMAC Check       │ ──► Mismatch: REFUSED (enrolment_tampered)
       └───────────────┬───────────────┘
                       │ Valid (HMAC matches file content)
                       ▼
       ┌───────────────────────────────┐
       │ 1. Working Directory Check    │ ──► Mismatch: REFUSED (outside enrolled tree)
       └───────────────┬───────────────┘
                       │ Valid (Root or linked worktree)
                       ▼
       ┌───────────────────────────────┐
       │ 2. Executable & Digest Check  │ ──► Mismatch: REFUSED (unpinned tool / digest drift)
       └───────────────┬───────────────┘
                       │ Valid (Exact path & SHA-256 match)
                       ▼
       ┌───────────────────────────────┐
       │ 3. Argument Schema Validation │ ──► Mismatch: REFUSED (illegal flag / unquoted space)
       └───────────────┬───────────────┘
                       │ Valid
                       ▼
             Spawn Subprocess (Direct)
----

* *Working Directory Confinement (`PM-SEC-2`)*: The working directory must resolve canonically via `Path.toRealPath()` to the project's enrolled root or a live linked git worktree verified via `git worktree list --porcelain`. Arbitrary paths or symlink escapes are rejected with outcome `refused` and reason `path_traversal_rejected`.
* *Working Directory Selection (`PM-ARCH-5`)*: The working directory is derived from the plan's persisted worktree presence at job start, never from the phase: jobs for plans whose `worktree_path` is set run in the plan's worktree root; jobs for plans whose `worktree_path` is `null` and plan-less jobs run in the main checkout (link:filesystem-layout.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). A job that removes a worktree never runs with a working directory inside that worktree.
* *Verify-Not-Resolve Executable Resolution (`PM-EXEC-1`, `PM-EXEC-2`, `PM-EXEC-3`, `PM-EXT-5`)*: The runtime *never* searches the system `PATH`:
** *Wrapper Jobs (`mvnw`, `gradlew`, `pw`)*: The wrapper must be committed at the root of the tree, must match an enrolled wrapper name in the project's enrolment file, and its SHA-256 content hash must match the enrolled digest. The digest check also covers every file that decides which tool runs and with which flags, recorded at enrolment as the wrapper's `pinned_files`: the wrapper jar and wrapper properties (`gradle/wrapper/gradle-wrapper.jar`, `gradle/wrapper/gradle-wrapper.properties`, `.mvn/wrapper/maven-wrapper.properties`) and the repository build configuration (`.mvn/maven.config`, `.mvn/jvm.config`, `gradle.properties`) where present; a pinned file that appears after enrolment counts as changed. Enrolment of `mvnw` or `gradlew` requires `distributionSha256Sum` in the wrapper properties, so the downloaded distribution is pinned as well. A mismatch refuses the job with `refused`, reason `build_config_changed`, the changed paths, and the `pm-mcp operator enrol` command that re-baselines them (`PM-EXEC-2`). The interpreter-based wrapper `pw` is never started through its `#!/usr/bin/env` shebang: the runtime invokes the enrolled interpreter host tool (the wrapper's `interpreter`) with the wrapper as its first argument. What a wrapper runs is decided by the enrolled canonical template of the build verb (`build.canonical_templates`) or its compiled default; there is no per-wrapper goal allowlist.
** *Host Tools (`git`, `gh`, `glab`, `python3`, `npm`, `npx`)*: The runtime invokes the exact absolute `executable_path` recorded in the project's enrolment file after verifying that the file's current SHA-256 matches the enrolment record.
** *Project Script Jobs (`project_script`, `PM-EXT-5`)*: Both the script file (`script_path`) and its interpreter (`interpreter`, an enrolled host tool) must match their enrolled SHA-256 digests (`project_scripts.<project_script_id>` of the project's enrolment file), the job's use must match the script's `binding` (`worker_kind` and `target`), and the job arguments must validate against the script's enrolled `argument_schema`; the budget is the script's `max_timeout_seconds`. There is no job kind for legacy `plan-marshall` scripts.
* *Argument Schema Validation (`PM-EXEC-1`, `PM-EXEC-5`)*: The argument vector (`argv`) is checked against a closed allowlist schema per tool type. Shell meta-characters (`|`, `;`, `&`, `$`, `` ` ``, `>`, `<`) are never evaluated: the runtime spawns every job without a shell, and the `#!/bin/sh` wrappers `mvnw` and `gradlew` receive the validated vector as positional arguments. This validation guards only against injection through link parameters; flags that come from repository content (the build configuration files above) are governed by their enrolled digests, not by the argument schema.

[#enrolment-integrity]
=== Enrolment Integrity Check (`PM-EXEC-2`)

Step 0 of the pipeline verifies the HMAC-SHA-256 sidecar `<PM_MCP_BASE>/enrolments/<project_id>.json.hmac` against the current enrolment file of the job's project (link:store-schemas.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]) before every verify-not-resolve check, in addition to the check in the project's recovery after a runtime start. A failed check blocks only this project's jobs. Key handling, operator re-baselining, and the accepted residual risks (hosts without a keyring; macOS, where the Keychain releases the key to the `pm-mcp` binary without a passphrase) are specified in link:cli-and-security.adoc#enrolment-integrity[CLI, Coordination & Security Specification, Enrolment Integrity].

* *Mismatch*: The job is refused with reason `enrolment_tampered` (outcome `refused`) and a `security` record is appended to `audit.jsonl`; the runtime never repairs or re-signs the file and trusts no enrolment until the operator re-baselines it through the operator CLI.
* *Write Protection*: Jobs cannot write `<PM_MCP_BASE>` on Linux (<<Linux Filesystem Confinement (Landlock)>>); the HMAC is the control against writers that are not jobs, such as a model-driven host shell.

== Subprocess Lifecycle & Process-Group Isolation

Every job runs as a direct child of the always-on runtime (`pm-mcpd`), started through the launcher `pm-mcp-exec`, independent of any host connection (link:runtime-model.adoc[Runtime & Interaction Model Specification]), inside its own isolated operating system process group (`PM-EXEC-4`, `PM-EXEC-5`, `PM-IMPL-1`).

=== Process-Group Creation via the `pm-mcp-exec` Launcher
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-2[PM-WATCH-JOB-2]_

Java's `ProcessBuilder` cannot place a child into a new process group or session (`setpgid`/`setsid`); a child started directly would inherit the runtime's own process group, and signalling that group would hit the runtime and every other job. The runtime therefore starts every job through the launcher `pm-mcp-exec`, a separate tiny native binary of the release (plain GraalVM native image with FFM, no Quarkus, module `pm-mcp-modules/pm-mcp-exec`), started by its path in the runtime's own installation directory `<PM_MCP_HOME>/bin/`, never through `PATH`:

. The runtime verifies the job (verify-not-resolve, `PM-EXEC-2`) and starts `<PM_MCP_HOME>/bin/pm-mcp-exec -- <verified absolute executable> <args…>` with `ProcessBuilder`, keeping all of its I/O handling (pipes, in-memory `stdin` payloads, log redirection, exit codes).
. The launcher calls `setpgid(0, 0)` via FFM, so its PID becomes the process-group ID, and then replaces itself with the target via `execve` (never `execvp`: no `PATH` search, `PM-EXEC-1`). The job's PID recorded by the runtime is therefore both the job PID and its process-group ID.
. Cancellation and timeouts signal exactly that group (`kill(-pid, …)`). Warm build daemons that detach themselves into their own session (Gradle daemon, `mvnd`) are intentionally not affected (`PM-EXEC-4`).
. `pm-mcp-exec` is not a user command and not a verb of the CLI `pm-mcp`: it accepts only an absolute executable path, an argument vector, and (on Linux) the confinement sets, performs no verification of its own, reads no file of `<PM_MCP_BASE>`, and holds no secret.

*Alternative for later implementations (macOS only)*: Start jobs directly via FFM `posix_spawn` with `POSIX_SPAWN_SETPGROUP` (the mechanism already used for the detached runtime start, link:runtime-model.adoc[Runtime & Interaction Model Specification]). This removes the extra `execve` hop but replaces `ProcessBuilder` completely: pipes, `stdin` streaming, output capture, and exit-status reaping (`waitpid`) must then be implemented on FFM as well. The job contract (process group = job PID, outcome classification) is identical, so the runtime can switch implementations without changing any other specification. On Linux the `pm-mcp-exec` launcher (or an equivalent restricted spawner thread) stays mandatory: `PR_SET_NO_NEW_PRIVS` and the Landlock ruleset must be applied between `fork` and `execve`, and `posix_spawn` offers no hook for that.

[source,java]
----
List<String> argv = new ArrayList<>(List.of(pmMcpExecBinary, "--")); // <PM_MCP_HOME>/bin/pm-mcp-exec
argv.addAll(verifiedArgv); // verifiedArgv.get(0) is the verified absolute executable path
ProcessBuilder pb = new ProcessBuilder(argv);
pb.directory(verifiedWorkingDir.toFile());
// Environment sanitization
pb.environment().clear();
pb.environment().putAll(sanitizedEnvAllowlist);
// Standard input handling: /dev/null by default, or in-memory pipe for multi-line payloads
if (stdinPayload.isPresent()) {
    pb.redirectInput(ProcessBuilder.Redirect.PIPE);
} else {
    pb.redirectInput(ProcessBuilder.Redirect.from(new File("/dev/null")));
}
// Direct output redirection to job log file (never inherits the runtime's stdin/stdout)
pb.redirectOutput(jobLogPath.toFile());
pb.redirectErrorStream(true);
Process process = pb.start();
if (stdinPayload.isPresent()) {
    byte[] bytes = stdinPayload.get();
    Thread.startVirtualThread(() -> {
        try (OutputStream out = process.getOutputStream()) {
            out.write(bytes);
            out.flush();
        } catch (IOException ignored) {
            // Child process exited early; handled by exit-code & outcome classifier
        }
    });
}
----

=== In-Memory `stdin` Streaming vs Retired Temp-File Patterns (`PM-EXEC-5`)

When a workflow primitive served by the CLI variant (link:cli-and-security.adoc#cli-variant-credentials[CLI, Coordination & Security Specification, Credentials of the CLI Variant]) passes multi-line text to an enrolled `git` or `ci` tool, `JobRuntime` supplies the validated UTF-8 bytes in `stdinPayload`. The native variant runs in process and passes the same text as an in-memory request payload; it has no job and no `stdin`.

The `stdin` forms of the CLI variant are closed:

* `git`: `git -C <tree> commit -F -`.
* `gh`: `gh pr create|edit|comment --body-file -`, `gh issue create|comment --body-file -`, and `gh api graphql --input -` for the fixed GraphQL documents.
* `glab`: the operations whose `glab` subcommand has no confirmed `stdin` form (`mr create`, `mr note`, `issue note`) are sent as `glab api <endpoint> --input -` with a server-composed JSON body. Until the Milestone-1 verification of these forms passes, these operations return `unsupported_by_variant{reason: no_stdin_form}` in the CLI variant, and the `gitlab` integration needs the native variant for them; free text is never moved to the argument vector or a file to work around it.

For every form:

* *Zero Temp or Scratch Files*: The server never writes commit messages or PR/issue bodies to scratch files, neither in the manner of `plan-marshall`'s `.plan/temp/{plan_id}-commit-msg.txt` and `<plan>/work/ci-bodies/` nor to `/tmp/`.
* *Zero Shell / Argv Exposure*: Multi-line text is never placed in `verifiedArgv`, avoiding OS `ARG_MAX` limits and `ps` command-line inspection.
* *Deterministic EOF*: The virtual writer thread closes `process.getOutputStream()` immediately after flushing `bytes`, guaranteeing that `git` and `gh` see EOF and never hang waiting for interactive input.

=== Process Termination & Cancellation Protocol
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-3[PM-WATCH-JOB-3]_

When a job exceeds its allocated budget (`PM-EXEC-4`, link:timeouts.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]), when the user/client calls `cancel`, or when the runtime drains:

1. *SIGTERM Escalation*: The runtime sends `SIGTERM` to the job's process group (`kill(-pgid, SIGTERM)` via Java FFM, `PM-TECH-4`), whose ID equals the job PID (see <<Process-Group Creation via the `pm-mcp-exec` Launcher>>).
2. *Grace Period*: `pm-mcp` waits the termination grace period (link:timeouts.adoc#grace-period[Timeouts & Budgets Specification]) for all processes in the group to exit cleanly.
3. *SIGKILL Cleanup*: If any process of the group remains alive after the grace period, `pm-mcp` issues `kill(-pgid, SIGKILL)`. Steps 1–3 address the group, never only its leader: they run to completion even when the leader has already exited and only descendants remain.
4. *Cancel Before the Group Exists*: The launcher calls `setpgid` after it starts, so a cancel (or budget expiry, or drain) that reaches a job in that window gets `ESRCH` from `kill(-pgid, …)`. The runtime then signals the PID directly (`kill(pid, SIGTERM)`) and retries against the group after the short bounded delay of link:timeouts.adoc#cancel-group-retry[Timeouts & Budgets Specification, Cancel-Before-Group Retry], and records `cancel_before_group: true` in the job record.
5. *Outcome*: The outcome of a terminated job is derived by <<outcome-derivation>>; relay termination never affects a job. A `timed_out` job is `no_verdict` in every roll-up (link:timeouts.adoc#no-verdict-rule[Timeouts & Budgets Specification, Timed-Out Outcomes Are No-Verdict]).
6. *Live Orphans after a Runtime Crash*: Each job record stores the job PID (which is its process-group ID) and the process start instant. In the project's recovery after the next runtime start, for every record left `running` the runtime probes the process group with `kill(-pgid, 0)` together with the record: a group exists while any of its members lives, and a PGID cannot be reused while its group is alive, so a live group whose ID equals the recorded PGID of a `running` record is that job's group, even when the leader (whose start instant was recorded) has exited. Such a group is terminated with steps 1–3 and the job recorded as `killed`; it is never adopted or re-executed (link:runtime-model.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery]). A group that no longer exists needs no termination; the record is settled `killed` as well.

[#in-process-operations]
=== In-Process Operations (Native Variant)
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-3[PM-WATCH-JOB-3]_

A `git` or `ci` operation of the native variant (JGit, provider HTTP clients) runs inside the runtime: no argument vector, no environment, no process group, no Landlock ruleset, and no `pm-mcp-exec` launcher exist for it. It is still a job of the runtime, so waits, cancellation, metrics, and recovery treat it like any other job:

* *Job Record*: Every in-process operation gets a job record of its kind (`git` or `ci`, job id prefix `g` or `c`) with `execution: in_process`, its budget key `<kind>:<operation>`, `budget_seconds`, and `budget_derivation`; the process fields (`argv_digest`, `pid`, `process_started_at`, `spawned_at`, `exit_code`, `signal`) are `null` and `confinement` is `not_applicable` (link:store-schemas.adoc#job-record[Store Schemas Specification, Job Record]). It writes no job log file.
* *Budget & Cancellation*: The operation runs under the budget of its operation class; at budget expiry, on `cancel:<job_id>`, and at drain it is cancelled cooperatively (JGit `ProgressMonitor`, interruption of the HTTP exchange), every HTTP request carries the compiled per-request connect and read timeout, and an operation that does not return within the grace period is abandoned with its late result discarded (link:timeouts.adoc#in-process-operations[Timeouts & Budgets Specification, In-Process Operations]). A partial result is never used.
* *Outcome*: Rows 1 to 4 of <<outcome-derivation>> apply unchanged (`refused` before the operation starts, `cancelled`, `timed_out` as `no_verdict`, `killed` at drain or for a record left `running` by a previous runtime instance; nothing is probed or adopted). Otherwise the fate is `succeeded` when the operation returned a domain outcome of its closed contract enumeration, `failed` when it returned a transport outcome (`auth_failed`, `permission_denied`, `provider_unavailable`, `malformed_response`, `unsupported_by_variant`, `capability_missing`), and `indeterminate` when it ended outside its contract (an unexpected exception, recorded by its class). A provider rate limit (`rate_limited{reset_at}`, or a `Retry-After`) is neither a failure nor a timeout: the operation is re-issued after the stated instant, the time until then does not count against its budget, and the wait records `provider_rate_limit` (<<_bounded_long_poll_progress_reset_waiting_primitives_pm_wf_8_pm_impl_4>>).

=== Bounded Long-Poll & Progress-Reset Waiting Primitives (`PM-WF-8`, `PM-IMPL-4`)
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-5[PM-WATCH-JOB-5], link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-6[PM-WATCH-JOB-6], link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-19[PM-WATCH-JOB-19]_

When a workflow transition spawns a long-running `build`, `ci`, or `project_script` job, or when the model invokes `pm_build` (`PM-SVC-1`, `PM-SVC-4`):

* *Bounded Wait Slice*: The server holds the request open for at most the bounded wait window (`bounded_wait_seconds` of the client profile; value, bounds, and the rule relating it to the host idle timeout in link:timeouts.adoc#bounded-wait[Timeouts & Budgets Specification, Bounded Wait Window]). If the job completes within the window, the server immediately evaluates the completion guard and returns the next workflow state.
* *Progress Notifications*: When the client profile supports `progress_resets_timeout == true` and supplies a `_meta.progressToken`, the call waits up to the progress wait upper bound (link:timeouts.adoc#progress-wait[Timeouts & Budgets Specification]) and the job runner emits periodic `notifications/progress` frames (current build stage and elapsed time, at the interval of link:timeouts.adoc#progress-interval[Timeouts & Budgets Specification]) over the calling host connection (relayed to the host by `pm-mcp serve`).
* *Non-Blocking Wait Links*: If the job is still running when the window elapses, the call returns a valid hypermedia state with the implicit `wait:<job_id>` (`rel: wait`, `form: wait`) and `cancel:<job_id>` (`rel: abort`, `form: noop`) links (`PM-WF-8`, link:workflow-dsl.adoc#implicit-job-links[Workflow DSL Specification, Implicit Links of Job States]), never failing with an MCP transport timeout.
* *Wait Attribution*: Every wait slice records `wait_reason` (closed enum `build`, `ci`, `review_bot_window`, `operator_decision`, `merge_queue`, `precondition_poll`, `provider_rate_limit`) and `deliberate` (`true` for an operator ruling or a rate window). `provider_rate_limit` is the time a provider's API rate limit (`Retry-After` or a rate-limit reset instant) deferred the next observation (link:timeouts.adoc#ci-repoll-cadence[Timeouts & Budgets Specification, Provider Re-Poll Cadence]); it is never a timeout and never a failure. `record-metrics` sums wait time per reason and reports deliberate waits separately from poll misses, never as one "waste" figure.

=== Warm Language Server Pool & Orthogonal Service Access (`PM-SVC-2`, `PM-SVC-4`, `PM-TOOL-2`)
_Implementation watch: link:../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-5[PM-WATCH-TOOL-5]_

The Job Runtime manages a bounded pool of warm Language Server Protocol (LSP) subprocesses (`max_lsp_instances` in `machine-config.json`, default `3`) spoken via Eclipse `LSP4J` over `stdio` (`PM-TECH-2`, `PM-TECH-3`):

* *Verify-Not-Resolve Launch*: Each language server binary (`jdtls`, `pyright-langserver`, `typescript-language-server`, `rust-analyzer`, or the marketplace corpus language server) is verified against `language_servers` of the project's enrolment file `enrolments/<project_id>.json` before launch.
* *Lifecycle & Eviction*: Instances are keyed by `(canonical_worktree_path, language_id)` (the plan worktree, or the main checkout at the enrolled `project_root`), initialized lazily on the first `pm_lsp` call (`PM-TOOL-2`, `PM-SVC-4`), evicted cleanly (`shutdown` -> `exit` -> `SIGTERM`) after the language server idle timeout (`lsp_idle_timeout_seconds`; start, request, and idle timeouts in link:timeouts.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle]) or when the runtime drains or stops, and restarted automatically (up to 2 retries) on unexpected exit.

[#outcome-derivation]
== Outcome Derivation
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-1[PM-WATCH-JOB-1]_

The runtime derives every job outcome itself, at the boundary, from evidence it observed: whether it refused the job before spawn, which signal it sent and why, the wait status of the process (exit code or terminating signal), and the parse of the job log (`PM-EXEC-4`, `PM-SVC-1`). A status that a job reports about itself (the `status` field of a `project_script` output payload) is evidence to check, never the outcome. The table is closed and evaluated top to bottom; the first matching row decides. The derived outcome, the matching row, the exit code or signal, and `cancel_before_group` (<<Process Termination & Cancellation Protocol>>) are recorded in the job record.

[cols="1,3,2,3"]
|===
|# |Evidence |Outcome |Notes

|1
|The job was refused before spawn: verify-not-resolve pipeline (<<Verify-Not-Resolve Execution Pipeline>>, including `enrolment_tampered`, `build_config_changed`, `path_traversal_rejected`), argument schema, or admission.
|`refused`
|Carries the refusal `reason`; no process ever existed.

|2
|The runtime sent the termination signal because of a `cancel:<job_id>` (or the cancel of a composite constituent).
|`cancelled`
|Whatever the process's exit status after the signal.

|3
|The runtime sent the termination signal because the job's budget expired (link:timeouts.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]).
|`timed_out`
|Whatever the process's exit status after the signal; `no_verdict` in every roll-up (link:timeouts.adoc#no-verdict-rule[Timeouts & Budgets Specification]).

|4
|The process ended by any other signal: the runtime's drain or orphan termination, a crash signal (`SIGSEGV`, `SIGBUS`, `SIGABRT`, `SIGILL`, `SIGFPE`), an external `SIGKILL` (for example the OOM killer) or any other external signal; or the record was left `running` by a previous runtime instance.
|`killed`
|The signal is recorded (`signal` name and number, or `runtime_restart`); never retried without an explicit workflow transition.

|5
|The job log is missing, truncated, or unreadable.
|`indeterminate`
|Also for exit code `0`; no findings are emitted.

|6
|A `project_script` reports a `status` that contradicts the exit code or the parsed evidence.
|`indeterminate`
|The contradiction (reported status, exit code, parse result) is recorded.

|7
|Exit code `0` and the tool parser found its positive success marker, with no contradicting evidence.
|`succeeded`
|Success markers: build — the engine's terminal success marker (`BUILD SUCCESS`, `BUILD SUCCESSFUL`) or the tool's passing summary (<<Native Build Output Parsers>>); `git` — exit `0` plus the post-condition read where the primitive declares one; `ci` — a parseable `--json` payload of the expected shape; `project_script` — a schema-valid output payload whose `status` agrees.

|8
|Exit code `0` without the positive success marker, or with contradicting evidence (parsed errors, failing test counts).
|`indeterminate`
|Never folded into `succeeded` or `failed`.

|9
|Non-zero exit code and the parser extracted at least one diagnostic.
|`failed`
|Located diagnostics become findings.

|10
|Non-zero exit code and no parsed diagnostic.
|`failed_unparsed` for `build` jobs; `failed` for every other job type
|<<Unparseable Output Fallback (`failed_unparsed`)>>.
|===

For an in-process operation of the native variant, rows 5 to 10 are replaced by the contract-based rule of <<in-process-operations>>; the success markers of row 7 for `git` and `ci` apply to the jobs of the CLI variant.

Language server instances of the warm LSP pool are not classified by this table; their failures are reported as the non-run reasons of link:domain-extensions.adoc[Domain Extensions Specification] (Explicit Non-Run Reporting) and the timeouts of link:timeouts.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle].

== Linux Filesystem Confinement (Landlock)
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-20[PM-WATCH-JOB-20]_

On Linux (`PM-SEC-5`, `PM-TECH-4`), the `pm-mcp-exec` launcher (<<Process-Group Creation via the `pm-mcp-exec` Launcher>>) confines every job before `execve`:

. `prctl(PR_SET_NO_NEW_PRIVS, 1)`: the job and all its descendants can never gain privileges (setuid/setgid binaries, file capabilities).
. A Landlock ruleset (Landlock ABI >= 2, Linux >= 5.19, applied via FFM) that grants read and execute access to the whole filesystem except `<PM_MCP_BASE>/run/` (see *Read set* below) and write access only to:
** every enrolled project root (which contains all of that project's worktrees under `.marshall/local/worktrees/` and its `.marshall/local/temp/`; never the per-project machine store under `<PM_MCP_BASE>`),
** the build toolchain caches declared per project in the enrolment field `write_paths` (for example `~/.m2/repository`, `~/.gradle`, `~/.npm`, `~/.cache/pip`),
** the system temporary directory (`/tmp`; the JVM ignores `TMPDIR` for `java.io.tmpdir`) and device nodes under `/dev`.

The write set never contains `<PM_MCP_BASE>` (enrolments, machine configuration, credentials, logs, and the machine stores stay out of every job's reach) and never `~/.plan-marshall/`.

*Read set*: `<PM_MCP_BASE>/run/` holds the runtime token (link:runtime-model.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]) and is outside every job's read set. Because Landlock rules only grant access, the runtime builds the read set as read and execute rules on `/` minus the path to `run/`: for each directory from `/` down to `<PM_MCP_BASE>`, a rule for every entry except the next directory on that path, and for `<PM_MCP_BASE>` a rule for every entry except `run/`. The entries are enumerated at job start; an entry created later on that path (for example a new file directly in the home directory) is not readable by the job, which is accepted. On macOS and on Linux without Landlock a job can read the token like any process of the user; this lies within the same-user boundary accepted for the operator channel (link:../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]). The runtime token and every other runtime secret are never passed in a job's argument vector or environment (<<Job Environment (`PM-SEC-5`)>>).

The ruleset is inherited across `fork`/`execve` and cannot be removed by the job. The runtime passes the read and write sets to the launcher as an argument vector computed from the project's enrolment file at job start, so enrolment changes take effect for the next job without restarting anything.

Properties and limits:

* *Warm build daemons*: A Gradle daemon or `mvnd` started from a confined job keeps that job's ruleset. Because the ruleset covers all enrolled project roots, later builds of any enrolled project can reuse it; after enrolling a new project, the operator stops running warm daemons once so the next build starts one with the extended ruleset.
* *Container runtimes*: Docker, Docker Compose, and Testcontainers talk to the container daemon over its socket; writes performed by the daemon itself are outside the job's confinement (`PM-EXEC-4`).
* *Not covered*: Landlock does not restrict network address families and does not provide a private `/tmp`. `RestrictAddressFamilies` and `PrivateTmp` are therefore not enforced.
* *ABI Floor*: ABI 1 denies every cross-directory rename and link (`LANDLOCK_ACCESS_FS_REFER` arrives with ABI 2), which breaks Gradle, npm, and Java `Files.move` with `EXDEV`. On a kernel offering only ABI 1 the runtime applies no ruleset and records `confinement: partial(abi=1)`; it never reports a job as confined unless ABI >= 2 was applied. Rights that later ABIs add (for example `LANDLOCK_ACCESS_FS_TRUNCATE`, ABI 3) are handled as best effort, and the applied ABI is recorded in every job record.
* *Unavailable Landlock*: On kernels without Landlock (older kernels, some WSL2 kernels), jobs run with `PR_SET_NO_NEW_PRIVS` only; the runtime records `confinement: unavailable` in each job record and in `pm-mcp status`, and this is an accepted residual platform risk (`PM-SEC-5`).

=== Unparseable Output Fallback (`failed_unparsed`)
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-7[PM-WATCH-JOB-7], link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-14[PM-WATCH-JOB-14]_

If a build exits with a non-zero exit code but the output parser cannot extract any structured diagnostic (row 10 of <<outcome-derivation>>; a build ended by a signal, including a crash, is `killed`):

== Adaptive Build Timeouts, Coverage Parsers & Gate Honesty (`PM-EXEC-6`)

=== Adaptive Timeout Learning
_Implementation watch: link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-15[PM-WATCH-JOB-15], link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-16[PM-WATCH-JOB-16]_

`pm-mcp` persists observed execution durations per project in `<PM_MCP_BASE>/projects/<project_id>/build-timings.json` (link:store-schemas.adoc#build-timings-store[Store Schemas Specification, Build Timings Store]), keyed by budget key (for build jobs the canonical command: build system, canonical verb of the <<canonical-build-verbs>>, module, and sorted profiles; for `git` and `ci` operations the operation key `<kind>:<operation>`, the same for an in-process operation of the native variant and a job of the CLI variant, <<in-process-operations>>); there is no repository-local and no machine-level timeout store, so a moved checkout keeps its budgets. The blend formula, the engine floors, the allocation rule, the escalation budget and its cap, operator budgets, and the no-verdict rule for `timed_out` are defined only in link:timeouts.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]; this section defines which runs feed the learned baseline $L$:

* *Finished Runs Feed $L$*: Every finished run (any exit code) feeds $L$ with its duration; `killed` and `cancelled` runs never do. An in-process operation has finished when it returned a result of its contract; the time it spent deferred by a provider rate limit is excluded from the duration.
* *Timed-Out Runs Never Feed $L$*: A `timed_out` run is a non-finish, so its duration is unknown. It never feeds $L$; it sets the one-shot escalation budget of link:timeouts.adoc#escalation-budget[Timeouts & Budgets Specification] for the next run of the same key, which the next finished run clears. *Deliberate change vs. `plan-marshall`*: `plan-marshall` blends its doubled timeout into $L$, so one residue-slowed timeout inflates every later budget.
* *Residue-Poisoned Runs*: A finished run whose worktree held build residue above the hygiene threshold at its start (the count of git-ignored build output files measured at job start, beside the <<worktree-sha>> scan; the threshold is a named engine constant recorded with the observation) is stored as `poisoned` and not blended while clean observations exist. The learned value's hygiene (`observations`, `poisoned`, `escalated`) is recorded in the build timings store and the job record and shown by `pm-mcp status`; it is never rendered in the job facts (link:hypermedia-format.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
* *Budget Derivation*: Every allocated budget records `budget_derivation` (`learned` with its observation count, `escalated`, `operator`, or `floor_default`; link:timeouts.adoc#budget-allocation[Timeouts & Budgets Specification, Allocated Budget]) in the job record, never in the representation: the model acts on the offered links, not on the derivation. Every `timed_out` outcome is `no_verdict`, whatever the derivation; the derivation selects only the retry offer, server-side (link:timeouts.adoc#no-verdict-rule[Timeouts & Budgets Specification]).
* *Budget Scope & Measurement*: Every budget states the statistic it came from and the scope it applies to (link:timeouts.adoc#no-verdict-rule[Timeouts & Budgets Specification], Budget statistic). Its scope is the budget key, so a figure measured under one key is never applied to another.
* *Runner-Dependent Verdicts*: When the same test population is red under one canonical command and green under another (for example a real-tree test that times out under a module-scoped test run but passes under `verify`), the job facts report both keys with their verdicts (the budgets stay in the job records); the difference is never left implicit.
* *Cold Rebuilds*: A finished run that starts after a dependency sync or a build-cache invalidation since the key's previous observation (a changed resolved-dependency set or a cleared build cache) is stored as `cold`. Like a `poisoned` run it is not blended into $L$ while warm observations exist, and it is never read as a regression of $L$.
* *Seeded Wait Budgets*: The expected duration of a CI wait (link:hypermedia-format.adoc#_deterministic_evaluation_immediate_short_circuit_matrix[Hypermedia Format Specification, Short-Circuit Matrix]) is seeded from the project's known-slow ceilings (the operator budgets in the enrolment) when no learned figure exists. CI waits are re-polled and never lapse, so a seeded figure sets only the expected duration recorded with the wait (shown by `pm-mcp status`, never rendered), never a failure deadline (link:timeouts.adoc#ci-wait[Timeouts & Budgets Specification, CI Wait]). Review-bot waits are bounded by the bot's rate window, re-review timeout, and attempt ceiling, never by a learned or seeded figure (link:timeouts.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows]).
* *No Inherited Baselines*: Every learned value starts from the project's own finished runs under `PM-MCP`; learned timeouts of legacy `plan-marshall` are never read or imported (`PM-MIG-2`).

=== Native Coverage Report Parsers

The build runtime parses coverage artifacts natively after test execution to evaluate threshold compliance, porting `plan-marshall`'s format-agnostic coverage parser (`script-shared/scripts/build/_coverage_parse.py`, formats JaCoCo, Cobertura, LCOV, and Istanbul JSON). As in that parser, the threshold verdict (`passed`) compares the overall *line* percentage with the threshold, and the low-coverage list compares each item's line percentage with it; every other metric is parsed, rendered in the job facts, and never feeds a threshold:

* *JaCoCo (`jacoco.xml`)*: StAX XML reader extracting the `INSTRUCTION`, `BRANCH`, `LINE`, and `METHOD` counters (overall `instruction`, `branch`, `line`, `method` percentages from `covered / (missed + covered)`), plus per class the `LINE` counter and the methods with missed `METHOD` counters (`<init>` and `<clinit>` excluded) as `missed_methods` detail. Threshold metrics: overall `line`, per-class `line`.
* *Cobertura (`coverage.xml`, as written by `coverage.py` for pytest)*: StAX XML reader extracting the root `line-rate` and `branch-rate` and per class `line-rate` (methods with `line-rate` 0 as `missed_methods` detail). Threshold metrics: overall `line`, per-class `line`.
* *LCOV (`lcov.info`)*: Line-oriented parser over the per-file records `SF:`, `LF:`, `LH:`, `BRF:`, `BRH:`, `FNF:`, `FNH:` (up to `end_of_record`), summed over all files into overall `line` (`LH/LF`), `branch` (`BRH/BRF`), and `function` (`FNH/FNF`) percentages (`statement` equals `line`, since LCOV has no statement counter). `DA:` records may be kept as per-line detail but never enter a percentage or a threshold. Threshold metrics: overall `line`, per-file `line`.
* *Istanbul (`coverage-summary.json`)*: Jackson streaming reader extracting the `pct` of `lines`, `statements`, `functions`, and `branches` from `total` and per file. Threshold metrics: overall `line` (`lines.pct`), per-file `line`.

=== Gate Honesty Verification
_Implementation watch: link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-2[PM-WATCH-GEN-2], link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-8[PM-WATCH-JOB-8], link:../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-17[PM-WATCH-JOB-17]_

Before marking a module or pre-push quality gate as `fresh` in `change-ledger.jsonl` (`PM-SVC-1`), the runtime applies four honesty checks:

1. *Examined Population*: The set of modules and source files actually compiled and tested in the build log must be non-empty and must cover every module mapped from the plan's realized file footprint.
2. *Gate Coverage*: The gate scope of a build is computed from its `module` argument, never from its verb: an absent `module` is the whole tree, a present `module` is that module only. A module-scoped run of any verb never satisfies a whole-tree gate, and a whole-tree gate (`quality-gate`, `verify`, `coverage`, `arch-gate` of the <<canonical-build-verbs>>) is satisfied only by a whole-tree run of that verb. Every gate result carries server-derived coverage facts in `plan-marshall`'s terms (`script-shared/scripts/build/_gate_coverage.py`, verified at plan-marshall commit `88fcfc9ef`), which the server derives from the parsed build and the gate definition and the model never supplies:
** `gate_coverage`: `COMPLETE` (at least one dimension checked over its full scope and none degraded), `PARTIAL` (the degraded dimensions are named with their reason; a clean exit is then not a full pass), or `UNKNOWN` (nothing checked and nothing degraded recorded; the run certifies nothing). A dimension attempted over an empty scope is recorded as `empty_scope`, neither a pass nor a gap.
** `structural_limits`: per checked analysis kind, what the analysis cannot evaluate however wide its scope (for example type checking cannot decide whether a well-typed value is correct, tests are silent on inputs no test supplies); an analysis kind without a registered limit is recorded `UNKNOWN`, never omitted.
** `uncovered`: the dimensions the run did not cover, split into `not_at_this_scope` (the gate performs them, but not at this scope) and `not_by_this_gate` (no invocation of this gate performs them); without a declared scope the split is `undeclared`, never an empty list.
** `parity_population`: the recorded dimensions along which the local gate is compared with CI, each `equal`, `subset`, or `closed`; the population is asserted non-empty, because a parity table over nothing reads as perfect parity.
+
All four are persisted in the gate's job record and step record. The representation of a gate result renders only what the model acts on: `gate_coverage` with, for `PARTIAL`, the degraded dimensions and their reasons, and `uncovered`, so a clean exit is never reported as a full pass. `structural_limits` (a static, registered property of each analysis kind) and `parity_population` (local-versus-CI parity evidence for metrics and the quality report) are never rendered (link:hypermedia-format.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
3. *Test-Scope Divergence Detection*: Detects and rejects runs where test filtering flags or skipped-test properties excluded tests belonging to modified modules.
4. *Baseline Separation*: A failing whole-tree gate (`quality-gate`, `verify`, `coverage`) is re-run on the plan's merge base (`merge-base(HEAD, origin/<base_branch>)`) in the plan's baseline scratch worktree before any routing. The baseline worktree is a detached worktree at the merge base, created natively with `git.worktree-add` at `.marshall/local/worktrees/baseline-<plan_id>-<sha12>` (`<sha12>` the first 12 hex digits of the merge-base SHA), never the primary checkout and never the plan's worktree; it is reused by every base run of the plan while the merge base is unchanged, replaced (the old one removed, a new one created) when the merge base moves, and removed when the plan leaves `finalize`, is archived, or is aborted; the recovery sweep removes one whose plan is gone or terminal (link:filesystem-layout.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). Before each reuse it must be clean (`git.status` empty); a dirty baseline worktree is replaced, never used. Located diagnostics present on both sides are `baseline` and never become plan findings; for coverage, a threshold failure in a module whose main sources the plan did not change is `baseline_debt` (one non-blocking finding of severity `info` per module, never fanned out into build-error or Q-Gate findings). A gate red only through baseline diagnostics yields the gate verdict `baseline_red` (a verdict of the gate step, not a job outcome; both build jobs keep their own outcomes), which routes to `<phase>.baseline-red` (escalate only; the plan never remediates it) and is recorded with the merge-base SHA; the remaining diagnostics route to `triage_required`. A base run that cannot be executed or parsed leaves every diagnostic attributed to the plan (fail-closed) and says so in `facts`. A quality-gate or format job run in the baseline scratch worktree (or any fresh worktree of the base) must leave `git.status` empty; a job that rewrites committed files there is reported as dirtying the base, never silently accepted, and the worktree is replaced before the next base run.

== Working-Tree Hash (`worktree_sha`, `PM-SVC-1`)

`worktree_sha` stamps every build and change entry in `change-ledger.jsonl` and keys every freshness gate. It is a PM-MCP-native digest: its inputs and framing follow `plan-marshall`'s `script-shared/scripts/worktree_sha.py`, but git is invoked with fixed configuration-neutralising options, so its bytes deliberately differ from that script's. Byte parity is not required, because the digest is never exchanged between the two systems (`PM-MIG-2`); the differential tests (`PM-TEST-2`) compare equality behaviour instead (rule 6):

1. *Inputs*: Three git invocations, run with the worktree root as working directory. `<neutral>` stands for the fixed configuration options `-c core.quotePath=false -c diff.renames=false -c diff.algorithm=myers -c diff.context=3 -c diff.orderFile=`, which git accepts only before the subcommand. The argument vectors are exactly these; the runtime adds no other option, and a change of any of them is a new hash version (rule 4):
** `git <neutral> rev-parse HEAD`
** `git <neutral> diff --no-color --no-ext-diff --no-textconv --src-prefix=a/ --dst-prefix=b/ HEAD`
** `git <neutral> ls-files --others --exclude-standard` (only the `-c` options; the `diff` options do not apply)
2. *Framing*: `sha256(strip(HEAD) ‖ NUL ‖ diff ‖ NUL ‖ Σ(path ‖ NUL ‖ bytes ‖ NUL))` over the raw output bytes. Untracked paths are the non-empty output lines (split as Python `str.splitlines()` splits the `surrogateescape`-decoded output, which also breaks on `\r`, `\v`, `\f`, `\x1c`–`\x1e`, `\x85`, `\u2028` and `\u2029`), sorted by Unicode code point (Python `sorted()` on `str`, never a locale collation or UTF-16 code unit order), encoded as UTF-8 with undecodable bytes preserved (Python `surrogateescape`). An unreadable file contributes empty bytes.
3. *Neutralised git-configuration sensitivities*: The digest hashes git's textual output. The fixed options of rule 1 neutralise every setting known to change it: `diff.noprefix` and `diff.mnemonicPrefix` (overridden by the explicit `--src-prefix=a/ --dst-prefix=b/`), `color.diff` (`--no-color`), `diff.external` (`--no-ext-diff`) and textconv drivers such as `diff.<driver>.textconv` via `.gitattributes` (`--no-textconv`; `--no-ext-diff` alone does not disable them), `diff.renames`, `diff.algorithm`, `diff.context`, `diff.orderFile`, and `core.quotePath` (non-ASCII paths in `ls-files` are emitted unquoted, so they can be opened). The digest is therefore independent of user, system, and repository git configuration. Remaining sensitivity: none known. A sensitivity found later is fixed by a new hash version (rule 4), never by an in-place change of the invocation.
4. *Hash version*: Every record that carries a `worktree_sha` also carries `worktree_sha_version` (currently `1`, the invocation of rule 1 with the framing of rule 2): the `change-ledger.jsonl` rows and the `freshness_reconcile` record, whose version is that of its `prior_build_worktree_sha` (link:store-schemas.adoc[Store Schemas Specification]). Any change of the invocation or the framing is a new version. Freshness gates compare digests only of equal versions: a row of another version never matches the live digest and never makes a gate `fresh`; the gate reports it like an absent row for that notation.
5. *Fail-closed on git failure*: If any of the three git invocations fails (non-zero exit, termination by a signal, or its timeout), no digest is produced. The value is `unavailable`, recorded with the failing command (the argument vector) and its failure (`exit_code`, `signal`, or `timed_out`) as `worktree_sha_failure`; an unresolvable `HEAD` is such a failure. Every freshness gate keyed on it evaluates indeterminate, never `fresh`: the gate status is `undecidable` with `stale_reason: worktree_sha_unavailable` (link:phase-workflows.adoc[Phase Workflows Specification], Worktree Freshness Gate), and an `unavailable` value never equals another `unavailable`. This is a *deliberate change* against `plan-marshall`, whose `worktree_sha.py` ignores the exit codes of `git diff` and `git ls-files` and hashes the empty output of a failed call into an ordinary digest.
6. *Differential tests (`PM-TEST-2`)*: Over the same fixture trees, both implementations are run and their *equality behaviour* is compared, never their bytes: the same tree yields the same digest (on each side), and any change of a tracked file's content, an untracked path or its content, or `HEAD` yields a different digest (on each side). Fixtures include non-ASCII and `splitlines()`-boundary paths, unreadable untracked files, and a repository configuration setting each option of rule 3; for the last, PM-MCP's digest must stay unchanged while plan-marshall's may change. A git failure fixture asserts `unavailable` (rule 5) and is excluded from the comparison.

== Security Boundary & Confinement Adversarial Testing (`PM-TEST-5`, `PM-SEC-1`, `PM-SEC-2`, `PM-SEC-5`)

The `pm-mcp-core` and `pm-mcp-server` verification suite enforces automated adversarial tests (`PM-TEST-5`) across every job and ingestion boundary:

1. *Workspace & Symlink Escape Rejection (`PM-SEC-2`)*: Adversarial fixtures containing `..` segments, URL-encoded path traversal, and intra-worktree symlinks pointing outside `<workspace-root>` must be rejected (`path_traversal_rejected`: job outcome `refused` for a job, `rejected.reason` for a `pm_do` argument) before any file descriptor or subprocess is opened.
2. *Tampered Binary & Wrapper Rejection (`PM-EXEC-2`, `PM-EXEC-3`, `PM-EXT-5`)*: Modifying 1 byte of an enrolled `mvnw`, `gradlew`, `pw`, one of a wrapper's `pinned_files` (wrapper jar, wrapper properties, `.mvn/maven.config`, `.mvn/jvm.config`, `gradle.properties`), host binary, or `project_script` without operator re-enrolment, or adding a pinned build configuration file after enrolment, must fail the SHA-256 preflight check with `refused` and emit a `security` event in `audit.jsonl`.
3. *Argument Vector Injection & Environment Sanitization (`PM-EXEC-1`, `PM-SEC-5`)*: Passing shell metacharacters (`; rm -rf`, `$(...)`, backticks) or non-allowlisted flags (`-Dexec.executable=...`, `--init-script`) in job parameters must be rejected at schema validation, and spawned child environments must never contain `GITHUB_TOKEN` or `SONAR_TOKEN`.
4. *Untrusted Reader Containment (`PM-SEC-1`)*: Sub-agent dispatches targeting `execution-context-reader` are verified to emit zero MCP tool permissions and pass all ingested candidate structs through the deterministic Java validator before writing to `.marshall/` stores.
5. *Landlock Write Set (`PM-SEC-5`)*: On a Landlock-capable kernel, a job that writes its project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (and any other path under `<PM_MCP_BASE>` or `~/.plan-marshall/`) fails with a permission error and leaves the file unchanged; a matched positive control writes inside the enrolled project root.
6. *Enrolment Tampering (`PM-EXEC-2`)*: Editing a project's enrolment file out of band without the operator CLI makes the next job of that project refuse with `enrolment_tampered` and an `audit.jsonl` `security` record, while a job of a second enrolled project on the same runtime still runs (matched control); the same edit re-baselined through the operator CLI is accepted.
