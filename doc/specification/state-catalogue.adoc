== Overview

This document is the central catalogue of every workflow state of *plan-marshall-mcp* (`PM-MCP`). Every state identifier used anywhere in the requirements, the specifications, the roadmap, or the implementation watch is defined here exactly once, in one row of one table, with its phase value, its kind, where it is entered from, what it offers, where it exits to, and the section that specifies its behaviour. Other documents describe behaviour; they name a state only by its identifier and link to its row here (anchor `state-<state id>`, <<_state_identifier_grammar>>).

The catalogue is normatively equal to the state table that the diagram generator produces from the workflow definitions (`renderAsciiDocTables`, link:workflow-dsl.adoc#_automated_mermaid_asciidoc_table_and_ascii_diagram_generation[Workflow DSL Specification, Diagram Generation], `PM-IMPL-5`). Once the `*.pmwf` definitions exist, a build test (`StateCatalogueDriftTest`) compares the generated columns (state identifier, phase value, kind, entered from, offered links and outcomes, exits to) with this catalogue and fails the build when they differ, beside the `WorkflowDiagramDriftTest` (link:workflow-dsl.adoc#_build_time_drift_gate[Workflow DSL Specification, Build-Time Drift Gate]). The *Defined in* column is maintained by hand; the same test verifies that every link in it resolves. Until the definitions exist, this catalogue is the reference the definitions are written against: a state that is not in the catalogue does not exist, and a new state is added here before any other document uses it.

*Default units*: The phase and sub-workflow units are project-owned: a project runs its own copies in `.marshall/config/*.pmwf` (link:workflow-dsl.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]). This catalogue documents the *default* units the binary ships, and `StateCatalogueDriftTest` compares it with the default units only. A project unit may differ within the compiled invariants (for example by omitting an optional finalize step or adding a project step's state); its states are published with the project's effective configuration (`pm://project/config`), never added to this catalogue.

A cell reading _(to be specified)_ marks behaviour that no specification defines yet; the row records everything that is known.

=== State Identifier Grammar

* *Form*: A state identifier is `<unit>.<name>`: the workflow unit it belongs to, a dot, and the state name. Both parts follow the DSL `identifier` production (lowercase letter first, then lowercase letters, digits, `_`, `-`; link:workflow-dsl.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification, EBNF]). State names are kebab-case (`finalize.concurrent-wait`). The dialogue name `awaiting_answers` keeps its established snake-case form; no other name uses `_`. `awaiting_user` is a state kind (<<_state_kinds>>), never part of a state identifier: a routine question state is named by its question (`init.sibling-collision`). A migrated legacy name (`finalize.push_wait`) is listed only in <<state-catalogue-migrated>>.
* *Units*: The unit of a plan-workflow state is its phase file (`init`, `refine`, `outline`, `plan`, `execute`, `land`, `finalize`, link:workflow-dsl.adoc#workflow-definition-units[Workflow DSL Specification, Workflow Definition Units]); of a sub-workflow state the sub-workflow's family prefix (`git`); of every other top-level workflow its own prefix (`setup` for `project-setup.pmwf`, `epic` for `epic.pmwf`); of an entity state its entity kind (`envelope`).
* *Exceptions*: The plan's successful terminal state is the bare identifier `completed` (`PM-WF-1` admits both bare and phase-qualified terminal identifiers). The plan's single abort terminal is `plan.aborted`: its prefix names the scope type, not the Phase 4 unit `plan`, and it is declared in `finalize.pmwf` (link:workflow-dsl.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Workflow DSL Specification, `finalize.pmwf` Excerpt]); the epic's is `epic.aborted`. Entity states may carry a third segment (`envelope.task.active`); no other state does.
* *Anchors*: Every catalogued state carries the anchor `state-<state id>` (for example `link:state-catalogue.adoc#state-finalize.ci-failed[finalize.ci-failed]`); a generic state `<phase>.x` carries `state-phase.x`. A condition overlay carries `condition-<kind>` (for example `link:state-catalogue.adoc#condition-footprint_violation[footprint_violation]`); the anchors of the former generic states it replaces (`state-phase.blocked`, `state-phase.footprint-violation`, `state-phase.dispatch-incomplete`, `state-phase.config-drift`) stay on its row. Each unit table carries the anchor named in its heading.
* *Not states*: Primitive identifiers share the dotted form (`primitive_id = identifier "." identifier`) but are never states: `review.check-structural-caps`, `finalize.watch-ci-and-bots`, `finalize.record-in-branch-fix`, `finalize.restart-watch`, `finalize.retry-emit-landing`, `finalize.spend-ratio`, `finalize.landing-status`, `finalize.wait-status`, `plan.allocate-remediation-tasks`, `plan.loop-status`, `plan.resume-aborted-call`, `findings.triage`, `lane.budget-check`, `land.recapture-changes`, the epic primitives (`epic.inspect-ledger`, `epic.stage-plan`, `epic.ingest-message`, `epic.enqueue-landing`, `epic.land-ledger`, `epic.archive-ledger`), `git.pre-commit-verify-freshness`, `git.push-barrier-decision`, `git.branch-sync-state`, `build.verify-worktree`, and the other `do`, `auto`, `job`, `facts`, and `predicate:` targets of the DSL excerpts. Where a state and its primitive share a name (`git.inspect-worktree`, `git.detect-artifacts`, `git.resolve-message`, `git.stage-and-commit`, `git.evaluate-push-policy`, `finalize.retry-landing-delivery`, `finalize.close-pr-and-archive`, `finalize.hand-back-and-archive`, `finalize.adopt-pr`, `finalize.archive-plan`, `finalize.wind-down`), the catalogue row is the state. Configuration keys (`workflow.plan.phase-1-init.minimum_lane`), file names (`outline.md`, `init.pmwf`), and effort roles (`plan.<phase>.effort`) are not states either.
* *Other status vocabularies*: The following closed vocabularies are record statuses, not workflow states, and are defined where their record is defined: task statuses (`pending` .. `removed`, link:store-schemas.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]), dispatch lifecycle states (`ALLOCATED`, `CLAIMED`, `RETURNED`, `INCOMPLETE_SUBMISSION`, `UNCONFIRMED`, `SUPERSEDED`, link:dispatch-and-effort.adoc#_dispatch_id_generation_lifecycle_states[Dispatch & Effort Specification]), per-bot participation states and `bot_status` / `ci_status` (link:hypermedia-format.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations]), the 14-state epic queue row vocabulary (link:dispatch-and-effort.adoc#_git_distributed_epic_ledger_per_file_store_layout_adr_024[Dispatch & Effort Specification, Git-Distributed Epic Ledger]), finding statuses, and job outcomes (`PM-EXEC-4`).

=== State Kinds

Every state has exactly one kind. The first five follow the DSL `state_body` alternatives; `awaiting_user` and `blocked` classify link states by the decision they wait for; `overlay` is the kind of a condition, which is not a state (link:phase-workflows.adoc#_routine_user_interaction_vs_operator_authorizing_decisions[Phase Workflows Specification, Routine User Interaction vs Operator-Authorizing Decisions]).

[cols="1,4"]
|===
|Kind |Meaning

|`auto`
|Runs one primitive in the same turn (`auto` clause) and follows its outcome; never a resting state.

|`link`
|Offers declared links (`link` clauses) and rests until the model follows one. A state whose only declared link is `escalate` (for example `finalize.loop-limit-reached`) is a `link` state: the escalation is requested by the model, decided by the operator.

|`job`
|Runs one asynchronous job (`job` clause); rests with the implicit `wait:<job_id>` and `cancel:<job_id>` links (link:workflow-dsl.adoc#implicit-job-links[Workflow DSL Specification, Implicit Links]); its outcomes are the closed job outcome set including `cancelled`.

|`composite_job`
|Runs several jobs as one composite wait (`composite_job` clause); the composite identifier equals the state identifier (`wait:finalize.concurrent-wait`).

|`call`
|Invokes a sub-workflow (`call` clause); never a resting state itself: while the sub-workflow runs, the representation shows the active sub-workflow state, and the sub-workflow's terminal outcome selects the exit.

|`awaiting_user`
|A `link` state of the routine user dialogue: it carries typed questions in `facts` and accepts the answer by elicitation or by the model-relayed `submit` link `answer_questions` (recorded with `channel: model_relayed`). The kind name is never part of a state identifier: the states of this kind are named by their question (`init.lesson-premise`, `init.sibling-collision`, `init.domain-choice`, `init.posture-choice`, `init.recipe-candidate`, `refine.awaiting_answers`, `outline.awaiting_answers`, `<phase>.qgate-exhausted`, `setup.offer-new-steps`). A routine answer that would end the plan is the request `abort` (rel `escalate`), which raises the operator decision `abort-plan` (link:workflow-dsl.adoc#decision-registry[Workflow DSL Specification, Decision Registry]); it is never answered by the model.

|`blocked`
|A state that is entered by its own workflow condition and waits for an operator decision: the scope records `pending_decision`, renders `facts.operator_command`, and offers exactly one link, `wait:decision:<decision_id>`. The only state of this kind is `execute.awaiting-infeasible-decision`. An `escalate` link followed without elicitation never enters a state of this kind; it raises the `blocked` condition on the current state (<<condition-blocked>>).

|`overlay`
|Not a state: an engine-owned condition recorded on the scope (`pending_condition` in `mcp/status.json`) while the current state and `call_stack` stay unchanged. While it is set, the current state's representation keeps `state`, names the condition in the field `condition`, and renders only the condition's links. Conditions are catalogued in <<state-catalogue-conditions>>, never in a state table, and are never declared in a DSL unit (link:workflow-dsl.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]).

|`terminal`
|No outgoing transition; `links[0]` (the self-report link `report_bypass` stays accepted and unrendered). Every terminal state declares `terminal <outcome_id> <outcome_class>` (link:workflow-dsl.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification, EBNF]); a sub-workflow terminal state's outcome is the one returned to its caller. A plan or epic terminal state has phase value `completed` or `aborted` (`PM-WF-1`); each scope type has exactly one abort terminal (`plan.aborted`, `epic.aborted`, class `failure`), reachable from every phase. A sub-workflow's abort terminal (`git.done-aborted`, class `aborted`) only returns `aborted` to its caller. The workspace scope has no terminal state (<<state-catalogue-setup>>).
|===

=== Generic Per-Phase States

A generic state is written `<phase>.x` and stands for one concrete state per unit in which it occurs: `<phase>` is replaced by the unit prefix (`refine.awaiting_answers`, `execute.baseline-red`). A generic state is defined once in <<state-catalogue-generic>>; its expansion table lists the units where it occurs. A unit table repeats a concrete expansion only where that expansion has behaviour beyond the generic definition (`refine.awaiting_answers`, `execute.baseline-red`, `finalize.baseline-red`). A generic state is a real state that a DSL transition targets; what the engine raises on any state of any unit (a pending operator decision, a footprint violation, an incomplete dispatch, configuration drift, store tampering, a guard that could not be evaluated) is a condition overlay (<<state-catalogue-conditions>>), not a generic state. `*.x` in other documents means the same as `<phase>.x`.

== Conditions (Overlays)

A condition is raised by the engine, not by a DSL transition, on whatever state the scope is in, in any unit, including a sub-workflow state and an `auto` state whose primitive raised it. It is recorded in `mcp/status.json` as `pending_condition` (`kind`, `decision_id` when an operator decision is pending, `facts`, `raised_at`; link:store-schemas.adoc#_workflow_state_store_mcpstatus_json[Store Schemas Specification, Workflow State Store]) while `state`, `phase`, and `call_stack` stay unchanged. While it is set, the representation keeps `state` as the current state id, names the condition in the field `condition` (link:hypermedia-format.adoc#canonical-top-level-fields[Hypermedia Format Specification, Canonical Top-Level Fields]), carries the condition's `facts`, and renders only the condition's links; the implicit `report_bypass` stays accepted and unrendered. Every other link of the state, declared or implicit, is not offered (`link_not_available`). A scope carries at most one condition. A decision resolution is routed like a primitive outcome of the state that raised the condition, through the Decision Registry (link:workflow-dsl.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]): inside a sub-workflow it stays inside the sub-workflow and `call_stack` is untouched. Conditions are never declared in a DSL unit and are never a transition target.

[#state-catalogue-finalize]
=== Phase 6: `finalize`

The start state of `finalize.pmwf` is `finalize.settle-commit`. The finalize steps of the manifest are executed in `order` (link:phase-workflows.adoc#_normative_step_catalogue_across_ordering_bands[Phase Workflows Specification, Normative Step Catalogue]); only the steps that have their own state are listed here. The branch-cleanup step (order `70`) runs as the merge path `finalize.merge-gate` -> `finalize.merge-lease` -> `finalize.merge-sync` -> `finalize.merge-evidence-wait` / `finalize.merge-barrier` -> `finalize.merge-gap` / `finalize.merge-dispatch` -> `finalize.merge-queue-wait`; its link states (`finalize.merge-lease-interrupted`, `finalize.merge-conflict`, `finalize.merge-sync-escalate`, `finalize.merge-remote-moved`, `finalize.merge-gap`, `finalize.merge-refused`, `finalize.merge-queue-exit`) hold no merge lease, and an unmerged plan leaves the path only through `abort-plan` or the approved `wind-down-unmerged` (`finalize.wind-down`). The `archive-plan` step (order `1100`) runs in `finalize.archive-plan`. A plan of source `pr` (lane `adopt`) enters Phase 6 through `finalize.adopt-pr`; its `sync-baseline` step (order `3`) only checks (it records the upstream commit count with action `noop` or `check` and never rebases), so the branch is rebased only in `finalize.merge-sync`. The state of every other manifest step (`sync-baseline`, `simplify`, `security-audit`, `pre-submission-self-review`, `architecture-refresh`, `pre-push-quality-gate`, `adr-propose`, the post-merge and post-run steps, `emit-landing`) is _(to be specified)_; a `mutates_source` step always routes through `finalize.settle-commit`. For a `land` plan every `loop_back` is replaced by `escalate`, `abort` (the request `abort-plan`), and `recapture`; the same holds for the model links of `finalize.merge-conflict` and `finalize.merge-remote-moved`. An `aborted` outcome of `git.commit_and_push` in a finalize `call` state enters `finalize.commit-aborted` (<<state-phase.commit-aborted>>).

[#state-catalogue-git]
== Sub-Workflow `git.commit_and_push`

Declared in `git-commit-and-push.pmwf` (`scope subworkflow`, start `git.inspect-worktree`). Every state declares `phase inherit`: the phase value is the caller's. Callers: `execute.chain-tail-commit`, `execute.remediation-commit`, `finalize.settle-commit`, `finalize.push-barrier`, `setup.land-changes`, `epic.commit-ledger`. Every caller routes the terminal outcome `aborted` (class `aborted`) to one of its own `link` states, never to its scope's abort terminal (link:workflow-dsl.adoc#static-verification-rules[Workflow DSL Specification, Static Verification Rule 6]).

The sub-workflow has three operator escalations (`gitignore_oracle_failure`, `force_stale_push`, `force_push_with_lease`); each `approved` exit enters an `auto` state performing the approved action (link:workflow-dsl.adoc#static-verification-rules[Static Verification Rule 10]): `git.stage-under-oracle-override`, `git.push-under-freshness-override`, `git.push-with-lease`. A hook failure is never bypassed (`git.commit-fix`), and a rebase conflict is resolved by the model (`git.resolve-conflicts`). Every caller routes `in_sync` like `pushed_clean`.

[#state-catalogue-setup]
== Project Setup: `setup` (workspace)

Declared in `project-setup.pmwf` (`scope workspace`), hosted by the project's workspace scope; phase value `workspace`. The single start state `setup.entry` routes every run by server facts: a first run to `setup.prepare-workspace`, a reconcile run to `setup.reconcile-config`. The unit has no terminal state: the workspace scope lives as long as the project's enrolment and rests in `setup.completed` between runs, whose `reconcile` link starts the next run. Enrolment (`pm-mcp operator enrol`) creates the workspace scope and is not a state of it; the first run creates `.marshall/` and `.marshall/config/` with the default workflow units, with no legacy input. `project-setup.pmwf` is compiled into the binary and never project-owned.
