== Overview

This document defines the normative hypermedia state representation format (HATEOAS) and deterministic Token-Oriented Object Notation (TOON) encoding rules for *plan-marshall-mcp* (`PM-MCP`). Every call to `pm_start`, `pm_state`, or `pm_do` returns an authoritative state representation rendered in TOON containing the scope identifier, closed state and phase names, optional vocabulary skill URI, contextual facts, and the set of valid hypermedia links.

Every workflow state representation is serialized as a top-level TOON object with a fixed canonical field ordering.

[#canonical-top-level-fields]
=== Canonical Top-Level Fields
_Implementation watch: link:../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-2[PM-WATCH-HYP-2], link:../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-3[PM-WATCH-HYP-3]_

[cols="1,1,1,3"]
|===
|Field |Presence |Type |Normative Definition

|`scope`
|Required
|Closed enum
|`"plan"`, `"epic"`, `"workspace"` (the project's workspace scope, which hosts `project-setup`), or `"entity"` (when queried by a dispatched leaf sub-agent with `entity`); `"none"` only in the refusal of a `pm_start` call (link:mcp-tools.adoc#pm-start-refusal[MCP Tools Specification, `pm_start` Refusals]), which also omits the fields that require a scope (`state`, `phase`, the scope identifier).

|`plan_id` / `epic_id`
|Required (one of), except for `scope: workspace`
|String
|The addressed plan identifier (`plan_id`) or orchestrator epic identifier (`epic_id`). A `workspace` representation carries neither; its project is the one named by the request's `PM-MCP-Workspace` header.

|`entity`
|Conditional
|String
|Present iff `scope == "entity"` (e.g., `envelope-2`, `F-12`).

|`state`
|Required
|Dotted enum
|Closed-enum state name (`<phase>.<step>[.<substate>]`, e.g., `finalize.concurrent-wait`, `execute.verify-sweep` (a job state, also while its job runs); every state is catalogued in the link:state-catalogue.adoc[State Catalogue]; while a sub-workflow is active, the active sub-workflow state, e.g., `git.compose-message`). Never a boolean.

|`condition`
|Conditional
|Closed enum
|Present iff the scope's `pending_condition` is set (link:store-schemas.adoc[Store Schemas Specification]): the condition kind (`blocked`, `footprint_violation`, `dispatch_incomplete`, `config_drift`, `store_tampered`, `guard_indeterminate`; link:state-catalogue.adoc#state-catalogue-conditions[State Catalogue, Conditions]). `state` stays the current state id; `facts` carry the condition and `links` list only the condition's links (link:workflow-dsl.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]).

|`phase`
|Required
|Closed enum
|Lifecycle phase (`init`, `refine`, `outline`, `plan`, `execute`, `finalize`, `completed`, `aborted`, `orchestrate`, or `workspace`, mapped 1:1 to `phase-1-init`..`phase-6-finalize`, `completed`, `aborted`, `orchestrator`, `workspace` in `status.json`; link:identifiers.adoc#id-phase[Identifier Registry, `phase`]).

|`summary`
|Required
|String
|Single-line human-readable status summary (`1..160` ASCII characters).

|`skill`
|Optional
|URI String
|URI of the vocabulary skill guiding model judgment in this state (`skill://pm/<path>/SKILL.md`; the DSL clause `skill pm/<path>` maps to `skill://pm/<path>/SKILL.md`). Omitted in purely deterministic states.

|`rejected`
|Optional
|Object
|Present only when the immediately preceding `pm_do` transition, or a `pm_start` call, was rejected (`link`, closed-enum `reason`, and diagnostic `detail`; link:mcp-tools.adoc[MCP Tools Specification], § Rejected Transition Representation and § `pm_start` Refusals). A refused `pm_start` returns a scope-less representation (`scope: none`) that carries only `rejected`, `facts`, and `links[0]`.

|`profile_warning`
|Optional
|Closed enum
|`client_identity_mismatch`, present when the calling host is not the client the scope was entered with, so the rendered dispatch and skill forms may not fit it (link:client-profiles.adoc[Client Profiles Specification], Mismatch Resolution & Audit Behavior). Serving through the `neutral` profile raises no warning: its links already carry the fallback, and the choice is recorded in the session row (<<model-facing-minimality>>).

|`facts`
|Required
|Object
|Minimal key-value map of domain facts required to exercise judgment in `state`, restricted to fields with a declared operational purpose (<<model-facing-minimality>>). Large payloads are referenced via `pm://` resource URIs.

|`links`
|Required
|Tabular TOON array
|`links[N]{rel,link,form,free}:` listing all transitions valid from `state`. Empty (`links[0]{rel,link,form,free}:`) only in terminal states (`PM-WF-1`).

|`dispatch`
|Conditional
|Object
|Present iff `links` contains a link with `form == "dispatch"`. Contains the pre-rendered host sub-agent invocation (`link`, `host_tool`, `params`, `prompt`).
|===

[#facts-content-rules]
=== Facts Content Rules
_See Requirement link:../Requirements.adoc#PM-TOOL-5[PM-TOOL-5: Tool Schema Stability & Context Budget Discipline]_

_Implementation watch: link:../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-5[PM-WATCH-HYP-5]_

The server renders `facts` under six general rules. Rules 1 to 5 apply to every representation and every resource derived from the same stores; rule 6 applies to every representation, tool result, and error payload:

1. *Server-Derived Counts Name Their Population*: Every count in `facts` (deliverables, files, tasks, findings) is derived by the server from the structured store at render time, never copied from authored text, and names its population in the key (for example `files_realized`, `files_declared`, `files_declared_unrealized`), so realized and declared-but-unrealized members are never mixed in one number.
2. *Population-Checked Aggregates*: A server-aggregated count or coverage figure (findings, reviewed comments, tokens, examined modules) is computed together with its population size. A zero over a non-empty population that structurally cannot be zero, or a figure whose population cannot be read, is rendered `indeterminate`, never `0` or "clean".
3. *Closed-Vocabulary Rule*: Every closed enumeration that classifies observed or judged input (statuses, dispositions, buckets, verdicts, linkage) contains an explicit out-of-set member (`unknown`, `indeterminate`, `not_applicable`, or `out_of_scope`, as fits). No member doubles as a stand-in for an unclassifiable case, and a malformed input is classified differently from an absent one.
4. *Truncation Is Reported*: Any server-side clamp of text (pull-request body sections, comment bodies against a provider's size cap such as 65,536 characters) reports `truncated: true` with the original and the kept length and cuts at a sentence or line boundary; text is never cut mid-sentence silently.
5. *Continuation Policy Is Always Rendered*: Every plan and epic representation carries `facts.continuation_policy` (`stop_at_phase_boundary` or `stop_on_issue_only`, persisted in `mcp/status.json`, link:store-schemas.adoc[Store Schemas Specification], Workflow State Store), and every rendered dispatch prompt carries it as the line `CONTINUATION: <policy>`, so the operator's standing instruction survives compaction and dispatch boundaries without being re-issued. With `stop_on_issue_only` the model continues across phase boundaries and stops only at an escalation, a `blocked` condition or state, or a state of kind `awaiting_user`. The policy is set only through the operator channel: the representations of phase-boundary states (where the policy takes effect) offer `continuation-policy` (rel `escalate`, no free parameters), which the server answers by MCP elicitation to the operator; `pm-mcp operator continuation-policy (--plan <plan_id> | --epic <epic_id>) <policy>` sets it at any time. A value relayed by the model is never accepted (`PM-WF-12`).
6. [[model-facing-minimality]]*Model-Facing Minimality*: A representation (its top-level fields, `facts`, and the `dispatch` block), a tool result (`pm_build`, `pm_lsp`, `pm_plans`, `pm_epics`, `pm_skills`, `pm_skill`, `pm_skill_file`), and an error payload (`rejected`, the `isError: true` envelope, JSON-RPC `error.data`) carry only information that changes what the model does next: the offered links and their parameters, the facts its judgement in the current state needs, the error it must correct, the identifiers it must pass back (`dispatch_id`, `job_id`, `decision_id`, `finding_id`, `entity`), and the text it must relay to the user or operator (`summary`, `facts.operator_command`). Everything else is recorded, never returned: the implementation variant that served an operation; derivation and provenance sources (`budget_derivation`, the `source` of a configuration value or a resolved limit, a build template's source); internal versions (`format_version`, `worktree_sha_version`, binary and relay versions) unless the model must act on them; confinement and sandbox details; lease and holder internals (`holder_instance`); digests and hashes the model makes no decision on (`worktree_sha`, `config_hash`, `input_digest`); calibration bases (`predicted_cost_basis`); timing internals (elapsed seconds, `derived_at`, `recorded_at`, job durations, learned-budget hygiene); retry bookkeeping; the internal job identifiers of a composite wait; tallies and populations that serve only metrics; and `audit_id`, except on the errors an operator must look up (`internal_fault`, `file_unreadable`). Such data goes to `audit.jsonl`, the metrics store, the job record, or the server log, and where a human or the operator needs it, it is served on demand by the operator surfaces (`pm-mcp status`, the `pm-mcp operator` CLI, and `pm://` resources such as `pm://project/config`), never pushed in a representation or tool result. When the model's judgement needs a count (for example the open blocking findings), the count is rendered and its population list is not; rules 1 and 2 name and check a population, they do not require rendering it. A build-time test (`ModelFacingFieldAuditTest`) walks every representation, tool-result, and error-payload record type and fails on any field that is not in the registry of model-facing fields, in which every entry declares its operational purpose (`link_parameter`, `pass_back`, `judgement`, `error_correction`, or `relay`); a new model-facing field is a registry change with a stated purpose.

=== Canonical Representation Example

`finalize.push-barrier` is a `call` state (`call git.commit_and_push`), so it is never a resting state: while the push barrier runs, the representation shows the active `git.*` sub-workflow state with `phase` inherited from the caller. The example shows `git.compose-message`, entered when the barrier (`message_mode=none_assert_clean`) finds unexpected uncommitted files:

[source,toon]
----
scope: plan
plan_id: plan-2026-042
state: git.compose-message
phase: finalize
summary: "push barrier found 2 uncommitted files, commit message required"
skill: "skill://pm/git/commit-message/SKILL.md"
facts:
  changed_files: 2
  continuation_policy: stop_at_phase_boundary
  module_scope: http
  suggested_type: fix
links[2]{rel,link,form,free}:
  next,commit,submit,"message:text[1..2000]"
  abort,abort,noop,""
----

== The Five Normative Link Forms
_See Requirement link:../Requirements.adoc#PM-WF-2[PM-WF-2: Closed Link Relation Grammar & Link Forms]_

_See Requirement link:../Requirements.adoc#PM-WF-8[PM-WF-8: Asynchronous Job Links & Wait Transitions]_

_See Requirement link:../Requirements.adoc#PM-IMPL-4[PM-IMPL-4: Bounded Long-Poll & Progress-Reset Waiting Primitives]_

Every row in `links[N]{rel,link,form,free}:` belongs to one of five closed link forms (`submit`, `wait`, `dispatch`, `escalate`, `noop`). The `form` column defines the interaction mechanics expected from the caller.

[cols="1,2,2,3"]
|===
|Link Form |Target Tool |`free` Column |Execution Semantics

|`submit`
|`pm_do(scope, link, args)`
|Non-empty typed parameter list (e.g., `"outline:text[1..65536]"`, `"disposition:enum[FIX\|SUPPRESS\|ACCEPT],reply_text:text[1..4000]"`)
|Submits model judgment artifacts or a sub-agent completion report (`returned:<dispatch_id>`) to the server. The server validates `args` against the link's closed schema before executing the backing primitive.

|`wait`
|`pm_do(scope, link, {})`
|`""` (empty)
|Monitors an asynchronous background job (`wait:<job_id>`), a composite wait state (`wait:<composite_id>`), or a pending operator decision of a `blocked` condition or of `execute.awaiting-infeasible-decision` (`wait:decision:<decision_id>`). Blocks up to the bounded wait window or, on a connection that qualifies, the progress wait bound with periodic MCP progress notifications (values in link:timeouts.adoc#waits[Timeouts & Budgets Specification]) and returns either the terminal state representation or the updated running representation of a job state.

|`dispatch`
|Host sub-agent tool (rendered in `dispatch.host_tool`) followed by `pm_do(scope, "returned:<dispatch_id>", args)`
|`""` on the `dispatch` row; companion `returned:<dispatch_id>` link has `form: submit`
|Instructs the parent session (the dispatching plan or epic session) to invoke its host sub-agent tool verbatim using `dispatch.host_tool`, `dispatch.params`, and `dispatch.prompt`. The sub-agent executes in leaf entity scope; once it finishes, the parent reports completion via `returned:<dispatch_id>`. *Pairing rule*: every `dispatch:<entity>` row is paired with exactly one `returned:<dispatch_id>` row of its active dispatch, with one exception: a reader dispatch (`execution-context-reader`) is paired with `ingest_candidates:<dispatch_id>` (rel `submit`, form `submit`) instead, which carries the candidate payload and the return fields together (link:dispatch-and-effort.adoc#_reader_agent_family_execution_context_reader[Dispatch & Effort Specification, Reader Agent Family]). The recovery links of a dispatch are defined in <<dispatch-recovery-links>>.

|`escalate`
|`pm_do(scope, link, args)` -> triggers MCP Elicitation or the `blocked` condition's operator wait
|Declared per decision kind in the Decision Registry (link:workflow-dsl.adoc#decision-registry[Workflow DSL Specification, Decision Registry]): for example `"reason:text[1..500]"` (plus optional structured target parameters such as `target_project:text`), the question envelope of `escalate:TASK-NNN` (`"question:schema[question-envelope]"`, <<named-parameter-schemas>>), or `""` for `continuation-policy`
|Requests an operator decision that the model is not permitted to take. If the host supports MCP elicitation, prompts the user directly; otherwise records the pending decision and raises the `blocked` condition on the current state (`condition: blocked`, `state` unchanged), emitting the `pm-mcp operator` CLI command in `facts` and offering only the link `wait:decision:<decision_id>` (rel `wait`), a bounded wait on that decision record.

|`noop`
|`pm_do(scope, link, {})`
|`""` (empty)
|Triggers a deterministic server-side transition that requires zero free judgment parameters from the model (for example `push`, `cancel:<job_id>`, `sync`, or advancing a green gate).
|===

=== Sub-Agent Dispatch Block (`form: dispatch`)
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-10[PM-WATCH-DISP-10]_

When a state offers a `dispatch` link, the representation includes a top-level `dispatch` object pre-rendered through the scope's client profile:

[source,toon]
----
scope: plan
plan_id: plan-2026-042
state: execute.dispatch-ready
phase: execute
summary: envelope-2 ready for dispatch (3 tasks)
facts:
  continuation_policy: stop_on_issue_only
links[2]{rel,link,form,free}:
  dispatch,"dispatch:envelope-2",dispatch,""
  submit,"returned:dsp-0001-a9f3c2",submit,"status:enum[success|error|loop_back|blocked|harness_cancellation],display_detail:text[1..80],token_usage:int[1..10000000]?,input_tokens:int[0..10000000]?,output_tokens:int[0..10000000]?,cache_read_input_tokens:int[0..10000000]?,cache_creation_input_tokens:int[0..10000000]?,tool_uses:int[0..100000]?"
dispatch:
  link: "dispatch:envelope-2"
  host_tool: Agent
  params:
    subagent_type: "plan-marshall-execution-context-level-4"
  prompt: "name: envelope-2\ndispatch_id: dsp-0001-a9f3c2\nplan_id: plan-2026-042\nentity: envelope-2\nskills: skill://pm/execute/task/SKILL.md, skill://pm/domain/java/core/SKILL.md\nWORKTREE: /home/dev/repo/.marshall/local/worktrees/plan-2026-042\nCONTINUATION: stop_on_issue_only\nstart: pm_state(plan_id=\"plan-2026-042\", entity=\"envelope-2\", dispatch_id=\"dsp-0001-a9f3c2\")"
----

`WORKTREE` is the canonical absolute path of the plan's worktree root (`Path.toRealPath()`, as stored in `status.json` `worktree_path`), so a host without a durable working directory resolves it against no root; it is rendered by the server and is never a model input, so `PM-TOOL-1` is unaffected. The `returned:` row shows the usage parameters of a profile declaring `dispatch.token_usage_components: all` and `dispatch.reports_tool_uses: true`; the server renders only the parameters the active profile can report, and it measures `duration_ms` itself (link:dispatch-and-effort.adoc[Dispatch & Effort Specification], Normative Schema for `returned:<dispatch_id>`). The total `token_usage` never accepts `0`; a component may be a measured `0`.

[#dispatch-recovery-links]
==== Dispatch Recovery Links

Two entity-addressed links recover a dispatch that did not end in a confirmed submission. Both address the dispatched entity, never the `dispatch_id`, take no free parameters, and are defined with the dispatch lifecycle in link:dispatch-and-effort.adoc#dispatch-recovery-links[Dispatch & Effort Specification, Dispatch Recovery Links]; their relation and form satisfy the closed relation table (<<_closed_link_relations_rel>>) and workflow-dsl Rule 12 (`LinkRelation` / `LinkForm`, link:workflow-dsl.adoc#static-verification-rules[Workflow DSL Specification]):

[cols="1,1,1,3"]
|===
|Link |`rel` |`form` |Semantics

|`redispatch:<entity>`
|`retry`
|`noop`
|Offered beside a `dispatch:<entity>` whose dispatch is `ALLOCATED` or `CLAIMED`. Supersedes that dispatch and re-offers the entity's remaining work as a fresh `dispatch:<entity>` with a new `dispatch_id`.

|`resume:<entity>`
|`next`
|`noop`
|Offered only by the `dispatch_incomplete` condition (link:state-catalogue.adoc#condition-dispatch_incomplete[State Catalogue, Conditions]). Records the dispatch `RETURNED` when the entity's required `submit` is now recorded; otherwise supersedes it and re-offers the remaining work as a fresh `dispatch:<entity>`.
|===

[#self-report-link]
=== Self-Report Link (`report_bypass`)
_See Requirement link:../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

`report_bypass` (rel `submit`, form `submit`, free `action:text[1..500],reason:text[1..1000]`) is an implicit engine link (link:workflow-dsl.adoc#implicit-job-links[Workflow DSL Specification, Implicit Links]): `pm_do` accepts it in every state of a live plan, epic, or entity scope, terminal states included (never for an archived plan), but it is never rendered in `links`, so rendered link sets (the single `wait:decision:` link of a `blocked` condition, `links[0]` of a terminal state) stay exact. Its only announcement is rule (7) of the always-loaded core skill `skill://pm/core` (link:mcp-tools.adoc[MCP Tools Specification], Core Conduct Vocabulary). It is the link with which the model reports an action it took outside the offered links: a bypass of a sanctioned path, a direct read or write of `.marshall/`, or a host tool call that replaced a missing link. Following it writes an audit record (`category: transition`, `event: self_report`) and files a `self_report` finding (link:store-schemas.adoc[Store Schemas Specification], Findings Ledger Record), then returns the unchanged current representation; it never changes the scope's state and is never refused for its content beyond the parameter bounds. It is accepted in every state because a bypass cannot be anticipated by state, and not rendered because it would add the same link to every representation.

The server can observe writes to digest-protected stores and changes to the worktree footprint, but not host-side reads of `.marshall/` or host actions that leave no store or footprint change. Those remain an accepted residual risk (`PM-SEC-1`): they are visible only when self-reported.

== Closed Link Relation & Identifier Grammar
_See Requirement link:../Requirements.adoc#PM-WF-2[PM-WF-2: Closed Link Relation Grammar & Link Forms]_

_See Requirement link:../Requirements.adoc#PM-WF-3[PM-WF-3: Capability Enforcement by Link Omission]_

=== Closed Link Relations (`rel`)

Every link's `rel` column is drawn from a closed enumeration of 11 relation identifiers:

[cols="1,1,3"]
|===
|`rel` Value |Allowed Forms |Semantic Meaning

|`next`
|`noop`, `submit`
|Default forward transition along the primary workflow path.

|`alt`
|`noop`, `submit`
|Alternative forward transition (e.g., `skip_recipe` to proceed with standard planning, or re-committing before push). The planning lane is never a model-selected link: it is computed by the server.

|`retry`
|`noop`
|Repeat the last failed deterministic operation (build, push, CI fetch) without changing code, or supersede an unconfirmed dispatch and re-offer its entity (`redispatch:<entity>`, <<dispatch-recovery-links>>).

|`fix`
|`noop`, `submit`, `dispatch`
|Enter a remediation sub-state or allocate fix tasks for a failed build or gate finding.

|`loop_back`
|`noop`, `submit`
|Return from `finalize` to `execute` in the plan's worktree by allocating fresh remediation tasks (subject to `in_worktree` and `max_iterations`).

|`submit`
|`submit`
|Deliver model-authored judgment output or sub-agent return status to the server.

|`dispatch`
|`dispatch`
|Launch a leaf sub-agent for an entity envelope, module, or untrusted-content reader task.

|`wait`
|`wait`
|Block on a running asynchronous job or composite wait state.

|`escalate`
|`escalate`
|Request operator intervention or cross-project approval through the operator channel.

|`abort`
|`noop`, `submit`
|Cancel a running job (`cancel:<job_id>`) or leave a sub-workflow or phase flow, which returns the outcome `aborted` to its caller. Ending the whole plan or epic is never an `abort` link: it is the operator decision `abort-plan` or `abort-epic`, requested through an `escalate` link (link:workflow-dsl.adoc#decision-registry[Workflow DSL Specification, Decision Registry]).

|`emit`
|`noop`, `submit`
|Epic-only relation: mark a staged plan in the epic ledger as launched and emit its `pm-mcp enter` bootstrap command.
|===

[#link-identifier-grammar]
=== Link Identifier Grammar (`<action>`, `<action>:<entity_id>`, `<action>:decision:<decision_id>`)

Link identifiers (`link` column) are server-derived, stateless tokens of the form `<action>`, `<action>:<entity_id>`, or `<action>:decision:<decision_id>`. Their grammar and length bounds (action name, entity identifier, and the whole link identifier) are defined in the link:identifiers.adoc#id-link-id[Identifier Registry]; the three forms have the following semantics:

1. *Scope-Wide Link (`<action>`)*: An action name alone (for example `push`, `commit`, `refine`, `outline`, `escalate`, `loop_back`); it applies to the entire `plan_id` or `epic_id` scope.
2. *Entity-Addressed Link (`<action>:<entity_id>`)*: An action name, `:`, and a link:identifiers.adoc#id-entity-id[entity identifier] (for example `triage:F-12`, `submit:TASK-004`, `dispatch:envelope-2`, `redispatch:envelope-2`, `returned:dsp-0001-a9f3c2`, `ingest_candidates:dsp-0002-7c01de`, `wait:b-2291`, `cancel:b-2291`, `wait:finalize.concurrent-wait`); it is validated against both the scope's state and the addressed `<entity_id>`'s state under the scope lock (`PM-WF-4`).
3. *Decision-Addressed Link (`<action>:decision:<decision_id>`)*: An action name, `:decision:`, and a link:identifiers.adoc#id-decision-id[`decision_id`]; it addresses a pending operator decision record. The only such link is `wait:decision:<decision_id>` (for example `wait:decision:dec-7f3a`), offered as the sole link of a `blocked` or `store_tampered` condition and of `execute.awaiting-infeasible-decision` (link:workflow-dsl.adoc#escalation-decision-wait[Workflow DSL Specification]); it is valid only while that decision is pending.

=== Free Parameter Descriptor Grammar (`free` Column)

The `free` column specifies the closed schema for `pm_do(..., args)` in compact human- and model-readable form:

[source,ebnf]
----
free_spec     = "" | param_decl , { "," , param_decl } ;
param_decl    = param_name , ":" , param_type , [ "?" ] ;
param_name    = lowercase_alpha , { lowercase_alpha | digit | "_" } ;
param_type    = scalar_type
              | "list<" , scalar_type , ">" ;
scalar_type   = "text" , [ int_range ]
              | "int" , [ int_range ]
              | "enum[" , enum_val , { "|" , enum_val } , "]"
              | schema_ref ;
schema_ref    = "schema[" , schema_name , "]" ;
schema_name   = lowercase_alpha , { lowercase_alpha | digit | "-" } ;   (* identifiers.adoc, named parameter schema *)
int_range     = "[" , int , ".." , int , "]" ;
enum_val      = alpha , { alpha | digit | "_" | "-" } ;
int           = "0" | nonzero_digit , { digit } ;
alpha         = lowercase_alpha | uppercase_alpha ;
lowercase_alpha = ? ASCII "a".."z" ? ;
uppercase_alpha = ? ASCII "A".."Z" ? ;
digit         = "0" | nonzero_digit ;
nonzero_digit = ? ASCII "1".."9" ? ;
----

`param_name` is bounded as registered in the link:identifiers.adoc#id-param-name[Identifier Registry]. `param_type` mirrors the DSL `type_spec` (link:workflow-dsl.adoc[Workflow DSL Specification]): lists use the single syntax `list<…>` (for example `paths:list<text>?`), enum values may contain upper case (`enum[FIX|SUPPRESS|ACCEPT]`), and there is no free-form object type: the only object-valued type is the named schema reference `schema[<schema_name>]` (<<named-parameter-schemas>>), also as a list element (`list<schema[<schema_name>]>`).

[#named-parameter-schemas]
==== Named Parameter Schemas

A parameter of type `schema[<schema_name>]` takes a JSON object as its value; the server validates it against the closed JSON Schema (`additionalProperties: false` at every object level) registered under `<schema_name>`, in the same in-process validation as every other parameter (link:workflow-dsl.adoc#independent-transition-validation[Workflow DSL Specification, Independent Server-Side Transition & Parameter Validation], step `P`). A violation is rejected with `invalid_link_args`, and `rejected.detail` names the parameter and the JSON pointer of the offending member. `schema_name` follows the link:identifiers.adoc#id-schema-name[Identifier Registry, named parameter schema] grammar. Named schemas are compiled into the binary beside the workflow definitions and are closed: a new name, or a change of a registered schema, ships only with a workflow version. A `schema[…]` type naming an unregistered schema fails DSL validation (Rule 1, link:workflow-dsl.adoc#static-verification-rules[Workflow DSL Specification, Static Verification Rules]). A named schema describes only model-supplied members; server-owned fields are never part of it, and a payload carrying one is rejected by `additionalProperties: false`.

|===
|`schema_name` |Content |Used by

|`question-envelope`
|The model-supplied part of the sub-agent question envelope (`BatchedQuestionEnvelope` without the server-owned `question_id`, `source_entity`, and `prompt_kind`): `question_text`, `default_assumption`, and `options` as objects `{branch_key, label, description, recommended?}`; definition in link:dispatch-and-effort.adoc#question-envelope-schema[Dispatch & Effort Specification, Prompt Envelopes & Entity Escalation Protocol]

NOTE: Boolean parameters are prohibited in workflow transitions to preserve explicit closed-enum intent (e.g., `decision:enum[approve|reject]` rather than `approved:bool`). A trailing `?` marks an optional parameter (such as `token_usage:int[1..10000000]?` or the component `cache_creation_input_tokens:int[0..10000000]?`).

=== Direct In-Band Multi-Line Text Payloads (`PM-WF-2`, `PM-WF-6`)

Because `pm_do(scope_id, link, args)` is transported as a structured JSON-RPC 2.0 request over `stdio`, parameters of type `text[min..max]` accept arbitrary multi-line UTF-8 strings (including Markdown headings `#`, fenced code blocks, quotes, shell metacharacters, and Unicode) directly in `args`:

* *No Scratch-File Staging*: The model never invokes host `Write` or `Edit` tools on `.marshall/` files and never creates staging files of the kind `plan-marshall` needed (`.plan/temp/*-commit-msg.txt`, `work/ci-bodies/*.md`, `work/pending-tasks/*.json`, `work/lesson-body-*.md`). This is a model-facing rule, not a prevention: host file tools can still write `.marshall/`. The runtime detects such a write after the fact, on the next transition that reads a digest-protected store (`store_tampered`, link:store-schemas.adoc[Store Schemas Specification], § Store Digest Verification); writes to files outside the digest-protected set are not detected.
* *Single-Turn Atomic Validation & Persistence*: When the model follows a `submit` link such as `commit` (`message:text[1..2000]`), `submit:outline` (`outline:text[1..65536]`), `create_pr` (`body:text[1..32768]`), or `triage:F-12` (`disposition:enum[FIX|SUPPRESS|ACCEPT],reply_text:text[1..4000]`), the server validates both the parameter bounds and the domain content grammar in-process before persisting the target store or streaming the payload to a child tool via `stdin` (`PM-EXEC-5`).
* *Self-Correcting Validation Feedback*: If a submitted multi-line payload violates a structural rule (for example, an `outline` missing a `(read|write-new|write-replace|write-conditional|delete)` file-intent suffix, or a `message` violating Conventional Commits syntax), the server leaves the state unmutated and returns `rejected.reason = "invalid_link_args"` with exact line-level `detail` alongside the current TOON representation so the model can resubmit immediately in the next turn. `rejected.detail` names the offending parameter or token, the expected shape (the schema fragment), and one corrected example.

== Composite Wait Representation & Short-Circuit Semantics
_See Requirement link:../Requirements.adoc#PM-WF-8[PM-WF-8: Asynchronous Job Links & Wait Transitions]_

_See Requirement link:../Requirements.adoc#PM-WF-9[PM-WF-9: Composite Wait States & Short-Circuit Failure Handling]_

During Phase 6 (`finalize`), CI verification and automated PR review bots run concurrently after branch push. Rather than forcing the model to poll two separate jobs sequentially, the workflow engine exposes the composite wait state `finalize.concurrent-wait`.

=== `finalize.concurrent-wait` Representation

[source,toon]
----
scope: plan
plan_id: plan-2026-042
state: finalize.concurrent-wait
phase: finalize
summary: "waiting on CI run (running) and review bot (pending)"
facts:
  bot_status: pending
  bots[1]{bot_kind,roster_class,state,refusal_mode,completion_check,at_head}:
    coderabbit,required,in_progress,none,pending,false
  ci_status: running
  continuation_policy: stop_on_issue_only
  pr_number: 184
links[2]{rel,link,form,free}:
  wait,"wait:finalize.concurrent-wait",wait,""
  abort,"cancel:finalize.concurrent-wait",noop,""
----

Both links are the implicit links of the `composite_job` state (link:workflow-dsl.adoc#implicit-job-links[Workflow DSL Specification]); they are never declared in DSL source. The constituent job identifiers (the CI job and the review-bot job), the branch, and the elapsed wait time are recorded in the scope's `mcp/status.json` and the job records and shown by `pm-mcp status`; they are never rendered, because both links address the composite, not a constituent job (<<model-facing-minimality>>).

=== Closed Status Enumerations in `finalize.concurrent-wait`
_Implementation watch: link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-26[PM-WATCH-PHASE-26]_

* `ci_status`: `running` | `passed` | `failed` | `not_triggered` | `cancelled`. CI evaluation excludes check-runs owned by registered review bots: a review bot is not a build check.
* Per-bot `state` (one row of `facts.bots` per tracked bot, rendered separately from its `completion_check` and `at_head` evidence, because participation, a finished completion check, and a green check prove different things): `participated` | `participated_but_empty` | `participated_stale` | `refused` | `declined` | `absent` | `not_triggered` | `not_wired` | `rereview_silent_failure` | `run_stuck` | `in_progress` | `unproven` | `unreadable` | `silent` | `unsatisfiable` | `unregistered_kind`.
** `refusal_mode` (set only for `refused`, otherwise `none`): `rate` | `weekly_quota` | `size` | `no_unreviewed_commit` | `unknown`.
** `completion_check`: `passed` | `pending` | `failed` | `not_declared`; `at_head`: `true` | `false`.
** The three "nobody reviewed" shapes stay distinct: `not_triggered` (never triggered), `rereview_silent_failure` (a re-review failed silently), and `run_stuck` (the bot's run never left the queue).
** An exhausted poll yields `unproven`, never `absent`. `unreadable` (the read failed) and `silent` (the read succeeded and nothing was published) are opposite claims and are never merged.
** `declined` requires review evidence naming a commit that is not the merge candidate; evidence that names no commit resolves `unproven`. A fetch that returns zero comments resolves to exactly one of: no review covering `HEAD` (`absent` or `unproven`), reviewed clean (`participated_but_empty`), or fetch unreachable (`unreadable`).
* `bot_status` is the aggregate over the required bots only (optional bots are reported in `facts.bots` but never gate): `pending` | `running` | `completed` | `not_configured` | `unestablished` | `refused_awaitable` | `refused_hard` | `refused_structural` | `no_unreviewed_commit` | `unproven` | `cancelled`.
** `completed`: every required bot is `participated` or `participated_but_empty` for the current `HEAD`.
** `not_configured`: the required set is empty and the operator answered it so (roster aggregate `vacuous`); the merge is recorded with `review_state: vacuous`.
** `unestablished`: the required set is empty because the roster question was never put or the roster was migrated (roster aggregate `unestablished`); it never passes as reviewed and needs a `review_barrier_gap` grant.
** `refused_awaitable`: a required bot refused with mode `rate` and the registry classifies its rate limit as an awaitable window.
** `refused_hard`: a required bot refused with mode `weekly_quota` or `unknown`, or with mode `rate` under a hard or unknown rate-limit class (spend cap, quota exhaustion); waiting cannot recover it.
** `refused_structural`: a required bot refused with mode `size` (the diff exceeds the bot's structural cap).
** `no_unreviewed_commit`: a required bot refused with mode `no_unreviewed_commit`.
** `unproven`: the poll budget, derived from the bot's registered interval, is exhausted while a required bot is in any other non-participating state.
** `not_configured` and `unestablished` arise only for an empty required set. When required bots differ, the first matching value in the order `cancelled`, `refused_structural`, `refused_hard`, `running`, `pending`, `unproven`, `no_unreviewed_commit`, `refused_awaitable`, `completed` is the aggregate.

== Deterministic Native TOON Encoder Specification
_See Requirement link:../Requirements.adoc#PM-IMPL-3[PM-IMPL-3: Deterministic Native TOON Encoder]_

`pm-mcp-core` implements a dedicated, zero-reflection Java TOON encoder (`ToonEncoder`) conforming to the official TOON specification for the subset emitted by PM-MCP. The specification version is pinned after verifying the current official specification and its conformance fixtures in Milestone 1 (`PM-IMPL-3`). The rules below restate the official syntax for that subset and add PM-MCP's determinism rules (Rules 1–3), which the official specification permits. Given identical input records, `ToonEncoder` produces byte-for-byte identical UTF-8 output across JVM and GraalVM native image executions.

=== Encoding Rules
_Implementation watch: link:../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-4[PM-WATCH-HYP-4]_

1. *Character Encoding & Line Endings*: UTF-8 without BOM; line separator is strictly `LF` (`\n`, `0x0A`), and `CR` (`\r`) never appears outside escaped string literals. Every encoded document ends with a single trailing `\n`, and no line may contain trailing spaces (`0x20`).
2. *Indentation*: Exactly 2 ASCII spaces (`"  "`) per nesting level; tabs (`\t`) are never used for indentation.
3. *Key Ordering*: Top-level representation keys follow the fixed canonical order defined in <<canonical-top-level-fields>>. Java `Record` types serialize components in their declared record component order, dynamic `Map<String, ?>` containers (such as `facts`) sort keys in deterministic ASCII lexicographical order (`String::compareTo`), and keys with `null` or `Optional.empty()` values are omitted completely (never serialized as `key: null`).
4. *Scalar Formatting & Quoting*: Integers use base-10 ASCII digits (`-?[0-9]+`) with no leading zeroes or thousands separators. A string value is emitted unquoted if and only if it is non-empty, has no leading or trailing whitespace, contains no control characters (`0x00..0x1F`, `0x7F`), contains none of the characters the official specification reserves (such as the active delimiter `,`, `:`, `"`, `\`, brackets, and braces), and does not match `true`, `false`, `null`, or a numeric literal. All other strings, including multi-line strings such as `dispatch.prompt`, are enclosed in `"` using only the official escapes `\\`, `\"`, `\n`, `\r`, and `\t`; there are no block literals. The exact set of characters that forces quoting follows the pinned official specification (minimal quoting).
5. *Primitive Arrays*: Lists of scalar strings or integers (`List<String>`, `List<Integer>`) serialize inline with a length header as `key[N]: val1,val2,val3`, applying scalar quoting per element.
6. *Tabular Object Arrays*: Homogeneous lists of records (such as `links` and `failures`) serialize using the official TOON tabular header syntax `<field_name>[<row_count>]{<col_1>,<col_2>,...,<col_k>}:` where `<row_count>` is the exact decimal count of rows (`0` or more), column names are comma-separated with no spaces, and each row is indented 2 spaces deeper with cells quoted per Rule 4 when necessary.
