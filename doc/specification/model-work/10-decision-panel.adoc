[#decision-panel]
== Recommendation Score & Decision Panel
_See Requirements link:../../Requirements.adoc#PM-WF-18[PM-WF-18: Question Recommendation Score & Decision Panel], link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides], link:../../Requirements.adoc#PM-WORK-6[PM-WORK-6: Role Qualification], link:../../Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-45[PM-WATCH-DISP-45]_

Every question carries a recommendation and a score that says how sure the asker is of it. In the question mode `panel` the server adjudicates every question set before it is delivered: it asks the panel roles its adjudication unit declares the same questions without showing them the recommendation and answers the set itself where the asker and the panel agree with confidence; every other set reaches the user as in mode `auto`, with every system's answer shown. Question records, their delivery, the modes, and the deadlines are specified in xref:06-envelopes-questions-deadlines.adoc#question-records[Question Records]; this part specifies the score, the panel, the adjudication, and the panel's calibration. The panel exists for model diversity: the asking roles run on one harness and its models, the panel roles on other harnesses and models, so an automatic decision rests on judgments that do not share one model's blind spots.

[#recommendation-score]
=== Recommendation Score

*Asked by a task*: Every question a task creates (`ask`, `ask:TASK-NNN`, an item of a `questions` list) carries, in its question envelope (xref:06-envelopes-questions-deadlines.adoc#question-envelope-schema[Question Envelope]):

* exactly one option with `recommended: true`, the asker's choice;
* `recommendation_confidence`, an integer `0` to `100`: the asker's confidence that the recommended option is right;
* `rationale`, `10` to `500` characters: why the asker recommends it, naming the evidence;
* `decision_kind`, one value of the closed set of <<decision-kinds>>.

A payload without them, or with no or several recommended options, is refused `invalid_link_args`, and the worker submits again.

*Raised by the server*: A question a server primitive raises carries the primitive's recommended option, its score mapped to `0` to `100`, a server-composed rationale (the scores the choice rests on), and the kind the adjudication unit declares for it (<<panel-configuration>>; the column below shows the shipped declaration). A primitive that computes no score, and a question without a recommended option, scores `0`.

|`approach`
|The top recipe score times `100` (link:../domain-extensions/05-recipes-and-extension-points.adoc[Domain Extensions Specification, Tier-1 Init Routing]).

|`init.sibling-collision` (`kind_sibling_collision`)
|`scope`
|`0`.

|`init.domain-choice` (`kind_domain_choice`)
|`placement`
|The top domain's share of the detection scores times `100`; `0` without a unique top score.

|`outline.review` (`kind_outline_review`)
|`scope`
|`0`.

|Workspace setup choices (class `setup`, `kind_setup_choice`)
|`external_fact`
|`0`.
|===

*Question set and its score*: The questions of one creation form a *question set*: one `ask` or `ask:TASK-NNN` (one question), one `submit` with its `questions` list, or one server primitive. Every record of a set names the set by the `question_id` of its first question (`question_set`, link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]). The set's *score* is the lowest `recommendation_confidence` of its questions.

*Shown everywhere*: The recommendation, its confidence, and its rationale are persisted with the record and shown on every delivery channel: the web app (link:../cli-and-security/03-web-server.adoc[CLI, Coordination & Security Specification, Web Access]) and the answer links of the entry session (link:../hypermedia-format/01-representation-and-link-forms.adoc#question-waiver-and-exit-links[Hypermedia Format Specification, Task, Answer, Waiver-Request & Exit Links]).

[#decision-kinds]
=== Decision Kinds

The kind says what a question decides, and so whether a model may decide it at all. The set is closed; a kind a model cannot judge from the repository and the plan is excluded from automatic decisions by default.

[cols="2,4,1"]
|===
|`decision_kind` |The question decides |Shipped `auto_kinds`

|`interpretation` |What an aspect of the request or of a finding means. |yes
|`approach` |Which of several technical ways the plan takes. |yes
|`granularity` |How the work is cut into deliverables or plan tasks. |yes
|`placement` |Where a change belongs (module, package, file, domain). |yes
|`test_strategy` |How a change is tested. |yes
|`scope` |What is in or out of the plan, compatibility, and follow-up work. |no
|`product_behaviour` |Behaviour a user or a client of the product sees, contracts included. |no
|`assurance` |How much security, review, or verification a change needs. |no
|`external_fact` |A fact or an organisational decision outside the repository and the plan. |no
|===

A worker chooses the kind that fits the question best; where two fit, the role skill directs it to the one of them that is not in the shipped `auto_kinds`.

[#panel-configuration]
=== Panel Configuration: Role Artifacts & the Adjudication Unit

Everything that shapes an automatic decision is configuration that can be read, verified, and changed without a code change, and none of it is an operator key: the *role artifacts* of the panel roles (harness, model, effort, skills; xref:01-roles-and-configuration.adoc#roles[Roles as Configuration Artifacts]) and the *declarations* of the project's adjudication unit `question-adjudicate.pmwf`, a project-owned unit in `.marshall/config/` (git-tracked, reviewed like code, link:../workflow-dsl/02-units-jobs-decisions.adoc#unit-declarations[Workflow DSL Specification, Unit Declarations]). The operator decides only who answers a class's questions (`questions.mode`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]): the adjudication acts in the classes whose effective mode is `panel` (xref:06-envelopes-questions-deadlines.adoc#question-delivery[Delivery, Mode & Server-Owned Deadlines]).

[cols="2,2,2,4"]
|===
|Declaration |Shipped |Compiled bounds |Meaning

|`panel_roles`
|`[panel-a, panel-b]`
|`1` to `2` distinct role names
|The panel roles, named from the effective role set.

|`quorum`
|`2`
|`2` to one more than the number of panel roles
|How many systems must agree. The asker, or the primitive of a server-raised question, counts as one system; each available panel role counts as one.

|`min_score`
|`90`
|`80` to `100`
|The lowest confidence of an agreeing answer, and of a dissent that blocks.

|`auto_kinds`
|`interpretation`, `approach`, `granularity`, `placement`, `test_strategy`
|a subset of the shipped list
|The decision kinds that may be decided automatically.

|`asker_must_win`
|`false`
|`true` or `false`
|`true`: a set is adjudicated only when its score is at least `min_score`, and decided only on the asker's recommended option. `false`: the asker is one system among the others, so the panel roles can decide a question the asker was unsure of.

|`panel_wait_seconds`
|`900`
|`60` to `1800`
|The bound of the adjudication from the set's creation (link:../timeouts/01-job-budgets-and-waits.adoc#panel-wait[Timeouts & Budgets Specification, Panel Wait]).

|`max_false_auto_percent`
|`5`
|`0` to `10`
|The calibration level: the highest share of false automatic decisions at which a kind qualifies (<<panel-calibration>>).

|`kind_<server question>`
|the kinds of the server-question table (<<recommendation-score>>)
|the shipped kind, or a kind not in the shipped `auto_kinds`
|The kind of each server-raised question.
|===

A project unit can only tighten: no declaration can admit a kind outside the shipped `auto_kinds`, let one system decide alone, or lower `min_score` below its compiled floor; the bounds are checked on every load of the unit (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants], `INV-ADJ-1`). The question states of a plan run the project's unit bound in the plan instance; the question states of the epic, workspace, and bootstrap units run the binary's default unit, like every sub-workflow those compiled-only units call. Every adjudication record carries the declarations it applied with their source (`unit` with the unit's digest, or `compiled` for the default unit), so decisions stay comparable across projects (xref:11-decision-records.adoc#decision-record-content[Decision Records, Content]).

*Asking roles*: The asking roles of a project are the roles of every `job llm` state of its composed units whose task entities offer `ask`, `ask:TASK-NNN`, or a `submit` with a `questions` list.

*Available systems*: A declared panel role is *available* for an adjudication when its effective artifact is valid, its harness is eligible as a worker host and enrolled on the machine, it has a valid qualification record (xref:01-roles-and-configuration.adoc#qualification-records[Qualification Records]), and its start-failure guard does not hold (xref:03-supervision-and-recycling.adoc#start-failure-guard[Start-Failure Guard]). A panel role whose artifact fails only with `harness_not_eligible` or `harness_unknown` is unavailable, not invalid: a panel role on a harness that is not yet eligible as a worker host stays unavailable until it is. The *systems* of an adjudication are the asker and every available panel role; an unavailable role gets no task and is recorded with the outcome `unavailable`. With the shipped quorum `2`, the asker and one available panel role must agree; when both panel roles are available, all three answer and a confident dissent of any one blocks the decision. When fewer systems are available than `quorum`, the set is delivered with the reason `panel_unavailable`, without a task.

*Validation*: The unit load checks the declarations against their bounds; every composition of a plan instance or an epic workflow in a project where a class's effective mode is `panel` checks the panel against the effective role set, refusing the composition with the reason, the rule, and the role (link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Rule 13]); every adjudication checks it again, because a role artifact may change later:

[cols="2,5"]
|===
|Reason |Rule

|`panel_invalid`
|A panel role is not defined by the effective role set (absent, or invalid for a reason other than its harness's eligibility or enrolment, xref:01-roles-and-configuration.adoc#role-validation[Validation]), its class is not `read_only`, or it sets `session_first`.

|`panel_not_diverse`
|A panel role names the same model as an asking role or as another panel role, on any harness (model identifiers compared without a `<provider>/` prefix).
|===

The choice of a panel model is configuration: the shipped panel defaults are the configuration that passed the panel calibration on the release's corpus (<<panel-calibration>>), and the model a project runs follows from its own calibration, never from a fixed rule.

[#adjudication]
=== The Adjudication (`question.adjudicate`)

Every question state runs the sub-workflow `question.adjudicate` (the project's unit in a plan, the default unit elsewhere, <<panel-configuration>>) for the scope's new question set before the set is delivered (unit, states, and binding: link:../workflow-dsl/02-units-jobs-decisions.adoc#question-adjudicate-unit[Workflow DSL Specification, Adjudication Unit]; rows: link:../state-catalogue/13-question-adjudication.adoc[State Catalogue, Question Adjudication]). While it runs, the set's records are open and not yet delivered: no answer link, no web entry, and no deadline.

. *Check*: The set is adjudicated only when its class's effective mode is `panel`, the panel passes the validation (<<panel-configuration>>), at least `quorum` systems are available, every question's `decision_kind` is in `auto_kinds` and qualified by the panel's calibration (<<panel-calibration>>), and, with `asker_must_win`, the set's score is at least `min_score`. Otherwise the unit ends `delivered` at once, with the reason `mode`, `panel_invalid`, `panel_not_diverse`, `panel_unavailable`, `kind_ineligible`, `kind_unqualified`, or `below_score` (in a mode other than `panel` nothing is recorded).
. *Panel tasks*: The server creates one task per available panel role, each for its own entity of the kind `panel` (`panel-<question_set>-<role>`), through the model caller and the task protocol like every task (xref:01-roles-and-configuration.adoc#model-caller[The Model Caller], xref:02-task-protocol.adoc[Task Protocol]): qualification and its conservative fallback, the re-offer budget, the model slots, and fencing apply. Every panel task runs `fresh` and is never offered to the entry session. With no panel roles, the step completes at once.
. *Decide*: The server applies the decision rule (<<decision-rule>>) to the answers; the unit's ending transaction records the result on every record of the set (<<panel-record>>).
. *End*: `auto_decided` answers every question of the set with the agreed option (`channel: panel`); the question state takes the outcome of that answer like any other. `delivered` hands the set to the delivery of its mode, `auto` in mode `panel`, with the panel's answers attached; the question wait (link:../timeouts/01-job-budgets-and-waits.adoc#question-wait[Timeouts & Budgets Specification, Question Wait]) starts at the delivery.

The adjudication is bounded by the declared panel wait (link:../timeouts/01-job-budgets-and-waits.adoc#panel-wait[Timeouts & Budgets Specification, Panel Wait]): at its expiry the server cancels the open panel tasks, which count as without an answer. It never asks the operator or the user anything of its own, and it is never repeated for a set. The operator's `abort` or `delete-plan` while it runs cancels the panel tasks with the records.

[#panel-blind-input]
=== Blind Input
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-45[PM-WATCH-DISP-45]_

A panel task's entity carries in its `facts`:

* the question set: every question's `question_id`, `question_text`, `decision_kind`, and its options (`branch_key`, `label`, `description`) in their recorded order;
* the facts of the asking state with the evidence the decision rests on (xref:06-envelopes-questions-deadlines.adoc#decision-evidence[Evidence in Facts]), composed as for the asking task; for a server-raised question, the facts the primitive's question state shows.

It never carries the `recommended` flags, `recommendation_confidence`, `rationale`, or `default_assumption` of a question, the answers of another panel role, or the asking task's submission beyond what its facts show. The entity offers one closing link `submit:panel` (rel `submit`) with `answers: list<schema[panel-answer]>`, one item per question of the set: `{question_id, branch_key, confidence (0..100), rationale (text 10..500)}` (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]); an item for an unknown question, a missing item, or an unknown `branch_key` is refused `invalid_link_args`. The entity offers no `ask`, no `consult`, and no infeasible link.

[#decision-rule]
=== Decision Rule
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-45[PM-WATCH-DISP-45]_

For each question of the set, the answering systems are the asker (its recommended option and `recommendation_confidence`) and every available panel role whose task ended `submitted` with a valid answer. A question is *agreed* on option `o` when:

* at least `quorum` systems chose `o`, each with a confidence of at least `min_score`,
* no system chose another option with a confidence of at least `min_score`, and
* with `asker_must_win`, `o` is the asker's recommended option.

The set is `auto_decided` when every question of the set is agreed; otherwise it is `delivered` with the reason `disagreement`. A panel task that ended `lost` (its role became undefined or unavailable after the check, its re-offers spent, or the panel wait expired) or `infeasible` has no answer and never counts as agreement; with too few answering systems the quorum is not reached.

[#panel-record]
=== Record, Delivery & Audit

The adjudication of a set in mode `panel` writes one decision record per question of the set (decision point `question.adjudicate`, xref:11-decision-records.adoc#question-decisions[Decision Records, Question Decisions & the Panel]) and one `adjudicated` line on each question record that names it (link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]). The decision record holds the outcome (`auto_decided`: the agreed option as its `choice`; `delivered`: `choice: null`), the reason (`agreement`, `mode`, `panel_invalid`, `panel_not_diverse`, `panel_unavailable`, `kind_ineligible`, `kind_unqualified`, `below_score`, or `disagreement`), the set's score against `min_score` and the agreeing and the available systems against `quorum` as measurements with their source (`unit` and the unit's digest, or `compiled`), and, when the panel ran, every system's answer: the asker or the primitive, and each panel role with its harness, model, `branch_key`, confidence, rationale, `queue_task_id`, and task outcome (`unavailable` for a role that got no task). An auto-decided record is closed `answered` with `channel: panel`.

* *Delivered with the panel's answers*: A delivered set shows, per question, the asker's recommendation with its confidence and rationale and every panel role's answer with its confidence and rationale, on the web app and in the facts of the answer links; the deadline, the class fallback, and the answer validation are those of mode `auto`.
* *Audit*: Every auto-decided question is listed in the pull-request body and the landing record with the agreed option and the systems that agreed, like every other answer; an answer that changes the plan's intent creates an amendment of source `panel`. The decision record is the standing decision a later task, a re-planning, or the retrospective cites by its `decision_id`; a later question that revisits it and is answered otherwise appends a correction to it (xref:11-decision-records.adoc#decision-corrections[Corrections]).
* *Accounting*: The usage of a panel task is accounted to its role and to the scope like every task (xref:09-completion-usage-and-spend.adoc[Task Completion, Usage & Spend]).

[#panel-and-consultation]
=== Panel and Consultation

A panel task uses the task mechanics of a consultation (xref:05-consultation.adoc[Consultation]): a task of another role through the server, served by the model caller and the task protocol. It differs in who starts it and what it sees: the server starts it for a question set, never a worker, its facts are blind to the asker's judgment, and its answer goes to the adjudication, never to the asking task.

[#panel-calibration]
=== Panel Calibration
_See Requirement link:../../Requirements.adoc#PM-WORK-6[PM-WORK-6: Role Qualification]_

A panel role is graded like every `read_only` role on its corpus topics (xref:01-roles-and-configuration.adoc#qualification-topics[Corpus Topics of a Role]); a role without a valid qualification record is unavailable. The panel as a whole is calibrated in addition, because what matters is not how often one role answers right but how often the adjudication would decide automatically and wrongly.

* *Configuration calibrated*: The declarations `panel_roles`, `quorum`, `min_score`, and `asker_must_win` of the project's adjudication unit, the configuration digests of the panel roles available at the calibration (xref:01-roles-and-configuration.adoc#role-artifact[Role Artifact Schema]), and the configuration digest of the asking role it is measured with (`--asker <role>`, default `outline`). Its *panel digest* is the SHA-256 over these values.
* *Run*: `pm-operator roles qualify --panel` (link:../cli-and-security/02-credentials-and-operator.adoc#operator-roles[CLI, Coordination & Security Specification, Roles]) takes every corpus item under `decision/` with `review.status` `draft` or `confirmed` and a closed answer. Per item it runs one fresh task of the asking role and one blind task of each available panel role through the task protocol, each answering with an option and a confidence like a panel answer (<<panel-blind-input>>), and applies the decision rule (<<decision-rule>>) with the declarations. The tasks run under the model slots and the launch contract of production, like role grading (xref:01-roles-and-configuration.adoc#grading[Grading]).
* *Measurements per kind*: An item counts for the kind its tag `decision-kind:<kind>` names (the decision export sets it, xref:11-decision-records.adoc#corpus-export[Corpus Export]); an untagged item counts only for the totals. Per kind and in total the record stores the items graded, the *automatic share* (items the adjudication would decide automatically), and the *false automatic share* (of those, the items whose agreed option is neither `target.answer` nor one of `target.alternatives`), with every item's answers, cost, and time. The record stores measurements, never a pass flag.
* *Qualified kind*: A kind qualifies when at least one item of the kind was graded and its false automatic share is at most `max_false_auto_percent`, read from the unit at every check, so a changed level applies to the existing record at once. A question of an unqualified kind is delivered with the reason `kind_unqualified`; without a valid calibration record no kind qualifies.
* *Record*: `qualification/panel.json` of the project role set, bound to the panel digest and the corpus revision (link:../store-schemas/16-task-queue.adoc#panel-calibration-record[Store Schemas Specification, Panel Calibration Record]). It is invalid when a declaration it covers, a panel role's or the asker's configuration, the set of available panel roles, or the corpus revision changes; `pm-operator status` then names the panel uncalibrated until it is run again.
* *Shipped calibration*: The release ships the calibration of its default panel (`classpath:/roles/qualification/panel.json`). The shipped panel roles, their models, and the shipped declarations are the configuration that passed this calibration on the release's corpus; the level of each panel model follows from that measurement. The project setup calibrates the panel on the machine's harness versions with the role grading at install (xref:01-roles-and-configuration.adoc#install-grading[Grading at Install]), and the operator excludes the calibration from it with `qualification.skip_panel` in `local-config.json` (default `false`; link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), a key of its own because `skip_roles` names roles and a role may be named `panel`.
* *Shown*: `pm-operator roles show --panel` and the web app's roles view show per kind the items, the automatic share, the false automatic share against the level, and whether the kind qualifies.

The calibration grows with the corpus: the real questions of plans, exported with the answer finally given (xref:11-decision-records.adoc#corpus-export[Corpus Export]) and harvested from existing plan-marshall runs (link:../../roadmap.adoc[Roadmap]), make the per-kind measurements meaningful; the user's overrides of a recommendation are the negative examples that show a false automatic decision.
