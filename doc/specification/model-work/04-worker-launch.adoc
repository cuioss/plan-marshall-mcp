[#model-job-launch]
== Worker Launch
_See Requirements link:../../Requirements.adoc#PM-WF-5[PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint], link:../../Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Slots & Usage per Task], link:../../Requirements.adoc#PM-SKILL-4[PM-SKILL-4: Skill Delivery to Workers & State through Representations], link:../../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

Every worker of `PM-MCP` is a job of kind `llm` that the server starts itself through the headless command line of an enrolled harness (`claude -p`, `opencode run`), like a build. The model caller reads the artifact of the role a task names (xref:01-roles-and-configuration.adoc[Roles & Configuration]) and starts a worker of that role: one per task for a `fresh` role, a supervised worker that takes task after task for a `warm` role (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]). This part specifies how one worker is launched: its launch contract, tool set, connection, working directory, model slot, launch prompt, skill delivery, environment, and budget. How a worker receives, acknowledges, and submits tasks is the task protocol (xref:02-task-protocol.adoc[Task Protocol]).

[source,text]
----
pm-mcpd (workflow engine, supervisor)                                  harness CLI (worker)
 task queued for role R (queue_task_id qt-…)
 model caller reads role artifact R:
   harness, model, effort  <- role artifact
   template                <- client profile `headless` block of the harness
   tool set                <- role artifact `tools` (within its class)
   cwd                     <- plan worktree | project checkout | private `cwd/` (screener)
   launch prompt           <- shim + core conduct + task protocol + role skill
                              (+ task skills + contract envelope for a fresh worker)
   mcp config              <- `pm-mcp serve --job`; job token and generation in its environment
 model slot lease (machine cap, one writer worker per plan)
 pm-exec (process group, confinement, environment) ------------------> claude -p … / opencode run …
                                                                          |
 job-bound connection <---------------- pm_wait / ack / pm_state / pm_do -+ tools of the role
 per-turn usage parsed from the harness output                            |
 fate: succeeded | failed | timed_out | killed | … <---------------------- + exit
 task outcome evaluated on persisted records (09)
----

A worker is a leaf (`PM-WF-5`): its connection never follows a link that starts a model, so a worker never starts another worker, and the harness tool that starts sub-agents is never in its tool set (<<job-tool-sets>>). A worker that needs another model's judgment consults through the server (xref:05-consultation.adoc[Consultation]).

[#launch-contract]
=== Launch Contract

The server composes the launch of every worker from server-owned inputs only; no element is read from a file the model can write. The composed contract is recorded in the worker's job record (`harness`, `role`, `form`, `model`, `effort` with `effort_narrowed_from` where narrowed, `generation_id`, `prompt_digest`, and the `argv_digest` of the composed argument vector; link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]):

[cols="1,4"]
|===
|Element |Source

|Harness, model, effort
|The role artifact's `harness`, `model`, and `effort` (xref:01-roles-and-configuration.adoc[Roles & Configuration]); the effort is narrowed where the harness does not accept it (<<model-and-effort>>). Nothing else selects a harness: neither the client of the entry session nor any setting outside the role set.

|Command template
|The `headless` block of the harness's client profile: an argument-vector template with typed slots and declared capabilities (link:../client-profiles/01-profile-schema.adoc#headless-block[Client Profiles Specification, Profile Schema]), composed as an inline named agent or by per-call flags (<<agent-composition>>).

|Working directory
|The plan worktree when it exists, else the enrolled project checkout; for the screener the empty `cwd/` subdirectory of its job-private directory (<<job-working-directory>>).

|Tool set
|The role artifact's `tools`, exact names within the tool set of its class (<<job-tool-sets>>).

|Launch prompt
|The server-composed prompt file: shim paragraph, core conduct, task-protocol skill, role skill, and for a fresh worker the skills and the contract envelope of its one task (<<job-prompt>>).

|MCP connection back
|A per-call MCP configuration that starts only the job relay `pm-mcp serve --job --socket <path>`, with the job token and the generation in the relay's environment (<<job-token>>); none for a `zero_tool` worker.

|Output
|The per-turn usage and, where the role's class has one, the structured result, parsed from the harness output (xref:09-completion-usage-and-spend.adoc#job-result-schema[Worker Result & Usage Parsing]).
|===

The composed argument vector passes the argument schema validation of every job (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Verify-Not-Resolve Execution Pipeline]); free text (the prompt, the agent definition, the result schema) never enters the argument vector beyond the file paths and the inline-agent JSON the template declares. A change of the role artifact applies to the next worker generation; a running generation keeps the contract it was launched with.

[#harness-selection]
=== Harness Eligibility & Launch Refusals
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-33[PM-WATCH-DISP-33]_

*Eligibility*: A harness hosts workers only when its client profile's `worker` block declares `eligible: true` (link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification, Worker Block]), which a profile does only after the worker behaviour has been measured on that harness (link:../evaluation.adoc#limits[Evaluation Reference, Limits]). A role artifact that names an ineligible harness, a model outside the harness's `restricted_models`, or a harness that lacks a capability of the role's class is invalid when the role set is loaded and counts as undefined (xref:01-roles-and-configuration.adoc[Roles & Configuration]); the launch therefore never meets an unsupported combination of a valid role.

*Capabilities per class*: Every role belongs to one class, and a class needs a fixed set of the capabilities a `headless` block declares:

[cols="1,3,3"]
|===
|Class |Harness tools |Required capabilities

|`writer`
|The harness's file-reading, file-writing and shell tools and its MCP resource-reading tools (`headless.resource_tools`)
|`per_call_mcp`, `tool_allowlist`

|`read_only`
|The harness's file-reading and search tools and its MCP resource-reading tools
|`per_call_mcp`, `tool_allowlist` (with a read-only tool set)

|`zero_tool`
|None, and no MCP connection (the screener, xref:07-untrusted-text-screening.adoc#screener[Screener])
|`zero_tools`
|===

*Harnesses*:

[cols="1,1,4,3"]
|===
|Harness |Eligible |Launch |Notes

|`claude`
|yes
|Inline agent (`--agents '<json>'`, `--agent pm-job`), `--mcp-config` with `--strict-mcp-config`, `--json-schema`, `--no-session-persistence`, `--output-format stream-json`; `zero_tool` with `--tools ""`, `--setting-sources ""`, `--max-turns 1`, `--system-prompt-file`
|Its interactive session may take tasks (`session_tasks: true`).

|`opencode`
|yes
|Inline agent in `OPENCODE_CONFIG_CONTENT` with a local MCP command; `read_only` with every permission denied except the read tools; the result parsed from the final message against the schema, fail-closed
|Only the models in `restricted_models` accept a restricted agent; unreliable exit codes (`exit_reliable: false`); its interactive session takes no tasks (`session_tasks: false`).

|`codex`
|no
|Per-call flags (`agent_mode: flags`)
|Not measured as a worker host.

|`antigravity`, `neutral`
|no
|—
|No `headless` block.
|===

*Harness enrolment*: A harness executable is an enrolled host tool of the machine: `pm-operator enrol-harness <client>` records its absolute path, the version its version probe reports, and its SHA-256 digest (link:../cli-and-security/02-credentials-and-operator.adoc#operator-enrol-harness[CLI, Coordination & Security Specification, Harness Enrolment]; store: link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]). Before every launch the runtime verifies it without resolving (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Verify-Not-Resolve Execution Pipeline]). Because harnesses update themselves, a changed digest whose version probe reports a version within the profile's `headless.supported_versions` is accepted and audited (the new digest is recorded). The enrolment records path, version, and digest only: `PM-MCP` never stores or exports a harness's authentication. The harness must already be logged in by its own login (cached under its home).

*Launch refusals*: A launch is refused before spawn, with fate `refused` and a reason, when the harness is not enrolled (`harness_not_enrolled`), its version lies outside the supported range (`harness_version_unsupported`), the harness enrolment store `harnesses.json` fails its HMAC check (`harness_tampered`, audit `security` record `enrolment_tampered`; `pm-operator enrol-harness <client>` shows path, version, and digest and rewrites the file and its sidecar), the prompt cannot be composed (`prompt_composition_failed`, <<job-prompt>>), or a verify-not-resolve check fails. A refusal counts as a start failure of the role on that harness: the supervisor stops starting workers there after the compiled number of consecutive start failures, reports the reason and the resolving operator command in `pm-operator status`, the web app, and the audit log, and the role's waiting tasks take their conservative fallback (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]). A harness that is not logged in starts and fails before its first call, which is a start failure by the same rule.

[#model-and-effort]
=== Model & Effort

* *From the role only*: The role artifact's `model` and `effort` fill the `{{model}}` and `{{effort}}` slots of the harness's template (<<agent-composition>>); a `null` value fills neither slot, so the harness's own default applies. No other configuration names a model or an effort for a worker, and no agent file is installed per model or per client.
* *Narrowing*: An effort that the harness does not accept for the model (as `headless.model_efforts` declares, link:../client-profiles/01-profile-schema.adoc#headless-block[Client Profiles Specification, `headless`]) narrows to the nearest accepted lower value, never to a higher one; the job record keeps the artifact's value as `effort_narrowed_from`, and `pm-operator roles show <role>` reports the narrowing. A model with an empty effort list takes no effort flag.

[#agent-composition]
=== Agent Composition per Harness (`agent_mode`)

The `headless` block declares `agent_mode: inline | flags`, the typed slots `{{prompt_file}}`, `{{model}}`, `{{effort}}`, `{{mcp_config}}`, `{{result_schema}}`, `{{tools}}`, `{{cwd}}`, and `{{agent}}` (the rendered inline agent definition), the per-class argument templates `class_args` (a class without an entry is not runnable on that harness), the launch environment `env`, and the capabilities. The server fills only the slots the template declares.

* *`inline`* (Claude Code, OpenCode): the server renders a per-worker named agent from the same slots (Claude Code: the `--agents` JSON with `tools`, `model`, `effort`, `mcpServers`, `maxTurns`, and `prompt`; OpenCode: the agent in `OPENCODE_CONFIG_CONTENT`) into the `{{agent}}` slot and starts the harness as that agent. Nothing is installed in the host's agent directory, so a newly composed agent is never "not found" and no environment variable of the host overrides its model.
* *`flags`*: the same slots become per-call flags.
* *Tools loaded directly*: A worker's tools are callable from its first turn. Where a harness defers MCP tool definitions behind a tool search, the profile's `headless.env` switches the deferral off, because a fresh worker that cannot call its tools directly ends without a result.
* *Session residue*: The ephemeral flag (`--no-session-persistence`) is passed where the block declares `ephemeral`; a harness without it declares `session_residue: persisted`, which `pm-operator status` reports. The harness's persistent memory is switched off through `headless.env`, so a worker never writes into the operator's memory and never reads what another worker left there.

[#job-tool-sets]
=== Tool Sets

The tool set of a worker is the class's harness tools (<<harness-selection>>) and the role artifact's `PM-MCP` tools, each by exact name, never by a pattern. The artifact's `tools` must lie within the set of its class, which the role set's validation checks (xref:01-roles-and-configuration.adoc[Roles & Configuration]):

* *`writer`*: `pm_wait`, `pm_state`, `pm_do`, `pm_skill`, `pm_skill_file`, `pm_build`, and `pm_lsp`.
* *`read_only`*: `pm_wait`, `pm_state`, `pm_do`, `pm_skill`, `pm_skill_file`, and `pm_lsp` limited to its read operations: `rename` is refused with `invalid_arguments`. `pm_build` is not in the set.
* *`zero_tool`*: none.

`pm_wait` is the worker's only wait tool (link:../mcp-tools/01-core-workflow-tools.adoc[MCP Tools Specification, Core Workflow Tools]; semantics xref:02-task-protocol.adoc[Task Protocol]); `pm_state` and `pm_do` reach only the worker's own task entities (<<job-token>>). The set is rendered into `{{tools}}` and enforced a second time by the daemon on the job-bound connection. The harness tools of `writer` and `read_only` include the harness's MCP resource-reading tools (`headless.resource_tools`; an empty list means the harness offers none and its workers read no resources). Never in a tool set: the harness's sub-agent tool (`Agent`, `task`, `spawn_agent`), a tool that asks the user, the web tools, and every operator action or scope-creating link. The harness allowlist is defence in depth; the containment is the daemon's per-request binding.

[#job-token]
=== Job Token, Generation & Connection Binding
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-10[PM-WATCH-DISP-10], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-30[PM-WATCH-DISP-30], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-34[PM-WATCH-DISP-34]_

A worker never receives the runtime token (link:../runtime-model/01-processes-and-transport.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]). It connects back through a capability of its own:

1. *Job token and generation*: At spawn the server mints a random 256-bit job token, stores only its SHA-256 in the job record, and revokes it with the job's fate (link:../runtime-model/01-processes-and-transport.adoc#job-token[Runtime & Interaction Model Specification, Job Token]). The worker's MCP configuration starts the relay `pm-mcp serve --job` with `PM_MCP_JOB_TOKEN` and `PM_MCP_JOB_ID` in the relay's environment and the daemon's socket path as a relay argument; `PM_MCP_JOB_ID` is the worker's `generation_id`. The relay sends both on every request and removes identity and generation arguments from the tool schemas it passes to the harness (link:../runtime-model/03-relay.adoc[Runtime & Interaction Model Specification, Relay]), so the model never sees, passes, or invents them.
2. *Per-request binding*: The daemon resolves the job from the token's digest on every request (stateless; no connection state) and enforces: `pm_state` and `pm_do` address only the task entities leased to the worker's generation, else `job_scope_mismatch`; a fenced generation is refused `generation_fenced`; a token of an ended job is refused `job_ended`; `tools/list` and every call are limited to the worker's tool set (<<job-tool-sets>>); `resources/list` and `resources/read` work as in a session, read-only, for every resource of the worker's own project and `skill://pm/…` (the project boundary is the only read boundary, link:../mcp-tools/03-resource-uris.adoc[MCP Tools Specification, Resource URIs]); `pm_do` never admits a link that starts a model, and a consultation only through a `consult` link of the task's state (xref:05-consultation.adoc[Consultation]). The first accepted request records `connected_at` in the job record.
3. *Not a session*: A worker connection is no interactive session: it takes its client profile from the job record, and every audit row it causes carries the `job_id`.
4. *Strict MCP configuration*: The per-call MCP configuration is exclusive, so only the job relay connects (`--strict-mcp-config`; OpenCode an inline configuration that replaces `mcp`). The entry commands of the `PM-MCP` client bundle exit at once when `PM_MCP_JOB_ID` is set (link:../cli-and-security/01-cli-and-installer.adoc#command-tree[CLI, Coordination & Security Specification, Command Tree]), so the host's own integration never starts inside a worker.

[#job-working-directory]
=== Working Directory, Project Files & Screener Isolation

* *`writer` and `read_only` workers*: The process working directory is the plan worktree when the plan has one, else the enrolled project checkout (for the workspace, an epic, and a plan without worktree), by the working-directory rule of every job (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Working Directory Selection]). The harness loads the project's own instructions and skills natively from there (for example `CLAUDE.md`, `AGENTS.md`, project skill directories). No prompt field names a worktree, and the client profile declares no working-directory property. A warm worker serves tasks of one plan worktree or of the project checkout only, because its working directory is fixed at launch; the supervisor starts warm workers per working directory (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]).
* *The screener*: runs in the empty `cwd/` subdirectory of its job-private directory (<<job-prompt>>), which it can read and never write, with project and user settings off where the harness offers it (`--setting-sources ""`; OpenCode an inline configuration that replaces everything), so no project file and no project skill reaches it; its prompt is the server-fixed screener prompt only (xref:07-untrusted-text-screening.adoc#screener[Screener]).

[#model-slots]
=== Model Slots & One Writer per Plan
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-31[PM-WATCH-DISP-31]_

* *Machine cap*: Every running worker, warm or fresh, holds a lease of the machine lease store `model-slots.json` beside `build-slots.json` (link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]), with the cap `model_slots` in `machine-config.json` (link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration]; default and bounds: link:../timeouts/02-runtime-leases-operator-web.adoc#model-slot-lease[Timeouts & Budgets Specification, Model slot lease]). A warm worker holds its slot for its whole generation, idle or not. Admission is FIFO in request order; stale slots are reaped in the admission transaction as build slots are.
* *Queued*: A task waiting for a worker is `queued` (xref:02-task-protocol.adoc[Task Protocol]); a launch waiting for a slot has the job record status `queued`, and the worker's budget starts at spawn, so the time in the slot queue never counts against it (link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]).
* *One writer per plan*: At most one worker of a `writer` role runs or waits for a slot per plan at a time (serial envelope tasks: they share one worktree, one chain-tail commit, and one module build, xref:06-envelopes-questions-deadlines.adoc#envelope-early-end[Early End of an Envelope Task]); `read_only` and `zero_tool` workers of the plan run beside it within the machine cap.
* *Fan-out*: A `job llm … each …` state (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Model Job States]) queues one task per element of its server-computed list (architecture enrichment: one task per module; a screening batch above the split bound: one task per part) at once; the slots and the role's `count` bound how many workers serve them.

[#job-prompt]
=== Launch Prompt & Contract Envelope
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-9[PM-WATCH-DISP-9], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-10[PM-WATCH-DISP-10], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-24[PM-WATCH-DISP-24]_

The server hands a worker what it needs to start in one prompt file and decides exactly what the worker knows; the worker starts without loading anything.

* *Job-private directory*: The runtime creates `<PM_MCP_BASE>/run/jobs/<job_id>/` (mode `0700`, files `0600`; link:../filesystem-layout.adoc[Filesystem Layout Specification, Job-Private Directories]) before spawn and removes it when the job settles. It holds the prompt file, the rendered result schema, the per-call MCP configuration (none for a `zero_tool` worker), and, for the screener, the empty working directory `cwd/`. The worker reads its own directory, the one exception to the rule that a job never reads `<PM_MCP_BASE>`; no worker can write there. The prompt file's SHA-256 is the job record's `prompt_digest`.
* *Launch prompt, in this order*: (1) the shim paragraph (<<shim-paragraph>>); (2) the core conduct skill `skill://pm/core/SKILL.md`; (3) the task-protocol skill `skill://pm/task-protocol/SKILL.md`; (4) the role skill `skill://pm/role/<role>/SKILL.md` and the further skills of the role artifact's `skills`. A `zero_tool` worker receives none of these; its prompt is server-fixed (xref:07-untrusted-text-screening.adoc#screener[Screener]).
* *Fresh worker*: The prompt of a fresh worker adds (5) the skills its one task requires that (1) to (4) do not hold: the state's `skill` clauses, the project's domain skills, and for an envelope task the union of its plan tasks' `skills[]` (xref:06-envelopes-questions-deadlines.adoc#_deterministic_envelope_packing_algorithm_envelopepacker[Deterministic Envelope Packing Algorithm]); and (6) the task's contract envelope. Skills are rendered in-band up to the compiled prompt in-band bound (link:../timeouts/03-retention-host-config.adoc#prompt-in-band-bound[Timeouts & Budgets Specification, Prompt in-band skill bound]); above it, the remaining skills of (5) are rendered as their section index with the `skill://` URIs and section anchors that `pm_skill` serves (link:../mcp-tools/02-service-and-skill-tools.adoc[MCP Tools Specification, Service & Skill Tools]). Items (1) to (4) are always in-band.
* *Contract envelope*: the `queue_task_id`; the scope (`plan_id`, `epic_id`, or `NO_PLAN`) and the task's `entity`; the first call (`pm_state` on that entity); the links the entity offers with their named parameter schemas (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]); the worker's result schema; and the rule that deliverables reach the server only through the entity's `submit` links. The envelope stands for the offer of the fresh worker's one task: the task is leased to the worker's generation at spawn, and the worker acknowledges and executes it by the task protocol (xref:02-task-protocol.adoc[Task Protocol]). A warm worker's prompt holds no contract envelope; each offer carries its own.
* *One definition*: One definition of the contract envelope drives both the composed prompt and the job-bound checks of the worker's calls (<<job-token>>); no contract field is validated by the model.
* *Fail closed*: A prompt that cannot be composed (a skill that does not resolve or renders empty, a schema that does not render) refuses the launch before spawn with `prompt_composition_failed` (<<harness-selection>>); no worker ever runs with a required skill missing.
* *Project files*: Project-level instructions and skills load natively from the working directory (<<job-working-directory>>); `pm_skill` serves only compiled skills (project-local vocabulary skills: link:../../later-improvements.adoc#_l_4_project_local_vocabulary_skills[Later Improvements, L-4]).

[#skill-delivery]
=== Skill Delivery Record & Re-Delivery
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-44[PM-WATCH-DISP-44]_

For every task the server computes the required skill set: core conduct, task protocol, the role skill, the skills of the task's state, and the project's domain skills, each identified by URI and digest (`PM-SKILL-4`). The server delivers the set; it never waits for a model to fetch a skill.

* *Delivery record*: The server keeps one delivery record per generation (a worker's `job_id`, or a session's `sg-` generation): per skill its URI, its digest, and the instant of delivery. The launch prompt's in-band skills are recorded at spawn. A new generation starts with an empty record, so a successor receives everything again; nothing depends on what a predecessor knew. The record is kept with the job record of a worker and with the generation record of a session (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]).
* *Offer*: An offer to a warm worker or a session carries in-band every required skill whose URI and digest its generation's record lacks, and names the others by URI and digest (offer format: xref:02-task-protocol.adoc[Task Protocol]); the in-band skills are recorded with the offer.
* *Re-delivery*: A skill is delivered again (1) to every new generation, (2) after a clear or compaction that the relay reports for a session generation, which empties that generation's record, and (3) whenever the skill's digest changed (a new release or project configuration), because the record holds the old digest. A clear or compaction its host does not report stays invisible to the server; the shim covers it (<<shim-paragraph>>).
* *Offer bound*: The server never offers a task whose skills missing from the generation's record exceed the compiled prompt in-band bound; such a task goes to a fresh worker of the role, whose launch prompt carries them.
* *Host activation*: When a connection declares the client capability of the MCP Skills Extension (`io.modelcontextprotocol/skills`), the server switches that connection to host activation: offers name the required skills by URI and digest only, and the host loads them through its own skill path. The client profile records the verified support (`skills_extension`, link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification, Profile Schema]).
* *Results against the contract*: What the server receives is checked against the link and schema the contract names, whatever the model made of a skill. Whether a model applies a skill is measured (link:../evaluation.adoc#results[Evaluation Reference], E13) and qualified per role (xref:01-roles-and-configuration.adoc[Roles & Configuration]), never assumed.

[[shim-paragraph]]*Shim paragraph*: Every launch prompt of a `writer` or `read_only` worker starts with the paragraph that the shim skill of the client bundle carries for an interactive session (link:../client-profiles/03-bundle-manifest.adoc[Client Profiles Specification, Bundle Manifest]): skills of `plan-marshall` arrive in-band or are named by a `skill://pm/` URI; a named skill is binding and is read through `pm_skill`, sections through their anchors; a skill is never reconstructed from memory; a skill of the same name from elsewhere does not replace it. The paragraph never chooses skills.

[#job-environment-and-budget]
=== Environment, Confinement & Budget

A worker is confined like every job of its project (link:../job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification, Linux Filesystem Confinement]): no access to `<PM_MCP_BASE>` beyond read access to its own job-private directory (<<job-prompt>>), and writes only to the write set of every job and the harness sub-paths its profile declares (`headless.writable_paths`), with network access for the harness's model provider. `headless.writable_paths` lists only what a headless harness must write to run (its login or credential file, caches, the session directory) and never a settings, skill, or command file that the bundle manifest manages (link:../client-profiles/01-profile-schema.adoc#headless-block[Client Profiles Specification, Profile Schema]), so a worker cannot change the host's `PM-MCP` integration. Its environment holds the rows of every job, the harness switches of `headless.env`, and `PM_MCP_JOB_TOKEN` and `PM_MCP_JOB_ID` as the only `PM-MCP` values (link:../job-runtime/02-confinement-and-environment.adoc#_job_environment_pm_sec_5[Job Runtime Specification, Job Environment]); no variable of the calling host's session reaches it, and no harness authentication variable is captured, stored, or exported by `PM-MCP`. The worker uses the harness's own login, cached under the harness home.

Every worker runs under the job budget of its role, learned per role above the floor of the role artifact's `budget_floor_seconds` (link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]): a fresh worker's job ends after its one task, a warm worker's job after its generation (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]). Budget expiry, the supervisor's end of a worker, and drain end it through the termination protocol of every job (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_process_termination_cancellation_protocol[Job Runtime Specification, Process Termination & Cancellation Protocol]).
