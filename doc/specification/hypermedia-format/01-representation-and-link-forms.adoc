_Implementation watch: link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-1[PM-WATCH-HYP-1]_

Every representation is serialized as a top-level TOON object with a fixed canonical field ordering. The server drives every plan and epic itself, so a representation offers links only where a model acts (`PM-WF-1`).

[#representation-kinds]
=== Representation Kinds
_Implementation watch: link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-9[PM-WATCH-HYP-9]_

[cols="1,2,3"]
|===
|Kind |Addressed as |Links

|Task entity
|`scope: entity` with the `plan_id` or `epic_id` of its scope (neither for a task of the workspace scope, which is addressed with `plan_id: "NO_PLAN"`) and the `entity` of the task (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). It is served only to the worker whose generation holds the task's lease: a headless worker, or the entry session when it takes a task as an optional worker (`PM-WORK-5`).
|While the task is offered, only `ack`. After the acknowledgement, the links of the entity unit of the task's kind, the `infeasible` link (evidence required) on every task entity except the consultation entity (link:../model-work/05-consultation.adoc#consult-serving[Model Work Specification, Serving the Consultation]), the `ask` link where its state declares one, and one `consult:<role>` link per `consult role` clause of its state (<<question-waiver-and-exit-links>>).

|Session-driven state
|A pending plan or epic bootstrap (`scope: entity`, `plan_id: "NO_PLAN"` with `entity: <entry_id>`), and the workspace scope (`scope: workspace`, `plan_id: "NO_PLAN"`), which hosts the project setup and the lesson maintenance. The entry session drives them.
|The declared links of the state, the implicit `step_out` in a resting link state of a sub-workflow, the answer links of an open question record, and the bounded self-remedy link of a condition.

|View
|`scope: plan` or `scope: epic`. The entry session and the web app read it; the engine moves the scope.
|Only the answer links `answer:<question_id>` of the scope's open question records; otherwise empty. A view never offers a transition of the scope.
|===

The representation of a task entity and of a session-driven state is the result of every `pm_do` on it, so each followed link returns the next representation of the entity it addressed. A worker addresses only the task entities leased to its generation (link:../workflow-dsl/05-primitives.adoc#independent-transition-validation[Workflow DSL Specification, Transition Validation], step 2).

[#canonical-top-level-fields]
=== Canonical Top-Level Fields
_Implementation watch: link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-2[PM-WATCH-HYP-2], link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-3[PM-WATCH-HYP-3]_

[cols="1,1,1,3"]
|===
|Field |Presence |Type |Normative Definition

|`scope`
|Required
|Closed enum
|`"plan"`, `"epic"`, `"workspace"` (the project's workspace scope, which hosts `project-setup`; a call addresses it with `plan_id: "NO_PLAN"`, link:../identifiers/01-general-rules-and-registry.adoc#id-no-plan[Identifier Registry, `NO_PLAN`], never with a `scope` input), or `"entity"` (a task entity, or a pending bootstrap entry of the workspace scope, <<representation-kinds>>).

|`plan_id` / `epic_id`
|Required (one of), except for `scope: workspace`, a bootstrap entry, and a task entity of the workspace scope
|String
|The addressed plan identifier (`plan_id`) or orchestrator epic identifier (`epic_id`); a task entity carries the identifier of the scope its task belongs to. A `workspace` representation, the representation of a bootstrap entry, and a task entity of the workspace scope carry neither (not even the `NO_PLAN` sentinel that addresses them): the absence tells the caller to address the scope with `plan_id: "NO_PLAN"`. Their project is the one the session's relay names, for a worker the one of its job record.

|`entity`
|Conditional
|String
|Present iff `scope == "entity"`: the entity a task works on (for example `envelope-2` or `enrich-http`), the task's `queue_task_id` where its state names no entity of its own, or the `entry_id` of a bootstrap entry (for example `ent-3f9a2c41`).

|`state`
|Required
|Dotted enum
|Closed-enum state name (`<phase>.<step>[.<substate>]`; every state is catalogued in the link:../state-catalogue.adoc[State Catalogue]). In a view, the scope's current state (a `job llm` state also while its tasks run, for example `refine.analyze`; while a sub-workflow is active, the active sub-workflow state, for example `git.compose-message`). For a task entity, the state of the task: `task.offered` before the acknowledgement, afterwards the state of the entity unit of its kind (for example `entity.active` or `envelope.task.active`). Never a boolean.

|`condition`
|Conditional
|Closed enum
|Present iff the scope's `pending_condition` is set (link:../store-schemas.adoc[Store Schemas Specification]): the condition kind (`footprint_violation`, `job_incomplete`, `config_drift`, `guard_indeterminate`, `precondition_unmet`, `integrity_breach`; link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-conditions[State Catalogue, Conditions]). `state` stays the current state id and `facts` carry the condition (link:../workflow-dsl/04-ast-node-model.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]). In a plan or epic the self-remedy is server logic (a server retry, or a task of the role whose work raised the condition), so a view offers no link for it; in a session-driven state the condition's only link is its bounded self-remedy. `integrity_breach` is the only pause: it renders `links[0]` and `facts.operator_command` (`accept-edit`, `abort`), and every `pm_do` on the paused scope is rejected with `integrity_paused` until the operator resolves it.

|`phase`
|Required
|Closed enum
|Lifecycle phase (`init`, `refine`, `outline`, `plan`, `execute`, `finalize`, `completed`, `aborted`, `orchestrate`, or `workspace`, mapped 1:1 to `phase-1-init`..`phase-6-finalize`, `completed`, `aborted`, `orchestrator`, `workspace` in `status.json`; link:../identifiers/01-general-rules-and-registry.adoc#id-phase[Identifier Registry, `phase`]). A task entity carries the phase of the state that created its task.

|`summary`
|Required
|String
|Single-line human-readable status summary (`1..160` ASCII characters).

|`skill`
|Optional
|URI String
|URI of the vocabulary skill guiding model judgment in this state (`skill://pm/<path>/SKILL.md`; the DSL clause `skill pm/<path>` maps to `skill://pm/<path>/SKILL.md`). A task entity carries the `skill` of the state that created its task. Omitted in views and in purely deterministic states.

|`rejected`
|Optional
|Object
|Present only when the immediately preceding `pm_do` transition was rejected (`link`, closed-enum `reason`, and diagnostic `detail`; link:../mcp-tools.adoc[MCP Tools Specification], § Rejected Transition Representation). A condition the plan bootstrap re-checks when it creates the scope is no rejection: the entry returns to `start.ready` with the reason in `facts` (link:../state-catalogue.adoc[State Catalogue], Bootstrap).

|`facts`
|Required
|Object
|Minimal key-value map of domain facts required to exercise judgment in `state`, restricted to fields with a declared operational purpose (<<model-facing-minimality>>). Large payloads are referenced via `pm://` resource URIs.

|`links`
|Required
|Tabular TOON array
|`links[N]{rel,link,form,free}:` listing every transition valid for the caller (<<representation-kinds>>). Empty (`links[0]{rel,link,form,free}:`) in a view without an open question record, in terminal states, and under the `integrity_breach` condition, whose only resolutions are operator verbs.
|===

[#facts-content-rules]
=== Facts Content Rules
_See Requirement link:../../Requirements.adoc#PM-TOOL-5[PM-TOOL-5: Tool Schema Stability & Context Budget Discipline]_
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-14[PM-WATCH-JOB-14]_

_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-12[PM-WATCH-TOOL-12]_

The server renders `facts` under seven general rules. Rules 1 to 4 apply to every representation and every resource derived from the same stores; rules 5 to 7 apply to every representation, tool result, and error payload:

1. *Server-Derived Counts Name Their Population*: Every count in `facts` (deliverables, files, tasks, findings) is derived by the server from the structured store at render time, never copied from authored text, and names its population in the key (for example `files_realized`, `files_declared`, `files_declared_unrealized`), so realized and declared-but-unrealized members are never mixed in one number.
2. *Population-Checked Aggregates*: A server-aggregated count or coverage figure (findings, reviewed comments, tokens, examined modules) is computed together with its population size. A zero over a non-empty population that structurally cannot be zero, or a figure whose population cannot be read, is rendered `indeterminate`, never `0` or "clean".
3. *Closed-Vocabulary Rule*: Every closed enumeration that classifies observed or judged input (statuses, dispositions, buckets, verdicts, linkage) contains an explicit out-of-set member (`unknown`, `indeterminate`, `not_applicable`, or `out_of_scope`, as fits). No member doubles as a stand-in for an unclassifiable case, and a malformed input is classified differently from an absent one.
4. *Truncation Is Reported*: Any server-side clamp of text (pull-request body sections, comment bodies against a provider's size cap such as 65,536 characters) reports `truncated: true` with the original and the kept length and cuts at a sentence or line boundary; text is never cut mid-sentence silently.
5. [[model-facing-minimality]]*Model-Facing Minimality*: A representation (its top-level fields and `facts`), a tool result (`pm_wait`, `pm_build`, `pm_lsp`, `pm_plans`, `pm_epics`, `pm_skills`, `pm_skill`, `pm_skill_file`), and an error payload (`rejected`, the `isError: true` envelope, JSON-RPC `error.data`) carry only information that changes what the model does next: the offered links and their parameters, the facts its judgement in the current state needs (for a decision, the evidence the decision rests on: the code at the commit, the log line, the standing decision, link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Envelopes, Questions & Deadlines]), the error it must correct, the identifiers it must pass back (`question_id`, `finding_id`, `entity`), and the text it must relay to the user or operator (`summary`, `facts.operator_command`). Everything else is recorded, never returned: the implementation variant that served an operation; derivation and provenance sources (`budget_derivation`, the `source` of a configuration value or a resolved limit, a build template's source); internal versions (`format_version`, `worktree_sha_version`, binary and relay versions) unless the model must act on them; confinement and sandbox details; lease and holder internals (`holder_instance`, the lease of a task, the worker's generation and job token, queue positions, attempt counts); digests and hashes the model makes no decision on (`worktree_sha`, `config_hash`, `input_digest`); calibration bases (`predicted_cost_basis`); timing internals (elapsed seconds, `derived_at`, `recorded_at`, job durations, learned-budget hygiene); retry bookkeeping; the internal job identifiers of a composite wait; the role configuration and launch contract of a worker (harness, model, effort, form, argument vector, prompt file, job token digest, model-slot lease) and its parsed usage and cost; screener verdicts beyond the `withheld` marker of a withheld item; tallies and populations that serve only metrics; and `audit_id`, except on the errors an operator must look up (`internal_fault`, `file_unreadable`). Such data goes to `audit.jsonl`, the metrics store, the job record, the queue task record, or the server log, and where a human or the operator needs it, it is served on demand by the operator surfaces (the operator CLI `pm-operator`, for example `pm-operator status`, the web app the runtime serves over the Local API, and `pm://` resources such as `pm://project/config`), never pushed in a representation or tool result. Web listener, pairing, and paired-device details (listener, certificate fingerprint, `device_id`, device labels, the channel of an operator action), the supervisor state of a worker, and the `stalled` state of a plan are operator data only and never model-facing. When the model's judgement needs a count (for example the open blocking findings), the count is rendered and its population list is not; rules 1 and 2 name and check a population, they do not require rendering it. A build-time test (`ModelFacingFieldAuditTest`) walks every representation, tool-result, and error-payload record type and fails on any field that is not in the registry of model-facing fields, in which every entry declares its operational purpose (`link_parameter`, `pass_back`, `judgement`, `error_correction`, or `relay`); a new model-facing field is a registry change with a stated purpose.
6. [[operator-command-relay]]*Operator Commands Are Relay Text for Three Cases Only*: `facts.operator_command` is rendered only in a view or a session-driven state, and only where the next step belongs to the operator and the session's part is to relay it to the user: the `integrity_breach` pause (`pm-operator accept-edit …` and `pm-operator abort …`), a waiver hint (a pending waiver request, or a waivable gate whose remediation budget is exhausted: the `pm-operator waive <plan_id> <gate> …` command with the closed gate identifier), and a condition whose server self-remedy needs an operator setting, grant, enrolment, or credential first (`pm-operator credentials …`, `pm-operator grant-access …` for a cross-project access, or `pm-operator enrol-harness …`), while the server retries within the condition's budget. A task entity never carries it. No representation asks the model to relay an operator decision: none exists. The session relays a waiver hint as information and never answers it; a waiver is written only through the operator channel, and a model-relayed "waive" is not accepted (`PM-WF-12`).
7. [[options-defined-once]]*Options Are Defined Once, in the Representation*: Where a judgment chooses among options (the remedy links of a remediation decision, the options of a question record, the dispositions of a triage), the representation that offers the choice states each offered option's definition exactly once, as `facts.options[N]{option,definition}` keyed by the link identifier or the enum value it defines, rendered from the one compiled definition of that option. Only offered options are listed. A role skill refers to the options by name and never redefines them, because a model follows the literal definition it reads over a differing one elsewhere.

_Implementation watch: link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-6[PM-WATCH-HYP-6]_

[#call-path-breadcrumb]
==== Call-Path Breadcrumb (`facts.call_path`)

While a sub-workflow is active (a `call` has made the sub-workflow's first state current, link:../workflow-dsl/06-reusable-sub-workflows.adoc#_call_stack_execution_persistence_semantics[Workflow DSL Specification, Call-Stack Execution]), a view and a session-driven state carry `facts.call_path`, the call-site state ids of the scope's call stack from the root frame outward (for example `call_path[1]: finalize.push-barrier`); it is absent at the root frame. In a session-driven state it states where the implicit `step_out` returns to (one frame up, <<question-waiver-and-exit-links>>). A task entity never carries it: the task's own `skill` and `facts` frame its one judgment.

[#remediation-evidence-facts]
==== Remediation Evidence (`facts.failures`)

The decision task of a remediation policy unit (`remediation-<class>.choose`, link:../workflow-dsl/08-remediation-units.adoc#remediation-units[Workflow DSL Specification, Remediation Policy Units]) renders the server-gathered failure envelopes as `failures[N]{failure_id,class,kind,file,line,message,excerpt_uri}`, the budgets left per offered remedy, and the definitions of the offered remedies (rule 7). `excerpt_uri` points at an untrusted evidence resource (`pm://plan/{plan_id}/evidence/{evidence_id}`, link:../mcp-tools/03-resource-uris.adoc[MCP Tools Specification, Resource URI Surface]); log text is never inlined beyond `message`. The envelope's `source` and `fingerprint` (class, kind, file, normalized message), the provider run and job ids, log URLs, and the provider variant are recorded in the evidence record and the job record, never rendered: the server, not the model, compares fingerprints (<<model-facing-minimality>>). A failure the operator cannot waive carries `waivable: false`.

=== Canonical Representation Examples

The decision task of `remediation.ci-failure` after its acknowledgement, as its `triage-ci` worker reads it; the remedies the call site binds and the budgets leave are its links, each defined once in `facts.options`:

[#link-forms]
== The Two Normative Link Forms
_See Requirement link:../../Requirements.adoc#PM-WF-2[PM-WF-2: Closed Link Relation Grammar & Link Forms]_

_See Requirement link:../../Requirements.adoc#PM-WF-8[PM-WF-8: Asynchronous Job Links & Wait Transitions]_

Every row in `links[N]{rel,link,form,free}:` belongs to one of two closed link forms (`submit`, `noop`). The `form` column defines the interaction mechanics expected from the caller. Waiting on a job and cancelling it are engine events, never links: a job's completion moves its state, and a view shows the job's progress (`PM-WF-8`). The only waits a model holds are a worker's `pm_wait` (link:../mcp-tools/01-core-workflow-tools.adoc[MCP Tools Specification, Core Workflow Tools]) and a running `pm_build`. No form requests an operator decision: operator influence reaches a plan only through operator verbs (waivers, `abort`, the integrity resolutions) on the operator channel. No form starts a model: every model step is a task of a role (<<model-job-states>>).

[cols="1,2,2,3"]
|===
|Link Form |Target Tool |`free` Column |Execution Semantics

|`submit`
|`pm_do(scope, link, args)`
|Non-empty typed parameter list (e.g., `"outline:text[1..65536]"`, `"disposition:enum[FIX\|SUPPRESS\|ACCEPT],reply_text:text[1..4000]"`)
|Submits model judgment artifacts to the server: from a worker for its leased task entity, or from the entry session on a session-driven state or an answer link. The server validates `args` against the link's closed schema before executing the backing primitive.

|`noop`
|`pm_do(scope, link, {})`
|`""` (empty)
|Triggers a deterministic server-side transition that requires zero free judgment parameters from the model (for example the task acknowledgement `ack`, or a link of the project setup that runs a server step).
|===

[#question-waiver-and-exit-links]
=== Task, Answer, Waiver-Request & Exit Links
_See Requirement link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_

_See Requirement link:../../Requirements.adoc#PM-WF-18[PM-WF-18: Question Recommendation Score & Decision Quorum]_

_See Requirement link:../../Requirements.adoc#PM-WORK-4[PM-WORK-4: Consultation through the Server]_

_Implementation watch: link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-7[PM-WATCH-HYP-7]_

These links are ordinary `submit` or `noop` links; their relation and form satisfy the closed relation table (xref:02-link-grammar.adoc#_closed_link_relations_rel[Closed Link Relations (`rel`)]):

[cols="2,1,1,5"]
|===
|Link |`rel` |`form` |Semantics

|`ack`
|`next`
|`noop`
|The only link of an offered task entity (`task.offered`). The worker's explicit acknowledgement of the offer, within its host's acknowledgement deadline; it returns the task entity in the first state of its entity unit (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]).

|`ask` (`question:schema[question-envelope]`)
|`submit`
|`submit`
|Offered on a task entity only by states that declare it. Creates a server-owned question record (`origin: model`) from the model-supplied envelope (xref:02-link-grammar.adoc#named-parameter-schemas[Named Parameter Schemas]) and ends the task with the outcome `asked`; the state then waits on the record in its question state and offers a new task with the answer in its `facts` (link:../workflow-dsl/02-units-jobs-decisions.adoc#question-states[Workflow DSL Specification, Question States]). Server-raised questions (init classifiers, the optional outline review) are created by their primitive, never through `ask`.

|`ask:<task_id>` (`question:schema[question-envelope]`)
|`submit`
|`submit`
|The task-question link of a task envelope entity (`envelope.task.active`). Records the question for the plan task and ends the envelope task (`yield_reason: question`, server-recorded); the envelope's remaining plan tasks, the asking one included, go to the next envelope task, which receives the answer in `facts`. No task waits on a question.

|`infeasible` (`evidence:text[1..2000]`)
|`submit`
|`submit`
|Implicit link of every task entity except the consultation entity, after the acknowledgement (link:../model-work/05-consultation.adoc#consult-serving[Model Work Specification, Serving the Consultation]). Ends the task with the outcome `infeasible` and its evidence (required); the calling state routes the outcome (link:../model-work/02-task-protocol.adoc#task-outcomes[Model Work Specification, Closed Task Outcomes]). It carries no `confidence` (xref:02-link-grammar.adoc#decision-confidence-parameter[Decision Confidence Parameter]).

|`consult:<role>` (`question:text[1..4000]`)
|`consult`
|`submit`
|One per `consult role <role>` clause of the task's state, and no other (link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification, Grammar]). Submits a question to a task of the named role and moves the asking task to `consulting`; the answer arrives as the answer to the worker's next `pm_wait`, and the task's final submit must refer to it. A consulted task offers no `consult` link of its own (link:../model-work/05-consultation.adoc[Model Work Specification, Consultation]).

|`answer:<question_id>` (`branch_key:enum[…],text:text[1..2000]?`)
|`submit`
|`submit`
|Offered to the entry session for every open question record of the scope once it is delivered (after its adjudication): in a view of a plan or epic, and in a question state of a session-driven unit. The enum lists the record's option keys, each defined once in the record's options. The link's `facts` show the question, its `decision_kind`, the recommended option with its `recommendation_confidence` and `rationale`, the set's score, and, for a set the adjudication escalated, every vote's role, `branch_key`, confidence, and rationale (link:../model-work/10-decision-quorum.adoc#adjudication-record[Model Work Specification, Ask or Quorum, Record]), so the user sees why each role chose; the session relays the user's choice (`channel: session`). The first valid answer on any channel wins: an unknown `branch_key` is refused `invalid_link_args`, a second answer `already_answered`, an answer after the record's deadline `question_expired`. A relayed answer is a content answer only: an override is never taken as a content answer, and a content answer is never an override (`PM-WF-12`). A worker is never offered an answer link.

|`request_waiver` (`rationale:text[1..2000]`)
|`escalate`
|`submit`
|Offered only on the decision task of a remediation policy unit whose `waiver_wait_seconds` is positive and whose failing gate is on the closed waivable list. Files a waiver request (link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-request-record[Store Schemas Specification, Waiver Request Record]) that the operator answers only through the operator channel (`pm-operator waive`); the unit then waits server-side, bounded by `waiver_wait_seconds`. It is a request, never a decision the model waits on inside the call.

|`step_out` (`reason:text[1..2000]`)
|`abort`
|`submit`
|Implicit link of every resting link state of a sub-workflow that the entry session drives (the bootstrap source units and the lesson maintenance unit). Unwinds exactly one frame: the sub-workflow returns the control outcome `stepped_out` with the reason, and the caller routes it once. A step-out consumes no budget and writes no waiver. No task entity and no view offers it: a sub-workflow inside a plan or epic is left early only by the server (link:../workflow-dsl/01-grammar.adoc#sub-workflow-exits[Workflow DSL Specification, Sub-Workflow Exit Contract]).
|===

No model ends a plan or an epic: a task ends only in its closed outcomes `submitted`, `asked`, `infeasible`, and `lost` (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]), and ending a scope as `aborted` is the operator verb `pm-operator abort <plan|epic> <id> --reason`, which moves the scope to `plan.aborted` or `epic.aborted` in its next transaction.

[#model-job-states]
=== Task States (`job llm`)

A state that needs a model (refine analysis, outline authoring, the Q-Gate, task envelopes, triage, remediation decisions, the screener, and every other task site of link:../model-work.adoc[Model Work Specification]) is a task state (DSL `job llm <entity_kind> role <role> [each <primitive_id>]`, link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Task States]). Entering it creates one queue task per entity for the named role; a worker of that role receives the task as the answer to its `pm_wait` and works on the task entity. The plan representation stays a view: it carries `state`, `summary`, and `facts.task_status` (the furthest task protocol state its tasks reached: `queued`, `offered`, `executing`, or `consulting`), and never a launch instruction, a link, or anything of the worker's configuration (<<model-facing-minimality>>).

* *Completion Is the Awaited Event*: When every task of the state has ended, the server runs the return-evaluation primitive of the entity kind over the persisted records the tasks submitted and takes the transition of its closed outcome. A worker's own final output never carries a deliverable: deliverables reach the server only through `submit` links.
* *The Worker's Connection*: A worker reaches PM-MCP only through its job relay (`pm-mcp serve --job`) with its job-bound capability and generation (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]); its representations follow this format with the links of its leased task entity, and a link that would start a model is never offered to it (single-level leaf rule, `PM-WF-5`). The skills and the contract of an offered task are rendered from the same link and schema definitions as its representations, so one definition drives both.
* *Missing Submission*: When a worker ends or is fenced without the task's required submission, the worker's attempt ends; the server offers the task again within the self-remedy budget of the state, and only when it is spent does the task close `lost` and the state take its conservative fallback (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Task States]). No link resumes a task. A call that carries the token of an ended worker is refused `job_ended`, a call of a fenced generation `generation_fenced`.
