=== Closed Link Relations (`rel`)

Every link's `rel` column is drawn from a closed enumeration of 9 relation identifiers. Waiting on a job and cancelling it are engine events, never relations (xref:01-representation-and-link-forms.adoc#link-forms[Link Forms]):

[cols="1,1,3"]
|===
|`rel` Value |Allowed Forms |Semantic Meaning

|`next`
|`noop`, `submit`
|Default forward transition along the primary workflow path (for example the task acknowledgement `ack`).

|`alt`
|`noop`, `submit`
|Alternative forward transition of a session-driven state (e.g., `skip_recipe` to proceed with standard planning). The planning lane is never a model-selected link: it is computed by the server.

|`retry`
|`noop`, `submit`
|Repeat the last failed deterministic operation (build, push, CI fetch, re-scan, bot re-trigger) without changing code. The `retry` of a remediation decision task is a `submit` link carrying `reason:enum[flaky\|infra\|timeout]`, bounded by the policy's retry budget; in a session-driven state it is the bounded self-remedy of a condition.

|`fix`
|`noop`, `submit`
|Choose an in-branch fix for a failed build, check, or gate finding; the `fix` of a remediation decision task is bounded by the policy's fix budget, and a worker of the plan's writer role does the fix.

|`loop_back`
|`noop`, `submit`
|Return from `finalize` to `execute` in the plan's worktree by allocating fresh remediation tasks (the `loop_back` form of a remediation policy's `fix`, which returns `fix_requested` to its caller and is bounded by the policy's fix budget), or re-author the outline (`loop_back_outline`, bounded by the loop-back budget).

|`submit`
|`submit`
|Deliver model-authored judgment output to the server: from a worker for its leased task entity, or from the entry session on a session-driven state or an answer link (`answer:<question_id>`).

|`escalate`
|`submit`
|File a request for operator action (`request_waiver`, xref:01-representation-and-link-forms.adoc#question-waiver-and-exit-links[Task, Answer, Waiver-Request & Exit Links]). The request is a record the operator answers only with an operator verb; the model never waits on the operator inside the call, and no link requests an operator decision.

|`consult`
|`submit`
|Ask another role through the server (`consult:<role>`, one link per `consult role` clause of the task's state, `PM-WORK-4`); the answer arrives through the asker's next `pm_wait`.

|`abort`
|`submit`
|Leave a sub-workflow the entry session drives through the implicit `step_out`, which unwinds one frame and returns the control outcome `stepped_out` to its caller. Ending a plan or epic as `aborted` is never a link: it is the operator verb `pm-operator abort`.
|===

[#link-identifier-grammar]
=== Link Identifier Grammar (`<action>`, `<action>:<entity_id>`, `consult:<role>`, `answer:<question_id>`)

Link identifiers (`link` column) are server-derived, stateless tokens of the form `<action>` or `<action>:<qualifier>`. Their grammar and length bounds (action name, qualifier, and the whole link identifier) are defined in the link:../identifiers/01-general-rules-and-registry.adoc#id-link-id[Identifier Registry]; the four forms have the following semantics:

1. *Scope-Wide Link (`<action>`)*: An action name alone (for example `ack`, `submit`, `ask`, `retry`, `fix`, `loop_back`, `request_waiver`, `step_out`, or a link of a session-driven state such as `skip_recipe`); it applies to the addressed task entity or session-driven state as a whole.
2. *Entity-Addressed Link (`<action>:<entity_id>`)*: An action name, `:`, and a link:../identifiers/01-general-rules-and-registry.adoc#id-entity-id[entity identifier] (for example `submit:TASK-004`, `ask:TASK-004`, `revise:TASK-004`); it is validated against both the addressed state and the addressed `<entity_id>`'s state under the scope lock (`PM-WF-4`).
3. *Role-Addressed Link (`consult:<role>`)*: The action `consult`, `:`, and a role name of the effective role set (link:../identifiers/01-general-rules-and-registry.adoc[Identifier Registry, role name]), for example `consult:review-security`; it exists exactly once per `consult role <role>` clause of the task's state.
4. *Question-Addressed Link (`answer:<question_id>`)*: The action `answer`, `:`, and a link:../identifiers/01-general-rules-and-registry.adoc#id-question-id[`question_id`] (for example `answer:Q-004`); it addresses an open question record of the scope, is offered only to the entry session (xref:01-representation-and-link-forms.adoc#question-waiver-and-exit-links[Task, Answer, Waiver-Request & Exit Links]), and is valid only while that record is open.

=== Free Parameter Descriptor Grammar (`free` Column)

The `free` column specifies the closed schema for `pm_do(..., args)` in compact human- and model-readable form:

[source,ebnf]
----
free_spec     = "" | param_decl , { "," , param_decl } ;
param_decl    = param_name , ":" , param_type , [ "?" ] ;
param_name    = lowercase_alpha , { lowercase_alpha | digit | "_" } ;
param_type    = scalar_type
              | "list<" , scalar_type , ">" ;
scalar_type   = "text" , [ int_range ]
              | "int" , [ int_range ]
              | "enum[" , enum_val , { "|" , enum_val } , "]"
              | schema_ref ;
schema_ref    = "schema[" , schema_name , "]" ;
schema_name   = lowercase_alpha , { lowercase_alpha | digit | "-" } ;   (* identifiers.adoc, named parameter schema *)
int_range     = "[" , int , ".." , int , "]" ;
enum_val      = alpha , { alpha | digit | "_" | "-" } ;
int           = "0" | nonzero_digit , { digit } ;
alpha         = lowercase_alpha | uppercase_alpha ;
lowercase_alpha = ? ASCII "a".."z" ? ;
uppercase_alpha = ? ASCII "A".."Z" ? ;
digit         = "0" | nonzero_digit ;
nonzero_digit = ? ASCII "1".."9" ? ;
----

`param_name` is bounded as registered in the link:../identifiers/01-general-rules-and-registry.adoc#id-param-name[Identifier Registry]. `param_type` mirrors the DSL `type_spec` (link:../workflow-dsl.adoc[Workflow DSL Specification]): lists use the single syntax `list<…>` (for example `paths:list<text>?`), enum values may contain upper case (`enum[FIX|SUPPRESS|ACCEPT]`), and there is no free-form object type: the only object-valued type is the named schema reference `schema[<schema_name>]` (<<named-parameter-schemas>>), also as a list element (`list<schema[<schema_name>]>`).

[#named-parameter-schemas]
==== Named Parameter Schemas

A parameter of type `schema[<schema_name>]` takes a JSON object as its value; the server validates it against the closed JSON Schema (`additionalProperties: false` at every object level) registered under `<schema_name>`, in the same in-process validation as every other parameter (link:../workflow-dsl/05-primitives.adoc#independent-transition-validation[Workflow DSL Specification, Independent Server-Side Transition & Parameter Validation], step `P`). A violation is rejected with `invalid_link_args`, and `rejected.detail` names the parameter and the JSON pointer of the offending member. `schema_name` follows the link:../identifiers/01-general-rules-and-registry.adoc#id-schema-name[Identifier Registry, named parameter schema] grammar. Named schemas are compiled into the binary beside the workflow definitions and are closed: a new name, or a change of a registered schema, ships only with a workflow version. A `schema[…]` type naming an unregistered schema fails DSL validation (Rule 1, link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Static Verification Rules]). A named schema describes only model-supplied members; server-owned fields are never part of it, and a payload carrying one is rejected by `additionalProperties: false`.

[cols="1,3,2"]
|===
|`schema_name` |Content |Used by

|`question-envelope`
|The model-supplied part of a question record (`BatchedQuestionEnvelope` without the server-owned `question_id`, `class`, `origin`, and `source_entity`): `question_text`, `default_assumption`, `recommendation_confidence`, `rationale`, `decision_kind`, and `options` (exactly one `recommended`) as objects `{branch_key, label, description, recommended?}`; definition in link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]
|`ask` and `ask:TASK-NNN` (`question:schema[question-envelope]`); the `questions:list<schema[question-envelope]>?` parameter of the `submit` link of a refine or outline task entity

|`question-answer`
|One answer to an open question record: `question_id` (link:../identifiers/01-general-rules-and-registry.adoc#id-question-id[Identifier Registry, `question_id`]), `branch_key` (one of the record's option keys), and optional `text` (`1..2000` characters, recorded with the answer and, where the answer changes intent, in the amendment); definition in link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]
|The answer of the web app's answer endpoint; the entry session answers through `answer:<question_id>` with the record's `branch_key` and optional `text` as plain parameters

|`panel-answer`
|One panel role's answer to one question of an adjudicated set: `question_id`, `branch_key` (one of the question's option keys), `confidence` (integer `0..100`), and `rationale` (`10..500` characters); definition in link:../model-work/10-decision-panel.adoc#panel-blind-input[Model Work Specification, Blind Input]
|`submit:panel` of a panel task (`answers:list<schema[panel-answer]>`, one item per question of the set)

|`triage-groups`
|The triage of one gather firing: one entry per finding group `(domain, rule_id)` of the firing's batch with its disposition (`FIX`, `SUPPRESS`, `ACCEPT`), `reply_text` (`1..4000` characters), optional `requirement_refs`, and `population` for `FIX`, plus per-finding exceptions (`finding_id` with its own disposition and reply); a finding withheld by the screener is never part of it; definition in link:../model-work/07-untrusted-text-screening.adoc#batched-triage[Model Work Specification, Batched Triage]
|`submit:triage-groups` of the triage task of a gather firing (`triage:schema[triage-groups]`)

|`simplify-proposal`
|One simplification the read-only simplify task proposes: `file` (a repository-relative path of the plan footprint), `change` (`1..4000` characters, what to change), `rationale` (`1..2000` characters); the server records it as a proposal record with its `proposal_id` (link:../identifiers/02-registry-stores-to-web.adoc#id-proposal-id[Identifier Registry, `proposal_id`]) and never applies it itself
|`submit:simplify` of the simplify task (`proposals:list<schema[simplify-proposal]>`)
|===

NOTE: Boolean parameters are prohibited in workflow transitions to preserve explicit closed-enum intent (e.g., `decision:enum[approve|reject]` rather than `approved:bool`). A trailing `?` marks an optional parameter (such as `paths:list<text>?` or `questions:list<schema[question-envelope]>?`).

=== Direct In-Band Multi-Line Text Payloads (`PM-WF-2`, `PM-WF-6`)

Because `pm_do(scope_id, link, args)` is transported as a structured JSON-RPC 2.0 request over `stdio`, parameters of type `text[min..max]` accept arbitrary multi-line UTF-8 strings (including Markdown headings `#`, fenced code blocks, quotes, shell metacharacters, and Unicode) directly in `args`:

* *No Scratch-File Staging*: The model never invokes host `Write` or `Edit` tools on `.marshall/` files and never creates staging files of the kind `plan-marshall` needed (`.plan/temp/*-commit-msg.txt`, `work/ci-bodies/*.md`, `work/pending-tasks/*.json`, `work/lesson-body-*.md`). This is a model-facing rule, not a prevention: host file tools can still write `.marshall/`. The runtime detects such a write after the fact, on the next transition that reads a digest-protected store (the `integrity_breach` condition with kind `store_tampered`, which pauses the scope; link:../store-schemas.adoc[Store Schemas Specification], § Store Digest Verification); writes to files outside the digest-protected set are not detected.
* *Single-Turn Atomic Validation & Persistence*: When the model follows a `submit` link such as `commit` (`message:text[1..2000]`), `submit:outline` (`outline:text[1..65536]`), `create_pr` (`body:text[1..32768]`), or `retitle` (`pr_title:text[1..72]`), the server validates both the parameter bounds and the domain content grammar in-process before persisting the target store or streaming the payload to a child tool via `stdin` (`PM-EXEC-5`).
* *Self-Correcting Validation Feedback*: If a submitted multi-line payload violates a structural rule (for example, an `outline` missing a `(read|write-new|write-replace|write-conditional|delete)` file-intent suffix, or a `message` violating Conventional Commits syntax), the server leaves the state unmutated and returns `rejected.reason = "invalid_link_args"` with exact line-level `detail` alongside the current TOON representation so the model can resubmit immediately in the next turn. `rejected.detail` names the offending parameter or token, the expected shape (the schema fragment), and one corrected example.
