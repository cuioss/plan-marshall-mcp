== Overview

This document specifies the data-driven client profile schema, on-the-fly placeholder rendering rules, three-tier environment identity detection and mismatch auditing, neutral fallback profile behavior, and embedded client bundle `bundle-manifest.json` schema for *plan-marshall-mcp* (`PM-MCP`). By translating vocabulary skills, sub-agent dispatch payloads, and host tool idioms at request time from the scope's persisted `mcp/entry.json` record, the `pm-mcp` binary serves Claude Code (`claude`), OpenCode (`opencode`), Antigravity (`antigravity`), Codex (`codex`), and unknown MCP hosts (`neutral`) concurrently without static per-runtime corpus generation.

`connection.durable_cwd` records whether the host keeps its shell working directory across tool calls. When it is `false`, rendered dispatch prompts and vocabulary skills carry the directive to address files in the plan's worktree by absolute path, because a working directory set by an earlier call cannot be relied on.

=== Profile Override Hierarchy

At runtime, `pm-mcp` resolves a client profile by merging three layers in order of increasing precedence:

1. *Compiled Binary Baseline* (`classpath:/profiles/<client_id>.json`): Authoritative defaults shipped with the `pm-mcp` binary.
2. *Machine-Wide Operator Overrides* (`~/.plan-marshall/mcp/conf/profiles/<client_id>.json`): Optional partial JSON override allowing the operator to customize connection settings such as `connection.bounded_wait_seconds` across all repositories on the workstation. Model pins are not overridden here.

Model pins are resolved separately from the machine-local effort ladder `.plan/local/effort-ladder.json`, with the profile's `models` as compiled default (link:dispatch-and-effort.adoc[Dispatch & Effort Specification]). No git-tracked configuration carries client profile overrides or model pins (ADR-021); a `client_profiles` block in `.plan/marshal.json` is ignored and logged to `audit.jsonl`.

=== Rendering Invariants

1. *Zero Unresolved Placeholders*: If any `{{...}}` token in a skill template fails to resolve against the active `ClientProfile`, `ClientProfileRenderer` fails closed and logs a template defect rather than emitting raw `{{...}}` syntax to the model.
2. *Per-Variant SHA-256 Digest (`PM-SKILL-2`)*: The `_meta.sha256` digest published by `pm_skills` / `pm_skill` and `resources/read` is computed *after* rendering the skill for `(project_config, client_id, daemon_version)`. Each client sees a stable, deterministic SHA-256 digest for its rendered variant.
3. *Dispatch Suppression When Unsupported (`PM-WF-5`, `PM-CLIENT-4`)*: When `profile.dispatch.supported == false` (such as on the `neutral` profile or a host whose sub-agents lack MCP access), the workflow engine automatically suppresses `form: dispatch` links and instead serves the entity's task links directly in the main plan scope.
4. *Vocabulary-Only Translation*: `ClientProfileRenderer` varies only the placeholder dimensions of `PM-CLIENT-2` (host tool names, skill load directives, command names, tool idioms, model and effort, dispatch). It never varies emphasis, scaffolding, structure, or format: rendered variants of one template are byte-identical outside resolved placeholders.
5. *Profile Completeness*: Every canonical placeholder, and every rendering dimension added later, has a resolution in every built-in profile including `neutral`. A build-time test renders every template for every built-in profile and fails on any unresolved or missing form.

[#host-resident-surface-inventory]
=== Host-Resident Surface Inventory

For every built-in profile, the build derives and publishes the host-resident surface: the bytes the host injects into every turn by its registration mechanism (entry command descriptions, execution-context variant descriptions, MCP tool schemas and descriptions when `schema_residency: resident`, and the `pm_skills` catalogue entries once loaded), per component and in total, together with the population it measured. Residency follows the actual injection mechanism, not file existence; the population is the served set for the profile (after domain filtering, `PM-SKILL-2`), not the set of files in the binary.

* *Derived Bounds*: Any length or shape bound on a description is derived from the measured distribution of the inventory and records that derivation; a build-time test enforces the bound.
* *Named Runtimes*: A description shape rule names the runtimes and models it was reasoned about; every runtime reads the descriptions byte-identically.

== Three-Tier Environment Detection Matrix & Mismatch Auditing
_See Requirement link:../Requirements.adoc#PM-CLIENT-1[PM-CLIENT-1: Advisory Entry Identity Declaration & Persistence]_

_See Requirement link:../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Three-Tier Environment Mismatch Detection & Audit]_

_See Requirement link:../Requirements.adoc#PM-CLIENT-4[PM-CLIENT-4: Neutral Fallback Profile for Unknown Clients]_

Client identity is advisory routing and rendering metadata, never a security credential. To prevent silent profile corruption and provide full forensic visibility, PM-MCP evaluates and logs three independent identity tiers on every `pm-mcp enter` execution and every MCP tool request.

=== The Three Identity Tiers

* *Tier 1 — Declared Entry Identity (`declared_client`)*:
** Supplied explicitly via `pm-mcp enter --client <client_id> <entry> [plan_id | epic_id]` by the installed client bundle's entry command.
** Persisted in `<scope_dir>/mcp/entry.json` alongside `workspace_root`, `entry`, `client_version`, `client_session_id`, and `entered_at`.
* *Tier 2 — Detected Environment & Protocol Signature (`detected_client`)*:
** *At Entry (`pm-mcp enter`)*: Evaluated by inspecting the process environment inherited from the host shell against the detection signals and precedence of the <<host-integration-table>>.
** *At Tool Call (`stdio`)*: Evaluated from the MCP protocol `clientInfo.name` and `clientInfo.version` fields received during the session's `initialize` handshake (`absent` when omitted).
* *Tier 3 — Authenticated OS Principal (`os_principal`)*:
** The operating system effective user ID (`uid`) and username owning the local `pm-mcp` child process.

*Detection precedence*: Primary signals are evaluated in the fixed order `antigravity` -> `opencode` -> `claude` (the order `plan-marshall` uses, so a host launched from inside another host is attributed to the innermost known agent consistently), then `codex` _(provisional)_; the first match wins. === Mismatch Resolution & Audit Behavior

[cols="2,2,3"]
|===
|Scenario |Active Profile Selected |Audit & Representation Effect

|`declared_client == detected_client` (e.g., both `claude`)
|`claude`
|`audit.jsonl` records `identity_match: "exact"`, `environment_match_tier: "MATCHED"`. No warning in representation.

|`pm-mcp enter` has `declared_client: "claude"`, but environment matches `unknown` (no conflicting host markers)
|`claude`
|`audit.jsonl` records `environment_match_tier: "UNVERIFIED"`. No warning in representation.

|`pm-mcp enter` has `declared_client: "claude"`, but environment matches `opencode` (`CONTRADICTED`)
|`claude` (honors explicit `--client`, never switches silently)
|`audit.jsonl` records `event: "client_identity_mismatch"`, `identity_mismatch: true`, `environment_match_tier: "CONTRADICTED"`, `declared_client`, `detected_client`, `os_principal`. `pm-mcp enter` prints a mismatch notice; representations include `profile_warning: client_identity_mismatch`.

|`claude` (persisted `entry.json` remains authoritative until re-entered)
|`audit.jsonl` records the cross-client call mismatch. The returned TOON representation includes `profile_warning: client_identity_mismatch` and `facts.recorded_client: claude` so the calling session sees it has not entered the plan with its own client bundle.

|`mcp/entry.json` records `"client_id": "neutral"`. Every representation includes `profile_warning: neutral_fallback`; all host-specific `dispatch` links are replaced with inline `submit` task links, and skill loading uses `pm_skill`.

The `pm-mcp` binary embeds the templates for all supported client bundles under `classpath:/bundles/<client>/` (`claude`, `opencode`, `antigravity`, `codex`) and extracts them directly via `pm-mcp client install|update|remove|status` (link:cli-and-security.adoc[CLI, Coordination & Security Specification]). Multiple hosts (`claude`, `opencode`, `antigravity`, `codex`) can be installed and operated concurrently on the same machine and repository (`PM-DIST-5`).

=== Ownership & Digest Verification on Install/Update/Remove

1. *Install Record Persistence (`PM-DIST-2`, `PM-DIST-4`)*: When `pm-mcp client install` or `update` applies a manifest, it records the installed `bundle_version`, `scope`, target root, and the `sha256` of every written file and `shared_configs` key in `~/.plan-marshall/mcp/state/install-records.json`.
2. *Modification Conflict Protection (`PM-DIST-4`)*: During `pm-mcp client update` or `remove`, before overwriting or deleting any file in `files[]`, `pm-mcp client` computes the current on-disk file's SHA-256 and compares it with the `sha256` recorded in `install-records.json`. If the user has modified the file (digest mismatch), `pm-mcp client` skips overwriting that file, reports the conflict on the terminal, and preserves the user's changes unless `--force` is confirmed interactively.
3. *Surgical Shared Configuration Merging (`PM-DIST-3`, `PM-DIST-5`)*: For `shared_configs[]`, `pm-mcp client` parses the existing JSON/TOML file, updates or removes *only* the keys listed in `owned_keys`, and preserves all other MCP servers, hooks, and settings owned by the user or by sibling AI host installations.
4. *Permission Rule Grammar (`PM-DIST-2`, `PM-CRED-3`)*: `pm-mcp client install` and `update` refuse to render a host permission rule with a non-terminal `*` and refuse a deny rule for a path containing whitespace (such a path cannot be protected by a deny rule), reporting the credential-directory rule they could not install. The rule grammar check has one implementation, shared by the build-time bundle manifest tests and the installer.
