== Overview

This document specifies the data-driven client profile schema, on-the-fly placeholder rendering rules, three-tier environment identity detection and mismatch auditing, neutral fallback profile behavior, and embedded client bundle `bundle-manifest.json` schema for *plan-marshall-mcp* (`PM-MCP`). By translating vocabulary skills, sub-agent dispatch payloads, and host tool idioms at request time from the scope's persisted session history (`sessions.jsonl`, current identity = last row), `PM-MCP` serves Claude Code (`claude`), OpenCode (`opencode`), Antigravity (`antigravity`), Codex (`codex`), and unknown MCP hosts (`neutral`) concurrently without static per-runtime corpus generation.

`dispatch.token_usage_components` and `dispatch.reports_tool_uses` are the profile's usage-reporting capability. The server renders on the `returned:<dispatch_id>` link only the usage parameters the profile declares (link:dispatch-and-effort.adoc[Dispatch & Effort Specification], Normative Schema for `returned:<dispatch_id>`); a figure the host cannot report is recorded `unmeasured` with reason `not_reported_by_client`, and the model is never asked for a figure its host does not expose. The values are verified per host in Milestone 1 like the other _(provisional)_ host facts.

`connection.idle_timeout_seconds`, `connection.bounded_wait_seconds`, and `connection.progress_resets_timeout` are the host's timing facts; their values, the rule that keeps the bounded wait below the host idle timeout (enforced by profile validation for the compiled profile and every override), and their Milestone 1 verification are defined in link:timeouts.adoc#host-integration[Timeouts & Budgets Specification, Host Integration] and link:timeouts.adoc#bounded-wait[Bounded Wait Window].

`connection.durable_cwd` records whether the host keeps its shell working directory across tool calls. When it is `false`, rendered dispatch prompts and vocabulary skills carry the directive to address files in the plan's worktree by absolute path, because a working directory set by an earlier call cannot be relied on.

=== Profile Override Hierarchy

At runtime, `pm-mcp` resolves a client profile by merging two layers in order of increasing precedence:

1. *Compiled Binary Baseline* (`classpath:/profiles/<client_id>.json`): Authoritative defaults compiled into the runtime binary (`pm-mcpd`).
2. *Machine-Wide Operator Overrides* (`<PM_MCP_BASE>/conf/profiles/<client_id>.json`): Optional partial JSON override allowing the operator to customize connection settings such as `connection.bounded_wait_seconds` across all repositories on the workstation. Model pins are not overridden here.

Model pins are resolved separately from the machine-local effort ladder (`effort_ladder` of the operator file `<PM_MCP_BASE>/projects/<project_id>/local-config.json`, link:store-schemas.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), with the profile's `models` as compiled default (link:dispatch-and-effort.adoc[Dispatch & Effort Specification]). No git-tracked configuration carries client profile overrides or model pins (ADR-021); the closed team schemas admit no such key, so a `client_profiles` block in a team file is the finding `unknown_config_key` (`config_invalid`).

=== Rendering Invariants
_Implementation watch: link:../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-1[PM-WATCH-CLIENT-1], link:../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-6[PM-WATCH-CLIENT-6], link:../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-23[PM-WATCH-EXT-23]_

1. *Zero Unresolved Placeholders*: If any `{{...}}` token in a skill template fails to resolve against the active `ClientProfile`, `ClientProfileRenderer` fails closed and logs a template defect rather than emitting raw `{{...}}` syntax to the model.
2. *Per-Variant SHA-256 Digest (`PM-SKILL-2`)*: The digest `_meta["de.cuioss.pm-mcp/sha256"]` published by `pm_skills` / `pm_skill` and `resources/read` is the SHA-256 of the rendered bytes the client receives (after rendering for `(project_config, client_id, pm_mcp_version)`); it is stable while those bytes are unchanged, and a configuration or version change that leaves a skill's rendered bytes unchanged leaves its digest unchanged.
3. *Dispatch Suppression When Unsupported (`PM-WF-5`, `PM-CLIENT-4`)*: When `profile.dispatch.supported == false` (such as on the `neutral` profile or a host whose sub-agents lack MCP access), the workflow engine automatically suppresses `form: dispatch` links and instead serves the entity's task links directly in the main plan scope.
4. *Vocabulary-Only Translation*: `ClientProfileRenderer` varies only the placeholder dimensions of `PM-CLIENT-2` (host tool names, skill load directives, command names, tool idioms, model and effort, dispatch). It never varies emphasis, scaffolding, structure, or format: rendered variants of one template are byte-identical outside resolved placeholders.
5. *Profile Completeness*: Every canonical placeholder, and every rendering dimension added later, has a resolution in every built-in profile including `neutral`. A build-time test renders every template for every built-in profile and fails on any unresolved or missing form.
6. *Technique Preconditions Rendered per Project*: A skill section whose technique precondition (link:domain-extensions.adoc[Domain Extensions Specification], Core Architectural Invariants, Technique Preconditions) is unmet in the project is rendered with the marker "available technique, not adopted in this project" in place of binding wording; the precondition result is an input of the rendered variant and of its `_meta.sha256` digest. This is a project dimension, not a client dimension, so it does not break Rendering Invariant 4.

[#calibration-decision]
=== Calibration Decision
_Implementation watch: link:../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-1[PM-WATCH-CLIENT-1], link:../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-2[PM-WATCH-CLIENT-2]_

Model-facing content is calibrated once, for the weakest model reachable through the built-in effort ladders of all profiles, and rendered vocabulary-only (Rendering Invariant 4). This is a recorded decision, not a default: a byte-identical export is not neutral, and its cost is that stronger models receive more scaffolding than they need (a larger resident surface, `PM-TOOL-5`). The decision is revisited when the behavioural conformance harness (link:workflow-dsl.adoc#behavioural-conformance-harness[Workflow DSL Specification], `PM-TEST-6`) produces a per-client behavioural signal, and before the `codex` profile leaves provisional status. Any calibration axis added later is keyed by the resolved model of the effort ladder, never by the `client_id`, because one client hosts several models (the `opencode` ladder is unpinned and inherits the session model). Such an axis multiplies the rendered digests (`PM-SKILL-2`) and requires per-model content and a `PM-TEST-6` verdict for every model it distinguishes before it ships.

[#host-resident-surface-inventory]
=== Host-Resident Surface Inventory
_Implementation watch: link:../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-3[PM-WATCH-CLIENT-3]_

For every built-in profile, the build derives and publishes the host-resident surface: the bytes the host injects into every turn by its registration mechanism (entry command descriptions, execution-context variant descriptions, MCP tool schemas and descriptions when `schema_residency: resident`, and the `pm_skills` catalogue entries once loaded), per component and in total, together with the population it measured. Residency follows the actual injection mechanism, not file existence; the population is the served set for the profile (after domain filtering, `PM-SKILL-2`), not the set of files in the binary.

* *Derived Bounds*: Any length or shape bound on a description is derived from the measured distribution of the inventory and records that derivation; a build-time test enforces the bound.
* *Named Runtimes*: A description shape rule names the runtimes and models it was reasoned about; every runtime reads the descriptions byte-identically.

== Three-Tier Environment Detection Matrix & Mismatch Auditing
_See Requirement link:../Requirements.adoc#PM-CLIENT-1[PM-CLIENT-1: Advisory Entry Identity Declaration & Persistence]_

_See Requirement link:../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Three-Tier Environment Mismatch Detection & Audit]_

_See Requirement link:../Requirements.adoc#PM-CLIENT-4[PM-CLIENT-4: Neutral Fallback Profile for Unknown Clients]_

Client identity is advisory routing and rendering metadata, never a security credential. To prevent silent profile corruption and provide full forensic visibility, PM-MCP evaluates and logs three independent identity tiers on every `pm-mcp enter` execution and every MCP tool request.

=== The Three Identity Tiers

* *Tier 1 — Declared Entry Identity (`declared_client`)*:
** Supplied explicitly via `pm-mcp enter --client <client_id> <plan|epic|workspace> [plan_id | epic_id]` by the installed client bundle's entry command.
** Persisted as `client` in a new row of the scope's append-only session log `sessions.jsonl` (link:store-schemas.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]) together with `client_session_id`, `client_detected`, `environment_match_tier`, the exact host build `client_build` (from the profile's version probe, <<host-identity-probes>>), the model identity (`model_family`, `model_id`, `model_source`), `pm_mcp_version`, `bundle_version`, `project_id`, `entered_from`, `first_seen_at`, `last_seen_at`, and `transcript_locator`. The current identity of a scope is its last row.
* *Tier 2 — Detected Environment & Protocol Signature (`detected_client`)*:
** *At Entry (`pm-mcp enter`)*: Evaluated by the runtime from the environment signature that `pm-mcp enter` computes from the process environment inherited from the host shell, against the detection signals and precedence of the <<host-integration-table>>.
** *At Tool Call (`stdio`)*: Evaluated per request from the relay's connection headers (link:runtime-model.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]): `PM-MCP-Env-Signature`, computed by the relay from its inherited environment, and `PM-MCP-Client-Info`, the `clientInfo.name` and `clientInfo.version` of the host's `initialize` request as the relay recorded it (`absent` when omitted). The transport is sessionless: the runtime keeps no per-connection handshake state and derives Tier 2 from the headers of each request.
* *Tier 3 — Authenticated OS Principal (`os_principal`)*:

[#session-lifecycle-hook]
== Session Lifecycle Hook & Scope Pointer
_See Requirement link:../Requirements.adoc#PM-CLIENT-6[PM-CLIENT-6: Post-Compaction Scope Pointer]_

_Implementation watch: link:../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-4[PM-WATCH-CLIENT-4]_

After `/clear` or compaction the model has lost the `plan_id` it needs for `pm_state(plan_id)` (`PM-MIG-4`). The client bundle therefore carries a session-start hook on every profile whose Host Integration Table row names session lifecycle hook events: an owned `hook_entry` element in the host's settings file (<<bundle-manifest-scopes>>), plus a `hook` file where the host needs one. The hook runs `pm-mcp hook session-start --client <client_id>` (link:cli-and-security.adoc#session-start-hook[CLI, Coordination & Security Specification]) and injects its stdout verbatim. The verb reads persisted files only and never starts the runtime, so the hook works while no runtime runs.

* *Pointer, Never a Body*: The payload is a pointer: `scope_type`, `scope_id`, `phase`, and the literal next call (`pm_state(plan_id="…")`, `pm_state(epic_id="…")`, or `pm_state(plan_id="NO_PLAN")`), nothing else. It never carries facts, links, or state content, so it cannot go stale against the stores.
* *Events*: The hook fires on the host events listed in the table's hook-event column, which cover `startup`, `resume`, `clear`, and `compact` where the host distinguishes them.
* *Size Ceiling*: The payload is at most 512 bytes UTF-8. The CLI never truncates it; an `*IT` test asserts the ceiling for the largest valid identifiers at build time.
* *Three Normative Cases*: A live scope bound to the workspace (and, where the profile provides one, to the host session id) yields the pointer; no bound scope yields empty output and exit `0`; an unreadable or tampered scope state yields a one-line notice naming the scope and `pm-mcp status`, exit `0`. The hook never fails the host session.
* *Pointer and Drift Notice*: The hook prints the pointer and, after it, the bundle drift notice for its client (link:cli-and-security.adoc#bundle-drift-notice[CLI, Coordination & Security Specification, Bundle Drift Notice], `PM-DIST-4`). The two parts are independent: each is printed whenever its own condition holds, neither suppresses or alters the other, and the size ceiling above applies to the pointer.
* *Fallback Without Hooks*: On a host without lifecycle hooks, `pm_plans` and `pm_epics` mark the scope last entered by the request's host session (the `PM-MCP-Client-Session` header, matched against the `client_session_id` of the session rows, link:runtime-model.adoc[Runtime & Interaction Model Specification], Connection Metadata; without a session id, the scope with the most recent session row in the project) in their `last_entered` column (link:mcp-tools.adoc[MCP Tools Specification]).

== Embedded Client Bundle `bundle-manifest.json` Schema
_See Requirement link:../Requirements.adoc#PM-DIST-1[PM-DIST-1: Single Version Authority & Embedded Client Bundles]_

_See Requirement link:../Requirements.adoc#PM-DIST-2[PM-DIST-2: Embedded Bundle Extraction & Interactive Client Installer]_

_See Requirement link:../Requirements.adoc#PM-DIST-3[PM-DIST-3: Uniform Host MCP STDIO Connection Configuration]_

_See Requirement link:../Requirements.adoc#PM-DIST-4[PM-DIST-4: Bundle Upgrade Detection & Atomic Reconciliation]_

_See Requirement link:../Requirements.adoc#PM-DIST-5[PM-DIST-5: Multi-Host Concurrent Coexistence on One Machine]_

_Implementation watch: link:../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-5[PM-WATCH-CLIENT-5]_

The runtime binary `pm-mcpd` embeds the templates for all supported client bundles under `classpath:/bundles/<client>/` (`claude`, `opencode`, `antigravity`, `codex`) and applies them on the requests of `pm-mcp client install|update|remove` (link:cli-and-security.adoc#client-installer[CLI, Coordination & Security Specification, Client Bundle Installer]); `pm-mcp client status` needs no runtime and reads the install records directly. The bundle version is the release version; `pm-mcp` carries it for the drift checks. The host MCP configuration of every bundle still launches `pm-mcp serve` (`PM-DIST-3`). Multiple hosts (`claude`, `opencode`, `antigravity`, `codex`) can be installed and operated concurrently on the same machine and repository (`PM-DIST-5`).

[#bundle-manifest-scopes]
*One manifest per client, two scopes*: A client has exactly one manifest. Files that both scopes install (commands, agent variants, hook files) are declared once in `files[]` and placed through the scope's `directories` map; the `scopes` object holds a `user` and a `project` section, each with its target root, its `directories`, its `shared_configs[]` (host configuration files with owned keys and owned elements), and the files that only that scope installs (`files[]` inside the section, with a `target_path` relative to the target root). `pm-mcp client install --scope <scope>` selects one section; a host that supports only one scope declares only that section. `pm-mcp client install|update --scope project` refuses while the project has non-terminal plans or epics and names them; the `user` scope is unaffected (link:cli-and-security.adoc#client-installer[CLI, Coordination & Security Specification, Client Bundle Installer]). The install record stores the scope (link:store-schemas.adoc#machine-state-records[Store Schemas Specification, Machine State Records]).

*Owned elements*: Besides owned keys (a whole value at a dotted key path, such as the MCP server entry), a shared configuration owns individual elements of arrays that other parties share, identified by their exact normalized value:

* `permission_rule`: a host permission rule in the host's `deny`, `ask`, or `allow` list, classed `enforcement` (a defense-in-depth boundary whose removal or weakening is operator-gated, link:cli-and-security.adoc#client-operator-gate[CLI, Coordination & Security Specification, Operator Gate]) or `convenience`. The normalized value is the rendered rule text (placeholders `{pm_mcp_base}` and `{home}` resolved, surrounding whitespace removed). A rule template naming `{pm_mcp_base}` renders to one owned element per path form of the host's rule syntax: for `claude` always the absolute form (`Read(//<abs>/**)`, `Edit(//<abs>/**)`) and, when `<PM_MCP_BASE>` lies under `{home}`, additionally the home-relative form (`Read(~/<rel>/**)`, `Edit(~/<rel>/**)`, `<rel>` relative to `{home}`).
* `hook_entry`: one entry of a host hook array (for example a `SessionStart` entry running `pm-mcp hook session-start --client claude`). The normalized value is the canonical JSON serialization of the entry (RFC 8785).

A rule that names a machine path (the `<PM_MCP_BASE>/**` deny rules) is never written into a team-shared, git-tracked file: in the `project` scope it goes to the host's machine-local project settings file (for `claude`, `.claude/settings.local.json`), so the shared files keep zero user-specific paths (`PM-DIST-2`).

*Recommended permission rules*: On every host with permission rules, each scope's bundle installs as `enforcement` rules the machine root deny rules (Ownership & Digest Verification, item 5) and deny rules for the operator-facing verbs `Bash(pm-mcp operator:*)` and `Bash(pm-mcp web:*)`, rendered in the host's rule syntax and placed in its `ask` list where the host has no `deny` list. === Ownership & Digest Verification on Install/Update/Remove
_Implementation watch: link:../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-7[PM-WATCH-CLIENT-7], link:../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-12[PM-WATCH-CLI-12]_

1. *Install Record Persistence (`PM-DIST-2`, `PM-DIST-4`)*: When `pm-mcp client install` or `update` applies a manifest, the runtime records per `(client, scope, target root)` the installed `bundle_version`, the `scope`, the absolute target root, the `sha256` of every written file and owned key value, and every owned element with its normalized value and its `sha256` in `<PM_MCP_BASE>/state/install-records.json` (link:store-schemas.adoc#machine-state-records[Store Schemas Specification]).
2. *Modification Conflict Protection (`PM-DIST-4`)*: During `pm-mcp client update` or `remove`, before overwriting or deleting any recorded file or owned key, the runtime computes the current on-disk SHA-256 and compares it with the recorded `sha256`; a recorded owned element is unmodified only while an element with its recorded normalized value is present in its array. A modified entry (digest mismatch, or an element edited or deleted by the user) is skipped and reported on the terminal, and the user's change is preserved unless `--force` is confirmed interactively.
3. *Surgical Shared Configuration Merging (`PM-DIST-3`, `PM-DIST-5`)*: For `shared_configs[]`, the runtime parses the existing JSON/TOML file and changes *only* the keys listed in `owned_keys` and the recorded owned elements: `install` appends a missing owned element (one already present with the same normalized value is neither duplicated nor recorded as owned), `update` replaces the recorded elements and appends new ones, and `remove` deletes the recorded elements only. All other MCP servers, hooks, rules, and settings owned by the user or by sibling AI host installations are preserved, including their order.
4. *Permission Rule Grammar (`PM-DIST-2`, `PM-CRED-3`)*: `pm-mcp client install` and `update` refuse to render a host permission rule with a non-terminal `*` and refuse a deny rule for a path containing whitespace (such a path cannot be protected by a deny rule), reporting the credential-directory rule they could not install. The rule grammar check has one implementation, shared by the build-time bundle manifest tests and the installer.
5. *Machine Root Deny Rules (`PM-CRED-3`, `PM-SEC-2`)*: On every host with file-tool permission rules, the bundle installs deny rules for `<PM_MCP_BASE>/**` as `enforcement` `permission_rule` elements in addition to the credential rules, in the absolute form and, when `<PM_MCP_BASE>` lies under the home directory, also in the home-relative form (<<bundle-manifest-scopes,Owned elements>>), so host file tools cannot read or write the enrolment files `enrolments/`, `state/`, `run/` (the runtime token), or the fallback credential store. This is defense in depth only: a host shell tool bypasses it, and no `Bash` rule tries to cover shell access vectors to `<PM_MCP_BASE>`; enrolment integrity rests on the runtime's HMAC verification (link:cli-and-security.adoc[CLI, Coordination & Security Specification]). If `<PM_MCP_BASE>` contains whitespace, the installer refuses under item 4.
6. *Side-by-Side with Legacy `plan-marshall` (`PM-MIG-2`, `PM-DIST-5`)*: A bundle installs no legacy executor, no `execute-script.py` permission rule, and never edits, removes, or takes over artifacts or permission rules of an installed legacy `plan-marshall` plugin. Its command, agent, hook, and skill-stub names and its owned configuration keys are distinct from the legacy plugin's (for example agent `plan-marshall-execution-context-level-3` beside the plugin's `plan-marshall:execution-context-level-3`); a build-time bundle manifest test fails on a name that collides with the legacy plugin's installed names. Both may therefore be installed on one machine and used in the same repository.
7. *Drift Checks (`PM-DIST-4`)*: `bundle_outdated` compares the recorded `bundle_version` with the bundle version embedded in the running `pm-mcp`; `bundle_modified` compares the recorded digests and normalized values with the disk and lists the edited and missing entries. Both are reported by `pm-mcp enter`, the session-start hook, and `pm-mcp client status`, and fixed by `pm-mcp client update` (`--force` for modified entries) (link:cli-and-security.adoc#bundle-drift-notice[CLI, Coordination & Security Specification, Bundle Drift Notice]).
