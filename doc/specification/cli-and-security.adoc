== Overview

This document specifies the operator-facing command line of the *plan-marshall-mcp* (`PM-MCP`) native binary (`pm-mcp`) and the machine-level security mechanisms around the runtime: cross-process `FileChannel.lock()` coordination, the embedded client bundle installer (`pm-mcp client`), the entry identity recorder (`pm-mcp enter`), token-lane credential resolution, operator channel isolation (`pm-mcp operator`), and the security audit log.

The process topology (always-on runtime, `pm-mcp serve` STDIO relay), the local transport, `stdout` hygiene, runtime start/stop/drain, crash recovery, and logical plan sessions are specified exclusively in the link:runtime-model.adoc[Runtime & Interaction Model Specification].

== Process Coordination
_See Requirement link:../Requirements.adoc#PM-ARCH-1[PM-ARCH-1: Process Ownership & Always-On Runtime]_

_See Requirement link:../Requirements.adoc#PM-ARCH-2[PM-ARCH-2: Local-by-Design & Zero External Cloud Dependency]_

_See Requirement link:../Requirements.adoc#PM-SEC-4[PM-SEC-4: Local Transport Isolation, Zero Network Exposure & Stream Hygiene]_

The runtime, the `pm-mcp serve` relays, and the operator CLI share the machine-level state under `<PM_MCP_BASE>` (default `~/.plan-marshall-mcp/`; layout and permissions in link:filesystem-layout.adoc#machine-layout[Filesystem Layout Specification]). No legacy `plan-marshall` process reads, writes, or locks this state, and `PM-MCP` takes no lock of the legacy trees (`PM-MIG-2`). Every read-modify-write of a shared store is performed under the `FileChannel.lock()` of the store's sibling lock file in `<PM_MCP_BASE>/locks/` (`build-slots`, `build-timings`, `enrolments`, `install-records`, `machine-config`, `merge`, `operator-auth`, `review-bot`), never under a lock on the store file itself, which the atomic write-and-rename that completes the write replaces. Only the append-only `logs/audit.jsonl` is locked directly; `logs/audit.head` is written under that audit lock. Locks are acquired in the one total order of link:store-schemas.adoc#lock-free-snapshot-reads[Store Schemas Specification, Transaction Locks]. The operator CLI acts directly on these stores and never calls the runtime's MCP endpoint; the runtime revalidates state from disk inside every locked transition (link:runtime-model.adoc#_operator_cli_interaction[Runtime & Interaction Model Specification]).

Runtime process lifecycle, singleton discovery (`locks/runtime.lock`, `state/runtime.json`), the Unix domain socket endpoint, relay `stdout` hygiene, startup permission verification, crash recovery, and drain are specified in the link:runtime-model.adoc[Runtime & Interaction Model Specification].

== Direct Binary Bundle Extraction & Client Installer (`pm-mcp client`)
_See Requirement link:../Requirements.adoc#PM-DIST-1[PM-DIST-1: Single Version Authority & Embedded Client Bundles]_

_See Requirement link:../Requirements.adoc#PM-DIST-2[PM-DIST-2: Embedded Bundle Extraction & Interactive Client Installer]_

_See Requirement link:../Requirements.adoc#PM-DIST-3[PM-DIST-3: Uniform Host MCP STDIO Connection Configuration]_

_See Requirement link:../Requirements.adoc#PM-DIST-4[PM-DIST-4: Bundle Upgrade Detection & Atomic Reconciliation]_

The `pm-mcp` binary is the single version authority for all client integration bundles. All bundle manifests and templates are compiled directly into the native image under `classpath:/bundles/<client>/` (`claude`, `opencode`, `antigravity`, `codex`).

=== Embedded Classpath Bundle Layout

[cols="2,2,3"]
|===
|Classpath Resource Path |Client IDs |Normative Contract

|`classpath:/bundles/{client}/bundle-manifest.json`
|`claude`, `opencode`, `antigravity`, `codex`
|Contains the normative `ClientBundleManifest` (see link:client-profiles.adoc[Client Profiles Specification]) declaring `bundle_version`, `daemon_version`, `manifest_sha256`, `files[]`, and `shared_configs[]` for `scope=user` and `scope=project`.

|`classpath:/bundles/{client}/files/{bundle_path}`
|`claude`, `opencode`, `antigravity`, `codex`
|Immutable UTF-8 template bytes for every command (`/plan-marshall`, `/plan-orchestrator`, `/marshall-steward` or `$plan-marshall` skills), sub-agent variant template (`execution-context-level-1..7`, `execution-context`, `execution-context-reader-level-1..7`, `execution-context-reader`; rendered at install time from the effective effort ladder), and optional hook referenced in `bundle-manifest.json`.
|===

=== Path Traversal & Integrity Guards During Bundle Extraction

1. Every `bundle_path` and `target_path` in `bundle-manifest.json` is validated against the link:identifiers.adoc#id-bundle-path[bundle path grammar] before touching the filesystem.
2. Target installation paths are resolved against the canonical scope root (`user` home directory or `project` repository root) via `Path.resolve(targetPath).normalize()` and verified with `startsWith(canonicalScopeRoot)` (`PM-SEC-2`).
3. Before writing any extracted file, `pm-mcp client` computes the SHA-256 digest of the classpath resource bytes and verifies that it matches the `sha256` declared in `bundle-manifest.json`. For `rendered` files this is the template digest; the digest of the rendered output is recorded in `install-records.json` and used for later modification detection.

=== `pm-mcp client` CLI Subcommands (`install`, `update`, `remove`, `status`)

* `pm-mcp client install <claude|opencode|antigravity|codex> [--scope user|project]`:
** Reads `classpath:/bundles/<client>/bundle-manifest.json` directly in-process.
** Computes the diff between the target filesystem and the manifest (`files[]` additions/modifications and surgical `shared_configs[]` key merges into the host configuration files of the link:client-profiles.adoc#host-integration-table[Host Integration Table]).
** Displays the complete planned file and configuration changes on the terminal and requires interactive operator confirmation (unless `--yes` is passed for non-interactive CI/automation; see <<client-operator-gate>>).
** Writes each file atomically (`*.tmp` + `fsync` + `Files.move(..., ATOMIC_MOVE)`) and records the installed `bundle_version`, `daemon_version`, `scope`, and per-file SHA-256 digests in `<PM_MCP_BASE>/state/install-records.json` under `<PM_MCP_BASE>/locks/install-records.lock`.
* `pm-mcp client update [<client>] [--scope user|project]`:
** Compares the running binary's embedded `bundle-manifest.json` against `install-records.json`, detects any user-modified files via SHA-256 comparison (refusing to overwrite modified files without interactive confirmation), removes retired files from prior bundle versions, and atomically applies updates.
* `pm-mcp client remove <client> [--scope user|project]`:
** Removes only the unmodified files and `owned_keys` recorded in `install-records.json`, leaving all user-owned configuration keys and sibling host installations intact.
* `pm-mcp client status`:
** Reports installed bundle versions, binary version parity, and any local file modifications across all scopes.

[#client-operator-gate]
=== Operator Gate for Security-Weakening Changes

The host file-tool deny rules installed with a bundle (among them the rules covering `<PM_MCP_BASE>/**`, which include the fallback credential store `<PM_MCP_BASE>/credentials/`, `PM-CRED-3`) are a defense-in-depth boundary against the model; a model-driven shell bypasses them. A model-driven shell must not be able to remove them through the installer:

* `pm-mcp client remove` always requires an interactive terminal (`System.console() != null && System.console().isTerminal()`) and interactive confirmation; `--yes` is rejected.
* `pm-mcp client install` and `pm-mcp client update` compute whether the planned change removes or weakens any installed deny rule (a rule deleted, narrowed, or replaced by an allow rule). If so, they require an interactive terminal and interactive confirmation of the listed rule changes; `--yes` is rejected for that change and the command exits without writing anything.
* `--yes` remains accepted for `install` and `update` changes that keep or strengthen every deny rule.

== Entry Identity Recording (`pm-mcp enter`)
_See Requirement link:../Requirements.adoc#PM-CLIENT-1[PM-CLIENT-1: Advisory Entry Identity Declaration & Persistence]_

_See Requirement link:../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Three-Tier Environment Mismatch Detection & Audit]_

_Implementation watch: link:../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-1[PM-WATCH-CLI-1]_

When a user invokes `/plan-marshall`, `/plan-orchestrator`, or `/marshall-steward` (or the corresponding Codex skill), the host's entry command executes:

[source,bash]
----
pm-mcp enter --client <claude|opencode|antigravity|codex|neutral> <plan|epic|workspace> [<plan_id>|<epic_id>] [--from-epic <epic_id>] [--model <model_id>]
----

1. *Project Resolution & Enrolment*: Resolves the project from the current working directory by the project resolution rule (link:filesystem-layout.adoc#project-resolution[Filesystem Layout Specification, Project Resolution Rule]: `git rev-parse --show-toplevel` and `--git-common-dir` → enrolled `project_root` → `project_id`; a toplevel under `.marshall/local/worktrees/<x>/` → `worktree_of: <x>`; anything else refused as unenrolled), verifies the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (integrity-checked, <<enrolment-integrity>>) and, for the `plan` and `epic` scopes, that the plan lifecycle is offered in the project (lifecycle gate open, project not released, <<enrolment-lifecycle-release>>); the `workspace` scope requires enrolment only.
2. *Three-Tier Environment Detection*: Evaluates the inherited process environment against `--client` using the detection signals and precedence of the link:client-profiles.adoc#host-integration-table[Host Integration Table] (`PM-CLIENT-3`), logging the comparison to `<PM_MCP_BASE>/logs/audit.jsonl`.
3. *Host Build Probe*: Runs the version probe of the declared client's profile (link:client-profiles.adoc#host-identity-probes[Client Profiles Specification, Host Identity Probes]) with a bounded timeout, without a shell, and records its output as `client_build`; a host without a probe, a failed probe, or an expired timeout records `null`, never a guessed value. The model identity is taken from the host where the profile's identity probes name a source (`model_source: host`), else from `--model` (`model_source: declared`; the family is derived from the identifier by the compiled model-family table), else recorded `null`.
4. *Session Row Persistence*: For an existing plan or epic, or the project's workspace scope (link:filesystem-layout.adoc#workspace-home[Filesystem Layout Specification, Workspace Home]), acquires the scope lock (`<PM_MCP_BASE>/projects/<project_id>/locks/{workspace,plan-<plan_id>,epic-<epic_id>}.lock`) and appends one row to the scope's session log in the per-project machine store (`plans/<plan_id>/sessions.jsonl`, `epics/<epic_id>/sessions.jsonl`, or `workspace/sessions.jsonl`) as a journaled transaction (link:store-schemas.adoc#transaction-journal[Store Schemas Specification, Transaction Journal]). For a plan that does not exist yet, allocates a fresh `entry_id`, writes the pending entry record `<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>.json` (the session row plus `entry_id` and `from_epic`), and prints the `entry_id` for the host's entry command, which passes it to `pm_start`; `pm_start` makes the row the first row of the new plan's session log and copies `from_epic` into `origin.epic_id`, so concurrent sessions entering new plans never overwrite each other's record. A row carries `client_session_id` (read from the host's session ID variable of the link:client-profiles.adoc#host-integration-table[Host Integration Table], null when the host provides none), the declared `client`, `client_detected`, `environment_match_tier`, `client_build`, `model_family`, `model_id`, `model_source`, `pm_mcp_version`, `bundle_version` (from `state/install-records.json`), `project_id`, `entered_from` and `worktree_of`, `first_seen_at`, `last_seen_at`, and `transcript_locator` (rendered from the profile's transcript locator, null when unavailable; schema in link:store-schemas.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]); the detected environment signature and OS principal are recorded in `audit.jsonl` only. When the declared client differs from the previous row's, `pm-mcp enter` also appends an `identity` audit record (`event: entry_handover`) whose `details` carry the previous and the new `client` and `client_session_id`.
5. *Bundle Drift Notice (`PM-DIST-4`)*: Compares the `bundle_version` recorded in `<PM_MCP_BASE>/state/install-records.json` against the binary's `daemon_version`; if skewed, emits a `bundle_outdated` warning so the initial `pm_start` / `pm_state` representation prompts `pm-mcp client update <client_id>`.

== Session-Start Scope Pointer (`pm-mcp hook session-start`)
_See Requirement link:../Requirements.adoc#PM-CLIENT-6[PM-CLIENT-6: Post-Compaction Scope Pointer]_

`pm-mcp hook session-start --client <client_id>` resolves the project from the current working directory by the project resolution rule (link:filesystem-layout.adoc#project-resolution[Filesystem Layout Specification, Project Resolution Rule]) and the live scope from persisted records only: the session logs of the project's plans, epics, and workspace scope, matched on `client_session_id` where the host exposes it (Host Integration Table session ID variable), otherwise the scope with the most recent session row (`last_seen_at`) in the project; `mcp/status.json` supplies its phase. A working directory that does not resolve to an enrolled project yields empty output. It never contacts the runtime's MCP endpoint, loads no skill, and writes nothing. Its output is the pointer defined in link:client-profiles.adoc#session-lifecycle-hook[Client Profiles Specification, Session Lifecycle Hook & Scope Pointer]: empty when no scope matches, a one-line notice naming the scope and `pm-mcp status` when the matched scope's state is unreadable or fails its digest check, and exit code `0` in every case. The resolution is deterministic: the same records always yield the same pointer.

_Implementation watch: link:../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-2[PM-WATCH-CLI-2], link:../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-4[PM-WATCH-CLI-4]_

*Proven Write Credential for Upstream Filing*: A credential that an operator-confirmed filing job would use to write to a vendor tracker (the lesson Upstream Release, link:store-schemas.adoc#lesson-record[Store Schemas Specification, Lesson Record]) is proven by a write-permission probe on the target tracker before the filing job is offered; without a passed probe the release action only renders the issue body for the operator to file.

=== Two-Lane Provider Architecture

External provider integrations are strictly partitioned into two authentication lanes:

1. *System Lane (`git`, `gh`, `glab`)*: Executed as verified subprocess jobs (`PM-EXEC-5`) that inherit the developer's existing CLI authentication (`~/.gitconfig`, SSH agent, `gh auth`). `pm-mcp` never reads, extracts, or stores CLI-lane tokens.
2. *Token Lane (SonarQube/SonarCloud and authenticated upstream MCP servers)*: Executed directly by `pm-mcp`'s in-process HTTP client (`de.cuioss:cui-http`). Tokens are resolved per request by credential key (`PM-CRED-1`) from the credential store hierarchy: `<project>/<credential_key>` (project-scoped override) -> `<credential_key>` (global fallback), and sent only to the origin of the entry's `url` (`PM-CRED-5`). That `url` belongs to the operator-owned credential entry; the team configuration (`.marshall/config/project.json`) may only reference a credential key and never decides where a token is sent.

The provider operations of both lanes are contracts of the provider modules (`pm-mcp-git`, `pm-mcp-ci`, `pm-mcp-findings`, `pm-mcp-analysis`), implemented by `pm-mcp-github`, `pm-mcp-gitlab`, and `pm-mcp-sonar` (link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]); the lane assignment per variant (native or CLI adapter) is an open design topic (link:../discussions/git-provider-modules.adoc[Git and Provider Modules]).

=== OS Keyring Backends & Fallback File Store

The `CredentialStore` service uses exactly one active backend per machine, chosen at runtime start: the OS keyring when one is available, otherwise the fallback file store. A secret never exists in two backends, and within the active backend the project entry `<project>/<credential_key>` is resolved before the global entry `<credential_key>` (`PM-CRED-2`). `<project>` is the project's enrolment identifier (`PM-CRED-3`), never derived from a remote URL or a checkout path. The backends are:

* *macOS Keychain (Primary on macOS)*: Invokes macOS Security framework APIs (`SecItemAdd`, `SecItemCopyMatching`, `SecItemUpdate`, `SecItemDelete`) directly via Java 25's Foreign Function & Memory (FFM) API (`java.lang.foreign.Linker`). Items are stored under PM-MCP's own service name `de.cuioss.pm-mcp` (qualified by the instance directory when a non-default `PM_MCP_BASE` is set, `PM-DIST-5`) with account `<credential_key>` or `<project>/<credential_key>` and a trusted-application ACL restricting unprompted read access to the signed `pm-mcp` binary.
* *Linux Secret Service (Primary on Linux)*: Communicates with `org.freedesktop.secrets` over the user session D-Bus (`gnome-keyring` / `KWallet`) storing attributes `service=de.cuioss.pm-mcp`, `credential_key=<credential_key>`, and optional `project=<project>`.
* *Permission-Guarded Fallback File Store*: When no OS keyring is available (headless Linux or WSL2), secrets are stored in the `PM-MCP` credential file format (`format_version`, closed schema, written only by `pm-mcp operator credentials`, `PM-CRED-3`) at `<PM_MCP_BASE>/credentials/<credential_key>.json` and `<PM_MCP_BASE>/credentials/<project>/<credential_key>.json` (directory mode `0700`, file mode `0600`, see link:filesystem-layout.adoc[Filesystem Layout Specification] and link:store-schemas.adoc[Store Schemas Specification]). If ownership or permission checks on a credential file fail, `pm-mcp` refuses to read it and blocks only the step that needs that credential: the engine raises the `blocked` condition on the step's current state with `facts.reason: credentials_file_insecure` and `facts.operator_command` naming the exact `pm-mcp operator credentials` command that repairs it (`PM-CRED-4`). The runtime itself keeps running; it exits with code `77` only when `<PM_MCP_BASE>` or its state files fail the startup ownership and permission checks (link:runtime-model.adoc#_startup_sequence[Runtime & Interaction Model Specification]).

* *No Legacy Credential Access*: The `CredentialStore` never reads legacy `plan-marshall` credentials (its keyring entries, `~/.plan-marshall/credentials/`, `PLAN_MARSHALL_CREDENTIALS_DIR`, `PLAN_MARSHALL_HOME`), and no verb imports them (`PM-MIG-2`). Credentials enter the `PM-MCP` stores only through `pm-mcp operator credentials`, each entry operator-owned, including its allowed `url`.

=== Operator-Only Credential CLI & Runtime Secret Redaction

* *Operator CLI Verbs*: Credential mutations and verifications are restricted exclusively to interactive TTY invocations of `pm-mcp operator credentials set|status|check|verify|remove|migrate|rotate <credential_key> [--project]`. `set` always reads the secret from the terminal with echo disabled (`System.console().readPassword()`), together with the non-secret fields (`url`, `auth_type`, header settings); when targeting the file store it writes the complete credential file in the `PM-MCP` format (`format_version`, closed schema, link:store-schemas.adoc#credential-store[Store Schemas Specification, Credential Store]) atomically with mode `0600`. The CLI is the only writer of credential files: no placeholder file and no hand-edited file exists, and a file the CLI did not write in the current format is refused (`credentials_file_invalid`). Secrets are never accepted from command-line arguments or environment variables.
* *Zero Model Exposure & Redaction*: No MCP tool, resource, or state representation exposes credential values (`status` and `check` report only metadata: provider name, scope, backend type, and configured status). Every secret value resolved for a request is added to the in-memory redaction registry of the `SecretRedactor` filter, which keeps it for the runtime's lifetime solely to scrub matching byte/character sequences to `[REDACTED]` across tool results, representations, log records, `audit.jsonl` entries, and error messages. The registry is never persisted and never exported to subprocess environments or logs; it is discarded when the runtime stops (`PM-CRED-5`).

== Operator Channel Isolation & Privileged CLI (`pm-mcp operator`)
_See Requirement link:../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Elicitation & Operator CLI)]_

_See Requirement link:../Requirements.adoc#PM-WF-12[PM-WF-12: Routine User Dialogue vs Operator-Authorizing Elicitation]_

_Implementation watch: link:../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-3[PM-WATCH-CLI-3]_

Privileged actions—project enrolment (`enrol`, `unenrol`), project release (`release-project`, <<enrolment-lifecycle-release>>), credential management (`credentials`), gate overrides (`force-gate`), merge-barrier overrides (`authorize-merge`), cross-project access grants (`grant-access`), plan deletion (`delete-plan`), acceptance of manual store edits (`accept-edit`), and maintenance of the shared epic worktree (`epic-worktree teardown|adopt`, link:filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification])—are unreachable from every MCP tool.

1. *Dual Operator Channels*: Authorizing decisions require either (a) native MCP Elicitation (`elicitation/create`) on hosts where `client_profile.connection.elicitation_supported == true`, or (b) the interactive `pm-mcp operator <action>` CLI executing directly against the local state stores under `FileChannel.lock()`.
2. *Interactive TTY & Keyring / Passphrase Verification*: `pm-mcp operator` verifies that it is attached to an interactive terminal (`System.console() != null && System.console().isTerminal()`), detects and rejects the coding-agent environment signals of the link:client-profiles.adoc#host-integration-table[Host Integration Table] (primary and secondary) unless interactive operator authentication succeeds, and verifies the operator credential stored in the OS keyring (service name `de.cuioss.pm-mcp`, account `operator`). On platforms without binary-bound Keychain ACLs (Linux Secret Service or fallback file store), `pm-mcp operator` additionally prompts interactively (no echo) for the operator passphrase, verified against a salted PBKDF2-HMAC-SHA256 hash (`>= 600,000` iterations) with exponential back-off rate-limiting (link:timeouts.adoc#operator-auth-backoff[Timeouts & Budgets Specification, Operator Passphrase Back-Off]) and audit logging on every attempt. The failure counter and the next-allowed timestamp persist in `<PM_MCP_BASE>/state/operator-auth.json` (mode `0600`, updated under `<PM_MCP_BASE>/locks/operator-auth.lock`), so starting a new CLI process does not reset the back-off; a successful verification resets the counter.
3. *Accepted Residual Risk (macOS)*: Because the Keychain ACL trusts the `pm-mcp` binary itself and no passphrase is required on macOS, a model-driven shell can pass the operator checks by running `pm-mcp operator` inside a pseudo-terminal (for example via `script`) with the agent environment markers removed. This is accepted and documented as a residual risk (`PM-SEC-3`); the TTY and environment-marker checks remain as guards against accidental invocation.
4. *Blocked Condition*: When a workflow requires operator authorization and MCP Elicitation is unavailable, the engine raises the `blocked` condition on the scope's current state (link:state-catalogue.adoc#condition-blocked[State Catalogue, Conditions]; the state and `call_stack` stay unchanged), records the pending operator decision (`decision_id`) in the scope's `mcp/status.json`, populates `facts.operator_command` with the exact `pm-mcp operator ...` invocation, and offers only the link `wait:decision:<decision_id>` (rel `wait`). Following it performs a bounded wait (`PM-IMPL-4`, link:timeouts.adoc#decision-wait[Timeouts & Budgets Specification, Operator Decision Wait]) on that decision record and returns the next state as soon as the operator resolves the decision on the terminal, or the unchanged representation with its `blocked` condition when the wait bound expires. An elicitation left unanswered when its call's wait window expires falls back to this condition (link:timeouts.adoc#elicitation-wait[Timeouts & Budgets Specification, Elicitation Request]).

[#enrolment-integrity]
=== Enrolment Integrity
_See Requirement link:../Requirements.adoc#PM-SEC-5[PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement]_

* *One File, One HMAC, One Lock per Project*: Every project has its own enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (link:store-schemas.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]). Every write of it by the operator CLI (`enrol`, `unenrol`, re-baselining) runs under `<PM_MCP_BASE>/locks/enrolments/<project_id>.lock` and also writes the sidecar `<PM_MCP_BASE>/enrolments/<project_id>.json.hmac`, an HMAC-SHA-256 over the canonical file content. `unenrol` removes the file and its sidecar. The key lives in the OS keyring under the `PM-MCP` namespace (service `de.cuioss.pm-mcp`, operator lane); on hosts without a keyring it lives in `<PM_MCP_BASE>/state/enrolment-hmac.key` (mode `0600`).
* *Verification*: The runtime verifies a project's HMAC in the project's recovery after a runtime start, before the project is first served (link:runtime-model.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery]), and before every verify-not-resolve check of the project's jobs (`PM-EXEC-2`, link:job-runtime.adoc#enrolment-integrity[Job Runtime Specification]); `pm-mcp enter` and the operator CLI verify it before they use the file. On mismatch it refuses with `enrolment_tampered`, appends an `audit.jsonl` record, and names the operator command; nothing in that file is trusted until the operator re-baselines it interactively (`pm-mcp operator accept-edit --enrolment <project_id>`, after reviewing the displayed difference). A tampered file blocks only its own project; every other enrolled project keeps being served.
* *Residual Risk*: Landlock keeps jobs from writing `<PM_MCP_BASE>` on Linux (`PM-SEC-5`), but a host shell driven by the model is not a job and is not confined; the HMAC is the control against it. On macOS the Keychain releases the key to the `pm-mcp` binary without a passphrase, so a model-driven shell that passes the operator checks (Accepted Residual Risk (macOS) above) can re-baseline a tampered file. On hosts without a keyring the key file is readable by every process of the same user, so the HMAC detects edits made without the key but not a deliberate forgery. Both are documented as accepted residual risks (`PM-SEC-5`).

[#enrolment-lifecycle-release]
=== Enrolment, Lifecycle Gate & Release
_See Requirement link:../Requirements.adoc#PM-MIG-1[PM-MIG-1: Six-Stage Build-Out & Per-Project Plan Lifecycle]_

_See Requirement link:../Requirements.adoc#PM-MIG-5[PM-MIG-5: Quantitative Triggers & Project Release]_

`PM-MCP` and legacy `plan-marshall` keep separate state trees (`PM-MIG-2`, link:filesystem-layout.adoc#coexistence-lifecycle[Filesystem Layout Specification]). There is no crossing: `PM-MCP` imports nothing from legacy `plan-marshall` (no configuration, lessons, `project-architecture/`, credentials, or learned build timeouts) and never reads or writes `.plan/` or `~/.plan-marshall/`. A project is taken into use as follows; each operator verb is interactive and writes an `audit.jsonl` record:

* `pm-mcp operator enrol`: writes the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` with its HMAC sidecar (link:store-schemas.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]): the project root (refused with `enrolment_root_conflict` when another enrolment file already names it), wrappers with their `pinned_files` and interpreter, host tools, the canonical and discovery command templates it overrides, provider `verify_argv` overrides, project scripts with binding, argument schema (validated as a schema), and maximum timeout, command budgets, write paths, the captured build environment, and language servers; each field is shown to the operator for confirmation. On first enrolment it creates the project's machine store `<PM_MCP_BASE>/projects/<project_id>/` (link:filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]) with its workspace scope.
* The project setup workflow in the workspace scope (link:domain-extensions.adoc#_architecture_enrichment_judgment_links_project_setup_state_machine[Domain Extensions Specification, Project Setup State Machine]) creates, on its first run, `.marshall/` with its `.gitignore` partition (link:filesystem-layout.adoc#repository-layout[Filesystem Layout Specification]) and `.marshall/config/` with copies of the binary's default workflow units (the JSON team files are sparse and start absent); no legacy input exists.
* *Lifecycle gate*: The plan lifecycle (the `plan` and `epic` scopes) is offered in an enrolled project once the Stage 4 exit criteria are met (`PM-MIG-4`) and until the project is released; before that the orthogonal services and the workspace scope are available.
* `pm-mcp operator release-project`: the operator's switch-off for the `PM-MIG-5` triggers; stops offering the plan lifecycle for the project. Plans in flight stay readable in the project's machine store and nothing is converted. The project can continue on legacy `plan-marshall`, whose `.plan/` `PM-MCP` never touched.

== Security Audit Trail & Three-Tier Identity Verification
_See Requirement link:../Requirements.adoc#PM-SEC-6[PM-SEC-6: Security Audit Trail & Tamper-Evident Logging]_

_See Requirement link:../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Three-Tier Environment Mismatch Detection & Audit]_

_See Requirement link:../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

Every MCP tool call, state transition, job execution, credential lookup, and operator command appends a structured JSONL record to `<PM_MCP_BASE>/logs/audit.jsonl` (mode `0600`, appended under the audit lock on the log file itself, the leaf of the lock order, schema defined in link:store-schemas.adoc[Store Schemas Specification]):

* *Three-Tier Identity Tuple*: Every audit record captures (1) `declared_client` (the declared `client` of the scope's last session row, link:store-schemas.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]), (2) `detected_env` (from environment signatures at `enter` or MCP `clientInfo`), and (3) `os_principal` (`System.getProperty("user.name")` / `geteuid()`). Any disagreement between Tier 1 and Tier 2 sets `identity_mismatch: true` in `audit.jsonl`; the returned TOON representation carries only the top-level `profile_warning: client_identity_mismatch` (link:client-profiles.adoc[Client Profiles Specification], Mismatch Resolution & Audit Behavior), never the identity tuple.
* *Hash Chain*: Every record carries `prev_hash`, the lowercase hex SHA-256 of the previous record's canonical line (its exact UTF-8 bytes in the file, without the trailing newline). The first record of a new log carries the genesis value (64 `0` characters). Records are appended only by writers that hold the log's lock and read the current last line first.
* *Anchored Head (`logs/audit.head`)*: After every append the writer updates, under the same lock, the sidecar `logs/audit.head` with the current file name, record count, last `event_id`, and head hash (the hash of the last canonical line), protected by an HMAC-SHA-256 under the integrity key of the enrolment store (<<enrolment-integrity>>). The chain alone proves only that the records present are consistent; the anchored head makes a deleted log, a reset to the genesis value, a truncated tail, and a consistently rewritten chain detectable.
* *Rotation & Checkpoints*: When `audit.jsonl` exceeds `audit_rotation.max_bytes` or `audit_rotation.max_days` (`machine-config.json`, link:timeouts.adoc#audit-rotation-age[Timeouts & Budgets Specification]), the writer appends a `checkpoint` record (record count, head hash, HMAC under the same key), renames the file to `audit-<first_event_id>.jsonl`, and starts the new `audit.jsonl` with a record whose `prev_hash` is the hash of that checkpoint line. Every rotated file is listed in the append-only index `logs/audit-index.jsonl` (file name, first and last `event_id`, record count, checkpoint hash), itself hash-chained and anchored in `audit.head`. A retention purge (link:store-schemas.adoc#evidence-based-removal-sweeps[Store Schemas, Evidence-Based Removal Sweeps]) removes only whole rotated files and never their index entries, so a purged file stays accounted for.
* *Chain Verification at Runtime Start*: The runtime verifies incrementally: the HMAC of `audit.head`, the index, and the records of the current file after its last checkpoint. A missing log, a reset to genesis, a record count below the anchored count, or a head mismatch is reported as `audit_chain_broken` with `reason` `missing`, `reset`, `truncated`, or `head_mismatch`; a broken link inside the verified range uses `reason: link_broken` and names the first broken line. The full chain across all rotated files is verified on demand by `pm-mcp operator audit verify`. The same reporting rules apply to every result: on `stderr`, in `pm-mcp status`, and as an `audit_chain_broken` security record; the log is never rewritten or silently repaired, and the next record chains to the last line as found.
* *Residual Risk*: The anchoring is tamper-evident, not tamper-proof: a process that holds the integrity key (on macOS, anything that runs the `pm-mcp` binary, <<enrolment-integrity>>; on hosts without a keyring, any process of the user) can forge a consistent head. This is accepted and documented with the enrolment integrity risk (`PM-SEC-6`).
* *Error Sanitization*: Unhandled exceptions or protocol errors return only a closed-enum error code to the MCP caller, plus the `audit_id` (a UUIDv7, link:identifiers.adoc#id-audit-id[Identifier Registry]) only where the operator must look the error up (`internal_fault`, `file_unreadable`; link:hypermedia-format.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]); stack traces and host filesystem paths are written exclusively to `<PM_MCP_BASE>/logs/daemon.log`.

== Outbound HTTPS Security (`cui-http`) & Native Runtime Stack
_See Requirement link:../Requirements.adoc#PM-TECH-1[PM-TECH-1: Java 25+ & Quarkus MCP Runtime Foundation]_

_See Requirement link:../Requirements.adoc#PM-TECH-2[PM-TECH-2: Outbound HTTPS Client, LSP Client & McpAssured Testing Libraries]_

_See Requirement link:../Requirements.adoc#PM-TECH-3[PM-TECH-3: GraalVM Native Executable & Startup/Memory Bounds]_

_See Requirement link:../Requirements.adoc#PM-TECH-4[PM-TECH-4: Operating System Platform Integration (macOS & Linux)]_

_See Requirement link:../Requirements.adoc#PM-SVC-3[PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging]_

_See Requirement link:../Requirements.adoc#PM-TEST-5[PM-TEST-5: Security Boundary & Confinement Adversarial Testing]_

* *Outbound HTTPS Hardening (`de.cuioss:cui-http`)*: All outbound REST calls (SonarQube/SonarCloud) and remote upstream MCP calls use `de.cuioss:cui-http`'s `HttpHandler` and `ResilientHttpAdapter` with TLS 1.2+, mandatory certificate/hostname verification, HTTPS-only redirect following, and origin-pinned bearer token transmission (stripping `Authorization` headers on any cross-origin redirect). All URL/path/header parameters composed into outbound requests are validated through `de.cuioss.http.security` pipelines.
* *GraalVM Native Image & Resource Bounds*: Compiled as a standalone native executable (`Java 25+`, Quarkus `quarkus-mcp-server-http`, Virtual Threads); startup and memory bounds for the runtime and the relay are defined in `PM-TECH-3` and verified as described in the link:runtime-model.adoc[Runtime & Interaction Model Specification].
* *STDIO & Confinement Adversarial Verification (`PM-TEST-5`)*: Integration tests (`*IT`) using `McpAssured` (`McpStdioTestClient`) verify the transport isolation properties listed in the link:runtime-model.adoc#_verification[Runtime & Interaction Model Specification], that insecure permissions (`0755`) on `<PM_MCP_BASE>/enrolments/` trigger fail-closed termination at runtime start (exit code `77`), that insecure permissions (`0644`) on one project's enrolment file block only that project (`enrolment_insecure`), that a project's enrolment file edited outside the operator CLI is refused with `enrolment_tampered` for that project while a second enrolled project is still served, that a job writing `<PM_MCP_BASE>/enrolments/<project_id>.json` fails under the Linux Landlock write set, while an insecure fallback credential file blocks only the step that needs it (`credentials_file_insecure`), and that path-traversal or command-injection payloads are deterministically rejected and logged to `audit.jsonl`.
