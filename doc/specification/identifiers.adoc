== Overview

This document is the single source of every identifier that *plan-marshall-mcp* (`PM-MCP`) defines, persists, renders, or accepts: its grammar (a regular expression and a maximum length), who generates it, the scope in which it is unique, whether it is ever reused, and where it is used. Every other specification refers to the anchor of an identifier here (for example link:identifiers.adoc#id-plan-id[`plan_id`]) instead of restating its grammar. JSON Schema `pattern` values in tool and store schemas remain in place, because a schema must be self-contained, but each one equals the grammar registered here; a schema pattern that narrows an identifier to one of its forms (for example `pm_build` accepting only build jobs) names the narrowing in this registry.

Derivation procedures stay in their owning specification (plan ID derivation and phantom-ID refusal in link:phase-workflows.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation], `dispatch_id` lifecycle in link:dispatch-and-effort.adoc#_dispatch_id_generation_lifecycle_states[Dispatch & Effort Specification], the DSL lexical grammar in link:workflow-dsl.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification]); this registry holds only what an identifier looks like and how long it lives.

[#general-rules]
== General Rules

The following rules apply to every identifier in the registry; a table row states only what it adds.

1. *ASCII only*: Every identifier consists of printable ASCII characters (`0x21..0x7E`); none contains whitespace, a path separator other than the ones its grammar names, or a character that needs escaping in a file name, a URI path segment, a TOON scalar, or a host tool name. Unicode normalization never applies because no identifier admits non-ASCII input.
2. *Case*: Identifiers are lower case unless the grammar admits upper case explicitly (entity-addressed identifiers such as `TASK-001` and `F-12`, `module_id`, repository paths). An identifier is compared byte-exactly; the server never folds case to make two identifiers match.
3. *Separators*: `-` separates words inside one identifier, `_` separates words inside names that must also be valid tool or parameter names, `.` separates the segments of a dotted identifier (`state_id`, `primitive_id`), `:` separates the parts of a link identifier and a finalize step identifier, and `/` separates URI and path segments. No other separator is used, and an identifier never starts or ends with a separator unless its grammar says so.
4. *Maximum length*: Every identifier has a maximum length, stated in the table; a grammar whose regex is unbounded is bounded by the stated length (enforced as `maxLength` in a schema, or by the server's validator where the schema subset cannot express it). An identifier that exceeds its bound is refused, never truncated.
5. *Server-generated identifiers are opaque to the model*: The model copies a server-generated identifier verbatim from a representation, a dispatch prompt, or a tool result; it never composes, increments, or parses one. The server never derives meaning from the model's spelling of such an identifier beyond looking it up in the addressed scope.
6. *Model-supplied identifiers are validated server-side*: Every identifier that arrives from the model (tool arguments, link identifiers, `args` values that name an entity) is checked against its grammar by the server's argument validator before it is looked up, and a violation is answered as defined in link:mcp-tools.adoc#protocol-errors-vs-domain-workflow-failure-states[MCP Tools Specification, Protocol Errors] (`invalid_arguments` for tool arguments, `rejected` for link arguments). A grammatically valid identifier that names nothing in the addressed scope is `scope_not_found` or `link_not_available`, never an empty result.
7. *No identifier encodes another scope's identifier*: An identifier is resolved only within the scope that the same call addresses; it never embeds the `plan_id`, `epic_id`, or `project_id` of another scope (`dispatch_id`, `message_id`, `job_id`, and `decision_id` carry no scope). Composite storage addresses such as `plans/<plan_id>/`, `locks/plan-<plan_id>.lock`, the credential account `<project_id>/<credential_key>`, the archived epic directory `<epic_id>-<YY-MM-DD>`, the capture ref `refs/pm-mcp/captures/<plan_id>` of a `local_changes` plan (link:phase-workflows.adoc#_plan_source_contracts[Phase Workflows, Plan Source Contracts]), or the baseline scratch worktree `.marshall/local/worktrees/baseline-<plan_id>-<sha12>` (`<sha12>` the first 12 hex digits of the merge-base commit, link:job-runtime.adoc#_gate_honesty_verification[Job Runtime, Gate Honesty Verification]) are paths built from identifiers, not identifiers, and are never parsed back into one.
8. *Stability*: An identifier is immutable once allocated. An identifier marked _never reused_ is not allocated again after its entity is deleted, archived, or retired; one marked _re-derivable_ is computed from content and is equal whenever the content is equal.
9. *Schema subset*: A tool `inputSchema` expresses a grammar with a lookaround-free `pattern` plus `minLength`/`maxLength` (link:mcp-tools.adoc[MCP Tools Specification], Architectural Constraint 3). Stored schemas may use lookaround.

[#registry]
== Registry

`Generated by` names the party that allocates the value: *server* (the runtime or the operator CLI computes it), *model* (supplied in a tool call or link argument, validated by the server), *operator* (set through an operator CLI verb or operator-owned file), *user* (typed into the host entry command), or *build* (fixed in the compiled binary, a workflow definition, or a compiled-in catalogue).

[#resolution-record]
== Resolution Record

Unifying the identifiers (operator decision D40(a)) removed the following divergences; each resolution chose the most restrictive rule consistent with every use.

[cols="1,3"]
|===
|Identifier |Resolution

|`recipe_key` / `recipe_id`
|`pm_start.recipe_id` admitted `_` and 64 characters while `recipe_key` admitted any length: a key with `_` or of more than 37 characters produced a recipe plan ID outside the `plan_id` grammar. Both now use the `recipe_key` grammar with at most 37 characters, and `recipe_id` is the parameter name only.

|`plan_slug`
|The slug admitted one or two characters, which derive no valid `plan_id`; the minimum length is now 3.

|`lesson_id`
|`pm_start.lesson_id` accepted any `^[A-Za-z0-9][A-Za-z0-9_.-]{1,63}$` token while the lesson store defines the dated form; `pm_start` now uses the lesson store grammar.

|Link identifier and `entity`
|`pm_do.link` bounded neither part (`maxLength` 128), the hypermedia patterns allowed 64-character actions (138 characters in total), and `entity` admitted `:`, which no entity-addressed link can carry. Actions are now at most 32 characters, entities follow one grammar without `:`, and the link is at most 106 characters.

|`module_id`
|`pm_build.module` admitted `/` and `:` and 128 characters, which cannot appear in the URI segment of `pm://architecture/modules/{module_id}` or in the entity `enrich-<module_id>`; `module_id` now has one grammar of at most 57 characters.

|Canonical build verb
|`pm_build.command` and `PM-TOOL-2` listed `compile`, `test`, `module-tests`, `quality-gate`, `verify`, `coverage`, `format-check`, while the domain templates and the build classes used `plan-marshall`'s canonical commands. One closed set, equal to `plan-marshall`'s `ALL_CANONICAL_COMMANDS`, now serves all of them (link:job-runtime.adoc#canonical-build-verbs[Canonical Build Verb Set]); `test` and `format-check` are removed.

|`job_id`
|Only builds had a grammar (`b-`); CI (`c-`) and review-bot (`r-`) jobs appeared only in examples, and the other job kinds had none. One grammar with a kind prefix now covers all seven job kinds.

|`decision_id`
|Generic 64-character token although the server generates it; now `dec-` plus hex, as in the examples.

|`audit_id`
|The security specification defined a UUIDv7 while the error envelope example showed `aud-20260925-004192`; `audit_id` is the UUIDv7 `event_id` of the audit record. `transaction_id` uses the same UUIDv7 form.

|`phase`
|Findings used `2-refine`..`6-finalize` while the status store used `phase-2-refine`..`phase-6-finalize`, and the representation projection omitted the `workspace` phase. Every persisted `phase` now uses the status-store value; the representation projection gained `workspace`.

|`upstream tool name` / `server_id`
|`^up_[a-z0-9_]+$` let a `server_id` containing `_` make the name ambiguous and did not bound the length; `server_id` is now alphanumeric and the name at most 64 characters.

|Skill URIs
|`^skill://pm/[a-z0-9/_-]+/SKILL\.md$` admitted empty and separator-only segments; segments now start with a letter or digit.

|Recipe `script_job_id`
|Named a key of the enrolled `project_scripts`, not a job; renamed `project_script_id`.

|SHA-256 and migration patterns
|`[a-f0-9]` / `\d` spellings of the same grammar are normalized to `[0-9a-f]` / `[0-9]`.
|===
