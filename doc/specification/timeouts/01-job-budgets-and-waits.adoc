[#job-budgets]
== Job Budgets & Escalation
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-3[PM-WATCH-JOB-3], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-15[PM-WATCH-JOB-15], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-16[PM-WATCH-JOB-16]_

Every job, and every in-process `git` or `ci` operation of the native variant (<<in-process-operations>>), runs under a wall-clock budget $t$ allocated at its start and recorded, with its `budget_derivation`, in the job record (`PM-EXEC-4`, `PM-EXEC-6`); the representation carries neither, since the derivation only selects the retry link the server offers (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). The budget is keyed per project by the *budget key*:

* build jobs: the canonical command `<build_system>:<verb>[@<module_id>]` (canonical verb from the link:../job-runtime/02-confinement-and-environment.adoc#canonical-build-verbs[Canonical Build Verb Set], module omitted for a whole-tree run; a build profile is named literally in the verb's template and is no key component), for example `maven:quality-gate` or `maven:module-tests@plan-marshall-mcp`;
* `git` and `ci` operations: `<kind>:<operation>`, where `<operation>` is the closed contract operation name of the composing primitive, for example `git:worktree-remove` or `ci:checks`. The key is the same for the native and the CLI variant: a project uses one variant per integration, so the key needs no variant component;
* `project_script` jobs: `project_script:<project_script_id>`;
* model jobs (kind `llm`): `llm:<role_key>`, one key per role whatever the harness, for example `llm:plan.phase-5-execute.effort.default` or `llm:screen.effort` (role keys of the link:../dispatch-and-effort/03-escalation-roles-readers.adoc#_role_registry_lookup_hierarchy[Role Registry]).

The budget of every job starts at its spawn: a job recorded `queued` while it waits for a build or model slot (<<model-slot-wait>>; link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas, Machine Lease Stores]) has no budget running, and its queued time is outside the budget and outside the model job's measured duration.

Learned values live in the project's `<PM_MCP_BASE>/projects/<project_id>/build-timings.json` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#build-timings-store[Store Schemas, Build Timings Store]) under this key (link:../job-runtime/03-parsers-and-gates.adoc#_adaptive_timeout_learning[Job Runtime Specification, Adaptive Timeout Learning], which defines which runs feed the learned baseline).

[#in-process-operations]
=== In-Process Operations of the Native Variant

A native `git` or `ci` operation runs inside the runtime, not as a process (link:../job-runtime/01-pipeline-and-subprocesses.adoc#in-process-operations[Job Runtime Specification, In-Process Operations]); the operation classes, floors, allocation, learning, escalation, and the no-verdict rule above apply to it unchanged:

* *Cooperative Cancellation*: At budget expiry, on `cancel:<job_id>`, and at drain, the runtime cancels the operation cooperatively: JGit operations through their `ProgressMonitor` (`isCancelled`) and revision-walk cancellation, provider requests by interrupting the HTTP exchange. Every HTTP request additionally carries the <<http-request-timeout>>, so no single request can outlast the class budget.
* *Abandonment*: An operation that has not returned within the termination grace period (<<grace-period>>) after cancellation is abandoned: it is recorded at the deadline, and the result that arrives later is discarded.
* *Partial Results Discarded*: A cancelled or abandoned operation yields no result record; nothing it observed before the cancellation is used. A mutation it may have applied is established only from the observed repository or provider state before any retry, as for a job (a push by `ls-remote`, a merge or enqueue by the provider observation, a worktree removal by the <<worktree-remove-recheck>>).
* *Outcome*: Budget expiry records `timed_out`, which is `no_verdict` (<<no-verdict-rule>>); cancellation records `cancelled`, drain records `killed`.

[#no-verdict-rule]
=== Timed-Out Outcomes Are No-Verdict

* *Every `timed_out` is `no_verdict`*: A job settled `timed_out` counts as `no_verdict` in every roll-up (landing facts, metrics, gate facts, CI taxonomy, finding counts), never as `failed` and never as `succeeded`, whatever its `budget_derivation`. It never fails a gate, and it emits zero located code errors or findings (`PM-EXEC-4`).
* *The derivation selects only the retry offer*: A `timed_out` job auto-offers `retry` with the escalation budget $E$ when $E > t$ (derivations `floor_default`, `learned`, `operator`, and `escalated` below the cap). When $E = t$ (the budget already reached $\max(t, C)$) or for a `project_script`, `retry` is offered at $t$, bounded by the retry budget of the calling policy or the condition budget (<<remediation-budgets>>); no `escalate` link exists, and `facts.operator_command` names the enrolment verb with which the operator may set an operator budget above the cap.
* *Budget statistic*: A budget always names the statistic it came from (the blend $L$ with its observation count, never a median or percentile); a p50 or p95 duration quoted in a record or report is labelled as such and is never used as a budget.

[#worktree-remove-recheck]
=== Partial-Removal Re-Check after a Timed-Out `git worktree remove`

A `timed_out` `git worktree remove` can leave a partially deleted tree. Before any retry and before the removal is recorded:

1. The runtime runs `git.worktree-list` in the main checkout (budget class <<git-local-budget>>) and checks whether the worktree directory still exists.
2. *Unregistered and absent*: the removal is complete; it is recorded (`worktree_path: null`) with `removal_evidence: recheck`.
3. *Registered but the directory is absent*: the runtime runs `git.worktree-prune` and repeats step 1 once; it records the removal only on the re-checked positive evidence.
4. *Directory present (registered or not)*: `worktree_path` stays set, the step reports `worktree_removal: partial` with the remaining path, and `retry` is offered with the escalation budget; the retry never adds `--force`.
5. *Re-check itself fails or times out*: the removal is `indeterminate`; nothing is recorded as removed (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas, Evidence-Based Removal Sweeps]).

[#remediation-budgets]
== Remediation Budgets, Question & Waiver Waits
_See Requirements link:../../Requirements.adoc#PM-WF-7[PM-WF-7: Remediation Policies, Loop-Back & Iteration Bounds], link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides], link:../../Requirements.adoc#PM-WF-13[PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier]_
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-39[PM-WATCH-STORE-39]_

Every blocking condition of a plan has a bounded self-remedy and then a defined fallback (`returned` or `handed_back`, link:../phase-workflows/06-finalize-re-entry-and-merge.adoc[Phase Workflows Specification, Plan Outcomes]); no wait of a plan is unbounded except the integrity pause and a question in `questions.mode: operator`, which the operator chose. Remediation budgets are call arguments of the project-owned phase units, bound with their source in the plan instance (link:../store-schemas/14-plan-instance-waivers-questions.adoc#plan-instance[Store Schemas, Plan Instance]); they are counted per plan and policy class and never reset (link:../store-schemas/14-plan-instance-waivers-questions.adoc#policy-counter[Store Schemas, Remediation Budget Accounting]). A step-out consumes no budget.

*Deadline processing*: The waiver wait and the question deadline are engine-owned instants persisted with their record (`expires_at`), processed by the runtime's deadline timer (link:../job-runtime/01-pipeline-and-subprocesses.adoc#engine-deadlines[Job Runtime Specification, Engine Deadlines]); the two never overlap in one plan, the integrity pause holds both fallbacks until it ends, and `abort` / `delete-plan` close pending questions `cancelled` and waiver requests `expired`.
