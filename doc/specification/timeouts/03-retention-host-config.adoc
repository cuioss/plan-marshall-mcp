[#size-limits]
== Model Job Input Size Limits

Two compiled size bounds shape what a model job receives in-band. Their values are _provisional_: the Milestone 1 headless-CLI spikes calibrate them against the context windows of the supported harnesses, and this table is the one place the calibrated values are recorded. The table uses the columns above; a size bound has no expiry, so that column states what happens above the bound.

[cols="2,3,2,2,2,3,2"]
|===
|Name |Value / derivation |Configurable? |Floor / cap |Applies to |Behaviour above the bound |Defined for

|[[prompt-in-band-bound]]Prompt in-band skill bound
|Provisional `262144` bytes of rendered skill content per prompt file (UTF-8), counted in composition order.
|fixed
|—
|The prompt file of every model job except the screener
|The remaining skills are rendered as their section index with the URIs that `pm_skill` serves; the job is never refused for size.
|link:../dispatch-and-effort/05-model-job-launch.adoc#job-prompt[Model Jobs & Effort Specification, Job Prompt]

|[[screening-split-bound]]Screening split bound
|Provisional `65536` bytes of level-1-cleaned item text per screener part (UTF-8, delimiters included); a single item above the bound forms a part of its own.
|fixed
|—
|Screener jobs (`screen.effort`) over a `batch-v1` batch
|The batch's uncached items are split into consecutive parts in item order, one screener job each: the screener state is a fan-out `job llm` state (`job llm screen role screen.effort each screen.batch-parts`, over the server-computed list of parts), which completes when every part has its verdict.
|link:../dispatch-and-effort/06-untrusted-text-screening.adoc#screener[Model Jobs & Effort Specification, Screener Job]
|===

[#configuration-keys]
== Configuration Keys

The configurable values above, by store:

* `machine-config.json` (operator CLI, link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas, Machine Configuration Store]): `drain_timeout_seconds`, `escalation_cap_seconds`, `model_slots`, `progress_wait_max_seconds`, `lsp_idle_timeout_seconds`, `lsp_start_timeout_seconds`, `lsp_request_timeout_seconds`, `audit_rotation.max_days`, `audit_rotation.retain_days`, `client_profiles.<client_id>.connection.{bounded_wait_seconds, idle_timeout_seconds, progress_resets_timeout}` (machine-wide overrides of the compiled client profile values), and `project_defaults.retention.*` (machine-wide defaults of the per-project retention keys). The `proxy` and `web` objects of the same file hold no timeout.
* `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (operator CLI, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas, Operator Local Configuration]): `retention.*`, `questions.wait_seconds` (machine-wide defaults in `machine-config.json` `project_defaults`), and, per upstream server, `upstream_mcp.servers.<server_id>.connect_timeout_seconds` and `read_timeout_seconds` (written by `pm-operator upstream allow`, link:../mcp-tools.adoc[MCP Tools Specification, Upstream MCP Proxy]; <<host-integration>>, Outbound HTTPS and upstream MCP call timeouts).
* Project-owned phase units `.marshall/config/*.pmwf` (team, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Units]): the remediation call arguments `retry_budget`, `fix_budget`, `waiver_wait_seconds`, within the compiled hard caps (xref:01-job-budgets-and-waits.adoc#remediation-budgets[Remediation Budgets]); a plan's effective ceiling is raised only by a `raise` waiver.
* `enrolments/<project_id>.json` (operator CLI, link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas, Project Enrolment Store]): `command_budgets` (operator budgets per budget key, `llm:<role_key>` of model jobs included), `project_scripts.<project_script_id>.max_timeout_seconds`.
* Client profile (compiled; the operator override is the `client_profiles` object of `machine-config.json` above): `connection.bounded_wait_seconds`, `connection.idle_timeout_seconds`, `connection.progress_resets_timeout`.

No team configuration file (`.marshall/config/*.json`) holds a timeout, wait, threshold, or retention value; the remediation budgets are unit call arguments, not configuration keys. Tuning values that calibrate server algorithms are compiled constants (`fixed` above, and in the owning specification: the recipe auto-route threshold `0.6`, the lane prune thresholds, the refine confidence threshold `95`, the iteration caps, the step wait timeouts, the preference recurrence threshold, the untrusted raw-input byte cap, the review rate-window floor `3600`, the re-review completion allowance `600`, the default review attempt ceiling `6`, the provider re-poll cadence `30`, the merge-queue stall fallback `3600`, the native request timeouts, the `git.commit-fix` cap of `3` failed commit attempts per identical staged change set: staged tree id plus message, reset when either changes, CLI variant only, exhaustion returns `stepped_out` with cause `attempts_exhausted` to the caller, the attempt caps of the other model loops of `git.commit_and_push` (xref:01-job-budgets-and-waits.adoc#commit-attempt-caps[Commit sub-process attempt caps]), the model job role floors (xref:01-job-budgets-and-waits.adoc#model-job-budget[Model job budget]), the hard caps of the remediation budgets, the condition budget, the watch restart budget, and the failed-step re-fire); per-project tuning would make metrics incomparable across projects (`PM-MIG-5` triggers).

A value outside its floor or cap is never used: the runtime clamps it to the bound and reports the configured value, the used value, and the source (`machine_config`, `local_config`, `enrolment`, `profile_override`, `compiled_default`, `invalid`, or `unreadable`) in `pm-operator status` and in the record of the affected job (`clamped_values`, link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas, Job Record]) or wait, never in its facts: the model cannot change an operator value.

[#resolved-divergences]
== Resolved Divergences

The definitions that existed before this document, and how they were resolved:

[cols="2,4"]
|===
|Item |Divergence and resolution

|No-verdict rule
|`PM-EXEC-6` and Adaptive Timeout Learning made only a `timed_out` job with a `floor_default` or `escalated` budget no-verdict, while Process Termination counted every `timed_out` as `no_verdict`. Every `timed_out` is now `no_verdict`; the derivation selects only the retry offer (xref:01-job-budgets-and-waits.adoc#no-verdict-rule[Timed-Out Outcomes Are No-Verdict]).

|Escalation
|$E = \min(2 \times t, 1800)$ lowered the budget when $t > 1800$ (for example after an operator budget above the cap). Now $E = \max(t, \min(2 \times t, C))$ with the configurable cap $C$.

|Operator budget vs floors
|Job Runtime let an operator per-command budget "win over every derivation", while Domain Extensions said floors are "never violated, even if an explicit bound is configured". An operator budget may exceed the cap but is clamped up to the engine floor ($\max(F, O)$), as `plan-marshall`'s explicit bound is.

|Python floor
|Job Runtime and `PM-EXEC-6` put the `330` floor on "pytest", Domain Extensions on "pyproject". `plan-marshall` applies `PYTEST_OUTER_FLOOR_SECONDS` to every pyproject command; the floor is keyed by build system (`pyproject`).

|Progress notification interval
|Job Runtime emitted frames every 5 s, `PM-IMPL-4` required "at least every 60 seconds", and the Hypermedia Format described "60s MCP progress notifications". The interval is `5`; `60` is the ceiling between two frames.

|LSP idle key
|MCP Tools named the eviction key `idle_timeout_seconds`, which is the client profile's host idle timeout; the key is `lsp_idle_timeout_seconds` in `machine-config.json`.

|Drain timeout key
|Runtime Model referenced `drain_timeout_seconds` in `machine-config.json`, which the schema did not define; the key is now in the schema.

|Git, CI and script budgets
|Undefined; a watch fixture recorded a 60 s git budget firing twice. Defined per operation class with floors (xref:01-job-budgets-and-waits.adoc#job-budgets[Job Budgets & Escalation]); `project_script` uses the enrolled maximum, which the enrolment schema did not carry. The classes apply unchanged to the in-process operations of the native variant (xref:01-job-budgets-and-waits.adoc#in-process-operations[In-Process Operations of the Native Variant]).

|Review-bot window floor and attempt ceiling
|This document and Phase Workflows registered different rate-window floors, and the registry's default `attempt_ceiling` had no source. The floor is `3600` and the default ceiling `6`, `plan-marshall`'s window default and attempt cap (xref:01-job-budgets-and-waits.adoc#review-bot-windows[Review bot windows]).

|Bounded wait vs host idle timeout
|"Safely below the host's idle timeout" had no rule; profile validation now rejects `bounded_wait_seconds` above `idle_timeout_seconds − 30`.

|Sub-agent time bound
|The host-dispatched sub-agent had no timeout ("there is no dispatch timeout") and a `dispatch_id` became stale only when superseded, while every job had a budget. Every sub-agent is now a server-launched model job under a per-role budget with floors (xref:01-job-budgets-and-waits.adoc#model-job-budget[Model job budget]); `dispatch_id` and its staleness are removed.

|Setup question expiry
|The question wait named the `recommended` option as the setup fallback, while the setup states declare their own fallback (`skip`, `keep_build_map`, no change). The declared fallback of the question state applies (xref:01-job-budgets-and-waits.adoc#question-wait[Question wait]).

|Operator waits
|The operator decision wait never expired and the elicitation fallback raised a `blocked` condition, so an unattended plan could wait without bound. Under the self-enforcing process (link:../../discussions/workflow-consistency.adoc[Workflow Consistency]) the decision wait and the grant expiry rows are removed; every human wait is bounded (<<configuration-keys>>; xref:01-job-budgets-and-waits.adoc#remediation-budgets[Remediation Budgets, Question & Waiver Waits]) except the integrity pause and an operator-chosen `questions.mode: operator`.
|===
