[#size-limits]
== Worker Input Size Limits

Two compiled size bounds shape what a worker receives in-band. Their values are _provisional_: the Milestone 0 headless-CLI spikes calibrate them against the context windows of the supported harnesses, and this table is the one place the calibrated values are recorded. The table uses the columns above; a size bound has no expiry, so that column states what happens above the bound.

[cols="2,3,2,2,2,3,2"]
|===
|Name |Value / derivation |Configurable? |Floor / cap |Applies to |Behaviour above the bound |Defined for

|[[prompt-in-band-bound]]Prompt in-band skill bound
|Provisional `262144` bytes of rendered skill content per prompt file (UTF-8), counted in composition order.
|fixed
|—
|The launch prompt of every worker except the screener, and the skills an offer carries
|The remaining skills are rendered as their section index with the URIs that `pm_skill` serves; the worker is never refused for size, and a submit before it has loaded every required skill is rejected `skills_not_loaded` with the missing URIs (link:../model-work/04-worker-launch.adoc#skill-delivery[Model Work Specification, Skill Delivery Record]).
|link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]

|[[screening-split-bound]]Screening split bound
|Provisional `65536` bytes of level-1-cleaned item text per screener part (UTF-8, delimiters included); a single item above the bound forms a part of its own.
|fixed
|—
|Screener tasks (role `screener`) over a `batch-v1` batch
|The batch's uncached items are split into consecutive parts in item order, one screener task each: the screener state is a fan-out `job llm` state (`job llm screen role screener each screen.batch-parts`, over the server-computed list of parts), which completes when every part has its verdict.
|link:../model-work/07-untrusted-text-screening.adoc[Model Work Specification, Screener]
|===

[#configuration-keys]
== Configuration Keys

The configurable values above, by store:

* `machine-config.json` (operator CLI, link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas, Machine Configuration Store]): `drain_timeout_seconds`, `escalation_cap_seconds`, `model_slots`, `progress_wait_max_seconds`, `lsp_idle_timeout_seconds`, `lsp_start_timeout_seconds`, `lsp_request_timeout_seconds`, `audit_rotation.max_days`, `audit_rotation.retain_days`, `client_profiles.<client_id>.connection.{bounded_wait_seconds, idle_timeout_seconds, progress_resets_timeout}` (machine-wide overrides of the compiled client profile values), and `project_defaults.retention.*` (machine-wide defaults of the per-project retention keys). The `proxy` and `web` objects of the same file hold no timeout.
* `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (operator CLI, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas, Operator Local Configuration]): `retention.*`, `questions.wait_seconds` (machine-wide defaults in `machine-config.json` `project_defaults`), and, per upstream server, `upstream_mcp.servers.<server_id>.connect_timeout_seconds` and `read_timeout_seconds` (written by `pm-operator upstream allow`, link:../mcp-tools.adoc[MCP Tools Specification, Upstream MCP Proxy]; <<host-integration>>, Outbound HTTPS and upstream MCP call timeouts).
* Project-owned phase units `.marshall/config/*.pmwf` (team, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Units]): the remediation call arguments `retry_budget`, `fix_budget`, `waiver_wait_seconds`, within the compiled hard caps (xref:01-job-budgets-and-waits.adoc#remediation-budgets[Remediation Budgets]); a plan's effective ceiling is raised only by a `raise` waiver. The declarations of `replan.pmwf` (re-planning thresholds, budget, prerequisite wait) and `question-adjudicate.pmwf` (the decision declarations, `ask` or a quorum per decision kind, the vote wait, and the calibration level), within their compiled bounds (link:../workflow-dsl/02-units-jobs-decisions.adoc#unit-declarations[Workflow DSL Specification, Unit Declarations]).
* `enrolments/<project_id>.json` (operator CLI, link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas, Project Enrolment Store]): `command_budgets` (operator budgets per budget key, `llm:<role>` of workers included), `project_scripts.<project_script_id>.max_timeout_seconds`.
* Client profile (compiled; the operator override is the `client_profiles` object of `machine-config.json` above, for the `connection` keys only): `connection.bounded_wait_seconds`, `connection.idle_timeout_seconds`, `connection.progress_resets_timeout`, and the worker values `worker.ack_deadline_seconds`, `worker.ack_informational`, `worker.silence_grace_seconds`, `worker.idle_wakeups` (xref:01-job-budgets-and-waits.adoc#worker-supervision[Worker Supervision & Recycling]).
* Role artifacts (operator files of the role sets, link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]): `budget_floor_seconds` (xref:01-job-budgets-and-waits.adoc#model-job-budget[Worker budget]), `recycling.idle_wakeups`, `recycling.token_budget`, `recycling.tasks_per_generation`.

No team configuration file (`.marshall/config/*.json`) holds a timeout, wait, threshold, or retention value; the remediation budgets are unit call arguments, not configuration keys. Tuning values that calibrate server algorithms are compiled constants (`fixed` above, and in the owning specification: the recipe auto-route threshold `0.6`, the lane prune thresholds, the refine confidence threshold `95`, the iteration caps, the step wait timeouts, the preference recurrence threshold, the untrusted raw-input byte cap, the review rate-window floor `3600`, the re-review completion allowance `600`, the default review attempt ceiling `6`, the provider re-poll cadence `30`, the merge-queue stall fallback `3600`, the native request timeouts, the attempt caps of `git.commit_and_push` (xref:01-job-budgets-and-waits.adoc#commit-attempt-caps[Commit sub-process attempt caps], xref:01-job-budgets-and-waits.adoc#commit-fix-change-set-cap[`git.commit-fix` change-set cap]), the language server restart cap (xref:02-runtime-leases-operator-web.adoc#lsp-restart-cap[Language server restart cap]), the compiled minimum of the role floors (xref:01-job-budgets-and-waits.adoc#model-job-budget[Worker budget]), the start-failure guard, the task re-offer budget, the hard caps of the remediation budgets, the condition budget, the watch restart budget, and the failed-step re-fire); per-project tuning would make metrics incomparable across projects (`PM-MIG-5` triggers).

A value outside its floor or cap is never used: the runtime clamps it to the bound and reports the configured value, the used value, and the source (`machine_config`, `local_config`, `enrolment`, `profile_override`, `compiled_default`, `invalid`, or `unreadable`) in `pm-operator status` and in the record of the affected job (`clamped_values`, link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas, Job Record]) or wait, never in its facts: the model cannot change an operator value.
