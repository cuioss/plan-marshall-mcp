== Plan Workflow

The plan workflow is one definition unit merged from `init.pmwf`, `refine.pmwf`, `outline.pmwf`, `plan.pmwf`, `execute.pmwf`, `land.pmwf`, and `finalize.pmwf`; its start state is `init.classify` (link:../workflow-dsl/02-units-jobs-decisions.adoc#workflow-definition-units[Workflow DSL Specification, Workflow Definition Units]). The lane topology is specified in link:../phase-workflows/01-planning-phases-1-2.adoc#_lifecycle_topology_phases_14[Phase Workflows Specification, Lifecycle Topology].

|[[state-init.classify]]`init.classify`
|`phase-1-init`
|`auto`
|`pm_start` (start state of the plan workflow).
|Runs in fixed order: recipe scorer, request-aspect classification, and (source `lesson`) doc-shaped predicate for every source other than `recipe` (`auto_route_recipe` only chooses auto-route vs `init.recipe-candidate`), initial planning-lane router and `scope_estimate`, sibling collision detector, workflow settings resolution, `main_sha` base stamp. For source `local_changes`: collision detector and settings only. For source `pr`: sets the closed `planning_lane` value `adopt` (fixed at `pm_start`, outside the lane ratchet, like `land`), takes the pull request's changed files as `declared_files`, runs the collision detector over them (footprint disjointness like every source; a collision refuses with the existing reason), settings, and base stamp, and composes the finalize manifest with the shared resolver over those `declared_files` (no tasks).
|`init.recipe-selected` (source `recipe`, a doc-shaped lesson routed to `lesson-cleanup`, or the operator's `recipes.auto_route` with the top score at or above the compiled auto-route threshold `0.6`); `init.recipe-candidate` (the only recipe selection state: candidates at or above `0.35`, none auto-routed); `init.lesson-premise` (lesson premise obsolete); `init.sibling-collision`; `init.domain-choice` (ambiguous domain); `init.posture-choice`; `init.ready`.

|`phase-1-init`

|`use_recipe:<recipe_key>` (`next` for the top-scoring recipe, `alt` for the others), `skip_recipe` (`alt`).
|`use_recipe` -> `init.recipe-selected`; `skip_recipe` -> `init.ready` (standard light/deep routing).

|[[state-init.recipe-selected]]`init.recipe-selected`
|`phase-1-init`
|`auto`
|`init.classify` (source `recipe`, doc-shaped lesson, or auto-route); `init.recipe-candidate` (`use_recipe`).
|Binds the recipe; sets `confidence = 100`, `planning_lane = deep` (`track = complex`); renders `status.metadata.pr_title` from the recipe's `pr_title_template` with `recipe_params` (the `pr_title` producer of the recipe path, rule 8); runs the recipe's `target_harvester` (none for kind `request_scoped`, whose deliverables come from the pre-diagnosed request). Harvested targets are confirmed or pruned through `confirm_recipe_targets` in `outline.recipe-confirm`.
|`outline.recipe-entry` (phase `phase-3-outline`) by the recipe shortcut, skipping Phase 2 and the Phase 3 change-type and Q-Gate steps; an empty harvest ends the plan `completed` with `merge_outcome: no_pr` and fact `empty_harvest`, never an empty pull request _(transition path to the terminal to be specified)_.
|link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_source_contracts[Phase Workflows Specification, Plan Source Contracts (`recipe`)]; link:../domain-extensions/05-recipes-and-extension-points.adoc#_tier_1_init_routing_deterministic_deliverable_generation[Domain Extensions Specification, Tier-1 Init Routing items 1, 5, 7, 9]

|[[state-init.ready]]`init.ready`
|`phase-1-init`
|`auto`
|`init.classify`, the `init` question states (`init.lesson-premise`, `init.sibling-collision`, `init.domain-choice`, `init.posture-choice`), `init.recipe-candidate` (`skip_recipe`).
|Routes by `planning_lane` alone; the `deep` exit applies the clean-tree guard.
|`deep` -> `refine.baseline-reconcile`; `light` -> `init.light-gate`; `land` -> `land.worktree-init`; `adopt` (source `pr`) -> `finalize.adopt-pr` (phase `phase-6-finalize`).
|link:../phase-workflows/01-planning-phases-1-2.adoc#_lifecycle_topology_phases_14[Phase Workflows Specification, Lifecycle Topology]; link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Land Lane]; link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_source_contracts[Plan Source Contracts (`pr`)]

|[[state-init.light-gate]]`init.light-gate`
|`phase-1-init`
|`auto`
|`init.ready` (`light` plans only).
|`auto lane.budget-check` over the request's declared files: server budget trigger over declared files `A` and one-hop neighbours (cap `25`, band `8`), fail toward `deep` on unresolved neighbours, baseline probe; records `lane_budget` in `audit.jsonl`. The same primitive runs in `outline.light-regate`.
|Pass -> `outline.detect-change-type` (phase `phase-3-outline`, `phase_2_mode = collapsed_light`, `facts.light_read_set`); budget, `neighbours_indeterminate`, or `baseline_conflict` -> `refine.baseline-reconcile` (one-way ratchet to `deep`).
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#light-gate[Phase Workflows Specification, Light Gate]

=== Phase 2: `refine`

Deep-lane plans only (including a plan ratcheted from `light`).

[cols="2,1,1,2,3,2,2"]
|===
|State id |Phase value |Kind |Entered from |Offered links / outcomes |Exits to |Defined in

|[[state-refine.baseline-reconcile]]`refine.baseline-reconcile`
|`phase-2-refine`
|`auto`
|`init.ready` (`deep`); `init.light-gate` (escalation); `outline.light` (`escalate_to_deep`) and `outline.light-regate` (escalation), both with the phase set back to `phase-2-refine` and `phase_2_mode = full`.
|Non-mutating merge-conflict probe against upstream (only when a base branch is configured; native JGit `ResolveMerger` or CLI `git merge-tree`). Outcomes: `no_overlap`, `overlap_no_content_conflict` (`auto_reconcilable: true`), `overlap_with_content_conflict` (blocking Q-Gate findings).
|`refine.analyze` (every outcome; a content conflict carries its blocking findings into refinement).
|link:../phase-workflows/01-planning-phases-1-2.adoc#_phase_entry_baseline_reconciliation[Phase Workflows Specification, Phase Entry & Baseline Reconciliation]

|[[state-refine.analyze]]`refine.analyze`
|`phase-2-refine`
|`link`
|`refine.baseline-reconcile`; `refine.awaiting_answers` (the single re-dispatch).
|Refine sub-agent dispatch with `returned:<dispatch_id>`; `submit:refine` (`clarified_request`, `pr_title`, six dimension scores, `evidence_class`, `compatibility`, `simplicity`, per-claim hypothesis verdicts of an emitted plan, batched `refine_prompt` questions).
|Confidence at or above threshold -> `refine.qgate` (lesson-derived plans) or `refine.ready`; below threshold on the first pass, or a refuted hypothesis -> `refine.awaiting_answers`; a claim refuted again -> `refine.hypothesis-refuted`; below threshold on the second pass -> Phase 3 with `low_confidence_manual_review: true` _(via `refine.ready`, to be specified)_; missing submission -> the `dispatch_incomplete` condition on this state (xref:01-conventions-generic-conditions.adoc#condition-dispatch_incomplete[Condition dispatch incomplete]).
|link:../phase-workflows/01-planning-phases-1-2.adoc#_five_quality_dimensions_fixed_weight_confidence_aggregation[Phase Workflows Specification, Five Quality Dimensions]; link:../phase-workflows/01-planning-phases-1-2.adoc#_single_batch_clarification_re_dispatch_ceiling[Single-Batch Clarification & Re-Dispatch Ceiling]

|[[state-refine.awaiting_answers]]`refine.awaiting_answers`
|`phase-2-refine`
|`awaiting_user`
|`refine.analyze` (at most once).
|`answer_questions` or elicitation; at most 4 questions in one batch. `operator_answered` evidence requires an answered round of this state.
|`refine.analyze` (writes `## Clarifications` and `## Clarified Request`, increments `refine_redispatch_count`).
|link:../phase-workflows/01-planning-phases-1-2.adoc#_single_batch_clarification_re_dispatch_ceiling[Phase Workflows Specification, Single-Batch Clarification]; xref:01-conventions-generic-conditions.adoc#state-phase.awaiting_answers[Awaiting answers]

|[[state-refine.hypothesis-refuted]]`refine.hypothesis-refuted`
|`phase-2-refine`
|`link`
|`refine.analyze` (a hypothesis claim of an emitted plan refuted in the second pass).
|`escalate` (operator-authorizing: continue with a narrowed scope, _decision kind to be registered_); `abort` (rel `escalate`, the request `abort-plan`: abort for re-staging). On entry the server appends `hypothesis_refuted` to the epic inbox.
|Continue with narrowed scope (intent amendment) -> `refine.ready` _(to be specified)_; `abort-plan` `aborted` -> `plan.aborted`, `resumed` -> this state.
|link:../phase-workflows/01-planning-phases-1-2.adoc#_five_quality_dimensions_fixed_weight_confidence_aggregation[Phase Workflows Specification, Open Hypotheses of Emitted Plans]

|[[state-refine.qgate]]`refine.qgate`
|`phase-2-refine`
|`auto`
|`refine.analyze` (lesson-derived deep-lane plans only).
|Narrative-vs-code validation, at most 3 iterations, content-hash rerun gate; `stale` findings non-blocking, `invalid` blocking. Remediation link _(to be specified)_.
|Clean -> `refine.ready`; exhausted or unchanged -> `refine.qgate-exhausted`.
|link:../phase-workflows/03-q-gate-and-execute.adoc#_q_gate_validation_loop[Phase Workflows Specification, Q-Gate Validation Loop]

|[[state-refine.ready]]`refine.ready`
|`phase-2-refine`
|`auto`
|`refine.analyze`, `refine.qgate`, `refine.qgate-exhausted` (`force-gate`), `refine.hypothesis-refuted` (continue).
|Phase 2 exit guards: artifact gate (`## Clarified Request`, non-empty `pr_title`), Blocking Findings Guard, Clean Main Checkout Guard.
|`outline.detect-change-type` (phase `phase-3-outline`).
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#_planning_transition_guards_real_world_invariants[Phase Workflows Specification, Planning Transition Guards]

|link:../phase-workflows/03-q-gate-and-execute.adoc#_single_writer_heuristic_vs_judgment_fallback[Phase Workflows Specification, Judgment Fallback]

|[[state-outline.deep]]`outline.deep`
|`phase-3-outline`
|`link`
|`outline.detect-change-type`, `outline.classify-change-type` (deep lane); `outline.review` (revision); `outline.awaiting_answers`.
|Outline sub-agent dispatch with `returned:<dispatch_id>`; `submit:outline` (`outline:text[1..65536]`, batched `outline_prompt` questions); full discovery, ADR scan, consumer sweeps. The submit primitive validates the outline before accepting it (`OutlineValidator`: intent markers, six-bucket classifier, `Added dependencies`, change-type scope reconciliation; then the single domain narrowing pass, which may set `pr_title_stale`); a refusal is `invalid_link_args`, a `rejected` representation of this state.
|Accepted -> `outline.qgate` (or `outline.review` when the surgical bypass holds); open questions -> `outline.awaiting_answers`; missing submission -> the `dispatch_incomplete` condition on this state (xref:01-conventions-generic-conditions.adoc#condition-dispatch_incomplete[Condition dispatch incomplete]).

|[[state-outline.light]]`outline.light`
|`phase-3-outline`
|`link`
|`outline.detect-change-type`, `outline.classify-change-type` (light lane); `outline.light-regate` (pass, after an `outline.review` revision).
|One collapsed light envelope: `submit:outline` carrying `clarified_request`, `pr_title`, and `outline`, read bound `facts.light_read_set`; or `outcome = escalate_to_deep` with `escalation_trigger` (`premise`, `cross_module_ripple`, `public_symbol_deletion`). No Q-Gate. The submit primitive runs the widen-only domain merge and then validates as in `outline.deep`; a refusal is `invalid_link_args`.
|Accepted -> `outline.review` (records `phase-2-refine` done); `escalate_to_deep` -> `refine.baseline-reconcile`.
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#light-envelope[Phase Workflows Specification, Collapsed Light Envelope]; link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#_phase_3_outline_validation_rules_outline_review_gate[Phase 3 Validation Rules]

|[[state-outline.light-regate]]`outline.light-regate`
|`phase-3-outline`
|`auto`
|`outline.review` (change request on a `light` plan).
|`auto lane.budget-check` over the `Affected files` of the current `outline.md` (the light gate's budget trigger, neighbour resolution, and baseline probe; records `lane_budget`). No Phase 1 state is re-entered.
|Pass -> `outline.light` (re-dispatch with the new `facts.light_read_set`); budget, `neighbours_indeterminate`, or `baseline_conflict` -> `refine.baseline-reconcile` (one-way ratchet to `deep`).
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#light-gate[Phase Workflows Specification, Light Gate]

|[[state-outline.recipe-entry]]`outline.recipe-entry`
|`phase-3-outline`
|`auto`
|`init.recipe-selected` (recipe shortcut).
|Derives the outline deliverables from the harvest of the recipe's `target_harvester`, or from the pre-diagnosed request for a `request_scoped` recipe, and writes `outline.md`.
|`outline.recipe-confirm`.
|link:../domain-extensions/05-recipes-and-extension-points.adoc#_tier_1_init_routing_deterministic_deliverable_generation[Domain Extensions Specification, Tier-1 Init Routing]; link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_source_contracts[Phase Workflows Specification, Plan Source Contracts (`recipe`)]

|[[state-outline.recipe-confirm]]`outline.recipe-confirm`
|`phase-3-outline`
|`link`
|`outline.recipe-entry`.
|`confirm_recipe_targets` (`submit`): confirms or prunes the harvested targets and their deliverables.
|`outline.review`; zero targets after pruning end the plan `completed` with `merge_outcome: no_pr` and fact `empty_harvest` _(transition path to the terminal to be specified)_.
|link:../domain-extensions/05-recipes-and-extension-points.adoc#_tier_1_init_routing_deterministic_deliverable_generation[Domain Extensions Specification, Tier-1 Init Routing]

|[[state-outline.awaiting_answers]]`outline.awaiting_answers`
|`phase-3-outline`
|`awaiting_user`
|`outline.deep` or `outline.light` whose returned dispatch left `outline_prompt` questions unresolved.
|`answer_questions` or elicitation (Phase 3 design clarifications; routine dialogue). Answers that change intent are recorded in `amendments[]`.
|Back to the authoring state (`outline.deep` / `outline.light`) or on to `outline.qgate` / `outline.review` _(to be specified; no re-dispatch ceiling is specified for Phase 3)_.
|link:../dispatch-and-effort/03-escalation-roles-readers.adoc#_parent_session_aggregation_awaiting_answers[Dispatch & Effort Specification, Parent Session Aggregation]; link:../phase-workflows/01-planning-phases-1-2.adoc#_routine_user_interaction_vs_operator_authorizing_decisions[Phase Workflows Specification, Routine User Dialogue]

|[[state-outline.qgate]]`outline.qgate`
|`phase-3-outline`
|`auto`
|`outline.deep` (accepted submission, no surgical bypass).
|Q-Gate validators, at most 3 iterations (fixed `until_clean`; no `off` or `once` mode), content-hash rerun gate. Remediation link _(to be specified)_.
|Clean -> `outline.review`; exhausted or unchanged -> `outline.qgate-exhausted`.
|link:../phase-workflows/03-q-gate-and-execute.adoc#_q_gate_validation_loop[Phase Workflows Specification, Q-Gate Validation Loop]

|[[state-outline.review]]`outline.review`
|`phase-3-outline`
|`link`
|`outline.deep` (accepted, no Q-Gate), `outline.light` (accepted), `outline.qgate`, `outline.qgate-exhausted` (`force-gate`), `outline.recipe-confirm`.
|Operator-authorizing approval (elicitation or `pm-mcp operator decide`), never automatic (no continuation policy or configuration key approves an outline; a compiled invariant of the `outline` unit); `accept_nonblocking` (`alt`, `submit`, `rationale:text[1..2000]`); operator change request. `facts`: pending `3-outline` findings, `added_dependencies[]`. Persisted; survives `/clear`.
|Approval with no pending `3-outline` finding -> `plan.derive-tasks` (phase `phase-4-plan`); change request -> `outline.deep` (deep lane) or `outline.light-regate` (light lane), the feedback filed as `3-outline` Q-Gate findings; without elicitation, the `blocked` condition on this state (xref:01-conventions-generic-conditions.adoc#condition-blocked[Condition blocked]).
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#_4_persisted_outline_review_state_surviving_clear[Phase Workflows Specification, Persisted `outline.review` State]
