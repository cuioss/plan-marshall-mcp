[#state-catalogue-finalize-merge]
== Phase 6: `finalize` (Merge Path & Post-Run Band)

Continues xref:04-plan-finalize-terminal.adoc#state-catalogue-finalize[Phase 6: `finalize`] with the post-push ADR step (order `62`), the branch-cleanup step (order `70`), the post-run band (`900..999`), the landing (`1000`), and the archive (`1100`). The branch-cleanup step runs as the merge path `finalize.merge-gate` -> `finalize.merge-lease` -> `finalize.merge-sync` -> `finalize.merge-evidence-wait` / `finalize.merge-barrier` -> `finalize.merge-dispatch` -> `finalize.merge-queue-wait`. No merge-path state holds the merge lease while it waits or while a task of the plan runs; an unmerged plan leaves the path only through `finalize.hand-back`, and no link or waiver merges over a provider refusal. After the merge no fallback exists (link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#merge-path[Phase Workflows Specification, Merge Path]).

|[[state-finalize.merge-sync]]`finalize.merge-sync`
|`phase-6-finalize`
|`auto`
|`finalize.merge-lease` (`succeeded`), holding the lease.
|`merge.sync-base`: fetches the base and rebases the plan branch onto `origin/<base_branch>`, then pushes it with an explicit lease (the last recorded push), only when the derived fact `branch_up_to_date_required` holds (an `indeterminate` fact counts as holding) or the base changed a path of the plan's realized footprint since the merge base; a base that is already an ancestor of `HEAD` is never rebased. Independently of a rebase, it pushes with the explicit lease whenever the local `HEAD` differs from the last recorded push. A rebase re-stamps `main_sha`. Every outcome other than success releases the lease first; on `rejected_lease` the branch is reset to its pre-rebase `HEAD`. A failed fetch or a push failure other than a lease rejection is `sync_failed`, bounded by the compiled retry budget of the merge path.
|`replan` (before the rebase, `replan.detect` raised `merge_conflict` from a trial merge or `base_advanced`; the lease released) -> `finalize.replan`; `not_required` -> `finalize.merge-barrier`; `rebased`, `pushed` -> `finalize.merge-evidence-wait`; `conflict`, `rejected_lease` (the remote branch moved) -> `finalize.remediate-merge-conflict`; `sync_failed` (budget left) -> `finalize.merge-gate`; `retry_spent` -> `finalize.hand-back` (gap `cause: exhausted`, `budget: server_rule_retry`, link:../timeouts/01-job-budgets-and-waits.adoc#server-rule-retry[Timeouts & Budgets Specification, Server-Rule Retry Budget]).

|[[state-finalize.merge-dispatch]]`finalize.merge-dispatch`
|`phase-6-finalize`
|`auto`
|`finalize.merge-barrier` (`pass`). Pruned with reason `auto_merge_off` when the operator's `merge.auto_merge` is `false`, together with `finalize.merge-queue-wait` and `finalize.merge-queue-exit`.
|`merge.dispatch`: `ci.merge` (safe-merge with the `merge_method`) or, when the derived fact `merge_queue_enforced` holds, `ci.enqueue`, both bound to the expected head SHA, the `HEAD` the barrier evaluated. `merged` counts only from `ci.pr-observe`, an enqueue only from the observed `ci.queue-membership`. On `merged`: realized footprint capture, worktree removal with `worktree_path` cleared, branch removal per ref, lease released; for a `land` plan the `declared_files` tree at the capture snapshot is compared with the merged plan head (ignoring base-changed paths): equal removes the capture ref, otherwise `capture_ref_retained` is owed; squash-landed local commits on the main checkout's branch become a `cleanup` owed item naming the operator command (the main checkout is never moved). On `not_mergeable` and `enqueued_indeterminate` the lease is released. *Deliberate change vs. `plan-marshall`*: `plan-marshall` can merge with `--admin`.
|`merged` -> `finalize.next-step` (`completes default:branch-cleanup as done`); `enqueued`, `enqueued_indeterminate` -> `finalize.merge-queue-wait`; `head_moved` -> `finalize.merge-gate`; `not_mergeable{reason}` -> `finalize.merge-refused`.
|link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#_cross_plan_merge_mutex_fifo_admission_queue[Phase Workflows Specification, Cross-Plan Merge Mutex item 5]

|[[state-finalize.merge-refused]]`finalize.merge-refused`
|`phase-6-finalize`
|`auto`
|`finalize.merge-dispatch` (`not_mergeable`, lease released).
|`merge.route-refusal`: routes by `facts.reason`, a closed class: `conflict`, `behind`, `checks_pending`, `checks_failed`, `review_required`, `blocked`, `draft`, `method_not_allowed`, `unknown`. `behind` and `conflict` mark the derived fact `branch_up_to_date_required` stale, so the next `finalize.merge-sync` rebases; `checks_pending` and `checks_failed` re-enter the gate, whose evidence wait and barrier observe the checks. These re-entries are bounded by a compiled retry budget. `review_required`, `blocked`, `draft`, `method_not_allowed`, and `unknown` are a refusal by the provider's protection rules, which is not waivable and not retried. No link is offered.
|`re_enter` (`behind`, `conflict`, `checks_pending`, `checks_failed`, budget left) -> `finalize.merge-gate`; `provider_refused` (`review_required`, `blocked`, `draft`, `method_not_allowed`, `unknown`) and `retry_spent` (the retry budget spent) -> `finalize.hand-back` (gap `cause: provider_refused`).
|link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#_cross_plan_merge_mutex_fifo_admission_queue[Phase Workflows Specification, Cross-Plan Merge Mutex]

|[[state-finalize.merge-queue-wait]]`finalize.merge-queue-wait`
|`phase-6-finalize`
|`composite_job`
|`finalize.merge-dispatch` (`enqueued`, `enqueued_indeterminate`; lease released); `finalize.merge-queue-exit` (`resume_wait`).
|Waits for a terminal queue outcome: `merged`, `ejected`, `closed`, `timed_out`; `merged` only from `ci.pr-observe` or `ci.queue-membership`. The bound is stall-based: every observed progress (a change of queue position or entry state) restarts the clock, and `timed_out` is reached only after no progress for twice the queue's check-response timeout (from `merge_queue_enforced`), else the compiled fallback `3600` s. After `enqueued_indeterminate` the observation settles the wait. A constituent `killed`, `timed_out`, or `indeterminate` fate maps to `interrupted`. On `merged` the post-merge actions of `finalize.merge-dispatch` run.
|`merged` -> `finalize.next-step` (`completes default:branch-cleanup as done`); `ejected`, `closed`, `timed_out`, `interrupted`, `cancelled` -> `finalize.merge-queue-exit`.
|link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#_cross_plan_merge_mutex_fifo_admission_queue[Phase Workflows Specification, Cross-Plan Merge Mutex item 5]; link:../timeouts/01-job-budgets-and-waits.adoc#merge-queue-wait[Timeouts & Budgets Specification, Merge-Queue Landing Wait]

|[[state-finalize.merge-queue-exit]]`finalize.merge-queue-exit`
|`phase-6-finalize`
|`auto`
|`finalize.merge-queue-wait` (every outcome but `merged`).
|`merge.route-queue-exit`: routes by a fresh observation of the pull request and the queue, together with the exit outcome (`timed_out` recorded as `no_verdict`) and the ejection reason. An open pull request that is not queued re-enters the gate within the compiled retry budget; a pull request that is still queued resumes the wait within the restart budget of the evidence wait (default `2`). No link is offered.
|`re_enter` (open, not queued, budget left) -> `finalize.merge-gate`; `resume_wait` (still queued, budget left) -> `finalize.merge-queue-wait`; `closed` and `budget_spent` -> `finalize.hand-back` (a still-queued pull request owes `post_merge_cleanup`).
|link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#_cross_plan_merge_mutex_fifo_admission_queue[Phase Workflows Specification, Cross-Plan Merge Mutex]; link:../timeouts/01-job-budgets-and-waits.adoc#merge-queue-wait[Timeouts & Budgets Specification, Merge-Queue Landing Wait]

[#state-catalogue-post-run]
=== Post-Run Band, Landing & Archive

Every plan passes these states, whatever its outcome; after a fallback or an empty harvest the plan instance in force contains only them. Degraded inputs are recorded as `indeterminate`, a floor, or `unmeasured`, never refused; a store I/O failure of an `auto` post-run step is a transaction failure, not a workflow outcome. No post-run state takes a fallback: a task that cannot be done completes its step `skipped`.
