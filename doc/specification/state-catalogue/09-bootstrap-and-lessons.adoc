[#state-catalogue-bootstrap]
== Bootstrap of a Plan: `bootstrap-plan`
_See Requirement link:../../Requirements.adoc#PM-WF-1[PM-WF-1: Hypermedia State Representation (HATEOAS)]_

Every scope is created by the bootstrap of its kind; there is no creation tool. `pm-mcp enter` records a pending entry record (kind, the requested id, a free-text hint of the user's words) and prints its `entry_id` unless it names a live scope (link:../cli-and-security/01-cli-and-installer.adoc[CLI, Coordination & Security Specification, `pm-mcp enter`]). `bootstrap-plan.pmwf` and `bootstrap-epic.pmwf` are compiled-only entity units hosted by the workspace scope (`phase inherit`, phase value `workspace`): one instance per pending entry record, instance id = `entry_id`, state kept in the record, addressed with `pm_state` / `pm_do(plan_id: "NO_PLAN", entity: "<entry_id>")` (link:../mcp-tools/01-core-workflow-tools.adoc[MCP Tools Specification, Core Workflow Tools]). Nothing exists under `plans/` or `epics/` before the `create` link succeeds, so an abandoned or swept entry leaves no scope. Choosing what to work on is the user's intent relayed by the model: the bootstrap offers links, never question records, waits, or fallbacks (link:../phase-workflows/07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Phase Workflows Specification, Questions, Waivers & Operator Influence]). Each way to start is one source unit and one link; the model maps the user's words onto a link, and the server validates every argument. Every terminal deletes the pending record in the transaction that enters it; the pending-record sweep removes records that never reach one, and a later `pm_state` on that `entry_id` is refused `scope_not_found`.

[#state-catalogue-source]
=== Source Units

A source unit (`scope subworkflow`, compiled only, `phase inherit`) gathers and checks one source before any scope exists; its exit contract is `done {source record}` or `stepped_out` (the model's `step_out` of a resting link state, which the bootstrap routes back to its choice). External text (issue and pull request title and body) passes the deterministic level-1 validator of the server first and then the level-2 screener, one `batch-v1` batch per firing (link:../dispatch-and-effort/06-untrusted-text-screening.adoc#two-level-guard[Model Jobs & Effort Specification, Two-Level Guard for External Text]); lesson, recipe, local-changes, and epic-row content is the project's own and is validated only. A new way to start is one more source unit and one more `start.choose` link.

[#state-catalogue-bootstrap-epic]
== Bootstrap of an Epic: `bootstrap-epic`
_Implementation watch: link:../../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-38[PM-WATCH-DISP-38]_

`pm-mcp enter … epic [<epic_id>]` records a pending entry of kind `epic`. The unit gathers the epic's header and vision; its `create` link creates the epic scope in one transaction: the machine store `epics/<epic_id>/`, the session row, `status.json` at `epic.decompose`, `epic.json` (title, `parallelization_scope`, lifecycle), the ledger directory in the shared epic worktree, and the vision section of `spec.md`. An epic whose git-tracked ledger exists (`.marshall/orchestrator/<epic_id>/` with `epic.json`, read through the Epic Ledger Resolution Seam, link:../filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification, Shared Epic Worktree]) but has no machine scope (`epics/<epic_id>/` absent, for example after a clone on another machine) is adopted instead: the ledger is the durable truth, and the adoption creates only the machine scope from it and never rewrites it.

== Lesson Maintenance: `lessons` (workspace)

Declared in `lessons.pmwf` (`scope workspace`, compiled only), hosted by the workspace scope beside project setup and entered from its resting state `setup.completed` (`maintain_lessons`), to which it returns; the bootstrap's `maintain:lessons` hands the session over to it. The server computes the candidates, a model job judges them, and the server writes every change under the lesson lock. No plan is created.

|`reviewed` -> `lessons.done`; missing submission -> the `job_incomplete` condition (its `resume` stays offered on the workspace scope).

|`analyze` -> `lessons.analyze`; `finish` -> `setup.completed`.
