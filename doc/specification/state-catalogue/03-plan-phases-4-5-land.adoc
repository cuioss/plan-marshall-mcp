[#state-catalogue-execute]
== Phase 5: `execute`

[cols="2,1,1,2,3,2,2"]
|===
|State id |Phase value |Kind |Entered from |Offered links / outcomes |Exits to |Defined in

|[[state-execute.worktree-init]]`execute.worktree-init`
|`phase-5-execute`
|`auto`
|`plan.qgate`, `plan.qgate-exhausted` (`force-gate`).
|Creates the feature branch and the worktree `.marshall/local/worktrees/<plan_id>/`; records `worktree_path` in the same transaction.
|`execute.dispatch-ready`.
|link:../phase-workflows/03-q-gate-and-execute.adoc#_worktree_materialization_envelope_execution_loop[Phase Workflows Specification, Worktree Materialization]

|[[state-execute.dispatch-ready]]`execute.dispatch-ready`
|`phase-5-execute`
|`link`
|`execute.worktree-init`; `execute.chain-tail-commit` (next deliverable); `execute.deviation-review`; `execute.exit-barrier` (open tasks, runnable tasks remain); `execute.awaiting-infeasible-decision` (`remove-deliverable`); `finalize.ci-failed` and every other finalize `loop_back` (`allocated`); `finalize.allocate-after-extension` (`allocated`).
|`dispatch:envelope-M` paired with `returned:<dispatch_id>`; `redispatch:envelope-M` (rel `retry`, form `noop`) while that dispatch is `ALLOCATED` or `CLAIMED` (link:../dispatch-and-effort/02-dispatch-observability-and-spend.adoc#dispatch-recovery-links[Dispatch & Effort Specification, Dispatch Recovery Links]). Entity-scoped links of the envelope (`submit:TASK-NNN`, `deviate:TASK-NNN`, `infeasible:TASK-NNN`, `yield:envelope-M`, `escalate:TASK-NNN`) belong to `envelope.task.active`. Dependency-ordered dispatch.
|Chain tail verified -> `execute.chain-tail-commit`; batched deviations -> `execute.deviation-review`; a task question (`escalate:TASK-NNN`) raises the `blocked` condition on the envelope's entity scope, never a plan state (xref:01-conventions-generic-conditions.adoc#condition-blocked[Condition blocked]); missing submission -> the `dispatch_incomplete` condition on this state (xref:01-conventions-generic-conditions.adoc#condition-dispatch_incomplete[Condition dispatch incomplete]); all envelopes complete (or a relocation forces the whole-tree sweep) -> `execute.verify-sweep`; no runnable task and an open `infeasible` decision -> `execute.awaiting-infeasible-decision`. _(How entity-scope submits drive this plan state while other envelopes run is to be specified.)_
|link:../phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution]

|[[state-execute.chain-tail-commit]]`execute.chain-tail-commit`
|`phase-5-execute`
|`call`
|`execute.dispatch-ready` (the last task of a deliverable passed verification).
|`call git.commit_and_push (message_mode=auto_deliverable, push_mode=never)`, then the module-scoped build job running the configured per-deliverable verification verbs (default `compile` and `module-tests`) _(state of the build job to be specified)_.
|`committed_local` / `clean` and a passing module build -> `execute.dispatch-ready`; failed build or no verdict (`timed_out`, `killed`, `indeterminate`, `refused`, `failed_unparsed`) -> `execute.verification-feedback`; `aborted` -> `execute.commit-aborted` (xref:01-conventions-generic-conditions.adoc#state-phase.commit-aborted[Commit aborted]).
|link:../phase-workflows/03-q-gate-and-execute.adoc#_per_deliverable_chain_tail_commit_module_build_git_commit_and_push[Phase Workflows Specification, Per-Deliverable Chain-Tail Commit]; link:../workflow-dsl/06-reusable-sub-workflows.adoc#_call_site_reuse_matrix_across_workflows[Workflow DSL Specification, Call-Site Reuse Matrix]

|[[state-execute.deviation-review]]`execute.deviation-review`
|`phase-5-execute`
|`link`
|`execute.dispatch-ready` (batched `ScopeDeviationRequest` records); every finalize `loop_back` and `finalize.allocate-after-extension` (`footprint_review`: `realized − (declared ∪ approved_widening)` non-empty).
|Operator-authorizing, per deviation: `hold` (optional guidance), `accept` (mandatory `rationale`), `split` (lesson title); elicitation or `pm-mcp operator decide`.
|`execute.dispatch-ready` (for a loop-back, remediation allocation continues after the review); without elicitation, the `blocked` condition on this state (xref:01-conventions-generic-conditions.adoc#condition-blocked[Condition blocked]).
|link:../phase-workflows/03-q-gate-and-execute.adoc#_scope_deviation_contract[Phase Workflows Specification, Scope-Deviation Contract]

|[[state-execute.verify-sweep]]`execute.verify-sweep`
|`phase-5-execute`
|`job`
|`execute.dispatch-ready` (all envelopes complete); `execute.remediation-commit`; `execute.exit-barrier` (`stale` / `undecidable`).
|Runs `manifest.phase_5.verification_steps` (`module-tests`, `quality-gate`, `coverage`, `arch-gate`) with footprint-driven scope and the relocation override; a failing whole-tree gate is re-run on the merge base first.
|All green -> `execute.exit-barrier`; plan failures -> `execute.verification-feedback` (`triage_required`); red only through baseline diagnostics -> `execute.baseline-red`.
|link:../phase-workflows/03-q-gate-and-execute.adoc#_whole_tree_verification_gates_triage_required_routing[Phase Workflows Specification, Whole-Tree Verification Gates]

|[[state-execute.verification-feedback]]`execute.verification-feedback`
|`phase-5-execute`
|`link`
|`execute.verify-sweep`; `execute.chain-tail-commit` (module build failed or without verdict).
|`dispatch:verify-feedback` or inline `fix` links (diagnose against `verify_failure_scope`, apply the fix); `retry` after a no-verdict build. Failures are filed in `findings.jsonl`.
|Fix applied -> `execute.remediation-commit`; `retry` -> the failed build _(to be specified)_.
|link:../phase-workflows/03-q-gate-and-execute.adoc#_whole_tree_verification_gates_triage_required_routing[Phase Workflows Specification, `triage_required` Routing]

|[[state-execute.remediation-commit]]`execute.remediation-commit`
|`phase-5-execute`
|`call`
|`execute.verification-feedback`.
|`call git.commit_and_push (message_mode=interactive, push_mode=never)`: validates the Conventional Commit message, stamps `change-ledger.jsonl`.
|`committed_local` / `clean` -> `execute.verify-sweep`; `aborted` -> `execute.commit-aborted` (xref:01-conventions-generic-conditions.adoc#state-phase.commit-aborted[Commit aborted]).
|link:../workflow-dsl/06-reusable-sub-workflows.adoc#_call_site_reuse_matrix_across_workflows[Workflow DSL Specification, Call-Site Reuse Matrix]

|[[state-execute.baseline-red]]`execute.baseline-red`
|`phase-5-execute`
|`link`
|`execute.verify-sweep`.
|As xref:01-conventions-generic-conditions.adoc#state-phase.baseline-red[Baseline red].
|Accept -> the sweep continues to `execute.exit-barrier` _(to be specified)_; stop -> `plan.aborted`.
|link:../phase-workflows/03-q-gate-and-execute.adoc#_whole_tree_verification_gates_triage_required_routing[Phase Workflows Specification, Baseline-Red Gates]

|[[state-execute.exit-barrier]]`execute.exit-barrier`
|`phase-5-execute`
|`auto`
|`execute.verify-sweep` (all green).
|Dual gate evaluated together: pending-tasks and clean-tree gate (every task terminal with its disposition, empty porcelain) and worktree freshness gate (`fresh`, `exempt`, `stale`, `undecidable` with `stale_reason`).
|Pass -> `finalize.settle-commit` (phase `phase-6-finalize`); freshness `stale` / `undecidable` -> `execute.verify-sweep`; open tasks -> `execute.dispatch-ready` while runnable tasks remain, otherwise `execute.awaiting-infeasible-decision`; a dirty tree _(to be specified)_.
|link:../phase-workflows/03-q-gate-and-execute.adoc#_phase_5_exit_barrier_dual_freshness_pending_tasks_gates[Phase Workflows Specification, Phase 5 Exit Barrier]

|[[state-execute.awaiting-infeasible-decision]]`execute.awaiting-infeasible-decision`
|`phase-5-execute`
|`blocked`
|`execute.dispatch-ready` (no runnable task remains while the operator decision on an `infeasible` deliverable is open); `execute.exit-barrier` (open tasks, none runnable).
|`wait:decision:<decision_id>` only; never a link that changes a task or a deliverable.
|`remove-deliverable` -> `execute.dispatch-ready` or `execute.verify-sweep` _(to be specified)_; `loop-back-outline` -> phase `phase-3-outline` (`outline.deep` / `outline.light`, _to be specified_).
|link:../phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution items 3, 5]

[#state-catalogue-land]
== Land Lane: `land`

Plans started from `local_changes` only. The `land.*` states run in phase `phase-5-execute`.

[cols="2,1,1,2,3,2,2"]
|===
|State id |Phase value |Kind |Entered from |Offered links / outcomes |Exits to |Defined in

|[[state-land.worktree-init]]`land.worktree-init`
|`phase-5-execute`
|`auto`
|`init.ready` (`land`).
|Creates the plan's branch at the capture's snapshot commit (`refs/pm-mcp/captures/<plan_id>`) and its worktree `.marshall/local/worktrees/<plan_id>/`, records `worktree_path`; then restores the main checkout's captured paths (untracked ones included) to `HEAD` only where their content digest still equals the capture, lists the paths edited after the capture (left untouched) in `facts`, and re-records `entry_baseline` from the main checkout it leaves. Main's index and refs are never touched.
|`land.verify-sweep`.
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane item 3]

|[[state-land.verify-sweep]]`land.verify-sweep`
|`phase-5-execute`
|`job`
|`land.worktree-init`; `land.verification-feedback` (`recapture`: `recaptured`); `land.recapture` (`recaptured`); `land.exit-barrier` (freshness failure).
|Execute's exit verification over the captured footprint: `manifest.phase_5.verification_steps` with footprint-driven scope and relocation override, baseline-red separation, realized footprint equals the captured `declared_files`.
|Green -> `land.exit-barrier`; failures -> `land.verification-feedback`; baseline-only red _(to be specified: `land.baseline-red` or `execute.baseline-red`)_.
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane item 3]

|[[state-land.verification-feedback]]`land.verification-feedback`
|`phase-5-execute`
|`link`
|`land.verify-sweep`.
|Files the failures in `findings.jsonl`; offers `recapture` (`fix`, no free parameters, `do land.recapture-changes`) once the user has fixed the changes, `escalate` (decision kind `land-verification-failed`), and `abort` (rel `escalate`, the request `abort-plan`). Never `loop_back`, never tasks.
|`recapture`: `recaptured` -> `land.verify-sweep` (new `captured_changes`, `recapture_count` incremented), `no_local_changes` -> this state (refused); `land-verification-failed`: `recapture` -> `land.recapture`, `abort-plan` -> `plan.aborted`; `abort-plan`: `aborted` -> `plan.aborted`, `resumed` -> this state.
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane items 4, 5]; link:../workflow-dsl/02-units-jobs-decisions.adoc#decision-registry[Workflow DSL Specification, Decision Registry]

|[[state-land.recapture]]`land.recapture`
|`phase-5-execute`
|`auto`
|`land.verification-feedback` (`land-verification-failed`: `recapture`, the operator's approval).
|`auto land.recapture-changes`: the recapture of the `recapture` link, executed as the approved action (Rule 10): re-derives the footprint from the main checkout and carries the changes onto the plan's branch with the capture mechanic of `land.worktree-init` (a new snapshot commit, the capture ref moved to it).
|`recaptured` -> `land.verify-sweep`; `no_local_changes` -> `land.verification-feedback`.
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane item 5]; link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Static Verification Rule 10]

|[[state-land.exit-barrier]]`land.exit-barrier`
|`phase-5-execute`
|`auto`
|`land.verify-sweep` (green).
|The Phase 5 exit barrier with zero tasks; clean-tree and freshness gates unchanged.
|Pass -> `finalize.settle-commit` (phase `phase-6-finalize`); fail -> `land.verify-sweep` _(to be specified)_.
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane item 3]
