== Conventions
_See Requirement link:../../Requirements.adoc#PM-WF-1[PM-WF-1: Hypermedia State Representation (HATEOAS)]_

=== State Identifier Grammar

* *Form*: A state identifier is `<unit>.<name>`: the workflow unit it belongs to, a dot, and the state name. Both parts follow the DSL `identifier` production (lowercase letter first, then lowercase letters, digits, `_`, `-`; link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification, EBNF]). State names are kebab-case (`finalize.concurrent-wait`). The dialogue name `awaiting_answers` keeps its established snake-case form. `awaiting_user` is a state kind (<<_state_kinds>>), never part of a state identifier: a question state is named by its question (`init.sibling-collision`).
* *Units*: The unit of a plan-workflow state is its phase file (`init`, `refine`, `outline`, `plan`, `execute`, `land`, `finalize`, link:../workflow-dsl/02-units-jobs-decisions.adoc#workflow-definition-units[Workflow DSL Specification, Workflow Definition Units]); of a sub-workflow state the sub-workflow's family prefix (`git` for `git.commit_and_push`; `remediation-<class>` for the remediation unit `remediation.<policy>`, for example `remediation-ci` for `remediation.ci-failure`, xref:08-remediation-units.adoc#state-catalogue-remediation[Remediation Units]; the unit's own name for a source unit, for example `source-issue`, xref:09-bootstrap-and-lessons.adoc#state-catalogue-source[Source Units], and for the lesson maintenance unit `lessons`); of every other top-level workflow its own prefix (`setup` for `project-setup.pmwf`, `epic` for `epic.pmwf`); of an entity state its entity unit (`envelope`, `entity`, `entity-multi`, and `start` for `bootstrap-plan`, `start-epic` for `bootstrap-epic`, xref:09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap[Bootstrap]); of a state of the task-protocol unit `worker-task` the prefix `task` (xref:10-entity-units.adoc#state-catalogue-worker-task[Task Protocol Unit]).
* *Exceptions*: The plan's non-abort terminal states are the bare plan outcome names `completed` (plan `outcome` `merged`, or `no_change` for an empty harvest; the declared outcome id `merged` of the terminal is nominal), `handed_back`, and `returned` (`PM-WF-1` admits both bare and phase-qualified terminal identifiers). The plan's abort terminal `plan.aborted` and its fallback state `plan.return` carry the scope type as prefix, not the Phase 4 unit `plan`, and are declared in `finalize.pmwf` like the terminals (link:../workflow-dsl/03-reference-excerpt.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Workflow DSL Specification, `finalize.pmwf` Excerpt]); the epic's abort terminal is `epic.aborted`. Entity states may carry a third segment (`envelope.task.active`), and so does the question state of a task's `ask`, named by the asking state and `.asked` (`execute.infeasible-review.asked`); no other state does.
* *Anchors*: Every catalogued state carries the anchor `state-<state id>` (for example `link:04-plan-finalize-terminal.adoc#state-finalize.hand-back[finalize.hand-back]`); a generic state `<phase>.x` carries `state-phase.x`, a generic remediation state `remediation-<class>.x` carries `state-remediation.x`. A condition overlay carries `condition-<kind>` (for example `link:01-conventions-generic-conditions.adoc#condition-footprint_violation[footprint_violation]`); a condition that covers a generic state also carries that state's anchor on its row. Each unit table carries the anchor named in its heading.
* *Not states*: Primitive identifiers share the dotted form (`primitive_id = identifier "." identifier`) but are never states: `review.check-structural-caps`, `finalize.watch-ci-and-bots`, `finalize.retry-emit-landing`, `finalize.spend-ratio`, `finalize.landing-status`, `finalize.wait-status`, `execute.evaluate-envelope-return` (the return-evaluation primitive of the envelope task), `plan.allocate-remediation-tasks`, `findings.triage`, `lane.budget-check`, `merge.gate-entry`, `merge.sync-base`, `merge.evaluate-barrier`, `merge.dispatch`, `waiver.lookup`, `start.create-scope`, the remediation primitives (`remediation.check-budgets`, `remediation.gather-<class>-evidence`, `remediation.request-waiver`, `remediation.await-waiver`, `remediation.offer-actions`, `remediation.conservative-retry`, `remediation.rerun-checks`, `remediation.rescan`, `remediation.retrigger-bots`, `remediation.rerun-build`, `remediation.continue-integration`), the epic primitives (`epic.next-work`, `epic.pending-messages`, `epic.unanalyzed-landings`, `epic.stage-plan`, `epic.ingest-message`, `epic.land-ledger`, `epic.archive-ledger`), `git.pre-commit-verify-freshness`, `git.push-barrier-decision`, `git.branch-sync-state`, `git.rebase-onto-upstream`, `git.rebase-continue`, `build.enqueue-verification`, `build.verify-worktree`, and the other `do`, `auto`, `job`, `facts`, and `predicate:` targets of the DSL excerpts. Where a state and its primitive share a name (`git.inspect-worktree`, `git.detect-artifacts`, `git.resolve-message`, `git.stage-and-commit`, `git.evaluate-push-policy`, `finalize.adopt-pr`, `finalize.restart-watch`, `finalize.route-push`, `finalize.hand-back`, `finalize.archive-plan`, `plan.return`, `outline.assume-change-type`, `git.template-message`, `finalize.adopt-blocked`, `finalize.merge-lease-interrupted`, `finalize.archive-unobserved`, and every router state such as `outline.route-rework`), the catalogue row is the state. Configuration keys (`workflow.plan.phase-1-init.minimum_lane`), file names (`outline.md`, `init.pmwf`), and role names (`implement`, `triage-ci`) are not states either.
* *Other status vocabularies*: The following closed vocabularies are record statuses, not workflow states, and are defined where their record is defined: task statuses of plan tasks (`pending` .. `removed`, link:../store-schemas/06-task-references-manifest.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]), the worker states (`waiting` .. `ended`) and the task outcomes (`submitted`, `asked`, `infeasible`, `lost`) of a queue task (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]), job record statuses (a queue task waiting for a worker is `queued`) and job fates (`PM-EXEC-4`, link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]), per-bot participation states and `bot_status` / `ci_status` / `analysis_status` (link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations]), the epic queue row vocabulary (link:../model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]), question record closures (`answered`, `assumed`, `cancelled`, link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]), waiver request outcomes, and finding statuses.

=== State Kinds

Every state has exactly one kind. The first five follow the DSL `state_body` alternatives; `awaiting_user` is derived from the AST (a state whose body starts with `question <class>`); `overlay` is the kind of a condition, which is not a state. `StateCatalogueDriftTest` derives every kind from the AST.

The server drives every plan and epic. A plan or epic state is server logic (`auto`, `job`, `composite_job`, `call`), a task of a role (`job llm`), or a question state; a plan or epic representation is a view whose `links` list is empty except for the answer links of open question records. The kind `link` exists only where a model acts on links: the states of the plan and epic bootstraps, their source units, the project setup, and the lesson maintenance, which the entry session drives, and the entity states of a task, which its worker follows.

[cols="1,4"]
|===
|Kind |Meaning

|`auto`
|Runs one primitive in the same transaction (`auto` clause) and follows its outcome; never a resting state, except `epic.active`, whose outcome `idle` lets the epic rest until the next epic event re-evaluates it.

|`link`
|Offers declared links (`link` clauses) and rests until the model follows one: on an entity state of a task, its worker; on a state the entry session drives, the session. Every resting `link` state of a sub-workflow the entry session drives (a source unit, `lessons`) also offers the implicit `step_out (reason: text[1..2000])` (<<exits-and-fallbacks>>).

|`job`
|Runs one asynchronous job (`job` clause) and rests until it settles; its completion is an engine event, never a link a model follows, and its outcomes are exactly the closed job outcome set of `PM-EXEC-4`, including `cancelled` (a cancel by the server or the operator). A *model state* (`job llm <entity_kind> role <role> [each <primitive_id>]`, link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Model Job States]) is the exception: entering it creates one queue task for the named role, run through the task-protocol unit `worker-task` (xref:10-entity-units.adoc#state-catalogue-worker-task[Task Protocol Unit]) and served to a worker of that role, which works on the task's entity unit; the state's outcomes are those of the entity kind's return-evaluation primitive over the persisted records, plus the reserved outcome `lost`. With `each <primitive_id>` it creates one task per element of a server-computed list, each with its own entity, and completes when every entity has its required submission (`setup.enrich-architecture`, the screener states). A state may declare `consult role <role>`, which offers its task's worker one `consult:<role>` link (link:../model-work/05-consultation.adoc[Model Work Specification, Consultation]). The closed task outcomes route as follows: `submitted`, `asked`, and `infeasible` take the return evaluation, whose outcomes include the state's question state `<state>.asked` (for `asked`, only on a state that declares `ask`) and the infeasible exit the row names (link:../model-work/09-completion-usage-and-spend.adoc#return-evaluation[Model Work Specification, Return Evaluation]). An attempt that ends without the required submission is offered again within the state's self-remedy budget (`job_incomplete`, <<condition-job_incomplete>>). A task closes `lost` when its re-offers are spent or when it is closed without an attempt because its role is undefined, unqualified (`PM-WORK-6`), or unavailable; the state routes `lost` to its conservative fallback, recorded with the task's reason (link:../model-work/01-roles-and-configuration.adoc#conservative-fallback[Model Work Specification, Conservative Fallback]). A row names the fallback it takes; a plan-scope state whose row names none takes the fallback of the position (<<exits-and-fallbacks>>). The screener (`job llm screen role screener each screen.batch-parts`) has no entity: its evaluation validates the structured `screen-verdict` output of every batch part, fail-closed, with the outcomes `clean` and `suspicious`.

|`composite_job`
|Runs several jobs, or one observation with domain outcomes, as one composite wait (`composite_job` clause) whose identifier equals the state identifier; its completion is an engine event. Its primitive declares its own closed outcomes and how a constituent `killed`, `timed_out`, or `indeterminate` fate maps to them.

|`call`
|Invokes a sub-workflow (`call` clause); never a resting state itself. The call makes the sub-workflow's first state current, and the representation shows the call path. The call site routes every outcome of the sub-workflow's exit contract: `done` with a typed result record, or the domain outcomes of a remediation unit, and the control outcome `stepped_out` where the unit can return it (link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Rule 6]).

|`awaiting_user`
|A question state: it waits on open question records (link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]; link:../phase-workflows/07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Phase Workflows Specification, Questions, Waivers & Operator Influence]). A record is raised by the state's primitive (server-owned options), by a task's `ask` link, or by the `questions` of an authoring submit. Every content question of a plan or epic is delivered through the web app, which notifies the paired devices, and is shown to the entry session while one is open as the answer link `answer:<question_id>` of the scope's representation; MCP elicitation carries only the project setup's questions and the bootstraps' choices, which are links, not question records (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Envelopes, Questions & Deadlines]). The first valid answer wins and is recorded with its channel (`web`, `session`, `elicitation`, `model`, `assumption`). The awaited events are `QUESTION_ANSWER` and `TIME`: the server owns the deadline (`questions.wait_seconds`, none in mode `operator`) and on expiry records the compiled fallback of the question class (`channel: assumption`) and routes it like an answer, without a model call. Every resolution enters one target: a re-entrant `auto` state that reads the answer and decides (`init.classify`, `outline.route-review`, `setup.probe-merge-queue`), or the single continuation of the state; an `ask` question state returns to its asking state, whose next task shows the answer, or its expiry, in `facts`. The states of this kind are closed: `init.sibling-collision`, `init.domain-choice`, `init.recipe-candidate`, `refine.awaiting_answers`, `outline.awaiting_answers`, `outline.review`, `execute.task-question`, `execute.infeasible-review.asked`, `setup.merge-queue`, `setup.reseed-build-map`, `setup.offer-new-steps`. A new question state is catalogued before any document uses it.

|`overlay`
|Not a state: an engine-owned condition recorded on the scope (`pending_condition` in `mcp/status.json`) while the current state and `call_stack` stay unchanged. While it is set, the current state's representation keeps `state` and names the condition in the field `condition`. Conditions are catalogued in <<state-catalogue-conditions>>, never in a state table, and are never declared in a DSL unit (link:../workflow-dsl/04-ast-node-model.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]).

|`terminal`
|No outgoing transition; `links[0]`. Every terminal state declares `terminal <outcome_id> <outcome_class>` (link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification, EBNF]); a sub-workflow terminal state's outcome is the one returned to its caller. The plan's terminals are `completed`, `handed_back`, and `returned`, each entered only from `finalize.archive-plan` after the post-run band, and `plan.aborted` (class `failure`), entered only by the operator's `abort`, `delete-plan`, or the `abort` resolution of an integrity breach. The epic's terminals are `epic.archived` and `epic.aborted`. The workspace scope has no terminal state (xref:06-setup-epic-other.adoc#state-catalogue-setup[Project Setup: `setup` (workspace)]).
|===

[#exits-and-fallbacks]
=== Exits, Step-Outs & Fallbacks

No state waits for an operator decision or for a session (link:../phase-workflows/01-planning-phases-1-2.adoc#plan-outcomes[Phase Workflows Specification, Plan Outcomes, Fallback Routes & Remediation Policies]). Every blocking situation has a bounded self-remedy and then a defined fallback:

* *Task outcomes*: No task ends a plan and no plan or epic state offers a `hand_back` or `step_out` link. A task ends only in its closed outcomes; a plan leaves its course early only through a server rule (a spent budget, a server step-out, an expired question, a task closed `lost`) or through a closed decision a task submits where its state offers one (`return` of `refine.hypothesis-refuted`, `hand_back` of `execute.infeasible-review`). A task that ends `infeasible` or closes `lost` takes the exit its row names, by default the fallback of the position.
* *Fallback of the position*: `plan.return` in Phases 1–4 (which forwards a plan branch with commits beyond the base to `finalize.hand-back`), `finalize.hand-back` in Phase 5, the land lane, and Phase 6 before the merge. After the merge no fallback exists: a failing post-merge step is retried within its budget and otherwise completes `failed` with an owed item, and a post-run task that cannot be done completes its step `skipped`. The epic and the workspace scopes have no fallback.
* *`step_out`*: Inside a sub-workflow of a plan or epic only the server steps out: `stepped_out {by: server, cause, reason}` when an attempt cap or a bounded retry of the unit is spent (`git.stepped-out`); the caller routes it once, to a fallback state or to its own recovery state. The implicit `step_out (reason: text[1..2000])` link exists only on the resting `link` states of a sub-workflow the entry session drives (the source units, `lessons`): it unwinds one frame and returns `stepped_out {by: model, cause: step_out, reason}`. A server step-out of cause `condition` (a spent condition budget) unwinds every frame at once to the fallback of the plan-scope position, and no recovery state of a caller routes it (<<state-catalogue-conditions>>). An interrupted rebase is aborted by the server before the frame unwinds. A step-out consumes no budget and writes no waiver.
* *Fallback states*: `plan.return` and `finalize.hand-back` (xref:04-plan-finalize-terminal.adoc#state-catalogue-fallback[Plan Fallbacks & Terminal States]) compose a post-run-only plan instance version, in force from the transition that enters them for the rest of their chain, and continue into the post-run band; the transaction entering them, or `plan.aborted`, records every begun, unsettled step `failed`.
* *Operator influence*: Waivers (`pm-operator waive` / `unwaive`) are records read at gate evaluation and by the waiver wait of a remediation unit; `pm-operator abort` and `delete-plan` are engine-owned scope-wide transitions into `plan.aborted` / `epic.aborted` in the next transaction. None is a DSL transition of a catalogued state.

=== Generic Per-Phase States

A generic state is written `<phase>.x` and stands for one concrete state per unit in which it occurs: `<phase>` is replaced by the unit prefix (`refine.awaiting_answers`, `execute.remediate-build`). A generic state is defined once in <<state-catalogue-generic>>, including its per-unit exits; its expansion table lists the units where it occurs. A unit table repeats a concrete expansion only where that expansion has behaviour beyond the generic definition (`refine.awaiting_answers`, `outline.awaiting_answers`). A generic state is a real state that a DSL transition targets; what the engine raises on any state of any unit (an integrity breach, a footprint violation, an incomplete task, configuration drift, an unmet precondition, a guard that could not be evaluated) is a condition overlay (<<state-catalogue-conditions>>), not a generic state. `*.x` in other documents means the same as `<phase>.x`.

[#state-catalogue-conditions]
== Conditions (Overlays)

A condition is raised by the engine, not by a DSL transition, on whatever state the scope is in, in any unit, including a sub-workflow state and an `auto` state whose primitive raised it. It is recorded in `mcp/status.json` as `pending_condition` (`kind`, `facts`, `raised_at`, the self-remedy attempts; link:../store-schemas/02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Store Schemas Specification, Workflow State Store]) while `state`, `phase`, and `call_stack` stay unchanged. While it is set, the representation keeps `state` as the current state id, names the condition in the field `condition` (link:../hypermedia-format/01-representation-and-link-forms.adoc#canonical-top-level-fields[Hypermedia Format Specification, Canonical Top-Level Fields]), and carries the condition's `facts`; no task of the current state is served. A scope carries at most one condition. Conditions are never declared in a DSL unit and are never a transition target (link:../workflow-dsl/04-ast-node-model.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]).

*Bounded self-remedy*: Every condition except `integrity_breach` runs its self-remedy without a session: the server retries where a retry can clear it (after the compiled condition retry delay), and where clearing it needs work, it creates a task of the role whose work raised it. Each attempt counts against a compiled budget of `3` attempts per condition instance (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]); the operator may remove the cause at any time, and the next attempt observes it. On a plan scope a spent budget takes the fallback of the current position (<<exits-and-fallbacks>>) with the condition recorded as the gap (`cause: condition`); inside a sub-workflow the engine steps out of every frame at once (`stepped_out {by: server, cause: condition}`) to that fallback, and no caller's recovery state routes it. Where the fallback itself lacks what is missing (no push credential), `handed_back` degrades to the local branch with the gap stated in the landing record. On the epic and the workspace scopes, which have no fallback, the server retries continue without a budget at the condition retry delay; on the workspace scope the entry session may also follow the condition's `retry` link. A task's re-offers are bounded on every scope (`job_incomplete`).

|[[condition-integrity_breach]]`integrity_breach`
|`kind: store_tampered`: a digest mismatch of a plan, epic, workspace, or lesson store decided by a locked reader after journal recovery (that scope pauses). `kind: enrolment_tampered`: an enrolment file of the project whose HMAC sidecar does not verify (every running plan of the project pauses; a tampered `harnesses.json` pauses nothing and raises `precondition_unmet` with reason `harness_tampered` instead). `facts`: `kind`, `store`, `recorded_digest`, `current_digest`; `facts.operator_command` names `pm-operator accept-edit` and `pm-operator abort`. Replaces any other condition of the scope.
|None: every `pm_do` is rejected with `integrity_paused`, and no task of the scope is offered. Unbounded and without fallback; the deadlines of a pending question record or waiver request are held until the pause ends.

Or `pm-operator abort`.
|`accept-edit`: the current state continues; state and `call_stack` are untouched. `abort`: `plan.aborted` / `epic.aborted`.

|[[condition-precondition_unmet]]`precondition_unmet`
|An operator-side precondition of the current step fails, with `facts.reason`: `credential_missing`, `credential_check_failed`, `credentials_file_insecure` (`PM-CRED-3`, `PM-CRED-4`); `config_changed` (the `.marshall/config/` Recovery Guard of a planning transition: a team file or workflow unit changed since `entry_baseline`); `ledger_unreadable` (a ledger read of an epic state: the unreadable ledger files or rows and the parse diagnostic); `format_outdated`, `format_newer` (a scope store written by another binary version, link:../store-schemas/01-format-and-session-log.adoc[Store Schemas Specification, Format Versioning]); `grant_missing` (an access to another project without the operator's grant record, link:../store-schemas/15-screening-and-grants.adoc#grant-record[Store Schemas Specification, Grant Record]); `push_remote_indeterminate` (the derived fact `push_remote` of `git.evaluate-push-policy` could not be derived); `harness_capability_missing` (a worker whose role needs a capability its harness does not declare, with `facts.missing`), `harness_unsupported` (an unenrolled harness or a version outside the profile's supported range: the launch refusals `harness_not_enrolled`, `harness_version_unsupported`); `harness_tampered` (the harness enrolment store `harnesses.json` fails its HMAC check: the worker launch is refused with a `security` audit record `enrolment_tampered`, nothing is paused, and `facts.operator_command` names `pm-operator enrol-harness <client>`, which rewrites the file and its sidecar after showing path, version, and digest); `prompt_composition_failed` (the worker's launch prompt could not be composed). The step that met it is not executed.
|Server `retry`: the interrupted check runs again after the condition retry delay. `facts.operator_command` names the repair (`pm-operator credentials …`, committing or restoring the configuration file, `pm-operator config --project <project_id>`, `pm-operator grant-access <plan> <project> read\|read-write --reason …`, `pm-operator enrol-harness <client>`, or an edit of the role artifact); never a model-relayed answer.
|A retry whose check passes; a failing check keeps the condition with refreshed `facts` and counts one attempt.
|Clearing continues the interrupted step. A spent budget takes the fallback (plan scope). On the epic scope the retries continue; an unreadable ledger ends only when it reads again or by `pm-operator abort epic`. Setup failures of the workspace scope enter `setup.needs-repair` instead.

|[[condition-footprint_violation]][[state-phase.footprint-violation]]`footprint_violation`
|A boundary breach, never a change inside the plan's worktree beyond the declared footprint (that is recorded as an unplanned change): the footprint check that `git.stage-and-commit` runs first for every caller (a path outside the plan's worktree, a pinned build file or protected path, a main-checkout change since `entry_baseline`); the same check on a task `submit:TASK-*` link; the Clean Main Checkout Guard of any plan transition. The link or primitive that met the violation is not executed; no commit is made. Not waivable.
|For offending paths inside the plan's worktree: a `fix` task of the plan's writer role `implement`, whose `facts` carry the offending files, reverts them and submits. A main-checkout change since `entry_baseline` is never the plan's to revert (`baseline_dirty`): the server re-checks it on each attempt, and the user or the operator removes the cause.
|An attempt after which the footprint check passes; a failing check keeps the condition with refreshed `facts`.
|Clearing continues the interrupted step. A spent budget takes the fallback.
|link:../workflow-dsl/06-reusable-sub-workflows.adoc#_six_stage_execution_contract_of_git_commit_and_push[Workflow DSL Specification, Stage 4]; link:../workflow-dsl/05-primitives.adoc#independent-transition-validation[Transition Validation item 6]; link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#_planning_transition_guards_real_world_invariants[Phase Workflows Specification, Clean Main Checkout Guard]; link:../mcp-tools/04-errors-and-testing.adoc#_normative_classification_matrix[MCP Tools Specification, Classification Matrix]

|[[condition-job_incomplete]]`job_incomplete`
|An attempt of a task ended without the submission its entity requires (for an entity of the multi-submit unit: its closing submit): its worker was lost or ended while holding the task (`PM-WORK-3`); the server observes the end itself. On a fan-out state (`each`) the condition covers every unfinished entity. `facts`: the attempt's end and the worker's job fate, the entity's recorded progress (on a fan-out state per unfinished entity).
|The server offers the task again as a new attempt, to exactly one worker per attempt, within the re-offer budget (link:../model-work/02-task-protocol.adoc#re-offer[Model Work Specification, Re-Offer]): the lease is released, the successor starts with an empty context, and a multi-submit entity continues from what its repeatable submits persisted; on a fan-out state only the unfinished entities are offered again. No link is offered.
|An attempt whose entity records its required submission.
|The return-evaluation outcome is taken. A spent budget closes the task `lost`, which the state routes to its conservative fallback (<<_state_kinds>>); on every scope, the epic and the workspace included, the `lost` route is the state's declared one.
|link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Model Job States]; link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]

|[[condition-config_drift]][[state-phase.config-drift]]`config_drift`
|A phase entry in Phases 2–6 whose current `config_hash` differs from the one in the header of the plan instance version in force and whose candidate instance version differs in effect (the phase handshake, not a DSL transition).
|Server decision in the raising transaction: `adopt` when the candidate contains the current state and every `call_stack` state (the candidate becomes a new instance version, composition event `config_adopted`), otherwise `keep` (the plan continues on the version in force). `facts`: the instance diff and the decision.
|The decision, recorded in `audit.jsonl` and `instance/composition.jsonl`.
|The interrupted phase entry continues in the current state on the adopted or the kept version.
|link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#_planning_transition_guards_real_world_invariants[Phase Workflows Specification, Outside-World Invariants]; link:../store-schemas/14-plan-instance-waivers-questions.adoc#plan-instance[Store Schemas Specification, Plan Instance]

|[[condition-guard_indeterminate]]`guard_indeterminate`
|A guard of the current state (built-in, `predicate:`, or one reading a `depends_on_config` key) evaluated to `COULD_NOT_EVALUATE(reason)`; the result is never folded into held or not held.
|Server `retry`: the state's guards are evaluated again after the condition retry delay. `facts`: the guard, the transition it gates, the reason.
|A retry in which every guard of the state evaluates to `HELD` or `NOT_HELD`; a repeated `COULD_NOT_EVALUATE` keeps the condition with refreshed `facts`.
|Clearing continues the current state with the transitions whose guards hold. A spent budget takes the fallback.
