== Conventions
_See Requirement link:../../Requirements.adoc#PM-WF-1[PM-WF-1: Hypermedia State Representation (HATEOAS)]_

=== State Identifier Grammar

* *Form*: A state identifier is `<unit>.<name>`: the workflow unit it belongs to, a dot, and the state name. Both parts follow the DSL `identifier` production (lowercase letter first, then lowercase letters, digits, `_`, `-`; link:../workflow-dsl/01-module-boundary-and-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification, EBNF]). State names are kebab-case (`finalize.concurrent-wait`). The dialogue name `awaiting_answers` keeps its established snake-case form; no other name uses `_`. `awaiting_user` is a state kind (<<_state_kinds>>), never part of a state identifier: a routine question state is named by its question (`init.sibling-collision`). An identifier of the documents that is not a catalogue state is listed only in xref:06-setup-epic-other.adoc#state-catalogue-migrated[Migrated and Non-Conforming Identifiers].
* *Units*: The unit of a plan-workflow state is its phase file (`init`, `refine`, `outline`, `plan`, `execute`, `land`, `finalize`, link:../workflow-dsl/02-units-jobs-decisions.adoc#workflow-definition-units[Workflow DSL Specification, Workflow Definition Units]); of a sub-workflow state the sub-workflow's family prefix (`git`); of every other top-level workflow its own prefix (`setup` for `project-setup.pmwf`, `epic` for `epic.pmwf`); of an entity state its entity kind (`envelope`).
* *Exceptions*: The plan's successful terminal state is the bare identifier `completed` (`PM-WF-1` admits both bare and phase-qualified terminal identifiers). The plan's single abort terminal is `plan.aborted`: its prefix names the scope type, not the Phase 4 unit `plan`, and it is declared in `finalize.pmwf` (link:../workflow-dsl/03-reference-excerpt.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Workflow DSL Specification, `finalize.pmwf` Excerpt]); the epic's is `epic.aborted`. Entity states may carry a third segment (`envelope.task.active`); no other state does.
* *Anchors*: Every catalogued state carries the anchor `state-<state id>` (for example `link:04-plan-finalize-terminal.adoc#state-finalize.ci-failed[finalize.ci-failed]`); a generic state `<phase>.x` carries `state-phase.x`. A condition overlay carries `condition-<kind>` (for example `link:01-conventions-generic-conditions.adoc#condition-footprint_violation[footprint_violation]`); the anchors of the former generic states it replaces (`state-phase.blocked`, `state-phase.footprint-violation`, `state-phase.dispatch-incomplete`, `state-phase.config-drift`) stay on its row. Each unit table carries the anchor named in its heading.
* *Not states*: Primitive identifiers share the dotted form (`primitive_id = identifier "." identifier`) but are never states: `review.check-structural-caps`, `finalize.watch-ci-and-bots`, `finalize.record-in-branch-fix`, `finalize.restart-watch`, `finalize.retry-emit-landing`, `finalize.spend-ratio`, `finalize.landing-status`, `finalize.wait-status`, `plan.allocate-remediation-tasks`, `plan.loop-status`, `plan.resume-aborted-call`, `findings.triage`, `lane.budget-check`, `land.recapture-changes`, the epic primitives (`epic.inspect-ledger`, `epic.stage-plan`, `epic.ingest-message`, `epic.enqueue-landing`, `epic.land-ledger`, `epic.archive-ledger`), `git.pre-commit-verify-freshness`, `git.push-barrier-decision`, `git.branch-sync-state`, `build.verify-worktree`, and the other `do`, `auto`, `job`, `facts`, and `predicate:` targets of the DSL excerpts. Where a state and its primitive share a name (`git.inspect-worktree`, `git.detect-artifacts`, `git.resolve-message`, `git.stage-and-commit`, `git.evaluate-push-policy`, `finalize.retry-landing-delivery`, `finalize.close-pr-and-archive`, `finalize.hand-back-and-archive`, `finalize.adopt-pr`, `finalize.archive-plan`, `finalize.wind-down`), the catalogue row is the state. Configuration keys (`workflow.plan.phase-1-init.minimum_lane`), file names (`outline.md`, `init.pmwf`), and effort roles (`plan.<phase>.effort`) are not states either.
* *Other status vocabularies*: The following closed vocabularies are record statuses, not workflow states, and are defined where their record is defined: task statuses (`pending` .. `removed`, link:../store-schemas/06-task-references-manifest.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]), dispatch lifecycle states (`ALLOCATED`, `CLAIMED`, `RETURNED`, `INCOMPLETE_SUBMISSION`, `UNCONFIRMED`, `SUPERSEDED`, link:../dispatch-and-effort/02-dispatch-observability-and-spend.adoc#_dispatch_id_generation_lifecycle_states[Dispatch & Effort Specification]), per-bot participation states and `bot_status` / `ci_status` (link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations]), the 14-state epic queue row vocabulary (link:../dispatch-and-effort/04-epic-coordination.adoc#_git_distributed_epic_ledger_per_file_store_layout_adr_024[Dispatch & Effort Specification, Git-Distributed Epic Ledger]), finding statuses, and job outcomes (`PM-EXEC-4`).

=== State Kinds

Every state has exactly one kind. The first five follow the DSL `state_body` alternatives; `awaiting_user` and `blocked` classify link states by the decision they wait for; `overlay` is the kind of a condition, which is not a state (link:../phase-workflows/01-planning-phases-1-2.adoc#_routine_user_interaction_vs_operator_authorizing_decisions[Phase Workflows Specification, Routine User Interaction vs Operator-Authorizing Decisions]).

[cols="1,4"]
|===
|Kind |Meaning

|`auto`
|Runs one primitive in the same turn (`auto` clause) and follows its outcome; never a resting state.

|`link`
|Offers declared links (`link` clauses) and rests until the model follows one. A state whose only declared link is `escalate` (for example `finalize.loop-limit-reached`) is a `link` state: the escalation is requested by the model, decided by the operator.

|`job`
|Runs one asynchronous job (`job` clause); rests with the implicit `wait:<job_id>` and `cancel:<job_id>` links (link:../workflow-dsl/02-units-jobs-decisions.adoc#implicit-job-links[Workflow DSL Specification, Implicit Links]); its outcomes are the closed job outcome set including `cancelled`.

|`composite_job`
|Runs several jobs as one composite wait (`composite_job` clause); the composite identifier equals the state identifier (`wait:finalize.concurrent-wait`).

|`call`
|Invokes a sub-workflow (`call` clause); never a resting state itself: while the sub-workflow runs, the representation shows the active sub-workflow state, and the sub-workflow's terminal outcome selects the exit.

|`awaiting_user`
|A `link` state of the routine user dialogue: it carries typed questions in `facts` and accepts the answer by elicitation or by the model-relayed `submit` link `answer_questions` (recorded with `channel: model_relayed`). The kind name is never part of a state identifier: the states of this kind are named by their question (`init.lesson-premise`, `init.sibling-collision`, `init.domain-choice`, `init.posture-choice`, `init.recipe-candidate`, `refine.awaiting_answers`, `outline.awaiting_answers`, `<phase>.qgate-exhausted`, `setup.offer-new-steps`). A routine answer that would end the plan is the request `abort` (rel `escalate`), which raises the operator decision `abort-plan` (link:../workflow-dsl/02-units-jobs-decisions.adoc#decision-registry[Workflow DSL Specification, Decision Registry]); it is never answered by the model.

|`blocked`
|A state that is entered by its own workflow condition and waits for an operator decision: the scope records `pending_decision`, renders `facts.operator_command`, and offers exactly one link, `wait:decision:<decision_id>`. The only state of this kind is `execute.awaiting-infeasible-decision`. An `escalate` link followed without elicitation never enters a state of this kind; it raises the `blocked` condition on the current state (<<condition-blocked>>).

|`overlay`
|Not a state: an engine-owned condition recorded on the scope (`pending_condition` in `mcp/status.json`) while the current state and `call_stack` stay unchanged. While it is set, the current state's representation keeps `state`, names the condition in the field `condition`, and renders only the condition's links. Conditions are catalogued in <<state-catalogue-conditions>>, never in a state table, and are never declared in a DSL unit (link:../workflow-dsl/04-ast-node-model.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]).

|`terminal`
|No outgoing transition; `links[0]` (the self-report link `report_bypass` stays accepted and unrendered). Every terminal state declares `terminal <outcome_id> <outcome_class>` (link:../workflow-dsl/01-module-boundary-and-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification, EBNF]); a sub-workflow terminal state's outcome is the one returned to its caller. A plan or epic terminal state has phase value `completed` or `aborted` (`PM-WF-1`); each scope type has exactly one abort terminal (`plan.aborted`, `epic.aborted`, class `failure`), reachable from every phase. A sub-workflow's abort terminal (`git.done-aborted`, class `aborted`) only returns `aborted` to its caller. The workspace scope has no terminal state (xref:06-setup-epic-other.adoc#state-catalogue-setup[Project Setup: `setup` (workspace)]).
|===

=== Generic Per-Phase States

A generic state is written `<phase>.x` and stands for one concrete state per unit in which it occurs: `<phase>` is replaced by the unit prefix (`refine.awaiting_answers`, `execute.baseline-red`). A generic state is defined once in <<state-catalogue-generic>>; its expansion table lists the units where it occurs. A unit table repeats a concrete expansion only where that expansion has behaviour beyond the generic definition (`refine.awaiting_answers`, `execute.baseline-red`, `finalize.baseline-red`). A generic state is a real state that a DSL transition targets; what the engine raises on any state of any unit (a pending operator decision, a footprint violation, an incomplete dispatch, configuration drift, store tampering, a guard that could not be evaluated) is a condition overlay (<<state-catalogue-conditions>>), not a generic state. `*.x` in other documents means the same as `<phase>.x`.

== Conditions (Overlays)

A condition is raised by the engine, not by a DSL transition, on whatever state the scope is in, in any unit, including a sub-workflow state and an `auto` state whose primitive raised it. It is recorded in `mcp/status.json` as `pending_condition` (`kind`, `decision_id` when an operator decision is pending, `facts`, `raised_at`; link:../store-schemas/02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Store Schemas Specification, Workflow State Store]) while `state`, `phase`, and `call_stack` stay unchanged. While it is set, the representation keeps `state` as the current state id, names the condition in the field `condition` (link:../hypermedia-format/01-representation-and-link-forms.adoc#canonical-top-level-fields[Hypermedia Format Specification, Canonical Top-Level Fields]), carries the condition's `facts`, and renders only the condition's links; the implicit `report_bypass` stays accepted and unrendered. Every other link of the state, declared or implicit, is not offered (`link_not_available`). A scope carries at most one condition. A decision resolution is routed like a primitive outcome of the state that raised the condition, through the Decision Registry (link:../workflow-dsl/04-ast-node-model.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]): inside a sub-workflow it stays inside the sub-workflow and `call_stack` is untouched. Conditions are never declared in a DSL unit and are never a transition target.
