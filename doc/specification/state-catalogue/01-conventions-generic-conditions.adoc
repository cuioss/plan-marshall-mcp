== Conventions
_See Requirement link:../../Requirements.adoc#PM-WF-1[PM-WF-1: Hypermedia State Representation (HATEOAS)]_

=== State Identifier Grammar

* *Form*: A state identifier is `<unit>.<name>`: the workflow unit it belongs to, a dot, and the state name. Both parts follow the DSL `identifier` production (lowercase letter first, then lowercase letters, digits, `_`, `-`; link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification, EBNF]). State names are kebab-case (`finalize.concurrent-wait`). The dialogue name `awaiting_answers` keeps its established snake-case form. `awaiting_user` is a state kind (<<_state_kinds>>), never part of a state identifier: a question state is named by its question (`init.sibling-collision`). An identifier of the documents that is not a catalogue state is listed only in xref:06-setup-epic-other.adoc#state-catalogue-migrated[Migrated and Non-Conforming Identifiers].
* *Units*: The unit of a plan-workflow state is its phase file (`init`, `refine`, `outline`, `plan`, `execute`, `land`, `finalize`, link:../workflow-dsl/02-units-jobs-decisions.adoc#workflow-definition-units[Workflow DSL Specification, Workflow Definition Units]); of a sub-workflow state the sub-workflow's family prefix (`git` for `git.commit_and_push`; `remediation-<class>` for the remediation unit `remediation.<policy>`, for example `remediation-ci` for `remediation.ci-failure`, xref:08-remediation-units.adoc#state-catalogue-remediation[Remediation Units]); of every other top-level workflow its own prefix (`setup` for `project-setup.pmwf`, `epic` for `epic.pmwf`); of an entity state its entity unit (`envelope`, `entity`).
* *Exceptions*: The plan's non-abort terminal states are the bare plan outcome names `completed` (outcome `merged`, or `no_change` for an empty harvest), `handed_back`, and `returned` (`PM-WF-1` admits both bare and phase-qualified terminal identifiers). The plan's abort terminal `plan.aborted` and its fallback state `plan.return` carry the scope type as prefix, not the Phase 4 unit `plan`, and are declared in `finalize.pmwf` like the terminals (link:../workflow-dsl/03-reference-excerpt.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Workflow DSL Specification, `finalize.pmwf` Excerpt]); the epic's abort terminal is `epic.aborted`. Entity states may carry a third segment (`envelope.task.active`); no other state does.
* *Anchors*: Every catalogued state carries the anchor `state-<state id>` (for example `link:04-plan-finalize-terminal.adoc#state-finalize.hand-back[finalize.hand-back]`); a generic state `<phase>.x` carries `state-phase.x`, a generic remediation state `remediation-<class>.x` carries `state-remediation.x`. A condition overlay carries `condition-<kind>` (for example `link:01-conventions-generic-conditions.adoc#condition-footprint_violation[footprint_violation]`); the anchors of the former generic states and conditions it replaces stay on its row. Each unit table carries the anchor named in its heading.
* *Not states*: Primitive identifiers share the dotted form (`primitive_id = identifier "." identifier`) but are never states: `review.check-structural-caps`, `finalize.watch-ci-and-bots`, `finalize.retry-emit-landing`, `finalize.spend-ratio`, `finalize.landing-status`, `finalize.wait-status`, `execute.evaluate-envelope-return` (the return-evaluation primitive of the envelope dispatch), `plan.allocate-remediation-tasks`, `findings.triage`, `lane.budget-check`, `merge.gate-entry`, `merge.sync-base`, `merge.evaluate-barrier`, `merge.dispatch`, `waiver.lookup`, the remediation primitives (`remediation.check-budgets`, `remediation.gather-<class>-evidence`, `remediation.request-waiver`, `remediation.await-waiver`), the epic primitives (`epic.inspect-ledger`, `epic.stage-plan`, `epic.ingest-message`, `epic.enqueue-landing`, `epic.land-ledger`, `epic.archive-ledger`), `git.pre-commit-verify-freshness`, `git.push-barrier-decision`, `git.branch-sync-state`, `build.verify-worktree`, and the other `do`, `auto`, `job`, `facts`, and `predicate:` targets of the DSL excerpts. Where a state and its primitive share a name (`git.inspect-worktree`, `git.detect-artifacts`, `git.resolve-message`, `git.stage-and-commit`, `git.evaluate-push-policy`, `finalize.adopt-pr`, `finalize.restart-watch`, `finalize.hand-back`, `finalize.archive-plan`, `plan.return`), the catalogue row is the state. Configuration keys (`workflow.plan.phase-1-init.minimum_lane`), file names (`outline.md`, `init.pmwf`), and effort roles (`plan.<phase>.effort`) are not states either.
* *Other status vocabularies*: The following closed vocabularies are record statuses, not workflow states, and are defined where their record is defined: task statuses (`pending` .. `removed`, link:../store-schemas/06-task-references-manifest.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]), dispatch lifecycle states (`ALLOCATED`, `CLAIMED`, `RETURNED`, `INCOMPLETE_SUBMISSION`, `UNCONFIRMED`, `SUPERSEDED`, link:../dispatch-and-effort/02-dispatch-observability-and-spend.adoc#_dispatch_id_generation_lifecycle_states[Dispatch & Effort Specification]), per-bot participation states and `bot_status` / `ci_status` / `analysis_status` (link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations]), the 14-state epic queue row vocabulary (link:../dispatch-and-effort/04-epic-coordination.adoc#_git_distributed_epic_ledger_per_file_store_layout_adr_024[Dispatch & Effort Specification, Git-Distributed Epic Ledger]), question record closures (`answered`, `assumed`, `cancelled`, link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]), waiver request outcomes, finding statuses, and job outcomes (`PM-EXEC-4`).

=== State Kinds

Every state has exactly one kind. The first five follow the DSL `state_body` alternatives; `awaiting_user` is derived from the AST (a `link` state that waits on open question records); `overlay` is the kind of a condition, which is not a state. `StateCatalogueDriftTest` derives every kind from the AST.

[cols="1,4"]
|===
|Kind |Meaning

|`auto`
|Runs one primitive in the same turn (`auto` clause) and follows its outcome; never a resting state.

|`link`
|Offers declared links (`link` clauses) and rests until the model follows one. Every resting `link` state of a sub-workflow also offers the implicit `step_out (reason: text[1..2000])` (<<exits-and-fallbacks>>).

|`job`
|Runs one asynchronous job (`job` clause); rests with the implicit `wait:<job_id>` and `cancel:<job_id>` links (link:../workflow-dsl/02-units-jobs-decisions.adoc#implicit-job-links[Workflow DSL Specification, Implicit Links]); its outcomes are exactly the closed job outcome set of `PM-EXEC-4`, including `cancelled`.

|`composite_job`
|Runs several jobs, or one observation with domain outcomes, as one composite wait (`composite_job` clause); the composite identifier equals the state identifier (`wait:finalize.concurrent-wait`). Its primitive declares its own closed outcomes and how a constituent `killed`, `timed_out`, or `indeterminate` fate maps to them.

|`call`
|Invokes a sub-workflow (`call` clause); never a resting state itself. Guided step-in: the call makes the sub-workflow's first resting state current, and the representation shows the call-path breadcrumb. The call site routes every outcome of the sub-workflow's exit contract: `done` with a typed result record, or the domain outcomes of a remediation unit, and the control outcome `stepped_out` (link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Rule 6]).

|`awaiting_user`
|A `link` state that waits on open question records (link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]; link:../phase-workflows/07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Phase Workflows Specification, Questions, Waivers & Operator Influence]). A record is raised by the state's primitive (server-owned options) or created by the model's `ask` link; it is answered as the operator configured its class (`questions.mode`, `questions.delivery`): through `answer_questions` (`answers:list<schema[question-answer]>`, each `{question_id, branch_key, text?}`, `session` delivery), or by elicitation or the paired web device, where the model may long-poll `wait:question:<question_id>` (bounded). The awaited event is `QUESTION_ANSWER`. The state carries an engine-owned deadline (`questions.wait_seconds`, none in mode `operator`), processed by the job-runtime timer without a model call; on expiry the compiled fallback of the question class is recorded (`channel: assumption`, or `model` for a task question) and routed like an answer. With `session` delivery the state is a stop point of every continuation policy. The states of this kind are closed: `init.lesson-premise`, `init.sibling-collision`, `init.domain-choice`, `init.recipe-candidate`, `refine.awaiting_answers`, `outline.awaiting_answers`, `outline.review`, `execute.task-question`, `setup.merge-queue`, `setup.reseed-build-map`, `setup.offer-new-steps`. A new question state is catalogued before any document uses it.

|`overlay`
|Not a state: an engine-owned condition recorded on the scope (`pending_condition` in `mcp/status.json`) while the current state and `call_stack` stay unchanged. While it is set, the current state's representation keeps `state`, names the condition in the field `condition`, and renders only the condition's links. Conditions are catalogued in <<state-catalogue-conditions>>, never in a state table, and are never declared in a DSL unit (link:../workflow-dsl/04-ast-node-model.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]).

|`terminal`
|No outgoing transition; `links[0]` (the self-report link `report_bypass` stays accepted and unrendered). Every terminal state declares `terminal <outcome_id> <outcome_class>` (link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification, EBNF]); a sub-workflow terminal state's outcome is the one returned to its caller. The plan's terminals are `completed`, `handed_back`, and `returned`, each entered only from `finalize.archive-plan` after the post-run band, and `plan.aborted` (class `failure`), entered only by the operator's `abort`, `delete-plan`, or the `abort` resolution of an integrity breach. The epic's terminals are `epic.archived` and `epic.aborted`. The workspace scope has no terminal state (xref:06-setup-epic-other.adoc#state-catalogue-setup[Project Setup: `setup` (workspace)]).
|===

[#exits-and-fallbacks]
=== Exits, Step-Outs & Fallbacks

No state waits for an operator decision (link:../phase-workflows/01-planning-phases-1-2.adoc#plan-outcomes[Phase Workflows Specification, Plan Outcomes, Fallback Routes & Remediation Policies]). Every blocking situation has a bounded self-remedy and then a defined fallback:

* *`hand_back`*: The model's exit at plan scope: `hand_back (reason: text[1..2000])` (rel `abort`, form `submit`) on every plan-scope link state at which the plan can end. It takes the fallback of the current position at once: `plan.return` in Phases 1–4, `finalize.hand-back` in Phase 5, the land lane, and Phase 6 before the merge. It is never offered inside a sub-workflow.
* *`step_out`*: The model's exit inside a sub-workflow: the implicit `step_out (reason: text[1..2000])` on every resting `link` state of a sub-workflow (never on `auto`, `job`, or `composite_job` states). It unwinds one frame and returns `stepped_out {by, cause, reason}`; the caller routes it once, to a state offering `hand_back`, to a fallback state, or back to its own recovery state (a remediation unit routes a nested commit's `stepped_out` back to its `decide`). An interrupted rebase is aborted by the server before the frame unwinds. A step-out consumes no budget and writes no waiver.
* *Fallback states*: `plan.return` and `finalize.hand-back` (xref:04-plan-finalize-terminal.adoc#state-catalogue-fallback[Plan Fallbacks & Terminal States]) compose a post-run-only plan instance version and continue into the post-run band; the transaction entering them, or `plan.aborted`, records every begun, unsettled step `failed`. After the merge no fallback exists: a failing post-merge step is retried within its budget and otherwise owed.
* *Operator influence*: Waivers (`pm-mcp operator waive` / `unwaive`) are records read at gate evaluation and by the waiver wait of a remediation unit; `pm-mcp operator abort` and `delete-plan` are engine-owned scope-wide transitions into `plan.aborted` / `epic.aborted` in the next transaction. None is a DSL transition of a catalogued state.

=== Generic Per-Phase States

A generic state is written `<phase>.x` and stands for one concrete state per unit in which it occurs: `<phase>` is replaced by the unit prefix (`refine.awaiting_answers`, `execute.remediate-build`). A generic state is defined once in <<state-catalogue-generic>>, including its per-unit exits; its expansion table lists the units where it occurs. A unit table repeats a concrete expansion only where that expansion has behaviour beyond the generic definition (`refine.awaiting_answers`, `outline.awaiting_answers`). A generic state is a real state that a DSL transition targets; what the engine raises on any state of any unit (an integrity breach, a footprint violation, an incomplete dispatch, configuration drift, an unmet precondition, a guard that could not be evaluated) is a condition overlay (<<state-catalogue-conditions>>), not a generic state. `*.x` in other documents means the same as `<phase>.x`.

[#state-catalogue-conditions]
== Conditions (Overlays)

A condition is raised by the engine, not by a DSL transition, on whatever state the scope is in, in any unit, including a sub-workflow state and an `auto` state whose primitive raised it. It is recorded in `mcp/status.json` as `pending_condition` (`kind`, `facts`, `raised_at`, the self-remedy attempts; link:../store-schemas/02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Store Schemas Specification, Workflow State Store]) while `state`, `phase`, and `call_stack` stay unchanged. While it is set, the representation keeps `state` as the current state id, names the condition in the field `condition` (link:../hypermedia-format/01-representation-and-link-forms.adoc#canonical-top-level-fields[Hypermedia Format Specification, Canonical Top-Level Fields]), carries the condition's `facts`, and renders only the condition's links; the implicit `report_bypass` stays accepted and unrendered. Every other link of the state, declared or implicit, is not offered (`link_not_available`). A scope carries at most one condition. Conditions are never declared in a DSL unit and are never a transition target (link:../workflow-dsl/04-ast-node-model.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]).

*Bounded self-remedy*: Every condition except `integrity_breach` offers its self-remedy links, bounded by a compiled budget of `3` attempts per condition instance; the operator may remove the cause at any time. On a plan scope a spent budget takes the fallback of the current position (<<exits-and-fallbacks>>) with the condition recorded as the gap (`cause: condition`); inside a sub-workflow the engine steps out of every frame (`stepped_out {by: server, cause: condition}`), and each caller routes it. Where the fallback itself lacks what is missing (no push credential), `handed_back` degrades to the local branch with the gap stated in the landing record. On the epic and the workspace scopes, which have no fallback, the self-remedy stays offered without a budget.

|A boundary breach, never a change inside the plan's worktree beyond the declared footprint (that is recorded as an unplanned change): the footprint check that `git.stage-and-commit` runs first for every caller (a path outside the plan's worktree, a pinned build file or protected path, a main-checkout change since `entry_baseline`); the same check on a task `submit:TASK-*` link; the Clean Main Checkout Guard of any plan transition. The link or primitive that met the violation is not executed; no commit is made. Not waivable.
|`fix`. `facts`: offending files, `baseline_dirty` (never offered for revert).
|`fix`, when the footprint check that follows it passes; a failing check keeps the condition with refreshed `facts`.
|Clearing re-renders the current state; the interrupted link is followed again. A spent budget takes the fallback.

|[[condition-dispatch_incomplete]][[state-phase.dispatch-incomplete]]`dispatch_incomplete`
|`returned:<dispatch_id>` with `status: success` while the entity has not recorded its required `submit`; the dispatch is marked `INCOMPLETE_SUBMISSION`. The current state is the dispatching state.
|`resume:<entity>` (rel `next`, form `noop`; complete or re-dispatch after inspecting disk state).
|`resume:<entity>`: the entity's required `submit` is recorded (dispatch `RETURNED`), or the remaining work is re-dispatched with a fresh `dispatch_id` (dispatch `SUPERSEDED`).
|The dispatching state continues; the return-evaluation outcome of the completed submission is taken. A spent budget takes the fallback.
|link:../dispatch-and-effort/02-dispatch-observability-and-spend.adoc#_post_return_integrity_invariants[Dispatch & Effort Specification, Post-Return Integrity Invariants item 2]

|[[condition-config_drift]][[state-phase.config-drift]]`config_drift`
|A phase entry in Phases 4–6 whose current `config_hash` differs from the one in the header of the plan instance version in force and whose candidate instance version differs in effect (the phase handshake, not a DSL transition).
|`adopt`, `keep`. `facts`: the instance diff.
|`adopt` composes the candidate as a new instance version (composition event `config_adopted`), refused, and resolved as `keep`, when it does not contain the current state and every `call_stack` state; `keep` continues on the version in force. The choice is recorded in `audit.jsonl` and `instance/composition.jsonl`.
|The interrupted phase entry continues in the current state on the adopted or the kept version.

|[[condition-guard_indeterminate]]`guard_indeterminate`
|A guard of the current state (built-in, `predicate:`, or one reading a `depends_on_config` key) evaluated to `COULD_NOT_EVALUATE(reason)`; the result is never folded into held or not held.
|`retry` (re-evaluates the state's guards). `facts`: the guard, the link it gates, the reason.
|`retry`, when every guard of the state evaluates to `HELD` or `NOT_HELD`; a repeated `COULD_NOT_EVALUATE` keeps the condition with refreshed `facts`.
|Clearing re-renders the current state with the links whose guards hold. A spent budget takes the fallback.
