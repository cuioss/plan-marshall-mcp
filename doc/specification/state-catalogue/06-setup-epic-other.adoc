== Project Setup: `setup` (workspace)

Declared in `project-setup.pmwf` (`scope workspace`), hosted by the project's workspace scope; phase value `workspace`. The single start state `setup.entry` records `setup_run: first_run | reconcile` and routes every run by it. The unit has no terminal state: the workspace scope lives as long as the project's enrolment and rests in `setup.completed` between runs, whose `reconcile` link starts the next run. Enrolment (`pm-operator enrol`) creates the workspace scope and is not a state of it; the first run creates `.marshall/` and `.marshall/config/` with the default workflow units, with no legacy input. `project-setup.pmwf` is compiled into the binary and never project-owned. A setup choice is taken on the channel of the store it writes: operator configuration (integration variant, commit identity, operator posture) only through the operator channel, team configuration as a workspace-scope question record (class `setup`). Every server-raised question state is preceded by an `auto` probe state that enters it only when something needs an answer; a model's `ask` enters the asking state's `.asked` question state. Every setup failure enters `setup.needs-repair`, never a condition (link:../domain-extensions/04-setup-state-machine.adoc#setup-probe-states[Domain Extensions Specification, Probe States]; link:../domain-extensions/04-setup-state-machine.adoc#setup-questions[Setup Choices by Owner]). The entry session drives the setup: it follows the `link` states and relays the user's choices, and MCP elicitation may carry the setup's questions beside the web app. The model work of the setup is done by tasks of roles like every other model work (`setup.enrich-architecture`, role `enrich`; the commit tasks of `setup.land-changes`), which the session may take as an optional worker where the role permits it.

[#state-catalogue-epic]
== Epic Workflow: `epic`

Declared in `epic.pmwf` (`scope epic`, start `epic.decompose`); the epic scope is created by `bootstrap-epic` (xref:09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap-epic[Bootstrap of an Epic]); phase value `orchestrator` (DSL `phase orchestrate`) for every non-terminal state. The DSL excerpt is in link:../model-work/08-epic-coordination.adoc#epic-workflow[Model Work Specification, Epic Workflow (`epic.pmwf`)]. After the bootstrap the epic runs without a session: `epic.active` is the server's resting state, every judgment is a task of a `read_only` epic role (`decompose`, `reground`, `coordinate`, `landing`), and every ledger write commits through a `git.commit_and_push` call; the epic offers no link, and its representation is a view. When an epic task closes `lost` (its re-offers spent, `role_unqualified`, or `role_unavailable`), the item it served is marked `held` with the reason, listed in `pm-operator status` and the web app, and skipped by `epic.next-work` until the effective role set changes or the operator acts on the epic; the state continues at `epic.active` (`epic.decompose` keeps resting instead). Nothing waits for an operator decision; the operator stops an epic with `pm-operator abort epic <epic_id> --reason`.

|`epic.decompose` (`submitted`).
|`call git.commit_and_push (message_mode=step_or_fallback, push_mode=never)` in the shared epic worktree on the fixed epic branch, staging only `.marshall/orchestrator/**`.
|`done` -> `epic.active`; `stepped_out` -> `epic.active` (the writes stay uncommitted and are committed with the next ledger write).

|[[state-epic.active]]`epic.active`
|`orchestrator`
|`auto`
|`epic.commit-decomposition`, `epic.commit-ledger`, `epic.landing` (every outcome); `start-epic.adopt` (`adopted`, for an adopted ledger that has a queue row); itself (`idle`).
|`auto epic.next-work`, the epic's next work: it first starts every launchable plan the epic's `parallelization_scope` admits, through the plan bootstrap without a session (xref:09-bootstrap-and-lessons.adoc#state-start.launch[`start.launch`]), and reconciles every shipped row without a landing record, then takes the first outcome that holds, skipping `held` items. On `idle` the epic rests here, the one resting `auto` state, until the next epic event re-evaluates it: an inbox append, a plan outcome of one of its rows, a landing record, a ledger commit, an observed advance of the default branch, a change of the effective role set, or an operator action on the epic. `facts`: the queue rows, `unlanded_shipped` (count and `plan_id` values, zero included), the pending messages, the `held` items, `primary_checkout_behind`.
|`rows_ungrounded` (a start candidate's specification predates `HEAD`) -> `epic.reground`; `rows_stale` -> `epic.recut`; `message_pending` -> `epic.ingest`; `landing_unanalyzed` -> `epic.analyze-landing`; `ledger_unlanded` (the epic branch holds commits the default branch lacks, and the last landing did not fail on the same head) -> `epic.landing`; `settled` (no live row, no pending message, every landing analyzed, the ledger landed) -> `epic.review-completion`; `idle` -> this state.
|link:../model-work/08-epic-coordination.adoc#epic-workflow[Model Work Specification, Next Work]; link:../model-work/08-epic-coordination.adoc#server-started-plans[Server-Started Plans]

|[[state-epic.landing]]`epic.landing`
|`orchestrator`
|`job`
|`epic.active` (`ledger_unlanded`).
|`epic.land-ledger`: one pull request from the epic branch for all pending ledger changes; repository-wide epics-worktree lock; ledger paths only; required CI checks only; waits for `merged`, `ejected`, `closed`, or `timed_out`; post-merge epic-branch resync. The primary checkout is never moved: the fact `primary_checkout_behind` names `git pull` for it. Its git steps are the primitives of the plan merge (`git.stage-and-commit`, `git.push`, `ci.pr-create`, `ci.merge` or `ci.enqueue` bound to the expected head SHA, `ci.pr-observe`) under the epics-worktree lock, with the stall-based queue bound of `finalize.merge-queue-wait`.
|`succeeded` (observed `merged`) -> `epic.active`; `failed` (`ejected`, `closed`, `timed_out`) and every other job outcome, `cancelled` included -> `epic.active` (worktree and branch unchanged; the same epic-branch head is not landed again, and the next ledger commit or a default-branch advance resumes the landing).
|link:../model-work/08-epic-coordination.adoc#epic-landing[Model Work Specification, Epic Landing]
