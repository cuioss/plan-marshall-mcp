[#state-catalogue-setup]
== Project Setup: `setup` (workspace)

Declared in `project-setup.pmwf` (`scope workspace`), hosted by the project's workspace scope; phase value `workspace`. The single start state `setup.entry` records `setup_run: first_run | reconcile` and routes every run by it. The unit has no terminal state: the workspace scope lives as long as the project's enrolment and rests in `setup.completed` between runs, whose `reconcile` link starts the next run. Enrolment (`pm-mcp operator enrol`) creates the workspace scope and is not a state of it; the first run creates `.marshall/` and `.marshall/config/` with the default workflow units, with no legacy input. `project-setup.pmwf` is compiled into the binary and never project-owned. A setup choice is taken on the channel of the store it writes: operator configuration (integration variant, commit identity, operator posture) only through the operator channel, team configuration as a workspace-scope question record (class `setup`). Every server-raised question state is preceded by an `auto` probe state that enters it only when something needs an answer; a model's `ask` enters the asking state's `.asked` question state. Every setup failure enters `setup.needs-repair`, never a condition (link:../domain-extensions/04-setup-state-machine.adoc#setup-probe-states[Domain Extensions Specification, Probe States]; link:../domain-extensions/04-setup-state-machine.adoc#setup-questions[Setup Choices by Owner]).

[#state-catalogue-epic]
== Epic Workflow: `epic`

Declared in `epic.pmwf` (`scope epic`, start `epic.decompose`); the epic scope is created by `bootstrap-epic` (xref:09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap-epic[Bootstrap of an Epic]); phase value `orchestrator` (DSL `phase orchestrate`) for every non-terminal state. The DSL excerpt is in link:../dispatch-and-effort/04-epic-coordination.adoc#epic-workflow[Model Jobs & Effort Specification, Epic Workflow (`epic.pmwf`)]. No epic state waits for an operator decision; the operator stops an epic with `pm-mcp operator abort epic <epic_id> --reason`.

[cols="2,1,1,2,3,2,2"]
|===
|State id |Phase value |Kind |Entered from |Offered links / outcomes |Exits to |Defined in

|[[state-epic.decompose]]`epic.decompose`
|`orchestrator`
|`link`
|The epic's creation by `bootstrap-epic` (the `created` outcome of `start.create-scope`, run by the `create` link of `start-epic.ready`, or `start-epic.adopt` for an adopted ledger it places here; the unit's start state; the header and the vision section of `spec.md` exist); `epic.commit-decomposition` (every outcome).
|`draft` (rel `next`, `noop`): a model job drafts the decomposition; `workstream` (`submit`: `workstream_id`, `title`, `order`); `spec_section` (`submit`: `anchor`, `text`: writes a staged plan section of `spec.md`; its claim sections are parsed by the link's content validator, which refuses the payload with `invalid_link_args` and the `detail` code `claim_section_unreadable` for an `unreadable` claim section or `section_too_large` for more than six deliverables); `stage` (as in `epic.active`); `decomposed` (rel `next`, `noop`, guard `epic.decomposition-ready`: at least one staged row, and every staged row's section parses). A ledger read that fails raises `precondition_unmet` (`ledger_unreadable`, xref:01-conventions-generic-conditions.adoc#condition-precondition_unmet[Condition precondition unmet]), which ends only when the ledger reads or by the operator's `abort`.
|`draft` -> `epic.decompose-draft`; a `workstream`, `spec_section`, or `stage` write -> `epic.commit-decomposition`; `decomposed` -> `epic.active`.
|link:../dispatch-and-effort/04-epic-coordination.adoc#epic-workflow[Model Jobs & Effort Specification, Epic Workflow]

|`drafted` -> `epic.commit-decomposition`; missing submission -> the `job_incomplete` condition (its `resume` stays offered on the epic scope).
|link:../dispatch-and-effort/04-epic-coordination.adoc#epic-workflow[Model Jobs & Effort Specification, Epic Workflow]

|`done` -> `epic.decompose`; `stepped_out` -> `epic.decompose` (the write stays uncommitted and is committed with the next ledger write).

|The epic's resting state: `stage` (`submit`, a scope-wide link without entity: stages a plan as a queue row from `plan_slug` (becomes the `plan_id`; same grammar and phantom checks), `spec_section` (the anchor of a section in `spec.md`, `text[1..128]`), `surface_paths`, `surface_modules?`, `prerequisites?` (`plan_id` list), and `workstream_id?`; the server assigns the row's `ordinal`; refusals `surface_overlap`, `surface_undeclared`); `workstream` and `spec_section` (as in `epic.decompose`, for later additions; never for a `launched` or `running` row); `emit:<plan_id>` (`emit`, `noop`) for `staged` rows whose prerequisites are all `terminal.shipped` and whose re-grounding verdict is not `stale` (a stale row is emitted only after its section is re-submitted); `facts.emitted_command` is the host entry command of the emitting session's client, which starts the plan's bootstrap; `reground` (rel `next`, `noop`, guard `epic.has-ungrounded-row`): a model job re-grounds every staged row whose spec was written or last re-grounded before `HEAD`; `ingest:<message_id>` (`submit` with `kind: enum[transferred\|re-scoped\|left_alone]` and `note: text[1..2000]?`: claims and processes an inbox message, including intake of a transfer offer and the source disposition); `land-ledger` (`next`, `noop`: the epic landing); `archive` (`next`, `noop`). Beside these, the epic links specified in the Model Jobs & Effort Specification: `submit_landing:<plan_id>`, `reconcile_landing:<plan_id>`, `transfer_offer:<plan_id>`, `mailbox_send:<plan_id>`, The child's `bootstrap-plan` sets its row `running` in the plan's creation transaction. A landing maps the plan outcome onto the row status: `merged` -> `merged`, `no_change` -> `completed`, `aborted` -> `abandoned`, `returned` -> `returned` (closed unshipped, re-stageable as a new row), `handed_back` -> `handed_back` (live until the landing reconciliation observes the pull request: merged -> `merged`, closed -> `abandoned`). A landing whose unplanned paths overlap a sibling's declared surface is only noted for the landing reconciliation (unplanned-change overlaps).
|A ledger write (`stage`, `workstream`, `spec_section`, `emit`, `ingest`, `submit_landing`, `reconcile_landing`, `transfer_offer`) -> `epic.commit-ledger`; `reground` -> `epic.reground`; `land-ledger` -> `epic.landing`; `archive` -> `epic.archived`.

|[[state-epic.landing]]`epic.landing`
|`orchestrator`
|`job`
|`epic.active` (`land-ledger`).
|The epic landing: one pull request from the epic branch for all pending ledger changes; repository-wide epics-worktree lock; ledger paths only; required CI checks only; waits for `merged`, `ejected`, `closed`, or `timed_out`; post-merge epic-branch resync. The primary checkout is never moved: a fact names `git pull` for it. Implicit `wait:` / `cancel:` links. Its git steps are the primitives of the plan merge (`git.stage-and-commit`, `git.push`, `ci.pr-create`, `ci.merge` or `ci.enqueue` bound to the expected head SHA, `ci.pr-observe`) under the epics-worktree lock, with the stall-based queue bound of `finalize.merge-queue-wait`.
|`succeeded` (observed `merged`) -> `epic.active`; `failed` (`ejected`, `closed`, `timed_out`) and every other job outcome, `cancelled` included -> `epic.active` (worktree and branch unchanged, so `land-ledger` resumes).
