== On-the-Fly Placeholder Rendering Rules
_See Requirement link:../../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

_See Requirement link:../../Requirements.adoc#PM-SKILL-2[PM-SKILL-2: Per-Project Skill Generation & Digest Integrity]_

_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-2[PM-WATCH-CLIENT-2]_

Vocabulary skill templates (`SKILL.md`), the launch prompts of workers, and operator guidance strings are authored once in canonical placeholder notation and rendered on the fly by `ClientProfileRenderer`. A call of an interactive session renders with the client its relay declares (`pm-mcp serve --client <client>`, link:../runtime-model.adoc[Runtime & Interaction Model Specification, Relay]); a worker's prompt and every call of its job connection render with the profile of the harness its role names, recorded in its job record (xref:01-profile-schema.adoc#headless-block[Client Profile Schema, `headless`]).

`{{tool:ask_user}}` names the host tool the entry session uses to relay to the user an open question shown through an answer link (`answer:<question_id>`) or a choice of a bootstrap or of the project setup; the answer is always submitted through the offered link, never taken from the host tool's result alone, and the tool is never used for an operator override (link:../hypermedia-format/01-representation-and-link-forms.adoc[Hypermedia Format Specification]). Questions reach the user dependably through the web app (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]); a worker has no `{{tool:ask_user}}` in its tool set.

`{{command:plan}}`, `{{command:epic}}`, and `{{command:workspace}}` render the host entry command of each entry kind (`commands.entries`, one placeholder per entry command). Every entry command takes the same arguments on every host: an optional id and the user's free text, which it passes to `pm-mcp enter` as the entry's hint (link:../cli-and-security/01-cli-and-installer.adoc#_entry_identity_recording_pm_mcp_enter[CLI, Coordination & Security Specification, Entry Identity Recording]). The server starts the plans of an epic itself, so no command is rendered for the operator to type (link:../model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]).

[#entry-command-prefix]
*Entry command prefix*: The host entry commands carry the prefix `mcp-` (`/mcp-plan-marshall`, `/mcp-plan-orchestrator`, `/mcp-marshall-steward`; `$mcp-…` skills on `codex`), so they complete together in the harness (`/mcp…`) and coexist with the commands of the `plan-marshall` plugin in a mixed installation (`PM-MIG-2`); the bundle's command and skill files are named after them (xref:03-bundle-manifest.adoc[Bundle Manifest]). The rename to the plain names once the `plan-marshall` plugin is retired is recorded in link:../../later-improvements.adoc#_l_9_plain_entry_command_names[Later Improvements, L-9].

In `{{skill_load:<uri>}}`, `<scope>` is the rendering scope's argument: `plan_id="<plan_id>"` (`plan_id="NO_PLAN"` for the workspace scope) or `epic_id="<epic_id>"`, because `pm_skill` requires exactly one of them (link:../mcp-tools/01-core-workflow-tools.adoc#_surface_design_context_budget_discipline[MCP Tools Specification, Architectural Constraints item 11]).

=== Rendering Invariants
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-1[PM-WATCH-CLIENT-1], link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-6[PM-WATCH-CLIENT-6], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-23[PM-WATCH-EXT-23]_

1. *Zero Unresolved Placeholders*: If any `{{...}}` token in a skill template fails to resolve against the active `ClientProfile`, `ClientProfileRenderer` fails closed and logs a template defect rather than emitting raw `{{...}}` syntax to the model.
2. *Per-Variant SHA-256 Digest (`PM-SKILL-2`)*: The digest `_meta["de.cuioss.pm-mcp/sha256"]` published by `pm_skills` / `pm_skill` and `resources/read` is the SHA-256 of the rendered bytes the client receives (after rendering for `(project_config, client_id, pm_mcp_version)`); it is stable while those bytes are unchanged, and a configuration or version change that leaves a skill's rendered bytes unchanged leaves its digest unchanged.
3. *No Worker Without an Eligible Harness (`PM-WF-5`, `PM-WORK-1`, `PM-CLIENT-4`)*: Rendering never replaces a worker by inline work in the entry session. A role whose harness has `headless: null` (`antigravity`, `neutral`), is not eligible (`worker.eligible: false`), lacks a capability the role's class needs, or runs a model not listed in `worker.restricted_models` is invalid on load and counts as undefined, so a unit naming it is refused `role_undefined` at composition (xref:01-profile-schema.adoc#worker-block[Client Profile Schema, Worker Block]; link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]).
4. *Vocabulary-Only Translation*: `ClientProfileRenderer` varies only the placeholder dimensions of `PM-CLIENT-2` (host tool names, skill load directives, command names, tool idioms; model and effort enter only the launch argument vector). It never varies emphasis, scaffolding, structure, or format: rendered variants of one template are byte-identical outside resolved placeholders.
5. *Profile Completeness*: Every canonical placeholder, and every rendering dimension added later, has a resolution in every built-in profile including `neutral`. A build-time test renders every template for every built-in profile and fails on any unresolved or missing form.
6. *Technique Preconditions Rendered per Project*: A skill section whose technique precondition (link:../domain-extensions.adoc[Domain Extensions Specification], Core Architectural Invariants, Technique Preconditions) is unmet in the project is rendered with the marker "available technique, not adopted in this project" in place of binding wording; the precondition result is an input of the rendered variant and of its `_meta.sha256` digest. This is a project dimension, not a client dimension, so it does not break Rendering Invariant 4.

[#calibration-decision]
=== Calibration Decision
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-1[PM-WATCH-CLIENT-1], link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-2[PM-WATCH-CLIENT-2]_

Model-facing content is written once and rendered vocabulary-only (Rendering Invariant 4), the same for every model a role set names. Whether it is adequate for a model is what role qualification measures: a role whose configuration does not reach the agreement level on its corpus topics with this content is unqualified, and its tasks take the conservative fallback (link:../model-work/01-roles-and-configuration.adoc#qualification[Model Work Specification, Role Qualification]). A calibration axis of the content is keyed by the model of the role artifact, never by the `client_id`, because one client hosts several models; such an axis multiplies the rendered digests (`PM-SKILL-2`) and requires per-model content and a qualification of every role on each model it distinguishes before it ships.

[#host-resident-surface-inventory]
=== Host-Resident Surface Inventory
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-3[PM-WATCH-CLIENT-3]_

For every built-in profile, the build derives and publishes the host-resident surface of the entry session: the bytes the host injects into every turn by its registration mechanism (the descriptions of the three entry commands and of the shim skill, MCP tool schemas and descriptions when `schema_residency: resident`, and the `pm_skills` catalogue entries once loaded), per component and in total, together with the population it measured. A worker loads the tools of its role directly from its launch configuration and receives its skills from the server (`PM-SKILL-4`), so it has no host-resident surface of its own to inventory. Residency follows the actual injection mechanism, not file existence; the population is the served set for the profile (after domain filtering, `PM-SKILL-2`), not the set of files in the binary.

* *Derived Bounds*: Any length or shape bound on a description is derived from the measured distribution of the inventory and records that derivation; a build-time test enforces the bound.
* *Named Runtimes*: A description shape rule names the runtimes and models it was reasoned about; every runtime reads the descriptions byte-identically.

== Entry Identity Audit & Host Detection
_See Requirement link:../../Requirements.adoc#PM-CLIENT-1[PM-CLIENT-1: Entry Identity Declaration]_

_See Requirement link:../../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Entry Identity Audit]_

_See Requirement link:../../Requirements.adoc#PM-CLIENT-4[PM-CLIENT-4: Neutral Fallback Profile for Unknown Clients]_

Client identity is advisory routing and rendering metadata, never a security credential. PM-MCP cross-checks the declared identity of an interactive session once, at `pm-mcp enter`, against the host environment and records the result for the operator; it performs no identity check per tool call. A call of an interactive session renders from the client its relay declares (`pm-mcp serve --client <client>`), and a worker's call from its job record, which names the harness of its role (link:../mcp-tools/01-core-workflow-tools.adoc#job-bound-connections[MCP Tools Specification, Job-Bound Connections]).

=== The Three Identity Tiers

* *Tier 1 — Declared Entry Identity (`declared_client`)*:
** Supplied explicitly via `pm-mcp enter --client <client_id> <plan|epic|workspace> [<plan_id>|<epic_id>]` by the installed client bundle's entry command.
** Persisted as `client` in the entry row that `pm-mcp enter` appends to the scope's session log `sessions.jsonl`, together with the host session identifier, the detected client and `environment_match_tier`, the exact host build `client_build` (from the profile's version probe, <<host-identity-probes>>), the model identity, `pm_mcp_version`, `bundle_version`, `project_id`, `entered_from`, and the entry instant (link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]). Only `pm-mcp enter` appends a row; a worker appends none.
* *Tier 2 — Detected Environment (`detected_client`)*:
** Evaluated by the runtime from the environment signature that `pm-mcp enter` (the relay binary) computes from the process environment inherited from the host shell, against the detection signals and precedence of the <<host-integration-table>>.
* *Tier 3 — Authenticated OS Principal (`os_principal`)*:
** The operating system effective user ID (`uid`) and username owning the `pm-mcp enter` process.

*Detection precedence*: Primary signals are evaluated in the fixed order `antigravity` -> `opencode` -> `claude` (the order `plan-marshall` uses, `script-shared/scripts/target_context.py` `detect_target_from_env`, the single implementation, which `marketplace_paths.py` delegates to; because the signals are inherited, a host launched from inside another host is attributed by this fixed order, not necessarily to the innermost agent), then `codex` _(provisional)_; the first match wins. Secondary signals (`CLAUDECODE` _(provisional)_, `AI_AGENT` _(provisional)_) are consulted only when no primary signal matches. The same signals are the host session markers that the job launcher never passes to a worker, so a harness started by the runtime never inherits the markers of the operator's host (link:../job-runtime/02-confinement-and-environment.adoc#_job_environment_pm_sec_5[Job Runtime Specification, Job Environment]).

*MCP tool names per host*: A host names the tools of the `plan-marshall` server `mcp__plan-marshall__<tool>` (`claude`), `plan-marshall_<tool>` (`opencode`), or reaches them through its built-in `call_mcp_tool` with server and tool name (`antigravity`). A role's tool set and every rendered tool reference use this form; a tool allowlist names every tool exactly, never by a wildcard (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]).

*Antigravity environment*: Antigravity passes its environment to the `stdio` server it starts, so its relay reads its identity from the environment like on every other host, although the host has only one global MCP entry.

[#host-detection-table]
*Host-detection table (compiled, `pm-api`)*: The host-detection data, that is the environment signals and their precedence, the session ID variable, and the version-probe argument vector with its pattern and model source, is one compiled, data-only table in `pm-api` (link:../module-structure.adoc#module-pm-api[Module Structure Specification, `pm-api`]). It is the single source: both client binaries depend only on `pm-api` and read it directly, and the client profiles of `pm-core` take their `identity` object and their detection signals from it instead of repeating the values. The relay binary `pm-mcp` (link:../module-structure.adoc#module-pm-relay[Module Structure Specification, `pm-relay`]) computes the environment signature and runs the version probe in `enter` and reads the session ID variable; `pm-operator` (link:../module-structure.adoc#module-pm-operator[Module Structure Specification, `pm-operator`]) reads the signals only for its operator checks, which refuse a verb while a coding-agent environment signal is present (link:../cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]). It computes no environment signature. Operator overrides do not touch it (xref:01-profile-schema.adoc#_profile_override_hierarchy[Profile Override Hierarchy]).

*Codex tool names*: The Codex columns of the placeholder table above are provisional; in particular Codex has no `write_file` tool and writes files through `apply_patch`, so `{{tool:write_file}}` resolves to `apply_patch` like `{{tool:edit_file}}`.

*OpenCode tool names*: The `opencode` column follows `plan-marshall`'s `marketplace/targets/opencode/mapping.json` (at `969cbfeb5`). Its entry `"Write": "edit"` sits under `tool_permissions` and names the OpenCode permission category that governs writing, not the tool: the file-create tool is `write`, so `{{tool:write_file}}` resolves to `write`.

=== Mismatch Resolution & Audit Behavior

[cols="2,2,3"]
|===
|Scenario at `pm-mcp enter` |Active Profile Selected |Audit Effect

|`declared_client == detected_client` (e.g., both `claude`)
|`claude`
|The enter record (`category: identity`, `event: entered`) carries `details.environment_match_tier: "MATCHED"` and `details.identity_mismatch: false`.

|`declared_client: "claude"`, but the environment matches `unknown` (no conflicting host markers)
|`claude`
|The enter record carries `details.environment_match_tier: "UNVERIFIED"` and `details.identity_mismatch: false`.

|`declared_client: "claude"`, but the environment matches `opencode` (`CONTRADICTED`)
|`claude` (honors explicit `--client`, never switches silently)
|The enter record carries `details.environment_match_tier: "CONTRADICTED"`, `details.identity_mismatch: true`, and the identity tuple (`declared_client`, `detected_env`, `os_principal`) in `details` (link:../store-schemas/12-machine-stores.adoc#audit-log[Store Schemas Specification, Audit Log]). `pm-mcp enter` prints a mismatch notice, and the operator sees the mismatch in `pm-operator status` and the web app.

|Unrecognized client or `--client neutral`
|`neutral`
|The session row records `"client": "neutral"` and `audit.jsonl` records the fallback; the operator sees the active profile of every session in `pm-operator status`, the session row, and the audit record.
|===

No model-facing representation carries a mismatch, a neutral-profile marker, or any other identity notice (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). A connection whose relay declares a client other than the one its scope was entered with is rendered for the client its relay declares; nothing is checked or recorded per call. Under `neutral`, skill loading uses `pm_skill`, the session takes no task, and no role can name the profile as its harness (Rendering Invariant 3).
