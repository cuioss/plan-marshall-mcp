== On-the-Fly Placeholder Rendering Rules
_See Requirement link:../../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

_See Requirement link:../../Requirements.adoc#PM-SKILL-2[PM-SKILL-2: Per-Project Skill Generation & Digest Integrity]_

_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-2[PM-WATCH-CLIENT-2]_

Vocabulary skill templates (`SKILL.md`), the prompt files of model jobs, and operator guidance strings are authored once in canonical placeholder notation and rendered on the fly by `ClientProfileRenderer` using the `client` recorded in the last row of the scope's `sessions.jsonl`; a model job's prompt file renders with the profile of the job's harness (xref:01-profile-schema.adoc#headless-block[Client Profile Schema, `headless`]).

`{{tool:ask_user}}` names the host tool the model uses to relay a question record delivered in the session (`questions.delivery` resolved to `session`) to the user; the answer is always submitted through the `answer_questions` link, never taken from the host tool's result alone, and the tool is never used for an operator override (link:../hypermedia-format/01-representation-and-link-forms.adoc#question-waiver-and-exit-links[Hypermedia Format Specification]).

`{{command:plan}}`, `{{command:epic}}`, and `{{command:workspace}}` render the host entry command of each entry kind (`commands.entries`, one placeholder per entry command). Every entry command takes the same arguments on every host: an optional id, `--from-epic <epic_id>`, and the user's free text, which it passes to `pm-mcp enter` as the entry's hint (link:../cli-and-security/01-cli-and-installer.adoc#_entry_identity_recording_pm_mcp_enter[CLI, Coordination & Security Specification, Entry Identity Recording]). The command an epic emits for a `launched` queue row is rendered for the client of the emitting session's last row as `{{command:plan}} <plan_id> --from-epic <epic_id>` (for example `/plan-marshall <plan_id> --from-epic <epic_id>` for `claude`, `pm-mcp enter --client neutral plan <plan_id> --from-epic <epic_id>` for `neutral`; link:../dispatch-and-effort/04-epic-coordination.adoc[Model Jobs & Effort Specification, Epic Coordination]), so the operator types it into the host.

In `{{skill_load:<uri>}}`, `<scope>` is the rendering scope's argument: `plan_id="<plan_id>"` (`plan_id="NO_PLAN"` for the workspace scope) or `epic_id="<epic_id>"`, because `pm_skill` requires exactly one of them (link:../mcp-tools/01-core-workflow-tools.adoc#_surface_design_context_budget_discipline[MCP Tools Specification, Architectural Constraints item 10]).

`{{model:*}}` resolves only in a profile with a `headless` block, from its ladder `models`; `antigravity` and `neutral` run no model jobs and carry no ladder (xref:01-profile-schema.adoc#headless-block[Client Profile Schema, `headless`]). The placeholder occurs only in content rendered with a harness's profile (the prompt files of model jobs), never in content served to a session. The `{{model:*}}` resolutions are a snapshot with the same provenance as the <<host-integration-table,Host Integration Table>> (`plan-marshall/standards/effort-levels.md` at `1d4a1da37`; provisional values verified in Milestone 1) and are re-confirmed whenever the host integration facts of a profile are re-verified and whenever the <<calibration-decision>> is revisited.

=== Rendering Invariants
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-1[PM-WATCH-CLIENT-1], link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-6[PM-WATCH-CLIENT-6], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-23[PM-WATCH-EXT-23]_

1. *Zero Unresolved Placeholders*: If any `{{...}}` token in a skill template fails to resolve against the active `ClientProfile`, `ClientProfileRenderer` fails closed and logs a template defect rather than emitting raw `{{...}}` syntax to the model.
2. *Per-Variant SHA-256 Digest (`PM-SKILL-2`)*: The digest `_meta["de.cuioss.pm-mcp/sha256"]` published by `pm_skills` / `pm_skill` and `resources/read` is the SHA-256 of the rendered bytes the client receives (after rendering for `(project_config, client_id, pm_mcp_version)`); it is stable while those bytes are unchanged, and a configuration or version change that leaves a skill's rendered bytes unchanged leaves its digest unchanged.
3. *No Model Job Without a Launch Contract (`PM-WF-5`, `PM-CLIENT-4`)*: Rendering never replaces a model job by inline work in the main session. When the job's harness has `headless: null` (`antigravity`, `neutral`) or lacks a capability the job class needs, the job state raises `precondition_unmet` naming the missing capability and the `model_jobs.harness` setting (xref:01-profile-schema.adoc#headless-block[Client Profile Schema, `headless`]).
4. *Vocabulary-Only Translation*: `ClientProfileRenderer` varies only the placeholder dimensions of `PM-CLIENT-2` (host tool names, skill load directives, command names, tool idioms, model and effort). It never varies emphasis, scaffolding, structure, or format: rendered variants of one template are byte-identical outside resolved placeholders.
5. *Profile Completeness*: Every canonical placeholder, and every rendering dimension added later, has a resolution in every built-in profile including `neutral`; the one exception is `{{model:*}}`, which resolves only in the profiles with a `headless` block. A build-time test renders every template for every built-in profile and fails on any unresolved or missing form.
6. *Technique Preconditions Rendered per Project*: A skill section whose technique precondition (link:../domain-extensions.adoc[Domain Extensions Specification], Core Architectural Invariants, Technique Preconditions) is unmet in the project is rendered with the marker "available technique, not adopted in this project" in place of binding wording; the precondition result is an input of the rendered variant and of its `_meta.sha256` digest. This is a project dimension, not a client dimension, so it does not break Rendering Invariant 4.

[#calibration-decision]
=== Calibration Decision
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-1[PM-WATCH-CLIENT-1], link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-2[PM-WATCH-CLIENT-2]_

Model-facing content is calibrated once, for the weakest model reachable through the built-in effort ladders of all profiles, and rendered vocabulary-only (Rendering Invariant 4). This is a recorded decision, not a default: a byte-identical export is not neutral, and its cost is that stronger models receive more scaffolding than they need (a larger resident surface, `PM-TOOL-5`). The decision is revisited when the behavioural conformance harness (link:../workflow-dsl/07-loop-back-diagrams-verification.adoc#behavioural-conformance-harness[Workflow DSL Specification], `PM-TEST-6`) produces a per-client behavioural signal, and before the `codex` profile leaves provisional status. Any calibration axis added later is keyed by the resolved model of the effort ladder, never by the `client_id`, because one client hosts several models (the `opencode` ladder is unpinned and inherits the session model). Such an axis multiplies the rendered digests (`PM-SKILL-2`) and requires per-model content and a `PM-TEST-6` verdict for every model it distinguishes before it ships.

[#host-resident-surface-inventory]
=== Host-Resident Surface Inventory
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-3[PM-WATCH-CLIENT-3]_

For every built-in profile, the build derives and publishes the host-resident surface: the bytes the host injects into every turn by its registration mechanism (entry command descriptions, MCP tool schemas and descriptions when `schema_residency: resident`, and the `pm_skills` catalogue entries once loaded), per component and in total, together with the population it measured. Residency follows the actual injection mechanism, not file existence; the population is the served set for the profile (after domain filtering, `PM-SKILL-2`), not the set of files in the binary.

* *Derived Bounds*: Any length or shape bound on a description is derived from the measured distribution of the inventory and records that derivation; a build-time test enforces the bound.
* *Named Runtimes*: A description shape rule names the runtimes and models it was reasoned about; every runtime reads the descriptions byte-identically.

== Three-Tier Environment Detection Matrix & Mismatch Auditing
_See Requirement link:../../Requirements.adoc#PM-CLIENT-1[PM-CLIENT-1: Advisory Entry Identity Declaration & Persistence]_

_See Requirement link:../../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Three-Tier Environment Mismatch Detection & Audit]_

_See Requirement link:../../Requirements.adoc#PM-CLIENT-4[PM-CLIENT-4: Neutral Fallback Profile for Unknown Clients]_

Client identity is advisory routing and rendering metadata, never a security credential. To prevent silent profile corruption and provide full forensic visibility, PM-MCP evaluates and logs three independent identity tiers on every `pm-mcp enter` execution and every MCP tool request.

=== The Three Identity Tiers

* *Tier 1 — Declared Entry Identity (`declared_client`)*:
** Supplied explicitly via `pm-mcp enter --client <client_id> <plan|epic|workspace> [<plan_id>|<epic_id>] …` by the installed client bundle's entry command.
** Persisted as `client` in a new row of the scope's append-only session log `sessions.jsonl` (link:../store-schemas/01-format-and-session-log.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]) together with `client_session_id`, `client_detected`, `environment_match_tier`, the exact host build `client_build` (from the profile's version probe, <<host-identity-probes>>), the model identity (`model_family`, `model_id`, `model_source`), `pm_mcp_version`, `bundle_version`, `project_id`, `entered_from`, `first_seen_at`, `last_seen_at`, and `transcript_locator`. The current identity of a scope is its last row.
* *Tier 2 — Detected Environment & Protocol Signature (`detected_client`)*:
** *At Entry (`pm-mcp enter`)*: Evaluated by the runtime from the environment signature that `pm-mcp enter` computes from the process environment inherited from the host shell, against the detection signals and precedence of the <<host-integration-table>>.
** *At Tool Call (`stdio`)*: A job connection (a model job's relay `pm-mcp serve --job`) is not evaluated: it takes its profile from the job record and appends no session row (link:../mcp-tools/01-core-workflow-tools.adoc#job-bound-connections[MCP Tools Specification, Job-Bound Connections]). Every other request is evaluated from the relay's connection headers (link:../runtime-model.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]): `PM-MCP-Env-Signature`, computed by the relay from its inherited environment, and `PM-MCP-Client-Info`, the `clientInfo.name` and `clientInfo.version` of the host's `initialize` request as the relay recorded it (`absent` when omitted). The transport is sessionless: the runtime keeps no per-connection handshake state and derives Tier 2 from the headers of each request.
* *Tier 3 — Authenticated OS Principal (`os_principal`)*:
** The operating system effective user ID (`uid`) and username owning the local `pm-mcp` child process.

*Detection precedence*: Primary signals are evaluated in the fixed order `antigravity` -> `opencode` -> `claude` (the order `plan-marshall` uses, `script-shared/scripts/marketplace_paths.py` `detect_target_from_env`; because the signals are inherited, a host launched from inside another host is attributed by this fixed order, not necessarily to the innermost agent), then `codex` _(provisional)_; the first match wins. Secondary signals (`CLAUDECODE` _(provisional)_, `AI_AGENT`) are consulted only when no primary signal matches. At tool-call time the relay's environment signature and the connection's MCP `clientInfo.name` are evaluated per host connection (link:../runtime-model.adoc#_connection_metadata[Runtime & Interaction Model Specification]).

[#host-detection-table]
*Host-detection table (compiled, `pm-mcp-api`)*: The host-detection data, that is the environment signals and their precedence, the session ID variable, the version-probe argument vector with its pattern and model source, and the transcript locator, is one compiled, data-only table in `pm-mcp-api` (link:../module-structure.adoc#module-pm-mcp-api[Module Structure Specification, `pm-mcp-api`]). It is the single source: `pm-mcp enter` and the relay, which depend only on `pm-mcp-api`, read it directly, and the client profiles of `pm-mcp-core` take their `identity` object and their detection signals from it instead of repeating the values. Operator overrides do not touch it (xref:01-profile-schema.adoc#_profile_override_hierarchy[Profile Override Hierarchy]).

*Codex tool names*: The Codex columns of the placeholder table above are provisional; in particular Codex has no `write_file` tool and writes files through `apply_patch`, so `{{tool:write_file}}` resolves to `apply_patch` like `{{tool:edit_file}}`.

*OpenCode tool names*: The `opencode` column follows `plan-marshall`'s `marketplace/targets/opencode/mapping.json` (at `969cbfeb5`). Its entry `"Write": "edit"` sits under `tool_permissions` and names the OpenCode permission category that governs writing, not the tool: the file-create tool is `write`, so `{{tool:write_file}}` resolves to `write`. The column stays _(provisional)_ until Milestone 1 verifies it against the host.

[#session-lifecycle-hook]
== Session Lifecycle Hook & Scope Pointer
_See Requirement link:../../Requirements.adoc#PM-CLIENT-6[PM-CLIENT-6: Post-Compaction Scope Pointer]_

_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-4[PM-WATCH-CLIENT-4]_

After `/clear` or compaction the model has lost the `plan_id` it needs for `pm_state(plan_id)` (`PM-MIG-4`). The client bundle therefore carries a session-start hook on every profile whose Host Integration Table row names session lifecycle hook events: an owned `hook_entry` element in the host's settings file (xref:03-bundle-manifest.adoc#bundle-manifest-scopes[Bundle manifest scopes]), plus a `hook` file where the host needs one. The hook runs `pm-mcp hook session-start --client <client_id>` (link:../cli-and-security/01-cli-and-installer.adoc#session-start-hook[CLI, Coordination & Security Specification]) and injects its stdout verbatim. The verb reads persisted files only and never starts the runtime, so the hook works while no runtime runs; inside a model job (`PM_MCP_JOB_ID` set) it exits at once without output, like the entry commands.

* *Pointer, Never a Body*: The payload is a pointer: `scope_type`, `scope_id`, `phase`, and the literal next call (`pm_state(plan_id="…")`, `pm_state(epic_id="…")`, `pm_state(plan_id="NO_PLAN")`, or for a pending bootstrap entry `scope_type: entry`, the `entry_id`, the bootstrap state as `phase`, and `pm_state(plan_id="NO_PLAN", entity="<entry_id>")`), nothing else. It never carries facts, links, or state content, so it cannot go stale against the stores; an open question record of the scope is not part of it either, it is served by the `pm_state` call the pointer names.
* *Events*: The hook fires on the host events listed in the table's hook-event column, which cover `startup`, `resume`, `clear`, and `compact` where the host distinguishes them.
* *Size Ceiling*: The payload is at most 512 bytes UTF-8. The CLI never truncates it; an `*IT` test asserts the ceiling for the largest valid identifiers at build time.
* *Pending Bootstrap Entry*: A bootstrap interrupted by `/clear` or compaction before its scope exists is pointed at like a scope: the candidates are the live scopes and the pending entry records of the project, restricted to those matched on the host session id where the profile provides one, and the newest wins (a live scope by `last_seen_at`, a pending entry by `created_at`, a tie to the live scope; link:../cli-and-security/01-cli-and-installer.adoc#session-start-hook[CLI, Coordination & Security Specification]). The hook reads the record file only and never starts the daemon.
* *Three Normative Cases*: A live scope or pending entry bound to the workspace (and, where the profile provides one, to the host session id) yields the pointer; no bound scope yields empty output and exit `0`; an unreadable or tampered scope state yields a one-line notice naming the scope and `pm-mcp status`, exit `0`. The hook never fails the host session.
* *Pointer and Drift Notice*: The hook prints the pointer and, after it, the bundle drift notice for its client (link:../cli-and-security/01-cli-and-installer.adoc#bundle-drift-notice[CLI, Coordination & Security Specification, Bundle Drift Notice], `PM-DIST-4`). The two parts are independent: each is printed whenever its own condition holds, neither suppresses or alters the other, and the size ceiling above applies to the pointer.
* *Fallback Without Hooks*: On a host without lifecycle hooks, `pm_plans` and `pm_epics` mark the scope last entered by the request's host session (the `PM-MCP-Client-Session` header, matched against the `client_session_id` of the session rows, link:../runtime-model.adoc[Runtime & Interaction Model Specification], Connection Metadata; without a session id, the scope with the most recent session row in the project) in their `last_entered` column (link:../mcp-tools.adoc[MCP Tools Specification]).
