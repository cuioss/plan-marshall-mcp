== Embedded Client Bundle `bundle-manifest.json` Schema
_See Requirement link:../../Requirements.adoc#PM-DIST-1[PM-DIST-1: Single Version Authority & Embedded Client Bundles]_

_See Requirement link:../../Requirements.adoc#PM-DIST-2[PM-DIST-2: Embedded Bundle Extraction & Interactive Client Installer]_

_See Requirement link:../../Requirements.adoc#PM-DIST-3[PM-DIST-3: Uniform Host MCP STDIO Connection Configuration]_

_See Requirement link:../../Requirements.adoc#PM-DIST-4[PM-DIST-4: Bundle Upgrade Detection & Atomic Reconciliation]_

_See Requirement link:../../Requirements.adoc#PM-DIST-5[PM-DIST-5: Multi-Host Concurrent Coexistence on One Machine]_

_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-5[PM-WATCH-CLIENT-5]_

The runtime binary `pm-mcpd` embeds the templates for all supported client bundles under `classpath:/bundles/<client>/` (`claude`, `opencode`, `antigravity`, `codex`) and applies them on the requests of `pm-operator client install|update|remove` (link:../cli-and-security/01-cli-and-installer.adoc#client-installer[CLI, Coordination & Security Specification, Client Bundle Installer]); `pm-operator client status` needs no runtime and reads the install records directly. The bundle version is the release version, which every binary of a release carries: `pm-mcp` evaluates the drift checks of `pm-mcp enter` against its own, `pm-operator client status` against its own. The host MCP configuration of every bundle launches the relay as `pm-mcp serve --client <client>` (`PM-DIST-3`, `PM-CLIENT-1`). Multiple hosts (`claude`, `opencode`, `antigravity`, `codex`) can be installed and operated concurrently on the same machine and repository (`PM-DIST-5`).

[#bundle-manifest-scopes]
*One manifest per client, two scopes*: A client has exactly one manifest. Files that both scopes install (entry commands and skills, the shim skill) are declared once in `files[]` and placed through the scope's `directories` map; the `scopes` object holds a `user` and a `project` section, each with its target root, its `directories`, its `shared_configs[]` (host configuration files with owned keys and owned elements), and the files that only that scope installs (`files[]` inside the section, with a `target_path` relative to the target root). `pm-operator client install --scope <scope>` selects one section; a host that supports only one scope declares only that section. `pm-operator client install|update --scope project` refuses while the project has non-terminal plans or epics and names them; the `user` scope is unaffected (link:../cli-and-security/01-cli-and-installer.adoc#client-installer[CLI, Coordination & Security Specification, Client Bundle Installer]). The install record stores the scope (link:../store-schemas/12-machine-stores.adoc#machine-state-records[Store Schemas Specification, Machine State Records]).

*Owned elements*: Besides owned keys (a whole value at a dotted key path, such as the MCP server entry), a shared configuration owns individual elements of arrays that other parties share, identified by their exact normalized value:

* `permission_rule`: a host permission rule in the host's `deny`, `ask`, or `allow` list, classed `enforcement` (a defense-in-depth boundary whose removal or weakening is operator-gated, link:../cli-and-security/01-cli-and-installer.adoc#client-operator-gate[CLI, Coordination & Security Specification, Operator Gate]) or `convenience`. The normalized value is the rendered rule text (placeholders `{pm_mcp_base}` and `{home}` resolved, surrounding whitespace removed). A rule template naming `{pm_mcp_base}` renders to one owned element per path form of the host's rule syntax: for `claude` always the absolute form (`Read(//<abs>/**)`, `Edit(//<abs>/**)`) and, when `<PM_MCP_BASE>` lies under `{home}`, additionally the home-relative form (`Read(~/<rel>/**)`, `Edit(~/<rel>/**)`, `<rel>` relative to `{home}`).

A rule that names a machine path (the `<PM_MCP_BASE>/**` deny rules) is never written into a team-shared, git-tracked file: in the `project` scope it goes to the host's machine-local project settings file (for `claude`, `.claude/settings.local.json`), so the shared files keep zero user-specific paths (`PM-DIST-2`).

[#bundle-content]
=== Bundle Content per Host
_See Requirement link:../../Requirements.adoc#PM-SKILL-4[PM-SKILL-4: Skill Delivery to Workers & State through Representations]_

A client bundle carries what the entry session needs and nothing for workers, whose launch the runtime composes per worker from the role artifact and the client profile (xref:01-profile-schema.adoc#headless-block[Client Profile Schema, `headless`]). Every bundle installs exactly:

* *Entry commands*: the three `mcp-` prefixed entry commands in the host's command form (`kind: command`), or as skills on a host whose entry commands are skills (`kind: entry_skill`, `$mcp-…` on `codex`). Each runs `pm-mcp enter` and exits at once inside a worker (`PM_MCP_JOB_ID` set).
* *MCP configuration*: the owned key of the relay, `pm-mcp serve --client <client>`, in the host's MCP configuration file of each scope (xref:02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table]). Antigravity has one global MCP entry and no project-scope MCP configuration, so its bundle writes the entry in the `user` scope only; its relay still reads its identity from the environment, which Antigravity passes to the `stdio` server it starts.
* *Permission rules*: the recommended rules below, on every host with permission rules.
* [[shim-skill]]*Shim skill*: the skill `mcp-plan-marshall-skills` (`kind: shim_skill`) in the host's own skill format and skill directory of each scope (xref:02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table]: `.claude/skills/`, `.opencode/skills/`, and `.agents/skills/` for Antigravity's workspace). Its text is the shim paragraph that every server-composed launch prompt also carries (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]): skills of `plan-marshall` arrive in-band or are named by a `skill://pm/` URI; a named skill is binding and is read through `pm_skill`; a skill is never reconstructed from memory, and a skill of the same name from elsewhere does not replace it. The shim chooses no skills. It covers a clear or compaction the host does not report to the relay. A host whose profile records verified support of the MCP Skills Extension (`skill_loading.skills_extension: true`, xref:01-profile-schema.adoc#_normative_client_profile_json_schema[Client Profile Schema]) gets no shim in its next bundle.

A bundle installs no lifecycle hook, no agent file, and no executor; the host's settings file is touched only at the owned permission elements.

The settings file names and rule forms of the `claude` example are established Claude Code conventions; the corresponding values of the other hosts are _(provisional)_ like their other host facts and are verified in Milestone 0.

[#recommended-permission-rules]
*Recommended permission rules*: On every host with permission rules, each scope's bundle installs as `enforcement` rules the machine root deny rules (Ownership & Digest Verification, item 5) and one deny rule for the whole operator binary `pm-operator` (`Bash(pm-operator:*)`), rendered in the host's rule syntax and placed in its `ask` list where the host has no `deny` list. The rule covers every verb of `pm-operator`, including `web`, `client`, `runtime`, `drain` and `status`; no rule names a sub-command, and the relay binary `pm-mcp` (`serve`, `enter`) stays allowed, because the host and the model's session run it. The rules keep a model-driven shell from running operator verbs through the host's shell tool by accident; they are defense in depth only, since the operator proof rests on the checks of `pm-operator` (link:../cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation], link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).

=== Ownership & Digest Verification on Install/Update/Remove
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-7[PM-WATCH-CLIENT-7], link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-9[PM-WATCH-CLIENT-9], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-12[PM-WATCH-CLI-12]_

1. *Install Record Persistence (`PM-DIST-2`, `PM-DIST-4`)*: When `pm-operator client install` or `update` applies a manifest, the runtime records per `(client, scope, target root)` the installed `bundle_version`, the `scope`, the absolute target root, the `sha256` of every written file and owned key value, and every owned element with its normalized value and its `sha256` in `<PM_MCP_BASE>/state/install-records.json` (link:../store-schemas/12-machine-stores.adoc#machine-state-records[Store Schemas Specification]).
2. *Modification Conflict Protection (`PM-DIST-4`)*: During `pm-operator client update` or `remove`, before overwriting or deleting any recorded file or owned key, the runtime computes the current on-disk SHA-256 and compares it with the recorded `sha256`; a recorded owned element is unmodified only while an element with its recorded normalized value is present in its array. A modified entry (digest mismatch, or an element edited or deleted by the user) is skipped and reported on the terminal, and the user's change is preserved unless `--force` is confirmed interactively.
3. *Surgical Shared Configuration Merging (`PM-DIST-3`, `PM-DIST-5`)*: For `shared_configs[]`, the runtime parses the existing JSON/TOML file and changes *only* the keys listed in `owned_keys` and the recorded owned elements: `install` appends a missing owned element (one already present with the same normalized value is neither duplicated nor recorded as owned), `update` replaces the recorded elements and appends new ones, and `remove` deletes the recorded elements only. All other MCP servers, hooks, rules, and settings owned by the user or by sibling AI host installations are preserved, including their order.
4. *Permission Rule Grammar (`PM-DIST-2`, `PM-CRED-3`)*: `pm-operator client install` and `update` refuse to render a host permission rule with a non-terminal `*` and refuse a deny rule for a path containing whitespace (such a path cannot be protected by a deny rule), reporting the credential-directory rule they could not install. The rule grammar check has one implementation, shared by the build-time bundle manifest tests and the installer.
5. *Machine Root Deny Rules (`PM-CRED-3`, `PM-SEC-2`)*: On every host with file-tool permission rules, the bundle installs deny rules for `<PM_MCP_BASE>/**` as `enforcement` `permission_rule` elements in addition to the credential rules, in the absolute form and, when `<PM_MCP_BASE>` lies under the home directory, also in the home-relative form (<<bundle-manifest-scopes,Owned elements>>), so host file tools cannot read or write the enrolment files `enrolments/`, `state/`, `run/` (the runtime token), or the fallback credential store. This is defense in depth only: a host shell tool bypasses it, and no `Bash` rule tries to cover shell access vectors to `<PM_MCP_BASE>`; enrolment integrity rests on the runtime's HMAC verification (link:../cli-and-security.adoc[CLI, Coordination & Security Specification]). If `<PM_MCP_BASE>` contains whitespace, the installer refuses under item 4.
6. *Side-by-Side with Legacy `plan-marshall` (`PM-MIG-2`, `PM-DIST-5`)*: A bundle installs no `plan-marshall` executor, no `execute-script.py` permission rule, and never edits, removes, or takes over artifacts or permission rules of an installed `plan-marshall` plugin. Its command and skill names and its owned configuration keys are distinct from the `plan-marshall` plugin's: the command and entry-skill files are named after the `mcp-` prefixed entry commands (`mcp-plan-marshall`, `mcp-plan-orchestrator`, `mcp-marshall-steward`; xref:02-placeholders-and-detection.adoc#entry-command-prefix[Placeholders & Detection, entry command prefix]) and the shim skill is `mcp-plan-marshall-skills`; it installs no agent file, since workers compose their agent per launch (xref:01-profile-schema.adoc#headless-block[Client Profile Schema, `headless`]); a build-time bundle manifest test fails on a name that collides with the `plan-marshall` plugin's installed names. Both may therefore be installed on one machine and used in the same repository.
7. *Drift Checks (`PM-DIST-4`)*: `bundle_outdated` compares the recorded `bundle_version` with the release version of the evaluating binary (every binary of a release carries the release version, which is the bundle version): `pm-mcp` evaluates it against its own in `enter`, `pm-operator client status` against its own; `bundle_modified` compares the recorded digests and normalized values with the disk and lists the edited and missing entries. Both are reported by `pm-mcp enter` and `pm-operator client status`, and fixed by `pm-operator client update` (`--force` for modified entries) (link:../cli-and-security/01-cli-and-installer.adoc#bundle-drift-notice[CLI, Coordination & Security Specification, Bundle Drift Notice]).
