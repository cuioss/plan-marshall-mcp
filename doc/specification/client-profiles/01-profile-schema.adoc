== Normative Client Profile JSON Schema
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-8[PM-WATCH-CLIENT-8]_

_See Requirement link:../../Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy]_

_See Requirement link:../../Requirements.adoc#PM-TOOL-5[PM-TOOL-5: Tool Schema Stability & Context Budget Discipline]_

_See Requirement link:../../Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Slots & Usage per Task]_

A client profile is the one configuration document of a harness: `classpath:/profiles/<client_id>.json`, a resource of `pm-api` (`claude.json`, `opencode.json`, `antigravity.json`, `codex.json`, `neutral.json`). Everything the system knows about a harness is in its profile and nowhere else (<<harness-as-data>>). Every profile is validated against the following JSON Schema (Draft 2020-12):

[#harness-as-data]
=== The Profile Is the Harness

_See Requirement link:../../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

A harness exists for the system as its profile document and as nothing else. The code reads profiles through one generic reader and holds no harness by name: no constant, no `switch`, no class, and no test fixture of production code names `claude`, `opencode`, or any other client. What the code implements are the mechanisms the schema names (a slot, a delivery mode, a signal match, a class with an enforced or an advisory tool set); which of them a harness uses is data.

* *One document, two readers*: the documents are resources of `pm-api`. Its reader parses the `detection` and `identity` objects with the streaming API of `jackson-core` and skips the rest; these two objects of all profiles are the host-detection table (xref:02-placeholders-and-detection.adoc#host-detection-table[Host-Detection Table]) that `pm-mcp` and `pm-operator` use. The profile loader of `pm-core` reads the whole document from the same resource and validates it against the schema above.
* *A new or changed harness is a changed document*: a new harness is a new profile; a new measurement, a new harness version, or a corrected value is a change of its profile, with the evidence in the link:../evaluation.adoc[Evaluation Reference]. Neither needs a change of Java code, as long as the harness needs no mechanism the schema lacks; a new mechanism is a change of the schema and of the reader, made once for all harnesses.
* *Validation*: profile validation runs when the runtime loads the profiles and as a build test over every shipped profile. Beside the schema it checks that `client_id` equals the file name, that the `detection.precedence` values are pairwise different, and the rules stated with each block below. A profile that fails is refused as a whole, with the document and the JSON Pointer of the failing value; the runtime never runs on a part of a profile.
* *Unknown values fail closed*: a profile value the reader does not know (a delivery mode, a capability, a tool-set kind of a newer schema) refuses the profile; it is never ignored.

[#role-classes]
=== Role Classes of a Harness

`headless.classes` states, per role class, whether the harness can run it and how far it holds a worker to the tools of its role.

* *The screener needs a harness without tools*: `zero_tool` is the class of the screener and the judge, which read untrusted or ungraded text (link:../model-work/07-untrusted-text-screening.adoc#screener[Model Work Specification, Screener]). It is the one class for which the harness must restrict the worker, and the restriction is total: no tool, no MCP connection, project and user settings off. A harness that cannot be started that way declares `zero_tool: null`, and no screener or judge role may name it. This is the only class restriction the system depends on.
* *For the other classes a restriction is welcome and not required*: `writer` and `read_only` workers act on text that has passed the screener, inside the confinement of the job launcher, and the server limits what they can reach of `PM-MCP` on every request (link:../model-work/04-worker-launch.adoc#job-tool-sets[Model Work Specification, Tool Sets]). `tool_set: enforced` means the harness also limits the worker to the tools of its role; `tool_set: advisory` means it cannot, the worker runs with every tool of the harness, and the role's tool set only tells it which to use. Both are runnable. `pm-operator roles show <role>` reports an advisory tool set, so the operator sees which roles run unrestricted.

[#headless-block]
`headless` is the harness's launch contract for workers; the host never starts a sub-agent. How the server composes a worker's launch from the role artifact and this block, the tool sets of the role classes (`writer`, `read_only`, `zero_tool`), the composition per `agent_mode`, the harness enrolment, and the working directory are specified in link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]. A role artifact of a class its harness cannot run (<<role-classes>>) is invalid on load and counts as undefined (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]). Only `neutral` declares `headless: null`. Values the evaluation did not measure stay _(provisional)_ like the other host facts.

[#headless-usage]
*Usage pointers*: Usage and cost are read from the harness output through `headless.usage`, never asked from a model. Each pointer fills the column of the same name in the task's metrics row (link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]), with two exceptions: `cache_read` fills `cache_read_input_tokens` and `cache_creation` fills `cache_creation_input_tokens`. `headless.usage` has no pointer for the total: `total_tokens` is derived from the four token components. The same per-turn figures give the supervisor a warm worker's context size for its token budget (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]).

[#headless-writable-paths]
*Writable paths*: `headless.writable_paths` extends only the Landlock write set of workers. It lists the sub-paths a headless harness must write to run: its login or credential file, its caches, its session directory, and its own state file. Profile validation refuses an entry that equals, contains, or lies inside a settings, command, or skill file or directory the client's bundle manifest manages, and any shared configuration file in which the bundle owns an `enforcement` element (xref:03-bundle-manifest.adoc[Bundle Manifest]), so a harness home as a whole (`~/.claude`) is never an entry and a worker cannot rewrite the host's deny rules, the entry commands, or the shim skill. The operator's own session and the bundle installer, which runs in `pm-mcpd`, are not restricted by it. The compiled entries:

[[claude-state-file]]*The `claude` state file*: `~/.claude.json` holds the harness's own state, which a headless run rewrites, together with the user-scope MCP registration the bundle owns as one key (`mcpServers.plan-marshall`). It is the one shared configuration file among the writable paths: the bundle owns no `enforcement` element in it, a worker's own MCP configuration is the per-call one of its launch (`--strict-mcp-config`), and a change of the owned key is reported as `bundle_modified` by the bundle drift check at the next `pm-mcp enter` and by `pm-operator client status` (xref:03-bundle-manifest.adoc[Bundle Manifest], Drift Checks). That a worker can change this one key until the drift check reports it is accepted: the file stays in the write set, because the harness cannot run headless without rewriting it. _Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-8[PM-WATCH-CLIENT-8]_

[[headless-data-home]]*Per-worker data home*: `headless.data_home` is declared for a harness whose local state is one per-user store that all its processes share, so that a stalled worker cannot hold that store's lock against every other worker and against the operator's own sessions. `opencode` declares `{"variable": "XDG_DATA_HOME", "login_file": "opencode/auth.json"}`: every worker gets its own data directory below its job-private directory, with the harness's login file copied in, and the directory is removed when the job settles (link:../job-runtime/02-confinement-and-environment.adoc#worker-data-home[Job Runtime Specification, Per-Worker Data Home]). Profile validation refuses a `variable` that matches a credential pattern or that the job environment already sets. `claude` and `codex` declare `null`. _Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-60[PM-WATCH-DISP-60]_

[[headless-tool-result-limit]]*Tool-result limit*: `headless.tool_result_limit_chars` is the largest tool result the harness passes to its model whole. A harness that cuts a larger result keeps the full text where a worker restricted to the server's tools cannot read it, so the worker would lose the task's identifiers. The server therefore returns no tool result above the limit to a worker of that harness: identifiers and links come first, and the remaining content is named as parts below the limit, read through the harness's resource tools (link:../model-work/02-task-protocol.adoc#offer[Model Work Specification, Offer]; value and basis: link:../timeouts/03-retention-host-config.adoc#tool-result-limit[Timeouts & Budgets Specification, Harness Tool-Result Limit]). `opencode` declares the provisional `32000`, `claude` `null`. Profile validation refuses a non-null limit on a profile without `resource_tools`. _Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-12[PM-WATCH-CLIENT-12]_

*No harness credentials*: `PM-MCP` never stores or exports a harness's authentication, and a profile declares no authentication variable. The harness CLI must already be logged in by its own login, cached under its home; a harness that is not logged in fails its worker's start (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, start failures]).

*Resource tools*: `headless.resource_tools` names the harness's tools that list and read MCP resources (a harness may have one tool for each). They enter the tool allowlist of the `writer` and `read_only` classes, never of `zero_tool`, because `resources/read` and `resources/list` work on a job connection (link:../mcp-tools/01-core-workflow-tools.adoc#job-bound-connections[MCP Tools Specification, Job-Bound Connections]).

`connection.idle_timeout_seconds`, `connection.bounded_wait_seconds`, and `connection.progress_resets_timeout` are the host's timing facts; their bounds and the rule relating the bounded wait to the host idle timeout (enforced by profile validation for the compiled profile and every override) are defined in link:../timeouts/03-retention-host-config.adoc#host-integration[Timeouts & Budgets Specification, Host Integration] and link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Bounded Wait Window]; the compiled values are listed in <<worker-block>>. Whether a host answers MCP elicitation is not a profile fact: it is taken from the capabilities the calling connection declared (link:../runtime-model.adoc[Runtime & Interaction Model Specification, Connection Metadata]), which are authoritative.

Rules of the block, checked by profile validation:

* *Eligibility*: `eligible: true` requires a non-null `headless` block. A host is eligible only after its worker behaviour has been measured on it under the target conditions (the real relay, confined writer workers) and every fault of the fault matrix passed (link:../../Requirements.adoc#PM-TEST-4[PM-TEST-4]; exit detection within the link:../timeouts/01-job-budgets-and-waits.adoc#exit-detection-bound[exit detection bound]). `claude` is eligible. `opencode` is eligible with its per-worker data home (<<headless-data-home>>), without which a stalled worker blocks every other process of the harness, and with its tool-result limit (<<headless-tool-result-limit>>); Antigravity (its fault matrix passed only as a smoke run with unconfined workers), Codex (not measured), and `neutral` are not eligible. The operator assigns the roles of an ineligible host to an eligible harness. A role artifact naming a harness that is not eligible is invalid (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]).
* *Session tasks*: `session_tasks: true` requires `eligible: true`. `opencode` declares `false`: its session keeps the whole task loop in one turn, answers the operator only after the loop, and keeps an earlier loop running after `/new` (link:../evaluation.adoc#limits[Evaluation Reference, Limits]); the two loops share one relay and cannot be told apart (link:../runtime-model/03-relay.adoc[Runtime & Interaction Model Specification, Relay]).
* *Restricted models*: a worker of a class whose `tool_set` is `enforced` runs with a restricted tool set, so a model that refuses a restricted agent cannot host one. An entry `*` stands for every model of the harness, an entry `<provider>/*` for every model of that provider. The free OpenCode models refuse a restricted agent and are not listed; of the OpenCode Go models only the measured `opencode-go/muse-spark-1.3-contributor` is listed (link:../evaluation.adoc[Evaluation Reference]), and another one is listed once it is measured.
* *Informational acknowledgement*: with `ack_informational: true`, `ack_deadline_seconds` equals the silence limit, `connection.bounded_wait_seconds` plus `silence_grace_seconds` (`240 + 30 = 270` measured on `opencode`, where a provider stall of 120.8 s left a live worker's task unacknowledged), and a missing acknowledgement ends no worker: silence alone decides. The supervisor applies the silence limit of the effective connection values, so an operator override of the bounded wait moves both.
* *Bounded wait and idle timeout*: on a host whose progress resets its timeout, a worker's `pm_wait` is always held with progress frames, so its bounded wait may exceed the host idle timeout (`opencode`: `240` against `60`); on any other host the bounded wait stays below the idle timeout by the margin of link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Timeouts & Budgets Specification, Bounded Wait Window].
* *Host markers*: `host_markers` lists only marker kinds verified on the host; every shipped profile has none yet, so a clear or compaction stays invisible to the runtime and the shim covers it (link:../runtime-model/03-relay.adoc[Runtime & Interaction Model Specification, Relay]).
* *Values of an ineligible host*: while `eligible` is `false`, no other value of the block has an effect, and each except `session_tasks` and `host_markers` is `null` unless it was measured on the host; the extrapolated Antigravity values of the evaluation are entered only once they are measured.
* *A worker that does not continue*: an `opencode` process stopped while a model request is open may never continue after it is resumed, and the harness sets no timeout on that request. The supervisor ends such a worker by silence at its silence limit and never earlier (link:../model-work/03-supervision-and-recycling.adoc#detection[Model Work Specification, Detection]), so the limitation costs one silence limit before the task is offered again; it does not affect eligibility.

The relay and the server need no other host value for workers: identity, role, and generation travel in the worker's environment, never in the profile (link:../runtime-model.adoc[Runtime & Interaction Model Specification, Relay]).

=== Profile Override Hierarchy

The runtime resolves a client profile by merging two layers in order of increasing precedence:

1. *Compiled Binary Baseline* (`classpath:/profiles/<client_id>.json`): The profile documents compiled into the binaries (<<harness-as-data>>).
2. *Machine-Wide Operator Overrides* (`machine-config.json`, the closed object `client_profiles.<client_id>.connection`, link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration]): Optional override of the connection settings `bounded_wait_seconds`, `idle_timeout_seconds`, and `progress_resets_timeout` across all repositories on the workstation, set with `pm-operator config`. No other profile key can be overridden: the `worker` block, the `headless` block, and the `detection` and `identity` objects that form the host-detection table (xref:02-placeholders-and-detection.adoc#host-detection-table[Host-Detection Table]) are never touched by an override.

Harness, model, and effort of a worker come only from its role artifact (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]), an operator file, rendered into the `{{model}}` and `{{effort}}` slots of `headless`; a profile carries no model choice. A change of a role artifact applies to the next worker of the role; nothing is re-installed. No git-tracked configuration carries client profile overrides, role sets, or model pins (`PM-WORK-1`, `PM-EXT-6`); the closed team schemas admit no such key, so a `client_profiles` block in a team file is the finding `unknown_config_key` (`config_invalid`).
