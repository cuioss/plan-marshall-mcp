[#headless-block]
`headless` is the harness's launch contract for workers; the host never starts a sub-agent. How the server composes a worker's launch from the role artifact and this block, which capabilities each role class (`writer`, `read_only`, `zero_tool`) needs, the composition per `agent_mode`, the harness enrolment, and the working directory are specified in link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]. A role artifact whose harness lacks a capability its class needs is invalid on load and counts as undefined (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]). `antigravity` (one global MCP entry, no per-call MCP configuration) and `neutral` declare `headless: null`. Values the evaluation did not measure stay _(provisional)_ like the other host facts.

[#headless-usage]
*Usage pointers*: Usage and cost are read from the harness output through `headless.usage`, never asked from a model. Each pointer fills the column of the same name in the task's metrics row (link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]), with two exceptions: `cache_read` fills `cache_read_input_tokens` and `cache_creation` fills `cache_creation_input_tokens`. `headless.usage` has no pointer for the total: `total_tokens` is derived from the four token components. The same per-turn figures give the supervisor a warm worker's context size for its token budget (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]).

[#headless-writable-paths]
*Writable paths*: `headless.writable_paths` extends only the Landlock write set of workers. It lists the sub-paths a headless harness must write to run: its login or credential file, its caches, and its session directory (for example `~/.claude/.credentials.json` and `~/.claude/projects` for `claude`, `~/.codex/auth.json` and `~/.codex/sessions` for `codex`; _(provisional)_ until verified with writer workers in confinement). Profile validation refuses an entry that equals, contains, or lies inside a file or directory the client's bundle manifest manages (settings, command, skill, and MCP registration files, xref:03-bundle-manifest.adoc[Bundle Manifest]), so a harness home as a whole (`~/.claude`) is never an entry and a worker cannot rewrite the host's deny rules or the shim skill. The operator's own session and the bundle installer, which runs in `pm-mcpd`, are not restricted by it.

*No harness credentials*: `PM-MCP` never stores or exports a harness's authentication, and a profile declares no authentication variable. The harness CLI must already be logged in by its own login, cached under its home; a harness that is not logged in fails its worker's start (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, start failures]).

*Resource tools*: `headless.resource_tools` names the harness's tools that list and read MCP resources (a harness may have one tool for each). They enter the tool allowlist of the `writer` and `read_only` classes, never of `zero_tool`, because `resources/read` and `resources/list` work on a job connection (link:../mcp-tools/01-core-workflow-tools.adoc#job-bound-connections[MCP Tools Specification, Job-Bound Connections]).

`connection.idle_timeout_seconds`, `connection.bounded_wait_seconds`, and `connection.progress_resets_timeout` are the host's timing facts; their bounds and the rule relating the bounded wait to the host idle timeout (enforced by profile validation for the compiled profile and every override) are defined in link:../timeouts/03-retention-host-config.adoc#host-integration[Timeouts & Budgets Specification, Host Integration] and link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Bounded Wait Window]; the compiled values are listed in <<worker-block>>. Whether a host answers MCP elicitation is not a profile fact: it is taken from the capabilities the calling connection declared (link:../runtime-model.adoc[Runtime & Interaction Model Specification, Connection Metadata]), which are authoritative.

=== Worker Block
_See Requirement link:../../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

_See Requirement link:../../Requirements.adoc#PM-WORK-3[PM-WORK-3: Supervision & Recycling]_

_See Requirement link:../../Requirements.adoc#PM-WORK-5[PM-WORK-5: Interactive Session as Optional Worker]_

The `worker` block holds the per-host values of the task protocol and of supervision. The supervisor, the task protocol, and the session's optional tasks read them from the profile of the worker's harness, which its role names (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol], link:../model-work/03-supervision-and-recycling.adoc[Supervision & Recycling]); the token budget and the other recycling rules come from the role artifact (link:../model-work/01-roles-and-configuration.adoc[Roles & Configuration]). The compiled values below are the measured ones (link:../evaluation.adoc#parameters[Evaluation Reference, Substantiated Values]):

|`worker.session_tasks` |`true` |`false` |`false` |`false` |`false`
|`worker.restricted_models` |`["*"]` |`["space-bunny-free", "opencode-go/*"]` |`null` |`null` |`null`
|`worker.ack_deadline_seconds` |`15` |`270` |`null` |`null` |`null`
|`worker.ack_informational` |`false` |`true` |`null` |`null` |`null`
|`worker.silence_grace_seconds` |`30` |`30` |`null` |`null` |`null`
|`worker.idle_wakeups` |`3` |`3` |`null` |`null` |`null`
|`worker.host_markers` |`[]` |`[]` |`[]` |`[]` |`[]`

Rules of the block, checked by profile validation:

* *Eligibility*: `eligible: true` requires a non-null `headless` block. A host is eligible only after its worker behaviour has been measured on it: Antigravity (measured only in part), Codex (not measured), and `neutral` are not eligible, and the operator assigns their roles to an eligible harness. A role artifact naming a harness that is not eligible is invalid (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]).
* *Session tasks*: `session_tasks: true` requires `eligible: true`. `opencode` declares `false`: its session keeps the whole task loop in one turn, answers the operator only after the loop, and keeps an earlier loop running after `/new` (link:../evaluation.adoc#limits[Evaluation Reference, Limits]); the two loops share one relay and cannot be told apart (link:../runtime-model/03-relay.adoc[Runtime & Interaction Model Specification, Relay]).
* *Restricted models*: a worker always runs with a restricted tool set, so a model that refuses a restricted agent cannot host one. An entry `*` stands for every model of the harness, an entry `<provider>/*` for every model of that provider. The free OpenCode models other than `space-bunny-free` refuse a restricted agent and are not listed; the OpenCode Go models accept one.
* *Informational acknowledgement*: with `ack_informational: true`, `ack_deadline_seconds` equals the silence limit, `connection.bounded_wait_seconds` plus `silence_grace_seconds` (`240 + 30 = 270` on `opencode`, where a provider stall of 120.8 s left a live worker's task unacknowledged), and a missing acknowledgement ends no worker: silence alone decides. The supervisor applies the silence limit of the effective connection values, so an operator override of the bounded wait moves both.
* *Bounded wait and idle timeout*: on a host whose progress resets its timeout, a worker's `pm_wait` is always held with progress frames, so its bounded wait may exceed the host idle timeout (`opencode`: `240` against `60`); on any other host the bounded wait stays below the idle timeout by the margin of link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Timeouts & Budgets Specification, Bounded Wait Window].
* *Host markers*: `host_markers` lists only marker kinds verified on the host; every shipped profile has none yet, so a clear or compaction stays invisible to the runtime and the shim covers it (link:../runtime-model/03-relay.adoc[Runtime & Interaction Model Specification, Relay]).
* *Values of an ineligible host*: while `eligible` is `false`, every other value of the block except `session_tasks` and `host_markers` is `null`; the extrapolated Antigravity values of the evaluation are entered only once they are measured.

The relay and the server need no other host value for workers: identity, role, and generation travel in the worker's environment, never in the profile (link:../runtime-model.adoc[Runtime & Interaction Model Specification, Relay]).

=== Profile Override Hierarchy

The runtime resolves a client profile by merging two layers in order of increasing precedence:

1. *Compiled Binary Baseline* (`classpath:/profiles/<client_id>.json`): Authoritative defaults compiled into the runtime binary (`pm-mcpd`).
2. *Machine-Wide Operator Overrides* (`machine-config.json`, the closed object `client_profiles.<client_id>.connection`, link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration]): Optional override of the connection settings `bounded_wait_seconds`, `idle_timeout_seconds`, and `progress_resets_timeout` across all repositories on the workstation, set with `pm-operator config`. No other profile key can be overridden: the `worker` block, the `headless` block, and the compiled host-detection table (xref:02-placeholders-and-detection.adoc#host-detection-table[Host-Detection Table]) are never touched by an override.

Harness, model, and effort of a worker come only from its role artifact (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]), an operator file, rendered into the `{{model}}` and `{{effort}}` slots of `headless`; a profile carries no model choice. A change of a role artifact applies to the next worker of the role; nothing is re-installed. No git-tracked configuration carries client profile overrides, role sets, or model pins (`PM-WORK-1`, `PM-EXT-6`); the closed team schemas admit no such key, so a `client_profiles` block in a team file is the finding `unknown_config_key` (`config_invalid`).
