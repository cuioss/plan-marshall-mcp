== Normative Client Profile JSON Schema
_See Requirement link:../../Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy]_

_See Requirement link:../../Requirements.adoc#PM-TOOL-5[PM-TOOL-5: Tool Schema Stability & Context Budget Discipline]_

_See Requirement link:../../Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Job Accounting & Effort Role Resolution]_

Client profiles are declarative JSON documents compiled into `pm-mcp-core` under `classpath:/profiles/<client_id>.json` (`claude.json`, `opencode.json`, `antigravity.json`, `codex.json`, `neutral.json`) and validated against the following JSON Schema (Draft 2020-12):

[#headless-block]
`headless` is the harness's launch contract for model jobs; the host never starts a sub-agent. How the server selects the harness, which capabilities each job class (`writer`, `read_only`, `zero_tool`) needs, the support rule (`precondition_unmet` naming the missing capability and `model_jobs.harness`, no inline fallback in the main session), the composition per `agent_mode`, the harness enrolment, and the working directory are specified in link:../dispatch-and-effort/05-model-job-launch.adoc#model-job-launch[Model Jobs & Effort Specification, Model Job Launch]. `antigravity` (no per-call MCP, system prompt, or tool allowlist) and `neutral` declare `headless: null` and run no model jobs in v1. Usage and cost are read from the harness output through `headless.usage`, never asked from a model. Every value is _(provisional)_ like the other host facts and verified per harness in the Milestone 1 host spikes.

`connection.idle_timeout_seconds`, `connection.bounded_wait_seconds`, and `connection.progress_resets_timeout` are the host's timing facts; their values, the rule that keeps the bounded wait below the host idle timeout (enforced by profile validation for the compiled profile and every override), and their Milestone 1 verification are defined in link:../timeouts/03-retention-host-config.adoc#host-integration[Timeouts & Budgets Specification, Host Integration] and link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Bounded Wait Window]. Whether a host answers MCP elicitation is not a profile fact: it is taken from the capabilities the calling connection declared in its `initialize` request (link:../runtime-model.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]), which are authoritative.

=== Profile Override Hierarchy

At runtime, `pm-mcp` resolves a client profile by merging two layers in order of increasing precedence:

1. *Compiled Binary Baseline* (`classpath:/profiles/<client_id>.json`): Authoritative defaults compiled into the runtime binary (`pm-mcpd`).
2. *Machine-Wide Operator Overrides* (`<PM_MCP_BASE>/conf/profiles/<client_id>.json`): Optional partial JSON override allowing the operator to customize connection settings such as `connection.bounded_wait_seconds` across all repositories on the workstation. Model pins are not overridden here.

Model pins are resolved separately from the machine-local effort ladder (`effort_ladder` of the operator file `<PM_MCP_BASE>/projects/<project_id>/local-config.json`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), with the profile's `models` as compiled default (link:../dispatch-and-effort.adoc[Model Jobs & Effort Specification]); a model job resolves its role to a level and the level to the ladder entry of its harness, rendered into the `{{model}}` and `{{effort}}` slots of `headless`, and an operator model for the role (`model_jobs.roles.<role>.model` in `local-config.json`) replaces the ladder's model. A ladder change applies to the next job; nothing is re-installed. No git-tracked configuration carries client profile overrides or model pins (ADR-021); the closed team schemas admit no such key, so a `client_profiles` block in a team file is the finding `unknown_config_key` (`config_invalid`).
