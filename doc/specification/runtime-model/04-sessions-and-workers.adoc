== Server-Driven Scopes
_See Requirement link:../../Requirements.adoc#PM-ARCH-8[PM-ARCH-8: Server-Driven Continuation & Connection Independence]_

A scope is identified by its `plan_id` (or `epic_id`, or the project's workspace scope, addressed by the reserved `plan_id` value `NO_PLAN`) and consists of its persisted files (`sessions.jsonl` with the entry rows, `status.json`, and the stores in link:../store-schemas.adoc[Store Schemas Specification]). Nothing else carries workflow state: not a host conversation, not a relay, not a worker, not the MCP transport, and not runtime memory, which is a cache that is revalidated against the files (`PM-ARCH-6`).

The runtime drives every plan and epic from its creation to a terminal state itself (`PM-ARCH-1`). It advances a scope on transitions and on engine events (a job's completion, a task's outcome, a deadline, an observed provider state), never because a connection calls. A state that needs no model is server logic; a state that needs a model puts a task of the role it names into the project's task queue, which a worker of that role, or the entry session as an optional worker, does along the links of the task's entity (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). An epic starts its launchable plans itself (link:../model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]). A plan or epic representation is therefore a view: its `links` list is empty, apart from the answer links of its open question records (`PM-WF-1`).

=== Entry Session
_See Requirement link:../../Requirements.adoc#PM-WORK-5[PM-WORK-5: Interactive Session as Optional Worker]_

The entry session is the host session that runs an entry command. Its relay is `pm-mcp serve --client <client>`, and its tool surface is the session surface (link:../mcp-tools/01-core-workflow-tools.adoc[MCP Tools Specification, Session and Worker Surfaces]). It does exactly this:

* *Entry*: `pm-mcp enter` records the entry row, issues the session's generation, and opens a pending bootstrap entry or names the live scope (link:../cli-and-security/01-cli-and-installer.adoc#_entry_identity_recording_pm_mcp_enter[CLI, Coordination & Security Specification, Entry Identity Recording]). Only `pm-mcp enter` appends a row to a session log.
* *Driving*: It follows the links of the plan and epic bootstraps, their source units, and the project setup (`pm_state` and `pm_do` with `plan_id: NO_PLAN`); the sub-workflows they call (the source units, `lessons.pmwf`) offer the implicit `step_out` link (`PM-WF-16`, link:../workflow-dsl/02-units-jobs-decisions.adoc#session-driven-units[Workflow DSL Specification, Session-Driven Units]).
* *Viewing*: It lists scopes with `pm_plans` and `pm_epics` and shows a plan or epic with `pm_state`; the web app and `pm-operator status` are the dependable views (link:../cli-and-security/03-web-server.adoc#web-app[CLI, Coordination & Security Specification, Web App]).
* *Answering*: While it views a scope with open question records, it relays the user's answer through the scope's answer link `answer:<question_id>` (channel `session`); the web app is the dependable channel, and the first valid answer wins (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]).
* *Optional worker*: Where its client profile allows session tasks (`worker.session_tasks`), it may take tasks through `pm_wait` like a worker: only tasks of `read_only` roles whose artifact allows the session first (`session_first`), of the scope it entered, and whose working directory equals the session's, never a writer task, because it runs outside the job confinement. A task the session does not acknowledge within its host's acknowledgement deadline goes to a headless worker of the role (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). Its usage is recorded `unmeasured` unless its host reports usage per turn.

No plan or epic waits on the entry session: a scope continues while no session is connected, and a session that leaves loses nothing.

=== Worker Connections
_See Requirement link:../../Requirements.adoc#PM-WORK-2[PM-WORK-2: Task Protocol]_

A worker connection is bound to its job and generation by the job token (link:01-processes-and-transport.adoc#job-token[Local Trust: Job Token]): its tool set is that of its role's class, its links are those of the task entities leased to its generation, and its resource reads are read-only within its own project (link:../mcp-tools/01-core-workflow-tools.adoc#job-bound-connections[MCP Tools Specification, Worker Connections]). It carries no session identity and appends no session row; its audit records carry its `job_id`, role, and generation (`PM-SEC-6`). The supervisor watches it by the process, the acknowledgement, and its calls, never by the transport (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]).

=== Call Cycle

Every scoped call (`pm_state`, `pm_do`, `pm_build`, `pm_lsp`) and every `pm_wait` executes as:

. *Bind the connection*: For a worker connection, resolve the job from the token and check, in this order, the job and the generation: an ended job is refused `job_ended` (a worker's generation is fenced when its job ends, so this check comes first), a fenced generation of a running job `generation_fenced`, and a scope or entity that is not a task entity leased to the generation `job_scope_mismatch` (link:../mcp-tools/04-errors-and-testing.adoc[MCP Tools Specification, Errors]). For a session connection, check its generation the same way, take the client profile from `PM-MCP-Client`, and resolve the scope from the `plan_id`/`epic_id` argument, or, for `plan_id: NO_PLAN`, from the verified `PM-MCP-Workspace` header and the workspace home `<PM_MCP_BASE>/projects/<project_id>/workspace/` (link:../filesystem-layout/03-project-store.adoc#workspace-home[Filesystem Layout Specification]) (`PM-ARCH-4`). No call appends a session row.
. For mutating calls, acquire the scope lock (`PM-WF-4`) and load the current state from disk, discarding stale cache entries.
. Validate the link and arguments against the persisted state (`PM-WF-6`) and, on a task entity, against the lease and the generation (`PM-WORK-2`).
. Execute exactly one transition, including any auto-steps it chains, and persist all resulting state atomically before releasing the lock.
. Render the new representation with the links valid for the calling connection (the links of a leased task entity for its generation; the bootstrap, setup, and answer links for a session), using the connection's client profile and capabilities.

Because the transition is persisted before the response is produced, the files always reflect every call whose effects happened, whether or not its response reached the caller. What follows a task's submission (the next state, the next task, a job) is the engine's work, not the caller's.

=== Continuation

* *By the server*: Plans and epics continue through engine events and tasks; no transition of a plan or epic depends on a host connection, and a job or task may complete while no host is connected.
* *Viewing*: Any connection may view a scope with `pm_state(plan_id | epic_id)` at any time, with identical results for identical persisted state.
* *After context loss*: An entry session that lost its context (`/clear`, compaction, a new host session) runs its entry command again, which names the live scope or opens a new entry and issues a new generation, or finds its scope with `pm_plans` and `pm_epics`; a pending bootstrap entry continues with `pm_state(plan_id: NO_PLAN, entity: <entry_id>)`.
* *After worker replacement*: A successor worker starts with an empty context and receives the task again; nothing is handed over, because every task carries what its state needs (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]).
* *Concurrency*: Any number of connections, workers and sessions, may address the same scope concurrently. Concurrency is resolved by the scope lock and entity-scoped links (`PM-WF-4`); replayed or stale links are rejected with the current representation (`PM-TOOL-4`), and every call of a fenced generation is refused.

=== Stalled Plans
_Implementation watch: link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-2[PM-WATCH-RUN-2], link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-8[PM-WATCH-RUN-8]_

The runtime continues every plan and epic itself, so a scope that does not move is a fault of the supervision or of the environment, made visible to the operator, never to a model:

* *Definition*: A non-terminal plan or epic is `stalled` when it has no pending condition, awaits no event (no running job, no task queued or leased within its budget, no open CI, merge-queue, or review-bot wait, no waiver wait, no open question record), and its last transition or task progress is older than the compiled stalled threshold (link:../timeouts/02-runtime-leases-operator-web.adoc#stalled-threshold[Timeouts & Budgets Specification]). A role the supervisor cannot serve stalls nothing: its tasks close `lost` with `role_unavailable` and their states take the conservative fallback, and the start-failure guard reports the harness's error text to the operator (link:../model-work/03-supervision-and-recycling.adoc#start-failure-guard[Model Work Specification, Start-Failure Guard]). A scope under an integrity pause is listed with the pause, not as `stalled`. Stalled is derived from persisted state, the supervisor's records, and the audit log on read, never stored as workflow state.
* *Cause*: Every stalled scope names its cause; the closed cause set is `no_progress` (with the idle span).
* *Visibility*: `pm-operator status` (plan view), the web app, and the epic view show `stalled` with its cause; the runtime emits it on the event streams (link:01-processes-and-transport.adoc#local-api[Local API]). A scope in an `operator`-mode question state is listed as waiting for an answer (with the question id), never as `stalled`.
* *Record*: The first time a scope is found stalled in an episode (an episode ends with the scope's next transition or task progress), the runtime appends one `plan_stalled` audit record with the scope and the cause; metrics count the gap as idle time.
* *Minimality*: `stalled`, its cause, and `plan_stalled` never appear in a model-facing representation (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

=== Connection-Scoped Rendering

Some rendering decisions depend on the calling connection, not on the scope:

* *Waiting*: The calls a model holds open are a worker's or session's `pm_wait` and a running `pm_build` (`PM-IMPL-4`). A `pm_wait` always holds for at most `connection.bounded_wait_seconds`, with progress frames during it where the host's timeout is reset by progress; a `pm_build` uses a progress wait only when the connection declared progress support, supplied a `progressToken`, and the client profile states that progress resets the host's timeout (`connection.progress_resets_timeout`), and otherwise a bounded wait within `connection.bounded_wait_seconds` (link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Timeouts & Budgets Specification]; link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification, Profile Schema]).
* *Elicitation*: Used only on a session connection that declared elicitation support, and only for the choices of the project setup and of the plan and epic bootstraps, which the entry session drives, among them the operator-configuration choices the server raises in the project setup (`PM-SEC-3`); without that capability the state offers the choice as a link, and an operator-configuration choice names the `pm-operator` command and offers `retry`. The capabilities the connection declared are the only source of this decision, never the client profile. A worker connection receives no elicitation request. No operator decision is ever pending: overrides are the operator's own initiative, never taken through elicitation (link:../cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]).
* *Content questions*: Never connection-dependent. Every open question record of a plan or epic is shown in the web app, which notifies the paired devices, and rendered with its answer link to every session viewing the scope (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]).
* *Skill activation*: A session connection that declared the client capability of the MCP Skills Extension gets offers that name skills by URI and digest only (host activation); every other connection gets the required skills in-band (link:../mcp-tools/02-service-and-skill-tools.adoc[MCP Tools Specification, Skill Tools]).
* *Client profile*: A session's calls render with the profile of the client its relay declares; a worker's with the profile of its role's harness, recorded in its job record.

The same scope may therefore render differently for two connections at the same moment without any difference in persisted state.

=== Long-Running Work

Jobs run in the runtime, independent of any call. The engine awaits a job's completion as an event and advances the scope; a composite wait settles or short-circuits the same way, and cancelling a job is the engine's or the operator's act (`PM-WF-8`, `PM-WF-9`). No model polls or cancels a job; the plan representation shows a running job's progress as a view. The only exception is `pm_build`, which continues a running build by its own `job_id` within the same bounded window (`PM-TOOL-2`).

== Failure Semantics

[cols="2,3"]
|===
|Event |Behaviour

|Host closes the conversation or kills the session relay (`stdin` EOF, `SIGTERM`, `SIGKILL`)
|The relay closes its runtime connection and exits. The runtime holds no state for the connection. Plans, epics, jobs, workers, locks held by in-flight transitions (released at transition end), and persisted state are unaffected. A task the session held returns to the queue when its acknowledgement deadline (link:../timeouts/01-job-budgets-and-waits.adoc#ack-deadline[Timeouts & Budgets Specification]) or its silence limit (link:../timeouts/01-job-budgets-and-waits.adoc#silence-limit[Timeouts & Budgets Specification]) passes (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]).

|A host kills and restarts a relay mid-session
|The new relay reads its identity from its environment again and binds to the same generation (link:03-relay.adoc#_generations_at_the_relay[Relay, Generations at the Relay]); a worker continues its task. A held call of the old relay is lost; the caller calls again.

|A worker's process exits, stalls, or stops acknowledging
|The supervisor ends it, fences its generation, revokes its job token, releases its lease at once, and offers its task to a successor exactly once; a worker that exits before its first call is a start failure (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]).

|Relay dies while a call is in flight
|The runtime completes and persists the transition; only the response is lost. An offer whose response is lost stays leased: the worker's next `pm_wait` receives the same offer again under the same lease (link:../model-work/02-task-protocol.adoc#ack[Model Work Specification, Acknowledge]). A worker that makes no such call before its acknowledgement deadline (link:../timeouts/01-job-budgets-and-waits.adoc#ack-deadline[Timeouts & Budgets Specification]) is ended and its task offered to a successor, except where its host's acknowledgement is informational, where its silence limit (link:../timeouts/01-job-budgets-and-waits.adoc#silence-limit[Timeouts & Budgets Specification]) decides. The next `pm_state` from any connection returns the resulting state.

|Runtime not running when a relay starts or reconnects
|A session relay starts it on demand (link:01-processes-and-transport.adoc#_start_modes[Start Modes]); a worker relay never does. While the socket does not accept connections, the relay answers pending requests with `runtime_unavailable` after the runtime start timeout (link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-start-timeout[Timeouts & Budgets Specification]) when it started the runtime, otherwise at once (link:03-relay.adoc#relay-rules[Relay Rules]), and keeps retrying on subsequent requests. Because the runtime keeps no session, a request after a runtime restart is served normally; only requests in flight during the restart are lost.

|Runtime crashes during a transition
|Atomic write-and-rename guarantees each store is either fully updated or unchanged, and the scope's transaction journal makes a multi-store transaction complete by roll-forward. The relay answers the in-flight request with `runtime_unavailable`; after restart, the project's recovery completes before its first call is served (link:02-startup-recovery-drain.adoc#per-project-recovery[Per-Project Recovery]), and `pm_state` shows the persisted state.

|Runtime crashes while jobs and workers run
|After the next start, the project's recovery terminates the orphaned jobs and workers if still alive, records them `killed`, fences the worker generations, and returns their leased tasks to the queue, each offered again exactly once (link:02-startup-recovery-drain.adoc#per-project-recovery[Per-Project Recovery]).

|Runtime draining
|New calls receive representations with `facts.runtime: draining`, and no new task is offered; after exit, the next `pm-mcp` or `pm-operator` command that needs the runtime (a session relay start included) brings up a new runtime.

|Runtime stops or crashes while web access is enabled
|The web listener ends with the runtime: open browser streams end, and a browser gets a refused connection until the next runtime start opens the listener again. Paired devices and `web.enabled` are unaffected.
|===

== CLI Interaction

Only the relays (`pm-mcp serve`) call the runtime's MCP endpoint; no command of `pm-mcp` or `pm-operator` writes a store. Every command that reads or changes state (operator verbs, the entry rows, generations, and pending entries of `pm-mcp enter`, `pm-operator client` install records, `pm-operator web` pairing and devices, `pm-operator status`) is a request to the link:01-processes-and-transport.adoc#local-api[Local API], executed by the runtime as a locked, journaled, audited transaction like any MCP call; its effect is visible to the next call without notification. A damaged store blocks only its scope or project, so repair verbs run through the runtime as well. Only `pm-operator status` (runtime not running), `pm-operator drain`, and `pm-operator client status` work without a running runtime, and none of them writes (link:01-processes-and-transport.adoc#local-api[Local API], Availability).

[#cli-direct-reads]
*Files the client binaries read directly*: `pm-mcp` and `pm-operator` read files only from this closed list and never write any of them. Both binaries read `state/runtime.json` (liveness and the version check), `run/runtime.token` (authentication, under the client check of link:01-processes-and-transport.adoc#runtime-token[Local Trust: Runtime Token]), and `state/install-records.json` with the target files recorded there (the drift checks of `pm-mcp enter` and `pm-operator client status`). Only `pm-mcp` reads the hint file named by `pm-mcp enter --hint-file`, which lies under `.marshall/local/temp/`. Only `pm-operator` reads `machine-config.json` (the drain bound of `pm-operator drain`). A worker relay reads none of them. The normative list is link:../cli-and-security/01-cli-and-installer.adoc#cli-file-reads[CLI, Coordination & Security Specification, Direct file reads]. The read-only codec for these files, the client over the Unix socket, the on-demand start procedure (link:01-processes-and-transport.adoc#_start_modes[Start Modes]), and the drift checks live in the contract module `pm-api`, shared by both binaries. Their only lock is `runtime-start.lock`. Details of each verb are in link:../cli-and-security.adoc[CLI, Coordination & Security Specification].

== Verification
_Implementation watch: link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-3[PM-WATCH-RUN-3]_

* *Relay integration tests (`*IT`)*: `McpAssured.newStdioClient()` spawns `pm-mcp serve --client claude` with an isolated `PM_MCP_BASE`, which starts a private runtime on demand. Tests cover `id` preservation, the runtime token on every forwarded request (a request without it or with a stale one is refused with `401`; the relay re-reads the token once after a runtime restart), the `Mcp-Method` and `Mcp-Name` headers on every forwarded request, both host protocol forms (`server/discover` with per-request `params._meta`, and `initialize`), elicitation round trips on a bootstrap choice, progress forwarding, and continuation from a second client via `pm_state`.
* *Relay rule tests*: A notification for which the runtime's transport returns a body writes nothing to `stdout`; a killed runtime makes the relay answer every held request with `runtime_unavailable` within one second (a test bound of this check, not a runtime timeout); a `notifications/cancelled` for an answered request is dropped and changes nothing; a `tools/list` result shows no property of the identity set, and an identity argument a client sends is not forwarded; a relay killed under a held `pm_wait` and started again with the same environment binds the same generation; a second `initialize` or `server/discover` on the same relay keeps its generation, while a changed host session identifier or a host marker that reports a new session binds a new generation (`new_session`) and fences the earlier one; a `pm-mcp enter` of the same session identity supersedes the relay's generation, and the relay's next request is repeated once in the new generation; `pm-mcp serve` without `--job` exits at once when `PM_MCP_JOB_ID` is set.
* *Runtime restart tests*: Kill the runtime during an active job, a leased task, and a pending transition; verify the job and worker are recorded `killed`, their generations fenced, their tasks offered again exactly once, stores consistent, and the plan continuing without a connection.
* *Startup order tests*: A second runtime started against a live one exits `0` at once and leaves `<PM_MCP_BASE>` byte-identical (no audit record, `runtime.json` and the socket unchanged); a stale socket and `runtime.json` left by a killed runtime are removed only after the lock is acquired; a restarted runtime writes a new `runtime.token` before its socket accepts a connection; a call addressing a project whose recovery exceeds the project recovery wait returns `runtime_recovering`, and the repeated call after recovery is served.
* *Socket path length tests*: A `PM_MCP_BASE` long enough to push `run/runtime.sock` over the platform `sun_path` limit makes the start refuse with a diagnostic naming the path on `stderr` and in `audit.jsonl` and with exit code `77`; no socket, token, or `runtime.json` is written, and nothing is created in the system temporary directory.
* *Cold-start measurement (`PM-TECH-3`)*: The ≤ 50 ms target is measured from process start to the socket accepting connections (step 7 of link:02-startup-recovery-drain.adoc#_startup_sequence[Startup Sequence]) on a clean state (empty `PM_MCP_BASE`, no stale files, no projects to recover), excluding every per-project recovery.
* *First-request measurement (`PM-TECH-3`)*: Against a running runtime, the `pm-mcp serve` relay forwards the host's `initialize`, and every other command of `pm-mcp` and `pm-operator` sends its first request, within ≤ 50 ms of process start.
* *Idle memory measurement (`PM-TECH-3`)*: The resident set size of an idle `pm-mcpd` (socket bound, no job, worker, or language server running) is ≤ 64 MB, excluding child jobs and language servers.
* *Isolation tests (`PM-TEST-5`)*: Verify that the runtime opens no TCP/UDP listener while web access is disabled (under listener fallback (1) only the loopback listener of link:01-processes-and-transport.adoc#_transport_endpoint[Transport Endpoint]), that the socket, `runtime.token`, and their directory have modes `0600`/`0600`/`0700`, that a client refuses a `run/` directory or token file with a foreign owner, a broader mode, or a symlink, that `/api/v1` and `/mcp` refuse a request without the runtime token, that the token appears in no log, audit record, or job environment, that a job cannot read `run/runtime.token` under Landlock, that a worker reads its own `run/jobs/<job_id>/` and neither writes it nor reads another job's, that a job token is refused on `/api/v1`, that `resources/read` on a worker connection serves a resource of the worker's project and refuses one of another project (`-32002`, `scope_not_found`), that a worker connection is refused `job_scope_mismatch` for a scope or entity not leased to its generation, `generation_fenced` after its generation was fenced, and `job_ended` after its job's fate (a revoked token is never answered `401`; an unknown or malformed one always is), that it never appends a session row, and that every line the relay writes to `stdout` is a valid JSON-RPC 2.0 message.
* *Web listener tests*: With `web.enabled` the runtime opens exactly one additional listener, on `127.0.0.1` unless `web.lan` is set; on it `/mcp` and every path outside the web app and `/api/v1/` are unreachable, the runtime token and a job token are answered `401`, a device secret is checked on every request (a revoked one is refused on the next), and a device secret is refused on the Unix socket; `pm-operator web disable` closes the listener while a running job continues, a restart with `web.enabled` opens it again, and a drained runtime leaves no listener behind.
* *CLI availability tests*: With no runtime running, `pm-operator status` reports "not running" and `pm-operator client status` reports the install records, both without starting a runtime or writing a file; `pm-operator drain` exits `0`; every other command starts the runtime on demand and reports `running` only after an authenticated round trip; `pm-operator drain` never signals a process whose start instant differs from `runtime.json`.
* *Stalled tests*: An aged fixture (a non-terminal plan without pending condition or awaited event whose last transition is older than the stalled threshold) is reported `stalled` with cause `no_progress` by `pm-operator status` and the event stream, produces exactly one `plan_stalled` record per episode, and changes no model-facing representation; a plan waiting on an `operator`-mode question is listed as waiting for an answer and never as `stalled`.
