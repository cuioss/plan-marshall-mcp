== Overview

This document specifies the deterministic sub-agent dispatch lifecycle, task envelope bin-packing algorithms, post-return observability protocol, non-blocking sub-agent question batching, effort role resolution and 7-level capability ladder, read-only untrusted content ingestion (`execution-context-reader`), and epic plan emission (`emit:<plan>`) for *plan-marshall-mcp* (`PM-MCP`).

In the legacy script-and-prose architecture, sub-agent orchestration relied on prose conventions for task sizing, unverified return summaries, and static build-time agent variant files that lacked MCP tool declarations. `PM-MCP` replaces these mechanisms with server-owned envelope entities, tracked `dispatch_id` lifecycles paired with `returned:<dispatch_id>` transitions, server-resolved effort roles, a strict two-family agent boundary (`execution-context` workers vs. MCP-free `execution-context-reader` extractors), and operator-mediated epic plan emission.

== Task Envelope Bin-Packing & Sequential Task Yield
_See Requirements link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint], link:../Requirements.adoc#PM-WF-14[PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution]_

During Phase 4 (`plan`), the workflow engine does not dispatch sub-agents per individual task. Instead, it sizes each planned task, packs compatible tasks into budget-bounded execution envelopes (`envelope-1`, `envelope-2`, ...), and dispatches one leaf sub-agent per envelope.

[#cost-sizing]
=== Cost Sizing (`derive-cost-size`), Envelope Budget & Minimum Dispatch Work

The cost model is `plan-marshall`'s (`manage-tasks/scripts/_tasks_cost.py`, `manage-tasks/scripts/_tasks_envelope.py`, the defaults in `manage-config/scripts/_config_defaults.py`, and `extension-api/standards/dispatch-granularity.md` § 1.2), verified at commit `88fcfc9ef`; re-verify against the latest `plan-marshall` version before implementing. It predicts the token consumption of a task's work (generation, reasoning, and in-context skill loads), not wall-clock time; the build count is deliberately not a signal, because a build is token-cheap whatever its duration. The dominant cost of a dispatch is the per-task work, not the envelope's re-establishment overhead, so bundling tasks amortises only that minor share.

1. *Size Rubric*: For every planned task $t$, `TaskCostEstimator` (the `derive-cost-size` function) computes a deterministic weighted score from four signals of the task record (link:store-schemas.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]):
+
$$\text{score}(t) = 10 \cdot N_{\text{steps}}(t) + W_{\text{profile}}(t) + 3 \cdot N_{\text{skills}}(t) + 4 \cdot N_{\text{files}}(t)$$
+
where $N_{\text{steps}}(t)$ is the number of the task's `steps` (the dominant term), $N_{\text{skills}}(t)$ the number of its `skills[]`, $N_{\text{files}}(t)$ the number of its distinct `target_files`, and $W_{\text{profile}}(t)$ the weight of its `profile`: `implementation` `12`, `module_testing` `12`, `verification` `4`, and the default weight `8` for every other member of the task profile enum (`integration_testing`, `documentation`), as `plan-marshall` weights a profile it does not list. There is no per-profile base cost.
2. *Six Sizes*: The score maps to `cost_size` through monotone bands, so raising any signal never lowers the size:
+
[cols="1,2,2"]
|===
|`cost_size` |Score band |Default `predicted_cost_tokens`

|`XS` |$\text{score} < 30$ |`5K`
|`S` |$30 \le \text{score} < 60$ |`25K`
|`M` |$60 \le \text{score} < 150$ |`60K`
|`L` |$150 \le \text{score} < 300$ |`130K`
|`XL` |$300 \le \text{score} < 700$ |`260K`
|`XXL` |$\text{score} \ge 700$ |`520K`
|===
3. *Size-to-Token Table*: `predicted_cost_tokens(t)` is defined as the value of the task's `cost_size` in the size-to-token table; it is a table lookup, never a per-task computation. The table is derived, never configured: its compiled defaults are the column above, and a hand-set table could only be less accurate than the calibration (*deliberate change vs. `plan-marshall`*: its `plan.phase-5-execute.cost_size_token_table` does not exist). The table's values are labelled `uncalibrated` until the server recalibrates them from a measured `metrics.json` population (link:store-schemas.adoc#metrics-store[Store Schemas Specification, Metrics Store]: per envelope the summed `predicted_cost_tokens` beside the measured token components); a recalibrated table carries `basis: calibrated` with its population count and is kept as the derived fact `cost_calibration` of the project's `derived-facts.json` (link:store-schemas.adoc#derived-fact-kinds-discovery-calibration[Store Schemas Specification, Derived fact kinds]), and every figure derived from a table (`predicted_cost_tokens`, the Phase 4 budget projection) carries the basis of the table it used.
4. *Envelope Budget*: Envelopes are packed Next-Fit under a per-envelope budget derived from the context budget of the plan's client profile (`dispatch.context_budget_tokens`, link:client-profiles.adoc[Client Profiles Specification]; compiled fallback `400K`, `plan-marshall`'s `per_envelope_budget_tokens` default), because it depends on the model's context window, a property of the operator's host and ladder; the operator may override it per project (`envelope_budget_tokens` in `local-config.json`, link:store-schemas.adoc#local-config[Store Schemas Specification, Operator Local Configuration]); a team file never sets it. The budget is a plan-time packing bound over summed `predicted_cost_tokens`, never a runtime comparand: a sub-agent cannot measure its own context use mid-turn, and a sub-agent that runs short of context leaves through `yield:envelope-M` (link:phase-workflows.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution]). A task whose predicted cost alone exceeds the budget (an `XXL` task under the defaults) is placed alone in its envelope.
5. *Envelope Sharing*: Tasks share an envelope only when they target the same module and resolve under the same effort role; the execution profile is not a sharing criterion, so a deliverable's `implementation` and `module_testing` tasks share one envelope.
6. *Minimum Dispatch Work (10K)*: `10K` tokens is the minimum judgement work that justifies a dispatch of its own (`dispatch-granularity.md` § 1.2), not an envelope ceiling. An envelope whose summed `predicted_cost_tokens` stays below `10K` (for example a lone `XS` task) is merged by the server into its adjacent envelope of the same module and effort role, the preceding one first, even when the merged envelope then exceeds the budget; without such a neighbour it stays alone, and the plan representation lists it in the fact `below_minimum_dispatch`.

The rubric prices a byte when it enters a context and ignores how long it stays resident. Isolating work in a separate envelope is justified only when re-creating the envelope's starting context (created bytes bill 1.25) costs less than the residency it removes (read bytes bill 0.1 per remaining turn); this condition is evaluated per split, never assumed. The server supplies both inputs: `record-metrics` publishes per envelope the `predicted_cost_tokens` beside the measured token components, and per envelope split (`yield:envelope-M`) the re-creation and residency terms, or `not_derivable` when a component is unmeasured.

=== Deterministic Envelope Packing Algorithm (`EnvelopePacker`)
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-1[PM-WATCH-DISP-1]_

Given the ordered sequence of tasks $T = [t_1, t_2, \dots, t_n]$ produced during Phase 4 (`plan`), each stamped with its `predicted_cost_tokens` (<<cost-sizing>>), `EnvelopePacker` runs automatically in-process upon `plan.describe-tasks` submission to partition $T$ into an ordered list of envelopes, each a contiguous slice of $T$, so topological dependency order is preserved. The packer never re-derives a task's cost; it only sums the stamped values:

[source,java]
----
package de.cuioss.pm.mcp.core.dispatch;

import java.util.ArrayList;
import java.util.List;
import java.util.Set;

public final class EnvelopePacker {

    /** Minimum predicted work that justifies a dispatch of its own (dispatch-granularity § 1.2). */
    public static final long MIN_DISPATCH_TOKENS = 10_000;

    public enum CostSize { XS, S, M, L, XL, XXL }

    public record PlannedTaskSummary(
            String taskId,
            String moduleId,
            String role,
            Set<String> skillUris,
            CostSize costSize,
            long predictedCostTokens,
            List<String> dependsOnTaskIds
    ) {}

    public record PackedEnvelope(
            String envelopeId,
            String moduleId,
            String role,
            List<String> taskIds,
            List<String> unionSkillUris,
            long totalPredictedCostTokens
    ) {}

    /**
     * @param orderedTasks         topological order over depends_on, ties broken by task_id
     * @param envelopeBudgetTokens the configured per-envelope budget (default 400K)
     */
    public List<PackedEnvelope> packEnvelopes(List<PlannedTaskSummary> orderedTasks, long envelopeBudgetTokens) {
        List<List<PlannedTaskSummary>> groups = new ArrayList<>();
        List<PlannedTaskSummary> current = new ArrayList<>();
        long currentTotal = 0;

        // Next-Fit in task order: close the open envelope when the next task is
        // incompatible or would push it past the budget; a task over budget sits alone.
        for (PlannedTaskSummary task : orderedTasks) {
            boolean fits = !current.isEmpty()
                    && canShareEnvelope(current.getFirst(), task)
                    && currentTotal + task.predictedCostTokens() <= envelopeBudgetTokens;
            if (!fits && !current.isEmpty()) {
                groups.add(current);
                current = new ArrayList<>();
                currentTotal = 0;
            }
            current.add(task);
            currentTotal += task.predictedCostTokens();
        }
        if (!current.isEmpty()) {
            groups.add(current);
        }

        mergeBelowMinimum(groups);

        List<PackedEnvelope> envelopes = new ArrayList<>();
        for (List<PlannedTaskSummary> group : groups) {
            envelopes.add(sealEnvelope(envelopes.size() + 1, group));
        }
        return List.copyOf(envelopes);
    }

    private boolean canShareEnvelope(PlannedTaskSummary first, PlannedTaskSummary candidate) {
        // Same module and same effort role; the execution profile is not a criterion
        return first.moduleId().equals(candidate.moduleId())
                && first.role().equals(candidate.role());
    }

    private void mergeBelowMinimum(List<List<PlannedTaskSummary>> groups) {
        // An envelope below the minimum dispatch work joins its adjacent compatible
        // envelope (preceding first), even past the budget; contiguity is kept.
        for (int i = 0; i < groups.size(); i++) {
            List<PlannedTaskSummary> small = groups.get(i);
            if (total(small) >= MIN_DISPATCH_TOKENS) {
                continue;
            }
            int target = -1;
            if (i > 0 && canShareEnvelope(groups.get(i - 1).getFirst(), small.getFirst())) {
                target = i - 1;
            } else if (i + 1 < groups.size() && canShareEnvelope(groups.get(i + 1).getFirst(), small.getFirst())) {
                target = i + 1;
            }
            if (target < 0) {
                continue; // stays alone; reported in the fact below_minimum_dispatch
            }
            if (target < i) {
                groups.get(target).addAll(small);
            } else {
                groups.get(target).addAll(0, small);
            }
            groups.remove(i);
            i--;
        }
    }

    private static long total(List<PlannedTaskSummary> group) {
        return group.stream().mapToLong(PlannedTaskSummary::predictedCostTokens).sum();
    }

    private PackedEnvelope sealEnvelope(int index, List<PlannedTaskSummary> group) {
        PlannedTaskSummary head = group.getFirst();
        List<String> taskIds = group.stream().map(PlannedTaskSummary::taskId).toList();
        List<String> skills = group.stream()
                .flatMap(t -> t.skillUris().stream())
                .distinct()
                .sorted()
                .toList();
        return new PackedEnvelope("envelope-" + index, head.moduleId(), head.role(), taskIds, skills, total(group));
    }
}
----

*Dependency Order*: The ordered input $T$ is the topological order of the task graph persisted in each task's `depends_on` (link:store-schemas.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]; Kahn's algorithm, ties broken by `task_id`), and `PlannedTaskSummary.dependsOnTaskIds` is that field, so no envelope places a task before one of its dependencies. The same field governs dispatch: a task is yielded only when every task in its `depends_on` is `completed` or `skipped`, and an envelope is offered only when its first task is yieldable (link:phase-workflows.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution]); a task whose dependency ended `infeasible` or `removed` is never yielded.

=== Sequential Task Yield Within an Envelope
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-1[PM-WATCH-DISP-1]_

When a sub-agent is spawned for an envelope (`entity = "envelope-N"`), it interacts with the daemon exclusively at `scope = "entity"`. The sub-agent never receives all task bodies upfront in its dispatch prompt; instead, the server yields tasks one at a time as hypermedia state representations:

The diagram abbreviates identifiers: `dsp-01` stands for a full `dispatch_id` such as `dsp-0001-8f2a1c` and `TASK-1` for `TASK-001` (link:identifiers.adoc#id-dispatch-id[`dispatch_id`], link:identifiers.adoc#id-task-id[`task_id`]).

1. *Initial Yield (`start`)*: The sub-agent invokes `pm_state(scope="entity", plan_id="<plan_id>", entity="envelope-N")`. The server transitions the active `dispatch_id` for `envelope-N` from `ALLOCATED` to `CLAIMED` and returns the state representation for the first uncompleted task $t_1$ (`state: "envelope.task.active"`, `facts.task_id: "TASK-001"`). The representation offers the sub-agent's four exits from a task: `submit:TASK-001` (complete the task), `escalate:TASK-001` (a blocking operator question), `yield:envelope-N` (give back the envelope's remaining tasks, for example when the context runs short), and `infeasible:TASK-001` (the task is impossible as specified, with evidence); link:phase-workflows.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution] defines what the server does on each. `deviate:TASK-001` is offered beside them and reports a scope deviation (link:phase-workflows.adoc#_scope_deviation_contract[Phase Workflows Specification, Scope-Deviation Contract]).
2. *Sequential Advancement on `submit`*: When the sub-agent completes task $t_i$ and invokes `pm_do(scope="entity", link="submit:TASK-i", args={...})`, the engine atomically persists task $t_i$'s result in the plan store and advances the envelope cursor to $t_{i+1}$. If $i < k$, the `pm_do` call immediately returns the representation for task $t_{i+1}$ without returning to the parent session.
3. *Terminal Envelope Completion*: When the final task $t_k$ in `envelope-N` is submitted, `pm_do` transitions the entity to the terminal state `envelope.completed` with an empty `links` table (`links[0]{rel,link,form,free}:`). The sub-agent then exits and returns its completion summary to the parent session.

== Dispatch Observability & Return Protocol
_See Requirements link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint], link:../Requirements.adoc#PM-WF-14[PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution]_

Because MCP servers do not directly spawn host sub-agents—the host session executes its native agent-spawning tool (`Agent` in Claude Code, `task` in OpenCode, `invoke_subagent` in Antigravity, `spawn_agent` in Codex)—the server cannot observe sub-agent termination, harness cancellation, or token consumption unless the dispatching session reports the outcome back through a paired hypermedia link.

=== `dispatch_id` Generation & Lifecycle States

Every time the workflow engine renders a representation offering a `dispatch:<entity>` link (including concurrent fan-out dispatches such as per-module architecture enrichment), it allocates or reuses an active `dispatch_id` and pairs the dispatch link with a corresponding `returned:<dispatch_id>` transition link in the parent representation. *Pairing exception*: a reader dispatch (<<_reader_agent_family_execution_context_reader>>) is paired with `ingest_candidates:<dispatch_id>` instead, which carries the return fields of `returned:<dispatch_id>` together with the candidate payload; no `returned:` link is rendered for it.

* *Identifier Format*: `dsp-<4_digit_seq>-<6_hex_nonce>` (link:identifiers.adoc#id-dispatch-id[`dispatch_id` grammar], e.g., `dsp-0003-8f2a1c`), unique within its plan or epic scope. The identifier carries no scope: every call that names it also names its `plan_id` or `epic_id`, and the server resolves it only within that addressed scope; an identifier unknown in the addressed scope is rejected (`rejected.reason: link_not_available`).
* *Audit Logging on Render*: One `[DISPATCH]` audit record is written per firing (never per role lookup). A re-dispatch after an unconfirmed or failed run allocates a new `dispatch_id` and writes a new `[DISPATCH]` record.

The lifecycle state of a dispatch is the closed enumeration `ALLOCATED | CLAIMED | RETURNED | INCOMPLETE_SUBMISSION | UNCONFIRMED | SUPERSEDED`, persisted on the dispatch record. No state is entered by a clock: there is no dispatch timeout.

[cols="1,3,3"]
|===
|Lifecycle State |Entry |Exit

|`ALLOCATED`
|A representation offering `dispatch:<entity>` is rendered and persisted with a new `dispatch_id`. A re-render before the sub-agent claims the dispatch reuses the same `dispatch_id`.
|`CLAIMED` on the first entity-scoped call; `RETURNED` or `INCOMPLETE_SUBMISSION` when the return arrives unclaimed (always for a reader dispatch, whose sub-agent has no MCP tools and never claims); `SUPERSEDED` on `redispatch:<entity>`; `UNCONFIRMED` at phase close.

|`CLAIMED`
|The first entity-scoped `pm_state` or `pm_do` call targeting `entity` (or carrying `dispatch_id`). Records `claimed_at`; confirms that the host launched the sub-agent and that it has MCP connectivity.
|`RETURNED` or `INCOMPLETE_SUBMISSION` on the return; `SUPERSEDED` on `redispatch:<entity>`; `UNCONFIRMED` at phase close.

|`RETURNED`
|The parent session follows `returned:<dispatch_id>` (for a reader dispatch `ingest_candidates:<dispatch_id>`) with a non-`success` status, or with `status: success` while the entity has recorded its required `submit`; or `resume:<entity>` finds that `submit` recorded. Records `returned_at`, `reported_status`, `display_detail`, `token_usage` and each reported token component and `tool_uses` (`measured` integer or `"unmeasured"`), and the server-measured `duration_ms`.
|None (terminal). A non-`success` return leaves the remaining work to a fresh dispatch with a new `dispatch_id` (Post-Return Integrity Invariants, item 3); the returned dispatch is never superseded.

|`INCOMPLETE_SUBMISSION`
|The return reports `status: success` while the entity has not recorded its required `submit` (Post-Return Integrity Invariants, item 2); the return fields are recorded as for `RETURNED`, and the `dispatch_incomplete` condition is raised on the dispatching state.
|`RETURNED` or `SUPERSEDED` on `resume:<entity>`. The condition's `escalate` defers the exit to the operator and never settles the dispatch; if the scope is aborted while the condition holds, `INCOMPLETE_SUBMISSION` is its terminal disposition.

|`UNCONFIRMED`
|Derived by the server when the phase that allocated the dispatch closes (its phase transition or the scope's abort) while the dispatch is still `ALLOCATED` (never claimed) or `CLAIMED` (never returned).
|None (terminal).

|`SUPERSEDED`
|`redispatch:<entity>` on an `ALLOCATED` or `CLAIMED` dispatch; `resume:<entity>` that re-dispatches the remaining work of an `INCOMPLETE_SUBMISSION` dispatch; a loop-back iteration that creates a new envelope for the entity.
|None (terminal). Any subsequent `pm_do` or `pm_state` referencing a `SUPERSEDED` `dispatch_id` is rejected immediately with `reason: "stale_dispatch_id"`.
|===

There is no separate aborted state. A dispatch whose sub-agent the host harness aborted is `RETURNED` with `status: harness_cancellation` when the parent session reports it; an abort that is never reported leaves the dispatch `ALLOCATED` or `CLAIMED` until `redispatch:<entity>` supersedes it or the phase close derives `UNCONFIRMED`.

[#dispatch-recovery-links]
==== Dispatch Recovery Links (`redispatch:<entity>`, `resume:<entity>`)

Both links are entity-addressed (link:hypermedia-format.adoc#link-identifier-grammar[Hypermedia Format Specification, Link Identifier Grammar]); `<entity>` is the dispatched entity (`envelope-M`, `enrich-<module_id>`, a finding), never the `dispatch_id`, so the link stays valid across the dispatch it replaces. Neither takes a free parameter, and neither re-runs a sub-agent blindly: both first inspect the entity store and the worktree (Post-Return Integrity Invariants, item 3) and render the observed partial progress in `facts`.

* *`redispatch:<entity>`* (rel `retry`, form `noop`): offered by the dispatching state beside every `dispatch:<entity>` whose dispatch is `ALLOCATED` or `CLAIMED`. Following it marks that dispatch `SUPERSEDED` and returns the dispatching state with a fresh `dispatch:<entity>` for the entity's remaining work, paired with the return link of the new `dispatch_id`.
* *`resume:<entity>`* (rel `next`, form `noop`): offered only by the `dispatch_incomplete` condition (link:state-catalogue.adoc#condition-dispatch_incomplete[State Catalogue, Conditions]). Following it re-reads the entity's persisted state: when the required `submit` is now recorded, the dispatch becomes `RETURNED`, the condition is cleared, and the dispatching state takes its outcome for the completed submission; otherwise the dispatch becomes `SUPERSEDED`, the condition is cleared, and the dispatching state offers a fresh `dispatch:<entity>` for the remaining work.

=== Normative Schema for `returned:<dispatch_id>`
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-3[PM-WATCH-DISP-3], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-4[PM-WATCH-DISP-4], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-5[PM-WATCH-DISP-5]_

In the parent representation, every active `dispatch:<entity>` link is accompanied by a `returned:<dispatch_id>` link with `rel = "submit"` and `form = "submit"` (a reader dispatch by `ingest_candidates:<dispatch_id>` instead, whose schema adds the candidate payload to these fields; <<_reader_agent_family_execution_context_reader>>):

[source,text]
----
links[2]{rel,link,form,free}:
  dispatch,dispatch:envelope-1,dispatch,-
  submit,returned:dsp-0001-4b9c10,submit,"status:enum[success|error|loop_back|blocked|harness_cancellation],display_detail:text[1..80],token_usage:int[1..10000000]?,input_tokens:int[0..10000000]?,output_tokens:int[0..10000000]?,cache_read_input_tokens:int[0..10000000]?,cache_creation_input_tokens:int[0..10000000]?,tool_uses:int[0..100000]?"
----

The link above is rendered for a client profile declaring `dispatch.token_usage_components: all` (link:client-profiles.adoc[Client Profiles Specification]). The server renders only the usage parameters the active profile can report: `total_only` omits the four component parameters, `none` omits every token parameter, and `tool_uses` is rendered only where the profile declares `dispatch.reports_tool_uses: true`. A parameter that is not rendered is recorded as `unmeasured` with the reason `not_reported_by_client`, never as `0`. `duration_ms` is never a link parameter: the server measures it (Post-Return Integrity Invariants, item 6).

When the sub-agent finishes (or fails/cancels in the host harness), the parent session invokes `pm_do` on `returned:<dispatch_id>` with the following JSON Schema for `args`:

[source,json]

=== Post-Return Integrity Invariants
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-6[PM-WATCH-DISP-6], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-7[PM-WATCH-DISP-7], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-8[PM-WATCH-DISP-8], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-5[PM-WATCH-GEN-5], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-8[PM-WATCH-GEN-8]_

The workflow engine enforces six non-negotiable post-return invariants when processing `returned:<dispatch_id>`:

1. *Unmeasured Token Usage Never Fabricates Zero*: If `token_usage` is omitted or `null` in `returned:<dispatch_id>`, the server persists `"token_usage": "unmeasured"` in the dispatch ledger and phase metrics store (`metrics.json`). It **must never** record `0`, because a zero token count corrupts cost aggregations and masks missing host telemetry. A step that runs inline by design (for example when the neutral profile converts a dispatch into an inline step, `PM-CLIENT-4`) records `"token_usage": "inline"`; `unmeasured` and `inline` are declared before any scoring and never collapse into each other or into `0`. Every token total aggregated from the dispatch ledger is published as a population-stamped aggregate (`rows`, `rows_unmeasured`, `population_count`, with the population `dispatched`; link:store-schemas.adoc#metrics-store[Store Schemas Specification, Metrics Store]); when `rows_unmeasured > 0` the total is marked `total_is_floor: true` and never wins a reconciliation against another source.
2. *Submit-Before-Return Verification (No Synthesized Submissions)*: When `returned:<dispatch_id>` is called with `status: "success"`, the server inspects the persisted state of the target `entity`. If the entity reached its required terminal submission state (e.g., `envelope.completed`, or the expected outline/triage artifact was submitted via `pm_do`), the return succeeds and advances the parent workflow. If the entity has **not** recorded its required `submit` transition (for example, the sub-agent edited files or answered in prose and returned `"success"` without calling `pm_do(link="submit:...")`), the server **never synthesizes a missing submission**. Instead, it marks the dispatch record `INCOMPLETE_SUBMISSION`, logs an attribution defect in the audit log, and raises the `dispatch_incomplete` condition on the dispatching parent state (link:state-catalogue.adoc#condition-dispatch_incomplete[State Catalogue, Conditions]; the state and `call_stack` stay unchanged), offering only `resume:<entity>` (to complete or re-dispatch after inspecting disk state) and `escalate`.
3. *No Blind Retry on Unconfirmed Dispatches*: When a dispatch fails to return (`harness_cancellation`, empty return, or host crash) or remains `ALLOCATED` / `CLAIMED` without completion, the server never retries the sub-agent blindly and never re-offers it on a timeout. It inspects the worktree (`worktree_sha`) and entity store on disk first, exposes the observed partial progress (e.g., tasks $t_1$ completed, $t_2$ pending in `envelope-1`) in `facts`, and issues a fresh `dispatch_id` only for the remaining uncompleted tasks in the envelope.
4. *Citations-Only Return for Read-Only Workers*: Read-only worker dispatches (such as deep-lane codebase exploration or verification sweeps) persist their detailed findings and component assessments via entity-scoped `submit` links during execution and return a short `display_detail`, keeping raw findings out of the parent session's context window. The server computes the aggregate counts from the records the entity submitted and renders them as `facts` of the parent representation; `display_detail` is display text only and is never read as evidence of a count.
5. *Dispatch Reconciliation*: The `[DISPATCH]` audit record written on render and the `returned:<dispatch_id>` entry of the dispatch ledger are two records of one dispatch. Every `[DISPATCH]` record ends in exactly one terminal disposition: `RETURNED`, `SUPERSEDED`, `UNCONFIRMED` (still `ALLOCATED` or `CLAIMED` when its phase closes), or `INCOMPLETE_SUBMISSION` (only when the scope was aborted while the `dispatch_incomplete` condition held); <<_dispatch_id_generation_lifecycle_states>>. `record-metrics` publishes, per divergence class (`row_absent_from_return_ledger`, `row_absent_from_dispatch_audit`, `boundary_never_closed`, `phase_re_entered`), the row count and the token mass the divergence hides.
+
[#cause-class]
*Cause Classes*: Every dispatch carries exactly one `cause_class` from the closed set `terminal_error`, `retryable`, `returned_with_findings`, `benign`, `stall`, `unconfirmed` (metrics row field, link:store-schemas.adoc#metrics-store[Store Schemas Specification, Metrics Store]). A returned dispatch is classified from its termination `status` (and `INCOMPLETE_SUBMISSION` from that disposition); `unconfirmed` is the class of every dispatch in the lifecycle state `UNCONFIRMED`, whose cause is the absence of any observable reaction of the host: the dispatch was never claimed and never returned before its phase closed. A `SUPERSEDED` dispatch keeps the class of its return when one was recorded and is otherwise `stall` (its remaining work was re-offered). The per-class populations sum to the total dispatch population of the phase and of the plan, `UNCONFIRMED` dispatches included, with an asserted residual of `0`; a dispatch left unclassified fails the assertion and is never dropped from the total.
6. *Per-Column Usage Persistence & Server-Measured Duration*: The total, each token component, and `tool_uses` are persisted independently, each as a measured integer or `"unmeasured"`; a column is never derived from another (the total is never split, the components are never summed into a missing total) and never defaulted to `0`. `duration_ms` is measured by the server from the dispatch's `claimed_at` to its `returned_at` (from its render to `returned_at` for a dispatch that was never claimed, recorded with `duration_basis: rendered` instead of `claimed`); a dispatch that never returns keeps `duration_ms: "unmeasured"`. When every usage column of every dispatch in a phase is `"unmeasured"`, `record-metrics` reports `instrument_dark: true` for that phase instead of a total.

== Spend Accounting & Budget Anchors
_See Requirement link:../Requirements.adoc#PM-WF-14[PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution]_

_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-2[PM-WATCH-DISP-2], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-3[PM-WATCH-DISP-3], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-35[PM-WATCH-PHASE-35]_

Measured spend is compared against a fixed anchor table keyed by the plan's `scope_estimate` (`none`, `surgical`, `single_module`, `multi_module`, `broad`, link:phase-workflows.adoc[Phase Workflows Specification]) and its `ChangeType` (`feature`, `bug_fix`, `tech_debt`, `enhancement`, `verification`, `analysis`). Every pair of the full cross-product is either `anchored` or `fallback`; no pair is left undefined. The Phase 4 budget projection compares the summed predicted task cost with the anchor of the plan's pair.

[cols="2,2,2,2"]
|===
|`scope_estimate` |`ChangeType` |Warning (tokens / wall minutes) |Error (tokens / wall minutes)

|`surgical` |`feature`, `tech_debt` |600,000 / 45 |1,000,000 / 75
|`surgical` |`bug_fix` |500,000 / 30 |800,000 / 45
|`single_module` |`feature`, `tech_debt` |1,000,000 / 75 |1,600,000 / 120
|`single_module` |`bug_fix` |800,000 / 60 |1,300,000 / 90
|`multi_module` |`feature`, `tech_debt` |1,500,000 / 120 |2,500,000 / 180
|`multi_module` |`bug_fix` |1,200,000 / 90 |2,000,000 / 150
|`broad` |`feature`, `tech_debt` |2,000,000 / 180 |3,500,000 / 240
|`broad` |`bug_fix` |1,500,000 / 120 |2,500,000 / 180
|===

All other pairs (every pair with `scope_estimate` `none`, and every pair with `ChangeType` `enhancement`, `verification`, or `analysis`) are `fallback` pairs. A fallback pair has no absolute anchor and is checked against normalized ceilings instead: tokens per changed file above 50,000, worked seconds per task above 900 (unanchored), a single phase's share of the plan's tokens above 0.50, or tokens per deliverable above 500,000. The canonical reference plan for the table is a surgical bug fix of 958,064 tokens over 2 files.

The values mirror `plan-marshall`'s budget anchors; re-verify them against the latest `plan-marshall` version before implementing.

The server applies the anchors at three points, and nowhere else:

* *Planning-Time Projection (advisory)*: At `plan.describe-tasks` the Phase 4 budget projection yields the non-blocking `split_advice` fact (link:phase-workflows.adoc[Phase Workflows Specification], Deterministic Task Derivation). It never enters a state of kind `awaiting_user` or `blocked` and never raises a condition.
* *Pre-Merge Finalize Spend Check*: Before the pre-merge barrier, `default:branch-cleanup` compares the plan's cumulative finalize spend (the tokens of every Phase 6 dispatch and of the measured main session in Phase 6, one population per figure) with the error column of the plan's pair; for a fallback pair it compares the finalize phase's share of the plan's tokens with the `0.50` ceiling. Above it, the plan enters `finalize.spend-escalate`, where the operator acknowledges the overrun before the merge proceeds; an acknowledgement covers the spend recorded up to its instant, so further finalize spend is checked again. The ratio (`finalize_spend_ratio`: value, compared column, unit, population) is a landing fact in every case. An unmeasured finalize spend yields `finalize_spend_ratio: not_derivable` and no escalation; it is never read as within budget.
* *Post-Run Comparison*: `record-metrics` and the post-run quality report render measured spend against the pair's anchor.

*Spend Classes*: Every dispatch is classified by what it produced, from the entity and findings records the server holds, never from its termination `status`:

[cols="1,4"]
|===
|Class |Condition

|`submitted`
|The dispatched entity recorded its required `submit` transition.

|`findings_only`
|No required `submit` was recorded, but the dispatch filed at least one finding (`FindingRecord.dispatch_id`).

|`no_product`
|The dispatch returned or was superseded without a submit and without a filed finding.

|`unmeasured`
|The dispatch's token usage is unmeasured, whatever it produced (its product is still shown in the cross-tabulation); it is counted by rows, never summed as `0`.
|===

Every dispatch belongs to exactly one class; the class token sums add up to the measured total with an asserted residual of `0`, and `unmeasured` rows are reported as a row count beside the sums. The termination `status` (`success`, `error`, `loop_back`, `blocked`, `harness_cancellation`) is a separate dimension, rendered as a cross-tabulation with the classes, so an `error` return that filed real findings is `findings_only`, never waste.

== Sub-Agent Question Batching & Non-Blocking Escalation
_See Requirements link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint], link:../Requirements.adoc#PM-WF-14[PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution]_

Sub-agents operating at `scope = "entity"` are strictly forbidden from directly prompting the human operator or blocking in an interactive wait loop.

=== Architectural Rationale

1. *Turn and Lock Conservation*: A sub-agent blocked waiting for human input holds an active host sub-session and prevents parallel sibling sub-agents from completing their fan-out batch.
2. *Host Elicitation Limitations*: Agent hosts (Claude Code, OpenCode, Antigravity) do not reliably route MCP elicitation requests or interactive user-question modals originating from inside background/child sub-agents to the top-level terminal UI.
3. *Single Bounded Escalation Guarantee*: Collecting ambiguities across all sub-agents in a phase allows the parent session to present a single, consolidated question batch to the operator rather than interrupting the user piecemeal.

=== Prompt Envelopes & Entity Escalation Protocol

When a sub-agent encounters an ambiguity or requires an operator decision during `phase-2-refine`, `phase-3-outline`, or `phase-5-execute`, it follows one of two non-blocking paths:

1. *Best-Judgment Completion with Attached Prompt Envelopes (`refine_prompt`, `outline_prompt`)*: In planning and outline states (`refine`, `outline`), the sub-agent completes its draft artifact using its best engineering judgment and includes structured open questions in the `questions` array of its `submit` link payload (free parameter `questions:list<schema[question-envelope]>?`, link:hypermedia-format.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]). Each question conforms to the `BatchedQuestionEnvelope` schema below, where every selectable option carries a canonical `branch_key` enum value bound to a downstream workflow transition.
2. *Immediate Entity-Scoped `escalate` (`escalate_ask`, `status: "blocked"`)*: In execution states (`execute`) where a task cannot safely proceed without an authoritative decision (e.g., an undeclared scope deviation or contradictory interface contract), the sub-agent invokes `pm_do(scope="entity", link="escalate:<task_id>", args={"question": {"question_text": "...", "options": [...]}})` (free parameter `question:schema[question-envelope]`). The server persists the pending question as a `BatchedQuestionEnvelope` with `prompt_kind: escalate_ask` in the plan store, records the pending decision, and raises the `blocked` condition on the entity scope (link:state-catalogue.adoc#condition-blocked[State Catalogue, Conditions]): the entity stays in `envelope.task.active` and renders only `wait:decision:<decision_id>`. The sub-agent returns `status: "blocked"` to the parent session and never waits on the decision itself. This is the only question path of Phase 5: there is no parent answers state, and `execute.dispatch-ready` keeps dispatching the envelopes that do not depend on the blocked task. The operator answers through elicitation or `pm-mcp operator`; the resolution clears the condition, records the answer as the task's guidance (an intent amendment when it changes intent), and the envelope is offered again as `dispatch:envelope-M` with a fresh `dispatch_id`, whose sub-agent resumes the task with the answer in `facts`.

[#question-envelope-schema]
*Server-Owned Fields*: `question_id` and `source_entity` are assigned by the server when it persists a question, never by the sub-agent. `question_id` is the next value of a scope-wide counter of the plan or epic (link:identifiers.adoc#id-question-id[Identifier Registry, `question_id`]), never reused; `source_entity` is the `entity` of the entity-scoped call that carried the question, or the call's `dispatch_id` when it names no entity. `prompt_kind` follows from the carrying link (`escalate_ask` for `escalate:<task_id>`, `refine_prompt` or `outline_prompt` for the `submit` link of a refine or outline entity). The model therefore supplies a question without these three fields: the free schema of the `escalate:<task_id>` link and the item schema of the `questions` array of a `submit` payload are the `BatchedQuestionEnvelope` minus `question_id`, `prompt_kind`, and `source_entity` (that is `question_text`, `default_assumption`, and `options`, each option an object `{branch_key, label, description, recommended?}`), and a payload that carries a server-owned field is rejected with `invalid_link_args`. This model-supplied subset is registered as the named parameter schema `question-envelope` (link:hypermedia-format.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]): the free parameter `question:schema[question-envelope]` of `escalate:<task_id>` and `questions:list<schema[question-envelope]>?` of the `submit` link of a refine or outline entity. === Parent Session Aggregation (`*.awaiting_answers`)

When the parent session processes `returned:<dispatch_id>` for all dispatches in the current state and the plan store contains one or more unresolved `BatchedQuestionEnvelope` records:

1. The engine transitions the parent plan to `<phase>.awaiting_answers` (`refine.awaiting_answers` or `outline.awaiting_answers`; the batched `refine_prompt` and `outline_prompt` questions exist only in Phases 2 and 3, and a Phase 5 question is the entity escalation `escalate:<task_id>` of <<_prompt_envelopes_entity_escalation_protocol>> item 2, never an answers state).
2. The representation exposes the consolidated questions in `facts.pending_questions` and offers an `answer_questions` link (accepting a map of `question_id -> branch_key` via MCP elicitation or model-relayed user answers for non-authorizing clarifications, as governed by `PM-SEC-3`).
3. Submitting `answer_questions` resolves the batched questions in one transition and advances the plan.

== Role Registry, Effort Level Ladder (Levels 1–7) & Variant Installation
_See Requirements link:../Requirements.adoc#PM-WF-14[PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution], link:../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

`PM-MCP` decouples workflow dispatch states from concrete LLM model identifiers through a two-stage resolution pipeline:

1. **Role Resolution**: Maps a dispatch's role key to an abstract **effort level** (`level-1`..`level-7` or `inherit`).
2. **Ladder & Variant Resolution**: Maps that level and the scope's current declared `client` (the last row of its session log `sessions.jsonl`, link:store-schemas.adoc#scope-session-log[Store Schemas Specification, Scope Session Log]) to an installed per-client agent variant pinning the runtime-specific `model` and `effort`.

The role registry, the level vocabulary, the resolve chain, the ladders, and the variant naming mirror `plan-marshall` (`plan-marshall/standards/effort-roles.md`, `effort-levels.md`, `effort-variants.md`, ADR-021), verified at commit `1d4a1da37`. Re-verify against the latest `plan-marshall` version before implementing.

=== Role Registry & Lookup Hierarchy
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-11[PM-WATCH-DISP-11]_

Configured values are the strings `level-1` .. `level-7` or `inherit`; any other value is a hard error on read. Effort keys are validated against the role registry below on the same read: a group the registry does not know (for example `plan.phase-1-init.effort`, or an unknown key under `orchestrator.effort`) or a sub-key its group does not list is a validation error exactly like an invalid value, never skipped with a fallback to the `default` slot. The validation on read of the effective configuration reports it (in `pm://project/config` and in `setup.reconcile-config`, link:domain-extensions.adoc#config-upgrades[Domain Extensions Specification, Validation on Every Read]) as an `unknown_config_key` finding naming the key path in `workflow.json`, and the server logs `PM_MCP-100` (link:../LogMessages.adoc[Log Messages]). There are no mandatory keys and no built-in per-role defaults: an unconfigured role resolves to `inherit`.

[cols="2,2,4"]
|===
|Group |Sub-keys |Where the sub-keys fire

|`plan.phase-2-refine.effort`
|`default`
|The phase's dispatches (refine body, issue-body reader ingestion, q-gate validation).

|`plan.phase-3-outline.effort`
|`default`
|Outline dispatches, including architecture enrichment and the collapsed light-lane envelope (`outline.light`, which folds the light plan's refine work; link:phase-workflows.adoc#planning-lanes[Phase Workflows Specification, Planning Lanes]), as in `plan-marshall`, which resolves the light envelope under the `phase-3-outline` role.

|`plan.phase-4-plan.effort`
|`default`
|Task planning dispatches.

|`plan.phase-5-execute.effort`
|`default`, `verification-feedback`
|`default`: task envelopes; `verification-feedback`: per-finding FIX / SUPPRESS / ACCEPT triage of build findings.

|`plan.phase-6-finalize.effort`
|`default`, `verification-feedback`, `post-run-review`
|`default`: finalize dispatches such as create-pr and pre-submission self-review; `verification-feedback`: Sonar, review-bot, and plugin-doctor finding triage; `post-run-review`: lessons capture (the plan retrospective is computed in-process and dispatches nothing).

|`orchestrator.effort`
|`analyze`, `decompose`, `reader` (plus `default` slot and `max` ceiling)
|Epic landing analysis, decomposition, and untrusted-text ingestion. Resolves under the top-level `orchestrator` block, not under `plan`.
|===

Phase 1 (`init`) runs inline and has no role. A group may be a plain string (one level for every sub-key) or an object with per-sub-key values and a `default` slot.

==== Deterministic Role Lookup Algorithm

1. **Plan roles**: `plan.<phase>.effort.<subkey>` -> `plan.<phase>.effort.default` -> `plan.<phase>.effort` (string) -> `plan.effort` -> `inherit`.
2. **Orchestrator roles**: `orchestrator.effort.<surface>` -> `orchestrator.effort.default` (or the plain string) -> `plan.effort` -> `inherit`, then clamped to `orchestrator.effort.max` on the ordinal ladder (`min(resolved, max)`; an unset `max` is a no-op). Before the clamp, a result of `inherit` is resolved to a concrete level: with `max` set it becomes `max` itself, because the session model has no rung the server can order against the ceiling; with `max` unset it stays `inherit`. *Deliberate change vs. `plan-marshall`*: its clamp passes `inherit` through unclamped, so an inheriting surface escaped the ceiling. Orchestrator dispatches always name their surface so the clamp cannot be bypassed.
3. **Unknown group or sub-key**: A validation error of the effort configuration (see above), reported by the validation on read of the effective configuration and logged as `PM_MCP-100`; the lookup never falls back from an unknown key to the `default` slot.

[#effort-ladders]
=== Effort Ladders (`effort_ladder` in `<PM_MCP_BASE>/projects/<project_id>/local-config.json`)
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-12[PM-WATCH-DISP-12]_

The ladder maps each level to a concrete `model` and `effort` per client runtime. The team file `.marshall/config/workflow.json` carries only the target-neutral levels; model pins are never stored in git-tracked configuration (ADR-021).

* **Machine-local ladder**: The operator file `<PM_MCP_BASE>/projects/<project_id>/local-config.json` holds `effort_ladder: {"<client_id>": {"level-N": {"model": <string|null>, "effort": <string|null>}}}` (link:store-schemas.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), with machine-wide defaults in `machine-config.json` `project_defaults.effort_ladder`; `plan-marshall`'s own ladder file is never read. `model: null` means unpinned (the dispatch inherits the session model).
* **Compiled defaults**: When an entry is absent (the file is sparse), the ladder compiled into the client profile (link:client-profiles.adoc[Client Profiles Specification]) applies and `pm://project/config` reports the source `compiled_default`; nothing is seeded into the file.
* **Narrow but never escalate (ADR-021)**: A ladder entry serves only its own level and never provisions a model beyond the capability of the resolved rung. ADR-021 (status *Proposed* in `plan-marshall`) also prescribes an entry-kind discriminator (`local` / `provider`) that `plan-marshall`'s current file format does not yet carry; verify its status before implementing the ladder reader.
* **Capability gating**: A variant for a `(model, effort)` pair is installed only when the model alias supports that effort (for Claude, `xhigh` and `max` depend on the alias). A level whose variant is not installed dispatches on the canonical `inherit` variant. The resolver never names a variant that is not installed.

=== Per-Client Variant Installation (`execution-context`)
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-9[PM-WATCH-DISP-9], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-24[PM-WATCH-DISP-24]_

Because agent hosts such as Claude Code and OpenCode load sub-agent definitions from static files at session startup and bind model/effort settings plus allowed tool lists in agent frontmatter, `pm-mcp client install <client>` renders and installs the per-level variant files into the host's agent directory:

* **Worker Family Variants**: `execution-context-level-1` through `execution-context-level-7` (for installed levels) and `execution-context` (the `inherit` variant).
* **Reader Family Variants**: `execution-context-reader-level-1` through `execution-context-reader-level-7` and `execution-context-reader` (`inherit`), so a reader role resolves at any level like every other role.
* **Rendered at Install Time**: Variant files are rendered from the templates in the embedded bundle and the effective ladder (`effort_ladder` of `local-config.json`, then `project_defaults`, then the compiled defaults). The bundle manifest marks them `rendered`; the installer verifies the template digest and records the rendered digest in `install-records.json`. A ladder change takes effect after `pm-mcp client update` and a host restart.
* **Mandatory MCP Tool Inclusion**: Every installed `execution-context` worker variant **must** include the `PM-MCP` tool surface (`mcp__plan-marshall__pm_state`, `mcp__plan-marshall__pm_do`, `mcp__plan-marshall__pm_build`, `mcp__plan-marshall__pm_lsp`, `mcp__plan-marshall__pm_skill`, `mcp__plan-marshall__pm_skill_file` or host-equivalent wildcard `mcp__plan-marshall__*`) alongside host file/shell tools (`Read`, `Write`, `Edit`, `Glob`, `Grep`, `Bash`). Without these MCP tool permissions, a sub-agent cannot execute `start: pm_state(...)` or submit its work via `pm_do`.
* **Concise Universal Worker Body**: The prompt body of every `execution-context-*` variant is reduced to a deterministic 5-step execution loop:
** Load `skill://pm/core` and every URI listed in `skills[]` via `pm_skill` (or `resources/read`); if any load fails or returns no content, stop without performing work and return `status: error` with `display_detail: "skill load failed: <uri>"`.
** Call the exact `start: pm_state(...)` command from the dispatch prompt.
** Perform the judgment or code/test authoring required by the returned state representation.
** Follow `pm_do(scope="entity", link="...", args={...})` until the entity representation reaches a terminal state (`links[0]`).
** Return `{status, display_detail}` to the caller (the dispatching session adds host-reported `token_usage` on `returned:<dispatch_id>`) without asking the user questions or spawning sub-agents.
* **Persona & Execution Lane Flattening**:
** *Personas*: The server resolves persona DAGs (`composes:` and `profiles:` with cycle rejection) at representation-build time, flattening them into `skills[]` URIs (`skill://pm/core` + `skill://pm/domain/...`). The legacy 1,500-line `persona-plan-marshall-agent` is stripped of Bash/CLI hygiene rules (roughly two-thirds of its volume) and distilled into `skill://pm/core`.
** *Execution Lanes*: Execution postures (`minimal ⊏ standard ⊏ full`, selected at `phase-1-init`) prune optional workflow elements server-side while enforcing **floor immunity** (a lane override of `off` on core or derived-state elements is ignored and noted in diagnostics; an unresolved `ask` element is dropped only when its external provider is absent).

== Reader Agent Family (`execution-context-reader`)
_See Requirements link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint], link:../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

When a workflow ingests untrusted free-form external content—such as external web pages or GitHub/GitLab issue descriptions—`PM-MCP` isolates the untrusted payload inside the **`execution-context-reader`** agent family. Pull request review comments and static-analysis messages are not dispatched to a reader per finding; they pass one batched deterministic validation pass (the same validator as Boundary 2) before triage, as in `plan-marshall` (`plan-marshall/workflow/verification-feedback.md`).

The reader contract mirrors `plan-marshall` (ADR-003, `agents/execution-context-reader.md`, `untrusted-ingestion`), verified at commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing. The containment boundary is the deterministic validator, not the reader's restricted tool surface: the tool surface only bounds the blast radius of a hijacked reader.

=== Two-Boundary Containment Architecture

[source,text]
----
Untrusted External Source (Web / Issue / PR Body)
                      │
                      ▼
┌──────────────────────────────────────────────────────────┐
│ Boundary 1: Reader Sub-Agent (execution-context-reader)  │
│  • Tools: WebSearch, WebFetch, Read, Grep ONLY           │
│  • WebFetch restricted to the domain allowlist           │
│  • NO MCP Tools (no pm_do, pm_state, pm_build, pm_start) │
│  • NO Write, Edit, or Bash tools                         │
│  • Output: Structured candidate JSON/text in response    │
└─────────────────────────────┬────────────────────────────┘
                              │ Plain-text response to parent session
                              ▼
┌──────────────────────────────────────────────────────────┐
│ Parent Session (dispatching plan or epic)                │
│  • Treats reader output as opaque untrusted candidate    │
│  • Calls pm_do(link="ingest_candidates:<dispatch_id>",   │
│                args={candidates, status, display_detail})│
└─────────────────────────────┬────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────┐
│ Boundary 2: Deterministic Server-Side Validator (PM-MCP) │
│  • Enforces strict JSON schema & length/charset bounds   │
│  • Rejects/clamps per closed schema (no extra keys)      │
│  • Rejects URLs whose host fails the domain allowlist    │
│  • Persists validated records to findings/references     │
└──────────────────────────────────────────────────────────┘
----

=== Normative Reader Constraints

1. *Strict Read-Only Host Tool Allowlist*: Installed `execution-context-reader` variants declare exactly `WebSearch`, `WebFetch`, `Read`, and `Grep` (or client-profile equivalents). `Write`, `Edit`, `MultiEdit`, `Bash`, and the host sub-agent tool (`Agent`/`task`/`invoke_subagent`/`spawn_agent`) are strictly excluded.
2. *Zero MCP Tools*: Reader variants are provisioned with **zero `pm_*` MCP tools**. Unlike worker sub-agents, a reader sub-agent does not call `pm_state` or `pm_do`. Instead, the server embeds the extraction schema and target source locators directly inside the rendered `dispatch` prompt's `reader_contract` block. Even if adversarial prompt injection inside an issue body or web page hijacks the reader sub-agent's instructions, the sub-agent has no tool capable of mutating workflow state, modifying files, or executing shell commands.
3. *Deterministic Server Validator Seam*: The reader sub-agent returns its extracted candidate records as structured text to the dispatching parent session. The parent session relays that candidate payload into the paired server validation link `ingest_candidates:<dispatch_id>` (rel `submit`, form `submit`), which replaces `returned:<dispatch_id>` for a reader dispatch (the pairing exception of <<_dispatch_id_generation_lifecycle_states>>): its free parameters are the candidate payload plus the return fields of `returned:<dispatch_id>`, and following it records the dispatch's return (`RETURNED`; a reader never claims its dispatch) and runs the compiled deterministic validator before writing any candidate to `references.json` or `findings.jsonl`.
4. *Outbound Domain Allowlist*: `WebFetch` from a reader is restricted to the operator-maintained WebFetch domain allowlist (host permission rules installed by the client bundle). Because the reader holds untrusted input, file read access, and outbound fetch at once, the allowlist is what closes the exfiltration path for bytes read via `Read`.
5. *Validator Duties*: The deterministic validator (a) enforces the extraction schema (`additionalProperties: false`, `maxLength`, `maxItems`, `pattern`) and rejects structural violations, (b) clamps over-long strings and arrays, and (c) re-checks every URL-bearing field against the same domain allowlist, rejecting unknown or red-flag hosts. It does not attempt to detect or strip prompt-injection text; only a `status: success` result is persisted.
6. *Separation from Citations-Only Rule*: Reader containment is a security boundary (`PM-SEC-1`) and must never be conflated with the citations-only context-conservation rule used by trusted read-only worker sub-agents.

== Orchestrator Epic Plan Emission (`emit:<plan>`) & Epic Coordination
_See Requirements link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint], link:../Requirements.adoc#PM-WF-15[PM-WF-15: Epic Plan Emission & Cross-Plan Merge Mutex]_

An orchestrator epic (`scope = "epic"`) decomposes a multi-plan initiative into workstreams and staged plan specifications, tracks cross-plan dependencies, keeps the declared surfaces of its own unordered plans disjoint, reconciles landing outcomes, and coordinates shared repository locks. The states of the epic workflow are catalogued in the link:state-catalogue.adoc#state-catalogue-epic[State Catalogue, Epic Workflow: `epic`].

[#epic-workflow]
=== Epic Workflow (`epic.pmwf`)

The epic workflow is the DSL unit `epic.pmwf` (`scope epic`); its states carry the prefix `epic.` and the phase value `orchestrator` (short form `orchestrate`), and its terminal states are `epic.archived` (phase value `completed`) and `epic.aborted` (phase value `aborted`). `epic.entry` routes by the ledger's state; `epic.active` is the resting state that offers the epic's work; every ledger write commits through `epic.commit-ledger`; `land-ledger` runs the epic landing (<<epic-landing>>). Ending the epic is the operator decision `abort-epic` (link:workflow-dsl.adoc#decision-registry[Workflow DSL Specification, Decision Registry]). Excerpt (`emit:<plan_id>` and the ledger-writing links other than `stage` and `ingest`, which all continue to `epic.commit-ledger`, and the landing's git internals are abbreviated):

[source,text]
----
workflow epic version 1 format 1
scope epic
start epic.entry

state epic.entry
  phase orchestrate
  auto epic.inspect-ledger
    initialized         -> epic.active
    resumed             -> epic.active

state epic.active
  phase orchestrate
  link submit stage:<plan> [submit] (spec_section: text[1..65536], surface_paths: list<text[1..512]>, surface_modules: list<text[1..128]>?, prerequisites: list<text[1..64]>?)
    do epic.stage-plan
      staged            -> epic.commit-ledger
  # emit:<plan_id> (rel emit), submit_landing, reconcile_landing, transfer_offer, mailbox_send: abbreviated
  link submit ingest:<message_id> [submit] (disposition: text[1..2000])
    do epic.ingest-message
      processed         -> epic.commit-ledger
  link next land-ledger [noop] ()
    do epic.enqueue-landing
      started           -> epic.landing
  link next archive [noop] ()
    do epic.archive-ledger
      archived          -> epic.archived
  link escalate abort [escalate] (reason: text[1..500])
    escalate abort-epic
      aborted           -> epic.aborted
      resumed           -> epic.active

state epic.commit-ledger
  phase orchestrate
  call git.commit_and_push (message_mode=step_or_fallback, push_mode=never)
    committed_local      -> epic.active
    committed_and_pushed -> epic.active
    pushed_clean         -> epic.active
    clean                -> epic.active
    aborted              -> epic.active

state epic.landing
  phase orchestrate
  job epic.land-ledger       # git internals: open design topic git/GitHub/GitLab approach
    succeeded           -> epic.active
    failed              -> epic.active
    refused             -> epic.active
    cancelled           -> epic.active
    timed_out           -> epic.active
    killed              -> epic.active
    indeterminate       -> epic.active

state epic.archived terminal archived success
  phase completed

state epic.aborted terminal aborted failure
  phase aborted
----

The parameter lists of `stage:<plan>` and `ingest:<message_id>` are illustrative _(to be specified with the staging and inbox primitives)_; the refusals `surface_overlap` and `surface_undeclared` of `stage` are `rejected` representations of `epic.active` (<<epic-surface-disjointness>>). The landing job settles `succeeded` only on the observed `merged` outcome; `ejected`, `closed`, and `timed_out` settle it `failed` and leave worktree and branch unchanged, so `land-ledger` resumes (<<epic-landing>> item 8).

=== Why Epics Emit Plans Rather Than Dispatching Sub-Agents
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-22[PM-WATCH-DISP-22]_

A plan (`scope = "plan"`) is a top-level workflow that dispatches its own leaf sub-agents (`scope = "entity"`). Under the single-level leaf constraint (`PM-WF-5`), a sub-agent can never spawn child sub-agents. Consequently, an epic **must never** invoke a child plan via a `dispatch` link or launch it inline.

Instead, the epic state machine exposes the **`emit:<plan_id>`** hypermedia link (`rel = "emit"`, `form = "submit"`):

* *Emission Checks Prerequisites Only*: Surface disjointness is a modelling invariant of the epic, checked when a plan is staged (<<epic-surface-disjointness>>), never a runtime gate at emission. The epic representation renders an `emit:<plan_id>` link for every `staged` row whose prerequisite rows (`prerequisites[]`) are all in the partition `terminal.shipped` (`merged` or `completed`: the prerequisite's code is on the default branch, so a dependent may emit before the prerequisite's post-run steps finish); following it compares no surfaces. A `parked` row is never offered `emit`.
* *Emission Transition (`launched`, Never `running`)*: When the model follows `pm_do(scope="epic", link="emit:<plan_id>", args={})`, the server atomically updates the plan's queue row `.marshall/orchestrator/<epic_id>/queue/<plan_id>.json` to `status: "launched"` (with `emitted_at` timestamp) and returns the exact operator entry command in `facts.emitted_command`:
+
[source,text]
----
pm-mcp enter --client <client_id> plan <plan_id> --from-epic <epic_id>
----
+
The invariant *Emit is not running* is strictly enforced: the epic representation pre-renders the eligible `emit:<plan_id>` commands, and only the human operator starts the new plan session. There is no `auto_emit` setting (*deliberate change vs. `plan-marshall`*: its `orchestrator.auto_emit` does not exist), and `parallelization_scope` is answered per epic and stored in `epic.json` (compiled default `1`), never a configuration default.

* *Automatic Observation of `running` via the Child Plan's Start*: When the operator runs the emitted entry command in a new host session, `pm-mcp enter` writes the pending entry record (recording `--from-epic <epic_id>`) that `pm_start` consumes: its session becomes the first row of `plans/<plan_id>/sessions.jsonl` and its `from_epic` becomes `origin.epic_id` of the plan's `mcp/status.json` in the per-project machine store. The next call on the epic scope reads the child plan's `origin.epic_id` under the epic lock and transitions the epic's queue row for `<plan_id>` from `launched` to `running` without requiring manual status updates in the epic session; no file watcher is involved.

* *Single Epic Pointer, Fail Loud*: Epic membership of a plan has one carrier, `origin.epic_id`, filled from the pending entry record's `from_epic` written by the emitted `pm-mcp enter … --from-epic <epic_id>` command; `pm_start` has no epic parameter and copies `from_epic` into `origin.epic_id` (link:store-schemas.adoc[Store Schemas Specification], Workflow State Store). Every consumer reads membership only from there. `pm_start` refuses with `epic_pointer_mismatch` when the new `plan_id` equals a queue row in state `launched` of some epic and `from_epic` is absent or names another epic. A plan with `from_epic` set never skips `default:emit-landing`; an unresolvable epic yields `landing_delivery: pending`, never a dropped step and never a refusal after the merge.
* *Re-Grounding Staleness at Emission*: The representation offering `emit:<plan_id>` shows, per candidate, `regrounded_at_sha` (the commit the row's specification was last re-grounded against, <<server-derived-landing-facts>> item 2) and `main_commits_since` (commits on the default branch since then, with the count of those touching the row's expected surface). It adds a warning fact when the specification was never re-grounded or when the default branch advanced on its expected surface since; the warning never withholds the `emit` link.

[#epic-surface-disjointness]
=== Staging-Time Surface Disjointness (Epic Modelling Invariant)
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-16[PM-WATCH-DISP-16], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-21[PM-WATCH-DISP-21]_

Disjointness of plan surfaces is an invariant the epic establishes when it cuts its work into plans, not a property the server re-evaluates at runtime. The server enforces it once, when a plan is staged, and only within one epic:

1. *Declared Surface*: Every staged plan declares its expected surface in its queue row (`declared_surface: {paths: [...], modules: [...]}`, <<_git_distributed_epic_ledger_per_file_store_layout_adr_024>>). Paths may be files, directories (prefix-matched) or globs (expanded); every entry must name a git-tracked path or glob inside the workspace, and modules are resolved to their directories through module discovery (`.marshall/architecture.json`). A plan whose surface cannot be declared (an empty surface, an entry under a git-ignored tree such as `.marshall/local/**` or outside the workspace, or an entry that cannot be evaluated) is refused with `surface_undeclared` naming the offending entries. There is no `indeterminate` path: a surface is either declared and comparable, or the staging is refused.
2. *Staging Check*: When the epic writes a queue row (staging a plan with its specification, or amending the declared surface or `prerequisites[]` of a `staged` row), the server compares the declared surface under the epic lock against the declared surface of every other non-terminal row of the same epic (every `live` state, `parked` included). An overlap is admitted only when the two rows are ordered through prerequisites: one depends, transitively over `prerequisites[]`, on the other, so it can only be emitted after the other reached `terminal.shipped`. An unordered overlap refuses the write with `surface_overlap`, naming the overlapping plans and paths; the epic re-cuts the plans or declares the ordering. The queue row is written only when the check passes.
3. *Emission*: `emit:<plan_id>` checks only prerequisites (`terminal.shipped`); it performs no surface comparison, because the invariant already holds for every staged row.
4. *Scope*: The check covers one epic. There is no cross-epic comparison and no comparison against plans started without an epic; conflicts with those surface at rebase or merge and are the operator's responsibility. Their handling belongs to the open git/GitHub/GitLab design topic.
5. *Runtime Drift Is Reported, Never Blocking*: When the operator accepts a scope deviation of a running plan of the epic (`execute.deviation-review` `accept`, link:phase-workflows.adoc#_scope_deviation_contract[Phase Workflows Specification, Scope-Deviation Contract]) and the plan's effective surface (declared surface plus the accepted `approved_widening` paths) now overlaps the declared surface of another non-terminal row of the same epic that is not ordered with it, the server appends a `surface_overlap_detected` event to the epic inbox (link:store-schemas.adoc#epic-inbox-record[Store Schemas Specification, Epic Inbox & Plan Mailbox Records]) naming the plans and paths. The event never blocks the plan, the deviation, or any emission; the epic decides whether to re-order or re-cut the affected staged rows.

=== Git-Distributed Epic Ledger & Per-File Store Layout (ADR-024)
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-13[PM-WATCH-DISP-13], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-14[PM-WATCH-DISP-14], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-15[PM-WATCH-DISP-15], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-16[PM-WATCH-DISP-16], link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-30[PM-WATCH-STORE-30]_

To allow epic state to merge cleanly across worktrees and machines via Git without monolithic file conflicts, the daemon persists epic state under `.marshall/orchestrator/<epic_id>/` using a strict per-concern file split:

[cols="2,2,3"]
|===
|Path |Writer Discipline |Contents & Invariants

|`epic.json`
|Daemon only (atomic write-and-rename under epic lock).
|Epic header (link:store-schemas.adoc#epic-header[Store Schemas Specification, Epic Header]): `epic_id` (the epic's identity, kept unchanged when the epic is archived to `.marshall/archived-orchestrators/<epic_id>-<YY-MM-DD>/`, link:filesystem-layout.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]; the dated suffix and the title are never identities), title, workstream definitions, the per-epic `parallelization_scope`, the coarse `lifecycle`, and `format_version`. It carries no FSM state: the workflow state (`epic.*`) lives only in the epic's `status.json` in the per-project machine store, so the two files never share a name.

|`queue/<plan_id>.json`
|Daemon only (exclusive create `CREATE_NEW` on addition; row-local read-modify-write on update).
|One file per staged plan (schema: link:store-schemas.adoc#epic-queue-row[Store Schemas Specification, Queue Row]), keyed by the child plan's `plan_id` in the canonical plan grammar (link:identifiers.adoc#id-plan-id[Identifier Registry]; derivation in link:phase-workflows.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]), which is allocated and phantom-ID checked when the row is staged. The epic-local ordinal (`PLAN-03`, `PLAN-PR-025B`) is kept only as the display-only field `ordinal`; no link, envelope, resource, or lookup addresses a row by it, and the write side and the read side of every epic↔plan address (emission, `from_epic`, running observation, inbox, landings) use `plan_id`. Each row tracks the closed 14-state plan vocabulary partitioned into `live` (`staged`, `ready`, `launched`, `running`, `blocked`, `parked`), `terminal.shipped` (`merged`, `completed`), and `terminal.closed_unshipped` (`abandoned`, `superseded`, `split`, `retired`, `transferred`, `resolved`). `parked` is an operator hold: a parked row is never offered `emit`, but its declared surface still takes part in the staging-time disjointness check (<<epic-surface-disjointness>>). Each row carries `prerequisites[]` (the `plan_id` values of rows of the same epic it depends on; emission waits until all are in `terminal.shipped`) and `declared_surface{paths[], modules[]}` (its expected surface, written only when the staging check passes). The closed-unshipped members mirror `plan-marshall` (`orchestrator.py`, `CLOSED_UNSHIPPED_PLAN_STATUSES`): `superseded` (the work was absorbed by a named successor row), `transferred` (the row moved to another epic's ledger, <<cross-epic-transfer>>), `retired` (withdrawn, no successor carries it), `resolved` (the defect closed with no plan work at all); `abandoned` and `split` are `PM-MCP` members. A row staged by intake carries `intake{source_epic, source_plan_id, source_location, message_id}`; a row whose work left carries `disposition` (`transferred`, `re-scoped`, or `left_alone`) with the confirming message. Executing child plans **never** write to `queue/` directly.

|`inbox.jsonl`
|Strictly append-only event log (link:store-schemas.adoc#epic-inbox-record[Store Schemas Specification, Epic Inbox & Plan Mailbox Records]), appended under the epic lock by the plan-scope outbox link (<<plan-scope-outbox-link>>), by `default:emit-landing`, by other epics (<<cross-epic-transfer>>), and by the owning epic's own claim and processing transitions; no line is ever rewritten.
|Structured cross-scope messages from executing child plans (scope deviations, blocker reports, process findings, landing notifications) from other epics (`transfer_offer`, `intake_confirmed`), and from the server (`surface_overlap_detected`, <<epic-surface-disjointness>>). Each `message` event carries a store-assigned, never-reused `message_id` (`msg-NNNN`); `claimed` and `processed` events reference it, and a message's current state (`pending`, `claimed`, `processed`) is the fold of its events. Distinguishes the three empty states (`no_file`, `empty_file`, `all_processed`) from `unreadable` (reported with the failing line), which is never read as empty. Plan-side writes resolve through the epic ledger resolution seam to the shared epic worktree copy, never the primary checkout.

|`landings.jsonl`
|Append-only under epic lock when a landing notification is reconciled.
|Structured landing history records for completed or closed child plans (<<server-derived-landing-facts>>; record schema by reference to the landing envelope: link:store-schemas.adoc#landing-record[Store Schemas Specification, Landing Record]). Each landing carries the plan's whole findings ledger as `findings[]`, so the epic never depends on the archived plan directory to read them.

|`spec.md`
|Written only through epic-scope `submit` links.
|The epic specification: workstream and staged-plan sections, including each staged plan's claim sections and expected surface (the authoritative, checked copy is the queue row's `declared_surface`). Served as `pm://epic/{epic_id}/spec/{section}` (link:mcp-tools.adoc[MCP Tools Specification]).

|`resume_anchor.md`
|Daemon-rendered markdown artifact.
|Human- and clone-readable queue overview and resumption summary. Regenerated automatically on merge conflict; regeneration refuses with an explicit diagnostic if any `queue/<plan_id>.json` source file is unreadable.
|===

The ledger directory is fully git-tracked. The epic's non-tracked scope state (the FSM `status.json`, the session log `sessions.jsonl`, `digests.json`, and the transaction journal) is not part of it; it lives in `epics/<epic_id>/` of the per-project machine store (link:filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]).

[#plan-scope-outbox-link]
==== Plan-Scope Outbox Link (`outbox:send`)
_Implementation watch: link:../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-32[PM-WATCH-STORE-32], link:../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-1[PM-WATCH-TOOL-1]_

Every plan state of a plan whose `mcp/status.json` carries `origin.epic_id` offers `outbox:send` (rel `submit`, form `submit`, free `kind:enum[scope_deviation|blocker_report|process_finding|landing_notification],summary:text[1..200],body:text[1..16384]`). The target inbox is derived by the store from `origin.epic_id` and the sending `plan_id`; the caller supplies no path or epic identifier. `landing_notification` is emitted only by `emit-landing`. Following the link appends one `message` event, returns its store-assigned `message_id`, and never changes the plan's own state.

*Read Access*: The epic scope reads every message of its inbox (`pm://epic/{epic_id}/inbox` and the per-message resource `pm://epic/{epic_id}/inbox/{message_id}`). A plan scope reads only the messages it sent itself, with their current delivery state (`pending`, `claimed`, `processed`); any other message id answers `scope_not_found`, so no plan learns what a sibling plan reported.

[#plan-mailbox]
==== Plan Mailbox (Epic → Plan Channel)

The epic → plan direction is a per-plan mailbox `mcp/mailbox.jsonl` in the plan directory, mirroring `plan-marshall`'s addressee mailbox (`plan-orchestrator` `inbox write --target-plan`, `inbox mailbox`). It lives in the plan directory of the per-project machine store, which never moves except on archival, when the mailbox moves with it (link:filesystem-layout.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), and follows the same strictly append-only event model with store-assigned, never-reused `message_id` values as the epic inbox (link:store-schemas.adoc#epic-inbox-record[Store Schemas Specification, Epic Inbox & Plan Mailbox Records]):

* *Write*: The owning epic's session follows `mailbox_send:<plan_id>` (rel `submit`, free `kind:enum[advisory|spec_amendment|coordination],summary:text[1..200],body:text[1..16384]`), offered for every queue row whose child plan exists. The server appends one `message` event under the plan lock, taken before any epic lock as the total lock order requires (link:store-schemas.adoc#lock-free-snapshot-reads[Store Schemas Specification]), addressed by the child `plan_id` (the queue key); the caller supplies no path. Only the epic named in the plan's `origin.epic_id` may write the mailbox.
* *Target Resolution*: A target plan that does not exist (a `staged` row not yet started) or is archived is refused at write time with `target_undeliverable`, and the message is never written elsewhere. For an existing plan the write succeeds and reports the target's liveness (`running`, `not_running`, or `indeterminate` when its `mcp/status.json` or session log is unreadable); `not_running` and `indeterminate` never withhold delivery, because the plan reads its mailbox when it resumes.
* *Read*: A plan reads only its own mailbox: every plan representation carries `facts.mailbox` (`delivery_state`: `never_delivered`, `delivered_unconsumed`, `consumed`, or `unmeasured`; `unconsumed_count`), and the resource `pm://plan/{plan_id}/mailbox` (and `…/mailbox/{message_id}`) serves the messages with their consumption. Reading is fail-open: an unreadable mailbox renders `delivery_state: unmeasured` with `mailbox_state: unreadable` and never blocks the plan. `mailbox_ack:<message_id>` appends a `consumed` event.
* *Advisory Only*: A mailbox message never changes the plan's state, scope, or tasks; an epic changes a launched or running plan's scope only through the operator (<<server-derived-landing-facts>> item 2, *Running Rows Are Not Re-Scoped*). The mailbox is covered by the plan's store digests (`mcp/digests.json`), so an out-of-band edit is detected.

[#cross-epic-transfer]
==== Cross-Epic Intake & Transfer

A row moves from one epic to another only as a recorded transfer over the two inboxes; only the owning epic's session ever changes its own queue rows:

1. *Offer*: The source epic follows `transfer_offer:<plan_id>` (rel `submit`, free `target_epic:epic_id,rationale:text[1..2000]`), which appends a `message` event of kind `transfer_offer` (`source_epic`, `source_plan_id`, `source_location`) to the target epic's inbox under the target epic lock. An offer is not a transfer: the source row stays unchanged.
2. *Intake*: The target epic's session stages its own row from the offer, subject to the staging-time surface check (<<epic-surface-disjointness>>); the new row carries `intake{source_epic, source_plan_id, source_location, message_id}`, and the server appends `intake_confirmed` to the source epic's inbox.
3. *Source Disposition*: On `intake_confirmed` the source epic's session sets the source row's `disposition` (`transferred`, which moves the row to `terminal.closed_unshipped` status `transferred`; `re-scoped`; or `left_alone`). A source row stays live until its own session records the disposition, and the representation lists pending offers and unanswered confirmations as facts.

[#epic-landing]
=== Epic Landing (`land-ledger`)
_See Requirement link:../Requirements.adoc#PM-WF-15[PM-WF-15: Epic Plan Emission & Cross-Plan Merge Mutex]_

Ledger changes are edited in the shared epic worktree (link:filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification]) and reach the default branch only through the `land-ledger` link of `epic.active`, which runs the landing in the state `epic.landing` (<<epic-workflow>>):

1. *One Landing for All Epics*: A landing covers every pending change in the shared epic worktree, whatever epic made it, in one pull request from the epic branch. There are never concurrent per-epic landing pull requests.
2. *Repository-Wide Serialization*: The landing holds the repository-wide epics-worktree lock for its git steps; a concurrent `land-ledger` waits for the lock or is answered with the open pull request. The landing never joins the per-repository plan merge FIFO or takes the plan merge lease (link:phase-workflows.adoc[Phase Workflows Specification], Cross-Plan Merge Mutex): its diff is confined to `.marshall/orchestrator/**` and `.marshall/archived-orchestrators/**`, disjoint from every plan surface by construction, so plan merges and epic landings never block each other.
3. *Ledger Paths Only*: The landing stages and commits only `.marshall/orchestrator/**` and `.marshall/archived-orchestrators/**`, even though the worktree holds nothing else; a diff touching any other path refuses the landing.
4. *Pull-Request Reuse & Composition*: A repeated landing reuses the open pull request of the epic branch and never opens a duplicate; title and body are composed from the landing snapshot (epics touched, queue rows changed, landings and inbox records added), never from plan artifacts.
5. *Gate*: Required CI checks only. The plan pre-merge review barrier (link:phase-workflows.adoc[Two Fail-Closed Barrier Predicates]) does not apply: a ledger-only diff draws no review-bot participation (`.marshall/**` is excluded from review bots), so Predicate 2 could never be satisfied.
6. *Merge Confirmation*: The landing waits for a terminal outcome (`merged`, `ejected`, `closed`, or `timed_out`) and is stamped `landed` only from the provider's observed pull-request state (`merged`, with the merge commit on the base branch), never from a merge command's return value or exit code.
7. *Post-Merge*: The primary checkout's default branch is fast-forwarded when it is clean and checked out. The epic branch is resynced by merging the new default branch into it inside the epic worktree, without removing the worktree; ledger writes committed after the landing snapshot stay on the branch. A reset of the epic branch to the default branch, a rebase, and a recreation of the branch are forbidden, because each could discard post-snapshot writes.
8. *Failure*: CI failure, queue ejection, or wait timeout stops the landing and reports it; worktree and branch are left exactly as they were (no reset), so following `land-ledger` again resumes.

[#server-derived-landing-facts]
=== Server-Derived Landing Facts, Spec Re-Grounding & Cross-Plan Locks
_Implementation watch: link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-17[PM-WATCH-DISP-17], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-18[PM-WATCH-DISP-18], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-19[PM-WATCH-DISP-19], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-20[PM-WATCH-DISP-20], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-22[PM-WATCH-DISP-22], link:../implementation-watch/dispatch-and-effort.adoc#PM-WATCH-DISP-23[PM-WATCH-DISP-23], link:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-42[PM-WATCH-GEN-42], link:../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-38[PM-WATCH-PHASE-38]_

[[_server_derived_landing_facts_spec_re_grounding_cross_plan_locks]]
1. *Server-Derived Landing Facts (`n/a` vs. `unknown`)*: When a child plan reaches `completed` and merges, the daemon derives objective landing facts directly from the git commit history, plan audit log, and realized footprint store (commits merged, files changed, tasks completed, loop-back count, test/coverage deltas). Values that do not apply to the plan's profile are recorded as `"n/a"`, while values that could not be read due to missing artifacts are recorded as `"unknown"`—degraded answers are never folded into `"n/a"`. The model in the epic session submits only the semantic landing analysis and downstream impact judgment via `submit_landing:<plan_id>`.
** *Landing Shape*: A landing record is the landing envelope that `emit-landing` writes, defined once in link:phase-workflows.adoc#_landing_envelope_emit_landing[Phase Workflows Specification, Landing Envelope] (identity and merge facts, figures, step record, review facts, `findings[]`, narrative and amendments, completeness, one landing per `plan_id`, and the non-landing record written when nothing merged); `landings.jsonl` stores it unchanged.
** *Squash-Aware Landing Commit*: The landing commit is located as the base-branch commit whose subject ends with `(#<pr_number>)`; a two-parent merge-commit lookup is never the only tier.
** *Fact States*: Every landing is plan-typed: `"n/a"` is never legal at the pull-request and merge keys and is legal at the deliverable and task keys only for landings of `local_changes` plans (`plan_source`, whose land lane has no deliverables or tasks), and every `"n/a"` names the rule, derived from plan data, that made the fact inapplicable. A fact whose source question no longer applies after the observed event (for example the provider's mergeable state after the pull request merged) is recorded as `"not_applicable_after_merge"`, distinct from both `"n/a"` and `"unknown"`; a genuinely failed read stays `"unknown"` and keeps the landing incomplete. A fact that is `"unknown"` on every landing of an epic is surfaced as a detector defect.
** *No Partial Landing*: A landing without its fact block is refused at write time (`landing_facts_missing`); it is never persisted partially.
** *Shipped-Without-Landing Reconciliation*: Every epic representation compares the queue rows in `terminal.shipped` with `landings.jsonl`. Rows without a landing record are listed in `facts.unlanded_shipped` (count and `plan_id` values; the count is always stated, zero included) and offer `reconcile_landing:<plan_id>`, which derives the landing facts server-side from the child plan's archived stores and git history. A shipped row is never treated as landed without a landing record.
2. *Specification Corpus Re-Grounding*: When reviewing staged specifications against repository `HEAD`, the epic workflow offers read-only analysis dispatches (or an inline fallback link) whose entity scope exposes only a draft `submit` link (enforcing no direct ledger writes). Every persisted re-grounding claim verdict is explicitly labeled `observed` or `hypothesis`, where every `hypothesis` must name the specific repository file or artifact that confirms or refutes it.
** *Claim-Section Parse States*: Every claim section of a staged specification (`spec.md`) parses to exactly one of `absent`, `empty`, `unreadable` (a table or prose where a bullet list is expected, or a heading that matches only case-insensitively), or `parsed`. `unreadable` blocks admission of that row (no `emit` link; the reason is stated in `facts`) and never passes vacuously; `absent` and `empty` are reported as distinct states.
** *Verdict Record*: A persisted re-grounding verdict record carries `claim` (section and claim index), `label` (`observed` | `hypothesis`), `verdict` (`corroborated` | `contradicted` | `partially_exercised` | `unverifiable`), `checked_at` (the commit SHA the claim was checked against), `by` (the `dispatch_id` or scope that produced it), `scope_change` (`none` | `rescoped`), `exercised_path` (the components actually tested, for example `reader -> classifier`), and `evidence` (text). `contradicted` is admissible only when `exercised_path` covers every component the claim names; otherwise the verdict is `partially_exercised`.
** *Archived Snapshots Are Not Siblings*: Cross-checks against sibling epics read the active root and the archived root (link:filesystem-layout.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]) and identify an epic only by the `epic_id` in its `epic.json`; an archived snapshot whose `epic_id` equals the checking epic's own is never a sibling candidate, and a distinct epic is still enumerated and compared.
** *Running Rows Are Not Re-Scoped*: The epic offers no spec-editing or re-scoping link for a queue row in `launched` or `running`; a re-grounding verdict that would re-scope such a row is recorded as pending and applied only after the row reaches a terminal state. Overlapping work waits for the running plan to land.
3. *Fixed Lock Hierarchy & Cross-Plan Coordination Primitives*: All representation and resource reads execute against atomic filesystem snapshots without holding scope locks during long-running script or build jobs, and whenever an operation mutates multiple scopes, short transaction locks are acquired in a strict global order (`workspace` lock -> `plan` lock -> `epic` lock -> `machine` lock), while long-lived claims are leases (link:store-schemas.adoc[Store Schemas Specification], `PM-IMPL-7`). The server serializes PR merge execution across concurrent plans via a fair per-repo FIFO admission queue and merge lease in `<PM_MCP_BASE>/state/merge-queue.json`, while shared review-bot rate-window claims (e.g., CodeRabbit hourly windows) are leases in `<PM_MCP_BASE>/state/review-bot-windows.json`. Machine-wide build concurrency is bounded by the slot cap in `<PM_MCP_BASE>/machine-config.json`, where stale slot reaping (`ProcessHandle.of(pid)`) executes inside the same atomic state transition as new job admission and the FIFO queue never drops a submitted build.
