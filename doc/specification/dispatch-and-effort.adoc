== Overview

This document specifies the deterministic sub-agent dispatch lifecycle, task envelope bin-packing algorithms, post-return observability protocol, non-blocking sub-agent question batching, effort role resolution and 7-level capability ladder, read-only untrusted content ingestion (`execution-context-reader`), and epic plan emission (`emit:<plan>`) for *plan-marshall-mcp* (`PM-MCP`).

In the legacy script-and-prose architecture, sub-agent orchestration relied on prose conventions for task sizing, unverified return summaries, and static build-time agent variant files that lacked MCP tool declarations. `PM-MCP` replaces these mechanisms with server-owned envelope entities, tracked `dispatch_id` lifecycles paired with `returned:<dispatch_id>` transitions, server-resolved effort roles, a strict two-family agent boundary (`execution-context` workers vs. MCP-free `execution-context-reader` extractors), and operator-mediated epic plan emission.

== Task Envelope Bin-Packing & Sequential Task Yield
_See Requirements link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint], link:../Requirements.adoc#PM-WF-14[PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution]_

During Phase 4 (`plan`), the workflow engine does not dispatch sub-agents per individual task. Instead, it computes a deterministic context cost for each planned task, packs compatible tasks into bounded execution envelopes (`envelope-1`, `envelope-2`, ...), and dispatches one leaf sub-agent per envelope.

=== The 10K Context Budget Rule & Cost Sizing (`derive-cost-size`)

Sub-agent context quality degrades when a single worker session accumulates excessive file reads, skill definitions, and intermediate edit diffs. To prevent mid-task context exhaustion while avoiding the cold-start overhead of spawning a separate sub-agent for every trivial change ("bundle rather than iterate"), the engine enforces a **10,000-token active working budget** (`ENVELOPE_BUDGET_TOKENS = 10_000`) for task bin-packing.

For every planned task $t$, the `derive-cost-size` function computes an estimated token cost $\text{cost}(t)$ and maps it to a discrete T-shirt size class (`XS`, `S`, `M`, `L`, `XL`):

$$\text{cost}(t) = B_{\text{profile}}(t) + (N_{\text{files}}(t) \times 900) + (N_{\text{steps}}(t) \times 600) + (N_{\text{skills}}(t) \times 750)$$

where:

* $B_{\text{profile}}(t)$ is the base overhead of the task's execution profile (`implementation`: `1800`, `module_testing`: `2000`, `verification`: `1200`, `documentation`: `1400`).
* $N_{\text{files}}(t)$ is the number of target and reference files bound to the task.
* $N_{\text{steps}}(t)$ is the number of sequential sub-steps within the task.
* $N_{\text{skills}}(t)$ is the count of distinct domain vocabulary skills (`skill://pm/domain/...`) resolved for the task's profile and module.

[cols="1,2,2,3"]
|===
|Cost Size |Estimated Token Range |Normalized Weight |Packing Constraint

|`XS`
|$\text{cost}(t) \le 2,500$
|`2,000`
|Packable with compatible tasks up to `10,000` budget and at most `4` tasks per envelope.

|`S`
|$2,500 < \text{cost}(t) \le 4,500$
|`4,000`
|Packable with compatible tasks up to `10,000` budget and at most `3` tasks per envelope.

|`M`
|$4,500 < \text{cost}(t) \le 7,500$
|`6,500`
|Packable with at most one `XS` task sharing the exact same module and profile (`\le 10,000`).

|`L`
|$7,500 < \text{cost}(t) \le 10,000$
|`10,000`
|Solo envelope only (`max_tasks = 1`). Never combined with other tasks.

|`XL`
|$\text{cost}(t) > 10,000$
|`10,000+`
|Solo envelope only (`max_tasks = 1`); triggers a plan-phase warning advising deliverable decomposition if $N_{\text{files}}(t) > 6$.
|===

=== Deterministic Envelope Packing Algorithm (`EnvelopePacker`)

Given the ordered sequence of tasks $T = [t_1, t_2, \dots, t_n]$ produced during Phase 4 (`plan`), `EnvelopePacker` runs automatically in-process upon `plan.describe-tasks` submission to partition $T$ into an ordered list of `TaskEnvelope` records while preserving topological dependency order:

[source,java]
----
package de.cuioss.pm.mcp.core.dispatch;

import java.util.ArrayList;
import java.util.List;
import java.util.Set;

public final class EnvelopePacker {

    public static final int ENVELOPE_BUDGET_TOKENS = 10_000;
    public static final int MAX_TASKS_PER_ENVELOPE = 4;

    public enum CostSize {
        XS(2_000, 4),
        S(4_000, 3),
        M(6_500, 2),
        L(10_000, 1),
        XL(12_000, 1);

        private final int normalizedTokens;
        private final int maxTasksInEnvelope;

        CostSize(int normalizedTokens, int maxTasksInEnvelope) {
            this.normalizedTokens = normalizedTokens;
            this.maxTasksInEnvelope = maxTasksInEnvelope;
        }

        public int normalizedTokens() { return normalizedTokens; }
        public int maxTasksInEnvelope() { return maxTasksInEnvelope; }
    }

    public record PlannedTaskSummary(
            String taskId,
            String moduleId,
            String profile,
            String role,
            Set<String> skillUris,
            CostSize costSize,
            int estimatedTokens,
            List<String> dependsOnTaskIds
    ) {}

    public record PackedEnvelope(
            String envelopeId,
            String moduleId,
            String profile,
            String role,
            List<String> taskIds,
            List<String> unionSkillUris,
            int totalNormalizedTokens
    ) {}

    public List<PackedEnvelope> packEnvelopes(List<PlannedTaskSummary> orderedTasks) {
        List<PackedEnvelope> envelopes = new ArrayList<>();
        List<PlannedTaskSummary> currentBatch = new ArrayList<>();
        int currentBudget = 0;
        int currentMaxTasks = MAX_TASKS_PER_ENVELOPE;

        for (PlannedTaskSummary task : orderedTasks) {
            CostSize size = task.costSize();
            int weight = size.normalizedTokens();

            boolean compatibleWithCurrent = !currentBatch.isEmpty()
                    && canShareEnvelope(currentBatch.getFirst(), task)
                    && (currentBatch.size() + 1) <= Math.min(currentMaxTasks, size.maxTasksInEnvelope())
                    && (currentBudget + weight) <= ENVELOPE_BUDGET_TOKENS;

            if (!compatibleWithCurrent && !currentBatch.isEmpty()) {
                envelopes.add(sealEnvelope(envelopes.size() + 1, currentBatch, currentBudget));
                currentBatch.clear();
                currentBudget = 0;
                currentMaxTasks = MAX_TASKS_PER_ENVELOPE;
            }

            currentBatch.add(task);
            currentBudget += weight;
            currentMaxTasks = Math.min(currentMaxTasks, size.maxTasksInEnvelope());
        }

        if (!currentBatch.isEmpty()) {
            envelopes.add(sealEnvelope(envelopes.size() + 1, currentBatch, currentBudget));
        }
        return List.copyOf(envelopes);
    }

    private boolean canShareEnvelope(PlannedTaskSummary first, PlannedTaskSummary candidate) {
        // Tasks share an envelope only when they target the same module, execution profile, and effort role
        return first.moduleId().equals(candidate.moduleId())
                && first.profile().equals(candidate.profile())
                && first.role().equals(candidate.role());
    }

    private PackedEnvelope sealEnvelope(int index, List<PlannedTaskSummary> batch, int budget) {
        PlannedTaskSummary head = batch.getFirst();
        List<String> taskIds = batch.stream().map(PlannedTaskSummary::taskId).toList();
        List<String> skills = batch.stream()
                .flatMap(t -> t.skillUris().stream())
                .distinct()
                .sorted()
                .toList();
        return new PackedEnvelope(
                "envelope-" + index,
                head.moduleId(),
                head.profile(),
                head.role(),
                taskIds,
                skills,
                budget
        );
    }
}
----

=== Sequential Task Yield Within an Envelope

When a sub-agent is spawned for an envelope (`entity = "envelope-N"`), it interacts with the daemon exclusively at `scope = "entity"`. The sub-agent never receives all task bodies upfront in its dispatch prompt; instead, the server yields tasks one at a time as hypermedia state representations:

[source,text]
----
Parent Session                     PM-MCP Daemon                    Sub-Agent (envelope-1)
──────┬───────                     ──────┬──────                    ──────────┬───────────

      │─────────────────────────────────►│                                    │
      │◄─────────────────────────────────│                                    │
      │ Representation with              │                                    │
      │ dispatch:envelope-1 (dsp-01)     │                                    │

      │ Spawn Sub-Agent (host_tool)      │                                    │
      │──────────────────────────────────────────────────────────────────────►│

      │                                  │   entity="envelope-1")             │
      │                                  │◄───────────────────────────────────│

1. *Initial Yield (`start`)*: The sub-agent invokes `pm_state(scope="entity", plan_id="<plan_id>", entity="envelope-N")`. The server transitions the active `dispatch_id` for `envelope-N` from `UNCLAIMED` to `CLAIMED` and returns the state representation for the first uncompleted task $t_1$ (`state: "envelope.task.active"`, `facts.task_id: "TASK-1"`, `links: [submit:TASK-1, escalate:TASK-1]`).
2. *Sequential Advancement on `submit`*: When the sub-agent completes task $t_i$ and invokes `pm_do(scope="entity", link="submit:TASK-i", args={...})`, the engine atomically persists task $t_i$'s result in the plan store and advances the envelope cursor to $t_{i+1}$. If $i < k$, the `pm_do` call immediately returns the representation for task $t_{i+1}$ without returning to the parent session.
3. *Terminal Envelope Completion*: When the final task $t_k$ in `envelope-N` is submitted, `pm_do` transitions the entity to the terminal state `envelope.completed` with an empty `links` table (`links[0]{rel,link,form,free}:`). The sub-agent then exits and returns its completion summary to the parent session.

== Dispatch Observability & Return Protocol
_See Requirements link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint], link:../Requirements.adoc#PM-WF-14[PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution]_

Because MCP servers do not directly spawn host sub-agents—the host session executes its native agent-spawning tool (`Agent` in Claude Code, `task` in OpenCode, `invoke_subagent` in Antigravity, `spawn_agent` in Codex)—the server cannot observe sub-agent termination, harness cancellation, or token consumption unless the dispatching session reports the outcome back through a paired hypermedia link.

=== `dispatch_id` Generation & Lifecycle States

Every time the workflow engine renders a representation offering a `dispatch:<entity>` link (including concurrent fan-out dispatches such as per-module architecture enrichment), it allocates or reuses an active `dispatch_id` and pairs the dispatch link with a corresponding `returned:<dispatch_id>` transition link in the parent representation:

* *Identifier Format*: `dsp-<plan_or_epic_id>-<4_digit_seq>-<6_hex_nonce>` (e.g., `dsp-auth-refactor-0003-8f2a1c`).
* *Audit Logging on Render*: One `[DISPATCH]` audit record is written per firing (never per role lookup). A re-dispatch after an unconfirmed or failed run allocates a new `dispatch_id` and writes a new `[DISPATCH]` record.

[cols="1,2,3"]
|===
|Lifecycle State |Trigger |Server Invariants

|`UNCLAIMED`
|Representation containing `dispatch:<entity>` is rendered and persisted.
|The sub-agent has not yet contacted the daemon. If the parent session calls `pm_state` again before the sub-agent claims the dispatch, the same `dispatch_id` remains active unless explicitly superseded by `redispatch:<entity>`.

|`CLAIMED`
|First entity-scoped `pm_state` or `pm_do` call arrives targeting `entity` (or carrying `dispatch_id`).
|Records `claimed_at` timestamp. Confirms the host actually launched the sub-agent and the sub-agent has MCP connectivity.

|`RETURNED`
|Parent session invokes `pm_do` on `returned:<dispatch_id>` after the sub-agent finishes.
|Records `returned_at`, `reported_status`, `display_detail`, and `token_usage` (`measured` integer or `"unmeasured"`). Cross-checks entity state before advancing the parent workflow.

|`SUPERSEDED`
|Parent session invokes `redispatch:<entity>` on an `UNCLAIMED` or aborted dispatch, or a loop-back iteration creates a new envelope.
|Any subsequent `pm_do` or `pm_state` referencing a `SUPERSEDED` `dispatch_id` is rejected immediately with `reason: "stale_dispatch_id"`.
|===

=== Post-Return Integrity Invariants

The workflow engine enforces five non-negotiable post-return invariants when processing `returned:<dispatch_id>`:

1. *Unmeasured Token Usage Never Fabricates Zero*: If `token_usage` is omitted or `null` in `returned:<dispatch_id>`, the server persists `"token_usage": "unmeasured"` in the dispatch ledger and phase metrics store (`metrics.json`). It **must never** record `0`, because a zero token count corrupts cost aggregations and masks missing host telemetry. A step that runs inline by design (for example when the neutral profile converts a dispatch into an inline step, `PM-CLIENT-4`) records `"token_usage": "inline"`; `unmeasured` and `inline` are declared before any scoring and never collapse into each other or into `0`. Every token total aggregated from the dispatch ledger is published as a population-stamped aggregate (`rows`, `rows_unmeasured`, `population_count`, with the population `dispatched`; link:store-schemas.adoc#metrics-store[Store Schemas Specification, Metrics Store]); when `rows_unmeasured > 0` the total is marked `total_is_floor: true` and never wins a reconciliation against another source.
2. *Submit-Before-Return Verification (No Synthesized Submissions)*: When `returned:<dispatch_id>` is called with `status: "success"`, the server inspects the persisted state of the target `entity`. If the entity reached its required terminal submission state (e.g., `envelope.completed`, or the expected outline/triage artifact was submitted via `pm_do`), the return succeeds and advances the parent workflow. If the entity has **not** recorded its required `submit` transition (for example, the sub-agent edited files or answered in prose and returned `"success"` without calling `pm_do(link="submit:...")`), the server **never synthesizes a missing submission**. Instead, it marks the dispatch record `INCOMPLETE_SUBMISSION`, logs an attribution defect in the audit log, and transitions the parent state to `<phase>.dispatch-incomplete` offering `resume:<entity>` (to complete or re-dispatch after inspecting disk state) and `escalate`.
3. *No Blind Retry on Unconfirmed Dispatches*: When a dispatch fails to return (`harness_cancellation`, empty return, or host crash) or remains `UNCLAIMED` / `CLAIMED` without completion, the server never retries the sub-agent blindly. It inspects the worktree (`worktree_sha`) and entity store on disk first, exposes the observed partial progress (e.g., tasks $t_1$ completed, $t_2$ pending in `envelope-1`) in `facts`, and issues a fresh `dispatch_id` only for the remaining uncompleted tasks in the envelope.
4. *Citations-Only Return for Read-Only Workers*: Read-only worker dispatches (such as deep-lane codebase exploration or verification sweeps) persist their detailed findings and component assessments via entity-scoped `submit` links during execution and return a short `display_detail`, keeping raw findings out of the parent session's context window. The server computes the aggregate counts from the records the entity submitted and renders them as `facts` of the parent representation; `display_detail` is display text only and is never read as evidence of a count.
5. *Dispatch Reconciliation*: The `[DISPATCH]` audit record written on render and the `returned:<dispatch_id>` entry of the dispatch ledger are two records of one dispatch. Every `[DISPATCH]` record ends in exactly one terminal disposition: `RETURNED`, `SUPERSEDED`, or `UNCONFIRMED` (still `UNCLAIMED` or `CLAIMED` when its phase closes). `record-metrics` publishes, per divergence class (`row_absent_from_return_ledger`, `row_absent_from_dispatch_audit`, `boundary_never_closed`, `phase_re_entered`), the row count and the token mass the divergence hides.

== Spend Accounting & Budget Anchors
_See Requirement link:../Requirements.adoc#PM-WF-14[PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution]_

Measured spend is compared against a fixed anchor table keyed by the plan's `scope_estimate` (`none`, `surgical`, `single_module`, `multi_module`, `broad`, link:phase-workflows.adoc[Phase Workflows Specification]) and its `ChangeType` (`feature`, `bug_fix`, `tech_debt`, `enhancement`, `verification`, `analysis`). Every pair of the full cross-product is either `anchored` or `fallback`; no pair is left undefined. The Phase 4 budget projection compares the summed predicted task cost with the anchor of the plan's pair.

[cols="2,2,2,2"]
|===
|`scope_estimate` |`ChangeType` |Warning (tokens / wall minutes) |Error (tokens / wall minutes)

|`surgical` |`feature`, `tech_debt` |600,000 / 45 |1,000,000 / 75
|`surgical` |`bug_fix` |500,000 / 30 |800,000 / 45
|`single_module` |`feature`, `tech_debt` |1,000,000 / 75 |1,600,000 / 120
|`single_module` |`bug_fix` |800,000 / 60 |1,300,000 / 90
|`multi_module` |`feature`, `tech_debt` |1,500,000 / 120 |2,500,000 / 180
|`multi_module` |`bug_fix` |1,200,000 / 90 |2,000,000 / 150
|`broad` |`feature`, `tech_debt` |2,000,000 / 180 |3,500,000 / 240
|`broad` |`bug_fix` |1,500,000 / 120 |2,500,000 / 180
|===

All other pairs (every pair with `scope_estimate` `none`, and every pair with `ChangeType` `enhancement`, `verification`, or `analysis`) are `fallback` pairs. A fallback pair has no absolute anchor and is checked against normalized ceilings instead: tokens per changed file above 50,000, worked seconds per task above 900 (unanchored), a single phase's share of the plan's tokens above 0.50, or tokens per deliverable above 500,000. The canonical reference plan for the table is a surgical bug fix of 958,064 tokens over 2 files.

The values mirror `plan-marshall`'s budget anchors; re-verify them against the latest `plan-marshall` version before implementing.

== Sub-Agent Question Batching & Non-Blocking Escalation
_See Requirements link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint], link:../Requirements.adoc#PM-WF-14[PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution]_

Sub-agents operating at `scope = "entity"` are strictly forbidden from directly prompting the human operator or blocking in an interactive wait loop.

=== Architectural Rationale

1. *Turn and Lock Conservation*: A sub-agent blocked waiting for human input holds an active host sub-session and prevents parallel sibling sub-agents from completing their fan-out batch.
2. *Host Elicitation Limitations*: Agent hosts (Claude Code, OpenCode, Antigravity) do not reliably route MCP elicitation requests or interactive user-question modals originating from inside background/child sub-agents to the top-level terminal UI.
3. *Single Bounded Escalation Guarantee*: Collecting ambiguities across all sub-agents in a phase allows the parent session to present a single, consolidated question batch to the operator rather than interrupting the user piecemeal.

=== Prompt Envelopes & Entity Escalation Protocol

When a sub-agent encounters an ambiguity or requires an operator decision during `phase-2-refine`, `phase-3-outline`, or `phase-5-execute`, it follows one of two non-blocking paths:

1. *Best-Judgment Completion with Attached Prompt Envelopes (`refine_prompt`, `outline_prompt`, `escalate_ask`)*: In planning and outline states (`refine`, `outline`), the sub-agent completes its draft artifact using its best engineering judgment and includes structured open questions in the `questions` array of its `submit` link payload. Each question conforms to the `BatchedQuestionEnvelope` schema below, where every selectable option carries a canonical `branch_key` enum value bound to a downstream workflow transition.
2. *Immediate Entity-Scoped `escalate` (`status: "blocked"`)*: In execution states (`execute`) where a task cannot safely proceed without an authoritative decision (e.g., an undeclared scope deviation or contradictory interface contract), the sub-agent invokes `pm_do(scope="entity", link="escalate:<task_id>", args={"question": "...", "options": [...]})`. The server persists the pending question in the plan store and immediately transitions the entity to `envelope.blocked` (an immutable terminal state for that dispatch). The sub-agent returns `status: "blocked"` to the parent session.

=== Parent Session Aggregation (`*.awaiting_answers`)

When the parent session processes `returned:<dispatch_id>` for all dispatches in the current state and the plan store contains one or more unresolved `BatchedQuestionEnvelope` records:

1. The engine transitions the parent plan to `<phase>.awaiting_answers` (e.g., `refine.awaiting_answers`, `outline.awaiting_answers`, `execute.awaiting_answers`).
2. The representation exposes the consolidated questions in `facts.pending_questions` and offers an `answer_questions` link (accepting a map of `question_id -> branch_key` via MCP elicitation or model-relayed user answers for non-authorizing clarifications, as governed by `PM-SEC-3`).
3. Submitting `answer_questions` resolves the batched questions in one transition and advances the plan (or re-dispatches the unblocked envelope with a new `dispatch_id`).

== Role Registry, Effort Level Ladder (Levels 1–7) & Variant Installation
_See Requirements link:../Requirements.adoc#PM-WF-14[PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution], link:../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

`PM-MCP` decouples workflow dispatch states from concrete LLM model identifiers through a two-stage resolution pipeline:

1. **Role Resolution**: Maps a dispatch's role key to an abstract **effort level** (`level-1`..`level-7` or `inherit`).
2. **Ladder & Variant Resolution**: Maps that level and the scope's recorded `client_id` (`mcp/entry.json`) to an installed per-client agent variant pinning the runtime-specific `model` and `effort`.

The role registry, the level vocabulary, the resolve chain, the ladders, and the variant naming mirror `plan-marshall` (`plan-marshall/standards/effort-roles.md`, `effort-levels.md`, `effort-variants.md`, ADR-021), verified at commit `1d4a1da37`. Re-verify against the latest `plan-marshall` version before implementing.

=== Role Registry & Lookup Hierarchy

Configured values are the strings `level-1` .. `level-7` or `inherit`; any other value is a hard error on read. There are no mandatory keys and no built-in per-role defaults: an unconfigured role resolves to `inherit`.

[cols="2,2,4"]
|===
|Group |Sub-keys |Where the sub-keys fire

|`plan.phase-2-refine.effort`
|`default`
|The phase's dispatches (refine body, issue-body reader ingestion, q-gate validation).

|`plan.phase-3-outline.effort`
|`default`
|Outline dispatches, including architecture enrichment.

|`plan.phase-4-plan.effort`
|`default`
|Task planning dispatches.

|`plan.phase-5-execute.effort`
|`default`, `verification-feedback`
|`default`: task envelopes; `verification-feedback`: per-finding FIX / SUPPRESS / ACCEPT triage of build findings.

|`plan.phase-6-finalize.effort`
|`default`, `verification-feedback`, `post-run-review`
|`default`: finalize dispatches such as create-pr and pre-submission self-review; `verification-feedback`: Sonar, review-bot, and plugin-doctor finding triage; `post-run-review`: lessons capture and plan retrospective.

|`orchestrator.effort`
|`analyze`, `decompose`, `reader` (plus `default` slot and `max` ceiling)
|Epic landing analysis, decomposition, and untrusted-text ingestion. Resolves under the top-level `orchestrator` block, not under `plan`.
|===

Phase 1 (`init`) runs inline and has no role. A group may be a plain string (one level for every sub-key) or an object with per-sub-key values and a `default` slot.

==== Deterministic Role Lookup Algorithm

1. **Plan roles**: `plan.<phase>.effort.<subkey>` -> `plan.<phase>.effort.default` -> `plan.<phase>.effort` (string) -> `plan.effort` -> `inherit`.
2. **Orchestrator roles**: `orchestrator.effort.<surface>` -> `orchestrator.effort.default` (or the plain string) -> `plan.effort` -> `inherit`, then clamped to `orchestrator.effort.max` on the ordinal ladder (`min(resolved, max)`; an unset `max` is a no-op). Orchestrator dispatches always name their surface so the clamp cannot be bypassed.
3. **Unknown sub-key**: A warning (`WARN_UNKNOWN_EFFORT_ROLE`) is logged and the lookup continues at the `default` slot; an unknown key never blocks a dispatch.

=== Effort Ladders (`.plan/local/effort-ladder.json`)

The ladder maps each level to a concrete `model` and `effort` per client runtime. `.plan/marshal.json` carries only the target-neutral levels; model pins are never stored in git-tracked configuration (ADR-021).

* **Machine-local ladder**: The git-ignored file `.plan/local/effort-ladder.json` holds `{"targets": {"<client_id>": {"level-N": {"model": <string|null>, "effort": <string|null>}}}}`, the format `plan-marshall` uses. `model: null` means unpinned (the dispatch inherits the session model).
* **Compiled defaults**: When the file or a target entry is absent, the ladder compiled into the client profile (link:client-profiles.adoc[Client Profiles Specification]) applies and the representation carries a warning; the project setup workflow seeds the file from the compiled defaults.
* **Narrow but never escalate (ADR-021)**: A ladder entry serves only its own level and never provisions a model beyond the capability of the resolved rung. ADR-021 (status *Proposed* in `plan-marshall`) also prescribes an entry-kind discriminator (`local` / `provider`) that `plan-marshall`'s current file format does not yet carry; verify its status before implementing the ladder reader.
* **Capability gating**: A variant for a `(model, effort)` pair is installed only when the model alias supports that effort (for Claude, `xhigh` and `max` depend on the alias). A level whose variant is not installed dispatches on the canonical `inherit` variant. The resolver never names a variant that is not installed.

=== Per-Client Variant Installation (`execution-context`)

Because agent hosts such as Claude Code and OpenCode load sub-agent definitions from static files at session startup and bind model/effort settings plus allowed tool lists in agent frontmatter, `pm-mcp client install <client>` renders and installs the per-level variant files into the host's agent directory:

* **Worker Family Variants**: `execution-context-level-1` through `execution-context-level-7` (for installed levels) and `execution-context` (the `inherit` variant).
* **Reader Family Variants**: `execution-context-reader-level-1` through `execution-context-reader-level-7` and `execution-context-reader` (`inherit`), so a reader role resolves at any level like every other role.
* **Rendered at Install Time**: Variant files are rendered from the templates in the embedded bundle and the effective ladder (`.plan/local/effort-ladder.json` or the compiled defaults). The bundle manifest marks them `rendered`; the installer verifies the template digest and records the rendered digest in `install-records.json`. A ladder change takes effect after `pm-mcp client update` and a host restart.
* **Mandatory MCP Tool Inclusion**: Every installed `execution-context` worker variant **must** include the `PM-MCP` tool surface (`mcp__plan-marshall__pm_state`, `mcp__plan-marshall__pm_do`, `mcp__plan-marshall__pm_build`, `mcp__plan-marshall__pm_lsp`, `mcp__plan-marshall__pm_skill` or host-equivalent wildcard `mcp__plan-marshall__*`) alongside host file/shell tools (`Read`, `Write`, `Edit`, `Glob`, `Grep`, `Bash`). Without these MCP tool permissions, a sub-agent cannot execute `start: pm_state(...)` or submit its work via `pm_do`.
* **Concise Universal Worker Body**: The prompt body of every `execution-context-*` variant is reduced to a deterministic 5-step execution loop:
** Load `skill://pm/core` and every URI listed in `skills[]` via `pm_skill` (or `resources/read`); if any load fails or returns no content, stop without performing work and return `status: error` with `display_detail: "skill load failed: <uri>"`.
** Call the exact `start: pm_state(...)` command from the dispatch prompt.
** Perform the judgment or code/test authoring required by the returned state representation.
** Follow `pm_do(scope="entity", link="...", args={...})` until the entity representation reaches a terminal state (`links[0]`).
** Return `{status, display_detail}` to the caller (the dispatching session adds host-reported `token_usage` on `returned:<dispatch_id>`) without asking the user questions or spawning sub-agents.
* **Persona & Execution Lane Flattening**:
** *Personas*: The server resolves persona DAGs (`composes:` and `profiles:` with cycle rejection) at representation-build time, flattening them into `skills[]` URIs (`skill://pm/core` + `skill://pm/domain/...`). The legacy 1,500-line `persona-plan-marshall-agent` is stripped of Bash/CLI hygiene rules (roughly two-thirds of its volume) and distilled into `skill://pm/core`.
** *Execution Lanes*: Execution postures (`minimal ⊏ standard ⊏ full`, selected at `phase-1-init`) prune optional workflow elements server-side while enforcing **floor immunity** (a lane override of `off` on core or derived-state elements is ignored and noted in diagnostics; an unresolved `ask` element is dropped only when its external provider is absent).

== Reader Agent Family (`execution-context-reader`)
_See Requirements link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint], link:../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

When a workflow ingests untrusted free-form external content—such as external web pages or GitHub/GitLab issue descriptions—`PM-MCP` isolates the untrusted payload inside the **`execution-context-reader`** agent family. Pull request review comments and static-analysis messages are not dispatched to a reader per finding; they pass one batched deterministic validation pass (the same validator as Boundary 2) before triage, as in `plan-marshall` (`plan-marshall/workflow/verification-feedback.md`).

The reader contract mirrors `plan-marshall` (ADR-003, `agents/execution-context-reader.md`, `untrusted-ingestion`), verified at commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing. The containment boundary is the deterministic validator, not the reader's restricted tool surface: the tool surface only bounds the blast radius of a hijacked reader.

=== Two-Boundary Containment Architecture

[source,text]
----
Untrusted External Source (Web / Issue / PR Body)
                      │
                      ▼
┌──────────────────────────────────────────────────────────┐
│ Boundary 1: Reader Sub-Agent (execution-context-reader)  │
│  • Tools: WebSearch, WebFetch, Read, Grep ONLY           │
│  • WebFetch restricted to the domain allowlist           │
│  • NO MCP Tools (no pm_do, pm_state, pm_build, pm_start) │
│  • NO Write, Edit, or Bash tools                         │
│  • Output: Structured candidate JSON/text in response    │
└─────────────────────────────┬────────────────────────────┘
                              │ Plain-text response to parent session
                              ▼
┌──────────────────────────────────────────────────────────┐
│ Parent Session (dispatching plan or epic)                │
│  • Treats reader output as opaque untrusted candidate    │
│  • Calls pm_do(link="ingest_candidates:<dispatch_id>",   │
│                args={candidates, status, display_detail})│
└─────────────────────────────┬────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────┐
│ Boundary 2: Deterministic Server-Side Validator (PM-MCP) │
│  • Enforces strict JSON schema & length/charset bounds   │
│  • Rejects/clamps per closed schema (no extra keys)      │
│  • Rejects URLs whose host fails the domain allowlist    │
│  • Persists validated records to findings/references     │
└──────────────────────────────────────────────────────────┘
----

=== Normative Reader Constraints

1. *Strict Read-Only Host Tool Allowlist*: Installed `execution-context-reader` variants declare exactly `WebSearch`, `WebFetch`, `Read`, and `Grep` (or client-profile equivalents). `Write`, `Edit`, `MultiEdit`, `Bash`, and the host sub-agent tool (`Agent`/`task`/`invoke_subagent`/`spawn_agent`) are strictly excluded.
2. *Zero MCP Tools*: Reader variants are provisioned with **zero `pm_*` MCP tools**. Unlike worker sub-agents, a reader sub-agent does not call `pm_state` or `pm_do`. Instead, the server embeds the extraction schema and target source locators directly inside the rendered `dispatch` prompt's `reader_contract` block. Even if adversarial prompt injection inside an issue body or web page hijacks the reader sub-agent's instructions, the sub-agent has no tool capable of mutating workflow state, modifying files, or executing shell commands.
3. *Deterministic Server Validator Seam*: The reader sub-agent returns its extracted candidate records as structured text to the dispatching parent session. The parent session relays that candidate payload into the paired server validation link (e.g., `ingest_candidates:<dispatch_id>`), which simultaneously records the `returned:<dispatch_id>` observability metrics and runs the compiled deterministic validator before writing any candidate to `references.json` or `findings.jsonl`.
4. *Outbound Domain Allowlist*: `WebFetch` from a reader is restricted to the operator-maintained WebFetch domain allowlist (host permission rules installed by the client bundle). Because the reader holds untrusted input, file read access, and outbound fetch at once, the allowlist is what closes the exfiltration path for bytes read via `Read`.
5. *Validator Duties*: The deterministic validator (a) enforces the extraction schema (`additionalProperties: false`, `maxLength`, `maxItems`, `pattern`) and rejects structural violations, (b) clamps over-long strings and arrays, and (c) re-checks every URL-bearing field against the same domain allowlist, rejecting unknown or red-flag hosts. It does not attempt to detect or strip prompt-injection text; only a `status: success` result is persisted.
6. *Separation from Citations-Only Rule*: Reader containment is a security boundary (`PM-SEC-1`) and must never be conflated with the citations-only context-conservation rule used by trusted read-only worker sub-agents.

== Orchestrator Epic Plan Emission (`emit:<plan>`) & Epic Coordination
_See Requirements link:../Requirements.adoc#PM-WF-5[PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint], link:../Requirements.adoc#PM-WF-15[PM-WF-15: Epic Plan Emission & Cross-Plan Merge Mutex]_

An orchestrator epic (`scope = "epic"`) decomposes a multi-plan initiative into workstreams and staged plan specifications, tracks cross-plan dependencies and surface disjointness, reconciles landing outcomes, and coordinates shared repository locks.

=== Why Epics Emit Plans Rather Than Dispatching Sub-Agents

A plan (`scope = "plan"`) is a top-level workflow that dispatches its own leaf sub-agents (`scope = "entity"`). Under the single-level leaf constraint (`PM-WF-5`), a sub-agent can never spawn child sub-agents. Consequently, an epic **must never** invoke a child plan via a `dispatch` link or launch it inline.

Instead, the epic state machine exposes the **`emit:<plan_id>`** hypermedia link (`rel = "emit"`, `form = "submit"`):

* *Surface Disjointness Gate*: While building the epic representation, the server computes the expected file/module footprint surface of every staged plan waiting in the workstream queue against all currently live (`launched` or `running`) plans. A single server-side reader evaluates expected surfaces; an `indeterminate` surface is **never** treated as disjoint, and `absent`, `unlistable`, and `unreadable` surfaces remain distinct states (ADR-019). Only plans whose expected surface is provably disjoint from all active plans (and whose prerequisite plans have `shipped`) have an `emit:<plan_id>` link rendered.
** *Surface Entries*: Expected surfaces may contain files, directories, and globs; directories are prefix-matched and globs expanded, never dropped. An entry must name a git-tracked path or glob inside the plan's write boundary; an entry under a git-ignored tree (for example `.plan/local/**`) or outside the workspace makes the surface `unreadable` with reason `untracked_surface`. An entry that cannot be evaluated makes the surface `indeterminate`; neither is ever read as disjoint.
** *Stated Tallies*: The gate publishes per-state tallies over the whole candidate population in `facts` (`disjoint`, `overlapping`, `indeterminate`, `absent`, `unlistable`, `unreadable`), each with a stated zero. An empty overlap list beside a non-zero `indeterminate` count is reported as `unchecked`, never as a pass, and underivable surfaces are never folded into the disjoint count.
* *Emission Transition (`launched`, Never `running`)*: When the model follows `pm_do(scope="epic", link="emit:<plan_id>", args={})`, the server atomically updates the plan's queue row `.plan/orchestrator/<epic_id>/queue/<plan_id>.json` to `status: "launched"` (with `emitted_at` timestamp) and returns the exact operator entry command in `facts.emitted_command`:
+
[source,text]
----
pm-mcp enter --client <client_id> plan <plan_id> --from-epic <epic_id>
----
+
The invariant *Emit is not running, and `auto_emit` never automates the start* is strictly enforced: `auto_emit` only pre-renders eligible `emit:<plan_id>` commands in the representation; only the human operator starts the new plan session.

* *Automatic Observation of `running` via Child `mcp/entry.json`*: When the operator runs the emitted entry command in a new host session, `pm-mcp enter` writes `.plan/local/plans/<plan_id>/mcp/entry.json` (recording `--from-epic <epic_id>`). The next call on the epic scope reads the child plan's entry record under the epic lock and transitions the epic's queue row for `<plan_id>` from `launched` to `running` without requiring manual status updates in the epic session; no file watcher is involved.

=== Git-Distributed Epic Ledger & Per-File Store Layout (ADR-024)

To allow epic state to merge cleanly across worktrees and machines via Git without monolithic file conflicts, the daemon persists epic state under `.plan/orchestrator/<epic_id>/` using a strict per-concern file split:

[cols="2,2,3"]
|===
|Path |Writer Discipline |Contents & Invariants

|`status.json`
|Daemon only (atomic write-and-rename under epic lock).
|Epic header metadata, active workflow state (`orchestrate.*`), workstream definitions, and `format_version`.

|`queue/<PLAN-ID>.json`
|Daemon only (exclusive create `CREATE_NEW` on addition; row-local read-modify-write on update).
|One file per staged plan tracking the 10-state plan vocabulary partitioned into `live` (`staged`, `ready`, `launched`, `running`, `blocked`), `terminal.shipped` (`merged`, `completed`), and `terminal.closed_unshipped` (`abandoned`, `superseded`, `split`). Executing child plans **never** write to `queue/` directly.

|`inbox.jsonl`
|Append-only via the plan-scope outbox link (<<plan-scope-outbox-link>>); claim-on-consumption under epic lock.
|Structured cross-scope envelopes written by executing child plans (scope deviations, blocker reports, process findings, landing notifications). Supports only three valid in-place status mutations (`pending` -> `claimed` -> `processed`) and distinguishes the three empty states (`no_file`, `empty_file`, `all_processed`) from `unreadable` (reported with the failing line), which is never read as empty.

|`landings.jsonl`
|Append-only under epic lock when a landing notification is reconciled.
|Structured landing history records for completed or closed child plans (<<server-derived-landing-facts>>). Each landing carries the plan's whole findings ledger as `findings[]`, so the epic never depends on the archived plan directory to read them.

|`spec.md`
|Written only through epic-scope `submit` links.
|The epic specification: workstream and staged-plan sections, including each staged plan's claim sections and expected surface. Served as `pm://epic/{epic_id}/spec/{section}` (link:mcp-tools.adoc[MCP Tools Specification]).

|`resume_anchor.md`
|Daemon-rendered markdown artifact.
|Human- and clone-readable queue overview and resumption summary. Regenerated automatically on merge conflict; regeneration refuses with an explicit diagnostic if any `queue/<PLAN-ID>.json` source file is unreadable.
|===

[#plan-scope-outbox-link]
==== Plan-Scope Outbox Link (`outbox:send`)

Every plan state of a plan whose `mcp/entry.json` carries `from_epic` offers `outbox:send` (rel `submit`, form `submit`, free `kind:enum[scope_deviation|blocker_report|process_finding|landing_notification],summary:text[1..200],body:text[1..16384]`). The target inbox is derived by the store from `from_epic` and the sending `plan_id`; the caller supplies no path or epic identifier. `landing_notification` is emitted only by `emit-landing`. Following the link appends one message and never changes the plan's own state.

[#epic-landing]
=== Epic Landing (`land`)
_See Requirement link:../Requirements.adoc#PM-WF-15[PM-WF-15: Epic Plan Emission & Cross-Plan Merge Mutex]_

Ledger changes are edited in the shared epic worktree (link:filesystem-layout.adoc#shared-epic-worktree[Filesystem Layout Specification]) and reach the default branch only through the `land` link of an epic scope:

1. *One Landing for All Epics*: A landing covers every pending change in the shared epic worktree, whatever epic made it, in one pull request from the epic branch. There are never concurrent per-epic landing pull requests.
2. *Repository-Wide Serialization*: The landing holds the repository-wide epics-worktree lock for its git steps; a concurrent `land` waits for the lock or is answered with the open pull request.
3. *Ledger Paths Only*: The landing stages and commits only `.plan/orchestrator/**`, even though the worktree holds nothing else.
4. *Pull-Request Reuse & Composition*: A repeated landing reuses the open pull request of the epic branch and never opens a duplicate; title and body are composed from the landing snapshot (epics touched, queue rows changed, landings and inbox records added), never from plan artifacts.
5. *Gate*: Required CI checks only. The plan pre-merge review barrier (link:phase-workflows.adoc[Two Fail-Closed Barrier Predicates]) does not apply: a ledger-only diff draws no review-bot participation (`.plan/**` is excluded from review bots), so Predicate 2 could never be satisfied.
6. *Merge Confirmation*: The landing waits for a terminal outcome (`merged`, `ejected`, `closed`, or `timed_out`) and is stamped `landed` only from the provider's observed pull-request state (`merged`, with the merge commit on the base branch), never from a merge command's return value or exit code.
7. *Post-Merge*: The primary checkout's default branch is fast-forwarded when it is clean and checked out; the epic branch is resynced to the new default branch without removing the worktree and without discarding ledger writes made after the landing snapshot.
8. *Failure*: CI failure, queue ejection, or wait timeout stops the landing and reports it; worktree and branch are left exactly as they were (no reset), so following `land` again resumes.

[#server-derived-landing-facts]
=== Server-Derived Landing Facts, Spec Re-Grounding & Cross-Plan Locks

[[_server_derived_landing_facts_spec_re_grounding_cross_plan_locks]]
1. *Server-Derived Landing Facts (`n/a` vs. `unknown`)*: When a child plan reaches `completed` and merges, the daemon derives objective landing facts directly from the git commit history, plan audit log, and realized footprint store (commits merged, files changed, tasks completed, loop-back count, test/coverage deltas). Values that do not apply to the plan's profile are recorded as `"n/a"`, while values that could not be read due to missing artifacts are recorded as `"unknown"`—degraded answers are never folded into `"n/a"`. The model in the epic session submits only the semantic landing analysis and downstream impact judgment via `submit_landing:<plan_id>`.
** *Landing Shape*: A landing record is the landing envelope that `emit-landing` writes, defined once in link:phase-workflows.adoc#_landing_envelope_emit_landing[Phase Workflows Specification, Landing Envelope] (identity and merge facts, figures, step record, review facts, `findings[]`, narrative and amendments, completeness, one landing per `(plan_id, landing_kind)`, and the non-landing record written when nothing merged); `landings.jsonl` stores it unchanged.
** *Squash-Aware Landing Commit*: The landing commit is located as the base-branch commit whose subject ends with `(#<pr_number>)`; a two-parent merge-commit lookup is never the only tier.
** *Fact States*: `"n/a"` is legal at the pull-request and merge keys only for `ad_hoc` landings, and every `"n/a"` names the rule, derived from plan data, that made the fact inapplicable. A fact whose source question no longer applies after the observed event (for example the provider's mergeable state after the pull request merged) is recorded as `"not_applicable_after_merge"`, distinct from both `"n/a"` and `"unknown"`; a genuinely failed read stays `"unknown"` and keeps the landing incomplete. A fact that is `"unknown"` on every landing of an epic is surfaced as a detector defect.
** *No Partial Landing*: A landing without its fact block is refused at write time (`landing_facts_missing`); it is never persisted partially.
** *Shipped-Without-Landing Reconciliation*: Every epic representation compares the queue rows in `terminal.shipped` with `landings.jsonl`. Rows without a landing record are listed in `facts.unlanded_shipped` (count and `plan_id` values; the count is always stated, zero included) and offer `reconcile_landing:<plan_id>`, which derives the landing facts server-side from the child plan's archived stores and git history. A shipped row is never treated as landed without a landing record.
2. *Specification Corpus Re-Grounding*: When reviewing staged specifications against repository `HEAD`, the epic workflow offers read-only analysis dispatches (or an inline fallback link) whose entity scope exposes only a draft `submit` link (enforcing no direct ledger writes). Every persisted re-grounding claim verdict is explicitly labeled `observed` or `hypothesis`, where every `hypothesis` must name the specific repository file or artifact that confirms or refutes it.
** *Claim-Section Parse States*: Every claim section of a staged specification (`spec.md`) parses to exactly one of `absent`, `empty`, `unreadable` (a table or prose where a bullet list is expected, or a heading that matches only case-insensitively), or `parsed`. `unreadable` blocks admission of that row (no `emit` link; the reason is stated in `facts`) and never passes vacuously; `absent` and `empty` are reported as distinct states.
** *Verdict Record*: A persisted re-grounding verdict record carries `claim` (section and claim index), `label` (`observed` | `hypothesis`), `verdict` (`corroborated` | `contradicted` | `partially_exercised` | `unverifiable`), `checked_at` (the commit SHA the claim was checked against), `by` (the `dispatch_id` or scope that produced it), `scope_change` (`none` | `rescoped`), `exercised_path` (the components actually tested, for example `reader -> classifier`), and `evidence` (text). `contradicted` is admissible only when `exercised_path` covers every component the claim names; otherwise the verdict is `partially_exercised`.
** *Running Rows Are Not Re-Scoped*: The epic offers no spec-editing or re-scoping link for a queue row in `launched` or `running`; a re-grounding verdict that would re-scope such a row is recorded as pending and applied only after the row reaches a terminal state. Overlapping work waits for the running plan to land.
3. *Fixed Lock Hierarchy & Cross-Plan Coordination Primitives*: All representation and resource reads execute against atomic filesystem snapshots without holding scope locks during long-running script or build jobs, and whenever an operation mutates multiple scopes, short transaction locks are acquired in a strict global order (`plan` lock -> `epic` lock -> `machine` lock), while long-lived claims are leases (link:store-schemas.adoc[Store Schemas Specification], `PM-IMPL-7`). The server serializes PR merge execution across concurrent plans via a fair per-repo FIFO admission queue and merge lease in `~/.plan-marshall/mcp/state/merge-queue.json`, while shared review-bot rate-window claims (e.g., CodeRabbit hourly windows) are leases in `~/.plan-marshall/mcp/state/review-bot-windows.json`. Machine-wide build concurrency is bounded by the slot cap in `~/.plan-marshall/mcp/machine-config.json`, where stale slot reaping (`ProcessHandle.of(pid)`) executes inside the same atomic state transition as new job admission and the FIFO queue never drops a submitted build.
