== Architecture Enrichment Judgment Links & Project Setup State Machine

Only semantic module enrichment (`responsibility`, `purpose`, and `key_packages` with their reasoning) requires model judgment. `PM-MCP` replaces the legacy `marshall-steward` first-run wizard (Steps 1–16) and its `upgrade` verb with one dedicated **`project-setup`** state machine (`classpath:/workflows/project-setup.pmwf`), hosted by the project's workspace scope (`scope workspace`; entered with `pm-mcp enter --client <client> workspace` and driven through `pm_state` / `pm_do` with `plan_id: "NO_PLAN"`, `PM-ARCH-4`; its state lives in `workspace/mcp/status.json` of the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/`, link:../filesystem-layout.adoc#workspace-home[Filesystem Layout Specification, Workspace Home]). The workspace scope exists once the project is enrolled: `pm-mcp operator enrol` creates the project's machine store for every project, and the first run of the setup workflow creates `.marshall/`. Enrolment (`pm-mcp operator enrol`, host tools) therefore precedes the workspace scope and is never a state of the setup workflow; the credentials of the git and provider integrations are verified in `setup.verify-credentials`, and every other missing secret is handled by the credential check (`pm-mcp operator credentials`, `PM-CRED-3`) where the credential is used. The workflow has one start state, `setup.entry`, an `auto` state that routes by server facts: without `.marshall/config/` (first run) to `setup.prepare-workspace`, which creates `.marshall/config/` with the copies of the binary's default workflow units (the JSON team files stay absent until a deviation is configured, since they are sparse), otherwise to the reconcile path starting at `setup.reconcile-config`. The workflow unit `project-setup.pmwf` itself is compiled into the binary and is never project-owned: the setup workflow must be able to repair a project whose units fail verification. The workflow has no terminal state: the workspace scope lives as long as the project's enrolment, and every run ends in the resting `link` state `setup.completed`, whose `reconcile` link returns to `setup.entry` for the next run. A project that also runs on legacy `plan-marshall` starts from a clean slate like any other: `PM-MCP` imports nothing from its `.plan/` (`PM-MIG-2`), so its first setup run takes the first-run path; setup never reads or writes `.plan/`. Its states are catalogued in the link:../state-catalogue/06-setup-epic-other.adoc#state-catalogue-setup[State Catalogue, Project Setup: `setup`].

[#setup-integration-variants]
*Integration variants* (`setup.select-integration-variants`): Every git and provider operation is a contract of a provider module (link:../../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]) with two interchangeable implementations: the *native variant* (in-process JGit, respectively the GitHub or GitLab client over `cui-http`, authenticated with the agent credential of the token lane) and the *CLI variant* (the enrolled `git`, `gh`, or `glab` host tool, acting with the operator's ambient authentication). The project's variant is decided explicitly, per integration, by the operator in this state; there is no implicit default, the compiled default table holds no variant, and `machine-config.json` `project_defaults` cannot carry one.

* *Integrations*: `git` (the `git.*` contracts: repository, worktree, and transport operations, among them the working-tree digest `git.worktree-sha`, one operation with the same digest in both variants, link:../job-runtime/03-parsers-and-gates.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash]) and the CI provider integration `github` or `gitlab` (the `ci.*` contracts together with the provider's review-thread and code-scanning finding sources, `pm-mcp-findings`). The provider integration asked for is the one the local derivation of `ci_provider` names (a known provider host of the push remote) or the team override `project.json` `ci_provider`; when neither names it, only `git` is asked here, and `setup.select-providers` asks the provider integration once its `configure_providers` link sets the override. The Sonar integration (`pm-mcp-sonar`) has only a native variant and is not asked. One variant holds for all operations of an integration; integrations may differ (for example `git` `cli` with `github` `native`), operations within one integration never do.
* *Decision*: The choice is taken only through the operator channel: following the state's link `select_variants` (rel `next`) opens an elicitation; on a connection without elicitation support it raises the `blocked` condition (link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-blocked[State Catalogue, `blocked`]) whose `facts.operator_command` names `pm-mcp operator config --project <project_id>`. Per integration the elicitation shows `native` as the recommended value, the result of the derived fact `git_native_capability` (for `git`: each repository feature the native variant cannot serve, with its reason), and, for a `cli` choice, that the operator's own ambient identity (credential helper, SSH agent, `gh`/`glab` login, signing key) will act for every operation of that integration. A `cli` choice requires the host tool in the project's enrolment (`cli_tool_not_enrolled` names `pm-mcp operator enrol`). The answer is written to `local-config.json` `integrations.<integration>.variant` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]); the same elicitation captures the commit author `commit_identity {name, email}` while it is unset, prefilled with the operator's global git `user.name` and `user.email` read once as a proposal and confirmed or edited by the operator (never re-read silently afterwards).
* *Validity*: The state passes without a link when every integration it asks for has a stored choice that is still valid. A stored `native` choice is invalid while `git_native_capability` reports a missing capability for it (a repository feature that appeared after the decision: hooks, signing requirement, filter drivers, LFS, submodules, SHA-256 or partial or sparse repositories, an SSH-only remote); the state then asks again and shows the finding. There is no automatic fallback to the CLI variant: switching silently would switch to the operator's credentials.
* *Before the decision*: No git or provider operation runs for the project, in either variant, before the integration it belongs to has a valid choice: every such primitive refuses with `integration_variant_unset` naming the integration and this state, and `pm_start` of the project refuses with the same reason. The derivation of `git_native_capability` itself is no git operation: the server reads the repository configuration and files directly (`extensions.*`, `core.hooksPath`, non-sample files under `.git/hooks/`, `.husky/`, `lefthook.yml`, `.pre-commit-config.yaml`, `.gitattributes` drivers, `.gitmodules`, `lfs.url`, the remote URLs).
* *Model-facing minimality*: The chosen variants, the capability details, and the identity notice are rendered to the operator (elicitation) and served on demand by the operator surfaces (`pm-mcp operator config`, `pm-mcp status`, `pm://project/config`), never pushed into the state's model-facing `facts`, which name only the integrations still undecided (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

[#setup-verify-credentials]
*Credential verification* (`setup.verify-credentials`): An `auto` state that checks, per decided integration, that the chosen variant can act, then refreshes the network derived facts (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts]) with the chosen variants:

* *Native `github`*: resolves the token-lane entry `github` (`PM-CRED-2`, project entry before global entry). For a GitHub App it mints the App JWT (RS256, JDK `Signature`), resolves the App's installation for the repository, and mints an installation token restricted to the repository and a read-only permission set (held in memory per `PM-CRED-5`, never persisted); for a fine-grained or classic personal access token it calls `ci.whoami`. The check derives the network facts `agent_identity` (login, kind, permissions on the repository; operator-only) and `checks_visible`. A credential that cannot read check runs is accepted: the operator is told that `ci.checks` will report `completeness: incomplete`. A token without expiry is accepted and shown on `pm-mcp operator credentials status`.
* *Native `gitlab`*: resolves the entry `gitlab` (project access token, group access token, service-user or personal access token, all accepted alike) and calls `ci.whoami`; an `expires_at` within the credential expiry warning window (link:../timeouts/02-runtime-leases-operator-web.adoc#credential-expiring-window[Timeouts & Budgets Specification]) is reported as `expiring`.
* *Native `git`*: the transport credential is the provider's entry for a provider host and `git-https` for any other HTTPS host; the check resolves the effective push and fetch URLs (with `insteadOf` rewrites), requires `https` after the SSH mapping of known provider hosts and the origin of the credential entry's `url` (`remote_origin_mismatch`, audited), and reads the push remote's refs with `git.ls-remote`.
* *CLI integrations*: no credential is read; the state verifies the enrolled host tool and records that the integration acts as `identity: operator_ambient` (audit record).
* *Committer identity*: the committer of server commits is resolved from the verified agent credential (a GitHub App's `<slug>[bot]` noreply address, the token's user), else the fixed `plan-marshall-mcp` noreply identity; the author is the operator's `commit_identity`. Both variants produce the same author and committer metadata.
* *Failure*: a missing credential or a failing check raises the `blocked` condition with the `pm-mcp operator credentials` command (`PM-CRED-3`); its resolution re-runs the check. A failing check is never a fallback to another variant or credential.

Exit: `setup.project-settings` on the first run, `setup.detect-domains` on the reconcile run; back to `setup.select-integration-variants` when the refreshed facts invalidate a stored `native` choice (for example the network fact `signed_commits_required`, an input of `git_native_capability`).

[#setup-merge-queue]
*Merge-queue probe* (`setup.merge-queue`): The state reports the derived network fact `merge_queue_enforced` (`{enforced, available, check_response_timeout}`, link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts Store]) for the base branch. The project is eligible when a CI provider integration is selected, the derived fact `push_remote` is non-empty, and `available` is not `no`. `available` is `no` only where the provider's answer is readable: GitHub, a repository owned by a user, or a private or internal repository whose organization plan is readable and is not Enterprise Cloud; GitLab, a tier below Premium when the tier is readable. An `indeterminate` or stale value counts as eligible. It passes without a link when the queue is enforced or the project is not eligible. Otherwise it names the provider setting that enables the queue (GitHub: the "Require merge queue" rule of a ruleset on the base branch; GitLab: merge trains with merged-results pipelines) and offers `recheck_merge_queue` (re-derives the fact after the operator changed the setting) and `skip_merge_queue`. The server never changes the setting and persists no key: administrative repository changes need admin scope, which the agent identity does not hold. *Deliberate change vs. `plan-marshall`*: `plan-marshall` provisions the queue (ruleset create or update, `merge_trains_enabled=true`) and persists a `use_merge_queue` opt-in.

In `setup.enrich-architecture`, the engine offers concurrent entity-scoped `dispatch:enrich-<module_id>` links (or direct `enrich:<module_id>` submission links for single-module repositories). The submission parameters mirror `plan-marshall`'s `architecture enrich module` and `architecture enrich package` commands (`manage-architecture/scripts/architecture.py`, purpose values from `manage-architecture/standards/architecture-persistence.md`), verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing:

[cols="2,1,5"]
|===
|Parameter |Required |Content

|`responsibility`
|Yes
|Module description, 1–3 sentences.

|`responsibility_reasoning`
|No
|Sources the responsibility was derived from (for example the README overview or a central type).

|`purpose`
|No
|Module classification, closed enum `library` \| `extension` \| `deployment` \| `runtime` \| `parent` \| `bom` \| `integration-tests` \| `benchmark`.

|`purpose_reasoning`
|No
|Signal the purpose was derived from (for example `packaging=jar`, no runtime dependencies).

|`reasoning`
|No
|Shared rationale, applied to `responsibility_reasoning` and `purpose_reasoning` where the specific field is not supplied.

|`key_packages`
|No
|List of `{package, description, components}`: `package` is a repository-relative path that must resolve to an existing location (the path is the identity key), `description` is 1–2 sentences and required, and `components` optionally names the package's key types. A dotted package identifier is rejected with `invalid_link_args` whose `detail` names `non_resolving_package_key` (link:../mcp-tools/04-errors-and-testing.adoc#rejection-reasons[closed rejection reasons]); only the server-derived `packages` facts of `pm://architecture/modules/{module_id}` may carry dotted names.
|===

The reasoning fields carry the enrichment rationale required by `PM-EXT-3` and are persisted next to the values they justify. *Deliberate hardening vs. `plan-marshall`*: `purpose` is validated against the closed enum; `plan-marshall` documents the same eight values but its CLI accepts any string. The state cannot transition to `setup.commit-changes` until the **`every_module_enriched`** guard evaluates to `true` (every discovered module has a `responsibility`). On the reconcile path the state is scoped to the modules listed in `changed[]` of `pm://architecture/drift`: only those are offered for enrichment, and the state passes without a dispatch when the list is empty; a module listed in `indeterminate[]` is never treated as changed.

*Landing*: `setup.commit-changes` is a `link` state offering the routine decision `land` or `leave`; `land` enters the `call` state `setup.land-changes`, which runs `call git.commit_and_push (message_mode=step_or_fallback, push_mode=if_push_remote)` on the primary checkout with the setup staging set `.marshall/config/**` (team files and workflow units), `.gitignore`, and `.marshall/project-architecture/**` (link:../workflow-dsl/06-reusable-sub-workflows.adoc#_call_site_reuse_matrix_across_workflows[Workflow DSL Specification, Call-Site Reuse Matrix]). Every outcome except `aborted` enters `setup.completed`; `aborted` returns to the decision. `leave` enters `setup.completed` with the changes uncommitted.

=== Steward Wizard Step Mapping

Every step of the `plan-marshall` first-run wizard and every stage sub-step and gate of its `upgrade` verb maps to exactly one disposition: a `project-setup` state, or *retired* with the reason. No wizard step or upgrade gate survives outside the `project-setup` workflow. The wizard steps mirror `marshall-steward/references/wizard-flow.md` and the upgrade stages and gates mirror `marshall-steward/scripts/upgrade.py` and `references/upgrade-flow.md`, verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing.
