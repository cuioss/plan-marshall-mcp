== Architecture Enrichment Judgment Links & Project Setup State Machine

Only semantic module enrichment (`responsibility`, `purpose`, and `key_packages` with their reasoning) requires model judgment. `PM-MCP` replaces `plan-marshall`'s `marshall-steward` first-run wizard (Steps 1–16) and its `upgrade` verb with one dedicated **`project-setup`** state machine (`classpath:/workflows/project-setup.pmwf`), hosted by the project's workspace scope (`scope workspace`; entered with `pm-mcp enter --client <client> workspace` and driven by the entry session through `pm_state` / `pm_do` with `plan_id: "NO_PLAN"`, `PM-ARCH-4`; its state lives in `workspace/mcp/status.json` of the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/`, link:../filesystem-layout/03-project-store.adoc#workspace-home[Filesystem Layout Specification, Workspace Home]). The workspace scope exists once the project is enrolled: `pm-operator enrol` creates the project's machine store for every project, and the first run of the setup workflow creates `.marshall/`. Enrolment (`pm-operator enrol`, host tools) therefore precedes the workspace scope and is never a state of the setup workflow; the credentials of the git and provider integrations are verified in `setup.verify-credentials`, and every other missing secret is handled by the credential check (`pm-operator credentials`, `PM-CRED-3`) where the credential is used. The workflow has one start state, `setup.entry`, an `auto` state that records the run type `setup_run: first_run | reconcile` in the workspace status and routes by it: without `.marshall/config/` a first run to `setup.prepare-workspace`, which creates `.marshall/config/` with the copies of the binary's default workflow units (the JSON team files stay absent until a deviation is configured, since they are sparse), otherwise a reconcile run to `setup.reconcile-config`. Every later fork of the run follows the recorded `setup_run`, never the existence of `.marshall/config/` (which the first run creates at once), so an interrupted first run keeps its first-run path; the next run's `setup.entry` records it anew. The workflow unit `project-setup.pmwf` itself is compiled into the binary and is never project-owned: the setup workflow must be able to repair a project whose units fail verification. The workflow has no terminal state: the workspace scope lives as long as the project's enrolment, and every run ends in the resting `link` state `setup.completed`, whose `reconcile` link returns to `setup.entry` for the next run. The workspace scope is not a plan: the plan outcomes and their fallbacks do not apply to it, and every setup failure rests in one repair state with a path back into the run (<<setup-needs-repair>>). A project that also runs on `plan-marshall` starts from a clean slate like any other: `PM-MCP` imports nothing from its `.plan/` (`PM-MIG-2`), so its first setup run takes the first-run path; setup never reads or writes `.plan/`. Its states are catalogued in the link:../state-catalogue/06-setup-epic-other.adoc#state-catalogue-setup[State Catalogue, Project Setup: `setup`].

[#setup-operator-files]
*Operator files* (`setup.check-operator-files`): An `auto` state that validates the operator file `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]) and the project's effective role set, the shipped set overridden by the machine and project sets (role sets are operator files, link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]). It fails closed: a malformed `local-config.json` exits `malformed`, and a role that a unit of the project names but the effective set does not define, an invalid artifact included, exits `role_undefined` naming the role and the state; both enter `setup.needs-repair`. It seeds nothing and writes no default; an unqualified role is no failure here, because its tasks take their conservative fallback where they arise (`PM-WORK-6`).

[#setup-probe-states]
*Probe states*: A `link` state rests until a link is followed, so no setup link state "passes without a link". Each setup state that asks only when something needs an answer is preceded by an `auto` probe state whose primitive decides, from server facts, whether the question arises: `setup.probe-integration-variants` (`current` -> `setup.verify-credentials`, `needs_answer` -> `setup.select-integration-variants`), `setup.probe-build-map` (`in_sync` -> `setup.probe-new-steps`, `drift` -> `setup.reseed-build-map`), `setup.probe-new-steps` (`current` -> `setup.probe-enrichment`, `changed` -> `setup.offer-new-steps`), `setup.probe-merge-queue` (`not_needed`, the queue enforced or the project not eligible, -> `setup.probe-qualification`, `needs_answer` -> `setup.merge-queue`), `setup.probe-qualification` (`current` -> `setup.probe-enrichment`, `grade` -> `setup.qualify-roles`, <<setup-qualification>>), and `setup.probe-enrichment` (`nothing_to_enrich` -> `setup.commit-changes`, `enrich` -> `setup.enrich-architecture`). A skipped question is therefore an audited probe outcome, never an implicit pass, and a question state is entered only when it has something to ask.

[#setup-questions]
*Setup choices by owner*: A setup choice is taken on the channel of the store it writes. A choice that writes operator configuration (the integration variant, the commit identity, the operator posture in `setup.project-settings`) is taken only through the operator channel: an MCP elicitation where the entry session's connection declared elicitation support, otherwise the state's `facts` name `pm-operator config --project <project_id>` and the entry session follows `retry` after the operator acted; it is never a question record, and a value relayed by the model is never accepted (`PM-WF-12`). A choice the team owns is a content question of the workspace scope: a server-raised question record of class `setup` (link:../store-schemas/14-plan-instance-waivers-questions.adoc#question-record[Store Schemas Specification, Question Record]) with server-owned options, created by the probe that routes to its question state (`setup.merge-queue`, `setup.reseed-build-map`, `setup.offer-new-steps`). It is delivered like every content question, through the web app and through its answer link on the workspace representation while the entry session is open, and additionally as an MCP elicitation where the entry session's connection declared elicitation support (channel `elicitation`); the first valid answer wins, and the project's `questions.mode` and `questions.wait_seconds` set its deadline (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]). On expiry the question state's declared fallback is recorded as an assumption: `skip` for the merge queue, `keep_build_map` for the reseed (a hand edit is never discarded without an answer), and no change for an offered unit (neither `adopt` nor `decline`: `derived_from` stays, so the offer repeats on the next reconcile run). In the link states (`setup.project-settings`, `setup.seed-build-map`, `setup.select-providers`, `setup.configure-finalize`, `setup.commit-changes`) the entry session relays the team's choice directly through the state's links, like a bootstrap choice; these states create no question record.

[#setup-integration-variants]
*Integration variants* (`setup.probe-integration-variants`, `setup.select-integration-variants`): Every git and provider operation is a contract of a provider module (link:../../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]) with two interchangeable implementations: the *native variant* (in-process JGit, respectively the GitHub or GitLab client over `cui-http`, authenticated with the agent credential of the token lane) and the *CLI variant* (the enrolled `git`, `gh`, or `glab` host tool, acting with the operator's ambient authentication). The effective variant of each integration is `native` unless the operator chose `cli`: `native` is the compiled default, an operator choice is stored in `local-config.json` `integrations.<integration>.variant` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), and `machine-config.json` `project_defaults` cannot carry one. The server never writes the default into the operator file.

* *Integrations*: `git` (the `git.*` contracts: repository, worktree, and transport operations, among them the working-tree digest `git.worktree-sha`, one operation with the same digest in both variants, link:../job-runtime/03-parsers-and-gates.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash]) and the CI provider integration `github` or `gitlab` (the `ci.*` contracts together with the provider's review-thread and code-scanning finding sources of the findings contract). The provider integration checked is the one the local derivation of `ci_provider` names (a known provider host of the push remote) or the team override `project.json` `ci_provider`; when neither names it, only `git` is checked here, and a provider integration named by an override that `configure_providers` sets later in the run is checked (variant and credential) by the next reconcile run. The analysis providers (behind the code-analysis contract, among them Sonar through `pm-provider-sonar`) have only a native variant and are not checked here. One variant holds for all operations of an integration; integrations may differ (for example `git` `cli` with `github` `native`), operations within one integration never do.
* *Probe*: `setup.probe-integration-variants` reports `current` when every checked integration's effective variant is valid and `commit_identity` is set, otherwise `needs_answer`. An effective `native` variant (default or stored) is invalid while the derived fact `git_native_capability` reports a used repository feature the native variant cannot serve (hooks, signing requirement, filter drivers, LFS, submodules, SHA-256 or partial or sparse repositories, an SSH-only remote), including a feature that appeared after an earlier run; a stored `cli` choice is invalid while its host tool is not in the project's enrolment (`cli_tool_not_enrolled` names `pm-operator enrol`). There is no automatic fallback to the CLI variant: switching silently would switch to the operator's credentials.
* *Operator choice*: `setup.select-integration-variants` takes the choice only through the operator channel (<<setup-questions>>). Where the connection declared elicitation support, its link `select_variants` (rel `next`) opens the elicitation; per integration that native cannot serve it shows the `git_native_capability` findings with their reasons and, for a `cli` choice, that the operator's own ambient identity (credential helper, SSH agent, `gh`/`glab` login, signing key) will act for every operation of that integration. The operator may instead remove the feature from the repository. The same elicitation captures the commit author `commit_identity {name, email}` while it is unset, prefilled with the operator's global git `user.name` and `user.email` read once as a proposal and confirmed or edited by the operator (never re-read silently afterwards). Without elicitation support the state's `facts` name `pm-operator config --project <project_id>`, which sets the variant and the commit identity. `retry` (rel `alt`, and rel `next` without elicitation support) re-enters the probe.
* *Before a valid variant*: No git or provider operation runs for the project, in either variant, while the integration it belongs to has no valid effective variant: every such primitive refuses with `integration_variant_unset` naming the integration and `setup.select-integration-variants`, and a plan or epic bootstrap of the project routes to `start.setup-required` with the same reason (the bootstrap's commit transaction re-checks it). The derivation of `git_native_capability` itself is no git operation: the server reads the repository configuration and files directly (`extensions.*`, `core.hooksPath`, non-sample files under `.git/hooks/`, `.husky/`, `lefthook.yml`, `.pre-commit-config.yaml`, `.gitattributes` drivers, `.gitmodules`, `lfs.url`, the remote URLs).
* *Model-facing minimality*: The effective variants, the capability details, and the identity notice are rendered to the operator (elicitation) and served on demand by the operator surfaces (`pm-operator config`, `pm-operator status`, `pm://project/config`), never pushed into the state's model-facing `facts`, which name only the integrations that need an operator choice and, without elicitation support, the operator command (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

[#setup-verify-credentials]
*Credential verification* (`setup.verify-credentials`): An `auto` state that checks, per checked integration, that its effective variant can act, then refreshes the network derived facts (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts]) with the effective variants:

* *Native `github`*: resolves the token-lane entry `github` (`PM-CRED-2`, project entry before global entry). For a GitHub App it mints the App JWT (RS256, JDK `Signature`), resolves the App's installation for the repository, and mints an installation token restricted to the repository and a read-only permission set (held in memory per `PM-CRED-5`, never persisted); for a fine-grained or classic personal access token it calls `ci.whoami`. The check derives the network facts `agent_identity` (login, kind, permissions on the repository; operator-only) and `checks_visible`. A credential that cannot read check runs is accepted: the operator is told that `ci.checks` will report `completeness: incomplete`. A token without expiry is accepted and shown on `pm-operator credentials status`.
* *Native `gitlab`*: resolves the entry `gitlab` (project access token, group access token, service-user or personal access token, all accepted alike) and calls `ci.whoami`; an `expires_at` within the credential expiry warning window (link:../timeouts/02-runtime-leases-operator-web.adoc#credential-expiring-window[Timeouts & Budgets Specification]) is reported as `expiring`.
* *Native `git`*: the transport credential is the provider's entry for a provider host and `git-https` for any other HTTPS host; the check resolves the effective push and fetch URLs (with `insteadOf` rewrites), requires `https` after the SSH mapping of known provider hosts and the origin of the credential entry's `url` (`remote_origin_mismatch`, audited), and reads the push remote's refs with `git.ls-remote`.
* *CLI integrations*: no credential is read; the state verifies the enrolled host tool and records that the integration acts as `identity: operator_ambient` (audit record).
* *Committer identity*: the committer of server commits is resolved from the verified agent credential (a GitHub App's `<slug>[bot]` noreply address, the token's user), else the fixed `plan-marshall-mcp` noreply identity; the author is the operator's `commit_identity`. Both variants produce the same author and committer metadata.
* *Failure*: a missing credential or a failing check enters `setup.needs-repair`, whose `facts` name the `pm-operator credentials` command (`PM-CRED-3`); its `retry` re-runs the check. A failing check is never a fallback to another variant or credential.

Exit: by `setup_run`, `setup.project-settings` on the first run, `setup.detect-domains` on the reconcile run; back to `setup.probe-integration-variants` when the refreshed facts invalidate an effective `native` variant (for example the network fact `signed_commits_required`, an input of `git_native_capability`).

[#setup-merge-queue]
*Merge-queue probe* (`setup.probe-merge-queue`, `setup.merge-queue`): The probe reads the derived network fact `merge_queue_enforced` (`{enforced, available, check_response_timeout}`, link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts Store]) for the base branch. The project is eligible when a CI provider integration is checked, the derived fact `push_remote` is non-empty, and `available` is not `no`. `available` is `no` only where the provider's answer is readable: GitHub, a repository owned by a user, or a private or internal repository whose organization plan is readable and is not Enterprise Cloud; GitLab, a tier below Premium when the tier is readable. An `indeterminate` or stale value counts as eligible. The probe reports `not_needed` when the queue is enforced or the project is not eligible. Otherwise it raises a workspace question record whose context names the provider setting that enables the queue (GitHub: the "Require merge queue" rule of a ruleset on the base branch; GitLab: merge trains with merged-results pipelines) and enters `setup.merge-queue`, which waits on it with the options `recheck` (re-enters the probe, which re-derives the fact after the team changed the setting) and `skip` (the fallback on expiry, <<setup-questions>>). The server never changes the setting and persists no key: administrative repository changes need admin scope, which the agent identity does not hold. *Deliberate change vs. `plan-marshall`*: `plan-marshall` provisions the queue (ruleset create or update, `merge_trains_enabled=true`) and persists a `use_merge_queue` opt-in.

[#setup-needs-repair]
*Setup repair* (`setup.needs-repair`): One `link` state covers every setup failure, so every state keeps a path back to `setup.entry` (Rule 3) and no failure links sit on an `auto` state. It is entered from `setup.check-operator-files` (`malformed`, `role_undefined`), `setup.reconcile-config` (`invalid`, `format_refused`), `setup.verify-credentials` (a missing credential or a failing check), every fate of the plain `job` state `setup.discover-modules` other than `succeeded` (`failed`, `refused`, `timed_out`, `killed`, `indeterminate`, `cancelled`), `setup.qualify-roles` (`cancelled`, <<setup-qualification>>), and as the declared fallback of `setup.enrich-architecture` (<<setup-enrichment>>); a per-descriptor parse failure is a finding of a succeeded discovery, never a job failure. Its `facts` name the failed state, the file, the role, or the modules, and the finding, and for a failure the operator must repair, the operator command (`pm-operator config --project <project_id>` for the operator file, `pm-operator roles show <role>` for a role, `pm-operator credentials` for a credential). Links: `retry` (rel `next`) re-enters the failed state; `rewrite_config:<file>` (rel `fix`), offered for a team JSON file refused by format, writes the server-rendered rewrite at the current format (every key still valid carried over, every dropped key named, shown as a diff; xref:06-configuration.adoc#config-upgrades[Configuration Validation & Upgrades Before 1.0]) and re-enters `setup.reconcile-config`. The operator file is never rewritten by a link. The exits of `setup.discover-modules` follow `setup_run`: the first run and a reconcile run without `build-map.json` go to `setup.seed-build-map`, whose exit follows `setup_run` in turn; a reconcile run with `build-map.json` goes to `setup.probe-build-map`.

[#setup-qualification]
*Role qualification at install* (`setup.probe-qualification`, `setup.qualify-roles`): The qualification records the release ships are the release's grading on the harness versions of its own test machine and only a starting point (link:../model-work/01-roles-and-configuration.adoc#qualification-records[Model Work Specification, Qualification Records]). Every setup run grades the roles again whose grading the machine lacks:

* *Probe*: `setup.probe-qualification` computes the roles to grade: every role of the project's effective set that has no valid qualification record for its configuration on the enrolled harness version (major.minor) of the machine, the shipped record included, minus the roles the operator excluded in `qualification.skip_roles` of `local-config.json` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), and every quorum declaration of the project's adjudication unit without a valid decision calibration record when `qualification.skip_decisions` is `false` (link:../model-work/10-decision-panel.adoc#quorum-calibration[Model Work Specification, Quorum Calibration]). On the first run this is every role, because a shipped record is bound to the release's harness versions; on a reconcile run it is the roles whose record a change invalidated (a model, effort, skill, or harness major.minor change, or a new corpus revision). An empty list reports `current`; otherwise the probe enqueues the grading and reports `grade` (it declares `enqueuesJob()`, Rule 1).
* *Grading*: `setup.qualify-roles` is a `composite_job` that runs the grading of `pm-operator roles qualify` for each listed role in turn (link:../model-work/01-roles-and-configuration.adoc#grading[Model Work Specification, Grading]) and writes its record, and, when quorum declarations are listed, calibrates them after the roles and writes their decision calibration records. Its constituents are the grading's worker and judge jobs; they run through the machine's model slots like every model job, and their usage is recorded in the workspace scope's metrics, so a first setup run costs one grading per role. Its facts name each role with its item count and its state. It reports `graded` when every listed role was graded (whether or not it qualified), `incomplete` when a role's grading could not finish (its start-failure guard holds, or its workers were lost beyond the re-offer budget), and `cancelled`. `graded` and `incomplete` exit to `setup.probe-enrichment`; `cancelled` enters `setup.needs-repair`, whose `retry` re-enters `setup.probe-qualification`.
* *Until graded*: A role without a valid record, skipped or not yet graded, is unqualified: its tasks take the conservative fallback (link:../model-work/01-roles-and-configuration.adoc#conservative-fallback[Model Work Specification, Conservative Fallback]). An unqualified role is no setup failure. `pm-operator status` lists the unqualified roles; after a harness update changes the major.minor, the next setup reconcile run grades the affected roles again, and `pm-operator status` names the setup run (`pm-mcp enter --client <client> workspace`) until it has.

[#setup-enrichment]
*Architecture enrichment* (`setup.enrich-architecture`): A model state with fan-out, declared `job llm enrich-module role enrich each setup.enrichment-modules` over the server-computed list of the modules to enrich (link:../workflow-dsl/02-units-jobs-decisions.adoc[Workflow DSL Specification, Model States]): it creates one task of the role `enrich` (class `read_only`, link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]) per module, each with its own entity `enrich-<module_id>`, a single-module repository included. All tasks are queued at once; the role's count and the machine's model slots bound how many workers serve them (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]), and the workers take them through the task protocol (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). The entry session may take them as an optional worker where its host allows session tasks (`PM-WORK-5`). Each worker records its module through its entity's `submit:enrich-<module_id>` link. The submission parameters mirror `plan-marshall`'s `architecture enrich module` and `architecture enrich package` commands (`manage-architecture/scripts/architecture.py`, purpose values from `manage-architecture/standards/architecture-persistence.md`), verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing:

|`reasoning`
|No
|Shared rationale, applied to `responsibility_reasoning` and `purpose_reasoning` where the specific field is not supplied.

|`key_packages`
|No
|List of `{package, description, components}`: `package` is a repository-relative path that must resolve to an existing location (the path is the identity key), `description` is 1–2 sentences and required, and `components` optionally names the package's key types. A dotted package identifier is rejected with `invalid_link_args` whose `detail` names `non_resolving_package_key` (link:../mcp-tools/04-errors-and-testing.adoc#rejection-reasons[closed rejection reasons]); only the server-derived `packages` facts of `pm://architecture/modules/{module_id}` may carry dotted names.
|===

The reasoning fields carry the enrichment rationale required by `PM-EXT-3` and are persisted next to the values they justify. *Deliberate hardening vs. `plan-marshall`*: `purpose` is validated against the closed enum; `plan-marshall` documents the same eight values but its CLI accepts any string. Enrichment is model work, not a question: the modules to enrich are computed by `setup.probe-enrichment`, which enters the state only when at least one module needs enrichment (first run: every module without a `responsibility`; reconcile run: the modules listed in `changed[]` of `pm://architecture/drift`, never a module listed in `indeterminate[]`). The state completes when every entity has its required submission: its return evaluation reports `all_enriched` once every module of that set has a `responsibility`, which exits to `setup.commit-changes`. A task that ends without its `submit:enrich-<module_id>` submission (a `lost` worker included) is offered again by the server within the state's compiled self-remedy budget; a task that ends `asked` waits for its workspace question and is offered again with the answer in its `facts` (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Questions]). The state's declared fallback is `setup.needs-repair`: it is taken when a task is still without its submission after the budget, when a task ends `infeasible` (its evidence in the repair state's `facts`), and at once when the role is unqualified (reason `role_unqualified`, `PM-WORK-6`; the state offers no `retry` of its own). The repair state's `facts` name the unenriched modules, and its `retry` re-enters `setup.enrich-architecture`, which creates tasks only for the modules still unenriched. No condition of this state waits for a model, so the setup never completes with a module unenriched (`PM-EXT-3`).

*Landing*: `setup.commit-changes` is a model `link` state offering `land` or `leave`; `land` enters the `call` state `setup.land-changes`, which runs `call git.commit_and_push (message_mode=step_or_fallback, push_mode=if_push_remote)` on the primary checkout with the setup staging set `.marshall/config/**` (team files and workflow units), `.gitignore`, and `.marshall/project-architecture/**` (link:../workflow-dsl/06-reusable-sub-workflows.adoc#_call_site_reuse_matrix_across_workflows[Workflow DSL Specification, Call-Site Reuse Matrix]). Its `done` (whatever its result `{commit?, pushed, clean}`) enters `setup.completed`; `stepped_out` returns to `setup.commit-changes` with the changes uncommitted. `leave` enters `setup.completed` with the changes uncommitted.

=== Steward Wizard Step Mapping

Every step of the `plan-marshall` first-run wizard and every stage sub-step and gate of its `upgrade` verb maps to exactly one disposition: a `project-setup` state, or *retired* with the reason. No wizard step or upgrade gate survives outside the `project-setup` workflow. The wizard steps mirror `marshall-steward/references/wizard-flow.md` and the upgrade stages and gates mirror `marshall-steward/scripts/upgrade.py` and `references/upgrade-flow.md`, verified at plan-marshall commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing.
