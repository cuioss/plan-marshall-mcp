== Configuration Split (Team Files, Operator Files & Enrolment, Server State)
_See Requirement link:../../Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

In the legacy architecture, `.plan/marshal.json` and `.plan/local/run-configuration.json` mixed declarative project settings, operator posture, frozen extension hook snapshots (`skill_domains`), overridable shell commands (`verify_command`), language-server argument vectors, server bookkeeping, and learned runtime timeouts inside workspace files that the model's file/shell tools could modify.

`PM-MCP` keeps none of these files and imports nothing from them: it never reads or writes `.plan/` (`PM-MIG-2`) and enforces a fundamental security invariant: **Nothing that decides what binary or argument vector executes on the host may be read from a file the model can write.** Configuration and operational state are partitioned by owner class across strictly separated stores, and every file has exactly one owner class: *team* (git-tracked, shared through the repository), *operator* (machine-local, written only through the operator channel), or *server* (machine-local state and caches). A value the server can observe or derive is never configured (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts Store]); a tuning value that calibrates a server algorithm is a compiled constant (link:../timeouts/03-retention-host-config.adoc#configuration-keys[Timeouts & Budgets Specification, Configuration Keys]); an option whose only effect is to weaken a guarantee does not exist.

=== Tier 1: Git-Tracked Team Configuration (`.marshall/config/`)
_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-29[PM-WATCH-EXT-29]_

1. *No Frozen Hook Snapshots*: Unlike `plan-marshall`'s `.plan/marshal.json`, no team file stores frozen hook outputs (skill lists, globs, recipes, `bundle`, `outline_skill`, `workflow_skill_extensions`). The compiled-in domain descriptors in `pm-mcp` are authoritative; domain activation and active profiles are derived (`setup.detect-domains`, per-module Axis-A applicability), and `domains.json` holds only overrides where the derivation is wrong for the repository (`enabled`, `always_on`, `file_globs`, `disabled_profiles`).
2. *No Default Seeding*: Team files are sparse: no compiled default and no domain default is ever written into them. The two exceptions are the build map and the default workflow units, which `setup.prepare-workspace` copies from the binary into `.marshall/config/` when it creates the directory (xref:04-setup-state-machine.adoc#_architecture_enrichment_judgment_links_project_setup_state_machine[Project Setup State Machine]). A domain descriptor contributes no `config_defaults` map; its defaults are compiled defaults of the effective configuration (link:../store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]). `plan-marshall`'s per-domain `project_skills` key does not exist: `PM-MCP` serves only compiled skills, and project automation enters as project-local recipes or enrolled `project_script` steps (project-local vocabulary skills are deferred, link:../../later-improvements.adoc#_l_4_project_local_vocabulary_skills[Later Improvements, L-4]).
3. *Derived Providers & Origin Pinning*: The version-control provider is always `git`; the CI provider is derived from the remote host (derived fact `ci_provider`), overridable only by `project.json` `ci_provider` for self-hosted remotes; whether an integration runs natively or through its CLI is operator posture (`local-config.json` `integrations.<integration>.variant`, xref:04-setup-state-machine.adoc#setup-integration-variants[Setup integration variants]), never a team key, because it decides whose credentials act; code analysis providers (the provider model `pm-mcp-analysis`; Sonar through its adapter `pm-mcp-sonar`, others such as CodeQL through adapters of their own) are configured under `project.json` `integrations.<provider>`, because their coordinates are project facts the server cannot observe. Each adapter maps its provider's results (quality-gate conditions, new issues) to the one closed `analysis_status` enumeration and tags its issues with the provider, so the finalize wait, the remediation policy `remediation.analysis`, and the waiver gates `analysis_gate:<provider>` and `findings:<provider>` are provider-neutral, and a new provider needs only an adapter and its `integrations` entry. For token-lane REST providers (`PM-CRED-2`), a team file only references the credential key; it never decides where a token is sent. The single issuing origin to which the daemon's REST client restricts authentication headers is the origin of the operator-owned credential entry's `url` (`https://`, `PM-CRED-5`), never a value from a model-writable team file (forbidding cross-origin or HTTP downgrade redirects). A provider `verify_command` is never read from a team file; an override is an enrolment `verify_argv` (Tier 2).
4. *One Owner per Key*: Operator posture (integration variants, commit identity, continuation default, question delivery, mode, and wait, outline review, merge policy (`merge.auto_merge`), interaction mode, language, commit trailer, effort ladder, retention) never appears in a team file; a team file that carries it fails validation with `unknown_config_key`.

=== Tier 2: Enrolled Argument Templates & Slot Cap (`<PM_MCP_BASE>`)
_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-32[PM-WATCH-EXT-32]_

To prevent argument injection without requiring the operator to re-enrol the project every time a new module is added, build enrolment binds wrappers and host tools to **typed argument templates** defined by domain support. The templates live in the project's enrolment file (`build.canonical_templates.<build_system>.<verb>` and `build.discovery_templates.<build_system>.<name>`, link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]); they decide what a build job runs, and no separate goal allowlist exists:

[source,json]
----
{
  "build": {
    "canonical_templates": {
      "maven": {
        "module-tests": ["test", "-pl", "{module}"],
        "quality-gate": ["verify", "-DskipTests", "-pl", "{module}"],
        "integration-tests": ["verify", "-Pintegration-tests", "-pl", "{module}"]
      }
    },
    "discovery_templates": {}
  }
}
----

* **Typed Placeholder Validation at Job Time**: `{module}` is the only placeholder; a template names its build profile literally (as `-Pintegration-tests` above), so no profile is ever substituted. When the daemon constructs a build job, it substitutes `{module}` and validates it against its own cached module discovery snapshot (the derived fact `module_discovery`): it must be a discovered module path or coordinate in the repository. A template with any other placeholder is refused when the enrolment is validated.
* **Enrolled Template Precedence**: An enrolled template for a canonical verb replaces the compiled default template for that project; every build job record names the template source (`enrolled` or `compiled_default`), which `pm-mcp status` shows; build representations and `pm_build` results never carry it (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). Templates are never read from a team configuration file (`PM-EXT-6`).
* **Forbidden Free Flags**: Arbitrary user- or model-supplied flags—specifically `-D`, `-f`, `--file`, `-s`, `--settings`, `--init-script`, or shell metacharacters—are never accepted in canonical build jobs. Flags that repository files inject (`.mvn/maven.config`, `.mvn/jvm.config`, `gradle.properties`) are not filtered here; those files are pinned by the wrapper enrolment and refuse the build when changed (link:../job-runtime.adoc[Job Runtime Specification], Verify-Not-Resolve).
* **Machine-Wide Slot Cap & Source Discrimination**: `machine-config.json` holds `max_build_slots`. On every build submission, the scheduler resolves the cap and records both the value and its resolution `source` (`machine_config`, `default`, `invalid`, or `unreadable`) in the job record and `pm-mcp status`, never in a tool result; `invalid` and `unreadable` configuration files are surfaced explicitly in diagnostics and never silently folded into `"default"`.

=== Tier 3: Adaptive Build Timeouts & Crash-Replay State

The daemon maintains learned operational metrics and job journals in Tier 3 server state:

1. *Adaptive Timeout Learning (`build-timings.json`)*: One store per project, `<PM_MCP_BASE>/projects/<project_id>/build-timings.json` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#build-timings-store[Store Schemas Specification, Build Timings Store]), keyed by canonical budget key (for build jobs the normalized canonical command `(build_system, canonical_verb, module_id)`); no repository-local and no machine-level timeout store exists, so a moved checkout keeps its budgets. The server maintains a max-biased learned baseline from observed run durations and allocates each job budget from it; the per-engine floors are never violated, also not by an operator budget, which may exceed the escalation cap but is clamped up to the floor. Which runs feed the baseline is defined in link:../job-runtime/03-parsers-and-gates.adoc#_adaptive_timeout_learning[Job Runtime Specification, Adaptive Timeout Learning]; the blend, the floors, the allocation, the escalation budget and its cap, operator budgets, and `budget_derivation` are defined only in link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets].
2. *No Inherited Timeouts*: Every learned value starts from the project's own finished runs under `PM-MCP`; learned timeouts of legacy `plan-marshall` (`.plan/local/run-configuration.json`) are never read or imported (`PM-MIG-2`). Until a key has a learned value, its budget is the floor default (link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]).
3. *Gate Honesty & Examined Population Tracking*: Before a green build or quality gate clears open findings in `findings.jsonl`, the server's compiled log and report parsers verify that for Maven and Gradle the build log explicitly contains the engine's terminal success marker (e.g., `BUILD SUCCESS` / `BUILD SUCCESSFUL`) in addition to exit code `0`, and that the tool examined a non-empty file/test population capable of reaching the finding's file and category (e.g., `mypy` gates run with `--no-incremental` / cache disabled so untouched files with broken cross-module types are not skipped).
4. *Crash Replay & Atomic Fate Recording*: Every spawned job is recorded in the daemon's write-ahead job journal, one job record `<PM_MCP_BASE>/projects/<project_id>/jobs/<job_id>.json` per job (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]), prior to `ProcessBuilder.start()`. Request status (`running`) is never treated as terminal fate; terminal fate (`succeeded`, `failed`, `failed_unparsed`, `timed_out`, `cancelled`, `killed`, `indeterminate`), derived by link:../job-runtime/01-pipeline-and-subprocesses.adoc#outcome-derivation[Job Runtime Specification, Outcome Derivation], is written atomically at process termination; `refused` is written atomically when the job is refused before spawn, so no journal entry of a refused job ever reaches `ProcessBuilder.start()`. If the daemon restarts while a job record is still `running`, journal replay settles the orphaned job `killed` ("do not retry blindly") by the recovery rules of link:../job-runtime.adoc[Job Runtime Specification] and attaches no synthetic error findings.

[#config-upgrades]
== Configuration Validation & Upgrades Before 1.0 (`PM-EXT-7`)
_See Requirement link:../../Requirements.adoc#PM-EXT-7[PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades]_

In legacy `plan-marshall`, schema and default updates to `.plan/marshal.json` were split across ad-hoc hooks inside `manage-config.py -> sync-defaults` (`RETIRED_STEP_KEY_RENAMES`, `run_at_all -> lane`, lane materialization), separate CLI canonicalizers (`steps-sort`, `normalize-keys`), and one-shot subcommands in `marshall-steward/scripts/upgrade.py` (`migrate-bot-lists`, `validate-bot-lists`). Every new migration required adding prose instructions to `upgrade-flow.md` that the LLM had to read into its context window and execute via separate `Bash` calls—polluting the model's Chain of Thought (CoT) with historical schema trivia even on already-current repositories. The seeding, sorting, and offered-step bookkeeping existed only to keep a materialised copy of compiled defaults consistent.

`PM-MCP` has none of this machinery. Team files are sparse and hold no defaults, so there is nothing to seed, sync, sort, normalize, or offer through a ledger; there is no `system` block, no seed fingerprint, no migration chain (`ConfigMigrationCommand`, `ConfigReconciler`), and no startup migration. It never reads, converts, or upgrades a legacy `.plan/marshal.json` (`PM-MIG-2`).

=== 1. One Version Rule for Every File Kind
_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-21[PM-WATCH-EXT-21]_

Every team configuration file, the operator's `local-config.json`, every enrolment and credential file, every server store, and every workflow unit declares its format version (`format_version`, or the `format` of a unit header). Before 1.0 a binary accepts exactly the current version of each kind and refuses any other with `format_outdated` or `format_newer` naming the file (link:../store-schemas/01-format-and-session-log.adoc#format-versioning[Store Schemas Specification, Format Versioning]); a reader never rewrites a file. The migration mechanism for 1.0 and later (one mechanism for every file kind) is decided at 1.0 with the knowledge of the actual format churn.

=== 2. Validation on Every Read & the Effective Configuration

Every computation of the effective configuration (at `pm_start`, phase handshakes, `pm-mcp enter`, and `setup.reconcile-config`) parses the team files and the operator file against their closed schemas, applies the server-side rules of each key, loads and verifies the project's workflow units (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]), resolves every value along its chain (team or operator file, derived fact, compiled default), and publishes the result with per-key sources as `pm://project/config` (link:../store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]). A non-object root fails before any field access. Unknown keys are `unknown_config_key` findings naming the key path, never silently kept as unread settings; a setup or config link that would write an undeclared key is refused (`invalid_link_args`). Review-bot tokens are checked against the registered bot kinds (`unregistered_kind`) and effort keys against the role registry (`PM_MCP-100`).

=== 3. Upgrade Path: Drain, Release Notes, Offered Default Changes
_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-22[PM-WATCH-EXT-22]_

A new binary reaches a project in three ways, none of which rewrites a file silently:

. *New compiled defaults* take effect at once for every key a team or operator file does not set, because the files are sparse. In-flight plans stay on their plan instance until they adopt a re-composition (§ 5).
. *A `format_version` bump* of a file kind is listed in the release notes with the changed keys. Scope stores of in-flight plans follow the drain rule: `pm-mcp drain` reports the live scopes, and the operator finishes them before upgrading. For a team JSON file the binary refuses (`format_outdated`), `setup.reconcile-config` enters `setup.needs-repair` (xref:04-setup-state-machine.adoc#setup-needs-repair[Setup repair]), whose link `rewrite_config:<file>` writes a server-rendered rewrite at the current format: every key still valid is carried over, every key the new schema no longer admits is listed by name as dropped, and the rewrite is shown as a diff and lands only through `setup.commit-changes`. An operator file is refused by the CLI naming the file and the changed keys, and the operator sets the keys again through `pm-mcp operator config`.
. *Changed default workflow units* are found by `setup.probe-new-steps` and offered in `setup.offer-new-steps`, one workspace question record per changed unit (xref:04-setup-state-machine.adoc#setup-questions[Setup choices by owner]), as a three-way diff: from the default revision the project unit was derived from (`derived_from` in the unit header) to the binary's current default revision, applied to the project's unit. `adopt` applies the hunks and advances `derived_from`; `decline` advances `derived_from` without applying them, so a declined change is never offered again, and a step the team removed from its unit is never restored (only hunks between two default revisions are ever offered). An unanswered offer changes nothing: `derived_from` stays, and the offer repeats on the next reconcile run. The resulting unit is verified like every project unit before it can land.

=== 4. Anti-CoT-Clutter Guarantees

To ensure configuration upgrades never degrade model reasoning or bloat context windows:

1. *Zero Migration Prose in Skills (`PM-SKILL-1`, `PM-EXT-7`)*: No vocabulary skill (`skill://pm/...`) or workflow state prompt ever instructs the model to run `sync-defaults`, `steps-sort`, `normalize-keys`, or `migrate-*` commands, nor mentions retired configuration keys (`enabled_bots`, `run_at_all`, `default:automated-review`, `skill_domains`).
2. *Silent Fast-Path When Current*: At `pm_start`, phase handshakes, and `pm-mcp enter`, the server compares the digests of the team files, the operator file, the project's workflow units, the derived facts, and the compiled defaults with those of the last validated effective configuration; when they match, verification completes in memory and emits **zero** facts, links, or warnings into the state representation.
3. *Upgrades Only in the Setup Workflow*: Offered default changes and format rewrites happen only in `project-setup` (`setup.reconcile-config`, `setup.needs-repair`, `setup.offer-new-steps`), whose receipt lists only non-empty deltas (`format_refusals[]`, `rewrites[]`, `unit_changes_offered[]`, `findings[]`).

=== 5. Plan Instance: Configuration Snapshot, Composition Rules & Adoption

Every plan executes its own *plan instance* `plan.pmwf`, a DSL unit the server composes from the templates and the plan's facts (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]). The templates are the project's workflow units (`.marshall/config/*.pmwf`, among them the remediation policy units) as verified at load; a failing unit is never replaced by a default unit, it refuses the plan lifecycle. The configuration is never copied into the plan: each fact stays in the store that owns it (compiled defaults, team files, the operator's `local-config.json`, derived facts; waivers in the plan's append-only waiver record; lane, deliverables, footprint, and tasks in the plan stores). The instance carries their *effect* with provenance: the lane's route and the units it uses, every pruned step and link with its prune reason and source fact, every policy call with its bound budgets and allowed actions and the source of each value (the call argument of the named unit file, or the waiver id of a `raise`), every gate marked waived with its waiver id, and a header with the digests of every input: every effective value with its source, the compiled defaults, the derived facts the values rest on, the team files, the operator file, the templates, and the composition rule file. The header replaces the former `config_hash` snapshot and the instance's step list replaces `execution-manifest.json`; a binary upgrade that changes a default therefore changes an in-flight plan only through an adopted re-composition.

*Composition rules*: Which steps, links, and policy actions a plan's facts prune is declared data, not code: one composition rule file, compiled into the binary and versioned like the default units, whose rules map a plan fact or an effective configuration value to prunes (with a reason from the closed prune-reason enumeration) and policy bindings (link:../store-schemas/14-plan-instance-waivers-questions.adoc#composition-rules[Store Schemas Specification, Composition Rules]). For example, `lane = land` binds every policy call with `actions: [retry]` and prunes task allocation, `loop_back`, and the in-branch fix links with reason `land_lane`, a project without a push remote prunes the remote-bound finalize steps with reason `local_only`, and the operator's `merge.auto_merge: false` prunes the merge execution with reason `auto_merge_off`. The rule file is neither team nor operator configuration: it has no copy in `.marshall/config/` and no key overrides it, and the compiled invariants are checked on every composed version, so no rule and no fact can compose an instance that violates them. Team overrides of templates and composition rules are deferred (link:../../later-improvements.adoc#_l_5_team_overrides_of_templates_and_composition_rules[Later Improvements, L-5]).

*Versions*: The instance is immutable and versioned; a version is composed only on one of the closed composition events (`start`, `outline`, `plan`, `config_adopted`, `waiver`, `fallback`, `empty_harvest`, `deliverable_removed`), takes effect at the next transition, never mid-state, and keeps state ids stable, so the current position maps across versions and completed history is never rewritten. Storage, header schema, position rule, and display are specified in link:../store-schemas/14-plan-instance-waivers-questions.adoc#plan-instance[Store Schemas Specification, Plan Instance].

*Adoption*: Whenever an edit, a changed derived fact, a changed workflow unit or rule file, or a new binary changes an input digest of the header, the next phase handshake (`phase-workflows.adoc`, Outside-World Invariants) detects it and composes a candidate in-process: a candidate that differs from the version in force only in its header is adopted silently (composition event `config_adopted`, nothing rendered); a differing one raises the `config_drift` condition on the phase entry state (`adopt` / `keep`, audited; link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-config_drift[State Catalogue, Conditions]), whose rendering is the instance diff. A candidate that no longer contains the plan's current state or an entry of its `call_stack` offers only `keep`; a version composed on a server event (fallback, empty harvest) is composed in the transaction that enters its target state and therefore always contains it. At Phase 6 entry the server re-computes the plan's own inputs of the `plan` event (`realized_footprint_digest`, `change_type`, `providers_digest`): a difference composes the `plan` event again with the realized inputs and records the changed inputs in the audit record of the re-composition, and an input the server cannot re-derive is listed as `unchecked` in that record, never omitted; neither the digests nor the changed inputs are rendered, because the re-composition needs no model decision. The header's configuration digests read the configuration of the plan's current location (the worktree copy of `.marshall/config/` from Phase 5 on), so a deliverable that edits a configuration file or workflow unit is detected at the next handshake.

=== 6. Build-Time Verification

JUnit 5 build tests in `pm-mcp-core` enforce:

** Every configuration schema is closed at every level and valid JSON Schema (draft 2020-12); the compiled default table satisfies it.
** Every default workflow unit passes the static verification rules and the compiled invariants (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification]), and the invariant checker refuses a fixture set of weakened units (a mandatory step removed, the push barrier bypassed, the Q-Gate removed from a phase that requires it).
** The shipped composition rule file is valid against its closed schema, every rule names a registered fact predicate, target, and prune reason, and the plan instances composed from the default units for a fixture matrix of plan facts (every lane, a local-only project, an empty harvest, a fallback) pass the compiled invariants.
** A three-way default-unit offer never re-adds a hunk the fixture project removed, and a declined offer is not repeated.
