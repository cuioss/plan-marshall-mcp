The exchange between the server and a worker. Every worker follows it, whether the server started it or it is the interactive session that started the plan. The exceptions are the tool-less workers, the screener of untrusted text and the judge that grades role qualification: they have no connection to the server, so their task ends with their process, by a valid verdict or without one (xref:roles.adoc#untrusted-content[Roles, Untrusted content]). The protocol is a reusable sub-workflow of the workflow DSL: every transition is server logic, and the model only follows the links it is offered. The states, parameters, and rules are specified in link:../../specification/model-work.adoc[Model Work]; the values per host in link:../../specification/client-profiles.adoc[Client Profiles].

== Steps

image::../../resources/harness-as-worker-task-exchange.svg[One task from offer to submit between workflow engine, task queue, and worker, including the wait-again answer and the acknowledgement, align=center]

. *Wait*: the worker holds a wait call open for a bounded window, below the host's idle limit; where the host's progress frames reset that limit, the server sends them during the wait, and the window may then exceed it.
. *Offer*: the server answers the wait with a task. MCP gives the server no way to make a harness act, so a warm worker's offer is always the answer to a pending call; a fresh worker's one task is leased to it at spawn and arrives in its launch prompt. The task is leased to the worker's current generation and carries the skills it requires that this generation has not received yet.
. *Acknowledge*: the worker confirms the task. The acknowledgement tells the server that the worker is alive and has the task.
. *Execute*: the worker does the task by following the links of the task's representation. During long work its calls serve as heartbeats.
. *Submit*: the worker submits a structured result through the offered link. The server checks it against the link's schema, the lease, and the generation.
. *Wait or end*: the server answers the next wait with the next task, with "wait again", or with "end".

== States

image::../../resources/harness-as-worker-task-states.svg[Worker states: waiting, offered, acknowledged, executing, consulting, submitted, lost, and ended, with their transitions, align=center]

A worker is _waiting_ while it holds a wait call, _offered_ once a task is leased to it, _acknowledged_ and then _executing_ while it works along the task's links, and _consulting_ while it waits for another role's answer. A submit leads back to waiting or to the end. A worker the server gives up on is _lost_: its lease is released at once and its task returns to the queue for a successor.

[#supervision]
== Supervision

Neither the transport nor the model reports that a worker is lost or about to give up. The server therefore watches each worker itself and tells two cases apart.

A worker is *lost* when it stops doing its part: its process exits without the server's instruction, it does not acknowledge an offer in time, or it falls silent, with no open wait call and no other call for longer than its host allows. The server ends it, and its task goes to a successor.

A warm worker is *recycled* before it fails: after a run of wake-ups without a task, because a long-idle worker tends to give up and every wake-up costs, or when its context approaches the role's token budget, because a warm loop breaks as its context grows. A recycle is no loss: the server answers the worker's next wait with "end", never in the middle of a task. The same holds when the role's configuration changes: a worker started with the old configuration gets no new task and is recycled, and the successor starts with the new one.

A worker that exits before its first call has not been lost but failed to start, typically because its harness cannot start at all. Replacing it would start workers without end, so after a few such starts the server starts no more workers of that role on that harness, tells the operator, and lets the role's tasks take their fallback (<<task-end>>). The detection rules are specified in link:../../specification/model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling].

== Fencing and leases

image::../../resources/harness-as-worker-worker-replacement.svg[A stalled worker of generation 1 is replaced by generation 2, which receives the same task; the late submit of generation 1 is refused, align=center]

* Every worker has a generation, issued with its job token and carried by the relay.
* A task is leased to one generation; a call or submit of another generation for that task is refused.
* When the server replaces a worker, it releases the lease at once and offers the task to the successor exactly once.
* The successor starts with an empty context. Nothing is handed over, because every task carries what its state needs.

[#task-end]
== How a task ends

A task ends in one of four outcomes. It is _submitted_ when the worker delivered its result through the offered link. It is _asked_ when the worker needs an answer it cannot find: the question becomes a record the server serves, and the work continues in a new task with the answer in its facts. It is _infeasible_ when the worker shows with evidence that the task cannot be done as given, which the creating state answers by its infeasible route. It is _lost_ when no worker delivers.

A lost attempt is not yet a lost task: the server offers the task again, to a successor, within a small budget of re-offers. Only when that budget is spent, or when no qualified worker of the role can be started at all, does the task end lost, and the state that created it takes its declared conservative fallback. No outcome asks the operator mid-plan.

[#consultation]
== Consultation

A worker that needs another model's judgment asks through the server, never directly, and only where the workflow provides for it: a state declares the consultations it offers by role name (for example `consult role triage-review`), and the server looks up that role's configuration like any other.

. While executing, the worker follows one of the consultation links its state offers and submits the question.
. The server creates a task for the named role and runs it like any other task.
. The asker waits within its bounded wait, with progress frames where the host needs them.
. The answer arrives as the answer to the asker's next wait; the asker continues and refers to the consultation in its final submit.

image::../../resources/harness-as-worker-consultation.svg[A worker asks another role through the server and receives the answer through its pending wait, align=center]

The flow is deterministic and stays within the single-level leaf constraint: a worker never starts another model itself.

== The interactive session as a worker

The session that started a plan may take a task when it is attentive, beside a headless worker that takes the task when the session does not acknowledge in time. It takes only tasks that change nothing, of a `read_only` role whose configuration offers its tasks to a session first, only on a host whose session can take tasks at all, and only tasks of the scope it entered that run in its own working directory; a writer's task never goes to a session, because the session runs outside the confinement. The plan never waits on the session. Each start of a session gives it a new generation, which fences an earlier loop of the same session that may still be running.
