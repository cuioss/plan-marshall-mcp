The conclusion of roadmap Milestone 0, Part A (control direction and the pull mechanism, 2026-10-01 to 2026-10-03). The decision gate of xref:../../discussions/control-direction.adoc#gate[Control Direction] is the operator's; this document states what the measurements establish, what they rule out, and the design that follows from them.

== The answer in one paragraph

The server can be the driver. A headless harness process that the server starts holds a pull loop for hours, survives being killed without losing or duplicating its task, keeps injected text from travelling, and reports its usage per task; one small decision costs about 9 s and 0.02 USD as a fresh job. What breaks is the model's willingness to keep pulling: when nothing arrives for a long time, when its context grows large, or when it runs inside an interactive session. Neither the transport nor the model reports that it happened. The server therefore has to supervise its workers, and the interactive session cannot be a driver. With supervision the harness as worker works in principle; the parts of it that were not measured are planned in xref:evaluation.adoc[Evaluation].

== Ruled out or limited

[cols="1,4", options="header"]
|===
|Finding |Evidence

|The interactive session is not a driver
|V10: Claude Code paused itself for up to 30 minutes and queued the operator's input while looping; OpenCode stopped after 58 cycles and asked the operator

|A worker left idle gives up
|V2: OpenCode with `space-bunny-free` stopped after 33 and 102 empty cycles ("nothing to decide")

|A warm context has a ceiling
|V3: Haiku stopped pulling at 135k to 150k tokens in four runs of four; Sonnet held to 787k at 0.27 USD per decision

|The server learns nothing from the transport
|V9 and the setup: a dropped call is not noticed; every redelivery came from lease expiry

|Hosts differ in their limits
|V1: Claude Code 30 minutes of silence, OpenCode 60 s without progress, Antigravity 180 s that progress cannot extend

|Antigravity is the weakest worker host
|one global server entry (no separable workers), a 180 s limit, no cache-creation usage, 17 s per fresh decision
|===

== The design that follows

=== Task protocol

A worker, whether spawned by the server or the session that started the plan, complies with one protocol, modelled as a reusable sub-workflow so that every transition is deterministic server logic:

. *Wait*: the worker holds a wait call open, bounded below the host's limit by the client profile (240 s on Claude Code, progress frames on OpenCode, 150 s on Antigravity).
. *Offer*: the server answers the wait with a task, bound to the worker's generation.
. *Acknowledge*: the worker acknowledges, explicitly or by its first call that follows the task's link. No acknowledgement within the deadline means the worker is lost: the server ends it and offers the task to a successor. The deadline must tolerate provider stalls (OpenCode stalled for about 310 s).
. *Execute*: the worker does the task by following the links of the task's representation; its calls serve as heartbeats during long work.
. *Submit*: a structured result through the offered link, checked against the generation and the lease; a submit of a replaced generation is refused.
. *Wait or end*: the server answers the next wait with the next task, with "wait again", or with "end".

=== Supervision

The server ends a worker and, when there is work, starts a successor:

* when its process exits (the strongest signal; both measured failure modes ended that way headless);
* when it neither holds a wait nor calls within the bounded wait plus a grace;
* when it does not acknowledge an offered task in time;
* after an idle period of a few wake-ups (about 15 minutes), before it gives up on its own, and because idling costs about a tenth of the context per wake-up;
* when its context approaches the token budget (well below 100k tokens for Haiku), from the per-turn usage;
* optionally after a task that carried untrusted text (not required by V8).

A lease is released at once when the server replaces its holder; the successor starts with an empty context, because every task carries what its state needs.

*New or opportunistic model starts*, each a fresh job:

* *Outline* and *planning*.
* *Coding*, as the execution context of a task (a writer job; writer jobs belong to Part B).
* *Reviews*: security, simplify, and the pre-submission self-review, the latter split into two review agents: (a) does the code implement the requirement correctly and completely, (b) is the implementation itself correct and compliant with the rules. Their quality is part of xref:evaluation.adoc#e7[E7].

*Typed and configurable*: every model process has a type (class, tool set) and is configured by effort level or, better, per project or machine with its own harness and model, for example OpenCode for planning and the main thread, Claude Code for coding, Antigravity for reviews (xref:evaluation.adoc#e8[E8]). The measurements rank the hosts: Claude Code fits well as a job harness; OpenCode with `space-bunny-free` gave up in idle loops, other models are unmeasured; Antigravity has the weakest profile (180 s limit, no cache-creation usage, one global server entry, xref:evaluation.adoc#e6[E6]).

*A model asks a model through the workflow*: the consultation is modelled as a workflow step, so that it is always deterministic and stays within the single-level leaf constraint (xref:evaluation.adoc#e5[E5]).

*The task protocol is a sub-workflow*: wait, offer, acknowledge, execute along the links, submit, wait or end, as a reusable sub-workflow of the workflow DSL, so that the supervision is server logic and the model only follows links.

=== Requirements on the job runtime and the relay

* Every worker runs in a directory outside the project tree or with the harness's project instructions and persistent memory switched off, with its MCP tools loaded directly (`ENABLE_TOOL_SEARCH=false` on Claude Code).
* The relay carries identity and generation, adds the per-request headers of a sessionless host, never answers a notification, and reports a lost daemon at once.
* Client profiles: `bounded_wait_seconds` 240 / progress required / 150, and `progress_resets_timeout` true / true / false for Claude Code / OpenCode / Antigravity.
* A terminated job reports no usage; the runtime records its usage as unmeasured.

== For the decision gate

Read against the four decisions of the gate:

. *Direction*: the evidence supports the server driving the interior of plans and epics through supervised headless workers (option 2 of xref:../../discussions/control-direction.adoc#options[Control Direction]), with the interactive session as entry and viewer. It speaks against any design that depends on the interactive session to keep pulling.
. *Form of small decisions*: fresh jobs by default; supervised warm workers for roles with frequent small decisions; resuming a stored session is possible but brings back the context that recycling removes.
. *Deterministic server logic*: every model decision costs 9 to 20 s whatever its form, which is the price of leaving a decision with a single bound action to a model.
. *Watching a running plan*: the interactive session can watch, and a long call does not block it, but it cannot be relied on to react promptly; the web application and `pm-operator status` are the dependable views.

The supervision protocol, consultation through the server, the session-first offer, Antigravity as a concurrent job host, and the quality of open-ended decisions are not measured yet; xref:evaluation.adoc[Evaluation] plans their verification.
