An analysis of who drives the workflow. Since the decisions of xref:../../discussions/server-launched-agents.adoc[Server-Launched Sub-Agents] the server starts harness processes for delegated work, while the interactive harness session still drives every other step by calling `PM-MCP`. This document asks whether more of the workflow should move to the direction "`PM-MCP` calls the harness", what that buys and costs, and what has to be proven before it can be decided.

Figures refer to the working tree of 2026-10-01 (`feature/prepare` at `4140829`).

[#question]
== The question

Two directions of control exist side by side:

* *Session-driven* (harness -> `PM-MCP`): the model of the interactive session reads the current state with `pm_state` and moves the scope with `pm_do`. Nothing advances a `link` state unless a session calls.
* *Server-driven* (`PM-MCP` -> harness): the server launches a harness process as a job of kind `llm` for one role and entity, and evaluates what the job submitted.

image::../../resources/harness-as-worker-control-directions.svg[Session-driven and server-driven control: the interactive session, PM-MCP, and a headless harness, and what each does in both directions, align=center]

Should the server become the driver of the workflow, calling the harness for decisions and work, instead of depending on a live session to drive it?

Three consequences of the session-driven part are visible in the specifications:

. *A plan stops when the session does.* The session rows, the session-start hook with its scope pointer, the recovery after `/clear` and compaction, the three identity tiers, and the client handover exist to survive the loss of the driving session.
. *The interactive session is an unconfined writer.* It resolves merge conflicts, applies accepted simplify proposals, and makes in-branch fixes with the operator's own permissions, outside the confinement, the tool sets, and the one-writer rule that model jobs obey. Its token use is the separately measured population `main_context`, which depends on a host-specific transcript locator.
. *An epic cannot start its plans.* `emit:<plan_id>` returns a host command; only the operator starts the plan's session.

One property already holds and matters for everything below: every state must be answerable from `pm_state` alone (the recovery criterion of `PM-MIG-4`). A decision therefore never depends on what an earlier turn of the same session saw.

[#communication]
== How a server-launched job communicates

The server starts the process, and from then on every exchange is initiated by the harness: the job calls `pm_state`, `pm_do`, and its other tools over its job-bound connection (`pm-mcp serve --job`). The server never pushes into a running harness. A job that has to wait does so by *pulling*: it follows a `wait:` link, the call blocks up to the bounded wait of the client profile (progress notifications keep the call alive where the host honours them), and returns either the awaited event or the instruction to wait again.

This is the same mechanism the interactive session uses today for `wait:<job_id>`. Its stability is therefore a precondition of the present design as much as of any alternative, and it has not been measured.

[#options]
== Options for the direction

. *Stay as specified.* The session drives `link` states; the server launches jobs for delegated work.
. *The server drives the interior of plans and epics* (the operator's inclination). Every `link` state of a plan or epic that asks for model judgement or model writing becomes a model-job state with a role. A plan runs to one of its ends without a session; an epic launches its plans itself. The session keeps what is a conversation by nature: the bootstrap (the user's words become a plan), answering question records, and project setup. It may watch a running plan.
. *Full inversion.* No model role in the session; plans are started from `pm-operator` or the web app. The harness is a worker only.
. *A headless driver session per plan.* The hypermedia protocol stays as it is; the server launches one long-running harness process that plays the part of the interactive session.

|Option |Gains |Costs

|1
|No redesign.
|The three consequences of <<inventory>> remain.

|2
|Unattended plans (the self-enforcing process without a terminal that must stay open); one confinement and one accounting for all model work; real epic orchestration; a small client side (registration, entry commands, question relay), so that a host without a headless mode can still be a front end.
|Every small decision is a model job: start-up latency and prompt overhead per decision, unless warm (<<warm>>) or made deterministic. |3
|As 2, with the smallest client side.
|Gives up the conversational entry, the one place where the session is the better tool.

|4
|Least redesign for unattended plans.
|Keeps the accumulating context and the dependence on a model that must keep following `wait:`; a long plan outgrows one context.
|===

[#warm]
== Warm sessions for small decisions

Option 2 multiplies short model jobs. A fresh process per decision pays the start of the harness, the MCP connection, and the prompt (core skill, role skills, contract) every time. Because communication is harness -> `PM-MCP`, a session can instead stay alive and pull its next piece of work:

* *W1, fresh job per decision* (the decided form of model jobs): complete isolation between decisions; the cost is latency and tokens per start. The provider's prompt cache may make the repeated prompt cheap in tokens; it does not remove the start-up time.
* *W2, warm worker per plan*: one long-lived read-only harness session per plan (and, where needed, per model level) that loops: pull a task through a blocking tool call, decide, submit, pull again. Writer work stays in separate writer jobs, one at a time per plan. The worker is recycled at defined points (phase boundary, token budget, after a task that carried untrusted text, on any failure).
* *W3, warm pool across plans*: rejected in this analysis, because one session would carry content of several plans or projects.
* *W4, resumed session*: a fresh process that resumes a stored harness session; start-up latency remains, the context is kept.

What a warm worker changes in the model-job design, and therefore has to hold:

* The job token is bound to one entity today; a worker's binding moves from task to task, enforced by the server per request.
* Model, effort, and tool set are fixed when the process starts; a worker serves one job class and one model level.
* Skills can no longer all sit in the prompt file; the task carries what its state needs.
* Usage is reported when a headless run ends; attribution per task needs per-turn usage in the harness output.
* Context accumulates: later decisions see earlier tasks. A manipulated task could influence later ones, and an automatic compaction of the harness could drop the loop instruction.
* An idle worker that keeps calling the wait tool consumes tokens on every cycle.

== What must be verified first

None of the options can be chosen on paper. The following verifications need no product code beyond a stub MCP server with a blocking wait tool and scripted tasks; they run per harness that offers a headless mode, and V1, V2 and V10 also in the interactive session. Pass criteria are set before a run and recorded with the result. The record is xref:record.adoc[Run Record]; the runs are driven by the project-local skills `test-v1` to `test-v10`.

[#gate]
== Decision gate

When V1 to V10 are recorded, the operator decides, in this order:

. the direction (<<options>>);
. the form of small decisions: fresh jobs (W1), a warm worker per plan (W2), or a resumed session (W4), per harness where the results differ;
. which decisions of a running plan become deterministic server logic instead of model decisions (candidates: a remediation `decide` state with a single bound action, the commit message of a deliverable commit);
. how a running plan is watched (the session as a viewer, the web app, `pm-operator status`).

The roadmap from Milestone 2 on is written for the design as specified today; the gate's decisions are applied to the requirements, the specifications, and the milestones 2 to 14 before Milestone 2 starts.

[#impact]
== What option 2 would change (not applied)

* *Workflow*: the plan-scope and epic-scope `link` states with model judgement become model-job states with roles; the states that write (conflict resolution, applying simplify proposals, in-branch fixes) become writer jobs; `emit` starts the plan.
* *Tools and hypermedia*: the session's tool surface shrinks to entering, answering questions, and watching; representations are rendered for jobs.
* *Clients*: the bundles shrink; session recovery, identity tiers, and the `main_context` population lose most of their purpose.
* *Model jobs*: a decision role per state family; with W2 a worker binding, a task loop, recycle rules, and per-task usage.
* *Roadmap*: the phase milestones 7 to 11 and the bundle milestone 13.
