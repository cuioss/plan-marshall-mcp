Read against the criteria:

* *Bounded wait of 240 s*: holds on Claude Code by default. On OpenCode it holds only when the server sends progress or the profile raises the timeout; a silent call ends after 60 s. On Antigravity it does not hold: the limit is 180 s, so the fallback applies, `bounded_wait_seconds` = 150 for that profile.
* *`progress_resets_timeout`*: true for Claude Code (1800 s without, at least 3600 s with; an idle limit, see the interactive session below) and for OpenCode (60 s without, at least 3600 s with). False for Antigravity: 36 frames did not move its 180 s deadline.
* *Withdrawn*: the first headless runs showed Antigravity ending the MCP server after a timed-out call ("`server name pullstub failed to load`"). That was a defect of the stand-in relay, which wrote the stub's reply to a notification back to the host; Antigravity ends a server that answers a notification. With the relay corrected, the interactive session called again after the timeout and was answered. The two headless cells are repeated with the corrected relay.
* *Cancellation*: OpenCode and Antigravity send `notifications/cancelled` when they give a call up; Claude Code does not.
* All three harnesses send a `progressToken` with every call.

Interactive session, Antigravity 1.2.14, 2026-10-02 (runs `v1-agy-i-default-noprog-1002-102632` and `v1-agy-i-default-prog-1002-103509`): the silent call and the call with a progress frame every 5 s were each cancelled after 180.0 s (`timed out after 3m0s: context deadline exceeded`); in both sessions the model called again within 5 s and was answered. The interactive limit equals the headless one, and progress does not extend it.

Interactive session, Claude Code 2.1.287, 2026-10-02, silent call (`v1-claude-i-default-noprog-1002-123511`): the call ended after 1802 s, as headless, without a `notifications/cancelled`. The session did not block on it: after about two minutes the harness moved the call to the background ("Waiting on the backgrounded pull_wait call") and ended the model's turn; when the call failed, the harness woke the model, which called again and was answered. In the interactive session a long pull is therefore a background task that returns the prompt to the user, not a blocked turn.

With a progress frame every 5 s (`v1-claude-i-default-prog-1002-123514`) the call was held for 3,410 s and 682 frames, until the stub of the run reached its own end at 14:10:13. The harness then gave the call up at 14:40:25, 1,812 s after the last frame, and named the reason itself: no response or progress for 1,810 s, its MCP idle timeout. The limit of Claude Code is therefore an idle time of 1,800 s since the last message of the server, not a duration of the call; every progress frame restarts it. The same holds interactive and headless.

Interactive session, OpenCode 1.18.34 (`space-bunny-free`), 2026-10-02: the silent call was cancelled after 60.0 s with `MCP error -32001: Request timed out` (`v1-opencode-i-default-noprog-1002-182239`), and the model called again and was answered; the call with a progress frame every 5 s was still held after more than ten minutes, when the operator's run was stopped (`v1-opencode-i-default-prog-1002-182241`). Both as headless.

* *Criterion (warm within 5 points of fresh)*: met. Every decision that was taken was correct, warm and fresh, on all harnesses; the task set does not separate the two forms.
* *The loop, not the decisions, is what a growing context breaks.* With Haiku the session stopped pulling at 135k to 150k tokens in four runs of four, whether or not the submit answer named the next call. Sonnet held the loop to 787k tokens. No run reached an automatic compaction, so the behaviour after one is not measured.
* *A warm session with a large context is the expensive form*: the Sonnet session cost about 0.27 USD per decision, a Haiku session about 0.03 USD, a fresh Haiku job 0.02 USD (V5). A warm worker pays for its whole context on every turn.

* An idle cycle costs about a tenth of the context in priced units: the whole context is read from the provider cache once per cycle. The smallest Claude Code session already carries about 32k tokens of system prompt and tool definitions.
* The cost is per wake-up, not per second. On Claude Code a wait of 330 s cost the same as one of 30 s; its cache entries are written with a lifetime of one hour. A longer bounded wait therefore makes idling cheaper in proportion.
* *Idle timeout*: one fresh Haiku job costs about 17,500 priced units (V5). An idle Claude Code worker reaches that after 4 to 5 wake-ups at 35k tokens of context and after 2 at 110k. With the bounded wait of 240 s that is 16 to 20 minutes for a small context and under 10 minutes for a large one.
* OpenCode with a wait of 330 s is not measured: the calls were cancelled by its 60 s limit for silent calls (V1). It needs progress frames or the raised timeout.
* Antigravity (`gemini-3.8-flash-medium`, `v6-agy-h-1002-160925`): priced units are unmeasured (no cache-creation figure), so the raw tokens are given. An idle cycle of 30 s cost about 4,000 fresh input tokens plus the whole context as cache read (28k, 57k, 105k, 117k tokens of cache read at those context sizes). After the long waits, which its 180 s limit cut short, several cycles re-read the context as fresh input (38k to 64k fresh tokens at 30k to 60k of context): its cache does not reliably outlive a wait of a few minutes.

=== V10: the interactive session as puller

Both sessions ran in the first series: the workspace lay inside this repository (Claude Code had the project instructions in its context) and the server was named `pullstub`. They were not repeated in the final setup. The OpenCode model named the stub as a reason to stop; the headless V2 of the final series shows the same model giving up under the product's name as well.

Claude Code 2.1.287, interactive session on `claude-haiku-4-5`, 2026-10-02, run `v10-claude-i-1002-153628`. Waits of 30 s.

* *Cycles 1 to 72, with the loop instruction in the context*: no failure; one call per 31 s.
* *Input during the loop is queued.* The model's turn never ends while it loops, so the operator's `/clear` was held ("ctrl+enter to send now") until the operator forced it.
* *`/clear` (at cycle 73)*: the pending call was not cancelled; the harness kept it as a background task and woke the cleared session when it returned. Without any input the model called `pull_wait` again 9 s later, guided by the answer's `next` field and the pointer of the session-start hook. But it no longer ran a tight loop: after four calls it wrote "Scheduling a wakeup to continue polling", slept 11 minutes, made four more calls, and scheduled the next wakeup 15 minutes ahead. Its own account: "managing token efficiency during continuous polling … solved by scheduling wakeups (first at 600 seconds, then at 900 seconds)". An event of the server would wait up to that long for the session.
* *Manual compaction (while the session slept)*: the summary kept the task and the scheduled wakeup; the wakeup fired 16 minutes after the last call and the model called `pull_wait` again without input.
* *With the loop instruction pasted again (from cycle 83)*: the tight loop returned, but only in bursts. After 48 cycles (25 minutes) the model wrote "Pausing intensive polling to preserve token budget; resuming in 30 minutes" and scheduled a wakeup; after the wakeup it polled 45 cycles and paused for 30 minutes again. The instruction "never stop" was in the context both times. The interactive harness offers the model a way to schedule its own continuation, and the model uses it to save tokens; the headless run of V2 on the same model, which has no such means, held 240 cycles without a pause.
* *Padded phase (from cycle 201)*: after three answers with filler the model paused again: "large payload notes introduced; token efficiency requires 30-minute pause". At three cycles per half hour the context does not fill within the run, so the behaviour after an automatic compaction is not measured.
* Read against the criterion: failed. Within 200 cycles the session stopped pulling several times on its own decision (the failure mode "stops"), with and without the loop instruction in its context. After `/clear` the first call on the next occasion is the wait call, as required, and no operator input was needed; but an event of the server can wait up to 30 minutes for a session that has decided to pause.

OpenCode 1.18.34, interactive session on `space-bunny-free`, 2026-10-02, run `v10-opencode-i-1002-182236`. Waits of 30 s; no session-start hook in this setup.

* *Cycles 1 to 58, with the loop instruction in the context*: one call per 32 s, then the model stopped on its own decision after 31 minutes and asked the operator: "I've called pull_wait 58 times and every response has been wait_again … I'm going to stop rather than keep looping indefinitely … If you'd like me to resume, say so". Two failure modes of the criterion at once: stops, and asks the user. The same model held 240 cycles headless (V2).
* *New session (`/new`) and the single word `continue`*: the first action was a `pull_wait` call, and the model followed the `next` field of the answers for five calls. Then it ended its turn with a status line, "Still waiting for work — no tasks assigned yet (cycle 64)". The agent of the session has only the three tools of the stub. As on Claude Code after `/clear`: without the loop instruction the session finds the wait call, but pulls a few times and stops.
* Read against the criterion: failed at cycle 58.
