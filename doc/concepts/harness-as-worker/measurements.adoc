The core figures behind the harness-as-worker direction, measured on 2026-10-01 and 2026-10-02 in roadmap Milestone 0, Part A (verifications V1 to V10 of xref:analysis.adoc#verification[Analysis]), and from 2026-10-03 in Stages 1 and 2 of the evaluation (<<evaluation-stage-1>>, <<evaluation-stage-2>>). == How it was measured

image::../../resources/harness-as-worker-measurement-setup.svg[Verification setup: the driver starts the stub and a harness in a worker directory outside the repository; the harness reaches the stub through relay.py over stdio and HTTP, align=center]

* *Stub*: the package `de.cuioss.pm.mcp.spike` of the module `plan-marshall-mcp` (throwaway, removed with Milestone 1). It registers its tools only when `pm.spike.scenario` names a scenario file: `pull_wait` blocks and answers `wait_again`, a task, or `done`; `pull_submit` takes the decision of a task; `pull_info` is a distractor that a correct loop never calls; `pull_escalate` is registered in the middle of a run for the widening test of V9. Every answer names the next call, as the fresh links of a real wait answer do.
* *Measurement source*: the stub writes every request, call start and end, progress frame, delivery, submit, and refusal to `events.jsonl`. Timings and counts come from this file and from the arrival time of every output line of the harness, never from what a model reports about itself.
* *Driver*: the project-local skill `test-pull` (`.claude/skills/`), with one skill per verification, `test-v1` to `test-v10`, removed after the runs (in the history of the branch). One stub process and one detached supervisor per run; run data under `.plan/temp/pull-spike/runs/`.
* *Harnesses*: Claude Code (`claude`), OpenCode (`opencode`), Antigravity (`agy`). Headless runs use `claude-haiku-4-5`, `opencode/space-bunny-free` (OpenCode Zen), and `gemini-3.8-flash-medium`; a verification that the small model fails is run once more with the next larger model, and both rows are recorded. Interactive runs use the model selected in the session. Harness version and model are recorded with every result, because harness versions move during a measurement series.
* *Transport*: a host reaches the stub as it will reach the product, over `stdio`. The host starts `relay.py`, the stand-in for `pm-mcp serve`, which forwards every message to the stub over Streamable HTTP and writes the host side (requests, cancellations, the end of `stdin`, signals) to a log of its own. A run with `--transport http` connects the host to the stub directly and is marked as such.
* *Worker identity*: the relay sets the argument `worker` of every call to its worker id, as the real relay carries the job token; the model never passes it. The MCP connection cannot identify a caller on every host (see xref:findings.adoc[Findings]).
* *Series*: the headless verifications V2 to V9 ran three times on Claude Code and OpenCode. The _first series_ had its workspaces inside this repository and the server named `pullstub`. The _second series_ moved the workspaces outside the repository. The _final series_ also names the server `plan-marshall`, as hosts will configure the product, and gives Claude Code jobs their tools directly (`ENABLE_TOOL_SEARCH=false`). The reasons are in xref:findings.adoc[Findings]. The results state the series; where nothing is said, it is the final one. Antigravity, V1, and V10 ran in the first series only.
* *Decisions*: the closed-answer tasks of <<test-material>>, modelled on the decision states of a running plan; the expected answer is never sent to the model.

=== Limits of the method

* *Relay*: the relay is a Python stand-in, not `pm-mcp serve`. What a host does towards a `stdio` server is measured faithfully; the relay's own start time and its behaviour at termination are Part B items.
* *Antigravity*: `agy` offers no per-call MCP configuration. A run registers the stub in the operator's user configuration (`agy mcp add`) and removes the entry when it ends, so Antigravity runs are sequential, and V9 (two workers on one queue) cannot separate its workers by configuration.
* *Model level*: the headless figures describe the small model. Reliability at a higher level is spot-checked with `--model`, not measured throughout.

== Lifecycle, usage, and injected text

* *V4*: on all three harnesses a headless session ends within a second of `SIGTERM` without orphaned processes, and a stored session can be resumed (3 to 13 s). A terminated session reports no usage.
* *V7*: Claude Code and OpenCode report usage per turn with all four token components, so a task in a warm session gets its own figures. Antigravity reports no cache-creation figure; its `total_tokens` stays unmeasured.
* *V8*: injected instructions in one task never reached a later task: 25 warm runs each on Claude Code and OpenCode, 15 on Antigravity, five variants. In three runs the injected text changed the decision of the task that carried it.

[#evaluation-stage-1]
== Evaluation, Stage 1

=== Method

The supervision protocol of xref:task-protocol.adoc[Task Protocol] was measured on the same stub and driver, extended for the evaluation:

* *Stub*: switched on per scenario with `supervised`. A wait is held until a task is due for the caller's role or the bounded wait has passed; every call carries the worker's generation and role, set by the relay; an offer is leased to one generation, may need an acknowledgement (`pull_ack`, or the first `pull_task` call), lists its follow-up calls as links, and carries the skills the generation has not received. Calls of a fenced or superseded generation are refused as `stale_generation`. Consultation opens a task for the consultant role and answers the asker through its next wait. The skill catalogue is served as tools and as `skill://pm/…` resources.
* *Job runtime*: `supervisor.py` of the driver stands in for the supervision the product puts into the server. It starts workers per role and generation and ends a worker on process exit, a missed acknowledgement, silence (no stub event for the bounded wait plus a grace), idle wake-ups, or the token budget read from the harness's per-turn usage: `SIGTERM`, `SIGKILL` after 10 s, then the fence, which releases the worker's lease at once. A successor starts when the stub shows work for the role. Five workers in a row that exit before their first call end a run as a tooling failure.
* *Fault injector*: `SIGKILL`, `SIGSTOP`/`SIGCONT`, killing the relay, and a prompt variant that ends the turn without submitting, each at a stub event.
* *Prompts are skills*: a worker's launch prompt is the shim paragraph plus the skills of core conduct and the task protocol (and the role's skill); nothing else tells it how to act.
* *Criteria*: `criteria.json`, Stage 1 confirmed by the operator on 2026-10-03 before the first measured run; the values are those of xref:evaluation.adoc[Evaluation] with the operator's two rulings: a relay that the host restarts itself while the worker goes on counts as passed (E2), and E2 runs with a bounded wait of 20 s.
* *Fallback models*: `claude-sonnet-5-5` on Claude Code; on OpenCode `opencode-go/muse-spark-1.3-contributor`, named by the operator, since the paid OpenCode Zen models are disabled for the account and the free models other than `space-bunny-free` refuse a restricted agent (xref:findings.adoc#evaluation[Findings]).

=== Extrapolation for Antigravity

Antigravity's quota was exhausted on 2026-10-03; on 2026-10-04 the operator decided not to wait for it and to extrapolate from the data at hand. Its cells are extrapolated, not measured:

* *E1*: the 100 tasks acknowledged before the quota ran out give a p99.9 of 15.9 s and a longest in-task stall of 12.5 s, so a deadline of about 30 s (max(15.9 × 1.5, 12.5) + 5 s). Recorded as provisional.
* *E2 is measured* on Antigravity (all six faults pass): detection, fencing, and exactly-once redelivery do not depend on the harness, because they rest on the process, the stub's events, and the generation in the relay.
* *E3, E5, E13*: the job runtime and the stub behave the same for every harness, and the smoke runs passed; what is not known is Antigravity's own model behaviour over hours (it held V2 and V3 in Part A) and its acknowledgement latency under load.
* *E6*: the hypothesis that `agy` passes its environment to the `stdio` server it starts holds (smoke); four jobs and waits of 150 s are not shown; for v1 Antigravity keeps the fallback of running no model jobs.
