Every model process is a worker of a role. A role fixes the worker's type (class and tool set), whether it is kept warm or started fresh, and its configuration (effort level, harness, model). All workers follow the xref:task-protocol.adoc[Task Protocol].

[#target-picture]
== Warm workers per project

Kept while there is work, supervised, and recycled when idle or when the token budget is reached.

== Fresh workers

Started for one task and ended after its submit.

* *Outline* and *planning*.
* *Coding*, as the execution context of a task. A writer worker: one at a time per plan, in confinement (Milestone 0, Part B).
* *Reviews*:
** security review;
** simplify review;
** pre-submission self-review, split into two review workers: (a) does the code implement the requirement correctly and completely, (b) is the implementation itself correct and compliant with the rules.

The quality of these roles on real cases is part of xref:evaluation.adoc#e7[E7]. A fresh worker costs about 9 s and 0.02 USD to start on Claude Code with Haiku and a warm provider cache (V5), and it never waits idle, which is the situation in which workers gave up in Part A.

[#untrusted-content]
== Untrusted content

Untrusted text (PR comments, Sonar messages, web content, issue bodies) is cleaned up on the server first, by the deterministic level-1 validation, and then checked by a model for harmful instructions before it reaches any worker.

The form of that model is open:

[cols="1,3,3", options="header"]
|===
| |Fresh zero-tool screener (specification) |Warm contained screener (operator's picture)

|Form
|a fresh job per batch, server-fixed prompt, no tools, isolated directory, one turn, fail-closed
|a supervised warm worker whose only tools are wait and submit

|For
|nothing to misuse, nothing carried from one batch to the next
|no start cost per batch; V8 found no carry-over between tasks in 65 warm runs

|Against
|a start per batch (about 9 s)
|a pulling worker keeps tools; in Part A injected text did act on the task that carried it (three runs)
|===

xref:evaluation.adoc#e9[E9] compares both forms on the same injection variants and clean samples; the form is chosen by the result and the cost per verdict.

== Typed and configurable

* *Type*: every role has a class (reader, writer, zero-tool) and a declared tool set; a worker gets nothing beyond it. In Part A an allowlist of explicit tool names kept a tool added in mid-run uncallable (V9); a wildcard did not.
* *Configuration*: by effort level, or better per project or machine with its own harness and model, for example:
** OpenCode for planning and the main thread;
** Claude Code for coding;
** Antigravity for reviews.
* *Host suitability, as measured*: Claude Code fits well as a worker host (holds the loop, exact recovery, usage per turn, 9 s per fresh decision). OpenCode with `space-bunny-free` gave up in idle loops; other models are unmeasured. Antigravity has the weakest profile: a 180 s limit that progress cannot extend, no cache-creation usage, 17 s per fresh decision, and one global server entry, so several concurrent workers depend on xref:evaluation.adoc#e6[E6]. Routing roles across harnesses is xref:evaluation.adoc#e8[E8].

== A worker asks another role

A worker that needs another model's judgment, for example project triage asking a review role, asks through the server (xref:task-protocol.adoc#consultation[Task Protocol, Consultation]). The consultation is a workflow step, so it is always deterministic, and it stays within the single-level leaf constraint (xref:evaluation.adoc#e5[E5]).
