= plan-marshall-mcp — Concept
:toc: left
:toclevels: 2
:nofooter:

== Purpose

This document set describes *plan-marshall-mcp* (PM-MCP): a local MCP server that takes over the process logic plan-marshall implements today as a corpus of filesystem skills plus locally executed Python scripts.

The central idea is a *hypermedia-driven workflow*. The client asks the server for the state of a plan or orchestrator epic. The answer is a representation of that state together with pre-fabricated next tool calls (links), in the style of HATEOAS. The model follows links and contributes judgment only; the server owns the state machine.

The concept documents record decisions. Analyses, research and variants that were considered live in xref:discussions/README.adoc[Discussions].

== Key decisions

[cols="1,3"]
|===
|Area |Decision

|Server
|One local MCP server combining skills, tools, resources, a build server, a warm LSP pool and an MCP proxy (xref:02-architecture.adoc[Architecture]).

|Workflow
|Hypermedia: state representations with links carrying bound and free parameters, a `state_token` per state, forbidden actions never offered (xref:03-hypermedia-workflow.adoc[Hypermedia Workflow]).

|Skills
|Static vocabulary skills generated per project; per-state content as tool results; tool-based delivery with the MCP Skills extension as an addition (xref:04-skill-model.adoc[Skill Model]).

|Clients
|Client identity declared per session at the entry points by a minimal entry script and carried as a bound link parameter; skills, representations and links translated on the fly through data-driven client profiles, replacing build-time generation per runtime (xref:15-client-profiles.adoc[Client Profiles]).

|Tools
|Small verb set around `pm.state` and `pm.do`; failures are states, not errors (xref:05-tool-surface.adoc[Tool Surface]).

|Builds
|Always through the project's wrapper; backend chosen per project — container backend by default, host build server as alternative (xref:07-build-execution.adoc[Build Execution], xref:08-container-backend.adoc[Container Backend]).

|State
|All state persisted in the filesystem, processes hold caches only; no session context — scope travels in every call (xref:02-architecture.adoc#_state_persistence[State persistence]).

|Security
|Confinement to the working directory, other projects only after user approval; capability by omission; operator-only enrolment; verify-not-resolve for every build (xref:09-security.adoc[Security and Trust Model]).

|Technology
|Java 21+, Quarkus, Quarkus MCP Server; native executables on a distroless base as target image; cui-http and TokenSheriff; git and CI access without command-line tools (xref:10-technology.adoc[Technology]).

|Testing
|Scripts categorised as ported, redesigned or retired; differential tests against the Python implementation before a ported script is switched; end-to-end scenarios for the redesigned workflow (xref:14-test-strategy.adoc[Test Strategy]).

|Delivery
|PM-MCP container image, build runtime images, host build server binary; one MCP entry per host (xref:11-distribution.adoc[Distribution]).
|===

Several hosts run side by side on one machine, all served by the same core daemon. Each session declares its client identity when it enters through an entry point; from then on every link it receives carries that identity, and everything rendered for it is translated through its client profile.

=== Terms

[cols="1,3"]
|===
|Term |Meaning

|Machine
|The developer's computer. Runs one PM-MCP core daemon and any number of hosts.

|Host
|An agent runtime that connects to MCP servers and hosts the model — Claude Code, OpenCode, Antigravity. Several hosts can run on the same machine at the same time.

|Session
|One conversation in a host. Sessions of different hosts, and several sessions of the same host, use PM-MCP concurrently.

|Sub-agent
|A session started by another session through a `dispatch` link; it inherits the dispatching session's client identity.

|PM
|The model-side participant: the model working in a session.

|Operator
|The human responsible for the machine and its projects. Enrols projects, answers escalations and is the only party that takes operator-only actions.

|PM-MCP
|The plan-marshall MCP server described here, consisting of front ends and a core daemon.

|Front end
|The thin stdio MCP server a host starts for a session; forwards every request to the core daemon.

|Core daemon
|The long-lived PM-MCP process per machine owning workflow engine, state, build server, LSP pool, MCP proxy and audit.

|Entry point
|A user-invoked command through which a session enters plan-marshall: configuration wizard, plan lifecycle, epic orchestration. The only artefact installed per host.

|Entry script
|The minimal script an entry point runs to detect the session's client identity from the host's environment.

|Client identity
|The host a session runs in (`claude`, `opencode`, `antigravity`, …), declared at the entry point and carried as a bound parameter of every link.

|Client profile
|The data describing how PM-MCP renders content for one host: tool names, load mechanism, command naming, models, dispatch, component scope.

|Plan / epic
|The units of work PM-MCP manages, addressed by `plan_id` and `epic_id`.

|Representation
|The server's answer describing the current state of a plan or epic, including its links.

|Link
|A pre-fabricated tool call offered in a representation, identified by a relation (`rel`).

|Bound / free parameter
|Parameters of a link filled in by the server (passed unchanged) versus supplied by the model (where judgment is required).

|State token
|The version of a plan's or epic's state, bound into every link; a stale token makes a call fail with the current representation.

|Vocabulary skill
|A static skill explaining how to interpret representations and link relations, and how to exercise judgment in a given state.

|Wrapper
|The build entry point committed at the root of a project (`mvnw`, `gradlew`, `pw`, …); the only way PM-MCP starts a build.

|Build backend
|The component that executes build jobs for a project: the container backend or the host build server.

|Container backend
|Runs each build in a short-lived build container through Docker or Podman.

|Host build server
|The successor of `marshalld`; runs builds natively on the machine with its toolchains.

|Enrolment
|The operator's registration of a project, its build backend and its allowed wrappers and arguments.
|===
