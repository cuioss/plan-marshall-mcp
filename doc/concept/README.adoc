= plan-marshall-mcp — Concept
:toc: left
:toclevels: 2
:nofooter:

== Purpose

This document set describes *plan-marshall-mcp* (PM-MCP): a local MCP server that takes over the process logic plan-marshall implements today as a corpus of filesystem skills plus locally executed Python scripts.

The central idea is a *hypermedia-driven workflow*. The client asks the server for the state of a plan or orchestrator epic. The answer is a representation of that state together with the valid next transitions as links — a link id plus the parameters that need judgment — in the style of HATEOAS. The model follows links and contributes judgment only; the server owns the state machine.

The concept documents record decisions. Analyses, research and variants that were considered live in xref:discussions/README.adoc[Discussions].

[IMPORTANT]
====
The concept describes the *target design*; none of it is implemented yet. Statements in the present tense — "PM-MCP validates", "access is refused", "the model never passes paths" — are requirements the implementation must meet, not descriptions of existing behaviour. Guarantees become effective only with the implementation that enforces them, and each is covered by the test strategy (xref:14-test-strategy.adoc[Test Strategy]).
====

== Key decisions

[cols="1,3"]
|===
|Area |Decision

|Server
|One local MCP server combining skills, tools, resources, a build server, a warm LSP pool and an MCP proxy (xref:02-architecture.adoc[Architecture]).

|Workflow
|Hypermedia: state representations with links — a link id plus free parameters, followed through `pm_do` — every call validated against persisted state, forbidden actions never offered (xref:03-hypermedia-workflow.adoc[Hypermedia Workflow]).

|Skills
|Static vocabulary skills generated per project; per-state content as tool results; tool-based delivery with the MCP Skills extension as an addition (xref:04-skill-model.adoc[Skill Model]).

|Clients
|Client identity declared at the entry points by `pm-mcp enter` and persisted with the plan or epic; skills, representations and links translated on the fly through data-driven client profiles, replacing build-time generation per runtime (xref:15-client-profiles.adoc[Client Profiles]).

|Tools
|Small verb set around `pm_state` and `pm_do`; failures are states, not errors (xref:05-tool-surface.adoc[Tool Surface]).

|Builds
|Always through the project's wrapper, natively on the host as subprocesses of the daemon, like `marshalld`; every git operation as a git job with the host's `git` (xref:07-build-execution.adoc[Build Execution]).

|State
|All workflow and daemon state persisted in the filesystem, credentials in the credential store, processes hold caches only; no session context — plan or epic and entity travel in every call, client identity and workspace root in the entry record (xref:02-architecture.adoc#_state_persistence[State persistence]).

|Security
|Confinement to the working directory, other projects only after user approval; capability by omission; operator actions only through elicitation or the operator CLI, never through MCP tools; verify-not-resolve for every job; loopback endpoint with short-lived tokens (xref:09-security.adoc[Security and Trust Model]).

|Credentials
|System lane: `git`, `gh`, `glab` keep their own credentials. Token lane: OS credential store first, plan-marshall's file store as fallback; secrets entered only by the operator (xref:08-credentials.adoc[Credential Handling]).

|Technology
|Java 25+, Quarkus, Quarkus MCP Server; one native executable `pm-mcp` on the host; cui-http and TokenSheriff; git and CI through the host's `git`, `gh`, `glab` (xref:10-technology.adoc[Technology]).

|Testing
|Scripts categorised as ported, redesigned or retired; differential tests against the Python implementation before a ported script is switched; end-to-end scenarios for the redesigned workflow (xref:14-test-strategy.adoc[Test Strategy]).

|Implementation
|Own workflow engine and TOON encoder, Jackson for JSON; JSON for storage, TOON for output; project-local `pm-mcp-` development skills; bounded and progress waits as links; foundation first, then by category (xref:16-implementation.adoc[Implementation Approach]).

|Delivery
|Native binary `pm-mcp` as a package; one MCP entry per host — direct HTTP with `pm-mcp token` as header helper, or `pm-mcp serve --stdio` (xref:11-distribution.adoc[Distribution]).
|===

 └─────────────────────────────────────────────────────────────────────────────────┘
 Operator: enrols projects, answers escalations, takes operator-only actions
----

Several hosts run side by side on one machine, all served by the same daemon. Each session declares its client identity when it enters a plan or epic through an entry point; the identity is persisted with that plan or epic, and everything rendered in its scope is translated through the client profile.

=== Terms

[cols="1,3"]
|===
|Term |Meaning

|Machine
|The developer's computer. Runs one PM-MCP daemon and any number of hosts.

|Host
|An agent runtime that connects to MCP servers and hosts the model — Claude Code, OpenCode, Antigravity. Several hosts can run on the same machine at the same time.

|Session
|One conversation in a host. Sessions of different hosts, and several sessions of the same host, use PM-MCP concurrently.

|Sub-agent
|A session started by another session through a `dispatch` link; it works in the dispatching plan's or epic's scope and uses its recorded client identity.

|PM
|The model-side participant: the model working in a session.

|Operator
|The human responsible for the machine and its projects. Enrols projects, answers escalations and is the only party that takes operator-only actions, through elicitation or the operator CLI.

|PM-MCP
|The plan-marshall MCP server described here: the native binary `pm-mcp` and the daemon it runs.

|`pm-mcp`
|The native executable on every machine. Its modes: the daemon, the header helper `pm-mcp token`, the stdio relay `pm-mcp serve --stdio`, the entry call `pm-mcp enter` and the operator CLI.

|Daemon
|The long-lived PM-MCP process per machine, native on the host and the successor of `marshalld`: the MCP server, owning workflow engine, state, build server, LSP pool, MCP proxy and audit; started on demand or as an OS user service.

|Entry point
|A user-invoked command through which a session enters plan-marshall: configuration wizard, plan lifecycle, epic orchestration. Together with the execution-context agent variants, the only artefact installed per host.

|Entry call
|`pm-mcp enter`, the single action of an entry point: detects the session's client identity and working directory from the host's environment and has the daemon write the entry record.

|Entry record
|The file in a plan's or epic's `mcp/` directory holding the client identity, client session and workspace root of the last entry; every call in that scope reads it.

|Client identity
|The host a session runs in (`claude`, `opencode`, `antigravity`, …), declared at the entry point and persisted with the plan or epic in its entry record.

|Client profile
|The data describing how PM-MCP serves one host: tool names, load mechanism, command naming, models, dispatch, component scope, connection.

|Plan / epic
|The units of work PM-MCP manages, addressed by `plan_id` and `epic_id`.

|Representation
|The server's answer describing the current state of a plan or epic, including its links.

|Link
|A transition offered in a representation: a relation (`rel`), a link id and the free parameters; followed with `pm_do`.

|Link id
|The transition and, where it acts on part of a plan or epic, the addressed entity (`push`, `triage:F-12`); derived from the persisted state.

|Free parameter
|A parameter of a link supplied by the model, where judgment is required.

|Job
|A build, git, CI or script operation the daemon runs as a subprocess on the host, verified against the enrolment; long-running jobs are followed through `wait` links.

|Vocabulary skill
|A static skill explaining how to interpret representations and link relations, and how to exercise judgment in a given state.

|Wrapper
|The build entry point committed at the root of a project (`mvnw`, `gradlew`, `pw`, …); the only way PM-MCP starts a build.

|Credential store
|Where token-lane credentials and PM-MCP's own secrets live: the OS credential store, or the file store `~/.plan-marshall/credentials/` as fallback.

|Enrolment
|The operator's registration of a project and its allowed wrappers and arguments.
|===
