== Scope

The phase state machine as a whole and phases 1–4 (init, refine, outline, plan):

* `plan-marshall/SKILL.md` (312 lines) routes actions; `plan-marshall/workflow/planning.md` (1,088) and `planning-outline.md` (598) are the actual orchestrator for phases 1–4.
* The phase skills: `phase-1-init` (1,260 lines), `phase-2-refine` (374 plus 961 of detail), `phase-3-outline` (828 plus 1,263 plus the light lane with 312), `phase-4-plan` (1,251).
* `manage-status` (about 8,000 lines of script): transition, planning lane, change-type heuristic, confidence aggregation, sibling collision, classification validation, step recording.
* The phase handshake: `plan-marshall/scripts/phase_handshake.py`, `_invariants.py` (1,980 lines), `_handshake_store.py`.
* `ref-workflow-architecture/standards/`: phases, phase lifecycle, change types, scope deviation, agents.

== How it works today

The phase model is a forward state machine, `1-init → … → 6-finalize`, with one back-edge from finalize to execute. No single piece of code carries it; it is spread over prose the orchestrator follows, deterministic scripts, and shared contract documents.

Phase 1 runs in the main session and asks the user up to six questions directly. Phases 2–4 run as `execution-context` dispatches; a sub-agent that needs input returns a prompt envelope (`refine_prompt`, `outline_prompt`, `escalate_ask`) and the main session asks. Correctness is enforced mostly by prose ("never skip …") and mechanically only at a few points: the handshake, the artifact gate on `transition`, and `git status --porcelain` after each planning phase.

The documents already disagree with each other — `workflow-overview.md` still dispatches phase 1 and loops the outline review "until approval", `phases.md` describes an unbounded refine loop, `phase-2-refine` states both "max iterations 5" and "re-dispatch at most once". A single state machine removes this class of drift.

== Gaps in the concept

. *Routine user dialogue.* The concept knows only `escalate` to an operator decision. Phases 1–4 have about ten routine interactions — existing plan, obsolescence, recipe choice, ambiguous domain, sibling collision, posture, clarifications, outline review, Q-Gate exhaustion — several of them with free text. Missing: an awaiting-user state, an elicitation form schema, and the fallback without elicitation.
. *Plan sources.* `pm_start(request)` does not cover description, issue, lesson and recipe sources, the base branch, moving the lesson file with its premise check, and fetching the issue body through CI.
. *Recipes* are not modelled (see xref:04-extensions.adoc[Extension Mechanism]).
. *Workflow settings* that decide link emission are not listed.
. *Stores needed by phases 1–4* are missing from the transition order in 16: outline parsing and validation, architecture queries, the execution manifest, request sections.
. *Token metrics* once phase boundaries are gone.
. *Outline vocabulary per change type and domain* is not in the skill catalogue.
. *Edits under `.plan/` by the model* outside the server: no store digests yet.

== Conflicts

* *Sub-agent escalation.* Concept 03 sends a sub-agent's decision through `escalate` and blocks it in a wait. plan-marshall deliberately lets the sub-agent finish with its best judgment, return questions in one batch and allow one re-dispatch (`ref-workflow-architecture/standards/agents.md:121-158`). That is cheaper and bounded; see README, sub-agent questions.
* *Deleting a plan.* 03 makes deletion operator-only, but init answers delete plans (obsolete → close, collision → rename or abort, exists → replace). An elicitation answer counts as operator consent; the lesson carry-back veto of `delete-plan` stays.
* *Approval by the model.* plan-marshall lets the model ask for approval and relay the answer. Under 09 the model must never approve an outline or accept a deviation; hosts without elicitation make this a usability question (see README, user interaction).

== Invariants to preserve

* Planning phases write only under the plan directory; the main checkout is clean at every planning transition; `marshal.json` is never discarded without an operator decision.
* A bare transition out of 2, 3 or 4 is refused unless the artifact exists or a reasoned exemption is recorded.
* Task creation is not idempotent: `batch-add` is atomic, and the plan phase never runs twice against existing tasks.
* The lane ratchet is one-way. An unknown scope estimate biases to deep; an unset change type does not (`phase-1-init:832-860`).
* Refine only widens domains; outline narrows them once.
* Change type has a single writer; disagreement between plan and deliverable scope is refused; classification validation flags but never blocks.
* Phantom plan ids are refused; recipe plan ids carry a timestamp suffix.
* Clarifications are asked in one batch; re-dispatch at most once; review feedback is persisted as Q-Gate findings.
* The Q-Gate loop runs at most three iterations, with the content-hash rerun gate, the exit on the pending count and the surgical bypass predicate.
* Handshake drift is a signal, never rationalised or remediated automatically; the loop-back override fires once; worktree refusals are never bypassed; the `.plan/` exemption is keyed on git trackedness.
* Missing counts are omitted, never zeroed.
* A scope deviation is decided before it is logged; accept needs a persisted rationale that appears in the PR body; split creates a lesson; deviations are batched into one question.
* Posture preview and manifest composition use the same resolver.
* A PR title exists from refine on.

== Conclusions

. Phases 1 and 4 are mostly deterministic: init becomes `pm_start` with server classifiers and user-choice states, and phase 4 can be computed by the engine, which saves a dispatch. Judgment concentrates in three submit states — refine analysis, outline authoring, change-type fallback — each with a closed parameter set.
. Handshakes collapse into transition guards. Invariants that detect the model's process violations become obsolete; those observing git, configuration and findings stay as guards.
. The user interaction model is the main open decision for the planning phases.
. Resume needs sub-phase states: pending approval, refine questions and answers, re-dispatch counters and Q-Gate iterations are persisted, and the plan does not advance past outline before approval.
. Change type and scope deviation carry over almost unchanged as data; enforcement becomes stronger because no link records a softening.
