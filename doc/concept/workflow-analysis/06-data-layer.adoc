== Scope

The fourteen `manage-*` skills of the data layer and the worktree commands of `workflow-integration-git`, together with their shared helpers: `tools-file-ops/scripts/file_ops.py` (1,867 lines: path resolution, atomic writes, TOON output, error handling), the JSONL store, `rmw_json` of the lock core, and `script-shared` (paths, `worktree_sha`, argument parsing). The model reaches all of it through `python3 .plan/execute-script.py {bundle}:{skill}:{script}` (`ref-workflow-architecture/standards/manage-contract.md`). `manage-worktree` is an empty leftover.

*Command surface*, counted from the argument parsers: about 165 commands — status 31, tasks 20, lessons 19, findings 15, locks 13 (merge lock 9, build queue 4), references 11, files 10, solution outline 10, metrics 10, plan documents 7, ADR 7, logging 5, change ledger 4, CI artifacts 3 — plus about 7 worktree commands. The `SKILL.md` files alone have about 14,200 lines; `manage-status` has 1,726 lines of documentation and about 11,200 of script.

Three structural facts shape the results:

* Paths resolve relative to the cwd (ADR-002, `file_ops.py:482`); the plan directory moves into the worktree in phase 5 and back in finalize.
* Writes are guarded per file (exclusive create in `rmw_json`, `_status_core.write_status`); there is no lock per plan.
* Every operational failure is exit code 0 with `status: error` on stdout (`tools-script-executor/standards/exit-code-convention.md`).

== Gaps in the concept

. *Project-level stores have no location* in the 02 state table: lessons, the change ledger, global and plan-less logs, lock logs, run configuration, architecture enrichment, archived plans with retention, build results outside a plan.
. *Judgment rationale.* The decision log records the model's reasons; 02 derives logs from the audit, but a rationale cannot be derived. Proposal: an optional `rationale` parameter on every `submit`, recorded in the audit log.
. *Large Markdown submissions* (outline, request, lesson bodies). Proposal: small texts as parameters; large documents written by the host tool to a path the server names, then validated by `submit`.
. *Merge-queue semantics*: FIFO fairness, rate windows sharing the queue without taking the mutex, budget reclaim, jittered polling, stale holders with a live worktree.
. *Lock files during coexistence*: Python's merge lock and build queue (and `marshalld`) must interoperate with the daemon on the same files; 12 covers only plan ownership.
. *Writers outside the executor*: the build hook and the merge lock write `status.json` directly (`_status_core.py:140`); the executor's refusal does not stop them.
. *Atomicity across scopes*: plan deletion carries lessons into the global corpus, and promotion moves findings into lessons; the plan lock does not cover the lessons store, and no lock order is stated.
. *Missing resources*: references and footprint, request, lessons, metrics, CI artifacts, audit and log extracts, archived plans.
. *Normalisation for differential tests*: ported stores return fields that exist only because of ADR-002 (`resolved_from`, `scope`, `plan_visibility`, store resolution); 14 must declare them normalised, or the adapter emulates cwd semantics.
. *Envelope packing* has no owner.

== Conflicts

. *Freshness key.* 06 and 03 key freshness on the commit. `worktree_sha` keys on the working tree — HEAD plus staged, unstaged and untracked changes; the change ledger documents that a HEAD key gives a false `fresh` at a pre-commit gate. The model edits uncommitted files, so the concept must adopt the working-tree hash.
. *Plan directory location.* 02 keeps `.plan/` compatible and resolves by `plan_id`; ADR-002 moves the plan directory into the worktree in phase 5, and Python resolves by cwd. A plan owned by PM-MCP needs one fixed location, and the executor's refusal check must find the entry record in either tree. Proposal: PM-MCP never relocates; on entry it moves a relocated plan back, reusing the rollback-safe move of `integrate`.
. *Metrics provenance.* 02 derives metrics rather than letting the model write them, but token usage is only visible to the host — today from dispatch notifications and from reading the host's session transcripts outside the workspace, which conflicts with 09 confinement. Proposal: usage as an optional fact of the dispatch return or `submit`; transcript enrichment only opt-in and operator-approved.
. *Error envelopes and "no internals".* 09 reports failures as a closed-enum reason with an audit id; plan-marshall preserves domain envelopes verbatim, for example `lesson_carry_back_incomplete` with the skipped lessons. Resolution: domain verdicts are facts of a failure state; only server faults are opaque.
. *Inconsistency to settle before differential tests.* `manage-contract.md` states both "0 success, 1 error" and the three-tier model; the Python behaviour, not the prose, is the reference.

== Invariants to preserve

* *Absence.* A negative from a scope that could not see the subject is unknown (ADR-009, `manage-locks/standards/scope-limited-negative-is-unknown.md`); findings distinguish the benign empty store from an absent plan; `add` and `ingest` never create a phantom store; lesson ids resolve to one of three states.
* *Plan deletion.* Carry lessons back first; claim destinations with exclusive create; skip symlinked sources; refuse deletion if any lesson did not land; "not attempted" is not "no lesson file".
* *Merge authorization.* Bound to HEAD and gap class; the check has no per-kind filter; malformed records are fail-closed `lapsed`; a new grant overwrites, there is no revoke.
* *Findings gate.* Armed by state, not by a call — the earlier call-armed gate was inert everywhere; actionable and knowledge types are fixed sets; rejected is not pending; Q-Gate counts sum over all phase files; a producer whose fetched and stored counts differ creates a blocking finding; `raw_input` quarantine with a 64 KiB cap, triage reads only clean fields.
* *Freshness.* One `worktree_sha` implementation shared by writer and gate; changed paths come from git, never from declared files; the ledger is append-only.
* *Step recording.* HEAD at completion is required for HEAD-dependent steps; finalize step names come from a closed set; a display detail is never a control token; loop-back targets are execute or finalize only.
* *Metrics.* Re-entering a phase end accumulates by provenance — explicit deltas are added, accumulator values are not added twice; worked time never exceeds wall time.
* *Locks.* Queue changes merge rather than replace, so co-tenant keys survive; rate windows never take the merge mutex; reaping happens in the same atomic change as admission; a stale holder is not reclaimed while its worktree is live; build-queue liveness is checked per project; a cap disagreement is reported, never reconciled; lock logging is best-effort and outside the critical section.
* *Status writes.* Whole-document writes happen inside the guard, and fields owned by other writers are re-read inside it.
* *Other.* Storing CI artifacts is idempotent per plan and run; scope reconciliation compares in both directions; timestamps are UTC with second precision.

== Conclusions

. *About 165 commands collapse into a few model-facing surfaces.* Roughly 60% become internal server operations (store access, ledgers, locks, logs), about 25% engine transitions or guards (routing, `next`, loop guard, step recording, gates, freshness, footprint); reads become `pm_state` facts or resources; destructive and overriding commands (plan deletion, merge grants, lock release, slot limits) go to the operator channel. No `manage-*` command becomes an MCP tool of its own.
. *Clean ports for differential tests*: references, tasks, findings with ingest, Q-Gate and assessments, lessons, CI artifacts, the outline parser, the change ledger core with `worktree_sha`, and the orchestrator ledger.
. *Stores tied to model behaviour* are specified against the engine instead: step recording, token metrics, model-written logs, path-allocate commands, transition and routing, the loop-exit guard, and locks, whose liveness model changes.
. *Locking is the largest change of mechanism.* The daemon's per-plan serialised writes are strictly stronger than per-file guards, but merge-queue fairness, rate windows, the lock order across scopes and the interoperation with Python lock files still need to be specified.
. *Two decisions come before the stores are ported*: the working-tree hash as freshness key, and retiring the ADR-002 relocation with a normalising move on entry — which also removes most of the envelope fields that would otherwise add noise to the differential tests.
