== Scope

The largest deterministic block of plan-marshall, about 90,000 lines of Python and Markdown:

* the shared build library `script-shared/scripts/build/` (about 10,000 lines) and the four `build-*` skills (about 8,500: discovery, execution, parsers);
* `manage-build-server` and `build-server-client` (about 5,500: the `marshalld` daemon and its client);
* `manage-config` (15,000), `manage-architecture` (14,000), `marshall-steward` (10,000), `tools-integration-ci` (8,000), `manage-run-config` (3,700), `manage-providers` (2,900);
* `extension-api/standards/`: canonical commands, build API, build execution, build systems, build extension point, module discovery, `marshal.json` reference, provider extension point.

== How it works today

The steward wizard seeds `marshal.json`. Extensions discover modules by running the build tool itself (for example `mvn help:all-profiles dependency:tree`, `build-maven/scripts/_maven_cmd_discover.py:570`) and write `derived.json` per module, which contains complete command strings. The model asks `architecture resolve` for a command and receives a `python3 .plan/execute-script.py …` string to run through Bash, optionally routed to `marshalld`, which checks it against a registry. The build wrapper writes the log, learns the timeout, parses the log into status, errors, warnings and tests, and returns TOON. Providers are declared per skill and persisted into `marshal.json`; secrets live in `~/.plan-marshall/credentials/`.

== Gaps in the concept

. *Project setup.* No successor for the wizard's steps 5–13: base branch, providers, architecture, build map, skill domains, finalize steps, CI, credentials. Proposal: a project-level setup state machine with links for the judgment parts and operator-CLI hand-offs for enrolment and secrets.
. *Argument schemas* are named in 07 and left open in 13. Proposal: argument templates per canonical verb as domain-support data (`test -pl {module}`, `verify -P{profile} -pl {module}`), with typed placeholders checked at job time against the server's own discovery — module in the discovered set, profile declared in the descriptor. The operator enrols wrapper and template set, not concrete values, so a new module needs no re-enrolment. Free `-D`, `-f`, `--settings` or `-s` are never accepted.
. *Discovery jobs* run the build tool (`help:all-profiles dependency:tree`, Gradle `properties`, `dependencies`, `tasks`) and need enrolled templates of their own.
. *Timeout source*: learning, floors and keying need a home in server state.
. *Architecture and module model*: discovery caching, enrichment links, query resources, the build map with `derive-verification` and the derivation resolvers are not covered.
. *Coverage, warnings, examined population*: 11 names only log parsers.
. *Provider details*: category cardinality, detection patterns, non-secret configuration, and where a token-lane provider's base URL comes from — 08's "only to the issuing origin" needs a stored origin.
. *Language server binaries*: today an argument vector in a git-ignored file the model can write. Proposal: from domain-support data, host overrides through enrolment like wrappers.
. *Crash replay*: a job in flight during a daemon crash is replayed as `killed`.
. *Migration sequencing*: stage 2 promises structured results from `pm_build`, which needs either Java parsers by then or build jobs that still run as Python script jobs.

== Conflicts

. *Outcome enum.* 07 has succeeded, failed, refused, cancelled, timed out; plan-marshall has success, error, timeout, killed, indeterminate (`build-execution.md:55-88`), and the daemon uses unknown (ADR-009). Without `killed`, restart kills are retried blindly; without `indeterminate`, "could not tell" is folded into a neighbour. Fix: add both to 07 — applied.
. *Wrapper only.* npm has no wrapper (`build-execution.md:201`); Maven and Gradle fall back to the system binary, pyproject to `pwx`. Under 07 an npm project cannot build. Fix: an executable kind "enrolled host tool", as for `git` and `gh`, bound to its absolute path and content hash at enrolment and checked against the same argument schema — applied in 07.
. *Overridable `verify_command`.* It lives in tracked `marshal.json` as a legitimate override and is executed after `shlex.split` (`_providers_core.py:1075`). Under PM-MCP the model never supplies an argument vector: it comes from domain support only, overrides through the operator.
. *MCP proxy example.* 06 names a CI provider and a code-quality service as upstream MCP servers, contradicting 07 and 08 (CI through the official CLI) and ADR-018 (API providers through the REST client). Corrected in 06.
. *Documentation drift not to inherit:* `.plan/architecture/` versus the real `.plan/project-architecture/`; `.plan/credentials/` in the `marshal.json` reference; `ci.commands` although the data model has no `ci` block.

== Invariants to preserve

* Non-finishes stay apart: timeout, killed and indeterminate never become error, create no error rows and store no findings; killed means "do not retry blindly"; only a zero-failure test block is attached to a non-finish.
* Branch on error explicitly; an unknown status is reported as unrecognised, never as red. Read the status, not the exit code.
* Maven and Gradle success needs the log marker, not only exit 0.
* A green run clears findings only if it examined a non-empty population with an analysis able to reach them; gates run mypy without cache.
* Timeout learning: one key per distinct argument string; an explicit bound overrides the learned value but not the floor; a killed duration is never learned.
* Verify-not-resolve: both execution root and cwd are checked; a worktree must be live, share the root's git common directory and lie under a registered container; builds run in a clean environment without provider secrets. PM-MCP re-verifies worktree paths read from plan state, because the model's shell can edit `.plan/`.
* Enrolment is never reachable from a plan.
* The slot cap is machine-wide and independent of the cwd, always reported with its source; invalid and unreadable are never folded into default.
* Audit fate is written at termination, not joined later.
* The build map is seeded once, read fail-closed and applies only to discovered modules.
* Every build carries its plan, with a sentinel routed to the main checkout for builds outside a plan.
* Credentials: command-line declarations carry no HTTP fields; placeholders mean incomplete; symlink and escape protection; HTTPS for authentication headers; sanitised project names.

== Conclusions

. *Build execution transfers almost entirely; the resolution layer inverts.* Vocabulary, result shape, parsers, timeout learning, slot cap, journal and audit carry over. What changes is who composes the command: the chain from `resolve` to an executable string to Bash becomes server-side composition checked against the enrolment.
. *The argument schema is the central undecided contract*: templates per canonical verb as domain data with typed placeholders checked against discovery, covering discovery runs and tools without a wrapper. The job outcome enum regains `killed` and `indeterminate`.
. *Parsers split into engines and pattern data*: engines and structured-format readers (JUnit and JaCoCo XML, LCOV, Jest JSON, TAP) compiled in; categories, markers, routing and Sonar rules as data; acceptable warnings and coverage thresholds as project configuration.
. *`marshal.json` splits three ways*: project configuration (tracked; the model may propose changes through links) — plan and project settings, skill domains, build map, provider selection and non-secret provider configuration, acceptable warnings, coverage; operator enrolment (`~/.plan-marshall/mcp/`) — wrappers, argument templates, worktree containers, slot cap, language server and host tool binaries, `verify_command` overrides; server state — learned timeouts, CI durations, discovery cache, verification times, jobs and logs. Rule: nothing that decides what executes comes from a file the model can write.
. *Architecture analysis belongs on the server* but is not in the concept: discovery, dependency graph, module lookup, impact, `derive-verification` and drift checks as server-computed resources; only enrichment remains judgment. A project setup state machine replaces the steward.
