== Purpose

The concept documents so far settle the technical frame of PM-MCP. This analysis looks at the other side: plan-marshall's *workflow* — the phase model — and its *contracts*, above all the extension API (`marketplace/bundles/plan-marshall/skills/extension-api`). For every element it records whether it transfers to PM-MCP, what changes, and what the concept does not cover yet.

It is an analysis, not a decision record. Decisions that follow from it go into the concept documents.

== Method

The plan-marshall repository was read area by area and every element measured against the concept. Paths in the area documents are relative to `marketplace/bundles/plan-marshall/skills/` of the plan-marshall repository unless stated otherwise.

Every element receives one verdict:

[cols="1,4"]
|===
|Verdict |Meaning

|Transfers
|The concept or contract carries over essentially unchanged, reimplemented in Java where it is code.

|Reshaped
|The intent carries over, the mechanism changes: model-followed instructions become server state and links, a script becomes a job or a guard, a Markdown contract becomes data.

|Obsolete
|Exists only because of the current architecture — model-driven orchestration, Bash hygiene, plugin cache, executor generation, host call ceilings — and disappears.

|Open
|Carrying it over needs a decision the concept has not made yet; the area document names it and proposes an answer.
|===

== What transfers well

* *The stores and their data contracts.* Tasks, references, findings, lessons, CI artifacts, the change ledger and the orchestrator ledger are clean ports for differential tests. Their defect-driven invariants — absence semantics, veto rules, append-only ledgers — carry over unchanged.
* *Deterministic classifiers and gate logic.* Recipe match, planning lane, change-type heuristic, confidence aggregation, verdict currency, freshness, the CI failure taxonomy, the pre-merge barrier, the finalize step ordering bands and the merge mutex are pure functions or closed rules; they become engine code with the same semantics.
* *The build contract.* The canonical command vocabulary, the result shape, the log and coverage parsers, adaptive timeouts, the slot cap, journal replay and verify-not-resolve transfer almost entirely.
* *The dispatch structure.* Level-pinned agents, the prompt body fields and the leaf invariants match concept 03; the dispatch granularity heuristics become rules for where the engine offers `dispatch` links.
* *Judgment contracts with closed shapes.* Change type (a closed enum with a single writer), scope deviation (hold, accept, split), triage per finding and the triage vocabulary per domain map directly onto `submit` links and vocabulary skills.
* *The merge cores of the extension API.* Edge derivation and path attribution merges carry provenance and collision rules that must be ported as they are.

== What does not transfer

* *Model-run orchestration.* About 70% of the finalize skill and most of the planning workflow documents describe mechanics the model follows: step loops, re-entry rules, completion guards, phase entry and exit rituals. They become the workflow engine.
* *Process self-checks.* Handshake invariants that detect the model's own process violations, `mark-step-done` and `assert-step-recorded`, required-step lists and completion guards exist because the model could skip steps; the engine cannot.
* *Architecture workarounds.* The executor and its notation, Bash hygiene, path-allocate content passing, `manage-files`, cwd-relative path resolution with sibling-worktree lookup, execution tiers and timeout clamping for the 600-second Bash ceiling, plugin-cache resolution, extension loading through `importlib`, and envelope packing driven by the orchestrator's context budget.
* *About two thirds of the base persona*, which is Bash and script hygiene. The rest becomes `skill://pm/core`.

== Decisions the concept needs

The area documents converge on a set of decisions. Several were found independently in more than one area.

[cols="1,3,2"]
|===
|Topic |Proposal |Areas

|User interaction
|A `*.awaiting_user` state with typed questions, answered through elicitation. Non-authorising choices (domain, recipe, posture, clarifications) may fall back to answers relayed by the model, recorded as such; authorising decisions (outline approval, deviation accept, drift override, merge consent, plan deletion) require elicitation or the operator CLI. Whether Claude Code supports elicitation decides the usability of the finalize pilot.
|01, 02, 03

|Sub-agent questions
|Sub-agents finish with their best judgment and submit open questions with the result; the question becomes a pending decision in the dispatching session's representation. No blocking `escalate` inside a sub-agent.
|01, 03

|Freshness key
|The working-tree hash (`worktree_sha`: HEAD plus staged, unstaged and untracked changes), not the commit. Builds run before the commit; a commit key reads an unbuilt dirty tree as fresh. Applied in 03 and 06.
|02, 06

|Plan directory location
|PM-MCP never moves a plan directory. A plan moved into its worktree by legacy phase 5 (ADR-002) is moved back when PM-MCP takes it over.
|02, 06

|Dispatch unit
|An envelope of tasks, packed by the engine at plan time; each task `submit` returns the envelope's next task. Applied in 03.
|02, 03, 06

|Dispatch observability
|Every rendered dispatch carries a `dispatch_id`; the dispatching session reports the return (status, display detail, token usage) through a `returned:<dispatch_id>` link. This is also the only source of token metrics, which the server cannot see; missing usage is recorded as unmeasured, never as zero.
|01, 02, 03, 06

|Composite and non-job waits
|`wait:<state>` for waits without a single job: the finalize barrier over CI, review and Sonar, review-bot rate windows, merge-lock admission and merge-queue landing.
|02

|Backward transitions
|Loop-back from finalize to execute with its persisted iteration ceiling, and the light-to-deep outline escalation, as explicit engine transitions.
|01, 02

|Epics emit plans
|The epic link is `emit:<plan>`, which returns the entry command for the operator; a plan is never dispatched as a sub-agent. `running` is observed from the plan's entry record. Applied in 03.
|03

|Reader agents
|A second, read-only agent family without MCP tools for untrusted content; its candidate result goes through the dispatching session into a server-side validation link.
|03

|Project extensions
|No in-process plugins in the native binary. Project steps and recipes are data plus Markdown vocabulary; project code runs out of process as a permanent project script job with a declared argument schema.
|02, 04

|Recipes
|A recipe model: definition data, server-side deterministic deliverable mapping, judgment states for selection, and recipe match during init.
|01, 04

|Argument schemas
|Argument templates per canonical verb as domain-support data, with typed placeholders checked against the server's own module discovery; the operator enrols wrapper and template set. Covers discovery invocations and host tools without a wrapper, such as npm.
|05

|Configuration split
|`marshal.json` splits into project configuration (git-tracked), operator enrolment (`~/.plan-marshall/mcp/`) and server state. Nothing that decides what executes comes from a file the model can write.
|05

|Architecture and setup
|Module discovery, the dependency graph and verification derivation as server-computed resources; enrichment as judgment links. A project setup state machine replaces the steward wizard.
|04, 05

|Locks
|Lock-free snapshot reads, one lock order across scopes (plan, epic, machine), merge-queue fairness and rate windows specified, and interoperation with the Python lock files during coexistence.
|03, 06

|Workflow settings
|The `*_without_asking` knobs, lane selection, thresholds and execution postures as engine configuration that decides which links are offered.
|01, 02, 03
|===

== Corrections to the concept

The analysis found statements in the concept that contradicted established plan-marshall contracts. They have been corrected in the concept documents:

* 03, dispatch example: dispatches a single task; plan-marshall dispatches envelopes (xref:02-execute-finalize.adoc[Execute and Finalize]).
* 03, epic orchestration: a `dispatch` link starts a staged plan; epics must emit plans (xref:03-dispatch-orchestration.adoc[Dispatch and Orchestration]).
* 03 and 06, build server: freshness keyed on the commit (see above).
* 07, job contract: the outcome enum lacks `killed` and `indeterminate`, which plan-marshall keeps apart from failures (xref:05-build-config-providers.adoc[Build, Configuration and Providers]).
* 07, wrapper rule: a project without a wrapper (npm) cannot build at all.
* 08, file store: the layout is not identical to plan-marshall's — entries are keyed by the provider skill name, the project directory by the repository name, and entries may carry header fields.
* 06, MCP proxy: names a CI provider and a code-quality service as upstream MCP servers, which contradicts CI jobs and the token lane.
