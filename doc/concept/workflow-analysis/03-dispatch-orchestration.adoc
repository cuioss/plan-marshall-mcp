== Scope

* *Dispatch contract* (about 2,600 lines): the agents `execution-context` and `execution-context-reader`; the per-client variant emitters `marketplace/targets/{claude,opencode,antigravity}/variant_emitter.py`, which produce levels 1–7 and an `inherit` variant; `extension-api/standards/` (execution-context workflow, dispatch granularity, dynamic level executor, lane element, profiles) and `ref-workflow-architecture/standards/` (agents, dispatch walkthrough and logging, skill loading, citations-only return, execute-task skills, operator prompt authoring).
* *Level selection*: `plan-marshall/standards/effort-{levels,roles,variants}.md`.
* *Personas*: nine `persona-*` skills and `manage-personas`; the base persona `persona-plan-marshall-agent` has about 1,500 lines.
* *Epic orchestration*: `plan-orchestrator` (531 lines plus about 2,100 of workflows and standards, `orchestrator.py`, `_orchestrator_inbox.py`), `persona-plan-orchestrator/standards/orchestration-model.md`, `manage-locks`, the concepts orchestration, execution context, personas, parallelism and locking, and ADR-024. `marshall-orchestrator` is an empty leftover.

== How it works today

The main context resolves a role to a level and a variant (`manage-config effort resolve-target`, which also writes the `[DISPATCH]` log), flattens the persona into `skills[]` and dispatches with the five-field prompt body. The sub-agent loads the base persona and the skills, reads the workflow document, persists through scripts and returns `status` and `display_detail`.

== Gaps in the concept

. *Dispatch link fields* against the real contract: a `dispatch_id`; role and resolved level; a reader schema and a way to select the reader family; a replacement for `plan_id: none` and `instructions`; the rule that runtime inputs live in entity state; the flattened persona in `skills[]`.
. *Return channel.* The server never learns about harness cancellation, empty or error returns, or token usage, so it cannot run the no-progress predicate or detect a missing submit. Proposal: every `dispatch` link pairs with `returned:<dispatch_id>` (status, display detail, usage).
. *Role registry* and where it is configured — project configuration or machine-local ladder.
. *Variant installation*: MCP tools in the tool list, the reader family, alias-gated levels, session-pinned reload.
. *Execution postures* (lanes): floor immunity, prune predicates, overrides per element, cost preview.
. *Personas*: no entries and no composition model in the skill catalogue of 04.
. *Envelopes*: dispatch an envelope entity, not a task, keeping plan-time bin-packing.
. *Plan and epic linkage*: `pm_start` has no reference to a staged specification, so detection and the landing obligation have no anchor.
. *Parallel fan-out*: nothing says a representation may offer several concurrent `dispatch` links (for example enrichment per module).

== Conflicts

. *Epics start plans by `dispatch` (03 Epic orchestration).* A plan dispatches its own sub-agents, and a sub-agent is a leaf, so a plan cannot run as a sub-agent. plan-marshall forbids launching inline (`orchestration-model.md`, prime directive). The epic link must be `emit:<plan>`, returning a `pm-mcp enter` command for the operator and recording `launched`; `running` is observed when the plan's entry record appears.
. *Reader family and "results through `submit`" (03).* Decided and adopted: reader agents are equipped with NO MCP tools (strictly read-only) by security design. Their candidate extract returns in the text response to the dispatching session, which submits it to a server-side deterministic validator before findings are persisted; reader agents never receive `pm_do` (xref:../03-hypermedia-workflow.adoc#dispatch[Sub-agent dispatch]).
. *Blocking `escalate` in sub-agents.* plan-marshall's sub-agents return an otherwise complete result with open questions, and the orchestrator batches them. A sub-agent blocked in `wait` burns turns, and it is unverified whether hosts show elicitation raised from a sub-agent. Proposal: an entity-scope `escalate` records a pending decision and ends the sub-agent with `blocked`; the question fires from the dispatching session.
. *Serialised writes and the git-distributed epic (ADR-024).* A daemon lock does not span machines; reconciliation across machines stays a git merge. Open: which checkout's copy of the epic the daemon writes. Proposal: the main checkout's copy, under the epic lock, committed by git jobs of the orchestrator — which changes ADR-024's "a plan's worktree write is visible at merge" and needs an explicit decision.
. *Coexistence locking (12 Coexistence).* Holding the plan lock for the whole duration of a script job serialises parallel sub-agents and blocks transitions for minutes. Reads must be lock-free snapshots; cross-scope writes need a fixed lock order: plan, then epic, then machine.
. *"No build-time generation per client" (15).* Agent variants remain per-client files with model and effort baked in; that generation stays and moves into installation.

== Invariants to preserve

* Sub-agents never dispatch, never reach the operator, record their outcome before returning; a dispatcher never synthesises a missing record and halts with attribution instead.
* One dispatch log record per firing, never per role; a re-fire records again; no hand-written log beside the seam.
* The reader's containment is a deterministic validator, not the reader itself; it is never folded into the citations-only rule.
* Never name a variant that was not installed.
* Unknown role keys warn and fall back; they never block a dispatch. Orchestrator dispatches name their role explicitly, so the `max` clamp cannot be bypassed.
* A lane `off` on core or derived-state elements is ignored and noted; an unresolved `ask` is dropped only when its provider is absent.
* Indeterminate is never disjoint; one reader of the expected surface; absent, unlistable and unreadable stay distinct (ADR-019); the three inbox empty states, the four mailbox states, `n/a` versus `unknown`.
* Emit is not running, and `auto_emit` never automates the start. The executing plan never writes the ledger. The inbox is append-only, with three recorded in-place changes. Consumption is a claim. Adding a queue row uses exclusive create. Row-local read-modify-write. The legacy layout is refused, never read as empty. Regeneration refuses on an unreadable source.
* A dispatch that does not return is never retried blindly: verify the state on disk, then complete inline.
* Claims are labelled observed or hypothesis; a hypothesis names the artifact that confirms or refutes it.
* Reaping happens in the same atomic change as admission; the build limiter is FIFO and never drops a build.

== Conclusions

. The dispatch concept in 03 matches plan-marshall's structure but lacks the *observability loop* — `dispatch_id`, return report, role-to-level layer. Without it the server cannot enforce the post-return invariants plan-marshall has already debugged.
. There are *two agent families*: workers and readers. The reader's read-only containment without MCP tools is resolved: readers return candidates in text to the caller, which runs the deterministic server validator, preserving the untrusted-ingestion security perimeter.
. *Epics emit plans; they never dispatch them.* PM-MCP improves on plan-marshall by observing `running` from the entry record and deriving landing facts on the server.
. *Personas and lanes become server data*; about two thirds of the base persona disappears, the rest becomes `skill://pm/core`.
. Per-plan locking fits one daemon, but the epic tier is distributed through git: the concept needs the epic write location, a lock order across scopes and lock-free reads, and must not carry the coexistence rule over to parallel sub-agents.
