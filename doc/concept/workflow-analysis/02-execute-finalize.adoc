== Scope

Phases 5 and 6. Finalize is the pilot of the migration (xref:../12-migration.adoc[Migration Path], stage 3) and is covered in detail.

* `phase-6-finalize`: 11,500 lines of Markdown and 4,400 of Python; `SKILL.md` alone 1,984 lines, `branch-cleanup.md` 2,107; 72 test files.
* `phase-5-execute` (1,563 lines plus 730 of standards and 550 of Python) and `execute-task` (465 plus 980).
* `manage-execution-manifest` (9,400 lines), `automatic-review` (7,500), `workflow-pr-doctor`, the git, GitHub, GitLab and Sonar integrations.
* `extension-api/standards/`: finalize step order bands, finalize step, build verify step, verify.

== How it works today

Phase 4 composes the execution manifest `execution.toon`: the verification steps of phase 5, the lane-resolved finalize steps and a snapshot of step parameters.

Phase 5 dispatches one execution context per *envelope* — a bin-packed group of tasks — which loops over its tasks and loads `execute-task` for each (`phase-5-execute/SKILL.md:132-136`). When the last task of a deliverable finishes, the envelope commits and runs a module-scoped build; at the end, whole-tree gates run. Build failures return as `triage_required` and trigger a verification-feedback dispatch. The phase transition requires both the freshness gate and the pending-tasks gate.

Phase 6 is a loop the model runs over the manifest's steps (`phase-6-finalize/SKILL.md:664-1599`), with re-entry, commit instrumentation, a completion guard, metrics bookkeeping and three hooks: escalate-ask, loop-back and unified triage. The order is fixed in bands: settle (below 11), exactly one push (11), a concurrent wait region, the merge gate (70), a post-run band (above 70).

== Gaps in the concept

. *Composite and non-job waits.* The finalize barrier (wake on any arm's change, re-settle only the affected arms), review-bot rate windows lasting hours, merge-lock admission and merge-queue landing have no single job. Proposal: `wait:<state>`, for example `wait:finalize-barrier`; the server polls the arms internally.
. *Backward transitions.* Loop-back from finalize to execute with fix tasks, the persisted iteration ceiling and both knobs (`loop_back_without_asking`, `finalize_without_asking`) are not described; the state machine example in 03 is forward-only.
. *Project-local steps.* 11 Domain support has no mechanism for `project:finalize-step-*` or verify steps. Proposal: steps declared as data with the descriptor facts above, either as a script job with an enrolled command or as a judgment step with a project vocabulary skill; bands and ordering are validated at composition.
. *Token metrics.* Only the host sees usage. Proposal: the dispatch return carries usage; missing usage is recorded as unmeasured, never as zero.
. *Binary upgrade in the middle of a plan.* The concept migrates state formats only. Proposal: the plan program is frozen with the version of the step definitions; an upgrade offers an explicit `recompose` link instead of drifting.
. *Not described yet:* merge authorization records, the review-bot registry as data, lanes, presets and execution profiles, the local-only mode without push, landing emission to the epic inbox, archiving, and the rendering of the PR's intent section.

== Conflicts

. *Operator decisions.* plan-marshall asks about twelve questions through the model — pre-merge consent, merge anyway, accept a coverage gap, red-CI override, defer, disable a reviewer, pre-rebase confirmation, scope deviation, triage options — and the model records the grants (`branch-cleanup.md:42-47`). Concept 09 makes overriding a gate operator-only. Proposal: everything that mints a merge grant or demotes a required bot goes through elicitation; scope deviation and triage remain judgment with operator escalation. Without elicitation every interactive merge needs the operator CLI — a usability risk to decide before the pilot.
. *Dispatch unit.* The example `dispatch:task-4` (03) contradicts one context per envelope (`phase-5-execute/SKILL.md:134`). Proposal: the dispatched entity is the envelope; each task `submit` returns the envelope's next task; packing stays plan-time data.
. *Freshness key.* 06 tracks "which commit a result belongs to". plan-marshall keys on `worktree_sha`, which includes uncommitted changes, because phase 5 builds before it commits; it also has the `exempt` route and the re-stale reconciliation inside finalize. A commit key reads an unbuilt dirty tree as fresh.
. *Plan state location during coexistence.* ADR-002 moves the plan directory into the worktree for phases 5 and 6. A finalize pilot entered after a legacy phase 5 finds its state there. Proposal: plans owned by PM-MCP never move; for a legacy hand-over the first engine transition moves the directory back, keeping "move back before removing the worktree" and the merge lock.
. *Return statuses.* The concept's closed set is `success`, `error`, `loop_back`, `blocked`. plan-marshall also needs `budget_yield`, `triage_required`, `escalate_ask`, `infeasible` and `baseline_drift`. In PM-MCP they are persisted server states, not return values; the concept should say so.

== Invariants to preserve

* *HEAD-dependent verdicts.* A verdict is never green for a HEAD it was not computed against; a missing HEAD means re-fire, with the old verdict reported as unverified. A verdict is preserved only on HEAD equality or when the change does not touch its declared inputs, and the HEAD is never re-stamped on a preserve. Remote verdicts — CI, review, Sonar — declare no inputs. A rebase re-stales everything, but only when it actually rebased.
* *Freshness.* Read the status member itself, never "not stale"; status, not exit code; every build ledger row matches a build notation of this project; a stale result carries its reason; phase 5 evaluates both gates before acting on either.
* *Ordering.* Settle, exactly one push, wait, merge, post-run. The pre-push quality gate is last in the settle band; source-mutating steps precede the merge; post-run review and source mutation exclude each other; reads and destroys edges hold; no two steps share an order.
* *Push.* Re-entry is decided by branch parity; a merged and deleted branch is never pushed again; the tree is clean before the push.
* *Pre-merge barrier.* Both predicates — unhandled comments and required-bot participation against this HEAD. An unknown verdict never authorises and never mints a grant. Route on "admissible" (right HEAD and right gap class), not on "authorised"; a decision-log entry is never evidence; the authorization check is the last gate before the merge.
* *Merging.* The merge dispatch set is closed (safe merge, merge queue). The mutex is released at every wait and every abort with FIFO order kept; a holder is reclaimed only when provably stale.
* *Loop-back.* Target only execute or finalize; ceiling checked before the knob; counter persisted.
* *Outcomes.* `executed`, `skipped`, `loop_back`, `failed` and `error` stay distinct; token figures are unmeasured rather than zero; "could not look" is never a zero count.
* *Escalations.* Options are rendered exactly as returned, recommendation first; a structural refusal is never offered a wait; a decline is not a timeout; an absent outcome is unknown, not a timeout.
* *CI.* A definitive conclusion wins over the deadline fallback; "no checks" is distinct from red; failures are never cached; a red Sonar or review arm still runs its finding pass.
* *Phase 5.* Green needs a verdict artifact and a clean tree; the server re-verifies what the agent claims; `infeasible` is terminal, and no weaker deliverable is substituted under the same name; no batched destructive checkout; a file relocation always triggers the whole-tree gate; the commit belongs to the envelope, never to the task.

== Conclusions

. Finalize is a good pilot. About 70% of its prose is state-machine mechanics; the remaining judgment is small — simplify, security audit, self-review, PR body, triage decisions and replies, lessons, ADRs, retrospective, architecture tier 1. The step descriptor facts carry over as a record.
. The operator split is the critical decision for stage 3: merge consent and every grant go through elicitation, and elicitation support in Claude Code decides whether the pilot is usable.
. Finalize cannot run on links alone before the wait model covers composite and non-job waits.
. The manifest becomes a persisted plan program; its selection rules transfer, reconcile, loadability checks, execution tiers and step recording disappear, and execution logging moves into the audit log.
. Phase 5 needs one decision — envelope dispatch — and one correction — freshness on the working-tree hash. Everything built around host timeouts disappears.
