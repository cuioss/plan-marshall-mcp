[cols="1,3"]
|===
|Area |Decision

|Language and framework
|Java 25+ with Quarkus.

|MCP implementation
|The Quarkiverse https://github.com/quarkiverse/quarkus-mcp-server[Quarkus MCP Server] extension, tracking its 2.1 line for the extension API.

|MCP endpoint
|Served by the daemon with the framework's Streamable HTTP transport on loopback TCP; hosts connect directly or through `pm-mcp serve --stdio` (xref:02-architecture.adoc#_mcp_endpoint[MCP endpoint]).

|One native executable, `pm-mcp`, running on the host (<<_native_binary>>).

|Implemented by PM-MCP on the framework's extension API; tool-based delivery is primary regardless (xref:04-skill-model.adoc#_delivery[Skill Model]).

|Long-running work
|PM-MCP's own job model (jobs with `wait` and `cancel` links); the MCP Tasks extension is adopted once the framework ships it and hosts support it.

|HTTP security and OAuth
|https://github.com/cuioss/cui-http[cui-http] and https://github.com/cuioss/TokenSheriff[TokenSheriff] (<<_security_libraries>>).

|LSP client
|Eclipse LSP4J, registered for reflection and dynamic proxies for native image; replaced if it cannot run natively (<<_native_binary>>).

|Python
|Not part of PM-MCP. plan-marshall's existing scripts run during migration only, as script jobs of the daemon with the host's Python (xref:12-migration.adoc[Migration Path]). The test environment runs them next to the Java implementation (xref:14-test-strategy.adoc[Test Strategy]).

|Git and CI access
|Every git operation as a git job with the host's `git`, every CI operation as a CI job with `gh` or `glab`; the daemon contains no git or CI client of its own (xref:07-build-execution.adoc#_git_jobs[Git jobs], xref:07-build-execution.adoc#_ci_jobs[CI jobs]). == Rationale

* The Quarkus MCP Server supports the current protocol revision (`2026-07-28`) and legacy stateful clients simultaneously, offers stdio and Streamable HTTP, runtime registration of tools and resources, and an extension API for custom methods.
* One codebase yields one native executable for all modes of `pm-mcp`.
* The security layer is first-party, hardened and benchmarked, and matches the operator's expertise.
* Known gaps are covered: Skills are implemented on the extension API; Tasks are not required by the design.

Risks carried with this choice — the framework is a Quarkiverse extension outside the official SDK tiers, the extension API is not yet in a released version, Tasks support is a draft — are tracked in xref:13-open-questions.adoc[Open Questions].

== Security libraries

cui-http::
Validation of inbound requests on PM-MCP's HTTP endpoints (attack-pattern detection), TLS context management, and the HTTP client for token-lane services (code-quality service, upstream MCP servers; xref:08-credentials.adoc[Credential Handling]).

TokenSheriff::
* *Server side* — `token-sheriff-validation` protects PM-MCP's HTTP endpoints as an OAuth resource wherever they are reachable beyond the local machine, in team or remote deployments.
* *Client side* — `token-sheriff-client` performs OAuth and OIDC client flows: the MCP proxy connecting to upstream MCP servers that use MCP's OAuth-based authorization, and token acquisition for code-quality APIs.

Both provide Quarkus extensions.

Transport requirements for every OAuth and upstream connection:

* HTTPS only, with certificate and host-name validation; no option disables validation;
* redirects are followed only to HTTPS targets — a redirect to plain HTTP is an error, never a downgrade;
* tokens are sent only to the origin they were issued for.

== Delivery

`pm-mcp`::
One native binary per platform, delivered as a package (Homebrew for macOS and Linux) and as signed release archives (xref:11-distribution.adoc[Distribution]). Its modes:
+
[cols="1,3"]
|===
|Mode |Purpose

|`pm-mcp daemon`
|The daemon: MCP server, workflow engine, build server, LSP pool (xref:02-architecture.adoc#_daemon[Daemon])

|`pm-mcp token`
|Header helper for hosts that connect directly; derives a short-lived token, prints the authorization header and starts the daemon on demand

|`pm-mcp serve --stdio`
|stdio relay for hosts that cannot obtain headers dynamically

|`pm-mcp enter`
|Entry call of the user-invoked entry points (xref:15-client-profiles.adoc#_entry_call[Entry call])

|`pm-mcp operator`
|Operator CLI (xref:09-security.adoc#operator-channel[Operator channel])
|===

Release integrity::
Every release carries a signature, checksums and a CycloneDX SBOM. Dependency and vulnerability scanning is a gate in CI; dependencies are version-pinned.

== Native binary

The target is one native executable without interpreter or bundled command-line tools. The daemon runs `git`, the wrappers and — during migration — Python scripts as subprocesses with the host's own installations.

* *No Python in PM-MCP.* Not-yet-ported plan-marshall scripts run as script jobs with the host's Python.
* *No git or CI client.* Git and CI run as jobs with the host's `git`, `gh` and `glab`.
* *LSP4J.* Its JSON-RPC layer uses dynamic proxies and Gson reflection over the protocol classes. PM-MCP registers these classes for reflection and the service interfaces as proxies, and verifies the LSP client under native image. The native executable is the fixed goal, not LSP4J: if LSP4J cannot run natively, it is replaced by a different LSP client — for example a minimal one of PM-MCP's own for the operations it uses — rather than moving the daemon to the JVM.
* *Closed world.* Domain support is compiled into the binary or shipped as data with the release; nothing is loaded as code at runtime (xref:11-distribution.adoc#_domain_support[Domain support]).
* *JVM mode* is used for development and tests only.
* *Loopback TCP.* The endpoint listens on loopback TCP, not on a Unix domain socket: Quarkus supports domain sockets only with Netty native transports, which are not supported in native executables.

== Consequences for this repository

* The repository is a Quarkus multi-module build. Its modules are the daemon, the command-line modes of `pm-mcp`, the Skills extension and the domain support; each module is added with its first code.
* The build produces the native `pm-mcp` binary per platform.
* The Skills extension implementation is written so it can be contributed upstream to the Quarkus MCP Server once stable.
