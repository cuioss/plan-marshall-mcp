== Approach

The migration is incremental. plan-marshall's executor already dispatches every operation by notation (`{bundle}:{skill}:{script}`), which gives a mechanical first seam. Each stage ships on its own and is measured against plan-marshall's token and defect baselines before the next starts. Ported scripts are switched to Java individually once they meet the switch-over criteria — differential tests pass, own JUnit tests exist, and a parallel run on real plans shows no unexplained differences (xref:14-test-strategy.adoc#_switch_over[Switch-over]).

== Stages

=== Stage 1 — Executor adapter

PM-MCP exposes the existing executor as tools. Skills stay as they are but replace `python3 .plan/execute-script.py …` Bash calls with tool calls. Where the scripts run — in an interim PM-MCP image or through the host build server — is open (xref:10-technology.adoc#_target_image[Target image]).

The migration inventory assigns every script to a category — ported, redesigned, retired — which decides how it is tested and when it is replaced (xref:14-test-strategy.adoc[Test Strategy]).

Result: Bash hygiene no longer applies to plan-marshall operations; the MCP permission model replaces Bash allowlists. No behavioural change otherwise.

=== Stage 2 — Build server and host backend

The build server moves into PM-MCP with the common job contract; `pm.build` replaces the resolve-then-run pattern and returns structured results. The first backend is the host backend, evolved from `marshalld`, so builds behave exactly as today.

Result: build commands disappear from skills; build output leaves context.

=== Stage 3 — Container backend

The container backend is added and becomes the default for newly enrolled projects; existing projects switch per project after verification.

=== Stage 4 — Hypermedia pilot: finalize

The finalize phase is the pilot for the workflow engine. It has the clearest state machine, the most gates, and the highest defect rate. `pm.state(plan_id)` returns finalize representations with links; the finalize skills shrink to vocabulary skills.

Exit criteria: finalize runs end-to-end through links only, with no model-composed calls, and resume after `/clear` works from `pm.state` alone.

=== Stage 5 — Remaining phases and epics

Init, refine, outline, plan and execute follow, then orchestrator epics.

=== Stage 6 — LSP pool and MCP proxy

The warm LSP pool replaces per-call language servers; selected upstream MCP servers are proxied.

=== Stage 7 — Skill serving and distribution switch

Vocabulary skills are served by PM-MCP and translated per client profile; the filesystem skill corpus, the plugin-cache distribution chain and the build-time multi-target generation are retired for plan-marshall's process skills.

== Coexistence

During migration both models coexist:

* the state store is shared: a plan started under the current model can be continued through PM-MCP and vice versa for as long as both are supported;
* each stage switches a clearly bounded surface; no stage requires the next one;
* the current distribution remains available until stage 7 completes;
* the PM-MCP image reaches its distroless native target state once no script runs inside it and the daemon runs natively.

== Measurement

Each stage is compared against the current model on:

* billing weight per plan (resident context times turns);
* workflow-discipline defects (invented arguments, skipped steps, out-of-order steps);
* resume success after `/clear` and compaction;
* build duration per backend;
* distribution and cache incidents.
