== Approach

The migration is incremental. plan-marshall's executor already dispatches every operation by notation (`{bundle}:{skill}:{script}`), which gives a mechanical first seam. Each stage ships on its own and is measured against plan-marshall's token and defect baselines before the next starts. Ported scripts are switched to Java individually once they meet the switch-over criteria — differential tests pass, own JUnit tests exist, and a parallel run on real plans shows no unexplained differences (xref:14-test-strategy.adoc#_switch_over[Switch-over]).

== Stages

=== Stage 1 — Daemon and executor adapter

The PM-MCP daemon replaces `marshalld` on the host with three job types: `build`, `git` (xref:07-build-execution.adoc#_git_jobs[Git jobs]) and `script`. A script job runs a not-yet-ported plan-marshall script as a subprocess with the host's Python, `git` and `gh`, under the same verification as every other job. It sets `PLAN_BASE_DIR` to the plan-state root the daemon resolved for the plan, so plan-marshall's path resolution (`file_ops.get_base_dir`, which otherwise walks up from the working directory, ADR-002) never depends on the job's working directory — also when the job runs in the plan's worktree.

PM-MCP exposes the existing executor as tools and runs each call as a script job. The entry points call `pm-mcp enter`, which writes the entry record and makes PM-MCP the owner of the plan (<<_coexistence>>). Skills stay as they are but replace `python3 .plan/execute-script.py …` Bash calls with tool calls. PM-MCP itself contains no interpreter (xref:10-technology.adoc#_native_binary[Native binary]).

The migration inventory assigns every script to a category — ported, redesigned, retired — which decides how it is tested and when it is replaced (xref:14-test-strategy.adoc[Test Strategy]).

Result: Bash hygiene no longer applies to plan-marshall operations; the MCP permission model replaces Bash allowlists. No behavioural change otherwise.

=== Stage 2 — Build server

The build server moves into PM-MCP with the common job contract; `pm_build` replaces the resolve-then-run pattern and returns structured results. Builds run as in stage 1, exactly as with `marshalld`.

Result: build commands disappear from skills; build output leaves context.

=== Stage 3 — Hypermedia pilot: init

The redesigned workflows switch in phase order, starting at the beginning of a plan, so every phase switches onto the state its predecessor already wrote through PM-MCP. Init is the pilot for the workflow engine. `pm_state(plan_id)` returns init representations with links; the init skills shrink to vocabulary skills, which PM-MCP serves from this stage on through its skill tools (xref:04-skill-model.adoc#_delivery[Delivery]), since representations name them. The pilot starts once the stores init writes — status and references — are ported, because the engine writes only through Java stores under the plan's lock (xref:16-implementation.adoc#_transition_order[Transition order]).

Init needs two decisions first: routine user interaction — its questions to the user — and the plan sources beyond a free-text request (xref:13-open-questions.adoc#_open_decisions[Open decisions]).

Exit criteria: init runs end-to-end through links only, with no model-composed calls; resume after `/clear` works from `pm_state` alone; the plan continues in the legacy refine phase without loss.

=== Stage 4 — Remaining phases and epics

The remaining phases follow in order, each measured before the next one starts: refine and outline, plan, execute with envelope dispatch, finalize; then orchestrator epics. Each phase switches once the stores it writes are ported.

=== Stage 5 — LSP pool and MCP proxy

The warm LSP pool replaces per-call language servers; selected upstream MCP servers are proxied.

=== Stage 6 — Skill serving and distribution switch

All vocabulary skills are served by PM-MCP and translated per client profile; the filesystem skill corpus, the plugin-cache distribution chain and the build-time multi-target generation are retired for plan-marshall's process skills.

== Coexistence

During migration both models coexist:

* the state store is shared, and each plan has exactly one owner at a time. Entering a plan through PM-MCP writes its entry record (xref:15-client-profiles.adoc#_persistence[Persistence]) and makes PM-MCP the owner: from then on the daemon performs every write to that plan under the plan's lock. A legacy script writes the plan state directly, so the daemon holds the plan's lock for the whole duration of every script job on that plan; script jobs on one plan never overlap each other or a transition. The Python executor refuses write operations on a plan that has an entry record; this guard does not exist in plan-marshall yet and is added there before stage 1 ships (<<_plan_marshall_prerequisites>>). The operator releases a plan back to the current model by dropping its entry record through the operator CLI;
* each stage switches a clearly bounded surface; no stage requires the next one;
* the current distribution remains available until stage 6 completes;
* PM-MCP is a native executable without interpreter from the first stage (xref:10-technology.adoc#_native_binary[Native binary]).

Some steps need changes in plan-marshall first; each is a pull request there, released before the PM-MCP step that relies on it:

|===

== Measurement and rollback

Each stage is compared against the current model on:

* billing weight per plan (resident context times turns);
* workflow-discipline defects (invented arguments, skipped steps, out-of-order steps), and link arguments `pm_do` rejects;
* resume success after `/clear` and compaction (100% pass threshold required);
* build duration and execution overhead (within +/- 5% of direct CLI baseline);
* distribution and cache incidents.

Rollback criteria::
Each migration stage maintains an explicit rollback path. If differential tests, crash recovery validation, or client compatibility regress beyond baseline thresholds, the entry record can be dropped through the operator CLI (`pm-mcp operator release-plan`) to return plan ownership immediately to the Python executor, and the previous distribution can be reactivated without loss of persisted state.
