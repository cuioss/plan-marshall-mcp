== Decisions

. *Builds always run through the project's wrapper.* Every build is `<wrapper> <arguments>` in the plan's worktree — `mvnw`, `gradlew`, `pw` or equivalent, committed at the root of the tree. PM-MCP never invokes a toolchain binary directly.
. *Builds run natively on the host*, as subprocesses of the daemon, with the host's toolchains — as plan-marshall's `marshalld` runs them.
. *Every git operation runs as a git job* with the host's `git` (<<_git_jobs>>).
. *Builds, git jobs and script jobs share one job contract*, one policy model and one result format.

Variants that were considered and the research behind them are in xref:discussions/execution-alternatives.adoc[Execution Alternatives], xref:discussions/execution-patterns.adoc[Execution Patterns] and xref:discussions/container-backend.adoc[Container Backend].

== Enrolment

A project's wrappers and argument schemas are part of its enrolment, set by the operator through the operator CLI (xref:09-security.adoc#operator-channel[Operator channel]) and never by the model or a plan:

[source,yaml]
----
project: /Users/oliver/git/TokenSheriff
build:
  wrappers: [mvnw]
----

Enrolment is stored in `~/.plan-marshall/mcp/`.

== Job contract

PM-MCP's build server composes each job and runs it as a subprocess of the daemon.

Job specification::
* job type: `build`, `git` (<<_git_jobs>>) and, until the last plan-marshall script is ported, `script` (xref:12-migration.adoc[Migration Path]);
* project and worktree;
* executable and argument vector (checked against the argument schema);
* environment allowlist;
* limits: timeout.

Operations::
`submit` → job id; `events` (log stream and state changes); `wait` (bounded); `cancel`.

Outcome::
Closed-enum state — `succeeded`, `failed`, `refused`, `cancelled`, `timed_out` — plus exit code, log location and duration. `refused` (the job did not match the enrolment) is a distinct state in the representation, never reported as a failed build.

Implemented once in PM-MCP:

* enrolment and argument schemas (verify-not-resolve);
* the scheduler with the machine-wide slot cap;
* the job store and the audit log;
* log parsing into the structured build result (xref:05-tool-surface.adoc#_build_results[Build results]);
* freshness tracking for gates.

== Execution

The daemon keeps `marshalld`'s properties:

* strictly opt-in: a project is served only after operator enrolment;
* verify-not-resolve: each job is checked against the enrolment — worktree containment (enrolled root or a live linked worktree of it), wrapper at the tree root and tracked by git, argument schema — and refused otherwise;
* the executable is run directly, never through a shell, in its own process group;
* machine-wide slot cap, job journal, append-only audit;
* enrolment is operator-only and never reachable from a plan.

Builds run with the developer's privileges and toolchains; on Linux they inherit the daemon's systemd confinement (xref:09-security.adoc#_hardening[Hardening]).

=== Builds that start containers

They use the host's container runtime directly, as when the developer runs the build by hand: native container builds, image builds, Compose stacks and Testcontainers work unchanged.

=== Warm processes

The daemon is long-lived, so projects can use build daemons (Gradle daemon, `mvnd`) that stay warm between builds. Whether a project does is a property of its wrapper and configuration.

== Git jobs

Every git operation — reading ones such as status, log, diff and the file footprint of a plan as well as commit, push, fetch, merge, rebase, creating and removing worktrees — runs as a *git job*: a subprocess of the daemon running the host's `git` with the developer's own configuration. Credential helpers, SSH agent, commit signing and hooks behave exactly as when the developer runs `git` by hand. This applies to every enrolled project.

* PM-MCP composes each git job from a closed set of operations and their argument vectors; the model never supplies git arguments.
* Each job is verified like a build job: the repository must be the enrolled root or a live linked worktree of it. `git` is executed directly, never through a shell.
* Commit messages and other text are passed as data through stdin or a file, never as part of a command line.
* Hooks are repository code and run with the developer's privileges, as they do when the developer commits by hand.

The daemon contains no git implementation of its own; git behaves in every operation exactly as it does for the developer.
