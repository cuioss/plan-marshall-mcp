Measurements behind the decision to start a fresh container per build (xref:../08-container-backend.adoc#warm-builders[Container Backend]).

== Setup

* macOS developer machine, 10 CPUs.
* Container runtime: OrbStack.
* Worktree mounted at the same absolute path; the host's Maven repository mounted as cache.
* All builds offline, so dependency resolution does not add network variance.

== Results

[cols="2,1,1"]
|===
|Measurement |Host (native) |Fresh container

|Bare container start (`docker run --rm … true`, 5 runs)
|–
|0.31–0.54 s

|Minimal Maven module, `mvnw -o compile` (3 runs)
|1.7–2.7 s
|2.4–3.7 s

|`cui-http-core`, `mvnw -o test` (2–3 runs)
|33.0–38.5 s
|28.8–43.3 s
|===

== Findings

* The fixed cost of a fresh container is about 0.3–1 s per build (container start plus cold JVM).
* For real test runs this is smaller than the variance between identical runs.
* No bind-mount penalty was measurable for this Maven workload on OrbStack.
* Incremental build state is not lost: `target/` lives in the mounted worktree and carries over between containers.
* Caches matter more than warm processes: in the offline setup the mounted dependency repository is a precondition for the build at all; in online runs a build without it downloads every dependency. The online cost was not measured.
* Python wrappers (`pw`) have no warm-process component; only their tool cache matters.
* A warm process would save JVM start and JIT warm-up — seconds per build, relevant only for many very short builds.

== Not yet measured

* Docker Desktop and `podman machine` on macOS.
* A full plan-marshall `verify`.
* Many short, frequent builds (single-module compiles, single tests) as they occur during task execution.
