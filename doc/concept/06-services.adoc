The daemon hosts three services that today are separate processes or started per call.

[[build-server]]
== Build server

=== Role

Owns builds for all enrolled projects on the machine: job lifecycle, scheduling with a machine-wide slot cap, policy and audit. This is the role plan-marshall's `marshalld` daemon fills today. Builds run natively on the host as subprocesses of the daemon (xref:07-build-execution.adoc[Build Execution]).

=== Behaviour

* Build commands are resolved server-side from the project's configuration and its domain support (xref:11-distribution.adoc#_domain_support[Domain support]) and invoke the project's wrapper, or, where the build system has no wrapper, an enrolled host tool bound to its path and hash (xref:07-build-execution.adoc[Build Execution]). The model never sees or composes a build command line.
* A build is a job: submission returns a job id and a `running` representation; completion is observed through its `wait` link (xref:03-hypermedia-workflow.adoc#long-running[Long-running operations]).
* The result is structured: closed-enum status, counts, located errors and failing tests. The log is a resource.
* Scoping is automatic: a build for `plan_id` runs in that plan's worktree.
* Freshness is tracked by the server: which working-tree state a result belongs to — the commit plus staged, unstaged and untracked changes, because builds run before the commit — and whether it covers the scope a gate requires. Gates read this directly instead of asking the model to judge build coverage.

=== Gains

* Timeout handling is the server's concern; host tool timeouts no longer shape how builds are invoked.
* Concurrency limits apply across all sessions and sub-agents.
* Build output never floods context.

[[lsp]]
== LSP and LSP proxy

=== Role

Holds language servers warm per workspace and language and exposes them through `pm_lsp`. Today plan-marshall's LSP client spawns a server per call and tears it down, paying cold start on every call and in every sub-agent.

=== Behaviour

* A pool keyed by (workspace, language). A plan's worktree is its own workspace.
* Servers start lazily and shut down on idle or when a plan's worktree is removed.
* Operations: `workspace/symbol`, `definition`, `references`, `documentSymbol`, `rename` (as a verified `WorkspaceEdit`), and diagnostics.
* A rename is applied by the server and its footprint recorded in the plan's state, so the realized change set is known without the model reporting it.
* Language servers run on the host as subprocesses of the daemon, with the host's toolchains.

=== LSP proxy

The pool is available to editors through a proxy endpoint, protected like the MCP endpoint — loopback only and token-authenticated (xref:09-security.adoc#_local_attack_surface[Local attack surface]). An IDE can attach to the language server the plan is using instead of starting its own. Diagnostics the IDE sees and diagnostics the model sees come from the same server instance.

=== Gains

* No cold start per call.
* Coordinate-based navigation replaces bulk file reads, which reduces context.
* Sub-agents share warm servers.

[[mcp-proxy]]
== MCP proxy

=== Role

Aggregates upstream MCP servers (for example an issue tracker or a documentation service) behind PM-MCP's surface. CI providers are not proxied — they run as CI jobs through their command-line tools (xref:07-build-execution.adoc#_ci_jobs[CI jobs]) — and services with a REST API, such as code-quality services, are reached directly through the token lane (xref:08-credentials.adoc[Credential Handling]).

=== Behaviour

* Upstream tools are re-exposed selectively: only the tools a workflow uses, optionally narrowed in their parameters. This reduces resident tool schemas compared to connecting each upstream server directly.
* Upstream calls are scoped and logged like PM-MCP's own calls.
* Workflow links may resolve to upstream tools; `pm_do` executes the upstream call with the arguments the server derives from the link and the persisted state.

=== Provenance

Proxying makes PM-MCP the origin the host sees. To avoid laundering trust:

* upstream content keeps its originating server in `_meta` under a PM-MCP prefix;
* upstream skills are never re-served as PM-MCP skills;
* upstream content is treated as untrusted input by the workflow engine;
* each upstream server is reached with PM-MCP's own credentials for that server; no token received from a host or another server is passed through (xref:09-security.adoc#_hardening[Hardening]).

See xref:09-security.adoc[Security and Trust Model].
