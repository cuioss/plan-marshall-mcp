The core daemon hosts three services that today are separate processes or started per call.

[[build-server]]
== Build server

=== Role

Owns builds for all enrolled projects on the machine: job lifecycle, scheduling with a machine-wide slot cap, policy and audit. This is the role plan-marshall's `marshalld` daemon fills today. Execution is delegated to a build backend selected per project (xref:07-build-execution.adoc[Build Execution]).

=== Behaviour

* Build commands are resolved server-side from the project's configuration and always invoke the project's wrapper. The model never sees or composes a build command line.
* A build is a job: submission returns a job id and a `running` representation; completion is observed via `pm.wait` (xref:03-hypermedia-workflow.adoc#long-running[Long-running operations]).
* The result is structured: closed-enum status, counts, located errors and failing tests. The log is a resource.
* Scoping is automatic: a build for `plan_id` runs in that plan's worktree.
* Freshness is tracked by the server: which commit a result belongs to, and whether it covers the scope a gate requires. Gates read this directly instead of asking the model to judge build coverage.

=== Gains

* Timeout handling is the server's concern; host tool timeouts no longer shape how builds are invoked.
* Concurrency limits apply across all sessions and sub-agents.
* Build output never floods context.

[[lsp]]
== LSP and LSP proxy

=== Role

Holds language servers warm per workspace and language and exposes them through `pm.lsp`. Today plan-marshall's LSP client spawns a server per call and tears it down, paying cold start on every call and in every sub-agent.

=== Behaviour

* A pool keyed by (workspace, language). A plan's worktree is its own workspace.
* Servers start lazily and shut down on idle or when a plan's worktree is removed.
* Operations: `workspace/symbol`, `definition`, `references`, `documentSymbol`, `rename` (as a verified `WorkspaceEdit`), and diagnostics.
* A rename is applied by the server and its footprint recorded in the plan's state, so the realized change set is known without the model reporting it.
* Where the language-server processes run — they need the project's toolchains — is open (xref:13-open-questions.adoc[Open Questions]).

=== LSP proxy

The pool is available to editors through a proxy endpoint: an IDE can attach to the language server the plan is using instead of starting its own. Diagnostics the IDE sees and diagnostics the model sees come from the same server instance.

=== Gains

* No cold start per call.
* Coordinate-based navigation replaces bulk file reads, which reduces context.
* Sub-agents share warm servers.

[[mcp-proxy]]
== MCP proxy

=== Role

Aggregates upstream MCP servers (for example a CI provider, a code-quality service, an issue tracker) behind PM-MCP's surface.

=== Behaviour

* Upstream tools are re-exposed selectively: only the tools a workflow uses, optionally narrowed in their parameters. This reduces resident tool schemas compared to connecting each upstream server directly.
* Upstream calls are scoped and logged like PM-MCP's own calls.
* Workflow links may target upstream tools; the server binds the parameters.

=== Provenance

Proxying makes PM-MCP the origin the host sees. To avoid laundering trust:

* upstream content keeps its originating server in `_meta` under a PM-MCP prefix;
* upstream skills are never re-served as PM-MCP skills;
* upstream content is treated as untrusted input by the workflow engine.

See xref:09-security.adoc[Security and Trust Model].
