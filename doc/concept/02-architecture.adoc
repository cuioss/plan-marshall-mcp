== Principles

. *The server owns process; the model owns judgment.* Everything deterministic — state, transitions, gates, argument assembly, execution — lives in PM-MCP. The model decides only what requires judgment.
. *State is addressed, never reconstructed.* Every interaction names a `plan_id` or an `epic_id`. The server answers with the authoritative state; the model never rebuilds state from documents.
. *State lives in the filesystem.* Every piece of state is persisted in files; no process holds state that is lost when it stops. There is no session context (<<_state_persistence>>).
. *Confined to the working directory.* Every PM-MCP operation is limited to the project the context works in; other projects are reachable only after the user's approval (xref:09-security.adoc#_workspace_confinement[Workspace confinement]).
. *Hypermedia drives the workflow.* The server tells the model what it can do next as links — link ids with the parameters that need judgment (xref:03-hypermedia-workflow.adoc[Hypermedia Workflow]).
. *One binary, one version.* Skills, tools, client profiles and services come from the same binary and cannot drift.
. *Local by design.* PM-MCP runs on the developer's machine, next to the repository and worktrees. It is not a remote service.
. *Runtime-neutral.* Everything a host needs is reachable through plain MCP tools; MCP extensions are used where present and are never a precondition.

=== MCP endpoint

The daemon is the MCP server. It serves MCP over Streamable HTTP on the loopback interface; the endpoint declares the `resources` capability and the Skills extension and exposes the tool surface. Hosts connect in one of two ways, recorded per client in the client profile (xref:15-client-profiles.adoc#_client_profiles[Client profiles]):

Direct::
The host connects to the endpoint over Streamable HTTP and obtains the cookie from a header helper it runs on every connection — for Claude Code `"headersHelper": "pm-mcp token"`. The cookie appears in neither the host's configuration nor its environment.

stdio::
Hosts that cannot obtain headers dynamically start `pm-mcp serve --stdio` as their MCP server. This mode of the same binary relays every message between the host's stdio and the daemon's endpoint; it has no tools and no state.

The endpoint (xref:09-security.adoc#_local_attack_surface[Local attack surface]):

* binds to `127.0.0.1` only, configured explicitly;
* validates the `Origin` and `Host` headers on every request and rejects unexpected values with HTTP 403, which blocks DNS rebinding from web pages;
* requires the daemon's cookie, a random secret written at every start to a file only the user can read (xref:09-security.adoc#_hardening[Hardening]).

=== Daemon

A long-lived native process on the host, running as the developer's user — the successor of plan-marshall's `marshalld`. It owns everything that must outlive a host session or be shared across sessions and sub-agents:

Workflow engine::
The state machines for plans (init → refine → outline → plan → execute → finalize, including the finalize step sequence) and for orchestrator epics, written as definitions in PM-MCP's workflow DSL over Java primitives (xref:16-implementation.adoc#_workflow_definition[Workflow definition]). It computes representations and links and validates every transition.

State store::
Reads and writes the authoritative plan and epic state in the filesystem (<<_state_persistence>>). Access happens through the engine only; in memory the daemon keeps caches, never the only copy.

Build server::
Jobs, scheduling and policy. Builds, git operations and scripts run as subprocesses of the daemon (xref:06-services.adoc#build-server[Build server], xref:07-build-execution.adoc[Build Execution]).

LSP pool and proxy::
Warm language servers per workspace and language (xref:06-services.adoc#lsp[LSP]).

Skill generator::
Produces the vocabulary skills per project and client from project configuration, the domain support of the release and the client profile (xref:04-skill-model.adoc[Skill Model], xref:15-client-profiles.adoc[Client Profiles]).

Upstream MCP connections::
Connections to other MCP servers whose tools and resources PM-MCP re-exposes (xref:06-services.adoc#mcp-proxy[MCP proxy]).

Audit and event log::
Every transition, tool call and build is recorded. Metrics, retrospectives and landing records are derived from it rather than written by the model.

== Interaction model

[source,text]
----
Model                          PM-MCP
  │  pm_state(plan_id)            │
  ├──────────────────────────────►│  engine computes representation
  │  representation + links       │
  │◄──────────────────────────────┤
  │  (optionally loads the        │
  │   vocabulary skill named in   │
  │   the representation)         │
  │  pm_do(scope, link, free)     │
  ├──────────────────────────────►│  validate against state, execute
  │  result + next representation │
  │◄──────────────────────────────┤
  ⋮                               ⋮
----

Every transition returns the next representation, so the workflow is a chain of link-follows; a separate `pm_state` call is needed only to resume.

== Scoping

Every call is scoped by identifiers. `plan_id` or `epic_id` and the entity travel in the call; `client` and `project` are read from the scope's entry record:

* `client` — the agent runtime (`claude`, `opencode`, `antigravity`, …) of the session, declared at the entry point by `pm-mcp enter` and persisted with the plan or epic (xref:15-client-profiles.adoc#_persistence[Persistence]); it selects the client profile used to render skills, representations and links (xref:15-client-profiles.adoc[Client Profiles]). The model never decides it.
* `plan_id` — a plan and its worktree. The server resolves the worktree, branch and configuration from it; the model never passes paths.
* `epic_id` — an orchestrator epic.
* entity — the task, finding or job a transition acts on, named in the link id (xref:03-hypermedia-workflow.adoc#_links[Links]).
* `project` — the workspace root: the repository checkout the entry point was invoked in, persisted in the entry record; every PM-MCP operation is confined to it (xref:09-security.adoc#_workspace_confinement[Workspace confinement]).

A call without a plan or epic scope is limited to discovery and plan creation (`pm_plans`, `pm_epics`, `pm_start`).

== State persistence

=== Decision

All workflow and daemon state is persisted in the filesystem; credentials live in the credential store, the OS credential store or its file-store fallback. Processes hold caches only.

[cols="1,2"]
|===
|State |Location

|Plan state: phase, tasks, findings, references, build jobs of the plan; the entry record (client identity, workspace root) in the plan's `mcp/` directory
|The project's `.plan/` tree (git-ignored local part)

|Epic state: ledgers, inbox, landings
|The project's `.plan/` tree (git-tracked part)

|Approvals for access beyond the project (xref:09-security.adoc#_access_to_other_projects[Access to other projects])
|The project's `.plan/` tree (git-ignored local part)

|Credentials of the token lane and PM-MCP's own secrets (xref:08-credentials.adoc[Credential Handling])
|The OS credential store; fallback `~/.plan-marshall/credentials/`

|Enrolment, build-slot and lock state, client install records, daemon lock file and port, logs and audit log
|`~/.plan-marshall/mcp/` — machine-wide, at user level, next to plan-marshall's `credentials/` and `marshalld/`; the instance directory of the installation (xref:11-distribution.adoc#_server_installation[Server installation])
|===

=== No session context

MCP does not provide a session to hold state in: protocol `2025-11-25` has a handshake-based session, but the current revision `2026-07-28` removed it, and every request describes itself in its metadata. PM-MCP therefore does not use one, in either revision:

* the scope of a call — plan or epic, and the addressed entity in the link id — travels in its arguments; the client identity and workspace root are read from the plan's or epic's persisted entry record;
* every call is answered from the persisted state alone, so host restarts, `/clear`, compaction, daemon restarts and switching clients mid-plan lose nothing.

The layout and file formats are compatible with plan-marshall's `.plan/` tree during migration.

== Boundaries

In scope::
Process state and transitions, execution of deterministic operations (git, builds, CI provider, file-footprint capture, findings storage), language services, skill generation, aggregation of upstream MCP servers.

Out of scope::
Content produced by judgment (outlines, code, triage decisions, commit and PR prose). The server stores and validates it; the model writes it.

Not relied on::
MCP sampling for server-initiated model calls. Every judgment step is a free parameter of a link the model follows.

== Deployment topology

* One daemon per machine, native on the host, serving all enrolled projects (xref:10-technology.adoc#_delivery[Delivery]).
* It works directly on the repositories and worktrees at their paths; nothing is mounted or translated.
* Builds, git operations, scripts and language servers run as its subprocesses (xref:07-build-execution.adoc[Build Execution]).
* Cross-session coordination (merge mutex, review-bot rate windows, build slots) is serialised by the daemon and persisted as files, so a daemon restart loses no lock, window or slot.

=== Lifecycle

Start on demand::
`pm-mcp token`, `pm-mcp serve --stdio` and `pm-mcp enter` start the daemon when its endpoint is not reachable. A lock file in `~/.plan-marshall/mcp/` and the port binding ensure that exactly one daemon runs.

Explicit control::
`pm-mcp daemon start`, `stop`, `restart`, `status` and `run`, also as the scripts `bin/start.sh`, `bin/stop.sh`, `bin/run.sh` and `bin/status.sh` of the installation (xref:11-distribution.adoc#_server_installation[Server installation]).

Idle exit::
A daemon started on demand exits after an idle timeout, once no connection, job or language server is active.

OS service::
Optionally, the operator registers the daemon as a user service (`pm-mcp operator service install`): a launchd LaunchAgent on macOS, a `systemd --user` unit on Linux, each running `pm-mcp daemon run`. The OS then starts it at login and restarts it after a crash; it does not exit on idle.

Drain::
Stopping or restarting drains the daemon: queued jobs stay queued, running jobs finish, then it exits. Jobs are its subprocesses, so it never exits while one runs. The next daemon continues from the persisted state.

Unreachable daemon::
If the daemon cannot be started, `pm-mcp token` and `pm-mcp serve --stdio` report `daemon_unavailable` with the operator command that diagnoses it.

=== Updates

* Binary, skills, client profiles and tools are one version (xref:11-distribution.adoc#_updates[Updates]).
* Whenever `pm-mcp token`, `pm-mcp serve --stdio` or `pm-mcp enter` connects, it compares its own version with the running daemon's. If the binary on disk is newer, it asks the daemon to drain and restart; hosts reconnect.
* Every state file carries a format version. On start, the daemon migrates older formats forward.
