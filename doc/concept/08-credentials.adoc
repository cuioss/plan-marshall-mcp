= Credential Handling
:toc: left
:toclevels: 2
:nofooter:

xref:README.adoc[Concept] » Credential Handling

== Decisions

. *Two lanes.* A provider is either *system-authenticated* — its own command-line tool holds the credential — or *token-authenticated* — PM-MCP holds a token for it. This follows plan-marshall's provider model.
. *PM-MCP holds no credential for the system lane.* `git`, `gh` and `glab` keep their own credentials; CI providers are integrated through their official command-line tools as jobs (xref:07-build-execution.adoc#_ci_jobs[CI jobs]).
. *Two stores for the token lane* and for PM-MCP's own secrets: the *OS credential store* as the primary store, the *file store* in `~/.plan-marshall/credentials/` as the fallback. The file store keeps plan-marshall's layout and format.
. *Secrets never pass through the model.* They are entered by the operator, read by the daemon at the moment of use, and never appear in results, errors, logs or the audit log.

== Lanes

[cols="1,2,2,2"]
|===
|Lane |Providers |Credential held by PM-MCP |Verification

|System
|`git`, `gh`, `glab`
|None — the tool's own store: git credential helpers and SSH agent, the `gh` and `glab` logins
|The provider's verify command as a job, for example `gh auth status`

|Token
|Services without a command-line tool: code-quality services (Sonar), upstream MCP servers, other REST providers
|A token or basic credentials in the credential store
|An authenticated request to the provider's verify endpoint
|===

The lane is a property of the provider's declaration in the domain support (xref:11-distribution.adoc#_domain_support[Domain support]), not a setting.

== PM-MCP's own secrets

PM-MCP keeps two secrets of its own in the same stores:

* the signing secret from which `pm-mcp token` derives short-lived MCP tokens (xref:09-security.adoc#_hardening[Hardening]);
* the operator token of the operator CLI (xref:09-security.adoc#operator-channel[Operator channel]).

Both are created by `pm-mcp operator` on first use and can be rotated with `pm-mcp operator credentials rotate`.

== Stores

=== OS credential store

The primary store.

[cols="1,2,3"]
|===
|Platform |Store |Notes

|macOS
|Keychain (login keychain)
|Items are created with an access control list that trusts only the `pm-mcp` binary. Any other program reading them — including a shell the model drives — triggers a confirmation prompt to the user instead of reading silently.

|Linux
|Secret Service (GNOME Keyring, KWallet) over D-Bus
|No per-application access control: any process of the user's session can read an unlocked collection. Protects at rest and against other users.

|Windows
|—
|PM-MCP runs inside WSL, which has no Secret Service by default; the file store applies.
|===

Entries use the service name `plan-marshall-mcp` and the account `<provider>` for global entries or `<project>/<provider>` for project entries. The value holds the same fields as a file-store entry.

The store is available only where it can be reached: Secret Service needs a session bus and an unlocked keyring, which headless Linux machines, containers and WSL usually lack. PM-MCP then uses the file store.

=== File store

The fallback, identical to plan-marshall's credential files, so a credential configured for plan-marshall serves PM-MCP and vice versa.

* Location `~/.plan-marshall/credentials/`, below the home root that `PLAN_MARSHALL_HOME` overrides.
* Global entries in `<provider>.json`, project entries in `<project>/<provider>.json`.
* The directory has mode `0700`, every file `0600`. Files are created atomically with that mode, and the mode is verified after writing.
* Every path is canonicalised and must stay inside the directory; project names are sanitised to `[a-zA-Z0-9._-]`.

[source,json]
----
{
  "auth_type": "token",
  "token": "REPLACE_WITH_YOUR_TOKEN",
  "verified_at": "2026-09-24T09:20:00Z"
}
----

`auth_type` is `none`, `token` or `basic` (with `username` and `password`). The placeholders `REPLACE_WITH_YOUR_TOKEN`, `REPLACE_WITH_YOUR_USERNAME` and `REPLACE_WITH_YOUR_PASSWORD` mark an entry as incomplete.

The directory mode is the boundary against other users. Processes of the same user — including a shell the model drives — can read the files. Deny rules for the host's file tools, installed with `pm-mcp operator install-client` where the host has a permission model, are defence in depth only.

=== Resolution

For a provider, PM-MCP looks up, in this order:

. OS credential store, project entry;
. OS credential store, global entry;
. file store, project entry;
. file store, global entry.

The first complete entry is used; an entry with placeholders is skipped as incomplete. `pm-mcp operator credentials status` shows, for every provider, which store serves it and whether it is verified — never the secret.

== Configuration

Secrets enter only through the operator:

* `pm-mcp operator credentials set <provider> [--project]` asks for the secret on the terminal without echo and writes it to the OS credential store. The secret is never a command-line argument or an environment variable.
* Without an OS credential store, `set` creates the file-store entry with placeholders and names its path; the operator replaces the placeholders in the file, as with plan-marshall.
* `check` reports completeness, `verify` runs the provider's verification, `remove` deletes an entry, and `migrate` moves a file-store entry into the OS credential store and deletes the file.

The model sees only states: `complete`, `incomplete`, `not_found`, `verified`, `unverified`. A plan that needs a missing credential moves into a `*.blocked` state whose representation names the operator command (xref:09-security.adoc#operator-channel[Operator channel]).

== Use

* The daemon reads a secret at the moment of use and holds it in memory only for that request. It is never cached, written elsewhere or passed to a subprocess; system-lane tools use their own stores.
* HTTPS only, with certificate and host-name validation; a token is sent only to the origin it was issued for; a redirect to plain HTTP is an error (xref:10-technology.adoc#_security_libraries[Security libraries]).
* No token passthrough: the MCP proxy reaches each upstream server with its own credential for that server, never with a token received from a host or another server (xref:09-security.adoc#_hardening[Hardening]).
* Secrets never appear in results, errors or the audit log; error responses from providers are redacted before they are logged.

== Protection

[cols="2,2,2"]
|===
|Threat |OS credential store |File store

|Other local users
|Protected by the store
|Protected by modes `0700` / `0600`

|The model's shell, same user
|macOS: confirmation prompt through the access control list. Linux: readable while the keyring is unlocked
|Readable; deny rules are defence in depth only

|Secret in the model's context
|Never: the operator enters secrets
|Never: the operator edits the file

|At rest
|Encrypted by the store
|Plain file, protected by file modes only
|===
