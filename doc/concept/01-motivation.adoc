== Current architecture in one paragraph

plan-marshall ships as a marketplace of bundles containing skills (Markdown instructions) and Python scripts. The host loads skills from the filesystem into model context. The skills instruct the model to run scripts through a generated executor (`python3 .plan/execute-script.py {bundle}:{skill}:{script} …`) via the host's Bash tool. Plan state lives in a git-ignored `.plan/local/` tree; orchestrator state in git-tracked ledgers. A multi-target generator translates the corpus for other runtimes (OpenCode, Antigravity), and a distribution chain publishes generated trees to dist branches from which hosts install them.

== Cost of the current architecture

=== Process rules are enforced by prose

The workflow (phases, finalize steps, gates, which arguments to pass, which actions are operator-only) is described in Markdown and executed by the model. Rules such as "execute only the documented commands", "never invent arguments", "never `--force` the freshness gate" or "one command per Bash call" exist because the model regularly breaks them. Every rule that must be followed is a rule that can be forgotten, misread, or lost to a context compaction.

=== The model assembles every call

Each script call is composed by the model from prose: the plan id, the worktree path, the step name, flags. Wrong or stale arguments are a recurring defect class, and resuming after `/clear` or a compaction requires reconstructing state from documents.

=== Resident context dominates cost

Measured cost is dominated by context re-read across turns, not by generation. Whole phase workflow documents sit in context although only the current step matters. Bash output and TOON parsing add further volume.

=== Bash is the execution channel

Every operation travels through the host's Bash tool. That drags in shell hygiene rules, a PreToolUse hook family to enforce them, permission allowlists and permission tooling — all of which exist only because Bash is the transport.

=== Skills and scripts can drift apart

Skill text and the scripts it names are distributed together but loaded through different mechanisms (plugin cache versus generated executor). A stale cache, a registry pin left behind, or an executor not regenerated produces a model reading one version of the instructions while executing another.

=== Distribution is a multi-stage chain

Source bundles → generator → `target/{runtime}/` → dist branch or tag → host marketplace install → plugin cache → executor regeneration → host restart. Each stage has its own failure modes and recovery documentation.

=== Language servers start cold

The LSP client spawns a language server per call and tears it down afterwards. Cold start is paid on every call, in every sub-agent.

=== Multi-runtime support is translation

Each additional runtime needs a generator target translating skill vocabulary and conventions. Only Claude Code is tested as a runtime, so calibration differences surface invisibly.

== What moving into a server changes

[cols="2,3"]
|===
|Problem |Server-side answer

|Rules enforced by prose
|The state machine lives in code; forbidden transitions are not offered and are rejected.

|Model assembles calls
|The server returns pre-fabricated calls with all bound parameters filled in (xref:03-hypermedia-workflow.adoc[Hypermedia Workflow]).

|Resident context
|Only the current state's representation and guidance enter context.

|Bash as transport
|Every operation is an MCP tool call; Bash hygiene becomes irrelevant to plan-marshall operations.

|Skill/script drift
|Skills and implementation are served by the same process and cannot diverge.

|Distribution chain
|One set of versioned artifacts and one host configuration entry (xref:11-distribution.adoc[Distribution]).

|Cold LSP
|Language servers are held warm and shared (xref:06-services.adoc[Services]).

|Runtime translation
|Every target runtime speaks MCP; the interaction model is identical across runtimes.
|===

== What does not move

Judgment stays with the model: refining a request, writing a solution outline, implementing, triaging findings, writing commit and PR text. The target design narrows the model's work to exactly these activities and makes them explicit as the free parameters of links.
