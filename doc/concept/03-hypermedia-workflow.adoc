== Idea

The workflow is a hypermedia application in the HATEOAS sense. The client asks for the state of a plan or epic; the server answers with a *representation* of that state and the *links* — pre-fabricated tool calls — that are valid from it. The model advances the workflow by following links. It never needs to know the state machine, never assembles a call from prose, and never sees a transition that is not allowed.

[cols="1,1"]
|===
|REST / HATEOAS |PM-MCP

|Resource
|A plan (`plan_id`) or an orchestrator epic (`epic_id`)

|Representation
|Result of `pm.state` or of any transition call

|Link / form
|Pre-fabricated tool call with bound and free parameters

|Link relation (`rel`)
|The meaning of a link (`next`, `retry`, `escalate`, …)

|Media type documentation
|Vocabulary skills (xref:04-skill-model.adoc[Skill Model])

|Conditional request (`ETag` / `If-Match`)
|`state_token`
|===

== Representation

A representation is returned as a tool result in TOON. It contains everything the model needs for the current state and nothing else.

[source,toon]
----
scope: plan
plan_id: PLAN-X
state: finalize.push-barrier
state_token: 7f3a91c2
summary: tasks 11/11 done, freshness gate green, branch not pushed
guidance: skill://pm/finalize/push-barrier/SKILL.md
facts:
  branch: feature/PLAN-X
  commits_ahead: 4
  gate.freshness: green
links[3]{rel,tool,bound,free}:
  next,pm.push,"plan_id=PLAN-X;token=7f3a91c2",""
  amend,pm.commit,"plan_id=PLAN-X;token=7f3a91c2","message"
  escalate,pm.ask_operator,"plan_id=PLAN-X;token=7f3a91c2","reason"
----

=== Fields

`scope`, `plan_id` / `epic_id`::
What the representation describes.

`state`::
A dotted, closed-enum state name. Phase and step are both part of the name, so the state alone determines which links can exist.

`state_token`::
Opaque version of the state. Changes on every transition. Carried by every link (see <<state-token>>).

`summary`::
One line of human-readable status, for the model and for terminal display.

`guidance`::
URI of the vocabulary skill that explains how to act in this state. Omitted when the state needs no judgment.

`facts`::
The state data the model needs to exercise judgment in this state — never more. Larger data is referenced as a resource URI, not inlined.

`links`::
The valid transitions. Empty only in terminal states.

== Links

A link is a complete tool call description:

`rel`::
The relation, from a closed vocabulary (<<relations>>).

`tool`::
The MCP tool to call.

`bound`::
Parameters the server has already filled in. The model passes them unchanged.

`free`::
Parameters the model must supply. These are exactly the places where judgment is required. Each free parameter has a name and a type; the guidance skill describes what a good value looks like.

A link is a *form*, not only a pointer: the bound part removes argument-invention defects, the free part makes the model's contribution explicit and small.

=== Relations

[[relations]]
The relation vocabulary is closed and documented once, in a vocabulary skill:

[cols="1,3"]
|===
|rel |Meaning

|`next`
|The default forward transition.

|`alt`
|An alternative forward transition (e.g. a light versus a deep outline lane).

|`retry`
|Repeat the last operation after a transient failure.

|`fix`
|Enter a remediation sub-state (e.g. a failed build, a quality-gate finding).

|`submit`
|Hand judgment output to the server (an outline, a triage decision, a task result).

|`dispatch`
|Start a sub-agent; the link carries a ready-to-use prompt (<<dispatch>>).

|`wait`
|Poll or monitor a long-running operation (<<long-running>>).

|`escalate`
|Ask the operator; the workflow blocks until answered.

|`abort`
|Leave the workflow in a defined state.
|===

=== Omission is enforcement

Links the model must not use are not emitted. Operator-only transitions — forcing a gate, overriding a merge barrier, deleting a plan — never appear as links to the model. They are available only through an operator channel (a user-invoked prompt or command, or an explicit `escalate` answer).

Omission is the primary mechanism; the server additionally rejects any call that is not a valid transition (<<validation>>).

== State token

[[state-token]]
Every representation carries a `state_token`; every link binds it. A transition call succeeds only if the token matches the current state. Otherwise the server rejects the call and returns the current representation.

Token check, transition and persistence form one atomic compare-and-set per plan or epic: the engine validates the token, applies the transition and writes the new state and token as a single step under that plan's or epic's lock. Of two calls carrying the same token, exactly one succeeds; the other receives the new representation.

This protects against:

* stale links replayed after a context compaction or `/clear`;
* two sub-agents acting on the same state concurrently;
* a model following a link from a representation it received several turns earlier.

The rejection is not an error the model must interpret: it contains the fresh representation, so the model simply continues from it.

== Validation

[[validation]]
Links guide; they do not secure. Every tool call is validated by the workflow engine independently of whether it came from a link:

* the target transition exists from the current state;
* the `state_token` matches;
* bound parameters equal the values the server would bind;
* free parameters satisfy their schema.

A call that bypasses the links is treated exactly like a call through them.

== Explicit outcomes

States and results are closed enumerations, never booleans. Distinct outcomes stay distinct:

* `merged`, `queued`, `ejected`, `not_run` — not a single `success`;
* `reviewed_clean`, `not_reviewed`, `review_pending` — not "no findings";
* `green`, `red`, `stale`, `not_evaluated` for a gate.

A signal that hides a caveat cannot be expressed in the representation format.

== Sub-agent dispatch

[[dispatch]]
A `dispatch` link carries the complete prompt for a sub-agent, including scope identifiers and the entry tool call:

[source,toon]
----
links[1]{rel,tool,bound,free}:
  dispatch,host.agent,"level=3;prompt_ref=pm://plans/PLAN-X/dispatch/task-4",""
----

The prompt is a resource the server renders for the session's client — its sub-agent mechanism, model map and tool names (xref:15-client-profiles.adoc[Client Profiles]). The sub-agent's first action is the tool call named in it, which returns the sub-agent's own representation. The orchestrating model never assembles dispatch prompts.

== Long-running operations

[[long-running]]
Builds, CI waits, review-bot windows and merge queues outlast a tool call. Such a transition returns immediately with a representation in a `*.running` state and a `wait` link:

[source,toon]
----
state: execute.verify.running
summary: build job b-2291 running (module-tests), 00:03:12 elapsed
links[2]{rel,tool,bound,free}:
  wait,pm.wait,"plan_id=PLAN-X;job=b-2291;token=c01d",""
  abort,pm.cancel,"plan_id=PLAN-X;job=b-2291;token=c01d",""
----

`pm.wait` blocks up to a bounded time and returns either the final representation or the same `running` representation with updated progress. Hosts that support progress notifications receive them in addition; nothing depends on it.

== Resumption

Resuming any plan or epic, after `/clear`, a compaction, a host restart or a new cloud VM, is one call: `pm.state(plan_id)`. The resume anchor is server state. Nothing has to be re-derived from documents or memory.

== Epic orchestration

The same model applies to orchestrator epics. `pm.state(epic_id)` returns the epic's representation: staged plans, running plans, pending inbox messages, and links such as `dispatch` (start a staged plan), `submit` (record a landing analysis) or `escalate`. Cross-reading live plan state, which the orchestrator ledger today must do by hand, is part of computing the representation.

== Dynamic paths

Not every path needs hypermedia. Two kinds of paths exist:

Engine-driven paths::
Phase progression, finalize steps, gates, merge and landing. Fully described by the state machine; every step is a link.

Judgment-driven paths::
Outline authoring, implementation inside a task, triage. The representation hands the model guidance and facts plus a single `submit` link; what happens between receiving the state and submitting is the model's work.
