= Hypermedia Workflow
:toc: left
:toclevels: 3
:nofooter:

xref:README.adoc[Concept] » Hypermedia Workflow

== Idea

The workflow is a hypermedia application in the HATEOAS sense. The client asks for the state of a plan or epic; the server answers with a *representation* of that state and the *links* — the transitions valid from it, each identified by a link id — that the model can follow. The model advances the workflow by following links. It never needs to know the state machine, never assembles a call from prose, and never sees a transition that is not allowed.

[cols="1,1"]
|===
|REST / HATEOAS |PM-MCP

|Resource
|A plan (`plan_id`) or an orchestrator epic (`epic_id`)

|Representation
|Result of `pm_state` or of any transition call

|Link / form
|Link id plus the free parameters the model supplies

|Link relation (`rel`)
|The meaning of a link (`next`, `retry`, `escalate`, …)

|Media type documentation
|Vocabulary skills (xref:04-skill-model.adoc[Skill Model])
|===

== Representation

A representation is returned as a tool result in TOON. It contains everything the model needs for the current state and nothing else.

[source,toon]
----
scope: plan
plan_id: PLAN-X
state: finalize.push-barrier
summary: tasks 11/11 done, freshness gate green, branch not pushed
guidance: skill://pm/finalize/push-barrier/SKILL.md
facts:
  branch: feature/PLAN-X
  commits_ahead: 4
  gate.freshness: green
links[3]{rel,link,free}:
  next,push,""
  alt,commit,"message:text"
  escalate,escalate,"reason:text"
----

=== Fields

`scope`, `plan_id` / `epic_id`::
What the representation describes.

`state`::
A dotted, closed-enum state name. Phase and step are both part of the name, so the state alone determines which links can exist.

`summary`::
One line of human-readable status, for the model and for terminal display.

`guidance`::
URI of the vocabulary skill that explains how to act in this state. Omitted when the state needs no judgment.

`facts`::
The state data the model needs to exercise judgment in this state — never more. Larger data is referenced as a resource URI, not inlined.

`links`::
The valid transitions. Empty only in terminal states.

== Links

A link is a transition the model can follow:

`rel`::
The relation, from a closed vocabulary (<<relations>>).

`link`::
The link id: the transition, followed by the addressed entity where the transition acts on part of the plan or epic — `push`, `triage:F-12`, `wait:b-2291`. The id is derived from the persisted state; the server stores no link.

`free`::
Parameters the model must supply, each with a name and a type. These are exactly the places where judgment is required; the guidance skill describes what a good value looks like.

Every link is followed with one call:

[source,text]
----
pm_do(plan_id | epic_id, link, args)
----

The model copies the scope and the link id and supplies the free parameters as `args`. Everything else — worktree, branch, build command, upstream tool arguments — the server resolves from the link id and the persisted state. The only exception is `dispatch`, which the model executes with the host's sub-agent mechanism (<<dispatch>>).

A link is a *form*, not only a pointer: the link id removes argument-invention defects, the free part makes the model's contribution explicit and small.

=== Relations

[[relations]]
The relation vocabulary is closed and documented once, in a vocabulary skill:

[cols="1,3"]
|===
|rel |Meaning

|`next`
|The default forward transition.

|`alt`
|An alternative forward transition (e.g. a light versus a deep outline lane).

|`retry`
|Repeat the last operation after a transient failure.

|`fix`
|Enter a remediation sub-state (e.g. a failed build, a quality-gate finding).

|`submit`
|Hand judgment output or sub-agent return report to the server (an outline, a triage decision, a task result, dispatch return).

|`dispatch`
|Start a sub-agent; the link comes with the rendered host call (<<dispatch>>).

|`wait`
|Poll or monitor a long-running operation (<<long-running>>).

|`escalate`
|Request an operator decision through the operator channel; the workflow blocks until it is answered (xref:09-security.adoc#operator-channel[Operator channel]).

|`abort`
|Leave the workflow in a defined state.
|===

=== Omission is enforcement

Links the model must not use are not emitted. Operator-only transitions — forcing a gate, overriding a merge barrier, deleting a plan — never appear as links to the model. They are taken only through the operator channel — MCP elicitation or the operator CLI (xref:09-security.adoc#operator-channel[Operator channel]).

Omission is the primary mechanism; the server additionally rejects any call that is not a valid transition (<<validation>>).

== Concurrency and repeated calls

[[concurrency]]
The scope of a call is its logical context only: `plan_id` or `epic_id`, and the entity a transition acts on (a task, a finding); the client comes from the scope's entry record. Every call is evaluated against the persisted state of its scope at the moment it arrives.

Three rules make this safe:

Serialised writes::
Validation, transition and persistence form one step under the plan's or epic's lock. Of two concurrent calls, the second is evaluated against the state the first left behind.

Entity addressing::
A transition that acts on part of a plan names the entity in its link id and is validated against that entity's current state: a triage decision for a finding that is no longer open is rejected. Sub-agents working on different tasks of the same plan do not interfere with each other.

Idempotent side effects::
Operations with external effects check the target state before acting and report what they found: pushing an already pushed branch returns `already_pushed`; requesting a build for a working-tree state and scope that is already running joins that job instead of starting another.

These rules cover stale links replayed after a context compaction or `/clear`, sub-agents acting concurrently, and links followed from a representation received several turns earlier. A rejected call is not an error the model must interpret: it contains the current representation, so the model continues from it.

== Validation

[[validation]]
Links guide; they do not secure. Every tool call is validated by the workflow engine independently of whether it came from a link:

* the link id is one of the links of the current state — the transition exists and the addressed entity accepts it;
* free parameters satisfy their schema.

A call that bypasses the links is treated exactly like a call through them.

== Explicit outcomes

States and results are closed enumerations, never booleans. Distinct outcomes stay distinct:

* `merged`, `queued`, `ejected`, `not_run` — not a single `success`;
* `reviewed_clean`, `not_reviewed`, `review_pending` — not "no findings";
* `green`, `red`, `stale`, `not_evaluated` for a gate.

A signal that hides a caveat cannot be expressed in the representation format.

== Sub-agent dispatch

[[dispatch]]
Sub-agents follow plan-marshall's execution-context structure: a generic dispatcher agent, installed per level so that each variant pins model and effort, receives a short prompt body naming its scope, skills and working directory, and returns a status to the dispatching session.

A `dispatch` link comes with the rendered host call. The model passes `host_tool`, `params` and `prompt` unchanged:

[source,toon]
----
links[1]{rel,link,free}:
  dispatch,dispatch:envelope-2,""
dispatch:
  link: dispatch:envelope-2
  host_tool: Agent
  params:
    subagent_type: plan-marshall:execution-context-level-3
  prompt: |
    name: envelope-2
    dispatch_id: d-0417
    plan_id: PLAN-X
    entity: envelope-2
    skills: [skill://pm/execute/task/SKILL.md, skill://pm/domain/java/core/SKILL.md]
    WORKTREE: .plan/local/worktrees/PLAN-X
    start: pm_state(plan_id="PLAN-X", entity="envelope-2")
----

Prompt body::
+
[cols="1,3"]
|===
|Field |Content

|`name`
|Label for logging and metrics.

|`dispatch_id`
|Identifies this dispatch; the sub-agent's calls carry it.

|`plan_id` / `epic_id`
|The scope the sub-agent works in.

|`entity`
|The entity the sub-agent works on: an envelope of tasks, a finding, a module.

|`skills[]`
|Vocabulary skill URIs to load before starting. `skill://pm/core/SKILL.md` is loaded implicitly and never listed.

|`WORKTREE`
|Repository-relative working directory for the host's file tools; `.` for the main checkout.

|`caller_phase`
|Optional; set when the same work is dispatched from more than one phase.

|`start`
|The sub-agent's first call. The work itself is not in the prompt: `pm_state(plan_id, entity)` returns the sub-agent's representation with guidance, facts and links.
|===

Envelopes::
Tasks are not dispatched one by one. At plan time the engine packs the tasks of a plan into envelopes sized for one sub-agent context; the sub-agent's representation serves the envelope's current task, and each task `submit` returns the next one until the envelope is done. This keeps one context per envelope, as plan-marshall does.

Rendering::
The client profile recorded with the plan or epic resolves the level to the host's agent variant and model, and renders the host tool, its parameters and the skill load mechanism (xref:15-client-profiles.adoc[Client Profiles]). The orchestrating model never assembles dispatch prompts.

Leaf::
A sub-agent is a leaf. Representations in an entity scope never contain `dispatch` links; every dispatch originates from the session that works in the plan or epic scope. Operator decisions a sub-agent needs go through `escalate` and the operator channel (xref:09-security.adoc#operator-channel[Operator channel]).

Return::
A sub-agent persists its results through its own `submit` links, not through its answer. It returns `status` (`success`, `error`, `loop_back`, `blocked`) and `display_detail` (at most 80 ASCII characters, no trailing period). The dispatching session then continues from its current representation.

Tracking::
The server renders a dispatch but never sees the host run it. It therefore tracks every dispatch by its `dispatch_id`:
+
* The sub-agent's first call in the entity scope claims the dispatch.
* The dispatching session reports the host's return through a `submit` link with id `returned:<dispatch_id>`: free parameters `status` (closed enum: `success`, `error`, `loop_back`, `blocked`), `display_detail` (at most 80 ASCII characters, no trailing period), and optional `token_usage`. Missing usage is recorded as unmeasured, never as zero.
* A dispatch that was never claimed, or was claimed but has neither returned nor submitted anything within a bound, is shown as `unconfirmed` in the dispatching session's representation, with a `dispatch` link that dispatches the same entity again — after a host timeout, a cancelled sub-agent or a crashed session.
* A new dispatch supersedes the old `dispatch_id`. Submits under a superseded id are rejected, so a sub-agent presumed lost that is still running cannot write a second result.

Hosts whose sub-agents cannot reach MCP servers::
The client profile marks dispatch as unavailable. Representations then offer the work to the dispatching session itself instead of a `dispatch` link.

Reader agents::
A dedicated sub-agent pattern for ingesting untrusted external content (PR review comments, Sonar issues, web pages). By security design, reader agents are equipped with NO MCP tools (strictly read-only). They return candidate extracts in their text response to the dispatching session. The dispatching session submits this candidate data to the server via a validation link, where a deterministic server-side validator verifies the schema before persisting findings. Reader agents never receive direct write access or PM-MCP transition tools (xref:09-security.adoc#_untrusted_content[Untrusted content]).

== Long-running operations

[[long-running]]
Builds, CI waits, review-bot windows and merge queues outlast a tool call. Such a transition returns immediately with a representation in a `*.running` state and a `wait` link:

[source,toon]
----
state: execute.verify.running
summary: build job b-2291 running (module-tests), 00:03:12 elapsed
links[2]{rel,link,free}:
  wait,wait:b-2291,""
  abort,cancel:b-2291,""
----

Following the `wait` link blocks up to a bounded time and returns either the final representation or the same `running` representation with updated progress. When the host's client profile states that progress notifications keep a call alive and the call carries a progress token, the same link blocks longer and sends progress; otherwise it is the bounded wait (xref:16-implementation.adoc#_waiting_primitives[Waiting primitives]).

Composite waits::
When multiple operations run concurrently — notably the finalize wait region running CI verification and automated review bots in parallel — the engine represents them as a single composite state (e.g. `finalize.concurrent-wait`). The representation displays progress facts for all active jobs (`ci: running`, `review: pending`) and offers a single composite wait link `wait:finalize.concurrent-wait`. If a hard CI failure occurs, the engine immediately short-circuits: the pending review wait is cancelled, and the representation moves directly to a failure state with `fix` and `loop_back` links.

== Resumption

Resuming any plan or epic, after `/clear`, a compaction, a host restart or a daemon restart, is one call: `pm_state(plan_id)`. The resume anchor is server state. Nothing has to be re-derived from documents or memory.

== Loop-back transitions

[[loop-back]]
When finalize triage, CI verification or quality gates determine that code fixes are required, a `loop_back` transition returns the plan to Phase 5 (`execute`):

* *Worktree bound*: Loop-back is strictly only possible while the plan is active in its worktree. Once the plan passes the merge barrier and moves back to the main checkout (during branch cleanup), loop-back transitions are eliminated by link omission.
* *Fresh remediation tasks*: Each loop-back allocates new fix tasks and envelopes in the worktree rather than reopening completed tasks. Sub-agents receive fresh task and dispatch IDs, so metrics accumulate additively without collision or duplicate counts.
* *Iteration ceiling*: Automated loop-backs are capped by the project configuration (`.plan/marshal.json -> phase-6-finalize.max_iterations`, default: 3). If iterations reach this ceiling, the engine transitions to `finalize.loop-limit-reached` and offers only an `escalate` link for operator approval.

== Epic orchestration

The same model applies to orchestrator epics. `pm_state(epic_id)` returns the epic's representation: staged plans, running plans, pending inbox messages, and links such as `emit` (start a staged plan), `submit` (record a landing analysis) or `escalate`. A plan is never dispatched as a sub-agent — it dispatches sub-agents itself, and sub-agents are leaves. `emit` records the plan as launched and returns the entry command the operator runs in a session of their choice; the plan counts as running once its entry record appears (xref:15-client-profiles.adoc#_persistence[Persistence]). Cross-reading live plan state, which the orchestrator ledger today must do by hand, is part of computing the representation.

== Dynamic paths

Not every path needs hypermedia. Two kinds of paths exist:

Engine-driven paths::
Phase progression, finalize steps, gates, merge and landing. Fully described by the state machine; every step is a link.

Judgment-driven paths::
Outline authoring, implementation inside a task, triage. The representation hands the model guidance and facts plus a single `submit` link; what happens between receiving the state and submitting is the model's work.
