== From a corpus to a program

plan-marshall today distributes a corpus through a multi-stage chain: generator per runtime, dist branches and tags, marketplace install per host, plugin cache with registry pin, executor regeneration, host restart. Each stage has its own failure modes, and each additional runtime adds a generator target and an install path.

PM-MCP distributes a program:

. Versioned artifacts, released as a unit: the native binary `pm-mcp` and, per client, the entry commands and the execution-context agent variants (xref:10-technology.adoc#_delivery[Delivery]).
. One MCP server entry in the host configuration — user-level, or project-level so that every checkout uses it. The entry contains neither paths nor secrets and can be committed.
. Skills generated per project at runtime (xref:04-skill-model.adoc[Skill Model]).

== Host configuration

The form of the MCP server entry depends on the client (xref:02-architecture.adoc#_mcp_endpoint[MCP endpoint]). Clients that obtain headers dynamically connect directly:

[source,json]
----
{
  "mcpServers": {
    "plan-marshall": {
      "type": "http",
      "url": "http://127.0.0.1:<port>/mcp",
      "headersHelper": "pm-mcp token"
    }
  }
}
----

Clients without dynamic headers:

[source,json]
----
{
  "mcpServers": {
    "plan-marshall": {
      "command": "pm-mcp",
      "args": ["serve", "--stdio"]
    }
  }
}
----

== Updates

* The operator upgrades `pm-mcp` through the package manager or `pm-mcp operator upgrade`, which verifies the release's signature and checksum before replacing the binary.
* Updating the binary updates skills, tools, client profiles and services together. There is no second copy that can lag behind.
* The next connection finds a newer binary than the running daemon and has the daemon drain and restart; hosts reconnect (xref:02-architecture.adoc#_updates[Updates]).
* Hosts see changed skill digests and refresh their skill registry; no host restart is required for new skill content.
* Per-client artefacts — entry commands and execution-context agent variants — are installed with `pm-mcp operator install-client <client>`. `pm-mcp enter` checks their version and reports stale ones.

== Multiple runtimes

Every client (Claude Code, OpenCode, Antigravity, and others) connects to the same server, also when several clients run on one machine. Per client, only the entry points — thin commands in the client's command format that call `pm-mcp enter` — and the execution-context agent variants per level are installed. There is no per-runtime generator target for the corpus:

* skills, representations and links are translated on the fly through the client's profile (xref:15-client-profiles.adoc[Client Profiles]);
* skills are delivered through tools everywhere and through the MCP Skills extension where supported;
* the workflow and PM-MCP's own tools are identical across runtimes.

== Domain support

Domain support (Java, Python, frontend, documentation, OCI, requirements) is part of the release, not a separately installed extension:

* *Data:* vocabulary skills, build commands per build system, LSP configurations and triage rules ship with the binary.
* *Code:* log parsers that turn build output into structured results are compiled into the binary.

A project activates the domains it needs through its configuration. Execution uses the host: wrappers, toolchains and language servers are the developer's own installations.
