== Decisions

. Every request PM-MCP handles is associated with a *client identity* — the agent runtime, for example `claude`, `opencode` or `antigravity`. It is as essential as the plan or epic scope.
. Several clients run on the same machine against the same PM-MCP. The identity is therefore declared *per session*, at the entry points into plan-marshall, not per machine or per server configuration.
. The declaration is made by a *minimal entry script* that detects the client from its environment; the model does not determine it.
. After the entry, the identity travels as a *bound parameter* of every link, like `plan_id` and `state_token`.
. Everything PM-MCP renders for the model — skills, representations, links — is translated *on the fly* through a data-driven *client profile*. There is no build-time generation per runtime.

== Why the client identity is needed

plan-marshall's source corpus is written in Claude Code's vocabulary. Other runtimes use different tool names, load mechanisms, command names and models. Today a build-time generator (`marketplace/targets`) emits a translated copy per runtime. The translation covers:

[cols="1,3"]
|===
|Dimension |Example

|Tool names
|`Read` becomes `view_file` (Antigravity) or `read` (OpenCode); `AskUserQuestion` becomes `ask_question` or `question`.

|Load directives
|`Skill: {bundle}:{skill}` becomes a `view_file` or `skill` tool call.

|Command names
|`/skill-name` becomes a namespaced command id.

|Tool idioms
|Runtime-specific idioms rewritten, preserved or reworded per registered disposition.

|Models and effort
|Abstract levels mapped to runtime-specific model ids and effort settings.

|Frontmatter and agents
|Frontmatter transformed and validated per runtime; agent variants emitted per level.

|Component scope
|Components declaring `targets:` exist only on the named runtimes.
|===

In PM-MCP the same translation happens per request, which requires knowing the client.

== How the identity is established

=== Entry points

A session enters plan-marshall through one of its user-invoked entry points:

* the configuration wizard (today `/marshall-steward`);
* plan lifecycle (today `/plan-marshall:plan-marshall`);
* epic orchestration (today `/plan-marshall:plan-orchestrator`).

These entry points are the only client-specific artefacts installed per client. Each is a thin command in the client's own command format whose single action is to run the entry script and pass its result to PM-MCP's entry tool (`pm.enter`).

=== Entry script

A minimal, dependency-free script that reports the session's client identity and, where available, a client session id. It detects the client from the environment the client sets for its processes. For Claude Code these are, for example:

* `AI_AGENT` — for example `claude-code_2-1-280_agent`;
* `CLAUDECODE=1`;
* `CLAUDE_CODE_SESSION_ID` — the client's own session id.

The detection rules per client are part of the client profiles. A client whose environment is not recognised is reported as `unknown`; the entry command may also pass the identity explicitly, since each entry command is installed for one client.

=== Binding

`pm.enter(client, client_session, entry, …)` returns the first representation. From then on, every link carries `client` — and the client session id where known — as bound parameters, exactly like `plan_id` and `state_token` (xref:03-hypermedia-workflow.adoc#_links[Links]). The model passes them unchanged and never decides them.

This works without protocol-level sessions: protocol `2026-07-28` is stateless, and the identity is part of each call's arguments. PM-MCP also records the identity with the plan or epic run it drives, so a resumed run (`pm.state`) offers links for the client that resumes it — which may differ from the client that started it.

=== Cross-check

MCP carries the client's self-reported name and version — in the initialisation handshake for stateful clients and in the per-request metadata of protocol `2026-07-28`. PM-MCP compares it with the declared identity. A mismatch is recorded in the audit log and reported to the operator; it does not silently change the profile.

=== Sub-agents

A `dispatch` link carries the client identity into the rendered sub-agent prompt, and the sub-agent's first tool call binds it again. Sub-agents therefore use the same profile as the session that dispatched them.

== Client profiles

A client profile is data, owned by PM-MCP and versioned with it:

* tool-name map;
* load-directive and command-name templates;
* idiom rewrites with their dispositions;
* model and effort map per level;
* sub-agent dispatch mechanism (the host tool and parameters a `dispatch` link resolves to);
* component scope (which skills exist for this client);
* protocol capabilities known for the client (Skills extension support, progress notifications, tool-call timeouts).

The rewrite engine and the per-runtime mapping data of plan-marshall's `marketplace/targets` are carried over as the starting point.

== What is rendered per client

Vocabulary skills::
Generated per project *and* client (xref:04-skill-model.adoc[Skill Model]). Digests are computed per rendered variant, so each client sees a stable, verifiable catalogue.

Representations and links::
Links to PM-MCP's own tools are client-independent apart from the bound `client` parameter. Links that resolve to client capabilities — sub-agent dispatch, operator questions, file access in guidance — are rendered with the client's tool names and parameters (xref:03-hypermedia-workflow.adoc#dispatch[Sub-agent dispatch]).

Dispatch prompts::
Rendered with the client's model map, tool names and load mechanism.

User-invocable entry points::
Exposed under the client's command naming.

== Scope reduction through the target design

The target design removes most of what the translation handles today: vocabulary skills contain no commands, script names or tool-call sequences, because operations arrive as links to PM-MCP tools. What remains client-specific is the host-side surface — sub-agents, questions to the operator, file and search tools used during implementation, models — which keeps the profiles small.

== Unknown clients

A session whose identity is `unknown` or has no profile is served with a *neutral profile*: plain MCP tools only, no host-tool references, no dispatch links. The representation marks the session as running on the neutral profile, so the degradation is visible instead of silent.

== Out of scope

Targets that are not MCP clients — for example PR-Agent instruction packs — are not client profiles. They remain export artefacts produced from the vocabulary skills where still needed.
