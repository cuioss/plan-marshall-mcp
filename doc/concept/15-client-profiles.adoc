= Client Profiles
:toc: left
:toclevels: 2
:nofooter:

xref:README.adoc[Concept] » Client Profiles

== Decisions

. Every request PM-MCP handles is associated with a *client identity* — the agent runtime, for example `claude`, `opencode` or `antigravity`. It is as essential as the plan or epic scope.
. Several clients run on the same machine against the same PM-MCP. The identity is therefore declared at the *entry points* into plan-marshall, not per machine, per server configuration or per connection.
. The declaration is made by `pm-mcp enter`, which detects the client from the environment the client sets for its processes; the model does not determine or relay it.
. The identity is *persisted with the plan or epic* it enters, in that plan's or epic's `mcp/` directory. Every call in that scope reads it from there; links do not carry it. A later entry into the same plan or epic replaces it.
. Everything PM-MCP renders for the model — skills, representations, links — is translated *on the fly* through a data-driven *client profile*. There is no build-time generation per runtime.

== Why the client identity is needed

plan-marshall's source corpus is written in Claude Code's vocabulary. Other runtimes use different tool names, load mechanisms, command names and models. Today a build-time generator (`marketplace/targets`) emits a translated copy per runtime. The translation covers:

[cols="1,3"]
|===
|Dimension |Example

|Tool names
|`Read` becomes `view_file` (Antigravity) or `read` (OpenCode); `AskUserQuestion` becomes `ask_question` or `question`.

|Load directives
|`Skill: {bundle}:{skill}` becomes a `view_file` or `skill` tool call.

|Command names
|`/skill-name` becomes a namespaced command id.

|Tool idioms
|Runtime-specific idioms rewritten, preserved or reworded per registered disposition.

|Models and effort
|Abstract levels mapped to runtime-specific model ids and effort settings.

|Frontmatter and agents
|Frontmatter transformed and validated per runtime; agent variants emitted per level.

|Component scope
|Components declaring `targets:` exist only on the named runtimes.
|===

In PM-MCP the same translation happens per request, which requires knowing the client.

== How the identity is established

=== Entry points

A session enters plan-marshall through one of its user-invoked entry points:

* the configuration wizard (today `/marshall-steward`);
* plan lifecycle (today `/plan-marshall:plan-marshall`);
* epic orchestration (today `/plan-marshall:plan-orchestrator`).

These entry points and the execution-context agent variants per level (xref:03-hypermedia-workflow.adoc#dispatch[Sub-agent dispatch]) are the only client-specific artefacts installed per client. Each is a thin command in the client's own command format whose single action is one call of `pm-mcp`:

[source,text]
----
pm-mcp enter <entry> [plan_id | epic_id]
----

=== Entry call

`pm-mcp enter` runs in the host's shell and inherits the environment the client sets for its processes. It detects the client identity and, where available, a client session id, takes the working directory, and sends them with the entry and the scope to the daemon, which writes the entry record (<<_persistence>>). It prints only the scope and the first call for the model — `pm_state(plan_id)` for an existing plan or epic, `pm_start(request)` for a new plan. The identity never passes through the model.

For Claude Code the environment contains, for example:

* `AI_AGENT` — for example `claude-code_2-1-280_agent`;
* `CLAUDECODE=1`;
* `CLAUDE_CODE_SESSION_ID` — the client's own session id.

The detection rules per client are part of the client profiles. A client whose environment is not recognised is reported as `unknown`; the entry command may also pass the identity explicitly (`--client`), since each entry command is installed for one client.

=== Persistence

The daemon writes the entry record on every `pm-mcp enter`. The record lives in the `mcp/` sub-directory of the plan's or epic's directory in the `.plan/` tree:

[source,json]
----
{
  "client": "claude",
  "client_version": "2.1.280",
  "client_session": "c7e1…",
  "entry": "plan",
  "workspace_root": "/Users/oliver/git/TokenSheriff",
  "entered_at": "2026-09-24T10:12:03Z"
}
----

* Every call scoped to the plan or epic renders skills, representations and links for the recorded client. The model never passes the identity.
* An entry without a plan or epic id writes the record at project level in the same form; `pm_start` creates the plan and moves the record into it. The configuration wizard keeps its record at project level.
* Entering an existing plan or epic again, from the same or another client, replaces the record. The last entry determines the profile; each replacement is recorded in the audit log.
* A plan or epic is driven by one client at a time. Entering it from another client hands it over: from then on every scoped call, including those of sessions of the previous client, is rendered for the new client. A call whose self-reported client differs from the record is flagged in its representation, so a session that lost the plan sees it instead of acting on a foreign profile (<<_cross_check>>).
* The `mcp/` directory is local to the machine and never tracked by git, also inside the git-tracked epic directories.

This needs no protocol-level session: protocol `2026-07-28` is stateless, and every call is answered from the persisted record. `pm_state(plan_id)` after `/clear` or a compaction renders for the recorded client without re-entry.

=== Cross-check

MCP carries the client's self-reported name and version — in the initialisation handshake for stateful clients and, optionally, in the per-request `clientInfo` metadata of protocol `2026-07-28`. Where it is present, PM-MCP compares it with the recorded identity; a mismatch is recorded in the audit log, reported to the operator and flagged in the representation, and it does not silently change the profile or the record. Where it is absent, the call is served on the recorded identity and the audit record notes `client_info: absent`.

=== Sub-agents

Sub-agents work in the scope of the plan or epic that dispatched them and therefore read the same entry record. They use the same profile as the dispatching session without passing an identity.

== Client profiles

A client profile is data, owned by PM-MCP and versioned with it:

* tool-name map;
* load-directive and command-name templates;
* idiom rewrites with their dispositions;
* model and effort map per level;
* sub-agent dispatch mechanism: the host tool, the execution-context agent variant and model per level, and the parameters a `dispatch` link resolves to, or the marker that the host's sub-agents cannot reach MCP servers;
* component scope (which skills exist for this client);
* connection: direct Streamable HTTP with a header helper, or `pm-mcp serve --stdio` for clients that cannot obtain headers dynamically (xref:02-architecture.adoc#_mcp_endpoint[MCP endpoint]);
* protocol capabilities known for the client (Skills extension support, progress notifications, tool-call timeouts, elicitation);
* tool schema loading — resident or on demand — and, for on-demand hosts, the tools the entry command preloads (`pm_start`, `pm_state`, `pm_do`).

The rewrite engine and the per-runtime mapping data of plan-marshall's `marketplace/targets` are carried over as the starting point.

== What is rendered per client

Vocabulary skills::
Generated per project *and* client (xref:04-skill-model.adoc[Skill Model]). Digests are computed per rendered variant, so each client sees a stable, verifiable catalogue.

Representations and links::
Links to PM-MCP's own tools are client-independent. Links that resolve to client capabilities — sub-agent dispatch, questions to the user, file access in guidance — are rendered with the client's tool names and parameters (xref:03-hypermedia-workflow.adoc#dispatch[Sub-agent dispatch]).

Dispatch prompts::
Rendered with the client's model map, tool names and load mechanism.

User-invocable entry points::
Exposed under the client's command naming.

== Scope reduction through the target design

The target design removes most of what the translation handles today: vocabulary skills contain no commands, script names or tool-call sequences, because operations arrive as links to PM-MCP tools. What remains client-specific is the host-side surface — sub-agents, questions to the user, file and search tools used during implementation, models — which keeps the profiles small.

== Unknown clients

A session whose identity is `unknown` or has no profile is served with a *neutral profile*: plain MCP tools only, no host-tool references, no dispatch links. The representation marks the session as running on the neutral profile, so the degradation is visible instead of silent.

== Out of scope

Targets that are not MCP clients — for example PR-Agent instruction packs — are not client profiles. They remain export artefacts produced from the vocabulary skills where still needed.
