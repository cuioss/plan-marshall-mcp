== Open decisions

Placement of legacy scripts during migration::
Not-yet-ported plan-marshall scripts run either inside an interim PM-MCP image with CPython, `git` and `gh` (no host prerequisite, target image reached only at the end of migration) or through the host build server (distroless image from the start, host build server required on every machine, job contract extended by a script job type, latency of frequent short calls over the outbound channel). See xref:10-technology.adoc#_target_image[Target image].

Language-server placement::
Where warm language servers run: in PM-MCP's environment (toolchains in the PM-MCP image), in per-project containers, or on the host through the host build server. Options in xref:discussions/execution-alternatives.adoc#_language_servers[Execution Alternatives].

Named verbs versus one transition tool::
`pm.do` keeps the schema surface constant; named verbs are more self-describing and may be followed more reliably by some models. Needs measurement across runtimes.

Representation format::
TOON for compactness versus JSON with an MCP output schema for host-side validation. Possibly both: structured content with a TOON text rendering.

State file formats::
State is persisted in the filesystem (xref:02-architecture.adoc#_state_persistence[State persistence]); whether the formats stay those of plan-marshall's `.plan/` tree beyond migration, and how concurrent writers are serialised when several daemons or hosts touch the same project, is open.

Cloud sessions::
A cloud session can use PM-MCP only if the project's MCP configuration can start it from a fresh clone. Whether the cloud lane becomes a PM-MCP client or stays a separate lane is open.

Roots and elicitation support::
Which clients provide MCP roots and support elicitation — the preferred channel for approving access to other projects (xref:09-security.adoc#_workspace_confinement[Workspace confinement]).

Client detection::
The environment variables OpenCode and Antigravity set for their processes, and their self-reported names in MCP's client information, are to be verified; Claude Code sets `AI_AGENT`, `CLAUDECODE` and `CLAUDE_CODE_SESSION_ID`.

Entry point delivery::
Whether the entry points are installed as client commands or served as MCP prompts, which some clients expose as commands.

Model identity::
MCP does not tell the server which model a session runs. Whether calibration beyond vocabulary — per model rather than per client — is needed, and how the model would be identified, is open.

Build backend details::
* Enrolment file format and location, shared by both backends.
* Protocol of the host build server's outbound connection.
* Migration of `marshalld`: in-place evolution versus a new implementation as a Java native binary.
* Build runtime images: upstream images versus cuioss-owned images.
* Network policy granularity of the container backend beyond on or off.
* Windows hosts.

Third build backend::
Whether a microVM backend with a private runtime per build (Docker Sandboxes) is added. Candidate and verification points in xref:discussions/execution-alternatives.adoc#_candidate_microvm_backend_docker_sandboxes[Execution Alternatives].

== Verifications pending

. Container backend performance with Docker Desktop and `podman machine` on macOS, and for a full plan-marshall `verify` (OrbStack results in xref:discussions/container-build-measurements.adoc[Container Build Measurements]).
. Container-using builds end to end: TokenSheriff's integration tests (native container build, image build, Compose stack, published ports) with `containers: siblings` on OrbStack, Docker Desktop and rootless Podman.
. Rootless Podman on Linux end to end: ownership (`--userns=keep-id`), SELinux labelling, caches, Testcontainers.
. The Java container-runtime client, LSP4J and the git library under Quarkus native image — a precondition for the native daemon and the distroless target image.
. Short, frequent builds during task execution, to decide whether warm builder containers are needed.

== Risks

Framework maturity::
The Quarkus MCP Server is a Quarkiverse extension outside the official MCP SDK tiers, maintained by a small group; the extension API needed for the Skills extension is not yet released; Tasks support is a draft. Mitigation: PM-MCP's own job model, tool-based skill delivery, and an upstream contribution of the Skills extension.

Host support varies::
Skills extension support, progress notifications, sub-agent access to MCP servers and tool-call timeouts differ between hosts. Mitigation: plain tools as the baseline, extensions as enhancement.

Models ignoring links::
A model may call tools out of sequence or re-derive arguments. Mitigation: validation of every call independent of links; rejection returns the fresh representation.

Resident schema cost::
A large tool surface can cost more context than it saves. Mitigation: small verb set, aggregation behind `pm.do`, selective upstream proxying.

Judgment quality regression::
Removing whole-phase documents removes context the model may have used implicitly. Mitigation: vocabulary skills per judgment state; measure outline and triage quality in the finalize pilot before extending.

Single point of failure::
A daemon crash stalls all sessions on the machine. Mitigation: job state persisted, front ends reconnect, idempotent transitions keyed by `state_token`.

Proxy trust laundering::
Upstream content presented under PM-MCP's origin. Mitigation: provenance in `_meta`, untrusted marking, no re-serving of upstream skills.

Build isolation depends on the runtime::
Container-using builds are only as isolated as the runtime allows. Mitigation: rootless runtimes required on Linux; projects that cannot meet this use the host backend.

Migration duration::
Two models coexisting prolongs maintenance cost. Mitigation: bounded stages with exit criteria; retire each current-model surface when its stage completes.
