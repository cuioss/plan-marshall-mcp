== Decisions

. Every plan-marshall script is assigned to one of three categories — *ported*, *redesigned*, *retired* — and tested according to its category.
. Ported scripts are replaced only after *differential tests* show that the Java implementation behaves like the Python implementation at the tool boundary.
. Redesigned parts are tested against the state machine specification and through *end-to-end scenarios*, not against the Python behaviour.
. The test environment (CI and local) runs the Python and the Java implementation side by side until the last ported script is replaced.

== Starting point

plan-marshall's logic is not trivial:

* 436 script files with about 248,000 lines; median 356 lines, 65 files above 1,000 lines, the largest about 5,900 lines.
* A test suite of 1,351 test files with about 572,000 lines.
* 283 test files (1,322 calls) test scripts at the CLI boundary through `run_script(...)` in `test/conftest.py`: argument vector in, TOON output and exit code out.
* About 1,050 test files import script internals directly.

Much of the code encodes corrected defects (state resolution, lock staleness, resume anchors, signal truthfulness). A rewrite without a safety net reintroduces them.

The assignment of every script to a category is maintained as a migration inventory; it is part of the first migration stage.

== Differential tests

=== Contract

Every script has the same contract: an argument vector in; TOON on stdout, an exit code, and changes to the plan state out. A differential test executes the same call against both implementations from the same starting state and compares:

* the TOON output, normalised (ordering where irrelevant, timestamps, generated identifiers);
* the exit code;
* the resulting plan-state tree, normalised the same way.

=== Seam

PM-MCP's executor adapter (xref:12-migration.adoc[Migration Path]) is the single entry point for script calls, in tests and in production. It takes a notation (`{bundle}:{skill}:{script}`) and an argument vector and returns TOON and an exit code. Per script it routes to one of three modes:

* `python` — a script job of the daemon;
* `java` — the Java implementation;
* `parallel` — the Java implementation answers, the script job runs as well in a shadow run, and differences are logged.

The shadow run never touches the live plan or the outside world:

* it runs on a copy of the plan-state tree taken before the call, and its resulting tree is compared with the live one the Java implementation produced;
* scripts with external effects (git writes, CI or PR operations) are not eligible for `parallel` mode; their switch-over relies on differential tests against fixture repositories and sandboxed CI stubs.

Tests reach the Java implementation through a running test instance of the daemon, never by starting a JVM per call.

=== Sources of test cases

Existing CLI-level tests::
`run_script()` is the single seam through which the 283 CLI-level test files execute scripts. Made switchable between the Python script and the executor adapter of a test daemon, these tests become contract tests for the Java side without being rewritten.

Recorded invocations::
The executor logs script calls. Invocations recorded from real plan runs are replayed against both implementations, covering argument combinations no handwritten test exercises.

Targeted cases::
Added where the inventory shows gaps, especially for the defect classes named above.

=== Switch-over

A ported script is switched to Java when:

. all differential tests pass;
. its own JUnit tests exist;
. it has run in `parallel` mode on real plans without unexplained differences.

After the switch, its differential tests remain until the Python implementation is deleted.

== Redesigned parts

* *State machine tests*: for every state, the emitted links, the rejected transitions, concurrent and repeated calls, idempotent side effects and the closed-enum outcomes (xref:03-hypermedia-workflow.adoc[Hypermedia Workflow]).
* *End-to-end scenarios*: complete plan runs driven through links only — including resume after context loss, concurrent sub-agents, build failures, refusals and footprint violations — against fixture repositories.
* *Outcome comparison*: for selected real plans, the artefacts at the end (commits, PR state, findings, lessons) are compared with a run under the current plan-marshall, not the individual calls.

== Module tests

The about 1,050 test files that exercise script internals are not carried over. Each Java module gets its own JUnit tests, following the cuioss testing standards.

== Consequence for the test environment

Until migration is complete, CI and local test runs need Python and plan-marshall's scripts next to the Java implementation. In production, not-yet-ported scripts run as script jobs of the daemon (xref:12-migration.adoc[Migration Path]).
