= Implementation Approach
:toc: left
:toclevels: 2
:nofooter:

xref:README.adoc[Concept] » Implementation Approach

== Decisions

. *Libraries only where they are small and native-capable.* The workflow engine and the TOON encoder are PM-MCP's own code; JSON uses the Jackson that Quarkus manages.
. *JSON for machine state, TOON for output.* Persisted machine state is JSON or JSONL with a format version; documents written for people and the model stay Markdown; TOON is produced only when a result is rendered for the model.
. *Project-local development skills* under their own `pm-mcp-` prefix drive a development instance of PM-MCP, separated from the installed plan-marshall commands and from real state.
. *Two waiting primitives*, both links: a bounded `wait` that any host survives, and a `wait` carrying progress notifications where the client profile allows longer calls. MCP Tasks are adopted later.
. *Transition: foundation first, then by category.* The foundation routes every call to the Python scripts; then ported stores switch individually, redesigned workflows switch phase by phase, retired parts are dropped with the surface that replaces them.
. *Workflows are defined in a DSL over Java primitives.* Every operation is a primitive, a Java command with typed parameters and a closed set of outcomes; every workflow is a definition in PM-MCP's own workflow DSL that wires primitives into states and links. The engine interprets the definitions, and the diagrams are generated from them.
. *Plain Java core, Quarkus assembly.* Primitives, engine, DSL and stores live in a plain Java module without Quarkus; the Quarkus module assembles them into the daemon; a packaging module builds the release.

== Libraries

[cols="1,2,3"]
|===
|Need |Choice |Reason

|Workflow engine
|Own code: an interpreter for definitions in the workflow DSL, over primitives with sealed outcome types (<<_workflow_definition>>)
|The small libraries are dormant or archived — stateless4j (last release 2019), squirrel-foundation (2022, pulls Guava and MVEL), easy-states (archived). Enterprise engines (Camunda, Flowable, Temporal, Spring Statemachine) bring their own persistence and runtime, which contradicts filesystem state and derived links (xref:03-hypermedia-workflow.adoc[Hypermedia Workflow]). The build-time validation of the definitions gives the exhaustiveness check a library would.

|Workflow DSL
|Own line-based grammar and parser
|Standard notations do not fit: SCXML and BPMN are heavy XML without the notions of link, free parameter and judgment; Mermaid and PlantUML describe diagrams, not executable guards and outcomes. A YAML schema would need a YAML library as a new dependency. A small grammar of its own parses in a few hundred lines and reports errors with line numbers.

|TOON output
|Own encoder for the subset PM-MCP emits: objects, tabular arrays, inline primitive arrays, quoting and escaping by the specification (v4.1)
|The Java implementation JToon (`dev.toonformat:jtoon`) is maintained and spec-compliant, but brings Jackson 3 next to Quarkus's Jackson 2 and a runtime code generator (Blackbird) that is a risk under native image. An encoder over PM-MCP's own records is small and has no reflection.

|TOON input
|A reader for plan-marshall's TOON dialect, in the test and migration code only
|The model sends arguments as JSON; PM-MCP parses TOON only to compare Python output in differential tests and to convert legacy TOON stores. plan-marshall's parser deviates from the specification (tab rows sniffed instead of declared, JSON in table cells, block scalars, comments), so a spec parser does not read it. The reverse direction does not exist: no Python code reads PM-MCP's TOON. Python callers keep calling the Python version of a script during coexistence, and state shared between both is JSON.

|JSON
|Jackson 2 as managed by Quarkus, with records; persisted types registered for reflection
|Already in the stack; records serialise without mapping code. Types read and written outside REST are not discovered by Quarkus and need `@RegisterForReflection`.
|===

The TOON encoder is verified against the conformance fixtures of the TOON specification, for the subset it emits.

== Storage and output formats

=== Principle

The store is written and read by the server only; the model sees representations and results, rendered as TOON (xref:05-tool-surface.adoc[Tool Surface]). Storage therefore optimises for exact round-trips, schema evolution and tooling; output optimises for tokens.

[cols="1,2"]
|===
|Kind |Format

|State the server reads and writes
|JSON, one document per entity; JSONL for append-only logs (findings, change ledger, audit). Every document carries a format version; the daemon migrates older versions forward on start (xref:02-architecture.adoc#_updates[Updates]).

|Documents written for people and the model
|Markdown, unchanged: request, solution outline, landings, lessons, epic and inbox documents.

|Results and representations
|TOON, rendered from the same records at the tool boundary.
|===

=== plan-marshall's current stores

plan-marshall already stores its core state as JSON — `status.json`, `tasks/TASK-NNN.json`, `references.json`, the orchestrator ledger — and renders it as TOON on output. The stores still written as TOON are auxiliary or derived:

[cols="2,1,2"]
|===
|Store |Category |Target

|`execution.toon` (execution manifest), `handshakes.toon` (phase invariants)
|Redesigned
|Replaced by the workflow engine's JSON state; not converted.

|`work/metrics*.toon`, `work/fragment-*.toon`, `work/retro-fragments.toon`
|Ported
|JSON, converted in plan-marshall before the owning script is ported.

|`work/module_mapping.toon`, `work/deliverable-hashes.toon`, `work/lessons-consult.toon`, `artifacts/ci-runs/{N}/manifest.toon`
|Ported
|JSON, converted in plan-marshall before the owning script is ported.

|`work/ci-precondition-cache.toon`
|Redesigned
|Part of the finalize state; not converted.

|`.plan/local/marshall-state.toon`
|Retired
|Removed with executor generation.
|===

Converting in plan-marshall first keeps one format per store on the shared state tree during coexistence (xref:12-migration.adoc#_coexistence[Coexistence]); the differential tests then compare JSON state trees and TOON output only. Skill instructions that read a `.toon` store directly — the retrospective reads `handshakes.toon` and `work/metrics.toon` — are replaced by `pm_state` and resources.

== Development skills

Development of PM-MCP needs Claude Code sessions that drive the server under development. They are project-local skills in this repository, `.claude/skills/pm-mcp-*`, and never part of what PM-MCP delivers.

[cols="1,3"]
|===
|Skill |Purpose

|`pm-mcp-dev`
|Build and start a development daemon, stop it, show its status and log. Registers it as the MCP server `pm-mcp-dev`, so its tools (`mcp__pm-mcp-dev__pm_state`) never collide with an installed PM-MCP or with plan-marshall's commands.

|`pm-mcp-scenario`
|Run an end-to-end scenario against a fixture project: enter a plan, follow links until a target state, report the path taken and every deviation.

|`pm-mcp-inspect`
|Show the persisted state, entry record and audit log of a development plan.
|===

The development daemon runs with its own home (`PLAN_MARSHALL_HOME` pointing into `.plan/temp/`), its own port and its own OS credential store service name (`plan-marshall-mcp-dev` instead of `plan-marshall-mcp`), so it never touches the operator's plans, enrolment or credentials: a credential missing for development is reported as `not_found`, never resolved from the operator's entries. The skills call the build through the project's canonical commands.

== Waiting primitives

=== Host limits

Long-running work — builds, CI runs, review-bot windows, merge queues — regularly exceeds what one tool call may take. For Claude Code:

* An HTTP MCP call is aborted after *5 minutes without a response or progress notification* (`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`; 30 minutes for stdio). A progress notification resets the idle timer.
* The overall limit per call (`MCP_TOOL_TIMEOUT`) is far above any job; progress does not extend it.
* In the main conversation, a call still running after 2 minutes moves to the background and the model continues; calls of sub-agents are never moved to the background.
* Claude Code does not support MCP Tasks; the Quarkus MCP Server extension does not implement them yet.

Other hosts differ; the limits are part of the client profile (xref:15-client-profiles.adoc#_client_profiles[Client profiles]).

=== Primitives

A job always outlives the call that follows it: it runs in the daemon and its state is persisted (xref:07-build-execution.adoc[Build Execution]). Waiting is therefore only a question of how long one call blocks.

[cols="1,3"]
|===
|Primitive |Behaviour

|Bounded wait
|`wait:<job>` blocks up to a bound below the host's idle timeout — by default 4 minutes — and returns the final representation or the running one with updated progress and a new `wait` link. Works on every host and in sub-agents; costs one turn per bound.

|Progress wait
|The same `wait:<job>` link, on a host whose profile states that progress resets the idle timeout: the call sends a progress notification at least every 60 seconds and blocks until the job ends or a longer bound (default 30 minutes) is reached.

|Cancel
|`cancel:<job>` ends a job; the representation shows the cancelled state.
|===

The model does not choose between the waits. The server uses the progress wait only when both hold — the client profile states that progress resets the idle timeout, and the call carries a progress token; otherwise it uses the bounded wait. There is no separate polling primitive: a `wait` that returns early is the poll. MCP Tasks replace the progress wait once the framework and the hosts support them (xref:10-technology.adoc#_decisions[Technology]).

=== Tests

Both primitives are tested through the link approach, not as tool internals:

* integration tests with a controllable fake job: a bounded wait across several bounds, a progress wait with notifications, cancel during a wait, a daemon restart during a wait followed by resume through `pm_state`;
* a Claude Code scenario (`pm-mcp-scenario`) with a job longer than the idle timeout and the idle timeout lowered, in the main conversation and in a sub-agent.

== Workflow definition

=== Primitives

A primitive is one operation of the server, implemented as a Java command:

* a name (`git.commit`, `ci.watch`, `findings.triage`);
* a parameter record — the free parameters a link may pass and the values the engine resolves from state;
* a closed set of outcomes as a sealed type or enumeration (`ok`, `nothing_to_commit`, `hook_failed`);
* its effects: the stores it writes, whether it starts a job and of which kind.

A primitive knows no state, link or other primitive. It is unit-tested on its own, with plain JUnit and without Quarkus (<<_modules>>).

=== Definitions

A workflow — the plan phases, the finalize step sequence, epic orchestration — is a definition in the DSL, a resource compiled into the binary. An excerpt of finalize:

[source,text]
----
workflow finalize version 1
start commit

state commit
  skill pm/finalize/commit-message
  link next commit (message: text 1..2000)
    do git.commit
      ok                -> push
      nothing_to_commit -> ci
      hook_failed       -> commit.fix

state push
  auto git.push
    ok       -> ci
    rejected -> sync

state ci
  job ci.watch
    success  -> review
    failure  -> ci.fix
    killed   -> ci
----

[cols="1,3"]
|===
|Construct |Meaning

|`state`
|A state; its name is persisted in the plan or epic.

|`link <rel> <id> (<free parameters>)`
|A link offered in the state, with its relation from the closed vocabulary and typed free parameters (xref:03-hypermedia-workflow.adoc#_links[Links]).

|`do <primitive>`
|The primitive run when the link is followed.

|`auto <primitive>`
|A primitive the server runs on entering the state, without a link.

|`job <primitive>`
|A primitive that starts a job; the state offers `wait` and `cancel` (<<_waiting_primitives>>).

|`guard <primitive>`
|A condition; the link is offered only while it holds.

|`dispatch <envelope>`, `escalate <decision>`
|A sub-agent dispatch, an operator decision.

|`skill`
|The vocabulary skill a judgment state names in its representation.

|`<outcome> -> <state>`
|The transition per outcome of the primitive.

|`call <workflow>`
|A reusable sub-workflow, for example the build-and-fix loop that execute and finalize share.
|===

=== Validation

Definitions are checked in the build, by unit tests of the core module; a definition that fails does not ship:

* every primitive exists, and the link's free parameters match its parameter record;
* every outcome of every primitive is handled — the exhaustiveness a `switch` over a sealed type would give;
* every state is reachable from the start, every non-terminal state has a way out, terminal states are declared;
* relations come from the closed vocabulary, link ids are unique per state, every named skill exists;
* state names of released versions are kept or mapped: a renamed or removed state needs a `migrate <old> -> <new>` line, because running plans carry state names across a daemon upgrade (xref:02-architecture.adoc#_updates[Updates]). A committed list of released state names makes this checkable.

The daemon parses the same definitions at start with the same parser, and fails closed if one does not validate (xref:09-security.adoc[Security]).

=== Diagrams

A generator in the build renders every definition as a Mermaid state diagram and as a table of states, links and outcomes, into AsciiDoc under `doc/`. The generated files are committed, and a test fails when they differ from the definitions, so the documented workflow cannot drift from the executed one. The daemon serves the same rendering as a resource, with a plan's current state marked, for operators and for `pm-mcp-inspect`.

== Modules

[cols="1,1,3"]
|===
|Module |Kind |Content

|`pm-mcp-core`
|Plain Java
|Primitives, workflow DSL (parser, validator, diagram generator), engine, stores, TOON encoder, client bundle sources and manifests. Depends on Jackson and cui-java-tools only; no Quarkus, CDI or MCP.

|`pm-mcp-server`
|Quarkus
|The assembly; today's `plan-marshall-mcp` module, renamed so that all modules share the `pm-mcp-` prefix of the binary: MCP tools, daemon lifecycle, HTTP endpoints including the install endpoint, command-line modes, CDI wiring, native-image configuration, `*IT` tests.

|`pm-mcp-dist`
|Packaging
|The release archive per platform: installation layout, control scripts, service templates, SBOM (xref:11-distribution.adoc#_server_installation[Server installation]).
|===

* *Dependency direction.* The server depends on the core, never the reverse. The core defines interfaces for what it needs from the daemon — running a job, taking a plan's lock — and the server implements them.
* *No framework in the core.* The server creates core objects through CDI producers. Records the core persists are registered for reflection in the server (`@RegisterForReflection(targets = …)`), and a test there checks that every persisted core type is registered.
* *Build times.* Most changes are to primitives, definitions and stores; `test -pl pm-mcp-core` runs without Quarkus augmentation. The Quarkus build runs for changes to the surface; the native build only in the release profile.
* *Coverage and logging.* Each module meets the coverage minimum on its own. The `LogRecord` constants move to the core, so both modules share one numbering.
* *Further modules* — the Skills extension, domain support — are added with their first code, as today's rule requires (xref:10-technology.adoc#_consequences_for_this_repository[Consequences for this repository]).

The split is made with the first core code, not before: the rename and the new core module land together.

== Transition order

The transition follows two axes: first the foundation, then the categories of the migration inventory (xref:14-test-strategy.adoc#_categories[Categories]).

. *Foundation.* Module split, binary with installation layout, daemon, state store with JSON and format versions, TOON renderer, workflow DSL and engine, entry, jobs and the executor adapter. Every script call still runs the Python script; nothing changes in behaviour.
. *Ported stores*, bottom-up by data dependency: references, tasks, findings, status, then lessons, metrics and the git and CI integrations. For status this is the `status.json` store only; the phase lifecycle and routing in `manage-status` are not ported but replaced by the workflow engine. Each switches individually after its differential tests pass (xref:14-test-strategy.adoc#_switch_over[Switch-over]).
. *Redesigned workflows*, phase by phase in phase order, starting with the init pilot. A phase switches once the stores it writes are ported, because the workflow engine writes only through Java stores under the plan's lock.
. *Retired parts* are removed together with the surface that makes them obsolete, not in advance.

The roadmap orders these steps with the services (xref:../roadmap.adoc[Roadmap]).
