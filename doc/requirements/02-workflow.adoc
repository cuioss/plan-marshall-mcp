== Hypermedia Workflow Engine (PM-WF)

[#PM-WF-1]
=== PM-WF-1: Hypermedia State Representation (HATEOAS)

The system must model all plan and orchestrator workflows as hypermedia state machines adhering strictly to HATEOAS principles. Clients discover valid operations exclusively through server-generated representations and links.

* The system must return workflow states as TOON-formatted text representations containing: `scope` (`plan`, `epic`, `workspace` for the project's workspace scope hosting `project-setup`, `entity` for a dispatched leaf sub-agent's query, or `none` only in a `pm_start` refusal, which omits the scope-bound fields), `plan_id` or `epic_id` (neither for `workspace`), `state` (dotted closed-enum), `summary` (single-line human-readable status), optional `skill` (URI to a static vocabulary skill), `facts` (minimal key-value pairs required for model judgment), and `links` (list of valid transitions).
* The system must advance the workflow exclusively via link-follow transitions, where each followed link immediately returns the subsequent state representation to form an unbroken transition chain.
* The system must omit large artifacts, raw build outputs, and detailed task definitions from `facts`, exposing them instead as read-only MCP resource URIs (`pm://...`).
* The system must emit an empty `links` list only when a plan or epic reaches an immutable terminal state, whose phase value is `completed` or `aborted` (terminal state identifiers always map to one of these two phase values); the workspace scope has no terminal state and never emits an empty `links` list, because every setup run ends in the resting state `setup.completed`, whose `reconcile` link starts the next run; each scope type must have exactly one abort terminal state (`plan.aborted`, `epic.aborted`), reachable from every phase, and no phase-specific abort terminal; an `abort` link inside a sub-workflow or phase flow must only leave that flow and return the outcome `aborted` to its caller, never end the plan or epic; a plan's `completed` state always carries its `merge_outcome` (`PM-WF-13`), so one terminal state answers whether the plan's work merged.
* The system must ensure that the model requires no advance knowledge of the state machine graph, never composes CLI commands from prose instructions, and never encounters transitions that are invalid in the current state.
* The process must stay server-enforced when the team owns its workflow units (`.marshall/config/*.pmwf`, `PM-IMPL-5`): the server executes only units that pass the static verification rules and the invariants compiled into the binary for every phase, and a unit can only compose compiled primitives and enrolled project scripts; a changed unit reaches a running plan only through the audited `config_drift` adopt-or-keep decision.

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification] and the link:specification/state-catalogue.adoc[State Catalogue] for implementation details.

[#PM-WF-2]
=== PM-WF-2: Closed Link Relation Grammar & Link Forms

State transitions must be structured as hypermedia forms using a closed vocabulary of link relations and typed parameter declarations.

* The system must restrict link relations (`rel`) strictly to the closed enumeration of 11 relations: `next` (default forward transition), `alt` (alternative forward path), `retry` (repeat after transient failure), `fix` (remediation sub-state), `loop_back` (bounded backward transition to an earlier phase), `submit` (hand judgment artifact to server), `dispatch` (sub-agent invocation), `wait` (monitor asynchronous operation), `escalate` (request operator intervention), `abort` (cancel a job or leave a sub-workflow or phase flow early; ending the plan or epic is an operator decision), and `emit` (materialize a staged child plan from an epic queue).
* The system must structure each offered link using one of 5 closed interaction form shapes (`submit`, `wait`, `dispatch`, `escalate`, `noop`) consisting of: `rel` (relation from closed enumeration), `link` (transition identifier optionally qualified by entity, e.g. `push`, `triage:F-12`, `wait:b-2291`), and `free` (comma-separated list of typed parameters required from model judgment).
* The system must execute all transitions through a single uniform MCP tool verb: `pm_do(plan_id | epic_id, link, args?, scope?, entity?, dispatch_id?)`, where `plan_id` may be the literal `NO_PLAN` for the project's workspace scope (`PM-TOOL-1`).
* The system must derive all execution context (worktree paths, git branch names, build commands, and upstream parameters) server-side from the `link` identifier and persisted state, requiring the model to supply only judgment values via `args`.
* The system must accept all model-authored multi-line text artifacts (commit messages, pull/merge-request bodies, review replies, clarified request documents, solution outlines, task descriptions, lesson bodies, and ADR bodies) directly in-band as typed UTF-8 string parameters in `args`, strictly eliminating legacy multi-step temp-file and path-allocation patterns (`.plan/temp/*-commit-msg.txt`, `work/ci-bodies/`, `work/pending-tasks/`, `work/lesson-body-*.md`, `prepare-body`, `prepare-comment`, `prepare-add`, and `resolve-path` followed by host `Write`).

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification], link:specification/workflow-dsl.adoc[Workflow DSL Specification], link:specification/phase-workflows.adoc[Phase Workflows Specification], and the link:specification/identifiers.adoc[Identifier Registry] for implementation details.

[#PM-WF-3]
=== PM-WF-3: Capability Enforcement by Link Omission

The hypermedia engine must enforce workflow capabilities and security boundaries primarily by omitting forbidden transitions from state representations.

* The system must enforce capability and privilege boundaries by omitting unauthorized transitions from the `links` list of generated representations.
* The system must never emit operator-only transitions (forcing gate evaluations, overriding merge barriers, deleting plans, or modifying project enrolment) as links in model-facing representations.
* The system must restrict privileged and operator-only actions exclusively to the operator channels of `PM-SEC-3` (MCP elicitation, the operator CLI, or a paired web device, the CLI-only actions of `PM-SEC-7` excepted).
* The system must independently evaluate and reject any transition call targeting an unoffered or omitted link, returning a structured rejection alongside the current valid representation.
* The system must record engine-raised conditions (a pending operator decision, a footprint violation, an incomplete dispatch, configuration drift, store tampering) as a condition overlay on the scope's current state, never as a state change: the current state and the sub-workflow call stack stay unchanged, the representation names the condition and offers only the condition's links, and a decision resolution is routed as an outcome of the state that raised the condition.

[#PM-WF-4]
=== PM-WF-4: Entity-Scoped Links & Fine-Grained Concurrency

Transitions operating on sub-components of a plan must address entities explicitly, ensuring safe concurrency across parallel sessions and sub-agents.

* The system must allow links to address specific sub-entities of a plan or epic by embedding the entity identifier within the link string (e.g. `triage:F-12`, `submit:TASK-003`, `wait:b-2291`).
* The system must execute validation, state mutation, and persistence as a single atomic operation under the mutual exclusion lock of the target plan or epic.
* The system must validate entity-scoped transitions against the current persisted state of that specific entity, rejecting stale transitions (such as triaging an already resolved finding) while allowing concurrent operations on distinct entities.
* The system must guarantee idempotent side effects for state transitions: attempting an already completed external action (such as pushing an up-to-date branch) must report success without redundant side effects, and requesting a build for a running worktree must join the active job.
* The system must handle replayed or stale links (resulting from context compaction or `/clear`) safely by rejecting the stale transition and returning the current valid state representation without raising fatal MCP protocol errors.

See the link:specification/workflow-dsl.adoc[Workflow DSL Specification], link:specification/hypermedia-format.adoc[Hypermedia Format Specification], and the link:specification/identifiers.adoc[Identifier Registry] for implementation details.

[#PM-WF-5]
=== PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint

Sub-agents must be dispatched as single-level leaf workers using rendered host commands, tracked deterministically by unique dispatch identifiers.

* The system must package tasks during Phase 4 (`plan`) into envelopes bounded by a configurable per-envelope token budget, delivering each envelope's current task within the sub-agent's state representation.
* The system must format `dispatch` links with fully rendered host execution structures, supplying `host_tool`, `params`, and a structured `prompt` body specifying `name`, `dispatch_id`, `plan_id` or `epic_id`, `entity`, `skills[]`, `WORKTREE` while the plan has a worktree (the canonical absolute path of the plan's worktree root), the operator's persisted continuation policy, and initial state command `start: pm_state(...)`.
* The system must enforce the single-level leaf constraint: sub-agents operating within entity scopes are terminal workers and must never receive `dispatch` links or spawn child sub-agents.
* The system must require sub-agents to persist deliverables via their own `submit` links and return a structured completion status to the parent session: `status` (`success`, `error`, `loop_back`, `blocked`, `harness_cancellation`), `display_detail` (maximum 80 ASCII characters, no trailing period), and optional `token_usage`. Missing token usage must be recorded as unmeasured rather than zero.
* The system must track sub-agent lifecycles using unique `dispatch_id` tokens: mark the dispatch claimed upon the sub-agent's first entity-scoped call, re-offer a dispatch that was never claimed or never returned with a new `dispatch_id` only on request (`redispatch`) after inspecting the persisted progress, derive it as unconfirmed when its phase closes (never through a clock-based timeout), and immediately reject submissions referencing superseded `dispatch_id` tokens.
* The system must equip reader sub-agents (used for untrusted external content ingestion) with only `WebSearch` and `WebFetch` (no local file tools; local content is passed in-band in the dispatch prompt) and zero MCP transition tools, requiring candidate data to be passed as plain text to the dispatching session for server-side schema validation.

See the link:specification/dispatch-and-effort.adoc[Dispatch & Effort Specification], link:specification/workflow-dsl.adoc[Workflow DSL Specification], and link:specification/client-profiles.adoc[Client Profiles Specification] for implementation details.

[#PM-WF-6]
=== PM-WF-6: Independent Server-Side Transition & Parameter Validation

The workflow engine must strictly validate all transition attempts and free parameters server-side, treating client calls as untrusted input.

* The system must validate every incoming `pm_do` invocation against the persisted state of the addressed scope independently of how the client constructed the request.
* The system must verify that the requested link ID exists within the set of valid transitions for the current state and that any addressed entity is currently in an accepting sub-state.
* The system must validate all supplied free parameters (`args`) against the link's closed JSON schema, enforcing `additionalProperties: false` and strict type conformity.
* For `submit` transitions carrying document or prose payloads (such as `outline.md`, `request.md`, Conventional Commit messages, PR bodies, or ADR AsciiDoc), the system must run the domain validator (`OutlineValidator`, `AsciiDocValidator`, `ConventionalCommitValidator`) in-process on the submitted parameter before atomically persisting the target store, making unvalidated store writes structurally impossible.
* The system must reject any invalid transition, malformed parameter payload, or failed content validation with a structured validation error payload that includes the rejection cause and the current, unmutated state representation.

[#PM-WF-7]
=== PM-WF-7: Worktree-Constrained Loop-Back & Iteration Bounds

Remediation loops from finalize back to execution must be strictly bounded and confined to active worktrees.

* The system must allow `loop_back` transitions returning a plan from Phase 6 (`finalize`) to Phase 5 (`execute`) only while the plan remains located within its dedicated worktree.
* The system must eliminate `loop_back` transitions by link omission immediately once the plan passes the pre-merge barrier and its worktree is removed.
* The system must allocate fresh, additive remediation tasks and envelopes within the worktree for each loop-back iteration, never reopening previously completed tasks, and must assign fresh dispatch IDs to preserve additive metric accounting.
* The system must enforce an automated loop-back iteration cap that is a compiled constant (`3`, not configurable); only an operator-granted extension of one plan may exceed it.
* The system must transition the plan to `finalize.loop-limit-reached` when the iteration ceiling is exhausted, offering exclusively an `escalate` link requiring operator intervention.
* The system must require every workflow step or verification layer that invokes the model (Q-Gate, pre-submission self-review, simplify, finding triage, any judging model) to declare a design-time ceiling on its iterations and dispatches in its step definition; no model-invoking loop may be unbounded, and no per-tool-call model gate may exist without a stated cost ceiling.
* The system must compare the plan's cumulative finalize spend with the error column of its budget anchor before merging; an overrun must be acknowledged by the operator before the merge proceeds, and the spend ratio must be recorded as a landing fact.

[#PM-WF-8]
=== PM-WF-8: Asynchronous Job Links & Wait Transitions

Long-running subprocesses and external provider waits must be modeled as asynchronous jobs with bounded polling transitions.

* The system must transition immediately to a job state, rendered as the running representation of a job state, upon initiating a long-running subprocess (builds, CI status checks, review-bot rate windows, merge queues), returning a representation containing `wait:<job_id>` and `cancel:<job_id>` links.
* The system must implement the `wait` link transition as a bounded blocking operation that returns either the completed outcome representation or an updated running representation with fresh progress metrics.
* The system must observe provider state (CI checks, review-bot output, merge-queue membership) at a fixed compiled cadence, with conditional requests where the provider supports them and one shared observation per credential and resource; a provider rate limit must defer the next observation to the stated reset and be attributed as a wait reason, never as a timeout or failure.
* The system must support extended wait intervals with periodic MCP progress notifications when the client profile indicates host support and the request includes a progress token.
* The system must restrict asynchronous job outcomes to a closed enumeration: `succeeded`, `failed`, `failed_unparsed` (build jobs only), `refused`, `cancelled`, `timed_out`, `killed`, and `indeterminate`.
* Composite and workflow primitives (such as the concurrent-wait region) must declare their own closed outcome enumerations per primitive; these are workflow outcomes, distinct from job outcomes, and are subject to exhaustive handling in the workflow DSL (`PM-IMPL-5`).

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification], link:specification/job-runtime.adoc[Job Runtime Specification], link:specification/workflow-dsl.adoc[Workflow DSL Specification], and link:specification/timeouts.adoc#waits[Timeouts & Budgets Specification] for implementation details.

[#PM-WF-9]
=== PM-WF-9: Composite Wait States & Short-Circuit Failure Handling

Concurrent asynchronous operations during finalization must be coordinated through unified composite wait states with immediate failure short-circuiting.

* The system must represent concurrent finalize operations (such as parallel CI pipeline execution and automated review-bot analysis) as a single unified composite state (`finalize.concurrent-wait`).
* The system must display discrete progress facts for all concurrent operations within the composite representation's `facts` block (e.g. `ci_status: running`, `bot_status: pending`) and expose a single composite wait transition `wait:finalize.concurrent-wait`.
* The system must immediately short-circuit the composite wait upon detecting a hard failure in any constituent job (such as a red CI pipeline): cancel all remaining pending wait jobs, and transition the representation directly to a failure state providing `fix` and `loop_back` links.
* The system must classify every failed CI check deterministically by the provider's conclusion (failure class) and by the check's log parsed with the build output parsers (failure kind), file it as a finding of source `ci`, and treat a failed required check it cannot classify as blocking; it must not classify a failure as flaky.

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification], link:specification/workflow-dsl.adoc[Workflow DSL Specification], and link:specification/phase-workflows.adoc[Phase Workflows Specification] for implementation details.

[#PM-WF-10]
=== PM-WF-10: Phase 1–4 Planning Invariants, Lane Ratchet & Artifact Gates

Planning phases (`phase-1-init` through `phase-4-plan`) must enforce deterministic artifact gates, main-checkout cleanliness, and a one-way planning lane ratchet.

* The system must support multiple plan initialization sources in `pm_start` (`request`, `issue` fetched via CI job, `lesson` with premise check and a claim of the lesson, which stays in the lesson store, `recipe` with a deterministic timestamp suffix, `local_changes`, which captures the user's own current changes of the main checkout as the plan's declared footprint, and `pr`, which adopts an existing pull request whose head branch the agent identity can push to and runs it through the finalize pipeline with the same states, gates, budgets, and landing as every other plan), while rejecting phantom plan IDs shaped like UUIDs or lesson IDs.
* The system must route a `local_changes` plan into the `land` lane, which skips refine, outline, plan, and execute task work, runs the verification and footprint checks of execute's exit over the captured changes, and then runs `phase-6-finalize` with every guarantee (step verdicts, pre-merge barrier, landing); a loop-back from finalize in a `land` plan offers only `escalate` and `abort` (no task allocation), and fixes made by the user are taken in by a `recapture` link that re-derives the footprint server-side before verification runs again. The changes captured at entry are the plan's footprint, not entry dirt: the capture never touches the main checkout's index or refs, keeps a recoverable snapshot of the captured state until the plan's changes are merged (on every other ending the snapshot stays until the operator removes it, and the plan owes its removal), and returns only those captured paths of the main checkout to their committed state whose content is still the captured content, so edits made after the capture are never lost.
* The system must route a `pr` plan into the `adopt` lane, fixed at plan creation and outside the planning lane ratchet like `land`: it skips refine, outline, plan, and execute, composes its execution manifest over the pull request's changed files, verifies through the finalize pipeline, and never rebases the adopted branch outside the merge gate; the pull request's changed files take part in the sibling collision check like the declared footprint of every other source.
* The system must record the primary checkout's porcelain state as an entry baseline when a plan is created. A plan writes its state only through server links into the per-project machine store, and server-owned repository writes happen only in worktrees (the plan worktree and the shared epic worktree), so any path modified, staged, or untracked in the main checkout since that baseline, outside the git-ignored `.marshall/local/`, violates the plan's rules: in every phase the transition refuses with a hard error and raises a footprint-violation condition on the current state, attributed to the plan. Dirt present at entry is reported as a fact (`facts.baseline_dirty`), never blocks, and is never offered for revert. A file under `.marshall/config/` (team configuration or workflow unit) changed since entry raises the operator-blocked condition (`blocked`) on the current state, in which the operator commits or restores it; a dirty `.marshall/config/` when `pm_start` is called refuses `pm_start` (`config_dirty`), except for a `local_changes` plan, whose captured change set includes it.
* The system must refuse transitions out of `phase-2-refine`, `phase-3-outline`, or `phase-4-plan` unless the phase's required artifact exists and passes structural validation (with `--allow-bare-transition` exemptions restricted to the operator channel).
* The system must route the planning pipeline by lane: a `light` plan skips the `phase-2-refine` states and runs one collapsed light envelope that folds refine without the confidence loop (clarified request, pull-request title), the simple outline, and deliverable derivation together, while a `deep` plan runs the full refine loop, outline, and plan pipeline. The light envelope must still satisfy the phase artifact gates (clarified request and pull-request title, validated outline, operator outline approval); the server records `phase-2-refine` completion when the envelope's submission carries them.
* The system must enforce a one-way planning lane ratchet (`light` -> `deep`): before the light envelope is dispatched, the server computes a deterministic budget over the declared affected files and their one-hop neighbours resolved from the architecture inventory (escalate when more than 25 files in total or more than 8 declared files), never from a sub-agent file-read counter; neighbours it cannot resolve send the plan `deep` with the recorded reason; the envelope may escalate by judgment (false premise, cross-module ripple, public symbol deletion); unknown scope estimates bias to `deep`; and light-to-deep escalation executes as a first-class engine transition with no way back.
* The system must let the team require the deep lane for every plan (`minimum_lane: deep` in the team configuration); the router otherwise decides, the `light` -> `deep` ratchet always applies, and neither a forced `light` lane nor a disabled ratchet may exist. The recipe auto-route threshold is a compiled constant (`PM-EXT-4`, `0.6`).
* The system must derive a plan's autonomy only from its per-plan `continuation_policy` (default from the operator's machine-local configuration, changed only through the operator channel); it must not offer per-transition auto-continue flags, and no setting may turn an operator-authorizing decision (outline approval, merge gates) into an automatic transition.
* The system must ensure `phase-2-refine` only widens active skill domains, `phase-3-outline` narrows them at most once, and a pull-request title is present from `phase-2-refine` onward, describes the scope that actually ships, and is re-confirmed before pull-request creation whenever a scope-shrinking transition (domain narrowing, `split` or `infeasible` deviation, gate-removed deliverable) occurred after it was authored; an empty title is a hard error.
* The system must compute `phase-4-plan` task derivation (profile mapping, dependency DAG cycle detection, skill resolution, and atomic task creation) deterministically over structured deliverables, using the same resolver for posture preview and execution manifest composition (in general, every derived planning question such as epic linkage, worktree presence, freshness, or posture must have exactly one resolver); task dependencies must be persisted per task (`depends_on`) and checked by the server on every task creation (every reference exists, the graph is acyclic), and envelope packing and dispatch must follow them.

[#PM-WF-11]
=== PM-WF-11: Q-Gate Validation Loop, Change-Type & Scope-Deviation Contracts

Quality gates, change-type classification, and scope-deviation handling must be governed by deterministic server validators and closed enumerations.

* The system must enforce a single writer for `change_type` (a closed enum of six values), falling back to a guided judgment `submit` link when the deterministic heuristic is ambiguous, and refusing transitions when plan-level scope and deliverable-level scope disagree.
* The system must execute Q-Gate validation loops in the engine for Phase 3 (deep lane only) and Phase 4, always iterating until clean (no mode may switch the gate off or stop it after one pass), and for lesson-derived plans in Phase 2, with a hard cap of 3 iterations, remediation of Phase 4 findings only through targeted per-task revision links that never change the task set (structural changes loop back to Phase 3 by operator decision), a content-hash rerun gate (an unchanged artifact is never re-validated: it exits clean without blocking findings and goes straight to Q-Gate exhaustion with them), an immediate exit when pending blocking findings reach zero, and a deterministic surgical-change bypass predicate.
* When an executing sub-agent encounters a scope deviation, the system must require a structured deviation submission (`hold`, `accept`, or `split`), transition the task to a blocked state awaiting batched operator consent via elicitation, require a persisted rationale included in the PR body for `accept`, and automatically seed a lesson for `split`.
* The system must restrict task status to `pending`, `in_progress`, `blocked`, `completed`, `skipped` (operator only, with a recorded reason), `infeasible` (reported by the sub-agent with evidence; tasks independent of it through `depends_on` continue, and the plan enters `execute.awaiting-infeasible-decision` only when nothing runnable remains while the operator decision is open), and `removed` (deliverable removed by the outline gate, a `split`, or the operator after `infeasible`); an `infeasible` task must block the plan until the operator either removes the deliverable (with a stale pull-request title and a recorded scope amendment) or loops back to `phase-3-outline`, and the model must never choose removal. `phase-5-execute` must be left only when every task is in a terminal status and every `skipped`, `infeasible`, or `removed` task carries its recorded disposition.

[#PM-WF-12]
=== PM-WF-12: Routine User Dialogue vs Operator-Authorizing Elicitation

The workflow engine must distinguish routine informational user choices from security- or scope-authorizing operator decisions.

* The system must model routine user interactions during planning (such as existing-plan handling, recipe choice, ambiguous domain selection, sibling collision resolution, posture selection, and batched refine clarifications) as states of the kind `awaiting_user`, each named by its question (the kind is never part of a state identifier), with typed question schemas, asking clarifications in a single batch and allowing at most one refine re-dispatch. A question of an execution sub-agent must be raised only as an entity escalation that blocks its task, never as a separate answers state of the plan.
* Where a host does not support MCP elicitation for routine non-authorizing choices, the system may accept answers relayed by the model and must record the relay provenance in the audit log.
* For authorizing decisions (outline approval in `outline.review`, scope-deviation acceptance, handshake drift override, pre-merge authorization including the `automatic-review` force-done, Q-Gate override on exhaustion (`force-gate`), ending a plan or an epic (`abort-plan`, `abort-epic`), archiving a plan whose pull request is open and unmerged, and plan deletion, including replacing an existing plan on a collision), the system must strictly require one of the operator channels of `PM-SEC-3` (MCP elicitation, the operator CLI, or a paired web device), never accepting model-relayed approvals. A routine answer that would end the plan must only request the operator decision `abort-plan`; the model must never end a plan or epic itself.
* The system must type every operator escalation decision like a primitive: each decision kind must declare a closed set of outcomes, each classified as approving, denying, or aborting, and an operator resolution naming any other outcome must be refused. An approving outcome must lead to a step that performs the approved action in the same transaction (for example, granting a loop-back extension allocates the fix tasks it grants); it must never lead to a terminal state or to a state that only continues the flow without performing the action.
* Every third-party dependency a plan adds must be named in the approved solution outline (a per-deliverable `Added dependencies` section approved in `outline.review`); before the merge the server must derive the added dependency coordinates from the build files the plan changed and file a blocking finding for every coordinate the approved outline does not name, and a changed build file it cannot parse must make the check indeterminate, never clean.

[#PM-WF-13]
=== PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier

Phase 6 (`phase-6-finalize`) must execute steps according to compile-time-verified ordering bands, preserve valid step verdicts across rebases, and gate branch merge on a fail-closed barrier.

* The system must organize finalize steps into five strict ordering bands verified at build time against order collisions, read-after-destroy hazards, and mutual exclusions:
** *Settle band (`order < 11`)*: `sync-baseline` (3), `simplify` (5), `security-audit` (7), `pre-submission-self-review` (8), `architecture-refresh` (9), `pre-push-quality-gate` (10).
** *Push boundary (`order == 11`)*: `push` (11), gated on working-tree build freshness.
** *Concurrent wait & triage region (`11 < order < 70`)*: `create-pr` (20), `ci-verify` (22), `automatic-review` (30), `sonar-roundtrip` (40), unified finding triage (`triage:F-n`), and `adr-propose` (62).
** *Merge gate (`order == 70`)*: `branch-cleanup` (70).
** *Post-run band (`order > 70`)*: `lessons-capture` (991), `preference-emitter` (992), `record-metrics` (998), `print-phase-breakdown` (999), `emit-landing` (1000), and `archive-plan` (1100), plus the optional `plan-retrospective` (995).
* The system must record `head_at_completion` for every completed `head_dependent` finalize step (refusing `done` without it) and evaluate verdict currency (`verdict_currency`) across rebases so a step verdict is retained when a `HEAD` advance does not touch its inputs; every `head_dependent` step must declare a server-validated `input_scope` (`remote_state`, `open_ended`, `plan_footprint`, or `declared` with non-empty `verdict_inputs`), and a missing scope must be a validation error, never a default.
* The system must enforce a fail-closed pre-merge review barrier in `branch-cleanup` (70); any operator merge authorization grant must be bound to both the current `HEAD` SHA and exactly one gap class of the merge-authorization roster (`review_barrier_gap`, `merge_action`, `red_ci_gate`, `rereview_timeout`, `find_step_completion`), and the operator's standing merge consent (`merge.auto_merge` in the machine-local `local-config.json`, default `false`) may satisfy only `merge_action`; no standing policy mints a grant for any other gap class; a grant covers only the findings that were open when it was minted.
* The pre-merge barrier must treat a required review bot as having reviewed the merge candidate only on bot-authored review evidence (a review object, a declared clean verdict, or a completed check-run) that covers the current `HEAD`; a zero finding count, a refusal, a status placeholder, a trigger acknowledgement, or an empty or never-established required roster must never be rendered or evaluated as a completed review.
* The system must record on the merge record, the pull request, and the landing whether a merge was reviewed, merged over an answered empty required roster (`vacuous`), or merged under a review-gap grant without a review covering the merge candidate (`unreviewed_by_grant`).
* The system must rebase a plan branch onto its base at the merge gate only when the provider requires an up-to-date branch or the base changed a path of the plan's footprint, must bind every merge and merge-queue enqueue to the head commit the pre-merge barrier and the grants evaluated (a moved head re-enters the merge gate), must count a merge or an enqueue only from the provider's observed state, and must bound a merge-queue wait by observed progress (no progress for twice the queue's check-response timeout) rather than by a fixed budget. Every failure of the merge path (lease interruption, rebase conflict, a remote branch moved by others, a provider refusal to merge, a merge-queue exit) must end in a state that offers retry and abort, and, past the lease, the operator decision to wind the plan down unmerged; a denied merge authorization must never abort the plan, and no path may merge over a provider refusal or force-push over foreign commits.
* The system must record on the terminal `completed` state a required, server-derived `merge_outcome` (`merged`, `enqueued_not_landed`, `declined`, `no_pr`, `dequeued`, `local_only`, or `handed_back`), derived from one observation of the provider's pull-request state and git through the same single mapping that derives the landing's `merge_state`, never from a model argument; a failed observation never completes the plan. `archive-plan` must refuse to archive a plan whose pull request is open and unmerged, and only an operator override through the operator channel may archive it: closing the pull request with a comment (after re-observing it; `declined`, or `merged` when it merged meanwhile), or, for a plan that adopted an existing pull request, handing it back open with a summary comment (`handed_back`); `enqueued_not_landed` records a pull request archived while in a merge queue after the operator wound the plan down unmerged. Every pull-request comment a plan posts must be posted at most once, also across retries. The refusal exists only where nothing merged; a merged plan (`merge_outcome: merged`) is always archived.
* The system must record every obligation a plan incurs but does not discharge as a typed owed-item record (kind, discharger, discharge proof) written by the step that incurs it; owed items survive archival and are listable without reading prose, from the epic inbox for epic plans and from a project-level owed index for every plan, and a plan that owes nothing records an explicit empty set.
* The system must keep archived plan and epic records readable by their `plan_id` or `epic_id` after archival, read-only, for as long as the project retains them. Archived plans stay in the per-project machine store (`<PM_MCP_BASE>/projects/<project_id>/archive/<plan_id>/`), so each record keeps exactly one authoritative location and never leaves the workstation (`PM-ARCH-2`); reading another project's archived plans requires the operator-approved cross-project escalation (`PM-SEC-2`).

=== PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution

Sub-agent dispatches must pack tasks into budget-bounded envelopes, track dispatch lifecycles through explicit `dispatch_id` return links, and resolve model/effort levels from a role registry.

* The system must automatically bin-pack implementation tasks in-process upon `plan.describe-tasks` submission into budget-bounded *task envelopes* (`EnvelopePacker`), sizing each task with a deterministic rubric into a server-derived (calibrated) size-to-token table, labelling every prediction `uncalibrated` until the server recalibrates the table from measured metrics, and merging an envelope below the minimum work that justifies a dispatch into a compatible neighbour; each task `submit` within an envelope must return the representation of the envelope's next pending task.
* The system must assign a unique `dispatch_id` to every rendered `dispatch` link, mark it claimed on the first entity call carrying that ID, and require the dispatching session to report sub-agent completion via a `returned:<dispatch_id>` link carrying `status`, `display_detail`, host `token_usage`, and, where the client profile declares them, the host's token components and tool-use count; the server measures the dispatch duration itself.
* The system must record missing sub-agent token usage as `unmeasured` (never as `0`; a measured `0` is legal only for a token component), flag any reported `success` where the target entity was not submitted, and allow safe re-dispatch of unconfirmed dispatches.
* The system must resolve the sub-agent effort level (`level-1`..`level-7` and `inherit`) from a hierarchical role registry (`plan.<phase>.effort.<subkey>` -> `plan.<phase>.effort.default` -> `plan.<phase>.effort` (string) -> `plan.effort` -> `inherit`, with an orchestrator `max` clamp that `inherit` never escapes; an effort key unknown to the registry is a configuration validation error, never a silent fallback) rendered via the effort ladder of the machine-local operator file `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (compiled client profile ladder as default; never git-tracked model pins), and must never emit a variant name that is not installed.

[#PM-WF-15]
=== PM-WF-15: Epic Plan Emission & Cross-Plan Merge Mutex

Orchestrator epics and concurrent plans must coordinate safely across sessions without sub-agent nesting violations or merge races.

* The system must expose staged epic plans via an `emit:<plan_id>` link that returns the operator entry command rather than dispatching a full plan as a sub-agent, observing the child plan's `running` state from its start (the plan's recorded epic origin).
* The system must treat surface disjointness as a modelling invariant of one epic, checked when the epic stages a plan rather than at emission: each staged plan declares its expected file/module surface, staging is refused with `surface_overlap` when that surface overlaps the declared surface of another non-terminal plan of the same epic that is not ordered with it through prerequisites, and with `surface_undeclared` when the surface cannot be declared; `emit:<plan_id>` checks only that the prerequisites have shipped. Plans of other epics and plans started without an epic are not checked (their conflicts surface at rebase or merge and are the operator's responsibility), and an accepted scope deviation that makes a running plan overlap an unordered plan of its epic is reported to the epic inbox (`surface_overlap_detected`) without blocking.
* The system must serialize concurrent plan rebases and merges within a repository through a per-repo FIFO admission queue and merge lease persisted in `<PM_MCP_BASE>/state/merge-queue.json` and updated only under the short transaction lock `<PM_MCP_BASE>/locks/merge.lock` (cross-plan review-bot rate-window claims are coordinated separately via `<PM_MCP_BASE>/state/review-bot-windows.json` under `<PM_MCP_BASE>/locks/review-bot.lock`), where the lease is held across the rebase-to-merge critical section, automatically releases whenever the plan enters a wait state, and is reclaimed from stale holders via runtime liveness (PID plus start time) or expired lease budgets (`PM-IMPL-7`).
* The system must land git-tracked epic ledger changes through one repository-wide epic landing that serializes its git steps under its own repository-wide lock outside the plan merge queue, confines its diff to the orchestrator ledger paths, reuses the open landing pull request, and never discards ledger writes made after its snapshot (the epic branch is resynced by merging the default branch into it, never by a reset).

[#PM-WF-16]
=== PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push

Multi-step domain sub-processes must be modeled as reusable, parameterized compound sub-workflows (`scope subworkflow`) invoked over a persisted call stack rather than duplicated across phase state graphs.

* The system must support reusable compound sub-workflows (`scope subworkflow`) invoked via parameterized `call <subworkflow_id>(<param_bindings>)` states, persisting the active call stack (`call_stack`) in `mcp/status.json` so interactive pauses, asynchronous job waits, and crash recovery inside a sub-workflow preserve the caller's phase, return state, and bound parameters.
* The system must verify at build time that the sub-workflow call graph across all `*.pmwf` definitions is a strict directed acyclic graph (DAG) with maximum call-stack depth $\le 4$, and that every `call` state's `<outcome> -> <target_state>` clauses form an exact 1-to-1 bijection with the target sub-workflow's declared `terminal <outcome>` states.
* The system must provide a canonical reusable `git.commit_and_push` sub-workflow (`git-commit-and-push.pmwf`) shared across Phase 5 (`execute` deliverable chain-tail and remediation commits), Phase 6 (`finalize` settle-step commit instrumentation, `push` barrier, and post-PR re-push, including the re-push of an adopted pull request of a plan of source `pr`), `marshall-steward`, and `plan-orchestrator`.
* The `git.commit_and_push` sub-workflow must execute the complete config-driven git commit and push lifecycle:
** Inspect working-tree changes (`git status --porcelain`) in the resolved worktree or primary checkout; when the working tree is clean, either return `clean` immediately (`push_mode=never`) or proceed directly to the push barrier (`push_mode=if_push_remote` or `always`).
** Detect and clean build/temp artifacts against `artifact-patterns.json` while respecting `.gitignore` (failing closed if the `.gitignore` oracle fails), unconditionally excluding `.marshall/**` and nested git worktrees/submodules, auto-deleting `safe` untracked artifacts, and pausing in an interactive `git.artifact-review` state only when `uncertain` tracked artifacts or prohibited secret files are detected.
** Resolve and validate the commit message in-memory (using either a caller-supplied deterministic template or an interactive `git.compose-message` `submit` transition with diff-derived `type`/`scope` facts), validate Conventional Commits syntax, and deterministically append the configured `Co-Authored-By` trailer, read from the operator's `commit_trailer{name,email}` in the machine-local `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (machine-wide default in `machine-config.json`, compiled default `Co-Authored-By: plan-marshall <noreply@cuioss.de>`) and never from a team configuration file.
** Stage scoped paths (the dirty paths within the plan's declared footprint, accepted deviations, task target files, and step-declared outputs; a dirty path outside that set is never staged and fails the commit loudly, naming the path) and execute `git -C <tree> commit -F -` by streaming the UTF-8 commit message over `stdin`, capture the new `commit_sha` and git-sourced `changed_paths`, append a `kind="change"` entry to `change-ledger.jsonl`, and—when invoked from a Phase 6 `mutates_source: true` step—re-stamp the committing step's `head_at_completion` when it is `head_dependent: true` and record a `freshness_reconcile` entry for every commit made after the latest successful build.
** Evaluate push policy from caller parameters (`push_mode`: `never`, `if_push_remote`, `always`, `post_pr_conditional`) and the server-derived presence of a push remote (a local-only run is derived from its absence, never configured), enforce the `pre-commit-verify-freshness` gate before pushing, push unconditionally on the plan branch's first push (tracked by a persisted `branch_pushed_at` fact), and on re-entry push only when the `branch-sync-state` parity probe reports `ahead` (`synced`, `remote_absent_landed`, and unknown states never push; `remote_absent_unverified` is first resolved by provider evidence: a merged pull request makes it landed and never re-pushed, no pull request at all makes it pushed, any other observation never pushes), force a push only with an explicit expected remote SHA and only on the operator's approval, and transition to structured recovery states (`git.commit-fix` on pre-commit hook failure, never bypassing the hook; `git.sync-required` on non-fast-forward rejection; `git.resolve-conflicts` for a rebase conflict, resolved by the model, never by an operator decision) before returning a closed terminal outcome (`committed_local`, `committed_and_pushed`, `pushed_clean` only after an executed push, `in_sync` when nothing needed pushing, `clean`, or `aborted`) to the caller state. Every operator-approved escalation inside the sub-workflow must execute the approved action in the transition that applies the approval.
** Author every commit as the operator (the operator's configured commit identity) and commit it as the agent identity resolved from the provider credential (a fixed system identity when none resolves), identically in the native and the CLI variant, keeping the configured `Co-Authored-By` trailer.
* The per-deliverable verification verbs that Phase 5 runs after each deliverable's chain-tail commit must be configurable in the team configuration (`workflow.json` key `plan.phase-5-execute.per_deliverable_verbs`), defaulting to `compile` and `module-tests` (as `plan-marshall`'s `per_deliverable_build`, by operator decision).
