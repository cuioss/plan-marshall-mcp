== Hypermedia Workflow Engine (PM-WF)

[#PM-WF-1]
=== PM-WF-1: Hypermedia State Representation (HATEOAS)

The system must model all plan and orchestrator workflows as hypermedia state machines adhering strictly to HATEOAS principles. Clients discover valid operations exclusively through server-generated representations and links.

* The system must return workflow states as TOON-formatted text representations containing: `scope` (`plan`, `epic`, `workspace` for the project's workspace scope hosting `project-setup` and the lesson maintenance, or `entity` for a task entity of a worker or a pending plan or epic bootstrap addressed by its `entry_id`), `plan_id` or `epic_id` (neither for `workspace`), `state` (dotted closed-enum), `summary` (single-line human-readable status), optional `skill` (URI to a static vocabulary skill), `facts` (minimal key-value pairs required for model judgment), and `links` (list of valid transitions).
* The system must drive every plan and epic itself (`PM-ARCH-1`): a state that needs no model is server logic, and a state that needs one is a task of a role (`PM-WF-5`, `PM-WORK-2`). Links are offered only where a model acts: on a worker's task entities, on the states of the plan and epic bootstraps and of the project setup that the entry session drives, and as the answer links of open question records (`PM-WF-12`); a plan or epic representation is otherwise a view whose `links` list is empty. Each followed link immediately returns the subsequent representation of the entity it addressed.
* The system must omit large artifacts, raw build outputs, and detailed task definitions from `facts`, exposing them instead as read-only MCP resource URIs (`pm://...`).
* A plan or epic must reach an immutable terminal state whose phase value is `completed` or `aborted` (terminal state identifiers always map to one of these two phase values); a task entity or a pending plan or epic bootstrap (scope `entity`) ends in a terminal state of its entity unit, which never ends the scope that hosts it; the `integrity_breach` pause offers no link, its only resolutions being operator verbs (`PM-WF-3`); the workspace scope has no terminal state, because every setup run ends in the resting state `setup.completed`, whose `reconcile` link starts the next run; each scope type must have exactly one abort terminal state (`plan.aborted`, `epic.aborted`), reachable from every phase and entered only by the operator's `abort`, `delete-plan`, or the resolution of an integrity breach, and no phase-specific abort terminal; a sub-workflow must be left early only with the control outcome `stepped_out`, returned to its caller by the server when the sub-workflow's attempts or bounded retries are exhausted, or, in a sub-workflow the entry session drives, by its implicit `step_out` link (`PM-WF-16`), and never ends the plan or epic; a condition whose self-remedy budget is spent unwinds every call frame to the phase's fallback (`PM-WF-3`).
* The system must end every plan that the operator does not abort in exactly one of four outcomes, each reached only through `finalize.archive-plan` after the post-run band: `merged` (the terminal `completed`, which always carries its `merge_outcome`, `PM-WF-13`), `handed_back` (the work delivered as an open pull request, a draft after a fallback and ready for review when the operator's `merge.auto_merge` is off and the pre-merge barrier passed, or as a branch where no pull request can exist, with the gaps documented in a pull-request comment and a label), `returned` (the planning result only, nothing implemented), or `no_change` (the terminal `completed`: a recipe run whose harvest yielded no targets, without a commit or pull request, `merge_outcome: no_pr`); the terminal states of `handed_back` and `returned` map to the phase value `completed`. Every blocking condition of a plan must end in a bounded self-remedy followed by a defined fallback to `returned` or `handed_back` (`returned` while the plan branch has no commit beyond the base and `handed_back` once it has, in every phase until the merge: the Phases 1–4 fallback `plan.return` forwards a plan with committed work to the hand-back, and the Phase 5 fallback returns a plan without; none after the merge), so no plan waits for an operator decision or for a session; the only pause is an integrity breach (`PM-WF-3`), and the only unbounded wait is a question whose class the operator configured as `questions.mode: operator` (`PM-WF-12`). The landing record carries the outcome (`merged`, `handed_back`, `returned`, `no_change`, or `aborted`).
* The system must ensure that the model requires no advance knowledge of the state machine graph, never composes CLI commands from prose instructions, and never encounters transitions that are invalid in the current state.
* The process must stay server-enforced when the team owns its workflow units (`.marshall/config/*.pmwf`, `PM-IMPL-5`): the server executes only units that pass the static verification rules and the invariants compiled into the binary for every phase, and a unit can only compose compiled primitives and enrolled project scripts; a changed unit reaches a running plan only through a re-composition of the plan's instance that the server adopts (the audited `config_drift` condition, `PM-IMPL-5`).

[#PM-WF-2]
=== PM-WF-2: Closed Link Relation Grammar & Link Forms

State transitions must be structured as hypermedia forms using a closed vocabulary of link relations and typed parameter declarations.

* The system must restrict link relations (`rel`) strictly to the closed enumeration of 9 relations: `next` (default forward transition), `alt` (alternative forward path), `retry` (repeat after transient failure), `fix` (remediation sub-state), `loop_back` (bounded backward transition to an earlier phase), `submit` (hand a judgment artifact to the server), `escalate` (file a waiver request, which only the operator answers through the operator channel, `PM-WF-12`), `consult` (ask another role through the server, `PM-WORK-4`), and `abort` (leave a sub-workflow the entry session drives through `step_out`; ending the plan or epic as `aborted` is only the operator's `abort`). Waiting on a job and cancelling it are engine events, never links.
* The system must structure each offered link using one of 2 closed interaction form shapes (`submit`, `noop`) consisting of: `rel` (relation from closed enumeration), `link` (transition identifier optionally qualified by entity, e.g. `submit:TASK-003`, `ask:TASK-003`), and `free` (comma-separated list of typed parameters required from model judgment); the options of a decision are defined once, in the representation that offers them.
* The system must execute all link transitions through a single uniform MCP tool verb: `pm_do(plan_id | epic_id, link, args?, scope?, entity?)`, where `plan_id` may be the literal `NO_PLAN` for the project's workspace scope (`PM-TOOL-1`).
* The system must derive all execution context (worktree paths, git branch names, build commands, and upstream parameters) server-side from the `link` identifier and persisted state, requiring the model to supply only judgment values via `args`.
* The system must accept all model-authored multi-line text artifacts (commit messages, pull/merge-request bodies, review replies, clarified request documents, solution outlines, task descriptions, lesson bodies, and ADR bodies) directly in-band as typed UTF-8 string parameters in `args`, never through `plan-marshall`'s multi-step temp-file and path-allocation patterns (`.plan/temp/*-commit-msg.txt`, `work/ci-bodies/`, `work/pending-tasks/`, `work/lesson-body-*.md`, `prepare-body`, `prepare-comment`, `prepare-add`, and `resolve-path` followed by host `Write`).

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification], link:specification/workflow-dsl.adoc[Workflow DSL Specification], link:specification/phase-workflows.adoc[Phase Workflows Specification], and link:specification/identifiers.adoc[Identifier Registry] for implementation details.

[#PM-WF-3]
=== PM-WF-3: Capability Enforcement by Link Omission

The hypermedia engine must enforce workflow capabilities and security boundaries primarily by omitting forbidden transitions from state representations.

* The system must enforce capability and privilege boundaries by omitting unauthorized transitions from the `links` list of generated representations.
* The system must never emit operator-only transitions (setting or revoking a waiver, aborting a plan or an epic, resolving an integrity breach, deleting plans, or modifying project enrolment) as links in model-facing representations.
* The system must restrict privileged and operator-only actions exclusively to the operator channels of `PM-SEC-3` (the operator CLI or a paired web device, the CLI-only actions of `PM-SEC-7` excepted; MCP elicitation carries only the operator-configuration choices the server raises itself).
* The system must independently evaluate and reject any transition call targeting an unoffered or omitted link, returning a structured rejection alongside the current valid representation.
* The system must record engine-raised conditions (a footprint violation, an indeterminate guard, an incomplete task, an unmet operator-side precondition such as a missing credential or a changed team configuration file, configuration drift, an integrity breach) as a condition overlay on the scope's current state, never as a state change: the current state and the sub-workflow call stack stay unchanged, and the representation names the condition and, where the entry session drives the scope, offers only the condition's links. Every condition except an integrity breach runs its self-remedy, bounded by a compiled budget per condition instance: the server retries where a retry can clear it, and where clearing it needs judgment or work, a task of the role whose work raised it (for example `fix` of a footprint violation by the plan's writer role); the operator may remove the cause at any time, and when the budget is spent the plan takes its phase's fallback (`PM-WF-1`) with the condition recorded as the gap. An integrity breach (`integrity_breach`: a tampered plan, epic, or workspace store, a tampered lesson, or a tampered project enrolment; a tampered harness enrolment is no breach but an unmet precondition of the worker launch, `PM-EXEC-1`) pauses the affected scope (for an enrolment, every running plan of the project; for a lesson, the lesson source of every plan bootstrap fails with the reason) without a model link and without a bound, refusing every `pm_do` and offering no task of the scope, with `integrity_paused`, until the operator re-baselines it (`accept-edit`, after the engine re-verifies) or, for a plan or epic only, ends the scope (`abort`); a workspace store, a lesson, or an enrolment is resolved only by `accept-edit`.

[#PM-WF-4]
=== PM-WF-4: Entity-Scoped Links & Fine-Grained Concurrency

Transitions operating on sub-components of a plan must address entities explicitly, ensuring safe concurrency across parallel workers and sessions.

* The system must allow links to address specific sub-entities of a plan or epic by embedding the entity identifier within the link string (e.g. `submit:TASK-003`, `ask:TASK-003`).
* The system must execute validation, state mutation, and persistence as a single atomic operation under the mutual exclusion lock of the target plan or epic.
* The system must validate entity-scoped transitions against the current persisted state of that specific entity, rejecting stale transitions (such as submitting an already completed task) while allowing concurrent operations on distinct entities.
* The system must guarantee idempotent side effects for state transitions: attempting an already completed external action (such as pushing an up-to-date branch) must report success without redundant side effects, and requesting a build for a running worktree must join the active job.
* The system must handle replayed or stale links (from a compaction, a `/clear`, or a fenced worker generation) safely by rejecting the stale transition (`generation_fenced` for a fenced generation, `PM-WORK-2`) and, for `pm_do`, returning the current valid representation, without raising fatal MCP protocol errors.

[#PM-WF-5]
=== PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint

Every piece of model work inside a plan or an epic must be a task of a role (`PM-WORK-1`), done by a single-level leaf worker that the server itself launches through the headless command line of an enrolled harness, supervises, and bounds; the host never dispatches a sub-agent, and no model work runs in the interactive session unless the session takes a task as an optional worker (`PM-WORK-5`).

* The system must package tasks during Phase 4 (`plan`) into envelopes bounded by a configurable per-envelope token budget, delivering each envelope's current task within its task entity's representation (`PM-WF-14`).
* The system must bind every model step to a job state naming a role (DSL `job llm <entity_kind> role <role> [each <primitive_id>]`), whose completion is an engine event, never a link a model polls: a state declared with `each` fans out over a server-computed list into one task per element, each with its own entity, and completes when every entity has its required submission or its fallback.
* The system must compose every worker's launch server-side and record it in the worker's job record: the harness, model, and effort from the role's artifact (`PM-WORK-1`), the argument vector from the harness's client profile (`headless` template: an inline named agent where the harness offers one, per-call flags otherwise; nothing is installed), the working directory (the plan worktree, else the project checkout, so that project instructions and skills load natively), the server-composed launch prompt (`PM-SKILL-4`), a strict per-call MCP configuration that starts only the job relay `pm-mcp serve --job` (`PM-SEC-4`), and the job token and generation in the relay's environment.
* The system must fix the PM-MCP tool set of a worker by its role's class: every worker except `zero_tool` gets `pm_wait` and `pm_state` and `pm_do` on its own task entities, `pm_skill`, and `pm_skill_file`; `writer` workers additionally `pm_build` and `pm_lsp`; `read_only` workers `pm_lsp` limited to its read operations (`rename` is refused with `invalid_arguments`) and never `pm_build`; `zero_tool` workers get no tool and no PM-MCP connection.
* The system must enforce the single-level leaf constraint: a worker reaches PM-MCP only through its job-bound connection, which offers its role's tool set, the links of the task entities leased to its generation, and read-only resource reads (`resources/read` and `resources/list`: every resource of the worker's own project plus `skill://pm/...`, the project boundary being the only read boundary, `PM-TOOL-3`), and never a scope-creating action, an operator action, or a link that starts a model; a consultation goes through the server (`PM-WORK-4`); the client bundle's entry commands stay inert inside a worker.
* The system must require a worker to persist deliverables only through its task entity's `submit` links and to raise a question only as a question record (`PM-WF-12`); the server evaluates a task only from persisted records, never from a worker's exit status or final output.
* The system must observe every worker's end itself and record its fate (`succeeded`, `failed`, `timed_out`, `killed`, `cancelled`, `indeterminate`, or `refused`) in its job record, bounded by a per-role budget learned above compiled floors; a fresh worker's job ends after its one task, a warm worker's job after its generation; a call carrying the token of an ended job is refused (`job_ended`).
* The system must run the injection screener of `PM-SEC-1` as a fresh `zero_tool` worker with a server-fixed prompt, an empty job-private working directory, one turn, and project and user settings disabled where the harness allows.

[#PM-WF-6]
=== PM-WF-6: Independent Server-Side Transition & Parameter Validation

The workflow engine must strictly validate all transition attempts and free parameters server-side, treating client calls as untrusted input.

* The system must validate every incoming `pm_do` invocation against the persisted state of the addressed scope independently of how the client constructed the request.
* The system must verify that the requested link ID exists within the set of valid transitions for the current state and that any addressed entity is currently in an accepting sub-state.
* The system must validate all supplied free parameters (`args`) against the link's closed JSON schema, enforcing `additionalProperties: false` and strict type conformity.
* For `submit` transitions carrying document or prose payloads (such as `outline.md`, `request.md`, Conventional Commit messages, PR bodies, or ADR AsciiDoc), the system must run the domain validator (`OutlineValidator`, `AsciiDocValidator`, `ConventionalCommitValidator`) in-process on the submitted parameter before atomically persisting the target store, making unvalidated store writes structurally impossible.
* The system must reject any invalid transition, malformed parameter payload, or failed content validation with a structured validation error payload that includes the rejection cause and the current, unmutated state representation.

See the link:specification/workflow-dsl.adoc[Workflow DSL Specification], link:specification/hypermedia-format.adoc[Hypermedia Format Specification], link:specification/phase-workflows.adoc[Phase Workflows Specification], and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-WF-7]
=== PM-WF-7: Remediation Policies, Loop-Back & Iteration Bounds

Remediation loops from finalize back to execution must be strictly bounded and confined to active worktrees.

* The system must allow `loop_back` transitions returning a plan from Phase 6 (`finalize`) to Phase 5 (`execute`) only while the plan remains located within its dedicated worktree.
* The system must eliminate `loop_back` transitions by link omission immediately once the plan passes the pre-merge barrier and its worktree is removed.
* The system must allocate fresh, additive remediation tasks and envelopes within the worktree for each loop-back iteration, never reopening previously completed tasks, and must serve them as new tasks with their own task ids to preserve additive metric accounting.
* The system must bound a loop-back from Phase 5 to `phase-3-outline` (after an infeasible deliverable) by a compiled loop-back budget of `1`, raisable only through the Q-Gate fix budget: it returns to the lane's outline authoring state, keeps the plan's worktree and its committed work, composes new plan instance versions at the outline and plan events without rewriting history, and on exhaustion hands the plan back when Phase 5 committed work, otherwise returns it.
* The system must handle every failure class of a plan (Q-Gate findings, build failure, CI failure, analysis-provider failure, review findings and missing review evidence, merge conflict, spend overrun) through a remediation policy, a project-owned DSL sub-workflow unit per class (`remediation.qgate-findings`, `.build-failure`, `.ci-failure`, `.analysis`, `.review-findings`, `.merge-conflict`, `.spend`): the server gathers the evidence (structured failures with fingerprints, logs only as untrusted resource URIs) and composes the facts of the decision with the evidence it rests on, the policy's decide step is a task of the policy's role (`PM-WORK-1`), which chooses one action of a closed set the server validates (`retry` with a reason, bounded by the retry budget; `fix`, bounded by the fix budget, which is the loop limit; `request_waiver` with a rationale, offered only for a waivable gate while a waiver wait is configured), and the unit returns only its reachable outcomes of `resolved`, `waived`, `exhausted`, and `fix_requested`, plus the control outcome `stepped_out`; where the bound budgets leave only one action, the server takes it without a task, and while the role is unqualified its tasks take the conservative fallback of `PM-WORK-6`; every caller routes `exhausted` and `stepped_out` to its phase's fallback (`PM-WF-1`).
* The system must bind the budgets (retry, fix, and waiver wait) as call arguments of the project-owned phase units, capped by compiled hard limits, with the shipped values and hard limits of the link:specification/timeouts/01-job-budgets-and-waits.adoc#remediation-budgets[Timeouts & Budgets Specification, Remediation Budgets]; budgets are counted per plan and failure class, persisted, and never reset. A retry or fix budget beyond its bound value can only be raised by an operator waiver (`--raise`, `PM-SEC-3`), which never exceeds the compiled hard limit; revoking a raise lowers the ceiling at the next budget check.
* The system must require every workflow step or verification layer that invokes the model (Q-Gate, pre-submission self-review, simplify, finding triage, any judging model) to declare a design-time ceiling on its iterations and tasks in its step definition; no model-invoking loop may be unbounded, and no per-tool-call model gate may exist without a stated cost ceiling.
* The system must compare the plan's cumulative finalize spend with the error column of its budget anchor before merging; an overrun calls the spend remediation policy, which hands the plan back unless the operator waived the spend check (a `met` waiver of the gate `spend`, evaluated once at the merge gate's entry), and the spend ratio must be recorded as a landing fact.

[#PM-WF-8]
=== PM-WF-8: Asynchronous Job Links & Wait Transitions

Long-running subprocesses and external provider waits must be modeled as asynchronous jobs with bounded polling transitions.

* The system must transition immediately to a job state upon initiating a long-running subprocess or observation (builds, CI status checks, review-bot rate windows, merge queues, and workers, `PM-WF-5`), and must advance the workflow on the job's completion as an engine event; no model polls or cancels a job, and the plan representation shows the job's progress as a view.
* The system must implement the waits a model holds (a worker's `pm_wait`, `PM-WORK-2`, and a running `pm_build`, `PM-TOOL-2`) as bounded blocking calls that return a result or an answer to wait again before the host's limit (`PM-IMPL-4`).
* The system must observe provider state (CI checks, review-bot output, merge-queue membership) at a fixed compiled cadence, with conditional requests where the provider supports them and one shared observation per credential and resource; a provider rate limit must defer the next observation to the stated reset and be attributed as a wait reason, never as a timeout or failure.
* The system must support extended waits with periodic MCP progress notifications when the client profile indicates host support and the request includes a progress token.
* The system must restrict asynchronous job outcomes to a closed enumeration: `succeeded`, `failed`, `failed_unparsed` (build jobs only), `refused`, `cancelled`, `timed_out`, `killed`, and `indeterminate`.
* Composite and workflow primitives (such as the concurrent-wait region) must declare their own closed outcome enumerations per primitive; these are workflow outcomes, distinct from job outcomes, and are subject to exhaustive handling in the workflow DSL (`PM-IMPL-5`).

[#PM-WF-9]
=== PM-WF-9: Composite Wait States & Short-Circuit Failure Handling

Concurrent asynchronous operations during finalization must be coordinated through unified composite wait states with immediate failure short-circuiting.

* The system must represent concurrent finalize operations (such as parallel CI pipeline execution and automated review-bot analysis) as a single unified composite state (`finalize.concurrent-wait`).
* The system must display discrete progress facts for all concurrent operations within the composite representation's `facts` block (e.g. `ci_status: running`, `analysis_status: passed`, `bot_status: pending`, where `analysis_status` aggregates every configured code analysis provider) and complete the composite state as one engine event.
* The system must immediately short-circuit the composite wait upon detecting a hard failure in any constituent job (such as a red CI pipeline): cancel all remaining pending wait jobs and call the remediation policy of the failing class (`PM-WF-7`), one class at a time in the fixed order CI, analysis, review findings; after a `resolved` or `waived` outcome the wait re-observes every class whose verdict is stale at the new `HEAD`. A constituent job that is killed, times out, or ends indeterminate restarts the watch within a compiled restart budget, and then the plan is handed back.
* The system must classify every failed CI check deterministically by the provider's conclusion (failure class) and by the check's log parsed with the build output parsers (failure kind), file it as a finding of source `ci`, and treat a failed required check it cannot classify as blocking; it must not classify a failure as flaky (only the model's bounded `retry` names that reason). A failure is baseline-only, and never reaches the model, when the provider's CI result of the same check on the base (or, only where no provider result exists, a local build of the merge base) shows the same failure fingerprints (`PM-EXEC-6`).

[#PM-WF-10]
=== PM-WF-10: Phase 1–4 Planning Invariants, Lane Ratchet & Artifact Gates

Planning phases (`phase-1-init` through `phase-4-plan`) must enforce deterministic artifact gates, main-checkout cleanliness, and a one-way planning lane ratchet.

* The system must create a plan only through the plan bootstrap (`bootstrap-plan`, `PM-TOOL-1`), whose source units gather and verify the source before the plan exists: `request` (the user's text), `issue` (fetched by a bounded provider read and passed through the two-level guard for external text, `PM-SEC-1`), `lesson` (an active, unclaimed lesson whose premise is checked before the plan exists: an obsolete lesson is retired without creating a plan, a refuted premise is carried into the plan as an amendment; the lesson is claimed when the plan is created and stays in the lesson store), `recipe` (parameters validated against the recipe's schema, `PM-EXT-4`, and a plan id with a deterministic timestamp suffix), `local_changes` (the user's own current changes of the main checkout, captured when the plan is created as the plan's declared footprint), `pr` (an existing pull request whose head branch the agent identity can push to, run through the finalize pipeline with the same states, gates, budgets, and landing as every other plan), and `epic_row` (the staged spec section of a queue row the server launches for its epic, `PM-WF-15`); the system must reject phantom plan IDs shaped like UUIDs or lesson IDs.
* The system must route a `local_changes` plan into the `land` lane, which skips refine, outline, plan, and execute task work, runs the verification and footprint checks of execute's exit over the captured changes, and then runs `phase-6-finalize` with every guarantee (step verdicts, pre-merge barrier, landing); the plan never changes the user's code: its remediation policies are bound with the action `retry` only (no `fix`, no task allocation, no `loop_back`, pruned in its plan instance with reason `land_lane`), and a land plan whose policy is exhausted is handed back with the failure documented, so the user fixes the branch after the run. The changes captured at entry are the plan's footprint, not entry dirt: the capture is taken once and never repeated, never touches the main checkout's index or refs, keeps a recoverable snapshot of the captured state until the plan's changes are merged (on every other ending the snapshot stays until the operator removes it, and the plan owes its removal), and returns only those captured paths of the main checkout to their committed state whose content is still the captured content, so edits made after the capture are never lost.
* The system must route a `pr` plan into the `adopt` lane, fixed at plan creation and outside the planning lane ratchet like `land`: it skips refine, outline, plan, and execute, composes its plan instance over the pull request's changed files, verifies through the finalize pipeline, and never rebases the adopted branch outside the merge gate; the pull request's changed files take part in the sibling collision check like the declared footprint of every other source.
* The system must record the primary checkout's porcelain state as an entry baseline when a plan is created. A plan writes its state only through server links into the per-project machine store, and server-owned repository writes happen only in worktrees (the plan worktree and the shared epic worktree), so any path modified, staged, or untracked in the main checkout since that baseline, outside the git-ignored `.marshall/local/`, violates the plan's rules: in every phase the transition refuses with a hard error and raises a footprint-violation condition on the current state, attributed to the plan. Dirt present at entry is reported as a fact (`facts.baseline_dirty`), never blocks, and is never offered for revert. A file under `.marshall/config/` (team configuration or workflow unit) changed since entry raises the `precondition_unmet` condition (reason `config_changed`) on the current state, which names the file and the operator's remedy (commit or restore it) and offers only its bounded `retry` (`PM-WF-3`); a dirty `.marshall/config/` keeps a plan bootstrap in its setup precondition state and is checked again when the plan is created (`config_dirty`), except for a `local_changes` plan, whose captured change set includes it.
* The system must refuse transitions out of `phase-2-refine`, `phase-3-outline`, or `phase-4-plan` unless the phase's required artifact exists and passes structural validation; no exemption exists.
* The system must route the planning pipeline by lane: a `light` plan skips the `phase-2-refine` states and runs one collapsed light envelope that folds refine without the confidence loop (clarified request, pull-request title), the simple outline, and deliverable derivation together, while a `deep` plan runs the full refine loop, outline, and plan pipeline. The light envelope must still satisfy the phase artifact gates (clarified request and pull-request title, validated outline, passed outline gate); the server records `phase-2-refine` completion when the envelope's submission carries them.
* The system must enforce a one-way planning lane ratchet (`light` -> `deep`): before the light envelope task starts, the server computes a deterministic budget over the declared affected files and their one-hop neighbours resolved from the architecture inventory (escalate when more than 25 files in total or more than 8 declared files), never from a worker's file-read counter; neighbours it cannot resolve send the plan `deep` with the recorded reason; the envelope task may escalate by judgment (false premise, cross-module ripple, public symbol deletion); unknown scope estimates bias to `deep`; and light-to-deep escalation executes as a first-class engine transition with no way back.
* The system must let the team require the deep lane for every plan (`minimum_lane: deep` in the team configuration); the router otherwise decides, the `light` -> `deep` ratchet always applies, and neither a forced `light` lane nor a disabled ratchet may exist. The recipe auto-route threshold is a compiled constant (`PM-EXT-4`, `0.6`).
* The system must run every plan to its outcome without a stop for a session or an operator: no setting stops a plan between phases, and no setting may pass a server gate (the outline gate, the pre-merge barrier) that its evidence does not pass; only an operator waiver (`PM-SEC-3`) admits a failing waivable gate.
* The system must ensure `phase-2-refine` only widens active skill domains, `phase-3-outline` narrows them at most once, and a pull-request title is present from `phase-2-refine` onward, describes the scope that actually ships, and is re-confirmed before pull-request creation whenever a scope-shrinking transition (domain narrowing, a deliverable removed after `infeasible`, a gate-removed deliverable) occurred after it was authored; an empty title is a hard error.
* The system must compute `phase-4-plan` task derivation (profile mapping, dependency DAG cycle detection, skill resolution, and atomic task creation) deterministically over structured deliverables, using the same resolver for every composition of the plan instance (`PM-IMPL-5`), whose steps pruned by the plan's posture (chosen in the plan bootstrap, otherwise the projection's default; mandatory steps are never pruned) are shown with their reason in the first instance diagram, the posture preview (in general, every derived planning question such as epic linkage, worktree presence, freshness, or posture must have exactly one resolver); task dependencies must be persisted per task (`depends_on`) and checked by the server on every task creation (every reference exists, the graph is acyclic), and envelope packing and the order of the envelope tasks must follow them.

=== PM-WF-11: Q-Gate Validation Loop, Change-Type & Unplanned-Change Recording

Quality gates, change-type classification, and scope-deviation handling must be governed by deterministic server validators and closed enumerations.

* The system must enforce a single writer for `change_type` (a closed enum of six values), falling back to a task of the classification role when the deterministic heuristic is ambiguous, and refusing transitions when plan-level scope and deliverable-level scope disagree.
* The system must run the Q-Gate of Phase 3 (deep lane only) and Phase 4, and for lesson-derived plans of Phase 2, as a task of the phase's Q-Gate role (class `read_only`) whose completion the server evaluates: the task submits assessments and findings, the server runs the compiled mechanical checks and decides `clean` or `blocking` from the persisted findings alone (no mode may switch the gate off or stop it after one pass), and a `blocking` verdict calls the Q-Gate remediation policy (`remediation.qgate-findings`, `PM-WF-7`; shipped fix budget `3`, no `retry`). Its `fix` returns to the phase's authoring state with the findings as facts (Phase 4 findings only through targeted per-task revision links that never change the task set; a structural change is a bounded loop-back to Phase 3), an unchanged artifact is refused as `fix_unchanged` instead of being re-validated, `resolved` or `waived` (waived findings recorded as accepted by waiver) exits the phase, and `exhausted` returns the plan (`returned`); the validator population per phase and a deterministic surgical-change bypass predicate are fixed in the specification.
* The system must pass the outline gate without an operator decision when the outline's Q-Gate returned `clean`, `resolved`, or `waived` (or does not apply: light lane, recipe, surgical bypass), the task derivation dry-run succeeds (checked on every outline submission, which is refused when the outline is not derivable), and no `3-outline` finding is pending; a review of the outline by the user is an optional question record (`approve` or `revise`, the latter charged to the Q-Gate fix budget), asked only when the operator configured it or the plan bootstrap requested it (`PM-WF-12`).
* The system must accept and record unplanned changes, never review them: a writer worker may change files beyond the plan's declared footprint inside the plan's worktree without asking, the declared footprint stays the statement of intent, and the server records the realized minus the declared paths as unplanned changes with their provenance (task or loop-back) and lists them in the pull-request body and the landing record; only a boundary breach (a path outside the worktree, the main checkout, a protected path) is refused, by the non-waivable footprint guards (`PM-SEC-1`). For an epic plan, an overlap of unplanned paths with a sibling's declared surface is only noted in the landing record.
* The system must restrict task status to `pending`, `in_progress`, `completed`, `infeasible` (reported by the envelope task with evidence; tasks independent of it through `depends_on` continue), and `removed` (deliverable removed by the outline gate or after `infeasible`). When nothing runnable remains and a deliverable is infeasible, a task of the plan's re-planning role judges it with the infeasible deliverables and their server-computed transitive dependents as facts: it removes the deliverable (a recorded gap in the pull request and the landing record, the pull-request title marked stale; removing the last deliverable is refused), loops back to `phase-3-outline` within the compiled loop-back budget, or hands the plan back; it may first ask the user (`PM-WF-12`). `phase-5-execute` must be left only when every task is in a terminal status and every `infeasible` or `removed` task carries its recorded disposition.

=== PM-WF-12: Question Records vs Operator Overrides

The workflow engine must distinguish content questions, which reach the user through one server question mechanism, from operator overrides, which only the operator channel carries.

* The system must model every content question of a scope (the init classifier questions: recipe candidate, sibling collision, and domain choice; the batched refine and outline clarifications; the optional outline review; a Phase 5 task question; a question a worker raises before one of its judgments; the team-configuration choices of the workspace setup) as a server-owned question record in the scope's question store (question, options with `branch_key`, the `recommended` option or a `default_assumption`, question class, and origin), created by a worker's `ask` link, by an envelope task's `ask:TASK-NNN` link (which records the question and ends the envelope task; the remaining tasks, the asking task included, go to the next envelope task with the answer in its facts), by the `questions` list of a refine or outline authoring task's `submit`, or by a server classifier. A scope waits for an open question only in a state of the derived kind `awaiting_user`, named by its question (the kind is never part of a state identifier), on a server-owned deadline; clarifications are asked in a single batch, and at most one refine task is served again for them. The posture is never asked (`PM-WF-10`). Choices made before a scope exists (what to work on, a lesson's premise, recipe parameters, accepting an external text the screener flagged) are links of the plan or epic bootstrap that the model follows after relaying the user's choice, never question records.
* The system must validate every answer against the question record's options (an unknown `branch_key`, a second answer, and an answer after expiry are refused), record it with its channel (`web`, `session`, `elicitation`, `model`, or `assumption`), keep open and answered questions in the scope's question store, and record an answer that changes the plan's intent as an amendment (source `user`, `model`, `assumption`, or `refutation`) listed in the pull-request body and the landing record.
* The system must deliver every content question of a plan or epic through the web app, which notifies the paired devices (`PM-SEC-7`) and is the dependable channel, and must also show it to the entry session while one is open, through the answer links of the scope's representation, whose answer the session relays from the user; the first valid answer wins. MCP elicitation must carry only the choices of the project setup and of the plan and epic bootstraps, which the entry session drives. `questions.mode` (per project in the operator's `local-config.json`, with optional overrides per question class: init, clarification, review, task) selects `operator` (waited for without a bound, the one operator-chosen exception to bounded waits, listed as waiting for an answer in `pm-operator status` and the web app), `model` (a task of the asking role answers with a confidence, accepted at or above the compiled refine confidence threshold, otherwise handled as `auto`; a question the server raised itself has no asking role and is handled as `none`), `none` (the recommended option or the default assumption applied at once and recorded as an assumption), or `auto` (the default: waited for `questions.wait_seconds`, link:specification/timeouts/01-job-budgets-and-waits.adoc#question-wait[Timeouts & Budgets Specification, Question Wait], on a server-side timer). The server owns every deadline and default: the expiry of an `auto` question takes the compiled fallback of its class: an init question the classifier's recommended option, or the `returned` route where no safe default exists; a clarification its default assumption, recorded as an assumption amendment; the outline review the `returned` route; a task question or a question a worker raised before its own judgment the stated default of the question, validated against the options; a team-configuration choice of the workspace setup the fallback its question state declares, recorded as an assumption.
* The system must treat operator overrides as never being content questions and accept them only through the operator CLI or a paired web device (`PM-SEC-3`), never as a link and never relayed by the model: setting and revoking waivers, ending a plan or an epic (`abort`), resolving an integrity breach (`accept-edit` or `abort`), plan deletion, cross-project access grants (`PM-SEC-2`), and operator configuration; an operator-configuration choice the server raises itself during the project setup (among them the integration variant, which defaults to `native` and is asked only when the native variant cannot serve a used feature, and the commit identity) may also be answered through MCP elicitation. An override is never taken as a content answer, and a content answer given through elicitation or a paired device is never an override. Team-configuration choices of the project setup are content questions of the workspace scope. No model ends a plan or an epic: a worker's task ends only in its closed task outcomes (`PM-WORK-2`), and only the operator's `abort` ends a scope as `aborted`.
* The system must let the operator influence a running plan only through waivers: a waiver declares one gate of a closed list met or raises one budget (`--raise`), is plan-scoped with a mandatory reason, is recorded append-only in the plan's waiver record by the operator channel alone, may be set at any time until the gate's fallback is taken (and is refused afterwards), applies to every later evaluation of its gate, composes a new version of the plan instance (`PM-IMPL-5`), and is listed with every consumption in a pull-request comment and the landing record. Waivable are only review evidence (per bot), a named failing CI check, the quality gate of an analysis provider, the open findings of a class after triage, the Q-Gate findings of a phase, the spend check (a `met` waiver of the gate `spend`), and the fix and retry budgets (`--raise`); integrity breaches, the footprint and main-checkout guard, job confinement, credentials, security findings, and the operator boundary are never waivable. A waivable gate admits a failure only through a waiver lookup that logs its consumption. A waiver request filed by a worker (`request_waiver`) is announced to the operator (`pm-operator status`, `pm-operator waivers`, the web app, the plan view, and an idempotent pull-request comment with a label), independently of the question delivery, and is answered only by a waiver; its bounded wait then ends in the fallback.
* Every third-party dependency a plan adds must be named in the solution outline that passed the outline gate (a per-deliverable `Added dependencies` section); before the merge the server must derive the added dependency coordinates from the build files the plan changed and file a blocking finding for every coordinate the outline does not name, and a changed build file it cannot parse must make the check indeterminate, never clean.

=== PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier

Phase 6 (`phase-6-finalize`) must execute steps according to compile-time-verified ordering bands, preserve valid step verdicts across rebases, and gate branch merge on a fail-closed barrier.

* The system must organize finalize steps into five strict ordering bands verified at build time against order collisions, read-after-destroy hazards, and mutual exclusions:
** *Settle band (`order < 11`)*: `sync-baseline` (3), `simplify` (5), `security-audit` (7), `pre-submission-self-review` (8), `architecture-refresh` (9), `pre-push-quality-gate` (10).
** *Push boundary (`order == 11`)*: `push` (11), gated on working-tree build freshness.
** *Concurrent wait & triage region (`11 < order < 70`)*: `create-pr` (20), `ci-verify` (22), `automatic-review` (30), `analysis-roundtrip` (40), unified finding triage (one triage job per gather firing), and `adr-propose` (62).
** *Merge gate (`order == 70`)*: `branch-cleanup` (70).
** *Post-run band (`order > 70`)*: `lessons-capture` (991), `preference-emitter` (992), `record-metrics` (998), `print-phase-breakdown` (999), `emit-landing` (1000), and `archive-plan` (1100), plus the optional `plan-retrospective` (995).
* The system must record `head_at_completion` for every completed `head_dependent` finalize step (refusing `done` without it) and evaluate verdict currency (`verdict_currency`) across rebases so a step verdict is retained when a `HEAD` advance does not touch its inputs; every `head_dependent` step must declare a server-validated `input_scope` (`remote_state`, `open_ended`, `plan_footprint`, or `declared` with non-empty `verdict_inputs`), and a missing scope must be a validation error, never a default.
* The system must enforce a fail-closed pre-merge review barrier in `branch-cleanup` (70) that no operator grant and no standing policy can pass: before it evaluates, the merge gate re-sends every triaged finding response that was not transmitted; open findings that are not triaged, and missing review evidence of a required bot, call the review-findings remediation policy (`PM-WF-7`), whose `exhausted` outcome hands the plan back; a failing waivable gate is admitted only by an operator waiver of the closed list (`PM-WF-12`), whose consumption is bound to the evaluated `HEAD` and to the findings it covered.
* The pre-merge barrier must treat a required review bot as having reviewed the merge candidate only on bot-authored review evidence (a review object, a declared clean verdict, or a completed check-run) that covers the current `HEAD`; a zero finding count, a refusal, a status placeholder, a trigger acknowledgement, or an empty or never-established required roster must never be rendered or evaluated as a completed review.
* The system must record on the merge record, the pull request, and the landing whether a merge was reviewed, merged over an answered empty required roster (`vacuous`), or merged under a consumed `review_evidence` waiver without a review covering the merge candidate (`unreviewed_by_waiver`).
* The system must rebase a plan branch onto its base at the merge gate only when the provider requires an up-to-date branch or the base changed a path of the plan's footprint, must bind every merge and merge-queue enqueue to the head commit the pre-merge barrier evaluated (a moved head re-enters the merge gate), must count a merge or an enqueue only from the provider's observed state, and must bound a merge-queue wait by observed progress (no progress for twice the queue's check-response timeout) rather than by a fixed budget. A rebase conflict, at the merge gate or already in `sync-baseline` when the upstream changes overlap the plan's paths, calls the merge-conflict remediation policy; every other failure of the merge path (lease interruption, a remote branch moved by others, a provider refusal to merge, a merge-queue exit) ends after its bounded retry in the `handed_back` fallback, a refusal by the provider's protection rules (required review, branch protection, draft, merge method) at once. No path may merge over a provider refusal (which is not waivable), and no path may force-push except a lease-protected push of the plan's own branch after a server rebase.
* The system must record on the terminal state of every plan that ends through `finalize.archive-plan` a required, server-derived `merge_outcome` (`merged`, `enqueued_not_landed`, `declined`, `no_pr`, `dequeued`, `local_only`, `handed_back`, or `awaiting_human_merge`), derived from one observation of the provider's pull-request state and git through the same single mapping that derives the landing's `merge_state`, never from a model argument; a failed observation never completes the plan. A plan whose pull request is open and unmerged when it takes its fallback is handed back (`finalize.hand-back`): the pull request stays open (opened as a draft when the fallback creates it) with an idempotent gap comment and the label `pm-mcp:handed-back`, and the post-run band and the archive still run; a plan without a push remote (derived, never configured) ends `handed_back` by design with `merge_outcome: local_only`, its plan branch kept. The operator's merge policy `merge.auto_merge` (`local-config.json`, default `true`) decides only whether the plan merges itself: with `false` the plan instance leaves out the merge execution, and a plan whose pre-merge barrier passed ends `handed_back` with its pull request ready for review (never a draft) and `merge_outcome: awaiting_human_merge`; the policy never passes a barrier predicate or a gate and is not a waiver. Every pull-request comment a plan posts must be posted at most once, also across retries. After the merge no fallback exists: a failing post-merge step is re-fired once and otherwise recorded as an owed item, and a merged plan (`merge_outcome: merged`) is always archived.
* The system must record every obligation a plan incurs but does not discharge as a typed owed-item record (kind, discharger, discharge proof) written by the step that incurs it; owed items survive archival and are listable without reading prose, from the epic inbox for epic plans and from a project-level owed index for every plan, and a plan that owes nothing records an explicit empty set.
* The system must keep archived plan and epic records readable by their `plan_id` or `epic_id` after archival, read-only, for as long as the project retains them. Archived plans stay in the per-project machine store (`<PM_MCP_BASE>/projects/<project_id>/archive/<plan_id>/`), so each record keeps exactly one authoritative location and never leaves the workstation (`PM-ARCH-2`); reading another project's archived plans requires the operator's cross-project access grant (`PM-SEC-2`).

[#PM-WF-14]
=== PM-WF-14: Task Envelopes, Model Slots & Usage per Task

Implementation tasks must be packed into budget-bounded envelopes, workers must run within machine-wide and per-plan concurrency bounds, and usage must be accounted per task from the harness's own output.

* The system must automatically bin-pack implementation tasks in-process upon `plan.describe-tasks` submission into budget-bounded *task envelopes* (`EnvelopePacker`), sizing each task with a deterministic rubric into a server-derived (calibrated) size-to-token table, labelling every prediction `uncalibrated` until the server recalibrates the table from measured metrics, and merging an envelope below the minimum work that justifies a task into a compatible neighbour; each task `submit` within an envelope must return the representation of the envelope's next pending task. Envelope tasks must run serially: a chain-tail submit, a question (`ask:TASK-NNN`), an infeasible report, or a `yield` ends the envelope task (a yield with the server-recorded reason `chain_tail`, `question`, or `context`) and hands the remaining tasks, the asking task included, to the next envelope task, and the plan reacts only to the envelope task's completion, whose outcome a server return-evaluation primitive derives from the persisted entity state in a fixed precedence (pending question, pending infeasible judgment, chain tail, continue, all complete).
* The system must lease a machine-wide model slot for every running worker, warm or fresh (`model-slots.json`, cap in `machine-config.json`): a warm worker holds its slot for its whole generation, idle or not; a task waiting for a worker is `queued`, and a worker's budget starts at spawn. At most one worker of a `writer` role may run per plan, while `read_only` and `zero_tool` workers of the plan run beside it within the machine cap.
* The system must take token usage, cost, and duration from the harness's own output as the client profile's usage declaration maps it, never from a model's self-report: per task from the per-turn usage of a warm worker's turns that served the task, and per job from a fresh worker's run (population `model_job`, duration measured from spawn to exit); a field the harness does not report is recorded as `unmeasured` (never as `0`; a measured `0` is legal only for a token component), a token total is derived as the sum of the four token components (input, output, cache read, cache creation) only when all four are measured and is `unmeasured` otherwise, and a run-total record is never read as a context size.
* The system must take the harness, model, and effort of every worker only from its role's artifact (`PM-WORK-1`); an effort the harness or model does not support narrows to the nearest supported value, never escalates, and is recorded. No agent variant is installed, and an artifact change applies to the next worker generation.

=== PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex

Orchestrator epics and concurrent plans must come into existence through a server-side intake and coordinate safely without nesting a plan inside a task or racing merges.

* The system must create an epic only through the epic bootstrap (`bootstrap-epic`, `PM-TOOL-1`), which gathers the title, the vision (from the user's text or a fetched issue, `PM-SEC-1`), and `parallelization_scope`, and whose completion creates the epic scope with its header and the vision section of its specification in one transaction; the epic workflow then starts at decomposition, where a task of the epic's decomposition role drafts workstreams and staged plan sections submitted through server-checked links (a section of more than six deliverables is refused as `section_too_large`), and the epic becomes active only with at least one staged row.
* The system must adopt, never re-create, an epic whose git-tracked ledger exists without the epic's machine scope (for example after a clone): the epic bootstrap offers the adoption for such a ledger, and its completion creates only the machine scope from the ledger, the durable truth, which it never rewrites, entering decomposition only when the ledger has no queue row at all and the active state otherwise; an unreadable or invalid ledger ends the adoption in a failure state that names the reason.
* The system must start every launchable plan of an epic itself, within the epic's `parallelization_scope` and the machine's model slots: a staged row is launchable when its prerequisites have shipped and a re-grounding at the current `HEAD` did not judge its spec `stale`; the server creates the plan through the plan bootstrap's `epic_row` source without a session, which reads the row's staged spec section as the request, binds the plan to its row, and sets the row `running` in the plan's creation transaction. A task of the epic's re-grounding role judges every staged row whose spec predates the current `HEAD`, and a row judged `stale` is not launched until its section is submitted again.
* The system must map every plan outcome onto its epic queue row: `merged` to `merged`, `no_change` to `completed`, `aborted` to `abandoned`, `handed_back` to the live status `handed_back` until the epic's landing reconciliation observes the pull request merged (`merged`) or closed (`abandoned`), and `returned` to the closed status `returned` (the work may be staged again only as a new row); a prerequisite counts as shipped only as `merged` or `completed`.
* The system must treat surface disjointness as a modelling invariant of one epic, checked when the epic stages a plan rather than at emission: each staged plan declares its expected file/module surface, staging is refused with `surface_overlap` when that surface overlaps the declared surface of another non-terminal plan of the same epic that is not ordered with it through prerequisites, and with `surface_undeclared` when the surface cannot be declared; the launch checks only that the prerequisites have shipped and that the row's spec is not judged `stale`. Plans of other epics and plans started without an epic are not checked (their conflicts surface at rebase or merge and are the operator's responsibility), and an unplanned change (`PM-WF-11`) that makes a running plan overlap the declared surface of a sibling plan of its epic is only noted in the landing record, never blocking; the epic's landing reconciliation handles it.
* The system must serialize concurrent plan rebases and merges within a repository through a per-repo FIFO admission queue and merge lease persisted in `<PM_MCP_BASE>/state/merge-queue.json` and updated only under the short transaction lock `<PM_MCP_BASE>/locks/merge.lock` (cross-plan review-bot rate-window claims are coordinated separately via `<PM_MCP_BASE>/state/review-bot-windows.json` under `<PM_MCP_BASE>/locks/review-bot.lock`), where the lease is held across the rebase-to-merge critical section, automatically releases whenever the plan enters a wait state, and is reclaimed from stale holders via runtime liveness (PID plus start time) or expired lease budgets (`PM-IMPL-7`).
* The system must land git-tracked epic ledger changes through one repository-wide epic landing that serializes its git steps under its own repository-wide lock outside the plan merge queue, confines its diff to the orchestrator ledger paths, reuses the open landing pull request, and never discards ledger writes made after its snapshot (the epic branch is resynced by merging the default branch into it, never by a reset).

=== PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push

Multi-step domain sub-processes must be modeled as reusable, parameterized compound sub-workflows (`scope subworkflow`) invoked over a persisted call stack rather than duplicated across phase state graphs.

* The system must support reusable compound sub-workflows (`scope subworkflow`) invoked via parameterized `call <subworkflow_id>(<param_bindings>)` states, persisting the active call stack (`call_stack`) in `mcp/status.json` so tasks, asynchronous job waits, and crash recovery inside a sub-workflow preserve the caller's phase, return state, and bound parameters.
* The system must verify at build time that the sub-workflow call graph across all `*.pmwf` definitions is a strict directed acyclic graph (DAG) with maximum call-stack depth $\le 4$, and that every `call` state's `<outcome> -> <target_state>` clauses form an exact 1-to-1 bijection with the target sub-workflow's exit contract: `done` with a typed result record, domain outcomes only where callers genuinely continue differently (for a remediation policy the reachable subset of `resolved`, `waived`, `exhausted`, `fix_requested`), and the control outcome `stepped_out`.
* A sub-workflow inside a plan or epic must be left early only by the server (`stepped_out` when its attempts or bounded retries are exhausted); a sub-workflow the entry session drives (the bootstraps and their source units, the project setup) must offer the implicit `step_out` link (with a reason) in every resting link state, which unwinds one call frame and returns `stepped_out` to its caller. A call makes the sub-workflow's first state current, the representation shows the call path, and each model step asks for exactly one piece of judgment through one link naming its skill section, never bundling unrelated inputs or asking for what the server can derive.
* The system must provide a canonical reusable `git.commit_and_push` sub-workflow (`git-commit-and-push.pmwf`) shared across Phase 5 (`execute` deliverable chain-tail and remediation commits), Phase 6 (`finalize` settle-step commit instrumentation, `push` barrier, and post-PR re-push, including the re-push of an adopted pull request of a plan of source `pr`), the in-branch fixes of the remediation units (`remediation.ci-failure`, `remediation.review-findings`, `remediation.analysis`), the epic ledger commit (`epic.commit-ledger`), and the landing of the project-setup changes (`setup.land-changes`).
* The `git.commit_and_push` sub-workflow must execute the complete config-driven git commit and push lifecycle:
** Inspect working-tree changes (`git status --porcelain`) in the resolved worktree or primary checkout; when the working tree is clean, either return at once (`push_mode=never`) or proceed directly to the push barrier (`push_mode=if_push_remote` or `always`).
** Detect and clean build/temp artifacts against the compiled artifact pattern table (a classpath resource of `pm-core`, not a configuration file) while respecting `.gitignore` (failing closed if the `.gitignore` oracle fails), unconditionally excluding `.marshall/**` and nested git worktrees/submodules, auto-deleting `safe` untracked artifacts, and serving a task of the artifact-review role (`git.artifact-review`) only when `uncertain` tracked artifacts or prohibited secret files are detected.
** Resolve and validate the commit message in-memory (using either a caller-supplied deterministic template or a task of the commit-message role, `git.compose-message`, with diff-derived `type`/`scope` facts), validate Conventional Commits syntax, and deterministically append the configured `Co-Authored-By` trailer, read from the operator's `commit_trailer{name,email}` in the machine-local `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (machine-wide default in `machine-config.json`, compiled default `Co-Authored-By: plan-marshall <noreply@cuioss.de>`) and never from a team configuration file.
** Stage the worktree's dirty paths that the artifact review did not classify as build or temporary artifacts (paths beyond the plan's declared footprint are staged and recorded as unplanned changes, `PM-WF-11`; a path outside the worktree or a protected path is never staged and fails the commit loudly, naming the path) and execute `git -C <tree> commit -F -` by streaming the UTF-8 commit message over `stdin`, capture the new `commit_sha` and git-sourced `changed_paths`, append a `kind="change"` entry to `change-ledger.jsonl`, and—when invoked from a Phase 6 `mutates_source: true` step—re-stamp the committing step's `head_at_completion` when it is `head_dependent: true` and record a `freshness_reconcile` entry for every commit made after the latest successful build.
** Evaluate push policy from caller parameters (`push_mode`: `never`, `if_push_remote`, `always`, `post_pr_conditional`) and the server-derived presence of a push remote (a local-only run is derived from its absence, never configured; a presence that cannot be determined raises the `precondition_unmet` condition with its bounded retry, then the fallback), enforce the `pre-commit-verify-freshness` gate before pushing, push unconditionally on the plan branch's first push (tracked by a persisted `branch_pushed_at` fact), and on re-entry push only when the `branch-sync-state` parity probe reports `ahead` (`synced` never pushes and counts as pushed; `remote_absent_landed` never pushes and returns `pushed: false` with `landed: true`; `remote_absent_unverified` and every unrecognised state end in a server step-out with the cause `push_state_unknown`), force a push only as a lease-protected push (explicit expected remote SHA) of the plan's own branch after a server rebase, refusing every other force push, and handle its failures locally in structured recovery states (`git.commit-fix`, a task of the plan's writer role, on pre-commit hook failure, never bypassing the hook; `git.sync-required`, server logic, on non-fast-forward rejection; `git.resolve-conflicts`, a task of the plan's writer role, for a rebase conflict) before returning its exit contract to the caller state: `done` with the result record `{commit?, pushed, landed?, clean}` (`pushed`: the remote branch holds `HEAD` after the call), or `stepped_out` (by the server when the compiled attempt cap of a recovery loop, the bounded `.gitignore` oracle retry, or a push-state check ends it), on which callers branch by guards such as `result.pushed` and `result.landed`.
** Author every commit as the operator (the operator's configured commit identity) and commit it as the agent identity resolved from the provider credential (a fixed system identity when none resolves), identically in the native and the CLI variant, keeping the configured `Co-Authored-By` trailer.
* The per-deliverable verification verbs that Phase 5 runs after each deliverable's chain-tail commit must be configurable in the team configuration (`workflow.json` key `plan.phase-5-execute.per_deliverable_verbs`), defaulting to `compile` and `module-tests` (as `plan-marshall`'s `per_deliverable_build`); a failing per-deliverable build or verification sweep calls the build-failure remediation policy (`PM-WF-7`), whose `fix` allocates remediation tasks and whose `exhausted` outcome hands the plan back.
