== Hypermedia Workflow Engine (PM-WF)

[#PM-WF-1]
=== PM-WF-1: Hypermedia State Representation (HATEOAS)

The system must model all plan and orchestrator workflows as hypermedia state machines adhering strictly to HATEOAS principles. Clients discover valid operations exclusively through server-generated representations and links.

* The system must return workflow states as TOON-formatted text representations containing: `scope` (`plan` or `epic`), `plan_id` or `epic_id`, `state` (dotted closed-enum), `summary` (single-line human-readable status), optional `guidance` (URI to a static vocabulary skill), `facts` (minimal key-value pairs required for model judgment), and `links` (list of valid transitions).
* The system must advance the workflow exclusively via link-follow transitions, where each followed link immediately returns the subsequent state representation to form an unbroken transition chain.
* The system must omit large artifacts, raw build outputs, and detailed task definitions from `facts`, exposing them instead as read-only MCP resource URIs (`pm://...`).
* The system must emit an empty `links` list only when a plan or epic reaches an immutable terminal state (`completed`, `abandoned`).
* The system must ensure that the model requires no advance knowledge of the state machine graph, never composes CLI commands from prose instructions, and never encounters transitions that are invalid in the current state.

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification] for implementation details.

[#PM-WF-2]
=== PM-WF-2: Closed Link Relation Grammar & Link Forms

State transitions must be structured as hypermedia forms using a closed vocabulary of link relations and typed parameter declarations.

* The system must restrict link relations (`rel`) strictly to the closed enumeration of 11 relations: `next` (default forward transition), `alt` (alternative forward path), `retry` (repeat after transient failure), `fix` (remediation sub-state), `loop_back` (bounded backward transition to an earlier phase), `submit` (hand judgment artifact to server), `dispatch` (sub-agent invocation), `wait` (monitor asynchronous operation), `escalate` (request operator intervention), `abort` (defined early termination), and `emit` (materialize a staged child plan from an epic queue).
* The system must structure each offered link using one of 5 closed interaction form shapes (`submit`, `wait`, `dispatch`, `escalate`, `noop`) consisting of: `rel` (relation from closed enumeration), `link` (transition identifier optionally qualified by entity, e.g. `push`, `triage:F-12`, `wait:b-2291`), and `free` (comma-separated list of typed parameters required from model judgment).
* The system must execute all transitions through a single uniform MCP tool verb: `pm_do(plan_id | epic_id, link, args)`.
* The system must derive all execution context (worktree paths, git branch names, build commands, and upstream parameters) server-side from the `link` identifier and persisted state, requiring the model to supply only judgment values via `args`.
* The system must accept all model-authored multi-line text artifacts (commit messages, pull/merge-request bodies, review replies, clarified request documents, solution outlines, task descriptions, lesson bodies, and ADR bodies) directly in-band as typed UTF-8 string parameters in `args`, strictly eliminating legacy multi-step temp-file and path-allocation patterns (`.plan/temp/*-commit-msg.txt`, `work/ci-bodies/`, `work/pending-tasks/`, `work/lesson-body-*.md`, `prepare-body`, `prepare-comment`, `prepare-add`, and `resolve-path` followed by host `Write`).

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification], link:specification/workflow-dsl.adoc[Workflow DSL Specification], and link:specification/phase-workflows.adoc[Phase Workflows Specification] for implementation details.

[#PM-WF-3]
=== PM-WF-3: Capability Enforcement by Link Omission

The hypermedia engine must enforce workflow capabilities and security boundaries primarily by omitting forbidden transitions from state representations.

* The system must enforce capability and privilege boundaries by omitting unauthorized transitions from the `links` list of generated representations.
* The system must never emit operator-only transitions (forcing gate evaluations, overriding merge barriers, deleting plans, or modifying project enrolment) as links in model-facing representations.
* The system must restrict privileged and operator-only actions exclusively to the authenticated operator channel (MCP elicitation or operator CLI).
* The system must independently evaluate and reject any transition call targeting an unoffered or omitted link, returning a structured rejection alongside the current valid representation.

See the link:specification/workflow-dsl.adoc[Workflow DSL Specification] and link:specification/hypermedia-format.adoc[Hypermedia Format Specification] for implementation details.

[#PM-WF-4]
=== PM-WF-4: Entity-Scoped Links & Fine-Grained Concurrency

Transitions operating on sub-components of a plan must address entities explicitly, ensuring safe concurrency across parallel sessions and sub-agents.

* The system must allow links to address specific sub-entities of a plan or epic by embedding the entity identifier within the link string (e.g. `triage:F-12`, `task:T-3`, `wait:b-2291`).
* The system must execute validation, state mutation, and persistence as a single atomic operation under the mutual exclusion lock of the target plan or epic.
* The system must validate entity-scoped transitions against the current persisted state of that specific entity, rejecting stale transitions (such as triaging an already resolved finding) while allowing concurrent operations on distinct entities.
* The system must guarantee idempotent side effects for state transitions: attempting an already completed external action (such as pushing an up-to-date branch) must report success without redundant side effects, and requesting a build for a running worktree must join the active job.
* The system must handle replayed or stale links (resulting from context compaction or `/clear`) safely by rejecting the stale transition and returning the current valid state representation without raising fatal MCP protocol errors.

See the link:specification/workflow-dsl.adoc[Workflow DSL Specification] and link:specification/hypermedia-format.adoc[Hypermedia Format Specification] for implementation details.

[#PM-WF-5]
=== PM-WF-5: Sub-Agent Dispatch & Single-Level Leaf Constraint

Sub-agents must be dispatched as single-level leaf workers using rendered host commands, tracked deterministically by unique dispatch identifiers.

* The system must package tasks during Phase 4 (`plan`) into envelopes sized for single sub-agent context limits, delivering each envelope's current task within the sub-agent's state representation.
* The system must format `dispatch` links with fully rendered host execution structures, supplying `host_tool`, `params`, and a structured `prompt` body specifying `name`, `dispatch_id`, `plan_id` or `epic_id`, `entity`, `skills[]`, `WORKTREE`, and initial state command `start: pm_state(...)`.
* The system must enforce the single-level leaf constraint: sub-agents operating within entity scopes are terminal workers and must never receive `dispatch` links or spawn child sub-agents.
* The system must require sub-agents to persist deliverables via their own `submit` links and return a structured completion status to the parent session: `status` (`success`, `error`, `loop_back`, `blocked`, `harness_cancellation`), `display_detail` (maximum 80 ASCII characters, no trailing period), and optional `token_usage`. Missing token usage must be recorded as unmeasured rather than zero.
* The system must track sub-agent lifecycles using unique `dispatch_id` tokens: mark the dispatch claimed upon the sub-agent's first entity-scoped call, re-offer unconfirmed or timed-out dispatches with a new `dispatch_id`, and immediately reject submissions referencing superseded `dispatch_id` tokens.
* The system must equip reader sub-agents (used for untrusted external content ingestion) with strictly read-only capabilities and zero MCP transition tools, requiring candidate data to be passed as plain text to the dispatching session for server-side schema validation.

See the link:specification/dispatch-and-effort.adoc[Dispatch & Effort Specification], link:specification/workflow-dsl.adoc[Workflow DSL Specification], and link:specification/client-profiles.adoc[Client Profiles Specification] for implementation details.

[#PM-WF-6]
=== PM-WF-6: Independent Server-Side Transition & Parameter Validation

The workflow engine must strictly validate all transition attempts and free parameters server-side, treating client calls as untrusted input.

* The system must validate every incoming `pm_do` invocation against the persisted state of the addressed scope independently of how the client constructed the request.
* The system must verify that the requested link ID exists within the set of valid transitions for the current state and that any addressed entity is currently in an accepting sub-state.
* The system must validate all supplied free parameters (`args`) against the link's closed JSON schema, enforcing `additionalProperties: false` and strict type conformity.
* For `submit` transitions carrying document or prose payloads (such as `outline.md`, `request.md`, Conventional Commit messages, PR bodies, or ADR AsciiDoc), the system must run the domain validator (`OutlineValidator`, `AsciiDocValidator`, `ConventionalCommitValidator`) in-process on the submitted parameter before atomically persisting the target store, making unvalidated store writes structurally impossible.
* The system must reject any invalid transition, malformed parameter payload, or failed content validation with a structured validation error payload that includes the rejection cause and the current, unmutated state representation.

See the link:specification/workflow-dsl.adoc[Workflow DSL Specification], link:specification/hypermedia-format.adoc[Hypermedia Format Specification], and link:specification/phase-workflows.adoc[Phase Workflows Specification] for implementation details.

[#PM-WF-7]
=== PM-WF-7: Worktree-Constrained Loop-Back & Iteration Bounds

Remediation loops from finalize back to execution must be strictly bounded and confined to active worktrees.

* The system must allow `loop_back` transitions returning a plan from Phase 6 (`finalize`) to Phase 5 (`execute`) only while the plan remains located within its dedicated worktree.
* The system must eliminate `loop_back` transitions by link omission immediately once the plan passes the pre-merge barrier and relocates back to the main checkout.
* The system must allocate fresh, additive remediation tasks and envelopes within the worktree for each loop-back iteration, never reopening previously completed tasks, and must assign fresh dispatch IDs to preserve additive metric accounting.
* The system must enforce an automated loop-back iteration cap governed by project configuration (`.plan/marshal.json -> phase-6-finalize.max_iterations`, default: 3).
* The system must transition the plan to `finalize.loop-limit-reached` when the iteration ceiling is exhausted, offering exclusively an `escalate` link requiring operator intervention.

See the link:specification/workflow-dsl.adoc[Workflow DSL Specification], link:specification/phase-workflows.adoc[Phase Workflows Specification], and link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.

[#PM-WF-8]
=== PM-WF-8: Asynchronous Job Links & Wait Transitions

Long-running subprocesses and external provider waits must be modeled as asynchronous jobs with bounded polling transitions.

* The system must transition immediately to an asynchronous running state (`*.running`) upon initiating a long-running subprocess (builds, CI status checks, review-bot rate windows, merge queues), returning a representation containing `wait:<job_id>` and `cancel:<job_id>` links.
* The system must implement the `wait` link transition as a bounded blocking operation that returns either the completed outcome representation or an updated running representation with fresh progress metrics.
* The system must support extended wait intervals with periodic MCP progress notifications when the client profile indicates host support and the request includes a progress token.
* The system must restrict asynchronous job outcomes to a closed enumeration: `succeeded`, `failed`, `refused`, `cancelled`, `timed_out`, `killed`, and `indeterminate`.

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification] and link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-WF-9]
=== PM-WF-9: Composite Wait States & Short-Circuit Failure Handling

Concurrent asynchronous operations during finalization must be coordinated through unified composite wait states with immediate failure short-circuiting.

* The system must represent concurrent finalize operations (such as parallel CI pipeline execution and automated review-bot analysis) as a single unified composite state (`finalize.concurrent-wait`).
* The system must display discrete progress facts for all concurrent operations within the composite representation's `facts` block (e.g. `ci: running`, `review: pending`) and expose a single composite wait transition `wait:finalize.concurrent-wait`.
* The system must immediately short-circuit the composite wait upon detecting a hard failure in any constituent job (such as a red CI pipeline): cancel all remaining pending wait jobs, and transition the representation directly to a failure state providing `fix` and `loop_back` links.

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification], link:specification/workflow-dsl.adoc[Workflow DSL Specification], and link:specification/phase-workflows.adoc[Phase Workflows Specification] for implementation details.

[#PM-WF-10]
=== PM-WF-10: Phase 1–4 Planning Invariants, Lane Ratchet & Artifact Gates

Planning phases (`phase-1-init` through `phase-4-plan`) must enforce deterministic artifact gates, main-checkout cleanliness, and a one-way planning lane ratchet.

* The system must support multiple plan initialization sources in `pm_start` (`request`, `issue` fetched via CI job, `lesson` with premise check and file relocation, and `recipe` with a deterministic timestamp suffix), while rejecting phantom plan IDs shaped like UUIDs or lesson IDs.
* The system must enforce a clean primary checkout (`git status --porcelain` outside git-ignored `.plan/local/`) at every planning phase transition and transition to an operator-blocked state (`*.blocked`) if `.plan/marshal.json` has uncommitted modifications.
* The system must refuse transitions out of `phase-2-refine`, `phase-3-outline`, or `phase-4-plan` unless the phase's required artifact exists and passes structural validation (with `--allow-bare-transition` exemptions restricted to the operator channel).
* The system must enforce a one-way planning lane ratchet (`light` -> `deep`): the light lane enforces a bounded read set (cap 25 files, band 8 modules), unknown scope estimates bias to `deep`, and light-to-deep escalation executes as a first-class engine transition.
* The system must ensure `phase-2-refine` only widens active skill domains, `phase-3-outline` narrows them at most once, and a pull-request title is present from `phase-2-refine` onward.
* The system must compute `phase-4-plan` task derivation (profile mapping, dependency DAG cycle detection, skill resolution, and atomic task creation) deterministically over structured deliverables, using the same resolver for posture preview and execution manifest composition.

See the link:specification/phase-workflows.adoc[Phase Workflows Specification] for implementation details.

[#PM-WF-11]
=== PM-WF-11: Q-Gate Validation Loop, Change-Type & Scope-Deviation Contracts

Quality gates, change-type classification, and scope-deviation handling must be governed by deterministic server validators and closed enumerations.

* The system must enforce a single writer for `change_type` (a closed enum of six values), falling back to a guided judgment `submit` link when the deterministic heuristic is ambiguous, and refusing transitions when plan-level scope and deliverable-level scope disagree.
* The system must execute Q-Gate validation loops (`off`, `once`, `until_clean`) in the engine with a hard cap of 3 iterations, a content-hash rerun gate, an immediate exit when pending blocking findings reach zero, and a deterministic surgical-change bypass predicate.
* When an executing sub-agent encounters a scope deviation, the system must require a structured deviation submission (`hold`, `accept`, or `split`), transition the task to a blocked state awaiting batched operator consent via elicitation, require a persisted rationale included in the PR body for `accept`, and automatically seed a lesson for `split`.

See the link:specification/phase-workflows.adoc[Phase Workflows Specification] for implementation details.

[#PM-WF-12]
=== PM-WF-12: Routine User Dialogue vs Operator-Authorizing Elicitation

The workflow engine must distinguish routine informational user choices from security- or scope-authorizing operator decisions.

* The system must model routine user interactions during planning (such as existing-plan handling, recipe choice, ambiguous domain selection, sibling collision resolution, posture selection, and batched refine clarifications) as `*.awaiting_user` states with typed question schemas, asking clarifications in a single batch and allowing at most one refine re-dispatch.
* Where a host does not support MCP elicitation for routine non-authorizing choices, the system may accept answers relayed by the model and must record the relay provenance in the audit log.
* For authorizing decisions (outline approval in `outline.review`, scope-deviation acceptance, handshake drift override, pre-merge authorization, and plan deletion), the system must strictly require MCP elicitation or the operator CLI (`PM-SEC-3`), never accepting model-relayed approvals.

See the link:specification/phase-workflows.adoc[Phase Workflows Specification] and link:specification/daemon-endpoint.adoc[Daemon Endpoint Specification] for implementation details.

[#PM-WF-13]
=== PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier

Phase 6 (`phase-6-finalize`) must execute steps according to compile-time-verified ordering bands, preserve valid step verdicts across rebases, and gate branch merge on a fail-closed barrier.

* The system must organize finalize steps into five strict ordering bands verified at build time against order collisions, read-after-destroy hazards, and mutual exclusions:
** *Settle band (`order < 11`)*: `sync-baseline` (3), `simplify` (5), `security-audit` (7), `self-review` (8), `architecture-refresh` (9), `pre-push quality gate` (10).
** *Push boundary (`order == 11`)*: `push` (11), gated on working-tree build freshness.
** *Concurrent wait & triage region (`11 < order < 70`)*: `create-pr` (20), `ci-verify` (22), `automatic-review` (30), `sonar-roundtrip` (40), unified finding triage (`triage:F-n`), and `adr-propose` (62).
** *Merge gate (`order == 70`)*: `branch-cleanup` (70).
** *Post-run band (`order > 70`)*: `lessons-capture` (991), `preference-emitter` (992), `record-metrics` (998), `phase-breakdown` (999), `emit-landing` (1000), and `archive-plan` (1100).
* The system must record `head_at_completion` for every completed finalize step and evaluate verdict currency (`verdict_currency`) across rebases so a step verdict is retained when a `HEAD` advance does not touch its declared `verdict_inputs`.
* The system must enforce a fail-closed pre-merge review barrier in `branch-cleanup` (70); any operator merge authorization grant must be cryptographically bound to both the current `HEAD` SHA and the specific gap class.

See the link:specification/phase-workflows.adoc[Phase Workflows Specification] for implementation details.

[#PM-WF-14]
=== PM-WF-14: Dispatch Envelopes, Return Observability & Effort Role Resolution

Sub-agent dispatches must pack tasks into context-budgeted envelopes, track dispatch lifecycles through explicit `dispatch_id` return links, and resolve model/effort levels from a role registry.

* The system must bin-pack implementation tasks at plan time into context-sized *task envelopes* (`pack-envelopes`); each task `submit` within an envelope must return the representation of the envelope's next pending task.
* The system must assign a unique `dispatch_id` to every rendered `dispatch` link, mark it claimed on the first entity call carrying that ID, and require the dispatching session to report sub-agent completion via a `returned:<dispatch_id>` link carrying `status`, `display_detail`, and host `token_usage`.
* The system must record missing sub-agent token usage as `unmeasured` (never as `0`), flag any reported `success` where the target entity was not submitted, and allow safe re-dispatch of unconfirmed dispatches.
* The system must resolve the sub-agent effort level (levels 1–7 and `inherit`) from a hierarchical role registry (`plan.<phase>.effort.<subkey>` -> phase default -> plan default -> `inherit`, with an orchestrator `max` clamp) rendered via the active client profile and local `effort-ladder.json`, and must never emit a variant name that is not installed.

See the link:specification/dispatch-and-effort.adoc[Dispatch & Effort Specification] and link:specification/client-profiles.adoc[Client Profiles Specification] for implementation details.

[#PM-WF-15]
=== PM-WF-15: Epic Plan Emission & Cross-Plan Merge Mutex

Orchestrator epics and concurrent plans must coordinate safely across sessions without sub-agent nesting violations or merge races.

* The system must expose staged epic plans via an `emit:<plan_id>` link that returns the operator entry command rather than dispatching a full plan as a sub-agent, observing the child plan's `running` state from its `mcp/entry.json` record.
* The system must serialize concurrent plan rebases and merges within a repository through a daemon-owned, per-repo main-anchored FIFO admission queue and merge mutex (`<repo_main>/.plan/local/locks/merge-mutex.json`, storing both `waiting` FIFO admission entries and co-tenanted per-bot `rate_windows` claims without coupling rate-window waits to the merge mutex) that holds across the rebase-to-merge critical section, automatically releases whenever the plan enters a wait state, and reclaims expired lock budgets.

See the link:specification/dispatch-and-effort.adoc[Dispatch & Effort Specification] and link:specification/phase-workflows.adoc[Phase Workflows Specification] for implementation details.

[#PM-WF-16]
=== PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push

Multi-step domain sub-processes must be modeled as reusable, parameterized compound sub-workflows (`scope subworkflow`) invoked over a persisted call stack rather than duplicated across phase state graphs.

* The system must support reusable compound sub-workflows (`scope subworkflow`) invoked via parameterized `call <subworkflow_id>(<param_bindings>)` states, persisting the active call stack (`call_stack`) in `mcp/status.json` so interactive pauses, asynchronous job waits, and crash recovery inside a sub-workflow preserve the caller's phase, return state, and bound parameters.
* The system must verify at build time that the sub-workflow call graph across all `*.pmwf` definitions is a strict directed acyclic graph (DAG) with maximum call-stack depth $\le 4$, and that every `call` state's `on <outcome> -> <target_state>` clauses form an exact 1-to-1 bijection with the target sub-workflow's declared `terminal <outcome>` states.
* The system must provide a canonical reusable `git.commit_and_push` sub-workflow (`git-commit-and-push.pmwf`) shared across Phase 5 (`execute` deliverable chain-tail and remediation commits), Phase 6 (`finalize` settle-step commit instrumentation, `push` barrier, and post-PR re-push), `pr-doctor`, `marshall-steward`, and `plan-orchestrator`.
* The `git.commit_and_push` sub-workflow must execute the complete config-driven git commit and push lifecycle:
** Inspect working-tree changes (`git status --porcelain`) in the resolved worktree or primary checkout; when the working tree is clean, either return `clean` immediately (`push_mode=never`) or proceed directly to the push barrier (`push_mode=if_configured` or `always`).
** Detect and clean build/temp artifacts against `artifact-patterns.json` while respecting `.gitignore` (failing closed if the `.gitignore` oracle fails), unconditionally excluding `.plan/**` and nested git worktrees/submodules, auto-deleting `safe` untracked artifacts, and pausing in an interactive `git.artifact-review` state only when `uncertain` tracked artifacts or prohibited secret files are detected.
** Resolve and validate the commit message in-memory (using either a caller-supplied deterministic template or an interactive `git.compose-message` `submit` transition with diff-derived `type`/`scope` facts), validate Conventional Commits syntax, and deterministically append the configured `Co-Authored-By` trailer (`commit-trailer`, default `Co-Authored-By: plan-marshall <noreply@cuioss.de>`).
** Stage scoped paths and execute `git -C <tree> commit -F -` by streaming the UTF-8 commit message over `stdin`, capture the new `commit_sha` and git-sourced `changed_paths`, append a `kind="change"` entry to `change-ledger.jsonl`, and—when invoked from a Phase 6 `mutates_source: true` step—re-stamp `head_at_completion` on `head_dependent: true` steps and record a `freshness_reconcile` entry for steps at `order >= 10`.
** Evaluate push policy from caller parameters (`push_mode`: `never`, `if_configured`, `always`, `post_pr_conditional`) and `.plan/marshal.json` (`phase-5-execute.commit_and_push`, default `true`), enforce the `pre-commit-verify-freshness` gate and `branch-sync-state` parity probe (`ahead`, `synced`, `remote_absent_landed`, `remote_absent_unverified`) before pushing, and transition to structured recovery states (`git.commit-fix` on pre-commit hook failure, `git.sync-required` on non-fast-forward rejection) before returning a closed terminal outcome (`committed_local`, `committed_and_pushed`, `pushed_clean`, `clean`, or `aborted`) to the caller state.

See the link:specification/workflow-dsl.adoc[Workflow DSL Specification], link:specification/phase-workflows.adoc[Phase Workflows Specification], and link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.
