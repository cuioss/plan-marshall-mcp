== Implementation Architecture & Core Subsystems (PM-IMPL)

[#PM-IMPL-1]
=== PM-IMPL-1: Decoupled Plain-Java Core Engine & Quarkus Assembly

To guarantee fast unit test execution, clean architectural boundaries, and framework independence, the code must separate domain logic from the Quarkus runtime assembly, and the private part of the product must be no more than that assembly and the model-facing content.

* The code must be organised in the repositories and modules of the link:specification/module-structure.adoc[Module Structure Specification], the only listing of the repositories, the modules, their responsibilities and allowed dependencies: the parent POM in `pm-mcp-parent`; the client contract, the two command-line modules, the job launcher, and the web application in `pm-mcp-clients`; the plain-Java engine with the providers and the framework-free daemon logic in `pm-mcp-core`; the Quarkus daemon assembly `pm-mcp-server` with the model-facing content and the tests over all four binaries in `plan-marshall-mcp`; and every document in `plan-marshall-documentation`. Every module carries minimal real code and tests. One release produces four binaries: `pm-mcp` (the relay and the other host- and model-facing verbs, built by `pm-relay`), `pm-operator` (the operator CLI, built by the module of the same name), `pm-mcpd` (the daemon, built by `pm-mcp-server`), and `pm-exec` (the job launcher).
* Every repository must deploy its artifacts to the Maven registry of the GitHub organisation `plan-marshall` and to no other place, never to Maven Central or another public registry; the artifacts carry the group id `de.planmarshall`, and every Java package lies below `de.planmarshall`; the two library repositories deploy `SNAPSHOT` versions only and only the parent is released; a repository consumes the artifacts of another only from that registry and only in the order parent, clients, core, product (link:specification/module-structure.adoc#artifact-flow[Module Structure § Artifact Flow]).
* `plan-marshall-mcp` must be private before the first model-facing content is committed to it, and it is the only repository that must be private while the product is developed. It must hold no class that works without a Quarkus, CDI, Vert.x, or MCP type; such a class belongs to a library module. The model-facing content (the default workflow units, the shipped role set, the skill corpus, the client bundles) must be resources of `pm-mcp-server` and must not be part of any artifact of a public repository (link:specification/module-structure.adoc#model-facing-content[Module Structure § Model-Facing Content]).
* The daemon's logic that needs no framework must live in the library module `pm-runtime`, which depends on `pm-core` only among the PM-MCP modules: the implementations of the service interfaces of `pm-core` (job execution, secret resolution, plan locking), the runtime start sequence, the credential stores, the worker supervisor and the launch composition, the language server pool, and the ingestion validator.
* Domain logic must live in plain-Java library modules without Quarkus, CDI, MCP libraries, JGit, or `cui-http`: the foundation `pm-core` (service interfaces and the `Primitive<P, R>` SPI, the provider-neutral findings and code-analysis contracts, state stores, configuration, client profile translation, the TOON encoder) and, on top of it, `pm-workflow` (the workflow DSL parser, validator and diagram generator, the interpreter, the hypermedia state engine, and the plan-domain primitives; the default workflow units it loads are content of the assembly). Both depend only on the JDK, Jackson, and `cui-java-tools` (and `pm-workflow` on `pm-core`); the one exception is `pm-core`'s dependency on `pm-api`, used only for the compiled host-detection table its client profiles read (`PM-CLIENT-3`).
* The client contract of the daemon's REST API must be a module of its own (`pm-api`) that depends only on the streaming API of `jackson-core`, never on `jackson-databind`, and holds no engine or store code, so no client can reach them; beside the contract it holds what both command-line binaries share: the minimal HTTP/1.1 and Server-Sent Events client over the daemon's Unix domain socket (JDK `SocketChannel`), the on-demand start procedure (the start lock `runtime-start.lock`, the detached spawn of `pm-mcpd` by its path, the runtime-token file checks; `PM-ARCH-7`), the read-only codec of the closed list of files they read directly (`PM-ARCH-1`) with the drift checks over them (`PM-DIST-4`), and the host-detection table.
* The command line must be split by caller into two client modules: `pm-relay` builds the binary `pm-mcp` with only the harness- and model-facing verbs (`serve` including `serve --job`, and `enter`) and carries the release version, which is the bundle version, for the drift check of `enter`; `pm-operator` builds the binary `pm-operator` with every verb a human runs at a terminal, at its top level without an `operator` sub-level. Both depend on `pm-api` only, neither on the other, and both reach the daemon only through its Unix domain socket with the runtime token (`PM-SEC-4`). The split changes no verb's checks; it lets the host enforcement rule deny the whole binary `pm-operator` to the model while `pm-mcp` stays allowed (`PM-SEC-3`).
* The web adapter must be a package of `pm-mcp-server` (`de.planmarshall.mcp.server.web`) beside the local adapter, never a module, binary, or process of its own; `pm-mcp-server` depends on the web application resource module `pm-web-app` and serves it on the web listener (`PM-SEC-7`).
* The job confinement launcher `pm-exec` must use neither Quarkus nor picocli (link:specification/job-runtime.adoc[Job Runtime Specification]).
* Each provider operation must be a contract (typed input record, closed outcome enumeration including the shared transport outcomes, TOON output) in a contract module (`pm-provider-git`, `pm-provider-ci`) or, for the provider-neutral findings and code-analysis contracts whose data the stores and the workflow engine use, in `pm-core`; the implementation modules provide a native variant and, where one exists, a CLI adapter variant behind the same contract. Which variant serves an integration is set per project and integration in project setup: `native` unless the derived `git_native_capability` finds a used feature the native variant cannot serve, and only then by the operator's choice, never by a model or a content answer (`PM-SEC-3`; no automatic fallback; `PM-EXEC-5`); one variant serves all operations of an integration. The variant, the credential origin, and the timing of an operation go to its audit record, never into its model-facing result.
* The plain native-image modules (`pm-relay`, `pm-operator`, `pm-exec`) must be built with `org.graalvm.buildtools:native-maven-plugin` in a `native` profile of their own module; the one Quarkus module (`pm-mcp-server`) uses the Quarkus native build. CI must build each binary natively in the repository of its module, on Linux; the release layout is assembled in `plan-marshall-mcp` from `pm-mcpd` of its own build and the three other binaries resolved from the registry.
* The deterministic scenario replay harness (`pm-scenario`, `PM-TEST-4`) must be a test-scope part of `pm-workflow` (JUnit, in-process), not a module of its own.
* Provider resolution must use explicit registries (CI providers in `pm-provider-ci`, finding sources by source kind and code-analysis providers in `pm-core`) whose modules are passed to the registry's constructor: `pm-mcp-server` produces each registry through a CDI producer, and plain-Java tests construct it directly; no `ServiceLoader` or classpath discovery.
* Every contract with two variants must be verified by differential tests that run the same fixtures against the native and the CLI implementation and require the same outcome and TOON output (for the linked-worktree lifecycle additionally: every tree the native code writes is accepted by `git worktree list --porcelain`, `git status`, and `git fsck`, and the native code operates every tree the CLI writes); provider clients are verified against recorded responses and, out of band, by `pm-conformance`.
* Dependency direction must flow strictly toward `pm-core` as stated in link:specification/module-structure.adoc#dependency-rules[Module Structure § Dependency Rules]: no provider module depends on `pm-workflow`, no client module on `pm-core`, `pm-workflow`, or a provider module (`pm-relay` and `pm-operator` depend on `pm-api` only), and `pm-core` on no other PM-MCP module except `pm-api`. `pm-core` must define service interfaces (e.g., job execution, plan locking, secret resolution) implemented by `pm-runtime`. The direction must be enforced by an automated build check in every code repository. Because `pm-workflow` sees neither the `git.*` and `ci.*` primitives the provider modules contribute nor the default units, the build-time validation of every workflow unit against the assembled primitive catalogue runs in `pm-mcp-server`; the native-image reachability metadata of plain JGit (`PM-TECH-2`) and of the provider records is registered there as well.
* Unit tests in the plain-Java library modules (e.g., `test -pl pm-core` in `pm-mcp-core`) must execute directly on the JVM without Quarkus augmentation, and an automated build test in `pm-mcp-server` must verify that every persisted Java record in `pm-core`, `pm-workflow`, `pm-runtime`, and the provider modules is registered for GraalVM native reflection.
* All modules must share a unified `LogRecord` numbering registry defined in `pm-core`, and every module must independently satisfy project test coverage minimums.

See the link:specification/module-structure.adoc[Module Structure Specification], link:specification/workflow-dsl.adoc[Workflow DSL & Engine Specification], link:specification/job-runtime.adoc[Job Runtime Specification], and link:specification/phase-workflows.adoc[Phase Workflows & Finalize Specification] for implementation details.

[#PM-IMPL-2]
=== PM-IMPL-2: Versioned JSON/JSONL Storage & TOON Wire Output

The system must separate internal persistence formats from model-facing wire representations, optimizing disk storage for schema evolution and wire output for token efficiency.

* All server-owned machine state must be persisted as canonical JSON documents (one file per entity, such as `status.json`, `references.json`, `TASK-NNN.json`, `jobs/<job_id>.json`) or append-only JSONL logs (`findings.jsonl`, `change-ledger.jsonl`, `sessions.jsonl`, `audit.jsonl`) serialized via Jackson 2 over Java records. A JSONL log whose records change (`findings.jsonl`, `review-participation.jsonl`) stays append-only: every change appends the full record again, the current record is the last readable line of its key, and earlier lines are its history.
* Every persisted JSON document and JSONL record, including the git-tracked team configuration files (`.marshall/config/*.json`) and the operator-owned `local-config.json`, `machine-config.json`, enrolment, harness enrolment (`harnesses.json`), and credential files (`PM-CRED-3`), must carry a mandatory integer `format_version` attribute. Before 1.0 the daemon must accept exactly the current version of each file kind and refuse any other with `format_outdated` or `format_newer` naming the file; it must never migrate a store on startup, and a format bump is handled by the drain rule, the release notes, and the project setup workflow (`PM-EXT-7`); the migration mechanism for 1.0 and later is decided at 1.0.
* Narratives authored for human and model consumption (`request.md`, `outline.md`, `spec.md`, lesson bodies) must stay Markdown text; structured metadata of a narrative lives beside it (a lesson's YAML front matter, validated against a closed schema with `format_version`); the narrative of an epic landing is a Markdown field of its structured landing record, which is written as one atomic unit together with its server-derived facts, so no narrative-only landing can exist.
* Model-facing tool results and state representations must be rendered into TOON format strictly at the MCP wire boundary from the underlying Java records.

See the link:specification/store-schemas.adoc[Store Schemas Specification], link:specification/hypermedia-format.adoc[Hypermedia Format & TOON Encoding Specification], and link:specification/identifiers.adoc[Identifier Registry] for implementation details.

[#PM-IMPL-3]
=== PM-IMPL-3: Deterministic Native TOON Encoder

`PM-MCP` must implement its own zero-reflection TOON encoder for model output, avoiding external runtime bytecode generation dependencies.

* The system must implement a native, reflection-free TOON encoder in `pm-core` that is a full encoder of the official TOON specification version 4.1, pinned to release v4.1.3 (commit `a6b801a3326980ab2cb615b0ffe44457e091f7b6`), with the canonical encoder options only (comma delimiter, indentation of 2 spaces): it must emit for every value the form the official rules require (objects, inline primitive arrays, empty arrays as `key: []`, tabular arrays with field groups for nested uniform columns, the keyed tabular form for maps of uniform objects, and the list form for non-uniform arrays), quote strings minimally with the official escapes (`\u00XX` for C0 control characters without a short escape; DEL neither quoted nor escaped; no block literals), and end a document without a trailing newline.
* The TOON encoder must pass byte-exact every encode conformance fixture of the pinned release except the fixtures that set an encoder option outside the canonical options, which the conformance test lists with that reason; a newer official version is pinned only when its fixtures pass the same way.
* A reader for `plan-marshall`'s TOON dialect (supporting tab-sniffed rows, embedded JSON cells, and block scalars) must be restricted strictly to test utilities for differential test comparison (`PM-TEST-2`) and must never be part of the production code.

See the link:specification/hypermedia-format.adoc[Hypermedia Format & TOON Encoding Specification] for implementation details.

[#PM-IMPL-4]
=== PM-IMPL-4: Bounded Long-Poll & Progress-Reset Waiting Primitives

Because builds, CI runs, review-bot windows, and the waits of workers exceed typical MCP tool call timeouts across hosts, the system must provide resilient waiting primitives backed by persistent daemon jobs that survive relay termination, worker replacement, and host restarts (`PM-ARCH-8`).

* Every background job must execute inside the always-on runtime and is awaited by the engine as an event; a composite wait (such as `finalize.concurrent-wait` across CI runs and review-bot rate windows) settles when all member jobs settle or short-circuits as soon as a required job fails, and cancelling a job terminates its process group; none of these is a model link.
* The calls a model holds open must use two waiting primitives:
** *Bounded Wait*: Blocks up to a configurable duration and returns either a result or an answer to wait again; the duration stays safely below the host's idle timeout unless the host's progress notifications reset that timeout, in which case the server holds the call through its window with progress notifications.
** *Progress Wait*: Activated automatically when *both* the active client profile declares that MCP progress notifications reset the host's idle timer *and* the incoming MCP request supplies a `progressToken`; emits progress notifications periodically, never with a gap the host could read as idle; a running `pm_build` and its `job_id` continuation then block until a result or an extended upper bound, while a worker's `pm_wait` keeps its bounded window and is held through it by the notifications.
* The server must select between bounded wait and progress wait automatically without model involvement, for a worker's `pm_wait` (`PM-WORK-2`, a consultation's wait included) and for a running `pm_build`, which continues a running build via its own `job_id` argument and blocks for the bounded wait, or the progress wait where it is selected (`PM-TOOL-2`); no other polling tool exists.

The window values, their bounds, and the progress interval are defined in the link:specification/timeouts/01-job-budgets-and-waits.adoc#waits[Timeouts & Budgets Specification]; the per-host tool-call timeout thresholds and whether `notifications/progress` resets them are measured per host and recorded in the client profiles (link:specification/evaluation.adoc[Evaluation Reference]).

See the link:specification/hypermedia-format.adoc[Hypermedia Format & TOON Encoding Specification], link:specification/job-runtime.adoc[Job Runtime Specification], link:specification/timeouts.adoc[Timeouts & Budgets Specification], link:specification/mcp-tools.adoc[MCP Tool & Resource Surface Specification], link:specification/model-work.adoc[Model Work Specification], and link:specification/runtime-model.adoc[Runtime & Interaction Model Specification] for implementation details.

[#PM-IMPL-5]
=== PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation

All plan phase lifecycles, finalize sequences, and epic workflows must be defined in a declarative domain-specific language (DSL) validated at build time and on every load. Every phase unit and the sub-workflow units `git.commit_and_push`, `remediation.*`, `replan`, and `question.adjudicate` are project-owned (`.marshall/config/*.pmwf`, copied from the binary's default units by the project setup workflow; the epic, setup, lesson-maintenance, bootstrap, and source units are compiled only, link:later-improvements.adoc#_l_5_team_overrides_of_templates_and_composition_rules[Later Improvements, L-5]) so the team sees and reviews the process it runs; the process stays server-enforced because every project unit is verified against rules and invariants compiled into the binary.

* Every workflow operation must be encapsulated as a unit-testable Java primitive declaring a canonical name (e.g., `git.commit`, `ci.watch`), a typed parameter record, a sealed outcome enumeration (`ok`, `nothing_to_commit`, `hook_failed`), and explicit store/job side effects.
* Workflow state machines must be authored in `PM-MCP`'s line-based workflow DSL supporting `state`, `skill`, `link <rel> <id> (<params>)`, `do <primitive>`, `auto <primitive>`, `job <primitive>`, `guard <primitive>`, `job llm <entity_kind> role <role> [each <primitive>]` (a role named freely from the role set, `PM-WORK-1`), `consult role <role>` (a consultation the state offers, `PM-WORK-4`), `call <workflow>`, `declare <name> = <value>` (a decision parameter of a unit, within compiled bounds), `<outcome> -> <state>`, and state migration rules (`migrate <old> -> <new>`).
* Build-time unit tests (for the default units) and every load of a project's units must validate every workflow DSL definition, failing closed if any check fails (a failing project unit refuses the project's plan lifecycle with its file and line and is never replaced by a default unit):
** Every referenced primitive and vocabulary skill exists, and link free parameters match the primitive's parameter record; every role a `job llm` state or a `consult` clause names exists in the effective role set when a plan instance or epic workflow is composed (`role_undefined` otherwise, `PM-WORK-1`).
** The task protocol of `PM-WORK-2` is one compiled sub-workflow that every `job llm` state uses; no unit redefines it.
** Every sealed outcome of every invoked primitive is explicitly handled (compile-grade exhaustiveness).
** Every state is reachable from the `start` state, every non-terminal state has at least one outbound transition, and all link identifiers are unique within a state.
** Every state name present in a committed registry of previously released versions is either preserved or mapped via an explicit `migrate <old> -> <new>` rule (default units).
** A unit declares decision parameters (`declare <name> = <value>`) only where its compiled declaration schema admits them, and every declared value lies within its compiled bounds; `question.adjudicate` alone declares per decision kind `decide <kind> -> ask` or `decide <kind> -> quorum(<role>, ..., <score>)`; the project's `question.adjudicate` and `replan` units differ from the default units only in their declarations and in the roles they name, and the listed roles of every quorum declaration are `read_only` and run on pairwise different models when a plan instance or epic workflow is composed.
** Every project unit satisfies the compiled invariants of its phase: the mandatory steps and states are present, the outline gate, the Q-Gate, footprint checks, push barrier, and pre-merge barrier lie on every required path, the finalize ordering bands hold, every step completes exactly once per firing, every remediation policy's budgets stay within the compiled hard caps and its `exhausted` and `stepped_out` outcomes lead to a defined fallback, only the operator API writes waivers and every waiver lookup names a gate of the closed list, condition overlays are unchanged, and no path weakens a guarantee; project steps bind only to enrolled project scripts.
* Every plan must execute its own plan instance, a DSL unit the server composes from the templates (compiled defaults, the project-owned units, the remediation policy units, and the shipped composition rule file) and the plan's facts, which stay in their owning stores and are never duplicated: the instance carries their effect with provenance (the lane's route, pruned steps, links, and policy actions with their reason and source fact, policy calls with their bound budgets and source, gates waived with the waiver id) and a header with the digests of every input, and carries the step lists and the configuration snapshot. The instance is immutable and versioned: a closed set of composition events (`start`, `outline`, `plan`, `config_adopted`, `waiver`, `fallback`, `empty_harvest`, `replan`) composes a new version, recorded with its cause; a changed project unit reaches a running plan only when the server adopts it: the re-composed instance is adopted when it verifies and contains the current state and every state of the call stack, and kept otherwise, recorded in the audit log and the landing record; a version composed by a server event (`outline`, `plan`, `fallback`, `empty_harvest`, `replan`) is in force for the rest of its composing chain, from the transition entering its target state, and one composed by an operator or configuration event (`config_adopted`, `waiver`) from the next transition; a version is valid only when it contains the current state and every state of the call stack, keeps completed history, and passes the compiled invariants.
* A build-time generator must render every DSL workflow definition into Mermaid state diagrams and AsciiDoc state/link/outcome tables under `doc/` (plus an ASCII state/transition table for terminal output), and a CI test must fail if committed documentation drifts from the DSL definitions; the same generator renders each plan's instance in force (active state, pruned steps with their reason, waived gates with their waiver id) as a read-only resource, so the process in force is visible per plan.
* The link:specification/state-catalogue.adoc[State Catalogue] must be normatively equal to the state table the DSL diagram generator produces: the catalogue documents the default units, and a build-time drift test must fail when a state defined in any default `*.pmwf` unit is missing from the catalogue or vice versa, or when a catalogue row's phase value, kind, or exits differ from the definitions.

See the link:specification/workflow-dsl.adoc[Workflow DSL & Engine Specification], link:specification/state-catalogue.adoc[State Catalogue], and link:specification/model-work.adoc[Model Work Specification] for implementation details.

[#PM-IMPL-6]
=== PM-IMPL-6: Native Build Output Parsers & Fallback Diagnostics

To keep raw compiler and test logs out of model context while ensuring no build failure goes undiagnosed, `PM-MCP` must compile domain log parsers into the binary and provide a deterministic fallback for unparsed failures.

* The system must include compiled Java build output parsers for supported domain toolchains, one per `plan-marshall` parser module (Maven, Gradle, npm errors, TypeScript, ESLint, Jest, TAP, Python pyproject pytest/ruff/mypy, and OpenRewrite), and coverage report parsers (JaCoCo, Cobertura, LCOV, Istanbul JSON) that extract structured error locations (file path, line, column, rule/message), test summaries, and coverage metrics into the build result representation.
* If a build job exits with a non-zero status code but the domain parser extracts zero structured error items (for example, due to an early wrapper crash, network failure, or unrecognized toolchain output), the system must:
** Record the build outcome with the distinct status `failed_unparsed` (never reporting an empty error list as a clean failure).
** Attach the bounded tail of the raw build log (last 50 lines / 4 KB) and the `pm://plan/{plan_id}/builds/{job_id}/log` resource URI directly in the representation so the model or operator can diagnose the root cause.

See the link:specification/job-runtime.adoc[Job Runtime Specification] and link:specification/mcp-tools.adoc[MCP Tool & Resource Surface Specification] for implementation details.

[#PM-IMPL-7]
=== PM-IMPL-7: Data Store Invariants, Footprint Reconciliation & Lock Ordering

Persisted stores must preserve defect-driven data integrity invariants, detect out-of-band working-tree edits, and prevent deadlocks across concurrent scopes.

* The system must record a content digest (size and SHA-256) on every server write to the plan store files in the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/` in a sidecar outside the protected stores, verify it on read so any out-of-band modification by the model or external tools is detected immediately, and let the operator accept an intentional edit through the operator CLI (`pm-operator accept-edit`, addressing a plan, epic, or workspace store, a lesson, or an enrolment), which shows the path and the recorded against the current size and SHA-256 before confirmation (no diff, because prior content is not kept). A mismatch raises the `integrity_breach` condition (`PM-WF-3`), which pauses the scope; its resolutions are closed: `accept-edit` (after which the engine re-verifies before clearing it), or the operator verb `abort` for a plan or epic; a workspace store, a lesson, or an enrolment is resolved only by `accept-edit`, and while a lesson is unverified the lesson source of a plan bootstrap fails with the reason. Tampering must be decided only under the store's lock; a lock-free reader that sees a mismatch must report it as unverified.
* The system must make every multi-store write of a plan, epic, or workspace scope crash-consistent through a per-scope transaction journal that is written and synced before the stores and rolled forward on recovery; a transaction that also writes outside its scope (such as the creation of a plan with its epic queue row, its lesson claim, and the deletion of its pending entry, or a job start with the scope's `active_job`) must write in a fixed order, the authoritative store first, and the runtime must derive every later write of that order from the authoritative store at startup, so a crash between the writes is completed by recovery and never leaves two stores disagreeing; the system must record digests only through the journal, and repair a torn last line of an append-only JSONL store only at the tail, under the store's lock, with an audit record.
* The system must implement three-way file footprint reconciliation in `references.json` comparing (1) declared files, (2) structured deliverable-derived files (partitioned into three disjoint sets: expected modifications, conditional modifications, and read-only references), and (3) git-realized modified files pairwise by symmetric difference in both directions; a realized footprint whose recorded state is not `measured` must be reported as indeterminate, never as clean.
* The system must apply a lesson to a plan by claiming it in the lesson store when the plan is created, never by moving the lesson file: the claim is turned into an in-file retirement (`applied`) only when the plan ends `merged`, and released when it ends `returned`, `handed_back`, `no_change`, or `aborted` or is deleted (`delete-plan`), so a plan deletion never needs to carry a lesson back.
* The system must serve read-only store queries from lock-free atomic file snapshots.
* The system must hold short transaction locks only for the duration of one transaction and acquire all locks in one total order: workspace -> plan locks (lexicographic by `plan_id`) -> epic locks (lexicographic by `epic_id`) -> `epics-worktree` -> lesson store (`<PM_MCP_BASE>/projects/<project_id>/locks/lessons.lock`, held for lesson id allocation and every lesson write) -> local configuration (`locks/local-config.lock`) -> derived facts (`locks/derived-facts.lock`) -> build timings (`locks/build-timings.lock`) -> task queue (`locks/queue.lock`, held for queue task and worker records) -> machine store locks (alphabetical by lock path, the per-project enrolment locks lexicographic by `project_id`) -> leaf locks (audit log, plan mailboxes, digest sidecars; nothing is acquired after a leaf lock). The lock manager must assert this order on every acquisition and refuse an out-of-order acquisition as `internal_fault` with an audit record, covered by a unit test.
* The system must guard every store that is replaced by atomic rename with a sibling lock file, never with a lock on the store file itself; only the append-only stores that carry their own leaf lock (the audit log and the plan mailboxes) may be locked directly.
* The system must represent long-lived coordination claims (merge mutex, review-bot rate windows, build slots, model slots, and task leases per worker generation, `PM-WORK-2`) as persisted lease records that are claimed and released under a short transaction lock and never held as OS locks while other locks are acquired.
* The system must place workspace, plan, epic, epic worktree, lesson store, local configuration, derived facts, build timings, and task queue locks at fixed paths of the per-project machine store outside the directories they protect (`<PM_MCP_BASE>/projects/<project_id>/locks/`), so that no worktree or per-worktree copy ever splits a lock.
* The runtime must route every lock acquisition through a single lock manager that combines one in-process lock per lock key with at most one OS `FileChannel.lock()` per lock file, the OS lock serving only as the cross-process guard: the runtime is the only store writer, and the command-line binaries `pm-mcp` and `pm-operator` take no store or scope lock (their only lock is `runtime-start.lock`, a process lock outside the transaction order).
