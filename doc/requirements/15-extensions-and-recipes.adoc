== Domain Extensions, Architecture & Recipes (PM-EXT)

[#PM-EXT-1]
=== PM-EXT-1: Four-Axis Domain Descriptors (Axes A–D)

In the legacy architecture, domain bundles supply runtime Python classes (`extension.py`) loaded via `importlib`. Because `pm-mcp` compiles to a closed-world GraalVM native binary (`PM-TECH-3`), domain extensions must be modeled as compiled sealed Java interfaces and declarative domain descriptors across four orthogonal axes (preserving ADR-004 and ADR-013).

* The system must define sealed Java interfaces and declarative domain descriptors partitioning domain responsibilities across four orthogonal axes:
** *Axis A (Skill Loading & Profile Mapping)*: Maps domain profiles (`implementation`, `module_testing`, `integration_testing`, `security`, `documentation`, `code_review`, `audit`), triage (`skill://pm/triage/<domain>`), and outline guidance to static vocabulary skills (`skill://pm/domain/<domain>/<topic>`).
** *Axis B (File-to-Build Routing & Module Applicability)*: Evaluates declarative module applicability rules (`applies_to_module` predicates over build system, dependency coordinates, and file globs) and routes modified file paths to canonical build verification commands.
** *Axis C (Module Dependency Edge Derivation)*: Derives inter-module dependency edges from build descriptors (Maven POM, Gradle, `package.json`, `pyproject.toml`), documentation cross-references, and warm LSP symbol queries.
** *Axis D (Path Attribution)*: Claims ownership over repository path prefixes (`claim_paths`, such as `.plan/` or container directories) using constant prefix declarations.
* The system must never dynamically load arbitrary in-process Python or JVM bytecode from project or plugin directories at runtime.
* The system must keep the domain-detection glob dialect (Axis A/B) and the build-map `fnmatch` dialect separate so existing module routing behavior is preserved identically.

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] for implementation details.

[#PM-EXT-2]
=== PM-EXT-2: Provenance-Preserving Edge Derivation & Path Attribution Merges

When multiple domain resolvers contribute module dependency edges or path-prefix claims across a repository, the server must merge their outputs deterministically while preserving provenance and rejecting conflicting ownership claims (preserving ADR-014).

* The system must merge Axis C dependency edges across all active resolvers by set union while recording the contributing resolver provenance on every edge (`_derivation_merge`).
* The system must merge Axis D path-prefix claims (`_path_attribution_merge`) and resolve file ownership by longest-prefix match.
* The system must fail closed and report a deterministic configuration collision error if two distinct domains claim the exact same path prefix.

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] for implementation details.

[#PM-EXT-3]
=== PM-EXT-3: Module Discovery, Build Map & Architecture Enrichment

Project setup, module discovery, verification derivation, and architectural enrichment must be managed as server-owned resources and state transitions rather than prose-driven steward scripts.

* The system must discover project modules deterministically by parsing build descriptors and executing enrolled discovery jobs (cached per commit), exposing the module inventory, dependency graph, and impact neighborhood as read-only MCP resources (`PM-TOOL-3`).
* The system must maintain a write-once, fail-closed build map (`derive-verification`) mapping file globs, roles, and build classes to the required module and whole-tree verification set for any realized file footprint.
* The system must expose architectural enrichment (module responsibility, purpose, key packages, and rationale) as judgment `submit` links, enforcing a completeness guard that every discovered module is enriched before setup completes.
* The system must provide a dedicated project setup workflow state machine replacing the legacy `marshall-steward` wizard.

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-EXT-4]
=== PM-EXT-4: Declarative Recipe Model & Tier-1 Init Routing

Recipes represent repeatable, domain-invariant or domain-specific maintenance campaigns (such as `simplify-codebase`, `security-audit`, `code-review`, `agentfile-hygiene`, `lesson-cleanup`, `doc-verify`).

* The system must represent built-in and domain recipes as declarative recipe descriptors specifying trigger keywords, target scope parameters, deterministic deliverable mapping rules, and judgment states.
* During `phase-1-init`, the system must run Tier-1 deterministic recipe-match scoring across the registered recipe catalog ahead of general planning-lane routing, offering a recipe selection link when the score crosses the configured threshold while never overriding an explicit operator recipe choice.
* When a recipe plan is initialized, the system must append a deterministic timestamp suffix to the derived `plan_id` to prevent git branch collisions across repeated runs of the same recipe.

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] and link:specification/phase-workflows.adoc[Phase Workflows Specification] for implementation details.

[#PM-EXT-5]
=== PM-EXT-5: Out-of-Process Project Script Jobs & Domain Workers

Projects may define custom finalize steps (`finalize-step-*`), project-local recipes (`recipe-*`), or domain workers (custom log parsers or module discovery for languages not compiled into the release binary).

* The system must execute project-local extension code exclusively out of process as enrolled `project_script` jobs (`PM-EXEC-2`) with a declared JSON input argument schema and a validated JSON output schema.
* The system must require explicit operator enrolment (executable path, script SHA-256 digest, and argument schema in `~/.plan-marshall/mcp/enrolments.json`) before any project script job or custom domain worker can execute.
* Domain-specific internal capabilities (such as marker scanning or OpenRewrite log parsing) must be invoked only when declared by an active domain descriptor and must remain invisible when absent (preserving ADR-010).

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] and link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-EXT-6]
=== PM-EXT-6: Three-Way Configuration Split (Project, Enrolment, Server State)

In legacy `plan-marshall`, `marshal.json` mixed git-tracked project preferences with executable command strings and local runtime state. In PM-MCP, configuration is partitioned by trust boundary so no model-writable file can influence what binary or command executes on the host.

* The system must partition configuration across three disjoint stores:
** *Project Configuration (`.plan/marshal.json`, git-tracked)*: Holds non-executable project settings — enabled skill domains, workflow posture knobs (`*_without_asking`, lane defaults, `phase-6-finalize.max_iterations`), build-map routing globs, and `{tool}.acceptable_warnings`.
** *Operator Enrolment (`~/.plan-marshall/mcp/enrolments.json`, operator-only)*: Holds security-critical execution bindings — enrolled repository roots, build wrappers, pinned host tool paths and SHA-256 digests, and allowed argument templates.
** *Server State (`.plan/local/` and `~/.plan-marshall/mcp/`)*: Holds workflow status, learned adaptive build timeouts, lock state, and audit logs.
* The system must never read executable paths, wrapper names, or shell command strings from `.plan/marshal.json` or any other file in the repository working tree.

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] and link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.

[#PM-EXT-7]
=== PM-EXT-7: Versioned Command-Pattern Configuration Upgrades & Zero-CoT Reconciliation

Upgrades to the core project configuration (`.plan/marshal.json`) must be executed through a deterministic, version-tracked Command-Pattern pipeline inside the server rather than ad-hoc one-shot scripts or LLM-orchestrated multi-step CLI sequences.

* The system must maintain an explicit `system` tracking block in `.plan/marshal.json` recording `schema_version` (monotonically increasing integer), `baseline_version` (epoch compaction floor), `applied_migrations` (ordered list of applied migration command identifiers above `baseline_version`), `provisioned_binary_version`, and `config_seed_fingerprint` (SHA-256 digest of compiled-in defaults and enabled domain `config_defaults`).
* The system must encapsulate every version-specific structural or value migration ($v-1 \to v$) as an isolated, idempotent Java command implementing a sealed `ConfigMigrationCommand` interface (`targetVersion()`, `migrationId()`, `description()`, `execute(ObjectNode, MigrationContext)`), operating on the raw JSON AST prior to typed deserialization so runtime configuration records (`MarshalConfigRecord`) remain free of deprecated fields and legacy compatibility branches.
* The system must execute all `.plan/marshal.json` updates through a single atomic in-process reconciliation pipeline (`ConfigReconciler`) that sequentially runs:
** Pending `ConfigMigrationCommand` instances where `targetVersion > system.schema_version` in strictly ascending version order, preserving operator overrides losslessly.
** Non-destructive write-once default seeding (`syncDefaults`) from compiled-in defaults and enabled domain `config_defaults`.
** Deterministic canonicalization of `plan.phase-6-finalize.steps` order (`stepsSort` by `FinalizeStepDescriptor.order()`) and canonical top-level/nested JSON key order (`normalizeKeys`).
** Registry and schema post-condition validation (such as verifying configured review-bot tokens against registered bot kinds).
** Conditional atomic write-and-rename that persists `.plan/marshal.json` if and only if the canonical JSON content or `system` stamps changed.
* The system must prevent configuration upgrade clutter in the model's Chain of Thought (CoT) and codebase:
** Vocabulary skills and workflow prompts must never contain prose instructions for historical field migrations or multi-step CLI choreography (retiring separate model-invoked `sync-defaults`, `steps-sort`, `normalize-keys`, and `migrate-*` calls).
** When `system.schema_version` and `system.config_seed_fingerprint` match the running binary, configuration verification at plan startup or phase handshakes must execute as a silent $O(1)$ check emitting zero context tokens.
** Migration commands at or below `MINIMUM_SUPPORTED_SCHEMA_VERSION` must be retired at major epoch boundaries and compacted into `system.baseline_version`, bounding the size of both `system.applied_migrations` and the active command registry.
* When a `.plan/marshal.json` upgrade modifies configuration consumed by an in-flight plan's `execution-manifest.json`, the server must automatically re-compose the stale `execution-manifest.json` at the next phase handshake.
* Automated build-time JUnit tests (`PM-TEST-3`) must verify that registered `ConfigMigrationCommand` implementations form a contiguous, gap-free integer sequence from `MINIMUM_SUPPORTED_SCHEMA_VERSION + 1` to `CURRENT_SCHEMA_VERSION` with unique identifiers and 100% idempotency on re-run.

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] and link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.
