== Domain Extensions, Architecture & Recipes (PM-EXT)

[#PM-EXT-1]
=== PM-EXT-1: Four-Axis Domain Descriptors (Axes A–D)

In `plan-marshall`, domain bundles supply runtime Python classes (`extension.py`) loaded via `importlib`. Because `pm-mcpd` compiles to a closed-world GraalVM native binary (`PM-TECH-3`), domain extensions must be modeled as compiled sealed Java interfaces and declarative domain descriptors across four orthogonal axes (preserving `plan-marshall` ADR-004 and ADR-013).

* The system must define sealed Java interfaces and declarative domain descriptors partitioning domain responsibilities across four orthogonal axes:
** *Axis A (Skill Loading, Profile Mapping & Module Applicability)*: Maps domain profiles (`core`, `implementation`, `module_testing`, `integration_testing`, `quality`, `documentation`, `security`), triage (`skill://pm/triage/<domain>`), and outline guidance to static vocabulary skills (`skill://pm/domain/<domain>/<topic>`), and evaluates declarative module applicability rules (`applies_to_module` predicates over build system, packaging, dependency coordinates, module path, and file existence; AND within a rule, OR across rules) that decide which domains apply to a module. Each profile carries `defaults` and `optionals` skill lists, the `core` profile is merged into every profile, and an additive domain names the parent domain it extends (`additive_to`).
** *Axis B (File-to-Build Classification)*: Owned by build-system extensions (`maven`, `gradle`, `npm`, `pyproject`), never by language or content domains (`plan-marshall` ADR-004): declares explicit `(glob, role)` routes and classifies changed file paths into `(role, build_class)` build-map routes that resolve to canonical build verification commands.
** *Axis C (Module Dependency Edge Derivation)*: Derives inter-module dependency edges from build descriptors (Maven POM, Gradle, `package.json`, `pyproject.toml`), documentation cross-references, and warm LSP symbol queries.
** *Axis D (Path Attribution)*: Claims ownership over repository path prefixes (`claim_paths`, such as `.marshall/` or container directories) using constant prefix declarations.
* The system must never dynamically load arbitrary in-process Python or JVM bytecode from project or plugin directories at runtime.
* The system must keep the domain-detection glob dialect (Axis A) and the build-map `fnmatch` dialect separate so existing module routing behavior is preserved identically.

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] for implementation details.

[#PM-EXT-2]
=== PM-EXT-2: Provenance-Preserving Edge Derivation & Path Attribution Merges

When multiple domain resolvers contribute module dependency edges or path-prefix claims across a repository, the server must merge their outputs deterministically while preserving provenance and rejecting conflicting ownership claims (preserving `plan-marshall` ADR-014).

* The system must merge Axis C dependency edges across all active resolvers by set union while recording the contributing resolver provenance on every edge (`_derivation_merge`).
* The system must merge Axis D path-prefix claims (`_path_attribution_merge`) and resolve file ownership by longest-prefix match.
* When two domains claim the same normalized path prefix for different modules, the system must attribute no owner to that prefix (never an iteration-order winner) and report the collision as a provenance-carrying diagnostic; identical claims (same prefix, same module) must merge with combined producer provenance.
* Neither merge may throw or abort on a producer's output: every dropped edge or claim (self-edge, unknown module, malformed candidate, root-level or repository-escaping prefix) must be reported as a note on the producing resolver's or attributor's report, and a failing producer must be reported with an error status while its siblings still contribute. A second producer registered under an already-registered resolver or attributor ID must be dropped with a note (the first registration wins).

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] for implementation details.

[#PM-EXT-3]
=== PM-EXT-3: Module Discovery, Build Map & Architecture Enrichment

Project setup, module discovery, verification derivation, and architectural enrichment must be managed as server-owned resources and state transitions rather than prose-driven wizard scripts.

* The system must discover project modules deterministically by parsing build descriptors and executing enrolled discovery jobs (cached per live descriptor-content hash, so uncommitted descriptors are discovered), exposing the module inventory, dependency graph, and impact neighborhood as read-only MCP resources (`PM-TOOL-3`).
* The system must maintain a write-once, fail-closed build map (`derive-verification`) mapping file globs, roles, and build classes to the required module and whole-tree verification set for any realized file footprint; users correct seeded entries directly, and the map is re-derived only by an explicit, user-confirmed reseed.
* The system must expose architectural enrichment (module responsibility, purpose, key packages, and rationale) as `submit` links of tasks of the enrichment role (class `read_only`, one task per module through the model slots, `PM-WF-5`), enforcing a completeness guard that every discovered module is enriched before setup completes.
* The system must provide a dedicated project setup workflow state machine (`project-setup`, hosted by the project's workspace scope, `PM-ARCH-4`) taking over `plan-marshall`'s `marshall-steward` wizard and its upgrade flow, mapping every wizard step and upgrade gate to a setup state or retiring it with a stated reason; the workflow runs in an enrolled project (`pm-operator enrol`), creates `.marshall/` and `.marshall/config/` with copies of the binary's default workflow units on first run, offers a new binary's default-unit changes as a diff on later runs, and takes no input from a `plan-marshall` `.plan/` configuration (`PM-MIG-2`).

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-EXT-4]
=== PM-EXT-4: Declarative Recipe Model & Tier-1 Init Routing

Recipes represent repeatable, domain-invariant or domain-specific maintenance campaigns (such as `simplify-codebase`, `security-audit`, `code-review`, `agentfile-hygiene`, `lesson-cleanup`, `doc-verify`).

* The system must represent built-in and domain recipes as declarative recipe descriptors specifying the scoring inputs (name, description, optional domain, scope), default change type, a free per-recipe parameter input schema that the server validates `recipe_params` against (its enumerations may name a server-resolved option source of the closed set `domains`, `profiles`, `skills:<domain>`, `modules`, `base_branches`, resolved by the plan bootstrap's recipe source before the plan exists; an audit recipe declares its scope and base branch there), deterministic deliverable mapping rules (a target harvester, or `request_scoped` deliverables taken from a pre-diagnosed request), and judgment states.
* A recipe run whose harvest yields no targets must end as a completed plan without a pull request (`outcome: no_change`, `merge_outcome: no_pr`, fact `empty_harvest`), never with an empty pull request.
* During `phase-1-init`, the system must run Tier-1 deterministic recipe-match scoring across the whole registered recipe catalog ahead of general planning-lane routing, auto-routing to the top recipe when the operator's `recipes.auto_route` is enabled and its confidence reaches the compiled threshold `0.6` (a calibration of the scorer, not configurable, `PM-WF-10`), otherwise raising the init question record `init.recipe-candidate` (`PM-WF-12`) over the candidates at or above the confidence floor (`0.35`), and never overriding a plan explicitly started from a recipe. Scoring runs for every source other than `recipe`; `recipes.auto_route` only decides between auto-routing and asking. The same tier must compute, without a model call, the request-aspect classification and, for a lesson source, the doc-shaped predicate that routes a doc-shaped lesson to the `lesson-cleanup` recipe.
* When a recipe plan is initialized, the system must derive its `plan_id` as `recipe-{recipe_key}-{yyyy-mm-dd-hh-mm-ss}` (UTC) to prevent git branch collisions across repeated runs of the same recipe.

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] and link:specification/phase-workflows.adoc[Phase Workflows Specification] for implementation details.

[#PM-EXT-5]
=== PM-EXT-5: Out-of-Process Project Script Jobs & Domain Workers

Projects may define custom finalize steps (`finalize-step-*`), project-local recipes (`recipe-*`), or domain workers (custom log parsers or module discovery for languages not compiled into the release binary).

* The system must execute project-local extension code exclusively out of process as enrolled `project_script` jobs (`PM-EXEC-2`) with a declared JSON input argument schema and a validated JSON output schema.
* The system must require explicit operator enrolment (script path and SHA-256 digest, interpreter, binding to one worker kind and target, argument schema, and maximum timeout in the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json`) before any project script job or custom domain worker can execute, and must refuse a run whose use or arguments do not match the enrolled binding and schema.
* Domain-specific internal capabilities (such as marker scanning or OpenRewrite log parsing) must be invoked only when declared by an active domain descriptor and must remain invisible when absent (preserving `plan-marshall` ADR-010).
* The system must offer compiled domain extension points for the pre-submission self-review surfacer (`ext-self-review-<domain>`, whose outcome is `reviewed`, `not_covered` with the surfacer's reason, or `not_run` with reason `no_domain_surfacer`, never a clean result when no review happened), for retrospective aspects of the post-run quality report (observability only, never gating the merge), and for domain recipes compiled into the domain bundle (a duplicate recipe key fails the build).

See the link:specification/domain-extensions.adoc[Domain Extensions Specification] (link:specification/domain-extensions/05-recipes-and-extension-points.adoc#self-review-surfacer[§ Pre-Submission Self-Review Surfacer Extension Point], link:specification/domain-extensions/05-recipes-and-extension-points.adoc#retrospective-aspects[§ Retrospective Aspect Extension Point]) and link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-EXT-6]
=== PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)

In `plan-marshall`, `marshal.json` mixes git-tracked project preferences, operator posture, derived data, server bookkeeping, executable command strings, and local runtime state. In PM-MCP, every file has exactly one owner class, and configuration is partitioned by trust boundary so no model-writable file can influence what binary or command executes on the host.

* The system must partition configuration across disjoint owner classes, with no key in two of them:
** *Team configuration (`.marshall/config/`, git-tracked)*: four purpose files, each with its own closed schema and `format_version`: `project.json` (repository and collaboration policy), `workflow.json` (plan workflow policy), `domains.json` (overrides of the derived domain detection), and `build-map.json` (the seeded build map), plus the project-owned workflow units (`*.pmwf`); beside them, the project skill directory `.marshall/skills/` holds the team's extension skills (`PM-SKILL-5`), vocabulary that no gate, link, or workflow reads. The files are sparse: they hold only deviations from the derived and compiled defaults and never a default, a binary version, a fingerprint, a migration ledger, or an "offered" list. A provider credential is only referenced by key (never where a token is sent: that is the operator-owned credential entry's `url`, `PM-CRED-5`).
** *Operator files (operator-only)*: the enrolment, one file per project with its own HMAC (security-critical execution bindings — the enrolled repository root, build wrappers, pinned host tool paths and SHA-256 digests, command templates, project scripts, and budgets), `machine-config.json` (machine resources and bounds, the outbound `proxy` setting, the web access setting `web` of `PM-SEC-7`, the client-profile connection overrides of `PM-CLIENT-5`, and `project_defaults`), the machine role set `<PM_MCP_BASE>/roles/` and the per-project role set `<PM_MCP_BASE>/projects/<project_id>/roles/` with their qualification records (`PM-WORK-1`, `PM-WORK-6`), the machine skill directory `<PM_MCP_BASE>/skills/` (`PM-SKILL-5`), the harness enrolment `harnesses.json` (one file per machine with its own HMAC, `PM-EXEC-1`), and per project `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (operator posture: the native or CLI variant per git and provider integration, per project, applied as `native` unless the derived `git_native_capability` finds a used feature the native variant cannot serve, which then requires the operator's choice through the operator channel; the commit author identity, per project only and without a default; the merge policy `merge.auto_merge` (default `true`: the plan merges once the pre-merge barrier passes; `false`: the plan stops before the merge and hands back a ready pull request for a human merge), recipe auto-route, question mode and wait (`questions.mode`, `questions.wait_seconds`: who answers questions, `PM-WF-12`), and the optional outline review (`questions.outline_review`), the operator's qualification level and warm-fresh gap (`PM-WORK-6`), language, commit trailer, envelope budget override, resolver enablement, retention, and the upstream MCP allowlist `upstream_mcp` of `PM-SVC-3`). The integration variant decides whose credentials act (the agent identity of the token lane or the operator's ambient CLI authentication), so it must never be a team key or a derived value, and a variant other than `native` is never chosen without the operator.
** *Server State (`<PM_MCP_BASE>`, including the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/`)*: Holds workflow status, derived facts, learned adaptive build timeouts, lock state, and audit logs.
* The system must derive every value it can observe (CI provider, merge queue and its check-response timeout, default merge method, default base branch, the provider's branch rules such as required checks, up-to-date and signed-commit requirements, the agent identity of the provider credential and whether it can see check runs, the repository features the native git variant cannot serve, domain activation, active profiles, cost calibration, envelope budget) and must offer an override only where a derivation input can be ambiguous (`ci_provider`, `domains.*`, `merge_method`, `envelope_budget_tokens`); derived values are cached with their inputs and state, and a gate that depends on a derivation that failed must evaluate `indeterminate`.
* The system must compute the effective configuration server-side (compiled default, derived value, team file, operator file) and publish it with the source of every value as the resource `pm://project/config`.
* Tuning values that calibrate server algorithms (thresholds, iteration caps, step wait timeouts) must be compiled constants, except the decision parameters a project-owned workflow unit declares (the panel roles, quorum, minimum score, and decidable kinds of the question adjudication, `PM-WF-18`; the trigger thresholds, budget, and prerequisite wait of the re-planning unit, `PM-WF-17`): these are team-owned workflow configuration, reviewed like code, each within compiled bounds that a unit can only tighten, never open; comparability across projects is kept because every decision record carries the threshold it applied and its source (the unit with its digest, or compiled, `PM-WF-19`). No decision parameter is an operator key, and options whose only effect is to weaken a guarantee must not exist.
* The system must never read executable paths, wrapper names, or shell command strings from a team configuration file or any other file in the repository working tree.

See the link:specification/domain-extensions.adoc[Domain Extensions Specification], link:specification/store-schemas.adoc[Store Schemas Specification], and link:specification/model-work.adoc[Model Work Specification] for implementation details.

[#PM-EXT-7]
=== PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades

Configuration and workflow units must stay current without migration machinery before 1.0, without silent rewrites, and without LLM-orchestrated multi-step CLI sequences.

* Every team configuration file, operator file, and workflow unit must declare its format version; before 1.0 the system must accept exactly the binary's current version of each file kind and must refuse any other with `format_outdated` or `format_newer` naming the file, never rewriting it on read and never migrating it at runtime start. There is no migration command chain, no seed fingerprint, and no `system` bookkeeping block; the migration mechanism for 1.0 and later is decided at 1.0.
* The system must validate every team file and the operator file against its closed schema on every computation of the effective configuration; an undeclared key must be reported (`unknown_config_key`) and never kept as an unread setting, and a team file that fails validation must refuse the project's plan starts and phase handshakes naming the file.
* The system must never read, convert, or upgrade a `plan-marshall` `.plan/marshal.json` (`PM-MIG-2`).
* The system must reach a project with a new binary only through: new compiled defaults for keys the sparse files do not set; release notes listing every format change with its keys, together with the drain rule for in-flight scopes (`pm-operator drain`); and the project setup workflow, which offers changed default workflow units as a three-way diff (from the default revision the project unit derives from to the current one, so a removed step is never restored and a declined change is never re-offered) and a server-rendered rewrite of a refused JSON configuration file.
* Every phase unit and the sub-workflow units `git.commit_and_push`, `remediation.*`, `replan`, and `question.adjudicate` must be project-owned (`.marshall/config/*.pmwf`, copied from the defaults on first setup; the epic, setup, lesson-maintenance, bootstrap, and source units are compiled only, link:later-improvements.adoc#_l_5_team_overrides_of_templates_and_composition_rules[Later Improvements, L-5]) and must be verified on every load against the static verification rules and the compiled invariants of every phase (mandatory steps and states, the outline gate, Q-Gate presence, footprint checks, push and pre-merge barriers, finalize ordering bands, step completion exactly once, remediation policies that end in a defined fallback within the compiled budget caps, waivers written only by the operator channel, unchanged condition overlays, and no guarantee-weakening path); a violating unit must refuse the project's plan lifecycle with its file and line and never fall back silently to a default unit. Project steps must bind only to enrolled project scripts.
* The system must prevent configuration upgrade clutter in the model's Chain of Thought (CoT) and codebase:
** Vocabulary skills and workflow prompts must never contain prose instructions for historical field migrations or multi-step CLI choreography (retiring separate model-invoked `sync-defaults`, `steps-sort`, `normalize-keys`, and `migrate-*` calls).
** When the digests of the configuration inputs match the last validated effective configuration, configuration verification at plan startup or phase handshakes must execute as a silent check emitting zero context tokens.
* The system must execute an in-flight plan against its plan instance (`PM-IMPL-5`), whose header records the digests of every configuration input (compiled defaults, derived facts, team files, operator file, and process workflow units), so a later change (edit, changed default, changed derived fact, adopted unit change) must never silently change what an in-flight plan does: the server composes a candidate instance at the next phase handshake, adopts it without interaction only when it equals the current instance, and otherwise raises the configuration-drift condition, which the server resolves in the same transaction: it adopts the candidate when it verifies and contains the current state and every state of the call stack, and keeps the current instance otherwise, audited (`PM-IMPL-5`).
* Automated build-time JUnit tests (`PM-TEST-3`) must verify that every configuration schema is closed and valid, that every default workflow unit satisfies the compiled invariants, and that the invariant checker refuses a fixture set of weakened units.
