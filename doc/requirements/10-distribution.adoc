== Distribution & Client Packaging (PM-DIST)

[#PM-DIST-1]
=== PM-DIST-1: Single Version Authority & Embedded Client Bundles

`PM-MCP` distributes a compiled software system rather than a generated markdown corpus, unifying server and client components under a single version authority: one release.

* The system must distribute one release of four native executables built from one version: `pm-mcp` (the host- and model-facing command line: the relay and `enter`), `pm-operator` (the operator's command line), `pm-mcpd` (the runtime, started on demand by either of them, which also serves the optional web access), and `pm-exec` (the job launcher).
* The release must embed the client bundles (`classpath:/bundles/<client>/`) for every supported frontier coding agent runtime whose bundle has been delivered by the current stage (`PM-MIG-1`): Claude Code (`claude`), OpenCode (`opencode`), Antigravity (`antigravity`), and Codex (`codex`); full four-host coverage is reached at Stage 6. The bundle version is the release version.
* The system must eliminate separate client-side package downloads and repository distributions, ensuring that client-installed artifacts always originate directly from the installed release; no sub-agent or agent variant is installed into a host, because the runtime composes every worker's launch from the role artifact and the client profile at spawn (`PM-WF-5`).
* The system must embed the following artifacts within each client bundle:
** User-invocable entry commands / skills, named with the `mcp-` prefix (`PM-CLIENT-1`), that execute `pm-mcp enter --client <client>`.
** The shim skill of `PM-SKILL-4`, in the host's own skill format and directory, until the host supports the MCP Skills Extension; entry commands exit at once inside a worker (`PM_MCP_JOB_ID` set). A bundle installs no lifecycle hook.
** Host MCP `stdio` connection configurations (`pm-mcp serve --client <client>`), permission deny rules for `<PM_MCP_BASE>/**` including its credential directory, and, as defence in depth, an enforcement rule that denies the whole operator binary `pm-operator` to the model, while `pm-mcp` (`serve`, `enter`) stays allowed (`PM-SEC-3`).
* The system must structure the server filesystem installation using a clean separation between installation and instance directories:
** `<PM_MCP_HOME>/`: Read-only installation directory containing the four binaries (`bin/pm-mcp`, `bin/pm-operator`, `bin/pm-mcpd`, `bin/pm-exec`), the CycloneDX SBOM of the release (`sbom/`, covering the Java dependencies and the npm packages of the web application), and the release notes, and no configuration file (machine settings live in `<PM_MCP_BASE>/machine-config.json`). Unless the environment variable `PM_MCP_HOME` names it, it is resolved from the location of the running binary (`pm-mcp` or `pm-operator`) with symbolic links resolved.
** The binaries must start each other by absolute path from `<PM_MCP_HOME>/bin/`, never through `PATH`; the installation must put exactly two entries on `PATH`, the symbolic links `pm-mcp` and `pm-operator` in a user bin directory (or print the commands that create them).
** An upgrade must install the new release into a new versioned installation directory, switch the `PATH` symlinks, and then stop the old runtime with `pm-operator drain`; the old directory stays until that drain has completed.
** `<PM_MCP_BASE>/`: Mutable instance directory (default `~/.plan-marshall-mcp/`, overridable only by the environment variable `PM_MCP_BASE`) that survives software upgrades, containing `enrolments/` (one enrolment file per project), `harnesses.json` (the enrolled harness command lines of workers), `roles/` (the operator's machine role set, `PM-WORK-1`), `machine-config.json` (machine settings, the client-profile connection overrides included), `credentials/` (fallback credential store), `logs/`, `locks/`, `run/` (runtime token, socket, and job-private directories), `web/` (files of the optional web access), `projects/` (the per-project machine stores with plans, archived plans, lessons, and scope state), and `state/` (runtime-owned machine state, whose contents the link:specification/filesystem-layout.adoc#machine-layout[Filesystem Layout Specification, Machine Layout] alone defines).

See the link:specification/module-structure.adoc[Module Structure Specification] and the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification], the link:specification/cli-and-security/01-cli-and-installer.adoc#cli-binary[CLI, Coordination & Security Specification] (Command-Line Binaries & Installation Layout), and the link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-DIST-2]
=== PM-DIST-2: Embedded Bundle Extraction & Interactive Client Installer

Client configuration artifacts and bundles must be extracted directly from the release's embedded resources and applied via an interactive CLI installer without network access or a TCP listener.

* The release must embed one deterministic bundle manifest (`classpath:/bundles/<client>/bundle-manifest.json`) per supported client (`claude`, `opencode`, `antigravity`, `codex`), declaring the artifacts shared by both scopes once and one section per scope (`user`, `project`) with its target root, its shared host configuration files, and its scope-only artifacts, and defining target relative paths, file types, SHA-256 digests, file modes, owned configuration keys, and owned configuration elements.
* The installer must own shared host configuration at element level: host permission rules (`permission_rule`, in a deny, ask, or allow list, classed enforcement or convenience) are identified by their exact normalized value and recorded in the installation ledger; `install` appends missing elements, `update` replaces recorded elements, `remove` deletes recorded elements only, and a recorded element the user edited or deleted is changed only after an interactive `--force`.
* The system must provide a client installation tool (`pm-operator client install|update|remove|status`) whose changes are applied by the runtime as the single writer, that reads the embedded bundle manifest, compares it against the target filesystem and installation ledger, displays an interactive diff of files and permissions to be changed, and requires explicit operator confirmation on a TTY (`--yes` for non-interactive CI/automation).
* The client installer must require an interactive terminal and refuse `--yes` for `pm-operator client remove` and for any `install` or `update` change that removes or weakens an installed enforcement rule (including the `<PM_MCP_BASE>/**` and credential-directory deny rules, `PM-CRED-3`); `--yes` must be accepted only for changes that keep or strengthen every enforcement rule.
* The client installer must support two installation scopes, selected by `--scope` and recorded with the installation:
** `--scope user`: Installs entry commands and MCP `stdio` server configurations into the user-scope locations of the link:specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table].
** `--scope project`: Writes entry commands and MCP `stdio` settings into the project-scope locations of the link:specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table] (containing zero user-specific paths or secrets) for team version control; `pm-operator client install|update --scope project` must refuse while the project has non-terminal plans or epics, naming them (user scope is unaffected).

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-DIST-3]
=== PM-DIST-3: Uniform Host MCP STDIO Connection Configuration

The system must configure all supported coding agent hosts to spawn the `pm-mcp serve` relay over the `stdio` transport.

* The system must configure every supported host runtime to launch `pm-mcp serve` (command `pm-mcp`, argument `serve`) over `stdio`, writing only the owned key in the host configuration file named for that host and scope in the link:specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table].
* Because `pm-mcp` (the relay and `enter`) starts the runtime on demand and connects to it over its user-private Unix domain socket, reading the runtime token itself, host configuration requires no runtime pre-start, bearer token helper, or TCP port; the host configuration launches `pm-mcp serve` for every host.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] for implementation details.

[#PM-DIST-4]
=== PM-DIST-4: Bundle Upgrade Detection & Atomic Reconciliation

The system must detect discrepancies between installed client bundles and the installed release, performing safe, idempotent updates.

* The system must detect bundle drift during `pm-mcp enter` and `pm-operator client status`, issuing an actionable recommendation to run `pm-operator client update`: `bundle_outdated` when the recorded bundle version differs from the release version of the evaluating binary (every binary of a release carries the release version, which is the bundle version, `PM-DIST-1`: `pm-mcp` evaluates against its own for `enter`, `pm-operator client status` against its own), and `bundle_modified` when the recorded digest of an installed artifact or owned element differs from the disk (edited and missing entries listed).
* The system must record every installed file path, configuration key, and configuration element with its scope and digest in an installation ledger (`<PM_MCP_BASE>/state/install-records.json`); subsequent updates must modify or delete only recorded entries.
* The client updater must verify file digests and element values before overwriting; any file or element modified locally by the operator must be preserved and reported with a warning unless the operator confirms `--force` interactively.
* The client updater must merge shared host configuration files (per the link:specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table]) strictly at their owned keys (e.g., `mcpServers.plan-marshall` or `mcp.plan-marshall`), preserving all unowned configuration.
* When the release is upgraded on disk while the runtime is running, `pm-mcp enter`, the `pm-mcp serve` relay, and `pm-operator status` must detect the version mismatch against the runtime record (`state/runtime.json`) and allow graceful draining via `pm-operator drain`; `pm-operator client install|update` must refuse until the old runtime is drained.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-DIST-5]
=== PM-DIST-5: Multi-Host Concurrent Coexistence on One Machine

Multiple host connections across distinct coding agent hosts must operate simultaneously and safely across different projects or within the same project.

* The system must permit concurrent `pm-mcp serve` relays from any combination of supported coding agent runtimes (`claude`, `opencode`, `antigravity`, `codex`) on the same machine, all served by the one runtime of the active `PM_MCP_BASE`.
* The system must install client bundles into host-specific directories without file name collisions, including with the artifacts of a `plan-marshall` plugin installed side by side (the `mcp-` prefixed entry commands, `PM-CLIENT-1`).
* The system must coordinate machine-wide build slot caps (`build-slots.json`), per-repository merge queues (`merge-queue.json`), cross-plan review-bot rate windows (`review-bot-windows.json`), and per-plan locks fairly across all concurrent plans via `FileChannel.lock()`, taken by the runtime as the single writer (the verbs of `pm-mcp` and `pm-operator` are requests to the runtime).
* The system must permit `plan-marshall` and `PM-MCP` to be installed on the same machine and used in the same repository: `PM-MCP` keeps its state exclusively in `<PM_MCP_BASE>` and `.marshall/`, never reads or writes `~/.plan-marshall/` or `.plan/`, and never reads `PLAN_MARSHALL_HOME` or `PLAN_MARSHALL_CREDENTIALS_DIR`, without exception (`PM-MIG-2`).
* The system must support development and test isolation: setting `PM_MCP_BASE` to an alternate path must isolate the runtime instance, its socket, state locks, build slots, audit logs, and credential namespaces to that directory.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/filesystem-layout.adoc[Filesystem Layout Specification], and the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] for implementation details.
