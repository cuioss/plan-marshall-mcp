== Distribution & Client Packaging (PM-DIST)

[#PM-DIST-1]
=== PM-DIST-1: Single Version Authority & Embedded Client Bundles

`PM-MCP` distributes a compiled software system rather than a generated markdown corpus, unifying server and client components under a single version authority: one release.

* The system must distribute one release of four native executables built from one version: `pm-mcp` (the interactive and host-facing command line), `pm-mcpd` (the runtime, started on demand by `pm-mcp`), `pm-mcp-exec` (the job launcher), and `pm-mcp-web` (the optional web server).
* The release must embed the client bundles (`classpath:/bundles/<client>/`) for all four supported frontier coding agent runtimes: Claude Code (`claude`), OpenCode (`opencode`), Antigravity (`antigravity`), and Codex (`codex`); the bundle version is the release version.
* The system must eliminate separate client-side package downloads and repository distributions, ensuring that client-installed artifacts always originate directly from the installed release.
* The system must embed the following artifacts within each client bundle:
** User-invocable entry commands / skills that execute `pm-mcp enter --client <client>`.
** Execution-context sub-agent variant definitions per model effort level.
** Host lifecycle hooks (such as session-start checks for stale bundles or resumable plans) where supported by the host.
** Host MCP `stdio` connection configurations (`pm-mcp serve`), permission deny rules for `<PM_MCP_BASE>/**` including its credential directory, and, as defence in depth, deny or ask rules for the operator-facing verbs `pm-mcp operator` and `pm-mcp web`.
* The system must structure the server filesystem installation using a clean separation between installation and instance directories:
** `<PM_MCP_HOME>/`: Read-only installation directory containing the four binaries (`bin/pm-mcp`, `bin/pm-mcpd`, `bin/pm-mcp-exec`, `bin/pm-mcp-web`), the CycloneDX SBOM of the release (`sbom/`, covering the Java dependencies and the npm packages of the web application), and the release notes, and no configuration file (machine settings live in `<PM_MCP_BASE>/machine-config.json`). Unless the environment variable `PM_MCP_HOME` names it, it is resolved from the location of the running `pm-mcp` with symbolic links resolved.
** The binaries must start each other by absolute path from `<PM_MCP_HOME>/bin/`, never through `PATH`; the installation must put exactly one entry on `PATH`, a `pm-mcp` symbolic link in a user bin directory (or print the command that creates it).
** An upgrade must install the new release into a new versioned installation directory, switch the `PATH` symlink, and then stop the old runtime with `pm-mcp drain`; the old directory stays until that drain has completed.
** `<PM_MCP_BASE>/`: Mutable instance directory (default `~/.plan-marshall-mcp/`, overridable only by the environment variable `PM_MCP_BASE`) that survives software upgrades, containing `enrolments/` (one enrolment file per project), `machine-config.json`, `conf/` (operator overrides such as client profile overrides), `credentials/` (fallback credential store), `logs/`, `locks/`, `run/`, `projects/` (the per-project machine stores with plans, archived plans, lessons, and scope state), and `state/` (build slots, install records).

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification], the link:specification/cli-and-security.adoc#cli-binary[CLI, Coordination & Security Specification] (Command-Line Binary & Installation Layout), and the link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-DIST-2]
=== PM-DIST-2: Embedded Bundle Extraction & Interactive Client Installer

Client configuration artifacts and bundles must be extracted directly from the release's embedded resources and applied via an interactive CLI installer without network access or a TCP listener.

* The release must embed one deterministic bundle manifest (`classpath:/bundles/<client>/bundle-manifest.json`) per supported client (`claude`, `opencode`, `antigravity`, `codex`), declaring the artifacts shared by both scopes once and one section per scope (`user`, `project`) with its target root, its shared host configuration files, and its scope-only artifacts, and defining target relative paths, file types, SHA-256 digests, file modes, owned configuration keys, and owned configuration elements.
* The installer must own shared host configuration at element level: host permission rules (`permission_rule`, in a deny, ask, or allow list, classed enforcement or convenience) and host hook entries (`hook_entry`) are identified by their exact normalized value and recorded in the installation ledger; `install` appends missing elements, `update` replaces recorded elements, `remove` deletes recorded elements only, and a recorded element the user edited or deleted is changed only after an interactive `--force`.
* The system must provide a client installation tool (`pm-mcp client install|update|remove|status`) whose changes are applied by the runtime as the single writer, that reads the embedded bundle manifest, compares it against the target filesystem and installation ledger, displays an interactive diff of files and permissions to be changed, and requires explicit operator confirmation on a TTY (`--yes` for non-interactive CI/automation).
* The client installer must require an interactive terminal and refuse `--yes` for `pm-mcp client remove` and for any `install` or `update` change that removes or weakens an installed enforcement rule (including the `<PM_MCP_BASE>/**` and credential-directory deny rules, `PM-CRED-3`); `--yes` must be accepted only for changes that keep or strengthen every enforcement rule.
* The client installer must support two installation scopes, selected by `--scope` and recorded with the installation:
** `--scope user`: Installs entry commands and MCP `stdio` server configurations into the user-scope locations of the link:specification/client-profiles.adoc#host-integration-table[Host Integration Table].
** `--scope project`: Writes entry commands and MCP `stdio` settings into the project-scope locations of the link:specification/client-profiles.adoc#host-integration-table[Host Integration Table] (containing zero user-specific paths or secrets) for team version control.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-DIST-3]
=== PM-DIST-3: Uniform Host MCP STDIO Connection Configuration

The system must configure all supported coding agent hosts to spawn the `pm-mcp serve` relay over the `stdio` transport.

* The system must configure every supported host runtime to launch `pm-mcp serve` (command `pm-mcp`, argument `serve`) over `stdio`, writing only the owned key in the host configuration file named for that host and scope in the link:specification/client-profiles.adoc#host-integration-table[Host Integration Table].
* Because the CLI (the relay and every other `pm-mcp` verb that needs the runtime) starts the runtime on demand and connects to it over its user-private Unix domain socket, reading the runtime token itself, host configuration requires no runtime pre-start, bearer token helper, or TCP port; the host configuration launches `pm-mcp serve` for every host.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] for implementation details.

[#PM-DIST-4]
=== PM-DIST-4: Bundle Upgrade Detection & Atomic Reconciliation

The system must detect discrepancies between installed client bundles and the installed `pm-mcp` binary, performing safe, idempotent updates.

* The system must detect bundle drift during `pm-mcp enter`, the session-start hook, and `pm-mcp client status`, issuing an actionable recommendation to run `pm-mcp client update`: `bundle_outdated` when the recorded bundle version differs from the bundle version embedded in the running `pm-mcp`, and `bundle_modified` when the recorded digest of an installed artifact or owned element differs from the disk (edited and missing entries listed).
* The session-start hook must print the scope pointer and the drift notice independently of each other and must detect drift without starting the runtime.
* The system must record every installed file path, configuration key, and configuration element with its scope and digest in an installation ledger (`<PM_MCP_BASE>/state/install-records.json`); subsequent updates must modify or delete only recorded entries.
* The client updater must verify file digests and element values before overwriting; any file or element modified locally by the operator must be preserved and reported with a warning unless the operator confirms `--force` interactively.
* The client updater must merge shared host configuration files (per the link:specification/client-profiles.adoc#host-integration-table[Host Integration Table]) strictly at their owned keys (e.g., `mcpServers.plan-marshall` or `mcp.plan-marshall`), preserving all unowned configuration.
* When the release is upgraded on disk while the runtime is running, `pm-mcp enter`, the `pm-mcp serve` relay, and `pm-mcp status` must detect the version mismatch against the runtime record (`state/runtime.json`) and allow graceful draining via `pm-mcp drain`; `pm-mcp client install|update` must refuse until the old runtime is drained.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-DIST-5]
=== PM-DIST-5: Multi-Host Concurrent Coexistence on One Machine

Multiple host connections across distinct coding agent hosts must operate simultaneously and safely across different projects or within the same project.

* The system must permit concurrent `pm-mcp serve` relays from any combination of supported coding agent runtimes (`claude`, `opencode`, `antigravity`, `codex`) on the same machine, all served by the one runtime of the active `PM_MCP_BASE`.
* The system must install client bundles into host-specific directories without file name collisions.
* The system must coordinate machine-wide build slot caps (`build-slots.json`), per-repository merge queues (`merge-queue.json`), cross-plan review-bot rate windows (`review-bot-windows.json`), and per-plan locks fairly across all concurrent plans via `FileChannel.lock()`, taken by the runtime as the single writer (the CLI's verbs, operator verbs included, are requests to the runtime).
* The system must permit legacy `plan-marshall` and `PM-MCP` to be installed on the same machine and used in the same repository: `PM-MCP` keeps its state exclusively in `<PM_MCP_BASE>` and `.marshall/`, never reads or writes `~/.plan-marshall/` or `.plan/`, and never reads `PLAN_MARSHALL_HOME` or `PLAN_MARSHALL_CREDENTIALS_DIR`, without exception (`PM-MIG-2`).
* The system must support development and test isolation: setting `PM_MCP_BASE` to an alternate path must isolate the runtime instance, its socket, state locks, build slots, audit logs, and credential namespaces to that directory.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/filesystem-layout.adoc[Filesystem Layout Specification], and the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] for implementation details.
