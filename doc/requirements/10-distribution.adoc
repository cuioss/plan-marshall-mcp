== Distribution & Client Packaging (PM-DIST)

[#PM-DIST-1]
=== PM-DIST-1: Single Version Authority & Embedded Client Bundles

`PM-MCP` distributes a compiled software system rather than a generated markdown corpus, unifying server and client components under a single version authority.

* The system must distribute the native executable `pm-mcp` as a unified package containing all server runtime code and embedded client bundles for all supported AI client runtimes (Claude Code, OpenCode, Antigravity).
* The system must eliminate separate client-side package downloads and repository distributions, ensuring that client-installed artifacts always originate directly from the active daemon.
* The system must embed the following artifacts within each client bundle:
** User-invocable entry commands that execute `pm-mcp enter --client <client>`.
** Execution-context sub-agent variant definitions per model effort level.
** Host lifecycle hooks (such as session-start checks for stale bundles or resumable plans).
** Host MCP connection configurations and permission deny rules for credential directories.
* The system must structure the server filesystem installation using a clean separation between installation and instance directories:
** `<PM_MCP_HOME>/`: Read-only installation directory containing the `pm-mcp` binary, pass-through control scripts (`start.sh`, `stop.sh`, `restart.sh`, `run.sh`, `status.sh`), default configuration (`conf/pm-mcp.properties`), OS service templates, and CycloneDX SBOM.
** `<PM_MCP_BASE>/`: Mutable instance directory (default `~/.plan-marshall/mcp/`) that survives software upgrades, containing `conf/` (operator overrides), `logs/`, `run/` (pid, lock, cookie), and `state/` (enrolments, slots, install records).

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-DIST-2]
=== PM-DIST-2: Authenticated Loopback Bundle Endpoint & Client Installer

Client configuration artifacts and bundles must be served directly by the running daemon over an authenticated endpoint and applied via an interactive installer.

* The running daemon must serve client bundles via read-only HTTP endpoints:
** `GET /clients`: Lists supported client runtimes, bundle versions, and SHA-256 digests.
** `GET /clients/{client}/bundle?scope=user|project`: Returns the bundle manifest defining target relative paths, file types, SHA-256 digests, file modes, and owned JSON configuration keys.
** `GET /clients/{client}/files/{path}`: Returns the content of a specific bundle file.
* The `/clients` HTTP endpoint must enforce loopback binding (`127.0.0.1`), strict `Origin` and `Host` header validation, and bearer cookie authentication (`~/.plan-marshall/mcp/run/cookie`), preventing unauthenticated local inspection.
* The system must provide a client installation tool (`pm-mcp client install|update|remove|status`) that reads the local runtime cookie, fetches the manifest, displays an interactive diff of files and permissions to be changed, and requires explicit operator confirmation on a TTY.
* The client installer must support two installation scopes:
** `--scope user`: Installs entry commands and MCP configurations into the user's global client configuration.
** `--scope project`: Writes entry commands and MCP settings into the repository checkout (containing zero user paths or secrets) for team version control.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/daemon-endpoint.adoc[Daemon Endpoint Specification] for implementation details.

[#PM-DIST-3]
=== PM-DIST-3: Host MCP Connection Configuration (HTTP & Stdio)

The system must configure host connections to PM-MCP based on the transport capabilities declared in each host's client profile.

* The system must configure hosts capable of dynamic header execution (such as Claude Code) to connect via the Streamable HTTP transport:
+
[source,json]
----
{
  "mcpServers": {
    "plan-marshall": {
      "type": "http",
      "url": "http://127.0.0.1:<port>/mcp",
      "headersHelper": "pm-mcp token"
    }
  }
}
----
* The system must configure hosts lacking dynamic header support to connect via the stdio bridge relay:
+
[source,json]
----
{
  "mcpServers": {
    "plan-marshall": {
      "command": "pm-mcp",
      "args": ["serve", "--stdio"]
    }
  }
}
----
* The system must implement on-demand daemon startup within `pm-mcp token`, `pm-mcp serve --stdio`, and `pm-mcp enter`, launching the daemon in detached mode automatically if it is not currently running.

See the link:specification/daemon-endpoint.adoc[Daemon Endpoint Specification] and link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] for implementation details.

[#PM-DIST-4]
=== PM-DIST-4: Bundle Upgrade Detection & Atomic Reconciliation

The system must detect discrepancies between installed client bundles and the daemon, performing safe, idempotent updates.

* The system must detect bundle version or digest divergence during `pm-mcp enter` and session-start hooks, issuing an actionable recommendation to run `pm-mcp client update`.
* The system must record every installed file path and configuration key in an installation ledger (`~/.plan-marshall/mcp/state/install-records.json`); subsequent updates must modify or delete only recorded files.
* The client updater must verify file digests before overwriting; any file modified locally by the operator must be preserved and reported with a warning.
* The client updater must merge shared configuration files (such as host `settings.json`) strictly at owned keys (e.g., `mcpServers.plan-marshall`), preserving all unowned configuration.
* The daemon must detect when the installed `pm-mcp` binary is newer than the running daemon process upon new client connection, gracefully drain active jobs, terminate, and restart under the updated binary.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/daemon-endpoint.adoc[Daemon Endpoint Specification] for implementation details.

[#PM-DIST-5]
=== PM-DIST-5: Multi-Host Concurrent Coexistence on One Machine

A single PM-MCP daemon instance must support multiple concurrent host runtimes operating simultaneously across different projects or within the same project.

* The system must permit concurrent connections from multiple distinct AI client runtimes (Claude Code, OpenCode, Antigravity) to a single PM-MCP daemon on the machine.
* The system must install client bundles into host-specific directories without file name collisions or port conflicts.
* The system must manage machine-wide build slot caps and shared file locks fairly across all connected client hosts.
* The system must support development isolation: setting `PM_MCP_BASE` or `PLAN_MARSHALL_HOME` to an alternate path must launch an independent daemon instance with its own TCP port, runtime cookie, state locks, and credential namespace.

See the link:specification/filesystem-layout.adoc[Filesystem Layout Specification] and link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] for implementation details.
