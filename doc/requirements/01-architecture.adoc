== Core Architecture (PM-ARCH)

[#PM-ARCH-1]
=== PM-ARCH-1: Process Ownership & Always-On Runtime

The system must strictly divide responsibilities between deterministic process execution and probabilistic model judgment. All state tracking, transition sequencing, gate evaluations, and command assembly belong to the system, while the model is tasked exclusively with judgment-based contributions.

* The system must execute all workflow state machines, state transitions, quality gate evaluations, and command assembly inside the always-on `pm-mcp` runtime process, confining model contributions exclusively to judgment artifacts (request clarification, solution outline authoring, code implementation, finding triage, and commit/pull request descriptions).
* The system must run as a single always-on runtime process (daemon) per machine and `PM_MCP_BASE`, under the operating system privileges of the local developer user, whose lifetime and jobs are independent of any host conversation or host connection.
* The system must let host coding agents reach the runtime exclusively through a thin `pm-mcp serve` STDIO relay spawned by the host per connection, with zero listening network ports.
* The system must enforce mutual exclusion across concurrent sessions, sub-agents, and projects using OS-level `FileChannel.lock()` advisory locks and atomic write-then-rename operations within `.plan/` and `~/.plan-marshall/mcp/locks/`.
* The system must compile workflow definitions, state stores, tools, client profiles, vocabulary skills, and background services into a single GraalVM native binary, guaranteeing that all components operate on an identical release version without runtime drift.
* The system must reject any architecture where process ordering, transition permissions, or parameter assembly depend on prose instructions or client-side prompt compliance.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification] and the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-ARCH-2]
=== PM-ARCH-2: Local-by-Design & Zero External Cloud Dependency

The system must operate entirely on the developer's workstation, directly interacting with local repository trees and worktrees without reliance on cloud intermediaries.

* The system must execute all services, workflow transitions, and state management locally on the developer's workstation without requiring remote infrastructure, cloud-hosted backends, or telemetry reporting.
* The system must enforce workspace confinement, restricting all file reads, file modifications, and process executions strictly to the enrolled project root directory and its active linked worktrees.
* The system must reject any operation attempting to access or modify filesystem paths outside the enrolled project boundary unless explicitly authorized by the human operator through the operator channel.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] and link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-ARCH-3]
=== PM-ARCH-3: STDIO Host Transport, Local Relay & Frontier Protocol Compliance

Hosts must connect over the Model Context Protocol (MCP) `stdio` transport, relayed to the always-on runtime over a user-private local channel, targeting the frontier MCP `2026-07-28` specification.

* The system must communicate with host coding agents (`claude`, `opencode`, `antigravity`, `codex`) exclusively over standard input (`stdin`) and standard output (`stdout`) of the `pm-mcp serve` relay.
* The relay must forward MCP messages in both directions (requests, responses, notifications, and server-to-client requests such as elicitation) between the host and the runtime without interpreting them, preserving JSON-RPC `id` values.
* The runtime must serve MCP only over a Unix domain socket restricted to the owning OS user, omitting all TCP/UDP listeners.
* The relay must reserve `stdout` strictly for newline-delimited JSON-RPC 2.0 MCP messages and route all diagnostic logging to `stderr`; the runtime logs to `~/.plan-marshall/mcp/logs/daemon.log`.
* The system must target the MCP `2026-07-28` protocol version exclusively, omitting legacy protocol versions (`2025-11-25`, `2024-11-05`) and backward-compatibility shims.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification] for implementation details.

[#PM-ARCH-4]
=== PM-ARCH-4: Stateless Requests & Explicit Scope Addressing

The system must operate without transport-level session state, evaluating every request entirely from explicit scope identifiers and persisted filesystem records.

* The system must process every MCP tool invocation statelessly: MCP transport sessions and host connections may carry only negotiated protocol capabilities and connection metadata, never workflow state.
* The system must require every stateful workflow invocation to carry an explicit logical scope identifier (`plan_id` or `epic_id`) and, when addressing an entity-specific transition, the entity identifier within the link ID.
* The system must resolve the client identity (`client_id`) and the target project root (`workspace_root`) of scoped calls exclusively from the scope's persisted entry record (`entry.json`), rejecting client-supplied working directory or client-type overrides.
* The system must answer every workflow query and validate every transition entirely from persisted filesystem state, guaranteeing zero state loss across host restarts, context window compactions (`/clear`), or process restarts.
* The system must restrict unscoped tool requests strictly to global project discovery and initial plan instantiation (`pm_plans`, `pm_epics`, `pm_start`).

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/filesystem-layout.adoc[Filesystem Layout Specification], and the link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.

[#PM-ARCH-5]
=== PM-ARCH-5: Worktree-Bound Plan Location & Main-Bound Orchestrator Location

Plan execution state must be isolated inside worktrees to protect the main checkout, while orchestrator state remains anchored to the repository's main tree.

* The system must locate a plan's state directory within the main checkout's `.plan/local/plans/<plan_id>/` prior to worktree allocation, and relocate it into the worktree's `.plan/local/worktrees/<plan_id>/.plan/` during active execution.
* The system must ensure that the repository's main checkout working tree remains clean and unaffected by uncommitted plan execution artifacts at all times.
* The system must isolate all mutations to git-tracked orchestrator state (epic ledgers, inbox messages, and landing records) within dedicated worktrees, incorporating changes into the main branch strictly through standard branch merges.
* The system must automatically resolve the current filesystem location of any plan directory from its `plan_id` without requiring the client or model to provide filesystem paths.
* The system must pass the plan's resolved absolute directory path as the `PLAN_BASE_DIR` environment variable to all executed subprocesses and script adapters.

See the link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-ARCH-6]
=== PM-ARCH-6: Filesystem State Persistence & Cache-Only Process Memory

All durable workflow and coordinator data must reside in structured filesystem stores, with process memory functioning strictly as a transient cache.

* The system must persist all authoritative workflow states, tasks, findings, references, locks, build jobs, and audit events directly in filesystem files formatted as JSON or JSONL.
* The system must treat all in-memory process data structures as disposable caches, ensuring that any process exit, crash, or restart leaves persistent state intact and uncorrupted.
* The system must store credentials exclusively within the operating system credential store or its permission-guarded fallback file store (`~/.plan-marshall/credentials/`), keeping secrets in process memory only for the duration of the active request.
* The system must include a mandatory `format_version` integer property in every persisted JSON and JSONL state file.
* The system must automatically validate and migrate forward store file formats upon process startup before accepting incoming workflow requests.

See the link:specification/store-schemas.adoc[Store Schemas Specification] and link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-ARCH-7]
=== PM-ARCH-7: Atomic Plan State Relocation Across Worktrees

Directory moves between the main checkout and plan worktrees must occur atomically under mutual exclusion to prevent data loss or inconsistency during transitions.

* The system must create all plan worktrees within the repository's `.plan/local/worktrees/` directory, guaranteeing that worktree directories and main repository plan directories reside on the same filesystem volume to allow atomic renames.
* The system must acquire the plan-specific lock file prior to initiating any directory move between `.plan/local/plans/<plan_id>/` and `.plan/local/worktrees/<plan_id>/.plan/`.
* The system must record every directory relocation in a write-ahead journal (`move-journal.json`) before modifying filesystem paths.
* The system must relocate the plan's entry record (`entry.json`) atomically alongside the plan directory during all worktree creation, worktree destruction, and plan finalization operations.
* The system must inspect `move-journal.json` during server startup and automatically roll back or complete any interrupted directory move before processing new requests.

See the link:specification/move-journal.adoc[Move Journal Specification] and link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-ARCH-8]
=== PM-ARCH-8: Runtime & Relay Lifecycle, Crash Recovery & Job Drain

The runtime must run continuously and recover deterministically from crashes, while relays come and go with host connections without affecting runtime state or jobs.

* The system must start the runtime on demand when a relay finds none running, detached from the relay's process group and session so that no host action on the relay terminates it, and must optionally support start at login through the per-user OS service manager.
* The system must ensure that relay termination (`stdin` EOF or signals) closes only that host connection and never cancels, drains, or kills jobs or alters persisted state.
* The system must provide CLI inspection and lifecycle verbs: `pm-mcp status` to inspect the runtime, active plans, build slots, and running jobs across the machine, and `pm-mcp drain` to stop the runtime gracefully before an upgrade.
* On `SIGTERM`/`SIGINT` (including via `pm-mcp drain`), the runtime must stop admitting new jobs, allow running build/git/CI jobs to finish up to the configured drain timeout, record the remaining jobs as `killed`, terminate warm LSP child processes, and exit cleanly.
* The system must detect a version mismatch between an installed binary and the running runtime during `pm-mcp enter`, relay connection, and `pm-mcp status`, and recommend `pm-mcp drain`.
* The system must recover state on every runtime start before accepting calls: release stale locks and leases whose owning process (PID plus start time) is no longer alive, complete or roll back any interrupted `move-journal.json`, and mark orphaned `running` jobs as `killed` (terminating their process groups if still alive) without blind re-execution.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and the link:specification/move-journal.adoc[Move Journal Specification] for implementation details.

[#PM-ARCH-9]
=== PM-ARCH-9: Logical Plan Sessions & Connection-Independent Continuation

A working session with PM-MCP is a logical sequence of calls against one plan or epic, carried by persisted state rather than by any connection or conversation.

* The system must identify a logical session solely by its `plan_id` or `epic_id` and represent it solely by that scope's persisted files.
* The system must execute every mutating call as exactly one state transition that is fully persisted before the response is returned, so that a lost response never loses or duplicates a transition.
* The system must allow a logical session to continue either by following a link from the last representation or by calling `pm_state(plan_id | epic_id)` from any host connection, host, sub-agent, or later conversation, with identical results for identical persisted state.
* The system must allow multiple host connections to address the same logical session concurrently, serializing mutations through the scope lock (`PM-WF-4`).
* The system must let long-running jobs started in a logical session complete while no host is connected, exposing their outcome to the next call on that scope.
* The system may vary connection-dependent rendering (bounded vs. progress waits, elicitation vs. `*.blocked` operator fallback) by the capabilities of the calling host connection, never by persisted state differences.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification] for implementation details.
