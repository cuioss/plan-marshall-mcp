== Core Architecture (PM-ARCH)

[#PM-ARCH-1]
=== PM-ARCH-1: Process Ownership & Always-On Runtime

The system must strictly divide responsibilities between deterministic process execution and probabilistic model judgment. All state tracking, transition sequencing, gate evaluations, and command assembly belong to the system, while the model is tasked exclusively with judgment-based contributions.

* The system must execute all workflow state machines, state transitions, quality gate evaluations, and command assembly inside the always-on runtime process (`pm-mcpd`), confining model contributions exclusively to judgment artifacts (request clarification, solution outline authoring, code implementation, finding triage, and commit/pull request descriptions).
* The system must run as a single always-on runtime process (daemon) per machine and `PM_MCP_BASE`, under the operating system privileges of the local developer user, whose lifetime and jobs are independent of any host conversation or host connection.
* The system must let host coding agents reach the runtime exclusively through a thin `pm-mcp serve` STDIO relay spawned by the host per connection, with zero listening network ports.
* The runtime must open no TCP or UDP listener: its only listener is a user-private Unix domain socket that serves MCP (`/mcp`) to the relays and the local REST API (`/api/v1`) to the CLI and the optional web server, and authenticates every request with the runtime token (`PM-SEC-4`).
* The system must make the runtime the only writer of every store: the CLI (`pm-mcp`) and the optional web server (`pm-mcp-web`) hold no store logic and change state only through requests to the local API, which the runtime validates, locks, audits, and executes.
* The CLI must read directly only a closed list of files, which it never writes: `state/runtime.json`, `state/install-records.json` with the target files recorded there, the session-start hook files (the enrolment files for the project resolution rule, and the session logs, `mcp/status.json`, and digest sidecars of the project's plans, epics, and workspace scope), `machine-config.json` (for the drain bound), and `run/runtime.token` (authentication), as listed in link:specification/cli-and-security/01-cli-and-installer.adoc#cli-file-reads[CLI, Coordination & Security Specification, Direct file reads]; the read-only codec for these files lives in `pm-mcp-api`. The CLI's only lock is `runtime-start.lock`, and exactly four verbs work without a running runtime and never start one: `pm-mcp status`, `pm-mcp drain` (which waits at most the drain timeout plus the termination grace period plus a fixed 10 seconds), `pm-mcp hook session-start`, and `pm-mcp client status`.
* The system may run an optional web server (`pm-mcp-web`), off by default and started and stopped only by operator verbs, as the only process that opens a TCP listener; it is a client of the local API like the CLI and never serves MCP (`PM-SEC-4`, `PM-SEC-7`).
* The system must enforce mutual exclusion across concurrent sessions, sub-agents, and projects using OS-level `FileChannel.lock()` advisory locks and atomic write-then-rename operations within the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/` and `<PM_MCP_BASE>/locks/`.
* The system must compile workflow definitions, state stores, tools, client profiles, vocabulary skills, and background services into the native binaries of one release (the CLI `pm-mcp`, the runtime `pm-mcpd`, the job launcher `pm-mcp-exec`, and the web server `pm-mcp-web`), installed side by side and starting each other by path, guaranteeing that all components operate on an identical release version without runtime drift.
* The system must reject any architecture where process ordering, transition permissions, or parameter assembly depend on prose instructions or client-side prompt compliance.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-ARCH-2]
=== PM-ARCH-2: Local-by-Design & Zero External Cloud Dependency

The system must operate entirely on the developer's workstation, directly interacting with local repository trees and worktrees without reliance on cloud intermediaries.

* The system must execute all services, workflow transitions, and state management locally on the developer's workstation without requiring remote infrastructure, cloud-hosted backends, or telemetry reporting.
* The system must enforce workspace confinement, restricting all file reads, file modifications, and process executions strictly to the enrolled project root directory and its active linked worktrees, with exactly these exceptions:
** Jobs, confined per `PM-SEC-5`: they read the whole filesystem except `<PM_MCP_BASE>`, write only their own project root (with its worktrees), declared toolchain caches, `/tmp`, and `/dev`, and execute the enrolled toolchains.
** The runtime's own instance directory `<PM_MCP_BASE>`.
** The client bundle installer's targets: the host configuration in the user's home directory and, for a project-scope install, the project's host configuration files (`PM-DIST-2`).
** The toolchains and JDKs that jobs execute.
* The system must reject any operation attempting to access or modify filesystem paths outside the enrolled project boundary unless explicitly authorized by the human operator through the operator channel.
* The system must never transmit lesson or finding content to a vendor or upstream issue tracker automatically; content classified for an upstream audience stays in the local store until an explicit, content-reviewed operator action releases it, and a lesson classified `local` must never be offered for upstream filing.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/filesystem-layout.adoc[Filesystem Layout Specification], and link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.

[#PM-ARCH-3]
=== PM-ARCH-3: STDIO Host Transport, Local Relay & Frontier Protocol Compliance

Hosts must connect over the Model Context Protocol (MCP) `stdio` transport, relayed to the always-on runtime over a user-private local channel, targeting the frontier MCP `2026-07-28` specification.

* The system must communicate with host coding agents (`claude`, `opencode`, `antigravity`, `codex`) exclusively over standard input (`stdin`) and standard output (`stdout`) of the `pm-mcp serve` relay.
* The relay must forward MCP messages in both directions (requests, responses, notifications, and server-to-client requests such as elicitation) between the host and the runtime without interpreting them, preserving JSON-RPC `id` values.
* The runtime must serve MCP only over a Unix domain socket restricted to the owning OS user, omitting all TCP/UDP listeners.
* The relay must reserve `stdout` strictly for newline-delimited JSON-RPC 2.0 MCP messages and route all diagnostic logging to `stderr`; the runtime logs to `<PM_MCP_BASE>/logs/daemon.log`.
* The system must target the MCP `2026-07-28` protocol version exclusively, omitting legacy protocol versions (`2025-11-25`, `2024-11-05`) and backward-compatibility shims.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification] for implementation details.

[#PM-ARCH-4]
=== PM-ARCH-4: Stateless Requests & Explicit Scope Addressing

The system must operate without transport-level session state, evaluating every request entirely from explicit scope identifiers and persisted filesystem records.

* The system must process every MCP request statelessly, including at the transport: the runtime keeps no MCP transport session and no per-connection state. The relay attaches the host's `initialize` data (protocol version, capabilities, `clientInfo`) and its connection metadata to every forwarded request, so each request is self-describing and a runtime restart loses only the requests in flight.
* The system must require every stateful workflow invocation to carry an explicit logical scope identifier (`plan_id`, `epic_id`, or the reserved `plan_id` value `NO_PLAN` for the project's one workspace scope, `PM-TOOL-1`) and, when addressing an entity-specific transition, the entity identifier within the link ID.
* The system must resolve the client identity of scope-addressed calls exclusively from the last row of the scope's persisted session log (`sessions.jsonl`) and the target project root exclusively from the project's enrolment (the enrolled `project_root` of the per-project machine store the scope lives in), rejecting client-supplied working directory or client-type overrides.
* The system must answer every workflow query and validate every transition entirely from persisted filesystem state, guaranteeing zero state loss across host restarts, context window compactions (`/clear`), or process restarts.
* The system must distinguish exactly two request classes: *scope-addressed* requests carry `plan_id` or `epic_id` (and the entity where applicable); *workspace-addressed* requests take their project from the relay's `PM-MCP-Workspace` header: `pm_plans`, `pm_epics`, `pm_start`, the scoped tools (`pm_state`, `pm_do`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`) with `plan_id: "NO_PLAN"`, the upstream pass-through tools `up_*`, the scope-less resource reads (`pm://architecture/*`, `pm://project/*`, `pm://workspace/*`, `skill://pm/...`), and `resources/templates/list`. There are no other requests without a scope; a scoped tool called without `plan_id` or `epic_id` is refused (`PM-TOOL-1`).
* The system must verify, for every workspace-addressed request, that the `PM-MCP-Workspace` header names an enrolled project root, refusing the request with `project_not_enrolled` otherwise.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/filesystem-layout.adoc[Filesystem Layout Specification], the link:specification/store-schemas.adoc[Store Schemas Specification], and the link:specification/identifiers.adoc[Identifier Registry] for implementation details.

[#PM-ARCH-5]
=== PM-ARCH-5: Worktree-Bound Plan Execution & Main-Bound Orchestrator Location

Plan state must live outside the repository and plan execution must be isolated inside worktrees to protect the main checkout; git-tracked orchestrator state belongs to the repository's main branch, is edited only in the one shared epic worktree, and reaches the main branch only through a branch merge.

* The system must keep a plan's state directory in the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/plans/<plan_id>/` for the plan's whole life and never move it; a plan worktree (`.marshall/local/worktrees/<plan_id>/`) is only a git checkout created for execution and finalize and removed afterwards, and the plan's `status.json` records its `worktree_path` (or `null` while none exists).
* The system must clear `worktree_path` in the same transaction that records a worktree's removal, so that no store keeps pointing at a removed worktree.
* The system must keep no state in the repository's git-ignored `.marshall/local/`, which holds only worktrees and temporary files, so that deleting it loses no plan data.
* The system must ensure that the repository's main checkout working tree remains clean and unaffected by uncommitted plan execution artifacts at all times.
* The system must isolate all mutations to git-tracked orchestrator state (epic ledgers, inbox messages, landing records, and epic specifications) within one shared, long-lived epic worktree on one fixed branch, incorporating changes into the main branch strictly through a monitored branch landing that never removes that worktree.
* The system must resolve every read and write of git-tracked orchestrator state, including those made on behalf of child plans, to the shared epic worktree copy, and must never treat the primary checkout's copy as authoritative while the epic worktree exists.
* The system must resolve any plan directory and its worktree from its `plan_id` without requiring the client or model to provide filesystem paths.
* The system must start every job in the working directory that matches the plan's worktree presence at job start (the worktree root while the plan's persisted `worktree_path` is set; the main checkout while it is `null` and for plan-less jobs); the system must never run a job that removes a worktree with a working directory inside that worktree, and scripts receive the plan identity only through their own arguments.

See the link:specification/filesystem-layout.adoc[Filesystem Layout Specification], link:specification/job-runtime.adoc[Job Runtime Specification], and link:specification/dispatch-and-effort.adoc[Dispatch & Effort Specification] for implementation details.

[#PM-ARCH-6]
=== PM-ARCH-6: Filesystem State Persistence & Cache-Only Process Memory

All durable workflow and coordinator data must reside in structured filesystem stores, with process memory functioning strictly as a transient cache.

* The system must persist all authoritative workflow states, tasks, findings, references, locks, build jobs, and audit events directly in filesystem files formatted as JSON or JSONL.
* The system must treat all in-memory process data structures as disposable caches, ensuring that any process exit, crash, or restart leaves persistent state intact and uncorrupted.
* The system must store credentials exclusively within the operating system credential store or its permission-guarded fallback file store (`<PM_MCP_BASE>/credentials/`), keeping secrets in process memory only for the duration of the active request.
* The system must include a mandatory `format_version` integer property in every persisted JSON and JSONL state file, including the operator files (enrolment files and the credential files of `PM-CRED-3`).
* The system must validate the `format_version` of every store it reads and accept exactly the binary's current version, refusing any other with a named reason (`format_outdated`, `format_newer`) and never migrating a store on runtime start; the git-tracked team configuration and workflow units are never rewritten by the runtime, and a new binary's default changes reach them only through the project setup workflow (`PM-EXT-7`).

See the link:specification/store-schemas.adoc[Store Schemas Specification] and link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-ARCH-7]
=== PM-ARCH-7: Runtime & Relay Lifecycle, Crash Recovery & Job Drain

The runtime must run continuously and recover deterministically from crashes, while relays come and go with host connections without affecting runtime state or jobs.

* The system must start the runtime on demand when a CLI command that needs it (the `pm-mcp serve` relay included) finds none running, detached from the command's process group and session so that no host action on the relay terminates it, and must optionally support start at login through the per-user OS service manager; on-demand start stays the default on every platform.
* The system must ensure that relay termination (`stdin` EOF or signals) closes only that host connection and never cancels, drains, or kills jobs or alters persisted state.
* The system must provide CLI inspection and lifecycle verbs: `pm-mcp status` to inspect the runtime, active plans, build slots, and running jobs across the machine through the local API, reporting the runtime `running` only after an authenticated round trip and `not running` from the absent or dead runtime record without starting it; and `pm-mcp drain` to stop the runtime gracefully before an upgrade by signalling the recorded runtime process after verifying its PID and start instant.
* The system must report to the operator every non-terminal plan or epic that has no pending condition, awaits no event, and whose last transition or model call is older than a compiled threshold as `stalled` (in `pm-mcp status`, the web app, and the epic view), record one `plan_stalled` audit record per stall episode, and never show it in a model-facing representation.
* On `SIGTERM`/`SIGINT` (including via `pm-mcp drain`), the runtime must stop admitting new jobs, allow running jobs and in-process operations to finish up to the configured drain timeout, record the remaining jobs as `killed` and release only their build slots (merge-queue and review-bot leases are left in place, become orphaned at the next start, and are adopted or released by the recovery evidence rules exactly as after a crash), terminate warm LSP child processes, and exit cleanly.
* The system must detect a version mismatch between an installed binary and the running runtime during `pm-mcp enter`, relay connection, and `pm-mcp status`, and recommend `pm-mcp drain`.
* The system must start the runtime in a fixed order: acquire the singleton lock first (a runtime that loses it exits immediately with status `0` without writing anything, audit records included), remove a stale socket and stale runtime record only while holding that lock, verify directories and permissions, run only bounded verification (audit chain head and incremental chain, workflow definitions), write a fresh runtime token, bind the socket, and become ready; no store is migrated at start (`PM-ARCH-6`), and enrolment integrity is verified per project in its recovery.
* The system must recover each project's state after bind, lazily on the first call addressing the project and in a background pass, and must never serve a call addressing a project before its recovery has finished: such a call waits for it, bounded, and on expiry returns the retryable error `runtime_recovering`. Recovery must release stale locks whose owning process (PID plus start time) is no longer alive, mark leases served by a dead runtime instance as orphaned so that their owning scope (plan, epic, or workspace) adopts them on its next call, releasing a lease only on positive evidence of abandonment, roll forward any interrupted per-scope transaction journal, and mark orphaned `running` jobs as `killed` without blind re-execution, signalling nothing for a job spawned before the current system boot or whose record never received its PID (a job counts as running only after its record carries `pid` and `process_started_at`) and otherwise terminating its process group if still alive; a workflow state bound to such a job settles with the outcome `killed`, which its workflow routes explicitly, and no job is started again except through a declared transition.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], the link:specification/workflow-dsl/02-units-jobs-decisions.adoc#job-state-binding[Workflow DSL Specification, Job State Entry & Binding], and the link:specification/timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification] (drain timeout, start timeout, project recovery wait, lease expiry) for implementation details.

[#PM-ARCH-8]
=== PM-ARCH-8: Logical Plan Sessions & Connection-Independent Continuation

A working session with PM-MCP is a logical sequence of calls against one plan or epic, carried by persisted state rather than by any connection or conversation.

* The system must identify a logical session solely by its `plan_id` or `epic_id` and represent it solely by that scope's persisted files.
* The system must execute every mutating call as exactly one state transition that is fully persisted before the response is returned, so that a lost response never loses or duplicates a transition.
* The system must allow a logical session to continue either by following a link from the last representation or by calling `pm_state(plan_id | epic_id)` from any host connection, host, sub-agent, or later conversation, with identical results for identical persisted state.
* The system must allow multiple host connections to address the same logical session concurrently, serializing mutations through the scope lock (`PM-WF-4`).
* The system must let long-running jobs started in a logical session complete while no host is connected, exposing their outcome to the next call on that scope.
* The system may vary connection-dependent rendering (bounded vs. progress waits, elicitation vs. session delivery of a question record) by the capabilities of the calling host connection, never by persisted state differences.
