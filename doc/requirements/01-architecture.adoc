== Core Architecture (PM-ARCH)

[#PM-ARCH-1]
=== PM-ARCH-1: Process Ownership & Always-On Runtime

The system must strictly divide responsibilities between deterministic process execution and probabilistic model judgment. All state tracking, transition sequencing, gate evaluations, and command assembly belong to the system, while the model is tasked exclusively with judgment-based contributions.

* The system must execute all workflow state machines, state transitions, quality gate evaluations, and command assembly inside the always-on runtime process (`pm-mcpd`), confining model contributions exclusively to judgment artifacts (request clarification, solution outline authoring, code implementation, finding triage, and commit/pull request descriptions).
* The system must drive the interior of every plan and epic itself: every step that needs no model is server logic, and every step that needs one is a task of a role served by a supervised headless worker that the system starts as a model job (job kind `llm`) through the headless command line of an enrolled harness (`PM-WF-5`, `PM-WORK-1` to `PM-WORK-3`, `PM-EXEC-1`); it must never depend on a host dispatching a sub-agent or on an interactive session calling it. The interactive session is the entry (it turns the user's words into a plan or an epic and drives the bootstraps and the project setup) and a viewer; it may take a task as an optional worker (`PM-WORK-5`), and no plan or epic waits on it.
* The system must run as a single always-on runtime process (daemon) per machine and `PM_MCP_BASE`, under the operating system privileges of the local developer user, whose lifetime and jobs are independent of any host conversation or host connection.
* The system must let host coding agents reach the runtime exclusively through a thin `pm-mcp serve` STDIO relay spawned by the host per connection, never through a network port.
* The runtime must open no TCP or UDP listener unless the operator enabled web access: without it its only listener is a user-private Unix domain socket that serves MCP (`/mcp`) to the relays and the local REST API (`/api/v1`) to the command-line binaries `pm-mcp` and `pm-operator`, and authenticates every request with the runtime token (`PM-SEC-4`).
* The system must make the runtime the only writer of every store: the command-line binaries (`pm-mcp`, `pm-operator`) and a paired browser hold no store logic and change state only through requests to the local API, which the runtime validates, locks, audits, and executes.
* The command-line binaries must read directly only a closed list of files, which they never write: both read `state/runtime.json`, `run/runtime.token` (authentication), and `state/install-records.json` with the target files recorded there (the drift checks of `pm-mcp enter` and `pm-operator client status`); `pm-mcp` alone reads the hint file that an entry command names with `pm-mcp enter --hint-file` (the user's words, written by the entry command under `.marshall/local/temp/`); `pm-operator` alone reads `machine-config.json` (for the drain bound of `pm-operator drain`), as listed in link:specification/cli-and-security/01-cli-and-installer.adoc#cli-file-reads[CLI, Coordination & Security Specification, Direct file reads]; the read-only codec for these files lives in `pm-api`. The only lock either binary takes is `runtime-start.lock`, and exactly three verbs work without a running runtime and never start one: `pm-operator status`, `pm-operator drain` (which waits at most the drain timeout plus the termination grace period plus the fixed margin of the link:specification/timeouts/02-runtime-leases-operator-web.adoc#drain-timeout[Timeouts & Budgets Specification, Drain Timeout]), and `pm-operator client status`.
* The runtime may serve web access itself, off by default and enabled and disabled only by operator verbs (`pm-operator web enable|disable`): one additional HTTP listener of `pm-mcpd`, the only TCP listener of the system apart from the loopback fallback of `PM-SEC-4`, which routes only the web app and the local API, never serves MCP, and never accepts the runtime token; no separate web server process exists (`PM-SEC-4`, `PM-SEC-7`).
* The system must enforce mutual exclusion across concurrent sessions, jobs, and projects using OS-level `FileChannel.lock()` advisory locks and atomic write-then-rename operations within the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/` and `<PM_MCP_BASE>/locks/`.
* The system must compile workflow definitions, state stores, tools, client profiles, vocabulary skills, and background services into the four native binaries of one release (the relay binary `pm-mcp`, the operator CLI `pm-operator`, the runtime `pm-mcpd`, and the job launcher `pm-exec`), installed side by side and starting each other by path, guaranteeing that all components operate on an identical release version without runtime drift.
* The system must reject any architecture where process ordering, transition permissions, or parameter assembly depend on prose instructions or client-side prompt compliance.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-ARCH-2]
=== PM-ARCH-2: Local-by-Design & Zero External Cloud Dependency

The system must operate entirely on the developer's workstation, directly interacting with local repository trees and worktrees without reliance on cloud intermediaries.

* The system must execute all services, workflow transitions, and state management locally on the developer's workstation without requiring remote infrastructure, cloud-hosted backends, or telemetry reporting.
* The system must enforce workspace confinement, restricting all file reads, file modifications, and process executions strictly to the enrolled project root directory and its active linked worktrees, with exactly these exceptions:
** Jobs, confined per `PM-SEC-5`: they read the whole filesystem except `<PM_MCP_BASE>`, write only their own project root (with its worktrees), declared toolchain caches, `/tmp`, and `/dev`, and execute the enrolled toolchains; a model job (job kind `llm`) additionally reads its own job-private directory `<PM_MCP_BASE>/run/jobs/<job_id>/` (the one exception to the rule that jobs never read `<PM_MCP_BASE>`; no job writes there), writes the sub-paths of the harness's home that its client profile declares (its login or credential file, caches, and session directory; never a settings or hook file the client bundle manages), uses the network, and authenticates with the harness's own login, never with a PM-MCP credential.
** The runtime's own instance directory `<PM_MCP_BASE>`, which holds every file the runtime owns or trusts (the socket and the job-private directories included); the runtime keeps none of them in the system temporary directory.
** The installation directory `<PM_MCP_HOME>` with its two `PATH` symbolic links (`PM-DIST-1`).
** The per-user service unit that `pm-operator runtime install` writes for the OS service manager (`PM-ARCH-7`).
** The client bundle installer's targets: the host configuration in the user's home directory and, for a project-scope install, the project's host configuration files (`PM-DIST-2`).
** The read of the user's global git configuration by the native git variant, as untrusted input (`PM-SEC-1`).
** The toolchains and JDKs that jobs execute.
* The system must reject any operation attempting to access or modify filesystem paths outside the enrolled project boundary unless explicitly authorized by the human operator through the operator channel.
* The system must never transmit lesson or finding content to a vendor or upstream issue tracker automatically; content classified for an upstream audience stays in the local store until an explicit, content-reviewed operator action releases it, and a lesson classified `local` must never be offered for upstream filing.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/filesystem-layout.adoc[Filesystem Layout Specification], and link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.

[#PM-ARCH-3]
=== PM-ARCH-3: STDIO Host Transport, Local Relay & Frontier Protocol Compliance

Hosts must connect over the Model Context Protocol (MCP) `stdio` transport, relayed to the always-on runtime over a user-private local channel, targeting the frontier MCP `2026-07-28` specification.

* The system must communicate with host coding agents (`claude`, `opencode`, `antigravity`, `codex`) exclusively over standard input (`stdin`) and standard output (`stdout`) of the `pm-mcp serve` relay.
* The relay must forward MCP messages in both directions (requests, responses, notifications, and server-to-client requests such as elicitation) between the host and the runtime without interpreting them, preserving JSON-RPC `id` values.
* The runtime must serve MCP only over a Unix domain socket restricted to the owning OS user, never over a TCP or UDP listener (`PM-SEC-4`).
* The relay must reserve `stdout` strictly for newline-delimited JSON-RPC 2.0 MCP messages and route all diagnostic logging to `stderr`; the runtime logs to `<PM_MCP_BASE>/logs/daemon.log`.
* The system must target the MCP `2026-07-28` protocol version exclusively, omitting legacy protocol versions (`2025-11-25`, `2024-11-05`) and backward-compatibility shims.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification] for implementation details.

[#PM-ARCH-4]
=== PM-ARCH-4: Stateless Requests & Explicit Scope Addressing

The system must operate without transport-level session state, evaluating every request entirely from explicit scope identifiers and persisted filesystem records.

* The system must process every MCP request statelessly, including at the transport: the runtime keeps no MCP transport session and no per-connection state. The relay attaches the host's `initialize` data (protocol version, capabilities, `clientInfo`) and its connection metadata to every forwarded request, so each request is self-describing and a runtime restart loses only the requests in flight.
* The system must require every stateful workflow invocation to carry an explicit logical scope identifier (`plan_id`, `epic_id`, or the reserved `plan_id` value `NO_PLAN` for the project's one workspace scope, `PM-TOOL-1`) and, when addressing an entity-specific transition, the entity identifier within the link ID.
* The system must resolve the client profile of a session's call from the client its relay declares (`pm-mcp serve --client <client>`, written by the client bundle into the host's MCP configuration, `PM-CLIENT-1`) and of a worker's call from its job record, and the target project root exclusively from the project's enrolment (the enrolled `project_root` of the per-project machine store the scope lives in), rejecting client-supplied working directory or client-type overrides.
* The system must answer every workflow query and validate every transition entirely from persisted filesystem state, guaranteeing zero state loss across host restarts, worker replacements, context compactions, or process restarts.
* The system must distinguish exactly two request classes: *scope-addressed* requests carry `plan_id` or `epic_id` (and the entity where applicable); *workspace-addressed* requests take their project from the relay's `PM-MCP-Workspace` header: `pm_plans`, `pm_epics`, the scoped tools (`pm_state`, `pm_do`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`) with `plan_id: "NO_PLAN"` (including a pending plan or epic bootstrap addressed by its `entry_id` as `entity`, `PM-TOOL-1`), the upstream pass-through tools `up_*`, the scope-less resource reads (`pm://architecture/*`, `pm://project/*`, `pm://workspace/*`, `skill://pm/...`), and `resources/templates/list`. There are no other requests without a scope; a scoped tool called without `plan_id` or `epic_id` is refused (`PM-TOOL-1`).
* The system must verify, for every workspace-addressed request, that the `PM-MCP-Workspace` header names an enrolled project root, refusing the request with `project_not_enrolled` otherwise.

[#PM-ARCH-5]
=== PM-ARCH-5: Worktree-Bound Plan Execution & Main-Bound Orchestrator Location

Plan state must live outside the repository and plan execution must be isolated inside worktrees to protect the main checkout; git-tracked orchestrator state belongs to the repository's main branch, is edited only in the one shared epic worktree, and reaches the main branch only through a branch merge.

* The system must keep a plan's state directory in the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/plans/<plan_id>/` for the plan's whole life and never move it; a plan worktree (`.marshall/local/worktrees/<plan_id>/`) is only a git checkout created for execution and finalize and removed afterwards, and the plan's `status.json` records its `worktree_path` (or `null` while none exists).
* The system must clear `worktree_path` in the same transaction that records a worktree's removal, so that no store keeps pointing at a removed worktree.
* The system must keep no state in the repository's git-ignored `.marshall/local/`, which holds only worktrees and temporary files, so that deleting it loses no plan data.
* The system must ensure that the repository's main checkout working tree remains clean and unaffected by uncommitted plan execution artifacts at all times.
* The system must isolate all mutations to git-tracked orchestrator state (epic ledgers, inbox messages, landing records, and epic specifications) within one shared, long-lived epic worktree on one fixed branch, incorporating changes into the main branch strictly through a monitored branch landing that never removes that worktree.
* The system must resolve every read and write of git-tracked orchestrator state, including those made on behalf of child plans, to the shared epic worktree copy, and must never treat the primary checkout's copy as authoritative while the epic worktree exists.
* The system must resolve any plan directory and its worktree from its `plan_id` without requiring the client or model to provide filesystem paths.
* The system must start every job in the working directory that matches the plan's worktree presence at job start (the worktree root while the plan's persisted `worktree_path` is set; the main checkout while it is `null` and for plan-less jobs; the injection screener job alone runs in an empty job-private directory, `PM-SEC-1`); the system must never run a job that removes a worktree with a working directory inside that worktree, and scripts receive the plan identity only through their own arguments.

See the link:specification/filesystem-layout.adoc[Filesystem Layout Specification], link:specification/job-runtime.adoc[Job Runtime Specification], and link:specification/model-work.adoc[Model Work Specification] for implementation details.

[#PM-ARCH-6]
=== PM-ARCH-6: Filesystem State Persistence & Cache-Only Process Memory

All durable workflow and coordinator data must reside in structured filesystem stores, with process memory functioning strictly as a transient cache.

* The system must persist all authoritative workflow states, tasks, findings, references, locks, build jobs, and audit events directly in filesystem files formatted as JSON or JSONL.
* The system must treat all in-memory process data structures as disposable caches, ensuring that any process exit, crash, or restart leaves persistent state intact and uncorrupted.
* The system must store credentials exclusively within the operating system credential store or its permission-guarded fallback file store (`<PM_MCP_BASE>/credentials/`), keeping secrets in process memory only for the duration of the active request.
* The system must include a mandatory `format_version` integer property in every persisted JSON and JSONL state file, including the operator files (`machine-config.json`, the per-project `local-config.json`, the enrolment files, the harness enrolment `harnesses.json`, and the credential files of `PM-CRED-3`).
* The system must validate the `format_version` of every store it reads and accept exactly the binary's current version, refusing any other with a named reason (`format_outdated`, `format_newer`) and never migrating a store on runtime start; the git-tracked team configuration and workflow units are never rewritten by the runtime, and a new binary's default changes reach them only through the project setup workflow (`PM-EXT-7`).

See the link:specification/store-schemas.adoc[Store Schemas Specification] and link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-ARCH-7]
=== PM-ARCH-7: Runtime & Relay Lifecycle, Crash Recovery & Job Drain

The runtime must run continuously and recover deterministically from crashes, while relays come and go with host connections without affecting runtime state or jobs.

* The system must start the runtime on demand when a command of `pm-mcp` or `pm-operator` that needs it (the `pm-mcp serve` relay included) finds none running, detached from the command's process group and session so that no host action on the relay terminates it, and must optionally support start at login through the per-user OS service manager; on-demand start stays the default on every platform.
* The system must ensure that relay termination (`stdin` EOF or signals) closes only that host connection and never cancels, drains, or kills jobs or alters persisted state.
* The system must provide the inspection and lifecycle verbs of the operator CLI: `pm-operator status` to inspect the runtime, active plans, build slots, and running jobs across the machine through the local API, reporting the runtime `running` only after an authenticated round trip and `not running` from the absent or dead runtime record without starting it; and `pm-operator drain` to stop the runtime gracefully before an upgrade by signalling the recorded runtime process after verifying its PID and start instant.
* The system must report to the operator as `stalled` (in `pm-operator status`, the web app, and the epic view) every non-terminal plan or epic that has no pending condition, awaits no event, and whose last transition or task progress is older than a compiled threshold, record one `plan_stalled` audit record per stall episode, naming the cause, and never show it in a model-facing representation; a role the supervisor stopped serving is reported to the operator by the start-failure guard (`PM-WORK-3`), and its tasks take their fallback.
* On `SIGTERM`/`SIGINT` (including via `pm-operator drain`), the runtime must stop admitting new jobs and offering new tasks, end idle warm workers, allow running jobs, tasks, and in-process operations to finish up to the configured drain timeout, record the remaining jobs as `killed`, release their build and model slots and task leases (their tasks are offered again after the next start) (merge-queue and review-bot leases are left in place, become orphaned at the next start, and are adopted or released by the recovery evidence rules exactly as after a crash), terminate warm LSP child processes, and exit cleanly.
* The system must detect a version mismatch between an installed binary and the running runtime during `pm-mcp enter`, relay connection, and `pm-operator status`, and recommend `pm-operator drain`.
* The system must start the runtime in a fixed order: acquire the singleton lock first (a runtime that loses it exits immediately with status `0` without writing anything, audit records included), remove a stale socket and stale runtime record only while holding that lock, verify directories and permissions, run only bounded verification (audit chain head and incremental chain, workflow definitions), write a fresh runtime token, bind the socket, and become ready; no store is migrated at start (`PM-ARCH-6`), and enrolment integrity is verified per project in its recovery.
* The system must recover each project's state after bind, lazily on the first call addressing the project and in a background pass, and must never serve a call addressing a project before its recovery has finished: such a call waits for it, bounded, and on expiry returns the retryable error `runtime_recovering`. Recovery must release stale locks whose owning process (PID plus start time) is no longer alive, mark leases served by a dead runtime instance as orphaned so that their owning scope (plan, epic, or workspace) adopts them on its next call, releasing a lease only on positive evidence of abandonment, roll forward any interrupted per-scope transaction journal, and mark orphaned `running` jobs, workers included, as `killed` without blind re-execution, fencing their generations and returning their leased tasks to the queue, signalling nothing for a job spawned before the current system boot or whose record never received its PID (a job counts as running only after its record carries `pid` and `process_started_at`) and otherwise terminating its process group if still alive; a workflow state bound to such a job settles with the outcome `killed`, which its workflow routes explicitly, and no job is started again except through a declared transition.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/workflow-dsl/02-units-jobs-decisions.adoc#job-state-binding[Workflow DSL Specification, Job State Entry & Binding], and link:specification/timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification] (drain timeout, start timeout, project recovery wait, lease expiry) for implementation details.

[#PM-ARCH-8]
=== PM-ARCH-8: Server-Driven Continuation & Connection Independence

A plan or epic is carried by persisted state and continued by the server, never by a connection or conversation.

* The system must identify a plan or epic solely by its `plan_id` or `epic_id` and represent it solely by that scope's persisted files.
* The system must execute every mutating call as exactly one state transition that is fully persisted before the response is returned, so that a lost response never loses or duplicates a transition.
* The system must continue every plan and epic by itself after its creation, whether or not a host is connected, and must let any host connection, host, or later conversation view it through `pm_state(plan_id | epic_id)`, with identical results for identical persisted state.
* The system must bind the connection of a worker to its job and generation: it is authenticated by the job's own token, may address only the task entities leased to its generation with its tools, reads resources only read-only and only of the worker's own project, and carries no session identity (`PM-SEC-4`, `PM-WORK-2`).
* The system must allow several connections (workers and sessions) to address the same scope concurrently, serializing mutations through the scope lock (`PM-WF-4`).
* The system may vary connection-dependent rendering (bounded vs. progress waits) by the capabilities of the calling host connection, never by persisted state differences.
