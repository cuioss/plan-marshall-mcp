== MCP Tool & Resource Surface (PM-TOOL)

[#PM-TOOL-1]
=== PM-TOOL-1: Core Workflow Verb Set (pm_start, pm_state, pm_do)

The system must expose workflow discovery, state inspection, and state transitions through a minimal, uniform set of MCP tools.

* The system must provide `pm_start(entry_id, request | issue_number | lesson_id | recipe_id, plan_slug?, base_branch?, recipe_params?)` to initialize a new plan from any of the four supported sources (`request`, `issue`, `lesson`, or `recipe`) after an unscoped entry bootstrap (`pm-mcp enter`), consuming the pending entry record identified by `entry_id` by atomically relocating it into the created plan's `mcp/entry.json` and returning the plan's initial state representation; epic membership is taken only from that entry record's `from_epic` (written by the emitted `pm-mcp enter … --from-epic` command), never from a `pm_start` parameter.
* The system must provide `pm_state(plan_id | epic_id | scope=steward, scope?, entity?, dispatch_id?)` to return the current TOON representation of a plan or epic, or of a specific entity within that scope when invoked by a dispatched sub-agent.
* The system must provide `pm_plans()` and `pm_epics(include_archived?)` for unscoped discovery, returning concise one-line status summaries of active plans and epics (and, with `include_archived`, archived epics) together with per-root scan coverage, so an empty listing is distinguishable from a root that was not scanned.
* The system must provide `pm_do(plan_id | epic_id | scope=steward, link, args?, scope?, entity?, dispatch_id?)` as the sole state transition verb, executing forward transitions, submissions, sub-agent return reports (`returned:<dispatch_id>`), job polling (`wait:<job>`), and job cancellations (`cancel:<job>`).
* The system must declare `args` in `pm_do` as a generic object at the MCP schema layer and enforce strict server-side schema validation (`additionalProperties: false`, closed types) against the target link's parameter specification before executing any transition.
* The system must resolve all filesystem paths, worktree locations, and branch names server-side from `plan_id` or `epic_id`, prohibiting model-supplied paths in tool parameters.

See the link:specification/mcp-tools.adoc[MCP Tools Specification] and link:specification/hypermedia-format.adoc[Hypermedia Format Specification] for implementation details.

[#PM-TOOL-2]
=== PM-TOOL-2: Orthogonal Service Capability Tools (pm_build, pm_lsp)

The system must expose build execution and semantic code intelligence as orthogonal service tools that assist development without altering workflow phases.

* The system must provide `pm_build(plan_id?, command, module?, test_filter?, expect?, job_id?)` to execute builds through the runtime's build server (in the plan's worktree, or in the main checkout when `plan_id` is omitted) using abstract domain verbs (`compile`, `test`, `module-tests`, `quality-gate`, `verify`, `coverage`, `format-check`) rather than raw shell command lines; the optional `expect` (`green` by default, or `red`) declares an intentionally failing run, which files no finding, is surfaced when it unexpectedly passes, and never satisfies a build-freshness gate.
* The system must block `pm_build` for the same server-chosen bounded window as a `wait` link (`PM-IMPL-4`) and, when the build is not finished, return status `running` with its `job_id`; calling `pm_build` again with that `job_id` continues waiting on the same build.
* The system must return structured outcomes from `pm_build` containing a closed-enum status, test and error counts, and file-located failure diagnostics, referencing the full raw output exclusively via a resource URI (`pm://plan/{plan_id}/builds/{job_id}/log`).
* The system must provide `pm_lsp(plan_id, op, path?, line?, character?, query?, new_name?)`, scoped to the plan's worktree (`path` repository-relative), to execute semantic code operations (`workspace_symbol`, `document_symbol`, `definition`, `references`, `hover`, `diagnostics`, `rename`) against the daemon's warm language server pool.
* The system must exclude all privileged and operator-only actions from the MCP tool surface, restricting them exclusively to MCP elicitation or the operator CLI.

See the link:specification/mcp-tools.adoc[MCP Tools Specification] and link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-TOOL-3]
=== PM-TOOL-3: Read-Only MCP Resource URI Surface

Large workflow artifacts and logs must be exposed via read-only MCP resource URIs to prevent conversational context bloat.

* The system must expose read-only plan, epic, and architecture artifacts through the `pm://` MCP resource scheme, supporting at minimum:
** Plan resources: `pm://plan/{plan_id}/outline`, `pm://plan/{plan_id}/task/{task_id}`, `pm://plan/{plan_id}/findings`, `pm://plan/{plan_id}/builds/{job_id}/log`, `pm://plan/{plan_id}/status`, and the plan's own mailbox `pm://plan/{plan_id}/mailbox` (with `pm://plan/{plan_id}/mailbox/{message_id}`).
** Epic resources: `pm://epic/{epic_id}/spec/{section}`, `pm://epic/{epic_id}/ledger`, `pm://epic/{epic_id}/landings`, `pm://epic/{epic_id}/inbox`, and the per-message resource `pm://epic/{epic_id}/inbox/{message_id}` (the epic scope reads every message; a plan scope reads only the messages it sent).
** Project resources: the owed-item index `pm://project/owed`.
** Architecture resources: `pm://architecture/overview`, `pm://architecture/modules/{module_id}`, `pm://architecture/files` (inventory mode with scan coverage) and `pm://architecture/files?path={rel_path}`, `pm://architecture/graph`, `pm://architecture/neighbours/{module_id}`, `pm://architecture/impact?modules={csv}`, and `pm://architecture/drift`.
* The system must reference large artifacts by their `pm://` URI within state representations rather than inlining bulk content into `facts`.
* The system must make every tool result or representation that truncates, samples, or summarises content name what was omitted (count and unit) and carry a retrieval handle (`pm://` URI) to the full artefact.
* The system must enforce workspace and scope confinement when serving `pm://` resource reads.

See the link:specification/mcp-tools.adoc[MCP Tools Specification] and link:specification/domain-extensions.adoc[Domain Extensions Specification] for implementation details.

[#PM-TOOL-4]
=== PM-TOOL-4: Domain Failures as Valid Workflow States

Operational and verification failures must be represented as navigable workflow states rather than protocol-level tool errors.

* The system must represent domain and execution failures (e.g. failed builds, test failures, rejected git pushes, red quality gates) as valid workflow states whose representations offer appropriate recovery links (`fix`, `retry`, `escalate`).
* The system must handle rejected transitions (e.g. invalid link IDs, stale entity states, or schema validation failures) by returning a normal tool result containing the current valid representation and a structured `rejected` reason field, rather than raising an MCP error.
* The system must reserve JSON-RPC protocol error responses strictly for transport faults, malformed JSON-RPC requests, unknown tool names, and tool arguments that violate the tool's MCP input schema; tool execution problems (such as an unknown scope or an unhandled server exception) must be returned as tool results carrying only a closed-enum reason code and an audit record identifier, without leaking internal stack traces.

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification] and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-TOOL-5]
=== PM-TOOL-5: Tool Schema Stability & Context Budget Discipline

The MCP tool surface must remain compact, portable, and optimized for minimal context window consumption across all supported hosts.

* The system must maintain a fixed, compact set of MCP tools (`pm_start`, `pm_state`, `pm_do`, `pm_plans`, `pm_epics`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`), never exposing individual workflow scripts or phase steps as distinct MCP tools.
* As the one documented exception, the system must expose the transitional tool `pm_legacy_script(notation, args)` only while unported `plan-marshall` scripts remain (Migration Stages 1–5, `PM-MIG-1`, `PM-MIG-2`), and must remove it from the tool surface at Stage 6.
* The system must name all MCP tools using exclusively lowercase alphanumeric characters and underscores (`^[a-z0-9_]+$`) prefixed with `pm_` to guarantee compatibility across all host runtimes and LLM provider APIs.
* The system must return all tool results exclusively as TOON-formatted plain text, omitting `outputSchema` declarations and `structuredContent` payloads to minimize resident schema overhead.
* The system must configure client entry points on demand-loading hosts to preload `pm_start`, `pm_state`, and `pm_do` so that core workflow execution never blocks on deferred tool schema lookups.
* The system may reduce how much of a document enters context (sections, indexes, elision with retrieval handle), but must never reduce what is examined as a cost lever (fewer skills or standards, dropped checks, lowered effort on resume or tool-result turns).

See the link:specification/mcp-tools.adoc[MCP Tools Specification] and link:specification/client-profiles.adoc[Client Profiles Specification] for implementation details.
