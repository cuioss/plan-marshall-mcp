== MCP Tool & Resource Surface (PM-TOOL)

[#PM-TOOL-1]
=== PM-TOOL-1: Core Workflow Verb Set (pm_start, pm_state, pm_do)

The system must expose workflow discovery, state inspection, and state transitions through a minimal, uniform set of MCP tools.

* The system must provide `pm_start(entry_id, request | issue_number | lesson_id | recipe_id | local_changes | pr_number, plan_slug?, base_branch?, recipe_params?, summary?)` to initialize a new plan from exactly one of the six supported sources (`request`, `issue`, `lesson`, `recipe`, `local_changes`, the user's own current changes of the main checkout, whose optional `summary` states their intent, or `pr`, an existing pull request whose head branch the plan adopts in its own worktree and carries through the finalize verification loop; a head the agent identity cannot push to is refused) after a plan-less entry bootstrap (`pm-mcp enter`), consuming the pending entry record identified by `entry_id` by appending it as the first row of the created plan's `sessions.jsonl` and returning the plan's initial state representation; epic membership is taken only from that entry record's `from_epic` (written by the emitted `pm-mcp enter … --from-epic` command), never from a `pm_start` parameter.
* The system must require every scoped tool (`pm_state`, `pm_do`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`) to carry exactly one of `plan_id` or, where the tool accepts epics, `epic_id`, where `plan_id` is a real plan id or the reserved literal `NO_PLAN`, which cannot match the plan id grammar and addresses the project's workspace scope and its main checkout (workspace-addressed, `PM-ARCH-4`); a call without a scope must be refused as an argument violation (`invalid_arguments`), no tool may infer a scope from an omitted parameter, and no tool takes a `scope: "workspace"` input. The sentinel mirrors `plan-marshall`'s `NO_PLAN` convention.
* The system must provide `pm_state(plan_id | epic_id, entity?, dispatch_id?)` (`scope` may additionally name `plan`, `epic`, or `entity` explicitly) to return the current TOON representation of a plan, an epic, or the project's workspace scope (`plan_id: "NO_PLAN"`, which hosts the plan-less workflows such as `project-setup`), or of a specific entity within that scope when invoked by a dispatched sub-agent.
* The system must provide `pm_plans()` and `pm_epics(include_archived?)` for workspace-addressed discovery (`PM-ARCH-4`), returning concise one-line status summaries of active plans and epics (and, with `include_archived`, archived epics) together with per-root scan coverage, so an empty listing is distinguishable from a root that was not scanned.
* The system must provide `pm_do(plan_id | epic_id, link, args?, entity?, dispatch_id?)` (same scope rule as `pm_state`) as the sole state transition verb, executing forward transitions, submissions, sub-agent return reports (`returned:<dispatch_id>`), job polling (`wait:<job>`), and job cancellations (`cancel:<job>`).
* The system must declare `args` in `pm_do` as a generic object at the MCP schema layer and enforce strict server-side schema validation (`additionalProperties: false`, closed types) against the target link's parameter specification before executing any transition.
* The system must resolve all filesystem paths, worktree locations, and branch names server-side from `plan_id` or `epic_id`, prohibiting model-supplied paths in tool parameters.

See the link:specification/mcp-tools.adoc[MCP Tools Specification], link:specification/hypermedia-format.adoc[Hypermedia Format Specification], and the link:specification/identifiers.adoc[Identifier Registry] for implementation details.

[#PM-TOOL-2]
=== PM-TOOL-2: Orthogonal Service Capability Tools (pm_build, pm_lsp)

The system must expose build execution and semantic code intelligence as orthogonal service tools that assist development without altering workflow phases.

* The system must provide `pm_build(plan_id, command, module?, test_filter?, expect?, job_id?)` to execute builds through the runtime's build server (in the plan's worktree, or, when `plan_id` is `NO_PLAN`, in the main checkout as a workspace-addressed request whose ledger rows, findings, and log belong to the workspace scope) using exactly the closed canonical build verb set of the link:specification/job-runtime.adoc#canonical-build-verbs[Job Runtime Specification] (equal to `plan-marshall`'s canonical commands) rather than raw shell command lines, with the build's gate scope derived from its `module` argument (absent: whole tree; present: that module only), never from the verb; the optional `expect` (`green` by default, or `red`) declares an intentionally failing run, which files no finding and never satisfies a build-freshness gate; when `expect` is given, the result carries `expectation: met | violated` beside the unchanged `status`, and a red run that went green is recorded in the change ledger (`expected_red_went_green`).
* The system must block `pm_build` for the same server-chosen bounded window as a `wait` link (`PM-IMPL-4`) and, when the build is not finished, return status `running` with its `job_id`; calling `pm_build` again with that `job_id` continues waiting on the same build.
* The system must return structured outcomes from `pm_build` containing a closed-enum status, test and error counts, and file-located failure diagnostics, referencing the full raw output exclusively via a resource URI (`pm://plan/{plan_id}/builds/{job_id}/log`, or `pm://workspace/builds/{job_id}/log` for a `NO_PLAN` build).
* The system must provide `pm_lsp(plan_id, op, path?, line?, character?, query?, new_name?)`, scoped to the plan's worktree or, with `NO_PLAN`, to the main checkout (`path` repository-relative; `rename` with `NO_PLAN` is refused, because an edit is applied only inside a plan's worktree), to execute semantic code operations (`workspace_symbol`, `document_symbol`, `definition`, `references`, `hover`, `diagnostics`, `rename`) against the runtime's warm language server pool.
* The system must exclude all privileged and operator-only actions from the MCP tool surface, restricting them exclusively to the operator channels of `PM-SEC-3` (MCP elicitation, the operator CLI, or a paired web device, the CLI-only actions of `PM-SEC-7` excepted).

See the link:specification/mcp-tools.adoc[MCP Tools Specification], link:specification/job-runtime.adoc[Job Runtime Specification], and link:specification/timeouts.adoc[Timeouts & Budgets Specification] for implementation details.

[#PM-TOOL-3]
=== PM-TOOL-3: Read-Only MCP Resource URI Surface

Large workflow artifacts and logs must be exposed via read-only MCP resource URIs to prevent conversational context bloat.

* The system must expose read-only plan, epic, and architecture artifacts through the `pm://` MCP resource scheme, supporting at minimum:
** Plan resources: `pm://plan/{plan_id}/outline`, `pm://plan/{plan_id}/task/{task_id}`, `pm://plan/{plan_id}/findings`, `pm://plan/{plan_id}/builds/{job_id}/log`, `pm://plan/{plan_id}/status`, and the plan's own mailbox `pm://plan/{plan_id}/mailbox` (with `pm://plan/{plan_id}/mailbox/{message_id}`).
** Epic resources: `pm://epic/{epic_id}/spec/{section}`, `pm://epic/{epic_id}/ledger`, `pm://epic/{epic_id}/landings`, `pm://epic/{epic_id}/inbox`, and the per-message resource `pm://epic/{epic_id}/inbox/{message_id}`.
** Project resources: the owed-item index `pm://project/owed`.
** Workspace resources: `pm://workspace/status`, `pm://workspace/findings`, and `pm://workspace/builds/{job_id}/log`.
** Architecture resources: `pm://architecture/overview`, `pm://architecture/modules/{module_id}`, `pm://architecture/files` (inventory mode with scan coverage) and `pm://architecture/files?path={rel_path}`, `pm://architecture/graph`, `pm://architecture/neighbours/{module_id}`, `pm://architecture/impact?modules={csv}`, and `pm://architecture/drift`.
* The system must reference large artifacts by their `pm://` URI within state representations rather than inlining bulk content into `facts`.
* The system must make every tool result or representation that truncates, samples, or summarises content name what was omitted (count and unit) and carry a retrieval handle (`pm://` URI) to the full artefact.
* The system must enforce project confinement when serving `pm://` resource reads (`PM-SEC-2`): every resource is readable within its project, with no further per-scope read restriction, while representations point each scope at its own resources.

See the link:specification/mcp-tools.adoc[MCP Tools Specification], link:specification/domain-extensions.adoc[Domain Extensions Specification], and the link:specification/identifiers.adoc[Identifier Registry] for implementation details.

[#PM-TOOL-4]
=== PM-TOOL-4: Domain Failures as Valid Workflow States

Operational and verification failures must be represented as navigable workflow states rather than protocol-level tool errors.

* The system must represent domain and execution failures (e.g. failed builds, test failures, rejected git pushes, red quality gates) as valid workflow states whose representations offer appropriate recovery links (`fix`, `retry`, `escalate`).
* The system must handle rejected transitions (e.g. invalid link IDs, stale entity states, or schema validation failures) by returning a normal tool result containing the current valid representation and a structured `rejected` reason field, rather than raising an MCP error.
* The system must reserve JSON-RPC protocol error responses strictly for transport faults, malformed JSON-RPC requests, and unknown tool names; tool arguments that violate the tool's input schema or a server-enforced argument rule must be returned as tool execution errors (`isError: true`, closed `error_code: invalid_arguments` naming the offending parameter and rule) so the model can correct the call, and so must other tool execution problems (such as an unknown scope or an unhandled server exception), each carrying only a closed-enum reason code, and an audit record identifier only where the operator must look the error up (an unhandled server exception, an unreadable document), without leaking internal stack traces.
* The system must answer a resource read for an unknown scope or entity, or a path outside the permitted root, with the JSON-RPC resource error `-32002` whose `data` carries the closed `error_code` (`scope_not_found`, `path_traversal_rejected`), never with an empty payload; the audit record of the refusal is written but its identifier is not returned.

See the link:specification/hypermedia-format.adoc[Hypermedia Format Specification] and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-TOOL-5]
=== PM-TOOL-5: Tool Schema Stability & Context Budget Discipline

The MCP tool surface must remain compact, portable, and optimized for minimal context window consumption across all supported hosts.

* The system must maintain a fixed, compact core set of MCP tools (`pm_start`, `pm_state`, `pm_do`, `pm_plans`, `pm_epics`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`), never exposing individual workflow scripts or phase steps as distinct MCP tools. The only other tools on the surface are the operator-allowlisted upstream pass-through tools (`up_<server_id>_<tool>`, `PM-SVC-3`), which are configuration-dependent and never part of the core set.
* The system must expose no tool that runs legacy `plan-marshall` scripts, at any migration stage; the fixed tool set has no exception (`PM-MIG-2`).
* The system must name all MCP tools using exclusively lowercase alphanumeric characters and underscores, core tools prefixed with `pm_` and upstream pass-through tools with `up_` (grammars in the link:specification/identifiers.adoc#id-core-tool-name[Identifier Registry]), to guarantee compatibility across all host runtimes and LLM provider APIs.
* The system must return all tool results exclusively as TOON-formatted plain text, omitting `outputSchema` declarations and `structuredContent` payloads to minimize resident schema overhead.
* The system must configure client entry points on demand-loading hosts to preload `pm_start`, `pm_state`, and `pm_do` so that core workflow execution never blocks on deferred tool schema lookups.
* The system may reduce how much of a document enters context (sections, indexes, elision with retrieval handle), but must never reduce what is examined as a cost lever (fewer skills or standards, dropped checks, lowered effort on resume or tool-result turns).
* The system must return in representations, tool results, and error payloads only information that changes what the model does next (the offered links and their parameters, the facts its judgement needs, the error it must correct, the identifiers it must pass back, and the text it must relay), and must record everything else (implementation variants, derivation and provenance sources, internal versions, confinement details, lease internals, digests the model makes no decision on, calibration bases, timing internals, retry bookkeeping, and audit identifiers except on errors the operator must look up) in the audit log, the metrics store, job records, or server logs, served on demand through operator surfaces (`pm-mcp status`, the operator CLI, `pm://` resources) and never pushed to the model; a build-time test must check every model-facing field against a registry of fields with a declared operational purpose (link:specification/hypermedia-format.adoc#model-facing-minimality[Model-Facing Minimality]).

See the link:specification/mcp-tools.adoc[MCP Tools Specification], link:specification/hypermedia-format.adoc[Hypermedia Format Specification], link:specification/client-profiles.adoc[Client Profiles Specification], and the link:specification/identifiers.adoc[Identifier Registry] for implementation details.
