== Migration & Staged Porting (PM-MIG)

[#PM-MIG-1]
=== PM-MIG-1: Six-Stage Incremental Seam Migration

The transition from the legacy script-and-prose architecture to `PM-MCP` must proceed across six discrete, independently deployable migration stages.

* The system must execute the architectural migration in six sequential stages:
** *Stage 1 (Daemon & Executor Adapter)*: Replaces `marshalld` with the `pm-mcp` daemon; exposes legacy scripts via an executor adapter running `script` jobs with the host's Python interpreter in the working directory matching the plan's location (never setting `PLAN_BASE_DIR`, `PM-ARCH-5`), reachable by the model only through the transitional MCP tool `pm_legacy_script` (`PM-MIG-2`); replaces Bash allowlists with MCP tool permissions.
** *Stage 2 (Embedded Build Server)*: Moves build scheduling into `PM-MCP` under the common job contract; replaces `resolve-then-run` shell commands with `pm_build` returning structured diagnostics.
** *Stage 3 (Hypermedia Pilot — Init)*: Executes Phase 1 (Init) end-to-end via the hypermedia state machine and ported Java stores (`status.json` and `references.json`); serves Phase 1 vocabulary skills dynamically.
** *Stage 4 (Remaining Phases & Epics)*: Migrates Phases 2 through 6 (refine, outline, plan, execute with envelope dispatch, finalize) and epic orchestration in sequential phase order as their underlying stores are ported.
** *Stage 5 (Warm LSP Pool & Upstream MCP Proxy)*: Activates the shared warm Language Server Protocol pool and proxies designated external MCP servers.
** *Stage 6 (Skill Serving & Distribution Switch)*: Serves all vocabulary skills natively with on-the-fly profile translation; retires the filesystem skill corpus, plugin-cache distribution chain, and build-time multi-target generators; removes the transitional `pm_legacy_script` tool once no unported script remains (`PM-TOOL-5`).
* Each migration stage must operate as a self-contained production release without requiring completion of subsequent stages.
* The system must never run legacy `plan-marshall` and `PM-MCP` in parallel on the same machine: before Stage 1 a machine runs legacy `plan-marshall` only; from Stage 1 onward every remaining legacy script executes exclusively as a `script` job of the `PM-MCP` runtime (`PM-MIG-2`).

See the link:specification/store-schemas.adoc[Store Schemas & Data Model Specification], link:specification/job-runtime.adoc[Job Runtime & Execution Specification], and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-MIG-2]
=== PM-MIG-2: Exclusive Runtime per Machine & Routed Legacy Script Execution

`PM-MCP` is built step by step on top of the existing scripts, but the two systems never operate concurrently on one machine.

* The system must switch a machine from legacy `plan-marshall` to `PM-MCP` as a whole (hard cutover per machine) when Stage 1 is installed, and must never allow a host on that machine to execute legacy scripts directly.
* After cutover, the installed client bundles must remove all host permission allowlist entries for the legacy executor (`execute-script.py`), and the executor must refuse to run unless launched by the `PM-MCP` runtime as a `script` job, failing with an explicit ownership error.
* When `PM-MCP` invokes an unported script via a `script` job, the runtime must acquire and hold the addressed scope's lock for the entire duration of the subprocess execution, preventing overlapping script jobs or concurrent state transitions on that scope.
* The system must provide the transitional MCP tool `pm_legacy_script(notation, args)` for Migration Stages 1–5: it validates the argument vector against the script's registered argument schema, runs the unported script as a verified `script` job through the executor adapter under the addressed scope's lock, and returns the script's result as TOON; it must be removed at Stage 6 (`PM-MIG-1`, `PM-TOOL-5`).
* The system must provide an operator CLI command (`pm-mcp operator rollback`) that drains the runtime and restores direct legacy execution on the machine, as the reversal of the cutover (`PM-MIG-5`).

See the link:specification/filesystem-layout.adoc[Filesystem Layout Specification], link:specification/store-schemas.adoc[Store Schemas & Data Model Specification], and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-MIG-3]
=== PM-MIG-3: Shared Store Format Interoperability During Staged Porting

While ported Java primitives and not-yet-ported legacy scripts (executed as `script` jobs) operate on the same `.plan/` state tree, both must read and write identical data store formats.

* Legacy scripts and `PM-MCP` must never mutate shared stores concurrently: all writers run inside the one `PM-MCP` runtime and serialize through its scope and machine locks (`PM-MIG-2`), so no cross-runtime locking protocol is required; legacy scripts keep their internal guard-file mutexes among themselves.
* All auxiliary stores previously persisted in the legacy `.toon` dialect (`work/metrics*.toon`, `work/fragment-*.toon`, `work/retro-fragments.toon`, `work/module_mapping.toon`, `work/deliverable-hashes.toon`, `work/lessons-consult.toon`, and `artifacts/ci-runs/{N}/manifest.toon`) must be converted to canonical JSON in `plan-marshall` prior to porting their owning scripts to Java.
* Redesigned workflow stores (`execution.toon`, `handshakes.toon`, and `work/ci-precondition-cache.toon`) must be superseded directly by the `PM-MCP` workflow engine's JSON state rather than converted.
* Every shared JSON and JSONL store must include a mandatory integer `format_version` field to ensure deterministic schema validation across both implementations.
* The system must switch each ported store from its legacy format to its redesigned `PM-MCP` schema exactly once, in the stage that ports it, through a one-time converter (legacy -> target) paired with a reverse converter (target -> legacy) for rollback; every legacy script that reads or writes that store must be ported or retired in the same stage.
* Before implementing a store converter, the legacy format must be re-verified against the latest `plan-marshall` version; the legacy formats documented in the specification are a verified snapshot, not a contract.

See the link:specification/store-schemas.adoc[Store Schemas & Data Model Specification] and link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-MIG-4]
=== PM-MIG-4: Stage Exit Criteria & Legacy Surface Retirement

Advancement between migration stages and retirement of legacy components must be gated by objective verification criteria.

* A ported store or primitive must not switch from Python to Java until:
** 100% of differential equivalence tests pass against the Python baseline.
** Dedicated JUnit 5 module tests meet coverage and contract requirements.
** Parallel shadow execution on real plans records zero unexplained discrepancies.
* The Stage 3 Hypermedia Pilot (Init) must satisfy the following exit criteria before Stage 4 commences:
** The Init phase completes end-to-end exclusively via hypermedia links (`pm_start`, `pm_do`) with zero model-composed CLI invocations.
** Session recovery after `/clear` or context compaction succeeds 100% of the time using `pm_state(plan_id)` alone.
** Plans initialized by `PM-MCP` transition seamlessly into the legacy Phase 2 (Refine) workflow without state loss.
* Legacy surfaces (such as `.plan/local/marshall-state.toon`, executor generators, and permission fixers) must be retired atomically alongside the stage that supersedes them.

See the link:specification/workflow-dsl.adoc[Workflow DSL & State Machine Specification] and link:specification/store-schemas.adoc[Store Schemas & Data Model Specification] for implementation details.

[#PM-MIG-5]
=== PM-MIG-5: Quantitative Rollback Triggers & Safe Reversion

Every migration stage must be monitored against quantitative operational baselines and maintain a non-destructive rollback path.

* The system must define and enforce quantitative rollback triggers across each migration stage; a stage must halt and revert if any of the following thresholds are breached:
** Resident context billing weight (tokens multiplied by turns per plan) regresses relative to the legacy baseline.
** Workflow-discipline defects (invented arguments, skipped steps, or out-of-order transitions) occur, or valid link submissions are erroneously rejected by `pm_do`.
** Context recovery and resume accuracy after `/clear` or compaction drops below 100%.
** Build execution duration or daemon dispatch overhead exceeds the direct CLI baseline by more than 5%.
** Unresolved state corruption or lock deadlocks are detected.
* Upon triggering a rollback, executing `pm-mcp operator rollback` must drain the runtime, convert every store switched by the rolled-back stages back to its legacy format with the reverse converters (`PM-MIG-3`), restore direct legacy execution on the machine, and allow immediate reactivation of the legacy distribution without loss of persisted plan state, tasks, or git commits.

See the link:specification/store-schemas.adoc[Store Schemas & Data Model Specification] and link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.
