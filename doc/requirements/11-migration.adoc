== Migration & Project Lifecycle Gate (PM-MIG)

[#PM-MIG-1]
=== PM-MIG-1: Six-Stage Build-Out & Per-Project Plan Lifecycle

`PM-MCP` is built out beside `plan-marshall` in six discrete, independently deployable stages and taken into use per project; no stage switches a machine or a store (`PM-MIG-2`).

* The system must be built out in six sequential stages:
** *Stage 1 (Runtime & Operator Surface)*: Installs the always-on `pm-mcpd` runtime with its own machine root `<PM_MCP_BASE>` (`PM-MIG-2`), the STDIO relay (`pm-mcp`), the stores and the job runtime (including the model job kind `llm` with its launch contract, job token, and model slots, and the worker runtime of `PM-WORK-1` to `PM-WORK-6` as a mechanism tested against a fixture harness: role artifacts and the model caller, the task queue and task protocol, generations and fencing, the supervisor, consultation, the interactive session as optional worker, and role qualification), operator enrolment, and the operator CLI (`pm-operator`).
** *Stage 2 (Embedded Build Server, CI Jobs & Credentials)*: Moves build scheduling into `PM-MCP` under the common job contract, with `pm_build` replacing `resolve-then-run` shell commands and returning structured diagnostics; adds the orthogonal CI job and token-lane credential services.
** *Stage 3 (Hypermedia Pilot — Init)*: Executes the plan bootstrap with the sources `request`, `issue`, `lesson`, and `recipe` (`PM-TOOL-1`, `PM-WF-10`) and Phase 1 (Init) end-to-end via the hypermedia state machine and the Java stores (`mcp/status.json` and `references.json`) in the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/`; serves Phase 1 vocabulary skills dynamically; runs the first run of the project setup workflow (`PM-EXT-3`); provides the first real roles on the `claude` harness (`PM-WF-5`, `PM-WF-14`: headless launch template, default role artifacts, parsed usage, and their qualification records of `PM-WORK-6`) that the setup's architecture enrichment and the two-level guard for the `issue` source need (`PM-SEC-1`); and ships the `claude` client bundle with its installer, embedded in the release (`PM-DIST-1`).
** *Stage 4 (Remaining Phases & Epics)*: Adds Phases 2 through 6 (refine, outline, plan, execute with envelope tasks, finalize, and the `local_changes` and `pr` sources) with their roles, the optional web access with the web application and its question channel (`PM-SEC-7`, `PM-WF-12`), and epic orchestration with the epic bootstrap and the server-started plans of the `epic_row` source, in sequential phase order.
** *Stage 5 (Warm LSP Pool & Upstream MCP Proxy)*: Activates the shared warm Language Server Protocol pool and proxies designated external MCP servers.
** *Stage 6 (Remaining Hosts & Full Skill Serving)*: Extends client installation and bundles to the remaining hosts (`opencode`, `antigravity`, `codex`), adds the headless launch templates of `codex` and `opencode` and marks a harness eligible as a worker host only after its worker behaviour has been measured (`PM-CLIENT-2`), and serves all vocabulary skills with on-the-fly profile translation for every client profile.
* Each stage must operate as a self-contained production release without requiring completion of subsequent stages; a prerequisite is delivered by the first stage that needs it.
* No stage may deliver skills or client artifacts through `plan-marshall`, a filesystem skill corpus, a plugin-cache distribution chain, or build-time multi-target generators: every client artifact originates from the installed release (`PM-DIST-1`).
* The orthogonal services (`pm_build`, `pm_lsp`, CI jobs, credentials) may be used in any enrolled project alongside `plan-marshall` from the stage that delivers them.
* A project becomes usable for the plan lifecycle by operator enrolment (`pm-operator enrol`) followed by the project setup workflow in its workspace scope (`PM-EXT-3`), which creates `.marshall/` and a fresh configuration; `PM-MCP` takes no input from `plan-marshall` state (`PM-MIG-2`).
* The lifecycle gate must be a compiled constant of the release, never a setting: closed in every release before the Stage 4 exit criteria are met (`PM-MIG-4`) and open from the release that meets them. While the gate is closed, plans and epics are created only in a project the operator enrolled as a pilot (`pm-operator enrol --pilot`, recorded as `pilot: true` in the enrolment file and audited); in every other project the bootstrap's scope creation is refused with `lifecycle_closed`. With the gate open, `pilot` has no effect, and the plan lifecycle is offered in every enrolled project until the operator releases it (`PM-MIG-5`).

See the link:specification/store-schemas.adoc[Store Schemas Specification], link:specification/job-runtime.adoc[Job Runtime Specification], link:specification/mcp-tools.adoc[MCP Tools Specification], and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-MIG-2]
=== PM-MIG-2: Separate State Trees & Legacy Coexistence

`plan-marshall` and `PM-MCP` may both be installed on one machine and used in the same repository; they never share state.

* The system must keep all machine-level state under its own root `<PM_MCP_BASE>` (default `~/.plan-marshall-mcp/`, overridable only by the environment variable `PM_MCP_BASE`) including the per-project machine stores that hold all plan, lesson, and scope state (`<PM_MCP_BASE>/projects/<project_id>/`), and all repository-level documents and technical data (worktrees, temporary files) under `.marshall/`.
* The system must never read or write `~/.plan-marshall/` or a repository's `.plan/`, and must never read `PLAN_MARSHALL_HOME` or `PLAN_MARSHALL_CREDENTIALS_DIR`, without exception: `PM-MCP` imports nothing from `plan-marshall` (no configuration, lessons, architecture data, credentials, or learned timeouts); every project starts from a clean slate.
* The system must keep its OS keyring entries in its own namespace (service `de.cuioss.pm-mcp`) and never read `plan-marshall` keyring entries.
* The system must never run, route to, or expose `plan-marshall` scripts: there is no executor adapter, no `plan-marshall` script job, and no MCP tool or host permission rule that executes a `plan-marshall` script; `project_script` jobs of the project's own enrolled scripts (`PM-EXT-5`) are unaffected.
* The system must name its entry commands and their bundle files with the `mcp-` prefix (`/mcp-plan-marshall`, `/mcp-plan-orchestrator`, `/mcp-marshall-steward`, `PM-CLIENT-1`), so that a host on which the `plan-marshall` plugin is installed side by side offers both command sets without a collision.
* The system must never hand a plan over to a `plan-marshall` phase or take over a `plan-marshall` plan or epic in flight: those plans and epics finish in `plan-marshall`.
* Every JSON and JSONL store must include a mandatory integer `format_version` field without exception: the server-owned stores, the git-tracked team configuration files `.marshall/config/*.json`, and the operator files (`local-config.json`, `machine-config.json`, enrolment files, the harness enrolment `harnesses.json`, credential files of `PM-CRED-3`); every workflow unit declares its DSL format in its header.

See the link:specification/filesystem-layout.adoc[Filesystem Layout Specification], link:specification/store-schemas.adoc[Store Schemas Specification], link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/job-runtime.adoc[Job Runtime Specification], and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-MIG-4]
=== PM-MIG-4: Stage Exit Criteria & Lifecycle Gate

Advancement between stages and the offering of the plan lifecycle in enrolled projects must be gated by objective verification criteria.

* A store or primitive must not be released in a stage until:
** 100% of differential equivalence tests pass against the Python baseline over the fixture corpora (`PM-TEST-2`).
** Dedicated JUnit 5 module tests meet coverage and contract requirements.
** Parallel runs — the same requests executed by `plan-marshall` and by `PM-MCP` on separate clones or checkouts, the `PM-MCP` ones enrolled as pilots (`PM-MIG-1`) — are compared by the server-computed metrics (`priced_units`, discipline events, outline and triage quality) and show no unexplained regression of `PM-MCP` (`PM-MIG-5`). This criterion applies to stores and primitives released from Stage 3 on, the first stage with plans to run in parallel; Stages 1 and 2 are gated by the differential tests and the JUnit module tests alone.
* The Stage 3 Hypermedia Pilot (Init) must satisfy the following exit criteria before Stage 4 commences:
** The plan bootstrap and the Init phase complete end-to-end exclusively via hypermedia links (`pm_state`, `pm_do`) with zero model-composed CLI invocations beyond `pm-mcp enter`.
** Supervision is exact in 100% of the deterministic `PM-TEST-4` worker scenarios: every task is submitted exactly once after a killed, stalled, or recycled worker, every lease is released at the fence, and every call of a fenced generation is refused.
* The lifecycle gate (`PM-MIG-1`) is compiled open only in the release whose Stage 4 exit criteria are met: every phase and epic orchestration completes end-to-end in parallel runs without an evaluated trigger of `PM-MIG-5`, no trigger evaluates to `indeterminate`, every role the default units name either has a qualified configuration (`PM-WORK-6`) on a harness shipped by then (`claude`) or runs on its conservative fallback (link:specification/model-work/01-roles-and-configuration.adoc#conservative-fallback[Model Work Specification, Conservative Fallback]), the parallel runs and the triggers of `PM-MIG-5` deciding whether that fallback is good enough, and the release ships the web access with the web application (`PM-SEC-7`), so that the question channel of `PM-WF-12` is available wherever the plan lifecycle is offered. Making a further harness eligible as a worker host (Stage 6) requires its own worker measurement and the qualification of the roles assigned to it.

See the link:specification/store-schemas.adoc[Store Schemas Specification] and link:specification/state-catalogue.adoc[State Catalogue] for implementation details.

[#PM-MIG-5]
=== PM-MIG-5: Quantitative Triggers & Project Release

Every stage and every project offered the plan lifecycle must be monitored against quantitative operational baselines, and the operator must be able to release a project so that it is no longer offered the plan lifecycle.

* The system must define and evaluate quantitative triggers per stage and per project offered the plan lifecycle; each population-based trigger evaluates to `breached`, `clear`, or `indeterminate` (below its minimum population, a compiled constant, or with a side unmeasured; link:specification/phase-workflows/05-finalize-review-metrics-descriptor.adoc#migration-trigger-evaluation[Phase Workflows Specification, Migration Trigger Evaluation]); a breached trigger halts stage advancement or keeps the lifecycle gate closed and marks the affected project for release:
** Priced units per plan (`priced_units`, computed by the server from the persisted raw token components with the weights of its one named constant table) summed over the measured tasks and model jobs regress relative to the `plan-marshall` baseline. The `plan-marshall` baseline must itself be a measured population that publishes its plan count, date range, field presence, and producing instrument, re-derived from raw components under the same weights; its resident-context share is measured per component (entry commands, agent descriptions, skill descriptions, tool schemas) with its population and derivation recorded so it can be re-derived. When either side is unmeasured for the compared population, or the population is below its declared minimum size, the trigger evaluates to `indeterminate`.
** Engine-side workflow-discipline defects occur: a transition is accepted with invented arguments, with a skipped step, or out of sequence, or a valid link submission is erroneously rejected by `pm_do` (zero tolerance; these outcomes are deterministic).
** The per-plan rate of contained model-side discipline events (link calls rejected with `invalid_link_args` or `link_not_available`, and repeated identical rejected calls), counted by the server from its audit records, exceeds the `plan-marshall` baseline of argument-shape failures per plan; the `plan-marshall` baseline is a measured population published with its plan count before Stage 3.
** Worker supervision fails: a task submitted twice, a task lost without redelivery, or an accepted call of a fenced generation (zero tolerance; these outcomes are deterministic).
** The runtime's own build overhead exceeds 5%: the median over the build jobs of the evaluated stage or project of (job wall time − child wall time) / child wall time, both wall times recorded by the server in the job record; below the minimum population the trigger evaluates to `indeterminate`.
** A store or lock integrity event is recorded in the audit log: an `integrity_breach` of kind `store_tampered` not explained by an operator `accept-edit`, a `lock_order_violation`, or a `lock_wait_exceeded` record of a lock wait beyond its reporting threshold (link:specification/timeouts.adoc[Timeouts & Budgets Specification]); every such event counts, with zero tolerance.
* A cost lever (a change justified by a claimed saving against these triggers) must be proposed with a measured size and the population in which it fires, and its saving counts as measured only against a holdout share of runs executed without the lever.
* A trigger that evaluates to `indeterminate` halts advancement to the next stage and keeps a closed lifecycle gate closed, but does not by itself release a project already offered the plan lifecycle.
* The system must provide the operator CLI command `pm-operator release-project`, the operator's switch-off for these triggers, which records the release on the project's enrolment (audited) and stops offering the plan lifecycle for that project: it aborts every non-terminal plan and epic of the project through the engine-owned abort, their branches and stores stay as the abort leaves them and readable in `PM-MCP`'s own stores, nothing is converted, and the project can continue on `plan-marshall`, whose `.plan/` `PM-MCP` never touched. A later `pm-operator enrol` of the released project undoes the release (audited).
* The baseline measurements are parallel runs of `plan-marshall` on separate clones or checkouts; they measure `plan-marshall` behaviour and never feed `plan-marshall` data into `PM-MCP` stores.
