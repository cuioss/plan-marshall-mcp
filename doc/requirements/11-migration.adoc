== Migration & Project Lifecycle Gate (PM-MIG)

[#PM-MIG-1]
=== PM-MIG-1: Six-Stage Build-Out & Per-Project Plan Lifecycle

`PM-MCP` is built out beside legacy `plan-marshall` in six discrete, independently deployable stages and taken into use per project; no stage switches a machine or a store (`PM-MIG-2`).

* The system must be built out in six sequential stages:
** *Stage 1 (Runtime & Operator Surface)*: Installs the always-on `pm-mcpd` runtime with its own machine root `<PM_MCP_BASE>` (`PM-MIG-2`), the STDIO relay, the stores and the job runtime (including the model job kind `llm` with its launch contract, job token, and model slots, `PM-WF-5`), operator enrolment, and the operator CLI.
** *Stage 2 (Embedded Build Server, CI Jobs & Credentials)*: Moves build scheduling into `PM-MCP` under the common job contract, with `pm_build` replacing `resolve-then-run` shell commands and returning structured diagnostics; adds the orthogonal CI job and token-lane credential services.
** *Stage 3 (Hypermedia Pilot — Init)*: Executes the plan bootstrap with the sources `request`, `issue`, `lesson`, and `recipe` (`PM-TOOL-1`, `PM-WF-10`) and Phase 1 (Init) end-to-end via the hypermedia state machine and the Java stores (`status.json` and `references.json`) in the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/`; serves Phase 1 vocabulary skills dynamically; runs the first run of the project setup workflow (`PM-EXT-3`); provides the first model jobs on the `claude` harness (`PM-WF-5`, `PM-WF-14`: headless launch template, effort role resolution, parsed usage) that the setup's architecture enrichment and the two-level guard for the `issue` source need (`PM-SEC-1`); and ships the `claude` client bundle with its installer, embedded in the release (`PM-DIST-1`).
** *Stage 4 (Remaining Phases & Epics)*: Adds Phases 2 through 6 (refine, outline, plan, execute with envelope jobs, finalize, and the `local_changes` and `pr` sources) and epic orchestration with the epic bootstrap and the `epic_row` source, in sequential phase order.
** *Stage 5 (Warm LSP Pool & Upstream MCP Proxy)*: Activates the shared warm Language Server Protocol pool and proxies designated external MCP servers.
** *Stage 6 (Remaining Hosts & Full Skill Serving)*: Extends client installation and bundles to the remaining hosts (`opencode`, `antigravity`, `codex`), adds the headless launch templates of `codex` and `opencode` (`antigravity` runs no model jobs until its command line offers per-call MCP and tool allowlists, `PM-CLIENT-2`), and serves all vocabulary skills with on-the-fly profile translation for every client profile.
* Each stage must operate as a self-contained production release without requiring completion of subsequent stages; a prerequisite is delivered by the first stage that needs it.
* No stage may deliver skills or client artifacts through legacy `plan-marshall`, a filesystem skill corpus, a plugin-cache distribution chain, or build-time multi-target generators: every client artifact originates from the installed release (`PM-DIST-1`).
* The orthogonal services (`pm_build`, `pm_lsp`, CI jobs, credentials) may be used in any enrolled project alongside legacy `plan-marshall` from the stage that delivers them.
* A project becomes usable for the plan lifecycle by operator enrolment (`pm-mcp operator enrol`) followed by the project setup workflow in its workspace scope (`PM-EXT-3`), which creates `.marshall/` and a fresh configuration; `PM-MCP` takes no input from legacy `plan-marshall` state (`PM-MIG-2`).
* The plan lifecycle must be offered in an enrolled project only after the lifecycle gate has opened (the Stage 4 exit criteria are met, `PM-MIG-4`), and stops being offered when the operator releases the project (`PM-MIG-5`); it is never offered automatically before the gate opens.

See the link:specification/store-schemas.adoc[Store Schemas Specification], link:specification/job-runtime.adoc[Job Runtime Specification], link:specification/mcp-tools.adoc[MCP Tools Specification], and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-MIG-2]
=== PM-MIG-2: Separate State Trees & Legacy Coexistence

Legacy `plan-marshall` and `PM-MCP` may both be installed on one machine and used in the same repository; they never share state.

* The system must keep all machine-level state under its own root `<PM_MCP_BASE>` (default `~/.plan-marshall-mcp/`, overridable only by the environment variable `PM_MCP_BASE`) including the per-project machine stores that hold all plan, lesson, and scope state (`<PM_MCP_BASE>/projects/<project_id>/`), and all repository-level documents and technical data (worktrees, temporary files) under `.marshall/`.
* The system must never read or write `~/.plan-marshall/` or a repository's `.plan/`, and must never read `PLAN_MARSHALL_HOME` or `PLAN_MARSHALL_CREDENTIALS_DIR`, without exception: `PM-MCP` imports nothing from legacy `plan-marshall` (no configuration, lessons, architecture data, credentials, or learned timeouts); every project starts from a clean slate.
* The system must keep its OS keyring entries in its own namespace (service `de.cuioss.pm-mcp`) and never read legacy keyring entries.
* The system must never run, route to, or expose legacy `plan-marshall` scripts: there is no executor adapter, no legacy script job, and no MCP tool or host permission rule that executes a legacy script; `project_script` jobs of the project's own enrolled scripts (`PM-EXT-5`) are unaffected.
* The system must never hand a plan over to a legacy phase or take over a legacy plan or epic in flight: legacy plans and epics finish in `plan-marshall`.
* Every JSON and JSONL store must include a mandatory integer `format_version` field without exception: the server-owned stores, the git-tracked team configuration files `.marshall/config/*.json`, and the operator files (`local-config.json`, `machine-config.json`, enrolment files, credential files of `PM-CRED-3`); every workflow unit declares its DSL format in its header.

[#PM-MIG-4]
=== PM-MIG-4: Stage Exit Criteria & Lifecycle Gate

Advancement between stages and the offering of the plan lifecycle in enrolled projects must be gated by objective verification criteria.

* A store or primitive must not be released in a stage until:
** 100% of differential equivalence tests pass against the Python baseline over the fixture corpora (`PM-TEST-2`).
** Dedicated JUnit 5 module tests meet coverage and contract requirements.
** Parallel runs — the same requests executed by legacy `plan-marshall` and by `PM-MCP` on separate clones or checkouts — are compared by the server-computed metrics (`priced_units`, discipline events, outline and triage quality) and show no unexplained regression of `PM-MCP` (`PM-MIG-5`).
* The Stage 3 Hypermedia Pilot (Init) must satisfy the following exit criteria before Stage 4 commences:
** The plan bootstrap and the Init phase complete end-to-end exclusively via hypermedia links (`pm_state`, `pm_do`) with zero model-composed CLI invocations beyond `pm-mcp enter`.
** Session recovery after `/clear` or context compaction via `pm_state(plan_id)` alone reconstructs the working context in 100% of the deterministic `PM-TEST-4` compaction scenarios; the scope pointer of `PM-CLIENT-6` supplies the `plan_id` after context loss.
* The lifecycle gate (`PM-MIG-1`) opens only when the Stage 4 exit criteria are met: every phase and epic orchestration completes end-to-end in parallel runs without an evaluated trigger of `PM-MIG-5`, no trigger evaluates to `indeterminate`, and the live-model recovery rate measured under `PM-TEST-6` stays within its recorded tolerance band for every client profile shipped by then (`claude`). Offering the plan lifecycle through a host whose client profile ships later (Stage 6) requires that host's own live-model recovery measurement within its tolerance band. The live-model measurement is a lifecycle-gate criterion only, never a criterion of an earlier stage.

See the link:specification/workflow-dsl.adoc[Workflow DSL & Engine Specification], link:specification/store-schemas.adoc[Store Schemas Specification], and the link:specification/state-catalogue.adoc[State Catalogue] for implementation details.

[#PM-MIG-5]
=== PM-MIG-5: Quantitative Triggers & Project Release

Every stage and every project offered the plan lifecycle must be monitored against quantitative operational baselines, and the operator must be able to release a project so that it is no longer offered the plan lifecycle.

* The system must define and evaluate quantitative triggers per stage and per project offered the plan lifecycle; a breached trigger halts stage advancement or keeps the lifecycle gate closed and marks the affected project for release:
** Priced units per plan (`priced_units`, computed by the server from the persisted raw token components with the weights of its one named constant table) summed over the measured model jobs and the measured main session regress relative to the legacy baseline. The legacy baseline must itself be a measured population that publishes its plan count, date range, field presence, and producing instrument, re-derived from raw components under the same weights; its resident-context share is measured per component (entry commands, agent descriptions, skill descriptions, tool schemas) with its population and derivation recorded so it can be re-derived. When either side is unmeasured for the compared population, or the population is below its declared minimum size, the trigger evaluates to `indeterminate`.
** Engine-side workflow-discipline defects occur: a transition is accepted with invented arguments, with a skipped step, or out of sequence, or a valid link submission is erroneously rejected by `pm_do` (zero tolerance; these outcomes are deterministic).
** The per-plan rate of contained model-side discipline events (link calls rejected with `invalid_link_args` or `link_not_available`, and repeated identical rejected calls), counted by the server from its audit records, exceeds the legacy baseline of argument-shape failures per plan; the legacy baseline is a measured population published with its plan count before Stage 3.
** Context recovery after `/clear` or compaction, measured with a live model under `PM-TEST-6` over a stated population, falls outside its recorded tolerance band (evaluated at the lifecycle gate and for projects offered the plan lifecycle, not for earlier stages); an unscorable measurement is `indeterminate` and never counts as a pass.
** The runtime's own build overhead (job wall time minus the child process's wall time, measured by the server per build job) exceeds 5% of the child's wall time, as the median over the builds of the evaluated stage or project; below the declared minimum population the trigger evaluates to `indeterminate`.
** A store or lock integrity event is recorded in the audit log: an `integrity_breach` of kind `store_tampered` not explained by an operator `accept-edit`, a `lock_order_violation`, or a `lock_wait_exceeded` record of a lock wait beyond its reporting threshold (link:specification/timeouts.adoc[Timeouts & Budgets Specification]); every such event counts, with zero tolerance.
* A cost lever (a change justified by a claimed saving against these triggers) must be proposed with a measured size and the population in which it fires, and its saving counts as measured only against a holdout share of runs executed without the lever.
* A trigger that evaluates to `indeterminate` halts advancement to the next stage and keeps a closed lifecycle gate closed, but does not by itself release a project already offered the plan lifecycle.
* The system must provide the operator CLI command `pm-mcp operator release-project`, the operator's switch-off for these triggers, which stops offering the plan lifecycle for that project: plans in flight stay readable in `PM-MCP`'s own stores, nothing is converted, and the project can continue on legacy `plan-marshall`, whose `.plan/` `PM-MCP` never touched.
* The legacy baseline measurements are parallel runs of legacy `plan-marshall` on separate clones or checkouts; they measure legacy behaviour and never feed legacy data into `PM-MCP` stores.
