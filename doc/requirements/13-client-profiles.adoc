== Client Profiles & Dynamic Translation (PM-CLIENT)

[#PM-CLIENT-1]
=== PM-CLIENT-1: Advisory Entry Identity Declaration & Persistence

Every interaction with `PM-MCP` is associated with an agent runtime identity established at the session entry point and persisted with the active plan or epic scope.

* Every user-invoked entry command (`/mcp-marshall-steward` for project setup in the workspace scope, `/mcp-plan-marshall` for the plan lifecycle, `/mcp-plan-orchestrator` for epic orchestration; the `$mcp-…` skills on Codex) must execute `pm-mcp enter --client <client> <plan|epic|workspace> [plan_id | epic_id]` in the host's shell prior to the first MCP tool call, passing the user's words as an optional free-text hint as a file or on standard input (never on the command line) and, for a plan emitted by an epic, the epic's id (`--from-epic <epic_id>`); the entry names no source, which the bootstrap gathers (`PM-TOOL-1`).
* The entry commands must carry the `mcp-` prefix, and the command and skill files of the client bundles must follow the command names: the three commands complete together in the host (`/mcp…`) and coexist with the commands of the legacy `plan-marshall` plugin in a mixed installation (`PM-MIG-2`); the plain names follow once legacy `plan-marshall` is retired (link:later-improvements.adoc#_l_9_plain_entry_command_names[Later Improvements, L-9]).
* The client identity passed via `--client` (`claude`, `opencode`, `antigravity`, `codex`, `neutral`) must be treated strictly as advisory routing and rendering metadata used to format representations, skill syntax, and host tool names, never as an authenticated security credential.
* Upon `pm-mcp enter`, which sends what the host shell sees as one request to the runtime (started on demand) and writes no store itself, the runtime must append one row to the scope's append-only session log `sessions.jsonl` (in the plan or epic directory, or in the project's workspace home `<PM_MCP_BASE>/projects/<project_id>/workspace/`), recording the host session identifier (`client_session_id`, `null` when the host provides none), the declared and the detected client, the environment match tier, the exact host build obtained by the profile's version probe (`client_build`, `null` when unavailable), the model family, identifier, and source, the release version of the runtime that wrote the row (`pm_mcp_version`) and the installed bundle version (`bundle_version`), the `project_id`, whether the session entered from the main checkout or a worktree (and which), first- and last-seen instants, and the host transcript locator where the host has one; session logs must live only in the per-project machine store (`<PM_MCP_BASE>/projects/<project_id>/`), never in the repository or under git tracking, and no row records a filesystem path of the checkout.
* The server must also append a row when a scope-addressed call carries a host session identifier that differs from the scope's last row, so that every host session that worked on a scope is recorded.
* For a `plan` or `epic` entry that names no live scope (nothing named, a new, archived, or unknown id), the runtime must write a pending entry record `<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>.json` under a freshly allocated `entry_id`, holding the session row, the scope kind, the requested id, the hint, `from_epic`, and the state of the entry's bootstrap, and `pm-mcp enter` must print `entry: <entry_id>`; for a live scope named by its id it appends the session row and prints the scope. The bootstrap's completion must consume the record so that its session becomes the first row of the new scope's session log and its epic membership the plan's origin, so that concurrent entries never share or overwrite a record.
* All subsequent MCP tool calls within that plan or epic scope (including `pm_state` calls after `/clear` or compaction) must resolve the client profile from the last row of the scope's session log without requiring the model to pass client identity parameters; a model job's connection (`PM-WF-5`) takes its client profile from its job record, appends no session row, triggers no client handover, and carries its `job_id` in its audit records.
* Re-entering an existing plan or epic from the same or a different client runtime must append a row, hand over rendering to the new client profile, and record a change of the declared client as a handover event in the audit log.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification], the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], the link:specification/filesystem-layout.adoc[Filesystem Layout Specification], and the link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.

[#PM-CLIENT-2]
=== PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation

Instead of generating static per-runtime copies of the skill corpus at build time, `PM-MCP` must dynamically translate all model-facing artifacts per request using declarative client profiles for all supported coding agents (`claude`, `opencode`, `antigravity`, `codex`, and `neutral`).

* The system must translate vocabulary skills, state representations, hypermedia links, and the launches and prompt files of model jobs on the fly according to the active scope's client profile across the following dimensions:
** *Host Tool Names*: Translating canonical tool references to runtime-native names (e.g., `Read` -> `view_file` in Antigravity, `read` in OpenCode, or `read_file` in Codex _(provisional)_; `AskUserQuestion` -> `ask_question`, `question`, or `request_user_input` _(provisional)_).
** *Skill Load Directives*: Rendering skill invocation syntax for the client's native discovery mechanism (`pm_skill(plan_id="...", uri="...")` tool call or `resources/read` resource read).
** *Command Names*: Formatting the `mcp-` prefixed entry commands (`PM-CLIENT-1`) using the client's namespace conventions (a `/mcp-…` command, or a `$mcp-…` skill on Codex).
** *Tool Idioms*: Rewriting, preserving, or rewording runtime-specific idioms according to registered profile dispositions.
** *Models & Effort Levels*: Mapping abstract task complexity levels to runtime-specific model identifiers and thinking/effort parameters.
** *Headless Model Jobs*: Composing a model job's launch (`PM-WF-5`) from the profile's `headless` block: an argument-vector template with typed slots (prompt file, model, effort, MCP configuration, result schema, tools, working directory), the declared capabilities (per-call MCP, tool allowlist, zero tools, result schema, ephemeral run, usage and cost fields, reliable exit status, project-settings control), the supported harness version range, the writable harness paths (`PM-SEC-5`), the harness's MCP-resource-reading tools (allowlisted for the `writer` and `read_only` job classes, never for `zero_tool`), and `agent_mode` (`inline`: a per-job named agent rendered for Claude Code and OpenCode; `flags`: per-call flags for Codex). A harness lacking a capability that a role's job class needs runs no job of that role; the Antigravity and neutral profiles declare no headless template in the first iteration, and an operator on such a host names another installed harness (`model_jobs.harness`).
* Dynamic profile rendering must compute deterministic per-client skill digests so each client runtime observes a stable, verifiable skill catalogue.
* The system must restrict profile translation to the vocabulary dimensions above; any per-client or per-model change of wording, emphasis, or scaffolding requires a behavioural signal for that client (`PM-TEST-6`) and a recorded decision before it ships.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification], link:specification/dispatch-and-effort.adoc[Model Jobs & Effort Specification], and link:specification/mcp-tools.adoc[MCP Tools & Resources Specification] for implementation details.

[#PM-CLIENT-3]
=== PM-CLIENT-3: Three-Tier Environment Mismatch Detection & Audit

To prevent silent profile misrouting and maintain non-repudiable operational auditability, the system must cross-check declared client identities against host environment signatures and MCP handshake metadata.

* `pm-mcp enter` and `pm-mcp serve` must inspect the inherited process environment against the per-client detection signals and their fixed precedence defined in the link:specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table] (primary signals `ANTIGRAVITY_AGENT`, `OPENCODE` / `OPENCODE_PID`, `CLAUDE_CODE_SESSION_ID`, checked in this order, then `CODEX_SANDBOX` / `CODEX_CI` / `CODEX_THREAD_ID` for Codex _(provisional)_), treating values marked provisional there as unverified until Milestone 0.
* Every session-bound audit record (transitions and `enter`) must record three distinct identity tiers, while a machine-level audit record carries only the OS principal:
** *Tier 1 (Declared Client)*: The advisory identity passed via `--client` (or recorded as `client` in the scope's last session row).
** *Tier 2 (Detected Environment)*: The runtime signature detected from process environment variables or MCP `clientInfo` metadata (`unknown` if unrecognized, `absent` if omitted); at tool-call time both come from the connection metadata the relay forwards with every request, since the transport is sessionless.
** *Tier 3 (Authenticated OS Principal)*: The verified local operating system user principal owning the process.
* If the detected environment signature or MCP `clientInfo` disagrees with the declared client of the scope's last session row, the system must:
** Record the discrepancy (`identity_mismatch=true`) in the audit log and notify the operator.
** Flag the mismatch prominently in the returned state representation so a session that lost ownership of a plan does not silently act on a foreign client profile.
** Preserve the declared client without silently changing it during a regular tool call (a row appended by the server for a new host session keeps the previous declaration and records the detected client separately).

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-CLIENT-4]
=== PM-CLIENT-4: Neutral Fallback Profile for Unknown Clients

Connections originating from unrecognized or unprofiled MCP clients must degrade gracefully and visibly to a standard, host-agnostic interaction mode.

* When a session enters with an unrecognized client identity (`unknown`) or connects without a matching client profile, the system must serve the session using a built-in *neutral profile*.
* Under the neutral profile, the system must:
** Emit links and instructions referencing only `PM-MCP`'s own standard MCP tools (the full `PM-TOOL-5` surface: `pm_state`, `pm_do`, `pm_plans`, `pm_epics`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`).
** Omit all host-specific native tool names and shell idioms, and run no model job unless the operator names an installed harness (`model_jobs.harness`): a job state raises the `precondition_unmet` condition naming the missing headless template, and no model work runs inline in the main session (`PM-WF-5`).
** Make the profile visible to the operator per session, in `pm-operator status`, in the scope's session row, and in the audit record, never through a model-facing neutral-profile marker in the state representation (`PM-TOOL-5`).

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] for implementation details.

[#PM-CLIENT-5]
=== PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy

Client profiles must be governed as versioned, schema-validated data artifacts embedded in the binary and extensible via local configuration overrides.

* Every client profile definition must be a declarative JSON document carrying an explicit integer `schema_version` and minimum compatible server version (bundle versions and file digests live in the per-client `bundle-manifest.json`, `PM-DIST-2`).
* Each profile must declare the client's entry command names (the `mcp-` prefixed commands of `PM-CLIENT-1` in the client's own syntax), its `stdio` connection configuration (`pm-mcp serve`), supported protocol capabilities (progress notification idle-timer reset, tool-call timeout bounds; whether a connection supports MCP elicitation is taken only from the capabilities the connection declares), its `headless` block for model jobs (`PM-CLIENT-2`), and tool schema loading mode (resident vs on-demand preloading of `pm_state` and `pm_do`).
* The server must resolve client profiles using a two-tier override hierarchy (from lowest to highest precedence):
** Built-in profiles compiled into the `pm-mcpd` runtime binary (`classpath:/profiles/<client_id>.json` for `claude`, `opencode`, `antigravity`, `codex`, and `neutral`).
** Operator machine-level connection overrides in `<PM_MCP_BASE>/machine-config.json`: the closed object `client_profiles.<client_id>.connection` (`bounded_wait_seconds`, `idle_timeout_seconds`, `progress_resets_timeout`), set with `pm-operator config`; no other profile value can be overridden.
* The server must resolve model pins only from the machine-local effort ladder (`effort_ladder` of the operator file `<PM_MCP_BASE>/projects/<project_id>/local-config.json`), with the built-in profile ladder as default, and from the operator's model per model-job role and harness override in the same file (`model_jobs.roles.<role>.model`, `model_jobs.harness`), and must never read client profile overrides or model pins from git-tracked configuration (`plan-marshall` ADR-021).
* All profile documents must be validated against the closed client profile JSON Schema at startup, and the connection overrides against the closed schema of `machine-config.json`; a malformed profile or override must be rejected with a structured diagnostic error.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/timeouts/03-retention-host-config.adoc#host-integration[Timeouts & Budgets Specification] (host idle timeout, bounded wait bounds) for implementation details.

[#PM-CLIENT-6]
=== PM-CLIENT-6: Post-Compaction Scope Pointer

After context loss the model must re-learn which scope it works on without re-reading plan files.

* On hosts with session lifecycle hooks, the client bundle must install a session-start hook that, on the events `startup`, `clear`, and `compact`, emits a pointer (scope identifier, current phase, and the `pm_state` call to make) and never a state body; the payload has a hard size ceiling.
* The hook must also point at a pending bootstrap entry (a plan or epic entry whose scope does not exist yet) with the `pm_state` call that addresses it, preferring the scope or entry matched on the host session id and, among them, the newest; it stays within the same size ceiling and reads files only.
* The hook must emit nothing when no live scope or pending entry is bound to the workspace and session, and must degrade to a defined, non-crashing notice when the scope's state is unreadable.
* The pointer must be resolved by a deterministic verb of `pm-mcp` (`pm-mcp hook session-start`) from persisted records, without contacting or starting the runtime and without loading a skill.
* The same hook must also print the bundle drift notice (`PM-DIST-4`); the pointer and the drift notice are independent, and neither suppresses the other.
* On hosts without lifecycle hooks, `pm_plans` must mark the scope last entered by the current host session, identified by the `client_session_id` the relay forwards with every request and matched against the session logs; without a session identifier, the scope with the most recent session row in the workspace.
