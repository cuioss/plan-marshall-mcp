== Client Profiles & Dynamic Translation (PM-CLIENT)

[#PM-CLIENT-1]
=== PM-CLIENT-1: Entry Identity Declaration

The identity of an interactive host is declared at entry and recorded with the scope it enters; a worker's identity is its job record, and its harness comes from its role.

* Every user-invoked entry command (`/mcp-marshall-steward` for project setup in the workspace scope, `/mcp-plan-marshall` for the plan lifecycle, `/mcp-plan-orchestrator` for epic orchestration; the `$mcp-…` skills on Codex) must execute `pm-mcp enter --client <client> <plan|epic|workspace> [plan_id | epic_id]` in the host's shell prior to the first MCP tool call, passing the user's words as an optional free-text hint as a file or on standard input (never on the command line); the entry names no source, which the bootstrap gathers (`PM-TOOL-1`).
* The entry commands must carry the `mcp-` prefix, and the command and skill files of the client bundles must follow the command names: the three commands complete together in the host (`/mcp…`) and coexist with the commands of the `plan-marshall` plugin in a mixed installation (`PM-MIG-2`); the plain names follow once `plan-marshall` is withdrawn (link:later-improvements.adoc#_l_9_plain_entry_command_names[Later Improvements, L-9]).
* The client identity (`claude`, `opencode`, `antigravity`, `codex`, `neutral`) must be treated strictly as advisory routing and rendering metadata used to format representations, skill syntax, and host tool names, never as an authenticated security credential. The client bundle must declare it twice: in the entry commands (`--client`) and in the host's MCP configuration of the relay (`pm-mcp serve --client <client>`), from which the runtime renders every call of the session.
* Upon `pm-mcp enter`, which sends what the host shell sees as one request to the runtime (started on demand) and writes no store itself, the runtime must append one entry row to the scope's append-only session log `sessions.jsonl` (in the plan or epic directory, or in the project's workspace home `<PM_MCP_BASE>/projects/<project_id>/workspace/`), recording the host session identifier (`client_session_id`, `null` when the host provides none), the declared and the detected client, the exact host build obtained by the profile's version probe (`client_build`, `null` when unavailable), the model family and identifier where the host exposes them, the release version of the runtime that wrote the row (`pm_mcp_version`) and the installed bundle version (`bundle_version`), the `project_id`, whether the session entered from the main checkout or a worktree (and which), and the entry instant; session logs must live only in the per-project machine store (`<PM_MCP_BASE>/projects/<project_id>/`), never in the repository or under git tracking, and no row records a filesystem path of the checkout. Only `pm-mcp enter` appends a row.
* For a `plan` or `epic` entry that names no live scope (nothing named, a new, archived, or unknown id), the runtime must write a pending entry record `<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>.json` under a freshly allocated `entry_id`, holding the session row, the scope kind, the requested id, the hint, and the state of the entry's bootstrap, and `pm-mcp enter` must print `entry: <entry_id>`; for a live scope named by its id it appends the session row and prints the scope. The bootstrap's completion must consume the record so that its session becomes the first row of the new scope's session log, so that concurrent entries never share or overwrite a record.
* A worker's connection (`PM-WF-5`) must take its client profile from the harness its role names (`PM-WORK-1`), recorded in its job record; it appends no session row and carries its `job_id`, role, and generation in its audit records.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification], link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/filesystem-layout.adoc[Filesystem Layout Specification], link:specification/store-schemas.adoc[Store Schemas Specification], and link:specification/runtime-model.adoc[Runtime & Interaction Model Specification] for implementation details.

[#PM-CLIENT-2]
=== PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation

Instead of generating static per-runtime copies of the skill corpus at build time, `PM-MCP` must dynamically translate all model-facing artifacts per request using declarative client profiles for all supported coding agents (`claude`, `opencode`, `antigravity`, `codex`, and `neutral`).

* The system must translate vocabulary skills, state representations, hypermedia links, and the launches and prompt files of workers on the fly according to the client profile of the calling connection or of the worker's harness across the following dimensions:
** *Host Tool Names*: Translating canonical tool references to runtime-native names (e.g., `Read` -> `view_file` in Antigravity, `read` in OpenCode, or `read_file` in Codex _(provisional)_; `AskUserQuestion` -> `ask_question`, `question`, or `request_user_input` _(provisional)_).
** *Skill Load Directives*: Rendering skill invocation syntax for the client's native discovery mechanism (`pm_skill(plan_id="...", uri="...")` tool call or `resources/read` resource read).
** *Command Names*: Formatting the `mcp-` prefixed entry commands (`PM-CLIENT-1`) using the client's namespace conventions (a `/mcp-…` command, or a `$mcp-…` skill on Codex).
** *Tool Idioms*: Rewriting, preserving, or rewording runtime-specific idioms according to registered profile dispositions.
** *Models & Effort*: Rendering the model and effort a role names (`PM-WORK-1`) into the harness's model identifier and effort arguments.
** *Headless Model Jobs*: Composing a model job's launch (`PM-WF-5`) from the profile's `headless` block: an argument-vector template with typed slots (prompt file, model, effort, MCP configuration, result schema, tools, working directory), how the harness receives its MCP configuration (a slot of the launch or a file in the worker's working directory, exclusive or not), what it can run per role class (a `zero_tool` class only where it can be started with no tool and no MCP connection, which the screener and the judge require; for the `writer` and `read_only` classes whether it enforces the role's tool set or leaves the worker every tool of the harness, which is accepted), the declared capabilities (result schema, ephemeral run, usage and cost fields, reliable exit status, project-settings control), the supported harness version range, the writable harness paths and, where the harness's local state must not be shared between workers, a per-worker data directory (`PM-SEC-5`), the harness's per-tool-result limit (a task input or offer that would exceed it is delivered as resource reads below the limit, its identifiers first, so a harness that truncates a tool result never loses the task), the harness's MCP-resource-reading tools (allowlisted for the `writer` and `read_only` job classes, never for `zero_tool`), and `agent_mode` (`inline`: a per-job named agent rendered for Claude Code and OpenCode; `flags`: per-call flags for Codex). A harness lacking a capability that a role's class needs runs no worker of that role (`PM-WORK-1`).
** *Worker Parameters & Eligibility*: The profile's `worker` block: whether the harness is eligible as a worker host (`worker.eligible`), whether its interactive session may take tasks (`worker.session_tasks`, `PM-WORK-5`), which of its models accept an enforced tool set, the acknowledgement deadline and whether it is informational, the silence grace, and the idle wake-ups (`PM-WORK-3`); the bounded wait and whether progress resets the host's timeout are values of the profile's `connection` block, the host's timing facts. A harness is eligible only after its worker behaviour has been measured on it, under the target conditions, with every fault of the fault matrix passed: the Claude Code profile is eligible, the OpenCode profile is eligible with its per-worker data directory, and the Antigravity, Codex, and neutral profiles are not eligible until then; the operator assigns their roles to an eligible harness.
* Dynamic profile rendering must compute deterministic per-client skill digests so each client runtime observes a stable, verifiable skill catalogue.
* The system must restrict profile translation to the vocabulary dimensions above; any per-client or per-model change of wording, emphasis, or scaffolding requires a behavioural signal for that client (`PM-TEST-6`) and a recorded decision before it ships.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification], link:specification/model-work.adoc[Model Work Specification], and link:specification/mcp-tools.adoc[MCP Tools & Resources Specification] for implementation details. The measurements behind its values are recorded in the link:specification/evaluation.adoc[Evaluation Reference].

[#PM-CLIENT-3]
=== PM-CLIENT-3: Entry Identity Audit

To keep the declared identity of a session honest without checking it on every call, the system must cross-check it once, at entry, against the host environment and record the result for the operator.

* `pm-mcp enter` must inspect the inherited process environment against the per-client detection signals and their fixed precedence defined in the link:specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table] (primary signals `ANTIGRAVITY_AGENT`, `OPENCODE` / `OPENCODE_PID`, `CLAUDE_CODE_SESSION_ID`, checked in this order, then `CODEX_SANDBOX` / `CODEX_CI` / `CODEX_THREAD_ID` for Codex, which only `pm-mcp enter` sees because Codex passes a fixed variable list to its MCP servers; secondary signals `CLAUDECODE` and the host prefix of `AI_AGENT`), treating values marked provisional there as unverified; when the markers of more than one host are present (a host started inside another clears none of the other's markers), the host whose process-id marker names the nearest ancestor process of `pm-mcp enter` must be detected, the fixed order deciding only when no such marker resolves.
* The audit record of the entry must carry three identity tiers: the declared client (`--client`), the detected environment (`unknown` if unrecognized), and the authenticated OS principal; a disagreement between the first two is recorded as `identity_mismatch=true` and reported to the operator in `pm-operator status` and the web app, never in a model-facing representation.
* The system must perform no identity check per tool call: a call is rendered from the client its relay declares (`PM-CLIENT-1`), and a worker's call from its job record.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-CLIENT-4]
=== PM-CLIENT-4: Neutral Fallback Profile for Unknown Clients

Connections originating from unrecognized or unprofiled MCP clients must degrade gracefully and visibly to a standard, host-agnostic interaction mode.

* When a session enters with an unrecognized client identity (`unknown`) or connects without a matching client profile, the system must serve the session using a built-in *neutral profile*.
* Under the neutral profile, the system must:
** Emit links and instructions referencing only `PM-MCP`'s own standard MCP tools of the entry session (`PM-TOOL-1`).
** Omit all host-specific native tool names and shell idioms; the neutral profile is never a worker host, and its session takes no task (`PM-WORK-5`).
** Make the profile visible to the operator per session, in `pm-operator status`, in the scope's session row, and in the audit record, never through a model-facing neutral-profile marker in the state representation (`PM-TOOL-5`).

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] for implementation details.

[#PM-CLIENT-5]
=== PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy

Client profiles must be governed as versioned, schema-validated data artifacts embedded in the binary and extensible via local configuration overrides.

* Every client profile definition must be a declarative JSON document carrying an explicit integer `schema_version` and minimum compatible server version (bundle versions and file digests live in the per-client `bundle-manifest.json`, `PM-DIST-2`).
* The profile must be the one configuration document of a harness and the only place the system describes it: the detection signals and identity probes, the vocabulary, the launch contract of its headless run, what it can run per role class, and its worker parameters. Production code must read profiles through one generic reader and must name no harness; a new harness is a new profile document, and a new measurement or a corrected value of a harness is a change of its profile, with no change of code unless the harness needs a mechanism the schema lacks.
* Each profile must state whether its harness can run the `zero_tool` class, that is be started with no tool and no MCP connection: only such a harness may be named by a screener or judge role (`PM-SEC-1`). For the other role classes the profile must state whether the harness enforces a role's tool set or leaves the worker every tool it has; both are accepted, and the operator must be able to see which roles run unrestricted.
* Each profile must declare the client's entry command names (the `mcp-` prefixed commands of `PM-CLIENT-1` in the client's own syntax), its `stdio` connection configuration (`pm-mcp serve`), supported protocol capabilities (progress notification idle-timer reset, tool-call timeout bounds; whether a connection supports MCP elicitation is taken only from the capabilities the connection declares), its `headless` and `worker` blocks (`PM-CLIENT-2`), and tool schema loading mode (resident vs on-demand preloading of `pm_state` and `pm_do`).
* The server must resolve client profiles using a two-tier override hierarchy (from lowest to highest precedence):
** Built-in profiles compiled into the `pm-mcpd` runtime binary (`classpath:/profiles/<client_id>.json` for `claude`, `opencode`, `antigravity`, `codex`, and `neutral`).
** Operator machine-level connection overrides in `<PM_MCP_BASE>/machine-config.json`: the closed object `client_profiles.<client_id>.connection` (`bounded_wait_seconds`, `idle_timeout_seconds`, `progress_resets_timeout`), set with `pm-operator config`; no other profile value can be overridden.
* The server must resolve harness, model, and effort only from the role artifacts (`PM-WORK-1`), which are operator files, and must never read client profile overrides or model pins from git-tracked configuration (`PM-EXT-6`).
* All profile documents must be validated against the closed client profile JSON Schema at startup, and the connection overrides against the closed schema of `machine-config.json`; a malformed profile or override must be rejected with a structured diagnostic error.

See the link:specification/client-profiles.adoc[Client Profiles & Dynamic Translation Specification] and link:specification/timeouts/03-retention-host-config.adoc#host-integration[Timeouts & Budgets Specification] (host idle timeout, bounded wait bounds) for implementation details.
