== Platform Services (PM-SVC)

[#PM-SVC-1]
=== PM-SVC-1: Integrated Build Server & Working-Tree Hash Freshness

`pm-mcp` must host an integrated build server that manages cross-session build concurrency via shared filesystem slot locks, parses build outputs natively, and tracks working-tree freshness deterministically.

* The system must manage all project builds through an integrated build server within `pm-mcp`, enforcing a machine-wide build-slot concurrency cap (`~/.plan-marshall/mcp/state/build-slots.json` under `FileChannel.lock()`), execution policy, and audit logging across all enrolled projects and concurrent STDIO sessions.
* The system must resolve build commands server-side from project configuration and compiled domain support, invoking the project's wrapper or enrolled host tool within the plan's worktree without exposing command lines to the model.
* The system must parse raw build outputs using native Java log parsers (supporting Maven Surefire/Failsafe, Gradle, npm/Jest, and pytest) to produce structured results containing closed-enum status, test counts, and located error diagnostics.
* The system must return `status: failed_unparsed` accompanied by the raw build log resource URI (`pm://plan/{plan_id}/builds/{job_id}/log`) whenever a build subprocess crashes, segfaults, or emits unparseable output.
* The system must track build freshness against the exact working-tree state by computing a SHA-256 content hash over `git rev-parse HEAD`, `git diff HEAD`, and the sorted paths and contents of `git ls-files --others --exclude-standard`, maintaining bit-for-bit parity with plan-marshall's `worktree_sha` algorithm.
* The system must evaluate quality and pre-commit freshness gates directly against the recorded working-tree hash and build scope without relying on model attestation.

See the link:specification/job-runtime.adoc[Job Runtime Specification] and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-SVC-2]
=== PM-SVC-2: Warm Language Server Pool & Semantic Code Navigation

Each `pm-mcp` server process must maintain a pool of warm language servers per workspace and language over `stdio` pipes to provide low-latency semantic code navigation and refactoring.

* The system must maintain a warm language server pool keyed by `(workspace, language)`, treating each plan worktree as an isolated workspace.
* The system must start language server subprocesses lazily upon first `pm_lsp` request and terminate them automatically after an idle timeout, when the owning plan worktree is removed, or when the parent `pm-mcp` STDIO session exits.
* The system must expose semantic code operations through `pm_lsp`, supporting `workspace_symbol` (`workspace/symbol`), `document_symbol` (`textDocument/documentSymbol`), `definition` (`textDocument/definition`), `references` (`textDocument/references`), `hover` (`textDocument/hover`), `diagnostics` (`textDocument/publishDiagnostics`), and `rename` (`textDocument/rename`, executed as a verified `WorkspaceEdit`).
* The system must apply `rename` workspace edits directly on the server and automatically record all modified file paths in the plan's realized footprint state without requiring model self-reporting.

See the link:specification/job-runtime.adoc[Job Runtime Specification] and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-SVC-3]
=== PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging

The daemon must selectively aggregate configured upstream MCP servers while enforcing strict provenance tagging and credential isolation to prevent trust laundering.

* The system must selectively re-expose only the specific upstream MCP tools required by active workflows, optionally narrowing their parameter schemas to minimize client context overhead.
* The system must attach provenance metadata to all proxied upstream responses under a PM-MCP `_meta` prefix identifying the originating server, and must treat all upstream content as untrusted external input within the workflow engine.
* The system must never re-serve skills from upstream MCP servers as PM-MCP vocabulary skills.
* The system must authenticate to each upstream MCP server using credentials configured specifically for that server in the PM-MCP credential store, strictly prohibiting the passthrough of tokens received from host clients or other servers.

See the link:specification/mcp-tools.adoc[MCP Tools Specification] and link:specification/daemon-endpoint.adoc[Daemon Endpoint Specification] for implementation details.

[#PM-SVC-4]
=== PM-SVC-4: Orthogonal Service Access Outside Active Workflow Links

Developer assistance services (`pm_build`, `pm_lsp`) must remain directly callable during implementation tasks without requiring or triggering hypermedia state transitions.

* The system must allow the model and dispatched sub-agents to invoke `pm_build` and `pm_lsp` directly at any point during task implementation or troubleshooting, independent of the transitions currently listed in the state representation's `links`.
* The system must execute orthogonal `pm_build` and `pm_lsp` calls without mutating or advancing the plan's workflow phase or step state.
* The system must automatically scope orthogonal service calls to the worktree of the specified `plan_id` and record build outcomes and working-tree hashes in the plan's change ledger so that subsequent verification gates can reuse fresh green build results.

See the link:specification/mcp-tools.adoc[MCP Tools Specification] and link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.
