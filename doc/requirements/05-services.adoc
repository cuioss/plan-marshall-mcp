== Platform Services (PM-SVC)

[#PM-SVC-1]
=== PM-SVC-1: Integrated Build Server & Working-Tree Hash Freshness

`pm-mcpd` must host an integrated build server that manages cross-session build concurrency via shared filesystem slot locks, parses build outputs natively, and tracks working-tree freshness deterministically.

* The system must manage all project builds through an integrated build server within `pm-mcpd`, enforcing a machine-wide build-slot concurrency cap (`max_build_slots` in `<PM_MCP_BASE>/machine-config.json`; slot occupancy in `<PM_MCP_BASE>/state/build-slots.json` under its sibling lock `<PM_MCP_BASE>/locks/build-slots.lock`), execution policy, and audit logging across all enrolled projects and concurrent STDIO sessions.
* The system must resolve build commands server-side from project configuration and compiled domain support, invoking the project's wrapper or enrolled host tool within the plan's worktree without exposing command lines to the model.
* The system must parse raw build outputs using native Java log parsers (supporting Maven Surefire/Failsafe, Gradle, npm errors, TypeScript, ESLint, Jest, TAP, pytest, ruff, mypy, and OpenRewrite, `PM-IMPL-6`) to produce structured results containing closed-enum status, test counts, and located error diagnostics.
* The system must return `status: failed_unparsed` accompanied by the raw build log resource URI (`pm://plan/{plan_id}/builds/{job_id}/log`) whenever a build subprocess exits non-zero and yields no parsed diagnostic; a build ended by a signal, including a crash such as a segmentation fault, is `killed` with the signal recorded (link:specification/job-runtime/01-pipeline-and-subprocesses.adoc#outcome-derivation[Job Runtime Specification, Outcome Derivation]).
* The system must track build freshness against the exact working-tree state by computing a PM-MCP-native, variant-neutral SHA-256 content hash (`worktree_sha`, hash version 1) over the `HEAD` commit id plus, for every path the working-tree status reports as changed, deleted, or untracked (sorted by path), the path and either the file's bytes read from disk or a deletion marker. The digest is one operation of the git contract (`git.worktree-sha`, usable as a single workflow node) served by both variants from the same status information (native: JGit `StatusCommand`; CLI: `git status --porcelain -z`) and returns the digest together with its hash version. Every record carrying the digest must carry its hash version, a change of the computation must be a new version, and freshness gates must compare only digests of equal versions. If the status or a file read fails, no digest may be produced: the value is `unavailable` with the failing step recorded, and every freshness gate keyed on it must evaluate indeterminate, never fresh (a deliberate change against plan-marshall, which hashes the empty output of a failed call). Byte parity with plan-marshall's `worktree_sha` is not required, because the digest is never exchanged (`PM-MIG-2`); differential tests compare equality behaviour (`PM-TEST-2`).
* The system must evaluate quality and pre-commit freshness gates directly against the recorded working-tree hash and build scope without relying on model attestation.

See the link:specification/job-runtime.adoc[Job Runtime Specification] and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-SVC-2]
=== PM-SVC-2: Warm Language Server Pool & Semantic Code Navigation

The runtime must maintain a pool of warm language servers, shared by all host connections, per workspace and language over `stdio` pipes to provide low-latency semantic code navigation and refactoring.

* The system must maintain a warm language server pool keyed by `(workspace, language)`, treating each plan worktree as an isolated workspace.
* The system must start language server subprocesses through the job launcher `pm-mcp-exec` under the same confinement as jobs but without job records (after a runtime crash they end when their `stdin` closes), lazily upon first `pm_lsp` request and terminate them automatically after an idle timeout, when the owning plan worktree is removed, or when the runtime drains or stops, and must bound every language server start and request by a timeout that is reported, never answered with an empty result.
* The system must expose semantic code operations through `pm_lsp`, supporting `workspace_symbol` (`workspace/symbol`), `document_symbol` (`textDocument/documentSymbol`), `definition` (`textDocument/definition`), `references` (`textDocument/references`), `hover` (`textDocument/hover`), `diagnostics` (LSP 3.17 pull diagnostics via `textDocument/diagnostic`, falling back to the diagnostics last published through the `textDocument/publishDiagnostics` notification when the server lacks pull support), and `rename` (`textDocument/rename`, executed as a verified `WorkspaceEdit`).
* The system must apply `rename` workspace edits directly on the server and automatically record all modified file paths in the plan's realized footprint state without requiring model self-reporting.

See the link:specification/job-runtime.adoc[Job Runtime Specification], link:specification/mcp-tools.adoc[MCP Tools Specification], and link:specification/timeouts.adoc[Timeouts & Budgets Specification] for implementation details.

[#PM-SVC-3]
=== PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging

The runtime must be the host's single MCP entry point: configured upstream MCP servers are connected once, centrally, and reached through PM-MCP instead of being wired into every host, while provenance tagging and credential isolation prevent trust laundering.

* The system must read the upstream allowlist (servers, the tools re-exposed per server, and their credential keys) exclusively from the operator-owned `<PM_MCP_BASE>/conf/upstream-mcp.json`, per project; repository content such as the team configuration under `.marshall/config/` must never add a server or a tool.
* The system must re-expose only allowlisted upstream tools to the host, as a pass-through surface separate from the core `pm_*` tools, named `up_<server_id>_<tool>` (link:specification/identifiers/02-registry-stores-to-web.adoc#id-upstream-tool-name[Identifier Registry]), optionally narrowing their parameter schemas to minimize client context overhead; the pass-through surface changes only when the operator changes the allowlist.
* The system must let workflow steps call allowlisted upstream tools server-side, and must admit such results into plan stores only through the untrusted-ingestion validator (`PM-SEC-1`).
* The system must attach provenance metadata to all proxied upstream responses under the PM-MCP-prefixed `_meta` key `de.cuioss.pm-mcp/source` (MCP `_meta` key prefix convention) identifying the originating server, and must treat all upstream content as untrusted external input within the workflow engine.
* The system must never re-serve skills from upstream MCP servers as PM-MCP vocabulary skills.
* The system must authenticate to each upstream MCP server using credentials configured specifically for that server in the PM-MCP credential store, strictly prohibiting the passthrough of tokens received from host clients or other servers.

See the link:specification/mcp-tools.adoc[MCP Tools Specification], link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and the link:specification/identifiers.adoc[Identifier Registry] for implementation details.

[#PM-SVC-4]
=== PM-SVC-4: Orthogonal Service Access Outside Active Workflow Links

Developer assistance services (`pm_build`, `pm_lsp`) must remain directly callable during implementation tasks without requiring or triggering hypermedia state transitions.

* The system must allow the model and dispatched sub-agents to invoke `pm_build` and `pm_lsp` directly at any point during task implementation or troubleshooting, independent of the transitions currently listed in the state representation's `links`.
* The system must execute orthogonal `pm_build` and `pm_lsp` calls without mutating or advancing the plan's workflow phase or step state.
* The system must automatically scope orthogonal service calls to the worktree of the specified `plan_id` and record build outcomes and working-tree hashes in the plan's change ledger so that subsequent verification gates can reuse fresh green build results.

See the link:specification/mcp-tools.adoc[MCP Tools Specification] and link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.
