== Technology Stack & Platform Integration (PM-TECH)

[#PM-TECH-1]
=== PM-TECH-1: Java 25+ & Quarkus MCP Server Foundation

The implementation of `PM-MCP` builds upon a modern, high-performance Java runtime utilizing the Quarkus framework and the Quarkiverse MCP Server extension.

* The system must use Java 25+ as the baseline programming language level, utilizing modern Java features including records, pattern matching, sealed types, and Virtual Threads.
* The system must use Quarkus as the underlying server framework and the Quarkiverse Quarkus MCP Server extension tracking MCP protocol version `2026-07-28` while maintaining backwards compatibility with legacy stateful clients.
* The system must serve the Model Context Protocol over the Streamable HTTP transport on loopback TCP as its primary interface, and provide a stdio relay mode (`pm-mcp serve --stdio`) for clients that cannot inject HTTP headers dynamically.
* The system must implement the draft MCP Skills extension on top of the Quarkiverse extension API, structured to permit eventual upstream contribution.
* The system must implement core workflow mechanics, state machines, and TOON serialization as decoupled first-party code, avoiding heavy third-party workflow or state machine dependencies.

See the link:specification/daemon-endpoint.adoc[Daemon Endpoint Specification] and link:specification/mcp-tools.adoc[MCP Tools & Resources Specification] for implementation details.

[#PM-TECH-2]
=== PM-TECH-2: Security & HTTP Client Libraries (cui-http, TokenSheriff)

Inbound request sanitization, cryptographic validation, and outbound token interactions must be governed by proven, hardened enterprise libraries.

* The system must use `de.cuioss:cui-http` for inbound HTTP request validation (including automated attack-pattern detection and input sanitization) on all daemon endpoints.
* The system must use `cui-http` to manage TLS contexts and execute outbound HTTP requests for token-lane integrations, including code-quality services and upstream MCP servers.
* The system must use `de.cuioss:TokenSheriff` (`token-sheriff-validation`) to validate identity provider bearer tokens offline whenever the daemon endpoint is exposed beyond local loopback in remote or team environments.
* The system must use `TokenSheriff` (`token-sheriff-client`) to execute OAuth 2.1 and OIDC client flows when proxying upstream MCP servers that mandate MCP-compliant authorization.
* The system must enforce strict transport security for all external HTTP communication:
** HTTPS must be enforced for all outbound OAuth and upstream connections, with mandatory certificate and hostname verification that cannot be disabled.
** HTTP redirects must be followed only to HTTPS targets; any redirect attempting to downgrade to plain HTTP must be treated as a fatal connection error.
** Access tokens must be transmitted exclusively to the exact origin for which they were issued.

See the link:specification/daemon-endpoint.adoc[Daemon Endpoint Specification] and link:specification/job-runtime.adoc[Job Runtime & Execution Specification] for implementation details.

[#PM-TECH-3]
=== PM-TECH-3: GraalVM Native Executable & Startup/Memory Bounds

To ensure minimal host resource consumption and instant responsiveness, the system must compile to a single, standalone native executable with deterministic resource bounds.

* The system must produce a single standalone native executable (`pm-mcp`) per target platform using GraalVM Native Image, containing zero bundled JVM runtimes or Python interpreters.
* The system must adhere to a closed-world architecture: all domain definitions, workflow DSL state graphs, and native build log parsers must be compiled into the binary or packaged as static data, forbidding runtime loading of arbitrary executable bytecode.
* The native daemon must achieve a cold startup time to ready state of <= 50 milliseconds on reference hardware.
* The native daemon must maintain an idle Resident Set Size (RSS) memory footprint of <= 65 megabytes.
* The system must register all persisted types, Jackson serialization targets, and domain models for reflection (`@RegisterForReflection`); if Eclipse LSP4J dynamic proxies encounter native-image compilation barriers, the system must replace LSP4J with a lightweight JSON-RPC client rather than falling back to JVM deployment.

See the link:specification/daemon-endpoint.adoc[Daemon Endpoint Specification] and link:specification/job-runtime.adoc[Job Runtime & Execution Specification] for implementation details.

[#PM-TECH-4]
=== PM-TECH-4: Operating System Platform Integration (macOS & Linux)

The system must integrate natively with primary host operating systems, providing supervision templates, standard networking, and clean subprocess management.

* The system must support macOS (arm64, x86_64) and Linux (glibc, x86_64, aarch64) as first-tier deployment platforms, supporting Windows exclusively through the Windows Subsystem for Linux (WSL2).
* The system must package declarative service templates for operating system supervision:
** A launchd LaunchAgent property list (`pm-mcp.plist`) for macOS user sessions.
** A systemd user service unit (`pm-mcp.service`) for Linux user sessions.
* The system must listen exclusively on loopback TCP (`127.0.0.1:<port>`), utilizing standard TCP sockets to guarantee compatibility with native executables.
* The system must manage subprocess lifecycles using operating system process groups, providing clean process tree termination, SIGTERM graceful draining, and SIGKILL escalation upon timeout.

See the link:specification/daemon-endpoint.adoc[Daemon Endpoint Specification] and link:specification/job-runtime.adoc[Job Runtime & Execution Specification] for implementation details.
