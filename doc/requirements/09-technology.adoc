== Technology Stack & Platform Integration (PM-TECH)

[#PM-TECH-1]
=== PM-TECH-1: Java 25+ & Quarkus MCP Runtime Foundation

The implementation of `PM-MCP` builds upon a modern, high-performance Java runtime utilizing the Quarkus framework and the Quarkiverse MCP Server extension.

* The system must use Java 25+ as the baseline programming language level, utilizing modern Java features including records, pattern matching, sealed types, and Virtual Threads.
* The system must use Quarkus as the underlying framework and `io.quarkiverse.mcp:quarkus-mcp-server-http` in the runtime, tracking the frontier MCP protocol version `2026-07-28` exclusively, without legacy protocol fallbacks (`2025-11-25`, `2024-11-05`).
* The runtime (`pm-mcpd`) must serve MCP Streamable HTTP and the local REST API exclusively on a Unix domain socket (Vert.x with the Netty native transport, `kqueue` on macOS and `epoll` on Linux), authenticating every request through one Quarkus Security `HttpAuthenticationMechanism` (Bearer) with an `IdentityProvider` per token kind and resources annotated only `@Authenticated`; hosts must reach it exclusively through the `pm-mcp serve` STDIO relay, which boots no MCP server of its own.
* The CLI `pm-mcp` (including the relay) and the job launcher `pm-mcp-exec` must not use Quarkus: they are plain Java programs built with GraalVM `native-image` (`org.graalvm.buildtools:native-maven-plugin`); the CLI uses `info.picocli:picocli` with `picocli-codegen`, its own HTTP/1.1 and Server-Sent Events client over the JDK `SocketChannel` with `UnixDomainSocketAddress`, `jackson-core` without data binding, and `io.nayuki:qrcodegen`, and depends only on the API contract module (`PM-IMPL-1`). Only the runtime and the optional web server `pm-mcp-web` are Quarkus applications.
* The system must implement core workflow mechanics, state machines, and TOON serialization as decoupled first-party code, avoiding heavy third-party workflow or state machine dependencies.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and the link:specification/mcp-tools.adoc[MCP Tools & Resources Specification] for implementation details.

[#PM-TECH-2]
=== PM-TECH-2: Outbound HTTPS Client, LSP Client & McpAssured Testing Libraries

Outbound token-lane HTTPS communication, native git, Language Server Protocol integration, and MCP protocol verification must be governed by hardened, standard libraries.

* The system must use `de.cuioss:cui-http` (`HttpHandler`, `SecureSSLContextProvider`, `ResilientHttpAdapter`, `ETagAwareHttpAdapter`) to manage TLS contexts, input/response sanitization, and resilient outbound HTTPS requests for all token-lane integrations: the native provider clients (GitHub REST and fixed GraphQL documents, GitLab REST, SonarQube/SonarCloud REST) and remote upstream MCP servers. The provider clients must be thin clients of their own over `cui-http`, without a third-party provider SDK; the GitHub App JWT must be signed with the JDK (`RS256`, PKCS#8 key) without an additional cryptography library.
* The system must use Eclipse JGit (7.8 or later) through the Quarkiverse extension `quarkus-jgit` for the native git variant, with the JSch SSH module excluded; the native transport speaks HTTPS only. If the Milestone 1 native-image spike fails with `quarkus-jgit`, the fallback is JGit with own substitutions and reflection registrations in `pm-mcp-server`.
* The system must not require the `git`, `gh`, or `glab` command-line tools for an integration whose integration variant is native; they are required only for an integration the operator has set to the CLI variant (`PM-EXEC-5`).
* The system must use `org.eclipse.lsp4j:org.eclipse.lsp4j` for JSON-RPC 2.0 communication with warm language server subprocesses over `stdio` pipes.
* The system must use `io.quarkiverse.mcp:quarkus-mcp-server-test` (`McpAssured` and `McpStdioTestClient`) for automated MCP protocol verification across `@QuarkusTest` component tests and the `maven-failsafe-plugin` (`*IT.java`) integration tests: the packaged daemon over MCP/HTTP on its Unix socket (`pm-mcp-server`), the `pm-mcp serve` relay over real `stdio` against a reactor-built `pm-mcpd` staged into a temporary `PM_MCP_HOME/bin` (`pm-mcp-cli`), and the release-shape end-to-end tests over all four staged binaries (`pm-mcp-e2e`, `PM-IMPL-1`); the fourth integration test layer, the packaged web server (`pm-mcp-web-server`), serves no MCP and is verified without `McpAssured`.
* The system must enforce strict transport security for all external HTTP communication:
** HTTPS must be enforced for all outbound token-lane and upstream connections, with mandatory certificate and hostname verification that cannot be disabled.
** HTTP redirects must be followed only to HTTPS targets; any redirect attempting to downgrade to plain HTTP must be treated as a fatal connection error.
** Access tokens must be transmitted exclusively to the exact origin for which they were issued.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/job-runtime.adoc[Job Runtime Specification], and link:specification/mcp-tools.adoc[MCP Tools & Resources Specification] for implementation details.

[#PM-TECH-3]
=== PM-TECH-3: GraalVM Native Executable & Startup/Memory Bounds

To ensure minimal host resource consumption and instant per-session STDIO responsiveness, the system must compile to standalone native executables with deterministic resource bounds.

* The system must produce, per target platform and from one release version, four standalone native executables using GraalVM Native Image: the CLI `pm-mcp` (plain native image), the runtime `pm-mcpd` (Quarkus native), the job launcher `pm-mcp-exec` (plain native image), and the optional web server `pm-mcp-web` (Quarkus native), containing zero bundled JVM runtimes or Python interpreters.
* The system must adhere to a closed-world architecture: all domain definitions, workflow DSL state graphs, and native build log parsers must be compiled into the binary or packaged as static data, forbidding runtime loading of arbitrary executable bytecode.
* The native runtime `pm-mcpd` must achieve a cold startup time to ready state of <= 50 milliseconds on reference hardware, where ready means the runtime token is written and the socket is bound and accepting connections without any per-project recovery (recovery runs lazily per project and in a background pass after bind, `PM-ARCH-7`), measured on a clean state (no stale socket or runtime record, no project to recover); the `pm-mcp serve` relay must forward the host's `initialize` to a running runtime within <= 50 milliseconds of process start; and every other CLI command must send its first request to a running runtime within <= 50 milliseconds of process start.
* The native runtime `pm-mcpd` must maintain an idle Resident Set Size (RSS) memory footprint of <= 64 megabytes, excluding child jobs and language servers.
* The system must register all persisted types, Jackson serialization targets, and domain models for reflection (`@RegisterForReflection`); if Eclipse LSP4J dynamic proxies encounter native-image compilation barriers, the system must replace LSP4J with a lightweight Jackson JSON-RPC client rather than falling back to JVM deployment.

See the link:specification/module-structure.adoc[Module Structure Specification] and the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and the link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-TECH-4]
=== PM-TECH-4: Operating System Platform Integration (macOS & Linux)

The system must integrate natively with primary host operating systems, providing POSIX file locking, Linux Landlock filesystem confinement, and clean subprocess management.

* The system must support macOS (`arm64`, `x86_64`) and Linux (`glibc`, `x86_64`, `aarch64`) as first-tier deployment platforms, supporting Windows exclusively through the Windows Subsystem for Linux (WSL2).
* The system must coordinate the runtime's store writes using OS-level `FileChannel.lock()` advisory locks and atomic POSIX filesystem renames (`ATOMIC_MOVE`); the CLI, including the `pm-mcp serve` relay, writes no store and takes no store lock, its only lock being `runtime-start.lock`, which serializes the on-demand runtime start (`PM-ARCH-1`).
* The system must manage subprocess lifecycles using operating system process groups, providing clean process tree termination, `SIGTERM` graceful draining, and `SIGKILL` escalation upon timeout.
* On Linux, the system must use Landlock (ABI >= 2, kernel >= 5.19; a lower ABI is recorded as `confinement: partial(abi=N)`, never as confined) and `PR_SET_NO_NEW_PRIVS` to confine jobs to read-only filesystem access outside `<PM_MCP_BASE>` (which jobs can neither read nor write, a model job's own job-private directory excepted) with explicit write access for the job's own project root and the other paths listed in `PM-SEC-5`.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/job-runtime.adoc[Job Runtime Specification], and link:specification/timeouts/01-job-budgets-and-waits.adoc#grace-period[Timeouts & Budgets Specification] (termination grace period) for implementation details.
