== Technology Stack & Platform Integration (PM-TECH)

[#PM-TECH-1]
=== PM-TECH-1: Java 25+ & Quarkus MCP Runtime Foundation

The implementation of `PM-MCP` builds upon a modern, high-performance Java runtime utilizing the Quarkus framework and the Quarkiverse MCP Server extension.

* The system must use Java 25+ as the baseline programming language level, utilizing modern Java features including records, pattern matching, sealed types, and Virtual Threads.
* The system must use Quarkus as the underlying framework and `io.quarkiverse.mcp:quarkus-mcp-server-http` in the runtime, tracking the frontier MCP protocol version `2026-07-28` exclusively, without legacy protocol fallbacks (`2025-11-25`, `2024-11-05`).
* The runtime must serve MCP Streamable HTTP exclusively on a Unix domain socket (Vert.x with the Netty native transport, `kqueue` on macOS and `epoll` on Linux), and hosts must reach it exclusively through the `pm-mcp serve` STDIO relay, which boots no MCP server of its own.
* The system must implement core workflow mechanics, state machines, and TOON serialization as decoupled first-party code, avoiding heavy third-party workflow or state machine dependencies.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and the link:specification/mcp-tools.adoc[MCP Tools & Resources Specification] for implementation details.

[#PM-TECH-2]
=== PM-TECH-2: Outbound HTTPS Client, LSP Client & McpAssured Testing Libraries

Outbound token-lane HTTPS communication, Language Server Protocol integration, and MCP protocol verification must be governed by hardened, standard libraries.

* The system must use `de.cuioss:cui-http` (`HttpHandler`, `SSLContextProvider`, `ResilientHttpAdapter`) to manage TLS contexts, input/response sanitization, and resilient outbound HTTPS requests for token-lane integrations (such as SonarQube/SonarCloud REST APIs and remote upstream MCP servers).
* The system must use `org.eclipse.lsp4j:org.eclipse.lsp4j` for JSON-RPC 2.0 communication with warm language server subprocesses over `stdio` pipes.
* The system must use `io.quarkiverse.mcp:quarkus-mcp-server-test` (`McpAssured` and `McpStdioTestClient`) for automated MCP protocol verification across both `@QuarkusTest` component tests and `maven-failsafe-plugin` (`*IT.java`) end-to-end STDIO integration tests against the packaged JAR and GraalVM native executable.
* The system must enforce strict transport security for all external HTTP communication:
** HTTPS must be enforced for all outbound token-lane and upstream connections, with mandatory certificate and hostname verification that cannot be disabled.
** HTTP redirects must be followed only to HTTPS targets; any redirect attempting to downgrade to plain HTTP must be treated as a fatal connection error.
** Access tokens must be transmitted exclusively to the exact origin for which they were issued.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/job-runtime.adoc[Job Runtime & Execution Specification], and link:specification/mcp-tools.adoc[MCP Tools & Resources Specification] for implementation details.

[#PM-TECH-3]
=== PM-TECH-3: GraalVM Native Executable & Startup/Memory Bounds

To ensure minimal host resource consumption and instant per-session STDIO responsiveness, the system must compile to a single, standalone native executable with deterministic resource bounds.

* The system must produce a single standalone native executable (`pm-mcp`) per target platform using GraalVM Native Image, containing zero bundled JVM runtimes or Python interpreters.
* The system must adhere to a closed-world architecture: all domain definitions, workflow DSL state graphs, and native build log parsers must be compiled into the binary or packaged as static data, forbidding runtime loading of arbitrary executable bytecode.
* The native `pm-mcp` runtime must achieve a cold startup time to ready state (socket accepting connections) of <= 50 milliseconds on reference hardware, and the `pm-mcp serve` relay must forward the host's `initialize` to a running runtime within <= 50 milliseconds of process start.
* The native `pm-mcp` runtime must maintain an idle Resident Set Size (RSS) memory footprint of <= 64 megabytes, excluding child jobs and language servers.
* The system must register all persisted types, Jackson serialization targets, and domain models for reflection (`@RegisterForReflection`); if Eclipse LSP4J dynamic proxies encounter native-image compilation barriers, the system must replace LSP4J with a lightweight Jackson JSON-RPC client rather than falling back to JVM deployment.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and the link:specification/job-runtime.adoc[Job Runtime & Execution Specification] for implementation details.

[#PM-TECH-4]
=== PM-TECH-4: Operating System Platform Integration (macOS & Linux)

The system must integrate natively with primary host operating systems, providing POSIX file locking, Linux Landlock filesystem confinement, and clean subprocess management.

* The system must support macOS (`arm64`, `x86_64`) and Linux (`glibc`, `x86_64`, `aarch64`) as first-tier deployment platforms, supporting Windows exclusively through the Windows Subsystem for Linux (WSL2).
* The system must coordinate the runtime, `pm-mcp serve` relays, and CLI invocations using OS-level `FileChannel.lock()` advisory locks and atomic POSIX filesystem renames (`ATOMIC_MOVE`).
* The system must manage subprocess lifecycles using operating system process groups, providing clean process tree termination, `SIGTERM` graceful draining, and `SIGKILL` escalation upon timeout.
* On Linux, the system must use Landlock (kernel >= 5.13) and `PR_SET_NO_NEW_PRIVS` to confine jobs to read-only filesystem access with explicit write access for enrolled project roots and the other paths listed in `PM-SEC-5`.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] and link:specification/job-runtime.adoc[Job Runtime & Execution Specification] for implementation details.
