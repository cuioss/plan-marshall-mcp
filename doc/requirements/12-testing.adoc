== Quality Assurance & Testing Strategy (PM-TEST)

[#PM-TEST-1]
=== PM-TEST-1: Script Disposition Classification (Ported, Redesigned, Retired)

To preserve the defect-prevention knowledge encoded in the existing `plan-marshall` codebase (~315–436 scripts and ~22,000 test functions) without carrying over obsolete scaffolding, every script must be classified and tested according to its architectural disposition.

* The system must maintain an authoritative migration inventory that assigns every `plan-marshall` script (evaluated against a pinned repository commit prior to each migration stage) to exactly one of three mutually exclusive categories:
** *Ported*: Data and integration layer primitives—specifically the reading and writing of `status.json`, `tasks/`, `findings.jsonl`, `lessons`, and `references.json`, git and CI integrations, worktree SHA-256 freshness calculation, and pure classification heuristics.
** *Redesigned*: Phase lifecycle orchestration, routing, planning-lane selection, finalize dispatch, epic orchestration, and the execution manifest, which are superseded by the declarative hypermedia workflow engine.
** *Retired*: Executor proxy generation (`execute-script.py`), plugin-cache synchronization, host permission doctors/fixers, and static multi-target corpus generators made obsolete by the native daemon.
* The verification strategy for each component must be strictly bound to its disposition category: ported components must pass differential equivalence and JUnit module tests; redesigned components must pass state-machine and end-to-end scenario tests; retired components must be removed along with their legacy unit tests.

See the link:specification/store-schemas.adoc[Store Schemas & Data Model Specification] for implementation details.

[#PM-TEST-2]
=== PM-TEST-2: Differential Equivalence Testing for Ported Primitives

Ported data stores and primitives must be verified for behavioral equivalence against the reference Python implementation before replacing legacy scripts in production.

* The executor adapter must provide a single unified seam accepting script notation (`{bundle}:{skill}:{script}`) and argument vectors, supporting three configurable routing modes per script: `python`, `java`, and `parallel`.
* The differential test harness must execute identical invocations against both the Python reference script and a running test instance of the `PM-MCP` daemon (never spawning a new JVM per test call) from an identical initial state tree, asserting exact equivalence across:
** Normalized TOON stdout output (normalizing unordered map keys, timestamps, and generated identifiers).
** Process exit code.
** Normalized resulting `.plan/` filesystem state tree.
* In `parallel` shadow mode, the Java implementation must serve the live request while the Python script executes asynchronously against an isolated snapshot copy of the pre-call plan-state tree, logging any state or output divergence without affecting the live workspace.
* Primitives with external side effects (git commits/pushes, remote CI or PR mutations) must be excluded from live `parallel` shadow runs and verified instead against local fixture repositories and sandboxed CI stubs.
* The differential test corpus must combine existing CLI-level `run_script(...)` test suites, replayed invocation logs captured from real plan executions, and targeted regression cases for historical defect classes (lock staleness, path resolution, resume anchors).

See the link:specification/store-schemas.adoc[Store Schemas & Data Model Specification] and link:specification/job-runtime.adoc[Job Runtime & Execution Specification] for implementation details.

[#PM-TEST-3]
=== PM-TEST-3: State-Machine Invariant & Property Verification

Redesigned workflow phases and engine primitives must be verified against formal state-machine invariants and exhaustive outcome handling rules.

* Automated state-machine test suites must verify every state defined in the workflow DSL across the following properties:
** Exact emission of expected hypermedia links (`rel`, `link` identifier, and parameter schemas) and vocabulary skill references.
** Deterministic rejection of invalid, out-of-sequence, or unoffered transitions with closed-enum error outcomes.
** Safe concurrency and idempotency under duplicate or parallel `pm_do` requests against the same plan scope.
** Exhaustiveness of primitive outcome branches (`switch` over sealed outcome types).
* Every Java module (`pm-mcp-core`, `pm-mcp-server`) must maintain dedicated JUnit 5 test suites adhering to `cuioss` testing standards, replacing legacy Python unit tests that imported internal script modules directly.

See the link:specification/workflow-dsl.adoc[Workflow DSL & State Machine Specification] for implementation details.

[#PM-TEST-4]
=== PM-TEST-4: End-to-End Scenario & Compaction Resume Testing

Complete plan lifecycles must be verified through automated end-to-end hypermedia execution scenarios, including context loss and recovery simulations.

* The system must provide an automated scenario harness (`pm-mcp-scenario`) that drives complete plan lifecycles from `pm_start` through `finalize` against fixture repositories by following emitted hypermedia links exclusively.
* End-to-end test suites must exercise fault and recovery scenarios, including:
** Context loss and compaction simulation at every intermediate state, verifying that `pm_state(plan_id)` reconstructs the full working context and valid next links with 100% fidelity.
** Concurrent sub-agent envelope dispatch and completion barriers.
** Build failures, `failed_unparsed` diagnostics, enrolment refusals, and worktree footprint violations (`*.footprint-violation`).
** Daemon restart during active bounded and progress waits, followed by clean state resumption.
* For benchmark plans, final deliverable outcomes (git commits, pull request state, triaged findings, and recorded lessons) must be compared against baseline runs of legacy `plan-marshall`.

See the link:specification/workflow-dsl.adoc[Workflow DSL & State Machine Specification] and link:specification/mcp-tools.adoc[MCP Tools & Resources Specification] for implementation details.

[#PM-TEST-5]
=== PM-TEST-5: Security Boundary & Confinement Adversarial Testing

All trust boundaries, authentication gates, and filesystem confinement rules must be continuously verified via automated adversarial test suites.

* The security test suite must execute adversarial test vectors verifying:
** Rejection of path traversal sequences (`..`), symlink escapes, and out-of-workspace references with `path_traversal_rejected` / HTTP 403 (`PM-SEC-2`).
** Rejection of missing or mismatched bearer cookies (HTTP 401) and foreign `Origin` or `Host` headers (HTTP 403) on `/mcp/*`, `/clients/*`, and LSP endpoints (`PM-SEC-4`).
** Refusal of tampered build wrappers, un-enrolled host tools, or unapproved CLI arguments with outcome `refused` (`PM-EXEC-1`).
** Complete absence of unredacted secrets, bearer cookies, or operator tokens in tool outputs, error responses, subprocess environments, and audit logs (`PM-SEC-5`, `PM-SEC-6`).
** Enforcement of Linux `systemd-run --user` read-only filesystem confinement against build jobs attempting writes outside enrolled project roots (`PM-SEC-5`).

See the link:specification/daemon-endpoint.adoc[Daemon Endpoint Specification] and link:specification/job-runtime.adoc[Job Runtime & Execution Specification] for implementation details.
