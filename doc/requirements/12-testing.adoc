== Quality Assurance & Testing Strategy (PM-TEST)

[#PM-TEST-1]
=== PM-TEST-1: Script Disposition Classification (Ported, Redesigned, Retired)

To preserve the defect-prevention knowledge encoded in the existing `plan-marshall` codebase (~315 script modules in the plan-marshall bundle, ~438 across all bundles, and ~13,500 test functions (~28,000 test cases collected by pytest after parametrisation) as of plan-marshall commit `1d4a1da37`) without carrying over obsolete scaffolding, every script must be classified and tested according to its architectural disposition.

* The system must maintain an authoritative migration inventory that assigns every `plan-marshall` script (evaluated against a pinned repository commit prior to each migration stage) to exactly one of three mutually exclusive categories:
** *Ported*: Data and integration layer primitives whose semantic invariants are preserved while their on-disk store format is redesigned (the legacy format is mapped to the target format in test code only, `PM-TEST-2`)—specifically canonical store read/write invariants for `status.json`, `tasks/`, `findings.jsonl`, `lessons`, `references.json`, and the change ledger, the pure output parsers and classifiers of the git and CI integrations, worktree SHA-256 freshness calculation, and pure classification heuristics (excluding retired CLI staging verbs such as `prepare-add`/`commit-add`, `set-body --file`, `drain-dedup --candidates-file`, `--raw-input`, `--files-out`, and 600s `Bash`-ceiling task command promotion); for `lessons` only the storage invariants are ported, while the `add`-path component-ownership guard is a deliberate change replaced by an audience predicate and verified by state-machine tests instead of differential equivalence.
** *Redesigned*: Phase lifecycle orchestration, routing, planning-lane selection, finalize dispatch, epic orchestration, cross-session lock/queue coordination (`manage_locks`), the execution manifest (composed in-process by `ExecutionManifestResolver`), and the workflow-integration verbs of the git and CI integrations, which are superseded by the declarative hypermedia workflow engine and native OS `FileChannel.lock()` + `ProcessHandle.of(pid)` primitives.
** *Retired*: Executor proxy generation (`execute-script.py`), plugin-cache synchronization, host permission doctors/fixers, and static multi-target corpus generators, which have no counterpart in `PM-MCP` (they stay in legacy `plan-marshall`, `PM-MIG-2`).
* The verification strategy for each component must be strictly bound to its disposition category: ported components must pass differential equivalence and JUnit module tests; redesigned components must pass state-machine and end-to-end scenario tests; retired components are not reimplemented and carry no tests in `PM-MCP`.

See the link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.

[#PM-TEST-2]
=== PM-TEST-2: Differential Equivalence Testing for Ported Primitives

Ported data stores and primitives must be verified for behavioral equivalence against the reference Python implementation before they are released in a stage (`PM-MIG-4`).

* The differential test harness must execute identical invocations against both the Python reference script and a running test instance of the `PM-MCP` daemon (never spawning a new JVM per test call) from an identical initial fixture state, asserting exact equivalence across:
** Normalized TOON stdout output (normalizing unordered map keys, timestamps, and generated identifiers).
** Process exit code.
** Normalized resulting store state, compared after mapping the Python result's legacy `.plan/` tree to the target `.marshall/` format with the legacy -> target mapping, which exists in test code only and is not part of the specification; before a mapping is implemented or changed, the legacy format is re-verified against the latest `plan-marshall` version, and no reverse mapping exists.
* The working-tree hash (`worktree_sha`, `PM-SVC-1`) is exempt from byte equivalence, because it is a PM-MCP-native digest that is never exchanged (`PM-MIG-2`): over the same fixture trees, the tests must compare its equality behaviour on both sides (the same tree yields the same digest; any change of tracked content, an untracked path or its content, or `HEAD` yields a different digest), never the digest bytes.
* Differential tests run only over fixture corpora in test sandboxes, never on live stores: `PM-MCP` never executes a legacy script in production, and no shadow execution or routing seam exists (`PM-MIG-2`).
* Primitives with external side effects (git commits/pushes, remote CI or PR mutations) must be verified against local fixture repositories and sandboxed CI stubs.
* The differential test corpus must combine existing CLI-level `run_script(...)` test suites, replayed invocation logs captured from real plan executions, and targeted regression cases for historical defect classes (lock staleness, path resolution, resume anchors) and for every defect archetype catalogued in the link:ImplementationWatch.adoc[Implementation Watch].

See the link:specification/store-schemas.adoc[Store Schemas Specification] and link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-TEST-3]
=== PM-TEST-3: State-Machine Invariant, Property & McpAssured Protocol Verification

Redesigned workflow phases, engine primitives, and the MCP tool/resource surface must be verified against formal state-machine invariants and exhaustive outcome handling rules using JUnit 5 and `McpAssured`.

* Automated state-machine test suites must verify every state defined in the workflow DSL across the following properties:
** Exact emission of expected hypermedia links (`rel`, `link` identifier, and parameter schemas) and vocabulary skill references.
** Deterministic rejection of invalid, out-of-sequence, or unoffered transitions with closed-enum error outcomes.
** Safe concurrency and idempotency under duplicate or parallel `pm_do` requests against the same plan scope.
** Exhaustiveness of primitive outcome branches (`switch` over sealed outcome types).
** Exhaustiveness and classification of escalation decision outcomes: the static workflow verifier must reject an unregistered decision kind, an escalation whose routed outcomes differ from the kind's declared outcome set, and an approving outcome that does not enter a step performing the approved action.
* Every guard, gate, and detector must have a matched positive and negative control exercised in the configuration that consumes it.
* Every Java module (`pm-mcp-core`, the provider modules, `pm-mcp-server`; `PM-IMPL-1`) must maintain dedicated JUnit 5 test suites adhering to `cuioss` testing standards, replacing legacy Python unit tests that imported internal script modules directly.
* Component and integration tests in `pm-mcp-server` must use `io.quarkiverse.mcp:quarkus-mcp-server-test` (`McpAssured`) — utilizing `@QuarkusTest` for in-process tool/resource verification and `McpStdioTestClient` (`McpAssured.newStdioClient()`) under `maven-failsafe-plugin` (`*IT.java`) to verify the packaged application and GraalVM native executable over actual `stdin`/`stdout` pipes.

See the link:specification/workflow-dsl.adoc[Workflow DSL & Engine Specification] and link:specification/mcp-tools.adoc[MCP Tools & Resources Specification] for implementation details.

[#PM-TEST-4]
=== PM-TEST-4: End-to-End Scenario & Compaction Resume Testing

Complete plan lifecycles must be verified through automated end-to-end hypermedia execution scenarios, including context loss and recovery simulations: engine-level lifecycles in an in-process scenario harness, and relay and `stdio` transport behaviour in integration tests against the packaged application.

* The system must provide an automated scenario harness (`pm-mcp-scenario`): an in-process JUnit harness in the test scope of `pm-mcp-core` (`ScenarioReplayRunner`, link:specification/workflow-dsl.adoc#_deterministic_scenario_replay_harness_pm_mcp_scenario_pm_test_4[Workflow DSL Specification § Deterministic Scenario Replay Harness]) that drives complete plan lifecycles from `pm_start` through `finalize` against hermetic fixture repositories by following emitted hypermedia links exclusively, without a live model.
* The system must verify relay and `stdio` end-to-end behaviour (spawning the `pm-mcp serve` relay over `McpAssured.newStdioClient()`, which starts an isolated runtime under a temporary `PM_MCP_BASE`) in the `*IT` integration tests (`@QuarkusIntegrationTest`) against the packaged application, not in the scenario harness.
* End-to-end test suites (the scenario harness, and the `*IT` integration tests for the relay, connection, and crash cases) must exercise fault and recovery scenarios, including:
** Context loss and compaction simulation at every intermediate state, verifying that `pm_state(plan_id)` reconstructs the full working context and valid next links with 100% fidelity.
** Concurrent sub-agent envelope dispatch and completion barriers across parallel `McpStdioTestClient` sessions sharing the same `.marshall/` directory.
** Build failures, `failed_unparsed` diagnostics, enrolment refusals, and worktree footprint violations (the `footprint_violation` condition).
** `pm-mcp serve` relay termination (`EOF` / `SIGTERM`) during active bounded and progress waits, verifying that the job continues in the runtime and that a newly spawned `McpStdioTestClient` connection resumes the logical session via `pm_state`.
** Runtime crash and restart during an active job and during a pending transition, verifying that orphaned jobs are recorded as `killed` and that stores remain consistent.
* For benchmark plans, final deliverable outcomes (git commits, pull request state, triaged findings, and recorded lessons) must be compared against parallel baseline runs of legacy `plan-marshall` on a separate clone (`PM-MIG-4`). The legacy baseline is a one-time migration reference; any comparison reused release over release must report against an absolute reference and the delta to the previous release, never the delta alone.

See the link:specification/workflow-dsl.adoc[Workflow DSL & Engine Specification] and link:specification/mcp-tools.adoc[MCP Tools & Resources Specification] for implementation details.

[#PM-TEST-5]
=== PM-TEST-5: Security Boundary & Confinement Adversarial Testing

All trust boundaries, STDIO stream hygiene guarantees, and filesystem confinement rules must be continuously verified via automated adversarial test suites.

* The security test suite must execute adversarial test vectors verifying:
** Rejection of path traversal sequences (`..`), symlink escapes, and out-of-workspace references with `path_traversal_rejected` (`PM-SEC-2`).
** Strict `stdout` stream hygiene under `McpStdioTestClient`: verifying that every line emitted on `stdout` across startup, tool execution, child subprocess execution, and shutdown is a valid JSON-RPC 2.0 frame, and that all diagnostic logs are routed to `stderr` or `daemon.log` (`PM-SEC-4`).
** Refusal of tampered build wrappers, un-enrolled host tools, or unapproved CLI arguments with outcome `refused` (`PM-EXEC-1`).
** Complete absence of unredacted secrets or operator tokens in tool outputs, error responses, subprocess environments, `stderr`, and audit logs (`PM-SEC-5`, `PM-SEC-6`).
** Enforcement of Linux Landlock filesystem confinement against build jobs attempting writes outside the permitted paths, including a job writing its project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json`, which must fail, and `confinement: unavailable` reporting on kernels without Landlock (`PM-SEC-5`).
** Refusal with `enrolment_tampered` of every job of a project after an out-of-band change of its enrolment file that does not match the file's operator HMAC, while the jobs of another enrolled project still run (`PM-EXEC-2`).
** Hostile repository configuration against the native git variant: a `url.<base>.insteadOf` or `pushInsteadOf` rewrite and a `remote.<name>.pushurl` pointing to a foreign host are refused with `remote_origin_mismatch` and a security audit record, with no request carrying the credential reaching the foreign host (`PM-CRED-5`); `core.sshCommand`, `core.fsmonitor`, a `.gitattributes` filter driver, and a hook in a native-selected repository start no process and yield `capability_missing` (`PM-SEC-1`, `PM-SEC-5`).
** Absence of every token variable and askpass helper (`GH_TOKEN`, `GITHUB_TOKEN`, `GITLAB_TOKEN`, `GIT_ASKPASS`, `SSH_ASKPASS`) from the environment of CLI-variant `git` and `ci` jobs, and redaction of a derived installation token from every output, with no request using it after its credential was rotated or removed (`PM-CRED-1`, `PM-CRED-5`).

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] and link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-TEST-6]
=== PM-TEST-6: Behavioural Conformance of Model-Facing Content

Model-facing content (vocabulary skills, guidance strings, and hypermedia representations rendered per client profile) must be verified against live models, because `PM-TEST-1`..`PM-TEST-5` verify only the engine, never a model's behaviour. The verification is an out-of-band pre-release gate: it runs against a release candidate outside the regular Maven build, so no build, test, or CI check ever invokes a live model.

* [Harness] The system must provide a behavioural conformance harness, run outside the regular build, that drives a live model through scenarios, each consisting of the rule under test, the situation, the applied pressure, and a mechanically checkable observation; only rules whose violation is mechanically observable in tool calls or the resulting artifact tree are scored. The harness, the observation, and the scoring are PM-MCP tooling: observations are evaluated over the runtime's own records (the audit log, the stores, and the artifact tree), never over the model's report of what it did.
* [Verdict] Every verdict must be `held`, `violated`, or `indeterminate`, computed over a scored margin against a stated tolerance band and a stated population; a run that cannot be scored resolves to `indeterminate`, never to `held`, and a single run is reported as one sample, never as a verdict.
* [Baseline] Every baseline must publish its numbers (never only a pass result), carry at least one negative control expected to score `violated`, and bind each verdict to the rendered skill digests (`PM-SKILL-2`), the binary version, and the client profile digest it was measured against; a changed digest invalidates the verdict. Baselines and verdicts must be kept as versioned, reviewed artifacts of the PM-MCP repository per client and model, never in a runtime store.
* [Scorer] The scorer must stay fixed while the model under test varies and must never be the scored model or its sibling at default configuration; the harness must check scorer independence before each run and refuse the run if it is unmet.
* [Report] Every report must state the token consumption per client and model, and compare against an absolute reference as well as the delta to the previous baseline.
* [Cost] Every scoring layer, including LLM-as-judge, must declare its cost ceiling (runtime, tokens, and money per run) at design time, and the harness sizing must be published before it is used as a routine gate.
* [Tested] A client profile counts as behaviourally tested only when a behavioural signal exists for it; structural tests (rendering, digests, registration, resolution) do not qualify.
* [Evidence] A verdict is evidence for a separately authorized decision: it never directly authorizes an edit of model-facing content, and a `violated` verdict is scoped to the rule, pressure, model, and client it was measured on.
