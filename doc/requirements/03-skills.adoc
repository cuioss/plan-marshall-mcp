== Skill Generation & Delivery (PM-SKILL)

[#PM-SKILL-1]
=== PM-SKILL-1: Static Vocabulary Skills & Separation from Process Logic

The system must strictly decouple static domain guidance and judgment criteria from dynamic workflow process execution, eliminating whole-phase procedural instruction documents.

* The system must restrict skill content strictly to static vocabulary guidance that answers "how to act well", defining state semantics, link relation meanings, domain standards (Java, Python, documentation), and qualitative criteria for free parameter judgment (such as solution outline structure, triage rationale, or commit message formatting).
* The system must prohibit the inclusion of executable command lines, script names, filesystem paths, or argument lists within skills, requiring all actionable instructions to arrive dynamically as hypermedia links.
* The system must organize all generated skills under the uniform namespace prefix `pm/` (e.g. `skill://pm/core/SKILL.md`, `skill://pm/outline/SKILL.md`, `skill://pm/execute/task/SKILL.md`, `skill://pm/domain/<domain>/SKILL.md`).
* The system must enforce progressive disclosure across three tiers: resident lightweight catalogue entries (name and description), on-demand vocabulary skills loaded only when referenced by a state representation's `skill` field, and auxiliary supporting files loaded only when explicitly linked; a worker receives the skills of its task from the server instead (`PM-SKILL-4`).
* The system must completely eliminate monolithic phase-level workflow markdown documents from client conversational context.

See the link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-SKILL-2]
=== PM-SKILL-2: Per-Project Skill Generation & Digest Integrity

The daemon must compile a tailored skill catalogue per project and client profile, publishing content digests to maintain host approval integrity.

* The system must generate the project skill catalogue dynamically within the daemon from four inputs: the client profile of the calling connection, the project's effective configuration (`pm://project/config`: the team files under `.marshall/config/` over the derived and compiled defaults), the release's compiled domain capabilities, and the server version.
* The system must tailor the skill catalogue strictly to the technologies active in the project (e.g. omitting Java skills for projects without Java modules).
* The system must compute and publish deterministic SHA-256 digests for all generated skills, ensuring content remains invariant for identical configuration and binary versions so that client-side security approvals remain cached and valid.
* The system must generate the skills of the worker protocol: the core conduct skill (follow the offered links, act only through them, deliver only through submit links), the task-protocol skill (what a wait, an offer, "wait again", and "end" mean; acknowledging, executing, submitting, consulting), and one role skill per role, the role's contract (`PM-WORK-1`).
* The system must generate minimal operational announcement skills for external tools (e.g. build skills) that describe available capability verbs and outcome meanings without revealing internal execution commands.

See the link:specification/client-profiles.adoc[Client Profiles Specification] and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-SKILL-3]
=== PM-SKILL-3: Standard MCP Tool & Resource Skill Delivery

Skills must be published in the structures of the MCP Skills Extension (`io.modelcontextprotocol/skills`) and mirrored by standard MCP tools and resource templates that every target coding agent supports (`claude`, `opencode`, `antigravity`, `codex`).

* The system must implement skill delivery through standard MCP tools available to all MCP hosts: `pm_skills(plan_id | epic_id)` (list catalogue names, descriptions, and URIs), `pm_skill(plan_id | epic_id, uri, section?)` (fetch `SKILL.md` content, its section index, and URI, or with `section` only the section of that anchor, the digest carried only in the result's `_meta`), and `pm_skill_file(plan_id | epic_id, uri, section?)` (fetch auxiliary supporting files, with the same `section` semantics), each addressed with exactly one of `plan_id` (a plan id or `NO_PLAN` for the workspace scope) or `epic_id`, which selects the rendering inputs (`PM-TOOL-1`); with `NO_PLAN` the client profile comes from the calling connection and the domains from the project configuration.
* The system must also expose the skill catalogue via standard MCP resources (`resources/templates/list` and `resources/read` for the single URI template `skill://pm/{+path}/SKILL.md`, RFC 6570 reserved expansion, plus `skill://pm/{+path}/{file}` for supporting files) without relying on unadopted custom protocol extensions; a `resources/read` of a `skill://` URI renders for the project's workspace scope with the client profile detected for that request.
* The system must publish every skill as a `SKILL.md` with its supporting files, each an MCP resource under `skill://pm/...`, with a manifest per skill (its `SKILL.md` URI, its frontmatter, and every file with its SHA-256 digest and size), declare the Skills Extension, and answer `skills/list`, `skills/get`, and `resources/read`; the tools above serve the same manifests, URIs, and digests as a mirror of the extension, never as a second format, and no skill is `dynamic`, comes from a second origin, or instructs code execution on the host.
* The system must reference all skills uniformly via standard canonical URI notation (`skill://pm/...`).

See the link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-SKILL-4]
=== PM-SKILL-4: Skill Delivery to Workers & State through Representations

Every worker must have the skills its task requires in its context when it works on the task, delivered deterministically by the server; per-plan and per-state information must be delivered exclusively through tool result representations, never through dynamic or mutating skills.

* The system must deliver all dynamic state, phase progress, task metrics, and available transitions exclusively through the tool return values of `pm_state` and `pm_do` formatted as TOON text representations.
* The system must compute, for every task, the required skill set (core conduct, task protocol, the role skill, the skills of the task's state, and the project's domain skills), each identified by URI and digest, and must deliver it, never wait for a model to fetch it: a worker's launch prompt carries the shim paragraph, the core conduct, the task-protocol skill, and the role skill in-band; a fresh worker's prompt additionally carries the skills of its one task, in-band up to a size bound (above it, a section index with the `skill://` URIs and section anchors to fetch through `pm_skill`), followed by the task's contract envelope (its task and entity, the first call `pm_state` on its entity, the links with their named schemas, and the rule that deliverables reach the server only through `submit` links); an offer to a warm worker or a session carries in-band the required skills its generation has not received yet and names the others by URI and digest. Project-level instructions and skills load natively from the worker's working directory, and PM-MCP serves no project-local skill (link:later-improvements.adoc#_l_4_project_local_vocabulary_skills[Later Improvements, L-4]).
* The system must keep a delivery record per worker generation (skill, digest, instant) and must deliver a skill again to a new generation, after a compaction or clear its host reports, and whenever the skill's digest changed; it must never offer a task whose required skills it cannot deliver within the offer's size bound, and must check what it receives against the link and schema the contract names, whatever the model made of the skill.
* The client bundle of every host must install a shim skill in the host's own skill format and directory (`PM-DIST-1`), and every server-composed launch prompt must carry the same paragraph: skills of `plan-marshall` arrive in-band or are named by a `skill://pm/` URI; a named skill is binding and is read through `pm_skill`; a skill is never reconstructed from memory, and a skill of the same name from elsewhere does not replace it. The shim never chooses skills. When a connection declares the client capability of the Skills Extension, the server must switch that connection to host activation (offers name skills by URI only), and the client profile records the verified support, so that the next bundle of that host no longer installs the shim.
* The system must prohibit the delivery of per-plan, per-task, or per-state content via skills, rejecting `resources: "dynamic"` skill declarations to avoid host caching anomalies and unapproved permission prompts.
* The system must ensure that conversational context is refreshed per state transition with only the active state's minimal relevant facts and links; a fact without operational value for the model (such as the implementation variant that served an operation, a derivation source, or an internal version or digest) is logged and audited, never rendered (`PM-TOOL-5`, link:specification/hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Model-Facing Minimality]).

See the link:specification/mcp-tools.adoc[MCP Tools Specification] and link:specification/hypermedia-format.adoc[Hypermedia Format Specification] for implementation details.
