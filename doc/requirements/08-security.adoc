== Security & Trust Model (PM-SEC)

[#PM-SEC-1]
=== PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment

The security architecture of `PM-MCP` enforces a strict dual-boundary security model separating the host runtime from the MCP server, and contains untrusted content encountered during execution.

* The system must enforce a two-boundary security model comprising:
** An internal PM-MCP tool boundary where all state transitions are closed enumerations, parameters are schema-validated, workspace access is server-confined, job execution is verified against operator enrolment, and operator capabilities are omitted.
** An external host tool boundary governing the AI model's native file and shell access outside PM-MCP's direct control.
* The system must give workers of `read_only` roles (among the default roles: Q-Gate, triage, the reviews, lessons author, architecture enrichment, epic decomposition and re-grounding, lessons review) no file-writing tools and no write-capable PM-MCP service tool (no `pm_build`, and `pm_lsp` without `rename`), let every worker reach PM-MCP only through its job-bound connection, limited to the links of its leased task entities and read-only resource reads within its project (`PM-WF-5`), and give workers of `zero_tool` roles (among the default roles: the injection screener and the qualification judge `judge`) zero tools and no PM-MCP connection, so that untrusted or speculative reasoning paths cannot alter plan state beyond their entity's validated submissions.
* The system must tag all external content—including repository code, build definitions, pull request comments, review-bot outputs, and responses from upstream MCP servers—with provenance metadata (for proxied upstream content, the `_meta` key `de.planmarshall-mcp/source`, `PM-SVC-3`) and treat it as untrusted.
* The system must treat repository configuration (`.git/config` and its includes, `.gitattributes`, `.gitmodules`, hook directories, and the user's global git configuration as read by an in-process operation) as untrusted input: the native git variant reads only an allowlist of content-shaping keys and ignores every other key (among them `credential.*`, `core.sshCommand`, `core.fsmonitor`, `http.*` proxy settings, and includes outside the repository), never starts a process named by repository content (hooks, filter drivers, signing programs, `core.fsmonitor`) but refuses such an operation with `capability_missing`, and sends the agent credential only after the origin check of the effective remote URL (`PM-CRED-5`).
* The system must prohibit state machine transitions derived solely from untrusted external content; external review-bot comments or CI statuses may create findings or trigger verification checks, but must never directly mark a quality gate green or bypass a merge barrier.
* The system must pass every externally authored free text (issue and pull-request titles and bodies, review comments and bot findings, analysis-provider messages, and upstream MCP results entering a store) through two guards before it reaches a model as content, and CI log and build excerpts (the output of its own jobs) through the first guard only:
** Level 1, the deterministic validator of the server and the containment boundary: a Unicode stage run to a fixpoint (tag characters, variation selectors, format, control, private-use and unassigned code points, lone surrogates, and terminal escape sequences removed; content normalized to NFC and a normalized copy used for detection), a Markdown syntax-tree stage (`org.commonmark:commonmark`: images removed, links outside the operator's optional domain allowlist neutralized, raw HTML, HTML comments, and collapsed sections removed, the known disclosure footers of review bots removed, exfiltration-shaped URLs flagged, extracted URLs validated), length bounds, a closed schema for every structured field (undeclared keys rejected), and a rule table whose matches are risk signals and findings, never a gate on their own; every change is reported, never silently dropped, and the text is delivered to a model only inside spotlighting delimiters that mark it untrusted.
** Level 2, a fresh zero-tool screener worker (`PM-WF-5`) that receives the level-1-cleaned texts of one source or gather firing as one server-built batch (split above a size bound into parts, each screened by its own screener worker; texts already screened in the scope are taken from a cache keyed by their SHA-256) and returns a closed verdict per text (`clean` or `suspicious` with the flagged spans), validated by the server; the screener can only restrict, never grant: a missing, extra, or unparseable verdict counts as `suspicious`, and screened text stays marked untrusted.
** A `suspicious` text in a bootstrap source is shown with its flagged spans in a link state whose `accept` (audited; the text stays marked untrusted) or implicit `step_out` (back to the choice) the entry session follows after relaying the user's choice; inside a plan the text is withheld and only its structured fields (author, file, line, kind) are delivered, the finding stays pending until its unit ends through its budget and fallback (the hand-back report lists the withheld items), and only a `met` waiver of that finding lets the plan proceed.
* The system must record the repository state of the main checkout and active worktrees at task start, and verify realized changes at task submit and inside the commit operation itself, before every commit of every caller (plan, epic, and workspace scope), whichever link or state leads to it; any change detected outside the assigned worktree, any change inside it to a wrapper's pinned build files (`PM-EXEC-1`) or to a protected path, and any main-checkout change since the plan's entry baseline must raise a footprint-violation condition on the scope's current state (`PM-WF-3`) with an explanatory finding, make no commit, and run only its bounded self-remedy `fix` (a task of the plan's writer role), after whose budget the plan takes its phase's fallback; this guard is never waivable. A change inside the worktree beyond the plan's declared footprint is no violation: it is committed and recorded as an unplanned change (`PM-WF-11`).
* The system must document as an accepted residual risk that the host-side actions of an interactive session and host-side reads of `<PM_MCP_BASE>/projects/**` are not observable; an interactive session never takes a writer task (`PM-WORK-5`), so all plan work that changes files runs in confined workers.

[#PM-SEC-2]
=== PM-SEC-2: Workspace Confinement & Path Traversal Prevention

To prevent unauthorized file modifications or cross-project data leakage, all PM-MCP file and repository operations must be strictly confined to the enrolled repository root and its active worktrees.

* The system must resolve the project at session entry (`pm-mcp enter`) and for every `PM-MCP-Workspace` header by one rule (git top-level and common git directory mapped to an enrolled project root; a worktree only under `.marshall/local/worktrees/`) and record the resolved `project_id` and entry origin, never a path, in the scope's session log.
* The system must derive workspace confinement exclusively from server-verified data: the `PM-MCP-Workspace` header resolved against the enrolment for workspace-addressed requests and the enrolled project root of the scope's per-project machine store for scope-addressed requests (`PM-ARCH-4`); client-declared MCP roots are advisory and never widen or narrow the confinement.
* The system must canonicalize all paths (resolving all symbolic links) for every filesystem, git, and build operation, asserting that the target path resides within the enrolled workspace root or a live linked git worktree whose git common directory resolves to that root.
* The system must reject any path traversal attempt (including directory traversal sequences `..`, absolute paths outside the workspace, or symlinks pointing outside the root) with an explicit `path_traversal_rejected` error outcome.
* The system must forbid AI models from specifying raw filesystem paths for state manipulation; all target scopes (`plan_id`, `epic_id`) must be resolved server-side from persisted state.
* The system must admit cross-project access (such as multi-repo epic landing or dependency verification) only under an operator grant: the operator issues it on the operator's own initiative (`pm-operator grant-access <plan_id> <project_id> read|read-write --reason <text>`, or, for the read-only organisation and foreign-repository provider reads of `PM-EXEC-5`, `pm-operator grant-access <plan_id> --org <owner> read` or `--repo <owner>/<name> read`), limited to enrolled projects, or to reads of the named organisation, group, or repository at the plan's provider, and to the plan's lifetime (a grant is never revoked: it holds until the plan ends, and aborting the plan is the only way to stop it), and the runtime records it append-only in the plan's store and in the audit log; the model never requests one through a link, and an access without a grant raises the `precondition_unmet` condition naming the operator command (`PM-WF-3`), whose bounded retry ends in the phase's fallback.

[#PM-SEC-3]
=== PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)

Privileged operations that alter machine configuration, security posture, or project boundaries must be strictly isolated from the AI model's capability surface.

* The system must exclude all operator-only capabilities—including project enrolment and harness enrolment, setting and revoking waivers, aborting a plan or an epic, resolving an integrity breach, deleting plan directories, and granting cross-project access—from the MCP tool surface and link emissions.
* The system must reject any attempt to execute operator-only actions via `pm_do` regardless of supplied arguments, and must limit a worker's connection to its role's tool set, the links of its leased task entities, and read-only resource reads within its own project (`PM-WF-5`).
* The system must provide exactly two isolated channels for operator overrides (waivers, `abort`, integrity resolutions, plan deletion, cross-project access grants, operator configuration, `PM-WF-12`) and must accept MCP elicitation only for the operator-configuration choices the server raises itself (such as the integration variant) and for the setup and bootstrap choices of `PM-WF-12`; an operator-configuration choice the server raises itself is taken by elicitation or by an operator channel, never by a model or a content answer; none of them routes through the AI model, an override is never taken as a content answer, and a content answer given through elicitation or a paired device is never an override; the channel of every privileged action is recorded in the audit log:
** Operator CLI (the binary `pm-operator`, whose verbs stand at its top level without an `operator` sub-level, `pm-operator <verb>` and `pm-operator web <verb>`): Operator verbs that `pm-operator` accepts only when it is attached to an interactive terminal (`System.console().isTerminal()`) and none of the host agent environment markers is present, that ask for interactive confirmation, and that it then sends to the runtime's local API, which executes them; its inspection, lifecycle, and installer verbs (`status`, `drain`, `runtime`, `client`) keep their own rules (`PM-ARCH-7`, `PM-DIST-2`). The host enforcement rule installed with the client bundles denies the whole binary `pm-operator` to the model (`Bash(pm-operator:*)`), while `pm-mcp` (`serve`, `enter`) stays allowed; the rule is defence in depth. No passphrase, operator session, or operator credential exists (link:later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).
** Paired web device: A browser paired through an operator verb, which has the operator's rights except the CLI-only actions (`PM-SEC-7`).
* The system must never wait for an operator decision: no operator verb resolves a pending decision, and the operator acts on the operator's own initiative through `pm-operator waive` / `unwaive` / `waivers`, `abort`, `accept-edit`, `delete-plan`, `grant-access`, `enrol-harness`, `credentials`, `config`, and `roles`, each through the same local API endpoints the web app uses. Where a condition needs the operator (an integrity breach, a missing credential or operator setting), its representation names the matching operator command as text the model relays, never as a link.
* The system must document as an accepted residual risk that the operator checks of `pm-operator` guard only against accidental and naive invocation: a model-driven shell that deliberately defeats them (a pseudo-terminal, a cleared environment, indirect invocation) can run operator verbs, and, because the runtime cannot verify these checks, any process of the same OS user that holds the runtime token can call the operator endpoints of the local API directly; a user proof the model cannot produce is deferred (link:later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification] (operator endpoints of the local API), link:specification/mcp-tools.adoc[MCP Tools & Resources Specification], link:specification/workflow-dsl.adoc[Workflow DSL Specification], link:specification/store-schemas.adoc[Store Schemas Specification] (waiver record), link:specification/timeouts/02-runtime-leases-operator-web.adoc#operator-waivers-questions[Timeouts & Budgets Specification] (waiver and question waits), and link:specification/model-work.adoc[Model Work Specification] for implementation details.

[#PM-SEC-4]
=== PM-SEC-4: Local Transport Isolation, Operator-Gated Network Exposure & Stream Hygiene

By connecting hosts over `stdio` and relaying to the runtime over a user-private Unix domain socket, `PM-MCP` keeps the MCP endpoint and the runtime token off every network listener, which removes network-borne attack vectors (DNS rebinding, cross-origin browser requests, unauthorized local TCP port access, and SSH port-forwarding leaks) from the host path, and enforces strict OS-level process and stream isolation; the only network exposure is the web access the operator enables (`PM-SEC-7`).

* The runtime must open no TCP or UDP listener in any production execution mode unless the operator enabled web access (`PM-SEC-7`); without it its only listener must be a Unix domain socket with mode `0600` inside a `0700` directory owned by the active OS user, serving the MCP endpoint and the local API, and the socket is never served to a browser. The socket lies only at its default path under `<PM_MCP_BASE>/run/`: when that path exceeds the platform's socket path limit (`sun_path`), the runtime must refuse to start with a diagnostic that names the path and tells the operator to choose a shorter `PM_MCP_BASE`, and never falls back to a path under the system temporary directory. Should a platform or a later Quarkus, Vert.x, or platform version rule out the domain-socket listener, the only permitted substitute is a listener bound to `127.0.0.1` that requires the runtime token and rejects every request with a foreign `Host` or any `Origin` header.
* The system must authenticate every local request with the runtime token: a fresh 256-bit secret that the runtime writes atomically at every start, before binding, to `<PM_MCP_BASE>/run/runtime.token` (mode `0600`, directory `0700`), that every client reads only after verifying owner, mode, and the absence of symlinks, that is never logged, passed as an argument, or exported to a job, and that no job can read on Linux (outside the Landlock read set); the peer UID may additionally be checked where the listener exposes it, but is never required.
* The system must authenticate a worker's connection only with its own job token: a fresh 256-bit secret minted at the worker's spawn, stored only as its SHA-256 in the job record, valid only while the job runs and its generation is not fenced, passed with the worker's generation in the job's environment to the job relay `pm-mcp serve --job`, which sends both on every request (the token as `PM-MCP-Job-Token` in place of the runtime token), and accepted on the MCP endpoint only; per request the runtime binds tool calls to the task entities leased to that generation and resource reads (`resources/read`, `resources/list`; read-only) to the worker's own project and `skill://pm/...`, and refuses another scope or entity (`job_scope_mismatch`), a fenced generation (`generation_fenced`), and any call after the job ended (`job_ended`); a revoked job token is still resolved by its hash, so such calls get these reasons, and only an unknown or malformed token is rejected as unauthenticated.
* No tool schema may carry an identity, role, or generation argument: the relay carries them in its connection metadata, which the runtime turns into the request's security identity, and never forwards such an argument a host sends, so that a model never sees, passes, or invents them; it must carry a session's generation the same way, ask the runtime for a new generation at each new host session it observes (`PM-WORK-5`), and pass on the clear and compaction markers its host provides.
* The relay must keep the host's view of a lost runtime consistent: it answers every pending request with an error at once when its stream to the runtime is lost (a host never waits out its own limit on a dead server), ignores a host's cancellation of a request already answered, never answers a notification, sends the `Mcp-Method` and `Mcp-Name` headers on every forwarded request, and tolerates being restarted by its host mid-session (the identity comes again from the environment, and the runtime binds the new relay to the same generation).
* The runtime may open one additional HTTP listener, the web listener, only while the operator has enabled web access (off by default, enabled and disabled only by an operator verb): on loopback (`127.0.0.1`) over plain HTTP by default, or on all interfaces only over TLS. On that listener the runtime must route only the static web app and `/api/v1/`: the MCP endpoint `/mcp` and every other path are never reachable there, and the runtime token is never accepted there; a request there authenticates only with a device secret (`PM-SEC-7`).
* The system must enforce strict `stdout` stream hygiene in the `pm-mcp serve` relay: `stdout` is reserved exclusively for newline-delimited JSON-RPC 2.0 MCP messages, while all diagnostics are routed strictly to `stderr`; the runtime writes its diagnostics to `<PM_MCP_BASE>/logs/daemon.log`.
* The system must redirect `stdout` and `stderr` of all spawned child subprocesses (`build`, `git`, `ci`, `project_script`, `llm`, and warm LSP servers) to dedicated capture pipes or log files, never allowing a child process to inherit a descriptor connected to a host.
* The system must create every file under `<PM_MCP_BASE>` with mode `0600` and every directory with mode `0700`, and must refuse startup unless `<PM_MCP_BASE>`, `enrolments/`, and `run/` are owned by the active OS user with mode `0700` and the files under `state/` with mode `0600`; the `0700` base directory is what protects every other file under it. Enrolment and credential files are checked on every use: an enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` with a foreign owner or a mode broader than `0600` blocks only its project (`enrolment_insecure`), never the runtime start.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and link:specification/model-work.adoc[Model Work Specification] for implementation details.

[#PM-SEC-5]
=== PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement

Subprocesses spawned by PM-MCP for builds, CLI-variant git and CI provider operations, enrolled project scripts, and model jobs must be executed with sanitized environments and OS-level confinement.

* The system must run native-variant git and provider operations in process without starting any subprocess (`PM-EXEC-5`); `git` and `ci` jobs exist only for the CLI variant, and repository hooks, filter drivers, and signing programs run only inside such a CLI-variant `git` job, started by `git` itself under that job's environment and confinement.
* The system must spawn all subprocesses directly via operating system process creation APIs without invoking intermediate system shells (`/bin/sh` or `/bin/bash`), and place each job in its own distinct process group; the only shell that runs is the interpreter of a committed, enrolled `#!/bin/sh` wrapper (`mvnw`, `gradlew`), which receives the validated argument vector as positional arguments.
* The system must build every subprocess environment from scratch against a strict, specified allowlist (per variable: permitted job types and provenance, enrolment snapshot or runtime-computed), never inheriting the runtime's own environment; the runtime token, device secrets, credential secrets, token variables (`GH_TOKEN`, `GITHUB_TOKEN`, `GITLAB_TOKEN`, every `*_TOKEN`), askpass helpers (`GIT_ASKPASS`, `SSH_ASKPASS`), and flag-injecting variables (`JAVA_TOOL_OPTIONS`, `MAVEN_OPTS`, `GRADLE_OPTS`) must never be exported to child environments; a CLI-variant `git` or `ci` job receives only the listed configuration-discovery variables (`HOME`, the SSH agent socket for an SSH remote, the provider CLI configuration directories) and non-interactive guards, and authenticates with the operator's ambient credentials by design (`PM-CRED-1`); a model job (`llm`) receives no authentication variable for its harness, which authenticates with its own login cached under its home (PM-MCP never captures, stores, or exports a harness's authentication, `PM-EXEC-1`; the one exception is the per-worker data directory below, into which the runtime copies the harness's own login file for the job's lifetime without reading it), and `PM_MCP_JOB_TOKEN` and `PM_MCP_JOB_ID` as the only PM-MCP values, never a PM-MCP credential; no job receives `DBUS_SESSION_BUS_ADDRESS` or `XDG_RUNTIME_DIR`, so no job finds the user's session bus and with it the Secret Service (a CLI-variant job therefore cannot use a login kept only there), and a build job receives the container-engine variables (`DOCKER_HOST`, `DOCKER_CONFIG`, `TESTCONTAINERS_*`) only when its project's enrolment opts into the container engine (`PM-EXEC-4`).
* The system must pass free-text parameters (such as commit messages, PR descriptions, and outline text) of a subprocess exclusively in memory via standard input (`stdin`) (`PM-EXEC-5`), never via temporary files and never interpolated into command-line arguments; a CLI-variant operation for which the host tool offers no `stdin` form is `unsupported_by_variant`.
* The system must confine every subprocess on Linux before execution, in the job launcher `pm-exec`:
** `PR_SET_NO_NEW_PRIVS`, so that no job or descendant can gain privileges.
** A Landlock filesystem ruleset (ABI >= 2; a kernel offering only ABI 1 is recorded as `confinement: partial(abi=1)`, never as confined) granting write access only to the job's own project root (including its worktrees and `.marshall/local/temp/`), declared build toolchain caches, the system temporary directory (`/tmp`), device nodes (`/dev`), for a `ci` job of the CLI variant its CLI's configuration directory (`GH_CONFIG_DIR` / `GLAB_CONFIG_DIR`), for a `build` or `project_script` job (and a CLI-variant `git` job that runs repository hooks) the project's daemon store `<PM_MCP_BASE>/projects/<project_id>/daemons/` (read and write, holding only the build daemons' registries, nothing the runtime reads), and for a model job the writable harness paths its client profile declares (a model job also keeps network access), and read-only access to the whole filesystem except all of `<PM_MCP_BASE>`, which is neither readable nor writable apart from the daemon store and the job-private directory below (`<PM_MCP_HOME>` with the binaries stays readable), the session bus socket (`$XDG_RUNTIME_DIR/bus`), and, without the project's container-engine opt-in, the container engine's socket path (Landlock governs a `connect(2)` to a pathname socket only from ABI 9, through `LANDLOCK_ACCESS_FS_RESOLVE_UNIX`, which `pm-exec` must handle wherever the kernel offers it, recording the applied ABI in the job record; below ABI 9 the withheld variables are the only guard); the directories on the path from `/` to `<PM_MCP_BASE>` stay traversable but cannot be listed by a job, because the read set grants their entries one by one; the writable set never contains `<PM_MCP_BASE>` apart from the daemon store, another enrolled project root, or `~/.plan-marshall/`, which adversarial tests prove with a job whose write to `<PM_MCP_BASE>/enrolments/<project_id>.json` fails, whose write to another enrolled project root fails, and whose reads of `<PM_MCP_BASE>/run/runtime.token` and of a credential file under `<PM_MCP_BASE>/credentials/` fail, each with a positive control that the permitted counterpart succeeds (`PM-TEST-5`).
** For a model job only, read-only access to its own job-private directory `<PM_MCP_BASE>/run/jobs/<job_id>/` (mode `0700`, files `0600`; it holds the prompt file, the rendered result schema, the per-call MCP configuration, and the empty working directory of the `zero_tool` workers, the screener and the judge, and of the qualification items that carry corpus context), an exception to the exclusion of `<PM_MCP_BASE>`; no job can write there, so nothing the runtime trusts lies in a job-writable place. The only writable part is the worker's data directory `<PM_MCP_BASE>/run/jobs/<job_id>/data/` (mode `0700`), created only for a harness whose client profile declares a per-worker data home: the runtime points the declared variable (for OpenCode `XDG_DATA_HOME`) at it, copies the harness's own login file into it with mode `0600` at spawn, never reads anything from it, and removes it with the job-private directory when the job settles, and in the project's recovery where a runtime died while the worker ran, so no two workers share the harness's local state and no login copy outlives its job.
** Writable harness paths that contain only what a headless harness must write to run (its login or credential file, caches, and session directory) and never a settings, command, or skill file that the client bundle manages (`PM-DIST-2`); a model job therefore cannot change the host configuration the installer owns, while the operator's own session and the bundle installer in `pm-mcpd` are unaffected, because the rule restricts only the write set of model jobs.
* The system must compute the writable set from the job's project enrolment at every job start, so that enrolment changes take effect for the next job; warm build daemons (Gradle daemon, `mvnd`) inherit the confinement of the job that started them, and the runtime points every build job at its project's daemon store, keyed by the digest of the job's write set, so that a job only ever reaches a daemon started under its own ruleset (`PM-EXEC-4`).
* The system must protect every enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` and the harness enrolment `<PM_MCP_BASE>/harnesses.json`, each with its own HMAC-SHA-256 over its canonical content, written by the runtime with every write of the file (operator verbs only, and for `harnesses.json` also an accepted harness self-update, `PM-EXEC-1`) with a key held in the OS keyring under the PM-MCP namespace (operator lane) or, on hosts without a keyring, in `<PM_MCP_BASE>/state/` (mode `0600`); the runtime must verify a project's enrolment file before first serving the project after a start and before every verify-not-resolve check (`PM-EXEC-2`), refuse with `enrolment_tampered` and an audit record on mismatch for that project only, and accept a re-baseline only through an operator verb; it must verify `harnesses.json` before every model-job launch, where a mismatch refuses only the model job and is re-baselined by `pm-operator enrol-harness` (`PM-EXEC-1`).
* The system must document as accepted residual risks that the enrolment HMAC does not stop a deliberate forgery on hosts without a keyring, where the key file is readable by every process of the same user, nor a re-baseline of a tampered file by a model-driven shell that defeats the operator checks or by a same-user process calling the operator endpoint directly (`PM-SEC-3`).
* The system must document as accepted residual platform risks the absence of equivalent unprivileged sandboxing on macOS, and on Linux kernels without Landlock, where jobs run with `PR_SET_NO_NEW_PRIVS` only and the job record states `confinement: unavailable`.
* The system must document as an accepted residual risk that the Linux Secret Service grants every unconfined process of the same user (the operator's host shell, a model-driven shell of an interactive session) read access to an unlocked collection and with it to the Token Lane secrets; jobs are kept off the session bus (above), and the macOS Keychain's per-application access control is the stronger platform guard (`PM-CRED-2`).
* The system must document as an accepted residual risk that on a Linux kernel below Landlock ABI 9 a job that names the session bus socket or, without the container-engine opt-in, the container engine's socket by its path can connect to it, because only the withheld environment variables keep the job away (verified on Landlock ABI 8: a client that looks the bus up does not find it, a connect by path succeeds); from ABI 9 the ruleset refuses the connection without any change of configuration.
* The system must show the operator, when a project opts into the container engine (`PM-EXEC-4`), that its jobs hold the authority of the Docker group, whose daemon runs outside the job's confinement and can read and write every host path, `<PM_MCP_BASE>` included; the opt-in is recorded in the audit log and every job of the project states `confinement: partial(container_engine)`.

[#PM-SEC-6]
=== PM-SEC-6: Security Audit Trail & Tamper-Evident Logging

The system must maintain an append-only, tamper-evident audit record of all security-relevant operations, authentication events, and identity assertions.

* The system must record every tool invocation, state machine transition, job submission, credential access, and operator action to an append-only JSONL audit log (`<PM_MCP_BASE>/logs/audit.jsonl`).
* The system must chain the audit records: every record must carry `prev_hash`, the SHA-256 of the previous record's canonical line (a defined genesis value for the first record); the runtime must anchor the chain head (record count and head hash) in an HMAC-protected sidecar under the enrolment integrity key, rotate the log only through checkpoint records listed in a hash-chained index, verify incrementally from the last checkpoint at start (full verification on operator demand), and report a broken chain (including a deleted, reset, or truncated log) to the operator and record it in the audit log, never silently repaired; the anchoring is tamper-evident, not tamper-proof, against a process holding the integrity key.
* The system must record three distinct identity layers in the audit record of every `pm-mcp enter`, a worker's job id, role, and generation in every record of a worker's operation, and only the OS principal for machine-level operations:
** The declared client identity (`--client` parameter from entry point).
** The detected environment signature (host detection signals per the link:specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table], or MCP `clientInfo`).
** The authenticated operating system user principal running the process.
* The system must explicitly flag any discrepancy between declared client identity and detected environment signature at entry (`identity_mismatch=true`) in the audit log and report it to the operator, never in a model-facing representation (`PM-CLIENT-3`).
* The system must never rewrite a recorded measurement or audit fact: a correction is appended as its own record that names the record it corrects, and every measurement record carries the `head_sha` and round it was taken at. Decision records (`PM-WF-19`) follow the same rule but are scope records, not part of this audit trail: an operator action a decision record cites (a waiver) stays recorded here.
* The system must redact all sensitive credentials, passwords, and tokens, including the runtime token, device secrets, and pairing codes, before writing entries to diagnostic logs or the audit log.
* The system must sanitize error responses returned to AI models, suppressing internal exception traces, stack traces, and local system paths, returning only closed-enum error codes and, for errors the operator must look up (an unhandled server exception, an unreadable document), the unique audit record identifier for operator diagnostics.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] and link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.

[#PM-SEC-7]
=== PM-SEC-7: Optional Web Access, Device Pairing & Browser Channel Hardening

A paired browser may observe and operate the runtime through optional web access that the runtime itself serves once the operator has enabled it, without exposing the MCP endpoint or the runtime token on the network and without handing the browser any credential the operator cannot revoke at once.

* The system must deliver browser access from the runtime itself (`pm-mcpd`), never through a separate web server process: the runtime serves the static web app and the local API on one additional HTTP listener, the web listener, which is absent unless the operator enabled web access (`pm-operator web enable [--lan]`, or a first `pm-operator web pair` or `pm-operator web open`, which enables the loopback listener) and is closed by `pm-operator web disable`; without it the runtime opens no TCP listener (`PM-SEC-4`).
* The system must persist the setting in the closed object `web` of `<PM_MCP_BASE>/machine-config.json` (`enabled`, a boolean, default `false`; `lan`, a boolean, default `false`; `port`, an integer, default `7420`): `enabled` and `lan` are written only through these operator verbs, which take no port option, and `port` is changed with `pm-operator config`; the runtime must open the listener at every start while `enabled` is `true`, and paired devices survive `web disable`.
* The system must never choose another port than `web.port`: an occupied port at `web enable` fails the verb and leaves `web` unchanged, and an occupied port at a runtime start leaves the web listener closed, reported by `pm-operator status`, while the runtime still starts.
* The system must let `web enable` and `web disable` take effect immediately: the runtime opens or closes the web listener while running, without touching plans or jobs.
* The web listener must exist only while the runtime runs: with the runtime stopped a browser gets a refused connection, and no other process answers in the runtime's place.
* The system must serve the web listener on loopback (`127.0.0.1`) over plain HTTP by default and, with `--lan`, on all interfaces only over TLS with a certificate the runtime generates itself (kept under `<PM_MCP_BASE>/web/tls/`) and whose SHA-256 fingerprint the operator CLI and the pairing page show.
* The system must validate the `Host` header of every request before routing, grant no CORS, and set on every web response the strict Content Security Policy (including `frame-ancestors 'none'` and `require-trusted-types-for 'script'`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer`.
* The system must route on the web listener only the static web app and the local API under `/api/v1/`, including its event streams: the MCP endpoint `/mcp` and every other path must never be reachable there, and the runtime token must never be accepted there (`PM-SEC-4`).
* The system must pair a browser only through a one-time code issued by an operator CLI verb (8 characters, single use, one open pairing, kept only as a hash, with the lifetime and failed-attempt limit of the link:specification/timeouts/02-runtime-leases-operator-web.adoc#web-access[Timeouts & Budgets Specification, Web Access]) exchanged for a per-device secret of 256 bits that the runtime stores only as a SHA-256 hash and never logs.
* The system must authenticate a browser only by its device secret, sent as `Authorization: Bearer pmw_…`, which the runtime checks against the web device store on every request and on every event-stream connect, without a cache, so that a revocation ends the device's streams and rejects its next request.
* The system must let the operator list and revoke paired devices individually or all at once, expire a device after the link:specification/timeouts/02-runtime-leases-operator-web.adoc#device-idle-expiry[device idle expiry] without use, and record every pairing, failed pairing attempt, and revocation in the audit log (`PM-SEC-6`).
* The system must make the web app the dependable view of every plan, epic, worker, and task (`pm-operator status` being the terminal view) and the dependable channel of content questions, which it notifies and answers (`PM-WF-12`).
* The system must treat every paired device as an operator channel with the operator's rights, except the CLI-only actions (issuing pairing codes, enabling or disabling web access, entering credential secrets), and audit every action with its channel and device; roles and step-up are deferred (link:later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]), as are OAuth, token rotation, and sender-constrained credentials (link:later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).
* The system must document as an accepted consequence that browser-facing HTTP, TLS, and static serving run in the process that holds the credential store and the workflow engine; the mitigations are that web access is off by default, that the listener is loopback-only by default, that every request passes the `Host` validation and needs a device secret, and that the listener routes nothing but the web app and `/api/v1/`.

See the link:specification/cli-and-security/03-web-server.adoc#web-server[CLI, Coordination & Security Specification, Web Access & Pairing], link:specification/runtime-model/01-processes-and-transport.adoc#_transport_endpoint[Runtime & Interaction Model Specification, Transport Endpoint] (web listener), link:specification/store-schemas/12-machine-stores.adoc#web-access-records[Store Schemas Specification, Web Access Records], and link:specification/timeouts/02-runtime-leases-operator-web.adoc#web-access[Timeouts & Budgets Specification, Web Access] for implementation details.
