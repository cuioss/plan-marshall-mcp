== Security & Trust Model (PM-SEC)

[#PM-SEC-1]
=== PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment

The security architecture of `PM-MCP` enforces a strict dual-boundary security model separating the host runtime from the MCP server, and contains untrusted content encountered during execution.

* The system must enforce a two-boundary security model comprising:
** An internal PM-MCP tool boundary where all state transitions are closed enumerations, parameters are schema-validated, workspace access is server-confined, job execution is verified against operator enrolment, and operator capabilities are omitted.
** An external host tool boundary governing the AI model's native file and shell access outside PM-MCP's direct control.
* The system must give read-only model jobs (Q-Gate, triage, security audit, lessons author, architecture enrichment, epic decomposition and re-grounding, lessons review) no file-writing tools and reach PM-MCP only through their job-bound connection, limited to their own entity's links (`PM-WF-5`), and must give the injection screener job zero tools and no PM-MCP connection, so that untrusted or speculative reasoning paths cannot alter plan state beyond their entity's validated submissions.
* The system must tag all external content—including repository code, build definitions, pull request comments, review-bot outputs, and responses from upstream MCP servers—with provenance metadata (for proxied upstream content, the `_meta` key `de.cuioss.pm-mcp/source`, `PM-SVC-3`) and treat it as untrusted.
* The system must treat repository configuration (`.git/config` and its includes, `.gitattributes`, `.gitmodules`, hook directories, and the user's global git configuration as read by an in-process operation) as untrusted input: the native git variant reads only an allowlist of content-shaping keys and ignores every other key (among them `credential.*`, `core.sshCommand`, `core.fsmonitor`, `http.*` proxy settings, and includes outside the repository), never starts a process named by repository content (hooks, filter drivers, signing programs, `core.fsmonitor`) but refuses such an operation with `capability_missing`, and sends the agent credential only after the origin check of the effective remote URL (`PM-CRED-5`).
* The system must prohibit state machine transitions derived solely from untrusted external content; external review-bot comments or CI statuses may create findings or trigger verification checks, but must never directly mark a quality gate green or bypass a merge barrier.
* The system must pass every externally authored free text (issue and pull-request titles and bodies, review comments and bot findings, analysis-provider messages, and upstream MCP results entering a store) through two guards before it reaches a model as content, and CI log and build excerpts (the output of its own jobs) through the first guard only:
** Level 1, the deterministic validator of the server and the containment boundary: a Unicode stage run to a fixpoint (tag characters, variation selectors, format, control, private-use and unassigned code points, lone surrogates, and terminal escape sequences removed; content normalized to NFC and a normalized copy used for detection), a Markdown syntax-tree stage (`org.commonmark:commonmark`: images removed, links outside the operator's optional domain allowlist neutralized, raw HTML and HTML comments removed, exfiltration-shaped URLs flagged, extracted URLs validated), length bounds, a closed schema for every structured field (undeclared keys rejected), and a rule table whose matches are risk signals and findings, never a gate on their own; every change is reported, never silently dropped, and the text is delivered to a model only inside spotlighting delimiters that mark it untrusted.
** Level 2, a zero-tool screener job (`PM-WF-5`) that receives the level-1-cleaned texts of one source or gather firing as one server-built batch (split above a size bound; texts already screened in the scope are taken from a cache keyed by their SHA-256) and returns a closed verdict per text (`clean` or `suspicious` with the flagged spans), validated by the server; the screener can only restrict, never grant: a missing, extra, or unparseable verdict counts as `suspicious`, and screened text stays marked untrusted.
** A `suspicious` text in a bootstrap source is shown with its flagged spans in a link state whose `accept` (audited; the text stays marked untrusted) or `back` the model follows after relaying the user's choice; inside a plan the text is withheld and only its structured fields (author, file, line, kind) are delivered, the finding stays pending until its unit ends through its budget and fallback (the hand-back report lists the withheld items), and only a `met` waiver of that finding lets the plan proceed.
* The system must record the repository state of the main checkout and active worktrees at task start, and verify realized changes at task submit and inside the commit operation itself, before every commit of every caller (plan, epic, and workspace scope), whichever link or state leads to it; any change detected outside the assigned worktree, any change inside it to a wrapper's pinned build files (`PM-EXEC-1`) or to a protected path, and any main-checkout change since the plan's entry baseline must raise a footprint-violation condition on the scope's current state (`PM-WF-3`) with an explanatory finding, make no commit, and restrict offered links to the bounded self-remedy `fix`, after whose budget the plan takes its phase's fallback; this guard is never waivable. A change inside the worktree beyond the plan's declared footprint is no violation: it is committed and recorded as an unplanned change (`PM-WF-11`).
* The system must offer the model a self-report link that records an action taken outside the server (including a bypass of a sanctioned path) as an audited event and a finding, and must document as an accepted residual risk that host-side reads of `<PM_MCP_BASE>/projects/**` and unreported host actions are not observable.

[#PM-SEC-2]
=== PM-SEC-2: Workspace Confinement & Path Traversal Prevention

To prevent unauthorized file modifications or cross-project data leakage, all PM-MCP file and repository operations must be strictly confined to the enrolled repository root and its active worktrees.

* The system must resolve the project at session entry (`pm-mcp enter`) and for every `PM-MCP-Workspace` header by one rule (git top-level and common git directory mapped to an enrolled project root; a worktree only under `.marshall/local/worktrees/`) and record the resolved `project_id` and entry origin, never a path, in the scope's session log.
* The system must derive workspace confinement exclusively from server-verified data: the `PM-MCP-Workspace` header resolved against the enrolment for workspace-addressed requests and the enrolled project root of the scope's per-project machine store for scope-addressed requests (`PM-ARCH-4`); client-declared MCP roots are advisory and never widen or narrow the confinement.
* The system must canonicalize all paths (resolving all symbolic links) for every filesystem, git, and build operation, asserting that the target path resides within the enrolled workspace root or a live linked git worktree whose git common directory resolves to that root.
* The system must reject any path traversal attempt (including directory traversal sequences `..`, absolute paths outside the workspace, or symlinks pointing outside the root) with an explicit `path_traversal_rejected` error outcome.
* The system must forbid AI models from specifying raw filesystem paths for state manipulation; all target scopes (`plan_id`, `epic_id`) must be resolved server-side from persisted state.
* The system must admit cross-project access (such as multi-repo epic landing or dependency verification) only under an operator grant: the operator issues it on the operator's own initiative (`pm-mcp operator grant-access <plan_id> <project_id> read|read-write --reason <text>`), limited to enrolled projects and to the plan's lifetime, and the runtime records it append-only in the plan's store and in the audit log; the model never requests one through a link, and an access without a grant raises the `precondition_unmet` condition naming the operator command (`PM-WF-3`), whose bounded retry ends in the phase's fallback.

[#PM-SEC-3]
=== PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)

Privileged operations that alter machine configuration, security posture, or project boundaries must be strictly isolated from the AI model's capability surface.

* The system must exclude all operator-only capabilities—including project enrolment and harness enrolment, setting and revoking waivers, aborting a plan or an epic, resolving an integrity breach, deleting plan directories, and granting cross-project access—from the MCP tool surface and link emissions.
* The system must reject any attempt to execute operator-only actions via `pm_do` regardless of supplied arguments, and must limit a model job's connection to its role's tool set and its own entity's links (`PM-WF-5`).
* The system must provide exactly two isolated channels for operator overrides (waivers, `abort`, integrity resolutions, plan deletion, cross-project access grants, operator configuration, `PM-WF-12`) and must accept MCP elicitation only for the operator-configuration choices the server raises itself (such as the integration variant) and for content questions delivered per `PM-WF-12`; none of them routes through the AI model, an override is never taken as a content answer, and a content answer given through elicitation or a paired device is never an override; the channel of every privileged action is recorded in the audit log:
** Operator CLI (`pm-mcp operator <verb>` and `pm-mcp web <verb>`): Operator verbs that the CLI accepts only when it is attached to an interactive terminal (`System.console().isTerminal()`) and none of the host agent environment markers is present, that ask for interactive confirmation, and that the CLI then sends to the runtime's local API, which executes them; the host deny rules installed with the client bundles (`Bash(pm-mcp operator:*)`, `Bash(pm-mcp web:*)`) are defence in depth. No passphrase, operator session, or operator credential exists in the first iteration.
** Paired web device: A browser paired through an operator verb, which has the operator's rights except the CLI-only actions (`PM-SEC-7`).
* The system must never wait for an operator decision: no operator verb resolves a pending decision, and the operator acts on the operator's own initiative through `pm-mcp operator waive` / `unwaive` / `waivers`, `abort`, `accept-edit`, `delete-plan`, `grant-access`, `enrol-harness`, `credentials`, `config`, and `continuation-policy`, each through the same local API endpoints the web app uses. Where a condition needs the operator (an integrity breach, a missing credential or operator setting), its representation names the matching operator command as text the model relays, never as a link.
* The system must document as an accepted residual risk that the CLI's operator checks guard only against accidental and naive invocation: a model-driven shell that deliberately defeats them (a pseudo-terminal, a cleared environment, indirect invocation) can run operator verbs, and, because the runtime cannot verify the CLI's checks, any process of the same OS user that holds the runtime token can call the operator endpoints of the local API directly; a user proof the model cannot produce is deferred (link:later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/runtime-model.adoc#local-api[Runtime & Interaction Model Specification] (operator endpoints of the local API), link:specification/mcp-tools.adoc[MCP Tools & Resources Specification], link:specification/workflow-dsl.adoc[Workflow DSL Specification], link:specification/store-schemas.adoc[Store Schemas Specification] (waiver record), and link:specification/timeouts/02-runtime-leases-operator-web.adoc#operator-waivers-questions[Timeouts & Budgets Specification] (waiver and question waits) for implementation details.

[#PM-SEC-4]
=== PM-SEC-4: Local Transport Isolation, Zero Network Exposure & Stream Hygiene

By connecting hosts over `stdio` and relaying to the runtime over a user-private Unix domain socket, `pm-mcp` eliminates network-borne attack vectors (DNS rebinding, cross-origin browser requests, unauthorized local TCP port access, and SSH port-forwarding leaks) and enforces strict OS-level process and stream isolation.

* The runtime must open zero TCP or UDP listeners in any production execution mode; its only listener must be a Unix domain socket with mode `0600` inside a `0700` directory owned by the active OS user, serving the MCP endpoint and the local API and never serving either to a browser. Should the Milestone 1 verification rule out the domain-socket listener, the only permitted substitute is a listener bound to `127.0.0.1` that requires the runtime token and rejects every request with a foreign `Host` or any `Origin` header.
* The system must authenticate every local request with the runtime token: a fresh 256-bit secret that the runtime writes atomically at every start, before binding, to `<PM_MCP_BASE>/run/runtime.token` (mode `0600`, directory `0700`), that every client reads only after verifying owner, mode, and the absence of symlinks, that is never logged, passed as an argument, or exported to a job, and that no job can read on Linux (outside the Landlock read set); the peer UID may additionally be checked where the listener exposes it, but is never required.
* The system must authenticate a model job's connection only with its own job token: a fresh 256-bit secret minted at the job's spawn, stored only as its SHA-256 in the job record, valid only while the job runs, passed in the job's environment to the job relay `pm-mcp serve --job`, which sends it as `PM-MCP-Job-Token` in place of the runtime token, and accepted on the MCP endpoint only; per request the runtime refuses a scope or entity other than the job's (`job_scope_mismatch`) and any call after the job ended (`job_ended`).
* The system may open a TCP listener only in the optional web server (`pm-mcp-web`), off by default and started only by an operator verb, on loopback over HTTP or on the LAN only over TLS, never serving the MCP endpoint (`PM-SEC-7`).
* The system must enforce strict `stdout` stream hygiene in the `pm-mcp serve` relay: `stdout` is reserved exclusively for newline-delimited JSON-RPC 2.0 MCP messages, while all diagnostics are routed strictly to `stderr`; the runtime writes its diagnostics to `<PM_MCP_BASE>/logs/daemon.log`.
* The system must redirect `stdout` and `stderr` of all spawned child subprocesses (`build`, `git`, `ci`, `project_script`, `llm`, and warm LSP servers) to dedicated capture pipes or log files, never allowing a child process to inherit a descriptor connected to a host.
* The system must create every file under `<PM_MCP_BASE>` with mode `0600` and every directory with mode `0700`, and must refuse startup unless `<PM_MCP_BASE>`, `enrolments/`, and `run/` are owned by the active OS user with mode `0700` and the files under `state/` with mode `0600`; the `0700` base directory is what protects every other file under it. Enrolment and credential files are checked on every use: an enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` with a foreign owner or a mode broader than `0600` blocks only its project (`enrolment_insecure`), never the runtime start.

[#PM-SEC-5]
=== PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement

Subprocesses spawned by PM-MCP for builds, CLI-variant git and CI provider operations, enrolled project scripts, and model jobs must be executed with sanitized environments and OS-level confinement.

* The system must run native-variant git and provider operations in process without starting any subprocess (`PM-EXEC-5`); `git` and `ci` jobs exist only for the CLI variant, and repository hooks, filter drivers, and signing programs run only inside such a CLI-variant `git` job, started by `git` itself under that job's environment and confinement.
* The system must spawn all subprocesses directly via operating system process creation APIs without invoking intermediate system shells (`/bin/sh` or `/bin/bash`), and place each job in its own distinct process group; the only shell that runs is the interpreter of a committed, enrolled `#!/bin/sh` wrapper (`mvnw`, `gradlew`), which receives the validated argument vector as positional arguments.
* The system must build every subprocess environment from scratch against a strict, specified allowlist (per variable: permitted job types and provenance, enrolment snapshot or runtime-computed), never inheriting the runtime's own environment; the runtime token, device secrets, credential secrets, token variables (`GH_TOKEN`, `GITHUB_TOKEN`, `GITLAB_TOKEN`, every `*_TOKEN`), askpass helpers (`GIT_ASKPASS`, `SSH_ASKPASS`), and flag-injecting variables (`JAVA_TOOL_OPTIONS`, `MAVEN_OPTS`, `GRADLE_OPTS`) must never be exported to child environments; a CLI-variant `git` or `ci` job receives only the listed configuration-discovery variables (`HOME`, the SSH agent socket for an SSH remote, the provider CLI configuration directories) and non-interactive guards, and authenticates with the operator's ambient credentials by design (`PM-CRED-1`); a model job (`llm`) receives only the authentication variables its client profile declares for the harness and that the operator's enrolment captured, and `PM_MCP_JOB_TOKEN` and `PM_MCP_JOB_ID` as the only PM-MCP values, and never a PM-MCP credential.
* The system must pass free-text parameters (such as commit messages, PR descriptions, and outline text) of a subprocess exclusively in memory via standard input (`stdin`) (`PM-EXEC-5`), never via temporary files and never interpolated into command-line arguments; a CLI-variant operation for which the host tool offers no `stdin` form is `unsupported_by_variant`.
* The system must confine every subprocess on Linux before execution, in the job launcher `pm-mcp-exec`:
** `PR_SET_NO_NEW_PRIVS`, so that no job or descendant can gain privileges.
** A Landlock filesystem ruleset (ABI >= 2; a kernel offering only ABI 1 is recorded as `confinement: partial(abi=1)`, never as confined) granting write access only to the job's own project root (including its worktrees and `.marshall/local/temp/`), declared build toolchain caches, the system temporary directory (`/tmp`), device nodes (`/dev`), and for a model job the harness home directories its client profile declares (a model job also keeps network access), and read-only access to the whole filesystem except all of `<PM_MCP_BASE>`, which is neither readable nor writable (`<PM_MCP_HOME>` with the binaries stays readable); the writable set never contains `<PM_MCP_BASE>`, another enrolled project root, or `~/.plan-marshall/`, which adversarial tests prove with a job whose write to `<PM_MCP_BASE>/enrolments/<project_id>.json` fails, whose write to another enrolled project root fails, and whose reads of `<PM_MCP_BASE>/run/runtime.token` and of a credential file under `<PM_MCP_BASE>/credentials/` fail, each with a positive control that the permitted counterpart succeeds (`PM-TEST-5`).
* The system must compute the writable set from the job's project enrolment at every job start, so that enrolment changes take effect for the next job; warm build daemons (Gradle daemon, `mvnd`) are per project and inherit the confinement of the job that started them.
* The system must protect every enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` with its own HMAC-SHA-256 over its canonical content, written by the runtime with every write of the file (operator verbs only) with a key held in the OS keyring under the PM-MCP namespace (operator lane) or, on hosts without a keyring, in `<PM_MCP_BASE>/state/` (mode `0600`); the runtime must verify it before first serving the project after a start and before every verify-not-resolve check (`PM-EXEC-2`), refuse with `enrolment_tampered` and an audit record on mismatch for that project only, and accept a re-baseline only through an operator verb.
* The system must document as accepted residual risks that the enrolment HMAC does not stop a deliberate forgery on hosts without a keyring, where the key file is readable by every process of the same user, nor a re-baseline of a tampered file by a model-driven shell that defeats the operator checks or by a same-user process calling the operator endpoint directly (`PM-SEC-3`).
* The system must document as accepted residual platform risks the absence of equivalent unprivileged sandboxing on macOS, and on Linux kernels without Landlock, where jobs run with `PR_SET_NO_NEW_PRIVS` only and the job record states `confinement: unavailable`.

[#PM-SEC-6]
=== PM-SEC-6: Security Audit Trail & Tamper-Evident Logging

The system must maintain an append-only, tamper-evident audit record of all security-relevant operations, authentication events, and identity assertions.

* The system must record every tool invocation, state machine transition, job submission, credential access, operator action, and model self-report of an action taken outside the server (`PM-SEC-1`) to an append-only JSONL audit log (`<PM_MCP_BASE>/logs/audit.jsonl`).
* The system must chain the audit records: every record must carry `prev_hash`, the SHA-256 of the previous record's canonical line (a defined genesis value for the first record); the runtime must anchor the chain head (record count and head hash) in an HMAC-protected sidecar under the enrolment integrity key, rotate the log only through checkpoint records listed in a hash-chained index, verify incrementally from the last checkpoint at start (full verification on operator demand), and report a broken chain (including a deleted, reset, or truncated log) to the operator and record it in the audit log, never silently repaired; the anchoring is tamper-evident, not tamper-proof, against a process holding the integrity key.
* The system must record three distinct identity layers for every session-bound audited operation (transitions and `enter`), and only the OS principal for machine-level operations:
** The declared client identity (`--client` parameter from entry point).
** The detected environment signature (host detection signals per the link:specification/client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table], or MCP `clientInfo`).
** The authenticated operating system user principal running the process.
* The system must explicitly flag any discrepancy between declared client identity and detected environment signature (`identity_mismatch=true`) in the audit log and return a warning in the state representation.
* The system must never rewrite a recorded measurement or audit fact: a correction is appended as its own record that names the record it corrects, and every measurement record carries the `head_sha` and round it was taken at.
* The system must redact all sensitive credentials, passwords, and tokens, including the runtime token, device secrets, and pairing codes, before writing entries to diagnostic logs or the audit log.
* The system must sanitize error responses returned to AI models, suppressing internal exception traces, stack traces, and local system paths, returning only closed-enum error codes and, for errors the operator must look up (an unhandled server exception, an unreadable document), the unique audit record identifier for operator diagnostics.

[#PM-SEC-7]
=== PM-SEC-7: Optional Web Server, Device Pairing & Browser Channel Hardening

A paired browser may observe and operate the runtime through an optional web server, without widening the runtime's own network exposure and without handing the browser any credential the operator cannot revoke at once.

* The system must deliver browser access through a separate web server process (`pm-mcp-web`) that is a client of the runtime's local API like the CLI, holds no store logic, and is absent unless the operator enables it (`pm-mcp web enable`, or the first `pm-mcp web pair`); the runtime itself keeps zero TCP listeners (`PM-SEC-4`).
* The system must serve the web listener on loopback over HTTP by default and on the LAN only over TLS with a self-generated certificate whose SHA-256 fingerprint the CLI and the pairing page show.
* The system must validate the `Host` header of every request before routing, grant no CORS, and set on every web response the strict Content Security Policy (including `frame-ancestors 'none'` and `require-trusted-types-for 'script'`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer`.
* The system must never make the MCP endpoint `/mcp` reachable through the web server; it must proxy only the local API, including its event streams, to the runtime's Unix socket.
* The system must pair a browser only through a one-time code issued by an operator CLI verb (8 characters, single use, one open pairing, kept only as a hash, with the lifetime and failed-attempt limit of the link:specification/timeouts/02-runtime-leases-operator-web.adoc#web-access[Timeouts & Budgets Specification, Web Access]) exchanged for a per-device secret of 256 bits that the runtime stores only as a SHA-256 hash and never logs.
* The system must check the device secret forwarded by the web server in the runtime on every request and on every event-stream connect, without a cache, so that a revocation ends the device's streams and rejects its next request; the web server alone must never decide that a device is valid.
* The system must let the operator list and revoke paired devices individually or all at once, expire a device after the link:specification/timeouts/02-runtime-leases-operator-web.adoc#device-idle-expiry[device idle expiry] without use, and record every pairing, failed pairing attempt, and revocation in the audit log (`PM-SEC-6`).
* The system must treat every paired device as an operator channel with the operator's rights, except the CLI-only actions (issuing pairing codes, starting or stopping the web server, entering credential secrets), and audit every action with its channel and device; roles and step-up are deferred (link:later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]), as are OAuth, token rotation, and sender-constrained credentials (link:later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).

See the link:specification/cli-and-security/03-web-server.adoc#web-server[CLI, Coordination & Security Specification, Web Server & Pairing], the link:specification/store-schemas/12-machine-stores.adoc#web-access-records[Store Schemas Specification, Web Access Records], and the link:specification/timeouts/02-runtime-leases-operator-web.adoc#web-access[Timeouts & Budgets Specification, Web Access] for implementation details.
