== Credential Management (PM-CRED)

[#PM-CRED-1]
=== PM-CRED-1: Dual-Lane Credential Separation (System vs Token Lane)

External provider authentication must be partitioned into a System Lane, in which the operator's host CLI tools act with the operator's own authentication, and a Token Lane managed by the daemon's credential stores, in which `PM-MCP` acts with an agent identity.

* The system must classify every external provider declaratively in domain support into either the *System Lane* or the *Token Lane*; for the `git`, `github`, and `gitlab` integrations the lane follows the project's integration variant (`PM-EXEC-5`): the native variant is Token Lane, the CLI variant is System Lane.
* The system must hold zero credentials for System Lane providers (the CLI variant of `git`, `github` through `gh`, `gitlab` through `glab`), delegating authentication by design entirely to the host tool's native stores (git credential helpers, SSH agent, and CLI login profiles), never injecting an agent token into such a job (no `GH_TOKEN`, `GITLAB_TOKEN`, or `GIT_ASKPASS` helper), showing the operator, when the operator chooses the CLI variant, that it acts with the operator's own identity, recording `identity: operator_ambient` in the audit record of every such job, and verifying readiness by running the tool's verification command as a job (e.g. `gh auth status`).
* The system must manage credentials for Token Lane providers (REST code-quality services such as Sonar, authenticated upstream MCP servers, and the native variant of the git HTTPS transport, GitHub, and GitLab) within PM-MCP's credential stores and verify them via authenticated requests to the provider's verification endpoint (for GitHub and GitLab the identity read `ci.whoami`, reporting the identity and its permissions on the enrolled repository).
* The system must identify every Token Lane credential by its credential key: `github`, `gitlab`, and `git-https` (any other HTTPS git remote) for the native git and provider integrations; `mcp-<server_id>` for an upstream MCP server (`PM-SVC-3`); otherwise the key the project configuration names for the integration (`credential_key`, for example `sonar`).
* The system must accept as the GitHub agent credential a GitHub App installation (recommended), a fine-grained personal access token, or a classic personal access token, and as the GitLab agent credential a project access token, a group access token, a personal access token of a service user, or the operator's own personal access token, all on equal footing: neither the token type nor a missing expiry is refused or warned about in a workflow (the operator credential status shows a missing expiry, `PM-CRED-4`); a credential that cannot read check runs must yield `completeness: incomplete` on the checks read, never a refusal.
* The system must resolve the committer identity of agent commits from the agent credential (for a GitHub App `<app-slug>[bot]` with its `users.noreply.github.com` address, for a token the token's user as reported by `ci.whoami`), falling back to a fixed `plan-marshall-mcp` noreply identity when no Token Lane provider credential of the project resolves one (for example when every integration uses the CLI variant), and must keep this identity operator-visible only, never in model-facing representations.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] and link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-CRED-2]
=== PM-CRED-2: OS Credential Store Priority & Native Access

The operating system's native credential store must serve as the primary repository for Token Lane secrets, resolved ahead of file-based fallbacks.

* The system must prioritize the operating system credential store for all Token Lane credentials and the enrolment integrity key (the only operator-lane secret; no operator credential, token, or passphrase is stored), using PM-MCP's own service name `de.cuioss.pm-mcp` (qualified by the instance directory when a non-default `PM_MCP_BASE` is set, `PM-DIST-5`) and account identifiers `<credential_key>` (global) or `<project>/<credential_key>` (project-scoped).
* The system must integrate with the macOS login Keychain using an Access Control List (ACL) that trusts only the runtime binary `pm-mcpd`, the only process that reads or writes the credential store, ensuring that any read attempt by another process—including a shell driven by the model—triggers an interactive OS confirmation prompt to the user.
* The system must integrate with the Linux Secret Service (`org.freedesktop.secrets` via GNOME Keyring or KWallet) over the D-Bus session Unix domain socket using the JDK's native `UnixDomainSocketAddress` channel.
* The system must use exactly one active credential store per machine: the OS credential store when one is available, otherwise the fallback file store (`PM-CRED-3`); a secret never exists in both. Within the active store it must resolve the project entry before the global entry, selecting the first complete entry and skipping entries marked with placeholders.
* The system must automatically fall back to the file credential store when an OS credential store is unavailable (such as headless Linux environments without an unlocked keyring or Windows WSL sessions).
* The system must never read keyring entries of legacy `plan-marshall` (`PM-MIG-2`); credentials enter `PM-MCP` only through `pm-mcp operator credentials`.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] and link:specification/filesystem-layout.adoc[Filesystem Layout Specification] for implementation details.

[#PM-CRED-3]
=== PM-CRED-3: Permission-Guarded Fallback File Credential Store

When the OS credential store is unavailable, secrets must be stored in a permission-guarded directory of PM-MCP's own instance directory, in PM-MCP's own versioned credential file format.

* The system must read and write the fallback file credential store at `<PM_MCP_BASE>/credentials/`, global entries at `<credential_key>.json` and project entries at `<project>/<credential_key>.json`; every file carries `format_version` and follows a closed schema, is written only by `pm-mcp operator credentials`, and a file in another format or version is refused with a reason naming the file and field.
* The system must never read `~/.plan-marshall/credentials/`, `PLAN_MARSHALL_CREDENTIALS_DIR`, or `PLAN_MARSHALL_HOME` (`PM-MIG-2`); legacy credential files are never imported.
* The system must use as `<project>` the project's enrolment identifier, the name of its enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (`PM-EXEC-2`): assigned by the operator, unique per machine, and identical for the main checkout and all its worktrees; it is never derived from a remote URL or a checkout path.
* The system must enforce POSIX directory permissions of `0700` on the credential store directory and `0600` on every credential file, creating files atomically with `0600` mode and verifying permissions immediately after creation.
* The system must canonicalize all resolved credential file paths to prevent directory traversal outside `<PM_MCP_BASE>/credentials/` and must sanitize `<project>` names strictly to `[a-zA-Z0-9._-]`.
* The system must support the credential schema of `PM-MCP`: `url`, `auth_type` set to `token` (with optional `header_name` and `header_value_template`, defaulting to `Authorization` and `Bearer {token}`), `basic` (with `username` and `password`), or `github_app` (with `client_id`, the PKCS#8 `private_key`, and an optional `installation_id`), the provider token kind determined from the provider at `set` and `verify` (GitHub fine-grained or classic personal access token; GitLab project, group, or personal access token), an optional `expires_at`, and `verified_at`; the `plan-marshall` values `none` and `system` have no credential entry.
* The system must include defense-in-depth host file-tool deny rules covering `<PM_MCP_BASE>/**`, and with it `<PM_MCP_BASE>/credentials/`, when installing client bundles (`pm-mcp client install`).

See the link:specification/filesystem-layout.adoc[Filesystem Layout Specification], link:specification/store-schemas.adoc[Store Schemas Specification], and link:specification/client-profiles.adoc[Client Profiles Specification] for implementation details.

[#PM-CRED-4]
=== PM-CRED-4: Operator-Only Secret Entry & Zero Model Exposure

Secrets must be entered exclusively by the human operator and must never be exposed to the model or passed through CLI flags.

* The system must restrict all credential configuration and lifecycle operations exclusively to the operator CLI (`pm-mcp operator credentials`), executed by the runtime through its local API; the runtime must refuse the entry of a secret from a web-originated request.
* The system must read secrets interactively from the terminal with echo disabled during `pm-mcp operator credentials set <credential_key> [--project]`, for the OS credential store and the file store alike (the CLI sends the secret to the runtime only in the body of one local API request over the Unix domain socket and keeps no copy; for the file store the runtime writes the complete credential file atomically; no placeholder or hand-edited credential file exists, and a file the runtime did not write in the current format is refused), strictly prohibiting secrets in CLI arguments or environment variables.
* The system must provide operator credential management subcommands: `status` (displaying serving store, verification status, and expiry without revealing secret values: `expiring` within the link:specification/timeouts/02-runtime-leases-operator-web.adoc#credential-expiring-window[credential expiry warning window] before `expires_at`, and a notice for an entry without a known expiry), `check` (verifying completeness), `verify` (testing provider authentication and reporting the resolved identity and its permissions), `rotate` (replacing the secret of an existing entry), `remove` (deleting an entry), and `migrate` (transferring a file-store entry into the OS credential store and deleting the file).
* The system must keep the closed-enum credential status indicators (`complete`, `incomplete`, `not_found`, `verified`, `unverified`, `expiring`) operator-only: they appear in the operator CLI and `pm-mcp status`, never in a model-facing representation; the workflow engine uses them only to decide the `precondition_unmet` condition below, whose representation names the reason and the operator command, never the credential details.
* The system must transition any workflow step requiring a missing or incomplete credential, or a credential whose file fails the ownership or permission checks (`PM-CRED-3`), into the `precondition_unmet` condition on its current state (`PM-WF-3`, reasons `credential_missing`, `credential_check_failed`, `credentials_file_insecure`), whose representation specifies the exact `pm-mcp operator credentials` command as relay text and offers only its bounded `retry` (the operator may set the credential at any time), after which the plan takes its phase's fallback (a hand-back that needs the missing credential degrades to a local branch, the gap stated in the landing record); a credential is never waivable; an insecure credential file must block only the steps that need it, never the runtime start.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-CRED-5]
=== PM-CRED-5: Outbound Domain Scoping & Output Secret Redaction

Token Lane secrets must be held in memory only during active requests, scoped strictly to their issuing HTTPS origin, and redacted from all outputs.

* The system must read a Token Lane secret from the credential store only at the moment of an outbound HTTP request, retain it for use in memory solely for the duration of that request, and never cache it for reuse, persist it elsewhere, or pass it to subprocesses; there are exactly two named exceptions:
** an in-memory redaction registry of resolved secret values, kept for the runtime's lifetime and used solely to scrub output, which is never persisted and never exported to subprocesses or logs;
** short-lived tokens derived from a stored secret (GitHub App installation tokens), held in memory per installation and permission set until the link:specification/timeouts/03-retention-host-config.adoc#derived-token-reuse-margin[derived token reuse margin] before their expiry, registered with the redaction registry, never persisted, never exported, never passed to a subprocess, and dropped on credential rotation, removal, or revocation and on runtime stop; the stored secret they derive from keeps the per-request rule.
* The system must enforce HTTPS with full TLS certificate and hostname verification for all Token Lane requests, transmit credentials exclusively to the origin of the `url` of the operator-owned credential entry and, for the `github` and `gitlab` entries, to the API origin the provider module derives from it by a compiled rule (team configuration such as `.marshall/config/project.json` may only reference a credential key and never determines where a token is sent), and abort any HTTP redirect to a plain `http://` URL as an error.
* The system must apply the same origin pinning to the native git transport: the effective fetch and push URL of the remote, resolved with every `url.<base>.insteadOf`/`pushInsteadOf` rewrite and `remote.<name>.pushurl`, must be `https` (after the mapping of an SSH remote of a known provider host to its HTTPS form) and its origin must equal the credential entry's origin; otherwise the operation is refused with `remote_origin_mismatch` and a security record in the audit log, and no request carrying the credential is sent.
* The system must prohibit credential passthrough in the MCP proxy, authenticating to each upstream MCP server exclusively with PM-MCP's own configured credential for that server and never forwarding tokens received from a host or another server.
* The system must redact and strip all secret values from tool results, state representations, error payloads, diagnostic logs, and the audit log, sanitizing upstream provider error responses before logging or returning them.
